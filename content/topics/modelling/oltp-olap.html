OLTP vs OLAP

Kern: OLTP (Online Transaction Processing) ist ein Workload mit vielen kleinen Schreib- und Lesezugriffen auf einzelne Zeilen. OLAP (Online Analytical Processing) ist ein Workload mit wenigen grossen Leseabfragen über Millionen Zeilen. Darum braucht OLTP einen Row Store mit normalisiertem Modell, OLAP einen Column Store mit dimensionalem Modell.

1. Wo sitzen OLTP und OLAP?

  1. Anwendung: schreibt Bestellungen, Trades, Buchungen. Beispiel: INSERT eines Trades.
  2. OLTP-DB: speichert den aktuellen Zustand. Sie garantiert ACID (Atomarität, Konsistenz, Isolation, Dauerhaftigkeit) pro Transaktion.
  3. ETL/ELT: kopiert die Daten weg. CDC (Change Data Capture) liest Änderungen aus dem Log, Batch liest periodisch.
  4. OLAP-System: Warehouse oder Lakehouse. Es hält die Historie und ist für grosse Scans gebaut.
  5. BI: Dashboards und Reports lesen nur das OLAP-System, nicht die OLTP-DB.

2. Die Reise einer Analyse-Abfrage (die Geschichte zum Merken)

  1. Die Frage kommt: „Wie viel MWh pro Monat?“ Die Abfrage braucht nur datum und volume.
  2. Im Row Store: PostgreSQL speichert eine Tabelle als Heap, also Seiten von meist 8 kB mit ganzen Zeilen. Ein Seq Scan liest jede Seite komplett. Die breite xml-Spalte kommt mit, obwohl niemand sie braucht.
  3. Im Column Store: Jede Spalte liegt separat, z. B. in Parquet-Dateien (spaltenorientiertes Dateiformat). Die Engine liest nur die zwei benötigten Spalten: Projection Pushdown.
  4. Kompression: Eine Spalte hat gleichartige Werte. Dictionary- und Run-Length-Encoding machen sie sehr klein.
  5. Überspringen: Jede Row Group speichert Min/Max-Statistiken pro Spalte. Ein Filter datum >= '2026-01-01' überspringt ganze Blöcke: Predicate Pushdown.
  6. Rechnen: Die Engine summiert ganze Vektoren von Werten auf einmal: vektorisierte Ausführung. Das Ergebnis sind 12 Zeilen statt 100 Millionen.
  7. Kehrseite: Ein UPDATE einer einzelnen Zeile ist im Column Store teuer. Darum schreibt man dort in Batches.

3. Beispiel: Row Store liest ganze Zeilen

Gleiche 100 000 Trades, einmal breit (mit 400 Byte Payload), einmal nur mit den zwei Spalten, die die Abfrage braucht. Das simuliert den Effekt eines Column Stores.

4. Details, die Interviewer fragen

  1. Workload-Merkmale OLTP: kurze Transaktionen, Zugriff über Primärschlüssel oder Index, viele parallele Nutzer, aktueller Zustand. Beispiel: „Trade T1 speichern“.
  2. Workload-Merkmale OLAP: lange Leseabfragen, Scans über viele Zeilen, wenige Spalten, Aggregationen, Historie. Beispiel: „Volumen pro Monat und Land“.
  3. Normalisiert (3NF): Jeder Fakt steht genau einmal. Das verhindert Update-Anomalien (gleiche Information an zwei Stellen widersprüchlich). Preis: viele Joins beim Lesen.
  4. Dimensional: Das Modell trennt Fakten (Messwerte, z. B. MWh) von Dimensionen (Kontext, z. B. Datum, Partner). Dimensionen sind bewusst denormalisiert. Ziel: einfache, schnelle Abfragen.
  5. Warum denormalisieren im OLAP erlaubt ist: Die Daten werden per ETL geladen, nicht von Nutzern geändert. Die Pipeline garantiert die Konsistenz, nicht die Normalform.
  6. Row Store: speichert alle Spalten einer Zeile zusammen. Gut für Insert, Update und Lookup ganzer Zeilen. Beispiel: PostgreSQL-Heap, SQL Server Rowstore.
  7. Column Store: speichert jede Spalte zusammen. Gut für Scans weniger Spalten und Kompression. Beispiel: Parquet, ORC, Dremio, ClickHouse, SQL Server Columnstore Index.
  8. Updates im Column Store: Dateien sind meist unveränderlich. Änderungen laufen als Copy-on-Write (Datei neu schreiben) oder Merge-on-Read (Delete-Dateien, beim Lesen verrechnen). Beispiel: Apache Iceberg kann beides.
  9. Lange Analysen auf PostgreSQL: Eine lange Transaktion hält einen alten Snapshot. VACUUM darf tote Zeilen dann nicht entfernen. Die Tabellen wachsen (Bloat).
  10. Read Replica als Zwischenlösung: Reports laufen auf einer Kopie. Auf einem Hot Standby können lange Abfragen aber mit der Replikation kollidieren und abgebrochen werden.
  11. HTAP (Hybrid Transactional/Analytical Processing): ein System für beide Workloads, z. B. Row Store plus Spaltenkopie. Es reduziert Kopien, ist aber ein Kompromiss.
  12. Datenfrische: OLAP ist eine Kopie. Batch heisst Stunden alt, CDC heisst Sekunden bis Minuten. Die nötige Frische bestimmt die Architektur.

5. Vergleich

  • Ziel: OLTP = Geschäft abwickeln. OLAP = Geschäft verstehen.
  • Abfrage: OLTP liest und schreibt wenige Zeilen per Key. OLAP scannt Millionen Zeilen, liest wenige Spalten.
  • Daten: OLTP = aktueller Zustand. OLAP = Historie, oft mit Versionen (SCD2).
  • Speicher: OLTP = Row Store, B-Tree-Indizes. OLAP = Column Store, Partitionen, Min/Max-Statistiken.
  • Modell: OLTP = 3NF. OLAP = Star Schema (Kimball), Data Vault als Integrationsschicht oder One Big Table.
  • Schreiben: OLTP = viele Einzel-Transaktionen. OLAP = Bulk-Loads, Append, MERGE in Batches.
  • Kennzahl: OLTP = Latenz in ms und Transaktionen/s. OLAP = Scan-Durchsatz und Abfragezeit in Sekunden.

6. In der Produktion

  1. Reports bremsen die operative DB: Grosse Scans verdrängen den Cache und belegen CPU. Fix: Analytik auf eine Kopie verlagern (Replica, Warehouse, Lakehouse).
  2. Bloat durch lange Abfragen: Eine stundenlange Report-Transaktion blockiert VACUUM. Fix: statement_timeout für Report-User, Reports woanders ausführen.
  3. Kleine Dateien im Column Store: Viele kleine Batches erzeugen tausende kleine Parquet-Dateien. Scans werden langsam. Fix: grössere Batches, regelmässige Compaction.
  4. Einzel-Updates im Lakehouse: Jeder Update schreibt Dateien neu oder erzeugt Delete-Dateien. Fix: Änderungen sammeln und als ein MERGE pro Batch schreiben.
  5. SELECT * auf Column Store: liest alle Spalten und zerstört den Vorteil. Fix: nur benötigte Spalten abfragen, schmale Views für BI.
  6. Zahlen weichen ab: OLTP zeigt live, OLAP den Stand vom letzten Load. Fix: Ladezeitpunkt im Report anzeigen, Frische-SLA vereinbaren.

7. Diagnose: Werkzeuge und Abfragen

  • EXPLAIN (ANALYZE, BUFFERS): wie viele Seiten eine Abfrage liest. Hohe Buffer-Zahl bei kleinem Ergebnis = Scan-Workload.
  • pg_stat_statements: welche Abfragen am meisten Zeit und I/O verbrauchen.
  • SELECT pid, now() - xact_start, query FROM pg_stat_activity ORDER BY 2 DESC;: lange Transaktionen finden.
  • pg_relation_size, pg_stat_user_tables.n_dead_tup: Tabellengrösse und tote Zeilen (Bloat-Hinweis).
  • Iceberg-Metadatentabellen, z. B. SELECT * FROM db.tbl.files in Spark: Anzahl und Grösse der Dateien.
  • Spark UI und Dremio Query Profile: gelesene Bytes, übersprungene Dateien, Scan-Zeit.

8. Senior-Punkte

  1. Workloads trennen ist die wichtigste Entscheidung. Das Modell folgt dem Workload, nicht umgekehrt.
  2. Nicht zu früh ein Warehouse bauen. Bei wenigen GB reichen PostgreSQL, eine Replica und Materialized Views oft aus.
  3. Frische ist eine Anforderung. Erst fragen: „Wie alt dürfen die Zahlen sein?“ Dann Batch oder CDC wählen.
  4. Column Stores kosten beim Schreiben. Updates, Deletes und kleine Batches brauchen Compaction und Wartung.
  5. Normalisierter Kern, dimensionale Marts: Integration sauber halten, für Nutzer einfach denormalisiert ausliefern.
  6. Analytische Daten sind reproduzierbar: Rohdaten aufbewahren, dann lässt sich jede Schicht neu rechnen.

10. Fallen

  • „Ein Column Store ist einfach schneller.“ → Nur für Scans weniger Spalten. Für Einzel-Inserts und Updates ist er langsamer.
  • „Denormalisierung ist immer schlecht.“ → Im OLTP ja, wegen Anomalien. Im OLAP ist sie gewollt, die Pipeline sichert die Konsistenz.
  • „OLAP heisst OLAP-Cube.“ → Nein. OLAP ist der Workload. Ein Cube ist nur eine mögliche Technik, heute meist Star Schema auf Column Store.
  • „Eine Read Replica löst alles.“ → Sie entlastet den Primary, bleibt aber ein Row Store mit 3NF-Modell. Grosse Scans bleiben langsam.
  • „Ein Index macht die Monatsauswertung schnell.“ → Kaum. Sie liest die meisten Zeilen; ein Index hilft bei selektiven Abfragen.

11. Fragen

Was ist der Unterschied zwischen OLTP und OLAP?

OLTP sind viele kleine Transaktionen auf einzelnen Zeilen, z. B. Trades speichern. OLAP sind wenige grosse Leseabfragen mit Aggregation über viele Zeilen und Historie.

Was ist ein Row Store, was ein Column Store?

Ein Row Store speichert alle Spalten einer Zeile zusammen. Ein Column Store speichert die Werte einer Spalte zusammen. Der erste passt zu Zeilenzugriffen, der zweite zu Scans weniger Spalten.

Warum ist ein Column Store für Analysen schneller?

Er liest nur die benötigten Spalten, komprimiert sie stark und überspringt Blöcke per Min/Max-Statistik. Dazu kommt vektorisierte Ausführung.

Warum ist ein Column Store schlecht für OLTP?

Eine Zeile ist auf viele Spalten-Dateien verteilt. Einzel-Insert oder Update muss viele Stellen ändern oder Dateien neu schreiben.

Was ist Projection Pushdown?

Die Engine liest nur die Spalten, die die Abfrage braucht. Im Column Store spart das direkt I/O.

Was ist Predicate Pushdown?

Filter werden bis zum Speicher geschoben. Mit Min/Max-Statistiken pro Block oder Partition werden ganze Blöcke übersprungen.

Warum normalisiert man OLTP-Datenbanken?

Jede Information steht genau einmal. Das verhindert Update-Anomalien und hält Schreibvorgänge klein.

Warum denormalisiert man im Warehouse?

Weniger Joins, einfachere SQL für Nutzer und BI-Tools. Die Daten ändern sich nur per ETL, darum entstehen keine Anomalien durch Nutzer.

Was ist ein dimensionales Modell?

Ein Modell mit Faktentabellen (Messwerte auf festem Grain) und Dimensionstabellen (beschreibender Kontext). Das bekannteste ist das Star Schema nach Kimball.

Ist PostgreSQL ein Row Store?

Ja. Tabellen sind Heaps aus Seiten mit ganzen Zeilen. Spaltenspeicher gibt es nur über Extensions oder externe Engines.

Warum schaden lange Report-Abfragen einer PostgreSQL-OLTP-DB?

Sie belegen CPU und Cache. Und ihr alter Snapshot verhindert, dass VACUUM tote Zeilen entfernt, was Bloat erzeugt.

Reicht eine Read Replica für Reporting?

Für moderate Reports oft ja. Bei grossen Scans und Historie nicht, und auf einem Hot Standby können lange Abfragen wegen Replikationskonflikten abbrechen.

Was ist CDC?

Change Data Capture liest Änderungen aus dem Transaktionslog der Quelle. So bekommt das OLAP-System Änderungen in Sekunden, ohne die Quelle mit Abfragen zu belasten.

Was ist HTAP?

Ein System für Transaktionen und Analysen zugleich, meist mit Row Store plus Spaltenkopie. Spart Pipelines, ist aber ein Kompromiss bei Last und Isolation.

Wie gehen Lakehouse-Formate mit Updates um?

Copy-on-Write schreibt betroffene Dateien neu. Merge-on-Read schreibt Delete-Dateien und verrechnet beim Lesen. Iceberg unterstützt beide.

Was ist das Small-Files-Problem?

Viele kleine Dateien erzeugen viel Metadaten- und Öffnungsaufwand bei Scans. Lösung: grössere Batches und regelmässige Compaction.

Warum ist SELECT * auf einem Column Store schlecht?

Es liest alle Spalten und hebt den Vorteil des Spaltenspeichers auf. Nur benötigte Spalten abfragen.

Wann brauchen Sie kein separates Warehouse?

Bei kleinen Datenmengen und einfachen Reports. Dann reichen Replica, Materialized Views oder ein Reporting-Schema.

Was bestimmt, ob Sie Batch oder Streaming laden?

Die geforderte Datenfrische und wie die Daten ankommen. Minuten-Latenz und Dateilieferungen sprechen für Batch, das ist einfacher idempotent zu machen.

Szenario: Ein Fachbereich will ein Dashboard direkt auf der Produktions-DB. Was sagen Sie?

Ich prüfe Datenmenge und Frische-Bedarf. Für kleine Abfragen eine Replica mit Timeout, sonst eine Kopie im Warehouse/Lakehouse mit dimensionalem Modell.

Szenario: Seit neue Monatsreports laufen, wächst die OLTP-Tabelle stark und wird langsam. Ursache?

Wahrscheinlich lange Transaktionen, die VACUUM blockieren. Prüfen mit pg_stat_activity und n_dead_tup; Reports auslagern und statement_timeout setzen.

Szenario: Abfragen im Lakehouse werden jede Woche langsamer, obwohl die Datenmenge kaum wächst. Woran denken Sie?

An kleine Dateien und viele Delete-Dateien aus häufigen Updates. Prüfen über die Iceberg-Metadatentabellen, dann Compaction und Snapshots aufräumen.
