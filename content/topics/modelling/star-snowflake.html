Star vs Snowflake Schema

Modelling · Tier 1 · Quellen: Kimball Group „Dimensional Modeling Techniques“ (Star Schemas and OLAP Cubes, Snowflaked Dimensions, Outrigger Dimensions, Role-Playing, Degenerate und Junk Dimensions), PostgreSQL 17 Doku (EXPLAIN)

Kern: Ein Star Schema ist eine Faktentabelle in der Mitte mit denormalisierten Dimensionstabellen direkt daneben. Ein Snowflake Schema normalisiert die Dimensionen weiter in Untertabellen. Star heisst weniger Joins und einfache SQL, Snowflake heisst weniger Redundanz, aber mehr Joins.

1. Wo sitzt das Star Schema?

  1. Faktentabelle: eine Zeile pro Messereignis, z. B. pro Trade. Sie enthält Fremdschlüssel und Messwerte.
  2. Dimensionstabellen: eine Zeile pro Objekt, z. B. pro Marktteilnehmer. Sie enthalten Text-Attribute zum Filtern und Gruppieren.
  3. Star: jede Dimension hängt direkt an der Faktentabelle. Ein Join pro Dimension.
  4. Snowflake: eine Dimension wird aufgeteilt, z. B. dim_participant → dim_country (gestrichelt). Ein Join mehr.
  5. Platz im Datenfluss: Das Star Schema ist die Präsentationsschicht. Im Lakehouse ist das typisch die Gold-Schicht.

2. Die Reise einer Star-Abfrage (die Geschichte zum Merken)

  1. Die Frage: „MWh und EUR pro Monat, Land und Commodity.“ Alle Gruppierungs-Attribute liegen in Dimensionen.
  2. Dimensionen zuerst: Die Engine liest die kleinen Dimensionen und wendet Filter an, z. B. country = 'CH'.
  3. Hash-Tabellen: Aus jeder gefilterten Dimension baut sie eine kleine Hash-Tabelle über den Surrogate Key.
  4. Fakten scannen: Die grosse Faktentabelle wird einmal gelesen. Jede Zeile prüft ihre Keys gegen die Hash-Tabellen: Hash Join.
  5. Gruppieren: Passende Zeilen werden nach Dimensions-Attributen summiert.
  6. Snowflake: Vor dem Fakten-Join braucht es einen Join Dimension → Unterdimension. Bei kleinen Dimensionen ist das billig. Bei grossen Dimensionen und vielen Ebenen wird es teurer und die SQL länger.

3. Beispiel: Star und Snowflake in PostgreSQL

CREATE TABLE dim_date (date_key int PRIMARY KEY, full_date date, month text, year int);
CREATE TABLE dim_participant (participant_key int PRIMARY KEY, participant_code text,
  name text, country text, participant_type text);
CREATE TABLE dim_product (product_key int PRIMARY KEY, product_name text,
  commodity text, delivery_type text);
CREATE TABLE fact_trade (date_key int REFERENCES dim_date,
  participant_key int REFERENCES dim_participant, product_key int REFERENCES dim_product,
  trade_id text, volume_mwh numeric, value_eur numeric);
-- 3 Tage, 2 Teilnehmer (CH, DE), 3 Produkte (Strom Base/Peak, Gas), 5 Trades

SELECT d.month, p.country, pr.commodity, sum(f.volume_mwh) AS mwh, sum(f.value_eur) AS eur
FROM fact_trade f
JOIN dim_date d         ON d.date_key = f.date_key
JOIN dim_participant p  ON p.participant_key = f.participant_key
JOIN dim_product pr     ON pr.product_key = f.product_key
GROUP BY d.month, p.country, pr.commodity ORDER BY 1,2,3;

Jetzt dieselbe Frage „Volumen pro Commodity“, einmal Star, einmal Snowflake (commodity in eigener Tabelle dim_commodity):

-- Star
EXPLAIN (COSTS OFF) SELECT pr.commodity, sum(f.volume_mwh)
FROM fact_trade f JOIN dim_product pr ON pr.product_key = f.product_key GROUP BY pr.commodity;

  1. Die Star-Abfrage hat einen Join pro Dimension. Alle Attribute zum Gruppieren liegen direkt in den Dimensionen.
  2. Der Plan ist das klassische Muster: Seq Scan auf den Fakten, Hash auf der kleinen Dimension, Hash Join, dann HashAggregate.
  3. Im Snowflake braucht dieselbe Frage einen Hash Join mehr. Bei fünf Dimensionen mit je zwei Ebenen sind es schnell zehn Joins.
  4. Das Ergebnis ist gleich. Der Unterschied liegt in Lesbarkeit, Planer-Aufwand und Join-Kosten.

4. Details, die Interviewer fragen

  1. Denormalisierte Dimension: Hierarchien liegen flach in einer Tabelle, z. B. product → commodity. Kimball empfiehlt das: Nutzer verstehen es leichter und es ist meist schneller.
  2. Snowflaked Dimension: Kimball rät davon ab. Grund: schwer zu navigieren für Business-Nutzer und oft langsamer.
  3. Outrigger: eine Dimension verweist bewusst auf eine zweite Dimension. Beispiel: dim_participant.first_trade_date_key → dim_date. Erlaubt, aber sparsam.
  4. Redundanz ist billig: Dimensionen sind klein im Vergleich zu Fakten. Im Column Store komprimiert ein Dictionary wiederholte Texte fast auf null.
  5. Surrogate Keys (künstliche Integer-Schlüssel) verbinden Fakten und Dimensionen. Sie sind klein und unabhängig vom Quellsystem.
  6. Role-Playing Dimension: eine physische Dimension in mehreren Rollen. Beispiel: dim_date als Handelsdatum und als Lieferdatum, über Views oder Aliase.
  7. Degenerate Dimension: ein Schlüssel ohne eigene Tabelle, direkt in der Faktentabelle. Beispiel: trade_id.
  8. Junk Dimension: sammelt kleine Flags und Codes in einer Tabelle. Beispiel: is_cancelled, order_type statt zehn Mini-Dimensionen.
  9. Galaxy / Fact Constellation: mehrere Faktentabellen teilen dieselben Conformed Dimensions. Beispiel: fact_trade und fact_order nutzen dieselbe dim_participant.
  10. Snowflake ist sinnvoll, wenn eine Unterebene sehr gross ist oder eigene Attribute hat, die viele Dimensionen teilen. Oder wenn ein Tool ein normalisiertes Modell verlangt.
  11. Star Schema und OLAP-Cube: Kimball nennt beide als physische Form desselben dimensionalen Modells. Heute ist das Star Schema auf einem Column Store der Normalfall.
  12. One Big Table (OBT): Fakten und alle Attribute in einer breiten Tabelle. Ohne Joins, aber jede Attributänderung heisst: grosse Tabelle neu schreiben.

5. Vergleich

  • Joins: Star = ein Join pro Dimension. Snowflake = mehrere pro Dimension.
  • Redundanz: Star = Attribute wiederholt in der Dimension. Snowflake = jede Ebene einmal.
  • SQL und BI: Star = einfach, Self-Service geeignet. Snowflake = länger, Nutzer müssen das Modell kennen.
  • Pflege: Star = ETL muss Attribute denormalisieren. Snowflake = näher an der Quelle, einfacher zu laden.
  • Speicher: Snowflake spart etwas Platz in den Dimensionen. Bei Column Stores ist der Unterschied klein.
  • Gegen 3NF: Snowflake ist nur in den Dimensionen normalisiert. Die Faktentabelle bleibt in beiden Formen gleich.
  • Gegen OBT: OBT hat null Joins, aber riesige Rewrites bei Änderungen und keine Wiederverwendung von Dimensionen.

6. In der Produktion

  1. Doppelte Zeilen nach dem Join: Die Dimension hat zwei Zeilen pro Key (z. B. fehlerhafter SCD2-Load). Summen verdoppeln sich. Fix: Unique-Constraint auf den Surrogate Key, Tests auf Eindeutigkeit.
  2. Verlorene Fakten: Ein Fakt hat einen Key, der in der Dimension fehlt. Der Inner Join filtert ihn still weg. Fix: „Unknown“-Zeile in jeder Dimension, Fremdschlüssel nie NULL.
  3. Snowflake-Ketten: BI-Nutzer joinen falsch oder vergessen eine Ebene. Fix: flache Views oder flache Dimensionen für die Präsentation.
  4. Dimension wächst stark: Eine Kunden-Dimension mit Millionen Zeilen und vielen Versionen macht den Hash Join teuer. Fix: schnell wechselnde Attribute in eine Mini-Dimension auslagern.
  5. Fakt-zu-Fakt-Join: Zwei Faktentabellen direkt joinen erzeugt Mehrfachzählung. Fix: jede getrennt aggregieren, dann über Conformed Dimensions zusammenführen (Drill Across).

7. Diagnose: Werkzeuge und Abfragen

  • EXPLAIN (ANALYZE, BUFFERS): Anzahl Joins, Join-Typ, geschätzte gegen echte Zeilen.
  • Eindeutigkeit prüfen: SELECT participant_key, count(*) FROM dim_participant GROUP BY 1 HAVING count(*) > 1;
  • Waisen-Fakten finden: SELECT count(*) FROM fact_trade f LEFT JOIN dim_product p USING (product_key) WHERE p.product_key IS NULL;
  • Summen-Abgleich: sum(volume) auf der Faktentabelle allein gegen dieselbe Summe nach allen Joins. Abweichung = Join-Problem.
  • Dremio Query Profile oder Spark UI: welcher Join wie viele Zeilen erzeugt, Broadcast oder Shuffle.

8. Senior-Punkte

  1. Default ist Star. Snowflake nur mit Grund: sehr grosse Unterebene, geteilte Hierarchie, Tool-Vorgabe.
  2. Modell für Nutzer bauen. Wer Self-Service-BI will, braucht flache Dimensionen mit sprechenden Namen.
  3. Speicher ist selten das Argument. Dimensionen sind klein, Column Stores komprimieren Redundanz weg.
  4. Snowflake im Lade-Modell, Star in der Präsentation ist ein üblicher Kompromiss: normalisiert laden, per View oder Gold-Job flach ausliefern.
  5. Join-Korrektheit testen: Summen vor und nach dem Join vergleichen. Doppelte Dimensionszeilen sind der häufigste stille Fehler.
  6. Verteilte Engines: kleine Dimensionen werden per Broadcast Join verteilt, das ist billig. Grosse Dimensionen erzeugen einen Shuffle.

10. Fallen

  • „Snowflake ist moderner als Star.“ → Nein. Snowflake heisst hier nur „normalisierte Dimensionen“, nicht die Firma Snowflake.
  • „Im Snowflake ist die Faktentabelle normalisiert.“ → Nein. Nur die Dimensionen sind aufgeteilt.
  • „Star Schema verschwendet viel Speicher.“ → Kaum. Die Redundanz liegt in kleinen Dimensionen, die Fakten sind gleich gross.
  • „Mehr Normalisierung ist immer sauberer.“ → Im OLAP zählt Lesbarkeit und Abfragezeit. Die Konsistenz sichert der ETL.
  • „Zwei Faktentabellen kann man direkt joinen.“ → Das zählt doppelt. Erst getrennt aggregieren, dann über gemeinsame Dimensionen kombinieren.

11. Fragen

Was ist ein Star Schema?

Eine Faktentabelle mit Messwerten und Fremdschlüsseln in der Mitte, darum herum denormalisierte Dimensionstabellen. Jede Dimension ist mit einem Join erreichbar.

Was ist ein Snowflake Schema?

Ein Star Schema, dessen Dimensionen weiter normalisiert sind. Hierarchie-Ebenen liegen in eigenen Tabellen, z. B. Produkt → Commodity.

Welche Vorteile hat ein Star Schema?

Wenige Joins, einfache SQL, gut für BI-Tools und Self-Service. Der Optimizer hat ein klares Muster: grosse Fakten, kleine Dimensionen.

Welche Vorteile hat ein Snowflake Schema?

Weniger Redundanz in den Dimensionen und einfachere Pflege einzelner Ebenen. Es ist näher an normalisierten Quellsystemen.

Was empfiehlt Kimball?

Flache, denormalisierte Dimensionen. Snowflaking rät er ab, weil Nutzer es schwer navigieren und es die Performance verschlechtern kann.

Wann wählen Sie trotzdem Snowflake?

Wenn eine Unterebene sehr gross ist oder eigene Attribute hat, die mehrere Dimensionen teilen. Oder wenn ein Tool ein normalisiertes Modell erwartet.

Ist die Faktentabelle im Snowflake anders?

Nein. Sie bleibt gleich. Nur die Dimensionen sind aufgeteilt.

Wie führt eine Engine eine Star-Abfrage aus?

Sie filtert die kleinen Dimensionen, baut Hash-Tabellen und scannt die Fakten einmal mit Hash Joins. Danach gruppiert sie nach Dimensions-Attributen.

Was ist eine Role-Playing Dimension?

Eine Dimension in mehreren Rollen, z. B. dim_date als Handelsdatum und Lieferdatum. Umgesetzt mit Aliasen oder Views.

Was ist eine Degenerate Dimension?

Ein Schlüssel in der Faktentabelle ohne eigene Dimensionstabelle, z. B. trade_id. Er dient zum Gruppieren oder Zurückverfolgen.

Was ist eine Junk Dimension?

Eine Tabelle für kleine Flags und Codes mit wenigen Werten. Sie ersetzt viele Mini-Dimensionen und hält die Faktentabelle schmal.

Was ist eine Outrigger-Dimension?

Eine Dimension, die auf eine andere Dimension verweist, z. B. ein Datum im Kunden-Datensatz. Kimball erlaubt das sparsam.

Was ist ein Galaxy-Schema?

Mehrere Faktentabellen, die dieselben Conformed Dimensions teilen. Damit lassen sich Prozesse über gemeinsame Attribute vergleichen.

Warum joint man zwei Faktentabellen nicht direkt?

Mehrere Zeilen auf beiden Seiten multiplizieren sich, Summen werden zu gross. Richtig ist Drill Across: getrennt aggregieren, dann über Conformed Dimensions kombinieren.

Was ist One Big Table und wann passt sie?

Alle Fakten und Attribute in einer breiten Tabelle. Sie passt für einen festen Use Case auf einem Column Store, schlecht für sich ändernde Attribute.

Spielt Speicher bei Star vs Snowflake eine Rolle?

Kaum. Dimensionen sind klein und Column Stores komprimieren wiederholte Werte. Lesbarkeit und Joins sind wichtiger.

Wie verhindern Sie, dass Fakten beim Join verloren gehen?

Jede Dimension bekommt eine „Unknown“-Zeile. Fakten ohne passenden Key zeigen darauf, nie auf NULL.

Wie verhalten sich Star-Joins in Spark?

Kleine Dimensionen werden per Broadcast Join an alle Executors verteilt, die Fakten werden nicht geshuffelt. Grosse Dimensionen erzwingen einen Shuffle.

Szenario: Nach einem Load sind alle Umsätze im Dashboard doppelt so hoch. Was prüfen Sie?

Doppelte Zeilen pro Key in einer Dimension, z. B. zwei aktive SCD2-Versionen. Summe der Fakten allein gegen Summe nach Joins vergleichen, dann Unique-Constraint einführen.

Szenario: Fachnutzer sagen, das Modell mit 25 Tabellen ist unbenutzbar. Was tun Sie?

Ich biete flache Dimensionen oder Views als Star an. Das normalisierte Modell bleibt intern für das Laden.

Szenario: Die Summe pro Produkt stimmt, aber die Gesamtsumme ist kleiner als in der Quelle. Warum?

Fakten mit unbekanntem Produkt-Key fallen durch den Inner Join. Fix: Unknown-Zeile in der Dimension und Ladeprüfung auf Waisen.
