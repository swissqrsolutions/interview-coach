Slowly Changing Dimensions (SCD)

Modelling · Tier 1 · Quellen: Kimball Group „Dimensional Modeling Techniques“ (SCD Type 0–7, Late Arriving Dimensions, Late Arriving Facts), PostgreSQL 17 Doku (MERGE, Exclusion Constraints, btree_gist, Range Types), Release Notes PostgreSQL 15, 17, 18

Kern: Eine Slowly Changing Dimension ist eine Dimension, deren Attribute sich selten ändern, z. B. der Name eines Marktteilnehmers. Der SCD-Typ legt fest, ob die alte Version verloren geht oder erhalten bleibt. SCD2 schreibt eine neue Zeile pro Version, damit alte Fakten mit den damals gültigen Attributen berichtet werden.

1. Wo sitzt die SCD-Logik?

  1. Quelle: kennt nur den aktuellen Stand. Beispiel: Teilnehmer A0001 heisst jetzt „Alpen Energie Holding AG“.
  2. Staging: der neue Stand plus ein Änderungsdatum (Business-Datum, nicht Ladezeit, wenn verfügbar).
  3. Change Detection: vergleicht Staging mit der aktuellen Version. IS DISTINCT FROM behandelt NULL korrekt, ein Hash-Diff (Hash über alle Attribute) vergleicht viele Spalten auf einmal.
  4. Dimension: wird je nach SCD-Typ überschrieben oder versioniert.
  5. Fakten-Load: sucht den Surrogate Key der Version, die am Datum des Fakts gültig war.

2. Die Reise einer Namensänderung (die Geschichte zum Merken)

  1. Ausgangslage: A0001 hat eine Version, key 1, gültig ab 2025-01-01 bis „offen“ (9999-12-31).
  2. Die Änderung kommt: Staging meldet den neuen Namen mit Änderungsdatum 2026-03-01.
  3. Alte Version schliessen: key 1 bekommt valid_to = 2026-03-01 und is_current = false.
  4. Neue Version einfügen: key 4 mit neuem Namen, valid_from = 2026-03-01, is_current = true.
  5. Fakten zuordnen: Ein Trade vom 15. Februar bekommt key 1, ein Trade vom 2. März key 4. Alte Reports zeigen weiter den alten Namen.
  6. Intervall-Regel: halboffen [valid_from, valid_to). Abfrage: datum >= valid_from AND datum < valid_to. So gibt es keine Lücke und keine Überlappung.

3. Beispiel: SCD2 mit MERGE in PostgreSQL 17

Tabelle: Surrogate Key, Natural Key, Attribute, Gültigkeit. Ein Exclusion Constraint verhindert überlappende Versionen pro Natural Key. Für = auf text in einem GiST-Index braucht es die Extension btree_gist.

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE dim_participant_scd2 (
  participant_key  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate key
  participant_code text    NOT NULL,                                  -- natural key
  name             text    NOT NULL,
  country          text    NOT NULL,
  valid_from       date    NOT NULL,
  valid_to         date    NOT NULL DEFAULT '9999-12-31',
  is_current       boolean NOT NULL DEFAULT true,
  CONSTRAINT no_overlap EXCLUDE USING gist
    (participant_code WITH =, daterange(valid_from, valid_to) WITH &&)
    DEFERRABLE INITIALLY DEFERRED);
-- Start: A0001 'Alpen Energie AG', B0002 'Nordstrom Trading GmbH', beide ab 2025-01-01
-- Staging (change_date 2026-03-01): A0001 neuer Name, B0002 unverändert, C0003 neu

MERGE: Ein MERGE führt pro Quellzeile höchstens eine Aktion aus. SCD2 braucht für eine Änderung aber zwei: alte Version schliessen und neue einfügen. Darum kommt jede geänderte Zeile zweimal in die Quelle: einmal mit merge_key (trifft und schliesst), einmal mit NULL (trifft nie und fügt ein).

MERGE INTO dim_participant_scd2 AS d
USING (
  SELECT s.participant_code AS merge_key, s.* FROM stg_participant s
  UNION ALL
  SELECT NULL, s.* FROM stg_participant s
  JOIN dim_participant_scd2 d
    ON d.participant_code = s.participant_code AND d.is_current
   AND (d.name, d.country) IS DISTINCT FROM (s.name, s.country)
) AS src
ON d.participant_code = src.merge_key AND d.is_current
WHEN MATCHED AND (d.name, d.country) IS DISTINCT FROM (src.name, src.country) THEN
  UPDATE SET valid_to = src.change_date, is_current = false
WHEN NOT MATCHED BY TARGET THEN
  INSERT (participant_code, name, country, valid_from)
  VALUES (src.participant_code, src.name, src.country, src.change_date)
RETURNING merge_action() AS action, d.participant_key AS key, d.participant_code AS code,
          d.name, d.valid_from, d.valid_to, d.is_current;

Echte Ausgabe, PostgreSQL 17.12. Demo-Tabellen und Extension danach gelöscht. Lücken in den Keys (5 fehlt) kommen vom fehlgeschlagenen Insert: Identity-Werte werden nicht zurückgegeben.

  1. MERGE-Ergebnis: A0001 wird geschlossen (UPDATE) und neu eingefügt (INSERT). C0003 ist neu (INSERT). B0002 ist unverändert und erscheint nicht.
  2. RETURNING merge_action() zeigt pro Zeile die Aktion. Das gibt es seit PostgreSQL 17, ebenso WHEN NOT MATCHED BY SOURCE. MERGE selbst gibt es seit PostgreSQL 15.
  3. Retry: Der zweite Lauf ändert nichts (MERGE 0). Der Load ist idempotent.
  4. Deferred Constraint: Die Reihenfolge der Zeilen im MERGE ist nicht garantiert. Wird die neue Version vor dem Schliessen der alten eingefügt, überlappen sie kurz. DEFERRABLE INITIALLY DEFERRED prüft erst beim Commit.
  5. Lookup per Datum: Der Trade vom 15. Februar bekommt key 1, obwohl er nach der Änderung geladen wird. Nie einfach is_current nehmen.
  6. Constraint schützt: Der naive rückdatierte Insert hätte zwei gültige Versionen erzeugt. Der Exclusion Constraint lehnt ihn ab.
  7. Späte Änderung: Version 1 wird geteilt. T8 und T9 lagen im neuen Zeitraum und zeigen jetzt auf key 6. T7 bleibt bei key 1.

4. Details, die Interviewer fragen: die SCD-Typen

  1. Typ 0 – Original behalten: Das Attribut ändert sich nie. Beispiel: Erst-Registrierungsdatum eines Teilnehmers.
  2. Typ 1 – Überschreiben: Der alte Wert geht verloren. Alte Fakten zeigen den neuen Wert. Beispiel: Tippfehler im Namen korrigieren. Aggregate über das Attribut können sich dadurch rückwirkend ändern.
  3. Typ 2 – Neue Zeile: Jede Änderung erzeugt eine Version mit neuem Surrogate Key. Kimball nennt mindestens drei Zusatzspalten: gültig ab, gültig bis, aktuelle Zeile. Beispiel: Name, Land, Teilnehmertyp.
  4. Typ 3 – Neue Spalte: prior_name neben name. Nur ein Vorgänger, keine volle Historie. Beispiel: Reorganisation, bei der man „alt gegen neu“ vergleichen will.
  5. Typ 4 – Mini-Dimension (Kimball): Schnell wechselnde Attribute (z. B. Bonitätsklasse) kommen in eine eigene kleine Dimension. Die Faktentabelle trägt beide Keys. Achtung: Andere Quellen nennen eine separate History-Tabelle „Typ 4“. Im Interview kurz klären, welche Bedeutung gemeint ist.
  6. Typ 5: Typ 4 plus ein Typ-1-Outrigger auf die aktuelle Mini-Dimension.
  7. Typ 6 – Typ 1 + 2 + 3: Typ-2-Zeilen mit einer zusätzlichen Spalte current_name. Diese wird bei jeder Änderung auf allen Versionen überschrieben. So kann man Fakten nach damaligem und nach aktuellem Wert gruppieren.
  8. Typ 7: Fakten tragen den Surrogate Key und den Durable Key. Über den Durable Key joint man eine „aktuelle“ Sicht, über den Surrogate Key die historische.
  9. valid_to: Sentinel oder NULL? 9999-12-31 macht Range-Abfragen einfach und indexfreundlich. NULL braucht COALESCE in jeder Abfrage.
  10. is_current ist redundant zu valid_to = '9999-12-31', aber bequem und gut indexierbar.
  11. Mehrere Änderungen pro Batch: Hat Staging zwei Zeilen für denselben Key, trifft MERGE dieselbe Zielzeile doppelt. Laut Doku gibt das einen Fehler (Cardinality Violation bei UPDATE). Fix: vorher deduplizieren oder Änderungen zeitlich geordnet nacheinander anwenden.
  12. Late Arriving Dimension: Der Fakt kommt vor dem Teilnehmer. Kimball: Platzhalter-Zeile mit Natural Key anlegen, Attribute später per Typ 1 füllen.
  13. Late Arriving Fact: Ein alter Trade kommt spät. Er bekommt den Key der Version, die an seinem Datum gültig war (Range-Lookup).
  14. PostgreSQL 18: PRIMARY KEY/UNIQUE mit WITHOUT OVERLAPS und Fremdschlüssel mit PERIOD. Das ersetzt den selbstgebauten Exclusion Constraint.

5. Vergleich

  • Typ 0: keine Änderung · keine Historie · trivial.
  • Typ 1: überschreiben · keine Historie · einfach, aber Reports ändern sich rückwirkend.
  • Typ 2: neue Zeile · volle Historie · mehr Zeilen, Range-Lookup im Fakten-Load.
  • Typ 3: neue Spalte · nur ein Vorgänger · für einmalige Umstellungen.
  • Typ 4 (Kimball): Mini-Dimension · Historie über die Fakten · für schnell wechselnde Attribute grosser Dimensionen.
  • Typ 6: Typ 2 + aktuelle Spalte · damals und heute · jede Änderung aktualisiert alle Versionen.
  • SCD2 gegen Snapshot-Dimension: Statt Versionen jeden Tag die ganze Dimension kopieren. Einfach, aber viel Speicher und Duplikate bei Joins ohne Datum.

6. In der Produktion

  1. Zwei aktive Versionen: Ein abgebrochener Load fügt die neue Version ein, schliesst die alte aber nicht. Joins verdoppeln Fakten. Fix: beides in einer Transaktion, Constraint gegen Überlappung, Test „max. eine Zeile mit is_current pro Key“.
  2. Versionsexplosion: Ein technisches Feld (z. B. last_updated) ist im Vergleich. Jede Ladung erzeugt eine Version. Fix: nur fachliche Attribute vergleichen.
  3. Falsche Gleichheit durch NULL: a <> b ist bei NULL nie wahr, Änderungen werden übersehen. Fix: IS DISTINCT FROM oder Hash-Diff mit NULL-Ersatz.
  4. Fakten mit is_current geladen: Spät ankommende Fakten bekommen die falsche Version. Fix: immer per Business-Datum und Intervall suchen.
  5. Rückdatierte Änderung: Einfach anhängen erzeugt Überlappungen. Fix: Version teilen, Folgeversion respektieren, Fakten im Zeitraum neu verschlüsseln.
  6. Zeitzonen: Änderungen mit Zeitstempel, Fakten mit Datum in anderer Zeitzone. Grenzfälle landen in der falschen Version. Fix: eine Zeitzone (UTC oder Geschäftszeitzone) festlegen.
  7. Lakehouse: SCD2-MERGE in Spark auf Iceberg oder Delta funktioniert mit demselben merge_key-Muster. Viele kleine MERGEs erzeugen viele Dateien. Fix: pro Batch ein MERGE, Compaction.

7. Diagnose: Werkzeuge und Abfragen

  • Mehrere aktuelle Versionen: SELECT participant_code FROM dim GROUP BY 1 HAVING count(*) FILTER (WHERE is_current) <> 1;
  • Lücken und Überlappungen: mit lead(valid_from) OVER (PARTITION BY participant_code ORDER BY valid_from) prüfen, ob es gleich valid_to ist.
  • Versionen pro Key: SELECT participant_code, count(*) FROM dim GROUP BY 1 ORDER BY 2 DESC LIMIT 10; Ausreisser zeigen falsche Change Detection.
  • Fakten mit falscher Version: Fakten joinen, deren Datum nicht im [valid_from, valid_to) ihrer Version liegt.
  • RETURNING merge_action() (PostgreSQL 17) im Load loggen: wie viele Inserts und Updates pro Lauf.
  • Exclusion Constraint als Wächter: Er verhindert Überlappungen, statt sie später zu finden.

8. Senior-Punkte

  1. SCD-Typ pro Attribut, nicht pro Tabelle. Tippfehler-Korrekturen sind Typ 1, Land oder Rolle Typ 2.
  2. Fachlich fragen: „Soll ein alter Report den alten oder neuen Namen zeigen?“ Die Antwort entscheidet den Typ.
  3. Business-Datum statt Ladezeit, wenn die Quelle es liefert. Sonst ist die Historie nur „wann wir es erfahren haben“.
  4. Idempotenz ist Pflicht: Ein Retry darf keine neue Version erzeugen. Change Detection plus Constraint sichern das.
  5. Late Changes kosten: Fakten müssen neu verschlüsselt werden. Alternative: Fakten tragen den Durable Key und das Datum, Versionen werden beim Lesen per Range-Join gesucht (Typ-7-Idee).
  6. Grosse Dimensionen mit schnellen Änderungen sprengen SCD2. Dann Mini-Dimension (Kimball Typ 4) oder Snapshot-Fakten.
  7. Rohdaten behalten: Wer alle Änderungen in Bronze hat, kann die SCD2-Dimension jederzeit neu aufbauen.

9. Aus dem Projekt

„SCD2 habe ich nicht in Produktion gebaut. Am nächsten ist ElCom MATCH: Pro Meldung schreibt der Job in einer Iceberg-Transaktion erst DELETE WHERE message_id = X, dann APPEND, und Statistiken werden pro Tag ersetzt statt addiert, damit Retries nichts doppelt schreiben, dasselbe Idempotenz-Ziel wie beim SCD2-MERGE.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „SCD2: Fakten bekommen immer die aktuelle Version.“ → Falsch. Sie bekommen die Version, die am Datum des Fakts gültig war.
  • „valid_to = Tag vor der nächsten Version, Abfrage mit BETWEEN.“ → Bei Zeitstempeln entstehen Lücken. Halboffen [from, to) mit >= und < ist sicher.
  • „Typ 4 ist immer die History-Tabelle.“ → Bei Kimball ist Typ 4 die Mini-Dimension. Begriff im Gespräch klären.
  • „Ein MERGE kann pro Zeile schliessen und einfügen.“ → Nein, höchstens eine Aktion pro Quellzeile. Darum die Quelle verdoppeln oder zwei Statements in einer Transaktion.
  • „Änderungen erkenne ich mit <>.“ → NULL-Werte rutschen durch. IS DISTINCT FROM verwenden.
  • „Typ 1 ist harmlos.“ → Überschreiben ändert alte Reports rückwirkend. Das muss fachlich gewollt sein.

11. Fragen

Was ist eine Slowly Changing Dimension?

Eine Dimension, deren Attribute sich selten und unregelmässig ändern. Der SCD-Typ legt fest, wie die Historie behandelt wird.

Was ist SCD Typ 0?

Das Attribut behält immer den Originalwert. Änderungen der Quelle werden ignoriert.

Was ist SCD Typ 1?

Der alte Wert wird überschrieben. Es gibt keine Historie, und alte Fakten zeigen den neuen Wert.

Was ist SCD Typ 2?

Jede Änderung erzeugt eine neue Zeile mit neuem Surrogate Key und Gültigkeitszeitraum. Alte Fakten behalten ihre alte Version.

Welche Spalten braucht eine SCD2-Dimension?

Surrogate Key, Natural Key, Attribute, valid_from, valid_to und is_current. Optional ein Hash-Diff für die Change Detection.

Was ist SCD Typ 3?

Eine zusätzliche Spalte für den vorherigen Wert. Nur eine Stufe Historie, gut für „alt gegen neu“-Vergleiche.

Was ist SCD Typ 4?

Bei Kimball: schnell wechselnde Attribute in eine Mini-Dimension, die Fakten tragen beide Keys. In anderen Quellen: aktuelle Tabelle plus separate History-Tabelle.

Was ist SCD Typ 6?

Typ 2 plus eine Typ-1-Spalte mit dem aktuellen Wert auf allen Versionen. Man kann nach damaligem und aktuellem Wert berichten.

Warum braucht SCD2 einen Surrogate Key?

Der Natural Key kommt pro Version mehrfach vor. Nur ein eigener Key pro Version macht die Zeile eindeutig für Fakten-Joins.

Warum halboffene Intervalle?

Mit [valid_from, valid_to) ist das Ende der alten Version gleich dem Anfang der neuen. Es gibt keine Lücken und keine doppelten Treffer.

Warum 9999-12-31 statt NULL als offenes Ende?

Range-Abfragen funktionieren ohne COALESCE und Indizes bleiben nutzbar. NULL ist auch möglich, macht jede Abfrage aber umständlicher.

Wie erkennen Sie Änderungen effizient?

Mit IS DISTINCT FROM über die fachlichen Spalten oder mit einem Hash-Diff. Technische Felder gehören nicht in den Vergleich.

Wie implementieren Sie SCD2 mit einem MERGE?

Geänderte Zeilen kommen zweimal in die Quelle: mit Merge-Key zum Schliessen, mit NULL-Key zum Einfügen. Ein MERGE führt dann UPDATE und INSERT in einem Statement aus.

Was passiert, wenn die Quelle zwei Zeilen für denselben Key hat?

MERGE würde dieselbe Zielzeile zweimal ändern. PostgreSQL meldet dann einen Fehler. Vorher deduplizieren oder Änderungen geordnet nacheinander anwenden.

Was ist neu bei MERGE in PostgreSQL 17?

RETURNING mit merge_action(), WHEN NOT MATCHED BY SOURCE und MERGE auf updatable Views. MERGE selbst gibt es seit PostgreSQL 15.

Wie verhindern Sie überlappende Versionen in PostgreSQL?

Mit einem Exclusion Constraint auf Natural Key (=) und daterange (&&), dafür btree_gist. Ab PostgreSQL 18 geht das mit WITHOUT OVERLAPS.

Warum ist der Exclusion Constraint deferrable?

Die Reihenfolge der Zeilen im MERGE ist nicht garantiert. Wird zuerst eingefügt, überlappen alte und neue Version kurz; die Prüfung beim Commit sieht nur den Endzustand.

Wie ordnen Sie einen Fakt der richtigen Version zu?

Über Natural Key und Business-Datum: datum >= valid_from AND datum < valid_to. Nicht über is_current.

Was ist eine Late Arriving Dimension?

Der Fakt kommt, bevor die Dimension den Teilnehmer kennt. Man legt eine Platzhalter-Zeile mit dem Natural Key an und füllt die Attribute später.

Was ist eine Late Arriving Fact?

Ein Fakt mit altem Datum kommt spät. Er bekommt per Range-Lookup die damals gültige Version, nicht die aktuelle.

Wie behandeln Sie eine rückdatierte Änderung?

Die betroffene Version wird am Änderungsdatum geteilt, die Folgeversion bleibt. Danach werden Fakten im neuen Zeitraum auf den neuen Key umgeschlüsselt, alles in einer Transaktion.

Wie machen Sie SCD2-Loads idempotent?

Change Detection gegen die aktuelle Version: Unveränderte Zeilen erzeugen nichts. Ein Retry ergibt null Änderungen.

Wie funktioniert SCD2 im Lakehouse?

Mit MERGE INTO in Spark auf Iceberg oder Delta, gleiches Merge-Key-Muster. Wichtig: pro Batch ein MERGE und Compaction gegen kleine Dateien.

Wann ist SCD2 die falsche Wahl?

Wenn sich Attribute sehr oft ändern oder die Dimension riesig ist. Dann Mini-Dimension, Snapshot-Fakten oder Typ 1 für unwichtige Attribute.

Szenario: Nach einem SCD2-Load sind manche Umsätze doppelt. Was prüfen Sie?

Ob Keys zwei aktive oder überlappende Versionen haben, z. B. nach einem halben Load. Abfrage mit count(*) FILTER (WHERE is_current), dann Load transaktional machen und Constraint einführen.

Szenario: Die Dimension hat pro Teilnehmer hunderte Versionen, obwohl sich fachlich wenig ändert. Ursache?

Die Change Detection vergleicht ein technisches Feld wie einen Zeitstempel. Nur fachliche Attribute vergleichen und die Dimension neu aufbauen.

Szenario: Ein Teilnehmer meldet, dass sein Name schon seit Oktober anders ist. Was tun Sie?

Die gültige Version am 1. Oktober teilen, die neue Version bis zur nächsten Änderung einfügen und die Fakten des Zeitraums umschlüsseln. Danach Reports für den Zeitraum neu rechnen.
