Code Reviews als Prozess

Kern: Ein Code Review ist die Prüfung einer Änderung durch eine andere Person, bevor sie in den Hauptzweig kommt. Es sichert die Code Health, also die langfristige Qualität der Codebasis, und verteilt Wissen im Team. Googles Grundregel lautet: Approve, sobald die Änderung die Code Health klar verbessert, auch wenn sie nicht perfekt ist.

Antwort-Muster

Frage: Wie machst du ein gutes Code Review?

  1. Mechanismus: Ich lese zuerst die Beschreibung, dann den Kernteil auf Design und dann den Rest. Grosse Probleme melde ich zuerst, Kleinigkeiten als Nit.
  2. Zahl: Ein PR hat ca. 100 Zeilen, nicht 1000. Die erste Antwort kommt innerhalb eines Arbeitstages.
  3. Trade-off: Ich approve, wenn die Änderung die Code Health klar verbessert. Perfektionismus bremst das ganze Team.
  4. Produktion: Warten PRs lange, plane ich feste Review-Zeit ein und schneide die PRs kleiner.

1. Die Reise eines Reviews (in welcher Reihenfolge ich lese)

  1. Macht die Änderung Sinn? Ich lese zuerst die Beschreibung. Passt das Ziel nicht, sage ich es sofort und höflich, mit einer Alternative.
  2. Den wichtigsten Teil zuerst: die Datei mit der meisten Logik. Ist das Design falsch, melde ich das sofort. Der Autor soll nicht weiter auf einem falschen Fundament bauen.
  3. Den Rest in sinnvoller Reihenfolge: oft zuerst die Tests, um das gewollte Verhalten zu verstehen. Ich lese jede Zeile, die ich reviewen soll.
  4. Urteil: Verbessert die Änderung die Code Health klar? Dann Approve, eventuell mit kleinen Kommentaren. Sonst „Changes requested“ mit klaren Gründen.
  5. Tempo: Ich antworte innerhalb eines Arbeitstages, aber nicht mitten in meiner Fokusarbeit. Ich nutze eine natürliche Pause.

2. Aufbau

  1. Branch: Der Autor macht eine kleine, abgeschlossene Änderung mit Tests.
  2. Pull Request (PR): Bei Google heisst er CL (Changelist). Er hat eine Beschreibung: was, warum, wie getestet.
  3. CI-Checks: Build, Tests, Linter und z. B. SonarQube Quality Gate laufen automatisch. Was eine Maschine prüfen kann, prüft kein Mensch.
  4. Menschliches Review: Design, Funktion, Komplexität, Tests, Namen. Das kann keine Maschine gut.
  5. Merge: Branch Protection verhindert Merge ohne Approval und grüne Checks.

3. Details, die Interviewer fragen

  1. Ziele eines Reviews: Code Health sichern, Fehler früh finden, Wissen verteilen und Standards halten. Juniors lernen dabei. Fehlerfinden ist nur ein Teil.
  2. Design und Funktion zuerst: Beim Design prüft man, ob die Änderung ins System passt. Bei der Funktion prüft man, ob der Code tut, was der Autor will. Randfälle und Nebenläufigkeit gehören dazu.
  3. Komplexität und Tests: Ein Leser soll den Code schnell verstehen. Over-Engineering ist Allgemeinheit „für später“ und gehört nicht hinein. Tests sind auch Code, der gewartet wird.
  4. Namen, Kommentare, Stil, Doku: Kommentare erklären das Warum, nicht das Was. Stil entscheidet der Style Guide.
  5. Kein perfekter Code: Google sagt, es gibt nur besseren Code. Der Reviewer soll nicht polieren, bis alles perfekt ist.
  6. Grösse: Laut Google sind ca. 100 Zeilen meist gut. 1000 Zeilen sind meist zu viel. Auch die Zahl der Dateien zählt.
  7. Kleine Änderungen schneiden: Man kann stapeln (Stacking), nach Dateien teilen, horizontal nach Schichten oder vertikal nach Features. Refactoring kommt in einen eigenen PR.
  8. Tempo: Die erste Antwort kommt in höchstens einem Arbeitstag. Langsame Reviews bremsen das ganze Team.
  9. Kommentar-Labels: Nit ist eine Kleinigkeit. Optional / Consider ist ein Vorschlag. FYI ist zum Nachdenken, nicht in diesem PR.
  10. LGTM with comments: Das ist ein Approve mit offenen kleinen Kommentaren. Der Autor erledigt sie sicher. Das spart Zeit über Zeitzonen.
  11. Konflikte: Zuerst sucht man Konsens mit Fakten und Guidelines. Dann folgt ein Gespräch per Video. Dann geht es an den Tech Lead oder ans Team. Ein PR soll nie wegen Streit liegen bleiben.
  12. Erklärung im Code, nicht im Tool: Versteht der Reviewer etwas nicht, macht der Autor den Code klarer. Eine Antwort nur im Review-Tool hilft späteren Lesern nicht.

4. Fallen

  • „Code Reviews sind zum Fehlerfinden.“ → Nur teilweise. Wissen teilen und Code Health sind genauso wichtig.
  • „Ich approve erst, wenn alles perfekt ist.“ → Falsch. Approve, wenn die Änderung die Code Health klar verbessert.
  • „Grosse PRs sind effizienter.“ → Falsch. Kleine PRs werden schneller und gründlicher reviewt und haben weniger Fehler.
  • „Der Reviewer soll den Code selbst fixen.“ → Falsch. Fixen ist Aufgabe des Autors. Der Reviewer zeigt Probleme und gibt Hinweise.
  • „Stilfragen gehören ins Review.“ → Besser automatisieren. Formatter und Linter entscheiden, der Style Guide ist die Autorität.
  • „Eine Erklärung im Review-Kommentar reicht.“ → Falsch. Besser den Code klarer machen oder einen Code-Kommentar schreiben.

5. Selbsttest

Warum?

Was sind die Ziele eines Code Reviews?

Code Health sichern, Fehler früh finden, Wissen verteilen und Standards halten. Dazu Mentoring für Juniors.

Wann geben Sie ein Approve?

Wenn die Änderung die Code Health klar verbessert, auch wenn sie nicht perfekt ist.

Was tun Sie, wenn Sie Code nicht verstehen?

Ich bitte den Autor, den Code klarer zu machen oder einen Kommentar hinzuzufügen. Eine Erklärung nur im Tool hilft späteren Lesern nicht.

Warum sind kleine PRs besser?

Sie werden schneller und gründlicher reviewt und haben weniger Fehler. Riesige PRs enden oft in einem „LGTM“ ohne Lesen.

Wie innen?

Wie machen Sie Code Reviews?

Ich lese zuerst die Beschreibung, dann den Kernteil auf Design, dann den Rest Zeile für Zeile. Grosse Probleme melde ich zuerst, Kleinigkeiten als Nit. Ich antworte innerhalb eines Arbeitstages.

Worauf achten Sie zuerst?

Auf das Design: Gehört die Änderung hierher, passt sie ins System? Danach Funktion, Komplexität und Tests.

Wie formulieren Sie Kritik?

Über den Code, nie über die Person. Ich erkläre das Warum und stelle oft eine Frage statt einer Anweisung.

Was prüfen Sie bei Tests?

Ob sie zur Änderung passen und ob sie fehlschlagen würden, wenn der Code kaputt ist. Tests sind auch Code, der gewartet wird.

Was ist Over-Engineering im Review?

Code, der allgemeiner ist als nötig, für Fälle, die vielleicht nie kommen. Reviewer sollen das besonders beachten.

Was bedeutet „Nit“?

Eine kleine Verbesserung, die der Autor ignorieren darf. Es hilft, Pflicht von Vorschlag zu trennen.

Was ist LGTM with comments?

Approve mit kleinen offenen Kommentaren, wenn der Autor sie sicher erledigt. Spart eine Review-Runde.

Wie teilen Sie eine grosse Änderung auf?

Stacking, nach Dateien, horizontal nach Schichten oder vertikal nach Features. Refactoring kommt in einen eigenen PR.

Zahlen

Wie gross sollte ein Pull Request sein?

Eine abgeschlossene Änderung zu einem Thema. Google nennt ca. 100 Zeilen meist gut, 1000 meist zu gross.

Wie schnell sollte ein Review kommen?

Innerhalb eines Arbeitstages. Aber nicht mitten in Fokusarbeit, sondern in einer natürlichen Pause.

Welches Ziel gilt für Time to first review?

Nach Google unter einem Arbeitstag.

Wann ist die Review-Verteilung ein Problem?

Wenn eine Person zum Beispiel 60 % aller Reviews macht. Sie ist dann ein Engpass.

Vergleich

Pair Programming oder asynchrones Review?

Pairing für schwierige, neue oder dringende Themen und Wissenstransfer. Async für normale Änderungen und über Zeitzonen.

Was prüft ein Tool, was ein Mensch?

Tools prüfen Stil, Formatierung, bekannte Bugs und Security-Muster. Menschen prüfen Design, Logik und Verständlichkeit.

Was bedeutet Ship / Show / Ask?

Ship: kleine sichere Änderung direkt mergen. Show: mergen und zeigen. Ask: vorher fragen. Das braucht Vertrauen und gute Tests.

Produktion

Szenario: PRs warten im Team regelmässig zwei Tage. Was schlagen Sie vor?

Feste Review-Zeit nach dem Daily, kleinere PRs, Review-Last verteilen. Wir messen Time to first review und sprechen in der Retro darüber.

Szenario: Ein Senior-Kollege schreibt harte Kommentare und Juniors trauen sich nicht mehr. Was tun Sie?

Ich spreche ihn privat an und zeige konkrete Beispiele. Im Team vereinbaren wir Regeln: über Code reden, Warum erklären, Nit markieren.

Szenario: Ein dringender Hotfix soll ohne Review in Produktion. Wie entscheiden Sie?

Ein schnelles Review, auch per Video in 10 Minuten, ist fast immer möglich. Geht es wirklich nicht, dokumentieren wir die Ausnahme und reviewen sofort danach.

Was machen Sie mit einem PR von 3000 Zeilen?

Ich bitte um Aufteilung. Geht das nicht, gebe ich zuerst Feedback zum Design, damit der Autor weiterkommt.

Wie verhindern Sie, dass Sie zum Engpass werden?

Reviews im Team verteilen, CODEOWNERS nur für kritische Teile und andere befähigen, auch komplexe Teile zu reviewen.

Design

Was gehört in eine Review-Checkliste?

Design, Randfälle, Fehlerbehandlung, Tests, Security (Auth, Input, Secrets), Logging ohne Personendaten, Migrationen, Doku.

Wie gehen Sie mit Uneinigkeit um?

Zuerst Konsens mit Fakten und Guidelines. Dann kurzes Gespräch, Ergebnis im PR notieren. Sonst Eskalation an Tech Lead oder Team.

Wie fördern Sie Juniors im Review?

Mit erklärenden Kommentaren, markiert als Nit oder FYI, und mit Lob für gute Lösungen. Juniors reviewen auch selbst, auch Code von Seniors.

Was geht kaputt bei Rubber Stamping?

Ein Approve ohne Lesen lässt Fehler durch. Lösung: kleinere PRs, Checkliste für kritische Punkte und Vorbild durch Seniors.

Mehr

Gerüst

  • Warum? Code Health sichern und Wissen verteilen. Fehlerfinden ist nur ein Teil.
  • Wie innen? Beschreibung lesen, dann Kernteil und Design, dann der Rest. Branch Protection verhindert Merge ohne Approval und grüne Checks.
  • Zahlen Ca. 100 Zeilen meist gut, 1000 meist zu viel. Erste Antwort in höchstens einem Arbeitstag.
  • Vergleich Async PR vs Pair vs Mob. Tool (Stil, bekannte Muster) vs Mensch (Design, Sinn).
  • Produktion Riesige PRs, wartende PRs, Rubber Stamping, Gatekeeper-Senior, harter Ton.
  • Design Approve bei klarer Verbesserung. Nit, Optional, FYI als Labels. Risiko bestimmt die Tiefe.

Beispiel: Review-Kommentare an einem PR (fiktiv)

Beispiel – fiktiver Pull Request #412 "Export: CSV pro Kanton"
Beschreibung: Neuer Endpoint /exports/{kanton}. Getestet mit 2 Integrationstests.

ExportService.java, Zeile 48
  Reviewer: "Hier laden wir alle Zeilen mit findAll() in den Speicher.
             Bei grossen Kantonen sind das Millionen Zeilen. Können wir
             streamen (Stream / Paging)? Sonst riskieren wir OutOfMemory."
  Autor:    "Guter Punkt, ich stelle auf Paging mit 5000 um."

ExportController.java, Zeile 21
  Reviewer: "Fehlt hier die Berechtigungsprüfung für den Kanton?
             Ein Nutzer aus BE könnte sonst ZH exportieren."
  Autor:    "Stimmt. Ich ergänze @PreAuthorize und einen Test dafür."

ExportServiceTest.java
  Reviewer: "Würde dieser Test fehlschlagen, wenn das Trennzeichen falsch ist?
             Er prüft nur die Zeilenanzahl."

CsvWriter.java, Zeile 10
  Reviewer: "Nit: Der Name 'tmp' sagt wenig. 'csvLine'?"
  Reviewer: "Schön gelöst mit dem Escaping von Anführungszeichen, danke!"

Ergebnis: Changes requested (Speicher + Berechtigung). Nit ist optional.
  1. Die wichtigen Punkte zuerst: Speicher (Design/Funktion) und Sicherheit (Berechtigung).
  2. Jeder Kommentar sagt warum. Er spricht über den Code, nie über die Person.
  3. Die Testfrage folgt Google: Würde der Test fehlschlagen, wenn der Code kaputt ist?
  4. „Nit:“ markiert eine Kleinigkeit. Der Autor darf sie ignorieren.
  5. Lob für gute Lösungen gehört dazu. Es zeigt, was das Team beibehalten soll.

Vergleich

  • Asynchrones PR-Review: flexibel, dokumentiert, gut über Zeitzonen. Nachteil: Wartezeit und lange Diskussions-Threads.
  • Pair Programming: Review in Echtzeit, kein Warten, viel Wissenstransfer. Nachteil: zwei Personen pro Aufgabe, ermüdend.
  • Mob Programming: das ganze Team an einer Aufgabe. Gut für schwierige oder neue Themen, teuer im Alltag.
  • Gemeinsames Review am Bildschirm: für grosse oder strittige Änderungen. Ergebnis als Kommentar festhalten.
  • Ship / Show / Ask: kleine sichere Änderung direkt mergen (Ship), mergen und zeigen (Show) oder vorher fragen (Ask). Braucht Vertrauen und gute Tests.
  • Mensch vs Tool: Linter, Formatter, SonarQube und Security-Scanner prüfen Stil und bekannte Muster. Menschen prüfen Design und Sinn.

In der Produktion (was schiefgeht)

  1. Riesige PRs (2000 Zeilen): Reviewer schreibt nur „LGTM“. Fehler rutschen durch. Lösung: kleine PRs, Feature Flags für halbfertige Features.
  2. PRs warten Tage: Kontextwechsel, Merge-Konflikte, Frust. Lösung: Review-Zeit fest einplanen, z. B. nach dem Daily. Work Item Age beobachten.
  3. Stil-Kriege im Review: Diskussion über Klammern und Leerzeichen. Lösung: Formatter und Linter in CI, Style Guide entscheidet.
  4. Gatekeeper-Senior: Eine Person muss alles reviewen. Sie wird zum Engpass. Lösung: Reviews verteilen, CODEOWNERS nur für kritische Teile.
  5. Harter Ton: „Das ist falsch.“ Juniors trauen sich nicht mehr. Lösung: Fragen stellen, Warum erklären, Code statt Person kritisieren.
  6. Rubber Stamping: Approve ohne Lesen. Lösung: kleinere PRs, Checkliste für kritische Punkte, Vorbild durch Seniors.
  7. Sicherheitslücken übersehen: Lösung: Checkliste mit Auth, Input-Validierung, Secrets, Logging von Personendaten. Dazu SAST in CI.

Diagnose: Review-Prozess messen

  • Time to first review: Zeit bis zur ersten Antwort. Ziel nach Google: unter einem Arbeitstag.
  • PR-Grösse: Verteilung der geänderten Zeilen. Viele grosse PRs zeigen fehlendes Schneiden.
  • Review-Verteilung: Wer reviewt wie viel? Eine Person mit 60 % ist ein Engpass.
  • Escaped Defects: Fehler in Produktion, die ein Review hätte finden können. Danach die Checkliste anpassen.
  • Tools: Bitbucket, GitHub, Azure DevOps Repos mit Branch Policies, Required Reviewers, CODEOWNERS; SonarQube PR-Decoration.

Senior-Punkte

  1. Wie ich reviewe: Beschreibung, dann Kernteil und Design, dann der Rest. Grosse Probleme früh und zuerst. Kleinigkeiten als „Nit“.
  2. Approve, wenn es klar besser ist, nicht wenn es perfekt ist. Perfektionismus bremst das Team.
  3. Review ist Mentoring. Ich erkläre das Warum, frage statt zu befehlen und lobe gute Lösungen.
  4. Automatisieren, was geht. Stil, Formatierung, bekannte Bugs und Security-Muster prüft CI. Menschenzeit geht an Design und Logik.
  5. Schnelle Reviews sind ein Teamziel. Ein PR, der zwei Tage wartet, kostet mehr als ein unterbrochener Nachmittag.
  6. Bei Streit: Fakten und Guidelines, dann ein kurzes Gespräch, dann Eskalation. Ergebnis im PR dokumentieren.
  7. Risiko bestimmt die Tiefe: Ein Tippfehler im UI braucht weniger als eine Änderung an Auth oder Datenmigration.
