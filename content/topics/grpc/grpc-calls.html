gRPC: Unary und Streaming, Deadlines

Kern: gRPC kennt vier Aufrufarten: Unary, Server Streaming, Client Streaming und Bidirectional Streaming. Ein Aufruf ist ein HTTP/2-Stream mit Nachrichten im Protobuf-Format. Eine Deadline begrenzt, wie lange der Client auf die Antwort wartet. Sie wird an Folgeaufrufe weitergegeben.

Antwort-Muster

Frage: Welche Aufrufarten hat gRPC, und wie funktionieren Deadlines?

  1. Mechanismus: Jeder Aufruf ist ein HTTP/2-POST auf /Service/Methode. Nachrichten haben ein 5-Byte-Präfix, der Status kommt in den Trailern.
  2. Zahl: Es gibt vier Aufrufarten und 17 Statuscodes (0 bis 16). Die empfangene Nachricht darf standardmässig höchstens 4 MB gross sein.
  3. Trade-off: Streaming spart Verbindungen und Latenz, ist aber komplexer bei Fehlern und Lastverteilung. Ohne Deadline wartet ein Client praktisch ewig.
  4. Produktion: Ich setze auf jedem Client-Aufruf eine Deadline, gebe sie an Folgeaufrufe weiter und wiederhole nur idempotente Aufrufe.

1. Ein Unary-Aufruf mit Deadline in 6 Schritten

  1. Client: Der Client ruft die Stub-Methode auf und setzt eine Deadline, zum Beispiel 2 Sekunden. Ohne Angabe gilt keine Deadline.
  2. Request: Die Bibliothek sendet einen HTTP/2-POST auf den Pfad /Service/Methode. content-type ist application/grpc. Die Frist reist im Header grpc-timeout, zum Beispiel 2S.
  3. Nachricht: Die Protobuf-Nachricht bekommt ein Präfix. Ein Byte sagt, ob sie komprimiert ist. Vier Byte (Big Endian) nennen die Länge.
  4. Server: Der Server liest die Frist und startet den Handler. Läuft die Frist ab, bricht das Runtime den Aufruf ab.
  5. Antwort: Der Server sendet Antwort-Header, die Nachricht und dann die Trailer.
  6. Status: Der Status steht in den Trailern (grpc-status). Der HTTP-Status ist bei einer gRPC-Antwort 200. Bei Erfolg ist der Code OK (0).

Der echte Lauf unten baut den Frame für HelloRequest{name="Bern"} von Hand. Er zeigt Flag 0 und Länge 6.

2. Aufbau

  1. Unary: Eine Anfrage, eine Antwort. Das entspricht einem normalen Funktionsaufruf.
  2. Server Streaming: Der Client sendet eine Anfrage. Der Server sendet eine Folge von Nachrichten.
  3. Client Streaming: Der Client sendet eine Folge. Der Server antwortet einmal, meist am Ende.
  4. Bidirectional Streaming: Beide Seiten senden unabhängig. Die Reihenfolge innerhalb einer Richtung bleibt.
  5. Metadata: Schlüssel-Wert-Paare in den HTTP/2-Headern, zum Beispiel für Authentifizierung. Namen mit -bin tragen Binärdaten.
  6. Status: Ein Code und eine Meldung. Sie stehen in den Trailern am Ende.

3. Details

  1. Wire-Format: Ein Aufruf ist ein HTTP/2-POST mit Pfad /Service/Methode. Die Header enthalten te: trailers, content-type: application/grpc und optional grpc-timeout. Danach folgen Nachrichten und am Ende die Trailer.
  2. Length-Prefixed Message: Jede Nachricht hat ein Byte Kompressions-Flag und vier Byte Länge (Big Endian). Die Kompression gilt pro Nachricht, es gibt keinen Kontext über Nachrichten hinweg.
  3. Status in Trailern: Der Status kommt immer in den Trailern, auch bei Erfolg. Bei einem sofortigen Fehler ohne Nachricht gibt es eine "Trailers-Only"-Antwort.
  4. Statuscodes: Es gibt 17 Codes von OK (0) bis UNAUTHENTICATED (16). Wichtig sind INVALID_ARGUMENT, NOT_FOUND, DEADLINE_EXCEEDED, UNAVAILABLE, INTERNAL und UNKNOWN.
  5. Deadline: Eine Deadline ist ein Zeitpunkt, an dem der Client nicht mehr wartet. Standard ist keine Deadline. Läuft sie ab, endet der Aufruf mit DEADLINE_EXCEEDED.
  6. Header grpc-timeout: Der Wert ist eine positive Zahl mit höchstens 8 Ziffern und eine Einheit: H, M, S, m, u oder n. Fehlt er, nimmt der Server eine unendliche Frist an.
  7. Server und Frist: Hat die Frist ein Aufruf überschritten, bricht der Server ihn ab (Status CANCELLED). Der Server-Code muss aber selbst prüfen, ob er abgebrochen wurde, und die Arbeit stoppen.
  8. Deadline Propagation: Ruft ein Server einen weiteren Server auf, soll die Frist weitergehen. Java und Go tun das standardmässig, C++ nur auf Anforderung. gRPC rechnet die Frist in eine Restzeit um, wegen unterschiedlicher Uhren.
  9. Retries: Wiederholungen sind standardmässig eingeschaltet, aber es gibt keine Standard-Policy. Ohne Policy wiederholt gRPC nur Fehler, bei denen sicher nichts angekommen ist. Nach dem Empfang der Antwort-Header ist der Aufruf "committed".
  10. Keepalive: HTTP/2-Pings prüfen, ob die Verbindung lebt. Im C-Core ist die Zeit beim Client standardmässig aus. Der Server sendet standardmässig alle 2 Stunden. Der Server toleriert zu häufige Pings nicht und sendet GOAWAY.
  11. Nachrichtengrösse: Der Go-Server nimmt standardmässig höchstens 4 MB pro Nachricht an. Java hat 4 MB als Standard. In .NET sind es für Empfang ebenfalls 4 MB. Grosse Daten gehören in Streams.
  12. Streaming-Kosten: Streaming-Aufrufe halten Ressourcen und eine Verbindung lange. Die Doku warnt, dass Streaming in manchen Sprachen mehr Threads braucht und langsamer als Unary sein kann.

4. Fallen

  • „gRPC hat standardmässig eine Deadline.“ → Falsch. Es hat keine. Der Client kann ewig warten. Man setzt sie immer selbst.
  • „Der gRPC-Fehler steht im HTTP-Status.“ → Falsch. Der HTTP-Status ist 200. Der gRPC-Status steht in den Trailern.
  • „DEADLINE_EXCEEDED heisst, die Aktion wurde nicht ausgeführt.“ → Falsch. Der Server kann sie schon ausgeführt haben. Bei Änderungen muss man das beachten.
  • „Der Server beendet seine Arbeit automatisch, wenn die Frist abläuft.“ → Falsch. Das Runtime bricht den Aufruf ab. Die eigene Arbeit muss der Code selbst stoppen.
  • „Retries sind mit Standardwerten aktiv.“ → Falsch. Ohne konfigurierte Policy gibt es fast keine Wiederholung. Man muss sie einrichten.
  • „Streaming ist immer schneller als Unary.“ → Falsch. Es spart Aufrufe, braucht aber mehr Ressourcen und ist bei Fehlern und Lastverteilung schwerer.

5. Selbsttest

Warum?

Warum braucht jeder Aufruf eine Deadline?

Ohne Deadline wartet der Client ewig auf einen hängenden Server. Threads und Verbindungen bleiben belegt.

Warum gibt es Streaming?

Für viele Nachrichten in einem Aufruf, zum Beispiel Live-Daten oder grosse Listen. Es spart den Aufbau pro Nachricht.

Warum steht der Status in den Trailern?

Der Server weiss den Status erst nach der letzten Nachricht. Trailer kommen nach dem Body, darum passt es dorthin.

Wie innen?

Wie sieht ein gRPC-Aufruf auf der Leitung aus?

HTTP/2 HEADERS mit POST und Pfad, DATA-Frames mit präfixierten Nachrichten, am Ende HEADERS mit den Trailern und grpc-status.

Wie wird die Deadline übertragen?

Als Restzeit im Header grpc-timeout, zum Beispiel 1500m für 1500 Millisekunden. Die Zeit läuft pro Hop weiter.

Was ist eine Trailers-Only-Antwort?

Eine Antwort ohne Nachricht, bei der Header und Status in einem HEADERS-Frame stehen. Sie kommt bei sofortigen Fehlern.

Wie funktioniert Deadline Propagation?

Der Server übernimmt die Restzeit des eingehenden Aufrufs für ausgehende Aufrufe. Java und Go machen es standardmässig.

Zahlen

Wie viele Aufrufarten hat gRPC?

Vier: unary, server streaming, client streaming und bidirectional streaming.

Wie viele Statuscodes gibt es?

17, von OK (0) bis UNAUTHENTICATED (16).

Wie gross ist das Präfix einer Nachricht?

5 Byte: 1 Byte Kompressions-Flag und 4 Byte Länge.

Wie gross darf eine empfangene Nachricht standardmässig sein?

4 MB beim Go-Server, bei Java und bei .NET.

Vergleich

Unary vs Streaming?

Unary ist einfach und passt zu den meisten Aufrufen. Streaming passt zu Datenströmen und grossen Folgen, ist aber schwerer zu betreiben.

gRPC-Deadline vs HTTP-Timeout?

Die Deadline wird über Grenzen weitergegeben. Ein HTTP-Timeout gilt oft nur lokal pro Client.

DEADLINE_EXCEEDED vs UNAVAILABLE?

DEADLINE_EXCEEDED: die Zeit war um. UNAVAILABLE: der Dienst war nicht erreichbar, meist vorübergehend. Wiederholen ist hier oft sinnvoll.

gRPC-Streaming vs WebSocket?

Beide sind lange Verbindungen. gRPC hat Schema, Status und Deadline. WebSocket ist ein roher Kanal.

Produktion

Welche Fehler wiederholt man?

Vor allem UNAVAILABLE und nur bei idempotenten Aufrufen. Bei Änderungen braucht man eine Idempotenz-Absicherung.

Wie vermeidet man Kettenreaktionen bei Ausfällen?

Mit Deadlines, Propagation und Begrenzung der Wiederholungen (Retry Throttling). Sonst verstärken Retries die Last.

Szenario: Aufrufe enden mit DEADLINE_EXCEEDED, aber der Server hat die Daten geändert. Was tun Sie?

Die Aktion kann trotz Fehler gelaufen sein. Ich mache den Aufruf idempotent, zum Beispiel mit einer Anfrage-ID. Der Client kann dann sicher wiederholen.

Szenario: Ein Streaming-Aufruf bricht nach einer Weile ohne Fehler im Server-Log ab. Was prüfen Sie?

Ich prüfe Proxys, Lastverteiler und Idle-Timeouts. Ich schalte Keepalive-Pings ein und passe die Einstellungen von Client und Server aufeinander an. Zu häufige Pings beantwortet der Server mit GOAWAY.

Design

Wie wähle ich eine Deadline?

Eine begründete Schätzung aus Netz und Verarbeitung, geprüft mit Lasttests. Kurz genug, um Ressourcen zu schützen, lang genug für normale Fälle.

Wann nehme ich Server Streaming?

Für Listen mit vielen Einträgen oder Live-Ereignisse. Ich nehme es nicht, wenn Pagination reicht.

Wie gestalte ich Fehler?

Mit dem passenden Statuscode und einer klaren Meldung. Details mit grpc-status-details-bin oder einer Fehlernachricht, keine Geheimnisse in der Meldung.

Gerüst

  • Warum? Ein Vertrag, generierte Clients, Streaming und Fristen in einem Protokoll.
  • Wie innen? HTTP/2-POST, 5-Byte-Präfix, Trailer mit Status, Header grpc-timeout.
  • Zahlen Vier Aufrufarten, 17 Statuscodes, 4 MB Standardgrösse für Nachrichten.
  • Vergleich Gegen REST, WebSocket, HTTP-Timeout. Unary gegen Streaming.
  • Produktion Hängende Aufrufe, Retries bei Änderungen, Idle-Timeouts bei Streams.
  • Design Deadline immer setzen, weitergeben, idempotent machen, Retries begrenzen.

Beispiel: Ein gRPC-Frame von Hand gebaut

// service Greeter { rpc SayHello (HelloRequest) returns (HelloReply); }
// message HelloRequest { string name = 1; }

msg   = f_len(1, b'Bern')                          # Protobuf: Feld 1, LEN
frame = b'\x00' + struct.pack('>I', len(msg)) + msg # Flag + Länge (4 Byte, Big Endian)
print(hexs(frame))

// Client in Go (Deadline 2 Sekunden):
//   ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
//   defer cancel()
//   reply, err := client.SayHello(ctx, &pb.HelloRequest{Name: "Bern"})
//   // err mit Code DeadlineExceeded, wenn die Frist abläuft
7) gRPC frame: HelloRequest{name='Bern'} (field 1, LEN)
00 00 00 00 06 0a 04 42 65 72 6e  -> flag=0 length=6

Echte Ausgabe, Python 3.12.10 (Frame von Hand gebaut, kein gRPC installiert). Der Go-Client im Kommentar ist nicht ausgeführt.

  1. Das erste Byte 00 ist das Kompressions-Flag. Die Nachricht ist nicht komprimiert.
  2. Die nächsten vier Bytes 00 00 00 06 sind die Länge 6, Big Endian.
  3. Die Nachricht selbst ist 0a 04 42 65 72 6e. 0a ist der Tag (Feld 1, LEN), 04 die Länge und Bern in UTF-8.
  4. Der HTTP/2-Request trägt zusätzlich die Header, zum Beispiel grpc-timeout: 2S für die Frist.

Vergleich

  • Unary: Wie ein normaler Aufruf. Einfach zu testen und zu wiederholen.
  • Server Streaming: Eine Anfrage, viele Antworten. Gut für Ereignisse.
  • Client Streaming: Viele Nachrichten hochladen, eine Antwort.
  • Bidirectional Streaming: Beide Seiten senden frei. Gut für Chat und Live-Abgleich.
  • REST mit Pagination: Seiten statt Stream. Einfacher zu cachen und zu lastverteilen.
  • Message Queue: Entkoppelt Sender und Empfänger zeitlich. gRPC-Aufrufe sind synchron.

Produktion

  1. Hängende Aufrufe: Ohne Deadline blockieren Threads. Lösung: auf jedem Aufruf eine Deadline.
  2. Retry-Sturm: Viele Wiederholungen überlasten einen kranken Dienst. Lösung: Retry Throttling und Begrenzung der Versuche.
  3. Doppelte Änderung: Ein wiederholter Aufruf ändert zweimal. Lösung: Idempotenz mit Anfrage-ID.
  4. Lastverteilung: Eine lange HTTP/2-Verbindung bleibt an einem Backend. Lösung: L7-Lastverteiler oder Client-Side Load Balancing.
  5. Stream bricht ab: Idle-Timeouts in Proxys schliessen die Verbindung. Lösung: Keepalive passend einstellen.
  6. Nachricht zu gross: Fehler bei mehr als 4 MB. Lösung: Streaming oder kleinere Teile, Limit bewusst anheben.

Diagnose: Werkzeuge und Befehle

  • grpcurl: ruft Methoden von der Kommandozeile auf (mit Reflection oder .proto).
  • grpc_cli oder Postman: testen Dienste interaktiv.
  • Logs mit dem Statuscode pro Aufruf: zeigen die Verteilung von DEADLINE_EXCEEDED und UNAVAILABLE.
  • Umgebungsvariablen GRPC_VERBOSITY=debug und GRPC_TRACE (C-Core): zeigen Verbindungs- und Protokolldetails.
  • Wireshark oder curl --http2: HTTP/2-Frames ansehen.
  • Metriken: Aufrufzahl, Latenz und Fehler je Methode und Statuscode.

Senior-Punkte

  1. Deadlines sind Pflicht, nicht Kür. Jeder Aufruf hat eine, und sie wird weitergegeben.
  2. Statuscodes sorgfältig wählen. Sie steuern Retries und Alarme.
  3. Retries nur bei Idempotenz. Und mit Begrenzung, sonst verstärken sie Ausfälle.
  4. Streaming bewusst einsetzen. Es verlangt Gegendruck, Keepalive und Plan für Neustarts.
  5. HTTP/2 verändert die Lastverteilung. Eine Verbindung trägt viele Aufrufe.
  6. Fehlerdetails ohne Geheimnisse. Die Meldung geht zum Client.
