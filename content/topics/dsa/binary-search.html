Binary Search

DSA · Tier 1 · Quellen: Java SE 25 API-Doku java.util.Arrays.binarySearch, java.util.Collections.binarySearch, java.util.TreeMap (floorKey, ceilingKey), CLRS 4. Auflage (2022): Kap. 2 „Getting Started“ (Binary Search als Übung), Kap. 12 „Binary Search Trees“

Kern: Binary Search ist eine Suche, die in jedem Schritt die Hälfte des Suchraums verwirft. Sie braucht eine monotone Eigenschaft: links „nein“, rechts „ja“ (oder sortierte Werte). Dann findet sie die Grenze in O(log n), auf Indizes oder auf möglichen Antworten.

1. Wo sitzt Binary Search?

  1. Suchraum: Der Suchraum ist das Intervall [lo, hi], in dem die Antwort noch liegen kann.
  2. mid: Man prüft das mittlere Element. Das Ergebnis sagt, welche Hälfte sicher weg kann.
  3. Auf dem Index: klassisch auf sortierten Arrays. Gesucht ist ein Wert oder eine Grenze.
  4. Auf der Antwort: Man sucht nicht im Array, sondern über mögliche Antworten. Voraussetzung: eine monotone Prüffunktion ok(x), also erst nur false, dann nur true.
  5. Kosten: O(log n) Schritte mal die Kosten eines Schritts. Bei „auf der Antwort“ ist ein Schritt oft O(n), also O(n log M).

2. Die Reise eines lower bound (die Geschichte zum Merken)

  1. Halboffenes Intervall: lo = 0, hi = n. hi ist exklusiv. Die Antwort n heisst „alle Elemente sind kleiner“.
  2. mid = 3: a[3] = 2 erfüllt die Bedingung. Es könnte die erste 2 sein, also darf mid nicht weg: hi = mid.
  3. mid = 1: wieder erfüllt, hi = 1.
  4. mid = 0: a[0] = 1 erfüllt nicht. mid ist sicher nicht die Antwort: lo = mid + 1.
  5. Ende: lo == hi. Das ist die Antwort. Die Schleife endet immer, weil das Intervall in jedem Schritt kleiner wird.

3. Beispiel: drei Templates und vier Klassiker in Java

Erkennen: sortierte Daten, „finde in O(log n)“, „erstes/letztes Vorkommen“, „kleinstes x, sodass …“, „maximiere das Minimum“, riesiger Antwortbereich (bis 10⁹) bei kleinem n.

Template 1 – exakte Suche, geschlossenes Intervall [lo, hi]:

static int search(int[] a, int target) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {                                    // <= weil hi inklusive ist
        int mid = lo + (hi - lo) / 2;                     // kein Overflow
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1; else hi = mid - 1;
    }
    return -1;
}

Template 2 – lower bound, halboffen [lo, hi), Ergebnis 0 bis n:

static int lowerBound(int[] a, int target) {
    int lo = 0, hi = a.length;                            // hi = n ist ein gültiges Ergebnis
    while (lo < hi) {                                     // < weil hi exklusiv ist
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1; else hi = mid; // hi = mid, nicht mid - 1
    }
    return lo;
}

Template 3 – auf der Antwort: kleinstes x in [lo, hi] mit ok(x) == true:

static int firstTrue(int lo, int hi, IntPredicate ok) {
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (ok.test(mid)) hi = mid; else lo = mid + 1;
    }
    return lo;
}

1. Koko Eating Bananas (auf der Antwort) – O(n log max):

static int minEatingSpeed(int[] piles, int h) {
    int max = Arrays.stream(piles).max().getAsInt();
    return firstTrue(1, max, k -> {
        long hours = 0;
        for (int p : piles) hours += (p + k - 1) / k;    // aufrunden ohne double
        return hours <= h;
    });
}

2. Search in Rotated Sorted Array (ohne Duplikate) – O(log n):

static int searchRotated(int[] a, int target) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        if (a[lo] <= a[mid]) {                            // linke Hälfte sortiert
            if (a[lo] <= target && target < a[mid]) hi = mid - 1; else lo = mid + 1;
        } else {                                          // rechte Hälfte sortiert
            if (a[mid] < target && target <= a[hi]) lo = mid + 1; else hi = mid - 1;
        }
    }
    return -1;
}

3. Find Minimum in Rotated Sorted Array – O(log n):

static int findMin(int[] a) {
    int lo = 0, hi = a.length - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] > a[hi]) lo = mid + 1; else hi = mid;  // Minimum liegt rechts von mid
    }
    return a[lo];
}

Echte Ausgabe, Oracle JDK 17.0.3. Testarray für search: [-1, 0, 3, 5, 9, 12].

  1. lowerBound für 8 liefert 6 = n. Das heisst: alle Elemente sind kleiner. Für 0 liefert es 0.
  2. Arrays.binarySearch findet 3 nicht. Der Einfügepunkt ist 4, also gibt es -(4) - 1 = -5 zurück. Ergebnis ≥ 0 heisst genau dann „gefunden“.
  3. Koko: Mit 4 Bananen pro Stunde braucht sie 1 + 2 + 2 + 3 = 8 Stunden. Mit 3 wären es 10.
  4. Rotated: [4,5,6,7,0,1,2] enthält 0 an Index 4. Das Minimum ist 0. Ein nicht rotiertes Array gibt das erste Element.
  5. (lo + hi) / 2 läuft über und wird negativ. lo + (hi - lo) / 2 und (lo + hi) >>> 1 sind korrekt.

4. Details, die Interviewer fragen

  1. Off-by-one vermeiden: Wähle ein Template und bleib dabei. Geschlossen: lo <= hi, hi = mid - 1. Halboffen: lo < hi, hi = mid.
  2. Endlosschleife: Bei lo < hi und lo = mid kann die Schleife hängen, weil mid abgerundet wird. Darum immer lo = mid + 1, oder mid aufrunden: lo + (hi - lo + 1) / 2.
  3. Erstes und letztes Vorkommen: Erstes = lowerBound(x). Letztes = lowerBound(x + 1) − 1. Anzahl = Differenz.
  4. Arrays.binarySearch bei Duplikaten: Die Doku garantiert nicht, welches Vorkommen gefunden wird. Für „erstes“ braucht man den eigenen lower bound.
  5. Unsortierte Eingabe: Laut Doku ist das Ergebnis dann undefiniert. Sortieren kostet O(n log n), lohnt also nur bei vielen Abfragen.
  6. Auf der Antwort: Grenzen festlegen (kleinste und grösste mögliche Antwort), ok(x) schreiben, Monotonie begründen. Typisch: Koko, Ship Within D Days, Split Array Largest Sum.
  7. Rotated mit Duplikaten: Bei a[lo] == a[mid] == a[hi] weiss man nicht, welche Hälfte sortiert ist. Dann lo++; schlimmster Fall O(n).
  8. TreeMap als Alternative: floorKey und ceilingKey liefern den nächsten kleineren oder grösseren Schlüssel in O(log n), auch bei Einfügungen.
  9. Overflow: (lo + hi) / 2 kann überlaufen. In der Antwort-Suche auch die Prüffunktion mit long rechnen.
  10. So sprichst du beim Coden: „Die Prüfung ist monoton: unter 4 reicht es nicht, ab 4 schon. Ich suche das erste true im Bereich 1 bis max. Ich nehme das halboffene Template: ok(mid) → hi = mid, sonst lo = mid + 1. O(n log max).“

5. Vergleich

  • Geschlossenes Template (lo <= hi): für „finde genau diesen Wert“.
  • Halboffenes Template (lo < hi): für Grenzen: erstes ≥, erstes true. Ergebnis kann n sein.
  • Arrays.binarySearch: fertig, aber kein garantiertes erstes Vorkommen. Negativer Rückgabewert kodiert den Einfügepunkt.
  • Collections.binarySearch: gleiches für Listen. Auf LinkedList ohne Index-Zugriff langsamer.
  • TreeMap/TreeSet: sortiert und veränderbar, O(log n) pro Abfrage und Einfügung.
  • Lineare Suche: O(n), braucht keine Sortierung. Bei wenigen Abfragen oft genug.

6. In der Produktion

  1. Overflow-Bug: (lo + hi) / 2 war lange ein bekannter Fehler in vielen Implementierungen. Er zeigt sich erst bei sehr grossen Arrays.
  2. Unsortierte Daten: binarySearch auf unsortierten Daten wirft keinen Fehler, sondern liefert still falsche Ergebnisse.
  3. Bereichsabfragen: Zeitreihen nach Zeitstempel sortiert halten, dann Start und Ende mit lower bound finden. Datenbank-Indizes (B-Bäume) machen dasselbe.
  4. Fehlersuche im Verlauf: git bisect findet den ersten schlechten Commit per Binary Search.

7. Diagnose

  • Kleine Tests: Array mit 0, 1 und 2 Elementen, Ziel kleiner als alle, grösser als alle, Duplikate.
  • lo, mid, hi ausgeben: Nach jedem Schritt. Bleibt das Intervall gleich, hast du eine Endlosschleife.
  • Invariante aussprechen: „Die Antwort liegt immer in [lo, hi).“ Jede Zuweisung muss sie erhalten.

8. Senior-Punkte

  1. Monotonie ist die eigentliche Voraussetzung, nicht Sortierung. Wer das sieht, löst auch Antwort-Suchen.
  2. Ein Template, immer. Off-by-one-Fehler kommen vom Mischen der Varianten.
  3. Die Doku kennen: Rückgabewert von Arrays.binarySearch, keine Garantie bei Duplikaten, undefiniert bei unsortiert.
  4. Sortieren für eine einzige Suche lohnt nicht. O(n log n) + O(log n) ist schlechter als O(n) linear.

10. Fallen

  • „mid = (lo + hi) / 2 ist immer korrekt.“ → Falsch. Overflow bei grossen Werten. lo + (hi - lo) / 2.
  • „Binary Search braucht ein sortiertes Array.“ → Zu eng. Sie braucht eine monotone Bedingung, auch über Antworten.
  • „Arrays.binarySearch findet das erste Vorkommen.“ → Falsch. Bei Duplikaten ist das nicht garantiert.
  • „Nicht gefunden gibt −1.“ → Nur beim eigenen Code. Die JDK-Methode gibt -(Einfügepunkt) - 1.
  • „lo < hi mit lo = mid geht.“ → Endlosschleife, wenn hi = lo + 1.
  • „Rotated Array mit Duplikaten ist O(log n).“ → Nicht garantiert. Schlimmster Fall O(n).

11. Fragen

Wann denkst du an Binary Search?

Bei sortierten Daten oder einer monotonen Ja/Nein-Bedingung, und wenn O(log n) oder „kleinstes x, sodass …“ gefragt ist.

Warum ist Binary Search O(log n)?

Jeder Schritt halbiert den Suchraum. Nach log₂ n Schritten ist nur ein Element übrig.

Wie berechnest du mid ohne Overflow?

lo + (hi − lo) / 2 oder (lo + hi) >>> 1.

Was ist der Unterschied zwischen lo <= hi und lo < hi?

lo <= hi gehört zum geschlossenen Intervall mit hi = mid − 1. lo < hi gehört zum halboffenen mit hi = mid.

Was ist ein lower bound?

Der erste Index mit a[i] ≥ x. Er ist n, wenn alle kleiner sind.

Wie findest du das letzte Vorkommen von x?

lowerBound(x + 1) − 1, danach prüfen, ob dort wirklich x steht.

Was gibt Arrays.binarySearch zurück, wenn nichts gefunden wird?

−(Einfügepunkt) − 1. Der Einfügepunkt ist der Index des ersten grösseren Elements oder die Länge.

Was ist Binary Search auf der Antwort?

Man sucht über mögliche Antworten statt über Indizes. Man braucht eine monotone Prüffunktion ok(x).

Wie löst du Koko Eating Bananas?

Suche das kleinste k von 1 bis max(piles), für das die Summe von ceil(p / k) ≤ h ist. O(n log max).

Wie suchst du in einem rotierten sortierten Array?

Eine Hälfte um mid ist immer sortiert. Liegt das Ziel in ihrem Bereich, dort suchen, sonst in der anderen.

Wie findest du das Minimum im rotierten Array?

Vergleiche a[mid] mit a[hi]. Ist a[mid] grösser, liegt das Minimum rechts, sonst bei mid oder links.

Warum vergleicht findMin mit a[hi] und nicht mit a[lo]?

Mit a[hi] ist die Entscheidung auch bei nicht rotierten Arrays eindeutig. Mit a[lo] braucht man einen Sonderfall.

Was passiert mit Duplikaten im rotierten Array?

Bei a[lo] == a[mid] == a[hi] ist unklar, welche Seite sortiert ist. Man verkleinert um eins, schlimmster Fall O(n).

Wie vermeidest du eine Endlosschleife?

Jeder Zweig muss das Intervall verkleinern. Bei lo = mid muss mid aufgerundet werden.

Wann nimmst du TreeMap statt Binary Search?

Wenn die Daten sich ändern. TreeMap hält sie sortiert, floorKey und ceilingKey sind O(log n).

Lohnt sich Sortieren für eine einzige Suche?

Nein. O(n log n) für das Sortieren ist teurer als eine lineare Suche in O(n).

Szenario: Deine Suche hängt bei zwei Elementen. Was prüfst du?

Ob ein Zweig lo = mid setzt, während mid abgerundet wird. Dann ändert sich nichts. Fix: lo = mid + 1 oder mid aufrunden.

Szenario: Der Interviewer gibt dir n ≤ 10⁵ und Werte bis 10⁹ und fragt nach der „kleinsten Kapazität“. Woran denkst du?

An Binary Search auf der Antwort. Bereich von max(Gewicht) bis Summe, ok(x) prüft in O(n), gesamt O(n log Summe).

Szenario: Eine Bibliothek liefert falsche Treffer von binarySearch, aber keinen Fehler. Was vermutest du?

Die Daten sind nicht sortiert, oder mit einem anderen Comparator sortiert als gesucht. Laut Doku ist das Ergebnis dann undefiniert.
