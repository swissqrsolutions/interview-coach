Big-O: Zeit und Speicher

Kern: Big-O ist eine obere Schranke dafür, wie Laufzeit oder Speicher mit der Eingabegrösse n wachsen. Es ignoriert Konstanten und kleine Terme. Im Interview sagst du nach jeder Lösung: „Zeit O(…), Speicher O(…), weil …“.

Antwort-Muster

Frage: Wie bestimmst du die Komplexität einer Lösung?

  1. Mechanismus: Ich benenne n, zähle die Schleifen und kenne die API-Kosten wie bei contains.
  2. Zahl: Verschachtelt multipliziere ich, nacheinander addiere ich. Danach streiche ich Konstanten und kleine Terme.
  3. Trade-off: Eine Map macht O(n²) zu O(n), kostet aber O(n) Speicher.
  4. Produktion: Ein contains auf einer Liste in einer Schleife ist im Test unsichtbar und bei grossen Daten sehr langsam.

1. Die Reise einer Komplexitätsanalyse

  1. n benennen: Du sagst zuerst, was n ist. „n ist die Länge des Arrays.“ Bei zwei Eingaben nimmst du zwei Variablen, z. B. n und m.
  2. Schleifen zählen: Eine Schleife über n ist O(n). Eine Schleife in einer Schleife ist O(n · n) = O(n²).
  3. Nacheinander addieren: Erst sortieren, dann einmal durchlaufen: O(n log n) + O(n). Das ist O(n log n).
  4. Versteckte Kosten: list.contains in einer Schleife ist selbst O(n). Zusammen also O(n²). Darum musst du die Kosten der Java-API kennen.
  5. Vereinfachen: Konstanten und kleinere Terme fallen weg. O(2n + 10) wird O(n).
  6. Speicher: Du zählst nur den Zusatzspeicher, also Maps, Kopien und Rekursionstiefe. Die Eingabe zählt man meist nicht mit.
  7. Laut sagen: Ein Satz mit Begründung. „Zeit O(n), weil jedes Element einmal in die Map geht. Speicher O(n) für die Map.“

2. Aufbau

  1. Wachstumsklasse: Big-O sortiert Algorithmen in Klassen. Beispiel: O(n) wächst linear mit n.
  2. Konstanten fallen weg: 3n + 5 ist O(n). Nur der grösste Term zählt.
  3. Zeit und Speicher: Beide bekommen ein eigenes Big-O. Rekursion kostet Speicher auf dem Call Stack.
  4. Eingabegrösse als Hinweis: Die Grenzen in der Aufgabe verraten die Zielkomplexität. Bei n bis 10⁵ ist O(n²) zu langsam.
  5. Faustregel: Ein moderner Rechner schafft grob 10⁸ einfache Schritte pro Sekunde. Das ist eine Schätzung, keine Messung.

3. Details, die Interviewer fragen

  1. O, Ω, Θ: O ist eine obere Schranke. Ω ist eine untere Schranke. Θ ist eine genaue Schranke, also beide zusammen. Im Interview meint „Big-O“ meist die enge obere Schranke des schlechtesten Falls.
  2. Best, Average, Worst Case: Das sind verschiedene Eingaben. Es sind nicht verschiedene Schranken. Quicksort ist im Durchschnitt O(n log n). Im schlechtesten Fall ist es O(n²).
  3. Amortisiert: Das ist der Durchschnitt über eine Folge von Operationen, ohne Zufall. n-mal ArrayList.add kostet zusammen O(n). Das sind O(1) pro add. Ein einzelnes add mit Resize kostet O(n).
  4. Amortisiert ≠ Average Case: Average Case hängt von zufälligen Eingaben ab. Amortisiert gilt für jede Folge. Es ist garantiert.
  5. Speicher der Rekursion: Jeder offene Aufruf liegt auf dem Call Stack. Rekursion mit Tiefe n kostet O(n) Speicher. Das gilt auch ohne Datenstruktur.
  6. Log-Basis: Die Basis spielt in Big-O keine Rolle. log₂ n und log₁₀ n unterscheiden sich nur um eine Konstante.
  7. Zwei Eingaben: Bei zwei Listen der Grösse n und m schreibst du O(n + m) oder O(n · m). Du schreibst nicht einfach O(n).
  8. Sortieren ist O(n log n): Vergleichsbasiertes Sortieren ist im schlechtesten Fall nicht besser als Ω(n log n). Darum ist „erst sortieren“ nie gratis.
  9. String-Operationen: substring, +, toCharArray und equals sind O(Länge). In einer Schleife zählt das mit.
  10. Hashing ist O(1) im Durchschnitt: HashMap.get ist nur bei guter Hash-Verteilung O(1). Der Schlüssel muss gehasht werden. Bei einem String der Länge k kostet das beim ersten Mal O(k).
  11. So sprichst du beim Coden: Nenne zuerst die naive Lösung mit Komplexität. Benenne dann den Engpass, z. B. „Das innere contains ist O(n).“ Nenne dann die Verbesserung, z. B. „Ein HashSet macht den Lookup O(1).“ Am Ende sagst du Zeit und Speicher mit Begründung.

4. Fallen

  • „O(2n) ist langsamer als O(n).“ → Falsch. Beide sind O(n). Konstanten fallen weg.
  • „HashMap ist immer O(1).“ → Falsch. Nur im Durchschnitt bei guter Hash-Verteilung.
  • „Amortisiert heisst Durchschnitt über zufällige Eingaben.“ → Falsch. Es ist der Durchschnitt über eine Folge von Operationen, garantiert.
  • „Rekursion braucht keinen Speicher.“ → Falsch. Jeder offene Aufruf liegt auf dem Stack: O(Tiefe).
  • „Zwei Schleifen sind O(n²).“ → Nur wenn verschachtelt. Nacheinander sind sie O(n).
  • „list.contains ist billig.“ → Falsch. Bei ArrayList und LinkedList ist es O(n).

5. Selbsttest

Warum?

Was ist Big-O?

Eine obere Schranke für das Wachstum von Laufzeit oder Speicher mit der Eingabegrösse. Konstanten und kleinere Terme fallen weg.

Warum ist ArrayList.add amortisiert O(1)?

Das Array wächst um einen Faktor (im JDK ca. 1,5). Kopiert wird nur selten, darum sind die Kopierkosten über alle adds verteilt O(1).

Warum ist String += in einer Schleife langsam?

Jeder Schritt kopiert den ganzen String. Summe 1 + 2 + … + n = O(n²). StringBuilder ist O(n).

Kann Sortieren mit Vergleichen schneller als n log n sein?

Nein, nicht im schlechtesten Fall. Die untere Schranke ist Ω(n log n). Counting Sort umgeht das, weil es nicht vergleicht.

Wie innen?

Was ist der Unterschied zwischen O, Ω und Θ?

O ist eine obere, Ω eine untere Schranke. Θ heisst, beide gelten mit derselben Funktion.

Was heisst amortisiert O(1)?

Eine Folge von n Operationen kostet zusammen O(n). Einzelne Operationen können teuer sein, z. B. ein Resize.

Wie viel Speicher braucht eine Rekursion?

O(maximale Tiefe) auf dem Call Stack. Bei einer Kette der Länge n also O(n).

Was ist der Unterschied zwischen Average Case und amortisiert?

Average Case mittelt über zufällige Eingaben. Amortisiert mittelt über eine Operationsfolge und gilt für jede Eingabe.

Warum spielt die Log-Basis keine Rolle?

Logarithmen verschiedener Basen unterscheiden sich nur um einen konstanten Faktor.

Zahlen

Wie schätzt du aus n die erwartete Lösung?

Grob 10⁸ Schritte pro Sekunde. n bis 10⁵ braucht O(n log n) oder besser, n bis 20 erlaubt O(2ⁿ).

Was kostet ArrayList.add(0, x)?

O(n). Alle Elemente rücken eine Position nach rechts.

Was kostet LinkedList.get(i)?

O(n). Die Liste läuft vom näheren Ende bis zum Index.

Was ist die Komplexität von zwei verschachtelten Schleifen über verschiedene Arrays?

O(n · m). Nicht O(n²), wenn die Grössen verschieden sein können.

Vergleich

Was kosten TreeMap.get und put?

Garantiert O(log n), weil TreeMap ein Rot-Schwarz-Baum ist.

Was kosten PriorityQueue.offer, poll und peek?

offer und poll O(log n), peek O(1). contains und remove(Object) O(n).

Welche Komplexität hat Arrays.sort?

O(n log n). Für Primitive Dual-Pivot Quicksort, für Objekte ein stabiler Mergesort (TimSort).

Produktion

Was kostet HashSet.contains im schlechtesten Fall?

Mit vielen Kollisionen mehr als O(1). Seit Java 8 begrenzen Baum-Buckets das auf O(log n) pro Bucket.

Szenario: Ein Import läuft mit 1 000 Zeilen in 1 s, mit 10 000 in 100 s. Was vermutest du?

10× mehr Daten, 100× mehr Zeit: O(n²). Ich suche ein contains, remove oder indexOf auf einer Liste in einer Schleife und ersetze es durch ein HashSet.

Szenario: Deine rekursive Lösung ist korrekt, aber bei grosser Eingabe kommt ein StackOverflowError. Was sagst du?

Die Rekursionstiefe ist O(n) und sprengt den Thread-Stack. Ich schreibe sie iterativ mit einem ArrayDeque als Stack um. Zeit bleibt gleich, Speicher liegt dann auf dem Heap.

Design

Wie sagst du die Komplexität im Interview?

n definieren, dann „Zeit O(…), weil …; Speicher O(…) für …“. Immer mit Grund.

Szenario: Der Interviewer fragt „Geht es schneller?“. Was tust du?

Ich nenne den Engpass und die untere Grenze. Wenn ich jedes Element ansehen muss, ist O(n) das Minimum. Dann prüfe ich, ob Speicher gegen Zeit hilft, z. B. eine Map.

Warum nennst du im Interview zuerst die naive Lösung?

Sie zeigt Struktur und gibt dir einen Engpass zum Verbessern. Danach nennst du Zeit und Speicher der besseren Lösung mit Begründung.

Warum zählst du die Eingabe beim Speicher meist nicht mit?

Die Eingabe ist schon da. Du zählst nur den Zusatzspeicher wie Maps, Kopien und die Rekursionstiefe.

Mehr

Gerüst

  • Warum? Big-O zeigt, wie Zeit und Speicher mit n wachsen, und trennt Lösungen für grosse Daten.
  • Wie innen? Nur der grösste Term zählt. Schleifen in Schleifen multiplizieren, Schleifen nacheinander addieren.
  • Zahlen Faustregel: ca. 10⁸ Schritte pro Sekunde. n bis 10⁵ braucht O(n log n), n bis 20 erlaubt O(2ⁿ).
  • Vergleich HashSet-Lookup O(1), TreeMap O(log n), list.contains O(n). ArrayList.add ist amortisiert O(1).
  • Produktion Verstecktes O(n²): contains oder String += in einer Schleife. Test mit 100 Einträgen sieht es nicht.
  • Design Zeit gegen Speicher tauschen: Eine Map macht O(n²) zu O(n), kostet aber O(n) Speicher.

Beispiel: Komplexität messen statt raten

Aufgabe 1 – Contains Duplicate (drei Lösungen, drei Klassen):

static long ops;  // zählt Vergleiche bzw. Set-Operationen

static boolean dupBrute(int[] a) {            // Zeit O(n^2), Speicher O(1)
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++) {
            ops++;
            if (a[i] == a[j]) return true;
        }
    return false;
}

static boolean dupSort(int[] a) {             // Zeit O(n log n), Speicher O(n) für die Kopie
    Integer[] b = Arrays.stream(a).boxed().toArray(Integer[]::new);
    Arrays.sort(b, (x, y) -> { ops++; return Integer.compare(x, y); });
    for (int i = 1; i < b.length; i++) { ops++; if (b[i].equals(b[i - 1])) return true; }
    return false;
}

static boolean dupSet(int[] a) {              // Zeit O(n), Speicher O(n)
    Set<Integer> seen = new HashSet<>();
    for (int x : a) { ops++; if (!seen.add(x)) return true; }
    return false;
}

Aufgabe 2 – Fibonacci (exponentiell gegen linear):

static long fibNaive(int n) {                 // Zeit O(2^n), Speicher O(n) Stack
    calls++;
    return n < 2 ? n : fibNaive(n - 1) + fibNaive(n - 2);
}

static long fibMemo(int n, long[] memo) {     // Zeit O(n), Speicher O(n)
    calls++;
    if (n < 2) return n;
    if (memo[n] != 0) return memo[n];
    return memo[n] = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
}

Aufgabe 3 – Binary Search: Schritte zählen, Aufgabe 4 – ArrayList-Kapazität (amortisiert), Aufgabe 5 – String-Verkettung:

static long binarySteps(int n, int target) {  // Zeit O(log n)
    int lo = 0, hi = n - 1; long steps = 0;
    while (lo <= hi) {
        steps++;
        int mid = lo + (hi - lo) / 2;
        if (mid == target) break;
        if (mid < target) lo = mid + 1; else hi = mid - 1;
    }
    return steps;
}

Echte Ausgabe, Oracle JDK 17.0.3. Die Zeiten in 5) sind eine einzelne Messung ohne Warm-up; nur die Grössenordnung zählt.

  1. Contains Duplicate: n = 20 000. Brute Force macht n(n−1)/2 ≈ 200 Mio. Vergleiche. Sortieren braucht ca. 280 000 Vergleiche, das ist nahe n · log₂ n ≈ 286 000. Das Set braucht genau n = 20 000 Schritte.
  2. Fibonacci: Naive Rekursion ruft sich 2,7 Mio. Mal auf. Mit Memoization (Ergebnisse merken) sind es 59 Aufrufe. Das ist der Sprung von O(2ⁿ) zu O(n).
  3. Binary Search: 1000× mehr Daten heisst nur 10 Schritte mehr. Das ist O(log n): log₂ 10⁹ ≈ 30.
  4. ArrayList: Die Kapazität wächst 10 → 15 → 22 → 33 … also um ca. Faktor 1,5. Nur bei diesen 6 Sprüngen wird kopiert. Darum ist add amortisiert O(1). Der Wachstumsfaktor ist eine JDK-Implementierung, die Doku legt ihn nicht fest.
  5. String +=: Jeder += kopiert den ganzen String neu. Das ist 1 + 2 + … + n = O(n²). StringBuilder hängt amortisiert in O(1) an.

Vergleich: Kosten der Java Collections

  • ArrayList: get, set, size O(1). add am Ende amortisiert O(1). add(0, x), remove(i), contains, indexOf O(n).
  • LinkedList: addFirst, addLast, removeFirst O(1). get(i) O(n), denn sie läuft vom näheren Ende bis zum Index.
  • HashMap / HashSet: get, put, contains, remove im Durchschnitt O(1). Iteration ist proportional zu Kapazität plus Grösse.
  • TreeMap / TreeSet: get, put, remove, containsKey garantiert O(log n). Dazu floorKey, ceilingKey für „nächster kleinerer/grösserer Schlüssel“.
  • ArrayDeque: push, pop, offer, poll, peek amortisiert O(1). contains und remove(Object) O(n).
  • PriorityQueue: offer, poll O(log n). peek, size O(1). contains, remove(Object) O(n).
  • Arrays.sort(int[]): Dual-Pivot Quicksort, laut Doku O(n log n) auf allen Daten. Nicht stabil, aber bei Primitiven egal.
  • Arrays.sort(Object[]) / Collections.sort: stabiler, adaptiver Mergesort (TimSort). Fast sortierte Daten brauchen nur ca. n Vergleiche.
  • Arrays.binarySearch: O(log n), nur auf sortierten Daten.

In der Produktion

  1. Verstecktes O(n²): list.contains oder list.remove in einer Schleife. Bei 100 Einträgen im Test unsichtbar, bei 100 000 in Produktion Minuten. Lösung: HashSet für Lookups.
  2. String-Verkettung in Schleifen: Logs oder CSV mit += bauen ist O(n²). Lösung: StringBuilder oder String.join.
  3. N+1-Abfragen: Eine Datenbankabfrage pro Element ist O(n) Netzwerk-Roundtrips. Lösung: eine Abfrage mit IN oder ein Join.
  4. Speicher statt Zeit: Eine Map über alle Daten ist O(n) Speicher. Bei Millionen Einträgen droht ein OutOfMemoryError. Lösung: streamen, partitionieren oder in der Datenbank rechnen.
  5. Tiefe Rekursion: Rekursion mit Tiefe n wirft bei grossen Eingaben StackOverflowError. Lösung: iterativ mit eigenem Stack.

Diagnose: Werkzeuge und Vorgehen

  • Verdoppelungstest: Eingabe verdoppeln, Zeit messen. Faktor 2 heisst O(n), Faktor 4 heisst O(n²).
  • Zähler im Code: Wie oben ops++. Zählt Schritte unabhängig von JIT und CPU.
  • JMH: das Benchmark-Werkzeug von OpenJDK. Es macht Warm-up und verhindert, dass der JIT toten Code entfernt.
  • Profiler (async-profiler, JFR, IntelliJ): zeigt die heisse Methode, z. B. viel Zeit in ArrayList.indexOf.
  • Im Interview ohne Werkzeuge: Schleifen zählen, API-Kosten nennen, an einem kleinen Beispiel von Hand durchgehen.

Senior-Punkte

  1. Big-O ist nicht alles. Konstanten und Cache-Verhalten zählen auch. Ein ArrayList-Scan über 50 Elemente kann schneller sein als eine HashMap.
  2. Zeit gegen Speicher ist eine Entscheidung. Eine Map macht O(n²) zu O(n), kostet aber O(n) Speicher. Du nennst beide Seiten.
  3. Zuerst die Grenze lesen. Die Grösse von n bestimmt die Zielkomplexität. Das spart Zeit beim Suchen nach der Lösung.
  4. Amortisiert ist nicht „immer schnell“. Ein einzelner Resize kann eine Latenzspitze sein. In heissen Pfaden setzt man die Grösse vorher.
  5. Erst korrekt, dann schnell. Im Interview zuerst die einfache Lösung nennen, dann verbessern. Das zeigt Struktur.
