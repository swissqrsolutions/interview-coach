DOM vs SAX vs StAX

Kern: DOM liest das ganze Dokument in einen Baum im Speicher. SAX liest einmal vorwärts und ruft Callbacks auf (Push). StAX liest vorwärts, aber der Code holt die Events selbst (Pull). Bei grossen Dateien ist DOM das Risiko, weil der Speicher mit der Dateigrösse wächst.

Antwort-Muster

Frage: Was ist der Unterschied zwischen DOM, SAX und StAX?

  1. Mechanismus: DOM baut einen Baum und erlaubt Zugriff und Änderung. SAX pusht Events in einen Handler. StAX lässt den Code Events per Cursor abrufen.
  2. Zahl: Im Test brauchte eine 23-MB-Datei in DOM zwischen 128 und 256 MB Heap. Eine 119-MB-Datei lief mit 32 MB Heap nur mit SAX und StAX.
  3. Trade-off: DOM ist bequem, kostet aber Speicher. SAX und StAX sind sparsam, aber nur vorwärts und mit mehr Code.
  4. Produktion: Bei grossen Nachrichten nehme ich StAX und baue nur kleine Teile als Objekte. Alle Parser konfiguriere ich gegen XXE.

1. Wie ein Dokument gelesen wird, in 6 Schritten

  1. Factory holen: DocumentBuilderFactory, SAXParserFactory oder XMLInputFactory sind der Einstieg (JAXP). Hier setzt man auch die Sicherheitseinstellungen.
  2. Parser erzeugen: Die Factory baut DocumentBuilder, SAXParser oder einen XMLStreamReader.
  3. Quelle öffnen: Datei, InputStream oder InputSource. Die Zeichenkodierung steht in der XML-Deklaration.
  4. Tokens lesen: Der Parser erkennt Start-Tags, Text, Attribute und Kommentare in Dokumentreihenfolge.
  5. Tokens verarbeiten: DOM baut daraus einen Baum. SAX ruft Methoden eines ContentHandler. Bei StAX ruft der Code next() auf.
  6. Ergebnis: DOM gibt ein Document zurück, und alles liegt im Speicher. SAX und StAX halten nur den aktuellen Zustand.

2. Aufbau

  1. Factory: Jede Technik hat eine Factory. Dort stellt man Namespaces, Validierung und Sicherheit ein.
  2. DOM-Baum: Document ist die Wurzel. Element, Attr und Text sind Knoten. Man navigiert und ändert sie.
  3. SAX-Handler: Man erweitert DefaultHandler und überschreibt die Callbacks, die man braucht.
  4. StAX-Reader: Der XMLStreamReader ist laut Doku der niedrigste und effizienteste Weg, XML zu lesen. XMLEventReader liefert Event-Objekte.
  5. Schreiben: DOM schreibt man mit einem Transformer. StAX hat den XMLStreamWriter. SAX liest nur.
  6. Gemeinsame Basis: Alle drei laufen im JDK ohne Zusatzbibliothek (Modul java.xml).

3. Details

  1. DOM: Er baut den ganzen Baum im Speicher. Man hat Zugriff in beliebiger Reihenfolge und kann Knoten ändern. Das ist bequem, kostet aber Speicher. Das Ergebnis von parse() ist ein Document.
  2. DOM-Speicher im Test: Eine 23-MB-Datei lief mit 256 MB Heap, aber nicht mit 128 MB. Eine 119-MB-Datei scheiterte mit 1 GB und lief mit 4 GB. Der Speicher ist also ein Mehrfaches der Dateigrösse. Der Wert hängt vom Inhalt ab.
  3. DOM-Standardwerte: Namespace-aware ist false. Dann liefert getLocalName() den Wert null. Validating, coalescing, ignoringComments und XInclude sind false. expandEntityReferences ist true.
  4. SAX: Der Parser ruft startElement, characters und endElement auf. Es gibt zu jedem startElement ein endElement, auch bei leeren Elementen. Der Code muss den Zustand selbst führen, oft mit einem Stack.
  5. SAX characters(): Text kann in mehreren Stücken kommen. Im Test lieferte Tom &amp; Jerry drei Aufrufe. Man sammelt den Text in einem StringBuilder und wertet ihn in endElement aus.
  6. SAX und Namespaces: Die SAXParserFactory ist standardmässig nicht namespace-aware. Im Test waren uri und localName dann leer. Mit setNamespaceAware(true) waren sie gefüllt.
  7. SAX Locator: Er gibt Zeile und Spalte. Er liefert nur während der Callbacks korrekte Werte. Damit baut man gute Fehlermeldungen.
  8. StAX: Der Code holt Events mit next(). Der Reader ist laut Doku vorwärts und read-only. Der Cursor steht immer auf dem aktuellen Event, und der Start-Zustand ist START_DOCUMENT.
  9. StAX Text: isCoalescing ist standardmässig false. Im Test gab Tom &amp; Jerry drei CHARACTERS-Events, mit true eines. getElementText() liefert immer zusammengefügten Text und wirft bei Kindelementen eine Exception.
  10. StAX-Standardwerte: isNamespaceAware ist true. supportDTD ist true. isReplacingEntityReferences ist true. Der Wert für externe Entities ist in der Doku nicht festgelegt.
  11. StAX seit Java 6: XMLStreamReader hat das Tag Since 1.6. getTextCharacters() liefert ein kurzlebiges Array. Man darf es nicht behalten.
  12. Push gegen Pull: Bei SAX steuert der Parser den Ablauf. Bei StAX steuert der Code ihn. StAX ist dadurch leichter zu lesen und kann zwischen Elementen andere Dinge tun.
  13. StAX mit JAXB: Der Unmarshaller akzeptiert einen XMLStreamReader auf START_ELEMENT. Danach steht der Reader hinter dem Element. So liest man eine grosse Datei Element für Element als Objekte.
  14. XXE: Im Test las DOM mit Standard-Einstellungen eine lokale Datei über eine externe Entity. StAX tat es auch. Mit FEATURE_SECURE_PROCESSING blockierte DOM den Zugriff. Bei StAX hilft SUPPORT_DTD=false. OWASP sagt, StAX kenne FEATURE_SECURE_PROCESSING nicht.

4. Fallen

  • „DOM ist schneller, weil der Baum im Speicher liegt.“ → Falsch. DOM braucht Speicher und Zeit zum Aufbau. Im Test war er bei der grossen Datei mit 4 GB Heap am langsamsten.
  • „SAX ruft characters() einmal pro Element.“ → Falsch. Text kann in mehreren Stücken kommen. Man sammelt ihn.
  • „Der DOM-Parser kennt Namespaces von Haus aus.“ → Falsch. Der Standard ist nicht namespace-aware, und getLocalName() gibt null.
  • „StAX ist dasselbe wie SAX.“ → Falsch. SAX pusht, StAX pullt. Der Code steuert bei StAX den Ablauf.
  • „Der Standard-Parser ist sicher.“ → Falsch. Im Test las er eine lokale Datei über eine externe Entity.
  • „Mit StAX kann man zurückspringen.“ → Falsch. Der Reader geht nur vorwärts. Wer zurück will, baut selbst Zustand auf oder nutzt DOM.

5. Selbsttest

Warum?

Warum braucht DOM so viel Speicher?

Jedes Element, Attribut und jeder Text ist ein eigenes Objekt mit Verweisen. Der ganze Baum liegt im Heap. Im Test brauchte eine 23-MB-Datei mehr als 128 MB.

Warum nimmt man bei grossen Dateien SAX oder StAX?

Beide lesen vorwärts und halten nur den aktuellen Zustand. Der Speicher hängt nicht von der Dateigrösse ab.

Warum ist StAX oft angenehmer als SAX?

Der Code steuert den Ablauf mit einer Schleife. Es gibt keine Callbacks, und man kann Zustand in lokalen Variablen halten.

Wie innen?

Wie funktioniert SAX?

Ein Parser liest vorwärts und ruft Methoden eines ContentHandler auf. Zu jedem startElement kommt ein endElement. Text kommt in Stücken.

Wie funktioniert StAX?

Ein XMLStreamReader steht auf dem aktuellen Event. Der Code ruft next() und fragt Name, Text oder Attribute ab.

Was ist der Unterschied zwischen XMLStreamReader und XMLEventReader?

Der StreamReader ist ein Cursor mit Abfragemethoden und der effizienteste Weg. Der EventReader liefert Event-Objekte, die man weitergeben kann.

Warum liefert characters() manchmal Teile?

Die Spezifikation erlaubt es dem Parser, zusammenhängenden Text zu teilen. Im Test gab es für Text mit einem Entity drei Aufrufe.

Wie schreibt man XML mit diesen APIs?

DOM mit einem Transformer. StAX mit XMLStreamWriter. SAX hat keine Schreib-API.

Wie bekommt man bei SAX die Zeilennummer?

Über den Locator. Er liefert nur während der Callbacks gültige Werte.

Wie kombiniert man StAX und JAXB?

Man liest mit StAX bis zu einem Element und übergibt den Reader dem Unmarshaller. Er liest das Element als Objekt, und der Reader steht danach dahinter.

Zahlen

Welche Namespace-Standardwerte gelten?

DocumentBuilderFactory und SAXParserFactory sind standardmässig nicht namespace-aware. XMLInputFactory ist es standardmässig.

Welche StAX-Standardwerte kennen Sie?

isCoalescing false, supportDTD true, isReplacingEntityReferences true, isNamespaceAware true.

Seit wann gibt es StAX im JDK?

Seit Java 6. Das Tag Since 1.6 steht bei XMLStreamReader.

Wie viel Speicher braucht DOM?

Ein Mehrfaches der Dateigrösse. Im Test lief eine 23-MB-Datei mit 256 MB, aber nicht mit 128 MB. Der genaue Faktor hängt vom Inhalt ab.

Vergleich

DOM gegen SAX gegen StAX?

DOM: Baum, bequem, viel Speicher. SAX: Push, sparsam, Zustand selbst führen. StAX: Pull, sparsam, Code steuert den Ablauf.

Wann nimmt man DOM?

Bei kleinen Dokumenten, wenn man in beliebiger Reihenfolge zugreift, mit XPath arbeitet oder das Dokument ändert.

Wann nimmt man SAX und wann StAX?

Beide für Ströme und grosse Dateien. StAX, wenn der Ablauf klar im Code stehen soll. SAX, wenn ein Handler-Modell passt.

DOM gegen JAXB?

DOM liefert einen allgemeinen Baum. JAXB liefert typisierte Objekte nach der XSD und braucht eine feste Struktur.

Produktion

Szenario: Ein Import grosser XML-Dateien stürzt mit OutOfMemoryError ab. Was tun Sie?

Ich ersetze DOM durch StAX. Ich lese Element für Element und baue nur ein Objekt je Datensatz. Dazu setze ich eine Grössengrenze für Eingaben.

Szenario: Ein Feld enthält manchmal nur den Teil vor einem „&“. Warum?

Der SAX-Handler nimmt nur den ersten characters()-Aufruf. Ich sammle den Text in einem StringBuilder und werte ihn in endElement aus.

Szenario: getLocalName() liefert null. Warum?

Der DOM-Parser ist nicht namespace-aware. Ich setze setNamespaceAware(true) an der Factory.

Szenario: Ein Upload-Endpoint liest fremde XML-Dateien. Wie sichern Sie den Parser?

Ich verbiete DOCTYPE oder deaktiviere DTDs und externe Entities, bei StAX mit SUPPORT_DTD false. Ich teste mit einer XXE-Datei, dass sie scheitert.

Design

Wie verarbeiten Sie eine 2-GB-Datei mit Millionen von Datensätzen?

Mit StAX als Strom. Pro Datensatz ein Unmarshal mit JAXB oder ein kleiner DOM. Verarbeitung und Schreiben in Batches.

Teilt man Parser zwischen Threads?

Nein. Die JDK-Doku macht dazu keine Zusage. Man erzeugt Parser pro Aufruf oder nutzt reset() für Wiederverwendung im selben Thread.

Wie stoppt man früh, wenn man das Gesuchte gefunden hat?

Mit StAX beendet man einfach die Schleife und schliesst den Reader. Das ist ein Vorteil gegenüber DOM, das immer alles liest.

Wie testet man Parser-Code auf XXE?

Mit einer Testdatei, die eine externe Entity auf eine lokale Datei enthält. Der Test erwartet einen Fehler statt des Dateiinhalts.

Mehr

Gerüst

  • Warum? Man wählt je nach Dateigrösse und Zugriffsmuster den passenden Parser.
  • Wie innen? DOM baut den Baum. SAX pusht Callbacks. StAX pullt Events mit einem Cursor.
  • Zahlen 23 MB brauchen im DOM zwischen 128 und 256 MB. Namespace-aware Standard false (DOM, SAX), true (StAX).
  • Vergleich DOM für klein und flexibel, StAX für gross und klar, SAX für Handler-Modelle.
  • Produktion OutOfMemoryError bei DOM. characters() in Stücken. XXE bei Standard-Einstellungen.
  • Design Strom plus Objekt je Datensatz, Parser pro Aufruf, XXE-Test.

// SAX: Text sammeln, in endElement auswerten
public void characters(char[] ch, int st, int len) { if (in) text.append(ch, st, len); }
public void endElement(String u, String l, String q) { if (q.equals("betrag")) sum = sum.add(new BigDecimal(text.toString())); }

// StAX: Schleife mit Cursor
while (r.hasNext())
  if (r.next() == XMLStreamConstants.START_ELEMENT && r.getLocalName().equals("betrag"))
    sum = sum.add(new BigDecimal(r.getElementText()));

Vergleich

  • DOM: Baum im Speicher, wahlfreier Zugriff, änderbar. Gut für kleine Dokumente und XPath.
  • SAX: Push mit Callbacks, nur vorwärts, kein Schreiben. Sparsam, aber Zustand von Hand.
  • StAX Cursor: XMLStreamReader, Pull, nur vorwärts, sparsam und schnell.
  • StAX Iterator: XMLEventReader, Pull mit Event-Objekten. Bequemer, mit mehr Objekten.
  • JAXB: Typisierte Objekte nach XSD, aufbauend auf einem dieser Parser.

Produktion

  1. OutOfMemoryError beim Import: DOM hält die ganze Datei. Lösung: StAX und ein Objekt je Datensatz.
  2. Abgeschnittene Texte: Der SAX-Handler liest nur das erste characters(). Lösung: StringBuilder und Auswertung in endElement.
  3. Namespace-Fehler: getLocalName() ist null oder Elemente werden nicht gefunden. Lösung: setNamespaceAware(true).
  4. XXE: Ein Standard-Parser liest lokale Dateien. Lösung: DOCTYPE verbieten oder DTD und externe Entities abschalten, bei StAX SUPPORT_DTD false.
  5. Billion Laughs: Ein verschachteltes Entity-Dokument erzeugt riesige Texte. Lösung: DOCTYPE verbieten. Das JDK begrenzt Expansionen standardmässig auf 64000.
  6. Geteilter Parser: Fehler unter Last. Lösung: Parser pro Aufruf erzeugen. Factories gelten nicht als thread-sicher, die Doku sagt dazu nichts.

Diagnose: Werkzeuge und Befehle

  • java -Xmx64m ...: Mit kleinem Heap testen, ob ein Parser als Strom arbeitet.
  • jcmd <pid> GC.class_histogram: Sehr viele DOM-Knotenobjekte zeigen einen Baum im Heap.
  • Heap Dump mit Eclipse MAT: Wer hält das Document?
  • JFR oder ein Profiler: Zeit im Parser gegen Zeit in der Verarbeitung trennen.
  • Locator im SAX-Handler: Zeile und Spalte bei Fehlern in die Meldung schreiben.
  • XXE-Testdatei im Unit-Test: Der Parser muss sie ablehnen.

Senior-Punkte

  1. Grösse und Zugriff entscheiden. Klein und flexibel gibt DOM. Gross oder Strom gibt StAX.
  2. Strom plus Objekt je Datensatz. StAX liest die Struktur, JAXB oder ein kleiner DOM baut das Einzelne. So bleibt der Speicher flach.
  3. Eingaben begrenzen. Grössenlimit und Timeouts gehören an jeden Endpoint, der fremdes XML liest.
  4. Sicherheit in der Factory. Jede Parser-Art hat eigene Schalter. Man kennt sie und testet sie.
  5. Text ist nie ein einziges Stück. Wer das vergisst, verliert Daten bei Entities.
  6. Messen statt raten. Ein Test mit kleinem Heap zeigt in Minuten, ob ein Import skaliert.
