Backfill und idempotente DAGs

Kern: Ein Backfill lässt einen DAG für vergangene Zeiträume laufen. Ein Task ist idempotent, wenn ein zweiter Lauf mit denselben Eingaben dasselbe Ergebnis gibt. Nur idempotente Tasks sind bei Retries, Backfills und Neustarts sicher.

Antwort-Muster

Frage: Was ist ein Backfill, und wie macht man einen DAG idempotent?

  1. Mechanismus: Ein Backfill erstellt DAG Runs für jedes Data Interval im Zeitraum. Jeder Task liest und schreibt nur sein eigenes Intervall.
  2. Zahl: Catchup ist standardmässig aus (catchup_by_default=False). Im Beispiel sind nach zwei Läufen der append-Variante 4 Zeilen statt 2 da.
  3. Trade-off: Überschreiben des Intervalls oder UPSERT macht den Lauf wiederholbar. Anhängen erzeugt Duplikate und ist einfach, aber unsicher.
  4. Produktion: Ich lese nie now() oder die neuesten Daten, sondern das Data Interval. So gibt ein Backfill dasselbe wie der Originallauf.

1. Ein Backfill in 8 Schritten

  1. Zeitraum wählen: Man wählt Start und Ende. Beides sind Zeitpunkte, aus denen Airflow die Data Intervals ableitet.
  2. Backfill starten: In der UI über Trigger und Backfill. Auf der CLI mit airflow backfill create --dag-id ... --from-date ... --to-date ....
  3. DAG Runs: Der Befehl führt alle Instanzen des DAGs für alle Intervalle im Zeitraum neu aus. Jeder Run hat sein Data Interval.
  4. Reprocess: Die Option --reprocess-behavior steuert, was mit bereits gelaufenen Runs passiert. Die Doku zeigt failed als Beispiel.
  5. Limit: --max-active-runs begrenzt, wie viele Runs gleichzeitig laufen. So überlastet ein Backfill die Quelle nicht.
  6. Task liest: Der Task nutzt data_interval_start und data_interval_end aus dem Run. Er liest keine „neuesten“ Daten.
  7. Task schreibt: Er überschreibt sein Intervall oder macht einen UPSERT. Ein zweiter Lauf ändert dann nichts.
  8. Prüfen: Zeilen und Summen pro Intervall mit der Quelle vergleichen. Erst dann gilt der Backfill als fertig.

--run-backwards startet mit dem jüngsten Intervall. Das hilft, wenn neue Daten zuerst wichtig sind.

2. Aufbau

  1. Das Data Interval ist der Zeitraum der Daten eines Runs. Es hat einen Start und ein Ende.
  2. Die logical date ist beim geplanten Run der Anfang des Data Interval.
  3. Ein Run läuft meist nach dem Ende seines Intervalls, wenn die Daten da sind.
  4. Eine Task Instance bekommt das Intervall als Kontext und Template-Variable.
  5. Der Sink muss pro Intervall wiederholbar schreiben können, zum Beispiel in eine Partition.
  6. Die Quelle muss pro Intervall stabil lesbar sein. Sonst gibt der Backfill andere Zahlen.

3. Details

  1. Catchup: Mit catchup=True erstellt der Scheduler einen Run für jeden geplanten Zeitpunkt, der noch nicht gelaufen ist. Mit False nur den letzten. Der Standard scheduler.catchup_by_default ist False.
  2. Catchup-Beispiel: Ein @daily DAG mit start_date 2015-12-01 wird am 2016-01-02 aktiv. Mit catchup=False gibt es einen Run. Mit True gäbe es einen Run für jede Mitternacht seit dem Start.
  3. Data Interval: Es ist der Zeitraum der Daten, die ein Run verarbeiten soll. Bei geplanten Runs läuft der Run meist nach dem Ende des Intervalls. Bei manuellen Runs passt das Intervall nicht immer zum angegebenen Datum.
  4. Backfill: Er läuft einen DAG für eine vergangene Zeit. Man startet ihn in der UI oder mit airflow backfill create. Optionen sind unter anderem --reprocess-behavior, --max-active-runs und --run-backwards.
  5. Clear statt Backfill: Ein Task, der gelöscht (cleared) wird, bekommt einen neuen Versuch. Airflow erhöht try_number, setzt max_tries auf 0 und den Status auf None. Man kann Past, Future, Upstream und Downstream wählen.
  6. Idempotenz-Regel: Die Doku sagt, Tasks sollen bei jeder Wiederholung dasselbe Ergebnis geben. Man soll sie wie Transaktionen in einer Datenbank behandeln.
  7. INSERT vs UPSERT: Die Doku sagt, man soll bei einer Wiederholung kein reines INSERT nutzen, weil es Duplikate geben kann. Man ersetzt es durch ein UPSERT.
  8. Feste Partition lesen: Die Doku sagt, ein Task soll nie die neuesten verfügbaren Daten lesen. Man kann data_interval_start als Partition nutzen, auch beim Schreiben nach S3 oder HDFS.
  9. Keine aktuelle Zeit: datetime.now() soll man nie in einem Task für kritische Berechnungen nutzen. Bei einem Backfill wäre das Ergebnis falsch.
  10. Overwrite pro Partition: Man löscht das Intervall und schreibt es neu, in einer Transaktion. Das ist idempotent und bei grossen Mengen oft schneller als ein UPSERT.
  11. Retries brauchen Idempotenz: Airflow wiederholt fehlgeschlagene Tasks mit fester Zahl und Abstand. Ein Task, der nach dem Schreiben scheitert, läuft erneut und schreibt noch einmal.
  12. depends_on_past: Mit True läuft ein Task nur, wenn er im vorigen Run erfolgreich war. Das erzwingt eine Reihenfolge, bremst aber Backfills. Beim ersten Run läuft er trotzdem.
  13. Späte Daten: Ein Backfill ist das Werkzeug, um ein Intervall neu zu rechnen, wenn spät Daten kommen. Er funktioniert nur sicher mit idempotenten Tasks.

4. Fallen

  • „Mit catchup=False gibt es keinen Backfill.“ → Falsch. Man kann trotzdem jederzeit manuell einen Backfill starten.
  • „Ein Backfill läuft mit dem heutigen Datum.“ → Falsch. Jeder Run hat das Data Interval seines Zeitraums. Der Task muss damit rechnen.
  • „INSERT im Task ist bei Retries unproblematisch.“ → Falsch. Die Doku warnt vor Duplikaten. Man nutzt UPSERT oder überschreibt das Intervall.
  • „Ein Task liest am besten die neuesten Daten.“ → Falsch. Die Doku sagt nie. Man liest feste Partitionen des Intervalls.
  • „datetime.now() ist in Ordnung, wenn man es einmal braucht.“ → Falsch. Nicht für kritische Berechnungen. Ein Backfill liefe mit der falschen Zeit.
  • „Der tägliche Run mit logical date 2026-01-01 läuft am 1. Januar um Mitternacht.“ → Falsch. Er verarbeitet das Intervall ab dem 1. Januar. Er läuft meist erst nach dem Ende des Intervalls.

5. Selbsttest

Warum?

Warum müssen Tasks idempotent sein?

Retries, Backfills und manuelle Neustarts führen Tasks mehrfach aus. Ohne Idempotenz entstehen Duplikate oder falsche Summen.

Warum soll man nie die neuesten Daten lesen?

Ein Backfill würde die heutigen Daten für ein altes Intervall lesen. Das Ergebnis wäre falsch und nicht wiederholbar.

Warum ist datetime.now() in Tasks gefährlich?

Jede Wiederholung bekäme eine andere Zeit. Das Ergebnis hängt dann vom Moment des Laufs ab.

Wie innen?

Was passiert bei catchup=True?

Der Scheduler erstellt für jeden geplanten Zeitpunkt seit dem letzten Run einen DAG Run.

Was macht airflow backfill create?

Es führt den DAG für alle Intervalle zwischen Start und Ende neu aus. Mit Optionen wie --max-active-runs und --run-backwards.

Was passiert beim Löschen (Clear) eines Tasks?

Airflow erstellt einen neuen Versuch, erhöht try_number, setzt max_tries auf 0 und den Status auf None. Der Task läuft neu.

Wie hängen logical date und Data Interval zusammen?

Bei geplanten Runs ist die logical date der Anfang des Data Interval. Der Run läuft meist nach dem Ende.

Wie wird ein Intervall idempotent überschrieben?

Löschen und Einfügen für das Intervall in einer Transaktion. Oder ein UPSERT auf den Schlüssel.

Wie erkennt man im Beispiel unten die Duplikate?

Die append-Variante hat nach dem zweiten Lauf 4 Zeilen und Summe 60. Die anderen haben 2 Zeilen und 30.

Zahlen

Welchen Standard hat catchup_by_default?

False.

Wie viele Zeilen hat die append-Tabelle im Beispiel nach der Korrektur?

6 Zeilen mit Summe 179. Die anderen Varianten haben 2 Zeilen mit Summe 119.

Wie viele Runs erzeugt ein @daily DAG mit catchup=False beim ersten Aktivieren?

Einen Run für die letzte Mitternacht. Mit catchup=True gäbe es einen für jede Mitternacht seit start_date.

Vergleich

Append vs Overwrite vs UPSERT?

Append ist einfach, aber nicht wiederholbar. Overwrite ersetzt das Intervall. UPSERT ändert Zeilen nach Schlüssel. Die letzten beiden sind idempotent.

Backfill vs Clear?

Backfill erstellt Runs für einen Zeitraum, auch neue. Clear startet vorhandene Task Instances neu.

Catchup vs Backfill?

Catchup ist ein DAG-Setting, das beim Start fehlende Runs erstellt. Ein Backfill startet man gezielt für einen Zeitraum.

Produktion

Nach einem Backfill sind die Zahlen doppelt so hoch. Was ist passiert?

Die Tasks hängen an und sind nicht idempotent. Ich stelle auf Overwrite oder UPSERT um und bereinige die Duplikate.

Ein Backfill überlastet die Quell-Datenbank. Was tun?

--max-active-runs senken und einen Pool für die Quelle nutzen.

Ein Task gibt beim Backfill andere Zahlen als im Originallauf. Warum?

Er liest „neueste“ Daten oder nutzt now(). Ich lese feste Partitionen und nutze das Data Interval.

Szenario: Ein Fehler in der Quelle hat 3 Wochen falsche Daten erzeugt. Was tun Sie?

Ich korrigiere die Quelle und starte einen Backfill für die 3 Wochen mit begrenzten parallelen Runs. Die Tasks sind idempotent, darum ersetzt der Lauf die Daten.

Szenario: Ein Task schreibt und scheitert danach. Beim Retry gibt es Duplikate. Was ändern Sie?

Ich ersetze INSERT durch Overwrite des Intervalls in einer Transaktion oder UPSERT. Dann ist der zweite Versuch sicher.

Design

Wie plant man idempotente Tasks?

Gleiche Eingabe, gleiches Ergebnis. Feste Partitionen lesen, Intervall überschreiben, keine Zeit aus der Uhr.

Wie behandelt man Seiteneffekte wie E-Mails?

Ein Seiteneffekt ist nicht wiederholbar. Man trennt ihn in einen Task, der nur beim ersten Mal sendet, oder prüft vorher einen Marker.

Wann ist ein Overwrite besser als ein UPSERT?

Bei grossen Intervallen, wo man ohnehin alles neu schreibt. UPSERT ist besser, wenn nur wenige Zeilen ändern.

Szenario: Eine Quelle liefert Daten bis 3 Tage spät. Wie gestalten Sie den DAG?

Ich lasse den DAG täglich laufen und rechne die letzten 3 Tage jedes Mal neu, idempotent. So holt sich jeder Lauf die späten Daten.

Mehr

Gerüst

  • Warum? Vergangene Zeiträume neu rechnen und Fehler sicher wiederholen, ohne Duplikate.
  • Wie innen? Ein Run pro Data Interval, jeder Task liest und schreibt nur sein Intervall.
  • Zahlen Catchup-Standard False. Im Beispiel: append 4 Zeilen statt 2 nach dem zweiten Lauf.
  • Vergleich Append vs Overwrite vs UPSERT. Backfill vs Clear.
  • Produktion Doppelte Zahlen, falsche Daten durch now(), Quelle überlastet.
  • Design Feste Partitionen lesen, Intervall überschreiben, späte Daten über ein Fenster neu rechnen.

Beispiel: Append, Overwrite und UPSERT bei Wiederholung

def run_append(day):                 # A: einfach anhängen
    db.execute("insert into t_append select * from src where day=?", (day,))

def run_overwrite(day):              # B: Tag löschen und neu schreiben, eine Transaktion
    with db:
        db.execute("delete from t_overwrite where day=?", (day,))
        db.execute("insert into t_overwrite select * from src where day=?", (day,))

def run_merge(day):                  # C: UPSERT auf den Schlüssel id
    db.execute("insert into t_merge select * from src where day=? "
               "on conflict(id) do update set amount=excluded.amount", (day,))

# Retry: derselbe Tag läuft zweimal. Dann wird die Quelle korrigiert und der Tag neu geladen.
nach Lauf 1 {'t_append': (2, 30), 't_overwrite': (2, 30), 't_merge': (2, 30)}
nach Lauf 2 {'t_append': (4, 60), 't_overwrite': (2, 30), 't_merge': (2, 30)}
nach Korrektur {'t_append': (6, 179), 't_overwrite': (2, 119), 't_merge': (2, 119)}

Echte Ausgabe, Python 3.12.10 mit sqlite3 (Logik der drei Schreibmuster, kein Airflow). Angezeigt: Zeilen und Summe pro Tabelle.

  1. Beim ersten Lauf sind alle drei Tabellen gleich: 2 Zeilen, Summe 30.
  2. Beim zweiten Lauf desselben Tages hat nur die append-Tabelle Duplikate (4 Zeilen, Summe 60).
  3. Overwrite und UPSERT bleiben bei 2 Zeilen und Summe 30. Beide sind idempotent.
  4. Dann wird die Quelle korrigiert (id 1 von 10 auf 99) und der Tag neu geladen.
  5. Overwrite und UPSERT zeigen den korrigierten Wert (Summe 119). Die append-Tabelle hat 6 Zeilen und ein falsches Ergebnis.

Vergleich

  • Append: einfach, nicht wiederholbar, erzeugt Duplikate.
  • Overwrite des Intervalls: idempotent, gut für Partitionen, braucht atomares Löschen und Schreiben.
  • UPSERT (MERGE): idempotent auf Schlüsseln, gut bei wenigen Änderungen.
  • Backfill: neue Runs für einen Zeitraum, mit Limits.
  • Clear: vorhandene Task Instances neu starten.
  • Full Refresh: alles neu bauen. Sicher, aber teuer.

Produktion

  1. Doppelte Daten nach Retry oder Backfill: Task ist nicht idempotent. Lösung: Overwrite oder UPSERT, Duplikate bereinigen.
  2. Falsche Zahlen im Backfill: Task liest „neueste“ Daten. Lösung: feste Partition aus dem Data Interval.
  3. Quelle überlastet: Zu viele parallele Runs. Lösung: --max-active-runs und Pool.
  4. Backfill dauert ewig: depends_on_past zwingt zur Reihenfolge. Lösung: nur nutzen, wenn nötig.
  5. Teilweise geschriebene Daten: Task scheitert mitten im Schreiben. Lösung: Transaktion oder Staging und atomarer Austausch.
  6. Späte Daten fehlen: Intervall wurde nie neu gerechnet. Lösung: Fenster der letzten Tage neu laden.

Diagnose: Werkzeuge und Befehle

  • airflow backfill create --dag-id D --from-date A --to-date B --max-active-runs 3: Backfill starten.
  • UI, Grid-Ansicht: Runs pro Intervall, Status, Versuchszahl.
  • Task-Log: welches Data Interval wurde gelesen und wie viele Zeilen geschrieben?
  • Zeilen und Summen pro Intervall in Quelle und Ziel vergleichen.
  • Duplikate suchen: select key, count(*) ... group by key having count(*) > 1.

Senior-Punkte

  1. Idempotenz ist die Grundlage von Betrieb: Retries, Backfills und Neustarts brauchen sie.
  2. Das Data Interval ist die einzige Zeit, die ein Task nutzt.
  3. Overwrite pro Partition ist oft das einfachste idempotente Muster.
  4. Ein Backfill ist ein Betriebsfall: Limits, Pools und Prüfung der Zahlen gehören dazu.
  5. Seiteneffekte brauchen Marker, damit sie nicht doppelt passieren.
  6. Späte Daten: ein gleitendes Fenster neu rechnen ist stabiler als ein Einzel-Backfill.
