XCom und Sensors

Kern: XCom ist der Weg, kleine Werte zwischen Tasks zu schicken. Sie liegen standardmässig in der Metadaten-Datenbank. Ein Sensor ist ein Operator, der auf ein Ereignis wartet, und er tut das im Modus poke, reschedule oder deferrable.

Antwort-Muster

Frage: Wie geben Tasks Daten weiter, und was ist der Unterschied zwischen poke und reschedule?

  1. Mechanismus: Eine Task schreibt per xcom_push in die Metadaten-Datenbank, die nächste liest per xcom_pull.
  2. Zahl: Der Rückgabewert geht unter dem Key return_value in die DB. Der Sensor-Modus poke ist der Standard.
  3. Trade-off: poke hält einen Worker-Slot die ganze Zeit. reschedule gibt ihn zwischen den Prüfungen frei, kostet aber jeden Start neu.
  4. Produktion: Ich schicke nur kleine Werte per XCom, grosse Daten gehen in einen Speicher. Lange Waits laufen deferrable.

1. XCom und Sensor in 7 Schritten

  1. Task läuft: Eine Task gibt einen Wert zurück. Viele Operatoren pushen ihn automatisch, wenn do_xcom_push an ist. Das ist der Standard.
  2. Push: Der Standard-Backend BaseXCom schreibt den Wert in die Airflow-Datenbank. Der Key heisst return_value.
  3. Sensor startet: Im Modus poke belegt der Sensor einen Worker-Slot für die ganze Laufzeit.
  4. Poke: Der Sensor prüft die Bedingung. Ist sie falsch, schläft er poke_interval Sekunden und prüft wieder.
  5. Bedingung wahr: Der Sensor endet mit success. Läuft er in den timeout, schlägt er fehl, oder er wird mit soft_fail übersprungen.
  6. Pull: Die nächste Task holt den Wert mit xcom_pull oder über ihr Argument bei TaskFlow.
  7. Retry: Schlägt die erste Task fehl, werden ihre XComs bei jedem Retry gelöscht. So bleibt die Task idempotent.

2. Aufbau

  1. Ein XCom ist ein Eintrag mit Key, Wert und der Task, die ihn schrieb.
  2. Das XCom-Backend bestimmt, wo der Wert liegt. Standard ist die Metadaten-Datenbank.
  3. Ein Sensor ist ein Operator, der wiederholt prüft.
  4. Der Worker-Slot ist ein Platz auf einem Worker. Ein Sensor kann ihn belegen.
  5. Der Triggerer ist ein eigener Prozess für Deferrable Operatoren.
  6. Eine Trigger-Klasse wartet asynchron auf ein Ereignis.

3. Details

  1. Push und Pull: Tasks pushen und pullen XComs mit xcom_push und xcom_pull über die Task Instance. Mit TaskFlow geschieht das über Rückgabewerte und Argumente.
  2. return_value: Viele Operatoren pushen ihr Ergebnis unter dem Key return_value, wenn do_xcom_push True ist. Das ist der Standard. Der Key steht als Konstante XCOM_RETURN_KEY in BaseXCom.
  3. Nur kleine Werte: Der Standard-Backend speichert in der Airflow-Datenbank. Das passt für kleine Werte. Die Doku sagt, man soll keine grossen Werte wie DataFrames übergeben. Grosse Daten gehören in Speicher wie S3 oder eine Datenbank. Per XCom geht nur der Pfad.
  4. Eigener Backend: Man setzt xcom_backend in der Konfiguration. Die Klasse muss BaseXCom erweitern. So kann ein Backend grosse Werte in einen Objektspeicher legen.
  5. Neu in 3.4: Laut Release Notes 3.4.0 liegen neue XCom-Zeilen in einer eigenen Tabelle xcom_v2. Ein eigener Backend, der serialize_value überschreibt, muss auch store_value und load_value umsetzen.
  6. Serialisierung: Ein XCom kann jeden serialisierbaren Wert haben, auch Objekte mit @dataclass oder @attr.define.
  7. Templates: In Templates holt man Werte mit task_instance.xcom_pull(task_ids='foo', key='table_name').
  8. Retry löscht: Schlug die erste Task fehl, werden ihre XComs bei jedem Retry gelöscht. Das macht den Lauf idempotent.
  9. poke und reschedule: poke ist der Standard. Der Sensor belegt den Slot die ganze Zeit und schläft zwischen den Prüfungen. reschedule gibt den Slot nach jeder Prüfung frei. Der Sensor wird nach poke_interval neu angesetzt. Für häufige Prüfungen nimmt man poke, für seltene reschedule.
  10. timeout und soft_fail: poke_interval ist die Zeit zwischen zwei Prüfungen. timeout ist die längste Laufzeit und zählt ab dem ersten Versuch. Mit soft_fail=True wird der Sensor bei Timeout SKIPPED statt FAILED.
  11. exponential_backoff: Ist er an, wächst der Abstand zwischen den Prüfungen exponentiell. max_wait ist die obere Grenze in Sekunden.
  12. Deferrable: Ein Deferrable Operator gibt seinen Worker-Slot beim Warten frei. self.defer(trigger, method_name, kwargs, timeout) löst eine besondere Exception aus und übergibt an den Triggerer. Der lokale Zustand geht verloren. Nur method_name und kwargs bleiben.
  13. Triggerer: Triggers laufen als asynchroner Code in einem Prozess, mit async def run. Blockierender Code würde alle anderen anhalten. Feuert der Trigger, setzt der Scheduler die Task neu an, und Airflow ruft die Methode mit context und event auf.
  14. Triggerer-HA: Man kann mehrere Triggerer betreiben. Fällt einer aus, wartet Airflow etwa 2,1 mal triggerer.job_heartbeat_sec und plant die Triggers auf einem anderen Triggerer neu. Standardkapazität ist 1000 Triggers pro Triggerer.

4. Fallen

  • „XCom ist ein guter Weg, einen DataFrame weiterzugeben.“ → Falsch. Er ist für kleine Werte. Grosse Daten gehören in einen Speicher, per XCom geht nur der Pfad.
  • „Ein poke-Sensor kostet nichts, wenn er nur wartet.“ → Falsch. Er belegt die ganze Zeit einen Worker-Slot. Viele Sensoren können alle Slots füllen.
  • „timeout gilt pro Prüfung.“ → Falsch. Er gilt ab dem ersten Versuch für den ganzen Sensor.
  • „Mit soft_fail ist der Sensor bei Timeout grün.“ → Falsch. Er ist SKIPPED. Abhängige Tasks laufen dann normal nicht.
  • „Ein Deferrable Operator behält seine Variablen.“ → Falsch. Beim defer() geht der lokale Zustand verloren. Nur method_name und kwargs bleiben.
  • „In einem Trigger darf ich time.sleep nutzen.“ → Falsch. Er blockiert den ganzen Triggerer. Man nutzt asyncio.sleep.

5. Selbsttest

Warum?

Warum teilen Tasks standardmässig keine Daten?

Sie laufen oft auf verschiedenen Workern und Hosts. Darum gibt es XCom als kleinen, zentralen Kanal.

Warum gibt es den Modus reschedule?

Ein poke-Sensor belegt einen Slot. reschedule gibt ihn zwischen den Prüfungen frei.

Warum Deferrable Operatoren?

Sie warten im Triggerer mit wenig Ressourcen. Ein Worker-Slot wird nicht belegt.

Wie innen?

Wo liegt ein XCom?

Standardmässig in der Airflow-Metadaten-Datenbank. Ein eigener Backend kann anderswo speichern.

Wie kommt der Rückgabewert in ein XCom?

Mit do_xcom_push=True (Standard) pusht der Operator den Wert unter dem Key return_value.

Wie funktioniert poke?

Der Sensor hält den Slot, prüft, schläft poke_interval Sekunden und prüft wieder.

Wie funktioniert reschedule?

Nach jeder Prüfung gibt der Sensor den Slot frei und wird nach poke_interval neu angesetzt.

Wie arbeitet defer()?

Es löst eine Exception aus. Der Triggerer führt den Trigger aus. Beim Ereignis ruft Airflow next_method mit context und event auf.

Was passiert, wenn ein Triggerer ausfällt?

Airflow wartet etwa 2,1 mal triggerer.job_heartbeat_sec und plant die Triggers auf einem anderen Triggerer neu.

Zahlen

Was ist der Standard-Modus eines Sensors?

poke.

Wie viele Triggers hat ein Triggerer standardmässig?

Eine Kapazität von 1000.

Wie heisst der Standard-Key für Rückgabewerte?

return_value.

Vergleich

poke vs reschedule vs deferrable?

poke hält den Slot. reschedule gibt ihn frei, startet aber jedes Mal neu. deferrable wartet im Triggerer.

XCom vs externer Speicher?

XCom ist für kleine Werte in der DB. Ein Speicher wie S3 ist für grosse Daten, XCom trägt nur den Pfad.

BaseXCom vs eigener Backend?

BaseXCom speichert in der DB. Ein eigener Backend kann zum Beispiel einen Objektspeicher nutzen.

Sensor vs Operator?

Ein Sensor wartet auf ein Ereignis. Ein Operator führt eine Aktion aus.

Produktion

Was tun, wenn die Metadaten-DB durch XComs wächst?

Grosse Werte aus XCom entfernen und nur Pfade übergeben. Alte XComs aufräumen oder einen eigenen Backend nutzen.

Was tun bei vielen wartenden Sensoren?

Auf reschedule oder deferrable wechseln, damit sie keine Slots halten.

Szenario: Alle Worker-Slots sind voll und neue Tasks starten nicht. Warum?

Viele poke-Sensoren halten Slots. Ich stelle sie auf reschedule oder deferrable.

Szenario: Ein Deferrable-Sensor bleibt hängen, obwohl das Ereignis eintrat. Was prüfen Sie?

Ob der Triggerer läuft, und ob der Trigger blockierenden Code hat. Die Triggerer-Logs zeigen Warnungen.

Szenario: Eine Task liest ein XCom, aber der Wert fehlt nach einem Retry. Warum?

Bei jedem Retry der ersten Task werden ihre XComs gelöscht. Die Task muss den Wert neu schreiben.

Design

Wie übergibt man grosse Ergebnisse?

In einen Speicher schreiben und den Pfad per XCom übergeben.

Welchen Modus für einen Sensor, der alle 5 Stunden prüft?

reschedule oder deferrable. poke würde den Slot fünf Stunden halten.

Wie begrenzt man eine endlose Wartezeit?

Mit timeout. Mit soft_fail wird der Sensor bei Timeout übersprungen.

Wie schreibt man einen eigenen Trigger?

Asynchron mit async def run und asyncio.sleep. Nichts Blockierendes aufrufen.

Wann exponential_backoff?

Wenn eine frühe Prüfung wahrscheinlich ist und spätere seltener nötig sind. Mit max_wait als Grenze.

Mehr

Gerüst

  • Warum? Kleine Werte zwischen Tasks teilen und effizient auf Ereignisse warten.
  • Wie innen? XCom in der Metadaten-DB mit Key return_value. Sensor mit poke, reschedule oder defer an den Triggerer.
  • Zahlen Standard-Modus poke. Triggerer-Kapazität 1000. Heartbeat-Wartezeit etwa 2,1 mal job_heartbeat_sec.
  • Vergleich poke gegen reschedule gegen deferrable. XCom gegen Speicher.
  • Produktion Volle Slots durch Sensoren, grosse XComs, blockierende Triggers.
  • Design Kleine XComs, Pfade statt Daten, deferrable für lange Waits.

Beispiel: Sensor mit reschedule und ein XCom

from airflow.sdk import dag, task
from airflow.providers.standard.sensors.filesystem import FileSensor

@dag(schedule="@daily")
def lieferung():
    warte = FileSensor(
        task_id="warte_auf_datei",
        filepath="/daten/eingang/lieferung.csv",
        poke_interval=300,        # alle 5 Minuten prüfen
        timeout=6 * 3600,         # nach 6 Stunden aufgeben
        mode="reschedule",        # Slot zwischen den Prüfungen freigeben
        soft_fail=True,           # bei Timeout SKIPPED statt FAILED
    )

    @task
    def zaehle():
        return {"zeilen": 1200}   # Rückgabewert wird als XCom (return_value) gespeichert

    @task
    def melde(info: dict):        # xcom_pull passiert automatisch
        print(info["zeilen"])

    warte >> melde(zaehle())

lieferung()

Nicht ausgeführt. Airflow ist hier nicht installiert.

  1. FileSensor prüft alle 300 Sekunden, ob die Datei da ist.
  2. mode="reschedule" gibt den Slot zwischen den Prüfungen frei.
  3. timeout begrenzt die Wartezeit. soft_fail=True macht daraus SKIPPED statt FAILED.
  4. zaehle gibt ein dict zurück. Airflow speichert es als XCom unter return_value.
  5. melde(zaehle()) übergibt den Wert. Airflow macht das xcom_pull selbst.
  6. Die Importpfade stammen aus meinem Wissen und sind nicht gegen eine Installation geprüft.

Vergleich

  • poke: Standard, hält den Slot.
  • reschedule: gibt den Slot frei, neuer Start pro Prüfung.
  • deferrable: async im Triggerer, Slot frei.
  • XCom: klein, in der DB.
  • Eigener Backend: andere Ablage, Klasse von BaseXCom.
  • Asset-Trigger: wartet nicht, sondern startet bei Ereignis. Siehe die Seite zu Dags und Operatoren.
  • TaskFlow: XCom über Rückgabewerte und Argumente.
  • Templates: xcom_pull im Text.

Produktion

  1. Metadaten-DB wächst: Zu grosse XComs. Lösung: Pfade statt Daten, Backend wechseln, aufräumen.
  2. Slots voll: Viele poke-Sensoren. Lösung: reschedule oder deferrable.
  3. Sensor fällt nach langer Zeit durch: timeout zu klein. Lösung: Wert und soft_fail prüfen.
  4. Triggerer hängt: Blockierender Code im Trigger. Lösung: async umsetzen, Warnungen im Log lesen.
  5. XCom fehlt: Retry hat es gelöscht oder die Task schrieb nichts. Lösung: Wert erneut schreiben.
  6. Upgrade auf 3.4 bricht Backend: Eigener Backend ohne store_value und load_value. Lösung: beide umsetzen.

Diagnose: Werkzeuge und Befehle

  • Admin-UI: Task Instance, Reiter XCom zeigt Key und Wert.
  • Task-Log eines Sensors: zeigt jede Prüfung und die Wartezeit.
  • Triggerer-Log: zeigt Warnungen zu blockierendem Code.
  • PYTHONASYNCIODEBUG=1: aktiviert zusätzliche Prüfungen für asynchronen Code im Triggerer.
  • Pools und Slot-Belegung in der Admin-UI: zeigen, wer Slots hält.
  • Tabellengrösse der XComs in der Metadaten-DB: zeigt Wachstum.

Senior-Punkte

  1. XCom ist ein Kanal für Metadaten, nicht für Daten.
  2. Ein wartender Sensor ist teuer, wenn er einen Slot hält. Deferrable ist die ressourcenschonende Form.
  3. Timeouts gehören immer dazu. Ein Sensor ohne Grenze ist ein Leck.
  4. Triggers sind asynchroner Code. Ein blockierender Aufruf trifft alle.
  5. Idempotenz zuerst. Retries löschen XComs, also schreibt jede Task ihre Werte neu.
  6. Backend-Wechsel ist ein Upgrade-Thema. Release Notes lesen, besonders bei 3.4.
