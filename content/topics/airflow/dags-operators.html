DAGs, Operators, Tasks

Kern: Ein DAG ist ein Workflow aus Tasks mit Abhängigkeiten und ohne Kreise. Ein Operator ist die Vorlage für einen Task, und ein Task läuft als Task Instance in einem DAG Run. Airflow plant und startet die Tasks, es verarbeitet die Daten nicht selbst.

Antwort-Muster

Frage: Was ist der Unterschied zwischen DAG, Task und Operator?

  1. Mechanismus: Der DAG beschreibt Tasks und ihre Reihenfolge. Ein Operator ist die Vorlage, und ein Aufruf im DAG-File erzeugt einen Task.
  2. Zahl: Jeder Lauf eines Tasks in einem DAG Run ist eine Task Instance mit eigenem Status. Ein Task läuft standardmässig, wenn alle Vorgänger success sind (all_success).
  3. Trade-off: Operators sind einfach und wiederverwendbar. TaskFlow mit @task ist kürzer, aber ohne Template-Rendering in den Argumenten.
  4. Produktion: Ich halte den Top-Level-Code im DAG-File leer, denn Airflow führt ihn bei jedem Parsen aus. Schwere Arbeit gehört in die Tasks.

1. Von der DAG-Datei zur Task Instance in 8 Schritten

  1. DAG-Datei: Ein DAG ist Python-Code in einem DAG Bundle. Das Standard-Bundle ist ein lokaler Ordner.
  2. DAG-Processor: Er führt die Datei aus und liest die DAG-Objekte auf Top-Level. Er läuft immer als eigener Prozess.
  3. Metadaten-DB: Der DAG-Processor speichert das Ergebnis in der Datenbank. Der Scheduler liest von dort.
  4. DAG Run: Der Scheduler erstellt für jeden geplanten Zeitpunkt einen DAG Run mit einem Data Interval.
  5. Task Instance: Pro Task entsteht eine Task Instance. Sie geht von none zu scheduled, queued, running und success.
  6. Executor: Der Executor läuft im Scheduler-Prozess. Er schickt den Task an einen Worker.
  7. Task läuft: Airflow rendert die Templates kurz vor pre_execute. Dann läuft execute() in einem neuen Subprozess.
  8. Status: Der Task meldet sein Ergebnis über den API-Server. Der DAG Run ist success, wenn alle Leaf-Tasks success oder skipped sind.

Ein Task Instance bekommt von Airflow Metadaten wie das Data Interval. Daten gibt man nicht per Default weiter. Dafür gibt es XComs.

2. Aufbau

  1. Der DAG-Processor parst DAG-Dateien und braucht sie nur lesend.
  2. Die Metadaten-DB ist meist PostgreSQL oder MySQL. Sie hält den Zustand aller Tasks.
  3. Der Scheduler erzeugt DAG Runs und gibt bereite Tasks an den Executor.
  4. Der API-Server zeigt die UI. Tasks sprechen über ihn mit Airflow, ohne direkten DB-Zugriff.
  5. Der Worker führt den Task aus. Er läuft nie Task-Code im eigenen Prozess, sondern in einem Subprozess.
  6. Der Triggerer ist optional. Er führt deferred Tasks in einer asyncio-Schleife aus.

3. Details

  1. DAG deklarieren: Es gibt drei Wege. Der Context Manager with DAG(...), der Konstruktor DAG() mit dag= an jedem Operator oder der Decorator @dag.
  2. Task, Operator, Sensor: Operators und Sensors sind Vorlagen. Ein Aufruf im DAG-File macht einen Task. @task ist die TaskFlow-Variante. Ein Sensor wartet auf ein externes Ereignis.
  3. Abhängigkeiten: Man schreibt a >> b oder set_downstream. Die Doku empfiehlt >>. Standardmässig läuft ein Task, wenn alle Vorgänger erfolgreich sind.
  4. Trigger Rules: Es gibt 13. Dazu gehören all_success (Standard), all_failed, all_done, one_failed, one_success, none_failed, none_skipped und always. Sie steuern, wann ein Task trotz Fehlern oben läuft.
  5. Task-Status: none, scheduled, queued, running, success, failed, skipped, upstream_failed, up_for_retry, up_for_reschedule, deferred und removed. Der ideale Weg ist none, scheduled, queued, running, success.
  6. Retries und Timeout: Standardmässig wiederholt Airflow fehlgeschlagene Tasks mit fester Zahl und festem Abstand. execution_timeout begrenzt jede Ausführung. Danach gibt es AirflowTaskTimeout.
  7. Skip und Fail: AirflowSkipException setzt den Task auf skipped. AirflowFailException lässt ihn ohne weitere Retries scheitern.
  8. Templating: template_fields eines Operators werden mit Jinja ersetzt, zum Beispiel {{ ds }}. Das passiert kurz vor pre_execute. Mit literal() verhindert man das Ersetzen.
  9. TaskFlow: @task ist das Gegenstück zu PythonOperator. Die Doku nennt es ohne Template-Rendering in den Argumenten. Rückgabewerte gehen per XCom an den nächsten Task.
  10. XCom: Tasks teilen standardmässig keine Daten. XCom ist für kleine Nachrichten. Für grosse Daten schreibt man in S3 oder HDFS und gibt nur den Pfad weiter.
  11. Parsen: Airflow führt jede DAG-Datei aus. Standardmässig prüft es nur Dateien, in denen „airflow“ und „dag“ vorkommen. Der Import-Timeout dagbag_import_timeout ist 30 Sekunden.
  12. Top-Level-Code: Er läuft bei jedem Parsen. Datenbank-Zugriff, schwere Berechnungen und Netzwerk gehören nicht dorthin. Die Doku zeigt ein Beispiel mit etwa 1000 Sekunden Parse-Zeit.
  13. Zombie-Tasks: Ein Task, der running bleibt, obwohl sein Prozess weg ist, hiess früher Zombie-Task. Airflow findet ihn, markiert ihn als failed oder wiederholt ihn.
  14. depends_on_past: Mit True läuft ein Task nur, wenn seine Instanz im vorigen DAG Run erfolgreich war. Beim allerersten Lauf läuft er trotzdem.

4. Fallen

  • „Airflow verarbeitet die Daten.“ → Falsch. Es plant und startet Tasks. Die Arbeit machen Spark, SQL oder andere Systeme.
  • „Ein DAG darf Kreise haben.“ → Falsch. Nein. DAG heisst gerichtet und ohne Kreise.
  • „Ein Task läuft immer, wenn der Vorgänger fertig ist.“ → Falsch. Nur bei all_success. Bei failed oder skipped hängt es von der Trigger Rule ab.
  • „Daten gehen automatisch an den nächsten Task.“ → Falsch. Nein. Man nutzt XCom für kleine Werte oder externen Speicher.
  • „Top-Level-Code im DAG-File läuft nur einmal.“ → Falsch. Er läuft bei jedem Parsen, also oft.
  • „datetime.now() im Task ist in Ordnung.“ → Falsch. Die Doku sagt, man soll es nie für kritische Berechnungen nutzen. Besser ist das Data Interval.

5. Selbsttest

Warum?

Warum ist ein DAG gerichtet und ohne Kreise?

Der Scheduler braucht eine klare Reihenfolge. Ein Kreis würde nie enden.

Warum soll Top-Level-Code leicht sein?

Der DAG-Processor führt ihn bei jedem Parsen aus. Schwerer Code verlangsamt alle DAGs.

Warum nutzt man nicht datetime.now() in Tasks?

Eine Wiederholung gäbe ein anderes Ergebnis. Das Data Interval ist bei jeder Wiederholung gleich.

Wie innen?

Was macht der DAG-Processor?

Er führt DAG-Dateien aus, liest die DAG-Objekte und speichert sie in der Metadaten-DB. Er läuft immer als eigener Prozess.

Was ist eine Task Instance?

Ein Lauf eines Tasks in einem DAG Run. Sie hat einen eigenen Status und eine Versuchszahl.

Wann rendert Airflow Templates?

Kurz vor pre_execute, also direkt vor dem Lauf des Tasks.

Wie laufen Tasks auf dem Worker?

Jede Task Instance läuft in einem neuen Subprozess. Der Worker führt Task-Code nie im eigenen Prozess aus.

Wie kommen Task-Daten in die DB?

Über den API-Server und die Execution API. Der Task-Subprozess greift nicht direkt auf die Datenbank zu.

Wie wird der Status eines DAG Runs bestimmt?

Aus den Leaf-Tasks. success, wenn alle success oder skipped sind. failed, wenn einer failed oder upstream_failed ist.

Zahlen

Wie viele Trigger Rules gibt es und welche gilt standardmässig?

13. Standard ist all_success.

Wie lang ist der Import-Timeout einer DAG-Datei?

30 Sekunden (dagbag_import_timeout).

Wie oft wird eine DAG-Datei mindestens geparst?

min_file_process_interval im Bereich dag_processor ist 30 Sekunden.

Vergleich

Operator vs TaskFlow @task?

Operators sind fertige Vorlagen für externe Systeme. @task ist kurzer Python-Code und reicht Werte per XCom weiter.

Operator vs Sensor?

Ein Operator führt eine Aktion aus. Ein Sensor wartet auf ein Ereignis, zum Beispiel eine Datei.

Task vs Task Instance?

Der Task ist die Definition im DAG. Die Task Instance ist ein konkreter Lauf in einem DAG Run.

Produktion

Die UI wird langsam und neue DAGs erscheinen spät. Was prüfen Sie?

Die Parse-Zeit der DAG-Dateien. Schwerer Top-Level-Code oder viele Dateien bremsen den DAG-Processor.

Ein Task bleibt auf running, obwohl der Pod weg ist. Was ist das?

Ein Zombie-Task. Airflow findet ihn nach einer Weile und markiert ihn als failed oder wiederholt ihn.

Ein Task schlägt an einem Fehler ohne Sinn immer wieder fehl. Was tun?

AirflowFailException werfen, damit keine Retries mehr laufen. Dazu eine Meldung loggen.

Szenario: Ein DAG-File lädt beim Parsen Variablen aus der Datenbank. Was tun Sie?

Ich verschiebe den Zugriff in den Task oder nutze Jinja-Templates. Variablen im Top-Level-Code machen bei jedem Parsen eine Anfrage.

Szenario: Ein Report-Task soll auch laufen, wenn ein Vorgänger scheitert. Wie bauen Sie das?

Ich setze trigger_rule="all_done" auf dem Report-Task. Er läuft dann, sobald alle Vorgänger fertig sind, egal wie.

Design

Wie viele Tasks pro DAG sind sinnvoll?

So viele, dass jeder Task eine klare, wiederholbare Einheit ist. Zu feine Tasks belasten den Scheduler, zu grosse sind schwer neu zu starten.

Wann nutzt man einen Sensor, wann einen Trigger auf Asset?

Ein Sensor wartet auf ein Ereignis in einem festen Zeitplan. Ein Asset-Trigger startet den DAG, wenn die Daten da sind.

Wie gibt man grosse Daten zwischen Tasks weiter?

In externen Speicher schreiben, etwa S3, und nur den Pfad per XCom übergeben.

Szenario: Ein DAG mit 500 dynamisch erzeugten Tasks parst langsam. Was ändern Sie?

Ich erzeuge die Tasks aus einer statischen Config-Datei und halte die Parse-Zeit klein. Fremde Systeme frage ich nicht beim Parsen ab.

Mehr

Gerüst

  • Warum? Eine Pipeline als Graph mit klarer Reihenfolge, Wiederholung und Überwachung.
  • Wie innen? DAG-Processor parst, Scheduler erzeugt Runs, Executor gibt an Worker, Task läuft im Subprozess.
  • Zahlen 13 Trigger Rules, Standard all_success. Import-Timeout 30 s, Parse-Intervall 30 s.
  • Vergleich Operator vs @task, Operator vs Sensor, Task vs Task Instance.
  • Produktion Schwerer Top-Level-Code, Zombie-Tasks, Variablen beim Parsen.
  • Design Wiederholbare Tasks, kleine XComs, klare Task-Grösse.

Beispiel: DAG mit Operator, TaskFlow und Trigger Rule

from datetime import datetime
from airflow.sdk import dag, task
from airflow.providers.standard.operators.bash import BashOperator

@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False,
     default_args={"retries": 2})
def orders_daily():
    extract = BashOperator(
        task_id="extract",
        bash_command="python extract.py --day {{ ds }}",   # Jinja-Template
    )

    @task
    def transform(path: str) -> str:
        return path + ".clean"                              # kleine Daten per XCom

    @task(trigger_rule="all_done")
    def report():
        ...

    extract >> transform("/data/orders") >> report()

orders_daily()

Nicht ausgeführt.

  1. @dag macht aus der Funktion einen DAG. Man muss sie aufrufen, damit Airflow ihn lädt.
  2. catchup=False verhindert Läufe für alle vergangenen Zeitpunkte seit start_date.
  3. retries=2 kommt über default_args auf alle Tasks.
  4. {{ ds }} ist ein Template. Airflow ersetzt es kurz vor der Ausführung.
  5. extract >> transform(...) >> report() legt die Reihenfolge fest.
  6. trigger_rule="all_done" lässt den Report laufen, auch wenn ein Vorgänger scheitert.

Vergleich

  • Operator: fertige Vorlage, z. B. BashOperator oder Provider-Operators.
  • TaskFlow @task: Python-Funktion als Task, Werte per XCom.
  • Sensor: wartet auf ein Ereignis. Standard-Modus poke belegt einen Worker-Slot.
  • Deferrable Operator: wartet im Triggerer, ohne Worker-Slot.
  • DAG-Datei statisch: schnell zu parsen. Dynamisch: flexibel, aber Parse-Risiko.
  • Task Group vs eigener DAG: Task Group gliedert nur die Ansicht, ein eigener DAG hat eigene Runs.

Produktion

  1. Langsames Parsen: Schwerer Top-Level-Code. Lösung: Arbeit in Tasks, Imports in Funktionen.
  2. DAG erscheint nicht: Datei enthält weder „airflow“ noch „dag“ oder hat einen Import-Fehler. Lösung: Safe Mode prüfen und Fehler in der UI lesen.
  3. Zombie-Tasks: OOM, Probe-Fehler oder Pod-Wechsel. Lösung: Ressourcen prüfen, Retries setzen.
  4. Zu grosse XComs: XCom ist für kleine Nachrichten gedacht. Lösung: Pfad statt Daten übergeben.
  5. Duplikate bei Retry: Task nicht wiederholbar. Lösung: Task idempotent bauen.
  6. Sensoren blockieren Slots: Lösung: Modus reschedule oder deferrable Variante.

Diagnose: Werkzeuge und Befehle

  • Airflow UI, Grid und Graph: Status jeder Task Instance und Logs.
  • Import-Fehler in der Airflow UI prüfen.
  • python mein_dag.py: zeigt, wie viel Code beim Parsen läuft.
  • Log einer Task Instance: Versuchszahl, Exception, Dauer.
  • Scheduler- und DAG-Processor-Logs: Parse-Zeiten pro Datei.

Senior-Punkte

  1. Airflow ist ein Orchestrator, kein Prozessor. Schwere Arbeit läuft anderswo.
  2. Der DAG-File ist Konfiguration. Er soll schnell und ohne Nebenwirkungen parsen.
  3. Tasks müssen wiederholbar sein. Retries sind Normalfall.
  4. Trigger Rules sind Fehler-Design. Ich plane, was bei einem Ausfall passiert.
  5. XCom ist für Metadaten, nicht für Daten.
  6. Task-Grösse ist ein Entwurf. Zu fein belastet den Scheduler, zu grob verteuert den Neustart.
