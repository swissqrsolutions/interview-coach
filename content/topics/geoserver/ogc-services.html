GIS-Dienste: WMS, WFS, GeoServer

Kern: WMS liefert fertige Kartenbilder, WFS liefert die Features selbst als Daten. Beide sind offene Standards des OGC, und GeoServer ist ein Server, der sie aus Datenquellen wie PostGIS anbietet. Man ruft sie über HTTP mit Parametern wie request=GetMap auf.

Antwort-Muster

Frage: Was ist der Unterschied zwischen WMS und WFS?

  1. Mechanismus: WMS rendert aus den Daten ein Bild. WFS gibt die Features mit Attributen und Geometrie zurück.
  2. Zahl: GeoServer unterstützt WMS 1.1.1 und 1.3.0 und WFS 1.0.0, 1.1.0 und 2.0.0.
  3. Trade-off: Ein Bild ist leicht zu zeigen, aber nicht auswertbar. WFS-Daten sind voll nutzbar, aber gross und brauchen ein Limit.
  4. Produktion: Ich nutze WMS für Karten, WFS für Daten, und prüfe Achsenreihenfolge und count.

1. Eine GetMap-Anfrage in 7 Schritten

  1. Anfrage: Der Client sendet einen HTTP-GET mit service=WMS, request=GetMap und weiteren Parametern.
  2. Prüfen: GeoServer liest die Version (1.1.1 oder 1.3.0) und prüft die Pflichtparameter.
  3. Layer finden: layers=demo:ort nennt Workspace und Layer. Der Layer gehört zu einem Store, zum Beispiel einer PostGIS-Datenbank.
  4. Daten lesen: GeoServer liest die Features im Bereich bbox aus dem Store.
  5. Stil anwenden: Der Stil bestimmt Farben, Linien und Symbole. Ohne Angabe in styles gilt der Standard-Stil.
  6. Rendern: GeoServer zeichnet ein Bild mit width mal height Pixeln im gewünschten format.
  7. Antwort: Das Bild geht als HTTP-Antwort zurück. Es enthält keine Attribute mehr.

2. Aufbau

  1. Der OGC (Open Geospatial Consortium) legt die Schnittstellen fest.
  2. WMS (Web Map Service) liefert Karten als Bild.
  3. WFS (Web Feature Service) liefert Features und kann sie ändern.
  4. Ein Workspace gruppiert Daten. Ein Store verbindet eine Datenquelle. Ein Layer veröffentlicht Daten daraus.
  5. Ein Stil beschreibt, wie ein Layer aussieht.
  6. GeoWebCache speichert fertige Kacheln, die WMTS ausliefert.

3. Details

  1. WMS-Versionen: Der OGC-Standard WMS 1.3.0 ist das Dokument 06-042. Es gibt auch 1.1.1, 1.1 und 1.0. GeoServer unterstützt 1.1.1 und 1.3.0.
  2. WMS-Operationen: GetCapabilities beschreibt den Dienst. GetMap liefert das Bild. GetFeatureInfo gibt Infos zu einem Punkt. Dazu kommen DescribeLayer und GetLegendGraphic.
  3. GetMap-Parameter: Pflicht sind service, version, request, layers, styles, crs oder srs, bbox, width, height und format. styles darf leer sein. Dann gilt der Standard-Stil. crs ist der Name ab 1.3.0.
  4. bbox: Die Reihenfolge ist minx,miny,maxx,maxy in den Einheiten des Koordinatensystems. Ein falsches System oder eine falsche Reihenfolge zeigt ein leeres oder verschobenes Bild.
  5. GetFeatureInfo: Man braucht zusätzlich query_layers und die Pixelposition (x,y, ab 1.3.0 i,j). info_format ist standardmässig text/plain, und feature_count ist 1. Die Doku sagt, WFS GetFeature ist flexibler.
  6. WFS-Versionen: GeoServer unterstützt 2.0.0, 1.1.0 und 1.0.0. In allen gibt es GetCapabilities, DescribeFeatureType, GetFeature, LockFeature und Transaction. Nur in 2.0.0 gibt es zum Beispiel GetPropertyValue und Stored Queries.
  7. GetFeature-Parameter: typeNames wählt den Typ (bis 1.1.0 typeName). count begrenzt die Anzahl (bis 1.1.0 maxFeatures). sortBy, propertyName, bbox, featureID und srsName filtern, sortieren und wählen das Ausgabesystem.
  8. WFS Transaction: Sie kann Features einfügen, ändern und löschen (WFS-T). GeoServer behandelt jede Transaktion atomar. Schlägt ein Element fehl, bleiben die Daten unverändert.
  9. LockFeature: Es sperrt Features langfristig, damit Änderungen konsistent bleiben. Wenige Clients unterstützen es.
  10. Achsenreihenfolge: EPSG:4326 wird als lon/lat angenommen. Die Form urn:ogc:def:crs:EPSG::4326 bedeutet lat/lon. WFS 1.1.0 und 2.0.0 folgen der EPSG-Definition. Mit srsName=EPSG:4326 liefern sie x/y. WFS 1.0.0 darf man dabei nicht beim Wort nehmen.
  11. Datenmodell: Ein Workspace gruppiert, ein Store verbindet eine Quelle, ein Layer veröffentlicht, und eine Layer Group fasst Layer zusammen. Stile gibt es als SLD, CSS, YSLD und MBStyle.
  12. Kacheln: GeoServer hat WMTS und GeoWebCache. Der Cache speichert fertige Kacheln. Man kann sie vorab erzeugen (Seeding) und neu erzeugen. Das spart Rechenzeit gegenüber WMS pro Anfrage.
  13. Fehler: Fehlermeldungen kommen standardmässig als XML. JSON ist auch möglich. JSONP ist standardmässig aus.

4. Fallen

  • „WMS und WFS sind dasselbe, nur anderer Name.“ → Falsch. WMS liefert ein Bild. WFS liefert Features mit Attributen und Geometrie.
  • „EPSG:4326 heisst immer lat/lon.“ → Falsch. In der Kurzform nimmt GeoServer lon/lat an. Die URN-Form urn:ogc:def:crs:EPSG::4326 bedeutet lat/lon.
  • „Mit GetFeatureInfo lese ich bequem alle Daten.“ → Falsch. Es gibt Infos zu einer Stelle, standardmässig ein Feature. Für Daten nimmt man WFS GetFeature.
  • „maxFeatures gilt in WFS 2.0.0.“ → Falsch. In 2.0.0 heisst es count. maxFeatures gehört zu den älteren Versionen.
  • „Eine WFS-Transaction wendet bei einem Fehler die guten Teile an.“ → Falsch. GeoServer behandelt sie atomar. Bei einem Fehler bleibt alles unverändert.
  • „Ein GetMap ist immer billig.“ → Falsch. GeoServer rendert für jede Anfrage ein Bild. Ohne Kachel-Cache kostet das Rechenzeit.

5. Selbsttest

Warum?

Warum gibt es offene OGC-Standards?

Verschiedene Server und Clients sprechen so dieselbe Sprache. Man kann Software tauschen.

Warum nimmt man WMS statt WFS für eine Hintergrundkarte?

Das Bild ist klein, schnell und braucht keine Auswertung. WFS würde viele Daten übertragen.

Warum braucht WFS ein Limit?

Ohne count kann eine Anfrage sehr viele Features liefern. Das belastet Server und Client.

Wie innen?

Was passiert bei GetMap?

GeoServer prüft die Parameter, findet den Layer, liest Features im bbox, wendet den Stil an und rendert ein Bild.

Welche Teile hat das Datenmodell?

Workspace, Store, Layer und Layer Group. Dazu kommen Stile.

Was ist GeoWebCache?

Ein Cache für fertige Kacheln. WMTS liefert sie aus. Man kann sie vorab erzeugen.

Was macht eine WFS-Transaction?

Sie fügt Features ein, ändert oder löscht sie. In GeoServer ist sie atomar.

Was macht LockFeature?

Es sperrt Features langfristig für konsistente Änderungen. Wenige Clients nutzen es.

Was liefert GetCapabilities?

Eine Beschreibung des Dienstes mit Layern, Versionen und Formaten.

Zahlen

Welche WMS-Versionen unterstützt GeoServer?

1.1.1 und 1.3.0.

Welche WFS-Versionen unterstützt GeoServer?

2.0.0, 1.1.0 und 1.0.0.

Was ist der Standard von feature_count bei GetFeatureInfo?

1.

Vergleich

WMS vs WFS?

WMS liefert Bilder, WFS liefert Daten und kann sie ändern.

WMS vs WMTS?

WMS rendert jede Anfrage frei. WMTS liefert feste Kacheln, die man cachen kann.

GetFeatureInfo vs GetFeature?

GetFeatureInfo gibt Infos zu einer Pixelstelle. GetFeature gibt Features nach Filter, mit Sortierung und Attributwahl.

WFS 1.1.0 vs 2.0.0?

2.0.0 nutzt count und typeNames und hat zusätzlich Stored Queries und GetPropertyValue.

Produktion

Was tun bei langsamen Karten?

Kacheln mit GeoWebCache nutzen, den Index in der Datenbank prüfen und den Stil vereinfachen.

Was tun, wenn Punkte an der falschen Stelle erscheinen?

Achsenreihenfolge und Koordinatensystem prüfen. EPSG:4326 und die URN-Form unterscheiden sich.

Szenario: Eine Webkarte lädt bei jedem Zoomen sehr langsam. Was tun Sie?

Ich schalte auf Kacheln um (WMTS mit GeoWebCache) und erzeuge sie vorab. Danach prüfe ich Stil und Datenbank-Index.

Szenario: Ein Client lädt per WFS einen ganzen Datensatz und bricht ab. Was tun Sie?

Ich setze count und lade seitenweise, oder filtere mit bbox. Für Hintergründe nehme ich WMS.

Szenario: Ein WFS-T-Update ändert nichts, und es gibt eine Fehlermeldung. Was heisst das?

GeoServer behandelt die Transaktion atomar. Ein Element ist fehlgeschlagen, also ist nichts geändert. Ich prüfe die Meldung und das Element.

Design

Wann nimmt man WMS, wann WFS?

WMS für Darstellung, WFS für Daten, Auswertung und Änderung.

Wie strukturiert man Daten in GeoServer?

Workspaces pro Projekt oder Thema, ein Store pro Quelle, ein Layer pro veröffentlichter Tabelle.

Wie begrenzt man die Last?

Mit Kachel-Cache, count-Limits und Indizes in der Datenbank.

Wie wählt man die Version?

Neue Clients nehmen WFS 2.0.0. Bei alten Clients prüft man Parameter und Achsenreihenfolge.

Wann nimmt man sortBy bei GetFeature?

Wenn die Reihenfolge zählt, zum Beispiel beim seitenweisen Laden. Ohne Sortierung ist die Reihenfolge nicht festgelegt.

Mehr

Gerüst

  • Warum? Offene Standards, damit Karten und Geodaten über HTTP verfügbar sind.
  • Wie innen? GetMap rendert ein Bild aus Layer, Stil und bbox. GetFeature liest Features aus dem Store.
  • Zahlen WMS 1.1.1 und 1.3.0. WFS 1.0.0, 1.1.0, 2.0.0. feature_count Standard 1.
  • Vergleich WMS gegen WFS. WMS gegen WMTS. GetFeatureInfo gegen GetFeature.
  • Produktion Langsame Karten ohne Cache, WFS ohne Limit, falsche Achsenreihenfolge.
  • Design Kacheln für Karten, WFS mit count, Indizes in der Datenbank.

Beispiel: Vier typische Anfragen

# 1) WMS: ein Kartenbild
GET /geoserver/wms?service=WMS&version=1.1.1&request=GetMap
    &layers=demo:ort&styles=&srs=EPSG:4326
    &bbox=8.4,47.3,8.7,47.5&width=768&height=512&format=image/png

# 2) WMS: was liegt an einem Pixel?
GET /geoserver/wms?service=WMS&version=1.1.1&request=GetFeatureInfo
    &layers=demo:ort&query_layers=demo:ort&styles=&srs=EPSG:4326
    &bbox=8.4,47.3,8.7,47.5&width=768&height=512&x=380&y=250
    &info_format=application/json

# 3) WFS: Features als Daten, höchstens 10
GET /geoserver/wfs?service=WFS&version=2.0.0&request=GetFeature
    &typeNames=demo:ort&count=10&srsName=EPSG:4326
    &outputFormat=application/json

# 4) WFS-T: Transaction (Body, POST)
<wfs:Transaction service="WFS" version="2.0.0" ...>
  <wfs:Insert> ... </wfs:Insert>
  <wfs:Update typeName="demo:ort"> ... </wfs:Update>
</wfs:Transaction>

Nicht ausgeführt.

  1. Block 1: GetMap mit allen Pflichtparametern. styles= bleibt leer, es gilt der Standard-Stil.
  2. Block 2: GetFeatureInfo braucht zusätzlich query_layers und die Pixelposition. Hier x und y für Version 1.1.1.
  3. Block 3: GetFeature in WFS 2.0.0 mit typeNames und count. Mit srsName=EPSG:4326 kommen x/y-Koordinaten.
  4. Block 4: Eine Transaction wird per POST mit XML gesendet. GeoServer führt sie atomar aus.
  5. Die Antworten habe ich nicht gemessen. Es lief kein GeoServer.

Vergleich

  • WMS: Bild, Parameter in der URL, bbox und Pixelgrösse.
  • WFS: Features, Filter, Sortierung, Transaktionen.
  • WMTS: feste Kacheln, gut cachebar.
  • OGC API Features: neuerer Dienst, in GeoServer als eigener Dienst gelistet.
  • WCS: Raster-Daten (Coverages), in GeoServer als Dienst gelistet.
  • GetFeatureInfo: Info zu einer Stelle.
  • GetFeature: Daten nach Filter.
  • PostGIS-Store: GeoServer liest direkt aus der Datenbank, mit deren Indizes.

Produktion

  1. Langsame Karten: Jede Anfrage wird neu gerendert. Lösung: GeoWebCache, Seeding, Stil vereinfachen.
  2. WFS überlastet: Anfragen ohne Limit. Lösung: count, bbox und seitenweises Laden.
  3. Falsche Positionen: Achsenreihenfolge verwechselt. Lösung: srsName und CRS-Form prüfen.
  4. Leeres Bild: Falsches bbox oder falsches System. Lösung: Einheiten und Reihenfolge prüfen.
  5. Alte Kacheln: Daten änderten sich, der Cache nicht. Lösung: Kacheln neu erzeugen.
  6. Fehlschlag bei WFS-T: Ein Element ist ungültig, die ganze Transaktion bleibt ohne Wirkung. Lösung: Fehlermeldung lesen, Element korrigieren.

Diagnose: Werkzeuge und Befehle

  • request=GetCapabilities: zeigt Layer, Versionen, Formate und Systeme.
  • request=DescribeFeatureType: zeigt das Schema eines WFS-Typs.
  • Layer Preview in der GeoServer-Weboberfläche: schneller Test eines Layers.
  • GeoServer-Log: zeigt Fehler und Anfragen.
  • Browser-Netzwerk-Tab oder curl: zeigt die genaue URL, Status und Antwortzeit.
  • EXPLAIN in der Datenbank: zeigt, ob der räumliche Index genutzt wird.

Senior-Punkte

  1. Karten und Daten trennen. Bilder per WMS oder Kacheln, Daten per WFS.
  2. Der Cache ist die Leistung. Gerenderte Kacheln sind billiger als jede neue Anfrage.
  3. Limits sind Pflicht. Jede Datenanfrage braucht eine Grenze.
  4. Achsenreihenfolge ist ein Klassiker. Immer die exakte CRS-Form und die Version prüfen.
  5. Die Datenbank bleibt wichtig. Räumliche Indizes in PostGIS machen die Dienste schnell.
  6. Standards schützen vor Lock-in. Clients sind austauschbar, solange sie OGC sprechen.
