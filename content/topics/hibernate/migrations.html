Flyway und Liquibase

Hibernate · Tier 1 · Quellen: Flyway-Doku (Redgate: Migrations, Repeatable/Undo Migrations, Transaction Handling, Settings cleanDisabled, validateOnMigrate, outOfOrder), Flyway-Quellcode (flyway_schema_history, PostgreSQL Advisory Lock), Liquibase-Doku (Changeset), Spring Boot Reference (Database Initialization), Introduction to Hibernate 7 (Kap. 2.7), PostgreSQL 17 Doku (ALTER TABLE, CREATE INDEX)

Kern: Flyway und Liquibase sind Werkzeuge für Schema-Migrationen: versionierte Änderungsskripte, die jede Datenbank genau einmal und in fester Reihenfolge bekommt. Sie lösen das Problem, dass Code und Schema in allen Umgebungen gleich sein müssen. Hibernate erzeugt in Produktion kein Schema, es prüft es nur (ddl-auto=validate). Ohne Ausfall geht das nur mit Expand/Contract: Schema erst erweitern, Code umstellen, Altes später entfernen.

1. Wo sitzen die Migrationen?

  1. Migrations-Skripte: liegen im Repo neben dem Code, Default in Spring Boot: classpath:db/migration.
  2. Flyway migrate: liest die Skripte, vergleicht mit der History-Tabelle und führt nur neue aus. Auf PostgreSQL nimmt Flyway einen Advisory Lock. So migrieren zwei Pods nicht gleichzeitig.
  3. flyway_schema_history: eine Zeile pro Migration: Version, Beschreibung, Checksum, Erfolg.
  4. Spring Boot: Die EntityManagerFactory hängt von Flyway bzw. Liquibase ab. Darum ist das Schema fertig, bevor Hibernate startet.
  5. Hibernate validate: prüft Tabellen und Spalten gegen das Mapping. Bei Abweichung startet die App nicht.

2. Die Reise einer Spalten-Umbenennung ohne Ausfall (die Geschichte zum Merken)

  1. Expand: Migration V5 fügt email hinzu, nullable, ohne Default-Berechnung. Die alte App ignoriert die Spalte.
  2. App v2: schreibt in beide Spalten und liest noch die alte. Während des Rolling Updates laufen v1 und v2 parallel. Beide funktionieren.
  3. Backfill: Ein Job kopiert alte Werte in Blöcken (z. B. 10 000 Zeilen pro Transaktion). So gibt es keine riesige Transaktion und keine langen Sperren.
  4. App v3: liest und schreibt nur noch die neue Spalte.
  5. Contract: Erst ein späteres Release löscht die alte Spalte und setzt NOT NULL. Ein Rollback auf v3 bleibt möglich.

3. Beispiel: was Migrationen in PostgreSQL sperren

-- Spalte mit konstantem Default vs. volatile Default: wird die Tabelle neu geschrieben?
select relfilenode from pg_class where relname='book';
vorher: 17177
alter table book add column status text not null default 'NEW';
nach konstantem Default: 17177
alter table book add column token double precision not null default random();
nach volatile Default: 17223

Echte Ausgabe, PostgreSQL 17.12 (Ausgabe mit psql -At, Beschriftung im SELECT).

-- Index in einer Migration
begin;
create index concurrently book_title_idx on book(title);
ERROR:  CREATE INDEX CONCURRENTLY cannot run inside a transaction block

create index concurrently book_title_idx on book(title);   -- ohne Transaktion
CREATE INDEX

Echte Ausgabe, PostgreSQL 17.12.

-- Lock-Warteschlange: Sitzung 1 hat eine offene Lese-Transaktion auf book,
-- Sitzung 2 startet ALTER TABLE, Sitzung 3 will nur lesen
select pid, pg_blocking_pids(pid) as blockiert_von, wait_event_type as warten, query
from pg_stat_activity where datname='hib_demo' and pid<>pg_backend_pid();
 pid | blockiert_von | warten  |                 query
-----+---------------+---------+---------------------------------------
 456 | {}            | Timeout | select pg_sleep(6)
 463 | {456}         | Lock    | alter table book add column isbn text
 470 | {463}         | Lock    | select count(*) from book where id=1

-- dieselbe Migration mit lock_timeout
set lock_timeout='1s';
alter table book add column ean text;
ERROR:  canceling statement due to lock timeout
real    0m1.327s

-- Constraint ohne langen Scan unter starker Sperre
alter table book add constraint book_price_pos check (price > 0) not valid;
ALTER TABLE
alter table book validate constraint book_price_pos;
ALTER TABLE

Echte Ausgabe, PostgreSQL 17.12.

  1. Konstanter Default: relfilenode bleibt gleich. PostgreSQL speichert den Default nur in den Metadaten. Das geht in Millisekunden.
  2. Volatile Default (random(), clock_timestamp()): neue Datei, die ganze Tabelle wird unter ACCESS EXCLUSIVE Sperre neu geschrieben. Bei grossen Tabellen ein Ausfall.
  3. CONCURRENTLY baut den Index ohne Schreib-Sperre, darf aber nicht in einer Transaktion laufen. Flyway packt jede Migration in eine Transaktion. Darum: eigene Migration mit Script-Config executeInTransaction=false.
  4. Lock-Warteschlange: ALTER TABLE wartet auf die offene Transaktion. Alle neuen Leser warten hinter dem ALTER. Eine schnelle Migration legt so die ganze Tabelle lahm.
  5. lock_timeout in der Migration bricht nach 1 s ab, statt alle Leser zu blockieren. Danach erneut versuchen.
  6. NOT VALID + VALIDATE: Das Hinzufügen prüft alte Zeilen nicht. VALIDATE prüft danach mit einer schwächeren Sperre, bei der Schreiben weiter geht.

4. Details, die Interviewer fragen

  1. Versioned Migration (V2__add_email.sql): läuft genau einmal, in Versions-Reihenfolge. Nach dem Ausführen nie mehr ändern. Flyway prüft die Checksum (validateOnMigrate, Default true).
  2. Repeatable Migration (R__views.sql): keine Version, nur Checksum. Läuft erneut, sobald sich die Checksum ändert. Immer nach allen versionierten. Gut für Views, Funktionen, Grants.
  3. Undo Migration (U2__add_email.sql): nur in Flyway Teams. In der Praxis rollt man meist vorwärts mit einer neuen Version zurück.
  4. outOfOrder (Default false): Eine V3, die nach V4 gemergt wurde, läuft dann nicht. Mit true läuft sie trotzdem.
  5. cleanDisabled (Default true): flyway clean löscht alle Objekte im Schema. In Produktion muss es aus bleiben.
  6. Transaktionen: Flyway führt jede Migration in einer eigenen Transaktion aus. PostgreSQL kann DDL transaktional zurückrollen. Ein Fehler hinterlässt also kein halbes Schema.
  7. Baseline: Für eine bestehende Datenbank ohne History: baseline markiert den Ist-Stand als Version X.
  8. Spring Boot: Für PostgreSQL braucht Flyway zusätzlich das Modul org.flywaydb:flyway-database-postgresql.
  9. Liquibase: Ein Changelog (SQL, XML, YAML oder JSON) enthält Changesets. Ein Changeset ist eindeutig über author:id plus Dateipfad. Liquibase führt es einmal aus, ausser mit runOnChange oder runAlways. Tracking-Tabellen: DATABASECHANGELOG und DATABASECHANGELOGLOCK. Spring-Boot-Default: db/changelog/db.changelog-master.yaml.
  10. ddl-auto in Spring Boot: Werte none, validate, update, create, create-drop. Default: create-drop nur bei Embedded-DB ohne Flyway/Liquibase, sonst none.

5. Vergleich

  • Flyway: SQL-first, einfache Namenskonvention, wenig Konzepte. Gut, wenn das Team SQL schreibt und eine Datenbank-Marke nutzt.
  • Liquibase: Changesets in XML/YAML/JSON oder SQL, datenbank-neutral formulierbar. Eingebaute Rollback-Definitionen, Contexts und Labels (z. B. nur in Test), Preconditions. Mehr Konzepte, mehr Flexibilität.
  • Hibernate ddl-auto=update: kein Migrations-Werkzeug. Es löscht nie, benennt nicht um, kennt keine Reihenfolge und keine Daten-Migration. Nur für lokale Experimente.
  • ddl-auto=validate: ändert nichts, prüft nur. Richtig für Produktion zusammen mit Flyway oder Liquibase.
  • Migration beim App-Start vs eigener Job: Start ist einfach. Ein Job (Kubernetes Job, Helm Hook, Init-Container) trennt Rechte und Zeitpunkt und blockiert keine Readiness Probes.

6. In der Produktion

  1. Checksum-Fehler beim Start: Jemand hat eine schon ausgeführte V-Migration geändert. Fix: Änderung zurücknehmen und als neue Version schreiben. flyway repair nur, wenn die Änderung bewusst und harmlos war (z. B. Kommentar).
  2. App blockiert nach Deployment: Ein ALTER TABLE wartet auf eine lange Transaktion, alle Queries stauen sich dahinter. Fix: SET lock_timeout am Anfang der Migration, Retry, lange Transaktionen vorher prüfen.
  3. Tabelle wird neu geschrieben: Typänderung (ALTER COLUMN TYPE) oder volatile Default auf grosser Tabelle. Fix: Expand/Contract mit neuer Spalte und Backfill in Blöcken.
  4. Rolling Update bricht alte Pods: Migration löscht oder benennt eine Spalte um, alte Pods nutzen sie noch. Fix: Expand/Contract über mehrere Releases.
  5. Fehlgeschlagene Migration auf einer Datenbank ohne transaktionales DDL: halbes Schema. Auf PostgreSQL meist kein Problem, ausser bei nicht-transaktionalen Statements wie CONCURRENTLY. Fix: solche Statements allein in eine Migration.
  6. Multi-Tenant: ein Tenant bleibt zurück. Bei einer Datenbank pro Tenant scheitert die Migration nur für einen Tenant. Fix: pro Tenant migrieren, Ergebnis pro Tenant loggen und überwachen, fehlgeschlagene Tenants gezielt wiederholen.

Per-Tenant-Migrationen (eine Datenbank oder ein Schema pro Tenant):

// beim Anlegen eines Tenants und beim Start für alle Tenants
Flyway.configure()
      .dataSource(tenantDataSource)          // eigene DB pro Tenant
      .locations("classpath:db/migration")
      .load()
      .migrate();

Code-Skizze, nicht ausgeführt. Bei Schema-pro-Tenant stattdessen das Schema des Tenants konfigurieren.

  1. Spring Boot migriert nur die Haupt-DataSource automatisch. Tenants braucht eigenen Code.
  2. Neue Tenants: Datenbank anlegen, dann sofort migrieren, dann erst freigeben.
  3. Bestehende Tenants: beim Deployment nacheinander oder begrenzt parallel migrieren. Viele Tenants machen das zu einer langen Operation.
  4. Alle Tenants müssen dieselbe Version erreichen. Die App muss während des Rollouts mit alter und neuer Version umgehen können (Expand/Contract).

7. Diagnose: Werkzeuge und Befehle

  • flyway info: welche Migrationen ausgeführt, offen oder fehlgeschlagen sind. flyway validate: Checksums prüfen.
  • select version, description, checksum, success from flyway_schema_history order by installed_rank;
  • Liquibase: liquibase status und liquibase history. Hängender Lock: Zeile in DATABASECHANGELOGLOCK prüfen.
  • Während der Migration: pg_stat_activity mit pg_blocking_pids(pid) zeigt die Lock-Warteschlange.
  • Vorher testen: Migration gegen eine Kopie mit Produktions-Datenmenge (Testcontainers oder Staging). Laufzeit und Sperren messen.
  • spring.jpa.hibernate.ddl-auto=validate: Abweichung zwischen Mapping und Schema fällt beim Start auf, nicht erst beim ersten Request.

8. Senior-Punkte

  1. Schema ist Code. Migrationen im Review, im CI gegen eine echte PostgreSQL getestet, nie von Hand in Produktion.
  2. Vorwärts statt zurück. Undo-Skripte für Daten sind selten korrekt. Besser: kleine Schritte, Backup, Fix als neue Version.
  3. Jede Migration muss mit zwei App-Versionen funktionieren. Das ist die Grundlage für Rolling Updates und Rollbacks.
  4. Sperren mitdenken: lock_timeout setzen, Indizes CONCURRENTLY, Constraints NOT VALID, Backfills in Blöcken.
  5. Wo läuft die Migration? Beim Start ist einfach, aber jeder Pod braucht DDL-Rechte. Ein eigener Job trennt Rechte und Verantwortung.
  6. Multi-Tenant skaliert schlecht ohne Automatik: Migration pro Tenant, Status pro Tenant, Alarm bei Abweichung.

10. Fallen

  • „ddl-auto=update reicht für Produktion.“ → Falsch. Es löscht und benennt nichts um, kennt keine Daten-Migration und keine Reihenfolge. In Produktion validate plus Flyway/Liquibase.
  • „Eine ausgeführte Migration kann ich noch korrigieren.“ → Nein. Die Checksum bricht. Korrekturen sind eine neue Version.
  • „Eine Spalte hinzufügen ist immer harmlos.“ → Nur mit konstantem Default. Ein volatile Default schreibt die Tabelle neu. Und jedes ALTER braucht eine kurze, aber starke Sperre.
  • „Umbenennen ist eine Migration.“ → Bei Rolling Updates sind es mehrere Releases (Expand/Contract).
  • „Spring Boot migriert alle Tenant-Datenbanken.“ → Nur die konfigurierte DataSource. Tenants brauchen eigenen Code.

11. Fragen

Warum braucht man ein Migrations-Werkzeug?

Damit jede Umgebung dieselben Schema-Änderungen genau einmal und in fester Reihenfolge bekommt. Das Schema ist dann versioniert wie Code.

Wie merkt sich Flyway, was schon gelaufen ist?

In der Tabelle flyway_schema_history: Version, Beschreibung, Checksum und Erfolg pro Migration.

Was ist der Unterschied zwischen versioned und repeatable Migrations?

Versioned (V) laufen genau einmal in Versions-Reihenfolge. Repeatable (R) laufen erneut, wenn sich ihre Checksum ändert, immer nach den versionierten.

Was passiert, wenn man eine ausgeführte Migration ändert?

Die Checksum passt nicht mehr, und validate beim migrate bricht ab. Korrektur gehört in eine neue Version.

Wann nutzen Sie flyway repair?

Um fehlgeschlagene Einträge zu entfernen oder Checksums nach einer bewussten, harmlosen Änderung neu zu setzen. Nicht als Routine.

Was ist der Unterschied zwischen Flyway und Liquibase?

Flyway ist SQL-first und einfach. Liquibase hat Changesets in mehreren Formaten, Rollback-Definitionen, Contexts und Preconditions.

Wie identifiziert Liquibase einen Changeset?

Über author:id plus Dateipfad. Ausgeführte Changesets stehen in DATABASECHANGELOG.

Welchen ddl-auto-Wert nutzen Sie in Produktion und warum?

validate. Hibernate prüft das Schema, ändert aber nichts. Änderungen kommen nur über Flyway oder Liquibase.

Warum ist ddl-auto=update gefährlich?

Es ist nicht versioniert, löscht nichts, kann nicht umbenennen und keine Daten migrieren. Ergebnisse hängen vom Zustand jeder Datenbank ab.

In welcher Reihenfolge starten Flyway und Hibernate in Spring Boot?

Flyway oder Liquibase zuerst. Die EntityManagerFactory hängt davon ab und startet danach.

Was ist Expand/Contract?

Erst das Schema erweitern, dann den Code umstellen, Altes erst in einem späteren Release entfernen. So passt jede Schema-Version zu alter und neuer App.

Wie benennen Sie eine Spalte ohne Ausfall um?

Neue Spalte anlegen, App schreibt beide, Backfill in Blöcken, App liest neu, später alte Spalte löschen.

Warum blockiert ein schnelles ALTER TABLE manchmal alles?

Es wartet auf eine starke Sperre hinter einer offenen Transaktion. Alle neuen Queries warten hinter dem ALTER. lock_timeout verhindert den Stau.

Wie legen Sie einen Index auf eine grosse Tabelle an?

Mit CREATE INDEX CONCURRENTLY in einer eigenen Migration ohne Transaktion, in Flyway per executeInTransaction=false.

Wann schreibt PostgreSQL bei ADD COLUMN die Tabelle neu?

Bei einem volatile Default wie random(). Ein konstanter Default steht nur in den Metadaten und ist sofort fertig.

Was bringt NOT VALID bei Constraints?

Der Constraint gilt sofort für neue Zeilen, alte werden nicht geprüft. VALIDATE prüft sie danach mit schwächerer Sperre.

Was passiert, wenn zwei Pods gleichzeitig migrieren wollen?

Flyway nimmt auf PostgreSQL einen Advisory Lock. Der zweite wartet und findet danach nichts mehr zu tun.

Migration beim App-Start oder als eigener Job?

Start ist einfach. Ein Job trennt DDL-Rechte und Zeitpunkt und hält lange Migrationen aus den Readiness Probes heraus.

Wie migrieren Sie eine Datenbank pro Tenant?

Programmatisch Flyway pro Tenant-DataSource: beim Anlegen des Tenants und beim Deployment für alle. Status pro Tenant loggen und überwachen.

Szenario: Nach einem Deployment hängen alle Requests, im pg_stat_activity wartet ein ALTER TABLE. Was tun Sie?

Den Blockierer mit pg_blocking_pids finden, oft eine lange Transaktion, und beenden. Künftig lock_timeout in Migrationen und Retry.

Szenario: Die App startet nicht mehr: „Validate failed: Migration checksum mismatch“. Was ist passiert?

Eine schon ausgeführte Migration wurde geändert. Änderung zurücknehmen und als neue Version liefern. repair nur bei bewusster, harmloser Änderung.

Szenario: Bei 200 Tenant-Datenbanken schlägt die Migration für 3 fehl. Wie gehen Sie vor?

Fehler pro Tenant loggen, die 3 gezielt analysieren und neu migrieren. Die App muss alte und neue Schema-Version bis dahin unterstützen (Expand/Contract).
