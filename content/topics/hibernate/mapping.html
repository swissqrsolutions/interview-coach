Beziehungen, Cascade, Inheritance Mapping

Kern: Mapping ist die Übersetzung zwischen Java-Objekten und Tabellen. Beziehungen (@ManyToOne, @OneToMany, @ManyToMany, @OneToOne) werden zu Foreign Keys oder Join-Tabellen. Vererbung wird zu einer, mehreren oder verbundenen Tabellen. Die wichtigste Regel: Nur die Owning Side einer Beziehung bestimmt, was in der Datenbank steht.

1. Wo sitzen Beziehungen in der Datenbank?

  1. @ManyToOne: Viele Bestellungen gehören zu einem Kunden. Die Spalte customer_id in orders ist der Foreign Key. Diese Seite ist die Owning Side.
  2. @OneToMany(mappedBy = "customer"): Die Gegenseite im Kunden. Sie ist die Inverse Side und hat keine eigene Spalte.
  3. @ManyToMany: Bücher und Autoren. Die Verbindung liegt in einer Join-Tabelle book_author.
  4. @OneToOne mit @MapsId: Das Profil nutzt die ID des Benutzers als eigenen Primärschlüssel. Keine extra Spalte, gut ladbar.
  5. Vererbung: Eine Java-Hierarchie (Payment → CardPayment, BankTransfer) wird nach einer von drei Strategien abgebildet. Siehe Beispiel.

2. Die Reise einer neuen Bestellposition

  1. Helper-Methode: Der Code ruft order.addLine(line), nicht direkt die Liste.
  2. Beide Seiten setzen: Die Methode macht lines.add(line) und line.setOrder(this). Nur so sind Java-Objekte und Datenbank gleich.
  3. Flush und Cascade: cascade = PERSIST an lines sorgt dafür, dass die neue Position mitgespeichert wird.
  4. Owner entscheidet: Hibernate liest den Foreign Key nur aus line.order, der Owning Side. Die Liste order.lines wird für die Spalte ignoriert.
  5. INSERT: Ein einziges INSERT mit order_id. Kein zweites UPDATE.
  6. Entfernen: removeLine nimmt die Position aus der Liste und setzt line.setOrder(null). Mit orphanRemoval = true löscht Hibernate die Zeile.

3. Beispiel: Beziehungen und drei Vererbungs-Strategien

@Entity class PurchaseOrder {
  @Id @GeneratedValue Long id;
  @ManyToOne(fetch = LAZY, optional = false) Customer customer;
  @OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true)
  List<OrderLine> lines = new ArrayList<>();
  void addLine(OrderLine l)    { lines.add(l); l.setOrder(this); }
  void removeLine(OrderLine l) { lines.remove(l); l.setOrder(null); }
}
@Entity class UserProfile { @Id Long id; @OneToOne(fetch = LAZY) @MapsId User user; }

@Entity @Inheritance(strategy = SINGLE_TABLE)            // oder JOINED, TABLE_PER_CLASS
abstract class Payment { @Id Long id; BigDecimal amount; }
@Entity class CardPayment  extends Payment { String cardNumber; }
@Entity class BankTransfer extends Payment { String iban; }

em.createQuery("from Payment", Payment.class).getResultList();   // polymorphe Query

Die Tabellen und das SQL, das Hibernate nach diesem Muster für from Payment erzeugt, direkt in PostgreSQL ausgeführt:

--- SINGLE_TABLE: eine Tabelle, Spalte dtype
 id |    dtype     | amount | card_number |            iban
----+--------------+--------+-------------+----------------------------
  1 | CardPayment  |     50 | 4111-xxxx   |
  2 | BankTransfer |    900 |             | CH93 0076 2011 6238 5295 7

--- JOINED: Basistabelle + eine Tabelle pro Unterklasse, LEFT JOINs
 id | amount | card_number |            iban            | clazz_
----+--------+-------------+----------------------------+--------
  1 |     50 | 4111-xxxx   |                            |      1
  2 |    900 |             | CH93 0076 2011 6238 5295 7 |      2

--- TABLE_PER_CLASS: eine volle Tabelle pro Klasse, UNION ALL
 Append
   ->  Seq Scan on card_payment_t
   ->  Seq Scan on bank_transfer_t

--- SINGLE_TABLE: Pflichtfeld einer Unterklasse nur per CHECK möglich
alter table payment_st add constraint card_needs_number
  check (dtype <> 'CardPayment' or card_number is not null);
insert into payment_st values (3,'CardPayment',10,null,null);
ERROR:  new row for relation "payment_st" violates check constraint "card_needs_number"

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_mapping, danach gelöscht). Das SQL ist von Hand nach dem Muster der Hibernate-Abfragen geschrieben; Hibernate selbst ist hier nicht installiert.

  1. SINGLE_TABLE braucht keinen Join und ist am schnellsten. Preis: viele NULL-Spalten. NOT NULL für card_number geht nicht direkt, nur per CHECK mit dtype.
  2. JOINED ist normalisiert, mit echten NOT NULL-Spalten pro Unterklasse. Jede polymorphe Query braucht einen Join pro Unterklasse.
  3. TABLE_PER_CLASS hat keine gemeinsame Tabelle. Polymorphe Queries werden UNION ALL über alle Tabellen. Ein Foreign Key auf „irgendein Payment“ ist unmöglich.
  4. clazz_ ist die Spalte, mit der Hibernate bei JOINED die Klasse jeder Zeile erkennt. Eine Discriminator-Spalte braucht JOINED nicht.
  5. @MapsId spart beim Profil eine eigene ID-Spalte. Das Profil lässt sich mit der User-ID direkt laden.

4. Details, die Interviewer fragen

  1. Owning Side: Die Seite mit dem Foreign Key oder der @JoinTable. Nur sie wird geschrieben. Die Seite mit mappedBy ist die Inverse Side; Änderungen nur dort speichert Hibernate nicht.
  2. Bidirektional synchron halten: Hibernate setzt die andere Seite nicht automatisch. Darum Helper-Methoden wie addLine. Sonst ist der Persistence Context bis zum nächsten Laden falsch.
  3. Unidirektionales @OneToMany: Ohne mappedBy und ohne @JoinColumn legt Hibernate eine Join-Tabelle an. Mit @JoinColumn gibt es oft INSERT plus extra UPDATE. Besser: @ManyToOne auf der Kind-Seite, optional mit mappedBy-Liste.
  4. @ManyToMany mit List: Eine List ohne Reihenfolge ist ein Bag. Beim Entfernen eines Elements löscht Hibernate oft alle Zeilen der Join-Tabelle und fügt den Rest neu ein. Mit Set gibt es ein einzelnes DELETE.
  5. @ManyToMany mit Extra-Spalten: Braucht die Verbindung eigene Daten (z. B. Rolle seit Datum), wird sie eine eigene Entity mit zwei @ManyToOne.
  6. @OneToOne: Auf der Inverse Side kann Hibernate meist nicht lazy laden, weil es nicht weiss, ob es einen Partner gibt. @MapsId auf der Owning Side ist die beste Form.
  7. Fetch-Standards: @ManyToOne und @OneToOne sind EAGER, Collections LAZY. Fast immer setzt man alles auf LAZY.
  8. Cascade: Gibt Operationen wie persist oder remove an verbundene Entities weiter. Sinnvoll von Eltern zu Kindern in einem Aggregat, gefährlich auf @ManyToOne und @ManyToMany.
  9. orphanRemoval vs CascadeType.REMOVE: REMOVE löscht Kinder, wenn der Elternteil gelöscht wird. orphanRemoval löscht ein Kind auch, wenn es nur aus der Collection entfernt wird.
  10. Vererbungs-Standard: Ohne @Inheritance nutzt JPA SINGLE_TABLE. Die Discriminator-Spalte heisst standardmässig DTYPE und enthält den Entity-Namen.
  11. @MappedSuperclass: Eine Basisklasse, die nur Felder vererbt (z. B. id, createdAt). Sie ist keine Entity; Queries auf sie und Beziehungen zu ihr gehen nicht.
  12. TABLE_PER_CLASS und IDs: IDs müssen über alle Tabellen eindeutig sein. IDENTITY funktioniert dafür nicht, man nimmt eine Sequenz.
  13. @Embeddable: Ein Wertobjekt ohne eigene ID, z. B. Address. Seine Felder landen als Spalten in der Tabelle der Entity.
  14. @ElementCollection: Eine Liste von Werten (z. B. Set<String> tags) in einer eigenen Tabelle. Ohne eigene ID; Änderungen schreiben oft die ganze Sammlung neu.
  15. equals und hashCode: In Sets braucht eine Entity stabile Werte. Die generierte ID fehlt vor dem Persist. Üblich: natürlicher Schlüssel oder ID-basiert mit festem hashCode pro Klasse.

5. Vergleich

  • SINGLE_TABLE: schnell, einfache Queries, polymorph ohne Join. Viele NULL-Spalten, keine echten NOT-NULL-Constraints pro Unterklasse.
  • JOINED: sauber normalisiert, echte Constraints. Joins bei jeder Abfrage, Inserts in mehrere Tabellen.
  • TABLE_PER_CLASS: jede Tabelle für sich vollständig. Polymorphe Queries als UNION, keine gemeinsamen Foreign Keys. Selten die richtige Wahl.
  • @MappedSuperclass: nur Code-Wiederverwendung, keine Polymorphie in der DB.
  • Unidirektional vs bidirektional: Unidirektional @ManyToOne ist am einfachsten. Bidirektional nur, wenn man die Collection wirklich navigiert.
  • Komposition statt Vererbung: Oft ist ein @Embeddable oder eine @ManyToOne zu einem Typ-Objekt klarer als eine Hierarchie.

6. In der Produktion

  1. Foreign Key bleibt leer: Nur order.getLines().add(line), ohne line.setOrder(order). Ergebnis: order_id NULL oder Constraint-Fehler. Lösung: Helper-Methoden, Owning Side setzen.
  2. Hunderte DELETE und INSERT: @ManyToMany mit List. Ein Element entfernen schreibt die Join-Tabelle neu. Lösung: Set oder eigene Join-Entity.
  3. Daten gelöscht: CascadeType.REMOVE oder ALL auf @ManyToMany zu geteilten Daten. Ein Buch löschen löscht seine Autoren. Lösung: Cascade nur im Aggregat.
  4. Langsame polymorphe Queries: JOINED mit 10 Unterklassen erzeugt 10 Joins. Lösung: SINGLE_TABLE, oder gezielt die Unterklasse abfragen.
  5. Riesige Single Table: 80 Spalten, die meisten NULL. Lösung: Hierarchie überdenken, Teile als JOINED oder eigene Tabellen.
  6. Schema und Mapping driften auseinander: ddl-auto=update in Produktion. Lösung: Flyway/Liquibase und ddl-auto=validate.

7. Diagnose

  • org.hibernate.SQL=DEBUG und org.hibernate.orm.jdbc.bind=TRACE: genaue Statements und Parameter, z. B. INSERT plus unnötiges UPDATE.
  • hibernate.generate_statistics=true: Anzahl Statements und Entity-Loads pro Session.
  • Schema-Vergleich: spring.jpa.hibernate.ddl-auto=validate stoppt den Start, wenn Mapping und Tabellen nicht passen.
  • Generiertes DDL ansehen: jakarta.persistence.schema-generation.scripts.action=create schreibt das DDL in eine Datei, gut zum Prüfen des Mappings.
  • PostgreSQL: \d+ tabelle zeigt Foreign Keys und Constraints. EXPLAIN zeigt Joins oder Append bei polymorphen Queries.

8. Senior-Punkte

  1. Weniger Beziehungen sind mehr. Jede bidirektionale Collection ist eine Quelle für N+1 und Inkonsistenz. Viele Beziehungen braucht man nur als ID.
  2. Aggregate bestimmen Cascade. Cascade nur vom Aggregat-Root zu seinen Teilen (Bestellung → Positionen). Nie zu geteilten Daten.
  3. Vererbung sparsam. SINGLE_TABLE als Standard, JOINED wenn Constraints wichtig sind. TABLE_PER_CLASS fast nie.
  4. Das Schema zuerst denken. Das Mapping folgt einem guten Tabellen-Design, nicht umgekehrt.
  5. Join-Tabellen mit Daten sind Entities. Sobald eine Beziehung Attribute hat, wird sie ein eigenes Objekt.
  6. Lesen über Projektionen. Für Listen und Reports DTO-Queries statt tiefer Entity-Graphen.

10. Fallen

  • „Ein lines.add(line) reicht, um die Beziehung zu speichern.“ → Falsch. Nur die Owning Side (line.order) zählt.
  • „@ManyToMany mit List ist gleich wie mit Set.“ → Falsch. Mit List schreibt Hibernate die Join-Tabelle oft komplett neu.
  • „Ohne @Inheritance gibt es eine Tabelle pro Klasse.“ → Falsch. Standard ist SINGLE_TABLE.
  • „@MappedSuperclass erlaubt Queries auf die Basisklasse.“ → Falsch. Sie ist keine Entity.
  • „orphanRemoval und CascadeType.REMOVE sind gleich.“ → Falsch. orphanRemoval löscht auch beim Entfernen aus der Collection.
  • „Unidirektionales @OneToMany ist am einfachsten.“ → Nicht für die DB. Es erzeugt eine Join-Tabelle oder extra UPDATEs.

11. Fragen

Was ist die Owning Side einer Beziehung?

Die Seite, die den Foreign Key oder die Join-Tabelle verwaltet. Nur ihre Änderungen schreibt Hibernate in die DB.

Was bedeutet mappedBy?

Es markiert die Inverse Side und nennt das Feld der Owning Side. Diese Seite hat keine eigene Spalte.

Warum braucht man Helper-Methoden bei bidirektionalen Beziehungen?

Hibernate setzt die Gegenseite nicht automatisch. Die Methode setzt beide Seiten, damit Objekte und DB gleich sind.

Was passiert bei einem unidirektionalen @OneToMany ohne @JoinColumn?

Hibernate legt eine Join-Tabelle an. Mit @JoinColumn gibt es oft INSERT und danach ein extra UPDATE für den Foreign Key.

Set oder List bei @ManyToMany?

Set. Mit einer List (Bag) löscht Hibernate beim Entfernen oft alle Zeilen der Join-Tabelle und fügt den Rest neu ein.

Wie bilden Sie eine Many-to-Many mit Zusatzdaten ab?

Als eigene Entity mit zwei @ManyToOne und den Zusatzspalten, z. B. Membership(user, team, role, since).

Was macht @MapsId?

Die abhängige Entity nutzt die ID der Elternentity als eigenen Primärschlüssel. Typisch für @OneToOne.

Warum ist die Inverse Side von @OneToOne oft nicht lazy?

Hibernate weiss ohne Abfrage nicht, ob ein Partner existiert, und muss null oder einen Proxy wählen. Darum lädt es sofort.

Welche Vererbungs-Strategien gibt es?

SINGLE_TABLE (eine Tabelle mit Discriminator), JOINED (Tabelle pro Klasse mit Joins), TABLE_PER_CLASS (volle Tabelle pro konkreter Klasse mit UNION).

Welche Strategie ist der Standard?

SINGLE_TABLE, mit einer Discriminator-Spalte DTYPE.

Wann wählen Sie JOINED?

Wenn Unterklassen viele eigene Pflichtfelder haben und Constraints wichtig sind. Preis: Joins bei polymorphen Abfragen.

Was ist der Nachteil von TABLE_PER_CLASS?

Polymorphe Queries werden UNION über alle Tabellen. Es gibt keinen gemeinsamen Foreign Key, und IDENTITY-IDs gehen nicht.

@MappedSuperclass vs Entity-Vererbung?

@MappedSuperclass vererbt nur Felder und ist keine Entity. Entity-Vererbung erlaubt polymorphe Queries und Beziehungen zur Basisklasse.

Was macht CascadeType.PERSIST?

Beim Persistieren der Eltern-Entity werden neue verbundene Entities mitgespeichert.

orphanRemoval vs CascadeType.REMOVE?

REMOVE löscht Kinder beim Löschen der Eltern. orphanRemoval löscht ein Kind zusätzlich, wenn es aus der Collection entfernt wird.

Warum kein Cascade auf @ManyToOne?

Viele Kinder teilen sich einen Elternteil. Ein REMOVE würde geteilte Daten löschen.

Was ist ein @Embeddable?

Ein Wertobjekt ohne eigene ID, dessen Felder als Spalten in der Tabelle der Entity liegen, z. B. eine Adresse.

Was ist eine @ElementCollection?

Eine Sammlung von Werten oder Embeddables in einer eigenen Tabelle, ohne eigene IDs. Änderungen schreiben oft die ganze Sammlung neu.

Wie implementieren Sie equals und hashCode für Entities?

Mit einem natürlichen Schlüssel oder ID-basiert mit konstantem hashCode pro Klasse. Nie mit allen Feldern und nie mit getClass bei Proxies.

Szenario: Neue Bestellpositionen werden gespeichert, aber order_id ist NULL. Warum?

Nur die Liste der Bestellung wurde ergänzt, nicht line.setOrder(order). Die Owning Side ist leer. Lösung: Helper-Methode, die beide Seiten setzt.

Szenario: Beim Entfernen eines Tags aus einem Artikel sieht man im Log 200 DELETE und 199 INSERT. Was ist los?

@ManyToMany mit List (Bag): Hibernate schreibt die Join-Tabelle neu. Lösung: Set statt List oder eigene Join-Entity.

Szenario: Ein Report über alle Zahlungsarten ist langsam, im Plan stehen zehn LEFT JOINs. Was tun Sie?

JOINED-Vererbung mit vielen Unterklassen. Für den Report eine DTO-Query auf die Basistabelle; langfristig SINGLE_TABLE prüfen oder gezielt Unterklassen abfragen.
