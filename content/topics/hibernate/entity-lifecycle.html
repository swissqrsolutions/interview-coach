Entity-Lebenszyklus

Kern: Der Entity-Lebenszyklus ist die Menge der Zustände, die ein Entity-Objekt gegenüber dem Persistence Context (der Objekt-Verwaltung einer Session) hat. Es gibt vier: transient, managed, detached, removed. Nur managed Objekte beobachtet Hibernate, und nur ihre Änderungen landen automatisch in der Datenbank.

Antwort-Muster

Frage: Welche Zustände hat ein Entity, und was macht Hibernate damit?

  1. Mechanismus: Vier Zustände: transient, managed, detached, removed. Nur managed Objekte beobachtet der Persistence Context.
  2. Zahl: Eine Sequence mit allocationSize 50 reserviert 50 IDs pro nextval. Das INSERT kommt erst beim Flush.
  3. Trade-off: Sequence erlaubt Batching. IDENTITY ist einfacher, aber jedes INSERT läuft sofort.
  4. Produktion: Nach merge arbeite ich mit dem Rückgabewert weiter, sonst geht die Änderung verloren.

1. Die Reise eines Entity-Objekts

  1. Geburt (transient): new Author("Anna") ist ein normales Java-Objekt. Es hat meist noch keine ID und keine Zeile.
  2. Aufnahme (managed): persist() legt das Objekt in den Persistence Context. Mit einer Sequence holt Hibernate nur die ID. Das INSERT kommt erst beim Flush.
  3. Leben (managed): Jede Änderung per Setter zählt. Beim Flush vergleicht Hibernate mit dem Snapshot (Dirty Checking) und schreibt ein UPDATE. Ein save() ist nicht nötig.
  4. Abschied (detached): Die Transaktion endet, die Session schliesst. Das Objekt hat noch seine ID. Änderungen daran sieht niemand.
  5. Rückkehr (merge): merge() sucht oder lädt die managed Instanz mit derselben ID. Es kopiert den Zustand darauf und gibt diese Instanz zurück. Das übergebene Objekt bleibt detached.
  6. Tod (removed): remove() markiert ein managed Objekt. Beim Flush kommt das DELETE. Danach ist das Objekt wieder ein normales Java-Objekt.

2. Aufbau

  1. Service-Code: Er erzeugt Objekte mit new. Hibernate kennt sie noch nicht.
  2. Session (Hibernate) bzw. EntityManager (JPA): die Arbeits-Einheit, meist eine pro Transaktion.
  3. Persistence Context: eine Map von (Entity-Typ, ID) auf genau ein Objekt. Daneben liegt ein Snapshot, der geladene Zustand für den Vergleich beim Flush.
  4. Action Queue: Hibernate sammelt INSERT, UPDATE und DELETE. Es schickt sie erst beim Flush zur Datenbank.
  5. Detached: Nach dem Schliessen der Session leben die Objekte weiter, aber niemand beobachtet sie mehr.

3. Details, die Interviewer fragen

  1. persist vs merge: persist() macht dasselbe Objekt managed. Es gibt void zurück. merge() gibt eine andere managed Instanz zurück. Man muss mit dem Rückgabewert weiterarbeiten.
  2. persist auf detached: Laut JPA kann EntityExistsException kommen. Sie kommt sofort oder beim Flush. Hibernate meldet „detached entity passed to persist“.
  3. remove auf detached: Das geht nicht. Man lädt zuerst oder nutzt merge. Dann entfernt man die managed Instanz.
  4. merge auf removed: Laut JPA kommt eine IllegalArgumentException.
  5. detach: Nicht geflushte Änderungen dieses Objekts gehen verloren. Das gilt auch für ein geplantes DELETE.
  6. Flush-Reihenfolge: Hibernate führt SQL nicht in der Reihenfolge deiner Aufrufe aus. Zuerst kommen die INSERTs, dann die UPDATEs. Danach folgen die Collection-Änderungen, ganz am Ende die DELETEs.
  7. Hibernate 6.6: merge() eines detached Objekts, dessen Zeile gelöscht wurde, wirft jetzt OptimisticLockException. Vorher gab es ein neues INSERT. Das gilt, wenn das Entity eine generierte ID oder eine nicht-primitive @Version hat.
  8. Hibernate 7: save, update, saveOrUpdate, delete und load sind entfernt. Ersatz sind persist, merge, remove und getReference.
  9. getReference: Es gibt einen Proxy zurück, also einen Platzhalter ohne SELECT. Damit setzt man eine Fremdschlüssel-Beziehung, ohne die Zeile zu laden. JPA 3.2 hat auch getReference(T entity) für detached Objekte.
  10. IDENTITY-Spalten: Die ID entsteht erst beim INSERT. Darum macht persist() das INSERT sofort. Insert-Batching ist dann nicht möglich.
  11. Spring Data save(): Es ruft persist, wenn das Entity neu ist. Sonst ruft es merge. Neu heisst, eine nicht-primitive @Version ist null. Ohne solche Version heisst es, die ID ist null. Eine selbst gesetzte ID ohne Version führt zu merge und einem zusätzlichen SELECT.
  12. Cascade: Das ist die Weitergabe einer Operation vom Eltern- an das Kind-Entity. Der Default ist keine Cascade. ALL enthält alle Typen darunter.
  13. PERSIST: persist(order) speichert auch neue OrderLines.
  14. MERGE: merge(order) kopiert auch die Lines aus dem DTO-Graph.
  15. REMOVE: remove(order) löscht auch die Lines. Laut JPA ist es nur für @OneToOne und @OneToMany gedacht.
  16. DETACH und REFRESH: Sie geben detach und refresh weiter.
  17. orphanRemoval = true: Ein Kind, das aus der Collection entfernt wird, wird gelöscht. Beispiel: order.getLines().remove(line) löst ein DELETE aus.

4. Fallen

  • „persist() macht sofort ein INSERT.“ → Nur bei IDENTITY. Sonst kommt das INSERT beim Flush.
  • „Nach merge(a) ist a managed.“ → Falsch. Managed ist der Rückgabewert. a bleibt detached.
  • „Für ein Update muss ich save() aufrufen.“ → Bei managed Entities nicht. Dirty Checking schreibt beim Flush.
  • „CascadeType.ALL ist ein guter Default.“ → Nein. Er enthält REMOVE und kann ganze Graphen löschen.
  • „Detached heisst gelöscht.“ → Nein. Detached heisst nur: nicht mehr beobachtet. Die Zeile existiert.

5. Selbsttest

Warum?

Warum braucht ein Update kein save()?

Hibernate vergleicht beim Flush jedes managed Objekt mit seinem Snapshot. Geänderte Objekte bekommen automatisch ein UPDATE.

Warum ist CascadeType.ALL auf @ManyToOne gefährlich?

Beim Löschen des Kindes wird auch der Elternteil gelöscht. Das trifft oft andere Datensätze, die denselben Elternteil nutzen.

Warum macht IDENTITY Batch-Inserts unmöglich?

Die ID entsteht erst beim INSERT. Hibernate muss sofort einfügen, um sie zu kennen, und kann nicht sammeln.

Warum gibt merge eine andere Instanz zurück?

merge kopiert den Zustand auf die managed Instanz mit derselben ID. Das übergebene Objekt bleibt detached.

Wie innen?

Welche Zustände hat ein Entity?

Transient (neu, unbekannt), managed (im Persistence Context), detached (hat ID, aber nicht mehr beobachtet) und removed (DELETE geplant).

Was macht persist()?

Es macht ein transientes Objekt managed und plant ein INSERT. Mit Sequence kommt das INSERT erst beim Flush.

Was passiert bei persist() mit einem detached Objekt?

Es ist ein Fehler. JPA erlaubt EntityExistsException, Hibernate meldet „detached entity passed to persist“.

Wie wird ein Objekt detached?

Durch detach(obj), clear() oder das Schliessen der Session, meist am Ende der Transaktion.

Was passiert mit Änderungen an einem detached Objekt?

Nichts. Sie landen erst in der Datenbank, wenn man sie per merge zurückholt oder auf eine geladene Instanz überträgt.

Was ist getReference()?

Es gibt einen Proxy ohne SELECT zurück. Nützlich, um eine Beziehung über die ID zu setzen.

Zahlen

Was bedeutet allocationSize = 50?

Ein nextval reserviert 50 IDs. Hibernate vergibt sie im Speicher. Das Inkrement der Sequence muss dazu passen.

Was hat sich in Hibernate 6.6 bei merge() geändert?

Fehlt die Zeile eines eindeutig detached Objekts, kommt jetzt eine OptimisticLockException statt eines neuen INSERT.

Welche Session-Methoden fehlen in Hibernate 7?

save, update, saveOrUpdate, delete und load. Man nutzt persist, merge, remove und getReference.

Vergleich

Was ist der Unterschied zwischen persist() und merge()?

persist macht dasselbe Objekt managed und gibt nichts zurück. merge kopiert den Zustand auf eine managed Instanz und gibt diese zurück.

Was ist orphanRemoval?

Ein Kind, das aus der Collection des Elternteils entfernt wird, wird gelöscht. Cascade REMOVE löscht dagegen nur beim Löschen des Elternteils.

Was ist eine StatelessSession?

Eine Session ohne Persistence Context. Kein Dirty Checking, kein Cache, jede Operation ist sofort SQL. Gut für Bulk-Verarbeitung.

Produktion

Was geht kaputt, wenn ich nach merge mit dem alten Objekt weiterarbeite?

Das alte Objekt bleibt detached. Änderungen daran sieht Hibernate nicht, und sie gehen verloren. Fix: den Rückgabewert von merge nutzen.

Szenario: Ein REST-PUT ändert nichts in der Datenbank, aber es gibt keinen Fehler. Was prüfen Sie?

Ob der Code mit dem Rückgabewert von merge weiterarbeitet. Ob überhaupt eine Transaktion läuft und committed wird. Und ob das Objekt detached geändert wurde.

Szenario: Beim Speichern einer Bestellung kommt „detached entity passed to persist“. Woran liegt es?

Ein verknüpftes Objekt mit ID läuft per Cascade PERSIST in persist. Fix: Referenz per getReference setzen oder die Cascade auf diese Beziehung entfernen.

Szenario: Nach einem Update fehlen plötzlich alle Positionen einer Bestellung. Was ist passiert?

Wahrscheinlich wurde ein DTO mit leerer Liste gemergt, und orphanRemoval hat alle Kinder gelöscht. Fix: Collection gezielt ändern statt ganzen Graphen mergen.

Design

Welche Cascade-Typen gibt es?

PERSIST, MERGE, REMOVE, REFRESH, DETACH und ALL. Default ist keine Cascade.

Wann ruft Spring Data save() persist und wann merge?

persist, wenn das Entity als neu gilt (Version-Wrapper null, ohne Version: ID null). Sonst merge, mit einem möglichen zusätzlichen SELECT.

Wie sieht ein gutes Update-Muster aus?

In der Transaktion laden, Setter aufrufen, fertig. Das ist klarer und sicherer als merge eines ganzen Graphen.

Mehr

Gerüst

  • Warum? Hibernate soll Änderungen automatisch erkennen und gebündelt schreiben. Dafür hat jedes Objekt einen klaren Zustand.
  • Wie innen? Persistence Context = Map (Typ, ID) → Objekt plus Snapshot. Der Flush vergleicht, die Action Queue schickt INSERT, UPDATE, DELETE.
  • Zahlen allocationSize 50: ein nextval reserviert 50 IDs. Hibernate 6.6: merge auf gelöschte Zeile → OptimisticLockException. Hibernate 7: save/update/delete/load entfernt.
  • Vergleich persist: dasselbe Objekt, void. merge: andere Instanz als Rückgabe. StatelessSession: kein Persistence Context.
  • Produktion Rückgabewert von merge ignoriert → Änderung weg. CascadeType.ALL auf @ManyToOne → Autor mitgelöscht. IDENTITY → kein Batching.
  • Design DTOs am Rand, Update per Setter in der Transaktion. Cascade nur bei echtem Besitz. @Version immer einplanen.

Beispiel: Zustände im SQL-Log sehen

@Entity
class Author {
  @Id @GeneratedValue Long id;   // Hibernate 6+: Sequence author_seq, Schritt 50
  String name;
  @Version int version;
}

// Transaktion 1
Author a = new Author("Anna");      // 1 transient
em.persist(a);                       // 2 managed, ID da, noch kein INSERT
em.flush();                          // 3 INSERT
em.detach(a);                        // 4 detached
a.setName("Anna C.");                // 5 Hibernate sieht das nicht
Author m = em.merge(a);              // 6 SELECT, Zustand auf neue Instanz kopiert
System.out.println(a == m);          // 7
em.flush();                          // 8 UPDATE mit Versionsprüfung
em.remove(m);                        // 9 removed
em.flush();                          // 10 DELETE
select nextval('author_seq')
insert into author (name,version,id) values (?,?,?)
select a1_0.id,a1_0.name,a1_0.version from author a1_0 where a1_0.id=?
false
update author set name=?,version=? where id=? and version=?
delete from author where id=? and version=?

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Log mit org.hibernate.SQL auf DEBUG. Aliasse können je nach Version abweichen.

$ psql -c "create sequence author_seq increment by 50" \
       -c "select nextval('author_seq'), nextval('author_seq')"
 nextval | nextval
---------+---------
       1 |      51

Echte Ausgabe, PostgreSQL 17.12.

  1. Bei persist() braucht Hibernate nur eine ID. Ein nextval reserviert einen Block von 50 IDs (pooled optimizer, allocationSize = 50 ist der JPA-Default). Die nächsten 49 IDs kosten keinen Datenbank-Aufruf.
  2. Das INSERT kommt erst beim Flush. Darum kann Hibernate viele INSERTs bündeln (JDBC Batching).
  3. Nach detach() ändert setName nur Java-Speicher.
  4. merge() lädt die Zeile per SELECT. Es kopiert „Anna C.“ auf eine neue managed Instanz. Darum a == m → false.
  5. Das UPDATE prüft version=?. Hat jemand die Zeile inzwischen geändert, trifft es 0 Zeilen → OptimisticLockException.
  6. Das DELETE hängt ebenfalls an der Version.

Vergleich

  • persist: transient → managed. Kein Rückgabewert. Für neue Objekte.
  • merge: detached (oder transient) → Kopie wird managed. Gibt die managed Instanz zurück. Für Objekte aus einer anderen Session, z. B. aus einem Formular.
  • remove: managed → removed. DELETE beim Flush.
  • detach / clear / close: managed → detached. Ein Objekt, alle Objekte, oder Session-Ende.
  • refresh: überschreibt den Zustand eines managed Objekts mit der Datenbank.
  • Cascade REMOVE vs orphanRemoval: REMOVE löscht Kinder, wenn der Elternteil gelöscht wird. orphanRemoval löscht ein Kind auch, wenn es nur aus der Collection fliegt.
  • Hibernate StatelessSession: kein Persistence Context, keine Zustände, kein Dirty Checking. Jede Operation ist sofort ein SQL. Gut für Bulk-Jobs.

In der Produktion

  1. Änderung geht verloren: Code ruft merge(dto), arbeitet aber mit dem alten Objekt weiter. Fix: Rückgabewert von merge nutzen.
  2. „detached entity passed to persist“: Ein Objekt mit gesetzter ID kommt in persist(). Typisch: Kind mit cascade = PERSIST zeigt auf einen schon gespeicherten Elternteil. Fix: Referenz per getReference(id) setzen oder merge.
  3. Unerwartete DELETEs: CascadeType.ALL auf @ManyToOne. Ein remove(book) löscht dann den Autor mit. Fix: Cascade nur vom Eltern- zum Kind-Entity, nie auf @ManyToOne.
  4. Ganze Collection überschrieben: Ein Request-DTO mit leerer Liste wird gemergt, orphanRemoval löscht alle Kinder. Fix: DTO explizit auf managed Entities abbilden statt blind zu mergen.
  5. Langsame Bulk-Imports: IDENTITY verhindert Batching, und der Persistence Context wächst. Fix: Sequence mit allocationSize, hibernate.jdbc.batch_size, regelmässig flush() + clear().

Diagnose: Werkzeuge und Befehle

  • logging.level.org.hibernate.SQL=DEBUG: jedes SQL. org.hibernate.orm.jdbc.bind=TRACE: die Parameter dazu.
  • em.contains(obj): ist das Objekt managed?
  • Hibernate.isInitialized(obj): ist ein Proxy schon geladen?
  • hibernate.generate_statistics=true: zählt Inserts, Updates, Deletes und Statements pro Session.
  • Test mit Testcontainers und PostgreSQL: Cascade- und Merge-Verhalten gegen eine echte Datenbank prüfen.

Senior-Punkte

  1. Managed Entities nicht über die Transaktion hinaus reichen. Am Rand (REST, UI) besser DTOs. Dann gibt es kaum detached Objekte und kaum merge.
  2. Update-Muster: In der Transaktion laden, Setter aufrufen, fertig. Das ist klarer und sicherer als merge eines ganzen Graphen.
  3. Cascade bewusst wählen: Nur bei echtem Besitz (Aggregate, z. B. Order → Lines). Nie zwischen unabhängigen Aggregaten.
  4. ID-Strategie ist eine Leistungsfrage: Sequence mit Pooling erlaubt Batching. IDENTITY ist einfach, aber langsam bei Massen-Inserts.
  5. Versionsfeld immer einplanen. Es schützt merge und Updates vor Lost Updates und hilft Spring Data, „neu“ zu erkennen.
  6. Hibernate 7 bereinigt die API. Alter Code mit saveOrUpdate muss vor dem Upgrade auf persist/merge umgebaut werden.
