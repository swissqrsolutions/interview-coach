Lazy vs Eager Loading

Kern: Lazy Loading lädt eine Beziehung erst beim ersten Zugriff, Eager Loading lädt sie sofort mit. Lazy spart unnötige Daten, braucht aber eine offene Session beim ersten Zugriff. Meist mappt man alles LAZY und lädt pro Use Case gezielt mit JOIN FETCH, Entity Graph oder DTO-Projektion.

Antwort-Muster

Frage: Was ist der Unterschied zwischen Lazy und Eager Loading?

  1. Mechanismus: Lazy lädt über einen Proxy oder PersistentBag erst beim Zugriff. Eager lädt sofort mit.
  2. Zahl: JPA-Default: To-one EAGER, To-many LAZY. Darum setze ich To-one selbst auf LAZY.
  3. Trade-off: Lazy spart Daten, braucht aber eine offene Session. Ohne sie kommt LazyInitializationException.
  4. Produktion: Ich lade pro Use Case in der Transaktion, mit JOIN FETCH, Entity Graph oder DTO.

1. Die Reise eines Lazy-Zugriffs

  1. Laden: Der Service lädt einen Author. books ist LAZY, also nur eine leere Hülle.
  2. Commit: @Transactional endet. Die Session schliesst. Der Author ist detached.
  3. Controller: Jackson ruft getBooks() auf, um JSON zu bauen.
  4. Exception: Die Hülle will nachladen, hat aber keine Session mehr: LazyInitializationException.
  5. Lösung: Die nötigen Daten in der Transaktion laden: per JOIN FETCH, Entity Graph oder direkt als DTO. Und Entities nicht als JSON nach aussen geben.

2. Aufbau

  1. Proxy: Für eine lazy To-one-Beziehung setzt Hibernate eine generierte Unterklasse des Entity ein. Sie kennt nur die ID. Der erste Aufruf eines Getters (ausser getId()) löst ein SELECT aus.
  2. Persistent Collection: Für eine lazy Collection setzt Hibernate eine eigene List/Set-Klasse ein, z. B. PersistentBag. size() oder Iterieren lädt sie.
  3. Session offen: Dann lädt Hibernate nach. Session zu: LazyInitializationException.
  4. Defaults: To-one ist EAGER, To-many ist LAZY. Das ist eine bekannte Falle der JPA-Spezifikation.

3. Details, die Interviewer fragen

  1. Warum To-one auf LAZY setzen? EAGER ist der JPA-Default für @ManyToOne und @OneToOne. In Queries lädt Hibernate EAGER-Beziehungen oft mit zusätzlichen SELECTs nach. Die Query joint sie nämlich nicht. Das erzeugt N+1. Die Hibernate-Doku empfiehlt, alle Beziehungen mit fetch = LAZY zu mappen.
  2. EAGER kann man nicht abschalten. Eine Query kann LAZY zu EAGER machen (JOIN FETCH). Umgekehrt geht es nicht.
  3. LAZY ist nur ein Hinweis. Laut JPA darf der Provider trotzdem laden. Die inverse Seite eines @OneToOne (mit mappedBy) lädt Hibernate ohne Bytecode Enhancement immer. Es weiss nicht, ob dort null steht.
  4. Lazy Spalten: @Basic(fetch = LAZY) ist für grosse Spalten gedacht, z. B. ein PostGIS-Polygon oder ein BLOB. Es wirkt nur mit Bytecode Enhancement.
  5. Lazy Group: Mit Bytecode Enhancement lädt Hibernate einzelne Attribute nach Bedarf. Alle lazy Einzel-Attribute bilden standardmässig eine Gruppe. Greift man auf eines zu, kommen alle. @LazyGroup ändert das.
  6. getId() auf einem Proxy lädt nichts. Die ID ist im Proxy gespeichert.
  7. Proxy und getClass(): Der Proxy ist eine Unterklasse. getClass() liefert die Proxy-Klasse. Darum vergleicht man in equals() nicht mit getClass(). Hibernate.unproxy(obj) liefert das echte Objekt.
  8. Entity Graph: @NamedEntityGraph oder em.createEntityGraph(...) beschreibt, was mitkommt. Man gibt ihn als Hint an die Query. Seit JPA 3.2 gibt es em.find(entityGraph, id). In Spring Data nutzt man @EntityGraph(attributePaths = "books").
  9. fetchgraph: Der Hint jakarta.persistence.fetchgraph macht Graph-Attribute EAGER. Alle anderen werden LAZY.
  10. loadgraph: Der Hint jakarta.persistence.loadgraph macht Graph-Attribute EAGER. Alle anderen folgen ihrem Mapping.
  11. DTO-Projektion: Beispiel ist select new com.x.BookDto(b.id, b.title, a.name) from Book b join b.author a. Es gibt keine Entities und keinen Persistence Context. Es gibt keine Lazy-Fallen und nur nötige Spalten. Ideal für Lese-Pfade und Listen.
  12. DISTINCT seit Hibernate 6: Hibernate filtert doppelte Eltern-Objekte bei JOIN FETCH immer selbst. distinct in HQL ist dafür nicht mehr nötig. Ein distinct im HQL geht aber weiter ins SQL.
  13. Batch Fetching: @BatchSize wirkt auf uninitialisierte Proxies und Collections. Hibernate lädt dann viele Eltern mit einem SELECT nach.
  14. Hibernate.initialize(a.getBooks()): Es lädt eine Collection explizit. Das geht nur, solange die Session offen ist.

4. Fallen

  • „@ManyToOne ist standardmässig LAZY.“ → Falsch. Laut JPA ist es EAGER. Man muss fetch = LAZY selbst setzen.
  • „EAGER verhindert N+1.“ → Nein. Bei Queries lädt Hibernate EAGER-Beziehungen oft mit Extra-SELECTs. Das ist N+1.
  • „enable_lazy_load_no_trans löst LazyInitializationException.“ → Es versteckt sie und erzeugt viele Mini-Transaktionen.
  • „Mit JOIN FETCH lade ich einfach alle Collections auf einmal.“ → Kartesisches Produkt oder MultipleBagFetchException.
  • „Für JOIN FETCH brauche ich DISTINCT gegen Duplikate.“ → In Hibernate 6+ nicht mehr. Hibernate entfernt doppelte Eltern selbst.

5. Selbsttest

Warum?

Warum sollte @ManyToOne LAZY sein?

EAGER lädt die Beziehung immer, bei Queries oft mit Extra-SELECTs pro Zeile. Das ist N+1 und kann pro Query nicht abgeschaltet werden.

Warum schalten Sie Open in View aus?

Es versteckt Queries ausserhalb der Transaktion, fördert N+1 und hält die Connection den ganzen Request lang.

Warum ist die inverse Seite von @OneToOne oft nicht lazy?

Hibernate weiss ohne Abfrage nicht, ob dort null oder ein Objekt steht. Ohne Bytecode Enhancement lädt es darum sofort.

Warum nicht zwei Collections per JOIN FETCH laden?

Das ergibt ein kartesisches Produkt. Bei zwei Bags wirft Hibernate MultipleBagFetchException.

Wie innen?

Was ist Lazy Loading?

Hibernate lädt eine Beziehung erst beim ersten Zugriff. Bis dahin steht ein Proxy oder eine leere Collection-Hülle da.

Was ist ein Hibernate-Proxy?

Eine generierte Unterklasse des Entity, die nur die ID kennt. Ein Getter-Aufruf lädt die Daten nach.

Wann kommt eine LazyInitializationException?

Wenn ein Proxy oder eine lazy Collection nachladen will, die Session aber schon geschlossen ist. Typisch: JSON-Mapping nach dem Commit.

Lädt getId() auf einem Proxy die Daten?

Nein. Die ID ist im Proxy gespeichert. Erst andere Getter lösen ein SELECT aus.

Was ist an equals() mit getClass() bei Proxies falsch?

Der Proxy ist eine Unterklasse. getClass() ist dann ungleich, und equals liefert false für dasselbe Entity.

Zahlen

Welche Fetch-Defaults hat JPA?

@ManyToOne und @OneToOne: EAGER. @OneToMany, @ManyToMany und @ElementCollection: LAZY. Einfache Spalten: EAGER.

Brauche ich in Hibernate 6 DISTINCT bei JOIN FETCH?

Nein. Hibernate 6 filtert doppelte Eltern-Objekte selbst aus dem Ergebnis.

Wie viele Zeilen liefert ein JOIN auf Bücher und Reviews für einen Autor?

Mit 10 Büchern und je 3 Reviews sind es 1 × 10 × 3 = 30 Zeilen. Bei zwei parallelen Collections wächst es als Produkt.

Vergleich

Was ist der Unterschied zwischen fetchgraph und loadgraph?

fetchgraph: nur die Graph-Attribute eager, alles andere lazy. loadgraph: Graph-Attribute eager, alles andere nach Mapping.

Was ist JOIN FETCH?

Ein JOIN in HQL/JPQL, der die Beziehung im selben SQL lädt und befüllt. Die Beziehung ist danach initialisiert.

Wann ist eine DTO-Projektion besser als ein Entity?

Bei Lese-Pfaden wie Listen und Reports. Nur nötige Spalten, kein Persistence Context, keine Lazy-Probleme.

Was ist der Unterschied zwischen JOIN FETCH und @BatchSize?

JOIN FETCH lädt in einem SQL mit JOIN. @BatchSize bleibt lazy, lädt aber viele Eltern mit einem SELECT nach. Es passt gut für mehrere Collections.

Produktion

Wie lösen Sie eine LazyInitializationException richtig?

Daten in der Transaktion laden: JOIN FETCH, Entity Graph oder DTO-Projektion. Nicht mit EAGER oder enable_lazy_load_no_trans.

Was ist Open Session in View?

Die Session bleibt bis zum Ende des Web-Requests offen. Lazy Loading geht dann auch in der View. In Spring Boot ist es per Default an, mit Warnung.

Szenario: Ein REST-Endpoint wirft „could not initialize proxy - no Session“. Was tun Sie?

Die Antwort als DTO im Service bauen und die nötigen Beziehungen dort per JOIN FETCH oder Entity Graph laden. Nicht EAGER und nicht enable_lazy_load_no_trans.

Szenario: Eine Seite mit 50 Zeilen braucht 51 Queries, obwohl alles LAZY ist. Warum?

Die View greift auf eine Beziehung pro Zeile zu, und Open in View lädt nach. Fix: Open in View aus, im Service per JOIN FETCH oder DTO laden.

Szenario: Eine Detail-Query mit JOIN FETCH auf Bücher und Awards braucht plötzlich Sekunden. Warum?

Zwei Collections im selben JOIN ergeben ein kartesisches Produkt. Fix: nur eine per JOIN FETCH, die andere per @BatchSize oder zweiter Query.

Design

Wie macht man eine grosse Spalte lazy?

@Basic(fetch = LAZY) mit Bytecode Enhancement. Ohne Enhancement: eigene Entity oder DTO-Projektion ohne die Spalte.

Welche Fetch-Strategie empfehlen Sie als Standard?

Alles LAZY mappen. Pro Use Case laden Sie mit JOIN FETCH, Entity Graph oder DTO-Projektion in der Transaktion.

Wie laden Sie zwei Collections eines Entity?

Eine per JOIN FETCH und die andere per @BatchSize oder in einer zweiten Query. Zwei per JOIN FETCH geben ein kartesisches Produkt.

Mehr

Gerüst

  • Warum? Nur laden, was der Use Case braucht. Alles LAZY mappen, pro Query gezielt fetchen.
  • Wie innen? Proxy (Unterklasse, kennt nur die ID) für To-one, PersistentBag für Collections. Zugriff ohne Session → LazyInitializationException.
  • Zahlen Defaults: To-one EAGER, To-many LAZY. Zwei Ebenen: 1 × 10 × 3 = 30 Zeilen. Pro Query höchstens eine Collection fetchen.
  • Vergleich JOIN FETCH: ein SQL pro Query. Entity Graph: getrennt von der Query. @BatchSize: lazy, aber gebündelt. DTO: schnell, nur lesen.
  • Produktion LazyInitializationException im Controller. Open in View versteckt N+1. Zwei Collections → kartesisches Produkt.
  • Design Fetch-Strategie in die Query, nicht ins Mapping. Listen als DTO. Open in View aus.

Beispiel: was JOIN FETCH in der Datenbank kostet

// HQL
select a from Author a left join fetch a.books where a.id = 1

Hibernate erzeugt ein SQL mit LEFT JOIN. So sieht das Ergebnis in PostgreSQL aus (100 Autoren, 1000 Bücher, 3000 Reviews):

select a.id as a_id, a.name, b.id as b_id, b.title
from author a left join book b on b.author_id = a.id
where a.id = 1 order by b.id limit 4;

 a_id |  name   | b_id |  title
------+---------+------+----------
    1 | Autor 1 |    1 | Buch 1
    1 | Autor 1 |  101 | Buch 101
    1 | Autor 1 |  201 | Buch 201
    1 | Autor 1 |  301 | Buch 301
(4 rows)

-- ein Autor mit seinen Büchern
select count(*) as zeilen from author a left join book b on b.author_id=a.id where a.id=1;
 zeilen
--------
     10

-- dazu noch die Reviews der Bücher (zwei Collections)
select count(*) as zeilen from author a left join book b on b.author_id=a.id
  left join review r on r.book_id=b.id where a.id=1;
 zeilen
--------
     30

-- dasselbe für alle Autoren
select count(*) as zeilen from author a left join book b on b.author_id=a.id
  left join review r on r.book_id=b.id;
 zeilen
--------
   3000

Echte Ausgabe, PostgreSQL 17.12.

  1. Ein JOIN wiederholt die Autor-Spalten in jeder Zeile. Für 1 Autor kommen 10 Zeilen.
  2. Hibernate 6+ entfernt die doppelten Autor-Objekte selbst. distinct ist in HQL dafür nicht mehr nötig.
  3. Mit einer zweiten Ebene (Reviews) wächst das Ergebnis: 1 × 10 × 3 = 30 Zeilen. Zwei parallele Collections (z. B. books und awards) ergeben ein kartesisches Produkt: Anzahl Bücher × Anzahl Awards.
  4. Sind beide Collections List ohne Index (Bags), lehnt Hibernate das ab: MultipleBagFetchException: cannot simultaneously fetch multiple bags.
  5. Regel: pro Query höchstens eine Collection fetchen. Weitere per @BatchSize oder in einer zweiten Query.

Vergleich

  • FetchType.EAGER im Mapping: immer geladen, überall. Kein Weg zurück pro Query. Fast nie richtig.
  • JOIN FETCH: eine Query, ein SQL, pro Use Case. Gut für eine Collection oder To-one-Ketten. Schlecht für mehrere Collections und Pagination.
  • Entity Graph: dasselbe wie JOIN FETCH, aber getrennt von der Query. Gut mit Spring-Data-Methoden wie findById.
  • @BatchSize / Subselect: lazy, aber gebündelt: ein SELECT für viele Eltern. Gut für mehrere Collections.
  • DTO-Projektion: kein Entity, nur Daten. Am schnellsten für Lesen. Nicht zum Ändern gedacht.
  • Open Session in View: lässt Lazy Loading bis in die View zu. Bequem, aber versteckte Queries ausserhalb der Transaktion.

In der Produktion

  1. LazyInitializationException im Controller: Entity wird nach dem Commit als JSON serialisiert. Fix: DTO im Service bauen, nötige Beziehungen per JOIN FETCH oder Entity Graph laden.
  2. Open in View versteckt N+1: In Spring Boot ist spring.jpa.open-in-view standardmässig an. Beim Start warnt Boot: „spring.jpa.open-in-view is enabled by default. Therefore, database queries may be performed during view rendering.“ Die Connection bleibt bis zum Ende des Requests belegt. Fix: spring.jpa.open-in-view=false und Daten im Service laden.
  3. hibernate.enable_lazy_load_no_trans=true als „Fix“: Jeder Lazy-Zugriff öffnet eine eigene Session und Transaktion. Das erzeugt versteckte N+1 und inkonsistente Daten. Hibernate markiert die Einstellung als unsicher und rät davon ab.
  4. EAGER-Kette lädt halbe Datenbank: Book → Author → Publisher → Country, alles EAGER. Ein findAll() erzeugt dutzende SELECTs. Fix: alles LAZY, gezielt fetchen.
  5. Speicher-Explosion bei JOIN FETCH: Zwei Collections in einer Query, kartesisches Produkt. Fix: eine Collection per JOIN FETCH, die andere per @BatchSize.
  6. Jackson und Proxies: Serialisierung eines nicht geladenen Proxys wirft Fehler oder löst Lazy Loading aus. Fix: keine Entities als API-Modell.

Diagnose: Werkzeuge und Befehle

  • logging.level.org.hibernate.SQL=DEBUG: zeigt jedes Lazy-SELECT. Ein SELECT nach dem Ende der Service-Methode bedeutet Open in View.
  • Hibernate.isInitialized(a.getBooks()): ist die Collection geladen?
  • PersistenceUnitUtil.isLoaded(entity, "books"): die JPA-Variante.
  • hibernate.generate_statistics=true: Anzahl Entity-Loads und Collection-Loads pro Session.
  • Beim Start im Log auf die Open-in-View-Warnung achten.
  • PostgreSQL: EXPLAIN ANALYZE auf das erzeugte JOIN-SQL. Grosse Zeilenzahl = kartesisches Produkt.

Senior-Punkte

  1. Mapping: alles LAZY. Fetch-Strategie gehört in die Query, nicht ins Mapping. So entscheidet jeder Use Case selbst.
  2. Lesen und Schreiben trennen: Listen und Reports als DTO-Projektion. Entities nur dort, wo man ändert.
  3. Open in View aus. Es koppelt die Connection-Dauer an die Request-Dauer und versteckt Queries. Bewusst laden ist besser.
  4. Eine Collection pro Query. Mehr Collections → Batch Fetching oder mehrere Queries. Das ist oft schneller als ein grosser JOIN.
  5. Grosse Spalten getrennt halten: Geometrien oder BLOBs in eigene Entities oder per Projektion ausschliessen, wenn kein Bytecode Enhancement aktiv ist.
  6. Lazy Loading ist kein Bug, sondern ein Vertrag: Wer ein Entity aus der Transaktion gibt, muss sagen, was geladen ist.
