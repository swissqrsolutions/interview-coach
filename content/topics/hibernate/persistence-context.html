Persistence Context

Hibernate · Tier 1 · Quellen: Introduction to Hibernate 7 (Kap. 1.5, 5.9, 6.3, 8.3, 8.15), Jakarta Persistence 3.2 (FlushModeType), Hibernate ORM 7.0 Migration Guide (QueryFlushMode), Hibernate Javadoc BatchSettings

Kern: Der Persistence Context ist die Objekt-Verwaltung einer Session: eine Map von Entity-ID auf genau ein Java-Objekt plus dessen geladenem Zustand. Er spart doppelte SELECTs (First-Level Cache), garantiert ein Objekt pro Zeile (Identity Guarantee) und findet Änderungen selbst (Dirty Checking). Beim Flush schreibt er die Änderungen als SQL in die Datenbank.

1. Wo sitzt der Persistence Context?

  1. Service-Methode: @Transactional öffnet die Transaktion. Spring bindet einen EntityManager daran.
  2. Persistence Context: jede Session hat ihren eigenen. Er lebt meist genau so lange wie die Transaktion.
  3. Snapshot: Kopie der geladenen Werte. Grundlage für das Dirty Checking.
  4. Action Queue: gesammelte SQL-Befehle. Sie gehen erst beim Flush raus.
  5. Second-Level Cache: optional und über alle Sessions geteilt. Er ist ein anderes Thema. Der Persistence Context ist der First-Level Cache und immer an.

2. Die Reise einer Änderung (die Geschichte zum Merken)

  1. Laden: em.find(Account.class, 1L) schickt ein SELECT. Hibernate legt das Objekt und einen Snapshot in den Context. Ein zweites find mit derselben ID schickt kein SQL.
  2. Ändern: acc.setBalance(80) ändert nur das Java-Objekt. Noch geht nichts zur Datenbank.
  3. Flush-Auslöser: Im Modus AUTO flusht Hibernate vor dem Commit und vor einer Query, deren Ergebnis die Änderung betreffen könnte. Oder der Code ruft flush().
  4. Dirty Checking: Hibernate vergleicht jedes managed Objekt Feld für Feld mit seinem Snapshot. Nur geänderte Objekte bekommen ein UPDATE.
  5. SQL senden: Die Action Queue sortiert: zuerst INSERTs, dann UPDATEs, zuletzt DELETEs. Mit hibernate.jdbc.batch_size gehen gleiche Statements gebündelt raus.
  6. Commit: Erst jetzt sehen andere Transaktionen die Änderung. Flush ist nicht Commit.
  7. Ende: Die Session schliesst. Der Context ist weg, alle Objekte sind detached.

3. Beispiel: Identity Guarantee gegen eine laufende Datenbank

Zwei Transaktionen in PostgreSQL, Isolation Read Committed (Default). Transaktion A liest zweimal. Transaktion B ändert dazwischen.

-- Transaktion A                      -- Transaktion B
begin;
select id, balance from account where id=1;
                                        update account set balance=80 where id=1;
                                        -- autocommit
select id, balance from account where id=1;
commit;
BEGIN
 id | balance
----+---------
  1 |  100.00
(1 row)

UPDATE 1          <- Transaktion B

 id | balance
----+---------
  1 |   80.00
(1 row)

COMMIT

Echte Ausgabe, PostgreSQL 17.12.

Dieselbe Situation mit Hibernate in Transaktion A:

Account a1 = em.find(Account.class, 1L);           // SELECT, balance=100
// ... Transaktion B setzt balance=80 und committet ...
Account a2 = em.find(Account.class, 1L);           // kein SQL
Account a3 = em.createQuery("from Account where id = 1", Account.class)
               .getSingleResult();                  // SELECT läuft, Zeile sagt 80
System.out.println(a1 == a2 && a2 == a3);          // true
System.out.println(a3.getBalance());                // 100.00
em.refresh(a3);
System.out.println(a3.getBalance());                // 80.00

Erwartetes Ergebnis (laut Doku, nicht ausgeführt).

  1. Die Datenbank liefert in Read Committed beim zweiten SELECT den neuen Wert 80.
  2. Das zweite find trifft den First-Level Cache. Es gibt kein SQL.
  3. Die Query geht zur Datenbank. Hibernate sieht aber: ID 1 ist schon im Context. Es gibt das vorhandene Objekt zurück und überschreibt es nicht.
  4. Darum a1 == a2 == a3. Pro ID gibt es genau ein Objekt. Das ist die Identity Guarantee.
  5. Effekt: innerhalb einer Session ein Repeatable Read auf Anwendungsebene, auch wenn die Datenbank nur Read Committed bietet. Frische Werte gibt es nur mit refresh().

4. Details, die Interviewer fragen

  1. Flush-Modi (Hibernate):
    • AUTO (Default): vor dem Commit und vor Queries, deren Ergebnis betroffen sein könnte.
    • COMMIT: nur vor dem Commit. Queries können veraltete Daten liefern.
    • ALWAYS: vor jeder Query. Teuer.
    • MANUAL: nie automatisch, nur per flush().
    JPA kennt nur AUTO und COMMIT (FlushModeType).
  2. AUTO und HQL: Hibernate flusht vor einer HQL-Query, wenn sie Tabellen mit offenen Änderungen berührt. Bei Native SQL kennt Hibernate die Tabellen nicht sicher. Vor kritischen Native Queries darum selbst flush() aufrufen.
  3. Hibernate 7: setFlushMode() auf Queries ist veraltet. Neu ist setQueryFlushMode(QueryFlushMode).
  4. Dirty Checking kostet: Bei jedem Flush prüft Hibernate alle managed Objekte. 50 000 Objekte im Context machen jeden Flush langsam.
  5. UPDATE schreibt alle Spalten: Standard ist ein festes UPDATE mit allen Spalten. Das SQL ist immer gleich und gut cachebar. @DynamicUpdate schreibt nur geänderte Spalten.
  6. Read-only: session.setDefaultReadOnly(true) oder ein Read-only-Hint bei Queries. Dann behält Hibernate keinen Snapshot und prüft nicht. Spart Speicher und CPU. Spring: @Transactional(readOnly = true) setzt das für die Hibernate-Session.
  7. Flush-Reihenfolge: INSERTs vor UPDATEs vor DELETEs. Löscht man eine Zeile und fügt eine neue mit gleichem Unique-Wert ein, kommt das INSERT zuerst → Unique-Verletzung. Fix: zwischen beiden flush().
  8. clear() vs detach(): clear() leert den ganzen Context, detach(obj) nur ein Objekt. Nicht geflushte Änderungen gehen dabei verloren.
  9. Lange Sessions: Ein Context über viele Requests (Extended Persistence Context) wächst, hält alte Daten und blockiert eventuell eine Connection. Heute meist vermieden.

5. Vergleich

  • First-Level Cache: pro Session, immer an, nur so lange wie die Transaktion. Schützt vor doppelten SELECTs per ID.
  • Second-Level Cache: pro SessionFactory, optional, über Transaktionen hinweg. Braucht eine Cache-Strategie und Invalidierung.
  • Query Cache: speichert Query-Ergebnisse als ID-Listen. Optional, nur mit Second-Level Cache sinnvoll.
  • Session vs StatelessSession: StatelessSession hat keinen Persistence Context, kein Dirty Checking, kein flush(). Jedes update() ist explizit.
  • flush vs commit: flush schickt SQL in die offene Transaktion. commit macht es dauerhaft und sichtbar. Ein Rollback nach dem Flush macht alles rückgängig.

6. In der Produktion

  1. Batch-Job wird immer langsamer und läuft in OutOfMemoryError: 1 Mio. Entities in einer Session. Fix: alle N Datensätze (z. B. 50, passend zu batch_size) flush() + clear(). Oder StatelessSession.
  2. Query liefert alten Wert: Die Identity Guarantee gibt das Objekt aus dem Context zurück. Fix: refresh() oder kurze Transaktionen.
  3. Unique-Verletzung beim Ersetzen: DELETE und INSERT mit gleichem Schlüssel in einer Transaktion. Flush-Reihenfolge macht INSERT zuerst. Fix: expliziter flush() nach dem remove.
  4. Unerwartete UPDATEs: Ein Getter normalisiert Daten, oder ein Converter liefert bei jedem Lesen ein neues, ungleiches Objekt. Dirty Checking sieht „geändert“. Fix: korrektes equals für Typen, keine Logik in Settern.
  5. Native Query sieht Änderung nicht: Im Modus COMMIT oder bei Native SQL. Fix: vorher flush().
  6. Lange Transaktion hält Locks und Connections: Ein Context über einen externen HTTP-Aufruf hinweg. Fix: externe Aufrufe ausserhalb der Transaktion.

7. Diagnose: Werkzeuge und Befehle

  • hibernate.generate_statistics=true: zählt pro Session Statements, Entity-Loads und Flushes.
  • logging.level.org.hibernate.SQL=DEBUG und org.hibernate.orm.jdbc.bind=TRACE: SQL und Parameter sehen, auch wann der Flush passiert.
  • session.getStatistics().getEntityCount(): wie viele Objekte im Context liegen.
  • hibernate.log_slow_query=500: Queries über 500 ms im Log (Default 0 = aus).
  • Heap-Dump (z. B. Eclipse MAT): viele EntityEntry-Objekte zeigen einen zu grossen Context.
  • PostgreSQL: select pid, state, xact_start from pg_stat_activity where state = 'idle in transaction' findet zu lange offene Transaktionen.

8. Senior-Punkte

  1. Kurze Sessions, kurze Transaktionen. Ein Context pro Request oder Use Case. Lange Sessions bringen Speicher, alte Daten und lange Locks.
  2. Lesen ohne Snapshot: Reine Lese-Pfade mit read-only oder DTO-Projektionen. Das spart viel Speicher und Flush-Zeit.
  3. Der Context ist kein Cache für Performance-Tuning. Er gilt nur in einer Transaktion. Wer über Requests cachen will, braucht Second-Level Cache oder einen echten Cache.
  4. Bulk-Arbeit gehört nicht ins Dirty Checking. Für Massen-Updates ein HQL- oder SQL-UPDATE. Achtung: das umgeht den Context, danach clear().
  5. Flush-Zeitpunkt kennen. Ein Constraint-Fehler kommt oft erst beim Flush, weit weg vom auslösenden Code. Im Test darum gezielt flush() aufrufen.

9. Aus dem Projekt

„Ich habe Hibernate bei NABODAT (Jakarta EE, Spring, PostgreSQL/PostGIS) eingesetzt; dort gilt dieselbe Regel: in der Transaktion laden, ändern, Hibernate schreibt beim Flush.“ (Prüfen und durch dein echtes Beispiel ersetzen. Konkrete Flush- oder Batch-Probleme stehen nicht im Profil.)

10. Fallen

  • „Flush heisst Commit.“ → Falsch. Flush schickt SQL in die offene Transaktion. Ein Rollback nimmt es zurück.
  • „Eine Query liefert immer den neuesten Stand.“ → Nicht für Objekte, die schon im Context sind. Hibernate gibt das vorhandene Objekt zurück.
  • „Der First-Level Cache spart Queries über Requests hinweg.“ → Nein. Er lebt nur so lange wie die Session.
  • „Dirty Checking ist gratis.“ → Es prüft alle managed Objekte bei jedem Flush. Bei grossen Contexts ist das teuer.
  • „FlushMode COMMIT ist immer schneller und sicher.“ → Queries in derselben Transaktion sehen dann die eigenen Änderungen nicht.

11. Fragen

Was ist der Persistence Context?

Die Objekt-Verwaltung einer Session: eine Map von Entity-ID auf genau ein Objekt plus Snapshot. Er ist First-Level Cache, Identity Map und Änderungs-Tracker.

Was ist der First-Level Cache?

Der Persistence Context selbst. Ein zweites find mit derselben ID in derselben Session schickt kein SQL.

Was ist die Identity Guarantee?

Pro Entity-ID gibt es in einer Session genau ein Java-Objekt. find und Query liefern dieselbe Instanz, also ist == true.

Was ist Dirty Checking?

Beim Flush vergleicht Hibernate jedes managed Objekt mit seinem Snapshot. Geänderte Objekte bekommen automatisch ein UPDATE.

Wann flusht Hibernate im Modus AUTO?

Vor dem Commit und vor einer Query, deren Ergebnis durch offene Änderungen betroffen sein könnte. Und bei explizitem flush().

Welche Flush-Modi gibt es?

Hibernate: AUTO, COMMIT, ALWAYS, MANUAL. JPA: AUTO und COMMIT.

Was ist der Unterschied zwischen flush und commit?

flush schickt das SQL in die laufende Transaktion. commit macht es dauerhaft und für andere sichtbar.

In welcher Reihenfolge schreibt Hibernate beim Flush?

Grob: INSERTs, dann UPDATEs, dann DELETEs. Das kann Unique-Constraints verletzen, wenn man löscht und neu einfügt.

Warum liefert eine Query manchmal einen alten Wert?

Ist die ID schon im Context, gibt Hibernate das vorhandene Objekt zurück und überschreibt es nicht. Frisch wird es nur mit refresh().

Was bringt @DynamicUpdate?

Das UPDATE enthält nur geänderte Spalten. Ohne sie schreibt Hibernate alle Spalten mit einem festen, cachebaren SQL.

Was bringt readOnly bei Transaktionen?

Hibernate hält keine Snapshots und macht kein Dirty Checking. Das spart Speicher und Flush-Zeit bei reinen Lese-Pfaden.

Wie verarbeiten Sie eine Million Datensätze mit Hibernate?

In Blöcken: alle N Datensätze flush() und clear(), mit passender jdbc.batch_size. Oder StatelessSession, oder ein SQL-Bulk-Update.

Was ist eine StatelessSession?

Eine Session ohne Persistence Context. Kein Cache, kein Dirty Checking, kein flush(). Jede Operation ist direkt SQL.

Was ist ein Extended Persistence Context?

Ein Context, der über mehrere Transaktionen oder Requests lebt. Er wächst, hält alte Daten und wird heute meist vermieden.

Was ist der Unterschied zwischen First- und Second-Level Cache?

First-Level gilt pro Session und ist immer an. Second-Level gilt für die ganze SessionFactory und ist optional.

Was passiert mit dem Context bei einem HQL-Bulk-UPDATE?

Das Bulk-UPDATE geht direkt zur Datenbank und umgeht den Context. Geladene Objekte sind danach veraltet, darum clear() oder refresh().

Szenario: Ein Import-Job wird nach 100 000 Datensätzen immer langsamer. Was tun Sie?

Der Context wächst, jeder Flush prüft alle Objekte. Fix: Blöcke mit flush() und clear(), JDBC-Batching, oder StatelessSession.

Szenario: Ein Test speichert erfolgreich, aber in Produktion kommt eine Constraint-Verletzung erst beim Commit. Warum?

Das SQL geht erst beim Flush raus, oft am Ende der Transaktion. Im Test fehlt der Flush. Fix: im Test flush() aufrufen, dann zeigt sich der Fehler sofort.

Szenario: Eine native Report-Query zeigt die gerade geänderte Bestellung noch mit altem Status. Warum?

Die Änderung liegt noch im Context und ist nicht geflusht. Bei Native SQL flusht Hibernate nicht verlässlich. Fix: vor der Query flush() aufrufen.
