Optimistic und Pessimistic Locking

Kern: Locking schützt gleichzeitige Transaktionen vor Lost Updates (eine Änderung überschreibt eine andere unbemerkt). Optimistic Locking sperrt nichts und prüft beim Schreiben eine @Version-Spalte; bei Konflikt kommt eine OptimisticLockException. Pessimistic Locking sperrt die Zeile schon beim Lesen mit SELECT … FOR UPDATE; andere warten. Optimistic passt zu seltenen Konflikten, pessimistic zu häufigen und teuren.

1. Wo sitzt das Locking?

  1. Optimistic: lebt in der Anwendung. Die Datenbank sieht nur eine normale Spalte und ein UPDATE mit Zusatz-Bedingung.
  2. Versionsprüfung: Hibernate hängt and version=? an jedes UPDATE und DELETE. Trifft es 0 Zeilen, hat jemand anderes geändert.
  3. Pessimistic: lebt in der Datenbank. Hibernate erzeugt eine Lock-Klausel am SELECT. Die Datenbank hält die Zeilensperre bis zum Ende der Transaktion.
  4. Unterschied: Optimistic erkennt Konflikte nachher. Pessimistic verhindert sie vorher, kostet aber Wartezeit.

2. Die Reise zweier gleichzeitiger Buchungen (die Geschichte zum Merken)

  1. Beide lesen: Zwei Benutzer öffnen dasselbe Konto. Beide sehen Saldo 100 und Version 0.
  2. A schreibt zuerst: Hibernate sendet update account set balance=80, version=1 where id=1 and version=0. Eine Zeile passt.
  3. A committet: Die Zeile hat jetzt Version 1.
  4. B schreibt: Dasselbe UPDATE mit version=0 trifft jetzt 0 Zeilen.
  5. Konflikt erkannt: Hibernate wirft OptimisticLockException (Spring: ObjectOptimisticLockingFailureException). B lädt neu und versucht es noch einmal, oder zeigt dem Benutzer den Konflikt.
  6. Pessimistic statt optimistic: B hätte beim Lesen mit PESSIMISTIC_WRITE gewartet, bis A committet. Dann liest B schon 80 und rechnet richtig.

3. Beispiel: beide Verfahren in PostgreSQL

Optimistic: das UPDATE, das Hibernate bei @Version sendet, zweimal hintereinander:

update account set balance=80, version=version+1 where id=1 and version=0;
UPDATE 1
update account set balance=70, version=version+1 where id=1 and version=0;
UPDATE 0

Echte Ausgabe, PostgreSQL 17.12.

Pessimistic: Sitzung 1 hält eine Zeilensperre (begin; select … for no key update;, dann 6 s offen). Sitzung 2 versucht dieselbe Zeile:

-- Sitzung 3 schaut zu
select pid, pg_blocking_pids(pid) as blockiert_von, wait_event_type, wait_event, query
from pg_stat_activity where datname='hib_demo' and pid<>pg_backend_pid();

-- Sitzung 2 mit Lock-Timeout
set lock_timeout = '2s';
select id, balance from account where id=1 for no key update;
ERROR:  canceling statement due to lock timeout
CONTEXT:  while locking tuple (0,4) in relation "account"
real    0m2.164s

-- NOWAIT: sofort Fehler
select id, balance from account where id=1 for no key update nowait;
ERROR:  could not obtain lock on row in relation "account"

-- SKIP LOCKED: gesperrte Zeilen überspringen
select id, owner from account order by id for no key update skip locked;
 id | owner
----+-------
  2 | Beat

Echte Ausgabe, PostgreSQL 17.12.

Warum FOR NO KEY UPDATE? Sitzung 1 sperrt einen Autor. Sitzung 2 fügt ein Buch mit Fremdschlüssel auf diesen Autor ein:

-- Sitzung 1: select id from author where id=1 for no key update;  (offen)
set lock_timeout='2s'; insert into book values (5001,'Neu',1,10);
INSERT 0 1
real    0m0.153s

-- Sitzung 1: select id from author where id=1 for update;  (offen)
set lock_timeout='2s'; insert into book values (5002,'Neu 2',1,10);
ERROR:  canceling statement due to lock timeout
CONTEXT:  while locking tuple (0,1) in relation "author"
SQL statement "SELECT 1 FROM ONLY "public"."author" x WHERE "id" OPERATOR(pg_catalog.=) $1 FOR KEY SHARE OF x"
real    0m2.203s

Echte Ausgabe, PostgreSQL 17.12.

  1. UPDATE 0 ist der Konflikt. Hibernate macht daraus die OptimisticLockException.
  2. pg_blocking_pids zeigt, wer wen blockiert. Wartende Sitzungen haben wait_event_type = Lock.
  3. lock_timeout beendet das Warten nach 2 s mit SQLSTATE 55P03. NOWAIT wirft sofort, SKIP LOCKED überspringt.
  4. Die Fremdschlüssel-Prüfung beim INSERT nimmt FOR KEY SHARE auf den Elternteil. FOR UPDATE blockiert sie, FOR NO KEY UPDATE nicht.
  5. Darum rendert Hibernate PESSIMISTIC_WRITE auf PostgreSQL als for no key update. Andere Datenbanken bekommen for update.

4. Details, die Interviewer fragen

  1. @Version-Typen (JPA): int, Integer, short, Short, long, Long, LocalDateTime, Instant, Timestamp. Zahlen sind besser als Zeitstempel: zwei Änderungen in derselben Millisekunde sind sonst gleich.
  2. Version nie selbst setzen. Hibernate setzt und erhöht sie. Für REST: Version im DTO mitschicken (oder als ETag) und beim Speichern vergleichen.
  3. LockModeType (JPA):
    • OPTIMISTIC: prüft die Version beim Commit, auch wenn das Entity nur gelesen wurde.
    • OPTIMISTIC_FORCE_INCREMENT: erhöht die Version, z. B. am Aggregat-Root, wenn sich nur ein Kind ändert.
    • PESSIMISTIC_READ: geteilte Sperre, PostgreSQL for share.
    • PESSIMISTIC_WRITE: exklusive Sperre, PostgreSQL for no key update.
    • PESSIMISTIC_FORCE_INCREMENT: Schreib-Sperre plus Versions-Erhöhung.
  4. Lock-Timeout setzen: Hint jakarta.persistence.lock.timeout in Millisekunden. 0 = NOWAIT. -2 = SKIP LOCKED (Hibernate-Wert). Seit JPA 3.2 auch typisiert: em.find(Account.class, 1L, LockModeType.PESSIMISTIC_WRITE, Timeout.ms(2000)).
  5. Timeout auf PostgreSQL ist versionsabhängig: PostgreSQL kennt kein FOR UPDATE WAIT n. Hibernate 6.6 ignoriert dort einen Zahlenwert (nur NOWAIT und SKIP LOCKED wirken). Ab Hibernate 7.1 setzt es dafür lock_timeout auf der Connection. Sicher ist immer: lock_timeout in der Datenbank oder Rolle setzen.
  6. Exceptions: SQLSTATE 55P03 wird in Hibernate 6.6 zu PessimisticLockException, in 7.x zu LockTimeoutException. Deadlock 40P01 wird LockAcquisitionException. In PostgreSQL ist die Transaktion nach dem Fehler abgebrochen. Man muss sie zurückrollen.
  7. Hibernate 7: Ein Lock auf einem detached Entity ist nicht mehr erlaubt.
  8. Ohne Versions-Spalte: @OptimisticLocking(type = DIRTY) oder ALL (Hibernate) vergleicht die alten Spaltenwerte im WHERE. Braucht @DynamicUpdate.
  9. Spring Data: @Lock(LockModeType.PESSIMISTIC_WRITE) auf der Repository-Methode, Timeout per @QueryHints.

5. Vergleich

  • Optimistic: keine Sperre, kein Warten, skaliert gut. Konflikt erst beim Schreiben, dann Retry oder Fehlermeldung. Gut bei seltenen Konflikten und langen „Benutzer-Transaktionen“ (Formular offen).
  • Pessimistic: Sperre ab dem Lesen, kein Retry nötig. Kostet Wartezeit und kann Deadlocks erzeugen. Gut bei häufigen Konflikten auf wenigen Zeilen (Kontostand, Zähler, Lager).
  • Atomares UPDATE: update account set balance = balance - 20 where id=1 and balance >= 20. Kein Lesen, kein Lock-Fenster. Oft die einfachste Lösung für Zähler.
  • SKIP LOCKED: für Job-Queues: jeder Worker holt sich ungesperrte Zeilen, keiner wartet.
  • Isolation Level SERIALIZABLE: Die Datenbank erkennt Konflikte selbst und bricht ab (SQLSTATE 40001). Auch das braucht Retry.

6. In der Produktion

  1. Lost Update ohne @Version: Zwei Sachbearbeiter speichern dasselbe Formular. Der zweite überschreibt still. Fix: @Version, Version im DTO mitschicken, Konflikt im UI anzeigen.
  2. Retry-Sturm: Viele Threads ändern dieselbe Zeile optimistisch. Fast alle scheitern und wiederholen. Fix: pessimistic Lock oder atomares UPDATE für diese Hot-Spot-Zeile. Retry mit Backoff und Limit.
  3. Threads hängen ewig: PESSIMISTIC_WRITE ohne Timeout, eine andere Transaktion bleibt offen. Fix: lock_timeout setzen, Transaktionen kurz halten, keine externen Aufrufe mit offener Sperre.
  4. Deadlocks: Transaktion A sperrt Konto 1 dann 2, B sperrt 2 dann 1. PostgreSQL bricht eine ab (40P01). Fix: immer in gleicher Reihenfolge sperren, z. B. nach ID sortiert.
  5. Retry ohne neue Transaktion: Nach einer Lock-Exception ist die PostgreSQL-Transaktion kaputt. Ein Retry in derselben Transaktion scheitert. Fix: Retry ausserhalb von @Transactional (z. B. Spring Retry um die Service-Methode).
  6. Fremdschlüssel-Inserts blockiert: Ein eigenes FOR UPDATE per Native Query auf Eltern-Zeilen bremst alle Kind-Inserts. Fix: FOR NO KEY UPDATE.

7. Diagnose: Werkzeuge und Befehle

  • select pid, pg_blocking_pids(pid), wait_event_type, wait_event, state, query from pg_stat_activity; zeigt Wartende und Blockierer.
  • select locktype, relation::regclass, mode, granted, pid from pg_locks where not granted; zeigt offene Lock-Wünsche.
  • log_lock_waits = on: PostgreSQL loggt jedes Warten länger als deadlock_timeout.
  • state = 'idle in transaction' in pg_stat_activity: offene Transaktionen, die Sperren halten. Gegenmittel: idle_in_transaction_session_timeout.
  • Hibernate: org.hibernate.SQL=DEBUG zeigt die Lock-Klausel (for no key update, nowait, skip locked).
  • Metriken: Anzahl OptimisticLockException und Retries pro Endpoint messen. Ein Anstieg zeigt einen Hot Spot.

8. Senior-Punkte

  1. Default: @Version auf jedem änderbaren Entity. Kostet fast nichts und verhindert Lost Updates.
  2. Pessimistic nur gezielt: für wenige Hot-Spot-Zeilen, immer mit Timeout, immer in kurzer Transaktion.
  3. Konflikt ist ein Fachfall. Bei Benutzer-Daten nicht automatisch wiederholen, sondern dem Benutzer zeigen. Bei technischen Zählern automatisch wiederholen.
  4. Lieber atomar als sperren. Ein UPDATE mit Bedingung oder ein atomarer Claim (UPDATE … RETURNING) braucht kein Lock-Fenster.
  5. Lock-Reihenfolge festlegen verhindert Deadlocks. Deadlocks sind ein Design-Fehler, kein Zufall.
  6. Versionsunterschiede kennen: Timeout-Verhalten und Exception-Typen haben sich zwischen Hibernate 6.6 und 7 geändert. Vor dem Upgrade testen.

9. Aus dem Projekt

„Bei MATCH holen sich Spark-Jobs ihre Nachrichten mit einem atomaren Claim (UPDATE … OUTPUT INSERTED.*, Pending → Processing) auf SQL Server, damit sich überlappende Läufe nicht doppelt verarbeiten; hängengebliebene Nachrichten setzt eine Stale-Job-Recovery nach Timeout zurück.“ (Prüfen und durch dein echtes Beispiel ersetzen. Das ist kein Hibernate-Locking, aber dasselbe Problem: konkurrierende Zugriffe ohne Lost Update.)

10. Fallen

  • „Optimistic Locking sperrt die Zeile.“ → Falsch. Es sperrt nichts. Es prüft die Version beim Schreiben.
  • „@Transactional verhindert Lost Updates.“ → Nein. In Read Committed können zwei Transaktionen dieselbe Zeile lesen und überschreiben.
  • „PESSIMISTIC_WRITE ist auf PostgreSQL immer FOR UPDATE.“ → Hibernate nutzt dort FOR NO KEY UPDATE, damit Fremdschlüssel-Inserts nicht blockieren.
  • „Der Lock-Timeout-Hint wirkt überall gleich.“ → Nein. Er ist laut JPA nur ein Hinweis. Auf PostgreSQL hängt er von der Hibernate-Version ab.
  • „Nach einer Lock-Exception einfach weitermachen.“ → In PostgreSQL ist die Transaktion danach abgebrochen. Nur Rollback und neue Transaktion helfen.

11. Fragen

Was ist ein Lost Update?

Zwei Transaktionen lesen denselben Stand und schreiben nacheinander. Die zweite überschreibt die erste, ohne es zu merken.

Wie funktioniert Optimistic Locking in Hibernate?

Mit einem @Version-Feld. Jedes UPDATE und DELETE prüft die alte Version im WHERE und erhöht sie. 0 Zeilen heisst Konflikt.

Welche Exception kommt bei einem optimistischen Konflikt?

JPA: OptimisticLockException, Hibernate nativ: StaleObjectStateException, Spring: ObjectOptimisticLockingFailureException.

Welche Typen darf @Version haben?

int, Integer, short, Short, long, Long, LocalDateTime, Instant und Timestamp. Zahlen sind sicherer als Zeitstempel.

Was macht PESSIMISTIC_WRITE in PostgreSQL?

Hibernate hängt for no key update an das SELECT. Die Zeile ist bis zum Commit für andere Schreiber gesperrt.

Warum FOR NO KEY UPDATE statt FOR UPDATE?

Die Fremdschlüssel-Prüfung bei Kind-Inserts nimmt FOR KEY SHARE. FOR UPDATE blockiert sie, FOR NO KEY UPDATE nicht.

Was ist PESSIMISTIC_READ?

Eine geteilte Sperre, in PostgreSQL for share. Andere dürfen lesen und ebenfalls teilen, aber nicht ändern.

Wann nutzen Sie OPTIMISTIC_FORCE_INCREMENT?

Wenn sich nur ein Kind ändert, aber das ganze Aggregat als geändert gelten soll. Die Version des Root steigt dann trotzdem.

Wie setzen Sie einen Lock-Timeout?

Hint jakarta.persistence.lock.timeout in ms oder seit JPA 3.2 Timeout.ms(...) als Option. Auf PostgreSQL zusätzlich lock_timeout setzen.

Was bedeuten NOWAIT und SKIP LOCKED?

NOWAIT wirft sofort einen Fehler, wenn die Zeile gesperrt ist. SKIP LOCKED überspringt gesperrte Zeilen, ideal für Job-Queues.

Wie ist der Timeout-Hint auf PostgreSQL umgesetzt?

Hibernate 6.6 kennt dort nur NOWAIT (0) und SKIP LOCKED (-2). Ab 7.1 setzt Hibernate für Zahlen lock_timeout auf der Connection.

Was ist der Unterschied zwischen LockTimeoutException und PessimisticLockException?

Laut JPA: LockTimeoutException bei Rollback nur des Statements, PessimisticLockException bei Rollback der Transaktion.

Wann wählen Sie pessimistic statt optimistic?

Bei häufigen Konflikten auf wenigen Zeilen, wo Retries teuer wären. Zum Beispiel Kontostand oder Lagerbestand.

Wie vermeiden Sie Deadlocks?

Zeilen immer in gleicher Reihenfolge sperren, Transaktionen kurz halten, Lock-Timeout setzen.

Wie geben Sie die Version über eine REST-API?

Version im DTO oder als ETag ausliefern. Beim Speichern mitschicken und vergleichen. Bei Abweichung 409 oder 412 zurückgeben.

Warum ist ein atomares UPDATE oft besser als ein Lock?

Es liest und schreibt in einem Statement. Es gibt kein Fenster zwischen Lesen und Schreiben und keine lange Sperre.

Wie finden Sie heraus, wer eine Zeile blockiert?

pg_stat_activity mit pg_blocking_pids(pid), dazu pg_locks where not granted. log_lock_waits loggt lange Wartezeiten.

Szenario: Benutzer beschweren sich, dass ihre Änderungen manchmal verschwinden. Was prüfen Sie?

Lost Updates: Fehlt @Version, oder wird die Version beim Speichern aus dem DTO ignoriert? Fix: @Version, Version mitschicken, Konflikt anzeigen.

Szenario: Unter Last steigen OptimisticLockExceptions auf einem Zähler stark an. Was tun Sie?

Der Zähler ist ein Hot Spot. Atomares UPDATE (counter = counter + 1) oder PESSIMISTIC_WRITE mit Timeout statt optimistischer Retries.

Szenario: Requests hängen minutenlang, im Thread-Dump warten sie auf JDBC. Wie gehen Sie vor?

In pg_stat_activity mit pg_blocking_pids den Blockierer finden, oft idle in transaction. Fix: Transaktion kürzen, lock_timeout und idle_in_transaction_session_timeout setzen.
