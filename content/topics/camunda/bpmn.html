BPMN-Grundlagen

Kern: BPMN ist eine Notation für Geschäftsprozesse, die Fachleute lesen und eine Engine ausführen kann. Ein Prozess besteht aus Events, Activities, Gateways und Sequence Flows. Beim Ausführen wandert ein Token durch das Diagramm.

Antwort-Muster

Frage: Was ist BPMN und wie läuft ein Prozess ab?

  1. Mechanismus: Ein Start Event erzeugt ein Token. Es folgt den Sequence Flows durch Tasks und Gateways bis zu einem End Event.
  2. Zahl: BPMN 2.0 erschien im Dezember 2010 bei der OMG. Ein Exclusive Gateway nimmt den ersten Flow in XML-Reihenfolge, dessen Bedingung stimmt.
  3. Trade-off: Ein Diagramm macht Abläufe für alle sichtbar. Zu viel Logik im Diagramm macht es aber unlesbar.
  4. Produktion: Ich setze auf jedem Gateway einen Default Flow und fange Fachfehler mit Error Events ab.

1. Ein Prozess in 7 Schritten

  1. Start Event: Eine neue Instanz entsteht. Sie bekommt ein Token.
  2. Activity: Das Token erreicht einen Task, zum Beispiel einen Service Task. Der Task läuft. Dann geht das Token weiter.
  3. Exclusive Gateway (XOR): Es prüft die Bedingungen in XML-Reihenfolge. Der erste Flow mit wahrer Bedingung gewinnt. Die übrigen Bedingungen prüft es nicht mehr.
  4. Kein Treffer: Passt keine Bedingung, nimmt das Gateway den Default Flow. Gibt es keinen, entsteht in Camunda 8 ein Incident.
  5. Parallel Gateway (AND): Beim Verzweigen nimmt es alle ausgehenden Flows. Es entstehen mehrere Tokens.
  6. AND-Join: Es wartet, bis jeder eingehende Flow genommen wurde. Erst dann geht ein Token weiter.
  7. End Event: Das Token endet. Hat die Instanz keine Tokens mehr, ist sie fertig.

2. Aufbau

  1. Events sind Ereignisse. Es gibt Start, Intermediate und End Events.
  2. Activities sind Arbeit. Ein Task ist atomar. Ein Subprocess und eine Call Activity fassen mehrere Schritte zusammen.
  3. Gateways steuern die Verzweigung. XOR wählt einen Weg. AND nimmt alle. OR nimmt alle passenden.
  4. Sequence Flows verbinden Elemente im selben Pool. Message Flows verbinden verschiedene Pools.
  5. Ein Pool ist ein Teilnehmer. Eine Lane teilt den Pool nach Rollen.
  6. Die Datei ist BPMN-XML. Das Diagramm (BPMNDI) liegt in derselben Datei, getrennt von der Logik.

3. Details

  1. Standard: BPMN 2.0 wurde im Dezember 2010 von der OMG veröffentlicht (Dokument formal/11-01-03). Die OMG-Seite nennt 2.0.1 als Nachfolger. Die Notation ist unabhängig von der Umgebung, die sie ausführt.
  2. Exclusive Gateway: Es prüft conditionExpression in XML-Reihenfolge und nimmt den ersten Treffer. Als Merge hat es Durchreiche-Semantik. Es synchronisiert nicht und führt parallele Flows nicht zusammen.
  3. Default Flow: Er hat keine Bedingung und gilt, wenn keine andere passt. Man wählt ihn in den Eigenschaften des Gateways. Eine leere Bedingung macht einen Flow nicht zum Default.
  4. Parallel Gateway: Als Split nimmt es alle ausgehenden Flows. Als Join wartet es auf alle eingehenden Flows. „Parallel“ heisst nicht eigene Threads. Alle Records einer Instanz liegen in Camunda 8 in einer Partition.
  5. Inclusive Gateway: Es verfolgt jeden Flow, dessen Bedingung stimmt. Jeder ausgehende Flow braucht eine Bedingung. Als Join wartet es, bis alle eingehenden Flows genommen sind oder kein aktiver Knoten sie mehr erreichen kann.
  6. Service Task gegen User Task: Ein Service Task ruft automatisierte Arbeit auf, etwa ein Programm. Ein User Task wartet auf einen Menschen. Dazu gibt es Send, Receive, Script, Business Rule und Manual Task.
  7. Subprocess und Call Activity: Ein Subprocess liegt eingebettet im selben Modell. Eine Call Activity ruft einen anderen Prozess auf. So nutzt man Teile wieder.
  8. Boundary Events: Sie hängen an einer Activity. Interrupting bricht die Activity ab. Non-interrupting (cancelActivity="false") lässt sie weiterlaufen und startet einen zusätzlichen Pfad.
  9. Timer Events: Es gibt Datum, Dauer und Zyklus in ISO 8601, zum Beispiel P10D oder R3/PT10H. In Camunda 8 muss ein Datum eine Zeitzone haben. In Camunda 7 gilt ohne Offset die lokale JVM-Zeitzone.
  10. Error Events: Ein BPMN-Error ist für Fachfehler, nicht für technische Exceptions. Ein Error Boundary Event fängt ihn und zerstört die Activity. Ohne errorRef fängt es jeden Error.
  11. Event-based Gateway: Es wartet auf mehrere Ereignisse. Das erste, das eintritt, bestimmt den Weg. Camunda 8 unterstützt es.
  12. Multi-Instance: Eine Activity läuft für jedes Element einer Liste. Parallel oder sequentiell. Dies ist das Gegenstück zu einer Schleife.
  13. Daten: DataObject und DataStore sind in Camunda 8 nur zum Modellieren da. Sie werden nicht ausgeführt. Daten liegen als Prozessvariablen.

4. Fallen

  • „Ein Exclusive Gateway als Merge wartet auf alle Flows.“ → Falsch. Es lässt jedes Token einzeln durch. Zum Warten braucht man ein Parallel Gateway.
  • „Parallel heisst, die Pfade laufen in eigenen Threads.“ → Falsch. Es heisst nur, dass sie unabhängig sind. Camunda 8 schreibt alle Records einer Instanz in dieselbe Partition.
  • „Ein Flow ohne Bedingung ist der Default.“ → Falsch. Den Default wählt man im Gateway aus. Eine leere Bedingung reicht nicht.
  • „Ein Error Event fängt jede Java-Exception.“ → Falsch. BPMN-Errors sind für Fachfehler. Technische Exceptions behandelt die Engine getrennt.
  • „Ein Parallel-Split mit Bedingungen filtert Pfade.“ → Falsch. Ein Parallel Gateway nimmt alle ausgehenden Flows. Für Auswahl braucht man Exclusive oder Inclusive.
  • „Ein DataObject speichert Daten im Prozess.“ → Falsch. In Camunda 8 ist es nur Modellierung. Echte Daten sind Variablen.

5. Selbsttest

Warum?

Warum nutzt man BPMN?

Fachbereich und Entwicklung lesen dasselbe Diagramm. Die Engine führt es aus. Die Dokumentation ist so immer aktuell.

Warum hat das Exclusive Gateway einen Default Flow?

Ohne Treffer sonst nirgends hin. Camunda 8 erzeugt dann einen Incident. Ein Default Flow macht den Prozess robust.

Warum trennt BPMN-XML Logik und Diagramm?

Die Engine liest nur die Logik. Das Diagramm ist für Menschen. So kann man das Layout ändern, ohne den Ablauf zu ändern.

Wie innen?

Was ist ein Token?

Ein Zeiger auf die aktuelle Position in der Instanz. Er läuft von Element zu Element. Ein Split erzeugt mehrere, ein End Event verbraucht eines.

Wie arbeitet das Exclusive Gateway?

Es prüft die Bedingungen in XML-Reihenfolge. Der erste Treffer gewinnt. Ohne Treffer folgt der Default Flow oder es entsteht ein Incident.

Wie arbeitet das Parallel Gateway?

Beim Split nimmt es alle Flows. Beim Join wartet es, bis jeder eingehende Flow genommen wurde.

Wie arbeitet das Inclusive Gateway?

Beim Split folgt es allen Flows mit wahrer Bedingung. Beim Join wartet es, bis alle eingehenden Flows genommen sind oder kein aktiver Knoten sie mehr erreichen kann.

Wie unterscheiden sich interrupting und non-interrupting Boundary Events?

Interrupting bricht die Activity ab und geht auf dem Event-Flow weiter. Non-interrupting lässt die Activity laufen und startet einen zusätzlichen Pfad.

Was ist der Unterschied zwischen Subprocess und Call Activity?

Ein Subprocess ist Teil desselben Modells. Eine Call Activity ruft einen eigenen Prozess auf, der separat deployt ist.

Wie funktioniert ein Error Boundary Event?

Es hängt an einem Subprocess oder einer Call Activity. Es fängt einen BPMN-Error mit passendem errorCode. Die Activity wird zerstört, der Fluss geht auf dem Event-Flow weiter.

Zahlen

Wann erschien BPMN 2.0?

Im Dezember 2010 bei der OMG, Dokument formal/11-01-03. Später folgte 2.0.1.

Welche Zeitformate gibt es bei Timern?

Datum, Dauer und Zyklus in ISO 8601. Beispiele sind P10D, PT15S und R5/PT10S. Zyklen kann man auch als Cron-Ausdruck schreiben.

Wie viele Bedingungen braucht ein Inclusive Gateway?

Jeder ausgehende Flow braucht eine Bedingung, ausser es gibt nur einen Flow. Ein Flow darf der Default sein und braucht dann keine.

Wie viele Tokens entstehen bei einem Parallel Split mit drei Flows?

Drei. Der Join wartet, bis alle drei angekommen sind.

Vergleich

XOR gegen AND gegen OR?

XOR wählt genau einen Weg. AND nimmt alle Wege. OR nimmt alle Wege mit wahrer Bedingung.

BPMN gegen Flussdiagramm?

BPMN hat feste Bedeutung für jedes Symbol und ist ausführbar. Ein Flussdiagramm ist nur ein Bild.

BPMN gegen Code im Service?

BPMN zeigt Ablauf, Warten und Zeit sichtbar und hält den Zustand. Code ist flexibler, aber Wartezeiten, Wiederholungen und Zustand baut man selbst.

Message Flow gegen Sequence Flow?

Ein Sequence Flow verbindet Elemente im selben Pool. Ein Message Flow verbindet verschiedene Pools.

Produktion

Warum entsteht ein Incident am Gateway?

Keine Bedingung traf zu und es gibt keinen Default Flow. Lösung: Default Flow setzen und Variablen prüfen.

Warum läuft ein Prozess nach dem Parallel-Join nie weiter?

Einer der eingehenden Flows kommt nie an. Meist wurde ein Pfad davor mit einem Exclusive Gateway verzweigt. Dann wartet der Join ewig.

Szenario: Ein Prozess hängt seit Tagen an einem Timer. Was prüfen Sie?

Das Datum und die Zeitzone. In Camunda 7 laufen Timer nur, wenn der Job Executor aktiv ist. Ohne Offset gilt die lokale Zeitzone des Servers.

Szenario: Ein Fachfehler aus einem Service soll den Prozess auf einem anderen Pfad weiterführen. Wie modellieren Sie das?

Ich werfe im Service einen BPMN-Error mit errorCode. Ein Error Boundary Event mit passendem errorRef fängt ihn. Der Flow danach führt den Alternativpfad.

Design

Wie gross darf ein Diagramm sein?

So gross, dass es auf einen Bildschirm passt. Grössere Teile gehören in Subprocesses oder Call Activities. So bleibt das Modell lesbar.

Was gehört ins Diagramm und was in Code?

Ins Diagramm gehören Reihenfolge, Warten, Zeit und Fehlerpfade. Fachregeln und Berechnungen gehören in Services oder Entscheidungstabellen.

Wie modelliert man Warten auf eine Antwort mit Timeout?

Ein Receive Task oder Message Event mit einem Timer als Boundary Event. Läuft der Timer ab, geht der Fluss auf den Timeout-Pfad.

Szenario: Eine Bestellung hat mehrere Positionen, jede muss einzeln geprüft werden. Wie modellieren Sie das?

Eine Multi-Instance Activity über die Liste der Positionen, parallel oder sequentiell. Nach dem Ende laufen die Ergebnisse zusammen weiter.

Wie benennt man Elemente?

Tasks als Verb mit Objekt, etwa „Bestellung prüfen“. Events als Zustand, etwa „Bestellung eingegangen“. Gateways als Frage, die Flows als Antwort.

Gerüst

  • Warum? Ein gemeinsames, ausführbares Bild des Ablaufs für Fachbereich und Entwicklung.
  • Wie innen? Token wandert über Sequence Flows durch Events, Activities und Gateways.
  • Zahlen BPMN 2.0 im Dezember 2010. XOR nimmt den ersten Treffer in XML-Reihenfolge.
  • Vergleich XOR, AND, OR. Subprocess gegen Call Activity. Interrupting gegen non-interrupting.

Beispiel: BPMN-XML lesen

<bpmn:process id="order" isExecutable="true">
  <bpmn:startEvent id="start"/>
  <bpmn:serviceTask id="check" name="Bestellung pruefen"/>
  <bpmn:exclusiveGateway id="xor" default="flowNormal"/>
  <bpmn:userTask id="approve" name="Manuell freigeben"/>
  <bpmn:endEvent id="end"/>
  <bpmn:sequenceFlow id="flowBig" sourceRef="xor" targetRef="approve">
    <bpmn:conditionExpression>${amount > 1000}</bpmn:conditionExpression>
  </bpmn:sequenceFlow>
  <bpmn:sequenceFlow id="flowNormal" sourceRef="xor" targetRef="end"/>
  ...
</bpmn:process>
process order executable = true
node  startEvent       id=start
node  serviceTask      id=check
node  exclusiveGateway id=xor default=flowNormal
node  userTask         id=approve
node  endEvent         id=end
flow  f1          start -> check
flow  f2          check -> xor
flow  flowBig     xor -> approve   if ${amount > 1000}
flow  flowNormal  xor -> end
flow  f5          approve -> end

Echte Ausgabe, Python 3.12.10 (xml.etree liest die Datei). Das ist kein Camunda-Lauf, es zeigt nur den Aufbau des XML.

  1. Der Prozess ist ein process-Element. isExecutable="true" sagt, dass eine Engine ihn ausführen darf.
  2. Jedes Element hat eine id. Die Flows verweisen mit sourceRef und targetRef darauf.
  3. Das Gateway nennt seinen Default Flow im Attribut default. Dieser Flow hat keine Bedingung.
  4. Nur flowBig trägt eine conditionExpression. Der Ausdruck selbst ist Sache der Engine (hier die Camunda-7-Schreibweise).

Vergleich

  • Exclusive (XOR): ein Weg, erster Treffer. Als Merge ohne Warten.
  • Parallel (AND): alle Wege. Join wartet auf alle.
  • Inclusive (OR): alle Wege mit wahrer Bedingung. Join wartet auf alle aktiven.
  • Event-based: das erste Ereignis entscheidet.
  • Subprocess: eingebettet im Modell. Call Activity: eigener Prozess.
  • Interrupting: bricht ab. Non-interrupting: zusätzlicher Pfad.

Produktion

  1. Incident am Gateway: Kein Treffer und kein Default. Lösung: Default Flow und Variablen prüfen.
  2. Join wartet ewig: Ein Pfad kommt nie an. Lösung: Verzweigung und Join passend wählen (AND mit AND).
  3. Timer feuert zur falschen Zeit: Zeitzone fehlt. Lösung: UTC oder Offset angeben.
  4. Fachfehler als Exception: Der Prozess landet im Incident. Lösung: BPMN-Error mit Error Boundary Event.
  5. Riesige Modelle: Niemand versteht sie. Lösung: Call Activities und Subprocesses.
  6. Änderungen am laufenden Prozess: Alte Instanzen laufen mit der alten Version weiter. Lösung: Migration planen.

Diagnose: Werkzeuge und Befehle

  • Modeler (Camunda Modeler oder bpmn.io): Diagramm prüfen und validieren.
  • Operate (Camunda 8) oder Cockpit (Camunda 7): zeigt Token, Variablen und Incidents.
  • BPMN-XML im Texteditor: default, sourceRef und Bedingungen prüfen.
  • Tests mit der Engine in-memory: Pfade durchspielen, Timer vorstellen.

Senior-Punkte

  1. Das Diagramm ist ein Vertrag zwischen Fachbereich und Entwicklung. Es muss lesbar bleiben.
  2. Jedes Gateway hat einen Default Flow. Das verhindert Incidents.
  3. Fachfehler sind Modell, technische Fehler sind Betrieb. Man trennt BPMN-Error und Exception.
  4. Wenig Logik in Bedingungen. Regeln gehören in Services oder Entscheidungstabellen.
  5. Versionierung planen. Laufende Instanzen bleiben auf der alten Version, bis man sie migriert.
  6. Nicht alles modellieren. Ein Prozess für drei Schritte ohne Wartezeit braucht keine Engine.
