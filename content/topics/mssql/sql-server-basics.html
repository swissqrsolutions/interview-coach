SQL Server für PostgreSQL-Entwickler

Kern: SQL Server spricht T-SQL, einen SQL-Dialekt mit Variablen, Batches und Fehlerbehandlung. Das Standard-Verhalten bei Nebenläufigkeit ist sperrenbasiert, nicht MVCC wie bei PostgreSQL. Die OUTPUT-Klausel liefert die geänderten Zeilen zurück und ersetzt dort RETURNING.

Antwort-Muster

Frage: Wie unterscheidet sich SQL Server von PostgreSQL im Alltag?

  1. Mechanismus: T-SQL schreibt Batches mit Variablen. OUTPUT gibt INSERTED und DELETED zurück, wo PostgreSQL RETURNING nutzt.
  2. Zahl: Standard ist READ COMMITTED mit Shared Locks. Mit READ_COMMITTED_SNAPSHOT ON nutzt SQL Server Row Versioning. In Azure SQL Database ist das der Standard.
  3. Trade-off: Sperren blockieren Leser, Row Versioning kostet Platz in tempdb. Dafür blockieren Leser und Schreiber sich nicht mehr.
  4. Produktion: Ich prüfe die Isolation der Datenbank, nehme THROW und XACT_ABORT ON und hole Identity-Werte per OUTPUT.

1. Ein INSERT mit OUTPUT in 7 Schritten

  1. Batch läuft: Der Client schickt einen Batch mit INSERT ... OUTPUT ....
  2. Zeilen schreiben: SQL Server schreibt die Zeilen in die Zieltabelle. Es hält dafür exklusive Locks bis zum Ende der Transaktion.
  3. Identity: Die Spalte mit IDENTITY bekommt ihren Wert. Er wird nie zurückgerollt, also entstehen Lücken.
  4. inserted füllen: Die Pseudotabelle INSERTED hat die Werte nach der Änderung. DELETED hat die Werte davor. Beide gibt es vor den Triggern.
  5. OUTPUT liefert: Ohne INTO gehen die Zeilen an den Client. Mit INTO landen sie in einer Tabellenvariable oder Tabelle.
  6. Trigger: Danach laufen die Trigger. Sie sehen schon die Änderung.
  7. Ende: COMMIT macht alles dauerhaft. Bei ROLLBACK ist alles weg. Die schon gelieferten OUTPUT-Zeilen sind dann trotzdem beim Client angekommen.

2. Aufbau

  1. Ein Batch ist eine Gruppe von T-SQL-Anweisungen, die zusammen an den Server gehen.
  2. INSERTED und DELETED sind Pseudotabellen mit den neuen und den alten Zeilen.
  3. READ_COMMITTED_SNAPSHOT ist eine Datenbank-Option. Sie ändert, wie READ COMMITTED liest.
  4. IDENTITY ist eine Spalte mit automatischem Wert. Sie entspricht grob einer PostgreSQL-Sequence.
  5. TRY...CATCH fängt Fehler. THROW gibt sie weiter.
  6. tempdb hält Row Versions. Das kostet Platz und I/O.

3. Details

  1. OUTPUT-Klausel: Sie gibt Werte aus jeder von INSERT, UPDATE, DELETE oder MERGE betroffenen Zeile zurück. Man nutzt INSERTED.spalte für den neuen Wert und DELETED.spalte für den alten. Bei INSERT geht nur INSERTED, bei DELETE nur DELETED.
  2. OUTPUT INTO: Das Ziel kann eine Tabellenvariable oder eine Tabelle sein. Die Tabelle darf keine aktiven Trigger haben und nicht an einem Fremdschlüssel teilnehmen. Ohne INTO darf das Ziel der Änderung keinen aktiven Trigger für diese Aktion haben.
  3. OUTPUT bei Fehler: Ein Befehl mit OUTPUT liefert Zeilen an den Client, auch wenn er einen Fehler hat und zurückgerollt wird. Man darf das Ergebnis bei einem Fehler nicht benutzen.
  4. OUTPUT-Reihenfolge: SQL Server garantiert keine Reihenfolge der gelieferten Zeilen. Für ein Queue-Muster braucht man ein WHERE, das die Reihenfolge festlegt. Mit READPAST überspringen konkurrierende Leser gesperrte Zeilen.
  5. $action bei MERGE: In einem MERGE gibt $action für jede Zeile INSERT, UPDATE oder DELETE zurück. Das ist nützlich für Audit und Logging.
  6. Standard-Isolation: READ COMMITTED ist der Standard. Mit READ_COMMITTED_SNAPSHOT OFF (Standard bei SQL Server) nimmt eine Abfrage Shared Locks. Sie wartet auf Zeilen, die ein anderer Schreiber geändert hat. Mit ON liest sie per Row Versioning einen konsistenten Stand vom Anweisungsstart und nimmt keine Locks.
  7. RCSI aktivieren: Beim Setzen der Option darf nur die Verbindung mit dem ALTER DATABASE in der Datenbank sein. In Azure SQL Database und in SQL database in Fabric ist die Option standardmässig an. Mit dem Hint READCOMMITTEDLOCK verlangt man trotzdem Locks.
  8. SNAPSHOT: Eine SNAPSHOT-Transaktion sieht den Stand vom Transaktionsstart. Dafür muss ALLOW_SNAPSHOT_ISOLATION an sein. Man kann nicht mitten in einer Transaktion auf SNAPSHOT wechseln. Das bricht die Transaktion ab.
  9. REPEATABLE READ und SERIALIZABLE: REPEATABLE READ hält Shared Locks bis zum Ende und lässt Phantome zu. SERIALIZABLE nimmt Range Locks und wirkt wie HOLDLOCK. Beide senken die Parallelität. Schreibende Locks gelten in jeder Stufe bis zum Ende.
  10. READ UNCOMMITTED und NOLOCK: Die Stufe liest auch nicht committete Daten (Dirty Reads). Der Hint NOLOCK wirkt wie diese Stufe für eine Tabelle. In PostgreSQL gibt es das nicht. READ UNCOMMITTED verhält sich dort wie READ COMMITTED.
  11. Fehler und Transaktionen: TRY...CATCH fängt Fehler mit Schweregrad über 10, die die Verbindung nicht schliessen. XACT_ABORT ON rollt bei einem Laufzeitfehler die ganze Transaktion zurück. Der Standard ist OFF, in Triggern ON. THROW beachtet XACT_ABORT, RAISERROR nicht. XACT_STATE() = -1 heisst, die Transaktion kann nur noch zurückgerollt werden.
  12. Identity: SCOPE_IDENTITY() gibt den letzten Wert im gleichen Scope zurück. @@IDENTITY gibt den letzten Wert der Session über alle Scopes zurück, also auch aus Triggern. Nimm SCOPE_IDENTITY oder OUTPUT.
  13. Paging: OFFSET ... FETCH braucht ORDER BY. Man kann es nicht mit TOP in derselben Abfrage mischen. Bei TOP nutzt man immer ORDER BY, sonst ist die Auswahl nicht vorhersagbar.

4. Fallen

  • „READ COMMITTED liest in SQL Server immer wie in PostgreSQL.“ → Falsch. Standardmässig nimmt SQL Server Shared Locks. Eine Abfrage kann auf einen Schreiber warten. Erst READ_COMMITTED_SNAPSHOT ON liest per Row Versioning.
  • „@@IDENTITY ist der richtige Weg für die neue ID.“ → Falsch. Es kann den Wert aus einem Trigger liefern. SCOPE_IDENTITY() oder OUTPUT INSERTED.id sind richtig.
  • „Wenn ein Befehl mit OUTPUT scheitert, hat der Client nichts bekommen.“ → Falsch. Der Client bekommt die Zeilen auch bei Fehler und Rollback. Das Ergebnis ist dann unbrauchbar.
  • „TRY...CATCH fängt jeden Fehler.“ → Falsch. Nicht Warnungen bis Schweregrad 10, nicht Fehler ab Schweregrad 20 die die Verbindung beenden, und nicht Kompilierfehler auf derselben Ebene.
  • „SET XACT_ABORT ist standardmässig an.“ → Falsch. Der Standard ist OFF. In Triggern ist er ON.
  • „NOLOCK macht Abfragen einfach schneller und sicher.“ → Falsch. Es erlaubt Dirty Reads. Zeilen können erscheinen oder verschwinden. Besser Row Versioning nutzen.

5. Selbsttest

Warum?

Warum gibt es OUTPUT?

Man braucht oft die geänderten Zeilen, zum Beispiel die neue Identity, den alten Wert oder gelöschte Daten. OUTPUT liefert sie im selben Befehl.

Warum blockieren Leser in SQL Server standardmässig?

Mit READ_COMMITTED_SNAPSHOT OFF nehmen Abfragen Shared Locks. Sie warten auf Zeilen mit exklusivem Lock.

Warum THROW statt RAISERROR?

THROW beachtet XACT_ABORT. Neue Anwendungen sollen THROW nutzen.

Wie innen?

Was sind INSERTED und DELETED?

Pseudotabellen mit den Zeilen nach und vor der Änderung. Sie sind bei OUTPUT sichtbar, bevor Trigger laufen.

Wie funktioniert READ COMMITTED mit Row Versioning?

Jede Anweisung bekommt einen konsistenten Stand vom Anweisungsstart. Locks schützen die Daten nicht vor Updates anderer.

Wie funktioniert SNAPSHOT?

Die Transaktion sieht den Stand vom Transaktionsstart. Leser und Schreiber blockieren sich nicht.

Wie arbeitet OUTPUT INTO?

Die Zeilen werden in eine Tabellenvariable oder Tabelle geschrieben, statt an den Client.

Was macht XACT_ABORT ON?

Bei einem Laufzeitfehler wird die ganze Transaktion zurückgerollt.

Was ist eine nicht committbare Transaktion?

Ein Fehler in einem TRY-Block hat sie ungültig gemacht. XACT_STATE() ist -1. Sie kann nur noch lesen oder zurückrollen.

Zahlen

Welcher Wert gilt für READ_COMMITTED_SNAPSHOT bei SQL Server und bei Azure SQL Database?

Bei SQL Server ist er OFF, bei Azure SQL Database ON.

Ab welcher Schwere fängt TRY...CATCH Fehler?

Bei Schweregrad über 10. Fehler ab 20, die die Verbindung beenden, fängt es nicht.

Seit wann gibt es OFFSET ... FETCH?

Seit SQL Server 2012.

Vergleich

OUTPUT vs RETURNING?

Beide liefern geänderte Zeilen. OUTPUT unterscheidet INSERTED und DELETED und kann in eine Tabelle schreiben. PostgreSQL RETURNING gibt die Spalten aus.

IDENTITY vs Sequence?

Beide vergeben Nummern ohne Rollback. IDENTITY gehört zur Spalte. Eine Sequence ist ein eigenes Objekt.

SQL Server READ COMMITTED vs PostgreSQL READ COMMITTED?

Beide verhindern Dirty Reads. SQL Server nutzt standardmässig Locks, PostgreSQL immer Versionen.

TOP vs OFFSET FETCH?

TOP begrenzt nur. OFFSET FETCH kann zusätzlich Zeilen überspringen. Man mischt sie nicht.

Produktion

Was tun bei blockierten Abfragen auf einer Berichtsdatenbank?

Row Versioning prüfen, also READ_COMMITTED_SNAPSHOT. Dann blockieren Leser und Schreiber sich nicht. Tempdb wird dafür grösser.

Was tun bei Lücken in Identity-Werten?

Sie sind normal, denn Rollbacks geben Werte nicht zurück. Man akzeptiert sie.

Szenario: Eine Abfrage hängt, weil ein anderer Job schreibt. Was tun Sie?

Ich prüfe Blocker und Isolation. Ich ziehe RCSI oder SNAPSHOT in Betracht und kürze die schreibende Transaktion.

Szenario: Nach einem Fehler meldet die Anwendung, die Transaktion könne nicht committet werden. Warum?

Sie ist uncommittable, XACT_STATE() = -1. Der CATCH-Block muss ROLLBACK machen.

Szenario: Mehrere Worker holen Jobs aus einer Tabelle und blockieren sich. Was tun Sie?

Ich nutze DELETE TOP (1) ... WITH (READPAST) OUTPUT DELETED.*. So überspringt jeder Worker gesperrte Zeilen.

Design

Wie holt man die neue ID sicher?

Mit OUTPUT INSERTED.id oder SCOPE_IDENTITY(). Nicht mit @@IDENTITY.

Wann nimmt man OUTPUT INTO?

Wenn man die Zeilen im selben Batch weiter nutzen will, zum Beispiel für Audit oder Folge-Inserts.

Wie schreibt man Fehlerbehandlung in T-SQL?

SET XACT_ABORT ON, BEGIN TRY mit Transaktion, im CATCH ROLLBACK und THROW.

Wie macht man Paging?

ORDER BY mit einer eindeutigen Spalte und OFFSET ... FETCH. Für stabile Seiten Snapshot oder Serializable in einer Transaktion.

Wann SERIALIZABLE?

Wenn Phantome nicht erlaubt sind. Range Locks senken die Parallelität, also nur wenn nötig.

Mehr

Gerüst

  • Warum? Gleiche relationale Ideen, anderer Dialekt, andere Standard-Mechanik.
  • Wie innen? T-SQL-Batches. OUTPUT über INSERTED und DELETED. Locks oder Row Versioning.
  • Zahlen RCSI: SQL Server OFF, Azure SQL Database ON. TRY...CATCH bei Schweregrad über 10. OFFSET FETCH seit 2012.
  • Vergleich OUTPUT gegen RETURNING. IDENTITY gegen Sequence. Locks gegen MVCC.
  • Produktion Blockierte Leser, Lücken bei Identity, uncommittable Transaktionen, NOLOCK-Fehler.
  • Design OUTPUT für IDs, THROW und XACT_ABORT, RCSI prüfen.

Beispiel: OUTPUT, RETURNING und Fehlerbehandlung

-- T-SQL: Queue-Muster mit OUTPUT
DELETE TOP (1) FROM dbo.job_queue WITH (READPAST)
OUTPUT DELETED.job_id, DELETED.payload
WHERE status = 'new';

-- T-SQL: Identity zurückholen, in eine Tabellenvariable
DECLARE @neu TABLE (id INT, name NVARCHAR(50));
INSERT dbo.kunde (name)
OUTPUT INSERTED.id, INSERTED.name INTO @neu
VALUES (N'Muster AG');
SELECT * FROM @neu;

-- T-SQL: UPDATE mit altem und neuem Wert
UPDATE dbo.konto
SET saldo = saldo - 100
OUTPUT DELETED.saldo AS alt, INSERTED.saldo AS neu
WHERE id = 1;

-- PostgreSQL: das Gleiche mit RETURNING
INSERT INTO kunde (name) VALUES ('Muster AG') RETURNING id, name;
UPDATE konto SET saldo = saldo - 100 WHERE id = 1 RETURNING saldo;

-- Fehlerbehandlung
SET XACT_ABORT ON;
BEGIN TRY
  BEGIN TRANSACTION;
  -- ... Änderungen ...
  COMMIT;
END TRY
BEGIN CATCH
  IF @@TRANCOUNT > 0 ROLLBACK;
  THROW;   -- Fehler weitergeben
END CATCH;

Nicht ausgeführt.

  1. Block 1: DELETE TOP (1) ... WITH (READPAST) OUTPUT DELETED.* nimmt einen Job aus der Queue und gibt ihn zurück. So steht es im Muster der Microsoft-Doku.
  2. Block 2: OUTPUT ... INTO @neu schreibt die Zeilen in eine Tabellenvariable statt an den Client.
  3. Block 3: DELETED.saldo ist der alte Wert und INSERTED.saldo der neue.
  4. Block 4: In PostgreSQL liefert RETURNING die geänderten Spalten.
  5. Block 5: SET XACT_ABORT ON, Transaktion im TRY, ROLLBACK und THROW im CATCH.
  6. Die Ausgabe habe ich nicht gemessen. Es lief kein SQL Server.

Vergleich

  • OUTPUT: INSERTED und DELETED, optional INTO.
  • RETURNING (PostgreSQL): gibt Spalten der geänderten Zeilen aus.
  • Locks (SQL Server Standard): Leser warten auf Schreiber.
  • Row Versioning (RCSI, SNAPSHOT): Leser lesen alte Versionen aus tempdb.
  • MVCC (PostgreSQL): immer Versionen, alte Zeilen bleiben im Heap bis VACUUM.
  • THROW: neu, beachtet XACT_ABORT. RAISERROR: älter, nicht.
  • SCOPE_IDENTITY: nur der eigene Scope. @@IDENTITY: alle Scopes der Session.
  • TOP: Begrenzung. OFFSET FETCH: Paging.

Produktion

  1. Blockierte Leser: Standard-READ-COMMITTED mit Locks. Lösung: RCSI oder SNAPSHOT, und kurze Schreib-Transaktionen.
  2. tempdb wächst: Row Versioning hält alte Versionen. Lösung: lange Transaktionen beenden und tempdb überwachen.
  3. Falsche ID nach INSERT: @@IDENTITY nahm den Wert aus einem Trigger. Lösung: SCOPE_IDENTITY() oder OUTPUT.
  4. OUTPUT mit Trigger: Ohne INTO geht es nicht, wenn die Zieltabelle einen aktiven Trigger hat. Lösung: OUTPUT INTO.
  5. Halbe Transaktion nach Fehler: XACT_ABORT ist OFF. Lösung: ON setzen oder im CATCH sauber zurückrollen.
  6. Seiten springen beim Paging: Sortierung nicht eindeutig oder Daten ändern sich. Lösung: eindeutige Sortierspalte und Snapshot.

Diagnose: Werkzeuge und Befehle

  • sys.dm_exec_requests und sys.dm_tran_locks: zeigen Blocker und Locks.
  • sp_whoisactive (Community-Tool) oder Activity Monitor: wer blockiert wen.
  • sys.databases mit is_read_committed_snapshot_on und snapshot_isolation_state: zeigt die Isolation-Optionen.
  • DBCC USEROPTIONS: zeigt Session-Optionen wie die Isolation.
  • Showplan (Execution Plan) in SSMS: zeigt Scans, Seeks und Warnungen.
  • @@TRANCOUNT und XACT_STATE(): zeigen den Zustand der Transaktion.

Senior-Punkte

  1. Standard-Isolation ist eine Datenbank-Entscheidung. Wer von PostgreSQL kommt, erwartet Versionen und bekommt Locks.
  2. OUTPUT spart Roundtrips und ist die sichere Art, an IDs zu kommen.
  3. Row Versioning hat einen Preis. Es braucht tempdb und kostet I/O. Es lohnt sich bei vielen Lesern.
  4. Fehlerbehandlung ist Pflicht: XACT_ABORT, TRY...CATCH, THROW, und XACT_STATE im CATCH.
  5. NOLOCK ist kein Tuning. Es tauscht Korrektheit gegen Tempo.
  6. Portierbarkeit planen. OUTPUT, TOP und IDENTITY haben in PostgreSQL andere Formen.
