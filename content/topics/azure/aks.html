AKS: Node Pools, Netzwerk, Identity, ACR

Kern: AKS (Azure Kubernetes Service) ist ein verwaltetes Kubernetes. Azure betreibt die Control Plane, ich betreibe die Node Pools und die Workloads. Die wichtigsten Entscheidungen sind Netzwerkmodell (CNI), Identity (Managed und Workload Identity), Image-Quelle (ACR) und Skalierung.

Antwort-Muster

Frage: Was verwaltet Azure bei AKS, und was bleibt beim Team?

  1. Mechanismus: Azure betreibt API-Server und etcd. Das Team betreibt Node Pools, Netzwerkmodell, Identity und Workloads.
  2. Zahl: AKS unterstützt 3 Minor-Versionen (N−2). Für das System-Pool empfiehlt Microsoft mindestens 3 Nodes.
  3. Trade-off: AKS gibt volle Kontrolle mit CRDs und Operatoren. Dafür braucht es Upgrades, Netz-Design und Bereitschaft.
  4. Produktion: Ich nutze Azure CNI Overlay mit Cilium und Workload Identity ohne Secrets. Upgrades laufen über einen Auto-Upgrade-Kanal mit Maintenance Window.

1. Die Reise eines Pods

  1. Ein Pod wartet. ArgoCD synchronisiert einen Spark-Job. Der Scheduler findet keinen Node mit genug CPU und Memory. Der Pod bleibt Pending.
  2. Karpenter reagiert. Karpenter sieht den Pending-Pod direkt. Er wählt eine passende VM-Grösse aus seinem NodePool und startet sie. Er braucht keine vordefinierten Node Pools je VM-Grösse.
  3. Kyverno prüft. Der Admission Controller Kyverno erlaubt nur Images aus der eigenen ACR. Er verlangt Labels und Resource Limits. Ein falscher Pod wird abgewiesen.
  4. Der Kubelet zieht das Image. Die Kubelet Identity hat die Rolle AcrPull auf der ACR. Es gibt kein imagePullSecret.
  5. Cilium vernetzt. Mit Azure CNI Overlay bekommt der Pod eine IP aus einem privaten Pod-CIDR. Cilium setzt mit eBPF die Network Policies durch: Der Pod darf nur zu MinIO, Nessie und Vault.
  6. Der Pod holt Secrets. Mit Workload Identity tauscht er sein Service-Account-Token bei Entra ID gegen ein Azure-Token. Damit liest er Key Vault. Kein Secret liegt im Repo.
  7. Der Job endet. Der Node ist leer. Karpenter konsolidiert: Er verschiebt Restpods und löscht die VM. So zahlt man Spark-Spitzen nur, solange sie laufen.

2. Aufbau

  1. Control Plane: Azure betreibt API Server, etcd und Scheduler. Ich sehe sie nicht als VMs. Im Free Tier ohne SLA, im Standard Tier mit Uptime-SLA.
  2. Node-Ressourcengruppe (MC_…): Hier legt AKS VM Scale Sets, Disks und Load Balancer an. Ich ändere dort nichts von Hand.
  3. System Node Pool: Er hostet kritische System-Pods wie CoreDNS und Cilium. Jeder Cluster braucht mindestens einen. Er ist immer Linux.
  4. User Node Pools: Sie hosten meine Anwendungen. Sie können auf 0 skalieren, Spot-VMs nutzen oder Windows sein.
  5. CNI: Das Container Network Interface gibt Pods ihre IPs und setzt Network Policies durch, z. B. Cilium.
  6. Entra ID: Login für Menschen, und über den OIDC Issuer Tokens für Pods (Workload Identity).
  7. ACR: Die Azure Container Registry liefert die Images. Der Kubelet zieht sie mit seiner Managed Identity.

3. Details, die Interviewer fragen

  1. System vs User Node Pool: Ein System Pool hostet kritische Add-ons und braucht laut Doku mindestens zwei Nodes. Microsoft empfiehlt drei. Ein User Pool hostet Apps und darf auf 0 skalieren.
  2. Node Pool = VM Scale Set: Jeder Pool ist ein VMSS mit einer VM-Grösse. Eine andere Grösse heisst neuer Pool. Mehrere Pools trennen Workloads per Taints, Labels und nodeSelector.
  3. Spot Node Pools: Spot-VMs sind stark rabattiert. Sie können aber jederzeit entzogen werden. Es gibt sie nur für User Pools. Sie sind gut für Batch wie Spark und schlecht für zustandsbehaftete Dienste.
  4. CNI Overlay: Azure CNI Overlay gibt Pods Adressen aus einem eigenen CIDR. Es spart VNet-IPs und skaliert gross. Es ist für die meisten Fälle empfohlen.
  5. CNI Pod Subnet: Azure CNI Pod Subnet gibt Pods echte VNet-IPs aus einem eigenen Subnetz. Sie sind direkt von On-Prem und gepeerten Netzen erreichbar.
  6. CNI Node Subnet und Kubenet: Azure CNI Node Subnet (legacy) legt Pods und Nodes ins gleiche Subnetz. Es verbraucht viele IPs. Kubenet (legacy) wird am 31. März 2028 eingestellt. Man migriert auf Overlay.
  7. BYO CNI: Man bringt ein eigenes CNI mit. Microsoft gibt dann keinen Support für das Netz.
  8. Azure CNI Powered by Cilium: Der Dataplane ist separat vom IPAM wählbar. Cilium nutzt eBPF statt iptables und ersetzt kube-proxy. Es setzt Network Policies durch. L7- und FQDN-Policies sowie Hubble-Observability gibt es über Advanced Container Networking Services (kostenpflichtig).
  9. Network Policy Engines: Es gibt Cilium, Calico oder Azure NPM. Azure NPM ist abgekündigt. Für neue Cluster nimmt man Cilium.
  10. Cluster Identity: Sie gehört zur Control Plane. Sie verwaltet Load Balancer, Disks und Subnetz. Sie braucht Network Contributor auf einem eigenen Subnetz.
  11. Kubelet Identity und Workload Identity: Die Kubelet Identity zieht Images aus der ACR. Die Workload Identity ist die Identität der Anwendung im Pod.
  12. Workload Identity: Sie nutzt OIDC Federation. Kubernetes signiert das Service-Account-Token. Entra ID vertraut dem OIDC Issuer des Clusters über eine Federated Identity Credential. Sie ersetzt die abgekündigte Pod-managed Identity.
  13. Entra-Integration für Menschen: Der Login läuft über Entra ID. Die Autorisierung läuft über Kubernetes RBAC mit Entra-Gruppen oder über Azure RBAC for Kubernetes. --disable-local-accounts verhindert das Admin-Kubeconfig.
  14. ACR-Integration: Die Kubelet Identity bekommt AcrPull. Private Endpoints und Geo-Replication brauchen die ACR-SKU Premium. Artifact Cache spiegelt öffentliche Images in die eigene ACR.
  15. Upgrades: Erst kommt die Control Plane, dann kommen die Node Pools. Minor-Versionen gehen nur einzeln, ohne Überspringen. AKS unterstützt 3 Minor-Versionen (N−2). LTS (2 Jahre) gibt es nur im Premium Tier.
  16. Upgrade-Mechanik: AKS erstellt Surge-Nodes. Es leert alte Nodes (cordon und drain) und löscht sie. maxSurge steuert das Tempo. Microsoft empfiehlt 33 % für Produktion. PodDisruptionBudgets werden respektiert und können ein Upgrade blockieren.
  17. Auto-Upgrade: Für Kubernetes gibt es die Kanäle none, patch, stable und rapid. Der Node OS Upgrade Channel ist separat. Er kennt NodeImage, SecurityPatch, Unmanaged und None. Planned Maintenance legt das Zeitfenster fest.
  18. Cluster Autoscaler vs Karpenter: Der Cluster Autoscaler skaliert bestehende Node Pools mit fester VM-Grösse. Karpenter wählt die VM-Grösse pro Bedarf und konsolidiert aktiv. Man nutzt nicht beide für dieselben Nodes.
  19. Node Auto Provisioning (NAP): NAP ist von AKS verwaltetes Karpenter. Man konfiguriert es mit den CRDs NodePool und AKSNodeClass. Es gibt keine Windows-Pools und keine Service Principals. Der Cluster lässt sich nicht stoppen. In AKS Automatic ist NAP vorkonfiguriert.
  20. Pricing Tiers: Free hat kein SLA und ist für Dev/Test. Standard hat ein Uptime-SLA und passt für grosse Cluster. Premium bringt zusätzlich LTS. Bezahlt werden vor allem die VMs, Disks, Load Balancer und Logs.

4. Fallen

  • „Bei AKS verwaltet Azure alles.“ → Falsch. Azure verwaltet die Control Plane. Nodes, Upgrades-Timing, Workloads und Netz-Design sind meine Aufgabe.
  • „Ein System Pool kann auf 0 skalieren.“ → Falsch. Mindestens zwei Nodes laut Doku. Nur User Pools dürfen auf 0.
  • „Kubenet ist der einfache Standard.“ → Falsch. Kubenet ist legacy und wird 2028 eingestellt. Standard ist Azure CNI Overlay.
  • „Cilium braucht man nur für Network Policies.“ → Unvollständig. Cilium ist auch der Dataplane: eBPF statt iptables, kein kube-proxy, Observability mit Hubble.
  • „Für ACR braucht jeder Pod ein imagePullSecret.“ → Falsch. Die Kubelet Identity mit AcrPull reicht.
  • „Workload Identity ist dasselbe wie Pod-managed Identity.“ → Falsch. Pod-managed Identity ist abgekündigt. Workload Identity nutzt OIDC Federation ohne NMI-DaemonSet.
  • „Man kann von 1.31 direkt auf 1.33 upgraden.“ → Falsch. Minor-Versionen nur einzeln.
  • „NAP und Cluster Autoscaler ergänzen sich auf denselben Nodes.“ → Falsch. Beide entscheiden über Nodes. Das gibt Konflikte.

5. Selbsttest

Warum?

Warum mehrere Node Pools?

Ein Pool hat eine VM-Grösse. Mehrere Pools trennen Workloads: System, Apps, Spark mit viel Memory, Spot, GPU, Windows.

Warum ist das Netzwerkmodell schwer zu ändern?

Es muss am Anfang stimmen. Default heute ist Azure CNI Overlay mit Cilium. Pod Subnet nimmt man nur bei echtem Bedarf an routbaren Pod-IPs.

Warum Workload Identity statt Secret im Pod?

Workload Identity hat keine Secrets, und die Tokens sind kurzlebig. Ein Client Secret muss rotiert werden und kann leaken.

Wie innen?

Was ist AKS?

Ein verwaltetes Kubernetes in Azure. Azure betreibt die Control Plane, ich betreibe Node Pools und Workloads.

Was bringt Azure CNI Powered by Cilium?

eBPF-Dataplane statt iptables, kein kube-proxy, Network Policy Enforcement. Mit Advanced Container Networking Services auch FQDN-/L7-Policies und Hubble.

Welche Identitäten hat ein AKS-Cluster?

Cluster Identity für Azure-Ressourcen der Control Plane, Kubelet Identity für den ACR-Pull und Workload Identities für die Apps.

Wie funktioniert Workload Identity?

Der Cluster hat einen OIDC Issuer. Eine Federated Credential sagt Entra ID, dass sie Tokens eines bestimmten Service Accounts vertraut. Der Pod tauscht sein SA-Token gegen ein Azure-Token.

Was muss im Pod gesetzt sein für Workload Identity?

Label azure.workload.identity/use: "true" und ein Service Account mit Annotation azure.workload.identity/client-id. Der Webhook setzt dann die AZURE_*-Variablen.

Wie zieht AKS Images aus der ACR?

Die Kubelet Identity bekommt AcrPull auf der ACR, z. B. per --attach-acr. Kein imagePullSecret nötig.

Wie läuft ein AKS-Upgrade ab?

Erst die Control Plane, dann die Node Pools. Pro Pool werden Surge-Nodes erstellt, alte Nodes cordoned und drained, dann gelöscht.

Was sind die Auto-Upgrade-Kanäle?

Für Kubernetes: none, patch, stable, rapid. Für das Node-OS getrennt: NodeImage, SecurityPatch, Unmanaged, None. Planned Maintenance legt das Fenster fest.

Was ist Node Auto Provisioning?

Von AKS verwaltetes Karpenter. Konfiguration über NodePool und AKSNodeClass. Grenzen: kein Windows, keine Service Principals, Cluster nicht stoppbar.

Was ist die MC_-Ressourcengruppe?

Die Node-Ressourcengruppe, die AKS verwaltet: VMSS, Disks, Load Balancer. Dort nichts von Hand ändern, sonst bricht AKS beim nächsten Update.

Zahlen

Was steuert maxSurge?

Wie viele zusätzliche Nodes beim Upgrade gleichzeitig entstehen. Höher ist schneller, braucht aber mehr IPs und Quota. Empfehlung für Produktion: 33 %.

Wie viele Kubernetes-Versionen unterstützt AKS?

Drei Minor-Versionen (N−2). Mit Premium Tier gibt es LTS mit 2 Jahren Support.

Welche Pricing Tiers hat AKS?

Free ohne SLA, Standard mit Uptime-SLA, Premium zusätzlich mit LTS. Die grössten Kosten sind aber die VMs.

Wie viele Nodes braucht ein System Pool?

Laut Doku mindestens zwei. Microsoft empfiehlt drei. Nur User Pools dürfen auf 0 skalieren.

Wann endet Kubenet?

Am 31. März 2028. Man migriert auf Azure CNI Overlay.

Vergleich

Was ist der Unterschied zwischen System und User Node Pool?

Der System Pool hostet kritische Add-ons wie CoreDNS und braucht laut Doku mindestens zwei Nodes. User Pools hosten Apps, dürfen auf 0 skalieren und Spot nutzen.

Welche CNI-Optionen gibt es in AKS?

Azure CNI Overlay, Azure CNI Pod Subnet, legacy Node Subnet, legacy Kubenet und BYO CNI. Dazu der Dataplane: Azure oder Cilium.

Overlay oder Pod Subnet?

Overlay spart VNet-IPs und skaliert weit, Pods sind von aussen nur über Services erreichbar. Pod Subnet, wenn On-Prem oder gepeerte Netze Pods direkt erreichen müssen.

Cluster Autoscaler oder Karpenter?

Der Autoscaler skaliert feste Node Pools hoch und runter. Karpenter wählt die VM-Grösse pro Pending-Pod und konsolidiert aktiv. Bei wechselnden Lasten wie Spark ist Karpenter effizienter.

Produktion

Wie senken Sie AKS-Kosten?

Requests messen und richtig setzen, Karpenter oder Autoscaler, Spot für Batch, Dev-Cluster nachts stoppen, Reservierungen oder Savings Plans für die Grundlast, Log-Volumen begrenzen.

Szenario: Nach dem Upgrade-Start hängt ein Node Pool seit einer Stunde. Was prüfen Sie?

PodDisruptionBudgets, die keinen Drain erlauben, und Single-Replica-Deployments. Dazu IP- und VM-Quota für Surge-Nodes. Events mit kubectl get events und den Upgrade-Status im Portal prüfen.

Szenario: Neue Pods hängen in ImagePullBackOff mit 401. Wie gehen Sie vor?

az aks check-acr laufen lassen. AcrPull der Kubelet Identity prüfen, dann Private DNS der ACR und ob das Image wirklich in dieser ACR liegt. Kyverno-Regeln für erlaubte Registries prüfen.

Design

Wie halten Sie App-Pods vom System Pool fern?

Mit dem Taint CriticalAddonsOnly=true:NoSchedule auf dem System Pool. System-Pods tolerieren ihn, App-Pods nicht.

Wann nutzen Sie Spot Node Pools?

Für Batch und unterbrechbare Arbeit, z. B. Spark-Executors. Nie für zustandsbehaftete oder einzelne kritische Pods.

Wann brauchen Sie ACR Premium?

Für Private Endpoints, Geo-Replication und höhere Durchsatzgrenzen. In regulierten Umgebungen mit privatem Netz ist das meist Pflicht.

Wie sichern Sie den Cluster-Zugriff für Menschen?

Entra-ID-Integration, Kubernetes RBAC mit Entra-Gruppen oder Azure RBAC, lokale Accounts deaktivieren, optional privater API Server.

Szenario: Spark-Jobs brauchen nachts 20 Nodes, tagsüber 2. Wie bauen Sie das?

Eigener User Pool oder Karpenter-NodePool für Spark, Executors auf Spot, Driver auf Regular. Karpenter oder NAP startet passende VMs und konsolidiert danach. Jobs idempotent, damit Evictions nur Zeit kosten.

Mehr

Gerüst

  • Warum? Kubernetes ohne Betrieb der Control Plane. Nodes, Upgrades und Netz-Design bleiben beim Team.
  • Wie innen? Jeder Node Pool ist ein VM Scale Set. Cilium nutzt eBPF statt iptables. Workload Identity tauscht ein Service-Account-Token gegen ein Entra-Token. Upgrade = Surge-Nodes, cordon, drain.
  • Zahlen AKS unterstützt 3 Minor-Versionen (N−2). Empfohlen: 3 System-Nodes, maxSurge 33 %. Kubenet endet am 31. März 2028.
  • Vergleich Overlay spart IPs, Pod Subnet gibt echte VNet-IPs. Cluster Autoscaler = feste VM-Grösse, Karpenter/NAP wählt sie pro Bedarf. Free, Standard, Premium (LTS).
  • Produktion Subnetz voll, PDB blockiert das Upgrade, ImagePullBackOff ohne AcrPull, AADSTS70021, Spot-Eviction.
  • Design Overlay mit Cilium als Default. Keine Secrets, eine Identität pro Workload. Cluster als Code, Upgrades als Routine.

Beispiel: Cluster mit Cilium, Workload Identity und ACR

# Cluster: Overlay + Cilium, OIDC + Workload Identity, ACR verbunden
az aks create -g rg-match -n aks-match -l switzerlandnorth \
  --tier standard \
  --network-plugin azure --network-plugin-mode overlay \
  --network-dataplane cilium --pod-cidr 192.168.0.0/16 \
  --enable-oidc-issuer --enable-workload-identity \
  --attach-acr acrmatch \
  --nodepool-name system --node-count 3 --node-vm-size Standard_D4ds_v5 \
  --nodepool-taints CriticalAddonsOnly=true:NoSchedule

# User Pool für Spark, Spot, skaliert bis 0
az aks nodepool add -g rg-match --cluster-name aks-match -n spark \
  --mode User --priority Spot --eviction-policy Delete --spot-max-price -1 \
  --enable-cluster-autoscaler --min-count 0 --max-count 10 \
  --node-vm-size Standard_E8ds_v5

az aks nodepool list -g rg-match --cluster-name aks-match \
  --query "[].{name:name, mode:mode, count:count, prio:scaleSetPriority}" -o table
Name    Mode    Count    Prio
------  ------  -------  -------
system  System  3        Regular
spark   User    0        Spot

Erwartetes Ergebnis (laut Doku, nicht ausgeführt).

  1. --network-plugin-mode overlay plus --network-dataplane cilium ergibt Azure CNI Powered by Cilium im Overlay-Modus. Pods verbrauchen keine VNet-IPs.
  2. --attach-acr vergibt AcrPull an die Kubelet Identity. Dafür braucht der Ausführende Owner- oder User-Access-Administrator-Rechte.
  3. Der System Pool hat den Taint CriticalAddonsOnly. So landen keine App-Pods darauf.
  4. Der Spot-Pool startet mit 0 Nodes. Spot-Nodes bekommen automatisch den Taint kubernetes.azure.com/scalesetpriority=spot:NoSchedule. Spark-Pods brauchen dafür eine Toleration.
  5. Die Federated Credential vertraut genau einem Service Account (system:serviceaccount:match:spark). Der Webhook von Workload Identity setzt die AZURE_*-Variablen. Das Azure SDK (DefaultAzureCredential) findet sie automatisch.

Vergleich

  • AKS vs Azure Container Apps: AKS gibt volle Kubernetes-Kontrolle (CRDs, Operatoren, Cilium, Karpenter). Container Apps ist serverless, ohne Cluster-Betrieb, aber mit weniger Kontrolle.
  • AKS Standard vs AKS Automatic: Automatic setzt Best Practices fest (NAP, Cilium, Workload Identity, Upgrades). Standard erlaubt jede Einstellung, verlangt aber mehr Betrieb.
  • Overlay vs Pod Subnet: Overlay spart IPs und skaliert weit. Pod Subnet, wenn externe Systeme Pods direkt per IP erreichen müssen.
  • Cilium vs Calico: Cilium mit eBPF, ohne kube-proxy, L7 möglich, Hubble. Calico ist reif und verbreitet, iptables oder eBPF.
  • Cluster Autoscaler vs Karpenter/NAP: Autoscaler ist einfach und vorhersagbar. Karpenter ist flexibler bei VM-Grössen und spart mehr Kosten bei wechselnder Last.
  • Workload Identity vs Secret im Pod: Workload Identity hat keine Secrets, Tokens sind kurzlebig. Ein Client Secret muss rotiert werden und kann leaken.
  • ACR vs Docker Hub: ACR ist privat, im eigenen Tenant, mit Private Endpoint und Entra-Auth. Docker Hub hat Rate Limits und liegt ausserhalb.

In der Produktion

  1. Subnetz voll: Mit Node Subnet oder Pod Subnet fehlen IPs beim Skalieren oder beim Upgrade (Surge-Nodes). Lösung: Overlay, oder Subnetz grösser planen inklusive Surge.
  2. Upgrade hängt: Ein PodDisruptionBudget mit maxUnavailable: 0 oder eine Single-Replica blockiert den Drain. Lösung: PDBs prüfen, mindestens 2 Replicas, Drain-Timeout setzen.
  3. ImagePullBackOff (401/403): Die Kubelet Identity hat kein AcrPull, oder die ACR ist privat ohne DNS. Lösung: az aks check-acr, Rolle und Private DNS Zone privatelink.azurecr.io prüfen.
  4. Workload Identity liefert 401 (AADSTS70021): Issuer, Subject oder Audience in der Federated Credential passen nicht. Oft ist Namespace oder Service-Account-Name falsch. Lösung: Subject genau vergleichen, Pod neu starten.
  5. Spot-Eviction mitten im Spark-Job: Der Node verschwindet mit 30 Sekunden Vorwarnung. Lösung: Job idempotent und neu startbar bauen, Driver auf Regular-Nodes, nur Executors auf Spot.
  6. System Pool überlastet: App-Pods laufen auf dem System Pool und verdrängen CoreDNS. Lösung: Taint CriticalAddonsOnly und eigene User Pools.
  7. SNAT-Port-Erschöpfung: Viele ausgehende Verbindungen über den Load Balancer erschöpfen die Ports. Lösung: NAT Gateway als Outbound Type, Connection Pooling.
  8. Version ausser Support: Der Cluster fällt aus dem N−2-Fenster. Dann gibt es nur noch eingeschränkten Support. Lösung: Auto-Upgrade-Kanal und Maintenance Window.

Diagnose: Werkzeuge und Befehle

  • kubectl describe pod und kubectl get events --sort-by=.lastTimestamp: Pending-Grund, Pull-Fehler, Evictions.
  • az aks check-acr -g rg -n aks --acr acrmatch.azurecr.io: prüft, ob die Nodes die ACR erreichen und sich anmelden können.
  • az aks get-upgrades, az aks nodepool get-upgrades: verfügbare Versionen und Node Images.
  • kubectl get nodepools,nodeclaims und Karpenter-Logs: warum Karpenter (oder NAP) einen Node startet oder nicht.
  • cilium status, hubble observe --verdict DROPPED: welche Verbindung eine Policy blockiert.
  • AKS Diagnose („Diagnose and solve problems“) im Portal: Netz, Identität, Upgrades.
  • Container Insights und Managed Prometheus: Node- und Pod-Metriken, ContainerLogV2, KubeEvents.
  • az aks show --query "{k8s:kubernetesVersion, tier:sku.tier, net:networkProfile}": schneller Überblick über den Cluster.

Senior-Punkte

  1. Das Netzwerkmodell ist schwer zu ändern. Es muss am Anfang stimmen. Default heute: Azure CNI Overlay mit Cilium. Pod Subnet nur bei echtem Bedarf an routbaren Pod-IPs.
  2. Keine Secrets für Azure-Zugriffe. Kubelet Identity für die ACR, Workload Identity für Apps. Eine Managed Identity pro Workload, nicht eine für alles.
  3. Cluster als Code: Terraform für Azure-Ressourcen, GitOps (ArgoCD) für alles im Cluster. Keine manuellen Änderungen, auch nicht in der MC_-Ressourcengruppe.
  4. Upgrades sind Routine, kein Projekt. Auto-Upgrade-Kanal, Maintenance Window, PDBs und mindestens 2 Replicas. Erst Dev, dann Prod.
  5. Kosten folgen den Nodes: Karpenter/NAP oder Autoscaler, Spot für Batch, richtige VM-Grössen über echte Requests. Requests ohne Messung verschwenden Geld.
  6. Guardrails im Cluster: Kyverno oder Azure Policy erzwingen ACR-only, keine privilegierten Pods, Limits. Sicherheit ist dann nicht von jedem Review abhängig.
  7. Selbst betriebenes Karpenter vs NAP: NAP spart Betrieb und Upgrades von Karpenter. Selbst betrieben gibt mehr Kontrolle über Version und Konfiguration.
