Event Grid vs Event Hub vs Service Bus

Azure · Tier 1 · Quellen: Microsoft Learn („Choose between Azure messaging services“, Event Grid delivery and retry, dead-letter, event filtering, namespaces/pull delivery, Event Hubs features/quotas/Kafka, Service Bus queues-topics-subscriptions, sessions, dead-letter queues, duplicate detection, Premium tier, private endpoints), Defender for Storage malware scan results, Azure Architecture Center (Asynchronous messaging options)

Kern: Azure hat drei Messaging-Dienste für drei Aufgaben. Event Grid verteilt einzelne Events per Push („etwas ist passiert“). Event Hubs nimmt Streams mit hohem Durchsatz auf, und Konsumenten lesen per Pull aus einem partitionierten Log. Service Bus ist ein Message Broker für wertvolle Geschäftsnachrichten mit Transaktionen, Sessions und Dead-Letter Queue.

1. Wo sitzen die drei Dienste?

  1. Event Grid: Event Grid ist ein Event-Router. Er pusht jedes Event an alle passenden Abonnenten. Beispiel: BlobCreated → Function.
  2. Event Hubs: Event Hubs ist ein Streaming-Dienst mit partitioniertem Log. Konsumenten lesen selbst und merken sich ihren Offset. Beispiel: Millionen Telemetrie-Events pro Minute.
  3. Service Bus: Service Bus ist ein Message Broker mit Queues (ein Empfänger) und Topics (viele Subscriptions). Beispiel: „Steuererklärung prüfen“ als Auftrag an einen Worker.
  4. Event vs Message: Ein Event meldet einen Fakt, und dem Sender ist egal, was passiert. Eine Message ist ein Auftrag mit Erwartung, dass jemand ihn erledigt.
  5. Push vs Pull: Event Grid pusht per HTTP. Event Hubs und Service Bus warten, bis der Konsument abholt.

2. Die Reise eines Scan-Ergebnisses (die Geschichte zum Merken)

  1. Ein Fakt entsteht. Defender for Storage hat eine Datei gescannt. Das Ergebnis ist ein Event vom Typ Microsoft.Security.MalwareScanningResult.
  2. Event Grid nimmt es an. Das Event landet in einem Event-Grid-Topic. Eine Event Subscription filtert auf diesen Typ.
  3. Event Grid pusht. Event Grid liefert per HTTP an das Ziel. Klappt es nicht, versucht er es mit exponentiellem Backoff erneut: standardmässig bis zu 30 Mal oder 24 Stunden.
  4. Endgültig fehlgeschlagen? Dann schreibt Event Grid das Event in einen Dead-Letter-Container im Blob Storage. Ohne diese Einstellung ist es weg.
  5. Event Hub speichert. Das Ziel ist ein Event Hub. Er hängt das Event an eine Partition an und hält es für die Retention-Zeit. Er löscht es nicht beim Lesen.
  6. Die Function holt ab. Eine Function liest per Pull, verarbeitet und schreibt einen Checkpoint. Bei Neustart liest sie ab dort weiter, notfalls doppelt.
  7. Warum zwei Dienste? Event Grid bringt das Event aus einer verwalteten Microsoft-Umgebung. Der Event Hub liegt privat und puffert, damit die Function im eigenen Tempo und im VNet liest.

3. Beispiel: Event Grid → Event Hub und eine Service-Bus-Queue mit Sessions

# 1) Event Hub: 4 Partitionen, 7 Tage Retention
az eventhubs namespace create -n evhns-upload-prod -g rg-upload-prod -l switzerlandnorth --sku Standard
az eventhubs eventhub create -n scan-results --namespace-name evhns-upload-prod -g rg-upload-prod \
  --partition-count 4 --cleanup-policy Delete --retention-time-in-hours 168

# 2) Event-Grid-Subscription: nur Scan-Ergebnisse, Ziel Event Hub, Dead-Letter in Blob
az eventgrid system-topic event-subscription create -n scan-to-hub \
  -g rg-upload-prod --system-topic-name st-upload-scan \
  --endpoint-type eventhub --endpoint "$EVENTHUB_ID" \
  --included-event-types Microsoft.Security.MalwareScanningResult \
  --max-delivery-attempts 30 --event-ttl 1440 \
  --deadletter-endpoint "$STORAGE_ID/blobServices/default/containers/eg-deadletter"

# 3) Service Bus: Queue mit Sessions, Duplicate Detection, DLQ nach 10 Versuchen
az servicebus namespace create -n sb-tax-prod -g rg-tax-prod -l switzerlandnorth --sku Premium
az servicebus queue create -n declarations --namespace-name sb-tax-prod -g rg-tax-prod \
  --enable-session true --requires-duplicate-detection true \
  --duplicate-detection-history-time-window PT10M \
  --max-delivery-count 10 --lock-duration PT1M --enable-dead-lettering-on-message-expiration true

  1. Die Partitionszahl legt die maximale Parallelität der Leser fest. Im Standard-Tier kann man sie später nicht ändern.
  2. Die Event-Grid-Subscription filtert auf einen Event-Typ. Andere Events gehen nicht an den Hub.
  3. --max-delivery-attempts 30 und --event-ttl 1440 (Minuten) sind die Standardwerte für Retry. Das Dead-Letter-Ziel muss man selbst setzen.
  4. Bei der Service-Bus-Queue sorgen Sessions für FIFO pro SessionId. Duplicate Detection verwirft gleiche MessageId innerhalb von 10 Minuten.
  5. Nach 10 Zustellversuchen (maxDeliveryCount) verschiebt Service Bus die Nachricht in die Dead-Letter Queue declarations/$deadletterqueue.

4. Details, die Interviewer fragen

  1. Event Grid – Topics: System Topics kommen von Azure-Diensten (Storage, Resource Groups). Custom Topics sind für eigene Events. Domains bündeln viele Topics für Multi-Tenant-Szenarien.
  2. Event Grid – Zustellung: At-least-once, keine Reihenfolge garantiert. Ziele: Webhook, Functions, Event Hubs, Service Bus, Storage Queue, Hybrid Connections.
  3. Event Grid – Retry und Dead-Letter: Exponentieller Backoff, Standard 30 Versuche oder 24 h. Danach Dead-Letter in Blob, falls konfiguriert. Bestimmte Fehler (z. B. 400, 413) werden nicht wiederholt.
  4. Event Grid – Schemas und Grösse: Event-Grid-Schema oder CloudEvents 1.0. Ein Event bis 1 MB, abgerechnet in 64-KB-Schritten.
  5. Event Grid – Webhook-Validierung: Ein Webhook muss beim Anlegen den Validation Handshake beantworten. So kann niemand fremde Endpunkte fluten.
  6. Event Grid Namespaces: Neuere Variante mit Pull Delivery (Konsument holt ab) und MQTT-Broker für IoT-Geräte.
  7. Event Hubs – Partitionen: Eine Partition ist ein geordnetes Log. Reihenfolge gilt nur innerhalb einer Partition. Gleicher Partition Key → gleiche Partition.
  8. Event Hubs – Consumer Groups: Eine Consumer Group ist eine eigene Lesesicht mit eigenen Offsets. Jede Anwendung bekommt ihre eigene.
  9. Event Hubs – Checkpointing: Der Konsument speichert seinen Offset selbst, meist im Blob Storage (EventProcessorClient). Event Hubs löscht nichts beim Lesen.
  10. Event Hubs – Kapazität: Standard: Throughput Units, 1 TU = 1 MB/s oder 1000 Events/s rein, 2 MB/s raus. Premium: Processing Units. Dedicated: Capacity Units.
  11. Event Hubs – Retention: Standard bis 7 Tage, Premium und Dedicated bis 90 Tage. Capture schreibt Events automatisch nach Blob oder ADLS (Avro/Parquet).
  12. Event Hubs – Kafka: Ab Standard spricht Event Hubs das Kafka-Protokoll. Kafka-Clients verbinden sich mit Port 9093 ohne Code-Änderung. Es ist kein echter Kafka-Cluster: kein ZooKeeper/KRaft-Zugriff, keine Kafka Streams-Infrastruktur auf Broker-Seite.
  13. Service Bus – Peek-Lock: Der Empfänger bekommt eine Nachricht mit Lock. Danach complete, abandon, deadLetter oder defer. Läuft der Lock ab, wird sie neu zugestellt.
  14. Service Bus – Receive-and-Delete: Die Nachricht ist beim Empfang gelöscht. Schneller, aber bei Absturz verloren (at-most-once).
  15. Service Bus – Sessions: Nachrichten mit gleicher SessionId gehen geordnet an genau einen Empfänger. Das ist FIFO pro Gruppe, z. B. pro Kunde.
  16. Service Bus – DLQ: Jede Queue und Subscription hat eine Dead-Letter Queue. Gründe: MaxDeliveryCount überschritten, TTL abgelaufen (falls aktiviert), Filter-Fehler oder explizites deadLetter.
  17. Service Bus – weitere Features: Duplicate Detection, Transaktionen über mehrere Entities, Scheduled Messages, Deferral, Auto-Forwarding, SQL- und Correlation-Filter auf Subscriptions.
  18. Service Bus – Tiers: Standard: geteilt, Nachrichten bis 256 KB. Premium: dedizierte Ressourcen, Nachrichten bis 100 MB, Private Endpoints, Availability Zones, Geo-Replikation.
  19. Netz: Service Bus Private Endpoints nur im Premium-Tier. Event Hubs ab Standard. Event Grid liefert an private Ziele über Managed Identity und die Ausnahme „trusted Microsoft services“.

5. Vergleich

  • Event Grid: Events (Fakten). Push per HTTP. Kein Speicher ausser Retry. Keine Reihenfolge. Ideal für reaktive Logik auf Azure-Events.
  • Event Hubs: Streams. Pull mit Offset. Retention und Replay. Reihenfolge pro Partition. Ideal für Telemetrie, Logs, Analytics, Kafka-Clients.
  • Service Bus: Messages (Aufträge). Pull mit Lock. DLQ, Sessions, Transaktionen, Duplicate Detection. Ideal für Geschäftsprozesse und Integrationen.
  • Storage Queues: sehr einfache, günstige Queue, bis 64 KB pro Nachricht, keine Sessions, keine Topics.
  • Event Hubs vs Kafka: Event Hubs ist verwaltet und spricht das Kafka-Protokoll. Eigenes Kafka gibt volle Kontrolle (Kafka Streams, Connect, Compaction-Details), kostet aber Betrieb.
  • Kombinationen sind normal: Event Grid → Service Bus für wichtige Events mit DLQ. Event Grid → Event Hub zum Puffern. Event Hub → Function oder Spark zum Verarbeiten.

6. In der Produktion

  1. Events weg nach 24 h: Das Ziel war einen Tag down, Event Grid gab auf. Lösung: Dead-Letter-Container konfigurieren und überwachen, oder an Service Bus/Event Hub liefern, die puffern.
  2. Doppelte Verarbeitung: Alle drei liefern at-least-once. Lösung: idempotente Konsumenten, Duplicate Detection bei Service Bus.
  3. Event Hub Throttling: Fehler ServerBusy, weil zu wenige TUs. Lösung: Auto-inflate aktivieren, TUs erhöhen oder Premium.
  4. Hot Partition: Ein Partition Key ist zu häufig, eine Partition hat allen Rückstand. Lösung: besseren Key wählen oder ohne Key senden, wenn Reihenfolge egal ist.
  5. DLQ läuft voll, niemand merkt es: Nachrichten liegen still in $deadletterqueue. Lösung: Alarm auf DeadletteredMessages, Prozess zum Prüfen und Resubmit.
  6. Lock verloren: Verarbeitung dauert länger als lockDuration. Die Nachricht kommt doppelt. Lösung: Lock automatisch erneuern (SDK maxAutoLockRenewDuration) oder Arbeit verkürzen.
  7. Private Endpoint bricht Event Grid: Event Hub nur privat, Event Grid kann nicht liefern. Lösung: Managed Identity für die Subscription, Rolle Azure Event Hubs Data Sender, „trusted Microsoft services“ erlauben. Oder bewusst eine dokumentierte Ausnahme.

7. Diagnose: Werkzeuge und Befehle

  • Event Grid Metriken: DeliverySuccessCount, DeliveryAttemptFailCount, DeadLetteredCount, DroppedEventCount.
  • Event Hubs Metriken: IncomingMessages, OutgoingMessages, ThrottledRequests, ServerErrors. Consumer-Lag aus Checkpoints vs letzter Sequenznummer.
  • Service Bus Metriken: ActiveMessages, DeadletteredMessages, ServerErrors, ThrottledRequests.
  • az servicebus queue show -n q --namespace-name ns -g rg --query countDetails: aktive, Dead-Letter- und geplante Nachrichten.
  • Service Bus Explorer im Portal: Nachrichten ansehen, DLQ lesen, erneut senden.
  • Diagnostic Settings → Log Analytics: Zustellfehler von Event Grid, Laufzeit-Logs von Event Hubs und Service Bus.
  • Event-Grid-Dead-Letter-Blobs: enthalten das Event plus deadLetterReason und lastHttpStatusCode.

8. Senior-Punkte

  1. Erst die Semantik, dann der Dienst. Fakt → Event Grid. Datenstrom → Event Hubs. Auftrag mit Verantwortung → Service Bus.
  2. Kein Dienst liefert exactly-once. Idempotenz liegt immer beim Konsumenten.
  3. Reihenfolge kostet Parallelität. Partitionen oder Sessions geben Reihenfolge nur pro Key. Globale Reihenfolge heisst ein Leser.
  4. Jeder Fehlerpfad braucht ein Ziel. Dead-Letter konfigurieren, überwachen und einen Resubmit-Prozess haben.
  5. Partitionen früh planen. Im Standard-Tier ist die Zahl fix. Sie begrenzt Konsumenten-Parallelität.
  6. Private Netze und Push vertragen sich schlecht. Event Grid kommt von aussen. Managed Identity und Trusted Services oder eine bewusst dokumentierte Ausnahme sind nötig.
  7. Kafka-Endpoint ist ein Migrationsweg, kein Kafka-Ersatz für alles. Kafka Streams, Connect und Compaction-Verhalten vorher prüfen.

10. Fallen

  • „Event Grid speichert Events wie eine Queue.“ → Falsch. Er hält sie nur für Retries, max. 24 h. Kein Replay.
  • „Event Hubs löscht ein Event nach dem Lesen.“ → Falsch. Es bleibt bis zum Ende der Retention. Jede Consumer Group liest selbst.
  • „Service Bus garantiert immer FIFO.“ → Falsch. Nur mit Sessions, und dann pro SessionId.
  • „Event Hubs garantiert Reihenfolge.“ → Nur pro Partition.
  • „Event Grid dead-lettert automatisch.“ → Falsch. Nur wenn ein Dead-Letter-Ziel konfiguriert ist.
  • „Service Bus Standard kann Private Endpoints.“ → Falsch. Nur Premium.
  • „Event Hubs mit Kafka-Endpoint ist ein Kafka-Cluster.“ → Falsch. Es spricht das Protokoll, ist aber ein anderer Dienst mit eigenen Grenzen.

11. Fragen

Was ist der Unterschied zwischen Event und Message?

Ein Event meldet einen Fakt, der Sender erwartet nichts. Eine Message ist ein Auftrag, und der Sender erwartet, dass jemand ihn verarbeitet.

Wann Event Grid?

Für reaktive Logik auf einzelne Events, besonders von Azure-Diensten. Push, Filter, Fan-out an viele Handler.

Wann Event Hubs?

Für hohe Datenströme wie Telemetrie oder Logs. Partitioniertes Log mit Retention, Replay und mehreren Consumer Groups.

Wann Service Bus?

Für wertvolle Geschäftsnachrichten. DLQ, Sessions, Transaktionen, Duplicate Detection, Topics mit Filtern.

Push vs Pull – wer macht was?

Event Grid pusht per HTTP. Event Hubs und Service Bus warten, bis der Konsument abholt. Pull schützt den Konsumenten vor Überlast.

Wie funktioniert Retry bei Event Grid?

Exponentieller Backoff, standardmässig bis 30 Versuche oder 24 Stunden. Danach Dead-Letter in Blob, falls konfiguriert, sonst verworfen.

Was ist eine Partition in Event Hubs?

Ein geordnetes Log. Reihenfolge gilt nur darin. Die Zahl der Partitionen begrenzt parallele Leser pro Consumer Group.

Was ist eine Consumer Group?

Eine eigene Lesesicht auf den Event Hub mit eigenen Offsets. Jede Anwendung nutzt ihre eigene.

Was ist Checkpointing?

Der Konsument speichert, bis wohin er gelesen hat, meist in Blob Storage. Nach Neustart liest er ab dort weiter.

Was ist eine Throughput Unit?

Kapazitätseinheit im Standard-Tier: 1 MB/s oder 1000 Events/s rein, 2 MB/s raus. Auto-inflate erhöht sie automatisch.

Kann Event Hubs Kafka ersetzen?

Für Produzenten und Konsumenten oft ja, über den Kafka-Endpoint ab Standard. Nicht für alles, was am Broker hängt, z. B. eigene Konfiguration oder Kafka-Betriebstools.

Peek-Lock vs Receive-and-Delete?

Peek-Lock sperrt die Nachricht, bis der Empfänger abschliesst; sicher, at-least-once. Receive-and-Delete löscht sofort; schneller, aber Verlust bei Absturz.

Was sind Service Bus Sessions?

Gruppen von Nachrichten mit gleicher SessionId. Sie gehen geordnet an genau einen Empfänger. FIFO pro Gruppe.

Wann landet eine Nachricht in der Service Bus DLQ?

Nach MaxDeliveryCount Fehlversuchen, bei abgelaufener TTL (falls aktiviert), bei Filterfehlern oder wenn der Code sie explizit dead-lettert.

Was ist Duplicate Detection?

Service Bus verwirft Nachrichten mit gleicher MessageId innerhalb eines Zeitfensters. Gut bei Sender-Retries.

Queue vs Topic in Service Bus?

Queue: ein logischer Empfänger, konkurrierende Konsumenten. Topic: viele Subscriptions, jede bekommt eine Kopie, optional mit Filter.

Welche Reihenfolge-Garantien gibt es?

Event Grid: keine. Event Hubs: pro Partition. Service Bus: mit Sessions pro SessionId.

Wie gross darf eine Nachricht sein?

Event Grid bis 1 MB. Event Hubs bis 1 MB (Standard/Premium). Service Bus Standard 256 KB, Premium bis 100 MB.

Wie machen Sie die Dienste privat?

Private Endpoints: Event Hubs ab Standard, Service Bus nur Premium. Event Grid liefert an private Ziele mit Managed Identity und Trusted Services.

Was ist Event Hubs Capture?

Automatisches Schreiben aller Events nach Blob oder ADLS in Avro oder Parquet. Gut für Archiv und Analytics.

Szenario: Ein Webhook-Ziel war einen Tag down, Events fehlen. Was ändern Sie?

Dead-Letter-Ziel in Blob konfigurieren und überwachen. Besser: Event Grid an Service Bus oder Event Hub liefern, damit gepuffert wird.

Szenario: Bestellungen eines Kunden werden in falscher Reihenfolge verarbeitet. Was tun Sie?

Service Bus Sessions mit SessionId = Kunden-ID, oder Event Hubs mit Partition Key = Kunden-ID. Konsument idempotent halten.

Szenario: Alles ist hinter Private Endpoints, aber das Defender-Ergebnis kommt nicht an. Wo suchen Sie?

Bei der Zustellung von Event Grid an den Event Hub: Managed Identity, Rolle Data Sender, Trusted Services. Dann Event-Grid-Metriken und Dead-Letter prüfen.
