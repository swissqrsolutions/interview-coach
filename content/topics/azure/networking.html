VNet, Subnetze, NSG, Private Endpoints, Private DNS

Kern: Ein Virtual Network (VNet) ist ein privates, isoliertes Netz in einer Azure-Region. Es löst das Problem, Dienste ohne Internet miteinander sprechen zu lassen. Private Endpoints holen PaaS-Dienste mit einer privaten IP ins VNet, und Private DNS sorgt dafür, dass ihr Name auf diese IP zeigt.

Antwort-Muster

Frage: Wie machen Sie einen Azure-Dienst nur privat erreichbar?

  1. Mechanismus: Ein Private Endpoint ist eine NIC mit privater IP im VNet. Eine Private DNS Zone lässt den normalen Namen auf diese IP zeigen.
  2. Zahl: Azure reserviert 5 IPs pro Subnetz. Ein /29 hat also nur 3 nutzbare Adressen.
  3. Trade-off: Ein Private Endpoint kostet pro Stunde und pro GB, ein Service Endpoint ist gratis. Dafür hat der Service Endpoint keine private IP.
  4. Produktion: Ich schalte Public Network Access ab und verlinke die Zone mit dem VNet. Bei Fehlern prüfe ich zuerst, ob der Name auf die private IP zeigt.

1. Die Reise eines Requests zum Private Endpoint

  1. Start: Die Function ruft stdemo.blob.core.windows.net auf. Der Code ist gleich wie ohne Private Endpoint. Nur DNS und Routing ändern sich.
  2. DNS-Frage: Die Anfrage geht an Azure DNS unter der virtuellen IP 168.63.129.16. Das ist der Standard-Resolver jedes VNets.
  3. CNAME: Das öffentliche DNS antwortet mit einem CNAME auf stdemo.privatelink.blob.core.windows.net. Diesen CNAME setzt Azure beim Anlegen des Private Endpoints.
  4. Private Zone: Ist die Zone privatelink.blob.core.windows.net mit dem VNet verlinkt, antwortet sie mit 10.20.1.4. Ohne Link kommt die öffentliche IP zurück.
  5. Route und NSG: Mit VNet Integration geht der ausgehende Verkehr der Function ins Integration-Subnetz. Dort gelten NSG und Routen (UDR).
  6. Private Endpoint: Das Paket erreicht die NIC des Private Endpoints. Private Link leitet es über das Microsoft-Backbone zum einen Storage Account weiter.
  7. Prüfung: Der Dienst akzeptiert den Verkehr über den PE, auch wenn Public Network Access aus ist. Danach prüft er Token und RBAC-Rolle.

2. Aufbau

  1. VNet: ein Adressraum (z. B. 10.20.0.0/16) in einer Region und Subscription. Ohne Peering spricht es mit keinem anderen VNet.
  2. Subnetz: ein Teil des Adressraums für eine Art von Ressource. Beispiel: snet-pe nur für Private Endpoints.
  3. Delegiertes Subnetz: ein Subnetz, das einem Dienst gehört. Beispiel: Microsoft.Web/serverFarms für App Service und Functions Premium.
  4. NSG (Network Security Group): eine Firewall-Regelliste auf Subnetz oder Netzwerkkarte.
  5. Private Endpoint (PE): eine Netzwerkkarte mit privater IP, die auf genau einen Dienst zeigt. Beispiel: Blob-Endpoint eines Storage Accounts.
  6. Private DNS Zone: eine DNS-Zone, die nur in verlinkten VNets gilt. Sie enthält die A-Records der Private Endpoints.

3. Details, die Interviewer fragen

  1. Reservierte IPs: Azure reserviert in jedem Subnetz 5 Adressen. Das sind die ersten vier und die letzte. Ein /29 hat also nur 3 nutzbare IPs.
  2. Adressplanung: VNets, die man peeren will, dürfen sich nicht überschneiden. Das gilt auch für On-Premises-Netze.
  3. NSG-Regeln: Jede Regel hat eine Priorität (100-4096, kleiner zuerst). Dazu kommen Richtung, Quelle, Ziel, Port, Protokoll und Allow/Deny. Die erste passende Regel gewinnt.
  4. Default-Regeln: Sie erlauben Verkehr im VNet und vom Load Balancer. Sie erlauben ausgehend ins Internet und verbieten den Rest (Priorität 65000-65500). Man überstimmt sie nur mit höherer Priorität.
  5. Stateful: Eine NSG merkt sich Verbindungen. Die Antwort auf eine erlaubte Anfrage braucht keine eigene Regel.
  6. Service Tags und ASGs: Service Tags sind von Microsoft gepflegte IP-Gruppen, z. B. Storage.SwitzerlandNorth oder AzureKeyVault. Application Security Groups gruppieren eigene NICs nach Rolle.
  7. NSG auf Subnetz und NIC: Beide werden geprüft. Eingehend kommt erst das Subnetz, dann die NIC. Ausgehend ist es umgekehrt.
  8. Private Endpoint: Er ist eine NIC mit privater IP, die auf eine Ressource und Sub-Resource zeigt. Verkehr geht nur hinein in den Dienst. Der Dienst baut keine Verbindungen ins VNet auf.
  9. PE und NSG/UDR: Auf PE-Subnetzen sind Network Policies standardmässig aus. Mit privateEndpointNetworkPolicies: Enabled wirken NSG und UDR auch auf PEs.
  10. Service Endpoint: Er schaltet auf Subnetz-Ebene einen optimierten Weg zum öffentlichen Endpoint eines Dienstes. Der Dienst sieht die private Quell-IP. Er erlaubt das Subnetz in seiner Firewall.
  11. Service Endpoint Grenzen: Es gibt keine private IP. On-Premises kann ihn nicht nutzen. Er gilt für den ganzen Dienst-Typ. Gegen Daten-Abfluss braucht es Service Endpoint Policies.
  12. Private DNS Zone: Sie gilt nur in VNets mit Virtual Network Link. Auto-Registration trägt nur VMs ein, keine Private Endpoints.
  13. Zonen-Namen: Blob nutzt privatelink.blob.core.windows.net. Key Vault nutzt privatelink.vaultcore.azure.net. Event Hub nutzt privatelink.servicebus.windows.net. Functions und App Service nutzen privatelink.azurewebsites.net.
  14. On-Premises DNS: On-Prem-Server kennen die Private Zones nicht. Die Lösung ist ein Azure DNS Private Resolver mit Inbound Endpoint und Conditional Forwarder.
  15. VNet Integration (Functions/App Service): Sie wirkt nur ausgehend. Sie braucht ein eigenes, delegiertes Subnetz. Eingehend privat geht nur über einen Private Endpoint auf die App.
  16. Delegation je Plan: Flex Consumption nutzt Microsoft.App/environments und min. /27. Elastic Premium und Dedicated nutzen Microsoft.Web/serverFarms und min. /28. Empfohlen ist /26 (Linux). Der klassische Consumption-Plan hat keine VNet Integration.
  17. Route All: Linux-Apps (ausser Flex Consumption) müssen vnetRouteAllEnabled setzen. Sonst geht nur privater Verkehr (RFC 1918) ins VNet.
  18. Functions-Storage hinter PE: AzureWebJobsStorage braucht PEs für blob, queue und table. Mit Azure-Files-Content-Share braucht es zusätzlich file.
  19. Hub-Spoke: Ein Hub-VNet hält gemeinsame Dienste wie Azure Firewall, VPN/ExpressRoute Gateway und DNS Resolver. Spokes sind die Workload-VNets. Sie peeren mit dem Hub.
  20. Peering ist nicht transitiv: Spoke A erreicht Spoke B nicht über den Hub. Dafür braucht es eine UDR auf die Firewall im Hub oder Virtual WAN.
  21. Kosten: Private Endpoints kosten pro Stunde und pro GB. Service Endpoints sind gratis.

4. Fallen

  • „Ein Private Endpoint sperrt den öffentlichen Zugang.“ → Falsch. Public Network Access muss man extra abschalten.
  • „Service Endpoint und Private Endpoint sind dasselbe.“ → Falsch. SE nutzt die öffentliche IP des Dienstes, PE eine private IP im VNet.
  • „VNet Integration macht die Function privat erreichbar.“ → Falsch. Sie wirkt nur ausgehend. Eingehend braucht es einen Private Endpoint.
  • „Peering ist transitiv.“ → Falsch. Spoke zu Spoke braucht Routing über eine Firewall oder Virtual WAN.
  • „Im Code muss ich die privatelink-URL eintragen.“ → Falsch. Die normale URL bleibt. DNS löst sie auf die private IP auf.
  • „Auto-Registration trägt Private Endpoints ein.“ → Falsch. Nur VMs. PEs brauchen eine DNS Zone Group oder Policy.
  • „Ein /29 reicht für 8 Ressourcen.“ → Falsch. Azure reserviert 5 IPs, es bleiben 3.

5. Selbsttest

Warum?

Ist VNet Peering transitiv?

Nein. Spoke-zu-Spoke-Verkehr braucht eine UDR auf eine Firewall oder NVA im Hub, oder Virtual WAN.

Warum reicht ein Private Endpoint allein nicht?

Er sperrt den öffentlichen Zugang nicht. Public Network Access muss man extra abschalten.

Warum ist DNS der schwierige Teil?

Der normale Name muss auf die private IP zeigen. Dafür braucht es Zonen mit Link, Forwarder für On-Prem und Records per Zone Group oder Policy.

Wie innen?

Was ist ein VNet?

Ein privates, isoliertes Netz in einer Region mit eigenem Adressraum. Es verbindet Azure-Ressourcen ohne Internet.

Was ist eine NSG?

Eine stateful Regelliste auf Subnetz oder NIC. Regeln nach Priorität, die erste passende gewinnt.

Welche Default-Regeln hat eine NSG?

VNet-intern erlaubt, Load Balancer eingehend erlaubt, Internet ausgehend erlaubt, alles andere verboten.

Was sind Service Tags?

Von Microsoft gepflegte IP-Gruppen für Dienste, z. B. Storage oder AzureKeyVault. Man nutzt sie statt fester IPs in NSG-Regeln.

Was ist ein Private Endpoint?

Eine NIC mit privater IP im eigenen Subnetz, die über Private Link auf eine bestimmte Ressource zeigt.

Wie funktioniert DNS mit Private Endpoints?

Der öffentliche Name zeigt per CNAME auf privatelink.*. Eine verlinkte Private DNS Zone löst diesen auf die private IP auf.

Was ist 168.63.129.16?

Die virtuelle IP von Azure DNS und Plattform-Diensten. Eigene DNS-Server sollten Azure-Zonen dorthin weiterleiten.

Was ist eine DNS Zone Group?

Eine Verknüpfung des Private Endpoints mit einer Private DNS Zone. Sie legt A-Records automatisch an und löscht sie wieder.

Was ist VNet Integration bei Functions?

Ausgehender Verkehr der App läuft über ein delegiertes Subnetz ins VNet. Sie macht die App nicht privat erreichbar.

Was macht vnetRouteAllEnabled?

Es schickt allen ausgehenden Verkehr ins VNet, nicht nur private Ziele. Dann gelten NSG, UDR, Firewall und NAT Gateway.

Wirken NSGs auf Private Endpoints?

Nur wenn Network Policies im PE-Subnetz aktiviert sind. Standardmässig nicht.

Zahlen

Wie viele IPs reserviert Azure pro Subnetz?

Fünf: die ersten vier und die letzte Adresse.

Welche Pläne unterstützen VNet Integration?

Flex Consumption, Elastic Premium und Dedicated. Der klassische Consumption-Plan nicht.

Welche Priorität haben NSG-Regeln?

Zwischen 100 und 4096, kleiner zuerst. Die Default-Regeln liegen bei 65000 bis 65500.

Wie gross muss das Subnetz für Flex Consumption sein?

Mindestens /27, mit der Delegation Microsoft.App/environments. Elastic Premium und Dedicated brauchen min. /28.

Vergleich

Private Endpoint vs Service Endpoint?

PE: private IP, pro Ressource, auch von On-Prem, kostet. SE: öffentlicher Endpoint über Backbone, pro Subnetz, gratis, nicht von On-Prem.

NSG vs Azure Firewall?

NSG: L3/L4 pro Subnetz, gratis. Azure Firewall: zentral, FQDN- und Applikationsregeln, Threat Intelligence, Logging.

VNet Integration vs Private Endpoint auf die App?

Integration = ausgehend von der App ins VNet. Private Endpoint = eingehend ins VNet zur App.

VNet Peering vs VPN Gateway?

Peering verbindet VNets direkt über das Backbone, schnell. VPN verbindet über verschlüsselte Tunnel, auch zu On-Prem.

Produktion

Was braucht der Functions-Storage hinter einem PE?

PEs für blob, queue und table, bei Azure-Files-Content-Share auch file, plus VNet Integration der App.

Wie prüfen Sie, ob eine NSG ein Paket blockiert?

Network Watcher IP Flow Verify und Effective Security Rules. Dazu VNet Flow Logs.

Szenario: Nach Umstellung auf Private Endpoint bekommt die Function 403 vom Storage. Was prüfen Sie?

Zuerst DNS aus der App: kommt die private IP? Dann Zone-Link, Zone Group, VNet Integration mit Route All und die NSG.

Szenario: Zwei Spokes können nicht miteinander sprechen, beide sind mit dem Hub gepeert. Warum?

Peering ist nicht transitiv. Lösung: UDR in beiden Spokes auf die Hub-Firewall und Firewall-Regeln, oder direktes Peering.

Design

Wie lösen On-Prem-Clients Private Endpoints auf?

Über Azure DNS Private Resolver mit Inbound Endpoint und einen Conditional Forwarder für die privatelink-Zonen.

Wie mache ich eine Function nur privat erreichbar?

Private Endpoint auf die App (privatelink.azurewebsites.net) und Public Network Access auf der App abschalten.

Was ist Hub-Spoke?

Ein zentrales Hub-VNet mit Firewall, Gateway und DNS, verbunden per Peering mit Workload-VNets (Spokes).

Szenario: Ein Dienst kann sein Event nur über einen öffentlichen Endpoint zustellen. Wie gehen Sie vor?

Bewusste Ausnahme für genau diesen Dienst. Mit Entra-Auth oder Managed Identity absichern, Zugriff loggen und die Ausnahme dokumentieren.

Gerüst

  • Warum? Dienste sprechen ohne Internet miteinander. Netzwerk allein ist aber keine Autorisierung.
  • Wie innen? Ein Private Endpoint ist eine NIC mit privater IP. Private DNS lässt den normalen Namen auf diese IP zeigen. VNet Integration wirkt nur ausgehend.
  • Zahlen Azure reserviert 5 IPs pro Subnetz, ein /29 hat 3 nutzbare. NSG-Priorität 100 bis 4096. Flex Consumption braucht min. /27.
  • Vergleich Private Endpoint = private IP, auch von On-Prem nutzbar. Service Endpoint = öffentlicher Endpoint über das Backbone, gratis. NSG filtert L3/L4, Firewall zentral.
  • Produktion DNS löst öffentlich auf, Subnetz zu klein, Peering nicht transitiv, NSG blockiert den Load Balancer.
  • Design Private Endpoint plus Public Access aus. DNS-Zonen zentral im Hub. Adressraum früh planen.

Beispiel: Private Endpoint mit DNS in Bicep

// pe-storage.bicep
resource zone 'Microsoft.Network/privateDnsZones@2020-06-01' = {
  name: 'privatelink.blob.core.windows.net'
  location: 'global'
}
resource link 'Microsoft.Network/privateDnsZones/virtualNetworkLinks@2020-06-01' = {
  parent: zone
  name: 'link-vnet-app'
  location: 'global'
  properties: { virtualNetwork: { id: vnet.id }, registrationEnabled: false }
}
resource pe 'Microsoft.Network/privateEndpoints@2023-11-01' = {
  name: 'pe-stdemo-blob'
  location: 'switzerlandnorth'
  properties: {
    subnet: { id: peSubnet.id }
    privateLinkServiceConnections: [ {
      name: 'blob'
      properties: { privateLinkServiceId: st.id, groupIds: [ 'blob' ] }   // Sub-Resource
    } ]
  }
}
resource dnsGroup 'Microsoft.Network/privateEndpoints/privateDnsZoneGroups@2023-11-01' = {
  parent: pe
  name: 'default'
  properties: { privateDnsZoneConfigs: [ { name: 'blob', properties: { privateDnsZoneId: zone.id } } ] }
}
# aus dem VNet (z. B. Kudu-Konsole der Function)
$ nslookup stdemo.blob.core.windows.net
Non-authoritative answer:
Name:    stdemo.privatelink.blob.core.windows.net
Address: 10.20.1.4
Aliases: stdemo.blob.core.windows.net

# vom Laptop im Internet
$ nslookup stdemo.blob.core.windows.net
Name:    <öffentlicher Storage-Cluster-Name>
Address: 20.<…>            # öffentliche IP, Zugriff aber gesperrt (Public Access aus)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Hier gibt es keine Azure CLI und keinen Account.

  1. groupIds: ['blob'] wählt die Sub-Resource. Für dfs, queue, table und file braucht es je einen eigenen PE.
  2. Die DNS Zone Group legt den A-Record automatisch an und löscht ihn mit dem PE. Ohne sie pflegt man Records von Hand.
  3. Von innen zeigt der Name auf 10.20.1.4. Von aussen auf die öffentliche IP. Der gleiche Name, zwei Antworten: Split-Horizon DNS.
  4. Der PE allein sperrt nichts. Erst publicNetworkAccess: 'Disabled' auf dem Storage Account schliesst den öffentlichen Weg.

Vergleich

  • Private Endpoint vs Service Endpoint: PE gibt dem Dienst eine private IP im VNet, auch von On-Prem nutzbar, pro Ressource. SE nutzt den öffentlichen Endpoint über das Backbone, pro Subnetz und Dienst-Typ, gratis.
  • NSG vs Azure Firewall: NSG filtert L3/L4 pro Subnetz, gratis. Azure Firewall ist zentral, stateful, mit FQDN-Regeln, TLS-Inspektion (Premium) und Logs.
  • VNet Integration vs Private Endpoint auf die App: Integration = ausgehend von der App ins VNet. PE = eingehend ins VNet zur App.
  • VNet Peering vs VPN Gateway: Peering verbindet VNets direkt über das Backbone, schnell. VPN verbindet über verschlüsselte Tunnel, auch zu On-Prem.
  • Hub-Spoke vs Virtual WAN: Hub-Spoke baut man selbst und kontrolliert alles. Virtual WAN ist ein verwalteter Hub mit transitivem Routing.
  • Azure vs Kubernetes: NSG ≈ NetworkPolicy auf Netzwerk-Ebene. Cilium-Policies wirken im Cluster, NSGs auf Subnetz und NIC.

In der Produktion

  1. DNS löst öffentlich auf: Die Zone ist nicht mit dem VNet verlinkt, oder ein eigener DNS-Server leitet nicht an 168.63.129.16 weiter. Symptom: 403 oder Timeout. Lösung: Zone verlinken, Forwarder prüfen.
  2. Doppelte Zonen: Zwei Teams legen je eine Zone privatelink.blob… an. Records fehlen in der jeweils anderen. Lösung: eine zentrale Zone im Hub, Records per Azure Policy.
  3. Subnetz zu klein: Die Function skaliert nicht, weil IPs fehlen. Lösung: Subnetz gross genug planen. Eine Integration lässt sich nicht einfach vergrössern.
  4. Route All vergessen: Die Linux-Function erreicht ein öffentliches Ziel nicht über NAT Gateway oder Firewall. Lösung: vnetRouteAllEnabled=true.
  5. Subnetz blockiert: App gelöscht, ohne die Integration zu lösen. Die Delegation bleibt, das Subnetz lässt sich nicht löschen. Lösung: Integration vorher entfernen.
  6. NSG blockiert den Load Balancer: Eine „Deny All“-Regel mit hoher Priorität blockiert Health Probes. Lösung: AzureLoadBalancer erlauben.
  7. Plattform-Dienst braucht Public: Manche Integrationen gehen nicht privat, z. B. Event-Grid-Zustellung von Defender-Ergebnissen. Lösung: bewusste, dokumentierte Ausnahme mit Auth und Monitoring.

Diagnose: Werkzeuge und Befehle

  • nslookup / nameresolver aus der Kudu-Konsole oder einem Pod: zeigt, ob die private IP kommt.
  • tcpping <host>:443 (App Service Kudu) oder nc -vz: prüft TCP-Erreichbarkeit.
  • Network Watcher – IP Flow Verify: sagt, welche NSG-Regel ein Paket erlaubt oder blockiert.
  • Effective Security Rules und Effective Routes einer NIC: az network nic list-effective-nsg, az network nic show-effective-route-table.
  • Connection Troubleshoot: testet den ganzen Weg von Quelle zu Ziel.
  • VNet Flow Logs mit Traffic Analytics: wer spricht mit wem. NSG Flow Logs werden abgelöst.
  • az network private-endpoint dns-zone-group list und az network private-dns record-set a list: fehlen Records?
  • Diagnose-Detektoren der Function App unter „Diagnose and solve problems“ (Netzwerk- und Key-Vault-Detektoren).

Senior-Punkte

  1. DNS ist der schwierige Teil, nicht der Private Endpoint. Zonen zentral, Records automatisch per Zone Group oder Policy.
  2. Private Endpoint plus Public Access aus. Sonst ist es nur ein zusätzlicher Weg, kein geschlossener.
  3. Ausnahmen bewusst entscheiden: Nicht jeder Dienst kann privat sein. Ausnahme dokumentieren, mit Identität absichern, überwachen.
  4. Adressraum früh planen: keine Überschneidungen mit anderen VNets und On-Prem, Subnetze mit Reserve für Skalierung.
  5. Defense in Depth: Netzwerk (PE, NSG) und Identität (Managed Identity, RBAC) zusammen. Netzwerk allein ist keine Autorisierung.
  6. Hub-Spoke ab mehreren Workloads: zentrale Firewall, DNS und Egress. Für ein einzelnes Projekt reicht oft ein VNet.
