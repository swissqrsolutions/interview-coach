Key Vault: Secrets, Keys, Zertifikate

Azure · Tier 1 · Quellen: Microsoft Learn – About Azure Key Vault, Azure RBAC vs access policies, Prepare for Key Vault API version 2026-02-01, Soft-delete overview, Use Key Vault references as app settings, Use the Azure Key Vault provider for Secrets Store CSI Driver in AKS, Configure key auto-rotation, Azure Key Vault service limits, Key Vault private link; External Secrets Operator docs

Kern: Azure Key Vault ist ein verwalteter Dienst für Secrets, kryptografische Keys und Zertifikate. Er löst das Problem, dass Passwörter und private Schlüssel in Code, Config oder Pipelines landen. Zugriff läuft über Entra ID und RBAC, jeder Zugriff wird geloggt, und gelöschte Objekte bleiben durch Soft Delete wiederherstellbar.

1. Wo sitzt Key Vault?

  1. Clients: Function und App Service lesen Secrets über Key Vault References. AKS-Pods über den CSI Driver oder den External Secrets Operator. Eigener Code über das SDK.
  2. Netzwerk: Der Vault ist über einen Private Endpoint erreichbar (Zone privatelink.vaultcore.azure.net). Public Network Access ist aus.
  3. Auth: Jeder Aufruf braucht ein Entra-Token. Azure RBAC prüft dann die Data-Rolle.
  4. Objekte: Secrets (beliebige Strings), Keys (RSA, EC) und Zertifikate (X.509 mit Key und Secret).
  5. Schutz: Jede Änderung ist eine neue Version. Gelöschtes bleibt durch Soft Delete erhalten.
  6. Betrieb: Events gehen an Event Grid, Zugriffe als AuditEvent an Log Analytics.

2. Die Reise eines Secrets (die Geschichte zum Merken)

  1. Anlegen: Die Pipeline schreibt db-password mit Ablaufdatum. Key Vault speichert es als Version v1. Die Pipeline hat dafür Key Vault Secrets Officer.
  2. App-Start: Die App-Setting DB_PASSWORD=@Microsoft.KeyVault(VaultName=kv-app-prod;SecretName=db-password) zeigt auf das Secret ohne Version. Die Plattform holt es mit der Managed Identity der App (Rolle Key Vault Secrets User).
  3. Cache: App Service und Functions cachen den Wert. Ohne Version holen sie spätestens nach 24 Stunden die neueste Version.
  4. Ablauf naht: 30 Tage vor dem Ablaufdatum sendet Key Vault Microsoft.KeyVault.SecretNearExpiry an Event Grid.
  5. Rotation: Eine Rotations-Function setzt ein neues Passwort in der Datenbank und speichert es als Version v2. Die alte Version bleibt lesbar.
  6. App lädt neu: Eine Config-Änderung startet die App neu und lädt sofort. Oder ein POST auf config/configreferences/appsettings/refresh. Sonst innerhalb von 24 Stunden.
  7. Löschen: Ein Delete markiert das Secret nur als gelöscht (Soft Delete). Der Name bleibt in der Frist reserviert.
  8. Purge: Erst ein Purge löscht endgültig. Mit Purge Protection geht das vor Fristende gar nicht, auch nicht für Owner.

3. Beispiel: Vault mit RBAC, Purge Protection und Reference

# Vault: RBAC-Modell, Purge Protection, kein Public Access
az keyvault create -g rg-app -n kv-app-prod -l switzerlandnorth \
  --enable-rbac-authorization true --enable-purge-protection true \
  --retention-days 90 --public-network-access Disabled

# Rolle nur für die Managed Identity der Function, nur auf diesen Vault
az role assignment create --assignee <functionPrincipalId> \
  --role "Key Vault Secrets User" --scope $(az keyvault show -n kv-app-prod --query id -o tsv)

# Secret mit Ablaufdatum
az keyvault secret set --vault-name kv-app-prod -n db-password \
  --value "$NEW_PW" --expires 2027-05-24T00:00:00Z

# Function-App-Setting als Reference
az functionapp config appsettings set -g rg-app -n func-upload \
  --settings "DB_PASSWORD=@Microsoft.KeyVault(VaultName=kv-app-prod;SecretName=db-password)"
$ az keyvault show -n kv-app-prod --query "properties.{rbac:enableRbacAuthorization, softDelete:enableSoftDelete, purge:enablePurgeProtection, days:softDeleteRetentionInDays, net:publicNetworkAccess}"
{ "rbac": true, "softDelete": true, "purge": true, "days": 90, "net": "Disabled" }

$ az keyvault secret show --vault-name kv-app-prod -n db-password --query "{id:id, exp:attributes.expires}"
{ "id": "https://kv-app-prod.vault.azure.net/secrets/db-password/<version-guid>",
  "exp": "2027-05-24T00:00:00+00:00" }

$ az keyvault key show --vault-name kv-app-prod -n jwt-signing --query "key.{kid:kid, kty:kty, n:n, e:e}"
{ "kid": "https://kv-app-prod.vault.azure.net/keys/jwt-signing/<version>", "kty": "RSA",
  "n": "<Base64URL-Modulus>", "e": "AQAB" }

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Hier gibt es keine Azure CLI und keinen Account. Die az-Befehle selbst brauchen wegen --public-network-access Disabled einen Weg ins VNet.

  1. --enable-rbac-authorization true wählt das RBAC-Modell. Ab API-Version 2026-02-01 ist RBAC für neue Vaults ohnehin der Standard.
  2. --enable-purge-protection true ist nicht umkehrbar. Customer-Managed Keys für Storage und andere Dienste verlangen sie.
  3. Die id enthält die Version. Eine Reference ohne Version folgt immer der neuesten.
  4. key show gibt nur den öffentlichen Teil zurück (n, e). Der private Schlüssel verlässt den Vault nie. Damit kann eine App RS256-JWTs lokal prüfen.

4. Details, die Interviewer fragen

  1. Secret: ein beliebiger String bis 25 KB, z. B. Passwort oder Connection String. Key Vault interpretiert ihn nicht.
  2. Key: ein RSA- oder EC-Schlüssel für sign/verify, encrypt/decrypt, wrapKey/unwrapKey. Die Operation läuft im Vault, der private Teil ist nicht exportierbar.
  3. Zertifikat: Key Vault legt dabei einen Key und ein Secret an. Das Secret enthält das Zertifikat mit privatem Schlüssel als PFX oder PEM, wenn der Key exportierbar ist.
  4. Zertifikats-Erneuerung: Mit integrierten CAs (DigiCert, GlobalSign) erneuert Key Vault automatisch. Eine Lifetime Action legt fest, wann: z. B. bei 80 % der Laufzeit.
  5. Standard vs Premium: Premium bietet HSM-geschützte Keys. Managed HSM ist ein eigener Dienst mit Single-Tenant-HSM-Pool und FIPS 140-3 Level 3.
  6. Versionen: Jedes Update erzeugt eine neue Version. Die URI ohne Version zeigt auf die aktuelle. Alte Versionen kann man deaktivieren.
  7. RBAC vs Access Policies: RBAC ist empfohlen und ab API 2026-02-01 Standard für neue Vaults. Access Policies sind das alte, Vault-lokale Modell.
  8. Risiko Access Policies: Wer Microsoft.KeyVault/vaults/write hat (z. B. Contributor), kann sich selbst eine Access Policy geben. Mit RBAC dürfen nur Owner und User Access Administrator Rechte vergeben.
  9. RBAC-Rollen: Key Vault Administrator, Secrets Officer, Secrets User (nur lesen), Crypto Officer, Crypto User, Crypto Service Encryption User, Certificates Officer, Reader (nur Metadaten).
  10. Scope: Rollen gehen auf den Vault oder sogar auf ein einzelnes Secret. Access Policies kennen nur den ganzen Vault.
  11. Soft Delete: immer an. Frist 7–90 Tage, Standard 90. Gelöschte Objekte und Vaults kann man wiederherstellen (recover).
  12. Purge Protection: verhindert endgültiges Löschen vor Fristende. Einmal an, nie wieder aus.
  13. Key Vault References: @Microsoft.KeyVault(SecretUri=…) oder @Microsoft.KeyVault(VaultName=…;SecretName=…). Standard ist die System-Assigned MI. Mit keyVaultReferenceIdentity eine User-Assigned MI.
  14. Reference und Netzwerk: Hinter Private Endpoint braucht die App VNet Integration. Linux-Apps (ausser Flex Consumption) brauchen vnetRouteAllEnabled.
  15. Reference nicht auflösbar: Dann steht in der Variable der Text @Microsoft.KeyVault(...) selbst. Die App startet, scheitert aber später.
  16. CSI Driver (AKS): Das Add-on azure-keyvault-secrets-provider mountet Secrets als Dateien. Eine SecretProviderClass beschreibt Vault, Objekte und Identität.
  17. CSI Rotation: Mit --enable-secret-rotation pollt der Driver regelmässig (Standard 2 Minuten). Die App muss die Datei neu lesen. Env-Vars aus einem gesyncten K8s Secret ändern sich erst nach Pod-Neustart.
  18. External Secrets Operator: synchronisiert Secrets mit refreshInterval in Kubernetes Secrets. Gut für GitOps, weil nur die ExternalSecret-Definition im Repo liegt.
  19. Key Rotation Policy: Keys können sich automatisch rotieren, z. B. alle 90 Tage. Für Secrets gibt es das nicht. Dafür nimmt man Event Grid und eine Function.
  20. Dual-Credential-Pattern: zwei gültige Credentials (z. B. Storage key1 und key2). Man rotiert immer das gerade unbenutzte. So gibt es keine Ausfallzeit.
  21. Throttling: Key Vault hat Limits pro Vault und Region in 10-Sekunden-Fenstern. Bei Überschreiten kommt 429. Lösung: Werte cachen, Backoff, nicht pro Request lesen.
  22. Netzwerk: Firewall mit IP-Regeln oder Private Endpoint. Die Option „Trusted Microsoft services“ lässt bestimmte Azure-Dienste trotz Firewall durch.
  23. Ein Vault pro App und Umgebung: Das empfiehlt Microsoft. Es begrenzt Schaden und Throttling und hält Rechte einfach.

5. Vergleich

  • Key Vault vs App Settings: App Settings sind verschlüsselt gespeichert, aber ohne Versionen, Rotation und Audit pro Zugriff.
  • Key Vault vs HashiCorp Vault: Azure Key Vault ist verwaltet und Azure-integriert. HashiCorp Vault kann dynamische Secrets (z. B. kurzlebige DB-User) und läuft überall.
  • Key Vault Standard vs Premium vs Managed HSM: Software-Keys, HSM-Keys im Mehrmandanten-Pool, eigener HSM-Pool mit voller Kontrolle.
  • CSI Driver vs External Secrets Operator: CSI mountet Dateien direkt im Pod, Secrets liegen nicht zwingend in etcd. ESO erzeugt K8s Secrets, einfacher für Apps und GitOps, aber Secrets liegen in etcd.
  • Key Vault Reference vs SDK im Code: Reference = keine Code-Änderung, bis 24 h Verzögerung. SDK = sofort aktuell, aber eigener Code und Cache nötig.
  • Secret vs Key für JWT: Key = Signatur im Vault, privater Teil bleibt drin. Secret mit PEM = App hat den privaten Schlüssel im Speicher.

6. In der Produktion

  1. Vault-Name blockiert: Vault gelöscht und neu deployt, Fehler „vault name already in use“. Grund: Soft Delete. Lösung: az keyvault recover oder anderer Name. Mit Purge Protection gibt es kein Purge.
  2. App nutzt altes Passwort: Rotation in der DB gemacht, App hat noch den gecachten Wert. Lösung: Dual-Credential-Pattern, Refresh-API oder Restart nach Rotation.
  3. 429 unter Last: Die App liest das Secret bei jedem Request. Lösung: einmal laden und cachen, oder Reference/CSI nutzen.
  4. Reference hinter PE scheitert: Route All fehlt oder DNS zeigt öffentlich. Im Log erscheint zuerst ein 403 von der öffentlichen IP. Laut Doku ist das normal, wenn danach ein erfolgreicher privater Zugriff folgt.
  5. Abgelaufenes Zertifikat: Niemand hat auf das Ablaufdatum geachtet. Lösung: Auto-Renew mit integrierter CA, Alert auf CertificateNearExpiry.
  6. Contributor mit Secret-Zugriff: Bei Access Policies gibt sich ein Contributor Lesezugriff. Lösung: auf RBAC migrieren.
  7. Signing-Key rotiert, alte Tokens ungültig: Die App kennt nur die neueste Key-Version. Lösung: kid im JWT-Header nutzen und alte Versionen während der Token-Lebenszeit akzeptieren.

7. Diagnose: Werkzeuge und Befehle

  • Diagnostic Settings mit Kategorie AuditEvent → Log Analytics: jeder Zugriff mit Identität, Operation und Ergebnis.
  • KQL: AzureDiagnostics | where ResourceProvider == "MICROSOFT.KEYVAULT" and httpStatusCode_d == 403 | project TimeGenerated, OperationName, identity_claim_oid_g, CallerIPAddress
  • Metriken: ServiceApiHit, ServiceApiLatency, Availability, SaturationShoebox (Auslastung gegenüber dem Limit).
  • az keyvault secret list-deleted, az keyvault list-deleted: was liegt im Soft-Delete.
  • Portal-Status der Reference: App Settings → Reference öffnen zeigt Auflösungsstatus und Fehler.
  • Detektor „Key Vault Application Settings Diagnostics“ unter „Diagnose and solve problems“.
  • AKS: kubectl describe pod (Mount-Fehler), Logs von secrets-store-csi-driver und secrets-store-provider-azure; bei ESO kubectl get externalsecret (Status SecretSynced).

8. Senior-Punkte

  1. RBAC statt Access Policies. Rechte-Vergabe nur durch Owner und User Access Administrator, PIM für Menschen.
  2. Purge Protection in Produktion an. Preis: Namen bleiben bis zu 90 Tage blockiert. In Test-Umgebungen bewusst entscheiden.
  3. Lesen und Rotieren trennen: Apps bekommen Secrets User, nur die Pipeline oder Rotations-Function Secrets Officer.
  4. Rotation planen, nicht nur speichern: Ablaufdatum, Event, Dual Credential, Cache-Verhalten der Clients.
  5. Am besten gar kein Secret: Managed Identity statt Connection String. Key Vault nur für das, was nicht per Entra geht.
  6. Keys im Vault nutzen, statt sie zu exportieren. Signieren im Vault, prüfen mit dem öffentlichen Schlüssel lokal.

10. Fallen

  • „Ein gelöschter Vault ist weg, der Name ist frei.“ → Falsch. Soft Delete hält ihn bis zu 90 Tage.
  • „Purge Protection kann ich später abschalten.“ → Falsch. Einmal an, immer an.
  • „Key Vault References aktualisieren sich sofort.“ → Falsch. Bis zu 24 Stunden, ausser bei Restart oder Refresh-API.
  • „Mit Reader auf dem Vault kann ich Secrets lesen.“ → Falsch. Reader sieht nur Metadaten. Lesen braucht Secrets User.
  • „Key Vault rotiert meine Secrets automatisch.“ → Falsch. Auto-Rotation gibt es für Keys und Zertifikate. Secrets rotiert man selbst.
  • „Ich lade den privaten Key aus dem Vault zum Signieren.“ → Falsch. Ein Key ist nicht exportierbar. Man ruft die sign-Operation auf.
  • „CSI-Rotation aktualisiert auch Env-Vars.“ → Falsch. Nur die gemounteten Dateien. Env-Vars brauchen einen Pod-Neustart.

11. Fragen

Was ist Azure Key Vault?

Ein verwalteter Dienst für Secrets, Keys und Zertifikate mit Entra-Auth, RBAC, Versionen, Soft Delete und Audit-Logs.

Secret vs Key vs Zertifikat?

Secret: beliebiger String. Key: RSA/EC-Schlüssel, Operationen im Vault. Zertifikat: X.509 mit zugehörigem Key und Secret plus Erneuerung.

RBAC oder Access Policies?

RBAC. Zentral, granular bis zum einzelnen Secret, mit PIM. Ab API 2026-02-01 Standard für neue Vaults.

Warum sind Access Policies riskant?

Wer vaults/write hat, z. B. Contributor, kann sich selbst Datenzugriff geben.

Welche Rolle braucht eine App, die nur Secrets liest?

Key Vault Secrets User, am besten nur auf diesem Vault oder Secret.

Was ist Soft Delete?

Gelöschte Vaults und Objekte bleiben 7–90 Tage wiederherstellbar. Es ist immer aktiv.

Was ist Purge Protection?

Sie verhindert endgültiges Löschen vor Ablauf der Frist. Nicht umkehrbar. Pflicht für viele Customer-Managed-Key-Szenarien.

Wie sieht eine Key Vault Reference aus?

@Microsoft.KeyVault(SecretUri=https://…/secrets/name) oder @Microsoft.KeyVault(VaultName=…;SecretName=…).

Wann sieht die App einen rotierten Secret-Wert?

Ohne Version spätestens nach 24 Stunden. Sofort nach Config-Änderung, Restart oder Refresh-API.

Welche Identität nutzt eine Reference?

Standard die System-Assigned MI. Mit keyVaultReferenceIdentity eine User-Assigned MI.

Was braucht eine Reference auf einen Vault hinter Private Endpoint?

VNet Integration, private DNS und bei Linux-Apps ausser Flex Consumption vnetRouteAllEnabled.

Wie kommen Secrets in AKS-Pods?

Mit dem Secrets Store CSI Driver als Dateien, oder mit dem External Secrets Operator als K8s Secrets. Identität jeweils über Workload Identity.

CSI Driver vs External Secrets Operator?

CSI: Dateien im Pod, nicht zwingend in etcd. ESO: K8s Secrets, einfacher für Apps und GitOps, aber in etcd.

Wie rotiert man Secrets?

Ablaufdatum setzen, SecretNearExpiry über Event Grid, Function erzeugt neue Version. Mit zwei Credentials ohne Ausfall.

Was ist das Dual-Credential-Pattern?

Zwei gültige Credentials. Man rotiert immer das nicht aktive und schaltet dann um.

Wie validiert man ein JWT mit Key Vault?

Signieren mit einem Key im Vault. Prüfen lokal mit dem öffentlichen Schlüssel, den man aus dem Vault liest und cacht. Der kid zeigt die Version.

Kann man den privaten Schlüssel eines Keys exportieren?

Nein. Signieren und Entschlüsseln laufen im Vault. Nur bei Zertifikaten mit exportierbarem Key liegt der private Teil im Secret.

Was passiert bei zu vielen Requests?

Key Vault antwortet mit 429. Lösung: cachen, Backoff, Last auf mehrere Vaults verteilen.

Standard vs Premium vs Managed HSM?

Standard: Software-Keys. Premium: HSM-Keys. Managed HSM: eigener Single-Tenant-HSM-Pool mit voller Kontrolle.

Wie sichern Sie Key Vault im Netzwerk ab?

Private Endpoint mit privatelink.vaultcore.azure.net und Public Network Access aus. Alternativ Firewall mit IP-Regeln.

Wie überwachen Sie Key Vault?

AuditEvent-Logs in Log Analytics, Metriken für Latenz und Sättigung, Alerts auf 403 und auf Near-Expiry-Events.

Szenario: Nach einer Passwort-Rotation fällt die App für Stunden aus. Warum, und wie verhindern Sie das?

Die App nutzt den gecachten alten Wert bis zu 24 Stunden. Lösung: Dual Credential, Refresh nach Rotation oder Restart, oder das SDK mit kurzem Cache.

Szenario: Das Terraform-Deployment scheitert mit "vault name already in use". Was ist los?

Der alte Vault liegt im Soft Delete. Wiederherstellen mit recover oder anderen Namen nehmen. Mit Purge Protection kein vorzeitiges Purge.

Szenario: Eine Function zeigt in der Variable den Text "@Microsoft.KeyVault(...)". Was prüfen Sie?

Die Reference wurde nicht aufgelöst. Im Portal den Status prüfen: Rolle der Identität, Syntax, Secret vorhanden, Netzwerk mit Route All und DNS.
