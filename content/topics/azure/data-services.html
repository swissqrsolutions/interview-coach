Daten-Services: ADF, Synapse, Fabric, Databricks

Kern: Azure Data Factory (ADF) orchestriert und kopiert Daten. Synapse bündelt SQL Pools, Spark und Pipelines in einem Workspace. Fabric ist die SaaS-Plattform mit OneLake, und Databricks ist eine Spark-Plattform für Lakehouse mit Delta Lake.

Antwort-Muster

Frage: Wann nimmst du ADF, Synapse, Fabric oder Databricks?

  1. Mechanismus: ADF bewegt und steuert Daten mit Pipelines. Synapse und Databricks rechnen mit SQL oder Spark. Fabric legt alles in OneLake im Delta-Format ab.
  2. Zahl: Eine ADF-Pipeline hat standardmässig höchstens 120 Activities. Fabric-Kapazität gibt es als F-SKU, abgerechnet pro Sekunde mit einer Minute Minimum.
  3. Trade-off: ADF ist einfach, rechnet aber wenig selbst. Databricks gibt volle Spark-Kontrolle und braucht mehr Betrieb. Fabric ist einfach, aber an eine Kapazität gebunden.
  4. Produktion: Ich nehme ADF zum Laden und Steuern. Gerechnet wird in Databricks oder Fabric, und Wiederholung (Retry) und Alerts sind Pflicht.

1. Ein Pipeline-Lauf in ADF

  1. Trigger: Ein Trigger startet die Pipeline. Er kann einen Zeitplan haben oder auf ein Ereignis reagieren.
  2. Run: ADF erzeugt einen Pipeline Run mit einer Run-ID. Parameter werden übergeben.
  3. Activities: Die Activities laufen nach ihren Abhängigkeiten. Bei Erfolg, Fehler oder Abschluss folgt die nächste.
  4. Linked Service: Er hält die Verbindung zu einem Speicher oder Dienst. Das Dataset beschreibt Tabelle, Datei oder Ordner darin.
  5. Integration Runtime (IR): Sie ist die Rechenumgebung. Sie führt Copy aus oder startet Data Flows und ruft Compute auf.
  6. Ergebnis: Daten landen im Ziel (Sink). Der Status wird in Monitor gespeichert. Bei Fehlern greift Retry, danach der Alert.

2. Aufbau

  1. ADF ist der Orchestrator. Er hat Pipelines, Triggers, Linked Services, Datasets und Integration Runtimes.
  2. Synapse Workspace hat Dedicated SQL Pool, Serverless SQL Pool, Spark Pool, Pipelines und Data Explorer.
  3. Fabric ist SaaS. Workloads sind Data Factory, Data Engineering, Data Warehouse, Real-Time Intelligence und Power BI.
  4. OneLake ist der eine Speicher für alle Fabric-Workloads. Er baut auf ADLS Gen2 auf.
  5. Databricks bietet Spark-Cluster, SQL Warehouses, Notebooks, Delta Lake und Unity Catalog.
  6. Speicher ist bei ADF, Synapse und Databricks meist ADLS Gen2. Fabric nutzt OneLake.

3. Details

  1. Pipeline und Activity: Eine Pipeline gruppiert Activities zu einer Aufgabe. Es gibt Bewegungs-, Transformations- und Kontroll-Activities. Standardmässig sind 120 Activities pro Pipeline erlaubt, inklusive innerer.
  2. Retry: Pro Activity ist der Standard 0 Wiederholungen. Du stellst Retry und Timeout in der Policy ein. Ohne Retry scheitert ein kurzer Netzfehler sofort.
  3. Integration Runtime: Es gibt drei Arten. Die Azure IR läuft in Azure und ist standardmässig AutoResolve. Die Self-hosted IR steht hinter deiner Firewall und baut nur ausgehende HTTP-Verbindungen auf. Die Azure-SSIS IR führt SSIS-Pakete aus.
  4. Managed Virtual Network: Die Azure IR kann dann Private Link nutzen. Ohne sie läuft der Verkehr über öffentliche Endpunkte.
  5. Schedule vs Tumbling Window: Schedule Trigger folgt der Uhr und kennt kein Backfill und kein Retry. Tumbling Window hat feste, lückenlose Zeitfenster. Es unterstützt Backfill und Retry, und eine Pipeline gehört zu genau einem Trigger.
  6. Event Trigger: Er startet bei einer Datei im Blob Storage oder bei einem Custom Event über Event Grid. So lädst du Daten sofort bei Ankunft.
  7. Mapping Data Flows: Sie sind visuelle Transformationen. Sie laufen als Activity auf Spark-Clustern, die ADF verwaltet. Du schreibst keinen Code.
  8. Synapse Serverless SQL: Du bezahlst nur für verarbeitete Daten, nicht für reservierte Ressourcen. Pro Abfrage zählt auf ganze MB aufgerundet, mindestens 10 MB.
  9. Synapse Dedicated SQL Pool: Die Grösse wird in DWU gemessen. Er ist ein Data Warehouse mit reservierter Leistung.
  10. Fabric-Kapazität: Ein F-SKU gibt Compute-Einheiten (CU). F2 hat 2 CU, F64 hat 64 CU. Azure rechnet pro Sekunde ab, mit einer Minute Minimum, ohne Bindung.
  11. OneLake und Shortcuts: Ein Shortcut zeigt auf Daten in ADLS, S3 oder GCS, ohne zu kopieren. Mirroring spiegelt eine operative Datenbank fast in Echtzeit in OneLake.
  12. Databricks: Es ist ein Lakehouse auf Spark. Unity Catalog regelt Zugriff und Governance. Delta Lake liefert Tabellen mit Transaktionen.

4. Fallen

  • „ADF ist ein ETL-Tool, das alles selbst rechnet.“ → Falsch. ADF orchestriert und kopiert. Gerechnet wird in Data Flows (Spark), Databricks, SQL oder anderen Diensten.
  • „Eine Self-hosted IR braucht eingehende Ports.“ → Falsch. Sie baut nur ausgehende HTTP-Verbindungen auf.
  • „Tumbling Window ist nur ein Schedule mit anderem Namen.“ → Falsch. Es hat feste, lückenlose Fenster, Backfill und Retry. Es startet nur eine Pipeline.
  • „Serverless SQL ist immer billiger als ein Dedicated Pool.“ → Falsch. Er rechnet pro verarbeiteter Datenmenge. Teure Abfragen auf grosse Dateien kosten viel.
  • „Fabric ersetzt Databricks einfach.“ → Falsch. Beide überschneiden sich, haben aber andere Modelle. Fabric ist SaaS mit Kapazität, Databricks ist eine eigene Spark-Plattform.
  • „Ein Activity-Fehler wiederholt sich von selbst.“ → Falsch. Der Standard für Retry ist 0. Du musst Retry setzen.

5. Selbsttest

Warum?

Warum nutzt man ADF und nicht ein eigenes Skript?

ADF bringt Trigger, Retry, Monitoring und fertige Konnektoren mit. Du betreibst keinen Server für den Zeitplan.

Warum braucht man eine Self-hosted Integration Runtime?

Wenn eine Datenquelle im privaten Netz liegt und die Cloud sie nicht direkt sieht. Die IR steht dort und verbindet nur nach aussen.

Warum Delta Lake statt reiner Parquet-Dateien?

Delta legt ein Transaktionslog über Parquet. So gibt es ACID-Schreibvorgänge und Time Travel.

Wie innen?

Wie arbeitet eine ADF-Pipeline intern?

Ein Trigger erzeugt einen Run. Activities laufen nach Abhängigkeiten. Eine Integration Runtime führt die Arbeit aus. Status steht in Monitor.

Was ist der Unterschied zwischen Linked Service und Dataset?

Der Linked Service ist die Verbindung zum Dienst. Das Dataset zeigt auf die Daten darin, etwa eine Tabelle oder einen Ordner.

Wie läuft ein Mapping Data Flow?

Er läuft als Activity auf einem von ADF verwalteten Spark-Cluster. ADF übersetzt die visuelle Logik in Code.

Was ist OneLake?

Der zentrale logische Data Lake von Fabric auf ADLS Gen2. Alle Workloads schreiben und lesen dort. Das Format ist Delta.

Wie liest Serverless SQL Daten?

Es fragt Dateien im Data Lake direkt per T-SQL ab. Es gibt keine eigenen Knoten, die du betreibst.

Zahlen

Wie viele Activities passen in eine Pipeline?

Standardmässig höchstens 120, inklusive innerer Activities in Containern. Es ist ein Soft Limit.

Wie viele Retries gelten standardmässig?

Keine. Der Standard für Retry ist 0.

Wie rechnet Fabric ab?

Mit F-SKU pro Sekunde, mindestens eine Minute. Es gibt eine optionale Jahresreservierung. F64 hat 64 Compute-Einheiten.

Was kostet eine kleine Serverless-Abfrage mindestens?

10 MB verarbeitete Daten. Die Menge wird pro Abfrage auf ganze MB aufgerundet.

Vergleich

ADF vs Fabric Data Factory?

Beide haben Pipelines. Fabric ergänzt Dataflow Gen2, Copy job und Mirroring und schreibt direkt nach OneLake.

Synapse vs Fabric?

Synapse ist ein PaaS-Workspace mit eigenen Pools. Fabric ist SaaS mit OneLake und Kapazität. Für dedizierte SQL Pools gibt es einen Migration Assistant.

Databricks vs Synapse Spark?

Databricks bietet Unity Catalog, SQL Warehouses und mehr Spark-Kontrolle. Synapse Spark ist im Workspace eingebaut.

Schedule Trigger vs Tumbling Window?

Schedule folgt der Uhr, ohne Backfill und Retry. Tumbling Window hat feste Fenster mit Backfill und Retry, aber nur eine Pipeline.

Dedicated vs Serverless SQL Pool?

Dedicated hat reservierte DWU für ein Warehouse. Serverless rechnet pro Datenmenge und fragt Lake-Dateien ab.

Produktion

Wie macht man Pipelines robust?

Retry und Timeout pro Activity setzen. Idempotente Ziele nutzen, damit ein Neustart keine Duplikate erzeugt. Alerts auf Fehler einrichten.

Wie lädt man nur neue Daten?

Mit einem Watermark (letzter Zeitstempel) oder einem Tumbling Window pro Zeitfenster. Das Fenster liefert die Grenzen als Parameter.

Wie überwacht man Pipelines?

Mit ADF Monitor und Azure Monitor Alerts auf fehlgeschlagene Runs. Fehler leitet man an eine Action Group.

Szenario: Der nächtliche Load ist ausgefallen, und niemand hat es bemerkt. Was tun Sie?

Eine Alert Rule auf fehlgeschlagene Pipeline Runs einrichten. Den Lauf mit Tumbling-Window-Backfill nachholen. Retry für kurze Fehler setzen.

Szenario: Die Self-hosted IR ist offline, und alle Loads stehen. Wie reagieren Sie?

Auf die IR-Maschine prüfen, Dienst starten. Für die Zukunft mehrere Knoten für Hochverfügbarkeit nutzen und Alerts auf den IR-Status setzen.

Design

Wann wählen Sie Databricks?

Bei komplexen Spark-Jobs, ML und wenn Sie Unity Catalog als Governance wollen. Sie nehmen dafür mehr Betrieb in Kauf.

Wann wählen Sie Fabric?

Wenn ein Team schnell eine integrierte Plattform mit Power BI und OneLake will. Sie planen dann die Kapazität.

Wann reicht Serverless SQL?

Für gelegentliche Abfragen auf Dateien im Lake. Für dauernde, schwere Last ist ein Dedicated Pool oder ein anderes Warehouse planbarer.

Szenario: Ein Team will Daten aus S3 und ADLS zusammen auswerten, ohne zu kopieren. Was empfehlen Sie?

Fabric mit OneLake Shortcuts. Ein Shortcut zeigt zero-copy auf S3 und ADLS. Beachten Sie Egress-Kosten und die Kapazität.

Mehr

Gerüst

  • Warum? Daten laden, steuern und auswerten, ohne eigene Server für den Ablauf.
  • Wie innen? ADF hat Trigger, Pipeline, Activities, Linked Services und IR. Fabric speichert alles in OneLake im Delta-Format.
  • Zahlen 120 Activities pro Pipeline. Retry-Standard 0. F-SKU pro Sekunde, eine Minute Minimum. Serverless mindestens 10 MB.
  • Vergleich ADF und Fabric Data Factory. Synapse und Fabric. Databricks und Synapse Spark.
  • Produktion Retry, Idempotenz, Alerts, Watermark, IR hochverfügbar.
  • Design Orchestrieren mit ADF, rechnen in Spark oder SQL, Speicher als Delta.

Beispiel: ADF-Pipeline mit einer Copy Activity (JSON)

{
  "name": "CopyBlobToSql",
  "properties": {
    "concurrency": 1,
    "activities": [
      {
        "name": "CopyFromBlob",
        "type": "Copy",
        "policy": { "retry": 2, "timeout": "0.01:00:00" },
        "inputs":  [ { "referenceName": "BlobIn",  "type": "DatasetReference" } ],
        "outputs": [ { "referenceName": "SqlOut", "type": "DatasetReference" } ],
        "typeProperties": {
          "source": { "type": "DelimitedTextSource" },
          "sink":   { "type": "AzureSqlSink" }
        }
      }
    ]
  }
}

Nicht ausgeführt (kein Azure-Zugang auf dieser Maschine). Die Datasets BlobIn und SqlOut müssten existieren.

  1. concurrency: 1 erlaubt nur einen Lauf gleichzeitig. Weitere Läufe warten in der Warteschlange.
  2. retry: 2 wiederholt die Activity zweimal. timeout bricht sie nach einer Stunde ab.
  3. inputs und outputs sind Datasets. Sie zeigen über ihren Linked Service auf Quelle und Ziel.

Vergleich

  • ADF: PaaS-Orchestrator, Pipelines und Data Flows. Stark beim Kopieren und Steuern.
  • Synapse: Workspace mit SQL Pools, Spark, Pipelines und Data Explorer.
  • Fabric: SaaS mit OneLake, Kapazität (F-SKU) und Power BI im selben Produkt.
  • Databricks: Spark-Lakehouse mit Delta Lake, Unity Catalog und SQL Warehouses.
  • Azure SQL / Postgres: Operative Datenbanken. Für Analytik spiegelt man sie in ein Lakehouse.
  • Event Hubs / Kafka: Für Streaming. ADF und Fabric nehmen oft nur Micro-Batches.

Produktion

  1. Pipeline schlägt nachts fehl, niemand merkt es: Kein Alert. Lösung: Azure Monitor Alert auf Failed Runs.
  2. Duplikate nach Neustart: Der Load ist nicht idempotent. Lösung: Upsert oder Staging mit Merge.
  3. Self-hosted IR fällt aus: Ein einzelner Knoten ist ein Single Point of Failure. Lösung: mehrere Knoten.
  4. Kosten laufen davon: Data Flows starten Cluster. Serverless-Abfragen lesen zu viele Daten. Lösung: Filter, Partitionierung und Kosten-Alerts.
  5. Zu viele Activities: Eine riesige Pipeline erreicht das Limit. Lösung: in Child-Pipelines teilen.
  6. Falsche Kapazität in Fabric: Eine zu kleine F-SKU bremst alle Workloads. Lösung: Auslastung beobachten und skalieren.

Diagnose: Werkzeuge und Befehle

  • ADF Monitor: Pipeline Runs, Activity Runs und Trigger Runs mit Fehlermeldung.
  • Azure Monitor / Log Analytics: Diagnostic Settings senden Run-Logs. Daraus baut man Alerts.
  • Fabric Kapazität: Die Auslastung beobachtest du in den Kapazitäts-Metriken.
  • Databricks Spark UI: Zeigt Stages, Shuffle und langsame Tasks.
  • Synapse Serverless: Die Menge verarbeiteter Daten pro Abfrage steht in den Kosten-Sichten.
  • IR-Status im ADF Manage: Zeigt Knoten, Version und Last der Self-hosted IR.

Senior-Punkte

  1. Trenne Steuern und Rechnen. ADF ruft Compute auf, es ersetzt ihn nicht.
  2. Pipelines müssen idempotent sein. Ein Neustart darf nie Duplikate bringen.
  3. Retry ist nicht voreingestellt. Setze Retry, Timeout und Alerts bewusst.
  4. Plattform ist eine Kostenentscheidung. Serverless zahlt pro Daten, Dedicated pro Zeit, Fabric pro Kapazität.
  5. Offenes Format schützt vor Lock-in. Delta und Parquet lassen sich in mehreren Engines lesen.
  6. Governance zuerst. Unity Catalog oder OneLake Catalog regeln Zugriff früh, nicht erst nach dem Wildwuchs.
