Azure Monitor, Log Analytics, Application Insights

Kern: Azure Monitor ist die Plattform für Telemetrie in Azure: Metrics, Logs und Traces. Logs liegen in einem Log Analytics Workspace und werden mit KQL abgefragt. Application Insights ist der APM-Teil für Anwendungen und nutzt heute OpenTelemetry. Die grösste Kostenfrage ist die Ingestion pro GB.

1. Wo sitzt Azure Monitor?

  1. Azure-Ressourcen liefern Plattform-Metriken automatisch und ohne Kosten. Ressourcen-Logs brauchen eine Diagnostic Setting, also eine Weiterleitung in einen Workspace.
  2. Anwendungen senden Requests, Dependencies, Exceptions und Traces an Application Insights. Die Daten landen im Log Analytics Workspace.
  3. VMs und AKS nutzen den Azure Monitor Agent (AMA). Was er sammelt, steht in einer Data Collection Rule (DCR).
  4. Eigene Anwendungen schreiben über die Logs Ingestion API in eigene Tabellen. Auch das läuft über eine DCR.
  5. Die Metrics-DB speichert numerische Zeitreihen. Plattform-Metriken bleiben 93 Tage.
  6. Der Log Analytics Workspace speichert Logs in Tabellen. Abfragen laufen mit KQL (Kusto Query Language).
  7. Der Azure Monitor Workspace speichert Prometheus-Metriken (Managed Prometheus). Er ist kein Log Analytics Workspace.
  8. Nutzen: Alerts, Workbooks, Azure Managed Grafana, Application Map, Export in Storage oder Event Hub.

2. Die Reise eines Audit-Events (die Geschichte zum Merken)

  1. Die App schreibt ein Event. Eine Audit-Library sammelt Events im Speicher. Sie sendet sie asynchron in Batches. Der Request des Benutzers wartet nicht darauf.
  2. Die App holt ein Token. Die Managed Identity holt ein Entra-Token für https://monitor.azure.com. Es gibt kein Secret im Code. Die Identity braucht die Rolle Monitoring Metrics Publisher auf der DCR.
  3. DNS löst privat auf. Der Name des DCE zeigt über eine Private DNS Zone auf eine private IP. Das regelt der Azure Monitor Private Link Scope (AMPLS).
  4. Der DCE nimmt an. Der Data Collection Endpoint (DCE) ist der Eingang für Daten. Bei Private Link ist er Pflicht. Ohne Private Link reicht der Ingestion-Endpoint der DCR selbst.
  5. Die DCR verarbeitet. Die DCR kennt das Eingangsschema (Stream, z. B. Custom-AuditEvent). Eine Transformation in KQL (transformKql) filtert oder maskiert Felder. Dann schreibt sie in die Zieltabelle.
  6. Der Workspace speichert. Eigene Tabellen enden auf _CL. Jede Tabelle hat einen Plan (Analytics, Basic, Auxiliary) und eine Retention.
  7. Jemand fragt ab. Ein Auditor oder ein Alert fragt mit KQL ab. Logs sind nicht sofort da: Die Latenz liegt meist bei Sekunden bis wenigen Minuten.

3. Beispiel: KQL-Abfragen und Ingestion per CLI

# Workspace und DCE anlegen (Auszug)
az monitor log-analytics workspace create -g rg-mon -n law-prod -l switzerlandnorth
az monitor data-collection endpoint create -g rg-mon -n dce-prod \
  -l switzerlandnorth --public-network-access Disabled

# Abfrage aus der CLI
az monitor log-analytics query -w <workspace-guid> --analytics-query "
AppRequests
| where TimeGenerated > ago(1h)
| summarize Anzahl = count(),
            Fehler = countif(Success == false),
            P95_ms = percentile(DurationMs, 95)
          by Name
| order by Fehler desc
| take 3" -o table
Name                    Anzahl    Fehler    P95_ms
----------------------  --------  --------  --------
POST /api/upload        1840      37        2310.5
GET /api/person/{id}    9210      4         180.2
GET /actuator/health    3600      0         3.1

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Werte sind beispielhaft. Kein Azure-Account in dieser Umgebung.

  1. AppRequests ist die Tabelle für eingehende Requests einer workspace-basierten Application-Insights-Ressource.
  2. where TimeGenerated > ago(1h) steht zuerst. Der Zeitfilter macht die Abfrage schnell und billig.
  3. summarize ... by Name gruppiert pro Endpoint. countif zählt nur Fehler, percentile berechnet P95.
  4. Der Upload hat die meisten Fehler und das höchste P95. Dort fängt die Analyse an.

Weitere KQL-Bausteine, die man kennen muss:

// 1) Fehler eines Requests über alle Teile verfolgen (Distributed Tracing)
union AppRequests, AppDependencies, AppExceptions
| where OperationId == "4bf92f3577b34da6a3ce929d0e0e4736"
| project TimeGenerated, Type, Name, Success, DurationMs
| order by TimeGenerated asc

// 2) Zeitreihe für ein Diagramm
AppRequests
| where TimeGenerated > ago(24h)
| summarize Fehlerquote = 100.0 * countif(Success == false) / count() by bin(TimeGenerated, 5m)
| render timechart

// 3) Container-Logs aus AKS (Container Insights)
ContainerLogV2
| where PodNamespace == "match" and LogLevel == "error"
| project TimeGenerated, PodName, LogMessage
| take 50

// 4) Welche Tabelle kostet am meisten?
Usage
| where TimeGenerated > ago(30d) and IsBillable == true
| summarize GB = sum(Quantity) / 1024 by DataType
| order by GB desc
DataType          GB
----------------  ------
ContainerLogV2    412.7
AppTraces         96.3
AppRequests       21.4
AuditEvent_CL     3.9

Erwartetes Ergebnis von Abfrage 4 (laut Doku, nicht ausgeführt). Werte sind beispielhaft. Quantity in der Tabelle Usage ist in MB.

  1. Abfrage 1 nutzt die OperationId. Sie ist die Trace-ID aus W3C Trace Context. So sieht man einen Request über alle Services.
  2. Abfrage 2 nutzt bin() für 5-Minuten-Fenster. render timechart zeichnet ein Diagramm.
  3. Abfrage 3 liest AKS-Logs. ContainerLogV2 ist das aktuelle Schema von Container Insights.
  4. Abfrage 4 zeigt den typischen Befund: Container-Logs und Traces dominieren die Kosten, nicht die Audit-Daten.

4. Details, die Interviewer fragen

  1. Metrics vs Logs: Metrics sind leichte numerische Zeitreihen mit Dimensionen. Sie sind schnell und gut für Alerts nahe Echtzeit. Logs sind Records mit vielen Feldern. Sie erlauben freie Analyse, sind aber langsamer und teurer.
  2. Log Analytics Workspace: Ein Workspace ist ein Datenspeicher mit Tabellen, Region, Zugriffsrechten und Retention. Er ist die Grenze für Kosten, Region und Zugriff.
  3. Table Plans: Jede Tabelle hat einen Plan.
    • Analytics: volle Funktionen, Alerts, Abfragen inklusive. Teuerste Ingestion.
    • Basic: günstigere Ingestion, Abfragen kosten pro gescanntem GB, nur einfache Log-Alerts.
    • Auxiliary: minimale Ingestion, langsame Abfragen, keine Alerts. Für Audit und Compliance.
  4. Retention: Die Analytics Retention ist im Analytics-Plan 30 Tage inklusive, für Application Insights und Sentinel 90 Tage. Sie lässt sich bis 2 Jahre verlängern. Die Total Retention (Long-term) geht bis 12 Jahre.
  5. Access Control Mode: Zugriff geht über den Workspace oder über die Ressource (Resource-context). Mit Resource-context sieht ein Team nur Logs seiner eigenen Ressourcen. Table-level RBAC schränkt einzelne Tabellen ein.
  6. KQL: Die Kusto Query Language ist eine read-only Pipeline-Sprache. Operatoren werden mit | verkettet: where, project, extend, summarize, join, render. Regel: zuerst nach Zeit filtern, dann nach Spalten, dann aggregieren.
  7. Application Insights: Heute ist jede Ressource workspace-based. Die klassischen Ressourcen sind seit Februar 2024 eingestellt. Verbindung über den Connection String, nicht mehr über den Instrumentation Key.
  8. OpenTelemetry: Microsoft liefert die Azure Monitor OpenTelemetry Distro für .NET, Node.js und Python. Für Java ist es der Application Insights Java Agent 3.x. Er basiert auf OpenTelemetry und braucht keinen Code: -javaagent:applicationinsights-agent.jar.
  9. Sampling: Sampling behält nur einen Teil der Telemetrie. Der Java Agent nutzt seit 3.4 standardmässig rate-limited sampling (5 Requests pro Sekunde). Ein Trace bleibt dabei vollständig, weil die Entscheidung pro Trace fällt.
  10. Data Collection Rule (DCR): Eine DCR definiert Quelle, Schema, Transformation und Ziel. Sie gilt für AMA, Logs Ingestion API und Container Insights. Diagnostic Settings nutzen (noch) keine DCR.
  11. Data Collection Endpoint (DCE): Ein DCE ist ein regionaler Endpoint für Ingestion und Agent-Konfiguration. Er ist Pflicht bei Private Link. Er muss in der Region des Ziel-Workspace liegen.
  12. Transformation: Eine ingestion-time transformation ist KQL in der DCR (source | where ... | project ...). Sie filtert Daten vor dem Speichern. So spart man Kosten und entfernt Personendaten.
  13. Alerts: Es gibt Metric Alerts (schnell, auf Metriken), Log Search Alerts (KQL, alle 1 bis 15 Minuten), Activity Log Alerts (z. B. Ressource gelöscht) und Prometheus Alerts. Eine Action Group definiert, wer benachrichtigt wird. Alert Processing Rules unterdrücken Alerts, z. B. im Wartungsfenster.
  14. Stateful Alerts: Ein stateful Alert feuert einmal und wird automatisch aufgelöst, wenn die Bedingung weg ist. Stateless feuert bei jeder Auswertung neu.
  15. Managed Prometheus: AKS-Metriken gehen in einen Azure Monitor Workspace. Abfrage mit PromQL, meist über Azure Managed Grafana. Das ist günstiger als Metriken als Logs zu speichern.
  16. Kosten: Ingestion kostet pro GB. Ab 100 GB pro Tag gibt es Commitment Tiers mit Rabatt. Ein Daily Cap stoppt die Ingestion bei einer Grenze. Danach fehlen Daten bis zum nächsten Tag.

5. Vergleich

  • Metrics: numerisch, 1-Minuten-Auflösung, 93 Tage, schnell, günstig. Gut für Alerts und Autoscaling.
  • Logs (Log Analytics): beliebige Records, KQL, lange Retention. Gut für Analyse, Audit und Korrelation.
  • Application Insights: APM-Sicht auf Logs: Requests, Dependencies, Application Map, Live Metrics. Speichert in Log Analytics.
  • Managed Prometheus + Grafana: Kubernetes-Metriken mit PromQL. Standard in der Cloud-Native-Welt, gut portierbar.
  • Selbst betriebenes Prometheus/Grafana im Cluster: volle Kontrolle, keine Ingestion-Kosten pro GB. Aber eigener Betrieb, Speicher und Hochverfügbarkeit.
  • Diagnostic Settings vs DCR: Diagnostic Settings leiten Ressourcen-Logs weiter. DCRs sind das neue Modell mit Transformation und Schema.
  • Analytics vs Basic vs Auxiliary: Häufig abgefragt und alarmiert → Analytics. Selten abgefragt → Basic. Nur Aufbewahrung → Auxiliary.

6. In der Produktion

  1. Die Rechnung explodiert: Debug-Logs oder Health-Check-Requests füllen den Workspace. Lösung: Usage-Tabelle auswerten, Log-Level senken, Health Checks per Sampling oder Transformation filtern, Tabelle auf Basic setzen.
  2. Daily Cap erreicht: Ab einer Grenze nimmt der Workspace nichts mehr an. Alerts sehen dann keine Daten mehr. Lösung: Cap nur als Notbremse, mit Alert auf das Cap-Event.
  3. Logs kommen nicht an (Private Link): Die App löst den DCE öffentlich auf oder die Private DNS Zone fehlt. Lösung: DCE ins AMPLS aufnehmen, DNS-Zonen privatelink.monitor.azure.com und weitere verknüpfen, nslookup prüfen.
  4. 403 bei der Logs Ingestion API: Die Managed Identity hat keine Rolle auf der DCR. Lösung: Monitoring Metrics Publisher auf der DCR vergeben. Die Rolle braucht einige Minuten, bis sie wirkt.
  5. Daten werden still verworfen: Das JSON passt nicht zum Stream-Schema der DCR. Lösung: Schema abgleichen, Tabelle DCRLogErrors aktivieren und prüfen.
  6. Tracing bricht ab: Ein Service gibt den traceparent-Header nicht weiter. Die Application Map zeigt dann getrennte Inseln. Lösung: OpenTelemetry überall, auch bei Messaging (Kafka, Event Hub) Kontext weitergeben.
  7. Alert-Flut: Zu viele Alerts ohne Handlung. Das Team ignoriert sie. Lösung: Alerts auf Symptome (Fehlerquote, Latenz), stateful, Action Groups pro Schweregrad.

7. Diagnose: Werkzeuge und Abfragen

  • Usage und _BilledSize: Welche Tabelle und welche Quelle kostet am meisten (summarize sum(_BilledSize) by _ResourceId).
  • Workspace Insights im Portal: Ingestion-Volumen, Latenz und Abfragelast.
  • DCRLogErrors: Fehler bei Ingestion und Transformation, nach Aktivierung in der DCR-Diagnostik.
  • Heartbeat: Ob Agents (AMA) noch Daten senden.
  • ingestion_time() - TimeGenerated: Ingestion-Latenz messen.
  • Live Metrics und Transaction Search in Application Insights: einzelne Requests in Echtzeit.
  • Application Map: Abhängigkeiten und Fehlerquoten zwischen Services.
  • az monitor data-collection rule show und nslookup <dce>.switzerlandnorth-1.ingest.monitor.azure.com: Konfiguration und private DNS prüfen.
  • LAQueryLogs: Wer welche Abfrage wie lange laufen liess (nach Aktivierung der Query-Audit-Logs).

8. Senior-Punkte

  1. Kosten entscheidet man bei der Ingestion, nicht beim Abfragen. Filtern in der App oder in der DCR ist billiger als speichern und nie lesen.
  2. Workspace-Design ist eine Architekturentscheidung: ein zentraler Workspace pro Umgebung ist einfach. Getrennte Workspaces nur bei Datenresidenz, Mandanten oder harter Zugriffstrennung.
  3. Audit-Logs sind keine Debug-Logs. Sie brauchen ein festes Schema, lange Retention, Zugriffsschutz und keine Sampling-Verluste. Darum eigene Tabelle über DCR, nicht AppTraces.
  4. Metriken für Alerts, Logs für Analyse. Ein Metric Alert ist schneller und billiger als eine KQL-Abfrage alle 5 Minuten.
  5. OpenTelemetry statt proprietärem SDK. So bleibt das Backend austauschbar, z. B. Azure Monitor heute und ein anderes Backend später.
  6. Private Link für Monitoring ist ein Netz-Thema: AMPLS ist DNS-basiert und wirkt auf das ganze VNet. Ein falsches AMPLS kann Monitoring für andere Teams brechen.
  7. Personendaten nie ungeprüft loggen. In der Schweiz gilt das DSG. Maskieren in der App oder in der DCR-Transformation.

10. Fallen

  • „Application Insights ist ein eigener Speicher.“ → Falsch. Heute ist es workspace-based. Die Daten liegen in Log Analytics.
  • „Für die Logs Ingestion API braucht man immer einen DCE.“ → Falsch. Die DCR hat einen eigenen Endpoint. Ein DCE ist Pflicht bei Private Link.
  • „Mehr Logs heisst bessere Observability.“ → Falsch. Mehr Logs heisst vor allem mehr Kosten. Gute Metriken und Traces finden Fehler schneller.
  • „Der Daily Cap ist eine Kostenkontrolle.“ → Nur eine Notbremse. Danach fehlen Daten, auch für Alerts und Audit.
  • „Prometheus-Metriken landen im Log Analytics Workspace.“ → Falsch. Managed Prometheus nutzt einen Azure Monitor Workspace.
  • „Der Instrumentation Key reicht zum Senden.“ → Falsch. Man nutzt den Connection String. Er enthält auch den regionalen Ingestion-Endpoint.
  • „Logs sind sofort abfragbar.“ → Falsch. Es gibt Ingestion-Latenz, meist Sekunden bis Minuten. Log Alerts müssen das einplanen.

11. Fragen

Was ist Azure Monitor?

Die Plattform für Telemetrie in Azure. Sie sammelt Metrics, Logs und Traces und bietet Abfragen, Alerts und Dashboards.

Was ist der Unterschied zwischen Metrics und Logs?

Metrics sind numerische Zeitreihen, schnell und günstig. Logs sind Records mit vielen Feldern, flexibel mit KQL, aber teurer und langsamer.

Was ist ein Log Analytics Workspace?

Ein Datenspeicher mit Tabellen für Logs. Er bestimmt Region, Zugriff, Retention und Kosten.

Wie viele Workspaces würden Sie anlegen?

So wenige wie möglich, meist einen pro Umgebung. Mehr nur bei Datenresidenz, Mandantentrennung oder harten Zugriffsregeln.

Was sind Table Plans?

Analytics, Basic und Auxiliary. Sie bestimmen Ingestion-Preis, Abfrage-Funktionen und Alerts. Häufig genutzte Daten in Analytics, Audit-Daten oft in Auxiliary.

Wie lange bleiben Logs gespeichert?

Analytics Retention standardmässig 30 Tage, für Application Insights 90 Tage, verlängerbar bis 2 Jahre. Long-term Retention bis 12 Jahre.

Wie ist eine KQL-Abfrage aufgebaut?

Tabelle, dann Operatoren mit Pipe: where, project, extend, summarize, order, render. Zeitfilter immer zuerst.

Wie finden Sie die langsamsten Endpoints?

AppRequests | where TimeGenerated > ago(1h) | summarize percentile(DurationMs, 95) by Name | top 10 by .... P95 statt Durchschnitt, weil Ausreisser zählen.

Was ist Application Insights?

Das APM von Azure Monitor. Es sammelt Requests, Dependencies, Exceptions und Traces und zeigt Application Map und Live Metrics.

Wie instrumentieren Sie eine Spring-Boot-App?

Mit dem Application Insights Java Agent 3.x per -javaagent und dem Connection String. Er basiert auf OpenTelemetry und braucht keinen Code.

Welche Rolle spielt OpenTelemetry?

Es ist der offene Standard für Traces, Metriken und Logs. Azure Monitor nimmt OpenTelemetry-Daten über die Distro oder den Java Agent an. So bleibt man herstellerneutral.

Was ist Sampling und welches Risiko hat es?

Nur ein Teil der Telemetrie wird gespeichert. Das spart Kosten. Risiko: seltene Fehler fehlen. Für Audit-Daten nie Sampling.

Was ist eine Data Collection Rule?

Eine Ressource, die Quelle, Schema, Transformation und Ziel der Daten beschreibt. Sie gilt für AMA, Logs Ingestion API und Container Insights.

Wann brauchen Sie einen Data Collection Endpoint?

Bei Private Link und für einige AMA-Datenquellen. Für die Logs Ingestion API reicht sonst der Endpoint der DCR.

Was ist eine Ingestion-time Transformation?

KQL in der DCR, das Daten vor dem Speichern filtert oder ändert. Gut für Kosten und zum Maskieren von Personendaten.

Welche Alert-Typen gibt es?

Metric Alerts, Log Search Alerts, Activity Log Alerts und Prometheus Alerts. Benachrichtigung über Action Groups.

Metric Alert oder Log Search Alert?

Metric Alert, wenn eine Metrik reicht: schneller und günstiger. Log Search Alert, wenn man Logik über Records braucht.

Was ist eine Action Group?

Eine wiederverwendbare Liste von Empfängern und Aktionen: E-Mail, SMS, Webhook, Logic App, Azure Function, ITSM.

Was kostet Azure Monitor am meisten?

Meist die Log-Ingestion pro GB, vor allem Container-Logs und Traces. Danach lange Retention und Abfragen auf Basic-Tabellen.

Wie senken Sie die Kosten?

Usage-Tabelle auswerten, Log-Level senken, Sampling, DCR-Transformation, Basic- oder Auxiliary-Plan, Commitment Tier ab 100 GB pro Tag.

Was ist ein Daily Cap?

Eine Tagesgrenze für die Ingestion. Danach werden Daten verworfen. Nur als Notbremse geeignet.

Was ist AMPLS?

Der Azure Monitor Private Link Scope. Er verbindet Workspaces, DCEs und Application Insights über Private Endpoints mit dem VNet. Er hängt an Private DNS.

Wie authentifiziert sich eine App an der Logs Ingestion API?

Mit einem Entra-Token, idealerweise über Managed Identity. Die Identity braucht die Rolle Monitoring Metrics Publisher auf der DCR.

Wo landen Prometheus-Metriken aus AKS?

In einem Azure Monitor Workspace (Managed Prometheus). Abfrage mit PromQL, meist in Azure Managed Grafana.

Wie verfolgen Sie einen Request über mehrere Services?

Über die OperationId (Trace-ID). Eine KQL-Abfrage mit union über Requests, Dependencies und Exceptions, oder die End-to-End-Ansicht.

Szenario: Die Azure-Monitor-Rechnung hat sich verdreifacht. Was tun Sie?

Mit der Usage-Tabelle und _BilledSize die Tabelle und Quelle finden. Meist neue Debug-Logs oder Container-Logs. Dann Log-Level, Filter in der DCR, Tabellen-Plan und ein Budget-Alert.

Szenario: Die Audit-Library sendet, aber im Workspace kommt nichts an. Wie gehen Sie vor?

DNS des DCE prüfen (private IP?), AMPLS und Private Endpoint prüfen. Rolle der Managed Identity auf der DCR prüfen. Dann Schema gegen den Stream prüfen und DCRLogErrors lesen.

Szenario: Ein Log Alert meldet nachts Fehler, aber im Dashboard ist alles grün. Warum?

Möglich sind Ingestion-Latenz und zu kleine Abfragefenster, oder Dashboard und Alert nutzen andere Daten. Fenster und Verzögerung des Alerts prüfen, Abfragen angleichen, ggf. Metric Alert nutzen.
