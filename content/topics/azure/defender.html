Defender for Cloud und Malware Scanning

Kern: Microsoft Defender for Cloud ist eine CNAPP-Plattform. Sie prüft die Konfiguration deiner Ressourcen (CSPM) und erkennt Angriffe auf Workloads (CWPP). Malware Scanning ist ein Teil von Defender for Storage und scannt Blobs mit Microsoft Defender Antivirus.

Antwort-Muster

Frage: Was ist Defender for Cloud, und wie scannt es Uploads auf Malware?

  1. Mechanismus: CSPM vergleicht Ressourcen mit dem Microsoft cloud security benchmark und liefert Empfehlungen und einen Secure Score. Malware Scanning scannt jeden neuen Blob und schreibt das Ergebnis als Index Tag.
  2. Zahl: Blobs bis 50 GB werden gescannt. Pro Storage Account gilt standardmässig ein Limit von 10'000 GB Upload pro Monat. Der Secure Score wird alle 8 Stunden berechnet.
  3. Trade-off: Der Scan läuft asynchron. Der Blob bleibt während des Scans lesbar, und das Blockieren braucht eigene Automation.
  4. Produktion: Ein Event Grid Event startet eine Function. Sie verschiebt oder löscht böse Blobs. ABAC sperrt ungescannte Blobs.

1. Der Weg eines Uploads beim On-upload Malware Scanning

  1. Upload: Eine App schreibt einen Blob in einen Container. Zuerst passiert nichts weiter am Blob.
  2. Event: Der Event Grid System Topic meldet den neuen oder geänderten Blob. Löschst du den Topic, stoppt der Scan.
  3. Zugriff: Die Identität StorageDataScanner liest den Blob. Sie hat die Rolle Storage Blob Data Owner.
  4. Scan: Microsoft Defender Antivirus prüft den Inhalt in der Region des Kontos. Der Dienst speichert die Datei nicht.
  5. Tag: Das Ergebnis steht als Blob Index Tag am Blob. Werte sind No threats found, Malicious, Error oder Not scanned. Dazu kommt die Scan-Zeit in UTC.
  6. Alert: Bei Malicious erzeugt Defender for Cloud einen Security Alert. Du kannst Soft delete aktivieren.
  7. Automation (optional): Event Grid liefert das Ergebnis fast in Echtzeit an Function, Webhook oder Service Bus. Log Analytics speichert es in der Tabelle StorageMalwareScanningResults.

Beim On-demand Scan scannst du bestehende Blobs. Du wählst das ganze Konto, einen Container, einen Pfad-Präfix oder einen einzelnen Blob.

2. Aufbau

  1. Defender for Cloud ist der Dienst auf Subscription-Ebene. Er sammelt Daten und zeigt Empfehlungen und Alerts.
  2. CSPM prüft die Konfiguration. Die Basis (Foundational CSPM) ist gratis. Der Plan Defender CSPM kostet extra.
  3. CWPP besteht aus Plänen pro Workload. Beispiele sind Servers, Containers, Storage, Databases, Key Vault, App Service und APIs.
  4. Defender for Storage ist ein Plan. Er hat Activity Monitoring, Sensitive Data Threat Detection und Malware Scanning.
  5. Scan-Ergebnisse gibt es auf vier Wegen. Das sind Index Tags, Alerts, Event Grid und Log Analytics.
  6. Alerts werden zu Incidents gruppiert. Du exportierst sie an ein SIEM oder löst Workflow Automations aus.

3. Details

  1. CNAPP: Defender for Cloud hat drei Kernteile. Das sind CSPM, DevSecOps und CWPP. Es schützt Azure, AWS, GCP und On-premises.
  2. Foundational vs Defender CSPM: Gratis sind Policy, Secure Score und Empfehlungen. Der bezahlte Plan bringt Attack Path Analysis, Cloud Security Explorer, Governance und Regulatory Compliance.
  3. Microsoft cloud security benchmark (MCSB): Er ist der Standard, der beim Aktivieren automatisch gilt. Nur seine eingebauten Empfehlungen zählen für den Secure Score.
  4. Secure Score: Für jede Control gilt Max Score geteilt durch (gesunde plus ungesunde Ressourcen), mal gesunde Ressourcen. Defender berechnet das alle 8 Stunden. Punkte gibt es erst, wenn du alle Empfehlungen einer Control erfüllst.
  5. Zwei Score-Modelle: Der klassische Secure Score liegt im Azure Portal. Der neue Cloud Secure Score (risikobasiert) liegt im Defender Portal und geht von 0 bis 100.
  6. Fix, Enforce, Deny: Fix behebt ein Problem sofort. Enforce deployt eine Policy, die neue Ressourcen korrigiert. Deny verhindert falsche neue Ressourcen.
  7. Preis von Defender for Storage: Der Plan kostet pro Storage Account. Malware Scanning kostet zusätzlich pro gescanntes GB.
  8. Monatliches Limit: Standard sind 10'000 GB hochgeladene Blobs pro Konto und Monat. Danach scannt Defender nicht mehr. Zwei Alerts warnen bei 75 % und beim Erreichen.
  9. Eingesetzte Ressourcen: Defender legt einen Event Grid System Topic, StorageDataScanner und bei Subscription-Aktivierung DefenderForStorageSecurityOperator an. Löschst du eine davon, stoppt der Scan.
  10. Grenzen: Append Blobs und Page Blobs werden nicht gescannt. Auch client-seitig verschlüsselte Blobs und NFS-3.0-Uploads nicht. On-upload gibt es nicht für Azure Files.
  11. Scan-Timeout: Er liegt zwischen 30 Minuten und 3 Stunden, je nach Grösse und Aufbau. Danach steht Scan timed out. Verschachtelte ZIP-Dateien brauchen am längsten.
  12. Hash Reputation Analysis: Sie vergleicht Hashes neuer Dateien mit bekannter Malware. Sie ist in allen Plänen enthalten. Malware Scanning scannt den ganzen Inhalt und ist nur im neuen Plan.

4. Fallen

  • „Defender blockiert Malware automatisch.“ → Falsch. Standard sind Tag und Alert. Blockieren geht mit Soft delete, ABAC oder eigener Automation.
  • „Ein Secure Score von 100 % heisst, wir sind sicher.“ → Falsch. Er misst nur die Konfiguration gegen den Benchmark. Er sagt nichts über Angriffe oder Code.
  • „Index Tags sind ein sicherer Beweis, dass ein Blob sauber ist.“ → Falsch. Wer Tags ändern darf, kann sie fälschen. Nimm für sichere Abläufe Alerts, Event Grid oder Log Analytics.
  • „Der Blob ist erst nach dem Scan lesbar.“ → Falsch. Der Zugriff bleibt offen. Eine App muss selbst auf das Ergebnis warten, oder ABAC sperrt ungescannte Blobs.
  • „Defender for Cloud ist komplett gratis.“ → Falsch. Nur Foundational CSPM ist gratis. Workload-Pläne wie Storage kosten Geld.
  • „Malware Scanning findet jede Malware.“ → Falsch. Es macht statische Analyse und kennt kein Mark of the Web. Client-seitig verschlüsselte oder in Teilen hochgeladene Dateien bleiben unerkannt.

5. Selbsttest

Warum?

Warum braucht man Malware Scanning, wenn Storage schon verschlüsselt ist?

Verschlüsselung schützt vor Datendiebstahl, nicht vor bösen Dateien. Ein Upload kann Malware enthalten, die später weiterverteilt wird.

Warum aktiviert man Defender for Storage auf Subscription-Ebene?

Dann sind alle bestehenden und neuen Konten geschützt. Einzelne Konten kann man ausnehmen.

Warum gibt es ein monatliches Scan-Limit?

Die Kosten sind pro GB. Das Limit hält die Rechnung planbar. Nach dem Limit bleiben neue Uploads ungescannt.

Wie innen?

Wie startet ein On-upload Scan?

Ein Event Grid System Topic meldet BlobCreated. Das startet den Scanner mit der Managed Identity StorageDataScanner.

Welche Engine scannt?

Microsoft Defender Antivirus, dieselbe Engine und dieselben Signatur-Updates wie bei Defender for Endpoint. Der Scan läuft in der Region des Kontos.

Wo steht das Scan-Ergebnis?

Als Blob Index Tag, als Security Alert, optional als Event Grid Event und in Log Analytics. Index Tags sind standardmässig an.

Was ist der Unterschied zwischen On-upload und On-demand?

On-upload scannt neue oder geänderte Blobs automatisch. On-demand scannt bestehende Daten auf Abruf, etwa nach einem Alert.

Wie berechnet sich der Secure Score einer Control?

Max Score geteilt durch die Zahl aller bewerteten Ressourcen, mal die Zahl gesunder Ressourcen. Alle 8 Stunden neu.

Zahlen

Wie gross darf ein Blob für den Scan sein?

Bis 50 GB pro Blob oder Datei. Alle Dateitypen und Archive wie ZIP oder RAR werden gescannt.

Wie hoch ist das Standard-Limit?

10'000 GB hochgeladene Blobs pro Storage Account und Monat. Man kann es pro Subscription oder pro Konto ändern.

Wann kommt der Cap-Alert?

Bei 75 % des Monatslimits kommt eine Warnung. Beim Erreichen kommt der zweite Alert, und das Scannen pausiert.

Wie lange darf ein Scan dauern?

Das Zeitfenster liegt zwischen 30 Minuten und 3 Stunden. Danach ist das Ergebnis Scan timed out.

Vergleich

Foundational CSPM vs Defender CSPM?

Foundational ist gratis und hat Empfehlungen und Secure Score. Defender CSPM bringt Attack Path, Cloud Security Explorer und Governance.

Malware Scanning vs Hash Reputation Analysis?

Malware Scanning prüft den ganzen Inhalt mit Defender Antivirus. Hash Reputation vergleicht nur Hashes mit bekannter Malware.

Defender for Cloud vs Azure Policy?

Policy definiert und erzwingt Regeln. Defender nutzt Policies für Empfehlungen und zeigt Score und Bedrohungen dazu.

Defender for Cloud vs Microsoft Sentinel?

Defender erzeugt Alerts und Empfehlungen für Cloud-Ressourcen. Sentinel ist das SIEM, das Alerts aus vielen Quellen sammelt und korreliert.

Produktion

Wie reagiert man automatisch auf Malware?

Event Grid sendet das Ergebnis an eine Function. Sie verschiebt den Blob in Quarantäne oder löscht ihn. Alternativ löst ein Alert eine Logic App aus.

Wie verhindert man, dass jemand einen ungescannten Blob liest?

Mit ABAC auf Basis des Index Tags. Nur Blobs ohne Treffer sind lesbar. Der Zugriff bleibt sonst offen.

Was tun bei einem False Positive?

Die Datei im Sample Submission Portal einreichen. Bei wiederkehrenden Alerts eine Suppression Rule anlegen.

Szenario: Nutzer laden Dokumente hoch. Eine App leitet sie sofort weiter. Wie bleibt Malware draussen?

Hochladen in einen Staging-Container. Event Grid meldet das Ergebnis. Nur saubere Blobs verschiebt eine Function in den Ziel-Container. Böse Blobs löscht sie.

Szenario: Der Scan hat plötzlich aufgehört. Was prüfen Sie?

Das Monatslimit, den Event Grid System Topic und die Identitäten. Wurde eine Ressource gelöscht, hilft Deaktivieren und neu Aktivieren.

Design

Wo schützt man gegen Malware, wenn die Datei client-seitig verschlüsselt ist?

Vor dem Verschlüsseln scannen oder Encryption at Rest mit Customer Managed Keys nutzen. Client-seitig verschlüsselte Blobs kann der Dienst nicht lesen.

Wann reicht Foundational CSPM?

Für kleine Umgebungen ohne Bedarf an Attack Path und Governance. Sonst lohnt sich Defender CSPM wegen der Priorisierung.

Szenario: Eine Chunk-Upload-App schreibt Dateien in Teilen. Funktioniert das Scannen?

Nicht zuverlässig. Header-Teile gelten als beschädigt, Tail-Teile wirken harmlos. Besser vor dem Aufteilen oder nach dem Zusammensetzen scannen.

Wie misst man Fortschritt bei der Sicherheit?

Mit dem Secure Score über die Zeit, etwa im Workbook. Dazu zählt man offene Empfehlungen pro Control und Alerts pro Woche.

Mehr

Gerüst

  • Warum? Konfiguration prüfen und Workloads vor Angriffen schützen. Malware nicht über Uploads verbreiten.
  • Wie innen? Policies erzeugen Empfehlungen und Score. Event Grid startet den Scan, Defender Antivirus scannt, ein Index Tag speichert das Ergebnis.
  • Zahlen 50 GB pro Blob. 10'000 GB Scan-Limit pro Konto und Monat. Score alle 8 Stunden. Scan-Timeout 30 Minuten bis 3 Stunden.
  • Vergleich Foundational gegen Defender CSPM. Malware Scanning gegen Hash Reputation. Defender gegen Sentinel.
  • Produktion Event Grid und Function für Quarantäne. ABAC gegen ungescannte Blobs. Cap-Alerts beachten.
  • Design Staging-Container, Scan, dann Freigabe. Index Tags nie als einzige Kontrolle.

Beispiel: Plan und Scan-Ergebnis abfragen

# Status des Defender-for-Storage-Plans in der Subscription
az security pricing show --name StorageAccounts

# Index Tags eines Blobs lesen (hier steht das Scan-Ergebnis)
az storage blob tag list \
  --account-name <konto> --container-name uploads \
  --name rechnung.pdf --auth-mode login

Nicht ausgeführt (kein Azure-Zugang auf dieser Maschine). Die genauen Tag-Namen siehst du im Portal am Blob.

  1. Der erste Befehl zeigt, ob der Plan Standard ist.
  2. Der zweite liest die Index Tags. Dort stehen das Scan-Ergebnis und die Scan-Zeit.
  3. Für sichere Abläufe liest du lieber das Event Grid Event als den Tag.

Vergleich

  • Defender for Cloud: Konfiguration und Bedrohungen für Azure, AWS, GCP und On-premises.
  • Azure Policy: Regeln definieren und erzwingen. Defender liest die Ergebnisse.
  • Microsoft Sentinel: SIEM und SOAR. Es sammelt Alerts aus Defender und anderen Quellen.
  • Defender for Endpoint: Schutz für Geräte. Die Antivirus-Engine ist die gleiche wie beim Storage-Scan.
  • Defender for Key Vault: Erkennt ungewöhnlichen Zugriff auf Key Vaults.
  • Defender for DevOps: Prüft Code und Pipelines in Azure DevOps, GitHub und GitLab auf falsche IaC-Einstellungen und Secrets.

Produktion

  1. Scan-Ergebnisse gehen ungenutzt verloren: Niemand liest die Tags. Lösung: Event Grid und Function oder ABAC bauen.
  2. Scan stoppt still: Das Monatslimit ist erreicht, oder eine Ressource wurde gelöscht. Lösung: Cap-Alerts überwachen, Policy gegen Löschen setzen.
  3. Alert-Flut durch False Positives: Backups enthalten Fragmente. Lösung: Suppression Rules für bekannte Fälle.
  4. Kosten steigen: Viele Lifecycle-Transaktionen und grosse Uploads treiben die Rechnung. Lösung: Limit pro Konto setzen und die Preis-Schätzung nutzen.
  5. Metadaten-Update direkt nach Upload: Der Scan kann fehlschlagen. Lösung: Metadaten beim Schreiben setzen oder warten.
  6. Ungescannte Dateien im Umlauf: Chunk-Uploads und Append Blobs fallen durch. Lösung: Format und Upload-Weg anpassen.

Diagnose: Werkzeuge und Befehle

  • Defender for Cloud → Security alerts: Alerts zu Malware und Storage ansehen.
  • Log Analytics: Die Tabelle StorageMalwareScanningResults zeigt jedes Scan-Ergebnis.
  • Blob Index Tags: Im Portal am Blob oder mit az storage blob tag list.
  • Event Grid: Den System Topic in der Resource Group prüfen. Ist er weg, stoppt der Scan.
  • Azure Resource Graph: Die Tabelle SecurityResources liefert Secure Score und Controls per Abfrage.
  • Workbook Secure Score Over Time: Zeigt den Verlauf pro Subscription.

Senior-Punkte

  1. Posture und Detection sind zwei Dinge. Der Secure Score sagt, wie gut du konfiguriert bist. Er sagt nicht, ob jemand angreift.
  2. Scannen ist nicht Blockieren. Ohne ABAC oder Staging-Container kann ein Blob gelesen werden, bevor das Ergebnis da ist.
  3. Index Tags sind Komfort, keine Kontrolle. Für Sicherheit nutzt man Alerts, Event Grid oder Log Analytics.
  4. Kosten sind pro GB. Setze ein Limit pro Konto und überwache die zwei Cap-Alerts.
  5. Aktivieren per Policy und IaC. So gibt es keine Konten ohne Schutz und keine Abweichung.
  6. Kennt die Lücken. Verschlüsselte, in Teilen geschriebene und Append-Blob-Daten bleiben ohne Scan. Plane dafür Ersatzmassnahmen.
