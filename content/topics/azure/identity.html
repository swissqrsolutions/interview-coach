Entra ID, Managed Identity, Workload Identity, RBAC

Azure · Tier 1 · Quellen: Microsoft Learn – What are managed identities?, Managed identity best practice recommendations, Workload identity federation, Use Microsoft Entra Workload ID with AKS, What is Azure RBAC?, Azure roles vs Microsoft Entra roles, Credential chains in the Azure Identity library for Java; External Secrets Operator docs (Azure Key Vault provider)

Kern: Microsoft Entra ID ist der Identity Provider von Azure: Er stellt Tokens für Benutzer und Anwendungen aus. Managed Identity und Workload Identity lösen das Problem, dass Anwendungen ohne gespeicherte Passwörter an Azure-Dienste kommen. Azure RBAC entscheidet dann, was diese Identität auf welcher Ressource darf.

1. Wo sitzt die Identität?

  1. Tenant: eine Entra-ID-Instanz einer Organisation. Alle Identitäten leben hier.
  2. Service Principal: die Identität einer Anwendung im Tenant. Eine Managed Identity ist ein Service Principal, dessen Credentials Azure selbst verwaltet.
  3. Federated Credential: eine Vertrauensregel. Entra akzeptiert ein Token eines fremden Issuers (z. B. AKS) statt eines Secrets.
  4. Entra-Rollen: Rechte im Verzeichnis selbst. Beispiel: Benutzer anlegen, App-Registrierungen verwalten.
  5. Azure RBAC: Rechte auf Azure-Ressourcen. Eine Role Assignment verbindet Principal, Rolle und Scope.
  6. Scope-Hierarchie: Management Group → Subscription → Resource Group → Ressource. Rechte vererben sich nach unten.

2. Die Reise eines Tokens mit Workload Identity (die Geschichte zum Merken)

  1. Pod startet: Der Pod nutzt einen ServiceAccount mit der Annotation azure.workload.identity/client-id. Der Pod trägt das Label azure.workload.identity/use: "true".
  2. Webhook: Ein Mutating Admission Webhook setzt Env-Vars: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_FEDERATED_TOKEN_FILE, AZURE_AUTHORITY_HOST. Das Kubelet legt ein projiziertes SA-Token mit Audience api://AzureADTokenExchange in die Datei.
  3. Token tauschen: Das SDK liest die Datei. Es schickt das Kubernetes-Token als Client Assertion an Entra. Kein Secret ist im Spiel.
  4. Entra prüft: Entra lädt die öffentlichen Schlüssel vom OIDC Issuer des Clusters. Es vergleicht Issuer, Subject (system:serviceaccount:<ns>:<sa>) und Audience mit der Federated Identity Credential.
  5. Access Token: Passt alles, stellt Entra ein Token für die User-Assigned Managed Identity aus. Es gilt typischerweise etwa eine Stunde.
  6. Zugriff: Der Pod ruft Key Vault mit dem Token auf. Key Vault prüft die RBAC-Rolle, z. B. Key Vault Secrets User.
  7. Ergebnis: Das Secret kommt zurück. Mit dem External Secrets Operator landet es als Kubernetes Secret im Namespace.

Ohne AKS ist der Weg kürzer: Auf einer VM holt das SDK das Token beim IMDS-Endpoint 169.254.169.254. Auf App Service und Functions über IDENTITY_ENDPOINT und IDENTITY_HEADER.

3. Beispiel: Workload Identity für den External Secrets Operator

# 1) Cluster mit OIDC Issuer und Workload Identity
az aks update -g rg-match -n aks-match --enable-oidc-issuer --enable-workload-identity
ISSUER=$(az aks show -g rg-match -n aks-match --query oidcIssuerProfile.issuerUrl -o tsv)

# 2) User-Assigned Managed Identity + Rolle nur auf den Key Vault
az identity create -g rg-match -n id-eso
az role assignment create --assignee <principalId> \
  --role "Key Vault Secrets User" --scope <keyVaultResourceId>

# 3) Vertrauen: nur dieser ServiceAccount in diesem Namespace
az identity federated-credential create -g rg-match --identity-name id-eso \
  --name fic-eso --issuer "$ISSUER" \
  --subject system:serviceaccount:external-secrets:eso-sa \
  --audiences api://AzureADTokenExchange
{
  "audiences": [ "api://AzureADTokenExchange" ],
  "issuer": "https://switzerlandnorth.oic.prod-aks.azure.com/<tenant-id>/<guid>/",
  "name": "fic-eso",
  "subject": "system:serviceaccount:external-secrets:eso-sa",
  "type": "Microsoft.ManagedIdentity/userAssignedIdentities/federatedIdentityCredentials"
}
apiVersion: v1
kind: ServiceAccount
metadata:
  name: eso-sa
  namespace: external-secrets
  annotations:
    azure.workload.identity/client-id: <clientId von id-eso>
---
apiVersion: external-secrets.io/v1
kind: ClusterSecretStore
metadata: { name: azure-kv }
spec:
  provider:
    azurekv:
      authType: WorkloadIdentity
      vaultUrl: https://kv-match.vault.azure.net
      serviceAccountRef: { name: eso-sa, namespace: external-secrets }
// Java im Pod oder in der Function: gleicher Code überall
TokenCredential cred = new DefaultAzureCredentialBuilder().build();
SecretClient kv = new SecretClientBuilder()
    .vaultUrl("https://kv-match.vault.azure.net").credential(cred).buildClient();
kv.getSecret("db-password").getValue();

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Hier gibt es keine Azure CLI, keinen Account und keinen AKS-Cluster.

  1. Issuer: Die URL ist pro Cluster eindeutig. Entra holt dort die öffentlichen Schlüssel, um SA-Tokens zu prüfen.
  2. Subject: Nur genau dieser ServiceAccount in diesem Namespace bekommt Tokens. Ein anderer Pod im Cluster nicht.
  3. Rolle auf Vault-Scope: nicht auf Subscription. Das ist Least Privilege.
  4. DefaultAzureCredential findet im Pod WorkloadIdentityCredential, in der Function ManagedIdentityCredential, lokal die Azure CLI.
  5. Die ESO-API-Version hängt von der installierten ESO-Version ab (ältere: v1beta1).

4. Details, die Interviewer fragen

  1. System-Assigned MI: gehört zu genau einer Ressource. Sie entsteht und stirbt mit ihr. Gut für eine App mit eigenen Rechten.
  2. User-Assigned MI: eine eigene Azure-Ressource. Mehrere Ressourcen können sie teilen. Man kann Rollen vergeben, bevor die App existiert.
  3. Wann User-Assigned: bei vielen Instanzen mit gleichen Rechten, bei Blue/Green-Deployments, bei Workload Identity und wenn Rechte schon beim Erstellen nötig sind.
  4. Token-Cache: Managed-Identity-Tokens werden gecacht. Rollen- oder Gruppenänderungen können darum bis zu Stunden brauchen. Microsoft empfiehlt Rollen direkt statt über Gruppen für MIs.
  5. Workload Identity Federation: Entra vertraut Tokens eines externen OIDC-Issuers. Beispiele: AKS, GitHub Actions, Azure DevOps Service Connections. Ersetzt Client Secrets.
  6. Federated Credentials pro Identität: höchstens 20 pro User-Assigned MI oder App Registration. Bei vielen Clustern oder Namespaces wird das eine Grenze.
  7. AKS Pod Identity (alt): ersetzt durch Workload Identity. Pod Identity nutzte NMI-Pods und IMDS-Abfangen.
  8. Role Definition: eine Liste von Actions, NotActions, DataActions, NotDataActions. Actions = Control Plane, DataActions = Daten.
  9. Control Plane vs Data Plane: Control Plane = Ressource verwalten (ARM). Data Plane = Inhalte lesen und schreiben (Blobs, Secrets). Beide haben eigene Rollen.
  10. Wichtige Rollen: Owner (alles inkl. Rechte vergeben), Contributor (alles ausser Rechte vergeben), Reader, User Access Administrator, Role Based Access Control Administrator (Rechte vergeben, mit Conditions einschränkbar).
  11. Data-Rollen: z. B. Storage Blob Data Reader/Contributor, Key Vault Secrets User, Azure Event Hubs Data Sender. Ohne sie gibt es mit Entra-Token keinen Datenzugriff.
  12. Vererbung: Eine Rolle auf der Subscription gilt in allen Resource Groups darunter. Darum Scope so klein wie möglich.
  13. Deny Assignments: verbieten Aktionen trotz Rolle. Man legt sie nicht direkt an. Sie kommen z. B. aus Deployment Stacks oder Managed Apps.
  14. Conditions (ABAC): Bedingungen an Role Assignments. Beispiel: nur Blobs mit einem bestimmten Index-Tag lesen.
  15. Entra-Rollen vs Azure-Rollen: Entra-Rollen verwalten Verzeichnis-Objekte (Benutzer, Apps). Azure-Rollen verwalten Ressourcen. Ein Global Admin hat nicht automatisch Rechte auf Subscriptions.
  16. Elevate Access: Ein Global Admin kann sich zum User Access Administrator auf Root-Scope machen. Das ist ein Notfall-Weg und wird überwacht.
  17. PIM: Privileged Identity Management vergibt Rollen nur auf Zeit und mit Begründung (just-in-time).
  18. Propagation: Neue Role Assignments brauchen einige Minuten. Direkt nach dem Deployment kommen darum oft kurz 403-Fehler.
  19. DefaultAzureCredential (Java): Reihenfolge Environment → Workload Identity → Managed Identity → IntelliJ → VS Code → Azure CLI → PowerShell → azd → Broker. Die erste, die ein Token bekommt, gewinnt.
  20. AZURE_TOKEN_CREDENTIALS: prod lässt nur die Deployment-Credentials zu, dev nur Entwickler-Tools. Oder ein einzelner Name wie ManagedIdentityCredential.
  21. User-Assigned MI im SDK: Bei mehreren MIs muss man die Client-ID angeben, z. B. managedIdentityClientId(...) oder AZURE_CLIENT_ID.
  22. App Registration vs Enterprise App: Die App Registration ist die globale Definition. Die Enterprise Application ist der Service Principal im Tenant.

5. Vergleich

  • System-Assigned vs User-Assigned MI: System = an eine Ressource gebunden, einfach. User = eigene Ressource, teilbar, vorab berechtigbar, nötig für Federation.
  • Managed Identity vs Service Principal mit Secret: MI hat keine Secrets und rotiert selbst. Ein Secret läuft ab, kann leaken und braucht Rotation.
  • Workload Identity vs Pod Identity: Workload Identity nutzt Standard-OIDC-Federation. Pod Identity fing IMDS-Aufrufe ab und ist abgelöst.
  • Workload Identity vs Kubernetes Secret mit Client Secret: kein Secret im Cluster, kein Ablauf, Rechte pro ServiceAccount.
  • Azure RBAC vs Entra-Rollen: Ressourcen vs Verzeichnis. Beide nutzen dieselben Identitäten.
  • Azure RBAC vs Key-Vault-Access-Policies: RBAC ist zentral, mit PIM und Deny Assignments. Access Policies sind ein altes, Vault-lokales Modell.
  • DefaultAzureCredential vs konkrete Credential: Default = bequem für lokal und Cloud. Konkret (z. B. ManagedIdentityCredential) = vorhersehbar und schneller in Produktion.
  • Azure vs AWS: Managed Identity ≈ IAM Role für EC2/Lambda. Workload Identity auf AKS ≈ IRSA/Pod Identity auf EKS.

6. In der Produktion

  1. 403 direkt nach dem Deployment: Die Role Assignment ist noch nicht propagiert. Lösung: Retry mit Backoff, Rollen vor dem App-Start vergeben (User-Assigned MI).
  2. Falsche Identität: Lokal klappt alles mit dem eigenen az login (Owner), in Azure fehlt der MI die Rolle. Lösung: lokal mit gleich kleinen Rechten testen, AZURE_TOKEN_CREDENTIALS.
  3. Env-Vars kapern die Kette: Jemand setzt AZURE_CLIENT_SECRET auf dem Host. EnvironmentCredential gewinnt vor der MI. Lösung: konkrete Credential in Produktion.
  4. Workload Identity geht nicht: Label am Pod fehlt, Subject falsch geschrieben, Namespace anders oder Issuer-URL alt. Fehler: AADSTS70021: No matching federated identity record found.
  5. Zu breite Rechte: Contributor auf der Subscription für eine Pipeline. Lösung: eigene Identität pro Pipeline und Umgebung, Scope Resource Group, PIM für Menschen.
  6. Gruppenänderung wirkt nicht: Die MI ist in einer Gruppe, das Token ist gecacht. Lösung: Rolle direkt auf die MI, Geduld oder Neustart.
  7. Gelöschte System-MI: Ressource neu erstellt, neue Principal-ID, alte Role Assignments zeigen ins Leere („Identity not found“). Lösung: User-Assigned MI oder Rollen im IaC mitdeployen.

7. Diagnose: Werkzeuge und Befehle

  • az role assignment list --assignee <principalId> --all -o table: welche Rollen hat die Identität wo.
  • Access control (IAM) → Check access im Portal: effektive Rechte einer Identität auf einer Ressource.
  • Entra Sign-in Logs → „Managed identity sign-ins“ und „Service principal sign-ins“: Fehlercodes wie AADSTS70021.
  • Activity Log: wer hat welche Role Assignment angelegt oder gelöscht.
  • Token dekodieren (z. B. jwt.ms): aud, oid, appid, roles prüfen.
  • Im Pod: env | grep AZURE_ und cat $AZURE_FEDERATED_TOKEN_FILE (nur Claims prüfen).
  • az identity federated-credential list -g <rg> --identity-name <mi>: Issuer und Subject vergleichen.
  • SDK-Logging auf INFO: zeigt, welche Credential in der Kette versucht wurde und warum sie scheiterte.

8. Senior-Punkte

  1. Keine Secrets für Azure-Zugriffe. Managed Identity in Azure, Workload Identity Federation für AKS und CI/CD.
  2. Least Privilege mit Scope: Data-Rolle auf die einzelne Ressource, nicht Contributor auf die Subscription.
  3. User-Assigned MI für Plattform-Code: Rollen im IaC vor der App, stabile Principal-ID, keine Race Conditions.
  4. Eine Identität pro Workload und Umgebung. Geteilte Identitäten verwischen das Audit und vergrössern den Schaden.
  5. DefaultAzureCredential bewusst einsetzen: bequem in der Entwicklung, in Produktion eingeschränkt oder konkret.
  6. Menschen über PIM, Maschinen über feste, kleine Rollen. Owner und User Access Administrator selten und überwacht.

10. Fallen

  • „Owner auf dem Storage Account darf Blobs per Entra lesen.“ → Falsch. Owner ist Control Plane. Dafür braucht es eine Data-Rolle.
  • „Global Admin darf alles in Azure.“ → Falsch. Entra-Rollen gelten fürs Verzeichnis. Für Ressourcen braucht es Azure-Rollen.
  • „System-Assigned MI überlebt ein Neuerstellen der App.“ → Falsch. Sie wird gelöscht, die neue hat eine andere ID.
  • „Workload Identity speichert ein Secret im Pod.“ → Falsch. Im Pod liegt nur ein kurzlebiges Kubernetes-Token.
  • „Eine neue Rolle wirkt sofort.“ → Falsch. Propagation braucht Minuten, gecachte MI-Tokens länger.
  • „DefaultAzureCredential nimmt immer die Managed Identity.“ → Falsch. Environment und Workload Identity kommen vorher.
  • „Contributor kann keine Daten lesen.“ → Vorsicht. Contributor kann Storage-Keys auslesen und bei Access Policies sich selbst Key-Vault-Rechte geben.

11. Fragen

Was ist Microsoft Entra ID?

Der Cloud Identity Provider von Microsoft. Er authentifiziert Benutzer und Anwendungen und stellt OAuth-2.0- und OIDC-Tokens aus.

Was ist eine Managed Identity?

Eine Entra-Identität für eine Azure-Ressource. Azure verwaltet und rotiert die Credentials, die App sieht nie ein Secret.

System-Assigned vs User-Assigned?

System: gehört einer Ressource, stirbt mit ihr. User: eigene Ressource, teilbar, vorab berechtigbar.

Wann nehmen Sie eine User-Assigned MI?

Bei mehreren Ressourcen mit gleichen Rechten, wenn Rechte vor der App da sein müssen, und für Workload Identity auf AKS.

Wie holt eine App ein Token mit Managed Identity?

Über einen lokalen Endpoint: IMDS (169.254.169.254) auf VMs, IDENTITY_ENDPOINT auf App Service und Functions. Das SDK macht das automatisch.

Was ist Workload Identity Federation?

Entra vertraut Tokens eines externen OIDC-Issuers und tauscht sie gegen ein Entra-Token. Kein Secret nötig.

Wie funktioniert Workload Identity auf AKS?

Der Cluster hat einen OIDC Issuer. Der Pod bekommt ein projiziertes SA-Token. Entra prüft es gegen die Federated Credential der MI und stellt ein Token aus.

Was muss für Workload Identity gesetzt sein?

OIDC Issuer und Workload Identity am Cluster, Federated Credential mit Issuer und Subject, SA-Annotation client-id und Pod-Label use: "true".

Was ist das Subject einer Federated Credential bei AKS?

system:serviceaccount:<namespace>:<serviceaccount>. Es muss genau passen.

Was ist Azure RBAC?

Autorisierung auf Azure-Ressourcen über Role Assignments: Principal, Rolle und Scope. Rechte vererben sich nach unten.

Azure-Rollen vs Entra-Rollen?

Azure-Rollen regeln Ressourcen (Owner, Contributor). Entra-Rollen regeln das Verzeichnis (Global Admin, App Admin).

Owner vs Contributor vs User Access Administrator?

Owner darf alles inklusive Rechte vergeben. Contributor alles ausser Rechte vergeben. User Access Administrator nur Rechte vergeben.

Was ist der Unterschied zwischen Actions und DataActions?

Actions betreffen die Verwaltung der Ressource. DataActions betreffen die Daten darin, z. B. Blob lesen oder Secret holen.

Wie setzen Sie Least Privilege um?

Eigene Identität pro Workload, kleinste passende Data-Rolle, kleinster Scope, PIM für Menschen, regelmässige Access Reviews.

Was ist PIM?

Privileged Identity Management: Rollen werden nur auf Zeit aktiviert, mit Begründung und optional Genehmigung.

Wie arbeitet DefaultAzureCredential?

Eine Kette: Environment, Workload Identity, Managed Identity, dann Entwickler-Tools wie IntelliJ und Azure CLI. Die erste mit Token gewinnt.

Sollte man DefaultAzureCredential in Produktion nutzen?

Mit Vorsicht. Microsoft nennt Nachteile wie unvorhersehbares Verhalten. Besser AZURE_TOKEN_CREDENTIALS=prod oder eine konkrete Credential.

Warum klappt es lokal, aber nicht in Azure?

Lokal nutzt die Kette oft das eigene Konto mit mehr Rechten. Die Managed Identity in Azure hat diese Rolle nicht.

Wie authentifiziert sich eine CI/CD-Pipeline ohne Secret?

Mit Workload Identity Federation: GitHub Actions oder Azure DevOps bekommen ein OIDC-Token, das Entra gegen eine Federated Credential prüft.

Was ist ein Deny Assignment?

Eine Sperre, die Aktionen trotz Rolle verbietet. Sie kommt aus Plattform-Funktionen wie Deployment Stacks, nicht von Hand.

Was sind ABAC-Conditions?

Bedingungen an einer Role Assignment, z. B. nur Blobs mit bestimmtem Tag oder Pfad. Sie verfeinern RBAC.

Szenario: Eine neue Function bekommt 403 beim Lesen aus Key Vault, die Rolle ist vergeben. Was prüfen Sie?

Propagation abwarten, richtige Identität (System vs User, Client-ID), Scope der Rolle, RBAC-Modell des Vaults und Netzwerk (Private Endpoint, Firewall).

Szenario: Ein Pod auf AKS meldet AADSTS70021. Was ist los?

Entra findet keine passende Federated Credential. Issuer-URL, Subject mit Namespace und SA-Name, Audience und Client-ID-Annotation vergleichen.

Szenario: Eine Pipeline hat Contributor auf der Subscription. Wie verbessern Sie das?

Eigene Identität pro Umgebung mit Federation statt Secret, Scope auf die Resource Group, nur nötige Rollen. Rechte-Vergabe über RBAC Administrator mit Conditions.
