Azure Functions: Trigger, Bindings, Pläne, Durable Functions

Azure · Tier 1 · Quellen: Microsoft Learn (Azure Functions hosting options / functions-scale, Flex Consumption plan, Triggers and bindings, Java developer guide, Isolated worker model guide, Event Hubs trigger, Blob trigger with Event Grid, Networking options, Identity-based connections, Durable Functions overview and patterns), Defender for Storage malware scanning docs, Azure Architecture Center

Kern: Azure Functions ist eine Plattform, die eine Funktion ausführt, wenn ein Trigger feuert. Bindings verbinden die Funktion deklarativ mit anderen Diensten, ohne SDK-Code. Der Hosting Plan bestimmt Skalierung, Netz, Cold Start und Kosten; Durable Functions ergänzt zustandsbehaftete Workflows.

1. Wo sitzt eine Function?

  1. Function App: Die Function App ist die Einheit für Deployment, Konfiguration und Skalierung. Sie enthält eine oder mehrere Funktionen. Beispiel: func-upload-prod.
  2. Functions Host: Der Host lauscht auf Trigger, führt Bindings aus und meldet Scale-Signale. Er liest host.json.
  3. Language Worker: Der Worker ist ein eigener Prozess für die Sprache, z. B. die JVM. Host und Worker sprechen über gRPC.
  4. Trigger: Ein Trigger startet die Funktion. Jede Funktion hat genau einen. Beispiel: @EventHubTrigger.
  5. Bindings: Ein Input Binding liest Daten, ein Output Binding schreibt Daten. Beispiel: @BlobOutput schreibt eine Datei.
  6. Host Storage: AzureWebJobsStorage ist ein Storage Account für Leases, Checkpoints, Timer-Locks und Durable-Zustand. Ohne ihn startet der Host nicht.

2. Die Reise eines Uploads durch die Quarantäne (die Geschichte zum Merken)

  1. Die Datei kommt an. Ein Client schickt eine Datei an die Upload-Function (HTTP-Trigger). Die Function prüft zuerst das JWT. Dann prüft Apache Tika die Byte-Signatur, nicht nur die Endung.
  2. Sofort antworten. Die Function schreibt die Datei in einen Quarantäne-Container und antwortet sofort. Sie wartet nicht auf den Scan. So bleibt sie weit unter dem 230-Sekunden-Limit.
  3. Defender scannt. Defender for Storage sieht das BlobCreated-Event und scannt die Datei. Er setzt einen Blob Index Tag mit dem Ergebnis.
  4. Das Ergebnis wird ein Event. Defender schickt das Ergebnis an ein Event-Grid-Topic. Event Grid pusht es weiter.
  5. Event Hub puffert. Event Grid liefert an einen Event Hub. Der Event Hub ist nur über Private Endpoint erreichbar.
  6. Die Scan-Function liest. Eine zweite Function mit Event Hub Trigger liest das Ergebnis aus dem Hub. Der Host speichert ihren Fortschritt als Checkpoint im Storage.
  7. Entscheidung. Sauber: Die Datei wird freigegeben, z. B. in einen anderen Container verschoben. Malware: Die Datei wird gelöscht. Die Function ist idempotent, weil Events doppelt kommen können.

3. Beispiel: Event Hub Function für das Scan-Ergebnis (Java)

public class ScanResultFunction {
  @FunctionName("onScanResult")
  public void run(
      @EventHubTrigger(name = "events", eventHubName = "scan-results",
                       connection = "ScanHub", cardinality = Cardinality.MANY)
      List<String> events,
      final ExecutionContext ctx) {
    for (String e : events) {
      ScanEvent ev = Json.parse(e);   // Event-Grid-Event, Typ Microsoft.Security.MalwareScanningResult
      String result = ev.data().scanResultType();      // "No threats found" oder "Malicious"
      if ("No threats found".equals(result)) blobs.release(ev.data().blobUri());   // idempotent
      else                                   blobs.deleteIfExists(ev.data().blobUri());
      ctx.getLogger().info(result + " " + ev.data().blobUri());
    }
  }
}

  1. cardinality = MANY liefert einen Batch. Das ist bei Event Hubs schneller als Einzel-Events.
  2. Nach dem Batch schreibt der Host einen Checkpoint pro Partition in den Host Storage. Bei einem Absturz liest die nächste Instanz ab dem letzten Checkpoint. Darum kann ein Event doppelt kommen.
  3. Eine Exception stoppt den Event-Hub-Trigger nicht. Ohne Retry-Policy geht der Host weiter, und das Event ist verloren. Darum die Retry-Policy in host.json und eigenes Fehler-Handling.
  4. __fullyQualifiedNamespace und __accountName sind identitätsbasierte Verbindungen. Die Function nutzt ihre Managed Identity, nicht einen Schlüssel.
  5. always-ready=1 hält eine Instanz für diese Funktion warm. Das reduziert den Cold Start im Flex Plan.

4. Details, die Interviewer fragen

  1. Flex Consumption: Serverlos, nur Linux. Skaliert bis 1000 Instanzen. Speichergrössen 512 MB, 2048 MB oder 4096 MB. Unterstützt VNet-Integration, Private Endpoints und Always Ready. Keine Deployment Slots.
  2. Per-Function Scaling (Flex): Jede Funktion skaliert auf eigenen Instanzen. Ausnahmen: Alle HTTP-Trigger skalieren zusammen, ebenso Blob-Trigger (Event Grid) und Durable-Trigger.
  3. Premium Plan: Mindestens eine Instanz ist immer warm. Dazu vorgewärmte Instanzen für Spitzen. VNet, längere Laufzeiten, grössere Instanzen (bis 4 vCPU / 14 GB).
  4. Dedicated Plan: Läuft auf einem App Service Plan. Feste Kosten, manuelles oder regelbasiertes Scaling. Always On muss an sein.
  5. Legacy Consumption: Timeout Standard 5, max. 10 Minuten, max. 1,5 GB, kein VNet. Linux Consumption endet am 30.09.2028. Neue Apps: Flex.
  6. Timeouts: Flex, Premium, Dedicated: Standard 30 Minuten, kein festes Maximum. HTTP-Antworten aber immer max. 230 Sekunden.
  7. Cold Start: Eine neue Instanz muss Host, Worker und Code laden. Bei Java dauert das länger. Gegenmittel: Always Ready, Premium, kleinere Abhängigkeiten.
  8. Isolated Worker Model (.NET): Der Code läuft in einem eigenen Prozess, nicht im Host. Freie .NET-Version und eigene Middleware. Das In-Process-Modell hat seit 10.11.2026 keinen Support mehr.
  9. Java: Java läuft immer im eigenen Worker-Prozess. Funktionen werden mit Annotationen wie @FunctionName und @HttpTrigger beschrieben. Unterstützt sind LTS-Versionen wie Java 17 und 21.
  10. Blob Trigger: Der klassische Blob Trigger fragt den Container ab (Polling) und ist langsam. Besser ist source = EventGrid. Flex Consumption unterstützt nur die Event-Grid-Variante.
  11. Event Hub Trigger: Pro Partition liest höchstens eine Instanz. Mehr Instanzen als Partitionen bringen nichts. Fortschritt per Checkpoint im Host Storage.
  12. Service Bus Trigger: Nutzt Peek-Lock. Bei Erfolg schliesst der Host die Nachricht ab. Nach zu vielen Fehlversuchen landet sie in der Dead-Letter Queue.
  13. Queue Storage Trigger: Nach 5 Fehlversuchen kommt die Nachricht in die Poison Queue <name>-poison.
  14. Retry-Policies: In host.json oder per Annotation, fixedDelay oder exponentialBackoff. Unterstützt für Timer, Event Hubs, Kafka und Cosmos DB. Service Bus und Queues nutzen ihre eigenen Wiederholungen.
  15. Identitätsbasierte Verbindungen: Statt Connection String setzt man <name>__fullyQualifiedNamespace oder __serviceUri. Die Managed Identity braucht passende Data-Plane-Rollen.
  16. Key Vault References: Ein App Setting wie @Microsoft.KeyVault(SecretUri=…) lädt ein Secret aus Key Vault über die Managed Identity.
  17. Private Networking: Inbound über Private Endpoint, Outbound über VNet-Integration. Der Host Storage darf auch privat sein, braucht dann Private Endpoints für Blob, Queue und Table und private DNS-Zonen.
  18. Durable Functions – Bausteine: Client startet eine Orchestrierung. Orchestrator beschreibt den Ablauf. Activity macht die echte Arbeit. Entity hält kleinen Zustand.
  19. Durable Functions – Replay: Der Orchestrator speichert jeden Schritt als History (Event Sourcing). Nach jedem await läuft er von vorne und liest die Ergebnisse aus der History. Darum muss er deterministisch sein: kein now(), kein Zufall, kein I/O.
  20. Durable Functions – Muster: Chaining, Fan-out/Fan-in, Async HTTP API (202 plus Status-URL), Monitor (wiederholtes Prüfen mit Timer), Human Interaction (auf externes Event warten mit Timeout), Aggregator (Entities).
  21. Durable Functions – Backends: Standard ist Azure Storage. Alternativen: MSSQL und der verwaltete Durable Task Scheduler.
// Fan-out/Fan-in in Java (Durable Functions)
@FunctionName("ProcessBatch")
public List<String> orchestrate(@DurableOrchestrationTrigger(name = "ctx") TaskOrchestrationContext ctx) {
  List<String> files = ctx.getInput(List.class);
  List<Task<String>> tasks = files.stream()
      .map(f -> ctx.callActivity("ConvertToPdf", f, String.class)).toList();
  return ctx.allOf(tasks).await();     // wartet auf alle; Zustand liegt in der History
}

5. Vergleich

  • Flex Consumption: serverlos, bis null, bis 1000 Instanzen, VNet, Always Ready. Nur Linux, keine Slots.
  • Premium: immer warm, vorgewärmte Instanzen, VNet, Windows und Linux, Slots. Kosten auch ohne Last.
  • Dedicated: fester App Service Plan, planbare Kosten, kein Event-Scaling.
  • Container Apps: eigenes Image, KEDA-Scaling, neben anderen Containern. Keine Slots.
  • Legacy Consumption: nur noch für Windows-Abhängigkeiten. Kein VNet, kurze Timeouts.
  • Durable Functions vs Logic Apps: Durable = Workflow als Code, testbar, versioniert. Logic Apps = Low-Code-Designer mit vielen Konnektoren.
  • Durable Functions vs Queue-Kette: Durable gibt Status, Retry und Fan-in eingebaut. Eine Queue-Kette ist einfacher, aber Status und Fan-in baut man selbst.

6. In der Produktion

  1. Events verloren bei Event Hub Trigger: Die Function wirft, der Host checkpointet trotzdem weiter. Lösung: Retry-Policy, eigenes Try/Catch mit Ablage in eine Fehler-Queue, Monitoring der Fehler.
  2. Doppelte Verarbeitung: Nach Neustart liest eine Instanz ab dem letzten Checkpoint erneut. Lösung: Funktionen idempotent bauen, z. B. „löschen, wenn vorhanden“.
  3. Host startet nicht im privaten Netz: Storage ist privat, aber DNS-Zonen oder Private Endpoints für Queue/Table fehlen. Lösung: alle nötigen Endpoints und privatelink.*-DNS-Zonen anlegen.
  4. HTTP 502/Timeout nach 230 s: Lange Verarbeitung in einer HTTP-Function. Lösung: sofort 202 antworten, Arbeit per Queue oder Durable Functions.
  5. Skalierung bleibt hängen: Event Hub hat 4 Partitionen, also lesen max. 4 Instanzen. Lösung: mehr Partitionen beim Anlegen planen.
  6. Durable Orchestrator verhält sich zufällig: Code nutzt LocalDateTime.now() oder ruft HTTP direkt. Replay liefert andere Werte. Lösung: ctx.getCurrentInstant(), I/O nur in Activities.
  7. Orchestrierung bricht nach Deployment: Geänderter Orchestrator-Code passt nicht zur alten History. Lösung: laufende Instanzen auslaufen lassen oder neue Orchestrator-Version mit neuem Namen.
  8. Secrets im App Setting: Connection Strings mit Schlüsseln. Lösung: identitätsbasierte Verbindungen und Key Vault References.

7. Diagnose: Werkzeuge und Befehle

  • Application Insights: Ausführungen, Dauer, Fehler, Abhängigkeiten. KQL: requests | where success == false, traces | where message has "Executed".
  • Live Metrics: Instanzen und Durchsatz in Echtzeit, gut bei Skalierungsfragen.
  • Diagnose und Problembehandlung im Portal: Detektoren für Cold Start, Storage, Netz.
  • func start mit Azurite (lokaler Storage-Emulator): lokal testen.
  • az functionapp config appsettings list und az functionapp show: Einstellungen und Plan prüfen.
  • Event Hubs Metriken: Incoming/Outgoing Messages und Consumer-Lag pro Partition.
  • Durable: statusQueryGetUri der Instanz, die History-Tabellen im Storage, oder das Dashboard des Durable Task Scheduler.

8. Senior-Punkte

  1. Schnell antworten, später arbeiten. HTTP-Functions speichern und quittieren. Schwere Arbeit läuft event-getrieben dahinter.
  2. At-least-once ist die Regel. Jeder Trigger kann doppelt liefern. Idempotenz ist Pflicht, nicht Option.
  3. Partitionen begrenzen die Parallelität. Bei Event Hub Triggern entscheidet die Partitionszahl über das Maximum an Instanzen.
  4. Kein Schlüssel im Code oder Setting. Managed Identity, identitätsbasierte Verbindungen, Key Vault References.
  5. Private Functions brauchen saubere DNS-Planung. Die meisten Netzfehler sind fehlende Private-DNS-Zonen.
  6. Durable Functions nur, wenn man Zustand braucht. Für einen Schritt reicht ein einfacher Trigger. Determinismus und Versionierung kosten Disziplin.
  7. Plan nach Lastprofil: stossweise → Flex, dauernd und latenzkritisch → Premium oder Always Ready, eigenes Image → Container Apps.

10. Fallen

  • „Eine Function kann mehrere Trigger haben.“ → Falsch. Genau einen Trigger, aber viele Bindings.
  • „Event Hub Trigger wiederholt fehlgeschlagene Events automatisch.“ → Falsch. Ohne Retry-Policy checkpointet der Host weiter.
  • „Mehr Instanzen lesen einen Event Hub schneller.“ → Nur bis zur Partitionszahl.
  • „Durable Orchestrator darf HTTP aufrufen und die Uhrzeit lesen.“ → Falsch. Er muss deterministisch sein. I/O gehört in Activities.
  • „Flex Consumption ist einfach der neue Name für Consumption.“ → Falsch. Neuer Plan mit VNet, Always Ready, Per-Function Scaling und anderen Grenzen.
  • „Mit Premium gibt es keinen Timeout für HTTP.“ → Falsch. HTTP-Antworten sind immer auf 230 s begrenzt.
  • „Der klassische Blob Trigger reagiert sofort.“ → Falsch. Er pollt. Sofort reagiert die Event-Grid-Variante.

11. Fragen

Was ist Azure Functions?

Eine serverlose Plattform, die Code ausführt, wenn ein Trigger feuert. Bindings verbinden ihn mit anderen Diensten ohne SDK-Code.

Trigger vs Binding?

Der Trigger startet die Funktion, genau einer pro Funktion. Bindings lesen oder schreiben Daten, beliebig viele.

Welche Hosting Plans gibt es?

Flex Consumption, Premium, Dedicated, Container Apps und Legacy Consumption. Sie unterscheiden sich in Skalierung, Netz, Cold Start und Kosten.

Was ist Flex Consumption?

Der aktuelle serverlose Plan: Linux, bis 1000 Instanzen, wählbare Speichergrösse, VNet, Always Ready, Abrechnung pro Ausführung und Speicher.

Wann Premium statt Flex?

Bei Windows-Bedarf, Deployment Slots, sehr konstanter Last oder grösseren Instanzen. Premium hält immer mindestens eine Instanz warm.

Was ist ein Cold Start?

Die Verzögerung, bis eine neue Instanz Host, Worker und Code geladen hat. Bei Java spürbar. Gegenmittel: Always Ready, Premium.

Warum endet eine HTTP-Function nach 230 Sekunden?

Der Load Balancer vor App Service hat dieses Idle-Timeout. Lange Arbeit gehört in Durable Functions oder eine Queue.

Was ist das Isolated Worker Model?

.NET-Code läuft in einem eigenen Prozess statt im Host. Freie .NET-Version, eigene Middleware. In-Process hat seit 10.11.2026 keinen Support mehr.

Wie skaliert ein Event Hub Trigger?

Nach Rückstand pro Partition. Pro Partition liest höchstens eine Instanz, also max. so viele Instanzen wie Partitionen.

Was passiert bei einer Exception im Event Hub Trigger?

Ohne Retry-Policy checkpointet der Host weiter, das Event ist verloren. Mit Retry-Policy wiederholt er den Batch.

Was passiert bei einer Exception im Service Bus Trigger?

Die Nachricht wird wieder freigegeben und neu zugestellt. Nach MaxDeliveryCount kommt sie in die Dead-Letter Queue.

Warum den Blob Trigger mit Event Grid nutzen?

Er reagiert sofort statt zu pollen und skaliert besser. Im Flex Plan ist er die einzige Variante.

Wie verbindet sich eine Function ohne Secrets?

Mit Managed Identity und identitätsbasierten Verbindungen, z. B. Conn__fullyQualifiedNamespace. Dazu Data-Plane-Rollen vergeben.

Wie machen Sie eine Function privat?

Private Endpoint für eingehend, VNet-Integration für ausgehend. Storage, Key Vault und Event Hub ebenfalls über Private Endpoints mit privaten DNS-Zonen.

Was ist Durable Functions?

Eine Erweiterung für zustandsbehaftete Workflows als Code. Orchestrator steuert, Activities arbeiten, Zustand liegt in einer History.

Warum muss ein Orchestrator deterministisch sein?

Er wird bei jedem Schritt neu abgespielt (Replay). Andere Werte beim Replay würden die History brechen.

Welche Durable-Muster kennen Sie?

Chaining, Fan-out/Fan-in, Async HTTP API, Monitor, Human Interaction, Aggregator mit Entities.

Was ist das Async-HTTP-API-Muster?

Der Client bekommt sofort 202 und eine Status-URL. Er fragt den Status ab, bis das Ergebnis fertig ist.

Was ist der Host Storage und wofür?

Ein Storage Account in AzureWebJobsStorage. Er hält Leases, Checkpoints, Timer-Locks und Durable-Zustand.

Wie geht man mit doppelten Events um?

Funktionen idempotent bauen: gleiche Eingabe, gleiches Ergebnis. Z. B. deleteIfExists oder ein Check per ID.

Szenario: Die Upload-Function läuft in Timeouts, weil sie auf den Virenscan wartet. Was ändern Sie?

Nach dem Blob-Write sofort antworten. Das Scan-Ergebnis kommt als Event und eine zweite Function gibt frei oder löscht.

Szenario: Nach dem Umstellen auf private Endpoints startet die Function App nicht mehr. Wo suchen Sie?

Beim Host Storage: fehlende Private Endpoints für Blob/Queue/Table oder fehlende privatelink-DNS-Zonen. Dazu VNet-Integration und Rollen der Managed Identity prüfen.

Szenario: Der Event Hub hat Rückstand, aber es laufen nur 4 Instanzen. Warum?

Der Hub hat wohl 4 Partitionen. Mehr Instanzen bringen nichts. Lösung: Batchgrösse und Code optimieren oder einen Hub mit mehr Partitionen planen.
