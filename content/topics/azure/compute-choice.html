Compute: Functions vs Container Apps vs App Service vs AKS

Kern: Die Compute-Wahl ist eine Abwägung zwischen Kontrolle und Betriebsaufwand. Functions ist Code pro Event, Container Apps ist serverloses Kubernetes für Container, App Service ist Hosting für Web-Apps und APIs, AKS ist ein volles Kubernetes. Je mehr Kontrolle, desto mehr Arbeit liegt beim Team.

1. Wo sitzen die vier Dienste?

  1. Azure Functions: Functions führt eine Funktion pro Event aus, z. B. Blob hochgeladen. Beispiel: Upload-Prüfung im Flex Consumption Plan.
  2. Azure Container Apps: Container Apps führt beliebige Container aus und skaliert mit KEDA (Event-basierter Autoscaler). Beispiel: ein Java-Service mit Sidecar.
  3. Azure App Service: App Service hostet Web-Apps und APIs auf einem App Service Plan (feste VM-Instanzen). Beispiel: Spring-Boot-API mit Staging-Slot.
  4. Azure Kubernetes Service: AKS ist ein Kubernetes-Cluster mit von Azure verwalteter Control Plane. Beispiel: Spark, Lakehouse und viele Komponenten in einem Helm Chart.
  5. Die Achse: Von links nach rechts steigen Kontrolle und Betriebsaufwand. Die richtige Wahl ist die linkeste, die alle Anforderungen erfüllt.

2. Die Reise einer Entscheidung (die Geschichte zum Merken)

  1. Start mit der Last. Ein Team baut einen Upload-Dienst. Dateien kommen unregelmässig, nachts fast nie. Jede Datei löst kurze Arbeit aus. Das passt zu Functions: Trigger auf Blob oder Event Hub, Kosten nur bei Arbeit.
  2. Dann kommt ein Fremdsystem. Ein Messaging-Client braucht ein Zertifikat, einen langen Prozess und einen festen Container. Functions passt nicht. Braucht das Team die Kubernetes-API? Nein.
  3. Container Apps reicht. Der Client läuft als Sidecar neben dem Service. Ein Init Container registriert das Zertifikat einmal beim Start. Azure betreibt das Kubernetes darunter.
  4. Ein anderes Projekt braucht mehr. Spark, ein Katalog, Object Storage, eine Query Engine, Policies und Node Autoscaling. Das sind Operatoren, CRDs und ein Helm-Stack. Hier gewinnt AKS.
  5. Die klassische API bleibt. Eine Spring-Boot-Web-App mit stetiger Last, Staging-Slot und einfachem Deployment. Dafür reicht App Service.
  6. Am Ende zählt Betrieb. Jeder Schritt nach rechts bringt Upgrades, Patches und Bereitschaftsdienst. Das Team wählt die einfachste Option, die die Anforderung erfüllt.

3. Beispiel: Container App mit Sidecar und Init Container (Bicep)

resource app 'Microsoft.App/containerApps@2024-03-01' = {
  name: 'ca-person-service'
  location: 'switzerlandnorth'
  identity: { type: 'UserAssigned', userAssignedIdentities: { '${uami.id}': {} } }
  properties: {
    environmentId: cae.id                       // Environment im eigenen VNet
    configuration: {
      ingress: { external: false, targetPort: 8080 }   // nur intern erreichbar
      registries: [ { server: 'acrexample.azurecr.io', identity: uami.id } ]
    }
    template: {
      initContainers: [ {
        name: 'cert-register'                   // läuft einmal, vor den anderen
        image: 'acrexample.azurecr.io/msg-client-init:1.4'
        resources: { cpu: json('0.25'), memory: '0.5Gi' }
      } ]
      containers: [
        { name: 'app',     image: 'acrexample.azurecr.io/person-service:2.3'
          resources: { cpu: json('1.0'),  memory: '2Gi' } }
        { name: 'msg-client', image: 'acrexample.azurecr.io/msg-client:1.4'   // Sidecar
          resources: { cpu: json('0.5'),  memory: '1Gi' } }
      ]
      scale: { minReplicas: 1, maxReplicas: 5,
        rules: [ { name: 'http', http: { metadata: { concurrentRequests: '50' } } } ] }
    }
  }
}

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Namen und Images sind Beispiele. Ausgabe gekürzt.

  1. Init Container laufen vor den App-Containern und müssen erfolgreich enden. Danach starten app und msg-client.
  2. Beide Container in containers teilen sich ein Replica: gleiches Netz (localhost) und gleiche Lebensdauer. Das ist das Sidecar-Muster.
  3. Die CPU/Memory-Summe pro Replica muss eine erlaubte Kombination sein. Im Consumption-Profil gilt das Verhältnis 1 vCPU zu 2 GiB, hier 1,75 vCPU / 3,5 GiB.
  4. ingress.external: false macht die App nur im Environment bzw. VNet erreichbar.
  5. Jede Änderung am template erzeugt eine neue Revision. Änderungen an configuration nicht.
  6. minReplicas: 1 verhindert Cold Starts. Mit 0 skaliert die App auf null und kostet im Leerlauf fast nichts.

4. Details, die Interviewer fragen

  1. Functions-Pläne: Flex Consumption (serverlos, Linux, bis 1000 Instanzen, VNet, Always Ready), Premium (vorgewärmte Instanzen, immer min. 1), Dedicated (App Service Plan), Container Apps. Der alte Consumption Plan ist Legacy; Linux Consumption endet am 30.09.2028.
  2. Functions-Grenzen: HTTP-Antwort max. 230 Sekunden wegen des Load Balancers. Lange Arbeit gehört in Durable Functions oder in eine Queue.
  3. Container Apps intern: Kubernetes, KEDA, Envoy (Ingress) und optional Dapr. Das Team sieht die Kubernetes-API nicht.
  4. Container-Apps-Environment: Ein Environment ist die gemeinsame Grenze für Netz und Logs. Apps darin sehen sich intern. Es kann in einem eigenen VNet liegen.
  5. Workload Profiles: Consumption (serverlos, pro Sekunde) und Dedicated (feste Grössen, auch GPU) in einem Environment.
  6. Revisionen: Eine Revision ist eine unveränderliche Version der App. Mit mehreren aktiven Revisionen teilt man Traffic, z. B. 90/10 für Canary.
  7. Container Apps Jobs: Jobs laufen bis zum Ende statt dauernd: manuell, nach Zeitplan oder per Event (KEDA).
  8. App Service Plan: Der Plan sind die VMs. Alle Apps im Plan teilen sie. Man zahlt den Plan, auch ohne Last.
  9. Deployment Slots: Ein Slot ist eine zweite Live-App, z. B. staging. Swap tauscht ohne Downtime und erlaubt schnellen Rollback. Ab Standard-Tier.
  10. Always On: Bei App Service hält Always On die App warm. Ohne es wird sie nach Leerlauf entladen.
  11. AKS Control Plane: Azure betreibt API-Server und etcd. Tiers: Free (ohne SLA), Standard (mit SLA), Premium (mit Long Term Support).
  12. AKS-Betrieb: Das Team plant Kubernetes-Upgrades, Node-Image-Updates, Add-ons, Netz (CNI) und Policies. Kubernetes-Minor-Versionen haben ca. ein Jahr Support.
  13. AKS Automatic: Ein Modus mit vorkonfigurierten Nodes, Skalierung und Sicherheit. Weniger Betrieb, aber weniger Freiheit.
  14. Skalierung im Vergleich: Functions skaliert nach Events. Container Apps nach KEDA-Regeln. App Service nach Autoscale-Regeln (CPU, Zeitplan). AKS mit HPA/KEDA für Pods und Cluster Autoscaler oder Karpenter (Node Auto Provisioning) für Nodes.
  15. Kostenmodelle: Flex: Ausführungen plus GB-Sekunden plus Always Ready. Container Apps Consumption: vCPU- und GiB-Sekunden. App Service: Plan-Instanzstunden. AKS: VMs der Nodes plus Control-Plane-Tier.
  16. Netz: Alle vier können ins VNet. Private Endpoints (inbound) gibt es bei Functions Flex/Premium/Dedicated und App Service. Container Apps nutzt ein internes Environment.

5. Vergleich

  • Functions: Einheit = Funktion. Skaliert pro Event, bis null. Wenig Betrieb. Grenzen: Programmiermodell, Laufzeitlimits, Cold Start.
  • Container Apps: Einheit = Container. Skaliert mit KEDA, bis null. Wenig Betrieb. Grenzen: keine Kubernetes-API, keine CRDs oder Operatoren.
  • App Service: Einheit = Web-App auf einem Plan. Skaliert nach Regeln, nicht bis null. Wenig Betrieb. Grenzen: vor allem HTTP-Workloads, Kosten pro Plan auch im Leerlauf.
  • AKS: Einheit = Pod auf Nodes. Skaliert Pods und Nodes. Viel Betrieb. Stärke: volle Kontrolle, Helm, Operatoren, Portabilität.
  • Weitere: Container Instances für einzelne kurze Container ohne Orchestrierung. Batch für grosse parallele Rechenjobs. Logic Apps für Low-Code-Workflows.

6. In der Produktion

  1. Cold Start bei Scale to Zero: Erste Requests nach Leerlauf sind langsam, besonders bei Java. Lösung: Always Ready (Flex), minReplicas: 1 (Container Apps), Premium Plan.
  2. HTTP-Timeout 230 s bei Functions: Ein langer Export bricht ab. Lösung: 202 zurückgeben und im Hintergrund arbeiten (Durable Functions oder Queue).
  3. App Service Plan überladen: Viele Apps teilen einen Plan, eine App frisst Speicher. Lösung: laute Apps in eigene Pläne, Metriken pro Instanz prüfen.
  4. AKS veraltet: Kubernetes-Version läuft aus dem Support. Lösung: geplante Upgrades, Maintenance Windows, Auto-Upgrade-Channel, Upgrade zuerst in dev.
  5. Kosten durch Overprovisioning in AKS: Nodes laufen halb leer. Lösung: Requests/Limits messen, Node Autoscaling (Karpenter bzw. Node Auto Provisioning), Spot für Batch.
  6. Subnetz zu klein: Container Apps oder VNet-Integration finden keine IPs mehr. Lösung: Subnetz-Grössen nach Doku planen, bevor man skaliert.
  7. Sidecar startet nicht: Der Init Container scheitert, die Replica bleibt hängen. Lösung: Logs pro Container lesen, Init idempotent bauen.

7. Diagnose: Werkzeuge und Befehle

  • Application Insights: Requests, Abhängigkeiten, Cold Starts, Fehler über alle vier Dienste.
  • az functionapp show -n app -g rg --query "{plan:serverFarmId, state:state}": Plan und Status.
  • az containerapp revision list -n app -g rg -o table und az containerapp logs show --follow: Revisionen und Logs.
  • az webapp log tail -n app -g rg und Kudu (<app>.scm.azurewebsites.net): App-Service-Logs und Diagnose-Konsole.
  • az aks get-upgrades -n aks -g rg, kubectl top nodes, kubectl get events: Upgrade-Stand und Lage im Cluster.
  • Azure Advisor und Cost Management: unterausgelastete Pläne und Nodes finden.

8. Senior-Punkte

  1. Wähle die einfachste Plattform, die alle harten Anforderungen erfüllt. Kubernetes „für später“ kostet heute Betrieb.
  2. Betrieb ist der grösste Kostenpunkt, nicht der VM-Preis. AKS braucht Leute für Upgrades, Netz, Policies und Bereitschaft.
  3. Mischen ist normal. Functions für Events, Container Apps für Services, AKS für Plattformen mit Operatoren. Gemeinsam sind Netz, Identität und Monitoring.
  4. Lastprofil entscheidet die Kosten. Stossweise Last → serverlos. Stetige hohe Last → feste Instanzen oder Nodes sind oft günstiger.
  5. Container geben Portabilität. Ein Container läuft auf Container Apps, App Service und AKS. Der Wechsel bleibt offen.
  6. Cold Start ist eine Geschäftsfrage: Wie schlimm ist eine langsame erste Anfrage? Danach entscheidet man über Always Ready oder minReplicas.
  7. AKS lohnt sich, wenn viele Komponenten mit Operatoren, CRDs und Helm laufen, oder wenn Portabilität verlangt ist.

10. Fallen

  • „Container Apps ist nur ein kleines AKS.“ → Falsch. Es läuft auf Kubernetes, aber ohne Zugriff auf die Kubernetes-API, CRDs oder Operatoren.
  • „Serverless ist immer günstiger.“ → Falsch. Bei stetiger hoher Last sind feste Instanzen oft günstiger.
  • „AKS ist voll verwaltet.“ → Nur die Control Plane. Nodes, Upgrades, Add-ons und Workloads bleiben beim Team.
  • „Eine HTTP-Function kann 30 Minuten antworten.“ → Falsch. Die Funktion läuft so lange, aber die HTTP-Antwort ist nach 230 s weg.
  • „App Service skaliert auf null.“ → Falsch. Der Plan kostet immer mindestens eine Instanz.
  • „Für neue serverlose Functions nimmt man den Consumption Plan.“ → Falsch. Microsoft empfiehlt Flex Consumption. Consumption ist Legacy.

11. Fragen

Wie wählen Sie zwischen Functions, Container Apps, App Service und AKS?

Von einfach nach komplex prüfen: Event-Code → Functions, Container ohne K8s-API → Container Apps, klassische Web-App → App Service, Operatoren und volle Kontrolle → AKS.

Was ist Azure Container Apps?

Eine serverlose Plattform für Container auf Kubernetes mit KEDA, Envoy und optional Dapr. Azure betreibt den Cluster, das Team sieht nur Apps und Revisionen.

Wann ist AKS die richtige Wahl?

Wenn man die Kubernetes-API braucht: Operatoren, CRDs, Helm-Stacks, eigene CNI oder Policies, Portabilität. Und wenn das Team Kubernetes betreiben kann.

Wann App Service?

Für Web-Apps und APIs mit stetiger Last. Stärken: Deployment Slots, eingebaute Auth, einfache Skalierung, kein Container nötig.

Welche Functions-Pläne gibt es?

Flex Consumption, Premium, Dedicated, Container Apps und der Legacy-Consumption-Plan. Für neue serverlose Apps: Flex Consumption.

Was ist ein Deployment Slot?

Eine zweite Live-Instanz der App, z. B. staging. Nach dem Test tauscht ein Swap ohne Downtime; Rollback ist ein zweiter Swap.

Was ist eine Revision in Container Apps?

Eine unveränderliche Version der App. Sie entsteht bei Änderungen am Template. Mehrere Revisionen erlauben Traffic Splitting.

Was sind Sidecar und Init Container in Container Apps?

Sidecar: zweiter Container im gleichen Replica, gleiches Netz. Init Container: läuft vorher einmal bis zum Ende, z. B. für Zertifikate oder Migrationen.

Wie skaliert Container Apps?

Mit KEDA-Regeln: HTTP-Requests, TCP, CPU, Memory oder Event-Quellen wie Service Bus. Zwischen minReplicas und maxReplicas, auch bis null.

Was kostet AKS?

Die Node-VMs, Disks und Netz. Die Control Plane ist im Free-Tier gratis; Standard und Premium kosten pro Cluster-Stunde und bringen SLA.

Was verwaltet Azure bei AKS, was nicht?

Azure: API-Server, etcd, Scheduler. Team: Upgrade-Planung, Nodepools, Add-ons, Netz, Policies, Workloads.

Was ist ein Cold Start und wie vermeiden Sie ihn?

Verzögerung, wenn eine neue Instanz erst starten muss. Gegenmittel: Always Ready, Premium Plan, minReplicas ≥ 1, kleinere Images, schnellerer Start.

Kann Functions auf Container Apps laufen?

Ja. Dann ist die Function ein Container in einem Container-Apps-Environment und skaliert mit KEDA. Gut, wenn man ein eigenes Image braucht.

Wie bekommen Sie einen Dienst ins private Netz?

Outbound über VNet-Integration, inbound über Private Endpoint (Functions, App Service) oder internes Environment (Container Apps). AKS liegt ohnehin im VNet.

Container Apps Jobs vs Functions Timer?

Jobs passen für Container, die bis zum Ende laufen, auch lange. Timer-Functions passen für kurzen Code nach Zeitplan.

Was sind Workload Profiles?

Rechenprofile im Container-Apps-Environment: Consumption (serverlos) oder Dedicated (feste VM-Grössen, auch GPU).

Warum ist Serverless nicht immer günstiger?

Man zahlt pro Nutzung. Bei Dauerlast summiert sich das und liegt oft über festen Instanzen.

Wie portabel sind die Optionen?

Container laufen überall. AKS ist am portabelsten. Functions-Code ist an Trigger und Bindings gebunden.

Szenario: Ein Team will für drei kleine REST-Services AKS. Was raten Sie?

Erst fragen, ob sie die K8s-API brauchen. Wenn nicht: Container Apps oder App Service. AKS bringt Upgrades und Betrieb, der sich hier nicht lohnt.

Szenario: Eine Java-Function antwortet nach Leerlauf erst nach Sekunden. Was tun Sie?

Cold Start. Always-Ready-Instanzen im Flex Plan oder Premium Plan. Dazu Startzeit messen und Abhängigkeiten beim Start reduzieren.

Szenario: Ein Fremdsystem verlangt einen dauerhaft laufenden Client mit Zertifikat neben Ihrem Service. Wo deployen Sie ihn?

Als Sidecar in derselben Container App. Ein Init Container registriert das Zertifikat einmal. Kein AKS nötig.
