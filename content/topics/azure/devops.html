Azure DevOps: Pipelines, Repos, Environments

Kern: Azure DevOps ist eine Plattform für Code, Builds und Deployments. Azure Repos hält den Git-Code, Azure Pipelines baut und deployt mit YAML, und Environments mit Approvals und Checks schützen Produktion. Service Connections verbinden sicher mit Azure, so wird jede Änderung reproduzierbar, geprüft und nachvollziehbar.

Antwort-Muster

Frage: Wie baut und deployt eine Azure-DevOps-Pipeline sicher nach Produktion?

  1. Mechanismus: Eine YAML-Pipeline baut und testet den Commit. Ein Deployment Job läuft gegen ein Environment mit Approvals und Checks.
  2. Zahl: Es gibt 3 Variablen-Syntaxen und 3 Deployment-Strategien. Das ist die Basis für Templates und Rollouts.
  3. Trade-off: Microsoft-hosted Agents sind wartungsfrei, erreichen aber keine privaten Netze. Self-hosted Agents im VNet brauchen Betrieb.
  4. Produktion: Ich nutze Workload Identity Federation statt Secret und gebe jeder Service Connection nur eine minimale Rolle. Das Quality Gate muss den Build blockieren.

1. Die Reise eines Commits

  1. Pull Request. Ein Entwickler öffnet einen PR auf main. Die Branch Policy verlangt Reviewer und eine erfolgreiche Build Validation. Ohne beides geht kein Merge.
  2. Build-Stage. Ein Agent holt den Code. Er baut mit einem Multi-Stage Dockerfile: Build-Image mit SDK, Laufzeit-Image schlank. Unit- und Integrationstests laufen.
  3. SonarQube. Die SonarQube-Tasks analysieren den Code. Das Quality Gate prüft z. B. Coverage auf neuem Code und neue Bugs. Ist es rot, stoppt die Pipeline, und der PR bleibt blockiert.
  4. Push in die ACR. Das Image bekommt einen eindeutigen Tag, z. B. die Build-ID. Der Push läuft über eine Service Connection.
  5. Deploy dev. Ein Deployment Job zielt auf das Environment dev. Dort gibt es keine Freigabe.
  6. Environment prod prüft. Bevor die Stage startet, laufen die Checks von prod: Freigabe durch eine Gruppe, nur von main, nur in Bürozeiten. Die Pipeline wartet.
  7. Deploy prod. Nach der Freigabe deployt der Job. Entweder direkt mit Helm über eine Service Connection mit Workload Identity Federation. Oder GitOps: Die Pipeline ändert den Image-Tag im Git, und ArgoCD synchronisiert.

2. Aufbau

  1. Organization und Project: Die Organization ist die oberste Einheit, an Entra ID gebunden. Ein Project gruppiert Repos, Pipelines und Rechte.
  2. Repos: Git-Repositories mit Pull Requests. Branch Policies schützen main.
  3. Pipelines: Eine YAML-Datei im Repo beschreibt Build und Deployment. Beispiel: azure-pipelines.yml.
  4. Library: Variable Groups teilen Variablen zwischen Pipelines. Eine Gruppe kann an einen Key Vault gebunden sein.
  5. Agent Pools: Ein Agent ist die Maschine, die einen Job ausführt. Microsoft-hosted, self-hosted oder Managed DevOps Pools.
  6. Service Connections: Gespeicherte, geschützte Verbindungen zu Azure, ACR oder SonarQube. Für Azure mit Workload Identity Federation, ohne Secret.
  7. Environments: Ein Ziel wie prod. Daran hängen Approvals und Checks und die Deployment-Historie.

3. Details, die Interviewer fragen

  1. YAML vs Classic: YAML Pipelines liegen versioniert im Repo und laufen durch Reviews. Classic Build- und Release-Pipelines klickt man im UI. Für Neues nimmt man YAML.
  2. Trigger: trigger: startet CI bei Push. schedules: startet nach Cron. resources.pipelines startet nach einer anderen Pipeline. Achtung: pr: gilt nur für GitHub und Bitbucket. Bei Azure Repos macht das die Branch Policy.
  3. Template Expression: ${{ variables.x }} wirkt beim Kompilieren. Man nutzt es für Bedingungen und Schleifen im YAML.
  4. Runtime Expression: $[ variables.x ] wirkt bei Laufzeitbeginn. Man nutzt es für Bedingungen.
  5. Macro Syntax: $(x) wirkt direkt vor dem Task. Es ist die häufigste der drei Syntaxen.
  6. Parameters vs Variables: Parameters sind typisiert und zur Kompilierzeit fix. Sie können die Struktur steuern. Variables sind Strings und können sich zur Laufzeit ändern.
  7. Templates: Es gibt Step-, Job-, Stage- und Variablen-Templates. template: fügt ein. extends: lässt die Pipeline von einem zentralen Template erben. Mit dem Check Required Template erzwingt man extends für ein Environment.
  8. Outputs zwischen Jobs: Ein Step setzt ##vso[task.setvariable variable=x;isOutput=true]. Ein anderer Job liest es über dependencies.Job.outputs['step.x'].
  9. Service Connection mit Workload Identity Federation: Azure DevOps stellt ein OIDC-Token aus. Entra ID vertraut ihm über eine Federated Credential auf einer App Registration oder Managed Identity. Es gibt kein Secret und keine Rotation wegen Ablauf.
  10. Rechte auf Service Connections: Pro Connection legt man fest, welche Pipelines sie nutzen dürfen. „Grant access to all pipelines“ ist für Produktion falsch. Die Azure-Rolle der Identity hält man minimal, z. B. nur auf eine Ressourcengruppe.
  11. Environments: Ein Environment ist ein logisches Ziel mit Historie. Ressourcen wie Kubernetes-Namespaces oder VMs können darin registriert sein.
  12. Approvals und Checks: Man konfiguriert sie am Environment, an der Service Connection oder am Agent Pool, nicht im YAML. Es gibt Approval, Branch Control, Business Hours, Required Template und Exclusive Lock. Dazu kommen Azure Function/REST und Query Azure Monitor Alerts.
  13. Deployment-Strategien: Es gibt runOnce, rolling (VMs) und canary. Jede hat Hooks wie preDeploy, deploy, routeTraffic, postRouteTraffic und on: failure.
  14. Variable Groups und Key Vault: Eine Gruppe kann an einen Key Vault gebunden sein. Nur Secrets werden gelesen, immer die neueste Version. Die Identity der Service Connection braucht Get und List. Bei RBAC braucht sie die Rolle Key Vault Secrets User. Eine Alternative ist der Task AzureKeyVault@2.
  15. Secret-Variablen: Sie werden im Log maskiert. Sie sind nicht automatisch als Umgebungsvariable da. Bei PRs aus Forks sind sie standardmässig nicht verfügbar.
  16. Agents: Microsoft-hosted Agents sind jedes Mal frisch und wartungsfrei. Sie haben aber keinen Zugang zu privaten Netzen. Self-hosted Agents oder Managed DevOps Pools laufen im eigenen VNet. Sie erreichen private Endpoints.
  17. Branch Policies: Dazu gehören Mindestanzahl Reviewer, verlinkte Work Items und gelöste Kommentare. Dazu kommen Build Validation und externe Status Checks wie das SonarQube-Gate.
  18. SonarQube-Tasks: Es gibt SonarQubePrepare, SonarQubeAnalyze und SonarQubePublish. Bei Maven und Gradle läuft die Analyse im Build-Task. Analyze entfällt dann. Für PR-Decoration braucht SonarQube die Azure-DevOps-Integration.

4. Fallen

  • „Approvals schreibe ich ins YAML.“ → Falsch. Approvals und Checks hängen am Environment oder an der Service Connection.
  • „pr: im YAML startet PR-Builds in Azure Repos.“ → Falsch. Bei Azure Repos braucht man eine Branch Policy mit Build Validation.
  • „Secret-Variablen sind in Scripts automatisch da.“ → Falsch. Man muss sie per env: explizit mappen.
  • „SonarQubePublish lässt die Pipeline bei rotem Gate scheitern.“ → Falsch. Es zeigt nur den Status. Blockieren mit sonar.qualitygate.wait=true oder Status Check als Branch Policy.
  • „$(var) und ${{ var }} sind dasselbe.“ → Falsch. ${{ }} wirkt beim Kompilieren, $( ) zur Laufzeit vor dem Task.
  • „Eine Key-Vault-Variable-Group liest alle Versionen und Keys.“ → Falsch. Nur Secrets und nur die neueste Version.
  • „Microsoft-hosted Agents erreichen meine Private Endpoints.“ → Falsch. Dafür braucht es Agents im eigenen VNet.

5. Selbsttest

Warum?

Warum YAML statt Classic?

YAML ist versioniert, im Review und wiederverwendbar über Templates. Classic ist im UI geklickt und schwer nachvollziehbar.

Warum Approvals nicht im YAML?

Sonst könnte jeder sie mit einem Commit entfernen. Am Environment liegen sie ausserhalb der Kontrolle der Pipeline-Autoren.

Warum Build once, deploy many?

Ein Image pro Commit mit unveränderlichem Tag wird durch alle Stages befördert. Nie pro Umgebung neu bauen, sonst testet man nicht das, was man ausliefert.

Wie innen?

Was ist Azure DevOps?

Eine Plattform mit Repos, Pipelines, Boards, Artifacts und Test Plans. Sie deckt Code, Build, Deployment und Planung ab.

Wie ist eine YAML-Pipeline aufgebaut?

Pipeline → Stages → Jobs → Steps. Steps sind Tasks oder Scripts. Jeder Job läuft auf einem Agent.

Was ist der Unterschied zwischen Stage und Job?

Eine Stage ist eine logische Phase, z. B. Build oder Deploy Prod. Ein Job ist eine Einheit, die auf einem Agent läuft. Stages laufen meist nacheinander, Jobs können parallel laufen.

Was ist eine Service Connection?

Eine gespeicherte Verbindung zu einem externen System wie Azure, ACR oder SonarQube. Pipelines nutzen sie, ohne Zugangsdaten zu sehen.

Was ist Workload Identity Federation bei Service Connections?

Azure DevOps stellt ein OIDC-Token aus. Entra ID vertraut ihm über eine Federated Credential. Es gibt kein Secret, das abläuft oder leakt.

Was ist ein Environment?

Ein logisches Deployment-Ziel wie dev oder prod. Es hat eine Historie und trägt Approvals und Checks.

Welche Checks gibt es?

Approval, Branch Control, Business Hours, Required Template, Exclusive Lock, Azure Function, REST API und Azure-Monitor-Alerts.

Was ist ein Deployment Job?

Ein Job mit deployment: und environment:. Er aktiviert die Checks, schreibt die Historie und unterstützt Strategien wie runOnce, rolling und canary.

Was sind Branch Policies?

Regeln für geschützte Branches: Reviewer, verlinkte Work Items, gelöste Kommentare, Build Validation, Status Checks.

Wie geben Sie Werte von einem Job an den nächsten?

Mit einer Output-Variable (setvariable ... isOutput=true) und dependencies.Job.outputs['step.name'] im nächsten Job.

Zahlen

Was bedeuten ${{ }}, $[ ] und $( )?

Kompilierzeit, Laufzeitbeginn und direkt vor dem Task. ${{ }} kann die YAML-Struktur ändern, die anderen nicht.

Welche Deployment-Strategien gibt es?

Drei: runOnce, rolling (für VMs) und canary. Jede hat Hooks wie preDeploy, deploy, routeTraffic und on: failure.

Welche SonarQube-Tasks gibt es?

Drei: SonarQubePrepare, SonarQubeAnalyze und SonarQubePublish. Bei Maven und Gradle entfällt Analyze.

Vergleich

Parameters oder Variables?

Parameters sind typisiert und zur Kompilierzeit fix. Variables sind Strings und zur Laufzeit veränderbar. Für Struktur und Templates: Parameters.

Microsoft-hosted oder self-hosted Agent?

Microsoft-hosted ist frisch und wartungsfrei, aber ohne privates Netz. Self-hosted oder Managed DevOps Pools für private Endpoints, eigene Tools oder grosse Caches.

Push-Deployment oder GitOps?

GitOps: Pipeline schreibt nur in Git, ArgoCD zieht. Keine Cluster-Rechte in der Pipeline, Drift wird korrigiert, Rollback per git revert.

Azure Pipelines vs GitHub Actions?

Pipelines hat starke Environments, Checks und Variable Groups für Enterprise. Actions ist näher am Code auf GitHub. Beide unterstützen OIDC zu Azure.

Produktion

Wie schützen Sie Secrets in Pipelines?

Secret-Variablen, maskiert im Log. Nicht ausgeben, nicht an Fork-PRs geben, nur explizit mappen. Besser noch: WIF und Managed Identity statt Secrets.

Wie lässt das Quality Gate die Pipeline scheitern?

Mit sonar.qualitygate.wait=true wartet der Scanner auf das Gate und scheitert bei Rot. Zusätzlich als Status Check in der Branch Policy.

Szenario: Alle Deployments scheitern seit heute mit „AADSTS7000222: client secret expired“. Was tun Sie?

Kurzfristig das Secret erneuern. Dann die Service Connection auf Workload Identity Federation umstellen, damit es kein Ablaufdatum mehr gibt.

Szenario: Ein Team deployt in Produktion ohne Freigabe. Wie verhindern Sie das?

Checks auch an die Prod-Service-Connection hängen, nicht nur ans Environment. Pipeline-Berechtigungen einschränken, Required Template und Branch Control nutzen.

Szenario: Der Deploy-Job erreicht den privaten AKS-API-Server nicht. Was ist die Lösung?

Microsoft-hosted Agents sind ausserhalb des VNets. Lösung: Managed DevOps Pool oder self-hosted Agent im VNet, oder GitOps mit ArgoCD im Cluster.

Design

Wie verwenden Sie Templates?

Gemeinsame Steps, Jobs oder Stages in eigene Dateien, mit typisierten Parametern. extends für einen verpflichtenden Rahmen über alle Pipelines.

Wie binden Sie Key Vault an?

Variable Group an Key Vault linken oder Task AzureKeyVault@2. Die Identity braucht Leserechte auf Secrets. Secrets per env: an Scripts geben.

Wie integrieren Sie SonarQube?

SonarQubePrepare vor dem Build, SonarQubeAnalyze danach, SonarQubePublish für den Status. Bei Maven/Gradle läuft die Analyse im Build-Task.

Warum ein Multi-Stage Dockerfile?

Build-Tools bleiben in der ersten Stage. Das Laufzeit-Image ist klein und hat weniger Angriffsfläche. Gut cachebar im CI.

Mehr

Gerüst

  • Warum? Jede Änderung ist reproduzierbar, geprüft und nachvollziehbar. Pipelines sind Code im Repo.
  • Wie innen? Approvals und Checks hängen an Environment oder Service Connection, nicht im YAML. Eine Service Connection mit WIF nutzt ein OIDC-Token statt Secret.
  • Zahlen 3 Variablen-Syntaxen: Template Expression, Runtime Expression, Macro. 3 Deployment-Strategien. 3 SonarQube-Tasks.
  • Vergleich Azure Pipelines hat starke Environments und Checks, Actions ist näher am Code auf GitHub. Push-Deploy braucht Cluster-Rechte, GitOps nicht. Microsoft-hosted Agents erreichen keine privaten Netze.
  • Produktion Abgelaufenes Service-Connection-Secret, Agent ohne privates Netz, Secret im Log, Quality Gate ohne Wirkung.
  • Design Kein Secret in der Pipeline. Build once, deploy many. Eine Service Connection pro Umgebung mit minimaler Rolle.

Beispiel: Multi-Stage-YAML mit Template, SonarQube und Environment

# azure-pipelines.yml
trigger:
  branches: { include: [ main ] }
# PR-Builds für Azure Repos kommen über die Branch Policy (Build Validation), nicht über "pr:"

variables:
  - group: match-prod-kv          # Variable Group, an Key Vault gebunden
  - name: imageTag
    value: $(Build.BuildId)

stages:
- stage: Build
  jobs:
  - job: BuildTest
    pool: { vmImage: ubuntu-latest }
    steps:
    - task: SonarQubePrepare@8
      inputs:
        SonarQube: sc-sonarqube
        scannerMode: cli
        configMode: manual
        cliProjectKey: match-api
        extraProperties: |
          sonar.qualitygate.wait=true
    - script: ./build.sh && ./test.sh
      displayName: Build und Tests
    - task: SonarQubeAnalyze@8      # bricht bei rotem Gate ab (qualitygate.wait)
    - task: SonarQubePublish@8
      inputs: { pollingTimeoutSec: '300' }
    - template: templates/docker-build-push.yml   # Step-Template
      parameters:
        repository: match/api
        tag: $(imageTag)

- stage: DeployProd
  dependsOn: Build
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: Deploy
    environment: match-prod        # Approvals + Checks hängen hier
    pool: { vmImage: ubuntu-latest }
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureCLI@2
            inputs:
              azureSubscription: sc-azure-prod-wif   # Workload Identity Federation
              scriptType: bash
              scriptLocation: inlineScript
              inlineScript: |
                az aks get-credentials -g rg-match -n aks-match
                helm upgrade --install match ./chart --set image.tag=$(imageTag)
            env:
              DB_PASSWORD: $(db-password)   # Secret aus Key Vault, explizit gemappt
# templates/docker-build-push.yml
parameters:
- name: repository
  type: string
- name: tag
  type: string
steps:
- task: Docker@2
  inputs:
    containerRegistry: sc-acr-match
    repository: ${{ parameters.repository }}
    command: buildAndPush
    Dockerfile: Dockerfile          # Multi-Stage: build → runtime
    tags: ${{ parameters.tag }}

  1. Hierarchie: Pipeline → Stages → Jobs → Steps. Stages laufen standardmässig nacheinander. Jobs einer Stage können parallel laufen. Jeder Job läuft auf einem eigenen Agent.
  2. Variable Group mit Key Vault: $(db-password) kommt zur Laufzeit aus dem Key Vault. Secrets landen nicht automatisch als Umgebungsvariable. Darum das explizite env:-Mapping.
  3. SonarQube: Prepare vor dem Build, Analyze danach, Publish zeigt das Gate im Run. sonar.qualitygate.wait=true lässt den Scanner auf das Gate warten und bei Rot fehlschlagen.
  4. Template: ${{ parameters.repository }} wird beim Kompilieren der Pipeline eingesetzt. Alle Teams nutzen denselben Docker-Schritt.
  5. Deployment Job: deployment: mit environment: aktiviert die Checks des Environments und schreibt die Deployment-Historie. runOnce ist die einfachste Strategie.
  6. Service Connection: sc-azure-prod-wif nutzt Workload Identity Federation. Es gibt kein Client Secret, das abläuft oder leakt.

Vergleich

  • Azure Pipelines vs GitHub Actions: Pipelines hat starke Environments, Checks und Variable Groups für Enterprise. Actions ist näher am Code auf GitHub und hat ein grosses Marketplace-Ökosystem. Beide unterstützen OIDC zu Azure.
  • Azure Pipelines vs Jenkins: Pipelines ist SaaS, ohne Server-Betrieb, mit integriertem RBAC. Jenkins ist flexibel, aber Plugins und Server muss man selbst pflegen.
  • Push-Deploy vs GitOps (ArgoCD): Push: Die Pipeline braucht Cluster-Rechte. GitOps: Der Cluster zieht aus Git, die Pipeline braucht nur Git-Schreibrechte. Drift wird automatisch korrigiert.
  • Service Connection mit Secret vs WIF: Secret läuft ab und kann leaken. WIF hat keine Secrets und kurzlebige Tokens.
  • Variable Group vs AzureKeyVault-Task: Variable Group ist zentral für viele Pipelines. Der Task ist pro Pipeline flexibler, z. B. mit Filter auf Secret-Namen.
  • Template template: vs extends:: template: fügt Bausteine ein. extends: gibt den Rahmen vor und ist für Governance gedacht.

In der Produktion

  1. Service Connection läuft ab: Das Client Secret einer alten Connection ist abgelaufen. Alle Deployments schlagen fehl. Lösung: auf Workload Identity Federation umstellen.
  2. Pipeline kommt nicht ins private Netz: Microsoft-hosted Agents erreichen privaten AKS-API-Server oder Key Vault nicht. Lösung: Managed DevOps Pools oder self-hosted Agents im VNet, oder GitOps.
  3. Secret im Log: Ein Script schreibt ein Secret transformiert (z. B. Base64) ins Log. Die Maskierung greift nicht. Lösung: nie Secrets ausgeben, Secrets nur per env: geben.
  4. Quality Gate wird ignoriert: SonarQubePublish zeigt Rot, aber die Pipeline ist grün. Lösung: sonar.qualitygate.wait=true oder Status Check als Branch Policy.
  5. Flaky Integrationstests: Ein Testcontainer wird im Build-Agent OOM-gekillt. Lösung: Speicher begrenzen, schwere Tests serialisieren, schnell scheitern.
  6. Jemand umgeht die Prod-Freigabe: Eine neue Pipeline deployt mit derselben Service Connection ohne Environment. Lösung: Checks auch an die Service Connection hängen, Pipeline-Berechtigung einschränken, Required Template.
  7. Langsame Builds: Jeder Build lädt alle Abhängigkeiten neu. Lösung: Cache@2, Docker-Layer-Reihenfolge im Multi-Stage Dockerfile, kleinere Images.

Diagnose: Werkzeuge und Befehle

  • Variable system.debug: true: ausführliche Logs für jeden Task.
  • „Download full YAML“ im Run: zeigt die Pipeline nach dem Einsetzen aller Templates.
  • Checks-Ansicht im Run: welcher Check wartet oder fehlschlägt.
  • az devops configure --defaults organization=https://dev.azure.com/<org> project=<p>, dann az pipelines runs list und az pipelines runs show --id <id> (Extension azure-devops).
  • az pipelines variable-group list: welche Variable Groups es gibt und ob sie an Key Vault gebunden sind.
  • Service-Connection-Seite → „Usage history“: welche Pipeline sie wann genutzt hat.
  • Audit Log der Organization: wer Rechte, Policies oder Connections geändert hat.
  • Entra-Sign-in-Logs der Service-Principal-Anmeldungen: warum ein WIF-Token abgelehnt wurde (Issuer/Subject).

Senior-Punkte

  1. Pipelines sind Code. YAML im Repo, Reviews, Templates für gemeinsame Bausteine. Keine geklickten Classic-Releases für Neues.
  2. Kein Secret in der Pipeline, wenn es ohne geht. WIF für Azure, Key Vault für den Rest, Managed Identity für Apps.
  3. Governance gehört an Ressourcen, nicht ins YAML. Approvals und Checks auf Environment und Service Connection. Sonst kann jeder sie im YAML entfernen.
  4. Quality Gates müssen blockieren. Ein Gate, das nur anzeigt, ändert nichts. Regeln nie pauschal abschalten, Ausnahmen begründen und dokumentieren.
  5. Build once, deploy many. Ein Image pro Commit, unveränderlicher Tag, durch alle Stages befördert. Nie pro Umgebung neu bauen.
  6. GitOps trennt Build und Deploy. Die Pipeline baut und schreibt in Git. ArgoCD deployt. Rollback ist ein git revert.
  7. Least Privilege für Service Connections: eine Connection pro Umgebung, Rolle nur auf die Ressourcengruppe, nur für bestimmte Pipelines freigegeben.
