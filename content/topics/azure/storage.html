Blob Storage: Tiers, SAS, Lifecycle, ADLS Gen2

Azure · Tier 1 · Quellen: Microsoft Learn – Blob Storage Introduction, Access tiers for blob data, Azure Storage redundancy, Grant limited access with SAS / Create a user delegation SAS, Lifecycle management overview, Azure Data Lake Storage hierarchical namespace, Introduction to Defender for Storage malware scanning, Prevent Shared Key authorization

Kern: Azure Blob Storage ist ein Object Store für unstrukturierte Daten in einem Storage Account. Er löst das Problem, Dateien billig, sicher und fast unbegrenzt zu speichern. Kosten steuert man mit Access Tiers und Lifecycle-Regeln, Zugriff mit Entra ID, RBAC und SAS.

1. Wo sitzt Blob Storage?

  1. Storage Account: die Hülle mit Name, Region, Redundanz und Netzwerkregeln. Beispiel: stdigiupload in Switzerland North.
  2. Endpoint: jeder Dienst hat eine URL. Blob: https://<account>.blob.core.windows.net. Mit HNS zusätzlich dfs.core.windows.net.
  3. Container: eine Gruppe von Blobs, ähnlich einem Bucket. Zugriffsrechte lassen sich pro Container vergeben.
  4. Blob: das eigentliche Objekt. Es gibt drei Typen: Block, Append und Page.
  5. Access Tier: die Preisklasse eines Block Blobs. Sie ändert Speicher- und Zugriffskosten, nicht die API.
  6. Auth: Entra ID mit RBAC-Rollen, SAS-Tokens oder Account Key (Shared Key).

2. Die Reise eines Uploads (die Geschichte zum Merken)

  1. Token holen: Die Upload-Function hat eine Managed Identity, also eine Identität ohne Passwort. Sie holt ein Entra-Token für https://storage.azure.com/. Sie erreicht den Account über einen Private Endpoint (private IP im VNet).
  2. Blob schreiben: Das SDK lädt grosse Dateien in Blöcken hoch (Put Block). Am Ende macht Put Block List den Blob sichtbar und atomar. Die Function antwortet dem Client sofort danach.
  3. Event: Storage meldet Microsoft.Storage.BlobCreated an ein Event Grid System Topic. Defender legt dieses Topic beim Aktivieren selbst an.
  4. Scan: Defender for Storage liest den Blob und scannt ihn mit Microsoft Defender Antivirus. Das läuft in derselben Region. Blobs bis 50 GB sind möglich.
  5. Ergebnis: Defender schreibt den Blob-Index-Tag Malware Scanning scan result (z. B. No threats found oder Malicious). Optional kommt ein Event über ein eigenes Event Grid Custom Topic.
  6. Reagieren: Eine zweite Function bekommt das Ergebnis, z. B. über Event Hub. Sie entscheidet allein auf Basis des Events, nicht des Tags.
  7. Freigeben oder löschen: Sauber: Blob in einen freigegebenen Container kopieren. Schädlich: löschen. Danach verschiebt eine Lifecycle Policy alte Dateien nach Cool oder Cold.

3. Beispiel: sicherer Account, Lifecycle und User Delegation SAS

// storage.bicep – Account ohne Shared Key, ohne Public Access
resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stdemoupload'
  location: 'switzerlandnorth'
  sku: { name: 'Standard_ZRS' }
  kind: 'StorageV2'
  properties: {
    accessTier: 'Hot'
    isHnsEnabled: false
    allowSharedKeyAccess: false        // nur Entra ID, keine Account-Key-SAS
    allowBlobPublicAccess: false
    publicNetworkAccess: 'Disabled'    // nur Private Endpoint
    minimumTlsVersion: 'TLS1_2'
  }
}

resource lifecycle 'Microsoft.Storage/storageAccounts/managementPolicies@2023-05-01' = {
  name: 'default'
  parent: st
  properties: { policy: { rules: [ {
    name: 'clean-to-cold'
    enabled: true
    type: 'Lifecycle'
    definition: {
      filters: { blobTypes: [ 'blockBlob' ], prefixMatch: [ 'clean/' ] }
      actions: { baseBlob: {
        tierToCool: { daysAfterModificationGreaterThan: 30 }
        tierToCold: { daysAfterModificationGreaterThan: 90 }
        delete:     { daysAfterModificationGreaterThan: 365 }
      } }
    } } ] } }
}
$ az storage blob generate-sas --account-name stdemoupload \
    --container-name clean --name report.pdf --permissions r \
    --expiry 2026-11-24T18:00Z --https-only \
    --auth-mode login --as-user --full-uri

"https://stdemoupload.blob.core.windows.net/clean/report.pdf?skoid=…&sktid=…
 &skt=2026-11-24T12%3A00%3A00Z&ske=2026-11-24T18%3A00%3A00Z&sks=b&skv=2024-11-04
 &sv=2024-11-04&st=…&se=2026-11-24T18%3A00%3A00Z&sr=b&sp=r&spr=https&sig=…"

$ az storage account show -n stdemoupload --query \
    "{sku:sku.name, tier:accessTier, hns:isHnsEnabled, sharedKey:allowSharedKeyAccess, net:publicNetworkAccess}"
{ "sku": "Standard_ZRS", "tier": "Hot", "hns": false, "sharedKey": false, "net": "Disabled" }

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Hier gibt es keine Azure CLI und keinen Account.

  1. allowSharedKeyAccess: false sperrt Account Key, Account SAS und Service SAS. Nur Entra-Tokens und User Delegation SAS funktionieren noch.
  2. --as-user --auth-mode login signiert die SAS mit einem User Delegation Key. Die Felder skoid, sktid, skt, ske zeigen das. Der Key gilt höchstens 7 Tage.
  3. sr=b heisst Blob, sp=r nur Lesen, spr=https nur HTTPS. Wenige Rechte, kurze Laufzeit.
  4. Der Aufrufer braucht die Aktion generateUserDelegationKey (z. B. in Storage Blob Delegator) und Leserechte auf den Blob. Die SAS gibt nie mehr Rechte als der Aufrufer hat.
  5. Die Lifecycle Policy wirkt nur auf clean/. Sie läuft etwa einmal pro Tag, nicht sofort.

4. Details, die Interviewer fragen

  1. Block Blob: besteht aus Blöcken, die erst Put Block List verbindet. Bis 50 000 Blöcke, maximal ca. 190,7 TiB. Standard für Dateien, Bilder, Parquet.
  2. Append Blob: erlaubt nur Anhängen am Ende (Append Block). Gut für Logs. Kein Tier-Wechsel möglich.
  3. Page Blob: besteht aus 512-Byte-Seiten mit wahlfreiem Schreiben. Bis 8 TiB. Basis für alte unmanaged VM-Disks.
  4. Access Tiers: Hot (oft genutzt), Cool (min. 30 Tage), Cold (min. 90 Tage), Archive (min. 180 Tage, offline). Kälter heisst: Speicher billiger, Zugriff teurer.
  5. Early Deletion: Wer vor der Mindestdauer löscht, überschreibt oder den Tier wechselt, zahlt die Resttage. Beispiel: Cool nach 21 Tagen löschen kostet 9 Tage extra.
  6. Archive: Ein archivierter Blob ist nicht lesbar. Man muss ihn erst rehydrieren (Set Blob Tier oder Copy Blob). Das dauert bis zu 15 Stunden, mit High Priority meist deutlich weniger.
  7. Archive und Redundanz: Archive geht nur mit LRS, GRS und RA-GRS. Mit ZRS oder GZRS gibt es kein Archive.
  8. Default Tier: Der Account hat einen Standard-Tier (Hot, Cool oder Cold). Blobs ohne eigenen Tier „erben“ ihn (inferred). Archive kann nie Standard sein.
  9. Smart Tier: verschiebt Blobs automatisch zwischen Hot, Cool und Cold nach Nutzung. Alternative zu eigenen Lifecycle-Regeln.
  10. Redundanz: LRS = 3 Kopien in einem Rechenzentrum. ZRS = 3 Kopien über 3 Availability Zones. GRS = LRS plus asynchrone Kopie in die Paar-Region. GZRS = ZRS plus Geo-Kopie.
  11. RA-GRS / RA-GZRS: erlauben Lesen in der Sekundär-Region über <account>-secondary. Die Geo-Kopie ist asynchron, also kann sie hinterherhinken.
  12. Schweiz: Switzerland North hat Zonen, die Paar-Region ist Switzerland West. Mit GRS bleiben die Daten so in der Schweiz.
  13. SAS-Typen: Account SAS (Account Key, mehrere Dienste), Service SAS (Account Key, ein Dienst), User Delegation SAS (Entra-Identität, nur Blob/ADLS). Microsoft empfiehlt die User Delegation SAS.
  14. SAS widerrufen: Eine Key-SAS stirbt nur durch Key-Rotation oder eine Stored Access Policy. Eine User Delegation SAS stirbt durch revoke-delegation-keys oder durch Entzug der Rolle.
  15. SAS Expiration Policy: Account-Einstellung mit maximaler SAS-Laufzeit. Längere SAS werden geloggt oder blockiert.
  16. Lifecycle Policy: JSON-Regeln mit Filter (blobTypes, prefixMatch, blobIndexMatch) und Aktionen (tierToCool, tierToCold, tierToArchive, delete). Gilt für Base Blobs, Versionen und Snapshots.
  17. Bedingungen: daysAfterModificationGreaterThan, daysAfterCreationGreaterThan, daysAfterLastAccessTimeGreaterThan. Letztere braucht Last Access Time Tracking.
  18. Lifecycle rehydriert nie. Von Archive zurück geht nur manuell oder per Code.
  19. Hierarchical Namespace (HNS): macht den Account zu ADLS Gen2. Ordner sind echte Objekte. Umbenennen eines Ordners ist eine atomare Metadaten-Operation, kein Kopieren aller Blobs.
  20. ACLs: ADLS Gen2 hat POSIX-artige ACLs pro Ordner und Datei, zusätzlich zu RBAC. Default ACLs vererben sich auf neue Kinder, nicht auf bestehende.
  21. HNS ist Einweg: Man kann HNS beim Erstellen setzen oder später per Upgrade aktivieren. Zurück geht nicht. Manche Blob-Features haben mit HNS Einschränkungen.
  22. Datenschutz: Soft Delete für Blobs und Container, Versioning, Point-in-time Restore und Immutability (WORM, z. B. Aufbewahrungspflicht).
  23. Verschlüsselung: Daten sind immer verschlüsselt (AES-256). Standard: Microsoft-Key. Optional: Customer-Managed Key in Key Vault mit Purge Protection.
  24. Defender Malware Scanning: On-Upload und On-Demand. Nur Block Blobs, keine Append- oder Page-Blobs. Client-seitig verschlüsselte Blobs kann es nicht scannen.
  25. Defender-Ergebnis: Index-Tags sind nicht manipulationssicher. Für Sicherheitsentscheidungen nimmt man Event Grid Events, Alerts oder Log Analytics (StorageMalwareScanningResults).
  26. Defender und Netzwerk: Scanning funktioniert mit Private Endpoints. Ein Event Grid Topic ohne Public Network Access wird laut Doku aber nicht für Scan-Ergebnisse unterstützt.

5. Vergleich

  • Blob Storage vs ADLS Gen2: gleicher Dienst. ADLS Gen2 = Blob mit HNS, echten Ordnern, ACLs und abfss:// für Spark.
  • Blob vs Azure Files: Files ist ein SMB/NFS-Dateisystem zum Mounten. Blob ist ein Object Store über HTTP.
  • Blob vs Managed Disks: Disks sind Block-Devices für VMs. Blob ist für Objekte.
  • Blob vs S3: Bucket ≈ Container, Object ≈ Blob, Presigned URL ≈ SAS, S3 Lifecycle ≈ Lifecycle Policy, Glacier ≈ Archive.
  • Blob vs MinIO: MinIO ist S3-kompatibel und läuft im eigenen Cluster. Blob ist ein verwalteter Dienst mit Redundanz und Tiers.
  • Account SAS vs Service SAS vs User Delegation SAS: nur die letzte hängt an einer Entra-Identität und überlebt ein Abschalten von Shared Key.
  • LRS vs ZRS vs GZRS: mehr Schutz (Rack → Zone → Region) gegen mehr Kosten und Einschränkungen (z. B. kein Archive mit ZRS).

6. In der Produktion

  1. Account Key geleakt: Jeder kann alles lesen und schreiben. Lösung: Shared Key abschalten, Entra ID mit Managed Identity, Keys rotieren.
  2. SAS ohne Ende: Eine SAS mit Laufzeit von Jahren liegt in einer Mail. Lösung: User Delegation SAS, kurze Laufzeit, SAS Expiration Policy.
  3. Archive-Falle: Ein Job will alte Dateien lesen und bekommt 409 BlobArchived. Lösung: vorher rehydrieren, oder nur Cold statt Archive nutzen.
  4. Unerwartete Kosten: Lifecycle schiebt nach Cool, ein Report liest täglich alles. Zugriffs- und Early-Deletion-Kosten steigen. Lösung: Zugriffsmuster messen, Last Access Time als Bedingung, oder Smart Tier.
  5. Throttling: Viele kleine Requests auf einen Account liefern 503 ServerBusy. Lösung: Retry mit Backoff (macht das SDK), grössere Blöcke, Last verteilen.
  6. Gelöscht ist gelöscht: Ohne Soft Delete ist ein falscher Delete endgültig. Lösung: Soft Delete und Versioning, und eine Resource Lock auf den Account.
  7. Unscanned Files: Die App liefert Dateien aus, bevor der Scan fertig ist. Lösung: Quarantäne-Container, Freigabe erst nach „No threats found“ aus dem Event.
  8. Private Endpoint ohne DNS: Die App löst die öffentliche IP auf und bekommt 403 AuthorizationFailure. Lösung: Private DNS Zone privatelink.blob.core.windows.net verlinken.

7. Diagnose: Werkzeuge und Befehle

  • Diagnostic Settings → Log Analytics, Tabelle StorageBlobLogs: wer hat was mit welcher Auth gemacht (AuthenticationType: OAuth, SAS, AccountKey).
  • KQL: StorageBlobLogs | where StatusCode == 403 | summarize count() by CallerIpAddress, AuthenticationType
  • Metriken: Transactions nach ResponseType (z. B. ServerBusyError), SuccessE2ELatency vs SuccessServerLatency.
  • az storage blob show --query properties.blobTier und properties.rehydrationStatus.
  • az storage account management-policy show: aktive Lifecycle-Regeln.
  • Defender: Security Alerts in Defender for Cloud, Tabelle StorageMalwareScanningResults.
  • Storage Explorer und AzCopy (azcopy login, azcopy copy): grosse Kopien, Rehydrierung per Copy.
  • nslookup <account>.blob.core.windows.net von innen: muss eine private IP liefern.

8. Senior-Punkte

  1. Identität statt Schlüssel. Shared Key aus, Managed Identity mit Data-Rolle (z. B. Storage Blob Data Contributor) pro App. Für Externe nur User Delegation SAS.
  2. Tiers sind eine Kostenrechnung, keine Ablage. Speicher, Zugriffe, Transaktionen und Mindestdauer zusammen rechnen.
  3. Redundanz nach Anforderung: ZRS gegen Zonenausfall, GZRS für Regionsausfall. Geo-Replikation ist asynchron, also RPO grösser als null.
  4. HNS früh entscheiden. Für Analytics (Spark, Iceberg, Delta) ja, für reine App-Dateien meist nein. Zurück geht nicht.
  5. Upload ist kein Freigabe-Signal. Malware-Scan und MIME-Prüfung gehören in eine Quarantäne-Pipeline.
  6. Kein Public Access auf Account-Ebene, Netzwerk über Private Endpoint, Ausnahmen bewusst dokumentieren.

10. Fallen

  • „Archive ist einfach ein billiger Hot-Tier.“ → Falsch. Archive ist offline. Lesen erst nach Rehydrierung, bis zu 15 Stunden.
  • „Lifecycle holt Daten aus Archive zurück.“ → Falsch. Lifecycle kann nicht rehydrieren.
  • „Eine SAS kann ich jederzeit löschen.“ → Falsch. Eine SAS ist ein signierter String. Widerruf nur über Key-Rotation, Stored Access Policy oder Delegation-Key-Widerruf.
  • „Owner auf dem Account darf Blobs lesen.“ → Nicht über Entra. Dafür braucht es eine Data-Rolle. Aber Owner und Contributor können die Keys auslesen.
  • „Mit Private Endpoint ist der öffentliche Zugang zu.“ → Falsch. Public Network Access muss man extra abschalten.
  • „Der Malware-Tag ist ein sicheres Freigabe-Signal.“ → Falsch. Tags kann jeder mit Tag-Rechten ändern. Events oder Alerts nutzen.
  • „ZRS plus Archive spart am meisten.“ → Geht nicht. Archive nur mit LRS, GRS, RA-GRS.

11. Fragen

Was ist Azure Blob Storage?

Ein Object Store für unstrukturierte Daten in einem Storage Account. Zugriff über HTTPS, Kosten über Tiers, Schutz über Redundanz.

Welche Blob-Typen gibt es?

Block Blobs für Dateien, Append Blobs für Logs (nur anhängen), Page Blobs für wahlfreien Zugriff wie VM-Disks.

Welche Access Tiers gibt es?

Hot, Cool (30 Tage), Cold (90 Tage), Archive (180 Tage, offline). Dazu Smart Tier, das automatisch zwischen Hot, Cool und Cold wechselt.

Was ist die Early Deletion Charge?

Wer vor der Mindestdauer löscht, überschreibt oder umzieht, zahlt die Resttage anteilig.

Wie lese ich einen Blob aus Archive?

Rehydrieren mit Set Blob Tier oder Copy Blob in einen Online-Tier. Standard dauert bis zu 15 Stunden, High Priority ist schneller und teurer.

LRS, ZRS, GRS, GZRS – was ist der Unterschied?

LRS: 3 Kopien in einem Rechenzentrum. ZRS: über 3 Zonen. GRS: LRS plus Kopie in der Paar-Region. GZRS: ZRS plus Geo-Kopie.

Was bringt RA-GRS?

Lesezugriff auf die Sekundär-Region über den -secondary-Endpoint, auch ohne Failover. Die Daten können leicht veraltet sein.

Welche SAS-Typen gibt es?

Account SAS und Service SAS (mit Account Key signiert) und User Delegation SAS (mit Entra-Identität signiert, nur Blob/ADLS).

Warum User Delegation SAS?

Kein Account Key nötig, an eine Identität gebunden, auditierbar, maximal 7 Tage gültig. Funktioniert auch mit abgeschaltetem Shared Key.

Wie widerrufe ich eine SAS?

Key-SAS: Account Key rotieren oder Stored Access Policy ändern. User Delegation SAS: Delegation Keys widerrufen oder Rolle entziehen.

Was ist eine Stored Access Policy?

Eine Richtlinie auf dem Container, auf die eine Service SAS verweist. Ändert oder löscht man sie, ist die SAS sofort ungültig.

Wie funktioniert eine Lifecycle Policy?

JSON-Regeln mit Filtern und Aktionen wie tierToCool oder delete, basierend auf Alter oder letztem Zugriff. Sie läuft ungefähr einmal am Tag.

Was ist ADLS Gen2?

Blob Storage mit Hierarchical Namespace: echte Ordner, atomares Umbenennen, POSIX-ACLs und der dfs-Endpoint für Analytics.

Warum ist HNS für Spark wichtig?

Spark und Tabellenformate benennen Ordner um und listen sie oft. Mit HNS ist das eine Metadaten-Operation statt vieler Kopien.

Kann ich HNS wieder abschalten?

Nein. Das Upgrade ist einseitig. Darum vorher die Feature-Unterstützung prüfen.

Wie sichere ich einen Storage Account ab?

Shared Key aus, Entra ID mit Managed Identity, keine anonymen Container, Private Endpoint, Public Network Access aus, TLS 1.2, Soft Delete und Versioning.

Welche Rolle braucht eine App zum Schreiben von Blobs?

Storage Blob Data Contributor auf Container- oder Account-Ebene. Owner oder Contributor reichen für den Datenzugriff über Entra nicht.

Wie funktioniert Defender Malware Scanning?

Beim Upload löst ein Event Grid System Topic den Scan aus. Ergebnis als Index-Tag, Alert, Event Grid Event oder Log-Analytics-Eintrag.

Was scannt Defender nicht?

Append- und Page-Blobs, client-seitig verschlüsselte Blobs, NFS-Uploads und Dateien über 50 GB.

Wie schütze ich Daten gegen versehentliches Löschen?

Soft Delete für Blobs und Container, Versioning, Resource Lock auf dem Account, bei Pflicht-Aufbewahrung Immutability Policies.

Blob Storage vs Azure Files?

Files ist ein mountbares SMB/NFS-Dateisystem. Blob ist ein Object Store über HTTP-API.

Wie lade ich grosse Dateien effizient hoch?

Mit Block-Upload: Blöcke parallel hochladen, dann Put Block List. Das SDK und AzCopy machen das automatisch.

Szenario: Ein Partner braucht für 2 Stunden Lesezugriff auf eine Datei. Was tun Sie?

User Delegation SAS nur für diesen Blob, nur Lesen, nur HTTPS, Ablauf in 2 Stunden. Erstellt von einer Identität mit genau diesen Rechten.

Szenario: Nach Aktivieren eines Private Endpoints bekommt die App 403. Warum?

Wahrscheinlich löst DNS noch die öffentliche IP auf, und Public Access ist aus. Private DNS Zone verlinken und mit nslookup von innen prüfen.

Szenario: Die Storage-Kosten steigen trotz Lifecycle nach Cool. Woran denken Sie?

An Lese- und Early-Deletion-Kosten, weil Daten in Cool doch oft gelesen werden. StorageBlobLogs prüfen, Regel auf Last Access Time umstellen oder Smart Tier nutzen.
