Metadaten: metadata.json, Manifest List, Manifests

Iceberg · Tier 1 · Quellen: Apache Iceberg Table Spec (Overview, Manifests, Manifest Lists, Snapshots, Scan Planning, Table Metadata, Sequence Numbers), Iceberg 1.x Docs (Configuration: Metrics, Spark Queries: Metadata Tables, Spark Procedures)

Kern: Iceberg-Metadaten sind ein Baum aus Dateien: Catalog-Zeiger → metadata.json → Manifest List → Manifests → Daten- und Delete-Dateien. Jede Ebene speichert Statistiken, mit denen ein Reader ganze Äste überspringt. So plant Iceberg eine Abfrage ohne Ordner-Listing und liest nur passende Dateien.

1. Wo sitzen die Metadaten?

  1. Catalog: Speichert nur den Pfad der aktuellen metadata.json. Beispiel: Nessie-Eintrag silver.reports → s3://…/00007-….metadata.json.
  2. metadata.json: Die Tabellen-Definition in JSON. Sie enthält alle Schemas, Partition Specs, Sort Orders, Properties und die Liste aller gültigen Snapshots.
  3. Manifest List: Eine Avro-Datei pro Snapshot. Sie listet die Manifests dieses Snapshots mit Zählern und Partitions-Grenzen.
  4. Manifest: Eine Avro-Datei mit je einer Zeile pro Daten- oder Delete-Datei. Jede Zeile hat Pfad, Partitionswerte, Zeilenzahl und Spalten-Statistiken.
  5. Daten- und Delete-Dateien: Parquet mit den Zeilen. Delete Files markieren gelöschte Zeilen.
  6. Teilen: Snapshots teilen sich unveränderte Manifests. Ein neuer Commit schreibt nur neue Manifests und eine neue Manifest List.

2. Die Reise einer Abfrage durch die Metadaten (die Geschichte zum Merken)

Abfrage: SELECT … FROM reports WHERE received_date >= '2026-11-02' AND received_date < '2026-11-03' AND message_id = 'm-42'

  1. Catalog fragen: Spark fragt den Catalog nach reports. Antwort: Pfad der aktuellen metadata.json.
  2. metadata.json lesen: Spark findet current-snapshot-id, das aktuelle Schema und alle Partition Specs. Der Snapshot zeigt auf seine Manifest List.
  3. Manifest List filtern: Jedes Manifest hat pro Partitionsfeld eine Unter- und Obergrenze (partitions). Ein Manifest nur mit Oktober-Tagen fällt sofort weg.
  4. Manifests filtern: In den übrigen Manifests prüft Spark jede Datei. Die Partition received_date_day = 2026-11-02 muss passen. Dann prüft es lower_bounds und upper_bounds von message_id. Liegt 'm-42' ausserhalb, fällt die Datei weg.
  5. Deletes zuordnen: Delete Files gelten nur für Dateien in derselben Partition mit passender Sequence Number. Position Deletes und Deletion Vectors gelten für Daten mit Sequence Number kleiner oder gleich. Equality Deletes nur für strikt ältere Daten.
  6. Scan Tasks bauen: Übrig bleibt eine kurze Dateiliste. Spark teilt sie in Tasks (nach split_offsets) und verteilt sie.
  7. Parquet lesen: Jeder Executor liest seine Datei. Parquet hat eigene Row-Group-Statistiken und überspringt noch mehr.

  1. last-sequence-number zählt Commits. Der Snapshot trägt dieselbe sequence-number.
  2. partition-specs hat eigene Partition Field IDs ab 1000. Sie bleiben über Spec-Wechsel stabil.
  3. content = 0 ist ein Daten-Manifest, content = 1 ein Delete-Manifest. Ein Manifest enthält nie beides.
  4. added_data_files_count zählt Einträge mit Status ADDED in dem Snapshot, der das Manifest geschrieben hat. Ein altes, geteiltes Manifest behält diesen Wert.
  5. Das Oktober-Manifest hat Grenzen 2026-10-01 … 2026-10-31. Eine Abfrage auf November liest es gar nicht.
  6. readable_metrics zeigt die Min/Max-Werte pro Datei. Für message_id = 'm-42' bleibt nur die zweite Datei übrig.

4. Details, die Interviewer fragen

  1. metadata.json-Felder: format-version, table-uuid, location, last-sequence-number, last-column-id, schemas, current-schema-id, partition-specs, default-spec-id, last-partition-id, sort-orders, properties, current-snapshot-id, snapshots, snapshot-log, metadata-log, refs, statistics. v3 ergänzt next-row-id.
  2. Snapshot-Felder: snapshot-id, parent-snapshot-id, sequence-number, timestamp-ms, manifest-list, summary, schema-id. v3 ergänzt first-row-id und added-rows.
  3. Operation im Summary: append (nur neue Dateien), replace (gleiche Daten, z. B. Compaction), overwrite (logisch ersetzt), delete (gelöscht).
  4. Manifest-List-Felder: manifest_path, manifest_length, partition_spec_id, content, sequence_number, min_sequence_number, added_snapshot_id, Zähler für added/existing/deleted Dateien und Zeilen, partitions (pro Feld contains_null, contains_nan, lower_bound, upper_bound).
  5. Manifest-Eintrag: status (0 = EXISTING, 1 = ADDED, 2 = DELETED), snapshot_id, sequence_number, file_sequence_number und data_file.
  6. data_file: content (0 = Daten, 1 = Position Deletes, 2 = Equality Deletes), file_path, file_format, partition, record_count, file_size_in_bytes, split_offsets, equality_ids, sort_order_id.
  7. Spalten-Statistiken: pro Field ID column_sizes, value_counts, null_value_counts, nan_value_counts, lower_bounds, upper_bounds. Sie sind nach Field ID gespeichert, nicht nach Name.
  8. Metrics Mode: Standard ist write.metadata.metrics.default = truncate(16): Min/Max werden auf 16 Zeichen gekürzt. Statistiken gibt es standardmässig nur für die ersten 100 Spalten (write.metadata.metrics.max-inferred-column-defaults).
  9. Sequence Numbers: Jeder Commit bekommt die nächste Nummer. Neue Einträge erben sie vom Manifest. So bestimmt Iceberg, ob ein Delete älter oder neuer als eine Datendatei ist.
  10. Gleicher Commit: Position Deletes gelten auch für Daten mit gleicher Sequence Number. Equality Deletes gelten nur für strikt ältere Daten. Neu angehängte Zeilen im selben Commit bleiben also sichtbar.
  11. Fast Append: Ein Append schreibt ein neues Manifest, statt alte umzuschreiben. Schnell, aber es entstehen viele kleine Manifests.
  12. Ein Spec pro Manifest: In v1–v3 enthält ein Manifest nur Dateien einer Partition Spec. Darum braucht die Manifest List partition_spec_id.
  13. v3 Deletion Vectors: Ein Deletion Vector ist eine Bitmap gelöschter Positionen einer Datei, gespeichert in einer Puffin-Datei. Der Eintrag hat referenced_data_file, content_offset, content_size_in_bytes.
  14. Table Statistics: Zusätzliche Statistiken (z. B. NDV-Sketches) liegen in Puffin-Dateien und stehen in statistics der metadata.json.
  15. Inclusive Projection: Ein Filter auf received_date wird zu einem Filter auf received_date_day. Er darf zu viele Dateien wählen, nie zu wenige. Der Rest wird beim Lesen gefiltert (Residual).
  16. Ausblick v4: Die Manifest List wird durch ein Root Manifest ersetzt. v4 ist noch nicht verabschiedet.

5. Vergleich

  • Iceberg: Baum aus unveränderlichen Dateien. Statistiken auf zwei Ebenen (Manifest List und Manifest). Commit = neuer Baum-Kopf.
  • Delta Lake: Lineares Log aus JSON-Commits plus Parquet-Checkpoints. Der Reader spielt das Log ab dem letzten Checkpoint nach.
  • Hive Metastore: Nur Partition → Ordner. Dateien und Statistiken pro Datei kennt er nicht.
  • Parquet-Footer: Statistiken pro Row Group, aber nur innerhalb einer Datei. Iceberg bringt diese Grenzen eine Ebene höher, ohne die Datei zu öffnen.

6. In der Produktion

  1. Planung dauert lange: Tausende kleine Manifests nach vielen Fast Appends. Lösung: CALL cat.system.rewrite_manifests('db.t').
  2. metadata.json wird gross: Jeder Snapshot steht darin. Nach Monaten ohne Expiry sind es Tausende. Lösung: expire_snapshots regelmässig.
  3. Alte metadata.json stapeln sich: Standard behält 100 tracked Versionen und löscht nichts. Lösung: write.metadata.delete-after-commit.enabled = true, Rest mit remove_orphan_files.
  4. Pruning greift nicht: Daten sind nicht sortiert, darum hat jede Datei fast den vollen Min/Max-Bereich. Lösung: WRITE ORDERED BY oder Compaction mit strategy => 'sort'.
  5. Keine Statistiken für breite Tabellen: Ab Spalte 101 gibt es standardmässig keine Min/Max. Lösung: write.metadata.metrics.column.<col> für wichtige Filter-Spalten setzen.
  6. Lange Strings: Bei truncate(16) unterscheiden sich IDs mit gleichem Präfix nicht. Lösung: full für diese Spalte, oder bessere Partitionierung.
  7. Driver-OOM beim Planen: Sehr viele Dateien und Delete Files. Lösung: Compaction, Manifests umschreiben, Deletes regelmässig einrechnen.

7. Diagnose: Werkzeuge und Befehle

  • SELECT * FROM t.manifests / t.all_manifests: Anzahl, Grösse, Content, Partitions-Grenzen.
  • SELECT * FROM t.files / t.data_files / t.delete_files: Dateien mit readable_metrics.
  • SELECT * FROM t.entries: Manifest-Einträge mit status und Sequence Numbers.
  • SELECT * FROM t.metadata_log_entries: alle metadata.json-Versionen.
  • SELECT count(*), sum(file_size_in_bytes) FROM t.files GROUP BY partition: Small Files pro Partition finden.
  • Spark UI / EXPLAIN: Anzahl gelesener Dateien und Pushed Filters prüfen.
  • Avro-Dateien direkt mit avro-tools tojson lesen, wenn man tief debuggen muss.

8. Senior-Punkte

  1. Pruning ist die eigentliche Leistung. Iceberg ist schnell, weil es Dateien nicht öffnet. Partitionierung und Sortierung entscheiden, wie gut das klappt.
  2. Metadaten sind Daten. Sie wachsen und brauchen Pflege wie die Daten selbst: Manifests umschreiben, Snapshots ablaufen lassen.
  3. Unveränderlich heisst teilbar. Snapshots teilen Manifests. Darum sind Time Travel und Commits billig.
  4. Statistiken kosten. Mehr Metriken machen Manifests grösser. Für viele Spalten counts oder none, für Filter-Spalten full.
  5. Sequence Numbers sind der Schlüssel für Deletes. Wer sie erklärt, versteht Merge-on-Read und Compaction-Konflikte.

9. Aus dem Projekt

„Bei MATCH schreibt jeder Ingestion-Commit DELETE WHERE message_id = X plus APPEND mit Merge-on-Read; dadurch entstehen pro Commit neue Daten- und Delete-Manifests, die wir mit rewrite_data_files und expire_snapshots klein halten.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Die Manifest List enthält die Datendateien.“ → Falsch. Sie enthält Manifests. Die Datendateien stehen in den Manifests.
  • „Jeder Snapshot kopiert alle Manifests.“ → Falsch. Unveränderte Manifests werden geteilt. Neu ist nur, was sich ändert.
  • „Iceberg listet die Partition-Ordner.“ → Falsch. Die Dateiliste kommt aus den Manifests.
  • „Statistiken stehen nach Spaltenname.“ → Falsch. Nach Field ID. Darum überleben sie ein Rename.
  • „Ein Delete File gilt für die ganze Tabelle.“ → Falsch. Nur für Daten derselben Partition mit passender Sequence Number (Ausnahme: unpartitionierte Equality Deletes).
  • „Ein Manifest kann Daten und Deletes mischen.“ → Falsch. content ist 0 (Daten) oder 1 (Deletes).

11. Fragen

Welche Metadaten-Ebenen hat Iceberg?

Catalog-Zeiger, metadata.json, Manifest List pro Snapshot, Manifests, dann Daten- und Delete-Dateien.

Was steht in metadata.json?

Schemas, Partition Specs, Sort Orders, Properties, alle gültigen Snapshots, Refs und der aktuelle Snapshot. Dazu ein Log alter Metadaten-Dateien.

Was ist eine Manifest List?

Eine Avro-Datei pro Snapshot. Sie listet dessen Manifests mit Zählern, Sequence Numbers und Partitions-Grenzen.

Was ist ein Manifest?

Eine Avro-Datei mit einer Zeile pro Daten- oder Delete-Datei. Jede Zeile hat Pfad, Partition, Zeilenzahl und Spalten-Statistiken.

Welche Statistiken speichert ein Manifest pro Datei?

Pro Field ID: Grösse, Anzahl Werte, Nulls, NaNs, untere und obere Grenze.

Wie hilft die Manifest List beim Pruning?

Pro Partitionsfeld kennt sie Min und Max über das ganze Manifest. Passt der Filter nicht, wird das Manifest gar nicht gelesen.

Warum Avro für Manifests und nicht Parquet?

Manifests werden zeilenweise geschrieben und ganz gelesen. Avro passt dafür gut und unterstützt Schema-Evolution. Analytische Spaltenzugriffe braucht man dort nicht.

Was bedeutet der Status eines Manifest-Eintrags?

0 = EXISTING, 1 = ADDED in diesem Snapshot, 2 = DELETED in diesem Snapshot. Nur EXISTING und ADDED sind live.

Was ist eine Sequence Number?

Eine fortlaufende Nummer pro Commit. Sie zeigt, ob ein Delete File neuer als eine Datendatei ist und auf sie wirkt.

Wann wirkt ein Position Delete, wann ein Equality Delete?

Position Delete: auf Daten mit Sequence Number kleiner oder gleich, gleiche Partition, passender Pfad. Equality Delete: nur auf strikt ältere Daten.

Was ist ein Deletion Vector?

Eine Bitmap gelöschter Zeilenpositionen für genau eine Datendatei, gespeichert in Puffin. In v3 ersetzt sie Position Delete Files.

Was ist ein Fast Append?

Ein Append schreibt nur ein neues Manifest dazu und lässt alte unverändert. Schneller Commit, aber viele kleine Manifests.

Was ist der Unterschied zwischen operation append und overwrite?

append fügt nur Dateien hinzu. overwrite fügt hinzu und entfernt logisch Daten, z. B. bei DELETE mit neuen Zeilen.

Was ist inclusive projection?

Ein Filter auf eine Spalte wird in einen Filter auf die Partition übersetzt. Er darf zu viele Dateien wählen, aber nie passende auslassen.

Warum sind Statistiken nach Field ID gespeichert?

Namen können sich ändern, IDs nie. So bleiben Statistiken nach Rename und Reorder richtig.

Was ist der Standard-Metrics-Mode?

truncate(16) für die ersten 100 Spalten. Andere Modi sind none, counts und full.

Warum braucht die Manifest List partition_spec_id?

In v1–v3 enthält ein Manifest nur Dateien einer Spec. Der Reader muss wissen, wie er die Partitionswerte darin deutet.

Wie werden alte metadata.json-Dateien entfernt?

Mit write.metadata.delete-after-commit.enabled = true und previous-versions-max. Nicht mehr getrackte Dateien entfernt remove_orphan_files.

Was ändert sich in v4?

Ein Root Manifest ersetzt die Manifest List, Deletion Vectors liegen beim Dateieintrag. v4 ist noch in Arbeit.

Szenario: Spark braucht eine Minute zum Planen, bevor der erste Task startet. Was prüfen Sie?

Anzahl Manifests und Dateien in t.manifests und t.files, und die Grösse der metadata.json. Lösung: rewrite_manifests, Compaction und expire_snapshots.

Szenario: Eine Abfrage nach einer ID liest trotzdem alle Dateien einer Partition. Warum?

Die Min/Max-Bereiche der Dateien überlappen, weil die Daten nicht sortiert sind. Oder die Spalte hat keine Metriken. Lösung: Sort Order oder Sort-Compaction, Metrics Mode prüfen.

Szenario: Nach Monaten liegen 10'000 metadata.json-Dateien im Bucket. Ist das gefährlich?

Nicht für die Korrektheit, aber für Kosten und Listing. Lösung: delete-after-commit aktivieren, Snapshots ablaufen lassen, Orphans entfernen.
