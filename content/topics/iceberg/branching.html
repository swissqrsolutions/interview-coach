Branches und Tags

Kern: Ein Branch in Iceberg ist ein benannter, beweglicher Zeiger auf einen Snapshot; ein Tag ist ein benannter, fester Zeiger. Beide leben in der metadata.json einer Tabelle als Snapshot References. Sie lösen zwei Probleme: Daten auf einem Branch prüfen, bevor Leser sie sehen (Write-Audit-Publish), und wichtige Stände wie einen Monatsabschluss vor dem Ablaufen schützen.

1. Wo sitzen Branches und Tags?

  1. Snapshot: ein Stand der Tabelle. Jeder Commit erzeugt einen neuen.
  2. main: der Standard-Branch. Leser ohne Angabe lesen main.
  3. Branch: eine eigene Linie von Snapshots. Writes auf audit ändern main nicht.
  4. Tag: ein fester Name für einen Snapshot, z. B. EOM-2026-10 für den Monatsabschluss.
  5. refs in der metadata.json: Hier stehen alle Branches und Tags mit Snapshot-ID und Retention.
  6. Datendateien werden geteilt. Ein Branch kopiert keine Daten, nur Metadaten.

2. Die Reise eines Batches durch Write-Audit-Publish

  1. Branch anlegen: Der Job erstellt audit vom aktuellen main. Der Branch muss existieren; ein Write legt ihn nicht an.
  2. Write: Der Job setzt spark.wap.branch = audit und schreibt. Der neue Snapshot hängt nur an audit.
  3. Audit: Qualitäts-Checks lesen audit: Zeilenzahl, Duplikate, Pflichtfelder.
  4. Publish: Sind die Checks grün, setzt fast_forward main auf den Kopf von audit. Das ist ein reiner Zeiger-Tausch.
  5. Leser: Dashboards sehen den neuen Stand in einem Schritt. Halbe oder ungeprüfte Daten sehen sie nie.
  6. Aufräumen: Der Branch hat eine Retention. Danach entfernt expire_snapshots den Zeiger. Sind die Checks rot, bleibt main unverändert, und die Daten auf audit verfallen.

3. Beispiel: WAP und Monatsabschluss in Spark SQL

-- einmalig: WAP für die Tabelle erlauben
ALTER TABLE lake.gold.daily_stats SET TBLPROPERTIES ('write.wap.enabled'='true');

-- 1) Branch anlegen, 7 Tage behalten
ALTER TABLE lake.gold.daily_stats CREATE BRANCH `audit-20261124` RETAIN 7 DAYS;

-- 2) Schreiben auf den Branch
SET spark.wap.branch = audit-20261124;
INSERT INTO lake.gold.daily_stats SELECT ... ;

-- 3) Prüfen: Branch gegen main
SELECT count(*) FROM lake.gold.daily_stats VERSION AS OF 'audit-20261124';
SELECT count(*) FROM lake.gold.daily_stats VERSION AS OF 'main';

-- 4) Veröffentlichen
CALL lake.system.fast_forward('gold.daily_stats', 'main', 'audit-20261124');

-- Monatsabschluss für ein Jahr schützen
ALTER TABLE lake.gold.daily_stats CREATE TAG `EOM-2026-10` RETAIN 365 DAYS;
SELECT name, type, snapshot_id, max_reference_age_in_ms FROM lake.gold.daily_stats.refs;
-- Erwartet:
-- count auf audit = count auf main + neue Zeilen
-- fast_forward: branch_updated = main, previous_ref = <alte ID>, updated_ref = <ID von audit>
-- refs:
-- name            type    snapshot_id   max_reference_age_in_ms
-- main            BRANCH  <neu>         NULL
-- audit-20261124  BRANCH  <neu>         604800000
-- EOM-2026-10     TAG     <neu>         31536000000

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spark und Iceberg laufen hier nicht. 604 800 000 ms = 7 Tage, 31 536 000 000 ms = 365 Tage.

  1. write.wap.enabled ist standardmässig false. Ohne diese Eigenschaft lehnt Iceberg WAP-Writes ab.
  2. spark.wap.branch lenkt alle Writes der Session auf den Branch. Man kann ihn nicht mit einem Branch-Bezeichner wie …branch_audit im gleichen Write kombinieren.
  3. fast_forward klappt nur, wenn main ein Vorfahre von audit ist. Hat jemand inzwischen auf main geschrieben, muss man neu aufsetzen.
  4. Der Tag hält Snapshot 365 Tage fest. expire_snapshots löscht ihn in dieser Zeit nicht.

4. Details, die Interviewer fragen

  1. Retention eines Branches: drei Werte: max-ref-age-ms (wie lange der Branch lebt), min-snapshots-to-keep und max-snapshot-age-ms (welche Snapshots im Branch bleiben). Ohne Angabe leben Branches und Tags für immer.
  2. Retention eines Tags: nur max-ref-age-ms. Danach entfernt expire_snapshots den Tag.
  3. Schema beim Lesen: Ein Branch nutzt das aktuelle Tabellen-Schema. Ein Tag (und eine Snapshot-ID) nutzt das Schema des Snapshots.
  4. Lesen eines Branches: VERSION AS OF 'audit' oder der Bezeichner lake.db.tbl.branch_audit. Ein Tag mit tag_EOM.
  5. Schreiben auf einen Branch: per Bezeichner branch_<name> (INSERT, MERGE, UPDATE, DELETE, writeTo) oder per spark.wap.branch.
  6. fast_forward vs cherrypick: fast_forward schiebt main auf den Kopf des Branches. cherrypick_snapshot übernimmt einen einzelnen Snapshot in den aktuellen Zustand.
  7. Iceberg-Branch vs Nessie-Branch: Iceberg-Branches gelten für eine Tabelle. Nessie-Branches gelten für den ganzen Katalog und können mehrere Tabellen gleichzeitig mergen.
  8. Kosten: Ein Branch kopiert keine Daten. Aber Snapshots auf dem Branch halten Dateien fest, bis der Branch abläuft.

5. Vergleich

  • Iceberg-Branch: pro Tabelle, eingebaut, keine Extra-Komponente. Gut für WAP einer Tabelle.
  • Nessie-Branch: über alle Tabellen eines Katalogs, mit Merge über mehrere Tabellen. Gut, wenn Silver und Gold zusammen publiziert werden müssen.
  • Staging-Tabelle + Swap: in eine Kopie schreiben, prüfen, dann umbenennen oder per INSERT OVERWRITE übernehmen. Funktioniert überall, kostet aber eine Kopie und ist oft nicht atomar.
  • Tag vs Snapshot-ID: Beide zeigen auf einen Stand. Nur ein Tag schützt ihn vor expire_snapshots und hat einen lesbaren Namen.

6. In der Produktion

  1. Speicher wächst trotz expire_snapshots: Alte Branches oder Tags ohne Retention halten Dateien fest. Lösung: Retention immer setzen, .refs regelmässig prüfen.
  2. fast_forward scheitert: Auf main wurde parallel geschrieben. Lösung: Ingest serialisieren oder Branch neu von main erstellen und Batch wiederholen.
  3. WAP-Write landet auf main: spark.wap.branch in einer anderen Session gesetzt oder write.wap.enabled fehlt. Lösung: Branch-Bezeichner im Tabellennamen nutzen, im Test prüfen.
  4. Audit-Abfrage liest den falschen Stand: Checks lesen main statt audit. Lösung: Branch explizit mit VERSION AS OF lesen.
  5. Verwaiste Audit-Branches nach Fehlern: Rote Checks hinterlassen Branches. Lösung: kurze Retention, z. B. 7 Tage.

7. Diagnose

  • SELECT * FROM lake.gold.daily_stats.refs: alle Branches und Tags mit Snapshot und Retention.
  • SELECT * FROM lake.gold.daily_stats.snapshots: Snapshots mit parent_id, so sieht man die Linien.
  • SELECT * FROM lake.gold.daily_stats.history: zeigt nur die Abfolge von main.
  • DESCRIBE TABLE EXTENDED zeigt write.wap.enabled und andere Properties.

8. Senior-Punkte

  1. WAP macht Qualitäts-Checks zu einem echten Gate. Leser sehen nur geprüfte Daten.
  2. Retention ist Pflicht. Ein Branch ohne Ablauf ist ein Speicherleck.
  3. Tags für fachliche Stände: Monatsabschluss, Regulierungs-Meldung, Modell-Trainingsstand. Dann ist die Antwort auf „welche Daten galten damals?“ ein Name.
  4. Pro Tabelle oder katalogweit? Müssen mehrere Tabellen zusammen sichtbar werden, reicht ein Iceberg-Branch nicht. Dann Nessie oder Publish in fester Reihenfolge.
  5. Ein Branch ersetzt keine Testumgebung für Code, nur für Daten.

9. Aus dem Projekt

„Bei ElCom MATCH habe ich keine Iceberg-Branches eingesetzt; die Absicherung war dort der Paritäts-Job und der Feature Switch, und Nessie diente als Katalog.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Ein Branch kopiert die Tabelle.“ → Falsch. Er teilt alle Dateien und kopiert nur Metadaten.
  • „Ein Write auf einen neuen Branch legt ihn an.“ → Falsch. Der Branch muss vorher existieren.
  • „Ein Tag liest mit dem aktuellen Schema.“ → Falsch. Ein Tag nutzt das Schema des Snapshots, ein Branch das aktuelle.
  • „Iceberg-Branches sind wie Nessie-Branches.“ → Falsch. Iceberg: eine Tabelle. Nessie: ganzer Katalog.
  • „Branches laufen automatisch ab.“ → Falsch. Standard ist „für immer“.

11. Fragen

Was ist ein Branch in Iceberg?

Ein benannter, beweglicher Zeiger auf einen Snapshot einer Tabelle. Neue Writes auf den Branch erzeugen dort neue Snapshots.

Was ist ein Tag?

Ein benannter, fester Zeiger auf einen Snapshot. Er schützt diesen Stand vor expire_snapshots, solange er lebt.

Wo werden Branches gespeichert?

Als refs in der metadata.json der Tabelle, mit Typ, Snapshot-ID und Retention.

Was ist Write-Audit-Publish?

Daten erst auf einen Branch schreiben, dort prüfen und bei Erfolg main per fast_forward darauf setzen. Leser sehen nur geprüfte Daten.

Wie schreiben Sie mit Spark auf einen Branch?

Mit dem Bezeichner tabelle.branch_name oder mit spark.wap.branch in der Session. Für WAP muss write.wap.enabled true sein.

Wie lesen Sie einen Branch oder Tag?

Mit VERSION AS OF 'name' oder dem Bezeichner branch_name bzw. tag_name.

Welches Schema gilt beim Lesen?

Ein Branch nutzt das aktuelle Tabellen-Schema. Ein Tag nutzt das Schema seines Snapshots.

Welche Retention-Einstellungen gibt es?

Für Branches max-ref-age-ms, min-snapshots-to-keep und max-snapshot-age-ms. Für Tags nur max-ref-age-ms. Standard: für immer.

Was macht fast_forward?

Es setzt einen Branch, meist main, auf den Kopf eines anderen Branches. Das geht nur, wenn main ein Vorfahre ist.

fast_forward oder cherrypick_snapshot?

fast_forward übernimmt die ganze Linie bis zum Kopf. cherrypick übernimmt einen einzelnen Snapshot.

Kostet ein Branch Speicher?

Nicht beim Anlegen. Aber seine Snapshots halten Dateien fest, bis der Branch abläuft.

Iceberg-Branch oder Nessie-Branch?

Iceberg-Branch für eine Tabelle. Nessie-Branch, wenn mehrere Tabellen zusammen geprüft und veröffentlicht werden müssen.

Wofür nutzen Sie Tags?

Für fachliche Stände wie Monatsabschluss oder Trainingsdaten eines Modells. So bleiben sie lesbar und geschützt.

Ersetzt ein Tag ein Backup?

Nein. Er liegt in derselben Tabelle und im selben Storage. Verliert man Storage oder Katalog, ist auch der Tag weg.

Was passiert mit einem Branch nach roten Checks?

main bleibt unverändert. Der Branch verfällt nach seiner Retention, oder man löscht ihn mit DROP BRANCH.

Szenario: Der Speicher wächst, obwohl expire_snapshots täglich läuft. Woran denken Sie?

An Branches oder Tags ohne Retention, die alte Snapshots festhalten. In .refs prüfen und Retention setzen oder alte Refs löschen.

Szenario: fast_forward schlägt fehl. Warum?

Auf main wurde seit dem Anlegen des Branches geschrieben, main ist kein Vorfahre mehr. Branch neu von main anlegen und den Batch wiederholen.

Szenario: Die Revision fragt, welche Zahlen beim Oktober-Abschluss galten. Wie antworten Sie?

Mit einem Tag EOM-2026-10, gelesen per VERSION AS OF. Er hält den Stand für die vereinbarte Zeit fest.
