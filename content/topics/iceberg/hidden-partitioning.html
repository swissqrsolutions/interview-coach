Hidden Partitioning und Partition Evolution

Iceberg · Tier 1 · Quellen: Apache Iceberg Table Spec (Partitioning, Partition Transforms, Bucket/Truncate Details, Partition Evolution, Scan Planning), Iceberg 1.x Docs (Partitioning, Evolution, Spark DDL: PARTITIONED BY, ADD/DROP/REPLACE PARTITION FIELD, Spark Queries: SQL functions)

Hidden Partitioning ist Iceberg-Partitionierung über Transforms auf normalen Spalten, z. B. days(received_date). Iceberg berechnet den Partitionswert selbst und speichert ihn nur in den Metadaten. Abfragen filtern auf die echte Spalte, und Iceberg leitet den Partitionsfilter ab. Partition Evolution ändert das Layout später, ohne alte Daten umzuschreiben.

1. Wo sitzt die Partitionierung?

  1. Quellspalte: Eine normale Spalte im Schema. Beispiel: received_date (TIMESTAMP).
  2. Partition Spec: Eine Liste von Feldern aus Quellspalte, Transform, Name und Partition Field ID. Beispiel: day(received_date) heisst received_date_day.
  3. Partition Tuple: Die berechneten Werte pro Datei. Sie stehen im Manifest, nicht als Spalte in den Daten.
  4. Datei: Alle Zeilen einer Datei haben dasselbe Partition Tuple. Der Writer trennt die Daten danach.
  5. Abfrage: Der User filtert die echte Spalte. Iceberg übersetzt den Filter in einen Partitionsfilter (inclusive projection) und überspringt Dateien.

2. Die Reise einer Partition Evolution (die Geschichte zum Merken)

  1. Start: Die Tabelle ist nach Monat partitioniert. Am Anfang kommen wenige Daten. Monatsdateien haben eine gute Grösse.
  2. Mehr Last: Die Daten wachsen stark. Abfragen auf einen Tag lesen einen ganzen Monat. Das Team ändert die Spec mit ALTER TABLE … REPLACE PARTITION FIELD.
  3. Neue Spec: Iceberg schreibt eine neue metadata.json mit Spec 1 als default-spec-id. Keine Datendatei wird bewegt. Neue Writes nutzen Spec 1.
  4. Split Planning: Eine Abfrage plant jede Spec für sich. Für alte Manifests leitet Iceberg einen Monatsfilter ab, für neue einen Tagesfilter. Jedes Manifest kennt seine partition_spec_id.
  5. Ein Ergebnis: Der User schreibt dieselbe SQL wie vorher. Er muss die Specs nicht kennen.
  6. Optional umschreiben: Wer alte Daten auch tageweise will, lässt rewrite_data_files laufen. Compaction schreibt mit der aktuellen Spec.

3. Beispiel: Tabelle mit Transforms, Abfrage, Evolution

-- Spark SQL, Iceberg 1.x mit SQL Extensions, Catalog "cat" (Beispieltabelle)
CREATE TABLE cat.demo.reports (
  message_id STRING, schema_type STRING, received_date TIMESTAMP, volume DECIMAL(18,4))
USING iceberg
PARTITIONED BY (days(received_date), schema_type);

-- Abfrage: nur die echte Spalte, keine Partitionsspalte
EXPLAIN SELECT count(*) FROM cat.demo.reports
WHERE received_date >= TIMESTAMP '2026-11-02 00:00:00'
  AND received_date <  TIMESTAMP '2026-11-03 00:00:00'
  AND schema_type = 'TRADE';

-- Evolution: zusätzlich nach message_id bucketen
ALTER TABLE cat.demo.reports ADD PARTITION FIELD bucket(8, message_id) AS msg_bucket;

SELECT spec_id, count(*) AS files FROM cat.demo.reports.files GROUP BY spec_id;
== Physical Plan ==

     received_date < 1762128000000000, schema_type = 'TRADE', …]

spec_id  files
0        412     -- alte Dateien: (received_date_day, schema_type)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Format des Plans hängt von der Spark-Version ab; Zahlen sind Beispielwerte.

  1. days(received_date) erzeugt die Partition received_date_day. In der Tabelle gibt es keine solche Spalte.
  2. Der Filter auf received_date wird an Iceberg gegeben (Pushed Filters). Iceberg macht daraus den Tagesfilter.
  3. ADD PARTITION FIELD ist nur eine Metadaten-Änderung. Sie braucht die Iceberg SQL Extensions (spark.sql.extensions = org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions).
  4. .files zeigt: Alte Dateien bleiben in Spec 0, neue landen in Spec 1. Beide Layouts leben in derselben Tabelle.

4. Details, die Interviewer fragen

  1. Transforms:
    • identity: Wert unverändert. Beispiel: schema_type.
    • year, month, day, hour: Zeit seit 1970 in Jahren, Monaten, Tagen, Stunden. hour nur für Timestamps.
    • bucket[N]: Hash-Wert modulo N. Für hohe Kardinalität wie IDs.
    • truncate[W]: Strings auf W Zeichen kürzen, Zahlen auf Vielfache von W abrunden. Beispiel: truncate(3) macht aus iceberg ice.
    • void: Immer null. Damit entfernt man Felder in v1-Tabellen.
  2. Bucket-Hash: 32-bit Murmur3 (x86, Seed 0): (murmur3(x) & Integer.MAX_VALUE) % N. Jede Engine muss gleich rechnen, darum ist der Hash in der Spec festgelegt.
  3. Spark-Syntax: PARTITIONED BY nimmt year, month, day, hour, bucket(N, col), truncate(L, col). Die alten Formen years, months, days, hours gehen auch.
  4. Hive-Problem 1: In Hive ist die Partition eine echte Spalte, z. B. dt STRING. Der Writer muss sie korrekt füllen. Ein falsches Format oder eine falsche Zeitzone ergibt stille Fehler.
  5. Hive-Problem 2: Der Reader muss WHERE dt = … zusätzlich schreiben. Filtert er nur received_date, liest er alles.
  6. Hive-Problem 3: Ein Layout-Wechsel braucht eine neue Tabelle und neue Abfragen.
  7. Inclusive Projection: Iceberg wählt alle Dateien, die passen könnten. Den Rest filtert es beim Lesen (Residual Filter).
  8. Partition Evolution: ADD, DROP und REPLACE PARTITION FIELD. Jede Änderung ist eine neue Spec mit neuer spec-id. Alte Daten bleiben, wie sie sind.
  9. Partition Field IDs: Sie beginnen bei 1000 und bleiben stabil. Gleichwertige Felder müssen ihre ID wiederverwenden. In v2 sind sie über alle Specs eindeutig.
  10. v1-Regeln: Felder nicht umsortieren, nicht löschen (stattdessen void), neue Felder nur ans Ende.
  11. DROP PARTITION FIELD: Die Quellspalte bleibt im Schema. Aber das Schema der Metadata Tables (z. B. .files) ändert sich.
  12. Dynamic Overwrite ändert sich: INSERT OVERWRITE im dynamischen Modus ersetzt nach der aktuellen Spec. Nach Wechsel von Tag auf Stunde ersetzt er Stunden, nicht mehr Tage. Besser explizit mit DataFrameWriterV2.overwrite(condition).
  13. Zeitzone: Spark TIMESTAMP ist in Iceberg timestamptz, also UTC. day() schneidet nach UTC-Tag, nicht nach Schweizer Tag.
  14. SQL-Funktionen: system.days(ts), system.bucket(16, id) zeigen den Transform-Wert in Abfragen. Sie funktionieren nur über einen Iceberg-Catalog.
  15. Type Promotion: Eine Partitions-Quellspalte darf nur so geändert werden, dass der Transform gleich bleibt. int → long geht beim Bucket, int → string nicht.
  16. v3: Die Spec erlaubt Multi-Argument-Transforms (mehrere Quellspalten). Engine-Support prüfen.

5. Vergleich

  • Hive-Partitionen: sichtbare Spalte, Ordner pro Wert, starres Layout, User muss Partitionsfilter kennen.
  • Iceberg Hidden Partitioning: Transform auf echter Spalte, Wert nur in Metadaten, Filter wird abgeleitet, Layout änderbar.
  • Delta Lake: Partitionen über Spalten, abgeleitete Werte über Generated Columns. Layout-Wechsel braucht Umschreiben. Alternative: Liquid Clustering.
  • Sortierung statt Partition: Eine Sort Order (WRITE ORDERED BY) gibt enge Min/Max pro Datei. Gut für Spalten mit hoher Kardinalität, die man nicht partitionieren will.
  • SQL-Server-Partitionierung: Partition Function und Scheme pro Tabelle, für OLTP und Wartung. Kein Engine-übergreifendes Format.

6. In der Produktion

  1. Zu feine Partitionen: hour() plus identity auf vielen Werten ergibt Tausende winzige Dateien. Abfragen und Planung werden langsam. Lösung: gröber partitionieren, Compaction, Ziel ist Dateigrösse nahe write.target-file-size-bytes (Standard 512 MB).
  2. Kein Pruning: Die Abfrage filtert to_date(received_date) = '2026-11-02' oder einen String. Der Filter wird nicht zum Partitionsfilter. Lösung: Bereich direkt auf der Spalte schreiben, Plan mit EXPLAIN prüfen.
  3. Tag nach UTC statt Ortszeit: Ein Report „pro Tag“ zählt Daten um Mitternacht im falschen Tag. Lösung: Zeitzone bewusst definieren und in der Geschäftslogik umrechnen.
  4. Viele offene Writer pro Task: Unsortierte Daten mit vielen Partitionen erzeugen viele Dateien pro Task und viel Speicher. Lösung: write.distribution-mode passend setzen (z. B. hash), Daten vor dem Write nach Partition verteilen.
  5. Overwrite nach Spec-Wechsel: Ein Job mit dynamischem Overwrite ersetzt plötzlich andere Bereiche. Lösung: explizites Overwrite mit Bedingung.
  6. Metadata-Queries brechen: Nach DROP PARTITION FIELD erwartet ein Monitoring-Query noch die alte Spalte in .partitions. Lösung: Queries anpassen, Feld lieber ersetzen als löschen.

7. Diagnose: Werkzeuge und Befehle

  • DESCRIBE TABLE EXTENDED t / SHOW CREATE TABLE t: aktuelle Partition Spec.
  • SELECT * FROM t.partitions: Zeilen, Dateien und Grösse pro Partition, inkl. spec_id.
  • SELECT spec_id, partition, count(*), avg(file_size_in_bytes) FROM t.files GROUP BY 1, 2: Small Files pro Partition.
  • EXPLAIN und Spark UI: Pushed Filters und Anzahl gelesener Dateien.
  • SELECT system.days(received_date), system.bucket(8, message_id) FROM t: welchen Partitionswert eine Zeile bekommt.
  • metadata.json: partition-specs, default-spec-id, last-partition-id.

8. Senior-Punkte

  1. Nach Abfragen partitionieren, nicht nach Bauchgefühl. Die häufigsten Filter entscheiden. Zeit plus eine kleine Kategorie ist oft genug.
  2. Lieber zu grob als zu fein. Zu feine Partitionen kosten mehr als zu grobe. Evolution erlaubt es, später feiner zu werden.
  3. Partition und Sortierung zusammen denken. Partition für grobe Filter, Sort Order für Min/Max innerhalb der Partition.
  4. Evolution ist kein Umbau. Alte Daten bleiben im alten Layout. Wer einheitliches Layout will, plant eine Compaction.
  5. Hidden Partitioning schützt vor User-Fehlern. Niemand muss eine Partitionsspalte kennen oder richtig füllen. Das macht die Tabelle für viele Engines und Teams sicher.
  6. bucket für Joins und Upserts: Gleich gebuckete Tabellen erlauben in Spark Storage-Partitioned Joins ohne Shuffle. Die Anzahl Buckets ist aber schwer zu ändern.

10. Fallen

  • „Bei Iceberg muss ich auf die Partitionsspalte filtern.“ → Falsch. Man filtert die echte Spalte. Iceberg leitet den Partitionsfilter ab.
  • „Partition Evolution schreibt die Daten um.“ → Falsch. Nur Metadaten ändern sich. Alte Dateien bleiben in der alten Spec.
  • „Die Ordnerstruktur bestimmt die Partition.“ → Falsch. Die Partition steht im Manifest. Ordnernamen sind nur Konvention.
  • „Mehr Partitionen machen Abfragen immer schneller.“ → Falsch. Zu viele Partitionen erzeugen Small Files und lange Planung.
  • „days(ts) teilt nach lokalem Tag.“ → Falsch. Bei timestamptz nach UTC-Tag.
  • „DROP PARTITION FIELD löscht die Spalte.“ → Falsch. Nur das Partitionsfeld. Die Spalte bleibt im Schema.

11. Fragen

Was ist Hidden Partitioning?

Partitionierung über Transforms auf normalen Spalten. Der Partitionswert steht nur in den Metadaten, und Iceberg leitet Partitionsfilter aus normalen Filtern ab.

Welche Probleme von Hive löst es?

Keine extra Spalte füllen, kein vergessener Partitionsfilter, keine falschen Formate. Und das Layout kann sich ändern, ohne Abfragen zu ändern.

Welche Transforms gibt es?

identity, year, month, day, hour, bucket[N], truncate[W] und void.

Wann nutze ich bucket?

Bei Spalten mit hoher Kardinalität wie IDs, wenn man gleichmässig verteilen oder Joins ohne Shuffle will.

Wie wird bucket berechnet?

32-bit Murmur3-Hash, Vorzeichenbit entfernt, modulo N. Die Spec legt das fest, damit alle Engines gleich rechnen.

Was macht truncate?

Strings auf L Zeichen kürzen, Zahlen auf Vielfache von W abrunden. Beispiel: truncate(10) macht aus 17 eine 10.

Was ist eine Partition Spec?

Die Liste der Partitionsfelder: Quellspalte, Transform, Name, Partition Field ID. Eine Tabelle kann mehrere Specs haben, eine ist der Standard.

Wie ändert man die Partitionierung in Spark?

ALTER TABLE … ADD, DROP oder REPLACE PARTITION FIELD. Dafür braucht es die Iceberg SQL Extensions.

Was passiert mit alten Daten bei Partition Evolution?

Nichts. Sie bleiben in der alten Spec. Abfragen planen jede Spec getrennt (Split Planning).

Wie bringe ich alte Daten ins neue Layout?

Mit rewrite_data_files. Die Compaction schreibt die Dateien mit der aktuellen Spec neu.

Was ist inclusive projection?

Iceberg übersetzt einen Spaltenfilter in einen Partitionsfilter, der alle möglichen Treffer einschliesst. Der genaue Filter läuft danach beim Lesen.

Warum wird mein Filter nicht zum Partitionsfilter?

Weil eine Funktion auf der Spalte steht, z. B. to_date(col) oder ein String-Vergleich. Besser einen Bereich direkt auf der Spalte schreiben.

Was ist der void-Transform?

Er liefert immer null. In v1-Tabellen ersetzt man damit ein Feld, statt es zu löschen.

Warum sind Partition Field IDs wichtig?

Sie sind die Feld-IDs der Partitionswerte in den Manifests. Bleiben sie stabil, lesen Metadaten aller Specs korrekt.

Wie ändert Partition Evolution dynamische Overwrites?

Dynamic Overwrite ersetzt nach der aktuellen Spec. Nach einem Wechsel werden andere Bereiche ersetzt. Darum explizit mit Bedingung überschreiben.

Partitionieren oder sortieren?

Partition für grobe, häufige Filter mit wenigen Werten. Sort Order für feine Filter auf vielen Werten innerhalb der Partition.

Welche Zeitzone nutzt day()?

Bei timestamptz die UTC-Zeit. Für Spark TIMESTAMP ist das der Fall.

Darf ich den Typ einer Partitions-Quellspalte ändern?

Nur wenn der Transform danach gleiche Werte liefert, z. B. int zu long beim Bucket. Sonst lehnt Iceberg die Änderung ab.

Szenario: Eine Tabelle ist nach hour(ts) und customer_id partitioniert, Abfragen sind langsam. Was tun Sie?

In t.files die Dateigrössen prüfen; wahrscheinlich viele winzige Dateien. Spec auf day(ts) und bucket(N, customer_id) ändern und alte Daten mit rewrite_data_files verdichten.

Szenario: Das Volumen ist zehnmal gestiegen, Tagespartitionen sind riesig. Brauchen Sie eine neue Tabelle?

Nein. ADD PARTITION FIELD, z. B. bucket auf eine ID, oder REPLACE von day auf hour. Neue Daten nutzen das neue Layout, Abfragen bleiben gleich.

Szenario: Ein Tagesreport zeigt Daten kurz nach Mitternacht am falschen Tag. Woran denken Sie?

An die Zeitzone: day() und viele Spark-Funktionen rechnen in UTC oder der Session-Zeitzone. Lösung: Geschäftstag explizit mit Zeitzone berechnen und Tests an der Tagesgrenze.
