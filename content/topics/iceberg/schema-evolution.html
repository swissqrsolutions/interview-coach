Schema Evolution

Schema Evolution ist das Ändern des Tabellenschemas ohne Umschreiben der Daten: Spalten hinzufügen, löschen, umbenennen, umsortieren oder Typen erweitern. Iceberg erkennt jede Spalte an einer festen Field ID, nicht an Name oder Position. Darum ist jede Änderung eine reine Metadaten-Änderung und liefert nie falsche Werte aus alten Dateien.

1. Wo sitzt das Schema?

  1. schemas: metadata.json hält alle Schema-Versionen mit schema-id. current-schema-id zeigt auf die aktuelle.
  2. Field ID: Jede Spalte, auch jedes Feld in Structs, Listen und Maps, hat eine eindeutige ID. Beispiel: 2 bleibt 2, auch nach Umbenennung von name zu party.
  3. last-column-id: Die höchste je vergebene ID. Neue Spalten bekommen immer eine neue ID. IDs werden nie wiederverwendet.
  4. Datendatei: Parquet speichert die Field ID je Spalte (field_id). Eine Datei wird nie wegen eines Schema-Wechsels umgeschrieben.
  5. Reader: Liest mit dem aktuellen Schema und sucht Spalten in der Datei nach ID. Fehlt eine ID, liefert er den Default oder null.

2. Die Reise einer Spalte (die Geschichte zum Merken)

  1. Anlegen: Ein Team fügt die Spalte note hinzu. Iceberg vergibt ID 5. Neue Dateien schreiben Werte unter ID 5.
  2. Umbenennen: note heisst jetzt comment. Nur der Name im Schema ändert sich. Alte Dateien liefern weiter ihre Werte, weil die ID gleich bleibt.
  3. Löschen: comment wird gelöscht. ID 5 steht nicht mehr im aktuellen Schema. Die Werte liegen noch in alten Dateien, aber niemand liest sie.
  4. Neu mit altem Namen: Später fügt jemand wieder note hinzu. Iceberg vergibt ID 6, nicht 5.
  5. Lesen: Iceberg sucht in alten Dateien ID 6 und findet sie nicht. Ergebnis: null. Das ist richtig. Ein Format nach Name würde die alten Werte von note wieder anzeigen.
  6. Position: Ein Format nach Position verschiebt beim Löschen alle Spalten dahinter. Iceberg hat dieses Problem nicht, weil die Reihenfolge nur Anzeige ist.

3. Beispiel: alle Änderungen in Spark SQL

-- Spark SQL, Iceberg 1.x mit SQL Extensions, Catalog "cat" (Beispieltabelle)
CREATE TABLE cat.demo.trades (id BIGINT, name STRING, amount INT, price FLOAT)
USING iceberg;
INSERT INTO cat.demo.trades VALUES (1, 'A', 100, 1.5);

ALTER TABLE cat.demo.trades ADD COLUMN currency STRING AFTER amount;   -- add + Position
ALTER TABLE cat.demo.trades RENAME COLUMN name TO counterparty;        -- rename
ALTER TABLE cat.demo.trades ALTER COLUMN amount TYPE BIGINT;           -- int → long
ALTER TABLE cat.demo.trades ALTER COLUMN price TYPE DOUBLE;            -- float → double
ALTER TABLE cat.demo.trades ALTER COLUMN price FIRST;                  -- reorder
ALTER TABLE cat.demo.trades DROP COLUMN currency;                      -- drop
ALTER TABLE cat.demo.trades ADD COLUMN currency STRING;                -- gleicher Name, neue ID

SELECT * FROM cat.demo.trades;

ALTER TABLE cat.demo.trades ALTER COLUMN counterparty TYPE INT;        -- nicht erlaubt
price  id  counterparty  amount  currency
1.5    1   A             100     NULL

-- letzte Zeile:
AnalysisException / IllegalArgumentException: Cannot change column type: counterparty: string -> int

-- metadata.json danach (gekürzt):
"current-schema-id" : 7,
"last-column-id" : 6,
"schemas" : [ … , { "schema-id" : 7, "fields" : [
   { "id" : 4, "name" : "price",        "type" : "double" },
   { "id" : 1, "name" : "id",           "type" : "long"   },
   { "id" : 2, "name" : "counterparty", "type" : "string" },
   { "id" : 3, "name" : "amount",       "type" : "long"   },
   { "id" : 6, "name" : "currency",     "type" : "string" } ] } ]

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Genauer Fehlertext hängt von Spark- und Iceberg-Version ab; Schema-IDs sind Beispielwerte.

  1. Kein Befehl schreibt eine Datendatei. Jeder erzeugt nur eine neue metadata.json mit neuer schema-id.
  2. Die alte Zeile wird mit dem neuen Schema gelesen: amount als long, price als double, counterparty mit dem alten Wert.
  3. Die gelöschte Spalte hatte ID 5. Die neue currency hat ID 6. Darum ist sie für alte Zeilen NULL.
  4. string → int ist keine erlaubte Promotion. Iceberg lehnt die Änderung ab, statt Daten kaputt zu machen.
  5. AFTER und FIRST brauchen die Iceberg SQL Extensions.

4. Details, die Interviewer fragen

  1. Fünf Operationen: Add (neue Spalte, auch in Structs), Drop, Rename, Update (Typ erweitern), Reorder. Alle sind Metadaten-Änderungen.
  2. Erlaubte Type Promotions (v1/v2): int → long, float → double, decimal(P,S) → decimal(P',S) mit P' > P. Nur die Präzision wächst, die Scale nie.
  3. Zusätzlich in v3: date → timestamp oder timestamp_ns (nicht zu timestamptz), und der Typ unknown zu jedem Typ.
  4. Nicht erlaubt: Verkleinern (long → int), Typwechsel (string → int), Felder in ein neues Struct verschieben, Primitive zu Struct machen.
  5. Garantien der Doku: Neue Spalten lesen nie Werte anderer Spalten. Drop ändert keine anderen Spalten. Update ändert keine anderen Spalten. Reorder ändert keine Werte.
  6. Pflichtspalten: Spark fügt neue Spalten als optional hinzu. Eine required-Spalte braucht in v3 initial-default und write-default ungleich null. DROP NOT NULL ist erlaubt, der Weg zurück nicht.
  7. Default-Werte (v3): initial-default gilt für alle Zeilen, die vor dem Hinzufügen geschrieben wurden. write-default gilt für neue Zeilen ohne Wert. Kein Umschreiben nötig.
  8. Column Projection: Fehlt eine ID in einer Datei, gilt diese Reihenfolge: Identity-Partitionswert aus dem Manifest, dann Name Mapping, dann initial-default, sonst null.
  9. Name Mapping: Migrierte Hive-Dateien haben keine Field IDs. schema.name-mapping.default ordnet Namen zu IDs zu. So funktioniert eine Migration ohne Umschreiben.
  10. Verschachtelte Typen: Felder in Structs, Elemente in Listen und Werte in Maps haben eigene IDs. Map-Keys dürfen keine Struct-Felder hinzufügen oder entfernen, die Gleichheit ändern.
  11. Statistiken: Min/Max stehen in Manifests nach Field ID. Bei Promotion werden alte Grenzen nicht umgeschrieben. Der Reader erkennt den alten Typ an der Byte-Länge (4 Bytes = int, 8 = long).
  12. Partitionsspalten: Eine Promotion ist verboten, wenn der Partition Transform danach andere Werte liefert.
  13. Kein Snapshot: Eine Schema-Änderung erzeugt eine neue metadata.json, aber keinen Snapshot.
  14. Konflikte: Ein Schema-Commit prüft, dass sich das Schema seit dem Laden nicht geändert hat. Sonst scheitert er.
  15. Schema beim Schreiben anpassen: Mit write.spark.accept-any-schema = true und der Option mergeSchema = true fügt Spark neue Spalten automatisch hinzu.
  16. Identifier Fields: ALTER TABLE … SET IDENTIFIER FIELDS id markiert Schlüsselspalten, z. B. für Upserts in Flink. Iceberg erzwingt sie nicht als Primary Key.

5. Vergleich

  • Iceberg: nach Field ID. Rename, Drop, Reorder und Widen sind sicher und billig.
  • Hive mit Parquet (nach Name): Rename verliert alte Werte. Drop und Re-Add mit gleichem Namen holt alte Werte zurück.
  • Hive mit CSV oder ORC nach Position: Drop in der Mitte verschiebt Werte. Nur Hinzufügen am Ende ist sicher.
  • Delta Lake: Ohne Column Mapping nach Name. Rename und Drop brauchen delta.columnMapping.mode = name. Typ-Erweiterung über das Feature Type Widening.
  • Avro: Schema Resolution nach Name mit Aliases und Defaults. Gut für Nachrichten, aber pro Datei, ohne Tabellen-Katalog.
  • SQL Server: ALTER TABLE ändert die Tabelle direkt. Manche Änderungen schreiben alle Zeilen um und sperren lange.

6. In der Produktion

  1. Downstream bricht nach Rename: Iceberg ist korrekt, aber Views, BI-Reports und Jobs nutzen den alten Namen. Lösung: Rename wie eine API-Änderung behandeln, zuerst Consumer anpassen.
  2. Typ passt nicht mehr: Ein Feld kam als string und soll decimal werden. Das ist keine Promotion. Lösung: neue Spalte hinzufügen, per Job füllen, Consumer umstellen, alte Spalte löschen.
  3. Ungewollte Spalten: mergeSchema nimmt jeden Tippfehler aus der Quelle als neue Spalte. Lösung: Schema im Job explizit prüfen, Merge nur bewusst erlauben.
  4. Gecachtes Schema: Eine Engine liest noch mit alten Metadaten und kennt die neue Spalte nicht. Lösung: Metadaten-Refresh der Engine oder Tabelle neu laden.
  5. Gelöschte Daten liegen noch da: Drop entfernt Werte nicht aus Dateien. Für Datenschutz reicht das nicht. Lösung: Dateien umschreiben (Compaction), dann Snapshots ablaufen lassen.
  6. Migrierte Tabelle liest null: Nach Hive-Migration fehlen Field IDs in alten Dateien. Lösung: schema.name-mapping.default setzen (die Migrations-Prozeduren tun das).

7. Diagnose: Werkzeuge und Befehle

  • DESCRIBE TABLE t / SHOW CREATE TABLE t: aktuelles Schema.
  • metadata.json: schemas, current-schema-id, last-column-id, Field IDs pro Spalte.
  • SELECT * FROM t.metadata_log_entries: latest_schema_id pro Metadaten-Version, also wann sich das Schema änderte.
  • SELECT * FROM t.snapshots: Spalte schema_id zeigt, mit welchem Schema ein Snapshot geschrieben wurde.
  • parquet-tools schema / parquet meta: field_id in einer Datendatei prüfen.
  • SHOW TBLPROPERTIES t: schema.name-mapping.default, write.spark.accept-any-schema.

8. Senior-Punkte

  1. IDs statt Namen sind der Kern. Wer das erklärt, erklärt auch, warum Hive falsche Werte liefern kann.
  2. Billig für die Tabelle heisst nicht billig für Consumer. Schema-Änderungen brauchen Kommunikation, Versionierung und Tests mit Downstream.
  3. Nur erweitern, nie verengen. Wer einen Typ wirklich ändern muss, plant Add, Backfill, Switch, Drop.
  4. Automatische Schema-Merges sind riskant. Für eine regulierte Plattform ist ein expliziter Vertrag (Schema im Code, Review) besser.
  5. Drop ist kein Löschen. Die Werte bleiben in alten Dateien und Snapshots. Das ist wichtig für Datenschutz.
  6. Format-Version zählt. Defaults und neue Promotions gibt es erst in v3. Alle Engines müssen v3 können.

10. Fallen

  • „Eine Spalte umbenennen heisst Daten umschreiben.“ → Falsch. Nur der Name im Schema ändert sich. Die Field ID bleibt.
  • „Drop und Re-Add mit gleichem Namen bringt die alten Werte zurück.“ → Falsch bei Iceberg. Die neue Spalte hat eine neue ID und ist für alte Zeilen null.
  • „Iceberg kann jeden Typ ändern.“ → Falsch. Nur Erweiterungen: int → long, float → double, Decimal-Präzision, in v3 date → timestamp.
  • „DROP COLUMN löscht die Daten.“ → Falsch. Die Werte bleiben in den Dateien, nur unsichtbar.
  • „Schema Evolution erzeugt einen Snapshot.“ → Falsch. Nur eine neue metadata.json mit neuer schema-id.
  • „Ich kann jederzeit eine Pflichtspalte hinzufügen.“ → Falsch. Ohne Default-Werte (v3) geht nur eine optionale Spalte.

11. Fragen

Was ist Schema Evolution in Iceberg?

Spalten hinzufügen, löschen, umbenennen, umsortieren oder erweitern, ohne Daten umzuschreiben. Jede Änderung ist eine neue Schema-Version in metadata.json.

Warum ist das in Iceberg sicher?

Jede Spalte hat eine feste Field ID. Reader suchen Spalten in Dateien nach ID, nicht nach Name oder Position.

Welche Type Promotions sind erlaubt?

int zu long, float zu double, decimal mit grösserer Präzision. In v3 zusätzlich date zu timestamp oder timestamp_ns und unknown zu jedem Typ.

Was passiert bei Drop und Re-Add mit gleichem Namen?

Die neue Spalte bekommt eine neue ID. Alte Zeilen zeigen null, nicht die alten Werte.

Warum ist Lesen nach Name gefährlich?

Ein gelöschter und wieder angelegter Name holt alte Werte zurück. Ein Rename verliert die alten Werte.

Warum ist Lesen nach Position gefährlich?

Löscht man eine Spalte in der Mitte, rutschen alle folgenden Spalten. Werte landen in falschen Spalten.

Was ist last-column-id?

Die höchste je vergebene Field ID. Neue Spalten bekommen immer eine höhere ID. IDs werden nie wiederverwendet.

Kann ich eine Pflichtspalte hinzufügen?

In v3 mit initial-default und write-default ungleich null. Sonst nur optionale Spalten.

Was sind initial-default und write-default?

initial-default gilt für Zeilen von vor dem Hinzufügen. write-default gilt für neue Zeilen ohne Wert. Beides ohne Umschreiben, ab v3.

Wie ändert man die Spaltenreihenfolge?

ALTER TABLE … ALTER COLUMN col FIRST oder AFTER other. Nur Metadaten, mit Iceberg SQL Extensions.

Wie ändere ich string zu int?

Gar nicht direkt. Neue Spalte anlegen, per Job füllen, Consumer umstellen, alte Spalte löschen.

Was ist ein Name Mapping?

Die Property schema.name-mapping.default ordnet Spaltennamen Field IDs zu. Sie hilft bei Dateien ohne IDs, z. B. nach einer Hive-Migration.

Erzeugt eine Schema-Änderung einen Snapshot?

Nein. Nur eine neue metadata.json mit neuer schema-id.

Welches Schema nutzt Time Travel?

Mit Snapshot-ID oder Zeitstempel das Schema des Snapshots. Mit einem Branch das aktuelle Tabellenschema.

Wie funktionieren Min/Max-Statistiken nach int zu long?

Alte Grenzen bleiben 4 Bytes. Der Reader erkennt an der Länge, dass sie als int geschrieben wurden.

Kann Spark das Schema beim Schreiben automatisch erweitern?

Ja, mit write.spark.accept-any-schema = true und der Option mergeSchema = true. Das sollte man bewusst und kontrolliert einsetzen.

Iceberg vs Delta Lake bei Schema Evolution?

Iceberg nutzt immer IDs. Delta braucht Column Mapping im Modus name für sicheres Rename und Drop.

Was sind Identifier Fields?

Markierte Schlüsselspalten, z. B. für Upserts in Flink. Iceberg prüft sie nicht als Primary Key.

Szenario: Nach einem Rename zeigt ein BI-Dashboard leere Werte. Ist Iceberg schuld?

Nein, Iceberg liest die Daten korrekt. Das Dashboard oder eine View nutzt den alten Namen oder ein gecachtes Schema. Lösung: Consumer anpassen, Metadaten-Refresh, Renames vorher ankündigen.

Szenario: Eine neue XML-Version liefert ein zusätzliches Feld. Wie gehen Sie vor?

ALTER TABLE ADD COLUMN als optionale Spalte, Parser anpassen, Tests für alte und neue Version. Alte Zeilen haben null; ein Backfill ist nur nötig, wenn die Quelle den Wert hat.

Szenario: Eine Spalte mit Personendaten muss weg. Reicht DROP COLUMN?

Nein. Die Werte liegen noch in Dateien und alten Snapshots. Nach dem Drop Dateien per Compaction umschreiben und Snapshots ablaufen lassen.
