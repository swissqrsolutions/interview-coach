Was ist ein Table Format? Iceberg-Grundlagen

Kern: Ein Table Format ist eine Metadaten-Schicht, die viele Datendateien zu einer Tabelle macht. Apache Iceberg verfolgt jede Datei einzeln und ändert die Tabelle nur über einen atomaren Commit. So bekommt man ACID auf Object Storage, und mehrere Engines (Spark, Dremio, Trino, Flink) nutzen dieselbe Tabelle.

1. Wo sitzt Iceberg im Lakehouse?

  1. Engines: Rechnen und SQL ausführen. Beispiel: Spark schreibt, Dremio liest dieselbe Tabelle.
  2. Catalog: Kennt pro Tabelle nur einen Zeiger auf die aktuelle metadata.json. Beispiel: Nessie speichert ihn in Postgres.
  3. Iceberg-Metadaten: Beschreiben Schema, Partitionierung, Snapshots und jede einzelne Datei. Sie liegen als Dateien neben den Daten.
  4. Datendateien: Normale, unveränderliche Parquet-Dateien. Iceberg ändert nie eine bestehende Datei.
  5. Object Storage: Speichert alles. Iceberg braucht nur Schreiben, Lesen mit Seek und Löschen. Ein atomares rename ist nicht nötig.

2. Die Reise eines Commits (die Geschichte zum Merken)

  1. Daten schreiben: Ein Spark-Job schreibt neue Parquet-Dateien in data/. Noch sieht sie niemand. Sie sind nur Dateien ohne Tabelle.
  2. Manifest schreiben: Ein Manifest ist eine Avro-Datei, die jede neue Datei mit Partition, Zeilenzahl und Min/Max-Werten pro Spalte auflistet.
  3. Manifest List schreiben: Die Manifest List zählt alle Manifests des neuen Stands auf. Sie ist der neue Snapshot, also der Tabellenstand nach diesem Commit.
  4. metadata.json schreiben: Eine neue Datei 00005-….metadata.json enthält Schema, Partition Spec und die Snapshot-Liste mit dem neuen Snapshot.
  5. Atomarer Swap: Der Writer bittet den Catalog: „Setze den Zeiger von v4 auf v5, aber nur wenn er noch v4 ist.“ Das ist optimistic concurrency. Nur dieser eine Schritt ist atomar, und er reicht.
  6. Sichtbar: Neue Reader laden v5. Reader, die schon v4 geladen haben, lesen v4 fertig. Niemand sieht einen halben Stand.
  7. Konflikt: War ein anderer Writer schneller, scheitert der Swap. Der Writer prüft, ob seine Änderung noch passt, und versucht es neu (Standard: commit.retry.num-retries = 4). Ein Append passt fast immer.

3. Beispiel: eine Iceberg-Tabelle anlegen und hineinschauen

-- Spark SQL, Iceberg 1.x, Catalog "cat" (Beispieltabelle, nicht das echte Projektschema)
CREATE TABLE cat.demo.reports (
  message_id    STRING,
  schema_type   STRING,
  received_date TIMESTAMP,
  volume        DECIMAL(18,4))
USING iceberg
PARTITIONED BY (days(received_date), schema_type)
TBLPROPERTIES ('format-version' = '2');

INSERT INTO cat.demo.reports VALUES
  ('m-1', 'TRADE', TIMESTAMP '2026-11-02 08:15:00', 10.5),
  ('m-2', 'ORDER', TIMESTAMP '2026-11-02 09:00:00', 3.0);

SELECT snapshot_id, operation, summary['added-data-files'] AS files,
       summary['total-records'] AS rows
FROM cat.demo.reports.snapshots;
snapshot_id          operation  files  rows
3051729675574597004  append     2      2

-- Dateien im Object Storage (gekürzt):
s3://lake/demo/reports/metadata/00000-1b2c….metadata.json      (CREATE)
s3://lake/demo/reports/metadata/00001-7d4e….metadata.json      (INSERT)
s3://lake/demo/reports/metadata/snap-3051729675574597004-1-9a1f….avro   (Manifest List)
s3://lake/demo/reports/metadata/9a1f…-m0.avro                  (Manifest)
s3://lake/demo/reports/data/received_date_day=2026-11-02/schema_type=ORDER/00000-0-….parquet
s3://lake/demo/reports/data/received_date_day=2026-11-02/schema_type=TRADE/00000-0-….parquet

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Snapshot-ID und UUIDs sind Beispielwerte. Der Pfad hängt vom Catalog und der Warehouse-Location ab.

  1. USING iceberg macht die Tabelle zu einer Iceberg-Tabelle. Der Catalog cat merkt sich nur den Zeiger auf die neueste metadata.json.
  2. Ein INSERT erzeugt genau einen Snapshot mit operation = append.
  3. Pro Commit entsteht eine neue metadata.json. Die alte bleibt liegen, bis man sie aufräumt.
  4. Zwei Partitionen ergeben zwei Parquet-Dateien. Die Ordnernamen sind nur Konvention. Iceberg findet Dateien über Manifests, nie über Ordner-Listing.
  5. .snapshots ist eine Metadata Table, also eine virtuelle Tabelle über die Metadaten. Es gibt auch .history, .files, .manifests, .partitions, .refs.

4. Details, die Interviewer fragen

  1. Problem 1 – kein Commit bei Parquet-Ordnern: Ein Reader listet den Ordner, während ein Job schreibt. Er sieht halbe Ergebnisse. Ein abgebrochener Job hinterlässt Dateien, die als Daten gelten.
  2. Problem 2 – Hive kennt nur Ordner: Der Hive Metastore speichert Partitionen als Ordner, nicht einzelne Dateien. Jede Abfrage muss Ordner listen. Auf S3 kostet ein LIST-Aufruf Zeit und liefert maximal 1000 Keys pro Seite.
  3. Problem 3 – Rename ist auf S3 nicht atomar: Hive- und Hadoop-Commits schreiben in einen Temp-Ordner und benennen um. Auf S3 ist Rename ein Kopieren plus Löschen. Ein Absturz mittendrin hinterlässt einen kaputten Stand.
  4. Problem 4 – sichtbare Partitionsspalten: In Hive muss der User eine extra Spalte wie dt füllen und filtern. Vergisst er den Filter, liest er die ganze Tabelle. Iceberg löst das mit Hidden Partitioning.
  5. Problem 5 – Schema nach Name oder Position: Hive liest Spalten nach Name oder Position. Umbenennen oder Löschen kann falsche Werte liefern. Iceberg nutzt Field IDs.
  6. Atomicity: Ein Commit ist ein einziger Compare-and-Swap des Metadaten-Zeigers im Catalog. Entweder alles oder nichts.
  7. Consistency: Beim Retry prüft Iceberg Regeln. Beispiel: Eine Compaction darf nur committen, wenn die ersetzten Dateien noch in der Tabelle sind.
  8. Isolation: Reader lesen einen festen Snapshot (Snapshot Isolation). Für DELETE, UPDATE, MERGE ist der Standard serializable (write.delete.isolation-level usw.).
  9. Durability: Alle Dateien sind unveränderlich im Object Storage. Der Catalog-Zeiger liegt in einer Datenbank, z. B. Postgres.
  10. Format-Versionen: v1: analytische Tabellen, nur Append und Overwrite ganzer Dateien. v2: Row-level Deletes über Delete Files und Sequence Numbers. v3: Deletion Vectors, Row Lineage, Default-Werte, neue Typen (variant, geometry, geography, timestamp_ns, unknown). v4 ist noch in Arbeit.
  11. Standard-Version: Iceberg 1.x legt neue Tabellen mit format-version = 2 an (seit 1.4.0). v3 muss man bewusst setzen, wenn alle Reader es können.
  12. Snapshot: Ein Snapshot ist der vollständige Tabellenstand nach einem Commit. Er ermöglicht Time Travel und Rollback.
  13. File Formats: Datendateien sind Parquet (Standard), ORC oder Avro. Manifests und Manifest Lists sind Avro. metadata.json ist JSON.
  14. Catalog-Arten: REST Catalog (offener HTTP-Standard), Nessie (Git-artige Commits über Tabellen), Hive Metastore, AWS Glue, JDBC. Alle speichern den Zeiger und machen den Swap atomar.
  15. Row-level Änderungen: Copy-on-Write schreibt betroffene Dateien neu. Merge-on-Read schreibt kleine Delete Files, Reader verrechnen sie. Standard ist Copy-on-Write (write.delete.mode).

5. Vergleich

  • Parquet-Ordner: nur ein File Format. Keine Transaktionen, kein Schema-Vertrag, Planung über Ordner-Listing.
  • Hive-Tabelle: Metastore mit Ordner-Partitionen. Kein atomarer Multi-Partition-Commit, Partitionsspalte sichtbar, Layout nicht änderbar.
  • Apache Iceberg: Dateiliste in Metadaten, atomarer Commit, Hidden Partitioning, Partition und Schema Evolution, offene Spec, viele Engines.
  • Delta Lake: Transaktions-Log (_delta_log) mit JSON-Commits und Checkpoints. Stark in Spark und Databricks. Partitionierung klassisch über Spalten (dazu Liquid Clustering).
  • Apache Hudi: Fokus auf Upserts und inkrementelle Pipelines (Timeline, Record-Level-Index). Mehr Betriebsaufwand.
  • Data Warehouse (z. B. SQL Server, Snowflake intern): Speicher und Engine sind eins. Schnell für viele kleine Transaktionen, aber kein offenes Format für mehrere Engines.

6. In der Produktion

  1. Catalog verloren: Liegt der Catalog-Zeiger in flüchtigem Speicher, ist die Tabelle nach einem Pod-Neustart „weg“. Die Dateien sind noch da, aber niemand kennt die aktuelle metadata.json. Lösung: Catalog mit echter Datenbank (z. B. Nessie auf Postgres) und Backups.
  2. Small Files: Viele kleine Commits erzeugen viele kleine Parquet-Dateien und Manifests. Abfragen werden langsam. Lösung: Batches bündeln, rewrite_data_files und rewrite_manifests regelmässig.
  3. Metadaten wachsen: Jeder Commit schreibt eine neue metadata.json und behält alte Snapshots. Lösung: expire_snapshots, write.metadata.delete-after-commit.enabled = true.
  4. Orphan Files: Abgebrochene Jobs hinterlassen Dateien, die kein Snapshot kennt. Lösung: remove_orphan_files (Standard: nur älter als 3 Tage).
  5. Commit-Konflikte: Zwei Jobs ändern gleichzeitig dieselben Dateien. Einer scheitert mit CommitFailedException oder ValidationException. Lösung: Jobs nicht überlappen lassen, Arbeit sauber aufteilen.
  6. Reader zu alt: Eine Engine kann eine neuere Format-Version oder Delete Files nicht lesen. Lösung: Format-Version nach dem schwächsten Reader wählen.

7. Diagnose: Werkzeuge und Befehle

  • SELECT * FROM t.snapshots / t.history: welche Commits es gab, mit Operation und Summary.
  • SELECT * FROM t.files: jede Datendatei mit Grösse, Zeilen, Partition und Min/Max.
  • SELECT * FROM t.manifests und t.partitions: Anzahl Manifests, Dateien pro Partition.
  • SELECT * FROM t.metadata_log_entries: Kette der metadata.json-Dateien.
  • SHOW TBLPROPERTIES t und DESCRIBE TABLE EXTENDED t: Format-Version, Modi, Partition Spec.
  • Object Storage direkt ansehen (z. B. mc ls bei MinIO): Ordner metadata/ und data/.
  • Catalog-Log (z. B. Nessie-Commit-Log): wann welcher Zeiger umgesetzt wurde.

8. Senior-Punkte

  1. Table Format ist nicht File Format. Parquet speichert Zeilen spaltenweise. Iceberg entscheidet, welche Parquet-Dateien gerade die Tabelle sind.
  2. Der Catalog ist der wertvollste Teil. Ohne Zeiger gibt es keine Tabelle. Er braucht Backup, HA und Monitoring wie eine Datenbank.
  3. Iceberg ist keine OLTP-Datenbank. Kein Index, kein erzwungener Primary Key, jeder Commit kostet Metadaten. Viele Einzel-Updates pro Sekunde passen nicht.
  4. Wartung gehört zum Design. Compaction, Snapshot Expiry und Orphan Cleanup müssen geplant laufen, sonst wird die Tabelle langsam und teuer.
  5. Offenheit ist der Hauptgrund. Mehrere Engines auf denselben Daten, kein Vendor Lock-in, Engine später austauschbar.
  6. Format-Version bewusst wählen. v3-Funktionen nur nutzen, wenn alle Reader und Writer sie unterstützen.

10. Fallen

  • „Iceberg ist ein Dateiformat wie Parquet.“ → Falsch. Iceberg ist ein Table Format. Die Daten liegen meist in Parquet.
  • „Iceberg braucht ein atomares Rename im Storage.“ → Falsch. Der atomare Schritt ist der Swap im Catalog. Object Storage reicht.
  • „Iceberg findet Dateien über Ordner.“ → Falsch. Es liest Manifests. Ordnernamen sind nur Konvention.
  • „Iceberg ist eine Query Engine.“ → Falsch. Iceberg ist Spec plus Bibliothek. Rechnen tun Spark, Dremio, Trino oder Flink.
  • „Iceberg-Tabellen sind ohne Pflege schnell.“ → Falsch. Ohne Compaction und Expiry wachsen Small Files und Metadaten.
  • „Neue Tabellen sind automatisch v3.“ → Falsch. Iceberg 1.x nutzt Standard format-version = 2.

11. Fragen

Was ist ein Table Format?

Eine Metadaten-Schicht, die festlegt, welche Datendateien gerade die Tabelle bilden. Dazu kommen Schema, Partitionierung und Historie.

Welches Problem löst Iceberg?

Parquet-Ordner und Hive-Tabellen haben keine atomaren Commits, langsame Ordner-Listings und starre Partitionen. Iceberg bringt ACID, Dateilisten in Metadaten und Evolution.

Warum sind Hive-Tabellen auf S3 problematisch?

Der Metastore kennt nur Ordner, darum muss jede Abfrage listen. Commits beruhen auf Rename, und Rename ist auf S3 Kopieren plus Löschen.

Wie erreicht Iceberg Atomarität?

Alle neuen Dateien werden zuerst geschrieben. Dann setzt der Catalog den Zeiger per Compare-and-Swap auf die neue metadata.json. Nur dieser Schritt muss atomar sein.

Was macht der Catalog?

Er bildet den Tabellennamen auf die aktuelle metadata.json ab. Er garantiert, dass nur ein Commit pro Version gewinnt.

Was ist ein Snapshot?

Der vollständige Tabellenstand nach einem Commit. Er zeigt auf eine Manifest List und damit auf alle gültigen Dateien.

Welche Isolation bietet Iceberg?

Reader sehen einen festen Snapshot (Snapshot Isolation). Für DELETE, UPDATE und MERGE ist serializable der Standard, snapshot ist einstellbar.

Was passiert bei zwei gleichzeitigen Commits?

Einer gewinnt den Swap. Der andere prüft, ob seine Änderung noch gültig ist, und versucht es neu. Sonst scheitert er.

Was unterscheidet v1, v2 und v3?

v1: analytische Tabellen. v2: Row-level Deletes mit Delete Files und Sequence Numbers. v3: Deletion Vectors, Row Lineage, Default-Werte, neue Typen.

Welche Format-Version ist Standard?

In Iceberg 1.x ist es v2 seit Version 1.4.0. v3 setzt man explizit mit format-version = 3.

Welche Anforderungen stellt Iceberg an den Storage?

Unveränderliche Dateien schreiben, mit Seek lesen und löschen. Kein Rename und kein Random-Write nötig.

Welche Engines können Iceberg nutzen?

Unter anderem Spark, Flink, Trino, Dremio, PyIceberg, DuckDB, Snowflake, Athena. Der Funktionsumfang pro Engine ist unterschiedlich.

Was sind Metadata Tables?

Virtuelle Tabellen über die Metadaten, z. B. t.snapshots, t.history, t.files, t.manifests, t.partitions. Man fragt sie mit normalem SQL ab.

Copy-on-Write oder Merge-on-Read?

Copy-on-Write schreibt betroffene Dateien neu: teure Writes, schnelle Reads. Merge-on-Read schreibt Delete Files: schnelle Writes, Reads müssen verrechnen.

Iceberg vs Delta Lake?

Beide bringen ACID auf Object Storage. Delta ist stark an Spark und Databricks gebunden. Iceberg hat eine offene Spec, Hidden Partitioning und Partition Evolution und viele Engines.

Ist Iceberg ein Ersatz für eine OLTP-Datenbank?

Nein. Es gibt keine Indizes und keinen erzwungenen Primary Key. Jeder Commit ist teuer. Es passt für analytische Lasten und Batch- oder Micro-Batch-Writes.

Warum entstehen Orphan Files?

Ein Job schreibt Dateien, aber sein Commit scheitert oder bricht ab. Kein Snapshot kennt die Dateien. remove_orphan_files räumt sie auf.

Wie plant Iceberg eine Abfrage ohne Ordner-Listing?

Es liest metadata.json, dann die Manifest List und die passenden Manifests. Partitionswerte und Min/Max-Werte filtern Dateien vor dem Lesen.

Szenario: Nach einem Neustart des Catalog-Pods sind alle Tabellen leer oder unbekannt. Was ist passiert?

Der Catalog hatte seinen Zustand in flüchtigem Speicher. Die Dateien liegen noch im Storage, aber der Zeiger fehlt. Lösung: persistentes Backend wie Postgres, Backups, und Tabellen notfalls aus der letzten metadata.json neu registrieren.

Szenario: Dremio zeigt kurz halbe Daten eines Spark-Jobs. Kann das mit Iceberg passieren?

Nicht über eine Iceberg-Tabelle, denn erst der Commit macht Daten sichtbar. Ich prüfe, ob Dremio ein Ordner-Dataset statt der Iceberg-Tabelle liest oder ob der Job mehrere Commits macht.

Szenario: Abfragen werden Woche für Woche langsamer, die Datenmenge wächst kaum. Was prüfen Sie?

Anzahl Dateien und Manifests in t.files und t.manifests, Anzahl Snapshots und Delete Files. Lösung: Compaction, rewrite_manifests und expire_snapshots einplanen.
