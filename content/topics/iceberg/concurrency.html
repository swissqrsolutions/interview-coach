Gleichzeitige Writes und optimistisches Commit

Iceberg · Tier 2 · Quellen: Apache Iceberg Table Spec (Optimistic Concurrency, Sequence Numbers), Iceberg 1.12 Docs (Configuration: commit.retry.*, write.*.isolation-level; Spark Procedures: rewrite_data_files), Iceberg REST Catalog OpenAPI Spec (requirements, /transactions/commit)

Kern: Iceberg nutzt Optimistic Concurrency Control: Jeder Writer arbeitet ohne Lock und versucht am Ende, den Tabellen-Zeiger im Katalog atomar von seiner Basis-Version auf seine neue Version zu setzen. War ein anderer schneller, prüft der Writer, ob dessen Änderungen mit seinen kollidieren. Ohne Konflikt wiederholt er nur den Metadaten-Commit, mit Konflikt scheitert er.

1. Wo sitzt die Concurrency-Kontrolle?

  1. Writer: Jeder Job (Ingest, MERGE, Compaction) schreibt seine Datendateien zuerst. Niemand sperrt die Tabelle.
  2. Neue Metadaten: Dann schreibt er neue Manifests, eine neue Manifest List und eine neue metadata.json.
  3. Katalog: Er hält den Zeiger auf die aktuelle metadata.json. Der Writer setzt ihn per Compare-and-Swap (CAS): nur wenn der Zeiger noch auf seiner Basis steht.
  4. REST-Katalog: Dort schickt der Writer requirements mit, z. B. „aktueller Snapshot ist noch X“. Der Server prüft sie atomar.
  5. Object Storage: Dateien eines gescheiterten Commits bleiben liegen. Sie werden zu Orphan Files, wenn niemand aufräumt.

2. Die Reise zweier Commits (Wettlauf)

  1. Beide lesen v1: Writer A (Ingest) und Writer B (MERGE) starten auf Snapshot v1.
  2. Dateien schreiben: Beide schreiben Parquet-Dateien. Das ist der teure Teil und läuft parallel.
  3. A gewinnt: A setzt den Zeiger von v1 auf v2. Der Katalog bestätigt.
  4. B scheitert beim CAS: Der Zeiger steht nicht mehr auf v1. B bekommt intern eine CommitFailedException.
  5. B lädt v2: B liest die neue Version und prüft, was A geändert hat.
  6. Kein Konflikt: A hat z. B. nur Dateien angehängt, die B nicht betreffen. B baut seine Metadaten auf v2 neu und committet v3. Konflikt: A hat Dateien gelöscht oder Daten geschrieben, die Bs Bedingung trifft. B wirft eine ValidationException, der Job scheitert.

3. Beispiel: CAS und Konfliktprüfung nachgebaut

history = [("v1.metadata.json", set())]          # (Version, geänderte Partitionen)

def commit(writer, base, new, touched):
    cur = cat.execute("SELECT metadata_location FROM iceberg_tables "
                      "WHERE name='silver.trade'").fetchone()[0]
    if cur != base:                               # jemand war schneller
        since = [h for v, h in history[[v for v, _ in history].index(base) + 1:]]
        hit = set().union(*since) & touched
        if hit:                                   # serializable: gleiche Partition geändert
            return f"{writer}: ValidationException, Konflikt auf {sorted(hit)}"
        base = cur                                # sonst auf neuem Stand wiederholen
    n = cat.execute("UPDATE iceberg_tables SET metadata_location=? "
                    "WHERE name='silver.trade' AND metadata_location=?", (new, base)).rowcount
    if n == 1:
        history.append((new, touched))
        return f"{writer}: commit OK  {base} -> {new}"
    return f"{writer}: CommitFailedException"

base = "v1.metadata.json"                         # A, B und C lesen alle v1
print(commit("A", base, "v2.metadata.json", {"day=2026-11-02"}))
print(commit("B", base, "v3.metadata.json", {"day=2026-11-03"}))
print(commit("C", base, "v4.metadata.json", {"day=2026-11-02"}))
A: commit OK  v1.metadata.json -> v2.metadata.json
B: commit OK  v2.metadata.json -> v3.metadata.json
C: ValidationException, Konflikt auf ['day=2026-11-02']
Katalog zeigt: v3.metadata.json

Echte Ausgabe, Python 3.12 + sqlite3 3.49.1. Ein Modell des Ablaufs, nicht Iceberg-Code: Die Tabelle iceberg_tables entspricht dem JDBC-Katalog von Iceberg, der den Zeiger ebenso per UPDATE … WHERE metadata_location = alt setzt.

  1. A committet direkt, weil der Zeiger noch auf v1 steht.
  2. B kam zu spät, aber A hat nur eine andere Partition geändert. B setzt auf v2 neu auf und gewinnt.
  3. C hat dieselbe Partition wie A geändert. Bei serializable ist das ein Konflikt: C scheitert.
  4. Der Zeiger springt nie zurück. Leser sehen immer eine ganze Version.

In Spark: Isolation pro Operation einstellen:

ALTER TABLE lake.silver.trade SET TBLPROPERTIES (
  'write.merge.isolation-level'  = 'snapshot',   -- Standard: serializable
  'commit.retry.num-retries'     = '10',         -- Standard: 4
  'commit.retry.min-wait-ms'     = '500');       -- Standard: 100

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): Ein MERGE scheitert dann nicht mehr, wenn parallel nur neue Daten angehängt werden, die seine Bedingung treffen würden. Spark läuft hier nicht.

4. Details, die Interviewer fragen

  1. Retry-Standardwerte: commit.retry.num-retries = 4, Wartezeit von 100 ms bis 60 s mit Backoff, insgesamt höchstens 30 Minuten (commit.retry.total-timeout-ms).
  2. Was wird beim Retry neu geschrieben? Nur Manifest List und metadata.json, evtl. ein Manifest. Die Datendateien bleiben. Darum sind Retries billig.
  3. Append gegen Append: Zwei reine Appends kollidieren nie. Der zweite setzt einfach auf dem ersten auf.
  4. serializable (Standard für DELETE, UPDATE, MERGE): Der Commit scheitert auch, wenn parallel neue Daten angehängt wurden, die seine Bedingung treffen.
  5. snapshot: Der Commit scheitert nur, wenn Dateien, die er ändert oder löscht, inzwischen geändert wurden. Parallele Appends sind erlaubt. Weniger Konflikte, schwächere Garantie.
  6. CommitStateUnknownException: Der Katalog antwortet nicht, der Commit ist vielleicht gelungen. Iceberg prüft den Status erneut (commit.status-check.num-retries = 3). Dateien dann nicht löschen, sonst wird die Tabelle kaputt.
  7. Compaction gegen Writer: Compaction ersetzt Dateien. Löscht ein Writer parallel Zeilen in diesen Dateien, gibt es einen Konflikt. partial-progress.enabled committet in Gruppen, so verliert man weniger Arbeit.
  8. Sequence Numbers: Jeder Commit bekommt eine wachsende Nummer. Delete Files gelten nur für Daten mit kleinerer Nummer. Compaction behält die alte Nummer der Daten, damit neuere Deletes weiter greifen.
  9. Multi-Table: Iceberg-Commits sind pro Tabelle atomar. Über mehrere Tabellen braucht man den Katalog: Nessie (Commit über mehrere Tabellen) oder den REST-Endpunkt /transactions/commit, wenn der Server ihn anbietet.
  10. Hadoop-Katalog: Er setzt den Zeiger per Datei-Rename. Auf S3 ist das nicht atomar. Darum nie für gleichzeitige Writer auf Object Storage.

5. Vergleich

  • Optimistisch (Iceberg, Delta): keine Locks, hoher Durchsatz bei wenig Konflikten. Bei vielen Konflikten verschwendet man Arbeit durch Retries und Fehler.
  • Pessimistisch (Locks, z. B. Hive mit Lock-Manager, OLTP-Datenbanken): kein verlorener Aufwand, aber Wartezeiten und Lock-Probleme bei langen Jobs.
  • Delta Lake: ebenfalls optimistisch, Konflikt über das Transaktions-Log (_delta_log, atomares „put if absent“ der nächsten Log-Datei).

6. In der Produktion

  1. Zwei Jobs scheitern abwechselnd mit ValidationException: Beide schreiben dieselben Partitionen. Lösung: Arbeit trennen (Partitionen pro Job), Jobs serialisieren, oder snapshot-Isolation, wenn fachlich erlaubt.
  2. Compaction scheitert immer: Ein Streaming-Job committet jede Minute in dieselbe Partition. Lösung: nur kalte Partitionen kompaktieren (Filter), partial-progress.enabled.
  3. Viele Orphan Files: gescheiterte Commits. Lösung: remove_orphan_files mit genug Abstand (older_than).
  4. Tabelle nach Timeout kaputt: Der Writer hat nach CommitStateUnknown Dateien gelöscht. Lösung: Iceberg-Version mit Status-Check, eigene Cleanup-Logik vermeiden.
  5. Hohe Commit-Rate, langsame Commits: Viele kleine Commits machen viele Metadaten-Dateien. Lösung: Batches bündeln, Manifests mergen lassen, write.metadata.delete-after-commit.enabled setzen.

7. Diagnose

  • SELECT committed_at, operation, summary FROM lake.silver.trade.snapshots ORDER BY committed_at DESC: wer committet wie oft.
  • Driver-Log: Retrying commit, CommitFailedException, ValidationException: Found conflicting files.
  • .metadata_log_entries: Zahl und Rate neuer metadata.json-Versionen.
  • Katalog-Logs (REST/Nessie): Status 409 Conflict pro Tabelle zählen.

8. Senior-Punkte

  1. Konflikte vermeidet man im Design, nicht mit Retries. Jeder Job besitzt seine Partitionen oder Nachrichten.
  2. serializable bleibt Standard. snapshot nur, wenn man fachlich begründen kann, dass parallele Appends egal sind.
  3. Wartung und Ingest koordinieren: Compaction auf kalte Daten, Ingest auf heisse.
  4. Der Katalog ist der Engpass und der Garant der Atomarität. Er braucht Verfügbarkeit und Backup.
  5. Nie aufräumen nach „unbekanntem“ Commit-Status. Lieber Orphan Files später entfernen.

9. Aus dem Projekt

„Bei ElCom MATCH verhindert ein atomarer SQL-Claim (UPDATE … OUTPUT INSERTED.*), dass überlappende Spark-Läufe dieselben Nachrichten verarbeiten, sodass Iceberg-Commit-Konflikte im Normalbetrieb gar nicht erst entstehen.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Iceberg sperrt die Tabelle beim Schreiben.“ → Falsch. Kein Lock, nur ein atomarer Zeiger-Tausch am Ende.
  • „Ein Retry schreibt alle Daten neu.“ → Falsch. Nur Metadaten werden neu geschrieben.
  • „Zwei Appends können kollidieren.“ → Falsch. Reine Appends kollidieren nie.
  • „Iceberg hat Transaktionen über mehrere Tabellen.“ → Nicht im Format. Nur über Katalog-Funktionen wie Nessie oder REST-Multi-Table-Commit.
  • „Der Hadoop-Katalog reicht auf S3.“ → Falsch. Rename ist dort nicht atomar.

11. Fragen

Wie verhindert Iceberg, dass zwei Writer sich überschreiben?

Mit einem atomaren Compare-and-Swap des Metadaten-Zeigers im Katalog. Nur ein Writer pro Basis-Version gewinnt.

Was passiert mit dem Verlierer?

Er lädt die neue Version und prüft Konflikte. Ohne Konflikt committet er erneut, mit Konflikt wirft er eine ValidationException.

Was ist der Unterschied zwischen CommitFailedException und ValidationException?

CommitFailedException: Der Zeiger hat sich geändert, ein Retry ist möglich. ValidationException: Die Änderungen widersprechen sich, ein Retry hilft nicht.

Was ist CommitStateUnknownException?

Der Katalog hat nicht geantwortet, der Commit ist vielleicht gelungen. Dann keine Dateien löschen, sondern den Status prüfen.

Welche Retry-Einstellungen gibt es?

commit.retry.num-retries (Standard 4), min-wait-ms (100), max-wait-ms (60 000) und total-timeout-ms (30 Minuten).

Warum sind Retries billig?

Die Datendateien bleiben. Nur Manifest List und metadata.json werden auf der neuen Basis neu geschrieben.

Können zwei Appends kollidieren?

Nein. Ein Append ändert keine bestehenden Dateien, der zweite setzt einfach auf.

serializable oder snapshot?

serializable scheitert auch bei parallelen Appends, die die eigene Bedingung treffen. snapshot erlaubt sie. Standard ist serializable.

Wie macht der REST-Katalog den Commit atomar?

Der Client schickt requirements wie „Snapshot ist noch X“ und updates. Der Server prüft und wendet sie atomar an, sonst kommt 409.

Warum kollidiert Compaction mit Writern?

Compaction ersetzt Dateien. Löscht oder ändert ein Writer parallel Zeilen darin, passen die Änderungen nicht zusammen.

Was hilft gegen Compaction-Konflikte?

Nur kalte Partitionen kompaktieren, partial-progress.enabled und Zeitfenster ohne Ingest.

Welche Rolle spielen Sequence Numbers?

Sie ordnen Commits. Delete Files gelten nur für ältere Daten, darum bleiben Deletes nach Compaction korrekt.

Gibt es Multi-Table-Transaktionen?

Nicht im Iceberg-Format. Nessie kann mehrere Tabellen in einem Commit ändern, der REST-Katalog optional über /transactions/commit.

Warum ist der Hadoop-Katalog auf S3 gefährlich?

Er nutzt Rename als atomaren Schritt. Auf S3 ist Rename nicht atomar, gleichzeitige Commits können sich überschreiben.

Wie verhindern Sie Konflikte im Design?

Jeder Job bekommt eigene Partitionen oder Nachrichten, z. B. per atomarem Claim. Wartung läuft auf kalten Daten.

Wie unterscheidet sich Delta Lake?

Auch optimistisch, aber über das Transaktions-Log: Der Writer legt die nächste Log-Datei atomar an. Konflikte prüft er gegen die Log-Einträge dazwischen.

Szenario: Zwei MERGE-Jobs scheitern jede Nacht abwechselnd. Was tun Sie?

Prüfen, ob sie dieselben Partitionen treffen. Dann Arbeit trennen oder die Jobs nacheinander laufen lassen. Mehr Retries lösen echte Konflikte nicht.

Szenario: Nach einem Netzwerkfehler fehlen Dateien, Abfragen scheitern mit FileNotFound. Was ist passiert?

Wahrscheinlich hat ein Writer nach unbekanntem Commit-Status aufgeräumt, obwohl der Commit gelungen war. Auf einen gültigen Snapshot zurückrollen und Cleanup-Logik entfernen.

Szenario: Die Compaction scheitert seit einer Woche, die Tabelle wird langsam. Wie gehen Sie vor?

Logs auf ValidationException prüfen, meist wegen eines Streaming-Writers. Compaction auf ältere Partitionen filtern und partial-progress aktivieren.
