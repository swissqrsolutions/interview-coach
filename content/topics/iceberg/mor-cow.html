Merge-on-Read vs Copy-on-Write, Delete Files

Kern: Copy-on-Write (CoW) und Merge-on-Read (MoR) sind zwei Arten, wie Iceberg Zeilen löscht oder ändert. CoW schreibt jede betroffene Datendatei komplett neu, MoR schreibt nur kleine Delete Files, die der Leser beim Lesen anwendet. CoW ist teuer beim Schreiben und billig beim Lesen, MoR ist umgekehrt.

Antwort-Muster

Frage: Was ist der Unterschied zwischen Copy-on-Write und Merge-on-Read?

  1. Mechanismus: Datendateien ändern sich nie. CoW schreibt betroffene Dateien neu, MoR hängt kleine Delete Files an.
  2. Zahl: Standard ist überall copy-on-write. MoR braucht mindestens Format v2, Deletion Vectors brauchen v3.
  3. Trade-off: CoW ist teuer beim Schreiben und schnell beim Lesen. MoR ist billig beim Schreiben, aber das Lesen wird mit jedem Delete File langsamer.
  4. Produktion: Bei MoR plane ich rewrite_data_files und expire_snapshots regelmässig ein.

1. Die Reise eines DELETE

  1. Planen: Spark fragt den Catalog nach dem aktuellen Snapshot. Mit den Min/Max-Statistiken der Manifests findet es die Dateien, die message_id = 4711 enthalten können.
  2. Copy-on-Write: Spark liest jede betroffene Datei ganz. Es schreibt alle Zeilen ausser den gelöschten in eine neue Datei. Der Commit ersetzt die alte Datei durch die neue (Operation overwrite).
  3. Merge-on-Read: Spark liest nur die betroffenen Zeilen und merkt sich Dateipfad und Zeilenposition. Es schreibt ein Position Delete File (v2) oder einen Deletion Vector (v3). Der Commit fügt nur dieses kleine File hinzu (Operation delete oder overwrite).
  4. Sonderfall ganze Datei: Passen alle Zeilen einer Datei zum Filter, entfernt Iceberg die Datei nur aus den Metadaten. Das ist in beiden Modi ein reiner Metadaten-Delete.
  5. Atomarer Commit: Der neue Snapshot wird erst sichtbar, wenn der Catalog den Zeiger tauscht. Leser sehen entweder alles oder nichts.
  6. Lesen danach: Bei CoW liest der Leser nur Data Files. Bei MoR lädt er zusätzlich die Delete Files und filtert gelöschte Positionen aus. Je mehr Delete Files, desto langsamer.
  7. Aufräumen: Später schreibt rewrite_data_files die Daten neu und wendet die Deletes an. Danach braucht niemand mehr die Delete Files.

2. Aufbau

  1. Catalog: hält den Zeiger auf die aktuelle metadata.json. Beispiel: Nessie im MATCH-Lakehouse.
  2. metadata.json: kennt Schema, Partition Spec und alle Snapshots.
  3. Manifest List: listet pro Snapshot alle Manifests auf. Jedes Manifest hat einen Typ: Daten oder Deletes.
  4. Data Manifests: listen Data Files, also Parquet-Dateien mit Zeilen. Sie werden nie verändert.
  5. Delete Manifests: listen Delete Files. Ein Delete File sagt: „Diese Zeilen gibt es nicht mehr.“
  6. Der Leser kombiniert beides. Er liest Data Files und blendet gelöschte Zeilen aus. Das ist das „Merge“ in Merge-on-Read.
  7. Delete Files gibt es erst ab Format v2. In v1 ist nur Copy-on-Write möglich.

3. Details

  1. Position Delete File (v2): Es ist eine Parquet-Datei mit den Spalten file_path und pos. Sie markiert die Zeile Nummer pos in genau dieser Datei als gelöscht. Ein Beispiel ist (…/00007.parquet, 4711).
  2. Equality Delete File: Sie löscht alle Zeilen, deren Spalten bestimmte Werte haben. Ein Beispiel ist id = 42 mit equality_ids = [id]. Der Writer muss die alte Zeile nicht finden. Darum nutzt Flink sie für Upserts aus Streams.
  3. Deletion Vector (v3): Er ist ein Roaring Bitmap, also eine komprimierte Bitmenge der gelöschten Positionen. Er liegt als Blob deletion-vector-v1 in einer Puffin-Datei. Das Format ist mit den Deletion Vectors von Delta Lake kompatibel.
  4. Höchstens ein DV pro Datendatei: Die v3-Spec erlaubt pro Snapshot nur einen Deletion Vector pro Data File. Ein neuer Delete muss den alten DV mergen. So sammelt der Leser nie viele kleine Deletes pro Datei.
  5. Position Deletes in v3: Neue Position Delete Files sind in v3 nicht mehr erlaubt. Alte aus v2 bleiben gültig. Ein DV für eine Datei ersetzt ihre alten Position Deletes.
  6. Sequence Numbers: Jeder Commit bekommt eine Data Sequence Number. Ein Position Delete gilt für Data Files mit gleicher oder kleinerer Nummer. Ein Equality Delete gilt nur für strikt kleinere Nummern. So löscht ein Upsert nicht die eigene neue Zeile.
  7. Spark schreibt keine Equality Deletes: Spark schreibt bei MoR immer Position Deletes oder DVs. Equality Deletes kommen meist von Flink oder CDC-Tools.
  8. UPDATE bei MoR: Iceberg ändert keine Zeile in einer Datei. Ein UPDATE ist ein Delete der alten Zeile. Dazu kommt ein Insert der neuen Zeile in eine neue Datei.
  9. MERGE INTO: Es nutzt write.merge.mode. Bei CoW schreibt es jede Datei mit einem Treffer neu. Bei MoR schreibt es Deletes plus neue Zeilen.
  10. Isolation Level: write.delete.isolation-level ist standardmässig serializable. snapshot erlaubt mehr parallele Commits. Es prüft aber weniger Konflikte.
  11. Delete Granularity: write.delete.granularity ist partition oder file. file schreibt ein Delete File pro Datendatei. Das sind mehr Dateien, aber gezielteres Lesen und einfacheres Aufräumen.
  12. Dateigrössen: write.target-file-size-bytes ist 512 MB. write.delete.target-file-size-bytes ist 64 MB.
  13. Format Version: format-version ist standardmässig 2. MoR braucht mindestens v2. Für Deletion Vectors braucht es v3. Jede lesende Engine muss v3 können.

4. Fallen

  • „Merge-on-Read ändert Zeilen direkt in der Parquet-Datei.“ → Falsch. Data Files sind unveränderlich. MoR schreibt zusätzliche Delete Files.
  • „MoR ist immer schneller.“ → Falsch. Nur beim Schreiben. Das Lesen wird langsamer, bis die Compaction läuft.
  • „Iceberg nutzt standardmässig Merge-on-Read.“ → Falsch. Standard ist copy-on-write für DELETE, UPDATE und MERGE.
  • „Spark schreibt Equality Deletes.“ → Falsch. Spark schreibt Position Deletes (v2) oder Deletion Vectors (v3). Equality Deletes kommen meist von Flink.
  • „In v3 gibt es keine Position Deletes mehr.“ → Halb falsch. Neue dürfen nicht geschrieben werden. Alte aus v2 bleiben gültig, bis man sie neu schreibt.
  • „Ein DELETE schreibt bei CoW immer Dateien neu.“ → Falsch. Trifft er ganze Dateien, ist es ein reiner Metadaten-Delete.

5. Selbsttest

Warum?

Warum sind Equality Deletes teuer beim Lesen?

Der Leser muss jede ältere Datendatei gegen alle Werte prüfen. Er weiss nicht, in welcher Datei die Zeile liegt.

Warum ist MoR beim Schreiben schneller?

Spark muss keine ganzen Dateien neu schreiben. Es schreibt nur ein kleines Delete File mit Pfad und Position.

Was geht kaputt, wenn Compaction und ein Delete gleichzeitig laufen?

Der Delete trifft Dateien, die die Compaction gerade umschreibt. Der Commit der Compaction scheitert mit einem Konflikt. Lösung: partial-progress.enabled und Compaction ausserhalb der Ingest-Fenster.

Wie innen?

Welche Table Properties steuern den Modus?

write.delete.mode, write.update.mode und write.merge.mode. Werte: copy-on-write (Standard) oder merge-on-read.

Was ist ein Position Delete File?

Eine Datei mit Paaren aus file_path und pos. Jedes Paar markiert eine Zeile in einer bestimmten Datendatei als gelöscht.

Was ist ein Equality Delete File?

Eine Datei mit Spaltenwerten, z. B. id = 42. Alle älteren Zeilen mit diesen Werten gelten als gelöscht. Der Writer muss die Zeile nicht suchen.

Was ist ein Deletion Vector?

Ein Roaring Bitmap der gelöschten Zeilenpositionen einer Datendatei. Er liegt als deletion-vector-v1-Blob in einer Puffin-Datei. Neu in Format v3.

Was passiert mit alten Position Deletes nach einem Upgrade auf v3?

Sie bleiben gültig. Neue Position Delete Files sind verboten. Ein neuer DV für eine Datei ersetzt ihre alten Position Deletes.

Welche Rolle spielen Sequence Numbers bei Deletes?

Ein Position Delete gilt für Data Files mit gleicher oder kleinerer Sequence Number. Ein Equality Delete nur für strikt kleinere. So löscht ein Upsert nicht seine eigene neue Zeile.

Wie funktioniert ein UPDATE bei Merge-on-Read?

Als Delete der alten Zeile plus Insert der neuen Zeile in eine neue Datei. Keine Datei wird verändert.

Wann schreibt ein DELETE gar keine Dateien?

Wenn der Filter ganze Dateien oder Partitionen trifft. Dann entfernt Iceberg die Dateien nur aus den Metadaten.

Wie werden Delete Files wieder entfernt?

rewrite_data_files schreibt die Daten neu und wendet die Deletes an. rewrite_position_delete_files fasst Position Deletes zusammen. expire_snapshots löscht danach die alten Dateien physisch.

Was ist write.delete.granularity?

Sie steuert, ob Spark ein Delete File pro Partition oder pro Datendatei schreibt. file erzeugt mehr, aber gezieltere Delete Files.

Welchen Isolation Level nutzt ein DELETE?

Standard ist serializable. snapshot erlaubt mehr parallele Commits, erkennt aber weniger Konflikte.

Wie sehen Sie, wie viele Deletes eine Tabelle hat?

Über die Metadatentabellen delete_files, partitions und snapshots. Dort stehen Anzahl und Art der Delete Files.

Zahlen

Ab welcher Format Version gibt es Delete Files?

Ab v2. In v1 gibt es nur Copy-on-Write. Deletion Vectors brauchen v3.

Wie viele Deletion Vectors darf eine Datendatei haben?

Höchstens einen pro Snapshot. Ein neuer Delete merged den alten Vector. Das hält das Lesen billig.

Was bedeuten delete-file-threshold und delete-ratio-threshold?

Optionen von rewrite_data_files. Eine Datei wird neu geschrieben, wenn sie mindestens so viele Delete Files hat oder ein bestimmter Anteil ihrer Zeilen gelöscht ist (Standard 0.3).

Vergleich

Was ist der Unterschied zwischen Copy-on-Write und Merge-on-Read?

CoW schreibt betroffene Datendateien ganz neu. MoR schreibt nur Delete Files, und der Leser wendet sie an. CoW kostet beim Schreiben, MoR beim Lesen.

Welche Engine schreibt welche Delete-Art?

Spark schreibt Position Deletes oder DVs. Flink schreibt bei Upserts Equality Deletes. Lesen müssen alle Engines alle Arten können.

Warum ist das Deletion-Vector-Format wichtig für Interoperabilität?

Iceberg v3 nutzt dasselbe Bitmap-Format wie Delta Lake. Das erleichtert Werkzeuge, die beide Formate lesen oder übersetzen.

Produktion

Szenario: Eine MoR-Tabelle wird jede Woche langsamer, obwohl die Datenmenge gleich bleibt. Was tun Sie?

In partitions und delete_files prüfen, ob sich Delete Files ansammeln. Dann regelmässig rewrite_data_files mit Delete-Schwelle und danach expire_snapshots planen.

Szenario: Ein täglicher MERGE trifft 0,1 % der Zeilen, schreibt aber 2 TB. Warum?

Die Tabelle nutzt Copy-on-Write. Jede Datei mit einem Treffer wird ganz neu geschrieben. Lösung: write.merge.mode = merge-on-read plus Compaction.

Szenario: Nach dem Upgrade auf v3 bricht ein Dashboard ab. Woran denken Sie?

Die Lese-Engine versteht Deletion Vectors oder v3-Metadaten nicht. Vor einem Upgrade müssen alle Engines v3 unterstützen. Das Upgrade lässt sich nicht zurückdrehen.

Design

Wann wählen Sie Copy-on-Write?

Bei seltenen, grossen Änderungen und vielen Lesern. Dann zahlt man einmal beim Schreiben und liest danach schnell.

Wann wählen Sie Merge-on-Read?

Bei häufigen, kleinen Änderungen, z. B. Re-Imports oder CDC. Dann ist Schreiben schnell, aber man braucht Compaction.

Mehr

Gerüst

  • Warum? Data Files sind unveränderlich. Darum gibt es zwei Wege für Deletes und Updates: Datei neu schreiben oder Delete File anhängen.
  • Wie innen? MoR schreibt Position Deletes (v2) oder Deletion Vectors (v3, Roaring Bitmap in Puffin). Sequence Numbers bestimmen, welcher Delete gilt.
  • Zahlen Standard überall copy-on-write, format-version 2. Dateigrösse 512 MB, Delete Files 64 MB. delete-ratio-threshold 0.3.
  • Vergleich CoW: teuer schreiben, schnell lesen. MoR mit DV: billig schreiben, Lesen etwas teurer. Equality Deletes: Lesen am teuersten.
  • Produktion Delete Files sammeln sich an und machen Scans langsam. Compaction mit rewrite_data_files und expire_snapshots.
  • Design Modus pro Operation wählen (write.delete.mode, write.update.mode, write.merge.mode). Vor v3 alle Engines prüfen.

Beispiel: von CoW auf MoR umstellen und Delete Files sehen

-- Spark SQL mit Iceberg SQL Extensions, Catalog "lake"
ALTER TABLE lake.silver.trades SET TBLPROPERTIES (
  'format-version'    = '3',
  'write.delete.mode' = 'merge-on-read',
  'write.update.mode' = 'merge-on-read',
  'write.merge.mode'  = 'merge-on-read'
);

DELETE FROM lake.silver.trades WHERE message_id = 4711;

SELECT snapshot_id, operation,
       summary['added-delete-files']     AS add_del,
       summary['added-position-deletes'] AS pos_del
FROM lake.silver.trades.snapshots ORDER BY committed_at DESC LIMIT 1;

SELECT content, file_format, record_count, referenced_data_file
FROM lake.silver.trades.delete_files;
snapshot_id          operation  add_del  pos_del

content  file_format  record_count  referenced_data_file

1        PUFFIN       630           s3://lake/silver/trades/data/received_date_day=2026-11-21/.../00002-...parquet

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). IDs, Pfade und Zahlen sind Beispielwerte. Die Spalten stammen aus den Iceberg-Metadatentabellen snapshots und delete_files.

  1. Die drei write.*.mode-Properties gelten getrennt für DELETE, UPDATE und MERGE. Standard ist überall copy-on-write.
  2. content = 1 heisst Position Deletes. 2 wäre Equality Deletes, 0 Daten.
  3. PUFFIN zeigt: In v3 sind es Deletion Vectors in Puffin-Dateien, nicht mehr Parquet-Position-Delete-Files.
  4. referenced_data_file zeigt: Ein Deletion Vector gehört genau zu einer Datendatei.
  5. Kein einziges Data File wurde neu geschrieben. Der Preis kommt beim Lesen und bei der späteren Compaction.

Vergleich

  • Copy-on-Write: Schreiben teuer (ganze Dateien neu), Lesen am schnellsten, keine Delete Files. Gut für seltene, grosse Batch-Änderungen und leselastige Tabellen.
  • MoR mit Position Deletes (v2): Schreiben billig, Lesen etwas teurer. Viele kleine Delete Files pro Datei möglich. Braucht regelmässige Compaction.
  • MoR mit Deletion Vectors (v3): wie Position Deletes, aber ein kompakter Bitmap pro Datei. Lesen günstiger, weniger kleine Dateien. Alle Engines müssen v3 lesen können.
  • MoR mit Equality Deletes: Schreiben am billigsten, der Writer sucht nichts. Lesen am teuersten: Jede ältere Datei muss gegen die Werte geprüft werden. Nur für Streaming-Upserts, mit enger Compaction.
  • Metadaten-Delete: Trifft der Filter ganze Dateien oder Partitionen, schreibt Iceberg gar nichts neu. Das ist immer am billigsten.

In der Produktion

  1. Abfragen werden mit der Zeit langsamer: Delete Files sammeln sich an. Jeder Scan muss sie laden und anwenden. Lösung: rewrite_data_files mit delete-file-threshold oder delete-ratio-threshold, regelmässig geplant.
  2. Equality Deletes sprengen das Lesen: Ein Flink-Upsert-Stream schreibt pro Checkpoint neue Equality Deletes. Leser müssen sie gegen alle älteren Dateien prüfen. Lösung: häufige Compaction, oder in v3 auf Position Deletes/DVs setzen, wo möglich.
  3. Eine Engine kann die Tabelle nicht mehr lesen: Nach dem Wechsel auf v3 versteht eine ältere Engine Deletion Vectors nicht. Lösung: Vor dem Upgrade alle Leser prüfen (Spark, Dremio, Trino). Das Upgrade lässt sich nicht zurückdrehen.
  4. Compaction-Commit schlägt fehl: Ein MoR-Delete trifft Dateien, die die Compaction gerade umschreibt. Der Commit der Compaction scheitert mit einem Konflikt. Lösung: partial-progress.enabled, kleinere Dateigruppen, Compaction ausserhalb der Ingest-Fenster.
  5. CoW macht Schreib-Jobs langsam und teuer: Ein MERGE trifft wenige Zeilen in vielen Dateien. Dann wird jede dieser 512-MB-Dateien neu geschrieben. Lösung: write.merge.mode = merge-on-read und eine Partitionierung, die Änderungen lokal hält.
  6. Speicher wächst: Alte Data Files und Delete Files bleiben, solange alte Snapshots sie brauchen. Lösung: expire_snapshots nach der Compaction.

Diagnose: Werkzeuge und Abfragen

  • SELECT * FROM t.delete_files: alle aktuellen Delete Files mit content, record_count, file_format.
  • SELECT partition, position_delete_record_count, position_delete_file_count, equality_delete_file_count FROM t.partitions: welche Partition die meisten Deletes hat.
  • SELECT operation, summary FROM t.snapshots: Keys wie added-delete-files, added-position-deletes, added-equality-deletes, total-delete-files.
  • SHOW TBLPROPERTIES t: aktuelle write.*.mode und format-version.
  • Spark UI und Scan-Metriken: Anzahl gelesener Delete Files pro Scan. Im Dremio Query Profile sieht man die Scan-Zeit pro Phase.
  • CALL lake.system.rewrite_data_files(table => 't', options => map('delete-file-threshold','2')): gezielt Dateien mit vielen Deletes neu schreiben.

Senior-Punkte

  1. Die Wahl gilt pro Operation. DELETE, UPDATE und MERGE haben je eine eigene Property. Man kann z. B. DELETE als MoR und MERGE als CoW fahren.
  2. MoR ist eine Schuld, die man später zahlt. Ohne geplante Compaction wird jede MoR-Tabelle langsam. MoR und Wartung gehören zusammen in ein Design.
  3. Faustregel: viele kleine Änderungen, oft geschrieben → MoR. Wenige grosse Änderungen, sehr oft gelesen → CoW.
  4. Equality Deletes nur bewusst. Sie sind schnell für den Writer, aber teuer für alle Leser. Spark-Batch-Jobs brauchen sie nicht.
  5. v3-Upgrade ist eine Plattform-Entscheidung. Deletion Vectors lohnen sich, aber nur wenn jede Engine v3 liest. Der Engpass ist meist die Lese-Engine, nicht Spark.
  6. Partitionierung entscheidet die Kosten. Ein Delete, der in einer Partition bleibt, berührt wenige Dateien. Ein Delete über alle Partitionen erzeugt viele Delete Files oder viele neu geschriebene Dateien.
