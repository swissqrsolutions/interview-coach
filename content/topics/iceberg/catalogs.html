Kataloge: Nessie, REST, Hive, Glue

Kern: Ein Iceberg-Katalog ist der Dienst, der für jede Tabelle den Zeiger auf die aktuelle metadata.json hält. Er macht Commits atomar: Ein Commit gilt nur, wenn der Katalog den Zeiger von „alt“ auf „neu“ tauschen kann. Ohne Katalog wüsste keine Engine, welche Version einer Tabelle gilt.

1. Wo sitzt der Katalog?

  1. Engines: Spark, Dremio, Trino oder Flink fragen den Katalog nach einer Tabelle. Beispiel: lake.silver.trades.
  2. Katalog: antwortet mit dem Ort der aktuellen metadata.json. Moderne Kataloge (REST) liefern die Metadaten direkt mit.
  3. Backend: speichert den Zeiger dauerhaft. Beispiel: Nessie mit PostgreSQL, Hive Metastore mit einer relationalen DB.
  4. metadata.json: liegt im Object Store. Ab hier liest die Engine selbst: Manifest List, Manifests, Parquet.
  5. Object Store: enthält alle Dateien aller Versionen. Welche Version gilt, weiss nur der Katalog.

2. Die Reise eines Commits (die Geschichte zum Merken)

  1. Basis lesen: Spark lädt die Tabelle beim Katalog. Aktuell ist Snapshot 41 in v41.metadata.json.
  2. Dateien schreiben: Spark schreibt neue Parquet-Dateien und Manifests in den Object Store. Noch sieht sie niemand.
  3. Neue Metadaten: Spark schreibt v42.metadata.json mit dem neuen Snapshot.
  4. Compare-and-Swap (CAS): Spark sagt dem Katalog: „Setze den Zeiger auf v42, aber nur wenn er noch auf v41 steht.“ Das ist der atomare Pointer Swap.
  5. Erfolg: Der Katalog tauscht den Zeiger. Ab sofort sehen alle Engines Snapshot 42. Es gibt keinen halben Zustand.
  6. Konflikt: Hat ein anderer Writer schon v42 committet, lehnt der Katalog ab. Spark lädt die neue Basis, prüft echte Konflikte und versucht es erneut. Standard sind 4 Wiederholungen (commit.retry.num-retries).
  7. Kein Lock während des Schreibens: Das ist optimistische Nebenläufigkeit. Nur der letzte kleine Schritt ist atomar.

3. Beispiel: Spark mit Nessie als REST-Katalog und ein Commit-Konflikt

# spark-defaults.conf: Nessie über die Iceberg-REST-API
spark.sql.extensions              org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions
spark.sql.catalog.lake            org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.lake.type       rest
spark.sql.catalog.lake.uri        http://nessie:19120/iceberg
spark.sql.catalog.lake.warehouse  warehouse

# Nessie-Server (application.properties): Postgres statt RocksDB
nessie.version.store.type=JDBC2
nessie.version.store.persist.jdbc.datasource=postgresql
quarkus.datasource.postgresql.jdbc.url=jdbc:postgresql://nessie-db:5432/nessie
# Was Spark beim Commit an den REST-Katalog schickt (gekürzt)
POST /iceberg/v1/{prefix}/namespaces/silver/tables/trades
{ "requirements": [ { "type": "assert-ref-snapshot-id", "ref": "main",
                      "snapshot-id": 41 } ],
  "updates":      [ { "action": "add-snapshot", "snapshot": { "snapshot-id": 42, ... } },
                    { "action": "set-snapshot-ref", "ref-name": "main",
                      "type": "branch", "snapshot-id": 42 } ] }

# Antwort, wenn ein anderer Writer schneller war
HTTP/1.1 409 Conflict
{ "error": { "type": "CommitFailedException", "code": 409,
             "message": "Requirement failed: branch main has changed ..." } }

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Struktur laut Iceberg REST OpenAPI Spec und Nessie-Doku. IDs und Text der Fehlermeldung sind Beispielwerte.

  1. type = rest heisst: Spark spricht nur die offene REST-API. Der gleiche Client geht auch gegen Polaris, Unity Catalog oder andere REST-Kataloge.
  2. JDBC2 mit PostgreSQL ist laut Nessie-Doku das Production-Backend. ROCKSDB ist nur für einen einzelnen Knoten.
  3. requirements sind die Bedingungen des CAS. Hier: „main zeigt noch auf Snapshot 41.“
  4. updates sind die Änderungen. Hier: neuen Snapshot hinzufügen und main darauf zeigen lassen.
  5. 409 ist der Konflikt. Der Iceberg-Client lädt dann neu und versucht es automatisch nochmal.

4. Details, die Interviewer fragen

  1. REST Catalog Spec: eine offene OpenAPI-Spezifikation des Iceberg-Projekts. Wichtige Endpunkte: GET /v1/config, Namespaces, loadTable, commitTable und POST /v1/{prefix}/transactions/commit für Commits über mehrere Tabellen.
  2. Server-seitiger Commit: Beim REST-Katalog prüft der Server die requirements und schreibt die neue metadata.json. Der Client muss den Speicher des Katalogs nicht kennen.
  3. Credential Vending: Der REST-Katalog kann beim loadTable kurzlebige Speicher-Credentials mitgeben (Header X-Iceberg-Access-Delegation: vended-credentials). Dann braucht die Engine keine festen S3-Keys. Alternative: remote-signing.
  4. Nessie: ein transaktionaler Katalog mit Git-Semantik. Er kennt Commits, Branches, Tags und Merges über alle Tabellen. Beispiel: auf einem Branch etl laden, prüfen, dann nach main mergen.
  5. Nessie-Zugriff: zwei Wege. Der eigene Iceberg-Client (type = nessie, uri = …/api/v2, ref = main) oder die Iceberg-REST-API unter /iceberg. Neue Setups nehmen REST.
  6. Nessie Version Store: nessie.version.store.type wählt das Backend. IN_MEMORY nur für Tests, ROCKSDB nur ein Knoten, JDBC2 (PostgreSQL), MONGODB2 und BIGTABLE für Production.
  7. Apache Polaris: ein Open-Source-Katalog, der die REST-Spec umsetzt. Er bringt Rollen-basierte Rechte (RBAC) und Credential Vending mit.
  8. Hive Metastore (HMS): speichert den Zeiger als Table Property metadata_location. Der Commit nutzt einen HMS-Lock oder ein atomares Alter-Table. Weit verbreitet, aber Hive-Infrastruktur nötig.
  9. AWS Glue: speichert metadata_location als Parameter der Glue-Tabelle. Der Swap nutzt die optimistische Versionierung von Glue (VersionId). Gut in AWS, mit Athena und EMR.
  10. JDBC-Katalog: eine Tabelle iceberg_tables in einer SQL-Datenbank. Der Swap ist ein UPDATE … WHERE metadata_location = <alt>. Einfach, aber ohne eigene API für andere Engines.
  11. Hadoop-Katalog: nutzt das Umbenennen von Dateien als Swap. Auf Object Stores wie S3 ist Umbenennen nicht atomar. Darum nicht für Production auf S3 oder MinIO.
  12. Spark-Konfiguration: spark.sql.catalog.<name>.type kennt hive, hadoop, rest, glue, nessie und jdbc. Eigene Klassen kommen über catalog-impl.
  13. Mehrere Tabellen atomar: Iceberg selbst ist atomar pro Tabelle. Nessie-Commits und der REST-Endpunkt transactions/commit können mehrere Tabellen gemeinsam ändern, wenn der Server es unterstützt.

5. Vergleich

  • REST (Spec): offen, Engine-neutral, Server macht den Commit, Credential Vending. Heute der Standard für neue Plattformen.
  • Nessie: REST plus Git-Semantik: Branches, Tags, Multi-Table-Commits. Braucht ein solides Backend und eigene GC (nessie-gc).
  • Polaris / Unity Catalog / Lakekeeper: REST-Kataloge mit Fokus auf Governance und Rechte. Gut für viele Teams und Engines.
  • Hive Metastore: alt und bewährt. Viele Engines können es, aber man betreibt Hive-Infrastruktur.
  • AWS Glue: verwaltet, billig in AWS. Bindet an AWS.
  • JDBC: minimal, eine SQL-Tabelle. Gut für kleine Setups und Tests.
  • Hadoop (Dateisystem): nur für HDFS oder lokale Tests, nicht für Object Stores.

6. In der Produktion

  1. Katalog-Zustand weg nach Pod-Neustart: Nessie lief mit eingebettetem RocksDB oder In-Memory. Ein Reschedule ohne dauerhaftes Volume verliert die Zeiger. Die Dateien sind noch da, aber keiner weiss, welche Version gilt. Lösung: JDBC2 mit PostgreSQL, mit Backup.
  2. Viele Commit-Konflikte: Mehrere Jobs schreiben gleichzeitig in dieselbe Tabelle. Retries laufen aus, Jobs scheitern mit CommitFailedException. Lösung: Writer serialisieren (z. B. atomares Claimen von Arbeit), weniger und grössere Commits, Retries erhöhen.
  3. Iceberg-GC löscht Daten anderer Branches: expire_snapshots auf Nessie-Tabellen sieht nur einen Branch. Lösung: gc.enabled = false und nessie-gc, oder nur einen Branch nutzen.
  4. Hadoop-Katalog auf S3: Zwei Writer überschreiben sich, weil Umbenennen nicht atomar ist. Lösung: echter Katalog (REST, JDBC, Nessie).
  5. Statische S3-Keys in jeder Engine: schwer zu rotieren, zu breite Rechte. Lösung: Credential Vending über einen REST-Katalog.
  6. Katalog als Single Point of Failure: Fällt der Katalog aus, kann keine Engine lesen oder schreiben. Lösung: mehrere Replicas, HA-Datenbank, Monitoring.

7. Diagnose: Werkzeuge und Befehle

  • curl http://nessie:19120/iceberg/v1/config: prüft, ob der REST-Katalog antwortet und welche Defaults er gibt.
  • curl http://nessie:19120/api/v2/trees: listet Nessie-Branches und Tags.
  • SELECT * FROM lake.silver.trades.metadata_log_entries: welche metadata.json-Dateien es gab und wann.
  • SELECT * FROM lake.silver.trades.refs: Branches und Tags der Tabelle.
  • Spark-Log: CommitFailedException und Retry-Meldungen zeigen Konflikte.
  • Nessie-Metriken: Prometheus-Endpunkt von Quarkus (/q/metrics) für Latenz und Fehler.
  • Backend: Gesundheit und Backups der PostgreSQL-Datenbank hinter Nessie.

8. Senior-Punkte

  1. Der Katalog ist das wertvollste Stück im Lakehouse. Die Dateien sind wertlos, wenn niemand weiss, welche Version gilt. Er braucht HA, Backup und ein echtes Backend.
  2. REST-Spec zuerst. Wer nur REST spricht, kann den Katalog später wechseln. Proprietäre Client-Kataloge binden Engines an einen Anbieter.
  3. Git-Semantik ist ein Werkzeug, kein Muss. Nessie-Branches sind stark für isolierte Loads und Tests. Aber sie verlangen eigene GC und Disziplin.
  4. Sicherheit gehört in den Katalog. Credential Vending und RBAC im Katalog sind besser als S3-Keys in jeder Engine.
  5. Atomar ist nur der Zeiger. Alles davor ist optimistisch. Viele parallele Writer brauchen Koordination ausserhalb von Iceberg.
  6. Cloud-Wahl prägt den Katalog: AWS → Glue oder S3 Tables. Offen und mehrere Engines → REST (Nessie, Polaris). Bestehendes Hadoop → HMS.

10. Fallen

  • „Der Katalog speichert die Daten oder Metadaten.“ → Falsch. Er speichert vor allem den Zeiger auf die aktuelle metadata.json. Alles andere liegt im Object Store.
  • „Iceberg sperrt die Tabelle während des Schreibens.“ → Falsch. Iceberg arbeitet optimistisch. Nur der Zeiger-Tausch ist atomar.
  • „Der Hadoop-Katalog reicht auf S3.“ → Falsch. Umbenennen ist auf Object Stores nicht atomar.
  • „Nessie ist ein eigenes Table Format.“ → Falsch. Nessie ist ein Katalog. Die Tabellen bleiben normale Iceberg-Tabellen.
  • „RocksDB in Nessie ist für Production auf Kubernetes ok.“ → Falsch. Nur für einen Knoten mit dauerhaftem Volume. Production: JDBC2 mit PostgreSQL.
  • „Ein Iceberg-Commit ist immer über mehrere Tabellen atomar.“ → Falsch. Nur pro Tabelle. Mehrere Tabellen brauchen Nessie oder transactions/commit.

11. Fragen

Was macht ein Iceberg-Katalog?

Er hält pro Tabelle den Zeiger auf die aktuelle metadata.json. Er macht Commits atomar durch einen Compare-and-Swap auf diesen Zeiger.

Was ist der atomare Pointer Swap?

Der Writer sagt: „Setze den Zeiger auf die neue Version, aber nur wenn er noch auf meiner Basis steht.“ Klappt es, ist der Commit sichtbar. Sonst gibt es einen Konflikt.

Was passiert bei einem Commit-Konflikt?

Der Client lädt die neue Basis und prüft, ob sich seine Änderungen wirklich überschneiden. Wenn nicht, schreibt er neue Metadaten und versucht es erneut, standardmässig bis zu 4 Mal.

Was ist die Iceberg REST Catalog Spec?

Eine offene OpenAPI-Spezifikation für Kataloge. Jede Engine mit REST-Client kann damit jeden REST-Katalog nutzen.

Was sind requirements und updates in einem REST-Commit?

Requirements sind Bedingungen, z. B. assert-ref-snapshot-id. Updates sind Änderungen, z. B. add-snapshot und set-snapshot-ref. Der Server wendet die Updates nur an, wenn alle Requirements stimmen.

Was ist Credential Vending?

Der Katalog gibt beim Laden einer Tabelle kurzlebige Speicher-Credentials mit. Die Engine braucht keine festen S3-Keys.

Was ist Nessie?

Ein transaktionaler Katalog mit Git-Semantik: Commits, Branches, Tags und Merges über mehrere Tabellen. Er spricht auch die Iceberg-REST-API.

Wofür nutzt man Nessie-Branches?

Für isolierte Loads und Tests. Man schreibt auf einen Branch, prüft die Daten und merged dann atomar nach main.

Welches Backend für Nessie in Production?

JDBC2 mit PostgreSQL, MONGODB2 oder BIGTABLE. ROCKSDB nur auf einem Knoten, IN_MEMORY nur für Tests.

Wie speichert der Hive Metastore den Zeiger?

Als Table Property metadata_location. Der Commit nutzt einen Lock oder ein atomares Alter-Table im Metastore.

Wie funktioniert der Glue-Katalog?

Die Glue-Tabelle hat den Parameter metadata_location. Der Swap nutzt die optimistische Versionierung von Glue.

Wie funktioniert der JDBC-Katalog?

Eine SQL-Tabelle mit metadata_location pro Tabelle. Der Swap ist ein UPDATE mit dem alten Wert in der WHERE-Klausel.

Warum ist der Hadoop-Katalog auf S3 gefährlich?

Er nutzt Umbenennen als atomaren Schritt. Auf Object Stores ist Umbenennen nicht atomar, also können sich Writer überschreiben.

Was ist Apache Polaris?

Ein Open-Source-REST-Katalog für Iceberg. Er bringt Rechteverwaltung (RBAC) und Credential Vending für mehrere Engines.

Sind Iceberg-Commits über mehrere Tabellen atomar?

Nicht von selbst. Iceberg ist atomar pro Tabelle. Nessie-Commits oder der REST-Endpunkt transactions/commit können mehrere Tabellen zusammen ändern.

Wie konfigurieren Sie einen Katalog in Spark?

Mit spark.sql.catalog.<name> = org.apache.iceberg.spark.SparkCatalog, dazu type (z. B. rest), uri und warehouse.

Was passiert, wenn der Katalog ausfällt?

Keine Engine kann Tabellen laden oder committen. Die Dateien sind sicher, aber unbenutzbar. Darum braucht der Katalog HA und Backups.

Warum darf man bei Nessie nicht einfach expire_snapshots laufen lassen?

Iceberg sieht nur die Snapshots eines Branches. Andere Branches brauchen vielleicht dieselben Dateien. Darum empfiehlt Iceberg gc.enabled = false und nessie-gc.

Welchen Katalog wählen Sie für eine neue Plattform?

Einen REST-Katalog, damit alle Engines über eine offene API arbeiten. Nessie bei Bedarf an Branches, Polaris bei Fokus auf Rechte, Glue in reinem AWS.

Szenario: Nach einem Pod-Neustart sind alle Tabellen in Nessie leer oder unbekannt. Was ist passiert?

Nessie lief mit In-Memory oder RocksDB ohne dauerhaftes Volume. Der Zeiger-Zustand ist weg, die Dateien nicht. Lösung: JDBC2 mit PostgreSQL und Backups. Die Tabellen lassen sich mit register_table aus der letzten metadata.json wieder anmelden.

Szenario: Zwei Ingest-Jobs scheitern immer wieder mit CommitFailedException. Was tun Sie?

Prüfen, ob sie dieselbe Tabelle gleichzeitig ändern. Arbeit atomar claimen, damit sich Jobs nicht überlappen. Weniger, grössere Commits und mehr Retries.

Szenario: Ein Team will von Nessie auf Polaris wechseln. Was ist der Aufwand?

Wenn alle Engines nur die REST-API nutzen, ändert sich vor allem die Konfiguration. Die Tabellen meldet man mit register_table neu an. Nessie-Branches und -Historie gehen dabei nicht mit.
