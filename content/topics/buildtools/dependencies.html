Abhängigkeiten: Scopes, Konflikte, BOM

Kern: Dependency Management ist die Verwaltung der Bibliotheken, die ein Projekt braucht. Maven lädt auch die Abhängigkeiten der Abhängigkeiten (transitive Dependencies). Wenn zwei Wege verschiedene Versionen bringen, entscheidet Nearest wins. Scopes steuern, wo eine Abhängigkeit gilt, und BOMs legen zusammenpassende Versionen zentral fest.

1. Wo sitzen die Abhängigkeiten?

  1. Direkte Abhängigkeit: steht in Ihrem POM. Beispiel: lib-a, lib-b.
  2. Transitive Abhängigkeit: kommt über eine andere Bibliothek mit. Beispiel: jackson über lib-a.
  3. Konflikt: Dasselbe Artefakt (groupId:artifactId) kommt in zwei Versionen. Auf dem Classpath darf nur eine liegen.
  4. Nearest wins: Die Version mit dem kürzesten Weg zur Wurzel gewinnt. Bei gleicher Tiefe gewinnt die zuerst deklarierte.
  5. dependencyManagement: legt Versionen zentral fest. Es hat Vorrang vor der Mediation bei transitiven Abhängigkeiten.

2. Die Reise einer Abhängigkeit bis zum Classpath

  1. Deklaration: Sie schreiben spring-boot-starter-web ins POM, oft ohne Version.
  2. Graph bauen: Maven liest das POM jeder Abhängigkeit und deren Abhängigkeiten. So entsteht ein Baum mit Dutzenden Knoten.
  3. Management anwenden: Versionen aus dependencyManagement und importierten BOMs werden eingesetzt. Hier kommt z. B. die Jackson-Version aus dem Spring-Boot-BOM.
  4. Mediation: Bleiben Konflikte, gewinnt die nächste Version. Exclusions schneiden Äste ab.
  5. Scope-Filter: Abhängigkeiten mit Scope test oder provided gehen nicht weiter an Konsumenten.
  6. Download: Fehlende JARs kommen aus dem Remote-Repo in den lokalen Cache.
  7. Classpath: Je nach Scope landen sie auf dem Compile-, Test- oder Runtime-Classpath.

3. Beispiel: Baum lesen, Konflikt lösen, BOM nutzen

<dependencyManagement>
  <dependencies>
    <dependency>                                  <!-- BOM importieren -->
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>   <!-- keine Version nötig -->
  </dependency>
  <dependency>
    <groupId>com.example</groupId>
    <artifactId>legacy-client</artifactId>
    <version>3.2.0</version>
    <exclusions><exclusion>                    <!-- alten Logger abschneiden -->
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion></exclusions>
  </dependency>
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>                       <!-- nur zur Laufzeit -->
  </dependency>
</dependencies>

4. Details, die Interviewer fragen

  1. Scopes:
    • compile (Standard): überall verfügbar und transitiv. Beispiel: Spring.
    • provided: zum Kompilieren und Testen, zur Laufzeit liefert sie die Umgebung. Nicht transitiv. Beispiel: Servlet-API im Application Server, Lombok.
    • runtime: nicht zum Kompilieren, aber zur Laufzeit und im Test. Transitiv. Beispiel: JDBC-Treiber.
    • test: nur für Testcode. Nicht transitiv. Beispiel: JUnit, Mockito.
    • system: wie provided, aber aus einem lokalen Pfad. Veraltet, vermeiden.
    • import: nur in dependencyManagement mit type pom. Importiert ein BOM.
  2. Transitivität: Eine transitive Abhängigkeit im Scope compile bekommt den Scope der direkten Abhängigkeit. Ist die direkte test, wird die transitive auch test. Transitive provided- und test-Abhängigkeiten fallen immer weg.
  3. Nearest wins genau: kürzester Pfad zur Wurzel, bei Gleichstand die zuerst deklarierte. Die höhere Version gewinnt nicht automatisch. Darum kann ein Upgrade einer Bibliothek eine ältere transitive Version bringen.
  4. Direkt deklarieren schlägt alles ausser dependencyManagement: Eine Version direkt im POM hat Tiefe 1 und gewinnt die Mediation.
  5. dependencyManagement vs dependencies: dependencyManagement legt nur Versionen, Scopes und Exclusions fest. Es fügt keine Abhängigkeit hinzu. dependencies fügt sie hinzu.
  6. BOM: Ein Bill of Materials ist ein POM, das in dependencyManagement passende Versionen einer Bibliotheksfamilie festlegt. Beispiele: spring-boot-dependencies, jackson-bom, junit-bom, testcontainers-bom. Importiert man mehrere BOMs, gewinnt bei Überschneidung das zuerst importierte.
  7. Parent vs BOM: Ein Projekt hat nur einen Parent. BOMs kann man mehrere importieren. Darum sind BOMs flexibler.
  8. optional: <optional>true</optional> heisst: Meine Konsumenten bekommen diese Abhängigkeit nicht automatisch. Sinnvoll für Bibliotheken mit Zusatz-Features.
  9. Exclusions: schneiden einen transitiven Ast ab. Typisch: alter Logger, doppelte Implementierungen, Konflikt-Bibliotheken.
  10. Dependency Convergence: Die Enforcer-Regel dependencyConvergence lässt den Build scheitern, wenn dasselbe Artefakt in verschiedenen Versionen im Baum vorkommt. So entscheidet man Konflikte bewusst.
  11. Symptome eines Konflikts: NoSuchMethodError, ClassNotFoundException, NoClassDefFoundError, AbstractMethodError zur Laufzeit. Kompiliert hat es, weil der Compile-Classpath anders war oder die Version erst zur Laufzeit wechselte.
  12. CVE-Scanning: Eine CVE ist eine öffentlich bekannte Sicherheitslücke mit Kennung. Werkzeuge vergleichen den ganzen Baum mit Datenbanken: OWASP Dependency-Check (Maven-Plugin), Trivy (auch Images), Snyk, GitHub Dependabot, Renovate für Updates. Transitive Lücken behebt man über dependencyManagement, nicht über Exclusions.
  13. SBOM: Eine Software Bill of Materials listet alle Komponenten eines Artefakts, z. B. im Format CycloneDX. Sie hilft bei der Frage: „Sind wir von der neuen Lücke betroffen?“

5. Vergleich

  • Maven: Nearest wins, Scopes, BOM über import.
  • Gradle: standardmässig höchste Version. Konfigurationen statt Scopes: implementation, api, compileOnly, runtimeOnly, testImplementation. BOMs über platform(...). Lock-Dateien möglich.
  • provided vs optional: Umgebung liefert zur Laufzeit vs Konsument entscheidet selbst.
  • Exclusion vs dependencyManagement: Ast entfernen vs Version erzwingen.
  • Parent-POM vs BOM: einer, vererbt auch Plugins und Properties vs mehrere, nur Versionen.
  • Dependency-Check vs Trivy: Java-Abhängigkeiten im Build vs Abhängigkeiten und OS-Pakete im fertigen Image.

6. In der Produktion

  1. NoSuchMethodError nach Upgrade: Zwei Bibliotheken brauchen verschiedene Versionen von z. B. Jackson. Nearest wins wählte die alte. Lösung: dependency:tree -Dverbose, Version im dependencyManagement festlegen, Enforcer-Regel.
  2. Kritische CVE in transitiver Abhängigkeit: Lösung: Version in dependencyManagement anheben, testen, deployen. Langfristig: direkte Bibliothek aktualisieren.
  3. Doppelte Logger-Bindings: „Multiple SLF4J providers“. Lösung: Exclusion der zweiten Implementierung.
  4. Fat JAR zu gross: Test- oder Build-Bibliotheken mit falschem Scope landen im Artefakt. Lösung: Scopes korrigieren, dependency:analyze.
  5. Build bricht ohne Code-Änderung: Version-Ranges oder SNAPSHOTs ziehen neue Versionen. Lösung: feste Versionen, keine Ranges.
  6. Supply-Chain-Risiko: Abhängigkeiten aus unbekannten Repos. Lösung: ein internes Repository als Proxy (Nexus, Artifactory, Azure Artifacts), Checksums, Scanning in der Pipeline.

7. Diagnose: Werkzeuge und Befehle

  • mvn dependency:tree, mit -Dverbose (verworfene Knoten) und -Dincludes=groupId:artifactId (Filter).
  • mvn dependency:tree -DoutputType=json (seit Plugin 3.7.0) für Werkzeuge.
  • mvn dependency:analyze: benutzt-aber-nicht-deklariert und deklariert-aber-unbenutzt.
  • mvn help:effective-pom: welche Version kommt aus welchem Management.
  • mvn versions:display-dependency-updates: verfügbare Updates.
  • maven-enforcer-plugin mit dependencyConvergence, banDuplicatePomDependencyVersions.
  • mvn org.owasp:dependency-check-maven:check, trivy fs . oder trivy image app:1.0.
  • Gradle: ./gradlew dependencies, ./gradlew dependencyInsight --dependency jackson-databind.
  • Laufzeit: java -verbose:class zeigt, aus welchem JAR eine Klasse geladen wird.

8. Senior-Punkte

  1. Versionen zentral, nie verstreut. Ein BOM oder Parent für alle Services. Module deklarieren keine Versionen.
  2. Konflikte bewusst entscheiden. Enforcer mit dependencyConvergence macht stille Mediation sichtbar.
  3. Was ich nutze, deklariere ich direkt. Sich auf transitive Abhängigkeiten zu verlassen bricht beim nächsten Upgrade.
  4. Scanning ist Teil der Pipeline, mit klaren Regeln: Kritisch blockiert den Build, Ausnahmen werden dokumentiert und laufen ab.
  5. Weniger Abhängigkeiten = weniger Risiko. Jede Bibliothek bringt Lücken, Konflikte und Upgrade-Arbeit.
  6. Automatische Updates (Renovate, Dependabot) mit guter Testabdeckung. Kleine, häufige Upgrades sind billiger als ein grosser Sprung.

10. Fallen

  • „Maven nimmt die neueste Version.“ → Falsch. Maven nimmt die nächste. Gradle nimmt standardmässig die höchste.
  • „dependencyManagement fügt Abhängigkeiten hinzu.“ → Falsch. Es legt nur Versionen fest.
  • „test-Abhängigkeiten meiner Bibliothek kommen bei Konsumenten an.“ → Falsch. test und provided sind nicht transitiv.
  • „Eine CVE in einer transitiven Abhängigkeit kann ich nicht beheben.“ → Falsch. Version im dependencyManagement anheben.
  • „Exclusion ist die Lösung für jeden Konflikt.“ → Nur wenn die Klasse wirklich nicht gebraucht wird. Sonst Version festlegen.
  • „Kompiliert, also passen die Versionen.“ → Falsch. Konflikte zeigen sich oft erst zur Laufzeit als NoSuchMethodError.

11. Fragen

Was ist eine transitive Abhängigkeit?

Eine Abhängigkeit, die über eine andere Bibliothek mitkommt, ohne dass Sie sie selbst deklarieren.

Welche Scopes gibt es in Maven?

compile, provided, runtime, test, system und import.

Was ist der Unterschied zwischen provided und runtime?

provided: zum Kompilieren da, zur Laufzeit liefert die Umgebung. runtime: nicht zum Kompilieren, aber zur Laufzeit da.

Welche Scopes sind nicht transitiv?

provided und test.

Wie löst Maven Versionskonflikte?

Nearest wins: die Version mit dem kürzesten Pfad. Bei gleicher Tiefe die zuerst deklarierte.

Gewinnt in Maven die höhere Version?

Nein, nur die nähere. Darum kann eine ältere Version gewinnen.

Wie erzwingen Sie eine Version?

Im dependencyManagement festlegen oder direkt deklarieren. Management hat Vorrang bei transitiven Abhängigkeiten.

Was ist der Unterschied zwischen dependencyManagement und dependencies?

dependencyManagement legt nur Versionen und Scopes fest. dependencies fügt Abhängigkeiten tatsächlich hinzu.

Was ist ein BOM?

Ein POM mit passenden Versionen einer Bibliotheksfamilie im dependencyManagement. Man importiert es mit type pom und scope import.

Warum BOM statt Parent?

Man hat nur einen Parent, kann aber mehrere BOMs importieren.

Was passiert, wenn zwei BOMs dieselbe Bibliothek verwalten?

Das zuerst importierte BOM gewinnt. Die Reihenfolge ist also wichtig.

Was macht eine Exclusion?

Sie entfernt einen transitiven Ast unter einer bestimmten Abhängigkeit.

Was bedeutet optional true?

Konsumenten meiner Bibliothek bekommen diese Abhängigkeit nicht automatisch. Sie fügen sie bei Bedarf selbst hinzu.

Wie finden Sie heraus, woher eine Version kommt?

mvn dependency:tree -Dverbose -Dincludes=gruppe:artefakt. In Gradle dependencyInsight.

Was zeigt dependency:analyze?

Genutzte, aber nicht deklarierte Abhängigkeiten und deklarierte, aber ungenutzte.

Welche Fehler deuten auf einen Versionskonflikt?

NoSuchMethodError, NoClassDefFoundError, ClassNotFoundException oder AbstractMethodError zur Laufzeit.

Was macht die Enforcer-Regel dependencyConvergence?

Sie lässt den Build scheitern, wenn ein Artefakt in mehreren Versionen im Baum vorkommt.

Wie scannen Sie Abhängigkeiten auf Sicherheitslücken?

OWASP Dependency-Check im Build, Trivy für Images, Snyk oder Dependabot. Kritische Funde blockieren die Pipeline.

Was ist eine SBOM?

Eine Liste aller Komponenten eines Artefakts, z. B. als CycloneDX. Sie beantwortet schnell, ob man von einer neuen Lücke betroffen ist.

Wie unterscheiden sich api und implementation in Gradle?

api gibt die Abhängigkeit an Konsumenten weiter. implementation hält sie intern. Das reduziert Kopplung und Neukompilierung.

Szenario: Nach einem Library-Upgrade wirft Produktion NoSuchMethodError in Jackson. Wie gehen Sie vor?

dependency:tree -Dverbose zeigt, welche Jackson-Version gewann. Ich setze die passende Version über das BOM im dependencyManagement und sichere es mit dependencyConvergence ab.

Szenario: Der Scanner meldet eine kritische CVE in einer transitiven Abhängigkeit. Was tun Sie?

Prüfen, ob der betroffene Code genutzt wird. Version im dependencyManagement anheben, testen, deployen. Dann die direkte Bibliothek aktualisieren und die Übersteuerung entfernen.

Szenario: Das Fat JAR enthält JUnit und Mockito. Was ist falsch?

Die Test-Bibliotheken haben nicht den Scope test. Ich korrigiere den Scope und prüfe mit dependency:tree.
