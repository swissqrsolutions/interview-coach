Maven: Lifecycle, Phasen, Plugins

Kern: Maven ist ein Build-Tool für Java, das nach Konvention baut: feste Ordner, ein fester Lifecycle aus geordneten Phasen. Die eigentliche Arbeit machen Plugin-Goals, die an Phasen gebunden sind. Wer eine Phase aufruft, bekommt alle vorherigen Phasen dazu. Aktuell sind Maven 3.10.x und 3.9.x; Maven 4 ist noch Release Candidate (Stand November 2026).

1. Wo sitzt was in Maven?

  1. mvn / mvnw: der Aufruf. Der Maven Wrapper (./mvnw) lädt eine feste Maven-Version. So baut jeder mit derselben Version.
  2. POM: das Project Object Model in pom.xml: Koordinaten (groupId:artifactId:version), Abhängigkeiten, Plugins. Zusammen mit Parent und Super-POM ergibt sich die Effective POM.
  3. Reactor: sortiert in Multi-Modul-Projekten die Module nach ihren Abhängigkeiten. Beispiel: domain vor service vor app.
  4. Lifecycle: die feste Reihenfolge der Phasen. Phasen sind nur Namen.
  5. Plugin-Goals: die Arbeit. Ein Goal (auch Mojo) ist eine Aufgabe eines Plugins, z. B. compiler:compile.
  6. Repositories: Maven lädt Plugins und Abhängigkeiten aus Remote-Repos in den lokalen Cache ~/.m2/repository.

2. Die Reise von mvn verify

  1. validate: Maven liest die POMs, baut die Effective POM und prüft sie. Der Reactor legt die Modul-Reihenfolge fest.
  2. Ressourcen und compile: resources:resources kopiert src/main/resources. compiler:compile übersetzt src/main/java nach target/classes.
  3. test-compile und test: Testcode wird übersetzt. surefire:test führt Unit-Tests aus. Ein roter Test stoppt den Build hier.
  4. package: jar:jar baut target/app-1.0.jar. Bei Spring Boot packt spring-boot:repackage ein ausführbares JAR.
  5. integration-test: failsafe:integration-test führt *IT-Tests gegen das gebaute Artefakt aus. Fehler stoppen den Build hier noch nicht.
  6. post-integration-test, dann verify: Aufräumen läuft (z. B. Container stoppen). Erst failsafe:verify macht den Build rot.
  7. install und deploy laufen nicht: verify ist die letzte gewählte Phase. install legt das JAR in ~/.m2, deploy lädt es in ein Remote-Repo.

3. Beispiel: Phasen, Bindings und ein Multi-Modul-Build

<!-- pom.xml (Parent, gekürzt) -->
<packaging>pom</packaging>
<modules>
  <module>domain</module>
  <module>service</module>   <!-- hängt von domain ab -->
  <module>app</module>       <!-- hängt von service ab -->
</modules>
<build><pluginManagement><plugins>
  <plugin>
    <artifactId>maven-failsafe-plugin</artifactId>
    <executions><execution>
      <goals><goal>integration-test</goal><goal>verify</goal></goals>
    </execution></executions>
  </plugin>
</plugins></pluginManagement></build>
<profiles>
  <profile>
    <id>ci</id>
    <activation><property><name>env.CI</name></property></activation>
    <properties><skipITs>false</skipITs></properties>
  </profile>
</profiles>

4. Details, die Interviewer fragen

  1. Drei Lifecycles: clean (pre-clean, clean, post-clean), default (Build bis deploy), site (Projekt-Website).
  2. Wichtige Phasen von default: validate, compile, test, package, integration-test, verify, install, deploy. Insgesamt sind es 23 Phasen, viele davon Zwischenphasen wie process-resources oder prepare-package.
  3. Phase vs Goal: Eine Phase ist ein Schritt im Lifecycle ohne eigene Logik. Ein Goal ist eine konkrete Aufgabe eines Plugins. Man kann beide aufrufen: mvn clean dependency:tree package.
  4. Standard-Bindings für jar: process-resources → resources:resources, compile → compiler:compile, test → surefire:test, package → jar:jar, install → install:install, deploy → deploy:deploy.
  5. Eigene Bindings: Unter <executions> bindet man ein Goal an eine Phase, z. B. jacoco:report an verify oder einen Code-Generator an generate-sources.
  6. Surefire vs Failsafe: Surefire stoppt bei Fehlern sofort. Failsafe stoppt erst in verify. So läuft post-integration-test immer und räumt auf. Darum mvn verify aufrufen, nicht integration-test.
  7. Test überspringen: -DskipTests kompiliert Tests, führt sie nicht aus. -Dmaven.test.skip=true kompiliert sie gar nicht. -DskipITs überspringt nur Failsafe.
  8. Multi-Modul: Ein Aggregator (<modules>) baut mehrere Module gemeinsam. Ein Parent (<parent>) vererbt Konfiguration. Oft ist ein POM beides, muss es aber nicht.
  9. Reactor-Optionen: -pl Module wählen, -am Abhängigkeiten mitbauen, -amd Abhängige mitbauen, -rf :modul ab diesem Modul fortsetzen, -T parallel.
  10. Profile: Ein Profil ändert die POM unter einer Bedingung. Aktivierung: -P name, activeByDefault, Property, JDK-Version, Betriebssystem, Existenz einer Datei. activeByDefault wird deaktiviert, sobald ein anderes Profil aktiv ist.
  11. Profile mit Vorsicht: Profile für Umgebungen (dev/prod) im Artefakt sind ein Anti-Pattern. Ein Artefakt sollte überall gleich sein. Umgebung gehört in die Laufzeit-Konfiguration.
  12. settings.xml: ~/.m2/settings.xml enthält Mirrors, Proxy und Zugangsdaten für Repos. Es gehört nicht ins Projekt-Repo.
  13. SNAPSHOT vs Release: 1.0-SNAPSHOT ist veränderlich und wird neu geladen. 1.0 ist unveränderlich. Releases dürfen keine SNAPSHOT-Abhängigkeiten haben.
  14. Maven 4 (RC): Neue before:- und after:-Phasen ersetzen pre-* und post-*. Es trennt Build-POM und Consumer-POM und braucht Java 17 zum Laufen.

5. Vergleich: Maven vs Gradle

  • Modell: Maven hat einen festen Lifecycle mit Phasen. Gradle hat einen Task-Graphen (DAG): Tasks und ihre Abhängigkeiten.
  • Konfiguration: Maven: deklaratives XML. Gradle: Kotlin- oder Groovy-DSL, also Code.
  • Geschwindigkeit: Gradle hat inkrementelle Tasks, einen Build Cache und einen Daemon. Unveränderte Tasks werden übersprungen. Maven baut ohne Erweiterungen jede Phase neu.
  • Konflikte: Maven: Nearest wins. Gradle: standardmässig die höchste Version.
  • API vs Implementation: Gradle trennt api und implementation. So sickern interne Abhängigkeiten nicht zu Konsumenten durch. Maven kennt das nicht direkt.
  • Lernkurve: Maven ist einheitlich und schnell verstanden. Gradle ist flexibler, aber Build-Skripte können komplex werden.
  • Versionen: aktuell Gradle 9.9 (November 2026), Maven 3.10/3.9.

6. In der Produktion (CI)

  1. Build auf CI anders als lokal: Andere Maven- oder JDK-Version. Lösung: Maven Wrapper, Toolchains oder festes Build-Image, maven-enforcer-plugin mit requireMavenVersion und requireJavaVersion.
  2. Integrationstests hinterlassen Container: mvn integration-test statt verify aufgerufen. post-integration-test lief nicht. Lösung: immer verify.
  3. Langsamer CI-Build: Jeder Lauf lädt alles neu. Lösung: ~/.m2/repository cachen, -T parallel, nur geänderte Module mit -pl … -amd.
  4. Plugin-Version nicht fixiert: Maven warnt, und der Build ändert sich mit neuen Maven-Versionen. Lösung: alle Plugin-Versionen in pluginManagement festlegen.
  5. Docker-Build: Im Multi-Stage-Dockerfile zuerst nur pom.xml kopieren und dependency:go-offline ausführen. Dann den Code. So bleibt die Abhängigkeits-Schicht im Cache.
  6. Interaktive Logs im CI: Lösung: -B (batch mode) und -ntp (kein Download-Fortschritt).

7. Diagnose: Werkzeuge und Befehle

  • mvn help:effective-pom: die vollständige POM nach Vererbung.
  • mvn help:active-profiles: welche Profile aktiv sind.
  • mvn help:describe -Dplugin=surefire -Ddetail: Goals und Parameter eines Plugins.
  • mvn -X: Debug-Ausgabe. -e: Stacktraces bei Fehlern.
  • mvn -B -ntp verify: CI-taugliche Ausgabe.
  • mvn -rf :service verify: nach einem Fehler ab dem Modul fortsetzen.
  • mvn -o: offline bauen, prüft ob alles lokal da ist.
  • Gradle: ./gradlew build --scan, ./gradlew tasks, --dry-run.

8. Senior-Punkte

  1. Konvention schlägt Konfiguration. Ein Standard-Maven-Projekt versteht jeder neue Kollege sofort. Eigene Lifecycle-Tricks kosten Wartung.
  2. Reproduzierbar bauen: Wrapper, fixierte Plugin-Versionen, Enforcer, keine SNAPSHOTs in Releases.
  3. Ein Artefakt für alle Umgebungen. Keine Profile pro Stage. Konfiguration zur Laufzeit.
  4. Parent-POM oder BOM zentral pflegen, damit viele Services gleiche Versionen nutzen.
  5. Maven oder Gradle? Maven für Einheitlichkeit und einfache Services. Gradle für grosse Mono-Repos, wo Build-Cache und inkrementelle Builds viel Zeit sparen.

10. Fallen

  • „mvn install braucht man für jeden Build.“ → Falsch. Im Reactor reicht verify. install nur, wenn andere Projekte lokal darauf zugreifen.
  • „Eine Phase führt nur sich selbst aus.“ → Falsch. Sie führt alle vorherigen Phasen ihres Lifecycles aus.
  • „pluginManagement aktiviert das Plugin.“ → Falsch. Es setzt nur Version und Konfiguration.
  • „mvn integration-test reicht für ITs.“ → Falsch. Dann läuft post-integration-test nicht und der Build wird nicht rot. verify nutzen.
  • „-DskipTests und -Dmaven.test.skip sind gleich.“ → Falsch. Das zweite kompiliert die Tests nicht einmal.
  • „Parent und Aggregator sind dasselbe.“ → Falsch. Parent vererbt, Aggregator baut zusammen.

11. Fragen

Was ist der Maven-Lifecycle?

Eine feste Reihenfolge von Phasen. Wer eine Phase aufruft, führt alle vorherigen Phasen mit aus.

Welche Lifecycles gibt es?

clean, default und site.

Nennen Sie die wichtigsten Phasen von default.

validate, compile, test, package, integration-test, verify, install, deploy.

Was ist der Unterschied zwischen Phase und Goal?

Eine Phase ist ein Schritt im Lifecycle ohne eigene Logik. Ein Goal ist eine Aufgabe eines Plugins, die an eine Phase gebunden wird.

Welches Goal läuft in der Phase test?

surefire:test, bei Packaging jar standardmässig.

Was ist ein Mojo?

Die Implementierung eines Plugin-Goals (Maven plain Old Java Object).

Warum Failsafe für Integrationstests?

Failsafe lässt den Build erst in verify scheitern. So läuft post-integration-test immer und räumt die Umgebung auf.

Was ist der Unterschied zwischen -DskipTests und -Dmaven.test.skip=true?

-DskipTests kompiliert Tests, führt sie aber nicht aus. maven.test.skip kompiliert sie auch nicht.

Was ist der Reactor?

Der Teil von Maven, der in Multi-Modul-Builds die Module nach Abhängigkeiten sortiert und baut.

Was machen -pl, -am und -amd?

-pl wählt Module, -am baut ihre Abhängigkeiten mit, -amd baut die Module mit, die von ihnen abhängen.

Was ist der Unterschied zwischen Parent und Aggregator?

Ein Parent vererbt Konfiguration. Ein Aggregator listet Module und baut sie gemeinsam.

Was ist pluginManagement?

Zentrale Festlegung von Plugin-Versionen und Konfiguration, ohne das Plugin zu aktivieren.

Was sind Maven-Profile und wie aktiviert man sie?

Bedingte Änderungen an der POM. Aktiviert mit -P, activeByDefault, Property, JDK, OS oder Datei.

Warum sind Umgebungs-Profile ein Anti-Pattern?

Dann gibt es pro Umgebung ein anderes Artefakt. Getestet wird nicht, was in Produktion läuft.

Was ist die Effective POM?

Die vollständige POM nach Vererbung von Parent und Super-POM und nach aktiven Profilen. Anzeigen mit help:effective-pom.

Was ist der Maven Wrapper?

Ein Skript (mvnw), das eine feste Maven-Version lädt. So bauen alle und das CI mit derselben Version.

Was ist ein SNAPSHOT?

Eine veränderliche Entwicklungsversion. Maven lädt sie neu. Ein Release darf keine SNAPSHOT-Abhängigkeiten haben.

Was ändert Maven 4?

before:/after:-Phasen statt pre-/post-, Trennung von Build- und Consumer-POM, Java 17 als Laufzeit. Stand November 2026 noch Release Candidate.

Maven oder Gradle?

Maven: einfach, einheitlich, deklarativ. Gradle: schneller durch Build-Cache und inkrementelle Tasks, flexibler, aber komplexer.

Wie löst Gradle Versionskonflikte im Unterschied zu Maven?

Gradle nimmt standardmässig die höchste Version. Maven nimmt die Version, die im Baum am nächsten ist.

Szenario: Der Build ist lokal grün und im CI rot. Wo suchen Sie?

Unterschiede bei Maven-, JDK- und Plugin-Versionen, settings.xml, aktiven Profilen und Umgebungsvariablen. Wrapper und Enforcer verhindern das.

Szenario: Nach jedem CI-Lauf bleiben Test-Container liegen. Was ist falsch?

Wahrscheinlich wird integration-test statt verify aufgerufen. Dann läuft post-integration-test nicht.

Szenario: Der Multi-Modul-Build dauert 25 Minuten. Wie beschleunigen Sie?

Repository cachen, -T parallel, nur geänderte Module mit -pl und -amd bauen, Integrationstests trennen. Bei sehr grossen Repos Gradle mit Build-Cache prüfen.
