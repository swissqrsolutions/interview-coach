Gradle-Grundlagen und Maven vs Gradle

Kern: Gradle ist ein Build-Tool, dessen Build-Skripte in Kotlin oder Groovy geschrieben sind. Es baut einen Task-Graphen und führt nur Tasks aus, deren Eingaben sich geändert haben. Maven beschreibt dagegen das Projekt deklarativ in einer pom.xml mit festem Lebenszyklus.

Antwort-Muster

Frage: Wie funktioniert ein Gradle-Build und was unterscheidet ihn von Maven?

  1. Mechanismus: Gradle durchläuft drei Phasen: Initialization, Configuration, Execution. Es baut einen Task-Graphen und führt nur nötige Tasks aus.
  2. Zahl: Der Daemon läuft seit Gradle 3.0 standardmässig und beendet sich nach drei Stunden Leerlauf. Build-Cache ist standardmässig aus.
  3. Trade-off: Gradle ist flexibler und bei grossen Builds oft schneller. Maven ist einheitlicher und einfacher zu lesen.
  4. Produktion: Ich nutze immer den Wrapper und committe ihn, damit alle dieselbe Gradle-Version verwenden.

1. Ein Gradle-Lauf, in 7 Schritten

  1. Wrapper: ./gradlew build liest gradle-wrapper.properties. Beim ersten Mal lädt es die dort genannte Gradle-Version und legt sie im Gradle User Home ab.
  2. Daemon: Der Wrapper nutzt einen laufenden Daemon wieder. Ist keiner passend da, startet er einen neuen.
  3. Initialization: Gradle führt Init-Skripte aus und liest die Settings-Datei. Sie legt fest, welche Projekte zum Build gehören.
  4. Configuration: Gradle wertet die Build-Dateien aller Projekte aus. Plugins und Skripte registrieren Tasks und deren Eingaben und Ausgaben.
  5. Task-Graph: Aus den gewählten Tasks und ihren Abhängigkeiten entsteht der Plan. Unabhängige Tasks dürfen parallel laufen.
  6. Up-to-date prüfen: Gradle vergleicht Fingerabdrücke der Eingaben mit dem letzten Lauf. Gleich heisst der Task wird übersprungen (UP-TO-DATE).
  7. Execution: Gradle führt die übrigen Tasks in der Reihenfolge des Graphen aus.

Der Build-Cache und der Configuration Cache sind zwei weitere Abkürzungen. Der erste spart Tasks, der zweite spart die Configuration-Phase.

2. Aufbau

  1. settings.gradle(.kts): nennt den Namen des Root-Projekts und die Subprojekte mit include.
  2. build.gradle(.kts): beschreibt ein Projekt. Die Endung .kts steht für Kotlin, ohne sie ist es Groovy.
  3. Task: die kleinste Arbeitseinheit, zum Beispiel Kompilieren oder Testen. Tasks haben Eingaben, Ausgaben und Abhängigkeiten.
  4. Plugin: erweitert Gradle. Das Java-Plugin fügt Tasks und Konventionen hinzu.
  5. Wrapper: gradlew, gradlew.bat und gradle-wrapper.properties mit distributionUrl.
  6. Gradle User Home: hier liegen die geladenen Distributionen und standardmässig der lokale Build-Cache.

3. Details

  1. Drei Phasen: Initialization erkennt die Projekte. Configuration baut den Task-Graphen. Execution führt die gewählten Tasks aus.
  2. Configuration-Phase läuft immer: Auch wenn alle Tasks übersprungen werden, läuft sie. Schwere Arbeit dort verlängert jeden Build. Der Configuration Cache spart diese Phase.
  3. Up-to-date-Prüfung: Gradle bildet einen Fingerabdruck der Eingaben (Pfade und Inhalts-Hash) vor dem Lauf und der Ausgaben danach. Auch der Code des Tasks zählt als Eingabe.
  4. NO-SOURCE: Sind alle mit @SkipWhenEmpty markierten Eingaben leer, zeigt Gradle NO-SOURCE.
  5. Build-Cache: Er verwendet Task-Ausgaben anderer Builds wieder. Der Schlüssel entsteht aus den Eingaben des Tasks. Der Cache ist standardmässig aus. Man schaltet ihn mit --build-cache oder org.gradle.caching=true ein.
  6. Lokal und remote: Der lokale Cache ist ein Verzeichnis im Gradle User Home. Ein Remote-Cache läuft über HTTP. Gradle fragt erst lokal, dann remote.
  7. Configuration Cache: Er speichert das Ergebnis der Configuration-Phase. Seit Gradle 9.0 ist er der bevorzugte Modus. Standardmässig an wird er laut Doku in Gradle 10.
  8. Daemon: Ein langlebiger Prozess, der den Build-Motor hält. Er ist seit Gradle 3.0 standardmässig aktiv. Nach drei Stunden Leerlauf beendet er sich. Er wird nur bei exakt gleicher Java- und Gradle-Version wiederverwendet.
  9. api und implementation: api reicht eine Abhängigkeit an die Compile-Classpath der Konsumenten weiter. implementation nicht. Darum müssen Konsumenten bei Änderungen an implementation nicht neu kompilieren.
  10. Weitere Configurations: compileOnly nur zum Kompilieren, runtimeOnly nur zur Laufzeit, testImplementation für Tests. Das Plugin java-library bietet api.
  11. Maven-Lebenszyklus: Maven hat feste Phasen wie validate, compile, test, package, verify, install, deploy. Wer eine Phase startet, startet alle früheren. Gradle kennt keine festen Phasen, sondern Tasks mit Abhängigkeiten.
  12. Maven heute: Laut Download-Seite ist Maven 3.10.2 die aktuelle Version und läuft ab JDK 8. Maven 4 ist noch ein Preview und für Produktion nicht freigegeben. Es braucht JDK 17.

4. Fallen

  • „Gradle führt bei jedem Lauf alle Tasks aus.“ → Falsch. Es überspringt Tasks mit unveränderten Eingaben (UP-TO-DATE). Das ist der Kern der Geschwindigkeit.
  • „Der Build-Cache ist standardmässig an.“ → Falsch. Er ist aus. Man schaltet ihn mit --build-cache oder org.gradle.caching=true ein.
  • „Die Configuration-Phase wird bei UP-TO-DATE übersprungen.“ → Falsch. Sie läuft immer, ausser der Configuration Cache trifft. Darum keine schwere Arbeit in der Configuration-Phase.
  • „Mit api statt implementation ist man sicherer.“ → Falsch. api macht die Abhängigkeit für alle Konsumenten sichtbar und löst bei Änderungen mehr Neukompilierung aus. Die Doku empfiehlt implementation.
  • „Den Wrapper muss man nicht einchecken.“ → Falsch. Man soll die Wrapper-Dateien einchecken, damit alle dieselbe Gradle-Version nutzen.
  • „Maven 4 ist der aktuelle Stand für Produktion.“ → Falsch. Laut Download-Seite ist Maven 4 noch ein Preview. Die aktuelle Version ist 3.10.2.

5. Selbsttest

Warum?

Warum nutzt man den Gradle Wrapper?

Alle Entwickler und der CI-Server nutzen dieselbe Gradle-Version, ohne sie zu installieren. Der Wrapper lädt sie bei Bedarf.

Warum ist Gradle bei grossen Builds oft schneller als Maven?

Es überspringt Tasks mit unveränderten Eingaben, nutzt Build-Cache und Daemon und kann Tasks parallel ausführen.

Warum implementation statt api?

Interne Abhängigkeiten bleiben unsichtbar für Konsumenten. Das gibt weniger Neukompilierung und einen kleineren Vertrag.

Wie innen?

Welche Phasen hat ein Gradle-Build?

Initialization, Configuration und Execution.

Wie erkennt Gradle, dass ein Task übersprungen werden kann?

Es vergleicht die Fingerabdrücke von Eingaben und Ausgaben mit dem letzten Lauf. Sind sie gleich, ist der Task UP-TO-DATE.

Wie wird der Cache-Schlüssel gebildet?

Aus den Eingaben des Tasks, zum Beispiel Typ, Eigenschaften und Werte. Der Task-Pfad gehört nicht dazu.

Was macht die Settings-Datei?

Sie definiert die Build-Struktur, also welche Projekte mit include dazugehören.

Was speichert der Configuration Cache?

Den Task-Graphen, den Zustand der Tasks und Ergebnisse der Dependency-Auflösung.

Zahlen

Wie lange lebt ein Daemon im Leerlauf?

Drei Stunden. Dann beendet er sich.

Seit welcher Version ist der Daemon standardmässig an?

Seit Gradle 3.0.

Ist der Build-Cache standardmässig an?

Nein. Er ist standardmässig aus.

Wann ist der Configuration Cache standardmässig an?

Laut Doku in Gradle 10. Seit Gradle 9.0 ist er der bevorzugte Modus.

Vergleich

Gradle vs Maven bei der Beschreibung?

Maven beschreibt deklarativ in pom.xml mit festem Lebenszyklus. Gradle nutzt Skripte in Kotlin oder Groovy und flexible Tasks.

Gradle vs Maven bei der Lesbarkeit?

Maven ist einheitlicher und einfacher zu lesen. Gradle ist freier und kann schwerer zu verstehen sein.

api vs implementation?

api gehört zur öffentlichen Schnittstelle und ist für Konsumenten beim Kompilieren sichtbar. implementation ist intern.

Build-Cache vs Configuration Cache?

Der Build-Cache spart Task-Ausführung. Der Configuration Cache spart die Configuration-Phase.

Produktion

Warum ist der Build lokal grün und auf dem CI-Server rot?

Oft unterschiedliche Gradle- oder Java-Version. Lösung: Wrapper nutzen und Java-Version im Build festlegen.

Warum dauert jeder Gradle-Start mehrere Sekunden, obwohl nichts passiert?

Die Configuration-Phase läuft. Lösung: Configuration Cache einschalten und schwere Arbeit aus der Configuration entfernen.

Szenario: Der CI-Build dauert 40 Minuten. Was prüfen Sie?

Build-Cache mit Remote-Cache einschalten, Tasks parallel laufen lassen und Build-Scan ansehen, welche Tasks nie UP-TO-DATE sind.

Szenario: Ein Task läuft immer, obwohl sich nichts geändert hat. Woran liegt es?

Meist hat der Task nicht deklarierte oder sich ändernde Eingaben, zum Beispiel einen Zeitstempel. Eingaben und Ausgaben sauber deklarieren.

Design

Wie strukturieren Sie einen Multi-Project-Build?

Ein Root-Projekt mit settings-Datei und include für Subprojekte. Gemeinsame Konfiguration in Plugins statt Kopien in jeder Build-Datei.

Szenario: Sie sollen ein Maven-Projekt auf Gradle umstellen. Wie gehen Sie vor?

Erst klären, ob es sich lohnt. Dann geht man schrittweise vor. Man übernimmt die Struktur, bildet Abhängigkeiten ab und vergleicht beide Builds parallel. Maven bleibt die Referenz, bis die Ergebnisse gleich sind.

Wann bleibt man bei Maven?

Wenn das Team Maven kennt, der Build einfach ist und die Standard-Konventionen reichen.

Wie hält man die Gradle-Version aktuell?

Mit dem Wrapper-Task: ./gradlew wrapper --gradle-version=.... Dann committet man die geänderten Wrapper-Dateien.

Mehr

Gerüst

  • Warum? Schnelle, inkrementelle Builds mit flexiblen Skripten.
  • Wie innen? Drei Phasen, Task-Graph, Fingerabdrücke, Daemon, Build-Cache, Configuration Cache.
  • Zahlen Daemon seit 3.0 und 3 Stunden Leerlauf, Build-Cache aus, Maven 3.10.2 aktuell, Maven 4 Preview.
  • Vergleich Gradle: Tasks und Skripte, flexibel. Maven: Lebenszyklus und POM, einheitlich.
  • Produktion Lokal grün, CI rot wegen Version. Lange Configuration. Task läuft immer.
  • Design Wrapper einchecken, implementation bevorzugen, Caches nutzen, Multi-Project sauber teilen.

Beispiel: Ein Java-Projekt mit Gradle (Kotlin DSL)

// settings.gradle.kts
rootProject.name = "shop"
include("api", "core")

// core/build.gradle.kts
plugins { `java-library` }
repositories { mavenCentral() }
dependencies {
    api("org.slf4j:slf4j-api:VERSION")           // Teil der öffentlichen API
    implementation("com.google.guava:guava:VERSION")  // intern
    testImplementation("org.junit.jupiter:junit-jupiter:VERSION")
}
tasks.test { useJUnitPlatform() }

Nicht ausgeführt (Gradle ist hier nicht installiert). VERSION ist ein Platzhalter.

  1. Die Settings-Datei nennt zwei Subprojekte, api und core.
  2. java-library bringt die Configuration api.
  3. api sehen Konsumenten beim Kompilieren. implementation sehen sie nicht.
  4. ./gradlew build baut alles. Beim zweiten Lauf ohne Änderung stehen Tasks als UP-TO-DATE.

Vergleich

  • Beschreibung: Maven deklarativ in XML. Gradle als Skript in Kotlin oder Groovy.
  • Ablauf: Maven mit festem Lebenszyklus und Phasen. Gradle mit Task-Graph aus Abhängigkeiten.
  • Inkrementell: Gradle hat Up-to-date-Prüfung, Build-Cache und Configuration Cache.
  • Erweiterung: Maven über Plugins mit festen Zielen. Gradle über Plugins und eigene Tasks im Skript.
  • Lernkurve: Maven ist einheitlich und leicht zu lesen. Gradle bietet mehr Freiheit und mehr Wege.
  • Wrapper: Gradle liefert ihn mit dem Task wrapper. Er lädt die gewünschte Gradle-Version.

Produktion

  1. Verschiedene Versionen auf CI und lokal: Kein Wrapper. Lösung: Wrapper einchecken und nutzen.
  2. Langsame Configuration: Schwere Arbeit im Skript. Lösung: Arbeit in Tasks verschieben, Configuration Cache einschalten.
  3. Tasks laufen immer: Eingaben sind nicht deklariert oder ändern sich. Lösung: Eingaben und Ausgaben deklarieren, keine Zeitstempel.
  4. Zu viel Neukompilierung: Zu viele api-Abhängigkeiten. Lösung: implementation bevorzugen.
  5. Viele Daemons fressen Speicher: Mehrere inkompatible Daemons laufen. Lösung: gradle --stop und gleiche Java-Version nutzen.
  6. Cache liefert Falsches: Ein Task hat nicht deklarierte Eingaben. Lösung: Eingaben prüfen, den Build-Scan ansehen.

Diagnose: Werkzeuge und Befehle

  • ./gradlew build --scan: erstellt einen Build-Scan mit Dauer pro Task.
  • ./gradlew build --info: zeigt, warum ein Task nicht up-to-date ist.
  • ./gradlew dependencies: zeigt den Abhängigkeitsbaum je Configuration.
  • gradle --status und gradle --stop: zeigen und beenden Daemons.
  • ./gradlew tasks: listet die verfügbaren Tasks.

Senior-Punkte

  1. Der Wrapper ist Pflicht. Er macht den Build reproduzierbar.
  2. Geschwindigkeit kommt aus Deklaration. Wer Eingaben und Ausgaben sauber angibt, gewinnt Cache und Up-to-date.
  3. Die Configuration-Phase ist heilig. Dort passiert nur Beschreibung, keine Arbeit.
  4. implementation ist der Standard, api nur für Typen der öffentlichen Schnittstelle.
  5. Ein Wechsel von Maven zu Gradle ist eine Teamentscheidung. Er lohnt bei grossen Builds und Bedarf an Flexibilität.
  6. Gleiche Konventionen im ganzen Repo schlagen cleveres Skripten. Das hält Builds lesbar.
