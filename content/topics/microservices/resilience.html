Resilience: Timeout, Retry, Circuit Breaker, Bulkhead

Kern: Resilience ist die Fähigkeit eines Service, Fehler seiner Abhängigkeiten auszuhalten. Sie verhindert, dass ein langsamer Service alle Aufrufer mitreisst (Cascading Failure, also eine Fehlerkette). Die Bausteine sind Timeout, Retry, Circuit Breaker, Bulkhead, Rate Limiter und Fallback. Der wichtigste ist der Timeout.

1. Wo sitzt Resilience im System?

  1. Resilience sitzt beim Aufrufer, nicht beim aufgerufenen Service. Der Aufrufer schützt sich selbst.
  2. Der Business-Code ruft den Client auf. Die Resilience-Schicht legt sich als Hülle (Decorator) darum.
  3. Resilience4j schachtelt die Muster in fester Reihenfolge: Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) ).
  4. Der Fallback liefert eine Ersatzantwort, wenn alles scheitert.
  5. Im Service Mesh (z. B. Istio) liegen Timeout und Retry alternativ im Sidecar-Proxy.

2. Die Reise eines Aufrufs (die Geschichte zum Merken)

  1. Timeout zuerst. Der Order Service ruft Payment mit einem Timeout von z. B. 2 s auf. Ohne Timeout wartet der Thread im schlimmsten Fall ewig.
  2. Fehler: Retry. Payment antwortet mit 503. Der Retry wartet kurz und versucht es erneut. Die Wartezeit wächst exponentiell, mit Zufall (Jitter).
  3. Viele Fehler: Circuit Breaker öffnet. Der Circuit Breaker misst die Fehlerrate in einem Sliding Window. Über 50 % wechselt er auf OPEN. Jetzt lehnt er Aufrufe sofort ab.
  4. Fallback antwortet. Statt eines Fehlers liefert der Fallback eine Ersatzantwort: „Zahlung wird später geprüft“.
  5. Bulkhead schützt den Rest. Der Bulkhead erlaubt nur z. B. 10 gleichzeitige Payment-Aufrufe. Die übrigen Threads bleiben frei für andere Endpunkte.
  6. Wartezeit vorbei: HALF_OPEN. Der Breaker lässt wenige Probe-Aufrufe durch. Gehen sie gut, schliesst er (CLOSED). Scheitern sie, öffnet er wieder.

3. Beispiel: Retry Storm und Circuit Breaker messen

a) Retry Storm vs Backoff mit Jitter. 1000 Clients rufen gleichzeitig einen Service auf. Er ist 5 Ticks lang down, danach schafft er 150 Aufrufe pro Tick.

def delay(strategy, attempt, rnd):
    if strategy == "sofort":   return 1                       # sofort wieder versuchen
    exp = min(CAP, BASE * 2 ** attempt)
    if strategy == "backoff":  return exp                     # 1,2,4,8 … ohne Zufall
    return 1 + rnd.randint(0, exp)                            # Full Jitter

# jeder Tick: fällige Clients rufen auf, max. CAPACITY gelingen,
# die anderen planen den nächsten Versuch mit delay(); max. 6 Versuche
1000 clients, dependency down for ticks 0-4, then 150 calls/tick, max 6 attempts
sofort           calls= 6000  retry_peak/tick= 1000  ok= 150  gave_up= 850  done_at_tick=5
backoff          calls= 5100  retry_peak/tick= 1000  ok= 600  gave_up= 400  done_at_tick=62
backoff+jitter   calls= 3683  retry_peak/tick=  472  ok=1000  gave_up=   0  done_at_tick=37

Echte Ausgabe, Python 3.12 (Simulation, Seed 42). 1 Tick ≈ 100 ms.

  1. Sofort: Alle 1000 Clients versuchen es jeden Tick wieder. Der Service bekommt 6-mal die normale Last. Nur 150 Aufrufe gelingen.
  2. Backoff ohne Jitter: Die Clients warten länger, aber alle gleich lang. Sie kommen als Welle von 1000 zurück. 400 geben auf.
  3. Backoff mit Jitter: Der Zufall verteilt die Versuche. Die Spitze sinkt auf 472. Alle 1000 Aufrufe gelingen, mit 39 % weniger Aufrufen.

b) Circuit Breaker als Zustandsmaschine (eigener Code, gleiche Logik wie Resilience4j): Fenster 10 Aufrufe, mindestens 5 Aufrufe, Schwelle 50 %, 3 s offen, 3 Probe-Aufrufe.

4. Details, die Interviewer fragen

  1. Timeout: Ein Timeout begrenzt die Wartezeit auf eine Antwort. Es gibt zwei Arten: Connect Timeout (Verbindung aufbauen) und Read Timeout (auf Daten warten). Ohne Timeout blockiert ein langsamer Service alle Threads des Aufrufers.
  2. Timeout-Budget: Der Timeout des Aufrufers muss grösser sein als die Summe der Versuche darunter. Sonst bricht der Aufrufer ab, während unten noch Retries laufen. Deadline Propagation gibt die Restzeit an den nächsten Service weiter.
  3. Retry nur bei transienten Fehlern: Ein transienter Fehler ist vorübergehend: 503, 429, Timeout, Verbindungsabbruch. Ein 400 oder 404 wird nie besser. Diese nicht wiederholen.
  4. Retry braucht Idempotenz: Eine Operation ist idempotent, wenn mehrfaches Ausführen das gleiche Ergebnis hat. Ein POST „Zahlung“ ist es nicht. Lösung: Idempotency Key im Header, den der Server speichert.
  5. Exponential Backoff: Die Wartezeit verdoppelt sich pro Versuch: 200, 400, 800 ms. Eine Obergrenze (Cap) verhindert zu lange Wartezeiten.
  6. Jitter: Jitter addiert Zufall zur Wartezeit. Ohne Jitter kommen alle Clients gleichzeitig zurück (Thundering Herd). Full Jitter wählt zufällig zwischen 0 und dem Backoff-Wert.
  7. Retry Storm: Ein Retry Storm entsteht, wenn jede Schicht wiederholt. 3 Schichten mit je 3 Versuchen ergeben bis zu 27 Aufrufe ganz unten. Darum nur an einer Stelle wiederholen, meist ganz aussen.
  8. Retry Budget: Ein Retry Budget begrenzt Retries auf einen Anteil der Requests, z. B. 10 %. So kann ein Client einen kranken Service nicht überfluten.
  9. Circuit Breaker Defaults (Resilience4j): failureRateThreshold 50 %, slidingWindowSize 100, minimumNumberOfCalls 100, waitDurationInOpenState 60 s, permittedNumberOfCallsInHalfOpenState 10.
  10. Sliding Window: COUNT_BASED zählt die letzten N Aufrufe. TIME_BASED zählt die Aufrufe der letzten N Sekunden. Bei wenig Traffic ist minimumNumberOfCalls wichtig, sonst öffnet ein einziger Fehler.
  11. Slow Calls: Der Circuit Breaker zählt auch langsame Aufrufe. Über slowCallRateThreshold öffnet er, obwohl kein Fehler kam.
  12. Weitere Zustände: Neben CLOSED, OPEN und HALF_OPEN gibt es DISABLED, FORCED_OPEN und METRICS_ONLY. Sie dienen dem Betrieb, z. B. für einen manuellen Not-Aus.
  13. Bulkhead: Ein Bulkhead trennt Ressourcen pro Abhängigkeit. Resilience4j hat zwei Arten: SemaphoreBulkhead (begrenzt gleichzeitige Aufrufe, Standard 25) und ThreadPoolBulkhead (eigener Thread-Pool mit Queue).
  14. Rate Limiter: Ein Rate Limiter begrenzt Aufrufe pro Zeitraum, z. B. 50 pro Sekunde. Er schützt einen Partner mit fester Quote. Der Bulkhead begrenzt dagegen die Gleichzeitigkeit.
  15. Time Limiter: Der TimeLimiter setzt einen Timeout auf asynchrone Aufrufe (CompletableFuture). Standard: 1 s. Für synchrone HTTP-Aufrufe setzt man den Timeout im HTTP-Client.
  16. Fallback: Ein Fallback liefert eine Ersatzantwort: Cache-Wert, Standardwert, leere Liste oder „später“. Er darf keinen Fehler verstecken, der den Nutzer falsch informiert.
  17. Aspect-Reihenfolge: Retry ist ganz aussen. Jeder Retry-Versuch geht also durch den Circuit Breaker. Ist der Breaker offen, scheitert auch der Retry sofort. Die Reihenfolge ist per *AspectOrder-Property änderbar.

5. Vergleich

  • Timeout: begrenzt die Wartezeit eines Aufrufs. Immer nötig, Basis für alles andere.
  • Retry: wiederholt einen gescheiterten Aufruf. Hilft bei kurzen Störungen, schadet bei Überlast.
  • Circuit Breaker: stoppt Aufrufe an einen kaputten Service. Hilft bei längeren Ausfällen.
  • Bulkhead: begrenzt gleichzeitige Aufrufe pro Abhängigkeit. Verhindert, dass eine Abhängigkeit alle Threads belegt.
  • Rate Limiter: begrenzt Aufrufe pro Zeit. Schützt den Aufgerufenen oder hält eine Quote ein.
  • Fallback: liefert Ersatz, wenn alles andere scheitert.
  • Resilience4j vs Hystrix: Hystrix (Netflix) ist seit 2018 im Wartungsmodus. Resilience4j ist leichtgewichtig, funktional und der Standard mit Spring Cloud Circuit Breaker.
  • Bibliothek vs Service Mesh: Ein Mesh (Istio, Linkerd) macht Timeout, Retry und Outlier Detection ohne Code. Die Bibliothek kennt dafür die Fachlogik, z. B. Fallback und Idempotenz.
  • Spring Framework 7 / Spring Boot 4: bringt eigene Annotationen @Retryable und @ConcurrencyLimit im Core. Einen Circuit Breaker bringt es nicht mit. Dafür bleibt Resilience4j.

6. In der Produktion

  1. Kein Timeout gesetzt: Ein Partner hängt, alle Threads im Pool warten. Der eigene Service fällt aus. Lösung: Connect- und Read-Timeout in jedem HTTP- und DB-Client setzen.
  2. Retry Storm nach kurzem Ausfall: Der Service kommt zurück und wird sofort wieder überrannt. Lösung: Backoff mit Jitter, Retry nur an einer Schicht, Retry Budget.
  3. Doppelte Buchung durch Retry: Der erste Versuch kam an, nur die Antwort ging verloren. Der Retry bucht doppelt. Lösung: Idempotency Key, Retry nur für idempotente Aufrufe.
  4. Breaker öffnet bei wenig Traffic: Nachts gibt es 2 Aufrufe, einer scheitert, 50 %. Lösung: minimumNumberOfCalls passend setzen, TIME_BASED-Fenster nutzen.
  5. Breaker öffnet bei 4xx: Fachliche Fehler (400, 404) zählen als Fehler. Lösung: ignoreExceptions oder recordExceptions konfigurieren.
  6. Retry-Zeit länger als Gateway-Timeout: Das Gateway bricht nach 5 s ab, unten laufen noch Retries. Lösung: Timeout-Budget von aussen nach innen planen.
  7. Annotation wirkt nicht: Der Aufruf kommt aus derselben Klasse (Self-Invocation). Der Spring-Proxy wird umgangen. Lösung: Aufruf über eine andere Bean.

7. Diagnose: Werkzeuge und Metriken

  • Actuator-Endpunkte: /actuator/circuitbreakers und /actuator/circuitbreakerevents zeigen Zustand und letzte Ereignisse.
  • Micrometer-Metriken: resilience4j_circuitbreaker_state, resilience4j_circuitbreaker_failure_rate, resilience4j_retry_calls (mit kind wie successful_with_retry), resilience4j_bulkhead_available_concurrent_calls.
  • Health Indicator: register-health-indicator: true zeigt den Breaker in /actuator/health. Vorsicht: nicht in die Liveness Probe aufnehmen.
  • Grafana-Alarm: Alarm auf „Breaker OPEN“ und auf steigende Retry-Rate.
  • Distributed Tracing: Ein Trace zeigt jeden Retry als eigenen Client-Span.
  • Thread Dump (jcmd <pid> Thread.print): viele Threads in SocketInputStream.read heisst fehlender Read-Timeout.

8. Senior-Punkte

  1. Timeouts zuerst. Ohne Timeout nützen Retry und Circuit Breaker wenig. Der Breaker sieht keinen Fehler, nur hängende Threads.
  2. Retry an genau einer Stelle. Jede zusätzliche Schicht multipliziert die Last. Meist wiederholt der äusserste Aufrufer oder das Mesh.
  3. Retry ist ein Vertrag mit dem Server. Er braucht Idempotenz und das Respektieren von Retry-After bei 429 und 503.
  4. Fallback ist eine fachliche Entscheidung. Ein veralteter Preis kann schlimmer sein als ein Fehler. Das klärt man mit dem Business.
  5. Werte aus Messungen ableiten. Timeout ≈ p99-Latenz plus Puffer. Bulkhead-Grösse ≈ Durchsatz × Latenz (Little's Law).
  6. Resilience testen. Mit Chaos-Tests (Toxiproxy, WireMock-Delays) prüft man, ob der Breaker wirklich öffnet.

10. Fallen

  • „Mehr Retries machen das System stabiler.“ → Falsch. Bei Überlast verstärken Retries die Last. Das ist ein Retry Storm.
  • „Exponential Backoff reicht.“ → Nicht ganz. Ohne Jitter kommen alle Clients gleichzeitig zurück.
  • „Ein POST darf man wiederholen.“ → Nur mit Idempotency Key. Sonst gibt es doppelte Buchungen.
  • „Der Circuit Breaker schützt meinen Service vor Last.“ → Falsch. Er schützt die Abhängigkeit und spart eigene Ressourcen. Gegen eingehende Last hilft ein Rate Limiter.
  • „HALF_OPEN kommt automatisch nach der Wartezeit.“ → Standard nein. Resilience4j wechselt beim nächsten Aufruf. Automatisch nur mit automaticTransitionFromOpenToHalfOpenEnabled.
  • „maxAttempts: 3 heisst 3 Retries.“ → Falsch. 3 Versuche inklusive des ersten, also 2 Retries.

11. Fragen

Was ist Resilience in Microservices?

Die Fähigkeit, Fehler von Abhängigkeiten auszuhalten. Ein Fehler soll sich nicht als Kette durch das System ausbreiten.

Was ist ein Cascading Failure?

Ein langsamer Service blockiert die Threads seiner Aufrufer. Diese werden selbst langsam und blockieren ihre Aufrufer. Am Ende fällt das ganze System aus.

Warum sind Timeouts das wichtigste Muster?

Ohne Timeout wartet ein Thread beliebig lange. Alle anderen Muster brauchen einen Fehler, und den liefert erst der Timeout.

Connect Timeout vs Read Timeout?

Connect Timeout begrenzt den Verbindungsaufbau. Read Timeout begrenzt das Warten auf Daten nach dem Aufbau. Beide setzen.

Welche Fehler darf man wiederholen?

Transiente Fehler: 503, 429, Timeouts, Verbindungsabbruch. Nicht 400, 401, 404 oder fachliche Fehler.

Was ist Exponential Backoff mit Jitter?

Die Wartezeit verdoppelt sich pro Versuch, mit Obergrenze. Jitter addiert Zufall. So verteilen sich die Retries über die Zeit.

Was ist ein Retry Storm?

Viele Clients oder Schichten wiederholen gleichzeitig. Der kranke Service bekommt ein Vielfaches der Last und erholt sich nicht.

Warum braucht Retry Idempotenz?

Der erste Versuch kann angekommen sein, nur die Antwort fehlt. Ohne Idempotenz führt der Retry die Aktion doppelt aus.

Was ist ein Idempotency Key?

Eine eindeutige ID pro Operation im Request-Header. Der Server speichert sie und führt dieselbe ID nur einmal aus.

Welche Zustände hat ein Circuit Breaker?

CLOSED (durchlassen und messen), OPEN (sofort ablehnen), HALF_OPEN (wenige Proben). Resilience4j hat zusätzlich DISABLED, FORCED_OPEN, METRICS_ONLY.

Wann öffnet der Circuit Breaker?

Wenn die Fehlerrate oder die Rate langsamer Aufrufe die Schwelle erreicht. Erst nach einer Mindestzahl Aufrufe im Sliding Window.

COUNT_BASED vs TIME_BASED Sliding Window?

COUNT_BASED bewertet die letzten N Aufrufe. TIME_BASED bewertet die Aufrufe der letzten N Sekunden. TIME_BASED passt besser bei schwankendem Traffic.

Was passiert in HALF_OPEN?

Eine feste Zahl Probe-Aufrufe geht durch, Standard 10. Ist ihre Fehlerrate unter der Schwelle, schliesst der Breaker, sonst öffnet er wieder.

Was ist ein Bulkhead?

Eine Trennwand für Ressourcen. Jede Abhängigkeit bekommt eine eigene Grenze für gleichzeitige Aufrufe oder einen eigenen Thread-Pool.

Semaphore- vs ThreadPool-Bulkhead?

Semaphore begrenzt gleichzeitige Aufrufe im Aufrufer-Thread. ThreadPool führt den Aufruf in einem eigenen Pool mit Queue aus, also asynchron.

Bulkhead vs Rate Limiter?

Bulkhead begrenzt gleichzeitige Aufrufe. Rate Limiter begrenzt Aufrufe pro Zeitraum.

Was ist ein guter Fallback?

Ein Cache-Wert, ein Standardwert oder eine ehrliche Meldung wie „später verfügbar“. Er darf den Nutzer nicht falsch informieren.

In welcher Reihenfolge wirken die Resilience4j-Annotationen?

Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) ). Retry ist aussen, jeder Versuch geht durch den Breaker.

Wie richten Sie Resilience4j in Spring Boot 3 ein?

resilience4j-spring-boot3 plus spring-boot-starter-aop. Annotationen wie @CircuitBreaker(name, fallbackMethod) und Konfiguration pro Instanz in application.yml.

Warum wirkt @CircuitBreaker manchmal nicht?

Bei Self-Invocation aus derselben Klasse umgeht der Aufruf den Spring-Proxy. Die Methode muss über eine andere Bean aufgerufen werden.

Wie wählen Sie den Timeout-Wert?

Aus der gemessenen Latenz, etwa p99 plus Puffer. Und passend zum Budget des Aufrufers darüber.

Library oder Service Mesh für Resilience?

Mesh für einheitliche Timeouts und Retries ohne Code. Library für fachliche Fallbacks, Idempotenz und feine Steuerung. Oft beides, aber Retry nur an einer Stelle.

Wie überwachen Sie Circuit Breaker?

Micrometer-Metriken wie resilience4j_circuitbreaker_state, Actuator-Endpunkte und einen Alarm bei OPEN.

Szenario: Ein Partner-Service ist langsam, und kurz danach ist Ihr Service down. Was ist passiert?

Fehlender Read-Timeout: Alle Threads warten auf den Partner. Lösung: Timeout, Bulkhead pro Partner, Circuit Breaker mit Fallback. Prüfen mit Thread Dump.

Szenario: Nach einem 30-Sekunden-Ausfall bleibt der Service minutenlang überlastet. Warum?

Retry Storm: Clients und mehrere Schichten wiederholen gleichzeitig. Lösung: Backoff mit Jitter, Retry nur aussen, Retry Budget, Circuit Breaker.

Szenario: Kunden werden nach einer Netzwerkstörung doppelt belastet. Was tun Sie?

Der Retry hat einen nicht idempotenten POST wiederholt. Lösung: Idempotency Key, den der Payment-Service speichert. Bis dahin Retry für diesen Aufruf abschalten.
