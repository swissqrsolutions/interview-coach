12-Factor App

Kern: Die 12-Factor App ist eine Methode für Anwendungen, die als Service laufen und leicht skalieren. Sie trennt Config vom Code, hält Prozesse stateless und schreibt Logs auf stdout. Ziel ist, dass man die App ohne Aufwand deployen, ersetzen und skalieren kann.

Antwort-Muster

Frage: Was ist eine 12-Factor App und welche Faktoren sind in der Praxis am wichtigsten?

  1. Mechanismus: Eine App, ein Codebase, Abhängigkeiten deklariert, Config in der Umgebung, Prozesse stateless und jederzeit ersetzbar.
  2. Zahl: Es sind zwölf Faktoren. Ein Release ist Build plus Config und bekommt eine eindeutige ID. Releases ändert man nie nachträglich.
  3. Trade-off: Stateless Prozesse skalieren einfach. Dafür muss Zustand in Backing Services liegen, und Sticky Sessions fallen weg.
  4. Produktion: Ich prüfe vor allem Config in Umgebungsvariablen, Stateless, schnellen Start mit sauberem Stopp bei SIGTERM und Logs auf stdout.

1. Von Code bis laufendem Prozess, in 6 Schritten

  1. Codebase (I): Es gibt ein Repository pro App. Production, Staging und der lokale Rechner sind Deploys desselben Codes.
  2. Build (II, V): Der Build holt die deklarierten Abhängigkeiten und kompiliert. Er nutzt keine Pakete, die zufällig auf dem Server liegen.
  3. Release (V, III): Ein Release ist der Build plus die Config des Deploys. Er hat eine eindeutige ID und wird nie verändert. Änderung heisst neuer Release.
  4. Run (VI, VII, IX): Die App startet als Prozess, öffnet selbst einen Port und hält keinen Zustand zwischen Anfragen. Sie startet schnell und stoppt sauber.
  5. Skalieren (VIII): Man startet mehr Prozesse, auch auf mehr Maschinen. Prozesse teilen nichts.
  6. Logs (XI): Jeder Prozess schreibt seinen Ereignisstrom ungepuffert auf stdout. Die Umgebung sammelt und leitet ihn weiter.

Backing Services (IV) wie Datenbank oder Queue hängen als Ressourcen an. Ihre Adresse steht in der Config. Admin-Aufgaben (XII) laufen als einmalige Prozesse mit demselben Release.

2. Aufbau

  1. I Codebase: Ein Repo pro App. Mehrere Repos sind ein verteiltes System, jede Komponente eine eigene App.
  2. II Dependencies: Alles Nötige steht in einem Manifest. Die App verlässt sich nicht auf Pakete des Systems.
  3. III Config: Alles, was zwischen Deploys wechselt, kommt aus Umgebungsvariablen.
  4. IV Backing services: Datenbank, Queue, Cache sind angehängte Ressourcen. Ihr Locator steht in der Config.
  5. V Build, Release, Run: Drei getrennte Stufen. Ein Release ist unveränderlich.
  6. VI bis XII: Stateless Processes, Port binding, Concurrency, Disposability, Dev/Prod Parity, Logs, Admin Processes.

3. Details

  1. Config und der Test: Die Quelle stellt eine Testfrage. Könnte man den Code jederzeit als Open Source freigeben, ohne Zugangsdaten zu verraten? Wenn ja, ist Config sauber getrennt.
  2. Umgebungsvariablen: Sie lassen sich pro Deploy ändern, ohne Code zu ändern. Man checkt sie kaum aus Versehen ein. Sie sind unabhängig von Sprache und Betriebssystem.
  3. Config-Gruppen skalieren schlecht: Benannte Umgebungen wie 'development' und 'production' führen zu einer Explosion von Kombinationen. Besser ist jede Variable einzeln pro Deploy.
  4. Backing Services: Die App behandelt Datenbank oder Mail-Dienst gleich, ob lokal oder von Dritten. Zum Tausch ändert sich nur der Handle in der Config.
  5. Build, Release, Run: Ein Release enthält Build und Config. Er hat eine eindeutige ID. Releases sind ein Append-only-Verzeichnis. Rollback heisst, einen früheren Release wieder zu starten.
  6. Stateless und Sticky Sessions: Prozesse sind stateless und teilen nichts. Sticky Sessions verletzen das Prinzip. Sitzungsdaten gehören in einen Store mit Ablaufzeit, zum Beispiel Redis.
  7. Lokaler Speicher: Speicher und Dateisystem eines Prozesses sind nur ein kurzer Cache für eine Anfrage. Der nächste Request kann bei einem anderen Prozess landen.
  8. Port Binding: Die App bringt ihren Webserver als Bibliothek mit und bindet einen Port. Sie wartet nicht auf einen Server, der von aussen injiziert wird.
  9. Concurrency: Verschiedene Arbeit läuft in verschiedenen Prozesstypen, zum Beispiel Web und Worker. Man skaliert durch mehr Prozesse, nicht durch eine grössere Maschine. Prozesse daemonisieren nicht.
  10. Disposability: Bei SIGTERM hört ein Web-Prozess auf, neue Verbindungen anzunehmen, beendet laufende Anfragen und endet. Ein Worker gibt seinen Job an die Queue zurück. Jobs müssen wiederholbar sein.
  11. Dev/Prod Parity: Drei Lücken sollen klein bleiben, nämlich Zeit, Personal und Werkzeuge. Man nutzt dieselbe Art und Version von Backing Services, nicht SQLite lokal und PostgreSQL in Produktion.
  12. Logs und Admin: Die App schreibt auf stdout und verwaltet keine Logdateien. Admin-Aufgaben wie Migrationen laufen als einmalige Prozesse im gleichen Release und mit der gleichen Config.

4. Fallen

  • „Die Config gehört in eine Datei im Repo, nach Umgebung benannt.“ → Falsch. Die Quelle bevorzugt Umgebungsvariablen pro Deploy. Benannte Gruppen skalieren nicht.
  • „Sticky Sessions sind eine gute Lösung für Sitzungen.“ → Falsch. Sie verletzen das Stateless-Prinzip. Sitzungen gehören in einen gemeinsamen Store.
  • „Die App verwaltet ihre Logdateien selbst.“ → Falsch. Sie schreibt auf stdout. Die Umgebung sammelt und leitet weiter.
  • „Ein Release kann man auf dem Server noch schnell ändern.“ → Falsch. Releases sind unveränderlich. Jede Änderung ist ein neuer Release mit neuer ID.
  • „SQLite lokal und PostgreSQL in Produktion ist unproblematisch.“ → Falsch. Kleine Unterschiede führen zu Fehlern erst in Produktion. Dieselbe Art und Version nutzen.
  • „Mehrere Repos pro App sind normal in 12-Factor.“ → Falsch. Mehrere Codebases bilden ein verteiltes System. Gemeinsamer Code wird eine Bibliothek.

5. Selbsttest

Warum?

Warum Config in Umgebungsvariablen?

Man ändert sie pro Deploy ohne Code-Änderung. Sie landen kaum aus Versehen im Repo und sind unabhängig von Sprache und System.

Warum sollen Prozesse stateless sein?

Dann kann jeder Prozess jede Anfrage bedienen. Man kann Prozesse frei starten, stoppen und vermehren.

Warum gibt es Dev/Prod Parity?

Je kleiner der Unterschied, desto öfter und sicherer kann man deployen. Fehler zeigen sich früh.

Wie innen?

Wie unterscheiden sich Build, Release und Run?

Build macht aus Code ein Bundle. Release kombiniert Build mit Config. Run startet die Prozesse eines Releases.

Wie geht ein Web-Prozess bei SIGTERM sauber unter?

Er nimmt keine neuen Verbindungen mehr an, beendet laufende Anfragen und endet dann.

Was macht ein Worker bei SIGTERM?

Er gibt den laufenden Job an die Queue zurück. Der Job muss darum wiederholbar sein.

Wie behandelt man Datenbank oder Queue?

Als angehängte Ressource. Adresse und Zugang stehen in der Config. Zum Tauschen ändert man nur die Config.

Wie funktioniert Skalierung hier?

Man startet mehr Prozesse nach Prozesstyp. Eine grössere Maschine reicht nicht, weil sie nur begrenzt wächst.

Zahlen

Wie viele Faktoren hat die 12-Factor App?

Zwölf. Sie sind von I bis XII nummeriert.

Wie viele Codebases hat eine App?

Genau eine, mit vielen Deploys.

Wie viele Lücken nennt Dev/Prod Parity?

Drei: Zeit, Personal und Werkzeuge.

Wie schnell soll ein Prozess starten?

In wenigen Sekunden. Eine genaue Zahl nennt die Quelle nicht.

Vergleich

Umgebungsvariablen vs Config-Datei im Repo?

Variablen ändern sich pro Deploy ohne Code. Dateien sind verstreut und liegen leichter versehentlich im Repo.

12-Factor vs Monolith?

12-Factor ist eine Betriebsmethode und gilt auch für Monolithen. Sie sagt nichts über die Grösse der App.

Stateless vs Sticky Sessions?

Stateless heisst jeder Prozess kann jede Anfrage bedienen. Sticky bindet einen Nutzer an einen Prozess und behindert Skalierung.

stdout vs Logdatei?

stdout lässt die Umgebung entscheiden, wohin Logs gehen. Eine Logdatei bindet die App an Dateisystem und Rotation.

Produktion

Warum verlieren Nutzer nach einem Deployment ihre Sitzung?

Die Sitzung lag im Speicher eines Prozesses. Lösung: Sitzung in einen gemeinsamen Store mit Ablaufzeit.

Warum brechen Requests beim Rolling Update ab?

Der Prozess beendet sich sofort bei SIGTERM. Lösung: Signal behandeln, laufende Anfragen beenden, dann stoppen.

Szenario: Ein Passwort liegt im Git-Verlauf. Was tun Sie?

Passwort sofort ändern und aus dem Verlauf entfernen. Danach alle Secrets über Umgebungsvariablen oder einen Secret-Store einlesen.

Szenario: Es funktioniert lokal, aber nicht in Produktion. Wie verringern Sie solche Fälle?

Dev/Prod Parity herstellen. Gleiche Datenbank-Art und -Version, gleiche Build-Schritte, häufige Deployments.

Design

Szenario: Sie sollen eine App containerfähig machen. Was ändern Sie zuerst?

Config aus dem Code lösen, Logs auf stdout schreiben, lokalen Zustand entfernen und SIGTERM sauber behandeln.

Wie hält man Start schnell und Stopp sauber?

Wenig Arbeit beim Start, Port selbst binden. Beim Stopp laufende Arbeit beenden und Jobs an die Queue zurückgeben.

Wo laufen Migrationen?

Als einmaliger Admin-Prozess mit dem gleichen Release und der gleichen Config wie die App.

Wie teilt man Code zwischen zwei Apps?

Als Bibliothek über einen Dependency Manager. Nicht durch ein gemeinsames Repo für beide Apps.

Mehr

Gerüst

  • Warum? Anwendungen bauen, die man leicht deployen, ersetzen und skalieren kann.
  • Wie innen? Ein Codebase, Release = Build plus Config, Prozesse stateless, Logs auf stdout, Config in der Umgebung.
  • Zahlen 12 Faktoren, 3 Lücken bei Dev/Prod Parity, eine Codebase pro App.
  • Vergleich Umgebungsvariablen statt Config-Dateien. Stateless statt Sticky Sessions. stdout statt Logdateien.
  • Produktion Sitzung geht beim Deployment verloren, Requests brechen bei SIGTERM, Secret im Verlauf.
  • Design Config entkoppeln, Zustand auslagern, SIGTERM behandeln, gleiche Backing Services in allen Umgebungen.

Beispiel: Config aus der Umgebung lesen

record Config(int port, String dbUrl, String logLevel) {
  static Config fromEnv(Map<String, String> env) {
    String db = env.get("DATABASE_URL");
    if (db == null) throw new IllegalStateException("DATABASE_URL fehlt");
    return new Config(Integer.parseInt(env.getOrDefault("PORT", "8080")), db,
                      env.getOrDefault("LOG_LEVEL", "INFO"));
  }
}
# ohne DATABASE_URL
Start abgebrochen: DATABASE_URL fehlt

# DATABASE_URL=postgres://db/shop PORT=9090
Start mit Config[port=9090, dbUrl=postgres://db/shop, logLevel=INFO]
event=started port=9090

Echte Ausgabe, Java 17.0.3. Die Werte kommen aus dem echten Prozess-Environment.

  1. Dieselbe Klasse läuft in jeder Umgebung. Nur die Variablen ändern sich.
  2. Fehlt ein Pflichtwert, bricht die App beim Start ab, statt später zu scheitern.
  3. Der Port hat einen Standardwert. Die Datenbank-Adresse hat keinen.
  4. Das Log-Ereignis geht auf stdout. Die Umgebung sammelt es.

Vergleich

  • 12-Factor: Betriebsmethode für Services. Gilt für Monolith und Microservice.
  • Klassisches Deployment: Config-Dateien auf dem Server, Logdateien lokal, Sitzung im Speicher.
  • Container und Orchestrator: passen gut zu 12-Factor, weil Prozesse ersetzbar und Config von aussen sind.
  • Umgebungsvariablen: einfach und überall. Bei vielen Werten oder Geheimnissen kommt ein Secret-Store dazu.
  • Config-Server: zentrale Verwaltung. Es ist ein Backing Service und kein Ersatz für saubere Trennung.
  • Sticky Sessions vs Session-Store: Sticky bindet an einen Prozess. Der Store gilt für alle Prozesse.

Produktion

  1. Zugangsdaten im Repo: Config liegt im Code. Lösung: Umgebungsvariablen oder Secret-Store, Schlüssel erneuern.
  2. Sitzung weg nach Deployment: Zustand im Prozess. Lösung: Sitzung in einen gemeinsamen Store.
  3. Abgebrochene Anfragen beim Update: SIGTERM wird nicht behandelt. Lösung: sauber beenden.
  4. Doppelte Jobs: Ein Worker stirbt mitten im Job. Lösung: Jobs wiederholbar machen (idempotent).
  5. Fehler nur in Produktion: Lokal andere Datenbank. Lösung: gleiche Art und Version überall.
  6. Logs gehen verloren: Die App schreibt in eine lokale Datei im Container. Lösung: auf stdout schreiben.

Diagnose: Werkzeuge und Befehle

  • Prozess-Environment prüfen: env auf Linux oder printenv. Zeigt, welche Variablen wirklich gesetzt sind.
  • Logs der Plattform: Sie zeigen die Ströme aller Prozesse an einem Ort.
  • Shutdown testen: Prozess mit SIGTERM beenden und prüfen, ob laufende Anfragen fertig werden.
  • Release-ID im Log: zeigt, welche Version einen Fehler erzeugt hat.
  • Vergleich der Umgebungen: Versionen von Datenbank und Laufzeit nebeneinanderlegen.

Senior-Punkte

  1. 12-Factor ist eine Checkliste, kein Dogma. Man bewertet jeden Faktor gegen die eigene Lage.
  2. Config und Stateless bringen am meisten. Sie machen Deployments und Skalierung einfach.
  3. Disposability entscheidet über Verfügbarkeit. Wer sauber stoppt, kann ohne Ausfall ausrollen.
  4. Unveränderliche Releases machen Rollback billig. Man startet den alten Release.
  5. Geheimnisse brauchen mehr als Umgebungsvariablen, sobald viele Teams oder strenge Regeln gelten.
  6. Parity ist die Versicherung gegen 'läuft nur bei mir'. Sie kostet etwas Aufwand im Entwicklungs-Setup.
