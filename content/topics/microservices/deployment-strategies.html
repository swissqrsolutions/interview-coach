Deployment: Rolling, Blue-Green, Canary, Feature Flags

Kern: Eine Deployment-Strategie legt fest, wie eine neue Version die alte ersetzt, ohne Ausfall und mit schnellem Rückweg. Die vier Grundformen sind Rolling Update, Blue-Green, Canary und Feature Flags. Deployment (Code ausrollen) und Release (Funktion für Nutzer einschalten) sind zwei verschiedene Schritte.

Antwort-Muster

Frage: Wie rollt man eine neue Version ohne Ausfall aus?

  1. Mechanismus: Ein Rolling Update ersetzt Pods schrittweise, solange die Readiness Probe grün ist, und ein Canary schickt erst wenig Traffic zur neuen Version.
  2. Zahl: Bei 10 Replicas und 25 % ergibt das maxSurge 3 und maxUnavailable 2. Im Test scheitern beim Rolling 3250 Requests, beim Canary mit Analyse nur 200.
  3. Trade-off: Rolling ist einfach, aber ein fachlicher Bug erreicht alle Nutzer. Canary begrenzt den Schaden, braucht aber Metriken und Traffic-Splitting.
  4. Produktion: Ich nutze Graceful Shutdown, Expand-Contract für die DB und Feature Flags mit Ablaufdatum.

1. Die Reise eines Releases

  1. Expand. Die DB bekommt die neue Spalte, die alte bleibt. Alte und neue Version funktionieren mit diesem Schema. Das ist der erste Teil von Expand-Contract.
  2. Deploy. v2 geht ins Cluster, die neue Funktion ist hinter einem Feature Flag aus. Nutzer merken nichts. Das ist ein Dark Launch.
  3. Canary. 10 % des Traffics gehen auf v2. Eine Analyse vergleicht Fehlerrate und Latenz. Ist sie rot, bricht der Rollout ab.
  4. Weiter. Bei grün steigt der Anteil auf 50 %, dann 100 %. v1 wird abgebaut.
  5. Release. Das Team schaltet das Flag an, zuerst für interne Nutzer, dann für alle. Bei Fehlern schaltet es in Sekunden zurück.
  6. Contract. Läuft keine alte Version mehr, entfernt eine spätere Migration die alte Spalte. Danach wird auch das Flag gelöscht.

2. Aufbau

  1. Die gewünschte Version steht in Git. Argo CD gleicht das Cluster mit Git ab (GitOps).
  2. Ein Kubernetes-Deployment verwaltet ReplicaSets. Pro Version gibt es ein ReplicaSet.
  3. Die Strategie im Controller bestimmt, wie schnell v2 wächst und v1 schrumpft.
  4. Der Service, ein Ingress oder ein Service Mesh verteilt den Traffic auf die Pods.
  5. Ein Feature Flag schaltet Code zur Laufzeit an oder aus, ohne neues Deployment.
  6. Metriken entscheiden bei Canary, ob es weitergeht oder abbricht.

3. Details, die Interviewer fragen

  1. Recreate: Es stoppt alle alten Pods und startet dann die neuen. Es gibt eine Ausfallzeit. Es ist nützlich, wenn zwei Versionen nie gleichzeitig laufen dürfen.
  2. RollingUpdate: Das ist der Standard in Kubernetes. Pods werden schrittweise ersetzt. Alte und neue Version laufen kurz gleichzeitig.
  3. maxSurge: So viele Pods darf es über der Soll-Anzahl geben. Der Standard ist 25 %. Prozentwerte rundet Kubernetes auf. Mehr Surge heisst schneller, aber mehr Ressourcen.
  4. maxUnavailable: So viele Pods dürfen unter der Soll-Anzahl fehlen. Der Standard ist 25 %. Prozentwerte rundet Kubernetes ab. Beide Werte gleichzeitig auf 0 sind nicht erlaubt.
  5. Readiness Probe: Sie sagt, ob ein Pod Traffic bekommen darf. Der Rollout wartet auf sie. Ohne sie bekommt ein startender Pod sofort Traffic.
  6. Liveness Probe: Sie startet einen hängenden Pod neu. Sie darf keine Abhängigkeiten prüfen. Sonst startet ein DB-Ausfall alle Pods neu.
  7. Graceful Shutdown: Kubernetes sendet SIGTERM und wartet terminationGracePeriodSeconds (Standard 30 s). Der Pod muss laufende Requests beenden. In Spring Boot hilft server.shutdown=graceful. Ein kurzer preStop-Sleep gibt dem Endpoint-Update Zeit.
  8. Rollback in Kubernetes: kubectl rollout undo deployment/order geht auf das vorherige ReplicaSet zurück. Mit GitOps wird das beim nächsten Sync überschrieben. Dort ist der Rollback ein git revert.
  9. Blue-Green: Es gibt zwei vollständige Umgebungen, Blue (live) und Green (neu). Man testet Green, dann schaltet der Router um. Rollback heisst zurückschalten. Der Preis sind doppelte Ressourcen während des Wechsels.
  10. Blue-Green in Argo Rollouts: activeService zeigt auf die Live-Version, previewService auf die neue. Mit autoPromotionEnabled: false wartet der Wechsel auf eine manuelle Freigabe.
  11. Canary: Ein kleiner Teil des Traffics geht auf die neue Version. Metriken entscheiden über den nächsten Schritt. Ohne Traffic-Router teilt Argo Rollouts über die Anzahl Pods, also nur grob.
  12. Analysis: Ein AnalysisTemplate fragt z. B. Prometheus ab, etwa ob die Fehlerrate unter 1 % liegt. Scheitert die Analyse, setzt Argo Rollouts den Traffic auf die stabile Version zurück (Abort).
  13. Feature Flag Typen (Fowler): Der Release Toggle versteckt unfertigen Code und ist kurzlebig. Der Experiment Toggle steuert A/B-Tests. Der Ops Toggle ist ein Not-Aus für teure Funktionen. Der Permissioning Toggle schaltet eine Funktion für bestimmte Nutzer frei.
  14. Dark Launch: Neuer Code läuft in Produktion, aber Nutzer sehen das Ergebnis nicht. Oft nutzt man gespiegelten Traffic (Shadow Traffic), um Last und Fehler zu messen.
  15. Expand-Contract: Man nennt es auch Parallel Change. Erst erweitert man das Schema (neue Spalte, beide schreiben). Dann migriert man. Dann entfernt man die alten Teile. So passt das Schema immer zu zwei Versionen.
  16. DB-Migration im Rollout: Flyway oder Liquibase laufen beim Start oder als eigener Job vor dem Deployment. Eine Migration darf die laufende alte Version nicht brechen.

4. Fallen

  • „Kubernetes rollt bei Fehlern automatisch zurück.“ → Falsch. Es markiert den Rollout nur als gescheitert. Rollback macht die Pipeline, Argo Rollouts oder ein Mensch.
  • „Blue-Green löst das DB-Problem.“ → Falsch. Beide Umgebungen teilen meist die DB. Das Schema muss beide Versionen tragen.
  • „Rolling Update hat keine gemischten Versionen.“ → Falsch. Während des Rollouts laufen v1 und v2 gleichzeitig.
  • „Canary heisst 10 % der Pods.“ → Nur ohne Traffic-Router. Mit Ingress oder Mesh ist der Traffic-Anteil unabhängig von der Pod-Zahl.
  • „Ein Feature Flag ist ein if, das man stehen lässt.“ → Falsch. Alte Flags machen Code unlesbar und gefährlich. Sie brauchen ein Ablaufdatum.
  • „kubectl rollout undo reicht mit Argo CD.“ → Falsch. Self-Heal setzt den Stand aus Git wieder durch.

5. Selbsttest

Warum?

Was ist der Unterschied zwischen Deployment und Release?

Deployment bringt Code in die Produktion. Release macht eine Funktion für Nutzer sichtbar. Feature Flags trennen beides.

Warum darf eine Migration keine Spalte direkt umbenennen?

Die alte Version läuft während des Rollouts noch und sucht die alte Spalte. Und ein Rollback wäre unmöglich.

Warum braucht Canary genug Traffic?

Bei wenigen Requests ist die Fehlerrate Zufall. Die Analyse braucht eine Mindestzahl Requests für eine sichere Entscheidung.

Wie innen?

Welche Strategien kennt ein Kubernetes Deployment?

RollingUpdate (Standard) und Recreate. Canary und Blue-Green braucht man mit Argo Rollouts, Flagger oder eigenen Services.

Welche Rolle spielt die Readiness Probe beim Rollout?

Erst wenn sie grün ist, bekommt der Pod Traffic und zählt als verfügbar. Dann baut der Rollout den nächsten alten Pod ab.

Was ist Blue-Green Deployment?

Zwei komplette Umgebungen. Die neue wird getestet, dann schaltet der Router um. Rollback heisst zurückschalten.

Was ist ein Canary Release?

Ein kleiner Traffic-Anteil geht auf die neue Version. Metriken entscheiden schrittweise über mehr Traffic oder Abbruch.

Wie entscheidet Argo Rollouts über einen Canary?

Über ein AnalysisTemplate, das z. B. Prometheus abfragt. Scheitert es, macht Argo Rollouts einen Abort und schickt allen Traffic auf stable.

Was ist ein Feature Flag?

Ein Schalter im Code, der eine Funktion zur Laufzeit an- oder ausschaltet. Ohne neues Deployment.

Welche Arten von Feature Toggles gibt es?

Release, Experiment, Ops und Permissioning Toggles. Sie unterscheiden sich in Lebensdauer und Dynamik.

Was ist ein Dark Launch?

Neuer Code läuft in Produktion, aber Nutzer sehen nichts. Man misst Last und Fehler vor dem Release.

Was gehört zu einem Graceful Shutdown?

SIGTERM abfangen, keine neuen Requests annehmen, laufende beenden. Spring Boot: server.shutdown=graceful. Dazu ein kurzer preStop-Sleep.

Zahlen

Was bedeuten maxSurge und maxUnavailable?

maxSurge: Pods über der Soll-Anzahl. maxUnavailable: Pods, die unter der Soll-Anzahl fehlen dürfen. Beide Standard 25 %.

Wie rundet Kubernetes die Prozentwerte?

maxSurge rundet auf, maxUnavailable rundet ab. Bei 10 Replicas: 3 und 2.

Was passiert bei progressDeadlineSeconds?

Nach 600 s ohne Fortschritt setzt Kubernetes die Condition ProgressDeadlineExceeded. Ein automatisches Rollback gibt es nicht.

Vergleich

Blue-Green vs Canary?

Blue-Green schaltet alles auf einmal um und braucht doppelte Ressourcen. Canary erhöht schrittweise und begrenzt den Schaden.

Wann wählen Sie Recreate?

Wenn zwei Versionen nie gleichzeitig laufen dürfen, z. B. bei einem exklusiven Lock oder inkompatiblem Format. Ausfallzeit muss akzeptabel sein.

Produktion

Szenario: Bei jedem Deployment gibt es für ein paar Sekunden 502-Fehler. Was prüfen Sie?

Readiness Probe, Graceful Shutdown, preStop-Sleep, maxUnavailable. Oft bekommt ein Pod nach SIGTERM noch Traffic, weil das Endpoint-Update später ankommt.

Szenario: Eine neue Version hat einen fachlichen Bug, aber alle Probes sind grün. Wie verhindern Sie das nächste Mal grossen Schaden?

Canary mit automatischer Analyse auf Fehlerrate und Latenz. Neue Funktion hinter einem Feature Flag. So begrenzt man den Schaden auf wenige Prozent.

Szenario: Sie müssen ein grosses Altsystem ablösen, ohne Big Bang. Wie gehen Sie vor?

Neue Lösung parallel betreiben, per Feature Switch umschalten. Ergebnisse automatisch vergleichen. Rollback ist Schalter zurück oder git revert.

Design

Wie erreichen Sie ein Rolling Update ohne Kapazitätsverlust?

maxUnavailable: 0 und maxSurge mindestens 1. Dazu Readiness Probe und Graceful Shutdown.

Wie machen Sie ein Rollback in Kubernetes?

kubectl rollout undo, optional --to-revision. Mit GitOps stattdessen git revert und Sync.

Was ist Expand-Contract?

Erst das Schema erweitern, dann Code und Daten migrieren, dann Altes entfernen. So passen alte und neue Version jederzeit zur DB.

Wie macht man Rollback mit Argo CD?

git revert des Commits, Argo CD synchronisiert den alten Stand. Manuelle Änderungen überschreibt Self-Heal.

Mehr

Gerüst

  • Warum? Ohne Ausfall releasen und Fehler schnell zurücknehmen. Deployment und Release sind getrennte Schritte.
  • Wie innen? Das Deployment verwaltet ReplicaSets, die Readiness Probe steuert den Rollout. Argo Rollouts: Canary mit Analyse, Blue-Green mit activeService und previewService.
  • Zahlen maxSurge und maxUnavailable je 25 %, bei 10 Replicas 3 und 2. progressDeadlineSeconds 600. Rolling mit Bug: 3250 Fehler, Canary: 200.
  • Vergleich Rolling: gemischte Versionen. Blue-Green: doppelte Ressourcen, sofortiger Rollback. Canary: kleinster Schaden. Feature Flags: Rollback in Sekunden.
  • Produktion 502 beim Rollout, hängender Rollout ohne Auto-Rollback, Rollback bricht die DB, Flag-Friedhof.
  • Design Expand-Contract für die DB. Rollback per git revert. Canary nur mit automatischer Analyse.

Beispiel: Rolling Update vs Canary bei einem Bug

v2 hat einen fachlichen Bug: 20 % ihrer Requests scheitern. Die Readiness Probe bleibt grün. 10 Replicas, 10 000 Requests pro Runde.

surge   = ceil(REPLICAS * 25 / 100)    # maxSurge rundet auf   -> 3
unavail = floor(REPLICAS * 25 / 100)   # maxUnavailable rundet ab -> 2
# Rolling: pro Runde alte Pods stoppen bis min. 8 ready, neue bis max. 13 Pods starten
# Canary: setWeight 10/25/50/100, Analyse: Fehlerrate der Canary-Pods < 5 %, sonst Abort
Rolling update: replicas=10 maxSurge=3 maxUnavailable=2 (max 13 pods, min 8 ready)
  round 1: v1 ready= 8 v2 ready= 0 v2 starting=5  traffic v2=  0%  failed=   0
  round 2: v1 ready= 3 v2 ready= 5 v2 starting=5  traffic v2= 62%  failed=1250
  round 3: v1 ready= 0 v2 ready=10 v2 starting=0  traffic v2=100%  failed=2000
  -> rollout complete, nobody stopped it. failed requests so far: 3250
  -> alert fires, 'kubectl rollout undo' needs similar rounds again.

Canary (Argo-Rollouts style): steps=[10, 25, 50, 100]%, analysis: canary error rate < 5%
  setWeight  10%: failed= 200  canary error rate=20%  analysis=FAIL -> abort, 100% back to v1
  -> failed requests in total: 200

Echte Ausgabe, Python 3.12 (vereinfachte Simulation, kein Kubernetes). Der echte Controller arbeitet ereignisgesteuert, nicht in Runden.

  1. Rundung: 25 % von 10 sind 2,5. maxSurge rundet auf 3, maxUnavailable ab auf 2. Also maximal 13 Pods, mindestens 8 bereit.
  2. Rolling: Kubernetes sieht nur die Readiness. Der fachliche Bug ist unsichtbar. Der Rollout läuft bis 100 %. 3250 Requests scheitern, bevor jemand reagiert.
  3. Canary: Die Analyse misst die Fehlerrate der neuen Pods. Schon bei 10 % ist sie 20 %. Der Rollout bricht automatisch ab: 200 Fehler statt 3250.
  4. Lehre: Canary hilft nur mit einer automatischen Analyse über echte Metriken.

Konfiguration (Manifeste, keine Laufzeit-Ausgabe):

# Kubernetes Deployment: Rolling Update
spec:
  replicas: 10
  minReadySeconds: 10          # Pod muss 10 s ready sein, bevor er zählt
  progressDeadlineSeconds: 600 # Standard: nach 10 min ohne Fortschritt "failed"
  revisionHistoryLimit: 10     # alte ReplicaSets für Rollback
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%            # Standard
      maxUnavailable: 0        # nie unter 10 bereite Pods
# Argo Rollouts: Canary mit Analyse
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      canaryService: order-canary
      stableService: order-stable
      trafficRouting:
        nginx: { stableIngress: order }
      analysis:
        templates: [ { templateName: error-rate } ]
        startingStep: 1
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100

Vergleich

  • Recreate: einfach, Ausfallzeit, keine gemischten Versionen.
  • Rolling Update: kein Ausfall, kaum Zusatzressourcen. Aber gemischte Versionen und langsamer Rollback. Fehler erreichen schnell alle Nutzer.
  • Blue-Green: sofortiges Umschalten und sofortiger Rollback. Doppelte Ressourcen. Die DB ist meist geteilt, also trotzdem Expand-Contract.
  • Canary: kleinster Schaden bei Fehlern, Entscheidung über Metriken. Braucht Traffic-Splitting, gute Metriken und genug Traffic für Statistik.
  • Feature Flags: trennen Release vom Deployment. Rollback in Sekunden. Preis: Code-Komplexität und technische Schuld durch alte Flags.
  • A/B-Test vs Canary: Canary prüft technische Gesundheit einer Version. Ein A/B-Test misst fachliches Verhalten von Nutzergruppen.
  • Kubernetes Deployment vs Argo Rollouts: Das Deployment kann nur Rolling und Recreate. Argo Rollouts (oder Flagger) bringt Canary, Blue-Green und Analyse.

In der Produktion

  1. Fehler 502 bei jedem Rollout: Pods bekommen Traffic vor dem Start oder nach SIGTERM. Lösung: Readiness Probe, Graceful Shutdown, preStop-Sleep, maxUnavailable: 0.
  2. Rollout hängt: Neue Pods werden nie ready. Nach progressDeadlineSeconds meldet Kubernetes ProgressDeadlineExceeded. Es macht aber kein automatisches Rollback. Lösung: Pipeline prüft kubectl rollout status und reagiert.
  3. Rollback bricht die DB: v2 hat eine Spalte gelöscht, v1 braucht sie. Lösung: Expand-Contract, destruktive Migrationen erst Releases später.
  4. Gemischte Versionen streiten: v1 und v2 lesen dieselben Events oder Caches in verschiedenen Formaten. Lösung: abwärtskompatible Formate, Tolerant Reader.
  5. Canary sieht nichts: Zu wenig Traffic, die Statistik ist zufällig. Lösung: längere Pausen, Mindestanzahl Requests in der Analyse.
  6. Flag-Friedhof: Hunderte alte Flags, niemand kennt ihre Wirkung. Lösung: Ablaufdatum und Owner pro Flag, Löschen als Teil der Definition of Done.
  7. Manueller Rollback mit GitOps verpufft: kubectl rollout undo wird von Argo CD mit Self-Heal wieder überschrieben. Lösung: Rollback über git revert.

Diagnose: Werkzeuge und Befehle

  • kubectl rollout status deployment/order: wartet und zeigt den Fortschritt.
  • kubectl rollout history deployment/order: alle Revisionen. --revision=3 zeigt Details.
  • kubectl rollout undo deployment/order --to-revision=3: Rollback auf eine bestimmte Revision.
  • kubectl rollout pause|resume deployment/order: Rollout anhalten, z. B. für einen manuellen Check.
  • kubectl get rs -l app=order und kubectl describe deployment order: ReplicaSets und Events.
  • kubectl argo rollouts get rollout order --watch: Schritte, Gewicht und Analyse-Ergebnis. abort und promote steuern manuell.
  • argocd app history order und argocd app diff order: was Argo CD synchronisiert hat.
  • Metriken pro Version: Fehlerrate und Latenz mit Label version oder rollouts-pod-template-hash in Grafana.

Senior-Punkte

  1. Deployment und Release trennen. Code geht oft und klein raus. Die Funktion schaltet das Business per Flag frei.
  2. Rollback planen, nicht hoffen. Jede Änderung braucht einen Weg zurück. Die DB ist der schwierigste Teil, darum Expand-Contract.
  3. Canary ohne Analyse ist nur langsames Rolling. Wert entsteht erst durch automatische Entscheidungen über SLO-Metriken.
  4. Strategie nach Risiko wählen. Interner Batch-Job: Rolling reicht. Zahlungsweg: Canary mit Analyse. Grosse Migration: Parallelbetrieb mit Feature Switch.
  5. GitOps ist die Quelle der Wahrheit. Rollback ist ein Commit. Manuelle Cluster-Änderungen gehen verloren oder verursachen Drift.
  6. Flags sind Schulden. Release Toggles leben Tage bis Wochen, dann werden sie gelöscht.
