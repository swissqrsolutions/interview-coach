Monolith vs Modulith vs Microservices

Kern: Ein Monolith ist eine Anwendung, die als eine Einheit gebaut und deployt wird. Ein Modulith (modularer Monolith) ist ein Monolith mit harten Modulgrenzen im Code. Microservices sind unabhängig deploybare Services, jeder mit eigenen Daten und eigenem Team. Microservices lösen ein Organisationsproblem: viele Teams sollen unabhängig liefern. Sie kosten dafür Netzwerk, verteilte Daten und Betrieb.

1. Wo sitzen Monolith, Modulith und Microservices?

  1. Monolith: Alle Funktionen liegen in einem Artefakt, z. B. einem Spring-Boot-JAR. Ein Aufruf ist ein Methodenaufruf, eine Änderung ist eine lokale Transaktion.
  2. Modulith: Derselbe eine Prozess, aber in Module nach Fachlichkeit geteilt. Ein Modul nutzt ein anderes nur über dessen API oder über Events.
  3. Microservices: Jedes Modul ist ein eigener Prozess mit eigener Datenbank. Aufrufe gehen über das Netzwerk.
  4. Die Achse ist kein Reifegrad. Sie ist ein Tausch: Team-Autonomie gegen Betriebskosten.

2. Die Reise eines Systems (die Geschichte zum Merken)

  1. Start als Monolith. Ein Team baut ein neues Produkt. Die Fachlichkeit ändert sich jede Woche. Ein Monolith ist hier am schnellsten (Fowler: MonolithFirst).
  2. Grenzen ziehen: Modulith. Das System wächst. Das Team teilt den Code in Module nach Bounded Context. Spring Modulith prüft die Grenzen im Test. Module sprechen über Events.
  3. Ein Modul wird Service. Ein zweites Team übernimmt „Payment“. Payment braucht eigene Releases oder eigene Skalierung. Das Team zieht das Modul heraus. Der alte Code leitet dorthin weiter: Strangler Fig, also schrittweises Ersetzen.
  4. Microservices nur, wo es sich lohnt. Andere Module bleiben im Modulith. Viele Firmen enden bei einer Mischung.
  5. Der Rückweg. War der Schnitt falsch, müssen Services immer zusammen deployen. Das ist ein verteilter Monolith. Zusammenlegen kostet viel. Darum testet man Grenzen zuerst im Modulith.

3. Beispiel: was ein Prozess-Grenzübertritt kostet

static int price(int id) { return id * 3 + 7; }          // Modul im selben Prozess

// derselbe Aufruf als eigener "Service" über HTTP auf localhost
HttpServer s = HttpServer.create(new InetSocketAddress("127.0.0.1", 8081), 0);
s.createContext("/price", ex -> { ... price(id) ... });
HttpClient c = HttpClient.newHttpClient();

for (int i = 0; i < n; i++) sum += price(i);                          // Modulith
for (int i = 0; i < n; i++) sum += Integer.parseInt(call(c, i));      // Service

// Verfügbarkeit einer synchronen Kette: jeder Service 99.9 %
for (int k : new int[]{1, 3, 5, 10, 20}) Math.pow(0.999, k);

Echte Ausgabe, Java 17 (Simulation: com.sun.net.httpserver und java.net.http.HttpClient auf einem Windows-Laptop, ohne TLS und ohne echtes Netz). Teil 2 ist reine Rechnung.

  1. Ein Methodenaufruf kostet Nanosekunden. Der JIT kann ihn sogar inlinen.
  2. Derselbe Aufruf über HTTP kostet hier rund 0,6 ms, also etwa 10 000-mal mehr. Im echten Netz mit TLS kommt noch mehr dazu.
  3. Hängen Services synchron hintereinander, multiplizieren sich ihre Verfügbarkeiten. 10 Services mit je 99,9 % ergeben nur 99,0 %.
  4. Darum schneidet man Services so, dass ein Use Case wenige Remote-Aufrufe braucht.

Die Modulith-Grenzen als Test (Spring Modulith):

// com.example.shop            ← Hauptpaket mit @SpringBootApplication
// com.example.shop.order      ← Modul "order", API = dieses Paket
// com.example.shop.order.internal  ← intern, für andere Module verboten
// com.example.shop.payment    ← Modul "payment"

class ModularityTests {
  @Test
  void verifiesModularStructure() {
    ApplicationModules.of(ShopApplication.class).verify();
  }
}

@Service
class PaymentListener {
  @ApplicationModuleListener               // async, eigene Transaktion, nach Commit
  void on(OrderPlaced event) { ... }       // Payment kennt Order nur über das Event
}

Code nach der Spring-Modulith-Referenz, hier nicht ausgeführt.

  1. Jedes direkte Unterpaket des Hauptpakets ist ein Application Module.
  2. Das Basispaket eines Moduls ist seine API. Unterpakete wie internal sind intern.
  3. verify() lässt den Test fehlschlagen bei: Zyklen zwischen Modulen, Zugriff auf interne Pakete und Abhängigkeiten ausserhalb von allowedDependencies.
  4. @ApplicationModuleListener verarbeitet das Event asynchron in einer neuen Transaktion nach dem Commit. So entkoppeln sich Module wie später echte Services.

4. Details, die Interviewer fragen

  1. Microservice: Ein Microservice ist ein Service, der unabhängig deploybar ist und einem Team gehört. Er besitzt seine Daten und ist um eine Business Capability gebaut. Die Grösse in Codezeilen ist kein Kriterium.
  2. Conway's Law: Conway's Law sagt: Ein System spiegelt die Kommunikationsstruktur der Organisation. Drei Teams an einem Monolithen bauen faktisch drei Teile mit unklaren Grenzen.
  3. Inverse Conway Maneuver: Das Inverse Conway Maneuver formt zuerst die Teams nach der Wunsch-Architektur. Die Architektur folgt dann den Teams.
  4. Team Topologies: Team Topologies nennt vier Teamtypen. Stream-aligned liefert einen Fachstrom. Platform liefert Self-Service-Infrastruktur. Enabling hilft anderen Teams. Complicated-subsystem kapselt Spezialwissen.
  5. Microservice Premium: Fowler nennt die Mehrkosten von Microservices den Microservice Premium. Er lohnt sich erst ab einer gewissen Komplexität des Systems.
  6. Voraussetzungen: Fowler nennt drei Mindestvoraussetzungen. Rapid Provisioning: neue Server in Stunden. Basic Monitoring: Fehler schnell sehen. Rapid Application Deployment: automatisierte Pipeline pro Service.
  7. Unabhängige Deploybarkeit: Das ist der Test. Kann Team A ohne Absprache mit Team B releasen? Wenn nicht, ist es ein verteilter Monolith.
  8. Database per Service: Jeder Service besitzt seine Tabellen. Andere Services greifen nur über seine API oder Events zu. Ohne das gibt es keine Unabhängigkeit.
  9. Verteilter Monolith: Ein verteilter Monolith hat die Kosten von Microservices und die Kopplung eines Monolithen. Zeichen: gemeinsame DB, gemeinsame Releases, lange synchrone Ketten.
  10. Modulith-Regeln in Spring Modulith: Module sind Unterpakete. Interne Typen liegen in Unterpaketen des Moduls. Zusätzliche APIs öffnet man mit @NamedInterface. Erlaubte Abhängigkeiten setzt man mit @ApplicationModule(allowedDependencies = …).
  11. Event Publication Registry: Spring Modulith speichert veröffentlichte Events in der Datenbank. Ein Listener, der scheitert, lässt das Event als unvollständig stehen. Es kann später erneut zugestellt werden.
  12. Event Externalization: Ein Event mit @Externalized geht zusätzlich an einen Broker wie Kafka. So wird aus einem Modul-Event ein Service-Event.
  13. Modul-Tests: @ApplicationModuleTest startet nur ein Modul (und optional seine Abhängigkeiten). Tests bleiben schnell und zeigen versteckte Kopplung.
  14. Skalierung: Ein Monolith skaliert gut horizontal: mehrere gleiche Instanzen hinter einem Load Balancer. Microservices skalieren nur einzelne Teile. Das lohnt sich nur bei sehr ungleicher Last.
  15. Strangler Fig: Strangler Fig ersetzt ein Altsystem Stück für Stück. Ein Proxy oder Gateway leitet einzelne Pfade schon zum neuen Service. Es gibt keinen Big-Bang-Wechsel.

5. Vergleich

  • Monolith: ein Deployment, eine DB, ACID-Transaktionen, einfaches Debugging. Risiko: Grenzen verschwimmen, Build und Tests werden langsam, alle Teams releasen zusammen.
  • Modulith: ein Deployment, aber geprüfte Modulgrenzen. Gute Basis für 1–3 Teams. Später einzelne Module herauslösbar. Risiko: eine Laufzeit, eine Skalierung, ein Technologie-Stack.
  • Microservices: unabhängige Releases, Skalierung und Technologie pro Service, Fehlerisolation. Preis: Netzwerk, Eventual Consistency, verteiltes Tracing, Plattform-Team.
  • Serverless-Funktionen: noch feiner geschnitten. Gut für Event-Verarbeitung mit Lastspitzen. Kalte Starts und viele kleine Teile erhöhen die Komplexität.

6. In der Produktion

  1. Verteilter Monolith: Services teilen eine DB oder ein Shared-Library-Modell. Jedes Release braucht alle Teams. Lösung: Datenbesitz klären, Schnittstellen versionieren, Services mit zu viel Kopplung zusammenlegen.
  2. Lange synchrone Ketten: Ein Request ruft fünf Services nacheinander. Latenzen addieren sich, Verfügbarkeiten multiplizieren sich. Lösung: Daten per Event replizieren, asynchron entkoppeln, Timeouts und Circuit Breaker.
  3. Monolith mit verschwimmenden Grenzen: Jede Änderung bricht etwas Fremdes. Lösung: Module ziehen und mit verify() oder ArchUnit im CI erzwingen.
  4. Zu viele kleine Services: Mehr Services als Entwickler. Jeder Service braucht Pipeline, Monitoring, Updates. Lösung: nach Bounded Context zusammenlegen.
  5. Kein Plattform-Team: Jedes Team baut eigene Pipelines und Logging. Lösung: gemeinsame Plattform mit Vorlagen, z. B. Helm-Chart, OpenTelemetry, Health Checks.
  6. Daten-Reports über alle Services: Ein Report braucht Joins über fünf DBs. Lösung: Events in einen Reporting-Store oder ein Lakehouse schreiben, nicht direkt in fremde DBs greifen.

7. Diagnose: Werkzeuge und Metriken

  • ApplicationModules.of(App.class).verify(): bricht den Build bei Modul-Verletzungen.
  • Spring Modulith Documenter: erzeugt C4- und PlantUML-Diagramme der Module aus dem Code.
  • ArchUnit: Architekturregeln als JUnit-Test, auch ohne Spring Modulith.
  • Distributed Tracing (OpenTelemetry, Jaeger, Application Insights): zählt Hops und zeigt die langsamste Stelle pro Request.
  • Change Coupling aus Git: Welche Services ändern sich immer im selben Commit oder Sprint? Hohe Werte zeigen einen falschen Schnitt.
  • DORA-Metriken: Deployment-Frequenz, Lead Time, Change Failure Rate, Time to Restore. Sie zeigen, ob die Architektur Teams wirklich schneller macht.
  • Release-Abhängigkeiten zählen: Wie viele Services müssen gemeinsam deployen? Ziel: null.

8. Senior-Punkte

  1. Microservices lösen Teamprobleme, keine Technikprobleme. Ein Team mit einem Produkt braucht sie fast nie.
  2. Erst die Grenzen, dann die Prozesse. Ein Modulith testet den Schnitt billig. Eine falsche Service-Grenze ist teuer.
  3. Unabhängige Deploybarkeit ist der Massstab. Nicht die Anzahl der Services und nicht ihre Grösse.
  4. Der Netzwerk-Aufruf ist kein Methodenaufruf. Er kann langsam sein, scheitern oder doppelt ankommen. Das Design muss das tragen.
  5. Plattform zuerst: CI/CD, Observability und Self-Service müssen vor dem zehnten Service stehen.
  6. Gemischte Architektur ist normal: ein Modulith-Kern plus wenige Services mit echten Gründen (Skalierung, Team, Sicherheit, Technologie).

10. Fallen

  • „Microservices sind moderner, also besser.“ → Falsch. Sie sind ein Tausch. Ohne mehrere Teams überwiegen meist die Kosten.
  • „Ein Microservice muss klein sein.“ → Falsch. Er muss fachlich zusammenhängend und unabhängig deploybar sein.
  • „Ein Monolith skaliert nicht.“ → Falsch. Er skaliert horizontal mit mehreren Instanzen.
  • „Wir teilen nur die Datenbank, sonst ist alles getrennt.“ → Dann ist es ein verteilter Monolith. Schema-Änderungen koppeln alle Teams.
  • „Modulith ist nur ein Monolith mit Paketen.“ → Falsch. Die Grenzen werden geprüft, und Module sprechen über APIs oder Events.
  • „Wir bauen alles neu als Microservices.“ → Big Bang ist riskant. Besser: Strangler Fig, Stück für Stück.

11. Fragen

Was ist ein Monolith?

Eine Anwendung, die als eine Einheit gebaut und deployt wird. Meist mit einer Datenbank und lokalen Transaktionen.

Was ist ein modularer Monolith (Modulith)?

Ein Monolith mit harten fachlichen Modulgrenzen. Module nutzen sich nur über APIs oder Events. Die Grenzen werden im Build geprüft.

Was ist ein Microservice?

Ein unabhängig deploybarer Service um eine Business Capability. Er gehört einem Team und besitzt seine Daten.

Wann wählen Sie Microservices?

Wenn mehrere Teams unabhängig liefern müssen, Teile sehr unterschiedlich skalieren oder andere Anforderungen haben (Sicherheit, Technologie). Und wenn Plattform und Monitoring bereit sind.

Wann bleiben Sie beim Monolithen oder Modulith?

Bei einem oder wenigen Teams, unklarer Domäne, neuem Produkt oder fehlender Plattform. Der Modulith hält die Tür zu Services offen.

Was ist Conway's Law?

Systeme spiegeln die Kommunikationsstruktur der Organisation. Service-Grenzen und Team-Grenzen sollten zusammenpassen.

Was ist das Inverse Conway Maneuver?

Man formt zuerst die Teams nach der gewünschten Architektur. Die Architektur folgt dann den Teams.

Welche Teamtypen kennt Team Topologies?

Stream-aligned, Platform, Enabling und Complicated-subsystem. Microservices passen gut zu stream-aligned Teams mit einer Plattform darunter.

Was ist der Microservice Premium?

Die Mehrkosten von Microservices: Netzwerk, verteilte Daten, Betrieb. Sie lohnen sich erst bei hoher Komplexität des Systems.

Was sind Voraussetzungen für Microservices?

Schnelles Provisioning, Basis-Monitoring und automatisiertes Deployment pro Service. Dazu Tracing und ein klarer Datenbesitz.

Was ist ein verteilter Monolith?

Services, die nur zusammen deployen können. Typisch: gemeinsame DB, gemeinsame Releases, lange synchrone Ketten.

Warum Database per Service?

Nur so kann ein Team sein Schema ändern, ohne andere zu fragen. Andere lesen über API oder Events.

Was kostet ein Remote-Aufruf im Vergleich zu einem Methodenaufruf?

Grössenordnungen mehr: Nanosekunden gegen Millisekunden. Dazu kommen Fehler, Timeouts und Duplikate.

Wie verhält sich Verfügbarkeit in einer synchronen Kette?

Sie multipliziert sich. 10 Services mit je 99,9 % ergeben ca. 99,0 %.

Was ist Spring Modulith?

Ein Spring-Projekt für modulare Monolithen. Es erkennt Module aus Paketen, prüft Grenzen mit verify(), testet Module einzeln und bietet Event-Unterstützung.

Was prüft ApplicationModules.verify()?

Keine Zyklen zwischen Modulen, kein Zugriff auf interne Pakete, und nur erlaubte Abhängigkeiten, wenn allowedDependencies gesetzt ist.

Was macht @ApplicationModuleListener?

Er verarbeitet ein Event asynchron, in einer neuen Transaktion, nach dem Commit des Senders. Module koppeln sich so lose wie Services.

Was ist die Event Publication Registry?

Spring Modulith speichert Events in der DB. Scheitert ein Listener, bleibt das Event unvollständig und kann neu zugestellt werden.

Wie löst man ein Modul aus einem Modulith heraus?

Events mit @Externalized an Kafka schicken, Daten in eigene DB migrieren, Modul als eigenen Service deployen, Aufrufer schrittweise umleiten (Strangler Fig).

Was ist das Strangler-Fig-Muster?

Ein Altsystem wird Stück für Stück ersetzt. Ein Proxy leitet einzelne Funktionen schon zum neuen System. Kein Big Bang.

Was bedeutet MonolithFirst?

Fowlers Rat: Neue Systeme als Monolith starten, bis die Grenzen klar sind. Dann gezielt Services herauslösen.

Skaliert ein Monolith?

Ja, horizontal mit mehreren Instanzen. Er skaliert nur nicht einzelne Teile getrennt.

Wie messen Sie, ob Microservices helfen?

Mit DORA-Metriken und der Zahl gemeinsamer Releases. Mehr Services bei sinkender Deployment-Frequenz heisst: falscher Schnitt.

Szenario: Drei Teams arbeiten an einem Monolithen und blockieren sich bei jedem Release. Was schlagen Sie vor?

Zuerst Modulgrenzen nach Bounded Context ziehen und mit verify() prüfen. Teams pro Modul zuordnen. Module mit eigenem Release-Bedarf schrittweise als Services herauslösen.

Szenario: Ein Startup mit 4 Entwicklern will mit 15 Microservices starten. Ihre Meinung?

Zu viel Premium für zu wenig Team. Besser ein Modulith mit klaren Grenzen und Events. Services erst bei echtem Bedarf.

Szenario: 12 Services müssen immer zusammen deployt werden. Was tun Sie?

Ursache suchen: gemeinsame DB, geteilte Modelle, synchrone Ketten, Change Coupling in Git. Dann Datenbesitz klären, Verträge versionieren und eng gekoppelte Services zusammenlegen.
