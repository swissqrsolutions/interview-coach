Migration vom Monolithen: Strangler Fig

Kern: Strangler Fig ist ein Migrationsmuster, das ein Altsystem Stück für Stück durch neue Services ersetzt. Eine Fassade (Proxy) vor dem Altsystem leitet jede Funktion entweder zum alten oder zum neuen Teil. Es löst das Risiko eines Big-Bang-Rewrites: Jeder Schritt ist klein, messbar und umkehrbar.

1. Wo sitzt die Strangler-Fassade?

  1. Fassade: ein Proxy vor dem Altsystem mit einer Routing-Tabelle. Beispiel: API Gateway, Ingress, Azure API Management, Feature Switch in der UI.
  2. Monolith: beantwortet alles, was noch nicht migriert ist. Er wird nur kleiner, nicht umgebaut.
  3. Neuer Service: übernimmt eine fachliche Funktion nach der anderen. Beispiel: zuerst Reports.
  4. Anti-Corruption Layer (ACL): ein Adapter, der Modelle zwischen alt und neu übersetzt. Beispiel: Zahl „1.234,50“ wird zu 1234.5.
  5. Datenweg: Daten folgen der Funktion, oft per ETL plus CDC (Change Data Capture, Änderungen aus dem DB-Log lesen).

2. Die Reise einer Funktion (die Geschichte zum Merken)

  1. Fassade einziehen. Alle Clients gehen über die Fassade. Am Anfang leitet sie alles zum Monolithen. Nutzer merken nichts.
  2. Eine Funktion bauen. Das Team wählt einen klaren fachlichen Schnitt, z. B. Reports. Gute Kandidaten: wenig Abhängigkeiten, hoher Nutzen, oft geändert.
  3. Shadow-Betrieb. Die Fassade ruft beide Seiten. Nutzer bekommen die alte Antwort. Ein Vergleich prüft die neue Antwort (Parity).
  4. Umschalten. Bei 100 % Übereinstimmung ändert die Fassade die Route. Bei Problemen geht die Route zurück, ohne neues Deployment.
  5. Alten Code löschen. Erst nach einer Beobachtungszeit. Dann folgt die nächste Funktion. Am Ende verschwindet der Monolith und oft auch die Fassade.

3. Beispiel: Fassade mit Shadow-Vergleich und Umschalten

ROUTES = {"/reports/": "shadow", "/invoices/": "legacy"}   # Routing-Tabelle

class Legacy:  GET /reports/... → {"src":"legacy","total":"1.234,50"}   # deutsches Zahlenformat
class NewSvc:  GET /reports/... → {"src":"new","total":1234.5}

def legacy_to_number(s):          # Anti-Corruption Layer
    return float(s.replace(".", "").replace(",", "."))

class Facade:
    mode = Route für den Pfad, sonst "legacy"
    "legacy" → alte Antwort · "new" → neue Antwort
    "shadow" → beide aufrufen, vergleichen, loggen, ALTE Antwort zurückgeben

for phase in [("1 shadow", {"/reports/": "shadow"}), ("2 cutover", {"/reports/": "new"})]:
    GET /reports/2026-11-23 und /invoices/42 über die Fassade (Port 8000)
phase 1 shadow {'/reports/': 'shadow'}
  shadow compare /reports/2026-11-23: legacy='1.234,50' new=1234.5 parity=True
  GET /reports/2026-11-23 -> {'src': 'legacy', 'total': '1.234,50'}
  GET /invoices/42 -> {'src': 'legacy', 'path': '/invoices/42'}
phase 2 cutover {'/reports/': 'new'}
  GET /reports/2026-11-23 -> {'src': 'new', 'total': 1234.5}
  GET /invoices/42 -> {'src': 'legacy', 'path': '/invoices/42'}

Echte Ausgabe, Python 3.12.10 (http.server + urllib, drei lokale Server auf 8000–8002). Code gekürzt.

  1. In Phase 1 bekommt der Nutzer weiter die alte Antwort. Die neue läuft nur im Schatten mit.
  2. Ein direkter Vergleich "1.234,50" == 1234.5 wäre falsch. Erst der ACL macht beide Seiten vergleichbar.
  3. In Phase 2 ändert sich nur ein Eintrag in der Routing-Tabelle. /invoices bleibt beim Monolithen.
  4. Der Rückweg ist dieselbe Zeile: "new" wieder auf "legacy".

4. Details, die Interviewer fragen

  1. Fassade als Übergangsarchitektur: Sie ist absichtlich temporär. Sie darf kein Single Point of Failure und kein Engpass werden.
  2. Was zuerst migrieren? Eine Funktion mit klarem Bounded Context, wenig eingehenden Abhängigkeiten und spürbarem Nutzen. Nicht den Kern mit den meisten Abhängigkeiten.
  3. Branch by Abstraction: Für Code tief im Monolithen. Man zieht eine Abstraktion (Interface) ein, baut die neue Implementierung dahinter und schaltet um. Gut, wenn man nicht per HTTP abfangen kann.
  4. Parallel Run: Alt und neu laufen gleichzeitig mit denselben Eingaben. Ergebnisse werden verglichen, nur alt zählt. Teuer, aber sehr sicher für Berechnungen.
  5. Daten migrieren: Erst liest der neue Service die alte DB. Dann eigene DB mit ETL plus CDC-Sync. Dann ist die neue DB die Wahrheit, die alten Tabellen werden entfernt.
  6. Rollback-Fenster: Zurück geht leicht, solange die alten Tabellen und der Sync existieren. Nach dem Löschen ist Rollback teuer.
  7. Abhängigkeiten in beide Richtungen: Der neue Teil ruft noch alte Funktionen. Der alte Teil ruft vielleicht migrierte Funktionen. Ein ACL schützt das neue Modell vor alten Begriffen.
  8. Unveränderbarer Monolith: Ohne Zugang zum Code bleibt die Datenbank als Einstieg, z. B. Trigger oder CDC.
  9. Wann nicht? Wenn Requests nicht abgefangen werden können, das System klein ist, oder das Altsystem sehr schnell weg muss.
  10. Fassaden-Typen: HTTP-Proxy oder Gateway (nach Pfad), Feature Switch in der UI (nach Nutzer oder Mandant), Message-Router (nach Event-Typ).

5. Vergleich

  • Big-Bang-Rewrite: alles neu, ein Stichtag. Lange kein Nutzen, hohes Risiko, Altsystem bekommt in der Zeit trotzdem Änderungen.
  • Strangler Fig: Funktion für Funktion hinter einer Fassade. Früher Nutzen, Rollback pro Schritt. Preis: zwei Systeme parallel betreiben.
  • Branch by Abstraction: wie Strangler, aber im Code statt vor dem System.
  • Parallel Run: Ergänzung zum Strangler für kritische Berechnungen. Beweist Gleichheit mit echten Daten.
  • Modulith zuerst: erst Module im Monolithen sauber trennen, dann herauslösen. Senkt das Risiko des Schnitts.
  • Lift and Shift: Monolith unverändert in die Cloud. Schnell, aber kein Architekturgewinn.

6. In der Produktion

  1. Migration bleibt bei 80 % stehen: Zwei Systeme laufen für Jahre. Lösung: Abschaltdatum pro Funktion, Budget für das Löschen planen.
  2. Ergebnisse weichen ab: Kleine Unterschiede bei Zahlen, Datum, Zeitzone, null vs leerer String. Lösung: automatischer Parity-Vergleich vor dem Umschalten.
  3. Fassade wird Engpass: Jeder Request geht durch sie. Lösung: hochverfügbar betreiben, Latenz messen, keine Fachlogik dort.
  4. Daten in zwei Systemen laufen auseinander: Beide schreiben dieselben Daten. Lösung: pro Datum genau einen Besitzer, der andere liest nur oder bekommt CDC.
  5. Verteilter Monolith: Der neue Service ruft für jede Anfrage synchron den alten auf. Lösung: Schnitt nach Fachlichkeit, Daten lokal halten.
  6. Fehlerhaftes Verhalten wird mitmigriert: Das Altsystem rechnet fachlich falsch. Lösung: zuerst Verhalten 1:1 migrieren, Korrektur danach als eigene, sichtbare Entscheidung.

7. Diagnose: Werkzeuge und Metriken

  • Routing-Anteil: Anteil Requests pro Ziel (alt/neu) in der Fassade. Zeigt den Fortschritt.
  • Parity-Rate: Anteil identischer Ergebnisse im Shadow- oder Parallel-Run, pro Funktion.
  • Fehler und Latenz pro Ziel: z. B. in Grafana. Neu darf nicht langsamer oder fehlerhafter sein als alt.
  • Distributed Tracing: Zeigt, ob der neue Service noch synchron den Monolithen ruft.
  • CDC-Lag: Verzögerung zwischen alter und neuer Datenbank vor dem Umschalten.
  • Tote Pfade: Access-Logs des Monolithen. Kein Traffic mehr auf einem Pfad heisst: Code kann weg.

8. Senior-Punkte

  1. Die Reihenfolge ist die wichtigste Entscheidung. Früher fachlicher Nutzen schafft Vertrauen und Budget für den Rest.
  2. Ohne messbare Parity kein Umschalten. Ein maschinell prüfbarer Vergleich ersetzt Diskussionen.
  3. Verhalten zuerst migrieren, Semantik später korrigieren. Sonst weiss niemand, ob ein Unterschied Bug oder Absicht ist.
  4. Rollback ohne Deployment (Route, Feature Switch) macht jeden Schritt billig umkehrbar.
  5. Löschen gehört zum Plan. Eine Migration ist erst fertig, wenn der alte Code weg ist.
  6. Die Daten sind der schwerste Teil, nicht der Code. Pro Datum braucht es einen klaren Besitzer.

10. Fallen

  • „Strangler Fig heisst, wir bauen alles neu.“ → Falsch. Man ersetzt Funktion für Funktion, das Altsystem läuft weiter.
  • „Die Fassade bleibt für immer.“ → Meist falsch. Sie ist Übergangsarchitektur und fällt am Ende weg, ausser als Adapter für alte Clients.
  • „Wir migrieren den Code, die Daten bleiben in der alten DB.“ → Nur als Zwischenschritt. Sonst entsteht ein verteilter Monolith.
  • „Wir korrigieren alte Fehler gleich mit.“ → Riskant. Dann ist Parity nicht mehr prüfbar.
  • „Zuerst den grössten, wichtigsten Teil.“ → Falsch. Zuerst einen klar geschnittenen Teil mit wenig Abhängigkeiten.

11. Fragen

Was ist das Strangler-Fig-Muster?

Ein Altsystem wird Funktion für Funktion ersetzt. Eine Fassade leitet jede Funktion zum alten oder neuen Teil, bis der alte leer ist.

Welches Problem löst es?

Das Risiko eines Big-Bang-Rewrites. Jeder Schritt ist klein, liefert früh Nutzen und ist umkehrbar.

Welche Phasen hat eine Strangler-Migration?

Fassade einziehen, Funktion bauen, im Schatten vergleichen, umschalten, alten Code löschen. Dann die nächste Funktion.

Was kann als Fassade dienen?

Ein API Gateway, ein Ingress, Azure API Management, ein Feature Switch in der UI oder ein Message-Router.

Welche Funktion migrieren Sie zuerst?

Eine mit klarem fachlichen Schnitt, wenig Abhängigkeiten und sichtbarem Nutzen. Nicht den Kern mit den meisten Verbindungen.

Was ist ein Anti-Corruption Layer?

Ein Adapter, der Modelle und Begriffe zwischen alt und neu übersetzt. Er schützt das neue Modell vor alten Konventionen.

Was ist Branch by Abstraction?

Eine Abstraktion im Code einziehen, neue Implementierung dahinter bauen, dann umschalten. Für Teile, die man nicht per Proxy abfangen kann.

Was ist ein Parallel Run?

Alt und neu verarbeiten dieselben Eingaben. Ergebnisse werden verglichen, aber nur alt ist massgebend. Gut für Berechnungen.

Was ist Shadow Traffic?

Die Fassade schickt Requests zusätzlich an den neuen Teil. Dessen Antwort wird nur verglichen, nicht an den Nutzer gegeben.

Wie migrieren Sie die Daten?

Zuerst nutzt der neue Service die alte DB. Dann eigene DB mit Initial-Load und CDC-Sync. Nach Validierung ist die neue DB die Wahrheit.

Wie lange ist ein Rollback möglich?

Solange alte Tabellen, Sync und alter Code existieren. Nach dem Löschen wird Rollback teuer.

Wann passt Strangler Fig nicht?

Wenn Requests nicht abfangbar sind, das System klein ist oder das Altsystem sehr schnell weg muss.

Was ist ein verteilter Monolith?

Services, die nur zusammen deployt oder betrieben werden können, z. B. durch viele synchrone Aufrufe oder eine geteilte DB.

Wie messen Sie den Fortschritt?

Anteil Requests pro Ziel in der Fassade, Anzahl migrierter Funktionen und gelöschter Code. Nicht die Zeilen neuen Codes.

Was tun mit fachlich falschem Verhalten im Altsystem?

Erst 1:1 migrieren und Parity beweisen. Die Korrektur danach als eigene, sichtbare Änderung mit dem Fachbereich.

Wie verhindern Sie, dass die Fassade zum Engpass wird?

Hochverfügbar betreiben, keine Fachlogik dort, Latenz überwachen. Am Ende entfernen.

Strangler Fig und Modulith, wie passen sie zusammen?

Ein Modulith trennt Module im Monolithen sauber. Danach kann man ein Modul mit Strangler Fig herauslösen.

Warum scheitern viele Migrationen bei 80 %?

Die schwierigen Reste haben wenig Nutzen, das Budget ist weg. Lösung: Abschaltdaten und Löschen fest einplanen.

Szenario: Die neue Berechnung liefert in 3 % der Fälle andere Zahlen. Was tun Sie?

Nicht umschalten. Abweichungen gruppieren und Ursachen suchen: Zahlenformat, Zeitzone, null vs leer. Jede Ursache fixen und den Parity-Job erneut laufen lassen.

Szenario: Das Management will einen kompletten Neubau mit Stichtag in 18 Monaten. Wie argumentieren Sie?

Big Bang heisst 18 Monate ohne Nutzen und ein riskanter Stichtag. Strangler Fig liefert in Wochen die erste Funktion, mit Rollback pro Schritt.

Szenario: Der Monolith-Code ist nicht änderbar, nur die Datenbank ist zugänglich. Wie migrieren Sie?

Fassade vor den Clients, Datenänderungen per CDC aus der DB lesen. Der neue Service baut seinen Zustand daraus und übernimmt Funktionen über die Fassade.
