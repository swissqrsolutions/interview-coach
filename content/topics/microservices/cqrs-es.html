CQRS und Event Sourcing

Kern: CQRS (Command Query Responsibility Segregation) trennt das Modell zum Schreiben vom Modell zum Lesen. Event Sourcing speichert nicht den aktuellen Zustand, sondern die Folge aller fachlichen Events. Beide sind unabhängig, passen aber gut zusammen: Events vom Schreibmodell bauen die Lesemodelle.

1. Wo sitzen CQRS und Event Sourcing?

  1. Command: eine Absicht, etwas zu ändern. Beispiel: WithdrawMoney(account-1, 50).
  2. Command Handler: lädt das Aggregate (Konsistenzgrenze aus DDD), prüft Regeln und erzeugt Events. Beispiel: „Kontostand reicht?“.
  3. Event Store: speichert Events nur anhängend (append-only). Beispiel: MoneyWithdrawn{amount:50}.
  4. Projector: liest neue Events und aktualisiert ein Lesemodell. Beispiel: Tabelle balance_view.
  5. Read Model: eine für Abfragen optimierte Kopie (Projektion). Beispiel: Suchindex, denormalisierte Tabelle.
  6. Query: liest nur das Read Model und ändert nichts.

2. Die Reise eines Commands (die Geschichte zum Merken)

  1. Stream laden: Der Handler liest alle Events von account-1. Ein Stream ist die geordnete Event-Liste eines Aggregates.
  2. Replay: Er spielt die Events auf einen leeren Zustand ab. Das heisst Rehydration. Ergebnis: Saldo 70, Version 3.
  3. Regel prüfen: Die Fachlogik entscheidet. 50 abheben ist erlaubt.
  4. Append mit Expected Version: Er schreibt Version 4, aber nur, wenn noch niemand Version 4 geschrieben hat. Das ist Optimistic Concurrency. Bei Konflikt lädt er neu und versucht es noch einmal.
  5. Projektion: Ein Projector liest neue Events ab seinem Checkpoint (letzte verarbeitete Position). Er aktualisiert die View.
  6. Query: Der Client liest die View. Bis der Projector läuft, sieht er den alten Stand. Das ist Eventual Consistency.

3. Beispiel: Event Store und Projektion in PostgreSQL

CREATE TABLE events (
  global_pos bigserial PRIMARY KEY,
  stream_id  text NOT NULL, version int NOT NULL,
  type text NOT NULL, data jsonb NOT NULL,
  UNIQUE (stream_id, version));               -- Optimistic Concurrency
-- account-1: Opened, Deposited 100, Withdrawn 30 · account-2: Opened, Deposited 50
-- zwei Commands haben beide Version 3 gelesen:
INSERT INTO events VALUES (DEFAULT,'account-1',4,'MoneyWithdrawn','{"amount":50}');
INSERT INTO events VALUES (DEFAULT,'account-1',4,'MoneyWithdrawn','{"amount":60}');
-- Rehydration: Stream abspielen
SELECT stream_id, max(version), sum(...) AS balance FROM events WHERE stream_id='account-1' GROUP BY 1;
-- Read Side: balance_view + checkpoint, Prozedur project() liest Events mit global_pos > checkpoint
CALL project(); SELECT * FROM balance_view; SELECT * FROM checkpoint;
INSERT ... ('account-2',3,'MoneyDeposited','{"amount":25}');
SELECT balance AS stale_balance ...; CALL project(); SELECT balance AS fresh_balance ...;
TRUNCATE balance_view; UPDATE checkpoint SET pos=0; CALL project();   -- Rebuild

  1. Der zweite Append mit Version 4 scheitert am Unique Constraint. Genau so erkennt ein Event Store einen Konflikt.
  2. Der Saldo 20 entsteht nur aus den Events: 100 − 30 − 50. Es gibt keine Spalte „Saldo“ auf der Schreibseite.
  3. Nach einem neuen Event zeigt die View noch 50 (stale). Erst nach project() zeigt sie 75.
  4. Der Rebuild löscht die View und spielt alles neu ab. Ergebnis identisch. Read Models sind also wegwerfbar.
  5. Der fehlgeschlagene Insert hat trotzdem eine Sequenznummer verbraucht. global_pos hat also Lücken. Das ist normal bei Sequences.

4. Details, die Interviewer fragen

  1. CQRS ohne Event Sourcing: Das geht. Schreiben in normalisierte Tabellen, Lesen aus Views oder einem Suchindex. Das ist die häufigste Form.
  2. Event Sourcing ohne CQRS: Geht für Abfragen pro Aggregate. Für Listen und Suchen braucht man fast immer Projektionen.
  3. Event-Design: Events beschreiben die fachliche Absicht in der Vergangenheit. Gut: SeatsReserved(2). Schlecht: RemainingSeatsChanged(42).
  4. Snapshot: ein gespeicherter Zustand nach N Events. Rehydration lädt den Snapshot und spielt nur neuere Events ab. Er ist eine Optimierung, nicht die Wahrheit.
  5. Event-Versionierung: Events sind unveränderlich. Strategien: tolerante Deserialisierung, Versionsfeld im Event, Upcaster (alte Form beim Lesen umwandeln). Events umschreiben nur als letzter Ausweg.
  6. Korrektur: Falsche Daten korrigiert man mit einem Compensating Event, nicht mit UPDATE. Beispiel: ReservationCanceled.
  7. Idempotente Projektoren: Zustellung ist meist at-least-once. Der Projector speichert die letzte Position und überspringt Duplikate, am besten in derselben Transaktion wie die View.
  8. Globale Reihenfolge: Eine Sequence vergibt Nummern beim Insert, nicht beim Commit. Eine spätere Nummer kann früher sichtbar sein. Ein naiver Projector „pos > checkpoint“ kann dann Events überspringen.
  9. Read-your-own-writes: Nach einem Command sieht der Nutzer die alte View. Lösungen: Antwort mit neuer Version, Client wartet bis View ≥ Version, oder Ergebnis direkt aus dem Command zurückgeben.
  10. Event Store vs Kafka: Kafka hat keine Abfrage pro Aggregate und keine Expected Version. Kafka verteilt Events, ein Event Store speichert sie als Wahrheit.
  11. Personendaten (DSG/DSGVO): Unveränderliche Events kollidieren mit Löschpflicht. Lösungen: Personendaten ausserhalb speichern und per ID referenzieren, oder Crypto-Shredding (Schlüssel pro Person löschen).
  12. Domain Events vs Integration Events: Event-Sourcing-Events sind intern und feingranular. Nach aussen publiziert man stabile Integration Events.
  13. Testen: Given (alte Events) – When (Command) – Then (neue Events). Das testet Fachlogik ohne Datenbank.

5. Vergleich

  • CRUD: speichert nur den aktuellen Zustand. Einfach, stark konsistent, aber keine Historie.
  • CRUD + Audit-Tabelle: Historie als Nebenprodukt. Der Zustand bleibt die Wahrheit, die Historie kann unvollständig sein.
  • CQRS (ohne ES): eigene Lesemodelle, Schreibseite bleibt CRUD. Guter Mittelweg für komplexe Abfragen.
  • Event Sourcing: Events sind die Wahrheit. Vollständige Historie, Replay, neue Projektionen jederzeit. Preis: Komplexität, Versionierung, Eventual Consistency.
  • Outbox: CRUD-Tabellen plus Events für andere Services. Kein Replay des eigenen Zustands.
  • Materialized View in der DB: CQRS im Kleinen, in einer Datenbank, ohne eigenen Projector.

6. In der Produktion

  1. Projektion hinkt stark nach: Nutzer sehen alte Daten. Lösung: Lag-Metrik (Kopfposition minus Checkpoint), Alarm, Projektor skalieren oder partitionieren.
  2. Projektion zählt doppelt: Ein Event wurde zweimal verarbeitet. Lösung: Checkpoint und View in einer Transaktion, oder idempotente Updates.
  3. Übersprungene Events: Ein Projector las pos > checkpoint, ein früherer Insert committete später. Lösung: nur bis zur ältesten offenen Transaktion lesen, oder Commit-geordnete Positionen nutzen.
  4. Rehydration wird langsam: Ein Aggregate hat 100 000 Events. Lösung: Snapshots, oder das Aggregate fachlich kürzer schneiden (z. B. pro Periode).
  5. Fehlerhafte Events in der Historie: Ein Bug hat falsche Events geschrieben. Lösung: Compensating Events oder Upcaster, nie heimlich umschreiben.
  6. Rebuild dauert Stunden: Neue Projektion über Millionen Events. Lösung: neue View parallel bauen, dann umschalten (Blue-Green für Read Models).
  7. Löschanfrage einer Person: Events dürfen nicht geändert werden. Lösung von Anfang an: Personendaten auslagern oder Crypto-Shredding.

7. Diagnose: Werkzeuge und Abfragen

  • Projection Lag: SELECT max(global_pos) - (SELECT pos FROM checkpoint WHERE projection='x') FROM events;
  • Stream einer Entität ansehen: SELECT version, type, data FROM events WHERE stream_id='account-1' ORDER BY version; Das ist das beste Debug-Werkzeug von Event Sourcing.
  • Konflikte zählen: Rate von Unique-Violation-Fehlern beim Append. Viele Konflikte heissen: Aggregate zu gross oder zu heiss.
  • Parity-Check: Projektion neu in eine Schattentabelle bauen und mit der Live-View vergleichen.
  • Stream-Länge: Verteilung der Events pro Stream. Lange Streams brauchen Snapshots.
  • Tracing: Correlation-ID und Causation-ID in den Event-Metadaten verfolgen.

8. Senior-Punkte

  1. Event Sourcing ist eine lokale Entscheidung pro Bounded Context, nicht für das ganze System. Gute Kandidaten: Ledger, Bestellungen, Prozesse mit Audit-Pflicht.
  2. CQRS ohne Event Sourcing reicht meistens. Event Sourcing nur, wenn Historie und Replay echten fachlichen Wert haben.
  3. Eventual Consistency muss die UI zeigen können. Sonst gibt es Tickets „meine Änderung fehlt“.
  4. Read Models sind wegwerfbar. Die Fähigkeit, sie neu zu bauen, ist der grösste Gewinn. Sie muss geübt und getestet sein.
  5. Event-Schemas sind öffentliche Verträge für immer. Versionierung und Upcasting plant man vor dem ersten Event.
  6. Migration in oder aus Event Sourcing ist teuer. Die Entscheidung ist schwer umkehrbar.

10. Fallen

  • „CQRS heisst zwei Datenbanken.“ → Falsch. CQRS heisst zwei Modelle. Sie können in einer Datenbank liegen.
  • „CQRS braucht Event Sourcing.“ → Falsch. Beide sind unabhängig.
  • „Kafka ist unser Event Store.“ → Meist falsch. Kafka fehlt das Lesen pro Aggregate und die Expected-Version-Prüfung.
  • „Events kann man bei Bugs korrigieren.“ → Nein. Man schreibt Compensating Events oder nutzt Upcaster.
  • „Snapshots ersetzen die Events.“ → Falsch. Snapshots sind ein Cache, die Events bleiben die Wahrheit.
  • „Mit CQRS ist alles schneller.“ → Lesen ja, aber man zahlt mit Verzögerung, mehr Code und mehr Betrieb.

11. Fragen

Was ist CQRS?

Die Trennung von Schreibmodell (Commands) und Lesemodell (Queries). Jedes Modell ist für seine Aufgabe optimiert und kann getrennt skalieren.

Was ist Event Sourcing?

Der Zustand wird als Folge fachlicher Events gespeichert. Den aktuellen Zustand erhält man durch Replay.

Brauchen CQRS und Event Sourcing einander?

Nein. CQRS geht mit normalen Tabellen. Event Sourcing braucht aber fast immer Projektionen für Listen und Suchen.

Was ist ein Command, was ist ein Event?

Ein Command ist eine Absicht und kann abgelehnt werden. Ein Event ist eine Tatsache in der Vergangenheit und wird nicht abgelehnt.

Was ist Rehydration?

Das Laden eines Aggregates durch Abspielen seiner Events. Mit Snapshot nur ab dem letzten Snapshot.

Wie verhindert ein Event Store parallele Konflikte?

Mit Optimistic Concurrency: Der Append nennt die erwartete Version. Ist sie schon vergeben, scheitert er, und der Handler lädt neu.

Was ist eine Projektion?

Ein Lesemodell, das aus Events gebaut wird. Es ist abgeleitet und jederzeit neu baubar.

Was ist ein Checkpoint?

Die letzte Event-Position, die ein Projector verarbeitet hat. Nach einem Neustart macht er dort weiter.

Warum müssen Projektoren idempotent sein?

Events kommen at-least-once. Ohne Idempotenz zählt die View doppelt und driftet von den Events weg.

Was ist ein Snapshot?

Ein gespeicherter Zustand nach N Events. Er beschleunigt Rehydration, ersetzt aber die Events nicht.

Wie versionieren Sie Events?

Additive Änderungen mit toleranter Deserialisierung. Brechende Änderungen mit neuer Version und Upcaster beim Lesen. Gespeicherte Events bleiben unverändert.

Was ist ein Upcaster?

Eine Funktion, die ein altes Event-Format beim Lesen ins aktuelle umwandelt. So kennt der Code nur die neueste Version.

Wie korrigieren Sie falsche Daten?

Mit einem Compensating Event, das die Wirkung umkehrt. Die Historie zeigt dann Fehler und Korrektur.

Was ist Eventual Consistency hier?

Das Lesemodell ist kurz älter als der Event Store. Die Verzögerung hängt vom Projector ab.

Wie lösen Sie Read-your-own-writes?

Command gibt die neue Version zurück, die UI wartet, bis die View diese Version hat. Oder die UI zeigt das Ergebnis direkt aus dem Command.

Warum ist Kafka kein guter Event Store?

Kafka kann nicht effizient einen Stream pro Aggregate lesen. Es kennt keine Expected Version. Es eignet sich zum Verteilen, nicht als Wahrheit pro Entität.

Wie gehen Sie mit dem Recht auf Löschung um?

Personendaten ausserhalb der Events halten und per ID referenzieren. Oder Crypto-Shredding: pro Person verschlüsseln und den Schlüssel löschen.

Warum kann ein Projector mit einer Sequence Events übersehen?

Nummern werden beim Insert vergeben, nicht beim Commit. Eine kleinere Nummer kann nach einer grösseren sichtbar werden und liegt dann hinter dem Checkpoint.

Wann ist Event Sourcing eine schlechte Wahl?

Bei einfachem CRUD, Stammdaten, kurzlebigen Systemen, Pflicht zu sofort konsistenten Views, oder einem Team ohne Event-Erfahrung.

Wann ist Event Sourcing eine gute Wahl?

Wenn Historie fachlich zählt: Ledger, Buchungen, Bestellprozesse, Audit-Pflicht. Und wenn neue Auswertungen aus alten Daten wertvoll sind.

Wie testen Sie ein event-sourced Aggregate?

Given: frühere Events. When: ein Command. Then: erwartete neue Events oder ein Fehler. Ohne Datenbank.

Domain Event vs Integration Event?

Domain Events sind intern und feingranular. Integration Events sind stabile, öffentliche Verträge für andere Services.

Szenario: Nutzer melden, dass ihre Änderung nach dem Speichern nicht sichtbar ist. Was tun Sie?

Projection Lag messen. Kurzfristig Read-your-own-writes mit Versionsnummer lösen. Langfristig Projector schneller machen und Lag alarmieren.

Szenario: Eine neue Auswertung braucht Daten aus 3 Jahren Events. Wie gehen Sie vor?

Neue Projektion parallel aus allen Events bauen, mit eigenem Checkpoint. Ergebnis prüfen, dann die UI umschalten. Die alte View bleibt bis dahin aktiv.

Szenario: Ein Bug hat eine Woche lang falsche Beträge als Events gespeichert. Was tun Sie?

Events nicht ändern. Compensating Events schreiben oder einen Upcaster für die betroffenen Versionen bauen. Danach Projektionen neu bauen und Ergebnisse mit einem Parity-Check prüfen.
