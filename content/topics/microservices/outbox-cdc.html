Outbox Pattern und Change Data Capture

Kern: Das Transactional Outbox Pattern schreibt Geschäftsdaten und ausgehendes Event in einer lokalen Transaktion. Das Event landet in einer Outbox-Tabelle, nicht direkt im Broker. Ein Relay oder Change Data Capture (CDC) bringt es danach zum Broker. So löst es das Dual-Write-Problem: DB und Broker sind nie dauerhaft uneinig.

1. Wo sitzt die Outbox?

  1. Order Service schreibt die Bestellung und das Event in einer DB-Transaktion.
  2. orders enthält die Geschäftsdaten. outbox enthält die Events als Zeilen.
  3. Der Relay liest neue Outbox-Zeilen. Entweder per Polling oder aus dem WAL (Write-Ahead Log, das Änderungsprotokoll der DB).
  4. Der Relay publiziert das Event nach Kafka.
  5. Der Consumer verarbeitet es idempotent, denn der Relay kann doppelt senden.

2. Die Reise eines Events (die Geschichte zum Merken)

  1. Commit: Der Service schreibt Bestellung und Outbox-Zeile in einer Transaktion. Beide sind da oder keine.
  2. Lesen: Der Polling Publisher fragt die Tabelle regelmässig ab. CDC mit Debezium liest stattdessen das WAL.
  3. Publish: Der Relay sendet das Event nach Kafka. Key ist die Aggregate-ID. So landen Events einer Bestellung in derselben Partition.
  4. Merken: Der Relay merkt sich den Fortschritt: Debezium speichert den Offset (Position im WAL), Polling setzt sent = 1.
  5. Crash dazwischen: Das Event ist in Kafka, der Fortschritt nicht gespeichert. Nach dem Neustart sendet der Relay es nochmal.
  6. Folge: Die Outbox garantiert at-least-once, nicht exactly-once. Die Event-ID macht Duplikate erkennbar.

3. Beispiel: Dual Write gegen Outbox

broker = []                     # steht für Kafka

# A) Dual Write: DB-Commit, dann Crash vor dem Publish
with db: db.execute("INSERT INTO orders VALUES (1, 120)")
raise Crash("process killed")
broker.append({"type": "OrderCreated", "id": 1})      # wird nie erreicht

# B) Dual Write: erst Publish, dann scheitert der DB-Commit
broker.append({"type": "OrderCreated", "id": 2})
with db:
    db.execute("INSERT INTO orders VALUES (2, 80)")
    raise Crash("constraint violation, rollback")

# C) Outbox: Crash in der Transaktion
with db:
    db.execute("INSERT INTO orders VALUES (3, 50)")
    db.execute("INSERT INTO outbox(id,aggregatetype,aggregateid,type,payload) VALUES (?,?,?,?,?)", ...)
    raise Crash("process killed before commit")

# D) Outbox-Relay: Publish, dann Crash vor "sent=1", Neustart
for eid, ... in db.execute("SELECT ... FROM outbox WHERE sent=0 ORDER BY rowid"):
    broker.append({"id": eid, ...})
    raise Crash("relay killed after publish")           # beim 2. Lauf: UPDATE outbox SET sent=1
A) dual write: DB commit, then crash before publish
    process killed
    orders=1 events=0  -> order without event
B) dual write: publish, then DB commit fails
    constraint violation, rollback
    orders=0 events=1  -> ghost event
C) outbox: crash inside the transaction
    process killed before commit
    orders=0 outbox=0  -> both or nothing
D) outbox: commit, relay publishes, crashes before marking sent
    relay killed after publish
    orders=1 events=['e-4', 'e-4']  -> at-least-once, duplicate
    consumer dedupes by event id: applied=1

Echte Ausgabe, Python 3.12 + SQLite (Simulation: eine Python-Liste steht für Kafka, eine Exception für den Prozessabsturz).

  1. A: Die Bestellung existiert, das Event nie. Andere Services erfahren nichts davon.
  2. B: Das Event ist draussen, die Bestellung nicht. Das ist ein Ghost Event: Andere reagieren auf etwas, das es nicht gibt.
  3. C: Mit Outbox rollt die DB beides zurück. Es gibt weder Bestellung noch Event.
  4. D: Der Relay sendet das Event zweimal. Der Consumer erkennt das Duplikat an der Event-ID e-4 und wendet es nur einmal an.

Debezium-Konfiguration (Kafka Connect, PostgreSQL):

-- Outbox-Tabelle im Order Service (Spaltennamen = Debezium-Standard)
CREATE TABLE outbox (
  id            uuid PRIMARY KEY,
  aggregatetype varchar(255) NOT NULL,   -- bestimmt das Topic
  aggregateid   varchar(255) NOT NULL,   -- wird der Kafka-Key
  type          varchar(255) NOT NULL,   -- z. B. OrderCreated
  payload       jsonb
);
-- postgresql.conf: wal_level = logical

{
  "name": "orders-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "plugin.name": "pgoutput",
    "database.hostname": "orders-db",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/secrets/db.properties:password}",
    "database.dbname": "orders",
    "topic.prefix": "orders",
    "table.include.list": "public.outbox",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregatetype",
    "transforms.outbox.route.topic.replacement": "outbox.event.${routedByValue}",
    "transforms.outbox.table.field.event.key": "aggregateid"
  }
}

Konfiguration nach Debezium-Doku (Outbox Event Router); hier nicht ausgeführt, kein Kafka vorhanden. Die letzten zwei Router-Zeilen sind die Standardwerte, nur zur Verdeutlichung.

  1. EventRouter ist eine SMT (Single Message Transformation). Sie macht aus einer Outbox-Zeile ein sauberes Event.
  2. aggregatetype = order ergibt das Topic outbox.event.order.
  3. aggregateid wird der Kafka-Key. Das sichert die Reihenfolge pro Bestellung.
  4. Die id ist die eindeutige Event-ID. Laut Doku dient sie z. B. zum Entfernen von Duplikaten.

4. Details, die Interviewer fragen

  1. Dual-Write-Problem: Ein Service schreibt in zwei Systeme ohne gemeinsame Transaktion. Ein Crash dazwischen lässt sie dauerhaft uneinig.
  2. Warum kein 2PC mit Kafka: Kafka nimmt nicht an XA-Transaktionen mit einer Datenbank teil. Die Outbox braucht nur die lokale DB-Transaktion.
  3. Polling Publisher: Ein Polling Publisher fragt SELECT … WHERE sent = 0 in Abständen ab. Einfach, aber Last auf der DB und Verzögerung durch das Intervall.
  4. Transaction Log Tailing: CDC liest das Änderungsprotokoll der DB: WAL bei PostgreSQL, Binlog bei MySQL. Debezium macht das als Kafka-Connect-Connector.
  5. Reihenfolge: Kafka ordnet nur innerhalb einer Partition. Darum ist der Key die Aggregate-ID. Events verschiedener Aggregate haben keine feste Reihenfolge.
  6. Reihenfolge beim Polling: Zwei parallele Transaktionen committen in anderer Reihenfolge als ihre IDs. Ein Poller kann so eine Zeile überspringen. CDC liest in Commit-Reihenfolge.
  7. Mehrere Poller: Laufen zwei Relay-Instanzen, senden sie dieselbe Zeile doppelt. Lösung: Leader-Wahl oder SELECT … FOR UPDATE SKIP LOCKED.
  8. Aufräumen: Beim Polling löscht ein Job gesendete Zeilen. Mit Debezium kann man die Zeile in derselben Transaktion gleich wieder löschen: Das WAL enthält das INSERT trotzdem. Der Event Router ignoriert DELETEs.
  9. Replication Slot: PostgreSQL hält das WAL, bis Debezium es gelesen hat. Steht der Connector, wächst das WAL und füllt die Platte.
  10. Inbox Pattern: Das Inbox Pattern ist das Gegenstück beim Consumer. Er speichert die Event-ID in einer Inbox-Tabelle, in derselben Transaktion wie seine Änderung. Duplikate scheitern am Primary Key.
  11. CDC ohne Outbox: Debezium kann auch Geschäftstabellen direkt streamen. Dann wird das interne Schema zum öffentlichen Vertrag. Die Outbox trennt beides.
  12. Payload-Design: Das Event enthält, was Consumer brauchen, und ist versioniert. Ein Schema Registry (Avro, JSON Schema) hilft gegen Brüche.

  • Outbox vs Event Sourcing: Beim Event Sourcing sind die Events selbst die Daten. Dort gibt es kein Dual Write. Die Outbox ergänzt ein normales Tabellenmodell.
  • Outbox vs Listen-to-yourself: Der Service publiziert zuerst und reagiert selbst auf sein Event. Das vermeidet Dual Write, macht den Service aber vom Broker abhängig.
  • Outbox vs Kafka-Transaktionen: Kafka-Transaktionen gelten nur innerhalb von Kafka. Sie schliessen keine externe DB ein.

6. In der Produktion

  1. Platte voll durch WAL: Der Debezium-Connector steht, der Replication Slot hält das WAL. Lösung: Alarm auf Slot-Grösse, max_slot_wal_keep_size setzen.
  2. Wenig Verkehr, WAL wächst trotzdem: Andere Tabellen schreiben viel, die Outbox kaum. Der Slot-Fortschritt bleibt stehen. Lösung: Debezium Heartbeat (heartbeat.interval.ms).
  3. Outbox-Tabelle wächst endlos: Niemand löscht gesendete Zeilen. Lösung: sofort löschen (CDC) oder Aufräum-Job (Polling).
  4. Doppelte Events nach Neustart: Der Relay sendet erneut. Lösung: idempotente Consumer oder Inbox.
  5. Falsche Reihenfolge: Events einer Bestellung landen in verschiedenen Partitionen. Lösung: Aggregate-ID als Key.
  6. Failover der DB: Nach einem Wechsel zur Replica fehlt eventuell der Replication Slot. Lösung: Slot-Failover der DB nutzen (PostgreSQL 17+ unterstützt synchronisierte Failover-Slots) oder neu snapshotten.

7. Diagnose: Werkzeuge und Kennzahlen

  • Outbox-Rückstand (Polling): SELECT count(*), min(created_at) FROM outbox WHERE sent = 0;
  • Replication Slots: SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) FROM pg_replication_slots;
  • Connector-Status: curl http://connect:8083/connectors/orders-outbox/status über die Kafka-Connect-REST-API.
  • Debezium-Metriken (JMX): MilliSecondsBehindSource zeigt, wie weit CDC hinterherhinkt.
  • Topic ansehen: kafka-console-consumer.sh --topic outbox.event.order --property print.key=true --from-beginning.
  • Consumer Lag: kafka-consumer-groups.sh --describe --group billing.

8. Senior-Punkte

  1. Jeder Dual Write ist ein Bug, der nur auf den richtigen Crash wartet.
  2. Outbox heisst at-least-once. Idempotente Consumer sind Pflicht, nicht optional.
  3. Die Outbox ist ein öffentlicher Vertrag. Events werden bewusst entworfen und versioniert, nicht aus Tabellen kopiert.
  4. CDC ist Betrieb. Replication Slots, WAL-Grösse und Connector-Status gehören ins Monitoring.
  5. Einfach starten: Polling reicht für wenig Last. CDC lohnt sich bei Volumen oder Latenz-Anforderungen.
  6. Reihenfolge nur pro Aggregat versprechen. Globale Reihenfolge kostet Parallelität.

10. Fallen

  • „Die Outbox gibt exactly-once.“ → Falsch. Sie gibt at-least-once. Duplikate löst der Consumer.
  • „Erst Kafka senden, dann DB schreiben, ist sicher.“ → Falsch. Scheitert die DB, gibt es ein Ghost Event.
  • „@Transactional deckt auch kafkaTemplate.send() ab.“ → Falsch. Die DB-Transaktion schliesst Kafka nicht ein.
  • „Debezium braucht keine Wartung.“ → Falsch. Ein stehender Connector füllt über den Replication Slot die Platte.
  • „Kafka hält alle Events in Reihenfolge.“ → Falsch. Nur innerhalb einer Partition.

11. Fragen

Was ist das Dual-Write-Problem?

Ein Service schreibt in DB und Broker ohne gemeinsame Transaktion. Ein Crash dazwischen lässt beide dauerhaft uneinig: Daten ohne Event oder Event ohne Daten.

Was ist das Transactional Outbox Pattern?

Daten und Event werden in einer lokalen Transaktion geschrieben, das Event in eine Outbox-Tabelle. Ein Relay publiziert es danach zum Broker.

Welche Zustellgarantie gibt die Outbox?

At-least-once. Ein Relay-Crash nach dem Senden führt zu einem Duplikat.

Was ist ein Polling Publisher?

Ein Job fragt die Outbox regelmässig nach ungesendeten Zeilen ab, sendet sie und markiert sie als gesendet.

Was ist Change Data Capture?

CDC liest das Änderungsprotokoll der DB, bei PostgreSQL das WAL, und macht daraus Events. Debezium ist das bekannteste Werkzeug.

Polling oder CDC – was wählen Sie?

Polling bei wenig Last und einfachem Betrieb. CDC bei viel Volumen, niedriger Latenz oder strenger Reihenfolge.

Was macht der Debezium Outbox Event Router?

Eine SMT, die Outbox-Zeilen in Events umbaut. Das Topic kommt aus aggregatetype, der Key aus aggregateid, der Inhalt aus payload.

Welche Spalten hat die Debezium-Outbox-Tabelle standardmässig?

id, aggregatetype, aggregateid, type und payload.

Wie sichern Sie die Reihenfolge der Events?

Die Aggregate-ID als Kafka-Key. Alle Events eines Aggregats landen in derselben Partition und bleiben in Reihenfolge.

Warum kann ein Poller Events überspringen?

Parallele Transaktionen committen in anderer Reihenfolge als ihre IDs. Liest der Poller „alles nach ID X“, fehlt eine später committete kleinere ID.

Wie räumen Sie die Outbox auf?

Polling: Job löscht gesendete Zeilen. CDC: Zeile in derselben Transaktion gleich wieder löschen. Das WAL enthält das INSERT trotzdem.

Was ist ein Replication Slot und warum ist er gefährlich?

PostgreSQL hält das WAL, bis der Slot-Consumer es gelesen hat. Steht Debezium, wächst das WAL und füllt die Platte.

Was ist das Inbox Pattern?

Der Consumer speichert die Event-ID in einer Inbox-Tabelle, in derselben Transaktion wie seine Änderung. Duplikate scheitern am Primary Key.

Warum nicht einfach Kafka-Transaktionen?

Sie gelten nur innerhalb von Kafka. Eine externe Datenbank ist nicht Teil davon.

Warum nicht CDC direkt auf der orders-Tabelle?

Dann wird das interne Schema zum öffentlichen Vertrag. Jede Spaltenänderung bricht Consumer. Die Outbox entkoppelt beides.

Hilft @Transactional in Spring gegen Dual Write?

Nein. Die DB-Transaktion umfasst Kafka nicht. Ein Rollback nach dem Senden lässt ein Ghost Event zurück.

Wie verhindern Sie Doppelsendungen mit mehreren Relay-Instanzen?

Leader-Wahl, sodass nur einer pollt. Oder SELECT … FOR UPDATE SKIP LOCKED, sodass jede Zeile nur einer Instanz gehört.

Was gehört in den Payload eines Outbox-Events?

Was Consumer brauchen, mit Event-ID, Typ und Version. Keine internen Tabellenstrukturen. Schema Registry gegen Brüche.

Was ist der Unterschied zwischen Outbox und Event Sourcing?

Beim Event Sourcing sind die Events die Daten selbst. Die Outbox ergänzt ein normales Tabellenmodell um ausgehende Events.

Szenario: Die Datenbank-Platte läuft voll, obwohl die Tabellen klein sind. Was prüfen Sie?

pg_replication_slots: Ein inaktiver Debezium-Slot hält das WAL. Connector-Status prüfen und reparieren. Danach max_slot_wal_keep_size und Alarm auf Slot-Grösse.

Szenario: Billing hat für manche Bestellungen nie ein Event bekommen. Die Bestellungen sind in der DB. Woran liegt es?

Wahrscheinlich Dual Write: DB-Commit, dann Crash vor dem Senden. Fix: Transactional Outbox. Bestehende Lücken per Abgleich-Job nachsenden.

Szenario: Ein Consumer sieht OrderShipped vor OrderCreated. Was ist falsch?

Die Events liegen in verschiedenen Partitionen, z. B. ohne Key oder mit wechselndem Key. Fix: Aggregate-ID als Key. Beim Polling zusätzlich in Commit-Reihenfolge lesen oder auf CDC wechseln.
