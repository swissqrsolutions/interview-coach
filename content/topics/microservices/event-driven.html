Event-Driven Architecture: Events, Commands, Event-Design

Microservices · Tier 1 · Quellen: Martin Fowler „What do you mean by ‚Event-Driven‘?“, CloudEvents Spec 1.0.2, Apache Kafka Doku (Partitions, Ordering, Producer Idempotence), Confluent Schema Registry Doku (Compatibility Types), microservices.io (Saga, Transactional Outbox), Azure Architecture Center (Event-driven architecture style, Choreography pattern)

Kern: Eine Event-Driven Architecture ist ein Stil, bei dem Services über Events kommunizieren, also Meldungen über etwas, das passiert ist. Sie löst das Problem der engen Kopplung: Der Sender kennt seine Empfänger nicht. Neue Empfänger kommen dazu, ohne den Sender zu ändern. Der Preis ist Eventual Consistency, also Daten, die erst nach kurzer Zeit überall gleich sind.

1. Wo sitzen Events im System?

  1. Der Producer (Order Service) speichert seine Daten und das Event in einer DB-Transaktion. Das Event steht in einer Outbox-Tabelle.
  2. Ein Relay (z. B. Debezium oder ein Poller) schreibt das Event aus der Outbox in den Broker.
  3. Der Broker speichert Events in einem Topic. Ein Topic ist in Partitionen geteilt. Nur innerhalb einer Partition gilt eine feste Reihenfolge.
  4. Jeder interessierte Service liest als eigene Consumer Group. Jede Gruppe bekommt alle Events.
  5. Der Producer weiss nicht, wer liest. Ein neuer Consumer wie Analytics braucht keine Änderung am Producer.

2. Die Reise einer Bestellung (die Geschichte zum Merken)

  1. Ein Command kommt an. Der Client schickt PlaceOrder. Ein Command ist ein Auftrag an genau einen Empfänger. Er darf abgelehnt werden.
  2. Order entscheidet. Der Order Service prüft und speichert. Dann schreibt er das Event OrderPlaced in die Outbox.
  3. Das Event ist eine Tatsache. Ein Event ist in der Vergangenheit benannt und unveränderlich. Niemand kann es ablehnen.
  4. Viele reagieren. Payment und Stock lesen OrderPlaced unabhängig voneinander. Keiner wartet auf den anderen.
  5. Kette ohne Dirigent. Payment veröffentlicht PaymentDone, Shipping reagiert darauf. Das ist Choreografie: jeder Service kennt nur seine Events.
  6. Etwas scheitert. Stock meldet StockFailed. Payment reagiert mit einer Rückbuchung. Das ist eine Kompensation in einer Saga, weil es keine verteilte Transaktion gibt.

Echte Ausgabe, Python 3.12 (Simulation eines partitionierten Logs, kein Kafka; Seed 3).

  1. Mit Key: Alle Events einer Bestellung landen in derselben Partition. Die Reihenfolge pro Bestellung bleibt. Null Probleme.
  2. Ohne Key: Die Events einer Bestellung liegen in drei Partitionen. Parallele Consumer lesen sie in falscher Reihenfolge. Sechs Fehler bei neun Events.
  3. Schiefe Verteilung: Mit nur drei Keys bleibt Partition 2 leer. Ein Key mit viel Last erzeugt eine Hot Partition.
  4. Tolerant Reader: Der alte Consumer ignoriert das neue Feld currency. So bricht ein neues optionales Feld keinen Consumer.

4. Details, die Interviewer fragen

  1. Event, Command, Query: Ein Event meldet eine Tatsache in der Vergangenheit (OrderPlaced), an beliebig viele Empfänger. Ein Command verlangt eine Aktion (PlaceOrder), an genau einen Empfänger. Eine Query fragt Daten ab und ändert nichts.
  2. Event Notification: Das Event enthält nur die ID und den Typ. Der Empfänger ruft beim Sender die Details ab. Kleine Events, aber Rückkopplung und mehr Last beim Sender.
  3. Event-Carried State Transfer: Das Event enthält alle nötigen Daten. Der Empfänger hält eine lokale Kopie. Er funktioniert auch, wenn der Sender down ist. Preis: grössere Events, doppelte Daten.
  4. Event Sourcing: Der Zustand ist die Liste der Events. Den aktuellen Zustand erhält man durch Abspielen (Replay). Das ist ein Speichermuster innerhalb eines Service, kein Integrationsmuster.
  5. Domain Event vs Integration Event: Ein Domain Event lebt innerhalb eines Bounded Context. Ein Integration Event ist der öffentliche Vertrag nach aussen. Interne Events nicht ungefiltert veröffentlichen.
  6. Event-Design: Name im Präteritum und fachlich (OrderCancelled, nicht OrderUpdated). Mit eventId, Zeitpunkt, Version und Aggregat-ID. Keine internen DB-Strukturen.
  7. CloudEvents: CloudEvents ist eine CNCF-Spezifikation für Event-Metadaten. Pflichtattribute: id, source, specversion, type. source + id ist eindeutig. Azure Event Grid unterstützt es nativ.
  8. Reihenfolge: Kafka garantiert die Reihenfolge nur pro Partition. Der Key bestimmt die Partition. Darum alle Events eines Aggregats mit dessen ID als Key senden.
  9. Mehr Partitionen später: Wächst die Anzahl Partitionen, zeigt ein Key auf eine andere Partition. Alte und neue Events eines Keys liegen dann getrennt. Darum Partitionen früh grosszügig planen.
  10. Zustellung: Die Regel ist at-least-once, also mindestens einmal. Duplikate kommen vor. Der Consumer muss idempotent sein, z. B. über eine Tabelle verarbeiteter eventIds.
  11. Transactional Outbox: Das Muster löst das Dual-Write-Problem: DB schreiben und Event senden sind zwei Systeme. Die Outbox macht daraus eine DB-Transaktion. Ein Relay sendet danach.
  12. Schema-Evolution: Neue Felder optional mit Default hinzufügen. Felder nie umbenennen oder Typen ändern. Eine Schema Registry prüft die Regeln beim Deployment.
  13. Kompatibilität: BACKWARD: neue Consumer lesen alte Events (Confluent-Standard). FORWARD: alte Consumer lesen neue Events. FULL: beides. TRANSITIVE prüft gegen alle früheren Versionen, nicht nur die letzte.
  14. Breaking Change: Ein neues Topic oder ein neuer Typ mit Version (order.placed.v2). Eine Zeit lang beide Versionen parallel publizieren.
  15. Choreografie vs Orchestrierung: Bei Choreografie reagiert jeder Service auf Events, ohne Zentrale. Bei Orchestrierung sendet ein Orchestrator Commands und kennt den Ablauf. Choreografie koppelt lose, ist aber schwer zu überblicken.
  16. Dead Letter Queue: Eine DLQ nimmt Events auf, die nach mehreren Versuchen scheitern. So blockiert ein kaputtes Event (Poison Message) nicht die ganze Partition.

5. Vergleich

  • Synchron (REST/gRPC): sofortige Antwort, einfache Fehlerbehandlung. Aber zeitliche Kopplung: Ist der Empfänger down, scheitert der Aufruf.
  • Asynchron mit Events: lose Kopplung, Puffer bei Lastspitzen. Aber Eventual Consistency, schwereres Debugging, Duplikate.
  • Event Notification vs Event-Carried State Transfer: kleine Events mit Rückruf gegen grosse Events mit lokaler Kopie.
  • Event Sourcing vs CRUD: vollständige Historie und Replay gegen Einfachheit. Event Sourcing nur, wenn die Historie fachlich wichtig ist.
  • Kafka / Event Hub: ein Log, Events bleiben gespeichert, Replay möglich, Reihenfolge pro Partition.
  • RabbitMQ / Service Bus Queue: eine Queue, Nachricht weg nach Bestätigung. Gut für Commands und Arbeitsverteilung.
  • Azure Event Grid: Push-basiertes Routing von diskreten Events, z. B. „Blob erstellt“. Kein Log für Replay.

6. In der Produktion

  1. Event verloren nach DB-Commit: Der Service schreibt die DB, stürzt vor dem Senden ab. Lösung: Transactional Outbox.
  2. Doppelte Verarbeitung: Ein Consumer stürzt nach der Arbeit, aber vor dem Offset-Commit ab. Das Event kommt wieder. Lösung: idempotenter Consumer mit eventId-Tabelle.
  3. Falsche Reihenfolge: Events ohne Key oder mit wechselndem Key. Lösung: Aggregat-ID als Key. Oder Versionsnummer im Event, ältere Events verwerfen.
  4. Consumer bricht nach Producer-Deployment: Ein Feld wurde umbenannt. Lösung: Schema Registry mit Kompatibilitätsprüfung in CI, nur additive Änderungen.
  5. Poison Message blockiert Partition: Ein Event wirft immer eine Exception. Lösung: begrenzte Retries, dann DLQ, Alarm auf DLQ.
  6. Consumer Lag wächst: Der Consumer ist langsamer als der Producer. Lösung: mehr Partitionen und Consumer-Instanzen, Verarbeitung beschleunigen. Mehr Consumer als Partitionen bringt nichts.
  7. Niemand versteht den Ablauf: Zehn Services reagieren in Ketten aufeinander. Lösung: Event-Katalog (z. B. AsyncAPI), Tracing über Events, bei langen Abläufen Orchestrierung.

7. Diagnose: Werkzeuge und Metriken

  • Consumer Lag: kafka-consumer-groups.sh --bootstrap-server … --describe --group shipping zeigt Offset, Log-End und Lag pro Partition.
  • Event Hub: Metriken IncomingMessages, OutgoingMessages, ThrottledRequests im Azure Monitor.
  • Event Grid: Metriken DeliverySuccessCount, DeliveryAttemptFailCount, DeadLetteredCount.
  • DLQ-Grösse: Alarm, sobald die DLQ wächst.
  • Tracing: traceparent in Message-Headern verbindet Producer- und Consumer-Spans.
  • Schema Registry: POST /compatibility/subjects/<subject>/versions/latest prüft ein neues Schema vor dem Deployment.
  • Outbox-Tabelle: Anzahl unveröffentlichter Zeilen als Metrik. Wächst sie, hängt das Relay.

8. Senior-Punkte

  1. Ein Event ist ein öffentlicher Vertrag. Es braucht Versionierung, Dokumentation und einen Owner, wie eine REST-API.
  2. Events nicht als versteckte Commands nutzen. SendEmailRequested an genau einen Empfänger ist ein Command. Dann besser eine Queue.
  3. Idempotenz ist Pflicht. At-least-once ist der Normalfall. Exactly-once gilt nur innerhalb von Kafka, nicht für Seiteneffekte wie E-Mails.
  4. Reihenfolge nur dort, wo sie zählt. Pro Aggregat ja, global fast nie. Globale Ordnung kostet Parallelität.
  5. Choreografie für kurze Abläufe, Orchestrierung für lange. Ab etwa vier Schritten mit Kompensation wird ein Orchestrator klarer.
  6. Eventual Consistency mit dem Business klären. Die UI muss zeigen, dass etwas „in Bearbeitung“ ist.

10. Fallen

  • „Kafka garantiert die Reihenfolge.“ → Nur pro Partition. Ohne Key gibt es keine Ordnung pro Aggregat.
  • „Mit Kafka bekomme ich exactly-once.“ → Nur innerhalb von Kafka (Transaktionen, Read-Process-Write). Externe Seiteneffekte brauchen Idempotenz.
  • „Event Sourcing heisst, wir nutzen Kafka.“ → Falsch. Event Sourcing ist ein Speichermuster. Kafka ist ein Transport.
  • „OrderUpdated mit allen Feldern ist ein gutes Event.“ → Schwach. Der Consumer muss raten, was passiert ist. Fachliche Events sind besser.
  • „Mehr Consumer machen es schneller.“ → Nur bis zur Anzahl Partitionen. Weitere Consumer bleiben untätig.
  • „Ein Feld umbenennen ist harmlos.“ → Falsch. Für alte Consumer ist es Löschen plus Hinzufügen, also ein Breaking Change.

11. Fragen

Was ist eine Event-Driven Architecture?

Services kommunizieren über Events, also Meldungen über Geschehenes. Der Sender kennt die Empfänger nicht. Das koppelt lose.

Event vs Command vs Query?

Event: Tatsache in der Vergangenheit, an viele. Command: Auftrag an einen, darf abgelehnt werden. Query: Abfrage ohne Änderung.

Wie benennen Sie Events?

Fachlich und im Präteritum: OrderPlaced, PaymentFailed. Nicht technisch wie OrderTableUpdated.

Event Notification vs Event-Carried State Transfer?

Notification enthält nur ID und Typ, der Empfänger fragt nach. State Transfer enthält alle Daten, der Empfänger hält eine Kopie und ist unabhängig vom Sender.

Was ist Event Sourcing?

Der Zustand wird als Folge von Events gespeichert. Der aktuelle Zustand entsteht durch Replay. Snapshots beschleunigen das.

Domain Event vs Integration Event?

Domain Events bleiben im Bounded Context. Integration Events sind der öffentliche, stabile Vertrag nach aussen.

Was ist CloudEvents?

Eine CNCF-Spezifikation für Event-Metadaten. Pflicht: id, source, specversion, type. Optional z. B. time, subject, datacontenttype.

Wie sichern Sie die Reihenfolge in Kafka?

Gleicher Key für alle Events eines Aggregats. Dann landen sie in derselben Partition. Dazu idempotenter Producer gegen Vertauschung bei Retries.

Was passiert, wenn man Partitionen hinzufügt?

Keys werden neu verteilt. Neue Events eines Keys landen in einer anderen Partition als alte. Die Reihenfolge pro Key kann kurz brechen.

Was ist at-least-once und was folgt daraus?

Ein Event kommt mindestens einmal, manchmal doppelt. Der Consumer muss idempotent sein.

Wie bauen Sie einen idempotenten Consumer?

Die eventId in einer Tabelle speichern, in derselben Transaktion wie die Änderung. Bekannte IDs überspringen. Oder Operationen so bauen, dass Wiederholung nichts ändert.

Was ist das Dual-Write-Problem?

DB und Broker sind zwei Systeme ohne gemeinsame Transaktion. Einer kann gelingen, der andere scheitern.

Wie funktioniert die Transactional Outbox?

Daten und Event in einer DB-Transaktion speichern, das Event in einer Outbox-Tabelle. Ein Relay oder CDC (Debezium) sendet es danach an den Broker.

Wie entwickeln Sie ein Event-Schema weiter?

Nur optionale Felder mit Default hinzufügen. Nichts umbenennen oder umtypisieren. Eine Schema Registry prüft die Kompatibilität.

BACKWARD vs FORWARD Compatibility?

BACKWARD: neue Consumer lesen alte Daten. FORWARD: alte Consumer lesen neue Daten. FULL: beides.

Was ist ein Tolerant Reader?

Ein Consumer, der unbekannte Felder ignoriert und nur liest, was er braucht. So überlebt er additive Änderungen.

Choreografie vs Orchestrierung?

Choreografie: Services reagieren auf Events, keine Zentrale. Orchestrierung: ein Orchestrator steuert mit Commands. Choreografie ist loser, Orchestrierung übersichtlicher.

Was ist eine Saga?

Eine Folge lokaler Transaktionen über mehrere Services. Scheitert ein Schritt, machen Kompensationen die vorherigen rückgängig.

Was ist eine Dead Letter Queue?

Ein Ablageort für Events, die nach mehreren Versuchen scheitern. So blockiert eine Poison Message nicht den Rest.

Kafka vs RabbitMQ?

Kafka ist ein Log mit Aufbewahrung, Replay und Reihenfolge pro Partition. RabbitMQ ist ein Broker mit Queues, gut für Commands und Routing.

Event Grid vs Event Hub?

Event Grid verteilt einzelne Events per Push, z. B. Blob-Ereignisse. Event Hub ist ein Log für grosse Datenströme mit Partitionen, ähnlich Kafka.

Wann ist Event-Driven die falsche Wahl?

Wenn der Nutzer sofort eine konsistente Antwort braucht. Oder bei einfachen Abläufen, wo ein REST-Aufruf reicht.

Szenario: Kunden sehen bezahlte Bestellungen als „offen“. Woran liegt es?

Möglich: falsche Reihenfolge (OrderPaid vor OrderPlaced, kein Key) oder Consumer Lag. Prüfen: Key, Partitionen, Lag. Lösung: Aggregat-ID als Key, Versionsnummer im Event.

Szenario: Nach einem Deployment des Producers stürzen zwei Consumer ab. Was tun Sie?

Rollback des Producers. Ursache meist ein Breaking Change im Schema. Danach Schema Registry mit Kompatibilitätsprüfung in CI und nur additive Änderungen.

Szenario: Ab und zu fehlt ein Event, obwohl die DB-Daten da sind. Warum?

Dual-Write: Die DB wurde geschrieben, das Senden scheiterte. Lösung: Transactional Outbox mit Relay oder CDC.
