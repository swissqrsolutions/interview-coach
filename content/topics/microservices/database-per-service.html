Database per Service und Datenkonsistenz

Kern: Database per Service ist ein Muster, bei dem jeder Service seine Daten privat hält. Andere Services lesen und schreiben diese Daten nur über seine API oder seine Events. Das löst die Kopplung über das Schema: Ein Team ändert seine Tabellen, ohne andere zu brechen. Der Preis: keine JOINs und keine ACID-Transaktion über Services, sondern Eventual Consistency.

1. Wo sitzt die Datenbank im System?

  1. Client oder API Gateway ruft die Services über ihre APIs auf.
  2. Jeder Service hat eine eigene Datenbank oder mindestens ein eigenes Schema.
  3. Nur der Besitzer-Service darf seine Tabellen lesen und schreiben.
  4. Braucht Order Daten von Customer, fragt er die API oder hört auf Events.
  5. Order kann eine lokale Kopie halten: customer_view. Das ist ein Read Model, also eine abgeleitete Lese-Tabelle.
  6. Der direkte Zugriff auf fremde Tabellen ist verboten. Er würde die Schemas wieder koppeln.

„Eigene Datenbank“ heisst nicht immer eigener Server. microservices.io nennt drei Stufen: private Tabellen pro Service, Schema pro Service, Datenbank-Server pro Service. Entscheidend ist die Regel: kein fremder Zugriff.

2. Die Reise einer Kundenänderung (die Geschichte zum Merken)

  1. Lokale Änderung: Customer Service ändert den Namen in seiner eigenen DB. Das ist eine normale lokale ACID-Transaktion.
  2. Event schreiben: In derselben Transaktion schreibt er ein Event CustomerRenamed in eine Outbox-Tabelle. So geht kein Event verloren.
  3. Broker: Ein Relay oder CDC (Change Data Capture) bringt das Event in ein Kafka Topic.
  4. Consumer: Order Service liest das Event. Er verarbeitet es idempotent, also Doppelte schaden nicht.
  5. Read Model: Order aktualisiert customer_view. Ab jetzt zeigt Order den neuen Namen.
  6. Inkonsistenz-Fenster: Zwischen Schritt 1 und 5 sind die Daten verschieden. Das System wird irgendwann konsistent, nicht sofort.

3. Beispiel: JOIN, API Composition und Read Model

orders = sqlite3.connect("orders.db"); customers = sqlite3.connect("customers.db")
# orders.db: orders, customer_view   customers.db: customer

# 1) JOIN über Service-Datenbanken
orders.execute("SELECT o.id, c.name FROM orders o JOIN customer c ON ...")

# 2) API Composition: zwei Aufrufe, JOIN im Speicher
names = dict(customers.execute("SELECT id, name FROM customer"))   # GET /customers
for oid, cid, total in orders.execute("SELECT id, customer_id, total FROM orders"):
    print(oid, names[cid], total)

# 3) Read Model per Event
customers.execute("UPDATE customer SET name='Ana Muster' WHERE id=1")
print(read_model_name())       # Event noch nicht verarbeitet
apply(("CustomerRenamed", 1, "Ana Muster"))
print(read_model_name())
1) JOIN across service databases
   error: no such table: customer
2) API composition (two calls, join in memory)
   order 10  Ana  total=120
   order 11  Ben  total=80
   order 12  Ana  total=40
3) read model via events (eventual consistency)
   source of truth : Ana Muster
   read model before event: Ana
   read model after  event: Ana Muster
   local JOIN now works: [(10, 'Ana Muster'), (11, 'Ben'), (12, 'Ana Muster')]

Echte Ausgabe, Python 3.12 + SQLite (Simulation: zwei SQLite-Dateien stehen für zwei Service-Datenbanken, ein Funktionsaufruf für den Broker).

  1. Ein JOIN über zwei Service-Datenbanken geht nicht. Die Tabelle customer existiert in der Order-DB nicht.
  2. API Composition ruft beide Services auf und verbindet die Daten im Speicher. Das funktioniert für kleine Mengen.
  3. Nach dem Update zeigt die Quelle schon „Ana Muster“, das Read Model noch „Ana“. Das ist das Inkonsistenz-Fenster.
  4. Nach dem Event ist das Read Model aktuell. Jetzt geht ein lokaler JOIN in der Order-DB.

4. Details, die Interviewer fragen

  1. Warum eigene Daten: Ein Service ist nur unabhängig deploybar, wenn sein Schema privat ist. Sonst bricht eine Spaltenänderung andere Services.
  2. Shared Database: Die Shared Database ist ein Muster, bei dem alle Services dieselben Tabellen nutzen. Sie gibt ACID und JOINs, koppelt aber Schema, Deployments und Last.
  3. Polyglot Persistence: Jeder Service wählt die passende Technik. Beispiel: PostgreSQL für Bestellungen, Elasticsearch für Suche, Redis für Sessions.
  4. Datenduplizierung: Services halten bewusst Kopien fremder Daten. Die Kopie ist read-only und wird per Event aktualisiert. Es gibt genau einen Besitzer (Source of Truth).
  5. API Composition: Ein API Composer ruft mehrere Services und verbindet die Antworten im Speicher. Problem: Latenz, Verfügbarkeit und grosse Datenmengen.
  6. CQRS Read Model: CQRS (Command Query Responsibility Segregation) trennt Schreib- und Lesemodell. Ein Read Model sammelt Events mehrerer Services in einer Abfrage-Tabelle.
  7. Eventual Consistency: Eventual Consistency heisst: Ohne neue Änderungen sind alle Kopien irgendwann gleich. Es gibt keine Garantie, wann.
  8. Konsistenz über Services: Schreiben über mehrere Services braucht eine Saga. Eine Saga ist eine Folge lokaler Transaktionen mit Kompensationen.
  9. Kein 2PC: Two-Phase Commit (2PC) koordiniert eine Transaktion über mehrere Datenbanken. Viele Broker und NoSQL-Datenbanken unterstützen es nicht. Es blockiert bei Ausfall des Koordinators.
  10. Referenzielle Integrität: Fremdschlüssel über Services gibt es nicht. Der Service speichert nur die ID und prüft sie per API oder Event.
  11. Reporting: Reports brauchen Daten aller Services. Lösung: Events oder CDC in ein Data Warehouse oder einen Lakehouse. Nie direkt auf die Service-DBs.
  12. Read-your-writes: Ein Nutzer sieht seine eigene Änderung im Read Model eventuell nicht sofort. Lösung: aus der Quelle lesen oder eine Version mitgeben.

5. Vergleich

  • Database per Service: lose Kopplung, unabhängige Deployments. Preis: keine JOINs, Eventual Consistency, Sagas.
  • Shared Database: einfache ACID-Transaktionen und JOINs. Preis: Schema-Kopplung, ein Team blockiert andere, eine DB als Engpass.
  • Schema pro Service, ein Server: günstiger Kompromiss. Rechte pro Schema verhindern fremden Zugriff. Last bleibt geteilt.
  • API Composition: immer aktuell, einfach. Langsam bei vielen Services, fällt aus, wenn ein Service ausfällt.
  • CQRS Read Model: schnelle lokale Abfragen, auch bei Ausfall der Quelle. Preis: veraltete Daten, mehr Infrastruktur.
  • Database per Tenant: eine DB pro Kunde, nicht pro Service. Ziel ist Isolation zwischen Kunden, nicht zwischen Teams.

6. In der Produktion

  1. Heimliche Shared Database: Ein Team liest „nur kurz“ fremde Tabellen. Später bricht eine Migration den anderen Service. Lösung: DB-Rechte pro Service, eigener DB-User.
  2. Verteilter Monolith: Jeder Request ruft fünf Services synchron. Ein Ausfall stoppt alles. Lösung: Read Models per Event statt Kettenaufrufe.
  3. Veraltete Kopie: Ein Consumer hängt, das Read Model ist Stunden alt. Lösung: Consumer Lag überwachen und alarmieren.
  4. Verlorene Events: Der Service schreibt in die DB und sendet danach ein Event. Ein Crash dazwischen verliert das Event. Lösung: Transactional Outbox.
  5. Doppelte Events: Broker liefern at-least-once, also eventuell mehrfach. Lösung: idempotente Consumer.
  6. Reporting auf Produktions-DBs: Grosse Abfragen bremsen die Services. Lösung: CDC oder Events in ein Data Warehouse.
  7. Migration vom Monolithen: Die gemeinsame DB lässt sich nicht an einem Tag teilen. Lösung: Tabelle für Tabelle übernehmen, erst Schreiben, dann Lesen umstellen.

7. Diagnose: Werkzeuge und Kennzahlen

  • DB-Rechte prüfen: In PostgreSQL zeigt \dp in psql, welche Rolle welche Tabelle lesen darf.
  • pg_stat_activity: SELECT usename, application_name FROM pg_stat_activity; zeigt, welche Anwendung auf welche DB zugreift.
  • Consumer Lag: kafka-consumer-groups.sh --describe --group order-service zeigt, wie weit ein Read Model hinterherhinkt.
  • Distributed Tracing (OpenTelemetry): zeigt, wie viele Services ein Request synchron aufruft.
  • Abgleich-Job: Ein Reconciliation Job vergleicht Quelle und Kopie und meldet Abweichungen.
  • Metrik „Alter des Read Models“: Zeit seit dem letzten verarbeiteten Event.

8. Senior-Punkte

  1. Der Service-Schnitt folgt den Daten. Müssen zwei Services oft gemeinsam schreiben, ist der Schnitt wahrscheinlich falsch.
  2. Jedes Datum hat genau einen Besitzer. Alle anderen halten nur read-only Kopien.
  3. Eventual Consistency ist eine Business-Frage. Man fragt die Fachseite: Wie alt darf die Anzeige sein?
  4. Schema pro Service reicht oft. Ein eigener Server pro Service kostet viel Betrieb.
  5. Reporting ist ein eigener Datenfluss. Events oder CDC gehen in ein Warehouse mit eigenem Modell.
  6. Erst modularer Monolith, dann Trennung. Getrennte Schemas im Monolithen machen die spätere Aufteilung einfach.

Das ist Isolation pro Mandant, das gleiche Prinzip wie Database per Service: kein fremder Zugriff, Schema-Änderungen kontrolliert pro Datenbank.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Database per Service heisst ein DB-Server pro Service.“ → Falsch. Eigenes Schema oder eigene Tabellen mit Rechten reichen oft.
  • „Wir lösen Konsistenz mit 2PC über alle Services.“ → Schlecht. Viele Systeme können es nicht, und es blockiert bei Ausfällen. Besser: Saga.
  • „Datenduplizierung ist immer schlecht.“ → Falsch. Kopien sind gewollt, solange es genau einen Besitzer gibt.
  • „Eventual Consistency heisst, die Daten sind manchmal falsch.“ → Ungenau. Sie sind zeitweise veraltet und holen auf.
  • „Für einen Report lese ich direkt alle Service-DBs.“ → Falsch. Das koppelt wieder alle Schemas. Besser: Events oder CDC in ein Warehouse.

11. Fragen

Was ist Database per Service?

Jeder Service hält seine Daten privat. Andere Services greifen nur über seine API oder seine Events darauf zu.

Welches Problem löst Database per Service?

Die Kopplung über das Schema. Ein Team kann seine Tabellen ändern und deployen, ohne andere Services zu brechen.

Was ist das Problem einer Shared Database?

Alle Services hängen am selben Schema. Eine Migration kann andere brechen. Last und Sperren eines Services treffen alle.

Wann ist eine Shared Database trotzdem in Ordnung?

Bei einem modularen Monolithen oder in einer Übergangsphase. Wichtig: klare Besitzer pro Tabelle und keine fremden Schreibzugriffe.

Muss jeder Service einen eigenen DB-Server haben?

Nein. Private Tabellen oder ein Schema pro Service mit eigenen Rechten reichen oft. Ein eigener Server bringt zusätzlich Last-Isolation.

Wie machen Sie einen JOIN über zwei Services?

Gar nicht direkt. Entweder API Composition im Speicher oder ein lokales Read Model, das per Event gefüllt wird.

Was ist API Composition?

Ein Composer ruft mehrere Services auf und verbindet die Antworten im Speicher. Einfach und aktuell, aber langsam und anfällig bei vielen Services.

Was ist ein CQRS Read Model?

Eine eigene Lese-Tabelle, die aus Events gebaut wird. Sie beantwortet Abfragen lokal und schnell, ist aber eventuell etwas veraltet.

Was ist Eventual Consistency?

Ohne neue Änderungen werden alle Kopien irgendwann gleich. Wann genau, ist nicht garantiert.

Wie erreichen Sie Konsistenz beim Schreiben über mehrere Services?

Mit einer Saga: lokale Transaktionen nacheinander, bei Fehler Kompensationen. Events zuverlässig mit dem Outbox Pattern senden.

Warum nicht einfach Two-Phase Commit?

Viele Broker und NoSQL-Datenbanken unterstützen kein 2PC. Es blockiert, wenn der Koordinator ausfällt. Es koppelt die Verfügbarkeit aller Teilnehmer.

Ist Datenduplizierung zwischen Services erlaubt?

Ja, als read-only Kopie. Es gibt genau einen Besitzer. Die Kopie wird per Event aktualisiert.

Wie ersetzen Sie Fremdschlüssel zwischen Services?

Der Service speichert nur die fremde ID. Gültigkeit prüft er per API oder über ein lokales Read Model.

Wie machen Sie Reporting über alle Services?

Events oder CDC fliessen in ein Data Warehouse oder einen Lakehouse. Dort gibt es ein eigenes Modell für Reports.

Was ist Polyglot Persistence?

Jeder Service wählt die passende Datenbank. Zum Beispiel relational für Bestellungen und eine Suchmaschine für Volltext.

Wie verhindern Sie, dass ein Team fremde Tabellen liest?

Eigener DB-User pro Service mit Rechten nur auf das eigene Schema. Zugriffe prüft man in pg_stat_activity.

Was ist ein verteilter Monolith?

Services sind getrennt deployt, aber eng gekoppelt, z. B. durch synchrone Kettenaufrufe oder eine gemeinsame DB. Man hat die Nachteile beider Welten.

Was ist Read-your-writes, und wie sichern Sie es?

Ein Nutzer sieht seine eigene Änderung sofort. Lösung: nach dem Schreiben aus der Quelle lesen oder auf eine Version im Read Model warten.

Wie teilen Sie die Datenbank eines Monolithen auf?

Schrittweise: Besitzer pro Tabelle festlegen, Zugriffe hinter APIs legen, Tabellen einzeln verschieben, Daten per CDC synchron halten.

Szenario: Die Bestellübersicht zeigt nach einer Namensänderung stundenlang den alten Namen. Was prüfen Sie?

Den Consumer Lag des Read-Model-Consumers. Hängt er an einer kaputten Nachricht? Dazu: Kommen die Events überhaupt im Topic an (Outbox, CDC)?

Szenario: Eine Migration im Customer Service bricht plötzlich den Billing Service. Was ist passiert, und was ändern Sie?

Billing liest direkt Customer-Tabellen: eine heimliche Shared Database. Lösung: Zugriff über API oder Events, eigene DB-Rechte pro Service.

Szenario: Das Management will einen Report über Bestellungen, Kunden und Zahlungen. Wie bauen Sie ihn?

Nicht per Abfrage auf alle Service-DBs. Events oder CDC aus jedem Service in ein Warehouse, dort ein eigenes Report-Modell. Aktualität mit der Fachseite klären.
