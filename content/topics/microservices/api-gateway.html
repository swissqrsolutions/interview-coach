API Gateway und BFF

Microservices · Tier 1 · Quellen: microservices.io (API Gateway / Backends for Frontends), Azure Architecture Center (Use API gateways in microservices, Gateway Routing, Gateway Aggregation, Gateway Offloading, Backends for Frontends pattern), Spring Cloud Gateway Reference (Server WebFlux: Route Predicate Factories, GatewayFilter Factories, RequestRateLimiter, TokenRelay), Microsoft Learn (API Management policies: validate-jwt, rate-limit-by-key, set-backend-service), Sam Newman (Backends For Frontends)

Kern: Ein API Gateway ist der einzige Eingang für Clients vor vielen Services. Es löst zwei Probleme: Clients müssen nicht jeden Service kennen, und Querschnittsaufgaben wie Auth, TLS und Rate Limiting liegen an einer Stelle. Ein BFF (Backend for Frontend) ist ein eigenes Gateway pro Client-Typ, z. B. Web und Mobile. Ein Gateway steuert den Verkehr von aussen nach innen (north-south), ein Service Mesh den Verkehr zwischen Services (east-west).

1. Wo sitzt das API Gateway?

  1. Clients: Web und Mobile brauchen unterschiedliche Daten und Formate.
  2. BFF: Jeder Client-Typ hat sein eigenes Backend. Das BFF formt Antworten genau für seinen Client. Es gehört meist dem Frontend-Team.
  3. API Gateway: Es nimmt alle Requests an, terminiert TLS, prüft Tokens, begrenzt Raten und leitet zum richtigen Service.
  4. Services: Sie sind von aussen nicht direkt erreichbar. Sie liegen in einem privaten Netz.
  5. Service Mesh: Verkehr zwischen Services läuft über Sidecars oder Node-Proxies. Das Mesh macht mTLS, Retries und Telemetrie.
  6. Oft gibt es nur Gateway oder nur BFFs. Beides zusammen ist auch üblich: BFFs hinter einem zentralen Gateway.

2. Die Reise eines Requests durch das Gateway (die Geschichte zum Merken)

  1. TLS: Der Request kommt über HTTPS an. Das Gateway entschlüsselt ihn (TLS Termination). Die Services sparen sich das Zertifikats-Handling.
  2. Route finden: Das Gateway vergleicht Pfad, Host, Header oder Methode mit seinen Predicates. /orders/42 passt zur Route „orders“. Keine Route: 404.
  3. Auth: Das Gateway prüft das JWT: Signatur, Ablauf, Audience. Fehlt es oder ist es falsch: 401.
  4. Rate Limit: Das Gateway zählt Requests pro Schlüssel, z. B. pro Benutzer oder Subscription. Zu viele: 429 Too Many Requests.
  5. Filter und Backend: Filter ändern den Request, z. B. Präfix entfernen oder Header setzen. Dann ruft das Gateway den Service mit Timeout. Backend kaputt: 502. Backend zu langsam: 504.
  6. Antwort: Response-Filter setzen Header, das Gateway loggt und misst. Der Client bekommt die Antwort.

3. Beispiel: ein Mini-Gateway mit Routing, Auth, Rate Limit und Aggregation

// drei Backends auf localhost: order 60 ms, customer 40 ms, product 50 ms
static Map<String, String> routes = Map.of(
    "/orders", "http://127.0.0.1:9001", "/customers", "http://127.0.0.1:9002",
    "/products", "http://127.0.0.1:9003");

static String handle(String path, String token, String client) {
  if (!"Bearer valid".equals(token)) return "401 Unauthorized";                   // Auth
  if (buckets.merge(client, 1, Integer::sum) > 3) return "429 Too Many Requests";  // 3 pro Client
  for (var r : routes.entrySet())
    if (path.startsWith(r.getKey()))
      return "200 " + get(r.getValue() + path.substring(r.getKey().length()));     // StripPrefix
  return "404 No route";
}
// Aggregation: nacheinander vs parallel mit CompletableFuture
String seq = get(order) + get(customer) + get(product);
var o = supplyAsync(() -> call(order)); var c = ...; var p = ...;
String par = o.join() + c.join() + p.join();

Echte Ausgabe, Java 17 (Simulation: drei com.sun.net.httpserver-Backends und ein selbst geschriebenes Gateway in einem Prozess, kein echtes Gateway-Produkt).

  1. Ohne Token bricht das Gateway mit 401 ab. Der Order-Service sieht den Request nie.
  2. Das Gateway entfernt das Präfix: Aus /orders/42 wird /42 beim Backend.
  3. Der 4. Request desselben Clients bekommt 429. Das Limit gilt pro Schlüssel (hier „web“).
  4. Für /invoices gibt es keine Route: 404.
  5. Aggregation nacheinander kostet die Summe (163 ms). Parallel kostet sie den langsamsten Aufruf (64 ms ≈ order mit 60 ms).

Dasselbe mit Spring Cloud Gateway (Server WebFlux):

spring:
  cloud:
    gateway:
      server:
        webflux:
          default-filters:
          - TokenRelay=                      # Access Token an Backends weitergeben
          routes:
          - id: orders
            uri: lb://order-service          # Load Balancing über Service Discovery
            predicates:
            - Path=/api/orders/**
            filters:
            - StripPrefix=1                  # /api/orders/42 -> /orders/42
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20
                redis-rate-limiter.requestedTokens: 1
                key-resolver: "#{@userKeyResolver}"
            - name: CircuitBreaker
              args:
                name: orders
                fallbackUri: forward:/fallback/orders

<policies>

4. Details, die Interviewer fragen

  1. Gateway Routing: Das Gateway leitet Requests nach Pfad, Host oder Header an Services. Clients kennen nur eine Adresse.
  2. Gateway Aggregation: Das Gateway ruft mehrere Services und baut eine Antwort. Das spart Round-Trips über langsame Mobilnetze.
  3. Gateway Offloading: Das Gateway übernimmt Querschnittsaufgaben: TLS, Auth, Rate Limiting, Caching, Kompression, Logging.
  4. BFF (Backend for Frontend): Ein BFF ist ein eigenes Backend pro Client-Typ. Es vermeidet ein „One size fits all“-API, das für keinen Client passt. Das Frontend-Team besitzt es.
  5. BFF und Security: Ein Web-BFF kann OAuth-Tokens serverseitig halten und dem Browser nur ein Session-Cookie geben. So liegen keine Tokens im Browser.
  6. Spring Cloud Gateway – Bausteine: Eine Route hat ID, Ziel-URI, Predicates (wann passt sie) und Filters (was passiert mit Request und Response).
  7. Spring Cloud Gateway – Varianten: Server WebFlux ist reaktiv auf Netty. Server Web MVC läuft auf Servlet, gut mit Virtual Threads. Beide nutzen dieselben Konzepte.
  8. RequestRateLimiter: Er nutzt einen Token Bucket in Redis. replenishRate = Tokens pro Sekunde, burstCapacity = maximale Tokens. Limit erreicht: 429. Findet der KeyResolver keinen Schlüssel, lehnt er standardmässig ab.
  9. TokenRelay: Der Filter TokenRelay gibt das OAuth2-Access-Token des Benutzers an das Backend weiter.
  10. Azure API Management (APIM): APIM ist ein verwaltetes Gateway mit Policies in vier Abschnitten: inbound, backend, outbound, on-error. Dazu kommen Products, Subscriptions (API-Keys) und ein Developer Portal.
  11. APIM Rate Limits: rate-limit-by-key zählt pro beliebigem Schlüssel und gibt 429 zurück. Die Zählung ist laut Doku nie ganz genau, weil sie verteilt ist. Sie zählt pro Gateway, nicht über alle Regionen. Im Consumption-Tier gibt es sie nicht.
  12. Rate Limit vs Quota: Ein Rate Limit schützt vor kurzen Spitzen (pro Sekunde, Minute). Eine Quota begrenzt das Volumen über lange Zeit (pro Monat).
  13. Gateway vs Service Mesh: Das Gateway regelt north-south: Clients zu Services, mit API-Management, Auth und Produkten. Das Mesh (Istio, Linkerd) regelt east-west: Service zu Service, mit mTLS, Retries, Traffic Shifting.
  14. Azure-Bausteine: Front Door ist globaler Eingang mit CDN und WAF. Application Gateway ist ein regionaler Layer-7-Load-Balancer mit WAF. APIM verwaltet APIs. Oft stehen sie hintereinander.
  15. Kubernetes: Ingress und die neuere Gateway API routen HTTP in den Cluster. Sie sind einfache Gateways ohne API-Management.

5. Vergleich

  • Direkte Client-zu-Service-Aufrufe: keine zusätzliche Komponente. Aber Clients kennen interne Adressen, jeder Service macht Auth selbst, viele Round-Trips.
  • Ein API Gateway: ein Eingang, zentrale Policies. Gefahr: wird Engpass und Sammelbecken für Logik.
  • BFF pro Client: passende APIs pro Client, Frontend-Team autonom. Preis: mehr Deployments, Code-Duplikation zwischen BFFs.
  • Service Mesh: Sicherheit und Resilienz zwischen Services, ohne Code-Änderung. Ersetzt kein Gateway für externe Clients.
  • Spring Cloud Gateway: Code und YAML im eigenen Repo, Teil der Spring-Welt, selbst betrieben.
  • Azure API Management: verwaltet, mit Developer Portal, Subscriptions, Analytics. Weniger flexibel bei eigener Logik, Kosten pro Tier.
  • GraphQL als BFF-Ersatz: Der Client wählt die Felder selbst. Das spart viele BFF-Endpunkte, bringt aber eigene Komplexität (Query-Kosten, Caching).

6. In der Produktion

  1. Gateway als Single Point of Failure: Fällt es aus, ist alles weg. Lösung: mehrere Instanzen, mehrere Zonen, Health Checks.
  2. Business-Logik im Gateway: Das Gateway wird ein neuer Monolith, den alle Teams ändern. Lösung: nur Querschnittsaufgaben ins Gateway, Fachlogik in Services oder BFFs.
  3. Falsche Timeouts: Gateway-Timeout kleiner als Backend-Zeit gibt 504, obwohl das Backend weiterarbeitet. Lösung: Timeouts von aussen nach innen abgestimmt setzen.
  4. Aggregation ohne Teilantwort: Ein langsamer Service macht die ganze Seite langsam. Lösung: parallel aufrufen, Timeout pro Aufruf, Teilantwort mit Fallback.
  5. Ungenaues Rate Limit: Jede Gateway-Instanz zählt allein. Lösung: zentraler Zähler (Redis) oder Limits pro Instanz bewusst einplanen.
  6. Auth nur am Gateway: Ein Angreifer im internen Netz umgeht es. Lösung: Services prüfen Tokens auch selbst (Zero Trust), oder mTLS im Mesh.
  7. BFF wird zum Monolithen: Ein BFF für alle Clients wächst. Lösung: ein BFF pro Client-Erlebnis, nicht pro Team-Wunsch.

7. Diagnose: Werkzeuge und Befehle

  • Spring Cloud Gateway Actuator: /actuator/gateway/routes zeigt alle aktiven Routen mit Predicates und Filtern (Endpoint muss freigegeben sein).
  • Micrometer-Metrik spring.cloud.gateway.requests: Dauer und Status pro Route.
  • Status-Codes lesen: 401/403 = Auth, 429 = Rate Limit, 502 = Backend-Fehler, 503 = kein Backend, 504 = Backend-Timeout.
  • APIM: Analytics im Portal, Application-Insights-Integration, Trace in der Test-Konsole zeigt jede Policy-Stufe.
  • Distributed Tracing: Das Gateway startet den Trace. Gateway-Zeit und Backend-Zeit getrennt ansehen.
  • curl -i -H "Authorization: Bearer …" https://api.example/orders/42: Header wie Retry-After oder X-RateLimit-Remaining prüfen.

8. Senior-Punkte

  1. Dünnes Gateway, schlaue Services. Ins Gateway gehören nur Querschnittsaufgaben.
  2. BFF gehört dem Frontend-Team. So ändert das Team API und UI zusammen, ohne Ticket an ein Backend-Team.
  3. Gateway und Mesh ergänzen sich. Gateway für north-south, Mesh für east-west.
  4. Defense in Depth: Auth am Gateway spart Last, ersetzt aber keine Prüfung im Service.
  5. Aggregation braucht Resilienz: parallel, Timeouts, Teilantworten, Circuit Breaker.
  6. Managed oder selbst betrieben ist eine Abwägung: APIM bringt Portal und Subscriptions, Spring Cloud Gateway bringt Code-Flexibilität und eigene Betriebslast.

10. Fallen

  • „Das Gateway macht Auth, also brauchen Services keine.“ → Falsch. Internes Netz ist kein Schutz. Services prüfen selbst oder nutzen mTLS.
  • „API Gateway und Service Mesh sind dasselbe.“ → Falsch. Gateway: north-south, API-Management. Mesh: east-west, mTLS, Resilienz.
  • „Ein BFF für alle Clients.“ → Das ist wieder ein allgemeines API. BFF heisst ein Backend pro Client-Typ.
  • „Aggregation im Gateway ist immer schneller.“ → Nur parallel und mit Timeouts. Nacheinander addieren sich die Latenzen.
  • „Rate Limiting zählt genau.“ → Falsch. Verteilt ist es fast immer ungefähr, auch laut APIM-Doku.
  • „Fachliche Regeln im Gateway sparen einen Service.“ → Das Gateway wird ein verteilter Monolith.

11. Fragen

Was ist ein API Gateway?

Der einzige Eingang für Clients vor vielen Services. Es routet Requests und übernimmt Querschnittsaufgaben wie Auth, TLS und Rate Limiting.

Welche Probleme löst ein API Gateway?

Clients kennen nur eine Adresse. Interne Services bleiben verborgen. Auth, Limits und Logging liegen zentral. Weniger Round-Trips durch Aggregation.

Was sind Gateway Routing, Aggregation und Offloading?

Routing: Requests an den richtigen Service. Aggregation: mehrere Aufrufe zu einer Antwort. Offloading: Querschnittsaufgaben vom Service ins Gateway.

Was ist ein BFF?

Ein Backend for Frontend: ein eigenes Backend pro Client-Typ, z. B. Web und Mobile. Es liefert genau die Daten, die dieser Client braucht.

Wann lohnt sich ein BFF?

Wenn Clients sehr unterschiedliche Daten brauchen oder ein Frontend-Team schnell und unabhängig ändern will.

Welche Nachteile haben BFFs?

Mehr Deployments und Betrieb. Logik kann sich zwischen BFFs doppeln. Gemeinsame Teile gehören dann in einen Service.

Wie hilft ein BFF bei der Sicherheit im Browser?

Das BFF hält OAuth-Tokens auf dem Server. Der Browser bekommt nur ein sicheres Session-Cookie.

Was ist eine Route in Spring Cloud Gateway?

ID, Ziel-URI, Predicates und Filters. Passt ein Request zu allen Predicates, laufen die Filter und der Request geht zur URI.

Was ist der Unterschied zwischen Predicate und Filter?

Ein Predicate entscheidet, ob eine Route passt, z. B. Path. Ein Filter ändert Request oder Response, z. B. StripPrefix.

Wie funktioniert der RequestRateLimiter?

Ein Token Bucket in Redis pro Schlüssel. replenishRate füllt nach, burstCapacity begrenzt Spitzen. Leer: 429.

Was macht der TokenRelay-Filter?

Er gibt das OAuth2-Access-Token des angemeldeten Benutzers an den Backend-Service weiter.

WebFlux oder Web MVC für Spring Cloud Gateway?

WebFlux ist reaktiv auf Netty und der Klassiker. Web MVC läuft auf Servlet, passt zu blockierendem Code und Virtual Threads.

Was ist Azure API Management?

Ein verwaltetes API Gateway mit Policies, Products, Subscriptions, Analytics und Developer Portal.

Welche Policy-Abschnitte hat APIM?

inbound, backend, outbound und on-error. Auth und Limits stehen meist in inbound.

Wie prüft APIM ein JWT?

Mit validate-jwt: OpenID-Konfiguration für die Schlüssel, Audience und Issuer prüfen. Fehler gibt 401.

Was ist der Unterschied zwischen Rate Limit und Quota?

Rate Limit begrenzt kurze Spitzen pro Sekunde oder Minute. Quota begrenzt das Volumen über lange Zeit.

Was ist der Unterschied zwischen API Gateway und Service Mesh?

Gateway: north-south, Clients zu Services, API-Management. Mesh: east-west, Service zu Service, mTLS, Retries, Telemetrie.

Was ist der Unterschied zwischen Gateway, Ingress und Load Balancer?

Ein Load Balancer verteilt Verkehr. Ein Ingress routet HTTP in einen Kubernetes-Cluster. Ein API Gateway kann zusätzlich Auth, Limits, Aggregation und API-Verwaltung.

Was bedeuten 502 und 504 am Gateway?

502: Das Backend antwortet falsch oder bricht ab. 504: Das Backend antwortet nicht vor dem Timeout.

Warum keine Fachlogik im Gateway?

Alle Teams müssten das Gateway ändern. Es wird zum Engpass und zum neuen Monolithen.

Wie macht man Aggregation robust?

Aufrufe parallel, Timeout pro Aufruf, Fallbacks und Teilantworten, Circuit Breaker pro Backend.

Brauchen Services noch Auth, wenn das Gateway prüft?

Ja. Zero Trust: Services prüfen Tokens selbst oder nutzen mTLS. Sonst ist das interne Netz offen.

Szenario: Die Mobile-App macht 7 Aufrufe für einen Screen und ist im Mobilnetz langsam. Was tun Sie?

Ein Mobile-BFF, das die 7 Aufrufe parallel serverseitig macht und eine kleine, passende Antwort liefert. Mit Timeouts und Teilantworten.

Szenario: Nach dem Einführen eines Gateways sehen Clients viele 504. Was prüfen Sie?

Timeouts von Gateway und Backend vergleichen, Backend-Latenz im Tracing ansehen, Connection-Pool des Gateways prüfen. Dann Timeouts abstimmen oder das Backend beschleunigen.

Szenario: Ein Partner überlastet Ihre API mit Batch-Abfragen. Wie schützen Sie die Services?

Rate Limit und Quota pro Subscription oder Client-ID am Gateway, 429 mit Retry-After. Für Batch-Bedarf eine eigene asynchrone Schnittstelle anbieten.
