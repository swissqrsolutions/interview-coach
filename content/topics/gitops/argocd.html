Argo CD: Sync, Prune, Self-Heal, Hooks, App of Apps

GitOps · Tier 1 · Quellen: argo-cd.readthedocs.io (stable: Automated Sync Policy, Sync Phases and Waves, Resource Health, ApplicationSet Generators, Secret Management, Upgrading 2.14 → 3.0), github.com/argoproj/argo-cd/releases (aktuell v3.6.2)

Kern: Argo CD ist ein GitOps-Controller für Kubernetes. Er vergleicht ständig den Soll-Zustand im Git-Repo mit dem Ist-Zustand im Cluster und gleicht Unterschiede an (Sync). So ist Git die einzige Quelle der Wahrheit, und manuelle Änderungen im Cluster werden erkannt und auf Wunsch zurückgedreht.

1. Wo sitzt Argo CD?

  1. Git-Repo: enthält den Soll-Zustand: Helm-Charts, Kustomize oder reines YAML.
  2. repo-server: klont das Repo und rendert Manifeste, z. B. wie helm template.
  3. application-controller: vergleicht gerenderte Manifeste mit dem Cluster. Er berechnet Sync-Status und Health und führt Syncs aus.
  4. argocd-server: API, Web-UI und CLI-Endpunkt. Auch für Git-Webhooks.
  5. applicationset-controller: erzeugt viele Applications aus Vorlagen.
  6. CRDs: Eine Application verbindet eine Quelle (Repo, Pfad, Revision) mit einem Ziel (Cluster, Namespace). Ein AppProject begrenzt, was eine Application darf.

2. Die Reise eines Git-Commits (die Geschichte zum Merken)

  1. Commit: Die CI-Pipeline setzt image.tag: 1842 in values.prod.yaml und committet.
  2. Refresh: Argo CD pollt das Repo alle 120 Sekunden plus bis zu 60 Sekunden Jitter. Mit einem Webhook geht es sofort.
  3. OutOfSync: Das gerenderte Deployment hat einen neuen Tag. Die Application ist OutOfSync.
  4. Sync: Mit automated startet der Sync selbst. Zuerst PreSync-Hooks (z. B. DB-Migration), dann Ressourcen nach Sync Waves, dann PostSync-Hooks.
  5. Health: Das Deployment ist Progressing, bis alle neuen Pods bereit sind. Danach Healthy.
  6. Drift: Jemand skaliert manuell auf 5 Replicas. Mit selfHeal stellt Argo CD nach dem Self-Heal-Timeout (Standard 5 s) den Git-Stand wieder her.
  7. Rollback: Bei automatischem Sync ist der Rollback-Knopf gesperrt. Der Weg zurück ist git revert.

3. Beispiel: eine Application mit Auto-Sync, Prune und Self-Heal

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: match-prod
  namespace: argocd
spec:
  project: match
  source:
    repoURL: https://dev.azure.com/org/match/_git/deploy
    targetRevision: main
    path: charts/match
    helm:
      valueFiles: [values.prod.yaml]
  destination:
    server: https://kubernetes.default.svc
    namespace: match
  syncPolicy:
    automated:
      prune: true        # aus Git entfernte Ressourcen löschen
      selfHeal: true     # manuelle Änderungen zurückdrehen
    syncOptions:
    - CreateNamespace=true
  ignoreDifferences:
  - group: batch
    kind: Job
    jsonPointers: [/spec/template]
$ argocd app get match-prod
Name:               argocd/match-prod
Sync Policy:        Automated (Prune)
Sync Status:        Synced to main (3f2a9c1)
Health Status:      Healthy

GROUP  KIND        NAMESPACE  NAME           STATUS  HEALTH   HOOK      MESSAGE
       Service     match      api            Synced  Healthy            service/api unchanged
apps   Deployment  match      api            Synced  Healthy            deployment.apps/api configured
batch  Job         match      create-buckets Succeeded       PostSync  job.batch/create-buckets created

$ git revert --no-edit 3f2a9c1 && git push      # Rollback
$ argocd app get match-prod | grep "Sync Status"
Sync Status:        Synced to main (8b04e7d)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Argo CD ist hier nicht installiert; Format nach Argo-CD-Doku, gekürzt.

  1. prune: true und selfHeal: true sind beide standardmässig aus. Man muss sie bewusst setzen.
  2. helm.valueFiles: Argo CD rendert das Chart mit der Prod-Datei. Es gibt keinen Helm-Release im Cluster.
  3. ignoreDifferences für Jobs: Ein Job-Template ist unveränderlich. Ohne Ausnahme wäre die App dauernd OutOfSync.
  4. Der PostSync-Hook legt Buckets an, nachdem alles Healthy ist.
  5. Nach git revert synchronisiert Argo CD den alten Stand. Die Historie zeigt beide Commits.

4. Details, die Interviewer fragen

  1. Sync-Status vs Health: Sync-Status sagt, ob Cluster und Git gleich sind (Synced / OutOfSync). Health sagt, ob die Ressource funktioniert (Healthy, Progressing, Degraded, Suspended, Missing, Unknown).
  2. Automated Sync: läuft nur, wenn die App OutOfSync ist. Mit automated.enabled: false lässt es sich explizit ausschalten.
  3. Prune: löscht Ressourcen, die aus Git entfernt wurden. Standard aus, damit ein Fehler im Repo nicht alles löscht. allowEmpty schützt zusätzlich vor einem leeren Soll-Zustand.
  4. Self-Heal: korrigiert Änderungen am Cluster, auch wenn Git gleich bleibt. Standard aus. Wartezeit über --self-heal-timeout-seconds (Standard 5 s).
  5. Refresh-Intervall: timeout.reconciliation in argocd-cm, Standard 120 s plus Jitter bis 60 s. Webhooks machen es sofort.
  6. Hooks: argocd.argoproj.io/hook: PreSync, Sync, PostSync, SyncFail, PreDelete, PostDelete, Skip. Ohne Delete-Policy gilt BeforeHookCreation.
  7. Sync Waves: argocd.argoproj.io/sync-wave, Standard 0, auch negativ. Reihenfolge: Phase, Wave, Kind (Namespaces zuerst), Name. Zwischen Waves 2 s Pause.
  8. Helm-Hooks in Argo CD: Argo CD übersetzt Helm-Hooks in eigene Hooks, z. B. pre-install → PreSync. Helm selbst läuft nicht.
  9. App of Apps: Eine Eltern-Application zeigt auf einen Ordner mit Application-YAMLs. So bootstrapt man viele Apps. Die Health von Application-Objekten wird seit 1.8 nicht mehr bewertet; dafür braucht man einen eigenen Lua-Health-Check.
  10. ApplicationSet: erzeugt Applications aus Generatoren: List, Cluster, Git, Matrix, Merge, SCM Provider, Pull Request, Cluster Decision Resource, Plugin. Typisch: eine App pro Cluster oder pro Ordner.
  11. Rollback: Die UI kann auf eine alte Revision zurück, aber nicht bei Auto-Sync. In GitOps ist git revert der saubere Weg.
  12. Argo CD 3.x: Tracking per Annotation statt Label ist Standard. Feinere RBAC: update/delete gelten nicht mehr automatisch für Unter-Ressourcen. Repos nur noch als Secrets, nicht in argocd-cm.

5. Vergleich

  • Argo CD: starke UI, Application-CRD, ApplicationSets, Multi-Cluster von einer Instanz.
  • Flux: modulare Controller (Source, Kustomize, Helm), kein zentrales UI, Helm-Releases bleiben echte Helm-Releases.
  • Pipeline mit helm upgrade (Push): einfach, aber die Pipeline braucht Cluster-Rechte und erkennt keinen Drift.
  • App of Apps vs ApplicationSet: App of Apps ist manuell und flexibel. ApplicationSet erzeugt viele ähnliche Apps aus einer Vorlage.
  • Auto-Sync vs manueller Sync: Auto für dev/test und für reife Prod-Setups. Manuell, wenn ein Mensch den Zeitpunkt bestimmen muss.

6. In der Produktion

  1. App ist immer OutOfSync: Ein Controller oder Webhook ändert Felder (z. B. HPA setzt replicas, Jobs sind unveränderlich). Lösung: ignoreDifferences, bei HPA replicas nicht im Manifest setzen.
  2. Prune löscht zu viel: Ein falscher Pfad im Repo, und alles verschwindet. Lösung: allowEmpty: false, Review, Prune=false auf kritischen Ressourcen (PVCs).
  3. Hotfix per kubectl edit verschwindet: Self-Heal dreht ihn zurück. Lösung: Fix immer über Git.
  4. Sync hängt an einem Hook: PostSync-Job läuft nicht durch. Lösung: Job-Logs, backoffLimit, Timeout, Delete-Policy.
  5. Secrets im Repo: Lösung laut Argo-CD-Doku: Secrets im Ziel-Cluster erzeugen, z. B. External Secrets Operator. Injection-Plugins werden nicht empfohlen, weil Argo CD dann Klartext in Redis cacht.
  6. Langsame Syncs bei vielen Apps: Lösung: Webhooks statt Polling, Controller-Sharding, Repo-Server skalieren.

7. Diagnose: Werkzeuge und Befehle

  • argocd app get <app>: Sync-Status, Health, Ressourcen und Hooks.
  • argocd app diff <app>: zeigt den genauen Unterschied Git ↔ Cluster.
  • argocd app history <app>: welche Git-Revision wann synchronisiert wurde.
  • argocd app sync <app> --dry-run: Sync testen.
  • kubectl -n argocd logs deploy/argocd-repo-server: Render-Fehler (Helm, Kustomize).
  • kubectl -n argocd logs statefulset/argocd-application-controller: Sync- und Diff-Fehler.
  • Prometheus-Metriken wie argocd_app_info (Labels für Sync und Health) für Alerts.

8. Senior-Punkte

  1. Git ist die Wahrheit. Keine manuellen Cluster-Änderungen; Self-Heal setzt das technisch durch.
  2. Prune und Self-Heal bewusst einschalten, mit Schutz: Review, allowEmpty: false, Ausnahmen für Daten-Ressourcen.
  3. Rollback ist git revert. Nachvollziehbar, reviewbar, und der Agent bleibt synchron.
  4. Reihenfolge mit Waves und Hooks modellieren: CRDs und Namespaces früh, Migration als PreSync, Smoke-Test als PostSync.
  5. AppProjects als Sicherheitsgrenze: erlaubte Repos, Ziel-Namespaces und Ressourcen-Typen pro Team.
  6. Secrets nie durch Argo CD schleusen. External Secrets im Ziel-Cluster ist die empfohlene Art.

10. Fallen

  • „Auto-Sync löscht entfernte Ressourcen.“ → Falsch. Nur mit prune: true.
  • „Auto-Sync dreht manuelle Änderungen zurück.“ → Falsch. Nur mit selfHeal: true.
  • „Synced heisst, die App läuft.“ → Falsch. Synced heisst nur „gleich wie Git“. Ob sie läuft, sagt Health.
  • „Rollback mache ich mit dem Knopf in der UI.“ → Nicht bei Auto-Sync. Und ohne Git-Änderung ist der Stand sofort wieder weg. git revert.
  • „Argo CD führt helm install aus.“ → Falsch. Es rendert nur und wendet selbst an; helm list zeigt nichts.
  • „Argo CD erkennt Änderungen sofort.“ → Nur mit Webhook. Sonst bis ca. 3 Minuten Polling.

11. Fragen

Was ist Argo CD?

Ein GitOps-Controller für Kubernetes. Er gleicht den Cluster ständig mit dem Soll-Zustand in Git ab.

Was ist eine Application?

Eine CRD, die eine Quelle (Repo, Pfad, Revision) mit einem Ziel (Cluster, Namespace) verbindet, plus Sync-Policy.

Was ist ein AppProject?

Eine Gruppe von Applications mit Grenzen: erlaubte Repos, Ziel-Cluster, Namespaces und Ressourcen-Typen.

Was ist der Unterschied zwischen Sync-Status und Health?

Sync-Status: Cluster gleich Git oder nicht. Health: Ressource funktioniert oder nicht.

Welche Health-Status gibt es?

Healthy, Progressing, Degraded, Suspended, Missing, Unknown.

Was macht prune?

Es löscht Ressourcen im Cluster, die aus Git entfernt wurden. Standardmässig aus.

Was macht selfHeal?

Es synchronisiert erneut, wenn sich der Cluster ändert, auch ohne neuen Commit. Manuelle Änderungen werden zurückgedreht.

Wie schnell erkennt Argo CD einen Commit?

Polling alle 120 s plus bis zu 60 s Jitter. Mit Git-Webhook sofort.

Welche Hooks gibt es?

PreSync, Sync, PostSync, SyncFail, PreDelete, PostDelete und Skip.

Was sind Sync Waves?

Eine Annotation mit einer Zahl. Niedrige Waves werden zuerst angewendet und müssen healthy sein, bevor die nächste startet. Standard ist 0.

Was ist App of Apps?

Eine Application, deren Quelle weitere Application-YAMLs enthält. So bootstrapt man einen Cluster mit vielen Apps.

Was ist ein ApplicationSet?

Eine Vorlage, die mit Generatoren viele Applications erzeugt, z. B. eine pro Cluster oder pro Ordner im Repo.

Welche Generatoren kennen Sie?

List, Cluster, Git, Matrix, Merge, SCM Provider, Pull Request, Cluster Decision Resource, Plugin.

Wie machen Sie einen Rollback?

git revert des schlechten Commits. Argo CD synchronisiert den alten Stand. Der UI-Rollback geht bei Auto-Sync nicht.

Wozu ignoreDifferences?

Um Felder zu ignorieren, die andere setzen oder die unveränderlich sind, z. B. Job-Templates oder von HPA gesetzte Replicas.

Wie behandelt Argo CD Helm-Charts?

Es rendert sie wie helm template und wendet die Manifeste selbst an. Helm-Hooks werden zu Argo-Hooks.

Wie gehen Sie mit Secrets um?

Nicht im Repo. External Secrets Operator oder ähnliche im Ziel-Cluster, Quelle Vault oder Key Vault. Argo CD empfiehlt das ausdrücklich.

Was hat sich in Argo CD 3.0 geändert?

Tracking per Annotation als Standard, feinere RBAC für Unter-Ressourcen, Repos nur noch als Secrets, Status-Felder werden standardmässig beim Diff ignoriert.

Szenario: Die App springt dauernd zwischen Synced und OutOfSync. Was prüfen Sie?

argocd app diff: Welches Feld ändert sich? Oft HPA-Replicas, Defaults vom API Server oder ein Mutating Webhook. Lösung: ignoreDifferences oder Feld aus dem Manifest nehmen.

Szenario: Ein Kollege hat per kubectl ein Memory-Limit erhöht, eine Minute später ist es weg. Warum?

Self-Heal hat den Git-Stand wiederhergestellt. Die Änderung muss per Pull Request ins Repo.

Szenario: Ein neues Release bricht Produktion. Wie rollen Sie zurück?

Den Commit im Deploy-Repo mit git revert umkehren und pushen. Argo CD synchronisiert, Health prüfen. Danach Ursache analysieren.
