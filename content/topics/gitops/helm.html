Helm: Charts, Values, Templates, Releases

Kern: Helm ist der Paketmanager für Kubernetes. Ein Chart ist ein Paket aus Go-Templates und Standard-Values, und Helm rendert daraus Kubernetes-Manifeste. Jede Installation ist ein Release mit nummerierten Revisionen, darum gibt es Upgrade und Rollback als Einheit.

Antwort-Muster

Frage: Was ist Helm, und wie läuft ein Upgrade ab?

  1. Mechanismus: Helm rendert ein Chart mit Values zu Manifesten und schickt sie an den API Server. Jede Revision speichert es als Secret im Namespace des Releases.
  2. Zahl: Ein Rollback von Revision 4 auf 3 erzeugt Revision 5 mit dem Inhalt von 3. Der Standard-Timeout ist 5 Minuten.
  3. Trade-off: Helm macht Pakete parametrisierbar. Dafür sind Go-Templates schwer lesbar, und CRDs aktualisiert Helm nicht.
  4. Produktion: Mit --rollback-on-failure rolle ich ein gescheitertes Upgrade automatisch zurück. Migrationen laufen als pre-upgrade Hook.

1. Die Reise eines Upgrades

  1. Values mergen: helm upgrade api ./chart -f values.prod.yaml --set image.tag=1842. Helm nimmt values.yaml, dann die Datei, dann --set. Der letzte Wert gewinnt.
  2. Rendern: Die Template Engine füllt {{ .Values.image.tag }} und baut das YAML.
  3. Hook: Ein Job mit helm.sh/hook: pre-upgrade migriert die Datenbank. Erst danach geht es weiter.
  4. Apply: Helm 4 nutzt für neue Releases Server-Side Apply. Alte Helm-3-Releases bleiben beim Client-Side-Verfahren (Three-Way-Merge).
  5. Wait: Mit --wait wartet Helm, bis Deployments bereit sind. Sonst gilt der Release sofort als deployed.
  6. Neue Revision: Revision 4 wird gespeichert. Scheitert sie, macht helm rollback api 3 eine neue Revision 5 mit dem Stand von 3.

2. Aufbau

  1. Chart: ein Ordner oder .tgz mit Chart.yaml (Name, Version, apiVersion: v2), values.yaml und templates/.
  2. Values: Standardwerte im Chart. Umgebungs-Dateien wie values.prod.yaml überschreiben sie.
  3. Helm CLI: rendert Templates mit Values zu YAML und schickt es an den API Server. Es gibt keinen Server-Teil im Cluster (kein Tiller mehr).
  4. Release-Secret: Helm speichert jede Revision eines Releases als Secret im Namespace des Releases.
  5. OCI Registry: Charts liegen versioniert in einer Registry, z. B. Azure Container Registry (oci://).

3. Details, die Interviewer fragen

  1. Chart-Aufbau: Ein Chart hat Chart.yaml, values.yaml und templates/. Dazu kommen charts/ für Abhängigkeiten und crds/. Optional prüft values.schema.json die Values.
  2. Chart-Version vs App-Version: version ist die Version des Charts (SemVer). appVersion ist die Version der Anwendung darin.
  3. Values-Reihenfolge: Zuerst gilt die values.yaml des Charts. Dann folgen Werte des Eltern-Charts. Dann folgen die -f-Dateien, die rechte gewinnt. Zuletzt gilt --set.
  4. Template-Funktionen: Es sind Go Templates plus Sprig. Wichtig sind include (benannte Templates aus _helpers.tpl), toYaml mit nindent, default, required, quote, tpl und lookup.
  5. Release: Ein Release ist eine Installation eines Charts unter einem Namen in einem Namespace. Jede Änderung ist eine neue Revision. Sie liegt als Secret.
  6. Upgrade-Flags: --reuse-values übernimmt alte Values. --reset-values nimmt die Chart-Standards. --reset-then-reuse-values kombiniert beides. Bei Chart-Upgrades ist das ein häufiger Fehler.
  7. Hooks: Es gibt pre-install, post-install, pre-upgrade, post-upgrade, pre-delete, post-delete, pre-rollback, post-rollback und test. helm.sh/hook-weight setzt die Reihenfolge. helm.sh/hook-delete-policy steuert das Löschen. Der Standard ist before-hook-creation.
  8. Hook-Ressourcen gehören nicht zum Release: helm uninstall löscht sie nicht. Darum nutzt man eine Delete-Policy oder ttlSecondsAfterFinished am Job.
  9. CRDs: CRDs im Ordner crds/ installiert Helm nur beim ersten Mal. Es aktualisiert und löscht sie nicht. Grosse Operatoren liefern CRDs darum oft separat.
  10. Helm 4 (aktuell 4.3): Neue Releases nutzen Server-Side Apply. Die Status-Prüfung läuft mit kstatus. Es gibt optionale WebAssembly-Plugins und Install per OCI-Digest. --atomic heisst jetzt --rollback-on-failure. --force heisst jetzt --force-replace. Charts mit apiVersion: v2 laufen unverändert. Charts v3 sind noch experimentell.
  11. Helm 3 Ende: Helm 3 bekam Bugfixes bis 8. Juli 2026. Security-Fixes gab es bis 11. November 2026. Heute ist Helm 4 die gepflegte Linie.
  12. --wait in Helm 4: Ohne Flag wartet Helm nur auf Hooks (hookOnly). Mit --wait nutzt es den Watcher (kstatus). --timeout ist standardmässig 5 Minuten.

4. Fallen

  • „Helm braucht Tiller im Cluster.“ → Veraltet. Tiller gab es nur in Helm 2. Helm 3 und 4 sind reine Clients.
  • „helm rollback stellt die alte Revision wieder her.“ → Fast: Es erzeugt eine neue Revision mit dem alten Inhalt.
  • „helm uninstall räumt alles weg.“ → Falsch. Hook-Ressourcen, CRDs und Ressourcen mit resource-policy: keep bleiben.
  • „Helm aktualisiert CRDs im crds/-Ordner.“ → Falsch. Nur beim ersten Install.
  • „--atomic gibt es nicht mehr.“ → Es heisst in Helm 4 --rollback-on-failure; der alte Name warnt nur.
  • „Mit ArgoCD sehe ich den Release in helm list.“ → Falsch. ArgoCD rendert nur und verwaltet die Objekte selbst.

5. Selbsttest

Warum?

Warum include statt template?

include gibt einen String zurück, den man weiterverarbeiten kann, z. B. mit nindent. template kann man nicht in eine Pipe geben.

Wie funktioniert helm rollback?

Es nimmt den Inhalt einer alten Revision und spielt ihn als neue Revision ein.

Was macht --rollback-on-failure?

Scheitert das Upgrade, rollt Helm automatisch auf die letzte erfolgreiche Revision zurück. In Helm 3 hiess das --atomic.

Wie innen?

Was ist Helm?

Der Paketmanager für Kubernetes. Er rendert Charts aus Templates und Values zu Manifesten und verwaltet Releases mit Revisionen.

Was ist ein Chart?

Ein Paket mit Chart.yaml, values.yaml, templates/ und optional Abhängigkeiten und CRDs.

Was ist ein Release?

Eine Installation eines Charts unter einem Namen in einem Namespace. Jede Änderung ist eine neue Revision.

Wo speichert Helm Releases?

Als Secrets im Namespace des Releases, eine pro Revision.

In welcher Reihenfolge werden Values angewendet?

values.yaml des Charts, Werte vom Eltern-Chart, dann -f-Dateien (die rechte gewinnt), dann --set.

Was macht helm template?

Es rendert das Chart lokal zu YAML, ohne Cluster und ohne Release.

Was ist _helpers.tpl?

Eine Datei mit benannten Templates (define), z. B. für Namen und Labels. Man nutzt sie mit include.

Was sind Helm Hooks?

Ressourcen mit helm.sh/hook-Annotation, die zu bestimmten Zeitpunkten laufen, z. B. pre-upgrade für Datenbank-Migrationen.

Was ist die Standard-Delete-Policy für Hooks?

before-hook-creation: Die alte Hook-Ressource wird gelöscht, bevor eine neue erstellt wird.

Zahlen

Ist Helm 3 noch unterstützt?

Nein, nicht mehr regulär: Security-Fixes gab es bis 11. November 2026. Neue Arbeit sollte auf Helm 4 laufen.

Wie viele Revisionen hat ein Release nach einem Rollback von Revision 4 auf 3?

Fünf. Der Rollback erzeugt eine neue Revision 5 mit dem Inhalt von Revision 3.

Wie lang ist der Standard-Timeout bei Helm 4?

5 Minuten, einstellbar mit --timeout.

Vergleich

Helm oder Kustomize?

Helm für parametrisierte, verteilte Pakete mit Releases. Kustomize für einfache Overlays auf echtes YAML ohne Templates. Oft kombiniert.

Was ist der Unterschied zwischen version und appVersion?

version ist die Chart-Version, appVersion die Version der Anwendung im Chart.

Was ist neu in Helm 4?

Server-Side Apply für neue Releases, kstatus-basiertes Warten, WebAssembly-Plugins, Install per OCI-Digest, umbenannte Flags. Charts v2 laufen weiter.

Produktion

Szenario: Ein Upgrade hängt in pending-upgrade. Was tun Sie?

helm history ansehen, dann helm rollback auf die letzte gute Revision. Danach Ursache suchen, z. B. abgebrochene Pipeline oder Timeout.

Szenario: Nach dem Chart-Update fehlen neue Default-Werte. Warum?

Wahrscheinlich --reuse-values: alte Values werden übernommen, neue Defaults nicht. Lösung: Values vollständig aus Dateien oder --reset-then-reuse-values.

Szenario: Der DB-Migration-Job soll vor jedem Deployment laufen. Wie lösen Sie das?

Als Hook (pre-install, pre-upgrade) mit Delete-Policy before-hook-creation und hook-succeeded. In ArgoCD als PreSync-Hook.

Design

Wie geht Helm mit CRDs um?

CRDs in crds/ werden nur beim ersten Install angelegt, nie aktualisiert oder gelöscht.

Wie verteilen Sie Charts?

Als OCI-Artefakt in einer Registry wie ACR, versioniert und am besten per Digest referenziert.

Wie validieren Sie Values?

Mit values.schema.json im Chart. helm lint und install prüfen die Values dagegen.

Was geht kaputt, wenn man sich auf helm uninstall zum Aufräumen verlässt?

Hook-Ressourcen, CRDs und Ressourcen mit resource-policy keep bleiben stehen. Darum Delete-Policy nutzen und CRDs getrennt verwalten.

Mehr

Gerüst

  • Warum? Ein parametrisiertes Paket statt vieler YAML-Kopien. Upgrade und Rollback als Einheit.
  • Wie innen? Values mergen (values.yaml, -f, --set) → rendern → Hook → apply → wait → neue Revision als Secret. Kein Tiller, nur Client.
  • Zahlen Rollback bei Revision 4 erzeugt Revision 5. Default-Timeout 5 Minuten. Helm 3 Security-Fixes bis 11. November 2026.
  • Vergleich Helm vs Kustomize. version vs appVersion. Helm 4 vs Helm 3.
  • Produktion Upgrade hängt in pending-upgrade. --reuse-values verliert neue Defaults. Hook-Ressourcen bleiben nach uninstall.
  • Design CRDs in crds/ nur beim ersten Install. values.schema.json validiert Values. Charts als OCI per Digest.

Beispiel: ein Chart rendern, upgraden, zurückrollen

# templates/deployment.yaml (Auszug)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "api.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: api
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
        resources: {{- toYaml .Values.resources | nindent 10 }}

# values.yaml: replicaCount: 1, image.repository: myacr.azurecr.io/api
# values.prod.yaml: replicaCount: 3
$ helm template api ./chart -f values.prod.yaml --set image.tag=1842 | grep -E "replicas|image:"
  replicas: 3
        image: "myacr.azurecr.io/api:1842"

$ helm upgrade --install api ./chart -n match -f values.prod.yaml --set image.tag=1842 --wait --rollback-on-failure
Release "api" has been upgraded. Happy Helming!
NAME: api
NAMESPACE: match
STATUS: deployed
REVISION: 4

$ helm history api -n match
REVISION  STATUS      CHART      APP VERSION  DESCRIPTION
3         superseded  api-0.7.0  1.0.0        Upgrade complete
4         deployed    api-0.7.0  1.0.0        Upgrade complete

$ helm rollback api 3 -n match
Rollback was a success! Happy Helming!

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Helm ist hier nicht installiert; Ausgabe nach Helm-Doku, gekürzt.

  1. helm template rendert lokal, ohne Cluster. Gut für Review und CI.
  2. replicas: 3 kommt aus values.prod.yaml, der Tag aus --set.
  3. upgrade --install ist idempotent: installiert, wenn der Release fehlt, sonst Upgrade.
  4. helm history zeigt alle Revisionen. Standard: höchstens 10 werden behalten (--history-max).
  5. Der Rollback erzeugt eine neue Revision 5. Revision 4 bleibt in der Historie.

Vergleich

  • Helm: Templates + Values, Releases mit Historie, Hooks, Paket-Verteilung. Nachteil: Template-YAML wird schnell unleserlich.
  • Kustomize: keine Templates, sondern Overlays und Patches auf echtes YAML. In kubectl eingebaut. Keine Releases, kein Rollback-Konzept.
  • Helm + ArgoCD: ArgoCD rendert das Chart wie helm template und wendet es selbst an. Es gibt dann keinen Helm-Release im Cluster; Historie und Rollback macht ArgoCD bzw. Git.
  • Helm 3 vs Helm 4: Helm 4 hat Server-Side Apply für neue Releases, umbenannte Flags, kstatus-Warten. Charts v2 bleiben kompatibel.
  • Operator: eigener Controller für komplexe Abläufe (Backup, Failover). Helm installiert nur, ein Operator betreibt.

In der Produktion

  1. Release hängt in pending-upgrade: Ein Upgrade wurde abgebrochen. Neue Upgrades scheitern. Lösung: helm history, dann helm rollback auf die letzte gute Revision.
  2. Upgrade „erfolgreich“, aber Pods crashen: Ohne --wait prüft Helm keinen Zustand. Lösung: --wait --rollback-on-failure und Readiness Probes.
  3. Values verschwinden nach Upgrade: Jemand nutzte --reuse-values mit neuem Chart, neue Defaults fehlen. Lösung: Values immer vollständig aus versionierten Dateien.
  4. Migration-Job bleibt hängen oder Name kollidiert: Lösung: hook-delete-policy: before-hook-creation,hook-succeeded. In ArgoCD sind Jobs unveränderlich; dafür Hooks oder ignoreDifferences.
  5. Secrets in values.yaml im Git: Lösung: Secrets nicht ins Chart, sondern per External Secrets Operator aus Vault oder Key Vault.
  6. „Kann Ressource nicht übernehmen“: Ein Objekt existiert schon ohne Helm-Labels. Lösung: --take-ownership bewusst nutzen oder Objekt neu erstellen.

Diagnose: Werkzeuge und Befehle

  • helm template und helm lint: rendern und prüfen ohne Cluster, ideal in CI.
  • helm upgrade --dry-run=server: rendern und gegen den API Server validieren.
  • helm get values api, helm get manifest api: welche Values und welches YAML die aktuelle Revision hat.
  • helm history api, helm status api: Revisionen und Zustand.
  • helm diff upgrade (Plugin): zeigt die Änderung vor dem Upgrade.
  • kubectl get secret -l owner=helm: die Release-Secrets.
  • helm test api: führt Test-Hooks aus.

Senior-Punkte

  1. Ein Chart, mehrere Values-Dateien. Umgebungsunterschiede nur in Values, nie als Kopie des Charts.
  2. Templates einfach halten. Viel Logik in Templates ist schwer zu reviewen. Lieber explizite Values.
  3. Schema und Lint in CI: values.schema.json fängt Tippfehler, bevor der Cluster sie sieht.
  4. Chart-Version pinnen und als OCI-Artefakt mit Digest verteilen. Reproduzierbar wie ein Image.
  5. Mit GitOps ist Git der Rollback, nicht helm rollback. Sonst stellt der Agent den Git-Stand wieder her.
  6. Helm 4 planen: umbenannte Flags in Pipelines anpassen, Post-Renderer als Plugins, SSA-Verhalten testen.
