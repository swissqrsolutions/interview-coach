GitOps-Prinzipien

Kern: GitOps ist ein Betriebsmodell, bei dem der gewünschte Zustand eines Systems deklarativ und versioniert in Git liegt. Software-Agenten im Zielsystem ziehen diesen Zustand selbst und gleichen die Realität ständig an. Das löst drei Probleme, nämlich wer was geändert hat (Audit), wie man zurückkommt (Rollback per Commit) und ob die Realität abweicht (Drift).

Antwort-Muster

Frage: Was ist GitOps, und was sind die vier Prinzipien?

  1. Mechanismus: Der Soll-Zustand liegt deklarativ und versioniert in Git. Ein Agent im Cluster zieht ihn und gleicht Soll und Ist ständig an.
  2. Zahl: OpenGitOps v1.0.0 nennt vier Prinzipien. Sie heissen Declarative, Versioned and Immutable, Pulled Automatically und Continuously Reconciled.
  3. Trade-off: Pull braucht keine Cluster-Zugangsdaten in der CI und schützt vor Drift. Dafür braucht es einen Agenten und ein sauberes Config-Repo.
  4. Produktion: Eine manuelle kubectl-Änderung wird zurückgedreht. Änderungen laufen darum immer per Pull Request ins Config-Repo.

1. Die Reise einer Änderung durch die vier Prinzipien

  1. Declarative: Das Team schreibt replicas: 2 in ein Manifest. Es beschreibt das Was, nicht das Wie.
  2. Versioned and Immutable: Die Änderung kommt per Pull Request in Git. Jeder Stand hat einen Commit, die Historie ist vollständig.
  3. Pulled Automatically: Der Agent im Cluster holt den neuen Stand selbst. Niemand ruft kubectl apply von aussen.
  4. Continuously Reconciled: Der Agent beobachtet den Cluster weiter. Jemand setzt manuell 5 Replicas. Der Agent sieht die Drift und stellt 2 wieder her.
  5. Rollback: Ein git revert ist eine neue Deklaration. Der gleiche Weg bringt den alten Stand zurück.

2. Aufbau

  1. App-Repo: enthält Code. CI baut und testet ihn und pusht ein Image in die Registry.
  2. Config-Repo: enthält den Soll-Zustand: Helm-Values, Manifeste. CI ändert hier nur den Image-Tag, per Commit oder Pull Request.
  3. Agent: läuft im Cluster und zieht den Soll-Zustand. CI braucht darum keine Cluster-Zugangsdaten.
  4. Reconcile-Schleife: Der Agent vergleicht Soll und Ist ständig und gleicht an.
  5. Secrets: liegen nicht im Repo. Ein Operator holt sie im Cluster aus einem Secret Store.

3. Details, die Interviewer fragen

  1. Die vier Prinzipien (OpenGitOps v1.0.0): Declarative heisst, der Soll-Zustand ist deklarativ beschrieben. Versioned and Immutable heisst, er ist unveränderlich und versioniert mit vollständiger Historie gespeichert. Pulled Automatically heisst, Agenten ziehen den Soll-Zustand selbst. Continuously Reconciled heisst, Agenten beobachten ständig und gleichen an.
  2. Git ist nicht Pflicht: Die Prinzipien sprechen von einer „Quelle“ mit Versionierung. Git ist nur die häufigste. Auch OCI-Registries dienen als Quelle.
  3. Pull vs Push: Beim Push deployt die CI-Pipeline aktiv in den Cluster. Sie braucht dafür Zugangsdaten. Beim Pull holt ein Agent im Cluster den Stand. Pull braucht keine eingehenden Cluster-Rechte für CI und erkennt Drift.
  4. Reconciliation: Die Reconcile-Schleife vergleicht Soll und Ist und gleicht an. Das ist das gleiche Muster wie bei Kubernetes-Controllern. Nur die Quelle ist Git.
  5. App-Repo und Config-Repo trennen: Code und Deploy-Konfiguration haben andere Lebenszyklen und Rechte. CI schreibt nur den Tag ins Config-Repo.
  6. Umgebungs-Promotion: Üblich ist ein Ordner oder eine Values-Datei pro Umgebung, zum Beispiel envs/dev und envs/prod. Ein Pull Request kopiert den Image-Tag von dev nach prod. Ein Branch pro Umgebung divergiert leicht und gilt als Anti-Pattern.
  7. Automatische Tag-Updates: Werkzeuge wie Argo CD Image Updater oder Flux Image Automation schreiben neue Tags selbst ins Repo. Für Prod nutzt man meist Pull Request und Review.
  8. Secrets in GitOps: Es gibt drei Wege. Erstens holt der External Secrets Operator Secrets im Cluster aus Vault oder Key Vault, und nur der Verweis liegt in Git. Zweitens liegen mit Sealed Secrets oder SOPS verschlüsselte Secrets in Git. Drittens gibt es Injection beim Rendern per Plugin, wovon Argo CD abrät.
  9. Drift: Drift heisst, der Ist-Zustand weicht vom deklarierten Soll ab. Ursachen sind kubectl edit, ein Hotfix im Portal oder fremde Controller.
  10. Was nicht in GitOps passt: Dazu gehören Daten wie Datenbank-Inhalte, sehr dynamische Werte wie HPA-Replicas und imperative Einmal-Aktionen. Diese braucht man als Jobs, Hooks oder Ausnahmen.

4. Fallen

  • „GitOps heisst, die Pipeline macht kubectl apply aus Git.“ → Falsch. Das ist Push-CD. GitOps verlangt einen Agenten, der zieht und ständig angleicht.
  • „GitOps braucht Git.“ → Nicht zwingend. Die Prinzipien verlangen eine versionierte, unveränderliche Quelle; Git ist die häufigste.
  • „Secrets verschlüsselt ins Repo ist immer okay.“ → Möglich (Sealed Secrets, SOPS), aber Rotation und Schlüssel bleiben Arbeit. Oft ist External Secrets besser.
  • „Ein Branch pro Umgebung ist GitOps-Standard.“ → Falsch. Ordner pro Umgebung auf einem Branch ist der übliche Weg.
  • „Rollback per UI-Knopf.“ → In GitOps: git revert, sonst widerspricht der Cluster dem Repo.

5. Selbsttest

Warum?

Welche Vorteile hat Pull?

Keine Cluster-Credentials in CI, ständiger Drift-Schutz, Audit und Rollback über Git.

Warum App-Repo und Config-Repo trennen?

Andere Lebenszyklen und Rechte. Code-Commits sollen nicht jedes Mal einen Deploy auslösen; Prod-Änderungen brauchen eigenes Review.

Ordner oder Branch pro Umgebung?

Ordner pro Umgebung auf einem Branch. Branches pro Umgebung divergieren und machen Merges riskant.

Warum rät Argo CD von Secret-Injection beim Rendern ab?

Argo CD braucht dann Zugriff auf die Secrets, und gerenderte Manifeste liegen im Klartext im Redis-Cache. Ausserdem werden Secret-Änderungen an Syncs gekoppelt.

Wie innen?

Was ist GitOps?

Ein Betriebsmodell: Der Soll-Zustand liegt deklarativ und versioniert in Git. Agenten ziehen ihn und gleichen den Ist-Zustand ständig an.

Nennen Sie die vier OpenGitOps-Prinzipien.

Declarative, Versioned and Immutable, Pulled Automatically, Continuously Reconciled.

Was heisst „deklarativ“?

Man beschreibt den gewünschten Endzustand, nicht die Schritte dorthin. Beispiel: replicas: 3 statt „starte einen Pod mehr“.

Was ist Drift?

Der Ist-Zustand weicht vom deklarierten Soll ab, z. B. nach kubectl edit. Der Agent erkennt und korrigiert ihn.

Was ist Reconciliation?

Eine Schleife: beobachten, mit dem Soll vergleichen, angleichen. Immer wieder, nicht nur bei einem Commit.

Wie macht man Rollback in GitOps?

git revert des Commits und push. Der Agent gleicht den Cluster an den alten Stand an.

Was gehört nicht in GitOps?

Daten, sehr dynamische Werte wie HPA-Replicas und imperative Einmal-Aktionen. Diese löst man mit Jobs, Hooks oder ignorierten Feldern.

Zahlen

Wie viele Prinzipien hat OpenGitOps?

Vier, in Version 1.0.0: Declarative, Versioned and Immutable, Pulled Automatically, Continuously Reconciled.

Welche drei Wege für Secrets gibt es?

External Secrets Operator mit Verweis in Git, verschlüsselte Secrets mit Sealed Secrets oder SOPS, und Injection beim Rendern. Argo CD rät vom dritten Weg ab.

Wie viele Replicas stellt der Agent im Drift-Beispiel wieder her?

Zwei. Jemand setzt manuell 5, der Agent stellt den deklarierten Stand von 2 wieder her.

Vergleich

Was ist der Unterschied zwischen Push und Pull?

Push: CI deployt aktiv in den Cluster mit eigenen Zugangsdaten. Pull: ein Agent im Cluster holt den Stand selbst und erkennt Drift.

Ist Terraform in einer Pipeline GitOps?

Teilweise: deklarativ und versioniert ja. Aber meist Push und ohne ständige Reconciliation. Drift-Checks per Plan schliessen die Lücke nur teilweise.

Welche Werkzeuge setzen GitOps um?

Argo CD und Flux für Kubernetes. Für Infrastruktur auch Crossplane oder Terraform-Controller.

Wie gehen Sie mit Secrets in GitOps um?

Nur Verweise in Git, z. B. ExternalSecret-Objekte. Der Operator holt die Werte aus Vault oder Key Vault. Alternativ verschlüsselt mit Sealed Secrets oder SOPS.

Produktion

Szenario: Produktion brennt, ein Kollege will per kubectl ein Limit erhöhen. Was sagen Sie?

Der Agent dreht es zurück. Schneller PR ins Config-Repo ist der richtige Weg. Im echten Notfall Auto-Sync kurz pausieren, ändern, sofort nach Git nachziehen.

Szenario: Ein Team will das Passwort der Datenbank in values.yaml schreiben. Was schlagen Sie vor?

Passwort in Vault oder Key Vault, im Repo nur ein ExternalSecret. Der Operator erzeugt das Kubernetes-Secret und aktualisiert es bei Rotation.

Szenario: Die Pipeline deployt heute per helm upgrade. Wie migrieren Sie zu GitOps?

Config-Repo mit Chart und Values pro Umgebung anlegen, Argo CD Application darauf zeigen, zuerst manueller Sync zum Vergleich. Dann CI nur noch Tags committen lassen, Cluster-Rechte aus CI entfernen, Auto-Sync einschalten.

Design

Wie promoten Sie von test nach prod?

Per Pull Request, der den getesteten Image-Tag oder Digest in die Prod-Values schreibt. Review, Merge, der Agent deployt.

Was geht kaputt, wenn CI Cluster-Zugangsdaten braucht?

Das ist Push-CD. Die Pipeline hat dann Schreibrechte im Cluster, und es gibt keinen ständigen Drift-Schutz. Pull vermeidet beides.

Was geht kaputt, wenn Secrets im Klartext im Repo liegen?

Jeder mit Lesezugriff sieht sie, und die Historie behält sie. Darum liegt im Repo nur ein Verweis, den ein Operator im Cluster auflöst.

Mehr

Gerüst

  • Warum? Audit, Rollback und Drift-Schutz kommen aus Git und einem Agenten. Niemand ruft kubectl apply von aussen.
  • Wie innen? Agent im Cluster zieht den Soll-Zustand und gleicht in einer Reconcile-Schleife ständig an. CI schreibt nur den Image-Tag ins Config-Repo.
  • Zahlen 4 Prinzipien (OpenGitOps v1.0.0). 3 Wege für Secrets. Drift: 5 Replicas manuell, Agent stellt 2 wieder her.
  • Vergleich Pull vs Push. GitOps vs Terraform-Pipeline. Ordner vs Branch pro Umgebung.
  • Produktion kubectl-Hotfix wird zurückgedreht. Passwort in values.yaml. Migration von helm upgrade zu Pull.
  • Design Secrets nur als Verweis im Repo. Promotion per Pull Request. HPA-Replicas und Daten gehören nicht in GitOps.

kubectl apply -f deploy.yaml          # Soll: replicas: 2, nginx:1.27-alpine

kubectl diff -f deploy.yaml; echo "exit=$?"

Echte Ausgabe, kubectl v1.37.0 gegen k3s v1.36.4 (lokal). Temp-Pfade und Annotation-Zeilen gekürzt.

  1. Direkt nach apply ist diff leer, Exit-Code 0: Soll gleich Ist.
  2. Nach scale zeigt diff: live sind es 5, deklariert sind 2. Exit-Code 1 heisst „Unterschied gefunden“. Das ist Drift.
  3. Ein erneutes apply stellt 2 wieder her. Genau das macht ein GitOps-Agent in einer Schleife, z. B. Argo CD mit selfHeal.

Vergleich

  • Push-CD (Pipeline deployt): einfach, schnell eingerichtet. Nachteile: Cluster-Rechte in CI, kein Drift-Schutz, Zustand nur in Pipeline-Logs.
  • Pull-GitOps (Agent zieht): Audit in Git, Drift-Erkennung, Rollback per Revert. Nachteile: zusätzlicher Controller, mehr Repos, Secrets brauchen eigene Lösung.
  • Ordner pro Umgebung: alles auf main, Unterschiede sichtbar per Diff. Empfohlener Standard.
  • Branch pro Umgebung: scheinbar einfach, aber Branches divergieren, Merges werden riskant.
  • External Secrets vs Sealed Secrets: External Secrets lässt Secrets im zentralen Store und unterstützt Rotation. Sealed Secrets braucht keinen externen Store, aber Rotation und Schlüsselpflege sind Handarbeit.

In der Produktion

  1. Hotfix per kubectl, dann weg: Der Agent dreht ihn zurück. Lösung: Notfall-Prozess über Git (schneller PR), notfalls Auto-Sync kurz pausieren und dokumentieren.
  2. Secret im Repo committet: Git-Historie ist dauerhaft. Lösung: Secret rotieren, External Secrets einführen, Secret-Scan in CI.
  3. Promotion vergessen: dev und prod laufen Wochen auseinander. Lösung: automatischer Promotion-PR nach erfolgreichem Test, Dashboard mit Versionen pro Umgebung.
  4. Endloser Sync-Kampf: HPA oder ein Operator ändert Felder, der Agent setzt sie zurück. Lösung: Felder nicht deklarieren oder ignorieren.
  5. Kaputter Commit legt alles lahm: Mit Prune löscht der Agent Ressourcen. Lösung: Review, Schema-Prüfung und helm template in CI, Schutz für Daten-Ressourcen.

Diagnose: Werkzeuge und Befehle

  • kubectl diff -f: zeigt Drift zwischen Datei und Cluster (Exit-Code 1 bei Unterschied).
  • argocd app diff / flux diff: Drift aus Sicht des Agenten.
  • git log -p envs/prod: wer hat wann was in Prod geändert.
  • kubectl get events und Audit-Logs des API Servers: wer hat manuell geändert.
  • kubectl get externalsecret -A: Status der Secret-Synchronisation.
  • Metriken des Agenten in Prometheus/Grafana: OutOfSync-Apps, fehlgeschlagene Syncs.

Senior-Punkte

  1. GitOps ist ein Vertrag: Keine manuellen Cluster-Änderungen. Ohne diese Disziplin bringt das Werkzeug wenig.
  2. Pull reduziert die Angriffsfläche: CI braucht keine Cluster-Admin-Rechte mehr. Nur der Agent im Cluster schreibt.
  3. Promotion ist ein Commit, kein Knopf. Damit ist jede Prod-Änderung reviewt und revertierbar.
  4. Secrets sind die Schwachstelle. Lösung festlegen, bevor das erste Secret gebraucht wird; Referenzen in Git, Werte im Store.
  5. Nicht alles ist deklarativ. Migrationen und Einmal-Aufgaben als Hooks oder Jobs modellieren, Daten bleiben ausserhalb.
  6. Infrastruktur und Workloads getrennt: Terraform baut den Cluster, der GitOps-Agent füllt ihn.
