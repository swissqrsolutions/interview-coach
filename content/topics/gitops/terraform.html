Terraform: State, Plan, Apply, Module, Drift

Kern: Terraform ist ein Infrastructure-as-Code-Werkzeug. Man beschreibt Cloud-Ressourcen deklarativ in HCL, und Terraform erstellt, ändert oder löscht sie über die APIs der Provider. Der State merkt sich, welche echte Ressource zu welchem Block gehört, plan zeigt den Unterschied zwischen Code, State und Realität und apply setzt ihn um.

Antwort-Muster

Frage: Was ist Terraform, und wie läuft eine Änderung ab?

  1. Mechanismus: Man beschreibt Ressourcen in HCL. Terraform vergleicht Code, State und Realität im plan und führt im apply genau diesen geprüften Plan aus.
  2. Zahl: Ein Lauf hat sieben Schritte, von init bis zum Schreiben des States. Mit -detailed-exitcode gibt plan den Code 2 zurück, wenn es Änderungen gibt.
  3. Trade-off: Der State macht Terraform genau, ist aber ein Risiko. Er kann Secrets enthalten und braucht Remote Backend und Lock.
  4. Produktion: In der Pipeline zeige ich den Plan im Pull Request und prüfe besonders destroy und replace.

1. Die Reise einer Änderung

  1. init: Ein Entwickler will den AKS-Nodepool von 3 auf 5 Nodes vergrössern. terraform init verbindet das Backend und lädt den Provider.
  2. Lock: Der Plan sperrt den State. Ein zweiter Lauf zur gleichen Zeit muss warten oder scheitert.
  3. Refresh: Terraform liest den echten Zustand aller Ressourcen über die API.
  4. Plan: Terraform vergleicht Code, State und Realität. Ergebnis: ~ update in-place für den Nodepool. Der Plan wird mit -out=tfplan gespeichert.
  5. Review: Die Pipeline zeigt den Plan im Pull Request. Ein Mensch prüft besonders destroy und replace.
  6. Apply: terraform apply tfplan führt genau den geprüften Plan aus. Hat sich der State inzwischen geändert, lehnt Terraform den alten Plan ab.
  7. Ende: Terraform schreibt den neuen State und gibt den Lock frei.

2. Aufbau

  1. HCL-Dateien: beschreiben den Soll-Zustand, z. B. einen AKS-Cluster. Sie liegen versioniert im Git-Repo.
  2. Terraform Core: liest den Code, baut einen Abhängigkeitsgraph und berechnet den Plan.
  3. Provider: ein Plugin pro Plattform. Beispiel: azurerm ruft die Azure-API auf.
  4. State: eine JSON-Datei, die Blöcke auf echte IDs abbildet. Sie liegt in einem Remote Backend mit Lock.
  5. Lock-Datei: .terraform.lock.hcl fixiert Provider-Versionen und Hashes. Sie gehört ins Repo.

3. Details, die Interviewer fragen

  1. State: Er bildet jede Ressourcen-Adresse auf eine echte ID ab. Ohne State weiss Terraform nicht, was ihm gehört. Er enthält auch Attribute, oft mit Secrets.
  2. Remote Backend und Locking: Ein Backend speichert den State zentral. Locking verhindert zwei gleichzeitige Schreib-Läufe. azurerm lockt nativ über Blob Storage. Beim S3-Backend ist use_lockfile die neue Art. DynamoDB-Locking ist deprecated.
  3. force-unlock: Bricht ein Lauf ab, bleibt der Lock hängen. terraform force-unlock <LOCK_ID> löst ihn. Man nutzt es nur, wenn sicher kein Lauf mehr aktiv ist.
  4. Saved Plan: plan -out speichert den Plan. apply tfplan führt genau diesen aus. Die Datei enthält Variablen, auch sensitive. Darum behandelt man sie wie ein Secret.
  5. Module: Ein Modul ist ein Ordner mit .tf-Dateien, Variablen und Outputs. Das Root-Modul ruft Child-Module auf. Man pinnt Versionen (Registry: version, Git: ?ref=v1.2.0).
  6. count vs for_each: count adressiert über den Index. Ein entferntes Element in der Mitte verschiebt alle anderen. for_each adressiert über Schlüssel und ist stabiler.
  7. Drift: Drift heisst, die Realität weicht vom Code ab, zum Beispiel durch eine Änderung im Portal. plan zeigt sie. plan -refresh-only übernimmt die Realität nur in den State, ohne Ressourcen zu ändern.
  8. Import: Ein import-Block (to, id) bringt eine bestehende Ressource unter Terraform. plan -generate-config-out=gen.tf erzeugt den passenden resource-Block. Der Block läuft durch normales plan/apply und ist reviewbar. Der alte Befehl terraform import ändert den State sofort.
  9. Refactoring ohne Neubau: Ein moved-Block benennt eine Ressource im Code um, ohne sie zu zerstören. Ein removed-Block nimmt sie aus dem State, ohne sie zu löschen.
  10. Workspaces: CLI-Workspaces sind mehrere States einer Konfiguration im selben Backend. Laut Doku sind sie keine geeignete Isolation für Umgebungen mit eigenen Rechten. Empfohlen sind Module plus eigene Konfiguration und eigenes Backend pro Umgebung.
  11. Secrets im State: sensitive = true verbirgt Werte nur in der Ausgabe. Sie stehen trotzdem in State und Plan. Ephemeral-Werte (ab 1.10) und write-only-Argumente wie password_wo (ab 1.11) bleiben ganz aus dem State.
  12. lifecycle: prevent_destroy blockiert das Löschen. ignore_changes ignoriert bestimmte Attribute, zum Beispiel vom Autoscaler gesetzte Node-Zahlen. create_before_destroy baut zuerst neu.

4. Fallen

  • „sensitive = true hält das Secret aus dem State.“ → Falsch. Nur aus der Ausgabe. Aus dem State nur mit ephemeral oder write-only.
  • „Workspaces sind der Weg für dev/test/prod.“ → Falsch laut Doku, wenn Rechte und Credentials getrennt sein müssen. Eigene Konfiguration und Backend pro Umgebung.
  • „terraform plan ändert nie etwas.“ → Plan ändert keine Ressourcen, aber er sperrt den State und liest die API. Ein gespeicherter Plan enthält sensitive Daten.
  • „State-Datei lösche ich, dann fange ich neu an.“ → Falsch. Dann will Terraform alles neu erstellen, und die alten Ressourcen sind verwaist.
  • „count und for_each sind gleich.“ → Falsch. count adressiert über Index und kann beim Entfernen Ressourcen neu bauen.
  • „DynamoDB ist Pflicht für S3-Locking.“ → Veraltet. use_lockfile lockt in S3 selbst; DynamoDB-Locking ist deprecated.

5. Selbsttest

Warum?

Wozu braucht Terraform den State?

Er bildet jede Ressource im Code auf eine echte ID ab und speichert Attribute. Ohne State weiss Terraform nicht, was ihm gehört.

Warum Remote State?

Damit Team und Pipeline denselben State nutzen, mit Lock, Versionierung und Zugriffskontrolle. Lokaler State geht verloren und kollidiert.

Workspaces oder Verzeichnisse für Umgebungen?

Verzeichnisse mit eigenem Backend, wenn Umgebungen getrennte Rechte brauchen. Workspaces teilen ein Backend und sind laut Doku keine Isolation.

count oder for_each?

for_each, wenn Elemente einen stabilen Schlüssel haben. count adressiert über Index; Entfernen in der Mitte verschiebt Adressen.

Wie innen?

Was ist Terraform?

Ein Infrastructure-as-Code-Werkzeug. Man beschreibt Ressourcen deklarativ in HCL, Terraform erstellt und ändert sie über Provider-APIs.

Was ist State Locking?

Das Backend sperrt den State während eines Laufs. Ein zweiter Lauf wartet oder scheitert. So wird der State nicht korrupt.

Was ist der Unterschied zwischen plan und apply?

plan berechnet und zeigt die Änderungen. apply führt sie aus. Mit plan -out und apply tfplan wird genau der geprüfte Plan angewendet.

Was macht plan -refresh-only?

Es gleicht nur den State an die Realität an, ohne Ressourcen zu ändern. Nützlich nach Änderungen ausserhalb von Terraform.

Wie übernehmen Sie eine bestehende Ressource?

Mit einem import-Block (to, id). plan -generate-config-out erzeugt den resource-Block. Danach normal plan und apply.

Was ist ein Modul?

Ein Ordner mit Terraform-Code, Variablen und Outputs. Man ruft ihn mehrfach mit anderen Parametern auf. Versionen pinnen.

Was ist .terraform.lock.hcl?

Die Lock-Datei mit Provider-Versionen und Hashes. Sie gehört ins Repo, damit alle dieselben Provider nutzen.

Zahlen

Was bedeuten +, ~, -/+ und - im Plan?

+ erstellen, ~ in-place ändern, -/+ ersetzen (löschen und neu), - löschen.

Ab welcher Version gibt es ephemeral Werte und write-only-Argumente?

Ephemeral Werte ab Terraform 1.10, write-only-Argumente ab 1.11. Beide bleiben aus dem State.

Welchen Exit-Code liefert plan -detailed-exitcode bei Änderungen?

Den Code 2. So kann eine Pipeline Drift automatisch erkennen.

Vergleich

import-Block oder terraform import?

Der Block läuft durch plan und Review und kann viele Ressourcen mit for_each importieren. Der Befehl ändert den State sofort ohne Plan.

Terraform oder Bicep für Azure?

Bicep: nur Azure, kein State, neue Features sofort. Terraform: Multi-Cloud, ein Werkzeug für Azure, Kubernetes und mehr, dafür State-Verwaltung.

Wie unterscheidet sich State Locking bei azurerm und S3?

azurerm lockt nativ über Blob Storage. Beim S3-Backend ist use_lockfile die neue Art. DynamoDB-Locking ist deprecated.

Produktion

Szenario: Die Pipeline meldet „Error acquiring the state lock“. Was tun Sie?

Prüfen, ob ein anderer Lauf aktiv ist. Wenn nicht, Lock-ID aus der Meldung nehmen und terraform force-unlock. Danach Parallel-Läufe in der Pipeline verhindern.

Szenario: Jemand hat im Portal die Node-Grösse geändert. Was passiert beim nächsten Apply?

Der Plan zeigt Drift und will den Code-Stand wiederherstellen, eventuell mit Replace. Entscheiden: Code anpassen oder Änderung zurückdrehen. Danach Schreibrechte einschränken.

Szenario: Der Plan zeigt -/+ für den AKS-Cluster nach einem harmlosen Refactoring. Was tun Sie?

Nicht applyen. Wahrscheinlich hat sich die Adresse geändert: moved-Block ergänzen. Oder ein Attribut erzwingt Replace: Änderung anders lösen, prevent_destroy setzen.

Was ist Drift und wie finden Sie ihn?

Die Realität weicht vom Code ab, z. B. durch Klicks im Portal. plan zeigt ihn; -detailed-exitcode liefert 2 bei Änderungen.

Design

Sind Secrets im State?

Ja, oft im Klartext. sensitive verbirgt sie nur in der Ausgabe. Ephemeral-Werte und write-only-Argumente bleiben ganz aus State und Plan.

Was macht ignore_changes?

Terraform ignoriert Änderungen an bestimmten Attributen. Typisch für Werte, die ein Autoscaler oder ein anderes System setzt.

Wie schützen Sie eine Datenbank vor Löschung?

lifecycle prevent_destroy, dazu Plan-Review in der Pipeline und Resource Locks in Azure.

Was macht ein moved-Block?

Er sagt Terraform, dass eine Ressource eine neue Adresse hat. So wird sie nicht gelöscht und neu erstellt.

Mehr

Gerüst

  • Warum? Infrastruktur als reviewbarer Code statt Klicks im Portal. Plan vor Apply.
  • Wie innen? init → Lock → Refresh → Plan (-out) → Review → Apply genau dieses Plans → State schreiben, Lock frei. State bildet Block auf echte ID ab.
  • Zahlen Plan-Symbole + ~ -/+ -. Ephemeral ab 1.10, write-only ab 1.11. -detailed-exitcode liefert 2 bei Änderungen.
  • Vergleich import-Block vs terraform import. Terraform vs Bicep. count vs for_each. Workspaces vs eigenes Backend.
  • Produktion Lock hängt → force-unlock. Drift durch Portal-Änderung. -/+ nach Refactoring → moved-Block.
  • Design Secrets bleiben im State (sensitive nur Ausgabe). prevent_destroy, ignore_changes. Saved Plan wie Secret behandeln.

Beispiel: AKS mit Remote State in Azure

terraform {
  required_version = ">= 1.11"
  required_providers {
    azurerm = { source = "hashicorp/azurerm" }
  }
  backend "azurerm" {
    use_oidc             = true          # Workload Identity Federation aus der Pipeline
    use_azuread_auth     = true          # Entra ID statt Access Key
    storage_account_name = "sttfstateprod"
    container_name       = "tfstate"
    key                  = "aks/prod.terraform.tfstate"
  }
}

module "aks" {
  source     = "./modules/aks"
  name       = "aks-match-prod"
  node_count = 5                          # vorher 3
}
$ terraform plan -out=tfplan -detailed-exitcode
Acquiring state lock. This may take a few moments...
module.aks.azurerm_kubernetes_cluster.this: Refreshing state... [id=/subscriptions/…/aks-match-prod]

Terraform will perform the following actions:

  # module.aks.azurerm_kubernetes_cluster.this will be updated in-place
  ~ resource "azurerm_kubernetes_cluster" "this" {
      ~ default_node_pool {
          ~ node_count = 3 -> 5
        }
    }

Plan: 0 to add, 1 to change, 0 to destroy.
Saved the plan to: tfplan
$ echo $?
2

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Terraform ist hier nicht installiert; Format nach der CLI-Doku, gekürzt.

  1. Der Backend-Block legt den State in Azure Blob Storage ab. Locking und Konsistenz-Prüfung macht das Backend nativ über Blob Storage.
  2. use_oidc und use_azuread_auth: Die Pipeline meldet sich ohne Secret an. Die Doku empfiehlt Entra ID statt Access Key.
  3. Das Modul kapselt den AKS-Code. Die Wurzel übergibt nur Parameter.
  4. ~ heisst in-place update. -/+ hiesse replace: löschen und neu bauen.
  5. -detailed-exitcode liefert 2 = „Änderungen vorhanden“. 0 = keine Änderung, 1 = Fehler. Gut für Drift-Checks in CI.

Vergleich

  • Terraform: Multi-Cloud, riesiges Provider-Ökosystem, eigener State. Lizenz: Business Source License (BSL), nicht mehr Open Source im engen Sinn.
  • OpenTofu: Open-Source-Fork von Terraform (Linux Foundation), weitgehend kompatibel, MPL-Lizenz.
  • Bicep / ARM: nur Azure, kein eigener State (Azure ist die Wahrheit), sofort neue Azure-Features.
  • Pulumi: Infrastruktur in TypeScript, Python, Go, C#. Auch mit State.
  • Crossplane: Infrastruktur als Kubernetes-Ressourcen, ständige Reconciliation wie GitOps.
  • Workspaces vs Verzeichnisse: Workspaces teilen Code und Backend, schnell für Test-Kopien. Verzeichnisse pro Umgebung mit eigenem Backend und eigenen Rechten sind sicherer für dev/test/prod.

In der Produktion

  1. State-Lock hängt nach abgebrochener Pipeline: Lösung: prüfen, dass kein Lauf aktiv ist, dann force-unlock. Pipeline so bauen, dass nur ein Lauf pro State gleichzeitig läuft.
  2. Plan will den AKS-Cluster ersetzen: Ein Attribut erzwingt replace. Lösung: Plan lesen, prevent_destroy setzen, Änderung anders lösen.
  3. Drift durch Klicks im Portal: Nächster Apply überschreibt sie oder scheitert. Lösung: täglicher Drift-Check mit -detailed-exitcode, Schreibrechte nur für die Pipeline.
  4. Autoscaler kämpft mit Terraform: Terraform setzt node_count immer wieder zurück. Lösung: ignore_changes für dieses Attribut.
  5. Secrets im State-Blob: Jeder mit Lesezugriff sieht Passwörter. Lösung: State-Zugriff per RBAC einschränken, Verschlüsselung, ephemeral/write-only, Secrets lieber in Key Vault erzeugen lassen.
  6. Provider-Upgrade bricht Plan: Lösung: Versionen pinnen, .terraform.lock.hcl committen, Upgrade bewusst mit init -upgrade in einem eigenen PR.

Diagnose: Werkzeuge und Befehle

  • terraform plan -detailed-exitcode: 0/1/2 für Drift-Checks in CI.
  • terraform plan -refresh-only: zeigt nur, was sich draussen geändert hat.
  • terraform state list, state show <addr>: was im State ist.
  • terraform validate, terraform fmt -check: Syntax und Format in CI.
  • terraform graph: Abhängigkeitsgraph.
  • TF_LOG=DEBUG: detaillierte Logs, z. B. API-Aufrufe des Providers.
  • terraform providers lock: Hashes für mehrere Plattformen (Windows-Entwickler, Linux-Agent) in die Lock-Datei schreiben.

Senior-Punkte

  1. Der State ist das wertvollste Artefakt. Remote, gesperrt, versioniert (Blob-Versioning), verschlüsselt, Zugriff minimal.
  2. Kleine States: Netzwerk, AKS und App-Infrastruktur getrennt. Kleinerer „Blast Radius“, schnellere Pläne.
  3. Plan im PR, Apply nur aus der Pipeline. Kein Apply vom Laptop gegen Produktion.
  4. Umgebungen über Verzeichnisse und Backends trennen, nicht über Workspaces, wenn Rechte verschieden sein müssen.
  5. Terraform für Infrastruktur, GitOps für Workloads. Terraform baut AKS; ArgoCD und Helm deployen in den Cluster.
  6. Replace ist das Risiko. Jeder -/+ auf zustandsbehafteten Ressourcen braucht einen zweiten Blick.
