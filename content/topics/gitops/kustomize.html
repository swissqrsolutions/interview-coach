Kustomize vs Helm

Kern: Kustomize baut Kubernetes-Manifeste aus einer Base und Overlays mit Patches, ohne Templates. Helm rendert dagegen Go-Templates mit Values und verwaltet Releases. Kustomize steckt in kubectl und passt gut zu GitOps mit Argo CD.

Antwort-Muster

Frage: Kustomize oder Helm, was nimmst du wann?

  1. Mechanismus: Kustomize liest eine kustomization.yaml, lädt die Base, erzeugt Generator-Objekte und wendet Patches an. Das Ergebnis ist reines YAML.
  2. Zahl: Kustomize steckt seit kubectl 1.14 in kubectl. Ein ConfigMap-Generator hängt einen Hash an den Namen.
  3. Trade-off: Kustomize hat keine Templates und keine Releases mit Rollback. Helm kann beides, hat aber schwer lesbare Templates.
  4. Produktion: Für eigene Apps pro Umgebung nehme ich Kustomize. Fremde Software kommt als Helm Chart, und Argo CD rendert beides.

1. Was kustomize build in Schritten tut

  1. Datei lesen: Kustomize sucht im Ordner die Datei kustomization.yaml. Sie ist der Einstieg.
  2. Resources laden: Unter resources stehen Dateien oder Ordner. Ein Ordner mit eigener kustomization.yaml wird zuerst gebaut. So entsteht die Kette Overlay, dann Base.
  3. Generatoren: Ein configMapGenerator erzeugt eine ConfigMap aus Literalen oder Dateien. Er hängt einen Hash des Inhalts an den Namen.
  4. Transformer: patches, namePrefix, labels und images ändern die geladenen Objekte. Jedes Feld arbeitet auf dem Ergebnis davor.
  5. Namen nachziehen: Wird ein Name geändert, passt Kustomize die Verweise darauf an. Ein configMapRef zeigt dann auf den neuen Namen.
  6. Ausgabe: Das fertige YAML geht auf stdout. kubectl kustomize zeigt es nur. kubectl apply -k wendet es an.

2. Aufbau

  1. Base ist die gemeinsame Vorlage mit normalem, gültigem YAML. Sie läuft auch allein.
  2. Overlay ist ein Ordner pro Umgebung. Er zeigt auf die Base und ändert nur Unterschiede.
  3. Patch ist eine Änderung an einem Objekt. Er kann ein Strategic Merge oder ein JSON Patch sein.
  4. Generator erzeugt ConfigMaps und Secrets aus Literalen oder Dateien.
  5. Transformer sind Felder wie namePrefix, labels und images. Sie wirken auf alle Objekte.
  6. Component ist ein wiederverwendbarer Baustein für mehrere Overlays.

3. Details

  1. Seit wann in kubectl: kubectl unterstützt Kustomize seit Version 1.14. kubectl kustomize ordner zeigt das Ergebnis. kubectl apply -k ordner wendet es an. Die eingebaute Kustomize-Version kann älter sein als die eigenständige.
  2. Kein Template, kein Zustand: Kustomize hat keine Variablen im YAML und keinen Server. Die Base bleibt gültiges YAML. Es gibt keine Releases und kein Rollback. Den Verlauf hat Git.
  3. patches: Das Feld patches ersetzt patchesStrategicMerge und patchesJson6902. Beide alten Felder gelten als deprecated. Ein Patch hat einen target und ist entweder Strategic Merge oder JSON Patch.
  4. Strategic Merge vs JSON Patch: Strategic Merge ist ein Teil-YAML, das mit dem Objekt verschmilzt. Listen werden dabei nach einem Schlüssel wie name zusammengeführt. JSON Patch nennt Operation und Pfad, etwa replace /spec/replicas. Er ist präzise.
  5. labels statt commonLabels: commonLabels ist deprecated. labels ist die Ersatz-Variante. Mit pairs setzt sie Labels an Objekte, ohne Selektoren zu ändern. Das ist wichtig, weil Selektoren in Deployments nicht änderbar sind.
  6. Generator-Hash: Der Name der ConfigMap bekommt ein Hash-Suffix. Ändert sich der Inhalt, ändert sich der Name. Dann sieht das Deployment eine neue Spec und startet Pods neu. Mit disableNameSuffixHash: true schaltest du das ab.
  7. behavior beim Generator: Ein Overlay kann eine Base-ConfigMap mit behavior: merge ergänzen oder mit replace ersetzen. Ohne behavior gibt es einen Namenskonflikt.
  8. images: Das Feld images setzt Name oder Tag eines Images, ohne das Deployment zu patchen. Eine CI-Pipeline ändert so nur eine Zeile.
  9. replacements statt vars: vars ist deprecated und wird entfernt. replacements kopiert einen Wert aus einem Feld in andere Felder.
  10. components: Ein Component ist ein wiederverwendbarer Teil, den ein Overlay einbindet. Beispiel ist ein Monitoring-Sidecar, den nur manche Umgebungen brauchen.
  11. Helm in Kustomize: Das Feld helmCharts rendert ein Chart und patcht dann das Ergebnis. Es braucht das Flag --enable-helm und ein installiertes helm.
  12. Secrets: Ein secretGenerator legt Secrets nur als Base64 ab, das ist keine Verschlüsselung. Klartext gehört nicht ins Git. Nimm Sealed Secrets, SOPS oder External Secrets.

4. Fallen

  • „Kustomize ist Helm ohne Templates, also dasselbe.“ → Falsch. Kustomize hat keine Releases, kein Rollback und keine Pakete. Es verändert vorhandenes YAML.
  • „Ein Overlay kopiert die Base.“ → Falsch. Das Overlay verweist auf die Base und enthält nur die Unterschiede.
  • „commonLabels ist harmlos.“ → Falsch. Es ändert auch Selektoren. Ein Deployment-Selector lässt sich später nicht ändern. Nimm labels.
  • „Der Hash-Suffix an der ConfigMap ist ein Fehler.“ → Falsch. Er löst gewollt einen Rollout aus, wenn sich die Konfiguration ändert.
  • „kubectl apply -k löscht entfernte Objekte automatisch.“ → Falsch. Ohne --prune bleiben sie im Cluster. Argo CD mit Prune räumt auf.
  • „Secrets im secretGenerator sind sicher im Git.“ → Falsch. Sie sind nur Base64. Verschlüssele sie mit SOPS oder Sealed Secrets.

5. Selbsttest

Warum?

Warum Kustomize statt Kopien der YAML-Dateien pro Umgebung?

Kopien laufen auseinander. Mit Base und Overlay pflegt man gemeinsame Teile einmal. Die Overlays enthalten nur Unterschiede.

Warum bekommt eine generierte ConfigMap einen Hash?

Ändert sich die Konfiguration, ändert sich der Name. Das Deployment sieht eine neue Referenz und startet die Pods neu.

Warum ist Template-freies YAML ein Vorteil?

Die Base ist gültiges YAML und lässt sich prüfen und lesen. Es gibt keine Template-Logik, die man erst im Kopf rendern muss.

Wie innen?

Wie baut Kustomize das Ergebnis?

Es liest die kustomization.yaml, lädt die Resources rekursiv, führt Generatoren aus und wendet Transformer an. Dann passt es Namensverweise an und gibt YAML aus.

Was ist der Unterschied zwischen Strategic Merge und JSON Patch?

Strategic Merge verschmilzt ein Teil-YAML mit dem Objekt und kennt Schlüssel für Listen. JSON Patch führt Operationen auf einem Pfad aus.

Wie ändert ein Overlay die Replicas?

Mit einem Patch auf das Deployment, etwa JSON Patch replace /spec/replicas. Das Overlay enthält nur diesen Patch.

Was macht kubectl apply -k?

Es baut die Kustomization und wendet das Ergebnis per apply an. Es entspricht kubectl kustomize | kubectl apply -f -.

Wie funktioniert helmCharts in Kustomize?

Kustomize ruft helm template auf und patcht dann die Ausgabe. Es braucht --enable-helm. Es gibt keinen Helm-Release im Cluster.

Zahlen

Seit welcher kubectl-Version gibt es Kustomize?

Seit 1.14.

Welche Kustomize-Version steckt in kubectl 1.37?

Auf dieser Maschine zeigt kubectl version --client die Kustomize Version v5.8.1.

Wie sieht der Hash-Suffix aus?

Ein kurzer Hash des Inhalts, etwa web-config-hf678c7m2b. Er hängt vom Inhalt ab.

Wie viele Replicas hat die Base, wie viele das Prod-Overlay im Beispiel?

Die Base hat 1, das Prod-Overlay setzt 3 per Patch.

Vergleich

Kustomize vs Helm?

Kustomize patcht reines YAML, ohne Templates und ohne Release-Verwaltung. Helm rendert Templates mit Values und verwaltet Releases mit Rollback.

Wann Helm?

Für Fremdsoftware wie Ingress oder Datenbank-Operatoren. Das Chart ist ein versioniertes Paket mit Values.

Wann Kustomize?

Für eigene Apps mit wenigen Unterschieden pro Umgebung. Kein Template-Code, klare Diffs im Pull Request.

Kann man beides kombinieren?

Ja. Kustomize kann Helm-Charts per helmCharts rendern und patchen. Argo CD kann ebenfalls Kustomize oder Helm direkt rendern.

Kustomize vs Jsonnet oder CUE?

Jsonnet und CUE sind Programmiersprachen für Konfiguration. Kustomize bleibt bei deklarativem YAML und Patches.

Produktion

Wie legt man Umgebungen an?

Ein Ordner base und je ein Ordner pro Umgebung unter overlays. Jedes Overlay zeigt auf die Base. Argo CD zeigt auf den Overlay-Pfad.

Wie ändert die CI das Image?

Mit kustomize edit set image oder per Pull Request auf das Feld images. Argo CD synchronisiert danach.

Wie verhindert man, dass ein Patch still ins Leere läuft?

Den Build in der CI ausführen und das Ergebnis prüfen, zum Beispiel mit einem Schema-Check. Ein falscher Target-Name führt zu einem Fehler.

Szenario: Nach dem Deploy laufen die Pods mit alter Konfiguration. Was prüfen Sie?

Ob der Hash-Suffix aktiv ist. Mit disableNameSuffixHash ändert sich der Name nicht, und es gibt keinen Rollout. Hash wieder anschalten oder Rollout manuell starten.

Szenario: Ein Team will Helm-Charts, ein anderes Kustomize. Wie entscheiden Sie?

Eigene Apps in Kustomize, Fremd-Charts in Helm. Beides rendert Argo CD gleich. Wichtig ist eine einheitliche Ordnerstruktur im Git.

Design

Wie viele Overlay-Ebenen sind sinnvoll?

Meist zwei, Base und Umgebung. Mehr Ebenen machen es schwer zu sehen, woher ein Wert kommt.

Wann nimmt man Components?

Wenn mehrere Overlays denselben optionalen Teil brauchen, etwa einen Sidecar oder eine NetworkPolicy.

Wie geht man mit Secrets um?

Nie im Klartext im Git. Sealed Secrets, SOPS oder External Secrets. Der secretGenerator ist nur Base64.

Szenario: Ein Deployment braucht pro Umgebung andere Env-Variablen und Replicas. Wie bauen Sie das?

Base mit Standardwerten. Pro Overlay ein ConfigMap-Generator mit merge und ein Patch für Replicas. Keine Kopie des Deployments.

Mehr

Gerüst

  • Warum? Eine Base, kleine Unterschiede pro Umgebung. Kein Kopieren und keine Templates.
  • Wie innen? kustomization.yaml, Resources laden, Generatoren, Transformer, Namen nachziehen, YAML ausgeben.
  • Zahlen Seit kubectl 1.14 eingebaut. Hash-Suffix am Generator-Namen. In diesem Lauf kubectl 1.37.0 mit Kustomize v5.8.1.
  • Vergleich Helm hat Templates, Releases und Rollback. Kustomize patcht reines YAML.
  • Produktion Overlays pro Umgebung, images für die CI, Secrets verschlüsselt, Argo CD rendert.
  • Design Zwei Ebenen, Components für Optionales, Helm für Fremdsoftware.

Beispiel: Base und Prod-Overlay bauen

# base/kustomization.yaml
resources:
- deployment.yaml          # replicas: 1, image nginx:1.27
configMapGenerator:
- name: web-config
  literals: [LOG_LEVEL=info]

# overlays/prod/kustomization.yaml
resources:
- ../../base
namePrefix: prod-
labels:
- pairs: {env: prod}
images:
- name: nginx
  newTag: "1.28"
patches:
- target: {kind: Deployment, name: web}
  patch: |-
    - op: replace
      path: /spec/replicas
      value: 3
configMapGenerator:
- name: web-config
  behavior: merge
  literals: [LOG_LEVEL=warn]

$ kubectl kustomize overlays/prod
apiVersion: v1
data:
  LOG_LEVEL: warn
kind: ConfigMap
metadata:
  labels:
    env: prod
  name: prod-web-config-dfk4bdbtkk
---
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    env: prod
  name: prod-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - envFrom:
        - configMapRef:
            name: prod-web-config-dfk4bdbtkk
        image: nginx:1.28
        name: web

Echte Ausgabe, kubectl v1.37.0 mit Kustomize v5.8.1. Die Dateien sind hier gekürzt. Es lief ohne Cluster.

  1. prod- steht vor beiden Namen. Das Label env: prod steht an beiden Objekten.
  2. Die ConfigMap hat den Hash-Suffix dfk4bdbtkk. Das configMapRef im Deployment zeigt auf den neuen Namen.
  3. replicas: 3 und nginx:1.28 kommen aus Patch und images. Die Base blieb unverändert.
  4. Der selector hat nur app: web. Das Label env in labels ändert Selektoren nicht.
  5. LOG_LEVEL ist warn, weil das Overlay mit merge den Base-Wert überschreibt.

Vergleich

  • Kustomize: patcht YAML, kein Template, kein Release. Steckt in kubectl.
  • Helm: Go-Templates plus Values, Chart als Paket, Releases mit Rollback und Hooks.
  • Helm Template mit Kustomize: helm template zuerst, dann Kustomize-Patches auf das Ergebnis.
  • Argo CD: Kann Kustomize, Helm und reines YAML aus einem Git-Ordner anwenden.
  • Jsonnet, CUE: Sprachen mit Logik. Mächtiger, aber schwerer zu lernen.
  • Plain YAML: Einfach, aber ohne Wiederverwendung bei vielen Umgebungen.

Produktion

  1. Selektor ändern geht nicht: Mit commonLabels änderte sich der Selector. Das Deployment lässt sich nicht updaten. Lösung: labels nutzen.
  2. Config ändert sich, Pods nicht: Der Hash-Suffix ist aus. Lösung: Hash an lassen.
  3. Overlays driften: Jedes Overlay patcht wild. Lösung: Unterschiede klein halten, Reviews, CI-Build.
  4. Entfernte Objekte bleiben: kubectl apply -k löscht nichts. Lösung: Prune in Argo CD oder --prune mit Labels.
  5. Secrets im Git: Der secretGenerator ist nur Base64. Lösung: SOPS, Sealed Secrets oder External Secrets.
  6. Alte Syntax: bases, patchesStrategicMerge und vars sind deprecated. Lösung: kustomize edit fix und neue Felder.

Diagnose: Werkzeuge und Befehle

  • kubectl kustomize ordner: Zeigt das fertige YAML, ohne Cluster.
  • kubectl diff -k ordner: Zeigt den Unterschied zum Cluster vor dem Apply.
  • kubectl apply -k ordner --dry-run=server: Prüft gegen den API-Server.
  • kustomize edit fix: Wandelt alte Felder in neue um.
  • Argo CD App Diff: Zeigt, was Argo CD aus dem Overlay rendert und was im Cluster steht.
  • Warnungen im Build: Meldungen zu deprecated Feldern in der Ausgabe ernst nehmen.

Senior-Punkte

  1. Das Werkzeug folgt dem Besitzer. Eigene Apps in Kustomize, fremde Pakete in Helm.
  2. Template-Logik ist Schuld. Je mehr if im YAML, desto schwerer die Fehlersuche. Kustomize zwingt zu einfachen Unterschieden.
  3. Release-Verwaltung ersetzt Git. Mit GitOps ist der Rollback ein Revert im Git, nicht helm rollback.
  4. Selektoren sind unveränderlich. Nimm labels und lass Selektoren in Ruhe.
  5. Hash-Suffix ist ein Feature. Er macht Config-Änderungen zu sauberen Rollouts.
  6. Einheitliche Struktur. Ein Standard-Layout mit base und overlays hilft jedem Team beim Lesen.
