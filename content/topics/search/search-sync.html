Suchindex synchron halten mit der Datenbank

Search · Tier 1 · Quellen: Debezium Reference (PostgreSQL Connector, Outbox Event Router), Elasticsearch 9 Reference (Aliases, Reindex API, Bulk API, Index API version_type, refresh, Index Settings), PostgreSQL 17 Doku (Logical Decoding, Replication Slots, max_slot_wal_keep_size), microservices.io: Transactional Outbox

Kern: Der Suchindex ist eine Kopie der Datenbank, und jede Änderung muss dort ankommen. Das Dual-Write-Problem heisst: DB und Index in zwei Schritten schreiben geht bei einem Fehler auseinander. Die Lösung ist, Änderungen aus der DB-Transaktion heraus weiterzugeben (Outbox oder CDC), idempotent und mit Eventual Consistency.

1. Wo sitzt die Synchronisation?

  1. Image API: Sie schreibt die Bild-Zeile und ein Outbox-Event in einer lokalen Transaktion. Beides oder nichts.
  2. WAL: PostgreSQL schreibt jede Änderung ins Write-Ahead Log, das Änderungsprotokoll der DB.
  3. Debezium: Debezium ist ein CDC-Werkzeug (Change Data Capture). Es liest das WAL über Logical Decoding und einen Replication Slot.
  4. Kafka: Die Events landen in einem Topic. Der Schlüssel ist die Bild-ID. So bleibt die Reihenfolge pro Bild erhalten.
  5. Indexer: Ein Consumer schreibt per _bulk in Elasticsearch. Bei Fehlern wiederholt er.
  6. Alias: Die Suche liest über einen Alias, also einen Zweitnamen für den echten Index. So kann man den Index ohne Ausfall austauschen.

Ohne Kafka geht es auch einfacher: Ein Poller liest die Outbox-Tabelle alle paar Sekunden und schreibt direkt in den Index.

2. Die Reise einer Änderung (die Geschichte zum Merken)

  1. Commit: Ein Bild bekommt neue Labels. Die API ändert die Zeile image und schreibt ein Event in outbox. Ein Commit für beides.
  2. Erfassen: Ein Poller liest offene Outbox-Zeilen. Oder Debezium liest den Insert aus dem WAL. Die Änderung kann nicht verloren gehen, sie steht in der DB.
  3. Upsert: Der Indexer schreibt das Dokument mit der DB-ID als Dokument-ID. Zweimal schreiben ergibt dasselbe Ergebnis: idempotent.
  4. Version prüfen: Kommt ein altes Event später an, darf es den neuen Stand nicht überschreiben. Elasticsearch prüft das mit version_type=external und der Version aus der DB.
  5. Fehler: Ist der Cluster nicht erreichbar, bleibt das Event offen. Der Indexer versucht es später erneut. Das heisst at-least-once: mindestens einmal, manchmal öfter.
  6. Refresh: Nach dem nächsten Refresh ist die Änderung suchbar. Die Gesamt-Verzögerung (Lag) ist Pipeline plus Refresh.
  7. Reindex: Ändert sich das Mapping, baut man einen neuen Index und schaltet den Alias um. Die Suche merkt nichts.

3. Beispiel: Dual Write gegen Outbox

# A) Dual Write: erst DB-Commit, dann Index-Aufruf
with db: db.execute("INSERT INTO image VALUES (1, 'Hund am Strand', 1)")
es.upsert(1, {...}, 1)                      # ConnectionError -> Bild fehlt im Index

# B) Outbox: Zeile + Event in EINER Transaktion
def save(image_id, caption, version):
    with db:
        db.execute("INSERT OR REPLACE INTO image VALUES (?,?,?)", ...)
        db.execute("INSERT INTO outbox(image_id, version, payload) VALUES (?,?,?)", ...)
# Relay: offene Events in Reihenfolge senden, erst nach Erfolg als gesendet markieren
# Index: Upsert nur, wenn version neuer ist (wie version_type=external)
A) Dual write: commit DB, then call the index
   index call failed: search cluster timeout
   DB rows: [(1, 'Hund am Strand', 1)]
   index docs: {} -> image is NOT searchable, nobody retries
B) Outbox: row + event in ONE transaction, relay retries
   round 1: event 1 (v1) failed: search cluster timeout -> stays in outbox
   round 2: event 1 (v1) failed: search cluster timeout -> stays in outbox
   round 3: event 1 (v1) indexed
   round 3: event 2 (v2) indexed
   index docs: {1: {'caption': 'Hund und Ball am Strand', 'version': 2}}
C) Redelivery of an old event (at-least-once): ignored (old version)
   index docs: {1: {'caption': 'Hund und Ball am Strand', 'version': 2}}

Echte Ausgabe, Python 3.12 mit SQLite (Modell von Dual Write und Transactional Outbox, nicht Elasticsearch oder Debezium selbst). Der Index ist eine Python-Klasse, die beim Schreiben absichtlich ausfällt.

  1. Bei A) ist die DB-Zeile da, der Index leer. Niemand merkt es, niemand wiederholt. Das ist das Dual-Write-Problem.
  2. Umgekehrte Reihenfolge (erst Index, dann DB) hilft nicht. Dann steht im Index ein Bild, das es in der DB nicht gibt.
  3. Bei B) steht das Event in der DB. Zwei Fehlversuche ändern nichts, Runde 3 schafft es.
  4. Die Events gehen in Reihenfolge: erst v1, dann v2. Am Ende steht v2 im Index.
  5. Bei C) kommt v1 noch einmal. Der Versions-Check ignoriert es. Ohne ihn stünde der alte Text wieder im Index.

4. Details, die Interviewer fragen

  1. Dual-Write-Problem: Zwei Systeme ohne gemeinsame Transaktion. Fällt der zweite Schritt aus, sind sie inkonsistent. Zwei parallele Requests können sich ausserdem in falscher Reihenfolge überholen.
  2. Warum kein verteiltes Commit (2PC)? Elasticsearch unterstützt kein Two-Phase Commit. Und 2PC koppelt die Verfügbarkeit beider Systeme.
  3. Transactional Outbox: Die App schreibt das Event in eine Outbox-Tabelle in derselben DB-Transaktion. Ein separater Prozess gibt es weiter. So hängt die Weitergabe nur am DB-Commit.
  4. Outbox weitergeben, zwei Wege: 1. Polling Publisher: liest offene Zeilen per SQL, markiert sie als gesendet. Einfach, etwas Verzögerung, Last auf der DB. 2. CDC: Debezium liest die Inserts aus dem WAL. Kein Polling, aber mehr Infrastruktur.
  5. Debezium Outbox Event Router: Eine SMT (Single Message Transformation) in Kafka Connect. Sie routet Outbox-Zeilen nach aggregatetype in Topics, Standard outbox.event.<aggregatetype>. Die Spalte id dient Consumern zum Erkennen von Duplikaten.
  6. CDC direkt auf der Tabelle: Debezium kann auch die image-Tabelle selbst lesen. Kein Outbox-Code nötig. Nachteil: Das Event ist das DB-Schema. Jede Spaltenänderung bricht den Consumer.
  7. Debezium und PostgreSQL: Der Connector nutzt Logical Decoding mit dem Plugin pgoutput und einen Replication Slot. Beim Start macht er einen Snapshot der Tabelle, dann streamt er Änderungen.
  8. Replication Slot: Der Slot merkt sich, bis wohin der Consumer gelesen hat. PostgreSQL behält das WAL ab dieser Stelle. Steht Debezium still, wächst das WAL und kann die Platte füllen.
  9. At-least-once und Idempotenz: CDC und Outbox liefern mindestens einmal. Darum muss das Schreiben in den Index idempotent sein: Dokument-ID = DB-Primärschlüssel, Upsert statt Insert.
  10. Reihenfolge: Kafka garantiert Reihenfolge nur pro Partition. Darum Schlüssel = Bild-ID. Zusätzlich schützt version_type=external: Elasticsearch nimmt nur eine höhere Version an.
  11. Deletes: Ein gelöschtes Bild muss auch aus dem Index. CDC liefert ein Delete-Event. Bei Outbox schreibt die App ein eigenes „deleted“-Event. Bei Soft Delete filtert der Index nach dem Flag.
  12. Eventual Consistency: Der Index hinkt der DB hinterher: Pipeline-Lag plus Refresh (Standard 1 s). Die API zeigt nach dem Speichern darum Daten aus der DB, nicht aus der Suche.
  13. Read-your-writes: Wenn die Suche sofort stimmen muss: synchron indexieren mit refresh=wait_for. Der Request wartet bis zum nächsten Refresh. Kostet Latenz, ersetzt aber nicht die Outbox.
  14. Warum Reindex? Den Typ oder Analyzer eines bestehenden Feldes kann man nicht ändern. Neue Felder kann man hinzufügen, alte Dokumente haben sie aber nicht.
  15. Reindex ohne Ausfall: 1. Neuen Index images_v3 mit neuem Mapping anlegen. 2. Daten laden: _reindex aus dem alten Index oder neu aus der DB. 3. Laufende Änderungen auch in v3 schreiben. 4. Prüfen (Anzahl, Stichproben). 5. Alias mit _aliases atomar umschalten. 6. Alten Index später löschen.
  16. Änderungen während des Reindex: Entweder schreibt der Indexer in beide Indizes. Oder man merkt sich die CDC-Position vor dem Start und spielt ab dort in v3 nach. Wegen Versions-Check schadet doppeltes Abspielen nicht.
  17. _reindex oder aus der DB? _reindex kopiert nur _source. Fehlen dort Daten oder ändern sich Embeddings, muss man aus der DB neu bauen. Die DB ist die Quelle der Wahrheit.
  18. Schnelles Laden: Im neuen Index refresh_interval: -1 und number_of_replicas: 0. Mit _bulk laden. Danach beides zurücksetzen.
  19. Abgleich (Reconciliation): Ein Job vergleicht regelmässig DB und Index: Anzahl, Versionen, fehlende IDs. Er repariert Abweichungen. Er fängt Fehler, die die Pipeline nicht sieht.

5. Vergleich

  • Dual Write (synchron im Request): einfach, schnell sichtbar. Inkonsistent bei Fehlern, Reihenfolge nicht sicher. Nur für Prototypen.
  • Outbox + Poller: konsistent, keine neue Infrastruktur, nur SQL. Leichte Verzögerung, Polling-Last, Outbox-Tabelle aufräumen.
  • Outbox + Debezium: konsistent, kurze Verzögerung, saubere Events mit eigenem Format. Braucht Kafka Connect und Replication Slot.
  • CDC direkt auf Tabellen: kein App-Code, fängt auch Änderungen per SQL-Skript. Events koppeln an das DB-Schema.
  • Batch-Reindex nach updated_at: einfach, gut als Backfill. Grosse Verzögerung, verpasst Deletes, Probleme bei gleichen Zeitstempeln.
  • Kein zweites System (PostgreSQL Full Text, pgvector): immer konsistent, kein Sync-Problem. Grenzen bei Relevanz und Skalierung.

6. In der Produktion

  1. Bilder fehlen in der Suche: Ein Dual Write ist still ausgefallen. Lösung: Outbox oder CDC, dazu ein Abgleich-Job, der fehlende IDs nachindexiert.
  2. Alter Stand im Index: Ein altes Event hat ein neues überholt. Lösung: Kafka-Schlüssel = Bild-ID und version_type=external mit DB-Version.
  3. PostgreSQL-Platte läuft voll: Debezium steht, der Replication Slot hält das WAL fest. Lösung: Slot-Lag überwachen und alarmieren. max_slot_wal_keep_size begrenzt das WAL, dann ist der Slot aber ungültig und man braucht einen neuen Snapshot.
  4. Outbox-Tabelle wächst endlos: Gesendete Zeilen bleiben liegen. Lösung: regelmässig löschen oder nach Datum partitionieren. Mit Debezium darf man die Zeile direkt nach dem Insert löschen, das Event steht im WAL.
  5. Gelöschte Bilder tauchen in der Suche auf: Delete-Events fehlen. Lösung: Delete als eigenes Event, plus Abgleich.
  6. Suche fällt beim Mapping-Wechsel aus: Index gelöscht und neu angelegt. Lösung: Alias von Anfang an, neuer Index, atomarer Umschalt.
  7. Lag wächst unter Last: Der Indexer schreibt einzeln. Lösung: _bulk, mehr Partitionen und Consumer, refresh_interval erhöhen.
  8. Reindex frisst den Cluster: _reindex konkurriert mit der Suche. Lösung: requests_per_second drosseln oder slices gezielt setzen, nachts laufen lassen.

7. Diagnose: Werkzeuge und Befehle

  • Anzahl vergleichen: GET images/_count gegen SELECT count(*) FROM image WHERE deleted = false;
  • Welcher Index ist live: GET _cat/aliases/images?v und GET _cat/indices/images_*?v.
  • Reindex-Fortschritt: GET _tasks?actions=*reindex&detailed.
  • Debezium-Status: GET /connectors/<name>/status an der Kafka-Connect-REST-API.
  • Kafka-Lag: kafka-consumer-groups.sh --bootstrap-server … --describe --group indexer.
  • Slot-Lag in PostgreSQL: SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) FROM pg_replication_slots;
  • Outbox-Stau beim Poller: SELECT count(*), min(created_at) FROM outbox WHERE sent = false;
  • Bulk-Fehler: Die _bulk-Antwort hat "errors": true und pro Eintrag einen Status. HTTP 200 heisst nicht, dass alles geklappt hat.

8. Senior-Punkte

  1. Die DB ist die Wahrheit, der Index ist eine Projektion. Ein kompletter Neuaufbau aus der DB muss jederzeit möglich sein.
  2. Nie Dual Write im Request. Outbox oder CDC, und das im Design sofort sagen.
  3. At-least-once plus Idempotenz ist das Ziel, nicht exactly-once. ID = Primärschlüssel, Versions-Check gegen Überholen.
  4. Alias vom ersten Tag an. Die App kennt nie den echten Indexnamen.
  5. Lag ist eine Metrik. Man misst Zeit von Commit bis suchbar und alarmiert darauf.
  6. Abgleich-Job als Sicherheitsnetz. Jede Pipeline verliert irgendwann etwas.

10. Fallen

  • „Ich schreibe erst in die DB und dann in Elasticsearch, das reicht.“ → Falsch. Das ist der Dual Write. Ein Fehler dazwischen macht beide inkonsistent.
  • „@Transactional deckt auch Elasticsearch ab.“ → Falsch. Die Transaktion gilt nur für die DB.
  • „Kafka liefert exactly-once bis in Elasticsearch.“ → Falsch. Rechnen Sie mit Duplikaten und machen Sie das Schreiben idempotent.
  • „Mapping ändern geht im laufenden Index.“ → Nur neue Felder. Typ oder Analyzer ändern braucht einen neuen Index.
  • „Index löschen und neu bauen ist ein Reindex.“ → Das ist ein Ausfall. Richtig: neuer Index plus Alias-Umschaltung.
  • „Replication Slots sind kostenlos.“ → Ein stehender Slot hält WAL fest und kann die DB-Platte füllen.

11. Fragen

Was ist das Dual-Write-Problem?

Eine App schreibt in zwei Systeme ohne gemeinsame Transaktion. Fällt ein Schritt aus oder überholen sich Requests, sind DB und Index inkonsistent.

Warum hilft es nicht, erst in den Index und dann in die DB zu schreiben?

Dann gibt es bei einem DB-Fehler Dokumente im Index, die es in der DB nicht gibt. Das Problem dreht sich nur um.

Was ist das Transactional-Outbox-Pattern?

Das Event kommt in eine Outbox-Tabelle in derselben DB-Transaktion wie die Daten. Ein separater Prozess gibt es an Kafka oder den Index weiter.

Wie kommt das Event aus der Outbox heraus?

Per Polling (SQL auf offene Zeilen, dann als gesendet markieren) oder per CDC (Debezium liest die Inserts aus dem WAL).

Was ist CDC?

Change Data Capture: Änderungen werden aus dem Transaktions-Log der DB gelesen, nicht aus der App. Bei PostgreSQL über Logical Decoding und einen Replication Slot.

Was ist Debezium?

Eine Sammlung von Kafka-Connect-Connectors für CDC. Sie liest das DB-Log und schreibt jede Änderung als Event in Kafka.

Outbox oder CDC direkt auf der Tabelle?

Outbox: eigenes, stabiles Event-Format, aber App-Code. CDC auf der Tabelle: kein App-Code, aber Events hängen am DB-Schema.

Was macht der Debezium Outbox Event Router?

Eine SMT, die Outbox-Zeilen nach aggregatetype in Topics routet und den payload als Event-Inhalt nimmt. Die id hilft Consumern gegen Duplikate.

Was ist ein Replication Slot und welches Risiko hat er?

Er merkt sich den Lese-Stand des Consumers. PostgreSQL behält das WAL ab dort. Steht der Consumer, wächst das WAL und kann die Platte füllen.

Welche Liefergarantie haben Outbox und CDC?

At-least-once. Duplikate kommen vor. Darum idempotent schreiben: Dokument-ID = Primärschlüssel, Upsert.

Wie verhindern Sie, dass ein altes Event einen neuen Stand überschreibt?

Kafka-Schlüssel = Entitäts-ID für Reihenfolge pro Entität. Zusätzlich version_type=external mit einer Version aus der DB.

Wie behandeln Sie Deletes?

CDC liefert ein Delete-Event, die Outbox ein eigenes „deleted“-Event. Der Indexer löscht das Dokument. Ein Abgleich-Job fängt verpasste Deletes.

Was heisst Eventual Consistency für die Suche?

Der Index zeigt Änderungen mit Verzögerung: Pipeline-Lag plus Refresh. Für kurze Zeit sehen Suche und DB verschieden aus.

Wie zeigt die UI ein gerade gespeichertes Bild, obwohl die Suche es noch nicht kennt?

Die Detail-Seite liest aus der DB, nicht aus dem Index. Oder der Write nutzt refresh=wait_for, wenn es sofort suchbar sein muss.

Wann brauchen Sie einen Reindex?

Bei Änderung von Feldtyp oder Analyzer, bei neuem Embedding-Modell und nach Datenfehlern. Neue Felder allein brauchen keinen neuen Index, aber alte Dokumente füllen.

Wie machen Sie einen Reindex ohne Ausfall?

Neuer Index mit neuem Mapping, Daten laden, laufende Änderungen mitschreiben, prüfen, Alias mit _aliases atomar umschalten, alten Index später löschen.

Was ist ein Index-Alias?

Ein Zweitname, der auf einen oder mehrere Indizes zeigt. Die App sucht über den Alias, so kann man den echten Index austauschen.

_reindex-API oder Neuaufbau aus der DB?

_reindex kopiert nur _source und ist schnell. Aus der DB neu bauen, wenn Daten fehlen, sich ändern oder neue Embeddings nötig sind.

Wie laden Sie Millionen Dokumente schnell?

_bulk-API, refresh_interval auf -1, number_of_replicas auf 0. Danach beides zurücksetzen.

Wie merken Sie, dass Index und DB auseinanderlaufen?

Abgleich-Job (Anzahl, Versionen, fehlende IDs), Metriken für Lag, Kafka-Consumer-Lag, Slot-Lag in PostgreSQL, Fehler in den _bulk-Antworten.

Warum kein Two-Phase Commit zwischen DB und Elasticsearch?

Elasticsearch unterstützt es nicht. 2PC koppelt ausserdem die Verfügbarkeit beider Systeme und blockiert bei Ausfällen.

Szenario: Nach dem Upload ist ein Bild in der DB, aber nie in der Suche. Wie finden und beheben Sie das?

Wahrscheinlich Dual Write mit stillem Fehler. Prüfen: Logs, _bulk-Fehler, Anzahl DB gegen _count. Fix: Outbox oder CDC, idempotenter Indexer, Abgleich-Job für Altlasten.

Szenario: Sie müssen den Analyzer des Caption-Feldes ändern, die Suche darf nicht ausfallen. Wie gehen Sie vor?

images_v3 mit neuem Mapping anlegen, mit _bulk aus der DB oder per _reindex füllen, laufende Events auch in v3 schreiben, prüfen, Alias images atomar umschalten, v2 später löschen.

Szenario: Die PostgreSQL-Platte füllt sich nachts, obwohl kaum geschrieben wird. Woran denken Sie?

An einen inaktiven Replication Slot von Debezium, der WAL festhält. Prüfen mit pg_replication_slots. Fix: Connector reparieren, Lag-Alarm, max_slot_wal_keep_size als Grenze.
