Inverted Index: wie Suche funktioniert

Kern: Ein Inverted Index ist eine Tabelle von Wort → Liste der Dokumente, die das Wort enthalten. Er löst das Problem, dass man sonst jedes Dokument lesen müsste. Die Suche schlägt nur die Wörter der Anfrage nach und sortiert die Treffer mit BM25 nach Relevanz.

1. Wo sitzt die Suche? (Beispiel: Bild-Upload mit Erkennung)

  1. Client lädt ein Bild hoch. Die Image API legt die Datei in den Object Storage, also einen Datei-Speicher wie S3.
  2. Ein Erkennungs-Modell liest das Bild. Es liefert Labels („hund“, „strand“), eine Caption (Satz zum Bild) und ein Embedding (Zahlenvektor).
  3. PostgreSQL speichert die Metadaten: ID, Besitzer, Datei-Pfad, Labels, Caption. Die DB ist die Quelle der Wahrheit.
  4. Ein Outbox- oder CDC-Prozess kopiert jede Änderung in den Suchindex. Das ist eine eigene Seite: „Suchindex synchron halten“.
  5. Die Suchanfrage geht an den Suchindex, nicht an die DB. Er liefert sortierte Bild-IDs.
  6. Die API baut daraus die Antwort, z. B. mit Vorschau-URLs aus dem Object Storage.

Der Suchindex enthält zwei Strukturen. Der Inverted Index sucht nach Wörtern (diese Seite). Der Vektorindex sucht nach Bedeutung (Seite „Vektorsuche“).

2. Die Reise einer Suchanfrage (die Geschichte zum Merken)

  1. Anfrage: Die Nutzerin tippt „Rote Hunde“. Die API schickt eine match-Query an Elasticsearch.
  2. Analyzer: Der Analyzer zerlegt den Text in Terms, also normierte Wörter. Er nutzt denselben Analyzer wie beim Indexieren. Aus „Rote Hunde“ wird z. B. [rot, hund].
  3. Term Dictionary: Das Term Dictionary ist die sortierte Liste aller Terms eines Feldes. Lucene findet einen Term darin in wenigen Schritten.
  4. Postings lesen: Zu jedem Term gibt es eine Postings-Liste: sortierte Doc-IDs, Häufigkeit, Positionen. Nur diese Listen werden gelesen.
  5. Kombinieren: AND schneidet die Listen, OR vereinigt sie. Ein Filter (z. B. owner_id) schneidet weitere Doc-IDs weg.
  6. Score: Jeder Treffer bekommt einen BM25-Score. Jeder Shard (Teil des Index) liefert seine besten k Treffer.
  7. Merge und Fetch: Der Koordinator-Knoten sortiert alle Shard-Ergebnisse. Dann holt er nur für die Gewinner das _source-Dokument. Das heisst query then fetch.

Beim Indexieren läuft der Weg umgekehrt: Text → Analyzer → Terms → neue Einträge im Index. Lucene schreibt sie in ein neues Segment. Nach dem nächsten Refresh (Standard: 1 Sekunde) ist das Dokument suchbar.

3. Beispiel: Inverted Index und BM25 selbst bauen

STOP = {"am", "im", "auf", "kein", "zwei"}
def analyze(text):                     # Tokenizer + lowercase + Stopwörter
    tokens = re.findall(r"\w+", text.lower())
    return [(pos, t) for pos, t in enumerate(tokens) if t not in STOP]

for d, text in docs.items():           # Index bauen: Term -> {Doc: [Positionen]}
    for pos, t in analyze(text):
        index[t].setdefault(d, []).append(pos)

# BM25 wie Lucene: k1 = 1.2, b = 0.75
idf = math.log(1 + (N - n + 0.5) / (n + 0.5))          # n = Docs mit dem Term
tfn = tf / (tf + k1 * (1 - b + b * length[d] / avgdl))
score += idf * tfn
1) Analyzer: 'Roter Hund am Strand' -> ['roter', 'hund', 'strand']
2) Inverted index (term -> doc:positions)
   ball     -> 3:[1]
   hund     -> 1:[1], 3:[5]
   hunde    -> 2:[1]
   katze    -> 4:[0]
   liegt    -> 4:[1]
   park     -> 2:[4]
   rotem    -> 4:[3]
   roter    -> 1:[0], 3:[0]
   sofa     -> 4:[4]
   spielen  -> 2:[2]
   strand   -> 1:[3], 3:[3]
3) BM25 for query 'roter Hund' (N=4, avgdl=3.5)
   doc 1 score=0.669  [roter: idf=0.693 tf=1 dl=3 -> 0.335; hund: idf=0.693 tf=1 dl=3 -> 0.335]  'Roter Hund am Strand'
   doc 3 score=0.595  [roter: idf=0.693 tf=1 dl=4 -> 0.298; hund: idf=0.693 tf=1 dl=4 -> 0.298]  'Roter Ball am Strand, kein Hund'
3) BM25 for query 'Hunde' (N=4, avgdl=3.5)
   doc 2 score=0.581  [hunde: idf=1.204 tf=1 dl=3 -> 0.581]  'Zwei Hunde spielen im Park'
4) Phrase 'roter hund': docs where position(hund) = position(roter)+1 -> [1]

Echte Ausgabe, Python 3.12 (Modell von Lucene-Inverted-Index und Lucene-BM25, nicht Elasticsearch selbst). Dokumente: 1 „Roter Hund am Strand“, 2 „Zwei Hunde spielen im Park“, 3 „Roter Ball am Strand, kein Hund“, 4 „Katze liegt auf rotem Sofa“.

  1. Der Analyzer macht alles klein und wirft Stopwörter weg. „am“ ist nicht im Index.
  2. Der Index ist nach Term sortiert. Jeder Term zeigt auf Doc-IDs und Positionen.
  3. „roter Hund“ liest nur zwei Listen: roter und hund. Dokument 2 und 4 werden nie angefasst.
  4. Doc 1 und Doc 3 haben gleiche idf und gleiche tf. Doc 1 gewinnt, weil es kürzer ist (dl=3 statt 4). Das ist die Längen-Normalisierung mit b.
  5. Doc 3 sagt „kein Hund“ und ist trotzdem Platz 2. Wort-Suche versteht keine Bedeutung.
  6. „Hunde“ findet Doc 1 nicht. „hund“ und „hunde“ sind verschiedene Terms. Ohne Stemming fehlen Treffer. Gleich bei „roter“ und „rotem“.
  7. „hunde“ kommt nur in 1 Dokument vor. Darum ist seine idf höher (1.204) als die von „hund“ (0.693). Seltene Wörter zählen mehr.
  8. Die Positionen erlauben eine Phrasensuche: „roter hund“ direkt hintereinander gibt es nur in Doc 1.

Dasselbe in Elasticsearch (Syntax echt, hier nicht ausgeführt):

    "labels":   { "type": "keyword" },

{ "query": { "bool": {
    "must":   { "match": { "caption": "rote Hunde" } },
    "filter": { "term":  { "owner_id": "42" } } } } }

Dasselbe in PostgreSQL (die „DB-Query“-Frage; Syntax echt, hier nicht ausgeführt):

ALTER TABLE image ADD COLUMN caption_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('german', caption)) STORED;
CREATE INDEX image_caption_gin ON image USING gin (caption_tsv);

SELECT id, ts_rank(caption_tsv, q) AS rank
FROM image, websearch_to_tsquery('german', 'rote Hunde') AS q
WHERE owner_id = 42 AND caption_tsv @@ q
ORDER BY rank DESC LIMIT 20;

Der GIN-Index von PostgreSQL ist ebenfalls ein Inverted Index. to_tsvector('german', …) ist der Analyzer mit deutschem Stemming.

4. Details, die Interviewer fragen

  1. So antworten Sie bei „Bild-Upload + Erkennung + Suche“: Datei in Object Storage. Metadaten und Labels in PostgreSQL. Änderungen per Outbox/CDC in Elasticsearch. Suche per bool-Query: match auf Caption, filter auf Besitzer. Für Bedeutung zusätzlich Vektorsuche.
  2. Analyzer: Ein Analyzer wandelt Text in Terms um. Er hat drei Teile: Character Filter (Zeichen ersetzen, z. B. HTML weg), Tokenizer (in Wörter zerlegen), Token Filter (lowercase, Stopwörter, Stemming, Synonyme). Details auf der Seite „Analyzer, Tokenizer, Stemming“.
  3. Standard-Analyzer: Der standard-Analyzer zerlegt nach Unicode-Wortgrenzen und macht lowercase. Er entfernt standardmässig keine Stopwörter und stemmt nicht. Für Deutsch gibt es den german-Analyzer.
  4. Gleicher Analyzer beim Indexieren und Suchen: Die Terms müssen exakt gleich sein. Sonst findet die Suche nichts.
  5. text vs keyword: Ein text-Feld wird analysiert, gut für Volltext. Ein keyword-Feld bleibt ein ganzer Wert, gut für Filter, Sortierung, Aggregation. Labels, IDs, Status sind keyword.
  6. match vs term: match analysiert die Anfrage. term sucht den Wert genau so, ohne Analyzer. term auf ein text-Feld mit „Hund“ findet nichts, weil „hund“ indexiert ist.
  7. Query- vs Filter-Kontext: must und should berechnen einen Score. filter und must_not sagen nur ja oder nein. Filter sind schneller und werden gecacht.
  8. BM25: BM25 ist die Standard-Relevanzformel in Elasticsearch, OpenSearch und Lucene. Drei Teile: tf (wie oft der Term im Dokument steht), idf (wie selten er im Index ist), Feldlänge (kurze Felder zählen mehr). Details auf der Seite „Relevanz: TF-IDF und BM25“.
  9. k1 und b: k1 (Standard 1.2) regelt die Sättigung: Der 10. Treffer eines Wortes bringt kaum mehr als der 3. b (Standard 0.75) regelt die Längen-Normalisierung. b = 0 schaltet sie aus.
  10. Postings-Liste: Die Doc-IDs sind sortiert und komprimiert (als Differenzen gespeichert). Darum kann Lucene Listen schnell schneiden. Mit Skip-Daten springt es über ganze Blöcke.
  11. Positionen: Lucene speichert pro Treffer die Position im Text. Das braucht man für match_phrase und Abstand-Suche (slop).
  12. Segmente: Ein Lucene-Index besteht aus Segmenten, also kleinen, unveränderlichen Teil-Indizes. Neue Dokumente kommen in neue Segmente. Im Hintergrund mergt Lucene kleine Segmente zu grossen.
  13. Update und Delete: Ein Segment ist unveränderlich. Ein Delete markiert das Dokument nur als gelöscht. Ein Update ist Delete plus neues Dokument. Erst ein Merge entfernt die alten Daten wirklich.
  14. Near Real-Time: Ein Refresh macht neue Segmente suchbar, standardmässig jede Sekunde. Ein Shard ohne Suchen seit 30 Sekunden ist search idle und refresht erst bei der nächsten Suche.
  15. Translog und Flush: Das Translog schreibt jede Operation sofort auf die Platte. So gehen Daten bei einem Absturz nicht verloren. Ein Flush macht einen Lucene-Commit und leert das Translog.
  16. Doc Values: Doc Values sind eine spaltenweise Speicherung pro Feld. Sie dienen zum Sortieren und Aggregieren. Der Inverted Index geht von Wort zu Doc, Doc Values gehen von Doc zu Wert.
  17. Shards und IDF: Jeder Shard rechnet idf nur mit seinen eigenen Dokumenten. Bei wenigen Dokumenten springen die Scores darum. search_type=dfs_query_then_fetch rechnet idf global, kostet aber eine Runde mehr.
  18. Tiefe Paginierung: from + size ist auf 10 000 begrenzt (index.max_result_window). Für tiefes Blättern nutzt man search_after mit einem Point in Time (PIT).
  19. Gesamtzahl der Treffer: Elasticsearch zählt standardmässig genau bis 10 000 (track_total_hits). Darüber zeigt es „≥ 10 000“. So kann Lucene schwache Treffer überspringen und ist schneller.

5. Vergleich

  • Inverted Index (Elasticsearch, OpenSearch, Solr): Volltextsuche mit Relevanz, Tippfehler-Toleranz (fuzziness), Facetten. Eigenes System, das man synchron halten muss.
  • PostgreSQL Full Text Search: tsvector, tsquery, GIN-Index. Kein zweites System, transaktional aktuell. Aber ts_rank ist kein BM25: Es kennt keine idf über alle Dokumente.
  • B-Tree-Index (normaler DB-Index): sucht Werte von links: caption = '…' oder LIKE 'Hund%'. Für LIKE '%hund%' hilft er nicht: Die DB liest die ganze Tabelle (Seq Scan).
  • pg_trgm mit GIN: Ein Trigramm-Index macht LIKE '%hund%' und Ähnlichkeitssuche schnell. Er kennt aber keine Wörter und keine Relevanz.
  • TF-IDF: der Vorgänger von BM25. Keine Sättigung bei tf, schwächere Längen-Normalisierung.
  • Vektorsuche: sucht nach Bedeutung statt nach Wörtern. Findet „Welpe“ bei „Hund“. Schwach bei exakten Wörtern, Namen, IDs. Darum oft beides: Hybrid Search.

6. In der Produktion

  1. „Ich habe gespeichert, aber finde es nicht“: Das Dokument ist noch nicht refresht. Lösung: Eventual Consistency akzeptieren oder beim Schreiben refresh=wait_for. Nie nach jedem Dokument _refresh aufrufen.
  2. Keine Treffer trotz passendem Wort: Falscher Analyzer oder term auf ein text-Feld. Lösung: mit _analyze prüfen, was im Index steht.
  3. Mapping Explosion: Dynamisches Mapping legt für jeden neuen JSON-Schlüssel ein Feld an. Bei freien Labels als Schlüssel wächst das Mapping ohne Grenze. Lösung: "dynamic": "strict" und Labels als Werte eines keyword-Feldes.
  4. Falsches Mapping: Den Typ eines bestehenden Feldes kann man nicht ändern. Lösung: neuer Index, Reindex, Alias umschalten (Seite „Suchindex synchron halten“).
  5. Langsame Suche durch tiefe Paginierung: from=9000 lässt jeden Shard 9000+ Treffer sortieren. Lösung: search_after mit PIT.
  6. Langsames Bulk-Laden: Jeder Refresh erzeugt kleine Segmente. Lösung: beim Laden refresh_interval: -1 und _bulk-API, danach zurücksetzen.
  7. Viele gelöschte Dokumente: Häufige Updates füllen Segmente mit gelöschten Docs. Speicher und Suche leiden. Merges räumen auf. Bei reinen Lese-Indizes hilft _forcemerge.
  8. LIKE '%…%' in PostgreSQL bei Millionen Zeilen: Seq Scan bei jeder Suche. Lösung: Full Text mit GIN, pg_trgm oder ein Suchindex.

7. Diagnose: Werkzeuge und APIs

  • GET images/_analyze {"field": "caption", "text": "Rote Hunde"}: zeigt die Terms, die der Analyzer erzeugt.
  • GET images/_explain/1 {"query": …}: zeigt, wie der BM25-Score für Dokument 1 entsteht (idf, tf, Feldlänge).
  • "explain": true in _search: dieselbe Erklärung für jeden Treffer.
  • "profile": true in _search (Profile API): Zeit pro Query-Teil und pro Shard.
  • GET images/_mapping: welches Feld welchen Typ und Analyzer hat.
  • GET _cat/indices?v und GET _cat/segments/images?v: Grösse, Dokumente, gelöschte Dokumente, Segmente.
  • Search Slow Log (index.search.slowlog.threshold.query.warn): loggt langsame Queries.
  • PostgreSQL: EXPLAIN (ANALYZE, BUFFERS) SELECT … zeigt, ob der GIN-Index genutzt wird (Bitmap Index Scan) oder ein Seq Scan läuft.

8. Senior-Punkte

  1. Die DB bleibt die Quelle der Wahrheit. Der Suchindex ist eine abgeleitete Kopie. Man muss ihn jederzeit aus der DB neu bauen können.
  2. Suche ist eventual consistent. Das sagt man im Design laut und plant dafür (Refresh, Sync-Verzögerung).
  3. Erst PostgreSQL, dann Elasticsearch. Für wenige Millionen Zeilen und einfache Suche reicht Full Text mit GIN. Ein zweites System kostet Betrieb und Synchronisation.
  4. Relevanz ist ein Produkt-Thema. Man misst sie mit echten Anfragen (z. B. Klickrate, Testsets), nicht nach Gefühl.
  5. Filter statt Query, wenn kein Score nötig ist. Besitzer, Status, Datum gehören in filter.
  6. Berechtigungen gehören in den Index. Ohne owner_id-Filter sieht ein Nutzer fremde Bilder in den Treffern.

10. Fallen

  • „Die Suche läuft mit LIKE '%hund%' in der DB.“ → Bei vielen Zeilen ein Seq Scan, ohne Relevanz und ohne Stemming.
  • „Elasticsearch durchsucht alle Dokumente.“ → Falsch. Es liest nur die Postings-Listen der gesuchten Terms.
  • „Nach dem Index-Request ist das Dokument sofort suchbar.“ → Falsch. Erst nach dem nächsten Refresh.
  • „term und match sind gleich.“ → Falsch. term analysiert die Anfrage nicht.
  • „Ein höherer Score heisst X Prozent relevanter.“ → Falsch. Scores sind nur innerhalb einer Anfrage vergleichbar.
  • „Elasticsearch ist meine Datenbank.“ → Riskant. Keine Transaktionen über Dokumente, Mapping-Änderungen brauchen Reindex.

11. Fragen

Was ist ein Inverted Index?

Eine Struktur von Term zu Liste der Dokumente, die den Term enthalten. Die Suche liest nur die Listen der gesuchten Terms statt aller Dokumente.

Warum heisst er „inverted“?

Ein Dokument zeigt normal auf seine Wörter. Der Index dreht das um: Das Wort zeigt auf seine Dokumente.

Was steht in einer Postings-Liste?

Sortierte Doc-IDs, pro Doc die Häufigkeit des Terms und optional die Positionen und Offsets.

Was macht ein Analyzer?

Er wandelt Text in Terms um: Character Filter, dann Tokenizer, dann Token Filter wie lowercase, Stopwörter, Stemming, Synonyme.

Warum muss der Analyzer beim Indexieren und Suchen gleich sein?

Die Suche vergleicht Terms exakt. Wird „Hunde“ beim Indexieren zu „hund“, muss die Anfrage auch „hund“ ergeben.

Was ist der Unterschied zwischen text und keyword?

text wird analysiert und dient der Volltextsuche. keyword bleibt ein ganzer Wert und dient Filtern, Sortieren und Aggregationen.

Warum findet eine term-Query „Hund“ nichts?

term analysiert die Anfrage nicht. Im text-Feld steht aber „hund“ in Kleinbuchstaben. Lösung: match oder ein keyword-Feld.

Wie funktioniert BM25 grob?

Score = Summe über die Query-Terms aus idf mal normierter tf. Seltene Terms zählen mehr, häufige Treffer sättigen, kurze Felder zählen mehr.

Was bedeuten k1 und b?

k1 (1.2) steuert die Sättigung der Termhäufigkeit. b (0.75) steuert die Längen-Normalisierung, b = 0 schaltet sie aus.

Warum ist BM25 besser als reines TF-IDF?

tf sättigt: Ein Wort 50-mal macht ein Dokument nicht 50-mal relevanter. Und die Feldlänge ist sauber eingerechnet.

Was ist der Unterschied zwischen Query- und Filter-Kontext?

Query-Kontext berechnet einen Score. Filter-Kontext entscheidet nur ja oder nein, ist schneller und wird gecacht.

Was ist ein Segment?

Ein kleiner, unveränderlicher Lucene-Index. Neue Dokumente kommen in neue Segmente. Lucene mergt sie im Hintergrund.

Wie funktionieren Update und Delete, wenn Segmente unveränderlich sind?

Delete markiert das Dokument als gelöscht. Update ist Delete plus Neu-Indexieren. Ein Merge entfernt die alten Daten.

Was heisst Near Real-Time?

Neue Dokumente sind erst nach einem Refresh suchbar. Standard: jede Sekunde, bei inaktiven Shards erst bei der nächsten Suche.

Wozu dient das Translog?

Es macht Schreibvorgänge dauerhaft, bevor ein Lucene-Commit passiert. Nach einem Absturz spielt Elasticsearch es erneut ab.

Was ist query then fetch?

Phase 1: Jeder Shard liefert IDs und Scores seiner besten Treffer. Phase 2: Der Koordinator holt nur für die Gewinner die Dokumente.

Warum sind Scores bei kleinen Indizes manchmal seltsam?

Jeder Shard rechnet idf lokal. Bei wenigen Dokumenten pro Shard weichen die Werte ab. Lösung: dfs_query_then_fetch oder ein Shard.

Was sind Doc Values?

Spaltenweise Speicherung pro Feld, von Doc zu Wert. Elasticsearch braucht sie zum Sortieren und Aggregieren.

Wie blättert man tief in Suchergebnissen?

Nicht mit from und size über 10 000. Mit search_after und einem Point in Time.

Wie macht man Volltextsuche nur mit PostgreSQL?

tsvector-Spalte mit to_tsvector, GIN-Index darauf, Abfrage mit @@ und websearch_to_tsquery, Sortierung mit ts_rank.

Warum ist LIKE '%hund%' langsam?

Ein B-Tree hilft nur bei festem Anfang. Mit führendem % liest die DB die ganze Tabelle. pg_trgm mit GIN hilft.

Wann reicht PostgreSQL, wann braucht man Elasticsearch?

PostgreSQL reicht für einfache Suche und moderate Datenmengen. Elasticsearch lohnt sich für BM25-Relevanz, Facetten, Tippfehler, grosse Mengen und viele Suchanfragen.

Wie prüfen Sie, warum ein Dokument nicht gefunden wird?

_analyze auf Text und Anfrage, _mapping prüfen, _explain für das Dokument, prüfen ob refresht und ob ein Filter es ausschliesst.

Szenario: Erklären Sie die Suche für einen Bild-Upload mit Bilderkennung.

Datei in S3, Metadaten und Labels in PostgreSQL, Sync per Outbox oder CDC nach Elasticsearch. Index mit caption als text, labels und owner_id als keyword, plus Embedding. Query: bool mit match auf caption, filter auf owner_id, optional kNN. Ergebnis: IDs, dann Vorschau-URLs.

Szenario: Nutzer suchen „Hunde“ und finden Bilder mit „Hund“ nicht. Was tun Sie?

Mit _analyze prüfen: Wahrscheinlich kein Stemming. Lösung: german-Analyzer auf dem Feld, neuer Index, Reindex, Alias umschalten.

Szenario: Die Suche wird langsam, Seite 500 dauert Sekunden. Was ist los?

Tiefe Paginierung: Jeder Shard sortiert from + size Treffer. Lösung: search_after mit PIT und eine Grenze in der UI. Mit Profile API und Slow Log bestätigen.
