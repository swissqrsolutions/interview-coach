DNS: Auflösung, Records, TTL

Kern: DNS (Domain Name System) ist eine verteilte Datenbank, die Namen in Daten übersetzt, meist in IP-Adressen. Es löst das Problem, dass Clients feste IPs kennen müssten. Jede Antwort hat eine TTL (Time to Live), also wie lange man sie cachen darf.

1. Wo sitzt DNS? (Pod in AKS mit Private Endpoint)

  1. Stub Resolver: Die Bibliothek im Pod (getaddrinfo) fragt den Server aus /etc/resolv.conf. Sie fragt nur, sie löst nicht selbst auf.
  2. CoreDNS: Der DNS-Server im Cluster beantwortet Namen unter cluster.local selbst. Alles andere leitet er weiter (forward).
  3. Rekursiver Resolver: In Azure ist das Azure DNS unter der festen IP 168.63.129.16. Er löst Namen komplett auf und cacht die Antworten.
  4. Private DNS Zone: Eine Zone, die nur in verlinkten VNets sichtbar ist. Hier steht die private IP des Private Endpoints.
  5. Öffentliches DNS: Die Hierarchie aus Root, TLD und autoritativen Servern. Für Azure-Dienste liefert sie einen CNAME auf den privatelink-Namen.

2. Die Reise einer DNS-Anfrage (die Geschichte zum Merken)

  1. Die App fragt: curl https://example.com ruft getaddrinfo("example.com"). Der Stub prüft zuerst die hosts-Datei und den OS-Cache.
  2. Frage an den Resolver ①: Der Stub schickt eine Anfrage über UDP Port 53 mit dem Flag RD (Recursion Desired). Er will eine fertige Antwort.
  3. Cache-Treffer? Hat der Resolver die Antwort im Cache und ist die TTL nicht abgelaufen, antwortet er sofort. Die TTL zählt dabei herunter.
  4. Root ②: Bei einem Miss fragt der Resolver einen Root-Server. Der antwortet mit einem Referral: „Frag die .com-Server.“
  5. TLD ③: Der .com-Server verweist auf die NS-Records von example.com. Er liefert oft gleich deren IPs mit (Glue Records).
  6. Autoritativ ④: Der zuständige Server antwortet mit dem A-Record. Das Flag AA (Authoritative Answer) ist gesetzt. Die TTL ist die volle Zonen-TTL, z. B. 300.
  7. Zurück zum Client ⑤: Der Resolver cacht die Antwort und gibt sie weiter. Ab jetzt baut der Client die TCP-Verbindung zur IP.

Der Resolver arbeitet iterativ: Er fragt selbst nacheinander. Für den Client ist es rekursiv: Er stellt eine Frage und bekommt das Endergebnis.

3. Beispiel: DNS mit nslookup abfragen

$ nslookup example.com 1.1.1.1
Non-authoritative answer:
Name:    example.com
Addresses:  2606:4700:10::ac42:93f3
	  2606:4700:10::6814:179a
	  172.66.147.243
	  104.20.23.154

$ nslookup -debug -type=a example.com 1.1.1.1          # rekursiver Resolver, Cache
	header flags:  response, want recursion, recursion avail.
    ->  example.com
	internet address = 172.66.147.243
	ttl = 55 (55 secs)

$ nslookup -debug -type=a example.com hera.ns.cloudflare.com   # autoritativer Server
	header flags:  response, auth. answer, want recursion
	internet address = 172.66.147.243
	ttl = 300 (5 mins)

$ nslookup -type=mx example.com 1.1.1.1
example.com	MX preference = 0, mail exchanger = (root)

$ nslookup -type=txt example.com 1.1.1.1
example.com	text =
	"v=spf1 -all"

$ nslookup -type=ns example.com 1.1.1.1
example.com	nameserver = hera.ns.cloudflare.com
example.com	nameserver = elliott.ns.cloudflare.com

$ nslookup gibtsnicht.invalid 1.1.1.1
*** one.one.one.one can't find gibtsnicht.invalid: Non-existent domain

Echte Ausgabe, curl/OpenSSL/Python unter Windows (nslookup, Resolver 1.1.1.1). Gekürzt: Kopfzeilen „Server/Address“ und Teile der Debug-Ausgabe.

  1. A und AAAA: example.com hat zwei IPv4- und zwei IPv6-Adressen. Der Client wählt eine davon.
  2. Non-authoritative: Die Antwort kommt aus dem Cache des Resolvers 1.1.1.1, nicht vom zuständigen Server.
  3. TTL im Cache: Der Resolver zeigt ttl = 55. Die volle TTL ist 300. Die Antwort liegt also seit 245 Sekunden im Cache.
  4. Autoritativ: Direkt beim Nameserver von example.com ist auth. answer gesetzt, und die TTL ist voll: 300.
  5. Null MX: MX preference = 0, mail exchanger = (root) heisst: Diese Domain nimmt keine Mails an (RFC 7505).
  6. TXT: v=spf1 -all ist ein SPF-Record. Er sagt: Kein Server darf Mails für diese Domain senden.
  7. NXDOMAIN: Für einen nicht existierenden Namen kommt „Non-existent domain“. Auch diese negative Antwort wird gecacht.

4. Details, die Interviewer fragen

  1. A / AAAA: Name → IPv4-Adresse / IPv6-Adresse. Mehrere Records für einen Namen sind normal.
  2. CNAME: Ein Alias: Name → anderer Name. Der Resolver folgt der Kette. Ein CNAME darf keine anderen Records neben sich haben. Darum geht er nicht am Zonen-Apex (example.com selbst).
  3. MX: Mail-Server einer Domain mit Priorität. Kleinere Zahl = bevorzugt.
  4. TXT: Freier Text. Genutzt für SPF, DKIM, DMARC und Domain-Verifikation (z. B. für Zertifikate oder Entra ID).
  5. SRV: Dienst-Ort mit Port: _dienst._proto.name → Priorität, Gewicht, Port, Ziel (RFC 2782). Kubernetes nutzt SRV für benannte Ports.
  6. NS und SOA: NS nennt die autoritativen Server einer Zone. SOA (Start of Authority) enthält Verwaltungsdaten der Zone, auch die TTL für negative Antworten.
  7. PTR: Rückwärtsauflösung: IP → Name, unter in-addr.arpa.
  8. TTL und Caching: Es gibt viele Caches: Browser, Anwendung (z. B. JVM), OS, CoreDNS, Resolver. Eine Änderung wirkt erst, wenn alle Caches abgelaufen sind.
  9. JVM-Cache: Java cacht erfolgreiche Lookups standardmässig 30 Sekunden (networkaddress.cache.ttl), ohne Security Manager. Mit Security Manager früher für immer.
  10. Negative Caching: Auch „gibt es nicht“ wird gecacht (RFC 2308). Die Dauer kommt aus dem SOA-Record der Zone.
  11. UDP und TCP: Normal ist UDP 53. Ist die Antwort zu gross, setzt der Server das TC-Bit (truncated). Der Client wiederholt über TCP 53.
  12. Private Endpoint DNS: Der öffentliche Name konto.blob.core.windows.net hat einen CNAME auf konto.privatelink.blob.core.windows.net. In der VNet beantwortet die Private DNS Zone privatelink.blob.core.windows.net diesen Namen mit der privaten IP. Die App behält ihre URL.
  13. Zone mit VNet verlinken: Eine Private DNS Zone wirkt nur in VNets mit Virtual Network Link. Ohne Link löst die VNet öffentlich auf.
  14. On-Premises: Lokale DNS-Server brauchen einen Conditional Forwarder zum Azure DNS Private Resolver (Inbound Endpoint). Microsoft empfiehlt, die öffentliche Zone weiterzuleiten, z. B. blob.core.windows.net, nicht privatelink….
  15. Kubernetes-Namen: Ein Service hat den A-Record svc.namespace.svc.cluster.local → ClusterIP. Ein Headless Service (clusterIP: None) liefert direkt die Pod-IPs.
  16. ndots:5: Pods haben options ndots:5 und mehrere Search Domains. Ein Name mit weniger als 5 Punkten wird zuerst mit jeder Search Domain probiert. Ein externer Name erzeugt so mehrere unnötige Anfragen.

5. Vergleich

  • Stub Resolver: im Client, fragt nur, cacht wenig.
  • Rekursiver Resolver: löst komplett auf, cacht viel (z. B. Azure DNS, 1.1.1.1, ISP).
  • Autoritativer Server: besitzt die Zone und gibt die Wahrheit mit AA-Flag aus (z. B. Azure DNS Zones, Cloudflare).
  • Forwarder: gibt Anfragen an einen anderen Resolver weiter (z. B. CoreDNS forward, Conditional Forwarder).
  • Öffentliche Zone vs Private Zone: Die öffentliche ist im Internet sichtbar. Die private nur in verlinkten VNets.
  • CNAME vs Alias-Record: CNAME zeigt auf einen Namen, nicht am Apex. Azure-Alias-Records und ALIAS bei anderen Anbietern zeigen auf eine Ressource und gehen auch am Apex.
  • ClusterIP-Service vs Headless: ClusterIP liefert eine virtuelle IP. Headless liefert alle Pod-IPs, gut für StatefulSets.

6. In der Produktion

  1. Private Endpoint löst öffentlich auf: Die Private DNS Zone fehlt oder ist nicht mit der VNet verlinkt. Die App geht über das Internet und bekommt 403 von der Firewall des Dienstes. Lösung: Zone anlegen, mit VNet verlinken, A-Record per DNS Zone Group automatisch pflegen.
  2. Eigener DNS-Server ignoriert die Private Zone: Die VNet nutzt einen eigenen DNS (z. B. Domain Controller). Lösung: Forwarder zu 168.63.129.16 oder zum DNS Private Resolver.
  3. NXDOMAIN für fremde Ressourcen: Mit einer Private Zone privatelink.blob… findet die VNet keine Konten, die woanders einen Private Endpoint haben. Lösung: Fallback to Internet am VNet-Link.
  4. Alte IP nach Umzug: Die TTL war hoch, Caches halten die alte IP. Lösung: TTL Tage vorher senken (z. B. auf 60 s), dann umziehen, dann wieder erhöhen.
  5. DNS-Last in Kubernetes: ndots:5 vervielfacht Anfragen für externe Namen. Lösung: vollqualifizierte Namen mit Punkt am Ende (api.example.com.), dnsConfig.options ndots senken, NodeLocal DNSCache.
  6. 5 Sekunden Verzögerung: Parallele A- und AAAA-Anfragen über UDP kollidieren in conntrack auf Linux. Eine Antwort geht verloren, der Client wartet 5 s Timeout. Lösung: NodeLocal DNSCache oder single-request-reopen.
  7. DNS-Policy blockt TCP: Network Policy erlaubt nur UDP 53. Grosse Antworten scheitern. Lösung: UDP und TCP 53 erlauben.

7. Diagnose: Werkzeuge und Befehle

  • nslookup name / nslookup -debug -type=a name server: Antwort, Flags und TTL (Windows und Linux).
  • dig name +noall +answer: kurze Antwort mit TTL. dig +trace name: ganze Kette Root → TLD → autoritativ.
  • dig @168.63.129.16 konto.blob.core.windows.net: Was sagt Azure DNS in dieser VNet? Erwartet: CNAME auf privatelink und eine 10.x-IP.
  • kubectl exec -it pod -- cat /etc/resolv.conf: Nameserver, Search Domains, ndots.
  • kubectl run -it --rm dnstest --image=busybox:1.36 -- nslookup kubernetes.default: DNS aus Sicht eines Pods testen.
  • kubectl -n kube-system logs -l k8s-app=kube-dns: CoreDNS-Fehler, mit Plugin log auch einzelne Anfragen.
  • curl -w "%{time_namelookup}": Wie lange dauert die Auflösung im echten Client?
  • tcpdump -i any port 53 / Wireshark Filter dns: Anfragen, Search-Domain-Versuche, fehlende Antworten.
  • ipconfig /displaydns und ipconfig /flushdns (Windows): lokalen Cache sehen und leeren.

8. Senior-Punkte

  1. „It’s always DNS.“ Bei Fehlern nach Netzwerk-Änderungen zuerst prüfen: Welche IP sieht der Client wirklich, von wo aus?
  2. DNS-Architektur ist Teil der Landing Zone. Private DNS Zones zentral im Hub, mit allen Spokes verlinkt, per Azure Policy automatisch befüllt.
  3. TTL ist ein Werkzeug für Migrationen. Kurz vor Änderungen senken, danach erhöhen. Hohe TTL spart Last, niedrige gibt Flexibilität.
  4. Viele Caches, eine Wahrheit: Browser, JVM, OS, CoreDNS und Resolver cachen getrennt. Debuggen heisst: jede Schicht einzeln prüfen.
  5. DNS-basiertes Load Balancing ist grob. Clients cachen und halten IPs fest. Für schnelles Failover braucht es einen echten Load Balancer.
  6. DNS-Erfolg heisst nicht Zugriff. Die privatelink-CNAMEs sind öffentlich auflösbar. Zugriff steuern Netzwerk-Regeln und RBAC.

10. Fallen

  • „Eine DNS-Änderung wirkt sofort.“ → Falsch. Erst wenn alle Caches ihre TTL abgelaufen haben.
  • „Für Private Endpoints ändere ich die Connection-URL auf privatelink.“ → Falsch. Die App behält den öffentlichen Namen. Der CNAME führt zur privaten Zone.
  • „DNS läuft nur über UDP.“ → Falsch. Grosse Antworten und Zonentransfers laufen über TCP.
  • „CNAME geht auch am Apex.“ → Falsch. Am Apex stehen SOA und NS. Ein CNAME darf nichts neben sich haben. Dafür gibt es Alias-Records.
  • „Conditional Forwarder auf privatelink.blob.core.windows.net.“ → Falsch laut Microsoft. Die öffentliche Zone blob.core.windows.net weiterleiten.
  • „NXDOMAIN wird nicht gecacht.“ → Falsch. Negative Antworten werden gecacht, gesteuert über den SOA-Record.

11. Fragen

Was ist DNS?

Eine verteilte, hierarchische Datenbank. Sie übersetzt Namen in Daten, meist IP-Adressen. Antworten werden für die TTL gecacht.

Was passiert, wenn ich example.com im Browser eingebe?

Browser- und OS-Cache prüfen, dann den rekursiven Resolver fragen. Bei Cache-Miss fragt er Root, dann .com, dann den autoritativen Server. Antwort mit TTL, cachen, dann TCP und TLS zur IP.

Rekursiv vs iterativ?

Rekursiv: Der Client bekommt das fertige Ergebnis vom Resolver. Iterativ: Der Resolver fragt selbst Server für Server und folgt Referrals.

Was ist ein autoritativer Server?

Der Server, der die Zone besitzt. Seine Antworten haben das AA-Flag und die volle TTL.

Was ist die TTL?

Die Zeit in Sekunden, die ein Record gecacht werden darf. Im Cache zählt sie herunter.

A vs AAAA vs CNAME?

A: IPv4-Adresse. AAAA: IPv6-Adresse. CNAME: Alias auf einen anderen Namen.

Warum geht CNAME nicht am Zonen-Apex?

Am Apex müssen SOA und NS stehen. Ein CNAME darf keine anderen Records neben sich haben. Lösung: Alias-Record.

Wofür sind MX und TXT?

MX nennt die Mail-Server mit Priorität. TXT trägt Text, z. B. SPF, DKIM, DMARC oder Domain-Verifikation.

Was ist ein SRV-Record?

Er nennt für einen Dienst Ziel-Host, Port, Priorität und Gewicht. Format: _dienst._proto.name.

Läuft DNS über UDP oder TCP?

Normal UDP 53. Bei zu grossen Antworten (TC-Bit) und Zonentransfers TCP 53.

Was ist Negative Caching?

Auch NXDOMAIN wird gecacht. Die Dauer kommt aus dem SOA-Record der Zone.

Wie funktioniert DNS für Azure Private Endpoints?

Der öffentliche Name hat einen CNAME auf den privatelink-Namen. Eine mit der VNet verlinkte Private DNS Zone beantwortet ihn mit der privaten IP. Die App-URL bleibt gleich.

Was ist 168.63.129.16?

Die feste virtuelle IP von Azure DNS in jeder VNet. Sie kennt die verlinkten Private DNS Zones.

Wie lösen On-Premises-Clients Private Endpoints auf?

Ein Conditional Forwarder für die öffentliche Zone (z. B. blob.core.windows.net) zeigt auf den Inbound Endpoint des Azure DNS Private Resolver.

Wie heisst ein Kubernetes-Service im DNS?

svc.namespace.svc.cluster.local, A-Record auf die ClusterIP. Ein Headless Service liefert die Pod-IPs.

Was macht ndots:5 in Pods?

Namen mit weniger als 5 Punkten werden zuerst mit allen Search Domains probiert. Externe Namen erzeugen so mehrere unnötige Anfragen. Lösung: Punkt am Ende oder ndots senken.

Was macht CoreDNS?

Es beantwortet cluster.local aus der Kubernetes-API und leitet alles andere an den Upstream-Resolver weiter. Es cacht Antworten.

Wie lange cacht Java DNS-Antworten?

Standard 30 Sekunden ohne Security Manager, steuerbar mit networkaddress.cache.ttl. Wichtig bei Failover über DNS.

Warum zeigt mein Resolver eine kleinere TTL als der autoritative Server?

Die Antwort liegt schon im Cache. Der Resolver zeigt die Rest-TTL.

Wie bereiten Sie eine DNS-Migration vor?

TTL Tage vorher senken, Änderung machen, prüfen, TTL wieder erhöhen.

Szenario: Eine App in AKS erreicht den Storage Account nicht, Fehler 403 „not authorized“. Public Access ist aus. Was prüfen Sie?

DNS aus dem Pod: Löst der Name auf eine 10.x-IP auf? Wenn nicht, fehlt die Private DNS Zone oder der VNet-Link, oder der eigene DNS leitet nicht an 168.63.129.16 weiter. Die App geht dann öffentlich raus und wird blockiert.

Szenario: Nach einem Failover auf eine neue IP gehen manche Clients noch eine Stunde zum alten Server. Warum?

Die TTL war hoch, Resolver und Anwendungen (z. B. JVM, Connection Pools) halten die alte IP. Lösung: niedrige TTL vor geplanten Wechseln, Clients mit begrenztem DNS-Cache, Pools erneuern.

Szenario: Pods haben sporadisch genau 5 Sekunden Verzögerung bei externen Calls. Woran denken Sie?

An DNS: verlorene UDP-Antworten durch conntrack-Race bei parallelen A/AAAA-Anfragen, dazu ndots:5. Prüfen mit tcpdump auf Port 53. Lösung: NodeLocal DNSCache, ndots senken, FQDN mit Punkt.
