Layer-4 vs Layer-7 Load Balancer und Proxies

Networking · Tier 1 · Quellen: Microsoft Learn (Azure Load Balancer Overview, Application Gateway Overview und FAQ, Front Door Overview, Load-Balancing-Optionen), kubernetes.io (Service, Ingress, Gateway API), kubernetes.io Blog „Ingress NGINX Retirement“ (Nov. 2025), RFC 9110 (Forwarded/Via), RFC 7239 (Forwarded)

Kern: Ein Load Balancer verteilt Verbindungen oder Requests auf mehrere Backends. Ein Layer-4-Balancer sieht nur IP, Port und Protokoll und verteilt ganze TCP/UDP-Verbindungen. Ein Layer-7-Balancer ist ein Reverse Proxy: Er versteht HTTP und entscheidet pro Request nach Host, Pfad oder Header.

1. Wo sitzen L4 und L7?

  1. Das OSI-Modell teilt Netzwerk in 7 Schichten. In der Praxis zählen vor allem L3 (IP), L4 (TCP/UDP) und L7 (HTTP).
  2. Ein L4-Balancer arbeitet auf TCP/UDP. Er sieht das 5-Tupel, aber nicht den Inhalt. Er leitet Pakete einer Verbindung immer an dasselbe Backend.
  3. Ein L7-Proxy beendet die Client-Verbindung, liest den HTTP-Request und baut eine eigene Verbindung zum Backend. Er sieht Pfad, Host, Header und Cookies.
  4. TLS liegt dazwischen. Ein L7-Proxy muss TLS entschlüsseln, um HTTP zu sehen. Ein L4-Balancer sieht nur verschlüsselte Bytes.

2. Die Reise eines Requests durch Azure und AKS (die Geschichte zum Merken)

  1. DNS: shop.example.com zeigt per CNAME auf Azure Front Door. Der Browser landet am nächsten Edge-Standort (Anycast).
  2. Front Door (global L7): Hier endet die TLS-Verbindung des Browsers. Front Door prüft die WAF-Regeln, liefert gecachte Inhalte und wählt die gesunde Region.
  3. Application Gateway (regional L7): Front Door baut eine neue HTTPS-Verbindung zum Gateway. Das Gateway routet nach Pfad, z. B. /api zu AKS.
  4. Azure Load Balancer (L4): Ein interner Load Balancer, den AKS für einen type: LoadBalancer-Service anlegt. Er verteilt TCP-Verbindungen auf die Knoten, ohne HTTP zu lesen.
  5. Ingress oder Gateway (L7 im Cluster): Ein Controller (z. B. NGINX, Envoy) liest Host und Pfad und wählt einen Service.
  6. Service (L4 im Cluster): Eine virtuelle ClusterIP. kube-proxy (iptables/IPVS) oder Cilium (eBPF) übersetzt sie per NAT in eine Pod-IP.
  7. Pod: Die App bekommt den Request. Die echte Client-IP steht im Header X-Forwarded-For, nicht im Socket.

3. Beispiel: Mini-L4-Proxy und Mini-L7-Proxy auf localhost

# l4_l7.py (Auszug): zwei Backends A (:9001) und B (:9002)
l4_proxy(8004, 9001)                           # leitet nur Bytes weiter, Ziel fest pro Verbindung
l7_proxy(8007, [("/api", 9002), ("/", 9001)])  # liest HTTP, routet pro Request, setzt X-Forwarded-For

for port in (8004, 8007):                      # je 2 Requests auf einer Keep-Alive-Verbindung
    c = http.client.HTTPConnection("127.0.0.1", port)
    for path in ("/shop", "/api/orders"):
        c.request("GET", path); print(c.getresponse().read())

$ curl -v --http1.1 https://example.com/ -o /dev/null
< HTTP/1.1 200 OK
< Server: cloudflare
< Age: 4552
< cf-cache-status: HIT
< CF-RAY: a5f8eb3b697733c3-ZRH
  1. L4 pro Verbindung: Der L4-Proxy sieht eine TCP-Verbindung und wählt einmal Backend A. Beide Requests landen dort, auch /api/orders. Er kann nicht nach Pfad routen.
  2. L7 pro Request: Der L7-Proxy liest jeden Request. /shop geht zu A, /api/orders zu B, obwohl der Client nur eine Verbindung hat.
  3. Quell-IP: In beiden Fällen sieht das Backend als peer den Proxy, nicht den Client. Nur der L7-Proxy reicht die Client-IP im Header X-Forwarded-For weiter.
  4. Neue Verbindungen: Der L7-Proxy baut eigene Verbindungen zum Backend (Ports 63706, 63707). Client- und Backend-Verbindung sind getrennt.
  5. Echter Edge-Proxy: example.com liegt hinter Cloudflare. Server: cloudflare, cf-cache-status: HIT und Age: 4552 zeigen: Ein L7-Proxy hat TLS beendet und die Antwort aus dem Cache geliefert. ZRH ist der Edge-Standort.

4. Details, die Interviewer fragen

  1. Reverse Proxy: Er steht vor Servern und nimmt Requests für sie an. Beispiele: NGINX, Envoy, Application Gateway. Ein Forward Proxy steht vor Clients und geht für sie ins Internet, z. B. ein Firmen-Proxy.
  2. TLS Termination: Der Proxy entschlüsselt TLS. Vorteile: Routing nach Pfad, WAF, Caching, zentrale Zertifikate. Zum Backend geht es dann im Klartext oder neu verschlüsselt.
  3. End-to-End TLS (Re-Encryption): Der Proxy entschlüsselt und verschlüsselt neu zum Backend. Der Proxy sieht den Inhalt, aber das Netz dahinter nicht.
  4. TLS Passthrough: Der Proxy entschlüsselt nicht. Er routet höchstens nach SNI im ClientHello. Das Backend hält das Zertifikat. Keine L7-Funktionen.
  5. Client-IP: L7-Proxies setzen X-Forwarded-For oder den Standard-Header Forwarded (RFC 7239). L4 kann die IP erhalten (Azure Load Balancer leitet Pakete ohne Proxy weiter) oder das PROXY-Protokoll nutzen.
  6. Health Probes: L4 prüft, ob ein Port offen ist. L7 prüft einen Pfad wie /healthz und den Status-Code. L7 erkennt also auch eine kaputte App mit offenem Port.
  7. Session Affinity: L4 hält eine Verbindung per Hash auf das 5-Tupel (Azure LB: Standard) oder auf die Client-IP. L7 nutzt ein Affinity-Cookie.
  8. Algorithmen: Round Robin, Least Connections, Hash (z. B. Client-IP), gewichtet. L4 kennt nur Verbindungen, L7 kann pro Request balancieren.
  9. Azure Load Balancer: L4, regional, TCP und UDP, öffentlich oder intern. Hohe Leistung, sehr geringe Latenz, keine TLS-Funktionen. Der Standard-SKU ist heute der normale.
  10. Azure Application Gateway: regionaler L7-Proxy für HTTP(S) und WebSocket. Pfad- und Host-Routing, TLS Termination, End-to-End TLS, WAF, Autoscaling (v2). Zum Backend spricht es immer HTTP/1.1.
  11. Azure Front Door: globaler L7-Proxy am Microsoft-Edge. Anycast, TLS am Edge, WAF, Caching (CDN), Failover zwischen Regionen. Premium erreicht Origins über Private Link.
  12. Traffic Manager: globale Verteilung per DNS. Kein Proxy, der Client verbindet direkt. Failover hängt an der DNS-TTL.
  13. Kubernetes Service: L4. ClusterIP (intern), NodePort (Port auf jedem Knoten), LoadBalancer (Cloud-L4-LB davor). Verteilt Verbindungen, nicht Requests.
  14. Kubernetes Ingress: L7-Regeln für HTTP: Host und Pfad → Service, TLS-Secret. Braucht einen Ingress Controller. Ingress selbst ist eingefroren, Neuerungen kommen in der Gateway API.
  15. Gateway API: Nachfolger von Ingress mit Rollen-Trennung (GatewayClass, Gateway, Routes). Kann HTTP, gRPC, TLS-Passthrough und TCP/UDP-Routing ausdrücken.

5. Vergleich

  • Sicht: L4 sieht IP, Port, Protokoll. L7 sieht den ganzen HTTP-Request.
  • Einheit: L4 verteilt Verbindungen. L7 verteilt Requests.
  • TLS: L4 leitet verschlüsselt weiter. L7 terminiert TLS (oder Passthrough ohne L7-Funktionen).
  • Protokolle: L4 jedes TCP/UDP-Protokoll (Datenbank, MQTT, DNS). L7 nur HTTP(S), WebSocket, gRPC.
  • Funktionen: L7 kann Routing nach Pfad, WAF, Caching, Header ändern, Retries, Rate Limits. L4 kann das nicht.
  • Leistung: L4 ist schneller und billiger pro Paket. L7 kostet mehr CPU und Latenz.
  • Azure: Load Balancer = L4 regional. Application Gateway = L7 regional. Front Door = L7 global. Traffic Manager = DNS global.
  • Kubernetes: Service = L4. Ingress und Gateway API = L7.

6. In der Produktion

  1. Backend sieht nur Proxy-IPs: Logs, Rate Limits und IP-Allowlists greifen ins Leere. Lösung: X-Forwarded-For auswerten, aber nur von vertrauten Proxies. Bei L4-Services in AKS: externalTrafficPolicy: Local erhält die Client-IP.
  2. Ungleiche Last bei langen Verbindungen: gRPC, HTTP/2 oder WebSockets halten eine Verbindung. Ein L4-Balancer verteilt sie nicht neu. Lösung: L7-Proxy oder Client-seitiges Balancing.
  3. 502/504 am Gateway: 502 heisst meist: Backend nicht gesund oder TLS zum Backend scheitert (falscher Hostname, unbekannte CA). 504: Backend antwortet zu langsam. Lösung: Health Probe, Backend-Zertifikat und Timeouts prüfen.
  4. Timeout-Kette falsch: Jeder Hop hat ein eigenes Timeout. Ist das innere länger als das äussere, bricht aussen ab, während innen noch gearbeitet wird. Lösung: Timeouts von aussen nach innen absteigend setzen.
  5. Backend ohne Front Door erreichbar: Angreifer umgehen die WAF. Lösung: Origin nur über Private Link oder Header X-Azure-FDID plus Service Tag AzureFrontDoor.Backend erlauben.
  6. Ingress-Controller veraltet: ingress-nginx bekommt seit März 2026 keine Updates und Security-Fixes mehr. Lösung: Migration auf eine Gateway-API-Implementierung oder einen gepflegten Controller.
  7. Sticky Sessions verdecken Probleme: Ein Pod hält viele Sessions, Skalierung hilft nicht. Lösung: zustandslose Apps, Session im Cache (Redis).

7. Diagnose: Werkzeuge und Befehle

  • curl -v https://host: Antwort-Header zeigen Proxies (Server, Via, X-Azure-Ref, Age).
  • curl -v --resolve host:443:IP https://host: direkt ein bestimmtes Backend oder Gateway testen, mit richtigem SNI und Host-Header.
  • openssl s_client -connect IP:443 -servername host: Welches Zertifikat liefert der Hop wirklich?
  • kubectl get svc,ingress,gateway,httproute -A: Welche Services und Routen gibt es?
  • kubectl get endpointslices -l kubernetes.io/service-name=svc: Hat der Service gesunde Pod-Endpunkte?
  • Application Gateway Backend Health im Portal oder az network application-gateway show-backend-health: Warum ist ein Backend „unhealthy“?
  • Access Logs von Front Door und Application Gateway: Status, Dauer pro Hop, Ziel-Backend.
  • Hubble (Cilium): hubble observe --to-pod ns/pod zeigt Flows und Policy-Verdicts bis zum Pod.

8. Senior-Punkte

  1. L4 oder L7 ist eine Frage der Anforderung: Braucht es Pfad-Routing, WAF, Request-Balancing? Dann L7. Nur Durchsatz für ein TCP-Protokoll? Dann L4.
  2. Jeder Hop ist ein Vertrag: Protokoll, TLS, Timeout, Health Probe, Header. Probleme entstehen an den Übergängen.
  3. Wo endet TLS? Das ist eine Sicherheitsentscheidung: Termination am Edge, Re-Encryption, oder mTLS bis zum Pod.
  4. Client-IP ist vertrauenswürdig nur vom ersten eigenen Proxy. X-Forwarded-For kann jeder Client fälschen.
  5. Weniger Stufen sind oft besser. Front Door + Application Gateway + Ingress sind drei L7-Proxies. Jede Stufe kostet Latenz und Fehlerquellen.
  6. Gateway API statt Ingress für Neues. Ingress ist eingefroren, ingress-nginx ist eingestellt.

10. Fallen

  • „Ein Kubernetes-Service balanciert Requests.“ → Falsch. Er balanciert Verbindungen (L4).
  • „Azure Load Balancer kann nach URL routen.“ → Falsch. Er ist L4. Dafür Application Gateway oder Front Door.
  • „Mit TLS Passthrough kann der Proxy trotzdem nach Pfad routen.“ → Falsch. Ohne Entschlüsseln sieht er nur SNI.
  • „Front Door und Traffic Manager machen dasselbe.“ → Falsch. Front Door ist ein Proxy. Traffic Manager antwortet nur per DNS.
  • „Ingress ist ein Load Balancer.“ → Falsch. Ingress ist eine Regel-Ressource. Den Verkehr macht der Ingress Controller.
  • „X-Forwarded-For ist sicher.“ → Falsch. Der Client kann ihn setzen. Nur Einträge vertrauter Proxies zählen.

11. Fragen

Was ist der Unterschied zwischen einem L4- und einem L7-Load-Balancer?

L4 sieht IP, Port, Protokoll und verteilt Verbindungen. L7 versteht HTTP und verteilt Requests nach Host, Pfad oder Header.

Was ist ein Reverse Proxy?

Ein Server vor den Backends, der Requests für sie annimmt und weiterleitet. Beispiele: NGINX, Envoy, Application Gateway.

Reverse Proxy vs Forward Proxy?

Ein Reverse Proxy schützt und verteilt für Server. Ein Forward Proxy geht für Clients ins Internet, z. B. ein Firmen-Proxy.

Was ist TLS Termination?

Der Proxy entschlüsselt TLS und sieht den HTTP-Inhalt. Dann kann er routen, cachen und filtern.

TLS Termination vs Passthrough?

Termination: Proxy entschlüsselt, L7-Funktionen möglich. Passthrough: Proxy leitet verschlüsselt weiter, routet höchstens nach SNI.

Was ist End-to-End TLS?

Der Proxy terminiert TLS und baut eine neue TLS-Verbindung zum Backend. So ist auch der Weg dahinter verschlüsselt.

Wie erfährt das Backend die Client-IP?

Über X-Forwarded-For oder Forwarded bei L7. Bei L4 über erhaltene Quell-IP oder das PROXY-Protokoll.

Was kann Azure Load Balancer?

L4-Verteilung von TCP und UDP, regional, öffentlich oder intern, mit Health Probes und Outbound-Regeln. Kein HTTP, kein TLS.

Was kann Azure Application Gateway?

Regionaler L7-Proxy: Pfad- und Host-Routing, TLS Termination, End-to-End TLS, WAF, Cookie-Affinity, Autoscaling.

Was kann Azure Front Door?

Globaler L7-Proxy am Edge: Anycast, TLS, WAF, Caching und Failover zwischen Regionen. Premium mit Private Link zu Origins.

Front Door vs Application Gateway?

Front Door ist global am Edge, für mehrere Regionen und Caching. Application Gateway ist regional in der VNet. Oft kombiniert.

Front Door vs Traffic Manager?

Front Door ist ein Proxy und sieht HTTP. Traffic Manager verteilt nur per DNS, der Client verbindet direkt.

Was ist ein Kubernetes-Service?

Eine stabile virtuelle IP und ein DNS-Name für eine Gruppe Pods. L4, umgesetzt von kube-proxy oder Cilium.

ClusterIP vs NodePort vs LoadBalancer?

ClusterIP nur intern. NodePort öffnet einen Port auf jedem Knoten. LoadBalancer stellt einen Cloud-L4-LB davor.

Was ist ein Ingress?

Eine Ressource mit L7-Regeln (Host, Pfad, TLS). Ein Ingress Controller setzt sie um.

Ingress vs Gateway API?

Gateway API ist der Nachfolger: Rollen-Trennung, mehr Protokolle (gRPC, TLS, TCP), weniger Annotationen. Ingress ist eingefroren.

Warum haben L7-Health-Probes einen Vorteil?

Sie prüfen eine echte HTTP-Antwort. Ein offener Port mit kaputter App fällt so auf.

Wie funktioniert Session Affinity bei L4 und L7?

L4 hasht das 5-Tupel oder die Client-IP. L7 setzt ein Affinity-Cookie.

Was ist das OSI-Modell in einem Satz pro Schicht, die zählt?

L3: IP-Adressen und Routing. L4: TCP/UDP mit Ports. L7: Anwendungsprotokolle wie HTTP.

Was bedeuten 502 und 504 an einem Gateway?

502: Antwort vom Backend fehlt oder ist ungültig, oft Health oder TLS zum Backend. 504: Backend antwortet nicht im Timeout.

Szenario: Application Gateway zeigt alle Backends als unhealthy, die Pods laufen aber. Was prüfen Sie?

Probe-Pfad und Port, Host-Header der Probe, TLS zum Backend (Zertifikat, Hostname, CA), NSG und Network Policies auf dem Weg. Backend Health im Portal zeigt den Grund.

Szenario: Rate Limiting in der App sperrt alle Nutzer gleichzeitig. Warum?

Die App sieht nur die IP des Proxys. Alle Nutzer teilen sich dieselbe IP. Lösung: X-Forwarded-For vom vertrauten Proxy auswerten oder Rate Limit am Proxy machen.

Szenario: Ein neuer gRPC-Service hinter einem L4-Service skaliert auf 5 Pods, aber nur einer arbeitet. Was tun Sie?

gRPC hält eine HTTP/2-Verbindung, L4 verteilt nur Verbindungen. Lösung: L7-Proxy (Gateway API mit GRPCRoute, Mesh) oder Headless Service mit Client-Balancing.
