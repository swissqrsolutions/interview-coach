TCP vs UDP

Networking · Tier 1 · Quellen: RFC 9293 (TCP), RFC 768 (UDP), RFC 5681 (TCP Congestion Control), RFC 7323 (Window Scaling), RFC 9000 (QUIC), Microsoft Learn (Azure Load Balancer, SNAT)

Kern: TCP und UDP sind die zwei Transportprotokolle über IP. Sie bringen Daten von einem Port auf Host A zu einem Port auf Host B. TCP ist verbindungsorientiert und liefert einen zuverlässigen, geordneten Byte-Strom. UDP schickt einzelne Datagramme ohne Verbindung, ohne Garantie und ohne Wartezeit.

1. Wo sitzen TCP und UDP?

  1. IP bringt Pakete von Host zu Host. IP garantiert nichts: Pakete können fehlen, doppelt oder vertauscht ankommen.
  2. TCP und UDP sitzen darüber auf Layer 4. Beide adressieren mit Ports eine Anwendung auf dem Host.
  3. TCP baut auf dem unzuverlässigen IP eine zuverlässige Verbindung. Es nummeriert, bestätigt und wiederholt Daten.
  4. UDP gibt IP fast unverändert an die Anwendung weiter. Zuverlässigkeit muss die Anwendung selbst bauen, wenn sie sie braucht.
  5. Eine Verbindung ist eindeutig durch das 5-Tupel: Protokoll, Quell-IP, Quell-Port, Ziel-IP, Ziel-Port.

2. Die Reise einer TCP-Verbindung (die Geschichte zum Merken)

  1. SYN: Der Client schickt ein Segment mit SYN-Flag und einer zufälligen Initial Sequence Number (ISN), also der Startnummer seiner Bytes. Er ist jetzt in SYN_SENT.
  2. SYN-ACK: Der Server antwortet mit seiner eigenen ISN. Er bestätigt die ISN des Clients mit ack=x+1.
  3. ACK: Der Client bestätigt die ISN des Servers. Beide sind ESTABLISHED. Das ist der 3-Way Handshake. Er kostet 1 RTT (Round Trip Time, Hin- und Rückweg).
  4. Daten: Jedes Byte hat eine Nummer. Der Empfänger bestätigt mit ACK das nächste erwartete Byte. Fehlt ein ACK, sendet der Sender nach einem Retransmission Timeout (RTO) erneut.
  5. Fenster: Jedes ACK trägt das Receive Window, also den freien Puffer beim Empfänger. Mehr darf der Sender nicht unbestätigt schicken. Das ist Flow Control.
  6. FIN: Wer zuerst schliesst, schickt FIN. Die Gegenseite bestätigt und ist in CLOSE_WAIT, bis ihre Anwendung close() aufruft. Dann schickt sie ihr eigenes FIN.
  7. TIME_WAIT: Wer zuerst geschlossen hat, wartet 2 × MSL (Maximum Segment Lifetime). So kann er ein verlorenes letztes ACK wiederholen. Und alte Pakete stören keine neue Verbindung mit gleichem 5-Tupel.

UDP hat nichts davon. Kein Handshake, kein ACK, kein FIN. Das erste Paket trägt schon Nutzdaten.

3. Beispiel: TCP und UDP auf localhost

# TCP: Server liest einmal, Client schickt zweimal
c = socket.socket(AF_INET, SOCK_STREAM); c.connect(("127.0.0.1", 50007))
c.sendall(b"hallo "); c.sendall(b"welt")          # Server: data = conn.recv(1024)

# UDP: zwei Datagramme, kein connect
u = socket.socket(AF_INET, SOCK_DGRAM)
u.sendto(b"hallo ", ("127.0.0.1", 50008)); u.sendto(b"welt", ("127.0.0.1", 50008))

# Port 50009 ist zu: einmal TCP, einmal UDP
c.connect(("127.0.0.1", 50009))
u.sendto(b"ping", ("127.0.0.1", 50009)); u.recvfrom(1024)

# Danach: netstat -an -p TCP | Zeilen mit :50007

TCP client: connect() ok in 0.39 ms (3-way handshake)
TCP server: 1 recv() -> b'hallo welt'
TCP client: 2x send(), Antwort b'OK'

== 2) UDP: keine Verbindung, Nachrichten-Grenzen ==
UDP client: 2x sendto(), kein connect, kein Handshake
UDP server: recvfrom() -> b'hallo '
UDP server: recvfrom() -> b'welt'

== 3) Port ist zu ==
TCP connect() -> ConnectionRefusedError: [WinError 10061] No connection could be made because the target machine actively refused it
UDP sendto() -> 4 Bytes 'gesendet', kein Fehler
UDP recvfrom() -> ConnectionResetError: [WinError 10054] An existing connection was forcibly closed by the remote host

== 4) TIME_WAIT nach dem Schliessen ==
TCP    127.0.0.1:50007        127.0.0.1:51069        TIME_WAIT

Echte Ausgabe, curl/OpenSSL/Python unter Windows (Python 3.12, Skript gekürzt). Der Server hat in Teil 1 zuerst geschlossen.

  1. Byte-Strom: Zwei send() kommen bei TCP als ein recv() an: b'hallo welt'. TCP kennt keine Nachrichten-Grenzen. Die Anwendung braucht ein eigenes Framing, z. B. Länge vor jeder Nachricht.
  2. Datagramme: Bei UDP bleibt jedes sendto() ein eigenes Datagramm. Die Grenzen bleiben erhalten.
  3. Port zu bei TCP: Der Ziel-Host antwortet auf SYN mit RST (Reset). connect() scheitert sofort mit „refused“.
  4. Port zu bei UDP: sendto() meldet Erfolg. Der Fehler kommt nur indirekt als ICMP Port Unreachable. Windows meldet ihn beim nächsten recvfrom() als WinError 10054. Über das Internet geht dieses ICMP oft verloren.
  5. TIME_WAIT: Der Server hat zuerst geschlossen. Darum steht sein Port 50007 in TIME_WAIT, nicht der Client.

4. Details, die Interviewer fragen

  1. Warum 3 Schritte im Handshake: Beide Seiten müssen ihre ISN senden und bestätigt bekommen. Mit 2 Schritten wüsste der Server nicht, ob der Client seine ISN kennt. Die ISN ist zufällig, damit Angreifer keine Pakete einschleusen.
  2. Zuverlässigkeit: TCP nutzt Sequenznummern (Reihenfolge, Duplikate erkennen), ACKs (Bestätigung) und eine Checksumme. Verlust erkennt TCP per Timeout oder per Fast Retransmit: 3 doppelte ACKs lösen sofort eine Wiederholung aus.
  3. Flow Control: Flow Control schützt den Empfänger. Das Receive Window sagt, wie viele Bytes noch passen. Window Scaling (RFC 7323) erlaubt Fenster über 64 KB.
  4. Congestion Control: Congestion Control schützt das Netz. Der Sender hält ein Congestion Window (cwnd). Slow Start verdoppelt cwnd pro RTT. Bei Verlust halbiert TCP das Fenster grob. Linux nutzt standardmässig CUBIC, Google oft BBR.
  5. Gesendet wird höchstens: min(Receive Window, Congestion Window). Darum ist eine neue Verbindung am Anfang langsam.
  6. Bandwidth-Delay Product: Durchsatz ≈ Fenster / RTT. Bei 64 KB Fenster und 100 ms RTT sind das nur ca. 5 Mbit/s, egal wie dick die Leitung ist.
  7. TIME_WAIT: RFC 9293 setzt die MSL auf 2 Minuten. Linux wartet fest 60 Sekunden. TIME_WAIT trifft immer den, der zuerst schliesst.
  8. CLOSE_WAIT: Die Gegenseite hat geschlossen, aber die eigene Anwendung ruft close() nicht auf. Viele CLOSE_WAIT heissen fast immer: Bug in der Anwendung, Socket-Leck.
  9. Ports: Well-known Ports 0–1023 (z. B. 22, 53, 443). Ephemeral Ports sind kurzlebige Quell-Ports des Clients. Linux nutzt 32768–60999, Windows 49152–65535.
  10. RST: Ein Reset bricht eine Verbindung sofort ab. Ursachen: Port zu, Firewall, Proxy-Timeout, Anwendung stirbt.
  11. Nagle und Delayed ACK: Nagle sammelt kleine Writes zu einem Segment. Delayed ACK wartet kurz mit dem ACK. Zusammen erzeugen sie bis zu ca. 40–200 ms Wartezeit. Lösung bei Request/Response: TCP_NODELAY.
  12. MSS und MTU: Die MTU ist die maximale Paketgrösse auf dem Link (meist 1500 Bytes). Die MSS ist der Nutzdaten-Anteil pro TCP-Segment (1500 − 40 = 1460).
  13. Head-of-Line Blocking: Fehlt ein Segment, hält TCP alle folgenden Bytes zurück. Die Anwendung wartet, auch wenn spätere Daten schon da sind.
  14. UDP-Header: nur 8 Bytes: Quell-Port, Ziel-Port, Länge, Checksumme (RFC 768). Kein Zustand im Kernel, kein Handshake.
  15. Wann UDP: wenn späte Daten wertlos sind (VoIP, Video, Games), wenn eine Anfrage in ein Paket passt (DNS, DHCP, NTP) oder wenn die Anwendung ein eigenes Protokoll baut (QUIC für HTTP/3, WireGuard).

5. Vergleich

  • Verbindung: TCP braucht einen Handshake (1 RTT). UDP sendet sofort.
  • Zuverlässigkeit: TCP wiederholt verlorene Daten. UDP verliert sie still.
  • Reihenfolge: TCP liefert geordnet. UDP liefert in beliebiger Reihenfolge.
  • Daten-Einheit: TCP ist ein Byte-Strom ohne Grenzen. UDP behält Datagramm-Grenzen.
  • Tempo-Regelung: TCP hat Flow und Congestion Control. UDP hat keine, die Anwendung muss selbst bremsen.
  • Header: TCP mindestens 20 Bytes. UDP 8 Bytes.
  • Broadcast/Multicast: nur mit UDP möglich.
  • Typisch TCP: HTTP/1.1, HTTP/2, gRPC, Datenbanken, Kafka, SSH.
  • Typisch UDP: DNS, QUIC/HTTP/3, VoIP, Streaming, DHCP, syslog.

6. In der Produktion

  1. Ephemeral Ports aufgebraucht: Viele kurze Verbindungen lassen Tausende Sockets in TIME_WAIT. Neue connect() scheitern. Lösung: Connection Pooling und Keep-Alive statt eine Verbindung pro Request.
  2. SNAT-Port-Erschöpfung in Azure: Ausgehender Verkehr über Load Balancer oder Default Outbound teilt sich wenige SNAT-Ports. Symptom: sporadische Timeouts nach aussen. Lösung: NAT Gateway, Pooling, Private Endpoints.
  3. Idle Timeout schneidet Verbindungen: Azure Load Balancer und NAT Gateway trennen inaktive TCP-Verbindungen standardmässig nach 4 Minuten. Der Client merkt es erst beim nächsten Write (RST). Lösung: TCP Keepalive oder Pool-Idle-Zeit kleiner als das Timeout.
  4. CLOSE_WAIT staut sich: Die Anwendung schliesst Sockets nicht, z. B. vergessene Response-Bodies. Lösung: Ressourcen immer schliessen (try-with-resources, with).
  5. MTU-Problem: Kleine Requests gehen, grosse hängen. Ursache: Overlay oder VPN (VXLAN, IPsec) verkleinert die MTU, ICMP „Fragmentation Needed“ ist geblockt. Lösung: MTU passend setzen oder MSS Clamping.
  6. UDP-Verlust ohne Fehler: Ein voller Empfangspuffer verwirft Datagramme still. Lösung: Puffer vergrössern, Zähler beobachten (netstat -su: „receive buffer errors“).
  7. Latenz durch Nagle: Kleine Nachrichten warten auf ACKs. Lösung: TCP_NODELAY (viele Clients wie gRPC setzen es schon).

7. Diagnose: Werkzeuge und Befehle

  • ss -tan (Linux): alle TCP-Sockets mit Status. ss -s: Zusammenfassung, z. B. Anzahl TIME_WAIT.
  • ss -tanp state close-wait: welcher Prozess Sockets nicht schliesst.
  • ss -ti: pro Verbindung RTT, cwnd, Retransmits.
  • netstat -ano (Windows): Sockets mit Status und PID.
  • nc -vz host 443 oder Test-NetConnection host -Port 443 (PowerShell): Ist der TCP-Port erreichbar?
  • curl -w "%{time_connect}": Dauer des TCP-Handshakes, also etwa 1 RTT.
  • tcpdump -i any 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-rst) != 0)': nur SYN und RST sehen.
  • Wireshark: Filter tcp.analysis.retransmission, tcp.analysis.zero_window. Zeigt Verlust und vollen Empfänger.
  • Hubble (Cilium): hubble observe --verdict DROPPED zeigt, welche Policy ein Paket verwirft.

8. Senior-Punkte

  1. „Zuverlässig“ heisst nur Transport. TCP bestätigt den Empfang im Kernel, nicht die Verarbeitung in der Anwendung. Für Ende-zu-Ende braucht es Bestätigungen auf Anwendungsebene, z. B. Kafka-Acks.
  2. Verbindungen sind teuer. Handshake, TLS und Slow Start kosten mehrere RTT. Pooling und Keep-Alive sind die wichtigste Optimierung.
  3. Timeouts gehören in jede Schicht: Connect-Timeout, Read-Timeout, Idle-Timeout im Pool, Keepalive unter dem LB-Timeout.
  4. TIME_WAIT ist kein Fehler. Es ist ein Schutz. Das Problem ist das Muster „eine Verbindung pro Request“.
  5. UDP heisst nicht unzuverlässig per se. QUIC baut Zuverlässigkeit pro Stream über UDP und umgeht so TCP-Head-of-Line-Blocking.
  6. Durchsatz hängt an RTT. Über Regionen hinweg begrenzt das Fenster den Durchsatz. Lösung: grössere Puffer, parallele Streams, Daten näher bringen.

10. Fallen

  • „UDP ist immer schneller.“ → Falsch. Ohne Congestion Control verliert UDP bei Last viele Pakete. Schnell ist nur der Start ohne Handshake.
  • „TCP garantiert, dass der Server die Nachricht verarbeitet hat.“ → Falsch. Nur, dass der Kernel die Bytes empfangen hat.
  • „Ein send() ergibt ein recv().“ → Falsch. TCP ist ein Byte-Strom. Nachrichten können verschmelzen oder zerfallen.
  • „TIME_WAIT hat der Server.“ → Falsch. TIME_WAIT hat, wer zuerst schliesst.
  • „DNS ist nur UDP.“ → Falsch. Grosse Antworten und Zonentransfers laufen über TCP 53.
  • „tcp_tw_recycle löst TIME_WAIT.“ → Falsch. Die Option brach Clients hinter NAT und wurde in Linux 4.12 entfernt.

11. Fragen

Was ist der Unterschied zwischen TCP und UDP?

TCP ist verbindungsorientiert, zuverlässig, geordnet und regelt das Tempo. UDP sendet einzelne Datagramme ohne Verbindung, ohne Garantie und ohne Tempo-Regelung.

Wie läuft der 3-Way Handshake ab?

SYN mit ISN des Clients, SYN-ACK mit ISN des Servers und Bestätigung, ACK des Clients. Danach sind beide ESTABLISHED. Kosten: 1 RTT.

Warum braucht es 3 Schritte, nicht 2?

Beide Seiten müssen ihre Startnummer senden und bestätigt bekommen. Mit 2 Schritten bleibt die ISN des Servers unbestätigt.

Wie macht TCP die Übertragung zuverlässig?

Sequenznummern, ACKs, Checksumme und Wiederholung nach Timeout oder 3 doppelten ACKs (Fast Retransmit).

Was ist der Unterschied zwischen Flow Control und Congestion Control?

Flow Control schützt den Empfänger über das Receive Window. Congestion Control schützt das Netz über das Congestion Window.

Was ist Slow Start?

Eine neue Verbindung startet mit kleinem Congestion Window und verdoppelt es pro RTT. Bei Verlust bremst TCP ab.

Was ist TIME_WAIT und warum gibt es das?

Der Zustand nach dem Schliessen beim aktiven Schliesser. Er wartet 2 × MSL. So kann er ein verlorenes letztes ACK wiederholen, und alte Pakete stören keine neue Verbindung.

Was bedeuten viele CLOSE_WAIT?

Die Gegenseite hat geschlossen, die eigene Anwendung aber nicht. Meist ein Socket-Leck im Code.

Was ist ein Ephemeral Port?

Ein kurzlebiger Quell-Port, den das OS dem Client für eine Verbindung gibt. Linux: 32768–60999, Windows: 49152–65535.

Was identifiziert eine TCP-Verbindung eindeutig?

Das 5-Tupel: Protokoll, Quell-IP, Quell-Port, Ziel-IP, Ziel-Port.

Was passiert bei connect() auf einen geschlossenen Port?

Der Host antwortet mit RST, connect() scheitert sofort mit „connection refused“. Antwortet niemand (Firewall verwirft), gibt es einen Timeout.

Was ist Head-of-Line Blocking bei TCP?

Fehlt ein Segment, hält TCP alle folgenden Bytes zurück, bis es wiederholt ist. Das bremst alle Streams in einer Verbindung, z. B. bei HTTP/2.

Was ist Nagle und wann schaltet man es ab?

Nagle sammelt kleine Writes. Mit Delayed ACK entsteht Wartezeit. Bei Request/Response mit kleinen Nachrichten: TCP_NODELAY.

Was ist MSS und was MTU?

MTU ist die maximale Paketgrösse auf dem Link, meist 1500. MSS ist der Nutzdaten-Anteil eines TCP-Segments, meist 1460.

Wann wählen Sie UDP?

Wenn späte Daten wertlos sind (VoIP, Games), bei kleinen Anfragen in einem Paket (DNS, NTP) oder für eigene Protokolle wie QUIC.

Warum läuft HTTP/3 über UDP?

QUIC baut Zuverlässigkeit pro Stream selbst. So blockiert ein verlorenes Paket nur seinen Stream. Und QUIC lässt sich im User Space weiterentwickeln, ohne Kernel- und Middlebox-Änderungen.

Warum nutzt DNS auch TCP?

Ist eine Antwort zu gross für UDP, setzt der Server das TC-Bit. Der Client fragt dann über TCP 53. Zonentransfers laufen immer über TCP.

Wie gross ist der UDP-Header und was steht drin?

8 Bytes: Quell-Port, Ziel-Port, Länge, Checksumme.

Was ist ein Keepalive und warum braucht man ihn?

Ein leeres Prüfpaket auf einer inaktiven Verbindung. Es hält NAT- und LB-Einträge am Leben und erkennt tote Gegenstellen.

Warum ist eine neue TCP-Verbindung langsamer als eine wiederverwendete?

Handshake (1 RTT), dazu TLS, und Slow Start mit kleinem Fenster. Eine warme Verbindung hat das alles schon hinter sich.

Szenario: Ein Service macht viele ausgehende HTTP-Calls und bekommt sporadisch „Cannot assign requested address“. Was ist los?

Ephemeral Ports sind aufgebraucht, meist durch TIME_WAIT nach kurzen Verbindungen. Prüfen mit ss -s. Lösung: Connection Pooling und Keep-Alive. In Azure auch SNAT-Ports prüfen, NAT Gateway nutzen.

Szenario: Eine Datenbankverbindung aus dem Pool wirft nach Ruhepausen „connection reset“. Warum?

Ein Load Balancer oder NAT hat die inaktive Verbindung nach dem Idle Timeout (Azure: 4 Minuten) verworfen. Lösung: TCP Keepalive oder Pool-Idle-Zeit kleiner als das Timeout, Verbindung vor Nutzung prüfen.

Szenario: Kleine API-Calls gehen, grosse Uploads hängen nach einem neuen VPN. Woran denken Sie?

An die MTU. Das VPN verkleinert sie, grosse Pakete werden verworfen, und ICMP „Fragmentation Needed“ kommt nicht durch. Prüfen mit ping -M do -s 1472. Lösung: MTU anpassen oder MSS Clamping.
