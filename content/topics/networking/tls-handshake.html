TLS-Handshake und Zertifikate

Networking · Tier 1 · Quellen: RFC 8446 (TLS 1.3), RFC 5280 (X.509-Zertifikate), RFC 6066 (SNI), RFC 7301 (ALPN), RFC 9000/9001 (QUIC mit TLS), OpenSSL 3.5 Doku (s_client), CA/Browser Forum Baseline Requirements

Kern: TLS (Transport Layer Security) ist ein Protokoll über TCP, das eine Verbindung verschlüsselt, vor Veränderung schützt und den Server authentifiziert. Im Handshake einigen sich Client und Server auf Schlüssel, und der Server beweist mit seinem Zertifikat, wer er ist. Ein Zertifikat ist vertrauenswürdig, wenn seine Kette bei einer Root-CA im eigenen Truststore endet.

1. Wo sitzt TLS?

  1. TLS sitzt zwischen Anwendung und TCP. Die Anwendung schreibt Klartext, TLS schickt verschlüsselte Records.
  2. Der Handshake läuft einmal am Anfang. Danach verschlüsselt der Record Layer jede Nachricht mit einem AEAD-Verfahren (z. B. AES-GCM), also Verschlüsselung plus Integritätsschutz.
  3. Der Server schickt sein Leaf-Zertifikat und die Intermediate-Zertifikate. Jedes ist vom nächsten signiert.
  4. Die Root CA schickt der Server nicht mit. Der Client hat sie schon in seinem Truststore. Nur dann ist die Kette gültig.
  5. Jede Laufzeit hat ihren eigenen Truststore: Windows-Store, /etc/ssl/certs, Java cacerts, Python certifi.

2. Die Reise eines TLS-1.3-Handshakes (die Geschichte zum Merken)

  1. ClientHello: Der Client schickt unterstützte Cipher Suites und gleich einen key_share, also seinen Teil eines (EC)DHE-Schlüsseltauschs. Er rät die Gruppe vorher (z. B. X25519). Im Klartext stehen auch SNI (gewünschter Hostname) und ALPN (gewünschtes Protokoll).
  2. ServerHello: Der Server wählt Suite und Gruppe und schickt seinen key_share. Ab jetzt kennen beide den gemeinsamen Schlüssel. Alles danach ist verschlüsselt.
  3. EncryptedExtensions: Weitere Antworten, z. B. das gewählte ALPN-Protokoll h2.
  4. Certificate: Der Server schickt Leaf- und Intermediate-Zertifikate. In TLS 1.3 sieht ein Lauscher das Zertifikat nicht mehr.
  5. CertificateVerify: Der Server signiert den bisherigen Handshake mit dem privaten Schlüssel seines Zertifikats. So beweist er, dass er den Schlüssel besitzt.
  6. Client prüft: Kette bis zur Root im Truststore, Gültigkeit, Hostname im SAN (Subject Alternative Name), Signatur. Scheitert ein Punkt, bricht der Client ab.
  7. Finished: Beide bestätigen mit einem MAC über den ganzen Handshake. Der Client schickt seinen HTTP-Request direkt mit. Das ist 1-RTT.
  8. NewSessionTicket: Nach dem Handshake schickt der Server ein Ticket. Damit kann der Client später schneller wiederverbinden (Resumption, optional mit 0-RTT).

Echte Ausgabe, curl/OpenSSL/Python unter Windows (OpenSSL 3.5.9, Python 3.12 mit OpenSSL 3.0). Gekürzt: Record-Header-Zeilen, PEM-Block, Session-Ticket-Daten, Pfade in Fehlermeldungen.

  1. Handshake-Nachrichten: Genau die Reise aus Abschnitt 2. Nach dem ServerHello kommen EncryptedExtensions, Certificate, CertificateVerify und Finished in einem Flug. Der Client antwortet nur mit Finished.
  2. ChangeCipherSpec: In TLS 1.3 ohne Funktion. Er ist nur für alte Middleboxen drin (Middlebox Compatibility Mode).
  3. Kette: Leaf (0) → zwei Intermediates (1, 2) → Root (3). Die Root ist hier quer-signiert (Cross-Sign) von einer älteren Root. So vertrauen ihr auch alte Clients.
  4. Gültigkeit: Das Leaf-Zertifikat gilt rund 90 Tage. Kurze Laufzeiten erzwingen Automatisierung.
  5. Gruppe: X25519MLKEM768 ist ein hybrider Post-Quanten-Schlüsseltausch. OpenSSL 3.5 und Cloudflare nutzen ihn standardmässig.
  6. ALPN: Der Server wählt h2. Das ist die HTTP-Version für diese Verbindung.
  7. Ohne SNI: Der Server weiss nicht, welches Zertifikat er schicken soll. Er bricht mit Alert 40 ab.
  8. Hostname falsch: Die Kette ist gültig, aber der Name steht nicht im SAN. Fehler 62.
  9. Fremde CA: Die Kette endet bei einer Root, die nicht im Truststore liegt. Die Meldung „unable to get local issuer certificate“ ist genau der Fehler hinter Firmen-Proxies.
  10. Dauer: TLS 1.3 braucht etwa 1 RTT plus Rechenzeit. TLS 1.2 braucht etwa 2 RTT. Der TCP-Connect davor zeigt die RTT (ca. 30 ms).

4. Details, die Interviewer fragen

  1. Was TLS liefert: Vertraulichkeit (Verschlüsselung), Integrität (keine unbemerkte Änderung), Authentizität (Server, optional Client).
  2. Asymmetrisch und symmetrisch: Der Handshake nutzt asymmetrische Kryptografie für Schlüsseltausch und Signatur. Die Daten verschlüsselt ein schneller symmetrischer Schlüssel.
  3. Forward Secrecy: TLS 1.3 nutzt nur kurzlebige (EC)DHE-Schlüssel. Wird der private Server-Schlüssel später gestohlen, bleiben alte Mitschnitte geheim.
  4. Was TLS 1.3 entfernt hat: RSA-Schlüsseltausch, statisches DH, CBC-Modi, RC4, SHA-1, Kompression, Renegotiation. Es bleiben 5 Cipher Suites.
  5. HelloRetryRequest: Hat der Client die falsche Gruppe geraten, fordert der Server einen neuen key_share an. Das kostet 1 RTT mehr.
  6. Zertifikat: enthält Public Key, Subject, SAN (gültige Hostnamen), Gültigkeit, Aussteller, Key Usage und die Signatur der CA. Clients prüfen den Hostnamen im SAN, nicht im CN.
  7. Chain of Trust: Jedes Zertifikat ist vom nächsten signiert. Der Server muss die Intermediates mitschicken. Fehlt eines, scheitern viele Clients (curl, Java, Python). Browser holen es manchmal selbst nach.
  8. Wildcard: *.example.com gilt für genau eine Ebene: api.example.com, nicht a.b.example.com und nicht example.com.
  9. Widerruf: Über CRL (Sperrliste) oder OCSP (Online-Abfrage). OCSP Stapling: Der Server liefert die OCSP-Antwort im Handshake mit.
  10. SNI (Server Name Indication): Der Client nennt den Hostnamen im ClientHello. So kann eine IP viele Zertifikate bedienen. SNI ist Klartext. ECH (Encrypted Client Hello) verschlüsselt ihn.
  11. mTLS (mutual TLS): Der Server schickt CertificateRequest. Der Client antwortet mit eigenem Certificate und CertificateVerify. So authentifizieren sich beide Seiten. Typisch für Service-zu-Service und Service Meshes.
  12. TLS Inspection (Firmen-Proxy): Der Proxy beendet die TLS-Verbindung, liest den Inhalt und baut eine neue zum Ziel. Dem Client zeigt er ein Zertifikat, das er mit der Firmen-CA neu signiert hat. Clients ohne diese CA im Truststore brechen ab.
  13. Truststores pro Laufzeit: Windows-Store, Linux /etc/ssl/certs (update-ca-certificates), Java cacerts (keytool), Python requests mit certifi (REQUESTS_CA_BUNDLE), Node.js (NODE_EXTRA_CA_CERTS).
  14. Laufzeit von Zertifikaten: Das CA/Browser Forum senkt die maximale Laufzeit öffentlicher Zertifikate schrittweise: 200 Tage ab März 2026, bis 47 Tage ab 2029. Manuelles Erneuern skaliert nicht mehr.

5. Vergleich

  • TLS 1.2: 2 RTT, viele alte Cipher Suites, Zertifikat im Klartext sichtbar, Forward Secrecy optional.
  • TLS 1.3: 1 RTT, 0-RTT bei Resumption möglich, nur 5 Suites, Zertifikat verschlüsselt, Forward Secrecy immer.
  • Server-TLS: Nur der Server beweist seine Identität. Standard im Web.
  • mTLS: Beide Seiten zeigen Zertifikate. Für Service-zu-Service, Zero Trust, Partner-APIs.
  • Öffentliche CA: im Truststore aller Geräte. Für öffentliche Endpunkte.
  • Private CA (z. B. Firmen-CA, cert-manager Issuer): nur dort vertraut, wo man sie verteilt. Für interne Dienste.
  • Self-signed: Zertifikat signiert sich selbst. Nur für Tests, oder wenn man es explizit pinnt.

6. In der Produktion

  1. Firmen-Proxy bricht Builds: pip, Maven, npm oder Spark melden „unable to get local issuer certificate“ oder PKIX path building failed. Ursache: Der Proxy signiert neu, die Laufzeit kennt die Firmen-CA nicht. Lösung: Firmen-CA in jeden Truststore des Images: OS-Store, Java cacerts, REQUESTS_CA_BUNDLE. Nie verify=False.
  2. Zertifikat abgelaufen: Ausfall über Nacht. Lösung: Automatisch erneuern (cert-manager, Key Vault mit Auto-Rotation, ACME) und Ablaufdatum überwachen.
  3. Intermediate fehlt: Browser gehen, curl und Java nicht. Lösung: die volle Kette (fullchain.pem) am Server konfigurieren.
  4. Falscher Hostname: Der Client spricht eine IP oder einen internen Namen an, der nicht im SAN steht. Lösung: Namen in den SAN aufnehmen oder den richtigen Namen nutzen. Hostname-Prüfung nie abschalten.
  5. SNI fehlt: Alte Clients oder Health Probes ohne SNI bekommen das Standard-Zertifikat oder einen Abbruch. Lösung: SNI im Client setzen, Standard-Zertifikat definieren.
  6. mTLS-Client-Zertifikat abgelaufen: Partner-Integration fällt aus, Fehler certificate required oder bad certificate. Lösung: Ablauf überwachen, Rotation mit Überlappung.
  7. Uhrzeit falsch: Ein Container mit falscher Zeit sieht gültige Zertifikate als „noch nicht gültig“. Lösung: NTP.

7. Diagnose: Werkzeuge und Befehle

  • openssl s_client -connect host:443 -servername host -showcerts: Kette, Protokoll, Cipher, Verify-Ergebnis.
  • openssl s_client … -msg oder -trace: jede Handshake-Nachricht.
  • openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName: Zertifikat lesen.
  • curl -v https://host: Verify-Fehler, ALPN, Zertifikat-Infos. curl --cacert ca.pem: mit eigener CA testen.
  • curl -w "%{time_connect} %{time_appconnect}": Dauer von TCP und TLS getrennt.
  • keytool -list -cacerts: Java-Truststore ansehen. -Djavax.net.debug=ssl:handshake: Java-Handshake loggen.
  • python -c "import certifi; print(certifi.where())": Welche CA-Datei nutzt requests?
  • Wireshark: Filter tls.handshake. Mit SSLKEYLOGFILE auch den Inhalt entschlüsseln.
  • kubectl describe certificate (cert-manager): Status und Ablauf von Zertifikaten im Cluster.

8. Senior-Punkte

  1. Zertifikate sind ein Betriebsprozess: Inventar, Automatisierung, Überwachung des Ablaufs. Die meisten TLS-Ausfälle sind abgelaufene Zertifikate.
  2. Vertrauen ist pro Laufzeit. Ein Container hat mehrere Truststores. Eine CA im OS-Store reicht nicht für Java oder requests.
  3. Verify nie abschalten. verify=False und -k öffnen Man-in-the-Middle. Richtig ist: die richtige CA hinzufügen.
  4. TLS-Termination ist eine Architektur-Entscheidung: Wo endet TLS (Front Door, Gateway, Pod)? Wo braucht es Re-Encryption oder mTLS?
  5. Kurze Laufzeiten sind gewollt. Sie begrenzen den Schaden gestohlener Schlüssel. Planen: ACME, cert-manager, Key Vault-Rotation.
  6. Private Schlüssel gehören in einen Tresor (Key Vault, HSM), nie ins Image oder Git.

10. Fallen

  • „TLS verschlüsselt auch den Hostnamen.“ → Falsch. SNI ist Klartext, ausser mit ECH. DNS-Anfragen sind ohne DoH/DoT auch sichtbar.
  • „Der Server schickt die Root CA mit.“ → Falsch. Die Root muss schon im Truststore des Clients sein.
  • „Geht im Browser, also ist das Zertifikat richtig.“ → Falsch. Browser ergänzen fehlende Intermediates. curl und Java nicht.
  • „Der CN zählt für den Hostnamen.“ → Falsch. Clients prüfen den SAN.
  • „SSL und TLS sind dasselbe.“ → Nicht ganz. SSL ist der veraltete Vorgänger und unsicher. Heute nur TLS 1.2 und 1.3.
  • „Wenn der Proxy das Problem ist, setze ich verify=False.“ → Falsch. Die Firmen-CA in den Truststore aufnehmen.

11. Fragen

Was ist TLS und was schützt es?

Ein Protokoll über TCP. Es liefert Vertraulichkeit, Integrität und Authentizität des Servers, optional auch des Clients.

Wie läuft der TLS-1.3-Handshake ab?

ClientHello mit key_share, SNI und ALPN. ServerHello mit key_share. Dann verschlüsselt: EncryptedExtensions, Certificate, CertificateVerify, Finished. Client: Finished plus erster Request. 1 RTT.

Warum ist TLS 1.3 schneller als TLS 1.2?

Der Client schickt seinen Schlüsselanteil gleich im ClientHello. So reicht 1 RTT statt 2.

Was ist Forward Secrecy?

Jede Verbindung nutzt kurzlebige Schlüssel. Ein später gestohlener Server-Schlüssel entschlüsselt keine alten Mitschnitte.

Was ist 0-RTT und was ist das Risiko?

Bei Wiederverbindung sendet der Client Daten im ersten Flug. Diese Daten kann ein Angreifer wiederholen. Nur für idempotente Requests.

Was steht in einem Zertifikat?

Public Key, Subject, SAN mit Hostnamen, Gültigkeit, Aussteller, Key Usage und die Signatur der CA.

Was ist die Chain of Trust?

Leaf ist vom Intermediate signiert, das Intermediate von der Root. Die Root liegt im Truststore des Clients. Nur dann ist die Kette gültig.

Warum gibt es Intermediate CAs?

Der Root-Schlüssel bleibt offline und sicher. Wird ein Intermediate kompromittiert, sperrt man nur dieses.

Was macht CertificateVerify?

Der Server signiert den Handshake mit seinem privaten Schlüssel. So beweist er, dass ihm das Zertifikat gehört.

Was ist SNI und warum braucht man es?

Der Client nennt den Hostnamen im ClientHello. So kann ein Server mit einer IP viele Zertifikate liefern.

Was ist ALPN?

Eine TLS-Erweiterung zur Wahl des Anwendungsprotokolls, z. B. h2 oder http/1.1. Spart eine Extra-Runde.

Was ist mTLS?

Beide Seiten zeigen Zertifikate. Der Server fordert mit CertificateRequest ein Client-Zertifikat an. Typisch zwischen Services.

Wie funktioniert TLS Inspection in einem Firmen-Proxy?

Der Proxy beendet TLS, liest den Inhalt und baut eine neue Verbindung zum Ziel. Dem Client zeigt er ein Zertifikat, das die Firmen-CA signiert hat.

Was bedeutet „unable to get local issuer certificate“?

Die Kette endet bei einer CA, die nicht im Truststore liegt. Oft ein Firmen-Proxy oder ein fehlendes Intermediate.

Was ist ein Truststore und warum gibt es mehrere?

Die Liste vertrauter Root-CAs. OS, Java, Python certifi und Node haben je eine eigene.

Wie wird ein Zertifikat widerrufen?

Über CRL oder OCSP. Mit OCSP Stapling liefert der Server die Antwort gleich mit.

Wofür gilt ein Wildcard-Zertifikat?

*.example.com gilt für eine Ebene, z. B. api.example.com. Nicht für example.com und nicht für a.b.example.com.

Was ist der Unterschied zwischen TLS-Termination und Passthrough?

Termination: Der Proxy entschlüsselt und sieht HTTP. Passthrough: Er leitet verschlüsselt weiter, das Backend hat das Zertifikat.

Was hat TLS 1.3 entfernt?

RSA-Schlüsseltausch, CBC, RC4, SHA-1, Kompression und Renegotiation. Es gibt nur noch 5 Cipher Suites.

Warum sieht man in TLS 1.3 das Zertifikat nicht mehr im Mitschnitt?

Es kommt nach dem ServerHello und ist schon verschlüsselt.

Szenario: Im Firmennetz scheitern pip install und Maven mit Zertifikatsfehlern, zu Hause geht alles. Was tun Sie?

Der Proxy signiert TLS neu. Firmen-CA besorgen und in alle Truststores aufnehmen: OS-Store, Java cacerts, REQUESTS_CA_BUNDLE bzw. pip-Konfiguration. Im Docker-Image fest einbauen. Nicht verify=False.

Szenario: Eine API geht im Browser, aber der Java-Client meldet PKIX path building failed. Warum?

Wahrscheinlich fehlt am Server ein Intermediate. Der Browser holt es nach, Java nicht. Prüfen mit openssl s_client -showcerts. Lösung: volle Kette am Server.

Szenario: Nach einem Wochenende ist der Ingress mit „certificate has expired“ down. Wie verhindern Sie das künftig?

Automatische Erneuerung mit cert-manager oder Key Vault-Rotation. Ablauf überwachen und alarmieren, z. B. 30 Tage vorher. Inventar aller Zertifikate führen.
