HTTP/1.1 vs HTTP/2 vs HTTP/3

Networking · Tier 1 · Quellen: RFC 9110 (HTTP Semantics), RFC 9112 (HTTP/1.1), RFC 9113 (HTTP/2), RFC 7541 (HPACK), RFC 9114 (HTTP/3), RFC 9204 (QPACK), RFC 9000 (QUIC), RFC 7838 (Alt-Svc), gRPC-Doku (PROTOCOL-HTTP2), Microsoft Learn (Application Gateway FAQ)

Kern: Alle drei Versionen haben dieselbe Semantik (Methoden, Status-Codes, Header nach RFC 9110). Sie unterscheiden sich im Transport der Nachrichten. HTTP/1.1 schickt Text, ein Request nach dem anderen pro Verbindung. HTTP/2 schickt binäre Frames vieler Streams über eine TCP-Verbindung. HTTP/3 nutzt QUIC über UDP und beseitigt so das TCP-Head-of-Line-Blocking.

1. Wo sitzen die drei Versionen?

  1. Semantik: Methoden, Status-Codes und Header sind in allen Versionen gleich. Eine App merkt die Version meist nicht.
  2. HTTP/1.1 (RFC 9112): Text-Nachrichten über TCP, optional mit TLS. Pro Verbindung läuft immer nur ein Request.
  3. HTTP/2 (RFC 9113): binäre Frames über TCP. Browser sprechen es nur mit TLS. Die Version wird im TLS-Handshake per ALPN ausgehandelt (h2).
  4. HTTP/3 (RFC 9114): Frames über QUIC (RFC 9000). QUIC läuft über UDP und enthält TLS 1.3 fest eingebaut.

2. Die Reise von zwei Requests (die Geschichte zum Merken)

  1. HTTP/1.1, Request A: Der Client öffnet eine TCP-Verbindung und schickt A. Er muss die ganze Antwort A lesen, bevor B auf dieselbe Verbindung darf. Das ist Head-of-Line Blocking auf HTTP-Ebene.
  2. HTTP/1.1, Ausweg: Browser öffnen darum bis zu 6 Verbindungen pro Host. Jede kostet Handshake, TLS und Slow Start.
  3. HTTP/2, Multiplexing: A wird zu Stream 1, B zu Stream 3. Ihre Frames laufen verschränkt über eine Verbindung. Kein Warten auf HTTP-Ebene mehr.
  4. HTTP/2, Paketverlust: TCP kennt keine Streams, nur einen Byte-Strom. Fehlt ein Paket von Stream 1, hält TCP alles dahinter zurück. Auch Stream 3 steht. Das ist TCP-Head-of-Line Blocking.
  5. HTTP/3, QUIC: QUIC kennt Streams selbst. Ein verlorenes Paket blockiert nur seinen Stream. Stream 3 wird sofort an die App geliefert.
  6. HTTP/3, Start: Der Client weiss vorher nicht, ob der Server HTTP/3 kann. Er lernt es aus dem Header alt-svc: h3=":443" oder aus einem DNS-HTTPS-Record. Beim nächsten Mal probiert er QUIC über UDP 443.

Diese curl-Version ist ohne HTTP/2-Bibliothek gebaut (--http2: „not supported“). Darum spricht ein kleines Python-Skript HTTP/2 von Hand: TLS mit ALPN, Preface, SETTINGS, zwei HEADERS-Frames mit HPACK.

# h2_raw.py (Auszug)
ctx.set_alpn_protocols(["h2", "http/1.1"])
block1 = bytes([0x82, 0x87, 0x84, 0x41, 11]) + b"example.com"  # GET, https, /, :authority neu
block2 = bytes([0x82, 0x87, 0x84, 0xBE])                         # 0xBE = Index 62, dynamische Tabelle
out  = b"PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n" + frame(SETTINGS, 0, 0, b"")
out += frame(HEADERS, END_STREAM|END_HEADERS, 1, block1)
out += frame(HEADERS, END_STREAM|END_HEADERS, 3, block2)

Echte Ausgabe, curl/OpenSSL/Python unter Windows (curl 8.23.0, Python 3.12). curl-Ausgabe gekürzt: schannel-Zeilen, IP-Adressen, Fortschrittsbalken und Teile der Header entfernt.

  1. ALPN: curl bietet http/1.1 an, der Server akzeptiert. Python bietet h2 an und bekommt h2. Die Version wird im TLS-Handshake entschieden, ohne Extra-Runde.
  2. Keep-Alive: Der zweite curl-Request nutzt dieselbe Verbindung: „Reusing existing connection“. In HTTP/1.1 sind Verbindungen standardmässig persistent.
  3. Chunked: Transfer-Encoding: chunked heisst: Die Länge steht nicht vorher fest. Der Body kommt in Stücken. Das gibt es nur in HTTP/1.1.
  4. Alt-Svc: Der Server sagt h3=":443"; ma=86400: „Ich kann HTTP/3 auf UDP 443, merk dir das 24 Stunden.“
  5. SETTINGS: Der Server erlaubt 256 parallele Streams und ein Startfenster von 64 KB pro Stream. WINDOW_UPDATE vergrössert das Fenster der ganzen Verbindung (Flow Control in HTTP/2).
  6. Multiplexing: Zwei Requests auf Stream 1 und 3 in einer TCP-Verbindung. Beide Antworten kommen zurück. Client-Streams haben ungerade Nummern.
  7. HPACK: Request 1 braucht 16 Bytes Header, Request 2 nur 4 Bytes. :authority steht nach Request 1 in der dynamischen Tabelle und kostet dann 1 Byte. Auch die Antwort-Header schrumpfen von 162 auf 28 Bytes.
  8. Status: 0x88 ist Index 8 der statischen HPACK-Tabelle: :status 200. Ein ganzer Status in einem Byte.

4. Details, die Interviewer fragen

  1. Keep-Alive (HTTP/1.1): Verbindungen bleiben standardmässig offen. Connection: close beendet sie nach der Antwort.
  2. Pipelining: HTTP/1.1 erlaubt mehrere Requests ohne Warten. Antworten müssen aber in Reihenfolge kommen. Browser haben es nie aktiviert, weil Proxies es oft falsch umsetzten.
  3. Binary Framing (HTTP/2): Jede Nachricht besteht aus Frames mit 9 Byte Header: Länge, Typ, Flags, Stream-ID. Typen: HEADERS, DATA, SETTINGS, WINDOW_UPDATE, RST_STREAM, PING, GOAWAY.
  4. Stream: Ein Stream ist ein Request-Response-Paar mit eigener ID. RST_STREAM bricht einen Stream ab, ohne die Verbindung zu schliessen.
  5. HPACK (RFC 7541): Header-Kompression mit statischer Tabelle (61 Einträge), dynamischer Tabelle und Huffman-Code. Sie setzt eine geordnete Übertragung voraus.
  6. QPACK (RFC 9204): HPACK-Variante für HTTP/3. QUIC-Streams kommen in beliebiger Reihenfolge an. Darum laufen Tabellen-Updates über eigene Encoder- und Decoder-Streams.
  7. Server Push: HTTP/2 konnte Antworten ungefragt senden. Browser haben es entfernt. Heute: 103 Early Hints oder Preload.
  8. Prioritäten: Das Prioritäts-Schema aus RFC 7540 ist in RFC 9113 veraltet. Ersatz: Extensible Priorities (RFC 9218) mit dem Header priority.
  9. h2c: HTTP/2 ohne TLS. Browser unterstützen es nicht. Im Cluster nutzt man es mit Prior Knowledge: Der Client weiss vorher, dass der Server HTTP/2 spricht.
  10. QUIC (RFC 9000): Transport über UDP mit Streams, Verlust-Erkennung, Congestion Control und eingebautem TLS 1.3. Neue Verbindung: 1 RTT statt TCP + TLS (2 RTT).
  11. 0-RTT: Bei einer Wiederverbindung kann QUIC Daten im ersten Paket senden. Risiko: Replay. Darum nur für idempotente Requests.
  12. Connection Migration: QUIC erkennt Verbindungen an einer Connection ID, nicht am 5-Tupel. Wechselt das Handy von WLAN auf Mobilfunk, läuft die Verbindung weiter.
  13. gRPC braucht HTTP/2: gRPC nutzt Streams für Streaming-RPCs und Trailers für den Status (grpc-status). Beides braucht HTTP/2 Ende zu Ende. Browser brauchen darum gRPC-Web über einen Proxy.
  14. Load Balancing bei HTTP/2: Ein Client hält eine lange Verbindung mit vielen Requests. Ein L4-Balancer verteilt Verbindungen, nicht Requests. Ein Pod bekommt so alle Last. Lösung: L7-Proxy oder Client-seitiges Balancing.

5. Vergleich

  • Format: HTTP/1.1 Text. HTTP/2 und HTTP/3 binäre Frames.
  • Parallelität: HTTP/1.1 ein Request pro Verbindung, darum mehrere Verbindungen. HTTP/2 und HTTP/3 viele Streams in einer Verbindung.
  • Head-of-Line Blocking: HTTP/1.1 auf HTTP-Ebene. HTTP/2 auf TCP-Ebene. HTTP/3 keins zwischen Streams.
  • Header-Kompression: HTTP/1.1 keine. HTTP/2 HPACK. HTTP/3 QPACK.
  • Transport: HTTP/1.1 und HTTP/2 über TCP. HTTP/3 über QUIC/UDP.
  • TLS: HTTP/1.1 optional. HTTP/2 in Browsern nur mit TLS. HTTP/3 immer TLS 1.3.
  • Verbindungsaufbau neu: HTTPS mit TCP + TLS 1.3: 2 RTT. HTTP/3: 1 RTT, bei Wiederverbindung 0-RTT möglich.
  • Erkennung: HTTP/2 per ALPN im TLS-Handshake. HTTP/3 per Alt-Svc-Header oder DNS-HTTPS-Record.

6. In der Produktion

  1. gRPC hinter Azure Application Gateway: Application Gateway spricht HTTP/2 nur mit Clients. Zum Backend spricht es immer HTTP/1.1. gRPC bricht. Lösung: Proxy mit HTTP/2 bis zum Backend, z. B. ein Ingress- oder Gateway-API-Controller.
  2. gRPC-Last ungleich verteilt: Ein Kubernetes-Service (L4) verteilt nur Verbindungen. Ein Client mit einer Verbindung trifft immer denselben Pod. Lösung: L7-Proxy oder Service Mesh, oder Headless Service mit Client-seitigem Balancing.
  3. HTTP/3 kommt nicht zustande: Firewalls blocken UDP 443. Clients fallen still auf HTTP/2 zurück. Das ist gewollt, aber man misst keine Verbesserung.
  4. Zu viele Verbindungen mit HTTP/1.1: Ein Client ohne Pool öffnet pro Request eine Verbindung. Folge: TIME_WAIT, SNAT-Erschöpfung, langsamer Start. Lösung: Keep-Alive und Pool.
  5. Idle Timeout bei langen Streams: Server-Streaming bei gRPC oder lange Downloads werden vom Proxy getrennt. Lösung: HTTP/2-PING oder gRPC-Keepalive, Proxy-Timeouts anpassen.
  6. HTTP/2-Angriffe: „Rapid Reset“ (CVE-2023-44487) öffnet und schliesst Streams in hoher Zahl. Lösung: Server- und Proxy-Versionen aktuell halten, Stream-Limits setzen.

7. Diagnose: Werkzeuge und Befehle

  • curl -v --http1.1 / --http2 / --http3 URL: Version erzwingen, ALPN und Header sehen (curl braucht dafür nghttp2 bzw. HTTP/3-Unterstützung, siehe curl -V).
  • curl -sI -o /dev/null -w "%{http_version}\n" URL: Welche Version wurde benutzt?
  • openssl s_client -connect host:443 -alpn h2,http/1.1: Was handelt der Server per ALPN aus?
  • Browser DevTools, Tab Network, Spalte „Protocol“: http/1.1, h2, h3.
  • grpcurl -plaintext host:port list: gRPC-Dienste testen, mit Reflection.
  • Wireshark: Filter http2 oder quic. Für TLS-Inhalte SSLKEYLOGFILE setzen und die Schlüssel laden.
  • nghttp -nv URL: zeigt jeden HTTP/2-Frame.

8. Senior-Punkte

  1. Die Version ist Sache der Infrastruktur. Die App-Semantik bleibt gleich. Entscheidend ist, was jeder Proxy auf dem Weg spricht.
  2. Jeder Hop handelt neu aus. Client → Front Door kann HTTP/3 sein, Front Door → Backend HTTP/1.1. „Wir nutzen HTTP/2“ gilt immer pro Hop.
  3. Lange Verbindungen brauchen L7-Balancing. HTTP/2 und gRPC verteilen sich mit L4 schlecht.
  4. HTTP/3 hilft vor allem bei schlechten Netzen: Mobilfunk, Paketverlust, Netzwechsel. Im Rechenzentrum ist der Gewinn klein.
  5. Weniger Verbindungen, mehr Wiederverwendung: Das bringt meist mehr als ein Versionswechsel.
  6. 0-RTT nur für idempotente Requests. Ein wiederholtes POST kann sonst doppelt buchen.

10. Fallen

  • „HTTP/2 löst Head-of-Line Blocking.“ → Nur halb. Auf HTTP-Ebene ja, auf TCP-Ebene nein. Das löst erst HTTP/3.
  • „HTTP/3 ist unverschlüsselt, weil UDP.“ → Falsch. QUIC enthält TLS 1.3 fest. Unverschlüsselt geht gar nicht.
  • „HTTP/2 braucht viele Verbindungen für Parallelität.“ → Falsch. Eine Verbindung reicht, Streams laufen parallel.
  • „Mit Application Gateway läuft gRPC Ende zu Ende.“ → Falsch. Zum Backend spricht es HTTP/1.1.
  • „Server Push ist die Zukunft.“ → Falsch. Browser haben es entfernt. Ersatz: 103 Early Hints.
  • „HTTP/2 ändert Status-Codes und Methoden.“ → Falsch. Die Semantik ist gleich (RFC 9110).

11. Fragen

Was ist der Hauptunterschied zwischen HTTP/1.1, HTTP/2 und HTTP/3?

Gleiche Semantik, anderer Transport. 1.1: Text, ein Request pro Verbindung. 2: binäre Frames, viele Streams über TCP. 3: Frames über QUIC/UDP, Streams unabhängig.

Was ist Keep-Alive in HTTP/1.1?

Die TCP-Verbindung bleibt nach der Antwort offen und wird für weitere Requests genutzt. In HTTP/1.1 ist das Standard.

Was ist Head-of-Line Blocking?

Ein wartendes Element hält alle folgenden auf. Bei HTTP/1.1 wartet Request B auf Antwort A. Bei HTTP/2 hält ein verlorenes TCP-Paket alle Streams auf.

Was ist Multiplexing in HTTP/2?

Viele Requests laufen als Streams mit eigener ID verschränkt über eine Verbindung.

Warum hat HTTP/2 Head-of-Line Blocking nur teilweise gelöst?

TCP liefert einen geordneten Byte-Strom. Fehlt ein Paket, wartet TCP mit allem dahinter, egal zu welchem Stream es gehört.

Was ist HPACK?

Header-Kompression in HTTP/2: statische Tabelle, dynamische Tabelle und Huffman. Wiederholte Header kosten nur ein Byte.

Warum braucht HTTP/3 QPACK statt HPACK?

HPACK setzt eine feste Reihenfolge voraus. QUIC-Streams kommen unabhängig an. QPACK schickt Tabellen-Updates über eigene Streams.

Was ist QUIC?

Ein Transportprotokoll über UDP mit Streams, Verlust-Erkennung, Congestion Control und eingebautem TLS 1.3. Basis von HTTP/3.

Warum läuft QUIC über UDP und nicht als neues Protokoll über IP?

Firewalls und NAT lassen neue Protokolle kaum durch. UDP kommt fast überall durch, und QUIC läuft im User Space.

Wie weiss der Client, welche Version der Server kann?

HTTP/2 per ALPN im TLS-Handshake. HTTP/3 per Alt-Svc-Header oder DNS-HTTPS-Record.

Was ist ALPN?

Application-Layer Protocol Negotiation: eine TLS-Erweiterung. Der Client bietet z. B. h2 und http/1.1 an, der Server wählt eins.

Was ist 0-RTT und was ist das Risiko?

Daten schon im ersten Paket einer Wiederverbindung. Ein Angreifer kann sie wiederholen (Replay). Darum nur für idempotente Requests.

Was ist Connection Migration?

QUIC erkennt eine Verbindung an der Connection ID. Ändert sich IP oder Port, läuft sie weiter.

Warum braucht gRPC HTTP/2?

gRPC nutzt Streams für Streaming-RPCs und Trailers für den Status. Beides gibt es so nur in HTTP/2.

Warum verteilt ein L4-Load-Balancer gRPC schlecht?

Er verteilt Verbindungen. gRPC schickt viele Requests über eine lange Verbindung. Ein Backend bekommt alles.

Was ist h2c?

HTTP/2 ohne TLS. Browser können es nicht. Intern nutzt man es mit Prior Knowledge.

Was passierte mit Server Push?

Browser haben es entfernt, weil es selten half. Ersatz: 103 Early Hints und Preload.

Was macht ein GOAWAY-Frame?

Der Server kündigt das Ende der Verbindung an. Laufende Streams dürfen fertig werden, neue gehen auf eine neue Verbindung. Wichtig für sauberes Deployment.

Ist HTTP/3 immer schneller?

Nein. Bei gutem Netz ist der Unterschied klein. Bei Verlust und Mobilfunk hilft es deutlich. UDP kostet auf manchen Servern mehr CPU.

Szenario: Ein gRPC-Service hinter Azure Application Gateway liefert nur Fehler. Warum?

Application Gateway spricht zum Backend nur HTTP/1.1. gRPC braucht HTTP/2 und Trailers. Lösung: Proxy mit HTTP/2 zum Backend, z. B. Ingress- oder Gateway-Controller.

Szenario: Drei gRPC-Pods, aber einer hat 100 % CPU und zwei sind leer. Warum?

Der Client hält eine HTTP/2-Verbindung. Der Kubernetes-Service balanciert nur Verbindungen. Lösung: L7-Proxy oder Mesh, oder Headless Service mit Client-Balancing (round_robin).

Szenario: Sie aktivieren HTTP/3 am Edge, aber die Messung zeigt keine Änderung. Woran liegt es?

Viele Clients erreichen UDP 443 nicht (Firmen-Firewalls) und fallen auf HTTP/2 zurück. Oder der erste Besuch nutzt noch TCP, weil Alt-Svc erst gelernt wird. Prüfen mit der Spalte Protocol in DevTools und Edge-Logs.
