Spring Cloud: Config, Gateway, Resilience4j

Spring · Tier 2 · Quellen: Spring Cloud Release Train 2026.0.0 Reference (Boot 4.2.0), Spring Cloud Gateway 5.1 Reference (Server WebFlux: Starter, How It Works), Spring Cloud Config Reference, Spring Cloud Circuit Breaker Reference, Resilience4j Doku (CircuitBreaker), Spring Framework 7.1 Reference („Resilience Features“)

Kern: Spring Cloud ist eine Sammlung von Projekten für typische Probleme verteilter Systeme. Die drei wichtigsten: Config (zentrale Konfiguration), Gateway (ein Eingang mit Routing und Filtern) und Circuit Breaker mit Resilience4j (Schutz vor kaputten Abhängigkeiten). Der aktuelle Release Train 2026.0.0 passt zu Spring Boot 4.2.

1. Wo sitzt Spring Cloud?

  1. Gateway: Ein Eingang für alle Clients. Er leitet /api/orders/** an den Order-Service und prüft z. B. Tokens und Rate Limits.
  2. Config Server: Ein Service, der Konfiguration aus Git, Vault oder einer DB liefert. Die Services holen sie beim Start.
  3. Services: Normale Spring-Boot-Apps mit dem Config-Client.
  4. Circuit Breaker: Im Order-Service um den Aufruf zu Payment. Ist Payment kaputt, ruft er ihn eine Zeit lang gar nicht mehr auf.
  5. Weitere Projekte: OpenFeign (deklarative HTTP-Clients), Spring Cloud Kubernetes (ConfigMaps), Stream (Kafka/RabbitMQ), Netflix Eureka (Service Discovery).

2. Die Reise eines Aufrufs durch Gateway und Circuit Breaker

  1. Handler Mapping: Das Gateway prüft jede Route. Eine Route hat ID, Ziel-URI, Predicates (Bedingungen wie Path=/api/orders/**) und Filter.
  2. Pre-Filter: Die Filter laufen vor dem Weiterleiten. Beispiel: Präfix entfernen, Header setzen, Rate Limit prüfen.
  3. Proxy: Das Gateway schickt den Request an den Service. Ohne Port in der URI nimmt es 80 bzw. 443.
  4. Service ruft Payment: Der Circuit Breaker ist CLOSED und zählt Erfolge und Fehler in einem Sliding Window (Standard: letzte 100 Aufrufe).
  5. Payment fällt aus: Sind mindestens 50 % der Aufrufe fehlgeschlagen, geht der Breaker auf OPEN. Jetzt kommt sofort CallNotPermittedException bzw. der Fallback. Payment bekommt Ruhe.
  6. Probe: Nach 60 Sekunden lässt HALF_OPEN 10 Probe-Aufrufe durch. Gehen sie gut, wird er CLOSED. Sonst wieder OPEN.
  7. Rückweg: Die Antwort läuft durch die Post-Filter des Gateways zurück zum Client.

3. Beispiel: Route, Config-Import, Circuit Breaker

# Gateway (spring-cloud-starter-gateway-server-webflux)
spring.cloud.gateway.server.webflux.routes:
  - id: orders
    uri: http://order-service:8080
    predicates: [ Path=/api/orders/** ]
    filters:
      - StripPrefix=1
      - name: CircuitBreaker
        args: { name: orders, fallbackUri: forward:/fallback/orders }

# Service: Konfiguration vom Config Server
spring.config.import: optional:configserver:http://config:8888

# Resilience4j im Service
resilience4j.circuitbreaker.instances.payment:
  sliding-window-size: 20
  minimum-number-of-calls: 10
  failure-rate-threshold: 50
  wait-duration-in-open-state: 30s
resilience4j.timelimiter.instances.payment.timeout-duration: 2s

@Service
class PaymentClient {
  private final CircuitBreakerFactory<?, ?> cbFactory;
  Payment pay(Order o) {
    return cbFactory.create("payment").run(
        () -> rest.post().uri("/payments").body(o).retrieve().body(Payment.class),
        ex -> Payment.pending(o));                     // Fallback
  }
}
Payment-Service gestoppt, 12 Aufrufe:
Aufruf 1–10: Fehler (Connection refused) → Fallback "PENDING", Breaker CLOSED
             nach Aufruf 10: Fehlerrate 100 % ≥ 50 % → OPEN
Aufruf 11–12: CallNotPermittedException → Fallback "PENDING", sofort (< 1 ms)
/actuator/health → "circuitBreakers": {"payment": {"status":"CIRCUIT_OPEN", ...}}
nach 30 s: nächster Aufruf → HALF_OPEN, Probe-Aufrufe

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spring Cloud 2026.0.0, Spring Boot 4.2, Resilience4j über Spring Cloud Circuit Breaker. Der Health-Indicator braucht management.health.circuitbreakers.enabled=true.

  1. minimum-number-of-calls: 10: Vor 10 Aufrufen rechnet der Breaker keine Fehlerrate. Mit dem Standard (100) bleibt er bei wenig Last lange zu.
  2. Im Zustand OPEN kostet ein Aufruf fast nichts. Der Fallback antwortet sofort.
  3. Der Fallback ist fachlich: Zahlung „pending“, später erneut versuchen. Ein Fallback, der nur null liefert, versteckt den Fehler.
  4. Der TimeLimiter bricht nach 2 s ab. Ein langsamer Partner wird so zu einem gezählten Fehler.
  5. optional: heisst: Ist der Config Server nicht da, startet der Service trotzdem. Ohne optional: scheitert der Start.

4. Details, die Interviewer fragen

  1. Release Train: Spring Cloud versioniert als Paket (Train), z. B. 2026.0.0 mit Boot 4.2 und 2025.1.x mit Boot 4.0/4.1. Man importiert die BOM spring-cloud-dependencies. Falsche Kombination: Fehler beim Start.
  2. Config-Client: Man bindet den Server mit spring.config.import=configserver:… ein. Der alte Bootstrap Context (bootstrap.yml) ist seit Train 2020.0 standardmässig aus.
  3. Config-Server-Backends: Git (Standard, versioniert), Vault, JDBC, Dateisystem. Dateien heissen {application}-{profile}.yml. Mit {cipher} speichert man verschlüsselte Werte.
  4. Refresh: @RefreshScope-Beans werden nach POST /actuator/refresh neu erzeugt. @ConfigurationProperties werden neu gebunden. Spring Cloud Bus verteilt den Refresh an alle Instanzen.
  5. Gateway-Varianten: Server WebFlux (reaktiv, Netty) und Server Web MVC (Servlet, auch mit Virtual Threads). Dazu ProxyExchange für einzelne Controller-Methoden.
  6. Gateway-Bausteine: Route = Ziel + Predicates + Filter. Predicate: Path, Method, Header, Host, Query, Weight. GatewayFilter pro Route, GlobalFilter für alle Routen.
  7. Rate Limiting im Gateway: RequestRateLimiter mit Redis und Token-Bucket. Antwort bei Überschreitung: 429.
  8. Circuit-Breaker-Zustände: CLOSED, OPEN, HALF_OPEN. Dazu Sonderzustände DISABLED, FORCED_OPEN, METRICS_ONLY.
  9. Resilience4j-Standards: Fehlerrate 50 %, Fenster 100 Aufrufe, mindestens 100 Aufrufe, 60 s offen, 10 Probe-Aufrufe. Langsame Aufrufe zählen erst ab 60 s als langsam.
  10. Weitere Resilience4j-Module: Retry (wiederholen), TimeLimiter (Zeitlimit), Bulkhead (max. gleichzeitige Aufrufe), RateLimiter (max. Aufrufe pro Zeit).
  11. Reihenfolge der Aspekte: Bei Annotations ist die Standard-Reihenfolge Retry außen, dann CircuitBreaker, RateLimiter, TimeLimiter, Bulkhead innen. Retry um einen offenen Breaker wiederholt nur Ablehnungen.
  12. Spring Cloud Circuit Breaker: Eine Abstraktion (CircuitBreakerFactory) über Resilience4j oder Spring Retry. Man kann den Anbieter wechseln, verliert aber Detail-Features.
  13. Framework 7 ohne Spring Cloud: @Retryable und @ConcurrencyLimit sind jetzt im Kern (aktiv mit @EnableResilientMethods). @Retryable wiederholt standardmässig 3-mal mit 1 s Pause. Einen Circuit Breaker hat der Kern nicht.
  14. OpenFeign: HTTP-Client als Interface. Heute bieten Spring HTTP Interfaces (@HttpExchange) dasselbe im Framework.
  15. Service Discovery: Eureka oder Consul registrieren Instanzen. In Kubernetes übernimmt das der Kubernetes-Service mit DNS. Eureka ist dort meist überflüssig.

5. Vergleich

  • Config Server vs Kubernetes ConfigMaps/Secrets: Config Server hat Git-Historie und Refresh für alle Plattformen. In Kubernetes reichen oft ConfigMaps plus Vault mit External Secrets Operator.
  • Spring Cloud Gateway vs Ingress/API-Management: Das Gateway ist Java-Code mit eigener Logik (Token-Tausch, Aggregation). Ein Ingress (NGINX, Envoy) ist schneller und einfacher, aber weniger flexibel.
  • Resilience4j vs Service Mesh: Resilience4j sitzt im Code und kennt Fallbacks. Ein Mesh (Istio, Linkerd) macht Retries und Timeouts ohne Code, aber ohne fachlichen Fallback.
  • Resilience4j vs Spring Framework 7 Resilience: Framework 7 hat Retry und Concurrency Limit. Für Circuit Breaker, TimeLimiter und RateLimiter bleibt Resilience4j.
  • Hystrix: Netflix Hystrix ist seit Jahren im Wartungsmodus und aus Spring Cloud entfernt. Nachfolger ist Resilience4j.

6. In der Produktion

  1. Retry-Sturm: Jede Schicht wiederholt 3-mal. Gateway, Service und Client ergeben 27 Aufrufe pro Klick. Der kranke Service stirbt ganz. Lösung: nur an einer Stelle wiederholen, mit Backoff und Jitter, und einem Circuit Breaker.
  2. Breaker öffnet nie: minimum-number-of-calls ist 100, aber es gibt nur 20 Aufrufe pro Minute. Lösung: Fenster passend zur Last oder zeitbasiertes Fenster.
  3. Kein Timeout: Ein Partner antwortet nach 60 s. Alle Threads warten. Lösung: Timeout an jedem Aufruf (HTTP-Client und TimeLimiter).
  4. Config Server als Single Point of Failure: Er ist down, kein Service startet. Lösung: mehrere Instanzen, optional: oder lokaler Fallback, Fail-Fast nur bewusst.
  5. Refresh mit halbem Zustand: Nach /refresh haben nur einige Instanzen die neue Konfiguration. Lösung: Spring Cloud Bus oder lieber Rolling Restart.
  6. Gateway als Monolith: Immer mehr Fachlogik wandert ins Gateway. Jede Änderung braucht ein Gateway-Deployment. Lösung: im Gateway nur Querschnitt (Routing, Auth, Limits).

7. Diagnose

  • /actuator/gateway/routes: alle Routen mit Predicates und Filtern (Endpoint freigeben).
  • /actuator/health mit Circuit-Breaker-Indicator: Zustand pro Breaker.
  • Metriken: resilience4j_circuitbreaker_state, resilience4j_circuitbreaker_failure_rate, resilience4j_circuitbreaker_calls. Alarm auf Zustand OPEN.
  • Events: circuitBreaker.getEventPublisher().onStateTransition(...) loggt jeden Wechsel.
  • curl http://config:8888/order-service/prod: zeigt, welche Werte der Config Server für Anwendung und Profil liefert.
  • /actuator/env: zeigt die Property-Quelle configserver:... und welche Werte gewinnen.
  • Traces: Zeigen, ob die Zeit im Gateway, im Service oder im Partner liegt.

8. Senior-Punkte

  1. Nicht alles von Spring Cloud braucht man in Kubernetes. Discovery, Load Balancing und Config liefert oft die Plattform. Spring Cloud dort nur für echte Lücken.
  2. Timeouts zuerst, dann Circuit Breaker, dann Retry. Ohne Timeout nützen die anderen wenig.
  3. Retries nur bei idempotenten Aufrufen oder mit Idempotency-Key. Sonst doppelte Zahlungen.
  4. Fallbacks sind Fachentscheidungen. „Zahlung pending“ oder „Empfehlungen leer“ muss das Business akzeptieren.
  5. Breaker-Werte aus Messungen ableiten: echte Latenz (p99) und Fehlerrate, nicht Standardwerte kopieren.
  6. Konfiguration ist Code: versioniert, reviewt, mit Rollback. Laufzeit-Refresh nur, wo er wirklich nötig ist.

10. Fallen

  • „Ein Circuit Breaker ersetzt Timeouts.“ → Falsch. Ohne Timeout zählt ein hängender Aufruf nie als Fehler.
  • „Mehr Retries machen das System stabiler.“ → Falsch. Sie vervielfachen die Last auf einen kranken Service.
  • „bootstrap.yml ist der Weg zum Config Server.“ → Veraltet. Heute spring.config.import.
  • „Spring Cloud ist für jeden Microservice Pflicht.“ → Falsch. Kubernetes deckt viel ab.
  • „Spring Framework 7 hat jetzt einen Circuit Breaker.“ → Falsch. Es hat Retry und Concurrency Limit, keinen Breaker.
  • „Ein Breaker öffnet nach dem ersten Fehler.“ → Falsch. Erst nach minimumNumberOfCalls und über der Fehlerrate.

11. Fragen

Was ist Spring Cloud?

Eine Sammlung von Projekten für verteilte Systeme: Config, Gateway, Circuit Breaker, Discovery, Stream, OpenFeign und mehr. Sie wird als Release Train passend zu einer Boot-Version geliefert.

Was ist ein Release Train?

Eine Gruppe von Spring-Cloud-Projekten mit getesteten Versionen, z. B. 2026.0.0 für Boot 4.2. Man importiert die BOM und setzt keine Einzelversionen.

Wie bindet ein Service den Config Server ein?

Mit spring.config.import=configserver:http://…. Mit optional: davor startet er auch ohne Server.

Wie ändern Sie Konfiguration ohne Neustart?

Beans mit @RefreshScope und POST /actuator/refresh. Für alle Instanzen Spring Cloud Bus. Oft ist ein Rolling Restart einfacher und sicherer.

Wie speichern Sie Secrets im Config Server?

Verschlüsselt mit {cipher} oder besser im Vault-Backend. Klartext-Secrets gehören nie ins Git-Repo.

Was ist eine Route im Gateway?

Eine ID, eine Ziel-URI, Predicates als Bedingungen und Filter für Änderungen. Passt ein Predicate, leitet das Gateway weiter.

Was ist der Unterschied zwischen GatewayFilter und GlobalFilter?

Ein GatewayFilter gilt für eine Route. Ein GlobalFilter gilt für alle Routen, z. B. Logging oder Auth.

Welche Gateway-Varianten gibt es?

Server WebFlux (reaktiv), Server Web MVC (Servlet) und ProxyExchange für einzelne Controller.

Wie macht man Rate Limiting im Gateway?

Mit dem RequestRateLimiter-Filter und Redis als Token-Bucket. Bei Überschreitung antwortet das Gateway 429.

Was ist ein Circuit Breaker?

Ein Schalter um einen entfernten Aufruf. Bei hoher Fehlerrate öffnet er und antwortet sofort mit Fallback. Nach einer Wartezeit testet er mit Probe-Aufrufen.

Welche Zustände hat ein Circuit Breaker?

CLOSED (normal), OPEN (blockiert), HALF_OPEN (testet). Resilience4j hat dazu DISABLED, FORCED_OPEN und METRICS_ONLY.

Welche Standardwerte hat Resilience4j?

50 % Fehlerrate, Fenster 100, mindestens 100 Aufrufe, 60 s offen, 10 Probe-Aufrufe.

Welche Exception kommt bei offenem Breaker?

CallNotPermittedException. Mit Fallback sieht der Aufrufer den Ersatzwert.

Was ist ein Bulkhead?

Eine Grenze für gleichzeitige Aufrufe zu einem Partner. So kann ein langsamer Partner nicht alle Threads belegen.

Retry und Circuit Breaker zusammen, wie?

Retry aussen, Breaker innen. Bei offenem Breaker darf Retry nicht wiederholen, sonst entstehen nur sinnlose Ablehnungen; CallNotPermittedException vom Retry ausschliessen.

Was bringt Spring Framework 7 an Resilience?

@Retryable mit Backoff und @ConcurrencyLimit, aktiviert mit @EnableResilientMethods. Ein Circuit Breaker fehlt.

Brauchen Sie Eureka in Kubernetes?

Meist nicht. Kubernetes-Services mit DNS übernehmen Discovery und Load Balancing.

OpenFeign oder HTTP Interfaces?

HTTP Interfaces (@HttpExchange) sind im Framework enthalten und brauchen kein Spring Cloud. Für neue Projekte meist die bessere Wahl.

Was gehört ins Gateway, was nicht?

Ins Gateway: Routing, Auth, Rate Limits, Header. Nicht ins Gateway: Fachlogik, die einem Service gehört.

Was ist der Unterschied zwischen Resilience4j und einem Service Mesh?

Resilience4j sitzt im Code und kennt fachliche Fallbacks. Ein Mesh arbeitet im Netzwerk, ohne Code-Änderung, aber ohne Fachwissen.

Szenario: Ein langsamer Payment-Service legt den ganzen Shop lahm. Was bauen Sie ein?

Timeout am Client, TimeLimiter, Circuit Breaker mit fachlichem Fallback und einen Bulkhead. Dazu Alarm auf den Breaker-Zustand.

Szenario: Nach einem kurzen Ausfall eines Services bricht ein zweiter zusammen, weil die Last plötzlich explodiert. Warum?

Retry-Sturm: Mehrere Schichten wiederholen gleichzeitig. Lösung: Retry nur an einer Stelle, mit exponentiellem Backoff und Jitter, plus Circuit Breaker.

Szenario: Das Team will Spring Cloud Config, Eureka und Gateway auf AKS einführen. Was raten Sie?

Erst prüfen, was Kubernetes schon liefert: Services statt Eureka, ConfigMaps und Vault statt Config Server, Ingress statt Gateway. Spring Cloud nur dort, wo Logik im Code nötig ist.
