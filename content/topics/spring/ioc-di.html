IoC und Dependency Injection

Kern: Inversion of Control (IoC) ist ein Prinzip: Nicht dein Code erzeugt seine Abhängigkeiten, sondern ein Container. Dependency Injection (DI) ist die Technik dafür: Der Container übergibt die Abhängigkeiten über Konstruktor, Setter oder Feld. In Spring ist dieser Container das ApplicationContext.

1. Wo sitzt der IoC-Container?

  1. Konfigurationsquellen: Der Component-Scan findet Klassen mit @Component, @Service, @Repository, @Controller. @Bean-Methoden liefern Beans aus Fremd-Bibliotheken. Spring Boot ergänzt Beans per Auto-Configuration.
  2. BeanDefinition: Aus jeder Quelle entsteht ein Bauplan: Klasse, Scope, Abhängigkeiten, Init- und Destroy-Methode. Noch existiert kein Objekt.
  3. BeanFactory: Der Kern des Containers. Er erzeugt Beans aus den BeanDefinitions und injiziert ihre Abhängigkeiten. Beispiel: getBean(OrderService.class).
  4. ApplicationContext: Er erweitert die BeanFactory um Environment, Events, Internationalisierung und Ressourcen. Er erzeugt alle Singletons schon beim Start (eager).
  5. Beans: Die fertigen Objekte. OrderService bekommt PaymentClient injiziert und ruft nie new PaymentClient() auf.

2. Die Reise einer Abhängigkeit (die Geschichte zum Merken)

  1. Injection Point: OrderService hat einen Konstruktor mit dem Parameter PaymentClient client. Das ist der Injection Point, also die Stelle, die eine Abhängigkeit braucht.
  2. Suche nach Typ: Der Container sucht alle Beans, die zu PaymentClient passen. @Autowired arbeitet also nach Typ, nicht nach Name.
  3. Kein Kandidat: Spring wirft NoSuchBeanDefinitionException, und der Start bricht ab. Ausnahme: Der Parameter ist Optional<PaymentClient>, ObjectProvider<PaymentClient> oder @Autowired(required = false).
  4. Mehrere Kandidaten: Es gibt twintClient und cardClient. Zuerst grenzt @Qualifier ein. Dann gewinnt eine @Primary-Bean. @Fallback-Beans (seit 6.2) fallen weg, wenn eine normale Bean übrig bleibt. Zuletzt vergleicht Spring den Parameternamen mit den Bean-Namen.
  5. Immer noch unklar: Spring wirft NoUniqueBeanDefinitionException.
  6. Genau ein Kandidat: Existiert die Bean noch nicht, erzeugt Spring sie zuerst. So entsteht der ganze Graph von unten nach oben. Erst dann ruft Spring den Konstruktor von OrderService auf.

3. Beispiel: drei Arten zu injizieren und ein Konflikt

public interface PaymentClient { String pay(int rappen); }

@Component class TwintClient implements PaymentClient { ... }
@Component class CardClient  implements PaymentClient { ... }

// 1) Konstruktor-Injection (empfohlen): final, kein @Autowired nötig
@Service
class OrderService {
  private final PaymentClient client;
  OrderService(@Qualifier("twintClient") PaymentClient client) {
    this.client = client;
  }
}

// 2) Setter-Injection: für optionale Abhängigkeiten
@Autowired void setAudit(AuditLog audit) { this.audit = audit; }

// 3) Field-Injection: funktioniert, aber nicht empfohlen
@Autowired private PaymentClient client;   // ohne @Qualifier!
***************************
APPLICATION FAILED TO START
***************************
Description:
Field client in ch.demo.ReportService required a single bean, but 2 were found:
	- cardClient: defined in file [.../CardClient.class]
	- twintClient: defined in file [.../TwintClient.class]

Action:
Consider marking one of the beans as @Primary, updating the consumer to accept
multiple beans, or using @Qualifier to identify the bean that should be consumed

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spring Boot zeigt Konflikte über einen FailureAnalyzer in dieser Form; der genaue Text kann je nach Version leicht abweichen.

  1. OrderService nutzt Konstruktor-Injection. Hat eine Klasse genau einen Konstruktor, braucht er kein @Autowired.
  2. @Qualifier("twintClient") wählt die Bean nach Name. Der Standard-Name einer @Component ist der Klassenname mit kleinem Anfangsbuchstaben.
  3. Das Feld in ReportService hat zwei Kandidaten und keinen Hinweis. Darum startet die Anwendung nicht. Das ist gut: Der Fehler kommt beim Start, nicht beim ersten Request.
  4. Hiesse das Feld twintClient, würde Spring diese Bean über den Namen wählen. Für Parameter braucht das seit 6.1 das Compiler-Flag -parameters. Spring Boot setzt es im Build-Plugin.

4. Details, die Interviewer fragen

  1. IoC vs DI: IoC ist das Prinzip (der Container steuert die Erzeugung). DI ist eine Umsetzung davon. Eine andere Umsetzung ist der Service Locator, also context.getBean(...) im eigenen Code. Den vermeidet man.
  2. Konstruktor-Injection: Felder können final sein. Das Objekt ist nach dem Konstruktor vollständig. Tests brauchen nur new OrderService(mock). Das Spring-Team empfiehlt sie für Pflicht-Abhängigkeiten.
  3. Setter-Injection: für optionale Abhängigkeiten mit sinnvollem Standardwert. Nachteil: Das Objekt ist kurz unvollständig.
  4. Field-Injection: Spring setzt das Feld per Reflection. Nachteile: kein final, versteckte Abhängigkeiten, Tests brauchen Spring oder Reflection, new liefert ein Objekt mit null-Feldern.
  5. Viele Konstruktor-Parameter: Sie sind ein Code Smell, also ein Warnsignal: Die Klasse hat zu viele Aufgaben. Field-Injection versteckt das nur.
  6. Mehrere Konstruktoren: Dann markiert man den gewünschten mit @Autowired. Sonst nimmt Spring den Standard-Konstruktor, falls vorhanden.
  7. @Qualifier: Er grenzt die Kandidaten nach Name oder eigenem Qualifier ein. Eigene Qualifier-Annotationen (z. B. @Twint) sind typsicherer als Strings.
  8. @Primary: Diese Bean gewinnt, wenn mehrere passen. Gut für einen Standard, z. B. die Haupt-DataSource.
  9. @Fallback (seit 6.2): Das Gegenteil von @Primary. Die Bean wird nur genommen, wenn keine normale Bean da ist. Gut für Standard-Beans in Bibliotheken.
  10. Alle Kandidaten injizieren: List<PaymentClient> oder Map<String, PaymentClient> liefert alle Beans. Die Map hat die Bean-Namen als Schlüssel. Das ist die Basis für das Strategy Pattern.
  11. Zirkuläre Abhängigkeit: A braucht B, B braucht A. Mit Konstruktor-Injection ist das unlösbar. Spring wirft BeanCurrentlyInCreationException.
  12. Wie Spring Zyklen mit Feldern löst: Spring hält drei Caches: singletonObjects (fertig), earlySingletonObjects (früh, halb fertig), singletonFactories (Fabrik für eine frühe Referenz). B bekommt eine frühe, noch nicht initialisierte Referenz auf A.
  13. Spring Boot und Zyklen: Spring Boot verbietet Zyklen standardmässig (spring.main.allow-circular-references=false). Auch Feld-Zyklen brechen dann den Start ab.
  14. Zyklus auflösen: Besser ist ein neues Design: gemeinsame Logik in eine dritte Bean, oder ein Event statt Rückruf. Notlösungen: @Lazy am Injection Point (Spring injiziert einen Proxy) oder ObjectProvider.
  15. BeanFactory vs ApplicationContext: Die BeanFactory erzeugt Beans erst auf Anfrage. Das ApplicationContext erzeugt Singletons beim Start, registriert BeanPostProcessors automatisch und bietet Events und Environment.
  16. Javax vs Jakarta: Spring Framework 7 unterstützt javax.inject und javax.annotation nicht mehr. Man nutzt jakarta.inject.Inject oder @Autowired.

5. Vergleich

  • Konstruktor-Injection: Pflicht-Abhängigkeiten, final, einfach testbar, Zyklen fallen sofort auf. Standard-Wahl.
  • Setter-Injection: optionale Abhängigkeiten, nachträglich änderbar. Objekt kurz unvollständig.
  • Field-Injection: kurz zu schreiben, aber schlecht testbar und versteckt Abhängigkeiten. Nur noch in Tests üblich.
  • @Qualifier: wählt bewusst an jedem Injection Point.
  • @Primary: legt einen globalen Standard fest.
  • @Fallback: legt eine Notlösung fest, die jede normale Bean verdrängt.
  • ObjectProvider: holt die Bean erst bei Bedarf, optional, lazy, auch für Prototypes.
  • Spring DI vs Jakarta CDI: ähnliche Idee. CDI ist der Jakarta-EE-Standard (z. B. Quarkus), Spring ist ein eigenes Framework.

6. In der Produktion

  1. Start bricht ab mit NoUniqueBeanDefinitionException: Eine neue Bibliothek bringt eine zweite Bean gleichen Typs, z. B. einen zweiten ObjectMapper. Lösung: @Qualifier oder @Primary an der eigenen Bean.
  2. Start bricht ab wegen Zyklus: Nach einem Upgrade auf aktuelles Spring Boot sind alte Feld-Zyklen verboten. Lösung: Zyklus im Design auflösen. Das Property auf true setzen ist nur eine Übergangslösung.
  3. NullPointerException im Test: Ein Test erzeugt eine Klasse mit Field-Injection per new. Die Felder bleiben null. Lösung: Konstruktor-Injection.
  4. Falsche Bean injiziert: Zwei Beans gleichen Typs, und der Parametername passt zufällig zu der falschen. Lösung: explizit @Qualifier setzen.
  5. Langsamer Start: Viele Beans erledigen teure Arbeit im Konstruktor (Netzwerk, Caches laden). Lösung: Arbeit verschieben, Startup messen, Lazy Initialization gezielt nutzen.

7. Diagnose: Werkzeuge und Befehle

  • FailureAnalyzer-Meldung beim Start: Sie nennt Bean, Injection Point und Kandidaten. Immer zuerst den Abschnitt „Description“ lesen.
  • /actuator/beans: alle Beans mit Typ, Scope und Abhängigkeiten.
  • /actuator/conditions oder --debug beim Start: zeigt, warum eine Auto-Configuration aktiv war oder nicht.
  • context.getBeanNamesForType(PaymentClient.class): zeigt alle Kandidaten eines Typs.
  • /actuator/startup mit BufferingApplicationStartup: misst, wie lange jede Bean beim Start braucht.
  • IntelliJ Spring-Plugin: zeigt Injection Points und markiert mehrdeutige Beans schon im Editor.

8. Senior-Punkte

  1. Konstruktor-Injection ist eine Design-Entscheidung, keine Stilfrage. Sie macht Abhängigkeiten sichtbar und die Klasse ohne Spring testbar.
  2. Zyklen sind ein Design-Fehler. Sie zeigen, dass zwei Klassen zu eng gekoppelt sind. @Lazy versteckt das Problem nur.
  3. Fail fast beim Start ist ein Vorteil von Eager-Singletons. Lazy Initialization verschiebt Fehler in den ersten Request.
  4. Bibliotheken sollten überschreibbare Beans liefern: @ConditionalOnMissingBean oder @Fallback. So kann der Nutzer eine eigene Bean setzen.
  5. Kein Service Locator im Business-Code. getBean() gehört nur in Infrastruktur-Code.
  6. DI ist kein Selbstzweck. Werte-Objekte, DTOs und Entities sind keine Beans. Sie entstehen mit new.

10. Fallen

  • „@Autowired injiziert nach Name.“ → Falsch. Nach Typ. Der Name ist nur ein letzter Fallback bei mehreren Kandidaten.
  • „Konstruktor-Injection braucht @Autowired.“ → Falsch. Bei genau einem Konstruktor ist es optional.
  • „Spring löst zirkuläre Abhängigkeiten immer.“ → Falsch. Mit Konstruktoren nie. Spring Boot verbietet auch Feld-Zyklen standardmässig.
  • „Field-Injection ist gleich gut, nur kürzer.“ → Falsch. Kein final, versteckte Abhängigkeiten, schlecht testbar.
  • „Ein Spring-Singleton gibt es einmal pro JVM.“ → Falsch. Einmal pro Container und Bean-Definition.
  • „@Primary und @Qualifier zusammen: @Primary gewinnt.“ → Falsch. Ein @Qualifier am Injection Point grenzt zuerst ein.

11. Fragen

Was ist Inversion of Control?

Ein Prinzip: Der Container erzeugt und verbindet die Objekte, nicht der Code selbst. Der Code sagt nur, was er braucht.

Was ist der Unterschied zwischen IoC und DI?

IoC ist das Prinzip. DI ist eine Technik, um es umzusetzen: Abhängigkeiten werden von aussen übergeben.

Was ist ein Spring Bean?

Ein Objekt, das der Spring-Container erzeugt, verbindet und verwaltet. Es entsteht aus einer BeanDefinition.

Was ist eine BeanDefinition?

Der Bauplan einer Bean: Klasse, Scope, Abhängigkeiten, Init- und Destroy-Methode, lazy oder nicht. Spring liest sie vor dem Erzeugen der Beans.

BeanFactory vs ApplicationContext?

Die BeanFactory ist der Kern und erzeugt Beans auf Anfrage. Das ApplicationContext erzeugt Singletons beim Start und bietet Events, Environment, Ressourcen und automatische BeanPostProcessors.

Welche Arten von Injection gibt es?

Konstruktor, Setter (oder Methode) und Feld. Empfohlen ist Konstruktor-Injection für Pflicht-Abhängigkeiten.

Warum Konstruktor-Injection statt Field-Injection?

Felder können final sein, das Objekt ist sofort vollständig, und Tests brauchen kein Spring. Abhängigkeiten sind im Konstruktor sichtbar.

Wann nutzen Sie Setter-Injection?

Für optionale Abhängigkeiten mit sinnvollem Standardwert. Oder wenn eine Bean später neu konfiguriert werden soll.

Braucht Konstruktor-Injection @Autowired?

Nein, nicht bei genau einem Konstruktor. Bei mehreren markiert man den gewünschten mit @Autowired.

Wie löst Spring mehrere Kandidaten auf?

Erst @Qualifier, dann @Primary bzw. @Fallback, zuletzt Parametername gleich Bean-Name. Bleibt es unklar, kommt NoUniqueBeanDefinitionException.

@Primary vs @Qualifier?

@Primary ist ein globaler Standard an der Bean. @Qualifier wählt am Injection Point und hat Vorrang.

Was ist @Fallback?

Seit Spring 6.2. Die Bean wird nur genommen, wenn keine normale Bean des Typs übrig ist. Gut für Standard-Beans in Bibliotheken.

Wie injizieren Sie alle Implementierungen eines Interfaces?

Mit List<T> oder Map<String, T>. Die Map hat die Bean-Namen als Schlüssel, gut für das Strategy Pattern.

Wie injizieren Sie eine optionale Abhängigkeit?

Mit Optional<T>, ObjectProvider<T>.getIfAvailable() oder @Autowired(required = false).

Was ist eine zirkuläre Abhängigkeit?

A braucht B und B braucht A. Mit Konstruktoren kann Spring keinen von beiden zuerst bauen und wirft BeanCurrentlyInCreationException.

Wie löst Spring Feld-Zyklen intern?

Mit drei Caches. A wird erzeugt, eine Fabrik für eine frühe Referenz landet in singletonFactories. B bekommt diese halb fertige Referenz auf A.

Erlaubt Spring Boot zirkuläre Abhängigkeiten?

Nein, standardmässig nicht: spring.main.allow-circular-references ist false. Der Start bricht mit einer Zyklus-Meldung ab.

Wie brechen Sie einen Zyklus auf?

Am besten im Design: gemeinsame Logik in eine dritte Bean oder ein Event statt Rückruf. Notlösung: @Lazy am Injection Point oder ObjectProvider.

Was macht @Lazy an einem Injection Point?

Spring injiziert einen Proxy. Die echte Bean wird erst beim ersten Methodenaufruf geholt.

Warum ist Service Locator (getBean) schlecht?

Der Code hängt am Container, und Abhängigkeiten sind versteckt. Tests werden schwer.

Was ist der Standard-Name einer @Component-Bean?

Der einfache Klassenname mit kleinem Anfangsbuchstaben, z. B. twintClient. Man kann ihn mit @Component("name") setzen.

Was hat sich bei Spring 7 bei Annotationen geändert?

javax.inject und javax.annotation werden nicht mehr unterstützt. Man nutzt die jakarta-Varianten.

Sollten Entities oder DTOs Beans sein?

Nein. Sie tragen Daten und entstehen mit new. Beans sind Services, Repositories, Clients, Konfiguration.

Szenario: Nach dem Hinzufügen einer Bibliothek startet die App nicht mehr: „required a single bean, but 2 were found“. Was tun Sie?

Die Meldung nennt beide Beans. Ich markiere meine eigene mit @Primary oder setze @Qualifier am Injection Point. Danach prüfe ich mit /actuator/beans, wer welche Bean bekommt.

Szenario: Nach dem Upgrade auf aktuelles Spring Boot meldet der Start einen Zyklus zwischen zwei Services. Was tun Sie?

Ich löse den Zyklus im Design: gemeinsame Logik extrahieren oder Events nutzen. allow-circular-references=true nur kurz als Übergang, mit Ticket.

Szenario: Ein Unit-Test wirft NullPointerException im Service, obwohl die App läuft. Woran liegt es?

Wahrscheinlich Field-Injection: Der Test erzeugt den Service mit new, die Felder bleiben null. Lösung: auf Konstruktor-Injection umstellen und Mocks übergeben.
