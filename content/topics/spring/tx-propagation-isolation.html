Propagation und Isolation in Spring

Kern: Propagation ist die Regel, was eine @Transactional-Methode tut, wenn schon eine Transaktion läuft. Isolation ist die Regel, wie viel eine Transaktion von parallelen Transaktionen sieht. Spring setzt Propagation selbst um, Isolation gibt es nur an die Datenbank weiter.

Antwort-Muster

Frage: Was ist der Unterschied zwischen REQUIRED und REQUIRES_NEW?

  1. Mechanismus: REQUIRED macht bei einer laufenden Transaktion mit. REQUIRES_NEW pausiert sie und startet eine neue auf einer zweiten Connection.
  2. Zahl: Es gibt 7 Propagation-Arten, REQUIRED ist der Standard. REQUIRES_NEW braucht pro Thread 2 Connections.
  3. Trade-off: REQUIRES_NEW committet unabhängig und bleibt bei einem Fehler aussen. Dafür kann es den Connection Pool blockieren.
  4. Produktion: Bei REQUIRED rollt ein innerer Fehler die ganze Transaktion zurück. Der äussere Commit wirft dann UnexpectedRollbackException.

1. Die Reise eines verschachtelten Aufrufs

  1. Start: placeOrder() hat REQUIRED. Es läuft keine Transaktion. Der Manager startet die physische Transaktion A.
  2. Mitmachen: reserveStock() hat auch REQUIRED. Es gibt schon A. Die Methode bekommt nur einen logischen Scope in A.
  3. Fehler innen: reserveStock() wirft eine RuntimeException. Der Interceptor kann A nicht allein zurückrollen. Er setzt A auf rollback-only.
  4. Fangen aussen: placeOrder() fängt die Exception und macht weiter. Die Markierung bleibt aber.
  5. Pausieren: writeAudit() hat REQUIRES_NEW. Der Manager suspendiert A und öffnet Transaktion B auf einer zweiten Connection.
  6. Unabhängiger Commit: B committet sofort. Danach setzt der Manager A fort.
  7. Ende: placeOrder() endet normal, der Interceptor ruft Commit. A ist rollback-only. Der Manager rollt zurück und wirft UnexpectedRollbackException.
  8. Ergebnis: Die Bestellung fehlt, der Audit-Eintrag aus B bleibt.

2. Aufbau

  1. AOP-Proxy: Der Aufruf geht durch einen Proxy, nicht direkt in die Methode. Darum wirkt @Transactional nur bei Aufrufen von aussen.
  2. TransactionInterceptor: Er liest die Attribute der Annotation, z. B. propagation = REQUIRES_NEW.
  3. PlatformTransactionManager: Er entscheidet: neue Transaktion, mitmachen, pausieren oder Fehler. Beispiel: JpaTransactionManager mit Spring Boot und JPA.
  4. TransactionSynchronizationManager: Er hält die aktuelle Transaktion im ThreadLocal. Darum gilt eine Transaktion nur im eigenen Thread.
  5. JDBC Connection: Der Manager setzt hier Auto-Commit aus und eventuell die Isolation.
  6. Datenbank: Sie entscheidet, was eine Isolationsstufe wirklich bedeutet. Spring prüft das nicht.

3. Details, die Interviewer fragen

Die 7 Propagation-Arten:

  1. REQUIRED (Standard): Die Methode macht mit, sonst startet sie neu. Ein Beispiel ist eine normale Service-Methode.
  2. REQUIRES_NEW: Sie startet immer eine neue physische Transaktion. Die laufende wird pausiert. Ein Beispiel ist ein Audit-Log, das auch bei Fehler bleiben soll.
  3. NESTED: Im laufenden Fall setzt sie einen Savepoint in derselben physischen Transaktion. Ohne laufende Transaktion verhält sie sich wie REQUIRED. Ein Beispiel ist ein Teilschritt, der scheitern darf.
  4. MANDATORY: Es muss eine Transaktion laufen. Sonst kommt IllegalTransactionStateException. Ein Beispiel ist eine Repository-Hilfsmethode, die nie allein laufen darf.
  5. SUPPORTS: Die Methode macht mit, wenn eine läuft. Sonst läuft sie ohne Transaktion. Ein Beispiel ist eine Lese-Methode, die beides verträgt.
  6. NOT_SUPPORTED: Sie läuft immer ohne Transaktion. Eine laufende wird pausiert. Ein Beispiel ist ein langer externer HTTP-Aufruf.
  7. NEVER: Läuft eine Transaktion, kommt IllegalTransactionStateException. Ein Beispiel ist Code, der nie in einer Transaktion laufen darf.

Weitere Regeln:

  1. Entscheidung im Manager: getTransaction im AbstractPlatformTransactionManager prüft zuerst, ob schon eine Transaktion läuft. Wenn ja, entscheidet handleExistingTransaction nach der Propagation. Wenn nein, wirft MANDATORY einen Fehler. REQUIRED, REQUIRES_NEW und NESTED starten neu.
  2. Leere Transaktion: SUPPORTS, NOT_SUPPORTED und NEVER ohne laufende Transaktion starten keine echte Transaktion. Spring erzeugt nur eine leere Transaktion, eventuell mit Synchronisation. Eine eigene Isolation wird dann ignoriert und im Log gewarnt.
  3. Physisch vs logisch: Eine physische Transaktion ist die echte DB-Transaktion. Jede @Transactional-Methode ist ein logischer Scope. Bei REQUIRED teilen sich viele Scopes eine physische Transaktion.
  4. Attribute beim Mitmachen: Eine teilnehmende Methode übernimmt Isolation, Timeout und readOnly der äusseren. Ihre eigenen Werte ignoriert Spring still.
  5. validateExistingTransaction: Dieses Flag am Transaction Manager lehnt abweichende Isolation und readOnly-Konflikte ab. Der Standard ist der stille Modus.
  6. REQUIRES_NEW braucht eine zweite Connection: Die äussere Connection bleibt belegt. Die Doku warnt vor Pool-Erschöpfung und Deadlock. Die Regel lautet, der Pool ist grösser als Threads plus 1.
  7. NESTED und JPA: NESTED nutzt JDBC-Savepoints. DataSourceTransactionManager kann es direkt. JpaTransactionManager hat nestedTransactionAllowed = false als Standard. Auch mit true gilt der Savepoint nur für JDBC, nicht für den EntityManager-Cache.
  8. Rollback-Regeln: Standard ist Rollback bei RuntimeException und Error. Checked Exceptions committen. Man ändert das mit rollbackFor und noRollbackFor. Seit 6.2 geht es global mit @EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS).
  9. UnexpectedRollbackException: Sie kommt, wenn innen rollback-only gesetzt wurde und aussen Commit gerufen wird. Sie zeigt, dass der Aufrufer an Commit glaubt, aber es Rollback gab.
  10. globalRollbackOnParticipationFailure: Dieses Flag (Standard true) markiert die ganze Transaktion bei einem Fehler in einem Teilnehmer. Ausschalten ist selten richtig.

Isolation und die Datenbank:

  1. DEFAULT: Spring setzt nichts. Es gilt die Einstellung der Datenbank.
  2. READ_UNCOMMITTED: Sie erlaubt Dirty Reads, also das Lesen nicht committeter Daten. In PostgreSQL verhält sie sich wie READ COMMITTED.
  3. READ_COMMITTED: Es zählen nur committete Daten. Zwei Lesungen können verschiedene Werte liefern, das ist ein Non-Repeatable Read. Es ist der Standard in PostgreSQL und SQL Server.
  4. REPEATABLE_READ: Gelesene Zeilen bleiben gleich. Es ist der Standard in MySQL InnoDB. PostgreSQL verhindert hier auch Phantom Reads, also neue Zeilen in einer Abfrage.
  5. SERIALIZABLE: Das Ergebnis ist wie bei Ausführung nacheinander. PostgreSQL bricht Konflikte mit SQLSTATE 40001 ab. Die Anwendung muss die ganze Transaktion wiederholen.
  6. SQL Server: READ COMMITTED nutzt Locks, ausser READ_COMMITTED_SNAPSHOT ist an. In Azure SQL Database ist RCSI standardmässig an.
  7. Mechanik: Bei einer neuen Transaktion ruft der Manager Connection.setTransactionIsolation(...). Danach setzt er den Wert zurück.
  8. JPA: Standard-JPA kennt keine eigene Isolation pro Transaktion. HibernateJpaDialect unterstützt sie, solange prepareConnection an ist (Standard).

4. Fallen

  • „Die innere Methode hat REQUIRED und eigene Isolation, also gilt die.“ → Falsch. Beim Mitmachen gilt die Isolation der äusseren Transaktion.
  • „Ich fange die Exception, dann committet alles.“ → Falsch. Die Transaktion ist schon rollback-only. Es kommt UnexpectedRollbackException.
  • „NESTED ist dasselbe wie REQUIRES_NEW.“ → Falsch. NESTED ist ein Savepoint in derselben Transaktion. Es committet erst mit der äusseren.
  • „NESTED funktioniert mit JPA einfach so.“ → Falsch. JpaTransactionManager erlaubt es standardmässig nicht. Und der Savepoint deckt nicht den EntityManager-Cache ab.
  • „READ_UNCOMMITTED macht PostgreSQL schneller.“ → Falsch. PostgreSQL behandelt es wie READ COMMITTED.
  • „Bei jeder Exception gibt es Rollback.“ → Falsch. Standard nur bei RuntimeException und Error.
  • „REQUIRES_NEW in derselben Klasse aufrufen reicht.“ → Falsch. Self-Invocation geht am Proxy vorbei. Die Annotation wirkt nicht.

5. Selbsttest

Warum?

Was passiert mit der Isolation einer Methode, die nur mitmacht?

Sie wird still ignoriert. Mit validateExistingTransaction = true wirft der Manager stattdessen einen Fehler.

Warum kann REQUIRES_NEW den Connection Pool blockieren?

Jeder Thread hält die äussere Connection und braucht eine zweite. Ist der Pool voll, warten alle aufeinander.

Warum wirkt REQUIRES_NEW nicht, wenn ich die Methode in derselben Klasse aufrufe?

Der Aufruf geht über this, nicht über den Proxy. Lösung: Methode in einen anderen Bean oder TransactionTemplate nutzen.

Wie innen?

Was ist Transaction Propagation?

Die Regel, was eine transaktionale Methode tut, wenn schon eine Transaktion läuft: mitmachen, neu starten, pausieren oder Fehler werfen.

Was macht REQUIRES_NEW?

Es pausiert die laufende Transaktion und startet eine neue physische Transaktion. Sie committet oder rollt unabhängig zurück.

Was macht NESTED?

Es setzt einen Savepoint in der laufenden Transaktion. Bei Fehler rollt nur der Teil bis zum Savepoint zurück. Ohne laufende Transaktion verhält es sich wie REQUIRED.

Welcher Transaction Manager unterstützt NESTED?

Out of the box der JDBC DataSourceTransactionManager. JpaTransactionManager nur mit nestedTransactionAllowed = true, und dann nur für JDBC-Zugriffe.

Was ist der Unterschied zwischen physischer und logischer Transaktion?

Die physische ist die echte DB-Transaktion. Jede @Transactional-Methode ist ein logischer Scope. Bei REQUIRED teilen sich mehrere Scopes eine physische Transaktion.

Wann kommt UnexpectedRollbackException?

Ein innerer Teilnehmer markiert die Transaktion als rollback-only, der äussere ruft trotzdem Commit. Spring rollt zurück und meldet das mit dieser Exception.

Wie setzt Spring die Isolation technisch?

Beim Start einer neuen Transaktion ruft der Manager Connection.setTransactionIsolation. Danach setzt er den alten Wert zurück.

Unterstützt JPA eigene Isolation pro Transaktion?

Standard-JPA nicht. Spring macht es mit HibernateJpaDialect möglich, solange prepareConnection an ist.

Wie entscheidet der Transaction Manager bei Beginn einer Transaktion?

getTransaction prüft, ob schon eine Transaktion läuft. Wenn ja, entscheidet handleExistingTransaction nach der Propagation. Wenn nein, wirft MANDATORY einen Fehler, und REQUIRED, REQUIRES_NEW und NESTED starten neu.

Zahlen

Welche Isolationsstufen kennt Spring?

DEFAULT, READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE. DEFAULT übernimmt die Einstellung der Datenbank.

Welche Isolation ist Standard in PostgreSQL, MySQL und SQL Server?

PostgreSQL: READ COMMITTED. MySQL InnoDB: REPEATABLE READ. SQL Server: READ COMMITTED, in Azure SQL Database mit RCSI.

Was ist an REPEATABLE READ in PostgreSQL besonders?

Es verhindert auch Phantom Reads. Dafür bricht es Konflikte mit einem Serialisierungsfehler ab.

Was muss die Anwendung bei SQLSTATE 40001 tun?

Die ganze Transaktion abbrechen und wiederholen. Das Retry muss ausserhalb der Transaktion liegen.

Wie viele Propagation-Arten gibt es?

Sieben. REQUIRED, REQUIRES_NEW, NESTED, MANDATORY, SUPPORTS, NOT_SUPPORTED und NEVER.

Vergleich

Was ist der Unterschied zwischen MANDATORY und NEVER?

MANDATORY wirft einen Fehler ohne laufende Transaktion. NEVER wirft einen Fehler mit laufender Transaktion.

SUPPORTS vs NOT_SUPPORTED?

SUPPORTS macht mit, wenn eine Transaktion läuft, sonst läuft es ohne. NOT_SUPPORTED läuft immer ohne und pausiert eine laufende.

Was sind Dirty Read, Non-Repeatable Read und Phantom Read?

Dirty Read: nicht committete Daten lesen. Non-Repeatable Read: gleiche Zeile, anderer Wert. Phantom Read: gleiche Abfrage, neue Zeilen.

Reicht SERIALIZABLE statt Locking?

Manchmal, aber mit vielen Abbrüchen. Oft besser: READ_COMMITTED plus SELECT FOR UPDATE oder optimistisches Locking mit @Version.

Produktion

Wie vermeiden Sie UnexpectedRollbackException?

Exception nicht fangen und weitermachen, fachliche Fehler ohne Rollback-Regel, oder den inneren Schritt mit NESTED oder REQUIRES_NEW trennen.

Szenario: Im Log steht „Transaction silently rolled back because it has been marked as rollback-only“. Was prüfen Sie?

Welcher innere Teilnehmer eine Exception warf, die aussen gefangen wurde. Mit DEBUG-Log des Transaction Managers sieht man „Participating transaction failed“. Dann Exception-Handling oder Propagation ändern.

Szenario: Unter Last hängen Requests, der Connection Pool ist voll, aber die DB ist ruhig. Woran denken Sie?

An REQUIRES_NEW in einer äusseren Transaktion: Threads warten auf ihre zweite Connection. Pool-Metriken und Thread Dump prüfen. Lösung: Pool grösser, REQUIRES_NEW entfernen oder nach aussen verlegen.

Szenario: Ein Audit-Eintrag soll auch bei Fehler der Bestellung gespeichert werden. Wie bauen Sie das?

Audit-Service in einem eigenen Bean mit REQUIRES_NEW. Dabei Pool-Grösse prüfen. Alternative: Audit nach dem Rollback in einem Listener schreiben.

Design

Welche Propagation ist der Standard?

REQUIRED. Läuft eine Transaktion, macht die Methode mit. Sonst startet sie eine neue.

Bei welchen Exceptions rollt Spring zurück?

Standard: RuntimeException und Error. Checked Exceptions committen. Änderbar mit rollbackFor, noRollbackFor oder seit 6.2 global mit rollbackOn.

Wann wählen Sie REQUIRED, REQUIRES_NEW oder NESTED?

REQUIRED ist der Standard für normale Service-Methoden. REQUIRES_NEW nehme ich nur für echte Unabhängigkeit wie ein Audit-Log. NESTED passt für einen Teilschritt, der scheitern darf, mit JDBC-Savepoint.

Mehr

Gerüst

  • Warum? Mehrere Service-Methoden rufen sich auf, und jede hat @Transactional. Propagation sagt, ob sie eine Transaktion teilen.
  • Wie innen? Der Manager entscheidet: neu starten, mitmachen, pausieren oder Fehler. Isolation setzt er mit Connection.setTransactionIsolation.
  • Zahlen Es gibt 7 Propagation-Arten und 5 Isolationsstufen. Standard ist REQUIRED und DEFAULT. Postgres-Fehler bei Konflikt: 40001.
  • Vergleich REQUIRES_NEW committet unabhängig, NESTED ist ein Savepoint. Spring reicht Isolation nur weiter, die Bedeutung kommt von der Datenbank.
  • Produktion Eine gefangene Exception in einer inneren Methode führt zu UnexpectedRollbackException. REQUIRES_NEW kann den Pool blockieren.
  • Design Die Transaktionsgrenze liegt im Service. Isolation setzt man nur so hoch wie nötig, und Retry liegt ausserhalb der Transaktion.

Beispiel: UnexpectedRollbackException erzeugen

@Service
class OrderService {
  private final StockService stock; private final AuditService audit;
  // Konstruktor weggelassen

  @Transactional                                   // REQUIRED
  public void placeOrder(Order o) {
    orderRepo.save(o);
    try { stock.reserve(o); }                      // anderer Bean → Proxy
    catch (OutOfStockException e) { log.warn("kein Lager"); }
    audit.write("order " + o.id());
  }
}

@Service
class StockService {
  @Transactional                                   // REQUIRED, macht mit
  public void reserve(Order o) { throw new OutOfStockException(); } // RuntimeException
}

@Service
class AuditService {
  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void write(String text) { auditRepo.save(new AuditEntry(text)); }
}

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Log-Zeilen gekürzt; der genaue Wortlaut kann je nach Version leicht abweichen.

  1. placeOrder startet die Transaktion. ISOLATION_DEFAULT heisst: Die Datenbank-Einstellung gilt.
  2. reserve macht mit („Participating“). Die Exception markiert die ganze Transaktion als rollback-only.
  3. write pausiert die äussere Transaktion („Suspending“) und committet unabhängig.
  4. Der äussere Commit wird zum Rollback. Spring meldet das laut mit UnexpectedRollbackException.
  5. Lösungen: reserve wirft eine fachliche Exception ohne Rollback (noRollbackFor), prüft vorher ohne Exception, oder läuft bewusst mit REQUIRES_NEW bzw. NESTED.

Vergleich

  • REQUIRED vs REQUIRES_NEW: eine gemeinsame Transaktion vs zwei unabhängige mit zwei Connections.
  • REQUIRES_NEW vs NESTED: REQUIRES_NEW committet unabhängig. NESTED ist ein Savepoint: rollt nur den Teil zurück, committet aber erst mit der äusseren.
  • SUPPORTS vs NOT_SUPPORTED: SUPPORTS macht mit, wenn möglich. NOT_SUPPORTED pausiert eine laufende Transaktion immer.
  • MANDATORY vs NEVER: Fehler ohne Transaktion vs Fehler mit Transaktion.
  • Spring Isolation vs DB-Isolation: Spring reicht nur den Wert weiter. Die Bedeutung kommt von der Datenbank.
  • Isolation vs Locking: Isolation regelt Lesen. Für „lesen und dann ändern“ braucht man oft SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE)) oder @Version (optimistisch).
  • @Transactional vs TransactionTemplate: deklarativ über Proxy vs programmatisch im Code. TransactionTemplate kennt die gleichen Propagation-Werte und hat kein Self-Invocation-Problem.

In der Produktion

  1. UnexpectedRollbackException im Log: Ein innerer Service wirft, der äussere fängt. Lösung: nicht fangen und weiterlaufen, oder den inneren Schritt mit NESTED / REQUIRES_NEW trennen, oder fachliche Ergebnisse statt Exceptions.
  2. Pool-Deadlock mit REQUIRES_NEW: Alle Threads halten eine Connection und warten auf die zweite. Symptom: Timeouts beim Holen einer Connection. Lösung: Pool grösser als Threads, REQUIRES_NEW sparsam.
  3. Isolation wirkt nicht: Die Methode macht nur in einer äusseren Transaktion mit. Ihre Isolation wird still ignoriert. Lösung: Isolation an der äussersten Methode setzen oder validateExistingTransaction = true.
  4. Serialisierungsfehler unter Last: Mit REPEATABLE_READ oder SERIALIZABLE in PostgreSQL kommen Abbrüche (40001). Lösung: ganze Transaktion wiederholen; Retry muss ausserhalb der Transaktion liegen.
  5. Lange Transaktionen: Ein HTTP-Aufruf in der Transaktion hält Locks und Connection. Lösung: externe Aufrufe ausserhalb der Transaktion, z. B. danach per Outbox.
  6. Checked Exception committet: Ein Fehler als checked Exception speichert halbe Daten. Lösung: rollbackFor oder global rollbackOn = ALL_EXCEPTIONS (6.2+).

Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.orm.jpa.JpaTransactionManager=DEBUG (oder org.springframework.jdbc.support.JdbcTransactionManager): zeigt „Creating new“, „Participating“, „Suspending“, „rollback-only“.
  • logging.level.org.springframework.transaction.interceptor=TRACE: zeigt jeden Ein- und Austritt pro Methode.
  • TransactionSynchronizationManager.isActualTransactionActive() und getCurrentTransactionName(): im Code oder Debugger prüfen.
  • PostgreSQL: SHOW transaction_isolation; und select pid, state, xact_start, query from pg_stat_activity; für lange oder hängende Transaktionen (idle in transaction).
  • SQL Server: DBCC USEROPTIONS zeigt die Isolation der Session.
  • Actuator / Micrometer: Pool-Metriken (aktive und wartende Connections) zeigen Pool-Erschöpfung durch REQUIRES_NEW.

Senior-Punkte

  1. Die Transaktionsgrenze ist eine Design-Entscheidung. Sie gehört an den Anfang eines Use Cases, meist im Service. Nicht in den Controller, nicht ins Repository.
  2. REQUIRES_NEW ist teuer. Zwei Connections pro Thread, eigener Commit, kein gemeinsamer Rollback. Nur für echte Unabhängigkeit wie Audit oder Fehlerprotokoll.
  3. Exceptions sind Kontrollfluss für Transaktionen. Wer eine Exception fängt, muss wissen, dass die Transaktion schon markiert ist.
  4. Isolation nur so hoch wie nötig. Höhere Stufen bringen Abbrüche und Retries. Oft reicht READ_COMMITTED plus gezieltes Locking oder @Version.
  5. Isolation ist datenbankspezifisch. Gleiche Annotation, anderes Verhalten auf PostgreSQL, MySQL und SQL Server. Tests gegen die echte DB (Testcontainers) sind Pflicht.
  6. Retry um die Transaktion, nicht in ihr. Ein Retry in einer abgebrochenen Transaktion hilft nicht. Spring Framework 7 bietet dafür @Retryable; die Retry-Grenze muss ausserhalb der Transaktion liegen.
