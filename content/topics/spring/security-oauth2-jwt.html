OAuth2 Resource Server mit JWT

Kern: Ein Resource Server ist eine API, die Requests mit einem Access Token annimmt, damit nicht jeder Service Passwörter kennen muss. Er prüft jedes JWT selbst, nämlich die Signatur mit dem öffentlichen Schlüssel des Ausstellers, dann Ablaufzeit, Issuer und Audience. Danach macht er aus Scopes oder Rollen Authorities für Spring Security.

Antwort-Muster

Frage: Wie prüft eine Spring-API ein JWT?

  1. Mechanismus: Der BearerTokenAuthenticationFilter liest den Bearer-Header. Der NimbusJwtDecoder nimmt über kid den öffentlichen Schlüssel aus der JWKS und prüft die Signatur.
  2. Zahl: Danach prüft er exp und nbf mit 60 Sekunden Toleranz und den iss. Der Standard-Algorithmus ist nur RS256.
  3. Trade-off: Die Prüfung ist lokal und schnell. Dafür gilt ein gestohlenes Token bis zum Ablauf. Introspection ist sofort widerrufbar, kostet aber einen Netzwerkaufruf.
  4. Produktion: Ich setze audiences. Sonst nimmt die API auch Tokens an, die für eine andere API gelten.

1. Die Reise eines Bearer-Tokens

  1. Token lesen: Der BearerTokenAuthenticationFilter liest den Header Authorization: Bearer eyJ…. Er baut ein BearerTokenAuthenticationToken.
  2. Provider wählen: Der ProviderManager gibt es an den JwtAuthenticationProvider.
  3. Signatur prüfen: Der JwtDecoder (NimbusJwtDecoder) liest den kid im Header. Er nimmt den passenden öffentlichen Schlüssel aus der JWKS und prüft die Signatur. Standard-Algorithmus: nur RS256.
  4. Claims prüfen: exp und nbf mit 60 Sekunden Toleranz (clock skew), dazu iss. aud nur, wenn konfiguriert.
  5. Authorities bauen: Der JwtAuthenticationConverter macht aus dem Claim scope oder scp Authorities mit Präfix SCOPE_. Andere Claims wie roles muss man selbst mappen.
  6. SecurityContext: Ein JwtAuthenticationToken mit dem Jwt als Principal. getName() ist der sub-Claim.
  7. Autorisierung: Der AuthorizationFilter prüft die Regeln. Fehlt das Recht: 403 mit error="insufficient_scope".

Wichtig: Mit issuer-uri holt Spring die Metadaten (/.well-known/openid-configuration) erst beim ersten Request mit JWT. Der Start hängt also nicht vom Authorization Server ab.

2. Aufbau

  1. Client: Holt beim Authorization Server ein Token. Eine SPA mit Login (Authorization Code mit PKCE), ein Service ohne Benutzer mit Client Credentials.
  2. Authorization Server: Stellt das JWT aus und signiert es mit seinem privaten Schlüssel. Beispiele: Microsoft Entra ID, Keycloak.
  3. Resource Server: Bekommt das Token im Header Authorization: Bearer …. Er prüft es lokal.
  4. JWKS: Die JSON Web Key Set ist die Liste der öffentlichen Schlüssel des Ausstellers. Der Resource Server lädt sie selten und speichert sie im Cache.
  5. SecurityContext: Nach der Prüfung liegt ein JwtAuthenticationToken mit Authorities darin.

3. Details, die Interviewer fragen

  1. issuer-uri: Er muss genau dem iss-Claim entsprechen. Spring liest daraus die Metadaten. Es findet die jwks_uri und prüft danach jeden iss.
  2. Verzögerte Suche: Spring sucht die Metadaten erst beim ersten Request mit JWT. Das macht ein SupplierJwtDecoder. Der Start hängt so nicht vom Authorization Server ab. Wer einen eigenen JwtDecoder deklariert, sollte ihn einpacken.
  3. jwk-set-uri: Das ist die direkte Adresse der Schlüssel. Dann fragt Spring keine Metadaten ab. Man setzt issuer-uri trotzdem, damit iss geprüft wird.
  4. public-key-location: Das ist ein fester öffentlicher Schlüssel als Datei. Es braucht kein Netzwerk. Es gibt aber keine automatische Schlüsselrotation.
  5. Audience: Der aud-Claim sagt, für welche API das Token ist. Spring prüft ihn nur, wenn audiences gesetzt ist oder ein eigener JwtClaimValidator existiert.
  6. Validator-Kette: Der Decoder prüft ein Token mit Validatoren. DelegatingOAuth2TokenValidator kombiniert sie. Typisch sind JwtTimestampValidator und JwtIssuerValidator. Eigene Validatoren setzt man mit setJwtValidator.
  7. Algorithmen: NimbusJwtDecoder vertraut standardmässig nur RS256. Andere erlaubt man mit jws-algorithms. Ein Token mit alg: none wird nie akzeptiert.
  8. Schlüsselrotation: Neue Schlüssel holt Spring automatisch über die JWKS. Die JWKS wird standardmässig 5 Minuten im Speicher gecacht.
  9. Clock skew: Standard sind 60 Sekunden für exp und nbf. Man stellt sie über JwtTimestampValidator ein.
  10. Scopes vs Rollen: Ein Scope ist ein Recht, das der Client im Namen des Users bekommt (delegiert). Eine Rolle ist ein Recht des Users oder der App selbst. Spring mappt Scopes mit SCOPE_. Rollen muss man selbst mappen.
  11. Boot-Properties fürs Mapping: authorities-claim-name, authority-prefix und principal-claim-name stehen unter spring.security.oauth2.resourceserver.jwt. Sie ersetzen aber nur eine Quelle. Für Scopes und Rollen braucht man einen DelegatingJwtGrantedAuthoritiesConverter.
  12. Entra ID Claims: scp ist ein String mit Leerzeichen und kommt nur in Benutzer-Tokens. roles ist ein Array mit App Roles. Bei Client Credentials gibt es nur roles. oid ist die stabile ID des Benutzers im Tenant.
  13. Entra v1 vs v2: v2-Tokens haben einen Issuer mit /v2.0 am Ende. Ihr aud ist die Client-ID der API. Die App-Registrierung der API entscheidet, welche Version kommt.
  14. Entra Gruppen: Ab 200 Gruppen kommt im JWT kein groups-Claim mehr. Stattdessen kommt ein Overage-Hinweis. Darum nimmt man lieber App Roles als Gruppen.
  15. Client vs Resource Server: Der Client (oauth2Client, oauth2Login) holt Tokens und ruft APIs auf. Der Resource Server (oauth2ResourceServer) nimmt Tokens an und prüft sie. Ein Service kann beides sein.
  16. Starter in Boot 4: Es gibt spring-boot-starter-security-oauth2-resource-server und …-oauth2-client. Die alten Namen ohne security- sind ersetzt.
  17. JWT vs Opaque Token: JWT prüft man lokal. Ein Widerruf wirkt erst bei Ablauf. Opaque Tokens prüft man per Introspection beim Aussteller. Sie sind sofort widerrufbar, kosten aber einen Netzwerkaufruf pro Request.
  18. Mehrere Aussteller: JwtIssuerAuthenticationManagerResolver wählt den Decoder nach dem iss-Claim. Das ist nützlich für mehrere Tenants.

4. Fallen

  • „Der Resource Server fragt bei jedem Request den Aussteller.“ → Falsch. Er prüft lokal mit dem gecachten öffentlichen Schlüssel.
  • „Spring prüft die Audience automatisch.“ → Falsch. Nur mit audiences oder eigenem Validator.
  • „Rollen aus dem Token werden automatisch zu ROLE_.“ → Falsch. Standard ist nur scope/scp mit Präfix SCOPE_.
  • „Ein JWT ist verschlüsselt.“ → Falsch. Ein signiertes JWT ist nur Base64. Jeder kann es lesen, keiner kann es ändern.
  • „Mit issuer-uri startet die App nicht, wenn Entra ID nicht erreichbar ist.“ → Falsch. Die Abfrage passiert beim ersten Token, nicht beim Start.
  • „Ein JWT kann man sofort widerrufen.“ → Falsch. Es gilt bis exp. Dafür kurze Laufzeiten oder Introspection.

5. Selbsttest

Warum?

Warum muss man die Audience prüfen?

Sonst akzeptiert die API Tokens, die für eine andere API ausgestellt wurden. Die Signatur ist trotzdem gültig.

Warum hat ein Client-Credentials-Token von Entra kein scp?

Es gibt keinen Benutzer, also keine delegierten Scopes. Die Rechte der App stehen im roles-Claim.

Warum App Roles statt Gruppen?

Gruppen sind GUIDs und ab 200 Gruppen fehlt der Claim im JWT. App Roles sind lesbar und klein.

Wie innen?

Was ist ein Resource Server?

Eine API, die Requests mit einem Access Token annimmt und das Token prüft. In Spring aktiviert man das mit oauth2ResourceServer(o -> o.jwt(...)).

Was braucht ein minimaler Resource Server in Spring Boot?

Den Starter für den Resource Server und die Property spring.security.oauth2.resourceserver.jwt.issuer-uri. Boot baut dann JwtDecoder und Filterkette.

Was prüft Spring an einem JWT standardmässig?

Die Signatur mit dem Schlüssel aus der JWKS, dazu exp, nbf und iss. Die Audience nur, wenn konfiguriert.

Woher kennt der Resource Server den öffentlichen Schlüssel?

Aus der JWKS des Ausstellers. Die Adresse kommt aus den OpenID-Metadaten oder direkt aus jwk-set-uri.

Was ist der kid im JWT-Header?

Die ID des Schlüssels, mit dem signiert wurde. Damit findet der Decoder den passenden Schlüssel in der JWKS, auch bei Rotation.

issuer-uri vs jwk-set-uri?

issuer-uri findet die Schlüssel über Metadaten und prüft iss. jwk-set-uri nennt die Schlüssel direkt; issuer-uri setzt man zusätzlich für die iss-Prüfung.

Wann holt Spring die Metadaten?

Beim ersten Request mit JWT, nicht beim Start. So hängt der Start nicht vom Aussteller ab.

Wie werden Scopes zu Authorities?

Der JwtGrantedAuthoritiesConverter liest scope oder scp und setzt den Präfix SCOPE_ vor jeden Wert.

Wie mappen Sie Rollen aus dem Token?

Mit einem zweiten Converter für den Claim roles und Präfix ROLE_, kombiniert über DelegatingJwtGrantedAuthoritiesConverter.

Zahlen

Was ist clock skew?

Eine Toleranz für Uhrzeitunterschiede bei exp und nbf. Spring nutzt standardmässig 60 Sekunden.

Welcher Algorithmus wird standardmässig akzeptiert?

Nur RS256. Andere Algorithmen muss man mit jws-algorithms oder am Decoder freigeben.

401 oder 403 bei einem Token ohne passenden Scope?

403 mit error="insufficient_scope". Das Token ist gültig, aber das Recht fehlt. Ein ungültiges Token gibt 401.

Wie lange cached Spring die JWKS?

Standardmässig 5 Minuten im Speicher. Neue Schlüssel holt Spring danach automatisch.

Ab wie vielen Gruppen fehlt bei Entra ID der groups-Claim?

Ab 200 Gruppen. Stattdessen kommt ein Overage-Hinweis. Darum App Roles nutzen.

Vergleich

OAuth2 Client vs Resource Server?

Der Client holt Tokens und ruft APIs auf. Der Resource Server nimmt Tokens an und prüft sie. Ein Service kann beides sein.

JWT vs Opaque Token?

JWT prüft man lokal, schnell, aber ohne sofortigen Widerruf. Opaque Tokens prüft man per Introspection beim Aussteller, aktuell, aber mit Netzwerkaufruf.

issuer-uri vs public-key-location?

issuer-uri findet die Schlüssel über Metadaten, mit Rotation. public-key-location ist ein fester Schlüssel, ohne Netzwerk und ohne Rotation.

Produktion

Wie testen Sie eine JWT-geschützte API ohne echten Aussteller?

Mit spring-security-test: .with(jwt().authorities(...)) in MockMvc. Der Decoder wird dabei umgangen.

Szenario: Nach dem Wechsel zu Entra ID gibt die API für alle Tokens 401. Wie gehen Sie vor?

TRACE-Log und WWW-Authenticate lesen. Dann iss und aud im Token mit issuer-uri und audiences vergleichen, oft v1 gegen v2. Zuletzt den Netzwerkweg zur JWKS prüfen.

Szenario: Ein Benutzer mit der Rolle Admin bekommt 403 auf /admin. Warum?

Der roles-Claim wird nicht gemappt; es gibt nur SCOPE_-Authorities. Lösung: roles mit ROLE_ mappen oder hasAuthority mit dem echten Namen prüfen.

Szenario: Ein gestohlenes Token muss sofort ungültig werden. Was sagen Sie?

Ein JWT gilt bis exp, lokal kann man es nicht widerrufen. Kurzfristig: Schlüssel rotieren oder eine Sperrliste. Langfristig: kurze Laufzeiten, BFF oder Introspection.

Warum ist der erste Request mit Token langsam oder fehlerhaft?

Metadaten und JWKS werden erst beim ersten Token geholt. Ein Proxy oder ein fehlendes CA-Zertifikat blockiert das. Lösung: Netzwerkweg testen oder jwk-set-uri setzen.

Design

Was ist das BFF-Muster?

Ein Backend for Frontend hält die Tokens und macht den Login. Der Browser bekommt nur ein Session-Cookie. Tokens sind so nicht im JavaScript.

Welche Claims sind bei Entra ID wichtig?

iss (Tenant und Version), aud (Client-ID der API), scp für delegierte Scopes, roles für App Roles, oid und tid für Benutzer und Tenant.

Wie gehen Sie mit mehreren Tenants oder Ausstellern um?

Mit JwtIssuerAuthenticationManagerResolver. Er wählt pro Request den Decoder nach dem iss-Claim und lehnt unbekannte Aussteller ab.

Ist ein JWT verschlüsselt?

Ein normales signiertes JWT nicht. Es ist Base64 und lesbar. Darum keine Geheimnisse in Claims.

Mehr

Gerüst

  • Warum? Nicht jeder Service muss Passwörter kennen. Die API prüft ein Token selbst.
  • Wie innen? BearerTokenAuthenticationFilter → JwtAuthenticationProvider → NimbusJwtDecoder (kid → JWKS → Signatur) → Claims prüfen → JwtAuthenticationConverter → Authorities SCOPE_….
  • Zahlen Standard nur RS256. Clock skew 60 Sekunden. JWKS-Cache 5 Minuten. Bei Entra ID fehlt ab 200 Gruppen der groups-Claim.
  • Vergleich JWT lokal ist schnell, Widerruf gilt erst bei Ablauf. Introspection ist aktuell, kostet aber einen Netzwerkaufruf pro Request. Resource Server vs Client.
  • Produktion Keine aud-Prüfung → Tokens fremder APIs werden akzeptiert. Rollen nicht gemappt → 403. Falscher Issuer (v1 gegen v2) → 401.
  • Design audiences setzen, App Roles statt Gruppen, kurze Laufzeit. Für Browser-Apps das BFF-Muster.

Beispiel: Resource Server für Microsoft Entra ID

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.microsoftonline.com/<tenant-id>/v2.0
          audiences: <client-id-der-api>      # v2-Token: aud = Client-ID der API
@Configuration
@EnableMethodSecurity
class ApiSecurity {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/reports/**").hasAuthority("SCOPE_reports.read")
            .requestMatchers("/api/admin/**").hasRole("Admin")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(converter())))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
    return http.build();
  }

  JwtAuthenticationConverter converter() {
    var scopes = new JwtGrantedAuthoritiesConverter();          // scp → SCOPE_
    var roles  = new JwtGrantedAuthoritiesConverter();
    roles.setAuthoritiesClaimName("roles");                    // App Roles von Entra
    roles.setAuthorityPrefix("ROLE_");
    var c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(new DelegatingJwtGrantedAuthoritiesConverter(scopes, roles));
    c.setPrincipalClaimName("oid");                            // stabile Benutzer-ID
    return c;
  }
}

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spring Security 7, Header gekürzt. Der genaue Text von error_description hängt von der Version ab.

  1. Ohne Token: 401 und nur WWW-Authenticate: Bearer (RFC 6750).
  2. Token für eine andere API: Signatur ist gültig, aber aud passt nicht. 401 mit invalid_token.
  3. Gültiges Token ohne Scope reports.read: angemeldet, aber nicht erlaubt. 403 mit insufficient_scope.
  4. Mit Scope: 200. Die Authorities sind z. B. SCOPE_reports.read und ROLE_Admin.

Vergleich

  • Resource Server: prüft Tokens, stateless, keine Login-Seite. Für APIs.
  • OAuth2 Client mit Login (oauth2Login): Browser-Login über OIDC, Session im Server. Für serverseitige Web-Apps und das BFF-Muster (Backend for Frontend hält die Tokens, der Browser nur ein Cookie).
  • OAuth2 Client ohne User: Client Credentials, um eine andere API aufzurufen. Spring Security 7 unterstützt OAuth2 auch für HTTP Service Clients.
  • Authorization Server: stellt Tokens aus. Seit Spring Security 7 ist Spring Authorization Server Teil von Spring Security. Meist nimmt man aber Entra ID oder Keycloak.
  • JWT lokal vs Introspection: lokal schnell und unabhängig, Introspection aktuell, aber abhängig vom Aussteller.

In der Produktion

  1. Alle Requests 401 nach Umstellung auf Entra v2: Der iss im Token passt nicht zur issuer-uri, z. B. v1-Token gegen v2-Issuer. Lösung: Token in einem Decoder ansehen, Token-Version der App-Registrierung prüfen.
  2. Token einer fremden API wird akzeptiert: aud wurde nicht geprüft. Lösung: audiences setzen.
  3. Rollen wirken nicht: hasRole("Admin") schlägt fehl, weil nur SCOPE_-Authorities existieren. Lösung: roles-Claim mit ROLE_ mappen.
  4. Sporadische 401 mit exp-Fehler: Uhren laufen auseinander. Lösung: NTP im Cluster, Toleranz nicht übertreiben.
  5. Erster Request langsam oder Fehler: Metadaten und JWKS werden beim ersten Token geholt. Ein Proxy oder fehlendes CA-Zertifikat blockiert das. Lösung: Netzwerkweg zu login.microsoftonline.com testen, CA-Bundle ins Image, oder jwk-set-uri setzen.
  6. Riesige Header: Tokens mit vielen Gruppen werden zu gross für Proxy-Limits. Lösung: App Roles statt Gruppen.
  7. Token geleakt: JWT bleibt bis exp gültig. Lösung: kurze Laufzeit, Refresh Tokens nur im BFF, nie Tokens loggen.

Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.security=TRACE: zeigt, welcher Validator ablehnt.
  • Header WWW-Authenticate lesen: invalid_token (Token falsch) vs insufficient_scope (Recht fehlt).
  • Token dekodieren (nur lokal, nie Produktions-Tokens in fremde Webseiten): iss, aud, exp, scp, roles, ver prüfen.
  • curl https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration: Issuer und jwks_uri sehen.
  • Tests: spring-security-test mit .with(jwt().authorities(new SimpleGrantedAuthority("SCOPE_reports.read"))) in MockMvc. Kein echter Aussteller nötig.
  • Endpoint zum Debuggen (nur lokal): @AuthenticationPrincipal Jwt jwt und die Authorities ausgeben.

Senior-Punkte

  1. Immer Issuer, Audience und Ablauf prüfen. Eine gültige Signatur allein heisst nur: „irgendwer beim Aussteller hat es bekommen“.
  2. Rechte als App Roles oder Scopes modellieren, nicht als Gruppen-IDs. Das ist lesbar, klein und unabhängig vom Tenant.
  3. Stateless lohnt sich bei Skalierung: keine Session, kein Sticky Load Balancing. Der Preis: Widerruf erst mit Ablauf.
  4. Browser-Apps: Tokens im Browser sind angreifbar. Das BFF-Muster hält Tokens im Backend.
  5. Autorisierung im Code ist Fachlogik. Das Token sagt „wer“ und „grob was“. Feine Regeln („eigene Datensätze“) gehören in Method Security.
  6. Lokale Prüfung macht unabhängig. Nach dem JWKS-Cache braucht die API den Aussteller nicht pro Request.
