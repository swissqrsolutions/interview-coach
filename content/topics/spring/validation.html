Bean Validation: @Valid, eigene Validatoren

Spring · Tier 2 · Quellen: Spring Framework 7.1 Reference („Java Bean Validation“, „Validation“ in Spring MVC Controllern), Spring Boot 4.2 Reference („Validation“), Spring-Quellcode MethodArgumentNotValidException, Jakarta Validation 3.1, Hibernate Validator Releases (9.1 in Boot 4.2), PostgreSQL 17 Doku (Constraints)

Kern: Bean Validation (Jakarta Validation 3.1) ist ein Standard, der Regeln als Annotations an Feldern und Parametern beschreibt. Er löst das Problem, dass Prüfcode sonst in jedem Controller kopiert wird. Hibernate Validator ist die Implementierung, und Spring ruft sie automatisch auf: an der Web-Grenze und bei @Validated-Beans.

1. Wo sitzt die Validierung?

  1. Web-Grenze: Spring MVC validiert @RequestBody, @ModelAttribute und Parameter. Beispiel: @Valid @RequestBody OrderRequest.
  2. Service: Eine Bean mit @Validated an der Klasse bekommt einen Proxy, also ein Hüll-Objekt, das vor jedem Aufruf prüft. Beispiel: find(@Size(min = 8) String code).
  3. Hibernate ORM: Ist ein Validator da, prüft Hibernate Entities vor INSERT und UPDATE. Das ist der validation-mode AUTO von Jakarta Persistence.
  4. Datenbank: Constraints wie NOT NULL und CHECK sind die letzte Grenze. Sie gelten auch für Batch-Jobs und SQL-Skripte.
  5. Hibernate Validator 9.1 (in Spring Boot 4.2) macht die eigentliche Arbeit. Spring Boot bringt ihn mit spring-boot-starter-validation.

2. Die Reise eines ungültigen Requests

  1. JSON lesen: Ein HttpMessageConverter (Jackson) baut aus dem Body ein OrderRequest. Ist der JSON kaputt oder "qty": "abc", kommt schon hier HttpMessageNotReadableException. Die Validierung läuft dann gar nicht.
  2. @Valid gesehen: Der Argument Resolver für @RequestBody sieht @Valid. Er ruft den Validator auf.
  3. Validator: Hibernate Validator liest die Annotations (einmal, dann im Cache). Er prüft alle Regeln und sammelt alle Verstösse. Mit @Valid an einem Feld geht er in verschachtelte Objekte (Cascading).
  4. Fehler sammeln: Spring macht aus jeder ConstraintViolation einen FieldError im BindingResult.
  5. Exception: Hat die Methode kein BindingResult-Parameter, wirft Spring MethodArgumentNotValidException. Der Controller läuft nicht.
  6. Antwort: ResponseEntityExceptionHandler oder Ihr @RestControllerAdvice macht daraus eine 400-Antwort. Standard-Text: "Invalid request content."

3. Beispiel: Request, eigener Validator, Datenbank

public record OrderRequest(
    @NotBlank @Email String email,
    @Min(1) @Max(100) int qty,
    @NotNull @Valid Address address,
    List<@NotBlank String> tags) {}           // Container-Element-Constraint

@ValidPeriod                                    // eigene Klassen-Regel
public record Period(LocalDate start, LocalDate end) {}

@Target(TYPE) @Retention(RUNTIME)
@Constraint(validatedBy = PeriodValidator.class)
public @interface ValidPeriod {
  String message() default "{period.invalid}";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload() default {};
}

public class PeriodValidator implements ConstraintValidator<ValidPeriod, Period> {
  public boolean isValid(Period p, ConstraintValidatorContext ctx) {
    if (p == null || p.start() == null || p.end() == null) return true;  // null prüft @NotNull
    return !p.end().isBefore(p.start());
  }
}

  1. Bean Validation meldet alle 4 Fehler auf einmal. Die Datenbank meldet nur den ersten Fehler pro Zeile.
  2. List<@NotBlank String> prüft jedes Element. Das heisst Container Element Constraint.
  3. @Valid am Feld address prüft das verschachtelte Objekt. Ohne @Valid bleibt zip: "" unentdeckt.
  4. PeriodValidator gibt bei null true zurück. Das ist die Regel im Standard: Nur @NotNull ist für null zuständig.
  5. Die fehlgeschlagenen Inserts haben trotzdem IDs verbraucht (die gute Zeile hat ID 4). Eine Identity-Sequenz wird nicht zurückgerollt.
  6. Die DB-Meldung enthält die ganze Zeile. Darum gehört sie ins Log, nie in die Antwort an den Client.

4. Details, die Interviewer fragen

  1. @Valid vs @Validated: @Valid (Jakarta) markiert ein Objekt für Cascading, also „prüfe auch das Innere“. @Validated (Spring) kann zusätzlich Gruppen angeben. An der Klasse aktiviert @Validated die Method Validation über einen Proxy.
  2. Zwei Exceptions im Controller: MethodArgumentNotValidException kommt, wenn nur ein @Valid-Objekt geprüft wird. HandlerMethodValidationException kommt, wenn Constraints direkt am Parameter stehen, z. B. @Min(1) @RequestParam int page. Seit Framework 6.1 validiert Spring MVC das ohne AOP. Man behandelt beide.
  3. BindingResult: Steht BindingResult direkt nach dem @Valid-Parameter, wirft Spring nichts. Der Controller muss die Fehler dann selbst prüfen. Das vergisst man leicht.
  4. @NotNull, @NotEmpty, @NotBlank: @NotNull verbietet nur null. @NotEmpty verbietet auch "" und leere Listen. @NotBlank verbietet auch " ", nur für Texte.
  5. null ist gültig: @Size, @Email, @Pattern, @Min akzeptieren null. Für Pflichtfelder braucht man immer zusätzlich @NotNull oder @NotBlank.
  6. Eigener Validator: Ein Constraint hat zwei Teile: die Annotation mit @Constraint(validatedBy = …) und eine ConstraintValidator-Klasse. Pflicht-Attribute: message, groups, payload.
  7. Validator mit Spring-Beans: Spring erzeugt Validatoren über die SpringConstraintValidatorFactory. Darum funktioniert Injection, z. B. ein Repository. Aber: DB-Abfragen im Validator sind langsam und haben Race Conditions.
  8. Kreuz-Feld-Regeln: „Ende nach Start“ gehört an die Klasse, nicht an ein Feld. Mit ctx.buildConstraintViolationWithTemplate(...).addPropertyNode("end") hängt man den Fehler an ein Feld.
  9. Gruppen: Eine Validation Group ist ein leeres Interface, z. B. OnCreate. Mit @Validated(OnCreate.class) laufen nur diese Regeln. Ohne Gruppe läuft Default. @GroupSequence legt eine Reihenfolge fest und stoppt nach der ersten fehlgeschlagenen Gruppe.
  10. Meldungen: {jakarta.validation.constraints.Min.message} ist ein Schlüssel. Hibernate Validator ersetzt {value} durch den Wert der Annotation. Spring Boot löst die Schlüssel auch über die eigene MessageSource auf, also messages.properties.
  11. Method Validation im Service: Braucht @Validated an der Klasse. Fehler: ConstraintViolationException. Sie läuft über einen Proxy, darum gilt sie nicht bei einem Aufruf in der eigenen Klasse (Self-Invocation).
  12. Rückgabewerte: Constraints an der Methode prüfen den Rückgabewert, z. B. @NotNull Order find(...). Das ist ein Vertrag (Design by Contract).
  13. Hibernate ORM: Mit Validator auf dem Classpath prüft Hibernate Entities vor dem Schreiben. Fehler kommt erst beim Flush, oft beim Commit. Spring meldet ihn dann als TransactionSystemException mit der ConstraintViolationException als Ursache.
  14. @ConfigurationProperties: Mit @Validated an der Properties-Klasse prüft Boot die Konfiguration beim Start. Eine falsche URL stoppt dann den Start statt den ersten Request.
  15. Fail Fast: Hibernate Validator kann nach dem ersten Fehler stoppen (hibernate.validator.fail_fast). Für APIs will man meistens alle Fehler auf einmal.

5. Vergleich

  • Bean Validation: deklarativ, alle Fehler auf einmal, an jeder Schicht nutzbar. Gut für Form und Format.
  • Spring Validator-Interface: Programmatische Prüfung mit validate(Object, Errors). Gut für Regeln, die schwer als Annotation passen. Wird mit @InitBinder an einen Controller gebunden.
  • Prüfung im Domain-Code: Geschäftsregeln wie „Kredit-Limit nicht überschritten“ gehören in den Service oder die Entity. Sie brauchen Zustand und Kontext.
  • Datenbank-Constraints: NOT NULL, CHECK, UNIQUE, Foreign Keys. Einzige Grenze, die bei Parallelität sicher ist (z. B. Eindeutigkeit).
  • OpenAPI-Schema-Validierung: prüft am Gateway oder in Tests gegen den Vertrag. Ergänzt Bean Validation, ersetzt sie nicht.
  • Jackson-Fehler: falscher Typ oder kaputtes JSON. Das ist Parsing, nicht Validierung, und kommt vorher.

6. In der Produktion

  1. @Valid wirkt nicht: Es fehlt spring-boot-starter-validation. Der Web-Starter bringt keinen Validator mehr mit (seit Boot 2.3). Ohne Validator ignoriert Spring @Valid still. Lösung: Starter hinzufügen und einen Test mit ungültigem Request schreiben.
  2. 500 statt 400: Ein Controller hat @Validated an der Klasse. Dann prüft der AOP-Proxy und wirft ConstraintViolationException, die kein Standard-Handler kennt. Lösung: @Validated an der Klasse entfernen (Spring MVC validiert selbst) oder die Exception im Advice behandeln.
  3. Eindeutigkeit im Validator: @UniqueEmail fragt die DB. Zwei Requests gleichzeitig kommen beide durch. Lösung: UNIQUE-Constraint in der DB und den Fehler als 409 übersetzen.
  4. Fehler erst beim Commit: Eine Entity-Regel schlägt beim Flush fehl. Der Client sieht 500 mit TransactionSystemException. Lösung: an der Web-Grenze mit DTO validieren, Entity-Validierung nur als Sicherheitsnetz.
  5. Daten im Fehlertext: Meldungen wie ${validatedValue} geben Eingaben zurück, auch Passwörter. Lösung: Feldname und Regel melden, nicht den Wert.
  6. Langsame Validierung: Ein Validator ruft pro Element einen Service auf. Bei Listen mit 10 000 Elementen dauert das. Lösung: Listen-Grösse begrenzen (@Size(max = …)) und teure Prüfungen gebündelt im Service machen.

7. Diagnose

  • Log von DefaultHandlerExceptionResolver (WARN): zeigt Resolved [MethodArgumentNotValidException ...] mit Anzahl und Feldern der Fehler.
  • logging.level.org.springframework.web=DEBUG: zeigt, welcher Argument Resolver und welcher Handler laufen.
  • Unit-Test ohne Spring: Validation.buildDefaultValidatorFactory().getValidator().validate(obj) liefert die Verstösse. Schnell, gut für eigene Constraints.
  • @WebMvcTest mit MockMvc: ungültigen Body senden, status().isBadRequest() und Feldfehler prüfen.
  • Actuator /actuator/beans: zeigt, ob eine Validator-Bean und methodValidationPostProcessor existieren.
  • Datenbank: \d+ tabelle in psql zeigt alle Constraints. Fehlercode 23514 (check_violation), 23502 (not_null), 23505 (unique).

8. Senior-Punkte

  1. Validieren an der Grenze, mit DTOs. Die API-Form gehört in Request-DTOs. Entities validieren nur als Sicherheitsnetz.
  2. Drei Ebenen, drei Aufgaben: Bean Validation für Form, Domain-Code für Geschäftsregeln, DB für Integrität. Keine Ebene ersetzt die andere.
  3. Eindeutigkeit und Existenz prüft die Datenbank. Ein Validator mit SELECT ist nur eine freundliche Vorprüfung.
  4. Ein Fehlerformat für alle Validierungsfehler: Beide Exceptions (MethodArgumentNotValidException, HandlerMethodValidationException) auf die gleiche Liste errors[{field, message}] abbilden.
  5. Gruppen sparsam nutzen. Zwei DTOs (CreateOrder, UpdateOrder) sind oft klarer als ein DTO mit Gruppen.
  6. Konfiguration beim Start validieren. Ein Fehler beim Deployment ist billiger als ein Fehler um 3 Uhr nachts.

10. Fallen

  • „@Size(min = 1) macht ein Feld zur Pflicht.“ → Falsch. null ist gültig. Pflicht heisst @NotNull oder @NotBlank.
  • „@Valid und @Validated sind gleich.“ → Falsch. Nur @Validated kennt Gruppen und aktiviert an der Klasse die Method Validation.
  • „Ein @UniqueEmail-Validator garantiert Eindeutigkeit.“ → Falsch. Bei parallelen Requests nicht. Das kann nur ein UNIQUE-Constraint.
  • „Ohne Fehler im Log läuft die Validierung.“ → Falsch. Ohne Validator auf dem Classpath ignoriert Spring @Valid still.
  • „Ein falscher Typ im JSON ist ein Validierungsfehler.“ → Falsch. Das ist ein Parsing-Fehler (HttpMessageNotReadableException) vor der Validierung.
  • „Method Validation im Service gilt auch beim internen Aufruf.“ → Falsch. Sie läuft über einen Proxy, Self-Invocation umgeht ihn.

11. Fragen

Was ist Bean Validation?

Ein Jakarta-Standard, der Regeln als Annotations an Feldern, Parametern und Klassen beschreibt. Hibernate Validator ist die Referenz-Implementierung. Spring ruft ihn automatisch auf.

Wie aktivieren Sie Validierung für einen Request-Body?

Mit @Valid (oder @Validated) vor @RequestBody. Dazu muss spring-boot-starter-validation auf dem Classpath sein.

@Valid vs @Validated?

@Valid ist Jakarta und steuert Cascading. @Validated ist Spring, kann Gruppen angeben und aktiviert an einer Klasse Method Validation per Proxy.

Was ist Cascading?

Mit @Valid an einem Feld prüft der Validator auch das verschachtelte Objekt. Ohne @Valid bleibt das Innere ungeprüft.

MethodArgumentNotValidException vs HandlerMethodValidationException?

Die erste kommt bei einem einzelnen @Valid-Objekt. Die zweite kommt, wenn Constraints direkt an Parametern stehen; dann validiert Spring die ganze Methode. Beide behandeln.

Was passiert mit einem BindingResult-Parameter?

Steht er direkt nach dem geprüften Parameter, wirft Spring keine Exception. Der Controller läuft und muss die Fehler selbst auswerten.

@NotNull vs @NotEmpty vs @NotBlank?

@NotNull: nicht null. @NotEmpty: nicht null und nicht leer (Text, Liste). @NotBlank: Text mit mindestens einem Nicht-Leerzeichen.

Ist null für @Email gültig?

Ja. Fast alle Constraints akzeptieren null. Für Pflicht zusätzlich @NotNull oder @NotBlank.

Wie schreiben Sie einen eigenen Validator?

Eine Annotation mit @Constraint(validatedBy = X.class) und den Attributen message, groups, payload. Dazu eine Klasse X implements ConstraintValidator<A, T> mit isValid.

Wie prüfen Sie „Ende nach Start“?

Mit einem Constraint an der Klasse, nicht am Feld. Der Validator sieht beide Werte und hängt den Fehler mit addPropertyNode an ein Feld.

Kann ein ConstraintValidator Spring-Beans nutzen?

Ja. Spring erzeugt Validatoren mit der SpringConstraintValidatorFactory, Injection funktioniert. DB-Abfragen dort sind aber teuer und nicht race-sicher.

Was sind Validation Groups?

Leere Interfaces, die Regeln gruppieren, z. B. OnCreate. @Validated(OnCreate.class) prüft nur diese Gruppe. Ohne Angabe läuft Default.

Was macht @GroupSequence?

Es prüft Gruppen nacheinander und stoppt nach der ersten Gruppe mit Fehler. So laufen teure Regeln nur, wenn billige bestanden sind.

Wie validieren Sie Parameter einer Service-Methode?

@Validated an die Klasse, Constraints an die Parameter. Spring Boot registriert den MethodValidationPostProcessor, der einen Proxy baut. Fehler: ConstraintViolationException.

Warum wirkt Method Validation bei einem internen Aufruf nicht?

Sie läuft im Proxy. Ein Aufruf über this geht am Proxy vorbei.

Wie validieren Sie Elemente einer Liste?

Mit Container Element Constraints, z. B. List<@NotBlank String>. Für Objekte in der Liste: List<@Valid Item>.

Wie validieren Sie Konfiguration?

@Validated an die @ConfigurationProperties-Klasse und Constraints an die Felder. Boot prüft beim Start und stoppt bei Fehlern.

Validiert Hibernate ORM auch?

Ja, wenn ein Validator da ist. Es prüft Entities vor Insert und Update. Der Fehler kommt beim Flush, oft erst beim Commit als TransactionSystemException.

Wie übersetzen Sie Fehlermeldungen?

Mit Schlüsseln wie {order.qty.min} und Dateien ValidationMessages.properties oder, in Spring Boot, messages.properties mit Locale-Varianten.

Warum braucht man trotzdem DB-Constraints?

Andere Wege schreiben auch in die DB: Skripte, Batch, andere Services. Und nur die DB garantiert Eindeutigkeit bei Parallelität.

Was ist Fail Fast?

Hibernate Validator stoppt nach dem ersten Fehler. Spart Zeit, aber der Client sieht nur einen Fehler pro Request.

Was gehört nicht in Bean Validation?

Geschäftsregeln mit Zustand oder anderen Daten, z. B. Kredit-Limit oder Lagerbestand. Die gehören in den Domain-Code.

Wie testen Sie einen eigenen Constraint?

Ohne Spring mit Validation.buildDefaultValidatorFactory().getValidator(). Gültige, ungültige und null-Werte prüfen.

Szenario: Ein Endpoint akzeptiert leere Pflichtfelder, obwohl @NotBlank im DTO steht. Was prüfen Sie?

Erstens: Fehlt @Valid am Parameter? Zweitens: Ist spring-boot-starter-validation da? Drittens: Gibt es ein BindingResult, das niemand auswertet?

Szenario: Ungültige Query-Parameter führen zu 500 statt 400. Woran liegt es?

Wahrscheinlich steht @Validated an der Controller-Klasse. Dann wirft der Proxy ConstraintViolationException. Lösung: @Validated entfernen oder die Exception im Advice auf 400 abbilden.

Szenario: Trotz @UniqueEmail-Validator gibt es doppelte Benutzer. Was tun Sie?

Der Validator hat eine Race Condition. Lösung: UNIQUE-Constraint in der DB, die Verletzung (SQLSTATE 23505) als 409 übersetzen, Duplikate vorher bereinigen.
