Spring Testing: @SpringBootTest, Slices, MockitoBean, Testcontainers

Kern: Spring Testing ist die Unterstützung von Spring für Tests mit einem echten ApplicationContext. Sie löst das Problem, dass Unit-Tests die Verdrahtung nicht prüfen. Man wählt die Grösse des Kontexts: ganz (@SpringBootTest) oder nur eine Schicht (Slice, z. B. @WebMvcTest). Der Kontext wird zwischen Tests gecacht, darum entscheidet die Konfiguration über die Laufzeit.

1. Wo sitzen die Testarten?

  1. Unit-Test: Eine Klasse mit new und Mockito-Mocks. Kein Spring. Für Fachlogik.
  2. Slice-Test: Ein kleiner Kontext für eine Schicht. @WebMvcTest lädt nur die Web-Schicht, @DataJpaTest nur JPA. Die Nachbarn ersetzt man mit @MockitoBean.
  3. @SpringBootTest: Der ganze Kontext wie in Produktion. Standard: kein Server, Mock-Web-Umgebung.
  4. Testcontainers: Echte Infrastruktur in Docker. @ServiceConnection verbindet sie automatisch mit Spring.
  5. Context Cache: Alle Spring-Tests teilen einen Cache. Gleiche Konfiguration heisst: Kontext nur einmal starten.

2. Die Reise eines Testlaufs (die Geschichte zum Merken)

  1. Start: JUnit 5 startet die Testklasse. Die SpringExtension (in @SpringBootTest und allen Slices enthalten) übernimmt.
  2. Cache-Schlüssel: Spring baut aus der Konfiguration einen Schlüssel: Konfigurationsklassen, aktive Profile, @TestPropertySource, Context Customizer. @MockitoBean-Felder gehören über die Customizer dazu.
  3. Im Cache? Gibt es den Schlüssel schon, nimmt Spring den fertigen Kontext. Das kostet fast nichts.
  4. Starten: Sonst startet Spring einen neuen Kontext. Container-Beans und @ServiceConnection-Container starten vor allen anderen Beans.
  5. Injizieren: Spring setzt @Autowired-Felder in die Testinstanz. Mocks ersetzen die echten Beans.
  6. Test läuft: Ein @Transactional-Test (oder @DataJpaTest) läuft in einer Transaktion.
  7. Aufräumen: Nach jedem Test: Rollback der Transaktion, Mocks werden zurückgesetzt.
  8. Kontext bleibt: Der Kontext bleibt für die nächste Klasse im Cache. Standard sind maximal 32 Kontexte, danach räumt LRU auf. Seit Spring Framework 7 können ungenutzte Kontexte pausiert werden.

3. Beispiel: Web-Slice und JPA-Slice mit Testcontainers

@WebMvcTest(OrderController.class)
class OrderControllerTest {

  @Autowired MockMvcTester mvc;
  @MockitoBean OrderService service;               // ersetzt die echte Bean

  @Test
  void returnsOrder() {
    given(service.find(7L)).willReturn(new OrderDto(7L, "OPEN"));
    assertThat(mvc.get().uri("/orders/7"))
        .hasStatusOk()
        .bodyJson().extractingPath("$.status").isEqualTo("OPEN");
  }

  @Test
  void unknownOrderGives404() {
    given(service.find(99L)).willThrow(new OrderNotFoundException(99L));
    assertThat(mvc.get().uri("/orders/99")).hasStatus(HttpStatus.NOT_FOUND);
  }
}

@DataJpaTest
@Testcontainers
class OrderRepositoryTest {

  @Container @ServiceConnection
  static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17");

  @Autowired OrderRepository repo;
  @Autowired TestEntityManager em;

  @Test
  void findsOpenOrders() {
    em.persist(new Order("OPEN"));
    em.persist(new Order("CLOSED"));
    em.flush();
    assertThat(repo.findByStatus("OPEN")).hasSize(1);
  }
}

  1. @WebMvcTest lädt nur den Controller, Advice und MVC-Infrastruktur. Der Service ist ein Mock. Der 404-Test prüft auch den @ControllerAdvice.
  2. @ServiceConnection liest URL, Benutzer und Passwort aus dem Container. Keine spring.datasource.*-Properties nötig.
  3. @DataJpaTest ersetzt die DataSource standardmässig durch eine eingebettete Test-DB. Eine Container-Verbindung über @ServiceConnection gilt aber als Test-Datenbank und bleibt.
  4. Jeder Test in @DataJpaTest rollt am Ende zurück. Die Daten stören den nächsten Test nicht.
  5. Zwei verschiedene Konfigurationen ergeben zwei Kontexte im Cache (missCount = 2).

4. Details, die Interviewer fragen

  1. @SpringBootTest webEnvironment: MOCK (Standard, kein Server), RANDOM_PORT (echter Server auf freiem Port), DEFINED_PORT, NONE (keine Web-Umgebung).
  2. Rollback mit echtem Server: Bei RANDOM_PORT laufen Client und Server in verschiedenen Threads. Die Server-Transaktion rollt nicht zurück, auch wenn der Test @Transactional ist.
  3. MockMvc: Testet Spring MVC ohne echten HTTP-Server. Im @WebMvcTest automatisch. In @SpringBootTest nur mit @AutoConfigureMockMvc. MockMvcTester ist die AssertJ-Variante.
  4. @WebMvcTest scannt: @Controller, @ControllerAdvice, Converter, Filter, HandlerInterceptor, WebMvcConfigurer und einige mehr. Keine @Service, @Repository oder normalen @Component.
  5. @DataJpaTest: Scannt Entities, baut Repositories, ist transaktional mit Rollback und loggt SQL. Mit @AutoConfigureTestDatabase(replace = Replace.NONE) behält man die konfigurierte DB.
  6. Weitere Slices: @JsonTest, @WebFluxTest, @DataJdbcTest, @JdbcTest, @RestClientTest und andere. Mehrere Slice-Annotationen in einem Test sind nicht unterstützt.
  7. @MockitoBean: Ersetzt eine Bean im Kontext durch einen Mockito-Mock. Kommt aus Spring Framework (seit 6.2), nicht aus Boot. @MockitoSpyBean wickelt die echte Bean in einen Spy.
  8. @MockBean: Die alte Boot-Annotation. Seit Boot 3.4 veraltet, in Boot 4.0 entfernt.
  9. Mocks und Cache: Jede andere Kombination von @MockitoBean ergibt einen anderen Cache-Schlüssel, also einen neuen Kontext. Darum Mocks in gemeinsamen Basisklassen bündeln.
  10. @ServiceConnection: Seit Boot 3.1. Es erzeugt ConnectionDetails aus dem Container, z. B. JdbcConnectionDetails für PostgreSQL. Unterstützt u. a. PostgreSQL, Kafka, Redis, MongoDB, RabbitMQ.
  11. @DynamicPropertySource: Die flexiblere Alternative. Man setzt Properties selbst: registry.add("spring.datasource.url", pg::getJdbcUrl).
  12. Container-Lebensdauer: Mit @Testcontainers und statischem @Container stoppt der Container nach der Klasse. Der gecachte Kontext zeigt dann auf einen toten Container. Besser: Container als Spring-Bean oder @ImportTestcontainers, dann lebt er so lange wie der Kontext.
  13. @DirtiesContext: Wirft den Kontext aus dem Cache. Teuer, weil der nächste Test neu startet. Nur bei echtem Zustand im Kontext.
  14. Cache-Grösse: Standard 32, änderbar mit spring.test.context.cache.maxSize.
  15. Boot 4 Änderungen: Test-Starter pro Technologie (z. B. spring-boot-starter-webmvc-test, spring-boot-starter-data-jpa-test). Neue Pakete wie org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest. TestRestTemplate braucht @AutoConfigureTestRestTemplate. Neu: RestTestClient.

5. Vergleich

  • Unit-Test: schnell, präzise, aber keine Verdrahtung, kein JSON, keine Security.
  • @WebMvcTest: Controller, Validierung, JSON, Fehler-Mapping, Security-Regeln. Ohne DB.
  • @DataJpaTest: Queries, Mappings, Constraints. Ohne Web.
  • @SpringBootTest (MOCK): ganzer Kontext, MockMvc, ohne Netzwerk.
  • @SpringBootTest (RANDOM_PORT): echter HTTP-Server, echte Filter. Am realistischsten, am langsamsten, kein automatischer Rollback.
  • H2 vs Testcontainers: H2 ist schnell, aber ein anderer SQL-Dialekt. Testcontainers testet die echte Datenbank, braucht aber Docker.
  • @MockitoBean vs @MockBean: gleiche Idee. @MockitoBean ist der Nachfolger im Framework, @MockBean gibt es in Boot 4 nicht mehr.

6. In der Produktion (der Test-Pipeline)

  1. Build dauert 20 Minuten: Jede Testklasse hat andere Mocks oder Properties. Spring startet Dutzende Kontexte. Lösung: wenige gemeinsame Basisklassen, Cache-Statistik prüfen, @DirtiesContext entfernen.
  2. Tests grün, Produktion kaputt: H2 akzeptiert SQL, das PostgreSQL ablehnt, oder umgekehrt. Lösung: Testcontainers mit derselben DB-Version wie in Produktion.
  3. Flaky Tests mit Daten: RANDOM_PORT-Tests rollen nicht zurück. Daten aus Test A stören Test B. Lösung: Daten explizit löschen, eindeutige Testdaten.
  4. „Connection refused“ in späteren Klassen: Der Container wurde nach der ersten Klasse gestoppt, der Kontext im Cache zeigt noch darauf. Lösung: Container als Bean oder geteiltes Interface mit @ImportTestcontainers.
  5. Docker in CI: Testcontainers braucht einen erreichbaren Docker-Daemon. Lösung: Docker-Version in CI festlegen, Images aus einer eigenen Registry spiegeln.
  6. Zu viel Speicher in CI: Viele Kontexte und Container gleichzeitig. Lösung: Cache-Grösse senken, Container begrenzen, schwere Tests seriell.
  7. Upgrade auf Boot 4 bricht Tests: @MockBean entfernt, TestRestTemplate nicht mehr automatisch, neue Pakete. Lösung: zuerst in 3.4/3.5 auf @MockitoBean umstellen.

7. Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.test.context.cache=DEBUG: Cache-Statistik mit Treffern und Fehlschlägen.
  • Startmeldung zählen: Wie oft erscheint das Spring-Banner oder „Started … in“ im Testlog? So oft wurde ein Kontext gebaut.
  • spring.test.mockmvc.print oder .andDo(print()): Request und Response im Log.
  • debug=true im Test: Condition Evaluation Report, welche Auto-Configuration lief.
  • Testcontainers-Log und docker ps: läuft der Container, welcher Port.
  • Build-Scan / Surefire-Report: langsamste Testklassen finden.

8. Senior-Punkte

  1. Kleinster Kontext, der das Risiko abdeckt. Fachlogik als Unit-Test, Web als Slice, Integration mit Testcontainers. Nicht alles als @SpringBootTest.
  2. Context Caching ist eine Architekturfrage. Wenige stabile Testkonfigurationen sind schneller als viele kleine Unterschiede.
  3. Echte Datenbank testen. Migrationen (Flyway), Constraints und native Queries zeigen Fehler nur gegen die echte DB.
  4. Mocks nur an Systemgrenzen. Zu viele Mocks testen die Mocks, nicht das System.
  5. Upgrade früh vorbereiten: @MockitoBean, Testcontainers mit @ServiceConnection und neue Test-Starter senken das Risiko beim Wechsel auf Boot 4.
  6. Tests sind Teil der Pipeline-Leistung. Laufzeit messen und als Qualitätsziel behandeln.

10. Fallen

  • „@SpringBootTest startet einen Server.“ → Falsch. Standard ist MOCK ohne Server. Nur RANDOM_PORT oder DEFINED_PORT starten einen.
  • „@Transactional im Test rollt immer zurück.“ → Falsch. Nicht bei echtem Server: Der Server arbeitet in einem eigenen Thread.
  • „@WebMvcTest lädt meine Services.“ → Falsch. Nur Web-Komponenten. Services muss man mocken.
  • „@MockBean geht in Boot 4 noch.“ → Falsch. Entfernt. Ersatz: @MockitoBean.
  • „Mocks sind gratis.“ → Falsch. Jede neue Mock-Kombination kostet einen neuen Kontext.
  • „@DirtiesContext macht Tests sicherer.“ → Nur bei echtem Zustand. Sonst macht es die Suite nur langsam.

11. Fragen

@SpringBootTest vs @WebMvcTest?

@SpringBootTest lädt den ganzen Kontext. @WebMvcTest nur die Web-Schicht mit MockMvc; Services ersetzt man mit @MockitoBean.

Was ist ein Test-Slice?

Ein Test mit einem kleinen Kontext für eine Schicht. Er lädt nur passende Komponenten und Auto-Configurations, z. B. @WebMvcTest oder @DataJpaTest.

Welche webEnvironment-Modi gibt es?

MOCK (Standard, kein Server), RANDOM_PORT, DEFINED_PORT und NONE.

Was lädt @WebMvcTest?

Controller, ControllerAdvice, Converter, Filter, Interceptors und WebMvcConfigurer. Keine Services, Repositories oder normalen Components.

Was macht @DataJpaTest?

Es baut Entities, Repositories und eine Test-DB. Jeder Test ist transaktional und rollt zurück. SQL wird geloggt.

Wie testen Sie @DataJpaTest gegen PostgreSQL statt H2?

Mit einem PostgreSQL-Testcontainer und @ServiceConnection. Oder mit @AutoConfigureTestDatabase(replace = NONE) und einer konfigurierten DB.

Was ist MockMvc?

Ein Werkzeug, das Spring MVC ohne echten Server aufruft. Es prüft Status, Header und JSON. MockMvcTester ist die AssertJ-Variante.

Wie bekommen Sie MockMvc in einem @SpringBootTest?

Mit @AutoConfigureMockMvc. In @WebMvcTest ist es automatisch da.

Was ist @MockitoBean?

Eine Annotation aus Spring Framework (seit 6.2). Sie ersetzt eine Bean im Test-Kontext durch einen Mockito-Mock.

@MockitoBean vs @MockBean?

Gleiche Idee. @MockBean kam aus Boot, ist seit 3.4 veraltet und in Boot 4 entfernt. @MockitoBean ist der Nachfolger.

@MockitoBean vs @Mock?

@Mock erzeugt nur ein Mock-Objekt im Unit-Test. @MockitoBean legt den Mock als Bean in den Spring-Kontext.

Wie funktioniert der Context Cache?

Spring baut aus der Testkonfiguration einen Schlüssel. Gleicher Schlüssel heisst gleicher Kontext. Standard maximal 32 Kontexte, danach LRU.

Was ändert den Cache-Schlüssel?

Konfigurationsklassen, Profile, Test-Properties, Context Customizer und damit auch @MockitoBean-Kombinationen.

Wann nutzen Sie @DirtiesContext?

Nur wenn ein Test den Kontext wirklich verändert, z. B. einen Singleton-Zustand. Es erzwingt einen Neustart und kostet Zeit.

Was macht @ServiceConnection?

Es liest Verbindungsdaten aus einem Testcontainer und erzeugt ConnectionDetails-Beans. Properties wie spring.datasource.url sind nicht nötig. Seit Boot 3.1.

@ServiceConnection vs @DynamicPropertySource?

@ServiceConnection ist automatisch für bekannte Container. @DynamicPropertySource setzt Properties von Hand und funktioniert für alles.

Warum sollte ein Container nicht nach der Testklasse stoppen?

Der gecachte Kontext zeigt sonst auf einen toten Container. Besser lebt der Container so lange wie der Kontext, als Bean oder mit @ImportTestcontainers.

Rollt ein @Transactional-Test mit RANDOM_PORT zurück?

Nein, nicht auf Server-Seite. Der Request läuft in einem anderen Thread mit eigener Transaktion.

Was ändert sich beim Testen mit Boot 4?

Test-Starter pro Modul, neue Pakete für Slices, @MockBean entfernt, TestRestTemplate nur mit @AutoConfigureTestRestTemplate, neuer RestTestClient, Testcontainers 2.

Was ist RestTestClient?

Eine nicht-reaktive Variante von WebTestClient aus Spring Framework 7. Sie kann gegen MockMvc oder einen laufenden Server testen.

Wie testen Sie Security-Regeln eines Controllers?

Im @WebMvcTest mit spring-security-test: @WithMockUser oder .with(jwt()). Pro Regel Tests für 200, 401 und 403.

Wie finden Sie heraus, warum die Testsuite langsam ist?

Cache-Statistik auf DEBUG, Kontext-Starts im Log zählen, langsamste Klassen im Report suchen. Meist sind es zu viele verschiedene Kontexte.

Szenario: Die Testsuite braucht 25 Minuten, im Log starten 40 Kontexte. Was tun Sie?

Unterschiede in Mocks, Properties und Profilen zusammenführen, gemeinsame Basisklassen bauen, @DirtiesContext entfernen. Dann die Cache-Statistik erneut prüfen.

Szenario: Alle Tests sind grün, aber in Produktion schlägt eine native Query fehl. Warum?

Die Tests liefen gegen H2 mit anderem SQL-Dialekt. Lösung: Repository-Tests mit Testcontainers und derselben PostgreSQL-Version wie in Produktion.

Szenario: Ab der dritten Testklasse kommt „Connection refused“ zur Datenbank. Woran liegt es?

Der Container wurde nach einer Klasse gestoppt, der gecachte Kontext nutzt ihn noch. Lösung: Container als Spring-Bean oder geteilt über @ImportTestcontainers.
