Spring Security: Filter Chain, Authentication, Authorization

Kern: Spring Security ist eine Kette von Servlet-Filtern vor dem DispatcherServlet. Sie löst zwei Fragen: Wer bist du? (Authentication) und Darfst du das? (Authorization). Das Ergebnis der Anmeldung liegt im SecurityContext, pro Request im aktuellen Thread.

1. Wo sitzt Spring Security?

  1. DelegatingFilterProxy: Ein normaler Servlet-Filter im Container. Er sucht die Spring-Bean springSecurityFilterChain und gibt den Request weiter. Er sucht sie erst bei Bedarf, also nach dem Start des Containers.
  2. FilterChainProxy: Die Spring-Bean hinter dem Namen. Sie wählt die passende SecurityFilterChain, leert am Ende den SecurityContext und prüft Requests mit der HttpFirewall.
  3. SecurityFilterChain: Eine Liste von Security-Filtern für eine Gruppe von Requests. Es gibt mehrere Ketten. Nur die erste passende läuft.
  4. DispatcherServlet: Kommt erst nach allen Security-Filtern. Ein abgewiesener Request erreicht keinen Controller.
  5. Method Security: Eine zweite Ebene über AOP-Proxies. Beispiel: @PreAuthorize("hasRole('ADMIN')") an einer Service-Methode.

2. Die Reise eines Requests durch die Kette (die Geschichte zum Merken)

  1. Context laden: Der SecurityContextHolderFilter lädt einen vorhandenen SecurityContext, z. B. aus der HTTP-Session. Bei einer stateless API gibt es keinen.
  2. Auth-Filter: Ein Filter liest die Credentials. Beispiele: UsernamePasswordAuthenticationFilter (Formular), BasicAuthenticationFilter (Header), BearerTokenAuthenticationFilter (JWT). Er baut daraus ein unauthentifiziertes Authentication-Objekt.
  3. AuthenticationManager: Der Filter übergibt an den ProviderManager. Er fragt seine AuthenticationProvider der Reihe nach. Beispiel: DaoAuthenticationProvider lädt den User über UserDetailsService und prüft das Passwort mit dem PasswordEncoder.
  4. SecurityContextHolder: Bei Erfolg kommt das authentifizierte Authentication-Objekt in den SecurityContext. Er liegt standardmässig in einem ThreadLocal.
  5. Anonymous: Hat sich niemand angemeldet, setzt der AnonymousAuthenticationFilter einen anonymen Benutzer.
  6. AuthorizationFilter: Der letzte Filter. Er fragt einen AuthorizationManager: Passt die Regel für diese URL zu den Authorities?
  7. Fehler: Eine AuthenticationException oder AccessDeniedException fängt der ExceptionTranslationFilter. Nicht angemeldet: AuthenticationEntryPoint (401 oder Redirect zum Login). Angemeldet, aber nicht erlaubt: AccessDeniedHandler (403).

3. Beispiel: zwei Ketten und Method Security

@Configuration
@EnableMethodSecurity
class SecurityConfig {

  @Bean @Order(1)
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/api/public/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(c -> c.disable());          // nur weil keine Cookies genutzt werden
    return http.build();
  }

  @Bean @Order(2)
  SecurityFilterChain web(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();
  }

  @Bean
  UserDetailsService users(PasswordEncoder enc) {
    return new InMemoryUserDetailsManager(
        User.withUsername("anna").password(enc.encode("pw")).roles("USER").build(),
        User.withUsername("ben").password(enc.encode("pw")).roles("ADMIN").build());
  }

  @Bean PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
  }
}

@Service
class ReportService {
  @PreAuthorize("hasRole('ADMIN') or #owner == authentication.name")
  Report load(String owner) { ... }
}

4. Details, die Interviewer fragen

  1. Warum DelegatingFilterProxy? Der Servlet-Container registriert Filter, bevor Spring Beans existieren. Der Proxy schliesst diese Lücke. Er sucht die Bean erst beim ersten Request.
  2. Mehrere SecurityFilterChain-Beans: Jede hat einen securityMatcher. Die Reihenfolge bestimmt @Order. Die allgemeinste Kette (/**) kommt zuletzt, sonst fängt sie alles.
  3. Filter-Reihenfolge: Die Standardkette beginnt mit DisableEncodeUrlFilter, SecurityContextHolderFilter, HeaderWriterFilter, CsrfFilter, LogoutFilter. Dann kommen die Auth-Filter. Am Ende stehen ExceptionTranslationFilter und AuthorizationFilter.
  4. Authentication-Objekt: Es hat principal (wer), credentials (meist Passwort, nach Erfolg gelöscht) und authorities (Rechte). Es ist zuerst Eingabe für den Manager, danach der angemeldete Benutzer.
  5. ProviderManager: Er hält eine Liste von Providern. Kann keiner den Typ verarbeiten, kommt ProviderNotFoundException. Optional fragt er einen Parent-Manager.
  6. AuthenticationProvider: Einer pro Anmeldeart. DaoAuthenticationProvider für Benutzername und Passwort, JwtAuthenticationProvider für JWT.
  7. GrantedAuthority: Ein Recht als String. Rollen haben den Präfix ROLE_. hasRole('ADMIN') ergänzt den Präfix, hasAuthority('ROLE_ADMIN') nicht.
  8. SecurityContextHolder: Standard ist MODE_THREADLOCAL. MODE_INHERITABLETHREADLOCAL gibt den Kontext an neu erzeugte Threads weiter. MODE_GLOBAL ist für Desktop-Programme.
  9. Context speichern: Seit Spring Security 6 speichert der SecurityContextHolderFilter nicht mehr automatisch. Eigener Login-Code muss SecurityContextRepository#saveContext aufrufen.
  10. AuthorizationManager: Die moderne Autorisierungs-API. Sie ersetzt AccessDecisionManager und Voter. In Spring Security 7 heisst die Methode authorize statt check, und die alte Access-API liegt im Modul spring-security-access.
  11. Method Security: @EnableMethodSecurity aktiviert @PreAuthorize, @PostAuthorize, @PreFilter, @PostFilter. @Secured und JSR-250 nur mit Opt-in. Es ersetzt @EnableGlobalMethodSecurity.
  12. Method Security und Proxies: Es ist AOP. Ein Aufruf innerhalb derselben Klasse (this.load()) geht nicht durch den Proxy und wird nicht geprüft.
  13. CSRF: Schützt Cookie-basierte Sessions vor fremden Formularen. Eine API nur mit Bearer-Token im Header braucht ihn nicht. Spring Security 7 hat csrf.spa() für Single-Page-Apps.
  14. Spring Boot Default: Gibt es keine eigene SecurityFilterChain, sichert Boot alles mit Form Login und HTTP Basic. Ohne eigenen User erzeugt Boot einen User mit zufälligem Passwort im Log.
  15. Versionen: Spring Security 6 entfernte WebSecurityConfigurerAdapter, man deklariert SecurityFilterChain-Beans. Spring Security 7 entfernte and(), authorizeRequests sowie AntPathRequestMatcher und MvcRequestMatcher zugunsten von PathPatternRequestMatcher.

5. Vergleich

  • Servlet-Filter (Security) vs HandlerInterceptor: Filter laufen vor dem DispatcherServlet, auch für statische Inhalte. Interceptors kennen den Controller. Security gehört in Filter.
  • URL-Regeln vs Method Security: URL-Regeln sind grob und zentral. Method Security ist fein und nah an der Fachlogik, z. B. „nur der Besitzer“. Gut ist beides.
  • Session vs stateless: Session speichert den Context zwischen Requests (Cookie, CSRF nötig). Stateless authentifiziert jeden Request neu, z. B. mit JWT.
  • 401 vs 403: 401 heisst „nicht angemeldet“. 403 heisst „angemeldet, aber nicht erlaubt“.
  • hasRole vs hasAuthority: hasRole ergänzt ROLE_. hasAuthority vergleicht exakt, z. B. SCOPE_read.
  • @PreAuthorize vs @Secured: @PreAuthorize kann SpEL mit Parametern. @Secured nur feste Rollen.

6. In der Produktion

  1. Eigener Filter läuft zweimal: Ein Filter als @Component registriert Boot zusätzlich im Container. Er läuft dann einmal dort und einmal in der Security-Kette. Lösung: kein @Component, oder FilterRegistrationBean mit setEnabled(false).
  2. Falsche Ketten-Reihenfolge: Die /**-Kette ohne @Order fängt auch /api/**. API-Clients bekommen dann Login-Redirects statt 401. Lösung: securityMatcher und @Order klar setzen.
  3. SecurityContext fehlt in @Async: Der neue Thread hat ein leeres ThreadLocal. Lösung: DelegatingSecurityContextExecutor oder DelegatingSecurityContextAsyncTaskExecutor.
  4. @PreAuthorize wirkt nicht: Aufruf in derselben Klasse, private Methode oder @EnableMethodSecurity fehlt. Lösung: über eine andere Bean aufrufen, Test für 403 schreiben.
  5. 403 bei POST trotz Login: CSRF ist aktiv, der Client schickt kein Token. Lösung: Token im Client mitsenden, oder bei reiner Bearer-API CSRF bewusst ausschalten.
  6. Langsamer Login: BCrypt oder Argon2 sind absichtlich teuer. Bei Basic Auth auf jedem Request kostet das CPU. Lösung: Token oder Session statt Passwort pro Request.
  7. Fehlende Regel öffnet Pfade: Ohne anyRequest() am Ende ist ein neuer Endpoint nicht geschützt. Lösung: immer mit anyRequest().authenticated() oder denyAll() abschliessen.

7. Diagnose: Werkzeuge und Befehle

  • Filterliste beim Start: Spring Security loggt die Filter jeder Kette auf DEBUG.
  • logging.level.org.springframework.security=TRACE: zeigt jeden Filter pro Request und warum er abweist.
  • @EnableWebSecurity(debug = true): druckt Request und Filterkette. Nur lokal, nie in Produktion.
  • curl -i: Status und WWW-Authenticate-Header prüfen.
  • Tests: spring-security-test mit @WithMockUser, .with(user("anna").roles("USER")), .with(jwt()) und csrf() in MockMvc.
  • Events: AuthenticationSuccessEvent, AbstractAuthenticationFailureEvent, AuthorizationDeniedEvent für Audit-Logs.
  • Actuator /actuator/mappings: welche Endpoints es gibt, um sie mit den Regeln zu vergleichen.

8. Senior-Punkte

  1. Default deny. Jede Kette endet mit anyRequest(). Neue Endpoints sind dann automatisch geschützt.
  2. Zwei Ebenen: URL-Regeln für grobe Grenzen, Method Security für Fachregeln. Fachregeln gehören nicht in Controller-Code.
  3. Getrennte Ketten pro Client-Typ: API (stateless, 401) und Browser (Session, Redirect) haben andere Bedürfnisse.
  4. CSRF nicht reflexartig ausschalten. Nur wenn wirklich keine Cookies authentifizieren.
  5. Security testen wie Fachlogik: Für jede Regel ein Test für 200, 401 und 403.
  6. Upgrade-Pfad planen: Lambda-DSL, authorizeHttpRequests und @EnableMethodSecurity schon in 6.x nutzen. Dann ist der Schritt auf 7 klein.

10. Fallen

  • „Spring Security ist ein HandlerInterceptor.“ → Falsch. Es ist eine Kette von Servlet-Filtern vor dem DispatcherServlet.
  • „Alle SecurityFilterChains laufen nacheinander.“ → Falsch. Nur die erste passende Kette läuft.
  • „hasRole('ROLE_ADMIN') ist richtig.“ → Falsch. hasRole ergänzt den Präfix selbst. Richtig: hasRole('ADMIN') oder hasAuthority('ROLE_ADMIN').
  • „401 und 403 sind dasselbe.“ → Falsch. 401: nicht angemeldet. 403: angemeldet, aber ohne Recht.
  • „@PreAuthorize schützt jeden Aufruf.“ → Falsch. Nur Aufrufe über den Proxy. Selbstaufrufe sind ungeschützt.
  • „Der SecurityContext ist überall verfügbar.“ → Falsch. Er liegt im ThreadLocal. Andere Threads sehen ihn nicht automatisch.

11. Fragen

Wie ist Spring Security in eine Web-Anwendung eingebunden?

Über einen Servlet-Filter DelegatingFilterProxy. Er gibt an die Bean FilterChainProxy weiter, die die passende SecurityFilterChain ausführt.

Warum gibt es DelegatingFilterProxy?

Der Container registriert Filter vor dem Spring-Kontext. Der Proxy sucht die Spring-Bean erst bei Bedarf und verbindet so Container und Spring.

Was macht FilterChainProxy?

Er wählt die erste passende SecurityFilterChain, wendet die HttpFirewall an und leert am Ende den SecurityContext.

Was ist eine SecurityFilterChain?

Eine Bean mit einem RequestMatcher und einer Liste von Security-Filtern. Man baut sie mit HttpSecurity.

Wie funktionieren mehrere Ketten?

Jede Kette hat einen securityMatcher, die Reihenfolge kommt aus @Order. Nur die erste passende Kette läuft.

Was ist das Authentication-Objekt?

Es enthält principal, credentials und authorities. Vor der Anmeldung ist es die Eingabe, danach der angemeldete Benutzer.

AuthenticationManager vs AuthenticationProvider?

Der Manager ist die API, meist ein ProviderManager. Er delegiert an Provider, von denen jeder eine Anmeldeart prüft.

Was macht DaoAuthenticationProvider?

Er lädt den User über UserDetailsService und vergleicht das Passwort mit dem PasswordEncoder.

Wo liegt der angemeldete Benutzer?

Im SecurityContext im SecurityContextHolder. Standard ist ein ThreadLocal pro Request-Thread.

Was macht der ExceptionTranslationFilter?

Er übersetzt Security-Exceptions in HTTP. Nicht angemeldet: AuthenticationEntryPoint. Kein Recht: AccessDeniedHandler mit 403.

Was ist der AuthorizationFilter?

Der letzte Filter der Kette. Er fragt einen AuthorizationManager, ob die Authentication die URL-Regel erfüllt.

hasRole vs hasAuthority?

hasRole('ADMIN') prüft ROLE_ADMIN. hasAuthority vergleicht den String exakt, z. B. SCOPE_read.

Wie aktivieren Sie Method Security?

Mit @EnableMethodSecurity. Danach wirken @PreAuthorize, @PostAuthorize, @PreFilter und @PostFilter. Boot aktiviert es nicht automatisch.

@PreAuthorize vs @PostAuthorize?

@PreAuthorize prüft vor dem Aufruf. @PostAuthorize prüft das Ergebnis mit returnObject, die Methode ist dann aber schon gelaufen.

Warum wirkt @PreAuthorize bei einem Selbstaufruf nicht?

Method Security ist AOP über einen Proxy. Ein Aufruf mit this geht am Proxy vorbei.

Wann darf man CSRF ausschalten?

Wenn keine Cookies oder Sessions authentifizieren, z. B. eine reine API mit Bearer-Token im Header.

Wie fügen Sie einen eigenen Filter hinzu?

Mit addFilterBefore, addFilterAfter oder addFilterAt in HttpSecurity. Nicht zusätzlich als @Component, sonst läuft er doppelt.

Was passiert ohne eigene Security-Konfiguration in Spring Boot?

Boot schützt alle Endpoints mit Form Login und HTTP Basic. Es erzeugt einen User mit zufälligem Passwort im Log.

Wie bekommt ein @Async-Thread den SecurityContext?

Mit einem DelegatingSecurityContextAsyncTaskExecutor, der den Kontext in den neuen Thread kopiert.

Was hat sich in Spring Security 6 und 7 geändert?

6 entfernte WebSecurityConfigurerAdapter, man nutzt SecurityFilterChain-Beans. 7 entfernte and(), authorizeRequests und AntPathRequestMatcher und bringt Multi-Faktor-Authentifizierung.

Wie testen Sie Security-Regeln?

Mit MockMvc und spring-security-test: @WithMockUser oder .with(user(...)). Pro Regel prüfe ich 200, 401 und 403.

Wie debuggen Sie eine unerwartete 403?

Logging auf TRACE für org.springframework.security. Dann sehe ich die gewählte Kette, den Filter und die fehlende Authority oder das CSRF-Token.

Szenario: Die API antwortet Clients mit einem 302 auf /login statt 401. Warum?

Die Browser-Kette mit Form Login fängt die API-Requests. Lösung: eigene API-Kette mit securityMatcher("/api/**") und höherer Priorität.

Szenario: Ein neuer Admin-Endpoint ist ohne Login erreichbar. Wie kann das passieren?

Eine zu breite permitAll-Regel steht vor der Admin-Regel, oder anyRequest() fehlt. Die erste passende Regel gewinnt. Lösung: Reihenfolge prüfen, Default deny, Test für 401.

Szenario: Im Audit-Log fehlt bei asynchroner Verarbeitung der Benutzer. Was tun Sie?

Der SecurityContext ist ThreadLocal und fehlt im Worker-Thread. Ich nutze einen Delegating-Executor oder gebe den Benutzer explizit als Parameter mit.
