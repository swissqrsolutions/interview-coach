AOP und Proxies

Kern: AOP (Aspect-Oriented Programming) ist eine Technik, um Querschnittsthemen wie Transaktionen, Security oder Logging an einer Stelle zu schreiben. Spring AOP setzt das mit einem Proxy um: ein Stellvertreter-Objekt vor der echten Bean, das zusätzlichen Code vor und nach dem Aufruf ausführt. Der Proxy ist entweder ein JDK Dynamic Proxy (über Interfaces) oder ein CGLIB-Proxy (über eine Unterklasse).

1. Wo sitzt der Proxy?

  1. Aufrufer: Der Controller hält eine Referenz auf OrderService. In Wahrheit ist es der Proxy.
  2. Proxy: Er hat dieselben Methoden wie die Bean. Er führt eine Kette von Interceptors aus, also Code vor und nach dem Aufruf.
  3. Interceptors: Jeder Advice (Security, Transaktion, eigener Aspekt) ist ein Glied der Kette. Die Reihenfolge kommt aus @Order.
  4. Target: Das echte Objekt mit der Business-Logik. Es weiss nichts vom Proxy.
  5. Auto-Proxy-Creator: Ein BeanPostProcessor. Er prüft nach der Initialisierung jeder Bean, ob ein Pointcut passt. Wenn ja, ersetzt er die Bean durch den Proxy.

2. Die Reise eines Methodenaufrufs (die Geschichte zum Merken)

  1. Aufruf: Der Controller ruft service.placeOrder() auf. service zeigt auf den Proxy.
  2. Proxy: Er holt die Interceptor-Kette für genau diese Methode. Passt kein Pointcut, ruft er das Target direkt auf.
  3. Hinweg: Der Advice mit der höchsten Priorität läuft zuerst, z. B. Security. Jeder ruft proceed() für das nächste Glied auf.
  4. Target: Am Ende der Kette läuft die echte Methode.
  5. Self-Invocation: Ruft placeOrder() intern this.audit() auf, ist this das Target, nicht der Proxy. Der Advice von audit() läuft nicht.
  6. Rückweg: Die Advices laufen in umgekehrter Reihenfolge. Der Advice mit der höchsten Priorität läuft zuletzt.
  7. Ergebnis: Der Proxy gibt Rückgabewert oder Exception an den Controller weiter.

3. Beispiel: JDK Dynamic Proxy und Self-Invocation in reinem Java

interface OrderService { void placeOrder(); void audit(); }

class OrderServiceImpl implements OrderService {
  public void placeOrder() { System.out.println("  target: placeOrder()"); this.audit(); }
  public void audit()      { System.out.println("  target: audit()"); }
}

OrderService target = new OrderServiceImpl();
InvocationHandler h = (proxy, m, a) -> {            // das ist der "Advice"
  System.out.println("  advice: before " + m.getName());
  try { return m.invoke(target, a); }
  finally { System.out.println("  advice: after  " + m.getName()); }
};
OrderService proxy = (OrderService) Proxy.newProxyInstance(
    OrderService.class.getClassLoader(), new Class<?>[] { OrderService.class }, h);

// 1) Klasse prüfen  2) proxy.audit()  3) proxy.placeOrder()  4) Cast auf Klasse
1) Proxy-Klasse
  class      = $Proxy0
  superclass = java.lang.reflect.Proxy
  instanceof OrderService     = true
  instanceof OrderServiceImpl = false
2) Aufruf von aussen: proxy.audit()
  advice: before audit
  target: audit()
  advice: after  audit
3) Aufruf von aussen: proxy.placeOrder()
  advice: before placeOrder
  target: placeOrder()
  target: audit()
  advice: after  placeOrder
4) Cast auf die Klasse
  ClassCastException

Echte Ausgabe, Java 17.0.3.1 (ohne Spring). Spring nutzt für JDK-Proxies genau diesen Mechanismus, mit einem eigenen InvocationHandler.

  1. Der JDK-Proxy ist eine neue Klasse $Proxy0. Sie erbt von java.lang.reflect.Proxy und implementiert nur das Interface.
  2. Darum ist der Proxy kein OrderServiceImpl. Wer die Klasse statt des Interfaces injiziert, bekommt in Spring einen Fehler (BeanNotOfRequiredTypeException).
  3. Bei Aufruf 2 läuft der Advice um audit().
  4. Bei Aufruf 3 läuft der Advice nur um placeOrder(). Das innere this.audit() geht am Proxy vorbei. Das ist das Self-Invocation-Problem. Mit @Transactional auf audit() gäbe es hier keine eigene Transaktion.

4. Details, die Interviewer fragen

  1. Begriffe: Aspect: Modul für ein Querschnittsthema. Join Point: Stelle im Ablauf, in Spring AOP immer ein Methodenaufruf. Pointcut: Ausdruck, der Join Points auswählt. Advice: Code, der dort läuft. Weaving: Verbinden von Aspekt und Code.
  2. Advice-Typen: @Before, @AfterReturning (nur bei Erfolg), @AfterThrowing (nur bei Exception), @After (immer, wie finally), @Around (umschliesst den Aufruf, muss proceed() aufrufen).
  3. Pointcut-Ausdrücke: execution(* ch.demo..*Service.*(..)) für Methoden-Signaturen. @annotation(Audited) für Annotationen. within(ch.demo.web..*) für Pakete. bean(*Service) ist nur in Spring AOP verfügbar.
  4. JDK Dynamic Proxy: eingebaut ins JDK. Nur Interface-Methoden. Der Proxy ist keine Instanz der Klasse. Core Spring nutzt ihn, wenn die Bean mindestens ein Interface hat.
  5. CGLIB-Proxy: eine zur Laufzeit erzeugte Unterklasse. CGLIB ist in spring-core eingebettet. Klassenname enthält $$SpringCGLIB$$.
  6. Grenzen von CGLIB: final-Klassen gehen nicht. final- und private-Methoden bekommen keinen Advice. Der Konstruktor läuft dank Objenesis nicht doppelt.
  7. Spring Boot Standard: spring.aop.proxy-target-class=true. Boot nutzt also CGLIB, auch wenn die Bean Interfaces hat. Core Spring ohne Boot bevorzugt JDK-Proxies.
  8. @Proxyable (seit 7.0): setzt den Proxy-Typ pro Bean, z. B. @Proxyable(INTERFACES). Seit 7.0 folgen auch @EnableAsync und ähnliche der globalen Einstellung.
  9. Self-Invocation: Ein Aufruf über this geht nicht durch den Proxy. Lösungen in dieser Reihenfolge: Code in eine andere Bean verschieben, Self-Injection (über @Lazy oder ObjectProvider), AopContext.currentProxy() mit exposeProxy = true (stark abgeraten), AspectJ-Weaving.
  10. Reihenfolge zwischen Aspekten: Niedriger @Order-Wert = höhere Priorität. Höchste Priorität läuft auf dem Hinweg zuerst, auf dem Rückweg zuletzt. Ohne @Order ist die Reihenfolge undefiniert.
  11. Reihenfolge in einem Aspekt: @Around, @Before, @After, @AfterReturning, @AfterThrowing. @After läuft aber effektiv nach @AfterReturning/@AfterThrowing (finally-Semantik). Zwei gleiche Advice-Typen im selben Aspekt: undefiniert.
  12. Spring AOP vs AspectJ: Spring AOP: Proxies zur Laufzeit, nur Methoden von Beans. AspectJ: Weaving im Bytecode (Compile-Time oder Load-Time), auch Felder, Konstruktoren, private Methoden und Self-Invocation.
  13. Wo Spring selbst AOP nutzt: @Transactional, @Async, @Cacheable, @PreAuthorize, @Retryable, @Validated, Scoped Proxies.
  14. Kotlin: Klassen sind standardmässig final. Das Compiler-Plugin kotlin-spring (all-open) öffnet Spring-Komponenten für CGLIB.

5. Vergleich

  • JDK Dynamic Proxy: nur Interfaces, keine Bibliothek nötig, Cast auf die Klasse scheitert.
  • CGLIB: Unterklasse, auch ohne Interface, Standard in Spring Boot. Nicht für final und private.
  • Spring AOP: einfach, Laufzeit-Proxies, nur Methoden von Spring-Beans, Self-Invocation-Problem.
  • AspectJ (CTW/LTW): mächtig, kein Self-Invocation-Problem, aber eigener Compiler oder Java-Agent.
  • @Around vs @Before/@After: @Around kann Argumente, Rückgabe und Exception ändern oder den Aufruf auslassen. Die anderen sind einfacher und sicherer.
  • Aspekt vs Filter/Interceptor: Filter und HandlerInterceptor wirken nur auf HTTP-Requests. Ein Aspekt wirkt auf jede Bean-Methode.

6. In der Produktion

  1. @Transactional, @Async oder @Cacheable wirkt nicht: meist Self-Invocation, private/final-Methode oder ein Objekt ohne Spring (new). Lösung: Aufruf über eine andere Bean.
  2. BeanNotOfRequiredTypeException: JDK-Proxy, aber ein Injection Point mit der Klasse statt dem Interface. Lösung: gegen das Interface programmieren oder CGLIB nutzen.
  3. Falsche Reihenfolge von Retry und Transaktion: Retry läuft innerhalb der Transaktion, und jede Wiederholung nutzt dieselbe kaputte Transaktion. Lösung: Retry mit höherer Priorität (kleinerer @Order), also aussen.
  4. Exception verschluckt: Ein @Around-Advice fängt Exceptions und gibt null zurück. Die Transaktion committed, der Aufrufer sieht keinen Fehler. Lösung: Exceptions weiterwerfen.
  5. Langsamer Start: Ein zu breiter Pointcut (z. B. execution(* *(..))) proxied viele Beans. Lösung: Pointcut auf Paket oder Annotation eingrenzen.

7. Diagnose: Werkzeuge und Befehle

  • bean.getClass().getName(): $$SpringCGLIB$$ = CGLIB, $Proxy = JDK-Proxy.
  • AopUtils.isAopProxy(bean), isCglibProxy, isJdkDynamicProxy, AopProxyUtils.ultimateTargetClass(bean).
  • Stacktrace lesen: CglibAopProxy$DynamicAdvisedInterceptor, ReflectiveMethodInvocation.proceed, TransactionInterceptor zeigen die Kette. Fehlen sie, lief der Aufruf am Proxy vorbei.
  • logging.level.org.springframework.aop=DEBUG: zeigt, welche Beans Proxies bekommen.
  • Log-Meldung „not eligible for auto-proxying“: Die Bean entstand zu früh und hat keinen Proxy.

8. Senior-Punkte

  1. Proxies erklären fast alle „Annotation wirkt nicht“-Bugs. Die erste Frage ist immer: Geht der Aufruf durch den Proxy?
  2. Eigene Aspekte sparsam einsetzen. Sie sind unsichtbar im Code. Logging, Metriken und Tracing gibt es fertig (Micrometer, OpenTelemetry).
  3. Reihenfolge ist eine Design-Entscheidung: Security aussen, dann Retry, dann Transaktion, dann Business-Logik.
  4. Self-Invocation durch Design lösen: eine zweite Bean ist klarer als AopContext oder Self-Injection.
  5. AspectJ-Weaving nur mit gutem Grund. Es löst Proxy-Grenzen, macht aber Build und Betrieb komplexer.

10. Fallen

  • „Spring nutzt immer JDK-Proxies, wenn es ein Interface gibt.“ → Falsch in Spring Boot. Dort ist CGLIB Standard (spring.aop.proxy-target-class=true).
  • „Mit CGLIB funktioniert auch Self-Invocation.“ → Falsch. Auch bei CGLIB ruft this das Target auf, nicht den Proxy.
  • „Aspekte wirken auf private Methoden.“ → Falsch. Nicht mit Spring AOP, nur mit AspectJ-Weaving.
  • „Ein höherer @Order-Wert heisst höhere Priorität.“ → Falsch. Der niedrigere Wert hat höhere Priorität.
  • „Spring AOP wirkt auf jedes Objekt.“ → Falsch. Nur auf Spring-Beans, nicht auf Objekte mit new.

11. Fragen

Was ist AOP?

Eine Technik, um Querschnittsthemen wie Transaktionen, Security oder Logging an einer Stelle zu schreiben. Spring setzt sie mit Proxies um.

Erklären Sie Aspect, Join Point, Pointcut und Advice.

Aspect ist das Modul. Join Point ist eine Stelle im Ablauf, in Spring ein Methodenaufruf. Pointcut wählt Join Points aus. Advice ist der Code, der dort läuft.

Welche Advice-Typen gibt es?

@Before, @AfterReturning, @AfterThrowing, @After (wie finally) und @Around (umschliesst den Aufruf).

Was muss ein @Around-Advice tun?

Er muss joinPoint.proceed() aufrufen und das Ergebnis zurückgeben. Sonst läuft die Methode nicht.

Wie funktioniert ein JDK Dynamic Proxy?

Das JDK erzeugt zur Laufzeit eine Klasse, die die Interfaces implementiert. Jeder Aufruf geht an einen InvocationHandler, der Advice ausführt und die echte Methode ruft.

Wie funktioniert ein CGLIB-Proxy?

CGLIB erzeugt zur Laufzeit eine Unterklasse und überschreibt die Methoden. Darum gehen final-Klassen und final- oder private-Methoden nicht.

Wann nutzt Spring JDK-Proxy, wann CGLIB?

Core Spring: JDK-Proxy, wenn die Bean ein Interface hat, sonst CGLIB. Spring Boot: standardmässig immer CGLIB.

Warum nutzt Spring Boot standardmässig CGLIB?

So funktioniert auch die Injection über die Klasse statt das Interface. Das vermeidet BeanNotOfRequiredTypeException.

Läuft der Konstruktor bei CGLIB zweimal?

Nein. Spring erzeugt die Proxy-Instanz mit Objenesis, ohne den Konstruktor aufzurufen.

Was ist das Self-Invocation-Problem?

Ein Aufruf über this geht direkt ans Target, nicht durch den Proxy. Der Advice der aufgerufenen Methode läuft nicht.

Wie lösen Sie Self-Invocation?

Am besten die Methode in eine andere Bean verschieben. Sonst Self-Injection, AopContext.currentProxy() mit exposeProxy oder AspectJ-Weaving.

Wer erzeugt die Proxies?

Ein Auto-Proxy-Creator, ein BeanPostProcessor. Er ersetzt die Bean nach der Initialisierung durch einen Proxy, wenn ein Pointcut passt.

Wie steuern Sie die Reihenfolge von Aspekten?

Mit @Order oder Ordered. Niedriger Wert = höhere Priorität: auf dem Hinweg zuerst, auf dem Rückweg zuletzt.

In welcher Reihenfolge laufen Advices im selben Aspekt?

@Around, @Before, @After, @AfterReturning, @AfterThrowing. @After läuft wegen finally-Semantik effektiv nach @AfterReturning und @AfterThrowing.

Spring AOP vs AspectJ?

Spring AOP nutzt Laufzeit-Proxies und nur Methoden von Beans. AspectJ webt in den Bytecode und kann mehr, z. B. private Methoden und Self-Invocation.

Welche Spring-Features nutzen AOP?

@Transactional, @Async, @Cacheable, @PreAuthorize, @Validated, @Retryable und Scoped Proxies.

Was ist @Proxyable?

Neu in Spring 7.0. Es legt den Proxy-Typ pro Bean fest, z. B. nur Interfaces oder Unterklasse, gegen den globalen Standard.

Wie erkennen Sie, ob eine Bean ein Proxy ist?

AopUtils.isAopProxy(bean) oder der Klassenname: $$SpringCGLIB$$ für CGLIB, $Proxy für JDK.

Warum braucht Kotlin das kotlin-spring-Plugin?

Kotlin-Klassen sind standardmässig final. CGLIB kann sie nicht ableiten. Das Plugin macht Spring-Komponenten open.

Szenario: @Cacheable auf einer Methode wirkt nicht, die Methode läuft jedes Mal. Was prüfen Sie?

Ob der Aufruf aus derselben Klasse kommt (Self-Invocation), ob die Methode private oder final ist, und ob Caching aktiviert ist. Lösung: Aufruf über eine andere Bean.

Szenario: Nach dem Setzen von spring.aop.proxy-target-class=false startet die App mit BeanNotOfRequiredTypeException. Warum?

Jetzt nutzt Spring JDK-Proxies für Beans mit Interface. Ein Injection Point verlangt die Klasse. Lösung: gegen das Interface injizieren oder proxyTargetClass=true.

Szenario: Ein Retry-Aspekt wiederholt einen DB-Fehler, aber jede Wiederholung scheitert sofort. Warum?

Retry läuft innerhalb derselben Transaktion. Sie ist nach dem Fehler schon rollback-only oder in der DB abgebrochen. Lösung: Retry mit kleinerem @Order nach aussen, damit jede Wiederholung eine neue Transaktion startet.
