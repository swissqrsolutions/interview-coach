Konfiguration: Properties, @ConfigurationProperties, Profiles

Spring · Tier 1 · Quellen: Spring Boot Reference 4.x („Externalized Configuration“, „Profiles“), Application Properties Appendix, Spring Cloud Vault Reference („Config Data API“), Microsoft Learn „Load a Secret from Azure Key Vault in a Spring Boot Application“

Kern: Die Externalized Configuration von Spring Boot sammelt Werte aus vielen Property Sources in einem Environment. Eine feste Reihenfolge entscheidet, welcher Wert gewinnt. So läuft dasselbe Jar in jeder Umgebung, nur die Konfiguration ändert sich.

1. Wo sitzt die Konfiguration?

  1. Property Source: eine Quelle für Schlüssel-Wert-Paare. Beispiel: application.yml, Umgebungsvariablen, Kommandozeile.
  2. Environment: die geordnete Liste aller Quellen. Eine Abfrage nimmt den ersten Treffer von oben.
  3. Config Data: die application-*.properties/.yml-Dateien, dazu Importe mit spring.config.import.
  4. Binder: füllt @ConfigurationProperties-Objekte typsicher, mit Relaxed Binding.
  5. @Value: löst einzelne Platzhalter wie ${app.timeout} auf. Es kann SpEL.
  6. Profile: aktivieren zusätzliche Dateien und Beans, z. B. application-prod.yml.

2. Die Reise eines Wertes (die Geschichte zum Merken)

  1. Start: SpringApplication legt das Environment an. Kommandozeile, System Properties und Umgebungsvariablen sind sofort da.
  2. Dateien: Boot sucht application.properties und .yml im Classpath, in classpath:/config, im Arbeitsverzeichnis und in ./config/. Spätere Orte gewinnen.
  3. Profile: Boot liest spring.profiles.active, z. B. aus SPRING_PROFILES_ACTIVE=prod. Eine Profile Group erweitert prod zu prod, proddb, prodmq.
  4. Profil-Dateien: application-prod.yml überschreibt application.yml. Dateien ausserhalb des Jars schlagen Dateien im Jar.
  5. Imports: spring.config.import lädt weitere Quellen. Beispiele: configtree: für Kubernetes-Secret-Dateien, vault:// für HashiCorp Vault.
  6. Binden: Der Binder füllt das Properties-Objekt. Mit @Validated bricht der Start bei falschen Werten ab.

3. Beispiel: welcher Wert gewinnt?

# application.yml (im Jar)
app:
  db:
    pool-size: 10
    timeout: 5s
spring:
  profiles:
    group:
      prod: "proddb,prodmq"
---
spring:
  config:
    activate:
      on-profile: "proddb"
app:
  db:
    pool-size: 20
@ConfigurationProperties("app.db")
@Validated
public record DbProperties(@Min(1) @Max(100) int poolSize, @NotNull Duration timeout) {}

@SpringBootApplication
@ConfigurationPropertiesScan
public class App {
  @Bean ApplicationRunner print(DbProperties p) {
    return args -> System.out.println("poolSize=" + p.poolSize() + " timeout=" + p.timeout());
  }
}
$ java -jar app.jar
poolSize=10 timeout=PT5S

$ SPRING_PROFILES_ACTIVE=prod java -jar app.jar
poolSize=20 timeout=PT5S

$ SPRING_PROFILES_ACTIVE=prod APP_DB_POOLSIZE=30 java -jar app.jar
poolSize=30 timeout=PT5S

$ SPRING_PROFILES_ACTIVE=prod APP_DB_POOLSIZE=30 java -jar app.jar --app.db.pool-size=40
poolSize=40 timeout=PT5S

$ java -jar app.jar --app.db.pool-size=0
APPLICATION FAILED TO START
Binding to target ... failed:
    Property: app.db.pool-size
    Value: "0"
    Reason: must be greater than or equal to 1

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Fehlermeldung gekürzt.

  1. Ohne Profil gilt die Datei im Jar: 10.
  2. prod aktiviert über die Group auch proddb. Das zweite YAML-Dokument gilt: 20.
  3. Die Umgebungsvariable APP_DB_POOLSIZE schlägt die Datei: 30. Regel: Punkte zu _, Bindestriche weg, Grossbuchstaben.
  4. Die Kommandozeile schlägt die Umgebungsvariable: 40.
  5. "5s" wird automatisch eine Duration. @Validated stoppt den Start bei 0, statt später in Produktion zu scheitern.

4. Details, die Interviewer fragen

  1. Reihenfolge (niedrig → hoch, Auszug): Default Properties, @PropertySource, Config Data, random.*, OS-Umgebungsvariablen, Java System Properties, JNDI, ServletContext/ServletConfig, SPRING_APPLICATION_JSON, Kommandozeile. In Tests darüber: properties von @SpringBootTest, @DynamicPropertySource, @TestPropertySource.
  2. Config-Dateien (niedrig → hoch): application.yml im Jar, application-{profile}.yml im Jar, application.yml ausserhalb, Profil-Datei ausserhalb.
  3. .properties vs .yml: Liegen beide am gleichen Ort, gewinnt .properties. Die Doku empfiehlt ein Format.
  4. @PropertySource: wird erst beim Context-Refresh geladen. Zu spät für logging.* und spring.main.*. YAML lädt es nicht.
  5. spring.config.import: lädt weitere Quellen. optional: verhindert einen Startfehler, wenn die Quelle fehlt.
  6. configtree: macht jede Datei in einem Ordner zu einer Property. Beispiel: Kubernetes-Secret als Volume unter /etc/config/.
  7. Relaxed Binding: pool-size, poolSize, pool_size und APP_DB_POOLSIZE binden auf dasselbe Feld. Kanonische Form: kebab-case, klein.
  8. Listen per Umgebungsvariable: my.service[0].other wird MY_SERVICE_0_OTHER.
  9. @ConfigurationProperties vs @Value: Relaxed Binding ja vs eingeschränkt. Metadaten (IDE-Hilfe) ja vs nein. SpEL nein vs ja.
  10. Constructor Binding: Ein Record oder eine Klasse mit einem Konstruktor bindet über den Konstruktor. So sind Properties unveränderlich. Aktivieren mit @ConfigurationPropertiesScan oder @EnableConfigurationProperties.
  11. Validierung: @Validated plus Jakarta-Constraints. Für verschachtelte Objekte zusätzlich @Valid.
  12. Profile aktivieren: spring.profiles.active, z. B. per SPRING_PROFILES_ACTIVE oder --spring.profiles.active=prod. Ohne Profil ist default aktiv.
  13. Profile Groups: spring.profiles.group.prod=proddb,prodmq. Ein Name aktiviert mehrere Profile.
  14. spring.profiles.include: fügt Profile immer hinzu, vor den aktiven.
  15. Einschränkung: active, default, include und group sind in Profil-Dateien und Profil-Dokumenten verboten.
  16. Multi-Document YAML: --- trennt Dokumente. spring.config.activate.on-profile und on-cloud-platform machen ein Dokument bedingt.
  17. @Profile: auf @Component oder @Configuration schaltet Beans pro Profil. Ausdrücke wie !prod oder cloud & azure sind möglich.
  18. Profilnamen: Boot prüft Namen (spring.profiles.validate=true): Buchstaben, Ziffern und wenige Zeichen wie -, _, ..

Secrets:

  1. Umgebungsvariablen: einfach, aber sichtbar für alle im Prozess und oft in Logs von Tools. Beispiel: Kubernetes-Secret als env.
  2. configtree: Kubernetes-Secret als Datei-Volume. Kein Secret in der Prozessumgebung.
  3. HashiCorp Vault: Spring Cloud Vault mit spring.config.import=vault://. Standardpfad: secret/${spring.application.name} plus ein Pfad pro Profil.
  4. Azure Key Vault: Spring Cloud Azure mit spring.cloud.azure.keyvault.secret.property-sources[0].endpoint. Login über DefaultAzureCredential, in Azure am besten Managed Identity.
  5. External Secrets Operator: synchronisiert Vault oder Key Vault in Kubernetes-Secrets. Die App liest dann env oder configtree, ganz ohne Vault-Client.
  6. Actuator: /actuator/env und /actuator/configprops maskieren Werte standardmässig (show-values=never).

5. Vergleich

  • @ConfigurationProperties: typsicher, gruppiert, validierbar, IDE-Metadaten. Für alles Eigene mit mehreren Werten.
  • @Value: ein einzelner Wert, SpEL möglich, kein Relaxed Binding im vollen Umfang. Für Einzelfälle.
  • Environment.getProperty: programmatisch, z. B. in Bibliotheks-Code. Ohne Typsicherheit.
  • Profile vs Feature-Property: Profil = Umgebung (dev, prod). Property = Schalter für ein Feature.
  • spring.config.location vs additional-location: ersetzt die Standard-Orte vs ergänzt sie.
  • Env/configtree vs Vault-Client: Plattform liefert Secrets vs App holt sie selbst. Ersteres hält die App einfacher.

6. In der Produktion

  1. Falscher Wert aktiv: Eine vergessene Umgebungsvariable schlägt die YAML-Datei. Lösung: /actuator/env/<name> zeigt, welche Quelle gewinnt.
  2. Profil fehlt: Die App startet mit default und nutzt lokale Werte in Produktion. Lösung: spring.profiles.default=none oder Pflicht-Properties mit @Validated.
  3. Secret im Git: Ein Passwort steht in application-prod.yml. Lösung: entfernen, rotieren, Secrets nur aus Vault/Key Vault, SonarQube/Secret-Scan im Build.
  4. Secret im Log: @Value-Werte oder ein Properties-Record mit toString landen im Log. Lösung: Secrets nie loggen, toString überschreiben.
  5. Falsche Schreibweise in @Value: @Value("${app.db.poolSize}") findet app.db.pool-size aus der Datei nicht. Lösung: kanonische Namen (kebab-case) in @Value, besser @ConfigurationProperties.
  6. Secret-Rotation: Gebundene Werte ändern sich nicht von selbst. Lösung: Neustart (Rolling Update) oder Refresh-Mechanismus, z. B. aus Spring Cloud.
  7. Startfehler durch fehlende Quelle: Vault ist nicht erreichbar. Lösung: bewusst entscheiden: fail fast (Standard) oder optional:.

7. Diagnose: Werkzeuge und Befehle

  • /actuator/env: alle Property Sources in Reihenfolge. /actuator/env/app.db.pool-size zeigt die gewinnende Quelle.
  • /actuator/configprops: alle gebundenen @ConfigurationProperties-Objekte.
  • Startlog: Boot loggt beim Start die aktiven Profile (Zeile „The following … profile(s) … active“).
  • spring-boot-properties-migrator: meldet umbenannte Properties nach einem Upgrade, z. B. Boot 4.
  • kubectl exec <pod> -- env und ls /etc/config: was die Plattform wirklich liefert.
  • logging.level.org.springframework.boot.context.config=TRACE: zeigt, welche Config-Dateien Boot lädt.

8. Senior-Punkte

  1. Ein Artefakt, viele Umgebungen. Das gleiche Image läuft überall. Nur Konfiguration und Secrets kommen von aussen (12-Factor).
  2. Wenige Profile. Profile pro Umgebung werden schnell unübersichtlich. Besser: Werte per Umgebungsvariable oder Helm Values, Profile nur für echte Unterschiede.
  3. Typsicher und fail fast. @ConfigurationProperties mit Records und @Validated. Ein Fehler beim Start ist billiger als ein Fehler um drei Uhr nachts.
  4. Secrets gehören der Plattform. Vault oder Key Vault, Zugriff per Identität (Managed Identity, Workload Identity), keine Passwörter im Repo.
  5. Die Reihenfolge erklären können. „Kommandozeile schlägt Env schlägt Datei, aussen schlägt innen, Profil schlägt Basis.“ Das löst die meisten Konfigurationsfragen.

10. Fallen

  • „application.yml schlägt Umgebungsvariablen.“ → Falsch. Umgebungsvariablen stehen höher. Die Kommandozeile noch höher.
  • „@PropertySource kann YAML laden.“ → Falsch. Nur Properties-Format, und es kommt spät.
  • „spring.profiles.active in application-prod.yml setzen.“ → Falsch. In Profil-Dateien verboten, Boot meldet einen Fehler.
  • „@Value und @ConfigurationProperties binden gleich.“ → Falsch. @Value hat nur eingeschränktes Relaxed Binding und keine Metadaten.
  • „Secrets in Umgebungsvariablen sind sicher.“ → Nur bedingt. Jeder Prozess-Dump und viele Tools sehen sie. Besser Dateien oder Vault.
  • „Ohne Profil ist kein Profil aktiv.“ → Falsch. Dann ist das Profil default aktiv.

11. Fragen

Was ist Externalized Configuration?

Konfiguration ausserhalb des Codes, aus vielen Quellen. Boot ordnet sie fest, damit dasselbe Jar überall läuft.

Welche Quelle gewinnt: Datei, Umgebungsvariable oder Kommandozeile?

Kommandozeile vor System Properties vor Umgebungsvariablen vor Config-Dateien.

In welcher Reihenfolge lädt Boot die Config-Dateien?

Datei im Jar, Profil-Datei im Jar, Datei ausserhalb, Profil-Datei ausserhalb. Die spätere gewinnt.

Wo sucht Boot nach application.yml?

Im Classpath-Root, in classpath:/config, im Arbeitsverzeichnis, in ./config und dessen direkten Unterordnern.

Was gewinnt bei .properties und .yml am gleichen Ort?

.properties. Besser nur ein Format nutzen.

Wie wird app.db.pool-size als Umgebungsvariable geschrieben?

APP_DB_POOLSIZE. Punkte werden Unterstriche, Bindestriche fallen weg, alles gross.

@ConfigurationProperties oder @Value?

@ConfigurationProperties für Gruppen von Werten: typsicher, validierbar, Relaxed Binding, IDE-Metadaten. @Value für Einzelwerte oder SpEL.

Wie machen Sie Properties unveränderlich?

Mit einem Record oder Konstruktor-Binding. Aktivieren über @ConfigurationPropertiesScan oder @EnableConfigurationProperties.

Wie validieren Sie Konfiguration?

@Validated auf der Properties-Klasse und Constraints wie @NotNull oder @Min. Falsche Werte stoppen den Start.

Was ist Relaxed Binding?

Verschiedene Schreibweisen binden auf dasselbe Feld: kebab-case, camelCase, Unterstrich, Umgebungsvariable.

Wie aktivieren Sie ein Profil?

Mit spring.profiles.active, z. B. als SPRING_PROFILES_ACTIVE oder --spring.profiles.active=prod.

Was ist eine Profile Group?

Ein Name für mehrere Profile. spring.profiles.group.prod=proddb,prodmq aktiviert mit prod alle drei.

Welches Profil ist aktiv, wenn keins gesetzt ist?

Das Profil default. Änderbar mit spring.profiles.default.

Wo darf spring.profiles.active nicht stehen?

In Profil-Dateien und in Dokumenten mit spring.config.activate.on-profile. Gleiches gilt für include und group.

Wie machen Sie ein YAML-Dokument profilabhängig?

Mit --- als Trenner und spring.config.activate.on-profile im Dokument.

Was macht spring.config.import?

Es lädt weitere Quellen, z. B. Dateien, configtree, Vault. Mit optional: startet die App auch ohne diese Quelle.

Was ist configtree?

Eine Import-Art, die jede Datei eines Ordners zu einer Property macht. Ideal für Kubernetes-Secrets als Volume.

Wie binden Sie HashiCorp Vault an?

Mit Spring Cloud Vault und spring.config.import=vault://. Standardpfad ist secret/ plus Anwendungsname, dazu ein Pfad pro Profil.

Wie binden Sie Azure Key Vault an?

Mit Spring Cloud Azure als Property Source über spring.cloud.azure.keyvault.secret.property-sources[0].endpoint. Login mit DefaultAzureCredential, in Azure Managed Identity.

Warum ist @PropertySource oft nicht genug?

Es lädt erst beim Refresh und kein YAML. Werte wie logging.* sind dann schon gelesen.

Wie sehen Sie, woher ein Wert kommt?

Mit /actuator/env/<name>. Es zeigt alle Quellen mit diesem Schlüssel und die gewinnende.

Szenario: In Produktion nutzt die App die lokale Datenbank-URL. Was prüfen Sie?

Aktive Profile im Startlog, dann /actuator/env für die URL. Oft fehlt SPRING_PROFILES_ACTIVE oder eine Variable ist falsch geschrieben.

Szenario: Ein Datenbank-Passwort liegt im Git-Repo. Was tun Sie?

Passwort sofort rotieren, aus dem Repo und der History entfernen. Secret in Vault oder Key Vault, Zugriff per Identität, Secret-Scan im Build.

Szenario: Ein Secret wird rotiert, aber die App nutzt weiter das alte. Warum, und was tun Sie?

Gebundene Werte werden beim Start gelesen. Lösung: Rolling Restart nach der Rotation automatisieren oder einen Refresh-Mechanismus nutzen. Danach prüfen, dass Connection Pools neue Verbindungen aufbauen.
