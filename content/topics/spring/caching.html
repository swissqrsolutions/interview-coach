Spring Cache: @Cacheable, Cache-Provider

Kern: Die Spring Cache Abstraction speichert das Ergebnis einer Methode und gibt es beim nächsten Aufruf mit gleichen Argumenten zurück, ohne die Methode auszuführen. Sie löst das Problem teurer, wiederholter Abfragen (DB, externe APIs). Sie ist nur eine Fassade, denn den echten Speicher liefert ein Provider wie Caffeine (lokal) oder Redis (verteilt).

Antwort-Muster

Frage: Wie funktioniert @Cacheable?

  1. Mechanismus: @EnableCaching baut einen Proxy. Der CacheInterceptor baut den Schlüssel aus den Argumenten und schaut im Cache nach. Bei einem Hit läuft die Methode nicht.
  2. Zahl: Im Test mit 50 Threads gab es 50 DB-Aufrufe, mit sync = true nur 1. Eine TTL kennt die Abstraktion nicht, sie kommt vom Provider.
  3. Trade-off: Caffeine ist schnell, aber jeder Pod hat seine eigene Kopie. Redis ist geteilt, kostet aber Netzwerk und Serialisierung.
  4. Produktion: Ich setze Grösse und TTL und nehme den Mandanten in den Schlüssel. Ich überwache die Hit-Rate.

1. Die Reise eines @Cacheable-Aufrufs

  1. condition: Ein SpEL-Ausdruck vor dem Aufruf. Ist er false, wird nicht gecacht. Beispiel: condition = "#currency != 'TEST'".
  2. Schlüssel: Der SimpleKeyGenerator baut ihn. Kein Argument: SimpleKey.EMPTY. Ein Argument: das Argument selbst. Mehrere: ein SimpleKey mit allen.
  3. Nachschauen: Gibt es einen Eintrag, ist das ein Hit. Die Methode läuft nicht.
  4. Miss: Die Methode läuft. Mit sync = true rechnet nur ein Thread pro Schlüssel; die anderen warten auf sein Ergebnis.
  5. unless: Ein SpEL-Ausdruck nach dem Aufruf. Er kann das Speichern verhindern, z. B. unless = "#result == null".
  6. Speichern: Der Wert kommt in den Cache. Wie lange er bleibt, entscheidet der Provider (TTL, Grösse). Die Abstraktion selbst kennt keine TTL.

2. Aufbau

  1. Proxy: @EnableCaching lässt Spring um Beans mit Cache-Annotations einen Proxy bauen. Der CacheInterceptor entscheidet: Cache oder Methode.
  2. CacheManager: Er verwaltet benannte Caches, z. B. rates. Spring Boot wählt ihn automatisch nach dem Classpath.
  3. Cache: Eine Map von Schlüssel (aus den Argumenten) auf Wert (das Ergebnis).
  4. Caffeine: Lokaler Cache im Heap jedes Pods. Sehr schnell, aber jeder Pod hat seine eigene Kopie.
  5. Redis: Geteilter Cache über das Netzwerk. Alle Pods sehen denselben Wert. Werte müssen serialisiert werden.

3. Details, die Interviewer fragen

  1. Vier Annotations: @Cacheable liest und rechnet bei einem Miss. @CachePut rechnet immer und schreibt das Ergebnis. @CacheEvict entfernt, und @Caching kombiniert mehrere. @CacheConfig setzt gemeinsame Einstellungen an der Klasse.
  2. @Cacheable und @CachePut zusammen: Die Doku rät stark ab. Das eine überspringt die Methode. Das andere erzwingt sie.
  3. Schlüssel bei mehreren Argumenten: Der Standard nimmt alle Argumente. Ist ein Argument unwichtig (z. B. ein Flag), muss man key setzen. Sonst gibt es Duplikate.
  4. key vs keyGenerator: Der SimpleKeyGenerator baut bei mehreren Parametern einen zusammengesetzten Schlüssel. Er nutzt equals und hashCode. key und keyGenerator schliessen sich aus. Setzt man beide, gibt es eine Exception.
  5. Schlüssel-Objekte: Sie brauchen korrekte equals und hashCode. Eine Entity ohne diese Methoden als Schlüssel trifft nie.
  6. condition vs unless: condition wird vor dem Aufruf geprüft. unless wird danach mit #result geprüft.
  7. null-Werte: Viele Provider speichern null als Platzhalter. Das schützt vor wiederholten Abfragen nach nicht existierenden Daten. Ein Optional.empty() wird als null gespeichert.
  8. Evict-Zeitpunkt: @CacheEvict entfernt standardmässig nach erfolgreichem Aufruf. Mit beforeInvocation = true entfernt es vorher, auch bei Exception.
  9. Proxy-Grenzen: Self-Invocation umgeht den Cache. Annotations wirken nur auf public-Methoden. Die Lösung ist ein Aufruf über eine andere Bean oder der AspectJ-Modus.
  10. CacheResolver: Der Standard-Resolver holt die Caches über den konfigurierten CacheManager. Bei mehreren Managern setzt man cacheManager pro Operation. Ein eigener CacheResolver ersetzt die Auflösung ganz.
  11. Provider-Auswahl in Boot: Boot prüft in dieser Reihenfolge: Generic, JCache, Hazelcast, Infinispan, Couchbase, Redis, Caffeine, Cache2k, Simple. Man setzt ihn fest mit spring.cache.type. none schaltet Caching aus und ist gut für Tests.
  12. Simple-Provider: Ohne Bibliothek nimmt Boot eine ConcurrentHashMap. Sie hat keine TTL und keine Grenze. Laut Doku ist sie nicht für Produktion.
  13. TTL: Sie gehört zum Provider. Bei Caffeine ist es expireAfterWrite, bei Redis spring.cache.redis.time-to-live. Unterschiedliche TTLs pro Cache brauchen einen Customizer oder eigene Konfiguration.
  14. Asynchrone und reaktive Methoden: CompletableFuture, Mono und Flux werden unterstützt. Bei Flux wird eine Liste gespeichert. Caffeine braucht dafür den Async-Modus (spring.cache.caffeine.cache-mode=async, seit Boot 4.2).
  15. Transaktionen: Ein Cache ist nicht transaktional. Ein @CachePut in einer Transaktion, die danach zurückrollt, lässt einen falschen Wert im Cache. TransactionAwareCacheManagerProxy verschiebt Put und Evict auf nach dem Commit.
  16. CacheErrorHandler: Standard ist der SimpleCacheErrorHandler. Er wirft jede Exception eines Cache-Zugriffs an den Aufrufer zurück. Ein eigener Handler kann sie nur loggen.
  17. Serialisierung bei Redis: Werte werden serialisiert. Klassen ändern sich mit Releases. Alte Einträge passen dann nicht mehr. Die Lösung ist JSON, ein Versions-Präfix im Schlüssel und eine kurze TTL.

4. Fallen

  • „@Cacheable hat eine TTL.“ → Falsch. Die Abstraktion kennt keine TTL. Der Provider regelt das.
  • „Der Standard-Cache in Boot ist produktionsreif.“ → Falsch. Simple ist eine Map ohne Grenze und ohne Ablauf.
  • „Ein Aufruf in der gleichen Klasse nutzt den Cache.“ → Falsch. Self-Invocation umgeht den Proxy.
  • „sync = true verhindert Stampede im ganzen Cluster.“ → Falsch. Es sperrt nur im eigenen Prozess.
  • „Der Cache ist Teil der Transaktion.“ → Falsch. Ohne TransactionAware-Proxy bleibt ein Put trotz Rollback.
  • „Ein Evict auf Pod A gilt für alle Pods.“ → Falsch bei lokalem Cache. Nur bei verteiltem Cache.

5. Selbsttest

Warum?

Warum wirkt @Cacheable bei einem internen Aufruf nicht?

Caching läuft im Proxy. Ein Aufruf über this umgeht ihn.

Ist der Cache transaktional?

Nein. Ein Put bleibt auch nach Rollback. TransactionAwareCacheManagerProxy verschiebt Put und Evict auf nach dem Commit.

Was ist eine Cache Stampede?

Ein beliebter Eintrag fehlt oder läuft ab, und viele Requests laden ihn gleichzeitig. Die Quelle wird überlastet.

Wie innen?

Was ist die Spring Cache Abstraction?

Eine Fassade, die Methoden-Ergebnisse per Annotation cacht. Den Speicher liefert ein Provider wie Caffeine oder Redis.

Wie aktivieren Sie Caching?

Mit @EnableCaching. Spring Boot konfiguriert dann einen CacheManager passend zum Classpath.

Wie entsteht der Cache-Schlüssel?

Der SimpleKeyGenerator nimmt alle Argumente: keins → SimpleKey.EMPTY, eins → das Argument, mehrere → SimpleKey. Mit key per SpEL anpassen.

condition vs unless?

condition prüft vor dem Aufruf, ob gecacht wird. unless prüft nach dem Aufruf mit #result, ob gespeichert wird.

Was macht sync = true?

Bei einem Miss rechnet nur ein Thread pro Schlüssel. Die anderen warten auf sein Ergebnis. Das schützt vor Stampede im eigenen Prozess.

Welchen Provider nimmt Spring Boot ohne Konfiguration?

Den ersten passenden in der Reihenfolge Generic, JCache, Hazelcast, Infinispan, Couchbase, Redis, Caffeine, Cache2k, sonst Simple.

Wann evict @CacheEvict?

Standardmässig nach erfolgreichem Aufruf. Mit beforeInvocation = true vorher und auch bei Exception.

Soll man null cachen?

Oft ja, gegen wiederholte Abfragen nach nicht existierenden Daten. Mit kurzer TTL, sonst sieht man neue Daten spät.

Kann man reaktive Methoden cachen?

Ja. Mono und CompletableFuture werden nach Fertigstellung gespeichert, Flux als Liste. Caffeine braucht dafür den Async-Modus.

Zahlen

Wie setzen Sie eine TTL?

Im Provider: Caffeine mit expireAfterWrite, Redis mit spring.cache.redis.time-to-live. Die Spring-Annotations haben keine TTL.

Welche Metriken zeigen, ob ein Cache etwas bringt?

cache.gets mit result=hit und miss, daraus die Hit-Rate. Dazu Grösse und Evictions.

Wie viele DB-Aufrufe gibt es bei 50 gleichzeitigen Lesern?

Im JDK-Test sind es 50 ohne Sperre und 1 mit computeIfAbsent, also wie bei sync = true.

Welche Grössen und Zeiten setzt das Caffeine-Beispiel?

maximumSize=10000 und expireAfterWrite=10m. Mit recordStats kommen Hit- und Miss-Zahlen dazu.

Vergleich

@Cacheable vs @CachePut?

@Cacheable überspringt die Methode bei einem Hit. @CachePut führt sie immer aus und schreibt das Ergebnis in den Cache.

Caffeine oder Redis?

Caffeine: lokal, sehr schnell, pro Pod. Redis: geteilt zwischen Pods, langsamer, braucht Serialisierung und Betrieb.

Spring Cache vs Hibernate Second-Level Cache?

Spring cacht beliebige Methoden-Ergebnisse, z. B. DTOs. Der Second-Level Cache cacht Entities nach ID unterhalb von JPA.

Produktion

Was passiert bei einem Redis-Ausfall?

Ohne Vorkehrung wirft jeder Zugriff eine Exception. Ein eigener CacheErrorHandler loggt den Fehler und lässt die Methode normal laufen.

Szenario: Nach einem Preis-Update sehen manche Kunden noch minutenlang den alten Preis. Warum?

Lokaler Caffeine-Cache: nur der Pod mit dem Update hat geleert. Lösung: verteilter Cache, Invalidierung an alle Pods oder kürzere TTL.

Szenario: Benutzer sehen manchmal die Daten eines anderen Mandanten. Was prüfen Sie im Cache?

Den Schlüssel: Fehlt die Mandanten-ID, teilen sich alle Mandanten einen Eintrag. Mandant in den Schlüssel, Cache leeren, Test mit zwei Mandanten.

Szenario: Jede volle Stunde gibt es eine CPU-Spitze auf der Datenbank. Woran denken Sie?

Viele Einträge laufen mit gleicher TTL gleichzeitig ab: Stampede. Lösung: sync = true, TTL mit Jitter oder refreshAfterWrite.

Design

Wie wählen Sie die TTL?

Aus der Fachfrage „Wie veraltet darf es sein?“. Danach setzt man die TTL im Provider, am besten mit Jitter.

Was gehört in den Cache-Schlüssel?

Alles, was das Ergebnis ändert, also Argumente, Mandant, Sprache und Rechte. Sonst gibt es Datenlecks.

Mehr

Gerüst

  • Warum? Teure, wiederholte Abfragen (DB, externe APIs) laufen nur einmal.
  • Wie innen? @EnableCaching → Proxy → CacheInterceptor: condition → Schlüssel → Hit oder Miss → unless → speichern. Der Provider liefert den Speicher.
  • Zahlen Test mit 50 Threads: 50 DB-Aufrufe ohne Sperre, 1 mit sync = true. Caffeine im Beispiel mit maximumSize=10000 und expireAfterWrite=10m.
  • Vergleich Caffeine ist lokal, Redis ist geteilt. Spring Cache cacht Methoden, Hibernate Second-Level Cache cacht Entities, HTTP-Caching cacht den ganzen Request.
  • Produktion Veraltete Daten zwischen Pods. Stampede bei einem ablaufenden Eintrag. Schlüssel ohne Mandant → Datenleck.
  • Design Erst messen, dann cachen. Die TTL ist eine Fachfrage. Der Cache ist optional.

Beispiel: Annotations, Konfiguration, Cache Stampede

@Configuration @EnableCaching class CacheConfig {}

@Service @CacheConfig(cacheNames = "rates")
class RateService {
  @Cacheable(key = "#from + '-' + #to", sync = true)
  BigDecimal rate(String from, String to) { return api.fetch(from, to); }   // 200 ms

  @CachePut(key = "#r.from + '-' + #r.to")
  BigDecimal update(Rate r) { return repo.save(r).value(); }

  @CacheEvict(allEntries = true)
  void reloadAll() { ... }
}

# application.yml
spring.cache:
  type: caffeine
  cache-names: rates
  caffeine.spec: maximumSize=10000,expireAfterWrite=10m,recordStats

Was sync = true bringt, zeigt ein Test mit 50 Threads, die gleichzeitig einen leeren Eintrag lesen. Spring nutzt für den einfachen Cache genau diese ConcurrentHashMap-Methoden:

get, dann put (wie sync=false)     50 gleichzeitige Leser -> DB-Aufrufe: 50, Zeit: 222 ms
computeIfAbsent (wie sync=true)    50 gleichzeitige Leser -> DB-Aufrufe:  1, Zeit: 209 ms

Echte Ausgabe, OpenJDK 17.0.3 (ConcurrentHashMap, 50 Threads, Ladezeit 200 ms). Spring ist hier nicht installiert.

  1. Ohne Sperre laden alle 50 Threads denselben Wert: Cache Stampede. Bei einem abgelaufenen, beliebten Eintrag trifft das die DB mit voller Wucht.
  2. Mit computeIfAbsent lädt genau ein Thread. Die anderen warten etwa gleich lang, belasten aber die DB nicht.
  3. sync = true sperrt nur pro Pod. Mit 10 Pods und Redis laden immer noch bis zu 10 Pods gleichzeitig.
  4. @CachePut führt die Methode immer aus und schreibt das Ergebnis in den Cache. @CacheEvict(allEntries = true) leert den ganzen Cache.
  5. recordStats in Caffeine liefert Hit- und Miss-Zahlen für Actuator-Metriken.

Vergleich

  • Caffeine: lokal, sehr schnell, gute Verdrängung (Window TinyLFU). Jeder Pod hat eigene Werte, Invalidierung nur lokal.
  • Redis: geteilt, überlebt Neustarts der App, Netzwerk-Latenz, Serialisierung. Ein weiteres System im Betrieb.
  • Zwei Ebenen (Caffeine vor Redis): schnell und geteilt, aber komplexe Invalidierung.
  • Hibernate Second-Level Cache: cacht Entities nach ID unterhalb von JPA. Spring Cache cacht Methoden-Ergebnisse, z. B. fertige DTOs.
  • HTTP-Caching (Cache-Control, ETag): cacht beim Client oder CDN. Spart den ganzen Request, nicht nur die DB-Abfrage.
  • Materialized View in der DB: vorberechnete Ergebnisse in der DB, für alle Konsumenten gleich, mit Refresh-Steuerung.

In der Produktion

  1. Veraltete Daten: Pod A ändert einen Wert und leert seinen Caffeine-Cache. Pod B liefert weiter den alten Wert. Lösung: kurze TTL, Redis oder Invalidierung per Event an alle Pods.
  2. Speicher voll: Ein Cache ohne maximumSize wächst ohne Grenze (z. B. der Simple-Provider). Lösung: immer Grösse und TTL setzen.
  3. Cache Stampede: Ein beliebter Eintrag läuft ab, hunderte Requests laden gleichzeitig. Lösung: sync = true, refreshAfterWrite in Caffeine, TTL mit Jitter.
  4. Cache wirkt nicht: @EnableCaching fehlt oder Self-Invocation. Lösung: Hit-Rate messen, Aufruf über die Bean.
  5. Fremde Daten im Cache: Der Schlüssel enthält nicht den Benutzer oder Mandanten. Benutzer B sieht Daten von A. Lösung: Mandant und Rechte gehören in den Schlüssel, oder nur öffentliche Daten cachen.
  6. Redis-Ausfall legt die App lahm: Jeder Zugriff wirft eine Exception. Lösung: ein CacheErrorHandler, der Fehler loggt und zur Methode durchfällt, plus Timeouts.

Diagnose

  • Metriken: cache.gets{result=hit|miss}, cache.puts, cache.evictions, cache.size. Hit-Rate = hits / (hits + misses).
  • /actuator/caches: alle Caches und ihre CacheManager; DELETE leert sie.
  • logging.level.org.springframework.cache=TRACE: zeigt Schlüssel und Hit/Miss pro Aufruf.
  • Redis: redis-cli --scan --pattern 'rates::*' und TTL <key> zeigen Einträge und Restlaufzeit. INFO stats zeigt keyspace_hits und keyspace_misses.
  • Test: Die echte Bean zweimal aufrufen und mit einem Mock prüfen, dass die Quelle nur einmal gerufen wurde.

Senior-Punkte

  1. Erst messen, dann cachen. Ein Cache versteckt langsame Queries, statt sie zu lösen. Erst Index und Query prüfen.
  2. Jeder Cache braucht eine Antwort auf „wie veraltet darf es sein?“ Daraus folgt die TTL. Das ist eine Fachfrage.
  3. Lokal oder verteilt ist eine Abwägung: Geschwindigkeit gegen Konsistenz zwischen Pods.
  4. Cache ist optional. Die App muss ohne Cache korrekt laufen, nur langsamer. Ausfall des Caches darf kein Ausfall der App sein.
  5. Sicherheit im Schlüssel: Mandant, Sprache, Rechte. Sonst Datenlecks.
  6. Hit-Rate überwachen. Ein Cache mit 5 % Hit-Rate kostet nur Speicher.
