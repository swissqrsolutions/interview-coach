Method Security: @PreAuthorize

Spring · Tier 2 · Quellen: Spring Security 7.2 Reference („Method Security“), Spring Boot 4.2 Reference (Security), PostgreSQL 17 Doku („Row Security Policies“)

Kern: Method Security ist Autorisierung direkt an Java-Methoden, z. B. mit @PreAuthorize("hasRole('ADMIN')"). Sie löst das Problem, dass URL-Regeln keine Fachlogik kennen: „Darf Anna dieses Konto sehen?“. Spring Security setzt sie mit AOP-Proxies und einem AuthorizationManager pro Annotation um.

1. Wo sitzt Method Security?

  1. Filter Chain: Sie meldet den Benutzer an und prüft grobe URL-Regeln. Beispiel: /api/** braucht Login.
  2. SecurityContextHolder: Er hält das Authentication-Objekt mit Name und Rechten (Authorities) für den aktuellen Thread.
  3. Proxy: @EnableMethodSecurity sorgt dafür, dass Spring um annotierte Beans einen Proxy baut. Der Proxy hat einen Interceptor pro Annotation.
  4. Reihenfolge: Jeder Interceptor hat eine Order. @PreFilter hat 100, @PreAuthorize 200. Die Post-Interceptoren laufen nach der Methode.
  5. Echte Methode: Sie läuft nur, wenn alle Pre-Prüfungen bestehen. Alle Annotations zusammen sind ein logisches UND.

2. Die Reise eines Aufrufs von readAccount(7)

  1. Proxy: Der Controller ruft accountService.readAccount(7). In Wahrheit ruft er den Proxy. Der Proxy startet den Interceptor von @PreAuthorize.
  2. SpEL bauen: Der MethodSecurityExpressionHandler liest den Ausdruck. Er baut einen Kontext mit authentication, den Parametern (#id) und Beans (@authz).
  3. Entscheidung: Der PreAuthorizeAuthorizationManager wertet aus. Er liest das Authentication-Objekt erst, wenn der Ausdruck es braucht (ein Supplier).
  4. Methode: Bei „ja“ läuft die echte Methode und lädt das Konto aus der DB.
  5. Post-Prüfung: @PostAuthorize prüft das Ergebnis als returnObject. Gehört das Konto Anna nicht, wird das Ergebnis nicht zurückgegeben.
  6. Ablehnung: Spring publiziert ein AuthorizationDeniedEvent und wirft eine AccessDeniedException.
  7. Antwort: Im Web-Request macht der ExceptionTranslationFilter daraus 403. In einem Batch-Job oder Kafka-Listener muss Ihr Code die Exception selbst behandeln.

3. Beispiel: Regeln an Service-Methoden

@Configuration
@EnableMethodSecurity                 // Pre/Post an, @Secured und JSR-250 aus
class SecurityConfig { }

@Target({METHOD, TYPE}) @Retention(RUNTIME)
@PreAuthorize("hasRole('{value}')")   // Template, braucht AnnotationTemplateExpressionDefaults-Bean
@interface HasRole { String value(); }

@Service
class AccountService {
  @PreAuthorize("@authz.canRead(#id, authentication)")    // eigene Bean "authz"
  Account readAccount(Long id) { ... }

  @PostAuthorize("returnObject.owner == authentication.name")
  Account readOwn(Long id) { ... }

  @HasRole("ADMIN")
  void close(Long id) { ... }
}

@Test @WithMockUser(username = "ben")
void benCannotReadAnnasAccount() {
  assertThrows(AccessDeniedException.class, () -> service.readOwn(1L));
}
GET /accounts/1   (Benutzer ben, Konto gehört anna)
HTTP/1.1 403 Forbidden

GET /accounts/1   (Benutzer anna)
HTTP/1.1 200 OK   {"id":1,"owner":"anna","balance":100}

Test benCannotReadAnnasAccount: PASSED

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spring Security 7.2, Spring Boot 4.2.

Die Alternative für Listen: nicht @PostFilter im Speicher, sondern Filtern in der Datenbank. Hier mit Row-Level Security in PostgreSQL:

alter table demo_method_security.account enable row level security;
create policy own_rows on demo_method_security.account
  using (owner = current_setting('app.username'));

begin; set local role app_user; set local app.username='anna';
select * from demo_method_security.account;
 id | owner | balance
----+-------+---------
  1 | anna  |     100
  3 | anna  |     300
(2 rows)

begin; set local role app_user; set local app.username='ben';
select * from demo_method_security.account where id=1;
 id | owner | balance
----+-------+---------
(0 rows)

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_method_security, Rolle app_user, danach gelöscht).

  1. @authz.canRead(...) ruft eine Spring-Bean. So bleibt komplexe Logik testbar in Java statt in langem SpEL.
  2. @PostAuthorize braucht das Ergebnis. Die Methode läuft also immer, auch bei „nein“. Darum nur für lesende Methoden.
  3. @HasRole("ADMIN") ist eine Meta-Annotation mit Template. Sie spart Wiederholung und Tippfehler in Strings.
  4. Ben sieht Annas Konto in der DB gar nicht: 0 Zeilen statt 403. Die DB filtert auch Listen und Paging korrekt.
  5. Die Rolle app_user ist kein Superuser. Der Tabellen-Besitzer und Superuser umgehen RLS ohne FORCE ROW LEVEL SECURITY.

4. Details, die Interviewer fragen

  1. @EnableMethodSecurity: Ersetzt das veraltete @EnableGlobalMethodSecurity. Standard: prePostEnabled = true. securedEnabled und jsr250Enabled muss man einschalten. Spring Boot schaltet Method Security nicht automatisch ein.
  2. Vier Pre/Post-Annotations: @PreAuthorize prüft vorher. @PostAuthorize prüft das Ergebnis. @PreFilter filtert eine Collection im Parameter (filterObject). @PostFilter filtert die zurückgegebene Collection.
  3. @Secured und @RolesAllowed: Ältere Annotations ohne SpEL. Die Doku empfiehlt @PreAuthorize.
  4. hasRole vs hasAuthority: hasRole('ADMIN') sucht die Authority ROLE_ADMIN. hasAuthority('SCOPE_read') vergleicht genau. Falscher Präfix ist der häufigste 403-Grund.
  5. Parameter in SpEL: #id braucht den Parameternamen. Er kommt aus @P, @Param oder dem Compiler-Flag -parameters. Der Spring-Boot-Parent (Maven) und das Gradle-Plugin setzen das Flag.
  6. Beans in SpEL: @authz.decide(#root) ruft eine Bean. Sie kann boolean, null (enthält sich), eine AuthorizationDecision oder einen AuthorizationManager liefern.
  7. Klasse vs Methode: Eine Annotation an der Klasse gilt für alle Methoden. Eine Annotation an der Methode ersetzt die der Klasse. Methoden ohne Annotation sind nicht geschützt.
  8. Interfaces: Annotations an Interfaces werden geerbt. Erbt eine Klasse widersprüchliche Annotations von zwei Interfaces, scheitert der Start.
  9. Gleiche Annotation zweimal: Zwei @PreAuthorize an einer Methode gehen nicht. Man kombiniert mit and/or oder ruft eine Bean.
  10. Self-Invocation: Ein Aufruf über this geht am Proxy vorbei. Die Prüfung fällt still weg. Lösung: Methode in eine andere Bean oder mode = AdviceMode.ASPECTJ.
  11. @AuthorizeReturnObject: Spring gibt einen Proxy des Ergebnisses zurück. Dann gelten die Annotations an dessen Gettern, z. B. @PreAuthorize an getEmail().
  12. @HandleAuthorizationDenied: Statt einer Exception liefert ein MethodAuthorizationDeniedHandler einen Ersatzwert, z. B. null oder "***". Gut zum Maskieren einzelner Felder.
  13. Templates: Mit einer AnnotationTemplateExpressionDefaults-Bean werden Platzhalter wie {value} in Meta-Annotations ersetzt.
  14. Eigene Logik: Ein eigener AuthorizationManager<MethodInvocation> ersetzt SpEL ganz. Ein eigener MethodSecurityExpressionHandler (als static @Bean) bringt z. B. eine RoleHierarchy.
  15. @PostAuthorize und @Transactional: Die Methode ist schon gelaufen. Hat sie geschrieben, ist die Änderung vielleicht schon passiert. Die Doku warnt ausdrücklich davor.

5. Vergleich

  • URL-Regeln in der Filter Chain: grob, schnell, vor jedem Controller. Kennen keine Daten. Gut als Grundschutz: „alles unter /admin nur für Admins“.
  • @PreAuthorize: fein, an Fachmethoden, kennt Parameter. Gilt auch, wenn der Service von Kafka oder einem Job gerufen wird.
  • @PostAuthorize: für „gehört dieses Objekt dem Benutzer?“, wenn man das Objekt erst laden muss.
  • @PostFilter: filtert im Speicher. Teuer bei grossen Listen und kaputt mit Paging (Seite hat dann weniger Einträge).
  • Filtern in der Query: where owner = :user oder Row-Level Security in der DB. Richtig für Listen und Paging.
  • Spring Security ACL: Rechte pro Objekt in eigenen Tabellen. Mächtig, aber schwer. Heute selten erste Wahl.
  • Externe Policy-Engine (z. B. OPA): Regeln zentral für viele Services. Mehr Betrieb, mehr Latenz.

6. In der Produktion

  1. Regeln greifen nicht: @EnableMethodSecurity fehlt. Alle Annotations werden still ignoriert. Lösung: Annotation setzen und einen Negativ-Test pro Regel schreiben.
  2. Neue Methode ohne Schutz: Jemand fügt eine Methode ohne Annotation hinzu. Sie ist offen. Lösung: Annotation an der Klasse als Standard, plus URL-Regel als zweite Linie.
  3. Paging kaputt mit @PostFilter: Eine Seite mit 20 Einträgen zeigt nach dem Filter 3. Lösung: in der Query filtern.
  4. 403 trotz richtiger Rolle: Das Token liefert ADMIN, die Regel sucht ROLE_ADMIN. Lösung: Authorities-Mapping prüfen, hasAuthority oder den Converter anpassen.
  5. Kein Benutzer in @Async: Der neue Thread hat keinen SecurityContext. @PreAuthorize wirft dann eine Exception. Lösung: DelegatingSecurityContextAsyncTaskExecutor.
  6. Langsame Regeln: @authz fragt bei jedem Aufruf die DB. Bei einer Liste mit 1000 Objekten sind das 1000 Abfragen. Lösung: Rechte einmal laden oder in der Query prüfen.

7. Diagnose

  • logging.level.org.springframework.security=TRACE: zeigt, welcher AuthorizationManager mit welchem Ergebnis entscheidet.
  • AuthorizationDeniedEvent mit einem @EventListener loggen: wer, welche Methode, welche Regel. Gut für Audit.
  • AopUtils.isAopProxy(bean) oder Debugger: Ist die Bean überhaupt ein Proxy?
  • Tests: @WithMockUser(roles = "ADMIN"), @WithMockUser(username = "ben"), und assertThrows(AccessDeniedException.class, …).
  • Actuator /actuator/beans: Sind die Method-Security-Advisors registriert?
  • PostgreSQL: select * from pg_policies zeigt RLS-Policies, falls man in der DB filtert.

8. Senior-Punkte

  1. Defense in Depth: URL-Regeln als Grundschutz, Method Security für Fachregeln, Query-Filter für Listen. Eine Ebene allein reicht nicht.
  2. Regeln an den Service, nicht an den Controller. So gelten sie auch für Kafka, Jobs und andere Einstiegspunkte.
  3. Wenig SpEL, viel Java: Komplexe Regeln in eine Bean (@authz) oder einen AuthorizationManager. SpEL-Strings prüft kein Compiler.
  4. Deny by default: Annotation an der Klasse oder Architektur-Test (z. B. ArchUnit), der jede öffentliche Service-Methode prüft.
  5. Listen gehören in die Datenbank gefiltert. @PostFilter nur für kleine Mengen.
  6. 404 statt 403 für fremde Objekte, wenn schon die Existenz geheim ist. Das ist eine bewusste Entscheidung.

10. Fallen

  • „Spring Boot aktiviert @PreAuthorize automatisch.“ → Falsch. Ohne @EnableMethodSecurity passiert nichts.
  • „@PostAuthorize verhindert, dass die Methode läuft.“ → Falsch. Sie läuft immer. Nur das Ergebnis wird blockiert.
  • „Zwei @PreAuthorize an einer Methode werden kombiniert.“ → Falsch. Das ist nicht unterstützt. Mit and kombinieren.
  • „Ein interner Aufruf ist auch geprüft.“ → Falsch. Self-Invocation umgeht den Proxy.
  • „@PostFilter ist ein guter Weg für Listen.“ → Nur für kleine Listen. Es filtert im Speicher und bricht Paging.
  • „hasRole('ROLE_ADMIN') ist korrekt.“ → Unnötig. hasRole setzt den Präfix selbst. Ohne Präfix: hasAuthority.

11. Fragen

Was ist Method Security?

Autorisierung an einzelnen Methoden mit Annotations wie @PreAuthorize. Sie ergänzt URL-Regeln um fachliche Prüfungen mit Parametern und Ergebnissen.

Wie aktivieren Sie Method Security?

Mit @EnableMethodSecurity an einer Konfigurationsklasse. Pre/Post-Annotations sind dann an, @Secured und JSR-250 nur mit eigenem Flag.

Wie funktioniert @PreAuthorize technisch?

Spring baut einen AOP-Proxy. Ein Interceptor wertet den SpEL-Ausdruck mit einem AuthorizationManager aus. Bei „nein“ wirft er eine AccessDeniedException.

@PreAuthorize vs @PostAuthorize?

Pre prüft vor dem Aufruf mit Parametern. Post prüft nach dem Aufruf mit dem Ergebnis returnObject, die Methode läuft also immer.

Was machen @PreFilter und @PostFilter?

Sie filtern Collections im Parameter oder im Ergebnis mit filterObject. Das passiert im Speicher.

Warum ist @PostFilter mit Paging problematisch?

Die DB liefert eine volle Seite, der Filter entfernt danach Einträge. Die Seite ist zu kurz, und die Gesamtzahl stimmt nicht.

@Secured vs @PreAuthorize?

@Secured kennt nur Rollen-Namen, kein SpEL. @PreAuthorize kann Parameter, Beans und Logik nutzen und ist die Empfehlung.

hasRole vs hasAuthority?

hasRole('X') sucht ROLE_X. hasAuthority('X') sucht genau X, z. B. SCOPE_read.

Wie greifen Sie in SpEL auf Parameter zu?

Mit #name. Der Name kommt aus @P, @Param oder dem Compiler-Flag -parameters.

Wie nutzen Sie eine Bean in einer Regel?

Mit @beanName.methode(...), z. B. @authz.canRead(#id, authentication). Die Logik ist dann normales, testbares Java.

Was passiert bei einer Annotation an Klasse und Methode?

Die Methoden-Annotation gewinnt. Die Klassen-Annotation gilt für alle anderen Methoden.

Warum wirkt @PreAuthorize bei Self-Invocation nicht?

Der Aufruf über this geht nicht durch den Proxy. Lösung: eigene Bean oder AspectJ-Modus.

Welche Exception kommt bei Ablehnung, und was sieht der Client?

AccessDeniedException. Im Web macht der ExceptionTranslationFilter daraus 403, oder 401, wenn niemand angemeldet ist.

Was ist eine Meta-Annotation in Spring Security?

Eine eigene Annotation wie @IsAdmin, die @PreAuthorize trägt. Mit Templates auch mit Parametern, z. B. @HasRole("ADMIN").

Was macht @AuthorizeReturnObject?

Es gibt einen Proxy des Ergebnisses zurück. Annotations an dessen Methoden werden dann auch geprüft, z. B. an getEmail().

Was macht @HandleAuthorizationDenied?

Es ersetzt die Exception durch einen Wert aus einem MethodAuthorizationDeniedHandler. So kann man Felder maskieren statt den ganzen Request abzulehnen.

Warum @PostAuthorize nicht auf schreibenden Methoden?

Die Methode ist schon gelaufen. Die Änderung kann schon geschrieben sein, bevor die Prüfung scheitert.

Wie testen Sie Method Security?

Mit @WithMockUser und einem Aufruf der Bean über den Spring-Kontext. Für jede Regel einen positiven und einen negativen Test.

Wie bekommt ein @Async-Thread den Benutzer?

Mit DelegatingSecurityContextAsyncTaskExecutor oder einer Context-Propagation. Sonst ist der SecurityContext leer.

Wann ersetzen Sie SpEL durch einen eigenen AuthorizationManager?

Wenn die Regel komplex ist, wiederverwendet wird oder Abhängigkeiten braucht. Java ist typisiert und testbar.

Was ist Row-Level Security?

Eine Datenbank-Funktion, die Zeilen pro Benutzer filtert. PostgreSQL setzt dafür Policies auf eine Tabelle; jede Query sieht nur erlaubte Zeilen.

Szenario: Ein Pentest zeigt, dass Benutzer fremde Rechnungen per ID lesen können. Was ändern Sie?

Eine Besitz-Prüfung an der Service-Methode, z. B. @PostAuthorize oder besser eine Query mit owner = :user. Dazu ein Negativ-Test pro Endpoint, eventuell 404 statt 403.

Szenario: Alle @PreAuthorize-Regeln sind nach einem Refactoring wirkungslos, Tests sind grün. Woran liegt es?

Wahrscheinlich fehlt @EnableMethodSecurity, oder die Aufrufe laufen jetzt intern über this. Die Tests prüfen nur den Erfolgsfall; es fehlen Negativ-Tests.

Szenario: Eine Liste zeigt pro Seite mal 20, mal 4 Einträge. Was ist los?

Vermutlich filtert @PostFilter nach dem Paging im Speicher. Lösung: in der Query oder per Row-Level Security filtern.
