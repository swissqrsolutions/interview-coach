Spring Data JPA

Kern: Spring Data JPA ist eine Schicht über JPA (meist Hibernate) und löst das Problem von immer gleichem DAO-Code. Man schreibt nur ein Repository-Interface, und Spring erzeugt die Implementierung zur Laufzeit. Queries kommen aus Methodennamen, aus @Query oder aus Specifications.

Antwort-Muster

Frage: Wie funktioniert ein Spring-Data-JPA-Repository intern?

  1. Mechanismus: Spring baut beim Start einen Proxy für das Interface. CRUD-Methoden gehen an SimpleJpaRepository, eigene Methoden an eine vorbereitete RepositoryQuery.
  2. Zahl: Ein Methodenname wird beim Start in einen PartTree zerlegt. Ein Page braucht eine zweite Query mit select count.
  3. Trade-off: Derived Queries sind schnell geschrieben, aber nur für einfache Bedingungen. Für Joins nehme ich @Query.
  4. Produktion: Eine Liste mit 100 Kunden erzeugt bei N+1 gleich 101 Queries. Ich löse das mit join fetch oder @EntityGraph.

1. Die Reise eines Repository-Aufrufs

  1. Beim Start: Spring liest jede Query-Methode. findByLastnameAndActiveTrue wird in einen PartTree zerlegt: Eigenschaften und Operatoren. Ein falscher Eigenschaftsname bricht den Start ab.
  2. Der Aufruf: Der Service ruft repo.findByLastname("Meier", PageRequest.of(0, 20)). Der Proxy schickt den Aufruf durch Interceptoren: Transaktion und Exception Translation (JPA-Fehler werden zu DataAccessException).
  3. Query bauen: Die passende RepositoryQuery bindet die Parameter. Bei abgeleiteten Queries baut sie eine Criteria-Query, bei @Query nutzt sie den JPQL- oder SQL-Text.
  4. SQL ausführen: Hibernate übersetzt in SQL und holt die Zeilen. Geladene Entities landen im Persistence Context.
  5. Count-Query: Der Rückgabetyp ist Page. Darum startet Spring eine zweite Query: select count(...). Bei Slice fällt sie weg.
  6. Konvertieren: Ist der Rückgabetyp eine Projektion, baut Spring einen Proxy oder ein DTO. Nur die nötigen Spalten werden gelesen.
  7. Ergebnis: Der Service bekommt eine Page. Greift er später auf eine Lazy-Beziehung zu, braucht er noch eine offene Session.

2. Aufbau

  1. Repository-Interface: Es erbt von JpaRepository<Customer, Long>. Es enthält keine Implementierung.
  2. Repository-Proxy: Spring baut beim Start einen Proxy für das Interface. Der Proxy ist eine Spring-Bean.
  3. SimpleJpaRepository: Die Standard-Implementierung für CRUD-Methoden. Beispiel: save, findById, deleteById.
  4. Query-Methoden: Eigene Methoden im Interface. Spring erzeugt für jede eine RepositoryQuery, also ein vorbereitetes Query-Objekt.
  5. EntityManager: Die JPA-API. Hibernate führt die Queries aus und verwaltet den Persistence Context, den Cache geladener Entities pro Transaktion.
  6. JDBC und Connection Pool: HikariCP verwaltet die Verbindungen zur Datenbank.

3. Details, die Interviewer fragen

  1. Repository-Hierarchie: Repository ist nur ein Marker. CrudRepository bringt CRUD. ListCrudRepository gibt List statt Iterable zurück. JpaRepository fügt JPA-Extras wie flush und saveAndFlush hinzu.
  2. Proxy-Bau: Die JpaRepositoryFactory baut den Proxy. Als Basisklasse nimmt sie SimpleJpaRepository. Für eigene Methoden fragt sie die Query-Lookup-Strategie.
  3. Query-Lookup: Die Standard-Strategie heisst CREATE_IF_NOT_FOUND. Spring sucht zuerst eine deklarierte Query. Findet es keine, baut es eine Query aus dem Methodennamen. Mit USE_DECLARED_QUERY bricht der Start ohne deklarierte Query ab.
  4. Derived Queries: Der Methodenname wird zur Query, z. B. findByLastnameAndAgeGreaterThan. Man begrenzt mit findFirst10By… oder einem Limit-Parameter. Lange Namen sind ein Zeichen für @Query.
  5. @Query: Der JPQL-Text steht an der Methode. Er hat Vorrang vor @NamedQuery. Mit nativeQuery = true oder @NativeQuery schreibt man echtes SQL. Benannte Parameter brauchen seit Version 4 kein @Param, wenn mit -parameters kompiliert wird.
  6. Native Query und Paging: Spring kann einfache Queries für Count und Sort umschreiben. Bei komplexen nativen Queries braucht man eine eigene countQuery.
  7. Projektionen: Eine Projektion liefert nur einen Teil der Entity. Es gibt Interface-Projektionen, DTO-Projektionen und dynamische Projektionen.
  8. Geschlossene Interface-Projektion: Sie hat nur Getter passend zu Feldern. Spring kann die Query optimieren.
  9. Offene Interface-Projektion: Sie nutzt @Value("#{target.firstname + ' ' + target.lastname}"). Es gibt keine Optimierung. Die ganze Entity wird geladen.
  10. DTO-Projektion: Ein DTO oder Record braucht keinen Proxy. Spring nutzt einen Konstruktor-Ausdruck. Verschachtelte Projektionen gehen nicht.
  11. Dynamische Projektion: Die Methode hat einen Class-Parameter, z. B. <T> List<T> findByLastname(String n, Class<T> type). So wählt der Aufrufer die Form.
  12. Page vs Slice vs Scroll: Page kennt die Gesamtzahl, kostet aber eine Count-Query. Slice weiss nur, ob es weitergeht. Die Scroll API (ScrollPosition, Window) erlaubt Keyset-Paging, also „weiter ab dem letzten Schlüssel“.
  13. Sort und Sicherheit: Spring Data lehnt Order mit Funktionsaufrufen ab. Für Ausdrücke wie LENGTH(firstname) braucht man JpaSort.unsafe.
  14. @Modifying: Es macht eine @Query zum Update oder Delete. flushAutomatically schreibt vorher offene Änderungen. clearAutomatically leert danach den Persistence Context. Beide sind standardmässig false.
  15. Transaktionen: SimpleJpaRepository ist auf Klassenebene mit readOnly = true transaktional. Schreibende CRUD-Methoden haben ein eigenes @Transactional. Eigene Query-Methoden haben keine Transaktion. Darum braucht @Modifying ein @Transactional.
  16. readOnly: readOnly = true setzt bei Hibernate den Flush-Modus auf MANUAL. Dirty Checking fällt weg. Es ist ein Hinweis zur Leistung, kein Schreibschutz.
  17. save(): save ruft persist bei einer neuen Entity, sonst merge. „Neu“ heisst, die ID ist null (oder die Version null). Bei selbst vergebenen IDs macht merge zuerst ein select. Die Lösung ist Persistable mit eigenem isNew().
  18. Derived Delete: deleteByLastname lädt zuerst alle Entities und löscht sie einzeln. So laufen @PreRemove-Callbacks, aber es ist langsam. Ein @Modifying-Delete ist eine einzige Query ohne Callbacks.
  19. Specifications: Eine Specification ist ein Stück Criteria-Bedingung als Objekt. Man kombiniert sie mit and und or zu dynamischen Filtern. Spring Data JPA 4.0 bringt PredicateSpecification, die vom Query-Typ unabhängig ist. Dazu kommen UpdateSpecification und DeleteSpecification.
  20. Fluent API: findBy(spec, q -> q.as(View.class).page(pageable)) kombiniert Specification, Projektion und Paging. Die Methode steht in JpaSpecificationExecutor.
  21. @EntityGraph: Er lädt Beziehungen gezielt mit, z. B. @EntityGraph(attributePaths = "company"). So löst man das N+1-Problem. Das heisst eine Query für die Liste plus eine pro Element.
  22. Open Session in View (OSIV): Spring Boot registriert im Web-Kontext standardmässig den OpenEntityManagerInViewInterceptor (spring.jpa.open-in-view=true). Der EntityManager bleibt den ganzen Request offen. Lazy Loading geht dann auch im Controller und bei der JSON-Serialisierung. Boot loggt beim Start eine Warnung, wenn man den Wert nicht explizit setzt.

4. Fallen

  • „Repository-Methoden sind immer transaktional.“ → Falsch. Nur die geerbten CRUD-Methoden. Eigene Query-Methoden brauchen @Transactional.
  • „readOnly = true verhindert Schreiben.“ → Falsch. Es ist ein Leistungshinweis. Hibernate überspringt Dirty Checking.
  • „@Modifying aktualisiert auch die geladenen Entities.“ → Falsch. Es geht direkt in die Tabelle. Der Persistence Context bleibt alt.
  • „deleteByX ist ein einziges DELETE.“ → Falsch. Es lädt alle Treffer und löscht sie einzeln.
  • „Eine Interface-Projektion lädt immer nur wenige Spalten.“ → Falsch. Nur eine geschlossene. Eine offene mit @Value lädt die ganze Entity.
  • „Open-in-View ist eine gute Lösung für LazyInitializationException.“ → Falsch. Es versteckt das Problem und kostet Verbindungen.

5. Selbsttest

Warum?

Warum schalten Sie Open-in-View aus?

Es hält die DB-Verbindung länger und erzeugt versteckte Queries in Controller und JSON-Serialisierung. Daten gehören im Service geladen.

Warum ist deleteByLastname langsam?

Es lädt alle Treffer und löscht jede Entity einzeln, damit Callbacks laufen. Für Bulk-Deletes eine @Modifying-Query nutzen.

Warum sind Inserts mit IDENTITY langsam?

Hibernate braucht die ID sofort nach jedem Insert und kann nicht bündeln. Mit SEQUENCE und hibernate.jdbc.batch_size geht Batching.

Wie innen?

Was ist Spring Data JPA?

Eine Schicht über JPA. Man schreibt Repository-Interfaces, Spring erzeugt die Implementierung als Proxy zur Laufzeit.

Wie entsteht die Implementierung eines Repository-Interfaces?

Beim Start baut Spring einen Proxy. CRUD-Methoden gehen an SimpleJpaRepository, eigene Methoden an vorbereitete Query-Objekte.

Wie funktioniert eine Derived Query?

Spring zerlegt den Methodennamen in Eigenschaften und Operatoren und baut daraus eine Criteria-Query. Ein falscher Name bricht den Start ab.

Sind Repository-Methoden transaktional?

Geerbte CRUD-Methoden ja, Lesen mit readOnly. Eigene Query-Methoden nein, dafür braucht man @Transactional.

Was macht save() bei einer neuen und einer bestehenden Entity?

Neue Entity: persist. Bestehende: merge. Neu heisst meist: ID oder Version ist null.

Was ist Open Session in View?

Der EntityManager bleibt für den ganzen HTTP-Request offen. Spring Boot aktiviert es standardmässig über spring.jpa.open-in-view.

Was ist eine LazyInitializationException?

Zugriff auf eine Lazy-Beziehung, nachdem die Session geschlossen ist. Lösung: im Service mit Fetch laden, nicht Open-in-View einschalten.

Was bewirkt readOnly = true bei Hibernate?

Der Flush-Modus wird MANUAL, Dirty Checking fällt weg. Das spart Zeit bei grossen Objektgraphen, schützt aber nicht vor Schreiben.

Zahlen

Was ist neu bei Specifications in Spring Data JPA 4?

PredicateSpecification ist unabhängig vom Query-Typ. Dazu kommen UpdateSpecification und DeleteSpecification für Updates und Deletes.

Page vs Slice?

Page kennt die Gesamtzahl und braucht dafür eine Count-Query. Slice weiss nur, ob es eine nächste Seite gibt, und ist darum billiger.

Wie viele Queries erzeugt eine Liste mit 100 Kunden bei N+1?

101. Eine Query für die Liste und je eine pro Kunde. Lösung: Fetch Join, @EntityGraph oder Batch Fetching.

Wie gross darf eine Seite höchstens sein?

Spring begrenzt mit spring.data.web.pageable.max-page-size. Der Standard ist 2000.

Vergleich

CrudRepository vs JpaRepository?

CrudRepository hat die Basis-CRUD-Methoden. JpaRepository erweitert um Listen, Paging, Sort und JPA-Methoden wie flush und saveAndFlush.

Wann nehmen Sie @Query statt Derived Query?

Bei Joins, Fetch Joins, Projektionen oder wenn der Methodenname zu lang wird. JPQL bleibt datenbankunabhängig.

Geschlossene vs offene Projektion?

Geschlossen: nur Getter passend zu Feldern, Spring liest nur diese Spalten. Offen: @Value-Ausdruck, Spring lädt die ganze Entity.

Spring Data JPA vs Spring Data JDBC?

JDBC hat keinen Persistence Context, kein Lazy Loading und kein Dirty Checking. Einfacher und vorhersehbarer, aber weniger Automatik.

Produktion

Was ist das N+1-Problem und wie lösen Sie es?

Eine Query für die Liste plus eine pro Element für eine Lazy-Beziehung. Lösung: Fetch Join, @EntityGraph, Batch Fetching oder DTO-Projektion.

Wie sehen Sie die SQL-Queries einer Anwendung?

logging.level.org.hibernate.SQL=DEBUG, Bind-Parameter mit TRACE, Hibernate Statistics und in PostgreSQL pg_stat_statements.

Szenario: Unter Last ist der Hikari-Pool leer, obwohl die Queries schnell sind. Was prüfen Sie?

Ob Open-in-View aktiv ist und Requests Verbindungen während langsamer Arbeit halten. Lösung: open-in-view=false, Daten im Service laden, Pool-Metriken beobachten.

Szenario: Eine Liste mit 50 Einträgen braucht 2 Sekunden. Im Log sind 51 Queries. Was tun Sie?

Das ist N+1. Ich lade die Beziehung mit Fetch Join oder @EntityGraph, oder ich nutze eine DTO-Projektion mit Join.

Szenario: Nach einem Bulk-Update zeigt der gleiche Request noch die alten Werte. Warum?

Die @Modifying-Query ändert nur die Tabelle, nicht den Persistence Context. Lösung: clearAutomatically = true oder Entities danach neu laden.

Design

Was ist bei nativen Queries mit Paging zu beachten?

Spring kann nur einfache Queries für Count umschreiben. Sonst muss man eine eigene countQuery angeben.

Was ist Keyset-Paging?

Man liest weiter ab dem letzten Schlüssel statt mit OFFSET. Es bleibt auch auf tiefen Seiten schnell. Spring Data bietet dafür die Scroll API.

Was macht @Modifying?

Es macht aus einer @Query ein Update oder Delete. Rückgabe ist die Anzahl geänderter Zeilen. Es braucht eine Transaktion.

Was bedeuten clearAutomatically und flushAutomatically?

flushAutomatically schreibt offene Änderungen vor der Query. clearAutomatically leert danach den Persistence Context, damit keine alten Entities bleiben.

Was ist eine Specification?

Eine Criteria-Bedingung als Objekt. Man kombiniert mehrere mit and/or zu dynamischen Filtern und ruft sie über JpaSpecificationExecutor auf.

Welche Arten von Projektionen gibt es?

Interface-Projektionen (geschlossen oder offen), DTO- bzw. Record-Projektionen und dynamische Projektionen mit einem Class-Parameter.

Mehr

Gerüst

  • Warum? Kein DAO-Code mehr. Man schreibt ein Interface, und Spring baut die Implementierung als Proxy.
  • Wie innen? Proxy → SimpleJpaRepository für CRUD, vorbereitete RepositoryQuery für eigene Methoden → EntityManager und Hibernate → HikariCP → DB. Der Methodenname wird beim Start in einen PartTree zerlegt.
  • Zahlen Page braucht eine zweite Count-Query, Slice nicht. Eine Liste mit 100 Kunden erzeugt bei N+1 gleich 101 Queries. Maximale Seitengrösse 2000.
  • Vergleich Derived Query für einfache Fälle, @Query für Joins, Specification für dynamische Filter. Spring Data JDBC hat keinen Persistence Context.
  • Produktion Open-in-View hält DB-Verbindungen, der Pool läuft leer. N+1 bei Listen. deleteBy… löscht einzeln.
  • Design open-in-view=false. Lesen mit DTOs, schreiben mit Entities. Offset-Paging für Seitenzahlen, Keyset für grosse Tabellen.

Beispiel: Repository mit allen Query-Arten

@Entity
class Customer {
  @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
  String firstname; String lastname; boolean active;
  @ManyToOne(fetch = FetchType.LAZY) Company company;
}

record CustomerView(String firstname, String lastname) {}   // DTO-Projektion

interface CustomerRepository extends JpaRepository<Customer, Long>,
                                     JpaSpecificationExecutor<Customer> {

  Page<CustomerView> findByLastname(String lastname, Pageable pageable);   // 1

  @Query("select c from Customer c join fetch c.company where c.id = :id")
  Optional<Customer> findWithCompany(Long id);                            // 2

  @Modifying(clearAutomatically = true)
  @Transactional
  @Query("update Customer c set c.active = false where c.lastname = :name")
  int deactivate(String name);                                             // 3
}

// Aufruf
repo.findByLastname("Meier", PageRequest.of(0, 20, Sort.by("firstname")));
repo.findWithCompany(7L);
repo.deactivate("Meier");
-- 1) Page mit Projektion
select c1_0.firstname,c1_0.lastname from customer c1_0
  where c1_0.lastname=? order by c1_0.firstname offset ? rows fetch first ? rows only
select count(c1_0.id) from customer c1_0 where c1_0.lastname=?
-- 2) join fetch: eine Query statt zwei
select c1_0.id,c1_0.active,c2_0.id,c2_0.name,c1_0.firstname,c1_0.lastname
  from customer c1_0 join company c2_0 on c2_0.id=c1_0.company_id where c1_0.id=?
-- 3) Bulk-Update, Rückgabe: Anzahl geänderter Zeilen
update customer set active=false where lastname=?

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). SQL-Log mit spring.jpa.show-sql=true, PostgreSQL-Dialekt. Aliasnamen und Formatierung hängen von der Hibernate-Version ab.

  1. Die DTO-Projektion liest nur zwei Spalten. Page erzeugt eine zweite Count-Query. offset/fetch first ist das Paging in SQL.
  2. join fetch lädt die Company in derselben Query. Ohne das käme beim Zugriff eine zweite Query, oder eine LazyInitializationException.
  3. @Modifying macht aus der Query ein Update. Es umgeht den Persistence Context. Darum clearAutomatically = true, sonst sieht man danach alte Entities.

Vergleich

  • Derived Query: schnell geschrieben, beim Start geprüft. Nur für einfache Bedingungen.
  • @Query (JPQL): volle Kontrolle, Joins, Fetch Joins, Projektionen. Bleibt datenbankunabhängig.
  • Native Query: echtes SQL, z. B. Window-Funktionen oder PostGIS. Keine Datenbankunabhängigkeit, Count-Query oft selbst schreiben.
  • Specification: dynamische Filter aus Bausteinen, typsicher mit dem JPA-Metamodell. Für Suchmasken mit vielen optionalen Feldern.
  • Querydsl / Query by Example: Alternativen für dynamische Queries. Query by Example ist sehr einfach, kann aber nur Gleichheit und String-Vergleiche.
  • Spring Data JDBC: kein Persistence Context, kein Lazy Loading, keine Dirty Checks. Einfacher und vorhersehbarer, aber weniger Komfort.
  • JdbcTemplate / JdbcClient: SQL von Hand, für Reports und Bulk-Arbeit. Kein ORM-Overhead.

In der Produktion

  1. Connection Pool leer durch Open-in-View: Der Request hält die Verbindung, solange Lazy Loading noch möglich ist. Ein langsamer Client oder ein externer Aufruf blockiert so eine DB-Verbindung. Lösung: spring.jpa.open-in-view=false und Daten im Service vollständig laden (Fetch Join, EntityGraph, DTO).
  2. N+1-Queries: Eine Liste mit 100 Kunden erzeugt 101 Queries. Lösung: join fetch, @EntityGraph, Batch Fetching (hibernate.default_batch_fetch_size) oder DTO-Projektion.
  3. Paging mit Collection-Fetch: join fetch auf eine Liste plus Pageable. Hibernate paginiert dann im Speicher und warnt mit „firstResult/maxResults specified with collection fetch; applying in memory“. Lösung: zuerst IDs paginieren, dann die Entities mit Fetch laden.
  4. Teure Count-Query: count(*) auf Millionen Zeilen bei jedem Seitenwechsel. Lösung: Slice, Keyset-Scrolling oder eigene schnelle countQuery.
  5. Alte Daten nach Bulk-Update: @Modifying ändert die Tabelle, aber nicht die Entities im Persistence Context. Lösung: clearAutomatically = true, oder Update vor dem Laden.
  6. Langsame Inserts: saveAll mit vielen Entities. Mit GenerationType.IDENTITY kann Hibernate Inserts nicht bündeln. Lösung: SEQUENCE und hibernate.jdbc.batch_size.
  7. Riesige Seiten: Ein Client fragt ?size=100000. Spring begrenzt mit spring.data.web.pageable.max-page-size (Standard 2000). Kleiner setzen.
  8. Page als JSON: PageImpl direkt zu serialisieren ist keine stabile API. Lösung: PagedModel oder @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO).

Diagnose: Werkzeuge und Einstellungen

  • spring.jpa.show-sql=true oder besser logging.level.org.hibernate.SQL=DEBUG: jede SQL-Query sehen.
  • logging.level.org.hibernate.orm.jdbc.bind=TRACE: die gebundenen Parameter sehen.
  • spring.jpa.properties.hibernate.generate_statistics=true: Anzahl Queries, Entities und Flushes pro Session.
  • Query-Zähler im Test (z. B. mit Hibernate Statistics): N+1 automatisch erkennen.
  • EXPLAIN ANALYZE in PostgreSQL: zeigt, ob ein Index genutzt wird.
  • HikariCP-Metriken über Actuator/Micrometer (hikaricp.connections.active, …pending): zeigt einen leeren Pool.
  • pg_stat_statements: die teuersten Queries in der Datenbank.

Senior-Punkte

  1. Open-in-View ausschalten. Es versteckt Lazy-Loading-Fehler und bindet DB-Verbindungen an die HTTP-Dauer. Die Transaktion gehört in den Service.
  2. Lesen mit DTOs, schreiben mit Entities. Projektionen lesen nur, was die Ansicht braucht. Entities lohnen sich, wenn man ändert.
  3. Jede Liste ist ein N+1-Kandidat. Fetch-Strategie bewusst pro Use Case wählen, nicht global EAGER setzen.
  4. Paging-Art ist eine API-Entscheidung: Offset-Paging für Seitenzahlen, Keyset für Endlos-Listen und grosse Tabellen.
  5. Bulk-Operationen am ORM vorbei sind schnell, aber umgehen Callbacks, Versionen und Cache. Das muss im Code sichtbar sein.
  6. Spring Data ist kein Ersatz für SQL-Wissen. Die generierte SQL muss man lesen und mit EXPLAIN prüfen.
