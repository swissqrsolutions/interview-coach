Spring Boot 2 → 3 → 4: Jakarta, Java 17+, Observability, Native Images

Kern: Spring Boot 3 ist die Generation auf Spring Framework 6, Java 17 und Jakarta EE (Paket jakarta.* statt javax.*). Sie brachte Observability mit Micrometer, GraalVM Native Images und ProblemDetail (RFC 9457). Spring Boot 4 (November 2025) baut auf Framework 7 und Jakarta EE 11 auf, bleibt bei Java 17 als Minimum und zerlegt Boot in kleine Module.

1. Wo sitzen die Generationen?

  1. Boot 2.7: Die letzte 2er-Version. Basis ist Java EE mit javax.*-Paketen.
  2. Boot 3.0: Neue Basis: Java 17, Spring Framework 6, Jakarta EE (Jakarta-EE-10-kompatible Abhängigkeiten), Spring Security 6, Hibernate 6.1.
  3. Boot 3.x Minor-Versionen: Neue Features ohne Bruch. Beispiele: @ServiceConnection in 3.1, @MockBean veraltet in 3.4. 3.5 ist die letzte 3er-Version.
  4. Boot 4.0: Spring Framework 7, Jakarta EE 11 mit Servlet 6.1, Spring Security 7, Hibernate 7, Jackson 3. Java-Minimum bleibt 17.
  5. Heute: Boot 4.1 kam im Juni 2026, auf spring.io ist aktuell 4.2 gelistet.

2. Die Reise einer Migration (die Geschichte zum Merken)

  1. Neueste 2.7: Zuerst auf die letzte 2.7.x. Alle Deprecation-Warnungen beheben. Was dort veraltet ist, fehlt in 3.0.
  2. Java 17 und Security 5.8: Die Anwendung läuft schon auf Java 17. Security zuerst auf 5.8, dort sind die 6er-APIs schon da.
  3. Boot 3.0: Version anheben. javax → jakarta: Imports wie javax.persistence werden zu jakarta.persistence. Auch alle Bibliotheken brauchen Jakarta-Versionen.
  4. Tests und Verhalten: Hibernate 6 erzeugt andere SQL. URL mit Schrägstrich am Ende (/orders/) passt nicht mehr automatisch. Eigene Auto-Configurations brauchen AutoConfiguration.imports statt spring.factories.
  5. Neueste 3.5: Hier die Vorbereitung für 4: @MockitoBean statt @MockBean, Lambda-DSL in Security, authorizeHttpRequests.
  6. Boot 4.0: Starter umbenennen (z. B. spring-boot-starter-webmvc), Jackson 3 (tools.jackson), Security 7, Test-Starter ergänzen.
  7. Aufräumen: spring-boot-properties-migrator zeigt umbenannte Properties beim Start. Nach der Migration wieder entfernen.

3. Beispiel: was sich im Code ändert

// Boot 2.7                                   // Boot 3.x / 4.x
import javax.persistence.Entity;              import jakarta.persistence.Entity;
import javax.validation.constraints.NotNull;  import jakarta.validation.constraints.NotNull;
import javax.servlet.http.HttpServletRequest; import jakarta.servlet.http.HttpServletRequest;

// ProblemDetail (Boot 3+), aktivieren mit spring.mvc.problemdetails.enabled=true
@RestControllerAdvice
class Errors {
  @ExceptionHandler(OrderNotFoundException.class)
  ProblemDetail notFound(OrderNotFoundException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setTitle("Order not found");
    pd.setProperty("orderId", e.id());
    return pd;
  }
}

// Observation API (Boot 3+): einmal messen → Metrik + Trace-Span
Observation.createNotStarted("order.import", registry)
           .lowCardinalityKeyValue("source", "xml")
           .observe(() -> importer.run());

 "detail":"Order 99 not found","instance":"/orders/99","orderId":99}

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Werte und Reihenfolge der Felder sind Beispiele.

  1. Nur die Paketnamen ändern sich. Die API bleibt gleich. Werkzeuge wie OpenRewrite automatisieren das.
  2. ProblemDetail ist das Fehlerformat nach RFC 9457 mit type, title, status, detail, instance. Eigene Felder kommen mit setProperty dazu. Content-Type ist application/problem+json.
  3. Eine Observation misst einmal und liefert Metrik und Trace-Span. Sie erscheint in Actuator und im Tracing-Backend.

4. Details, die Interviewer fragen

  1. Warum Java 17? Spring Framework 6 nutzt Records, Text Blocks und neuere APIs. Java 17 war die LTS-Version beim Start. Boot 4 behält 17 als Minimum und empfiehlt die neueste LTS.
  2. Warum jakarta? Java EE ging an die Eclipse Foundation. Die Marke javax durfte nicht weiter genutzt werden. Ab Jakarta EE 9 heissen die Pakete jakarta.*.
  3. Observability: Boot 3 nutzt die Observation API von Micrometer (ab 1.10). Eine Instrumentierung erzeugt Metriken und Traces. Micrometer Tracing ersetzt Spring Cloud Sleuth, das mit Boot 3 nicht mehr läuft. Backends: OpenTelemetry, Brave/Zipkin.
  4. Sampling: Standard ist 10 % der Traces (management.tracing.sampling.probability=0.1). Für Tests oft auf 1.0.
  5. AOT und Native Image: Boot 3 kann Anwendungen mit GraalVM zu nativen Programmen kompilieren. Spring macht dafür beim Build AOT-Verarbeitung: Es berechnet die Bean-Definitionen vorab und erzeugt Hinweise für Reflection.
  6. Grenzen von Native: Der Classpath ist beim Build fest. Beans dürfen sich zur Laufzeit nicht ändern. @Profile und @ConditionalOnProperty wirken nur eingeschränkt. Reflection, Ressourcen und Proxies brauchen Hinweise (RuntimeHints).
  7. ProblemDetail: Seit Spring Framework 6. In Boot opt-in mit spring.mvc.problemdetails.enabled=true (Standard false). ResponseEntityExceptionHandler liefert ProblemDetail für Spring-eigene Fehler.
  8. Auto-Configuration-Registrierung: Ab Boot 3.0 nur noch über META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Der Schlüssel in spring.factories geht nicht mehr.
  9. Trailing Slash: Ab Framework 6 passt /orders/ nicht mehr auf /orders. Ergebnis: 404.
  10. Actuator: /env und /configprops maskieren Werte standardmässig. httptrace heisst jetzt httpexchanges.
  11. Security 6: WebSecurityConfigurerAdapter ist entfernt. Man deklariert SecurityFilterChain-Beans. antMatchers wurde zu requestMatchers.
  12. HTTP-Clients: Apache HttpClient 4 wird in Framework 6 nicht mehr unterstützt, man braucht httpclient5. Neu: HTTP Interfaces mit @HttpExchange und RestClient (seit 6.1).
  13. Boot 4: modulare Starter. Statt grosser Jars gibt es kleine Module. spring-boot-starter-web heisst jetzt spring-boot-starter-webmvc. Jede Technologie hat einen Test-Starter. Für einen schnellen Umstieg gibt es spring-boot-starter-classic.
  14. Boot 4: Jackson 3. Neue Gruppen-IDs und Pakete: com.fasterxml.jackson wird tools.jackson. Jackson 2 geht noch, ist aber veraltet.
  15. Boot 4: Entfernt. Undertow (kann Servlet 6.1 nicht), @MockBean/@SpyBean, javax.annotation- und javax.inject-Annotationen, ListenableFuture.
  16. Boot 4 / Framework 7: Neu. API-Versionierung in MVC und WebFlux (spring.mvc.apiversion.*). HTTP Service Clients mit Auto-Configuration. @Retryable und @ConcurrencyLimit im Framework. JSpecify-Annotationen für Null-Sicherheit. OpenTelemetry-Starter. RestTestClient.
  17. Boot 4: Security 7. Kein and(), kein authorizeRequests. Multi-Faktor-Authentifizierung. Spring Authorization Server ist jetzt Teil von Spring Security.
  18. Boot 4: Native. GraalVM 25 oder neuer ist Pflicht.

5. Vergleich

  • Boot 2.7 → 3.0: der grosse Bruch. Java 17, jakarta, alle Bibliotheken müssen mitziehen. Aufwand steckt in Abhängigkeiten, nicht im eigenen Code.
  • Boot 3.5 → 4.0: kleiner im Code, breiter im Build. Starter-Namen, Jackson 3, Test-Annotationen, Security 7.
  • JVM vs Native Image: JVM: Warm-up, dann hohe Leistung, alles dynamisch. Native: Start in Millisekunden, wenig Speicher, aber lange Builds und weniger Dynamik.
  • Sleuth vs Micrometer Tracing: Sleuth war ein Spring-Cloud-Projekt nur für Tracing. Micrometer Tracing ist herstellerneutral und an die Observation API gekoppelt.
  • Eigenes Fehler-JSON vs ProblemDetail: ProblemDetail ist ein Standard. Clients und Gateways verstehen es ohne Absprache.

6. In der Produktion

  1. ClassNotFoundException für javax-Klassen: Eine Bibliothek nutzt noch javax.*. Lösung: Jakarta-Version der Bibliothek, sonst ersetzen. mvn dependency:tree zeigt die Quelle.
  2. 404 nach dem Upgrade: Clients rufen /orders/ mit Schrägstrich. Lösung: Clients anpassen oder ein Redirect-Filter. Nicht blind die alte Option zurückholen.
  3. Eigene Auto-Configuration lädt nicht: Sie steht noch in spring.factories. Lösung: AutoConfiguration.imports.
  4. Tracing fehlt nach Upgrade: Sleuth-Abhängigkeit ist weg. Lösung: Micrometer Tracing mit Bridge (OpenTelemetry oder Brave) und Exporter. In Boot 4 der OpenTelemetry-Starter.
  5. Andere SQL-Ergebnisse mit Hibernate 6: Typ-Mapping und Query-Übersetzung haben sich geändert. Lösung: Repository-Tests gegen die echte DB vor dem Upgrade.
  6. JSON sieht nach Boot 4 anders aus: Jackson 3 hat andere Standards und Pakete. Eigene Serializer und ObjectMapper-Konfiguration prüfen. Contract-Tests helfen.
  7. Native Image stürzt zur Laufzeit ab: Reflection ohne Hinweis. Lösung: RuntimeHints, @RegisterReflectionForBinding, Tests als Native Image laufen lassen.

7. Diagnose: Werkzeuge und Befehle

  • spring-boot-properties-migrator: meldet umbenannte und entfernte Properties beim Start.
  • OpenRewrite-Rezepte für Spring Boot: javax → jakarta, Security-DSL, Property-Namen.
  • mvn dependency:tree / gradle dependencies: alte javax-Abhängigkeiten finden.
  • /actuator/metrics, /actuator/prometheus: prüfen, ob Metriken nach dem Upgrade noch da sind.
  • Trace-ID im Log (Micrometer Tracing setzt sie in den MDC): prüfen, ob Tracing durchläuft.
  • mvn -Pnative native:compile und mvn -PnativeTest test: Native-Build und Tests mit den GraalVM Native Build Tools.
  • debug=true: Condition Evaluation Report, welche Auto-Configuration nach dem Upgrade fehlt.

8. Senior-Punkte

  1. In kleinen Schritten migrieren: Neueste Minor, Warnungen weg, dann die nächste Major. Nie Java, Boot und Bibliotheken gleichzeitig.
  2. Der Aufwand steckt in Abhängigkeiten. Vorher prüfen, ob jede Bibliothek eine Jakarta- bzw. Boot-4-Version hat.
  3. Tests vor dem Upgrade. Repository-Tests gegen die echte DB und Contract-Tests für JSON machen das Upgrade messbar.
  4. Support-Fenster planen: Open-Source-Support für eine Minor-Version ist begrenzt. Upgrades sind regelmässige Arbeit, kein Projekt alle fünf Jahre.
  5. Native Image ist eine Abwägung: lohnt sich für schnelle Starts und wenig Speicher. Für lange laufende Services mit hoher Last ist die JVM oft besser.
  6. Observability einmal richtig: Observation API, Trace-ID im Log, OTLP-Export. Dann sind Metriken, Logs und Traces verbunden.

10. Fallen

  • „Boot 4 braucht Java 21 oder 25.“ → Falsch. Minimum bleibt Java 17. Neuere LTS werden empfohlen.
  • „javax → jakarta ist nur Suchen und Ersetzen.“ → Falsch. Auch alle Bibliotheken müssen Jakarta-Versionen haben.
  • „ProblemDetail ist in Boot 3 automatisch aktiv.“ → Falsch. Opt-in mit spring.mvc.problemdetails.enabled=true.
  • „Spring Cloud Sleuth geht auch mit Boot 3.“ → Falsch. Der Nachfolger ist Micrometer Tracing.
  • „Native Images sind immer schneller.“ → Falsch. Nur beim Start und im Speicher. Spitzenleistung ist mit JIT oft höher.
  • „spring.factories funktioniert für Auto-Configuration weiter.“ → Falsch. Seit Boot 3.0 nur AutoConfiguration.imports.

11. Fragen

Was sind die grössten Änderungen in Spring Boot 3?

Java 17 als Minimum, Spring Framework 6, Jakarta EE statt javax, Observation API mit Micrometer, GraalVM Native Images und ProblemDetail.

Warum heisst es jakarta statt javax?

Java EE ging an die Eclipse Foundation, die Marke javax blieb bei Oracle. Ab Jakarta EE 9 heissen die Pakete jakarta.*.

Wie gehen Sie bei einer Migration von Boot 2 auf 3 vor?

Zuerst die neueste 2.7, Deprecations beheben, Java 17, Security 5.8. Dann Boot 3 mit properties-migrator und OpenRewrite, testen, Migrator entfernen.

Was macht spring-boot-properties-migrator?

Er meldet beim Start umbenannte oder entfernte Properties und mappt sie vorübergehend. Nach der Migration entfernt man ihn.

Was ist die Observation API?

Eine Micrometer-API ab 1.10. Man instrumentiert einmal und bekommt Metriken und Traces. Spring nutzt sie intern für Web, Datenbank und Messaging.

Was ersetzt Spring Cloud Sleuth?

Micrometer Tracing mit einer Bridge zu OpenTelemetry oder Brave. Sleuth läuft nicht mit Boot 3.

Wie viel wird standardmässig getraced?

10 % der Requests, über management.tracing.sampling.probability.

Was ist ein GraalVM Native Image?

Ein vorab kompiliertes, plattformspezifisches Programm ohne JVM zur Laufzeit. Startet in Millisekunden und braucht wenig Speicher.

Was macht Spring AOT?

Es berechnet beim Build die Bean-Definitionen vorab und erzeugt Code und Reflection-Hinweise. Native Images brauchen das.

Welche Grenzen haben Native Images mit Spring?

Fester Classpath, Beans dürfen sich zur Laufzeit nicht ändern, @Profile und @ConditionalOnProperty eingeschränkt. Reflection braucht Hinweise. Builds dauern lange.

Was ist ProblemDetail?

Das Standard-Fehlerformat nach RFC 9457 mit type, title, status, detail und instance. In Boot aktiviert mit spring.mvc.problemdetails.enabled=true.

Wie registriert man eigene Auto-Configurations in Boot 3?

In META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. spring.factories wird dafür nicht mehr gelesen.

Was hat sich beim URL-Matching geändert?

Trailing-Slash-Matching ist ab Framework 6 aus. /orders/ trifft /orders nicht mehr und gibt 404.

Was ist die Java-Version für Spring Boot 4?

Minimum Java 17, wie bei Boot 3. Framework 7 empfiehlt Java 25 als aktuelle LTS.

Was sind die wichtigsten Änderungen in Spring Boot 4?

Framework 7, Jakarta EE 11, Security 7, Hibernate 7, Jackson 3, modulare Starter, JSpecify, API-Versionierung, HTTP Service Clients, Undertow und @MockBean entfernt.

Was bedeutet die Modularisierung in Boot 4?

Boot liefert kleine Module statt grosser Jars. Starter heissen teils neu, z. B. spring-boot-starter-webmvc, und jede Technologie hat einen Test-Starter.

Was ändert Jackson 3?

Neue Gruppen-IDs und Pakete: tools.jackson statt com.fasterxml.jackson. Eigene Serializer und Mapper-Konfiguration müssen angepasst werden.

Was ist API-Versionierung in Framework 7?

Spring MVC und WebFlux können eine Version aus Header, Query-Parameter, Media Type oder Pfad lesen. Dieselbe URL kann mehrere Controller-Methoden je Version haben.

Warum wurde Undertow entfernt?

Undertow unterstützt Servlet 6.1 noch nicht, und Boot 4 setzt Servlet 6.1 voraus. Tomcat und Jetty bleiben.

Was ist JSpecify?

Ein Standard für Null-Annotationen wie @Nullable. Spring 7 und Boot 4 nutzen ihn statt der eigenen JSR-305-Annotationen.

Was ändert sich in Spring Security 7?

and() und authorizeRequests sind entfernt, nur noch Lambda-DSL. Neu sind Multi-Faktor-Authentifizierung und der integrierte Authorization Server.

Welche Resilience-Features bringt Framework 7?

@Retryable und @ConcurrencyLimit, aktiviert mit @EnableResilientMethods. Für einfache Fälle braucht man kein Spring Retry mehr.

Szenario: Nach dem Upgrade auf Boot 3 startet die App mit NoClassDefFoundError: javax/servlet/Filter. Was tun Sie?

Eine Bibliothek nutzt noch javax. Mit dependency:tree finde ich sie und nehme die Jakarta-Version oder ersetze sie.

Szenario: Nach dem Upgrade fehlen alle Traces in Jaeger. Woran denken Sie?

Sleuth ist weg. Ich brauche Micrometer Tracing mit OpenTelemetry-Bridge und OTLP-Exporter und prüfe das Sampling.

Szenario: Das Team will alle Services als Native Image bauen. Was raten Sie?

Nur wo Start und Speicher zählen, z. B. Functions oder viele kleine Pods. Für lange laufende Services mit Last bleibt die JVM, auch wegen Build-Zeit und Reflection-Aufwand.
