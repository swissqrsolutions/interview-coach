Spring MVC: DispatcherServlet, Request-Ablauf, Filter vs Interceptor

Kern: Der DispatcherServlet ist der Front Controller von Spring MVC, ein einziges Servlet nimmt alle Requests an. Er findet den passenden Controller, lässt die Argumente auflösen und die Antwort schreiben. Jeder Schritt ist eine austauschbare Strategie-Bean.

Antwort-Muster

Frage: Was passiert, wenn ein HTTP-Request bei Spring MVC ankommt?

  1. Mechanismus: Filter laufen zuerst. Der DispatcherServlet findet über das HandlerMapping den Controller, der HandlerAdapter löst die Argumente auf und ruft ihn auf.
  2. Zahl: Tomcat belegt pro Request einen Thread, standardmässig bis 200. Ein Fehler gibt zum Beispiel 406 oder 415.
  3. Trade-off: Ein Thread pro Request ist einfach und erlaubt blockierenden Code. Dafür legt ein langsamer Nachbar-Service die App lahm.
  4. Produktion: Unter Last steigen alle Antwortzeiten. Ich prüfe mit einem Thread Dump, ob alle Tomcat-Threads in einem Downstream-Aufruf warten.

1. Die Reise eines Requests

  1. Filter: POST /orders kommt an. Der Tracing-Filter setzt eine Trace-ID, Spring Security prüft das Token. Ein Filter kann den Request stoppen.
  2. Handler finden: Der DispatcherServlet fragt jedes HandlerMapping. RequestMappingHandlerMapping findet OrderController#create und liefert eine HandlerExecutionChain: Handler plus Interceptors.
  3. preHandle: Jeder Interceptor läuft. Gibt einer false zurück, endet der Request hier.
  4. Argumente auflösen: Der HandlerAdapter fragt HandlerMethodArgumentResolver pro Parameter. Für @RequestBody liest ein HttpMessageConverter (Jackson) das JSON. Danach läuft @Valid.
  5. Controller: Die Methode läuft und ruft den Service.
  6. Rückgabe schreiben: Ein ReturnValueHandler wählt per Content Negotiation (Header Accept) einen Converter. Er schreibt JSON und committet die Antwort.
  7. postHandle: Bei @ResponseBody ist die Antwort schon geschrieben. Header ändern geht hier nicht mehr.
  8. afterCompletion: läuft immer, auch nach Fehler. Gut für Aufräumen und Messen. Danach laufen die Filter rückwärts zu Ende.

Bei einer Exception springt der Ablauf zu den HandlerExceptionResolvern. Löst keiner sie, geht sie an den Container. Spring Boot leitet dann auf /error weiter.

2. Aufbau

  1. Servlet Container: Tomcat oder Jetty nimmt die HTTP-Verbindung an. Er gibt jedem Request einen Thread, Standard bei Tomcat bis 200.
  2. Filter Chain: Servlet-Filter laufen vor Spring MVC. Beispiel: Spring Security, CORS, Tracing.
  3. DispatcherServlet: das eine Servlet für alle Pfade (/). Er steuert, macht aber selbst wenig.
  4. HandlerMapping: findet den Handler für URL und Methode. Beispiel: RequestMappingHandlerMapping für @GetMapping.
  5. HandlerAdapter: ruft den Handler auf. Beispiel: RequestMappingHandlerAdapter für annotierte Controller.
  6. HandlerExceptionResolver: macht aus einer Exception eine Antwort. Beispiel: @ExceptionHandler-Methoden.

3. Details, die Interviewer fragen

  1. Front Controller: Er ist ein zentraler Einstieg für alle Requests. Der DispatcherServlet delegiert an Special Beans. Das sind HandlerMapping, HandlerAdapter, HandlerExceptionResolver, ViewResolver, LocaleResolver, MultipartResolver und FlashMapManager.
  2. Strategien laden: Beim Context-Refresh ruft der DispatcherServlet initStrategies auf. Er sucht alle Beans jedes Strategie-Typs und sortiert sie nach Order. Findet er keine, nimmt er die Defaults aus DispatcherServlet.properties.
  3. doDispatch: Die Methode ruft der Reihe nach getHandler, preHandle, den HandlerAdapter und postHandle auf. Dann folgt processDispatchResult. Am Ende läuft afterCompletion. Findet kein HandlerMapping einen Handler, gibt es einen 404.
  4. Exception im DispatcherServlet: processHandlerException löscht zuerst Content-Type und Puffer, falls die Antwort noch nicht committed ist. Dann fragt es jeden HandlerExceptionResolver der Reihe nach. Der erste mit einem Ergebnis gewinnt.
  5. HandlerMapping-Typen: RequestMappingHandlerMapping gilt für Annotationen. RouterFunctionMapping gilt für funktionale Endpoints. SimpleUrlHandlerMapping passt zum Beispiel für statische Ressourcen.
  6. Warum HandlerAdapter? Handler können sehr verschieden sein. Der Adapter versteckt, wie man sie aufruft. So bleibt der DispatcherServlet generisch.
  7. Argument Resolver: Ein HandlerMethodArgumentResolver liefert den Wert für einen Parameter. Beispiele sind @PathVariable, @RequestParam, @RequestHeader, @RequestBody und Principal. Eigene Resolver registriert man über WebMvcConfigurer.
  8. Message Converter: Ein HttpMessageConverter wandelt Body und Objekt um. Für JSON nimmt man Jackson. Spring Framework 7 und Boot 4 nutzen Jackson 3 im Paket tools.jackson. Jackson 2 bleibt als Fallback.
  9. Content Negotiation: Der Header Accept bestimmt das Antwortformat. Gibt es keinen passenden Converter, kommt 406. Ein falscher Content-Type im Request gibt 415.
  10. Interceptor-Methoden: preHandle kann den Request stoppen. postHandle läuft nach dem Handler. afterCompletion läuft immer am Ende.
  11. Header nach dem Controller ändern: Bei @ResponseBody geht das nicht in postHandle. Man nutzt ResponseBodyAdvice in einem @ControllerAdvice.
  12. Filter-Reihenfolge in Boot: Man setzt @Order auf der Filter-Klasse oder FilterRegistrationBean.setOrder. @Order auf der @Bean-Methode wirkt nicht.
  13. OncePerRequestFilter: Er läuft pro Request genau einmal. Das gilt auch bei internen Forwards oder Error-Dispatches.
  14. Path Matching: Spring MVC nutzt PathPatternParser. Spring Framework 7 hat Suffix-Matching und Trailing-Slash-Matching entfernt. /orders/ passt darum nicht auf /orders.
  15. API Versioning (Framework 7): Spring MVC kann Requests nach Version routen. Die Version kommt aus Header, Query-Parameter, Pfad-Segment oder Media-Type-Parameter. In Boot konfiguriert man das mit spring.mvc.apiversion.*.
  16. Validierung: @Valid @RequestBody wirft MethodArgumentNotValidException. Constraints direkt auf Parametern wie @Min lösen seit 6.1 die eingebaute Method Validation aus. Das wirft HandlerMethodValidationException.
  17. Threads: Ein Request belegt einen Thread. Bei Tomcat sind standardmässig maximal 200 erlaubt, über server.tomcat.threads.max. Mit spring.threads.virtual.enabled=true nutzt Tomcat Virtual Threads. Der Standard ist false.
  18. Async: Rückgabe von Callable, DeferredResult oder CompletableFuture gibt den Container-Thread frei. Die Antwort kommt später.

4. Fallen

  • „Interceptors laufen vor den Filtern.“ → Falsch. Filter umschliessen den DispatcherServlet. Interceptors laufen darin.
  • „In postHandle kann ich einen Header setzen.“ → Falsch bei @ResponseBody. Die Antwort ist schon committed.
  • „Ein Interceptor ist eine gute Security-Schicht.“ → Falsch. Die Doku empfiehlt Spring Security in der Filter-Kette.
  • „Der Controller wandelt JSON um.“ → Falsch. Das machen Argument Resolver und HttpMessageConverter.
  • „WebFlux ist immer schneller.“ → Falsch. Es braucht weniger Threads, aber nur mit nicht-blockierendem Code. Mit JDBC-Aufrufen bringt es nichts.
  • „/orders/ und /orders sind gleich.“ → Falsch seit Spring 6. In Spring 7 ist die alte Option entfernt.

5. Selbsttest

Warum?

Was macht ein HandlerAdapter?

Er ruft den Handler auf, egal welcher Art. So muss der DispatcherServlet keine Details kennen.

Wann kommt 415?

Wenn kein Converter den Content-Type des Requests lesen kann, z. B. text/plain statt application/json.

Warum kann postHandle keinen Header mehr setzen?

Bei @ResponseBody und ResponseEntity schreibt der HandlerAdapter die Antwort vorher. Lösung: ResponseBodyAdvice.

Wie innen?

Was ist der DispatcherServlet?

Der Front Controller von Spring MVC. Ein Servlet nimmt alle Requests an und delegiert an HandlerMapping, HandlerAdapter und weitere Strategie-Beans.

Beschreiben Sie den Weg eines Requests.

Filter, DispatcherServlet, HandlerMapping, preHandle, HandlerAdapter mit Argument Resolvern, Controller, Return Value Handler mit Converter, postHandle, afterCompletion, Filter zurück.

Was macht ein HandlerMapping?

Es findet zum Request den Handler und die passenden Interceptors. Ergebnis ist eine HandlerExecutionChain.

Was ist ein HandlerMethodArgumentResolver?

Eine Strategie, die einen Methodenparameter füllt, z. B. aus Pfad, Query, Header oder Body. Man kann eigene registrieren.

Was ist ein HttpMessageConverter?

Er wandelt den HTTP-Body in ein Objekt und zurück. Für JSON ist es Jackson.

Wie wählt Spring das Antwortformat?

Über Content Negotiation mit dem Accept-Header und den unterstützten Typen der Converter. Ohne Treffer kommt 406.

Was passiert bei einer Exception im Controller?

Die HandlerExceptionResolver versuchen sie zu lösen, z. B. @ExceptionHandler. Sonst geht sie an den Container, in Boot weiter an /error.

Welche Special Beans nutzt der DispatcherServlet?

HandlerMapping, HandlerAdapter, HandlerExceptionResolver, ViewResolver, LocaleResolver, MultipartResolver, FlashMapManager.

Wie lädt der DispatcherServlet seine Strategien?

Beim Context-Refresh ruft er initStrategies auf. Er sucht alle Beans jedes Typs und sortiert sie nach Order. Findet er keine, nimmt er die Defaults aus DispatcherServlet.properties.

Was macht doDispatch der Reihe nach?

getHandler, preHandle der Interceptors, HandlerAdapter mit dem Controller, postHandle, processDispatchResult und afterCompletion. Findet kein HandlerMapping einen Handler, gibt es einen 404.

Wie löst der DispatcherServlet eine Exception auf?

processHandlerException löscht Content-Type und Puffer, falls die Antwort noch nicht committed ist. Dann fragt es jeden HandlerExceptionResolver der Reihe nach. Der erste mit einem Ergebnis gewinnt.

Zahlen

Wie viele Requests verarbeitet Tomcat gleichzeitig?

Standard bis 200 Worker-Threads (server.tomcat.threads.max). Mit Virtual Threads gilt diese Grenze nicht.

Was ändert spring.threads.virtual.enabled?

Tomcat und andere Komponenten nutzen Virtual Threads. Blockierender Code skaliert dann besser. Standard ist false.

Was ist neu in Spring Framework 7 für MVC?

API Versioning, Jackson 3 als Standard, neue HttpMessageConverters-Konfiguration, alte Path-Matching-Optionen entfernt.

Vergleich

Filter vs Interceptor?

Filter: Servlet-Ebene, vor Spring MVC, sieht jeden Request, kennt keinen Handler. Interceptor: in Spring MVC, nach dem Mapping, kennt den Handler.

Wie unterscheidet sich WebFlux?

DispatcherHandler statt DispatcherServlet, WebFilter statt Servlet-Filter, nicht-blockierend mit Mono und Flux, meist auf Netty.

Wann wählen Sie WebFlux?

Bei Streaming, sehr vielen offenen Verbindungen und durchgehend reaktiven Treibern. Sonst MVC, eventuell mit Virtual Threads.

Produktion

Wie sehen Sie alle Endpoints einer App?

Mit /actuator/mappings. Es listet Controller, Filter und Servlets.

Szenario: Unter Last steigen die Antwortzeiten aller Endpoints, die CPU ist niedrig. Was prüfen Sie?

Thread Dump: Sind alle Tomcat-Threads in einem langsamen Downstream-Aufruf blockiert? Lösung: Timeouts, Circuit Breaker, Bulkhead, eventuell Virtual Threads.

Szenario: Ein Correlation-ID-Header soll in jeder Antwort stehen, auch bei 404 und Fehlern. Wo bauen Sie das?

In einem Servlet-Filter, der den Header vor chain.doFilter setzt. Ein Interceptor sieht nicht jeden Request und kommt bei Body-Antworten zu spät.

Szenario: Nach dem Upgrade liefert ein Endpoint 404, der vorher ging. Woran denken Sie?

An Path Matching: Trailing Slash oder Suffix wie .json passen nicht mehr. /actuator/mappings und DEBUG-Log prüfen, dann Clients oder Mapping anpassen.

Design

Welche Methoden hat ein HandlerInterceptor?

preHandle kann stoppen, postHandle läuft nach dem Handler, afterCompletion läuft immer am Ende.

Wie ordnen Sie Filter in Spring Boot?

@Order auf der Filter-Klasse, Ordered implementieren oder FilterRegistrationBean mit setOrder. @Order auf der Bean-Methode wirkt nicht.

Was ist OncePerRequestFilter?

Eine Basisklasse, die pro Request nur einmal läuft, auch bei Forward oder Error-Dispatch.

MethodArgumentNotValidException vs HandlerMethodValidationException?

Erste: @Valid auf einem @RequestBody-Objekt. Zweite: Constraints direkt auf Parametern, eingebaute Method Validation seit 6.1.

Mehr

Gerüst

  • Warum? Ein zentraler Einstieg macht Routing, Argumente und Fehler einheitlich. Jeder Schritt ist austauschbar.
  • Wie innen? Filter laufen vor dem DispatcherServlet. Dann kommen HandlerMapping, Interceptors, HandlerAdapter mit Argument Resolvern und der Controller.
  • Zahlen Tomcat hat standardmässig bis 200 Threads. Kein passender Converter gibt 406, ein falscher Content-Type gibt 415.
  • Vergleich Ein Filter kennt keinen Handler, ein Interceptor schon. MVC nutzt einen Thread pro Request, WebFlux ist nicht-blockierend.
  • Produktion Alle Threads sind belegt, wenn ein Downstream-Service langsam ist. Ein Header in postHandle kommt zu spät.
  • Design Security und Tracing gehören in Filter, Fehler in ein ControllerAdvice. Der Controller bleibt dünn.

Beispiel: Filter und Interceptor im Log

@Component @Order(1)
class TimingFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {
    log.info("filter before");
    try { chain.doFilter(req, res); } finally { log.info("filter after status={}", res.getStatus()); }
  }
}

class AuditInterceptor implements HandlerInterceptor {
  public boolean preHandle(HttpServletRequest r, HttpServletResponse s, Object h) { log.info("preHandle {}", h); return true; }
  public void postHandle(HttpServletRequest r, HttpServletResponse s, Object h, ModelAndView m) { log.info("postHandle committed={}", s.isCommitted()); }
  public void afterCompletion(HttpServletRequest r, HttpServletResponse s, Object h, Exception e) { log.info("afterCompletion ex={}", e); }
}

@Configuration
class WebConfig implements WebMvcConfigurer {
  public void addInterceptors(InterceptorRegistry reg) { reg.addInterceptor(new AuditInterceptor()).addPathPatterns("/orders/**"); }
}

@RestController
class OrderController {
  @PostMapping("/orders")
  ResponseEntity<OrderResponse> create(@Valid @RequestBody OrderRequest req) {
    log.info("controller");
    return ResponseEntity.status(201).body(new OrderResponse(42));
  }
}

  1. Der Filter läuft zuerst und zuletzt. Er umschliesst den ganzen DispatcherServlet.
  2. Das HandlerMapping findet die Methode. Erst danach kennt der Interceptor den Handler.
  3. Der Argument Resolver liest den Body mit Jackson. Der Return Value Handler schreibt die Antwort.
  4. postHandle sieht committed=true. Die Antwort ist schon unterwegs.
  5. afterCompletion läuft vor dem Ende des Filters. Der Filter sieht den finalen Status 201.

Vergleich

  • Filter: Servlet-Ebene, vor dem DispatcherServlet. Sieht jeden Request, auch statische Dateien und Fehler. Kennt keinen Handler. Beispiel: Security, CORS, Trace-ID, Request-Logging.
  • Interceptor: Spring-MVC-Ebene, nach dem HandlerMapping. Kennt den Handler (Methode, Annotationen). Laut Doku nicht ideal als Security-Schicht. Beispiel: Audit pro Controller, Locale.
  • AOP / ControllerAdvice: um die Controller-Methode oder für alle Controller. Beispiel: Exception Handling, ResponseBodyAdvice.
  • Spring MVC vs WebFlux: MVC: Servlet API, ein Thread pro Request, blockierend erlaubt. WebFlux: DispatcherHandler, nicht-blockierend mit Reactor (Mono/Flux), Standard-Server Netty, WebFilter statt Servlet-Filter.
  • WebFlux vs MVC mit Virtual Threads: Beide schaffen viele gleichzeitige Requests. Virtual Threads behalten den einfachen blockierenden Code. WebFlux lohnt sich bei Streaming und Backpressure.
  • @Controller vs @RestController: View-Name vs Body. @RestController = @Controller + @ResponseBody.

In der Produktion

  1. Alle Threads belegt: Ein langsamer Downstream-Service blockiert alle Tomcat-Threads. Neue Requests warten. Lösung: Timeouts, Circuit Breaker, Bulkhead, eventuell Virtual Threads.
  2. Header fehlt in der Antwort: Ein Interceptor setzt ihn in postHandle, zu spät. Lösung: ResponseBodyAdvice oder Filter mit Response-Wrapper.
  3. Security-Lücke durch Interceptor: Ein Interceptor prüft Pfade anders als das Mapping. Lösung: Security in die Filter-Kette (Spring Security).
  4. 404 nach Upgrade: Clients rufen /orders/ mit Slash. Seit 6.0 passt das nicht mehr, in 7 ist die Option entfernt. Lösung: Clients korrigieren oder Redirect-Filter.
  5. 406 / 415 Fehler: Falscher Accept- oder Content-Type-Header, oder Jackson fehlt im Classpath. Lösung: Header prüfen, DEBUG-Log von org.springframework.web.
  6. Body zweimal lesen: Ein Logging-Filter liest den Body, der Controller bekommt einen leeren Stream. Lösung: ContentCachingRequestWrapper und richtige Filter-Reihenfolge.
  7. Upgrade auf Jackson 3: Eigene ObjectMapper-Konfiguration greift nicht mehr. Lösung: Boot-4-Migration Guide, neue Pakete tools.jackson, JsonMapper-Beans.

Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.web=DEBUG: Mapping, gelesene und geschriebene Typen, Status pro Request.
  • spring.mvc.log-request-details=true (Standard false): zeigt Parameter und Header im DEBUG-Log. Vorsicht: sensible Daten.
  • /actuator/mappings: alle Endpoints, Filter und Servlets mit Mapping.
  • /actuator/metrics/http.server.requests: Dauer und Anzahl pro URI, Methode und Status.
  • Thread Dump (jcmd <pid> Thread.print): viele http-nio-8080-exec-*-Threads im Warten zeigen blockierte Requests.
  • Tracing (Micrometer Tracing / OpenTelemetry): zeigt die Zeit pro Schritt über Services hinweg.

Senior-Punkte

  1. Querschnitt an die richtige Stelle. Security und Tracing als Filter, Handler-bezogene Logik als Interceptor, Fehler im ControllerAdvice. Das gehört in ein Architektur-Review.
  2. Controller dünn halten. Er übersetzt nur HTTP in Service-Aufrufe. Logik, Transaktionen und Validierung der Fachregeln liegen im Service.
  3. MVC ist meist die richtige Wahl. Mit Virtual Threads skaliert blockierender Code gut. WebFlux nur bei echtem Streaming oder durchgehend reaktiven Treibern.
  4. Timeouts überall. Ein Thread pro Request heisst: ein langsamer Nachbar legt die ganze App lahm.
  5. Erweiterungspunkte kennen. Argument Resolver, Message Converter, ResponseBodyAdvice ersetzen viel duplizierten Controller-Code.
