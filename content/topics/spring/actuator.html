Actuator, Health Checks, Micrometer, Observability

Spring · Tier 2 · Quellen: Spring Boot 4.2 Reference („Endpoints“, „Metrics“, „Observability“), Spring Boot 4.2 Release Notes, Micrometer Doku (Concepts), Kubernetes Doku (Liveness, Readiness and Startup Probes)

Kern: Spring Boot Actuator ist ein Modul, das eine laufende Anwendung von aussen beobachtbar und steuerbar macht. Es liefert Endpoints wie /actuator/health und /actuator/prometheus. Micrometer ist die Metrik-Fassade dahinter: Der Code misst einmal, und Micrometer exportiert an Prometheus, OTLP oder andere Systeme.

1. Wo sitzt Actuator?

  1. Observations: Spring MVC, HTTP-Clients, JDBC-Pools und andere melden Messungen. Beispiel: jede HTTP-Anfrage wird zu http.server.requests.
  2. MeterRegistry: Micrometer sammelt die Werte als Meter (Zähler, Timer, Gauge) mit Tags wie uri und status.
  3. HealthIndicators: Kleine Prüfungen pro Abhängigkeit. Beispiel: db prüft, ob eine Verbindung gültig ist.
  4. Endpoints: Actuator macht alles per HTTP oder JMX sichtbar. Standard über HTTP: nur health.
  5. Draussen: Kubernetes ruft die Probes. Prometheus holt (scrape) die Metriken. Traces gehen per OTLP (OpenTelemetry-Protokoll) an einen Collector (push).

2. Die Reise eines Health-Checks

  1. kubelet fragt: Alle paar Sekunden ruft Kubernetes /actuator/health/readiness. Spring Boot stellt die Gruppen liveness und readiness standardmässig bereit.
  2. Health Group: Eine Health Group ist eine benannte Auswahl von Indicators. readiness enthält standardmässig nur readinessState.
  3. Indicators laufen: readinessState ist ACCEPTING_TRAFFIC, wenn die App gestartet ist. Beim Herunterfahren wechselt er auf REFUSING_TRAFFIC.
  4. Aggregieren: Der StatusAggregator sortiert alle Status. Der schlechteste gewinnt, z. B. ein DOWN unter fünf UP.
  5. HTTP-Code: DOWN und OUT_OF_SERVICE werden 503. UP und UNKNOWN werden 200.
  6. Readiness 503: Kubernetes nimmt den Pod aus dem Load Balancing. Er läuft weiter.
  7. Liveness 503: Kubernetes startet den Container neu. Hängt Liveness an der DB, starten bei einem DB-Ausfall alle Pods neu. Das macht den Ausfall grösser.

3. Beispiel: Konfiguration, Health, eigene Metrik

# application.yml
management:
  server.port: 8081                         # Actuator auf eigenem Port
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health:
    show-details: when-authorized
    probes.add-additional-paths: true        # /livez und /readyz auf Port 8080
    group.readiness.include: readinessState,db
  metrics.tags.application: order-service    # gemeinsamer Tag
  metrics.distribution.percentiles-histogram.http.server.requests: true

@Component
class OrderMetrics {
  private final Counter created;
  OrderMetrics(MeterRegistry registry) {
    created = Counter.builder("orders.created").tag("channel", "web").register(registry);
  }
  void onCreated() { created.increment(); }
}

@Component("payment")
class PaymentHealth implements HealthIndicator {
  public Health health() {
    return client.ping() ? Health.up().build()
                         : Health.down().withDetail("reason", "timeout").build();
  }
}
$ curl -s localhost:8081/actuator/health
{"status":"UP","groups":["liveness","readiness"]}

$ curl -s -o /dev/null -w "%{http_code}" localhost:8080/readyz
200

$ curl -s localhost:8081/actuator/prometheus | grep -E "orders_created|http_server_requests_seconds_count"
orders_created_total{application="order-service",channel="web"} 42.0
http_server_requests_seconds_count{application="order-service",error="none",exception="none",
  method="POST",outcome="SUCCESS",status="201",uri="/orders"} 42

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spring Boot 4.2 mit micrometer-registry-prometheus. Ohne Login zeigt health keine Details.

  1. Ohne Login sieht man nur den Gesamt-Status. show-details ist standardmässig never.
  2. Der Prometheus-Name bekommt _total für Zähler und _seconds für Timer. Micrometer übersetzt die Namen pro System.
  3. Das Tag uri ist das Template /orders bzw. /orders/{id}, nicht die echte URL. Sonst entstünden unendlich viele Zeitreihen.
  4. Mit percentiles-histogram exportiert Micrometer Histogramm-Buckets. Prometheus rechnet dann das p99 über alle Pods.
  5. db ist jetzt in der Readiness-Gruppe. Fällt die DB aus, nimmt Kubernetes den Pod aus dem Traffic, startet ihn aber nicht neu.

4. Details, die Interviewer fragen

  1. Exposure: Standardmässig ist über HTTP und JMX nur health sichtbar. Mehr mit management.endpoints.web.exposure.include. exclude gewinnt gegen include.
  2. Access: Jeder Endpoint hat einen Zugriffs-Level: none, read-only, unrestricted. shutdown und heapdump sind standardmässig gesperrt. management.endpoints.access.max-permitted setzt eine Obergrenze für alle.
  3. Security: Mit Spring Security und ohne eigene SecurityFilterChain schützt Boot alle Endpoints ausser health. Mit eigener Chain muss man die Regeln selbst schreiben.
  4. Sanitizing: /env und /configprops zeigen Werte standardmässig als ******. show-values kann never, when-authorized, always sein.
  5. Liveness vs Readiness: Liveness fragt „Ist der Prozess kaputt und braucht einen Neustart?“. Readiness fragt „Soll er gerade Traffic bekommen?“. Externe Systeme gehören höchstens in Readiness.
  6. Startup Probe: Kubernetes kennt eine dritte Probe für langsame Starts. Bis sie erfolgreich ist, wartet die Liveness-Probe. Man richtet sie oft auf den Liveness-Endpoint.
  7. Availability State: ApplicationAvailability hält LivenessState und ReadinessState. Code kann sie per AvailabilityChangeEvent.publish(...) ändern, z. B. „nicht bereit, Cache lädt noch“.
  8. Meter-Typen: Counter zählt nur hoch. Gauge zeigt einen aktuellen Wert (Queue-Länge). Timer misst Dauer und Anzahl. DistributionSummary misst Grössen (Bytes). LongTaskTimer misst laufende lange Aufgaben.
  9. Tags und Kardinalität: Jede Tag-Kombination ist eine eigene Zeitreihe. Ein Tag mit User-ID oder voller URL erzeugt Millionen Zeitreihen. Prometheus wird langsam oder fällt aus.
  10. Perzentile: Client-seitige Perzentile (percentiles) kann man nicht über Pods mitteln. Histogramme (percentiles-histogram) schon. Darum für Dashboards Histogramme.
  11. Observation API: Eine Observation misst einmal und erzeugt daraus Metrik und Span. Mit @Observed oder Observation.createNotStarted(...) für eigenen Code.
  12. Semantische Konventionen: Boot 4.2 kann mit management.observations.conventions=open-telemetry die stabilen OpenTelemetry-Namen nutzen. Dann ändern sich Metrik-Namen. Das bricht Dashboards.
  13. OTLP-Konfiguration: In Boot 4.2 setzt man Endpoint und Header einmal unter management.opentelemetry.otlp. Tracing, Logs und Metriken nutzen das gemeinsam.
  14. Caching: Lesende Endpoints ohne Parameter cachen ihre Antwort. Dauer: management.endpoint.<id>.cache.time-to-live.
  15. Eigener Endpoint: @Endpoint(id = "x") mit @ReadOperation, @WriteOperation, @DeleteOperation. Er funktioniert über HTTP und JMX.
  16. /loggers: Ein POST ändert das Log-Level zur Laufzeit, ohne Neustart. Sehr nützlich, aber nur geschützt freigeben.

5. Vergleich

  • Metriken: Zahlen über Zeit, billig, für Alarme und Trends. „Wie viele 5xx pro Minute?“
  • Logs: einzelne Ereignisse mit Text. „Was genau ist bei Bestellung 7 passiert?“
  • Traces: der Weg eines Requests über Services. „Welcher Service macht die 2 Sekunden?“
  • Micrometer vs OpenTelemetry SDK: Micrometer ist die Fassade in Spring. Es kann per OTLP exportieren. Das OTel SDK direkt ist herstellerneutral, aber ohne Spring-Integration.
  • Pull (Prometheus) vs Push (OTLP): Pull braucht eine erreichbare URL und Service Discovery. Push braucht einen Collector und geht durch Firewalls nach aussen.
  • Actuator vs Java Agent (z. B. OTel Java Agent): Actuator ist im Code und konfigurierbar. Ein Agent instrumentiert ohne Code-Änderung, ist aber schwerer zu kontrollieren.

6. In der Produktion

  1. Kaskaden-Neustarts: Liveness enthält db. Die DB hat 30 Sekunden Störung. Kubernetes startet alle Pods neu, danach Kaltstart-Last. Lösung: Liveness nur mit livenessState.
  2. Offene Endpoints: include: "*" ohne Security. /heapdump enthält Passwörter und Tokens im Speicher. Lösung: nur nötige Endpoints, eigener Port, nur intern erreichbar.
  3. Kardinalitäts-Explosion: Ein eigenes Tag mit Kunden-ID. Prometheus braucht plötzlich viel mehr RAM. Lösung: nur Tags mit wenigen Werten, MeterFilter als Grenze.
  4. Langsamer Health-Check: Ein Indicator ruft einen langsamen externen Service. Die Probe hat Timeout, der Pod gilt als krank. Boot loggt eine Warnung ab 10 Sekunden. Lösung: Ergebnis cachen oder asynchron prüfen.
  5. Kein graceful Shutdown: Pod bekommt SIGTERM, Requests brechen ab. Lösung: Graceful Shutdown (in Boot Standard) und Readiness wechselt sofort auf REFUSING_TRAFFIC.
  6. Dashboards brechen nach Upgrade: Metrik-Namen ändern sich, z. B. durch neue Konventionen. Lösung: Release Notes lesen, Dashboards als Code versionieren.

7. Diagnose

  • curl /actuator/health mit Login: zeigt Status jeder Komponente mit Details.
  • /actuator/metrics listet alle Meter-Namen. /actuator/metrics/http.server.requests?tag=status:500 filtert.
  • /actuator/threaddump: alle Threads, z. B. wenn alle Tomcat-Threads auf die DB warten.
  • /actuator/loggers/org.hibernate.SQL mit POST {"configuredLevel":"DEBUG"}: SQL live sehen, ohne Neustart.
  • PromQL: histogram_quantile(0.99, sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m]))) für das p99 pro Endpoint.
  • kubectl describe pod: zeigt fehlgeschlagene Probes und Neustarts (Liveness probe failed).
  • /actuator/conditions: zeigt, warum eine Auto-Configuration (z. B. Prometheus) nicht aktiv ist.

8. Senior-Punkte

  1. Liveness schlank, Readiness bewusst. Liveness prüft nur den eigenen Prozess. Ob eine DB in Readiness gehört, ist eine Entscheidung: Ohne DB nützt der Pod nichts, aber alle Pods fallen gleichzeitig raus.
  2. Actuator ist eine Angriffsfläche. Eigener Management-Port, nur im Cluster erreichbar, Security, minimale Exposure.
  3. Kardinalität ist ein Budget. Jedes neue Tag kostet Speicher in Prometheus. Hohe Kardinalität gehört in Logs oder Traces.
  4. Alarme auf Symptome, nicht auf Ursachen: Fehlerrate und Latenz (RED: Rate, Errors, Duration) statt CPU.
  5. Ein Standard für alle Services: gleiche Tags (application, env), gleiche Probes, gleiche Dashboards. Am besten als gemeinsame Auto-Configuration.
  6. Fachliche Metriken (Bestellungen pro Minute, Rückstau) sagen oft mehr als technische.

10. Fallen

  • „Actuator zeigt standardmässig alle Endpoints.“ → Falsch. Über HTTP nur health.
  • „Die DB gehört in den Liveness-Check.“ → Falsch. Ein DB-Ausfall startet dann alle Pods neu, ohne etwas zu lösen.
  • „Perzentile kann man über Pods mitteln.“ → Falsch. Nur Histogramme lassen sich korrekt zusammenrechnen.
  • „Ein Tag mehr kostet nichts.“ → Falsch. Jede Kombination ist eine Zeitreihe.
  • „/heapdump ist harmlos.“ → Falsch. Er enthält Secrets aus dem Speicher.
  • „Health UP heisst, die App funktioniert.“ → Nicht unbedingt. Health prüft nur, was die Indicators prüfen. Fachliche Fehler sieht man in Metriken.

11. Fragen

Was ist Spring Boot Actuator?

Ein Modul mit Endpoints für Health, Metriken, Konfiguration und Steuerung einer laufenden Anwendung. Es macht die App für Kubernetes und Monitoring sichtbar.

Welche Endpoints sind standardmässig über HTTP sichtbar?

Nur health. Alles andere muss man mit management.endpoints.web.exposure.include freigeben.

Wie schützen Sie Actuator-Endpoints?

Minimale Exposure, eigener Management-Port nur im Cluster, Spring Security mit Rolle. Gefährliche Endpoints wie heapdump und shutdown gesperrt lassen.

Liveness vs Readiness?

Liveness: Braucht der Prozess einen Neustart? Readiness: Soll er Traffic bekommen? Fehlende Readiness nimmt den Pod aus dem Service, fehlende Liveness startet ihn neu.

Gehört die Datenbank in den Liveness-Check?

Nein. Ein Neustart repariert die DB nicht. Alle Pods würden gleichzeitig neu starten.

Welchen HTTP-Code liefert health bei DOWN?

503. Auch OUT_OF_SERVICE wird 503. UP und UNKNOWN werden 200.

Wie wird der Gesamt-Status berechnet?

Der StatusAggregator sortiert alle Status nach einer Reihenfolge. Der schlechteste gewinnt.

Was ist eine Health Group?

Eine benannte Auswahl von Indicators mit eigenem Pfad, z. B. /actuator/health/readiness. Sie kann eigene Details- und Status-Regeln haben.

Wie schreiben Sie einen eigenen Health Check?

Eine Bean, die HealthIndicator implementiert und Health.up() oder Health.down() liefert. Der Bean-Name wird der Komponenten-Name.

Was ist Micrometer?

Eine Fassade für Metriken, wie SLF4J für Logs. Der Code nutzt eine API, der Export geht an Prometheus, OTLP oder andere Systeme.

Welche Meter-Typen gibt es?

Counter, Gauge, Timer, DistributionSummary, LongTaskTimer. Dazu FunctionCounter und FunctionTimer für bestehende Zähler.

Counter oder Gauge für die Queue-Länge?

Gauge. Die Queue-Länge steigt und fällt. Ein Counter steigt nur.

Was ist Kardinalität und warum ist sie gefährlich?

Die Anzahl verschiedener Tag-Kombinationen. Jede ist eine Zeitreihe in Prometheus. Zu viele kosten Speicher und machen Abfragen langsam.

Warum nutzt http.server.requests das URI-Template?

Damit /orders/1 und /orders/2 eine Zeitreihe /orders/{id} sind. Sonst wäre die Kardinalität unbegrenzt.

Warum Histogramme statt Perzentile?

Client-Perzentile sind pro Pod fertig gerechnet und nicht mittelbar. Histogramm-Buckets kann Prometheus über alle Pods summieren.

Was ist die Observation API?

Eine API in Micrometer, die einmal misst und daraus Metriken und Traces erzeugt. Spring nutzt sie für HTTP, Clients und Datenbanken.

Pull oder Push für Metriken?

Prometheus holt per Pull und braucht erreichbare Pods. OTLP schickt per Push an einen Collector. Kurzlebige Batch-Jobs brauchen Push, z. B. Pushgateway.

Wie ändern Sie ein Log-Level ohne Neustart?

POST auf /actuator/loggers/<name> mit {"configuredLevel":"DEBUG"}. Nur mit Schutz freigeben.

Warum sieht man in /env nur Sterne?

Actuator ersetzt Werte standardmässig durch ******. Mit show-values kann man das für berechtigte Benutzer lockern.

Wie nutzt Kubernetes die Probes bei einem Rolling Update?

Ein neuer Pod bekommt erst Traffic, wenn Readiness OK ist. Beim Stoppen meldet Readiness sofort „nicht bereit“, dann laufen offene Requests aus.

Was ist eine Startup Probe?

Eine Probe für langsame Starts. Bis sie erfolgreich ist, prüft Kubernetes Liveness nicht. So killt Kubernetes keinen Pod, der noch startet.

Was ist RED?

Rate, Errors, Duration: drei Kern-Metriken pro Service. Gute Basis für Alarme.

Szenario: Bei einer kurzen DB-Störung starten alle Pods neu und der Ausfall dauert 10 Minuten. Was ändern Sie?

Die DB ist in der Liveness-Gruppe. Liveness nur auf livenessState, die DB höchstens in Readiness. Dazu Startup Probe für den langsamen Start.

Szenario: Prometheus braucht nach einem Release fünfmal so viel RAM. Was prüfen Sie?

Neue Tags mit hoher Kardinalität, z. B. IDs oder rohe URLs. Mit PromQL die Meter mit den meisten Zeitreihen suchen, Tag entfernen oder per MeterFilter begrenzen.

Szenario: Ein Pentest findet /actuator/heapdump öffentlich erreichbar. Was tun Sie?

Sofort sperren, Secrets im Speicher als kompromittiert behandeln und rotieren. Danach eigener Management-Port, nur interne Erreichbarkeit, minimale Exposure und Security-Regeln.
