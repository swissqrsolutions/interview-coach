Bean Scopes

Kern: Ein Scope bestimmt, wie viele Instanzen einer Bean es gibt und wie lange sie leben. Standard ist singleton, also eine Instanz pro Container, geteilt von allen Threads. Andere Scopes sind prototype (neu bei jeder Anfrage), request und session (pro HTTP-Request oder -Session).

Antwort-Muster

Frage: Welche Bean Scopes gibt es und worauf muss man achten?

  1. Mechanismus: Der Standard ist singleton, eine Instanz pro Container. Prototype erzeugt bei jeder Anfrage eine neue Instanz, request und session binden sie an HTTP.
  2. Zahl: Ein Prototype in einem Singleton wird nur einmal injiziert. Er verhält sich dann wie ein Singleton.
  3. Trade-off: Singletons sind schnell, weil sie geteilt werden. Dafür müssen sie zustandslos und thread-sicher sein.
  4. Produktion: Unter Last sehen Benutzer manchmal Daten anderer Benutzer. Die Ursache ist ein veränderbares Feld in einem Singleton.

1. Die Reise einer Prototype-Bean in einen Singleton

  1. Start: Spring erzeugt den Singleton ImportService einmal beim Start.
  2. Injection: ImportService braucht einen CsvParser (prototype). Spring erzeugt einmal eine neue Instanz #1 und injiziert sie.
  3. Für immer #1: Abhängigkeiten werden nur beim Erzeugen aufgelöst. Der Singleton hält #1 für immer. Der Scope prototype hat keine Wirkung mehr.
  4. Race Condition: Zwei Requests importieren gleichzeitig. Beide schreiben in den Zustand von #1. Die Ergebnisse mischen sich.
  5. Fix: ImportService bekommt ObjectProvider<CsvParser> und ruft bei jedem Import getObject() auf.
  6. Neue Instanz: Jeder Import hat seinen eigenen Parser. Alternativen: @Lookup-Methode, Scoped Proxy oder jakarta.inject.Provider.

2. Aufbau

  1. singleton: eine Instanz pro Container und Bean-Definition. Beispiel: OrderService. Standard für fast alle Beans.
  2. prototype: jede Anfrage beim Container erzeugt eine neue Instanz. Beispiel: ein CsvParser mit internem Zustand.
  3. request: eine Instanz pro HTTP-Request. Beispiel: ein RequestContext mit Benutzer und Korrelations-ID.
  4. session: eine Instanz pro HTTP-Session. Beispiel: ein Warenkorb.
  5. application: eine Instanz pro ServletContext. Fast wie singleton, aber an den ServletContext gebunden.
  6. websocket: eine Instanz pro WebSocket-Sitzung.
  7. thread: existiert als SimpleThreadScope, ist aber nicht registriert. Man muss ihn selbst registrieren.

3. Details, die Interviewer fragen

  1. Spring-Singleton vs GoF-Singleton: Das GoF-Pattern erzwingt eine Instanz pro ClassLoader. Spring erzeugt eine Instanz pro Container und Bean-Definition. Zwei @Bean-Methoden mit derselben Klasse ergeben zwei Singletons.
  2. Prototype und Lebenszyklus: Spring erzeugt, füllt und initialisiert die Bean. Danach vergisst Spring sie. Destroy-Callbacks laufen nicht.
  3. Wann bekommt ein Singleton eine neue Prototype-Instanz? Nur einmal, beim eigenen Erzeugen. Danach nie wieder. Nur wenn er aktiv nachfragt, bekommt er eine neue.
  4. ObjectProvider: Er ist ein lazy Zugang zu Beans. Es gibt getObject() (Pflicht), getIfAvailable() (optional), getIfUnique() und stream(). Er erweitert ObjectFactory.
  5. @Lookup: Spring überschreibt die Methode per CGLIB. Sie ruft dann bei jedem Aufruf getBean() auf. Die Klasse darf darum nicht final sein.
  6. Scoped Proxy: Spring injiziert einen Proxy statt der echten Bean. Jeder Methodenaufruf sucht die Instanz im aktuellen Scope. Der Standard ist ein CGLIB-Proxy (ScopedProxyMode.TARGET_CLASS).
  7. Name der echten Bean: Die echte Bean hinter dem Scoped Proxy heisst scopedTarget. plus Bean-Name. Der Proxy trägt den normalen Namen.
  8. Scope-Interface: Ein Scope implementiert Scope. Die Methode get(name, objectFactory) liefert oder erzeugt die Instanz. Weitere Methoden sind remove und registerDestructionCallback.
  9. Speicherort im Request Scope: Die Bean liegt als Attribut im aktuellen RequestAttributes. Der erste Zugriff im Request erzeugt sie. Jeder weitere Zugriff im selben Request findet sie dort.
  10. @RequestScope und @SessionScope: Sie sind Kurzformen von @Scope("request") bzw. "session". Der Proxy-Modus ist TARGET_CLASS. Darum kann man sie direkt in Singletons injizieren.
  11. Request Scope ohne Request: In einem @Async-Thread oder @Scheduled-Job gibt es keinen gebundenen Request. Ein Zugriff wirft IllegalStateException. Die Meldung heisst „No thread-bound request found“ oder „Scope 'request' is not active“.
  12. Wie findet der Request Scope den Request? DispatcherServlet oder RequestContextFilter binden den Request an den Thread. Das geht über ThreadLocal.
  13. Thread-Sicherheit von Singletons: Spring macht nichts thread-sicher. Alle Request-Threads nutzen einen Singleton gleichzeitig. Darum muss er zustandslos (stateless) sein. Erlaubt sind nur final-Felder mit unveränderlichen oder thread-sicheren Objekten.
  14. Wenn Zustand nötig ist: Man nutzt lokale Variablen in der Methode, ConcurrentHashMap, AtomicLong oder einen kürzeren Scope. synchronized ist die letzte Wahl. Es bremst alle Requests.
  15. ThreadLocal in Singletons: In Thread-Pools bleibt der Wert am Thread hängen. Man löscht ihn immer im finally mit remove().
  16. Session Scope im Cluster: Die Session liegt im Speicher einer Instanz. Bei mehreren Pods braucht man Sticky Sessions oder Spring Session, zum Beispiel mit Redis. Die Bean muss dann serialisierbar sein.
  17. Eigener Scope: Man implementiert Scope. Man registriert ihn mit beanFactory.registerScope(...).

4. Fallen

  • „Ein Prototype in einem Singleton ist bei jedem Aufruf neu.“ → Falsch. Er wird nur einmal beim Erzeugen injiziert.
  • „Spring-Singletons sind thread-sicher.“ → Falsch. Spring synchronisiert nichts. Thread-Sicherheit ist Aufgabe des Codes.
  • „Spring ruft @PreDestroy für Prototypes auf.“ → Falsch. Nur Init-Callbacks laufen.
  • „Singleton heisst eine Instanz pro JVM.“ → Falsch. Pro Container und Bean-Definition.
  • „Request Scope funktioniert überall.“ → Falsch. Nur im Thread des Requests, nicht in @Async oder Jobs.

5. Selbsttest

Warum?

Warum kann man eine @RequestScope-Bean in einen Singleton injizieren?

@RequestScope erzeugt automatisch einen Scoped Proxy (TARGET_CLASS). Injiziert wird der Proxy, nicht die echte Instanz.

Was passiert bei @Scope("request") ohne Proxy in einem Singleton?

Der Start schlägt fehl: Beim Erzeugen des Singletons gibt es keinen aktiven Request.

Warum funktioniert Request Scope nicht in @Async?

@Async läuft in einem anderen Thread. Dort ist kein Request gebunden, darum kommt eine IllegalStateException.

Was ist das Problem mit ThreadLocal in Web-Apps?

Threads werden wiederverwendet. Ohne remove() sieht der nächste Request alte Werte, und es kann ein Memory Leak entstehen.

Wie innen?

Was ist ein Prototype-Bean?

Jede Anfrage beim Container liefert eine neue Instanz. Spring initialisiert sie, verwaltet sie danach aber nicht mehr.

Ruft Spring Destroy-Callbacks für Prototypes auf?

Nein. Der Aufrufer muss Ressourcen selbst freigeben.

Was passiert, wenn man einen Prototype in einen Singleton injiziert?

Der Singleton bekommt einmal eine Instanz und behält sie für immer. Der Prototype verhält sich dann wie ein Singleton.

Was ist ObjectProvider?

Ein lazy Zugang zu einer Bean. Methoden: getObject, getIfAvailable, getIfUnique, stream. Gut für optionale und Prototype-Beans.

Was macht @Lookup?

Spring überschreibt die Methode per CGLIB. Jeder Aufruf holt eine Bean aus dem Container, z. B. einen neuen Prototype.

Was ist ein Scoped Proxy?

Ein Stellvertreter, der in den Singleton injiziert wird. Bei jedem Aufruf leitet er an die Instanz des aktuellen Requests oder der Session weiter.

Wie weiss Spring, welcher Request aktuell ist?

DispatcherServlet oder RequestContextFilter binden den Request per ThreadLocal an den aktuellen Thread.

Wie erzeugt ein Scope seine Beans?

Über das Scope-Interface. get(name, objectFactory) liefert die vorhandene Instanz oder erzeugt eine neue. Der Request Scope legt sie als Attribut im aktuellen RequestAttributes ab.

Wie heisst die echte Bean hinter einem Scoped Proxy?

scopedTarget. plus Bean-Name. Der Proxy trägt den normalen Namen und wird injiziert.

Wann entsteht eine Request-Scope-Bean?

Beim ersten Zugriff im Request. Spring legt sie im aktuellen Request ab. Jeder weitere Zugriff im selben Request findet dieselbe Instanz.

Zahlen

Welche Bean Scopes gibt es in Spring?

singleton und prototype überall. request, session, application und websocket in einem web-fähigen Context. Dazu eigene Scopes.

Was ist der Standard-Scope?

singleton: eine Instanz pro Container und Bean-Definition, beim Start erzeugt.

Wie viele Singletons entstehen bei zwei @Bean-Methoden mit derselben Klasse?

Zwei. Ein Spring-Singleton gilt pro Container und Bean-Definition, nicht pro Klasse und nicht pro JVM.

Vergleich

Spring-Singleton vs Singleton-Pattern?

Das Pattern erzwingt eine Instanz pro ClassLoader. Spring hat eine Instanz pro Container und Bean-Definition. Zwei Definitionen ergeben zwei Instanzen.

Wie bekommt ein Singleton jedes Mal eine neue Prototype-Instanz?

Mit ObjectProvider.getObject(), einer @Lookup-Methode, jakarta.inject.Provider oder einem Scoped Proxy.

Produktion

Was ist das Problem mit Session Scope bei mehreren Instanzen?

Die Session liegt im Speicher einer Instanz. Man braucht Sticky Sessions oder externen Speicher wie Spring Session mit Redis.

Szenario: Unter Last sehen Benutzer manchmal Daten anderer Benutzer. Was prüfen Sie zuerst?

Veränderbare Felder in Singleton-Services oder Controllern, z. B. „currentUser“. Lösung: Feld entfernen, Wert als Parameter oder Request Scope.

Szenario: Ein @Async-Job wirft „No thread-bound request found“. Was tun Sie?

Der Job nutzt eine Request-Scope-Bean in einem anderen Thread. Ich kopiere die nötigen Werte vorher und übergebe sie als Parameter.

Szenario: Ein Import-Parser mit Fehlerliste liefert bei parallelen Importen gemischte Fehler. Warum?

Der Prototype-Parser ist in einen Singleton injiziert und wird geteilt. Lösung: ObjectProvider.getObject() pro Import.

Design

Sind Spring-Singletons thread-sicher?

Nein. Alle Request-Threads nutzen dieselbe Instanz. Sie müssen zustandslos oder selbst thread-sicher sein.

Wie schreiben Sie einen thread-sicheren Singleton?

Keine veränderbaren Felder. Nur final-Felder mit unveränderlichen oder thread-sicheren Objekten. Zustand in lokale Variablen oder Parameter.

Gibt es einen Thread Scope?

Ja, SimpleThreadScope. Er ist aber nicht registriert und muss selbst registriert werden.

Wann nutzen Sie prototype?

Für Beans mit Zustand, die Spring-Abhängigkeiten brauchen. Ohne Abhängigkeiten ist ein einfaches new oft klarer.

Mehr

Gerüst

  • Warum? Der Standard ist ein Singleton. Er wird von allen Threads geteilt, darum muss er zustandslos sein.
  • Wie innen? Der Container hält pro Bean-Definition einen Scope. Request und Session binden die Bean per ThreadLocal an den aktuellen Request.
  • Zahlen Ein Singleton pro Container und Bean-Definition. Ein Prototype in einem Singleton wird nur einmal injiziert.
  • Vergleich ObjectProvider ist die erste Wahl für Prototype in Singleton. Alternativen sind @Lookup und Scoped Proxy.
  • Produktion Unter Last sehen Benutzer Daten anderer Benutzer, wenn ein Singleton Zustand hält. Request Scope in @Async wirft eine IllegalStateException.
  • Design Singletons sind zustandslos. Zustand gehört in Parameter, Rückgabewerte oder die Datenbank.

Beispiel: Prototype in Singleton, falsch und richtig

@Component @Scope("prototype")
class CsvParser {
  private final List<String> errors = new ArrayList<>();   // Zustand!
  int id = SEQ.incrementAndGet();
}

@Service
class ImportServiceWrong {
  private final CsvParser parser;                 // einmal injiziert
  ImportServiceWrong(CsvParser parser) { this.parser = parser; }
  void run() { System.out.println("wrong: parser #" + parser.id); }
}

@Service
class ImportServiceRight {
  private final ObjectProvider<CsvParser> parsers;
  ImportServiceRight(ObjectProvider<CsvParser> parsers) { this.parsers = parsers; }
  void run() { System.out.println("right: parser #" + parsers.getObject().id); }
}

@RequestScope   // = @Scope("request") mit proxyMode TARGET_CLASS
@Component
class RequestInfo { String correlationId; }

// je 3× aufgerufen:
wrong.run(); right.run();
wrong: parser #1
wrong: parser #1
wrong: parser #1
right: parser #2
right: parser #3
right: parser #4

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Die genauen Nummern hängen von der Reihenfolge der Aufrufe ab.

  1. ImportServiceWrong sieht immer Parser #1. Abhängigkeiten werden nur einmal beim Erzeugen aufgelöst.
  2. ImportServiceRight holt bei jedem Aufruf eine neue Instanz über getObject().
  3. @RequestScope bringt automatisch einen Scoped Proxy mit. Ein Singleton kann RequestInfo injizieren. Jeder Aufruf geht an die Instanz des aktuellen Requests.
  4. Destroy-Callbacks gibt es für die Prototype-Parser nicht. Sie werden vom GC eingesammelt.

Vergleich

  • singleton: eine Instanz, geteilt, beim Start erzeugt, mit Destroy. Muss thread-sicher sein.
  • prototype: neue Instanz pro Anfrage, ohne Destroy. Gut für Objekte mit Zustand.
  • request: pro HTTP-Request, ein Thread. Gut für Request-Kontext.
  • session: pro Benutzer-Session, lange im Speicher. Schwierig im Cluster.
  • ObjectProvider: Typsicher, optional, ohne Proxy. Erste Wahl für Prototype in Singleton.
  • @Lookup: wenig Code, aber CGLIB-Unterklasse nötig.
  • Scoped Proxy: unsichtbar für den Aufrufer. Gut für request und session, verwirrend beim Debuggen.

In der Produktion

  1. Gemischte Daten zwischen Benutzern: Ein Singleton-Service speichert den aktuellen Benutzer in einem Feld. Unter Last sieht Benutzer A Daten von B. Lösung: Feld entfernen, Wert als Parameter übergeben oder Request Scope.
  2. Prototype wirkt wie Singleton: Ein Prototype mit Zustand ist in einen Singleton injiziert. Lösung: ObjectProvider.
  3. Fehler im Async-Thread: Ein @Async-Task greift auf eine Request-Scope-Bean zu und wirft IllegalStateException. Lösung: benötigte Werte vorher kopieren und als Parameter übergeben.
  4. Speicher wächst durch Sessions: Grosse Session-Beans bei vielen Benutzern füllen den Heap. Lösung: wenig in die Session, kurzer Timeout, externer Session-Speicher.
  5. Leck durch Prototypes: Prototypes mit offenen Ressourcen werden nie geschlossen. Lösung: try-with-resources beim Aufrufer.
  6. ThreadLocal-Leck: Ein ThreadLocal wird nicht gelöscht. Der nächste Request im gleichen Thread sieht alte Daten. Lösung: remove() im finally.

Diagnose: Werkzeuge und Befehle

  • /actuator/beans: zeigt den Scope jeder Bean.
  • Lasttest mit parallelen Requests (z. B. Gatling, k6): Race Conditions in Singletons zeigen sich nur unter Last.
  • Statische Analyse: SonarQube meldet veränderbare Felder in Spring-Komponenten.
  • Heap Dump mit Eclipse MAT: zeigt viele Prototype-Instanzen oder grosse Sessions.
  • Debugger: bean.getClass() zeigt $$SpringCGLIB$$ bei einem Scoped Proxy. AopUtils.isAopProxy(bean) prüft es im Code.

Senior-Punkte

  1. Singletons sind zustandslos. Das ist die wichtigste Regel. Zustand gehört in Parameter, Rückgabewerte oder die Datenbank.
  2. Prototype selten nutzen. Oft ist ein einfaches new in einer Fabrik-Methode klarer als ein Prototype-Bean.
  3. Request-Kontext explizit machen: Werte als Parameter übergeben ist leichter zu testen als ein Scoped Proxy.
  4. Session Scope begrenzt Skalierung. Zustandslose Services mit Token (z. B. JWT) skalieren horizontal einfacher.
  5. ObjectProvider vor @Lookup und Proxy: sichtbar im Konstruktor, ohne Magie, auch für optionale Beans.
