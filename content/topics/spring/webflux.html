Spring WebFlux und reaktive Programmierung

Spring · Tier 2 · Quellen: Spring Framework 7.1 Reference („Spring WebFlux“: Overview, Concurrency Model), Spring Boot 4.2 Release Notes (Reactor 3.9, Multipart-Limits), Reactor Core Reference und Javadoc Schedulers, Reactive Streams Spezifikation

Kern: Spring WebFlux ist das nicht-blockierende Web-Framework von Spring, gebaut auf Project Reactor. Es löst das Problem, dass ein Thread pro Request bei vielen langsamen I/O-Aufrufen viele Threads und viel Speicher braucht. WebFlux bedient viele Requests mit wenigen Event-Loop-Threads, etwa einem pro CPU-Kern.

1. Wo sitzt WebFlux?

  1. Reactor Netty: Der Standard-Server im WebFlux-Starter. Er hat wenige Event-Loop-Threads, die nur auf I/O-Ereignisse reagieren.
  2. DispatcherHandler: Das Gegenstück zum DispatcherServlet. Er findet den Handler und schreibt die Antwort ohne Blockieren.
  3. WebFilter: Filter für WebFlux. Servlet-Filter gibt es hier nicht.
  4. Handler: Annotierte Controller (@GetMapping) oder Router Functions (funktionale Routen). Beide liefern Mono oder Flux.
  5. Reaktive Clients: WebClient für HTTP, R2DBC für SQL-Datenbanken. Nur so bleibt die ganze Kette nicht-blockierend.

2. Die Reise eines reaktiven Requests

  1. Pipeline bauen: Der Controller gibt Mono<Order> zurück. Es ist ein Bauplan, noch ist nichts passiert. Diese Phase heisst Assembly.
  2. Subscribe: WebFlux abonniert den Bauplan. Erst jetzt startet die Arbeit. Ohne Subscribe passiert nichts (lazy).
  3. Backpressure: Der Subscriber fordert mit request(n) nur so viele Elemente an, wie er verarbeiten kann. So überrollt ein schneller Produzent keinen langsamen Konsumenten.
  4. I/O: Der R2DBC-Treiber schickt die Query. Der Thread wartet nicht. Er bedient sofort andere Requests.
  5. Daten da: Die DB antwortet. Ein Event-Loop-Thread ruft onNext auf. Es kann ein anderer Thread als in Schritt 1 sein.
  6. Operatoren: map wandelt um. flatMap startet einen weiteren asynchronen Aufruf, z. B. WebClient zum Lager-Service.
  7. Ende: onComplete oder onError beendet den Strom. WebFlux schreibt die Antwort. Ein Fehler läuft durch die Pipeline bis zu onErrorResume oder zum Framework.

3. Beispiel: Event Loop, blockierend vs nicht-blockierend

@GetMapping("/orders/{id}")
Mono<OrderView> get(@PathVariable long id) {
  return orderRepo.findById(id)                                   // R2DBC: Mono<Order>
      .switchIfEmpty(Mono.error(new OrderNotFound(id)))
      .flatMap(o -> stockClient.get().uri("/stock/{sku}", o.sku())
                     .retrieve().bodyToMono(Stock.class)
                     .timeout(Duration.ofSeconds(2))
                     .map(s -> new OrderView(o, s)));
}

// Blockierende Bibliothek? Dann weg vom Event Loop:
Mono.fromCallable(() -> legacyJdbcDao.load(id))
    .subscribeOn(Schedulers.boundedElastic());

Das Prinzip „ein Thread, viele Requests“ lässt sich mit Python asyncio echt messen. Es ist das gleiche Modell wie der Event Loop von Netty:

async def nonblocking(i): await asyncio.sleep(0.1)              # wie WebClient/R2DBC
async def blocking(i):    time.sleep(0.1)                       # wie JDBC auf dem Event Loop
async def offloaded(i):   await asyncio.to_thread(time.sleep, 0.1)   # wie boundedElastic
# je 100 "Requests" gleichzeitig mit asyncio.gather

nonblocking  100 Requests:  0.11 s, Threads=1
blocking     100 Requests: 10.06 s, Threads=1
offloaded    100 Requests:  0.56 s, Threads=21

Echte Ausgabe, Python 3.12.10 (asyncio). Das ist eine Analogie zum Modell, kein Spring-Code. Spring/Reactor ist hier nicht installiert.

  1. Nicht-blockierend: Ein Thread bedient 100 gleichzeitige Wartezeiten in 0,11 s. Das ist der Gewinn von WebFlux.
  2. Blockierend: Ein einziger blockierender Aufruf pro Request macht daraus 100 × 0,1 s = 10 s. Der Event Loop steht still, alle Requests warten.
  3. Ausgelagert: Ein eigener Thread-Pool rettet die Lage (0,56 s mit 20 Worker-Threads). In Reactor heisst das subscribeOn(Schedulers.boundedElastic()).
  4. Für fromCallable nimmt man subscribeOn, nicht publishOn. subscribeOn verlegt die Quelle, publishOn nur die Schritte danach.
  5. timeout(2s) am WebClient ist Pflicht. Ohne Timeout hängt ein Request bei einem toten Partner ewig.

4. Details, die Interviewer fragen

  1. Mono und Flux: Mono liefert 0 oder 1 Element. Flux liefert 0 bis N Elemente. Beide sind Publisher aus der Reactive Streams-Spezifikation (in Java 9 als java.util.concurrent.Flow).
  2. Vier Interfaces: Publisher, Subscriber, Subscription (mit request(n) und cancel()), Processor. Mehr ist die Spezifikation nicht.
  3. Backpressure: Der Konsument bestimmt das Tempo mit request(n). Kann eine Quelle nicht bremsen (z. B. Maus-Events), muss man puffern, verwerfen oder Fehler melden: onBackpressureBuffer, onBackpressureDrop.
  4. Cold vs Hot: Ein Cold Publisher startet für jeden Subscriber neu, z. B. eine HTTP-Abfrage. Ein Hot Publisher sendet unabhängig vom Subscriber, z. B. ein Event-Strom. share() oder cache() machen aus cold eher hot.
  5. map vs flatMap: map wandelt synchron 1 zu 1. flatMap gibt einen neuen Publisher zurück und läuft parallel, ohne Reihenfolge. concatMap hält die Reihenfolge, läuft aber nacheinander.
  6. subscribeOn vs publishOn: subscribeOn bestimmt den Thread der Quelle, egal wo es steht. publishOn wechselt den Thread für alle Schritte danach.
  7. Schedulers: parallel() hat einen Thread pro Kern, für CPU-Arbeit. boundedElastic() ist für blockierende Aufrufe: höchstens 10 × Kerne Threads, bis 100 000 wartende Aufgaben pro Thread.
  8. Fehlerbehandlung: onErrorResume (Ersatz-Publisher), onErrorReturn (Ersatzwert), onErrorMap (Exception umwandeln), retryWhen(Retry.backoff(...)). try/catch hilft nicht, der Fehler kommt später.
  9. Kontext statt ThreadLocal: Der Thread wechselt ständig. Darum funktionieren ThreadLocal, MDC und SecurityContextHolder nicht direkt. Reactor hat einen eigenen Context. Spring Security nutzt ReactiveSecurityContextHolder.
  10. Context Propagation: Die Bibliothek context-propagation überträgt Werte zwischen Context und ThreadLocal. Damit funktionieren Trace-IDs im Log. Aktiv mit Hooks.enableAutomaticContextPropagation().
  11. Transaktionen: @Transactional funktioniert reaktiv mit einem ReactiveTransactionManager (z. B. R2DBC). JPA-Transaktionen gibt es reaktiv nicht.
  12. R2DBC: Reaktiver Standard für SQL-Treiber. Spring Data R2DBC hat Repositories, aber kein Lazy Loading und keine Beziehungen wie JPA.
  13. Testen: StepVerifier prüft Signale Schritt für Schritt. WebTestClient testet Endpoints. BlockHound findet blockierende Aufrufe auf Event-Loop-Threads.
  14. WebClient in MVC: Man kann WebClient auch in Spring MVC nutzen. In Framework 7 ist für einfache, blockierende Aufrufe RestClient die erste Wahl.
  15. Multipart-Limits: Seit Boot 4.2 hat WebFlux Standard-Grenzen: höchstens 50 Teile und 1 MB Platte pro Teil. Grössere Uploads scheitern, bis man die Grenzen erhöht.

5. Vergleich

  • Spring MVC: ein Thread pro Request, einfacher Code, einfache Stacktraces, alle Bibliotheken (JPA, JDBC). Die Doku sagt: Funktioniert eine MVC-App gut, gibt es keinen Grund zu wechseln.
  • MVC mit Virtual Threads: blockierender Code, aber billige Threads (spring.threads.virtual.enabled=true, Java 21+). Löst das Thread-Problem für viele Fälle ohne reaktiven Stil.
  • WebFlux: echtes Streaming (Server-Sent Events, WebSocket), Backpressure, sehr viele gleichzeitige langsame Verbindungen, z. B. ein Gateway.
  • Kotlin Coroutines: reaktiver Unterbau, aber Code sieht sequentiell aus (suspend fun). WebFlux unterstützt sie direkt.
  • Leistung: Reaktiv ist nicht schneller pro Request. Es skaliert mit weniger Threads und weniger Speicher bei viel Warte-I/O.

6. In der Produktion

  1. Blockierender Aufruf auf dem Event Loop: Ein JDBC-Aufruf oder .block() im Handler. Mit 8 Event-Loop-Threads stehen nach 8 Requests alle still. Lösung: BlockHound in Tests, blockierende Teile auf boundedElastic.
  2. Nichts passiert: Ein Mono wird erzeugt, aber nie abonniert, z. B. repo.save(x); ohne Rückgabe. Lösung: jeden Publisher in die Kette einbauen und zurückgeben.
  3. Doppelte Aufrufe: Ein cold Mono wird zweimal abonniert. Der HTTP-Aufruf läuft zweimal. Lösung: cache() oder die Kette umbauen.
  4. Fehlende Trace-IDs im Log: MDC ist ThreadLocal, der Thread wechselt. Lösung: Context Propagation aktivieren.
  5. Speicher läuft voll: collectList() auf einem grossen Flux lädt alles in den Speicher. Lösung: streamen, buffer(n), Backpressure nutzen.
  6. Unlesbare Stacktraces: Der Fehler zeigt nur Reactor-Interna. Lösung: checkpoint("name") an wichtigen Stellen oder ReactorDebugAgent.

7. Diagnose

  • BlockHound (Java-Agent): wirft einen Fehler bei blockierenden Aufrufen auf nicht-blockierenden Threads. Ideal in Tests.
  • .log() in der Kette: zeigt alle Signale (onSubscribe, request, onNext) mit Thread-Namen.
  • checkpoint("orderLookup") und ReactorDebugAgent.init(): bessere Stacktraces mit Assembly-Ort.
  • Thread-Dump (/actuator/threaddump): Hängen reactor-http-nio-*-Threads in socketRead oder JDBC? Dann blockiert jemand.
  • Micrometer: flux.name("orders").tap(Micrometer.observation(registry)) misst Dauer und Fehler eines Flux.
  • StepVerifier.withVirtualTime(...): testet Timeouts und Retries ohne echte Wartezeit.

8. Senior-Punkte

  1. WebFlux nur mit Grund. Ein reaktiver Stack lohnt sich nur, wenn alles nicht-blockierend ist. Ein JPA-Aufruf in der Mitte zerstört den Vorteil.
  2. Virtual Threads verschieben die Entscheidung. Für „viele wartende Requests“ reicht heute oft MVC mit Virtual Threads. WebFlux bleibt stark bei Streaming und Backpressure.
  3. Kosten für das Team: steile Lernkurve, schwierigeres Debugging, andere Testwerkzeuge. Klein starten und messen.
  4. Gute Kandidaten: API-Gateways, Proxy-Services, Server-Sent Events, Fan-out zu vielen Services. Schlechte Kandidaten: CRUD mit JPA.
  5. Timeouts und Retries an jeden externen Aufruf. Reaktiv verschluckt sonst Hänger still.
  6. Gemischte Architektur ist okay: MVC-Services mit RestClient, ein reaktives Gateway davor.

10. Fallen

  • „WebFlux ist schneller als MVC.“ → Falsch. Es skaliert mit weniger Threads. Pro Request ist es oft etwas langsamer.
  • „Ein Mono läuft, sobald ich es erzeuge.“ → Falsch. Erst ein Subscribe startet die Arbeit.
  • „JPA funktioniert gut mit WebFlux.“ → Falsch. JPA blockiert. Reaktiv heisst R2DBC oder ein reaktiver Treiber.
  • „publishOn macht fromCallable nicht-blockierend.“ → Falsch. Die Quelle verlegt nur subscribeOn.
  • „MDC und SecurityContextHolder funktionieren wie in MVC.“ → Falsch. Der Thread wechselt; man braucht den Reactor Context.
  • „.block() im Controller ist okay.“ → Falsch. Auf einem Event-Loop-Thread wirft Reactor sogar eine Exception.

11. Fragen

Was ist Spring WebFlux?

Das nicht-blockierende Web-Framework von Spring auf Basis von Reactor. Es bedient viele Requests mit wenigen Event-Loop-Threads.

Was ist der Unterschied zwischen Mono und Flux?

Mono liefert 0 oder 1 Element, Flux 0 bis N. Beide sind Reactive-Streams-Publisher.

Was ist Backpressure?

Der Konsument bestimmt mit request(n), wie viele Elemente er bekommt. So überlastet ein schneller Produzent keinen langsamen Konsumenten.

Was ist Reactive Streams?

Eine kleine Spezifikation mit Publisher, Subscriber, Subscription und Processor. Sie definiert asynchrone Ströme mit Backpressure; Java 9 hat sie als Flow übernommen.

Warum braucht WebFlux so wenige Threads?

Threads warten nicht auf I/O. Sie reagieren nur auf Ereignisse und sind sofort frei für andere Requests.

Was passiert bei einem blockierenden Aufruf auf dem Event Loop?

Der Thread steht still, und alle Requests auf diesem Thread warten. Bei wenigen Threads friert die ganze App ein.

Wie binden Sie eine blockierende Bibliothek ein?

Mono.fromCallable(...) mit subscribeOn(Schedulers.boundedElastic()). So läuft der Aufruf auf einem eigenen Pool.

subscribeOn vs publishOn?

subscribeOn legt den Thread der Quelle fest, egal wo es steht. publishOn wechselt den Thread für alle folgenden Schritte.

map vs flatMap vs concatMap?

map: synchron 1 zu 1. flatMap: asynchron, parallel, ohne Reihenfolge. concatMap: asynchron, nacheinander, mit Reihenfolge.

Cold vs Hot Publisher?

Cold startet für jeden Subscriber neu, z. B. ein HTTP-Aufruf. Hot sendet unabhängig vom Subscriber, z. B. ein Event-Strom.

Was bedeutet „nothing happens until you subscribe“?

Eine Reactor-Kette ist nur ein Bauplan. Erst das Abonnieren startet die Arbeit. In WebFlux abonniert das Framework.

Wie behandeln Sie Fehler in Reactor?

Mit Operatoren: onErrorResume, onErrorReturn, onErrorMap, retryWhen. try/catch greift nicht, weil der Fehler später kommt.

Warum funktioniert ThreadLocal in WebFlux nicht?

Ein Request wechselt mehrmals den Thread. Werte gehören in den Reactor Context; Context Propagation überträgt sie für Logs und Tracing.

Kann man JPA mit WebFlux nutzen?

Technisch auf boundedElastic, aber dann verliert man den Vorteil. Reaktiv sind R2DBC oder reaktive NoSQL-Treiber.

Was ist R2DBC?

Ein reaktiver Standard für SQL-Treiber. Spring Data R2DBC bietet Repositories, aber kein Lazy Loading und keine JPA-Beziehungen.

Wie testen Sie reaktiven Code?

Mit StepVerifier für Signale, WebTestClient für Endpoints und BlockHound gegen versteckte Blockaden.

Was ist BlockHound?

Ein Java-Agent, der blockierende Aufrufe auf nicht-blockierenden Threads erkennt und einen Fehler wirft.

WebFlux oder MVC mit Virtual Threads?

Für blockierenden Code mit vielen wartenden Requests: MVC mit Virtual Threads, einfacher. Für Streaming, Backpressure und reaktive Ketten: WebFlux.

Was sind Router Functions?

Ein funktionales Modell: Routen und Handler als Lambdas statt Annotations. Es ist explizit und gut testbar.

Was liefert WebFlux für Server-Sent Events?

Ein Flux mit produces = TEXT_EVENT_STREAM_VALUE. Jedes Element wird ein Event, die Verbindung bleibt offen.

Ist reaktiver Code automatisch parallel?

Nein. Eine Kette läuft sequentiell, ein Element nach dem anderen. Parallelität entsteht durch flatMap oder parallel().

Szenario: Ein WebFlux-Service antwortet unter Last gar nicht mehr, die CPU ist niedrig. Was prüfen Sie?

Blockierende Aufrufe auf dem Event Loop. Thread-Dump: hängen reactor-http-nio-Threads in JDBC oder Socket-Reads? BlockHound in Tests, blockierende Teile auf boundedElastic.

Szenario: Ein Bestell-Endpoint speichert manchmal nichts, ohne Fehler. Woran liegt es?

Wahrscheinlich wird ein save()-Mono erzeugt, aber nicht in die Kette eingebaut und nie abonniert. Lösung: then(repo.save(x)) oder flatMap.

Szenario: Das Team will einen JPA-CRUD-Service auf WebFlux umstellen, „weil es moderner ist“. Was sagen Sie?

Kein Gewinn: JPA blockiert, der Code wird komplexer. Erst messen, ob Threads das Problem sind; dann eher Virtual Threads. WebFlux für Gateways und Streaming.
