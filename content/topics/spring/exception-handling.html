Fehlerbehandlung: @ControllerAdvice, ProblemDetail

Kern: Fehlerbehandlung in Spring MVC ist die Kette, die aus einer Exception eine saubere HTTP-Antwort macht. @ExceptionHandler-Methoden, meist zentral in einem @ControllerAdvice, übersetzen Fehler. ProblemDetail liefert dafür das Standardformat aus RFC 9457.

1. Wo sitzt die Fehlerbehandlung?

  1. Controller: wirft eine Exception, z. B. OrderNotFoundException.
  2. ExceptionHandlerExceptionResolver: sucht eine passende @ExceptionHandler-Methode. Zuerst im Controller selbst, dann in @ControllerAdvice-Klassen.
  3. ResponseStatusExceptionResolver: nutzt @ResponseStatus auf der Exception-Klasse und ResponseStatusException.
  4. DefaultHandlerExceptionResolver: übersetzt eingebaute Spring-Exceptions in Status-Codes, z. B. 405 oder 415.
  5. Container und /error: Löst niemand die Exception, geht sie an den Servlet Container. Spring Boot zeigt sie über /error an.
  6. Antwort: Ein ProblemDetail wird als application/problem+json geschrieben.

2. Die Reise einer Exception (die Geschichte zum Merken)

  1. throw: Der Service wirft OrderNotFoundException("Order 99"). Sie fliegt durch den Controller nach oben.
  2. Handler suchen: Der DispatcherServlet fängt sie und fragt die Resolver. Lokale @ExceptionHandler im Controller kommen vor globalen im Advice.
  3. Beste Methode: Passen mehrere, gewinnt der Typ mit der kleinsten Distanz (ExceptionDepthComparator). Die Exception selbst schlägt eine Cause. Zwischen Advices entscheidet @Order.
  4. Handler: Die Methode gibt ProblemDetail.forStatusAndDetail(NOT_FOUND, "Order 99 not found") zurück.
  5. Content Negotiation: Jackson schreibt ProblemDetail bevorzugt als application/problem+json. Das Feld status bestimmt den HTTP-Status.
  6. Antwort: Der Client bekommt 404 mit einem Standard-Body. Der Server loggt den Fehler nach seiner eigenen Regel.

3. Beispiel: globaler Handler mit ProblemDetail und Validierungsfehlern

@RestControllerAdvice
class GlobalErrors extends ResponseEntityExceptionHandler {

  @ExceptionHandler(OrderNotFoundException.class)
  ProblemDetail notFound(OrderNotFoundException ex) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    pd.setType(URI.create("https://api.acme.ch/problems/order-not-found"));
    pd.setTitle("Order not found");
    pd.setProperty("orderId", ex.orderId());
    return pd;
  }

  @Override
  protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
      HttpHeaders headers, HttpStatusCode status, WebRequest request) {
    ProblemDetail pd = ex.getBody();                       // schon 400 mit Titel
    pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
        .map(e -> Map.of("field", e.getField(), "message", e.getDefaultMessage())).toList());
    return handleExceptionInternal(ex, pd, headers, status, request);
  }

  @ExceptionHandler(Exception.class)
  ProblemDetail unexpected(Exception ex) {
    log.error("Unerwarteter Fehler", ex);                  // Details nur ins Log
    return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Interner Fehler");
  }
}

  1. @RestControllerAdvice gilt für alle Controller. Es ist @ControllerAdvice plus @ResponseBody.
  2. extends ResponseEntityExceptionHandler macht alle eingebauten Spring-MVC-Exceptions zu ProblemDetail.
  3. setProperty("orderId", ...) landet als eigenes Feld auf oberster Ebene im JSON.
  4. Die Validierungsfehler kommen als Liste errors. Der Client sieht, welches Feld falsch ist.
  5. Der Catch-All gibt nur einen neutralen Text aus. Stacktrace und Details stehen nur im Log.

4. Details, die Interviewer fragen

  1. ProblemDetail: eine Klasse für RFC 9457. Standardfelder: type, title, status, detail, instance. Eigene Felder über setProperty oder eine Unterklasse.
  2. RFC 9457: der Standard „Problem Details for HTTP APIs“. Er ersetzt RFC 7807. Media Type: application/problem+json.
  3. type: eine URI, die die Fehlerart beschreibt. Standard ist about:blank; dann soll title dem Status-Text entsprechen.
  4. ErrorResponse: ein Interface für Exceptions mit Status, Headern und ProblemDetail-Body. Alle Spring-MVC-Exceptions implementieren es.
  5. ErrorResponseException: eine Basisklasse für eigene Exceptions mit ProblemDetail. Beispiel: class OrderNotFound extends ErrorResponseException.
  6. ResponseStatusException: eine fertige Exception mit Status und Grund. Beispiel: throw new ResponseStatusException(NOT_FOUND, "Order 99"). Gut für einfache Fälle, koppelt aber Service an HTTP.
  7. @ResponseStatus: auf der Exception-Klasse legt einen festen Status fest. Kein Body-Format, wenig Kontrolle.
  8. ResponseEntityExceptionHandler: eine Basisklasse für den Advice. Sie behandelt alle eingebauten Exceptions und ruft überschreibbare handle...-Methoden auf.
  9. Aktivierung in Boot: spring.mvc.problemdetails.enabled=true (Standard false) registriert so einen Advice automatisch. Er hat Order 0. Eigener Advice muss davor liegen, um zu übernehmen.
  10. Lokal vs global: @ExceptionHandler im Controller gewinnt vor dem im @ControllerAdvice.
  11. Matching: Root-Exception vor Cause. Zwischen mehreren Advices: Ein höher priorisierter Advice gewinnt sogar mit Cause-Treffer.
  12. Advice einschränken: basePackages, annotations, assignableTypes. Diese Selektoren laufen zur Laufzeit und kosten etwas Leistung.
  13. produces auf @ExceptionHandler: Ein Handler pro Media Type, z. B. JSON für APIs und HTML für Browser.
  14. Validierungsfehler: @Valid @RequestBody wirft MethodArgumentNotValidException. Constraints direkt auf Parametern werfen HandlerMethodValidationException (seit 6.1). Beide sollte man behandeln.
  15. i18n: ResponseEntityExceptionHandler sucht Texte im MessageSource, Codes wie problemDetail.title.<Exception-Klasse>.
  16. Boot-Fallback /error: BasicErrorController liefert JSON mit timestamp, status, error, path. message, trace und errors sind standardmässig aus.
  17. Boot 4 Property-Namen: Boot 3.5 nutzt server.error.include-message usw., Boot 4 spring.web.error.include-message. Standard bleibt never.
  18. Client-Seite: RestClientResponseException.getResponseBodyAs(ProblemDetail.class) liest einen Fehler-Body typisiert.

5. Vergleich

  • @ExceptionHandler im Controller: nur für diesen Controller. Für Sonderfälle.
  • @ControllerAdvice / @RestControllerAdvice: zentral für alle Controller. Der Standardweg.
  • ResponseStatusException: schnell, ohne eigene Klasse. Aber HTTP-Wissen im Service.
  • @ResponseStatus auf Exception: fester Status, kein eigener Body.
  • Eigene Exception + Advice: Service wirft fachliche Exception, Advice übersetzt in HTTP. Saubere Schichten.
  • ProblemDetail vs eigenes Fehler-JSON: Standard, von Tools und Clients verstanden vs freies Format pro Team.
  • MVC vs WebFlux: Gleiches Modell mit @ControllerAdvice und ProblemDetail. Boot-Property dort: spring.webflux.problemdetails.enabled.

6. In der Produktion

  1. Stacktrace beim Client: Jemand setzt include-stacktrace=always oder gibt ex.getMessage() von SQL-Fehlern weiter. Lösung: neutrale Texte nach aussen, Details ins Log mit Trace-ID.
  2. Fehler im Filter nicht behandelt: Exceptions aus Servlet-Filtern erreichen den @ControllerAdvice nicht. Sie landen bei /error. Lösung: im Filter selbst behandeln; Security über AuthenticationEntryPoint und AccessDeniedHandler.
  3. Alles wird 500: Ein Catch-All für Exception fängt auch Spring-Exceptions wie 405 oder 415. Lösung: von ResponseEntityExceptionHandler erben oder Boot-Property nutzen.
  4. Uneinheitliche Fehlerformate: Jedes Team baut eigenes JSON. Lösung: ProblemDetail als Standard in einer gemeinsamen Bibliothek.
  5. Log-Flut: Jeder 404 als ERROR mit Stacktrace. Lösung: 4xx als WARN/INFO ohne Stacktrace, 5xx als ERROR.
  6. Zwei Advices kämpfen: Der Boot-Advice und ein eigener behandeln die gleiche Exception. Lösung: eigenen Advice mit höherer Priorität (@Order kleiner als 0) oder den Boot-Advice nicht aktivieren.

7. Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.web=DEBUG: zeigt, welcher Resolver die Exception gelöst hat („Resolved [...]“).
  • curl -i mit -H 'Accept: application/json' und ohne: prüft Content Negotiation und Status.
  • /actuator/metrics/http.server.requests?tag=status:500: Fehlerraten pro Endpoint; das Tag exception zeigt die Klasse.
  • Tracing: Trace-ID in Log und Antwort-Header, damit Support Fehler findet.
  • Tests: @WebMvcTest mit MockMvc und jsonPath("$.status") prüft jedes Fehlerformat.

8. Senior-Punkte

  1. Fehler sind Teil des API-Vertrags. Format, Status und type-URIs gehören in die API-Dokumentation (OpenAPI).
  2. Fachliche Exceptions im Service, HTTP im Advice. So bleibt der Service unabhängig vom Web.
  3. Nach aussen wenig, nach innen viel. Client bekommt Status, Typ und sicheren Text. Log bekommt Stacktrace, Kontext und Trace-ID.
  4. Ein Standard für alle Services. RFC 9457 mit gemeinsamer Bibliothek spart Client-Code in jedem Team.
  5. 4xx und 5xx getrennt behandeln. 4xx ist ein Client-Problem, 5xx weckt Bereitschaftsdienst. Alerting nur auf 5xx-Rate.

10. Fallen

  • „ProblemDetail ist in Spring Boot standardmässig aktiv.“ → Falsch. spring.mvc.problemdetails.enabled ist false, oder man erbt selbst von ResponseEntityExceptionHandler.
  • „@ControllerAdvice fängt alle Exceptions.“ → Falsch. Exceptions aus Filtern und Spring Security kommen dort nicht an.
  • „Der Advice gewinnt immer.“ → Falsch. Ein @ExceptionHandler im Controller selbst kommt zuerst.
  • „RFC 7807 ist der aktuelle Standard.“ → Veraltet. RFC 9457 ersetzt ihn.
  • „Validierungsfehler sind immer MethodArgumentNotValidException.“ → Falsch. Constraints auf Parametern ergeben HandlerMethodValidationException.
  • „Die Fehlermeldung an den Client ist harmlos.“ → Falsch. Sie kann SQL, Pfade oder Klassen verraten. Darum ist include-message standardmässig never.

11. Fragen

Wie behandeln Sie Exceptions in Spring MVC zentral?

Mit @RestControllerAdvice und @ExceptionHandler-Methoden. Am besten mit ProblemDetail als Body.

Was ist ProblemDetail?

Die Spring-Klasse für RFC 9457. Felder type, title, status, detail, instance und eigene Properties.

Was ist RFC 9457?

Der Standard „Problem Details for HTTP APIs“. Er ersetzt RFC 7807 und nutzt application/problem+json.

Wie aktivieren Sie ProblemDetail in Spring Boot?

Mit spring.mvc.problemdetails.enabled=true. Oder einen eigenen Advice, der von ResponseEntityExceptionHandler erbt.

Was macht ResponseEntityExceptionHandler?

Er behandelt alle eingebauten Spring-MVC-Exceptions und ErrorResponseException. Er liefert ProblemDetail und hat überschreibbare Methoden.

Was ist der Unterschied zwischen @ControllerAdvice und @RestControllerAdvice?

@RestControllerAdvice hat zusätzlich @ResponseBody. Rückgaben werden als Body geschrieben, nicht als View.

Welcher Handler gewinnt: im Controller oder im Advice?

Der im Controller. Globale Handler laufen nach den lokalen.

Wie wählt Spring zwischen mehreren passenden @ExceptionHandler?

Root-Exception vor Cause, dann der nächste Typ in der Hierarchie. Zwischen Advices entscheidet die Priorität.

Wann nutzen Sie ResponseStatusException?

Für einfache Fälle ohne eigene Klasse. Für fachliche Fehler besser eigene Exceptions und ein Advice.

Was macht @ResponseStatus auf einer Exception?

Es legt einen festen HTTP-Status fest. Der ResponseStatusExceptionResolver setzt ihn.

Welche HandlerExceptionResolver gibt es?

ExceptionHandlerExceptionResolver, ResponseStatusExceptionResolver, DefaultHandlerExceptionResolver, SimpleMappingExceptionResolver.

Was passiert, wenn kein Resolver die Exception löst?

Sie geht an den Servlet Container. Er macht einen Error-Dispatch nach /error, in Boot zum BasicErrorController.

Was enthält Boot's Standard-Fehler-JSON?

timestamp, status, error und path. message, trace und errors sind standardmässig ausgeschaltet.

Wie fügen Sie ProblemDetail eigene Felder hinzu?

Mit setProperty, z. B. orderId. Jackson schreibt sie auf oberster Ebene. Oder eine Unterklasse von ProblemDetail.

Wie geben Sie Validierungsfehler pro Feld zurück?

handleMethodArgumentNotValid überschreiben und die FieldErrors als Liste in eine Property schreiben.

MethodArgumentNotValidException vs HandlerMethodValidationException?

Erste bei @Valid auf einem Body-Objekt. Zweite bei Constraints direkt auf Parametern (Method Validation seit 6.1).

Warum erreicht eine Exception aus einem Filter den Advice nicht?

Filter laufen vor dem DispatcherServlet. Die Resolver-Kette gibt es dort noch nicht.

Wie behandeln Sie 401 und 403 aus Spring Security?

Über AuthenticationEntryPoint und AccessDeniedHandler in der Security-Konfiguration. Sie können auch ProblemDetail schreiben.

Wie übersetzen Sie Fehlertexte?

Über den MessageSource mit Codes wie problemDetail.title.<Klasse> und problemDetail.<Klasse>.

Was ändert sich in Boot 4 bei Fehler-Properties?

server.error.* heisst jetzt spring.web.error.*. Die Standardwerte bleiben gleich.

Wie liest ein Client einen ProblemDetail-Fehler?

Mit RestClientResponseException.getResponseBodyAs(ProblemDetail.class) oder bei WebClient mit WebClientResponseException.

Was gehört in die Fehlerantwort, was ins Log?

Antwort: Status, Typ, sicherer Text, eventuell Trace-ID. Log: Stacktrace, Kontext, interne Details.

Szenario: Clients sehen bei Fehlern SQL-Texte im Body. Was tun Sie?

Prüfen, ob include-message an ist oder ein Handler ex.getMessage() zurückgibt. Lösung: neutrale Texte, Catch-All-Handler, Details nur ins Log.

Szenario: Ein abgelaufenes Token ergibt HTML statt JSON-Fehler. Warum?

Die Exception entsteht in der Security-Filter-Kette, nicht im Controller. Lösung: eigener AuthenticationEntryPoint, der ProblemDetail als JSON schreibt.

Szenario: Drei Teams liefern drei verschiedene Fehlerformate. Wie vereinheitlichen Sie?

Gemeinsame Bibliothek mit Advice auf ProblemDetail-Basis, feste type-URIs, Dokumentation in OpenAPI. Schrittweise einführen, alte Felder kurz parallel liefern.
