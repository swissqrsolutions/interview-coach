KI-gestützte Entwicklung: Nutzen, Risiken, Regeln

Kern: KI-Coding-Tools wie GitHub Copilot oder Claude Code erzeugen Code, Tests und Erklärungen aus Kontext und Prompts. Sie machen Routinearbeit schneller, aber ihr Ergebnis ist ungeprüfter Code. Ein Senior bleibt verantwortlich: Er prüft, testet, schützt Daten und Lizenzen, genau wie bei Code eines neuen Kollegen.

1. Wo sitzt die KI im Entwicklungsprozess?

  1. Entwickler: gibt Ziel und Kontext vor. Er bleibt für jede Zeile verantwortlich.
  2. Completion: Vorschläge beim Tippen, z. B. die nächste Zeile oder Funktion.
  3. Chat: Fragen zum Code, Erklärungen, Entwürfe für Tests oder Refactorings.
  4. Agent: Das Tool liest Dateien, ändert mehrere Dateien und führt Befehle aus. Mehr Wirkung, mehr Risiko.
  5. Eigener Review und CI-Gates: Der Vorschlag durchläuft dieselben Prüfungen wie jeder Code.
  6. Grenzen: Personendaten, Secrets und Kundencode nur in freigegebenen Tools mit passendem Vertrag.

2. Die Reise eines KI-Vorschlags bis in main

  1. Test zuerst: Ich schreibe oder prüfe den Test selbst. Er definiert, was richtig ist, nicht die KI.
  2. Prompt: klein und präzise, mit Kontext: Framework, Version, Stil, Grenzen. Keine echten Personendaten, keine Secrets.
  3. Vorschlag lesen: Ich verstehe jede Zeile. Unbekannte APIs prüfe ich in der offiziellen Doku. KI-Modelle erfinden manchmal Methoden oder Pakete.
  4. Prüfen: Tests laufen, Randfälle, Security (Injection, Auth, Logging), Lizenz-Hinweise, neue Abhängigkeiten.
  5. PR: normales Team-Review. Bei grösseren KI-Anteilen schreibe ich das in die PR-Beschreibung, wenn das Team es so vereinbart hat.

3. Beispiel: KI-Vorschlag mit SQL Injection, im Review gefunden

import sqlite3

db = sqlite3.connect(":memory:")
db.execute("create table export (kanton text, betrag int)")
db.executemany("insert into export values (?, ?)",
               [("BE", 100), ("BE", 50), ("ZH", 900), ("GE", 300)])

# Vorschlag des KI-Assistenten (ungeprueft uebernommen)
def summe_ki(kanton):
    sql = f"select sum(betrag) from export where kanton = '{kanton}'"
    return db.execute(sql).fetchone()[0]

# Nach dem Review: Parameter statt String-Bau
def summe_review(kanton):
    sql = "select sum(betrag) from export where kanton = ?"
    return db.execute(sql, (kanton,)).fetchone()[0]

boese = "BE' or '1'='1"
print("KI-Version,     BE   :", summe_ki("BE"))
print("KI-Version,     boese:", summe_ki(boese))
print("Review-Version, BE   :", summe_review("BE"))
print("Review-Version, boese:", summe_review(boese))
KI-Version,     BE   : 150
KI-Version,     boese: 1350
Review-Version, BE   : 150
Review-Version, boese: None

Echte Ausgabe, Python 3.12.10 mit sqlite3 3.49.1 (python -I ai_review.py). Der „KI-Vorschlag“ ist ein typisches, hier selbst geschriebenes Muster, kein Mitschnitt eines Tools.

  1. Beide Versionen liefern für „BE“ korrekt 150. Ein einfacher Happy-Path-Test findet den Fehler nicht.
  2. Mit BE' or '1'='1 liefert die KI-Version 1350: die Summe aller Kantone. Das ist SQL Injection und ein Datenleck.
  3. Die Review-Version nutzt einen Parameter (?). Der böse String ist nur ein Wert, kein SQL. Ergebnis: kein Treffer.
  4. Lehre: KI-Code sieht oft richtig aus und besteht einfache Tests. Security-Review und Negativ-Tests bleiben Pflicht.

4. Details, die Interviewer fragen

  1. Wofür KI gut ist: Boilerplate, Tests als Entwurf, Regex und SQL erklären, Refactoring-Vorschläge, fremden Code verstehen, Doku-Entwürfe, Migrationen mit klarem Muster.
  2. Wofür weniger: Architektur-Entscheide mit vielen Randbedingungen, Security-kritischer Code ohne Review, neue Bibliotheksversionen nach dem Trainingsstand des Modells.
  3. Halluzinationen: Das Modell erfindet APIs, Konfigurationen oder Pakete. Ein erfundener Paketname kann von Angreifern registriert werden. Darum jede neue Abhängigkeit prüfen.
  4. Lizenzen: Vorschläge können öffentlichem Code ähneln. GitHub Copilot hat Code Referencing: Treffer mit öffentlichem Code werden je nach Policy blockiert oder mit Quelle und Lizenz angezeigt. Laut GitHub betrifft das weniger als 1 % der Inline-Vorschläge.
  5. Datenschutz: Was im Prompt steht, verlässt die Maschine. Laut GitHub werden Daten von Copilot Business und Enterprise nicht für Training genutzt. Für Free, Pro und Pro+ gilt seit April 2026: Nutzung für Training, ausser man widerspricht in den Einstellungen.
  6. Schweizer Recht: Laut EDÖB gilt das seit 1. September 2023 geltende Datenschutzgesetz (DSG) direkt auch für KI-gestützte Datenbearbeitung. Personendaten, z. B. AHV-Nummern, gehören nicht in nicht freigegebene Tools.
  7. Agenten-Risiken (OWASP Top 10 for LLM Applications 2025): Prompt Injection (LLM01), z. B. versteckte Anweisungen in einer README oder einem Issue. Excessive Agency (LLM06): Der Agent darf mehr, als er braucht.
  8. Agenten absichern: Least Privilege, keine Produktions-Credentials, Befehle bestätigen lassen, Sandbox oder Container, Änderungen nur über PR.
  9. Tests mit KI: Generierte Tests testen oft nur, was der Code tut, nicht was er tun soll. Erwartete Werte selbst festlegen.
  10. Kontext ist alles: Gute Ergebnisse brauchen Projektregeln, Versionen und Beispiele. Viele Tools lesen dafür eine Projektdatei mit Konventionen.

5. Vergleich

  • Completion vs Chat vs Agent: Completion ist schnell und lokal. Chat ist gut zum Verstehen. Agent ändert viele Dateien und führt Befehle aus, braucht also die strengsten Grenzen.
  • KI-Vorschlag vs Stack-Overflow-Snippet: Beide sind fremder Code. Beide brauchen Verständnis, Lizenz-Check und Tests.
  • KI-Review vs menschliches Review: KI findet Muster und Tippfehler schnell. Ein Mensch prüft Absicht, Design und Kontext. KI-Review ergänzt, ersetzt aber nicht.
  • Cloud-Modell vs lokales Modell: Cloud ist stärker, aber Daten verlassen das Haus. Lokal schützt Daten, ist aber schwächer und braucht Hardware.
  • Business- vs Privat-Lizenz: Business-Pläne haben Verträge zu Datennutzung und Admin-Policies. Privat-Konten gehören nicht an Kundencode.

6. In der Produktion

  1. Unsicherer Code im Merge: Injection, fehlende Auth-Prüfung, Secrets im Code. Lösung: SAST, Secret-Scanning und Security-Checkliste im Review.
  2. Erfundene oder bösartige Abhängigkeit: Lösung: neue Pakete nur nach Prüfung, Lockfiles, Dependency-Scanning, internes Repository.
  3. Personendaten im Prompt: Ein Entwickler kopiert echte Logs mit Namen in ein öffentliches Tool. Lösung: klare Regeln, freigegebene Tools, Testdaten statt Echtdaten.
  4. Agent löscht oder ändert zu viel: Lösung: Arbeit in Branch oder Worktree, keine Produktions-Zugänge, Befehle bestätigen, alles über PR.
  5. Code, den niemand versteht: Grosse generierte Blöcke ohne Erklärung. Lösung: kleine Schritte, Regel „nur mergen, was man erklären kann“.
  6. Veraltete APIs: Das Modell schlägt alte Versionen vor, z. B. javax.* statt jakarta.*. Lösung: Versionen im Prompt nennen, Doku prüfen.

7. Diagnose und Kontrollen

  • SAST und Quality Gates: SonarQube, CodeQL oder ähnliche Scanner in CI für jeden PR.
  • Secret-Scanning: z. B. GitHub Secret Scanning, gitleaks, Pre-Commit-Hooks.
  • Dependency-Scanning: Dependabot, OWASP Dependency-Check, Renovate. Neue Pakete im Review sichtbar machen.
  • Admin-Policies: Bei Copilot Business/Enterprise: Code-Referencing-Policy, freigegebene Modelle, Ausschluss sensibler Repos.
  • Audit: Welche Tools sind erlaubt, wer nutzt sie, mit welchen Daten? Das gehört in die Richtlinie des Kunden.
  • Negativ-Tests: böse Eingaben, Grenzwerte, fehlende Rechte. Sie finden, was KI-Code oft übersieht.

8. Senior-Punkte

  1. Verantwortung bleibt beim Menschen. „Die KI hat das geschrieben“ ist nie eine Ausrede.
  2. KI beschleunigt das Schreiben, nicht das Verstehen. Review, Tests und Architektur bleiben Senior-Arbeit.
  3. Regeln vor Tools: Zuerst klären, was der Kunde erlaubt. Im Bundesumfeld gelten Datenschutz und Informationssicherheit vor Produktivität.
  4. Kleine Schritte: Kurze Prompts, kleine Diffs, sofort testen. Grosse generierte Änderungen sind schwer zu reviewen.
  5. Qualitäts-Gates gelten für allen Code gleich. KI-Code braucht keinen eigenen Prozess, aber denselben strengen.
  6. Im Interview: ehrlich sagen, wie und wo man KI nutzt, welche Grenzen man einhält und wie man das Ergebnis prüft. Weder übertreiben noch verstecken.

10. Fallen

  • „KI-Code ist getestet, weil die KI Tests mitliefert.“ → Falsch. Generierte Tests prüfen oft nur das Ist-Verhalten. Erwartungen selbst festlegen.
  • „Mit TLS sind Prompts sicher.“ → Falsch. TLS schützt den Transport. Die Daten liegen danach beim Anbieter, je nach Vertrag.
  • „Alle Copilot-Pläne trainieren nicht mit meinem Code.“ → Falsch. Business und Enterprise nicht; Free, Pro und Pro+ seit April 2026 schon, ausser man widerspricht.
  • „Ein Agent mit vollen Rechten ist effizienter.“ → Riskant. Excessive Agency ist ein OWASP-Top-10-Risiko. Least Privilege.
  • „Wenn der Code kompiliert, stimmen die APIs.“ → Nicht immer. Erfundene Konfigurationswerte oder falsche Defaults kompilieren trotzdem.
  • „KI ersetzt das Code Review.“ → Falsch. KI-Review ergänzt. Absicht, Design und Kontext prüft ein Mensch.

11. Fragen

Wie nutzen Sie KI-Coding-Tools?

Für Boilerplate, Testentwürfe, Erklärungen und Refactoring-Vorschläge. Jeden Vorschlag lese, verstehe und teste ich. Ich merge nur Code, den ich erklären kann.

Welche Risiken sehen Sie?

Unsicherer oder falscher Code, erfundene APIs und Pakete, Lizenzprobleme, Datenabfluss im Prompt und bei Agenten zu viele Rechte.

Wie prüfen Sie KI-generierten Code?

Wie jeden fremden Code: lesen, Doku prüfen, Tests mit eigenen Erwartungen, Negativ-Tests, SAST und Team-Review.

Wie gehen Sie mit Datenschutz um?

Keine Personendaten, Secrets oder Kundendaten in nicht freigegebene Tools. Nur Tools mit passendem Vertrag, Testdaten statt Echtdaten.

Gilt das DSG auch für KI-Tools?

Ja. Laut EDÖB ist das seit 1. September 2023 geltende DSG direkt auf KI-gestützte Datenbearbeitung anwendbar.

Nutzt GitHub Ihren Code für Training?

Bei Copilot Business und Enterprise laut GitHub nicht. Bei Free, Pro und Pro+ seit April 2026 schon, ausser man widerspricht in den Einstellungen.

Wie gehen Sie mit Lizenzrisiken um?

Code-Referencing-Policy aktivieren: Treffer mit öffentlichem Code blockieren oder mit Quelle anzeigen. Lange, auffällige Vorschläge prüfe ich besonders.

Was ist Prompt Injection?

Versteckte Anweisungen in Daten, die das Modell liest, z. B. in einer README oder Webseite. Sie können einen Agenten zu falschen Aktionen bringen.

Was ist Excessive Agency?

Ein KI-Agent hat mehr Rechte oder Werkzeuge als nötig. OWASP führt es als LLM06 in der Top 10 2025.

Wie sichern Sie einen Coding-Agenten ab?

Least Privilege, keine Produktions-Zugänge, Befehle bestätigen, Arbeit in Branch oder Container, Ergebnis nur über PR.

Was sind Halluzinationen im Code?

Erfundene Methoden, Konfigurationen oder Pakete. Sie sehen plausibel aus. Darum Doku und Abhängigkeiten prüfen.

Warum sind KI-generierte Tests heikel?

Sie prüfen oft, was der Code tut, nicht was er tun soll. Ein Fehler im Code wird so zum erwarteten Wert.

Ersetzt KI das Code Review?

Nein. KI-Review findet Muster schnell. Absicht, Design und Kontext prüft ein Mensch.

Wo bringt KI am meisten?

Bei wiederkehrenden Mustern, fremdem Code verstehen, Testentwürfen und Doku. Weniger bei Architektur und Security-kritischem Code.

Wie messen Sie, ob KI dem Team hilft?

An Flow und Qualität: Cycle Time, Escaped Defects, Review-Zeit. Nicht an generierten Zeilen.

Kennzeichnen Sie KI-Code im PR?

Wenn das Team oder der Kunde es vereinbart, ja. Wichtiger ist, dass jeder PR geprüft und erklärbar ist.

Was sagen Sie im Interview zur KI-Nutzung?

Ehrlich: wofür ich KI nutze, welche Regeln ich einhalte und wie ich das Ergebnis prüfe. Kein Verstecken, kein Übertreiben.

Wie gehen Sie mit veralteten Vorschlägen um?

Ich nenne Versionen im Prompt und prüfe in der offiziellen Doku. Beispiel: jakarta statt javax ab Jakarta EE 9.

Szenario: Ein Kollege kopiert Produktionslogs mit AHV-Nummern in ein öffentliches KI-Tool. Was tun Sie?

Sofort stoppen und den Vorfall nach Kundenprozess melden. Danach klare Regeln, freigegebene Tools und anonymisierte Testdaten für das Team.

Szenario: Ein KI-Agent schlägt eine neue npm-Abhängigkeit vor, die niemand kennt. Wie prüfen Sie?

Existiert sie, wer pflegt sie, wie alt, wie viele Nutzer, welche Lizenz, bekannte Schwachstellen? Im Zweifel nicht nutzen oder eine bekannte Alternative wählen.

Szenario: Das Management will mit KI die Velocity verdoppeln. Wie reagieren Sie?

Ich erkläre, dass Schreiben schneller wird, Review, Tests und Abstimmung aber nicht. Ich schlage einen Pilot mit Flow- und Qualitätsmetriken vor.
