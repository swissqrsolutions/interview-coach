Secrets in Pipelines

Kern: Ein Secret ist ein Passwort, Token oder Schlüssel, den eine Pipeline für Zugriffe braucht. Es gehört nie in den Code und nicht in die Logs. Am besten gibt es gar keine langlebigen Secrets, denn OIDC tauscht ein kurzlebiges Token pro Job.

Antwort-Muster

Frage: Wie gehst du in Pipelines mit Secrets um?

  1. Mechanismus: Wo es geht, nutze ich OIDC (Workload Identity Federation). Die Pipeline bekommt ein kurzlebiges Token. Sonst holt sie Secrets zur Laufzeit aus Key Vault oder einem geschützten Variablenspeicher.
  2. Zahl: Azure Pipelines maskiert nur ganze Secret-Werte, nie Teilstrings. GitHub-Secrets dürfen bis 48 KB gross sein.
  3. Trade-off: OIDC braucht eine einmalige Vertrauens-Konfiguration. Dafür gibt es nichts zu rotieren und nichts zu stehlen.
  4. Produktion: Secrets gehen über Umgebungsvariablen und nie über die Kommandozeile. Forks bekommen keine Secrets.

1. Anmeldung ohne Secret mit OIDC

  1. Start: Ein Job braucht Zugriff auf eine Cloud. Es gibt kein gespeichertes Passwort dafür.
  2. JWT: Die CI-Plattform erzeugt pro Job ein JSON Web Token. Es enthält Claims wie Repository und Environment, zum Beispiel in sub.
  3. Austausch: Der Job schickt das Token an den Anbieter. Dort ist vorab eine Vertrauensstellung eingerichtet.
  4. Prüfung: Der Anbieter prüft Signatur, Aussteller und Claims gegen die Regel. Bei GitHub zum Beispiel die sub-Claim.
  5. Token: Bei Erfolg gibt es ein kurzlebiges Access Token. Es gilt nur für die Dauer des Jobs und läuft dann ab.
  6. Zugriff: Der Job nutzt das Token für Azure CLI oder Key Vault. Es gibt kein Secret zum Rotieren oder Leaken.

2. Aufbau

  1. Secret Variable ist ein verschlüsselter Wert in der Pipeline. Er wird in Logs maskiert.
  2. Variable Group mit Key Vault verlinkt Secret-Namen. Die Werte holt die Pipeline erst zur Laufzeit.
  3. Service Connection ist die Verbindung zu Azure. Mit Workload Identity Federation hat sie kein Secret.
  4. Environment schützt Deployments. Es kann Freigaben verlangen und Secrets begrenzen.
  5. Masking ersetzt bekannte Secret-Werte im Log durch Sterne.
  6. Secret Store ist die Quelle der Wahrheit. Beispiele sind Key Vault, HashiCorp Vault oder GitLab-Variablen.

3. Details

  1. Azure Pipelines, Secret Variables: Du setzt sie in der UI, in einer Variable Group oder aus Key Vault. Sie werden nicht automatisch in Umgebungsvariablen entschlüsselt. Du musst sie mit env: pro Schritt zuordnen.
  2. Masking ist Best Effort: Azure Pipelines maskiert nur ganze Werte, nie Teilstrings. Ein Secret wie JSON schützt nur den ganzen Text. Darum legt man pro Wert ein eigenes Secret an.
  3. Nie auf die Kommandozeile: Manche Betriebssysteme loggen Argumente. Gib Secrets nie mit echo aus. Übergib sie über Umgebungsvariablen.
  4. Variable Group mit Key Vault: Nur die Secret-Namen werden verlinkt. Beim Lauf holt die Pipeline die neuesten Werte aus dem Vault. Ein RBAC-Key-Vault hinter einem Private Endpoint wird von Azure DevOps nicht unterstützt.
  5. Workload Identity Federation (WIF): Microsoft empfiehlt sie für Azure-Service-Connections. Sie braucht keine Secrets. Der Azure-DevOps-Aussteller vstoken.dev.azure.com läuft am 1. Juli 2027 aus. Neue Verbindungen nutzen den Entra-Aussteller.
  6. Forks in Azure Pipelines: Bei GitHub-Pipelines sind Secrets für Pull Requests aus Forks standardmässig nicht verfügbar. Die Option Make secrets available to builds of forks hebt das auf. Das ist ein Risiko.
  7. GitHub Actions Secrets: Es gibt sie für Repository, Environment und Organisation. Bei Forks erhält der Workflow keine Secrets ausser GITHUB_TOKEN. An wiederverwendbare Workflows gehen sie nicht automatisch.
  8. GitHub OIDC: Jeder Job fragt ein JWT an. Der Job braucht dafür permissions: id-token: write. Die Cloud prüft die Claims und gibt ein Token, das nur für den Job gilt.
  9. GitHub Eigenheiten: Secrets lassen sich nicht direkt in if: verwenden. Nicht-Secrets maskiert man mit ::add-mask::. Secrets sind bis 48 KB erlaubt.
  10. GitLab Variablen: Sichtbarkeit ist Visible, Masked oder Masked and hidden. Seit GitLab 18.3 ist Masked die Voreinstellung. Protected beschränkt auf geschützte Branches und Tags.
  11. GitLab ID Tokens: Mit dem Schlüsselwort id_tokens erzeugt ein Job ein JWT. Die aud-Claim bindet es an einen Dienst. Der Dienst lehnt Tokens mit falscher aud ab.
  12. Jenkins Credentials: Die Direktive credentials() legt Werte als Umgebungsvariablen an. Für Benutzer und Passwort hängt sie _USR und _PSW an. Mit withCredentials bindet man sie nur im Block.
  13. Jenkins und Groovy: In doppelten Anführungszeichen interpoliert Groovy das Secret. Es erscheint dann in der Prozessliste. Mit einfachen Anführungszeichen expandiert die Shell die Variable.

4. Fallen

  • „Secret Variables sind automatisch in jedem Skript als Umgebungsvariable da.“ → Falsch. In Azure Pipelines musst du sie mit env: zuordnen.
  • „Masking schützt ein Secret zuverlässig.“ → Falsch. Es ist Best Effort. Teilstrings, Umwandlungen und strukturierte Daten werden nicht erkannt.
  • „Forks können unsere Pipelines gefahrlos bauen.“ → Falsch. Ein Fork-PR kann Code mitbringen, der Secrets ausliest. Darum bekommt er standardmässig keine.
  • „Ein Key Vault verlinkt in der Variable Group heisst, die Werte liegen in der Pipeline.“ → Falsch. Nur die Namen sind verlinkt. Die Werte werden bei jedem Lauf geholt.
  • „OIDC bedeutet, wir haben kein Risiko mehr.“ → Falsch. Die Vertrauens-Regel muss eng sein, zum Beispiel auf ein Environment. Eine breite Regel öffnet Zugriff für zu viele Jobs.
  • „docker login -p $PASSWORD ist sicher, weil das Secret maskiert ist.“ → Falsch. Argumente können geloggt oder in der Prozessliste sichtbar sein. Nutze stdin oder Umgebungsvariablen.

5. Selbsttest

Warum?

Warum gehören Secrets nicht ins Repository?

Git speichert alles für immer, und viele Personen haben Lesezugriff. Ein geleaktes Secret muss rotiert werden. Die Historie lässt sich kaum bereinigen.

Warum ist OIDC besser als ein Service-Principal-Secret?

Es gibt kein langlebiges Secret zu speichern oder zu rotieren. Das Token lebt nur für einen Job.

Warum bekommen Fork-PRs keine Secrets?

Ein Angreifer kann im Fork die Pipeline ändern und Secrets ausgeben. Darum sind sie dort aus.

Wie innen?

Wie funktioniert die OIDC-Anmeldung?

Die CI stellt pro Job ein JWT aus. Der Cloud-Anbieter prüft Aussteller und Claims gegen die Vertrauens-Regel und gibt ein kurzlebiges Access Token.

Wie holt eine Variable Group Secrets aus Key Vault?

Sie verlinkt nur die Namen. Bei jedem Lauf holt die Pipeline die aktuellen Werte aus dem Vault.

Was macht Masking im Log?

Der Agent ersetzt bekannte Secret-Werte im Log durch Sterne. Es werden nur vollständige Werte erkannt, nie Teilstrings.

Wie unterscheiden sich Masked und Protected bei GitLab?

Masked versteckt den Wert im Log. Protected gibt ihn nur Jobs auf geschützten Branches und Tags.

Warum einfache Anführungszeichen in Jenkins?

Bei einfachen expandiert die Shell die Variable. Bei doppelten interpoliert Groovy das Secret, und es landet in der Prozessliste.

Zahlen

Wie gross darf ein GitHub-Secret sein?

Bis 48 KB. Grössere Werte verschlüsselt man mit gpg und legt nur das Passwort als Secret ab.

Wann läuft der alte Azure-DevOps-Issuer aus?

Am 1. Juli 2027. Neue WIF-Verbindungen nutzen den Entra-Aussteller.

Wie viele Ebenen für GitHub-Secrets gibt es?

Drei, nämlich Repository, Environment und Organisation.

Wie lange gilt das OIDC-Access-Token?

Nur für die Dauer des Jobs. Danach läuft es ab.

Vergleich

Secret Variable vs Key-Vault-Verlinkung?

Eine Secret Variable liegt in der Pipeline-Konfiguration. Beim Key Vault liegt der Wert im Vault, mit Rotation und Audit.

Service Principal mit Secret vs WIF?

Das Secret läuft ab und kann leaken. WIF hat kein Secret. Microsoft empfiehlt WIF.

Azure DevOps vs GitHub Actions bei Forks?

Beide geben Fork-PRs standardmässig keine Secrets. In Azure DevOps gibt es dafür eine Option. Bei GitHub erhalten Workflows aus Forks keine Secrets, ausser GITHUB_TOKEN.

Pipeline-Secrets vs externer Vault?

Pipeline-Secrets sind einfach. Ein Vault bietet zentrale Rotation, Audit und kurzlebige Zugriffe.

Produktion

Wie rotiert man ein Secret ohne Ausfall?

Im Key Vault den neuen Wert setzen. Die Pipeline holt ihn beim nächsten Lauf. Bei OIDC gibt es nichts zu rotieren.

Wie begrenzt man, wer deployen darf?

Mit Environments, Freigaben und geschützten Branches. Die OIDC-Regel bindet das Token an das Environment.

Was tun bei einem geleakten Secret?

Sofort rotieren, auch wenn es maskiert war. Logs und Zugriffe prüfen. Ursache beheben, etwa ein Skript mit Echo.

Szenario: Ein Secret erscheint im Log eines Builds. Was tun Sie?

Das Secret rotieren, weil es kompromittiert ist. Den Log löschen oder sperren. Die Ursache suchen, zum Beispiel Transformation, Teilstring oder strukturierte Daten.

Szenario: Ein externer Beitrag per Fork-PR soll gebaut werden. Wie gehen Sie vor?

Ohne Secrets bauen, was standardmässig der Fall ist. Tests brauchen keine. Wenn Secrets nötig sind, erst nach Review in einen Branch des Repos übernehmen.

Design

Wann reicht eine Secret Variable?

Für wenige, unkritische Werte in einem Team. Für Cloud-Zugriffe nimmt man OIDC, für viele oder kritische Secrets einen Vault.

Wie sieht die OIDC-Regel aus?

So eng wie möglich. Zum Beispiel nur Repository X, Environment prod. Nicht der ganze Org-Zugriff.

Wie trennt man Secrets pro Umgebung?

Mit Environments und getrennten Vaults oder Identitäten pro Umgebung. Prod-Secrets sind nur für Prod-Jobs lesbar.

Szenario: Eine Pipeline soll in drei Subscriptions deployen. Wie lösen Sie die Anmeldung?

Pro Subscription eine Service Connection mit WIF und minimaler Rolle. Die Regel bindet jede an das passende Environment. Keine gemeinsamen Secrets.

Mehr

Gerüst

  • Warum? Zugangsdaten schützen und doch automatisch deployen.
  • Wie innen? OIDC tauscht ein JWT gegen ein kurzlebiges Token. Sonst holt die Pipeline Secrets zur Laufzeit aus dem Vault.
  • Zahlen 48 KB bei GitHub-Secrets. Issuer-Ende 1. Juli 2027. Masking nur für ganze Werte.
  • Vergleich Secret Variable gegen Vault. Service-Principal-Secret gegen WIF.
  • Produktion Env statt Kommandozeile. Forks ohne Secrets. Rotation, Environments.
  • Design OIDC mit enger Regel, Umgebungen trennen, Secrets pro Wert.

Beispiel: GitHub Actions: Azure-Login mit OIDC

name: deploy
on: [push]

permissions:
  id-token: write      # JWT anfordern
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: prod
    steps:
      - uses: azure/login@v3
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - run: az account show

Nicht ausgeführt (kein Azure- oder GitHub-Zugang auf dieser Maschine). Die Werte in secrets sind IDs, keine Passwörter. Das Beispiel der GitHub-Doku pinnt die Action an einen Commit-SHA.

  1. id-token: write erlaubt dem Job, ein JWT anzufordern.
  2. environment: prod setzt die sub-Claim auf das Environment. Die Azure-Vertrauens-Regel kann darauf prüfen.
  3. Es gibt kein Passwort. client-id, tenant-id und subscription-id sind keine Geheimnisse im engeren Sinn.
  4. Nur Werte aus secrets gehören in diese Felder. Keine Werte aus github.event.

Vergleich

  • Azure DevOps: Secret Variables, Variable Groups mit Key Vault, WIF-Service-Connections.
  • GitHub Actions: Secrets auf drei Ebenen, Environments, OIDC mit id-token.
  • GitLab CI: Variablen mit Masked, Protected und Hidden. id_tokens für OIDC.
  • Jenkins: Credentials-Plugin, credentials() und withCredentials.
  • Key Vault: Zentrale Rotation, Audit und Zugriffskontrolle.
  • HashiCorp Vault: Alternative mit kurzlebigen, dynamischen Secrets.

Produktion

  1. Secret im Log: Ein Skript gibt es aus, oder eine Umwandlung umgeht das Masking. Lösung: rotieren, Skript fixen, Secrets pro Wert.
  2. Fork-PR liest Secrets: Die Fork-Option ist an. Lösung: ausschalten und nur nach Review bauen.
  3. Abgelaufenes Secret: Ein Service-Principal-Secret läuft ab. Die Pipeline fällt aus. Lösung: WIF nutzen.
  4. Zu breite OIDC-Regel: Jeder Branch kann deployen. Lösung: Subject auf Environment oder Branch einschränken.
  5. Secret in Docker-Befehl: Argument sichtbar in Logs oder Prozessliste. Lösung: Umgebungsvariable oder stdin.
  6. Key Vault nicht erreichbar: Private Endpoint mit RBAC wird von Azure DevOps nicht unterstützt. Lösung: Zugriffsweg ändern, siehe Doku zum Zugriff auf einen privaten Key Vault.

Diagnose: Werkzeuge und Befehle

  • Pipeline-Log: Auf *** und auf sichtbare Teilwerte prüfen.
  • Entra → App Registration → Federated Credentials: Aussteller, Subject und Audience prüfen.
  • Key Vault → Diagnostic Logs: Zeigt, welche Identität wann welches Secret gelesen hat.
  • GitHub → Settings → Secrets: Zeigt Secrets auf Repository-, Environment- und Org-Ebene.
  • Azure DevOps → Service connections: Die Verbindung öffnen und die Nutzung ansehen.
  • Secret Scanning im Repo: Findet Passwörter im Code und in der Historie.

Senior-Punkte

  1. Das beste Secret ist keins. OIDC schlägt jedes gespeicherte Passwort.
  2. Masking ist ein Pflaster. Verlasse dich nie darauf.
  3. Begrenze die Reichweite. Eng gefasste Rollen, Environments, geschützte Branches.
  4. Rotation einplanen. Jedes Secret braucht Besitzer und Ablauf.
  5. Fork-Builds sind untrusted. Bau sie ohne Secrets und mit wenig Rechten.
  6. Prüfe die Pipeline-Definition als Code. Wer sie ändern darf, kann Secrets ausgeben. Das gehört in Reviews.
