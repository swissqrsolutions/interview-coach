CI/CD-Pipeline: Stufen und Qualitäts-Gates

Kern: Eine CI/CD-Pipeline ist eine automatische Kette von Stufen, nämlich build, test, scan, package und deploy. Jede Stufe ist ein Gate, und fällt sie durch, stoppt die Kette. So kommt nur geprüfter Code in Produktion, und zwar als ein unverändertes Artefakt, das von Umgebung zu Umgebung wandert.

Antwort-Muster

Frage: Welche Stufen hat eine CI/CD-Pipeline, und warum bauen wir nur einmal?

  1. Mechanismus: Die Pipeline läuft build, test, scan, package und deploy. Jede Stufe ist ein Gate, das die Kette stoppen kann.
  2. Zahl: Das Sonar-Gate prüft zum Beispiel Coverage auf neuem Code von mindestens 80 % und Duplikation von höchstens 3 %.
  3. Trade-off: Ein Build für alle Umgebungen ist reproduzierbar. Dafür muss die Konfiguration sauber von dem Artefakt getrennt sein.
  4. Produktion: Ich befördere dasselbe Image per Digest durch dev, test und prod. Prod braucht eine Approval am Environment.

1. Die Reise eines Commits

  1. build: Der Commit wird kompiliert. Abhängigkeiten kommen aus dem Cache, nicht jedes Mal aus dem Internet.
  2. test: Unit-Tests laufen zuerst, weil sie schnell sind. Danach Integrationstests, z. B. mit Testcontainers.
  3. scan: SonarQube prüft das Quality Gate. Ein Image-Scanner sucht bekannte Schwachstellen (CVEs).
  4. package: Ein Multi-Stage Dockerfile baut ein schlankes Image. Die Pipeline pusht es mit eindeutigem Tag in die Registry.
  5. dev/test: Dasselbe Image wird automatisch in dev und test deployt. Smoke-Tests prüfen es.
  6. prod: Eine Approval auf dem Environment gibt den Weg frei. Wieder dasselbe Image, nur andere Konfiguration.
  7. Gate rot: Jede rote Stufe stoppt die Kette. Der Entwickler bekommt die Meldung in Minuten, nicht in Tagen.

2. Aufbau

  1. Git-Repo: Ein Pull Request oder ein Push löst die Pipeline aus (Trigger).
  2. Pipeline als Code: Die Pipeline ist eine YAML-Datei im Repo. Sie ist versioniert und reviewt.
  3. Agent: Ein Agent ist eine Maschine, die die Jobs ausführt. Beispiel: Microsoft-hosted ubuntu-latest oder ein eigener Agent im VNet.
  4. SonarQube: prüft Code-Qualität und Sicherheit gegen ein Quality Gate.
  5. Registry: speichert das fertige Artefakt, z. B. ein Container-Image in Azure Container Registry.
  6. Umgebungen: dev, test, prod bekommen dasselbe Artefakt. Nur die Konfiguration ist pro Umgebung anders.

3. Details, die Interviewer fragen

  1. CI vs CD: Continuous Integration heisst, jeder Commit wird gebaut und getestet. Continuous Delivery heisst, jeder grüne Stand kann in Produktion. Continuous Deployment heisst, er geht automatisch in Produktion.
  2. Quality Gate: Ein Quality Gate ist eine Liste von Bedingungen, die erfüllt sein müssen. „Sonar way“ prüft neuen Code. Es darf keine neuen Issues geben. Alle neuen Security Hotspots müssen reviewt sein. Die Coverage muss ≥ 80 % sein. Die Duplikation muss ≤ 3 % sein.
  3. Neuer Code zuerst: Sonar bewertet vor allem neuen Code. So kann ein Legacy-Projekt ein Gate haben, ohne alle Altlasten zu fixen.
  4. Kleine Änderungen: Sonar prüft Coverage und Duplikation erst ab 20 neuen Zeilen (Standard). So scheitern kleine Fixes nicht an Prozent-Werten.
  5. Artefakt-Promotion: Man baut das Artefakt einmal und befördert es dann von Umgebung zu Umgebung. Neu bauen pro Umgebung erzeugt ein anderes, ungetestetes Artefakt.
  6. Unveränderliche Tags: Ein Tag wie latest kann sich ändern. Ein eindeutiger Tag (Build-ID, Git-SHA) oder der Digest (sha256:…) zeigt immer auf dasselbe Image.
  7. Cache vs Artefakt: Ein Cache beschleunigt nur. Fehlt er, läuft der Job trotzdem. Ein Artefakt braucht der nächste Job zwingend. Azure-Caches sind unveränderlich. Sie laufen nach 7 Tagen ohne Nutzung ab.
  8. Fail fast: Billige Prüfungen kommen zuerst, also Lint, Compile und Unit-Tests. Teure Tests laufen danach oder parallel. Ein roter Schritt stoppt die Kette sofort.
  9. Approvals und Checks: In YAML-Pipelines hängen Approvals am Environment, nicht im YAML. So kann ein Entwickler sie nicht im Pull Request entfernen.
  10. Deployment Job: Ein deployment-Job schreibt Deployment-Historie auf das Environment. Die Strategien sind runOnce, rolling und canary.
  11. PR-Validierung: Eine Branch Policy verlangt einen grünen Build vor dem Merge. Der Build läuft auf dem Merge-Ergebnis des PR.
  12. Secrets: Secrets kommen aus Variable Groups mit Key Vault oder über Workload Identity. Sie stehen nie im YAML und nie im Image.

4. Fallen

  • „Continuous Delivery heisst, jeder Commit geht automatisch live.“ → Falsch. Das ist Continuous Deployment. Delivery heisst: jederzeit auslieferbar.
  • „Wir bauen pro Umgebung neu, das ist sauberer.“ → Falsch. Dann testet man ein anderes Artefakt als das, was live geht.
  • „latest reicht als Tag.“ → Falsch. Nicht reproduzierbar, Rollback unklar. Eindeutiger Tag oder Digest.
  • „Ein Cache ist wie ein Artefakt.“ → Falsch. Cache ist optional und nur Beschleunigung. Artefakte sind Pflicht-Eingaben.
  • „Das Sonar-Gate scheitert, also Regel abschalten.“ → Falsch. Ursache fixen oder einzeln begründet ausnehmen.
  • „Approvals schreibe ich ins YAML.“ → Falsch bei Azure YAML-Pipelines. Sie gehören ans Environment.

5. Selbsttest

Warum?

Was heisst „build once, deploy many“?

Das Artefakt wird einmal gebaut und unverändert durch alle Umgebungen befördert. Nur Konfiguration ändert sich.

Warum Digest statt Tag?

Ein Tag kann neu vergeben werden. Ein Digest ist der Hash des Inhalts und zeigt immer auf genau dasselbe Image.

Was heisst fail fast?

Billige, schnelle Prüfungen zuerst. Der erste Fehler stoppt die Kette, damit Feedback schnell kommt und keine Zeit verschwendet wird.

Wie verhindern Sie, dass jemand die Pipeline umgeht?

Branch Policies: Pflicht-PR, Pflicht-Build, Reviewer. Kein direkter Push auf main.

Wie innen?

Welche Stufen hat eine typische CI/CD-Pipeline?

Build, Test, Scan, Package, Deploy in Umgebungen bis Produktion. Jede Stufe ist ein Gate, das die Kette stoppen kann.

Was ist ein Quality Gate?

Eine Menge von Bedingungen, die ein Build erfüllen muss. In SonarQube z. B. keine neuen Issues, Coverage auf neuem Code ≥ 80 %, Duplikation ≤ 3 %.

Wie lassen Sie die Pipeline am Sonar-Gate scheitern?

Mit sonar.qualitygate.wait=true im Prepare-Schritt. Der Scanner wartet auf das Ergebnis und schlägt bei rotem Gate fehl.

Was ist ein Multi-Stage Dockerfile?

Mehrere FROM-Stufen in einer Datei. Die Build-Stufe hat Compiler und Tools, das Endimage nur die Laufzeit und das Artefakt.

Wie funktioniert der Cache-Schlüssel in Azure Pipelines?

Segmente mit | getrennt: feste Strings, OS und Hashes von Dateien wie pom.xml oder package-lock.json. Ändert sich eine Lock-Datei, entsteht ein neuer Cache.

Wo konfigurieren Sie eine Freigabe für Produktion in Azure DevOps?

Als Approval-Check am Environment prod. Die Deployment-Stage wartet, bis die Freigabe da ist.

Was ist ein Deployment Job?

Ein Job-Typ, der gegen ein Environment deployt und Historie schreibt. Er unterstützt runOnce, rolling und canary.

Wie laufen Stages ohne dependsOn?

Der Reihe nach, wie im YAML. Mit dependsOn: [] läuft eine Stage parallel.

Was gehört in die Scan-Stufe?

Statische Analyse (SonarQube), Abhängigkeits-Scan, Image-Scan auf CVEs, Secret-Scan.

Wie kommen Secrets in die Pipeline?

Aus Key Vault über Variable Groups oder über Workload Identity der Service Connection. Nie im YAML oder im Image.

Zahlen

Welche Werte verlangt das Quality Gate „Sonar way“ für neuen Code?

Coverage mindestens 80 % und Duplikation höchstens 3 %. Dazu keine neuen Issues und alle neuen Security Hotspots reviewt.

Ab wie vielen neuen Zeilen prüft Sonar Coverage und Duplikation?

Standardmässig ab 20 neuen Zeilen. So scheitern kleine Fixes nicht an Prozent-Werten.

Wie lange lebt ein Azure-Pipeline-Cache ohne Nutzung?

7 Tage. Danach läuft er ab. Ein Cache darf aber ohnehin fehlen.

Vergleich

Was ist der Unterschied zwischen Continuous Delivery und Continuous Deployment?

Delivery: jeder grüne Stand kann live gehen, oft mit manueller Freigabe. Deployment: jeder grüne Stand geht automatisch live.

Was ist der Unterschied zwischen Cache und Pipeline-Artefakt?

Ein Cache beschleunigt und darf fehlen. Ein Artefakt ist die Ausgabe eines Jobs, die ein späterer Job zwingend braucht.

Push-Deploy aus der Pipeline oder GitOps?

Push ist einfach, aber die Pipeline braucht Cluster-Rechte. GitOps: Pipeline schreibt nur ins Repo, ArgoCD zieht. Weniger Rechte, Drift wird erkannt.

Produktion

Szenario: Die Pipeline dauert 45 Minuten und das Team pusht seltener. Was tun Sie?

Messen, wo die Zeit liegt. Dann Cache, Parallelisierung, schnelle Tests zuerst, Docker-Layer optimieren, langsame Suiten in nächtliche Läufe.

Szenario: In Test funktioniert alles, in Prod nicht. Die Pipeline baut pro Umgebung neu. Was ändern Sie?

Ein Build, ein Image, Promotion per Digest durch alle Umgebungen. Unterschiede nur in Konfiguration, die versioniert ist.

Szenario: SonarQube meldet hartcodierte Passwörter in Test-Fixtures. Was tun Sie?

Fake-Passwörter entfernen oder leer setzen, lokale Dev-Dateien begründet ausschliessen, Unterdrückungen dokumentieren. Die Regel nie pauschal abschalten.

Was sind flaky Tests und wie gehen Sie damit um?

Tests, die zufällig scheitern. Isolieren, markieren und fixen. Nie das ganze Gate abschalten.

Wie beschleunigen Sie eine Pipeline?

Abhängigkeiten cachen, Docker-Layer clever ordnen, Jobs parallelisieren, schnelle Tests zuerst, nur betroffene Teile bauen.

Design

Was geht kaputt, wenn man latest als Tag nutzt?

Der Stand ist nicht reproduzierbar, und ein Rollback ist unklar. Besser ist ein eindeutiger Tag oder der Digest.

Was geht kaputt, wenn die Approval im YAML steht?

Ein Entwickler kann sie im Pull Request entfernen. Darum gehört sie ans Environment.

Was geht kaputt, wenn man das Sonar-Gate bei Rot abschaltet?

Die Ursache bleibt und das Gate schützt nichts mehr. Besser die Ursache fixen oder einzeln begründet ausnehmen.

Mehr

Gerüst

  • Warum? Schnelles, sicheres Feedback. Nur geprüfter Code, immer dasselbe Artefakt.
  • Wie innen? build → test → scan → package → dev/test → prod mit Approval. Build once, deploy many. Ein rotes Gate stoppt die Kette.
  • Zahlen Sonar way: Coverage ≥ 80 %, Duplikation ≤ 3 %, Bewertung ab 20 neuen Zeilen. Azure-Cache läuft nach 7 Tagen ohne Nutzung ab.
  • Vergleich Delivery vs Deployment. Cache vs Artefakt. Push-Deploy vs GitOps.
  • Produktion Pipeline 45 Minuten → Cache, parallel, schnelle Tests zuerst. Neu bauen pro Umgebung → anderes Artefakt. Flaky Tests isolieren.
  • Design Digest statt latest. Approvals am Environment. Secrets aus Key Vault. Sonar-Regeln nie pauschal abschalten.

Beispiel: Azure Pipeline mit Sonar-Gate und Promotion

# Dockerfile (multi-stage)
FROM maven:3-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline        # Layer-Cache: nur bei neuem pom.xml
COPY src ./src
RUN mvn -B package -DskipTests

FROM eclipse-temurin:21-jre
COPY --from=build /src/target/app.jar /app/app.jar
USER 10001
ENTRYPOINT ["java","-jar","/app/app.jar"]
# azure-pipelines.yml (Auszug)
variables:
  MAVEN_CACHE_FOLDER: $(Pipeline.Workspace)/.m2/repository
  tag: $(Build.BuildId)
stages:
- stage: CI
  jobs:
  - job: build_test_scan
    steps:
    - task: Cache@2
      inputs:
        key: 'maven | "$(Agent.OS)" | **/pom.xml'
        restoreKeys: |
          maven | "$(Agent.OS)"
        path: $(MAVEN_CACHE_FOLDER)
    - task: SonarQubePrepare@<Version>     # Version der installierten Extension
      inputs:
        SonarQube: sonar-connection
        scannerMode: other
        extraProperties: |
          sonar.qualitygate.wait=true
    - script: mvn -B verify sonar:sonar -Dmaven.repo.local=$(MAVEN_CACHE_FOLDER)
    - task: Docker@2
      inputs:
        command: buildAndPush
        containerRegistry: acr-connection
        repository: api
        tags: $(tag)
- stage: DeployTest
  dependsOn: CI
  jobs:
  - deployment: deploy
    environment: test
    strategy: { runOnce: { deploy: { steps: [ script: ./deploy.sh test $(tag) ] } } }
- stage: DeployProd
  dependsOn: DeployTest
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: deploy
    environment: prod          # Approval ist im Environment "prod" konfiguriert
    strategy: { runOnce: { deploy: { steps: [ script: ./deploy.sh prod $(tag) ] } } }
Run #1842   main   Trigger: CI
  CI           ✓  Cache@2: Cache hit for key maven|"Linux"|…
                  Quality Gate: Passed
                  Pushed myacr.azurecr.io/api:1842
  DeployTest   ✓  deployment recorded on environment "test"
  DeployProd   ⏸  Waiting: 1 check (Approval) on environment "prod"

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Kein Azure-DevOps-Zugang in dieser Umgebung; Darstellung vereinfacht.

  1. Multi-Stage Dockerfile: Die erste Stufe hat Maven und JDK. Das Endimage hat nur JRE und das JAR. Kleiner, weniger Angriffsfläche.
  2. Layer-Cache: pom.xml wird vor dem Quellcode kopiert. Ändert sich nur Code, nutzt Docker den Abhängigkeits-Layer wieder.
  3. Cache@2: Der Schlüssel enthält den Hash aller pom.xml. Ändern sich die Abhängigkeiten, entsteht ein neuer Cache. restoreKeys liefert einen Teil-Treffer.
  4. sonar.qualitygate.wait=true: Der Scanner wartet auf das Gate-Ergebnis. Ist das Gate rot, schlägt der Schritt fehl.
  5. Stages: Ohne dependsOn laufen Stages der Reihe nach. Eine Stage läuft standardmässig nur, wenn ihre Vorgänger erfolgreich waren.
  6. Promotion: Test und Prod deployen denselben Tag 1842. Prod wartet auf die Approval des Environments.

Vergleich

  • Azure Pipelines: YAML mit Stages, Jobs, Environments, Approvals. Stark mit Azure und AKS, Service Connections mit Workload Identity.
  • GitHub Actions: Workflows pro Event, riesiger Marketplace, Environments mit Protection Rules.
  • Jenkins: selbst betrieben, Jenkinsfile, sehr flexibel. Preis: Pflege von Server und Plugins.
  • Bamboo: Atlassian-Server-Produkt mit Plänen und Deployment Projects.
  • CI-Push-Deploy vs GitOps-Pull: Bei Push hat die Pipeline Zugriff auf den Cluster. Bei GitOps schreibt die Pipeline nur ins Konfig-Repo; ArgoCD holt die Änderung.

In der Produktion

  1. Flaky Tests: Tests scheitern zufällig, das Team ignoriert Rot. Lösung: flaky Tests markieren und isoliert fixen, nie das Gate abschalten.
  2. Pipeline dauert 40 Minuten: Niemand wartet darauf. Lösung: Cache, Parallelisierung, Tests aufteilen, Docker-Layer-Reihenfolge, kleinere Images.
  3. „Works in test, fails in prod“: Pro Umgebung neu gebaut. Lösung: ein Artefakt, Promotion per Digest.
  4. Gate wird umgangen: Jemand pusht direkt auf main. Lösung: Branch Policies, Pflicht-Build, Pflicht-Review.
  5. Testcontainer OOM in CI: Datenbank-Container werden vom Kernel beendet. Lösung: Speicher begrenzen, Tests serialisieren, beim Start schnell scheitern.
  6. Cache vergiftet oder falsch: Ein fester Schlüssel aktualisiert nie. Lösung: Lock-Datei im Schlüssel, bei Bedarf Präfix wie v2.

Diagnose: Werkzeuge und Befehle

  • Pipeline-Logs mit system.debug=true: zeigen jeden Schritt detailliert.
  • Pipeline Analytics (Azure DevOps): Dauer, Erfolgsquote, flaky Tests über Zeit.
  • Cache-Meldungen im Log: „Cache hit“, „Cache miss“, „inexact“ (über cacheHitVar).
  • SonarQube-Projektseite: zeigt, welche Gate-Bedingung rot ist und auf welchen Zeilen.
  • docker history <image>: zeigt Layer und deren Grösse.
  • az acr repository show-tags bzw. show-manifests: welche Tags und Digests existieren.
  • Environment-Ansicht: welcher Build läuft wo, wer hat wann genehmigt.

Senior-Punkte

  1. Build once, deploy many. Was in Test geprüft wurde, muss bit-gleich in Produktion laufen.
  2. Gates müssen ernst sein. Ein Gate, das man per Knopf übergehen kann, ist kein Gate. Ausnahmen dokumentiert und begründet.
  3. Schnelles Feedback ist ein Architektur-Ziel. Unter 10 Minuten für den PR-Build ist ein gutes Ziel; jede Minute kostet das ganze Team.
  4. Pipeline ist Code: versioniert, reviewt, mit Templates wiederverwendet. Keine Klick-Konfiguration.
  5. Sicherheit gehört in die Kette: SAST, Abhängigkeits- und Image-Scan, Secret-Scan. Aber mit klaren Schwellen, sonst ignoriert man sie.
  6. Sonar-Funde fixen, nicht pauschal unterdrücken. Wenn nötig, einzeln begründet ausschliessen.
