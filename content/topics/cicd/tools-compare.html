Azure DevOps vs Jenkins vs GitHub Actions vs GitLab

Kern: Alle vier Werkzeuge haben dasselbe Grundmodell. Ein Trigger startet eine Pipeline, ein Agent oder Runner führt Jobs mit Schritten aus. Sie unterscheiden sich in Betrieb, Konfiguration, Ökosystem und darin, wo Code, Tickets und Artefakte liegen.

Antwort-Muster

Frage: Azure DevOps, Jenkins, GitHub Actions oder GitLab, was wählst du?

  1. Mechanismus: Alle vier lesen eine Pipeline als Code, planen Jobs und lassen sie auf Agents laufen. Jenkins ist selbst betrieben und plugin-basiert, die anderen drei kommen mit Plattform.
  2. Zahl: Ein Job darf auf GitHub-gehosteten Runnern 6 Stunden laufen. Bei Azure DevOps und GitLab ist der Standard 60 Minuten.
  3. Trade-off: Jenkins ist am flexibelsten, braucht aber am meisten Betrieb. Die Plattform-Lösungen sind einfacher, binden dich aber stärker.
  4. Produktion: Ich wähle das Werkzeug, in dem der Code schon liegt. Dazu zählen Secrets ohne Passwort, Freigaben und eigene Agents im privaten Netz.

1. Eine Pipeline läuft in allen vier Werkzeugen gleich ab

  1. Trigger: Ein Ereignis im Repository startet die Pipeline. Auch ein Zeitplan oder ein manueller Start geht.
  2. Laden: Die Definition liegt im Repo. Bei Azure DevOps, GitHub und GitLab ist es YAML. Bei Jenkins ist es ein Jenkinsfile.
  3. Planen: Der Dienst baut aus der Definition Stages und Jobs. Er beachtet Abhängigkeiten und Bedingungen.
  4. Agent holt den Job: Ein freier Agent nimmt den Job. Es gibt gehostete und selbst betriebene Agents. Bei Mangel wartet der Job in der Warteschlange.
  5. Schritte: Der Agent führt die Schritte nacheinander aus. Das sind Skripte oder wiederverwendbare Bausteine wie Tasks, Actions oder Plugins.
  6. Ergebnis: Status und Logs gehen zurück an den Dienst. Artefakte werden gespeichert. Ein Environment kann eine Freigabe verlangen.

2. Aufbau

  1. Azure DevOps: Pipeline besteht aus Stages, Jobs und Steps. Agents liegen in einem Pool. Environments geben Freigaben.
  2. GitHub Actions: Ein Workflow hat Jobs mit Schritten. Runner führen sie aus. Der Marketplace liefert fertige Actions.
  3. GitLab CI: Die Datei .gitlab-ci.yml definiert Stages und Jobs. Runner führen sie mit einem Executor aus.
  4. Jenkins: Der Controller verwaltet Konfiguration und Zugriff. Agents führen Builds aus. Plugins erweitern alles.
  5. Wiederverwendung: Templates in Azure DevOps, Reusable Workflows in GitHub, include in GitLab, Shared Libraries in Jenkins.
  6. Freigaben: Environments mit Approvals in Azure DevOps und GitHub. Geschützte Environments in GitLab. Eingabe-Schritte in Jenkins.

3. Details

  1. Azure Pipelines Zeitlimit: Ohne Angabe läuft ein Job höchstens 60 Minuten. Der Wert 0 heisst auf selbst betriebenen Agents unbegrenzt. Auf Microsoft-gehosteten Agents sind es 360 Minuten bei öffentlichen und 60 Minuten bei privaten Projekten.
  2. Azure Pipelines Gratis-Stufe: Für private Projekte gibt es einen Job mit höchstens 60 Minuten pro Lauf und 1'800 Minuten pro Monat. Der Microsoft-gehostete Teil muss man aktivieren. Die Stufe für selbst betriebene Agents ist automatisch da.
  3. Parallele Jobs: Ein Parallel Job ist Rechenkapazität für einen Job. Mit einem Parallel Job läuft ein Job zugleich. Weitere Jobs warten.
  4. Azure DevOps Environments: Ein Environment kann Approvals und Checks haben. Sie müssen erfüllt sein, bevor eine Stage die Ressource nutzt. Ein Deployment Job schreibt die Historie am Environment.
  5. GitHub Actions Grenzen: Ein Job auf gehosteten Runnern darf 6 Stunden laufen. Ein Workflow-Lauf darf 35 Tage dauern, inklusive Wartezeit. Eine Matrix erzeugt höchstens 256 Jobs pro Lauf. Ein Job auf selbst betriebenen Runnern wartet höchstens 24 Stunden in der Warteschlange.
  6. GitHub Environments: Required Reviewers geben Deployments frei. Es können bis zu sechs Personen oder Teams gelistet sein. Einer reicht für die Freigabe. Self-Review lässt sich verbieten.
  7. GitLab CI Aufbau: Jobs gehören zu Stages. Die Schlüsselwörter rules, needs, extends, include und environment steuern Ablauf und Wiederverwendung. needs erlaubt einen Ablauf ohne auf die ganze Stage zu warten.
  8. GitLab Zeitlimit: Das Standard-Timeout für Jobs im Projekt beträgt 60 Minuten. Es muss mindestens 10 Minuten und weniger als einen Monat betragen.
  9. Jenkins Architektur: Der Controller ist der Jenkins-Dienst. Er macht Konfiguration, Authentifizierung und HTTP. Agents führen Builds aus. Der Build auf dem Built-in Node wird aus Sicherheits- und Leistungsgründen nicht empfohlen.
  10. Jenkins Pipeline: Es gibt Declarative und Scripted Pipeline. Declarative braucht agent, stages und steps. Wiederverwendung läuft über Shared Libraries.
  11. Plugins: Jenkins lebt von Plugins. Das gibt Flexibilität, kostet aber Wartung, Updates und Kompatibilität.
  12. Ökosystem: GitHub hat den Marketplace mit Actions. Azure DevOps hat Tasks und die Extension Marketplace. GitLab bringt Registry, Issues und Security-Scans in einer Plattform mit.

4. Fallen

  • „Jenkins ist veraltet und kostenlos.“ → Falsch. Jenkins ist gepflegt und flexibel. Es kostet Betrieb, Updates und Plugin-Pflege.
  • „GitHub Actions ersetzt Azure DevOps vollständig.“ → Falsch. Azure DevOps hat Boards, Test Plans, Artifacts und mehr. Es kommt auf den Bedarf an.
  • „Ein Job darf überall gleich lang laufen.“ → Falsch. Limits unterscheiden sich. GitHub-gehostet 6 Stunden, Azure DevOps und GitLab standardmässig 60 Minuten.
  • „Selbst betriebene Runner sind automatisch sicherer.“ → Falsch. Du bist für Patches und Isolation verantwortlich. Nicht vertrauenswürdiger Code auf geteilten Runnern ist riskant.
  • „YAML-Pipelines sind in allen vier gleich portierbar.“ → Falsch. Syntax, Schlüsselwörter und Bausteine sind verschieden. Nur das Grundmodell ist gleich.
  • „Auf dem Built-in Node von Jenkins zu bauen ist bequem und harmlos.“ → Falsch. Es wird aus Sicherheits-, Leistungs- und Skalierungsgründen nicht empfohlen.

5. Selbsttest

Warum?

Warum Pipelines als Code?

Sie sind im Repo versioniert, reviewbar und reproduzierbar. Ein Rollback ist ein Git-Revert.

Warum ein selbst betriebener Agent?

Für Zugriff auf private Netze, spezielle Hardware oder weniger Wartezeit. Du betreibst und patchst ihn selbst.

Warum wählt man oft die Plattform, in der der Code liegt?

Trigger, Berechtigungen und PR-Status sind eng verbunden. Es gibt weniger Integrationen zu pflegen.

Wie innen?

Wie läuft ein Job in Azure Pipelines ab?

Die Pipeline wird in Stages und Jobs geplant. Ein Agent aus dem Pool holt den Job. Er führt die Steps aus und meldet den Status.

Wie ist Jenkins aufgebaut?

Ein Controller verwaltet Konfiguration, Zugriff und Zeitplan. Agents mit Executors führen die Builds aus. Plugins erweitern die Funktionen.

Wie arbeitet ein GitLab Runner?

Er holt Jobs vom GitLab-Server und führt sie mit einem Executor aus. Der Executor bestimmt die Umgebung, zum Beispiel eine Shell oder einen Container.

Was ist needs in GitLab?

Es erlaubt einem Job, direkt nach seinen Abhängigkeiten zu starten. Er wartet nicht auf die ganze vorherige Stage.

Wie geben Environments Deployments frei?

Das Environment hat Approvals und Checks. Ein Job, der es nutzt, wartet auf die Freigabe der Reviewer.

Zahlen

Wie lang darf ein Job auf GitHub-gehosteten Runnern laufen?

6 Stunden. Danach wird er beendet.

Wie viele Jobs erzeugt eine GitHub-Matrix höchstens?

256 pro Workflow-Lauf.

Was ist das Standard-Timeout in Azure Pipelines und GitLab?

Jeweils 60 Minuten.

Was bietet die Gratis-Stufe in Azure Pipelines für private Projekte?

Einen Job, höchstens 60 Minuten pro Lauf und 1'800 Minuten pro Monat.

Vergleich

Azure DevOps vs GitHub Actions?

Azure DevOps hat Boards, Repos, Artifacts und Test Plans in einem Produkt. GitHub Actions ist enger am Code und hat den grossen Marketplace.

GitLab CI vs GitHub Actions?

GitLab bringt Registry, Security und Issues in einer Plattform. GitHub Actions hat den grösseren Marketplace. Die Konzepte sind ähnlich.

Jenkins vs die Plattform-Lösungen?

Jenkins ist am flexibelsten und selbst betrieben. Die anderen drei sind einfacher im Betrieb, binden dich aber an die Plattform.

Declarative vs Scripted Pipeline in Jenkins?

Declarative hat feste Struktur und ist leichter lesbar. Scripted ist freier, aber komplexer.

Produktion

Wie sichert man Deployments nach Prod ab?

Mit Environments und Approvals, geschützten Branches und OIDC statt Passwörtern. Der Prod-Job läuft nur auf geschützten Branches.

Wie vermeidet man doppelte Pipeline-Logik?

Mit Templates, Reusable Workflows, include oder Shared Libraries. Ein Standard pro Firma, kleine Abweichungen pro Team.

Wie skaliert man Agents?

Mit Pools oder Runner-Gruppen und automatischer Skalierung, oft auf Kubernetes oder VM-Scale-Sets. Der Job wartet sonst in der Warteschlange.

Szenario: Alle Builds warten, obwohl der Agent frei scheint. Was prüfen Sie?

Ob genug Parallel Jobs gebucht sind, ob die Labels oder Demands passen und ob der Agent online ist. Dann die Warteschlange und die Limits ansehen.

Szenario: Ein Team will von Jenkins auf eine Plattform wechseln. Wie gehen Sie vor?

Pipelines nach Wert sortieren, ein Pilotprojekt migrieren, Plugin-Funktionen durch Bausteine ersetzen und Secrets neu aufsetzen. Jenkins parallel laufen lassen, bis alles umgezogen ist.

Design

Wann Jenkins?

Bei sehr speziellen Anforderungen, vorhandener Infrastruktur oder Plugins ohne Ersatz. Plane Betrieb und Updates ein.

Wann Azure DevOps?

Wenn Microsoft-Umfeld, Boards, Artifacts und Test Plans gebraucht werden. Es passt gut zu Azure-Deployments.

Wann GitHub Actions?

Wenn der Code auf GitHub liegt und Teams den Marketplace und einfache Workflows wollen.

Szenario: Ein Kunde verlangt, dass nichts den eigenen Netzwerkbereich verlässt. Was wählen Sie?

Selbst betriebene Agents oder Runner im Kundennetz, mit der Plattform oder Jenkins. Secrets und Artefakte bleiben im Netz.

Mehr

Gerüst

  • Warum? Build, Test und Deployment automatisch und wiederholbar ausführen.
  • Wie innen? Trigger, Pipeline laden, planen, Agent holt Job, Schritte, Ergebnis.
  • Zahlen GitHub 6 Stunden pro Job, Matrix 256. Azure DevOps und GitLab 60 Minuten. ADO-Gratisstufe 1'800 Minuten.
  • Vergleich Plattform gegen Jenkins. Azure DevOps gegen GitHub. Declarative gegen Scripted.
  • Produktion Environments mit Freigabe, OIDC, Templates, skalierbare Agents.
  • Design Werkzeug dort, wo der Code liegt. Jenkins nur bei klarem Bedarf.

Beispiel: Dieselbe Pipeline in vier Syntaxen

# Azure Pipelines (azure-pipelines.yml)
trigger: [main]
pool: { vmImage: ubuntu-latest }
steps:
- script: ./gradlew test

# GitHub Actions (.github/workflows/ci.yml)
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v7
    - run: ./gradlew test

# GitLab CI (.gitlab-ci.yml)
test:
  stage: test
  script: ./gradlew test

// Jenkins (Jenkinsfile, Declarative)
pipeline {
  agent any
  stages { stage('Test') { steps { sh './gradlew test' } } }
}

Nicht ausgeführt (keine der vier Plattformen auf dieser Maschine). Die Ausschnitte zeigen nur die Form. Checkout-Schritte und Java-Setup fehlen in einigen.

  1. Azure Pipelines und GitLab nutzen YAML mit script. Azure holt den Code automatisch aus dem Repo.
  2. GitHub braucht den Schritt actions/checkout und gibt die Runner-Art per runs-on an.
  3. Jenkins nutzt Groovy-Syntax. agent any wählt irgendeinen freien Agent.
  4. Die Konzepte sind gleich, die Schlüsselwörter nicht.

Vergleich

  • Azure DevOps: Boards, Repos, Pipelines, Artifacts und Test Plans in einem Produkt. Stark mit Azure.
  • GitHub Actions: Eng am Code, grosser Marketplace, Environments mit Reviewern.
  • GitLab CI: Eine Plattform mit Registry, Issues, Security und CI. Selbst betreibbar oder SaaS.
  • Jenkins: Open Source, selbst betrieben, sehr flexibel durch Plugins.
  • Kosten: Plattformen rechnen Minuten oder Parallel Jobs ab. Jenkins kostet Infrastruktur und Betrieb.
  • Lock-in: Pipeline-Syntax ist pro Werkzeug anders. Halte Logik in Skripten, damit ein Wechsel leichter ist.

Produktion

  1. Warteschlangen: Zu wenig Agents oder Parallel Jobs. Lösung: mehr Kapazität buchen oder Agents skalieren.
  2. Plugin-Chaos in Jenkins: Updates brechen Pipelines. Lösung: Plugins minimieren, Updates testen, Konfiguration als Code.
  3. Pipeline-Wildwuchs: Jedes Team baut anders. Lösung: gemeinsame Templates oder Libraries.
  4. Timeout bricht Jobs ab: Ein langer Job läuft in das Limit. Lösung: Job teilen, cachen oder Timeout bewusst setzen.
  5. Unsichere selbst betriebene Runner: Fremder Code läuft auf geteilter Maschine. Lösung: temporäre Runner und Trennung.
  6. Kein Rollback bei Deployments: Pipeline kennt nur Vorwärts. Lösung: Versionierte Artefakte und ein Rollback-Job.

Diagnose: Werkzeuge und Befehle

  • Pipeline-Log und Job-Details: Zeigen Schritt, Dauer und Fehler.
  • Agent-Status: Pools in Azure DevOps, Runner-Seite in GitHub und GitLab, Nodes in Jenkins.
  • Parallel-Job-Auslastung: In Azure DevOps die Seite zur Nutzung der Parallel Jobs ansehen.
  • Pipeline-Linter: GitLab hat einen CI-Lint. Azure DevOps und GitHub prüfen YAML im Editor.
  • Jenkins System Log und Build Queue: Zeigen Plugin-Fehler und wartende Jobs.
  • Audit-Logs: Zeigen, wer eine Pipeline oder ein Secret geändert hat.

Senior-Punkte

  1. Wähle nach Umfeld, nicht nach Mode. Der Code-Ort und die Cloud geben oft die Antwort.
  2. Betrieb ist ein Kostenfaktor. Jenkins ist nicht gratis, wenn du Controller, Plugins und Agents pflegst.
  3. Halte Logik in Skripten. Die Pipeline ruft sie nur auf. So bleibt ein Wechsel machbar.
  4. Standardisiere. Templates und Libraries verhindern Wildwuchs.
  5. Trenne Vertrauen. Fremder Code läuft auf kurzlebigen Runnern ohne Secrets.
  6. Plane Freigaben ein. Prod braucht Approvals, geschützte Branches und Audit.
