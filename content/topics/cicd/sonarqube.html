SonarQube und Code-Qualität

Kern: SonarQube analysiert Quellcode statisch auf Bugs, Sicherheitslücken, Code Smells, Duplikate und Testabdeckung. Ein Quality Gate ist eine Reihe von Bedingungen, die bestanden sein müssen. Das Prinzip Clean as You Code prüft vor allem den neuen Code und lässt alten Code in Ruhe.

Antwort-Muster

Frage: Wie bindest du SonarQube in die Pipeline ein, und was macht ein Quality Gate?

  1. Mechanismus: Ein Scanner analysiert den Code in der CI und schickt den Bericht an den Server. Der Server verarbeitet ihn asynchron und bewertet das Quality Gate.
  2. Zahl: Das Standard-Gate Sonar way verlangt auf neuem Code mindestens 80 % Abdeckung und höchstens 3 % Duplikate. Dazu keine neuen Issues.
  3. Trade-off: Ein strenges Gate sichert Qualität, kann aber Pull Requests blockieren. Darum gilt es für neuen Code, nicht für Altlasten.
  4. Produktion: Die Pipeline wartet auf das Gate-Ergebnis und schlägt bei Fail fehl. Der Pull Request wird bei Fail gesperrt.

1. Eine Analyse in der Pipeline, Schritt für Schritt

  1. Checkout: Die Pipeline holt den Code mit voller Git-Historie. Bei einem Shallow Clone fehlen die Blame-Daten, und die Analyse kann scheitern.
  2. Vorbereiten: Der Schritt Prepare Analysis Configuration setzt Server und Projekt-Key. In Azure Pipelines ist er die Task SonarQubePrepare.
  3. Bauen und testen: Bei Maven oder Gradle läuft die Analyse im Build mit. Die Tests schreiben einen Coverage-Bericht, etwa im JaCoCo-Format.
  4. Senden: Nach der Analyse schickt der Scanner das Ergebnis an den Server. Das sind Quellen, Issues und Metriken. Im Scanner-Log steht dann EXECUTION SUCCESS.
  5. Verarbeiten: Die Compute Engine arbeitet Berichte aus einer Warteschlange ab, einen nach dem anderen. Erst danach sind die Ergebnisse sichtbar.
  6. Bewerten: Der Server prüft das Quality Gate. Der Schritt Publish Quality Gate Result wartet darauf und meldet Pass oder Fail an die Pipeline.

2. Aufbau

  1. Scanner ist das Programm in der CI. Es gibt einen für Maven, Gradle, .NET und eine CLI für andere Sprachen.
  2. Server speichert Ergebnisse und zeigt sie im Web. Die Compute Engine verarbeitet die Berichte.
  3. Quality Profile ist die Regelmenge pro Sprache. Es legt fest, was ein Issue ist.
  4. Quality Gate ist der Pass-oder-Fail-Test mit Bedingungen auf Metriken. Jedes Projekt hat genau eines.
  5. New Code ist der Zeitraum, der als neu gilt. Standard ist die Previous version, Alternative ist eine Zahl von Tagen.
  6. Branch und Pull Request Analysis gehören zur Developer Edition. Die Community Build analysiert nur einen Branch.

3. Details

  1. Clean as You Code: Das Gate prüft neuen Code streng. Alter Code wird nicht blockiert. So kommt kein Team in ein „Alles ist rot“-Gefühl, und neue Schulden entstehen nicht.
  2. Sonar way: Das eingebaute Standard-Gate ist read-only. Es hat vier Bedingungen auf neuem Code. Keine neuen Issues, neue Security Hotspots geprüft, Coverage mindestens 80 % und Duplikate höchstens 3 %.
  3. Hotspots werden abgelöst: Security Hotspots laufen aus. Regeln, die früher Hotspots erzeugten, erzeugen jetzt Vulnerabilities oder Security-Issues. Die Hotspot-Bedingung gilt als deprecated.
  4. Gate-Bedingung: Eine Bedingung besteht aus Metrik, Operator und Fehlerwert. Beispiel ist Blocker Issues grösser als 0. Trifft eine Bedingung zu, schlägt das Gate fehl.
  5. Branch vs Pull Request: Bei einem Branch gelten Bedingungen auf neuem und auf Gesamtcode. Bei einem Pull Request gelten nur die Bedingungen auf neuem Code. Neu ist, was sich gegenüber dem Ziel-Branch geändert hat.
  6. Fudge Factor: Bedingungen auf Duplikate und Coverage werden erst ab 20 neuen Zeilen geprüft. So blockiert eine winzige Änderung das Gate nicht. Die Einstellung ist standardmässig an.
  7. Coverage: SonarQube misst keine Abdeckung selbst. Es importiert Berichte aus Tools wie JaCoCo. Fehlt der Bericht, gibt es keine Abdeckungs-Werte.
  8. MQR-Modus: Er weist jedem Issue pro Software-Qualität (Security, Reliability, Maintainability) eine eigene Severity zu. Die Stufen sind Blocker, High, Medium, Low und Info.
  9. SCM-Daten: SonarQube braucht einen vollen Git-Clone für Blame und die Erkennung von neuem Code. Ohne SCM-Daten nutzt es die Analyse-Daten, um geänderte Zeilen zu datieren.
  10. Asynchrone Verarbeitung: Der Scanner ist früher fertig als der Server. Erst wenn die Hintergrund-Task fertig ist, sind Ergebnisse sichtbar. Darum wartet die Pipeline auf das Gate.
  11. Pull Request Decoration: Der Gate-Status erscheint am Pull Request in der Plattform. Er kann den Merge blockieren. Die CI kann bei Fail ebenfalls fehlschlagen.
  12. Editionen: Es gibt Community Build, dazu Developer, Enterprise und Data Center. Branch- und PR-Analyse bringt die Developer Edition. Enterprise ergänzt zum Beispiel Bedingungen auf priorisierten Regeln.

4. Fallen

  • „Ein grünes Quality Gate heisst, der Code ist fehlerfrei.“ → Falsch. Es prüft nur die gewählten Bedingungen, vor allem auf neuem Code. Alter Code und Logikfehler bleiben unberührt.
  • „SonarQube führt die Tests aus und misst die Abdeckung.“ → Falsch. Es importiert nur einen Coverage-Bericht aus deinem Testlauf.
  • „Nach EXECUTION SUCCESS sind die Ergebnisse sofort da.“ → Falsch. Der Server verarbeitet den Bericht erst in einer Warteschlange. Die Pipeline muss auf das Gate warten.
  • „Ein Shallow Clone reicht für die Analyse.“ → Falsch. SonarQube braucht die volle Historie. Sonst fehlen Blame-Daten, und die Analyse kann scheitern.
  • „Das Gate gilt bei Pull Requests für den ganzen Code.“ → Falsch. Bei Pull Requests zählen nur Bedingungen auf neuem Code.
  • „Die Coverage-Grenze von 80 % gilt für den ganzen Code.“ → Falsch. Sonar way verlangt sie nur für neuen Code.

5. Selbsttest

Warum?

Warum prüft man vor allem neuen Code?

Alter Code lässt sich nicht schnell reparieren. Ein Gate auf neuem Code verhindert neue Schulden und blockiert das Team nicht.

Warum bricht man die Pipeline bei Gate-Fail ab?

Sonst wird das Gate ignoriert. Ein Fail muss den Merge oder das Deployment stoppen.

Warum braucht Sonar die volle Git-Historie?

Für Blame-Daten und die Erkennung von neuem Code. Bei einem Shallow Clone werden Blame-Daten übersprungen.

Wie innen?

Wie kommt das Ergebnis auf den Server?

Der Scanner analysiert lokal und sendet einen Bericht. Die Compute Engine verarbeitet ihn als Hintergrund-Task. Berichte laufen seriell.

Wie wird neuer Code bestimmt?

Über SCM-Blame und die New-Code-Definition. Standard ist die Previous version, Alternative eine Zahl von Tagen. Bei Pull Requests gilt die Änderung gegenüber dem Ziel-Branch.

Wie wird die Abdeckung berechnet?

Aus einem importierten Bericht, etwa JaCoCo. SonarQube rechnet daraus die Zeilen- und Bedingungsabdeckung. Fehlt der Bericht, hat das Projekt keine Abdeckungs-Werte.

Was macht ein Quality Profile?

Es legt fest, welche Regeln für eine Sprache aktiv sind. Die Treffer sind die Issues, die das Gate zählt.

Wie meldet SonarQube das Ergebnis an die CI?

Die CI wartet auf die Hintergrund-Task und liest das Gate. In Azure Pipelines macht das Publish Quality Gate Result.

Zahlen

Wie sind die Bedingungen von Sonar way?

Keine neuen Issues, neue Security Hotspots geprüft, Coverage auf neuem Code mindestens 80 %, Duplikate auf neuem Code höchstens 3 %.

Was ist der Fudge Factor?

Coverage- und Duplikat-Bedingungen werden erst ab 20 neuen Zeilen geprüft. So blockieren kleine Änderungen das Gate nicht.

Welche Severities gibt es im MQR-Modus?

Blocker, High, Medium, Low und Info.

Wie viele eingebaute Gates gibt es?

Zwei, Sonar way und Sonar way for agentic AI.

Vergleich

SonarQube vs Linter?

Ein Linter prüft Stil und einfache Fehler schnell im Editor. SonarQube prüft tiefer, speichert den Verlauf und hat Quality Gates.

SonarQube vs SAST- und Dependency-Scanner?

SonarQube prüft deinen eigenen Code. Dependency-Scanner prüfen Bibliotheken auf bekannte Lücken. Man braucht beides.

Community Build vs Developer Edition?

Developer bringt Branch- und Pull-Request-Analyse und mehr Sprachen. Die Community Build analysiert einen Branch.

SonarQube Server vs SonarQube Cloud?

Server betreibst du selbst. Cloud ist der gehostete Dienst von Sonar.

Produktion

Wie bindet man das Gate in Azure Pipelines ein?

Prepare Analysis vor dem Build, Build mit Analyse, danach Publish Quality Gate Result. Die Pipeline schlägt bei Fail fehl.

Wie sperrt man Merges bei schlechter Qualität?

Mit der Pull Request Decoration und einer Branch Policy, die den Sonar-Status verlangt. Ein Fail blockiert den Merge.

Wie geht man mit sehr altem Code um?

Mit Clean as You Code. Neuer Code erfüllt das Gate, alter Code wird schrittweise verbessert, wenn man ihn anfasst.

Szenario: Die Pipeline ist grün, aber im SonarQube fehlen die neuen Ergebnisse. Was prüfen Sie?

Ob die Hintergrund-Task noch in der Warteschlange ist oder fehlgeschlagen ist. Erst nach der Task sind Ergebnisse sichtbar. Danach Speicher und Logs der Compute Engine.

Szenario: Das Gate schlägt wegen der Coverage fehl, obwohl Tests laufen. Was ist die Ursache?

Der Coverage-Bericht wurde nicht gefunden oder nicht importiert. Pfad und Format prüfen und sicherstellen, dass die Tests vor der Analyse laufen.

Design

Welche Gate-Bedingungen wählen Sie?

Sonar way als Start. Auf neuem Code keine neuen Issues, genug Coverage und wenig Duplikate. Für Kernbibliotheken strenger.

Soll jedes Projekt dasselbe Gate haben?

Nicht unbedingt. Ein Framework verlangt oft mehr als eine kleine Web-App. Man weist Gates pro Projekt zu.

Wie führt man SonarQube in einem Team mit viel Altcode ein?

Mit dem Gate auf neuem Code und ohne Blockade für Altlasten. Neue Schulden sind sofort sichtbar.

Szenario: Entwickler klagen, dass kleine Fixes am Gate scheitern. Was tun Sie?

Prüfen, ob der Fudge Factor aktiv ist. Dann den Fall ansehen und das Gate nur bei echtem Bedarf anpassen. Das Gate nicht aufweichen, nur weil es stört.

Mehr

Gerüst

  • Warum? Qualität und Sicherheit automatisch prüfen, vor dem Merge.
  • Wie innen? Scanner, Bericht, Compute Engine, Quality Gate. Neuer Code über SCM-Blame.
  • Zahlen Sonar way: 80 % Coverage, 3 % Duplikate auf neuem Code. Fudge Factor 20 Zeilen.
  • Vergleich Linter, Dependency-Scanner, Community Build und Developer Edition.
  • Produktion Full Clone, Gate abwarten, PR-Decoration, Coverage-Bericht prüfen.
  • Design Clean as You Code, Gates pro Projekt, Gate nicht aufweichen.

Beispiel: Azure-Pipeline mit SonarQube-Tasks (Maven)

steps:
- checkout: self
  fetchDepth: 0            # volle Historie fuer Blame

- task: SonarQubePrepare@8
  inputs:
    SonarQube: '<service-connection>'
    scannerMode: 'other'
    extraProperties: 'sonar.projectKey=<project-key>'

- task: Maven@4
  inputs:
    sonarQubeRunAnalysis: true

- task: SonarQubePublish@8
  inputs:
    pollingTimeoutSec: '300'

# lokal ohne Azure DevOps
mvn clean verify org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
  -Dsonar.token=$SONAR_TOKEN

Nicht ausgeführt (kein SonarQube-Server auf dieser Maschine). Der Aufbau folgt der Sonar-Doku für SonarQube Server 2026.5. Die Task-Version muss zur installierten Extension passen. Die Doku nennt dazu @8.

  1. fetchDepth: 0 holt die ganze Historie. SonarQube braucht sie für Blame-Daten.
  2. SonarQubePrepare setzt Server und Projekt-Key. Es läuft vor dem Build.
  3. Die Maven-Task läuft mit der Analyse. Das Gate wird danach vom Server berechnet.
  4. SonarQubePublish wartet bis zu 300 Sekunden auf die Hintergrund-Task und meldet das Gate-Ergebnis.
  5. Lokal braucht das Plugin sonar.token und SONAR_HOST_URL.

Vergleich

  • SonarQube: Code-Qualität und Security-Regeln, Verlauf, Quality Gates, Branch- und PR-Analyse.
  • Linter (ESLint, Checkstyle): Schnelle Stilprüfung, ohne Verlauf und Gate.
  • SAST-Tools: Fokus auf Sicherheit im eigenen Code. Überschneidet sich mit SonarQube.
  • Dependency-Scanner: Prüft Bibliotheken auf bekannte Lücken. Ergänzt SonarQube.
  • JaCoCo: Misst Abdeckung. SonarQube liest nur den Bericht.
  • Defender for DevOps: Bringt Code-Scan-Ergebnisse in Defender for Cloud. Es ersetzt kein Quality Gate.

Produktion

  1. Analyse scheitert wegen Shallow Clone: Blame-Daten fehlen. Lösung: voller Checkout.
  2. Coverage fehlt oder 0 %: Bericht fehlt oder falscher Pfad. Lösung: Pfad setzen und Test-Task vor der Analyse laufen lassen.
  3. Gate wird ignoriert: Die Pipeline wartet nicht auf das Ergebnis. Lösung: Publish Quality Gate Result und Branch Policy.
  4. Warteschlange staut sich: Die Compute Engine ist überlastet oder ohne Speicher. Lösung: mehr Worker oder RAM, Fehler im Background-Tasks-Bereich ansehen.
  5. Neuer Code wird falsch bestimmt: Die New-Code-Definition passt nicht zum Release-Rhythmus. Lösung: auf eine Zahl von Tagen umstellen.
  6. Rauschen durch False Positives: Entwickler ignorieren das Tool. Lösung: Regeln im Quality Profile anpassen und Issues sauber als False Positive markieren.

Diagnose: Werkzeuge und Befehle

  • Project → Overview und Summary: Gate-Status und Bedingungen mit Ist-Werten.
  • Administration → Background Tasks: Zeigt die Warteschlange und fehlgeschlagene Berichte.
  • Scanner-Log: Zeigt Warnungen zu Shallow Clone, fehlendem Coverage-Bericht und Blame.
  • Quality Gate History: Zeigt, wann das Gate wechselte, und die Ursache.
  • Web API api/qualitygates: Gates per Skript lesen und verwalten.
  • Pull-Request-Ansicht im Server: Zeigt nur neue Issues für diesen PR.

Senior-Punkte

  1. Ein Gate ist eine Vereinbarung. Schwäche es nicht, nur weil es einem Team lästig ist.
  2. Neuer Code zählt. Nutze Clean as You Code, damit ein Altbestand die Einführung nicht tötet.
  3. Coverage ist nur eine Zahl. Ein Test ohne Aussage hebt sie. Prüfe auch die Testqualität.
  4. Das Gate ersetzt kein Review. Es findet Muster, keine Designfehler.
  5. Asynchrone Verarbeitung planen. Die Pipeline braucht einen Timeout für das Warten.
  6. Security-Scan ist ein Mix. SonarQube, Dependency-Scan, Secrets-Scan und Defender ergänzen sich.
