Branching-Strategien: Trunk-Based, GitFlow, GitHub Flow

Kern: Eine Branching-Strategie ist die Team-Regel, wie Code von der Entwicklung bis zum Release über Branches fliesst. Sie entscheidet, wie oft integriert wird und wie Releases und Hotfixes laufen. Die Wahl hängt am Release-Modell: kontinuierlich ausliefern passt zu Trunk-Based oder GitHub Flow, mehrere versionierte Releases parallel passen zu GitFlow.

1. Wo sitzt die Branching-Strategie?

  1. main / trunk: der zentrale Branch. In jeder modernen Strategie muss er immer baubar und grün sein.
  2. Feature-Branch: ein Branch für eine Änderung. Die Strategie legt fest, wie lange er leben darf.
  3. Release-Branch: ein Branch, der einen Release-Stand stabilisiert. Nicht jede Strategie braucht ihn.
  4. Feature Flags: Schalter im Code. Unfertiger Code ist gemergt, aber für Nutzer ausgeschaltet.
  5. Pipeline und Branch Policies setzen die Strategie technisch durch.

2. Die Reise eines Features in drei Modellen (die Geschichte zum Merken)

  1. Trunk-Based: Anna schreibt ein Feature. Sie mergt kleine Schritte täglich in den Trunk. Der unfertige Teil ist hinter einem Feature Flag versteckt. Ein Release-Branch entsteht erst kurz vor dem Release, nur Cherry-Picks gehen dorthin.
  2. GitHub Flow: Anna erstellt einen Branch, pusht, öffnet einen Pull Request. Nach Review und grünem Build mergt sie in main. Danach löscht sie den Branch. main ist immer deploybar.
  3. GitFlow: Anna zweigt von develop ab. Ihr Feature-Branch geht zurück in develop. Für das Release entsteht release/x aus develop. Er wird in master und develop gemergt und getaggt.
  4. Hotfix in GitFlow: Ein Hotfix zweigt von master ab und geht in master und develop.
  5. Der Unterschied: Je länger ein Branch lebt, desto später sieht das Team Konflikte. Trunk-Based integriert am häufigsten.

3. Beispiel: Trunk-Based mit Release-Branch in Git

# flags.properties: export.enabled=false
git switch -c feat/export main          # kurzer Branch (im Team: push → PR → Build → Review)
git commit -am "feat: export behind flag"
git switch main; git merge --no-edit feat/export; git branch -d feat/export

git switch -c release/1.4 main          # Release just in time schneiden
git tag v1.4.0

git switch main                         # Bug: Fix zuerst auf main
git commit -m "fix: export rounding"
git switch release/1.4
git cherry-pick -x e3a8756
git tag v1.4.1
git log --oneline --graph --all --decorate
Deleted branch feat/export (was f2e54ea).
[release/1.4 e3fd423] fix: export rounding
* e3a8756 (main) fix: export rounding
| * e3fd423 (HEAD -> release/1.4, tag: v1.4.1) fix: export rounding
|/
* f2e54ea (tag: v1.4.0) feat: export behind flag
* a21acb8 base

Echte Ausgabe, git 2.56.0.windows.3 (lokales Scratch-Repo ohne Remote; Push und PR entfallen).

  1. Der Feature-Branch lebt nur Stunden. Das Feature ist gemergt, aber per Flag aus.
  2. Der Release-Branch wird erst kurz vor dem Release geschnitten. Niemand entwickelt darauf.
  3. Der Fix entsteht auf main und kommt per cherry-pick -x auf release/1.4. So fehlt er im nächsten Release nicht.

4. Details, die Interviewer fragen

  1. Trunk-Based Development: Alle arbeiten auf einem Branch, dem Trunk. Lange Entwicklungs-Branches gibt es nicht. Kurze Feature-Branches sind für Review und CI erlaubt.
  2. Wie kurz ist kurz? trunkbaseddevelopment.com nennt höchstens zwei Tage. Länger wird es ein langlebiger Feature-Branch.
  3. Release-Branches im Trunk-Modell: Sie werden „just in time“ geschnitten. Entwickler committen dort nicht. Fixes gehen zuerst auf den Trunk und werden dann gepickt.
  4. Fix forward: Teams, die direkt vom Trunk releasen, brauchen oft keinen Release-Branch. Sie fixen auf dem Trunk und releasen neu.
  5. Feature Flags: Ein Feature Flag trennt Deploy von Release. Code ist in Produktion, aber das Feature ist aus. Arten: Release-Flag (kurzlebig), Experiment-Flag, Ops-Flag (Kill Switch), Permission-Flag.
  6. Branch by Abstraction: Für grosse Umbauten baut man eine Abstraktion ein. Alte und neue Implementierung leben nebeneinander. Umschalten per Flag, alte Version später löschen.
  7. GitFlow: zwei dauerhafte Branches, master und develop. Dazu feature/*, release/*, hotfix/*. Merges mit --no-ff, damit Features sichtbar bleiben.
  8. Die Notiz des GitFlow-Autors (2020): Für Continuous Delivery empfiehlt er einen einfacheren Workflow. GitFlow passt für explizit versionierte Software mit mehreren Versionen im Feld.
  9. GitHub Flow: sechs Schritte: Branch, Änderungen, Pull Request, Review, Merge, Branch löschen. Es gibt keinen develop- und keinen Release-Branch.
  10. Umgebungs-Branches (dev, test, prod) sind ein Anti-Pattern für Code. Sie divergieren. Besser: ein Artefakt, Promotion über Pipeline oder Konfig-Repo.
  11. Versionierung: Tags markieren Releases, z. B. v1.4.1 nach SemVer (MAJOR.MINOR.PATCH).

5. Vergleich

  • Trunk-Based: häufigste Integration, beste Basis für CI/CD. Braucht gute Tests, Feature Flags und Disziplin.
  • GitHub Flow: sehr einfach, ein dauerhafter Branch. Passt für Web-Apps mit kontinuierlichem Deployment. Wenig Hilfe für mehrere parallele Versionen.
  • GitFlow: klare Rollen, gut für versionierte Produkte mit Wartung alter Versionen. Nachteil: lange Branches, viele Merges, langsames Feedback.
  • Release-Branches (in jedem Modell): nötig, wenn mehrere Versionen parallel gepflegt werden. Fixes immer vom Trunk picken.

6. In der Produktion

  1. Merge-Hölle vor dem Release: Feature-Branches leben Wochen. Lösung: kurze Branches, tägliche Integration, Feature Flags.
  2. Hotfix fehlt im nächsten Release: Fix nur auf dem Release-Branch gemacht. Lösung: Regel „main zuerst, dann cherry-pick“.
  3. Flag-Friedhof: Hunderte alte Flags, niemand weiss, was aus ist. Lösung: Ablaufdatum pro Release-Flag, Aufräum-Ticket bei Einführung.
  4. Kaputter Trunk blockiert alle: Ein roter Build auf main. Lösung: PR-Build Pflicht, roten Commit sofort reverten.
  5. Umgebungs-Branches divergieren: prod-Branch hat Commits, die main nicht hat. Lösung: ein Artefakt, Konfiguration pro Umgebung in Dateien.

7. Diagnose: Werkzeuge und Befehle

  • git for-each-ref --sort=committerdate refs/remotes --format='%(committerdate:short) %(refname:short)': alte, vergessene Branches.
  • git log main..release/1.4 --oneline: was nur auf dem Release-Branch ist (sollte nur Cherry-Picks sein).
  • git cherry -v main release/1.4: welche Release-Commits auf main fehlen.
  • DORA-Metriken: Deployment-Frequenz, Lead Time, Change Failure Rate, Time to Restore. Lange Branches verschlechtern Lead Time.
  • Branch Policies in Azure DevOps bzw. Rulesets in GitHub: prüfen, ob Regeln wirklich erzwungen sind.

8. Senior-Punkte

  1. Das Release-Modell entscheidet, nicht der Geschmack. Kontinuierlich → Trunk-Based oder GitHub Flow. Mehrere Versionen im Feld → Release-Branches.
  2. Integration ist das Ziel. Konflikte und Risiko wachsen mit der Lebensdauer eines Branches.
  3. Feature Flags kosten. Mehr Code-Pfade, mehr Tests, technische Schulden. Sie brauchen Besitzer und Ablaufdatum.
  4. Deploy und Release trennen. Deploy ist technisch, Release ist eine Business-Entscheidung per Flag.
  5. GitFlow nicht aus Gewohnheit. Selbst der Autor rät bei Continuous Delivery davon ab.
  6. Regeln erzwingen: Branch Policies, Pflicht-Build, Pflicht-Review. Eine Wiki-Seite allein reicht nicht.

10. Fallen

  • „Trunk-Based heisst: keine Branches.“ → Falsch. Kurze Feature-Branches für Review und CI sind erlaubt, Release-Branches auch.
  • „GitFlow ist der Standard.“ → Falsch. Es ist ein Modell für versionierte Releases. Der Autor selbst empfiehlt für Continuous Delivery etwas Einfacheres.
  • „Feature Flags sind gratis.“ → Falsch. Jedes Flag verdoppelt Code-Pfade und muss wieder weg.
  • „Fix auf dem Release-Branch, später nach main.“ → Riskant. Wird vergessen. Main zuerst.
  • „Ein Branch pro Umgebung ist sauber.“ → Falsch. Die Branches divergieren; man testet nicht, was man ausliefert.

11. Fragen

Was ist Trunk-Based Development?

Alle integrieren in einen Branch, den Trunk. Keine langlebigen Entwicklungs-Branches; kurze Feature-Branches nur für Review und CI.

Was ist GitFlow?

Ein Modell mit master und develop als Dauer-Branches plus feature-, release- und hotfix-Branches. Releases werden auf master getaggt.

Was ist GitHub Flow?

Branch erstellen, ändern, Pull Request, Review, in main mergen, Branch löschen. main ist immer deploybar.

Wann passt GitFlow?

Bei explizit versionierter Software, die mehrere Versionen parallel pflegt, z. B. installierte Produkte oder Bibliotheken.

Wann passt Trunk-Based?

Bei Continuous Integration und Delivery, besonders bei Services, die oft deployen. Voraussetzung: gute automatische Tests.

Wie lange darf ein Feature-Branch leben?

Im Trunk-Modell höchstens etwa zwei Tage. Danach wird er ein langlebiger Branch mit Merge-Risiko.

Was sind Feature Flags?

Schalter im Code, die ein Feature zur Laufzeit an- oder ausschalten. Sie trennen Deploy von Release.

Welche Arten von Feature Flags gibt es?

Release-Flags (kurzlebig), Experiment-Flags (A/B), Ops-Flags (Kill Switch) und Permission-Flags (für bestimmte Nutzer).

Welche Nachteile haben Feature Flags?

Mehr Code-Pfade, mehr Testfälle, vergessene Flags als technische Schuld. Sie brauchen Besitzer und Ablaufdatum.

Was ist Branch by Abstraction?

Eine Abstraktion erlaubt, alte und neue Implementierung im Trunk nebeneinander zu haben. Man schaltet um und löscht dann die alte.

Wie kommt ein Hotfix in einen Release-Branch?

Fix zuerst auf main mit Test, dann per cherry-pick -x in den Release-Branch. So fehlt er im nächsten Release nicht.

Wie läuft ein Hotfix in GitFlow?

hotfix-Branch von master, Fix, dann Merge in master (mit Tag) und develop. Läuft ein Release-Branch, geht er dorthin statt in develop.

Warum sind Umgebungs-Branches schlecht?

Sie divergieren, und man testet nicht das Artefakt, das live geht. Besser: ein Artefakt und Promotion.

Warum nutzt GitFlow --no-ff?

So bleibt ein Merge-Commit pro Feature. Man sieht die Gruppe und kann sie als Ganzes reverten.

Was ist der Unterschied zwischen Deploy und Release?

Deploy bringt Code in eine Umgebung. Release macht ein Feature für Nutzer sichtbar, oft per Flag.

Welche Metriken zeigen, ob die Strategie funktioniert?

DORA: Deployment-Frequenz, Lead Time for Changes, Change Failure Rate, Time to Restore.

Wie setzen Sie eine Branching-Regel technisch durch?

Branch Policies oder Rulesets: Pflicht-PR, Pflicht-Build, Reviewer, kein Force Push, erlaubte Merge-Typen.

Szenario: Das Team nutzt GitFlow, Releases dauern Wochen und jeder Merge in develop ist schmerzhaft. Was schlagen Sie vor?

Schrittweise zu Trunk-Based: kurze Branches, PR-Builds, Feature Flags für Unfertiges. Release-Branches nur, wenn wirklich mehrere Versionen gepflegt werden.

Szenario: Ein grosses Feature dauert drei Monate. Wie bleiben Sie Trunk-Based?

In kleine Schritte zerlegen, täglich mergen, hinter einem Feature Flag verstecken. Für Umbauten Branch by Abstraction.

Szenario: Kunden nutzen Version 2.x und 3.x. Ein Sicherheits-Bug betrifft beide. Wie gehen Sie vor?

Fix auf main mit Test. Dann cherry-pick -x auf release/2.x und release/3.x, je eigene CI und Patch-Tag. Mit git cherry prüfen, dass er überall ist.
