Versionierung und Artefakte

Kern: Eine Version benennt einen unveränderlichen Stand der Software. Semantic Versioning codiert in MAJOR.MINOR.PATCH, wie stark sich die API ändert. Ein Artefakt wird einmal gebaut, in einem Feed oder einer Registry abgelegt und dann unverändert durch alle Stages befördert.

Antwort-Muster

Frage: Wie versionierst du Software, und wie verwaltest du Build-Artefakte?

  1. Mechanismus: Die CI berechnet aus dem Git-Stand eine Version, baut einmal und legt das Artefakt unter dieser Version ab. Alle Stages deployen dasselbe Artefakt.
  2. Zahl: SemVer hat drei Zahlen X.Y.Z. Ein Pre-release wie 1.0.0-rc.1 ist kleiner als 1.0.0. Gelöschte Pakete bleiben in Azure Artifacts 30 Tage im Recycle Bin.
  3. Trade-off: Automatische Versionen aus Commits sparen Arbeit, brauchen aber disziplinierte Commit-Nachrichten. Ein Tag wie latest ist bequem, aber veränderlich.
  4. Produktion: Ich deploye per Digest oder eindeutigem Tag, nie per latest. Retention-Regeln halten den Feed klein.

1. Der Weg eines Artefakts durch die Pipeline

  1. Quelle: Ein Commit oder ein Git-Tag wie v1.4.0 ist der Ausgangspunkt. git describe liefert daraus einen Namen.
  2. Version berechnen: Die CI nimmt den letzten Tag und zählt hoch. Oft hilft Conventional Commits. fix gibt PATCH, feat gibt MINOR, ein Breaking Change gibt MAJOR.
  3. Einmal bauen: Es gibt genau einen Build pro Version. Tests laufen gegen genau dieses Artefakt.
  4. Ablegen: Das Artefakt geht in einen Feed (NuGet, npm, Maven, Python) oder eine Container Registry. Die Version darf danach nicht mehr geändert werden.
  5. Befördern: Bestehen die Tests, bekommt dieselbe Version einen höheren Status. In Azure Artifacts ist das der View @prerelease und dann @release.
  6. Deployen: Jede Stage zieht dieselbe Version. Es gibt keinen Neu-Build für Prod.

2. Aufbau

  1. Git-Tag markiert einen Commit als Release. Er ist die Quelle der Wahrheit für die Version.
  2. Feed ist das Paket-Lager, etwa Azure Artifacts. Pakete haben Name und Version.
  3. Registry speichert Container Images. Ein Image hat Tags und eine Digest.
  4. Views in Azure Artifacts zeigen nur Pakete einer Qualitätsstufe. Die Standard-Views sind @local, @prerelease und @release.
  5. Upstream Source verbindet den Feed mit öffentlichen Registries. Geladene Pakete werden im Feed gespeichert.
  6. Retention löscht alte Versionen automatisch. Gelöschte Pakete liegen 30 Tage im Recycle Bin.

3. Details

  1. SemVer-Format: Eine Version ist X.Y.Z mit nicht-negativen Ganzzahlen ohne führende Nullen. Jede Zahl steigt numerisch. 1.9.0 ist kleiner als 1.10.0.
  2. Regeln für die Zahlen: PATCH steigt bei kompatiblen Fehlerkorrekturen. MINOR steigt bei neuer, kompatibler Funktion und bei Deprecation. MAJOR steigt bei inkompatiblen Änderungen. Bei MINOR wird PATCH auf 0 gesetzt, bei MAJOR werden MINOR und PATCH auf 0 gesetzt.
  3. Version 0.y.z: Sie steht für die erste Entwicklung. Alles darf sich jederzeit ändern. Erst 1.0.0 legt die öffentliche API fest.
  4. Unveränderlich: Eine veröffentlichte Version darf nicht mehr geändert werden. Jede Änderung braucht eine neue Version.
  5. Pre-release: Ein Bindestrich und Bezeichner wie 1.0.0-rc.1 markieren eine instabile Version. Sie hat kleinere Präzedenz als 1.0.0. Bezeichner vergleicht man Stück für Stück, Zahlen numerisch.
  6. Build-Metadaten: Nach einem Plus wie 1.0.0+build5 stehen Build-Daten. Sie zählen beim Vergleich nicht. Zwei Versionen, die sich nur dort unterscheiden, sind gleich.
  7. Conventional Commits: Die Nachricht fix: entspricht PATCH, feat: entspricht MINOR. Ein ! oder ein Footer BREAKING CHANGE: entspricht MAJOR. So kann ein Tool die Version berechnen.
  8. git describe: Der Befehl nennt den letzten Tag, die Zahl der Commits danach und den Kurz-Hash, etwa v1.4.0-2-g3a0ec19. Auf dem Tag selbst zeigt er nur den Tag.
  9. Container-Tags sind veränderlich: Ein Tag zeigt auf ein Image. Man kann dasselbe Tag neu pushen. Eine Digest ist der SHA-256-Hash des Manifests und ändert sich nie. Wer per Digest zieht, bekommt garantiert dieselbe Version.
  10. Tag-Strategie: Stabile Tags wie 1.4 eignen sich für Basis-Images. Für Deployments nimmt man eindeutige Tags, etwa mit Commit-SHA. Die Registry kann Images sperren, zum Beispiel mit --write-enabled false.
  11. Views und Promotion: In Azure Artifacts publiziert man nur in den Feed (@local). Danach befördert man die Version in @prerelease oder @release. So sehen Konsumenten nur geprüfte Stände.
  12. Upstream Sources: Ein Paket, das du aus einer öffentlichen Registry installierst, wird im Feed gespeichert. Es bleibt verfügbar, auch wenn die Quelle ausfällt. Für deterministische Restores nutzt du in der Konfiguration nur einen Feed mit Upstreams.

4. Fallen

  • „Eine Version kann man später korrigieren.“ → Falsch. Veröffentlichte Versionen sind unveränderlich. Jede Korrektur ist eine neue Version.
  • „1.10.0 ist kleiner als 1.9.0.“ → Falsch. Zahlen werden numerisch verglichen. 1.10.0 ist grösser. Als Text sortiert wäre es falsch.
  • „Ein Tag wie latest garantiert die neueste, stabile Version.“ → Falsch. Es ist nur ein veränderlicher Verweis. Zwei Hosts können verschiedene Images haben.
  • „Build-Metadaten (+) ändern die Reihenfolge.“ → Falsch. Sie werden beim Vergleich ignoriert.
  • „Für Prod bauen wir neu, damit es frisch ist.“ → Falsch. Ein Neu-Build ist ein anderes Artefakt. Man befördert das getestete.
  • „Ein gelöschtes Paket ist sofort weg.“ → Falsch. In Azure Artifacts liegt es 30 Tage im Recycle Bin und lässt sich wiederherstellen.

5. Selbsttest

Warum?

Warum SemVer?

Die Version sagt dem Nutzer, ob ein Update kompatibel ist. MAJOR heisst, es kann brechen. Tools wie Dependency-Bots nutzen das.

Warum nur einmal bauen?

Ein zweiter Build kann anders ausfallen, etwa durch neue Abhängigkeiten. Getestet wurde nur das erste Artefakt. Darum befördert man es.

Warum nie latest in Produktion?

Latest ändert sich, ohne dass man es merkt. Ein Rollback ist unklar, und Hosts können verschiedene Stände haben.

Wie innen?

Wie vergleicht SemVer zwei Versionen?

Major, Minor und Patch numerisch von links nach rechts. Bei Gleichheit hat ein Pre-release kleinere Präzedenz. Build-Metadaten zählen nicht.

Wie vergleicht man 1.0.0-beta.2 und 1.0.0-beta.11?

Die Bezeichner werden einzeln verglichen. Zahlen vergleicht man numerisch, also ist beta.2 kleiner als beta.11.

Was liefert git describe?

Den letzten erreichbaren Tag, die Anzahl der Commits seither und den Kurz-Hash. Auf einem getaggten Commit nur den Tag.

Was ist der Unterschied zwischen Tag und Digest bei Images?

Ein Tag ist ein veränderlicher Name. Die Digest ist der SHA-256 des Manifests und identifiziert den Inhalt eindeutig.

Wie arbeiten Upstream Sources in Azure Artifacts?

Der Feed sucht zuerst direkt publizierte Pakete, dann gespeicherte Upstream-Pakete, dann die Upstreams in ihrer Reihenfolge. Geladene Pakete werden gespeichert.

Zahlen

Wie lange liegen gelöschte Pakete im Recycle Bin?

30 Tage. Danach löscht Azure Artifacts sie endgültig.

Welche Views gibt es standardmässig?

@local, @prerelease und @release. Die letzten zwei sind Vorschläge und lassen sich umbenennen oder löschen.

Ab welcher Version ist die API stabil?

Ab 1.0.0. Vor 1.0.0 (0.y.z) darf sich alles ändern.

Wie viele Zahlen hat eine normale SemVer-Version?

Drei, nämlich MAJOR, MINOR und PATCH.

Vergleich

SemVer vs CalVer?

SemVer sagt etwas über Kompatibilität. CalVer (Jahr.Monat) sagt, wie alt ein Stand ist. CalVer passt zu Anwendungen ohne öffentliche API.

Pipeline Artifact vs Paket im Feed?

Ein Pipeline Artifact gibt Dateien innerhalb einer Pipeline weiter. Ein Paket im Feed ist versioniert und für viele Konsumenten gedacht.

Tag vs Digest?

Tag ist lesbar und veränderlich. Digest ist unveränderlich, aber unhandlich. Beides zusammen ist gut.

Manuelle vs automatische Versionen?

Manuell ist einfach und fehleranfällig. Automatisch aus Commits ist konsistent, braucht aber gute Commit-Regeln.

Produktion

Wie macht man ein Image unveränderlich?

Per Digest deployen, eindeutige Tags nutzen und das Image in der Registry sperren, etwa mit --write-enabled false.

Wie hält man den Feed klein?

Mit Retention-Regeln für alte Versionen. Releases behält man, Pre-releases löscht man schneller.

Wie verhindert man Dependency Confusion?

Mit einem einzigen Feed mit Upstreams. Er sucht in fester Reihenfolge, und eigene Pakete haben Vorrang vor Upstream-Paketen.

Szenario: Prod läuft mit anderem Code als Test, obwohl dasselbe Tag deployt wurde. Was ist passiert?

Das Tag wurde neu gepusht und zeigt nun auf ein anderes Image. Lösung ist ein eindeutiges Tag oder Deploy per Digest.

Szenario: Ein Release hat einen Bug, und jemand will die Version überschreiben. Wie reagieren Sie?

Nein, die Version bleibt unveränderlich. Man gibt Version 1.4.1 mit dem Fix heraus. Eine fehlerhafte Version kann man als deprecated markieren.

Design

Wie wählt man die Version in der CI?

Aus dem letzten Git-Tag plus Commits, oder aus Conventional Commits. Die Build-Nummer bleibt als Build-Metadaten oder Pre-release.

Wann ist ein Breaking Change MAJOR?

Wenn Konsumenten ihren Code anpassen müssen. Dazu zählt das Entfernen oder Umbenennen von API-Teilen.

Wie versioniert man interne Bibliotheken?

Mit SemVer und einem Feed pro Team oder Firma. Abhängige Teams sehen im View nur freigegebene Versionen.

Szenario: Mehrere Teams konsumieren Ihre Bibliothek. Wie gestalten Sie Releases?

SemVer strikt einhalten, Pre-release im View @prerelease zum Testen, Release im @release. Deprecations in MINOR ankündigen, Brüche nur in MAJOR.

Mehr

Gerüst

  • Warum? Reproduzierbare, nachvollziehbare Releases. Jeder weiss, was läuft.
  • Wie innen? Git-Tag, Version berechnen, einmal bauen, im Feed ablegen, befördern, deployen.
  • Zahlen X.Y.Z. Pre-release kleiner als Release. Recycle Bin 30 Tage. Drei Standard-Views.
  • Vergleich SemVer und CalVer. Tag und Digest. Pipeline Artifact und Paket.
  • Produktion Digest statt latest. Retention. Ein Feed mit Upstreams.
  • Design Version aus Git oder Commits, Promotion über Views, Breaking nur in MAJOR.

Beispiel: git describe und SemVer-Reihenfolge

# Repo mit Tag v1.4.0 und zwei Commits danach
git describe --tags
git checkout v1.4.0 && git describe --tags

# Reihenfolge nach SemVer (eigener Vergleich) und als Text
vs = ["1.0.0","1.0.0-rc.1","1.0.0-beta.11","1.0.0-beta.2",
      "1.0.0-alpha","1.9.0","1.10.0","1.0.0+build5"]
print(sorted(vs, key=semver_key))
print(sorted(vs))
v1.4.0-2-g3a0ec19
v1.4.0
['1.0.0-alpha', '1.0.0-beta.2', '1.0.0-beta.11', '1.0.0-rc.1', '1.0.0', '1.0.0+build5', '1.9.0', '1.10.0']
['1.0.0', '1.0.0+build5', '1.0.0-alpha', '1.0.0-beta.11', '1.0.0-beta.2', '1.0.0-rc.1', '1.10.0', '1.9.0']

Echte Ausgabe, git 2.56.0 und Python 3.12.10. semver_key ist mein eigener kleiner Vergleich nach den SemVer-Regeln, kein Bibliotheksaufruf.

  1. v1.4.0-2-g3a0ec19 heisst: zwei Commits nach dem Tag, Kurz-Hash 3a0ec19. Auf dem Tag steht nur v1.4.0.
  2. Bei SemVer ist beta.2 kleiner als beta.11 und jedes Pre-release kleiner als 1.0.0.
  3. 1.0.0+build5 steht direkt hinter 1.0.0. Die Build-Metadaten zählen nicht, beide sind gleich.
  4. Als Text sortiert stehen 1.10.0 vor 1.9.0. Das ist die typische Falle.

Vergleich

  • SemVer: MAJOR.MINOR.PATCH. Sagt etwas über Kompatibilität.
  • CalVer: Kalender als Version. Sagt etwas über das Alter. Gut für Apps und Betriebssysteme.
  • Build-Nummer: Zählt Läufe der CI. Eindeutig, aber ohne Aussage zur Kompatibilität.
  • Commit-SHA: Genau und eindeutig. Gut als Zusatz im Tag.
  • Azure Artifacts: Feed für NuGet, npm, Maven, Python, Cargo und Universal Packages.
  • Container Registry: Für Images. Tags, Digests und Sperren.

Produktion

  1. Falsches Image läuft: Ein mutierbares Tag wurde neu gepusht. Lösung: eindeutige Tags oder Digest.
  2. Feed wächst ohne Grenze: Jeder Build legt eine Version ab. Lösung: Retention-Regeln und Pre-release-Bereinigung.
  3. Orphans in der Registry: Neu gepushte Tags hinterlassen untagged Images, die Platz brauchen. Lösung: aufräumen und Retention.
  4. Build nicht reproduzierbar: Abhängigkeiten ändern sich zwischen Builds. Lösung: Lockfiles und ein Feed mit Upstreams.
  5. Breaking Change in MINOR: Konsumenten brechen nach einem Update. Lösung: Review der API-Änderungen, strikte SemVer-Regeln.
  6. Gelöschtes Paket wird gebraucht: Ein Build findet es nicht mehr. Lösung: Recycle Bin, Wiederherstellung innerhalb von 30 Tagen.

Diagnose: Werkzeuge und Befehle

  • git describe --tags: Zeigt den Stand relativ zum letzten Tag.
  • git tag --list und git log --oneline: Welche Tags gibt es, was liegt dazwischen.
  • Azure Artifacts → Feed → Package: Zeigt Versionen, Views, Quelle (Upstream oder lokal).
  • Azure Artifacts → Recycle Bin: Gelöschte Pakete ansehen und wiederherstellen.
  • Registry (Portal oder Azure CLI): Zeigt Manifest-Digests und auf welches Image ein Tag zeigt.
  • Pipeline-Lauf: Zeigt die Build-Nummer und das veröffentlichte Artefakt pro Run.

Senior-Punkte

  1. Ein Artefakt, viele Stages. Wer neu baut, deployt ungetestete Software.
  2. Versionen sind ein Vertrag. Ein Verstoss gegen SemVer kostet das Vertrauen der Konsumenten.
  3. Tags sind Zeiger, Digests sind Inhalt. Deploye per Digest oder eindeutigem Tag.
  4. Automatisiere die Version, aber nur mit klaren Commit-Regeln. Sonst entstehen falsche Sprünge.
  5. Promotion statt Kopie. Der Status ändert sich, das Artefakt bleibt gleich.
  6. Räume auf. Retention ist Teil des Designs, nicht eine Nacharbeit.
