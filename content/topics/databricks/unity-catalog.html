Unity Catalog und Workspaces

Kern: Unity Catalog ist die zentrale Governance-Schicht von Databricks für Daten und KI-Objekte. Alle Objekte heissen catalog.schema.objekt, und Rechte werden mit GRANT vergeben und vererbt. Ein Workspace ist eine Databricks-Umgebung, die an einen Metastore seiner Region gehängt wird.

Antwort-Muster

Frage: Wie ist Unity Catalog aufgebaut, und wie kommt ein Benutzer an eine Tabelle?

  1. Mechanismus: Metastore, Catalog, Schema, Objekt. Der Zugriff braucht USE CATALOG, USE SCHEMA und SELECT.
  2. Zahl: Pro Region gibt es einen Metastore. Er kann an viele Workspaces der Region gehängt werden.
  3. Trade-off: Ein Catalog pro Umgebung oder Team isoliert gut, kostet aber mehr Verwaltung. Managed Tables vereinfachen, External Tables behalten den Speicher bei dir.
  4. Produktion: Ich vergebe Rechte an Gruppen, lasse Jobs unter Service Principals laufen und gebe niemandem direkten Zugriff auf den Speicher.

1. Ein SELECT auf eine Tabelle in 7 Schritten

  1. Abfrage: Ein Benutzer startet SELECT * FROM main.sales.orders in einem Notebook oder SQL Warehouse.
  2. Workspace: Der Workspace ist an einen Metastore seiner Region gehängt. Nur dort sieht er die Objekte.
  3. Namen lösen: Der Name hat drei Teile. Catalog main, Schema sales, Tabelle orders.
  4. Rechte prüfen: Es braucht USE CATALOG auf dem Catalog, USE SCHEMA auf dem Schema und SELECT auf der Tabelle. SELECT kann vom Schema oder Catalog geerbt sein.
  5. Filter: Row Filter und Column Masks schränken Zeilen und Spalten ein, falls definiert.
  6. Speicher: Eine Managed Table liegt im verwalteten Speicher. Eine External Table liegt an einem Pfad, den eine External Location mit Storage Credential abdeckt.
  7. Audit: Unity Catalog protokolliert den Zugriff und erfasst die Lineage.

2. Aufbau

  1. Der Metastore ist die oberste Ebene. Er hält die Metadaten und die Rechte.
  2. Ein Catalog ist die Hauptebene für Isolation, zum Beispiel pro Umgebung oder Team.
  3. Ein Schema gruppiert Tabellen, Views, Volumes, Functions und Models.
  4. Storage Credential, External Location, Connections und Shares liegen direkt unter dem Metastore.
  5. Ein Workspace ist eine Databricks-Umgebung in einem Cloud-Konto. Er wird an einen Metastore gehängt.
  6. Alle Objekte sind Securable Objects, auf die man Rechte vergeben kann.

3. Details

  1. Governance-Schicht: Unity Catalog setzt Zugriffsrechte durch, erfasst Lineage und protokolliert Zugriffe für das Audit. Es gilt für alle Daten- und KI-Zugriffe im Workspace, sobald es aktiv ist.
  2. Dreistufiger Name: Tabellen, Views, Volumes, Functions und Models folgen dem Muster catalog.schema.objekt.
  3. Ein Metastore pro Region: Eine Organisation braucht einen Metastore für jede Region, in der sie arbeitet. Er kann an beliebig viele Workspaces dieser Region hängen. Die Region des Metastore muss zu den Workspaces passen.
  4. Metastore-Admin: Wer den Metastore anlegt, wird sein Besitzer. Man legt ihn im Account Console an und braucht dafür die Rolle Account Admin. Databricks empfiehlt, die Rolle an eine Gruppe zu übergeben.
  5. Rechte zum Lesen: Für eine Tabelle braucht man SELECT, dazu USE CATALOG auf dem Catalog und USE SCHEMA auf dem Schema. Ohne USE CATALOG reicht ein SELECT auf der Tabelle nicht. MODIFY erlaubt Einfügen, Ändern und Löschen und braucht dieselben Rechte darüber.
  6. Vererbung: Ein SELECT auf einem Schema gilt für alle jetzigen und künftigen Tabellen und Views darin. Auf einem Catalog gilt es für alles darunter. Das Gleiche gilt für MODIFY und Volume-Rechte.
  7. ALL PRIVILEGES und MANAGE: ALL PRIVILEGES umfasst alle Fähigkeiten, aber nicht MANAGE. MANAGE erlaubt Rechte verwalten, Besitzer übertragen, umbenennen und löschen. Es gibt nicht automatisch alle anderen Rechte.
  8. BROWSE: Es erlaubt, Objekte zu finden und ihre Metadaten zu sehen, ohne Zugriff auf die Daten. Es braucht kein USE CATALOG. Man vergibt es auf Catalog-Ebene.
  9. Managed und External: Bei Managed Tables und Volumes verwaltet Unity Catalog Governance und den Lebenszyklus der Dateien. Bei External Objekten verwaltet es nur die Governance. Die Daten bleiben in deinem Speicher.
  10. Storage Credential und External Location: Eine Storage Credential ist der Zugang zum Cloud-Speicher, zum Beispiel eine IAM-Rolle bei S3. Eine External Location verbindet einen Pfad mit einer Credential. Mehrere Locations können dieselbe Credential nutzen.
  11. Managed Storage: Er kann auf Metastore-, Catalog- oder Schema-Ebene gesetzt werden. Auf Metastore-Ebene ist er optional. Databricks rät zu Catalog-Ebene.
  12. Volumes: Volumes sind der Weg für nicht tabellarische Dateien. Man greift mit /Volumes-Pfaden zu. Tabellen soll man per Name statt per Pfad nutzen.
  13. Workspace: Ein Workspace ist eine Databricks-Umgebung in einem Cloud-Konto. Man legt ihn im Account Console, per Account API oder mit Terraform an. Serverless Workspaces kommen mit Serverless-Compute und Standardspeicher. Classic Workspaces nutzen Speicher und Compute im eigenen Konto.
  14. Workspace-Binding: Ein Catalog kann an bestimmte Workspaces gebunden werden. Das ist sinnvoll, wenn Arbeitsumgebung und Daten gleich isoliert sein sollen.
  15. Aktivierung: Unity Catalog ist für Workspaces, die nach dem 8. November 2023 angelegt wurden, automatisch aktiv. Ältere Workspaces muss man upgraden.

4. Fallen

  • „SELECT auf der Tabelle reicht zum Lesen.“ → Falsch. Es braucht auch USE CATALOG und USE SCHEMA.
  • „ALL PRIVILEGES enthält alles, auch MANAGE.“ → Falsch. MANAGE ist ausgenommen. Es steht für das Verwalten von Rechten, Besitz, Umbenennen und Löschen.
  • „BROWSE gibt Lesezugriff auf die Daten.“ → Falsch. Es zeigt nur Metadaten. Die Daten bleiben gesperrt.
  • „Ein Metastore gilt für die ganze Organisation weltweit.“ → Falsch. Es gibt einen Metastore pro Region, und er passt zu den Workspaces dieser Region.
  • „Mit External Tables verwaltet Unity Catalog auch die Dateien.“ → Falsch. Bei External Objekten verwaltet es nur die Governance.
  • „Direkter Zugriff auf den Bucket ist ein harmloser Ersatz.“ → Falsch. Er umgeht Governance und Audit von Unity Catalog.

5. Selbsttest

Warum?

Warum eine zentrale Governance-Schicht?

Rechte, Lineage und Audit gelten dann für alle Workspaces gleich, statt pro Workspace.

Warum Rechte an Gruppen vergeben?

Gruppen aus dem Identity Provider halten die Pflege klein. Einzelne Personen kommen und gehen.

Warum Catalogs als Isolationseinheit?

Ein Catalog trennt Umgebungen, Teams oder Geschäftsbereiche und lässt sich an Workspaces binden.

Wie innen?

Welche Ebenen hat das Objektmodell?

Metastore, Catalog, Schema und Objekte wie Tabelle, View, Volume, Function, Model.

Was braucht man, um eine Tabelle zu lesen?

SELECT auf der Tabelle, USE CATALOG und USE SCHEMA darüber.

Wie funktioniert Vererbung?

Ein Recht auf einem Schema oder Catalog gilt für alle Objekte darunter, auch künftige.

Was ist eine External Location?

Ein Speicherpfad mit einer Storage Credential, die den Zugriff erlaubt.

Was ist der Unterschied zwischen Managed und External Table?

Managed: Unity Catalog verwaltet Daten und Governance. External: nur die Governance, die Daten bleiben bei dir.

Wie wird ein Workspace mit Unity Catalog verbunden?

Man hängt ihn im Account Console an den Metastore seiner Region.

Zahlen

Wie viele Metastores braucht man?

Einen pro Region, in der man arbeitet.

Ab wann ist Unity Catalog automatisch aktiv?

Für Workspaces, die nach dem 8. November 2023 angelegt wurden.

Wie viele Namensteile hat ein Objekt?

Drei: catalog.schema.objekt.

Vergleich

Managed vs External Table?

Managed liegt im verwalteten Speicher. External liegt an einem Pfad mit External Location.

Volume vs Tabelle?

Eine Tabelle ist tabellarisch. Ein Volume ist für Dateien und wird mit /Volumes-Pfad genutzt.

MANAGE vs Besitzer?

Ähnlich, aber mit Unterschieden. MANAGE gibt nicht automatisch alle Rechte.

Workspace vs Metastore?

Der Workspace ist die Arbeitsumgebung. Der Metastore hält Metadaten und Rechte und gilt für viele Workspaces einer Region.

Produktion

Was tun, wenn jemand eine Tabelle nicht sieht?

Rechte prüfen. Es braucht USE CATALOG, USE SCHEMA und SELECT. Danach Workspace-Binding prüfen.

Wie schützt man Produktionstabellen?

Besitz an Gruppen, MODIFY nur für Service Principals, Jobs unter Service Principals.

Szenario: Ein Team braucht Zugriff auf Daten in einem zweiten Workspace. Was tun Sie?

Ich prüfe, ob beide am selben Metastore hängen und ob der Catalog an den Workspace gebunden ist. Dann vergebe ich Rechte an die Gruppe.

Szenario: Ein Team will die Daten direkt aus dem Bucket lesen. Was sagen Sie?

Nein. Direkter Zugriff umgeht Governance und Audit. Ich gebe Rechte über Unity Catalog, bei Dateien über ein Volume.

Szenario: Ein Analyst soll Tabellen finden, aber nicht lesen. Wie lösen Sie das?

Mit BROWSE auf dem Catalog. Er sieht Metadaten, aber keine Daten.

Design

Wie strukturiert man Catalogs?

Pro Umgebung, Team oder Geschäftsbereich. Für Isolation kann man Catalogs an Workspaces binden.

Wo legt man Managed Storage an?

Bevorzugt auf Catalog-Ebene. Auf Metastore-Ebene nur mit eigenem Bucket.

Wann External Tables?

Wenn Daten ausserhalb von Databricks verwaltet werden und dort bleiben sollen.

Wie läuft ein Produktionsjob?

Unter einem Service Principal, nicht unter einer Person.

Wie viele Metastores bei Mehrregion-Betrieb?

Einer pro Region. Für Austausch zwischen Regionen empfiehlt Databricks Databricks-to-Databricks Sharing.

Mehr

Gerüst

  • Warum? Eine Stelle für Rechte, Lineage und Audit über alle Workspaces.
  • Wie innen? Metastore → Catalog → Schema → Objekt. Rechte vererben sich nach unten.
  • Zahlen Ein Metastore pro Region. Drei Namensteile. Seit 8. November 2023 automatisch in neuen Workspaces.
  • Vergleich Managed gegen External. Tabelle gegen Volume. Workspace gegen Metastore.
  • Produktion Fehlendes USE CATALOG, direkter Bucket-Zugriff, Jobs unter Personen.
  • Design Gruppen, Service Principals, Catalog-Isolation, Volumes.

Beispiel: Rechte und Namen in Unity Catalog

-- Gruppe "analysten" darf Tabellen in main.sales lesen
GRANT USE CATALOG ON CATALOG main TO `analysten`;
GRANT USE SCHEMA  ON SCHEMA  main.sales TO `analysten`;
GRANT SELECT      ON SCHEMA  main.sales TO `analysten`;   -- gilt für alle jetzigen und künftigen Tabellen

-- Schreibrecht nur für einen Service Principal
GRANT MODIFY ON TABLE main.sales.orders TO `etl-job`;

-- Nur entdecken, nicht lesen
GRANT BROWSE ON CATALOG main TO `alle-mitarbeitende`;

-- Dreistufiger Name
SELECT * FROM main.sales.orders LIMIT 10;

-- Nicht tabellarische Dateien über ein Volume
-- /Volumes/main/sales/rohdaten/lieferung.csv

Nicht ausgeführt. Es gibt hier keinen Databricks-Workspace.

  1. Drei GRANT-Zeilen geben einer Gruppe Leserechte. USE CATALOG und USE SCHEMA sind Pflicht.
  2. Das SELECT auf dem Schema gilt für alle Tabellen darin, auch neue.
  3. MODIFY auf einer Tabelle geht an einen Service Principal. Menschen schreiben nicht direkt in Produktion.
  4. BROWSE erlaubt nur Entdecken von Objekten und Metadaten.
  5. Der Name main.sales.orders hat drei Teile.
  6. Der Volume-Pfad zeigt, wie man Dateien statt Tabellen adressiert. Die genaue GRANT-Syntax stand nicht auf den geprüften Doku-Seiten.

Vergleich

  • Metastore: oberste Ebene, pro Region.
  • Catalog: Isolation nach Umgebung oder Team.
  • Schema: Gruppe von Objekten.
  • Managed: UC verwaltet auch den Speicher.
  • External: nur Governance, Daten bleiben bei dir.
  • Volume: Dateien statt Tabellen.
  • Storage Credential: Zugang zum Speicher.
  • External Location: Pfad mit Credential.

Produktion

  1. Tabelle unsichtbar: USE CATALOG oder USE SCHEMA fehlt. Lösung: Rechte prüfen.
  2. Unerwarteter Zugriff: Vererbung von Schema oder Catalog. Lösung: Rechte auf dem passenden Level vergeben.
  3. Umgehung der Governance: Direkter Zugriff auf den Bucket. Lösung: nur Zugriff über Unity Catalog.
  4. Falsche Region: Metastore und Workspace passen nicht. Lösung: Metastore der richtigen Region nutzen.
  5. Persönliche Besitzer: Ein Mitarbeiter geht, die Tabelle hat keinen Besitzer. Lösung: Besitz an Gruppen.
  6. Ältere Workspaces: Unity Catalog fehlt. Lösung: Workspace upgraden.

Diagnose: Werkzeuge und Befehle

  • Catalog Explorer: zeigt Objekte, Rechte, Lineage und Besitzer.
  • SHOW GRANTS ON TABLE main.sales.orders: zeigt Rechte.
  • Audit-Log als System Table: zeigt Zugriffe und Aktivität.
  • Lineage im Catalog Explorer: zeigt, woher Daten kommen und wohin sie gehen.
  • Account Console: zeigt Metastores, Workspaces und die Zuordnung.
  • SELECT current_metastore(): zeigt den Metastore der Sitzung.

Senior-Punkte

  1. Governance gehört in eine Schicht. Eine Stelle für Rechte statt Regeln in jedem Workspace.
  2. Catalogs sind das Isolationsmittel. Struktur und Workspace-Binding bestimmen die Trennung.
  3. Gruppen und Service Principals, keine Einzelpersonen für Rechte und Produktionsjobs.
  4. Managed vereinfacht, External behält die Kontrolle über den Speicher.
  5. Nie am Governance-Layer vorbei. Direkter Bucket-Zugriff macht Audit wertlos.
  6. Pro Region planen. Ein Metastore pro Region, Austausch zwischen Regionen über Databricks-to-Databricks Sharing.
