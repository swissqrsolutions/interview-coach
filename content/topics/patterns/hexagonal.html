Hexagonale Architektur (Ports and Adapters)

Kern: Die hexagonale Architektur (Ports and Adapters, Alistair Cockburn) stellt die Anwendung in die Mitte und alle Technik nach aussen. Die Mitte spricht nur über Ports (Interfaces), die Technik hängt sich über Adapter an. So kann man die Anwendung gleich gut von UI, Tests oder Batch treiben und ohne DB testen.

1. Wo sitzt die hexagonale Architektur?

  1. Hexagon: die Anwendung selbst, also Domänenmodell und Use Cases. Sie importiert kein Spring Web, kein JPA, kein Kafka.
  2. Port: ein Interface an der Grenze, in der Sprache der Anwendung. Beispiel: OrderRepository.save(Order).
  3. Adapter: übersetzt zwischen einer Technik und einem Port. Beispiel: JpaOrderAdapter mappt Order auf eine JPA-Entity.
  4. Driving Side (links, primary): Akteure, die die Anwendung auslösen. REST, CLI, Test, Kafka-Consumer.
  5. Driven Side (rechts, secondary): Systeme, die die Anwendung benutzt. DB, Payment-Provider, Mail, Kafka-Producer.
  6. Die Zahl sechs hat keine Bedeutung. Cockburn wählte das Sechseck nur, damit Platz für mehrere Ports ist.

2. Die Reise einer Bestellung (die Geschichte zum Merken)

  1. Controller (driving adapter): POST /orders kommt an. Der Controller mappt JSON auf ein PlaceOrderCommand. Er kennt nur den Port PlaceOrderUseCase.
  2. Port in: PlaceOrderUseCase.place(command) ist der Eingang. Er beschreibt, was die Anwendung kann.
  3. Service: PlaceOrderService implementiert den Port. Er baut die Order, und die Order prüft ihre Regeln.
  4. Port out: Der Service braucht Speicher und Zahlung. Er ruft OrderRepository.save() und PaymentPort.charge(). Beide Interfaces gehören dem Hexagon.
  5. Driven Adapter: JpaOrderAdapter implements OrderRepository speichert wirklich. Der Kontrollfluss geht nach aussen, die Abhängigkeit zeigt nach innen. Das ist Dependency Inversion.
  6. Konfiguration: Eine @Configuration-Klasse (der Composition Root) steckt Adapter und Service zusammen. Nur sie kennt alle konkreten Klassen.

3. Beispiel: ein Kern, zwei Driving Adapter

// Kern: keine Framework-Imports
interface PlaceOrderUseCase { OrderId place(long amountRappen); }           // driving port
interface OrderRepository  { void save(Order o); Optional<Order> find(OrderId id); } // driven port
interface PaymentPort      { boolean charge(OrderId id, long amountRappen); }  // driven port

final class PlaceOrderService implements PlaceOrderUseCase {
  PlaceOrderService(OrderRepository repo, PaymentPort payment) { ... }
  public OrderId place(long amount) {
    Order o = new Order(new OrderId("O-" + (++seq)), amount); // Order prüft: amount > 0
    if (payment.charge(o.id(), o.amount())) o.markPaid();
    repo.save(o);
    return o.id();
  }
}
// Adapter aussen: InMemoryOrderRepository, FakePayment (lehnt ab 100'000 ab),
// HttpLikeAdapter (JSON → Use Case), BatchAdapter (CSV → Use Case)

// Composition Root
var repo = new InMemoryOrderRepository();
PlaceOrderUseCase core = new PlaceOrderService(repo, new FakePayment());
new HttpLikeAdapter(core).post("{\"amount\":4990}");
new HttpLikeAdapter(core).post("{\"amount\":0}");
new BatchAdapter(core).run(List.of("1200", "250000"));

Echte Ausgabe, Oracle JDK 17.0.3. Kein Spring, keine DB: der Kern läuft mit Fake-Adaptern.

  1. Derselbe PlaceOrderService wird von HTTP und von Batch getrieben. Genau das ist Cockburns Ziel.
  2. Der HTTP-Adapter übersetzt die Domain-Exception in 400 Bad Request. HTTP-Codes kennt nur der Adapter.
  3. O-2 fehlt. Die ID wurde vergeben, dann warf der Konstruktor. Solche Details sieht man sofort im schnellen Kern-Test.
  4. O-4 bleibt NEW: Der Fake-Payment-Adapter lehnt ab. So testet man den Fehlerpfad ohne echten Payment-Provider.

Dasselbe in Spring Boot (eine Möglichkeit, Package by Feature):

com.acme.order
├── domain
│   ├── model          Order, OrderId, Money          (reines Java)
│   └── service        PricingPolicy                  (Domain Service)
├── application
│   ├── port
│   │   ├── in         PlaceOrderUseCase, PlaceOrderCommand
│   │   └── out        OrderRepository, PaymentPort
│   └── service        PlaceOrderService implements PlaceOrderUseCase
├── adapter
│   ├── in
│   │   ├── web        OrderController (@RestController), OrderRequest DTO
│   │   └── messaging  OrderKafkaListener
│   └── out
│       ├── persistence JpaOrderAdapter, OrderJpaEntity, SpringDataOrderRepo
│       └── payment     PspPaymentAdapter (RestClient)
└── config             OrderConfig (@Configuration, @Bean PlaceOrderService)
  1. domain und application haben keine Spring-Annotationen. Darum werden sie per @Bean in config erzeugt.
  2. OrderJpaEntity liegt im Adapter. Das Domain-Order hat kein @Entity.
  3. @Transactional sitzt am Use Case. Puristen legen es in einen Decorator in config. Pragmatiker erlauben diese eine Spring-Annotation im Application-Ring.

4. Details, die Interviewer fragen

  1. Cockburns Absicht: Die Anwendung soll gleich gut von Benutzern, Programmen, automatischen Tests oder Batch-Skripten getrieben werden. Und sie soll ohne ihre Laufzeit-Geräte und DBs entwickelt und getestet werden.
  2. Primary vs Secondary: Cockburn nennt die Seiten primary und secondary. Er sagt selbst: man kann sie auch driving und driven Adapter nennen.
  3. Wem gehört der Port? Immer dem Hexagon. Der Port ist in Domänensprache: save(Order), nicht insertRow(Map).
  4. Driving Port: Er wird vom Hexagon implementiert und vom Adapter aufgerufen. Oft heisst er Use Case oder Input Port.
  5. Driven Port: Er wird vom Hexagon aufgerufen und vom Adapter implementiert. Hier wirkt Dependency Inversion.
  6. Wie viele Ports? Cockburn bevorzugt wenige, typisch zwei bis vier. Ein Port pro Zweck, nicht pro Tabelle.
  7. Kein oben und unten: Es gibt nur innen und aussen. UI und DB sind beide „aussen“. Das ist der Unterschied zu Layered.
  8. Mapping: Jeder Adapter mappt sein Modell auf das Domänenmodell. Kosten: mehr Klassen. Nutzen: DB-Schema und API ändern sich unabhängig von der Domäne.
  9. Composition Root: Eine Stelle verdrahtet alles, in Spring die @Configuration. Sonst ist der Kern indirekt doch an Spring gebunden.
  10. Testpyramide: Domain- und Use-Case-Tests laufen in Millisekunden mit Fakes. Adapter-Tests prüfen einzeln: @WebMvcTest für den Controller, @DataJpaTest oder Testcontainers für JPA.
  11. Test als Adapter: Ein Test ist für das Hexagon nur ein weiterer driving Adapter. Cockburn nennt Test-Harnesse wie FIT ausdrücklich.
  12. Hexagonal ist kein DDD. Es sagt nichts über Aggregates oder Value Objects. Es trennt nur Anwendung und Technik. Beides passt aber gut zusammen.

5. Vergleich

  • Layered: Stapel, Abhängigkeit nach unten bis zur DB. Hexagonal: Kreis, Abhängigkeit nach innen.
  • Onion (Palermo, 2008): gleiche Idee, aber mit benannten inneren Ringen (üblich: Domain Model, Domain Services, Application Services). Palermo verweist selbst auf Cockburn.
  • Clean (Martin, 2012): vereint Hexagonal und Onion unter der Dependency Rule. Fügt Input/Output Ports und Presenter hinzu.
  • Ports and Adapters vs Adapter-Pattern (GoF): Ein Adapter im Hexagon ist oft ein GoF-Adapter. Das Architekturmuster ist aber der ganze Aufbau mit Ports.
  • Anti-Corruption Layer (DDD): ein besonders defensiver driven Adapter zu einem fremden System. Er übersetzt dessen Modell in das eigene.

6. In der Produktion

  1. Framework im Kern: @Entity, ResponseEntity oder KafkaTemplate im Domain-Paket. Der Kern ist nicht mehr austauschbar. Lösung: ArchUnit-Regel, Mapping in den Adapter.
  2. Mapping-Explosion: Für jedes Feld drei Klassen und zwei Mapper. Für CRUD-Teile zu teuer. Lösung: Hexagonal nur für Kontexte mit echter Logik, CRUD einfacher halten.
  3. Generische Ports: GenericRepository<T> mit findBy(Map). Das ist eine durchgereichte DB-API. Lösung: fachliche Methoden wie findOpenOrdersOf(customerId).
  4. Transaktionen über Adapter: DB-Write und Kafka-Send in einem Use Case. Ohne Outbox gehen Nachrichten verloren. Lösung: Transactional Outbox als driven Adapter.
  5. Lazy Loading leckt: Der JPA-Adapter gibt Proxies nach innen. Fehler tauchen später im Kern auf. Lösung: im Adapter vollständig laden und mappen.
  6. Adapter-Logik: Fachregeln landen im Controller oder im Kafka-Listener. Lösung: Adapter nur übersetzen lassen, Regeln im Kern.

8. Senior-Punkte

  1. Der Kernnutzen ist Testbarkeit und späte Technik-Entscheidungen. Austausch der DB ist ein Nebeneffekt, selten der Grund.
  2. Kosten ehrlich nennen: mehr Klassen, Mapping, Einarbeitung. Für CRUD-Services lohnt es sich oft nicht.
  3. Ports in Domänensprache, sonst ist es nur ein Interface vor JPA ohne Wert.
  4. Pragmatismus bei Annotationen: Ein @Transactional am Use Case ist meist ok. Ein @Entity am Domain-Objekt koppelt das Modell an das Schema.
  5. Regeln automatisch prüfen. Ohne ArchUnit erodiert die Struktur in Monaten.
  6. Package by Feature zuerst. Jeder Bounded Context bekommt sein eigenes Hexagon, nicht ein globales für die ganze Firma.

10. Fallen

  • „Hexagonal heisst sechs Schichten oder sechs Ports.“ → Falsch. Die Zahl sechs ist bedeutungslos.
  • „Ein Port ist eine Klasse im Adapter.“ → Falsch. Der Port ist ein Interface und gehört dem Hexagon.
  • „Die DB ist unten, die UI oben.“ → Falsch. Beide sind aussen: UI ist driving, DB ist driven.
  • „Driven Ports implementiert der Kern.“ → Falsch. Der Kern ruft sie auf, der Adapter implementiert sie.
  • „Hexagonal ist dasselbe wie DDD.“ → Falsch. Hexagonal trennt Technik, DDD modelliert die Fachlichkeit.
  • „Mit Spring Data JPA im Service ist es hexagonal, weil JpaRepository ein Interface ist.“ → Falsch. Das Interface gehört Spring und spricht JPA-Sprache, nicht die der Domäne.

11. Fragen

Was ist hexagonale Architektur?

Ein Muster von Alistair Cockburn: Die Anwendung steht in der Mitte, Technik hängt aussen über Adapter an Ports. Ziel: von beliebigen Akteuren treibbar und ohne DB testbar.

Was ist ein Port?

Ein Interface an der Grenze der Anwendung, in ihrer eigenen Sprache. Es gehört dem Kern.

Was ist ein Adapter?

Eine Klasse, die eine Technik mit einem Port verbindet und übersetzt. Beispiel: REST-Controller oder JPA-Repository-Implementierung.

Driving vs driven Adapter?

Driving (primary) Adapter lösen die Anwendung aus, z. B. REST, Tests. Driven (secondary) Adapter werden von ihr benutzt, z. B. DB, Mail.

Wer implementiert einen driving Port, wer einen driven Port?

Den driving Port implementiert der Kern (Use-Case-Service). Den driven Port implementiert der Adapter.

Wo wirkt Dependency Inversion?

Auf der driven Seite. Der Kern ruft die DB auf, hängt aber nur vom eigenen Interface ab. Der Adapter hängt vom Kern ab.

Warum ein Sechseck?

Nur für die Zeichnung: Platz für mehrere Ports und Adapter. Die Zahl sechs bedeutet nichts.

Wie unterscheidet sich Hexagonal von Layered?

Layered hat oben und unten, die Domäne hängt von der DB ab. Hexagonal hat innen und aussen, alles hängt vom Kern ab.

Wie sieht ein Spring-Boot-Service hexagonal aus?

Pakete domain, application/port/in|out, adapter/in/web, adapter/out/persistence, config. Kern ohne Spring, Verdrahtung per @Bean.

Wo liegt die JPA-Entity?

Im Persistence-Adapter, getrennt vom Domain-Objekt. Der Adapter mappt zwischen beiden.

Welche Testvorteile bringt Hexagonal?

Use Cases laufen mit Fake-Adaptern in Millisekunden, ohne Spring und DB. Adapter testet man einzeln mit @WebMvcTest oder Testcontainers.

Ist ein Unit-Test ein Adapter?

Ja, für den Kern ist er ein weiterer driving Adapter. Cockburn nennt Test-Harnesse ausdrücklich.

Wie viele Ports soll man haben?

Wenige, nach Zweck geschnitten. Cockburn nennt meist zwei bis vier. Nicht ein Port pro Tabelle.

Was ist der Composition Root?

Die eine Stelle, die konkrete Adapter und Services verbindet. In Spring eine @Configuration-Klasse.

Darf @Transactional im Application-Kern stehen?

Pragmatisch ja, es ist ein kleiner Kompromiss. Puristen nutzen einen Decorator im Config-Paket.

Was sind die Nachteile?

Mehr Klassen und Mapping, mehr Einarbeitung. Bei reinem CRUD überwiegen die Kosten.

Wie prüfen Sie die Regeln?

ArchUnit onionArchitecture() oder eigene Regeln im CI. Schnell lokal: jdeps -verbose:package.

Ist Spring Data JpaRepository ein Port?

Nein. Es gehört Spring und spricht JPA-Sprache. Ein Port ist das eigene OrderRepository; ein Adapter nutzt intern das Spring-Data-Repository.

Wie passt ein Kafka-Consumer hinein?

Als driving Adapter. Er liest die Nachricht, mappt sie auf ein Command und ruft den Use-Case-Port.

Was hat Hexagonal mit der Anti-Corruption Layer zu tun?

Eine ACL ist ein driven Adapter, der ein fremdes Modell ins eigene übersetzt. Sie schützt den Kern vor fremden Begriffen.

Szenario: Im Code-Review sehen Sie @Entity auf der Domain-Klasse Order. Was sagen Sie?

Das koppelt Modell und DB-Schema. Ich schlage eine eigene OrderJpaEntity im Adapter mit Mapping vor. Bei sehr einfachem Modell kann man es bewusst akzeptieren, aber dann dokumentiert.

Szenario: Use-Case-Tests brauchen 40 Sekunden, weil sie Spring starten. Was tun Sie?

Den Service ohne Spring mit new und Fake-Adaptern testen. Wenn das nicht geht, hängt der Kern an Spring; diese Abhängigkeit entferne ich zuerst.

Szenario: Das Team soll von REST auf Kafka-Events als Eingang umsteigen. Was ändert sich?

Nur ein neuer driving Adapter (Kafka-Listener), der denselben Use-Case-Port ruft. Domain und Application bleiben unverändert.
