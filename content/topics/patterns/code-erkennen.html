Drill: Pattern im Code erkennen

So antwortest du im Interview — immer in 3 Schritten, 30 Sekunden gesamt:

  1. Pattern benennen: „Das ist ein Decorator" — zuerst der Name, ohne Umschweife.
  2. Woran erkannt: nenne das eine Schlüssel-Merkmal in der Struktur („gleiche Schnittstelle wie das umhüllte Objekt, delegiert und legt Verhalten dazu").
  3. Wo Spring/Java es benutzt: eine Fundstelle aus JDK oder Spring zeigt, dass du es aus der Praxis kennst, nicht aus dem Buch.

1. Entscheidungsbaum: Welches Pattern wofür?

2. Übung 1

public class ExportConfig {
    private final Path ziel;
    private final char trennzeichen;
    private final boolean mitKopfzeile;

    private ExportConfig(Einstellungen e) {
        this.ziel = e.ziel;
        this.trennzeichen = e.trennzeichen;
        this.mitKopfzeile = e.mitKopfzeile;
    }

    public static class Einstellungen {
        private Path ziel;
        private char trennzeichen = ';';
        private boolean mitKopfzeile = true;

        public Einstellungen ziel(Path p) { this.ziel = p; return this; }
        public Einstellungen trennzeichen(char c) { this.trennzeichen = c; return this; }
        public Einstellungen ohneKopfzeile() { this.mitKopfzeile = false; return this; }
        public ExportConfig fertig() { return new ExportConfig(this); }
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Builder. Schlüssel-Merkmal: jede Setz-Methode gibt this zurück (fluent), erst der letzte Schritt fertig() erzeugt das unveränderliche Zielobjekt — dessen Konstruktor ist privat.

In Spring/Java: HttpRequest.newBuilder(), UriComponentsBuilder, Lomboks @Builder.

Nicht nehmen, wenn: das Objekt nur 2–3 Pflichtfelder hat — ein Konstruktor oder ein Record ist dann kürzer und klarer.

3. Übung 2

abstract class BerichtExport {
    public void exportieren(List<Bericht> daten) throws IOException {
        try (DatenZiel ziel = oeffneZiel()) {
            for (Bericht b : daten) {
                ziel.schreibe(b);
            }
        }
    }

    protected abstract DatenZiel oeffneZiel() throws IOException;
}

class CsvExport extends BerichtExport {
    @Override
    protected DatenZiel oeffneZiel() {
        return new CsvZiel(Path.of("bericht.csv"));
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Factory Method. Schlüssel-Merkmal: die Oberklasse ruft eine abstrakte Methode auf, deren einzige Aufgabe das Erzeugen eines Objekts ist — die Unterklasse entscheidet, welche konkrete Klasse entsteht.

In Spring/Java: @Bean-Methoden sind Fabrikmethoden des Containers; im JDK Collection.iterator().

Nicht nehmen, wenn: es nur eine Implementierung gibt und keine zweite absehbar ist — dann reicht new.

Warum ist das nicht Template Method?

Die Struktur ist verwandt (Oberklasse ruft abstrakten Schritt). Der Unterschied liegt im Zweck des Schritts: Erzeugt er ein Objekt, ist es Factory Method. Variiert er einen Verarbeitungs-Schritt eines festen Ablaufs (lesen, prüfen, speichern), ist es Template Method. Im Interview genau das sagen — es zeigt, dass du Struktur und Absicht trennst.

public enum LizenzPruefer {
    INSTANZ;

    private final Map<String, Boolean> cache = new ConcurrentHashMap<>();

    public boolean istGueltig(String schluessel) {
        return cache.computeIfAbsent(schluessel, this::pruefeBeimServer);
    }

        // HTTP-Aufruf zum Lizenzserver
        return true;
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Singleton — hier in der robustesten Form als Enum. Schlüssel-Merkmal: genau eine Instanz (INSTANZ), die JVM garantiert das bei Enums sogar gegen Reflection und Serialisierung; die Alternative ist eine statische Holder-Klasse.

In Spring/Java: Spring-Beans sind per Default im Scope „singleton" — aber vom Container verwaltet, nicht selbst gebaut; im JDK Runtime.getRuntime().

Nicht nehmen, wenn: du Dependency Injection hast — ein handgebautes Singleton ist globaler Zustand, schwer zu testen und zu mocken.

5. Übung 4

interface PortoRegel {
    BigDecimal porto(Sendung s);
}

class StandardPorto implements PortoRegel {
    public BigDecimal porto(Sendung s) { return new BigDecimal("4.99"); }
}

class ExpressPorto implements PortoRegel {
    public BigDecimal porto(Sendung s) {
        return new BigDecimal("12.99").add(s.gewichtZuschlag());
    }
}

class VersandService {
    private final PortoRegel regel;
    VersandService(PortoRegel regel) { this.regel = regel; }
    BigDecimal berechne(Sendung s) { return regel.porto(s); }
}
Welches Pattern? Woran erkennst du es?
Lösung

Strategy. Schlüssel-Merkmal: ein kompletter Algorithmus steckt hinter einer gemeinsamen Schnittstelle und wird von außen hineingegeben (Konstruktor) — der Nutzer VersandService kennt nur die Schnittstelle.

In Spring/Java: Comparator in sort(); Springs PasswordEncoder — welche Implementierung läuft, entscheidet die Konfiguration.

Nicht nehmen, wenn: es nur einen stabilen Algorithmus gibt — eine Schnittstelle mit einer einzigen Implementierung ist tote Indirektion.

6. Übung 5

interface BestandsAlarm {
    void bestandNiedrig(String artikel, int rest);
}

class LagerDienst {
    private final List<BestandsAlarm> alarme = new ArrayList<>();
    private final Map<String, Integer> bestand = new HashMap<>();

    void registrieren(BestandsAlarm a) { alarme.add(a); }

    void entnehmen(String artikel, int menge) {
        int rest = bestand.merge(artikel, -menge, Integer::sum);
        if (rest < 10) {
            for (BestandsAlarm a : alarme) {
                a.bestandNiedrig(artikel, rest);
            }
        }
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Observer (Listener). Schlüssel-Merkmal: das Subjekt hält eine Liste von Empfängern, die sich registrieren, und ruft bei einem Ereignis alle zurück — ohne zu wissen, wer sie sind.

In Spring/Java: ApplicationEventPublisher + @EventListener; im UI-Umfeld jeder ActionListener.

Nicht nehmen, wenn: der Sender das Ergebnis oder die Reihenfolge der Empfänger braucht — dann ist ein direkter Aufruf ehrlicher.

7. Übung 6

interface Versand {
    Quittung sende(Paket p);
}

class MessenderVersand implements Versand {
    private final Versand kern;
    private final MetrikRegistry metrik;

    MessenderVersand(Versand kern, MetrikRegistry metrik) {
        this.kern = kern;
        this.metrik = metrik;
    }

    @Override
    public Quittung sende(Paket p) {
        long start = System.nanoTime();
        try {
            return kern.sende(p);
        } finally {
            metrik.messe("versand.dauer", System.nanoTime() - start);
        }
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Decorator. Schlüssel-Merkmal: implementiert dieselbe Schnittstelle wie das Objekt, das es umhüllt, delegiert den Kern-Aufruf und legt Verhalten davor/danach — beliebig stapelbar.

In Spring/Java: BufferedInputStream um einen FileInputStream; Collections.unmodifiableList.

Nicht nehmen, wenn: die Schnittstellen nicht zusammenpassen — Übersetzen ist Adapter, nicht Decorator.

// Fremdbibliothek, nicht aenderbar:
class AltesFaxGeraet {
    void uebertrage(byte[] seiten, String nummer, int baudRate) {
        // ...
    }
}

    void sende(Nachricht n);
}

        geraet.uebertrage(seiten, n.empfaenger(), 14400);
    }

Welches Pattern? Woran erkennst du es?
Lösung

Adapter. Schlüssel-Merkmal: übersetzt zwischen zwei unpassenden Schnittstellen (unsere NachrichtenKanal-Welt gegen die Fremd-API) und fügt dabei kein neues fachliches Verhalten hinzu.

In Spring/Java: InputStreamReader (Bytes zu Zeichen), Arrays.asList (Array zu List); Springs HandlerAdapter heißt sogar so.

Nicht nehmen, wenn: beide Seiten dieselbe Schnittstelle haben — dann willst du vermutlich dekorieren, nicht adaptieren.

9. Übung 8

abstract class DatenImport {
    public final ImportErgebnis ausfuehren(Path quelle) {
        List<Zeile> zeilen = lesen(quelle);
        List<Zeile> gueltig = zeilen.stream()
                .filter(this::istGueltig)
                .toList();
        speichern(gueltig);
        return new ImportErgebnis(zeilen.size(), gueltig.size());
    }

    protected abstract List<Zeile> lesen(Path quelle);

    protected abstract boolean istGueltig(Zeile z);

    protected void speichern(List<Zeile> zeilen) {
        // Default: direkt in die Datenbank
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Template Method. Schlüssel-Merkmal: eine final-Methode legt das Skelett des Ablaufs fest (lesen, filtern, speichern), Unterklassen füllen einzelne Schritte per Vererbung — die Reihenfolge können sie nicht ändern.

In Spring/Java: die Grundidee hinter JdbcTemplate und Co. — der Rahmen (Verbindung, Fehler, Aufräumen) ist fest, dein Schritt wird eingesetzt (dort über Callbacks statt Vererbung).

Nicht nehmen, wenn: du neu entwirfst — Komposition (Strategy/Lambdas) koppelt loser als eine Vererbungs-Hierarchie.

10. Übung 9

interface TarifDienst {
    Tarif tarifFuer(Kunde k);
}

class GesicherterTarifDienst implements TarifDienst {
    private final TarifDienst echterDienst;
    private final ZugriffsPruefung pruefung;

    GesicherterTarifDienst(TarifDienst echterDienst, ZugriffsPruefung pruefung) {
        this.echterDienst = echterDienst;
        this.pruefung = pruefung;
    }

    @Override
    public Tarif tarifFuer(Kunde k) {
        if (!pruefung.darfLesen(SitzungsKontext.nutzer(), "TARIFE")) {
            throw new ZugriffVerweigertException();
        }
        return echterDienst.tarifFuer(k);
    }
}
Welches Pattern? Woran erkennst du es?
Lösung

Proxy. Schlüssel-Merkmal: gleiche Schnittstelle wie das echte Objekt, aber die Hülle kontrolliert den Zugriff (Sicherheit, Lazy Loading, Remote) — das fachliche Ergebnis bleibt unverändert.

In Spring/Java: genau so funktioniert @Transactional — Spring legt zur Laufzeit einen Proxy um die Bean, der vor dem Aufruf die Transaktion öffnet und danach committet oder zurückrollt; ebenso @Cacheable und @Async.

Nicht nehmen, wenn: du sichtbares Verhalten hinzufügen willst (Logging-Ausgabe, Metriken als Feature) — das ist die Absicht des Decorators.

Proxy oder Decorator — die 10-Sekunden-Antwort

Struktur identisch (gleiche Schnittstelle, Delegation) — entscheidend ist die Absicht: Der Proxy kontrolliert, ob/wie der Aufruf das echte Objekt erreicht; der Decorator reichert an, was dabei passiert. Im Interview: „Strukturell gleich, die Absicht unterscheidet sie — Spring nennt seine Transaktions-Hülle darum Proxy."

11. Übung 10

abstract class AntragsPruefung {
    private AntragsPruefung naechste;

    AntragsPruefung dann(AntragsPruefung n) { this.naechste = n; return n; }

    public Entscheidung pruefe(KreditAntrag a) {
        Entscheidung e = eigenePruefung(a);
        if (e != Entscheidung.WEITER) return e;
        return (naechste == null) ? Entscheidung.GENEHMIGT : naechste.pruefe(a);
    }

    protected abstract Entscheidung eigenePruefung(KreditAntrag a);
}

// Aufbau:
// betrug.dann(bonitaet).dann(limit);
// Entscheidung e = betrug.pruefe(antrag);
Welches Pattern? Woran erkennst du es?
Lösung

Chain of Responsibility. Schlüssel-Merkmal: jedes Glied hält eine Referenz auf das nächste und entscheidet pro Anfrage: selbst beantworten oder weiterreichen — der Aufrufer kennt nur den Kopf der Kette.

In Spring/Java: Servlet-Filter und die Spring-Security-FilterChain; HandlerInterceptor-Ketten in MVC.

Nicht nehmen, wenn: immer alle Schritte laufen müssen — das ist eine schlichte Pipeline/Liste, keine Kette mit Abbruch.

12. Übung 11: der Package-Baum

de.firma.vertrieb
├── domain
│   ├── Vertrag.java
│   ├── VertragsNummer.java
│   └── VertragsRegeln.java          (kein Framework-Import)
├── application
│   ├── VertragAbschliessen.java     (Use Case)
│   └── port
│       ├── in  VertragAbschliessenPort.java   (Interface)
│       └── out VertragsSpeicher.java          (Interface)
└── adapter
    ├── in  web  VertragsController.java       (Spring MVC)
    └── out persistence  JpaVertragsSpeicher.java  (JPA)
Welche Architektur? Woran erkennst du es — und was wäre der Unterschied zur klassischen Schichten-Architektur?
Lösung

Hexagonal / Ports & Adapters. Schlüssel-Merkmal: die Abhängigkeiten zeigen nach innen — domain und application importieren kein Framework; VertragsSpeicher ist ein Interface (Out-Port) innen, die JPA-Implementierung liegt außen im Adapter.

Unterschied zu Schichten: klassisch hieße es Controller → Service → Repository, und die Domäne hinge direkt an JPA-Annotationen; hier ist die Persistenz nur ein austauschbarer Stecker.

Nicht nehmen, wenn: die Anwendung ein kleines CRUD ist — die Port-Interfaces sind dann Zeremonie ohne Gegenwert.

13. Übung 12: zwei Dienste, eine Fachlichkeit

@Service
public class BestellungSchreibDienst {
    @Transactional
    public BestellungsId aufgeben(NeueBestellung befehl) {
        Bestellung b = Bestellung.neuAus(befehl);   // prueft Invarianten
        repo.save(b);
        events.publishEvent(new BestellungAufgegeben(b.id()));
        return b.id();
    }
}

@Service
public class BestellungLeseDienst {
    public List<BestellUebersicht> offene(KundenId kunde) {
        return jdbc.sql("SELECT * FROM bestell_uebersicht WHERE kunde_id = ?")
                   .param(kunde.wert())
                   .query(BestellUebersicht.class)
                   .list();
    }
}
Welche Architektur-Idee steckt hier? Woran erkennst du sie?
Lösung

CQRS (Command Query Responsibility Segregation) — zumindest seine Grundidee. Schlüssel-Merkmal: Schreiben und Lesen sind getrennte Wege: der Schreibdienst geht durchs Domänenmodell mit Invarianten und gibt nur eine Id zurück; der Lesedienst liest direkt aus einer zugeschnittenen Lese-Tabelle (bestell_uebersicht), ohne Domänenmodell.

In Spring/Java: oft schon als „Repository für Writes, JDBC-View für Reports" in ganz normalen Projekten; das Event deutet an, wie die Lese-Tabelle aktuell gehalten wird.

Nicht nehmen, wenn: Lese- und Schreibmodell praktisch identisch sind — dann erzeugt CQRS nur doppelte Wartung und Eventual-Consistency-Fragen ohne Nutzen.

14. Schichten vs Hexagonal auf einen Blick

15. Die drei Sätze, die einen Senior verraten

  • „Pattern-Namen sind Kommunikation, kein Selbstzweck — ich sage: das ist faktisch eine Strategy, auch wenn keine Klasse so heißt."
  • „Ich erkenne Patterns an der Struktur und der Absicht, nicht am Klassennamen — der bekannteste Decorator im JDK heißt BufferedInputStream."
  • „JDK und Spring bestehen aus Patterns: Comparator ist Strategy, die Filter-Kette ist Chain of Responsibility, @Transactional läuft über einen Proxy — ich nenne Fundstellen statt Lehrbuch-Definitionen."

16. Typische Fehler beim Pattern-Raten

  • Jedes if-else „Strategy" nennen: Strategy ist es erst, wenn der Algorithmus hinter einer gemeinsamen Schnittstelle steckt und von außen gewählt wird — ein switch im selben Methodenrumpf ist nur ein switch.
  • Singleton mit new + statischem Feld: ohne privaten Konstruktor und Instanz-Garantie (Enum oder statische Holder-Klasse) ist es nur eine globale Variable mit Race Condition beim ersten Zugriff.
  • Decorator mit Adapter verwechseln: das Unterscheidungsmerkmal ist die Schnittstelle — gleiche Schnittstelle + zusätzliches Verhalten = Decorator; Übersetzung zwischen zwei unpassenden Schnittstellen = Adapter.
  • Proxy mit Decorator verwechseln: gleiche Struktur, andere Absicht — der Proxy kontrolliert den Zugriff (Transaktion, Security, Lazy), der Decorator reichert das Ergebnisverhalten an. Wer das sauber trennt, punktet.

17. Schnellrunde: jedes Pattern in einem Satz

Builder in 1 Satz

Fluent-Methoden sammeln optionale Werte, ein letzter Schritt baut daraus das unveränderliche Objekt.

Factory Method in 1 Satz

Eine Methode, deren einzige Aufgabe das Erzeugen ist — die Unterklasse (oder der Container) entscheidet, welche konkrete Klasse entsteht.

Singleton in 1 Satz

Genau eine Instanz im Prozess, am sichersten als Enum — in Spring-Projekten übernimmt das aber der Container.

Strategy in 1 Satz

Ein austauschbarer Algorithmus hinter einer gemeinsamen Schnittstelle, von außen hineingegeben — wie ein Comparator.

Observer in 1 Satz

Ein Subjekt hält eine Liste registrierter Empfänger und benachrichtigt alle bei einem Ereignis, ohne sie zu kennen.

Decorator in 1 Satz

Gleiche Schnittstelle wie das umhüllte Objekt, delegiert und legt Verhalten dazu — stapelbar wie BufferedInputStream.

Adapter in 1 Satz

Übersetzt zwischen zwei unpassenden Schnittstellen, ohne fachlich etwas hinzuzufügen.

Template Method in 1 Satz

Eine finale Methode legt den Ablauf fest, Unterklassen füllen einzelne Schritte per Vererbung.

Proxy in 1 Satz

Gleiche Schnittstelle, kontrolliert aber den Zugriff auf das echte Objekt — so setzt Spring @Transactional um.

Chain of Responsibility in 1 Satz

Jedes Glied beantwortet die Anfrage selbst oder reicht sie ans nächste weiter — wie die Servlet-Filter-Kette.
