Erzeugungsmuster

Kern: Erzeugungsmuster (Creational Patterns) trennen das Erzeugen von Objekten vom Code, der sie nutzt. new KonkreteKlasse() überall im Code macht Austausch, Tests und Konfiguration schwer. In Spring übernimmt der Container den Grossteil dieser Arbeit.

Antwort-Muster

Frage: Wie unterscheidet sich ein Singleton in Spring vom GoF-Singleton?

  1. Mechanismus: Das GoF-Singleton hat einen privaten Konstruktor und genau eine Instanz pro ClassLoader. Spring hält eine Instanz pro Container und Bean-Definition.
  2. Zahl: Reflection erzeugt beim klassischen Singleton eine zweite Instanz. Beim Enum-Singleton verbietet die JVM das.
  3. Trade-off: Das statische Singleton ist globaler Zustand und schwer testbar. Das Spring-Singleton wird per DI übergeben und ist ersetzbar.
  4. Produktion: Zustand in einem Spring-Singleton teilen alle Requests. Daten fliessen dann zwischen Nutzern.

1. Die Reise eines Beans

  1. Deklaration: @Component oder eine @Bean-Methode beschreibt, wie ein Objekt entsteht. Die @Bean-Methode ist eine Factory Method.
  2. BeanDefinition: Spring speichert ein Rezept: Klasse, Abhängigkeiten, Scope. Noch existiert kein Objekt.
  3. getBean(): Der Container (BeanFactory) erzeugt das Objekt. Der Client ruft nie new.
  4. Scope prüfen: Der Standard-Scope ist singleton. Das heisst laut Spring-Doku: eine Instanz pro Container und pro Bean-Definition, nicht pro ClassLoader wie beim GoF-Singleton.
  5. prototype: Jeder Abruf erzeugt ein neues Objekt. Spring ruft für Prototypen keine Destroy-Callbacks auf.
  6. Fertigstellen: Spring injiziert Abhängigkeiten, ruft Init-Methoden auf und wickelt das Objekt bei Bedarf in einen Proxy. Der Client bekommt ein fertiges Objekt.

2. Aufbau

  1. Client: Er braucht ein Objekt und kennt nur dessen Interface. Beispiel: ein Service braucht einen PaymentGateway.
  2. Singleton: Es gibt genau eine Instanz pro ClassLoader. Beispiel: Runtime.getRuntime().
  3. Factory Method: Eine Methode entscheidet, welche konkrete Klasse entsteht. Beispiel: List.of(...).
  4. Abstract Factory: Ein Objekt erzeugt eine ganze Familie passender Objekte. Beispiel: DocumentBuilderFactory.
  5. Builder: Ein komplexes Objekt entsteht Schritt für Schritt und wird am Ende geprüft. Beispiel: RestClient.builder().
  6. Prototype: Ein neues Objekt entsteht als Kopie einer Vorlage. Beispiel: Spring-Scope prototype (nur namentlich verwandt).
  7. Spring Container: Er ist selbst eine grosse Factory. Er erzeugt Beans, verdrahtet sie und hält Singletons pro Container.

3. Details, die Interviewer fragen

Singleton. Ein Singleton ist eine Klasse mit genau einer Instanz. Sie hat einen globalen Zugriffspunkt (GoF).

// schlecht: lazy, aber nicht thread-sicher
class Config { private static Config instance;
  static Config get() { if (instance == null) instance = new Config(); return instance; } }   // Race: zwei Instanzen

// ok: Double-Checked Locking, nur mit volatile korrekt
class Config { private static volatile Config instance;
  static Config get() {
    Config c = instance;
    if (c == null) { synchronized (Config.class) { c = instance; if (c == null) instance = c = new Config(); } }
    return c; } }

// besser: Holder-Idiom (lazy, thread-sicher durch Klasseninitialisierung, ohne Lock)
class Config { private Config() {}
  private static class Holder { static final Config INSTANCE = new Config(); }
  static Config get() { return Holder.INSTANCE; } }

// am robustesten: Enum (Effective Java, Item 3)
enum Config { INSTANCE; String get(String key) { ... } }
  1. Holder-Idiom: Die JVM initialisiert eine Klasse beim ersten aktiven Zugriff. Sie garantiert dabei Thread-Sicherheit (JLS §12.4.2). Darum braucht es kein synchronized.
  2. Enum-Singleton: Es ist sicher gegen Reflection und Serialisierung. Es kann aber nicht von einer Klasse erben. Es ist immer eager.
  3. Warum volatile bei DCL: Ohne volatile kann ein anderer Thread eine Referenz auf ein halb konstruiertes Objekt sehen.
  4. Warum Singletons Tests schaden: Sie sind globaler Zustand. Der Zustand bleibt zwischen Tests erhalten. Man kann sie nicht per Konstruktor ersetzen. Die Abhängigkeit ist im Code versteckt, denn es steht Config.get() statt eines Parameters.
  5. Lösung: Man erzeugt das Objekt einmal und übergibt es per Dependency Injection. Spring-Singletons sind genau das. Es gibt eine Instanz, und sie ist ersetzbar.

Factory Method. Eine Factory Method erzeugt ein Objekt und versteckt die konkrete Klasse. Bei GoF entscheidet eine Unterklasse, welches Produkt entsteht. In der Praxis meint man oft eine statische Factory-Methode (Effective Java, Item 1).

// schlecht: Client kennt alle Klassen
Parser p = type.equals("ORDER") ? new OrderXmlParser() : new TradeXmlParser();
// besser: eine Stelle entscheidet, Name sagt die Absicht
interface ReportParser {
  static ReportParser forType(ReportType t) {
    return switch (t) { case ORDER -> new OrderXmlParser(); case TRADE -> new TradeXmlParser(); };
  }
  List<Record> parse(InputStream in);
}
  1. Vorteile statischer Factory-Methoden: Sie haben Namen, zum Beispiel Duration.ofSeconds. Sie können cachen, zum Beispiel Integer.valueOf. Sie können einen Subtyp liefern, zum Beispiel List.of.
  2. Spring: Jede @Bean-Methode ist eine Factory Method. FactoryBean<T> ist eine Factory, die selbst ein Bean ist.

Abstract Factory. Eine Abstract Factory ist ein Interface für eine ganze Familie zusammenpassender Objekte. Der Client bleibt unabhängig von der konkreten Familie.

interface StorageFactory { BlobStore blobStore(); Catalog catalog(); }
class AzureStorageFactory implements StorageFactory { ... }   // Azure Blob + Azure-Katalog
class LocalStorageFactory implements StorageFactory { ... }   // MinIO + lokaler Katalog
// Client: ein Parameter, und alle Teile passen zusammen
class Importer { Importer(StorageFactory f) { this.store = f.blobStore(); this.catalog = f.catalog(); } }
  1. JDK: DocumentBuilderFactory.newInstance() und XPathFactory liefern eine Implementierung. Der Classpath bestimmt sie.
  2. Spring: Eine @Profile("prod")-Konfigurationsklasse mit mehreren @Bean-Methoden wirkt wie eine Abstract Factory pro Umgebung.
  3. Unterschied zu Factory Method: Factory Method erzeugt ein Produkt. Abstract Factory erzeugt mehrere verwandte Produkte.

Builder. Ein Builder baut ein komplexes Objekt Schritt für Schritt. Er liefert es am Ende fertig und geprüft.

// schlecht: Telescoping Constructor, Reihenfolge leicht verwechselt
new Payment("CH93...", 12550, "CHF", null, null, true);
// besser: Builder, Validierung in build(), Ergebnis unveränderlich
Payment p = Payment.builder().iban("CH93...").amountRappen(12_550).reference("INV-42").build();
  1. Wann: Ein Builder lohnt sich ab etwa vier Parametern. Er hilft bei vielen optionalen Feldern. Er hilft auch, wenn Invarianten über mehrere Felder gelten.
  2. JDK/Spring: Beispiele sind StringBuilder, HttpRequest.newBuilder() und Stream.builder(). Dazu kommen RestClient.builder(), WebClient.builder(), ResponseEntity.ok().header(...).body(...) und UriComponentsBuilder.
  3. Lombok @Builder: Es spart Code. Es prüft aber keine Pflichtfelder. Die Prüfung muss man selbst einbauen.
  4. Records: Für wenige Pflichtfelder ist ein Record mit Compact Constructor oft besser als ein Builder.

Prototype. Ein Prototype ist ein Objekt, das als Vorlage dient. Neue Objekte entstehen durch Kopieren statt durch Konstruktion.

// schlecht: Object.clone() ist flach, Listen werden geteilt
Template copy = original.clone(); copy.tags.add("b");   // ändert auch original.tags
// besser: Copy-Konstruktor oder Kopier-Factory mit tiefer Kopie
Template(Template other) { this.name = other.name; this.tags = new ArrayList<>(other.tags); }
  1. Probleme mit Cloneable: Das Interface hat keine Methode. clone() umgeht Konstruktoren und kopiert flach. Bloch rät davon ab (Effective Java, Item 13).
  2. Spring prototype-Scope: Der Name ist ähnlich, aber Spring kopiert nicht. Es erzeugt jedes Mal ein neues Objekt nach der BeanDefinition.
  3. Falle: Ein Prototype-Bean in einem Singleton existiert nur einmal. Für ein neues Objekt pro Aufruf nutzt man ObjectProvider<T>.getObject() oder @Lookup.

4. Fallen

  • „Spring-Beans sind Singletons im GoF-Sinn.“ → Falsch. Spring-Singleton heisst eine Instanz pro Container und Bean-Definition. Die Klasse kann mehrfach existieren.
  • „Double-Checked Locking ohne volatile ist sicher.“ → Falsch. Andere Threads können ein halb initialisiertes Objekt sehen.
  • „clone() macht eine Kopie.“ → Nur flach. Referenzierte Objekte wie Listen werden geteilt.
  • „Ein privater Konstruktor garantiert ein Singleton.“ → Falsch. Reflection und Serialisierung erzeugen weitere Instanzen. Nur Enum schützt.
  • „Spring-Prototype-Scope ist das Prototype-Pattern.“ → Falsch. Spring kopiert nicht, es erzeugt neu.
  • „Integer-Objekte vergleicht man mit ==.“ → Falsch. Es klappt nur im Cache-Bereich −128 bis 127. Immer equals.

5. Selbsttest

Warum?

Warum ist das Holder-Idiom thread-sicher?

Die JVM initialisiert die Holder-Klasse beim ersten Zugriff genau einmal und synchronisiert das selbst. Darum braucht es kein Lock im Code.

Warum ist ein Enum das sicherste Singleton?

Die JVM verbietet das reflektive Erzeugen von Enums, und Serialisierung liefert dieselbe Konstante. Nachteil: keine Vererbung, immer eager.

Warum braucht Double-Checked Locking volatile?

Ohne volatile kann die Referenz sichtbar werden, bevor der Konstruktor fertig ist. Ein anderer Thread nutzt dann ein halbes Objekt.

Warum gelten Singletons als schlecht für Tests?

Sie sind globaler Zustand, der zwischen Tests bleibt. Sie lassen sich nicht per Konstruktor ersetzen. Die Abhängigkeit ist versteckt.

Wie innen?

Was sind Erzeugungsmuster?

Muster, die das Erzeugen von Objekten kapseln. GoF nennt fünf: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

Was ist eine Factory Method?

Eine Methode, die ein Objekt erzeugt und die konkrete Klasse versteckt. Beispiele: List.of, Integer.valueOf, jede @Bean-Methode.

Was ist ein FactoryBean in Spring?

Ein Bean, das selbst ein anderes Objekt erzeugt. getBean liefert das Produkt, mit &-Präfix das FactoryBean selbst.

Wo prüft ein Builder Pflichtfelder?

In build(). So kann kein ungültiges Objekt entstehen. Das Produkt selbst ist unveränderlich.

Was ist das Prototype-Pattern?

Neue Objekte entstehen durch Kopieren einer Vorlage. In Java am sichersten mit Copy-Konstruktor statt clone().

Was ist das Problem mit clone()?

Es kopiert flach, umgeht Konstruktoren und Cloneable hat keine Methode. Referenzierte Objekte werden geteilt.

Ruft Spring Destroy-Callbacks für Prototype-Beans auf?

Nein. Spring übergibt das Objekt und vergisst es. Der Client muss Ressourcen selbst freigeben.

Zahlen

Warum ist Integer.valueOf(128) == Integer.valueOf(128) false?

valueOf cacht nur −128 bis 127. Ausserhalb entstehen neue Objekte. Wrapper immer mit equals vergleichen.

Ab wie vielen Parametern lohnt sich ein Builder?

Ab etwa vier Parametern, bei vielen optionalen Feldern oder wenn Regeln über mehrere Felder gelten. Bei wenigen Pflichtfeldern ist ein Record klarer.

Wie viele Instanzen hat ein GoF-Singleton, wie viele ein Spring-Singleton?

Das GoF-Singleton hat eine Instanz pro ClassLoader. Das Spring-Singleton hat eine Instanz pro Container und Bean-Definition. Die Klasse kann also mehrfach existieren.

Vergleich

Wie unterscheidet sich das Spring-Singleton vom GoF-Singleton?

Spring: eine Instanz pro Container und Bean-Definition, per DI übergeben. GoF: eine Instanz pro ClassLoader mit globalem Zugriff.

Welche Vorteile haben statische Factory-Methoden gegenüber Konstruktoren?

Sie haben sprechende Namen, können Objekte cachen und einen Subtyp zurückgeben. Nachteil: Sie sind in der API schwerer zu finden.

Factory Method vs Abstract Factory?

Factory Method erzeugt ein Produkt. Abstract Factory erzeugt eine Familie passender Produkte über ein Interface.

Wann nutzen Sie einen Builder?

Bei vielen Parametern, vielen optionalen Feldern oder Regeln über mehrere Felder. Für wenige Pflichtfelder reicht ein Record.

Produktion

Dürfen Spring-Singleton-Beans Zustand haben?

Nur unveränderlichen oder thread-sicheren Zustand. Zustand pro Request in Feldern wird von allen Threads geteilt und führt zu Datenlecks.

Was passiert, wenn ein Prototype-Bean in ein Singleton injiziert wird?

Es wird nur einmal beim Erzeugen des Singletons injiziert. Für neue Instanzen: ObjectProvider.getObject() oder @Lookup.

Szenario: Tests sind einzeln grün, in der Suite rot. Was prüfen Sie?

Statischen Zustand, oft ein Singleton oder ein statischer Cache. Ich ersetze ihn durch ein injiziertes Bean und erzeuge pro Test neue Objekte.

Szenario: Nutzer sehen unter Last manchmal Daten anderer Nutzer. Woran denken Sie?

An ein Feld mit Request-Zustand in einem Singleton-Bean. Alle Threads teilen es. Fix: Zustand als Parameter oder lokale Variable.

Szenario: Im Review sehen Sie einen Konstruktor mit acht Parametern, drei davon null. Was schlagen Sie vor?

Einen Builder mit Prüfung in build() oder mehrere statische Factory-Methoden mit klaren Namen. Optionale Felder bekommen Defaults.

Design

Wie implementieren Sie ein thread-sicheres Singleton?

Am einfachsten als Enum oder mit dem Holder-Idiom. Double-Checked Locking geht nur mit volatile. In Spring nutze ich ein Bean mit Standard-Scope.

Wo nutzt das JDK eine Abstract Factory?

DocumentBuilderFactory, XPathFactory und TransformerFactory. Die Implementierung kommt aus dem Classpath.

Welche Builder gibt es in JDK und Spring?

StringBuilder, HttpRequest.newBuilder, Stream.builder, RestClient.builder, WebClient.builder, UriComponentsBuilder, ResponseEntity.

Ist Spring selbst ein Erzeugungsmuster?

Der Container ist eine grosse Factory. Er nutzt Factory Methods (@Bean), Singletons (Scope) und Builder (BeanDefinitionBuilder).

Mehr

Gerüst

  • Warum? new KonkreteKlasse() überall macht Austausch, Tests und Konfiguration schwer. Erzeugung und Nutzung gehören getrennt.
  • Wie innen? Spring: @Bean-Methode = Factory Method, BeanDefinition = Rezept, getBean() baut das Objekt. Default-Scope singleton: eine Instanz pro Container.
  • Zahlen Builder ab etwa vier Parametern. Integer.valueOf cacht −128 bis 127. clone() ist flach. Prototype-Beans bekommen keine Destroy-Callbacks.
  • Vergleich GoF-Singleton = pro ClassLoader. Spring-Singleton = pro Container und Bean-Definition. Factory Method = ein Produkt, Abstract Factory = eine Familie.
  • Produktion Flaky Tests durch statischen Zustand. Zustand in Singleton-Beans teilt Daten zwischen Nutzern. Prototype in Singleton ist nur einmal da.
  • Design Eine Instanz ist eine Konfigurationsfrage, darum Spring-Scope statt statischem Singleton. Wenige Pflichtfelder: Record statt Builder.

Echte Ausgabe, OpenJDK/Oracle JDK 17.0.3 (java CreationalDemo.java).

  1. Reflection bricht das klassische Singleton: setAccessible(true) öffnet den privaten Konstruktor. Es gibt zwei Instanzen.
  2. Enum ist geschützt: Die JVM verbietet das reflektive Erzeugen von Enums (JLS §8.9). Auch Serialisierung erzeugt keine Kopie.
  3. Holder ist lazy: Heavy wird erst beim ersten get() gebaut. Der Aufruf einer anderen statischen Methode reicht nicht.
  4. Globaler Zustand: „Test B“ sieht den Wert aus „Test A“. Tests hängen dann von der Reihenfolge ab.
  5. Builder prüft in build(): Ein Objekt ohne IBAN kann gar nicht entstehen. Das Objekt selbst ist unveränderlich.
  6. clone() ist flach: Das b landet auch im Original, weil beide dieselbe Liste teilen. Nur deepCopy() ist sicher.
  7. Factory Methods verstecken die Klasse: List.of liefert eine interne Klasse. Integer.valueOf gibt für −128 bis 127 gecachte Objekte zurück. Darum ist == bei 128 false.

Vergleich

  • GoF-Singleton vs Spring-Singleton: GoF: eine Instanz pro ClassLoader, globaler Zugriff, schwer testbar. Spring: eine Instanz pro Container und Bean-Definition, per DI übergeben, leicht ersetzbar.
  • Factory Method vs Abstract Factory: ein Produkt vs eine Familie von Produkten.
  • Builder vs Factory: Builder für viele Parameter und schrittweisen Aufbau. Factory für die Wahl der Klasse.
  • Builder vs Record: Record für wenige Pflichtfelder. Builder bei vielen optionalen Feldern.
  • Prototype vs Copy-Konstruktor: In Java ist der Copy-Konstruktor die sichere Form von Prototype.
  • Holder vs Enum vs DCL: Holder: lazy, einfach. Enum: am sichersten, eager. DCL: nur mit volatile, heute selten nötig.

In der Produktion

  1. Flaky Tests durch Singleton-Zustand: Tests laufen einzeln grün, zusammen rot. Ursache: statischer Zustand. Fix: Zustand in ein Spring-Bean, per DI übergeben, pro Test neu erzeugen.
  2. Zustand in Spring-Singleton-Beans: Ein Feld wie private String currentUser im @Service wird von allen Requests geteilt. Daten fliessen zwischen Nutzern. Fix: Services zustandslos halten, Zustand als Parameter.
  3. Zwei Singletons in einer App: Gleiche Klasse in zwei ClassLoadern, z. B. in einem Application Server. Fix: kein statisches Singleton, sondern ein Container-Bean.
  4. Unvollständige Objekte: Setter-basierte Erzeugung vergisst ein Pflichtfeld. Fix: Builder mit Prüfung in build() oder Konstruktor mit Pflichtfeldern.
  5. Geteilte Listen nach clone(): Eine „Kopie“ ändert das Original. Fix: tiefe Kopie oder unveränderliche Objekte.
  6. Prototype in Singleton: Man erwartet ein neues Objekt pro Request und bekommt immer dasselbe. Fix: ObjectProvider oder @Lookup.

Diagnose: Werkzeuge und Befehle

  • Grep im Review: static .* INSTANCE, getInstance(), nicht-finale static-Felder. Jedes ist ein Kandidat für globalen Zustand.
  • SonarQube: Regeln zu veränderbaren statischen Feldern und zu clone()-Overrides.
  • JUnit: Tests in zufälliger Reihenfolge laufen lassen (@TestMethodOrder(MethodOrderer.Random.class)). Reihenfolge-Abhängigkeiten werden sichtbar.
  • Spring Boot Actuator: /actuator/beans zeigt alle Beans mit Scope und Abhängigkeiten.
  • Heap Dump: Mehrere Instanzen einer „Singleton“-Klasse zeigen ClassLoader-Probleme.

Senior-Punkte

  1. „Eine Instanz“ ist eine Konfigurationsfrage, kein Klassendesign. Darum lieber Spring-Scope als statisches Singleton.
  2. Erzeugung und Nutzung trennen. Wer ein Objekt nutzt, sollte es nicht bauen. Das ist die Basis für Tests.
  3. Builder nicht automatisch. Für drei Pflichtfelder ist ein Record klarer. Builder lohnt sich bei vielen optionalen Feldern und Validierung.
  4. Unveränderliche Objekte lösen die meisten Prototype-Probleme. Kopieren wird dann unnötig.
  5. Factory-Logik an einer Stelle. Ein switch in einer Factory ist okay. Derselbe switch an vielen Stellen nicht.
  6. Spring-Beans sind zustandslos. Zustand pro Request gehört in Parameter, in den Request-Scope oder in die Datenbank.
