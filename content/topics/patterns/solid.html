SOLID

Patterns · Tier 1 · Quellen: Robert C. Martin, „Clean Architecture“ (Teil III, Kapitel 7–11); Barbara Liskov / Jeannette Wing, „A Behavioral Notion of Subtyping“ (ACM TOPLAS 1994); Martin Fowler, Refactoring-Katalog (refactoring.com/catalog); Spring Framework Reference (Dependency Injection); JLS 17 (sealed classes, records)

Kern: SOLID ist eine Gruppe von fünf Design-Prinzipien für Klassen und Module. Sie löst ein Problem: Code soll sich ändern lassen, ohne dass an vielen Stellen etwas bricht. Im Code-Review sind sie die Sprache, um zu sagen, warum ein Stück Code schlecht ist.

1. Wo sitzen die SOLID-Prinzipien?

  1. S – Single Responsibility: Jede Klasse hat einen Grund zur Änderung. Der Controller ändert sich nur für HTTP, der Service nur für Regeln.
  2. O – Open/Closed: Neue Rabatt-Typen kommen als neue Klasse dazu. InvoiceService bleibt unverändert.
  3. L – Liskov Substitution: Jede DiscountPolicy muss sich wie eine DiscountPolicy verhalten. Der Service darf keinen Unterschied merken.
  4. I – Interface Segregation: Notifier hat eine Methode. Niemand muss Methoden implementieren, die er nicht braucht.
  5. D – Dependency Inversion: Der Service hängt von Interfaces ab. Spring injiziert die echte Klasse, der Test eine Fake-Klasse.

2. Die Reise einer Änderung (die Geschichte zum Merken)

  1. Die Anforderung kommt: Mitarbeitende bekommen 50 % Rabatt. Das ist ein neuer Kundentyp.
  2. Im schlechten Design steht die Logik in switch-Blöcken über den Code verteilt. Jede Stelle muss man finden und ändern. Das ist Shotgun Surgery, also eine Änderung mit vielen kleinen Schnitten.
  3. Der Bug entsteht: Eine Stelle wird vergessen. Der default-Zweig wirft eine Exception, erst in Produktion.
  4. Im SOLID-Design ist der Rabatt eine Abstraktion (DiscountPolicy). Die neue Regel ist eine neue Klasse. Das ist OCP.
  5. Der Service bleibt gleich, weil er nur das Interface kennt (DIP). Der Test braucht keinen Mail-Server, weil Notifier ein Fake sein kann.
  6. Das Ergebnis: Die Änderung ist lokal, klein und mit einem Test abgesichert.

3. Beispiel: Verstösse sichtbar machen

static int resizeTo5x10(Rectangle r) { r.setWidth(5); r.setHeight(10); return r.area(); }
// LSP: Square extends Rectangle, setWidth setzt auch die Höhe
resizeTo5x10(new Rectangle());  resizeTo5x10(new Square());
area(new Rect(5, 10)); area(new Sq(5));          // Fix: sealed interface Shape + records

// ISP: Repository<T> mit find/save/delete, AuditLogRepo kann kein delete
repo.delete(7);
// Fix: Reader<T> und Writer<T>, AuditLog implementiert nur beide

// OCP + DIP: InvoiceServiceBad hat switch(customerType) und new SmtpMailer()
new InvoiceServiceBad().bill("a@b.ch", "VIP", 100);
new InvoiceServiceBad().total("STAFF", 100);
DiscountPolicy staff = a -> a * 0.5;
new InvoiceService(staff, (to, text) -> sent.add(to + ": " + text)).bill("a@b.ch", 100);
1) LSP
Rectangle 5x10 area = 50
Square    5x10 area = 100
fixed: Rect(5,10)=50 Sq(5)=25
2) ISP
delete -> java.lang.UnsupportedOperationException: audit log is append-only
fixed: AuditLog has no delete(): true
3) OCP + DIP
bad service in test -> no SMTP server in test
new type STAFF -> IllegalArgumentException: STAFF
fixed service with fake notifier -> [a@b.ch: Total 50.0]

Echte Ausgabe, OpenJDK/Oracle JDK 17.0.3 (java SolidDemo.java).

  1. LSP: Der Aufrufer erwartet 50. Mit Square bekommt er 100. Der Compiler merkt nichts. Der Fehler zeigt sich erst zur Laufzeit.
  2. LSP-Fix: Rect und Sq sind unveränderliche Records ohne Vererbung. Es gibt keine Setter, die man brechen kann.
  3. ISP: AuditLogRepo muss delete implementieren und wirft eine Exception. Das ist auch ein LSP-Verstoss.
  4. ISP-Fix: Mit kleinen Interfaces hat AuditLog gar kein delete. Der Fehler ist jetzt ein Compile-Fehler.
  5. DIP: Der schlechte Service erzeugt SmtpMailer selbst. Im Test gibt es keinen Server, also scheitert der Test.
  6. OCP: Der neue Typ STAFF trifft den default-Zweig. Der Fix ist eine neue DiscountPolicy, kein Edit.

4. Details, die Interviewer fragen

S – Single Responsibility Principle (SRP). Martin definiert es so: Ein Modul ist einem Akteur verantwortlich, also einer Gruppe von Menschen, die Änderungen verlangt. „Macht nur eine Sache“ ist die falsche Kurzform.

// schlecht: drei Akteure (Fachbereich, Reporting, DBA) in einer Klasse
class Employee {
  Money calculatePay() { ... }       // Fachbereich Lohn
  String reportHours() { ... }        // Reporting
  void save() { jdbc.update(...); }   // Datenbank-Team
}
// besser: eine Klasse pro Akteur, Daten getrennt
record Employee(EmployeeId id, Hours hours) {}
class PayCalculator { Money calculate(Employee e) { ... } }
class HourReporter  { String report(Employee e) { ... } }
interface EmployeeRepository { void save(Employee e); }
  1. Warnzeichen: Klassennamen wie Manager, Helper, Utils. Viele Imports aus verschiedenen Schichten. Viele Gründe in der Git-Historie.
  2. Refactoring: Extract Class (Fowler), also einen Teil in eine neue Klasse verschieben.

O – Open/Closed Principle (OCP). Ein Modul ist offen für Erweiterung und geschlossen für Änderung. Neues Verhalten kommt durch neuen Code, nicht durch Edits in getestetem Code.

// schlecht: jeder neue Typ ändert diese Methode
double total(String type, double amount) {
  switch (type) { case "REGULAR": return amount; case "VIP": return amount * 0.9;
                  default: throw new IllegalArgumentException(type); }
}
// besser: Strategy; neuer Typ = neue Klasse
interface DiscountPolicy { double apply(double amount); }
@Component("VIP") class VipDiscount implements DiscountPolicy { public double apply(double a) { return a * 0.9; } }
@Service class InvoiceService {
  private final Map<String, DiscountPolicy> policies;   // Spring füllt die Map: Bean-Name → Bean
  InvoiceService(Map<String, DiscountPolicy> policies) { this.policies = policies; }
}
  1. Refactoring: Replace Conditional with Polymorphism (Fowler).
  2. Grenze: Ein switch an genau einer Stelle ist oft okay. Erst wiederholte switch-Blöcke (Repeated Switches) sind ein Smell.

L – Liskov Substitution Principle (LSP). Ein Subtyp muss überall funktionieren, wo der Basistyp erwartet wird. Er darf Vorbedingungen nicht verschärfen und Nachbedingungen nicht abschwächen.

// schlecht: Square bricht die Erwartung "setWidth ändert nur die Breite"
class Square extends Rectangle {
  @Override void setWidth(int w) { this.w = w; this.h = w; }
}
// besser: keine Vererbung, unveränderliche Typen
sealed interface Shape permits Rect, Sq {}
record Rect(int w, int h) implements Shape {}
record Sq(int side) implements Shape {}
  1. Typische Verstösse: UnsupportedOperationException in einer Unterklasse, instanceof-Prüfungen beim Aufrufer, leere Overrides.
  2. JDK-Beispiel: List.of(...) ist eine List, aber add wirft UnsupportedOperationException. Die List-Doku erlaubt das als „optional operation“. Der Vertrag ist also schwach, nicht gebrochen.
  3. Regel: LSP betrifft das Verhalten, nicht die Signatur. Der Compiler prüft nur die Signatur.

I – Interface Segregation Principle (ISP). Kein Client soll von Methoden abhängen, die er nicht nutzt. Viele kleine Interfaces sind besser als ein grosses.

// schlecht: ein Read-only-Client hängt von save/delete ab
interface Repository<T> { T find(long id); void save(T t); void delete(long id); }
// besser: Rollen-Interfaces
interface Reader<T> { T find(long id); }
interface Writer<T> { void save(T t); }
class ReportService { ReportService(Reader<Report> reader) { ... } }
  1. Vorteil: Ein Mock im Test hat eine Methode statt zwölf. Änderungen an save zwingen ReportService nicht zum Neukompilieren.
  2. Spring Data: Repository ist ein leeres Marker-Interface. Man kann nur die Methoden deklarieren, die man braucht, statt JpaRepository mit allen Methoden.

D – Dependency Inversion Principle (DIP). High-Level-Module hängen nicht von Low-Level-Modulen ab. Beide hängen von Abstraktionen ab. Die Abstraktion gehört dem High-Level-Modul.

// schlecht: Geschäftslogik hängt direkt an Technik
class InvoiceService { private final SmtpMailer mailer = new SmtpMailer(); }
// besser: Interface im Domain-Paket, Implementierung im Infrastruktur-Paket
interface Notifier { void send(String to, String text); }            // domain
@Component class SmtpNotifier implements Notifier { ... }             // infrastructure
@Service class InvoiceService {
  private final Notifier notifier;
  InvoiceService(Notifier notifier) { this.notifier = notifier; }     // Constructor Injection
}
  1. DIP vs DI: DIP ist ein Prinzip über die Richtung der Abhängigkeit. Dependency Injection ist eine Technik, um Objekte von aussen zu übergeben. IoC Container wie Spring automatisieren DI.
  2. Constructor Injection: Die Spring-Doku empfiehlt sie für Pflicht-Abhängigkeiten. Felder können final sein, und Tests brauchen kein Spring.
  3. Hexagonale Architektur ist DIP auf Architekturebene: Die Domain definiert Ports, die Adapter implementieren sie.

5. Vergleich

  • SOLID vs Design Patterns: SOLID sind Prinzipien (das Warum). Patterns sind bewährte Lösungen (das Wie). Strategy ist eine Umsetzung von OCP.
  • SOLID vs DRY: DRY (Don't Repeat Yourself) heisst, Wissen nicht doppelt zu halten. Zu viel DRY verletzt SRP: zwei Akteure teilen dann Code, der sich verschieden ändern muss.
  • SOLID vs KISS/YAGNI: YAGNI (You Aren't Gonna Need It) bremst SOLID. Ein Interface mit nur einer Implementierung und ohne Test-Fake ist oft unnötig.
  • SOLID vs Clean Architecture: SOLID gilt für Klassen. Clean Architecture überträgt DIP auf Schichten und Komponenten.
  • Vererbung vs Komposition: Viele LSP-Probleme kommen aus Vererbung. „Composition over Inheritance“ (GoF, Kapitel 1) vermeidet sie.

6. In der Produktion

  1. Gleiche Änderung, viele Dateien: Ein neuer Typ braucht Edits in fünf Klassen. Ursache: OCP-Verstoss mit verteilten switch. Fix: Polymorphie oder eine Map von Strategien.
  2. Tests brauchen Datenbank und Mail-Server: Ursache: DIP-Verstoss mit new im Service. Fix: Constructor Injection und Interfaces für Infrastruktur.
  3. Merge-Konflikte in einer Riesenklasse: Fünf Teams ändern OrderService. Ursache: SRP-Verstoss. Fix: nach Akteuren teilen.
  4. Unterklasse wirft im Betrieb: UnsupportedOperationException aus einer Implementierung. Ursache: LSP/ISP-Verstoss. Fix: Interface teilen.
  5. Interface-Explosion: Jede Klasse hat ein Interface mit genau einer Implementierung. Der Code wird schwer zu navigieren. Fix: Interface nur an echten Grenzen (Infrastruktur, Plug-ins, Tests).

7. Diagnose: Werkzeuge und Befehle

  • SonarQube: Regeln für Komplexität (Cognitive Complexity), zu viele Methoden, zu viele Abhängigkeiten einer Klasse.
  • ArchUnit: Tests für Architekturregeln, z. B. „domain hängt nicht von infrastructure ab“ (DIP prüfen).
  • Git-Historie: git log --format= --name-only | sort | uniq -c | sort -rn | head zeigt Dateien mit den meisten Änderungen. Oft verletzen sie SRP.
  • IntelliJ: Dependency Structure Matrix und „Analyze Dependencies“ zeigen Zyklen.
  • Review-Fragen: Wie viele Gründe hat diese Klasse für eine Änderung? Was muss ich für einen neuen Typ ändern? Kann ich das ohne Spring testen?

8. Senior-Punkte

  1. SOLID ist ein Werkzeug, kein Ziel. Abstraktion kostet Lesbarkeit. Sie lohnt sich dort, wo sich Code wirklich ändert.
  2. OCP gilt für erwartete Änderungen. Man kann nicht gegen alles offen sein. Erste Änderung: einfach ändern. Zweite gleiche Änderung: abstrahieren.
  3. DIP ist der wichtigste Punkt für Testbarkeit. Infrastruktur (DB, HTTP, Zeit, Zufall) gehört hinter ein Interface.
  4. LSP ist ein Vertrag über Verhalten. Er wird mit Contract-Tests geprüft: dieselbe Test-Suite läuft gegen jede Implementierung.
  5. SRP denkt in Akteuren, nicht in Methodenzahl. Das hilft im Review, eine Trennung sachlich zu begründen.
  6. Im Review Prinzip und Folge nennen: „Das verletzt DIP, darum braucht der Test einen SMTP-Server.“ So wird Kritik konkret.

9. Aus dem Projekt

„In Code-Reviews achte ich besonders auf DIP: Infrastruktur wie Storage oder Mail kommt per Constructor Injection hinter ein Interface, damit Unit-Tests ohne Container laufen.“ (Prüfen und durch dein echtes Beispiel ersetzen, z. B. Code-Reviews in Bitbucket bei CARIAD oder die Code-Quality-Standards mit SonarQube bei Unisys.)

10. Fallen

  • „SRP heisst: eine Klasse macht nur eine Sache.“ → Ungenau. SRP heisst: ein Grund zur Änderung, also ein Akteur.
  • „DIP und Dependency Injection sind dasselbe.“ → Falsch. DIP ist die Richtung der Abhängigkeit. DI ist eine Technik dafür.
  • „Square extends Rectangle ist korrekt, weil ein Quadrat ein Rechteck ist.“ → Falsch bei veränderbaren Objekten. Das Verhalten der Setter bricht LSP.
  • „OCP heisst, Code nie ändern.“ → Falsch. Bugs fixt man direkt. OCP betrifft neue Varianten von Verhalten.
  • „Jede Klasse braucht ein Interface.“ → Falsch. Ein Interface lohnt sich an Grenzen und für Tests, nicht für jede Klasse.
  • „Wenn es kompiliert, ist LSP erfüllt.“ → Falsch. Der Compiler prüft Signaturen, nicht Verhalten.

11. Fragen

Was ist SOLID?

Fünf Prinzipien für änderbaren Code: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.

Was heisst Single Responsibility genau?

Eine Klasse ist einem Akteur verantwortlich und hat damit einen Grund zur Änderung. Mehrere Akteure in einer Klasse führen zu Konflikten und Seiteneffekten.

Woran erkennen Sie einen SRP-Verstoss im Review?

Viele Abhängigkeiten aus verschiedenen Schichten, Namen wie Manager oder Utils, Methoden, die sich nicht gegenseitig nutzen. Oft auch viele Änderungen in der Git-Historie.

Erklären Sie Open/Closed mit einem Beispiel.

Rabatte als Interface DiscountPolicy. Ein neuer Rabatt ist eine neue Klasse. InvoiceService bleibt unverändert, statt einen switch zu erweitern.

Welches Pattern setzt OCP oft um?

Strategy, auch Template Method und Decorator. Alle erlauben neues Verhalten ohne Edit am Aufrufer.

Was ist das Liskov-Prinzip?

Ein Subtyp muss überall den Basistyp ersetzen können, ohne dass der Aufrufer es merkt. Vorbedingungen nicht verschärfen, Nachbedingungen nicht abschwächen.

Warum verletzt Square extends Rectangle LSP?

Der Aufrufer erwartet, dass setWidth nur die Breite ändert. Square ändert beide Seiten. Bei 5×10 kommt 100 statt 50 heraus.

Ist eine UnsupportedOperationException immer ein LSP-Verstoss?

Nicht immer. Wenn der Basisvertrag die Operation als optional markiert, wie bei Collection.add, ist es erlaubt. Bei eigenen Interfaces ist es meist ein Design-Fehler.

Was ist Interface Segregation?

Clients sollen nur von Methoden abhängen, die sie nutzen. Lieber mehrere kleine Rollen-Interfaces als ein grosses.

Was ist Dependency Inversion?

High-Level-Logik und Low-Level-Technik hängen beide von einer Abstraktion ab. Die Abstraktion gehört zur Logik, nicht zur Technik.

Unterschied zwischen DIP, DI und IoC?

DIP ist das Prinzip. DI ist die Technik, Abhängigkeiten von aussen zu übergeben. IoC heisst, ein Framework steuert Erzeugung und Ablauf, z. B. der Spring Container.

Warum Constructor Injection statt Field Injection?

Pflicht-Abhängigkeiten sind sichtbar, Felder können final sein, und der Test braucht kein Spring. Zu viele Konstruktor-Parameter zeigen zudem einen SRP-Verstoss.

Wie hängen SOLID und Testbarkeit zusammen?

DIP erlaubt Fakes statt echter Infrastruktur. SRP und ISP machen Klassen und Mocks klein. LSP erlaubt Contract-Tests für alle Implementierungen.

Kann man SOLID übertreiben?

Ja. Interfaces ohne zweite Implementierung, zu viele kleine Klassen und Indirektionen machen Code schwer lesbar. YAGNI ist das Gegengewicht.

Wie verhält sich SRP zu DRY?

Code, der gleich aussieht, aber verschiedenen Akteuren gehört, sollte nicht zusammengelegt werden. Sonst bricht eine Änderung für Akteur A die Logik von Akteur B.

Wie sieht DIP auf Architekturebene aus?

Als hexagonale oder Clean Architecture. Die Domain definiert Ports als Interfaces. Adapter für DB oder HTTP implementieren sie.

Wie prüfen Sie Architekturregeln automatisch?

Mit ArchUnit-Tests, z. B. „Klassen in domain dürfen nicht von infrastructure abhängen“. Sie laufen im normalen Build.

Welches Fowler-Refactoring hilft bei SRP?

Extract Class, dazu Move Function und Move Field. Bei OCP: Replace Conditional with Polymorphism.

Wie hilft Spring bei OCP?

Spring kann alle Beans eines Typs als List oder Map injizieren. Eine neue Strategie ist dann nur eine neue @Component.

Ist ein switch immer ein OCP-Verstoss?

Nein. Ein switch an einer zentralen Stelle, z. B. einer Factory, ist okay. Problematisch ist derselbe switch an vielen Stellen.

Wie hilft Java 17 bei LSP-Problemen?

Records sind unveränderlich, also gibt es keine brechenden Setter. Sealed Interfaces legen die erlaubten Subtypen fest.

Wie formulieren Sie SOLID-Kritik im Code-Review?

Prinzip, Folge und Vorschlag nennen. Beispiel: „new SmtpMailer im Service verletzt DIP, darum braucht der Test einen Server. Vorschlag: Notifier per Konstruktor.“

Szenario: Ein Service hat 14 Konstruktor-Parameter. Was sagen Sie im Review?

Das ist ein SRP-Signal. Ich suche Gruppen von Abhängigkeiten, die zusammen genutzt werden, und schlage Extract Class vor. Oft entstehen zwei bis drei kleinere Services.

Szenario: Jeder neue Report-Typ braucht Änderungen in Parser, Validator und Writer. Was tun Sie?

Ein Interface pro Report-Typ, das Parsen, Validieren und Schreiben kapselt. Neue Typen sind dann neue Klassen. Die alten Klassen bleiben gleich.

Szenario: Unit-Tests eines Services brauchen eine echte Datenbank. Wie lösen Sie das?

Die DB-Zugriffe hinter ein Repository-Interface legen und per Konstruktor injizieren. Unit-Tests nutzen einen Fake, Integrationstests prüfen das echte Repository mit Testcontainers.
