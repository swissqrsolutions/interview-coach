Onion und Clean Architecture

Patterns · Tier 1 · Quellen: Jeffrey Palermo „The Onion Architecture“ Part 1 und Part 3 (2008); Robert C. Martin „The Clean Architecture“ (Clean Coder Blog, 2012); Alistair Cockburn „Hexagonal Architecture“ (2005); Martin Fowler bliki „PresentationDomainDataLayering“; ArchUnit User Guide (Onion Architecture)

Kern: Onion (Jeffrey Palermo, 2008) und Clean Architecture (Robert C. Martin, 2012) ordnen Code in Ringen um das Domänenmodell. Beide folgen derselben Regel wie Hexagonal: Quellcode-Abhängigkeiten zeigen nur nach innen. Sie unterscheiden sich vor allem in den Namen der inneren Ringe und darin, wie genau sie die Mitte vorschreiben.

1. Wo sitzen Onion und Clean?

  1. Entities (Clean): unternehmensweite Geschäftsregeln. Beispiel: Loan.isAffordable(). Sie ändern sich, wenn sich das Geschäft ändert, nicht die App.
  2. Use Cases (Clean): anwendungsspezifische Regeln, also der Ablauf eines Anwendungsfalls. Beispiel: CheckLoanInteractor.
  3. Interface Adapters (Clean): Controller, Presenter, Gateways. Sie wandeln Daten zwischen Use Case und Aussenwelt um.
  4. Frameworks & Drivers (Clean): Web-Framework, DB, Geräte. Martin nennt sie Details.
  5. Domain Model (Onion): das Objektmodell im Zentrum. Darum Domain Services und Application Services, die auch die Interfaces für Infrastruktur definieren.
  6. Aussen (Onion): UI, Infrastructure und Tests liegen im gleichen äusseren Ring. Data Access ist dort, nicht unten.

2. Die Reise eines Use Cases über die Grenze (die Geschichte zum Merken)

  1. Controller: Er nimmt das Formular an. Er baut ein einfaches Request Model (z. B. ein Record). Er ruft den Input Port.
  2. Input Port: ein Interface im Use-Case-Ring. Der Controller kennt nur dieses Interface.
  3. Interactor: implementiert den Input Port. Er holt die Regel aus der Entity und berechnet das Ergebnis.
  4. Output Port: Der Interactor muss das Ergebnis nach aussen geben. Er darf den Presenter nicht kennen. Also ruft er ein Interface im eigenen Ring.
  5. Presenter: implementiert den Output Port im äusseren Ring. Er formatiert ein View Model. Kontrollfluss geht nach aussen, Abhängigkeit nach innen: Dependency Inversion.
  6. Was über die Grenze geht: einfache Datenstrukturen. Martin: keine Entities und keine DB-Zeilen durchreichen.

3. Beispiel: Clean-Fluss ausführen, dann Pakete erkennen

// Entities
final class Loan { static boolean isAffordable(long incomePerYear, long rate) { return rate * 12 <= incomePerYear / 3; } }
// Use Cases
record CheckLoanRequest(long incomePerYear, long monthlyRate) { }
record CheckLoanResponse(boolean approved, long maxMonthlyRate) { }
interface CheckLoanInputPort  { void check(CheckLoanRequest req); }
interface CheckLoanOutputPort { void present(CheckLoanResponse res); }   // gehört dem Use Case
final class CheckLoanInteractor implements CheckLoanInputPort { ... out.present(new CheckLoanResponse(ok, max)); }
// Interface Adapters
final class LoanPresenter implements CheckLoanOutputPort { ... vm.text = "Bewilligt ..." }
final class LoanController { ... in.check(new CheckLoanRequest(income, rate)); }
// Frameworks & Drivers: main verdrahtet
var presenter  = new LoanPresenter();
var controller = new LoanController(new CheckLoanInteractor(presenter));

  1. Die Reihenfolge ist Controller → Interactor → Presenter. Der Kontrollfluss geht durch den Use Case nach aussen.
  2. Der Interactor gibt nichts zurück (void). Er „pusht“ das Ergebnis über den Output Port.

Drei Paketbäume. Welche Architektur ist es?

Baum 1
com.acme.billing
├── core
│   ├── domain
│   │   ├── model        Invoice, InvoiceLine, Money
│   │   └── services     TaxCalculator
│   └── application
│       ├── services     IssueInvoiceService
│       └── interfaces   IInvoiceRepository, IMailSender
├── infrastructure
│   ├── persistence      JpaInvoiceRepository implements IInvoiceRepository
│   └── mail             SmtpMailSender implements IMailSender
├── web                  InvoiceController
└── (tests)              liegen aussen, neben web und infrastructure

Antwort: Onion. Erkennbar an core gegen infrastructure, an den Ringen domain/model → domain/services → application/services, und daran, dass die Interfaces im Kern liegen und Infrastruktur sie implementiert. Es gibt keine Begriffe „Port“, „Adapter“, „Presenter“.

Baum 2
com.acme.billing
├── entities             Invoice, TaxRule
├── usecases
│   └── issueinvoice
│       ├── IssueInvoiceInputPort
│       ├── IssueInvoiceOutputPort
│       ├── IssueInvoiceInteractor
│       ├── IssueInvoiceRequest
│       └── IssueInvoiceResponse
├── interfaceadapters
│   ├── controllers      IssueInvoiceController
│   ├── presenters       IssueInvoicePresenter, InvoiceViewModel
│   └── gateways         InvoiceGateway (Interface), JpaInvoiceGateway
└── frameworks
    ├── web              SpringWebConfig
    └── db               JPA-Konfiguration

Antwort: Clean Architecture. Die vier Kreise sind wörtlich da: entities, usecases, interfaceadapters, frameworks. Typisch sind Interactor, Input/Output Port, Request/Response Model und Presenter mit View Model.

Baum 3
com.acme.billing
├── domain               Invoice, Money, TaxPolicy
├── application
│   ├── port
│   │   ├── in           IssueInvoiceUseCase
│   │   └── out          LoadCustomerPort, SaveInvoicePort, SendMailPort
│   └── service          IssueInvoiceService
└── adapter
    ├── in
    │   ├── web          InvoiceController
    │   └── batch        MonthlyInvoiceJob
    └── out
        ├── persistence  InvoicePersistenceAdapter
        └── mail         SmtpMailAdapter

Antwort: Hexagonal (Ports and Adapters). Erkennbar an port/in und port/out sowie adapter/in (driving) und adapter/out (driven). Zwei Seiten, symmetrisch. Ein Batch-Job ist einfach ein zweiter driving Adapter.

Zum Vergleich klassisch Layered: oben controller/, service/, repository/, entity/. Der Service importiert das Repository direkt, die Entity hat @Entity. Keine Interfaces gehören der Domäne.

4. Details, die Interviewer fragen

  1. Die Dependency Rule (Martin): Quellcode-Abhängigkeiten zeigen nur nach innen. Nichts in einem inneren Kreis kennt einen Namen aus einem äusseren Kreis.
  2. Palermos vier Grundsätze (Onion): Die Anwendung ist um ein unabhängiges Objektmodell gebaut. Innere Schichten definieren Interfaces, äussere implementieren sie. Die Kopplung zeigt zur Mitte. Der Kern ist ohne Infrastruktur kompilier- und lauffähig.
  3. Was wirklich gleich ist: Domäne in der Mitte, Infrastruktur aussen, Dependency Inversion an der Grenze, Tests ohne DB. Martin schreibt selbst, dass Clean Hexagonal, Onion und andere vereint.
  4. Unterschied 1, Struktur der Mitte: Hexagonal sagt nichts über das Innere. Onion schreibt Ringe vor: Domain Model, Domain Services, Application Services. Clean trennt Entities (unternehmensweit) von Use Cases (anwendungsspezifisch).
  5. Unterschied 2, Symmetrie: Hexagonal denkt in zwei Seiten, driving und driven. Onion und Clean denken in Ringen, nicht in Seiten.
  6. Unterschied 3, Ausgabe: Clean nutzt einen Output Port und Presenter. Der Use Case gibt nichts zurück. In Hexagonal und Onion gibt ein Service meist einen Wert zurück.
  7. Unterschied 4, Datenformat: Clean verlangt eigene Request/Response Models an der Grenze. Onion erlaubt das Domänenmodell weiter aussen zu nutzen.
  8. Unterschied 5, Platz der Tests: Onion legt Tests ausdrücklich in den äusseren Ring, neben UI und Infrastruktur. Hexagonal sieht Tests als driving Adapter. Gemeint ist dasselbe: Tests sind ein weiterer Client des Kerns.
  9. „Nur vier Kreise?“ Martin: nein, die Kreise sind schematisch. Man darf mehr haben, solange die Regel gilt.
  10. Entities in Clean ≠ JPA-Entities. Eine Clean-Entity ist ein Objekt mit Geschäftsregeln. Sie kennt keine Annotation einer DB.
  11. Gateway: Clean-Name für ein Interface zu DB oder externem Dienst. In Hexagonal heisst das driven Port, in Onion Repository-Interface im Kern.
  12. Screaming Architecture: Martins Idee, dass die oberste Ebene die Fachlichkeit zeigt (billing, order), nicht das Framework.

5. Vergleich

  • Hexagonal (2005): innen/aussen, Ports und Adapter, driving/driven. Mitte nicht vorgegeben.
  • Onion (2008): Ringe mit festen Namen um das Domänenmodell. Interfaces im Kern. UI, Infrastruktur, Tests zusammen aussen.
  • Clean (2012): vier schematische Kreise, Dependency Rule, Interactor, Input/Output Port, Presenter, eigene Datenstrukturen an Grenzen.
  • Layered: Stapel nach unten bis zur DB. Mit Dependency Inversion wird es praktisch Onion.
  • Gleich bei allen drei: Abhängigkeit zur Domäne, Technik austauschbar, Kern ohne Framework testbar.

6. In der Produktion

  1. Zeremonie: Für jeden Use Case fünf Dateien (Input Port, Output Port, Interactor, Request, Response). Bei einfachen Lesefällen zu viel. Lösung: Clean-Strenge nur, wo Logik ist; Queries direkter.
  2. Presenter in REST-APIs: Ein Output Port für JSON-Antworten fühlt sich künstlich an. Viele Teams lassen den Interactor ein Response-Objekt zurückgeben. Das ist ein bewusster Kompromiss, keine Verletzung der Dependency Rule.
  3. Leere Ringe: domain/services ist leer, application reicht nur durch. Lösung: Ringe nur anlegen, wenn sie Inhalt haben.
  4. Geteilte Entities: Mehrere Services teilen eine Entity-Bibliothek „weil Clean Entities unternehmensweit sind“. Das koppelt Deployments. Lösung: pro Bounded Context eigene Entities.
  5. Framework schleicht nach innen: @Entity, @JsonProperty, Pageable im Use-Case-Ring. Lösung: ArchUnit-Regel und Code-Review auf Imports.
  6. Namen ohne Wirkung: Pakete heissen core, aber core importiert infrastructure. Lösung: Richtung messen (jdeps, ArchUnit), nicht Namen glauben.

7. Diagnose: Werkzeuge und Befehle

  • ArchUnit onionArchitecture(): domainModels(...), domainServices(...), applicationServices(...), adapter(name, packages). Passt für Onion, Hexagonal und Clean, wenn man die Pakete zuordnet.
  • Clean mit Modulen erzwingen: Je Ring ein Maven/Gradle-Modul. Dann kann usecases frameworks gar nicht importieren, der Compiler verhindert es.
  • jdeps -verbose:package: listet echte Paket-Abhängigkeiten. Jede Zeile von innen nach aussen ist ein Verstoss.
  • Erkennen im Review: Suche nach den Wörtern. port/adapter → Hexagonal. core/infrastructure mit domain/services → Onion. usecases/interactor/presenter/gateway → Clean.
  • Dann die Richtung prüfen: Der Name sagt, was gewollt ist. Die Imports sagen, was wirklich ist.

8. Senior-Punkte

  1. Im Interview zuerst die Gemeinsamkeit: Alle drei sind Dependency Inversion um eine Domäne. Dann die Unterschiede in Vokabular und Vorgaben.
  2. Nicht dogmatisch: Die Dependency Rule ist das Wichtige. Die genaue Zahl der Ringe ist es nicht.
  3. Kosten gegen Nutzen: Clean bringt viel Struktur. Sie lohnt sich bei langlebiger, komplexer Fachlogik, nicht bei einem CRUD-Adapter.
  4. Ein Stil pro Codebasis. Mischformen mit ports hier und usecases da verwirren neue Kollegen mehr als jede Wahl.
  5. Architektur als Test. Ohne ArchUnit oder Module bleibt jeder Stil nur ein Paketname.
  6. Screaming zuerst: Oben die Fachlichkeit, darunter der Stil. So bleibt der Code nach Fachgrenzen schneidbar.

10. Fallen

  • „Onion, Clean und Hexagonal sind völlig verschiedene Architekturen.“ → Falsch. Gleiche Kernregel, verschiedene Begriffe und Detailtiefe.
  • „Clean Architecture hat genau vier Schichten.“ → Falsch. Martin sagt, die Kreise sind schematisch.
  • „Entities in Clean sind JPA-Entities.“ → Falsch. Es sind Geschäftsobjekte ohne DB-Wissen.
  • „In Onion ist die DB die innerste Schicht.“ → Falsch. Data Access liegt aussen, der Kern definiert nur Interfaces.
  • „Wenn das Paket core heisst, ist es Onion.“ → Falsch. Entscheidend ist die Richtung der Imports.
  • „Der Use Case darf den Presenter aufrufen, weil er ihn braucht.“ → Nur über einen Output Port aus dem Use-Case-Ring. Sonst bricht die Dependency Rule.

11. Fragen

Was ist die Onion Architecture?

Palermos Stil von 2008: Ringe um ein unabhängiges Domänenmodell. Innere Ringe definieren Interfaces, äussere implementieren sie, die Kopplung zeigt zur Mitte.

Was ist die Clean Architecture?

Robert C. Martins Stil von 2012: vier schematische Kreise Entities, Use Cases, Interface Adapters, Frameworks & Drivers. Zentral ist die Dependency Rule.

Wie lautet die Dependency Rule?

Quellcode-Abhängigkeiten zeigen nur nach innen. Ein innerer Kreis kennt keinen Namen aus einem äusseren Kreis.

Was ist der echte Unterschied zwischen Onion, Clean und Hexagonal?

Die Regel ist gleich. Hexagonal gibt nur innen/aussen mit Ports vor. Onion benennt die inneren Ringe. Clean trennt Entities und Use Cases und fügt Output Port und Presenter hinzu.

Was sind Entities in Clean Architecture?

Objekte mit unternehmensweiten Geschäftsregeln. Sie sind am stabilsten und kennen keine Anwendung und keine DB.

Was sind Use Cases?

Anwendungsspezifische Regeln: der Ablauf eines Anwendungsfalls. Sie orchestrieren Entities und sprechen über Ports mit der Aussenwelt.

Was ist ein Interactor?

Die Klasse, die einen Use Case umsetzt. Sie implementiert den Input Port und ruft den Output Port.

Warum braucht Clean einen Output Port und Presenter?

Der Use Case muss Ergebnisse nach aussen geben, darf aber den Presenter nicht kennen. Also definiert er ein Interface, das der Presenter implementiert.

Welche Daten dürfen über eine Grenze?

Einfache Datenstrukturen wie Request- und Response-Models. Keine Entities und keine DB-Zeilen.

Wo liegt in Onion der Datenzugriff?

Im äusseren Ring bei Infrastruktur. Der Kern definiert nur das Repository-Interface.

Was sind Palermos Grundsätze?

Unabhängiges Objektmodell in der Mitte; innere Schichten definieren Interfaces, äussere implementieren; Kopplung zur Mitte; Kern ohne Infrastruktur kompilier- und lauffähig.

Wie erkennen Sie Hexagonal an einem Paketbaum?

An port/in, port/out, adapter/in, adapter/out. Zwei Seiten: driving und driven.

Wie erkennen Sie Onion an einem Paketbaum?

An core gegen infrastructure, mit domain/model, domain/services, application/services und Interfaces im Kern.

Wie erkennen Sie Clean an einem Paketbaum?

An entities, usecases mit Interactor und Input/Output Ports, presenters, gateways, frameworks.

Reicht der Paketname, um die Architektur zu bestätigen?

Nein. Man muss die Imports prüfen, z. B. mit jdeps oder ArchUnit. Der Name zeigt nur die Absicht.

Hat Clean genau vier Kreise?

Nein. Martin sagt, sie sind schematisch. Es können mehr sein, solange die Dependency Rule gilt.

Was ist ein Gateway in Clean?

Ein Interface für Datenzugriff oder externe Dienste. Es entspricht einem driven Port in Hexagonal.

Was ist Screaming Architecture?

Die oberste Paketstruktur zeigt die Fachlichkeit, nicht das Framework. Man sieht sofort: das ist ein Billing-System.

Wann lohnt sich Clean nicht?

Bei CRUD ohne echte Regeln. Die vielen Ports und Modelle kosten mehr, als sie schützen.

Darf ein Interactor ein Ergebnis zurückgeben statt einen Presenter zu rufen?

Das ist ein verbreiteter Kompromiss für REST-APIs. Die Dependency Rule bleibt erfüllt, nur das Presenter-Muster entfällt.

Wie erzwingen Sie die Dependency Rule technisch?

Mit ArchUnit onionArchitecture() im CI oder mit einem Build-Modul pro Ring. Dann verhindert der Compiler falsche Imports.

Szenario: Im Code-Review hat der Use Case ein import ...presenters.InvoicePresenter. Was sagen Sie?

Das bricht die Dependency Rule. Der Use Case soll einen Output Port im eigenen Ring definieren; der Presenter implementiert ihn.

Szenario: Der Interviewer zeigt einen Paketbaum mit core und infrastructure und fragt, welcher Stil das ist. Wie antworten Sie?

Wahrscheinlich Onion, wegen Kern und Infrastruktur. Ich bestätige es erst, wenn die Interfaces im Kern liegen und kein Import von core nach infrastructure geht.

Szenario: Das Team will von Layered auf Clean umbauen. Wie gehen Sie vor?

Schrittweise: zuerst Repository-Interfaces in die Domäne ziehen, dann Use Cases aus Services schneiden, dann ArchUnit-Regeln aktivieren. Kein Big-Bang, pro Feature umziehen.
