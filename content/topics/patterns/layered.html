Layered Architecture

Patterns · Tier 1 · Quellen: Eric Evans, DDD Reference (2015) „Layered Architecture“; Martin Fowler bliki „PresentationDomainDataLayering“ (2015) und „AnemicDomainModel“; Jeffrey Palermo „The Onion Architecture, Part 1“ (2008); ArchUnit User Guide (Layer Checks); Spring Boot Reference „SQL Databases“ (Open EntityManager in View)

Kern: Die Layered Architecture (Schichtenarchitektur) teilt eine Anwendung in übereinander liegende Schichten mit je einer Aufgabe. Jede Schicht darf nur Schichten unter sich nutzen. Die Abhängigkeiten zeigen also nach unten, am Ende auf die Datenbank.

1. Wo sitzt die Layered Architecture?

  1. Presentation: nimmt Requests an und gibt Antworten zurück. Beispiel: OrderController mappt JSON auf ein DTO.
  2. Business: enthält die Regeln und die Transaktion. Beispiel: OrderService.place() prüft das Limit.
  3. Persistence: liest und schreibt Daten. Beispiel: OrderRepository extends JpaRepository.
  4. Datenbank: ist das Fundament. Alles hängt am Ende von ihr ab.
  5. Die Abhängigkeitsrichtung ist immer oben nach unten. Ein Aufruf nach oben ist ein Fehler.
  6. Evans nennt vier Schichten: User Interface, Application, Domain, Infrastructure. Fowler nennt drei: Presentation, Domain, Data Source. Die Idee ist gleich.

2. Die Reise eines Requests (die Geschichte zum Merken)

  1. Request kommt an. Ein Client schickt POST /orders mit JSON.
  2. Presentation: Der Controller validiert das JSON und baut ein DTO. Er kennt keine SQL-Details.
  3. Business: Der Service öffnet die Transaktion (@Transactional). Er prüft die Regel: Ist das Kreditlimit überschritten?
  4. Persistence: Das Repository speichert die Entity mit JPA. Hibernate erzeugt das SQL.
  5. Datenbank: Die DB schreibt die Zeile. Der Commit passiert beim Verlassen des Service.
  6. Rückweg: Die Entity geht zurück. Der Controller mappt sie auf ein Response-DTO.
  7. Die Falle: Bei vielen Requests hat der Service keine Logik. Er reicht nur durch. Das heisst Architecture Sinkhole.

3. Beispiel: strikte und lockere Schichten prüfen

@Layer(value = 3, name = "Presentation") class OrderController  { OrderService service; }
@Layer(value = 3, name = "Presentation") class ReportController { OrderRepository repo; } // überspringt Business
@Layer(value = 2, name = "Business")     class OrderService     { OrderRepository repo; }
@Layer(value = 1, name = "Persistence")  class OrderRepository  { JdbcTemplate jdbc; }
@Layer(value = 1, name = "Persistence")  class AuditRepository  { OrderService service; } // zeigt nach oben
@Layer(value = 0, name = "Database")     class JdbcTemplate     { }

// Für jedes Feld: Layer-Differenz = from - to
//  < 0 → nach oben → immer Verstoss
//  = 1 → direkt darunter → ok
//  > 1 → überspringt Schichten → strict: Verstoss, relaxed: ok
$ java LayerCheck

ReportController Presentation -> OrderRepository Persistence VIOLATION (skips 1 layer)
OrderService     Business     -> OrderRepository Persistence ok
OrderRepository  Persistence  -> JdbcTemplate    Database    ok

== mode: relaxed
OrderController  Presentation -> OrderService    Business    ok
ReportController Presentation -> OrderRepository Persistence ok (relaxed: skip allowed)
OrderService     Business     -> OrderRepository Persistence ok
OrderRepository  Persistence  -> JdbcTemplate    Database    ok
AuditRepository  Persistence  -> OrderService    Business    VIOLATION (points upwards)

Echte Ausgabe, Oracle JDK 17.0.3. Das Programm liest per Reflection die Felder jeder Klasse und vergleicht die Schicht-Nummern.

  1. Strict (geschlossene Schichten): ReportController greift direkt auf das Repository zu. Das ist ein Verstoss, weil er Business überspringt.
  2. Relaxed (offene Schichten): Derselbe Zugriff ist erlaubt. Die Regel heisst nur noch „nach unten“.
  3. AuditRepository → OrderService zeigt nach oben. Das ist in beiden Varianten falsch. Es erzeugt einen Zyklus.
  4. In echten Projekten prüft man das mit ArchUnit statt mit eigenem Code (siehe Diagnose).

4. Details, die Interviewer fragen

  1. Layer vs Tier: Ein Layer ist eine logische Gruppe im Code. Ein Tier ist eine physische Einheit, z. B. Browser, Server, DB-Server. Drei Layer können in einem Tier laufen.
  2. Strict Layering (closed layers): Eine Schicht ruft nur die direkt darunter. Vorteil: Änderungen bleiben lokal (Layers of Isolation). Nachteil: Durchreich-Code.
  3. Relaxed Layering (open layers): Eine Schicht darf jede tiefere Schicht nutzen. Vorteil: weniger Boilerplate. Nachteil: mehr Kopplung, Regeln wandern in den Controller.
  4. Offene Einzelschicht: Man kann auch nur eine Schicht öffnen, z. B. eine gemeinsame Utility-Schicht. Die Entscheidung muss dokumentiert sein.
  5. Abhängigkeit vs Kontrollfluss: Bei klassischen Layern zeigen beide nach unten. Der Service ruft das Repository auf und kennt seine Klasse.
  6. Transitive Abhängigkeit: Presentation hängt über Business auch von Persistence ab. Palermo nennt das das Kernproblem: UI und Logik koppeln an Data Access.
  7. Datenbank-zentriert: Man entwirft zuerst Tabellen, dann Entities, dann Services. Das Domänenmodell folgt dem Schema, nicht dem Fachwissen.
  8. Anemic Domain Model: Die Entities sind nur Getter und Setter. Die Logik liegt in Services. Fowler: alle Kosten eines Domänenmodells, keiner der Vorteile.
  9. Package by Layer vs Package by Feature: controller/, service/, repository/ verteilt ein Feature über drei Ordner. Fowler rät: oben nach Domänenmodulen teilen, Layer nur darin.
  10. DTO an der Grenze: Der Controller gibt keine JPA-Entity nach aussen. Sonst wird das DB-Schema zum API-Vertrag.
  11. Open Session in View: Spring Boot registriert in Web-Apps standardmässig OpenEntityManagerInViewInterceptor. Lazy Loading läuft dann noch im Controller. Das ist ein Schicht-Leck. Abschalten: spring.jpa.open-in-view=false.
  12. Transaktionsgrenze: @Transactional gehört in die Business-Schicht. Im Controller ist sie zu breit, im Repository zu schmal.
  13. Der Weg zu Hexagonal: Der Service definiert ein Repository-Interface, Persistence implementiert es. Damit dreht sich die Abhängigkeit um (Dependency Inversion). Fowler sagt: Diese Variante heisst oft Hexagonal Architecture.

5. Vergleich

  • Layered (klassisch): Abhängigkeiten nach unten bis zur DB. Einfach, bekannt, gut für CRUD. Domäne hängt an der Infrastruktur.
  • Layered mit Dependency Inversion: Domäne besitzt die Interfaces, Infrastruktur implementiert sie. Das ist der Schritt zu Onion und Hexagonal.
  • Hexagonal (Ports and Adapters): kein oben und unten, sondern innen und aussen. Alle Technik ist ein Adapter.
  • Onion / Clean: Ringe statt Stapel. Die Abhängigkeitsregel zeigt nach innen zur Domäne.
  • Vertical Slice: Ordnung nach Feature (Use Case), nicht nach technischer Schicht. Jedes Slice darf eigene Technik wählen.
  • MVC: ein Muster für die Presentation-Schicht, keine Gesamtarchitektur.

6. In der Produktion

  1. Sinkhole: Die meisten Services reichen nur durch. Jede kleine Änderung braucht drei Klassen. Lösung: für reine Lesepfade eine Schicht öffnen, bewusst und dokumentiert, oder Vertical Slices.
  2. Fat Service: Ein OrderService mit 3000 Zeilen. Alle Regeln, alle Fälle. Lösung: Logik in die Entities und Value Objects schieben, Service nur koordinieren.
  3. LazyInitializationException oder N+1-Queries im Controller: Folge von Open Session in View oder Entity-Rückgabe. Lösung: open-in-view=false, DTO-Projektion, Fetch Join.
  4. DB-Wechsel unmöglich: Services importieren JdbcTemplate oder JPA-Klassen. Lösung: Repository-Interface in der Domäne, Implementierung aussen.
  5. Tests sind langsam: Jeder Service-Test braucht eine DB, weil die Logik an JPA hängt. Lösung: Logik in reine Java-Klassen, DB nur in Repository-Tests (Testcontainers).
  6. Zyklen: Ein Repository ruft einen Service (Audit, Events). Lösung: Domain Events oder Spring ApplicationEvent statt Rückruf nach oben.
  7. Erosion: Ohne Prüfung bricht jede Woche jemand eine Regel. Lösung: ArchUnit-Test im CI.

7. Diagnose: Werkzeuge und Befehle

  • ArchUnit (JUnit-Test für Architektur): 
    @AnalyzeClasses(packages = "com.myapp")
class LayerTest {
  @ArchTest
  static final ArchRule layers = layeredArchitecture()
      .consideringAllDependencies()
      .layer("Controller").definedBy("..controller..")
      .layer("Service").definedBy("..service..")
      .layer("Persistence").definedBy("..persistence..")
      .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
      .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
      .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service");
}
    Das ist strict Layering. Für relaxed erlaubt man Persistence auch für Controller.
  • jdeps -verbose:package target/classes: zeigt jede Paket-Abhängigkeit. Teil des JDK, kein Plugin nötig.
  • IntelliJ: Analyze → Dependency Matrix zeigt Zyklen und Richtung.
  • Code-Review-Check: Imports lesen. Ein import ...repository im Controller oder import jakarta.persistence im Domain-Paket ist ein Signal.
  • Logs: LazyInitializationException und viele gleiche SQLs pro Request zeigen Schicht-Lecks.

8. Senior-Punkte

  1. Layered ist nicht falsch. Für CRUD mit wenig Logik ist es die billigste, verständlichste Wahl.
  2. Das Problem ist die Richtung, nicht die Schichten. Zeigt die Domäne auf die DB, ist sie an Technik gekettet.
  3. Strict oder relaxed ist eine Team-Entscheidung. Sie muss explizit sein und im CI geprüft werden.
  4. Package by Feature zuerst, Layer darin. So bleibt ein Feature an einem Ort und kann später ein Service werden.
  5. Keine Entities über die API. Sonst ist jede Schema-Änderung ein Breaking Change.
  6. Regeln gehören in die Domäne, nicht in den Service. Der Service koordiniert nur: laden, Methode aufrufen, speichern.
  7. Migration in kleinen Schritten: erst Interfaces in die Domäne ziehen, dann Adapter auslagern. Kein Big-Bang-Umbau.

10. Fallen

  • „Layer und Tier sind dasselbe.“ → Falsch. Layer ist logisch, Tier ist physisch.
  • „Relaxed Layering heisst, alles darf alles.“ → Falsch. Nur nach unten. Ein Aufruf nach oben bleibt verboten.
  • „Layered Architecture schützt die Domäne vor der DB.“ → Falsch. Klassisch hängt die Domäne von Persistence ab. Erst Dependency Inversion schützt sie.
  • „Ein Service mit return repo.findById(id) ist sauber.“ → Er ist ein Sinkhole. Einmal ok, als Muster ein Zeichen für zu viele Schichten.
  • „Wenn die Logik im Service steht, ist das DDD.“ → Falsch. Das ist ein Anemic Domain Model.
  • „Package by Layer ist der Standard, also gut.“ → Er verteilt jedes Feature. Fowler empfiehlt oben Domänenmodule.

11. Fragen

Was ist eine Layered Architecture?

Eine Aufteilung in Schichten mit je einer Aufgabe, z. B. Presentation, Business, Persistence. Jede Schicht nutzt nur Schichten unter sich.

In welche Richtung zeigen die Abhängigkeiten?

Von oben nach unten. Presentation kennt Business, Business kennt Persistence, Persistence kennt die DB.

Was ist der Unterschied zwischen strict und relaxed Layering?

Strict: nur die direkt darunterliegende Schicht. Relaxed: jede tiefere Schicht. Nach oben ist in beiden Fällen verboten.

Was sind closed und open layers?

Eine geschlossene Schicht darf nicht übersprungen werden. Eine offene Schicht darf man umgehen. So kann man strict und relaxed pro Schicht mischen.

Was ist der Vorteil von strict Layering?

Layers of Isolation: Eine Änderung in einer Schicht trifft nur die direkt darüber. Die Struktur bleibt vorhersehbar.

Was ist das Architecture Sinkhole?

Requests laufen durch Schichten, die nichts tun, nur durchreichen. Viel Code ohne Wert. Ein Zeichen, dass eine Schicht offen sein sollte oder das Muster nicht passt.

Layer vs Tier?

Layer ist eine logische Gruppe im Code. Tier ist eine physische Laufzeiteinheit, z. B. ein eigener Server.

Welche Schichten nennt Evans?

User Interface, Application, Domain, Infrastructure. Die Domain-Schicht soll frei von UI, Speicherung und Anwendungsablauf sein.

Was ist das grösste Problem der klassischen Layered Architecture?

Die Domäne hängt von Persistence und damit von der DB ab. Das Design wird datenbank-zentriert, Tests brauchen die DB.

Was ist ein Anemic Domain Model?

Entities mit nur Gettern und Settern, die Logik steht in Services. Fowler nennt es ein Anti-Pattern: Kosten eines Modells ohne seinen Nutzen.

Wie macht man aus Layered eine Hexagonal Architecture?

Die Domäne definiert Interfaces wie OrderRepository. Die Persistence-Schicht implementiert sie. Die Abhängigkeit zeigt dann nach innen.

Package by Layer oder Package by Feature?

Package by Feature oben, Layer darin. So liegt ein Feature an einem Ort und lässt sich später herauslösen.

Warum keine JPA-Entities im Controller zurückgeben?

Dann wird das DB-Schema zum API-Vertrag. Ausserdem drohen Lazy-Loading-Fehler und ungewollte Felder im JSON.

Was ist Open Session in View und warum ist es problematisch?

Der EntityManager bleibt bis zum Ende des Web-Requests offen. Lazy Loading passiert im Controller, also ein Schicht-Leck mit versteckten Queries. Spring Boot aktiviert es in Web-Apps standardmässig.

Wo gehört @Transactional hin?

In die Business-Schicht, auf die Use-Case-Methode. Dort ist die fachliche Einheit, die ganz oder gar nicht passieren soll.

Wie prüfen Sie Schichtregeln automatisch?

Mit ArchUnit: layeredArchitecture() mit whereLayer(...).mayOnlyBeAccessedByLayers(...) als JUnit-Test im CI. Dazu jdeps für einen schnellen Überblick.

Wann ist Layered die richtige Wahl?

Bei CRUD-Anwendungen mit wenig Fachlogik und einer festen Datenbank. Dort ist mehr Struktur nur Kosten.

Was passiert, wenn eine untere Schicht eine obere aufruft?

Es entsteht ein Zyklus. Man kann die Schichten nicht mehr einzeln ändern oder testen. Lösung: Event oder Interface in der unteren Schicht.

Ist MVC eine Layered Architecture?

Nein. MVC ordnet nur die Presentation-Schicht. Die Gesamtarchitektur kann trotzdem layered oder hexagonal sein.

Was ist eine transitive Abhängigkeit im Schichtenmodell?

Presentation hängt über Business indirekt von Persistence ab. Palermo betont: Auch indirekte Abhängigkeiten koppeln die UI an Data Access.

Szenario: Im Code-Review sehen Sie einen Controller, der direkt ein Repository nutzt. Was sagen Sie?

Ich frage zuerst, ob das Team relaxed Layering erlaubt. Wenn nicht, ist es ein Verstoss. Wenn doch, prüfe ich, dass keine Fachregel im Controller steht.

Szenario: Jeder neue Endpunkt braucht drei Klassen, die nur durchreichen. Was tun Sie?

Das ist ein Sinkhole. Ich öffne die Service-Schicht für reine Lesepfade, dokumentiert und per ArchUnit geprüft. Oder ich ordne nach Vertical Slices.

Szenario: Nach dem Release gibt es LazyInitializationException in einem Job, aber nicht im Web. Warum?

Im Web hält Open Session in View die Session offen und versteckt das Problem. Im Job gibt es das nicht. Lösung: open-in-view abschalten und Daten im Service gezielt laden.
