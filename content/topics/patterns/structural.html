Strukturmuster

Kern: Strukturmuster (Structural Patterns) setzen Klassen und Objekte zu grösseren Strukturen zusammen. Man will damit Verhalten ergänzen, Schnittstellen anpassen oder Komplexität verstecken, ohne bestehenden Code zu ändern. Fast alle arbeiten mit Komposition, ein Objekt hält also ein anderes und ruft es auf.

Antwort-Muster

Frage: Wie funktioniert @Transactional technisch?

  1. Mechanismus: Spring erzeugt beim Start einen Proxy um die Bean. Er hat dasselbe Interface, öffnet die Transaktion und ruft das echte Objekt.
  2. Zahl: Der Proxy macht COMMIT oder bei einer RuntimeException ROLLBACK. Spring Boot nutzt standardmässig CGLIB.
  3. Trade-off: Ein Proxy versteckt Verhalten. Ruft die Bean sich selbst auf (this.y()), läuft der Aufruf am Proxy vorbei.
  4. Produktion: Wirkt @Transactional nicht, prüfe ich Self-Invocation, private-Methoden und ob die Bean aus dem Container kommt.

1. Die Reise eines @Transactional-Aufrufs

  1. Der Aufruf startet: Der Controller hält eine Referenz auf AccountService. Er weiss nicht, dass es ein Proxy ist.
  2. Der Proxy greift ein: Spring hat beim Start einen Proxy erzeugt. Laut Spring-Doku nutzt das Framework einen JDK Dynamic Proxy, wenn das Ziel ein Interface hat, sonst CGLIB (eine erzeugte Unterklasse). Spring Boot setzt spring.aop.proxy-target-class=true als Standard, also CGLIB.
  3. Das Ziel arbeitet: Der TransactionInterceptor öffnet eine Transaktion und ruft das echte Objekt auf.
  4. Die Falle (Self-Invocation): Ruft das Ziel this.y() auf, geht der Aufruf direkt an das Objekt. Die Annotation auf y() wirkt nicht.
  5. Der Rückweg: Der Proxy macht COMMIT oder bei einer RuntimeException ROLLBACK.
  6. Grenzen von CGLIB: final-Klassen, final- und private-Methoden kann der Proxy nicht abfangen (Spring-Doku).

2. Aufbau

  1. Adapter: Er übersetzt ein fremdes Interface in das Interface, das der Client erwartet. Beispiel: InputStreamReader macht aus Bytes Zeichen.
  2. Decorator: Er hat dasselbe Interface wie das Ziel und fügt Verhalten hinzu. Beispiel: BufferedReader um einen Reader.
  3. Proxy: Er hat dasselbe Interface und kontrolliert den Zugriff: Transaktion, Sicherheit, Lazy Loading, Remote. Beispiel: Spring-AOP-Proxy für @Transactional.
  4. Facade: Sie bietet ein einfaches Interface vor einem komplexen Subsystem. Beispiel: JdbcTemplate vor JDBC.
  5. Composite: Er behandelt ein einzelnes Teil und eine Gruppe von Teilen gleich. Beispiel: Ordner und Datei haben beide size().

3. Details, die Interviewer fragen

Adapter. Ein Adapter wandelt das Interface einer Klasse in ein anderes um, das der Client erwartet (GoF). Es gibt Object Adapter (Komposition) und Class Adapter (Vererbung). In Java nutzt man fast immer Komposition.

// schlecht: SOAP-Typen sickern in die Domain
class TaxService { void declare(TaxDeclarationSoapRequest req) { soapClient.send(req); } }
// besser: Domain-Interface, Adapter übersetzt
interface TaxAuthority { Receipt submit(Declaration d); }                       // Port
class SoapTaxAuthorityAdapter implements TaxAuthority {
  public Receipt submit(Declaration d) { return toReceipt(soapClient.send(toSoap(d))); }
}
  1. JDK: Beispiele sind InputStreamReader (Bytes zu Zeichen), Arrays.asList und Collections.enumeration.
  2. Spring: HandlerAdapter lässt den DispatcherServlet verschiedene Handler-Typen gleich aufrufen. Ein Adapter in der hexagonalen Architektur implementiert einen Port.
  3. Anti-Corruption Layer (DDD): Das ist ein grosser Adapter zwischen zwei Modellen.

Decorator. Ein Decorator fügt einem Objekt dynamisch Verhalten hinzu. Er hat dasselbe Interface und delegiert an das innere Objekt. Er ist eine Alternative zu Unterklassen.

// schlecht: Unterklassen-Explosion
class CachingRetryingLoggingRateClient extends RateClient { ... }
// besser: Decorators frei kombinieren
interface RateClient { BigDecimal rate(String pair); }
class RetryingRateClient implements RateClient {
  private final RateClient inner;
  RetryingRateClient(RateClient inner) { this.inner = inner; }
  public BigDecimal rate(String pair) {
    for (int i = 1; ; i++) { try { return inner.rate(pair); } catch (IOException e) { if (i == 3) throw e; } }
  }
}
RateClient client = new CachingRateClient(new RetryingRateClient(new HttpRateClient()));
  1. Reihenfolge zählt: Ein Cache aussen spart Retries. Ein Retry aussen wiederholt auch Cache-Fehler.
  2. JDK: Beispiele sind die java.io-Streams und Collections.synchronizedList.
  3. Spring: Beispiele sind TransactionAwareCacheDecorator und HttpServletRequestWrapper (Servlet-API). Ein BeanPostProcessor kann ein Bean durch einen Wrapper ersetzen.
  4. Nachteil: Es gibt viele kleine Objekte. Stacktraces werden lang. equals und Identität ändern sich.

Proxy. Ein Proxy ist ein Stellvertreter mit demselben Interface. Er kontrolliert den Zugriff auf das echte Objekt. GoF nennt Remote Proxy, Virtual Proxy (lazy) und Protection Proxy (Rechte).

// schlecht: Querschnitt in jeder Methode
public void transfer() { tx.begin(); try { ... ; tx.commit(); } catch (RuntimeException e) { tx.rollback(); throw e; } }
// besser: Spring erzeugt den Proxy
@Transactional public void transfer() { ... }

// Self-Invocation-Falle
@Service class AccountService {
  public void transferAll() { for (...) transfer(); }          // this.transfer(): KEIN Proxy
  @Transactional(propagation = REQUIRES_NEW) public void transfer() { ... }
}
// Fix: transfer() in ein eigenes Bean verschieben und injizieren
  1. JDK Dynamic Proxy: java.lang.reflect.Proxy erzeugt zur Laufzeit eine Klasse, die Interfaces implementiert. Nur Interface-Methoden werden abgefangen.
  2. CGLIB: Es erzeugt eine Unterklasse. Das geht ohne Interface. Es geht aber nicht mit final und private.
  3. Spring nutzt Proxies für: @Transactional, @Cacheable, @Async und @PreAuthorize. Dazu kommen Spring-Data-Repositories. Auch @Configuration-Klassen sind Proxies, damit @Bean-Aufrufe das Singleton liefern.
  4. Hibernate: Lazy-Beziehungen sind Proxies (Virtual Proxy). Zugriff ausserhalb der Session wirft LazyInitializationException.
  5. Fixes für Self-Invocation laut Spring-Doku: Bevorzugt vermeidet man die Self-Invocation. Self-Injection oder AopContext.currentProxy() sind möglich, Letzteres ist stark abgeraten. AspectJ-Weaving hat das Problem nicht.

Facade. Eine Facade bietet ein einfaches, einheitliches Interface für ein Subsystem. Das Subsystem bleibt nutzbar. Die Facade versteckt nur die Komplexität.

// schlecht: Controller orchestriert fünf Klassen
zip = unzipper.decrypt(file, pw); xml = parser.parse(zip); validator.check(xml); writer.write(xml); status.done(id);
// besser: eine Facade mit einer Methode
class ReportImportFacade { ImportResult importReport(MessageId id) { ... } }
  1. Beispiele: JdbcTemplate versteckt Connection, Statement, ResultSet und Exceptions. SLF4J ist eine Logging-Facade.
  2. Gefahr: Eine Facade wächst leicht zur God Class. Sie soll delegieren. Sie soll nicht selbst Logik halten.

Composite. Ein Composite setzt Objekte zu Baumstrukturen zusammen. Der Client behandelt Blatt und Gruppe über dasselbe Interface.

interface Node { long size(); }
record FileNode(String name, long size) implements Node {}
record Dir(String name, List<Node> children) implements Node {
  public long size() { return children.stream().mapToLong(Node::size).sum(); }
}
  1. Beispiele: Swing/AWT Container und Component sind Composites. In Spring sind es CompositeCacheManager und CompositePropertySource. Validierungsregeln aus Unterregeln sind es auch.
  2. Trade-off: Ein Blatt hat Methoden wie add, die keinen Sinn ergeben (Transparenz). Oder der Client muss unterscheiden (Sicherheit). GoF diskutiert genau diesen Konflikt.

4. Fallen

  • „@Transactional auf einer Methode wirkt immer.“ → Falsch. Nicht bei Self-Invocation, nicht bei private/final, nicht bei Objekten ohne Container.
  • „Spring nutzt immer JDK Dynamic Proxies.“ → Falsch. Das Framework nutzt sie bei Interfaces. Spring Boot stellt standardmässig auf CGLIB.
  • „Decorator und Proxy sind dasselbe.“ → Struktur gleich, Absicht anders. Decorator ergänzt Verhalten, Proxy kontrolliert Zugriff.
  • „unmodifiableList ist unveränderlich.“ → Falsch. Sie ist eine schreibgeschützte Sicht. Die Quelle kann sich ändern.
  • „Eine Facade verbietet den Zugriff aufs Subsystem.“ → Falsch. Sie vereinfacht nur. Direkter Zugriff bleibt möglich.
  • „Arrays.asList liefert eine normale ArrayList.“ → Falsch. Es ist eine Sicht fester Grösse. add wirft eine Exception.

5. Selbsttest

Warum?

Decorator oder Unterklasse?

Decorator, wenn Funktionen frei kombinierbar sein sollen. Unterklassen führen sonst zu einer Explosion von Kombinationen.

Was ist das Self-Invocation-Problem?

Ein Aufruf this.methode() im selben Bean geht nicht durch den Proxy. Annotationen wie @Transactional oder @Async wirken dann nicht.

Warum ist @Configuration ein Proxy?

Damit ein Aufruf einer @Bean-Methode aus einer anderen @Bean-Methode das Singleton aus dem Container liefert und kein neues Objekt.

Ist Collections.unmodifiableList eine Kopie?

Nein, eine schreibgeschützte Sicht. Änderungen an der Quelle sind sichtbar. Für eine Kopie: List.copyOf.

Wie innen?

Was sind Strukturmuster?

Muster, die Klassen und Objekte zu grösseren Strukturen zusammensetzen. GoF nennt sieben, z. B. Adapter, Decorator, Proxy, Facade, Composite.

Was macht ein Adapter?

Er übersetzt ein vorhandenes Interface in das Interface, das der Client erwartet. Beispiel: InputStreamReader macht aus einem InputStream einen Reader.

Was ist ein Decorator?

Ein Objekt mit gleichem Interface, das an ein inneres Objekt delegiert und Verhalten hinzufügt. Mehrere Decorators lassen sich kombinieren.

Was ist ein Proxy?

Ein Stellvertreter mit gleichem Interface, der den Zugriff kontrolliert: lazy laden, Rechte prüfen, remote aufrufen, Transaktion steuern.

Wie funktioniert @Transactional technisch?

Spring erzeugt einen Proxy um das Bean. Der TransactionInterceptor öffnet die Transaktion, ruft das Ziel auf und macht Commit oder Rollback.

Was ist eine Facade?

Ein einfaches Interface vor einem komplexen Subsystem. Beispiel: JdbcTemplate vor Connection, Statement und ResultSet.

Was ist ein Composite?

Ein Baum, in dem Blatt und Gruppe dasselbe Interface haben. Der Client ruft size() auf, egal ob Datei oder Ordner.

Wie prüfen Sie, ob ein Bean ein Proxy ist?

Mit AopUtils.isAopProxy(bean) oder am Klassennamen: er enthält CGLIB oder beginnt mit $Proxy.

Zahlen

Welchen Proxy-Typ nutzt Spring Boot standardmässig?

CGLIB. spring.aop.proxy-target-class ist standardmässig true. Das Framework allein bevorzugt JDK-Proxies bei Interfaces.

Was zeigt das Decorator-Beispiel mit den Zahlen 1900 und 56?

Die Kette BufferedWriter, OutputStreamWriter, GZIPOutputStream macht aus 1900 Zeichen 56 gzip-Bytes. Jede Schicht fügt eine Funktion hinzu.

Wie berechnet das Composite-Beispiel root.size()?

Der Dir summiert rekursiv 300 + 200 + 500 und liefert 1000. Der Client unterscheidet nicht zwischen Datei und Ordner.

Vergleich

Object Adapter oder Class Adapter?

Object Adapter nutzt Komposition, Class Adapter Vererbung. In Java fast immer Object Adapter, weil es keine Mehrfachvererbung gibt.

JDK Dynamic Proxy vs CGLIB?

JDK Proxy implementiert Interfaces zur Laufzeit. CGLIB erzeugt eine Unterklasse und braucht kein Interface, kann aber final und private nicht abfangen.

Adapter vs Facade?

Adapter passt ein vorhandenes Interface an ein erwartetes an. Facade schafft ein neues, einfacheres Interface für viele Klassen.

Decorator vs Proxy?

Gleiche Struktur. Decorator ergänzt Verhalten und wird vom Client zusammengesteckt. Proxy kontrolliert Zugriff und wird oft vom Framework erzeugt.

Produktion

Wie lösen Sie Self-Invocation?

Am besten die Methode in ein eigenes Bean verschieben. Alternativen: Self-Injection oder AopContext.currentProxy(), letzteres rät Spring stark ab.

Was ist eine LazyInitializationException?

Ein Hibernate-Proxy wird nach dem Schliessen der Session gelesen. Fix: im Service mit Fetch Join laden oder ein DTO zurückgeben.

Szenario: Eine @Transactional-Methode schreibt Daten, aber bei einem Fehler gibt es keinen Rollback. Was prüfen Sie?

Ob der Aufruf durch den Proxy läuft (Self-Invocation, private Methode). Ob die Exception checked ist, denn Standard-Rollback gilt nur für RuntimeException. Dazu Transaktions-Logging auf DEBUG.

Szenario: Ein Schema-Update des externen SOAP-Partners bricht 40 Klassen. Was schlagen Sie vor?

Einen Adapter an der Grenze, der SOAP-Typen in eigene Domain-Typen übersetzt. Danach ändert sich bei Schema-Updates nur noch der Adapter.

Szenario: Ein HTTP-Client braucht Retry, Cache und Metriken. Wie bauen Sie das?

Als Decorators um ein gemeinsames Interface, mit bewusster Reihenfolge: Metriken aussen, dann Cache, dann Retry. In Spring oft fertig mit Resilience4j und Spring Cache.

Design

Wo nutzt Spring MVC einen Adapter?

HandlerAdapter. Der DispatcherServlet ruft darüber verschiedene Handler-Typen einheitlich auf, z. B. @RequestMapping-Methoden.

Wo im JDK finden Sie Decorators?

In java.io: BufferedReader, InputStreamReader, GZIPInputStream. Ausserdem Collections.synchronizedList.

Wo nutzt Spring Composite?

CompositeCacheManager fragt mehrere CacheManager nacheinander. CompositePropertySource fasst mehrere PropertySources zusammen.

Mehr

Gerüst

  • Warum? Man will Verhalten ergänzen, Schnittstellen anpassen oder Komplexität verstecken, ohne bestehenden Code zu ändern. Das geht mit Komposition.
  • Wie innen? Der Proxy hat dasselbe Interface wie das Ziel. Spring erzeugt ihn beim Start. @Transactional öffnet im Proxy die Transaktion.
  • Zahlen JDK-Beispiel: 1900 Zeichen werden durch die Decorator-Kette zu 56 gzip-Bytes. Composite: root.size() = 300 + 200 + 500 = 1000.
  • Vergleich Adapter ändert das Interface, Decorator behält es. Decorator ergänzt, Proxy kontrolliert. JDK Proxy braucht ein Interface, CGLIB scheitert an final.
  • Produktion @Transactional wirkt nicht bei Self-Invocation, bei private-Methoden oder bei new. Lazy-Proxy ausserhalb der Session wirft LazyInitializationException.
  • Design Fremde Modelle bleiben im Adapter. Facade orchestriert nur, sonst wird sie zur God Class. Im Review fragen: läuft der Aufruf durch den Proxy?

Beispiel: Decorator, Proxy, Adapter und Composite im JDK

// 1) Decorator-Kette: BufferedWriter → OutputStreamWriter → GZIPOutputStream → Bytes
new BufferedWriter(new OutputStreamWriter(new GZIPOutputStream(bytes), UTF_8));
// 2) JDK Dynamic Proxy mit "Transaktion"; transferAll() ruft intern this.transfer()
AccountService proxy = (AccountService) Proxy.newProxyInstance(loader, new Class<?>[]{AccountService.class},
    (p, m, a) -> { print("BEGIN tx " + m.getName()); Object r = m.invoke(target, a); print("COMMIT"); return r; });
proxy.transferAll();
// 3) Arrays.asList: Adapter von Array zu List
// 4) eigener Adapter: LegacyRates.getRate("EURCHF") → ExchangeRates.rate(EUR, CHF)
// 5) Collections.unmodifiableList: Schutz-Proxy
// 6) Composite: Dir und FileNode haben beide size()
1) Decorator: java.io stream chain
text 1900 chars -> gzip bytes: 56
read back starts with: Bern Zuerich Basel
2) Proxy: JDK dynamic proxy around AccountService
proxy class: $Proxy0
   [proxy] BEGIN tx transferAll
   transferAll() runs
   transfer() runs
   [proxy] COMMIT transferAll
3) Adapter: Arrays.asList is a fixed-size view
array after view.set: [X, b]
view.add -> UnsupportedOperationException
4) Adapter: own LegacyRatesAdapter
EUR->CHF = 0.93
5) unmodifiableList is a protection proxy, not a copy
ro = [a, b], List.copyOf = [a]
ro.add -> UnsupportedOperationException
6) Composite
root.size() = 1000

Echte Ausgabe, OpenJDK/Oracle JDK 17.0.3 (java StructuralDemo.java).

  1. Decorator: Jede Schicht hat ein Stream-Interface und fügt eine Funktion hinzu: Puffern, Zeichen-Codierung, Komprimierung. Aus 1900 Zeichen werden 56 Bytes.
  2. Proxy: Die Klasse $Proxy0 entsteht zur Laufzeit. Nur transferAll bekommt BEGIN/COMMIT. Der innere Aufruf transfer() läuft ohne Proxy. Genau das passiert mit @Transactional bei Self-Invocation.
  3. Adapter Arrays.asList: set schreibt durch ins Array. add geht nicht, weil ein Array eine feste Grösse hat.
  4. Eigener Adapter: Der Client nutzt Currency-Objekte. Der Adapter baut daraus den String, den die Legacy-API erwartet.
  5. unmodifiableList ist eine Sicht: Änderungen an der Quelle sind sichtbar ([a, b]). Nur Schreiben über die Sicht ist verboten. Für eine echte Kopie: List.copyOf.
  6. Composite: root.size() summiert rekursiv 300 + 200 + 500. Der Client unterscheidet nicht zwischen Datei und Ordner.

Vergleich

  • Adapter vs Facade: Adapter passt ein vorhandenes Interface an ein erwartetes an. Facade erfindet ein neues, einfacheres Interface für viele Klassen.
  • Decorator vs Proxy: Gleiche Struktur. Decorator ergänzt Verhalten und wird vom Client gebaut. Proxy kontrolliert Zugriff und wird oft vom Framework erzeugt.
  • Decorator vs Vererbung: Decorator kombiniert zur Laufzeit. Vererbung legt die Kombination zur Compile-Zeit fest.
  • Adapter vs Decorator: Adapter ändert das Interface. Decorator behält es.
  • JDK Proxy vs CGLIB: JDK Proxy braucht ein Interface. CGLIB erzeugt eine Unterklasse und scheitert an final.
  • Composite vs Decorator: Beide sind rekursiv. Composite hat viele Kinder, Decorator genau ein inneres Objekt.

In der Produktion

  1. @Transactional wirkt nicht: Ursache: Self-Invocation, private-Methode oder Objekt mit new statt aus dem Container. Fix: Methode in ein anderes Bean, public, per Injection.
  2. Kein Rollback bei Checked Exception: Standard-Rollback nur bei RuntimeException und Error. Fix: rollbackFor = Exception.class, wenn gewollt.
  3. LazyInitializationException: Ein Hibernate-Proxy wird nach dem Ende der Session gelesen. Fix: im Service mit Fetch Join laden oder DTO bauen.
  4. Adapter lässt fremde Typen durch: SOAP- oder JSON-Klassen erscheinen in der Domain. Ein Schema-Update bricht dann viele Klassen. Fix: Mapping nur im Adapter.
  5. Decorator-Reihenfolge falsch: Retry ausserhalb von Circuit Breaker oder Cache erzeugt Last-Spitzen. Fix: Reihenfolge bewusst festlegen und testen.
  6. unmodifiableList als „Kopie“: Daten ändern sich trotzdem, weil die Quelle sich ändert. Fix: List.copyOf.

Diagnose: Werkzeuge und Befehle

  • Klassenname prüfen: bean.getClass() zeigt einen Namen mit CGLIB (CGLIB) oder $Proxy (JDK). AopUtils.isAopProxy(bean) prüft es im Code.
  • Transaktions-Logging: logging.level.org.springframework.transaction=DEBUG zeigt, wann eine Transaktion beginnt und endet.
  • Stacktrace lesen: Fehlt TransactionInterceptor im Stack, lief der Aufruf nicht durch den Proxy.
  • Hibernate: spring.jpa.show-sql=true und Statistiken zeigen Lazy-Loads und N+1-Abfragen.
  • ArchUnit: Regel „Klassen im Paket domain hängen nicht von SOAP- oder HTTP-Typen ab“ schützt Adapter-Grenzen.

Senior-Punkte

  1. Spring ist voller Proxies. Wer Proxies versteht, versteht die meisten „Annotation wirkt nicht“-Bugs.
  2. Adapter sind Grenzschutz. Fremde Modelle bleiben im Adapter. Die Domain kennt nur eigene Typen.
  3. Decorator statt Unterklassen für Querschnitt wie Retry, Cache, Metriken. Aber oft ist eine fertige Lösung besser: Resilience4j, Spring Cache.
  4. Facade begrenzen. Sie orchestriert, sie entscheidet nicht. Sonst wird sie zur God Class.
  5. Proxies kosten wenig, aber sie verstecken Verhalten. Im Review frage ich: Läuft dieser Aufruf wirklich durch den Proxy?
  6. Muster benennen hilft im Review: „Das ist ein Adapter, also bitte keine Geschäftslogik hier.“
