DDD taktisch: Entity, Value Object, Aggregate, Repository

Patterns · Tier 1 · Quellen: Eric Evans, DDD Reference (2015); Vaughn Vernon „Effective Aggregate Design“ Part I und II (2011); Martin Fowler bliki „DDD_Aggregate“, „ValueObject“, „AnemicDomainModel“; Spring Data Commons Reference „Publishing Events from Aggregate Roots“ und Javadoc AbstractAggregateRoot

Kern: Taktisches DDD ist ein Satz von Bausteinen, um ein Fachmodell direkt im Code auszudrücken: Entity, Value Object, Aggregate, Repository, Domain Service, Domain Event, Factory. Das wichtigste ist das Aggregate: eine Gruppe von Objekten mit einer Konsistenzgrenze, die ihre Invarianten in einer Transaktion schützt. Gute Aggregates sind klein und verweisen auf andere nur per ID.

1. Wo sitzen die Bausteine?

  1. Entity: ein Objekt mit Identität über die Zeit. Zwei Kunden mit gleichem Namen sind verschiedene Kunden. Beispiel: PurchaseOrder mit OrderId.
  2. Value Object: ein Objekt ohne Identität, das einen Wert beschreibt. Gleich, wenn alle Werte gleich sind. Beispiel: Money(500, "CHF").
  3. Aggregate: ein Cluster aus Entities und Value Objects mit einer Grenze. Beispiel: Bestellung mit ihren Zeilen.
  4. Aggregate Root: die eine Entity, über die man das Aggregate betritt. Sie prüft alle Invarianten.
  5. Repository: lädt und speichert ganze Aggregates, wie eine Collection im Speicher. Nur für Roots.
  6. Domain Service: eine fachliche Operation, die zu keiner Entity passt. Beispiel: TransferService zwischen zwei Konten.
  7. Domain Event: eine Tatsache, die Fachleute interessiert, in Vergangenheitsform. Beispiel: OrderSubmitted.

2. Die Reise eines Commands (die Geschichte zum Merken)

  1. Application Service: Er bekommt den Befehl „Bestellung abschicken“. Er öffnet die Transaktion. Er enthält keine Fachregel, er koordiniert nur.
  2. Repository: Er lädt das ganze Aggregate über die Root, mit Versionsnummer (hier v2).
  3. Root: Der Service ruft order.submit(). Die Root prüft die Invarianten: nicht leer, Summe unter Limit.
  4. Event: Die Root merkt sich OrderSubmitted. Noch nichts ist veröffentlicht.
  5. Speichern: Das Repository prüft die Version (optimistic locking) und speichert. Ein Commit, ein Aggregate.
  6. Danach: Das Event geht an Abonnenten. Jeder ändert sein eigenes Aggregate in einer eigenen Transaktion. Das ist eventual consistency ausserhalb der Grenze.
  7. Konflikt: Arbeiten zwei Nutzer am gleichen Aggregate, gewinnt der erste Commit. Je grösser das Aggregate, desto öfter passiert das.

3. Beispiel: Value Object, Invariante, Event, Konflikt

record OrderSubmitted(OrderId orderId, Money total) { }  // Domain Event

final class PurchaseOrder {                               // Aggregate Root
  private final List<OrderLine> lines = new ArrayList<>();  // Entities innen

    OrderLine line = new OrderLine(lines.size() + 1, p, qty, price);

Echte Ausgabe, Oracle JDK 17.0.3. Beträge in Rappen. Vollständiger Code mit In-Memory-Repository, ohne Framework.

  1. Value Object: Zwei Money-Objekte sind gleich (equals), obwohl es zwei Instanzen sind (== false). Records liefern equals/hashCode über alle Felder.
  2. Selbstvalidierung: Ein negatives Money entsteht gar nicht. Der kompakte Konstruktor prüft.
  3. Invariante: Die zweite Zeile würde 11'000 ergeben. Die Root lehnt ab. Der Zustand bleibt gültig.
  4. Kapselung: Von aussen kann niemand die Liste ändern. Nur addLine darf das, und dort steht die Regel.
  5. Domain Event: submit() merkt sich das Event, save() veröffentlicht es. Es trägt IDs und Werte, keine Objekt-Referenzen.
  6. Optimistic Locking: Bill und Joe laden v2. Bill speichert, die Version wird 3. Joe scheitert. Genau dieses Problem beschreibt Vernon für ein zu grosses Aggregate.

4. Details, die Interviewer fragen

  1. Entity: durch Identität definiert, nicht durch Attribute. Evans: Das Modell muss festlegen, was „dasselbe Ding“ heisst. equals vergleicht die ID.
  2. Value Object: nur Attribute und Logik zählen. Evans: unveränderlich, alle Operationen side-effect-free, keine Identität. Fowler warnt vor Aliasing-Bugs bei veränderbaren Werten.
  3. Primitive Obsession vermeiden: Money statt long, Email statt String. Die Regel steht dann an einem Ort.
  4. Aggregate (Evans): Entities und Value Objects clustern, Grenze ziehen, eine Root wählen. Externe Objekte halten nur Referenzen auf die Root. Die Root setzt die Invarianten durch.
  5. Gleiche Grenze für Transaktion und Verteilung (Evans): innen synchron konsistent, über Grenzen asynchron. Ein Aggregate bleibt auf einem Server.
  6. Invariante (Vernon): eine Geschäftsregel, die immer konsistent sein muss, also transaktional. Beispiel: c = a + b. Ein Aggregate ist ein Synonym für eine transaktionale Konsistenzgrenze.
  7. Vernons Regel 1: Model True Invariants in Consistency Boundaries. Nur echte Geschäftsregeln ziehen Objekte zusammen. „Product hat Backlog Items“ ist keine Invariante, nur Komposition.
  8. Vernons Regel 2: Design Small Aggregates. Root plus minimal nötige Attribute und Value-Properties. Vernon berichtet aus einem Projekt: ca. 70 % der Aggregates nur mit Root und Value Objects, der Rest mit zwei bis drei Entities.
  9. Vernons Regel 3: Reference Other Aggregates by Identity. ProductId productId statt Product product. Weniger laden, weniger Speicher, leichter zu verteilen.
  10. Vernons Regel 4: Use Eventual Consistency Outside the Boundary. Regeln über mehrere Aggregates laufen per Domain Event in eigenen Transaktionen, mit Retry.
  11. Ein Aggregate pro Transaktion: Vernon nennt es eine Faustregel. Gründe für Ausnahmen: UI-Komfort (Batch-Anlage), fehlende Messaging-Technik, globale Transaktionen, Query-Performance.
  12. „Wessen Job ist es?“ (Evans via Vernon): Muss der aktuelle Nutzer die Daten konsistent machen, dann transaktional. Ist es der Job eines anderen oder des Systems, dann eventual.
  13. Repository (Evans): Illusion einer In-Memory-Collection aller Roots eines Typs. Methoden mit fachlichen Kriterien. Nur für Roots, die globalen Zugriff brauchen. Das Interface gehört zur Domäne.
  14. Domain Service vs Application Service: Ein Domain Service ist ein fachlicher Prozess, der keiner Entity gehört, benannt in der Ubiquitous Language. Ein Application Service enthält laut Evans keine Geschäftsregeln, er koordiniert nur.
  15. Domain Event (Evans): Teil des Modells, meist unveränderlich, mit Zeitpunkt und IDs der beteiligten Entities. Abzugrenzen von technischen System-Events.
  16. Factory: erzeugt ein ganzes Aggregate in einem Stück und setzt dabei die Invarianten durch. Nötig, wenn ein Konstruktor zu komplex wird.
  17. Spring Data: Eine @DomainEvents-Methode oder AbstractAggregateRoot.registerEvent() veröffentlicht Events bei save, saveAll, delete, deleteAll, deleteAllInBatch, deleteInBatch. deleteById veröffentlicht nicht.

5. Vergleich

  • Entity vs Value Object: Identität und Lebenszyklus gegen Wert und Unveränderlichkeit. Kann man es komplett ersetzen, statt es zu ändern? Dann Value Object.
  • DDD Aggregate vs JPA-Entity-Graph: Ein JPA-Graph kann beliebig gross sein. Ein Aggregate ist durch Invarianten begrenzt und wird ganz geladen und gespeichert.
  • Aggregate vs Collection: Fowler: Aggregates sind Fachbegriffe (Bestellung, Playlist), Collections sind generisch (List, Map).
  • DDD Repository vs DAO: Ein Repository arbeitet mit ganzen Aggregates in Fachsprache. Ein DAO arbeitet tabellen- oder zeilennah.
  • Domain Event vs Integration Event: Ein Domain Event lebt im Bounded Context. Ein Integration Event ist ein veröffentlichter Vertrag für andere Kontexte.
  • Rich Domain Model vs Anemic Domain Model: Verhalten in den Objekten gegen Getter/Setter mit Logik in Services.

6. In der Produktion

  1. Viele OptimisticLockException: Das Aggregate ist zu gross (Vernons Product mit allen Backlog Items). Lösung: nach echten Invarianten schneiden, per ID referenzieren.
  2. Langsames Laden: Ein Befehl lädt tausende Kinder, nur um eins hinzuzufügen. Lösung: kleines Aggregate, Kinder als eigenes Aggregate.
  3. Events vor dem Commit veröffentlicht: Der Konsument sieht Daten, die nach Rollback nicht existieren. Lösung: @TransactionalEventListener nach dem Commit oder Transactional Outbox.
  4. Events verloren: Commit ok, Broker down. Lösung: Outbox-Tabelle in derselben Transaktion, ein Relay sendet später.
  5. Invariante umgangen: Ein Repository für OrderLine oder ein öffentlicher Setter ändert Kinder ohne Root. Lösung: Repositories nur für Roots, keine Setter, Collections read-only.
  6. Kaskaden über Aggregate-Grenzen: @ManyToOne(cascade = ALL) auf ein anderes Aggregate speichert es mit. Lösung: nur ID halten.
  7. Eventual consistency bricht Annahmen: UI zeigt kurz alten Stand. Lösung: Fachbereich fragt nach erlaubter Verzögerung, UI zeigt Status „in Bearbeitung“.

7. Diagnose: Werkzeuge und Befehle

  • Logs: Zählen von ObjectOptimisticLockingFailureException pro Endpunkt. Hohe Rate = Aggregate zu gross oder zu heiss.
  • SQL-Log (logging.level.org.hibernate.SQL=debug): Wie viele SELECTs pro Befehl? Hunderte = Aggregate lädt zu viel.
  • Hibernate Statistics (spring.jpa.properties.hibernate.generate_statistics=true): Entities geladen pro Session.
  • ArchUnit: Regel „Repository-Interfaces nur für Klassen, die Aggregate Roots sind“ und „Domain-Paket importiert kein jakarta.persistence“.
  • Code-Review-Check: öffentliche Setter, getLines() mit veränderbarer Liste, Objekt-Referenzen auf andere Roots, @Transactional-Methoden mit zwei save() auf verschiedene Roots.
  • Unit-Test pro Invariante: Evans empfiehlt, Invarianten als Assertions oder automatische Tests festzuhalten.

8. Senior-Punkte

  1. Grenzen kommen aus Invarianten, nicht aus „hat ein“. Erst die Regel finden, dann das Aggregate schneiden.
  2. Klein ist der Standard. Gross nur, wenn eine echte Regel es erzwingt. Kleine Aggregates haben weniger Konflikte und skalieren.
  3. Eventual consistency ist eine Fachfrage. Fachleute akzeptieren oft Sekunden bis Stunden. „Wessen Job ist es?“ entscheidet.
  4. Value Objects sind der günstigste Gewinn. Sie machen Regeln testbar und Code lesbar, auch ohne volles DDD.
  5. DDD taktisch nur für den Core Domain. Für generische Teile reicht CRUD.
  6. Regeln brechen mit Grund und Dokumentation, z. B. Batch-Anlage mehrerer Aggregates, wenn es fachlich gleich ist wie einzeln.
  7. JPA ist ein Detail. Wenn JPA das Modell verformt, eigene Persistenz-Entities im Adapter nutzen.

10. Fallen

  • „Ein Aggregate ist eine Entity mit allen ihren Beziehungen.“ → Falsch. Es ist eine Konsistenzgrenze um echte Invarianten, meist klein.
  • „Jede Entity bekommt ein Repository.“ → Falsch. Nur Aggregate Roots, die globalen Zugriff brauchen.
  • „Ein Value Object darf man ändern, wenn es praktisch ist.“ → Falsch. Ersetzen, nicht ändern. Sonst drohen Aliasing-Bugs.
  • „Mehrere Aggregates in einer Transaktion sind normal.“ → Nur mit gutem Grund. Faustregel: ein Aggregate pro Transaktion.
  • „Domain Service und Application Service sind dasselbe.“ → Falsch. Domain Service hat Fachlogik, Application Service koordiniert nur.
  • „Ein Domain Event ist ein Kafka-Topic.“ → Falsch. Es ist ein Modellobjekt. Kafka ist nur ein möglicher Transport.
  • „Objekt-Referenz auf ein anderes Aggregate ist ok, Hibernate lädt lazy.“ → Vernon: lieber per ID. Sonst wird es verlockend, beide in einer Transaktion zu ändern.

11. Fragen

Was ist eine Entity?

Ein Objekt mit Identität und Lebenszyklus. Es bleibt dasselbe, auch wenn sich Attribute ändern. equals vergleicht die ID.

Was ist ein Value Object?

Ein Objekt ohne Identität, definiert durch seine Werte. Unveränderlich, gleich bei gleichen Werten, Operationen ohne Seiteneffekte.

Woran entscheiden Sie Entity oder Value Object?

Interessiert mich, welches Exemplar es ist, oder nur sein Wert? Kann ich es komplett ersetzen statt ändern, ist es ein Value Object.

Warum sind Java Records gut für Value Objects?

Unveränderliche Felder, equals/hashCode über alle Komponenten, und Validierung im kompakten Konstruktor.

Was ist ein Aggregate?

Ein Cluster aus Entities und Value Objects mit einer Grenze. Es wird als Einheit geladen, geändert und gespeichert.

Was ist die Aggregate Root?

Die eine Entity, über die man das Aggregate betritt. Externe Objekte referenzieren nur sie, und sie setzt die Invarianten durch.

Was ist eine Invariante?

Eine Geschäftsregel, die immer gelten muss, auch direkt nach jedem Commit. Beispiel: Summe der Zeilen höchstens Limit.

Nennen Sie Vernons Regeln für Aggregate-Design.

Echte Invarianten in Konsistenzgrenzen modellieren; kleine Aggregates; andere Aggregates nur per ID referenzieren; ausserhalb der Grenze eventual consistency.

Warum kleine Aggregates?

Weniger Daten pro Befehl, weniger Speicher und weniger Konflikte beim optimistic locking. Sie skalieren besser.

Warum Referenz per ID statt Objekt?

Das andere Aggregate wird nicht mitgeladen und nicht versehentlich in derselben Transaktion geändert. Es lässt sich auch anders speichern oder verteilen.

Wie viele Aggregates ändert eine Transaktion?

Als Faustregel eines. Andere werden per Domain Event in eigenen Transaktionen nachgezogen.

Wann darf man mehrere Aggregates in einer Transaktion ändern?

Vernon nennt UI-Komfort (Batch-Anlage), fehlende Messaging-Technik, verordnete globale Transaktionen und Query-Performance. Immer bewusst und begründet.

Was ist ein Repository im DDD-Sinn?

Eine Abstraktion wie eine Collection aller Roots eines Typs. Es lädt und speichert ganze Aggregates und bietet fachliche Suchmethoden.

Bekommt jede Entity ein Repository?

Nein. Nur Aggregate Roots, die global gefunden werden müssen. Innere Entities erreicht man über die Root.

Was ist ein Domain Service?

Eine fachliche Operation, die keiner Entity oder keinem Value Object natürlich gehört. Zustandslos, benannt in der Fachsprache.

Domain Service vs Application Service?

Der Domain Service enthält Fachlogik. Der Application Service koordiniert: laden, Methode aufrufen, speichern, Transaktion. Er enthält keine Geschäftsregeln.

Was ist ein Domain Event?

Ein Modellobjekt für etwas, das in der Fachdomäne passiert ist, z. B. OrderSubmitted. Unveränderlich, mit Zeitpunkt und IDs.

Wie veröffentlicht Spring Data Domain Events?

Über @DomainEvents oder AbstractAggregateRoot.registerEvent(). Veröffentlicht wird bei save/delete-Methoden des Repositories, nicht bei deleteById.

Was ist eine Factory im DDD?

Ein Objekt oder eine Methode, die ein komplexes Aggregate als Ganzes erzeugt und dabei die Invarianten prüft.

Was ist ein Anemic Domain Model?

Entities nur mit Gettern und Settern, Logik in Services. Fowler nennt es ein Anti-Pattern.

Wie schützt die Root ihre Invarianten technisch?

Keine öffentlichen Setter, Collections nur read-only nach aussen, Änderungen nur über fachliche Methoden, die prüfen.

Was bedeutet „Wessen Job ist es?“

Muss der aktuelle Nutzer die Konsistenz herstellen, dann transaktional. Ist es Aufgabe eines anderen oder des Systems, dann eventual consistency.

Szenario: Zwei Nutzer planen gleichzeitig Backlog Items und Releases, einer bekommt immer einen Fehler. Was ist los?

Ein zu grosses Aggregate (Product mit allen Kindern) und optimistic locking. Lösung: Backlog Item, Release, Sprint als eigene Aggregates mit ProductId.

Szenario: Im Code-Review ändert eine @Transactional-Methode Order und Customer und speichert beide. Was sagen Sie?

Ich frage nach der echten Invariante. Gibt es keine, soll Order ein Event publizieren und Customer separat reagieren. Gibt es eine, ist vielleicht die Grenze falsch geschnitten.

Szenario: Ein Konsument verarbeitet OrderSubmitted, findet die Order aber nicht in der DB. Warum?

Das Event wurde vor dem Commit veröffentlicht, oder der Commit schlug fehl. Lösung: nach dem Commit publizieren oder Transactional Outbox.
