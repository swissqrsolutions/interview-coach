DDD strategisch: Bounded Context und Context Map

Kern: Strategisches DDD teilt eine grosse Domäne in Bounded Contexts, in denen je ein eigenes Modell und eine eigene Ubiquitous Language gilt. Die Context Map zeigt, wie diese Kontexte zusammenhängen. Sie zeigt auch, wer upstream und wer downstream ist.

Antwort-Muster

Frage: Was ist ein Bounded Context und wie finden Sie seine Grenzen?

  1. Mechanismus: Ein Bounded Context ist die Grenze, in der ein Modell und seine Sprache einheitlich gelten. Ausserhalb heisst dasselbe Wort oft etwas anderes.
  2. Zahl: Beziehungen zwischen Kontexten beschreibt die Context Map mit Mustern wie Customer-Supplier, Conformist und Anticorruption Layer.
  3. Trade-off: Ein einziges Modell für alles ist einfacher zu erklären, aber nicht machbar. Viele Kontexte brauchen Übersetzung an den Grenzen.
  4. Produktion: Ich suche Grenzen dort, wo die Sprache wechselt, und lege pro Kontext ein Team und einen Service fest.

1. Von der Domäne zur Context Map, in 6 Schritten

  1. Domäne verstehen: Entwickler und Fachleute sammeln gemeinsam die Geschäftsfunktionen und ihre Verbindungen. Ein Whiteboard oder Event Storming reicht.
  2. Subdomains finden: Core bringt Wettbewerbsvorteil. Supporting hält das Geschäft am Laufen, differenziert aber nicht. Generic ist ein gelöstes Problem, das man kaufen kann.
  3. Sprache hören: Fachleute nutzen in verschiedenen Bereichen leicht andere Wörter. Wo ein Wort die Bedeutung wechselt, liegt oft eine Grenze.
  4. Kontexte ziehen: Pro Grenze entsteht ein Bounded Context mit eigenem Modell. Es enthält nur, was dort relevant ist.
  5. Beziehungen klären: Für jede Verbindung klärt man, wer liefert (upstream) und wer konsumiert (downstream). Der Upstream beeinflusst den Downstream, nicht umgekehrt.
  6. Context Map zeichnen: Jede Linie bekommt ein Muster, zum Beispiel Customer-Supplier oder Anticorruption Layer. Die Karte zeigt auch Teamabhängigkeiten.

Microservices folgen oft den Kontexten. Ein Service sollte keinen Kontext überspannen. Ein Kontext kann aber mehrere Services haben.

2. Aufbau

  1. Bounded Context: Grenze, in der ein Modell einheitlich gilt. Meist folgt sie der Sprache der Fachleute.
  2. Ubiquitous Language: gemeinsame, genaue Sprache von Entwicklern und Fachleuten. Sie lebt im Code und in Gesprächen.
  3. Subdomain: ein Teil des Geschäfts. Die Typen sind Core, Supporting und Generic.
  4. Context Map: zeigt die Kontexte und die Beziehungen. Sie klärt auch Verantwortung der Teams.
  5. Upstream und Downstream: Der Pfeil zeigt den Einfluss. Der Upstream beeinflusst den Downstream, der Downstream nicht den Upstream.
  6. Beziehungsmuster: Partnership, Shared Kernel, Customer-Supplier, Conformist, Anticorruption Layer, Open Host Service, Published Language, Separate Ways.

3. Details

  1. Bounded Context: Nach Fowler teilt DDD grosse Modelle in Bounded Contexts. Ein einziges Modell für ein grosses System ist nach Evans weder machbar noch wirtschaftlich.
  2. Sprache als Grenze: Verschiedene Gruppen nutzen verschiedene Wörter. Ändert sich die Sprache, braucht es ein anderes Modell. Das Wort 'Zähler' kann in zwei Abteilungen etwas anderes bedeuten.
  3. Technische Gründe: Grenzen können auch aus Technik entstehen, zum Beispiel ein In-Memory-Modell gegen ein relationales Modell. Meist ist aber die Sprache der Hauptgrund.
  4. Ubiquitous Language: Sie muss genau sein, weil Software mit Unklarheit schlecht umgeht. Sie entwickelt sich mit dem Wissen des Teams weiter.
  5. Core, Supporting, Generic: Core-Subdomains verdienen die meiste Design-Arbeit. Generic löst man mit fertigen Lösungen. Supporting braucht Eigenentwicklung, aber keinen grossen Aufwand.
  6. Subdomain ist nicht gleich Context: Subdomains beschreiben das Geschäft (Problem). Bounded Contexts beschreiben die Lösung im Code. Ein Kontext kann eine Subdomain umsetzen.
  7. Customer-Supplier: Upstream-Downstream-Beziehung, bei der die Prioritäten des Downstreams in die Planung des Upstreams einfliessen. Die Teams verhandeln den Vertrag.
  8. Conformist: Der Downstream übernimmt das Modell des Upstreams ohne Übersetzung. Das spart Aufwand und macht den Downstream abhängig.
  9. Anticorruption Layer (ACL): Der Downstream baut eine Übersetzungsschicht, die sein Modell vor dem fremden Modell schützt. Das kostet Latenz und einen Baustein im Betrieb.
  10. Open Host Service und Published Language: Der Upstream bietet eine klare API für viele Konsumenten (OHS) in einem dokumentierten Format (PL). Bei Microservices ist das besonders wichtig.
  11. Partnership und Shared Kernel: Beide sind symmetrisch. Bei Partnership entwickeln zwei Teams gemeinsam und stimmen sich eng ab. Beim Shared Kernel teilen sie einen kleinen Teil von Modell und Code.
  12. Separate Ways: Zwei Kontexte haben keine Integration. Das ist erlaubt, wenn der Nutzen der Verbindung kleiner ist als der Aufwand.

4. Fallen

  • „Ein Bounded Context ist ein Microservice.“ → Falsch. Ein Kontext ist eine Modellgrenze. Ein Service sollte keinen Kontext überspannen. Ein Kontext kann mehrere Services haben.
  • „Ein einheitliches Modell für das ganze Unternehmen ist das Ziel.“ → Falsch. Evans nennt es weder machbar noch wirtschaftlich. Man baut mehrere Modelle mit Grenzen.
  • „Strategisches DDD heisst Entities und Aggregates.“ → Falsch. Das ist taktisches DDD. Strategisch sind Kontexte, Subdomains und Context Map.
  • „Subdomains und Bounded Contexts sind dasselbe.“ → Falsch. Subdomains gehören zum Geschäft, Kontexte zur Lösung. Sie decken sich oft, aber nicht immer.
  • „Upstream bedeutet, der Dienst ist wichtiger.“ → Falsch. Upstream heisst, er beeinflusst den Downstream. Der Downstream hat keinen Einfluss auf ihn.
  • „Eine ACL ist immer nötig.“ → Falsch. Bei kleinen Unterschieden ist ein Conformist einfacher. Die ACL lohnt sich, wenn das fremde Modell das eigene verschmutzen würde.

5. Selbsttest

Warum?

Warum teilt man eine Domäne in Bounded Contexts?

Ein Modell für alles wird zu gross und unklar. Kleine Kontexte haben ein klares Modell und eine klare Sprache.

Warum ist die Sprache der beste Hinweis auf eine Grenze?

Wo ein Wort die Bedeutung wechselt, braucht es ein anderes Modell. Das zeigt sich im Gespräch mit Fachleuten.

Warum braucht man eine Context Map?

Sie macht Abhängigkeiten zwischen Kontexten und Teams sichtbar und zeigt, wo Übersetzung nötig ist.

Wie innen?

Was ist ein Bounded Context?

Eine Grenze, in der ein Modell und seine Ubiquitous Language einheitlich gelten.

Was ist Upstream und Downstream?

Der Upstream beeinflusst den Downstream. Der Downstream hat keinen Einfluss auf den Upstream. Der Pfeil zeigt den Einfluss.

Wie funktioniert ein Anticorruption Layer?

Er übersetzt zwischen zwei Modellen. Das eigene Modell bleibt sauber, das fremde System bleibt unverändert.

Wie unterscheiden sich Open Host Service und Published Language?

OHS ist die klare Schnittstelle des Upstreams. PL ist das dokumentierte Austauschformat dazu.

Was ist ein Shared Kernel?

Zwei Kontexte teilen einen kleinen Teil von Modell und Code. Änderungen müssen beide Teams abstimmen.

Zahlen

Wie viele Subdomain-Typen gibt es?

Drei: Core, Supporting und Generic.

Wie viele Kontexte soll ein Service überspannen?

Keinen. Ein Service gehört zu genau einem Kontext.

Welche Muster sind symmetrisch?

Partnership und Shared Kernel.

Wie viele Modelle hat ein grosses System?

Mehrere. Ein einziges Modell ist laut Evans weder machbar noch wirtschaftlich.

Vergleich

Conformist vs Anticorruption Layer?

Conformist übernimmt das Modell des Upstreams. Die ACL übersetzt und schützt das eigene Modell, mit mehr Aufwand.

Shared Kernel vs Partnership?

Beim Shared Kernel teilen zwei Kontexte einen Teil von Modell und Code. Bei Partnership arbeiten zwei Teams eng zusammen, ohne dass ein Code geteilt sein muss.

Customer-Supplier vs Conformist?

Beim Customer-Supplier fliessen die Wünsche des Downstreams in die Planung des Upstreams ein. Beim Conformist hat der Downstream keinen Einfluss.

Strategisches vs taktisches DDD?

Strategisch: Kontexte, Sprache, Context Map. Taktisch: Entities, Aggregates, Domain Services innerhalb eines Kontexts.

Produktion

Warum ändern sich zwei Services immer gemeinsam?

Meist teilen sie ein Modell oder eine Datenbank. Die Kontextgrenze liegt falsch. Lösung: Grenze neu ziehen oder Verträge trennen.

Warum verschmutzt ein Altsystem unser neues Modell?

Dessen Begriffe lecken in den Code. Lösung: einen Anticorruption Layer an die Grenze setzen.

Szenario: Zwei Teams streiten über die Bedeutung von 'Kunde'. Was tun Sie?

Zwei Kontexte benennen, zum Beispiel Sales und Billing, jeder mit eigenem Modell. An der Grenze übersetzt man.

Szenario: Ein Altsystem soll Schritt für Schritt abgelöst werden. Wie schützen Sie das neue Modell?

Ein Anticorruption Layer zwischen neu und alt. Er übersetzt in beide Richtungen und kann später entfallen, wenn das Altsystem weg ist.

Design

Szenario: Ein Shop soll in Microservices zerlegt werden. Wo ziehen Sie die Grenzen?

Mit Fachleuten Subdomains und Sprache sammeln. Zum Beispiel Katalog, Bestellung, Zahlung. Pro Kontext ein Team und ein oder mehrere Services.

Wo investieren Sie das meiste Design?

In die Core-Subdomain. Generic kauft man, Supporting baut man einfach.

Wie dokumentieren Sie die Beziehungen?

Mit einer Context Map. Pro Linie das Muster und die Richtung Upstream zu Downstream.

Wann ist Separate Ways sinnvoll?

Wenn die Integration mehr kostet, als sie bringt. Die Kontexte entwickeln sich dann unabhängig.

Mehr

Gerüst

  • Warum? Grosse Domäne in überschaubare Modelle mit klarer Sprache teilen.
  • Wie innen? Bounded Context = ein Modell, eine Sprache. Context Map = Beziehungen mit Mustern und Richtung.
  • Zahlen Drei Subdomain-Typen, zwei symmetrische Muster, ein Service pro Kontext.
  • Vergleich Conformist übernimmt, ACL übersetzt. Shared Kernel teilt Code, Partnership teilt Erfolg.
  • Produktion Services ändern sich nur zusammen, Altsystem verschmutzt das Modell, Streit um Begriffe.
  • Design Sprache hören, Core zuerst, ACL an fremden Grenzen, Context Map pflegen.

Beispiel: Ein Anticorruption Layer zwischen Sales und Billing

record SalesCustomer(String id, String name, String status) {}
record Debtor(String accountNo, String legalName, boolean creditChecked) {}

static class SalesToBillingAcl {
  Debtor translate(SalesCustomer c) {
    if (!c.status().equals("WON")) throw new IllegalArgumentException("Nur gewonnene Kunden: " + c.id());
    return new Debtor("D-" + c.id(), c.name().trim(), false);
  }
}
Sales sieht  : SalesCustomer[id=42, name= Muster AG , status=WON]
Billing sieht: Debtor[accountNo=D-42, legalName=Muster AG, creditChecked=false]
ACL lehnt ab: Nur gewonnene Kunden: 43

Echte Ausgabe, Java 17.0.3. Die Klassen sind ein kleines Eigenbau-Beispiel.

  1. Dasselbe Konzept heisst in Sales Customer und in Billing Debtor. Jeder Kontext hat sein Modell.
  2. Die ACL übersetzt Namen und Felder. Sie räumt auch die Daten auf (trim).
  3. Billing kennt das Sales-Modell nicht. Ändert Sales sein Modell, passt man nur die ACL an.
  4. Die ACL lehnt einen Interessenten ab. Sie trägt eine Regel der Grenze.

Vergleich

  • Strategisches DDD: Kontexte, Sprache, Context Map. Die grosse Struktur.
  • Taktisches DDD: Entities, Aggregates, Domain Services. Das Modell innerhalb eines Kontexts.
  • Bounded Context vs Microservice: Kontext ist eine Modellgrenze. Service ist eine Deployment-Einheit. Meist ist es ein Service pro Kontext.
  • Core vs Supporting vs Generic: Wettbewerbsvorteil, nötig aber nicht differenzierend, gelöstes Problem.
  • Conformist vs ACL: übernehmen oder übersetzen.
  • Shared Kernel vs Published Language: geteilter Code gegen geteiltes Format.

Produktion

  1. Gemeinsame Datenbank über Kontexte: Änderungen brechen andere Teams. Lösung: pro Kontext eigene Daten, Austausch über API oder Events.
  2. Ein Wort, zwei Bedeutungen im Code: Missverständnisse und Bugs. Lösung: pro Kontext eine eigene Sprache und Übersetzung an der Grenze.
  3. Altsystem prägt das neue Modell: Fremde Begriffe wandern in den Code. Lösung: Anticorruption Layer.
  4. Zu viele kleine Kontexte: Viel Übersetzung und Abstimmung. Lösung: Kontexte zusammenlegen, wenn die Sprache gleich ist.
  5. Context Map veraltet: Teams wissen nicht, wer wen beeinflusst. Lösung: Karte mit der Architektur pflegen.
  6. Shared Kernel wächst: Immer mehr gemeinsamer Code, Teams bremsen sich. Lösung: klein halten oder trennen.

Diagnose: Werkzeuge und Befehle

  • Event Storming: ein Workshop mit Fachleuten. Er zeigt Ereignisse, Sprache und Grenzen.
  • Glossar pro Kontext: Wörter mit unterschiedlicher Bedeutung zeigen die Grenzen.
  • Abhängigkeitsgraph: zeigt, welche Services und Module sich gegenseitig aufrufen.
  • Change-Coupling: Git-Verlauf zeigt, welche Dateien oder Services immer zusammen geändert werden.
  • Context Map zeichnen: mit Pfeilen für Upstream und Downstream und dem Muster pro Linie.

Senior-Punkte

  1. Grenzen folgen der Sprache und den Teams, nicht der Technik.
  2. Core zuerst. Dort lohnt tiefes Modellieren. Generic kauft man.
  3. Eine ACL ist eine Versicherung mit Prämie. Sie kostet Latenz und Betrieb, schützt aber das Modell.
  4. Die Context Map ist auch eine Teamkarte. Sie zeigt, wer auf wen warten muss.
  5. Grenzen ändern sich. Man darf sie neu ziehen, wenn das Wissen wächst.
  6. Nicht jede Verbindung braucht Integration. Separate Ways ist eine gültige Entscheidung.
