Anti-Patterns und Code Smells

Kern: Ein Anti-Pattern ist eine häufige Lösung, die erst gut aussieht, aber mehr Probleme macht als löst. Ein Code Smell ist ein Oberflächen-Signal im Code, das oft auf ein tieferes Design-Problem zeigt (Fowler). Im Code-Review muss man beide benennen, die Folge erklären und ein Refactoring vorschlagen.

1. Wo sitzen die Anti-Patterns?

  1. Primitive Obsession sitzt an den Grenzen: Signaturen mit String, double, int statt eigener Typen.
  2. God Class sitzt meist in der Service-Schicht: eine Klasse, die alles weiss und alles tut. Fowler nennt den Smell Large Class.
  3. Service Locator versteckt sich in Methoden: Locator.get(...) statt Konstruktor-Parameter.
  4. Anemic Domain Model sitzt im Domain-Paket: Entities ohne Verhalten, alle Regeln im Service.
  5. Shotgun Surgery sieht man im Git-Log: Eine fachliche Änderung braucht Edits in vielen Dateien.
  6. Leaky Abstraction sitzt an Technikgrenzen: ORM, Collections, Remote-Aufrufe. Details der Implementierung schlagen durch.

2. Die Reise eines Code-Reviews (die Geschichte zum Merken)

  1. Überblick: Wie gross ist der Diff? Berührt eine kleine fachliche Änderung zehn Dateien, ist das Shotgun Surgery.
  2. Signaturen lesen: transfer(String, String, double, String) ist Primitive Obsession. Zwölf Konstruktor-Parameter zeigen eine God Class.
  3. Verantwortung prüfen: Liegt die Regel „versendete Bestellung nicht ändern“ im Service oder im Objekt? Liegt sie im Service, ist das Modell anämisch.
  4. Grenzen prüfen: Ruft Geschäftscode ApplicationContext.getBean() auf? Das ist ein Service Locator. Lädt eine Schleife Lazy-Beziehungen? Das ist eine Leaky Abstraction mit N+1.
  5. Kommentar schreiben: Smell benennen, konkrete Folge nennen, Refactoring aus Fowlers Katalog vorschlagen. Nie nur „unschön“.

3. Beispiel: Anti-Patterns zur Laufzeit sehen

// 1) Primitive Obsession: Argumente vertauscht, kompiliert trotzdem
transferBad("CH9300762011623852957", "CHF", 100.0, "CH5604835012345678009");
0.1 + 0.2;                                   // double für Geld
new Iban("CHF");                             // record mit Validierung im Compact Constructor
Money.chf("0.1").amount().add(Money.chf("0.2").amount());
// 2) Anemic: jeder setzt status und lines direkt; Rich: Order.addLine prüft den Status
// 3) Service Locator: ReportJob holt Clock über Locator.get(); ReportJobDi bekommt Clock im Konstruktor
// 4) Leaky Abstraction: for (i...) list.get(i) mit ArrayList und LinkedList, je 50 000 Elemente
1) Primitive obsession: swapped arguments compile
   100.0 CH5604835012345678009 from CH9300762011623852957 to CHF
   0.1 + 0.2 as double = 0.30000000000000004
   value object: invalid IBAN: CHF
   Money: 0.3
2) Anemic model: anyone can break the rule
   anemic: status=SHIPPED lines=[late item]
   rich: order is SHIPPED, cannot add late item
3) Service locator: fails at runtime, not at wiring
   no service registered for Clock
   DI with fake clock: report at 42
4) Leaky abstraction: List.get(i) on LinkedList
   ArrayList  loop with get(i):     5 ms (sum=1249975000)
   LinkedList loop with get(i):   863 ms (sum=1249975000)

Echte Ausgabe, OpenJDK/Oracle JDK 17.0.3 (java AntiDemo.java). Die Zeiten sind ein einzelner Lauf ohne Warm-up, nur die Grössenordnung zählt.

  1. Primitive Obsession: Zielkonto und Währung sind vertauscht. Der Compiler merkt nichts, weil alles String ist. Der Fehler fällt erst in der Buchhaltung auf.
  2. double für Geld: 0.1 + 0.2 ergibt 0.30000000000000004. BigDecimal in einem Money-Typ rechnet exakt.
  3. Value Object: Der Record Iban lehnt „CHF“ sofort ab. Ungültige Werte können gar nicht entstehen.
  4. Anemic Model: Ein versendeter Auftrag bekommt noch eine Position. Im reichen Modell verhindert addLine das selbst.
  5. Service Locator: ReportJob lässt sich bauen, scheitert aber erst bei run(). Mit Konstruktor-Injection fehlt die Abhängigkeit schon beim Erzeugen, und der Test nutzt einen Fake.
  6. Leaky Abstraction: Beide sind eine List, gleiches Ergebnis. Aber LinkedList.get(i) läuft die Liste ab. Die Schleife wird O(n²), hier etwa 170× langsamer.

4. Details, die Interviewer fragen

God Class (Large Class). Eine God Class ist eine Klasse, die zu viel weiss und zu viel tut. Sie verletzt SRP. Fowler führt den Smell als Large Class.

// schlecht: OrderService mit Pricing, Steuer, Versand, PDF, Mail, Export
@Service class OrderService { /* 3000 Zeilen, 15 Abhängigkeiten */ }
// besser: nach Fachlichkeit schneiden
class PricingService { ... }  class ShippingService { ... }  class InvoicePdfRenderer { ... }
  1. Erkennen: viele Zeilen und Methoden, viele Konstruktor-Parameter, Felder, die nur von einem Teil der Methoden genutzt werden, häufige Merge-Konflikte.
  2. Refactoring: Extract Class, Move Function, Move Field. Schritt für Schritt, jeder Schritt mit grünen Tests.
  3. Ursache: „Nur noch eine Methode dazu“ über Jahre. Kein Mensch plant eine God Class.

Anemic Domain Model – die Debatte. Ein Anemic Domain Model hat Domain-Objekte mit Daten, aber fast ohne Verhalten. Alle Regeln stehen in Services. Fowler nennt es 2003 ein Anti-Pattern: Es hat „alle Kosten eines Domain Models, ohne seine Vorteile“.

// anämisch: Regel im Service, Objekt ungeschützt
class Order { String status; List<Line> lines; /* Getter, Setter */ }
class OrderService { void addLine(Order o, Line l) { if (!o.getStatus().equals("NEW")) throw ...; o.getLines().add(l); } }
// reich: Regel im Objekt, Invariante geschützt
class Order {
  private OrderStatus status = NEW; private final List<Line> lines = new ArrayList<>();
  void addLine(Line l) { if (status != NEW) throw new IllegalStateException(...); lines.add(l); }
  List<Line> lines() { return List.copyOf(lines); }
}
  1. Argumente gegen anämisch: Regeln sind verstreut und doppelt. Jeder kann Invarianten brechen. Das ist prozeduraler Code in Objekt-Kleidung.
  2. Argumente dafür: Für einfaches CRUD ist ein Transaction Script (Fowler, PoEAA) oft angemessen. JPA-Entities mit Settern und Jackson-DTOs drängen in diese Richtung.
  3. Moderne Gegenposition: Ein funktionaler Stil mit unveränderlichen Records und reinen Funktionen ist nicht „anämisch“ im schlechten Sinn. Die Regeln sind zentral und testbar, nur nicht in der Klasse.
  4. Senior-Antwort: Es kommt auf die Komplexität der Regeln an. Wenig Logik: Transaction Script. Viele Invarianten: reiches Modell mit Aggregates (DDD).
  5. Evans: Die Application-Schicht bleibt dünn. Sie koordiniert und delegiert an Domain-Objekte.

Service Locator. Ein Service Locator ist ein Registry-Objekt, bei dem Code seine Abhängigkeiten zur Laufzeit selbst abholt.

// schlecht: versteckte Abhängigkeit, Fehler erst zur Laufzeit
class ReportJob { String run() { return "report at " + Locator.get(Clock.class).now(); } }
@Service class X { @Autowired ApplicationContext ctx; void run() { ctx.getBean(Mailer.class).send(...); } }
// besser: Abhängigkeit im Konstruktor sichtbar
class ReportJob { private final Clock clock; ReportJob(Clock clock) { this.clock = clock; } }
  1. Fowlers Sicht (2004): Beide Ansätze entkoppeln. Beim Locator fragt die Klasse explizit, bei DI kommt die Abhängigkeit von aussen. Für wiederverwendbare Komponenten bevorzugt er DI.
  2. Warum es im Review als Anti-Pattern gilt: Abhängigkeiten sind in Methoden versteckt. Jede Klasse hängt am Locator. Fehler kommen erst zur Laufzeit.
  3. Erlaubte Ausnahmen in Spring: ObjectProvider<T> für lazy oder optionale Beans, Infrastruktur-Code und Framework-Grenzen.

Shotgun Surgery. Shotgun Surgery heisst: Eine Änderung braucht viele kleine Edits in vielen Klassen (Fowler). Das Gegenstück ist Divergent Change: Eine Klasse ändert sich aus vielen verschiedenen Gründen.

// schlecht: MwSt-Satz und Rundung an vielen Stellen
double vat = amount * 0.081;   // in InvoiceService, PdfRenderer, ExportJob, StatsCalculator
// besser: eine Stelle für die Regel
record VatRate(BigDecimal rate) { Money applyTo(Money net) { ... } }
  1. Erkennen: Git-Historie mit vielen Dateien pro fachlicher Änderung. Copy-Paste-Duplikate. Gleiche switch-Blöcke.
  2. Refactoring: Move Function, Move Field, Combine Functions into Class, bei Bedarf Inline Class, um Verstreutes zu sammeln.

Primitive Obsession. Primitive Obsession heisst: Fachbegriffe wie Geld, IBAN, E-Mail oder Zeitraum werden als String, double oder int dargestellt.

// schlecht
void transfer(String fromIban, String toIban, double amount, String currency)
// besser: Value Objects validieren bei der Erzeugung
record Iban(String value) { Iban { if (!value.matches("[A-Z]{2}\\d{2}[A-Z0-9]{1,30}")) throw new IllegalArgumentException(...); } }
record Money(BigDecimal amount, Currency currency) { ... }
void transfer(Iban from, Iban to, Money amount)
  1. Folgen: vertauschte Argumente, Validierung an vielen Stellen, Rundungsfehler, keine Fachsprache im Code.
  2. Refactoring: Replace Primitive with Object, Introduce Parameter Object, bei Typcodes Replace Type Code with Subclasses.
  3. Java 17: Records machen Value Objects billig: equals, hashCode, unveränderlich, Validierung im Compact Constructor.

Leaky Abstraction. Eine Leaky Abstraction ist eine Abstraktion, deren Implementierungsdetails trotzdem durchschlagen. Spolskys Gesetz: Alle nicht-trivialen Abstraktionen sind zu einem gewissen Grad undicht.

// schlecht: JPA sieht aus wie Objekte, macht aber SQL pro Zugriff (N+1)
for (Order o : orderRepo.findAll()) total += o.getLines().size();   // 1 + N Abfragen
// besser: Datenbedarf explizit
@Query("select o from Order o join fetch o.lines") List<Order> findAllWithLines();
  1. Beispiele: List.get(i) auf LinkedList, ORM und N+1, Remote-Aufruf, der wie ein lokaler aussieht (Latenz, Timeouts), @Transactional mit Self-Invocation.
  2. Eigene Abstraktionen: Ein Repository-Interface mit Page-Typen von Spring Data oder SQL-Exceptions lässt Technik in die Domain lecken.
  3. Umgang: Kosten im Vertrag nennen (Javadoc, Methodenname wie findAllWithLines), Exceptions an der Grenze übersetzen, Messwerte statt Annahmen.

5. Vergleich

  • Anti-Pattern vs Code Smell: Ein Anti-Pattern ist eine bekannte schlechte Lösung. Ein Smell ist nur ein Hinweis, der falsch sein kann.
  • Shotgun Surgery vs Divergent Change: Eine Änderung, viele Klassen vs eine Klasse, viele Änderungsgründe.
  • God Class vs Facade: Eine Facade delegiert und ist dünn. Eine God Class enthält die Logik selbst.
  • Anemic Model vs Transaction Script: Transaction Script ist ein bewusster Stil für einfache Logik. Anemic Model ist ein Domain Model, das seine Regeln verloren hat.
  • Service Locator vs Dependency Injection: Ziehen (pull) vs bekommen (push). DI macht Abhängigkeiten im Konstruktor sichtbar.
  • Primitive Obsession vs Data Clumps: Ein Fachwert als Primitive vs mehrere Werte, die immer zusammen auftreten (z. B. amount und currency).

6. In der Produktion

  1. Falsches Konto belastet: Vertauschte String-Parameter. Fix: Iban-Typ, eigene Typen für IDs (CustomerId, OrderId).
  2. Rappen-Differenzen in Reports: double für Geld. Fix: BigDecimal oder Rappen als long, in einem Money-Typ.
  3. Ungültige Zustände in der DB: Anämische Entities mit öffentlichen Settern. Fix: Regeln in Methoden der Entity, Setter entfernen, DB-Constraints als zweite Linie.
  4. Langsame Seite nach Release: N+1 durch Lazy Loading. Fix: Fetch Join, Entity Graph oder DTO-Projektion.
  5. Startet, aber scheitert beim ersten Job: Service Locator findet kein Bean. Fix: Constructor Injection, damit der Kontext schon beim Start scheitert.
  6. Jede Änderung wird teuer: God Class mit Merge-Konflikten und Regressionen. Fix: Tests drumherum (Characterization Tests), dann Extract Class in kleinen Schritten.

7. Diagnose: Werkzeuge und Befehle

  • SonarQube: Cognitive Complexity, Klassengrösse, Duplikate, zu viele Parameter. Gut als Trend, nicht als Urteil.
  • Git: git log --format= --name-only | sort | uniq -c | sort -rn | head zeigt Hotspots. git log --stat pro Ticket zeigt Shotgun Surgery.
  • IntelliJ: „Locate Duplicates“, Dependency-Analyse, Refactorings Extract Class und Introduce Parameter Object.
  • Hibernate: spring.jpa.properties.hibernate.generate_statistics=true und SQL-Logging zeigen N+1.
  • Grep: getBean(, double amount, String iban, public void set in Entities.
  • ArchUnit: Regeln wie „Domain hängt nicht von Spring Data ab“ gegen lecke Abstraktionen.

8. Senior-Punkte

  1. Ein Smell ist eine Frage, kein Urteil. Im Review frage ich nach dem Grund, bevor ich einen Umbau verlange.
  2. Kommentar-Formel: Smell → konkrete Folge → kleines Refactoring. „Unschön“ ist kein Review-Kommentar.
  3. Value Objects sind der billigste Gewinn. Records für Geld, IBAN und IDs verhindern ganze Fehlerklassen.
  4. Anemic oder rich ist eine Kontextfrage. Einfache CRUD-Services brauchen kein reiches Modell. Komplexe Regeln schon.
  5. Grosse Refactorings klein schneiden. Erst Tests, dann kleine Schritte, jeder Schritt deploybar. Kein „Big Bang“.
  6. Jede Abstraktion leckt. Man muss die Schicht darunter verstehen: SQL unter JPA, Netzwerk unter REST, Proxy unter Annotation.

B. Code-Reviews in Bitbucket bei CARIAD oder die SonarQube-Funde bei MATCH.)

10. Fallen

  • „Ein Code Smell ist immer ein Bug.“ → Falsch. Er ist ein Hinweis. Manchmal ist der Code bewusst so.
  • „Anemic Domain Model ist immer falsch.“ → Zu einfach. Für einfache Logik ist Transaction Script legitim. Problem ist ein Modell, das Regeln haben sollte und sie nicht hat.
  • „Fowler lehnt Service Locator komplett ab.“ → Falsch. Er sieht beide als Entkopplung, bevorzugt DI aber für wiederverwendbare Komponenten.
  • „double reicht für Geld, man rundet am Ende.“ → Falsch. Rundungsfehler summieren sich. BigDecimal oder Rappen als long.
  • „Eine God Class teilt man in einem grossen Refactoring.“ → Riskant. Erst Tests, dann kleine Schritte.
  • „Eine gute Abstraktion leckt nie.“ → Falsch. Jede nicht-triviale Abstraktion leckt. Man muss die Kosten kennen.

11. Fragen

Was ist ein Anti-Pattern?

Eine häufige Lösung, die zuerst gut aussieht, aber mehr Probleme erzeugt als löst. Es gibt meist eine bekannte bessere Alternative.

Was ist ein Code Smell?

Ein Oberflächen-Signal, das oft auf ein tieferes Design-Problem zeigt. Es ist ein Hinweis, kein Beweis.

Was ist eine God Class?

Eine Klasse, die zu viel weiss und tut. Viele Abhängigkeiten, viele Zeilen, viele Gründe zur Änderung. Fowler nennt den Smell Large Class.

Wie zerlegen Sie eine God Class?

Erst Tests als Sicherheitsnetz. Dann Gruppen von Feldern und Methoden finden, die zusammengehören, und mit Extract Class herauslösen. In kleinen Schritten.

Was ist ein Anemic Domain Model?

Domain-Objekte mit Daten, aber ohne Verhalten. Alle Regeln liegen in Services. Fowler nennt es ein Anti-Pattern.

Ist ein Anemic Domain Model immer schlecht?

Nein. Für einfache CRUD-Logik ist ein Transaction Script angemessen. Bei vielen Invarianten gehört die Logik ins Objekt.

Warum führen JPA und Spring oft zu anämischen Modellen?

Entities brauchen einen Default-Konstruktor, Tutorials zeigen Getter und Setter, und Services wirken als natürlicher Ort für Logik. Regeln kann man trotzdem in Entity-Methoden legen.

Was ist ein Service Locator?

Eine Registry, bei der Code seine Abhängigkeiten selbst abholt. In Spring zum Beispiel ApplicationContext.getBean() im Geschäftscode.

Warum ist Service Locator im Review ein Problem?

Abhängigkeiten sind versteckt, jede Klasse hängt am Locator, und fehlende Beans fallen erst zur Laufzeit auf.

Was sagt Fowler zu Service Locator vs DI?

Beide trennen Konfiguration von Nutzung. Für Klassen, die in mehreren Anwendungen laufen, bevorzugt er DI. Wichtiger ist für ihn das Prinzip der Trennung.

Ist ObjectProvider ein Service Locator?

Technisch ein gezielter Lookup, aber typisiert und im Konstruktor sichtbar. Für lazy oder optionale Beans ist das akzeptiert.

Was ist Shotgun Surgery?

Eine fachliche Änderung braucht viele kleine Edits in vielen Klassen. Die Regel ist verstreut statt an einem Ort.

Shotgun Surgery vs Divergent Change?

Shotgun Surgery: eine Änderung, viele Klassen. Divergent Change: eine Klasse, viele verschiedene Änderungsgründe.

Was ist Primitive Obsession?

Fachwerte wie Geld, IBAN oder IDs als String, int oder double. Folge: vertauschte Argumente und verstreute Validierung.

Wie beheben Sie Primitive Obsession in Java 17?

Mit Records als Value Objects und Validierung im Compact Constructor. Fowler: Replace Primitive with Object.

Warum nie double für Geld?

double ist binär und kann 0.1 nicht exakt darstellen. 0.1 + 0.2 ergibt 0.30000000000000004. Besser BigDecimal oder Rappen als long.

Was ist eine Leaky Abstraction?

Eine Abstraktion, deren Implementierung trotzdem durchschlägt. Beispiel: JPA versteckt SQL, aber Lazy Loading erzeugt N+1-Abfragen.

Nennen Sie ein JDK-Beispiel für eine Leaky Abstraction.

List.get(i) ist bei ArrayList O(1), bei LinkedList O(n). Gleiches Interface, ganz andere Kosten.

Wie vermeiden Sie N+1 mit JPA?

Fetch Join, Entity Graph oder DTO-Projektion. Hibernate-Statistiken oder SQL-Logging zeigen das Problem.

Wie formulieren Sie einen Review-Kommentar zu einem Smell?

Smell benennen, konkrete Folge nennen, kleines Refactoring vorschlagen. Beispiel: „double amount: Rundungsfehler. Vorschlag: Money mit BigDecimal.“

Welche Tools helfen beim Finden von Smells?

SonarQube, IntelliJ-Inspektionen und Duplikat-Suche, ArchUnit für Architekturregeln, Git-Historie für Hotspots.

Was sind Data Clumps?

Werte, die immer zusammen auftreten, z. B. amount und currency. Fix: Introduce Parameter Object oder ein eigener Typ.

Was ist Feature Envy?

Eine Methode nutzt mehr Daten einer anderen Klasse als ihrer eigenen. Fix: Move Function in die Klasse mit den Daten. Oft ein Zeichen für ein anämisches Modell.

Szenario: Sie reviewen eine Methode transfer(String, String, double, String). Was schreiben Sie?

Primitive Obsession: Argumente lassen sich vertauschen, double rundet falsch. Vorschlag: Iban- und Money-Records mit Validierung.

Szenario: Ein neues MwSt-Feld braucht Änderungen in zwölf Dateien. Was ist los und was tun Sie?

Shotgun Surgery. Ich sammle die MwSt-Logik in einem Typ oder Service mit Move Function, dann ändert sich künftig eine Stelle.

Szenario: Die Übersichtsseite ist nach einem Release langsam, das SQL-Log zeigt hunderte gleiche SELECTs. Was ist das?

N+1 durch Lazy Loading, eine Leaky Abstraction von JPA. Fix: Fetch Join oder DTO-Projektion, dann mit Statistiken die Anzahl Abfragen prüfen.
