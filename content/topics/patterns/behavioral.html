Verhaltensmuster

Patterns · Tier 1 · Quellen: GoF „Design Patterns“, Kapitel 5 (Behavioral Patterns); Spring Framework Reference: „Standard and Custom Events“ (ApplicationContext), Spring Security Reference: Servlet Architecture (FilterChainProxy, SecurityFilterChain); Java SE 21 API (java.util.Observer deprecated seit 9, Comparator, Runnable); Fowler, Refactoring-Katalog (Replace Conditional with Polymorphism)

Kern: Verhaltensmuster (Behavioral Patterns) sind Muster, die regeln, wer was entscheidet und wie Objekte zusammenarbeiten. Sie lösen ein Problem: grosse if/switch-Blöcke und eng gekoppelte Aufrufe. In modernem Java sind viele davon nur noch ein Lambda hinter einem funktionalen Interface.

1. Wo sitzen die Verhaltensmuster?

  1. Chain of Responsibility: Eine Kette von Handlern bearbeitet den Request. Jeder kann ihn weitergeben oder stoppen. Beispiel: Spring Security SecurityFilterChain.
  2. Strategy: Ein austauschbarer Algorithmus hinter einem Interface. Beispiel: Comparator.
  3. State: Das Verhalten hängt vom Zustand ab. Jeder Zustand kennt seine erlaubten Übergänge. Beispiel: Bestellung NEW → PAID → SHIPPED.
  4. Template Method: Eine Basisklasse legt die Schritte fest. Unterklassen füllen einzelne Schritte. Beispiel: HttpServlet.service() ruft doGet().
  5. Command: Ein Auftrag wird ein Objekt. Man kann ihn speichern, in eine Queue legen, rückgängig machen. Beispiel: Runnable an einen ExecutorService.
  6. Observer: Ein Subjekt meldet Ereignisse an alle registrierten Zuhörer. Beispiel: @EventListener in Spring.

2. Die Reise eines Events (die Geschichte zum Merken)

  1. Publish: ImportService ruft publisher.publishEvent(new TradeImported(id)). Er kennt die Zuhörer nicht. Das ist lose Kopplung.
  2. Verteilen: Laut Spring-Doku sind Listener standardmässig synchron. publishEvent() blockiert, bis alle fertig sind. Die Reihenfolge steuert @Order.
  3. Gleiche Transaktion: Synchrone Listener laufen im Transaktionskontext des Publishers. Ein Fehler im Listener kann die ganze Transaktion zurückrollen.
  4. Ein Listener wirft: Ohne Error-Handler läuft die Exception zurück zum Publisher. Die folgenden Listener laufen nicht mehr.
  5. Fixes: @TransactionalEventListener läuft erst nach dem Commit. @Async entkoppelt den Thread; Exceptions erreichen den Aufrufer dann nicht mehr (Spring-Doku). Für garantierte Zustellung: Outbox-Pattern.

3. Beispiel: alle sechs Muster in einem Programm

// 1) Strategy: Map<String, Comparator<Trade>>, Auswahl zur Laufzeit
trades.sort(strategies.get(key));
// 2) Observer: drei Listener, der zweite wirft
bus.subscribe(audit); bus.subscribe(e -> { throw new RuntimeException("mail server down"); }); bus.subscribe(stats);
// 3) Template Method: importFile() ist final, parse() abstrakt, validate() ein Hook
// 4) Command: Deposit(acc, amount) mit execute()/undo(), History als Deque
// 5) Chain: auth → rate limit → "200 OK"
// 6) State: enum OrderState { NEW, PAID, SHIPPED, CANCELLED } mit next(event)

3) Template Method

Echte Ausgabe, OpenJDK/Oracle JDK 17.0.3 (java BehavioralDemo.java). Die Firmennamen sind Beispieldaten.

  1. Strategy: Gleiche Liste, gleicher sort-Aufruf, anderes Ergebnis. Nur das Strategie-Objekt wechselt.
  2. Observer: Der Statistik-Listener läuft nie, weil der Mail-Listener wirft. Genau das passiert bei synchronen Spring-Events ohne Error-Handler.
  3. Template Method: Beide Importer teilen die Schrittfolge. Nur TradeReportImporter überschreibt den Hook validate.
  4. Command: Jede Einzahlung ist ein Objekt in der History. undo() nimmt die letzte zurück: 150 → 100.
  5. Chain: Ohne Token stoppt der erste Handler. Der Spammer kommt durch Auth, stoppt aber beim Rate-Limit. Normal läuft die ganze Kette.
  6. State: SHIPPED erlaubt kein cancel. Der verbotene Übergang wird zu einer klaren Exception statt zu falschen Daten.

4. Details, die Interviewer fragen

Strategy. Eine Strategy kapselt einen austauschbaren Algorithmus hinter einem Interface. Der Aufrufer wählt die Strategie, ohne den Algorithmus zu kennen.

// schlecht: if-Kaskade, wächst mit jedem Format
if (format.equals("CSV")) { ... } else if (format.equals("XLSX")) { ... } else if (format.equals("PDF")) { ... }
// besser: ein Interface, eine Klasse pro Format, Spring sammelt alle
interface ExportStrategy { String format(); byte[] export(Report r); }
@Service class ExportService {
  private final Map<String, ExportStrategy> byFormat;
  ExportService(List<ExportStrategy> all) { byFormat = all.stream().collect(toMap(ExportStrategy::format, s -> s)); }
  byte[] export(String format, Report r) { return byFormat.get(format).export(r); }
}
  1. JDK: Comparator, ThreadPoolExecutor mit RejectedExecutionHandler.
  2. Spring: PlatformTransactionManager, HttpMessageConverter, PasswordEncoder. Spring wählt oder delegiert je nach Konfiguration.
  3. Lambda: Hat das Interface nur eine Methode, ist die Strategie oft nur ein Lambda.

Observer. Ein Observer registriert sich bei einem Subjekt und wird bei Änderungen benachrichtigt. Das Subjekt kennt nur das Listener-Interface.

// schlecht: ImportService kennt alle Folgeschritte
void importFile(...) { save(...); auditService.log(...); mailService.send(...); statsService.recalc(...); }
// besser: Event publizieren, Listener entscheiden selbst
void importFile(...) { save(...); publisher.publishEvent(new TradeImported(messageId)); }
@Component class StatsListener {
  @TransactionalEventListener   // Standard-Phase: AFTER_COMMIT
  void on(TradeImported e) { stats.recalc(e.messageId()); }
}
  1. JDK: java.util.Observer und Observable sind seit Java 9 deprecated. Heute: eigene Listener-Interfaces, PropertyChangeListener, Flow (Reactive Streams).
  2. Push vs Pull: Push schickt die Daten im Event. Pull schickt nur eine ID, der Listener lädt selbst.
  3. Nachteile: Ablauf schwer nachzuvollziehen, Reihenfolge implizit, Memory Leaks durch nie abgemeldete Listener.
  4. Observer vs Pub/Sub: Observer ist im Prozess und meist synchron. Pub/Sub mit Kafka ist verteilt, asynchron und persistent.

Template Method. Eine Template Method definiert das Gerüst eines Algorithmus in einer Basisklasse. Unterklassen überschreiben einzelne Schritte, nicht die Reihenfolge.

// schlecht: Copy-Paste in zwei Importern, Schritt "validate" in einem vergessen
// besser: final Template, abstrakte Schritte, optionale Hooks
abstract class ReportImporter {
  final void importFile(String name) { String raw = read(name); List<String> rows = parse(raw); validate(rows); store(rows); }
  abstract List<String> parse(String raw);
  void validate(List<String> rows) { }   // Hook
}
// moderner: Komposition mit Callback statt Vererbung
jdbcTemplate.query("select * from trade where day = ?", (rs, i) -> new Trade(rs.getString("id")), day);
  1. JDK: AbstractList (nur get und size implementieren), HttpServlet.service() mit doGet/doPost, InputStream.read(byte[]) über read().
  2. Spring: JdbcTemplate, TransactionTemplate, RestTemplate nutzen eine Callback-Variante: Der feste Ablauf ist in der Template-Klasse, der variable Schritt kommt als Lambda.
  3. Hollywood-Prinzip: „Don't call us, we'll call you.“ Die Basisklasse ruft die Unterklasse.
  4. Nachteil: Vererbung koppelt stark. Tiefe Hierarchien sind schwer zu ändern. Darum oft Strategy oder Callback statt Template Method.

Command. Ein Command verpackt einen Auftrag als Objekt. Man kann ihn speichern, in eine Queue legen, loggen, wiederholen oder rückgängig machen.

// schlecht: Aufruf sofort und direkt, kein Undo, keine Queue
account.balance += 100;
// besser: Command-Objekt mit execute/undo
interface Command { void execute(); void undo(); }
record Deposit(Account acc, long amount) implements Command {
  public void execute() { acc.balance += amount; }
  public void undo()    { acc.balance -= amount; }
}
executor.submit(() -> importer.importFile(name));   // Runnable ist ein Command
  1. Einsatz: Undo/Redo, Job-Queues, Retry, Audit-Log, CQRS-Commands.
  2. Command vs Strategy: Command ist ein Auftrag (was tun). Strategy ist eine Art, etwas zu tun (wie).
  3. Serialisierte Commands: Eine Nachricht in einer Queue ist ein Command über Prozessgrenzen. Dann braucht sie Idempotenz.

Chain of Responsibility. Eine Chain of Responsibility gibt eine Anfrage durch eine Kette von Handlern. Jeder Handler bearbeitet sie, gibt sie weiter oder stoppt.

// schlecht: alle Prüfungen in einer Methode
if (!hasToken(req)) return 401; if (isRateLimited(req)) return 429; if (!isValid(req)) return 400; ...
// besser: Servlet-Filter, jeder mit einer Aufgabe
class RateLimitFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) throws ... {
    if (limiter.tryAcquire(req)) chain.doFilter(req, res);   // weiter
    else res.setStatus(429);                                   // Kette stoppt
  }
}
  1. Spring Security: FilterChainProxy wählt die erste passende SecurityFilterChain (Spring-Security-Doku). Ein Filter stoppt die Kette, indem er chain.doFilter nicht aufruft.
  2. Weitere Beispiele: HandlerInterceptor in Spring MVC, Logger-Hierarchie, Validierungsketten.
  3. Risiko: Niemand bearbeitet die Anfrage, oder die Reihenfolge ist falsch. Die Reihenfolge muss explizit und getestet sein.

State. Ein State-Objekt kapselt das Verhalten eines Zustands. Das Objekt ändert sein Verhalten, wenn sich sein Zustand ändert.

// schlecht: Status als String, Regeln verstreut
if (order.status.equals("SHIPPED") && action.equals("cancel")) ...   // in fünf Klassen ähnlich
// besser: Enum mit Übergängen an einer Stelle
enum OrderState {
  NEW  { OrderState next(String ev) { return switch (ev) { case "pay" -> PAID; case "cancel" -> CANCELLED; default -> fail(ev); }; } },
  PAID { OrderState next(String ev) { return switch (ev) { case "ship" -> SHIPPED; case "cancel" -> CANCELLED; default -> fail(ev); }; } },
  SHIPPED   { OrderState next(String ev) { return fail(ev); } },
  CANCELLED { OrderState next(String ev) { return fail(ev); } };
  abstract OrderState next(String event);
}
  1. Persistenz: In der DB steht der Zustand als Spalte. Übergänge brauchen ein atomares Update, z. B. UPDATE ... SET status='PAID' WHERE id=? AND status='NEW'.
  2. State vs Strategy: Gleiche Struktur. Bei State wechselt das Objekt den Zustand selbst. Bei Strategy wählt der Client.
  3. Grösser: Bei vielen Zuständen und Regeln hilft eine State-Machine-Bibliothek oder eine Workflow-Engine.

5. Vergleich

  • Strategy vs Template Method: Strategy nutzt Komposition und tauscht den ganzen Algorithmus. Template Method nutzt Vererbung und tauscht Schritte.
  • Strategy vs State: Strategy wählt der Client. State wechselt sich selbst nach Ereignissen.
  • Command vs Strategy: Command ist ein Auftrag mit Daten (was). Strategy ist ein Algorithmus (wie).
  • Observer vs Chain: Observer benachrichtigt alle Zuhörer. Chain gibt an den nächsten weiter, einer kann stoppen.
  • Chain vs Decorator: Ähnliche Struktur. Decorator ruft immer weiter. Ein Handler in der Chain darf stoppen.
  • Observer vs Messaging (Kafka): Observer im Prozess, flüchtig. Messaging verteilt, persistent, wiederholbar.

6. In der Produktion

  1. Event-Listener rollt die Transaktion zurück: Ein synchroner Listener wirft, der Import ist verloren. Fix: @TransactionalEventListener(phase = AFTER_COMMIT) oder Fehler im Listener fangen.
  2. Event geht verloren: AFTER_COMMIT-Listener läuft, aber die App stürzt vorher ab. Fix: Outbox: Event in derselben Transaktion in eine Tabelle schreiben.
  3. @Async-Fehler verschwinden: Exceptions erreichen den Aufrufer nicht. Fix: AsyncUncaughtExceptionHandler, Logging, Metriken.
  4. Falsche Filter-Reihenfolge: Logging-Filter vor Auth loggt Tokens, oder Rate-Limit nach teurer Arbeit. Fix: Reihenfolge mit @Order festlegen und testen.
  5. Verbotene Zustandsübergänge: Zwei Worker setzen dieselbe Nachricht gleichzeitig auf „Processing“. Fix: Übergang als bedingtes, atomares SQL-Update.
  6. Template-Hierarchie verkrustet: Fünf Ebenen abstrakter Klassen, jede Änderung bricht Unterklassen. Fix: auf Strategy und Komposition umbauen.

7. Diagnose: Werkzeuge und Befehle

  • Spring Events: logging.level.org.springframework.context.event=DEBUG; Breakpoint in SimpleApplicationEventMulticaster.multicastEvent zeigt alle Listener.
  • Security-Filterkette: logging.level.org.springframework.security=DEBUG zeigt die Filter in Reihenfolge pro Request.
  • Actuator: /actuator/mappings zeigt Handler und Filter.
  • Zustände: SQL-Abfrage wie SELECT status, count(*) FROM message GROUP BY status zeigt hängende Zustände.
  • Review-Signal: Wiederholte switch/if auf denselben Typ oder Status → Strategy oder State.

8. Senior-Punkte

  1. Lambdas ersetzen viele Klassen. Strategy, Command und Callback sind in Java oft ein funktionales Interface. Eine eigene Klasse lohnt sich bei Zustand oder viel Logik.
  2. Events entkoppeln Code, aber nicht Fehler. Synchrone Events teilen Thread und Transaktion. Die Phase muss eine bewusste Entscheidung sein.
  3. Zustände gehören an eine Stelle und in die Datenbank als atomarer Übergang. Ein Enum im Code reicht ohne atomares Update nicht.
  4. Komposition vor Vererbung: Template Method nur für kurze, stabile Abläufe. Sonst Strategy oder Callback.
  5. Reihenfolge ist Teil des Vertrags bei Chains und Listenern. Sie gehört in Code und Tests, nicht in Zufall.
  6. Kein Muster ohne zweiten Fall. Ein einziger Algorithmus braucht kein Strategy-Interface.

9. Aus dem Projekt

„Bei MATCH hat jede Nachricht einen Status (Pending → Processing → Completed/Failed); Spark übernimmt Nachrichten atomar mit UPDATE ... OUTPUT INSERTED.*, und hängende Processing-Einträge gehen nach einem Timeout zurück auf Pending – das ist State mit atomaren Übergängen.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Spring-Events sind asynchron.“ → Falsch. Standardmässig synchron im selben Thread und in derselben Transaktion.
  • „@TransactionalEventListener garantiert die Zustellung.“ → Falsch. Stürzt die App nach dem Commit ab, ist das Event weg. Dafür: Outbox.
  • „Strategy und State sind dasselbe.“ → Struktur gleich, Absicht anders. Bei State steuert das Objekt den Wechsel selbst.
  • „java.util.Observer ist der Standard für Observer in Java.“ → Falsch. Seit Java 9 deprecated.
  • „JdbcTemplate ist eine klassische Template Method.“ → Nur teilweise. Es nutzt Callbacks (Komposition), nicht Unterklassen.
  • „In einer Chain bearbeitet immer genau ein Handler.“ → Falsch. In Servlet-Filterketten arbeiten oft alle Handler, einer kann stoppen.

11. Fragen

Was sind Verhaltensmuster?

Muster für Zusammenarbeit und Verantwortung zwischen Objekten. GoF nennt elf, z. B. Strategy, Observer, Template Method, Command, Chain of Responsibility, State.

Was ist das Strategy-Pattern?

Ein austauschbarer Algorithmus hinter einem Interface. Der Aufrufer wählt die Strategie zur Laufzeit. Beispiel: Comparator.

Wie bauen Sie Strategy mit Spring?

Ein Interface und eine @Component pro Strategie. Spring injiziert alle als List oder Map, der Service wählt per Schlüssel.

Welches Refactoring führt zu Strategy oder State?

Replace Conditional with Polymorphism aus Fowlers Katalog. Wiederholte switch-Blöcke auf einen Typ sind das Signal.

Was ist das Observer-Pattern?

Zuhörer registrieren sich bei einem Subjekt und werden bei Ereignissen benachrichtigt. Das Subjekt kennt nur das Listener-Interface.

Sind Spring-Events synchron oder asynchron?

Standardmässig synchron. publishEvent blockiert, bis alle Listener fertig sind, und Listener laufen in der Transaktion des Publishers.

Was passiert, wenn ein synchroner Listener eine Exception wirft?

Ohne Error-Handler geht sie zum Publisher zurück. Folgende Listener laufen nicht, und die Transaktion kann zurückrollen.

Was macht @TransactionalEventListener?

Der Listener läuft in einer Phase der Transaktion, standardmässig nach dem Commit. Gibt es keine Transaktion, läuft er standardmässig gar nicht.

Was ist mit Exceptions in @Async-Listenern?

Sie erreichen den Aufrufer nicht. Man braucht einen AsyncUncaughtExceptionHandler und Monitoring.

Warum ist java.util.Observer deprecated?

Seit Java 9. Laut Javadoc ist das Event-Modell zu begrenzt: Die Reihenfolge der Benachrichtigungen ist nicht festgelegt, und Zustandsänderungen entsprechen nicht eins zu eins den Benachrichtigungen. Dazu ist Observable eine Klasse, kein Interface.

Observer vs Kafka Pub/Sub?

Observer läuft im Prozess und ist flüchtig. Kafka ist verteilt, persistent und erlaubt Replay.

Was ist eine Template Method?

Eine finale Methode in der Basisklasse legt die Schritte fest. Unterklassen implementieren einzelne Schritte oder Hooks.

Wo gibt es Template Method im JDK?

AbstractList, HttpServlet.service mit doGet und doPost, InputStream.read(byte[]) auf Basis von read().

Ist JdbcTemplate eine Template Method?

In der Callback-Variante. Der feste Ablauf liegt in JdbcTemplate, der variable Teil kommt als RowMapper oder Lambda, ohne Vererbung.

Was ist das Hollywood-Prinzip?

„Don't call us, we'll call you.“ Das Framework oder die Basisklasse ruft den eigenen Code auf, nicht umgekehrt.

Was ist das Command-Pattern?

Ein Auftrag als Objekt. Er lässt sich in Queues legen, loggen, wiederholen und rückgängig machen. Beispiel: Runnable an einen ExecutorService.

Command vs Strategy?

Command beschreibt was getan wird, mit Daten. Strategy beschreibt wie etwas getan wird.

Was ist Chain of Responsibility?

Eine Anfrage läuft durch eine Kette von Handlern. Jeder bearbeitet, gibt weiter oder stoppt. Beispiel: Servlet-Filter.

Wie funktioniert die Spring-Security-Filterkette?

FilterChainProxy wählt die erste passende SecurityFilterChain. Deren Filter laufen nacheinander. Ein Filter stoppt, indem er chain.doFilter nicht aufruft.

Chain vs Decorator?

Ähnliche Struktur. Ein Decorator ruft immer weiter. Ein Handler in der Chain darf die Verarbeitung beenden.

Was ist das State-Pattern?

Das Verhalten hängt vom Zustand ab. Jeder Zustand kennt seine erlaubten Übergänge. Verbotene Übergänge werfen eine klare Exception.

State vs Strategy?

Gleiche Struktur. Bei Strategy wählt der Client. Bei State wechselt das Objekt den Zustand nach Ereignissen selbst.

Wie sichern Sie Zustandsübergänge in der Datenbank?

Mit einem bedingten Update, z. B. WHERE status = 'NEW'. Nur ein Aufrufer gewinnt. Die Anzahl geänderter Zeilen zeigt, ob der Übergang geklappt hat.

Welche Muster ersetzen Lambdas in Java?

Viele Strategy-, Command- und Callback-Klassen. Jedes funktionale Interface mit einer Methode kann ein Lambda sein.

Szenario: Nach einem Import wird eine Mail verschickt. Fällt der Mailserver aus, ist der Import weg. Was ändern Sie?

Der Mail-Listener läuft synchron in der Transaktion. Ich nutze @TransactionalEventListener nach dem Commit und fange Fehler dort ab. Muss die Mail sicher raus, schreibe ich ein Outbox-Event.

Szenario: Im Review sehen Sie denselben switch über den Exportformat-Typ in vier Klassen. Was schlagen Sie vor?

Ein ExportStrategy-Interface mit einer Klasse pro Format. Spring sammelt sie in einer Map. Neue Formate sind dann neue Klassen ohne Edit.

Szenario: Zwei Worker verarbeiten dieselbe Nachricht doppelt. Wie lösen Sie das?

Den Zustandsübergang Pending → Processing als atomares, bedingtes Update. Nur ein Worker bekommt die Zeile. Dazu Stale-Recovery für hängende Processing-Einträge.
