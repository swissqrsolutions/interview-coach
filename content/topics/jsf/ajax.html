Ajax und Partial Rendering

Kern: Bei Ajax in Faces schickt das Skript faces.js nur einen Teil der Seite zum Server. execute wählt, was der Server verarbeitet. render wählt, was er neu zeichnet. Die Antwort ist eine Partial Response in XML, und der Browser ersetzt nur diese Teile im DOM.

Antwort-Muster

Frage: Wie funktioniert Ajax in JSF?

  1. Mechanismus: faces.ajax.request schickt Formular-Daten mit execute- und render-Listen. Der Server verarbeitet die execute-Teile, rendert die render-Teile und antwortet mit XML.
  2. Zahl: Standard bei f:ajax ist execute @this und render @none. Es laufen dieselben sechs Phasen wie bei einem normalen Request.
  3. Trade-off: Weniger Daten und weniger Neuzeichnen. Dafür braucht man gültige IDs und muss Messages selbst ins render nehmen.
  4. Produktion: Passiert beim Klick nichts, prüfe ich Validierungsfehler, Namenscontainer-IDs und ob das Ziel im DOM existiert.

1. Ein Ajax-Request in 6 Schritten

  1. Event: Der Benutzer klickt oder ändert ein Feld. Die Tag-Definition (f:ajax) hat dafür ein DOM-Event gewählt. Ohne Angabe wählt die Komponente selbst, zum Beispiel action oder valueChange.
  2. Request senden: Das Skript ruft faces.ajax.request(source, event, options) auf. Es legt den Request in eine Warteschlange und sendet ihn nacheinander. Das Formular muss die Quelle enthalten.
  3. Server erkennt Ajax: PartialViewContext.isAjaxRequest() ist wahr, wenn der Header Faces-Request den Wert partial/ajax hat.
  4. execute: processPartial lässt die Phasen 2 bis 5 nur für die Komponenten der execute-Liste laufen. Die übrigen Felder bleiben unberührt.
  5. render: Phase 6 schreibt nur die Komponenten der render-Liste. Der Writer ist der PartialResponseWriter.
  6. Response anwenden: Der Browser parst das XML und ersetzt die Ziele im DOM. Die Callbacks melden begin, complete und success.

2. Aufbau

  1. Tag und Skript: f:ajax hängt ein Verhalten an eine Komponente. Es erzeugt den Aufruf von faces.ajax.request.
  2. faces.js: Ab Faces 4.0 heisst das Skript faces.js und das Objekt window.faces. Vorher hiess es jsf.js und window.jsf.
  3. PartialViewContext: Er hält die execute- und render-IDs des Requests. Er führt die Verarbeitung nur für diese IDs aus.
  4. Search Expressions: Sie lösen Angaben wie @form oder :form:table zu Komponenten auf.
  5. PartialResponseWriter: Er schreibt statt der ganzen Seite nur das XML mit den Änderungen.
  6. Callbacks: onevent und onerror sind JavaScript-Funktionen für Status und Fehler.

3. Details

  1. f:ajax-Standardwerte: execute ist @this. render ist @none. disabled ist false. Der Event hängt von der Komponente ab. Wer ein Ziel zeichnen will, muss render setzen.
  2. Keywords in Faces: @all, @none, @this, @form, @parent, @namingcontainer, @composite, @child(n), @previous, @next, @root und @id(id). Sie lösen sich zu IDs auf, darum bleiben sie bei Umbenennungen stabil.
  3. Client-IDs und Namenscontainer: Ein h:form ist ein Namenscontainer. Seine Kinder haben IDs wie form:table. Aus einem anderen Container braucht man die absolute Form mit führendem Trenner, zum Beispiel :form2:display.
  4. execute gegen render: execute wählt die Komponenten für die Phasen 2 bis 5. render wählt sie für Phase 6. Ein Feld, das nicht in execute steht, wird nicht gelesen, validiert oder ins Model geschrieben.
  5. listener und immediate: Die Methode im Attribut listener läuft bei einem AjaxBehaviorEvent. Mit immediate="true" wird dieser Event in Apply Request Values ausgeliefert, sonst in Invoke Application.
  6. Validierungsfehler: Schlägt eine Validierung in execute fehl, springt Faces zu Render Response. Das Model bleibt alt. Die Meldung erscheint nur, wenn die Message-Komponente im render steht.
  7. resetValues: Mit resetValues="true" setzt Faces die Eingabewerte der render-Komponenten zurück. Dann zeigen sie wieder die Werte aus dem Bean. Man darf dabei keine @-Keywords nutzen.
  8. delay: Mit delay in Millisekunden sendet das Skript nur den letzten Aufruf. Das ist gut für Eingaben bei jedem Tastendruck.
  9. Partial Response: Das XML hat ein changes-Element mit update, insert, delete, attributes und eval. Dazu kommen extension, redirect und error. Ein redirect macht Navigation mit Redirect auch bei Ajax möglich.
  10. Statusmeldungen: Das Skript meldet begin, complete und success. Fehler heissen emptyResponse, malformedError und serverError. Bei einem error-Element liefert serverError Name und Text.
  11. Formular nötig: faces.ajax.request wirft einen Fehler, wenn das Element nicht in einem Formular liegt oder jakarta.faces.ViewState fehlt. Bei Datei-Upload im execute braucht das Formular multipart/form-data.
  12. f:ajax in Composites: Seit Faces 4.0 meint @this bei execute und render in einem Composite die Composite-Komponente.
  13. PrimeFaces p:ajax: process ist standardmässig @this. update ersetzt render. Das Skript basiert auf jQuery und nutzt nicht das Client-API von Mojarra oder MyFaces. Ohne Formular antwortet jeder Request mit HTTP 405.
  14. PrimeFaces-Extras: partialSubmit sendet nur die verarbeiteten Felder. global="false" löst kein ajaxStatus aus. PrimeFaces.current().ajax().update("id") aktualisiert zur Laufzeit. @widgetVar(name), @row(n) und @(.klasse) sind zusätzliche Selektoren.
  15. process="@all" ist eine Falle: Alle Pflichtfelder der Seite werden geprüft. Schlägt eines fehl, läuft die Action nicht. Die PrimeFaces-Doku zeigt das mit einem leeren Pflichtfeld neben einem Dropdown.

4. Fallen

  • „Ajax läuft ohne die 6 Phasen.“ → Falsch. Es sind dieselben Phasen, nur für execute- und render-Teile.
  • „f:ajax aktualisiert standardmässig die Seite.“ → Falsch. Der Standard für render ist @none.
  • „execute @this validiert das ganze Formular.“ → Falsch. Nur die eigene Komponente wird verarbeitet.
  • „Die ID im update ist immer die ID aus der XHTML-Datei.“ → Falsch. Im Namenscontainer ist es die Client-ID mit Präfix, aus anderen Containern mit führendem Trenner.
  • „Ein Ajax-Fehler zeigt immer eine Meldung.“ → Falsch. Ohne Message-Komponente im render sieht der Benutzer nichts.
  • „f:ajax und p:ajax haben dieselben Attribute.“ → Falsch. f:ajax nutzt execute und render. p:ajax nutzt process und update.

5. Selbsttest

Warum?

Warum nutzt man Partial Rendering?

Es spart Daten und Neuzeichnen. Zustand wie Scroll-Position und Eingaben in anderen Feldern bleibt erhalten. Der Server rendert nur die geänderten Teile.

Warum sollte execute klein sein?

Alles in execute wird gelesen, validiert und ins Model geschrieben. Ein kleines execute vermeidet Fehler in unbeteiligten Feldern und spart Daten.

Warum zeigt der Klick manchmal nichts?

Eine Validierung in execute ist fehlgeschlagen, und die Message steht nicht im render. Die Action lief nicht. Ich nehme die Messages ins render.

Wie innen?

Wie läuft ein Ajax-Request in Faces ab?

faces.ajax.request sendet execute und render mit dem Formular. Der Server verarbeitet die execute-Teile und rendert die render-Teile. Die Antwort ist XML, das das Skript ins DOM überträgt.

Woran erkennt der Server einen Ajax-Request?

Am Header Faces-Request mit dem Wert partial/ajax. PartialViewContext.isAjaxRequest liest ihn.

Was steht in der Partial Response?

Ein changes-Element mit update, insert, delete, attributes und eval. Dazu extension, redirect und error. Das ViewState-Update ist auch enthalten.

Welche Request-Parameter sendet Faces?

jakarta.faces.partial.ajax, jakarta.faces.source, jakarta.faces.partial.execute, jakarta.faces.partial.render und jakarta.faces.ViewState.

Wie werden IDs in einem Namenscontainer aufgelöst?

Relativ vom Namenscontainer der Quelle. Für andere Container nimmt man die absolute Form mit führendem Trenner, zum Beispiel :form2:display.

Was macht resetValues?

Es setzt die Eingabewerte der render-Komponenten zurück. So zeigen sie nach einem Validierungsfehler wieder den Bean-Wert.

Was ist der Unterschied zu PrimeFaces p:ajax?

p:ajax nutzt process und update statt execute und render und arbeitet mit jQuery statt dem Faces-Client-API. process ist standardmässig @this.

Zahlen

Welche Standardwerte hat f:ajax?

execute ist @this, render ist @none, disabled ist false. Der Event hängt von der Komponente ab.

Wie viele Phasen laufen bei Ajax?

Dieselben sechs. execute-Komponenten durchlaufen Phase 2 bis 5, render-Komponenten Phase 6.

Seit wann heisst das Skript faces.js?

Seit Faces 4.0. Vorher hiess es jsf.js, und das Objekt window.jsf heisst jetzt window.faces.

Welche Keywords kennt Faces für execute und render?

@all, @none, @this, @form, @parent, @namingcontainer, @composite, @child(n), @previous, @next, @root und @id(id).

Vergleich

execute gegen render?

execute bestimmt, was der Server liest, validiert und ins Model schreibt. render bestimmt, was er neu zeichnet.

f:ajax gegen p:ajax?

f:ajax ist Standard und nutzt execute und render. p:ajax ist PrimeFaces mit process und update, jQuery und Extras wie partialSubmit und Selektoren.

Ajax gegen Full Postback?

Ajax sendet und zeichnet Teile, der Full Postback die ganze Seite. Beide durchlaufen die 6 Phasen. Ajax spart Daten, braucht aber saubere IDs.

Ajax gegen eigenes REST-Frontend?

Faces-Ajax hält den Zustand auf dem Server und liefert HTML. Ein REST-Frontend hält den Zustand im Browser und liefert JSON. Faces ist einfacher zu bauen, kostet aber Speicher pro Benutzer.

Produktion

Szenario: Ein Ajax-Update einer Tabelle zeigt nichts Neues. Was prüfen Sie?

Ich schaue in den Browser-Netzwerk-Tab, ob die Antwort das Element enthält. Dann prüfe ich die ID mit Namenscontainer und ob das Ziel im DOM existiert. Auch ein Validierungsfehler kommt in Frage.

Szenario: Der Abbrechen-Button meldet „Pflichtfeld fehlt“. Was ändern Sie?

Der Button verarbeitet das ganze Formular. Ich setze execute oder process auf @this oder nutze immediate.

Szenario: PrimeFaces-Requests liefern HTTP 405. Woran liegt das?

Die Komponente liegt in keinem Formular. PrimeFaces braucht ein Formular für Ajax. Ich lege sie in ein h:form oder ein Fallback-Formular.

Szenario: Nach einem Session-Timeout passiert bei Ajax-Klicks nichts. Was tun Sie?

Der Server wirft eine ViewExpiredException, die als error-Element ankommt. Ich behandle sie mit einem ExceptionHandler und leite auf eine Seite um, oder nutze onerror.

Design

Wie wählen Sie execute und render?

execute nur die Felder, die die Action braucht. render nur die geänderten Teile samt Messages. @form oder @all vermeide ich.

Wie lässt man abhängige Dropdowns laufen?

Das erste Dropdown bekommt ein Ajax-Verhalten mit execute @this und render auf das zweite. Die Methode füllt die Auswahl. Pflichtfelder daneben bleiben ausserhalb.

Wie verhindert man zu viele Requests bei Eingaben?

Mit delay am Ajax-Verhalten. Das Skript sendet nur den letzten Aufruf innerhalb der Verzögerung.

Wie zeigt man Fehler zuverlässig?

Mit einer Messages-Komponente, die immer im render steht, zum Beispiel über p:autoUpdate in PrimeFaces. Dazu ein globaler onerror-Handler.

Mehr

Gerüst

  • Warum? Nur Teile der Seite senden und neu zeichnen. Weniger Daten, Zustand bleibt.
  • Wie innen? faces.ajax.request, Header partial/ajax, execute Phasen 2 bis 5, render Phase 6, XML-Antwort.
  • Zahlen f:ajax: execute @this, render @none. Sechs Phasen. faces.js seit Faces 4.0.
  • Vergleich execute gegen render. f:ajax gegen p:ajax. Ajax gegen Full Postback.
  • Produktion Klick ohne Wirkung (Validierung, ID, DOM). Cancel validiert alles. HTTP 405 ohne Formular.
  • Design Kleines execute, Messages im render, delay bei Eingaben, resetValues.

Beispiel: abhängige Dropdowns mit f:ajax und p:ajax

<h:form id="f">
  <!-- Standard-Faces -->
  <h:selectOneMenu id="kanton" value="#{ortBean.kanton}">
    <f:selectItems value="#{ortBean.kantone}"/>
    <f:ajax listener="#{ortBean.ladeOrte}" execute="@this" render="ort msg"/>
  </h:selectOneMenu>
  <h:selectOneMenu id="ort" value="#{ortBean.ort}">
    <f:selectItems value="#{ortBean.orte}"/>
  </h:selectOneMenu>
  <h:inputText id="email" value="#{ortBean.email}" required="true"/>
  <h:message id="msg" for="email"/>

  <!-- PrimeFaces: process und update -->
  <p:selectOneMenu id="kanton2" value="#{ortBean.kanton}">
    <f:selectItems value="#{ortBean.kantone}"/>
    <p:ajax listener="#{ortBean.ladeOrte}" process="@this" update="ort"/>
  </p:selectOneMenu>
  <p:commandButton value="Speichern" action="#{ortBean.speichern}"
                   process="@form" update="@form :growl" partialSubmit="true"/>
</h:form>
<p:growl id="growl"/>

Nicht ausgeführt. Auf dieser Maschine läuft keine Faces-Laufzeit. Die Attribute und Standardwerte stammen aus der Faces- und PrimeFaces-Dokumentation.

  1. execute="@this" verarbeitet nur das Dropdown. Das leere Pflichtfeld email blockiert die Methode ladeOrte nicht.
  2. render="ort msg" zeichnet das zweite Dropdown und die Message neu. Ohne msg sähe man keine Validierungsfehler.
  3. Bei p:ajax heissen die Attribute process und update. Der Standard für process ist @this.
  4. Der Button nutzt @form und :growl. Das Growl liegt ausserhalb des Formulars, darum steht der Trenner davor.
  5. partialSubmit="true" sendet nur die Felder, die verarbeitet werden.

Vergleich

  • f:ajax: Standard, execute und render, Skript faces.js.
  • p:ajax und PrimeFaces-Komponenten: process und update, jQuery, Selektoren, partialSubmit, ajaxStatus.
  • Full Postback: Ganze Seite, einfach, aber mehr Daten und Sprung im Browser.
  • Faces f:websocket: Push vom Server statt Ajax-Pull. Seit Faces 4.0 gibt es dort ein Attribut onerror.

Produktion

  1. Klick ohne Wirkung: Eine Validierung schlägt still fehl. Lösung: Message-Komponente im render, PhaseListener oder Breakpoint am Setter.
  2. Falsche ID im update: Ein Ziel in einem anderen Namenscontainer wird nicht gefunden. Lösung: absolute ID mit führendem Trenner oder ein Keyword.
  3. Ziel nicht im DOM: Ein Element mit rendered="false" existiert im Browser nicht und kann nicht ersetzt werden. Lösung: Umschliessendes Element ins render nehmen.
  4. process="@all": Fremde Pflichtfelder blockieren die Action. Lösung: process auf das Nötige begrenzen.
  5. HTTP 405 bei PrimeFaces: Es gibt kein Formular. Lösung: Komponente in ein Formular oder ein leeres Fallback-Formular am Seitenanfang.
  6. Alte jsf.js-Aufrufe: Eigenes JavaScript ruft jsf.ajax auf. Lösung: auf faces.ajax umstellen, wenn man auf Faces 4 wechselt.

Diagnose: Werkzeuge und Befehle

  • Browser DevTools, Network: Den Request mit jakarta.faces.partial.execute und jakarta.faces.partial.render ansehen. Die XML-Antwort prüfen.
  • Console: faces.ajax.addOnEvent(fn) und faces.ajax.addOnError(fn) loggen Status und Fehler.
  • PhaseListener mit ANY_PHASE: Zeigt, welche Phasen für den Ajax-Request laufen.
  • PROJECT_STAGE Development: Mehr Hinweise im Log, zum Beispiel zu nicht angezeigten Messages.
  • PartialViewContext.getExecuteIds() und getRenderIds() im Debugger: Welche IDs sind aufgelöst?
  • PrimeFaces: p:lifecycle zeigt die Dauer der Phasen. Die Dokumentation zu Search Expressions hilft bei „cannot find component“.

Senior-Punkte

  1. Ajax hat keinen eigenen Lebenszyklus. Wer die sechs Phasen versteht, versteht auch jeden Ajax-Fehler.
  2. execute klein, render genau. Das ist die wichtigste Stellschraube für Korrektheit und Daten.
  3. Messages gehören ins render. Sonst gibt es stille Fehler.
  4. Keywords statt Hard-coded-IDs. @form und @parent überstehen Umbauten.
  5. Version bewusst. Mit Faces 4.0 hat sich das Skript zu faces.js geändert. PrimeFaces 16 verlangt Faces 4.0 oder neuer.
  6. Stateful kostet. Jeder Ajax-Request hält die View auf dem Server. Das wirkt auf Speicher und Skalierung.
