Managed Beans, CDI, Scopes

JSF · Tier 2 · Quellen: Jakarta Faces 4.0 Release-Seite (Entfernung von @ManagedBean, neues @ClientWindowScoped), Jakarta Faces 4.1 Specification (Kap. 5.6 CDI-Integration, 7.8 State Saving), Faces 4.1 API-Doku (ViewScoped, ClientWindowScoped, FlowScoped), Mojarra 4.x WebConfiguration (Defaults), PrimeFaces 16 Doku „Performance" und „DataTable – Data binding"

Kern: Ein Backing Bean ist ein Java-Objekt, das Daten und Actions für eine JSF-Seite hält. Seit Jakarta Faces 4.0 ist es immer ein CDI-Bean mit @Named und einem Scope. Der Scope bestimmt, wie lange das Objekt lebt und wer es teilt.

1. Wo sitzen die Beans?

  1. Facelets-Seite: greift mit EL auf das Bean zu, z. B. #{orderBean.total}.
  2. EL-Resolver: findet das Bean über seinen Namen. Der Name kommt aus @Named, Standard ist der Klassenname mit kleinem Anfangsbuchstaben.
  3. CDI-Container: erzeugt das Bean beim ersten Zugriff (lazy). Bei normalen Scopes bekommt man einen Client-Proxy. Der Proxy leitet jeden Aufruf an die Instanz des aktuellen Kontexts weiter.
  4. Kontexte: Jeder Scope hat einen Speicherort. Application im ServletContext, Session in der HttpSession, View-Scope in der View Map innerhalb der Session.
  5. Lebensende: Endet der Kontext, ruft CDI @PreDestroy auf und gibt die Instanz frei.

2. Die Reise eines @ViewScoped-Beans (die Geschichte zum Merken)

  1. Erster Aufruf. Der Benutzer öffnet die Boden-Suchseite. Die Seite liest #{soilSearchBean.results}. CDI erzeugt das Bean und ruft @PostConstruct auf.
  2. Ablage. Das Bean liegt in der View Map der aktuellen UIViewRoot. Die View Map liegt in der Session.
  3. Ajax-Postbacks. Der Benutzer filtert, sortiert, blättert. Jeder Postback auf die gleiche View findet dieselbe Instanz. Filter und Auswahl bleiben erhalten.
  4. Navigation. Eine Action liefert ein Outcome zu einer anderen View. Die View Map wird zerstört, @PreDestroy läuft.
  5. Die Lücke. Schliesst der Benutzer den Tab oder klickt einen normalen Link (GET), erfährt der Server nichts. Das Bean bleibt, bis die Implementierung alte View Maps verdrängt (Mojarra: com.sun.faces.numberOfActiveViewMaps, Standard 25) oder die Session endet.

3. Beispiel: drei Scopes nebeneinander

@Named @RequestScoped
public class ReqCounter implements Serializable { int n; public int next() { return ++n; } }

@Named @ViewScoped                         // jakarta.faces.view.ViewScoped
public class ViewCounter implements Serializable { int n; public int next() { return ++n; } }

@Named @SessionScoped                      // jakarta.enterprise.context.SessionScoped
public class SessCounter implements Serializable { int n; public int next() { return ++n; } }

<!-- counter.xhtml -->
<h:form>
  <h:outputText id="out" value="req=#{reqCounter.next()} view=#{viewCounter.next()} sess=#{sessCounter.next()}"/>
  <h:commandButton value="+1"><f:ajax render="out"/></h:commandButton>
</h:form>
1. GET counter.xhtml         req=1 view=1 sess=1
2. Klick (Ajax)              req=1 view=2 sess=2
3. Klick (Ajax)              req=1 view=3 sess=3
4. F5 (neuer GET)            req=1 view=1 sess=4
5. zweiter Tab, GET          req=1 view=1 sess=5

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Annahme: jeder Ausdruck wird pro Request genau einmal ausgewertet.

  1. RequestScoped: jeder Request hat eine neue Instanz. Darum immer 1.
  2. ViewScoped: zählt über Ajax-Postbacks weiter. Ein neuer GET erzeugt eine neue View und damit ein neues Bean.
  3. SessionScoped: zählt über alles weiter, auch über Tabs. Zwei Tabs teilen sich dieselbe Instanz.

4. Details, die Interviewer fragen

  1. @ManagedBean ist weg: Jakarta Faces 4.0 hat die eigenen Managed Beans (@ManagedBean, jakarta.faces.bean.*) entfernt. In JSF 2.3 waren sie schon deprecated. Heute: @Named + CDI-Scope.
  2. Die Scopes:
    • @RequestScoped: ein HTTP-Request. Für Formulare ohne Zustand.
    • @ViewScoped (jakarta.faces.view): solange der Benutzer auf derselben View bleibt. Für Ajax-Seiten, Tabellen, Dialoge.
    • @SessionScoped: die ganze HTTP-Session. Für Login-Daten, Sprache.
    • @ApplicationScoped: eine Instanz für alle. Für Caches, Konfiguration. Muss thread-sicher sein.
    • @ConversationScoped: von conversation.begin() bis end(). Für mehrstufige Abläufe.
    • @FlowScoped (Faces Flows): solange der Benutzer in einem definierten Flow ist, z. B. einem Wizard.
    • @ClientWindowScoped (neu in 4.0): pro Browser-Fenster/Tab, über den ClientWindow-Mechanismus.
    • @Dependent: Standard ohne Annotation. Lebt so lange wie das Objekt, in das es injiziert wird.
  3. Passivating Scopes: Session, Conversation, View, Flow und ClientWindow sind passivating. Ihre Beans müssen Serializable sein. Sonst meldet CDI einen Deployment-Fehler.
  4. Client-Proxy: Normale Scopes injizieren einen Proxy, nicht die Instanz. Darum darf man ein @RequestScoped-Bean in ein @SessionScoped-Bean injizieren. Der Proxy liefert pro Request die richtige Instanz.
  5. Proxy-Regeln: Ein normal-scoped Bean braucht einen nicht-privaten No-Arg-Konstruktor und darf nicht final sein. Sonst kann CDI keinen Proxy bauen.
  6. Die falsche ViewScoped-Annotation (JSF 2.x): javax.faces.bean.ViewScoped gehörte zu @ManagedBean. Mit @Named ignorierte CDI sie. Das Bean verhielt sich wie @Dependent und verlor den Zustand bei jedem Request. Richtig: javax.faces.view.ViewScoped, heute jakarta.faces.view.ViewScoped.
  7. @PostConstruct statt Konstruktor: Im Konstruktor sind Injektionen noch nicht gesetzt. Initialisierung gehört in @PostConstruct. Bei Proxys kann der Konstruktor zudem mehrfach laufen.
  8. Injizierbare JSF-Objekte: Mit @Inject bekommt man FacesContext, ExternalContext, Flash, HttpSession und mehr. Das sagt die Spezifikation (Kap. 5.6).
  9. @ManagedProperty heute: jakarta.faces.annotation.ManagedProperty mit @Inject injiziert einen EL-Wert, z. B. #{param.id}.
  10. Flash: #{flash} hält Werte über genau einen Redirect. Typisch für „Gespeichert"-Meldungen nach Post-Redirect-Get.
  11. Thread-Sicherheit: Request- und View-Beans sieht meist nur ein Thread. Session-Beans können parallele Requests sehen (zwei Tabs). Application-Beans sehen immer viele Threads.

5. Vergleich

  • JSF @ManagedBean (bis 2.3): eigener Container, eigene Scopes (javax.faces.bean), Injektion mit @ManagedProperty. In 4.0 entfernt.
  • CDI @Named: Standard-Container von Jakarta EE. Interceptors, Events, Qualifier, Producer. Funktioniert auch in EJB, REST und Batch.
  • Spring Beans mit JSF: Mit dem SpringBeanFacesELResolver löst EL Spring-Beans auf. Spring kennt keinen View-Scope von Haus aus. JoinFaces bringt JSF in Spring Boot.
  • @ViewScoped vs. @SessionScoped: View-Scope ist pro Tab und Seite getrennt und räumt bei Navigation auf. Session-Scope teilt alles über Tabs und wächst bis Logout.
  • @ViewScoped vs. @ConversationScoped: View-Scope ist an eine Seite gebunden. Conversation umfasst mehrere Seiten, aber man muss begin() und end() selbst aufrufen.
  • OmniFaces @ViewScoped: Variante, die beim Verlassen der Seite (unload) das Bean sofort zerstört. Löst die Speicher-Lücke beim Tab-Schliessen.

6. In der Produktion

  1. Session wird riesig: Grosse Listen und Entitäten in @SessionScoped- oder @ViewScoped-Beans, mal 25 View Maps pro Session. Lösung: nur IDs und Filter halten, Daten mit LazyDataModel nachladen. Die PrimeFaces-Doku rät, Daten nicht in langlebigen Scopes zu halten.
  2. NotSerializableException: Beim Session-Replikat oder beim Neustart (Session-Persistenz) scheitert die Serialisierung. Ursache: nicht serialisierbares Feld, z. B. ein Service ohne Proxy. Lösung: Abhängigkeiten per @Inject (Proxys sind serialisierbar) oder transient.
  3. Zustand geht bei jedem Klick verloren: Falsche ViewScoped-Annotation oder @Named ohne Scope (@Dependent). Lösung: richtige Imports prüfen.
  4. Daten zwischen Tabs vermischt: Ein Wizard-Zustand liegt in @SessionScoped. Tab 2 überschreibt Tab 1. Lösung: @ViewScoped, @FlowScoped oder @ClientWindowScoped.
  5. Race Conditions: Ein @ApplicationScoped-Cache mit HashMap verliert Einträge. Lösung: ConcurrentHashMap oder ein echter Cache.
  6. LazyInitializationException: Ein View-Bean hält eine Hibernate-Entität. Beim nächsten Ajax-Request ist die Session zu. Lösung: benötigte Daten im Service laden (Fetch Join, DTO) oder neu laden.

7. Diagnose: Werkzeuge und Befehle

  • Heap Dump (jcmd <pid> GC.heap_dump) mit Eclipse MAT: Wer hält die grössten Objekte in der HttpSession?
  • Session-Grösse messen: Session-Attribute serialisieren und Bytes zählen, z. B. in einem Test oder Filter.
  • @PostConstruct und @PreDestroy loggen: zeigt, wann ein Bean wirklich entsteht und stirbt.
  • Weld-Logging (CDI-Implementierung in WildFly/GlassFish): zeigt Deployment-Fehler wie nicht serialisierbare Beans.
  • Mojarra-Parameter com.sun.faces.numberOfActiveViewMaps (Standard 25): begrenzt View Maps pro Session.
  • Lasttest mit mehreren Tabs: deckt geteilten Session-Zustand auf.

8. Senior-Punkte

  1. So kurz wie möglich. Request vor View vor Session. Jeder längere Scope kostet Speicher pro Benutzer.
  2. IDs statt Entitäten halten. Langlebige Beans speichern Filter, Seite und ausgewählte ID. Die Daten lädt man nach.
  3. View-Scope ist der Standard für Ajax-Seiten. Aber man muss seine Lücke kennen: Tab zu heisst nicht Bean weg.
  4. Serializable von Anfang an. Clustering oder Session-Persistenz kommt später oft dazu. Nachrüsten ist teuer.
  5. Bean = Präsentation, Service = Logik. Backing Beans rufen Services auf. Transaktionen und Regeln gehören in den Service. So bleibt die Logik ohne JSF testbar.
  6. Migration auf CDI planen: Bei JSF 2.x → Faces 4 muss jedes @ManagedBean umgestellt werden. Das ist ein eigener Schritt mit Tests.

10. Fallen

  • „@ManagedBean geht in Faces 4 noch.“ → Falsch. In 4.0 entfernt. Nur CDI.
  • „@ViewScoped endet, wenn der Tab geschlossen wird.“ → Falsch. Der Server merkt das nicht. Es endet bei Navigation, Verdrängung oder Session-Ende.
  • „@Named allein ist Request-Scope.“ → Falsch. Ohne Scope ist es @Dependent. @Model ist @Named + @RequestScoped.
  • „Ein kürzerer Scope darf nicht in einen längeren injiziert werden.“ → Falsch für normale Scopes. Der Client-Proxy löst das. Nur bei @Dependent lebt die Instanz mit dem Ziel.
  • „Session-Beans sind thread-sicher.“ → Falsch. Zwei Tabs können parallel zugreifen.
  • „Initialisierung im Konstruktor ist okay.“ → Falsch. Injektionen sind dort noch null. @PostConstruct nutzen.

11. Fragen

Was ist ein Backing Bean?

Ein Java-Objekt mit Daten und Actions für eine JSF-Seite. Die Seite greift per EL darauf zu.

Wie definiert man ein Bean in Jakarta Faces 4?

Mit @Named und einem CDI-Scope, z. B. @Named @ViewScoped. @ManagedBean gibt es seit 4.0 nicht mehr.

Warum wurde @ManagedBean entfernt?

CDI kann alles und mehr: Scopes, Interceptors, Events, Qualifier. Zwei Container nebeneinander waren doppelt und verwirrend.

Welche Scopes gibt es?

Request, View, Session, Application, Conversation, Flow, ClientWindow und Dependent.

Wie lange lebt ein @ViewScoped-Bean?

Solange Postbacks auf dieselbe View gehen. Es endet bei Navigation zu einer anderen viewId oder bei Session-Ende.

Wo liegt ein @ViewScoped-Bean?

In der View Map der UIViewRoot. Diese liegt in der Session.

Was passiert mit einem @ViewScoped-Bean, wenn der Tab geschlossen wird?

Nichts sofort. Es bleibt, bis die Implementierung alte View Maps verdrängt oder die Session abläuft. OmniFaces @ViewScoped räumt beim Unload auf.

Warum müssen View- und Session-Beans Serializable sein?

Es sind passivating Scopes. Die Session kann auf Disk geschrieben oder im Cluster repliziert werden.

Was ist @Dependent?

Der Standard-Scope ohne Annotation. Die Instanz lebt so lange wie das Objekt, in das sie injiziert wurde. Kein Proxy.

Was ist ein Client-Proxy?

CDI injiziert bei normalen Scopes einen Stellvertreter. Er leitet jeden Aufruf an die Instanz des aktuellen Kontexts weiter.

Darf ich ein RequestScoped-Bean in ein SessionScoped-Bean injizieren?

Ja. Der Proxy liefert pro Request die aktuelle Instanz.

Was war der Klassiker-Fehler mit ViewScoped in JSF 2.x?

@Named mit javax.faces.bean.ViewScoped. CDI ignorierte die Annotation, das Bean war Dependent und verlor den Zustand. Richtig war javax.faces.view.ViewScoped.

Warum @PostConstruct statt Konstruktor?

Im Konstruktor sind Injektionen noch nicht gesetzt. @PostConstruct läuft danach, genau einmal pro Instanz.

Was ist @ClientWindowScoped?

Ein Scope pro Browser-Fenster, neu in Faces 4.0. Er trennt Zustand zwischen Tabs derselben Session.

Wann @ConversationScoped?

Für Abläufe über mehrere Seiten mit klarem Start und Ende. Man ruft conversation.begin() und end() selbst auf.

Was ist der Flash Scope?

Ein Speicher, der genau einen Redirect überlebt. Typisch für Erfolgsmeldungen nach Post-Redirect-Get.

Wann @ApplicationScoped?

Für Daten, die für alle gleich sind: Konfiguration, Lookup-Listen, Caches. Der Code muss thread-sicher sein.

Welche JSF-Objekte kann man injizieren?

Unter anderem FacesContext, ExternalContext, Flash und HttpSession, direkt mit @Inject.

Was ist @Model?

Ein CDI-Stereotyp: @Named plus @RequestScoped.

Wie bindet man Spring-Beans in JSF?

Mit SpringBeanFacesELResolver in der faces-config.xml. Für View-Scope braucht Spring einen eigenen Scope oder JoinFaces.

Was gehört in ein Backing Bean, was nicht?

Hinein: UI-Zustand, Aufruf von Services, Messages. Nicht hinein: Transaktionen, Fachlogik, SQL.

Szenario: Nach jedem Ajax-Klick sind die Filter einer Tabelle zurückgesetzt. Was prüfen Sie?

Den Scope: wahrscheinlich Request oder Dependent, oder die falsche ViewScoped-Annotation. Lösung: jakarta.faces.view.ViewScoped und Serializable.

Szenario: Der Server hat nach einigen Stunden OutOfMemoryError, im Heap Dump sind viele Sessions mit grossen Listen. Was tun Sie?

Grosse Listen aus View- und Session-Beans entfernen, nur IDs und Filter halten, LazyDataModel nutzen. Dazu Zahl der View Maps und Session-Timeout prüfen.

Szenario: Zwei Tabs mit dem gleichen Wizard überschreiben sich gegenseitig. Warum?

Der Zustand liegt in einem SessionScoped-Bean, das beide Tabs teilen. Lösung: ViewScoped, FlowScoped oder ClientWindowScoped.
