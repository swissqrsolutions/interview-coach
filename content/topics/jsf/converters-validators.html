Converter und Validatoren

Kern: Ein Converter wandelt den String aus dem Request in ein Objekt und zurück. Ein Validator prüft das konvertierte Objekt und wirft bei einem Fehler eine ValidatorException. Beide laufen in der Phase Process Validations, vor dem Schreiben ins Modell.

Antwort-Muster

Frage: Wie laufen Konvertierung und Validierung in JSF ab?

  1. Mechanismus: Der Converter macht aus dem String ein Objekt. Danach prüfen Required und Validatoren das Objekt.
  2. Zahl: Die Phase heisst Process Validations und ist Phase 3 von 6. Bei einem leeren Wert laufen Validatoren nur, wenn VALIDATE_EMPTY_FIELDS es erlaubt.
  3. Trade-off: Validierung in der Oberfläche gibt schnelle Meldungen. Die harte Prüfung gehört zusätzlich in Service und Datenbank.
  4. Produktion: Ich nutze Bean Validation für Regeln am Modell und eigene Converter für Entitäten in Auswahllisten.

1. Ein Feld in 7 Schritten

  1. submittedValue: Apply Request Values liest den Request-Parameter als String. Das ist der submittedValue.
  2. Leerer String: Mit jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL wird ein leerer String zu null. Der Standard ist false.
  3. Konvertieren: getConvertedValue() ruft den Converter. Bei einem Fehler kommt eine Message und valid wird false.
  4. Required prüfen: Ist required gesetzt und der Wert leer, gibt es einen Fehler.
  5. Validatoren: Ist das Feld noch gültig, laufen die Validatoren. Jede ValidatorException setzt valid auf false.
  6. Gültig: Der neue Wert wird local value, der submittedValue wird null. Ändert sich der Wert, kommt ein ValueChangeEvent.
  7. Ungültig: Update Model Values läuft nicht. Der Render Response zeigt wieder den submittedValue und die Message.

2. Aufbau

  1. Die UIInput-Komponente hält submittedValue, local value und die Flags required und valid.
  2. Ein Converter<T> hat zwei Methoden, getAsObject und getAsString.
  3. Ein Validator<T> hat eine Methode, validate.
  4. Eine ConverterException oder ValidatorException trägt eine FacesMessage.
  5. Standard-Converter heissen zum Beispiel NumberConverter und DateTimeConverter. Standard-Validatoren sind etwa LengthValidator und RegexValidator.
  6. Registriert wird mit @FacesConverter und @FacesValidator oder per Tag und Attribut.

3. Details

  1. getAsObject: Die Methode wandelt String in Objekt. Bei null gibt sie null zurück. Bei einem Fehler wirft sie ConverterException. Die Spec sagt nichts zum leeren String.
  2. getAsString: Die Methode wandelt Objekt in String für den Render. Bei null gibt sie einen leeren String zurück.
  3. Registrierung: @FacesConverter(value = "id") gilt per Converter-ID. forClass gilt automatisch für einen Typ. managed = true macht den Converter zu einer CDI-Bean, damit Injection geht. Der Standard ist false.
  4. Standard-Converter: Faces hat Converter für Zahlen, Boolean, Enum und Datum. f:convertDateTime hat die ID jakarta.faces.DateTime. Der Standard-Typ ist date. Die Zeitzone ist laut Mojarra standardmässig GMT.
  5. Zeitzonen-Falle: Mit jakarta.faces.DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE nimmt Faces die System-Zeitzone statt GMT. Ohne das sieht man Datumswerte um eine oder mehrere Stunden verschoben.
  6. Validator-Regel: Ein Validator soll bei null oder leerem Wert nicht fehlschlagen, ausser er ist dafür gedacht. Für Prüfung auf Pflicht gibt es required.
  7. VALIDATE_EMPTY_FIELDS: Der Standard ist auto. Das heisst true, wenn Jakarta Validation im Classpath ist, sonst false. Mit true laufen Validatoren auch bei leerem Wert, damit @NotNull ablehnen kann.
  8. Standard-Validatoren: f:validateLength, f:validateLongRange, f:validateDoubleRange, f:validateRegex, f:validateRequired und f:validateBean. Dazu kommt f:validateWholeBean seit 2.3.
  9. validateWholeBean: Es prüft das ganze Bean nach den Einzelfeldern. Es braucht jakarta.faces.validator.ENABLE_VALIDATE_WHOLE_BEAN. Ohne den Parameter macht der Tag nichts.
  10. Bean Validation: Mit Jakarta Validation im Classpath fügt Faces den BeanValidator zu jedem Eingabefeld hinzu. Regeln wie @Size gelten dann ohne Tag.
  11. Meldungen: requiredMessage, converterMessage und validatorMessage ersetzen die Standardtexte. converterMessage ersetzt auch die Meldung, die der Converter selbst liefert.
  12. Auswahllisten: Bei h:selectOneMenu prüft Faces, ob der Wert gleich einer der Optionen ist. Sonst kommt „Validation Error: Value is not valid“. Mit Entitäten braucht man dafür einen Converter und ein sauberes equals.

4. Fallen

  • „Ein Validator läuft immer, auch bei Konvertierungsfehler.“ → Falsch. Nach einem Konvertierungsfehler ist das Feld ungültig. Die Validatoren laufen danach nicht mehr.
  • „Der Converter bekommt nie null.“ → Falsch. getAsObject kann null bekommen. Er muss null zurückgeben.
  • „Mit required ist das Feld nach dem Submit nie leer.“ → Falsch. required prüft nur auf leer. Ein Leerzeichen zählt als Wert, wenn der Converter es nicht kürzt.
  • „Bei einem Validierungsfehler wird das Modell teilweise geschrieben.“ → Falsch. Update Model Values läuft dann gar nicht.
  • „Ein selectOneMenu mit Entitäten braucht keinen Converter.“ → Falsch. Ohne Converter kommt ein String zurück. Das Feld wird ungültig, oder es steht ein falscher Typ im Modell.
  • „f:convertDateTime nimmt die Zeitzone des Servers.“ → Falsch. In Mojarra ist der Standard GMT. Man setzt timeZone oder den Context-Param.

5. Selbsttest

Warum?

Warum braucht JSF Converter?

Ein Request enthält nur Strings. Das Modell braucht Typen wie Long oder LocalDate. Der Converter macht diese Umwandlung und wieder zurück für die Anzeige.

Warum läuft die Validierung vor dem Modell?

Das Modell soll nur gültige Werte sehen. Schlägt etwas fehl, läuft Update Model Values nicht. Das Modell bleibt unverändert.

Warum zeigt ein ungültiges Feld den eingegebenen Text?

Der submittedValue wird bei einem Fehler nicht gelöscht. Render Response zeigt ihn wieder an. So sieht der Nutzer seine Eingabe.

Wie innen?

Wie ist die Reihenfolge in Process Validations?

Empty-String-Regel, Converter, Required-Prüfung, dann die Validatoren. Bei Erfolg wird der local value gesetzt und eventuell ein ValueChangeEvent gestellt.

Was passiert bei einer ConverterException?

Faces fügt die Message der Exception in den FacesContext. Das Feld wird ungültig. Die Validatoren laufen nicht mehr.

Wie wird ein eigener Converter registriert?

Mit @FacesConverter(value = "id") oder forClass für einen Typ. Im Tag über converter="id" oder f:converter. Mit managed = true ist er eine CDI-Bean.

Wie funktioniert @FacesValidator?

Der Wert ist die Validator-ID. Fehlt er, ist die ID der Klassenname mit kleinem Anfangsbuchstaben. Mit isDefault = true läuft der Validator auf allen passenden Feldern.

Wie prüft h:selectOneMenu seinen Wert?

validateValue prüft, ob der Wert gleich einer der Optionen ist. Sonst ist das Feld ungültig. Ein noSelectionOption mit required ergibt auch einen Fehler.

Was macht validateWholeBean?

Es validiert eine Kopie des Beans als Ganzes, wenn alle Einzelfelder gültig sind. Es braucht den Context-Parameter ENABLE_VALIDATE_WHOLE_BEAN.

Zahlen

In welcher Phase laufen Converter und Validatoren?

In Process Validations, Phase 3. Mit immediate="true" schon in Apply Request Values, Phase 2.

Welchen Standard hat INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL?

false. Ein leerer String bleibt ein leerer String. Mit true wird er zu null.

Welchen Standard hat VALIDATE_EMPTY_FIELDS?

auto. Das ist true, wenn Jakarta Validation vorhanden ist, sonst false.

Welchen Standard-Typ hat f:convertDateTime?

date. Weitere Typen sind time, both, localDate, localDateTime und andere java.time-Typen.

Vergleich

Faces-Validator gegen Bean Validation?

Faces-Validatoren gelten pro Feld in der Oberfläche. Bean Validation steht am Modell und gilt auch in Service und Datenbank-Schicht. Mit Jakarta Validation im Classpath prüft Faces die Annotationen automatisch.

Converter gegen Validator?

Der Converter ändert den Typ und wirft ConverterException. Der Validator prüft Regeln auf dem Typ und wirft ValidatorException.

required gegen @NotNull?

required prüft die Eingabe im Formular. @NotNull prüft das Modell. Beide ergeben Meldungen, sind aber unabhängig.

Validator-Methode gegen Validator-Klasse?

Eine validator-Methode am Bean ist schnell, aber nicht wiederverwendbar. Eine Klasse mit @FacesValidator gilt für viele Felder.

Produktion

Warum kommt „Validation Error: Value is not valid“ bei der Auswahlliste?

Der gewählte Wert ist nicht gleich einer Option. Meist fehlt ein Converter oder equals und hashCode der Entität sind falsch. Auch ein anderes Laden der Optionen im Postback kann es auslösen.

Warum ist ein Datum um einen Tag verschoben?

Die Zeitzone ist GMT und der Server ist anders. Lösung: timeZone am Converter setzen oder den Context-Parameter.

Szenario: Ein Speichern-Button tut nichts und es gibt keine Meldung. Was prüfen Sie?

Ich prüfe, ob eine Konvertierung oder Validierung scheitert, ohne dass die Message im Formular steht. Ich setze h:messages ins Formular und schaue ins Log.

Szenario: Alle Eingaben mit Umlauten werden abgelehnt. Wie gehen Sie vor?

Ich prüfe den Regex-Validator. Oft ist das Muster nur für ASCII. Ich passe das Muster an und teste mit echten Werten.

Design

Wo gehört welche Prüfung hin?

Format und Typ in den Converter. Feldregeln in Bean Validation. Fachregeln über mehrere Felder in den Service. Die Oberfläche zeigt nur die Meldungen.

Wie validiert man Regeln über mehrere Felder?

Mit f:validateWholeBean, mit einem Validator auf dem letzten Feld oder im Service. Der Service ist am sichersten, da er auch ohne Formular gilt.

Szenario: Eine Auswahlliste von 5000 Entitäten ist langsam. Was tun Sie?

Ich lade nur die Daten, die ich brauche, etwa mit Autocomplete. Der Converter lädt per ID genau eine Entität. Die Liste lade ich nicht bei jedem Postback neu.

Wie schreiben Sie einen robusten Converter?

Er behandelt null und leere Strings, wirft eine ConverterException mit klarer Message und ist ohne Zustand. getAsString und getAsObject müssen zusammenpassen.

Wie testen Sie einen Converter?

Mit einem Unit-Test auf getAsObject und getAsString, ohne Server. Mit null, leer, gültig und ungültig. Ein Rundlauf-Test zeigt, dass beide Methoden zusammenpassen.

Mehr

Gerüst

  • Warum? Requests sind Strings, das Modell braucht Typen. Nur gültige Werte kommen ins Modell.
  • Wie innen? Process Validations: Converter, required, Validatoren. Bei Fehler Message und kein Update Model.
  • Zahlen Phase 3 von 6. EMPTY_STRING_AS_NULL false. VALIDATE_EMPTY_FIELDS auto. convertDateTime Standard GMT.
  • Vergleich Faces-Validator: Feld und UI. Bean Validation: Modell. Service: letzte Instanz.
  • Produktion Value is not valid bei Auswahllisten, Zeitzonen-Verschiebung, fehlende Meldungen.
  • Design Converter für Typ, Bean Validation für Regeln, Service für Fachlogik.

Beispiel: Converter und Validator

@FacesConverter(forClass = Customer.class, managed = true)
public class CustomerConverter implements Converter<Customer> {
  @Inject CustomerService service;

  public Customer getAsObject(FacesContext c, UIComponent u, String v) {
    if (v == null || v.isBlank()) return null;
    try { return service.find(Long.parseLong(v)); }
    catch (NumberFormatException e) {
      throw new ConverterException(new FacesMessage("Ungueltige Kunden-ID"), e);
    }
  }
  public String getAsString(FacesContext c, UIComponent u, Customer v) {
    return v == null ? "" : String.valueOf(v.getId());
  }
}

@FacesValidator("zipValidator")
public class ZipValidator implements Validator<String> {
  public void validate(FacesContext c, UIComponent u, String v) {
    if (v == null || v.isEmpty()) return;          // Pflicht via required
    if (!v.matches("\\d{4}"))
      throw new ValidatorException(new FacesMessage("PLZ hat 4 Ziffern"));
  }
}

Nicht ausgeführt.

  1. Der Converter nutzt managed = true, damit @Inject funktioniert.
  2. Er gibt bei null oder leer null zurück. Das entspricht dem Vertrag.
  3. Eine ungültige ID wird zur ConverterException mit einer Message für den Nutzer.
  4. Der Validator lässt leere Werte durch. Die Pflicht prüft required="true".
  5. Eine ValidatorException macht das Feld ungültig. Update Model Values läuft dann nicht.

Vergleich

  • Converter: String ↔ Objekt. Fehler: ConverterException.
  • Validator: Regel auf dem Objekt. Fehler: ValidatorException.
  • required: Eingabe darf nicht leer sein. Eigene Message mit requiredMessage.
  • Bean Validation: Annotationen am Modell. Faces ruft sie automatisch, wenn Jakarta Validation vorhanden ist.
  • validateWholeBean: Prüft das Bean als Ganzes, nach den Einzelfeldern.
  • Service-Prüfung: Gilt immer, auch ohne Formular, zum Beispiel bei einer REST-Schnittstelle.

Produktion

  1. Value is not valid: Auswahlwert passt zu keiner Option. Lösung: Converter plus equals und hashCode.
  2. Datum verschoben: GMT gegen Server-Zeitzone. Lösung: timeZone setzen.
  3. Keine Meldung sichtbar: Kein h:messages im Formular. Lösung: Messages-Komponente ergänzen, im Ajax-Fall ins render.
  4. Leere Felder landen als leerer String in der DB: Standard false. Lösung: INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL setzen.
  5. Langsame Converter: Ein DB-Zugriff pro Zeile. Lösung: Cache oder Batch-Laden.
  6. Alte Validatoren brechen nach Update: Faces 2 ruft Validatoren auch bei leeren Werten. Lösung: leere Werte im Validator durchlassen.

Diagnose: Werkzeuge und Befehle

  • h:messages mit showDetail="true" zeigt alle Meldungen im Formular.
  • Browser Dev Tools Netzwerk-Tab: zeigt gesendete Werte und die Partial Response.
  • PhaseListener mit Logging: zeigt, ob Process Validations scheitern.
  • Unit-Test mit Mockito: ruft getAsObject und validate ohne Server auf.
  • Project Stage Development zeigt ausführliche Fehlerseiten und Meldungen.

Senior-Punkte

  1. Die UI-Validierung ist Komfort, keine Sicherheit. Die echte Prüfung steht im Service.
  2. Regeln einmal definieren. Bean Validation am Modell gilt in Oberfläche und Service.
  3. Converter sind Typ-Brücken, keine Geschäftslogik. Sie bleiben ohne Zustand.
  4. Entitäten in Auswahllisten: besser die ID als Wert und den Converter dünn halten.
  5. Zeitzonen immer explizit. Der Standard GMT überrascht in jedem Projekt.
  6. Meldungen sind Teil der UX. Eigene Texte per requiredMessage oder Resource Bundle.
