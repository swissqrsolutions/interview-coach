ViewState: client vs server

Kern: Der ViewState ist der gespeicherte Zustand des Komponentenbaums einer Faces-Seite. Er liegt entweder in der Session auf dem Server oder verschlüsselt im Browser, im versteckten Feld jakarta.faces.ViewState. Damit stellt Restore View beim nächsten Postback den Baum wieder her.

Antwort-Muster

Frage: Was ist der ViewState und wo liegt er?

  1. Mechanismus: Faces speichert den Zustand der Komponenten. Beim Server-Modus liegt er in der Session und das Feld trägt nur eine Referenz. Beim Client-Modus trägt das Feld den ganzen Zustand.
  2. Zahl: Mojarra hält je 15 Views pro logischer View und 15 logische Views in der Session. MyFaces hält standardmässig 20 Views.
  3. Trade-off: Server spart Bandbreite, kostet Session-Speicher und endet bei Session-Ablauf. Client kostet Bandbreite und CPU pro Request.
  4. Produktion: Ich nutze server, begrenze die Views, setze bei Clustern Session-Replikation und fange die ViewExpiredException ab.

1. Ein Postback in 7 Schritten

  1. Render Response: Faces zeichnet den Komponentenbaum als HTML. Der Zustand der Komponenten ist jetzt bekannt.
  2. Zustand sichern: Mit Partial State Saving (Standard seit 2.0) speichert Faces nur, was sich vom Anfangszustand der View unterscheidet.
  3. Server oder Client: Im Server-Modus liegt der Zustand in der Session. Im Client-Modus wird er serialisiert, komprimiert, verschlüsselt und als Text ins Feld geschrieben.
  4. Feld im Formular: Das HTML enthält ein verstecktes Feld jakarta.faces.ViewState. Sein Wert ist die Referenz oder der ganze Zustand.
  5. Restore View: Beim Postback baut Faces die View aus dem Facelets-Template. Dann spielt es die gespeicherten Änderungen ein.
  6. Zustand fehlt: Ist der Zustand nicht mehr da, wirft Faces eine ViewExpiredException. Das passiert nach Session-Ablauf oder wenn der Server die View verdrängt hat.
  7. Neu sichern: Nach der Verarbeitung rendert Faces wieder und sichert den neuen Zustand.

Die 6 Phasen selbst stehen auf der Seite zum Lebenszyklus. Hier geht es nur um den Zustand dazwischen.

2. Aufbau

  1. Der StateManager sichert und stellt den Zustand der View her.
  2. Der ResponseStateManager schreibt und liest das Feld im HTML. Er prüft auch, ob ein Request ein Postback ist.
  3. Das versteckte Feld heisst jakarta.faces.ViewState. Seine ID hat eine eindeutige Nummer pro View.
  4. Im Server-Modus hält die Session mehrere Views. Eine Obergrenze verdrängt die ältesten.
  5. Im Client-Modus bleibt auf dem Server nichts. Das Feld trägt alles.
  6. Mojarra und MyFaces haben eigene Parameter dafür. Die Namen unterscheiden sich.

3. Details

  1. Standardwert: Mojarra und MyFaces nutzen server als Standard. Das Javadoc der Spec nennt client. Darum setzt man jakarta.faces.STATE_SAVING_METHOD immer selbst.
  2. Server-Modus: Die Session hält den Zustand. Das Feld trägt nur eine Referenz. Das ist schneller, aber begrenzt. Es endet mit der Session.
  3. Client-Modus: Das Feld trägt den ganzen Zustand. Er ist praktisch unbegrenzt und überlebt Session-Ende. Er kostet CPU und Bandbreite bei jedem Request.
  4. Partial State Saving: jakarta.faces.PARTIAL_STATE_SAVING ist standardmässig an. Faces speichert nur Abweichungen vom Anfangszustand. Das ist schneller und viel kleiner. FULL_STATE_SAVING_VIEW_IDS erzwingt vollen Zustand für einzelne Views.
  5. Limits in Mojarra: com.sun.faces.numberOfLogicalViews ist 15, com.sun.faces.numberOfViewsInSession ist 15. Eine logische View ist eine View mit allen Postbacks. Die Session hält bis zum Produkt beider Werte.
  6. Limits in MyFaces: org.apache.myfaces.NUMBER_OF_VIEWS_IN_SESSION ist 20. NUMBER_OF_SEQUENTIAL_VIEWS_IN_SESSION ist 4 und gilt für Sequenzen aus POST und Redirect.
  7. ViewExpiredException: Sie kommt, wenn die Session ablief oder der Server die View verdrängt hat. Im Client-Modus kommt sie nach einem gesetzten Timeout, in Mojarra com.sun.faces.clientStateTimeout in Minuten.
  8. Verschlüsselung: Im Client-Modus muss der Zustand verschlüsselt und manipulationssicher sein. Schlägt die Prüfung fehl, wirft Faces eine ProtectedViewException. Mojarra kann die Verschlüsselung nur im Project Stage Development abschalten.
  9. Cluster: Im Client-Modus müssen alle Knoten denselben Schlüssel nutzen, bei MyFaces org.apache.myfaces.SECRET. Im Server-Modus braucht man Sticky Sessions oder Session-Replikation. Dann muss der Zustand serialisierbar sein.
  10. SERIALIZE_SERVER_STATE: Standard ist false. Mit true wird der Zustand schon beim Request serialisiert. So zeigt sich eine NotSerializableException sofort und nicht erst bei der Replikation.
  11. Kompression: Mojarra komprimiert den Zustand mit GZIP, Standard ist an. Im Client-Modus schrumpft das den Weg übers Netz. Im Server-Modus wirkt es nur mit SERIALIZE_SERVER_STATE.
  12. Sicherheit des Werts: Die Spec verlangt, dass der ViewState-Wert schwer vorhersagbar ist. Mojarra erzeugt standardmässig zufällige Server-State-IDs statt eines Zählers.
  13. Stateless Views: Mit transient="true" auf f:view speichert Faces keinen Zustand. Das spart Speicher bei reinen Lese-Seiten.
  14. Client Window: jakarta.faces.CLIENT_WINDOW_MODE ist standardmässig none, möglich ist url. Es trennt Browser-Tabs. Mojarra hält höchstens 10 Client Windows (seit 4.0).

4. Fallen

  • „Der ViewState liegt immer im Browser.“ → Falsch. Im Server-Modus liegt er in der Session. Das Feld trägt nur eine Referenz.
  • „Client-Modus heisst: der Server hat keine Session mehr.“ → Falsch. Die Session für Beans existiert weiter. Nur der Komponentenzustand liegt im Browser.
  • „Der Client-ViewState ist Klartext und manipulierbar.“ → Falsch. Er ist laut Spec verschlüsselt und manipulationssicher. Eine Manipulation führt zur ProtectedViewException.
  • „Der Server-Modus hat kein Limit.“ → Falsch. Die Session hält nur eine begrenzte Zahl an Views. Alte Views sind danach weg.
  • „Mit client geht die ViewExpiredException weg.“ → Falsch. Sie kommt auch dort, etwa nach einem Timeout oder bei kaputtem Zustand.
  • „Der ViewState ist die ganze Seite.“ → Falsch. Mit Partial State Saving ist er nur der Unterschied zum Anfangszustand. Die Seite entsteht neu aus Facelets.

5. Selbsttest

Warum?

Warum braucht Faces einen ViewState?

Der Server baut die Seite pro Request neu. Er muss wissen, wie der Baum und seine Werte beim letzten Render aussahen. Der ViewState liefert das.

Warum ist der Server-Modus meist der Standard?

Er sendet nur eine Referenz. Das spart Bandbreite und CPU. Der Zustand verlässt den Server nicht.

Warum gibt es Partial State Saving?

Der volle Baum ist gross. Meist ändert sich wenig. Faces speichert nur die Änderungen, das ist schneller und viel kleiner.

Wie innen?

Was steht im Feld jakarta.faces.ViewState?

Im Server-Modus eine Referenz auf den Zustand in der Session. Im Client-Modus der serialisierte, komprimierte und verschlüsselte Zustand als Text.

Wie stellt Restore View die View wieder her?

Es liest das Feld. Bei Partial State Saving baut es die View aus dem Facelets-Template. Dann spielt es die gespeicherten Änderungen ein.

Wie sichert Faces den Zustand im Client-Modus?

Es serialisiert den Zustand, komprimiert ihn (Mojarra: GZIP) und verschlüsselt ihn. Danach kommt Base64 als Text ins Feld.

Wie hält die Session den Zustand im Server-Modus?

Sie hält mehrere Views pro logischer View und mehrere logische Views. Mojarra begrenzt jedes auf 15. Älteste Einträge werden verdrängt.

Was ist eine logische View?

Eine erste angeforderte View mit allen ihren Postbacks. Ein zweiter Browser-Tab erzeugt eine neue logische View.

Wie erkennt Faces einen Postback?

Der Standard-RenderKit prüft, ob die Request-Parameter das Feld jakarta.faces.ViewState enthalten.

Zahlen

Wie viele Views hält die Session in Mojarra?

numberOfLogicalViews ist 15 und numberOfViewsInSession ist 15. Die Session hält bis zum Produkt der beiden Werte.

Wie viele Views hält MyFaces?

NUMBER_OF_VIEWS_IN_SESSION ist 20. NUMBER_OF_SEQUENTIAL_VIEWS_IN_SESSION ist 4.

Welche Standardwerte hat PARTIAL_STATE_SAVING?

true für Anwendungen ab Version 2.0. Für 1.2-Anwendungen ist es aus.

Welche Einheit hat clientStateTimeout?

Minuten. Der Wert gilt nur, wenn er gesetzt ist. Danach kommt eine ViewExpiredException.

Vergleich

Server gegen Client im Vergleich?

Server: wenig Netz, mehr Session-Speicher, Ende bei Session-Ablauf. Client: viel Netz und CPU, kein Session-Speicher, überlebt Session-Ende.

ViewState gegen Session-Bean?

Der ViewState speichert den Zustand der Komponenten. Beans speichern Anwendungsdaten. Beide leben getrennt und haben eigene Scopes.

Full State gegen Partial State?

Full speichert den ganzen Baum. Partial speichert nur Abweichungen. Partial ist Standard seit 2.0.

Faces-ViewState gegen JWT in REST?

Der ViewState hält UI-Zustand, ein JWT hält Identität. Ein REST-Frontend hält den UI-Zustand im Browser.

Produktion

Warum kommt nach Inaktivität eine ViewExpiredException?

Die Session ist abgelaufen und damit der Zustand weg. Im Server-Modus ist das normal. Man fängt sie mit einer Fehlerseite oder einem Handler ab.

Was bedeutet NotSerializableException im Cluster?

Eine Komponente oder Bean im Zustand ist nicht serialisierbar. Bei Replikation oder Passivierung scheitert es. SERIALIZE_SERVER_STATE macht den Fehler früher sichtbar.

Szenario: Nach dem Login-Timeout sehen Nutzer eine weisse Seite bei Ajax-Klicks. Was tun Sie?

Ich fange die ViewExpiredException mit einem ExceptionHandler. Bei Ajax leite ich auf Login oder Startseite um. Das Session-Timeout passe ich an.

Szenario: Der Heap wächst, obwohl wenige Nutzer da sind. Im Dump liegen viele UIViewRoot-Objekte in Sessions. Warum?

Der Server-Modus hält pro Session bis zu 15 mal 15 Views in Mojarra. Grosse Seiten summieren sich. Ich senke die Limits, nutze Stateless Views und verkleinere die Bäume.

Design

Server oder Client für ein neues Projekt?

Standardmässig Server. Client nur, wenn Sessions knapp sind oder ein Cluster ohne Session-Replikation läuft. Dann Schlüssel gleich auf allen Knoten.

Wie bleibt die Anwendung im Cluster stabil?

Mit Server-Modus braucht es Sticky Sessions oder Replikation und serialisierbaren Zustand. Mit Client-Modus braucht es denselben Schlüssel auf allen Knoten und genug Bandbreite.

Szenario: Eine Lese-Seite mit grosser Tabelle belastet die Session. Was ändern Sie?

Ich markiere die View als transient, wenn sie keinen Postback braucht. Oder ich setze Partial State Saving und Paginierung ein, damit der Baum klein bleibt.

Wie schützt der ViewState vor CSRF?

Die Spec verlangt einen schwer vorhersagbaren Wert. Ein Angreifer kann ihn nicht raten. Im Client-Modus schützt zusätzlich die Verschlüsselung vor Manipulation. Ein eigener Schutz gegen CSRF bleibt trotzdem sinnvoll.

Wie testen Sie, dass die Anwendung clusterfähig ist?

Ich schalte SERIALIZE_SERVER_STATE ein und fahre die Tests. Eine NotSerializableException zeigt sofort, welche Bean oder Komponente nicht serialisierbar ist.

Mehr

Gerüst

  • Warum? Der Server baut den Baum pro Request neu und braucht den Zustand vom letzten Render.
  • Wie innen? Feld jakarta.faces.ViewState, Server: Referenz in Session. Client: verschlüsselter Zustand im Feld.
  • Zahlen Mojarra 15 × 15 Views. MyFaces 20 Views und 4 sequentielle. Partial State an.
  • Vergleich Server: wenig Netz. Client: kein Session-Speicher, aber CPU und Bandbreite.
  • Produktion ViewExpiredException, Heap durch Views, NotSerializableException im Cluster.
  • Design Server als Standard, Limits setzen, transient für Lese-Seiten, Schlüssel gleich im Cluster.

Beispiel: web.xml Einstellungen

<context-param>
  <param-name>jakarta.faces.STATE_SAVING_METHOD</param-name>
  <param-value>server</param-value>
</context-param>
<context-param>
  <param-name>com.sun.faces.numberOfLogicalViews</param-name>
  <param-value>10</param-value>
</context-param>
<context-param>
  <param-name>jakarta.faces.SERIALIZE_SERVER_STATE</param-name>
  <param-value>true</param-value>
</context-param>

Nicht ausgeführt.

  1. Die erste Zeile setzt den Modus ausdrücklich. So hängt das Verhalten nicht vom Standard der Implementierung ab.
  2. Die zweite Zeile senkt die Zahl der logischen Views in Mojarra von 15 auf 10. Das spart Session-Speicher.
  3. Die dritte Zeile serialisiert den Zustand schon beim Request. Das ist gut für Tests auf Cluster-Tauglichkeit.
  4. Bei MyFaces heissen die Parameter anders, zum Beispiel org.apache.myfaces.NUMBER_OF_VIEWS_IN_SESSION.

Vergleich

  • Server-State: Session hält Zustand. Kleines Feld, begrenzte Views, Ende mit Session.
  • Client-State: Feld hält Zustand, verschlüsselt. Mehr Netz und CPU, kein Session-Speicher.
  • Partial State Saving: nur Änderungen. Standard seit 2.0.
  • Full State Saving: ganzer Baum. Nur für einzelne Views mit FULL_STATE_SAVING_VIEW_IDS.
  • Stateless View: transient="true". Kein Zustand, kein Postback-Restore.
  • Client Window: trennt Tabs. Mit CLIENT_WINDOW_MODE=url.

Produktion

  1. ViewExpiredException: Session ist abgelaufen. Lösung: Fehlerseite oder Redirect, Timeout prüfen.
  2. Hoher Heap: Viele Views pro Session. Lösung: Limits senken, Bäume klein halten, transient nutzen.
  3. Grosse Requests im Client-Modus: Das Feld ist gross. Lösung: Komprimierung an lassen oder auf Server wechseln.
  4. NotSerializableException: Cluster-Replikation scheitert. Lösung: Beans serialisierbar machen, SERIALIZE_SERVER_STATE in Tests.
  5. ProtectedViewException im Cluster: Knoten haben verschiedene Schlüssel. Lösung: denselben Schlüssel setzen.
  6. Zurück-Button zeigt alten Zustand: Der Browser stellt Felder wieder her. Mojarra setzt dafür autocomplete auf one-time-code.

Diagnose: Werkzeuge und Befehle

  • Browser Dev Tools: Feld jakarta.faces.ViewState im Formular und im Request ansehen. Länge zeigt den Modus.
  • Heap Dump mit Eclipse MAT: zeigt UIViewRoot und Zustandsobjekte pro Session.
  • Session-Grösse messen mit dem Server-Monitoring oder einem Serialisierungs-Test.
  • Log-Level der Faces-Implementierung erhöhen, um den Grund der Exception zu sehen.
  • Project Stage Development zeigt ausführliche Fehlerseiten.

Senior-Punkte

  1. Der Modus ist eine Betriebsentscheidung. Er bestimmt Speicher, Netz und Cluster-Verhalten.
  2. Immer explizit setzen. Spec und Implementierungen nennen verschiedene Standards.
  3. ViewExpired ist ein Normalfall. Man baut dafür eine Behandlung, keine Fehlermeldung.
  4. Zustand klein halten. Kleine Bäume und Paginierung sparen mehr als jede Einstellung.
  5. Cluster früh testen. Serialisierbarkeit zeigt sich spät, wenn man sie nicht erzwingt.
  6. Client-State ist kein Geheimnis. Verschlüsselt heisst nicht, dass sensible Daten hineingehören.
