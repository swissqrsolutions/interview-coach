JSF-Lebenszyklus: die 6 Phasen

Kern: Der JSF-Lebenszyklus ist die feste Folge von 6 Phasen, die jeder Faces-Request durchläuft. Er macht aus HTTP-Parametern konvertierte, validierte Werte im Bean und erst danach ruft er die Action auf. Ein Konvertierungs- oder Validierungsfehler springt direkt zu Render Response, das Model bleibt unverändert.

1. Wo sitzt der Lebenszyklus?

  1. FacesServlet: das zentrale Servlet (Front Controller). Es nimmt jeden Faces-Request an und startet den Lifecycle.
  2. FacesContext: das Objekt mit allem Request-Zustand. Beispiel: Messages, Response-Writer, renderResponse-Flag.
  3. Komponentenbaum: der Baum aus UIComponent-Objekten, gebaut aus der Facelets-Datei. Die Wurzel ist UIViewRoot.
  4. CDI-Beans: Java-Objekte mit Daten und Actions. Die Seite bindet sie über EL (Expression Language), z. B. #{orderBean.amount}.
  5. Converter und Validatoren: hängen an Eingabe-Komponenten. Sie laufen in Phase 3.
  6. State Manager: speichert den Zustand des Baums zwischen Requests (ViewState).
  7. Render Kit: erzeugt HTML. Bei Ajax erzeugt es eine Partial Response (XML mit Teil-Updates).

2. Die Reise eines Formular-Submits (die Geschichte zum Merken)

  1. Restore View. Der Benutzer schickt das Bestellformular ab. JSF findet die View-ID, z. B. /order.xhtml. Bei einem Postback (Submit der gleichen Seite) stellt JSF den Baum aus dem ViewState wieder her. Fehlt der State, kommt eine ViewExpiredException.
  2. Apply Request Values. Jede Komponente liest ihren Parameter (decode()). Der rohe String landet als submittedValue in der Komponente, nicht im Bean. Ein geklickter Button legt ein ActionEvent in die Warteschlange.
  3. Process Validations. Der Converter macht aus "42" einen Integer. Dann laufen die Validatoren. Klappt alles, wird der Wert zum local value. Hat er sich geändert, kommt ein ValueChangeEvent.
  4. Der Fehlerfall. Schlägt Konvertierung oder Validierung fehl, gibt es eine FacesMessage. Die Komponente ist valid=false. JSF springt nach dieser Phase direkt zu Render Response. Das Bean bleibt unberührt, die Action läuft nicht.
  5. Update Model Values. Erst jetzt ruft JSF die Setter auf, z. B. setAmount(42). Alle Werte sind gültig.
  6. Invoke Application. Zuerst laufen die Action Listener, dann die Action-Methode. Ihr Rückgabewert (Outcome) steuert die Navigation.
  7. Render Response. JSF baut bei Bedarf den neuen Baum, ruft die Getter auf und schreibt HTML. Zum Schluss speichert es den Zustand (ViewState).

Ein erster GET ohne View-Parameter hat nichts zu verarbeiten. Restore View erzeugt eine leere View und springt direkt zu Phase 6.

3. Beispiel: die Phasen mitloggen

// PhaseLogger.java – loggt jede Phase
public class PhaseLogger implements PhaseListener {
  public PhaseId getPhaseId() { return PhaseId.ANY_PHASE; }
  public void beforePhase(PhaseEvent e) { System.out.println("BEFORE " + e.getPhaseId()); }
  public void afterPhase(PhaseEvent e)  { }
}
// faces-config.xml: <lifecycle><phase-listener>demo.PhaseLogger</phase-listener></lifecycle>

<!-- order.xhtml -->
<h:form>
  <h:inputText value="#{orderBean.amount}" required="true">
    <f:validateLongRange minimum="1" maximum="100"/>
  </h:inputText>
  <h:commandButton value="Bestellen" action="#{orderBean.save}"/>
  <h:messages/>
</h:form>
// OrderBean.save() schreibt "SAVE amount=..."

BEFORE RESTORE_VIEW 1
BEFORE RENDER_RESPONSE 6

B) Submit mit amount = 42
BEFORE RESTORE_VIEW 1
BEFORE APPLY_REQUEST_VALUES 2
BEFORE PROCESS_VALIDATIONS 3
BEFORE UPDATE_MODEL_VALUES 4
BEFORE INVOKE_APPLICATION 5
SAVE amount=42
BEFORE RENDER_RESPONSE 6

C) Submit mit amount = 500

BEFORE APPLY_REQUEST_VALUES 2
BEFORE PROCESS_VALIDATIONS 3
BEFORE RENDER_RESPONSE 6

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Es gibt hier keine JSF-Laufzeit. PhaseId.toString() liefert Name und Nummer.

  1. A: Der erste GET hat keinen Postback. Darum folgen auf Phase 1 direkt Phase 6.
  2. B: Ein gültiger Submit läuft durch alle 6 Phasen. Die Action läuft in Phase 5.
  3. C: 500 ist ausserhalb von 1–100. Der Validator scheitert in Phase 3. Phase 4 und 5 fallen weg. save() läuft nicht, <h:messages/> zeigt den Fehler.

4. Details, die Interviewer fragen

  1. Die 6 Phasen: Restore View, Apply Request Values, Process Validations, Update Model Values, Invoke Application, Render Response. Die Reihenfolge ist fest.
  2. submittedValue, local value, Model: Ein Wert wandert in drei Schritten. Phase 2: String als submittedValue. Phase 3: konvertierter local value. Phase 4: Wert im Bean.
  3. Postback vs. Initial Request: Ein Postback ist ein POST auf die gleiche View. Nur dann wird der Baum aus dem State wiederhergestellt. FacesContext.isPostback() sagt es.
  4. GET mit View-Parametern: <f:viewParam> in <f:metadata> bindet Query-Parameter an das Bean. Dann laufen auch bei einem GET alle Phasen für diese Parameter. <f:viewAction> ruft eine Methode in Invoke Application auf.
  5. immediate="true" auf einem Input: Konvertierung und Validierung laufen schon in Phase 2. So wird dieses Feld vor allen anderen geprüft.
  6. immediate="true" auf einem Button: Die Action läuft am Ende von Phase 2. Validierung und Model-Update der normalen Felder fallen weg. Typisch für „Abbrechen".
  7. renderResponse() und responseComplete(): FacesContext.renderResponse() springt nach der aktuellen Phase zu Phase 6. responseComplete() beendet den Lebenszyklus ganz, z. B. nach einem Datei-Download oder Redirect.
  8. PhaseListener: ein Hook vor und nach Phasen. getPhaseId() wählt die Phase, ANY_PHASE heisst alle.
  9. Ajax und der Lebenszyklus: Ajax nutzt dieselben 6 Phasen. execute wählt die Komponenten für Phase 2 bis 5. render wählt die Komponenten für Phase 6. Standard bei <f:ajax>: execute @this, render @none.
  10. Getter laufen mehrfach: JSF ruft Getter in mehreren Phasen auf, z. B. für rendered und beim Rendern. Darum keine Datenbank-Abfrage in einem Getter.
  11. ValueChangeEvent: wird in Phase 3 erzeugt, aber erst am Ende der Phase ausgeliefert. Das Model hat dann noch den alten Wert.
  12. Navigation: Das Outcome wählt die nächste View. Standard ist Forward, die URL bleibt alt. Mit ?faces-redirect=true gibt es einen Redirect (Post-Redirect-Get).
  13. Leere Felder: Mit Bean Validation im Classpath validiert JSF auch leere Felder (VALIDATE_EMPTY_FIELDS). INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL macht aus "" ein null.
  14. Exceptions: Eine Exception in einer Phase geht an den ExceptionHandler. Bei Ajax schreibt JSF ein <error>-Element in die Partial Response.

5. Vergleich

  • JSF (komponentenbasiert, stateful): Der Server hält einen Komponentenbaum. Der Lebenszyklus konvertiert und validiert automatisch.
  • Spring MVC / Jakarta MVC (aktionsbasiert): Ein Request geht direkt an eine Controller-Methode. Es gibt keinen Baum und keinen ViewState. Binding und Validierung macht man pro Request.
  • Angular + REST: Der Zustand lebt im Browser. Der Server ist stateless und gibt JSON. Validierung läuft doppelt: Client und Server.
  • JSF 2.x vs. Jakarta Faces 4.x: Die 6 Phasen sind gleich. Geändert haben sich Paket (javax.faces → jakarta.faces), JSP-Support (entfernt in 4.0) und @ManagedBean (entfernt in 4.0, jetzt CDI).
  • immediate vs. partial processing: immediate verschiebt Arbeit in Phase 2. Partial processing (execute/process) verarbeitet nur ausgewählte Komponenten. Heute ist partial processing meist die sauberere Lösung.

6. In der Produktion

  1. Action läuft nicht, keine Fehlermeldung sichtbar: Ein Validator in einem anderen Feld schlägt fehl. Die Meldung wird nicht gerendert, weil <h:messages> fehlt oder nicht im render/update ist. Lösung: Messages immer mit aktualisieren, in Development PROJECT_STAGE setzen.
  2. Langsame Seite durch Getter: Ein Getter lädt Daten aus der DB und läuft pro Request mehrmals. Lösung: Daten in @PostConstruct oder in einer Action laden und im Bean halten.
  3. „Abbrechen"-Button validiert das Formular: Der Button verarbeitet das ganze Formular. Lösung: immediate="true" oder process="@this" bzw. execute="@this".
  4. Doppelte Bestellung durch F5: Nach einem POST mit Forward schickt der Browser den POST erneut. Lösung: Post-Redirect-Get mit faces-redirect=true.
  5. ViewExpiredException nach Session-Timeout: Restore View findet den State nicht. Lösung: Exception-Handler oder <error-page> für ViewExpiredException, Redirect auf die Seite.
  6. Wert „verschwindet" nach Validierungsfehler: Ungültige Felder zeigen den submittedValue, nicht den Bean-Wert. Ein Reset per Code wirkt nicht. Lösung: resetValues="true" (seit JSF 2.2) oder p:resetInput.

7. Diagnose: Werkzeuge und Einstellungen

  • PhaseListener mit ANY_PHASE: zeigt, welche Phasen laufen und wo der Request abbricht.
  • jakarta.faces.PROJECT_STAGE=Development: mehr Prüfungen und Fehlermeldungen. Mojarra warnt im Log: „FacesMessage(s) have been enqueued, but may not have been displayed.“
  • <h:messages globalOnly="false"/> temporär in die Seite: zeigt jede Validierungs-Meldung.
  • FacesContext.getCurrentInstance().isValidationFailed(): sagt, ob Phase 3 gescheitert ist.
  • Browser DevTools, Network: Bei Ajax den Request (jakarta.faces.partial.execute, ...render) und die Partial Response lesen.
  • PrimeFaces <p:lifecycle>: zeigt die Dauer jeder Phase auf der Seite.
  • Breakpoint in Setter und Action: Wird der Setter nicht erreicht, ist der Fehler in Phase 2 oder 3.

8. Senior-Punkte

  1. Das Model sieht nur gültige Daten. Das ist der grösste Vorteil des Lebenszyklus. Business-Code muss keine rohen Strings prüfen.
  2. Partial processing statt immediate. process/execute sagt genau, was verarbeitet wird. immediate ist schwer zu lesen, wenn es auf Inputs und Buttons gemischt ist.
  3. Getter ohne Logik. Daten laden gehört in @PostConstruct, <f:viewAction> oder eine Action. Das ist eine Performance- und eine Korrektheitsfrage.
  4. Validierung an der richtigen Stelle: Format und Pflichtfeld in der View oder per Bean Validation. Fachregeln über mehrere Felder in der Action oder mit <f:validateWholeBean>.
  5. Fehler sichtbar machen: Jedes Ajax-Update muss die Messages mitnehmen. Sonst „passiert nichts" für den Benutzer.
  6. Stateful hat Kosten: Baum und State brauchen Speicher pro Benutzer. Das beeinflusst Session-Grösse, Clustering und Skalierung.

10. Fallen

  • „Bei einem Validierungsfehler ist der Wert schon im Bean.“ → Falsch. Update Model Values läuft nicht. Das Bean hat den alten Wert.
  • „immediate="true" überspringt die Validierung.“ → Ungenau. Auf einem Input wird früher validiert, nicht gar nicht. Auf einem Button fallen nur die Phasen 3 bis 5 für die normalen Felder weg.
  • „Ajax hat einen eigenen Lebenszyklus.“ → Falsch. Es sind dieselben 6 Phasen, nur auf execute- und render-Teilbäume beschränkt.
  • „Ein Getter wird einmal pro Request aufgerufen.“ → Falsch. Oft mehrmals, in mehreren Phasen.
  • „Ein GET läuft immer durch alle Phasen.“ → Falsch. Ohne View-Parameter springt ein Initial Request von Phase 1 zu Phase 6.
  • „Die Action läuft in Render Response.“ → Falsch. In Invoke Application (Phase 5), mit immediate am Ende von Phase 2.

11. Fragen

Nennen Sie die 6 Phasen des JSF-Lebenszyklus.

Restore View, Apply Request Values, Process Validations, Update Model Values, Invoke Application, Render Response.

Was passiert in Restore View?

JSF baut den Komponentenbaum oder stellt ihn aus dem ViewState wieder her. Bei einem Initial Request ohne View-Parameter springt es danach direkt zu Render Response.

Was passiert in Apply Request Values?

Jede Komponente liest ihren Request-Parameter mit decode(). Der String wird submittedValue. Buttons legen ein ActionEvent in die Warteschlange.

Was passiert in Process Validations?

Converter wandeln den String in den Zieltyp, dann laufen die Validatoren. Bei Erfolg entsteht der local value, bei Fehler eine FacesMessage.

Was passiert bei einem Validierungsfehler?

Die Komponente wird ungültig und bekommt eine Message. Nach Phase 3 springt JSF zu Render Response. Model-Update und Action fallen weg.

Wann ruft JSF die Setter im Bean auf?

In Update Model Values (Phase 4). Erst dann, wenn alle verarbeiteten Felder gültig sind.

Wann läuft die Action-Methode?

In Invoke Application (Phase 5), nach den Action Listenern. Mit immediate="true" am Button schon am Ende von Phase 2.

Was macht immediate="true" auf einem Input?

Konvertierung und Validierung dieses Feldes laufen schon in Apply Request Values. So wird es vor den anderen Feldern geprüft.

Was macht immediate="true" auf einem Button?

Die Action läuft am Ende von Phase 2. Normale Felder werden weder validiert noch ins Model geschrieben. Typisch für Abbrechen.

Was ist der Unterschied zwischen submittedValue und local value?

submittedValue ist der rohe String aus dem Request. Local value ist der konvertierte und validierte Wert. Beide liegen in der Komponente, nicht im Bean.

Was ist ein Postback?

Ein Submit auf die gleiche View. Nur dann stellt Restore View den alten Baum aus dem State wieder her.

Was bewirken renderResponse() und responseComplete()?

renderResponse() springt nach der aktuellen Phase zu Render Response. responseComplete() beendet den Lebenszyklus ganz, z. B. nach einem Download.

Wie hängt Ajax mit dem Lebenszyklus zusammen?

Ajax nutzt die gleichen Phasen. execute bestimmt die Komponenten für Phase 2 bis 5, render die für Phase 6. Standard: execute @this, render @none.

Was ist ein PhaseListener?

Ein Hook mit beforePhase und afterPhase. Er dient für Logging, Messung oder Sicherheitsprüfungen pro Phase.

Warum keine Logik in Gettern?

JSF ruft Getter mehrfach und in mehreren Phasen auf. Eine DB-Abfrage im Getter läuft dann mehrmals pro Request.

Wann wird ein ValueChangeEvent ausgelöst?

In Process Validations, wenn der neue local value vom alten abweicht. Das Model ist zu diesem Zeitpunkt noch nicht aktualisiert.

Was ist f:viewParam und f:viewAction?

f:viewParam bindet Query-Parameter mit Konvertierung und Validierung an das Bean. f:viewAction ruft bei einem GET eine Methode auf, standardmässig in Invoke Application.

Forward oder Redirect bei der Navigation?

Standard ist Forward, die URL bleibt die alte. faces-redirect=true macht einen Redirect, das verhindert doppelte POSTs bei F5.

Was ist die ViewExpiredException?

Restore View findet den gespeicherten State nicht mehr, z. B. nach Session-Timeout. Man fängt sie mit einer Error-Page oder einem ExceptionHandler.

Warum zeigt ein ungültiges Feld nicht den neuen Bean-Wert?

Die Komponente rendert ihren submittedValue, solange sie ungültig ist. Lösung: resetValues="true" oder p:resetInput.

Was hat sich am Lebenszyklus zwischen JSF 2.x und Faces 4 geändert?

Die Phasen sind gleich. Neu sind Paketnamen (jakarta.faces), CDI statt @ManagedBean und kein JSP mehr.

Wie validiert man Regeln über mehrere Felder?

In der Action, mit einem Validator auf einer Komponente, die die anderen liest, oder mit f:validateWholeBean. Letzteres muss per Context-Parameter aktiviert werden.

Szenario: Ein Klick auf „Speichern" tut nichts, kein Fehler im Log. Wie gehen Sie vor?

Wahrscheinlich ein Validierungs- oder Konvertierungsfehler ohne sichtbare Message. Ich prüfe mit PhaseListener oder Breakpoint, ob Phase 4/5 laufen, und nehme h:messages in das Update auf.

Szenario: Der „Abbrechen"-Button meldet „Pflichtfeld fehlt". Was tun Sie?

Der Button verarbeitet das ganze Formular. Ich setze process="@this" (PrimeFaces) bzw. execute="@this" oder immediate="true".

Szenario: Eine Liste lädt pro Seitenaufruf 6× die gleiche Query. Warum?

Der Getter lädt die Daten und wird mehrmals aufgerufen, z. B. für rendered und beim Rendern. Ich lade einmal in @PostConstruct oder f:viewAction und halte das Ergebnis im Bean.
