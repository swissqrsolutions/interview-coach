Testcontainers

Kern: Testcontainers ist eine Bibliothek, die echte Abhängigkeiten wie PostgreSQL, Kafka oder Redis als Docker-Container aus dem Test heraus startet. Sie löst das Problem, dass Mocks und In-Memory-Datenbanken sich anders verhalten als Produktion. Jeder Test bekommt eine echte, frische, wegwerfbare Infrastruktur, und aktuell ist Testcontainers for Java 2.0.x.

Antwort-Muster

Frage: Wie funktioniert Testcontainers und warum nutzt man es statt H2?

  1. Mechanismus: Testcontainers startet über die Docker-API einen echten Container mit zufälligem Host-Port. Eine Wait Strategy wartet, bis er bereit ist.
  2. Zahl: Das Postgres-Modul wartet zweimal auf die Log-Zeile, mit 60 s Timeout. Der erste Lauf ist langsam, weil Docker das Image lädt.
  3. Trade-off: Echte Software gibt echtes Verhalten, aber der Test braucht Docker und mehr Zeit als H2. Container teilt man pro Klasse oder Lauf.
  4. Produktion: Nach einem Docker-Upgrade können alte Clients abgelehnt werden. Im CI killt der OOM-Killer schwere Container.

1. Die Reise eines Integrationstests

  1. Docker finden: Testcontainers sucht den Daemon (DOCKER_HOST, Socket, Docker Desktop). Dann startet es Ryuk.
  2. Image holen: Fehlt postgres:17 lokal, lädt Docker es. Der erste Lauf ist darum langsam.
  3. Container starten: mit Umgebungsvariablen (Benutzer, Passwort, DB) und einem zufälligen Host-Port.
  4. Warten: Ein laufender Container ist noch nicht bereit. Die Wait Strategy wartet z. B. auf eine Log-Zeile. Das Postgres-Modul wartet auf „database system is ready to accept connections“ zweimal, mit 60 s Timeout.
  5. Verbinden: Spring Boot liest Host und Port über @ServiceConnection. Ohne Spring nutzt man getJdbcUrl().
  6. Testen: Flyway migriert das echte Schema. Die Tests laufen gegen echtes SQL.
  7. Aufräumen: Der Container stoppt nach Klasse oder Lauf. Stirbt die JVM, löscht Ryuk ihn.

2. Aufbau

  1. Test: ein normaler JUnit-Test, oft mit Spring Boot.
  2. Container-Klasse: z. B. PostgreSQLContainer. Sie kennt Image, Port, Umgebungsvariablen und Wartebedingung.
  3. docker-java: spricht mit der Docker-API über den Socket. Kein docker-CLI nötig.
  4. Docker-Daemon: lokal (Docker Desktop, Linux) oder entfernt (DOCKER_HOST, Testcontainers Cloud).
  5. Ryuk: ein Hilfscontainer, der alle Container dieser Sitzung löscht, wenn die JVM endet. Auch nach einem Absturz.
  6. Zufällige Ports: Container-Port 5432 wird auf einen freien Host-Port gemappt. Keine Konflikte bei parallelen Builds.

3. Details, die Interviewer fragen

  1. Lebenszyklus mit JUnit: @Testcontainers aktiviert die Jupiter-Extension. @Container markiert verwaltete Felder. Ein static Feld startet einmal pro Klasse. Ein Instanzfeld startet pro Test. Die Extension ist laut Doku nur für sequenzielle Ausführung getestet.
  2. Singleton-Container-Pattern: Der Container liegt in einer abstrakten Basisklasse. Ein static-Block startet ihn mit start(), ohne @Container. Alle Testklassen teilen ihn. Ryuk räumt am Ende auf.
  3. Spring-Lebenszyklus: Der Container ist ein @Bean in einer @TestConfiguration. Spring startet Container-Beans vor allen anderen Beans. Es stoppt sie nach ihnen. Das passt zum Context-Caching von Spring.
  4. @ServiceConnection: Es gibt es seit Spring Boot 3.1. Es ersetzt die meisten @DynamicPropertySource-Methoden. Bei GenericContainer braucht es einen name, zum Beispiel @ServiceConnection(name = "redis").
  5. @DynamicPropertySource: Das ist die flexiblere, ältere Variante. Sie setzt beliebige Properties, zum Beispiel registry.add("app.s3.url", minio::getS3URL).
  6. @ImportTestcontainers: Die Container liegen als statische Felder in einem Interface. Mehrere Testklassen importieren dasselbe Set.
  7. Development-Time Services: Seit Spring Boot 3.1 kann man Testcontainers auch beim lokalen Start der App nutzen. Eine Test-main startet die App mit den Container-Beans.
  8. Wait Strategies: Es gibt Wait.forListeningPort(), Wait.forLogMessage(regex, n), Wait.forHttp("/health") und Wait.forHealthcheck(). Die Wahl entscheidet über Stabilität.
  9. Reuse: Man setzt withReuse(true) plus testcontainers.reuse.enable=true in ~/.testcontainers.properties. Alternativ nutzt man TESTCONTAINERS_REUSE_ENABLE=true. Der Container überlebt den Testlauf. Gleiche Konfiguration heisst gleicher Container. Die Funktion ist experimentell und laut Doku nicht für CI gedacht.
  10. Ryuk: Man kann ihn mit TESTCONTAINERS_RYUK_DISABLED=true abschalten, wenn die Umgebung selbst aufräumt. Manche Umgebungen brauchen Ryuk im privileged-Modus.
  11. Testcontainers 2.0: Der JUnit-4-Support ist entfernt. Module heissen jetzt testcontainers-*, zum Beispiel org.testcontainers:testcontainers-postgresql. Container-Klassen liegen in org.testcontainers.<modul>.
  12. Daten zwischen Tests: Ein geteilter Container heisst geteilte Daten. Man leert Tabellen vor jedem Test. Man nutzt @Transactional mit Rollback. Oder man nutzt eindeutige Testdaten pro Test.

CI-Anforderungen:

  • Docker-kompatibler Daemon: Er muss erreichbar sein. Getestet wird gegen aktuelles Docker auf Linux und Docker Desktop. Podman, Colima und Rancher Desktop gehen mit Konfiguration, sind aber nicht aktiv getestet.
  • Build im Container: Läuft der Build selbst in einem Container, mountet man den Docker-Socket (Docker-in-Docker-Muster). Gegebenenfalls setzt man TESTCONTAINERS_HOST_OVERRIDE.
  • Image-Zugriff: Hinter einem Firmen-Proxy oder ohne Internet braucht man eine eigene Registry. Testcontainers unterstützt Image Name Substitution.
  • Ressourcen: Man braucht genug RAM und CPU für alle parallelen Container. Sonst killt der OOM-Killer Container.
  • Docker-Version passend zum Client: Docker Engine 29 hat die minimale API-Version auf 1.44 angehoben. Ältere Clients bekommen „client version … is too old“. Die Lösung ist, Testcontainers zu aktualisieren.
  • Alternative: Testcontainers Cloud stellt einen entfernten Docker-Daemon bereit.

4. Fallen

  • „Ein laufender Container ist bereit.“ → Falsch. Erst die Wait Strategy sagt, wann er Verbindungen annimmt.
  • „Reuse ist gut für CI.“ → Falsch. Laut Doku nicht für CI gedacht und experimentell.
  • „Der Port ist immer 5432.“ → Falsch. Der Host-Port ist zufällig. getMappedPort nutzen.
  • „Ohne stop() bleiben Container für immer.“ → Nein, Ryuk räumt auf. Ausser Ryuk ist deaktiviert.
  • „Ein Container pro Test ist sauberer.“ → Sauber, aber sehr langsam. Besser Container teilen und Daten isolieren.
  • „Testcontainers braucht das Docker-CLI.“ → Falsch. Es spricht direkt mit der Docker-API.

5. Selbsttest

Warum?

Welches Problem löst es?

Mocks und In-Memory-DBs verhalten sich anders als Produktion. Testcontainers testet gegen die echte Software in der echten Version.

Warum zufällige Ports?

Damit parallele Builds und lokale Dienste keine Port-Konflikte haben. Den Port liefert getMappedPort.

Warum kein Reuse im CI?

Die Doku sagt, es ist nicht für CI gedacht und experimentell. Im CI will man jedes Mal einen sauberen Zustand.

Warum nicht einfach H2?

Anderer SQL-Dialekt, andere Constraints und anderes Locking. Tests sind grün, Produktion bricht.

Wie innen?

Was ist Testcontainers?

Eine Bibliothek, die echte Abhängigkeiten als Docker-Container aus dem Test startet und danach wegräumt.

Wie spricht Testcontainers mit Docker?

Über die Docker-API mit dem Client docker-java. Das CLI ist nicht nötig.

Was ist Ryuk?

Ein Hilfscontainer, der alle Container der Sitzung löscht, wenn die Test-JVM endet, auch nach einem Absturz.

Was ist eine Wait Strategy?

Die Bedingung, ab wann ein Container bereit ist: Port, Log-Zeile, HTTP-Endpoint oder Docker-Healthcheck.

Was ist der Unterschied zwischen static und Instanzfeld mit @Container?

static: ein Container für alle Tests der Klasse. Instanzfeld: ein neuer Container pro Testmethode.

Was macht @ServiceConnection?

Spring Boot erzeugt ConnectionDetails-Beans aus dem Container. Sie haben Vorrang vor den Verbindungs-Properties. Seit Spring Boot 3.1.

Wie funktioniert Reuse?

withReuse(true) und testcontainers.reuse.enable=true in ~/.testcontainers.properties. Der Container läuft nach dem Test weiter und wird beim nächsten Lauf mit gleicher Konfiguration wiederverwendet.

Wie lässt Spring Container-Beans starten und stoppen?

Container-Beans starten vor allen anderen Beans und stoppen nach ihnen. Einmal pro Application Context.

Zahlen

Warum wartet das Postgres-Modul auf die Log-Zeile zweimal?

Das Image startet zuerst eine Init-Instanz und fährt sie wieder herunter. Erst die zweite Meldung kommt vom echten Server.

Wie lange wartet das Postgres-Modul auf den Start?

Es wartet auf die Log-Zeile „database system is ready to accept connections“ zweimal, mit 60 s Timeout. Der erste Lauf ist langsam, weil Docker erst das Image holt.

Welche Docker-API-Version verlangt Docker Engine 29?

Mindestens 1.44. Ältere Clients bekommen „client version … is too old“. Die Lösung ist, die Testcontainers-Version anzuheben.

Vergleich

Wann nutzen Sie @DynamicPropertySource statt @ServiceConnection?

Wenn es keine ConnectionDetails für den Dienst gibt oder eigene Properties gesetzt werden müssen.

Was änderte Testcontainers 2.0?

JUnit 4 entfernt, Module heissen testcontainers-*, Container-Klassen liegen in eigenen Paketen pro Modul.

Testcontainers, Embedded-Server oder Docker Compose?

Testcontainers startet echte Software in gleicher Version wie Produktion pro Test oder Lauf. Embedded-Server brauchen kein Docker, haben aber oft andere Version und Konfiguration. Docker Compose im CI gibt eine feste Umgebung mit weniger Isolation und Port-Konflikten.

Produktion

Was braucht Testcontainers im CI?

Einen Docker-kompatiblen Daemon, Zugriff auf den Socket, Zugriff auf Images und genug Speicher für alle Container.

Szenario: Nach einem Docker-Update schlagen alle Testcontainers-Tests mit „client version is too old“ fehl. Was tun Sie?

Docker Engine 29 verlangt mindestens API 1.44. Ich aktualisiere Testcontainers. Übergangsweise fixiere ich die Docker-Version im CI.

Szenario: Im CI stirbt der Datenbank-Container mitten im Lauf mit Exit 137. Was prüfen Sie?

137 heisst SIGKILL, oft OOM. Ich prüfe docker inspect auf OOMKilled, setze ein Speicherlimit, reduziere Parallelität und teile Container.

Szenario: Die Integrationstests dauern 20 Minuten, jeder Test startet eigene Container. Wie beschleunigen Sie?

static- oder Singleton-Container, Spring-Context-Cache nutzen, Daten statt Container isolieren, lokal Reuse aktivieren.

Design

Was ist das Singleton-Container-Pattern?

Ein Container in einer Basisklasse, einmal manuell gestartet und von allen Testklassen geteilt. Ryuk räumt am Ende auf.

Wie isolieren Sie Daten bei einem geteilten Container?

Tabellen vor jedem Test leeren, Transaktion mit Rollback oder eindeutige Testdaten pro Test.

Wie testen Sie mit Testcontainers hinter einem Firmen-Proxy?

Images aus einer internen Registry ziehen, mit Image Name Substitution. Ryuk-Image ebenfalls spiegeln.

Mehr

Gerüst

  • Warum? Mocks und In-Memory-DBs verhalten sich anders als Produktion. Mit echtem, frischem Container testet man echtes SQL.
  • Wie innen? Die Bibliothek spricht über docker-java mit der Docker-API. Zufälliger Host-Port, Wait Strategy bis der Container bereit ist. Ryuk räumt auf.
  • Zahlen Das Postgres-Modul wartet zweimal auf die Log-Zeile, mit 60 s Timeout. Docker Engine 29 verlangt API-Version mindestens 1.44. Testcontainers for Java 2.0.x.
  • Vergleich Testcontainers = echte Software, braucht Docker. H2 = schnell, aber anderer Dialekt. Docker Compose im CI = weniger Isolation. Reuse ist experimentell.
  • Produktion Docker-Upgrade bricht alle Tests (API zu alt). Container wird OOM-gekillt (Exit 137). Wait Strategy nur auf den Port macht Tests flaky.
  • Design Container pro Lauf teilen, Daten isolieren. Gleiche Image-Version wie Produktion. Reuse nur lokal, nie im CI.

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Maven, JUnit und Testcontainers sind hier nicht installiert. Zeiten und IDs beispielhaft.

  1. -P mappt jeden Container-Port auf einen freien Host-Port, hier 32768. Testcontainers macht das immer. getMappedPort(5432) liefert ihn.
  2. Das Postgres-Image startet zweimal: zuerst eine Init-Instanz, die gleich wieder herunterfährt, dann den echten Server. Darum wartet das Modul auf die Log-Zeile zweimal. Wer nur auf den Port wartet, verbindet sich zu früh.
  3. Das Postgres-Modul startet den Server mit fsync=off. Das ist schneller und für Wegwerf-Daten unkritisch.
  4. static + @Container: ein Container für alle Tests der Klasse. Ein Instanzfeld startet einen Container pro Testmethode.
  5. @ServiceConnection erzeugt JdbcConnectionDetails. Diese haben Vorrang vor spring.datasource.*.
  6. Testcontainers 2.0: Die neue Klasse heisst org.testcontainers.postgresql.PostgreSQLContainer und ist nicht mehr generisch. Die alte in org.testcontainers.containers ist deprecated.

Vergleich

  • Testcontainers: echte Software, gleiche Version wie Produktion, braucht Docker, Start in Sekunden.
  • H2 / In-Memory-DB: sehr schnell, kein Docker. Aber anderer SQL-Dialekt, andere Constraints, falsches Vertrauen.
  • Embedded-Server (Embedded Kafka, Embedded Redis): kein Docker, aber oft andere Version und andere Konfiguration.
  • Docker Compose im CI: eine feste Umgebung für alle Tests. Weniger Isolation, Lebenszyklus ausserhalb des Tests, Port-Konflikte.
  • Gemeinsame Test-DB: keine Isolation, Tests stören sich, Daten verfallen. Nicht empfohlen.
  • WireMock: für HTTP-Partner, die man nicht als Container starten kann. Ergänzt Testcontainers.

In der Produktion (CI und Entwickler-Laptops)

  1. „Could not find a valid Docker environment“: Kein Daemon oder kein Zugriff auf den Socket. Lösung: Docker starten, Rechte prüfen, DOCKER_HOST setzen.
  2. Docker-Upgrade bricht alle Tests: Nach Docker Engine 29 lehnt der Daemon alte API-Versionen ab. Lösung: Testcontainers-Version anheben. Übergangsweise Docker-Version im CI fixieren.
  3. Container wird OOM-gekillt: Viele parallele Testklassen starten viele schwere Container. Lösung: Speicherlimit pro Container, weniger Parallelität für schwere Tests, Singleton-Container.
  4. Tests zu langsam: Jeder Test startet einen eigenen Container. Lösung: static-Container oder Singleton, Spring-Context-Cache nutzen, lokal Reuse.
  5. Flaky beim Start: Wait Strategy wartet nur auf den Port. Lösung: Log- oder Health-Wartebedingung.
  6. Image-Pull scheitert im CI: Rate-Limit von Docker Hub oder Proxy. Lösung: eigene Registry-Spiegelung und Image Name Substitution.
  7. Liegengebliebene Container: Ryuk deaktiviert und JVM mit kill -9 beendet. Lösung: Ryuk aktiv lassen oder CI-Agent räumt auf.

Diagnose: Werkzeuge und Befehle

  • docker ps --filter label=org.testcontainers=true: Container dieser Sitzungen anzeigen.
  • docker logs <id>: warum der Container nicht bereit wird.
  • container.getLogs() oder withLogConsumer(new Slf4jLogConsumer(log)): Container-Logs im Testlog.
  • docker inspect <id> --format '{{.State.OOMKilled}}': wurde der Container OOM-gekillt?
  • docker version und docker info: Daemon-Version und API-Version prüfen.
  • ~/.testcontainers.properties: Reuse, Docker-Strategie, Ryuk-Einstellungen.
  • Logger org.testcontainers auf DEBUG: zeigt Docker-Erkennung und Wartebedingungen.

Senior-Punkte

  1. Echte Abhängigkeiten für alles mit Protokoll oder Dialekt. SQL, Kafka, Redis, S3 teste ich gegen echte Container, nicht gegen Mocks.
  2. Startzeit ist das Hauptkosten-Thema. Ich teile Container pro Lauf und isoliere Daten statt Container.
  3. Gleiche Image-Version wie Produktion, als Konstante oder BOM gepflegt. Sonst testet man die falsche Version.
  4. CI ist Infrastruktur: Docker-Version, Speicher und Registry gehören in die Plattform-Planung.
  5. Reuse nur lokal. Im CI will ich jedes Mal einen sauberen Zustand.
  6. Nicht alles wird ein Testcontainers-Test. Geschäftslogik bleibt im Unit-Test. Container nur an den Grenzen.
