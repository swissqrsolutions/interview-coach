E2E: Playwright, Cypress, Selenium

Kern: Ein E2E-Test (End-to-End) steuert die fertige App in einem echten Browser wie ein Nutzer. Er prüft ganze Abläufe über Frontend, Backend und Datenbank. Er ist realistisch, aber langsam und anfällig für Flakiness.

Antwort-Muster

Frage: Wie testen Sie wichtige Abläufe End-to-End, und welches Werkzeug nehmen Sie?

  1. Mechanismus: Der Test öffnet einen Browser, sucht Elemente per Locator und klickt. Vor jeder Aktion wartet das Werkzeug, bis das Element bereit ist.
  2. Zahl: In Playwright gilt ein Test-Timeout von 30 Sekunden und ein Timeout für Assertions von 5 Sekunden. Retries sind standardmässig aus.
  3. Trade-off: E2E-Tests sind realistisch, aber langsam und brüchig. Darum schreibt man nur wenige und deckt den Rest mit Unit- und API-Tests ab.
  4. Produktion: Ich lasse Tests parallel laufen und sammle bei Fehlern einen Trace. Rote Tests untersuche ich, bevor ich Retries erhöhe.

1. Ein E2E-Test in 7 Schritten

  1. Neuer Context: Jeder Test bekommt einen frischen Browser Context. Das ist ein isoliertes Profil wie im Inkognito-Modus. Cookies und Storage sind leer.
  2. Seite öffnen: page.goto('/shop') lädt die App. Die Navigation hat standardmässig keinen eigenen Timeout.
  3. Locator: page.getByRole('button', { name: 'Pay' }) beschreibt ein Element. Er sucht erst bei der Aktion neu.
  4. Aktion: Vor click() prüft Playwright fünf Dinge. Es gibt genau ein Element. Es ist sichtbar, stabil, aktiviert und empfängt Events. Playwright wartet, bis alle Checks passen.
  5. Assertion: expect(locator).toBeVisible() versucht es erneut, standardmässig bis 5 Sekunden.
  6. Bei Fehler: Der Test scheitert nach dem Timeout. Der Report zeigt den Fehler. Mit on-first-retry nimmt Playwright beim ersten Retry einen Trace auf.
  7. Aufräumen: Nach einem Fehler verwirft Playwright den Worker samt Browser. Der nächste Test startet in einem neuen.

Cypress und Selenium folgen demselben Muster: Element suchen, warten, Aktion, prüfen. Sie lösen Warten und Isolation unterschiedlich.

2. Aufbau

  1. Runner: Er findet Tests, startet Worker und sammelt Ergebnisse. Playwright hat einen eigenen Runner.
  2. Browser und Context: Der Context ist ein isoliertes Profil. Mehrere Contexts teilen sich einen Browser.
  3. Locator: Beschreibt ein Element. Er löst erst bei der Aktion auf und findet es bei Neu-Rendern wieder.
  4. Warte-Strategie: Playwright wartet automatisch. Cypress wiederholt Queries und Assertions. Selenium wartet mit expliziten Waits.
  5. Reporter und Trace: Der Report zeigt Fehler. Der Trace zeigt Aktionen, DOM-Snapshots, Netzwerk und Konsole.
  6. CI-Betrieb: Parallele Worker und Sharding auf mehrere Maschinen halten die Laufzeit kurz.

3. Details

  1. Wo E2E hingehört: Fowler nennt UI-Tests brüchig, teuer und langsam. Man schreibt viel mehr Unit- als UI-Tests. Eine Alternative sind Tests auf Service- oder API-Ebene. Ein Fehler aus einem hohen Test wird zuerst mit einem Unit-Test nachgestellt.
  2. Actionability: Playwright prüft je Aktion bestimmte Dinge. Ein Klick braucht: sichtbar, stabil, empfängt Events, aktiviert, nicht inert. Stabil heisst, die Bounding Box blieb für mindestens zwei Animation Frames gleich. Mit force entfallen die nicht wesentlichen Checks.
  3. Locators: Die Doku empfiehlt zuerst getByRole(). Dazu kommen getByText(), getByLabel() und getByTestId(). Ein Locator ist streng. Passen mehrere Elemente, wirft eine Aktion einen Fehler. Man kann Locators verketten und filtern.
  4. Timeouts: Der Test-Timeout ist 30 Sekunden. Assertions haben getrennt 5 Sekunden. Action und Navigation haben keinen Standard-Timeout. Ein globaler Timeout ist nicht gesetzt.
  5. Isolation: Ein Browser Context ist wie ein Inkognito-Profil. Die Fixture context ist je Test neu. Contexts sind billig zu erzeugen. Ein Test kann mehrere Contexts nutzen, zum Beispiel für Admin und Nutzer.
  6. Parallel und Sharding: Testdateien laufen standardmässig parallel. Tests in einer Datei laufen nacheinander. Mit fullyParallel: true laufen alle parallel. Worker teilen nichts. --shard=2/3 verteilt die Suite auf mehrere Maschinen.
  7. Retries und Flaky: Fehlgeschlagene Tests werden standardmässig nicht wiederholt. Besteht ein Test erst im Retry, nennt der Report ihn flaky. Nach einem Fehler startet ein neuer Worker. Im Serial-Modus überspringt ein Fehler die folgenden Tests.
  8. Trace: Mit trace: 'on-first-retry' nimmt Playwright beim ersten Retry auf. Der Trace enthält jede Aktion und DOM-Snapshots vor und nach jeder Aktion. Dazu kommen Netzwerk, Fehler und Konsole. Man öffnet ihn über npx playwright show-report.
  9. Cypress-Architektur: Cypress läuft im Browser und hat so direkten Zugriff auf die App. Server-Zugriff geht über cy.task() oder cy.request(). Es steuert einen Browser auf einmal. Sprache ist nur JavaScript. Ein Wechsel der Domain im Test braucht cy.origin. Iframes sind eingeschränkt.
  10. Cypress-Retries: Queries wiederholen sich als Kette. Assertions nach einem Befehl wiederholen sich auch. Aktionen wie .click() laufen nur einmal. Das Limit ist 4 Sekunden (defaultCommandTimeout). Test-Retries sind standardmässig 0. Fehler in before und after lösen keinen Retry aus.
  11. Selenium: WebDriver steuert einen Browser wie ein Nutzer, lokal oder auf einer fremden Maschine über den Selenium-Server. Es ist eine W3C Recommendation. Es gibt Java, Python, C#, Ruby, JavaScript und Kotlin. Selenium Manager lädt den passenden Treiber seit 4.6 automatisch.
  12. Selenium-Waits: Ein Explicit Wait wartet in einer Schleife auf eine Bedingung. Ein Implicit Wait gilt für jede Suche und ist standardmässig 0. Die Doku sagt: nicht mischen. Das kann unvorhersehbare Wartezeiten erzeugen.

4. Fallen

  • „E2E-Tests sollen die Mehrheit der Tests sein.“ → Falsch. Sie sind langsam und brüchig. Man schreibt viel mehr Unit-Tests und wenige E2E-Tests für die wichtigsten Abläufe.
  • „Playwright braucht sleep zwischen den Schritten.“ → Falsch. Es wartet vor jeder Aktion selbst auf die Checks und wiederholt Assertions bis zum Timeout.
  • „force: true macht Tests stabiler.“ → Falsch. Es schaltet Checks ab. Der Test klickt dann auch, wenn das Element verdeckt ist. Echte Probleme bleiben verborgen.
  • „Cypress steuert beliebig viele Tabs und Browser.“ → Falsch. Cypress steuert einen Browser auf einmal. Tabs und Popups gehen nur über ein Plugin.
  • „Implicit und Explicit Waits kann man mischen.“ → Falsch. Die Selenium-Doku warnt davor. Es entstehen unvorhersehbare Wartezeiten.
  • „Retries machen Tests stabil.“ → Falsch. Sie verstecken Flakiness. Playwright und Cypress Cloud markieren solche Tests, damit man die Ursache sucht.

5. Selbsttest

Warum?

Warum schreibt man nur wenige E2E-Tests?

Sie sind langsam, teuer in der Pflege und anfällig für Flakiness. Unit- und API-Tests finden dieselben Fehler schneller.

Warum wartet Playwright automatisch?

Apps rendern asynchron. Ein fester Sleep ist entweder zu kurz oder zu lang. Die Checks warten genau auf den Zustand.

Warum ein Browser Context je Test?

Cookies und Storage eines Tests dürfen den nächsten nicht beeinflussen. Contexts sind billig und isolieren vollständig.

Wie innen?

Was prüft Playwright vor einem Klick?

Genau ein Element, sichtbar, stabil, empfängt Events, aktiviert und nicht inert. Es wartet, bis alles passt, oder läuft in den Timeout.

Was ist ein Browser Context?

Ein isoliertes, Inkognito-ähnliches Profil mit eigenen Cookies und Storage. Mehrere Contexts teilen sich einen Browser.

Wie funktioniert Retry-ability in Cypress?

Queries und danach folgende Assertions wiederholen sich bis zum Timeout. Aktionen laufen nur einmal, weil sie den Zustand ändern können.

Wie arbeitet WebDriver?

Ein Treiber steuert den Browser nach dem W3C-Standard. Das geht lokal oder über den Selenium-Server auf einer anderen Maschine.

Wie verteilt man eine grosse Suite?

Mit parallelen Workern und mit Sharding. --shard=2/3 lässt auf einer Maschine nur einen Teil laufen.

Zahlen

Wie lang ist der Standard-Timeout eines Playwright-Tests?

30 Sekunden.

Wie lang ist der Standard-Timeout für expect in Playwright?

5 Sekunden.

Wie lang ist das Standard-Limit für Cypress-Befehle?

4 Sekunden (defaultCommandTimeout).

Wie viele Retries gibt es standardmässig?

Keine, sowohl in Playwright als auch in Cypress. Der Implicit Wait in Selenium ist 0.

Vergleich

Playwright oder Cypress?

Playwright hat Contexts, Auto-Waiting und Sharding im Runner. Cypress läuft im Browser, hat aber Einschränkungen bei Domains, Tabs und Sprachen.

Playwright oder Selenium?

Selenium ist ein W3C-Standard mit vielen Sprachen und Grid. Playwright bringt Runner, Auto-Waiting und Trace Viewer mit.

Implicit oder Explicit Wait?

Implicit gilt global für jede Suche. Explicit wartet gezielt auf eine Bedingung. Man mischt sie nicht.

E2E oder API-Test?

E2E prüft den ganzen Weg über die Oberfläche. Ein API-Test prüft die Schicht darunter schneller und stabiler.

Produktion

Wie findet man die Ursache eines flaky Tests?

Mit dem Trace. Er zeigt Aktionen, DOM und Netzwerk zum Zeitpunkt des Fehlers.

Wie verkürzt man eine lange Laufzeit?

Parallele Worker, Sharding auf mehrere Maschinen und weniger Tests durch Verlagerung nach unten in die Pyramide.

Szenario: Ein Test läuft lokal grün, aber in der CI oft rot. Was prüfen Sie?

Zeitabhängigkeit, geteilte Testdaten und langsamere Rechner. Dann Trace der CI-Läufe lesen. Nicht einfach den Timeout erhöhen.

Szenario: 400 E2E-Tests brauchen zwei Stunden. Was tun Sie?

Prüfen, was man als API- oder Komponenten-Test ersetzen kann. Den Rest parallel und in Shards laufen lassen. Anmeldung und Daten per API aufbauen.

Design

Welche Abläufe testet man E2E?

Wenige, geschäftskritische Abläufe wie Login, Bezahlen und Einreichen. Alles andere gehört weiter unten in die Pyramide.

Wie wählt man Selektoren?

Nach Rolle und sichtbarem Namen, so wie ein Nutzer das Element sieht. Test-IDs sind der Ausweg. CSS-Klassen sind brüchig.

Szenario: Jeder Test legt Daten an, und Tests stören sich. Wie lösen Sie das?

Jeder Test legt eigene Daten mit eindeutigen Namen an. Er hängt nicht vom Zustand eines anderen ab. So laufen Tests parallel.

Wie testet man mehrere Nutzer, zum Beispiel einen Chat?

Mit mehreren Browser Contexts in einem Test. Jeder Context ist ein eigener Nutzer mit eigenen Cookies.

Mehr

Gerüst

  • Warum? Wichtige Abläufe so prüfen, wie ein Nutzer sie erlebt.
  • Wie innen? Context, Locator, Actionability-Checks, Assertion mit Retry, Trace.
  • Zahlen Test 30 s, expect 5 s, Cypress 4 s. Retries standardmässig 0. Selenium Manager seit 4.6.
  • Vergleich Playwright gegen Cypress gegen Selenium. Implicit gegen Explicit Wait.
  • Produktion Flaky in der CI. Zu lange Laufzeit. Gemeinsame Testdaten.
  • Design Wenige Tests. Parallel und isoliert. Trace statt Raten.

Beispiel: Ein Playwright-Test und die Config

import { test, expect } from '@playwright/test';

test('customer can place an order', async ({ page }) => {
  await page.goto('/shop');
  await page.getByRole('listitem').filter({ hasText: 'Book' })
            .getByRole('button', { name: 'Add to cart' }).click();
  await page.getByRole('link', { name: 'Cart' }).click();
  await page.getByRole('button', { name: 'Pay' }).click();
  await expect(page.getByText('Order confirmed')).toBeVisible();
});

// playwright.config.ts
export default defineConfig({
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  use: { trace: 'on-first-retry' },
});

Nicht ausgeführt.

  1. Locators: Der Test sucht per Rolle und Text. Er enthält keine CSS-Klassen und keine Wartezeiten.
  2. Warten: Jeder Klick wartet auf die Actionability-Checks. toBeVisible() wiederholt sich bis zum Timeout.
  3. fullyParallel: Alle Tests laufen parallel. Das setzt voraus, dass sie voneinander unabhängig sind.
  4. Retries und Trace: In der CI gibt es zwei Retries. Beim ersten Retry nimmt Playwright einen Trace auf.

Vergleich

  • Playwright: Eigener Runner, Browser Contexts, Auto-Waiting, Trace Viewer und Sharding.
  • Cypress: Läuft im Browser. Nur JavaScript. Ein Browser auf einmal. Queries und Assertions wiederholen sich.
  • Selenium: W3C WebDriver. Viele Sprachen. Selenium Manager. Man baut Runner und Waits selbst.
  • API-Test: Prüft die Schicht unter der Oberfläche. Schneller und stabiler.
  • Komponenten-Test: Prüft eine Komponente ohne ganze App. Mittelweg zwischen Unit und E2E.
  • Contract-Test: Prüft die Schnittstelle zwischen zwei Services ohne beide zu starten. Ersetzt viele E2E-Tests.

Produktion

  1. Flaky durch Timing: Tests raten die Zeit. Lösung: auf einen Zustand warten und feste Sleeps entfernen.
  2. Geteilte Daten: Tests ändern dieselben Datensätze. Lösung: eigene Daten je Test mit eindeutigen Namen.
  3. Lange Laufzeit: Zu viele Tests über die Oberfläche. Lösung: nach unten verlagern, parallel laufen lassen und Shards nutzen.
  4. Retries ohne Ursache: Die Suite wird grün und verbirgt Fehler. Lösung: flaky Tests aus dem Report verfolgen und beheben.
  5. Brüchige Selektoren: CSS-Klassen ändern sich. Lösung: Rollen, Labels oder Test-IDs.
  6. Umgebung instabil: Die Test-Umgebung hat langsame oder fehlende Dienste. Lösung: stabile, eigene Umgebung und Health-Check vor dem Lauf.

Diagnose: Werkzeuge und Befehle

  • Report öffnen: npx playwright show-report zeigt den HTML-Report mit Traces.
  • Trace erzwingen: --trace on nimmt lokal für jeden Lauf einen Trace auf.
  • Shard: npx playwright test --shard=2/3 lässt den zweiten von drei Teilen laufen.
  • Cypress: cypress run ist der Lauf für die CI (runMode). cypress open ist der interaktive Lauf (openMode).
  • Flaky-Liste: Der Playwright-Report zeigt Tests, die erst im Retry bestanden. Cypress Cloud zeigt einen Flaky-Filter.

Senior-Punkte

  1. E2E ist teuer, also bewusst einsetzen.: Jeder E2E-Test braucht einen Grund, den kein günstigerer Test abdeckt.
  2. Isolation ist die Grundlage.: Frischer Context, eigene Daten und kein geteilter Zustand machen Parallelität möglich.
  3. Warten auf Zustand, nie auf Zeit.: Das ist der wichtigste Stabilitätsfaktor.
  4. Flaky ist ein Fehlerbericht.: Ein Retry, der besteht, sagt, dass etwas schwankt. Die Ursache zu suchen kostet weniger als jahrelang zu retryen.
  5. Werkzeugwahl ist Kontext.: Team-Sprache, Browser-Bedarf und vorhandene Infrastruktur zählen mehr als Funktionslisten.
  6. Tests sind Produktcode.: Sie brauchen Reviews, Namen und Pflege wie der Rest.
