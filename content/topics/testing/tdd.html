TDD

Kern: TDD (Test-Driven Development) schreibt zuerst einen Test und dann den Code. Der Zyklus heisst Red, Green, Refactor. Man macht den Test rot, dann grün und räumt danach den Code auf.

Antwort-Muster

Frage: Wie läuft TDD ab, und was bringt es?

  1. Mechanismus: Ich schreibe einen kleinen Test, der fehlschlägt (Red). Dann schreibe ich den einfachsten Code, der ihn besteht (Green). Danach räume ich auf (Refactor).
  2. Zahl: Ein Zyklus hat drei Phasen. Jeder Zyklus dauert Minuten und nicht Stunden. In der Demo laufen drei Tests in 0,002 Sekunden.
  3. Trade-off: TDD kostet am Anfang Zeit. Dafür entsteht Code mit Tests, und ich denke zuerst an die Schnittstelle. Der häufigste Fehler ist, das Refactoring zu überspringen.
  4. Produktion: Bei einem Bug schreibe ich zuerst einen Test, der ihn zeigt. Erst dann behebe ich ihn.

1. Der TDD-Zyklus in 7 Schritten

  1. Testliste: Man schreibt eine Liste der Fälle, die funktionieren sollen. Neue Fälle kommen dazu, sobald sie einem einfallen.
  2. Einen Test wählen: Man nimmt einen Fall aus der Liste. Die Reihenfolge ist eine Fähigkeit. Gute Tests führen schnell zu den wichtigen Entwurfsfragen.
  3. Test schreiben: Man schreibt den Test für die nächste kleine Funktion. Dabei denkt man an die Schnittstelle und noch nicht an die Umsetzung.
  4. Red: Man lässt den Test laufen. Er muss scheitern, und zwar aus dem erwarteten Grund.
  5. Green: Man schreibt gerade so viel Code, dass der Test besteht.
  6. Refactor: Man räumt neuen und alten Code auf, damit er gut gebaut ist. Die Tests bleiben dabei grün.
  7. Abhaken: Man streicht den Fall von der Liste und nimmt den nächsten.

Die Demo unten zeigt Red und Green mit echter Ausgabe.

2. Aufbau

  1. Testliste: Eine Liste der geplanten Fälle. Man arbeitet sie nacheinander ab.
  2. Red: Ein Test, der noch scheitert. Er beschreibt das gewünschte Verhalten.
  3. Green: Gerade genug Code für den Test. Schönheit kommt später.
  4. Refactor: Aufräumen bei grünen Tests. Hier entsteht das Design.
  5. Sicherheitsnetz: Die wachsende Suite fängt Fehler bei jeder Änderung ab.
  6. Feedback: Der Lauf dauert Sekunden oder weniger. Nur so bleibt der Zyklus kurz.

3. Details

  1. Der Zyklus: Fowler beschreibt ihn in drei Schritten. Man schreibt einen Test für die nächste Funktion. Man schreibt Code, bis er besteht. Man räumt neuen und alten Code auf. Das heisst Red, Green, Refactor.
  2. Testliste: Vor dem Zyklus schreibt man die Liste der Fälle. Dann nimmt man einen, geht den Zyklus durch und wählt den nächsten. Neue Fälle fügt man jederzeit an.
  3. Red zuerst: Ein Test, der nie rot war, kann Fehler nicht zeigen. Man sieht ihn scheitern und prüft, ob die Meldung stimmt. Erst dann glaubt man, dass er etwas prüft.
  4. Kleinster Schritt: Für Green genügt der einfachste Code. Der darf sogar eine feste Zahl zurückgeben. Der nächste Test zwingt zur allgemeinen Lösung.
  5. Refactor: Fowler nennt das Überspringen des Refactorings den häufigsten Fehler. Das Ergebnis ist unordentlicher Code, der wenigstens Tests hat.
  6. Selbsttestender Code: Man schreibt funktionalen Code nur, um einen roten Test grün zu machen. So hat jede Zeile einen Test, der sie braucht.
  7. Schnittstelle zuerst: Der Test kommt vor der Umsetzung. Das zwingt dazu, die Schnittstelle zu durchdenken. Es trennt Schnittstelle und Implementierung.
  8. Zwei Schulen: Classicists nehmen echte Objekte und arbeiten oft von innen nach aussen. Mockists ersetzen Kollaborateure und arbeiten von aussen nach innen. Beides ist TDD.
  9. Schrittgrösse: Eine feste Regel gibt es nicht. Man wählt Tests, die schnell zu den wichtigen Entwurfspunkten führen. Wird ein Schritt lang, teilt man den Test auf.
  10. Bugs: Ein Fehler aus einem hohen Test oder aus der Produktion wird zuerst mit einem Unit-Test nachgestellt. Erst dann behebt man ihn. So bleibt er behoben.

4. Fallen

  • „TDD heisst, erst alle Tests schreiben und dann den Code.“ → Falsch. Man arbeitet mit einem Test auf einmal. Jeder durchläuft den ganzen Zyklus.
  • „Der erste Lauf soll grün sein.“ → Falsch. Er soll rot sein. Sonst weiss man nicht, ob der Test überhaupt etwas prüft.
  • „Refactoring ist optional.“ → Falsch. Das Überspringen ist laut Fowler der häufigste Fehler. Es bleibt unordentlicher Code zurück.
  • „TDD garantiert gutes Design.“ → Falsch. Es gibt ein Sicherheitsnetz und Feedback. Das Design kommt aus dem Refactoring und aus dem Urteil des Teams.
  • „Hohe Coverage heisst, man macht TDD.“ → Falsch. Coverage sagt nur, welche Zeilen liefen. Sie sagt nicht, ob der Test zuerst kam oder etwas prüft.
  • „TDD braucht immer Mocks.“ → Falsch. Classicists nutzen echte Objekte und Doubles nur bei Unbequemem.

5. Selbsttest

Warum?

Warum schreibt man den Test zuerst?

Man denkt an die Schnittstelle, bevor man implementiert. Jeder Code hat danach einen Test, der ihn verlangt.

Warum zuerst rot?

Ein Test, der nie rot war, könnte immer grün sein. Man sieht ihn scheitern und weiss, dass er etwas prüft.

Warum die Refactor-Phase?

Green nimmt den einfachsten Code. Das Refactoring macht daraus gute Struktur. Ohne es bleibt unordentlicher Code zurück.

Wie innen?

Wie läuft ein TDD-Zyklus ab?

Test schreiben, rot sehen, einfachsten Code schreiben bis grün, aufräumen. Dann der nächste Test.

Was ist die Testliste?

Eine Liste der Fälle, die funktionieren sollen. Man arbeitet sie nacheinander ab und ergänzt sie laufend.

Wie wählt man den nächsten Test?

Man nimmt den, der schnell zu den wichtigen Entwurfspunkten führt. Das ist eine Fähigkeit und keine feste Regel.

Wie kommt man von einem hartcodierten Wert zur echten Lösung?

Der erste Test besteht mit einer festen Zahl. Der zweite Test mit anderen Werten macht die feste Zahl falsch. So entsteht die allgemeine Regel.

Was passiert in der Demo in der Red-Phase?

Der Stub gibt den Betrag unverändert zurück. Zwei von drei Tests scheitern. Nur der Fall ohne Rabatt besteht.

Zahlen

Wie viele Phasen hat der Zyklus?

Drei: Red, Green und Refactor.

Wie viele Tests sind in der Demo rot, wie viele grün?

Zuerst zwei rot und einer grün. Nach der Umsetzung alle drei grün.

Wie viel Coverage verlangt TDD?

Keine feste Zahl. Coverage ist ein Nebenprodukt und kein Ziel.

Vergleich

TDD oder Tests nachträglich?

Bei TDD formt der Test die Schnittstelle. Nachträgliche Tests prüfen schon gebauten Code und sind schwerer zu schreiben.

Classical oder mockist?

Classical arbeitet mit echten Objekten, oft von innen nach aussen. Mockist ersetzt Kollaborateure und arbeitet von aussen nach innen.

Outside-in oder inside-out?

Outside-in beginnt bei der äusseren Schnittstelle und ersetzt innere Teile durch Doubles. Inside-out beginnt bei den Bausteinen und baut nach aussen.

TDD oder Spike?

Ein Spike erkundet eine Idee ohne Tests und wird weggeworfen. TDD baut den Code, der bleibt.

Produktion

Wie verhindert man, dass ein behobener Bug zurückkommt?

Man schreibt zuerst einen Test, der den Bug zeigt. Er bleibt in der Suite und schlägt bei Rückkehr des Fehlers an.

Szenario: Das Team gibt TDD auf, weil es zu langsam sei. Was prüfen Sie?

Die Laufzeit der Tests und die Grösse der Schritte. Langsame Tests und grosse Schritte bremsen den Zyklus. Man zerlegt und beschleunigt.

Szenario: Ein Refactoring bricht 30 Tests, obwohl das Verhalten gleich bleibt. Was ist falsch?

Die Tests prüfen die Implementierung, zum Beispiel Aufrufe an Mocks. Man schreibt sie so um, dass sie Ergebnisse prüfen.

Szenario: Ein altes Modul hat keine Tests. Wie gehen Sie vor?

Man hält zuerst das heutige Verhalten mit Tests fest. Danach ändert man in kleinen Schritten mit TDD.

Design

Wie zerlegen Sie «Rabatt 10 % nach zwei Jahren»?

Testliste: neuer Kunde, ab zwei Jahren, Rundung auf den Rappen. Jeder Fall wird ein Test.

Wie testet man Grenzwerte?

Man testet genau die Grenze und beide Seiten davon. Zum Beispiel ein Jahr, zwei Jahre und drei Jahre.

Szenario: Der Code hängt von der aktuellen Uhrzeit ab. Wie machen Sie ihn testbar?

Die Uhr kommt als Abhängigkeit hinein. Im Test gibt ein Stub eine feste Zeit zurück.

Szenario: Ein Test ist schwer zu schreiben. Was sagt das?

Oft hat die Klasse zu viele Abhängigkeiten oder eine unklare Aufgabe. Der Test zeigt ein Designproblem.

Mehr

Gerüst

  • Warum? Sicheres Sicherheitsnetz und gutes Design durch kleine Schritte.
  • Wie innen? Testliste, dann Red, Green, Refactor. Ein Test auf einmal.
  • Zahlen Drei Phasen. Demo: zwei von drei Tests rot, dann alle grün.
  • Vergleich TDD gegen Tests nachträglich. Classical gegen mockist. Outside-in gegen inside-out.
  • Produktion Refactoring übersprungen. Tests zu langsam. Tests prüfen die Implementierung.
  • Design Bug zuerst als Test. Schnittstelle zuerst. Uhr als Abhängigkeit.

Beispiel: Rabatt-Regel mit Red und Green

# test_shop.py  (drei Tests aus der Testliste)
def test_no_discount_for_new_customer:  price(10000, 0) == 10000
def test_ten_percent_after_two_years:   price(10000, 2) == 9000
def test_discount_rounds_down_to_cent:  price(1005, 2)  == 904

# RED: shop.py gibt den Betrag unverändert zurück
def price_with_discount(total_cents, customer_years):
    return total_cents

# GREEN: einfachster Code, der alle drei besteht
def price_with_discount(total_cents, customer_years):
    if customer_years >= 2:
        return total_cents * 90 // 100
    return total_cents

Echte Ausgabe, Python 3.12.10 (unittest). Im Rot-Teil sind die Traceback-Zeilen gekürzt. Die Testfunktionen sind oben als Kurzform geschrieben.

  1. Red: Der Test für neue Kunden besteht schon. Die beiden Rabatt-Tests scheitern aus dem richtigen Grund. Der Betrag blieb gleich.
  2. Green: Eine Bedingung und eine Rechnung reichen. Die Integer-Division rundet 904,5 auf 904 ab.
  3. Refactor: Hier gäbe es wenig aufzuräumen. Bei mehr Regeln würde man die Zahl 90 benennen oder eine Tabelle bauen. Die Tests bleiben dabei grün.
  4. Tempo: Die drei Tests laufen in Millisekunden. Das hält den Zyklus kurz.

Vergleich

  • TDD: Test zuerst. Der Zyklus steuert Code und Design.
  • Tests nachträglich: Der Code ist schon da. Tests sichern ihn ab, formen aber nicht die Schnittstelle.
  • Classical TDD: Echte Objekte, Doubles nur bei Unbequemem. Oft inside-out.
  • Mockist TDD: Kollaborateure werden ersetzt. Oft outside-in. Tests sind enger an die Implementierung gebunden.
  • Spike: Kurze Erkundung ohne Tests, die man wegwirft.
  • Characterization Tests: Halten das heutige Verhalten von altem Code fest, bevor man ihn ändert.

Produktion

  1. Refactoring übersprungen: Der Code wird unordentlich. Lösung: Refactor als feste Phase und im Review prüfen.
  2. Langsame Tests: Der Zyklus dauert zu lang, und niemand macht ihn. Lösung: Tests ohne Netz und Datenbank, kleine Einheiten.
  3. Tests prüfen die Implementierung: Refactorings brechen viele Tests. Lösung: Ergebnisse prüfen statt Aufrufe.
  4. Zu grosse Schritte: Ein Test verlangt zu viel auf einmal. Lösung: Test aufteilen und einfacheren Fall wählen.
  5. Legacy ohne Tests: TDD setzt beim bestehenden Code an. Lösung: erst Verhalten festhalten, dann in kleinen Schritten ändern.
  6. Bug ohne Test behoben: Er kommt später zurück. Lösung: zuerst ein Test, der ihn zeigt.

Diagnose: Werkzeuge und Befehle

  • Rot sehen: Jeden neuen Test einmal scheitern sehen. Die Fehlermeldung sollte die Erwartung nennen.
  • Laufzeit messen: Die Suite sollte in Sekunden laufen. Das Test-Framework zeigt die Zeit, zum Beispiel «Ran 3 tests in 0.002s».
  • Watch-Modus: Ein Runner im Watch-Modus startet Tests bei jeder Änderung. So bleibt das Feedback sofort da.
  • Mutation Testing: Werkzeuge ändern den Code und prüfen, ob die Tests es merken. So findet man Tests ohne Wirkung.
  • Git-Verlauf: Kleine Commits mit Test und Code zeigen, ob der Zyklus gelebt wird.

Senior-Punkte

  1. TDD ist eine Technik und kein Dogma.: Es passt gut bei klarer Logik. Bei Exploration oder UI nimmt man andere Wege.
  2. Das Refactoring ist die halbe Arbeit.: Ohne es bekommt man Tests, aber schlechten Code.
  3. Tests dokumentieren Verhalten.: Gute Namen beschreiben, was das System tut.
  4. Schwierige Tests zeigen Designprobleme.: Viele Abhängigkeiten oder ein unklarer Zweck werden beim Test sichtbar.
  5. Schulen sind Abwägung.: Classical und mockist haben beide Stärken. Das Team wählt nach Debugging-Kosten und Stil.
  6. Geschwindigkeit ist Teil der Technik.: Ein langsamer Test-Lauf macht TDD unpraktisch. Die Suite muss schnell bleiben.
