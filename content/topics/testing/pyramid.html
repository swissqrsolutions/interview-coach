Testpyramide und Teststrategie

Kern: Die Testpyramide ist ein Modell für die Verteilung von Tests: viele schnelle Unit-Tests, weniger Integrationstests, sehr wenige End-to-End-Tests. Sie löst das Problem langsamer, teurer und instabiler Testsuiten. Die Regel: Jeden Fehler auf der tiefsten Ebene testen, auf der er sichtbar wird.

1. Wo sitzt welcher Test?

  1. Unit-Test: prüft eine Klasse oder Funktion isoliert im Speicher. Beispiel: gebuehr(99.95) == 5.
  2. Integrationstest: prüft das Zusammenspiel mit einer echten Abhängigkeit. Beispiel: Repository gegen echtes PostgreSQL.
  3. End-to-End-Test (E2E): prüft einen Benutzerablauf durch das ganze System. Beispiel: Playwright klickt „Bestellen“ im Browser.
  4. Nach oben steigen Kosten, Laufzeit und Instabilität. Nach unten steigt die Präzision: Ein roter Unit-Test zeigt direkt die kaputte Zeile.
  5. Daneben gibt es Contract-Tests: Sie prüfen die Schnittstelle zwischen zwei Services ohne beide zu starten.

2. Die Reise eines Bugs durch die Teststufen

  1. Commit: Eine Entwicklerin baut einen Rundungsfehler in die Gebührenlogik ein.
  2. Static Analysis: Compiler und SonarQube finden Syntax- und Stilfehler. Den Logikfehler sehen sie nicht.
  3. Unit-Stufe: Der Test gebuehr(99.95) wird rot. Die Pipeline stoppt nach Sekunden. Die Fehlermeldung zeigt die Methode.
  4. Fehlt der Unit-Test, läuft der Bug weiter. Der Integrationstest prüft nur, ob die Bestellung gespeichert wird. Er bleibt grün.
  5. E2E-Stufe: Ein Browser-Test sieht vielleicht „5.00 CHF“ statt „0.00 CHF“. Die Analyse dauert lange: UI, API oder DB?
  6. Produktion: Findet ihn erst der Kunde, ist er am teuersten.
  7. Lehre: Für jeden Bug aus einer hohen Stufe schreibt man einen Test auf der tiefsten passenden Stufe. Fowler: „Push your tests as far down the test pyramid as you can.“

3. Beispiel: drei Stufen messen, ein Flaky Test entlarven

# levels.py (gekürzt): dieselbe Testsuite auf drei Stufen
def gebuehr(betrag_chf):                       # Geschäftslogik
    return 0 if betrag_chf >= 100 else 5

class UnitTest(TestCase):                       # reine Funktion
    def test_gratis_ab_100(self):   self.assertEqual(gebuehr(100), 0)
    def test_gebuehr_unter_100(self): self.assertEqual(gebuehr(99.95), 5)

class IntegrationTest(TestCase):                # echte DB (SQLite-Datei)
    def test_unique_constraint(self): ...       # zweimal 'A-1' → IntegrityError

class E2ETest(TestCase):                        # echter Server-Prozess + HTTP
    def test_server_antwortet(self): ...        # http.server starten, GET /, 200?
$ python -I levels.py
UnitTest         Tests=2  Fehler=0  Zeit=     0.2 ms
IntegrationTest  Tests=1  Fehler=0  Zeit=    21.5 ms
E2ETest          Tests=1  Fehler=0  Zeit=    75.5 ms

Echte Ausgabe, Python 3.12.10 (unittest, sqlite3, http.server).

# flaky.py: ein Hintergrund-Job braucht 5–15 ms
def test_mit_sleep():
    start_job(); time.sleep(0.010)              # feste Wartezeit
    return result == ["done"]
def test_mit_polling():
    start_job()
    while time.monotonic() < ende:              # auf die Bedingung warten
        if result == ["done"]: return True
        time.sleep(0.001)
$ python -I flaky.py
feste sleep(10 ms)   200 Läufe, 111 rot
Polling bis 1 s      200 Läufe, 0 rot
$ python -I flaky.py
feste sleep(10 ms)   200 Läufe, 102 rot
Polling bis 1 s      200 Läufe, 0 rot

Echte Ausgabe, Python 3.12.10. Zwei Läufe hintereinander, gleicher Code.

  1. Ein Unit-Test kostet hier etwa 0,1 ms. Der Integrationstest kostet rund 200-mal so viel, der E2E-Test rund 750-mal. Mit Browser, Docker und Netzwerk werden es Sekunden.
  2. Der Integrationstest findet einen Fehler, den kein Mock findet: den UNIQUE-Constraint der echten Datenbank.
  3. Der Sleep-Test ist flaky: gleicher Code, mal grün, mal rot. Die Rate schwankt zwischen den Läufen (111 vs 102).
  4. Die Lösung ist kein längerer Sleep. Die Lösung ist Warten auf eine Bedingung mit Timeout. In Java macht das Awaitility, in Playwright das Auto-Waiting.

4. Details, die Interviewer fragen

  1. Herkunft: Mike Cohn beschrieb die Pyramide in „Succeeding with Agile“ mit drei Schichten: Unit, Service, UI. Die Namen sind unwichtig. Wichtig sind zwei Regeln: Tests mit verschiedener Granularität schreiben, und je höher, desto weniger Tests.
  2. Was ist eine „Unit“? Zwei Schulen. Solitary (London-Schule): eine Klasse, alle Abhängigkeiten gemockt. Sociable (Klassik/Detroit): mehrere echte Klassen zusammen, nur langsame Grenzen (DB, Netzwerk) ersetzt. Sociable Tests brechen seltener beim Refactoring.
  3. Narrow vs Broad Integration: Ein narrow Integrationstest prüft genau eine Grenze, z. B. Repository gegen echte DB. Ein broad Integrationstest startet viele Teile und ruft Services über das Netzwerk. Narrow ist schneller und präziser.
  4. Testing Trophy: Kent C. Dodds' Modell mit vier Stufen: Static, Unit, Integration, E2E. Der Schwerpunkt liegt auf Integration: „Write tests. Not too many. Mostly integration.“ Grund: „The more your tests resemble the way your software is used, the more confidence they can give you.“
  5. Die Debatte Pyramide vs Trophy: Die Trophy stammt aus dem Frontend. Dort ist eine „Unit“ oft trivial, und das Zusammenspiel von Komponenten ist das Risiko. Die Pyramide stammt aus Backend-Systemen mit viel Logik. Beide sind sich einig: wenige E2E, und Tests sollen Verhalten prüfen, nicht Implementierung.
  6. Test Honeycomb: Für Microservices mit wenig Logik empfehlen manche viele Integrationstests pro Service und wenige isolierte Unit-Tests. Logik-arm heisst: Der Service ist vor allem Mapping zwischen HTTP, DB und Kafka.
  7. Ice-Cream-Cone (Anti-Pattern): Die umgekehrte Pyramide: viele manuelle und E2E-Tests, wenige Unit-Tests. Folge: lange Pipelines, viele Flaky Tests, späte Fehler.
  8. Contract-Tests: Consumer-Driven Contracts (z. B. Pact, Spring Cloud Contract): Der Consumer schreibt auf, was er braucht. Der Provider prüft das in seiner Pipeline. So ersetzt man viele broad E2E-Tests zwischen Services.
  9. Was teste ich wo?
    • Geschäftsregeln, Berechnungen, Randfälle (null, 0, Grenzwerte) → Unit.
    • SQL, Mapping, Transaktionen, Constraints, Serialisierung, Security-Konfiguration → Integration mit echter DB.
    • Schnittstellen zwischen Teams → Contract.
    • Wenige kritische Benutzerwege (Login, Bezahlen, Einreichen) → E2E.
  10. Flaky Test: Ein Flaky Test ist ein Test, der beim gleichen Code mal grün, mal rot ist. Häufige Ursachen: feste Sleeps, Zeit und Zeitzone, Reihenfolge der Tests, geteilter Zustand, Zufall ohne Seed, echte Netzwerkaufrufe, Parallelität.
  11. Reihenfolge: JUnit Jupiter läuft standardmässig sequenziell in einem Thread. Parallel läuft es erst mit junit.jupiter.execution.parallel.enabled=true. Dann werden versteckte Abhängigkeiten zwischen Tests sichtbar.
  12. Surefire vs Failsafe: Maven Surefire führt Unit-Tests in der Phase test aus (*Test.java, *Tests.java, Test*.java, *TestCase.java). Failsafe führt Integrationstests in integration-test und verify aus (*IT.java, IT*.java, *ITCase.java).
  13. Coverage: Code Coverage misst, welche Zeilen ein Test ausführt, nicht ob er etwas prüft. Ein Test ohne Assertion hat Coverage, aber keinen Wert. Mutation Testing (z. B. PIT) prüft die Tests selbst: Es ändert den Code und schaut, ob ein Test rot wird.

5. Vergleich

  • Unit: Millisekunden, sehr präzise, keine Infrastruktur. Findet keine Fehler zwischen Komponenten.
  • Integration (narrow): Sekunden, echte DB oder Broker, findet SQL- und Mapping-Fehler. Braucht Docker.
  • Contract: schnell, prüft Schnittstellen zwischen Teams. Braucht Disziplin und einen Broker für Verträge.
  • E2E: Minuten, höchstes Vertrauen pro Test, am instabilsten. Fehlerort schwer zu finden.
  • Pyramide: Schwerpunkt Unit. Passt zu Services mit viel Geschäftslogik.
  • Trophy: Schwerpunkt Integration, plus Static Analysis als Basis. Passt zu Frontends und dünnen Services.
  • Honeycomb: Schwerpunkt Integration pro Microservice, wenig isolierte Unit-Tests.

6. In der Produktion

  1. Pipeline dauert 45 Minuten: Zu viele E2E-Tests. Folge: Entwickler warten oder umgehen Tests. Lösung: E2E auf kritische Wege kürzen, Logik nach unten verschieben, Integrationstests parallelisieren.
  2. Flaky Tests zerstören Vertrauen: Das Team klickt „Rerun“, bis es grün ist. Echte Fehler gehen unter. Lösung: Flaky Tests messen, in Quarantäne verschieben, Ticket mit Owner, Ursache beheben. Rerun nur als Messung, nicht als Lösung.
  3. Alles gemockt, Produktion bricht: Unit-Tests grün, aber das echte SQL ist falsch. Lösung: Repository- und Mapping-Code gegen echte DB testen (Testcontainers), nicht gegen H2 oder Mocks.
  4. Tests brechen bei jedem Refactoring: Tests prüfen Implementierung (welche Methode wie oft gerufen wird). Lösung: Ergebnis und Verhalten prüfen, weniger verify.
  5. Geteilter Testzustand: Test A schreibt Daten, Test B erwartet eine leere Tabelle. Läuft B zuerst, ist alles grün. Lösung: Jeder Test baut seine Daten selbst auf und räumt auf, oder Transaktion mit Rollback.
  6. Zeitabhängige Tests: Ein Test bricht nur um Mitternacht oder bei Sommerzeit. Lösung: java.time.Clock injizieren und im Test fixieren.

7. Diagnose: Werkzeuge und Befehle

  • mvn test (nur Unit), mvn verify (Unit + Integration mit Failsafe).
  • mvn -Dtest=GebuehrTest#unter100 test: einen einzelnen Test ausführen.
  • -Dsurefire.rerunFailingTestsCount=2: zeigt Flaky Tests im Report als „flaky“. Nur zur Messung nutzen.
  • JUnit-Reports (target/surefire-reports/*.xml) im CI auswerten: Dauer pro Test, Fehlerrate über die Zeit.
  • @RepeatedTest(100): einen Verdacht auf Flakiness lokal reproduzieren.
  • junit.jupiter.execution.order.random.seed mit MethodOrderer.Random: Reihenfolge-Abhängigkeiten finden.
  • JaCoCo für Coverage, PIT für Mutation Testing, SonarQube als Quality Gate.
  • Awaitility (await().atMost(5, SECONDS).until(...)) statt Thread.sleep.

8. Senior-Punkte

  1. Die Form ist ein Ergebnis, kein Ziel. Ich frage: Wo ist das Risiko? Viel Logik → viele Unit-Tests. Viel Integration → viele Integrationstests.
  2. Tests sind Code mit Wartungskosten. Jeder Test muss sein Geld wert sein: Er findet echte Fehler und bricht nicht bei Refactoring.
  3. Feedback-Zeit ist ein Ziel. Unit-Stufe in Minuten. Integration parallel. E2E nach dem Merge oder nachts, wenn nötig.
  4. Flaky Tests sind Bugs mit Priorität. Sie sind manchmal echte Race Conditions im Produktionscode.
  5. Echte Abhängigkeiten statt Fakes für alles, was SQL oder Protokolle spricht. H2 ist nicht PostgreSQL.
  6. Coverage-Ziele sind ein schlechter Treiber. 80 % Coverage ohne gute Assertions sind wertlos. Ich nutze Coverage, um ungetestete Lücken zu finden, nicht als KPI.

10. Fallen

  • „Mehr E2E-Tests geben mehr Sicherheit.“ → Falsch. Ab einer gewissen Zahl bringen sie vor allem Laufzeit und Flakiness. Wenige kritische Wege reichen.
  • „100 % Coverage heisst fehlerfrei.“ → Falsch. Coverage misst ausgeführte Zeilen, nicht geprüfte Ergebnisse.
  • „Ein Flaky Test ist ein Testproblem.“ → Nicht immer. Oft zeigt er eine echte Race Condition.
  • „Unit-Test heisst: alles mocken.“ → Falsch. Sociable Unit-Tests mit echten Klassen sind gültig und robuster.
  • „H2 reicht als Test-DB.“ → Falsch. Dialekt, Constraints und Locking unterscheiden sich. Echte DB nutzen.
  • „Die Trophy widerlegt die Pyramide.“ → Falsch. Beide wollen wenige E2E und Tests, die Verhalten prüfen. Sie gewichten nur die Mitte anders.

11. Fragen

Was ist die Testpyramide?

Ein Modell für die Verteilung von Tests: viele Unit-Tests, weniger Integrationstests, sehr wenige E2E-Tests. Nach oben steigen Kosten, Laufzeit und Instabilität.

Woher kommt die Testpyramide?

Von Mike Cohn („Succeeding with Agile“), mit den Schichten Unit, Service und UI. Bekannt wurde sie durch Martin Fowler.

Was ist der Unterschied zwischen Unit- und Integrationstest?

Ein Unit-Test prüft eine Einheit isoliert im Speicher. Ein Integrationstest prüft das Zusammenspiel mit einer echten Abhängigkeit, z. B. einer Datenbank.

Was ist ein Solitary und was ein Sociable Unit-Test?

Solitary: eine Klasse, alle Abhängigkeiten gemockt. Sociable: mehrere echte Klassen zusammen, nur langsame Grenzen ersetzt. Sociable Tests überleben Refactoring besser.

Was ist die Testing Trophy?

Kent C. Dodds' Modell mit Static, Unit, Integration und E2E. Der Schwerpunkt liegt auf Integrationstests, weil sie der echten Nutzung näher sind.

Pyramide oder Trophy – was nutzen Sie?

Das hängt vom Risiko ab. Viel Geschäftslogik: Pyramide. Dünne Services und Frontends: mehr Integration. In beiden Fällen wenige E2E-Tests.

Was ist das Ice-Cream-Cone-Anti-Pattern?

Eine umgekehrte Pyramide mit vielen E2E- und manuellen Tests und wenigen Unit-Tests. Folge: langsame, instabile Pipelines und späte Fehler.

Was testen Sie auf Unit-Ebene?

Geschäftsregeln, Berechnungen, Validierung, Randfälle wie null, 0 und Grenzwerte.

Was testen Sie auf Integrationsebene?

SQL, Mapping, Transaktionen, Constraints, Serialisierung, Security-Konfiguration und Messaging, jeweils gegen echte Infrastruktur.

Was testen Sie mit E2E?

Nur wenige kritische Benutzerwege, z. B. Login, Antrag einreichen, Bezahlen. Den Rest decken tiefere Stufen ab.

Was sind Contract-Tests?

Tests der Schnittstelle zwischen Consumer und Provider. Der Consumer beschreibt seine Erwartung, der Provider prüft sie in seiner Pipeline. Beispiele: Pact, Spring Cloud Contract.

Was ist ein Flaky Test?

Ein Test, der beim gleichen Code mal grün, mal rot ist. Er zerstört das Vertrauen in die Pipeline.

Welche Ursachen haben Flaky Tests?

Feste Sleeps, Zeit und Zeitzone, Testreihenfolge, geteilter Zustand, Zufall ohne Seed, echte Netzwerkaufrufe und Parallelität.

Wie gehen Sie mit Flaky Tests um?

Messen, in Quarantäne verschieben, Ticket mit Owner, Ursache beheben. Automatisches Rerun nur zur Erkennung, nie als dauerhafte Lösung.

Warum ist Thread.sleep in Tests schlecht?

Die Wartezeit ist entweder zu kurz (flaky) oder zu lang (langsam). Besser auf eine Bedingung mit Timeout warten, z. B. mit Awaitility.

Was ist der Unterschied zwischen Surefire und Failsafe?

Surefire führt Unit-Tests in der Phase test aus. Failsafe führt Integrationstests in integration-test und verify aus. Dadurch läuft post-integration-test auch bei Fehlern.

Was sagt Code Coverage aus?

Welche Zeilen ein Test ausführt. Nicht, ob das Ergebnis geprüft wird. Gut zum Finden von Lücken, schlecht als Ziel.

Was ist Mutation Testing?

Ein Werkzeug (z. B. PIT) ändert den Code absichtlich. Bleibt jeder Test grün, sind die Tests schwach.

Warum nicht H2 statt der echten Datenbank?

H2 hat einen anderen SQL-Dialekt, andere Constraints und anderes Locking. Tests sind dann grün, Produktion bricht. Besser die echte DB in Docker.

Wie machen Sie zeitabhängigen Code testbar?

Mit einer injizierten java.time.Clock. Im Test ist die Zeit fest, z. B. Clock.fixed(...).

Wie lang darf eine Pipeline dauern?

Unit-Feedback sollte in wenigen Minuten da sein. Langsame Stufen laufen parallel oder später, z. B. nach dem Merge.

Szenario: Die Pipeline braucht 40 Minuten, und das Team umgeht die Tests. Was tun Sie?

Messen, wo die Zeit hingeht. Meist zu viele E2E-Tests. Logik nach unten verschieben, E2E auf kritische Wege kürzen, Integrationstests parallelisieren und Stufen trennen.

Szenario: Alle Unit-Tests sind grün, aber in Produktion schlägt ein SQL-Statement fehl. Was ändern Sie?

Das Repository war gemockt. Ich ergänze Integrationstests gegen die echte Datenbank mit Testcontainers und prüfe das echte SQL samt Constraints.

Szenario: Ein Test ist etwa jedes zehnte Mal rot. Wie gehen Sie vor?

Lokal mit @RepeatedTest oder in einer Schleife reproduzieren. Nach Sleeps, Zeit, Reihenfolge und geteiltem Zustand suchen. Bis zur Behebung in Quarantäne mit Ticket.
