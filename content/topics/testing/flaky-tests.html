Flaky Tests

Kern: Ein flaky Test besteht oder scheitert ohne Änderung an Code, Test oder Umgebung. Seine Fehler sind Rauschen, und das Team beginnt, rote Läufe zu ignorieren. Die Ursachen sind meist geteilter Zustand, falsches Warten, externe Dienste, Zeit oder Ressourcen.

Antwort-Muster

Frage: Wie gehen Sie mit flaky Tests um?

  1. Mechanismus: Ich reproduziere den Fehler mit vielen Läufen. Ich ordne die Ursache einer von fünf Gruppen zu und behebe sie. Ein Retry ist nur das Pflaster.
  2. Zahl: Playwright und Cypress wiederholen standardmässig nichts. Awaitility wartet standardmässig bis 10 Sekunden und fragt alle 100 Millisekunden.
  3. Trade-off: Retries halten die Pipeline grün, verstecken aber Fehler. Quarantäne schützt die gesunden Tests, braucht aber eine Frist.
  4. Produktion: Ich zähle flaky Tests pro Woche im Report. Flaky Tests bekommen einen Besitzer und eine Frist.

1. Einen flaky Test in 7 Schritten einkreisen

  1. Reproduzieren: Man lässt den Test viele Male laufen. Erst wenn er in einer Schleife manchmal scheitert, kann man die Ursache beweisen.
  2. Ursache einordnen: Fowler nennt fünf Gruppen. Das sind fehlende Isolation, asynchrones Verhalten, externe Dienste, Zeit und Ressourcen-Lecks.
  3. Fehlerlauf lesen: Man liest Log, Trace und Zeitpunkt des fehlgeschlagenen Laufs. Man sieht, was anders war als im grünen Lauf.
  4. Isolieren: Man lässt den Test allein laufen und danach in anderer Reihenfolge. So erkennt man geteilten Zustand.
  5. Ursache beheben: Auf eine Bedingung warten statt schlafen. Die Uhr ersetzen. Eigene Daten je Test anlegen. Externe Dienste durch Doubles ersetzen.
  6. Quarantäne: Ein Test, der nicht sofort behoben wird, kommt in eine eigene Suite. Er bekommt eine Frist.
  7. Gegenprobe: Man lässt den Test wieder viele Male laufen. Erst keine Fehler in vielen Läufen zählen als behoben.

Die Demo unten zeigt Schritt 1 und Schritt 5 mit echter Ausgabe.

2. Aufbau

  1. Isolation: Tests teilen Zustand wie Datenbankzeilen, Singletons oder statische Daten. Ein Test beschädigt den nächsten.
  2. Asynchronität: Der Test rät, wie lange etwas dauert. Mal reicht die Zeit, mal nicht.
  3. Externe Dienste: Echte oder instabile Systeme liefern wechselnde Antworten.
  4. Zeit: Der Code liest die Systemuhr. Das Ergebnis hängt vom Zeitpunkt des Laufs ab.
  5. Ressourcen: Ein Leck macht Tests rot, die zufällig an die Grenze stossen.
  6. Messung: Report und Flaky-Zähler zeigen, wie oft ein Test schwankt.

3. Details

  1. Schaden: Ein flaky Test erzeugt Rauschen. Fowlers Beispiel ist eine Suite mit 100 Tests und 10 flaky Tests. Sie ist oft rot. Dann prüft niemand mehr, ob ein Fehler echt ist.
  2. Isolation: Geteilter Zustand sind Datenbankzeilen, Singletons, statische Daten oder der aktuelle Benutzer. Jeder Test baut seinen Startzustand neu auf oder räumt auf. Ein Transaktions-Rollback am Ende ist eine einfache Lösung. Fehler beim Aufräumen müssen laut sein.
  3. Asynchronität: Feste Sleeps sind zu lang oder zu kurz. Besser sind Callbacks. Gibt es keine, fragt man in kurzem Abstand und mit grosszügigem Gesamt-Timeout. Bei Ablauf wirft man eine klare Timeout-Exception. Die Zeiten stehen an einer zentralen Stelle.
  4. Externe Dienste: Echte Dienste liefern wechselnde Antworten. Für deterministische Tests nimmt man Doubles, etwa selbst-initialisierende Fakes. Contract Tests laufen getrennt und regelmässig. Sie prüfen, ob die Doubles noch zum echten System passen.
  5. Zeit: Direkte Aufrufe der Uhr ändern sich von Lauf zu Lauf. Man kapselt die Systemuhr und setzt im Test einen Stub mit fester Zeit. Man testet auch um Mitternacht und zum Monatsende.
  6. Ressourcen-Lecks: Ein Leck trifft den Test, der gerade die Grenze überschreitet. Das wirkt zufällig. Man verwaltet Ressourcen über einen Pool. Mit Poolgrösse 1 scheitert der erste leckende Test sichtbar.
  7. Quarantäne: Man verschiebt nicht-deterministische Tests in einen eigenen Bereich. So geben gesunde Tests klares Feedback. Die Quarantäne darf kein Friedhof werden. Fowlers Beispiele sind höchstens 8 Tests oder höchstens eine Woche.
  8. Retries und Zähler: Playwright wiederholt standardmässig nicht. Besteht ein Test erst im Retry, heisst er flaky. Cypress hat standardmässig 0 Retries und zeigt in Cypress Cloud ein Flaky-Badge. Surefire zählt mit rerunFailingTestsCount «Flakes». Mit failOnFlakeCount kann der Build bei zu vielen scheitern.
  9. Awaitility: Standard-Timeout ist 10 Sekunden. Poll-Intervall und Poll-Delay sind 100 Millisekunden. untilAsserted wiederholt eine Assertion. Bei Ablauf kommt eine ConditionTimeoutException mit klarer Meldung.
  10. JUnit: Parallele Ausführung ist standardmässig aus (junit.jupiter.execution.parallel.enabled). @ResourceLock schützt gemeinsame Ressourcen. @Isolated lässt eine Klasse allein laufen. Die Standard-Reihenfolge ist deterministisch, aber absichtlich nicht offensichtlich.
  11. Zufällige Reihenfolge: MethodOrderer.Random mischt die Testmethoden. So findet man versteckte Abhängigkeiten. Wahre Unit-Tests sollten nicht von der Reihenfolge abhängen.
  12. Echter Fehler: Manchmal ist nicht der Test schuld. Eine Race Condition im Code zeigt sich als flaky Test. Deshalb gilt: erst die Ursache verstehen und dann entscheiden.

4. Fallen

  • „Ein Retry behebt flaky Tests.“ → Falsch. Er verdeckt sie. Die Suite wird grün, die Ursache bleibt. Man verfolgt die als flaky markierten Tests und behebt sie.
  • „Ein längerer sleep() macht den Test stabil.“ → Falsch. Er ist immer noch geraten. Besser wartet man auf eine Bedingung mit Timeout.
  • „Flaky heisst immer, der Test ist schlecht.“ → Falsch. Auch der Code kann eine Race Condition haben. Der flaky Test ist dann das einzige Anzeichen.
  • „JUnit führt Tests in der Reihenfolge der Datei aus.“ → Falsch. Die Reihenfolge ist deterministisch, aber nicht offensichtlich. Tests dürfen nicht davon abhängen.
  • „Quarantäne löst das Problem.“ → Falsch. Sie schützt nur die gesunden Tests. Ohne Frist wird sie zum Friedhof.
  • „Ein Test, der meistens grün ist, ist harmlos.“ → Falsch. Schon wenige flaky Tests lassen Teams rote Läufe ignorieren. Dann geht auch ein echter Fehler unter.

5. Selbsttest

Warum?

Warum sind flaky Tests schädlich?

Sie erzeugen Rauschen. Das Team lernt, rote Läufe zu ignorieren, und echte Fehler gehen unter. Zusätzlich kosten sie CI-Zeit.

Warum ist ein fester Sleep falsch?

Die Dauer ist geraten. Auf langsamen Rechnern ist sie zu kurz, auf schnellen verschwendet sie Zeit. Man wartet auf einen Zustand.

Warum sind Retries gefährlich?

Sie verbergen die Ursache und lassen den Fehler im Code. Zudem nehmen sie dem Team das Gefühl für den Zustand der Suite.

Wie innen?

Welche fünf Ursachen nennt Fowler?

Fehlende Isolation, asynchrones Verhalten, externe Dienste, Zeit und Ressourcen-Lecks.

Wie behebt man asynchrone Flakiness?

Mit Callbacks oder mit Polling in kurzem Abstand und grosszügigem Timeout. Bei Ablauf gibt es eine klare Exception.

Wie behebt man fehlende Isolation?

Jeder Test baut seinen Zustand neu auf oder räumt auf. Man teilt keine Singletons oder Zeilen. Ein Rollback am Testende hilft.

Wie behebt man Zeitprobleme?

Man kapselt die Systemuhr. Im Test setzt man eine feste Zeit. Man testet auch um Mitternacht und am Monatsende.

Wie arbeitet das Rerun von Surefire?

rerunFailingTestsCount wiederholt fehlgeschlagene Tests. Besteht ein Test erst später, zählt er als Flake und der Build bleibt grün.

Zahlen

Wie lang wartet Awaitility standardmässig?

10 Sekunden. Das Poll-Intervall ist 100 Millisekunden.

Wie viele Retries gibt es standardmässig in Playwright und Cypress?

Keine. Beide wiederholen nur, wenn man es einschaltet.

Wie gross darf eine Quarantäne sein?

Fowlers Beispiele sind 8 Tests oder eine Woche. Eine feste Zahl gibt es nicht, aber eine Grenze und Frist braucht es.

Was zeigt die Demo?

Ein Test mit Sleep scheiterte in 101 von 200 Läufen. Mit Warten auf ein Event scheiterte er in 0 von 200.

Vergleich

Retry oder Fix?

Ein Retry hält die Pipeline grün und verdeckt die Ursache. Ein Fix beseitigt sie. Retries sind eine Übergangslösung mit Zähler.

Quarantäne oder löschen?

Quarantäne schützt gesunde Tests und hält den Test am Leben. Wird er nie behoben, löscht man ihn besser, statt ihn zu pflegen.

Polling oder Callback?

Ein Callback meldet das Ende genau. Polling fragt in Abständen und braucht ein Timeout. Ein Callback ist besser, wenn es einen gibt.

Fake oder echter Dienst?

Ein Fake ist deterministisch und schnell, kann aber abweichen. Der echte Dienst ist realistisch, aber instabil. Contract Tests verbinden beide.

Produktion

Wie misst man Flakiness?

Mit dem Report. Playwright markiert Tests, die erst im Retry bestanden. Surefire zeigt «Flakes». Cypress Cloud zeigt eine Flaky Rate.

Szenario: Die CI ist jeden dritten Lauf rot, lokal ist alles grün. Was tun Sie?

Fehlerläufe sammeln und vergleichen. Auf Zeit, Reihenfolge, parallele Tests und langsamere Rechner prüfen. Verdächtige Tests in einer Schleife laufen lassen.

Szenario: Ein Test scheitert nur, wenn die ganze Suite läuft. Warum?

Wahrscheinlich teilt er Zustand mit einem anderen Test. Mit zufälliger Reihenfolge und Einzellauf findet man den Partner. Dann bekommt jeder Test eigene Daten.

Szenario: Ein Kafka-Test wartet mit Thread.sleep(2000) und scheitert manchmal. Was tun Sie?

Das Sleep durch Awaitility ersetzen. Auf den erwarteten Zustand warten, mit klarem Timeout. Dann sind schnelle Läufe schneller und langsame sicher.

Wie verhindert man, dass die Zahl flaky Tests wächst?

Mit einem Zähler im Report und einer Grenze für die Quarantäne. Dazu gilt eine Regel. Ein neuer flaky Test wird sofort behoben oder in Quarantäne geschoben.

Design

Wie baut man Tests deterministisch?

Jeder Test hat eigene Daten. Die Uhr ist eine Abhängigkeit. Externe Dienste ersetzt man durch Doubles. Man wartet auf Zustand und nicht auf Zeit.

Wie setzt man Awaitility ein?

await().atMost(5, SECONDS).untilAsserted(...) für eine Assertion. Der Timeout steht im Test, und bei Ablauf kommt eine ConditionTimeoutException.

Szenario: Das Team will Tests parallel laufen lassen. Was beachten Sie?

Parallelität ist in JUnit standardmässig aus. Tests müssen unabhängig sein. Gemeinsame Ressourcen schützt man mit @ResourceLock. Einzelne Klassen können mit @Isolated allein laufen.

Szenario: Ein neuer flaky Test blockiert den Release. Wie entscheiden Sie?

Erst prüfen, ob ein echter Fehler im Code steckt. Wenn nicht, den Test in Quarantäne legen und mit Frist und Besitzer beheben. Die Pipeline darf nicht ohne Grund rot bleiben.

Mehr

Gerüst

  • Warum? Der Test soll Fehler anzeigen und nicht würfeln. Vertrauen in die Suite ist das Ziel.
  • Wie innen? Fünf Ursachen: Isolation, Async, Remote, Zeit, Leaks. Jede hat einen Fix.
  • Zahlen Awaitility 10 s und 100 ms. Retries standardmässig 0. Demo: 101 von 200 gegen 0 von 200.
  • Vergleich Retry gegen Fix. Quarantäne gegen Löschen. Polling gegen Callback.
  • Produktion CI rot jeden dritten Lauf. Test hängt von Reihenfolge ab. Sleep in Kafka-Tests.
  • Design Eigene Daten, Uhr als Abhängigkeit, Warten auf Zustand, Zähler im Report.

Beispiel: Sleep gegen Warten, und geteilter Zustand

class Job:                        # Ergebnis kommt nach 10 bis 60 ms
    def start(self): ...          # Hintergrund-Thread, setzt result und done-Event

def sleep_test():                 # geraten
    j = Job(); j.start(); time.sleep(0.035)
    return j.result == "ok"
def wait_test():                  # wartet auf die Bedingung, Timeout 2 s
    j = Job(); j.start()
    return j.done.wait(timeout=2) and j.result == "ok"

cart = []                         # gemeinsamer Zustand
def test_add():   cart.append("a"); return cart == ["a"]
def test_empty(): return cart == []
fixed sleep(0.035): 101/200 runs failed
wait for event    : 0/200 runs failed
shared state, order add->empty: [True, False]
shared state, order empty->add: [True, True]

Echte Ausgabe, Python 3.12.10 (threading, time). Der Code oben ist gekürzt. Die genaue Fehlerzahl schwankt je Lauf, weil die Dauer zufällig ist.

  1. Sleep: Der Test rät 35 Millisekunden. Die Arbeit dauert 10 bis 60. Er scheitert etwa in jedem zweiten Lauf.
  2. Warten: Der Test wartet auf das Event. In 200 Läufen gab es keinen Fehler.
  3. Reihenfolge 1: Erst add, dann empty. Der zweite Test scheitert, weil die Liste noch gefüllt ist.
  4. Reihenfolge 2: Erst empty, dann add. Beide bestehen. Dieselben Tests, anderes Ergebnis.

Vergleich

  • Fixer Sleep: Geraten. Zu kurz ist flaky, zu lang ist langsam.
  • Warten auf Bedingung: Wartet genau so lang wie nötig. Mit Timeout und klarer Meldung.
  • Retry: Wiederholt den Test. Verdeckt die Ursache, zeigt aber den Flaky-Zähler.
  • Quarantäne: Eigene Suite für kranke Tests, mit Grenze und Frist.
  • Zufällige Reihenfolge: Deckt versteckte Abhängigkeiten zwischen Tests auf.
  • Doubles für externe Dienste: Machen Tests deterministisch. Contract Tests halten sie ehrlich.

Produktion

  1. CI-Pipeline unzuverlässig: Jeder dritte Lauf ist rot. Lösung: Fehlerläufe vergleichen und die häufigsten Verursacher zuerst beheben.
  2. Test hängt von Reihenfolge ab: Geteilter Zustand. Lösung: zufällige Reihenfolge einschalten und je Test eigene Daten nutzen.
  3. Langsame CI-Rechner: Zeitgrenzen sind zu knapp. Lösung: auf Bedingungen warten und nicht auf feste Zeiten.
  4. Externe Dienste in Tests: Ausfall des Partners macht Tests rot. Lösung: Doubles plus Contract Tests.
  5. Retries ohne Zähler: Niemand sieht, wie viele Tests schwanken. Lösung: Flaky-Zähler im Report und eine Obergrenze.
  6. Quarantäne als Friedhof: Die Tests bleiben ewig dort. Lösung: Grenze, Besitzer und Frist, danach beheben oder löschen.

Diagnose: Werkzeuge und Befehle

  • Schleife: Den verdächtigen Test 100 bis 200 Mal laufen lassen und die Fehlerquote zählen.
  • Reihenfolge: Test allein ausführen und danach mit MethodOrderer.Random in zufälliger Reihenfolge.
  • Trace: Bei Playwright den Trace des ersten Retrys öffnen. Er zeigt Aktionen, DOM und Netzwerk.
  • Surefire-Zusammenfassung: Die Zeile mit Flakes: zeigt, wie viele Tests erst im Rerun bestanden. Dafür -Dsurefire.rerunFailingTestsCount=2 setzen.
  • Awaitility-Meldung: Die ConditionTimeoutException nennt, welche Bedingung nicht erfüllt wurde.

Senior-Punkte

  1. Flaky ist eine Qualitätsmetrik.: Wer die Quote misst, kann sie senken. Wer sie nicht misst, gewöhnt sich daran.
  2. Eine rote Pipeline muss etwas bedeuten.: Sobald ein Team Rot ignoriert, ist die Pipeline wertlos.
  3. Ursache vor Pflaster.: Retries und Quarantäne kaufen Zeit. Sie ersetzen den Fix nicht.
  4. Determinismus ist Design.: Die Uhr, Zufall und externe Dienste als Abhängigkeiten machen Code testbar.
  5. Nicht jeder flaky Test ist ein Testfehler.: Eine Race Condition im Produktivcode zeigt sich oft zuerst im Test.
  6. Besitzer und Frist.: Ein flaky Test ohne Besitzer wird nie behoben.
