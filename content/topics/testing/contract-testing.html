Contract Testing

Kern: Ein Contract Test prüft die Schnittstelle zwischen Consumer und Provider, ohne beide zu starten. Der Vertrag besteht aus Beispielen für Request und Antwort. Der Provider besteht, wenn seine Antwort mindestens die erwarteten Daten enthält.

Antwort-Muster

Frage: Wie funktioniert ein Contract Test im Detail, und wie verhindert er kaputte Deployments?

  1. Mechanismus: Der Consumer-Test läuft gegen einen Mock-Provider und schreibt eine Pact-Datei. Der Provider spielt jede Anfrage nach, setzt Provider States und vergleicht lose.
  2. Zahl: Der Broker beantwortet can-i-deploy mit Exit-Code 0 oder 1. Die Pact-Spezifikation kennt v1, v1.1, v2, v3 und v4.
  3. Trade-off: Lose Prüfung heisst, der Provider darf Felder hinzufügen. Dafür prüft der Vertrag nur Form und Typ und nicht die Fachlogik.
  4. Produktion: Ich nehme die Git-SHA als Version, aktiviere Pending Pacts und melde jedes Deployment an den Broker.

1. Eine Vertragsänderung in 7 Schritten

  1. Consumer-Test: Der Consumer beschreibt Request und minimale Antwort an einem Mock-Provider. Sein echter Code ruft den Mock. Matcher wie like, term und each_like lockern die Antwort.
  2. Pact-Datei: Besteht der Test, schreibt Pact eine Datei mit jeder Interaction. Die Spezifikations-Version steht unter metadata.pactSpecification.version.
  3. Publish: Die Pipeline veröffentlicht die Datei am Broker. Als Version nimmt man die Git-SHA. Der Branch gehört dazu.
  4. Verifikation: Der Provider holt die Verträge nach Selektoren wie mainBranch oder deployedOrReleased. Pact sendet jede Anfrage an den echten Provider. Ein Provider State richtet vorher die Daten ein.
  5. Ergebnis: Das Ergebnis geht an den Broker. Mit enablePending bricht eine neue, noch nicht unterstützte Erwartung den Provider-Build nicht.
  6. can-i-deploy: Die Pipeline fragt die Matrix. Sie prüft, ob zwischen meiner Version und den Versionen in der Zielumgebung eine erfolgreiche Verifikation existiert.
  7. record-deployment: Nach dem Deployment meldet man Version und Umgebung. Sonst weiss der Broker nicht, was wo läuft.

Spring Cloud Contract dreht die Richtung. Der Vertrag liegt beim Producer. Daraus entstehen Tests und Stubs. Siehe Details 11 und 12.

2. Aufbau

  1. Consumer-Test: Läuft gegen einen Mock-Provider. Er prüft, dass der Consumer die Antwort versteht.
  2. Pact-Datei: Beschreibt jede Interaction. Sie ist ein Vertrag aus Beispielen und kein statisches Schema.
  3. Provider-Verifikation: Spielt die Anfragen gegen den echten Provider ab und vergleicht mit der minimalen Antwort.
  4. Provider State: Ein benannter Zustand der Provider-Daten, den der Consumer mit given nennt.
  5. Broker: Speichert Verträge und Ergebnisse je Version. Er führt die Matrix und beantwortet can-i-deploy.
  6. Spring Cloud Contract: Vertrag in Groovy oder YAML beim Producer. Erzeugte Tests prüfen ihn. Ein Stubs-Artefakt bedient die Consumer.

3. Details

  1. Matcher beim Consumer: Für Requests nimmt man exakte Werte. like prüft beim Provider nur den Typ. term koppelt ein Beispiel mit einem regulären Ausdruck. each_like verlangt je Element die gleiche Form und mindestens ein Element. Die Namen sind je Sprache leicht anders.
  2. Lose beim Provider: Der Provider ignoriert unerwartete Felder im JSON der Antwort. Andere Consumer dürfen sie nutzen. Das ist das Prinzip «streng beim Senden, locker beim Empfangen». Antworten sollte man so lose wie möglich beschreiben.
  3. Query-Strings: Ein String als Query ist ein exakter Vergleich. Ein Hash erlaubt Parameter in jeder Reihenfolge, und Werte können Matcher haben. Request-Bodies und Queries erlauben keine unerwarteten Werte. Zusätzliche Header sind erlaubt.
  4. Provider States: Ein State beschreibt Voraussetzungen des Providers, ähnlich wie Given in Cucumber. Der Consumer nennt ihn in given. Der Provider legt dafür Daten an oder stellt Fehlerfälle wie ein 500 ein. Jede Interaction wird für sich geprüft und darf nicht von einer früheren abhängen.
  5. Pact-Spezifikation: Es gibt v1, v1.1, v2, v3 und v4. Ein Provider kann Verträge älterer Versionen prüfen. Ein Wechsel der Version kann am Broker das Event contract_content_changed auslösen. Die Matcher-Regeln können sich ändern.
  6. Versionen: Die Doku empfiehlt die Git-SHA, einen Git-Tag oder eine Semver mit SHA wie 1.2.456+405b31ec6. Bei von Hand erhöhten Versionen überschreiben sich Verträge verschiedener Branches. Build-Nummern starten bei einem CI-Wechsel neu. Eine Version liegt auf genau einem Branch.
  7. Pending Pacts: Ein Pact ist pending, bis auf einem Branch die erste erfolgreiche Verifikation veröffentlicht wurde. Fehler in einem pending Pact lassen den Provider-Build nicht scheitern. Die Ergebnisse gehen trotzdem an den Broker. Der Consumer sieht, dass er noch nicht deployen kann. Man setzt enablePending und konfiguriert den Provider-Branch.
  8. WIP und Selektoren: WIP-Pacts sind immer pending. Der Provider wählt Verträge mit Selektoren wie { mainBranch: true } oder { deployedOrReleased: true }. So prüft er das, was in Produktion läuft, und den Hauptzweig.
  9. can-i-deploy: Die Argumente sind --pacticipant, --version und --to-environment. Die Matrix zeigt Paare von Consumer- und Provider-Version mit Ergebnis. Ohne Ziel vergleicht es mit der neuesten Version jeder integrierten App. Mit record-deployment trägt man Umgebungen ein, auch Vorproduktion.
  10. Grenzen: Verträge sind keine Funktionstests des Providers. Sie sollen Nachrichten prüfen und nicht Verhalten. Der Erfolg darf nicht von konkreten Daten abhängen. Pact kennt Queue-Technologien nicht. Dafür bleiben normale Tests.
  11. Spring Cloud Contract: Producer: Der Producer legt Verträge in Groovy-DSL oder YAML ab. Standardordner ist src/test/resources/contracts. Das Maven-Plugin erzeugt daraus Tests. Am Anfang scheitern sie. Alle erben von einer Basisklasse (baseClassForTests). Danach liegen App und Stubs im lokalen Repository.
  12. Spring Cloud Contract: Consumer: Der Consumer nutzt Stub Runner mit @AutoConfigureStubRunner(ids = ..., stubsMode = LOCAL). REMOTE lädt die Stubs aus einem Online-Repository. Messaging braucht @AutoConfigureMessageVerifier an der Basisklasse.

4. Fallen

  • „Pact prüft, dass die Antwort genau gleich ist.“ → Falsch. Der Provider besteht, wenn die Antwort mindestens die erwarteten Daten enthält. Zusätzliche Felder sind erlaubt.
  • „Ein Contract Test ersetzt die Provider-Tests.“ → Falsch. Er prüft nur die Form der Schnittstelle. Fachlogik und Daten prüfen Unit- und Integrationstests.
  • „Pending Pacts verstecken Fehler.“ → Falsch. Die Ergebnisse gehen an den Broker. Der Provider-Build bleibt grün, aber der Consumer sieht, dass er noch nicht deployen darf.
  • „Als Version nimmt man eine Nummer von Hand.“ → Falsch. Verträge verschiedener Branches überschreiben sich. Besser ist die Git-SHA.
  • „Ein Provider State setzt Zustand beim Consumer.“ → Falsch. Er beschreibt den Zustand des Providers. Der Consumer benennt ihn nur.
  • „Pact und Spring Cloud Contract sind gleich.“ → Falsch. Bei Pact schreibt der Consumer die Beispiele. Bei Spring Cloud Contract liegt der Vertrag meist beim Producer und erzeugt dort Tests.

5. Selbsttest

Warum?

Warum nutzt man like statt exakter Werte in Antworten?

Der Consumer braucht den Typ und nicht den Wert. Exakte Werte machen den Provider-Test brüchig, sobald sich Daten ändern.

Warum gibt es Pending Pacts?

Eine neue Consumer-Erwartung würde sonst den Provider-Build brechen, obwohl nichts deployt ist. Pending trennt «noch nicht unterstützt» von «kaputt gegangen».

Warum die Git-SHA als Version?

Sie ist eindeutig und zeigt auf einen Commit. Von Hand erhöhte Nummern überschreiben Verträge verschiedener Branches.

Wie innen?

Wie läuft die Provider-Verifikation ab?

Pact holt die Verträge. Je Interaction setzt es den Provider State und sendet die Anfrage an den echten Provider. Dann vergleicht es die Antwort lose.

Wie arbeiten Provider States?

Der Consumer nennt einen Namen mit given. Der Provider hat dafür einen Setup-Code, der Daten anlegt oder Stubs setzt.

Was steht in einer Pact-Datei?

Jede Interaction mit Request und minimaler Antwort. Die Spezifikations-Version steht unter metadata.pactSpecification.version.

Wie entsteht ein Test in Spring Cloud Contract?

Das Maven-Plugin liest die Verträge und erzeugt Testklassen. Sie erben von der Basisklasse (baseClassForTests).

Wie nutzt der Consumer die Stubs?

Mit Stub Runner und @AutoConfigureStubRunner. Er nennt die ids und den stubsMode.

Zahlen

Was bedeuten die Exit-Codes von can-i-deploy?

0 heisst, die Version ist sicher auszurollen. 1 heisst, sie ist es nicht.

Welche Pact-Spezifikations-Versionen gibt es?

v1, v1.1, v2, v3 und v4.

Wo liegen Verträge bei Spring Cloud Contract standardmässig?

In src/test/resources/contracts (Eigenschaft contractsDslDir).

Vergleich

Pact oder Spring Cloud Contract?

Pact ist consumer-driven, sprachübergreifend und hat einen Broker. Spring Cloud Contract ist Spring-nah, der Vertrag liegt beim Producer, und es erzeugt Tests und Stubs.

Consumer-driven oder provider-driven?

Consumer-driven: Der Consumer schreibt auf, was er nutzt. Provider-driven: Der Provider legt den Vertrag fest und die Consumer richten sich danach.

Contract Test oder OpenAPI-Schema?

Ein Schema beschreibt alles, was möglich ist. Pact prüft nur, was Consumer nutzen, anhand von Beispielen.

Pending oder WIP?

Pending gilt für Pacts ohne erfolgreiche Verifikation auf dem Branch. WIP-Pacts sind immer pending.

Tags oder Environments im Broker?

Neuere Broker haben Environments mit record-deployment. Ältere Broker nutzen Tags.

Produktion

Wie geht man mit einem Provider-Build um, der wegen eines neuen Consumer-Pacts rot wird?

Mit enablePending. Der Pact bleibt pending, bis die erste Verifikation erfolgreich war. Der Provider-Build bleibt grün.

Szenario: Die Verifikation läuft lokal grün und in der CI rot. Was prüfen Sie?

Den Provider State. Oft fehlen in der CI Testdaten, oder der State läuft nicht. Lösung: den State im Provider-Test sauber einrichten.

Szenario: can-i-deploy sagt «unknown». Warum?

Es gibt noch keine Verifikation für diese Version. Die Provider-Pipeline wurde noch nicht fertig. Lösung: auf das Ergebnis warten (Polling).

Szenario: Der Provider will ein Feld umbenennen. Wie vermeiden Sie einen Bruch?

Erst das neue Feld zusätzlich anbieten. Warten, bis alle Consumer umgestellt und verifiziert sind. Dann das alte Feld entfernen.

Design

Wie fein sollen Verträge sein?

So fein wie die Nutzung. Pro Consumer nur die Felder, die er liest, mit Typ-Matchern. Keine Fachlogik und keine konkreten Daten.

Wie testet man Messaging-Verträge?

Bei Spring Cloud Contract mit dem Messaging-Teil und @AutoConfigureMessageVerifier. Bei Pact beschreibt der Vertrag die Nachricht. Die Queue-Technik prüft Pact nicht.

Szenario: Ein Consumer braucht ein neues Feld. Wie läuft das ab?

Der Consumer ergänzt die Erwartung und veröffentlicht den Pact. Der Provider-Build ist durch Pending grün. Der Provider baut das Feld ein. Die Verifikation klärt, dass der Consumer deployen darf.

Wie wählt man die Version in der CI?

Die Git-SHA des Commits. Dazu den Branch am Broker melden. Man ruft can-i-deploy mit dieser Version auf.

Mehr

Gerüst

  • Warum? Kaputte Schnittstellen vor dem Deployment finden, ohne alle Services zu starten.
  • Wie innen? Consumer-Test, Pact-Datei, Replay, Provider States, lose Prüfung, Broker-Matrix.
  • Zahlen Exit-Code 0 oder 1. Spezifikation v1 bis v4. Standardordner src/test/resources/contracts.
  • Vergleich Pact gegen Spring Cloud Contract. Consumer-driven gegen provider-driven. Beispiele gegen Schema.
  • Produktion Rot in der CI wegen Provider States. Neue Erwartung bricht den Build. can-i-deploy unknown.
  • Design Git-SHA als Version. Pending einschalten. Deployments melden. Felder erst ergänzen, dann entfernen.

Beispiel: Die Regeln der Verifikation, nachgebaut

# Vertrag (vom Consumer geschrieben)
body     = {"id": 7, "status": "PAID", "items": [{"sku": "A1", "qty": 2}]}
matchers = {"id": "type",
            "status": "regex:^(NEW|PAID|SHIPPED)$",
            "items": "eachLike", "items[]": {"sku": "type", "qty": "type"}}

# Provider v1 fügt Felder hinzu.        -> PASS
# Provider v2 benennt status um.        -> FAIL
# Provider v3: id als String, items leer -> FAIL
provider v1 (adds fields): PASS
provider v2 (renames status): FAIL $.status: missing
provider v3 (id as string, no items): FAIL $.id: type str != int; $.items: array is empty

Echte Ausgabe, Python 3.12.10. Das ist ein eigenes Mini-Skript, das die Regeln von Pact nachbaut, und kein Pact. Es zeigt die Idee: Typ-Matcher, Regex, Array mit mindestens einem Element und ignorierte Zusatzfelder.

  1. v1: Neue Felder wie price und note stören nicht. Der Provider besteht.
  2. v2: Das Feld status fehlt. Der Consumer liest es. Die Verifikation scheitert.
  3. v3: Ein String statt einer Zahl bricht den Typ-Matcher. Ein leeres Array bricht eachLike.
  4. Folge: Der Fehler zeigt genau, welcher Pfad bricht. Das ist der Vorteil gegenüber einem langen E2E-Test.

Vergleich

  • Pact: Consumer schreibt Beispiele. Broker mit Matrix, Pending und can-i-deploy. Viele Sprachen.
  • Spring Cloud Contract: Vertrag in Groovy oder YAML beim Producer. Erzeugte Tests und Stubs. Stub Runner für Consumer.
  • OpenAPI-Schema: Beschreibt die ganze API. Es zeigt nicht, was Consumer wirklich nutzen.
  • Integrationstest: Startet echte Abhängigkeiten. Realistisch, aber langsamer und breiter.
  • E2E-Test: Prüft den ganzen Weg. Ein Contract Test ersetzt viele, aber nicht alle.
  • Mock im Consumer-Test: Allein beweist er nichts. Erst die Provider-Verifikation schliesst die Lücke.

Produktion

  1. Verifikation rot nur in der CI: Provider States laufen dort nicht oder Testdaten fehlen. Lösung: States im Provider-Test sauber einrichten.
  2. Build bricht bei neuer Erwartung: Ein neuer Consumer-Pact ist noch nicht unterstützt. Lösung: enablePending und Provider-Branch setzen.
  3. can-i-deploy unknown: Eine Verifikation fehlt noch. Lösung: auf das Ergebnis der Provider-Pipeline warten.
  4. Überschriebene Verträge: Versionen wurden von Hand erhöht. Lösung: Git-SHA als Version und Branch angeben.
  5. Umgebung unbekannt: Der Broker weiss nicht, was läuft. Lösung: nach jedem Deployment record-deployment aufrufen.
  6. Zu strenge Verträge: Konkrete Werte machen den Provider-Test brüchig. Lösung: Typ-Matcher und Regex statt exakter Werte.

Diagnose: Werkzeuge und Befehle

  • can-i-deploy: pact-broker can-i-deploy --pacticipant X --version Y --to-environment Z zeigt die Matrix und den Exit-Code.
  • Deployment melden: pact-broker record-deployment --pacticipant X --version Y --environment Z.
  • Pact-Datei lesen: Die JSON-Datei zeigt Interactions, Matcher und metadata.pactSpecification.version.
  • Dry-Run und Warten: can-i-deploy kennt einen Dry-Run, der immer erfolgreich endet. Es kann auch auf Verifikationsergebnisse warten. --latest kann Race Conditions haben.
  • Generierte Tests: Bei Spring Cloud Contract liegen die erzeugten Tests im Paket org.springframework.cloud.contract.verifier.tests.

Senior-Punkte

  1. Der Vertrag ist ein Gespräch.: Consumer-driven zwingt zur Frage: Was braucht ihr wirklich? Das senkt die Kopplung.
  2. Lose Antworten, strenge Anfragen.: Das Prinzip «streng senden, locker empfangen» macht Verträge langlebig.
  3. Pipeline schlägt Disziplin.: can-i-deploy und record-deployment gehören in die Pipeline und nicht in eine Checkliste.
  4. Verträge testen Form, nicht Fachlogik.: Wer Fachregeln in Verträge steckt, bekommt brüchige Tests.
  5. Felder erst ergänzen, dann entfernen.: So bleibt jede Zwischenstufe kompatibel und der Broker bestätigt den Weg.
  6. Die Richtung ist eine Teamfrage.: Consumer-driven passt, wenn Teams getrennt sind. Provider-driven passt, wenn ein Team beides besitzt.
