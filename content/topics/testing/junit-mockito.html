JUnit 6 und Mockito

Testing · Tier 1 · Quellen: junit.org, JUnit User Guide und Release Notes 6.0/6.1 (docs.junit.org), Mockito Javadoc 5.x (org.mockito.Mockito, MockitoSettings), Mockito Releases (GitHub), Spring Boot 4.0 Migration Guide

Kern: JUnit ist das Standard-Testframework für Java: Es findet Testmethoden, führt sie mit einem Lebenszyklus aus und meldet Ergebnisse. Mockito erzeugt Test Doubles, also Ersatzobjekte für Abhängigkeiten. Zusammen testen sie eine Klasse isoliert und schnell. Aktuell sind JUnit 6.1 und Mockito 5.x (Stand November 2026).

1. Wo sitzen JUnit und Mockito?

  1. JUnit Platform: die Basis. Der Launcher findet und startet Test-Engines. Maven, Gradle und IDEs sprechen nur mit ihr.
  2. JUnit Jupiter: die Engine und API für neue Tests: @Test, @BeforeEach, Assertions, Extensions.
  3. JUnit Vintage: führt alte JUnit-4-Tests aus. In JUnit 6 ist sie deprecated, nur für die Migration gedacht.
  4. MockitoExtension: eine Jupiter-Extension. Sie erzeugt Felder mit @Mock, @Spy, @Captor und prüft unnötige Stubs.
  5. SUT (System Under Test): die echte Klasse. Mockito setzt die Mocks per @InjectMocks ein, besser per Konstruktor von Hand.

JUnit 6 vs 5: JUnit 6.0.0 kam am 30.09.2025. Es braucht Java 17. Platform, Jupiter und Vintage haben jetzt eine gemeinsame Versionsnummer. Neu sind JSpecify-Nullability-Annotationen, FastCSV für @CsvSource, Kotlin-suspend-Tests und deterministische @Nested-Reihenfolge. Veraltete APIs und junit-platform-runner fielen weg. Die Jupiter-API (org.junit.jupiter.api) bleibt gleich. Darum gilt fast alles über „JUnit 5“ weiter.

2. Die Reise eines Tests (die Geschichte zum Merken)

  1. @BeforeAll: läuft einmal pro Klasse. Standardmässig muss die Methode static sein. Beispiel: teure Testdaten laden.
  2. Neue Instanz pro Test: Der Standard ist PER_METHOD. JUnit erzeugt für jede Testmethode ein neues Objekt der Testklasse. So teilen Tests keinen Feldzustand. MockitoExtension erzeugt dabei frische Mocks.
  3. @BeforeEach: bereitet jeden Test vor. Das ist Arrange: Objekte bauen, Stubs mit when(...) setzen.
  4. @Test: Act ruft die Methode der SUT auf. Assert prüft Ergebnis und, wenn nötig, Interaktionen mit verify.
  5. Strict Stubs: Nach dem Test prüft MockitoExtension, ob jeder Stub benutzt wurde. Ein unbenutzter Stub gibt UnnecessaryStubbingException. Standard ist Strictness.STRICT_STUBS.
  6. @AfterEach räumt nach jedem Test auf. @AfterAll räumt einmal am Ende auf.
  7. Mit @TestInstance(PER_CLASS) gibt es nur eine Instanz für alle Tests. Dann dürfen @BeforeAll und @AfterAll nicht-statisch sein. Preis: Tests können über Felder Zustand teilen.

3. Beispiel: Service mit Mock, Captor und Parametern

@ExtendWith(MockitoExtension.class)
class RechnungServiceTest {

  @Mock RechnungRepository repo;                 // Mock: leere Antworten
  @Mock Mailer mailer;
  @Captor ArgumentCaptor<Mail> mail;
  RechnungService service;

  @BeforeEach void setUp() {
    service = new RechnungService(repo, mailer, Clock.fixed(
        Instant.parse("2026-11-24T10:00:00Z"), ZoneId.of("Europe/Zurich")));
  }

  @Test void sendetMahnungFuerUeberfaelligeRechnung() {
    when(repo.findOffene()).thenReturn(List.of(new Rechnung("R-1", "a@b.ch", LocalDate.of(2026, 10, 1))));

    int anzahl = service.mahnen();

    assertEquals(1, anzahl);
    verify(mailer).send(mail.capture());         // genau einmal gesendet
    assertAll(
      () -> assertEquals("a@b.ch", mail.getValue().to()),
      () -> assertTrue(mail.getValue().subject().contains("R-1")));
    verifyNoMoreInteractions(mailer);
  }

  @Test void wirftBeiFehlenderAdresse() {
    when(repo.findOffene()).thenReturn(List.of(new Rechnung("R-2", null, LocalDate.of(2026, 1, 1))));
    var ex = assertThrows(IllegalStateException.class, () -> service.mahnen());
    assertEquals("Keine Adresse für R-2", ex.getMessage());
    verifyNoInteractions(mailer);
  }

  @ParameterizedTest(name = "{0} Tage überfällig → Stufe {1}")
  @CsvSource({ "0, 0", "29, 0", "30, 1", "60, 2", "365, 3" })
  void mahnstufe(int tage, int stufe) {
    assertEquals(stufe, RechnungService.mahnstufe(tage));
  }

  @Test void unnoetigerStub() {
    when(repo.findOffene()).thenReturn(List.of());
    when(repo.count()).thenReturn(5L);           // wird nie aufgerufen
    service.mahnen();
  }
}

  1. @Mock gibt Standardwerte zurück: null, 0, false, leere Listen. Erst when(...).thenReturn(...) macht ihn zum Stub.
  2. ArgumentCaptor fängt das Argument im verify ein. Danach prüft man die Felder mit normalen Assertions.
  3. assertAll meldet alle fehlgeschlagenen Teile, nicht nur den ersten.
  4. assertThrows gibt die Exception zurück. So prüft man auch die Meldung.
  5. @CsvSource erzeugt fünf Testfälle aus einer Methode. Jeder Fall erscheint einzeln im Report.
  6. Clock.fixed macht die Zeit testbar. „Überfällig“ hängt sonst vom Ausführungstag ab.
  7. Der unnötige Stub macht den Test rot. Das ist gewollt: Toter Testcode verwirrt Leser.

4. Details, die Interviewer fragen

  1. Assertions: assertEquals, assertTrue, assertNull, assertThrows, assertAll, assertTimeout, assertIterableEquals. Viele Teams nutzen AssertJ (assertThat(x).isEqualTo(y)) für lesbarere Meldungen.
  2. Weitere Annotationen: @DisplayName (lesbarer Name), @Nested (Gruppen), @Tag (z. B. „slow“ filtern), @Disabled, @RepeatedTest, @Timeout, @TempDir (temporäres Verzeichnis).
  3. Parameterized Tests: Quellen sind @ValueSource, @NullSource, @EmptySource, @NullAndEmptySource, @EnumSource, @MethodSource, @FieldSource, @CsvSource, @CsvFileSource, @ArgumentsSource. @ParameterizedClass parametrisiert eine ganze Klasse. Sie ist noch experimentell.
  4. Extension-Modell: Jupiter ersetzt JUnit-4-@RunWith und @Rule durch @ExtendWith. Mehrere Extensions lassen sich kombinieren, z. B. Spring und Mockito.
  5. Test Doubles (Gerard Meszaros):
    • Dummy: wird nur übergeben, nie benutzt.
    • Stub: liefert feste Antworten. Beispiel: when(repo.find(1)).thenReturn(x).
    • Mock: prüft Interaktionen. Beispiel: verify(mailer).send(any()).
    • Spy: echtes Objekt, einzelne Methoden überschrieben.
    • Fake: einfache echte Implementierung, z. B. In-Memory-Repository.
    In Mockito ist ein @Mock technisch beides: Stub und Mock.
  6. Spy und doReturn: Bei einem Spy ruft when(spy.get(0)) die echte Methode auf. Das kann werfen. Darum doReturn("x").when(spy).get(0). Ein Spy ist eine Kopie der Instanz, nicht ein Wrapper.
  7. Argument Matchers: any(), eq(), argThat(...). Regel: Nutzt ein Argument einen Matcher, brauchen alle Argumente Matcher. Sonst gibt es InvalidUseOfMatchersException.
  8. ArgumentCaptor: Mockito empfiehlt Captor mit verify, nicht beim Stubbing. Beim Stubbing fängt er nichts ein, wenn die Methode nie gerufen wird.
  9. verify-Varianten: times(2), never(), atLeastOnce(), verifyNoInteractions, verifyNoMoreInteractions, InOrder für die Reihenfolge.
  10. Inline Mock Maker: Seit Mockito 5 ist er Standard. Er kann final Klassen und Methoden mocken. mockStatic und mockConstruction nutzen ihn auch. Statische Mocks immer in try-with-resources schliessen.
  11. Java 21+ und der Agent: Mockito lädt sich zur Laufzeit als Java-Agent. Neuere JDKs warnen dabei. Die Mockito-Doku empfiehlt, das Mockito-JAR als -javaagent an die Test-JVM zu geben (z. B. in Surefire argLine).
  12. Strictness: STRICT_STUBS meldet unnötige Stubs und Argument-Mismatches. Ausnahme pro Stub: lenient().when(...). Pro Klasse: @MockitoSettings(strictness = LENIENT).
  13. Spring Boot 4: @MockBean und @SpyBean wurden entfernt. Ersatz aus Spring Framework: @MockitoBean und @MockitoSpyBean. Jeder geänderte Mock-Satz erzeugt einen neuen Spring-Context.

Wann nicht mocken:

  • Werte-Objekte und Records: einfach echt erzeugen.
  • Typen, die Ihnen nicht gehören (z. B. JdbcTemplate, HTTP-Clients): Der Mock bildet Ihr Missverständnis der API nach. Besser einen eigenen Adapter mocken und den Adapter mit echter Infrastruktur testen.
  • Datenbank und SQL: mit Testcontainers echt testen.
  • Die Klasse unter Test selbst: Ein Spy auf die SUT zeigt meist ein Design-Problem.
  • Wenn der Test nur die Implementierung nachbaut: zehn when und zehn verify heissen, der Test bricht bei jedem Refactoring.

5. Vergleich

  • JUnit 4: @RunWith, @Rule, @Before, öffentliche Klassen und Methoden. In JUnit 6 nur noch über die deprecated Vintage-Engine.
  • JUnit 5: Platform + Jupiter + Vintage, Extensions, Java 8 Basis. Getrennte Versionsnummern für Platform (1.x) und Jupiter (5.x).
  • JUnit 6: gleiche Jupiter-API, Java 17 Basis, eine Versionsnummer, JSpecify, alte APIs entfernt.
  • TestNG: Alternative mit Gruppen und Abhängigkeiten zwischen Tests. Im Spring-Umfeld selten.
  • Mock vs Stub: Stub liefert Antworten (Zustand prüfen). Mock prüft Aufrufe (Verhalten prüfen).
  • Mock vs Spy: Mock ist leer. Spy ruft echte Methoden auf, ausser den gestubbten.
  • Mock vs Fake: Fake hat echte, einfache Logik und ist wiederverwendbar. Mock wird pro Test programmiert.
  • Mockito vs MockK: MockK ist für Kotlin gebaut (Coroutines, Objekte). Mockito ist der Java-Standard.

6. In der Produktion

  1. Tests brechen bei jedem Refactoring: Ursache sind viele verify auf interne Aufrufe. Lösung: Ergebnis prüfen, verify nur für echte Seiteneffekte (Mail, Event, Zahlung).
  2. Grüne Tests, kaputte Produktion: Der Mock vom RestClient liefert ein Format, das der echte Server nie schickt. Lösung: Contract-Test oder WireMock mit echten Antworten.
  3. Statischer Mock leckt: mockStatic ohne close() beeinflusst andere Tests im selben Thread. Lösung: immer try (var m = mockStatic(...)).
  4. Langsame Spring-Tests: Jede Klasse mit anderen @MockitoBean baut einen neuen Context. Lösung: Mock-Sets vereinheitlichen, mehr reine Unit-Tests ohne Spring.
  5. Warnung zum dynamischen Agent im Build-Log, auf Java 21+: Lösung laut Mockito-Doku: -javaagent in der Surefire-argLine setzen.
  6. Migration 4 → 5/6: @Before → @BeforeEach, @RunWith(MockitoJUnitRunner) → @ExtendWith(MockitoExtension.class), @Test(expected=…) → assertThrows. Vintage nur übergangsweise.

7. Diagnose: Werkzeuge und Befehle

  • mvn -Dtest=RechnungServiceTest#mahnstufe test: einen Test gezielt starten.
  • mvn -Dgroups=fast test bzw. -DexcludedGroups=slow: nach @Tag filtern.
  • junit-platform.properties in src/test/resources: zentrale Einstellungen wie Lebenszyklus oder Parallelität.
  • Mockito.mockingDetails(obj): zeigt, ob ein Objekt ein Mock ist und welche Aufrufe es sah.
  • UnnecessaryStubbingException und PotentialStubbingProblem lesen: Sie zeigen Stubs, die nicht passen.
  • JUnit ConsoleLauncher mit --fail-fast (seit JUnit 6): stoppt nach dem ersten Fehler.

8. Senior-Punkte

  1. Mocks an Systemgrenzen, nicht zwischen eigenen kleinen Klassen. Je weniger Mocks, desto robuster der Test.
  2. Zustand prüfen vor Verhalten prüfen. verify nur für Seiteneffekte, die das Ergebnis sind.
  3. Konstruktor-Injektion macht Mockito-Magie (@InjectMocks) überflüssig. Der Test zeigt dann klar alle Abhängigkeiten.
  4. Schwer zu testen heisst schlecht entworfen. Viele Mocks zeigen zu viele Abhängigkeiten. mockStatic zeigt versteckte Kopplung.
  5. Strict Stubs anlassen. Sie halten Tests sauber und finden falsche Argumente früh.
  6. Parametrisierte Tests für Geschäftsregeln: Eine Tabelle mit Grenzwerten ist auch Doku für Fachleute.

10. Fallen

  • „JUnit 6 ist eine neue API.“ → Falsch. Die Jupiter-API bleibt. Neu sind Java 17 Basis, eine Versionsnummer und entfernte Altlasten.
  • „when(spy.x()) ist sicher.“ → Falsch. Es ruft die echte Methode auf. Bei Spies doReturn().when(spy) nutzen.
  • „Final Klassen kann Mockito nicht mocken.“ → Veraltet. Seit Mockito 5 ist der Inline Mock Maker Standard.
  • „@BeforeAll muss immer static sein.“ → Nur bei PER_METHOD. Mit @TestInstance(PER_CLASS) nicht.
  • „Mehr verify heisst gründlicher.“ → Falsch. Es koppelt den Test an die Implementierung.
  • „Captor beim Stubbing nutzen.“ → Mockito rät ab. Captor gehört zu verify, beim Stubbing sind Matcher besser.

11. Fragen

Welche aktuelle JUnit-Version gibt es und was ist neu?

JUnit 6 (6.1.x). Java 17 Basis, eine Versionsnummer für alle Module, JSpecify, FastCSV, Kotlin-suspend-Tests, alte APIs entfernt. Die Jupiter-API bleibt gleich.

Aus welchen Teilen besteht JUnit?

Platform (Launcher, Engine-API), Jupiter (neue API und Engine) und Vintage (JUnit 4, deprecated).

Wie sieht der Lebenszyklus eines Tests aus?

@BeforeAll einmal, dann pro Test: neue Instanz, @BeforeEach, @Test, @AfterEach. Am Ende @AfterAll.

Warum erzeugt JUnit pro Test eine neue Instanz?

Damit Tests keinen Feldzustand teilen. Das ist der Standard PER_METHOD.

Was ändert @TestInstance(PER_CLASS)?

Eine Instanz für alle Tests der Klasse. @BeforeAll darf dann nicht-statisch sein. Risiko: geteilter Zustand.

Was macht assertAll?

Es führt alle Assertions aus und meldet alle Fehler gemeinsam. Ohne assertAll stoppt der Test beim ersten Fehler.

Wie testen Sie eine Exception?

Mit assertThrows. Es gibt die Exception zurück, damit man Meldung und Felder prüfen kann.

Welche Quellen gibt es für Parameterized Tests?

@ValueSource, @CsvSource, @CsvFileSource, @MethodSource, @FieldSource, @EnumSource, @NullSource, @EmptySource, @ArgumentsSource.

Was ist der Unterschied zwischen Mock, Stub, Spy und Fake?

Stub liefert Antworten. Mock prüft Aufrufe. Spy ist ein echtes Objekt mit einzelnen überschriebenen Methoden. Fake ist eine einfache echte Implementierung.

Was gibt ein Mockito-Mock ohne Stub zurück?

Standardwerte: null, 0, false, leere Collections und leere Optionals.

Warum doReturn statt when bei einem Spy?

when(spy.methode()) ruft die echte Methode schon beim Stubbing auf. Das kann werfen oder Seiteneffekte haben.

Wofür ist ArgumentCaptor?

Er fängt ein Argument beim verify ein. Danach prüft man dessen Felder mit Assertions.

Was ist die Matcher-Regel in Mockito?

Nutzt ein Argument einen Matcher, brauchen alle einen. Feste Werte dann mit eq().

Was sind Strict Stubs?

Mockito meldet unbenutzte Stubs und falsche Argumente. Bei MockitoExtension ist STRICT_STUBS Standard.

Kann Mockito final und static mocken?

Ja. Seit Mockito 5 ist der Inline Mock Maker Standard. Static mit mockStatic im try-with-resources.

Was ersetzt @MockBean in Spring Boot 4?

@MockitoBean und @MockitoSpyBean aus dem Spring Framework. @MockBean und @SpyBean wurden in Boot 4.0 entfernt.

Wann mocken Sie nicht?

Werte-Objekte, fremde Typen wie JdbcTemplate, SQL und die Klasse unter Test selbst. Dort echte Objekte oder echte Infrastruktur nutzen.

Was bedeutet „Don't mock types you don't own“?

Ein Mock einer fremden API bildet nur Ihre Annahme nach. Besser einen eigenen Adapter mocken und diesen gegen die echte API testen.

Wie migrieren Sie von JUnit 4?

Annotationen ersetzen (@BeforeEach, @ExtendWith, assertThrows), Vintage nur übergangsweise nutzen, Rules durch Extensions ersetzen.

Warum warnt die JVM bei Mockito auf Java 21+?

Mockito lädt sich zur Laufzeit als Agent. Die Doku empfiehlt, Mockito explizit als -javaagent an die Test-JVM zu geben.

Was ist @InjectMocks und warum ist es umstritten?

Es setzt Mocks per Konstruktor, Setter oder Feld in die SUT. Es schlägt still fehl, wenn es nicht passt. Konstruktor von Hand ist klarer.

Wie testen Sie Code, der LocalDate.now() nutzt?

Eine Clock injizieren und im Test Clock.fixed nutzen. So ist der Test an jedem Tag gleich.

Szenario: Nach einem kleinen Refactoring sind 40 Tests rot, aber die Funktion stimmt. Was ist los?

Die Tests prüfen Implementierung mit vielen verify. Ich stelle auf Ergebnis-Assertions um und behalte verify nur für echte Seiteneffekte.

Szenario: Ein Test ist nur rot, wenn er nach einem bestimmten anderen Test läuft. Woran denken Sie?

Geteilter Zustand: ein nicht geschlossener mockStatic, ein statisches Feld oder Daten in der DB. Ich prüfe try-with-resources und isoliere die Daten.

Szenario: Unit-Tests mit gemocktem HTTP-Client sind grün, Produktion bekommt 400 vom Partner. Was ändern Sie?

Der Mock entsprach nicht dem echten Vertrag. Ich teste den Adapter mit WireMock oder einem Contract-Test gegen echte Beispielantworten.
