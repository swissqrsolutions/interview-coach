Mock, Stub, Spy, Fake

Kern: Ein Test Double ersetzt in einem Test eine echte Abhängigkeit, so wie ein Stunt Double einen Schauspieler. Es gibt fünf Arten: Dummy, Stub, Spy, Mock und Fake. Sie unterscheiden sich in ihrer Aufgabe. Sie liefern Antworten, zeichnen Aufrufe auf, prüfen Erwartungen oder haben eine einfache echte Logik.

Antwort-Muster

Frage: Was ist der Unterschied zwischen Mock, Stub, Spy und Fake?

  1. Mechanismus: Ein Stub liefert feste Antworten. Ein Spy ist ein Stub, der Aufrufe aufzeichnet. Ein Mock kennt seine erwarteten Aufrufe vorab und prüft sie. Ein Fake hat eine einfache echte Logik.
  2. Zahl: Meszaros nennt fünf Arten. Ein Dummy ist die fünfte. Er wird nur übergeben und nie benutzt.
  3. Trade-off: Behavior Verification prüft Aufrufe und koppelt den Test an die Implementierung. State Verification prüft das Ergebnis und überlebt Refactorings besser.
  4. Produktion: Ich prüfe zuerst den Zustand und das Ergebnis. Mocks nehme ich bei Seiteneffekten ohne Rückgabewert, zum Beispiel beim Mail-Versand.

1. Ein Test mit Doubles in 7 Schritten

  1. SUT bestimmen: Das System under Test ist die Klasse, die man prüft. Alles, was sie aufruft, ist ein Kollaborateur.
  2. Kollaborateure finden: Zum Beispiel ein Repository, ein Mailer und eine Uhr. Nicht jeder muss ersetzt werden.
  3. Rolle klären: Liefert der Kollaborateur Daten, braucht man Antworten. Löst das SUT einen Seiteneffekt aus, will man den Aufruf sehen.
  4. Double wählen: Daten ohne Logik gibt ein Stub. Wird er nicht benutzt, reicht ein Dummy. Aufrufe sieht man mit Spy oder Mock. Echte Logik im Speicher gibt ein Fake.
  5. Act: Der Test ruft das SUT auf, mit den Doubles als Abhängigkeiten.
  6. Verifizieren: Bei State Verification prüft man das Ergebnis oder den Zustand. Bei Behavior Verification prüft man, welche Aufrufe das SUT gemacht hat.
  7. Refactoring-Test: Man ändert die Implementierung, ohne das Verhalten zu ändern. Ein guter Test bleibt grün. Ein Test, der Aufrufe zählt, bricht oft.

Die Demo unten zeigt genau diesen letzten Schritt mit echter Ausgabe.

2. Aufbau

  1. Dummy: Füllt eine Parameterliste. Er wird nie benutzt.
  2. Stub: Gibt vorbereitete Antworten auf Aufrufe im Test. Auf alles andere antwortet er meist nicht.
  3. Spy: Ein Stub, der zusätzlich merkt, wie er aufgerufen wurde. Der Test fragt danach.
  4. Mock: Hat Erwartungen, die zusammen eine Spezifikation der Aufrufe bilden. Er kann bei unerwarteten Aufrufen werfen.
  5. Fake: Hat eine funktionierende Implementierung mit einer Abkürzung. Ein Beispiel ist eine In-Memory-Datenbank.
  6. Verifikation: State prüft das Ergebnis. Behavior prüft die Aufrufe an Kollaborateure.

3. Details

  1. Begriff: Gerard Meszaros hat das Vokabular geprägt. Der Oberbegriff ist Test Double. Martin Fowler fasst die fünf Arten in seinem Blog zusammen.
  2. Dummy: Ein Dummy wird herumgereicht und nie benutzt. Er füllt nur Parameter. Ein Beispiel ist ein Mailer, der in diesem Test nie gerufen werden darf.
  3. Stub: Er gibt vorbereitete Antworten auf Aufrufe im Test. Er hat keine Logik. In Mockito schreibt man when(repo.find(1)).thenReturn(x).
  4. Spy: Er ist ein Stub, der Informationen über Aufrufe sammelt. Fowlers Beispiel ist ein E-Mail-Dienst, der zählt, wie viele Mails er gesendet hat. In Mockito ist ein Spy ein echtes Objekt, bei dem man einzelne Methoden überschreibt.
  5. Mock: Er ist mit Erwartungen vorbereitet. Sie bilden eine Spezifikation der erwarteten Aufrufe. Er kann bei unerwarteten Aufrufen sofort werfen. Am Ende prüft der Test, ob alle Erwartungen eintraten.
  6. Fake: Er hat eine funktionierende Implementierung, die eine Abkürzung nimmt. Darum taugt er nicht für Produktion. Beispiele sind ein In-Memory-Repository oder eine In-Memory-Datenbank.
  7. Mockito-Besonderheit: Ein @Mock in Mockito ist technisch Stub und Mock zugleich. Man stubbt mit when und prüft mit verify. Bei einem Spy ruft when(spy.get(0)) die echte Methode auf. Darum nimmt man doReturn(...).when(spy).
  8. State oder Behavior: State Verification prüft Zustand und Ergebnis des SUT. Behavior Verification prüft die Aufrufe des SUT an seine Kollaborateure. Nur Mocks bestehen auf Behavior Verification. Fowler nennt die Wahl für die meisten Fälle klein.
  9. Classical und mockist: Classicists nehmen echte Objekte, wo es geht, und Doubles nur bei Unbequemem. Mockists ersetzen jeden Kollaborateur mit interessantem Verhalten. Mockists arbeiten oft von aussen nach innen.
  10. Kopplung: Mockist-Tests sind enger an die Implementierung gebunden. Fowler schreibt, dass eine geänderte Art der Aufrufe an Kollaborateure einen Mockist-Test meist bricht. Die Demo zeigt das.
  11. Isolation: Mockist-Tests schlagen eher nur dort fehl, wo der Fehler liegt. Classic-Tests können bei einem Fehler in vielen Clients rot werden. Dafür brauchen Mockists weniger Setup.
  12. Fakes ehrlich halten: Ein Double kann vom echten System abweichen. Fowler empfiehlt, Contract Tests getrennt und regelmässig laufen zu lassen. Sie prüfen, ob die Doubles noch zum echten System passen. Zeit ersetzt man durch eine Uhr, die man stubben kann.

4. Fallen

  • „Mock und Stub sind dasselbe.“ → Falsch. Ein Stub liefert Antworten. Ein Mock kennt erwartete Aufrufe und prüft sie.
  • „Ein Spy ist ein Mock.“ → Falsch. Ein Spy ist ein Stub, der Aufrufe aufzeichnet. Der Test fragt danach. Ein Mock prüft gegen Erwartungen.
  • „Mehr Mocks bedeuten bessere Tests.“ → Falsch. Mocks koppeln den Test an die Aufrufe. Bei Refactorings brechen sie, ohne dass ein Fehler da ist.
  • „Ein Fake ist ein Stub mit mehr Daten.“ → Falsch. Ein Fake hat eine echte, vereinfachte Logik. Ein Stub hat nur feste Antworten.
  • „@Mock in Mockito ist nur ein Mock.“ → Falsch. Technisch ist es Stub und Mock zugleich. Man stubbt mit when und prüft mit verify.
  • „Ein grüner Test mit Double zeigt, dass die echte Abhängigkeit passt.“ → Falsch. Das Double kann abweichen. Erst Contract Tests oder ein Integrationstest schliessen die Lücke.

5. Selbsttest

Warum?

Warum nutzt man Test Doubles?

Echte Abhängigkeiten sind langsam, nicht deterministisch oder haben Seiteneffekte. Ein Double macht den Test schnell, stabil und kontrollierbar.

Warum soll man nicht alles mocken?

Je mehr Aufrufe der Test prüft, desto enger ist er an die Implementierung gebunden. Jedes Refactoring bricht dann Tests.

Warum ist ein Fake oft besser als ein Mock für ein Repository?

Ein Fake speichert wirklich. Der Test prüft das Ergebnis und nicht, welche Methoden gerufen wurden. Er überlebt Refactorings besser.

Wie innen?

Was ist ein Dummy?

Ein Objekt, das nur übergeben und nie benutzt wird. Es füllt zum Beispiel eine Parameterliste.

Was ist ein Stub?

Ein Double mit vorbereiteten Antworten auf Aufrufe im Test. Er hat keine eigene Logik.

Was ist ein Spy?

Ein Stub, der zusätzlich aufzeichnet, wie er aufgerufen wurde. Der Test prüft die Aufzeichnung nach dem Aufruf.

Was ist ein Mock nach Fowler?

Ein Double mit vorab gesetzten Erwartungen. Er kann bei unerwarteten Aufrufen werfen und wird am Ende verifiziert.

Was ist ein Fake?

Ein Double mit funktionierender, vereinfachter Implementierung. Ein Beispiel ist ein In-Memory-Repository.

Zahlen

Wie viele Arten von Test Doubles nennt Meszaros?

Fünf: Dummy, Stub, Spy, Mock und Fake.

Wie viele Aufrufe zählt der Mock in der Demo vor dem Refactoring?

Genau einen. Nach dem Refactoring zählt er zwei und der Test bricht.

Wie viele Mocks sind pro Test sinnvoll?

Eine feste Zahl gibt es nicht. Wenige, an echten Grenzen. Meist reicht ein Mock für den Seiteneffekt.

Vergleich

Mock oder Stub?

Ein Stub liefert Daten. Ein Mock prüft Aufrufe. Nur der Mock besteht auf Behavior Verification.

Spy oder Mock?

Ein Spy zeichnet auf, und der Test prüft danach. Ein Mock kennt die Erwartung schon vorher und kann sofort werfen.

Fake oder Stub?

Ein Fake hat echte Logik und hält Zustand. Ein Stub gibt feste Antworten.

State oder Behavior Verification?

State prüft das Ergebnis und überlebt Refactorings. Behavior prüft Aufrufe und passt bei Seiteneffekten ohne Rückgabewert.

Classical oder mockist?

Classical nutzt echte Objekte und Doubles nur bei Unbequemem. Mockist ersetzt jeden Kollaborateur mit Verhalten. Mockist ist enger an die Implementierung gekoppelt.

Produktion

Wie halten Sie Fakes ehrlich?

Ein Contract Test läuft gegen den Fake und gegen die echte Abhängigkeit. Er zeigt, wenn der Fake abweicht.

Szenario: Alle Tests sind grün, aber die Produktion bricht beim Aufruf des Partner-Dienstes. Was war falsch?

Das Double entsprach nicht dem echten Dienst. Lösung: Contract Tests oder ein schmaler Integrationstest gegen den echten Dienst.

Szenario: Ein Refactoring ändert kein Verhalten, aber 50 Tests brechen. Was tun Sie?

Die Tests prüfen Aufrufe. Man stellt auf State Verification um und ersetzt Mocks durch Fakes, wo es geht.

Szenario: Ein Mockito-Spy wirft eine Exception beim Stubben mit when. Warum?

when(spy.get(0)) ruft die echte Methode auf. Lösung: doReturn(wert).when(spy).get(0).

Design

Wann ist ein Mock sinnvoll?

Bei Seiteneffekten ohne Rückgabewert, zum Beispiel einer Mail. Dort gibt es keinen Zustand zu prüfen. Auch bei Caches ist Behavior Verification sinnvoll.

Wann nimmt man einen Fake?

Wenn der Kollaborateur Zustand hat und man ihn oft braucht. Ein In-Memory-Repository ist das Standardbeispiel.

Szenario: Ein Test hängt von der aktuellen Uhrzeit ab. Wie lösen Sie das?

Man kapselt die Systemuhr hinter einem Interface. Im Test setzt man einen Stub mit fester Zeit. Direkte Aufrufe der Systemuhr werden vermieden.

Szenario: Ein Service sendet eine Willkommens-Mail. Wie testen Sie das?

Mit einem Spy oder Mock für den Mailer. Man prüft Empfänger und Anzahl. Das Ergebnis des Aufrufs prüft man per State Verification.

Mehr

Gerüst

  • Warum? Tests schnell, stabil und kontrollierbar machen, ohne echte Abhängigkeiten.
  • Wie innen? Dummy, Stub, Spy, Mock, Fake. State Verification und Behavior Verification.
  • Zahlen Fünf Arten nach Meszaros. Ein Mock zählt in der Demo erst 1, dann 2 Aufrufe.
  • Vergleich Mock gegen Stub. Spy gegen Mock. Fake gegen Stub. Classical gegen mockist.
  • Produktion Double weicht vom echten System ab. Refactoring bricht Tests.
  • Design Erst Zustand prüfen. Mock bei Seiteneffekten. Fakes mit Contract Tests absichern.

Beispiel: Fünf Doubles von Hand und ein Refactoring

interface Repo { Optional<String> find(int id); void save(int id, String name); }
interface Mailer { void send(String to, String text); }
interface Clock { long now(); }

// Service: begrüsst einen Kunden und sendet eine Mail
String welcome(int id) {
  String name = repo.find(id).orElse("guest");
  mailer.send(name + "@example.ch", "hello " + name + " at " + clock.now());
  return "Hello " + name;
}
// Stub: find() gibt immer "Anna".   Dummy: Mailer wirft, wenn er gerufen wird.
// Fake: FakeRepo mit HashMap.        Spy: SpyMailer merkt sich Aufrufe.
// Mock: MockMailer erwartet genau einen Aufruf an "Anna@example.ch".
// Refactoring: der Service sendet jetzt zusätzlich eine Kopie.
1) stub repo + spy mailer  (state check on result, behavior check on spy)
   result = Hello Anna
   spy.calls = [Anna@example.ch | hello Anna at 1000]
2) fake repo, two calls (state is kept between calls)
   Hello Ben / Hello guest
3) mock mailer with expectation
   verified: exactly one mail to Anna
4) refactor: the service now sends two mails (same result for the user)
   mock test breaks: expected 1 call, got 2
   state test on the result still passes: true

Echte Ausgabe, Java 17.0.3 (reine JDK-Klassen, kein Mockito). Der Code oben ist gekürzt.

  1. Fall 1: Der Stub liefert «Anna». Der Test prüft das Ergebnis (State) und die Aufzeichnung des Spys (Behavior).
  2. Fall 2: Das Fake speichert wirklich. Für Id 2 gibt es «Ben», für Id 99 den Standard «guest».
  3. Fall 3: Der Mock erwartet eine Mail an Anna und besteht, weil genau eine kam.
  4. Fall 4: Nach dem Refactoring sendet der Service zwei Mails. Der Mock-Test bricht. Der State-Test auf das Ergebnis bleibt grün.

Vergleich

  • Dummy: Wird nie benutzt. Füllt nur Parameter.
  • Stub: Feste Antworten. Liefert Eingaben für das SUT.
  • Spy: Stub mit Aufzeichnung. Der Test prüft danach.
  • Mock: Erwartungen vorab. Wirft bei Überraschungen und wird am Ende verifiziert.
  • Fake: Echte, einfache Logik. Gut für Repositories und Caches im Speicher.
  • Echtes Objekt: Bei schnellen, deterministischen Kollaborateuren ist das Echte oft das beste Double.

Produktion

  1. Double weicht vom Original ab: Der Test ist grün, die Produktion bricht. Lösung: Contract Tests gegen Double und Original.
  2. Refactoring bricht viele Tests: Tests prüfen Aufrufe statt Ergebnis. Lösung: State Verification und Fakes bevorzugen.
  3. Unnötige Stubs: Ein Test stubbt Aufrufe, die nie passieren. Lösung: Mockito mit strikten Stubs, das meldet unnötige Stubs.
  4. Spy mit when: Die echte Methode läuft beim Stubben und wirft. Lösung: doReturn(...).when(spy).
  5. Zeit im Test: Tests nutzen die Systemuhr und schwanken. Lösung: Uhr hinter ein Interface legen und stubben.
  6. Zu viele Doubles: Der Test prüft nur noch die Mocks. Lösung: echte Objekte nutzen, wo sie billig sind.

Diagnose: Werkzeuge und Befehle

  • Refactoring-Probe: Eine Methode ohne Verhaltensänderung umbauen. Brechen Tests, prüfen sie Implementierung.
  • Mockito Strictness: STRICT_STUBS meldet unnötige Stubs und Argument-Abweichungen.
  • verifyNoMoreInteractions: Zeigt, wo ein Test jeden Aufruf festnagelt. Sparsam einsetzen.
  • Mutation Testing: Werkzeuge wie PIT ändern den Code und prüfen, ob Tests es merken. Mocks ohne Wirkung fallen auf.
  • Test lesen: Zählt man mehr Zeilen Setup als Zeilen Prüfung, ist oft zu viel gemockt.

Senior-Punkte

  1. Verhalten, nicht Implementierung.: Ein Test soll sagen, was das System tut, nicht wie. Aufrufe zu zählen sagt wie.
  2. Mocks an Grenzen.: HTTP, Mail und Uhr sind Grenzen. Dazwischen nutzt man echte Objekte.
  3. Fakes brauchen Wartung.: Jedes Fake ist Code, der vom Original abweichen kann. Ein Contract Test hält es ehrlich.
  4. Beide Schulen haben Recht.: Fowler beschreibt classical und mockist als Abwägung. Teams wählen nach Debugging-Kosten und Design-Stil.
  5. Design-Signal.: Braucht ein Test viele Mocks, hat die Klasse oft zu viele Abhängigkeiten.
  6. Der Name sagt die Absicht.: Wer einen Spy «mock» nennt, verwirrt das Team. Namen wie spyMailer sagen, was gemeint ist.
