Project Nessie: Git für Daten

Kern: Project Nessie ist ein transaktionaler Catalog für Iceberg-Tabellen mit Versionierung wie in Git. Er speichert für jede Tabelle einen Zeiger auf ihre aktuellen Iceberg-Metadaten, und zwar in Commits auf Branches und Tags. Damit kann man Änderungen an mehreren Tabellen isoliert vorbereiten und gemeinsam sichtbar machen.

Antwort-Muster

Frage: Was ist Project Nessie, und was bringen Branches?

  1. Mechanismus: Nessie ist ein Catalog, der pro Iceberg-Tabelle einen Zeiger auf die Metadaten speichert. Commits, Branches und Tags versionieren alle Tabellen zusammen.
  2. Zahl: Der Server läuft auf Port 19120. Nessie bietet drei Isolationsstufen und prüft Konflikte mit dem erwarteten Hash.
  3. Trade-off: Ein Branch kostet nichts, weil er nur ein Zeiger ist. Der Merge bringt aber keine echte Datenbank-Transaktion, und Wartung wie expire_snapshots wird komplizierter.
  4. Produktion: Ich schreibe pro Lauf auf einen Branch und merge nach main. Als Version Store nehme ich PostgreSQL mit Backups.

1. Die Reise eines Commits: Branch, schreiben, mergen

  1. Ausgangslage: main zeigt auf Commit c2. Dremio liest von main.
  2. Tag setzen: Ein Tag ist ein fester Name für einen Commit, z. B. release-2026-11. Er bewegt sich nie. Gut für Audits und Reproduzierbarkeit.
  3. Branch erstellen: Ein Branch ist ein beweglicher Zeiger. etl_run startet bei c2. Das kostet nichts, es wird keine Datei kopiert.
  4. Schreiben: Spark schreibt silver.trades (Commit c3) und gold.stats (Commit c4) auf dem Branch. Jeder Iceberg-Commit ist ein Nessie-Commit.
  5. Prüfen: Checks laufen gegen den Branch. main ist davon nicht berührt.
  6. Mergen: Ein Merge bringt die Änderungen nach main. Leser sehen beide Tabellen gleichzeitig neu. So entsteht eine Art Multi-Table-Transaktion.
  7. Konflikt: Hat jemand dieselbe Tabelle auf main inzwischen geändert, lehnt Nessie den Merge ab. Nessie arbeitet mit optimistic locking pro Tabelle.

2. Aufbau

  1. Engines: Spark schreibt Iceberg-Tabellen, Dremio liest sie. Beide fragen Nessie: „Wo sind die aktuellen Metadaten von Tabelle X auf Branch main?“
  2. Nessie Server: ein Java-Dienst (Quarkus) mit REST API, standardmässig auf Port 19120. Er verwaltet References (Branches, Tags) und Commits.
  3. Version Store: die Datenbank, in der Nessie Commits und Zeiger speichert. In Produktion z. B. PostgreSQL mit dem Typ JDBC2.
  4. Object Store: Dort liegen die echten Iceberg-Dateien: metadata.json, Manifeste, Parquet-Daten. Nessie speichert sie nicht, nur den Zeiger darauf.
  5. Inhalt pro Tabelle: Laut Spezifikation speichert ein Commit für eine Iceberg-Tabelle den Zeiger auf die Metadaten und die IDs von Snapshot, Schema, Partition Spec und Sort Order.

3. Details, die Interviewer fragen

  1. Was ist ein Catalog? Ein Catalog bildet Tabellennamen auf die aktuelle Metadaten-Datei ab. Er macht den Commit atomar. Der Zeiger wechselt nur, wenn er noch auf dem erwarteten Stand ist.
  2. Commit: Ein Nessie-Commit enthält Operationen. Put setzt neuen Inhalt für einen Schlüssel. Delete entfernt ihn. Unmodified lässt ihn gleich. Ein Commit darf viele Tabellen umfassen.
  3. Content Key und Content ID: Der Content Key ist der Name, zum Beispiel silver.trades. Die Content ID ist eine feste ID, meist eine UUID. Sie bleibt bei Umbenennung gleich. Ein Rename ist ein Delete plus Put.
  4. Konflikterkennung: Jeder Commit nennt einen expectedHash. Das ist der Stand, den der Client kennt. Hat sich der Schlüssel seitdem geändert, wirft Nessie eine NessieConflictException.
  5. Isolation: Nessie bietet drei Stufen. Read Committed liest immer den neuesten Stand. Repeatable Read nutzt eine feste Commit-ID beim Start. Serializable prüft die gelesenen Tabellen. Alle nutzen optimistic locking auf Tabellenebene.
  6. Multi-Table-Transaktion: Ein Nessie-Commit kann viele Tabellen ändern. Iceberg selbst committet aber pro Tabelle. Die Iceberg-Doku sagt darum, dass Branch und Merge keine echte Datenbank-Transaktion sind. Sie kommen ihr aber nahe.
  7. Iceberg Snapshots vs Nessie Commits: Ein Iceberg Snapshot versioniert eine Tabelle. Ein Nessie Commit versioniert den ganzen Catalog. Time Travel über mehrere Tabellen geht nur mit Nessie.
  8. Version Store Backends (nessie.version.store.type): IN_MEMORY ist der Standard und gilt nur für Entwicklung und Tests. ROCKSDB ist produktiv, aber nur für einen Knoten. JDBC2 mit PostgreSQL ist produktionsreif. MariaDB, MySQL und CockroachDB sind experimentell.
  9. Weitere Backends: MONGODB2 und BIGTABLE sind produktiv. DYNAMODB ist Beta. CASSANDRA2 ist experimentell. Der alte Typ JDBC ist zur Entfernung vorgesehen.
  10. Iceberg REST Catalog: Nessie spricht auch die Iceberg-REST-Spezifikation unter /iceberg. Dann braucht der Client keine Nessie-Bibliothek. Nessie kann kurzlebige S3-Zugangsdaten ausgeben (Credential Vending). Es kann auch S3-Requests signieren (Request Signing).
  11. Warehouses: Mit REST konfiguriert der Server die Speicherorte. Dafür gibt es nessie.catalog.default-warehouse und nessie.catalog.warehouses.<name>.location. Die S3-Einstellungen stehen unter nessie.catalog.service.s3.*.
  12. Nessie GC: Iceberg-Prozeduren wie expire_snapshots kennen nur einen Stand der Tabelle. Eine Datei kann auf einem anderen Branch noch gebraucht werden. Nessie GC geht alle benannten References durch (mark). Danach löscht es nicht mehr gebrauchte Dateien (sweep). Die Iceberg-Doku warnt, dass Tabellenwartung mit Nessie komplizierter ist.

4. Fallen

  • „Nessie speichert die Daten.“ → Falsch. Nessie speichert nur Zeiger auf Iceberg-Metadaten. Die Dateien liegen im Object Store.
  • „Ein Branch kopiert die Tabellen.“ → Falsch. Ein Branch ist nur ein Zeiger. Es wird nichts kopiert.
  • „RocksDB ist für Produktion ungeeignet.“ → Ungenau. Laut Doku produktionsfähig, aber nur ein Knoten. Auf Kubernetes ohne festes Volume ist es riskant.
  • „Iceberg-Snapshots und Nessie-Commits sind dasselbe.“ → Falsch. Ein Snapshot gilt für eine Tabelle, ein Commit für den ganzen Catalog.
  • „expire_snapshots räumt mit Nessie alles sicher auf.“ → Falsch. Es kennt keine anderen Branches. Dafür gibt es Nessie GC.
  • „Mit Nessie hat Iceberg echte ACID-Transaktionen über Tabellen.“ → Ungenau. Branch und Merge kommen nahe, aber die Iceberg-Doku nennt es keine echte Multi-Table-Transaktion.

5. Selbsttest

Warum?

Warum PostgreSQL statt RocksDB auf Kubernetes?

RocksDB liegt lokal und nur auf einem Knoten. Ein Pod-Reschedule kann den Zustand verlieren. PostgreSQL ist extern, gesichert und hochverfügbar machbar.

Warum ist expire_snapshots mit Nessie heikel?

Es sieht nur einen Stand der Tabelle. Andere Branches können die Dateien noch brauchen. Nessie GC prüft alle References.

Warum kostet ein Nessie-Branch nichts?

Ein Branch ist nur ein beweglicher Zeiger auf einen Commit. Es wird keine Datei kopiert.

Wie innen?

Was ist Project Nessie?

Ein transaktionaler Catalog für Iceberg mit Git-ähnlicher Versionierung: Commits, Branches, Tags und Merges über alle Tabellen.

Was speichert Nessie für eine Iceberg-Tabelle?

Einen Zeiger auf die Metadaten-Datei und die IDs von Snapshot, Schema, Partition Spec und Sort Order. Die Daten selbst nicht.

Was ist ein Branch in Nessie?

Ein beweglicher, benannter Zeiger auf einen Commit. Neue Commits schieben ihn weiter. Er kopiert keine Daten.

Was ist ein Tag?

Ein fester Name für einen Commit. Er bewegt sich nicht. Gut für Audits und reproduzierbare Reports.

Was steht in einem Nessie-Commit?

Operationen Put, Delete oder Unmodified für Content Keys, also Tabellennamen. Ein Commit kann viele Tabellen umfassen.

Wie erkennt Nessie Konflikte?

Der Client nennt den erwarteten Hash. Hat sich die Tabelle seitdem geändert, kommt eine NessieConflictException. Das ist optimistic locking.

Welche Isolationsstufen bietet Nessie?

Read Committed, Repeatable Read und Serializable. Alle mit optimistic locking auf Tabellenebene.

Spricht Nessie die Iceberg REST API?

Ja, unter /iceberg. Der Branch steht im Pfad. Dazu Credential Vending oder S3 Request Signing.

Wie konfiguriert man Spark für Nessie?

Iceberg SparkCatalog mit type=nessie, uri auf /api/v2, ref für den Branch und warehouse. Dazu die Iceberg- und Nessie-SQL-Extensions.

Wie funktioniert Nessie GC?

Mark: alle benannten References durchgehen und lebende Inhalte sammeln. Sweep: nicht mehr gebrauchte Dateien löschen. Eine Cutoff-Policy legt fest, wie weit zurück Inhalte lebend bleiben.

Zahlen

Welche Version Stores gibt es?

IN_MEMORY (nur Tests), ROCKSDB (ein Knoten), JDBC2 mit PostgreSQL, MONGODB2, BIGTABLE, dazu DynamoDB (Beta) und Cassandra (experimentell).

Auf welchem Port läuft der Nessie Server?

Standardmässig auf Port 19120, mit REST API.

Wie viele Isolationsstufen bietet Nessie?

Drei: Read Committed, Repeatable Read und Serializable. Alle mit optimistic locking auf Tabellenebene.

Vergleich

Iceberg Snapshot vs Nessie Commit?

Ein Snapshot versioniert eine Tabelle. Ein Commit versioniert den ganzen Catalog, also alle Tabellen zusammen.

Nessie vs Hive Metastore?

Hive Metastore kennt keine Versionierung über Tabellen. Nessie hat Commits, Branches und Tags für den ganzen Catalog.

Nessie vs Iceberg-Branches?

Iceberg-Branches gelten für eine Tabelle. Nessie-Branches gelten für alle Tabellen im Catalog.

Credential Vending vs Request Signing?

Vending gibt dem Client kurzlebige, eingeschränkte S3-Zugangsdaten. Signing signiert jeden Request auf dem Server. Signing nur, wenn der Object Store kein STS hat.

Was ist der Unterschied zwischen JDBC und JDBC2?

JDBC ist der alte Typ und zur Entfernung vorgesehen. JDBC2 ist der aktuelle, mit PostgreSQL produktionsreif.

Produktion

Szenario: Nach einem Node-Wechsel sieht Dremio keine Tabellen mehr, die Dateien in MinIO sind da. Ursache?

Nessie lief mit RocksDB oder IN_MEMORY ohne festes Volume und hat den Zustand verloren. Lösung: PostgreSQL als Version Store, Tabellen neu registrieren, Backups einrichten.

Szenario: Zwei Spark-Jobs bekommen abwechselnd Commit-Konflikte. Was tun Sie?

Prüfen, ob sie dieselbe Tabelle schreiben. Dann Retry mit neuem Stand, Jobs serialisieren, z. B. mit einem atomaren Claim, oder auf getrennte Partitionen und Branches verteilen.

Was passiert, wenn der Version Store verloren geht?

Die Dateien liegen noch im Object Store, aber kein Catalog zeigt mehr darauf. Tabellen müssen aus Metadaten-Dateien neu registriert werden. Darum Backups.

Design

Wie bekommt man eine Multi-Table-Transaktion mit Nessie?

Auf einem Branch mehrere Tabellen ändern, prüfen, dann nach main mergen. Leser auf main sehen alle Änderungen gleichzeitig.

Szenario: Silver und Gold müssen für Leser immer zusammenpassen. Wie lösen Sie das?

Pro Lauf einen Nessie-Branch, beide Tabellen dort schreiben und prüfen, dann nach main mergen. Leser lesen nur main.

Was geht kaputt, wenn Nessie mit RocksDB ohne festes Volume läuft?

RocksDB liegt auf der lokalen Platte des Pods und nutzt nur einen Knoten. Ein Reschedule kann den Zustand verlieren. Lösung: PostgreSQL als Version Store.

Mehr

Gerüst

  • Warum? Mehrere Tabellen sollen für Leser gleichzeitig wechseln. Branch, prüfen, mergen.
  • Wie innen? Catalog = Name → aktuelle Metadaten-Datei. Commit nennt expectedHash (optimistic locking). Branch ist nur ein Zeiger, Nessie speichert keine Daten.
  • Zahlen Server auf Port 19120. 3 Isolationsstufen. Version Store: PostgreSQL (JDBC2) produktiv, RocksDB nur 1 Knoten.
  • Vergleich Iceberg Snapshot (eine Tabelle) vs Nessie Commit (ganzer Catalog). Nessie vs Hive Metastore. Credential Vending vs Request Signing.
  • Produktion RocksDB ohne festes Volume → Zustand weg. expire_snapshots kennt andere Branches nicht → Nessie GC. Commit-Konflikte bei zwei Jobs.
  • Design Pro Lauf ein Branch, dann nach main mergen. PostgreSQL als Version Store mit Backups. Keine echte Multi-Table-Transaktion.

Beispiel: Branch, Commit, Merge mit Spark SQL

# Spark-Konfiguration (laut Iceberg-Doku)
spark.sql.extensions = org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions,
                       org.projectnessie.spark.extensions.NessieSparkSessionExtensions
spark.sql.catalog.nessie           = org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.nessie.type      = nessie
spark.sql.catalog.nessie.uri       = http://nessie:19120/api/v2
spark.sql.catalog.nessie.ref       = main
spark.sql.catalog.nessie.warehouse = s3://lakehouse/warehouse

-- SQL (Nessie Spark SQL Extensions)
CREATE BRANCH IF NOT EXISTS etl_run IN nessie FROM main;
USE REFERENCE etl_run IN nessie;
INSERT INTO nessie.silver.trades SELECT ...;
INSERT OVERWRITE nessie.gold.stats SELECT ...;
SHOW LOG etl_run IN nessie;
MERGE BRANCH etl_run INTO main IN nessie;
CREATE TAG IF NOT EXISTS release_2026_11 IN nessie FROM main;

Erwartetes Ergebnis (laut Nessie-Doku, nicht ausgeführt; hier läuft kein Nessie): CREATE BRANCH gibt Typ, Name und Commit-Hash zurück. SHOW LOG listet die Commits mit Hash, Autor und Nachricht. Nach dem Merge zeigt main beide neuen Tabellenstände.

  1. Extensions: Die Nessie-Extensions bringen die Befehle CREATE BRANCH, MERGE BRANCH usw. Ihre Version muss zur Nessie-Version passen.
  2. uri zeigt auf die Nessie API v2. ref ist der Standard-Branch. warehouse ist der Basispfad für neue Tabellen.
  3. USE REFERENCE stellt die Session auf den Branch um. Alle folgenden Schreibvorgänge landen dort.
  4. MERGE BRANCH macht beide Tabellen auf main sichtbar. Vorher sehen Leser auf main nichts davon.
  5. Alternative heute: Nessie bietet auch eine Iceberg REST-Schnittstelle unter /iceberg. Der Client setzt dann type=rest und uri=http://nessie:19120/iceberg. Einen Branch wählt man über den Pfad, z. B. /iceberg/etl_run.

Vergleich

  • Nessie: Branches, Tags, Commits über alle Tabellen. Eigener Dienst mit eigener Datenbank.
  • Hive Metastore: klassischer Catalog, keine Versionierung über Tabellen. Braucht eine eigene Datenbank und Thrift.
  • JDBC Catalog (Iceberg): einfache Tabelle in einer SQL-Datenbank mit Zeigern. Keine Branches über Tabellen.
  • REST Catalog (z. B. Apache Polaris, Unity Catalog): Standard-API für viele Engines, Rechte zentral. Nessie bietet diese API ebenfalls.
  • Iceberg-Branches (pro Tabelle): Branches und Tags auf Snapshots einer Tabelle. Gut für WAP einer Tabelle, nicht für mehrere Tabellen gemeinsam.
  • Nessie vs Git: Gleiche Ideen (Commit, Branch, Tag, Merge). Aber Nessie hat keinen lokalen Klon, versioniert nur Metadaten-Zeiger und arbeitet als Server.

In der Produktion

  1. Catalog-Zustand weg nach Pod-Neustart: RocksDB liegt auf der lokalen Platte. Wird der Pod auf einen anderen Knoten verschoben, fehlen die Zeiger. Die Dateien im Object Store sind noch da, aber keine Tabelle findet sie. Lösung: PostgreSQL als Version Store (JDBC2).
  2. IN_MEMORY in Produktion: Jeder Neustart löscht den Catalog. Lösung: nie ausserhalb von Tests.
  3. Commit-Konflikte: Zwei Jobs schreiben gleichzeitig dieselbe Tabelle auf main. Einer bekommt einen Konflikt. Lösung: Retry mit neuem Stand, Jobs serialisieren oder Branch pro Lauf.
  4. Speicher wächst trotz expire_snapshots: Andere Branches oder Tags halten alte Dateien. Lösung: Branches aufräumen, Nessie GC einsetzen.
  5. Versionsmix: Spark-Extensions passen nicht zur Server-Version. Fehler bei SQL-Befehlen. Lösung: Versionen gemeinsam pinnen, z. B. im Helm-Chart und im Spark-Image.
  6. Backup vergessen: Der Version Store ist der wichtigste Teil. Ohne ihn sind alle Tabellen nur lose Dateien. Lösung: Datenbank-Backups wie bei jeder Produktions-DB.

Diagnose: Befehle und Werkzeuge

  • LIST REFERENCES IN nessie: alle Branches und Tags mit Hash.
  • SHOW LOG main IN nessie: Commit-Historie eines Branches.
  • MERGE DRY BRANCH etl_run INTO main IN nessie: Merge testen, ohne ihn auszuführen.
  • REST API: GET http://nessie:19120/api/v2/trees listet References.
  • Nessie Web UI und Nessie CLI: Branches und Inhalte ansehen.
  • Logs und Health: Management-Port 9000 (Quarkus) für Health und Metriken. Dazu die Logs der Version-Store-Datenbank.

Senior-Punkte

  1. Der Catalog ist der wertvollste Teil des Lakehouse. Ohne ihn sind Parquet-Dateien nur Dateien. Er braucht HA, Backups und eine echte Datenbank.
  2. Backend nach Betriebsmodell wählen. RocksDB ist nur ein Knoten auf lokaler Platte. In Kubernetes ist PostgreSQL meist die richtige Wahl.
  3. Branches sind billig, aber nicht gratis. Jeder offene Branch hält Dateien fest. Kurzlebige Branches mit klarer Aufräumregel.
  4. Multi-Table-Konsistenz ist der Hauptgrund für Nessie. Braucht man sie nicht, reicht oft ein einfacher REST- oder JDBC-Catalog.
  5. Wartung mit Nessie planen. Iceberg-Prozeduren sehen nur einen Stand. Für Branch-übergreifendes Aufräumen gibt es Nessie GC.
  6. REST-Catalog macht Engines austauschbar. Mit der Iceberg-REST-API braucht keine Engine eine Nessie-Bibliothek.
