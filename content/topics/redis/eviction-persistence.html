Eviction, TTL und Persistenz

Kern: Redis hält alle Daten im Speicher. Mit maxmemory und einer Eviction-Policy löscht es bei vollem Speicher Schlüssel. Mit TTL laufen einzelne Schlüssel von selbst ab. RDB (Snapshots) und AOF (Log jeder Änderung) schreiben die Daten auf Platte, damit sie einen Neustart überleben.

Antwort-Muster

Frage: Was passiert, wenn Redis voll ist, und wie überstehen Daten einen Neustart?

  1. Mechanismus: Bei Erreichen von maxmemory löscht Redis nach der Policy Schlüssel. Für den Neustart gibt es RDB-Snapshots und das AOF-Log.
  2. Zahl: maxmemory ist standardmässig 0, also unbegrenzt. Das AOF schreibt standardmässig jede Sekunde auf Platte (everysec).
  3. Trade-off: allkeys-lru eignet sich für Caches. Mit noeviction lehnt Redis neue Schreibzugriffe ab. AOF ist sicherer, RDB schneller beim Start.
  4. Produktion: Für Caches nehme ich eine Policy und TTL. Für Daten, die nicht verloren gehen dürfen, nehme ich RDB und AOF zusammen.

1. Eviction in 5 Schritten

  1. Befehl kommt: Ein Client führt einen Befehl aus, der Daten hinzufügt.
  2. Speicher prüfen: Bei jedem solchen Befehl prüft Redis die Speichernutzung gegen maxmemory.
  3. Policy fragen: Bei noeviction bekommt der Client einen Fehler. Sonst wählt Redis nach maxmemory-policy Schlüssel zum Löschen.
  4. Kandidaten ziehen: LRU und LFU sind Näherungen. Redis zieht eine kleine Stichprobe (maxmemory-samples, Standard 5) und löscht den schlechtesten Kandidaten.
  5. Wiederholen: Redis löscht, bis die Nutzung wieder unter dem Limit liegt. Ein einzelner grosser Befehl kann das Limit kurz weit überschreiten.

2. Aufbau

  1. maxmemory: Die Grenze für die Daten. Der Standard ist 0, also keine Grenze (64-Bit-Systeme).
  2. Eviction-Policy: Sie bestimmt, welche Schlüssel bei vollem Speicher gehen. Es gibt allkeys-* und volatile-*.
  3. TTL: Ein Schlüssel kann eine Lebensdauer haben. Danach löscht Redis ihn.
  4. RDB: Ein Snapshot des ganzen Datenbestands zu einem Zeitpunkt in einer Datei.
  5. AOF: Ein Log aller schreibenden Befehle. Beim Start spielt Redis es ab.
  6. Beides: RDB und AOF können zusammen laufen. Beim Neustart gilt das AOF als vollständiger.

3. Details

  1. maxmemory: Standard 0 auf 64-Bit-Systemen, also unbegrenzt. 32-Bit-Systeme haben eine implizite Grenze von 3 GB. Man setzt sie in redis.conf oder mit CONFIG SET.
  2. Puffer zählen nicht mit: Der Speicher für Replikations- und AOF-Puffer wird nicht mit maxmemory verglichen. Sonst gäbe es eine Rückkopplung mit unnötigen Löschungen. Man lässt darum etwas RAM frei.
  3. Policies: noeviction lehnt Schreiben mit Fehler ab. allkeys-lru, allkeys-lfu, allkeys-random wählen unter allen Schlüsseln. volatile-* wählt nur Schlüssel mit TTL. volatile-ttl nimmt die kürzeste Restzeit. Gibt es keine Schlüssel mit TTL, verhält sich volatile-* wie noeviction.
  4. Welche Policy? Die Doku nennt allkeys-lru einen guten Standard, wenn ein Teil der Schlüssel viel öfter gelesen wird. allkeys-random passt bei gleichmässigem Zugriff. Ein TTL kostet Speicher, darum ist allkeys-lru sparsamer als volatile-lru.
  5. Approximiertes LRU: Redis zieht eine Stichprobe und löscht den Schlüssel mit der längsten Zeit seit dem letzten Zugriff. Seit 3.0 gibt es einen Pool guter Kandidaten. maxmemory-samples ist 5. Mit 10 kommt es nahe an echtes LRU, kostet aber mehr CPU.
  6. LFU: Seit Redis 4.0 zählt Redis die Zugriffshäufigkeit mit einem Morris-Zähler (0 bis 255) und lässt ihn zerfallen. Standard: lfu-log-factor 10, lfu-decay-time 1 Minute. Der Zähler sättigt bei etwa einer Million Zugriffen.
  7. LRM und Schutz: Seit Redis 8.6 gibt es LRM (zuletzt geändert), das nur bei Schreibzugriffen den Zeitstempel erneuert. Seit 8.12 schützt BLESS SET einzelne Schlüssel vor Eviction.
  8. TTL setzen: EXPIRE ist O(1). Optionen NX, XX, GT, LT gibt es seit 7.0.0. Ein TTL von null oder ein vergangener Zeitpunkt löscht den Schlüssel sofort.
  9. TTL löschen oder erhalten: DEL, SET und *STORE-Befehle löschen den TTL. INCR, LPUSH und HSET lassen ihn bestehen. PERSIST macht den Schlüssel dauerhaft. RENAME überträgt den TTL.
  10. Ablauf passiv und aktiv: Passiv: Beim Zugriff auf einen abgelaufenen Schlüssel löscht Redis ihn. Aktiv: Redis prüft regelmässig eine zufällige Stichprobe von Schlüsseln mit TTL. Die Genauigkeit liegt seit 2.6 bei 0 bis 1 Millisekunde.
  11. TTL, Replikation und AOF: Läuft ein Schlüssel ab, schreibt der Master ein DEL ins AOF und an die Replicas. Replicas löschen nicht selbständig. Der Ablauf wird als absoluter Zeitstempel gespeichert, die Uhr muss darum stimmen.
  12. RDB und AOF: RDB ist eine kompakte Punkt-in-Zeit-Datei, gut für Backups und schnelle Starts. Der Elternprozess macht nur fork(), das Kind schreibt. AOF loggt jede Änderung. appendfsync hat always, everysec (Standard) und no. Mit everysec gehen höchstens etwa 1 Sekunde Schreibzugriffe verloren.

4. Fallen

  • „Redis löscht bei vollem Speicher automatisch alte Schlüssel.“ → Falsch. Nur mit einer Policy ausser noeviction. Mit noeviction lehnt Redis neue Schreibzugriffe ab, und maxmemory ist standardmässig 0.
  • „volatile-lru schützt mich vor einem vollen Speicher.“ → Falsch. Hat kein Schlüssel einen TTL, verhält es sich wie noeviction. Schreiben schlägt dann fehl.
  • „SET auf einen Schlüssel mit TTL behält den TTL.“ → Falsch. SET überschreibt den Wert und löscht den TTL. INCR und HSET erhalten ihn.
  • „Mit RDB verliere ich höchstens eine Sekunde.“ → Falsch. RDB macht Snapshots in Abständen, oft alle paar Minuten. Dann gehen die letzten Minuten verloren. Die Sekunde gilt für AOF mit everysec.
  • „Redis berechnet echtes LRU.“ → Falsch. Es ist eine Näherung mit Stichprobe, weil echtes LRU mehr Speicher kostet.
  • „Der AOF-Schreibpuffer zählt zu maxmemory.“ → Falsch. Puffer für AOF und Replikation sind ausgenommen. Man lässt darum Reserve frei.

5. Selbsttest

Warum?

Warum braucht ein Cache eine Eviction-Policy?

Ein Cache hält Kopien von Daten. Wird der Speicher voll, ist Löschen unkritisch, weil die Daten neu geladen werden können. Ohne Policy lehnt Redis bei noeviction neue Daten ab.

Warum setzt man TTLs?

Sie begrenzen das Alter von Daten und halten den Speicher klein. Wer TTLs gut nutzt, stösst seltener ans maxmemory-Limit.

Warum nutzt man RDB und AOF zusammen?

Die Doku sagt: Für eine Sicherheit wie bei PostgreSQL nimmt man beides. AOF gibt Haltbarkeit, RDB gibt Backups und schnellere Starts.

Wie innen?

Wie wählt Redis Schlüssel für die Eviction?

Es zieht eine zufällige Stichprobe (maxmemory-samples, Standard 5) und löscht den schlechtesten nach der Policy. Das ist approximiertes LRU oder LFU.

Wie funktioniert der Ablauf eines Schlüssels?

Passiv: Beim Zugriff auf einen abgelaufenen Schlüssel löscht Redis ihn. Aktiv: Redis prüft laufend Stichproben von Schlüsseln mit TTL und löscht abgelaufene.

Was passiert bei einem RDB-Snapshot?

Redis macht fork(). Das Kind schreibt die Daten in eine temporäre Datei und ersetzt dann die alte. Der Elternprozess macht kein Disk-I/O. Es gilt Copy-on-Write.

Was ist ein AOF-Rewrite?

Das Log wächst. Beim Rewrite schreibt ein Kind die kürzeste Befehlsfolge, die den aktuellen Bestand baut. Redis tauscht dann atomar. Seit 7.0 gibt es eine Base-Datei plus Incr-Dateien und ein Manifest.

Was passiert, wenn ein Schlüssel abläuft, mit AOF und Replicas?

Der Master schreibt ein DEL ins AOF und schickt es an die Replicas. Replicas löschen nicht selbständig, sie warten auf das DEL.

Wie lädt Redis nach einem Neustart, wenn beides an ist?

Aus dem AOF, weil es garantiert das vollständigste ist.

Zahlen

Was ist der Standard von maxmemory?

0, also keine Grenze, auf 64-Bit-Systemen. 32-Bit-Systeme haben implizit 3 GB.

Was sind die Standards bei LRU und LFU?

maxmemory-samples 5. lfu-log-factor 10, lfu-decay-time 1. Der LFU-Zähler geht von 0 bis 255.

Wie viel Daten kann man mit appendfsync everysec verlieren?

Höchstens etwa eine Sekunde Schreibzugriffe. Mit always praktisch keine, mit no entscheidet der Kernel, unter Linux oft etwa 30 Sekunden.

Wie genau läuft ein Ablauf ab?

Seit Redis 2.6 mit einem Fehler von 0 bis 1 Millisekunde.

Vergleich

allkeys-lru vs volatile-lru?

allkeys-lru wählt unter allen Schlüsseln und braucht keinen TTL. volatile-lru wählt nur Schlüssel mit TTL, hat aber Speicherkosten für den TTL und verhält sich ohne TTL-Schlüssel wie noeviction.

LRU vs LFU?

LRU löscht, was am längsten nicht benutzt wurde. LFU löscht, was am seltensten benutzt wird. LFU kann bei manchen Mustern eine bessere Trefferquote geben. Im Beispiel erreichte LFU 67.5 % gegen 66.5 %.

RDB vs AOF?

RDB: kompakt, schneller Start, aber Verlust der letzten Minuten möglich. AOF: höchstens etwa 1 Sekunde Verlust, grösser und je nach fsync langsamer.

Eviction vs TTL?

TTL gilt pro Schlüssel und löscht nach Zeit. Eviction greift bei vollem Speicher und löscht nach Policy, bei allkeys auch Schlüssel ohne TTL.

Produktion

Was tun, wenn Redis „OOM command not allowed“ meldet?

Der Speicher ist voll und die Policy ist noeviction oder volatile ohne TTL-Schlüssel. Lösung: Policy wählen (zum Beispiel allkeys-lru), TTLs setzen oder maxmemory prüfen.

Was tun, wenn die Trefferquote des Caches sinkt?

Mit INFO stats keyspace_hits und keyspace_misses prüfen. Dann evicted_keys und expired_keys ansehen. Viele Evictions deuten auf die falsche Policy oder zu wenig Speicher, viele Expires auf zu kurze TTLs.

Szenario: Redis ist langsam, jedes Mal wenn ein Snapshot läuft. Was tun Sie?

Der fork() kann bei grossen Datenmengen Millisekunden bis eine Sekunde stören. Ich prüfe die Datengrösse, die Häufigkeit der save-Punkte und ob AOF reicht. Eine kleinere Instanz oder Replicas für die Snapshots helfen.

Szenario: Nach einem Absturz ist das AOF abgeschnitten. Was tun Sie?

Moderne Redis-Versionen laden es trotzdem und verwerfen den letzten unvollständigen Befehl. Ist die Datei in der Mitte beschädigt, bricht Redis ab. Dann sichere ich die Datei und nutze redis-check-aof, zuerst ohne --fix.

Design

Wie konfigurieren Sie Redis als reinen Cache?

maxmemory setzen, Policy allkeys-lru, TTL auf Schlüsseln, keine Persistenz oder nur RDB. Dazu etwas RAM für Puffer frei lassen.

Wie konfigurieren Sie Redis für Daten, die nicht verloren gehen dürfen?

noeviction, damit nichts gelöscht wird. RDB und AOF mit everysec, Backups ausser Haus. Und die Daten gehören im Zweifel in eine Datenbank, Redis ist dann Kopie.

Wie mischen Sie Cache und dauerhafte Schlüssel in einer Instanz?

Mit volatile-lru, nur Cache-Schlüssel haben TTL. Die Doku rät aber zu zwei getrennten Instanzen, wenn möglich.

Wie sichern Sie Redis?

Die RDB-Datei darf man bei laufendem Server kopieren, sie wird atomar ersetzt. Täglich eine Kopie ausserhalb des Rechenzentrums. Bei reinem AOF vorher automatische Rewrites abschalten.

Mehr

Gerüst

  • Warum? Speicher ist begrenzt, Daten sollen ablaufen oder einen Neustart überleben.
  • Wie innen? Eviction: Stichprobe, schlechtester Kandidat. TTL: passiv und aktiv. RDB: fork. AOF: Log mit fsync.
  • Zahlen maxmemory 0, samples 5, everysec etwa 1 s Verlust, Ablauf 0 bis 1 ms.
  • Vergleich allkeys gegen volatile. LRU gegen LFU. RDB gegen AOF.
  • Produktion OOM bei noeviction. fork-Spitzen. Abgeschnittenes AOF.
  • Design Cache: allkeys-lru plus TTL. Wichtige Daten: AOF plus RDB.

Beispiel: Eviction-Policies im Modell vergleichen

KEYS, CAP, N = 10_000, 1_000, 60_000        # Schlüssel, Cache-Grösse, Zugriffe
weights = [1 / (i + 1) for i in range(KEYS)]  # wenige Schlüssel sind sehr beliebt
# Nach der Hälfte wechselt die Beliebtheit auf andere Schlüssel (neue Permutation)

noeviction            # voll: neue Schlüssel werden abgelehnt
random                # zufälliges Opfer
approx-lru, samples=1/5/10   # Stichprobe, ältester Zugriff verliert
true-lru              # exakt, teuer
approx-lfu, samples=5 # Stichprobe, seltenster Zugriff verliert (exakter Zähler)
Zugriffe: 60,000, Schluessel: 10,000, Cache: 1,000 Eintraege, Beliebtheit wechselt nach der Haelfte
noeviction             hit rate  38.5 %   evicted      0   rejected writes 35,883
random                 hit rate  62.6 %   evicted 21,448   rejected writes      0
approx-lru samples=1   hit rate  62.6 %   evicted 21,448   rejected writes      0
approx-lru samples=5   hit rate  66.5 %   evicted 19,098   rejected writes      0
approx-lru samples=10  hit rate  66.8 %   evicted 18,924   rejected writes      0
true-lru               hit rate  66.9 %   evicted 18,844   rejected writes      0
approx-lfu samples=5   hit rate  67.5 %   evicted 18,485   rejected writes      0

Echte Ausgabe, Python 3.12.10. Es ist ein Modell, nicht Redis selbst. Der LFU-Zähler ist exakt und ohne Zerfall, anders als der Morris-Zähler in Redis. Der Pool guter Kandidaten fehlt im Modell.

  1. noeviction hat nur 38.5 % Treffer, weil der Cache mit den alten beliebten Schlüsseln gefüllt bleibt. 35 883 Schreibzugriffe wurden abgelehnt.
  2. random erreicht 62.6 %. Das ist der Boden für Policies mit Löschen.
  3. Approximiertes LRU wird mit mehr Stichproben besser: 62.6 % bei 1, 66.5 % bei 5, 66.8 % bei 10. Das echte LRU erreicht 66.9 %.
  4. Schon mit 5 Stichproben liegt die Näherung nahe an echtem LRU, mit 10 noch näher. Das passt zur Doku: Mit 10 Stichproben nähert Redis echtes LRU an, kostet aber etwas mehr CPU.
  5. LFU erreicht hier 67.5 %. Bei diesem Zugriffsmuster mit stabil beliebten Schlüsseln hilft die Häufigkeit.
  6. Nach dem Wechsel der Beliebtheit passen sich LRU und LFU an. noeviction nicht.

Vergleich

  • noeviction: nichts wird gelöscht, neue Schreibzugriffe schlagen fehl. Für Daten, die nicht weg dürfen.
  • allkeys-lru: Standardwahl für Caches mit ungleichem Zugriff.
  • allkeys-lfu: nach Häufigkeit. Gut bei stabil beliebten Schlüsseln.
  • volatile-ttl: löscht Schlüssel mit der kürzesten Restzeit. Nur Schlüssel mit TTL.
  • RDB: Snapshot, kompakt. AOF: Log, haltbarer. Beides: Empfehlung der Doku für hohe Sicherheit.
  • Kein Persistenz: erlaubt für reine Caches.

Produktion

  1. OOM-Fehler: Der Speicher ist voll bei noeviction. Lösung: Policy wählen, TTLs setzen, maxmemory und Grösse prüfen.
  2. Kein Platz für Puffer: maxmemory ist gleich dem ganzen RAM. Replikations- und AOF-Puffer zählen nicht mit. Lösung: RAM für Puffer frei lassen (mem_not_counted_for_evict in INFO).
  3. fork-Spitzen: Bei grossen Datenmengen kann fork() Millisekunden bis eine Sekunde stören. Lösung: weniger Snapshots, kleinere Instanzen, Snapshots auf Replicas.
  4. Daten nach Absturz fehlen: RDB allein verliert die letzten Minuten. Lösung: AOF mit everysec zusätzlich.
  5. AOF abgeschnitten oder defekt: Lösung: redis-check-aof, zuerst ohne --fix, Datei vorher sichern.
  6. Uhr falsch: Ablaufzeiten sind absolute Zeitstempel. Eine RDB-Datei auf einem Rechner mit falscher Uhr kann viele Schlüssel sofort ablaufen lassen. Lösung: Uhr per NTP stabil halten.

Diagnose: Werkzeuge und Befehle

  • INFO stats: keyspace_hits, keyspace_misses, evicted_keys, expired_keys. Trefferquote = hits / (hits + misses).
  • INFO memory: used_memory_dataset, mem_not_counted_for_evict.
  • INFO persistence: aof_rewrite_in_progress, aof_last_bgrewrite_status.
  • CONFIG GET maxmemory* und CONFIG SET maxmemory-policy ...: Policy prüfen und im Betrieb ändern.
  • TTL key: Restzeit in Sekunden. -1 heisst kein TTL.
  • redis-check-aof: prüft und repariert ein AOF.

Senior-Punkte

  1. Cache oder Datenspeicher? Das bestimmt Policy und Persistenz. Ein Cache darf löschen, ein Speicher nicht.
  2. Trefferquote messen, nicht raten. evicted_keys und expired_keys zeigen, ob Policy oder TTL das Problem ist.
  3. Reserve einplanen. Puffer für Replikation und AOF zählen nicht zu maxmemory, und ein grosser Befehl kann das Limit kurz überschreiten.
  4. RDB und AOF sind verschiedene Versprechen: Backup und Startgeschwindigkeit gegen Haltbarkeit. Bei wichtigen Daten beides.
  5. Backups testen. Eine Kopie, die man nie wiederhergestellt hat, ist keine Sicherung.
  6. Redis ersetzt keine Datenbank, wenn Daten nicht verloren gehen dürfen. Es ist dann eine schnelle Kopie.
