Cache-Muster

Kern: Ein Cache ist eine schnelle Kopie von Daten, die eigentlich in einer langsameren Quelle liegen, z. B. in PostgreSQL. Cache-Muster legen fest, wer den Cache füllt, wann er aktualisiert wird und wie veraltete Daten verschwinden. Die schwierigsten Fragen sind Invalidierung und Stampedes, nicht das Speichern.

1. Wo sitzt der Cache?

  1. Source of Truth: die Datenbank. Nur sie ist verbindlich. Der Cache darf jederzeit leer sein.
  2. L2: verteilter Cache wie Redis: ein In-Memory-Key-Value-Store, den alle Pods teilen. Ein Netzwerk-Hop, aber kein Plattenzugriff.
  3. L1: lokaler Cache wie Caffeine: im Heap jedes Pods. Am schnellsten, aber jede Instanz hat ihre eigene Kopie.
  4. TTL (Time To Live): Ablaufzeit eines Eintrags. Danach löscht Redis den Schlüssel.
  5. Eviction: Ist der Speicher voll, entfernt Redis Schlüssel nach einer Policy, z. B. die am längsten nicht genutzten.

2. Die Reise eines Reads mit Cache-Aside (und ein Stampede)

  1. Lesen aus dem Cache: Die App fragt Redis mit GET produkt:42. Ist der Wert da (Hit), ist sie nach unter einer Millisekunde fertig.
  2. Miss: Der Wert fehlt. Die App liest aus der Datenbank.
  3. Füllen: Die App schreibt den Wert mit TTL: SET produkt:42 {...} EX 600.
  4. Antwort: Der nächste Request bekommt einen Hit.
  5. Stampede: Läuft die TTL eines sehr gefragten Schlüssels ab, gibt es viele Misses gleichzeitig. Alle fragen die DB. Die DB bricht unter der Last ein. Das heisst auch Thundering Herd oder Dogpile.
  6. Schutz: Nur ein Request lädt neu (Lock), die anderen warten kurz oder bekommen den alten Wert.

3. Beispiel: Stampede messen und mit SET NX verhindern

# stampede.py (gekürzt): Redis-Ersatz im Speicher, gleiche Logik
def naive(cache, k):                       # Cache-Aside ohne Schutz
    v = cache.get(k)
    if v is None:
        v = db_load(k); cache.set(k, v)    # db_load dauert 200 ms
    return v

def mit_lock(cache, k):                    # nur einer lädt
    while True:
        v = cache.get(k)
        if v is not None: return v
        if cache.set_nx(k):                # wie: SET lock:k 1 NX EX 10
            try:   v = db_load(k); cache.set(k, v); return v
            finally: cache.delete_lock(k)
        time.sleep(0.01)                   # kurz warten, erneut lesen

# 100 Threads fragen gleichzeitig "produkt:42" bei leerem Cache
$ python -I stampede.py
ohne Schutz        100 gleichzeitige Requests -> 100 DB-Abfragen, 238 ms
mit Lock (SET NX)  100 gleichzeitige Requests ->   1 DB-Abfragen, 212 ms

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Redis ist hier nicht installiert. Zahlen in INFO beispielhaft; TTL -1 nach SET und noeviction als Default laut redis.io und redis.conf.

  1. Ohne Schutz laden 100 Requests denselben Wert aus der DB. Mit Lock lädt einer. Die Gesamtzeit ist fast gleich, aber die DB-Last fällt um Faktor 100.
  2. SET ... NX EX 10 setzt den Lock nur, wenn er fehlt, und mit Ablauf. Stirbt der Halter, verschwindet der Lock nach 10 s von selbst.
  3. Der Lock-Wert ist eine eindeutige ID. Nur der Halter darf ihn löschen. Sonst löscht ein langsamer Pod den Lock eines anderen.
  4. Achtung: Ein SET ohne EX oder KEEPTTL löscht die TTL. Danach ist TTL = -1: Der Schlüssel lebt für immer.
  5. Default ist maxmemory-policy noeviction. Voll heisst dann: Schreibbefehle bekommen einen Fehler. Für einen Cache muss man eine Eviction-Policy wählen.
  6. Hit Rate = hits / (hits + misses) = 98,2 %. Ein Abfall zeigt falsche TTLs, falsche Policy oder Invalidierungs-Stürme.

4. Details, die Interviewer fragen

  1. Cache-Aside (Lazy Loading): Die App liest zuerst den Cache, bei Miss die DB, dann füllt sie den Cache. Beim Schreiben schreibt sie die DB und löscht den Cache-Eintrag. Das häufigste Muster. Spring @Cacheable und @CacheEvict setzen es um.
  2. Read-Through: Die App fragt nur den Cache. Der Cache selbst lädt bei Miss aus der DB über einen Loader. Beispiel: Caffeine LoadingCache. Code wird einfacher, der Cache braucht DB-Wissen.
  3. Write-Through: Jeder Write geht durch den Cache synchron in die DB. Cache und DB sind direkt konsistent. Preis: langsamere Writes, und selten gelesene Daten füllen den Cache.
  4. Write-Behind (Write-Back): Writes gehen in den Cache, die DB wird später asynchron und gebündelt aktualisiert. Sehr schnelle Writes. Risiko: Datenverlust, wenn der Cache vor dem Schreiben ausfällt, und schwierige Reihenfolge.
  5. Refresh-Ahead: Häufig gelesene Einträge werden vor Ablauf im Hintergrund neu geladen. Gut gegen Stampedes bei heissen Schlüsseln.
  6. TTL: begrenzt, wie alt ein Wert sein darf. Kurze TTL = frischer, aber mehr Misses. Lange TTL = mehr Hits, aber älter. TTL ist das Sicherheitsnetz, falls eine Invalidierung verloren geht.
  7. Ablauf in Redis: passiv (beim Zugriff wird ein abgelaufener Schlüssel gelöscht) und aktiv (Redis prüft regelmässig zufällige Schlüssel mit TTL). Abgelaufene Schlüssel sind nie sichtbar, belegen aber kurz Speicher.
  8. Eviction-Policies: noeviction (Default: Fehler beim Schreiben), allkeys-lru (Standardwahl für Caches), allkeys-lfu (selten genutzte zuerst), allkeys-random, volatile-lru/-lfu/-random/-ttl (nur Schlüssel mit TTL). Seit Redis 8.6 gibt es allkeys-lrm und volatile-lrm (zuletzt geändert).
  9. LRU ist angenähert: Redis prüft eine Stichprobe von Schlüsseln (maxmemory-samples, Default 5) und entfernt den ältesten davon. Das spart Speicher und ist praktisch fast so gut wie echtes LRU.
  10. volatile-* ohne TTL: Haben keine Schlüssel eine TTL, verhalten sich volatile-*-Policies wie noeviction.
  11. Stampede-Schutz:
    • Lock / Single Flight: Nur einer lädt (SET NX EX verteilt, oder lokal z. B. Caffeine, das pro Schlüssel nur einmal lädt).
    • TTL-Jitter: TTL zufällig streuen (z. B. 600 s ± 10 %), damit nicht alle Schlüssel gleichzeitig ablaufen.
    • Frühzeitiges Neu-Laden: Kurz vor Ablauf lädt ein Request mit wachsender Wahrscheinlichkeit neu (probabilistic early expiration).
    • Stale-While-Revalidate: Den alten Wert ausliefern und im Hintergrund neu laden.
  12. Invalidierung: Nach einem Write den Eintrag löschen, nicht neu schreiben. Grund: Zwei parallele Writes können den Cache sonst mit dem älteren Wert überschreiben. Reihenfolge: zuerst DB committen, dann löschen.
  13. Race beim Cache-Aside: Leser A liest alten Wert aus der DB. Schreiber B schreibt DB und löscht Cache. A schreibt danach den alten Wert in den Cache. Gegenmittel: kurze TTL, verzögertes zweites Löschen, oder Versionsnummern im Wert.
  14. Invalidierung über Events: Ein Service publiziert „produkt.geändert“ (z. B. Kafka, CDC mit Debezium). Alle Pods löschen ihren L1-Eintrag. Redis Pub/Sub geht auch, verliert aber Nachrichten bei Verbindungsabbruch.
  15. Cache Penetration: Anfragen nach Schlüsseln, die es nicht gibt, gehen immer an die DB. Lösung: auch „nicht gefunden“ kurz cachen (Negative Caching) oder Bloom-Filter.

5. Vergleich

  • Cache-Aside: App steuert alles, robust bei Cache-Ausfall. Erster Read ist immer ein Miss.
  • Read-Through: wie Cache-Aside, aber die Ladelogik sitzt im Cache. Sauberer Code.
  • Write-Through: Cache immer aktuell, Writes langsamer, Cache füllt sich mit Ungelesenem.
  • Write-Behind: schnellste Writes, Risiko Datenverlust. Nur für tolerante Daten wie Zähler.
  • Lokal (Caffeine) vs verteilt (Redis): Nanosekunden, aber pro Pod unterschiedlich vs geteilt, ein Netzwerk-Hop, eigener Betrieb.
  • Redis vs Memcached: Datentypen, Persistenz, Replikation, Lua vs nur Strings, einfacher, multithreaded.
  • Löschen vs Aktualisieren bei Writes: sicher gegen Races vs ein Miss weniger, aber Race-anfällig.

6. In der Produktion

  1. DB bricht nach Cache-Flush oder Redis-Neustart ein: Kalter Cache, alle Requests sind Misses. Lösung: Warm-up, Lock pro Schlüssel, Rate-Limit vor der DB, Redis-Replikation.
  2. Viele Schlüssel laufen gleichzeitig ab: Ein Batch hat alles mit derselben TTL geschrieben. Lösung: TTL-Jitter.
  3. Redis voll, Writes scheitern: „OOM command not allowed when used memory > 'maxmemory'“. Ursache: noeviction oder keine TTLs bei volatile-*. Lösung: allkeys-lru oder -lfu, TTLs setzen, maxmemory passend.
  4. Veraltete Daten nach Update: Invalidierung vergessen, Race oder L1-Cache in anderen Pods. Lösung: Löschen nach Commit, kurze L1-TTL, Invalidierungs-Events.
  5. Hot Key: Ein Schlüssel bekommt einen Grossteil der Last, ein Redis-Knoten glüht. Lösung: L1-Cache davor, Schlüssel replizieren.
  6. Big Key: Ein Wert mit vielen MB blockiert Redis beim Lesen oder Löschen. Lösung: aufteilen, UNLINK statt DEL.
  7. Personendaten im Cache: Auch ein Cache ist ein Datenspeicher. Lösung: Verschlüsselung in Transit, ACLs, kurze TTL, nur nötige Felder.

7. Diagnose: Werkzeuge und Befehle

  • INFO stats: keyspace_hits, keyspace_misses, evicted_keys, expired_keys.
  • INFO memory: used_memory, maxmemory, mem_fragmentation_ratio.
  • TTL key (-1 = keine TTL, -2 = existiert nicht), OBJECT FREQ key (bei LFU), MEMORY USAGE key.
  • redis-cli --bigkeys, redis-cli --hotkeys (braucht LFU-Policy), redis-cli --latency.
  • SLOWLOG GET 10: langsame Befehle, z. B. KEYS *.
  • SCAN 0 MATCH produkt:* COUNT 100 statt KEYS in Produktion.
  • Spring Boot Actuator: /actuator/caches, Micrometer-Metriken cache.gets{result=hit|miss}.

8. Senior-Punkte

  1. Erst messen, dann cachen. Ein Cache bringt Konsistenz-Probleme. Oft hilft vorher ein Index oder eine bessere Abfrage.
  2. Akzeptierte Veraltung festlegen. „Wie alt darf der Wert sein?“ ist eine fachliche Frage. Daraus folgt die TTL.
  3. Der Cache ist kein Speicher der Wahrheit. Das System muss mit leerem Cache funktionieren, nur langsamer.
  4. Löschen statt Aktualisieren, nach dem Commit, plus TTL als Sicherheitsnetz.
  5. Stampede-Schutz für heisse Schlüssel gehört ins Design, nicht in den Postmortem.
  6. Write-Behind nur, wenn Datenverlust akzeptabel ist. Für Geld oder Anträge nie.

10. Fallen

  • „Nach einem Update schreibe ich den neuen Wert in den Cache.“ → Race-anfällig. Besser löschen nach dem Commit.
  • „Redis entfernt bei vollem Speicher automatisch alte Schlüssel.“ → Falsch. Default ist noeviction: Writes scheitern.
  • „SET behält die TTL.“ → Falsch. SET ohne EX/KEEPTTL löscht sie.
  • „Redis LRU ist exakt.“ → Falsch. Es ist eine Stichproben-Annäherung.
  • „Write-Behind ist einfach schneller.“ → Schneller, aber mit Risiko für Datenverlust und Reihenfolge-Fehler.
  • „KEYS * zum Invalidieren.“ → Blockiert Redis. SCAN oder Schlüssel-Versionen nutzen.

11. Fragen

Was ist Cache-Aside?

Die App liest zuerst den Cache, bei Miss die DB und füllt dann den Cache. Beim Schreiben ändert sie die DB und löscht den Eintrag.

Was ist der Unterschied zwischen Cache-Aside und Read-Through?

Bei Cache-Aside lädt die App. Bei Read-Through lädt der Cache selbst über einen Loader.

Was ist Write-Through?

Jeder Write geht synchron durch den Cache in die DB. Der Cache ist immer aktuell, Writes sind langsamer.

Was ist Write-Behind?

Writes gehen in den Cache, die DB wird später asynchron aktualisiert. Sehr schnell, aber Datenverlust ist möglich.

Was ist Refresh-Ahead?

Heisse Einträge werden vor ihrem Ablauf im Hintergrund neu geladen. So gibt es für sie keinen Miss.

Wie wählen Sie eine TTL?

Nach der fachlich erlaubten Veraltung und der Änderungsrate. Plus Jitter, damit nicht alles gleichzeitig abläuft.

Wie läuft eine TTL in Redis ab?

Passiv beim Zugriff und aktiv durch regelmässige Stichproben unter Schlüsseln mit TTL.

Was bedeutet TTL -1 und -2?

-1: Schlüssel existiert ohne Ablaufzeit. -2: Schlüssel existiert nicht.

Welche Eviction-Policies gibt es?

noeviction, allkeys-lru, allkeys-lfu, allkeys-random, volatile-lru, volatile-lfu, volatile-random, volatile-ttl, und seit 8.6 allkeys-lrm und volatile-lrm.

Was ist die Default-Policy und warum ist sie für Caches gefährlich?

noeviction. Bei vollem Speicher scheitern Writes, statt alte Einträge zu entfernen.

Welche Policy nehmen Sie für einen reinen Cache?

Meist allkeys-lru, bei klaren Hot-Spots allkeys-lfu.

LRU oder LFU?

LRU entfernt lange nicht Genutztes. LFU entfernt selten Genutztes und schützt dauerhaft beliebte Schlüssel besser.

Ist das LRU in Redis exakt?

Nein. Redis nimmt eine Stichprobe (maxmemory-samples, Default 5) und entfernt den ältesten Schlüssel daraus.

Was ist ein Cache Stampede?

Ein heisser Schlüssel läuft ab und viele Requests laden ihn gleichzeitig aus der DB. Die DB wird überlastet.

Wie verhindern Sie einen Stampede?

Lock pro Schlüssel (SET NX EX), TTL-Jitter, frühzeitiges Neu-Laden oder alten Wert ausliefern und im Hintergrund laden.

Warum löschen statt aktualisieren nach einem Write?

Parallele Writes können den Cache sonst mit einem älteren Wert überschreiben. Löschen ist idempotent und sicher.

In welcher Reihenfolge: DB schreiben oder Cache löschen?

Erst DB committen, dann Cache löschen. Sonst kann ein Leser den alten Wert neu in den Cache laden.

Wie invalidieren Sie lokale Caches in mehreren Pods?

Mit Events (z. B. Kafka oder CDC), auf die jeder Pod reagiert, plus kurze lokale TTL als Netz.

Was ist Cache Penetration?

Anfragen nach nicht existierenden Schlüsseln gehen immer an die DB. Lösung: Negative Caching oder Bloom-Filter.

Wie messen Sie den Erfolg eines Caches?

Hit Rate aus keyspace_hits und keyspace_misses, dazu evicted_keys und die Latenz der DB.

Lokaler Cache oder Redis?

Lokal ist am schnellsten, aber pro Pod verschieden. Redis ist geteilt und konsistenter, kostet einen Netzwerk-Hop und Betrieb. Oft beides: L1 kurz, L2 länger.

Szenario: Nach einem Redis-Neustart fällt die Datenbank aus. Was ist passiert und was tun Sie?

Kalter Cache: Alle Requests sind Misses und treffen die DB. Lösung: Lock pro Schlüssel, Warm-up, Rate-Limit vor der DB und Redis mit Replikation.

Szenario: Benutzer sehen nach einer Preisänderung noch minutenlang den alten Preis. Wo suchen Sie?

Fehlende oder falsche Invalidierung, Race beim Cache-Aside oder lokale Caches in anderen Pods. Lösung: Löschen nach Commit, Events an alle Pods, kürzere TTL.

Szenario: Redis meldet „OOM command not allowed“. Was tun Sie?

maxmemory-policy prüfen: Wahrscheinlich noeviction oder volatile ohne TTLs. Auf allkeys-lru umstellen, TTLs setzen und grosse Schlüssel suchen.
