Redis-Datentypen und Einsatz

Kern: Redis ist ein Data Structure Server. Es speichert nicht nur Strings, sondern Hashes, Lists, Sets, Sorted Sets, Streams und mehr, und jede Struktur hat eigene Befehle mit bekannter Komplexität. Die Wahl des Typs bestimmt Speicher und Geschwindigkeit. Die Befehle sind atomar, mehrere Befehle zusammen laufen mit MULTI und EXEC.

Antwort-Muster

Frage: Welchen Redis-Datentyp nehmen Sie für eine Rangliste?

  1. Mechanismus: Ein Sorted Set. Jedes Mitglied hat einen Score, Redis hält die Mitglieder nach Score sortiert.
  2. Zahl: ZADD kostet O(log N). Einen Bereich lesen mit ZRANGE kostet O(log N + M).
  3. Trade-off: Alles liegt im Speicher. Ein Sorted Set braucht mehr RAM als ein Hash mit denselben Daten.
  4. Produktion: Ich lese Top-Listen mit ZRANGE in kleinen Bereichen und nie mit KEYS oder SMEMBERS auf grossen Mengen.

1. Typ wählen in 5 Schritten

  1. Zugriff klären: Welche Fragen stellt die Anwendung? Zum Beispiel „Wert zu Schlüssel“, „die Top 10“ oder „ist X schon da?“.
  2. Struktur zuordnen: Ein Wert ist ein String. Ein Record mit Feldern ist ein Hash. Eine Folge ist eine List oder ein Stream. Eine Menge ohne Doppelte ist ein Set. Eine sortierte Menge ist ein Sorted Set.
  3. Komplexität prüfen: Jede Befehlsseite nennt die Komplexität. Man vermeidet Befehle mit O(N) auf grossen Strukturen.
  4. Schlüssel entwerfen: Ein klares Namensschema mit Doppelpunkt, und früh klären, ob und wann der Schlüssel ablaufen soll.
  5. Grösse begrenzen: Eine List oder ein Set, das ewig wächst, füllt den Speicher. Man kürzt (LTRIM), lässt ablaufen oder teilt auf.

2. Aufbau

  1. Ein String ist die einfachste Form: eine Folge von Bytes. Ein Wert darf höchstens 512 MB gross sein.
  2. Ein Hash ist ein Record aus Feld-Wert-Paaren, ähnlich einer Java HashMap.
  3. Eine List hält Strings in Einfügereihenfolge. Kopf und Ende sind schnell.
  4. Ein Set hält eindeutige Strings ohne Ordnung.
  5. Ein Sorted Set hält eindeutige Strings, die nach einem Score geordnet sind.
  6. Ein Stream ist ein Append-only Log von Ereignissen.

3. Details

  1. String: Er speichert Text, Zahlen oder Binärdaten wie ein JPEG. Das Maximum ist 512 MB. INCR erhöht eine Zahl atomar, darum eignen sich Strings als Zähler.
  2. Bitmaps und Bitfields: Beides sind Strings mit Bit-Operationen. Bitmaps erlauben bitweise Befehle, Bitfields kodieren mehrere Zähler in einem Wert.
  3. Hash: Feld-Wert-Paare unter einem Schlüssel. HGET ist O(1), HSET ist O(1) pro Paar. Kleine Hashes sind speichersparend kodiert. Felder können seit Redis 7.4.0 einzeln ablaufen (HEXPIRE).
  4. List: Eine verkettete Liste. Einfügen und Entfernen an Kopf und Ende ist O(1), auch bei Millionen Einträgen. Der Zugriff per Index ist O(N). BLPOP blockiert, bis ein Element da ist. LTRIM hält die Liste auf feste Länge.
  5. Set: Hinzufügen, Entfernen und Prüfen sind O(1), unabhängig von der Grösse. SMEMBERS gibt alle Mitglieder zurück und ist O(N). Auf grossen Sets ist das gefährlich.
  6. Sorted Set: Intern ein Verbund aus Skip List und Hash Table. Haben zwei Mitglieder denselben Score, sortiert Redis sie lexikographisch. ZADD ist O(log N), Bereichsabfragen sind O(log N + M).
  7. Stream: Ein Append-only Log. Er hält Ereignisse in der Reihenfolge, in der sie auftreten, und gibt sie zur Verarbeitung weiter.
  8. HyperLogLog: Zählt eindeutige Elemente mit konstant etwa 12 KB. Der Standardfehler ist 0.81 %. PFCOUNT mit einem Schlüssel ist schnell, mit mehreren Schlüsseln langsamer, weil er vorher mischt.
  9. Weitere Typen: Geospatial-Indizes, JSON, Arrays, Time Series, Vector Sets und probabilistische Typen (Bloom, Cuckoo, Count-min, t-digest, Top-K). Sie gehören zu Redis Open Source, wie die Doku listet.
  10. KEYS ist gefährlich: Es ist O(N) über alle Schlüssel. Die Doku warnt vor dem Einsatz in Produktion. Man nutzt SCAN oder Sets.
  11. Mehrere Befehle zusammen: Ein einzelner Befehl wie INCR ist ein Schritt. Mehrere Befehle zusammen brauchen MULTI und EXEC. Ein Beispiel dafür ist RPUSH mit EXPIRE in der Doku.

4. Fallen

  • „Redis speichert nur Strings.“ → Falsch. Es hat Hashes, Lists, Sets, Sorted Sets, Streams und weitere Typen.
  • „KEYS * ist ein guter Weg, Schlüssel zu finden.“ → Falsch. Es ist O(N). Die Doku sagt: nicht im regulären Anwendungscode nutzen. Nimm SCAN.
  • „SMEMBERS ist schnell wie SADD.“ → Falsch. SADD ist O(1), SMEMBERS ist O(N) über das ganze Set.
  • „Eine Liste mit Zugriff LINDEX in einer Schleife ist effizient.“ → Falsch. Der Zugriff per Index ist O(N). Für Zugriff per Schlüssel nimmt man Hash oder Sorted Set.
  • „Ein Wert im String-Typ kann beliebig gross sein.“ → Falsch. Das Maximum ist 512 MB. Grosse Werte sind aber ein Zeichen für ein falsches Design.
  • „Ein Hash-Feld braucht keine TTL-Planung.“ → Falsch. Ein TTL gilt für den ganzen Schlüssel. Einzelne Felder ablaufen zu lassen geht erst seit 7.4.0 mit HEXPIRE.

5. Selbsttest

Warum?

Warum hat Redis verschiedene Datentypen statt nur Strings?

Jede Struktur hat Befehle, die auf dem Server laufen. So liest und ändert man Teile (ein Feld, einen Rang) ohne den ganzen Wert zu übertragen.

Warum ist INCR als Zähler sicher?

INCR liest, erhöht und schreibt den Wert in einem einzigen Befehl. Zwei Clients verlieren so keine Zählung, anders als bei GET und SET nacheinander.

Warum nimmt man einen Hash statt vieler Strings für ein Objekt?

Ein Hash bündelt die Felder unter einem Schlüssel. Man liest einzelne Felder mit HGET. Kleine Hashes sind zudem speichersparend kodiert.

Wie innen?

Wie ist ein Sorted Set aufgebaut?

Als Verbund aus Skip List und Hash Table. Die Skip List hält die Reihenfolge nach Score, die Hash Table findet Mitglieder direkt. Bei gleichem Score entscheidet die lexikographische Ordnung.

Wie ist eine Redis-List aufgebaut?

Als verkettete Liste. Kopf und Ende sind O(1). Ein Zugriff per Index braucht Arbeit proportional zum Index, also O(N).

Wie funktioniert ein Stream?

Er ist ein Append-only Log. Neue Einträge kommen ans Ende, und Konsumenten lesen sie in der Reihenfolge, in der sie auftraten.

Wie funktioniert HyperLogLog?

Er schätzt die Zahl eindeutiger Elemente. Redis nutzt für wenige Elemente eine Sparse-Darstellung und wechselt dann zur Dense-Darstellung mit 12 288 Bytes (16 384 Zähler mit 6 Bit).

Wie wird ein Wert in einer Rangliste aktualisiert?

ZADD mit demselben Mitglied und neuem Score ersetzt den Score. Mit ZINCRBY erhöht man ihn. Beides ist O(log N).

Wie ermöglicht man mehrere Befehle zusammen atomar?

Mit MULTI und EXEC. Zum Beispiel RPUSH und EXPIRE im Navigation-Session-Muster der Doku. Oder mit einem Lua-Skript oder einer Funktion.

Zahlen

Wie gross darf ein String-Wert sein?

Höchstens 512 MB.

Wie viel Speicher braucht ein HyperLogLog?

Etwa 12 KB (12 288 Bytes in der Dense-Darstellung), mit einem Standardfehler von 0.81 %.

Welche Komplexität haben ZADD, SADD und HGET?

ZADD O(log N), SADD O(1), HGET O(1).

Wie schnell ist KEYS?

O(N) über alle Schlüssel. Nach der Doku scannt es auf einem Einsteiger-Laptop 1 Million Schlüssel in etwa 40 Millisekunden. Das blockiert Redis trotzdem für diese Zeit.

Vergleich

Hash vs String mit JSON?

Ein Hash erlaubt Zugriff und Änderung einzelner Felder. Ein JSON-String muss man ganz lesen und schreiben. Für verschachtelte Daten gibt es zusätzlich den Typ JSON.

List vs Stream als Warteschlange?

Eine List mit BLPOP ist einfach, ein Element geht an genau einen Leser. Ein Stream ist ein Log, das man in Reihenfolge weiterverarbeitet und nachlesen kann.

Set vs Sorted Set?

Ein Set hat keine Ordnung, Operationen sind O(1). Ein Sorted Set ist nach Score geordnet, Operationen sind O(log N), dafür sind Ränge und Bereiche möglich.

HyperLogLog vs Set für eindeutige Zählungen?

Ein Set zählt exakt, braucht aber Speicher pro Element. HyperLogLog braucht konstant etwa 12 KB, zählt aber ungefähr mit 0.81 % Fehler.

Produktion

Was tun, wenn Redis plötzlich für Sekunden nicht antwortet?

Mit SLOWLOG prüfen, ob ein O(N)-Befehl läuft, zum Beispiel KEYS oder SMEMBERS auf einem grossen Set. Lösung: SCAN, SSCAN oder kleinere Strukturen.

Was tun, wenn der Speicher durch eine Liste wächst?

Die Liste hat keine Grenze. Lösung: LTRIM nach jedem Push, oder einen Stream mit Längenbegrenzung, oder TTL auf den Schlüssel.

Szenario: Eine Tages-Statistik zählt eindeutige Besucher mit einem Set und braucht Gigabytes. Was tun Sie?

Ich wechsle zu HyperLogLog mit PFADD und PFCOUNT. Es braucht etwa 12 KB pro Tag bei 0.81 % Fehler. Ist die exakte Zahl nötig, bleibt das Set.

Szenario: Ein Team will Sessions als einen Hash pro Nutzer mit allen Feldern speichern, aber einzelne Felder sollen ablaufen. Was empfehlen Sie?

Seit Redis 7.4.0 gibt es HEXPIRE für einzelne Felder. Davor gilt der TTL nur für den ganzen Schlüssel. Alternativ trennt man ablaufende Daten in einen eigenen Schlüssel.

Design

Wie entwerfen Sie Schlüsselnamen?

Mit Namensschema und Doppelpunkt, zum Beispiel user:42:profile. Das macht Schlüssel lesbar und gruppierbar. Dazu plane ich früh, ob und wann sie ablaufen.

Wie bauen Sie eine Top-10-Rangliste?

Ein Sorted Set mit Punkten als Score. ZADD oder ZINCRBY für Änderungen, ZRANGE mit Rückwärts-Reihenfolge für die Top 10.

Wie bauen Sie eine begrenzte Verlaufsliste?

Mit einer List: LPUSH neues Element, dann LTRIM auf die gewünschte Länge. So bleibt die Liste konstant gross.

Wann nehmen Sie Redis nicht?

Wenn die Daten nicht in den Speicher passen oder komplexe Abfragen mit Joins nötig sind. Redis ist ein Speicher für Strukturen mit bekannten Zugriffen, keine relationale Datenbank.

Mehr

Gerüst

  • Warum? Strukturen auf dem Server: Teile lesen und ändern, atomar, mit bekannter Komplexität.
  • Wie innen? String (Bytes), Hash (Felder), List (verkettet), Set, Sorted Set (Skip List + Hash Table), Stream (Log).
  • Zahlen String max. 512 MB. HyperLogLog 12 KB, 0.81 %. ZADD O(log N). SMEMBERS O(N).
  • Vergleich Hash gegen JSON-String. List gegen Stream. Set gegen HyperLogLog.
  • Produktion O(N)-Befehle (KEYS, SMEMBERS) blockieren. Unbegrenzte Listen füllen den RAM.
  • Design Zugriff zuerst klären. Schlüsselschema, TTL, Grösse begrenzen.

Beispiel: je ein Befehl pro Typ mit redis-cli

SET page:views 0
INCR page:views                          # String als Zähler

HSET user:42 name "Anna" city "Bern"     # Hash
HGET user:42 city

RPUSH history:42 "a" "b" "c"             # List
LTRIM history:42 -2 -1                   # nur die letzten 2 behalten

SADD tags:post:1 "redis" "cache"         # Set
SISMEMBER tags:post:1 "redis"

ZADD board 120 "anna" 95 "ben" 120 "cem" # Sorted Set
ZRANGE board 0 -1 WITHSCORES             # aufsteigend nach Score

PFADD visitors:today u1 u2 u3 u1         # HyperLogLog
PFCOUNT visitors:today

Nicht ausgeführt. Redis ist auf dieser Maschine nicht installiert.

  1. Teil 1: INCR erhöht den String-Wert atomar.
  2. Teil 2: Ein Hash hält die Felder name und city. HGET liest ein einzelnes Feld in O(1).
  3. Teil 3: LTRIM history:42 -2 -1 behält nur die letzten zwei Elemente. So bleibt die List begrenzt.
  4. Teil 4: Ein Set hält jeden Tag nur einmal. SISMEMBER prüft die Zugehörigkeit.
  5. Teil 5: anna und cem haben denselben Score 120. Redis ordnet sie dann lexikographisch, also zuerst anna, dann cem. ben mit 95 steht zuerst.
  6. Teil 6: u1 kommt zweimal vor. Ein HyperLogLog schätzt 3 eindeutige Elemente.

Die Beschreibung folgt aus der Doku. Die Befehle wurden nicht ausgeführt, darum steht hier keine Ausgabe.

Vergleich

  • String: ein Wert, Zähler, Cache-Eintrag. Maximum 512 MB.
  • Hash: Objekt mit Feldern, einzelne Felder lesen und ändern.
  • List: Folge mit schnellem Kopf und Ende. Gut für Verlauf und einfache Queues.
  • Set: Mitgliedschaft in O(1), Schnitt- und Vereinigungsmengen.
  • Sorted Set: Ranglisten, Zeitleisten nach Score, Bereichsabfragen.
  • Stream: Ereignis-Log zum Nachlesen und Weiterverarbeiten.

Produktion

  1. Blockierende Befehle: KEYS und SMEMBERS auf grossen Strukturen sind O(N). Lösung: SCAN, SSCAN, HSCAN, ZSCAN.
  2. Wachsende Strukturen: Eine List oder ein Set ohne Grenze füllt den Speicher. Lösung: LTRIM, TTL, Rotation nach Zeit.
  3. Grosse Werte: Ein String mit vielen MB belastet Netz und Redis bei jeder Übertragung. Lösung: aufteilen oder anders speichern.
  4. Hot Key: Ein Schlüssel wird extrem oft gelesen. Lösung: lokal zwischenspeichern oder den Schlüssel aufteilen.
  5. Fehlende Atomarität: Zwei Befehle nacheinander sind nicht atomar. Lösung: MULTI/EXEC oder ein Lua-Skript.
  6. Falsche Annahmen zu Ablauf: Ein TTL gilt für den ganzen Schlüssel. Lösung: eigene Schlüssel oder HEXPIRE ab 7.4.0.

Diagnose: Werkzeuge und Befehle

  • TYPE key: zeigt den Typ eines Schlüssels.
  • MEMORY USAGE key: zeigt den Speicher eines Schlüssels.
  • SLOWLOG GET: listet langsame Befehle.
  • SCAN 0 MATCH user:* COUNT 100: durchläuft Schlüssel in Stücken.
  • redis-cli --bigkeys: sucht die grössten Schlüssel je Typ.
  • INFO memory und INFO commandstats: Speicher und Befehlsstatistik.

Senior-Punkte

  1. Erst den Zugriff, dann den Typ. Die Befehle bestimmen die Struktur, nicht umgekehrt.
  2. Komplexität pro Befehl kennen. Ein O(N)-Befehl auf einer grossen Struktur blockiert alle anderen Clients.
  3. Jede Struktur braucht eine Grenze: Länge, TTL oder Rotation.
  4. Nicht alles in einen Schlüssel. Ein grosser Hash oder Set wird zum Hot Key und zum Problem beim Löschen.
  5. Schlüsselschema dokumentieren. Namen, Typ, TTL und Besitzer jeder Schlüsselgruppe.
  6. Approximation bewusst wählen. HyperLogLog spart Speicher gegen einen bekannten Fehler.
