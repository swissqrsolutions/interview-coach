Goroutines und Channels

Kern: Eine Goroutine ist eine leichte Funktion, die das Go-Runtime nebenläufig ausführt. Ein Channel ist eine typisierte Warteschlange, mit der Goroutines Werte austauschen und sich synchronisieren. Go folgt dem Motto: Teile Speicher durch Kommunikation.

Antwort-Muster

Frage: Wie funktionieren Goroutines und Channels, und wie unterscheiden sie sich von Java Threads?

  1. Mechanismus: Das Runtime verteilt viele Goroutines auf wenige Betriebssystem-Threads. Channels blockieren Sender und Empfänger, bis beide bereit sind.
  2. Zahl: Der Stack einer Goroutine startet mit 2 KB und wächst bis 1 GB auf 64-Bit. GOMAXPROCS ist standardmässig die Zahl der CPUs.
  3. Trade-off: Goroutines sind billig, aber ein Leck merkt man spät. Unbuffered Channels synchronisieren, buffered Channels entkoppeln.
  4. Produktion: Ich gebe jeder Goroutine einen context zum Abbruch, schliesse Channels nur auf der Sender-Seite und teste mit -race.

1. go func() und eine Nachricht in 6 Schritten

  1. go f(): Das go-Statement startet f als neue Goroutine. Argumente werden im aufrufenden Code ausgewertet. Der Stack ist anfangs 2 KB klein.
  2. Run Queue: Das Runtime legt die Goroutine in die lokale Warteschlange eines Prozessors (P). Diese Queue hat Platz für 256 Einträge.
  3. Thread: Ein Betriebssystem-Thread (M) holt die Goroutine und führt sie aus. Es laufen höchstens GOMAXPROCS Goroutines gleichzeitig.
  4. Senden: ch <- v auf einem Channel ohne Puffer blockiert, bis ein Empfänger bereit ist.
  5. Empfangen: v := <-ch blockiert, bis ein Sender da ist. Dann wird der Wert übergeben.
  6. Weiter: Beide Goroutines laufen weiter. Das Senden ist vor dem Abschluss des Empfangs synchronisiert. So sieht der Empfänger alle Schreibzugriffe vor dem Senden.

Beendet main seine Arbeit, endet das Programm. Das Runtime wartet nicht auf andere Goroutines.

2. Aufbau

  1. G ist die Goroutine mit eigenem, wachsendem Stack.
  2. M ist ein Betriebssystem-Thread. Er führt Code aus.
  3. P ist ein logischer Prozessor mit lokaler Run Queue. Die Anzahl ist GOMAXPROCS.
  4. Ein Channel hat einen Elementtyp und eine Kapazität. Kapazität 0 oder fehlend heisst unbuffered.
  5. Ein select wartet auf mehrere Channel-Operationen und nimmt eine, die bereit ist.
  6. Ein context transportiert Abbruch und Fristen über Goroutines hinweg.

3. Details

  1. Stack: Eine Goroutine startet mit einem Stack von 2 KB. Der Stack wächst bei Bedarf. Das Maximum ist 1 GB auf 64-Bit und 250 MB auf 32-Bit. Darüber stürzt das Programm ab.
  2. GOMAXPROCS: Es begrenzt, wie viele Goroutines gleichzeitig Go-Code ausführen. Der Standard ist die Zahl der CPUs. Seit Go 1.25 gilt in Containern die kleinere Zahl aus CPUs und Cgroup-Limit.
  3. Unbuffered Channel: Kapazität 0. Senden und Empfangen treffen sich. Der Austausch ist eine Synchronisation. Das Senden ist vor dem Abschluss des Empfangs synchronisiert.
  4. Buffered Channel: Mit Kapazität C blockiert Senden erst, wenn der Puffer voll ist. Der k-te Empfang ist vor dem Abschluss des (k+C)-ten Sendens synchronisiert.
  5. close: Nur der Sender schliesst. Ein Empfang auf einem geschlossenen Channel liefert immer sofort den Nullwert. Senden auf einen geschlossenen Channel löst eine Panic aus. Auch doppeltes close und close auf nil lösen eine Panic aus.
  6. nil Channel: Senden und Empfangen auf einem nil Channel blockieren für immer. In einem select wird so ein Zweig nie gewählt.
  7. select: Sind mehrere Zweige bereit, wählt Go zufällig einen aus (gleichverteilt, pseudozufällig). Mit default blockiert select nie. Ohne bereiten Zweig und ohne default wartet es.
  8. Goroutine-Leck: Eine Goroutine, die auf einen Channel wartet, den niemand bedient, bleibt für immer. Sie hält Speicher. Es gibt keinen Fehler.
  9. Schleifenvariablen: Seit Go 1.22 hat jede Iteration einer for-Schleife eigene Variablen. Davor teilten sich alle Goroutines in der Schleife dieselbe Variable.
  10. WaitGroup: Sie wartet auf mehrere Goroutines. Seit Go 1.25 startet wg.Go(f) eine Goroutine und zählt sie mit.
  11. Speichermodell: Ohne Synchronisation sind gleichzeitige Zugriffe auf eine Variable ein Data Race. Channels, sync.Mutex und sync/atomic schaffen eine happens-before-Beziehung.
  12. Mutex oder Channel: Channels sind gut für Übergabe von Besitz und Pipelines. Ein Mutex ist einfacher für geschützten Zustand wie einen Zähler.

4. Fallen

  • „Goroutines sind Threads.“ → Falsch. Sie sind vom Runtime verwaltete Funktionen auf wenigen Threads. Der Stack startet mit 2 KB.
  • „main wartet auf alle Goroutines.“ → Falsch. Das Programm endet, wenn main zurückkehrt. Andere Goroutines werden abgebrochen.
  • „Ein Empfang auf einem geschlossenen Channel blockiert.“ → Falsch. Er liefert sofort den Nullwert. Mit v, ok := <-ch erkennt man das Schliessen.
  • „Der Empfänger darf den Channel schliessen.“ → Falsch. Nur der Sender. Senden auf einen geschlossenen Channel löst eine Panic aus.
  • „Alle Goroutines in einer Schleife sehen ihren eigenen Wert.“ → Falsch. Erst seit Go 1.22. Davor teilten sie die Schleifenvariable.
  • „Ein select prüft die Zweige von oben nach unten.“ → Falsch. Sind mehrere bereit, wählt Go einen zufällig. Die Reihenfolge im Code zählt nicht.

5. Selbsttest

Warum?

Warum sind Goroutines billiger als Threads?

Der Stack startet mit 2 KB und wächst bei Bedarf. Das Runtime wechselt zwischen Goroutines selbst, ohne den Betriebssystem-Scheduler.

Warum gibt es Channels?

Sie übergeben Werte und synchronisieren zugleich. So teilt man Daten durch Weitergeben statt durch gemeinsamen Speicher mit Sperren.

Warum braucht man context?

Eine Goroutine kann nicht von aussen beendet werden. Ein Context meldet Abbruch und Frist, und die Goroutine beendet sich selbst.

Wie innen?

Wie plant das Runtime Goroutines?

G, M und P. Jedes P hat eine lokale Run Queue. Ein M mit einem P führt Goroutines aus. Leere P holen Arbeit von anderen.

Was passiert bei einem blockierenden Send?

Die sendende Goroutine wird geparkt. Der Thread führt eine andere Goroutine aus. Kommt ein Empfänger, wird sie wieder bereit.

Wie wächst ein Stack?

Das Runtime kopiert den Stack in einen grösseren Speicherbereich, wenn er voll ist. Das Maximum ist 1 GB auf 64-Bit.

Was liefert ein Empfang auf einem geschlossenen Channel?

Zuerst noch gepufferte Werte, danach den Nullwert. ok ist dann false.

Zahlen

Wie gross ist der Anfangs-Stack?

2 KB (2048 Bytes) im Runtime-Quellcode.

Wie gross wird der Stack höchstens?

1 GB auf 64-Bit, 250 MB auf 32-Bit.

Wie gross ist die lokale Run Queue eines P?

256 Einträge. Weitere Goroutines kommen in die globale Queue.

Was ist der Standard für GOMAXPROCS?

Die Zahl der logischen CPUs. Seit Go 1.25 gilt in Containern die kleinere Zahl aus CPUs und Cgroup-Limit.

Vergleich

Goroutine vs Java Thread?

Ein Java Platform Thread ist ein Betriebssystem-Thread. Eine Goroutine wird vom Go Runtime geplant und ist viel leichter.

Goroutine vs Java Virtual Thread?

Beide sind leicht und werden vom Laufzeitsystem geplant. Go hat dazu Channels und select in der Sprache.

Channel vs BlockingQueue?

Beide sind Warteschlangen mit Blockieren. Ein Channel kann geschlossen werden und hat select in der Sprache.

Channel vs Mutex?

Channel für Übergabe und Pipelines. Mutex für Schutz von geteiltem Zustand.

Produktion

Wie findet man Goroutine-Lecks?

Mit runtime.NumGoroutine() im Monitoring und dem pprof-Profil goroutine. Eine steigende Zahl ohne Last zeigt ein Leck.

Wie findet man Data Races?

Mit go test -race und go run -race. Der Race Detector meldet Zugriffe ohne Synchronisation.

Szenario: Der Speicher eines Dienstes wächst, die Zahl der Goroutines steigt. Was tun Sie?

Ich hole das pprof-Profil goroutine und suche, wo viele Goroutines warten. Meist wartet eine auf einen Channel ohne Gegenstück. Ich füge context und Abbruch mit select ein.

Szenario: Ein Programm hängt, alle Goroutines schlafen. Was prüfen Sie?

Ich prüfe auf Deadlock. Das Runtime meldet "all goroutines are asleep" nur, wenn gar keine mehr laufen kann. Ich suche unbuffered Channels ohne Gegenstück und fehlendes close.

Design

Wie begrenze ich die Zahl paralleler Goroutines?

Mit einem Channel als Semaphor, einem Worker-Pool mit fester Zahl oder errgroup mit Limit. Nie unbegrenzt starten.

Wie beende ich Goroutines sauber?

Mit context.WithCancel oder Timeout. Jede Goroutine prüft ctx.Done() in einem select. Der Starter wartet mit WaitGroup.

Wann Puffer, wann kein Puffer?

Ohne Puffer für sichere Übergabe. Mit Puffer für Entkoppeln und Bursts. Die Grösse ist eine Entscheidung und kein Allheilmittel.

Mehr

Gerüst

  • Warum? Billige Nebenläufigkeit mit Kommunikation statt Sperren. Viele Aufgaben auf wenige Threads.
  • Wie innen? G, M und P. Channels parken Goroutines. Stack wächst durch Kopieren.
  • Zahlen Stack 2 KB bis 1 GB. Run Queue 256. GOMAXPROCS gleich CPUs (Go 1.25: Cgroup-bewusst).
  • Vergleich Gegen Threads, Virtual Threads, BlockingQueue, Mutex.
  • Produktion Goroutine-Lecks, Data Races, Deadlocks, nil Channels.
  • Design Context zum Abbruch, Sender schliesst, Pool mit Grenze, -race im Test.

Beispiel: Worker-Pool mit Channels und Abbruch

func worker(ctx context.Context, id int, jobs <-chan int, results chan<- string, wg *sync.WaitGroup) {
    defer wg.Done()
    for {
        select {
        case <-ctx.Done():
            return                              // Abbruch von aussen
        case j, ok := <-jobs:
            if !ok { return }                   // jobs wurde geschlossen
            results <- fmt.Sprintf("worker %d: job %d", id, j)
        }
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    jobs := make(chan int)                      // unbuffered
    results := make(chan string, 10)            // buffered
    var wg sync.WaitGroup
    for i := 1; i <= 3; i++ {
        wg.Add(1)
        go worker(ctx, i, jobs, results, &wg)
    }
    go func() { for j := 1; j <= 5; j++ { jobs <- j }; close(jobs) }()   // Sender schliesst
    go func() { wg.Wait(); close(results) }()
    for r := range results { fmt.Println(r) }
}

Nicht ausgeführt.

  1. jobs hat keinen Puffer. Jedes Senden wartet auf einen freien Worker.
  2. Der Sender schliesst jobs. Die Worker sehen ok == false und enden.
  3. select mit ctx.Done() macht jeden Worker abbrechbar.
  4. Eine eigene Goroutine wartet mit wg.Wait() und schliesst dann results. So endet die Schleife in main.
  5. Die Reihenfolge der Ausgaben ist nicht festgelegt. Sie hängt vom Scheduler ab.

Vergleich

  • Goroutine: Vom Runtime geplant, 2 KB Stack, sehr viele möglich.
  • Java Platform Thread: Betriebssystem-Thread, schwer.
  • Java Virtual Thread: Leicht, vom JVM-Runtime geplant, blockiert billig.
  • Kotlin Coroutine: Leicht, mit suspend und Scopes statt Channels als Kern.
  • Channel: Typisierte Queue mit close und select in der Sprache.
  • Mutex (sync): Schutz für Zustand. Einfach bei kleinen kritischen Abschnitten.

Produktion

  1. Goroutine-Leck: Eine Goroutine wartet für immer. Lösung: Context mit Abbruch, select mit ctx.Done().
  2. Data Race: Zwei Goroutines ändern dieselbe Variable ohne Sperre. Lösung: Mutex, Atomics oder Channel. -race im CI.
  3. Deadlock: Alle warten aufeinander. Lösung: Reihenfolge der Sperren klären, Channels mit Gegenstück, Timeouts.
  4. Panic durch close: Senden auf einen geschlossenen Channel. Lösung: nur der Sender schliesst, ein Besitzer pro Channel.
  5. Unbegrenzte Goroutines: Eine pro Anfrage ohne Grenze füllt den Speicher. Lösung: Worker-Pool, Semaphor.
  6. CPU-Limit im Container: Vor Go 1.25 nutzte GOMAXPROCS die Zahl der Host-CPUs. Das gab Drosselung. Lösung: Go 1.25 oder neuer, oder GOMAXPROCS setzen.

Diagnose: Werkzeuge und Befehle

  • go test -race ./... und go run -race: finden Data Races.
  • pprof Profil goroutine: zeigt, wo Goroutines warten (/debug/pprof/goroutine?debug=2).
  • runtime.NumGoroutine(): als Metrik gegen Lecks.
  • GODEBUG=schedtrace=1000: schreibt jede Sekunde den Zustand des Schedulers.
  • go tool trace: zeigt Goroutines, Blockaden und GC auf einer Zeitachse.
  • SIGQUIT (Ctrl+\) auf einem Programm: gibt alle Goroutine-Stacks aus.

Senior-Punkte

  1. Jede Goroutine braucht ein Ende. Wer sie startet, muss wissen, wie sie endet.
  2. Ein Besitzer pro Channel. Der Sender schliesst. Empfänger schliessen nie.
  3. Context ist der Standard für Abbruch. Er läuft durch alle Schichten.
  4. Puffer sind keine Lösung für Überlast. Sie verschieben das Problem. Gegendruck braucht eine Grenze.
  5. Race Detector im CI. Data Races zeigen sich in Produktion zufällig.
  6. Mutex ist okay. Nicht alles muss ein Channel sein.
