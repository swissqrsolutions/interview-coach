Interfaces und Error Handling in Go

Kern: Ein Interface in Go beschreibt eine Menge von Methoden. Ein Typ erfüllt es implizit, ohne implements. Fehler sind normale Werte vom Typ error. Funktionen geben sie als letzten Rückgabewert zurück, und der Aufrufer prüft sie.

Antwort-Muster

Frage: Wie funktionieren Interfaces und Fehlerbehandlung in Go, und was ist anders als in Java?

  1. Mechanismus: Ein Typ erfüllt ein Interface, wenn er alle Methoden hat. Ein Interface-Wert hält einen dynamischen Typ und einen Wert.
  2. Zahl: Das Interface error hat genau eine Methode, Error() string. errors.Is und errors.As gibt es seit Go 1.13, errors.Join seit Go 1.20.
  3. Trade-off: Implizite Interfaces entkoppeln Code, aber man sieht nicht sofort, wer ein Interface erfüllt. Fehler als Werte sind explizit, aber wortreich.
  4. Produktion: Ich verpacke Fehler mit %w, prüfe sie mit errors.Is und errors.As und gebe nie einen typisierten nil-Zeiger als error zurück.

1. Ein Fehler von der Quelle bis zum Aufrufer in 6 Schritten

  1. Funktion: Eine Funktion gibt (T, error) zurück. Bei Erfolg ist error gleich nil.
  2. Fehler: Der Fehler ist ein Wert, der Error() string hat. errors.New("...") erzeugt einen einfachen, ein eigener Typ trägt Daten.
  3. Verpacken: fmt.Errorf("lesen: %w", err) fügt Kontext hinzu und behält den ursprünglichen Fehler in der Kette.
  4. Aufrufer: Der Aufrufer schreibt if err != nil. Er behandelt den Fehler oder gibt ihn nach oben weiter.
  5. Prüfen: errors.Is(err, ErrNotFound) sucht einen bestimmten Fehler in der Kette. errors.As(err, &target) sucht einen Fehler eines Typs.
  6. Aufräumen: defer führt Aufräumcode am Ende der Funktion aus, auch bei einem Fehler. Die Aufrufe laufen in umgekehrter Reihenfolge.

Eine panic ist für Programmierfehler gedacht. Normale Fehler sind Rückgabewerte.

2. Aufbau

  1. Ein Interface-Typ besteht aus einer Liste von Methoden. interface{ Read(p []byte) (int, error) } ist ein Beispiel.
  2. Ein Interface-Wert hat einen statischen Typ (das Interface) und einen dynamischen Typ (den echten Typ).
  3. Die Methodenmenge eines Typs T enthält Methoden mit Wert-Empfänger. Die von *T enthält beide.
  4. Das Interface error ist interface{ Error() string }. Es ist vordefiniert.
  5. Eine Type Assertion x.(T) prüft den dynamischen Typ. Mit v, ok := x.(T) gibt es keine Panic.
  6. Embedding von Interfaces und Structs ersetzt Vererbung. Methoden werden "hochgereicht".

3. Details

  1. Implizite Erfüllung: Ein Typ erfüllt ein Interface, wenn er alle Methoden hat. Es gibt kein implements. Dadurch definiert der Verbraucher das Interface, nicht der Anbieter.
  2. Kleine Interfaces: Gute Interfaces haben wenige Methoden, oft eine. io.Reader und error sind Beispiele. Man definiert sie dort, wo man sie braucht.
  3. Methodenmenge und Zeiger: Hat eine Methode einen Zeiger-Empfänger, erfüllt nur *T das Interface, nicht T. Das ist eine häufige Compiler-Meldung.
  4. Typisierter nil: Ein Interface mit einem *T mit Wert nil ist nicht nil, denn der dynamische Typ ist *T. Gibt eine Funktion error zurück und liefert einen nil-Zeiger von eigenem Typ, ist err != nil wahr.
  5. Type Assertion und Type Switch: v, ok := x.(T) prüft sicher. Ohne ok gibt es bei falschem Typ eine Panic. Ein switch x.(type) wählt nach Typ.
  6. error ist ein Wert: Der Aufrufer kann ihn vergleichen, ändern und weitergeben. Es gibt keine Exceptions im normalen Ablauf. Es gibt auch keine Stacktraces im Standard-Fehler.
  7. Wrapping: %w in fmt.Errorf behält den inneren Fehler. errors.Unwrap holt ihn. Seit Go 1.13 sind Is, As und Unwrap im Paket errors.
  8. errors.Is und errors.As: Beide laufen durch die ganze Kette. Is vergleicht mit einem Wert (oder einer eigenen Is-Methode). As sucht einen Typ und setzt das Ziel.
  9. errors.Join: Seit Go 1.20 fasst errors.Join mehrere Fehler zu einem zusammen. Is und As durchsuchen auch diese Baumstruktur.
  10. Sentinel- und Typ-Fehler: Ein Sentinel ist ein Wert wie var ErrNotFound = errors.New("not found"). Ein Fehlertyp trägt Daten, zum Beispiel einen Statuscode.
  11. defer: Ein defer-Aufruf läuft beim Verlassen der Funktion. Mehrere laufen in umgekehrter Reihenfolge. Argumente werden beim defer ausgewertet.
  12. panic und recover: panic bricht den normalen Ablauf ab und führt defer-Aufrufe aus. recover fängt sie, aber nur in einem defer. Man nutzt es an Grenzen, zum Beispiel in einem Server pro Anfrage.

4. Fallen

  • „Ein Typ muss das Interface deklarieren, das er erfüllt.“ → Falsch. Nein. Go prüft nur, ob die Methoden da sind. Es gibt kein implements.
  • „Ein Interface mit nil-Zeiger ist nil.“ → Falsch. Ein Interface ist nur nil, wenn Typ und Wert nil sind. Ein *T mit Wert nil im Interface ist nicht nil.
  • „T und *T erfüllen dasselbe Interface.“ → Falsch. Mit Zeiger-Empfängern erfüllt nur *T das Interface. Die Methodenmenge von T ist kleiner.
  • „Fehler vergleicht man mit ==.“ → Falsch. Verpackte Fehler sind nicht mehr gleich. Man nutzt errors.Is und errors.As.
  • „panic ist wie eine Java-Exception für Fehler.“ → Falsch. Panics sind für Programmierfehler. Normale Fehler sind Rückgabewerte.
  • „recover() fängt Panics überall.“ → Falsch. Nur in einer Funktion, die per defer läuft, und nur in derselben Goroutine.

5. Selbsttest

Warum?

Warum gibt es implizite Interfaces?

Der Code, der ein Interface braucht, kann es selbst definieren. Bibliotheken müssen es nicht vorher kennen. Das entkoppelt Pakete.

Warum sind Fehler Werte statt Exceptions?

Der Fehlerpfad ist im Code sichtbar. Jeder Aufruf zeigt, wo es schiefgehen kann. Es gibt keinen versteckten Kontrollfluss.

Warum verpackt man Fehler mit %w?

So kommt Kontext dazu und der ursprüngliche Fehler bleibt prüfbar mit errors.Is und errors.As.

Wie innen?

Was ist ein Interface-Wert?

Ein Paar aus dynamischem Typ und Wert. Das Interface selbst ist der statische Typ.

Wann ist ein Interface nil?

Wenn es keinen dynamischen Typ hat und keinen Wert. Ein typisierter nil-Zeiger macht es nicht nil.

Wie arbeitet errors.Is?

Es vergleicht den Fehler mit dem Ziel, dann ruft es Unwrap auf und wiederholt das. Bei Unwrap() []error durchsucht es alle.

Wie arbeitet defer?

Beim Ausführen wird der Aufruf mit seinen Argumenten gemerkt. Beim Verlassen der Funktion laufen alle Aufrufe in umgekehrter Reihenfolge.

Zahlen

Wie viele Methoden hat das Interface error?

Eine: Error() string.

Seit wann gibt es errors.Is und errors.As?

Seit Go 1.13.

Seit wann gibt es errors.Join?

Seit Go 1.20.

Vergleich

Go-Interface vs Java-Interface?

In Java deklariert die Klasse implements. In Go erfüllt ein Typ ein Interface automatisch, wenn die Methoden passen.

Go-Fehler vs Java-Exceptions?

Go gibt Fehler als Werte zurück und der Aufrufer prüft sie. Java wirft Exceptions und die laufen den Stack hoch. Beide haben "Ursache"-Ketten.

Go Embedding vs Java Vererbung?

Embedding ist Komposition. Methoden werden hochgereicht, es gibt aber keine Subtyp-Beziehung zum eingebetteten Typ.

defer vs try-finally?

Beide räumen auf. defer steht direkt neben dem Öffnen der Ressource und läuft am Funktionsende.

Produktion

Wie testet man auf einen bestimmten Fehler?

Mit errors.Is(err, ErrX) für Werte und errors.As(err, &target) für Typen. Nie mit == auf verpackte Fehler.

Wie vermeidet man den typisierten nil-Fehler?

Funktionen geben nil direkt zurück, wenn kein Fehler da ist. Nie einen Zeiger-Typ in einer Variable vom Typ error zurückgeben.

Szenario: err != nil ist wahr, aber die Meldung ist leer oder es kommt eine Panic. Was prüfen Sie?

Ich vermute einen typisierten nil. Die Funktion gibt einen *MyErr mit Wert nil als error zurück. Ich gebe direkt nil zurück.

Szenario: In den Logs steht nur "not found", niemand weiss woher. Was tun Sie?

Ich verpacke Fehler auf jeder Ebene mit Kontext (%w). So zeigt die Meldung den Weg, und errors.Is funktioniert weiter.

Design

Wo definiere ich ein Interface?

Beim Verbraucher, klein und mit nur den nötigen Methoden. Der Anbieter gibt konkrete Typen zurück.

Wann nehme ich einen Sentinel, wann einen Fehlertyp?

Sentinel für einfache Fälle wie "nicht gefunden". Fehlertyp, wenn der Aufrufer Daten braucht, zum Beispiel Statuscode oder Feld.

Wann ist panic richtig?

Bei Programmierfehlern und unmöglichen Zuständen. Für erwartbare Fehler wie Netzwerk oder Eingabe nutze ich Rückgabewerte.

Mehr

Gerüst

  • Warum? Entkopplung durch kleine Interfaces. Fehler sind sichtbar im Code.
  • Wie innen? Interface-Wert gleich Typ plus Wert. Fehlerkette mit Unwrap. defer in umgekehrter Reihenfolge.
  • Zahlen error hat eine Methode. Is und As seit 1.13. Join seit 1.20.
  • Vergleich Gegen Java-Interfaces, Exceptions, Vererbung, try-finally.
  • Produktion Typisierter nil, == auf verpackten Fehlern, fehlender Kontext.
  • Design Interface beim Verbraucher, %w verpacken, panic nur für Programmierfehler.

Beispiel: Fehlerkette, Interface und typisierter nil

var ErrNotFound = errors.New("not found")

type StatusError struct{ Code int }
func (e *StatusError) Error() string { return fmt.Sprintf("status %d", e.Code) }

func load(id int) error {
    return fmt.Errorf("load %d: %w", id, &StatusError{Code: 404})
}

func main() {
    err := load(7)
    fmt.Println(err)                                   // load 7: status 404
    var se *StatusError
    if errors.As(err, &se) { fmt.Println(se.Code) }    // 404
    fmt.Println(errors.Is(err, ErrNotFound))           // false

    var p *StatusError                                 // nil Zeiger
    var e error = p                                    // Interface mit Typ *StatusError
    fmt.Println(e == nil)                              // false !
}

Nicht ausgeführt.

  1. %w verpackt den *StatusError. Die Meldung zeigt den Kontext load 7.
  2. errors.As findet den *StatusError in der Kette. se.Code ist 404.
  3. errors.Is(err, ErrNotFound) ist false, denn dieser Fehler steckt nicht in der Kette.
  4. Die letzte Zeile ist die bekannte Falle. e hat den dynamischen Typ *StatusError und ist darum nicht nil, obwohl der Zeiger nil ist.

Vergleich

  • Go-Interface: Implizit, klein, beim Verbraucher definiert.
  • Java-Interface: Explizit mit implements, oft beim Anbieter definiert.
  • Go-Fehler: Rückgabewert, Kette mit %w, Prüfung mit errors.Is.
  • Java-Exceptions: Geworfen, Kette über cause, Stacktrace.

Produktion

  1. Verlorener Kontext: Fehler ohne %w zeigen nicht, woher sie kommen. Lösung: auf jeder Ebene verpacken.
  2. Typisierter nil: err != nil ist wahr, obwohl nichts schiefging. Lösung: nil direkt zurückgeben.
  3. Fehler ignoriert: _ = f() oder vergessener Rückgabewert. Lösung: Linter wie errcheck und golangci-lint.
  4. Fehler doppelt geloggt: Jede Ebene loggt und gibt weiter. Lösung: einmal behandeln, oben loggen.
  5. Panic im Server: Eine Panic in einer Goroutine beendet das Programm. Lösung: recover an der Grenze, zum Beispiel pro Anfrage.
  6. Zu grosse Interfaces: Mocks werden schwer. Lösung: kleine Interfaces beim Verbraucher.

Diagnose: Werkzeuge und Befehle

  • go vet: findet viele Fehler, auch falsche Format-Strings mit %w.
  • errcheck und golangci-lint: finden ignorierte Fehler.
  • fmt.Printf("%T %v", err, err): zeigt den dynamischen Typ eines Fehlers.
  • Debugger (Delve): zeigt Typ und Wert eines Interfaces.
  • go test -race und Tests mit errors.Is: prüfen die Fehlerkette.
  • Stacktrace bei Panic lesen: zeigt die Zeile und die Goroutine.

Senior-Punkte

  1. Interfaces beim Verbraucher. Kleine Interfaces machen Tests und Austausch einfach.
  2. Fehler sind API. Sentinels und Typen sind Teil des Vertrags. Man ändert sie nicht leichtfertig.
  3. Kontext statt Stacktrace. Verpacken liefert den Weg im Text. Man loggt nur einmal.
  4. Nie typisierte nil-Zeiger als error zurückgeben.
  5. panic ist keine Fehlerbehandlung. Es ist für Unmögliches und für Grenzen mit recover.
  6. Wortreich ist okay. if err != nil ist der Preis für sichtbaren Kontrollfluss.
