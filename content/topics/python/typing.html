Type Hints

Kern: Type Hints sind Typangaben im Code, zum Beispiel x: int. Python erzwingt sie zur Laufzeit nicht, es speichert sie nur. Ein Type Checker wie mypy oder pyright liest sie und findet Fehler vor dem Start.

Antwort-Muster

Frage: Was bringen Type Hints, wenn Python sie nicht prüft?

  1. Mechanismus: Python legt Hints nur in __annotations__ ab, und ein Type Checker liest den Quelltext statisch.
  2. Zahl: Seit 3.10 gibt es int | None, seit 3.11 Self, und seit 3.12 die Syntax def f[T]().
  3. Trade-off: Ich gewinne frühe Fehler und gute IDE-Hilfe, aber keine Garantie zur Laufzeit.
  4. Produktion: Ich lasse den Checker in der CI laufen und prüfe Daten von aussen extra, zum Beispiel JSON.

1. Vom Hint zur Fehlermeldung in 6 Schritten

  1. Schreiben: Man schreibt def double(x: int) -> int:. Die Hints stehen bei Parametern, Rückgabe und Variablen.
  2. Speichern: Python wertet die Angabe aus und legt sie in double.__annotations__ ab. Mehr passiert nicht.
  3. Laufzeit: Python ruft die Funktion auch mit "ab" auf. Das Ergebnis ist "abab", ohne Fehler.
  4. Checker liest: mypy oder pyright lesen den Quelltext. Sie führen den Code nicht aus.
  5. Vergleichen: Der Checker leitet den Typ jedes Ausdrucks ab (Type Inference). Dann prüft er, ob jedes Argument zum Parameter passt.
  6. Melden: Passt etwas nicht, meldet der Checker Datei und Zeile. In der CI bricht dann der Build ab.

2. Aufbau

  1. Ein Hint steht im Code und ist nur Metadaten.
  2. Der Type Checker ist ein eigenes Programm. Er gehört nicht zu Python.
  3. Das Modul typing der Standardbibliothek liefert die Hilfstypen.
  4. In 3.12 funktionieren list[int] und dict[str, int] direkt.
  5. Typing ist graduell. Man kann Hints Schritt für Schritt ergänzen.
  6. Zur Laufzeit lassen sich Hints lesen, zum Beispiel mit typing.get_type_hints.

3. Details

  1. Keine Prüfung zur Laufzeit: Die Doku sagt, der Python-Runtime erzwingt Annotationen nicht. Tools wie Type Checker und IDEs nutzen sie. Der Aufruf double("ab") läuft darum durch.
  2. Statische Prüfung: Der Checker braucht keinen Start des Programms. Er findet Fehler in Pfaden, die kein Test trifft.
  3. Optional: Optional[int] heisst int | None. Es heisst nicht, dass der Parameter fehlen darf. Das regelt der Default-Wert.
  4. Union-Syntax: Seit 3.10 schreibt man int | str statt Union[int, str]. Beide Formen sind gleich.
  5. Generics: Neu in 3.12 ist def first[T](xs: list[T]) -> T. Vorher brauchte man TypeVar. Die Typparameter stehen in __type_params__.
  6. type-Statement: Seit 3.12 gibt es type Vector = list[float]. Das ist ein Alias für einen Typ.
  7. Protocol: Ein Protocol beschreibt Methoden. Jede Klasse mit diesen Methoden passt, auch ohne Vererbung. Das ist strukturelle Typisierung und gibt es seit 3.8.
  8. runtime_checkable: Nur damit geht isinstance mit einem Protocol. Ohne es kommt ein TypeError. Geprüft wird nur, ob die Methoden da sind.
  9. TypedDict: Es beschreibt die Schlüssel eines dict. Zur Laufzeit bleibt es ein normales dict. NotRequired und Required gibt es seit 3.11.
  10. dataclass: Sie liest die Hints, um Felder zu bauen. Sie prüft aber keine Werte. P("text") für ein int-Feld geht durch.
  11. Any, object, cast: Any schaltet die Prüfung für diesen Wert aus. object erlaubt nur Operationen von object. cast sagt nur dem Checker etwas und ändert den Wert nicht.
  12. Literal, Final, Self: Literal['r','w'] erlaubt nur diese Werte (3.8). Final markiert Konstanten (3.8). Self steht für den eigenen Typ in Methoden (3.11).

4. Fallen

  • „Python prüft Type Hints beim Aufruf.“ → Falsch. Es sind nur Metadaten. double("ab") gibt "abab".
  • „Optional[int] heisst: Der Parameter darf fehlen.“ → Falsch. Es heisst int oder None. Ob er fehlen darf, sagt der Default-Wert.
  • „Eine dataclass wirft einen Fehler bei falschem Typ.“ → Falsch. Sie prüft nichts. Das macht nur der Type Checker, oder eine Validierungs-Bibliothek.
  • „Ein TypedDict ist eine eigene Klasse mit Prüfung.“ → Falsch. Zur Laufzeit ist es ein normales dict. Die Form kennt nur der Checker.
  • „Wenn mypy grün ist, gibt es keine Typfehler zur Laufzeit.“ → Falsch. Daten von aussen sind ungeprüft. Any, cast und # type: ignore lassen Lücken.
  • „isinstance(x, list[int]) prüft den Inhalt der Liste.“ → Falsch. Es wirft einen TypeError. Man kann nur gegen list prüfen.

5. Selbsttest

Warum?

Warum Type Hints, wenn Python sie nicht prüft?

Ein Type Checker findet Fehler vor dem Start. Die IDE bekommt bessere Vorschläge. Der Code ist leichter zu lesen.

Warum sind Hints freiwillig?

Python bleibt dynamisch. Man kann sie Schritt für Schritt einführen, auch in alten Projekten.

Warum prüft man Daten von aussen trotzdem zur Laufzeit?

Der Checker sieht nur den Code, nicht die Daten. JSON oder Formulare können alles enthalten.

Wie innen?

Wo speichert Python Hints?

In __annotations__ der Funktion oder Klasse. Das ist ein normales dict.

Wie liest man Hints mit aufgelösten Strings?

Mit typing.get_type_hints(f). Es wandelt Strings wie "list[int]" in echte Typen um.

Wie arbeitet ein Type Checker?

Er liest den Quelltext, leitet Typen ab und vergleicht sie. Er startet das Programm nicht.

Was ist strukturelle Typisierung?

Ein Typ passt, wenn er die nötigen Methoden hat. Vererbung ist nicht nötig. Dafür gibt es Protocol.

Was macht runtime_checkable?

Es erlaubt isinstance mit einem Protocol. Geprüft wird nur, ob die Methoden da sind.

Was ist ein TypeVar?

Eine Variable für einen Typ. In 3.12 schreibt man sie direkt in der Funktion, zum Beispiel def first[T](xs: list[T]) -> T.

Zahlen

Seit wann gilt int | None?

Seit Python 3.10. Es ist gleich wie Optional[int].

Seit wann gibt es Protocol und TypedDict?

Seit Python 3.8.

Was kam in 3.11 und 3.12 neu?

In 3.11 kamen Self, Required und NotRequired. In 3.12 kamen die Generics-Syntax und das type-Statement.

Vergleich

Protocol vs abstrakte Basisklasse?

Eine Basisklasse braucht Vererbung. Ein Protocol passt auf jede Klasse mit den Methoden.

TypedDict vs dataclass?

TypedDict beschreibt ein dict mit festen Schlüsseln. Eine dataclass erzeugt ein Objekt mit Feldern.

Hints vs Validierung wie Pydantic?

Hints prüft nur der Checker, vor dem Start. Eine Validierungs-Bibliothek prüft Daten zur Laufzeit.

mypy vs pyright?

Beide sind Type Checker für Python. Sie sind unterschiedliche Programme und können unterschiedlich streng sein.

Produktion

Was geht kaputt, wenn man Any überall nutzt?

Der Checker sieht keine Fehler mehr. Die Hints geben falsche Sicherheit.

Wie führt man Typing in ein altes Projekt ein?

Schritt für Schritt. Zuerst neue Module und öffentliche Funktionen, dann der Rest. Der Checker läuft in der CI.

Szenario: Der Checker ist grün, aber es kommt ein TypeError aus einer API-Antwort. Warum?

Die Antwort war nicht so, wie der Hint sagte. Der Checker kennt die Daten nicht. Lösung: Antwort an der Grenze validieren.

Szenario: Ein Team hat 400 Checker-Fehler und ignoriert sie. Was tun Sie?

Ich setze eine Baseline und erlaube keine neuen Fehler. Dann räume ich Modul für Modul auf. Ein Ignore braucht einen Grund.

Szenario: Jemand ändert Optional[int] zu int und der Build wird rot. Was ist das?

Der Checker findet Stellen, die None übergeben. Das ist sein Nutzen. Man behebt die Aufrufer.

Design

Wann nimmt man Protocol?

Wenn nur das Verhalten zählt, zum Beispiel close(). So bleiben Module lose gekoppelt.

Wie typisiert man eine Funktion, die den Typ durchreicht?

Mit einem Typparameter: def first[T](xs: list[T]) -> T | None.

Wann Literal?

Bei einer kleinen festen Menge von Werten, zum Beispiel Modi. Der Checker prüft dann den Wert.

Wie markiert man Konstanten?

Mit Final. Der Checker meldet dann eine Neuzuweisung.

Wann cast oder # type: ignore?

Nur wenn man mehr weiss als der Checker. Mit kurzem Kommentar. Beides ändert nichts zur Laufzeit.

Mehr

Gerüst

  • Warum? Ein Checker findet Fehler vor dem Start, ohne den Code auszuführen.
  • Wie innen? Hints liegen in __annotations__. Mypy oder pyright lesen den Quelltext und vergleichen Typen.
  • Zahlen int | None ab 3.10. Protocol, TypedDict, Literal, Final ab 3.8. Self ab 3.11. Generics-Syntax ab 3.12.
  • Vergleich Protocol statt Basisklasse. TypedDict statt dataclass bei dicts. Pydantic prüft zur Laufzeit.
  • Produktion Daten von aussen sind ungeprüft. Zu viel Any macht den Checker blind.
  • Design Checker in der CI, Daten an der Grenze validieren, Protocols an Modulgrenzen.

Beispiel: Was Hints zur Laufzeit tun

from dataclasses import dataclass
from typing import Protocol, TypedDict, get_type_hints, runtime_checkable, Optional

def double(x: int) -> int:
    return x * 2

print("1) Hints sind nicht erzwungen")
print(double("ab"))
print(double.__annotations__)

print("2) get_type_hints")
def f(a: "list[int]", b: Optional[str] = None) -> dict[str, int]: ...
print(get_type_hints(f))

print("3) Protocol (strukturell)")
@runtime_checkable
class Closer(Protocol):
    def close(self) -> None: ...
class File:
    def close(self) -> None: print("closed")
class Nope: pass
print(isinstance(File(), Closer), isinstance(Nope(), Closer))

print("4) TypedDict ist zur Laufzeit ein dict")
class User(TypedDict):
    name: str
    age: int
u: User = {"name": "Ada", "age": "x"}
print(type(u), u)

print("5) dataclass prueft keine Typen")
@dataclass
class P:
    x: int
print(P("kein int"))

print("6) Union-Syntax und Generics (3.12)")
def first[T](xs: list[T]) -> T | None:
    return xs[0] if xs else None
print(first([1, 2]), first([]), first.__type_params__)

Echte Ausgabe, Python 3.12.10. Die Ausgabe von mypy oder pyright: Nicht ausgeführt, beide sind hier nicht installiert.

  1. Block 1: double("ab") gibt abab. Python prüft den Hint nicht. Er steht nur in __annotations__.
  2. Block 2: get_type_hints macht aus dem String "list[int]" den Typ list[int].
  3. Block 3: Ein Protocol mit runtime_checkable. File hat close und passt. Nope nicht.
  4. Block 4: Das TypedDict-Objekt ist ein dict. Der falsche Wert "x" für age fällt zur Laufzeit nicht auf.
  5. Block 5: Die dataclass nimmt einen String für das int-Feld an.
  6. Block 6: def first[T] ist 3.12-Syntax. __type_params__ zeigt (T,).

Vergleich

  • Hints + Checker: prüft vor dem Start, kostet nichts zur Laufzeit.
  • Validierung (z. B. Pydantic): prüft Daten zur Laufzeit, kostet Zeit.
  • Protocol: strukturell, passt auf jede Klasse mit den Methoden.
  • ABC (abstrakte Basisklasse): nominell, braucht Vererbung.
  • TypedDict: feste Schlüssel in einem dict.
  • dataclass: Objekt mit Feldern, optional mit frozen.
  • Union: int | str ab 3.10, vorher Union[int, str].
  • Any vs object: Any erlaubt alles, object fast nichts.

Produktion

  1. Checker grün, Fehler zur Laufzeit: Daten von aussen waren anders. Lösung: an der Grenze validieren.
  2. Zu viel Any: Die Prüfung wird leer. Lösung: Any im Review zählen und abbauen.
  3. Ignore-Kommentare wachsen: Alte Fehler bleiben versteckt. Lösung: Ignores mit Grund und Ablauf.
  4. Checker langsam in der CI: Lösung: Cache nutzen und nur geänderte Pakete prüfen.
  5. Alte Python-Version: Neue Syntax läuft nicht. Lösung: Zielversion im Checker setzen.
  6. Hints und Code gehen auseinander: Lösung: Checker ist Pflicht in der CI.

Diagnose: Werkzeuge und Befehle

  • mypy src/ oder pyright: prüft das Projekt. Hier nicht ausgeführt.
  • python -c "import typing; print(typing.get_type_hints(f))": zeigt die Hints zur Laufzeit.
  • f.__annotations__: zeigt die rohen Hints.
  • reveal_type(x): lässt den Checker den abgeleiteten Typ zeigen. Es gilt nur beim Checker, nicht in Python.
  • IDE-Hinweise (zum Beispiel PyCharm oder VS Code): zeigen Typfehler schon beim Schreiben.

Senior-Punkte

  1. Hints sind Dokumentation, die ein Werkzeug prüft. Sie sind kein Schutz zur Laufzeit.
  2. Die Grenze zählt. Innen prüft der Checker, aussen muss man Daten validieren.
  3. Protocol an Modulgrenzen hält die Kopplung klein und macht Tests einfach.
  4. Graduell einführen. Neue Module streng, alte mit Baseline.
  5. Any ist eine Schuld. Jedes Any ist eine Stelle ohne Prüfung.
  6. Zielversion klar setzen. Syntax wie int | None oder def f[T] braucht die passende Python-Version.
