Iteratoren und Generatoren

Kern: Ein Iterator ist ein Objekt, das Werte einzeln auf Abruf liefert, über __next__(). Ein Generator ist der einfachste Weg, einen Iterator zu bauen, nämlich eine Funktion mit yield, die nach jedem Wert pausiert und ihren Zustand behält. So verarbeitet man grosse oder unendliche Datenströme mit konstantem Speicher.

Antwort-Muster

Frage: Was ist ein Generator, und warum spart er Speicher?

  1. Mechanismus: Eine Funktion mit yield liefert ein Generator-Objekt. Bei jedem next() läuft sie bis zum nächsten yield und pausiert mit ihrem Frame.
  2. Zahl: Im Beispiel braucht der Generator etwa 200 Bytes und die Liste 8,4 MB.
  3. Trade-off: Ein Generator spart Speicher, ist aber nur einmal durchlaufbar und hat kein len() und keinen Index.
  4. Produktion: Grosse Dateien lese ich zeilenweise mit einer Generator-Pipeline und schreibe Ergebnisse in Batches.

1. Die Reise eines Generators (Zustände)

  1. Erzeugen: p = betrag(...) ruft die Funktion auf, aber kein Code läuft. Zustand GEN_CREATED.
  2. Erstes next(): Der Code läuft bis zum ersten yield. Der Wert geht an den Aufrufer.
  3. Pause: Der Generator steht in GEN_SUSPENDED. Sein Frame (lokale Variablen, Position) bleibt erhalten.
  4. Nächstes next() oder send(v): Der Code läuft direkt nach dem yield weiter. Mit send(v) wird v der Wert des yield-Ausdrucks.
  5. Ende: Bei return oder Funktionsende wirft der Generator StopIteration. Der return-Wert steht in StopIteration.value.
  6. Abbruch: close() wirft GeneratorExit an der Pause-Stelle. finally-Blöcke laufen, z. B. Datei schliessen.

2. Aufbau

  1. Iterable: ein Objekt, das mit iter() einen Iterator liefert. Beispiel: eine Liste. Man kann es mehrmals durchlaufen.
  2. Iterator: ein Objekt mit __next__(). Es liefert den nächsten Wert oder wirft StopIteration. Sein __iter__() gibt sich selbst zurück.
  3. for-Schleife: ruft iter() und dann next(), bis StopIteration kommt. Sie fängt die Exception selbst.
  4. Generator-Funktion: eine Funktion mit yield. Ihr Aufruf führt keinen Code aus. Er liefert ein Generator-Objekt.
  5. Generator Expression: (x*x for x in daten). Wie eine List Comprehension, aber mit runden Klammern und lazy.

3. Details, die Interviewer fragen

  1. Iterator-Protokoll: __iter__() gibt den Iterator zurück. __next__() gibt den nächsten Wert. Am Ende kommt StopIteration. Ein Iterator ist selbst iterable, denn iter(it) is it ist True.
  2. Iterable vs Iterator: Eine Liste kann man oft durchlaufen. Jeder iter(liste) liefert einen neuen Iterator. Ein Iterator läuft nur einmal.
  3. yield vs return: yield pausiert und gibt einen Wert. return beendet den Generator. Sein Wert landet in StopIteration.value.
  4. yield from (seit Python 3.3, PEP 380): Es delegiert an einen Sub-Iterator. Es reicht auch send() und throw() weiter. Es liefert den return-Wert des Subgenerators.
  5. send(v): Es setzt den Generator fort und macht v zum Wert des yield-Ausdrucks. Der erste Aufruf muss next() oder send(None) sein. Sonst kommt TypeError: can't send non-None value to a just-started generator.
  6. throw() und close(): throw() wirft eine Exception an der Pause-Stelle. close() wirft GeneratorExit. GeneratorExit erbt von BaseException. Darum fängt except Exception es nicht.
  7. PEP 479 (Standard seit Python 3.7): Eine StopIteration im Generator-Code wird zum RuntimeError. Man beendet den Generator mit return.
  8. Generator Expression: Der erste for-Teil wird sofort ausgewertet. Fehler wie ein fehlender Name kommen also sofort. Alles andere ist lazy.
  9. Generator als Argument: sum(x*x for x in daten) braucht keine zweiten Klammern, wenn es das einzige Argument ist.
  10. itertools: islice schneidet einen Ausschnitt. chain verkettet. groupby gruppiert nur aufeinanderfolgende gleiche Schlüssel. tee macht mehrere Kopien und puffert. batched bildet Gruppen fester Grösse und ist neu in 3.12.
  11. Async Generatoren: Sie sind async def mit yield. Man durchläuft sie mit async for. Das Ende kommt über StopAsyncIteration.
  12. Kein len(), kein Index: Ein Generator kennt seine Länge nicht. gen[3] geht nicht. Dafür nutzt man islice.

4. Fallen

  • „Ein Generator-Aufruf führt den Code aus.“ → Falsch. Er liefert nur ein Generator-Objekt. Code läuft erst bei next().
  • „Man kann einen Generator mehrmals durchlaufen.“ → Falsch. Er ist danach erschöpft und liefert nichts mehr.
  • „range() ist ein Generator.“ → Falsch. Es ist ein lazy Sequenz-Objekt mit len() und Index.
  • „raise StopIteration beendet einen Generator.“ → Seit 3.7 falsch. Es wird ein RuntimeError. return nutzen.
  • „Generator Expressions sind komplett lazy.“ → Nicht ganz. Der erste for-Teil wird sofort ausgewertet.
  • „except Exception fängt GeneratorExit.“ → Falsch. GeneratorExit erbt von BaseException.

5. Selbsttest

Warum?

Warum sparen Generatoren Speicher?

Sie halten nur den aktuellen Zustand, nicht alle Werte. Im Beispiel 200 Bytes gegenüber 8,4 MB für eine Liste.

Was ist PEP 479?

Eine StopIteration im Generator wird zum RuntimeError. Standard seit Python 3.7. So enden Schleifen nicht still.

Was passiert, wenn man einen Generator zweimal durchläuft?

Der zweite Durchlauf ist leer. Kein Fehler.

Wie innen?

Was ist ein Iterator?

Ein Objekt mit __next__() und __iter__(). Es liefert Werte einzeln und wirft am Ende StopIteration.

Was ist ein Generator?

Eine Funktion mit yield. Ihr Aufruf liefert ein Generator-Objekt, das bei jedem next() bis zum nächsten yield läuft und pausiert.

Was passiert beim Aufruf einer Generator-Funktion?

Kein Code läuft. Python erzeugt ein Generator-Objekt im Zustand GEN_CREATED.

Wie funktioniert eine for-Schleife intern?

Sie ruft iter() auf dem Objekt und dann next(), bis StopIteration kommt.

yield vs return?

yield gibt einen Wert und pausiert. return beendet den Generator; sein Wert steht in StopIteration.value.

Was macht yield from?

Es delegiert an einen Sub-Iterator, reicht send und throw weiter und liefert dessen return-Wert. Seit Python 3.3.

Was macht send()?

Es setzt den Generator fort und macht den gesendeten Wert zum Ergebnis des yield-Ausdrucks. Der erste Aufruf muss next() oder send(None) sein.

Was machen throw() und close()?

throw() wirft eine Exception an der Pause-Stelle. close() wirft GeneratorExit; finally-Blöcke laufen.

Was ist eine Generator Expression?

Wie eine List Comprehension in runden Klammern. Sie erzeugt Werte lazy und braucht konstanten Speicher.

Wann wird eine Generator Expression ausgewertet?

Der erste for-Teil sofort, alles andere erst beim Abruf der Werte.

Was ist eine lazy Pipeline?

Mehrere Generatoren hintereinander. Jeder Wert läuft einzeln durch alle Stufen, erst wenn der Verbraucher ihn anfordert.

Zahlen

Wie viel Speicher spart der Generator im Beispiel?

Etwa 200 Bytes für den Generator gegenüber 8,4 MB für die Liste.

Seit welcher Python-Version gilt PEP 479?

Seit Python 3.7 ist es Standard. Eine StopIteration im Generator wird zum RuntimeError.

Seit welcher Version gibt es yield from und itertools.batched?

yield from seit Python 3.3 (PEP 380). itertools.batched ist neu in Python 3.12.

Vergleich

Was ist der Unterschied zwischen Iterable und Iterator?

Ein Iterable liefert mit iter() einen Iterator und kann mehrmals durchlaufen werden. Ein Iterator läuft nur einmal.

Ist range() ein Generator?

Nein. Es ist ein lazy Sequenz-Objekt mit len(), Index und mehrfacher Iteration.

Was ist der Haken bei groupby?

Es gruppiert nur aufeinanderfolgende gleiche Schlüssel. Ohne Sortierung entstehen mehrere Gruppen pro Schlüssel.

Was ist ein async Generator?

Eine async def-Funktion mit yield. Man nutzt ihn mit async for; das Ende signalisiert StopAsyncIteration.

Welche itertools-Funktionen nutzen Sie oft?

islice, chain, groupby, tee und batched (neu in 3.12) für Gruppen fester Grösse.

Produktion

Szenario: Ein Report zeigt beim zweiten Export keine Daten mehr. Woran denken Sie?

An einen Generator, der zweimal benutzt wird. Der zweite Durchlauf ist leer. Lösung: Generator neu erzeugen oder einmal in eine Liste wandeln.

Szenario: Ein Batch-Job stirbt mit MemoryError beim Verarbeiten einer grossen CSV. Was ändern Sie?

Zeilenweise lesen mit einer Generator-Pipeline statt alles zu laden. Ergebnisse in Batches schreiben, z. B. mit itertools.batched.

Szenario: Ein Generator liest aus einer Datei und wirft „I/O operation on closed file“. Warum?

Der with-Block hat die Datei geschlossen, bevor der Generator gelesen wurde. Lösung: with in den Generator verschieben.

Wie lese ich eine 20-GB-Datei?

Mit for line in f oder einem Generator. Nie mit read() oder readlines().

Design

Was geht kaputt, wenn ein Generator raise StopIteration nutzt?

Seit Python 3.7 wird daraus ein RuntimeError. Man beendet den Generator mit return.

Was geht kaputt, wenn man len() oder einen Index auf einen Generator nutzt?

Ein Generator kennt seine Länge nicht, gen[3] geht nicht. Für einen Ausschnitt nutzt man islice.

Was geht kaputt, wenn man einen Generator in zwei Schleifen nutzt?

Die zweite Schleife ist leer, ohne Fehler. Lösung: den Generator neu erzeugen oder einmal in eine Liste wandeln.

Mehr

Gerüst

  • Warum? Werte erst erzeugen, wenn der Verbraucher sie braucht. Ein Strom braucht nur den aktuellen Zustand.
  • Wie innen? Aufruf erzeugt nur ein Generator-Objekt (GEN_CREATED). next() läuft bis yield, der Frame bleibt (GEN_SUSPENDED). Ende wirft StopIteration.
  • Zahlen Beispiel: 200 Bytes gegenüber 8,4 MB. PEP 479 Standard seit 3.7. yield from seit 3.3. itertools.batched neu in 3.12.
  • Vergleich Iterable vs Iterator. Generator vs range. list vs lazy Pipeline. groupby nur für aufeinanderfolgende Schlüssel.
  • Produktion Generator zweimal benutzt → leerer zweiter Durchlauf. Grosse CSV → MemoryError. Datei im with-Block zu früh geschlossen.
  • Design Mit return enden, nicht raise StopIteration. Kein len() und kein Index (islice). Generator-Neustart durch neu erzeugen.

Beispiel: lazy Pipeline, Speicher, yield from, send, PEP 479

import sys, inspect, itertools

def lese_zeilen(zeilen):
    for z in zeilen:
        print(f"  lese: {z!r}")
        yield z

def nur_trades(zeilen):
    for z in zeilen:
        if z.startswith("TRADE"):
            yield z

def betrag(zeilen):
    for z in zeilen:
        yield int(z.split(";")[1])

daten = ["TRADE;100", "ORDER;7", "TRADE;250", "TRADE;40"]

print("1) Pipeline bauen")
p = betrag(nur_trades(lese_zeilen(daten)))
print("  Typ:", type(p).__name__, "| Zustand:", inspect.getgeneratorstate(p))
print("  erstes next():", next(p))
print("  Zustand:", inspect.getgeneratorstate(p))
print("  Rest summiert:", sum(p))
print("  nochmal summiert:", sum(p), "(erschoepft)")

print("2) Speicher")
liste = [i * i for i in range(1_000_000)]
gen = (i * i for i in range(1_000_000))
print("  Liste:    ", sys.getsizeof(liste), "Bytes")
print("  Generator:", sys.getsizeof(gen), "Bytes")

print("3) yield from")
def innen():
    yield 1
    yield 2
    return "fertig"
def aussen():
    ergebnis = yield from innen()
    yield f"innen sagt: {ergebnis}"
print(" ", list(aussen()))

print("4) send()")
def mittelwert():
    summe, n, avg = 0, 0, None
    while True:
        x = yield avg
        summe, n = summe + x, n + 1
        avg = summe / n
m = mittelwert()
next(m)
print("  ", m.send(10), m.send(20), m.send(60))

print("5) StopIteration im Generator (PEP 479)")
def kaputt():
    yield next(iter([]))
try:
    list(kaputt())
except RuntimeError as e:
    print("  RuntimeError:", e)

print("6) itertools.batched (neu in 3.12)")
print(" ", list(itertools.batched(range(7), 3)))
print("7) try/finally beim Abbruch")
def mit_aufraeumen():
    try:
        yield 1
        yield 2
    finally:
        print("  finally: Datei schliessen")
g = mit_aufraeumen()
next(g)
g.close()

Echte Ausgabe, Python 3.12.10 (python -I gen_demo.py). Die Speicherzahlen gelten für CPython 64 Bit.

  1. Lazy: Nach dem Bauen der Pipeline wurde keine Zeile gelesen. Erst next(p) zieht genau eine Zeile durch alle drei Stufen.
  2. Pull-Prinzip: sum(p) zieht den Rest. ORDER;7 wird gelesen, aber von nur_trades verworfen. 250 + 40 = 290.
  3. Einmalig: Der zweite sum(p) ergibt 0. Ein Generator ist danach erschöpft. Kein Fehler, einfach leer.
  4. Speicher: Die Liste braucht ca. 8,4 MB nur für die Zeiger (ohne die int-Objekte). Der Generator braucht 200 Bytes, egal wie viele Werte.
  5. yield from: delegiert an innen() und bekommt dessen return-Wert „fertig“.
  6. send(): schickt Werte in den Generator. Er wird zur Coroutine mit Zustand: laufender Mittelwert 10, 15, 30.
  7. PEP 479: Eine StopIteration im Generator wird seit Python 3.7 zum RuntimeError. So endet eine Schleife nicht still und falsch.
  8. close(): löst finally aus. So werden Ressourcen auch bei Abbruch freigegeben.

Vergleich

  • List Comprehension vs Generator Expression: Liste ist sofort fertig, mehrfach nutzbar, braucht O(n) Speicher. Generator ist lazy, einmalig, O(1) Speicher.
  • Generator vs eigene Iterator-Klasse: Generator ist kürzer und verwaltet den Zustand automatisch. Eine Klasse lohnt sich, wenn man weitere Methoden oder Mehrfach-Iteration braucht.
  • Generator vs Liste zurückgeben: Liste, wenn der Aufrufer Länge, Index oder mehrere Durchläufe braucht. Generator für Ströme und grosse Daten.
  • range vs Generator: range ist ein lazy Sequenz-Objekt, kein Iterator. Es hat len(), Index und kann mehrmals durchlaufen werden.
  • Python-Generator vs Java Stream: Beide sind lazy und einmalig. Java Streams haben parallele Ausführung und Collector; Python-Generatoren sind einfacher und pausierbar.

In der Produktion

  1. Generator zweimal genutzt, Daten fehlen: Der zweite Durchlauf ist leer, ohne Fehler. Lösung: einmal list(), wenn mehrfach nötig, oder Generator-Funktion neu aufrufen.
  2. MemoryError beim Einlesen: f.readlines() lädt die ganze Datei. Lösung: for line in f liest Zeile für Zeile.
  3. Datei schon geschlossen: Ein Generator liest aus einer Datei, die ein with-Block schon geschlossen hat. Lösung: with innerhalb des Generators.
  4. Ressourcen-Leck: Der Aufrufer bricht die Schleife ab. finally läuft erst bei close() oder Garbage Collection. Lösung: contextlib.closing oder den Generator explizit schliessen.
  5. Lazy versteckt Fehler: Ein Fehler in Zeile 1 Mio. kommt erst spät. Lösung: Validierung früh, gute Logs mit Zeilennummer.
  6. itertools.tee und groupby: tee puffert, wenn ein Zweig vorläuft; Speicher wächst. groupby braucht sortierte Daten, sonst entstehen doppelte Gruppen.

Diagnose

  • inspect.getgeneratorstate(g): GEN_CREATED, GEN_RUNNING, GEN_SUSPENDED, GEN_CLOSED.
  • inspect.isgenerator(x) und inspect.isgeneratorfunction(f): Ist das ein Generator?
  • sys.getsizeof(): flache Grösse eines Objekts. Für echte Speicherprofile: tracemalloc.
  • tracemalloc: Speicherspitzen finden, z. B. eine Liste statt eines Generators.
  • Debugger (pdb, IDE): Breakpoint in der Generator-Funktion greift erst beim ersten next().

Senior-Punkte

  1. Generatoren sind ein Werkzeug für Datenströme: Dateien, API-Seiten, DB-Cursor. Speicher bleibt konstant, egal wie gross die Daten sind.
  2. Pipelines aus kleinen Generatoren sind lesbar und testbar. Jede Stufe macht eine Sache: lesen, filtern, umwandeln.
  3. Lazy hat einen Preis: Einmal-Nutzung, späte Fehler, kein len(). Für kleine Daten ist eine Liste oft klarer.
  4. Ressourcen gehören in den Generator (with innen), damit Öffnen und Schliessen zusammen bleiben.
  5. In PySpark nutzt man das gleiche Prinzip: mapPartitions bekommt einen Iterator und kann mit yield Zeile für Zeile liefern, statt die ganze Partition in eine Liste zu laden.
  6. Paging-APIs: Ein Generator, der intern Seite für Seite holt, versteckt das Paging vor dem Aufrufer.
