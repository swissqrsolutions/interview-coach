Decorators und Context Manager

Kern: Ein Decorator ist eine Funktion, die eine Funktion nimmt und eine neue zurückgibt. Er fügt Verhalten wie Logging, Retry oder Caching hinzu, ohne den Code der Funktion zu ändern. Ein Context Manager ist ein Objekt mit __enter__ und __exit__, das mit with eine Ressource sicher öffnet und immer wieder schliesst.

Antwort-Muster

Frage: Was ist ein Decorator, und was ist ein Context Manager?

  1. Mechanismus: @d über def f heisst f = d(f). Der wrapper hält die Funktion als Closure. Ein Context Manager ruft __enter__ beim Eintritt und __exit__ beim Verlassen.
  2. Zahl: Ein Decorator mit Parameter hat drei Ebenen. __exit__ bekommt drei Parameter: Typ, Wert und Traceback.
  3. Trade-off: Decorators verstecken Verhalten und verändern die Funktion. Ohne functools.wraps stimmen Name und Doku nicht mehr.
  4. Produktion: Ein Retry-Decorator wiederholt nur idempotente Aufrufe. @lru_cache auf Methoden hält self und kann Speicher binden.

1. Die Reise eines with-Blocks

  1. Ausdruck auswerten: Python berechnet transaktion("t1"). Das Ergebnis ist der Context Manager.
  2. Eintreten: Python ruft __enter__(). Dessen Rückgabe landet in der Variable nach as. Bei open() ist das die Datei selbst.
  3. Block läuft: Dein Code arbeitet mit der Ressource.
  4. Normales Ende: Python ruft __exit__(None, None, None). Die Transaktion macht COMMIT.
  5. Exception: Python ruft __exit__ mit Typ, Exception und Traceback. Der Manager macht z. B. ROLLBACK.
  6. Entscheidung: Gibt __exit__ einen wahren Wert zurück, ist die Exception verschluckt. Sonst fliegt sie weiter. Normal ist: weiterfliegen lassen.

2. Aufbau

  1. Decorator: @timed über def lade heisst lade = timed(lade). Der Name zeigt danach auf den wrapper.
  2. wrapper: eine innere Funktion, die die Original-Funktion als Closure hält. Closure heisst: Sie merkt sich Variablen der äusseren Funktion.
  3. Context Manager: with open(p) as f ruft __enter__ beim Eintritt und __exit__ beim Verlassen.
  4. Garantie: __exit__ läuft auch bei Exception, return oder break. Das ist ein sicheres try/finally.
  5. Verbindung: @contextmanager ist ein Decorator, der aus einem Generator einen Context Manager baut.

3. Details, die Interviewer fragen

  1. Syntax-Zucker: @d über def f ist dasselbe wie f = d(f). Das passiert einmal, beim Laden des Moduls.
  2. Decorator mit Parameter: Er braucht drei Ebenen. Die Factory nimmt die Parameter. Der Decorator nimmt die Funktion. Der wrapper nimmt die Argumente.
  3. *args, **kwargs: Der wrapper nimmt alle Argumente und reicht sie weiter. So passt er auf jede Signatur.
  4. functools.wraps: Es kopiert __name__, __qualname__, __doc__ und __module__. Es setzt auch __wrapped__. Ohne es sind Logs, Tracebacks und Doku falsch.
  5. Klassen-Decorator: @dataclass nimmt eine Klasse und fügt __init__, __repr__ und __eq__ hinzu.
  6. Eingebaute Decorators: Es gibt @property, @staticmethod, @classmethod, @functools.cache, @functools.lru_cache(maxsize=…) und @functools.singledispatch.
  7. Decorator-Ausdrücke: Seit 3.9 (PEP 614) darf nach @ jeder Ausdruck stehen, zum Beispiel @handlers["x"].
  8. __exit__-Signatur: Sie ist __exit__(self, exc_type, exc_value, traceback). Ohne Exception sind alle drei None.
  9. Mehrere Manager: with a() as x, b() as y: geht. Klammern über mehrere Zeilen sind offiziell seit 3.10 erlaubt.
  10. Async: async with ruft __aenter__ und __aexit__. contextlib.asynccontextmanager baut ihn aus einem async Generator.
  11. contextlib-Werkzeuge: suppress ignoriert eine Exception. closing ruft close(). ExitStack verwaltet dynamisch viele Manager. nullcontext ist ein Platzhalter. chdir wechselt das Arbeitsverzeichnis (seit 3.11).
  12. Context Manager als Decorator: Ein mit @contextmanager gebauter Manager kann auch als @transaktion("t") über einer Funktion stehen (ContextDecorator).

4. Fallen

  • „Ein Decorator läuft bei jedem Aufruf.“ → Falsch. Der Decorator läuft einmal bei der Definition. Bei jedem Aufruf läuft der wrapper.
  • „Der obere Decorator wird zuerst angewendet.“ → Falsch. Der untere zuerst. Beim Aufruf ist der obere aussen.
  • „__exit__ läuft nur ohne Fehler.“ → Falsch. Es läuft immer, auch bei Exception, return und break.
  • „__exit__ soll True zurückgeben.“ → Falsch. True verschluckt die Exception. Normal ist None/False.
  • „@contextmanager räumt automatisch auf.“ → Nur mit try/finally um das yield.
  • „@lru_cache auf einer Methode ist harmlos.“ → Falsch. Der Cache hält self und verhindert Garbage Collection.

5. Selbsttest

Warum?

Warum functools.wraps?

Es kopiert Name, Docstring und Modul der Original-Funktion und setzt __wrapped__. Sonst heisst alles wrapper.

Was passiert, wenn __exit__ True zurückgibt?

Die Exception ist verschluckt und fliegt nicht weiter. Das nutzt z. B. contextlib.suppress.

with vs try/finally?

Gleiche Garantie. with bündelt Öffnen und Schliessen in einem wiederverwendbaren Objekt.

Wann läuft der Decorator-Code?

Einmal bei der Definition, meist beim Import des Moduls. Bei jedem Aufruf läuft der wrapper.

Wie innen?

Was ist ein Decorator?

Eine Funktion, die eine Funktion nimmt und eine neue zurückgibt. @d über def f ist f = d(f).

Wie schreiben Sie einen Decorator mit Parametern?

Mit drei Ebenen: eine Factory nimmt die Parameter, gibt den Decorator zurück, der den wrapper zurückgibt.

Was ist eine Closure?

Eine innere Funktion, die sich Variablen der äusseren Funktion merkt. Der wrapper merkt sich so func.

Was ist ein Context Manager?

Ein Objekt mit __enter__ und __exit__. Mit with öffnet es eine Ressource und schliesst sie immer.

Was gibt __enter__ zurück?

Den Wert für die Variable nach as. Bei open() ist das die Datei selbst.

Welche Parameter hat __exit__?

exc_type, exc_value und traceback. Ohne Exception sind alle None.

Wie funktioniert @contextmanager?

Code vor yield ist enter, der yield-Wert geht an as, Code nach yield ist exit. Aufräumen gehört in finally.

Wie macht man einen asynchronen Context Manager?

Mit __aenter__ und __aexit__ oder mit contextlib.asynccontextmanager. Nutzung mit async with.

Zahlen

cache vs lru_cache?

cache hat keine Grenze. lru_cache(maxsize=n) wirft die am längsten nicht genutzten Einträge raus.

Wie viele Ebenen hat ein Decorator mit Parameter?

Drei: die Factory mit den Parametern, der Decorator mit der Funktion und der wrapper mit den Argumenten.

Wie viele Parameter hat __exit__?

Drei: exc_type, exc_value und traceback. Ohne Exception sind alle None.

Vergleich

Python-Decorator vs Java-Annotation?

Die Annotation ist nur Metadaten für ein Framework. Der Decorator ist Code, der die Funktion sofort ersetzt.

Kann ein Context Manager auch Decorator sein?

Ja. Ein mit @contextmanager gebauter Manager kann über einer Funktion stehen und umhüllt dann jeden Aufruf.

Welche eingebauten Decorators kennen Sie?

property, staticmethod, classmethod, functools.cache, lru_cache, singledispatch, dataclass.

Was ist der Unterschied zwischen Decorator und Context Manager?

Ein Decorator ersetzt eine Funktion einmal bei der Definition. Ein Context Manager umschliesst einen Block bei jedem Eintritt mit enter und exit.

Produktion

Szenario: Ein Retry-Decorator legt Buchungen doppelt an. Was ist falsch?

Die Operation ist nicht idempotent. Nur idempotente Aufrufe wiederholen oder einen Idempotency-Key nutzen.

Szenario: Der Speicher eines Services wächst, im Code steht @lru_cache auf vielen Methoden. Ihr Verdacht?

Der Cache hält self und alle Argumente fest. Objekte werden nie freigegeben. Lösung: Cache auf Funktionsebene mit maxsize oder cached_property.

Szenario: Nach Fehlern bleiben DB-Verbindungen offen. Der Code nutzt @contextmanager. Wo suchen Sie?

Ob das yield in try/finally steht. Ohne finally läuft das Schliessen bei einer Exception nicht.

Design

Wofür ist ExitStack?

Für eine dynamische Zahl von Context Managern. Er schliesst sie in umgekehrter Reihenfolge.

Was macht @dataclass?

Es ist ein Klassen-Decorator. Er erzeugt __init__, __repr__ und __eq__ aus den Feldern.

In welcher Reihenfolge wirken gestapelte Decorators?

Der unterste wird zuerst angewendet. Beim Aufruf läuft der oberste aussen zuerst.

Mehr

Gerüst

  • Warum? Wiederkehrendes Verhalten an einer Stelle bündeln. Ressourcen werden auch bei Fehlern immer freigegeben.
  • Wie innen? @d über def f heisst f = d(f), einmal beim Laden. Der wrapper hält f als Closure. with ruft __enter__, dann __exit__ mit Exception-Info.
  • Zahlen Decorator mit Parameter hat 3 Ebenen. __exit__ hat 3 Parameter. lru_cache(maxsize=n) hat eine Grenze, cache nicht.
  • Vergleich Decorator (ersetzt Funktion) vs Context Manager (umschliesst Block). Python-Decorator vs Java-Annotation.
  • Produktion Retry doppelt gebucht (nicht idempotent). @lru_cache auf Methoden hält self. @contextmanager ohne finally lässt Verbindungen offen.
  • Design functools.wraps immer nutzen. __exit__ gibt normal None zurück. Gestapelte Decorators: der untere läuft zuerst.

Beispiel: Decorators und Context Manager bauen

import functools, time
from contextlib import contextmanager, suppress, ExitStack

print("1) Decorator ohne und mit functools.wraps")
def ohne_wraps(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"  {func.__name__} dauerte {time.perf_counter() - t0:.4f} s")
    return wrapper

@ohne_wraps
def a():
    """Doku von a"""
@timed
def lade(n):
    """Laedt n Zeilen."""
    return sum(range(n))

print("  ohne wraps:", a.__name__, a.__doc__)
print("  mit wraps: ", lade.__name__, lade.__doc__)
print("  Ergebnis:", lade(1_000_000))

print("2) Decorator mit Parameter (Decorator-Factory)")
def retry(times):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for versuch in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except ConnectionError as e:
                    print(f"  Versuch {versuch} fehlgeschlagen: {e}")
            raise RuntimeError("aufgegeben")
        return wrapper
    return deco

zaehler = {"n": 0}
@retry(times=3)
def hole():
    zaehler["n"] += 1
    if zaehler["n"] < 3:
        raise ConnectionError("Timeout")
    return "OK"
print("  ->", hole())

print("3) Reihenfolge beim Stapeln")
def tag(name):
    def deco(f):
        print(f"  dekoriere mit {name}")
        @functools.wraps(f)
        def w():
            return f"{name}({f()})"
        return w
    return deco
@tag("aussen")
@tag("innen")
def kern():
    return "x"
print("  Aufruf:", kern())

print("4) functools.cache")
@functools.cache
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)
print("  fib(80) =", fib(80), "|", fib.cache_info())

print("5) Context Manager als Klasse")
class Verbindung:
    def __enter__(self):
        print("  __enter__: oeffnen")
        return self
    def __exit__(self, exc_type, exc, tb):
        print(f"  __exit__: schliessen (Fehler: {exc_type.__name__ if exc_type else None})")
        return False
try:
    with Verbindung():
        raise ValueError("kaputt")
except ValueError as e:
    print("  Exception kommt weiter:", e)

print("6) @contextmanager")
@contextmanager
def transaktion(name):
    print(f"  BEGIN {name}")
    try:
        yield name
        print(f"  COMMIT {name}")
    except Exception:
        print(f"  ROLLBACK {name}")
        raise
with transaktion("t1"):
    pass
try:
    with transaktion("t2"):
        1 / 0
except ZeroDivisionError:
    print("  ZeroDivisionError weitergegeben")

print("7) suppress und ExitStack")
with suppress(FileNotFoundError):
    open("gibt_es_nicht.txt")
print("  FileNotFoundError unterdrueckt")
with ExitStack() as stack:
    for i in range(3):
        stack.enter_context(transaktion(f"x{i}"))
    print("  alle drei offen")

Echte Ausgabe, Python 3.12 (3.12.10, python -I deco_demo.py). Die Zeit bei lade schwankt.

  1. wraps: Ohne functools.wraps heisst die Funktion danach wrapper und verliert ihren Docstring. Mit wraps bleiben __name__, __doc__ und __wrapped__ erhalten.
  2. try/finally im wrapper: Die Zeit wird auch gemessen, wenn die Funktion eine Exception wirft.
  3. Factory: @retry(times=3) ruft zuerst retry(3) auf. Erst dessen Rückgabe ist der eigentliche Decorator. Darum drei Ebenen.
  4. Stapeln: Der untere Decorator wird zuerst angewendet. Beim Aufruf ist der obere aussen: aussen(innen(x)).
  5. cache: fib(80) braucht nur 81 echte Berechnungen statt Milliarden. cache_info() zeigt Treffer und Fehlschläge.
  6. __exit__ gibt False: Die Verbindung wird geschlossen, aber der ValueError geht trotzdem weiter.
  7. @contextmanager: Code vor yield ist __enter__, Code danach ist __exit__. Das raise im except gibt den Fehler weiter.
  8. ExitStack: öffnet beliebig viele Manager und schliesst sie in umgekehrter Reihenfolge (LIFO).

Vergleich

  • Decorator vs Vererbung: Decorator fügt Verhalten pro Funktion hinzu, ohne Klassenhierarchie. Vererbung ändert einen ganzen Typ.
  • Python-Decorator vs Java-Annotation: Eine Java-Annotation ist nur Metadaten; ein Framework (z. B. Spring AOP) wertet sie aus. Ein Python-Decorator ist Code, der sofort die Funktion ersetzt.
  • Python-Decorator vs Decorator Pattern (GoF): Das Pattern umhüllt Objekte zur Laufzeit. Der Python-Decorator umhüllt Funktionen oder Klassen bei der Definition.
  • with vs try/finally: gleiche Garantie. with bündelt Öffnen und Schliessen an einer Stelle und ist wiederverwendbar.
  • with vs Java try-with-resources: gleiche Idee. Java ruft close(); Python ruft __exit__ und kann die Exception sehen und verschlucken.
  • Klasse vs @contextmanager: Klasse für Zustand und Wiederverwendung. Generator-Variante für kurze Fälle.

In der Produktion

  1. Retry ohne Grenze und ohne Pause: Ein Retry-Decorator hämmert auf einen kaputten Dienst. Lösung: maximale Versuche, Backoff mit Jitter, nur bei vorübergehenden Fehlern wiederholen.
  2. Retry bei nicht idempotenter Aktion: Ein wiederholtes „Buchung anlegen“ erzeugt Duplikate. Lösung: nur idempotente Operationen wiederholen.
  3. lru_cache auf Methoden: Der Cache hält self fest. Objekte werden nicht freigegeben, der Speicher wächst. Lösung: Cache auf Modulfunktionen oder functools.cached_property.
  4. @cache ohne Grenze: Bei vielen verschiedenen Argumenten wächst er unendlich. Lösung: lru_cache(maxsize=…).
  5. Verschluckte Exceptions: Ein __exit__, das True zurückgibt, versteckt Fehler. Lösung: nur gezielte Typen unterdrücken, z. B. mit suppress(FileNotFoundError).
  6. @contextmanager ohne try/finally: Bei einer Exception läuft der Code nach yield nicht. Die Ressource bleibt offen. Lösung: yield immer in try/finally.

Diagnose

  • f.__wrapped__: die Original-Funktion hinter einem Decorator. inspect.unwrap(f) geht durch alle Schichten.
  • inspect.signature(f): zeigt dank wraps die echte Signatur, nicht (*args, **kwargs).
  • f.cache_info() und f.cache_clear(): Trefferquote und Reset von lru_cache.
  • Traceback lesen: Zeilen mit wrapper zeigen jede Decorator-Schicht.
  • ResourceWarning: mit python -X dev oder -W default sieht man nicht geschlossene Dateien.

Senior-Punkte

  1. Decorators für Querschnittsthemen: Logging, Metriken, Retry, Auth, Caching. Business-Logik gehört nicht hinein.
  2. Immer functools.wraps. Sonst sind Logs, Monitoring und Doku falsch.
  3. Jede Ressource mit Lebensdauer bekommt einen Context Manager: Datei, Verbindung, Lock, Transaktion, temporäres Verzeichnis.
  4. Zu viele Decorator-Schichten machen Debugging schwer. Drei gestapelte sind meist die Grenze.
  5. Retry ist eine Designentscheidung: nur bei idempotenten Aufrufen, mit Backoff und Grenze, und mit Log jedes Versuchs.
  6. Exceptions nie still verschlucken. Ein Context Manager räumt auf und lässt den Fehler weiterfliegen.
