pytest

Kern: pytest ist ein Test-Framework für Python. Es findet Tests nach Namen und schreibt assert um, damit Fehler genau zeigen, was nicht stimmt. Fixtures liefern Testdaten und Aufräumen, parametrize führt einen Test mit vielen Eingaben aus.

Antwort-Muster

Frage: Wie funktionieren Fixtures in pytest?

  1. Mechanismus: Ein Test nennt eine Fixture als Parameter. pytest ruft sie vorher auf und gibt den Wert in den Test.
  2. Zahl: Der Standard-Scope ist function. Es gibt auch class, module, package und session.
  3. Trade-off: Ein grosser Scope spart Zeit, teilt aber Zustand zwischen Tests. Das macht Tests abhängig.
  4. Produktion: Mit yield räume ich auf. Gemeinsame Fixtures liegen in conftest.py.

1. Ein Testlauf in 7 Schritten

  1. Entdecken: pytest sucht Dateien test_*.py oder *_test.py. Darin nimmt es Funktionen mit Präfix test.
  2. Import: pytest importiert Test-Module mit einem Import Hook. Der schreibt assert so um, dass Fehler Details zeigen.
  3. Sammeln: parametrize macht aus einer Funktion mehrere Test-Fälle.
  4. Fixtures aufbauen: Für jeden Parameter im Test ruft pytest die Fixture auf. Bei yield läuft der Teil davor als Setup.
  5. Test ausführen: Wirft ein assert eine Ausnahme, ist der Test fehlgeschlagen.
  6. Teardown: Der Code nach yield läuft in umgekehrter Reihenfolge.
  7. Exit Code: 0 heisst alles bestanden, 1 heisst Tests fehlgeschlagen. Die Codes 2 bis 6 haben eigene Bedeutungen.

2. Aufbau

  1. Test-Datei: Funktionen test_*. Jeder Parameter, der eine Fixture nennt, bekommt deren Wert.
  2. conftest.py: Fixtures darin gelten für alle Tests im Verzeichnis. Man importiert sie nicht.
  3. Fixture: Eine Funktion mit @pytest.fixture. Sie gibt einen Wert zurück oder liefert ihn mit yield.
  4. Scope: Wie lange eine Fixture lebt: function (Standard), class, module, package, session.
  5. Marks: Zum Beispiel skip, xfail und eigene Marker zum Auswählen.
  6. Eingebaute Fixtures: tmp_path, monkeypatch, capsys.

3. Details

  1. Entdeckung: Dateien test_*.py oder *_test.py. Funktionen mit Präfix test. Klassen mit Präfix Test und ohne __init__. Auch unittest.TestCase läuft.
  2. Assert Rewriting: Ein Import Hook schreibt assert in Test-Modulen um. Fehler zeigen dann die Werte. Helfer-Module ausserhalb der Tests werden nicht umgeschrieben, ausser man meldet sie mit register_assert_rewrite an.
  3. Fixture-Scope: Standard ist function, die Fixture wird nach dem Test zerstört. Ein grösserer Scope wie session teilt den Wert zwischen Tests.
  4. Caching in einem Test: Fordert ein Test dieselbe Fixture mehrmals an, entsteht sie nur einmal. Der Wert wird wiederverwendet.
  5. yield-Fixture: Der Code nach yield ist das Teardown. Es läuft in umgekehrter Reihenfolge. Wirft die Fixture vor dem yield, läuft ihr Teardown nicht.
  6. autouse: Mit autouse=True läuft eine Fixture für jeden Test, ohne dass er sie nennt. Das versteckt Abhängigkeiten und sollte selten sein.
  7. parametrize: Ein Test läuft mit mehreren Eingaben, je einer pro Fall. Gestapelte Dekoratoren ergeben das kartesische Produkt. Mit pytest.param(..., marks=pytest.mark.xfail) markiert man einzelne Fälle.
  8. monkeypatch: Methoden wie setattr, setenv, setitem, chdir. Alle Änderungen werden nach dem Test zurückgesetzt. Man patcht den Namen, den der Code benutzt.
  9. pytest.raises: Prüft, dass eine Ausnahme kommt. Mit match prüft man den Text per re.search, ein Teiltreffer genügt.
  10. pytest.approx: Vergleicht Fliesskommazahlen mit Toleranz. Beispiel: 0.1 + 0.2 == pytest.approx(0.3).
  11. Exit Codes: 0 alle bestanden, 1 Tests fehlgeschlagen, 2 Abbruch durch den Benutzer, 3 interner Fehler, 4 falsche Befehlszeile, 5 keine Tests gesammelt. Code 6 gilt, wenn die Grenze --max-warnings überschritten wird.
  12. Import-Modus: Der Standard heisst prepend. Die Doku empfiehlt importlib für neue Projekte. Bei prepend müssen Test-Dateinamen eindeutig sein.

4. Fallen

  • „Eine Fixture mit Scope session ist harmlos.“ → Falsch. Sie teilt Zustand zwischen allen Tests. Tests hängen dann von der Reihenfolge ab.
  • „Das Teardown läuft immer.“ → Falsch. Wirft die yield-Fixture vor dem yield, läuft ihr Teardown nicht. Aufräumen gehört darum in Fixtures, die einzeln sauber starten.
  • „Exit Code 5 heisst, Tests sind fehlgeschlagen.“ → Falsch. 5 heisst: keine Tests gesammelt. Fehlgeschlagen ist 1.
  • „monkeypatch.setattr(os, "getcwd", ...) ist die richtige Stelle.“ → Falsch. Man patcht den Namen im Modul, das ihn benutzt, nicht das Original.
  • „Zwei parametrize-Dekoratoren laufen parallel.“ → Falsch. Sie ergeben das kartesische Produkt: 2 mal 2 Werte sind 4 Läufe.
  • „assert 0.1 + 0.2 == 0.3 ist ein guter Test.“ → Falsch. Fliesskommazahlen brauchen pytest.approx.

5. Selbsttest

Warum?

Warum nutzt man pytest statt unittest?

pytest braucht nur einfache Funktionen und assert. Die Fehlermeldungen sind detailliert, und Fixtures und parametrize sind einfacher als setUp und Schleifen.

Warum schreibt pytest assert um?

Damit ein Fehler die Werte beider Seiten zeigt. Das geschieht beim Import mit einem Import Hook.

Warum gibt es Scopes bei Fixtures?

Teure Setups wie eine Datenbank-Verbindung will man nicht für jeden Test neu bauen. Ein grösserer Scope teilt sie.

Wie innen?

Wie findet pytest Tests?

Es sucht Dateien test_*.py oder *_test.py. Darin nimmt es Funktionen mit Präfix test und Methoden in Klassen mit Präfix Test ohne __init__.

Wie ruft pytest eine Fixture auf?

Der Name im Parameter des Tests ist der Schlüssel. pytest findet die Fixture, ruft sie auf und gibt den Wert in den Test. Fixtures können andere Fixtures anfordern.

Was passiert bei yield in einer Fixture?

Der Code vor yield ist das Setup, der Wert von yield geht in den Test. Der Code danach läuft als Teardown in umgekehrter Reihenfolge.

Was macht parametrize?

Es erzeugt beim Sammeln mehrere Test-Fälle aus einer Funktion, je einen pro Parameter-Satz. Jeder Fall läuft einzeln und kann einzeln fehlschlagen.

Wie funktioniert monkeypatch?

Es ersetzt Attribute, Umgebungsvariablen oder Dict-Einträge während des Tests. Nach dem Test macht pytest alle Änderungen rückgängig.

Was ist conftest.py?

Eine Datei für gemeinsame Fixtures und Hooks. Sie gilt für alle Tests im Verzeichnis und darunter. Man importiert sie nicht.

Zahlen

Welche Scopes gibt es und was ist der Standard?

function, class, module, package, session. Standard ist function.

Welche Exit Codes hat pytest?

0 bestanden, 1 Tests fehlgeschlagen, 2 Abbruch, 3 interner Fehler, 4 falsche Befehlszeile, 5 keine Tests, 6 Warnungs-Grenze überschritten.

Wie viele Läufe ergeben zwei gestapelte parametrize mit je 2 Werten?

Vier. Gestapelte Dekoratoren ergeben das kartesische Produkt.

Vergleich

pytest vs unittest?

unittest braucht Klassen und assertEqual. pytest nutzt Funktionen und assert und führt auch unittest-Tests aus.

Fixture vs setUp/tearDown?

Fixtures sind einzeln wählbar, haben Scopes und lassen sich kombinieren. setUp gilt für die ganze Klasse.

monkeypatch vs unittest.mock.patch?

monkeypatch ist eine Fixture mit automatischem Zurücksetzen. mock.patch bietet dazu Mock-Objekte mit Aufruf-Prüfung. Beide ersetzen Namen im benutzten Modul.

skip vs xfail?

skip führt den Test nicht aus. xfail führt ihn aus und erwartet einen Fehler. Besteht er trotzdem, meldet pytest xpassed.

Produktion

Was tun bei Tests, die nur manchmal fehlschlagen?

Meist teilen Tests Zustand, etwa über einen grossen Scope oder globale Variablen. Lösung: jeder Test bekommt eigenen Zustand, zum Beispiel über tmp_path.

Was tun, wenn ein Test ohne Fehler "ok" meldet, aber nichts prüft?

Prüfen, ob ein assert fehlt oder eine Bedingung immer wahr ist. Auch Exit Code 5 beachten: keine Tests gesammelt ist kein Erfolg.

Szenario: In der CI laufen 0 Tests, aber der Build ist grün. Warum?

Vielleicht fehlt der Pfad, oder die Dateinamen passen nicht. Dann endet pytest mit Exit Code 5. Wenn die CI diesen Code nicht als Fehler zählt, bleibt der Build grün. Lösung: Exit Code beachten und Namen prüfen.

Szenario: Ein Test ändert eine Umgebungsvariable und andere Tests brechen. Was tun Sie?

Ich nutze monkeypatch.setenv statt os.environ zu ändern. pytest setzt den Wert nach dem Test zurück.

Design

Wie bauen Sie einen sauberen Datenbank-Test?

Eine Fixture mit yield: Verbindung öffnen, Daten anlegen, nach yield aufräumen. Pro Test eine Transaktion oder eine frische Datei in tmp_path.

Wann nutzen Sie parametrize?

Wenn dieselbe Logik mit vielen Eingaben und Erwartungen läuft. Jeder Fall wird einzeln gemeldet, und Randfälle sind sichtbar.

Wie prüfen Sie eine erwartete Ausnahme?

Mit pytest.raises(ValueError, match="text"). match prüft den Text mit re.search.

Wie organisieren Sie Tests im Projekt?

Ein tests-Ordner neben dem Code, am besten mit src-Layout. Gemeinsame Fixtures in conftest.py. Dateinamen eindeutig oder importlib-Modus.

Mehr

Gerüst

  • Warum? Einfache Tests mit assert, klare Fehler, wiederverwendbare Fixtures.
  • Wie innen? Entdecken, Import mit assert-Umschreiben, Sammeln, Fixtures, Test, Teardown rückwärts.
  • Zahlen Scopes: function (Standard), class, module, package, session. Exit Codes 0 bis 6.
  • Vergleich unittest braucht Klassen. monkeypatch statt Hand-Patch. skip gegen xfail.
  • Produktion Geteilter Zustand macht Tests flaky. Exit Code 5 heisst keine Tests.
  • Design yield für Aufräumen. parametrize für Eingaben. conftest.py für Gemeinsames.

Beispiel: Fixture, parametrize und raises

import pytest

@pytest.fixture
def konto():
    k = {"saldo": 100}
    yield k                       # Setup davor, Teardown danach
    k.clear()

@pytest.mark.parametrize("betrag, erwartet", [(10, 90), (100, 0), (0, 100)])
def test_abheben(konto, betrag, erwartet):
    konto["saldo"] -= betrag
    assert konto["saldo"] == erwartet

def test_zu_viel(konto):
    with pytest.raises(ValueError, match="Saldo"):
        if konto["saldo"] < 500:
            raise ValueError("Saldo zu klein")

def test_float():
    assert 0.1 + 0.2 == pytest.approx(0.3)

Nicht ausgeführt. pytest ist auf dieser Maschine nicht installiert.

  1. konto ist eine Fixture mit yield. Der Test bekommt das Dict. Danach läuft k.clear() als Teardown.
  2. parametrize macht aus test_abheben drei Fälle. Jeder bekommt eine frische Fixture, weil der Scope function ist.
  3. pytest.raises prüft die Ausnahme. match="Saldo" sucht den Text per re.search.
  4. pytest.approx vergleicht mit Toleranz.
  5. Erwartet wird ein Lauf mit 5 Tests (3 + 1 + 1) und Exit Code 0. Das folgt aus der Doku und wurde nicht ausgeführt.

Vergleich

  • pytest: Funktionen, assert, Fixtures, parametrize, Plugins.
  • unittest: Teil der Standardbibliothek, Klassen und assertEqual. pytest führt diese Tests auch aus.
  • monkeypatch: Fixture, setzt alles nach dem Test zurück.
  • unittest.mock: Mock-Objekte, mit Prüfung der Aufrufe.
  • skip: nicht ausführen. xfail: ausführen, Fehler erwartet.
  • tmp_path: eigener Ordner pro Test. Besser als feste Pfade.

Produktion

  1. Flaky Tests: Geteilter Zustand über Scopes oder globale Variablen. Lösung: eigener Zustand pro Test.
  2. Grüner Build ohne Tests: Exit Code 5 wird übersehen. Lösung: Code in der CI prüfen und Sammelpfad kontrollieren.
  3. Namenskonflikte: Im Modus prepend brauchen Test-Dateien eindeutige Namen. Lösung: importlib oder eindeutige Namen.
  4. Umgebung leckt: Ein Test ändert os.environ. Lösung: monkeypatch.setenv.
  5. Langsame Suite: Jeder Test baut eine Datenbank neu. Lösung: grösserer Scope mit sauberem Rollback.
  6. Falsch gepatcht: Der Test patcht das Original statt den benutzten Namen. Lösung: im benutzenden Modul patchen.

Diagnose: Werkzeuge und Befehle

  • pytest -x: stoppt beim ersten Fehler.
  • pytest -k ausdruck: führt Tests nach Namen aus.
  • pytest --lf: wiederholt nur die letzten Fehler.
  • pytest -v: zeigt jeden Test mit Namen und Parametern.
  • pytest --fixtures: listet verfügbare Fixtures.
  • pytest --collect-only: zeigt, was gesammelt würde.

Senior-Punkte

  1. Tests müssen unabhängig sein. Jeder Test läuft allein und in jeder Reihenfolge.
  2. Scope ist ein Trade-off: Geschwindigkeit gegen Isolation. Im Zweifel function.
  3. autouse sparsam nutzen. Es versteckt Abhängigkeiten.
  4. Exit Codes in der CI beachten. Keine Tests gesammelt darf nicht grün sein.
  5. Patch am benutzten Namen. Besser noch: Abhängigkeiten übergeben, dann braucht man kein Patchen.
  6. Neue Projekte: src-Layout und importlib-Modus, wie die Doku empfiehlt.
