venv, pip, Packaging

Kern: Ein venv ist ein Ordner mit eigenem Interpreter und eigenem site-packages. pip installiert Pakete dort hinein, meist als wheel, also als fertiges ZIP. Das Projekt beschreibt sich selbst in pyproject.toml, und ein Build-Backend macht daraus sdist und wheel.

Antwort-Muster

Frage: Wie funktioniert ein venv, und was macht pip install?

  1. Mechanismus: Das venv hat eine pyvenv.cfg, einen Interpreter und ein eigenes site-packages. pip entpackt Wheels dorthin.
  2. Zahl: Seit Python 3.12 enthält ein neues venv nur noch pip, kein setuptools mehr.
  3. Trade-off: Ein Wheel wird nur entpackt, ein sdist muss zuerst gebaut werden. Das ist langsamer und riskanter.
  4. Produktion: Ich pinne Versionen, nutze pro Projekt ein venv und installiere in der CI mit Hashes, wenn es streng sein muss.

1. pip install in 7 Schritten

  1. Befehl: pip install demopkg läuft mit dem Python des venv, wenn man python -m pip aus dem venv nutzt.
  2. Index fragen: pip sucht die Dateien zum Namen in einem Paketindex, normalerweise PyPI. Er kann auch ein lokaler Ordner sein.
  3. Auflösen: Der Resolver sucht Versionen, die zu allen Anforderungen passen. Passt eine Annahme nicht, geht er zurück (Backtracking).
  4. Datei wählen: Ein Wheel passt, wenn seine Tags zum Python passen. Zum Beispiel passt py3-none-any überall.
  5. Bauen: Gibt es nur ein sdist, kann pip es nicht direkt installieren. Es ruft das Build-Backend auf, das in pyproject.toml steht, und baut ein Wheel.
  6. Entpacken: Ein Wheel enthält genau die Dateien, die kopiert werden. pip kopiert sie nach site-packages.
  7. Metadaten: Es entsteht name-version.dist-info mit METADATA und RECORD. RECORD listet alle Dateien mit Hash.

2. Aufbau

  1. pyproject.toml beschreibt Build und Metadaten des Projekts.
  2. Das Build-Backend baut aus dem Quellcode ein sdist und ein wheel.
  3. Ein sdist ist ein tar.gz mit dem Quellcode und der Datei PKG-INFO.
  4. Ein wheel ist ein ZIP und direkt installierbar.
  5. Das venv ist ein Ordner mit eigenem Interpreter und eigenen Paketen.
  6. Der Index liefert die Dateien. PyPI ist der Standard.

3. Details

  1. Was venv anlegt: Ein Ordner mit pyvenv.cfg, einem Unterordner bin (Windows: Scripts) und lib/pythonX.Y/site-packages. Der Interpreter ist dort eine Kopie oder ein Symlink. Der Schlüssel home zeigt auf das Basis-Python.
  2. sys.prefix: Im venv zeigt sys.prefix auf das venv. sys.base_prefix zeigt auf das Basis-Python. Ist sys.prefix != sys.base_prefix, läuft man im venv.
  3. Aktivieren ist optional: Die Aktivierung stellt nur den Ordner bin oder Scripts vorne in den PATH. Der volle Pfad zum Interpreter im venv reicht auch.
  4. Nicht verschiebbar: Skripte im venv haben absolute Pfade. Ein kopiertes oder verschobenes venv bricht. Man baut es neu, zum Beispiel mit pip install -r requirements.txt.
  5. Seit 3.12: setuptools ist keine Kern-Abhängigkeit des venv mehr. Ein neues venv enthält nur pip. Wer setuptools braucht, muss es installieren oder über build-system.requires holen.
  6. System-Pakete: Mit --system-site-packages sieht das venv auch die Pakete des Basis-Python. In pyvenv.cfg steht dann include-system-site-packages = true.
  7. pyproject.toml: Der Abschnitt [build-system] sollte immer da sein. Er nennt requires und build-backend. Im Abschnitt [project] ist nur name nie dynamisch. version darf das Backend liefern.
  8. sdist und wheel: Ein sdist ist ein tar.gz mit Quellcode und PKG-INFO. Ein wheel ist ein ZIP mit genau den Dateien zum Kopieren. Man lädt am besten beide hoch.
  9. Wheel-Name: Das Muster ist name-version-python-abi-platform.whl. Bei py3-none-any läuft das Paket auf jedem Python 3 und jeder Plattform. Das ist typisch für reinen Python-Code.
  10. Resolver: Seit pip 20.3 kann er zurückgehen (Backtracking). Passt nichts zusammen, kommt ResolutionImpossible. Ein Constraints-File begrenzt Versionen von indirekten Abhängigkeiten.
  11. Hashes und Pins: Mit --require-hashes muss jede Anforderung gepinnt sein, zum Beispiel mit ==. Mit --only-binary :all: baut pip nichts selbst und nimmt nur fertige Wheels.
  12. Extras und Skripte: optional-dependencies definiert Extras wie pip install name[gui]. [project.scripts] erzeugt Kommandos auf der Kommandozeile.

4. Fallen

  • „Ein venv kopiert das ganze Python.“ → Falsch. Es ist ein kleiner Ordner mit pyvenv.cfg, einem Interpreter (Kopie oder Symlink) und eigenem site-packages.
  • „Man muss ein venv aktivieren, sonst geht es nicht.“ → Falsch. Der volle Pfad zum Interpreter reicht. Aktivieren ändert nur den PATH.
  • „Ein venv kann man in einen anderen Ordner kopieren.“ → Falsch. Es hat absolute Pfade. Man erstellt es neu.
  • „pip install führt immer ein setup.py aus.“ → Falsch. Ein Wheel wird nur entpackt. Nur ein sdist wird zuerst vom Build-Backend gebaut.
  • „pip freeze ist ein Lockfile mit Hashes.“ → Falsch. Es listet die installierten Versionen ohne Hashes. Hashes braucht --require-hashes mit einer Datei, die sie enthält.
  • „Ein neues venv in 3.12 enthält setuptools.“ → Falsch. Seit 3.12 nicht mehr. Es enthält nur pip.

5. Selbsttest

Warum?

Warum ein venv pro Projekt?

Jedes Projekt hat eigene Versionen. So stören sich Projekte nicht, und das System-Python bleibt sauber.

Warum ist ein Wheel besser als ein sdist?

Es wird nur entpackt. Es gibt keinen Build, also schneller und ohne Compiler.

Warum pinnt man Versionen?

Ohne Pins kann ein neues Release den Build ändern. Mit Pins ist die Installation wiederholbar.

Wie innen?

Was liegt in einem venv?

pyvenv.cfg, Scripts oder bin mit Interpreter, und site-packages.

Wie erkennt Python, dass es im venv läuft?

Über pyvenv.cfg. Dann ist sys.prefix anders als sys.base_prefix.

Was macht pip bei einem Wheel?

Es entpackt die Dateien nach site-packages und legt .dist-info an.

Was macht pip bei einem sdist?

Es ruft das Build-Backend aus pyproject.toml auf. Das baut ein Wheel. Dieses wird dann installiert.

Was steht in RECORD?

Alle installierten Dateien mit Hash und Grösse. pip nutzt es beim Deinstallieren.

Wie löst pip Konflikte?

Der Resolver probiert Versionen und geht zurück, wenn etwas nicht passt (Backtracking). Sonst kommt ResolutionImpossible.

Zahlen

Seit wann kann der pip-Resolver zurückgehen?

Seit pip 20.3.

Was ändert sich im venv in Python 3.12?

setuptools ist keine Kern-Abhängigkeit mehr. Ein neues venv hat nur pip.

Was bedeutet py3-none-any?

Das Wheel läuft auf jedem Python 3. Es hängt von keiner ABI und keiner Plattform ab.

Vergleich

sdist vs wheel?

Das sdist ist der Quellcode und muss gebaut werden. Das Wheel ist fertig und wird nur kopiert.

--system-site-packages vs isoliertes venv?

Mit dem Flag sieht das venv auch System-Pakete. Isoliert sieht es nur seine eigenen.

requirements.txt vs pyproject.toml?

requirements.txt listet Pakete zum Installieren, oft mit Pins. pyproject.toml beschreibt das Projekt selbst, mit Build und Abhängigkeiten.

Constraints-File vs requirements.txt?

Ein Constraints-File begrenzt nur Versionen, es installiert nichts. Eine requirements-Datei installiert Pakete.

Produktion

Was geht kaputt, wenn man ein venv verschiebt?

Skripte zeigen auf alte absolute Pfade. Lösung: venv löschen und neu bauen.

Wie macht man Installationen wiederholbar?

Versionen pinnen, bei Bedarf Hashes nutzen, und immer in einem frischen venv installieren.

Szenario: Es läuft lokal, aber in der CI fehlt ein Paket. Warum?

Lokal kam das Paket aus dem System-Python oder einem anderen venv. Lösung: frisches venv, alles aus der Abhängigkeitsliste installieren.

Szenario: pip install dauert Minuten und lädt ein Paket oft neu. Was ist das?

Das ist Backtracking des Resolvers. Lösung: Pins oder ein Constraints-File setzen und Anforderungen lockern.

Szenario: Ein Build soll nur geprüfte Dateien installieren. Was tun Sie?

Ich nutze --require-hashes mit gepinnten Versionen und --only-binary :all:.

Design

Wie strukturiert man ein neues Projekt?

pyproject.toml mit [build-system] und [project], Quellcode in einem Paket, ein venv pro Checkout.

Wie definiert man Extras?

Mit optional-dependencies, zum Beispiel gui = ["PyQt5"]. Installiert wird mit name[gui].

Wie liefert man ein Kommando mit?

Mit [project.scripts], zum Beispiel spam-cli = "spam:main_cli".

Wann reicht ein reines Python-Wheel?

Wenn kein Code kompiliert werden muss. Dann ist py3-none-any möglich.

Wann Version dynamisch?

Wenn das Backend sie aus dem Code oder einem Git-Tag liest. Dann steht dynamic = ["version"].

Gerüst

  • Warum? Isolierte Abhängigkeiten pro Projekt, wiederholbare Installation.
  • Wie innen? venv: pyvenv.cfg und eigenes site-packages. pip: Index, Resolver, Wheel entpacken, .dist-info.
  • Zahlen pip 20.3 Backtracking. Python 3.12 venv ohne setuptools. py3-none-any für reines Python.
  • Vergleich Wheel statt sdist. requirements.txt statt pyproject.toml für Apps, pyproject für Pakete.
  • Produktion Verschobenes venv bricht. Fehlende Pins ändern Builds. Backtracking kostet Zeit.
  • Design Frisches venv in der CI, Pins und Hashes, Backend in pyproject.toml.

Echte Ausgabe, Python 3.12.10 und pip 25.0.1 unter Windows. Das Wheel demopkg habe ich von Hand als ZIP mit __init__.py, METADATA, WHEEL und RECORD gebaut. Es kam kein Paket aus dem Netz. Pfade sind durch <python> und <scratch> ersetzt.

  1. pyvenv.cfg zeigt mit home auf das Basis-Python. include-system-site-packages = false heisst isoliert.
  2. Das neue venv enthält nur pip. In 3.12 gibt es dort kein setuptools mehr.
  3. pip installiert das Wheel ohne Build. Es entstehen demopkg und demopkg-1.0.dist-info.
  4. RECORD listet jede Datei mit Grösse. Die Datei RECORD selbst hat keine.
  5. Im venv ist sys.prefix != sys.base_prefix wahr, der Import geht und importlib.metadata kennt die Version.
  6. Im System-Python gibt es demopkg nicht. Das ist die Isolation.

Vergleich

  • venv: in der Standardbibliothek, ein Ordner, pip dabei.
  • virtualenv: ein Zusatz-Tool für denselben Zweck. Es ist hier nicht Teil der Python-Doku.
  • pip: installiert Pakete aus Index, Ordner oder Datei.
  • sdist: Quellcode, braucht ein Build-Backend.
  • wheel: fertig, nur entpacken.
  • requirements.txt: Liste zum Installieren, oft mit Pins.
  • Constraints-File: begrenzt Versionen von indirekten Abhängigkeiten.
  • Backends: setuptools, hatchling, flit, PDM und uv-build sind Beispiele aus der Doku.

Produktion

  1. Paket fehlt in der CI: Lokal kam es aus einer anderen Umgebung. Lösung: frisches venv und vollständige Liste.
  2. venv verschoben: Skripte brechen. Lösung: neu bauen.
  3. Build ändert sich von selbst: Es gibt keine Pins. Lösung: Versionen pinnen.
  4. Sehr lange Installation: Backtracking. Lösung: Pins, Constraints, weniger strenge Anforderungen.
  5. Kein Wheel für die Plattform: pip baut aus dem sdist und braucht einen Compiler. Lösung: Wheels bereitstellen oder passende Plattform wählen.
  6. Unerwartete Quelle: Ein Paket kommt von einem falschen Index. Lösung: Hashes und eine feste Quelle.

Diagnose: Werkzeuge und Befehle

  • python -m pip --version: zeigt pip und das Python, zu dem es gehört.
  • python -m pip list und pip freeze: zeigen installierte Pakete.
  • pip check: sucht Konflikte zwischen installierten Paketen.
  • pip install -v: zeigt Details zu Index, Wheel und Build.
  • python -c "import sys, pkgutil; print(sys.prefix, sys.base_prefix)": zeigt, ob man im venv ist.
  • importlib.metadata.version("name"): liest die installierte Version.

Senior-Punkte

  1. Ein venv pro Projekt, nie in das System-Python installieren.
  2. Wiederholbarkeit kommt von Pins und Hashes, nicht von pip freeze allein.
  3. Wheels sind der Normalfall. Ein sdist-Build ist ein Risiko, weil beliebiger Build-Code läuft.
  4. Das Backend ist austauschbar. pyproject.toml ist die Schnittstelle.
  5. Aktivieren ist Komfort. Skripte und CI rufen besser den Interpreter im venv direkt auf.
  6. Konflikte früh lösen. Backtracking ist ein Hinweis auf zu lose oder widersprüchliche Anforderungen.
