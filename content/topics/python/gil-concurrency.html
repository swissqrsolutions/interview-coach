GIL, Threads, Multiprocessing, asyncio

Kern: Der GIL (Global Interpreter Lock) erlaubt in CPython nur einem Thread, Python-Bytecode auszuführen. Darum bringen Threads bei I/O etwas, bei CPU-Arbeit aber nichts. Für CPU-Arbeit nimmt man Prozesse, für viele I/O-Aufrufe asyncio.

Antwort-Muster

Frage: Was ist der GIL und was bedeutet er für Threads?

  1. Mechanismus: Ein Lock im Interpreter. Nur ein Thread führt gleichzeitig Bytecode aus.
  2. Zahl: Der Thread-Wechsel wird alle 5 ms angeboten. Bei I/O gibt der Thread den GIL sofort frei.
  3. Trade-off: Threads sind gut für I/O, nutzlos für CPU. Prozesse nutzen alle Kerne, kosten aber Start und Pickle.
  4. Produktion: Für CPU-Last nehme ich ProcessPoolExecutor. Für tausende Verbindungen nehme ich asyncio.

1. Ein Thread-Wechsel in 6 Schritten

  1. Thread A hält den GIL: Nur wer den GIL hat, führt Bytecode aus. Alle anderen Threads warten.
  2. Thread B wartet: Er wartet auf den GIL mit einem Timeout. Das Intervall steht in sys.getswitchinterval().
  3. Timeout läuft ab: Standard sind 0.005 Sekunden. B setzt eine Anfrage, dass A abgeben soll.
  4. A gibt ab: A prüft die Anfrage an einem Prüfpunkt der Bytecode-Schleife. Dann lässt A den GIL los.
  5. B übernimmt: Welcher Thread als nächster läuft, entscheidet das Betriebssystem. Der Interpreter hat keinen eigenen Scheduler.
  6. Blockierende Aufrufe: Bei I/O gibt ein Thread den GIL immer frei. Auch manche C-Erweiterungen geben ihn frei, zum Beispiel bei Kompression oder Hashing.

Bei CPU-Arbeit wechseln die Threads nur hin und her. Sie laufen nie gleichzeitig. Das zeigt das Beispiel unten.

2. Aufbau

  1. Threads teilen einen Prozess und einen Heap. Sie sind billig, aber der GIL begrenzt sie.
  2. Prozesse haben je einen eigenen Interpreter und GIL. Daten gehen per Pickle durch eine Pipe.
  3. asyncio nutzt einen Thread. Tasks wechseln nur bei await.
  4. concurrent.futures bietet ThreadPoolExecutor und ProcessPoolExecutor mit gleicher Schnittstelle.
  5. Free-threaded Build hat keinen GIL. Er ist ein eigener Build, nicht der Standard.
  6. Die Wahl hängt von der Last ab: I/O-bound, CPU-bound oder viele Verbindungen.

3. Details

  1. Warum gibt es den GIL? Er macht das Objektmodell sicher gegen gleichzeitigen Zugriff. Das gilt auch für eingebaute Typen wie dict. Das macht den Interpreter einfacher, kostet aber Parallelität.
  2. Wann wird der GIL freigegeben? Bei I/O immer. Manche C-Erweiterungen geben ihn bei Kompression oder Hashing frei. Reiner Python-Code gibt ihn nur beim Wechsel alle 5 ms ab.
  3. Switch Interval: Standard 0.005 Sekunden. Man setzt ihn mit sys.setswitchinterval. Der Wert ist ein Wunsch, die echte Zeit kann länger sein.
  4. Race Condition trotz GIL: Der GIL schützt den Interpreter, nicht Ihre Logik. x += 1 sind mehrere Bytecodes. Ein Wechsel dazwischen verliert Updates. Darum braucht man threading.Lock.
  5. ThreadPoolExecutor: Seit 3.13 gilt min(32, process_cpu_count() + 4) Worker. Vorher war es cpu_count() + 4. Der Default ist für I/O gedacht.
  6. ProcessPoolExecutor: Der Default ist os.process_cpu_count() seit 3.13. Auf Windows sind höchstens 61 Worker erlaubt.
  7. Start Method: Windows und macOS nutzen spawn. Linux nutzte fork. Seit 3.14 ist forkserver der Standard auf POSIX. Bei spawn braucht man den Guard if __name__ == "__main__".
  8. Pickle: Argumente und Resultate gehen per Pickle zwischen Prozessen. Lambdas und lokale Funktionen lassen sich nicht pickeln. Grosse Daten zu kopieren kostet Zeit.
  9. asyncio Task: create_task startet eine Coroutine. Der Event Loop hält nur schwache Referenzen. Ohne eigene Referenz kann ein Task verschwinden. Sicherer ist TaskGroup (seit 3.11).
  10. Blockierender Code im Loop: Ein time.sleep oder requests.get in einer Coroutine stoppt alle Tasks. Lösung: asyncio.to_thread (seit 3.9) oder eine async-Bibliothek.
  11. gather bei Fehler: Der erste Fehler geht sofort an den Aufrufer. Die anderen Aufgaben laufen weiter. Mit return_exceptions=True kommen Fehler als Resultate zurück.
  12. Free Threading: Seit 3.13 gibt es einen Build ohne GIL. PEP 779 macht ihn ab 3.14 offiziell unterstützt. Er braucht Erweiterungen, die dafür markiert sind. Sonst schaltet Python den GIL wieder ein.

4. Fallen

  • „Threads machen CPU-Code schneller.“ → Falsch. Mit GIL läuft nur ein Thread gleichzeitig. Das Beispiel zeigt keinen Gewinn.
  • „Der GIL macht meinen Code thread-sicher.“ → Falsch. Er schützt nur den Interpreter. x += 1 kann Updates verlieren.
  • „asyncio ist parallel.“ → Falsch. Es ist nebenläufig in einem Thread. Es gewinnt bei I/O, nicht bei CPU.
  • „Mehr Threads sind immer schneller.“ → Falsch. Mehr Threads kosten Speicher und Wechsel. Bei CPU-Arbeit bringen sie nichts.
  • „Ein Prozess-Pool hat keine Kosten.“ → Falsch. Start, Pickle und Kopieren der Daten kosten Zeit. Kleine Aufgaben werden langsamer.
  • „requests.get in einer Coroutine ist ok.“ → Falsch. Es blockiert den ganzen Event Loop.

5. Selbsttest

Warum?

Warum gibt es den GIL?

Er macht das Objektmodell von CPython sicher gegen gleichzeitigen Zugriff. Das vereinfacht den Interpreter. Der Preis ist fehlende Parallelität bei Python-Code.

Warum helfen Threads bei I/O trotz GIL?

Bei I/O gibt ein Thread den GIL immer frei. Andere Threads rechnen, während einer wartet.

Warum braucht man trotz GIL ein Lock?

Der GIL schützt nur den Interpreter. Eine Operation wie x += 1 besteht aus mehreren Bytecodes. Ein Wechsel dazwischen verliert Updates.

Wie innen?

Wie wechselt CPython zwischen Threads?

Ein wartender Thread setzt nach dem Switch Interval eine Anfrage. Der laufende Thread gibt den GIL an einem Prüfpunkt ab. Das Betriebssystem wählt den nächsten Thread.

Was ist das Switch Interval?

Die gewünschte Zeitscheibe pro Thread, Standard 0.005 Sekunden. Man liest sie mit sys.getswitchinterval().

Was passiert bei einem Prozess-Pool mit einer Aufgabe?

Die Funktion und die Argumente werden gepickelt und an einen Worker geschickt. Der Worker rechnet und schickt das Resultat gepickelt zurück.

Wie funktioniert asyncio innen?

Ein Event Loop in einem Thread führt Tasks aus. Ein Task läuft bis zum nächsten await. Dann wählt der Loop den nächsten bereiten Task.

Was ist der Unterschied zwischen spawn und fork?

fork kopiert den laufenden Prozess. spawn startet einen neuen Interpreter und importiert das Hauptmodul. Darum braucht spawn den Guard if __name__ == "__main__".

Zahlen

Wie viele Worker hat ThreadPoolExecutor standardmässig?

Seit 3.13 min(32, process_cpu_count() + 4). Vorher min(32, cpu_count() + 4).

Wie viele Worker hat ProcessPoolExecutor standardmässig?

os.process_cpu_count() seit 3.13. Auf Windows höchstens 61.

Wie gross ist der Mehraufwand im Free-threaded Build?

Laut Doku im Mittel etwa 1 % auf macOS aarch64 bis 8 % auf x86-64 Linux, je nach Last. Das gilt für die pyperformance-Benchmarks.

Was ist die Start Method seit 3.14 auf Linux?

forkserver. Vorher war es fork. Windows und macOS nutzen spawn.

Vergleich

Threads, Prozesse oder asyncio: wie wählen Sie?

CPU-bound: Prozesse. I/O-bound mit wenigen Aufrufen: Threads. Tausende Verbindungen: asyncio. Blockierende Bibliotheken: Threads.

asyncio vs Threads bei I/O?

Beide laufen mit einem GIL. asyncio hat weniger Speicher pro Task und Wechsel nur bei await. Dafür braucht es async-Bibliotheken im ganzen Stack.

multiprocessing vs ProcessPoolExecutor?

ProcessPoolExecutor ist die einfache Schnittstelle mit Futures. multiprocessing gibt mehr Kontrolle, zum Beispiel Queues, Pipes und Shared Memory.

GIL-Python vs Free-threaded Build?

Ohne GIL laufen Threads parallel. Dafür ist ein Thread etwas langsamer, und Erweiterungen müssen dafür markiert sein.

Produktion

Was tun, wenn die CPU-Auslastung eines Python-Dienstes bei 100 % eines Kerns hängt?

Das ist das typische GIL-Bild. Die Arbeit ist CPU-bound. Lösung: ProcessPoolExecutor, mehrere Worker-Prozesse oder ein C-Teil, der den GIL freigibt.

Was passiert, wenn man blockierenden Code in einer Coroutine aufruft?

Der ganze Event Loop steht. Alle anderen Tasks warten. Lösung: asyncio.to_thread oder eine async-Bibliothek.

Szenario: Eine async-API wird bei einem PDF-Export für alle Nutzer langsam. Warum?

Der Export rechnet CPU-bound im Event Loop. Der Loop kann keine anderen Tasks bedienen. Lösung: Export in einen Prozess-Pool auslagern und mit run_in_executor awaiten.

Szenario: Ein Prozess-Pool macht kleine Aufgaben langsamer als eine Schleife. Was tun Sie?

Pickle und Start kosten mehr als die Arbeit. Lösung: Aufgaben in grosse Blöcke bündeln (chunksize) oder bei Threads bleiben.

Design

Wie schützen Sie einen geteilten Zähler zwischen Threads?

Mit einem threading.Lock um die Änderung. Oder besser: keinen geteilten Zustand, sondern eine Queue.

Wie vermeiden Sie verlorene Tasks in asyncio?

Mit TaskGroup (seit 3.11). Sie hält starke Referenzen, wartet auf alle Tasks und gibt Fehler weiter.

Wie begrenzen Sie die Parallelität in asyncio?

Mit einer asyncio.Semaphore um die Aufrufe. So schickt man nicht tausend Anfragen gleichzeitig.

Wann nutzen Sie den Free-threaded Build?

Wenn Threads CPU-Arbeit parallel machen sollen und alle Erweiterungen dafür markiert sind. Ich prüfe vorher mit sys._is_gil_enabled(), dass der GIL wirklich aus ist.

Mehr

Gerüst

  • Warum? Der GIL macht den Interpreter einfach und sicher. Der Preis ist fehlende Parallelität.
  • Wie innen? Ein Lock mit Timeout. Wechsel nach 5 ms an Prüfpunkten, bei I/O sofort.
  • Zahlen Switch Interval 0.005 s. ThreadPool min(32, cpu + 4). Free-threaded Overhead 1 bis 8 %.
  • Vergleich CPU: Prozesse. I/O: Threads oder asyncio. Ohne GIL: Free-threaded Build.
  • Produktion Ein Kern bei 100 %: CPU-bound. Blockierender Aufruf im Event Loop: alles steht.
  • Design Keinen geteilten Zustand. Queue statt Lock. TaskGroup statt lose Tasks.

Beispiel: CPU gegen I/O, mit Threads, Prozessen und asyncio

def count(n):                      # reine CPU-Arbeit
    while n: n -= 1

serial:     count(N); count(N)                         # N = 20_000_000
threads:    ThreadPoolExecutor(2).map(count, [N, N])
processes:  ProcessPoolExecutor(2).map(count, [N, N])

time.sleep(0.5) x 10: seriell, 10 Threads, asyncio.gather(10 x asyncio.sleep(0.5))
4 Threads: je 1_000_000 mal box[0] += 1, ohne Lock
switchinterval 0.005
CPU serial (2 x count)       0.98 s
CPU 2 threads                0.95 s
CPU 2 processes              0.81 s
10 x sleep(0.5) serial       5.00 s
10 x sleep(0.5) 10 threads   0.50 s
10 x sleep(0.5) asyncio      0.56 s
counter 4 x 1_000_000 without lock: 4000000

Echte Ausgabe, Python 3.12.10 auf Windows (Start Method spawn). Zeiten sind Einzelmessungen.

  1. Zwei Threads brauchen 0.95 s, seriell 0.98 s. Der GIL verhindert den Gewinn bei CPU-Arbeit.
  2. Zwei Prozesse brauchen 0.81 s. Der Gewinn ist klein, weil der Start der Prozesse auf Windows (spawn) Zeit kostet. Bei längerer Arbeit wird er grösser.
  3. Bei sleep geben Threads den GIL frei. Zehn Threads brauchen 0.50 s statt 5.00 s.
  4. asyncio schafft dasselbe in einem Thread mit 0.56 s.
  5. Der Zähler ergab hier 4000000, also keine verlorenen Updates. Das ist Glück bei diesem Lauf und dieser Version. Die Sprache garantiert es nicht. Ein Lock bleibt Pflicht.

Vergleich

  • threading: billig, geteilter Speicher, gut bei blockierendem I/O. Bei CPU-Arbeit begrenzt der GIL.
  • multiprocessing: echte Parallelität mit eigenem GIL je Prozess. Kosten für Start und Pickle.
  • concurrent.futures: gleiche Schnittstelle für Threads und Prozesse. Gut zum Wechseln.
  • asyncio: ein Thread, kooperativ, sehr viele Tasks. Braucht async-Bibliotheken.
  • Free-threaded Build: Threads laufen parallel. Mehr Aufwand pro Thread und nicht jede Erweiterung ist bereit.
  • C-Erweiterungen mit GIL-Freigabe: zum Beispiel Kompression oder Hashing. Dort helfen auch Threads.

Produktion

  1. Ein Kern bei 100 %, die anderen leer: Das ist CPU-Arbeit unter dem GIL. Lösung: Prozess-Pool oder mehrere Worker-Prozesse hinter dem Server.
  2. Event Loop blockiert: Ein blockierender Aufruf in einer Coroutine stoppt alle Tasks. Lösung: asyncio.to_thread oder async-Bibliothek.
  3. Verschwundene Tasks: Ein create_task ohne Referenz kann vom Garbage Collector entfernt werden. Lösung: TaskGroup oder eine Menge mit Referenzen.
  4. Pickle-Fehler: Lambdas und lokale Funktionen gehen nicht in einen Prozess-Pool. Lösung: Funktion auf Modulebene.
  5. Windows-Start hängt oder startet endlos: Der Guard if __name__ == "__main__" fehlt. Das Hauptmodul wird in jedem Kind neu importiert.
  6. Zu viele gleichzeitige Anfragen: gather über tausende Aufrufe überlastet den Server. Lösung: Semaphore.

Diagnose: Werkzeuge und Befehle

  • sys.getswitchinterval(): zeigt das Switch Interval.
  • sys._is_gil_enabled() (ab 3.13): zeigt, ob der GIL läuft. python -VV zeigt, ob es ein Free-threaded Build ist.
  • PYTHON_GIL oder -X gil: steuert den GIL in einem Free-threaded Build.
  • asyncio.run(main(), debug=True): meldet langsame Callbacks im Event Loop.
  • py-spy (py-spy dump --pid): zeigt, wo jeder Thread steht.
  • top oder Task Manager: ein Kern bei 100 % deutet auf den GIL.

Senior-Punkte

  1. Erst messen, ob CPU oder I/O. Die Antwort bestimmt Threads, Prozesse oder asyncio.
  2. Der GIL schützt nicht Ihre Logik. Geteilter veränderbarer Zustand braucht Locks oder besser Queues.
  3. asyncio gilt für den ganzen Stack. Ein blockierender Aufruf macht den Vorteil zunichte.
  4. Prozesse haben Kosten: Start, Pickle, Speicher. Aufgaben bündeln.
  5. Free Threading ist eine Option, kein Standard. Erweiterungen und Bibliotheken müssen bereit sein. Vor dem Einsatz testen.
  6. Für Web-Dienste skaliert man oft mit mehreren Worker-Prozessen. Das umgeht den GIL ohne Code-Änderung.
