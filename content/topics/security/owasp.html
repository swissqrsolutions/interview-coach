OWASP Top 10

Security · Tier 1 · Quellen: OWASP Top 10:2025 (top10.owasp.org/2025, aktuelle Ausgabe), OWASP Cheat Sheet Series, Spring Security 7.2 Reference (Headers, CSRF)

Kern: Die OWASP Top 10 ist eine Liste der zehn wichtigsten Risiko-Kategorien für Web-Anwendungen. Die aktuelle Ausgabe ist 2025. Sie ist eine Awareness-Liste, kein vollständiger Standard. Für Prüfungen nutzt man OWASP ASVS.

1. Wo sitzen die Risiken?

Die Liste 2025 (Quelle: top10.owasp.org/2025):

  1. A01:2025 Broken Access Control: Benutzer handeln ausserhalb ihrer Rechte. Seit 2025 gehört auch SSRF hierher. Beispiel: IDOR.
  2. A02:2025 Security Misconfiguration: unsichere Standards und offene Endpunkte. Von Platz 5 auf 2 gestiegen. Beispiel: offener Actuator.
  3. A03:2025 Software Supply Chain Failures: neu, erweitert „Vulnerable and Outdated Components“ auf Build, Abhängigkeiten und Verteilung. Beispiel: Log4Shell.
  4. A04:2025 Cryptographic Failures: fehlende oder schwache Kryptografie. Beispiel: MD5 für Passwörter.
  5. A05:2025 Injection: Daten werden als Code ausgeführt. XSS gehört dazu. Beispiel: SQL per String-Verkettung.
  6. A06:2025 Insecure Design: Fehler im Entwurf, nicht im Code. Beispiel: kein Rate Limit bei Passwort-Reset.
  7. A07:2025 Authentication Failures: umbenannt von „Identification and Authentication Failures“. Beispiel: keine Sperre bei Credential Stuffing.
  8. A08:2025 Software or Data Integrity Failures: Code oder Daten ohne Integritätsprüfung. Beispiel: unsichere Deserialisierung.
  9. A09:2025 Security Logging and Alerting Failures: neuer Name betont Alerting. Beispiel: Angriffe stehen im Log, aber niemand wird alarmiert.
  10. A10:2025 Mishandling of Exceptional Conditions: neu. Fehler werden falsch behandelt: fail open, Stack Traces an den Client, halbe Transaktionen.

2. Die Reise eines Angriffs (die Geschichte zum Merken)

  1. Aufklärung. Der Angreifer schickt kaputte Eingaben. Die API antwortet mit Stack Trace und Versionen (A10). /actuator/env ist offen (A02).
  2. Einstieg. Er probiert geleakte Passwort-Listen (Credential Stuffing). Ohne Rate Limit und MFA klappt ein Login (A07).
  3. Ausweiten. Er ändert IDs in URLs (IDOR) oder lässt den Server interne URLs abrufen (SSRF). Beides ist A01. Ein Suchfeld ist per SQL injizierbar (A05).
  4. Daten abziehen. Die Daten liegen unverschlüsselt, die App nutzt einen DB-Admin-User (A04, Least Privilege fehlt).
  5. Unbemerkt. Tausende fehlgeschlagene Logins stehen im Log, aber kein Alert geht raus (A09).

3. Beispiel: Path Traversal (A01) in Java

static final Path BASE = Path.of("/data/uploads/tenant-a").toAbsolutePath().normalize();

static String naive(String name) { return BASE.resolve(name).toString(); }   // FALSCH

static String safe(String name) {                                            // RICHTIG
    Path p = BASE.resolve(name).normalize();
    if (!p.startsWith(BASE)) return "403 Forbidden (" + p + ")";
    return p.toString();
}
$ java Traversal.java
report.pdf                   naive=C:\data\uploads\tenant-a\report.pdf
                             safe =C:\data\uploads\tenant-a\report.pdf
../tenant-b/salaries.xlsx    naive=C:\data\uploads\tenant-a\..\tenant-b\salaries.xlsx
                             safe =403 Forbidden (C:\data\uploads\tenant-b\salaries.xlsx)
../../../etc/passwd          naive=C:\data\uploads\tenant-a\..\..\..\etc\passwd
                             safe =403 Forbidden (C:\etc\passwd)

Echte Ausgabe, OpenJDK 17.0.3 unter Windows (darum C:\-Pfade).

  1. resolve hängt den Namen nur an. .. bleibt drin. Das Dateisystem löst es später auf: Die Datei von Mandant B wird gelesen.
  2. normalize() löst .. auf. Danach prüft startsWith(BASE), ob der Pfad noch im erlaubten Ordner liegt.
  3. Besser noch: keine Dateinamen vom Benutzer. Die App speichert unter einer zufälligen ID und hält den Originalnamen in der DB.

4. Details, die Interviewer fragen: jede Kategorie mit Spring-Beispiel und Fix

  1. A01 Broken Access Control. Fehler: repo.findById(id) ohne Besitzer-Check. Fix: repo.findByIdAndTenantId(id, currentTenant()) oder @PreAuthorize mit Objekt-Check. SSRF: restClient.get().uri(userUrl) holt http://169.254.169.254/ (Cloud-Metadaten). Fix: Allowlist von Hosts, kein Redirect folgen, Egress-NetworkPolicy.
  2. A02 Security Misconfiguration. Fehler: management.endpoints.web.exposure.include=* öffentlich, /actuator/heapdump enthält Secrets. Fix: nur health,info exponieren, Actuator auf eigenem Port, mit Auth. Auch: allowedOrigins("*") mit Credentials, Default-Passwörter, Debug-Modus.
  3. A03 Software Supply Chain Failures. Fehler: alte Log4j-Version (Log4Shell, CVE-2021-44228) transitiv im Build. Fix: SBOM (CycloneDX-Plugin), Dependency-Scan in CI (OWASP Dependency-Check, Trivy, Dependabot), Images nur aus eigener Registry, signierte Artefakte.
  4. A04 Cryptographic Failures. Fehler: MessageDigest.getInstance("MD5") für Passwörter, Cipher.getInstance("AES") (Standard ist oft ECB). Fix: Argon2PasswordEncoder oder BCryptPasswordEncoder, AES/GCM/NoPadding mit zufälligem IV, Schlüssel im Key Vault, TLS überall.
  5. A05 Injection. Fehler: "SELECT … WHERE name = '" + name + "'" oder JPQL per Verkettung. Fix: PreparedStatement, Named Parameters (:name), Spring Data. XSS: th:utext mit Benutzer-Input. Fix: th:text (escaped) und CSP. Command Injection: Runtime.exec("sh -c convert " + file). Fix: ProcessBuilder mit Argument-Liste.
  6. A06 Insecure Design. Fehler: Passwort-Reset-Code mit 4 Ziffern und ohne Limit. Fix: Threat Modeling früh, lange zufällige Tokens, Rate Limit (z. B. Bucket4j), Business-Limits („max. 3 Gutscheine pro Konto“).
  7. A07 Authentication Failures. Fehler: eigenes Login-Formular ohne Sperre, Session-ID bleibt nach Login gleich. Fix: IdP (Keycloak, Entra ID) mit MFA, Rate Limit, Prüfung gegen geleakte Passwörter, Spring-Standard für Session Fixation nicht abschalten.
  8. A08 Software or Data Integrity Failures. Fehler: ObjectInputStream.readObject() auf Request-Daten (Gadget-Chains), Jackson mit Default Typing. Fix: keine Java-Deserialisierung von fremden Daten, JSON auf feste DTOs, ObjectInputFilter als Notbremse. Auch: CI-Pipeline darf nur signierte Artefakte deployen.
  9. A09 Security Logging and Alerting Failures. Fehler: fehlgeschlagene Logins nicht geloggt, oder Passwörter im Log. Fix: Spring AuthenticationFailureBadCredentialsEvent und AuthorizationDeniedEvent loggen, zentral sammeln, Alert bei Häufung. Keine Tokens, Passwörter oder Personendaten loggen.
  10. A10 Mishandling of Exceptional Conditions. Fehler: catch (Exception e) { return true; } im Berechtigungs-Check (fail open), server.error.include-stacktrace=always. Fix: im Fehlerfall verweigern (fail closed), @RestControllerAdvice mit ProblemDetail ohne Interna, @Transactional rollt ganz zurück.
// A10: fail open (FALSCH) vs fail closed (RICHTIG)
boolean canRead(User u, Doc d) {
  try { return policyClient.allowed(u, d); }
  catch (Exception e) { log.warn("policy down", e); return true; }   // jeder darf alles
}
boolean canReadSafe(User u, Doc d) {
  try { return policyClient.allowed(u, d); }
  catch (Exception e) { log.error("policy down, deny", e); return false; }
}

5. Vergleich

  • 2025 vs 2021: A01 bleibt Platz 1 und schluckt SSRF. Misconfiguration steigt von 5 auf 2. Crypto (2→4), Injection (3→5) und Insecure Design (4→6) fallen. Neu: A03 Supply Chain und A10 Exceptional Conditions.
  • Top 10 vs ASVS: Top 10 ist Awareness. ASVS (Application Security Verification Standard) ist eine prüfbare Anforderungsliste mit Stufen.
  • Top 10 vs API Security Top 10: Die API-Liste ist eigenständig und fokussiert z. B. BOLA (Object Level Authorization) und Ressourcen-Verbrauch.
  • SAST: prüft Quellcode (SonarQube, Semgrep). Findet Injection-Muster und hartkodierte Secrets.
  • DAST: greift die laufende App an (OWASP ZAP). Findet fehlende Header und offene Endpoints.
  • SCA: prüft Abhängigkeiten (Dependency-Check, Trivy, Dependabot). Deckt A03 ab.

6. In der Produktion

  1. Actuator offen im Internet: /actuator/env oder /heapdump zeigen Passwörter. Lösung: Management-Port intern, nur health öffentlich.
  2. Kritische CVE in transitiver Abhängigkeit: Niemand weiss, welche Services betroffen sind. Lösung: SBOM pro Image, zentral durchsuchbar.
  3. Stack Traces im JSON: Fehlerantworten zeigen Klassen, SQL und Versionen. Lösung: ProblemDetail mit Korrelations-ID, Details nur im Log.
  4. Policy-Service down = alles offen: Ein Catch-Block gibt true zurück. Lösung: fail closed, Circuit Breaker mit Ablehnung als Fallback.
  5. Hartkodierte Passwörter: SonarQube meldet Secrets in Tests und Compose-Dateien. Lösung: Secrets aus Vault, Test-Werte klar als Fake, Unterdrückungen begründet.
  6. Logs ohne Alarm: Ein Angriff läuft wochenlang. Lösung: Alerts auf Login-Fehler, 403-Häufung, ungewöhnliche Datenmengen.

7. Diagnose: Werkzeuge und Befehle

  • SAST: SonarQube Quality Gate in der Pipeline (Security Hotspots, „Hard-coded credentials“).
  • SCA: mvn org.owasp:dependency-check-maven:check, trivy image registry/app:tag, mvn dependency:tree -Dincludes=org.apache.logging.log4j.
  • SBOM: mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom.
  • DAST: OWASP ZAP Baseline-Scan gegen die Staging-Umgebung.
  • Header prüfen: curl -sI https://app | grep -iE 'content-security|strict-transport|x-frame|x-content-type'.
  • Actuator prüfen: curl -s https://app/actuator von aussen muss 401/404 geben.

8. Senior-Punkte

  1. Die Top 10 ist eine Checkliste für Gespräche, kein Sicherheitskonzept. Für Anforderungen und Abnahme: ASVS und Threat Modeling.
  2. Access Control ist Platz 1, weil Tools sie kaum finden. Sie braucht Tests pro Endpoint und Objekt, keine Scanner.
  3. Supply Chain ist Plattform-Arbeit: SBOM, eigene Registry, Policy (z. B. Kyverno „nur ACR-Images“), Signaturen. Ein Team allein schafft das nicht.
  4. Fail closed als Prinzip. Wenn etwas unklar ist, wird verweigert. Verfügbarkeit gegen Sicherheit bewusst abwägen und dokumentieren.
  5. Sichere Standards nicht abschalten. Spring hat CSRF, Header und Session Fixation an. Jede Ausnahme braucht eine Begründung.
  6. Findings nicht pauschal unterdrücken. Jede Unterdrückung einzeln begründen, sonst verliert das Tool sein Vertrauen.

10. Fallen

  • „Die aktuelle Liste ist von 2021.“ → Falsch. Die aktuelle Ausgabe ist 2025.
  • „SSRF ist eine eigene Kategorie.“ → Nicht mehr. 2021 war es A10. 2025 gehört es zu A01 Broken Access Control.
  • „XSS ist eine eigene Kategorie.“ → Falsch. XSS gehört zu Injection (A05).
  • „Wir erfüllen die OWASP Top 10, also sind wir sicher.“ → Falsch. Die Liste ist nur Awareness. Prüfbar ist ASVS.
  • „Ein Scanner findet Broken Access Control.“ → Kaum. Er kennt die Geschäftsregeln nicht. Dafür braucht es Tests und Reviews.
  • „Fehler fangen und weitermachen ist robust.“ → Gefährlich. Im Sicherheits-Check heisst das fail open (A10).

11. Fragen

Was ist die OWASP Top 10?

Eine Awareness-Liste der zehn wichtigsten Risiko-Kategorien für Web-Anwendungen. Die aktuelle Ausgabe ist 2025.

Nennen Sie die Top 10 von 2025.

Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures, Injection, Insecure Design, Authentication Failures, Software or Data Integrity Failures, Security Logging and Alerting Failures, Mishandling of Exceptional Conditions.

Was ist neu in 2025?

A03 Software Supply Chain Failures und A10 Mishandling of Exceptional Conditions. SSRF ging in A01 auf, Misconfiguration stieg auf Platz 2.

Was ist Broken Access Control? Beispiel in Spring?

Benutzer handeln ausserhalb ihrer Rechte. Beispiel: findById ohne Mandanten-Check. Fix: findByIdAndTenantId oder @PreAuthorize mit Objekt-Check.

Was ist SSRF und wie verhindern Sie es?

Der Server ruft eine vom Angreifer gewählte URL auf, z. B. interne Dienste oder Cloud-Metadaten. Fix: Host-Allowlist, keine Redirects folgen, Egress-Regeln im Netzwerk.

Was ist ein typisches Misconfiguration-Problem bei Spring Boot?

Alle Actuator-Endpunkte öffentlich, z. B. heapdump oder env. Fix: nur health und info, eigener Management-Port, Authentifizierung.

Was gehört zu Software Supply Chain Failures?

Verwundbare oder bösartige Abhängigkeiten, unsichere Build-Pipelines und Verteilung. Beispiele: Log4Shell, SolarWinds. Fix: SBOM, SCA in CI, signierte Artefakte, eigene Registry.

Welche Kryptografie-Fehler sehen Sie oft in Java?

MD5 oder SHA-1 für Passwörter, AES ohne Modusangabe (ECB), fester IV, Schlüssel im Code. Fix: Argon2/bcrypt, AES-GCM mit zufälligem IV, Key Vault.

Wie verhindern Sie SQL Injection in Spring?

PreparedStatement oder Named Parameters, Spring Data Methoden, nie String-Verkettung. Dazu ein DB-User mit minimalen Rechten.

Was ist Insecure Design?

Ein Fehler im Entwurf, den sauberer Code nicht behebt. Beispiel: Reset-Code ohne Rate Limit. Fix: Threat Modeling und Missbrauchsfälle früh einplanen.

Was ist Credential Stuffing?

Automatisierte Logins mit geleakten Benutzer-Passwort-Paaren aus anderen Diensten. Fix: MFA, Rate Limit, Prüfung gegen geleakte Passwörter.

Warum ist Java-Deserialisierung gefährlich?

readObject auf fremden Daten kann über Gadget-Chains Code ausführen. Fix: keine Java-Serialisierung für fremde Daten, JSON auf feste DTOs, ObjectInputFilter.

Was sollte man sicherheitsrelevant loggen, was nicht?

Loggen: Login-Erfolg und -Fehler, 403, Rechte-Änderungen, Admin-Aktionen. Nicht loggen: Passwörter, Tokens, sensible Personendaten.

Was bedeutet fail open vs fail closed?

Fail open erlaubt im Fehlerfall den Zugriff, fail closed verweigert ihn. Sicherheitsprüfungen müssen fail closed sein.

Wie behandeln Sie Fehler in einer Spring-API sicher?

Zentral mit @RestControllerAdvice und ProblemDetail, ohne Stack Trace und SQL. Eine Korrelations-ID verbindet die Antwort mit dem Log.

Was ist der Unterschied zwischen SAST, DAST und SCA?

SAST prüft Quellcode, DAST greift die laufende App an, SCA prüft Abhängigkeiten auf bekannte Schwachstellen.

Was ist OWASP ASVS?

Der Application Security Verification Standard: eine prüfbare Liste von Sicherheitsanforderungen in Stufen. Gut für Abnahme und Ausschreibungen.

Was ist eine SBOM?

Eine Software Bill of Materials: die Liste aller Komponenten inklusive transitiver Abhängigkeiten. Damit findet man bei einer neuen CVE schnell betroffene Services.

Szenario: Eine neue kritische CVE in einer Java-Bibliothek wird veröffentlicht. Was tun Sie?

Über SBOMs alle betroffenen Services finden, Ausnutzbarkeit bewerten, patchen oder per Konfiguration oder WAF entschärfen. Danach Scan in CI, damit die Version nicht zurückkommt.

Szenario: SonarQube meldet hartkodierte Passwörter in Tests und docker-compose. Wie gehen Sie vor?

Jeden Fund einzeln bewerten. Echte Secrets sofort rotieren und in den Vault. Fake-Werte klar kennzeichnen oder entfernen, lokale Dateien begründet ausschliessen, keine Regel pauschal abschalten.

Szenario: Ein Pentest findet, dass /actuator/heapdump öffentlich ist. Was ist der Schaden, und was tun Sie?

Ein Heap Dump enthält Secrets, Tokens und Personendaten. Sofort Endpunkt schliessen, alle Secrets der App rotieren, Zugriffslogs prüfen. Danach Management-Port intern und nur health öffentlich.
