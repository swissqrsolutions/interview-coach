Authentifizierung vs Autorisierung

Kern: Authentifizierung (AuthN) beantwortet „Wer bist du?“. Autorisierung (AuthZ) beantwortet „Was darfst du hier tun?“. AuthN kommt immer zuerst, AuthZ läuft bei jedem Request und für jedes Objekt neu.

1. Wo sitzen AuthN und AuthZ?

  1. Identity Provider (IdP): Der IdP prüft Passwort, MFA oder Zertifikat. Beispiel: Keycloak meldet einen LDAP-Benutzer an.
  2. AuthN in der Anwendung: Ein Filter liest Session-Cookie oder Bearer Token und baut einen Principal, also den angemeldeten Benutzer. Beispiel: BearerTokenAuthenticationFilter in Spring.
  3. AuthZ grob: Die Regel prüft URL und Rolle. Beispiel: /admin/** nur für ROLE_ADMIN.
  4. AuthZ fein: Die Regel prüft das konkrete Objekt. Beispiel: Rechnung 42 gehört dem Mandanten des Benutzers.
  5. Daten: Die Abfrage filtert zusätzlich nach Mandant. So schützt auch ein vergessener Check nicht alle Daten.

2. Die Reise eines Requests (die Geschichte zum Merken)

  1. Request kommt an. Anna ruft GET /invoices/42 auf. Sie schickt ein Session-Cookie oder einen Bearer Token mit.
  2. Identität prüfen. Der Filter prüft Signatur, Ablauf und Aussteller des Tokens. Fehlt der Token oder ist er ungültig, endet die Reise mit 401 Unauthorized.
  3. Principal bauen. Aus dem Token entstehen Benutzer-ID (sub) und Rechte (Authorities). Spring legt sie in den SecurityContext.
  4. URL-Regel. /invoices/** braucht die Rolle ACCOUNTANT. Fehlt sie: 403 Forbidden.
  5. Objekt-Regel. Die Rolle reicht nicht. Rechnung 42 muss zu Annas Mandant gehören. Fehlt diese Prüfung, liest Anna fremde Rechnungen: IDOR (Insecure Direct Object Reference).
  6. Antwort und Audit. Erst jetzt kommt 200 OK. Ein Audit-Log speichert wer, was, wann.

3. Beispiel: RBAC und ABAC im Vergleich

ROLE_PERMS = {"viewer": {"doc:read"}, "editor": {"doc:read", "doc:write"}}

def rbac(user, action, doc):          # nur Rolle -> Recht
    return any(action in ROLE_PERMS.get(r, set()) for r in user.roles)

def abac(user, action, doc):          # Rolle + Attribute
    if not rbac(user, action, doc): return False
    if user.tenant != doc.tenant: return False                       # Mandant
    if doc.classification == "secret" and user.dept != doc.dept: return False
    if action == "doc:write" and doc.owner != user.name: return False # Besitzer
    return True

anna = User("anna", {"editor"}, tenant="bern",    dept="finance")
mia  = User("mia",  {"editor"}, tenant="zuerich", dept="finance")
d1 = Doc(1, "bern", "finance", owner="anna", classification="internal")
d2 = Doc(2, "bern", "hr",      owner="tom",  classification="secret")
$ python -I authz_demo.py
anna doc:write doc1  RBAC=erlaubt    ABAC=erlaubt
mia  doc:read  doc1  RBAC=erlaubt    ABAC=verweigert
anna doc:read  doc2  RBAC=erlaubt    ABAC=verweigert
anna doc:write doc2  RBAC=erlaubt    ABAC=verweigert

Echte Ausgabe, Python 3.12.

  1. Anna ist editor und Besitzerin von doc1. Beide Modelle erlauben.
  2. Mia ist auch editor, aber im Mandanten Zürich. RBAC erlaubt trotzdem. Das ist ein Datenleck zwischen Mandanten.
  3. doc2 ist secret und gehört zu HR. Nur ABAC sieht die Abteilung.
  4. Fazit: RBAC regelt „welche Funktion“. Die Frage „welches Objekt“ braucht Attribute, also ABAC oder Objekt-Checks im Code.

Dasselbe in Spring Security 7:

@Configuration @EnableMethodSecurity
class SecurityConfig {
  @Bean SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
          .requestMatchers("/admin/**").hasRole("ADMIN")      // RBAC grob
          .anyRequest().authenticated())                       // Default: anmelden
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
  }
}

@PreAuthorize("hasAuthority('SCOPE_invoices.read') and @invoiceGuard.sameTenant(#id, authentication)")

4. Details, die Interviewer fragen

  1. 401 vs 403: 401 heisst „nicht authentifiziert“, der Name ist historisch falsch. 403 heisst „authentifiziert, aber nicht erlaubt“. Bei fremden Objekten ist 404 oft besser, weil es die Existenz versteckt.
  2. Faktoren: Ein Faktor ist Wissen (Passwort), Besitz (Handy, FIDO2-Key) oder Eigenschaft (Fingerabdruck). MFA kombiniert zwei verschiedene Arten. Passkeys (WebAuthn) sind phishing-resistent, weil sie an die Domain gebunden sind.
  3. Passwörter speichern: Passwörter speichert man als langsamen, gesalzenen Hash: Argon2id, scrypt oder bcrypt. Nie verschlüsselt, nie SHA-256 pur. In Spring: PasswordEncoderFactories.createDelegatingPasswordEncoder().
  4. Session (stateful): Der Server speichert den Zustand. Der Browser hält nur eine zufällige Session-ID im Cookie. Logout und Sperren wirken sofort.
  5. Token (stateless): Ein selbsttragender Token (meist JWT) enthält die Claims und eine Signatur. Jeder Service prüft ihn ohne DB-Zugriff. Dafür ist Widerruf schwer: Der Token gilt bis exp.
  6. Cookie-Flags: HttpOnly verbietet JavaScript-Zugriff (gegen XSS-Diebstahl). Secure erlaubt nur HTTPS. SameSite=Lax oder Strict bremst CSRF.
  7. Session Fixation: Der Angreifer schiebt dem Opfer eine bekannte Session-ID unter. Schutz: neue Session-ID nach Login. Spring Security macht das standardmässig.
  8. RBAC: Role-Based Access Control gibt Rechte an Rollen, Rollen an Benutzer. Einfach zu prüfen und zu auditieren. Problem: Rollen-Explosion (EDITOR_BERN_FINANCE).
  9. ABAC: Attribute-Based Access Control entscheidet über Attribute von Benutzer, Objekt, Aktion und Umgebung (z. B. Uhrzeit). Sehr flexibel, aber schwerer zu testen und zu erklären.
  10. ReBAC: Relationship-Based Access Control entscheidet über Beziehungen („Anna ist Mitglied von Team X, Team X besitzt Ordner Y“). Beispiel: Google Zanzibar, OpenFGA.
  11. Policy-Architektur: PEP (Policy Enforcement Point) erzwingt, PDP (Policy Decision Point) entscheidet. Beispiel: Spring-Filter als PEP, OPA (Open Policy Agent) als PDP.
  12. Least Privilege: Least Privilege heisst: jedes Konto bekommt nur die Rechte, die es für seine Aufgabe braucht, und nur so lange wie nötig. Das gilt für Menschen, Services, DB-User und Pods.
  13. Deny by default: Was keine Regel erlaubt, ist verboten. In Spring: anyRequest().authenticated() oder denyAll() am Ende.
  14. Scopes vs Rollen: Ein OAuth-Scope begrenzt, was ein Client im Namen des Benutzers darf. Eine Rolle beschreibt, was der Benutzer darf. Die echte Berechtigung ist die Schnittmenge.

5. Vergleich

  • Session-Cookie: sofortiger Logout, kleine Cookies, CSRF-Schutz nötig. Skaliert mit Sticky Sessions oder einem zentralen Store (Redis, Spring Session).
  • JWT Bearer Token: kein Server-Zustand, gut zwischen Microservices. Widerruf schwer, Token gross, Diebstahl gefährlich bis exp.
  • Opaque Token + Introspection: zufälliger String, der Resource Server fragt den IdP (RFC 7662). Widerruf sofort, aber ein Netzwerk-Call pro Request (Cache hilft).
  • RBAC: grob, einfach, gut für Funktionen („darf Rechnungen sehen“).
  • ABAC: fein, dynamisch, gut für Daten („nur eigener Mandant, nur Bürozeit“).
  • ReBAC: gut für Teilen und Hierarchien (Dokumente, Ordner, Teams).
  • ACL: Liste pro Objekt, wer was darf. Präzise, aber viel Pflege.

6. In der Produktion

  1. IDOR: Die API prüft nur die Rolle, nicht den Besitzer. Ein Benutzer ändert die ID in der URL und sieht fremde Daten. Lösung: Objekt-Check in jedem Use Case plus Mandanten-Filter in der Query. Broken Access Control ist A01:2025 der OWASP Top 10.
  2. Fehlende Regel = offen: Ein neuer Endpoint ist ohne Regel öffentlich. Lösung: deny by default und ein Test, der alle Endpoints ohne Token aufruft.
  3. Rollen aus Keycloak fehlen: Keycloak legt Rollen in realm_access.roles. Spring mappt standardmässig nur scope/scp zu SCOPE_*. Lösung: eigener JwtAuthenticationConverter.
  4. Rechte ändern sich, Token nicht: Ein entzogener Admin hat noch 30 Minuten einen gültigen Token. Lösung: kurze Access-Token-Laufzeit (5–15 Minuten), kritische Aktionen online prüfen.
  5. Admin-Konten für alles: Service-Accounts mit Owner-Rechten. Ein Leck wird zum Totalschaden. Lösung: Least Privilege, getrennte Identitäten pro Service, Managed Identity.
  6. Clientseitige Prüfung: Angular versteckt nur den Button. Die API erlaubt den Call trotzdem. Lösung: Autorisierung immer im Backend.

7. Diagnose: Werkzeuge und Befehle

  • logging.level.org.springframework.security=TRACE: zeigt Filter-Kette und welche Regel abgelehnt hat.
  • Token ansehen: Payload base64url-dekodieren (lokal, nie in fremde Webseiten kopieren). Prüfen: sub, aud, Rollen, exp.
  • curl -i -H "Authorization: Bearer $T" https://api/invoices/42: 401 oder 403? Header WWW-Authenticate nennt den Grund (z. B. invalid_token).
  • Tests: @WithMockUser(roles="USER") und jwt().authorities(...) aus spring-security-test. Für jeden Endpoint: ohne Token, falsche Rolle, fremder Mandant.
  • Keycloak Admin Console: „Evaluate“ im Client-Scope zeigt, welche Claims ein Token bekommt.
  • Audit-Log: Wer hat wann worauf zugegriffen? Viele 403 von einer Identität deuten auf Ausprobieren von IDs hin.

8. Senior-Punkte

  1. AuthN zentralisieren, AuthZ nahe an den Daten. Login gehört in den IdP. Die Objekt-Entscheidung gehört in den Service, der die Daten kennt.
  2. RBAC für Funktionen, Attribute für Daten. Reines ABAC überall ist schwer zu prüfen. Reines RBAC endet in Rollen-Explosion.
  3. Defense in Depth: Gateway prüft Token, Service prüft Objekt, DB filtert nach Mandant (z. B. eigene DB oder Row-Level Security).
  4. Session oder Token ist eine Abwägung: Browser-App mit eigenem Backend → Session-Cookie (BFF). Service-zu-Service → kurzlebiger Token.
  5. Least Privilege ist ein Prozess: Rechte regelmässig prüfen (Access Review), Just-in-Time-Admin statt Dauer-Admin.
  6. Autorisierung testbar machen: eine Matrix Rolle × Endpoint × Mandant als automatisierter Test.

10. Fallen

  • „401 heisst keine Berechtigung.“ → Falsch. 401 heisst nicht authentifiziert. Keine Berechtigung ist 403.
  • „Der Benutzer hat die Rolle, also darf er das Objekt sehen.“ → Falsch. Rolle ≠ Objekt. Ohne Besitzer- oder Mandanten-Check entsteht IDOR.
  • „JWT ist sicherer als Sessions.“ → Falsch. Anders, nicht sicherer. JWT tauscht sofortigen Widerruf gegen Skalierung.
  • „OAuth ist ein Login-Protokoll.“ → Falsch. OAuth 2 ist Autorisierung (delegierter Zugriff). Login macht OpenID Connect.
  • „Passwörter verschlüsseln wir mit AES.“ → Falsch. Passwörter werden gehasht (Argon2id, bcrypt), nicht verschlüsselt.
  • „Im Frontend ist der Button versteckt, also sicher.“ → Falsch. Jede Prüfung muss im Backend passieren.

11. Fragen

Was ist der Unterschied zwischen Authentifizierung und Autorisierung?

Authentifizierung prüft, wer jemand ist. Autorisierung prüft, was diese Identität mit einem bestimmten Objekt tun darf. AuthN kommt zuerst, AuthZ bei jedem Zugriff.

Wann antwortet eine API mit 401, wann mit 403?

401, wenn keine oder eine ungültige Identität vorliegt. 403, wenn die Identität bekannt ist, aber die Aktion nicht erlaubt ist.

Warum gibt man bei fremden Objekten manchmal 404 statt 403?

404 verrät nicht, dass das Objekt existiert. So kann ein Angreifer IDs nicht ausprobieren.

Was ist MFA, und warum sind Passkeys besser als SMS-Codes?

MFA kombiniert zwei verschiedene Faktor-Arten. Passkeys sind an die Domain gebunden und darum phishing-resistent. SMS-Codes kann man abfangen oder auf einer Fake-Seite abgreifen.

Wie speichert man Passwörter richtig?

Mit einem langsamen, gesalzenen Hash wie Argon2id, scrypt oder bcrypt. In Spring mit dem DelegatingPasswordEncoder, der das Verfahren im Hash-Präfix mitführt.

Session vs Token: Was ist der Kernunterschied?

Eine Session speichert den Zustand auf dem Server, der Browser hat nur eine ID. Ein Token trägt die Claims selbst und wird nur geprüft. Sessions kann man sofort beenden, Tokens gelten bis zum Ablauf.

Welche Cookie-Flags braucht ein Session-Cookie?

HttpOnly gegen Diebstahl per XSS, Secure für nur HTTPS, SameSite=Lax oder Strict gegen CSRF. Dazu ein enger Path und kein Domain-Attribut, wenn nicht nötig.

Was ist Session Fixation?

Der Angreifer setzt beim Opfer eine ihm bekannte Session-ID. Nach dem Login teilt er die Session. Schutz: nach Login eine neue Session-ID vergeben.

Was ist RBAC?

Rechte hängen an Rollen, Benutzer bekommen Rollen. Einfach und gut auditierbar. Nachteil: Feine Regeln führen zu sehr vielen Rollen.

Was ist ABAC?

Entscheidung über Attribute von Benutzer, Objekt, Aktion und Umgebung. Sehr flexibel, z. B. „nur eigener Mandant“. Nachteil: schwerer zu testen und zu erklären.

Wann wählen Sie RBAC, wann ABAC?

RBAC für Funktionen und Menüs. ABAC oder Objekt-Checks für Datenzugriff mit Mandanten, Besitzern oder Klassifizierung. In der Praxis meist beides kombiniert.

Was ist ReBAC?

Berechtigung über Beziehungen in einem Graphen, z. B. Mitglied, Besitzer, Ordner. Bekannt durch Google Zanzibar und OpenFGA. Gut für Teilen und Hierarchien.

Was ist Least Privilege?

Jede Identität bekommt nur die Rechte, die sie für ihre Aufgabe braucht, und nur so lange wie nötig. Das begrenzt den Schaden bei einem Leck.

Was ist IDOR?

Insecure Direct Object Reference: Die API nimmt eine ID aus dem Request und prüft nicht, ob sie dem Benutzer gehört. Lösung: Objekt-Check und Mandanten-Filter.

Was bedeutet deny by default?

Alles ist verboten, was keine Regel ausdrücklich erlaubt. So ist ein neuer Endpoint ohne Regel nicht automatisch offen.

Scope vs Rolle?

Ein Scope begrenzt, was ein Client im Namen des Benutzers darf. Eine Rolle beschreibt, was der Benutzer darf. Erlaubt ist nur die Schnittmenge.

Was sind PEP und PDP?

Der Policy Enforcement Point erzwingt die Entscheidung, z. B. ein Filter. Der Policy Decision Point trifft sie, z. B. OPA. So kann man Regeln zentral pflegen.

Wie funktioniert @PreAuthorize?

Mit @EnableMethodSecurity prüft Spring vor dem Methodenaufruf einen SpEL-Ausdruck. Er kann Authorities und eigene Beans für Objekt-Checks nutzen.

Was ist der Unterschied zwischen hasRole und hasAuthority in Spring?

hasRole("ADMIN") prüft die Authority ROLE_ADMIN, also mit Präfix. hasAuthority prüft den String exakt, z. B. SCOPE_read.

Warum fehlen Keycloak-Rollen in Spring oft?

Spring mappt standardmässig nur scope/scp zu SCOPE_*. Keycloak legt Rollen in realm_access.roles. Man braucht einen eigenen JwtAuthenticationConverter.

Wo sollte Autorisierung passieren?

Immer im Backend, nahe an den Daten. Das Frontend darf nur Anzeige steuern. Zusätzlich filtert die Datenbank nach Mandant.

Szenario: Ein Kunde sieht nach Ändern der URL-ID die Rechnungen eines anderen Kunden. Was tun Sie?

Sofort Objekt-Check einbauen und Query nach Mandant filtern. Audit-Logs auf weitere Zugriffe prüfen. Danach Tests für alle Endpoints mit fremden IDs ergänzen.

Szenario: Ein entlassener Admin hat nach Sperrung noch Zugriff auf die API. Warum?

Sein Access Token ist noch gültig, weil JWTs bis exp gelten. Lösung: kurze Laufzeit, Refresh Token widerrufen, kritische Aktionen online prüfen oder Introspection nutzen.

Szenario: Das Team will für jeden Kunden und jede Abteilung eine eigene Rolle anlegen. Was raten Sie?

Das führt zu Rollen-Explosion. Besser: wenige funktionale Rollen plus Attribute wie Mandant und Abteilung im Token und Objekt-Checks im Service.
