JWT

Kern: Ein JWT (JSON Web Token) ist ein kompaktes, signiertes Paket von Claims. Es besteht aus header.payload.signature, jeder Teil base64url-kodiert. Der Empfänger prüft es ohne Datenbank nur mit einem Schlüssel, und der Inhalt ist nicht verschlüsselt.

Antwort-Muster

Frage: Wie ist ein JWT aufgebaut und wie wird es geprüft?

  1. Mechanismus: Ein JWT hat drei base64url-Teile: Header, Payload, Signatur. Der Server prüft die Signatur mit einem Schlüssel, ohne Datenbank.
  2. Zahl: Zeit zählt. Die exp liegt in der Zukunft. Ein Access Token gilt nur 5–15 Minuten. Ein HS256-Schlüssel braucht mindestens 256 Bit.
  3. Trade-off: Lokal prüfbar heisst schwer widerrufbar. Signiert heisst nicht verschlüsselt, der Payload ist lesbar.
  4. Produktion: Algorithmus, iss und aud prüft man immer. Sonst gelten alg=none oder Tokens für andere APIs.

1. Die Reise einer Validierung

  1. Format prüfen. Genau drei Teile, gültiges base64url, gültiges JSON. Alles andere wird sofort abgelehnt.
  2. Algorithmus gegen eine Allowlist. Der Server erwartet z. B. nur RS256. Er übernimmt alg nie blind aus dem Header. So scheitern alg=none und Key Confusion.
  3. Schlüssel finden. Der kid zeigt auf einen Key im vertrauten JWKS des Issuers. Ein jku oder x5u aus dem Token wird ignoriert.
  4. Signatur prüfen. Mit dem Public Key über header.payload. Passt sie nicht, wurde etwas verändert.
  5. Aussteller und Empfänger. iss muss exakt dem erwarteten Issuer entsprechen. aud muss diese API enthalten.
  6. Zeit. exp muss in der Zukunft liegen, nbf in der Vergangenheit. Spring erlaubt standardmässig 60 Sekunden Clock Skew.
  7. Claims nutzen. Erst jetzt werden sub, scope und Rollen für die Autorisierung gelesen.

2. Aufbau

  1. Issuer: stellt das JWT aus und signiert es mit seinem Private Key. Beispiel: Keycloak oder Entra ID.
  2. JWKS (JSON Web Key Set, RFC 7517): eine JSON-Liste der Public Keys des Issuers. Jeder Key hat eine ID, den kid.
  3. Client: trägt das JWT im Header Authorization: Bearer. Er muss es nicht verstehen.
  4. Resource Server: holt den passenden Public Key über den kid, cacht ihn und prüft Signatur und Claims lokal.
  5. Aufbau: drei base64url-Teile mit Punkt getrennt. Die Signatur deckt header.payload ab.

3. Details, die Interviewer fragen

  1. Registrierte Claims (RFC 7519): Das sind iss (Aussteller), sub (Subjekt) und aud (Empfänger). Dazu kommen exp (Ablauf), nbf (nicht vor) und iat (ausgestellt um). Dazu kommt jti (eindeutige Token-ID). Zeiten sind Sekunden seit 1970 (NumericDate).
  2. JWS vs JWE: JWS (RFC 7515) signiert, der Inhalt bleibt lesbar. JWE verschlüsselt, der Inhalt ist geheim. „JWT“ meint fast immer JWS.
  3. HS256: Das ist HMAC mit SHA-256 und einem geteilten Geheimnis. Wer prüfen kann, kann auch signieren. RFC 7518 verlangt mindestens 256 Bit Schlüssel. RFC 8725 sagt, man nimmt nie ein merkbares Passwort als Schlüssel.
  4. RS256: Das ist eine RSA-Signatur mit SHA-256. Der Private Key signiert, der Public Key prüft. RFC 7518 verlangt mindestens 2048 Bit. Viele Services können prüfen, nur der IdP kann signieren.
  5. ES256 / EdDSA: Das sind elliptische Kurven. Die Schlüssel und Signaturen sind kleiner. Das ist gut, wenn alle Bibliotheken sie unterstützen.
  6. alg=none: Das ist ein „unsicheres JWT“ ohne Signatur. Eine Bibliothek darf es nur akzeptieren, wenn der Aufrufer es ausdrücklich erlaubt. Der Schutz ist eine Allowlist der Algorithmen.
  7. Key Confusion (RS256 → HS256): Der Server erwartet RS256 und hat einen Public Key. Der Angreifer signiert mit HS256. Er nutzt den öffentlichen Key als HMAC-Geheimnis. Eine Bibliothek, die alg aus dem Header nimmt, akzeptiert das. Der Schutz ist, dass ein Key zu genau einem Algorithmus gehört.
  8. kid, jku, x5u sind Angreifer-Eingaben: kid kann SQL- oder Pfad-Injection tragen. jku zeigt auf ein fremdes JWKS und kann SSRF auslösen. Der Schutz sind Keys nur aus dem konfigurierten JWKS. Der kid dient nur als Lookup-Schlüssel.
  9. JWKS-Rotation: (1) Neuen Key ins JWKS veröffentlichen. (2) Warten, bis alle Caches ihn haben. (3) Mit dem neuen Key signieren. (4) Den alten Key erst entfernen, wenn alle alten Tokens abgelaufen sind. Resource Server laden das JWKS neu, wenn ein unbekannter kid kommt.
  10. Explizite Typen: RFC 9068 gibt JWT Access Tokens den Typ typ: at+jwt. So verwechselt niemand ein ID Token mit einem Access Token.
  11. Widerruf: Ein JWT gilt bis exp. Eine Option ist eine kurze Laufzeit von Minuten. Eine andere ist eine Denylist über jti bis exp. Weitere Optionen sind Introspection mit Opaque Tokens und der Widerruf des Refresh Tokens. Im Notfall rotiert man den Signatur-Key, dann sind alle Tokens ungültig.
  12. Speichern im Browser: localStorage liest jedes XSS. Ein Token nur im JS-Speicher ist nach einem Reload weg. Ein HttpOnly-Cookie ist für JS unsichtbar. Es braucht aber CSRF-Schutz. Am sichersten ist ein BFF, denn der Browser sieht nie einen Token (RFC 10017).
  13. Was nicht in den Payload gehört: Passwörter, Gesundheitsdaten und die AHV-Nummer. Der Payload ist lesbar. Er landet in Logs.

4. Fallen

  • „JWT ist verschlüsselt.“ → Falsch. JWS ist nur signiert. Jeder kann den Payload lesen.
  • „Die Signatur stimmt, also ist der Token gültig.“ → Falsch. Auch iss, aud, exp, nbf und der Algorithmus müssen stimmen.
  • „Logout macht den JWT ungültig.“ → Falsch. Er gilt bis exp, ausser es gibt eine Denylist oder Introspection.
  • „HS256 mit einem guten Passwort reicht.“ → Falsch. RFC 8725 verbietet merkbare Passwörter als HMAC-Key. Nötig sind mindestens 256 Bit Zufall.
  • „Den Algorithmus liest man aus dem Header.“ → Falsch. Der Server legt ihn fest. Sonst sind alg=none und Key Confusion möglich.
  • „localStorage ist sicher, wir haben kein XSS.“ → Riskant. Ein einziges XSS oder eine kompromittierte npm-Abhängigkeit liest alle Tokens.

5. Selbsttest

Warum?

Ist ein JWT verschlüsselt?

Ein normales JWT (JWS) ist nur signiert. Jeder kann es lesen. Verschlüsselt ist nur JWE.

Was ist der Key-Confusion-Angriff?

Der Server erwartet RS256. Der Angreifer signiert mit HS256 und nutzt den öffentlichen RSA-Key als HMAC-Geheimnis. Schutz: Algorithmus fest an den Key binden.

Warum sind kid und jku gefährlich?

Sie kommen vom Angreifer. kid kann Injection tragen, jku kann auf ein fremdes JWKS zeigen. Keys nur aus dem konfigurierten JWKS laden.

Warum nutzt man hmac.compare_digest statt ==?

Der Vergleich in konstanter Zeit verhindert Timing-Angriffe. Mit == verrät die Laufzeit, wie viele Bytes stimmen.

Wie innen?

Wie ist ein JWT aufgebaut?

Drei base64url-Teile, mit Punkt getrennt: Header (alg, typ, kid), Payload (Claims) und Signatur über Header und Payload.

Welche Schritte gehören zur JWT-Validierung?

Format prüfen, alg gegen Allowlist, Key über kid aus vertrautem JWKS, Signatur, iss, aud, exp und nbf. Erst dann Claims nutzen.

Was ist der alg=none-Angriff?

Der Angreifer setzt alg auf none und entfernt die Signatur. Eine naive Bibliothek akzeptiert den Token ungeprüft. Schutz: feste Algorithmus-Allowlist.

Was ist ein JWKS?

Ein JSON-Dokument mit den Public Keys des Issuers, jeder mit kid. Resource Server laden es über die jwks_uri und cachen es.

Was ist typ: at+jwt?

Der explizite Typ für JWT Access Tokens nach RFC 9068. So kann ein Server ein ID Token nicht mit einem Access Token verwechseln.

Was prüft Spring Resource Server standardmässig?

Signatur mit RS256, exp und nbf mit 60 Sekunden Clock Skew und iss. aud nur, wenn audiences gesetzt ist.

Was ist der Unterschied zwischen JWT, JWS, JWE und JWK?

JWT ist das Claims-Format. JWS ist die Signatur-Hülle, JWE die Verschlüsselungs-Hülle. JWK ist das JSON-Format für Schlüssel.

Zahlen

Wie lang muss ein HS256-Schlüssel sein?

Mindestens 256 Bit, also so lang wie die Hash-Ausgabe. Zufällig erzeugt, kein Passwort.

Wie rotiert man Signaturschlüssel ohne Ausfall?

Neuen Key zuerst veröffentlichen, warten, dann damit signieren. Den alten Key erst entfernen, wenn alle alten Tokens abgelaufen sind.

Wie lange soll ein Access-Token-JWT gelten?

Kurz, etwa 5–15 Minuten, plus Refresh Token. Ein JWT mit 24 Stunden überlebt Sperrung und Rechte-Entzug.

Vergleich

HS256 oder RS256?

HS256 nutzt ein geteiltes Geheimnis, jeder Prüfer kann auch signieren. RS256 nutzt ein Schlüsselpaar, nur der Issuer signiert. Zwischen Systemen immer RS256 oder ES256.

Wo speichert man Tokens im Browser?

Am besten gar nicht: BFF mit HttpOnly-Session-Cookie. Wenn doch, nur im Speicher und kurzlebig. localStorage ist für jedes XSS lesbar.

JWT oder Opaque Token?

JWT ist lokal prüfbar und schwer widerrufbar. Ein Opaque Token braucht Introspection beim IdP, ist aber sofort widerrufbar. Das kostet einen Netzwerk-Call mehr.

Produktion

Was gehört nicht in einen JWT-Payload?

Geheimnisse und sensible Personendaten. Der Payload ist lesbar und landet in Logs und Browsern.

Szenario: Nach einer Key-Rotation beim IdP bekommen alle Benutzer 401. Was prüfen Sie?

Ob der kid im Token im JWKS der API ist. Wahrscheinlich ist ein Key fest konfiguriert oder der Cache lädt nicht neu. Lösung: jwks_uri nutzen, bei unbekanntem kid neu laden.

Szenario: Ein Pentester ändert die Rolle im Payload auf admin und bekommt Zugriff. Was ist kaputt?

Die Signatur wird nicht oder falsch geprüft, z. B. Token nur dekodiert oder alg aus dem Header übernommen. Lösung: Validierung mit Bibliothek, fester Algorithmus, Test mit manipulierten Tokens.

Design

Welche registrierten Claims kennen Sie?

iss, sub, aud, exp, nbf, iat und jti. Zeiten sind Sekunden seit 1970.

Wie widerruft man ein JWT?

Direkt gar nicht. Man nutzt kurze Laufzeiten, eine jti-Denylist, Introspection mit Opaque Tokens oder widerruft den Refresh Token.

Szenario: Ein Service soll Tokens sofort sperren können, z. B. bei Kontodiebstahl. Wie entwerfen Sie das?

Kurze Access Tokens plus Refresh Token Rotation und Widerruf beim IdP. Für sofortige Sperre: Introspection oder eine jti-Denylist bis exp. Im Notfall den Signatur-Key rotieren.

Mehr

Gerüst

  • Warum? Viele Services sollen einen Benutzer prüfen, ohne bei jedem Request die Datenbank oder den IdP zu fragen. Dafür reicht ein Schlüssel.
  • Wie innen? Drei base64url-Teile: header.payload.signature. Prüfung: Format, Algorithmus-Allowlist, kid im JWKS, Signatur, iss, aud, exp.
  • Zahlen HS256: Schlüssel mindestens 256 Bit. RS256: mindestens 2048 Bit. Spring erlaubt 60 Sekunden Clock Skew. Access Token: 5–15 Minuten.
  • Vergleich HS256 = ein geteiltes Geheimnis, jeder Prüfer kann fälschen. RS256 = Public Key über JWKS. JWT = lokal prüfbar, Opaque Token = sofort widerrufbar.
  • Produktion Nach Key-Rotation nur 401, wenn das JWKS fest konfiguriert ist. Ohne aud-Prüfung gilt ein Token für alle APIs. Tokens landen in Logs.
  • Design Nie selbst prüfen, Bibliothek mit Allowlist. Asymmetrisch zwischen Systemen. Widerruf einplanen. Payload minimal.

Vergleich

  • HS256: ein geteilter Schlüssel, schnell, gut innerhalb eines Systems. Schlecht für viele Prüfer: Jeder Prüfer kann fälschen.
  • RS256: Schlüsselpaar, Public Key frei verteilbar über JWKS. Standard bei IdPs und Microservices.
  • ES256: wie RS256, aber kleinere Keys und Signaturen.
  • JWT (selbsttragend): lokal prüfbar, kein IdP-Call, schwer widerrufbar.
  • Opaque Token: Zufalls-String, Introspection beim IdP, sofort widerrufbar, ein Netzwerk-Call mehr.
  • Session-Cookie: Server hält Zustand, sofortiger Logout, kein Token im Browser.

In der Produktion

  1. Plötzlich nur 401 nach Key-Rotation: Der IdP signiert mit neuem kid, die API hat ein altes JWKS fest konfiguriert. Lösung: JWKS über jwks_uri laden, bei unbekanntem kid neu holen.
  2. Keine aud-Prüfung: Ein Token für API A funktioniert auch bei API B. Lösung: audiences setzen.
  3. HS256-Secret in jedem Service: Ein Leck in einem Service erlaubt gefälschte Tokens für alle. Lösung: RS256/ES256, Private Key nur beim Issuer.
  4. Lange Laufzeit: Tokens mit 24 Stunden Laufzeit überleben Sperrung und Rechte-Entzug. Lösung: 5–15 Minuten plus Refresh Token.
  5. Tokens in Logs: Access-Logs speichern den Authorization-Header. Wer die Logs liest, hat gültige Tokens. Lösung: Header maskieren.
  6. Uhrzeit-Drift: Pods mit falscher Zeit lehnen frische Tokens ab (nbf). Lösung: NTP und kleine Clock Skew.

Diagnose: Werkzeuge und Befehle

  • Dekodieren lokal: cut -d. -f2 <<< "$T" | tr '_-' '/+' | base64 -d (Padding ggf. ergänzen). Keine produktiven Tokens auf fremde Webseiten kopieren.
  • curl -s $ISSUER/.well-known/openid-configuration | jq -r .jwks_uri, dann jq '.keys[] | {kid, alg, kty}': Ist der kid des Tokens dabei?
  • Header WWW-Authenticate der 401-Antwort: error="invalid_token", error_description="…".
  • Spring Log: logging.level.org.springframework.security.oauth2=DEBUG zeigt z. B. „The iss claim is not valid“ oder „Jwt expired at …“.
  • Zeit prüfen: date -u +%s auf dem Pod gegen exp und nbf im Token.

Senior-Punkte

  1. Nie selbst parsen und prüfen. Eine reife Bibliothek (Nimbus in Spring) mit fester Algorithmus-Allowlist und konfiguriertem Issuer.
  2. Asymmetrisch zwischen Systemen. HS256 nur, wenn Aussteller und Prüfer dasselbe System sind.
  3. JWT ist kein Session-Ersatz für Browser. Für Browser-Apps ist eine Server-Session (BFF) einfacher und sicherer. JWT glänzt zwischen Services.
  4. Widerruf ist ein Entwurfsthema. Kurze Laufzeit akzeptieren oder Introspection einplanen. Eine Denylist macht JWT wieder stateful.
  5. Key-Rotation regelmässig üben. Wer nie rotiert, rotiert im Notfall falsch.
  6. Minimaler Payload. Nur IDs und Rechte, keine Personendaten. Datenschutz (DSG) gilt auch für Tokens.
