OAuth 2 Flows

Security · Tier 1 · Quellen: RFC 6749 (OAuth 2.0), draft-ietf-oauth-v2-1-17 (OAuth 2.1, Okt. 2026, noch Internet-Draft), RFC 9700 (OAuth 2.0 Security BCP, Jan. 2025), RFC 7636 (PKCE), RFC 8628 (Device Grant), RFC 10017 (OAuth for Browser-Based Apps, Aug. 2026), RFC 9449 (DPoP), RFC 8705 (mTLS), RFC 7662 (Introspection)

Kern: OAuth 2 ist ein Framework für delegierte Autorisierung: Ein Client bekommt einen Access Token, statt das Passwort des Benutzers zu kennen. Der Flow (Grant) bestimmt, wie der Client zum Token kommt. Heute gilt: Authorization Code + PKCE für Benutzer, Client Credentials für Maschinen.

1. Wo sitzen die vier Rollen?

  1. Resource Owner: besitzt die Daten und gibt Zugriff frei. Beispiel: Anna erlaubt einer App, ihre Berichte zu lesen.
  2. Client: die Anwendung, die im Namen von Anna oder für sich selbst zugreift. Beispiel: eine Angular-App mit Backend.
  3. Authorization Server (AS): meldet Anna an, holt die Zustimmung und stellt Tokens aus. Beispiel: Keycloak-Realm.
  4. Resource Server (RS): die API mit den Daten. Sie prüft jeden Access Token. Beispiel: Spring Boot mit oauth2ResourceServer().
  5. Client-Typen: Ein Confidential Client kann ein Geheimnis sicher halten (Server). Ein Public Client kann es nicht (SPA, Mobile App, CLI).

2. Die Reise eines Logins mit Authorization Code + PKCE

  1. Vorbereitung. Der Client erzeugt einen zufälligen code_verifier (43–128 Zeichen). Daraus rechnet er die code_challenge = BASE64URL(SHA256(verifier)). Dazu kommt ein zufälliger state gegen CSRF.
  2. Redirect. Der Browser geht zu /authorize?response_type=code&client_id=…&redirect_uri=…&scope=…&state=…&code_challenge=…&code_challenge_method=S256.
  3. Login. Anna meldet sich beim AS an, nicht beim Client. Der Client sieht ihr Passwort nie. Danach bestätigt sie die Scopes (Consent).
  4. Code zurück. Der AS leitet auf die exakt registrierte redirect_uri zurück. In der URL steht ein kurzlebiger, einmaliger Authorization Code.
  5. state prüfen. Der Client vergleicht state mit dem gespeicherten Wert. Anders: Abbruch.
  6. Code tauschen. Der Client schickt Code und code_verifier per POST an /token. Ein Confidential Client authentifiziert sich zusätzlich. Der AS hasht den Verifier und vergleicht mit der Challenge.
  7. Tokens. Der AS gibt Access Token, oft Refresh Token und mit Scope openid ein ID Token zurück.
  8. API-Call. Der Client ruft die API mit Authorization: Bearer … auf. Der Resource Server prüft den Token.

Warum PKCE? Ein Angreifer kann den Code abfangen, z. B. über eine bösartige App mit gleichem URL-Schema. Ohne den Verifier ist der Code wertlos. Der Verifier verlässt den Client nur im Back-Channel.

3. Beispiel: PKCE selbst rechnen

import base64, hashlib, secrets
def b64u(b): return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

v = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"        # RFC 7636, Anhang B
print(b64u(hashlib.sha256(v.encode("ascii")).digest()))
v2 = secrets.token_urlsafe(32)                         # 32 Zufallsbytes
stored = b64u(hashlib.sha256(v2.encode()).digest())    # AS speichert nur die Challenge
check = lambda ver: b64u(hashlib.sha256(ver.encode()).digest()) == stored

4. Details, die Interviewer fragen

  1. Authorization Code + PKCE: der Standard für alles mit Benutzer: Web-App, SPA, Mobile, Desktop. RFC 9700 verlangt PKCE für Public Clients und empfiehlt es für Confidential Clients. OAuth 2.1 macht PKCE zur Pflicht. Nur S256 nutzen, nicht plain.
  2. Client Credentials: Der Client ist selbst der Resource Owner. Kein Benutzer, kein Browser, kein Refresh Token. Beispiel: Batch-Job ruft eine API.
  3. Device Authorization Grant (RFC 8628): für Geräte ohne gute Tastatur (TV, CLI). Das Gerät zeigt user_code und verification_uri. Der Benutzer meldet sich am Handy an. Das Gerät pollt /token mit grant_type=urn:ietf:params:oauth:grant-type:device_code.
  4. Device-Polling: Antwort authorization_pending heisst weiter warten. Ohne interval gilt 5 Sekunden. Bei slow_down muss das Intervall um 5 Sekunden wachsen.
  5. Refresh Token: holt einen neuen Access Token ohne neuen Login. Er geht nur an den AS, nie an die API. Für Public Clients verlangt RFC 9700: sender-constrained oder Rotation.
  6. Refresh Token Rotation: Jeder Refresh gibt einen neuen Refresh Token, der alte wird ungültig. Benutzt jemand einen alten Token erneut, widerruft der AS die ganze Kette. So fällt Diebstahl auf.
  7. Implicit Grant entfernt: Er lieferte den Access Token direkt in der URL (#access_token=…). Er landet in History, Logs und Referer. RFC 9700: SHOULD NOT. OAuth 2.1: nicht mehr spezifiziert.
  8. Password Grant entfernt: Der Client sammelt Benutzername und Passwort selbst. Das widerspricht der Idee von OAuth und verhindert MFA. RFC 9700: MUST NOT. OAuth 2.1: nicht mehr spezifiziert.
  9. Exakte redirect_uri: OAuth 2.1 verlangt exakten String-Vergleich. Wildcards erlauben Code-Diebstahl über offene Redirects. Ausnahme: Port bei Loopback-Adressen für native Apps.
  10. state und nonce: state schützt den Redirect gegen CSRF. nonce (OIDC) bindet das ID Token an den Request. PKCE schützt ebenfalls gegen CSRF, ersetzt aber nicht die Prüfung.
  11. Client-Authentifizierung: client_secret_basic (geteiltes Geheimnis), private_key_jwt (signiertes JWT, kein geteiltes Geheimnis), mTLS (RFC 8705). Stärker ist alles ohne geteiltes Geheimnis.
  12. Sender-Constrained Tokens: Ein gestohlener Bearer Token ist sofort nutzbar. DPoP (RFC 9449) und mTLS binden den Token an einen Schlüssel des Clients.
  13. Audience: RFC 9700 empfiehlt Access Tokens pro Resource Server (aud). Sonst kann eine API den Token an eine andere weiterreichen.
  14. Token Exchange / On-Behalf-Of: Service A tauscht den Benutzer-Token gegen einen Token für Service B (RFC 8693, in Entra „On-Behalf-Of“). So geht der Benutzerkontext weiter, mit passender Audience.

5. Vergleich

  • Authorization Code + PKCE: mit Benutzer, Browser-Redirect. Für Web, SPA (über BFF), Mobile, Desktop.
  • Client Credentials: ohne Benutzer. Für Service-zu-Service, Jobs, Daemons.
  • Device Code: mit Benutzer, ohne Browser auf dem Gerät. Für CLI, TV, IoT. Beispiel: az login --use-device-code.
  • Refresh Token: kein eigener Login-Flow, sondern Verlängerung. Nur mit Rotation oder Bindung für Public Clients.
  • Implicit: entfernt. Ersatz: Code + PKCE.
  • Password (ROPC): entfernt. Ersatz: Code + PKCE, für Tests eigene Test-Clients.
  • OAuth 2.0 vs 2.1: 2.1 fasst 2.0 und die Security-BCP zusammen: PKCE Pflicht, kein Implicit, kein Password, exakte Redirect-URIs, keine Tokens im Query-String. Stand Nov. 2026 ist 2.1 noch ein Internet-Draft.

6. In der Produktion

  1. Tokens im Browser-Speicher: Eine SPA legt Access und Refresh Token in localStorage. Ein XSS liest beide. Lösung: BFF (Backend for Frontend). RFC 10017 nennt BFF die sicherste Architektur für Browser-Apps.
  2. Wildcard-Redirect: https://*.example.ch/* ist registriert. Eine übernommene Subdomain stiehlt Codes. Lösung: exakte URIs.
  3. Refresh Token läuft nie ab: Ein gestohlener Token gilt Monate. Lösung: Rotation, absolute Lebensdauer, Widerruf bei Logout.
  4. Client Secret im Repo oder Frontend: Ein SPA-Bundle enthält ein Secret. Jeder kann es lesen. Lösung: SPA ist Public Client ohne Secret, Secrets nur im Backend aus dem Vault.
  5. Token-Endpoint überlastet: Jeder Request holt einen neuen Client-Credentials-Token. Lösung: Token cachen bis kurz vor expires_in. Spring OAuth2AuthorizedClientManager macht das.
  6. Uhrzeit-Drift: Tokens sind „noch nicht gültig“ oder „abgelaufen“. Lösung: NTP und eine kleine Clock-Skew-Toleranz (Spring: 60 Sekunden).

7. Diagnose: Werkzeuge und Befehle

  • Browser DevTools → Network: /authorize-Redirect, code im Callback, POST /token. Fehler stehen als error=… in der URL.
  • Typische Fehlercodes: invalid_grant (Code abgelaufen, schon benutzt, Verifier falsch), invalid_client (Secret falsch), unauthorized_client (Grant für Client nicht erlaubt), invalid_scope.
  • curl https://sso.example.ch/realms/demo/.well-known/openid-configuration: Endpoints, grant_types_supported, code_challenge_methods_supported.
  • Keycloak: Events („Login Events“) zeigen Fehler pro Client. Pro Client „Standard flow“, „Direct access grants“ (ROPC), „Service accounts“ (Client Credentials) einzeln aktivieren.
  • Spring: logging.level.org.springframework.security.oauth2=DEBUG.

8. Senior-Punkte

  1. Zwei Flows reichen fast immer: Code + PKCE für Benutzer, Client Credentials für Maschinen. Device Code nur, wenn es keinen Browser gibt.
  2. Browser-Apps: BFF als Standard. Tokens bleiben im Backend, der Browser hat nur ein HttpOnly-Session-Cookie. Preis: ein zusätzlicher Server und CSRF-Schutz.
  3. Kurze Access Tokens, kontrollierte Refresh Tokens. 5–15 Minuten Access Token, Rotation und Widerruf für Refresh Tokens.
  4. Kein geteiltes Geheimnis, wo möglich: private_key_jwt, mTLS oder in Azure Workload Identity Federation statt Client Secret.
  5. Eine Audience pro API. Ein Token für alle Services ist bequem, aber ein gestohlener Token öffnet dann alles.
  6. OAuth 2.1 heute schon anwenden. Es ist noch ein Draft, aber RFC 9700 macht dieselben Regeln schon zur Best Practice.

10. Fallen

  • „PKCE ist nur für Mobile Apps.“ → Falsch. RFC 9700 verlangt es für alle Public Clients und empfiehlt es für alle. OAuth 2.1 macht es Pflicht.
  • „Implicit Flow ist richtig für SPAs.“ → Falsch. Er ist entfernt. SPAs nutzen Code + PKCE, besser über ein BFF.
  • „Mit dem Access Token weiss der Client, wer der Benutzer ist.“ → Falsch. Der Access Token ist für die API. Die Identität liefert das ID Token (OIDC).
  • „state ist optional, wir haben PKCE.“ → Ungenau. PKCE schützt den Code-Tausch. state bindet den Redirect an die Browser-Session und trägt App-Zustand.
  • „Client Credentials gibt einen Refresh Token.“ → Falsch. Er sollte keinen geben. Der Client holt einfach einen neuen Token.
  • „OAuth 2.1 ist ein fertiger RFC.“ → Falsch. Stand Nov. 2026 ist es draft-17. Die Regeln stehen aber schon in RFC 9700.

11. Fragen

Was ist OAuth 2?

Ein Framework für delegierte Autorisierung. Ein Client bekommt einen Access Token mit begrenzten Rechten, statt das Passwort des Benutzers zu kennen.

Welche vier Rollen gibt es in OAuth 2?

Resource Owner (Benutzer), Client (App), Authorization Server (stellt Tokens aus) und Resource Server (API, prüft Tokens).

Was ist der Unterschied zwischen Public und Confidential Client?

Ein Confidential Client kann ein Geheimnis sicher halten, z. B. ein Server. Ein Public Client nicht, z. B. SPA, Mobile App oder CLI.

Wie läuft der Authorization Code Flow ab?

Redirect zum AS, Login und Consent, Redirect mit Code zurück, Code per Back-Channel gegen Tokens tauschen, dann API mit Bearer Token aufrufen.

Was ist PKCE und wie funktioniert es?

Proof Key for Code Exchange. Der Client sendet zuerst den SHA-256-Hash eines Zufallswerts und beim Token-Tausch den Wert selbst. Ein gestohlener Code ist ohne diesen Wert nutzlos.

Warum S256 und nicht plain?

Bei plain steht der Verifier schon im Authorization Request. Wer den Request sieht, kennt ihn. S256 verrät nur den Hash.

Wofür ist der state-Parameter?

Er bindet die Antwort an den eigenen Request und schützt gegen CSRF im Redirect. Er kann auch App-Zustand tragen, z. B. die Zielseite.

Wann nutzen Sie Client Credentials?

Wenn kein Benutzer beteiligt ist: Service-zu-Service, Batch-Jobs, Daemons. Der Client authentifiziert sich selbst und bekommt keinen Refresh Token.

Wie funktioniert der Device Code Flow?

Das Gerät holt device_code und user_code. Der Benutzer gibt den Code auf einem zweiten Gerät ein und meldet sich an. Das Gerät pollt so lange den Token-Endpoint.

Was bedeuten authorization_pending und slow_down?

authorization_pending: Benutzer noch nicht fertig, weiter pollen. slow_down: weiter pollen, aber das Intervall um 5 Sekunden erhöhen.

Was ist ein Refresh Token?

Ein langlebiger Token, mit dem der Client beim AS neue Access Tokens holt. Er geht nie an die API.

Was ist Refresh Token Rotation?

Jeder Refresh gibt einen neuen Refresh Token, der alte wird ungültig. Wird ein alter erneut benutzt, widerruft der AS die Kette. So erkennt man Diebstahl.

Warum wurde der Implicit Grant entfernt?

Der Access Token kam in der URL und landete in History, Logs und Referer. Es gab keine Bindung an den Client. Code + PKCE löst das.

Warum wurde der Password Grant entfernt?

Der Client sieht das Passwort, MFA und SSO gehen nicht, und Phishing wird normal. RFC 9700 sagt MUST NOT.

Was ändert OAuth 2.1 gegenüber 2.0?

PKCE Pflicht, Implicit und Password entfernt, exakte Redirect-URIs, keine Bearer Tokens im Query-String, Regeln für Refresh Tokens. Es ist noch ein Draft.

Was ist RFC 9700?

Die OAuth 2.0 Security Best Current Practice vom Januar 2025. Sie fasst die Sicherheitsregeln zusammen, die OAuth 2.1 übernimmt.

Warum muss die redirect_uri exakt stimmen?

Mit Wildcards oder Präfixen kann ein Angreifer den Code auf seine Seite umleiten, z. B. über einen offenen Redirect oder eine Subdomain.

Wie authentifiziert sich ein Confidential Client?

Mit client_secret, besser mit private_key_jwt oder mTLS. Die beiden letzten brauchen kein geteiltes Geheimnis.

Was ist ein sender-constrained Token?

Ein Token, der an einen Schlüssel des Clients gebunden ist, z. B. per DPoP oder mTLS. Ein gestohlener Token allein reicht dann nicht.

Was ist ein BFF?

Backend for Frontend: ein Server macht OAuth für die SPA und hält die Tokens. Der Browser hat nur ein HttpOnly-Cookie. RFC 10017 nennt es die sicherste Variante.

Was ist Token Exchange oder On-Behalf-Of?

Ein Service tauscht den eingehenden Benutzer-Token gegen einen Token für einen nachgelagerten Service. So bleibt der Benutzerkontext erhalten, mit passender Audience.

Opaque Token oder JWT als Access Token?

JWT wird lokal geprüft, schnell, aber schwer widerrufbar. Ein Opaque Token braucht Introspection beim AS, kann aber sofort widerrufen werden.

Szenario: Eine SPA speichert Tokens im localStorage. Was raten Sie?

Ein XSS kann alle Tokens stehlen. Ich empfehle ein BFF mit HttpOnly-Cookie. Mindestens: Tokens nur im Speicher, kurze Laufzeit, Refresh Token Rotation und eine strenge CSP.

Szenario: Ein nächtlicher Job ruft eine API mit dem Passwort eines echten Benutzers auf. Was ändern Sie?

Eigenen Client mit Client Credentials anlegen, nur die nötigen Scopes vergeben. Secret aus dem Vault oder besser private_key_jwt bzw. Managed Identity. Das Benutzerkonto wird nicht mehr gebraucht.

Szenario: Benutzer melden zufällig „invalid_grant“ beim Login. Wo suchen Sie?

Code abgelaufen oder doppelt eingelöst (z. B. Doppelklick oder Retry), Verifier passt nicht (z. B. mehrere Tabs überschreiben ihn), redirect_uri weicht ab, oder Uhrzeit-Drift. Keycloak-Events und Network-Tab zeigen den Grund.
