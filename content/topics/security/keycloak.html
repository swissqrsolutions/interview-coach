Keycloak

Kern: Keycloak ist ein Open-Source-Server für Identity und Access Management. Er führt Logins durch, verwaltet Benutzer und stellt Tokens nach OpenID Connect und SAML aus. Alles liegt in einem Realm, einem abgeschlossenen Bereich mit eigenen Benutzern, Clients und Rollen.

Antwort-Muster

Frage: Wie setzen Sie Keycloak für Login und Rollen in einer App ein?

  1. Mechanismus: Ein Realm hält Benutzer, Clients und Rollen. Die App leitet zum Realm. Sie bekommt Tokens, und Protocol Mapper legen die Claims hinein.
  2. Zahl: Die Endpoints liegen unter /realms/{realm}/protocol/openid-connect/. Die Login-Session läuft standardmässig 30 Minuten. Die SSO Session Max ist standardmässig 10 Stunden.
  3. Trade-off: Eigener Betrieb gibt volle Kontrolle und keine Lizenzkosten. Dafür trage ich Updates, Datenbank und Cluster selbst.
  4. Produktion: Hinter einem Proxy müssen Hostname und Proxy-Header stimmen. Sonst passt der Issuer im Token nicht zur Konfiguration der API.

1. Ein Login in 7 Schritten

  1. /auth: Der Client schickt den Browser zu /realms/{realm}/protocol/openid-connect/auth. Mit dabei sind client_id, scope und redirect_uri.
  2. Login-Session: Keycloak legt eine kurze Session für den Login an. Der Login-Timeout steht im Tab Sessions und ist standardmässig 30 Minuten.
  3. Browser Flow: Der Authentication Flow «browser» legt fest, was der Benutzer tun muss. Das sind zum Beispiel Passwort und OTP.
  4. Required Actions: Danach folgen offene Required Actions. Ein Beispiel ist «Passwort aktualisieren». Erst wenn alle erledigt sind, ist der Login fertig.
  5. SSO-Session: Keycloak legt die SSO-Session an. Eine zweite App im gleichen Realm braucht dann kein neues Passwort.
  6. Redirect: Keycloak leitet den Browser mit einem kurzlebigen code zurück zum Client.
  7. /token: Der Client tauscht den Code gegen Tokens. Die Protocol Mapper des Clients bestimmen, welche Claims im Token stehen.

Die API ruft Keycloak danach nicht mehr auf. Sie prüft die Signatur mit den Schlüsseln von /protocol/openid-connect/certs.

2. Aufbau

  1. Realm: Ein Bereich mit eigenen Benutzern, Credentials, Rollen und Gruppen. Realms sind voneinander isoliert.
  2. master: Der Realm «master» entsteht beim ersten Start. Er enthält den ersten Admin und dient nur zur Verwaltung anderer Realms.
  3. Client: Eine App oder API, die Tokens braucht. Jeder Client hat eigene Einstellungen und eigene Rollen.
  4. Rollen und Gruppen: Realm Roles gelten im ganzen Realm. Gruppen tragen Attribute und Rollen, die Mitglieder erben.
  5. Client Scopes: Wiederverwendbare Einstellungen für viele Clients. Sie bestimmen auch Claims je nach scope.
  6. Datenbank und Cache: Daten liegen in einer Datenbank. In Produktion nutzt Keycloak einen verteilten Cache (ispn).

3. Details

  1. Public und confidential: Ein confidential client beweist sich mit einem Secret oder einem Schlüsselpaar. Eine SPA kann kein Secret geheim halten. Sie ist ein public client und nutzt PKCE.
  2. Drei Wege zum Token: Standard flow ist der Authorization Code Flow. Direct access grants geben ein Token per REST-Aufruf für einen Benutzer. Service accounts roles geben einem Client ein Token ohne Benutzer. Direct Grant vermeidet man heute.
  3. Realm Roles und Client Roles: Ein Client kann eigene Rollen definieren. Sie gelten nur für ihn und bilden einen eigenen Namensraum. Eine Composite Role enthält andere Rollen. Wer sie hat, erbt alle.
  4. Protocol Mapper: Sie legen fest, welche Claims in OIDC-Tokens oder SAML-Assertions stehen. Das gilt je Client. Eigene Rollen- oder Attribut-Claims baut man hier.
  5. Service Account: Jeder Client hat einen eingebauten Service Account. Damit holt er sich selbst ein Access Token. Das ist der Weg für Service-zu-Service-Aufrufe.
  6. Lightweight Access Token: Die Clients security-admin-console und admin-cli nutzen seit Keycloak 26 standardmässig lightweight tokens. Sie tragen keine Rollen. Der Server löst Rollen aus der Session auf.
  7. Timeouts: Der Login-Timeout ist standardmässig 30 Minuten. SSO Session Max ist standardmässig 10 Stunden. Mit «Revoke Refresh Token» ist ein Refresh Token nach einmaliger Nutzung ungültig.
  8. Identity Brokering: Keycloak kann die Anmeldung an externe OIDC- oder SAML-Provider abgeben. Ein Beispiel ist Social Login. Die App sieht trotzdem nur Keycloak.
  9. User Federation: Keycloak prüft Passwörter gegen externe Speicher wie LDAP oder Active Directory. Eine Kerberos-Anbindung gibt es auch.
  10. Endpoints: Alle liegen unter /realms/{realm}/. Dort stehen .well-known/openid-configuration und protocol/openid-connect/ mit auth, token, userinfo, logout, certs, token/introspect und revoke. Introspection ist nur für confidential clients.
  11. Betriebsmodi: start-dev ist der Entwicklungsmodus. Dort ist HTTP an, die Datenbank dev-file und der Cache local. In Produktion ist http-enabled aus und hostname-strict an. Die Datenbank setzt man selbst.
  12. Cluster und Health: Für Produktion braucht man mindestens zwei Instanzen. Keycloak nutzt JGroups und Infinispan. Ein Load Balancer prüft /health/ready. Health und Metrics sind erst nach health-enabled und metrics-enabled da.

4. Fallen

  • „Ein Realm ist ein Client.“ → Falsch. Ein Realm ist der ganze Bereich. Ein Client ist nur eine App darin.
  • „Meine App läuft im Realm master.“ → Falsch. Der Realm master ist nur für die Verwaltung. Für Apps legt man eigene Realms an.
  • „Eine Client Role ist eine Realm Role.“ → Falsch. Eine Client Role hat einen eigenen Namensraum und gilt nur für den Client.
  • „start-dev ist auch für Produktion gut.“ → Falsch. Der Entwicklungsmodus nutzt HTTP, eine Datei-Datenbank und einen lokalen Cache. Das ist nichts für Produktion.
  • „Die API fragt Keycloak bei jedem Request.“ → Falsch. Ein JWT prüft die API selbst mit den Schlüsseln aus certs. Introspection braucht man nur bei Bedarf.
  • „Nach der Rollenänderung gilt die neue Rolle sofort.“ → Falsch. Ein ausgestelltes Token behält die alten Rollen bis zum Ablauf. Erst das nächste Token hat die neuen.

5. Selbsttest

Warum?

Warum Keycloak statt eines eigenen Logins?

Passwörter, MFA, SSO und Standard-Protokolle sind schwer sicher zu bauen. Keycloak liefert sie fertig. Alle Apps nutzen ein Login.

Warum gibt es Realms?

Ein Realm trennt Benutzer, Rollen und Clients vollständig. So kann ein Server mehrere getrennte Welten bedienen.

Warum Protocol Mapper?

Jede App will andere Claims im Token. Mapper legen das je Client fest, ohne Code in Keycloak.

Wie innen?

Was ist ein Realm?

Ein Bereich, der Benutzer, Credentials, Rollen und Gruppen verwaltet. Er ist von anderen Realms isoliert.

Wie läuft ein Login ab?

Auth-Request, Login-Session, Browser Flow, Required Actions, SSO-Session, Redirect mit Code, Token-Tausch.

Was sind Client Scopes?

Wiederverwendbare Einstellungen für mehrere Clients. Sie machen Claims auch vom Parameter scope abhängig.

Was ist Identity Brokering?

Keycloak gibt die Anmeldung an einen externen OIDC- oder SAML-Provider ab, zum Beispiel an Social Logins.

Was ist User Federation?

Keycloak prüft Zugangsdaten gegen externe Speicher wie LDAP oder Active Directory.

Zahlen

Wie lange gilt die Login-Session standardmässig?

Etwa 30 Minuten. Der Wert heisst «Login timeout» und steht im Tab Sessions.

Was ist der Standard für SSO Session Max?

10 Stunden.

Wie heisst der Token-Endpoint?

/realms/{realm}/protocol/openid-connect/token.

Welche Keycloak-Version gilt aktuell?

Die Doku zeigt 26.8.2. Neu in 26.8 sind unter anderem OID4VCI als Preview und SCIM-API-Unterstützung.

Vergleich

Keycloak oder Entra ID?

Keycloak ist Open Source und selbst betrieben. Entra ID ist ein SaaS-Dienst von Microsoft. Es ist eine Betriebsentscheidung.

Realm Role oder Client Role?

Eine Realm Role gilt im ganzen Realm. Eine Client Role gilt nur für einen Client und hat einen eigenen Namensraum.

Public oder confidential client?

Confidential beweist sich mit Secret oder Schlüsselpaar. Public kann das nicht, zum Beispiel eine SPA, und nutzt PKCE.

Standard flow oder Direct access grants?

Standard flow ist der Code Flow im Browser. Direct Grant schickt Passwörter an die App. Man vermeidet ihn heute.

Produktion

Was braucht Keycloak hinter einem Reverse Proxy?

Den richtigen Hostnamen und die Proxy-Header (proxy-headers mit forwarded oder xforwarded). Sonst stimmen Issuer und URLs nicht.

Wie prüft ein Load Balancer die Instanz?

Mit /health/ready. Der Readiness-Check meldet DOWN, bis der Start fertig ist.

Szenario: Die API lehnt alle Tokens ab, seit Keycloak hinter einem Ingress läuft. Was prüfen Sie?

Den Issuer im Discovery-Dokument gegen iss im Token und gegen die API-Konfiguration. Meist stimmen Hostname oder Schema nicht. Lösung: Hostname und Proxy-Header setzen.

Szenario: Ein Benutzer hat die Rolle verloren, kann aber noch zugreifen. Warum?

Sein Access Token trägt die alte Rolle bis zum Ablauf. Lösung: kurze Token-Lebensdauer. Bei Bedarf Introspection oder Revoke.

Wie viele Instanzen für Produktion?

Mindestens zwei. Keycloak nutzt dafür JGroups und Infinispan.

Design

Wie modellieren Sie Rollen?

Fachliche Rollen als Client Roles der jeweiligen App. Rollen für alle als Realm Roles. Gruppen bündeln Rollen für Teams.

Wie sichern Sie eine Spring-API mit Keycloak?

Als Resource Server mit issuer-uri auf den Realm. Spring holt das JWKS und prüft Signatur, Issuer und Ablauf.

Szenario: Ein Batch-Job soll eine API aufrufen. Wie bekommt er ein Token?

Ein eigener confidential Client mit Service Account. Der Job holt sich damit per Client Credentials ein Token. Kein Benutzer-Passwort.

Ein Realm für alle Kunden oder je Kunde einen?

Ein Realm trennt Benutzer und Einstellungen hart. Je Kunde ein Realm gibt Isolation, kostet aber mehr Pflege. Es ist eine Abwägung.

Mehr

Gerüst

  • Warum? Zentrales Login, SSO und Standard-Protokolle ohne Eigenbau.
  • Wie innen? Realm mit Clients, Rollen und Gruppen. Browser Flow, Protocol Mapper, Tokens über /protocol/openid-connect/.
  • Zahlen Login-Timeout 30 Minuten. SSO Session Max 10 Stunden. Version 26.8.
  • Vergleich Entra ID ist SaaS. Keycloak ist selbst betrieben. Client Role gegen Realm Role.
  • Produktion Issuer passt nicht hinter Proxy. Alte Rollen im Token. Mindestens zwei Instanzen.
  • Design Rollen als Client Roles. Service Account für Jobs. Kurze Token-Lebensdauer.

Beispiel: Keycloak lokal starten und eine API anbinden

# Keycloak im Entwicklungsmodus (Docker)
docker run -p 127.0.0.1:8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.8.2 start-dev

# Discovery des Realms "demo" (nach dem Anlegen in der Admin Console)
curl http://localhost:8080/realms/demo/.well-known/openid-configuration

# Spring Boot API als Resource Server (application.properties)
spring.security.oauth2.resourceserver.jwt.issuer-uri=http://localhost:8080/realms/demo

Nicht ausgeführt.

  1. Admin Console: Sie liegt unter http://localhost:8080/admin. Dort legt man den Realm demo, einen Client und Benutzer an.
  2. Discovery: Die Antwort enthält issuer, token_endpoint und jwks_uri.
  3. issuer-uri: Spring liest die Discovery beim Start. Es prüft danach jedes Token gegen Signatur, Issuer und Ablauf.
  4. Entwicklungsmodus: start-dev nutzt HTTP und eine Datei-Datenbank. Für Produktion gelten andere Optionen.

Vergleich

  • Keycloak: Open Source, selbst betrieben, Realms, LDAP und Brokering eingebaut.
  • Entra ID: SaaS von Microsoft, eng mit Azure verbunden. Kein eigener Betrieb.
  • Spring Authorization Server: Ein Framework, mit dem man einen eigenen Authorization Server baut. Mehr Code, mehr Freiheit.
  • OIDC oder SAML: Keycloak spricht beide. OIDC passt zu SPAs und APIs. SAML findet man in älteren Enterprise-Apps.
  • Lightweight oder volles Token: Lightweight tokens sind klein, tragen aber keine Rollen. Volle Tokens tragen die Claims direkt.

Produktion

  1. Issuer passt nicht: Hostname oder Schema im Token weichen von der API-Konfiguration ab. Lösung: hostname und proxy-headers korrekt setzen.
  2. Entwicklungsdatenbank in Produktion: dev-file ist für Produktion veraltet. Lösung: db auf eine echte Datenbank wie postgres setzen.
  3. Admin Console öffentlich: Admin API und Console gehören auf einen eigenen Hostnamen oder Pfad. Nicht für die Öffentlichkeit gedachte REST-APIs blockiert man am Proxy.
  4. Alte Rollen im Token: Rollen ändern sich erst im nächsten Token. Lösung: kurze Lebensdauer und Refresh Token.
  5. Instanz fällt aus: Mit nur einer Instanz ist das Login weg. Lösung: mindestens zwei Instanzen mit verteiltem Cache.
  6. Request-Stau: Ohne Grenze stauen sich Requests. Lösung: http-max-queued-requests setzen. Überzählige Requests bekommen sofort 503.

Diagnose: Werkzeuge und Befehle

  • Discovery prüfen: curl …/realms/{realm}/.well-known/openid-configuration zeigt Issuer und Endpoints.
  • Token lesen: Der Payload eines JWT ist Base64URL. Man dekodiert ihn lokal und prüft iss, aud, exp und Rollen-Claims.
  • Health: /health/ready zeigt, ob die Instanz bereit ist. Dafür muss health-enabled an sein.
  • Events: Die Admin Console zeigt Login-Events. Dort findet man fehlgeschlagene Logins und ihre Gründe.
  • Sessions: Der Tab Sessions zeigt aktive SSO-Sessions pro Benutzer und Client.

Senior-Punkte

  1. Keycloak ist ein System, das man betreibt.: Updates, Datenbank, Cache und Cluster gehören zum Preis. Gegenüber SaaS gewinnt man Kontrolle und verliert Betriebsruhe.
  2. Rollen gehören zur App.: Fachliche Rollen als Client Roles. Realm Roles nur für wirklich übergreifende Rechte.
  3. Token klein halten.: Grosse Tokens kosten Bandbreite und können Header-Limits sprengen. Nur Claims einbauen, die die API braucht.
  4. Kurze Lebensdauer statt Widerruf.: Ein JWT lässt sich nicht zurückrufen. Kurze Access Tokens und Refresh-Token-Rotation begrenzen den Schaden.
  5. Ein Client je App und Zweck.: SPA, Backend und Batch-Job bekommen getrennte Clients. So sind Rechte und Secrets sauber getrennt.
  6. Der Admin-Zugang ist ein Ziel.: Die Admin Console gehört nicht ins öffentliche Netz. Der master-Realm bleibt für Admins reserviert.
