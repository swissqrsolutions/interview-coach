OpenID Connect

Kern: OpenID Connect (OIDC) ist eine Identitätsschicht auf OAuth 2. Es fügt das ID Token hinzu: ein signiertes JWT, das dem Client sagt, wer sich angemeldet hat. OAuth gibt Zugriff, OIDC gibt Login.

1. Wo sitzt OIDC?

  1. OpenID Provider (OP): der Authorization Server mit OIDC-Funktionen. Er stellt ID Tokens aus. Beispiel: ein Keycloak-Realm.
  2. Relying Party (RP): der Client, der dem OP die Identität glaubt. Beispiel: eine Spring-Boot-Web-App mit oauth2Login().
  3. Scope openid: macht aus einem OAuth-Request einen OIDC-Request. Ohne ihn gibt es kein ID Token.
  4. ID Token: geht an den Client. Access Token: geht an die API. Das ist die wichtigste Trennung.

2. Die Reise eines Logins (die Geschichte zum Merken)

  1. Discovery. Der Client liest {issuer}/.well-known/openid-configuration. Dort stehen alle Endpoints und die jwks_uri. Keine URL ist hart kodiert.
  2. Authorization Request. Der Client schickt den Browser zu /authorize mit scope=openid profile email, state, nonce und PKCE.
  3. Login beim OP. Anna meldet sich bei Keycloak an. Der Client sieht kein Passwort. Keycloak kann dabei an LDAP oder einen anderen IdP weiterleiten.
  4. Token-Tausch. Der Client tauscht den Code gegen ID Token, Access Token und Refresh Token.
  5. ID Token prüfen. Signatur mit dem Schlüssel aus dem JWKS, iss exakt, aud enthält die eigene client_id, exp in der Zukunft, nonce gleich dem gesendeten Wert.
  6. Session. Der Client merkt sich den Benutzer über iss + sub. Der Browser bekommt ein Session-Cookie.
  7. UserInfo (optional). Für mehr Profildaten ruft der Client /userinfo mit dem Access Token auf. Das sub der Antwort muss exakt dem sub im ID Token entsprechen.

4. Details, die Interviewer fragen

  1. Pflicht-Claims im ID Token: iss, sub, aud, exp, iat. nonce ist Pflicht, wenn der Request eine nonce hatte. auth_time ist Pflicht bei max_age.
  2. sub: eine lokal eindeutige, nie neu vergebene ID innerhalb des Issuers, max. 255 ASCII-Zeichen. Der stabile Schlüssel ist iss + sub, nicht die E-Mail.
  3. azp: Authorized Party, die client_id, für die das Token ausgestellt wurde. Wichtig, wenn aud mehrere Werte hat.
  4. acr und amr: acr beschreibt die Stärke der Anmeldung, amr die Methoden (z. B. pwd, otp). Damit prüft eine App, ob MFA stattfand.
  5. Standard-Scopes: profile (Name, preferred_username, locale …), email (email, email_verified), address, phone. openid ist Pflicht.
  6. Discovery: /.well-known/openid-configuration liefert issuer, authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri, unterstützte Algorithmen und Scopes. Der issuer darin muss exakt zum iss passen.
  7. UserInfo: Standard ist JSON, signiert nur auf Wunsch. Aufruf mit Access Token. Das sub muss mit dem ID Token übereinstimmen, sonst Daten verwerfen.
  8. Keycloak-Pfade: Issuer ist https://host/realms/{realm}. Endpoints unter /realms/{realm}/protocol/openid-connect/: auth, token, userinfo, certs (JWKS), logout, token/introspect.
  9. Entra-ID-Pfade: Authority ist https://login.microsoftonline.com/{tenant}/v2.0, Discovery darunter. JWKS unter /discovery/v2.0/keys. UserInfo liegt bei Microsoft Graph. {tenant} kann eine Tenant-ID oder common, organizations, consumers sein.
  10. Entra: fremde Tokens nicht prüfen. Microsoft sagt: Tokens für APIs, die man nicht besitzt (z. B. Graph), nicht selbst validieren. Sie können ein spezielles Format haben.
  11. Logout: RP-Initiated Logout leitet zum end_session_endpoint. Back-Channel Logout schickt ein Logout-Token Server-zu-Server. Front-Channel Logout ruft eine URL im Browser auf. Die eigene Session muss die App immer selbst löschen.
  12. Hybrid und Implicit in OIDC: response_type=id_token gibt es noch in der Spezifikation. Empfehlung heute: nur code mit PKCE.

5. Vergleich

  • ID Token: für den Client. Zweck: Login-Beweis. aud = client_id. Immer JWT. Nicht an APIs schicken.
  • Access Token: für die API. Zweck: Zugriff. aud = API. JWT oder opaque. Der Client soll ihn nicht interpretieren.
  • Refresh Token: für den Authorization Server. Zweck: neue Tokens. Meist opaque.
  • OIDC vs SAML 2.0: beide machen SSO. SAML nutzt XML-Assertions und Browser-POST, verbreitet in alten Enterprise-Apps. OIDC nutzt JSON/JWT und passt zu SPAs, Mobile und APIs.
  • OIDC vs reines OAuth: OAuth sagt nur „dieser Token darf X“. OIDC sagt zusätzlich „das ist Anna, angemeldet um 9:02 mit MFA“.
  • Keycloak vs Entra ID: Keycloak ist Open Source und selbst betrieben, mit Realms, LDAP-Föderation und Identity Brokering. Entra ID ist SaaS von Microsoft, stark integriert mit Azure und Managed Identities.

6. In der Produktion

  1. Login über Access Token: Eine App nimmt ein beliebiges gültiges Access Token als Login. Ein Token für eine andere App reicht dann zum Login. Lösung: ID Token mit aud und nonce prüfen.
  2. Benutzer per E-Mail verknüpft: E-Mail ändert sich oder ist nicht verifiziert. Ein Angreifer übernimmt ein Konto. Lösung: Schlüssel iss + sub, E-Mail nur mit email_verified.
  3. Issuer passt nicht: Keycloak hinter Proxy meldet http://keycloak:8080/realms/demo, die App erwartet https://sso…. Validierung schlägt fehl. Lösung: Hostname von Keycloak richtig konfigurieren (hostname-Option), Proxy-Header.
  4. Multi-Tenant mit common: Das iss enthält die Tenant-ID jedes Benutzers. Eine feste Issuer-Prüfung schlägt fehl, keine Prüfung lässt fremde Tenants herein. Lösung: Liste erlaubter Tenants prüfen.
  5. Logout unvollständig: Die App löscht ihre Session, aber die SSO-Session bei Keycloak lebt. Der nächste Klick meldet still wieder an. Lösung: RP-Initiated Logout zusätzlich.
  6. Zu grosse Tokens: Alle Gruppen im Token, der Header wird zu gross, Proxy oder Server lehnt ab (HTTP 431 oder 400). Lösung: Claims mit Mappern begrenzen, Gruppen serverseitig nachladen.

7. Diagnose: Werkzeuge und Befehle

  • curl -s https://sso.example.ch/realms/demo/.well-known/openid-configuration | jq .issuer,.jwks_uri: stimmt der Issuer?
  • curl -s …/protocol/openid-connect/certs | jq '.keys[].kid': welche Schlüssel sind aktiv?
  • Token dekodieren: Header und Payload lokal base64url-dekodieren. Prüfen: iss, aud, azp, exp, kid.
  • Keycloak: Client → Client scopes → „Evaluate“ zeigt das ID Token, Access Token und die UserInfo eines Benutzers.
  • Entra ID: App registrations → Endpoints zeigt das Metadata-Dokument. Sign-in-Logs zeigen Fehlercodes.
  • Spring: logging.level.org.springframework.security=DEBUG, Fehler wie invalid_id_token oder invalid_nonce.

8. Senior-Punkte

  1. Identität und Zugriff trennen. ID Token nur im Client, Access Token nur an APIs. Diese Regel verhindert die meisten OIDC-Fehler.
  2. Bibliothek statt Eigenbau. Validierung, Discovery und Key-Rotation sind fehleranfällig. Spring Security, MSAL oder ein zertifizierter Client machen das richtig.
  3. Ein zentraler IdP gibt SSO, MFA und ein Audit an einer Stelle. Preis: Der IdP ist kritische Infrastruktur und braucht HA, Backup und Monitoring.
  4. Keycloak oder Entra ID ist eine Betriebsentscheidung: Selbst betreiben gibt Kontrolle und Datenhoheit, SaaS spart Betrieb und bringt Azure-Integration.
  5. Claims sparsam. Jedes Claim ist ein Datenschutz-Thema (DSG) und macht Tokens grösser. Nur das, was der Client wirklich braucht.
  6. Logout ist verteilt. App-Session, IdP-Session und Tokens enden nicht automatisch zusammen. Das muss man bewusst entwerfen.

10. Fallen

  • „OIDC ist eine Alternative zu OAuth.“ → Falsch. OIDC baut auf OAuth 2 auf und nutzt dessen Flows.
  • „Das ID Token schicke ich an die API.“ → Falsch. Die API bekommt das Access Token. Das ID Token ist für den Client.
  • „Die E-Mail ist die Benutzer-ID.“ → Falsch. Die stabile ID ist iss + sub.
  • „UserInfo ist immer signiert.“ → Falsch. Standard ist einfaches JSON über TLS. Signiert nur auf Wunsch.
  • „Logout in der App meldet auch bei Keycloak ab.“ → Falsch. Dafür braucht es RP-Initiated Logout.

11. Fragen

Was ist OpenID Connect?

Eine Identitätsschicht auf OAuth 2. Sie fügt das ID Token, den UserInfo-Endpoint und Discovery hinzu. Damit kann sich ein Benutzer bei einer App anmelden.

Was ist der Unterschied zwischen ID Token und Access Token?

Das ID Token sagt dem Client, wer sich angemeldet hat, aud ist die client_id. Das Access Token gibt Zugriff auf eine API, aud ist die API.

Welche Claims muss ein ID Token haben?

iss, sub, aud, exp und iat. Dazu nonce, wenn der Request eine nonce hatte, und auth_time bei max_age.

Wie prüft ein Client das ID Token?

Signatur mit dem JWKS-Schlüssel, iss exakt, aud enthält die client_id, exp nicht vorbei, iat plausibel, nonce gleich dem gesendeten Wert.

Wofür ist die nonce?

Sie bindet das ID Token an genau diesen Login-Request. Ein abgefangenes Token aus einem anderen Login wird so erkannt.

Was ist sub, und warum nicht die E-Mail als ID?

sub ist eine lokal eindeutige, nie neu vergebene ID beim Issuer. E-Mails ändern sich und sind nicht immer verifiziert. Schlüssel ist iss + sub.

Was ist azp?

Die Authorized Party, also die client_id, für die das Token ausgestellt wurde. Relevant, wenn aud mehrere Werte enthält.

Was ist das Discovery-Dokument?

JSON unter /.well-known/openid-configuration mit issuer, allen Endpoints, jwks_uri und unterstützten Algorithmen. Clients konfigurieren sich daraus selbst.

Was liefert der UserInfo-Endpoint?

Profil-Claims des Benutzers, aufgerufen mit dem Access Token. Standard ist JSON. sub muss mit dem ID Token übereinstimmen.

Welche Standard-Scopes gibt es?

openid (Pflicht), profile, email, address und phone. Jeder Scope steht für eine Gruppe von Claims.

Was sind acr und amr?

acr beschreibt die Stärke der Authentifizierung, amr die benutzten Methoden. Damit prüft eine App z. B., ob MFA benutzt wurde.

Wie sieht die Issuer-URL bei Keycloak aus?

https://host/realms/{realm}. Die Endpoints liegen unter /realms/{realm}/protocol/openid-connect/, z. B. token und certs.

Was ist bei Entra ID mit „common“ zu beachten?

Dann können Benutzer aus vielen Tenants kommen, und iss enthält deren Tenant-ID. Die App muss die erlaubten Tenants selbst prüfen.

Welche Logout-Varianten gibt es?

RP-Initiated Logout über den end_session_endpoint, Back-Channel Logout Server-zu-Server und Front-Channel Logout im Browser. Die App muss ihre eigene Session immer selbst löschen.

OIDC oder SAML?

Beide machen SSO. OIDC ist JSON/JWT-basiert und passt zu SPAs, Mobile und APIs. SAML ist XML-basiert und vor allem in älteren Enterprise-Apps verbreitet.

Wie konfigurieren Sie Spring Boot als OIDC-Client?

spring-boot-starter-oauth2-client, eine Registration mit client-id und scope openid, issuer-uri beim Provider, dazu http.oauth2Login(). Spring macht Discovery und ID-Token-Prüfung.

Warum soll ein Client das Access Token nicht lesen?

Es ist für die API bestimmt, das Format kann sich ändern oder opaque sein. Microsoft warnt ausdrücklich davor, z. B. Graph-Tokens selbst zu validieren.

Szenario: Nach dem Umzug von Keycloak hinter einen Ingress schlägt die Token-Validierung fehl. Was prüfen Sie?

Den issuer im Discovery-Dokument gegen iss im Token und gegen die konfigurierte issuer-uri. Meist stimmt Hostname oder Schema nicht. Lösung: Keycloak-Hostname und Proxy-Header richtig setzen.

Szenario: Ein Benutzer ist nach Logout sofort wieder angemeldet. Warum?

Die App hat nur ihre eigene Session gelöscht, die SSO-Session beim IdP lebt noch. Lösung: zusätzlich RP-Initiated Logout zum end_session_endpoint.

Szenario: Eine zweite App akzeptiert Tokens der ersten App als Login. Was ist falsch?

Sie prüft aud nicht oder nutzt Access Tokens als Login. Lösung: ID Token prüfen, aud muss die eigene client_id sein, dazu nonce.
