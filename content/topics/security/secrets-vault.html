Secret-Management mit Vault

Security · Tier 1 · Quellen: HashiCorp Vault Docs (Database Secrets Engine, Kubernetes Auth), Microsoft Learn (Azure Key Vault Soft-Delete, Workload Identity), External Secrets Operator Docs (Overview, Azure Key Vault Provider, API external-secrets.io/v1), OWASP Secrets Management Cheat Sheet, Kubernetes Docs (Secrets)

Kern: Secret-Management heisst: Passwörter, Keys und Zertifikate liegen an einem geschützten Ort, mit Zugriffskontrolle, Audit und Rotation. Es löst Secret Sprawl, also Secrets verstreut in Code, Config, CI und Chats. Das Ziel ist: kein Secret im Repo, kurze Lebensdauer, jeder Zugriff nachvollziehbar.

1. Wo sitzen die Secrets?

  1. Azure Key Vault: verwalteter Speicher für Secrets, Keys und Zertifikate. Zugriff über Entra-ID-Identitäten und Azure RBAC. Beispiel: DB-Passwort einer App.
  2. HashiCorp Vault: Secret-Server mit vielen Secrets Engines. Neben statischen Secrets (KV) erzeugt er dynamische Secrets. Beispiel: ein DB-User pro Pod mit 1 h Laufzeit.
  3. External Secrets Operator (ESO): ein Kubernetes-Controller. Er liest Secrets aus einem externen Store und schreibt sie als Kubernetes-Secret. Beispiel: ExternalSecret → Secret db-credentials.
  4. Workload Identity: Der Pod beweist seine Identität mit einem Kubernetes-ServiceAccount-Token. Entra ID tauscht es gegen ein Azure-Token. Kein Client Secret nötig.
  5. Git: enthält nur den Verweis (remoteRef.key), nie den Wert. So funktioniert GitOps ohne Secrets im Repo.

2. Die Reise eines Secrets (die Geschichte zum Merken)

  1. Anlegen. Ein Admin oder eine Pipeline legt database-password im Key Vault an. Niemand kopiert den Wert in Code oder Ticket.
  2. Verweis in Git. Ein ExternalSecret im Helm-Chart nennt nur den Namen database-password. ArgoCD deployt es wie jedes andere YAML.
  3. Identität. ESO nutzt einen ServiceAccount mit den Annotationen azure.workload.identity/client-id und tenant-id. Entra ID gibt ihm ein kurzlebiges Token. Es gibt kein Passwort für den Zugang zum Passwort.
  4. Holen. ESO liest den Wert aus dem Key Vault. Die Identität hat nur die Rolle „Key Vault Secrets User“ auf diesen Vault (Least Privilege).
  5. Kubernetes-Secret. ESO schreibt Secret database-credentials. Der Pod bekommt den Wert als Env-Variable oder Datei.
  6. Rotation. Jemand setzt eine neue Version im Key Vault. Die App merkt davon noch nichts.
  7. Refresh. Nach refreshInterval aktualisiert ESO das Kubernetes-Secret. Env-Variablen ändern sich erst nach Pod-Neustart. Gemountete Dateien aktualisiert das Kubelet nach einer Weile, aber nicht bei subPath.

3. Beispiel: Secret Scanning und der saubere Weg

RULES = [
  ("generic-password", re.compile(r"(?i)(password|passwd|pwd)\s*[:=]\s*(?!\$\{)([^\s\"']{6,})")),
  ("aws-access-key",   re.compile(r"\bAKIA[0-9A-Z]{16}\b")),
  ("github-pat",       re.compile(r"\bghp_[A-Za-z0-9]{36}\b")),
]
# gescannt: application.yml, application-prod.yml, docker-compose.local.yml, Client.java
$ python -I scan_demo.py
application.yml:4  generic-password  wert=Somm*** entropie=3.10
docker-compose.local.yml:4  generic-password  wert=post*** entropie=2.75
Client.java:1  aws-access-key    wert=AKIA*** entropie=3.68
Client.java:2  github-pat        wert=ghp_*** entropie=0.67
application-prod.yml: kein Fund (Platzhalter ${DB_PASSWORD})

Echte Ausgabe, Python 3.12. Ein Mini-Scanner mit Regeln im Stil von Gitleaks. Echte Tools haben Hunderte Regeln.

  1. Ein Klartext-Passwort in application.yml wird gefunden. Das ist ein echtes Leck.
  2. POSTGRES_PASSWORD: postgres in der lokalen Compose-Datei ist ein Fund, aber kein echtes Geheimnis. Er braucht eine begründete Ausnahme, keine abgeschaltete Regel.
  3. Bekannte Formate (AWS-Key, GitHub-Token) erkennt man am Präfix. Die Entropie hilft bei unbekannten Formaten. Der Dummy-Token mit 36× a hat fast keine Entropie, das Präfix findet ihn trotzdem.
  4. ${DB_PASSWORD} ist der richtige Weg: Der Wert kommt zur Laufzeit aus der Umgebung.

Der saubere Weg mit ESO und Azure Key Vault (laut ESO-Doku):

apiVersion: external-secrets.io/v1
kind: SecretStore
metadata: { name: azure-kv, namespace: app }
spec:
  provider:
    azurekv:
      authType: WorkloadIdentity
      vaultUrl: "https://my-vault.vault.azure.net"
      serviceAccountRef: { name: eso-workload-sa }
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: database-credentials, namespace: app }
spec:
  refreshInterval: 1h
  secretStoreRef: { kind: SecretStore, name: azure-kv }
  target: { name: database-credentials }
  data:
    - secretKey: password
      remoteRef: { key: database-password }

4. Details, die Interviewer fragen

  1. Secret Sprawl: Secrets liegen in Git, CI-Variablen, Wikis, Chats und Laptops. Niemand weiss, wo überall. Rotation ist dann unmöglich.
  2. Kubernetes-Secret ist nicht geheim: Die Daten sind nur base64-kodiert. Schutz kommt von RBAC, Verschlüsselung von etcd at rest und davon, wer Pods im Namespace starten darf.
  3. Statisch vs dynamisch: Ein statisches Secret lebt, bis jemand es ändert. Ein dynamisches Secret erzeugt Vault bei Bedarf mit einer Lease (TTL). Nach Ablauf widerruft Vault es.
  4. Vault-Begriffe: Auth Method (wer bist du: Kubernetes, OIDC, AppRole), Policy (welche Pfade darfst du), Secrets Engine (KV, Database, PKI, Transit), Lease (Lebensdauer), Seal/Unseal (Master-Key-Schutz, Auto-Unseal mit Cloud-KMS).
  5. Vault Kubernetes Auth: Der Pod schickt sein ServiceAccount-Token. Vault prüft es bei der Kubernetes-API und gibt ein Vault-Token mit passender Policy.
  6. Transit Engine: „Encryption as a Service“. Die App schickt Daten zum Ver- und Entschlüsseln, den Schlüssel sieht sie nie.
  7. Azure Key Vault Soft-Delete: ist bei neuen Vaults an und lässt sich nicht abschalten. Gelöschte Objekte bleiben 7–90 Tage wiederherstellbar, Standard 90. Purge Protection ist optional und verhindert endgültiges Löschen vor Ablauf.
  8. Azure-Zugriffsmodell: Azure RBAC (empfohlen) mit Rollen wie „Key Vault Secrets User“ statt alter Access Policies. Netz: Private Endpoint, Public Access aus.
  9. ESO-Ressourcen: SecretStore (pro Namespace), ClusterSecretStore (clusterweit), ExternalSecret (was holen), PushSecret (in die andere Richtung). Aktuelle API: external-secrets.io/v1.
  10. Alternativen zu ESO: Secrets Store CSI Driver mountet Secrets als Dateien direkt aus dem Store. Vault Agent Injector setzt einen Sidecar in den Pod. Sealed Secrets und SOPS verschlüsseln Secrets im Git.
  11. Rotation: (1) Neues Secret erzeugen. (2) Beide gelten parallel (zwei DB-User oder zwei Keys). (3) Apps umstellen. (4) Altes widerrufen. Ohne Parallelphase gibt es Ausfall.
  12. Secret Scanning in CI: Pre-Commit-Hook (z. B. Gitleaks) lokal, Scan in jeder Pipeline, Push Protection auf GitHub blockt bekannte Token-Formate beim Push. SonarQube meldet hartkodierte Passwörter.
  13. Lizenz: HashiCorp Vault steht unter der Business Source License. OpenBao ist ein Open-Source-Fork unter der Linux Foundation.

5. Vergleich

  • Azure Key Vault: verwaltet, günstig, Entra-ID-integriert, HSM-Option. Keine dynamischen DB-Secrets.
  • HashiCorp Vault: Cloud-neutral, dynamische Secrets, PKI, Transit. Muss betrieben werden (HA, Unseal, Backup) oder als HCP gekauft.
  • ESO: synchronisiert in Kubernetes-Secrets. Apps bleiben einfach (Env/Datei). Das Secret liegt aber dann auch in etcd.
  • CSI Driver: Datei im Pod, optional ohne Kubernetes-Secret. Pod startet nicht, wenn der Store nicht erreichbar ist.
  • Sealed Secrets / SOPS: verschlüsselt in Git. Gut für kleine Setups. Rotation und Audit sind schwächer als bei einem zentralen Store.
  • Managed Identity / Workload Identity: beste Lösung, wenn der Zieldienst Entra ID versteht (Storage, SQL, Key Vault). Dann gibt es gar kein Secret.

6. In der Produktion

  1. Secret in Git gepusht: Ein Passwort steht im Commit. Lösung: zuerst rotieren, dann History bereinigen. Die History bereinigen allein reicht nie, Forks und Caches haben es schon.
  2. Rotation ohne Neustart: Key Vault hat das neue Passwort, Pods nutzen das alte aus der Env. Lösung: Reload-Mechanismus (z. B. Reloader-Controller oder Checksum-Annotation im Deployment) oder Datei-Mount mit Re-Read.
  3. Store nicht erreichbar: Key Vault-Private-Endpoint oder DNS kaputt, ESO kann nicht refreshen. Bestehende Secrets bleiben, neue Namespaces starten nicht. Lösung: Status SecretSynced überwachen und alarmieren.
  4. Zu breite Rechte: Ein ClusterSecretStore mit Zugriff auf alle Secrets, jedes Team kann alles lesen. Lösung: Store pro Namespace oder Team, eigene Identität, eigene Vault-Policy.
  5. Secrets in Logs: Spring loggt Konfiguration oder /actuator/env ist offen. Lösung: Actuator schliessen, Werte maskieren.
  6. Vault sealed nach Neustart: Ohne Auto-Unseal braucht es manuelle Keys. Lösung: Auto-Unseal mit Cloud-KMS, HA mit Raft-Storage.

7. Diagnose: Werkzeuge und Befehle

  • kubectl get externalsecret -A: Spalte STATUS (SecretSynced) und READY.
  • kubectl describe externalsecret database-credentials -n app: Events zeigen 403 vom Key Vault oder fehlende Keys.
  • az keyvault secret show --vault-name my-vault --name database-password --query attributes: Version, aktiv, Ablaufdatum.
  • az role assignment list --assignee <client-id> --scope <vault-id>: Hat die Identität die richtige Rolle?
  • vault token lookup, vault lease lookup <lease_id>, Vault Audit Device: wer hat wann was gelesen?
  • Scanner: gitleaks git über die ganze History, SonarQube Security Hotspots, GitHub Secret Scanning Alerts.

8. Senior-Punkte

  1. Das beste Secret ist keins. Managed Identity und Workload Identity ersetzen Passwörter überall, wo der Zieldienst Entra ID kennt.
  2. Dynamisch vor statisch. Kurzlebige Credentials pro Instanz machen Lecks klein und Audit genau. Preis: Vault muss hochverfügbar sein.
  3. Rotation muss automatisch und geübt sein. Ein Secret, das man nicht ohne Ausfall rotieren kann, ist ein Risiko.
  4. ESO ist ein Kompromiss: einfache Apps, aber das Secret liegt auch in etcd. Darum etcd-Verschlüsselung und enges RBAC.
  5. Scanning in drei Stufen: lokal (Pre-Commit), beim Push (Push Protection), in CI (Pipeline-Gate). Funde einzeln begründen, nie Regeln pauschal abschalten.
  6. Bei einem Leck zählt die Reihenfolge: rotieren, Zugriffe prüfen, dann aufräumen. Nie nur den Commit löschen.

10. Fallen

  • „Kubernetes-Secrets sind verschlüsselt.“ → Falsch. Nur base64. Verschlüsselung at rest muss man für etcd aktivieren.
  • „Wir haben den Commit gelöscht, das Secret ist sicher.“ → Falsch. Es ist kompromittiert. Zuerst rotieren.
  • „ESO aktualisiert das Secret, also hat die App das neue Passwort.“ → Falsch. Env-Variablen ändern sich erst nach Pod-Neustart.
  • „Ein Client Secret für die Managed Identity.“ → Falsch. Managed und Workload Identity brauchen kein Secret.
  • „Rotation heisst: neuen Wert setzen.“ → Unvollständig. Ohne Parallelphase alt + neu fallen Apps aus.

11. Fragen

Was ist Secret Sprawl?

Secrets liegen verstreut in Code, Config, CI, Wikis und Chats. Niemand kennt alle Kopien, darum kann man sie weder prüfen noch rotieren.

Warum gehören Secrets nicht ins Git-Repo?

Git vergisst nichts, und viele Menschen und Systeme haben Lesezugriff. Ein Secret im Repo gilt als kompromittiert.

Sind Kubernetes-Secrets sicher?

Sie sind nur base64-kodiert. Sicher werden sie mit etcd-Verschlüsselung, engem RBAC und Kontrolle darüber, wer Pods starten darf.

Was macht der External Secrets Operator?

Er liest Secrets aus einem externen Store wie Key Vault oder Vault und schreibt sie als Kubernetes-Secret. Er aktualisiert sie im refreshInterval.

SecretStore vs ClusterSecretStore?

Ein SecretStore gilt nur in seinem Namespace. Ein ClusterSecretStore gilt clusterweit. Für Team-Trennung lieber SecretStore pro Namespace.

Was ist Workload Identity in AKS?

Ein Pod tauscht sein ServiceAccount-Token bei Entra ID gegen ein Azure-Token. So greift er ohne Client Secret auf Key Vault zu.

Was sind dynamische Secrets?

Vault erzeugt Credentials bei Bedarf, z. B. einen DB-User, mit einer Lease. Nach Ablauf widerruft Vault sie automatisch.

Was ist eine Lease in Vault?

Die Lebensdauer eines Secrets mit ID. Sie kann verlängert werden bis max_ttl und wird danach widerrufen.

Wie authentifiziert sich ein Pod bei Vault?

Mit der Kubernetes Auth Method: Er schickt sein ServiceAccount-Token, Vault prüft es bei der Kubernetes-API und gibt ein Token mit passender Policy.

Was ist Seal und Unseal in Vault?

Im Zustand sealed kann Vault seine Daten nicht entschlüsseln. Unseal braucht Key-Teile oder Auto-Unseal über ein Cloud-KMS.

Was ist die Transit Engine?

Encryption as a Service. Die App schickt Daten zum Verschlüsseln, der Schlüssel bleibt in Vault.

Was ist Soft-Delete und Purge Protection in Azure Key Vault?

Soft-Delete hält gelöschte Objekte 7–90 Tage wiederherstellbar, Standard 90. Purge Protection verhindert endgültiges Löschen vor Ablauf dieser Frist.

Wie rotiert man ein DB-Passwort ohne Ausfall?

Neues Credential anlegen, beide parallel gültig lassen, Apps umstellen und neu laden, dann das alte widerrufen. Dynamische Secrets machen das automatisch.

Wie bekommt eine App ein rotiertes Secret mit?

Bei Env-Variablen nur durch Pod-Neustart, z. B. per Reloader oder Checksum-Annotation. Bei Datei-Mounts kann die App die Datei neu lesen.

Wie scannen Sie nach Secrets?

Pre-Commit-Hook lokal, Push Protection auf der Plattform, Scan in jeder Pipeline und über die ganze History. Dazu SAST wie SonarQube.

ESO, CSI Driver oder Vault Agent?

ESO für einfache Apps mit Kubernetes-Secrets. CSI Driver, wenn das Secret nicht in etcd soll. Vault Agent für Vault-Features wie Templates und Lease-Erneuerung.

Azure Key Vault oder HashiCorp Vault?

Key Vault für Azure-only, verwaltet und günstig. Vault für Multi-Cloud und dynamische Secrets, aber mit Betriebsaufwand.

Szenario: Ein Entwickler hat einen Storage-Key in ein öffentliches Repo gepusht. Was tun Sie zuerst?

Den Key sofort rotieren, dann Zugriffslogs auf Missbrauch prüfen. Danach History bereinigen, Push Protection und Pre-Commit-Scan einführen, langfristig Managed Identity statt Key.

Szenario: Nach einer Passwort-Rotation im Key Vault scheitern Pods mit Login-Fehlern. Warum?

Das alte Passwort wurde in der DB schon geändert, aber Pods nutzen noch die alte Env. Oder ESO hat noch nicht refresht. Lösung: Parallelphase, Refresh abwarten, Pods neu starten lassen.

Szenario: kubectl get externalsecret zeigt SecretSyncedError. Wie gehen Sie vor?

describe zeigt den Fehler. Häufig: fehlende Rolle auf dem Key Vault, falsche client-id-Annotation, Netzwerk zum Private Endpoint oder falscher Secret-Name. Mit az role assignment list und DNS-Test prüfen.
