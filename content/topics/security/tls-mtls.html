TLS und mTLS

Kern: TLS verschlüsselt eine Verbindung und beweist dem Client, wer der Server ist. Bei mTLS (mutual TLS) beweist auch der Client seine Identität mit einem Zertifikat. So gehört die Identität zur Verbindung und steht nicht als Passwort im Request.

Antwort-Muster

Frage: Was ist mTLS und wann setzen Sie es ein?

  1. Mechanismus: Der Server schickt im Handshake eine CertificateRequest. Der Client antwortet mit Certificate, CertificateVerify und Finished.
  2. Zahl: Bei TLS 1.3 dauert der volle Handshake 1 RTT. Die Client-Zertifikate laufen in derselben Runde mit.
  3. Trade-off: Man bekommt eine starke Identität für Maschinen. Dafür muss man eine CA, Rotation und Sperrung betreiben.
  4. Produktion: Beendet ein Proxy das TLS, sieht die App das Zertifikat nur über Header. Diese Header muss man gegen Fälschung absichern.

1. Der mTLS-Handshake in 7 Schritten

  1. ClientHello: Der Client schickt Versionen, Cipher Suites und seinen key_share.
  2. ServerHello: Der Server wählt Parameter und schickt seinen key_share. Nach dem ServerHello ist jede Handshake-Nachricht verschlüsselt (RFC 8446, 1.2).
  3. CertificateRequest: Der Server schickt EncryptedExtensions und danach die CertificateRequest. Das ist der Moment, in dem aus TLS mTLS wird.
  4. Server-Teil: Der Server schickt sein Certificate, CertificateVerify und Finished.
  5. Server prüfen: Der Client prüft die Kette bis zu einer CA in seinem Truststore. Er prüft auch, ob der Hostname zum Zertifikat passt.
  6. Client-Teil: Der Client schickt sein Certificate. In CertificateVerify beweist er, dass er den privaten Schlüssel hat. Danach folgt Finished.
  7. Client prüfen: Der Server prüft die Kette gegen seinen eigenen Truststore. Passt sie nicht, bricht er mit einem Alert ab. Sonst fliessen die Anwendungsdaten.

Der normale TLS-Handshake steht auf der Seite «TLS-Handshake und Zertifikate». Hier geht es nur um die Client-Seite.

2. Aufbau

  1. Server-Zertifikat: Es beweist dem Client die Identität des Servers. Das ist normales TLS.
  2. Client-Zertifikat: Es beweist dem Server die Identität des Clients. Es braucht einen privaten Schlüssel auf dem Client.
  3. Truststore des Clients: Hier liegen die CAs für Server-Zertifikate. Das sind oft öffentliche CAs.
  4. Truststore des Servers: Hier liegen die CAs für Client-Zertifikate. Das ist oft eine eigene interne CA.
  5. Policy: Der Server entscheidet, ob ein Client-Zertifikat fehlt, erlaubt oder Pflicht ist.
  6. Identität abbilden: Die App liest Subject oder SAN aus dem Zertifikat. Daraus entsteht Name und Rolle des Aufrufers.

3. Details

  1. CertificateRequest: Der Server darf ein Client-Zertifikat anfordern. Die Nachricht muss auf EncryptedExtensions folgen. Sie muss signature_algorithms enthalten. Ein Server mit PSK sendet im Haupt-Handshake keine.
  2. CertificateVerify: Ein Zertifikat ist öffentlich. Darum reicht es nicht. Der Client signiert den Handshake mit dem privaten Schlüssel. So beweist er den Besitz.
  3. Post-handshake authentication: Ein Client kann die Extension post_handshake_auth senden. Dann darf der Server später eine CertificateRequest schicken. So fragt man erst bei einem geschützten Pfad nach dem Zertifikat.
  4. Fehler zeigen sich spät: In TLS 1.3 ist der Handshake aus Sicht des Clients mit seinem Finished fertig. Die Ablehnung des Servers kommt danach. Ein Client sieht den Fehler oft erst beim ersten Lesen.
  5. nginx: Dort ist ssl_verify_client standardmässig off. Es gibt on, optional und optional_no_ca. Die CAs stehen in ssl_client_certificate. ssl_verify_depth ist standardmässig 1.
  6. nginx-Variablen: $ssl_client_verify ist SUCCESS, FAILED:reason oder NONE. $ssl_client_s_dn liefert das Subject. $ssl_client_fingerprint liefert den SHA1-Fingerprint.
  7. Spring Boot: Ein SSL bundle bündelt Keystore und Truststore (spring.ssl.bundle.jks oder .pem). server.ssl.client-auth setzt den Modus und braucht einen Truststore. Mit reload-on-update lädt Tomcat oder Netty neue Dateien. Boot stellt keine Zertifikate aus.
  8. OAuth mit mTLS: RFC 8705 definiert zwei Methoden. tls_client_auth prüft eine Zertifikatskette und ein Subject (DN oder SAN). self_signed_tls_client_auth vergleicht mit registrierten Zertifikaten und prüft keine Kette.
  9. Certificate-bound Token: Das Token enthält cnf mit x5t#S256. Das ist der Base64URL-SHA-256-Hash des DER-Zertifikats. Die API muss das Zertifikat der Verbindung damit vergleichen. Bei Abweichung antwortet sie mit 401 und invalid_token.
  10. Metadaten: Der Server meldet tls_client_certificate_bound_access_tokens. Der Standard ist false. Ein Token kann so an einen Schlüssel gebunden werden. Ein gestohlenes Token ist ohne Schlüssel nutzlos.
  11. TLS am Proxy: RFC 8705 erlaubt, TLS am Load Balancer zu beenden. Wie die Zertifikatsdaten sicher zur App kommen, regelt die RFC nicht. Header vom Proxy muss die App als vertrauenswürdig behandeln und von aussen verwerfen.

4. Fallen

  • „mTLS ersetzt den Login der Benutzer.“ → Falsch. mTLS identifiziert den Client, meist eine Maschine. Benutzer melden sich weiter an.
  • „Ein gültiges Zertifikat heisst, der Client darf alles.“ → Falsch. Das Zertifikat ist nur Authentifizierung. Rechte kommen aus einer Zuordnung von Subject oder SAN zu Rollen.
  • „Jedes Zertifikat einer bekannten CA wird akzeptiert.“ → Falsch. Der Server vertraut nur CAs in seinem eigenen Truststore. Das Zertifikat einer fremden CA wird abgelehnt.
  • „Hinter dem Proxy sieht die App das Client-Zertifikat.“ → Falsch. Nur wenn der Proxy es weitergibt, meist als Header. Ohne Weitergabe sieht die App nichts.
  • „Der Client merkt sofort, dass sein Zertifikat abgelehnt wurde.“ → Falsch. In TLS 1.3 ist der Handshake für den Client früher fertig. Die Ablehnung kommt als Alert danach.
  • „Ein Token mit cnf kann jeder benutzen, der es hat.“ → Falsch. Die API vergleicht den Hash im Token mit dem Zertifikat der Verbindung. Ohne passendes Zertifikat gibt es 401.

5. Selbsttest

Warum?

Warum mTLS statt eines API-Keys?

Ein API-Key ist ein Geheimnis, das man kopieren kann. Bei mTLS bleibt der private Schlüssel beim Client. Er geht nie über das Netz.

Warum braucht man zwei Truststores?

Jede Seite prüft die andere. Der Client prüft den Server gegen seine CAs. Der Server prüft den Client gegen seine CAs.

Warum bindet man Tokens an ein Zertifikat?

Ein gestohlenes Bearer Token wäre sonst überall nutzbar. Mit cnf braucht der Dieb auch den privaten Schlüssel.

Wie innen?

Wie läuft ein mTLS-Handshake ab?

ClientHello, ServerHello, EncryptedExtensions, CertificateRequest, Server-Certificate mit Verify und Finished. Dann Client-Certificate mit Verify und Finished.

Was macht die CertificateRequest?

Der Server verlangt damit ein Client-Zertifikat. Sie folgt auf EncryptedExtensions und nennt die akzeptierten Signaturalgorithmen.

Was beweist CertificateVerify?

Dass der Absender den privaten Schlüssel zum Zertifikat besitzt. Er signiert damit den Handshake.

Was ist Post-handshake authentication?

Der Server fragt erst nach dem Handshake nach einem Zertifikat. Der Client muss vorher post_handshake_auth angeboten haben.

Wie funktioniert die Bindung nach RFC 8705?

Das Token enthält den SHA-256-Hash des Client-Zertifikats als cnf / x5t#S256. Die API vergleicht ihn mit dem Zertifikat der Verbindung.

Zahlen

Wie viele RTT braucht der volle TLS-1.3-Handshake?

1 RTT. Der Client schickt sein Zertifikat in seiner Antwort auf den Server-Teil.

Was ist in nginx der Standard von ssl_verify_client?

off. Es werden dann keine Client-Zertifikate geprüft.

Was ist der Standard von ssl_verify_depth?

1. Eine Kette mit einer Zwischen-CA braucht oft einen höheren Wert.

Was ist x5t#S256?

Der Base64URL-kodierte SHA-256-Hash der DER-Kodierung des Zertifikats, ohne Padding.

Vergleich

TLS oder mTLS?

TLS authentifiziert nur den Server. mTLS authentifiziert beide Seiten.

mTLS oder JWT?

mTLS beweist die Identität der Verbindung. Ein JWT trägt Claims und Rechte. Man kombiniert sie mit gebundenen Tokens.

tls_client_auth oder self_signed_tls_client_auth?

Die erste prüft eine Kette gegen eine CA. Die zweite vergleicht mit vorab registrierten Zertifikaten und prüft keine Kette.

TLS am Proxy beenden oder durchreichen?

Am Proxy ist einfacher und erlaubt Routing. Die App sieht dann das Zertifikat nur als Header. Durchreichen hält die Prüfung in der App.

Produktion

Wie sieht man in nginx den Grund einer Ablehnung?

In $ssl_client_verify. Der Wert ist FAILED:reason und nennt den Grund.

Wie rotiert man Zertifikate ohne Ausfall?

Neue Zertifikate früh ausstellen und Dateien ersetzen. Mit reload-on-update lädt Spring Boot sie ohne Neustart.

Szenario: Um 03:00 Uhr schlagen alle Aufrufe zwischen zwei Services fehl. Was prüfen Sie zuerst?

Das Ablaufdatum der Client- und Server-Zertifikate. Abgelaufene Zertifikate sind die häufigste Ursache. Lösung: automatische Erneuerung und eine Warnung vor dem Ablauf.

Szenario: nginx lehnt Clients mit gültigem Zertifikat ab. Die Kette hat eine Zwischen-CA. Warum?

Wahrscheinlich ist ssl_verify_depth mit 1 zu klein. Auch die Zwischen-CA muss im CA-File oder in der Kette sein.

Szenario: Ein Angreifer schickt selbst einen Header mit einem fremden Subject. Was ist falsch?

Die App vertraut einem Header, den der Proxy nicht überschreibt. Lösung: Der Proxy setzt den Header immer selbst und entfernt eingehende Kopien.

Design

Wie bildet man aus dem Zertifikat eine Identität ab?

Über SAN oder Subject. Die App ordnet sie einem Namen und Rollen zu. Die Zuordnung liegt in einer festen Liste, nicht im Zertifikat.

Wie aktiviert man mTLS in Spring Boot?

Ein SSL bundle mit Keystore und Truststore anlegen. Es mit server.ssl.bundle setzen und server.ssl.client-auth wählen.

Szenario: Ein Partner soll Ihre API per mTLS nutzen. Welche CA nehmen Sie?

Eine eigene CA nur für Clients. Jeder Partner bekommt ein Zertifikat. So kann man ein Zertifikat sperren, ohne öffentliche CAs zu vertrauen.

Wie schützt man Tokens zusätzlich?

Mit zertifikatsgebundenen Access Tokens nach RFC 8705. Der Authorization Server stellt sie aus und die API prüft den Hash.

Mehr

Gerüst

  • Warum? Die Identität des Clients gehört zur Verbindung und nicht in ein Geheimnis im Request.
  • Wie innen? CertificateRequest, Client-Certificate, CertificateVerify, Finished. Der Server prüft gegen seinen Truststore.
  • Zahlen 1 RTT. ssl_verify_client standardmässig off. ssl_verify_depth 1. x5t#S256 ist SHA-256.
  • Vergleich TLS gegen mTLS. API-Key gegen Zertifikat. tls_client_auth gegen self_signed_tls_client_auth.
  • Produktion Zertifikat abgelaufen. Zu kleine Verify-Tiefe. Header-Fälschung hinter dem Proxy.
  • Design Eigene Client-CA. Rotation automatisieren. Rechte per Mapping. Tokens an Zertifikate binden.

Beispiel: Ein mTLS-Server mit drei Clients

// Server (Node): Client-Zertifikat Pflicht, nur TLS 1.3
const server = tls.createServer({
  key, cert, ca: demoCA,          // ca = Truststore für Clients
  requestCert: true,
  rejectUnauthorized: true,
  minVersion: 'TLSv1.3'
}, s => {
  const c = s.getPeerCertificate();
  s.end(`hello ${c.subject.CN}, issuer ${c.issuer.CN}`);
});
// Clients: 1) ohne Zertifikat  2) Zertifikat der Demo CA
//          3) Zertifikat einer fremden CA ("Evil CA")
// Hash fürs Token (cnf / x5t#S256)
sha256(DER des Client-Zertifikats) -> base64url
   server log: ERR_SSL_PEER_DID_NOT_RETURN_A_CERTIFICATE
1 no client cert    -> FAILED ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED
2 cert from Demo CA -> hello billing-service, issuer Demo CA
   server log: ECONNRESET
3 cert from Evil CA -> FAILED (closed)
x5t#S256 of client cert: DfIuTN5KXaKrgEDN36ccjgXbfyZ0q2JB1Ee3L-AB-Lc

Echte Ausgabe, Node v24.20.0 und OpenSSL 3.5.9. Die Zertifikate stammen aus einer Demo-CA, die mit openssl erzeugt wurde. Den Hash hat openssl mit dem gleichen Ergebnis berechnet.

  1. Fall 1: Ohne Zertifikat bricht der Server ab. Der Client bekommt den Alert certificate_required.
  2. Fall 2: Das Zertifikat der Demo CA wird akzeptiert. Der Server liest daraus den Namen billing-service.
  3. Fall 3: Das Zertifikat einer fremden CA wird abgelehnt. Der Client sieht nur eine geschlossene Verbindung und keinen Grund.
  4. Hash: Das ist der Wert, der im Token unter cnf / x5t#S256 stehen würde.

Vergleich

  • TLS: Nur der Server hat ein Zertifikat. Der Client bleibt anonym oder meldet sich mit Passwort oder Token.
  • mTLS: Beide Seiten haben Zertifikate. Gut für Service-zu-Service und Partner-APIs.
  • API-Key: Ein kopierbares Geheimnis. Einfach, aber leicht zu stehlen und zu teilen.
  • JWT Bearer Token: Ein Token mit Claims. Ohne Bindung gilt es für jeden, der es besitzt.
  • Zertifikatsgebundenes Token: Ein Token plus Hash des Zertifikats. Es gilt nur mit dem passenden Schlüssel.
  • Service Mesh: Ein Mesh kann mTLS zwischen Services automatisch einrichten. Die Prinzipien oben bleiben gleich.

Produktion

  1. Zertifikat abgelaufen: Ein Ablauf legt Verbindungen sofort lahm. Lösung: automatische Erneuerung und eine Warnung lange vor dem Ablauf.
  2. Zu kleine Verify-Tiefe: Bei Zwischen-CAs scheitert die Prüfung. Lösung: ssl_verify_depth erhöhen und die Kette prüfen.
  3. Header-Fälschung: Die App glaubt einem Subject-Header. Lösung: Der Proxy überschreibt den Header und die App akzeptiert ihn nur vom Proxy.
  4. Private Schlüssel im Repository: Schlüssel gehören in einen Vault oder ein Secret. Lösung: Schlüssel rotieren, wenn einer einmal im Repository lag.
  5. Sperrung fehlt: Ein gestohlenes Zertifikat gilt bis zum Ablauf. Lösung: kurze Laufzeiten und eine Sperrliste der Client-CA.
  6. Verwirrende Fehler: Der Client sieht oft nur «closed». Lösung: Server-Logs und $ssl_client_verify lesen.

Diagnose: Werkzeuge und Befehle

  • openssl s_client: openssl s_client -connect host:443 -cert client.crt -key client.key -CAfile ca.crt testet einen mTLS-Aufruf und zeigt die Kette.
  • Zertifikat lesen: openssl x509 -in client.crt -noout -subject -issuer -dates -ext subjectAltName zeigt Subject, Aussteller, Laufzeit und SAN.
  • Hash berechnen: openssl x509 -in client.crt -outform DER | openssl dgst -sha256 -binary liefert den Hash für x5t#S256 (danach Base64URL).
  • nginx: Die Variable $ssl_client_verify im Log zeigt SUCCESS oder den Fehlergrund.
  • Wireshark: In TLS 1.3 sind Zertifikate verschlüsselt. Man sieht Alerts und den Zeitpunkt des Abbruchs.

Senior-Punkte

  1. mTLS löst Identität, nicht Rechte.: Authentifizierung und Autorisierung bleiben getrennt. Das Subject wird auf Rollen abgebildet.
  2. Der Betrieb der CA ist der Preis.: Ausstellung, Rotation und Sperrung müssen automatisch laufen. Sonst fällt das System beim ersten Ablauf aus.
  3. Kurze Laufzeiten sind sicherer.: Ein gestohlener Schlüssel gilt dann nur kurz. Das setzt Automatisierung voraus.
  4. Wo endet TLS?: Das ist eine Architekturfrage. Jeder Hop mit eigener TLS-Strecke braucht eine eigene Vertrauensentscheidung.
  5. Bindung statt Hoffnung.: Zertifikatsgebundene Tokens machen ein gestohlenes Token wertlos. Sie sind die Ergänzung, die oft fehlt.
  6. Fehler müssen sichtbar sein.: Ein Client sieht bei mTLS oft keinen Grund. Gute Server-Logs sparen Stunden.
