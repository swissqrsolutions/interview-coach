CAP, PACELC, Konsistenzmodelle

System Design · Tier 1 · Quellen: Gilbert und Lynch, „Brewer’s Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services“ (2002), Brewer, „CAP Twelve Years Later“ (IEEE Computer 2012), Abadi, „Consistency Tradeoffs in Modern Distributed Database System Design“ (IEEE Computer 2012), Kleppmann, DDIA (Kap. 5 und 9), Microsoft Learn (Azure Cosmos DB: Consistency levels), Apache Cassandra Doku (Consistency levels)

Kern: CAP ist ein Satz über verteilte Systeme: Bei einer Netzwerk-Partition muss ein System wählen zwischen Konsistenz (jeder Read sieht den neuesten Write) und Verfügbarkeit (jeder Knoten antwortet). PACELC ergänzt: Auch ohne Partition gibt es einen Tausch zwischen Latenz und Konsistenz. Konsistenzmodelle beschreiben genau, was ein Read sehen darf.

1. Wo sitzt CAP?

  1. Zwei Knoten halten Kopien von x. Sie tauschen Writes über das Netz aus.
  2. Partition: Das Netz zwischen den Knoten fällt aus. Beide laufen weiter, sehen sich aber nicht.
  3. Client A schreibt x = 2 auf Knoten 1. Knoten 2 erfährt davon nichts.
  4. Client B liest x auf Knoten 2. Jetzt muss das System wählen.
  5. CP: Knoten 2 antwortet mit Fehler. AP: Knoten 2 antwortet mit dem alten Wert. Beides zugleich geht nicht. Das ist der ganze Satz.

2. Die Reise eines Quorum-Writes und -Reads (die Geschichte zum Merken)

  1. Writer schickt an alle N Replicas. Hier ist N = 3, der Replikationsfaktor. Der Wert trägt eine Version.
  2. W Bestätigungen reichen. Mit W = 2 ist der Write erfolgreich nach zwei Acks. Replica 3 verpasst ihn, z. B. wegen kurzer Störung.
  3. Kein Rollback. Erreicht ein Write weniger als W Replicas, meldet er Fehler. Die Replicas, die ihn schon haben, behalten ihn aber.
  4. Reader fragt R Replicas. Mit R = 2 fragt er z. B. Replica 2 und 3.
  5. Neueste Version gewinnt. Weil R + W > N, ist mindestens eine gefragte Replica beim Write dabei gewesen. Der Reader sieht v2.
  6. Read Repair. Der Reader schreibt v2 zurück an Replica 3. Im Hintergrund gleicht Anti-Entropy (Vergleich mit Merkle Trees) weitere Unterschiede aus.

3. Beispiel: Quorum N/R/W simulieren

N = 3
def trial(R, W, down=0):
    replicas = [{"v": 1, "val": "old"} for _ in range(N)]
    alive = list(range(N - down))
    if len(alive) < W: return "write_fail"
    for i in random.sample(alive, W): replicas[i] = {"v": 2, "val": "new"}
    if len(alive) < R: return "read_fail"
    answers = [replicas[i] for i in random.sample(alive, R)]
    return max(answers, key=lambda a: a["v"])["val"]     # neueste Version gewinnt
# je 10000 Write+Read-Paare, einmal alle Knoten da, einmal 1 Knoten down

Echte Ausgabe, Python 3 (Simulation, random.seed(42)). Kein echtes Cassandra; die Zahlen zeigen das Prinzip.

  1. R = 1, W = 1: Read und Write überlappen oft nicht. Zwei Drittel der Reads sind veraltet (stale).
  2. R = 1, W = 2: Ein Drittel ist noch stale. Mit einem Knoten weniger sind es zufällig 0, weil beide lebenden Knoten den Write haben.
  3. R = 2, W = 2: R + W > N, kein stale Read. Ein Knoten darf ausfallen, alles läuft weiter. Das ist die übliche Wahl.
  4. W = 3 oder R = 3: auch keine stale Reads. Aber ein toter Knoten macht jeden Write bzw. Read unmöglich. Mehr Konsistenz kostet hier Verfügbarkeit.

4. Details, die Interviewer fragen

  1. CAP korrekt: Gilbert und Lynch beweisen: Bei einer Partition kann kein System zugleich linearizable und available sein. Available heisst dort: Jeder nicht ausgefallene Knoten antwortet ohne Fehler.
  2. „2 von 3 wählen“ ist falsch: Partitionen passieren einfach. P ist keine Option. Die Wahl C oder A gilt nur während einer Partition.
  3. CA: CA heisst nur „keine Partitionen möglich“, z. B. ein einzelner Knoten. Ein verteiltes System kann nicht CA sein.
  4. Brewer 2012: Brewer selbst betont: Partitionen sind selten. Die Wahl ist fein, z. B. pro Operation. Nach der Partition braucht es Recovery, also das Zusammenführen.
  5. PACELC: If Partition: A or C. Else: L or C. Auch im Normalbetrieb kostet Konsistenz Latenz, weil auf Replicas gewartet wird. Das betrifft das System die ganze Zeit, nicht nur bei Ausfällen.
  6. PACELC-Beispiele nach Abadi: Dynamo und Cassandra sind PA/EL. VoltDB und Megastore sind PC/EC. PNUTS ist PC/EL. Das hängt aber von der Konfiguration ab.
  7. Linearizability (strong): Jede Operation wirkt, als liefe sie atomar zu einem Zeitpunkt zwischen Start und Ende. Nach einem bestätigten Write sieht jeder Read den neuen Wert.
  8. Serializability ≠ Linearizability: Serializability ist Isolation von Transaktionen: Ergebnis wie nacheinander. Linearizability ist Aktualität eines einzelnen Objekts. Beides zusammen heisst strict serializability.
  9. Causal Consistency: Was kausal zusammenhängt, sieht jeder in derselben Reihenfolge. Eine Antwort erscheint nie vor ihrer Frage. Das ist das stärkste Modell, das auch bei Partition verfügbar bleibt.
  10. Read-your-writes: Ein Client sieht immer seine eigenen Writes. Andere Clients dürfen später sehen.
  11. Monotonic Reads: Ein Client sieht nie einen älteren Stand als zuvor.
  12. Consistent Prefix: Writes erscheinen in der Reihenfolge, in der sie passiert sind. Man sieht keine Lücken in der Mitte.
  13. Eventual Consistency: Ohne neue Writes werden alle Replicas irgendwann gleich. Wie lange das dauert, sagt das Modell nicht.
  14. Cosmos DB: Cosmos DB bietet fünf Stufen: Strong, Bounded Staleness, Session, Consistent Prefix, Eventual. Standard ist Session, also Read-your-writes pro Session-Token.
  15. Grenzen von Quorum: Auch mit R + W > N gibt es Randfälle. Sloppy Quorum mit Hinted Handoff schreibt auf Ersatzknoten. Gleichzeitige Writes mit Last-Write-Wins verlieren Daten. Uhren-Abweichung verfälscht LWW.
  16. Idempotenz: Eine Operation ist idempotent, wenn mehrfaches Ausführen das gleiche Ergebnis hat wie einmaliges. Wichtig, weil Retries nach Timeout normal sind. Ein Timeout sagt nicht, ob der Write passiert ist.
  17. Idempotency Key: Der Client schickt eine eindeutige ID pro Vorgang. Der Server speichert sie mit dem Ergebnis. Ein Retry mit gleicher ID liefert das alte Ergebnis statt einer neuen Buchung.
  18. Optimistic Concurrency: Ein Write gilt nur, wenn die Version noch stimmt, z. B. mit ETag und If-Match. Sonst kommt ein Konflikt (HTTP 412) und der Client liest neu.

5. Vergleich

  • Strong (Linearizable): immer neuester Wert. Kostet Latenz und bei Partition Verfügbarkeit. Beispiele: etcd, ZooKeeper-Writes, Spanner, Cosmos DB Strong.
  • Bounded Staleness: höchstens K Versionen oder T Sekunden alt.
  • Causal: Ursache vor Wirkung, sonst frei. Bleibt bei Partition verfügbar.
  • Session / Read-your-writes: eigene Writes sofort sichtbar, fremde später. Guter Standard für Nutzer-Apps.
  • Consistent Prefix: richtige Reihenfolge, aber eventuell veraltet.
  • Eventual: irgendwann gleich. Schnellste Reads, schwächste Garantie.
  • CP-Systeme (etcd, ZooKeeper, HBase): Fehler bei Partition auf der Minderheitsseite. AP-Systeme (Cassandra, DynamoDB im Standard): antworten immer, eventuell veraltet.

6. In der Produktion

  1. Doppelte Zahlung nach Retry: Der erste Request lief durch, die Antwort ging verloren. Der Retry bucht nochmals. Lösung: Idempotency Key mit Unique Constraint.
  2. Lost Update durch Last-Write-Wins: Zwei Clients schreiben gleichzeitig, einer gewinnt still. Lösung: Versionen, Compare-and-Set, ETag mit If-Match.
  3. Cassandra mit ONE für alles: Reads sind oft veraltet. Lösung: LOCAL_QUORUM für Reads und Writes bei RF = 3.
  4. Strong Consistency über Regionen: Jeder Write wartet auf eine andere Region, also viele Millisekunden. Lösung: Strong nur, wo nötig. Sonst Session oder Bounded Staleness.
  5. Cosmos DB Session ohne Token: Mehrere Instanzen teilen eine Nutzer-Session, aber nicht den Session-Token. Read-your-writes bricht. Lösung: Session-Token mitgeben oder Sticky Routing.
  6. Uhren-Abweichung: LWW mit Zeitstempeln verwirft neuere Writes eines Knotens mit nachgehender Uhr. Lösung: logische Versionen statt Wanduhr.

7. Diagnose: Werkzeuge und Befehle

  • Cassandra: CONSISTENCY LOCAL_QUORUM; und TRACING ON; in cqlsh zeigen, welche Replicas antworten. nodetool repair gleicht Replicas ab.
  • Cosmos DB: Antwort-Header x-ms-session-token zeigt den Session-Stand. Azure Monitor zeigt Replication Latency zwischen Regionen.
  • PostgreSQL: replay_lag in pg_stat_replication zeigt, wie veraltet Replica-Reads sind.
  • Jepsen: Testwerkzeug, das Partitionen erzeugt und Konsistenz-Verletzungen findet. Die Berichte zeigen, was Datenbanken wirklich garantieren.
  • Metriken: Anteil Retries, doppelte Idempotency Keys, 409/412-Konflikte. Sie zeigen, wie oft Konsistenz-Mechanismen greifen.

8. Senior-Punkte

  1. CAP ist zu grob für Designs. PACELC und konkrete Konsistenzmodelle sind die bessere Sprache. „Welche Garantie braucht diese Operation?“
  2. Konsistenz pro Operation wählen. Kontostand: strong. Like-Zähler: eventual. Profil des Nutzers: read-your-writes.
  3. Timeouts sind unklar. Jede Operation über das Netz braucht einen sicheren Retry. Darum Idempotenz von Anfang an.
  4. Konflikte gezielt lösen, nicht still mit Last-Write-Wins. Versionen oder CRDTs machen Konflikte sichtbar.
  5. Strong Consistency über Regionen kostet immer eine Round-Trip-Zeit. Das ist Physik, keine Konfiguration.
  6. „Eventual“ braucht eine Zahl. Im Betrieb misst man den Lag und setzt ein Ziel, z. B. p99 unter 1 Sekunde.

10. Fallen

  • „CAP heisst: Wähle 2 von 3.“ → Falsch. Partitionen passieren. Die Wahl ist C oder A, und nur während einer Partition.
  • „Unser System ist CA.“ → Falsch für verteilte Systeme. CA gibt es nur ohne Netz zwischen Knoten.
  • „C in CAP ist das C in ACID.“ → Falsch. CAP-C ist Linearizability. ACID-C sind Invarianten.
  • „R + W > N garantiert Linearizability.“ → Falsch. Sloppy Quorum, LWW und unvollständige Writes brechen das.
  • „Eventual consistency heisst: bald konsistent.“ → Falsch. Es gibt keine Zeitgrenze im Modell.
  • „Exactly-once Delivery löst das.“ → Falsch. Über ein Netz gibt es höchstens exactly-once Processing durch Idempotenz.

11. Fragen

Was sagt das CAP-Theorem?

Bei einer Netzwerk-Partition kann ein verteiltes System nicht zugleich konsistent (linearizable) und verfügbar sein. Es muss eines opfern.

Was bedeutet Consistency in CAP genau?

Linearizability: Jeder Read sieht den neuesten bestätigten Write, als gäbe es nur eine Kopie.

Was bedeutet Availability in CAP genau?

Jeder Request an einen nicht ausgefallenen Knoten bekommt eine Antwort ohne Fehler. Es gibt keine Zeitgrenze, aber auch kein „später“.

Warum ist „wähle 2 von 3“ falsch?

Partitionen kann man nicht abwählen. Die echte Wahl ist C oder A, und nur während einer Partition.

Gibt es CA-Systeme?

Nur ohne Partitionen, also praktisch ein einzelner Knoten. Ein verteiltes System muss sich bei Partition entscheiden.

Was ist PACELC?

Bei Partition: Availability oder Consistency. Sonst: Latency oder Consistency. Es zeigt den Preis von Konsistenz im Normalbetrieb.

Nennen Sie ein PA/EL- und ein PC/EC-System.

PA/EL: Cassandra, Dynamo. PC/EC: VoltDB, Megastore, Spanner. Je nach Konfiguration.

Was ist Linearizability?

Jede Operation wirkt atomar zu einem Zeitpunkt. Nach einem bestätigten Write sehen alle den neuen Wert.

Linearizability vs Serializability?

Linearizability: Aktualität eines Objekts. Serializability: Transaktionen wirken wie nacheinander, egal wie aktuell. Beides zusammen: strict serializability.

Was ist Eventual Consistency?

Ohne neue Writes werden alle Replicas irgendwann gleich. Keine Garantie, wann.

Was ist Read-your-writes?

Ein Client sieht seine eigenen Writes immer sofort. Typisch umgesetzt mit Lesen vom Leader oder Session-Token.

Was ist Causal Consistency?

Kausal abhängige Operationen sieht jeder in der gleichen Reihenfolge. Unabhängige dürfen verschieden erscheinen.

Was sind Monotonic Reads?

Ein Client sieht nie einen älteren Stand als vorher. Lösung: Client an eine Replica binden.

Welche Konsistenzstufen hat Cosmos DB?

Strong, Bounded Staleness, Session, Consistent Prefix, Eventual. Standard ist Session.

Was bedeuten N, R und W?

N ist die Anzahl Replicas. W ist die Anzahl Acks für einen Write. R ist die Anzahl Replicas, die ein Read fragt.

Warum R + W > N?

Dann überlappen Read- und Write-Menge in mindestens einer Replica. Der Read sieht den neuesten Write.

Welche Werte für N, R, W bei 3 Replicas?

Meist R = W = 2 (Quorum). Ein Knoten darf ausfallen, Reads sind aktuell.

Was ist ein Sloppy Quorum?

Fallen Stamm-Replicas aus, schreibt man auf Ersatzknoten. Hinted Handoff bringt die Daten später zurück. Erhöht Verfügbarkeit, bricht die Quorum-Garantie.

Was ist Read Repair?

Ein Read findet veraltete Replicas und schreibt den neuesten Wert zurück.

Was ist Last-Write-Wins und das Problem damit?

Der Write mit dem grössten Zeitstempel gewinnt. Gleichzeitige Writes gehen still verloren, Uhren-Abweichung verfälscht das Ergebnis.

Was ist Idempotenz?

Mehrfaches Ausführen hat das gleiche Ergebnis wie einmaliges. Nötig, weil Retries nach Timeout normal sind.

Wie bauen Sie einen idempotenten POST?

Client sendet Idempotency Key. Server speichert Key und Ergebnis mit Unique Constraint in der gleichen Transaktion. Ein Retry bekommt das gespeicherte Ergebnis.

Was ist Optimistic Concurrency?

Ein Write gilt nur, wenn die gelesene Version noch aktuell ist, z. B. ETag mit If-Match. Sonst Konflikt und neu lesen.

Szenario: Ein Kunde wurde nach einem Timeout doppelt belastet. Was ändern Sie?

Idempotency Key pro Zahlung, vom Client erzeugt. Server prüft per Unique Constraint und liefert beim Retry das alte Ergebnis. Auch der Zahlungsanbieter bekommt den Key.

Szenario: Ein globaler Like-Zähler und ein Kontostand im gleichen System. Welche Konsistenz?

Like-Zähler: eventual, schnell, z. B. CRDT-Counter. Kontostand: strong in einer Region mit Transaktion. Konsistenz pro Daten wählen.

Szenario: Cassandra mit RF = 3 liefert manchmal alte Werte. Woran liegt es?

Vermutlich Reads oder Writes mit ONE, also R + W ≤ N. Lösung: LOCAL_QUORUM für beide. Danach regelmässig nodetool repair laufen lassen.
