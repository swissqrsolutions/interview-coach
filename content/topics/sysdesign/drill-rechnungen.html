Drill 4: Monats-Rechnungen (Batch, Worker, idempotent)

1. Die Aufgabe

So stellt sie der Interviewer: „Ein Telekom-Anbieter hat 200'000 Kunden. Am 1. jedes Monats müssen für alle Kunden PDF-Rechnungen erzeugt und per E-Mail verschickt werden. Eine Rechnung braucht etwa 500 ms Rechenzeit (Positionen laden, PDF rendern). Der Mail-Provider erlaubt 100 Mails/s. Der Lauf muss bis 6:00 Uhr morgens fertig sein — und wenn um 3 Uhr ein Server abstürzt, darf keine Rechnung fehlen und keine doppelt verschickt werden."

20 Minuten: Stell die Uhr. Löse laut: Rückfragen, Durchsatzrechnung, Job-Tabelle, Worker-Schleife, Wiederanlauf. Dann erst vergleichen.

2. Schritt 1: Verstehen

Die Rückfragen — mit plausiblen Antworten:

  1. „Start 0:00, fertig 6:00 — sind die 6 Stunden hart?" → „Ja, um 6:00 schauen die ersten Kunden ins Postfach." Also plane ich mit Reserve: Ziel 2–3 h.
  2. „Doppelt schlimmer als fehlend, oder umgekehrt?" → „Doppelte Mail ist peinlich, doppelte Rechnung mit neuer Nummer ist ein Buchhaltungsfehler." ⇒ Rechnungsnummer muss deterministisch sein, Versand at-least-once mit Dedup.
  3. „Ändern sich Rechnungsdaten während des Laufs?" → „Nein, Abrechnungsperiode ist beim Start abgeschlossen." Gut: der Lauf arbeitet auf einem festen Schnappschuss.
  4. „Müssen die PDFs aufbewahrt werden?" → „Ja, 10 Jahre, Kunde kann sie im Portal abrufen." ⇒ Object Storage, nicht DB.
  5. „Gibt es Kunden ohne E-Mail?" → „5 % bekommen Brief." ⇒ Kanal ist ein Feld, Briefdruck ist ein zweiter Konsument desselben Laufs.
  6. „Was darf eine fehlerhafte Rechnung blockieren?" → „Nur sich selbst." ⇒ Fehler isolieren, Lauf läuft weiter, Fehlerliste am Ende.

Zahlenschätzung (laut rechnen): 200'000 × 0,5 s = 100'000 s Rechenzeit ≈ 28 h sequentiell ⇒ parallelisieren ist Pflicht. Mit 20 Workern: 100'000/20 = 5'000 s ≈ 84 min — passt ins Fenster. Mail-Limit: 200'000 / 100 pro s = 2'000 s ≈ 34 min reine Sendezeit, läuft parallel zum Erzeugen. Speicher: 200'000 PDFs × 100 KB = 20 GB/Monat, 10 Jahre ≈ 2,4 TB ⇒ Blob mit Lifecycle in kalte Stufe.

3. Anforderungen

Muss:

  • Jeder Kunde genau eine Rechnung pro Monat — auch nach Crash und Neustart.
  • Keine doppelte Rechnungsnummer, kein doppelter Versand.
  • Fertig bis 6:00; Fortschritt jederzeit abfragbar („wie viele offen/fertig/fehler?").
  • Einzelfehler (kaputte Stammdaten) stoppen den Lauf nicht.
  • PDFs 10 Jahre abrufbar, unveränderlich.

Kann:

  • Wiederholungslauf nur für Fehler-Fälle per Knopfdruck.
  • Vorschau-Lauf („dry run") ohne Versand.
  • Verteilen des Versands über den Vormittag (Lastglättung beim Support).
  • Briefdruck-Export als zweiter Kanal.

4. DB-Design

CREATE TABLE rechnungslauf (
  lauf_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  periode     date NOT NULL UNIQUE,     -- '2026-11-01': ein Lauf pro Monat
  gestartet   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE rechnungsjob (
  lauf_id      bigint NOT NULL REFERENCES rechnungslauf,
  kunde_id     bigint NOT NULL,
  status       text NOT NULL DEFAULT 'offen'
               CHECK (status IN ('offen','in_arbeit','fertig','fehler')),
  versuche     int NOT NULL DEFAULT 0,
  gestartet_am timestamptz,             -- fuer haengende Jobs (Timeout)
  fehler_text  text,
  pdf_url      text,
  PRIMARY KEY (lauf_id, kunde_id)       -- Idempotenz: 1 Job pro Kunde+Monat
);
-- DER Index der Aufgabe: Worker greifen sich offene Jobs
CREATE INDEX idx_job_offen ON rechnungsjob (lauf_id, status)
  WHERE status IN ('offen','in_arbeit');

CREATE TABLE rechnung (
  rechnung_id  text PRIMARY KEY,        -- deterministisch: 'R-2026-11-'
  kunde_id     bigint NOT NULL,
  periode      date NOT NULL,
  betrag       numeric(12,2) NOT NULL,
  pdf_url      text NOT NULL,
  versendet_am timestamptz,
  UNIQUE (kunde_id, periode)            -- zweites Netz gegen Doppel-Rechnung
);
  • rechnungslauf: Klammer um einen Monat; UNIQUE(periode) macht den Start-Knopf idempotent — zweimal drücken erzeugt keinen zweiten Lauf.
  • rechnungsjob: die Status-Maschine, eine Zeile pro Kunde; der Primärschlüssel (lauf_id, kunde_id) erzwingt „genau ein Job pro Kunde und Monat". Die Status-Spalte plus idx_job_offen ist die Arbeitsvorrat-Queue.
  • rechnung: das Ergebnis; die deterministische rechnung_id aus Periode + Kunde macht Wiederholungen harmlos — derselbe Kunde kann im selben Monat keine zweite Nummer bekommen.

5. API

  • POST /laeufe — Body {periode}; legt Lauf + 200'000 Jobs an (ein INSERT … SELECT aus der Kundentabelle); 409 bei existierender Periode.
  • GET /laeufe/{id} — Fortschritt: {offen, in_arbeit, fertig, fehler} (ein GROUP BY status).
  • GET /laeufe/{id}/fehler — Fehlerliste mit fehler_text für den Fachbereich.
  • POST /laeufe/{id}/retry — setzt alle fehler-Jobs zurück auf offen.
  • GET /kunden/{id}/rechnungen — Portal-Abruf; liefert kurzlebige signierte Blob-URL.
  • Kein öffentlicher Endpunkt für Worker: sie reden direkt mit der DB.

6. Pseudo-Code an der Tafel

// Worker-Schleife — laeuft identisch auf 20 Instanzen
solange lauf nicht fertig:

  BEGIN TRANSACTION
    // 1) Batch greifen: SKIP LOCKED = jeder Worker bekommt ANDERE Zeilen,
    //    niemand wartet auf fremde Locks
    jobs = SELECT * FROM rechnungsjob
           WHERE lauf_id = :lauf AND status = 'offen'
           LIMIT 100
           FOR UPDATE SKIP LOCKED
    wenn jobs leer: pause(5s); weiter      // fertig oder alles vergriffen

    UPDATE … SET status='in_arbeit', gestartet_am=now(),
                 versuche=versuche+1  WHERE (lauf_id,kunde_id) IN jobs
  COMMIT                                   // Claim sichtbar, Locks frei

  fuer job in jobs:
    versuche:
      rid = "R-" + periode + "-" + job.kunde_id   // 2) deterministisch!
      pdf = renderePdf(job.kunde_id, periode)
      blob.schreibe("rechnungen/" + rid + ".pdf", pdf)  // Overwrite = ok
      INSERT INTO rechnung (rechnung_id, …) VALUES (rid, …)
        ON CONFLICT (rechnung_id) DO NOTHING          // Retry = harmlos
      mailQueue.sende(rid)                 // Versand entkoppelt, 100/s
      UPDATE rechnungsjob SET status='fertig' WHERE …
    bei fehler e:
      // 3) Fehler isolieren: nur dieser Job, Lauf laeuft weiter
      UPDATE rechnungsjob SET status='fehler', fehler_text=e WHERE …

// Aufraeumer (alle 5 min): Crash-Opfer zurueck in den Vorrat
UPDATE rechnungsjob SET status='offen'
WHERE status='in_arbeit' AND gestartet_am < now() - interval '10 min';

7. Architektur

Sprich das Bild so: „Die DB ist die Queue: die Job-Tabelle ist der Arbeitsvorrat, SKIP LOCKED verteilt ihn kollisionsfrei auf 20 Worker. PDFs gehen in Blob, der Versand ist eine echte Queue mit Rate-Limit — damit der Mail-Provider das Tempo bestimmt, nicht wir."

8. Der schwierige Teil als Bild

Der Mechanismus in einem Satz: Jeder Job ist immer in genau einem Zustand, jeder Übergang ist ein atomares UPDATE — darum kann der Lauf nach jedem Crash einfach weitermachen: offen wird gearbeitet, hängendes in_arbeit fällt per Timeout zurück, fertig wird nie wieder angefasst.

9. Frontend kurz

  • Komponenten: LaufUebersichtComponent (Fortschrittsbalken aus GROUP BY status), FehlerListeComponent, RetryButtonComponent.
  • State: LaufService pollt GET /laeufe/{id} alle 10 s — kein WebSocket nötig für ein Admin-Tool.
  • Kundenportal: RechnungslisteComponent lädt signierte Blob-URLs, PDF öffnet direkt aus Blob.

10. Cloud (Azure)

  • Azure Functions (Timer-Trigger) als Scheduler: eine Funktion am 1. um 0:00, legt Lauf + Jobs an — kein eigener Cron-Server.
  • Container Apps oder AKS-Jobs für die 20 Worker: laufen 1–2 h pro Monat, danach auf 0 skaliert — Functions wären wegen 500 ms CPU-Rendering × 10'000 Stück pro Worker teurer und Timeout-anfälliger als ein Container, der Batches zieht.
  • Azure Database for PostgreSQL: trägt Jobs + Rechnungen; die Job-Tabelle mit SKIP LOCKED ersetzt hier einen Message-Broker.
  • Service Bus nur für den Mail-Versand: dort will ich Retry, DLQ und kontrollierten Abfluss mit 100/s — Event Hubs wäre falsch, es ist kein Stream, sondern einzelne Aufträge.
  • Blob Storage für PDFs: Lifecycle-Policy nach 90 Tagen in Cool/Archive; Immutability-Policy, weil Rechnungen unveränderlich sein müssen.
  • Monitor: Alarm „um 4:00 noch > 20 % offen" und auf die Fehler-Quote; Key Vault für DB- und Mail-Secrets.

11. Trade-offs

  • Message-Queue vs DB-als-Queue (SKIP LOCKED): gewählt DB, weil Job-Status, Ergebnis und Fortschritt sowieso in der DB liegen — eine Queue daneben hiesse zwei Wahrheiten (Queue sagt „weg", DB sagt „offen"). Preis: Worker pollen die DB, und ab ~Millionen Jobs/Tag mit vielen Workern wird die Job-Tabelle zum Hotspot — dann echte Queue.
  • Alles um 0:00 vs über Stunden verteilt: gewählt sofort erzeugen (Deadline 6:00), aber Versand über die Queue glätten. Preis: Lastspitze auf DB und Blob um 0:00–2:00 — akzeptiert, weil nachts sonst nichts läuft.
  • Deterministische Rechnungsnummer vs Sequenz: gewählt deterministisch (R-periode-kunde), weil Wiederholung dann per Konstruktion keine zweite Nummer erzeugen kann. Preis: Nummern sind nicht lückenlos aufsteigend über alle Kunden — wenn Buchhaltung das fordert, Sequenz + UNIQUE(kunde_id, periode) als Netz.
  • Batch 100 vs einzeln ziehen: gewählt Batch, weil 200'000 Einzel-Claims = 200'000 Transaktionen nur fürs Verteilen. Preis: stürzt ein Worker ab, hängen bis zu 100 Jobs 10 min im Timeout statt 1 — bei 84 min Gesamtlauf egal.
  • Timeout-Resurrection vs „in_arbeit manuell prüfen": gewählt automatischer Rückfall nach 10 min, weil ein 3-Uhr-Crash sonst Handarbeit um 3 Uhr heisst. Preis: ein nur langsamer Job kann doppelt laufen — genau dafür sind PDF-Overwrite und ON CONFLICT DO NOTHING da: doppelt ausführen ist harmlos, weil idempotent.

12. Selbsttest

Typische Fehler genau bei dieser Aufgabe:

  • „Eine Schleife über alle Kunden" ohne Zustand: Crash bei Kunde 120'000 ⇒ niemand weiss, wer schon dran war. Erst die Job-Tabelle macht den Lauf wiederanlauffähig.
  • FOR UPDATE ohne SKIP LOCKED: 20 Worker serialisieren sich auf denselben ersten 100 Zeilen — 19 warten, einer arbeitet.
  • Mail direkt im Worker senden: Provider drosselt bei 100/s ⇒ Worker blockieren beim Senden statt zu rendern; Rate-Limit gehört an eine eigene Stelle.
  • PDF in die DB (bytea): 20 GB/Monat blähen Backups und Vacuum; Blob ist dafür gebaut.
  • Status-Update und Arbeit in EINER langen Transaktion: Locks leben dann 50 s pro Batch; claimen und arbeiten gehören getrennt.
Warum genau FOR UPDATE SKIP LOCKED — was macht jedes der drei Wörter?

FOR UPDATE sperrt die selektierten Zeilen bis zum Commit, damit kein zweiter Worker sie gleichzeitig claimt. SKIP LOCKED überspringt Zeilen, die schon gesperrt sind, statt zu warten — jeder Worker bekommt sofort einen disjunkten Batch. Ohne SKIP LOCKED würden alle Worker auf die Locks des ersten warten.

Worker crasht um 3:00 mit 100 geclaimten Jobs. Was passiert, Schritt für Schritt?

Seine Transaktion war schon committet, die Jobs stehen auf in_arbeit mit gestartet_am=3:00. Um 3:10 setzt der Aufräumer sie zurück auf offen, andere Worker ziehen sie. Teilweise erledigte darunter: PDF wird überschrieben (gleicher Blob-Name), INSERT … ON CONFLICT DO NOTHING greift — keine doppelte Rechnung, keine Lücke.

Kann durch den 10-min-Timeout eine Rechnung doppelt gemailt werden?

Ja, im Randfall: Worker A hängt 11 min, hat aber schon in die Mail-Queue geschrieben; Worker B wiederholt den Job und schreibt nochmal. Darum dedupliziert der Mail-Sender auf rechnung_id: UPDATE rechnung SET versendet_am=now() WHERE rechnung_id=? AND versendet_am IS NULL — nur wer 1 Zeile trifft, sendet. At-least-once in der Queue, exactly-once-Wirkung über die DB.

Warum ist die deterministische rechnung_id der wichtigste Idempotenz-Baustein?

Weil jede Wiederholung — Timeout, Retry, manueller Neustart — dann auf denselben Schlüssel schreibt: gleicher Blob-Pfad (Overwrite), gleicher DB-Konflikt (DO NOTHING), gleiche Dedup-Zeile beim Versand. Mit einer Zufalls- oder Sequenz-ID müsste jede dieser Stellen eigene Duplikat-Erkennung bauen.

Jemand drückt den Start-Knopf zweimal. Was verhindert 400'000 Mails?

UNIQUE(periode) auf rechnungslauf: der zweite POST /laeufe läuft in den Constraint und bekommt 409. Selbst wenn jemand die Jobs doppelt anlegen wollte, blockt der Primärschlüssel (lauf_id, kunde_id) — und notfalls UNIQUE(kunde_id, periode) auf rechnung. Drei Schichten, alle in der DB.

Rechne: reichen 20 Worker wirklich bis 6:00?

200'000 × 0,5 s = 100'000 s CPU; / 20 Worker = 5'000 s ≈ 84 min reine Arbeit, plus Claim-Overhead (2'000 Batches × ~20 ms ≈ 40 s, vernachlässigbar). Start 0:00 ⇒ fertig ~1:30, Puffer 4,5 h für Retries und einen kompletten Wiederanlauf. Versand: 34 min bei 100/s, läuft parallel.

Skalierung ×10: 2 Mio Kunden. Was kippt zuerst?

Rechenzeit: 1 Mio s / 6 h Fenster ⇒ ~50 Worker nötig — noch problemlos, SKIP LOCKED verteilt auch auf 50. Danach der Versand: 2 Mio / 100 pro s = 5,5 h — jetzt wird das Mail-Limit die kritische Ressource ⇒ mit dem Provider höheres Limit verhandeln oder zweiten Provider sharden. Die Job-Tabelle (2 Mio Zeilen) bleibt klein.

Was geht kaputt, wenn der Blob-Storage während des Laufs 20 min ausfällt?

Die betroffenen Jobs werfen Exceptions und landen auf fehler (oder bleiben nach Timeout offen). Nichts geht verloren: nach dem Ausfall POST /laeufe/{id}/retry, die Fehler-Jobs laufen idempotent nochmal. Wichtig im Interview: der Lauf stoppt nicht, er degradiert — und Monitor alarmiert bei Fehler-Quote > x %.

Warum eine Zeile pro Kunde statt „Offset 0–9999 für Worker 1, 10000–19999 für Worker 2"?

Feste Bereiche sind Scheduling von Hand: stirbt Worker 7, bleibt sein Bereich liegen; ist ein Bereich voller teurer Kunden, wird er zum Nachzügler. Die Job-Tabelle ist Work-Stealing: schnelle Worker ziehen automatisch mehr — Lastausgleich ohne Koordinator.

Wie hältst du das Rate-Limit von 100 Mails/s technisch ein?

Ein Sender-Prozess (oder wenige) konsumiert die Mail-Queue mit Token Bucket: 100 Tokens/s, jede Mail verbraucht eins; bei 429/Throttle-Antwort des Providers Backoff und Nachricht zurück in die Queue. Die Render-Worker bleiben davon unberührt — genau dafür ist der Versand entkoppelt.

Fachbereich: „Rechnung von Kunde 4711 war falsch, bitte neu erzeugen und senden."

Einzelfall-Pfad: Job auf offen zurücksetzen und versendet_am auf NULL — der normale Mechanismus erledigt Rendern + Senden. Wichtig: fachlich korrigierte Rechnungen brauchen buchhalterisch eine Storno- und Neurechnung (neue ID), kein stilles Überschreiben — das sage ich aktiv, das ist Senior-Punkt.

Was geht kaputt, wenn zwei Aufräumer-Instanzen gleichzeitig laufen?

Nichts: beide führen dasselbe idempotente UPDATE aus (status='offen' WHERE status='in_arbeit' AND gestartet_am < …); die Zeilen landen höchstens einmal auf offen. Das ist das Muster der ganzen Seite: jeden Schritt so bauen, dass Doppel-Ausführung keine Doppel-Wirkung hat.

Sicherheits-/PII-Punkt: Was ist an 200'000 PDFs heikel?

Jedes PDF enthält Name, Adresse, Verbindungsdaten. Konkret: Blob-Container privat, Portal-Zugriff nur über kurzlebige signierte URLs (Minuten, nicht Tage), Autorisierung „Kunde sieht nur eigene kunde_id" serverseitig prüfen — eine erratbare URL wie /rechnungen/R-2026-11-4711.pdf ohne Auth wäre ein meldepflichtiger Vorfall.

Warum kein Spring Batch / fertiges Batch-Framework?

Darf man nennen: Spring Batch liefert genau diese Job-/Step-Status-Tabellen fertig. An der Tafel erkläre ich trotzdem den Mechanismus darunter — Status-Maschine + SKIP LOCKED — denn der Interviewer prüft, ob ich weiss, was das Framework für mich tut. Preis des Frameworks: eigenes Schema, eigene Lernkurve, weniger Kontrolle über das Claiming.

Wie merkt das System, dass der Lauf „fertig" ist?

Es gibt keinen expliziten Fertig-Moment nötig: GET /laeufe/{id} zählt per GROUP BY status; offen + in_arbeit = 0 heisst fertig. Für den Abschluss-Report reicht ein Check im Scheduler um 5:00: wenn nicht fertig oder fehler > Schwelle ⇒ Alarm an Bereitschaft.

Szenario: Um 2:00 ist die Hälfte der Jobs fehler mit „connection timeout" zur Kundendatenbank. Was tust du?

Nicht blind retryen: erst Ursache — die Positionsabfrage hat die Kunden-DB überlastet (20 Worker × parallele Queries). Sofort: Worker auf 5 drosseln, retry für die Fehler-Jobs; die Rechnung dazu: 100'000 s / 5 = längere Laufzeit, reicht es noch bis 6:00? Wenn nein: Eskalation + Teilversand priorisieren. Danach: Connection-Pool-Limit pro Worker und Lasttest gegen die Kunden-DB.
