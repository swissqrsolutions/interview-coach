Fall: Verteilter Job-Scheduler

Kern (die 1-Minuten-Antwort): Ein Job-Scheduler startet Aufgaben zur richtigen Zeit genau einmal pro geplantem Termin, auch wenn Knoten abstürzen. Ein Scheduler erzeugt fällige Runs mit Unique-Key (job_id, scheduled_for); Worker holen Runs atomar mit einer Lease und senden Heartbeats; ein Reaper gibt Runs abgestürzter Worker frei. Ausführung ist at-least-once, darum müssen Jobs idempotent sein.

1. Wo sitzt was? (Architektur)

  1. Admin-API: legt Jobs an: Name, Cron-Ausdruck, Zeitzone, Timeout, Retry-Regel. Beispiel: tagesstatistik täglich 02:00 Europe/Zurich.
  2. Scheduler: läuft z. B. jede Sekunde. Er sucht fällige Jobs und legt Runs an. Mehrere Instanzen dürfen laufen, weil der Unique-Key Duplikate blockt.
  3. PostgreSQL: Wahrheit für Definitionen, Runs, Status und Leases. Kein Zustand nur im Speicher.
  4. Worker: holen Runs mit SKIP LOCKED, senden alle 30 s einen Heartbeat und melden done oder failed.
  5. Reaper: findet Runs, deren Heartbeat zu alt ist, und setzt sie zurück auf pending.
  6. Ziel-System: die eigentliche Arbeit, z. B. ein Spark-Job über REST oder ein Batch-Endpoint.

2. Die Reise eines Runs (die Geschichte zum Merken)

  1. Fällig: Es ist 02:00 in Zürich. Der Job tagesstatistik hat next_run_at = 02:00.
  2. Run anlegen: Der Scheduler schiebt next_run_at um einen Tag weiter und legt einen Run für 02:00 an. Laufen zwei Scheduler, blockt der Unique-Key den zweiten Run.
  3. Claim: Worker A holt den Run atomar: running, worker = 'worker-a', attempts = 1.
  4. Heartbeat: Während der Arbeit setzt Worker A alle 30 s heartbeat_at = now(). So weiss das System: Er lebt.
  5. Erfolg: Worker A setzt done. Das Ergebnis überschreibt den ganzen Tag, statt etwas zu addieren.
  6. Absturz: Worker A stirbt nach 3 Minuten. Kein Heartbeat mehr. Nach 5 Minuten setzt der Reaper den Run zurück auf pending.
  7. Zweiter Versuch: Worker B holt den Run. Weil der Job idempotent ist, ist das Ergebnis gleich. Nach z. B. 3 Versuchen: failed und Alarm.

3. Beispiel: API, Datenmodell und die Queries laut gesagt

API:

POST  /v1/jobs            {name, schedule: "0 2 * * *", timezone: "Europe/Zurich",
                           timeoutSec, maxAttempts, misfirePolicy: "run_once"} → 201
PATCH /v1/jobs/{id}       {enabled: false}             (pausieren)
POST  /v1/jobs/{id}:trigger                            (manuell, Idempotency-Key)
GET   /v1/jobs/{id}/runs?status=failed&cursor=…     → Historie

Datenmodell:

CREATE TABLE jobs (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text NOT NULL UNIQUE,
  every       interval NOT NULL,          -- vereinfacht statt Cron-Ausdruck
  next_run_at timestamptz NOT NULL,
  enabled     boolean NOT NULL DEFAULT true
);
CREATE TABLE job_runs (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  job_id        bigint NOT NULL REFERENCES jobs(id),
  scheduled_for timestamptz NOT NULL,
  status        text NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','running','done','failed')),
  worker        text,
  heartbeat_at  timestamptz,
  attempts      int NOT NULL DEFAULT 0,
  UNIQUE (job_id, scheduled_for)
);
CREATE INDEX job_runs_pending_idx ON job_runs (scheduled_for) WHERE status = 'pending';
INSERT INTO jobs (name, every, next_run_at) VALUES
  ('tagesstatistik', '1 day',      '2026-11-24 02:00+01'),
  ('rechnungen',     '1 hour',     '2026-11-24 14:00+01'),
  ('cleanup',        '15 minutes', '2026-11-24 15:30+01');

Query 1, laut gesagt: „Um 15:00 schiebe ich jeden fälligen Job weiter und lege in derselben Anweisung den Run an. Der Unique-Key verhindert einen zweiten Run für denselben Termin.“

WITH due AS (
  UPDATE jobs SET next_run_at = next_run_at + every
  WHERE enabled AND next_run_at <= '2026-11-24 15:00+01'
  RETURNING id, next_run_at - every AS scheduled_for)
INSERT INTO job_runs (job_id, scheduled_for)
SELECT id, scheduled_for FROM due
ON CONFLICT (job_id, scheduled_for) DO NOTHING
RETURNING job_id, scheduled_for;
 job_id |     scheduled_for
--------+------------------------
      1 | 2026-11-24 02:00:00+01
      2 | 2026-11-24 14:00:00+01
(2 rows)
-- zweiter Scheduler versucht denselben Termin:
INSERT INTO job_runs (job_id, scheduled_for) VALUES (1, '2026-11-24 02:00+01')
ON CONFLICT (job_id, scheduled_for) DO NOTHING RETURNING job_id;
(0 rows)

Query 2, laut gesagt: „Worker A holt den ältesten offenen Run. Gesperrte Runs überspringt er.“

UPDATE job_runs SET status = 'running', worker = 'worker-a',
       heartbeat_at = now(), attempts = attempts + 1
WHERE id = (SELECT id FROM job_runs
            WHERE status = 'pending'
            ORDER BY scheduled_for
            LIMIT 1
            FOR UPDATE SKIP LOCKED)
RETURNING id, job_id, worker, attempts;
 id | job_id |  worker  | attempts
----+--------+----------+----------
  1 |      1 | worker-a |        1

Query 3, laut gesagt: „Worker A stirbt; sein Heartbeat ist 10 Minuten alt. Der Reaper setzt alles mit Heartbeat älter als 5 Minuten zurück.“

UPDATE job_runs SET status = 'pending', worker = NULL
WHERE status = 'running' AND heartbeat_at < now() - interval '5 minutes'
RETURNING id, job_id, status, attempts;
 id | job_id | status  | attempts
----+--------+---------+----------
  1 |      1 | pending |        1

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_job_scheduler, Session-Zeitzone Europe/Zurich, danach gelöscht). Der Heartbeat wurde für die Demo per UPDATE künstlich gealtert.

  1. Scheduler ohne Leader: Der Unique-Key macht mehrere Scheduler-Instanzen sicher. Kein Leader-Election nötig für die Korrektheit.
  2. Misfire sichtbar: rechnungen war seit 14:00 fällig. Der Tick um 15:00 legt nur einen Run an (14:00) und schiebt auf 15:00. Wie viele verpasste Termine nachgeholt werden, ist eine bewusste Misfire-Policy.
  3. Claim: SKIP LOCKED plus Partial Index ist eine sichere Queue in der DB.
  4. Recovery: Der Run ist wieder pending, attempts bleibt 1. Der nächste Claim zählt hoch. So begrenzt maxAttempts endlose Neustarts.

4. Details, die Interviewer fragen

  1. Anforderungen: Cron und einmalige Jobs, Zeitzonen, Retries, Timeouts, keine Doppel-Ausführung, Historie, Pausieren, manueller Start, Abhängigkeiten (Job B nach Job A).
  2. Schätzung: 100 000 Job-Definitionen, im Schnitt stündlich = ca. 28 Runs/s. Spitze zur vollen Stunde: viele Jobs mit 0 * * * * fallen in dieselbe Sekunde. Darum Jitter oder Verteilung über die Minute.
  3. Exactly-once gibt es nicht: Ein Worker kann die Arbeit fertig haben und vor done sterben. Dann läuft sie nochmals. Darum at-least-once plus idempotente Jobs.
  4. Idempotenz im Job: Ergebnis ersetzen statt addieren, Upserts, Schlüssel pro scheduled_for. Beispiel: Statistik für einen Tag neu rechnen und überschreiben.
  5. Lease und Heartbeat: Eine Lease ist ein zeitlich begrenztes Recht auf einen Run. Ohne Heartbeat läuft sie ab. Der Timeout muss länger sein als GC-Pausen und Netzwackler.
  6. Fencing Token: Ein „toter“ Worker kann noch leben (lange GC-Pause) und später schreiben. Ein Fencing Token (z. B. attempts) wird beim Schreiben ins Ziel geprüft. Ältere Tokens werden abgelehnt.
  7. Leader Election: Alternative zum Unique-Key: nur ein aktiver Scheduler. Mittel: Kubernetes Lease, PostgreSQL pg_try_advisory_lock, etcd. Auch dann bleibt der Unique-Key als Schutz.
  8. Misfire-Policy: Was passiert nach 3 h Ausfall? „Alle nachholen“, „einmal nachholen“ oder „überspringen“. Kubernetes CronJob startet bei über 100 verpassten Terminen nur den letzten.
  9. Zeitzonen und Sommerzeit: In Europe/Zurich gibt es 02:30 am letzten Sonntag im März nicht, und im Oktober zweimal. Jobs in UTC planen oder die Regel der Bibliothek kennen.
  10. Überlappung: Läuft der 02:00-Run noch um 02:00 am nächsten Tag? Policies: erlauben, überspringen, ersetzen. Kubernetes nennt das concurrencyPolicy: Allow (Standard), Forbid, Replace.
  11. Abhängigkeiten (DAG): Job B startet erst, wenn A done ist. Einfach: Status-Bedingung im Claim. Komplex: ein Workflow-Tool wie Airflow.
  12. Demand-driven statt Uhrzeit: Oft ist die bessere Frage „gibt es Arbeit?“ statt „ist es 02:00?“. Der Worker startet teure Jobs nur, wenn etwas pending ist.
  13. Skalierung: Eine DB-Queue trägt einige hundert bis tausend Claims pro Sekunde. Darüber: Partitionierung nach job_id oder ein Broker für die Ausführung, DB nur für Status.
  14. Historie: job_runs wächst endlos. Partitionierung nach Monat und Aufräumen alter Partitionen.

5. Vergleich: drei Design-Varianten

  • A. Kubernetes CronJob: kein eigener Code, Zeitzone (.spec.timeZone, stabil seit v1.27), Concurrency-Policy. Aber: Laut Doku können zwei Jobs oder keiner entstehen, darum idempotent. Wenig Sicht über viele Jobs hinweg.
  • B. DB-basierter Scheduler (wie oben, Quartz Clustering, db-scheduler): volle Kontrolle, Historie, Retries, Abhängigkeiten in SQL. Grenze: Durchsatz der DB.
  • C. Workflow-Engine (Airflow, Temporal): DAGs, Retries, UI, Backfills. Mächtig, aber eigener Betrieb und Lernkurve. Lohnt bei vielen abhängigen Schritten.

6. In der Produktion

  1. Job lief zweimal: Zwei Scheduler-Pods nach einem Rolling Update. Fix: Unique-Key auf (job_id, scheduled_for), idempotenter Job.
  2. Job lief nie: Scheduler war zur Zeit des Termins down, Misfire-Policy „überspringen“. Fix: Policy bewusst wählen, Alarm auf „erwarteter Run fehlt“.
  3. Runs hängen in running: Worker OOM-killed, kein Reaper. Fix: Heartbeat plus Reaper, Timeout pro Job.
  4. Reaper zu aggressiv: Timeout kürzer als echte Laufzeit, ein lebender Worker verliert seinen Run. Fix: Heartbeat statt fester Laufzeit, Fencing Token.
  5. Spitze zur vollen Stunde: Tausende Jobs um xx:00. Fix: Jitter über die Minute, Kapazitätsgrenzen pro Job-Typ.
  6. Sommerzeit: Ein Job lief im Oktober zweimal. Fix: in UTC planen oder Bibliotheksregel testen.

7. Diagnose: Werkzeuge und Queries

  • Backlog: SELECT count(*), now() - min(scheduled_for) FROM job_runs WHERE status = 'pending';
  • Hängende Runs: SELECT * FROM job_runs WHERE status = 'running' AND heartbeat_at < now() - interval '2 minutes';
  • Fehlende Runs: erwartete Termine gegen job_runs abgleichen (generate_series über die Cron-Zeiten).
  • Sperren: pg_locks und pg_stat_activity bei langsamen Claims.
  • Kubernetes: kubectl get cronjobs, kubectl get jobs, Events wie TooManyMissedTimes.
  • Metriken: Laufzeit pro Job, Fehlerrate, Versuche pro Run, Backlog-Alter. Alarm auf Backlog-Alter, nicht nur auf Fehler.

8. Senior-Punkte

  1. Korrektheit kommt aus Daten, nicht aus Prozessen. Der Unique-Key schützt auch dann, wenn zwei Scheduler laufen.
  2. At-least-once plus Idempotenz ist die ehrliche Garantie. Ich designe Jobs als „ersetze das Ergebnis“.
  3. Heartbeat statt fester Timeout, und Fencing Tokens, wenn ein Zombie-Worker Schaden machen kann.
  4. Misfire-Policy und Zeitzonen sind fachliche Entscheidungen. Ich frage, was nach einem Ausfall passieren soll.
  5. Demand-driven schlägt Uhrzeit, wenn Arbeit unregelmässig kommt: kein leerer Job-Start, weniger Ressourcen.
  6. Eigenen Scheduler nur, wenn nötig. CronJob oder eine fertige Bibliothek decken viele Fälle ab.

9. Aus dem Projekt

„Bei MATCH reicht ein .NET-Worker Spark-Jobs per REST nur ein, wenn Nachrichten pending sind; Spark claimt sie atomar (Pending → Processing), hängende Runs setzt eine Stale-Job-Recovery nach Timeout zurück, und die Statistik ersetzt das Tagesergebnis statt zu addieren, damit Retries sicher sind.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Mit Leader Election läuft jeder Job genau einmal.“ → Falsch. Ein alter Leader kann noch arbeiten. Idempotenz und Fencing bleiben nötig.
  • „Kubernetes CronJob startet garantiert genau einmal.“ → Falsch. Die Doku sagt: zwei Jobs oder keiner sind möglich.
  • „Ein Retry addiert einfach nochmals.“ → Doppelte Werte. Ergebnis ersetzen statt addieren.
  • „Zeitzone ist egal, der Server läuft in UTC.“ → Fachlich ist 02:00 Zürich gemeint. Sommerzeit verschiebt oder doppelt Runs.
  • „Timeout = erwartete Laufzeit.“ → Lange Runs werden zu Unrecht abgebrochen. Heartbeats nutzen.

11. Fragen

Skizzieren Sie den Job-Scheduler in einer Minute.

Jobs in einer DB, ein Scheduler legt fällige Runs mit Unique-Key an, Worker claimen mit Lease und Heartbeat, ein Reaper gibt verwaiste Runs frei. Jobs sind idempotent, weil die Ausführung at-least-once ist.

Wie verhindern Sie doppelte Ausführung?

Unique-Key auf Job und Termin beim Anlegen, atomarer Claim beim Holen. Gegen Zombie-Worker Fencing Tokens. Ganz ausschliessen kann man es nicht, darum idempotente Jobs.

Was ist eine Lease?

Ein zeitlich begrenztes Recht auf einen Run. Der Worker verlängert sie per Heartbeat. Läuft sie ab, darf ein anderer übernehmen.

Was ist ein Fencing Token?

Eine steigende Nummer pro Claim. Das Ziel-System lehnt Writes mit älterer Nummer ab. So kann ein Zombie-Worker nichts überschreiben.

Brauchen Sie Leader Election?

Nicht für die Korrektheit, wenn der Unique-Key Duplikate blockt. Für Effizienz kann ein Leader sinnvoll sein, z. B. mit Kubernetes Lease oder Advisory Lock.

Was ist eine Misfire-Policy?

Die Regel für verpasste Termine nach einem Ausfall: alle nachholen, einmal nachholen oder überspringen.

Wie gehen Sie mit Sommerzeit um?

In UTC planen oder die Regel der Cron-Bibliothek kennen und testen. 02:30 fehlt im März und kommt im Oktober zweimal.

Was passiert, wenn ein Run länger dauert als das Intervall?

Eine Concurrency-Policy entscheidet: parallel erlauben, neuen Run überspringen oder alten ersetzen.

Wie machen Sie einen Job idempotent?

Ergebnis pro Termin ersetzen statt addieren, Upserts, Schlüssel aus Job und scheduled_for.

Wie bauen Sie Abhängigkeiten?

B wird erst claimbar, wenn A done ist. Bei vielen Schritten eine Workflow-Engine.

Kubernetes CronJob oder eigener Scheduler?

CronJob für wenige, einfache Jobs. Eigener oder Bibliotheks-Scheduler für Historie, Retries, Abhängigkeiten und viele Jobs.

Wie skaliert die DB-Queue?

Mit SKIP LOCKED und Partial Index bis einige hundert bis tausend Claims pro Sekunde. Darüber Partitionierung oder ein Broker.

Was ist der Unterschied zwischen zeit- und bedarfsgesteuert?

Zeitgesteuert startet zur Uhrzeit, auch ohne Arbeit. Bedarfsgesteuert startet nur, wenn Arbeit pending ist. Das spart Ressourcen bei unregelmässigen Daten.

Welche Metriken alarmieren Sie?

Alter des ältesten pending Runs, hängende running Runs, fehlende erwartete Runs, Fehlerrate und Laufzeit pro Job.

Szenario: Ein täglicher Job lief heute zweimal. Wie untersuchen Sie das?

job_runs für den Tag ansehen: zwei Runs mit anderem scheduled_for oder ein Retry nach Reaper? Ursachen: kein Unique-Key, Sommerzeit, zu kurzer Timeout. Dann Job idempotent machen.

Szenario: Nach einem Deployment hängen viele Runs in running. Was tun Sie?

Die alten Pods wurden beendet, ohne Runs freizugeben. Reaper prüfen, Heartbeat-Timeout, graceful Shutdown, der Runs zurückgibt.

Szenario: Der Scheduler war 4 Stunden down. Was passiert beim Start?

Die Misfire-Policy entscheidet. Bei „alle nachholen“ kommt eine Welle von Runs, darum Parallelität begrenzen. Fachlich klären, ob alte Termine überhaupt Sinn ergeben.
