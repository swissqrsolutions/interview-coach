Drill 2: Live-Chat (WebSocket, Kafka, Fan-out)

1. Die Aufgabe

So stellt sie der Interviewer, wörtlich:

„Design einen Live-Chat für unsere App: 1:1-Chats und Gruppen bis 200 Mitglieder. Zur Spitze sind 50'000 Nutzer gleichzeitig verbunden, es werden rund 500 Nachrichten pro Sekunde gesendet. Nachrichten dürfen nicht verloren gehen, der Verlauf muss abrufbar sein, und wer offline ist, bekommt die Nachricht beim nächsten Öffnen. Latenz: Nachricht beim Empfänger in unter 1 Sekunde."

20 Minuten: Laut lösen — Methode, Anforderungen, DB, API, Pseudo-Code, Diagramm, Trade-offs. Erst danach vergleichen.

2. Schritt 1: Verstehen (die 5-Minuten-Methode angewendet)

Rückfragen mit plausiblen Interviewer-Antworten:

  1. „Wie gross ist eine Nachricht, gibt es Bilder?" — „Text ~0,5 KB; Bilder ja, aber als URL." → Bytes in Object Storage, Chat trägt nur Links.
  2. „Durchschnittliche Empfängerzahl pro Nachricht?" — „Meist 1:1, Gruppen im Schnitt 10." → Fan-out ≈ 500 × 10 = 5'000 Pushes/s im Mittel.
  3. „Muss die Reihenfolge stimmen?" — „Innerhalb eines Chats ja, global egal." → Ordnung pro Chat = Partition Key.
  4. „Zustellgarantie?" — „Nichts verlieren; Dubletten darf der Client wegfiltern." → persistieren vor Push, at-least-once.
  5. „Lesen vs Schreiben?" — „Verlauf-Scrollen dominiert klar." → leselastig: Index + Pagination zählen.
  6. „Presence (online/offline) nötig?" — „Ja, grüner Punkt reicht, darf 30 s alt sein." → Redis mit TTL, nichts Exaktes.

Zahlen laut vorrechnen: Schreiben: 500 msg/s × 0,5 KB = 250 KB/s ≈ 21 GB/Tag ≈ 8 TB/Jahr — Postgres geht, aber Partitionierung nach Zeit einplanen. Verbindungen: 50'000 gleichzeitig; ein Gateway-Knoten hält ~10k Verbindungen bequem → 5 bis 8 Gateway-Knoten. Spitze: 10× auf 5'000 msg/s bei Grossereignissen.

Scope laut: „Ich baue Senden, Zustellen, Verlauf, Presence. Ende-zu-Ende-Verschlüsselung, Reactions und Suche lasse ich weg. Ok?"

3. Anforderungen

Muss:

  • Zustellung online < 1 s; keine Nachricht verloren (persistiert, bevor bestätigt).
  • Reihenfolge innerhalb eines Chats stabil.
  • Offline-Fall: Push-Notification + Nachholen beim Reconnect.
  • Verlauf mit Pagination (ältere Nachrichten nachladen).
  • Presence mit Toleranz (bis 30 s alt ok).

Kann:

  • Gelesen-Haken, Tippt-gerade-Anzeige, Ende-zu-Ende-Verschlüsselung, Volltext-Suche, Multi-Region.

4. DB-Design

CREATE TABLE chats (                 -- 1:1 oder Gruppe
  id         uuid PRIMARY KEY,
  is_group   boolean NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE chat_members (          -- wer ist in welchem Chat
  chat_id   uuid NOT NULL REFERENCES chats(id),
  user_id   uuid NOT NULL,
  last_read_msg_id bigint,           -- fuer Ungelesen-Zaehler und Nachholen
  PRIMARY KEY (chat_id, user_id)
);

CREATE TABLE messages (              -- append-only, nie UPDATE im Hot Path
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  chat_id    uuid  NOT NULL REFERENCES chats(id),
  sender_id  uuid  NOT NULL,
  client_msg_id uuid NOT NULL,       -- Idempotenz: Client-Retry erzeugt kein Duplikat
  body       text  NOT NULL,         -- ~0,5 KB; Bilder nur als URL
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (chat_id, client_msg_id)
);

-- DER Index: Verlauf = "letzte N Nachrichten dieses Chats"
CREATE INDEX idx_hist ON messages (chat_id, id DESC);
-- Mitglieds-Sicht: "meine Chats" aufloesen
CREATE INDEX idx_user ON chat_members (user_id);

Warum so: messages ist append-only — Schreiben bleibt billig, und id (monoton pro Tabelle) ordnet den Verlauf. chat_members.last_read_msg_id macht Nachholen und Ungelesen-Zähler zu einer einzigen Range-Query. UNIQUE (chat_id, client_msg_id) fängt Client-Retries in der DB ab, nicht im Code.

5. API

  • GET /ws — WebSocket-Verbindung (Auth per Token beim Handshake); senden + empfangen laufen hierüber.
  • GET /v1/chats — meine Chats mit letzter Nachricht + Ungelesen-Zähler.
  • GET /v1/chats/{id}/messages?before_id=&limit=50 — Verlauf, Keyset-Pagination (nie OFFSET).
  • POST /v1/chats — Chat/Gruppe anlegen.
  • POST /v1/chats/{id}/members — Mitglied hinzufügen.
  • POST /v1/uploads — Upload-URL für Bilder holen (Blob, nicht über den Chat-Pfad).

6. Pseudo-Code an der Tafel

// --- Gateway: Client sendet ueber WebSocket ---
function onMessage(conn, msg):
  pruefeMitglied(conn.userId, msg.chatId)       // AuthZ bei jeder Nachricht
  id = db.insertMessage(msg)                    // 1. persistieren (Idempotenz-Key!)
  kafka.produce("messages", key=msg.chatId,     // 2. gleicher Chat → gleiche
                value={id, ...msg})             //    Partition → Reihenfolge bleibt
  conn.send(ack(msg.clientMsgId, id))           // 3. Haken an den Sender

// --- Fan-out-Worker (Consumer Group, n Instanzen) ---
function onKafkaRecord(rec):
  mitglieder = membersCache.get(rec.chatId)     // Redis-Cache, DB als Fallback
  for userId in mitglieder ohne rec.senderId:
    gatewayNode = redis.get("conn:" + userId)   // wo haengt der Nutzer?
    if gatewayNode != null:                     // --- ONLINE ---
      rpc(gatewayNode).push(userId, rec)        //   Gateway pusht ueber WebSocket
    else:                                       // --- OFFLINE ---
      pushDienst.notify(userId, vorschau(rec))  //   mobile Push-Notification
      // kein "Postfach" noetig: Nachricht liegt in der DB
  commitOffset(rec)                             // erst NACH dem Fan-out

// --- Client beim Reconnect: Nachholen ---
function onReconnect():
  fuer jeden chat: GET /messages?after_id=last_read_msg_id
  // Die DB ist die Wahrheit — der Push ist nur die schnelle Abkuerzung.

7. Architektur

Der Kernsatz dazu: „Das Gateway persistiert und produziert nur — wer die Nachricht bekommt, entscheidet der Fan-out-Worker hinter Kafka. So skalieren Annahme und Zustellung unabhängig."

8. Der schwierige Teil als Bild: Fan-out, online und offline

Merksatz: Gleicher Key → gleiche Partition → eine Reihenfolge. Innerhalb einer Partition liest der Worker die Nachrichten in Schreibreihenfolge — darum stimmt die Ordnung pro Chat, ohne globale Koordination.

9. Frontend kurz (Angular)

  • Komponenten: ChatListComponent, ChatWindowComponent (Virtual Scrolling für den Verlauf), MessageInputComponent.
  • ChatSocketService: eine WebSocket-Verbindung pro App, Reconnect mit Backoff + Jitter; nach Reconnect erst nachholen, dann live.
  • State über Signals: Nachricht optimistisch anzeigen (grau), beim Ack per client_msg_id bestätigen — Dubletten filtert dieselbe Id.

10. Cloud (Azure)

  • AKS für Gateways + Worker: 50k langlebige WebSocket-Verbindungen brauchen Kontrolle über Timeouts, Drain beim Deploy und Skalierung — auf AKS habe ich das; App Service ist für langlebige Verbindungen dieser Zahl die falsche Abstraktion.
  • Azure SignalR Service als Alternative laut nennen: managed WebSocket-Fan-out, nimmt mir die Gateway-Schicht ab. Preis: weniger Kontrolle, Kosten pro Verbindung — als Option erwähnen zeigt Azure-Kenntnis.
  • Event Hubs statt selbst betriebenem Kafka: Kafka-kompatibles Protokoll, Partitionen + Consumer Groups vorhanden, kein Cluster-Betrieb. Eigenes Kafka erst, wenn Features oder Kosten es erzwingen.
  • Azure Database for PostgreSQL für den Verlauf; Blob Storage für Bilder (Chat trägt nur URLs).
  • Azure Cache for Redis für Presence und user→Gateway-Routing.
  • Key Vault für Token-Signatur-Keys; Monitor: Alarm auf Consumer-Lag und Verbindungszahl pro Gateway.

11. Trade-offs

  • Kafka vs direkter WebSocket-Broadcast vom Gateway → Kafka, weil der Sender-Gateway sonst alle Empfänger auf allen Knoten selbst finden müsste und bei Absturz Nachrichten ohne Zustellung verloren wären. Preis: ein paar Millisekunden Latenz und eine Komponente mehr Betrieb.
  • Verlauf in Postgres vs Cassandra → Postgres, weil 8 TB/Jahr mit Zeit-Partitionierung beherrschbar sind und das Team Postgres kann. Preis: bei 100× Chat-Volumen (WhatsApp-Klasse) müsste ich auf einen Wide-Column-Store wie Cassandra migrieren — den Punkt nenne ich laut.
  • Presence via Redis-TTL vs exakte Events in der DB → Redis-TTL (Heartbeat 30 s, TTL 60 s): Absturz heilt sich selbst, wenn der Key abläuft. Preis: der grüne Punkt kann bis 60 s lügen — die Anforderung erlaubt das ausdrücklich.
  • Persistieren vor Publish vs Publish zuerst → DB zuerst, weil „keine Nachricht verloren" sonst am Broker-Ack hängt und Reconnect-Nachholen die DB als Wahrheit braucht. Preis: der Insert liegt im Latenzpfad des Senders (~wenige ms).
  • Sticky Sessions vs Routing-Tabelle in Redis → Redis-Routing, weil Sticky beim Gateway-Ausfall alle Sessions verliert und Rebalancing verhindert. Preis: jeder Fan-out macht einen Redis-Lookup — bei 5'000 Pushes/s gut innerhalb von Redis-Grenzen (~100k ops/s).

12. Selbsttest: Folgefragen des Interviewers

„Rechne: Wie viel Speicher braucht der Verlauf pro Jahr?"

500 msg/s × 0,5 KB ≈ 250 KB/s ≈ 21 GB/Tag ≈ 8 TB/Jahr. Antwort dazu: Zeit-Partitionierung in Postgres, alte Partitionen nach Blob archivieren oder löschen, je nach Produktentscheid.

„Warum ist chat_id der richtige Partition Key — und was wäre an user_id falsch?"

Die Ordnungs-Anforderung gilt pro Chat, und Kafka garantiert Ordnung nur innerhalb einer Partition — gleicher Key, gleiche Partition, fertig. user_id würde die Nachrichten eines Chats über Partitionen verstreuen: Reihenfolge weg, Fan-out-Logik kaputt.

„Was geht kaputt, wenn ein Gateway-Knoten abstürzt?"

~10k Clients verlieren die Verbindung und reconnecten über den LB auf andere Knoten — mit Backoff + Jitter, sonst Reconnect-Sturm. Ihre conn:-Keys in Redis laufen per TTL ab. Verpasste Nachrichten? Keine: sie liegen in der DB, Nachholen per after_id.

„Wie viele Fan-out-Worker können parallel arbeiten?"

Höchstens so viele wie Partitionen: In einer Consumer Group liest jede Partition genau ein Consumer. Bei 32 Partitionen bringen 40 Worker nichts — 8 stehen still. Darum Partitionszahl von Anfang an über dem Zielwert wählen; nachträgliches Erhöhen verschiebt die Key-Zuordnung.

„Wann committet der Worker den Offset — und warum genau dann?"

Nach dem Fan-out. Committet er vorher und stirbt, ist die Nachricht aus Broker-Sicht erledigt, aber nie gepusht — Clients sehen sie erst beim Reconnect. Commit nach der Arbeit heisst at-least-once: Im Crash-Fall wird doppelt gepusht, und der Client filtert per Message-Id.

„Eine Gruppe hat 200 Mitglieder. Was kostet eine Nachricht?"

1 DB-Insert, 1 Kafka-Produce, dann 200 Redis-Lookups (gebündelt per Pipeline/MGET: 1 Roundtrip) und bis zu 200 Pushes verteilt auf die Gateways. Der teure Teil ist der Push, nicht die Persistenz — genau darum liegt er asynchron hinter Kafka.

„×10: 500k Verbindungen, 5'000 msg/s. Was ändert ihr?"

Gateways: ~60 Knoten statt 6 — zustandslos, also nur Geld. Kafka: Partitionen und Worker hoch. Postgres-Schreiblast: 5'000 Inserts/s → Batching und Zeit-Partitionen; ab hier beginnt die ehrliche Diskussion über Cassandra für den Verlauf. Redis: 50k Pushes/s Lookups → Pipelines, dann Cluster.

„Sicherheitsfrage: Wie verhindert ihr, dass jemand fremde Chats liest oder hineinschreibt?"

AuthN beim WebSocket-Handshake (kurzlebiges Token), AuthZ bei jeder Aktion gegen chat_members — nie nur beim Connect, Mitgliedschaften ändern sich. Verlauf-API prüft dieselbe Tabelle. Bild-URLs sind signierte, ablaufende Blob-Links, keine öffentlichen Pfade.

„Der Nutzer sendet, das WLAN bricht ab, die App retryt. Zwei Nachrichten?"

Nein: Der Client generiert pro Nachricht eine client_msg_id; UNIQUE (chat_id, client_msg_id) macht den zweiten Insert zum No-op, der Client bekommt dasselbe Ack. Idempotenz liegt in der DB-Constraint, nicht in Anwendungslogik.

„Warum nicht Redis Pub/Sub statt Kafka für den Fan-out?"

Pub/Sub ist fire-and-forget: kein Replay, keine Offsets, kein Nachlesen nach Worker-Crash — wer nicht lauscht, verpasst. Kafka speichert die Nachrichten; ein neu gestarteter Worker liest ab seinem Offset weiter. Bei „nichts verlieren" ist das der Unterschied, der zählt.

„Wie funktioniert der Ungelesen-Zähler, ohne die DB zu quälen?"

last_read_msg_id pro Mitglied; ungelesen = Nachrichten mit id > diesem Wert — eine Range-Query auf idx_hist. Beim Öffnen des Chats wird der Wert hochgesetzt. Kein Zähler-UPDATE pro eingehender Nachricht, das wäre eine Hot Row pro Gruppe.

„Was passiert bei einem Netsplit: Nutzer wirkt online, ist aber weg?"

Der Push an sein Gateway läuft ins Leere, die Verbindung ist tot. Sichtbar wird das über den fehlenden Heartbeat: Nach spätestens 60 s (TTL) gilt er als offline. Die Nachricht ist nicht verloren — sie steht in der DB und kommt beim Reconnect per Nachholen.

„Warum Keyset-Pagination (before_id) statt OFFSET beim Verlauf?"

OFFSET 10'000 liest und verwirft 10'000 Zeilen — wird mit jeder Seite langsamer. WHERE chat_id = ? AND id < ? ORDER BY id DESC LIMIT 50 springt per Index direkt an die Stelle: konstante Kosten, egal wie tief gescrollt wird.

„Zwei Geräte desselben Nutzers gleichzeitig — was ändert sich?"

Aus conn:user wird eine Menge: conn:user:device → gateway, Fan-out pusht an alle Einträge. Gelesen-Status wird über last_read_msg_id zwischen Geräten konsistent, weil er serverseitig liegt und nicht im Client.

„Woran erkennt ihr im Betrieb, dass die Zustellung kippt?"

Consumer-Lag (Abstand Worker zu neuester Nachricht) ist die Metrik Nummer eins: wächst er, dauert die Zustellung länger als 1 s, lange bevor etwas crasht. Dazu: Verbindungen pro Gateway, Redis-Latenz, p95 vom Senden bis zum Push (Ende-zu-Ende gemessen).

„Tippt-gerade und Gelesen-Haken: Gehören die in denselben Pfad?"

Nein. „Tippt gerade" ist verlierbar und flüchtig: direkt Gateway-zu-Gateway oder Redis Pub/Sub, nie persistieren — sonst verzehnfacht ein Feature ohne Wert die Schreiblast. Gelesen-Haken ist ein last_read-Update, gedrosselt (z. B. max 1/s pro Chat).

Typische Fehler bei genau dieser Aufgabe:

  • Push zuerst, DB später: Gateway crasht nach dem Push, vor dem Insert — die Nachricht existiert beim Empfänger, aber nicht im Verlauf. Persistieren kommt immer zuerst.
  • Ordnung global versprechen: Unbezahlbar und unnötig. Die Anforderung ist Ordnung pro Chat — genau das liefert der Partition Key.
  • Presence exakt bauen wollen: Disconnect-Events gehen verloren (Stromausfall sendet kein Goodbye). TTL + Heartbeat ist das einzige robuste Modell.
  • Offline-Postfach pro Nutzer puffern: Doppelte Wahrheit neben der DB, die auseinanderläuft. Die DB ist das Postfach; offline heisst nur: Notification statt Push.
  • WebSocket-Details vergessen: LB-Idle-Timeouts, Heartbeats, Drain beim Deploy — wer „einfach WebSocket" sagt, bekommt genau hier die Folgefragen.
