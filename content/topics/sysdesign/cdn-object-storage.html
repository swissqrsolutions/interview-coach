CDN und Object Storage

System-Design-Grundlagen · Tier 1 · Quellen: Microsoft Learn (Blob Storage Introduction, Access Tiers, Scalability Targets, Put Block List, Grant limited access with SAS, Create a user delegation SAS, Private Endpoints for Storage, Azure Front Door Caching und Purge, Event Grid Blob Events), AWS S3 User Guide (Consistency Model, Multipart Upload Limits, Presigned URLs, Lifecycle), AWS What's New Dez. 2025 (S3-Objekte bis 50 TB), RFC 9111 (HTTP Caching), RFC 5861, RFC 8246 (immutable)

Kern: Object Storage (Azure Blob, AWS S3, MinIO) speichert Dateien als Objekte mit Schlüssel, Daten und Metadaten. Er ist billig, praktisch unbegrenzt und über HTTP erreichbar. Ein CDN (Content Delivery Network) hält Kopien an Edge-Standorten nahe beim Nutzer. Es senkt Latenz, Egress-Kosten und Last auf dem Origin.

1. Wo sitzen Object Storage und CDN?

  1. API: prüft, wer der Nutzer ist und was er darf. Sie gibt eine signierte URL heraus: eine URL mit Ablaufzeit und Signatur.
  2. Object Storage: nimmt die Datei direkt vom Client an. Die Bytes laufen nicht durch die API.
  3. Datenbank: speichert nur Metadaten: Schlüssel, Besitzer, Grösse, Status.
  4. Event und Worker: Ein Event (z. B. BlobCreated) startet Nacharbeit: Virenscan, Vorschaubild.
  5. CDN: liefert Downloads vom nächsten Edge-Standort (POP, Point of Presence). Nur bei einem Miss fragt es den Origin, also den Storage.

2. Die Reise eines Uploads und Downloads (die Geschichte zum Merken)

  1. Upload-URL holen: Der Client fragt die API. Die API prüft die Rechte und erzeugt einen eindeutigen Schlüssel, z. B. uploads/2026/11/<uuid>.pdf. Sie gibt eine SAS-URL (Azure) oder Presigned URL (S3) zurück: nur Schreiben, nur dieser Blob, 15 Minuten gültig.
  2. Teile hochladen: Grosse Dateien gehen in Teilen. Azure: Put Block. S3: UploadPart. Teile laufen parallel, ein Fehler wiederholt nur ein Teil.
  3. Commit: Azure: Put Block List. S3: CompleteMultipartUpload. Erst jetzt ist das Objekt sichtbar, und zwar ganz oder gar nicht.
  4. Event: Der Storage meldet „Objekt erstellt“ (Azure Event Grid, S3 Event Notifications). Ein Worker scannt die Datei und setzt den Status in der Datenbank auf „bereit“.
  5. Download-Request: Ein Nutzer öffnet die Datei. DNS führt ihn zum nächsten POP des CDN.
  6. Edge-Cache: Hat der POP eine frische Kopie, antwortet er sofort. Das ist ein Cache-Hit.
  7. Origin: Bei einem Miss holt der POP die Datei vom Storage. Der Header Cache-Control sagt, wie lange er sie behalten darf.
  8. Änderung: Ändert sich die Datei unter gleichem Namen, liefert das Edge die alte bis zum Ablauf. Lösung: neuer Name pro Version (z. B. app.3f9a.js) oder Purge (Invalidierung im CDN).

  1. Die Signatur ist ein HMAC: ein Hash über die Request-Felder mit einem geheimen Schlüssel. Nur der Server kennt den Schlüssel.
  2. Die URL ist öffentlich lesbar, aber nicht änderbar. Jede Änderung an Pfad, Rechten oder Ablaufzeit bricht die Signatur (Fälle 2, 3, 5).
  3. Die Ablaufzeit steht in der URL und ist mitsigniert. Nach 15 Minuten lehnt der Server ab (Fall 4).
  4. Der Storage braucht keinen Zustand: Er rechnet die Signatur nach. Darum kann man eine einzelne URL nicht gezielt widerrufen, nur den Schlüssel.
  5. Wer die URL hat, hat den Zugriff. Darum kurze Laufzeit, minimale Rechte, nur HTTPS.

4. Details, die Interviewer fragen

  1. Objekt-Modell: Bucket (S3) oder Container (Azure) enthält Objekte. Ein Objekt hat Key, Daten, Metadaten und ein ETag (Versionskennung). Der Namensraum ist flach. „Ordner“ sind nur Präfixe im Key.
  2. Unveränderliche Objekte: Man ändert kein Byte in der Mitte. Man ersetzt das ganze Objekt. Darum passt Object Storage für Dateien, nicht für Datenbanken.
  3. Konsistenz: S3 bietet seit Dezember 2020 Strong Read-after-Write für alle Operationen. Azure Blob ist ebenfalls stark konsistent. Ein CDN davor ist es nicht.
  4. Speicher-Tiers: Azure hat Hot, Cool, Cold und Archive. Je kälter, desto billiger der Speicher und teurer der Zugriff. Archive ist offline: Lesen braucht erst eine Rehydrierung (Stunden). Cool, Cold und Archive haben Mindest-Liegezeiten (30, 90, 180 Tage).
  5. Lifecycle Policies: Regeln verschieben Objekte nach Alter in kältere Tiers oder löschen sie. Beispiel: nach 30 Tagen Cool, nach 1 Jahr Archive, nach 10 Jahren löschen.
  6. Azure-SAS-Arten: Account SAS und Service SAS sind mit dem Account Key signiert. User Delegation SAS ist mit Microsoft-Entra-Anmeldedaten signiert. Microsoft empfiehlt die User Delegation SAS. Sie gilt höchstens 7 Tage.
  7. SAS widerrufen: Eine Service SAS kann an eine Stored Access Policy gebunden sein. Löscht man die Policy, ist die SAS ungültig. Sonst hilft nur Key-Rotation oder das Widerrufen der User Delegation Keys.
  8. S3 Presigned URL: mit Signature Version 4 signiert. Höchstens 7 Tage gültig. Mit temporären Credentials endet sie spätestens mit diesen.
  9. Multipart bei S3: Teile von 5 MiB bis 5 GiB, das letzte darf kleiner sein. Maximal 10 000 Teile. Objekte bis 50 TB (seit Dezember 2025, vorher 5 TB). Ein einzelnes PUT schafft bis 5 GB.
  10. Blocks bei Azure: Ein Block Blob besteht aus bis zu 50 000 Blöcken. Put Block lädt einen Block, Put Block List setzt die Datei zusammen. Nicht bestätigte Blöcke löscht Azure nach einer Woche.
  11. Abgebrochene Uploads: Bei S3 kosten nicht abgeschlossene Multipart-Uploads Speicher. Eine Lifecycle-Regel AbortIncompleteMultipartUpload räumt sie auf.
  12. Cache-Control (RFC 9111): max-age gilt für alle Caches, s-maxage nur für geteilte Caches wie CDNs. no-cache heisst: speichern, aber vor jeder Nutzung prüfen. no-store heisst: gar nicht speichern. private heisst: nur der Browser darf cachen.
  13. Revalidierung: Ist eine Kopie abgelaufen, fragt der Cache mit If-None-Match: <ETag> nach. Ist sie unverändert, antwortet der Origin 304 Not Modified ohne Body.
  14. Cache Key: Der Cache Key bestimmt, welche Requests dieselbe Kopie teilen. Meist URL plus ausgewählte Query-Parameter. Der Header Vary fügt Request-Header hinzu, z. B. Accept für WebP/AVIF.
  15. Versionierte Dateinamen: Ein Hash im Namen (app.3f9a.js) erlaubt max-age=31536000, immutable. Ein Deployment ändert den Namen, kein Purge nötig.
  16. Purge: Ein Purge löscht Kopien an allen POPs. Er dauert Minuten und ist bei manchen Anbietern pro Pfad kostenpflichtig. Er ist das Notfallwerkzeug, nicht der Normalfall.
  17. Bildauslieferung: Varianten (Thumbnail, mittel, gross) beim Upload erzeugen oder bei Bedarf durch einen Resize-Dienst hinter dem CDN. Moderne Formate (WebP, AVIF) über Accept und Vary. Im HTML srcset für passende Grössen.
  18. Privater Storage: Private Endpoints geben dem Storage eine private IP im VNet. Der öffentliche Zugang wird abgeschaltet. Front Door Premium erreicht so einen Origin über Private Link.

5. Vergleich

  • Object Storage: Dateien über HTTP, flach, billig, praktisch unbegrenzt. Kein Ändern in der Mitte.
  • Block Storage (Azure Managed Disk, EBS): eine Festplatte für eine VM. Schnell, änderbar, an einen Server gebunden.
  • File Storage (Azure Files, EFS): ein Netzlaufwerk mit Ordnern und Sperren (SMB, NFS). Für Altanwendungen und geteilte Ordner.
  • Datenbank: für kleine, strukturierte, abfragbare Daten. Nicht für grosse Dateien.
  • Azure Blob vs S3 vs MinIO: gleiches Modell. Blob nutzt SAS und Entra ID, S3 nutzt IAM und SigV4. MinIO spricht die S3-API und läuft selbst gehostet, z. B. in Kubernetes.
  • CDN-Produkte: Azure Front Door Standard/Premium ist das aktuelle Azure-CDN (CDN plus L7-Routing plus WAF). Dazu CloudFront, Cloudflare, Akamai.

6. In der Produktion

  1. Öffentlicher Container mit Patientendaten: Jemand stellt den Zugriff auf „public“. Lösung: anonymen Zugriff auf Account-Ebene verbieten, Private Endpoints, Azure Policy.
  2. SAS mit langer Laufzeit geleakt: Ein Jahr gültig, mit Account Key signiert. Lösung: User Delegation SAS, Minuten statt Monate, Key-Rotation, AllowSharedKeyAccess = false.
  3. Direkter Upload scheitert mit Private Endpoint: Der Client im Internet erreicht die private IP nicht. Lösung: Upload über einen Dienst im VNet oder über einen freigegebenen Eingang (z. B. Front Door Premium mit Private Link).
  4. Nutzer sehen alte Dateien: Gleicher Name, lange max-age. Lösung: versionierte Namen, kürzere TTL für HTML, Purge im Notfall.
  5. Private Antwort im CDN: Eine personalisierte Antwort ohne private wird für alle gecacht. Lösung: Cache-Control: private oder no-store, Auth-Pfade vom Caching ausnehmen.
  6. Kostenexplosion: Egress direkt aus dem Storage, abgebrochene Multipart-Uploads, Lesen aus Archive. Lösung: CDN, Lifecycle-Regeln, Tier-Planung.
  7. Upload-Abbrüche bei grossen Dateien: Ein PUT über 2 GB bricht im Mobilnetz ab. Lösung: Multipart mit Wiederaufnahme pro Teil.

7. Diagnose: Werkzeuge und Befehle

  • curl -I https://cdn.example.ch/app.js: zeigt Cache-Control, Age, ETag und den Cache-Status-Header des CDN (z. B. X-Cache: TCP_HIT bei Front Door).
  • Front Door Metriken: Byte Hit Ratio, Origin Request Count, Origin Latency, Access Logs mit Cache-Status.
  • Storage-Metriken: Transactions nach ResponseType (z. B. AuthorizationFailure), Egress, SuccessE2ELatency vs SuccessServerLatency.
  • Storage-Logs (Diagnostic Settings, S3 Server Access Logs, CloudTrail): wer hat mit welcher Auth-Art zugegriffen.
  • az storage blob list --account-name … --container-name … --auth-mode login: prüft Zugriff mit Entra ID statt Key.
  • aws s3api list-multipart-uploads --bucket …: zeigt offene, nie abgeschlossene Uploads.
  • nslookup <account>.blob.core.windows.net im VNet: muss die private IP des Private Endpoints liefern.

8. Senior-Punkte

  1. Bytes gehen nicht durch die API. Die API vergibt Rechte, der Storage trägt die Last.
  2. Kurzlebige, minimale Rechte: User Delegation SAS, nur ein Blob, nur write, Minuten. Ein geleakter Link schadet dann kaum.
  3. Hochgeladen ist nicht gleich sicher: Status „pending“, bis Scan und Prüfung fertig sind. Erst dann freigeben.
  4. Versionierte Namen statt Purge. Purge ist das Notfallwerkzeug.
  5. Cache-Header sind ein Vertrag zwischen Origin und allen Caches. Öffentlich, privat und Laufzeit bewusst pro Pfad setzen.
  6. Kosten mitdenken: Tier, Lifecycle, Egress und Transaktionen gehören ins Design, nicht erst in die Rechnung.

10. Fallen

  • „Object Storage hat Ordner.“ → Falsch. Der Namensraum ist flach. Ordner sind Präfixe im Key.
  • „Eine SAS-URL kann ich gezielt widerrufen.“ → Meist nicht. Nur über Stored Access Policy, Key-Rotation oder Widerruf der Delegation Keys.
  • „no-cache heisst: nicht cachen.“ → Falsch. Es heisst: vor Nutzung prüfen. Nicht speichern ist no-store.
  • „Das CDN ist konsistent mit dem Storage.“ → Falsch. Es liefert bis zum Ablauf der TTL die alte Kopie.
  • „Archive ist einfach billiger Speicher.“ → Lesen braucht Stunden und kostet. Dazu Mindest-Liegezeit von 180 Tagen.
  • „Ein Purge ist sofort weltweit wirksam.“ → Falsch. Er dauert, und Browser-Caches bleiben unberührt.

11. Fragen

Was ist Object Storage?

Ein Speicher für Dateien als Objekte mit Key, Daten und Metadaten, erreichbar über HTTP. Billig, praktisch unbegrenzt, flacher Namensraum.

Object Storage vs Block Storage vs File Storage?

Object: Dateien über HTTP, unveränderlich. Block: virtuelle Festplatte für eine VM. File: Netzlaufwerk mit Ordnern über SMB oder NFS.

Warum Dateien nicht in die Datenbank?

Grosse Binärdaten machen Backups, Replikation und Cache der DB teuer. Object Storage ist billiger und skaliert besser. Die DB hält nur Metadaten.

Was ist eine SAS?

Ein Shared Access Signature-Token in der URL. Es erlaubt begrenzten Zugriff auf Azure Storage: welche Ressource, welche Rechte, wie lange. Signiert mit Account Key oder Entra-Anmeldedaten.

Welche SAS-Arten gibt es?

Account SAS, Service SAS (beide mit Account Key) und User Delegation SAS (mit Entra ID). Microsoft empfiehlt die User Delegation SAS.

Wie widerrufen Sie eine SAS?

Service SAS über eine Stored Access Policy. Sonst Account Key rotieren oder User Delegation Keys widerrufen. Darum kurze Laufzeiten.

Was ist eine S3 Presigned URL?

Eine URL mit SigV4-Signatur und Ablaufzeit. Sie erlaubt eine bestimmte Operation auf ein Objekt ohne eigene AWS-Credentials. Höchstens 7 Tage gültig.

Warum lädt der Client direkt in den Storage?

Die API muss keine Bytes tragen. Uploads laufen parallel und skalieren mit dem Storage. Die API vergibt nur die Rechte.

Wie funktioniert Multipart Upload?

Upload starten, Teile parallel hochladen, dann abschliessen. S3: 5 MiB bis 5 GiB pro Teil, maximal 10 000 Teile. Azure: Put Block und Put Block List, bis 50 000 Blöcke.

Was passiert mit abgebrochenen Multipart-Uploads?

Bei S3 bleiben die Teile und kosten Speicher, bis man sie abbricht. Lifecycle-Regel AbortIncompleteMultipartUpload. Azure löscht unbestätigte Blöcke nach einer Woche.

Ist S3 konsistent?

Ja, seit Dezember 2020 mit Strong Read-after-Write für alle Operationen. Ein CDN davor ist es nicht.

Welche Access Tiers hat Azure Blob?

Hot, Cool, Cold, Archive. Je kälter, desto billiger der Speicher und teurer der Zugriff. Archive braucht Rehydrierung über Stunden.

Was ist ein CDN?

Ein Netz von Edge-Servern, die Kopien von Inhalten nahe beim Nutzer halten. Weniger Latenz, weniger Egress und weniger Last am Origin.

Was steuert, wie lange das CDN cacht?

Cache-Control vom Origin: max-age und s-maxage. Das CDN kann es per Regel überschreiben. Ohne Header gelten Standardwerte des Anbieters.

no-cache vs no-store?

no-cache: speichern, aber vor jeder Nutzung beim Origin prüfen. no-store: gar nicht speichern.

Was ist ein ETag und ein 304?

Das ETag kennzeichnet eine Version. Der Cache fragt mit If-None-Match. Ist die Version gleich, antwortet der Origin 304 ohne Body.

Wie invalidieren Sie Inhalte im CDN?

Am besten mit versionierten Dateinamen. Sonst per Purge für Pfade oder Wildcards. Purge dauert Minuten und erreicht keine Browser-Caches.

Was ist der Cache Key?

Die Teile eines Requests, die eine gecachte Kopie bestimmen: meist URL und gewählte Query-Parameter, dazu Header aus Vary.

Wie liefern Sie Bilder effizient aus?

Varianten in passenden Grössen, moderne Formate (WebP, AVIF) über Accept und Vary, srcset im HTML, lange TTL mit versionierten Namen, alles über das CDN.

Wie schützen Sie private Dateien hinter einem CDN?

Signierte URLs oder Tokens am Edge, kurze Laufzeit. Personalisierte Antworten mit Cache-Control: private. Origin nur über Private Link erreichbar.

Was bringen Private Endpoints für Storage?

Der Storage bekommt eine private IP im VNet, öffentlicher Zugang ist aus. Daten verlassen das private Netz nicht. Clients im Internet erreichen ihn dann nicht direkt.

Was ist MinIO?

Ein selbst gehosteter Object Storage mit S3-kompatibler API. Er läuft z. B. in Kubernetes. Code für S3 funktioniert damit meist ohne Änderung.

Szenario: Nach einem Deployment sehen manche Nutzer die alte JavaScript-Datei. Warum, und was tun Sie?

Gleicher Dateiname und lange max-age im CDN oder Browser. Kurzfristig Purge. Dauerhaft: Hash im Dateinamen, lange TTL mit immutable, HTML selbst kurz cachen.

Szenario: Patienten sollen PDFs bis 2 GB hochladen. Der Storage ist privat. Wie bauen Sie das?

API prüft Rechte und legt Metadaten an. Upload in Blöcken mit Wiederaufnahme, über einen Dienst im VNet oder einen Private-Link-Eingang. Danach Event, Virenscan, Status „bereit“. Download mit kurzlebiger User Delegation SAS.

Szenario: Die Storage-Rechnung hat sich verdreifacht. Wo suchen Sie?

Egress-Metriken (fehlt ein CDN?), Transaktionen (viele kleine Objekte?), offene Multipart-Uploads, falsches Tier, Lesen aus Archive, fehlende Lifecycle-Regeln.
