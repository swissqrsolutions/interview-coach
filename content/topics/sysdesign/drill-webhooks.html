Drill 1: Webhook-Dienst (Queue, Retry, DLQ)

1. Die Aufgabe

So stellt sie der Interviewer, wörtlich:

„Unsere Plattform soll Kunden per Webhook informieren: Bei Events wie payment.succeeded schicken wir einen HTTP-POST an eine URL, die der Kunde hinterlegt hat. Wir haben 5 Millionen Events pro Tag und rund 2'000 Kunden-Endpunkte. Manche Endpunkte sind langsam oder tagelang down. Kein Event darf verloren gehen, und unsere eigene API darf dadurch nicht langsamer werden — Annahme in p95 unter 200 ms. Design das."

20 Minuten: Löse die Aufgabe laut an einem leeren Blatt — Methode, Anforderungen, DB, API, Pseudo-Code, Diagramm, Trade-offs. Erst danach weiterlesen und vergleichen.

2. Schritt 1: Verstehen (die 5-Minuten-Methode angewendet)

Rückfragen mit plausiblen Interviewer-Antworten:

  1. „Wie gross ist ein Event?" — „JSON, rund 2 KB."
  2. „Dürfen Duplikate ankommen?" — „Ja, der Empfänger muss damit umgehen können." → at-least-once reicht.
  3. „Muss die Reihenfolge pro Kunde stimmen?" — „Nice to have, kein Muss."
  4. „Wie lange probieren wir es bei einem toten Endpunkt?" — „Etwa einen Tag, danach manuell." → Retry-Plan + DLQ (Dead-Letter Queue).
  5. „Spitzenlast?" — „Monatsabrechnung: kurzzeitig das Zehnfache."
  6. „Aufbewahrung der Events?" — „30 Tage, für Redelivery und Support."

Zahlen laut vorrechnen: 5 Mio ÷ ~100'000 s ≈ 60 QPS, Spitze ≈ 600 QPS. Speicher: 2 KB × 5 Mio = 10 GB/Tag, bei 30 Tagen Retention ~300 GB — passt in eine Postgres. Ausgehend: 60 bis 600 POSTs/s auf 2'000 Endpunkte, dazu Retries obendrauf.

Scope laut: „Ich baue Annahme, Persistenz, Zustellung mit Retry und DLQ. Endpunkt-Verwaltung nur als CRUD, kein Multi-Region. Ok?"

3. Anforderungen

Muss:

  • Event annehmen und dauerhaft speichern, bevor wir 200 antworten (p95 < 200 ms).
  • At-least-once-Zustellung: kein Event verloren, Duplikate erlaubt.
  • Retry mit Backoff (1m, 5m, 30m, 6h), danach DLQ mit manuellem Redelivery.
  • Signatur (HMAC) pro Request, damit der Kunde den Absender prüfen kann.
  • Ein langsamer Kunde darf andere Kunden nicht blockieren (Isolation).

Kann:

  • Strikte Reihenfolge pro Endpunkt; exactly-once; Live-Dashboard für Kunden; Multi-Region; Event-Filter pro Endpunkt.

4. DB-Design

CREATE TABLE endpoints (            -- 1 Zeile pro Kunden-URL
  id          uuid PRIMARY KEY,
  customer_id uuid NOT NULL,
  url         text NOT NULL,
  secret      text NOT NULL,        -- HMAC-Secret (aus Key Vault, hier nur Referenz)
  active      boolean NOT NULL DEFAULT true
);

CREATE TABLE events (               -- das angenommene Event, unveraenderlich
  id          uuid PRIMARY KEY,     -- = Idempotenz-Schluessel fuer den Empfaenger
  type        text  NOT NULL,       -- z.B. payment.succeeded
  payload     jsonb NOT NULL,       -- ~2 KB
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE deliveries (           -- 1 Zeile pro (Event, Endpunkt): der Zustell-Zustand
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id      uuid NOT NULL REFERENCES events(id),
  endpoint_id   uuid NOT NULL REFERENCES endpoints(id),
  status        text NOT NULL,      -- PENDING | OK | RETRY | DEAD
  attempts      int  NOT NULL DEFAULT 0,
  next_retry_at timestamptz,
  last_error    text
);

-- Index 1: der Scheduler fragt staendig "was ist jetzt faellig?"
CREATE INDEX idx_due ON deliveries (next_retry_at) WHERE status = 'RETRY';
-- Index 2: Kunden-Ansicht und Support: "alle Zustellungen dieses Endpunkts"
CREATE INDEX idx_ep  ON deliveries (endpoint_id, id DESC);
-- Index 3: DLQ-Uebersicht
CREATE INDEX idx_dead ON deliveries (status) WHERE status = 'DEAD';

Warum so: events ist unveränderliche Wahrheit (Replay jederzeit möglich). deliveries trägt den veränderlichen Zustand pro Ziel — Status und Zähler gehören nie ins Event. endpoints trennt Kunden-Konfiguration von Daten.

5. API

  • POST /v1/events — intern: Event annehmen, persistieren, 202 zurück.
  • POST /v1/endpoints — Kunde registriert URL, bekommt Secret einmalig zurück.
  • GET /v1/endpoints/{id}/deliveries?status=DEAD — Fehlerliste für Kunde/Support.
  • POST /v1/deliveries/{id}/redeliver — manuelles Redelivery aus der DLQ.
  • POST /v1/endpoints/{id}/ping — Test-Event senden (spart Support-Tickets).
  • DELETE /v1/endpoints/{id} — deaktivieren, offene Deliveries abbrechen.

6. Pseudo-Code an der Tafel

// --- Annahme (API, synchron, < 200 ms) ---
function annehmen(event):
  db.tx:
    events.insert(event)                      // 1. dauerhaft speichern
    for ep in aktiveEndpunkte(event.type):    // 2. Zustell-Auftraege anlegen
      deliveries.insert(event.id, ep.id, status=PENDING)
    outbox.insert(event.id)                   // 3. Outbox: gleiche Transaktion!
  return 202                                  // erst NACH Commit bestaetigen

// --- Outbox-Publisher (eigener Prozess) ---
loop:
  rows = outbox.leseOffen(limit=500)          // Polling, z.B. alle 200 ms
  queue.publish(rows, key=endpoint_id)        // Key: Reihenfolge pro Endpunkt
  outbox.markierePubliziert(rows)             // Broker down? Outbox puffert.

// --- Worker (Consumer Group, viele Instanzen) ---
function zustellen(delivery):
  sig = hmac(endpoint.secret, body + timestamp)
  resp = httpPost(endpoint.url, body,
                  headers={Webhook-Id: event.id, Signature: sig},
                  timeout=5s)                 // hartes Timeout, immer
  if resp.status in 200..299:
    delivery.status = OK
  else:
    delivery.attempts += 1
    plan = [1m, 5m, 30m, 6h]                  // Backoff-Stufen + Jitter
    if delivery.attempts <= 4:
      delivery.status = RETRY
      delivery.next_retry_at = now + plan[attempts-1] + zufall(0..30s)
    else:
      delivery.status = DEAD                  // DLQ: Mensch uebernimmt, Alarm
// Idempotenz: Webhook-Id ist immer dieselbe event.id —
// der Empfaenger dedupliziert damit; wir duerfen doppelt senden.

7. Architektur

Der Kernsatz dazu: „Die API schreibt nur in die DB und antwortet. Alles Langsame — fremde Endpunkte, Retries — passiert hinter der Queue, entkoppelt von der Annahme."

8. Der schwierige Teil als Bild: Retry, Backoff, DLQ

Warum diese Stufen: früh schnell (kurze Netz-Aussetzer heilen in Sekunden), spät selten (ein toter Server kommt nicht schneller zurück, nur weil du hämmerst). Jitter (Zufallsanteil) verhindert, dass tausende Retries im Gleichtakt feuern, wenn der Endpunkt zurückkommt.

9. Frontend kurz (Angular)

  • Komponenten: EndpointListComponent, DeliveryTableComponent (Filter: status), RedeliverButtonComponent.
  • State: ein Service mit Signals; Daten per REST, Polling alle 10 s — WebSocket lohnt sich für ein Admin-Dashboard nicht.
  • Redeliver: optimistisches Update vermeiden — Status erst nach Server-Antwort umschalten, sonst lügt die Tabelle.

10. Cloud (Azure)

  • AKS für Worker + API: ein Pool, horizontal skalierbar; App Service ginge für die API, aber Worker und API zusammen auf AKS halten das Deployment einheitlich.
  • Azure Service Bus statt selbst betriebenem Kafka: eingebaute Dead-Letter Queue und per-Message-Scheduling (scheduled delivery) passen exakt zu Retry/DLQ — bei 600 QPS brauchen wir Kafkas Durchsatz nicht. Event Hubs wäre für reines Hochvolumen-Streaming, hat aber kein per-Message-Retry.
  • Azure Database for PostgreSQL (managed): Backups, Patching, Replica per Klick — Betrieb ist hier nicht unser Geschäft.
  • Blob Storage: Events älter als 30 Tage als Archiv auslagern, DB bleibt klein.
  • Key Vault: HMAC-Secrets der Endpunkte — Secrets gehören nie als Klartext in die DB.
  • Azure Monitor: Alarm auf DLQ-Rate und Queue-Tiefe — die zwei Zahlen, die nachts wecken dürfen.

11. Trade-offs

  • At-least-once vs exactly-once → at-least-once, weil exactly-once über HTTP zu einem fremden System nicht garantierbar ist (Antwort kann nach Erfolg verloren gehen). Preis: Empfänger muss per Webhook-Id deduplizieren — das dokumentieren wir.
  • Outbox in der DB vs direkt in den Broker publizieren → Outbox, weil DB-Commit und Publish sonst auseinanderfallen können (Event gespeichert, Publish verloren — oder umgekehrt). Preis: Polling-Latenz (~Sekunden) und eine Tabelle mehr.
  • Push mit Retry vs Pull-API für Kunden → Push, weil das der Standard ist und Kunden keine Infrastruktur brauchen. Preis: wir tragen Retry-Komplexität; als Ergänzung bieten wir die Delivery-Liste als Pull-API für Abgleich an.
  • Service Bus (managed) vs eigenes Kafka → Service Bus, weil DLQ und Scheduling fertig sind und 600 QPS weit unter jeder Durchsatzgrenze liegen. Preis: Vendor-Lock-in und weniger Kontrolle über Partitionierung.
  • Gemeinsame Queue + Rate Limit pro Endpunkt vs eine Queue pro Kunde → gemeinsam, weil 2'000 Queues Betriebs-Chaos sind. Preis: Head-of-Line-Risiko — darum Timeout 5 s, Retries laufen über Scheduling (nicht blockierend) und max N parallele Sends pro Endpunkt.

12. Selbsttest: Folgefragen des Interviewers

„Wie viel Speicher braucht ein Jahr Events?"

2 KB × 5 Mio × 365 ≈ 3,7 TB pro Jahr. Darum Retention 30 Tage in der DB (~300 GB) und Archiv in Blob Storage — dort kostet 1 TB wenige Franken pro Monat.

„Ein grosser Kunde ist 6 Stunden down. Was passiert bei euch?"

Seine Deliveries laufen in RETRY und warten per next_retry_at — sie liegen in der DB, nicht im Speicher. Queue-Tiefe und Worker bleiben normal, andere Kunden merken nichts. Nach Rückkehr verteilt der Jitter die Nachlieferung.

„Was geht kaputt, wenn der Worker den Offset vor dem HTTP-POST committet?"

Stirbt der Worker zwischen Commit und POST, ist die Nachricht aus Sicht des Brokers erledigt — das Event wird nie zugestellt und verletzt „kein Verlust". Regel: erst Arbeit abschliessen (oder Retry-Zustand persistieren), dann Offset committen. Das macht die Verarbeitung at-least-once.

„Warum ist eure Zustellung trotzdem nur at-least-once?"

Der POST kann beim Kunden ankommen, aber die 200-Antwort geht im Netz verloren — wir müssen wiederholen, der Kunde sieht das Event doppelt. Das ist prinzipbedingt bei HTTP ohne gemeinsame Transaktion. Lösung: stabile Webhook-Id, Empfänger dedupliziert.

„Wonach wählt ihr den Partition Key, und was wäre falsch?"

endpoint_id: gleiche Partition = Reihenfolge pro Endpunkt bleibt grob erhalten, Last verteilt sich über 2'000 Endpunkte. Falsch wäre customer_id eines Riesen-Kunden als Hotspot oder gar kein Key (Round-Robin): dann ist jede Reihenfolge weg.

„Wie skaliert der Worker-Pool — und wo ist die Grenze?"

Worker sind eine Consumer Group: jede Partition wird von genau einem Consumer der Gruppe gelesen. Mehr Worker als Partitionen bringen nichts — die Parallelität ist durch die Partitionszahl gedeckelt. Darum Partitionen von Anfang an grosszügig wählen (z. B. 32).

„×10: 50 Mio Events/Tag. Was ändert ihr?"

600 QPS Durchschnitt, 6'000 Spitze: API-Pods und Worker horizontal hoch, Partitionen prüfen, DB-Schreiblast über Batch-Inserts bündeln; 100 GB/Tag → Retention in der DB auf 7 Tage senken, Rest nur noch Blob. Architektur bleibt gleich — das sage ich laut, denn genau dafür war die Queue da.

„Sicherheitsfrage: Der Kunde trägt http://10.0.0.5/admin als URL ein."

Das ist SSRF (Server-Side Request Forgery): unser Worker würde ins eigene interne Netz posten. Abwehr: URL-Validierung (nur https, keine privaten IP-Bereiche, DNS-Auflösung prüfen) und Egress über einen Proxy ohne Route ins interne Netz.

„Wie prüft der Kunde, dass der Webhook echt ist?"

Wir signieren timestamp + body mit HMAC und seinem Secret und senden Signatur + Timestamp im Header. Er rechnet die Signatur nach und verwirft Requests mit altem Timestamp (z. B. > 5 min) — das blockt Fälschung und Replay.

„Was ist eine Poison Message, und was tut ihr dagegen?"

Eine Nachricht, deren Verarbeitung immer crasht (z. B. kaputtes JSON) — ohne Schutz blockiert sie ihre Partition für immer. Darum: Fehler fangen, attempts zählen, nach Limit in DEAD schieben und den Offset trotzdem committen. Die Partition läuft weiter.

„Endpunkt kommt nach 6 h zurück, 50'000 offene Deliveries. Zerlegt ihr ihn?"

Ohne Schutz ja — Thundering Herd. Zwei Bremsen: Jitter verteilt die fälligen Retries, und pro Endpunkt gilt ein Sende-Limit (z. B. 50 parallel / Token Bucket). Lieber in 10 Minuten nachliefern als den Kunden erneut umwerfen.

„Postgres ist down. Was passiert mit eurem p95 < 200 ms?"

Die Annahme schlägt fehl — wir antworten schnell mit 503 statt zu hängen (Timeout auf dem DB-Call). Der Produzent muss retryen können; „annehmen ohne zu persistieren" wäre schlimmer, denn eine 202 wäre dann eine Lüge. Gegenmassnahme: HA-Postgres mit Failover.

„Warum pollt der Outbox-Publisher? Ist das nicht hässlich?"

Polling alle 200 ms ist simpel, crash-sicher und bei 60 QPS völlig ausreichend (Latenz < 1 s). Die Alternativen (DB-Trigger, Change Data Capture) sind mehr Betrieb. Senior-Antwort: „Hässlich, aber korrekt und billig — CDC rüste ich nach, wenn die Latenz je stört."

„Wie merkt ihr, dass das System insgesamt kippt?"

Drei Metriken mit Alarm: Queue-Tiefe (wächst = Worker kommen nicht nach), DLQ-Rate (springt = Bug oder grosser Kunde tot), Alter des ältesten unpublizierten Outbox-Eintrags (wächst = Publisher hängt). Dazu p95 der Ingest-API.

„Der Kunde sagt: Ich habe Event X nie bekommen. Wie beweist ihr das Gegenteil?"

deliveries hält pro Versuch Status, Zeitpunkt und last_error; dazu loggen wir den Antwort-Status des Kunden. Support-Antwort in einer Query: „5 Versuche, dein Server gab 500, hier die Zeiten — Redelivery-Knopf ist im Dashboard."

„Braucht die Reihenfolge-Garantie den Retry-Pfad nicht kaputt zu machen?"

Doch, genau das tut sie: Event 2 kann gelingen, während Event 1 im Retry hängt — Reihenfolge weg. Strikte Ordnung pro Endpunkt hiesse: bei Fehler alles für diesen Endpunkt anhalten. Das war als „Kann" eingestuft; genau deshalb klärt man es in Minute 4 und nicht in Minute 40.

Typische Fehler bei genau dieser Aufgabe:

  • Synchron zustellen: API ruft den Kunden-Endpunkt direkt auf — ein langsamer Kunde macht eure API langsam. Die 200-ms-Anforderung ist dann unhaltbar.
  • Retry im RAM: Worker-Neustart = alle wartenden Retries weg = Events verloren. Retry-Zustand gehört in die DB.
  • Exactly-once versprechen: Über fremdes HTTP nicht möglich — wer es verspricht, bekommt die Folgefrage und fällt.
  • DLQ vergessen: Ohne Endzustand retryt ihr tote Endpunkte ewig und niemand merkt es. DLQ + Alarm + Redelivery-API gehören zur Antwort.
  • SSRF nie erwähnen: Vom Kunden kontrollierte URLs sind die klassische Sicherheitsfalle dieser Aufgabe.
