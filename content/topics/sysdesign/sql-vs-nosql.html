SQL vs NoSQL

Kern: SQL vs NoSQL ist die Wahl des Datenmodells für einen Service. Relationale Datenbanken bieten Schema, Joins und ACID-Transaktionen. NoSQL-Datenbanken (Document, Key-Value, Wide-Column, Graph) tauschen davon etwas gegen einfache horizontale Skalierung oder ein passenderes Modell. Die Entscheidung folgt den Zugriffsmustern, nicht dem Trend.

1. Wo sitzt die Datenbank?

  1. Service: Der Service kennt seine Zugriffsmuster, also welche Queries wie oft laufen.
  2. Relational: Daten liegen normalisiert in Tabellen, also ohne Duplikate. Joins verbinden sie beim Lesen.
  3. Document: Ein Objekt liegt als ein JSON-Dokument, inklusive verschachtelter Teile. Ein Read holt alles auf einmal.
  4. Key-Value: Die Datenbank kennt nur Schlüssel und Wert. Sie sucht nichts im Wert.
  5. Wide-Column: Der Partition Key wählt den Knoten, der Clustering Key sortiert die Zeilen darin.
  6. Graph: Knoten sind Objekte, Kanten sind Beziehungen. Queries laufen Kanten entlang.

2. Die Reise einer Entscheidung (die Geschichte zum Merken)

  1. Zugriffsmuster aufschreiben. Welche Queries laufen? Wie viele Reads und Writes pro Sekunde? Wie gross wird der Datenbestand?
  2. Invarianten prüfen. Eine Invariante ist eine Regel, die immer gelten muss, z. B. „Kontostand ≥ 0“. Betrifft sie mehrere Objekte, braucht es eine Transaktion. Dann ist PostgreSQL die Standardwahl.
  3. Form der Daten. Ein Objekt mit Unterteilen ist ein Baum, z. B. eine Bestellung mit Positionen. Ein Baum passt in ein Dokument oder eine JSONB-Spalte. Viele-zu-viele-Beziehungen und Pfade passen in einen Graph.
  4. Skalierung. Reicht ein grosser Knoten plus Read Replicas, bleibt man relational. Nur wenn Writes oder Daten über einen Knoten wachsen, lohnt ein verteiltes NoSQL-System.
  5. Mehrere Speicher sind normal. Das heisst Polyglot Persistence: PostgreSQL als Wahrheit, Redis als Cache, ein Suchindex für Volltext.

3. Beispiel: Transaktion und Dokument in einer Datenbank

CREATE TABLE account(id TEXT PRIMARY KEY, balance INT NOT NULL CHECK (balance >= 0));
CREATE TABLE orders(id INT PRIMARY KEY, doc TEXT NOT NULL);   -- JSON-Dokument

with db:   # eine ACID-Transaktion
    db.execute("UPDATE account SET balance = balance + ? WHERE id = ?", (amount, dst))
    db.execute("UPDATE account SET balance = balance - ? WHERE id = ?", (amount, src))

# Dokumente: {"customer":"anna","items":[{"sku":"A1","qty":2},...],"total":59.0}
SELECT id, json_extract(doc,'$.customer'), json_array_length(doc,'$.items'),
       json_extract(doc,'$.total'), json_extract(doc,'$.coupon') FROM orders;
SELECT o.id, json_extract(i.value,'$.qty') FROM orders o, json_each(o.doc,'$.items') i
 WHERE json_extract(i.value,'$.sku') = 'A1';
1) relational: transaction + constraint
   transfer 30: ok
   balances: [('anna', 70), ('ben', 30)]
   transfer 500: rollback (CHECK constraint failed: balance >= 0)
   balances: [('anna', 70), ('ben', 30)]
2) document in JSON column: schema on read
   (1, 'anna', 2, 59.0, None)
   (2, 'ben', 1, 19.5, 'WINTER')
   (3, 'cara', 0, None, None)
3) query inside the document: orders containing sku A1
   [(1, 2), (2, 1)]

Echte Ausgabe, Python 3.12 mit sqlite3 (SQLite 3.49), Simulation. SQLite steht hier für eine relationale Datenbank mit JSON-Funktionen. In PostgreSQL heisst das JSONB mit ->> und @>.

  1. Beim Transfer von 500 bekommt ben zuerst +500. Danach verletzt anna den CHECK. Die Transaktion rollt beide Updates zurück. Das ist Atomicity.
  2. Die Regel „Kontostand ≥ 0“ prüft die Datenbank selbst. Das ist Schema-on-Write: Falsche Daten kommen gar nicht hinein.
  3. Das Dokument von cara hat kein total. Niemand stoppt den Write. Das ist Schema-on-Read: Der lesende Code muss fehlende Felder behandeln.
  4. Query 3 sucht im Dokument. Eine relationale Datenbank mit JSON-Spalte kann also beides: Transaktionen und flexible Dokumente.

4. Details, die Interviewer fragen

  1. ACID: Atomicity heisst alles oder nichts. Consistency heisst, Invarianten gelten nach der Transaktion. Isolation heisst, parallele Transaktionen stören sich nicht. Durability heisst, ein Commit überlebt einen Absturz.
  2. Isolation Levels: PostgreSQL nutzt standardmässig Read Committed. Repeatable Read liefert einen festen Snapshot. Serializable verhindert alle Anomalien, kann aber Transaktionen abbrechen. Dann muss die Anwendung wiederholen.
  3. BASE: Basically Available, Soft state, Eventually consistent beschreibt viele NoSQL-Systeme. Der Begriff ist unscharf. Besser konkret fragen: Welche Konsistenz pro Operation?
  4. Schema-on-Write vs Schema-on-Read: Bei Schema-on-Write prüft die Datenbank die Struktur beim Schreiben. Bei Schema-on-Read interpretiert der Code die Struktur beim Lesen. Ein Schema gibt es also immer, nur an anderer Stelle.
  5. Normalisierung vs Denormalisierung: Normalisiert heisst, jede Information steht einmal. Denormalisiert heisst, Daten werden kopiert, damit ein Read schneller ist. Preis: Jede Kopie muss bei Änderungen nachgezogen werden.
  6. Locality: Ein Dokument liegt zusammen auf der Platte. Ein Read holt das ganze Objekt ohne Join. Bei kleinen Änderungen wird aber oft das ganze Dokument neu geschrieben.
  7. Joins in NoSQL: Viele Document Stores können nur schwach joinen. Die Anwendung joint dann selbst. Das führt schnell zu N+1-Queries, also einer Query pro Zeile.
  8. Transaktionen in NoSQL: MongoDB kann Multi-Document-Transaktionen, aber mit Kosten. Cosmos DB macht Transaktionen nur innerhalb einer logischen Partition. Cassandra bietet nur Lightweight Transactions (Compare-and-Set über Paxos) pro Partition.
  9. Skalierung: Relationale Datenbanken skalieren zuerst vertikal (grösserer Knoten) und mit Read Replicas. Wide-Column- und Key-Value-Systeme sind von Anfang an auf horizontale Verteilung per Partition Key gebaut.
  10. Partition Key: Der Partition Key bestimmt, auf welchem Knoten ein Datensatz liegt. Er muss Last gleichmässig verteilen und die häufigsten Queries auf eine Partition begrenzen.
  11. Wide-Column-Modellierung: In Cassandra modelliert man pro Query eine Tabelle. Die Daten werden dafür dupliziert. Ad-hoc-Queries sind teuer oder verboten.
  12. LSM-Tree vs B-Tree: Ein LSM-Tree (Log-Structured Merge-Tree) schreibt sequenziell und mischt später. Gut für viele Writes, z. B. Cassandra. Ein B-Tree ändert Seiten an Ort und Stelle. Gut für Reads, z. B. PostgreSQL.
  13. JSONB in PostgreSQL: JSONB speichert JSON binär und zerlegt. Ein GIN-Index beschleunigt @> (enthält) und Schlüssel-Suchen. jsonb_path_ops ist kleiner und schneller, unterstützt aber weniger Operatoren.
  14. json vs jsonb: json speichert den Text genau so, wie er kam. jsonb entfernt doppelte Schlüssel (der letzte gewinnt) und behält die Schlüssel-Reihenfolge nicht. jsonb ist fast immer die richtige Wahl.
  15. Grenzen von JSONB: Ein Update schreibt den ganzen JSONB-Wert neu. Der Planner hat keine Statistik über Felder im Dokument. Häufig gefilterte Felder gehören darum in eigene Spalten.
  16. NewSQL: NewSQL-Systeme wie Spanner, CockroachDB oder YugabyteDB bieten SQL und ACID über viele Knoten. Preis: höhere Write-Latenz durch Konsens über Knoten.

5. Vergleich

  • Relational (PostgreSQL, Azure SQL): Joins, ACID, Ad-hoc-Queries, festes Schema. Skaliert vertikal plus Read Replicas. Sharding nur mit Zusatz, z. B. Citus.
  • Document (MongoDB, Cosmos DB for NoSQL): flexible JSON-Dokumente, gute Locality. Schwach bei Joins und Viele-zu-viele-Beziehungen.
  • Key-Value (Redis, DynamoDB): sehr schnelle Lookups per Schlüssel. Keine Queries über Werte, ausser mit Zusatzindex.
  • Wide-Column (Cassandra, HBase, Bigtable): sehr hohe Schreiblast, lineare Skalierung, Multi-Datacenter. Modell folgt den Queries, keine Joins.
  • Graph (Neo4j, Cosmos DB for Apache Gremlin): Pfade und Beziehungen über viele Ebenen. Schwach bei grossen Aggregationen.
  • PostgreSQL mit JSONB: Mittelweg. Feste Kernfelder als Spalten, variable Felder als JSONB. Ein System, eine Transaktion.
  • NewSQL (Spanner, CockroachDB): SQL und ACID verteilt. Höhere Latenz und Kosten.

6. In der Produktion

  1. Hot Partition in Cosmos DB: Ein schlechter Partition Key schickt die meiste Last auf eine Partition. Cosmos DB antwortet mit HTTP 429 (zu viele Request Units). Lösung: Partition Key mit hoher Kardinalität, z. B. tenantId plus userId als Hierarchical Partition Key.
  2. Dokument wächst ohne Grenze: Ein Array im Dokument wächst mit jedem Event. MongoDB erlaubt max. 16 MB pro Dokument. Lösung: wachsende Listen als eigene Dokumente oder Tabelle.
  3. Schema-Drift: Alte Dokumente haben alte Felder. Der Code bricht bei fehlenden Feldern. Lösung: Schema-Version im Dokument und tolerantes Lesen.
  4. JSONB ohne Index: Eine Query auf ein JSONB-Feld macht einen Seq Scan über die ganze Tabelle. Lösung: GIN-Index oder Expression-Index, z. B. CREATE INDEX ON t ((doc->>'status')).
  5. NoSQL gewählt, Joins gebraucht: Die Anwendung joint selbst mit vielen Requests. Latenz steigt stark. Lösung: Denormalisieren oder zurück zu relational.
  6. Grosse Partitionen in Cassandra: Eine Partition mit Millionen Zeilen macht Reads und Compaction langsam. Lösung: Zeit-Bucket in den Partition Key, z. B. (sensor_id, day).

7. Diagnose: Werkzeuge und Befehle

  • EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL: zeigt Seq Scan vs Index Scan und echte Zeiten.
  • pg_stat_statements: Extension, die die teuersten Queries nach Gesamtzeit zeigt.
  • Cosmos DB: Header x-ms-request-charge zeigt die Request Units pro Operation. Azure Monitor zeigt 429-Raten und Normalized RU Consumption pro Partition.
  • MongoDB: db.coll.find(...).explain("executionStats") zeigt COLLSCAN vs IXSCAN.
  • Cassandra: nodetool tablestats zeigt maximale Partitionsgrösse. TRACING ON in cqlsh zeigt den Weg einer Query.
  • Redis: SLOWLOG GET zeigt langsame Befehle, redis-cli --bigkeys zeigt sehr grosse Schlüssel.

8. Senior-Punkte

  1. Start mit PostgreSQL, solange es keinen konkreten Grund dagegen gibt. Ein Knoten trägt viel mehr als die meisten Systeme brauchen.
  2. Erst die Queries, dann das Modell. Bei NoSQL ist das Pflicht, bei SQL gute Praxis.
  3. „Schemaless“ gibt es nicht. Das Schema wandert nur in den Code. Dort muss es versioniert und getestet werden.
  4. Transaktionsgrenze = Partitionsgrenze. In verteilten NoSQL-Systemen gibt es günstige Transaktionen nur innerhalb einer Partition. Das prägt den Partition Key.
  5. Polyglot Persistence kostet Betrieb. Jede zusätzliche Datenbank braucht Backups, Monitoring und Wissen im Team.
  6. JSONB für Variabilität, Spalten für Abfragen. Felder in WHERE, JOIN oder Constraints gehören in Spalten.

10. Fallen

  • „NoSQL skaliert, SQL nicht.“ → Falsch. PostgreSQL trägt mit Read Replicas und Partitionierung sehr viel. NoSQL skaliert nur mit gutem Partition Key.
  • „NoSQL hat kein Schema.“ → Falsch. Das Schema liegt im lesenden Code (Schema-on-Read).
  • „NoSQL kann keine Transaktionen.“ → Zu pauschal. MongoDB kann Multi-Document-Transaktionen, Cosmos DB innerhalb einer Partition.
  • „Für JSON-Daten brauche ich MongoDB.“ → Nicht unbedingt. PostgreSQL JSONB mit GIN-Index reicht oft.
  • „Das C in ACID ist das C in CAP.“ → Falsch. ACID-C heisst Invarianten. CAP-C heisst Linearizability.

11. Fragen

Was ist der Hauptunterschied zwischen SQL und NoSQL?

SQL-Datenbanken haben ein festes Schema, Joins und ACID-Transaktionen. NoSQL-Datenbanken haben andere Modelle (Document, Key-Value, Wide-Column, Graph) und skalieren oft einfacher horizontal. Dafür sind Joins und Transaktionen eingeschränkt.

Welche NoSQL-Arten gibt es?

Document (MongoDB, Cosmos DB), Key-Value (Redis, DynamoDB), Wide-Column (Cassandra, HBase), Graph (Neo4j).

Wann wählen Sie eine relationale Datenbank?

Bei Beziehungen zwischen Objekten, Invarianten über mehrere Zeilen, Ad-hoc-Queries und Reporting. Also bei den meisten Business-Anwendungen.

Wann wählen Sie einen Document Store?

Wenn Objekte Bäume sind, meist ganz gelesen werden und die Struktur variiert. Beispiel: Produktkatalog mit unterschiedlichen Attributen.

Wann wählen Sie Key-Value?

Wenn nur per Schlüssel gelesen und geschrieben wird, mit sehr kleiner Latenz. Beispiele: Session, Cache, Feature Flags.

Wann wählen Sie Wide-Column?

Bei sehr hoher Schreiblast und bekannten Queries, z. B. Zeitreihen, Events, IoT. Oft über mehrere Rechenzentren.

Wann wählen Sie eine Graph-Datenbank?

Wenn Queries Pfade über viele Ebenen gehen. Beispiele: Betrugserkennung, Empfehlungen, Netzwerk-Topologie.

Was bedeutet ACID?

Atomicity (alles oder nichts), Consistency (Invarianten gelten), Isolation (parallele Transaktionen stören sich nicht), Durability (Commit überlebt Absturz).

Was ist BASE?

Basically Available, Soft state, Eventually consistent. Ein grobes Gegenstück zu ACID für viele verteilte NoSQL-Systeme.

Schema-on-Write vs Schema-on-Read?

Schema-on-Write prüft beim Schreiben in der Datenbank. Schema-on-Read interpretiert beim Lesen im Code. Ein Schema gibt es in beiden Fällen.

Was ist Denormalisierung und was kostet sie?

Daten werden kopiert, damit Reads ohne Join auskommen. Kosten: mehr Speicher und jede Kopie muss bei Änderungen aktualisiert werden.

Warum sind Joins in Document Stores ein Problem?

Die Datenbank kann sie schlecht oder gar nicht. Die Anwendung joint selbst, oft mit vielen Requests (N+1).

Können NoSQL-Datenbanken Transaktionen?

Teilweise. MongoDB über mehrere Dokumente, Cosmos DB innerhalb einer logischen Partition, Cassandra nur Lightweight Transactions pro Partition.

Wie skaliert eine relationale Datenbank?

Zuerst vertikal, dann Read Replicas für Reads. Für Writes: Partitionierung oder Sharding, z. B. mit Citus oder per Tenant.

Was ist ein Partition Key und wie wählen Sie ihn?

Er bestimmt den Knoten eines Datensatzes. Er braucht hohe Kardinalität, gleichmässige Last und muss in den häufigsten Queries vorkommen.

Was ist JSONB?

Ein binärer JSON-Typ in PostgreSQL. Er ist schnell zu lesen und mit GIN indexierbar. Doppelte Schlüssel und Reihenfolge gehen verloren.

Wann JSONB, wann eigene Spalten?

JSONB für variable, selten gefilterte Felder. Spalten für Felder in WHERE, JOIN, Constraints und Sortierung.

Welchen Index nutzen Sie für JSONB?

GIN für Containment (@>) und Schlüssel-Suche. Für ein einzelnes Feld einen B-Tree-Expression-Index, z. B. auf (doc->>'status').

LSM-Tree vs B-Tree?

LSM-Tree schreibt sequenziell und ist gut für viele Writes. B-Tree ändert Seiten direkt und ist gut für Reads und Range Scans.

Was ist NewSQL?

Verteilte Datenbanken mit SQL und ACID über viele Knoten, z. B. Spanner, CockroachDB. Preis: höhere Write-Latenz durch Konsens.

Was ist Polyglot Persistence?

Mehrere Datenbanktypen in einem System, je nach Aufgabe. Beispiel: PostgreSQL als Wahrheit, Redis als Cache, Suchindex für Volltext.

Ist das C in ACID das gleiche wie in CAP?

Nein. ACID-C heisst, Invarianten gelten. CAP-C heisst Linearizability, also jeder Read sieht den neuesten Write.

Szenario: Ein Shop mit Bestellungen, Zahlungen und Lagerbestand. Welche Datenbank?

PostgreSQL. Bestellung, Zahlung und Lagerabbau brauchen eine Transaktion und Constraints. Variable Produktattribute als JSONB, Warenkorb eventuell in Redis.

Szenario: Cosmos DB liefert viele 429-Fehler, obwohl die gesamte RU-Kapazität nicht ausgelastet ist. Warum?

Eine Hot Partition. Ein Partition Key hat zu viel Last, die anderen sind leer. Prüfen: Normalized RU Consumption pro Partition. Lösung: Partition Key mit höherer Kardinalität oder Hierarchical Partition Key.

Szenario: 50 000 Sensoren schreiben jede Sekunde einen Messwert. Abfragen sind immer „Sensor X, Zeitraum Y“. Welche Datenbank?

Wide-Column wie Cassandra mit Partition Key (sensor_id, Tag) und Clustering nach Zeit. Alternative: PostgreSQL mit TimescaleDB oder Zeit-Partitionierung, wenn ein Knoten reicht.
