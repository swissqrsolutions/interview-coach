Übung: Schwache Designs erklären und verbessern

So funktioniert diese Seite: Du siehst 4 Architektur-Diagramme. Jedes Design funktioniert heute — und ist trotzdem schwach. Genau so eine Aufgabe kommt im Interview: „Hier ist ein Design. Was ist das Problem? Was würdest du ändern?"

Dein Ablauf pro Diagramm (laut sprechen, 60–90 Sekunden):

  1. Beobachtung: „Ich sehe, dass …"
  2. Mechanismus: „Das ist ein Problem, weil …"
  3. Folge mit Zahl: „Bei X Nutzern / wenn Y ausfällt passiert …"
  4. Senior-Fix: „Ich würde … ändern. Der Trade-off ist …"

Erst sprechen, dann die Antworten öffnen.

1. Die Checkliste für jedes Diagramm

Ein Senior sucht immer in derselben Reihenfolge:

  • SPOF: Welche Box darf nicht ausfallen? Was passiert dann?
  • Zustand (State): Wo liegen Sessions, Dateien, Caches? Kann ich die App-Knoten verdoppeln?
  • Synchrone Ketten: Wer wartet auf wen? Latenzen addieren sich, Verfügbarkeiten multiplizieren sich.
  • Datenverlust: Wo sind die Backups? Liegen sie auf derselben Platte/Region? Wurde Restore je getestet?
  • Lastspitzen: Was bremst 10× Traffic? Gibt es Queue, Rate Limit, Backpressure?
  • Nebenläufigkeit: Wo ist Read-then-Write ohne Lock oder atomares Update?

Und er sagt immer einen Trade-off: jede Verbesserung kostet Geld, Komplexität oder Konsistenz.

2. Übung 1: Der Webshop auf einem Server

Ein kleiner Webshop. Alles läuft auf einer virtuellen Maschine. Die Sessions liegen im RAM der App, Produktbilder auf der lokalen Platte, das Backup schreibt ein Cron-Job — auf dieselbe Platte.

Deine Aufgabe: Nenne mindestens 4 Schwächen mit Begründung. Dann: Wie sieht die Senior-Version aus — und wann wäre dieses einfache Design trotzdem okay?
Lösung: Was ist schwach?
  • SPOF: Eine VM. Stirbt sie (Hardware, Kernel-Update, volle Platte), ist alles weg: Shop, Datenbank, Bilder.
  • Backup auf derselben Platte: Das ist kein Backup. Platte kaputt = Daten und Backup kaputt. Restore wurde nie getestet.
  • Sessions im RAM: Jeder Neustart loggt alle Nutzer aus. Und eine zweite App-Instanz ist unmöglich, weil die Session nur auf Server 1 existiert.
  • Bilder auf lokaler Platte: gleiches Problem — Knoten 2 hätte die Dateien nicht.
  • Deploy = 2 Minuten Downtime, und DB und App teilen sich CPU/RAM: ein langsames SQL bremst den ganzen Shop.
Senior-Lösung: besseres Design

Ziel: App-Knoten zustandslos machen, Zustand auslagern, Daten doppelt sichern.

  • Load Balancer → 2+ App-Knoten ohne Zustand. Sessions in Redis oder als signiertes Cookie/JWT.
  • Bilder in Object Storage (S3-kompatibel), davor ein CDN.
  • PostgreSQL getrennt (managed oder eigene VM) mit Replica; WAL-Backups in eine andere Region; Restore vierteljährlich testen.
  • Deploy rolling oder blue-green → keine Downtime.

Trade-off: Mehr Teile, mehr Kosten (~3–5 VMs statt 1), mehr Betrieb. Senior-Satz: „Bis ein paar tausend Nutzer trägt eine VM — aber Offsite-Backup und getestetes Restore sind ab Tag 1 Pflicht, denn das kostet fast nichts."

Folgefrage: Warum ist das Backup das schlimmste Problem — schlimmer als der SPOF?

Ausfall kostet Stunden, Datenverlust ist endgültig. Ein toter Server ist in 1–2 h neu aufgebaut, wenn die Daten existieren. Ohne Offsite-Backup kann ein einziger Plattendefekt die Firma beenden. Darum: erst Datensicherheit, dann Verfügbarkeit.

Was geht kaputt, wenn man einfach eine 2. VM mit der gleichen App danebenstellt?

Logins funktionieren nur zufällig: Die Session liegt im RAM von Knoten 1; landet der nächste Request auf Knoten 2, ist der Nutzer ausgeloggt. Hochgeladene Bilder erscheinen nur auf einem Knoten. Und zwei Apps schreiben in eine lokale DB auf VM 1 — die bleibt SPOF. Zustand zuerst auslagern, dann skalieren.

3. Übung 2: Die synchrone Kette im Checkout

Ein Checkout ruft vier Services nacheinander per REST auf — ohne Timeouts. Erst wenn alle geantwortet haben, bekommt der Kunde „Bestellt ✓".

Deine Aufgabe: Welche zwei Rechnungen zeigen das Problem? Welche Aufrufe müssen synchron bleiben, welche nicht — und warum?
Lösung: Was ist schwach?
  • Latenz addiert sich: 300 + 200 + 800 + 400 ms = 1,7 s im besten Fall — die langsame E-Mail bremst das Bezahlen.
  • Verfügbarkeit multipliziert sich: 4 Services mit je 99 % ⇒ 0,99⁴ ≈ 96 %. Der Checkout fällt aus, wenn irgendeiner ausfällt — auch der unwichtige.
  • Kein Timeout: Hängt die E-Mail, hängt der Thread im Checkout. Viele hängende Threads = Thread-Pool voll = ganzer Service steht.
  • Retry-Gefahr: Klickt der Kunde nochmal, wird ohne Idempotenz doppelt bezahlt.
Senior-Lösung: besseres Design
  • Kritischer Pfad bleibt synchron, mehr nicht: Payment und Inventory — mit Timeout (z. B. 500 ms), kleinem Retry-Budget und Circuit Breaker.
  • E-Mail und Treuepunkte werden Events: Checkout schreibt „OrderPlaced" in eine Queue (Outbox-Pattern, damit DB-Commit und Event zusammen passieren). Die Services lesen asynchron.
  • Idempotency-Key vom Client: derselbe Klick erzeugt nie zwei Bestellungen.

Ergebnis: Antwortzeit ~0,6 s statt 1,7 s; E-Mail-Ausfall verliert keine Bestellung mehr. Trade-off: E-Mail kommt eventual consistent — ein paar Sekunden später ist hier völlig okay.

Folgefrage: Warum reicht „Timeout überall" allein nicht?

Ein Timeout beendet nur das Warten — die Bestellung ist dann trotzdem fehlgeschlagen, obwohl nur die unwichtige E-Mail klemmte. Die eigentliche Korrektur ist Entkopplung: Unkritisches gehört aus dem kritischen Pfad heraus. Timeout + Retry + Circuit Breaker schützen den Rest.

Was geht kaputt, wenn Payment einen Retry ohne Idempotenz bekommt?

Request 1 bucht ab, die Antwort geht verloren (Netz), Retry bucht nochmal ab: doppelte Abbuchung. Darum sendet der Checkout einen Idempotency-Key; Payment speichert „Key → Ergebnis" und gibt beim zweiten Mal dasselbe Ergebnis zurück, ohne neu zu buchen.

4. Übung 3: Der 24-Stunden-Cache

Eine Produkt-API cached in Redis. Geschrieben wird direkt in PostgreSQL — am Cache vorbei. Sessions und Produkt-Cache teilen sich dieselbe Redis-Instanz.

Deine Aufgabe: Finde 3 Fehler in diesem Cache-Design. Was passiert genau, wenn Redis ausfällt? Und warum ist noeviction + Sessions eine schlechte Kombination?
Lösung: Was ist schwach?
  • Keine Invalidierung: Der Admin ändert den Preis in der DB, der Cache liefert bis zu 24 h den alten. Kunden kaufen zum falschen Preis.
  • Redis voll + noeviction: Schreibbefehle bekommen Fehler. Weil Sessions in derselben Instanz liegen, schlagen plötzlich Logins fehl, nur weil der Produkt-Cache gewachsen ist.
  • Redis down = Stampede: 100 % der Reads gehen auf einmal zur DB; dazu laufen viele Keys gleichzeitig ab (alle um dieselbe Uhrzeit gesetzt). Die DB bekommt Lastspitzen, für die sie nie dimensioniert war.
  • Zwei Arten von Daten, eine Policy: Cache darf Daten verlieren, Sessions nicht — dieselbe Instanz kann nicht beides richtig machen.
Senior-Lösung: besseres Design
  • Invalidieren beim Schreiben: Admin-API löscht den Key (DEL produkt:42) oder schickt ein Event; dazu kurze TTL mit Jitter (z. B. 5 min ± 60 s) als Sicherheitsnetz.
  • Zwei Redis-Instanzen: Cache mit allkeys-lru (darf vergessen), Sessions getrennt mit Persistenz und noeviction.
  • Stampede-Schutz: pro Key nur ein Nachlader (Lock/Request-Coalescing) oder stale-while-revalidate; DB-Pool klein halten, damit die DB nie ertrinkt; Circuit Breaker mit degradierter Antwort.

Trade-off: Invalidierung macht den Schreibpfad komplexer. Senior-Satz: „Die DB bleibt die einzige Wahrheit — der Cache darf immer gelöscht werden, nie gebraucht werden müssen."

Folgefrage: Warum TTL mit Jitter?

Ohne Jitter laufen Keys, die zur gleichen Zeit gesetzt wurden, zur gleichen Zeit ab — z. B. nach einem Deploy. Dann fragen tausende Requests im selben Moment die DB (Cache-Stampede). ± zufällige Sekunden verteilen die Misses über die Zeit.

Was geht kaputt, wenn man den Fix „Cache beim Schreiben updaten" (statt löschen) wählt?

Zwei fast gleichzeitige Writes können sich im Cache überholen: Write A (alt) überschreibt im Cache Write B (neu), obwohl die DB B hat — der Cache lügt dann bis zur TTL. Löschen ist robuster: der nächste Read holt garantiert den DB-Stand.

5. Übung 4: Ticket-Verkauf ohne Schutz

Konzertkarten: Verkaufsstart 10:00 Uhr, 500 Tickets, 10'000 Leute klicken gleichzeitig. Die App prüft den Bestand mit lesen → prüfen → schreiben.

Deine Aufgabe: Wo genau entsteht Überverkauf? Rechne: Was passiert mit 10'000 gleichzeitigen Requests an 50 DB-Verbindungen? Nenne 3 Schutz-Schichten der Senior-Lösung.
Lösung: Was ist schwach?
  • Race Condition: 200 Requests lesen gleichzeitig „verkauft = 499", alle prüfen „< 500", alle schreiben +1 → Überverkauf. Lesen-prüfen-schreiben ohne Lock ist nie atomar.
  • Kein Backpressure: 10'000 Requests kämpfen um 50 DB-Verbindungen; Threads und Verbindungen stauen sich, Timeouts kaskadieren, auch andere Seiten sterben.
  • Kein Rate Limit / Warteraum: Bots feuern hunderte Requests pro Sekunde und gewinnen gegen echte Kunden.
  • Statische Dateien über die App: Bilder/CSS fressen genau in der Spitze App-Kapazität; eine Region = keine Reserve.
Senior-Lösung: besseres Design
  • Atomar statt lesen-prüfen-schreiben: UPDATE tickets SET verkauft = verkauft + 1 WHERE id = 7 AND verkauft < 500 — die DB prüft und schreibt in einem Schritt; 0 betroffene Zeilen = ausverkauft. Alternativ Redis DECR als schneller Vorzähler.
  • Warteraum + Queue: Nutzer bekommen sofort eine Platznummer; Worker arbeiten die Käufe mit kontrollierter Rate ab (Backpressure statt Absturz).
  • Rate Limit am Gateway (Token Bucket, z. B. 5 req/s pro IP/Session) gegen Bots; Idempotency-Key gegen Doppelkäufe; CDN für alles Statische.
  • Vorher Lasttest mit 2–3× erwarteter Spitze.

Trade-off: Warteraum = schlechteres Erlebnis für Späte, aber faires, stabiles System. Senior-Satz: „Lieber kontrolliert warten lassen als unkontrolliert ausfallen."

Folgefrage: Reicht SELECT … FOR UPDATE statt des atomaren UPDATE?

Es ist korrekt (Zeile wird gesperrt), aber alle 10'000 Käufe serialisieren sich auf eine Zeilen-Sperre — jeder wartet in der DB. Das atomare UPDATE hält die Sperre nur Mikrosekunden; FOR UPDATE hält sie die ganze Transaktion. Bei Hot Rows: Sperrzeit minimieren oder den Zähler nach Redis ziehen.

Was geht kaputt, wenn man einfach die App auf 30 Pods skaliert?

Nichts wird besser, es wird schlimmer: 30 Pods erzeugen noch mehr gleichzeitige DB-Zugriffe auf dieselbe heiße Zeile und denselben 50er-Pool. Der Engpass ist die DB-Zeile, nicht die App-CPU. Skalieren hilft nur hinter einer Queue mit kontrollierter Abarbeitung.

6. Typische Fehler beim Kritisieren

  • Alles schlechtreden: „Das ist alles Mist, ich würde Microservices nehmen." Ein Senior sagt zuerst, was okay ist und für welche Grösse das Design reicht.
  • Buzzwords ohne Mechanismus: „Kafka rein, Kubernetes drauf." Immer erklären, welches Problem das Werkzeug löst — sonst wirkt es auswendig gelernt.
  • Big-Bang-Redesign: Der beste Schluss-Satz ist eine Reihenfolge: „Zuerst Backup offsite (Tag 1), dann Sessions raus (Woche 1), dann LB + 2. Knoten (Monat 1)."
  • Keine Zahlen: „Das skaliert nicht" ohne Rechnung überzeugt nicht. Eine einzige Rechnung (0,99⁴ ≈ 96 %) ist stärker als fünf Adjektive.

Übe jedes Diagramm, bis du die Analyse in 90 Sekunden frei sprechen kannst — Beobachtung, Mechanismus, Zahl, Fix, Trade-off.
