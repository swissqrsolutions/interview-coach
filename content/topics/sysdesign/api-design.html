API-Design im System Design

System Design · Tier 1 · Quellen: RFC 9110 (HTTP Semantics: Methoden, Idempotenz, 202, ETag/If-Match, 412), RFC 9457 (Problem Details), IETF draft-ietf-httpapi-idempotency-key-header-09 (Entwurf, kein RFC), Azure Architecture Center: „Asynchronous Request-Reply pattern“ und „Web API design best practices“, Microsoft Learn: API Management Versions und Revisions, Durable Functions HTTP API, Event Grid Webhook-Validierung, gRPC-Doku (grpc.io), GraphQL-Spezifikation, OpenAPI 3.1

Kern: API-Design ist der Vertrag zwischen Client und Service: Ressourcen, Methoden, Statuscodes, Fehler. Ein guter Vertrag bleibt stabil, obwohl sich der Service ändert. Im System-Design-Interview zählen vier Punkte: Pagination, Idempotenz bei Retries, Versionierung und asynchrone lange Abläufe.

1. Wo sitzt die API im System?

  1. Clients: Browser, Apps und Partner-Systeme rufen die öffentliche API auf. Meist REST mit JSON.
  2. API Gateway: Es prüft Token, setzt Limits und leitet Versionen weiter. Beispiel: Azure API Management.
  3. Service: Er implementiert den Vertrag. Der Vertrag steht in einer OpenAPI-Datei, also einer maschinenlesbaren Beschreibung.
  4. Interne Aufrufe: Zwischen Services passt oft gRPC: binär, schnell, mit festem Schema.
  5. Lange Jobs: Sie laufen über eine Queue im Hintergrund. Die API antwortet sofort mit 202 Accepted.
  6. Webhook: Der Service ruft selbst den Partner auf, wenn etwas passiert. So muss der Partner nicht ständig fragen (Polling).

2. Die Reise einer Bestellung durch die API (die Geschichte zum Merken)

  1. Request. Der Client schickt POST /v1/orders. Er erzeugt vorher einen Idempotency-Key, also eine eindeutige ID für genau diesen Auftrag.
  2. Key prüfen. Der Service sucht den Key in seiner DB. Neu: Er verarbeitet den Auftrag. Bekannt: Er liefert die gespeicherte Antwort zurück. Kein Doppelauftrag.
  3. 202 Accepted. Die Bestellung braucht Zeit. Der Service antwortet sofort mit 202 und einem Location-Header auf eine Status-Ressource.
  4. Worker. Ein Hintergrund-Prozess holt den Auftrag aus der Queue. Er bucht Zahlung und Lager.
  5. Status abfragen. Der Client fragt GET /v1/operations/42. Antwort: running mit Retry-After: 5. Der Client wartet so lange.
  6. Fertig. Der Status ist succeeded und zeigt auf die neue Ressource /v1/orders/981.
  7. Webhook. Optional ruft der Service den Partner direkt auf. Das Event ist signiert und wird bei Fehlern wiederholt.

3. Beispiel: Pagination und Idempotency-Key

a) Offset vs Cursor, neueste zuerst, 3 pro Seite, SQLite im Speicher (pagination.py, gekürzt):

SELECT id FROM orders ORDER BY id DESC LIMIT 3 OFFSET ?         -- Offset
SELECT id FROM orders WHERE id < ? ORDER BY id DESC LIMIT 3     -- Cursor (Keyset)
cursor = base64url(json({"id": last_id}))                       -- opak für den Client
# zwischen Seite 1 und 2: zwei neue Bestellungen (11, 12), bzw. Bestellung 10 gelöscht
Offset pagination
  page 1: [10, 9, 8]
  -- 2 new orders inserted (11, 12)
  page 2: [9, 8, 7]  duplicates: [8, 9]

Cursor pagination (WHERE id < last_id)
  page 1: [10, 9, 8]  next_cursor: eyJpZCI6IDh9
  -- 2 new orders inserted (11, 12)
  page 2: [7, 6, 5]  duplicates: []

Delete during offset paging

b) Idempotency-Key: Die erste Antwort geht verloren, der Client wiederholt (idempotency.py, gekürzt):

if key in self.keys:
    old_fp, status, resp = self.keys[key]
    if old_fp != fingerprint(body): return 422, ...    # gleicher Key, anderer Body
    return status, resp | {"replayed": True}           # gespeicherte Antwort
charge(); self.keys[key] = (fingerprint(body), 201, resp)
Without idempotency key
  attempt 1 -> 201 {'id': 'pay_1', 'amount': 120}  (response lost, client times out)
  attempt 2 -> 201 {'id': 'pay_2', 'amount': 120}
  charges in DB: [('pay_1', 120), ('pay_2', 120)]

With Idempotency-Key
  key: 00000000-0000-0000-0000-000000001234
  attempt 1 -> 201 {'id': 'pay_1', 'amount': 120}  (response lost, client times out)
  attempt 2 -> 201 {'id': 'pay_1', 'amount': 120, 'replayed': True}
  charges in DB: [('pay_1', 120)]

Same key, different body
  -> 422 {'error': 'key reused with different body'}
No key
  -> 400 {'error': 'Idempotency-Key required'}

Echte Ausgabe, Python 3 (Simulation). SQLite aus der Standardbibliothek; die Zahlungs-API ist simuliert.

  1. Offset mit Inserts: Zwei neue Zeilen schieben alles nach hinten. Seite 2 zeigt 9 und 8 doppelt.
  2. Cursor mit Inserts: Seite 2 beginnt nach der letzten gesehenen ID. Keine Duplikate, egal was neu kommt.
  3. Offset mit Delete: Eine gelöschte Zeile zieht alles nach vorne. Bestellung 7 wird übersprungen. Der Client merkt es nie.
  4. Query Plan: Offset muss alle übersprungenen Zeilen lesen (SCAN). Der Cursor springt über den Index direkt hin (SEARCH). Tiefe Seiten bleiben schnell.
  5. Ohne Key: Der Retry bucht ein zweites Mal. Der Kunde zahlt 240 statt 120 CHF.
  6. Mit Key: Der Retry bekommt die gleiche Antwort (pay_1). Es gibt nur eine Buchung.
  7. Missbrauch: Gleicher Key mit anderem Body gibt 422. Fehlender Key gibt 400. So empfiehlt es der IETF-Entwurf.

4. Details, die Interviewer fragen

  1. Ressourcen: URLs benennen Dinge im Plural, keine Verben: /orders/981/items, nicht /getOrderItems. Die Methode ist das Verb.
  2. Methoden und Idempotenz: Idempotent heisst: mehrfach senden wirkt wie einmal. Laut RFC 9110 sind GET, HEAD, PUT, DELETE idempotent. POST und PATCH sind es nicht automatisch.
  3. Statuscodes: 201 + Location nach Erstellen, 202 für angenommen, 204 ohne Inhalt. 400 ungültig, 401 nicht angemeldet, 403 nicht erlaubt, 404 fehlt, 409 Konflikt, 422 fachlich ungültig, 429 zu viele Requests.
  4. Fehlerformat: Problem Details (RFC 9457) ist ein Standard-JSON für Fehler: type, title, status, detail, instance. Content-Type: application/problem+json. RFC 9457 ersetzt RFC 7807.
  5. Offset-Pagination: ?offset=40&limit=20. Einfach, erlaubt Sprung auf Seite 7. Aber: Duplikate und Lücken bei Änderungen, und tiefe Seiten werden langsam.
  6. Cursor-Pagination: Der Server gibt einen opaken Cursor zurück, z. B. Base64 der letzten ID. Die Abfrage nutzt WHERE id < ? auf einem Index. Stabil und schnell, aber kein Sprung auf Seite 7.
  7. Stabile Sortierung: Ein Cursor braucht eine eindeutige Sortierung. Bei created_at kommt die ID als Tie-Breaker dazu: (created_at, id) < (?, ?).
  8. Idempotency-Key: Der Client sendet einen Header Idempotency-Key mit einer UUID. Der Server speichert Key, Fingerabdruck des Body und Antwort. Ein IETF-Entwurf beschreibt das (draft-09): 400 ohne Key, 422 bei anderem Body, 409, wenn der erste Request noch läuft.
  9. Key-Speicher: Key und Geschäftsaktion gehören in dieselbe Transaktion. Sonst gibt es bei einem Absturz dazwischen wieder Duplikate. Keys laufen nach einer dokumentierten Frist ab, z. B. 24 Stunden.
  10. Versionierung: Varianten: im Pfad (/v1/), als Query (?api-version=2024-05-01, wie Azure) oder im Header. Neue Version nur bei Breaking Changes: Feld entfernen, Typ ändern, Pflichtfeld neu.
  11. Nicht-brechende Änderungen: Neue optionale Felder und neue Endpunkte brauchen keine Version. Clients sind Tolerant Reader: Sie ignorieren unbekannte Felder.
  12. APIM-Versionen und Revisionen: Eine Version ist ein neuer, sichtbarer Vertrag. Eine Revision ist eine nicht-brechende Änderung, die man testet und dann live schaltet.
  13. Asynchrone API: Asynchronous Request-Reply (Azure Architecture Center): 202 Accepted + Location auf einen Status-Endpunkt + Retry-After. Ist der Job fertig, zeigt der Status auf das Ergebnis. Azure Durable Functions liefern das Muster fertig mit.
  14. Optimistic Concurrency: Jede Ressource hat ein ETag, also eine Versionsmarke. Der Client sendet If-Match. Hat sich die Ressource geändert, kommt 412 Precondition Failed. So überschreibt niemand fremde Änderungen.
  15. Webhooks: Der Service ruft eine URL des Partners auf. Pflicht: Signatur (HMAC über Body und Zeitstempel), Retries mit Backoff und idempotente Empfänger, weil Events doppelt kommen können. Azure Event Grid prüft neue Webhook-URLs mit einem Validierungs-Handshake.

5. Vergleich: REST, gRPC, GraphQL

StilStärkeSchwäche
REST (HTTP + JSON)überall unterstützt, HTTP-Caching, einfach zu debuggenOver- und Underfetching, viele Roundtrips
gRPC (HTTP/2 + Protobuf)schnell, binär, Streaming, Code aus .protoBrowser nur über gRPC-Web, schwer lesbar
GraphQLClient wählt Felder, ein Endpunkt, ein RoundtripHTTP-Caching schwer, N+1-Abfragen, teure Queries
  • Öffentliche API, Partner: REST mit OpenAPI. Jeder kann es nutzen.
  • Interne Service-zu-Service-Aufrufe: gRPC. Schnell und mit striktem Vertrag.
  • Viele verschiedene Frontends mit eigenen Datenwünschen: GraphQL, oft als BFF (Backend for Frontend). N+1 löst man mit Batching (DataLoader).
  • Polling vs Webhook: Polling ist einfach, aber verschwendet Requests. Webhooks sind sofort, brauchen aber eine erreichbare, sichere URL beim Partner.

6. In der Produktion

  1. Doppelte Zahlungen nach Timeouts: Client wiederholt POST, der erste lief aber durch. Lösung: Idempotency-Key, in derselben Transaktion gespeichert.
  2. Doppelte oder fehlende Einträge beim Export: Offset-Pagination über eine Tabelle mit laufenden Inserts. Lösung: Cursor-Pagination mit stabiler Sortierung.
  3. Langsame tiefe Seiten: OFFSET 100000 liest 100 000 Zeilen. Lösung: Cursor auf einem Index.
  4. Gateway-Timeout bei langen Jobs: Gateways und Load Balancer brechen lange Requests ab. Azure App Service zum Beispiel nach 230 s. Lösung: 202 + Status-Endpunkt.
  5. Breaking Change ohne Version: Ein umbenanntes Feld bricht Clients, die man nicht kennt. Lösung: Contract Tests, OpenAPI-Diff in der Pipeline, neue Version.
  6. Webhook-Empfänger überlastet oder down: Events gehen verloren. Lösung: Retries mit Backoff, Dead-Letter, und eine API zum Nachladen verpasster Events.
  7. Lost Update: Zwei Benutzer bearbeiten dieselbe Ressource, der zweite überschreibt den ersten. Lösung: ETag und If-Match.

7. Diagnose: Werkzeuge und Befehle

  • curl -i: zeigt Status, Location, Retry-After, ETag einer Antwort.
  • OpenAPI-Linter (z. B. Spectral) und OpenAPI-Diff: finden Stilfehler und Breaking Changes in der Pipeline.
  • Contract Tests (z. B. Pact): prüfen, dass Anbieter und Konsument denselben Vertrag erfüllen.
  • Application Insights: Requests und Abhängigkeiten pro Operation. Die W3C-Trace-Context-Header (traceparent) verbinden Aufrufe über Services.
  • API Management Analytics: Aufrufe, Fehler und Latenz pro API, Operation und Subscription.
  • Datenbank: EXPLAIN auf Pagination-Abfragen. SCAN statt Index-Zugriff zeigt ein Offset-Problem.
  • Metriken: Anteil der Replays pro Idempotency-Key, Webhook-Erfolgsquote, Alter der offenen Async-Operationen.

8. Senior-Punkte

  1. Jeder Netzwerk-Call kann zweimal ankommen. Darum braucht jeder schreibende Endpunkt eine Idempotenz-Strategie.
  2. Der Vertrag zuerst. OpenAPI vor dem Code, mit Review und Linter. Breaking Changes sind teuer, sobald Partner ihn nutzen.
  3. Versionieren ist die letzte Wahl. Erst additive Änderungen und Tolerant Reader. Jede Version muss man jahrelang betreiben.
  4. Lang heisst asynchron. Alles über wenige Sekunden: 202, Status-Ressource, optional Webhook.
  5. Cursor als Standard für Listen, die wachsen. Offset nur für kleine, stabile Daten oder Admin-UIs.
  6. Der Stil folgt dem Konsumenten. REST für Partner, gRPC intern, GraphQL für viele Frontends. Nicht alles mit einem Stil lösen.

10. Fallen

  • „POST ist idempotent, wenn der Code sauber ist.“ → Falsch. Ohne Idempotency-Key erzeugt ein Retry einen zweiten Datensatz.
  • „Offset-Pagination ist bei Änderungen korrekt.“ → Falsch. Inserts erzeugen Duplikate, Deletes Lücken.
  • „Jede Änderung braucht eine neue API-Version.“ → Falsch. Nur Breaking Changes. Neue optionale Felder nicht.
  • „202 heisst, die Arbeit ist erledigt.“ → Falsch. 202 heisst nur: angenommen. Das Ergebnis kommt über den Status-Endpunkt.
  • „Ein Webhook kommt genau einmal.“ → Falsch. Meist at-least-once. Der Empfänger muss Duplikate erkennen.
  • „Der Idempotency-Key ist ein Standard-Header.“ → Falsch. Er ist ein IETF-Entwurf, verbreitet z. B. durch Zahlungs-APIs.

11. Fragen

Wie benennen Sie REST-Ressourcen?

Nomen im Plural mit Hierarchie, z. B. /orders/981/items. Die HTTP-Methode ist das Verb.

Welche HTTP-Methoden sind idempotent?

GET, HEAD, PUT, DELETE (und OPTIONS, TRACE). POST und PATCH nicht automatisch.

PUT vs PATCH?

PUT ersetzt die ganze Ressource und ist idempotent. PATCH ändert Teile und ist nicht automatisch idempotent.

Welchen Status nach einem erfolgreichen POST?

201 Created mit Location-Header auf die neue Ressource. Bei langer Verarbeitung 202 Accepted.

Wie geben Sie Fehler zurück?

Als Problem Details (RFC 9457): application/problem+json mit type, title, status, detail. Dazu ein passender Statuscode.

400 vs 422?

400: Die Anfrage ist formal kaputt, z. B. ungültiges JSON. 422: formal ok, aber fachlich ungültig.

401 vs 403?

401: nicht oder falsch angemeldet. 403: angemeldet, aber nicht berechtigt.

Offset vs Cursor-Pagination?

Offset ist einfach und erlaubt Seitensprünge, liefert aber Duplikate und Lücken bei Änderungen und ist tief langsam. Cursor ist stabil und schnell, aber ohne Seitensprung.

Warum ist OFFSET auf tiefen Seiten langsam?

Die Datenbank liest alle übersprungenen Zeilen und wirft sie weg. Ein Cursor springt per Index direkt hin.

Was steht in einem Cursor?

Die Sortierwerte des letzten Eintrags, z. B. created_at und id. Base64-kodiert und opak für den Client.

Was ist ein Idempotency-Key?

Eine eindeutige ID vom Client pro Auftrag. Der Server speichert sie mit der Antwort. Ein Retry bekommt die gespeicherte Antwort statt einer neuen Aktion.

Was speichert der Server zum Idempotency-Key?

Key, Fingerabdruck des Body, Status und Antwort, Ablaufzeit. Alles in derselben Transaktion wie die Aktion.

Was passiert bei gleichem Key und anderem Body?

Fehler, laut IETF-Entwurf 422. Läuft der erste Request noch: 409.

Wie versionieren Sie eine API?

Im Pfad (/v1), als Query (api-version, wie Azure) oder im Header. Neue Version nur bei Breaking Changes.

Was ist ein Breaking Change?

Eine Änderung, die bestehende Clients bricht: Feld entfernen oder umbenennen, Typ ändern, neues Pflichtfeld, andere Bedeutung.

Version vs Revision in API Management?

Version: neuer, sichtbarer Vertrag für Breaking Changes. Revision: nicht-brechende Änderung, getestet und dann live geschaltet.

Wie bauen Sie eine API für lange Jobs?

202 Accepted mit Location auf eine Status-Ressource und Retry-After. Der Status zeigt am Ende auf das Ergebnis. Optional ein Webhook.

Polling vs Webhook?

Polling: Client fragt regelmässig, einfach, aber verschwenderisch. Webhook: Server ruft an, sofort, aber braucht sichere, erreichbare URL und Retries.

Wie sichern Sie Webhooks ab?

HMAC-Signatur über Body und Zeitstempel, nur HTTPS, Zeitfenster gegen Replay, idempotenter Empfänger.

Wie verhindern Sie Lost Updates?

Mit ETag und If-Match. Hat sich die Ressource geändert, antwortet der Server 412 Precondition Failed.

REST vs gRPC?

REST: JSON, überall nutzbar, gut für Partner. gRPC: Protobuf über HTTP/2, schnell, Streaming, ideal intern. Im Browser nur über gRPC-Web.

Wann GraphQL?

Wenn viele Frontends unterschiedliche Daten brauchen. Preis: schwieriges HTTP-Caching, N+1-Abfragen, Schutz vor teuren Queries nötig.

Was ist das N+1-Problem bei GraphQL?

Ein Resolver lädt für jedes Element einzeln nach. Aus einer Liste werden N+1 DB-Abfragen. Lösung: Batching mit DataLoader.

Szenario: Kunden melden doppelte Belastungen, immer bei langsamen Antworten. Was tun Sie?

Client-Retries nach Timeouts. Lösung: Idempotency-Key Pflicht für POST, Speicherung in derselben Transaktion, Replay der Antwort. Duplikate über Logs bereinigen.

Szenario: Ein nächtlicher Export über /orders?offset=… liefert Duplikate und fehlende Bestellungen. Warum?

Während des Exports kommen neue Bestellungen dazu oder werden gelöscht. Offset verschiebt sich. Lösung: Cursor-Pagination mit stabiler Sortierung.

Szenario: Ein Report-Endpunkt läuft 5 Minuten und bricht mit Gateway-Timeout ab. Wie ändern Sie die API?

Asynchron machen: POST gibt 202 mit Status-URL. Ein Worker erstellt den Report. Der Client fragt den Status oder bekommt einen Webhook und lädt dann das Ergebnis.
