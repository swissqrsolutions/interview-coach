Drill 5: IoT-Telemetrie (Kafka, Zeitreihen, Alarme)

1. Die Aufgabe

So stellt sie der Interviewer: „Eine Kühllogistik-Flotte hat 20'000 Fahrzeuge. Jedes sendet alle 10 Sekunden Position und Kühlraum-Temperatur — zusammen also rund 2'000 Nachrichten pro Sekunde, rund um die Uhr. Die Disposition will jedes Fahrzeug live auf der Karte sehen, Temperaturkurven der letzten Tage anschauen, und wenn die Temperatur länger als 5 Minuten über −18 °C liegt, muss ein Alarm raus. Rohdaten sollen 90 Tage aufbewahrt werden."

20 Minuten: Stell die Uhr. Löse laut: Rückfragen, Datenvolumen, Ingest-Pfad, Speicher-Schema, Alarm-Logik, ein Diagramm. Dann erst vergleichen.

2. Schritt 1: Verstehen

Die Rückfragen — mit plausiblen Antworten:

  1. „Darf eine einzelne Nachricht verloren gehen?" → „Einzelne ja, aber keine Lücken von Minuten — und kein verpasster Alarm." ⇒ at-least-once reicht, Alarm-Pfad ist der kritische.
  2. „Wie schnell muss der Alarm nach der Grenzverletzung kommen?" → „Innerhalb ~1 Minute nach Ablauf der 5 Minuten." ⇒ Stream-Verarbeitung, kein 15-min-Batch.
  3. „Kommen Nachrichten verspätet oder unsortiert an (Funkloch, Tunnel)?" → „Ja, Fahrzeuge puffern bis 1 h und senden nach." ⇒ Event-Zeit vom Gerät mitführen, nicht Empfangszeit; Alarm auf Event-Zeit rechnen.
  4. „Wer liest wie? Live-Karte vs Kurven vs Reports?" → „Karte: letzter Punkt je Fahrzeug. Kurven: 1 Fahrzeug, Zeitraum. Reports: Tages-Aggregate je Flotte." Drei Lesemuster ⇒ drei Datenformen.
  5. „Wie viele Alarme erwarten wir?" → „Ein paar Dutzend pro Tag." ⇒ Alarm-Ausgang ist winzig, der Eingang ist das Volumenproblem.
  6. „Wächst die Flotte?" → „Ziel 100'000 Fahrzeuge in 3 Jahren." ⇒ Partitionierung heute so wählen, dass ×5 ohne Umbau geht.

Zahlenschätzung (laut rechnen): 20'000 / 10 s = 2'000 msg/s. Nachricht ~100 Bytes (id, ts, lat, lon, temp) ⇒ 200 KB/s ≈ 17 GB/Tag Rohdaten. 90 Tage ≈ 1,5 TB — gut für eine partitionierte PostgreSQL, zu viel für „eine grosse Tabelle mit B-Tree-Index über alles". Zeilen: 2'000 × 86'400 = 173 Mio Zeilen/Tag ⇒ Einzel-INSERTs verbieten sich, Batch-Insert ist Pflicht.

3. Anforderungen

Muss:

  • 2'000 msg/s dauerhaft aufnehmen, Spitzen (Nachsenden nach Funkloch) ×5 abfedern.
  • Reihenfolge pro Fahrzeug erhalten (für Alarm-Fenster und Kurven).
  • Alarm: Temperatur > −18 °C über 5 min ⇒ Meldung < 1 min danach, kein Duplikat-Spam.
  • Live-Position je Fahrzeug < 30 s alt; Kurvenabfrage 1 Fahrzeug/7 Tage < 2 s.
  • Rohdaten 90 Tage, dann automatisch weg; Aggregate länger.

Kann:

  • Geofencing (Fahrzeug verlässt Route).
  • Export für Audits (Kühlkette nachweisen).
  • Vorhersage „Aggregat defekt" aus Temperaturtrend.
  • Replay: Alarm-Logik rückwirkend auf Rohdaten neu rechnen.

4. DB-Design

-- Rohdaten: partitioniert NACH TAG — loeschen = Partition droppen
CREATE TABLE messung (
  fahrzeug_id  int NOT NULL,
  ts           timestamptz NOT NULL,   -- Event-Zeit vom Geraet
  lat          double precision NOT NULL,
  lon          double precision NOT NULL,
  temp_c       real NOT NULL,
  PRIMARY KEY (fahrzeug_id, ts)
) PARTITION BY RANGE (ts);
CREATE TABLE messung_2026_11_26 PARTITION OF messung
  FOR VALUES FROM ('2026-11-26') TO ('2026-11-27');
-- Der PK (fahrzeug_id, ts) traegt die Kurven-Query:
--   WHERE fahrzeug_id = ? AND ts BETWEEN ? AND ?
-- Partition-Pruning auf ts haelt die Query auf wenigen Tages-Partitionen.

-- Live-Karte: EIN Datensatz je Fahrzeug, per UPSERT ueberschrieben
CREATE TABLE fahrzeug_zuletzt (
  fahrzeug_id int PRIMARY KEY,
  ts timestamptz NOT NULL, lat double precision, lon double precision,
  temp_c real
);

-- Downsampling: 5-min-Aggregate, Faktor 30 kleiner, lange aufbewahrt
CREATE TABLE messung_5min (
  fahrzeug_id int NOT NULL,
  zeitfenster timestamptz NOT NULL,    -- auf 5 min gerundet
  temp_min real, temp_max real, temp_avg real, anzahl int,
  PRIMARY KEY (fahrzeug_id, zeitfenster)
) PARTITION BY RANGE (zeitfenster);    -- monatliche Partitionen

CREATE TABLE alarm (
  alarm_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  fahrzeug_id int NOT NULL,
  beginn      timestamptz NOT NULL,
  ende        timestamptz,             -- NULL = noch aktiv
  max_temp    real,
  UNIQUE (fahrzeug_id, beginn)         -- Replay erzeugt keine Duplikate
);
  • messung: append-only Zeitreihe; die Tages-Partitionierung ist DIE Entscheidung — Retention heisst DROP TABLE messung_2026_08_28 statt DELETE über 173 Mio Zeilen. (Gleiches Modell bieten Zeitreihen-Erweiterungen für PostgreSQL fertig an — nennen, nicht dran hängen.)
  • fahrzeug_zuletzt: 20'000 Zeilen, beantwortet die Karte ohne Scan über die Zeitreihe.
  • messung_5min: bedient Kurven über Wochen und Reports; Rohdaten braucht nur, wer in Minuten zoomt.
  • alarm: Zustand mit beginn/ende statt Einzelevents — „noch aktiv" ist eine Query, und der Unique-Constraint macht Replays harmlos.

5. Topics und API

  • Kafka-Topic telemetrie — 48 Partitionen, Key = fahrzeug_id ⇒ alle Nachrichten eines Fahrzeugs in einer Partition, dort in Reihenfolge; Retention z. B. 7 Tage als Wiederanlauf-/Replay-Puffer.
  • Kafka-Topic alarme — klein; entkoppelt Alarm-Erkennung von Zustellung (Mail/SMS/Push).
  • GET /fahrzeuge/zuletzt — alle letzten Positionen für die Karte (eine 20'000-Zeilen-Tabelle).
  • GET /fahrzeuge/{id}/messungen?von=…&bis=…&aufloesung=roh|5min — Kurven.
  • GET /alarme?aktiv=true — offene Alarme für das Dashboard.
  • Ingest: Fahrzeuge → MQTT/HTTPS-Gateway (TLS, Geräte-Auth) → Producer schreibt nach Kafka. Geräte reden nie direkt mit Kafka.

6. Pseudo-Code an der Tafel

// Consumer (Gruppe "persistenz+alarm") — pro Partition ein Faden,
// dadurch Reihenfolge pro Fahrzeug garantiert
zustand = map fahrzeug_id -> {ueberGrenzeSeit, alarmAktiv}  // im RAM

schleife:
  batch = kafka.poll(max 5000 nachrichten, 1 s)   // 1) Batches, nie einzeln

  // 2) Rohdaten als EIN Batch-Insert (COPY/multi-row), nicht 5000 INSERTs
  db.batchInsert("messung", batch)
  db.upsertZuletzt(letzteNachrichtJeFahrzeug(batch))

  // 3) Alarm-Fenster pro Fahrzeug, auf EVENT-Zeit gerechnet
  fuer n in batch:                                 // pro Fahrzeug geordnet
    z = zustand[n.fahrzeug_id]
    wenn n.temp_c > -18:
      wenn z.ueberGrenzeSeit == null: z.ueberGrenzeSeit = n.ts
      wenn n.ts - z.ueberGrenzeSeit >= 5 min und nicht z.alarmAktiv:
        INSERT INTO alarm (fahrzeug_id, beginn) VALUES (…)
          ON CONFLICT DO NOTHING                   // Replay-sicher
        kafka.sende("alarme", n.fahrzeug_id, …)
        z.alarmAktiv = true                        // kein Duplikat-Spam
    sonst:                                         // wieder unter Grenze
      wenn z.alarmAktiv: UPDATE alarm SET ende = n.ts WHERE …
      z = zuruecksetzen

  kafka.commitOffsets()   // 4) NACH dem Schreiben: at-least-once,
                          //    Crash wiederholt den Batch — Inserts sind
                          //    idempotent (PK/ON CONFLICT faengt Duplikate)

// Separater Aggregat-Job (alle 5 min): INSERT INTO messung_5min
//   SELECT fahrzeug_id, runde(ts, 5 min), min/max/avg(temp_c), count(*)
//   FROM messung WHERE ts im letzten Fenster GROUP BY 1,2
//   ON CONFLICT … DO UPDATE   -- Nachzuegler aktualisieren das Fenster

7. Architektur

Sprich das Bild so: „Kafka ist der Stossdämpfer: Geräte-Spitzen und Nachsende-Fluten treffen den Broker, nicht die DB. Die Consumer-Gruppe zieht in Batches und schreibt drei Formen: Rohdaten (Tag-Partitionen), letzter Stand (Upsert), Aggregate. Der Alarm läuft im selben Consumer auf dem geordneten Strom pro Fahrzeug."

8. Der schwierige Teil als Bild

Der Mechanismus in einem Satz: Kafka garantiert Reihenfolge nur innerhalb einer Partition — weil der Key fahrzeug_id jedes Fahrzeug fest auf eine Partition hasht und jede Partition in der Gruppe genau einem Consumer gehört, sieht genau ein Prozess alle Messungen eines Fahrzeugs in Reihenfolge und kann das 5-min-Fenster im lokalen Zustand rechnen.

9. Frontend kurz

  • Komponenten: FlottenKarteComponent (Leaflet/MapLibre, 20'000 Marker geclustert), TemperaturKurveComponent, AlarmListeComponent.
  • State: TelemetrieService pollt /fahrzeuge/zuletzt alle 15 s; Alarme optional per SSE pushen.
  • Kurven: FE fragt aufloesung=5min an, Rohauflösung nur beim Zoomen unter 1 h — nie 173 Mio Punkte in den Browser.

10. Cloud (Azure)

  • Event Hubs statt selbst betriebenem Kafka: gleiches Modell (Partitionen, Keys, Consumer Groups, Kafka-kompatibler Endpunkt), kein Broker-Betrieb. Service Bus wäre falsch: 2'000 msg/s Dauerstrom mit Replay ist Streaming, keine Auftrags-Queue.
  • AKS oder Container Apps für Gateway + Consumer: Consumer sind langlaufende Prozesse mit RAM-Zustand — kein Fall für kurzlebige Functions.
  • Azure Functions passt dagegen gut für den Notifier (Trigger auf alarme, wenige Events/Tag) und den 5-min-Aggregat-Job (Timer).
  • Azure Database for PostgreSQL mit Tages-Partitionen; Alternative benennen: spezialisierte Zeitreihen-Angebote (Timescale-artig) oder Azure Data Explorer, wenn Ad-hoc-Analytik über die ganze Flotte dominiert.
  • Blob Storage: Rohdaten älter 90 Tage als Parquet exportieren, bevor die Partition gedroppt wird — Audit-Nachweis Kühlkette, Cent-Kosten.
  • Monitor: Alarm auf Consumer-Lag (wichtigste Metrik des Systems) und DB-Insert-Latenz; Key Vault für Geräte-Zertifikate und Connection Strings.

11. Trade-offs

  • Kafka/Event Hubs vs Service Bus: gewählt Kafka-Modell, weil Dauerstrom + Reihenfolge pro Key + Replay (Offsets zurücksetzen) gebraucht werden. Preis: Partitionszahl ist eine frühe Festlegung (Parallelität ≤ Partitionen), und Consumer-Gruppen-Betrieb (Lag, Rebalancing) will überwacht sein.
  • Roh + Aggregat vs nur Aggregat: gewählt beides, weil Audits und Alarm-Replays die Rohdaten brauchen und Dashboards die Aggregate. Preis: doppelte Schreiblast und 1,5 TB statt 50 GB — bewusst bezahlt, Rohdaten sind hier der Produktwert (Kühlketten-Nachweis).
  • Alarm im Persistenz-Consumer vs eigener Stream-Job: gewählt im Consumer, weil der geordnete Strom dort schon vorliegt und die Logik 20 Zeilen ist. Preis: Alarm und Persistenz teilen Deployment und Ausfall — wächst die Regel-Menge (mehrere Regeln, Konfiguration pro Kunde), auslagern in eigene Consumer-Gruppe auf demselben Topic.
  • Fensterzustand im RAM vs in der DB: gewählt RAM, weil pro Nachricht ein DB-Roundtrip für den Zustand 2'000 extra Queries/s hiesse. Preis: nach Crash/Rebalancing ist der Zustand weg — Recovery: letzte 5 min aus der DB nachlesen oder schlicht neu aufbauen (max. 5 min verspäteter Alarm, dokumentiert und akzeptiert).
  • Tages-Partitionen vs eine grosse Tabelle: gewählt Partitionen, weil Retention sonst DELETE + Vacuum über Milliarden Zeilen wäre und Queries über ts ganze Partitionen überspringen (Pruning). Preis: Partition-Verwaltung (anlegen/droppen) muss automatisiert und überwacht sein — fehlende Morgen-Partition = Insert-Fehler.
  • Upsert-Tabelle für „zuletzt" vs max(ts)-Query: gewählt Upsert, weil die Karte sonst alle 15 s ein Top-1-per-Fahrzeug über die Zeitreihe rechnet. Preis: 2'000 Upserts/s zusätzlich — gebündelt pro Batch (nur letzter Wert je Fahrzeug) real ~einige hundert/s.

12. Selbsttest

Typische Fehler genau bei dieser Aufgabe:

  • Geräte schreiben direkt in die DB: 20'000 offene Verbindungen, keine Pufferung, kein Backpressure — das Gateway + Kafka sind genau dafür da.
  • Einzel-INSERT pro Nachricht: 2'000 Transaktionen/s dauerhaft quälen die DB grundlos; Batch/COPY reduziert das auf ~2–20 Writes/s.
  • Key weglassen oder Key = Timestamp: dann verteilt Kafka round-robin, Messungen eines Fahrzeugs landen überall — kein geordnetes Fenster, Alarm-Logik kaputt.
  • Alarm auf Empfangszeit statt Event-Zeit: Nachgesendete Tunnel-Daten lösen Fehlalarme aus oder verschlucken echte.
  • „Mehr Consumer als Partitionen" als Skalierungsplan: die überzähligen bekommen nichts — Parallelität ist durch die Partitionszahl gedeckelt.
Warum garantiert der Partition-Key die Reihenfolge — Mechanismus, nicht Behauptung?

Der Producer berechnet hash(key) % partitionen — gleicher Key, gleiche Partition, immer. Eine Partition ist ein append-only Log: Nachrichten bekommen aufsteigende Offsets und werden in Offset-Reihenfolge konsumiert. Über verschiedene Partitionen gibt es keine Ordnung — brauchen wir auch nicht, Fahrzeuge sind unabhängig.

Warum 48 Partitionen und nicht 4 oder 1'000?

Partitionen = maximale Consumer-Parallelität. Heute reichen 3–6 Consumer (je ~400–700 msg/s), aber bei 100'000 Fahrzeugen (10'000 msg/s) will ich auf 20–40 hochskalieren können, ohne Partitionen nachträglich zu erhöhen — denn das ändert die Hash-Zuordnung und bricht die Reihenfolgegarantie im Übergang. 1'000 wäre Overhead (Dateien, Rebalancing-Dauer) ohne Nutzen.

Ein Consumer crasht. Was passiert mit seinen 16 Partitionen und dem Alarm-Zustand?

Die Gruppe rebalanciert: die 16 Partitionen gehen an die übrigen Consumer, die ab dem letzten committeten Offset weiterlesen — Nachrichten gehen nicht verloren, einige werden doppelt verarbeitet (at-least-once). Der RAM-Fensterzustand ist weg; der Übernehmer baut ihn aus den nächsten Messungen bzw. per Nachlesen der letzten 5 min auf. Schlimmster Fall: ein Alarm kommt Minuten später.

Offsets werden NACH dem DB-Schreiben committet. Was folgt daraus — und warum knallt es nicht?

Crash zwischen Schreiben und Commit ⇒ der Batch wird nochmal konsumiert und nochmal geschrieben. Deshalb ist jeder Schreibpfad idempotent: messung hat PK (fahrzeug_id, ts) (Duplikat ⇒ ON CONFLICT DO NOTHING), der Upsert überschreibt mit demselben Wert, alarm hat UNIQUE(fahrzeug_id, beginn). At-least-once + idempotente Writes = praktisch exactly-once-Wirkung.

Rechne: Wie gross wird die Rohtabelle, und warum ist Partitionieren Pflicht?

173 Mio Zeilen/Tag × 90 Tage ≈ 15,6 Mrd Zeilen, ~1,5 TB mit Indexen. Löschen per DELETE WHERE ts < … müsste täglich 173 Mio Zeilen entfernen und hinterlässt Bloat, den Vacuum abtragen muss. DROP einer Tages-Partition ist eine Metadaten-Operation in Millisekunden — und Queries mit ts-Filter lesen per Pruning nur die betroffenen Tage.

Montagmorgen verlassen 5'000 Fahrzeuge gleichzeitig ein Funkloch-Depot und senden je 1 h Puffer nach. Was passiert?

Kurzzeitig ×5–×10 Eingangsrate. Kafka nimmt das auf (Broker schreiben sequentiell, das ist ihr Normalfall); der Consumer-Lag steigt und baut sich über Minuten ab — die DB sieht weiter gleichmässige Batches. Wichtig: Alarm rechnet auf Event-Zeit, sonst würden die nachgesendeten „alten" Messwerte als frische 5-min-Verletzung gelesen.

Wie verhinderst du, dass ein aktiver Alarm alle 10 s eine neue SMS auslöst?

Der Alarm ist ein Zustand, kein Event: beim Überschreiten wird einmal eine alarm-Zeile mit beginn angelegt und alarmAktiv=true gemerkt; weitere heisse Messungen ändern höchstens max_temp. Erst wenn die Temperatur zurückfällt, wird ende gesetzt und der Zustand gelöscht — die nächste Verletzung ist ein neuer Alarm.

Ein Fahrzeug sendet gar nichts mehr — Sensor tot. Merkt das jemand?

Nicht über den Stream: wo keine Nachricht ist, feuert keine Regel. Das braucht einen Absenz-Check: ein Timer-Job (z. B. jede Minute) fragt fahrzeug_zuletzt nach ts < now() − 10 min ⇒ Alarm „Fahrzeug stumm". Im Interview aktiv nennen — das Fehlen von Daten ist bei Kühlketten selbst ein Alarmfall.

Skalierung ×10: 200'000 Fahrzeuge, 20'000 msg/s. Was änderst du wo?

Kafka: Partitionen waren dafür geplant (48 ⇒ ggf. neues Topic mit 96 und Umzug), mehr Consumer. DB: 170 GB/Tag Rohdaten — jetzt kippt die Entscheidung: Rohdaten nach Blob/Parquet (billig, append-only), in PostgreSQL nur noch Aggregate + zuletzt + Alarme; oder ein dediziertes Zeitreihen-/Analytik-System. Der Alarm-Pfad bleibt unverändert — er hängt nur an Kafka, nicht an der DB. Genau diese Umbau-Reihenfolge nennen.

Was geht kaputt, wenn die DB 10 Minuten down ist?

Consumer bekommen Insert-Fehler, committen keine Offsets und pausieren (Backoff). Kafka puffert weiter — bei 7 Tagen Retention sind 10 min nichts. Danach arbeiten die Consumer den Lag ab. Verloren geht nichts; Live-Karte und Alarme sind um die Ausfallzeit verspätet. Das ist der Satz: „Kafka entkoppelt Verfügbarkeit des Ingest von Verfügbarkeit der DB."

Warum reicht PRIMARY KEY (fahrzeug_id, ts) als einziger Index auf den Rohdaten?

Die einzige Rohdaten-Query ist „ein Fahrzeug, ein Zeitfenster" — exakt die führenden Spalten des PK, plus Partition-Pruning über ts. Jeder weitere Index kostet bei 2'000 Inserts/s dauerhaft Schreibarbeit. Flotten-weite Fragen („alle Fahrzeuge über −18° gestern") beantwortet messung_5min, nicht die Rohtabelle.

Nachrichten eines Fahrzeugs kommen aus dem Puffer unsortiert an. Bricht das Fenster?

Innerhalb der Verbindung sendet das Gerät chronologisch, und die Partition erhält die Producer-Reihenfolge — der Normalfall ist also geordnet. Gegen Restfälle (Reconnect, doppelte Sendung) hilft: Fenster-Logik ignoriert Messungen älter als der letzte verarbeitete ts des Fahrzeugs, und der PK verwirft Duplikate. Das erwähne ich als bewusste Vereinfachung.

Sicherheits-Punkt: Was ist der wichtigste Schutz am Ingest?

Geräte-Identität: jedes Fahrzeug authentifiziert sich mit eigenem Zertifikat/Token (pro Gerät widerrufbar), Gateway validiert Schema und Wertebereiche (−40…+40 °C, plausible Koordinaten) und wirft Müll weg, Rate-Limit pro Gerät gegen Amok-Sender. Positionsdaten sind zudem Personenbezug (Fahrer!) — Zugriff rollenbasiert, Export protokolliert.

Interviewer: „Warum nicht einfach alle 10 s in Redis und fertig?"

Redis beantwortet nur die Live-Karte (letzter Wert). Die Aufgabe verlangt 90 Tage Historie (1,5 TB — nicht RAM-tauglich), Kurvenabfragen und ein zeitliches Alarm-Fenster über geordnete Messungen. Antwortmuster: anerkennen, wofür es passt („zuletzt"-Cache wäre legitim), dann mit den Zahlen zeigen, was fehlt.

Wie testest du die Alarm-Logik, bevor sie live geht?

Replay: Rohdaten eines echten Tages in ein Test-Topic einspielen (Offsets ab 0) und die Alarm-Ausgabe gegen bekannte Vorfälle vergleichen — das geht, weil Kafka Nachrichten behält und Consumer-Offsets frei setzbar sind. Dazu Unit-Tests der Fensterlogik mit synthetischen Serien: genau 4:50 über Grenze (kein Alarm), 5:10 (Alarm), Lücke im Funkloch, Nachsende-Batch.

Szenario: Disposition meldet „Karte hängt 20 Minuten hinterher". Diagnose-Reihenfolge?

1) Consumer-Lag im Monitoring — steigt er? Dann ist der Consumer zu langsam oder tot (Rebalancing-Schleife, DB-Latenz). 2) Lag normal ⇒ DB prüfen: blockiert der Upsert (Lock, Autovacuum, fehlende Morgen-Partition)? 3) Beides normal ⇒ FE/API: pollt die Karte noch, cached der Browser? Die eine Metrik, die zuerst zählt, ist der Lag — darum steht sie im Monitor-Alarm.

Übe den Drill, bis du Partition-Key, Consumer-Gruppe, Batch-Insert und das 5-min-Fenster in einem Zug an die Tafel zeichnest — mit den Zahlen 2'000 msg/s, 173 Mio Zeilen/Tag, 1,5 TB.
