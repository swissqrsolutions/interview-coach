Fall: URL-Shortener

Gerüst

Warum?
Kurzer Code → lange URL, extrem leselastig (100:1). Der Redirect-Pfad bleibt minimal, Klicks werden asynchron gezählt.
Wie innen?
Sequenz-ID → Base62-Code, code → long_url als PK-Lookup. Redirect: CDN → Redis → DB, Antwort 302 mit Location. Klick-Event in die Queue, Upsert pro Tag.
Zahlen
62⁷ ≈ 3,5 Billionen Codes. Ca. 40 Writes/s, 4000 Redirects/s, Spitze 20 000/s. PK-Lookup 0,07 ms; 500 000 Links ≈ 58 MB.
Vergleich
Zähler + Base62: eindeutig, aber ratbar. Hash der URL: deterministisch, Kollisionen prüfen. Zufall/Key Generation Service: nicht ratbar, mehr Betrieb.
Produktion
Viraler Link = Hot Key → CDN plus lokaler Cache. Bot-Scans → Format prüfen, Negative Caching, Rate Limit pro IP.
Design
302 statt 301, wenn Klicks und Zieländerung zählen. Statistik nie synchron im Redirect-Pfad. Ratbarkeit ist eine Anforderung.

Antwort-Muster

Frage: Wie funktioniert ein URL-Shortener?

  1. Mechanismus: Eine eindeutige ID wird in Base62 kodiert, der Redirect ist ein Key-Value-Lookup mit 302.
  2. Zahl: 7 Base62-Zeichen geben 3,5 Billionen Codes, die Last ist etwa 100:1 leselastig.
  3. Trade-off: 301 spart Last, aber der Browser cached ihn: keine Klickzählung, kein Zielwechsel.
  4. Produktion: Heisse Links kommen aus CDN und Redis, Klicks zählt ein asynchroner Aggregator.
Kern (die 1-Minuten-Antwort): Ein URL-Shortener bildet einen kurzen Code auf eine lange URL ab und leitet per HTTP-Redirect weiter. Codes entstehen aus einer eindeutigen ID in Base62, 7 Zeichen reichen für 3,5 Billionen Links. Das System ist extrem lese-lastig: Redirects kommen aus Cache und CDN, die Datenbank ist ein einfacher Key-Value-Lookup. Klicks werden asynchron gezählt, damit der Redirect schnell bleibt.

1. Wo sitzt was? (Architektur)

  1. CDN / Load Balancer: nimmt alle Requests an und kann Redirects am Edge cachen. Beispiel: ein beliebter Link wird nie bis zum Service durchgereicht.
  2. Redirect-Service: zustandslos, skaliert horizontal. Er liest den Code, findet die lange URL und antwortet mit 302 Location: ….
  3. Redis: hält heisse Codes. Wenige Prozent der Links bekommen fast alle Klicks.
  4. PostgreSQL: speichert alle Links. Zugriff nur über den Primary Key code.
  5. Create-API: erzeugt neue Codes, prüft die Ziel-URL und Rate Limits. Getrennt vom Redirect-Pfad, weil die Last 100× kleiner ist.
  6. Klick-Stream: jeder Redirect schickt ein Event in eine Queue. Ein Aggregator zählt pro Code und Tag.

2. Die Reise eines Klicks (die Geschichte zum Merken)

  1. Klick: Lea klickt https://s.example.ch/15HZKM in einer E-Mail.
  2. Edge: Das CDN prüft seinen Cache. Bei einem Hit antwortet es sofort. Der Service sieht den Klick dann nicht.
  3. Service: Er prüft das Format (nur Base62, max. Länge). Ungültige Codes gehen nie an die DB.
  4. Redis: GET link:15HZKM liefert die lange URL in ca. 1 ms.
  5. DB bei Miss: Ein PK-Lookup mit Filter auf Ablauf. Danach schreibt der Service den Wert mit TTL in Redis.
  6. Redirect: Der Service antwortet 302 Found mit Location: https://www.admin.ch/…. Der Browser folgt.
  7. Klick zählen: Ein Event geht asynchron in die Queue. Fällt die Queue aus, funktioniert der Redirect trotzdem.

3. Beispiel: API, Datenmodell und die Queries laut gesagt

API:

POST /v1/links   {longUrl, customAlias?, expiresAt?}   (Idempotency-Key)
     → 201 {code, shortUrl, expiresAt}
GET  /{code}     → 302 Location: longUrl  | 404 | 410 (abgelaufen)
GET  /v1/links/{code}/stats?from=2026-11-01&to=2026-11-24 → [{day, clicks}]
DELETE /v1/links/{code} → 204

Datenmodell:

CREATE FUNCTION base62(n bigint) RETURNS text LANGUAGE plpgsql IMMUTABLE AS $$
DECLARE a text := '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
        r text := '';
BEGIN
  IF n = 0 THEN RETURN '0'; END IF;
  WHILE n > 0 LOOP r := substr(a, (n % 62)::int + 1, 1) || r; n := n / 62; END LOOP;
  RETURN r;
END $$;
CREATE TABLE links (
  code       text PRIMARY KEY,
  long_url   text NOT NULL,
  owner_id   bigint,
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz
);
CREATE TABLE click_daily (
  code   text NOT NULL REFERENCES links(code),
  day    date NOT NULL,
  clicks bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (code, day)
);
CREATE SEQUENCE link_id_seq START 1000000000;

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_url_shortener, 500 000 Links, danach gelöscht). Die vorherige Zeile hatte 1 Klick.

  1. Base62: 1 Mrd. ergibt 6 Zeichen (15FTGg). Ab 62⁷ braucht man 8 Zeichen.
  2. Sequenz-Codes sind ratbar: Nach 15HZKM kommt 15HZKN. Wer das nicht will, mischt die ID vorher (z. B. eine umkehrbare Permutation) oder nutzt Zufall plus Kollisionsprüfung.
  3. Lookup: 0,07 ms über den Primary Key. Die DB ist nicht der Engpass, sondern die Zahl der Requests.
  4. Grösse: 500 000 Links brauchen 58 MB mit Index, also ca. 120 Bytes pro Link bei kurzen URLs.
  5. Klick-Upsert: Der Aggregator schreibt 250 Klicks in einem Statement. Pro Klick ein UPDATE würde eine heisse Zeile sperren.

4. Details, die Interviewer fragen

  1. Anforderungen: Kurz-URL erzeugen, weiterleiten, optional eigener Alias, Ablaufdatum, Statistik. Nicht-funktional: Redirect p99 unter 50 ms, sehr hohe Verfügbarkeit, Codes nicht erratbar (falls gefordert).
  2. Schätzung: 100 Mio. neue Links pro Monat sind ca. 40 Writes/s. Lesen zu Schreiben 100:1 gibt ca. 4000 Redirects/s, Spitze ca. 20 000/s.
  3. Speicher: 100 Mio. × 12 × 5 Jahre = 6 Mrd. Links. Bei ca. 500 Bytes mit langen URLs sind das ca. 3 TB. Das passt auf wenige Shards.
  4. Code-Länge: 62⁶ ≈ 57 Mrd., 62⁷ ≈ 3,5 Billionen. 7 Zeichen reichen für Jahrzehnte.
  5. Variante Zähler + Base62: eindeutig ohne Kollision. Verteilte Zähler: jede Instanz holt Blöcke von IDs (z. B. 1000 auf einmal). Nachteil: ratbar, und die Sequenz ist ein zentraler Punkt.
  6. Variante Hash: MD5 oder SHA-256 der URL, die ersten 7 Base62-Zeichen. Gleiche URL gibt gleichen Code. Nachteil: Kollisionen möglich, also prüfen und bei Kollision Salt anhängen.
  7. Variante Key Generation Service: Ein Dienst erzeugt vorab zufällige, freie Codes und gibt sie in Blöcken aus. Schnell, nicht ratbar. Nachteil: eine weitere Komponente mit eigenem Zustand.
  8. 301 vs 302: 301 ist laut RFC 9110 heuristisch cachebar. Browser kommen dann oft nicht mehr vorbei: weniger Last, aber keine Klickzählung und keine Änderung des Ziels. 302 kommt jedes Mal zum Service.
  9. 307 und 308: erhalten die HTTP-Methode. Für GET-Links ist das egal. 308 ist wie 301 heuristisch cachebar.
  10. Caching: Links ändern sich fast nie. Darum lange TTL in Redis und am CDN mit Cache-Control: max-age. Beim Löschen: Redis-DEL und CDN-Purge.
  11. Negative Caching: 404-Antworten kurz cachen. Sonst scannen Bots zufällige Codes direkt gegen die DB.
  12. Sharding: Nach Hash des Codes. Jeder Redirect trifft genau einen Shard. Es gibt keine Queries über Shards hinweg, ausser Statistik pro Besitzer.
  13. Gleiche lange URL zweimal: Entweder ein neuer Code pro Anfrage (eigene Statistik) oder Wiederverwendung pro Besitzer über einen Index auf (owner_id, long_url_hash).
  14. Missbrauch: Phishing und Malware hinter kurzen Links. Ziel-URL beim Erstellen gegen eine Reputationsliste prüfen, Rate Limit pro Nutzer und IP, Meldefunktion.
  15. Statistik: Klicks als Events, nicht als UPDATE pro Klick. Aggregation pro Minute oder Tag. Rohdaten optional in Object Storage für Analysen.

5. Vergleich: drei Varianten für die Code-Erzeugung

  • A. Zähler + Base62: keine Kollision, kürzeste Codes, einfach. Ratbar; braucht verteilte ID-Blöcke.
  • B. Hash der URL, gekürzt: deterministisch, keine zentrale Sequenz. Kollisionen prüfen; gleiche URL für verschiedene Nutzer gibt denselben Code.
  • C. Zufall / Key Generation Service: nicht ratbar, schnell. Kollisionsprüfung oder Vorab-Pool; mehr Betrieb.

6. In der Produktion

  1. Viraler Link überlastet einen Redis-Knoten: Hot Key. Fix: CDN-Caching mit kurzer TTL, lokaler In-Process-Cache vor Redis.
  2. Bot scannt Codes: Viele 404, DB-Last steigt. Fix: Format früh prüfen, Negative Caching, Rate Limit pro IP.
  3. Ziel-URL geändert, alte bleibt: 301 wurde gesendet und im Browser gecacht. Fix: 302 nutzen, wenn Ziele änderbar sein sollen.
  4. Klick-Zählung hinkt: Queue staut sich. Der Redirect läuft weiter; die Zahlen kommen später. Fix: Consumer skalieren, Alarm auf Lag.
  5. Sequenz als Engpass: Jede Instanz fragt pro Link die DB. Fix: CACHE der Sequenz oder ID-Blöcke pro Instanz.
  6. Phishing-Meldungen: Link sperren mit Status statt löschen, Cache und CDN invalidieren, Ziel-Domain blocken.

7. Diagnose: Werkzeuge und Queries

  • Hit Ratio von CDN und Redis (INFO stats: keyspace_hits, keyspace_misses).
  • Statuscode-Verteilung: Anteil 404 und 410 am Edge. Ein Sprung bei 404 heisst Scan oder kaputte Kampagne.
  • pg_stat_statements: Anzahl und Zeit des Lookup-Statements. Es sollte fast nur Index Scans geben.
  • Queue-Lag des Klick-Consumers.
  • p99-Latenz pro Stufe: Edge, Service, Redis, DB.

8. Senior-Punkte

  1. Lese-Pfad und Schreib-Pfad trennen. Der Redirect ist ein eigener, minimaler Service.
  2. 302 ist mein Standard, weil ich Ziele ändern und Klicks zählen will. 301 nur, wenn Last wichtiger ist als Kontrolle.
  3. Statistik nie im Redirect-Pfad synchron schreiben. Events und Aggregation halten den Redirect schnell und robust.
  4. Ratbarkeit ist eine Anforderung, keine Nebensache. Bei privaten Links nehme ich Zufall statt Sequenz.
  5. Die DB ist hier fast trivial. Die echte Arbeit sind Cache, Missbrauchsschutz und Betrieb.

9. Aus dem Projekt

„Einen URL-Shortener habe ich nicht gebaut. Das nächste echte Muster: Bei MATCH ist die Verarbeitung idempotent und crash-sicher, ähnlich wie hier der Upsert für Klicks.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „301 ist besser, weil permanent.“ → Nur für Last. Der Browser cached ihn; man verliert Klicks und kann das Ziel nicht mehr ändern.
  • „MD5 der URL, erste 7 Zeichen, fertig.“ → Falsch. Kollisionen sind möglich und müssen geprüft werden.
  • „Jeder Klick macht UPDATE … SET clicks = clicks + 1.“ → Heisse Zeile, Sperren, langsamer Redirect. Events und Aggregation nutzen.
  • „Auto-Increment-IDs sind sicher.“ → Sie sind ratbar. Jeder kann alle Links durchprobieren.
  • „Wir brauchen NoSQL wegen der Grösse.“ → Ein paar TB Key-Value schafft auch PostgreSQL mit Sharding. Die Wahl ist Betrieb, nicht Pflicht.

11. Selbsttest

Warum?

Was ist der Engpass?

Die Redirect-Requests, nicht die Daten. Darum Caching auf jeder Stufe und zustandslose Services.

Warum trennen Sie Create-API und Redirect-Service?

Die Redirect-Last ist etwa 100-mal grösser. Der Redirect-Pfad bleibt minimal und zustandslos, die Create-API darf komplexer sein.

Wie innen?

Skizzieren Sie den URL-Shortener in einer Minute.

Create-API erzeugt eindeutige ID, kodiert sie in Base62 und speichert code → URL. Der Redirect-Service liest über CDN, Redis und DB und antwortet mit 302. Klicks gehen async in eine Queue.

Wie erzeugen Sie eindeutige Codes in einem verteilten System?

ID-Blöcke aus einer zentralen Sequenz pro Instanz, oder Zufallscodes mit Kollisionsprüfung, oder ein Key Generation Service.

Wo cachen Sie?

Am CDN, in Redis und optional In-Process. Links ändern sich selten, also lange TTL und Invalidierung beim Löschen.

Wie zählen Sie Klicks?

Jeder Redirect schickt ein Event in eine Queue. Ein Aggregator schreibt Summen pro Code und Tag mit einem Upsert.

Was geht kaputt, wenn jeder Klick ein UPDATE clicks = clicks + 1 macht?

Eine heisse Zeile: Jeder Klick wartet auf die Sperre, der Redirect wird langsam. Darum Events in eine Queue und gebündelte Upserts.

Zahlen

Wie lang muss der Code sein?

Base62 mit 7 Zeichen gibt 3,5 Billionen Codes. Bei 100 Mio. Links pro Monat reicht das sehr lange.

Wie schätzen Sie die Last?

100 Mio. Links pro Monat sind ca. 40 Writes/s. Bei 100:1 Lesen ca. 4000 Redirects/s, Spitze ca. 20 000/s.

Wie viel Speicher brauchen Sie?

6 Mrd. Links in 5 Jahren mal ca. 500 Bytes sind ca. 3 TB. Gemessen: 500 000 kurze Links brauchen 58 MB.

Warum reichen 7 Base62-Zeichen?

62 hoch 7 sind rund 3,5 Billionen Codes. Bei 100 Mio. neuen Links pro Monat reicht das für Jahrzehnte.

Vergleich

Warum nicht ein Hash der URL?

Gekürzte Hashes kollidieren. Man muss prüfen und neu würfeln. Ausserdem bekommen alle Nutzer für dieselbe URL denselben Code.

301 oder 302?

302, wenn man Klicks zählen und Ziele ändern will. 301 ist cachebar und spart Last, aber der Service sieht spätere Klicks nicht.

SQL oder NoSQL?

Beides geht, es ist ein Key-Value-Zugriff. PostgreSQL reicht mit Sharding; ein Key-Value-Store spart Betrieb bei sehr grossen Mengen.

Produktion

Was tun Sie gegen Hot Keys?

CDN-Caching und ein kleiner lokaler Cache vor Redis. So trifft ein viraler Link nicht einen einzelnen Knoten.

Wie verhindern Sie Missbrauch?

Ziel-URL gegen Reputationsliste prüfen, Rate Limit beim Erstellen, Sperr-Status für gemeldete Links, Negative Caching gegen Scans.

Szenario: Ein Link wird viral und Redis-Latenz steigt. Was tun Sie?

Hot Key: CDN-TTL setzen, lokalen In-Process-Cache aktivieren. Danach prüfen, ob der Key auf einem überlasteten Shard liegt.

Szenario: Ein Kunde ändert das Ziel, aber Nutzer landen noch auf der alten Seite. Warum?

Wahrscheinlich 301 im Browser-Cache oder alter Wert im CDN. Fix: 302 nutzen, beim Ändern Redis-DEL und CDN-Purge.

Szenario: Plötzlich viele 404 und hohe DB-Last. Was passiert?

Ein Bot rät Codes. Fix: Format früh prüfen, 404 negativ cachen, Rate Limit pro IP, eventuell Codes nicht mehr sequenziell vergeben.

Was geht kaputt, wenn Sie 301 statt 302 senden?

Der Browser cached den Redirect. Spätere Klicks erreichen den Service nie: keine Zählung, und ein geändertes Ziel kommt nicht mehr an.

Design

Wie gehen Sie mit eigenen Aliasen um?

Insert mit ON CONFLICT DO NOTHING. Null Zeilen heisst vergeben, die API antwortet 409.

Wie sharden Sie die Daten?

Nach Hash des Codes. Jeder Redirect trifft einen Shard. Statistik pro Besitzer liegt separat.

Wie behandeln Sie abgelaufene Links?

expires_at im Lookup filtern und 410 Gone antworten. Ein Job löscht oder archiviert alte Zeilen.

Warum ist Ratbarkeit eine Design-Anforderung?

Sequenz-Codes sind durchprobierbar: Nach 15HZKM kommt 15HZKN. Für private Links braucht es Zufall oder eine umkehrbare Permutation.
