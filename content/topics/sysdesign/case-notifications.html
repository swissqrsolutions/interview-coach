Fall: Benachrichtigungs-System

Gerüst

Warum?
Viele Services, ein Versand: Präferenzen, Idempotenz und Rate Limits an einer Stelle. Zustellung ist at-least-once → Dedupe über Schlüssel.
Wie innen?
API prüft Idempotenz-Schlüssel und Präferenzen, eine Zeile pro Kanal (Unique-Key). Worker claimen mit SKIP LOCKED, rufen den Provider, Retry mit Backoff, DLQ.
Zahlen
50 Mio. Nachrichten/Tag ≈ 580/s; Broadcast an 10 Mio. in 10 min ≈ 17 000/s. Backoff 4 s bis 1 h Deckel, nach 5 Versuchen dead. FCM Multicast: 500 Tokens.
Vergleich
Jeder Service sendet selbst: alles dupliziert. DB-Queue: einfach, bis einige tausend/s. Broker: Durchsatz und Replay, mehr Betrieb.
Produktion
Newsletter verstopft Login-Codes → Prioritäts-Queues. Provider-Ausfall → Circuit Breaker, Jitter gegen den Retry-Sturm.
Design
Transaktional und Marketing nie in derselben Queue. Dauerhafte Fehler nie wiederholen (Token löschen). Keine sensiblen Daten im Push.

Antwort-Muster

Frage: Wie designen Sie ein Benachrichtigungs-System für Push, E-Mail und SMS?

  1. Mechanismus: Eine zentrale API prüft Idempotenz und Präferenzen und legt pro Kanal eine Nachricht in eine eigene Queue.
  2. Zahl: 50 Mio. Nachrichten pro Tag sind rund 580 pro Sekunde, ein Broadcast braucht 17 000 pro Sekunde.
  3. Trade-off: Zustellung ist at-least-once, Duplikate verhindert nur der Idempotenz-Schlüssel.
  4. Produktion: Transaktionale Nachrichten bekommen eine eigene Queue, damit kein Newsletter einen Login-Code verzögert.
Kern (die 1-Minuten-Antwort): Ein Benachrichtigungs-System nimmt Ereignisse von vielen Services an und stellt sie über Push, E-Mail, SMS und In-App zu. Eine zentrale API prüft Präferenzen, Idempotenz und Rate Limits und legt pro Kanal eine Nachricht in eine eigene Queue. Kanal-Worker sprechen mit externen Providern, wiederholen mit Backoff und verschieben Hoffnungslose in eine DLQ. Zustellung ist at-least-once; Duplikate verhindert ein Idempotenz-Schlüssel.

1. Wo sitzt was? (Architektur)

  1. Services: senden fachliche Ereignisse, z. B. „Bestellung 981 versendet“. Sie kennen keine Kanäle.
  2. Notification-API: prüft den Idempotenz-Schlüssel, liest Präferenzen, wendet Rate Limits an und rendert das Template in der Sprache des Nutzers (de, fr, it).
  3. PostgreSQL: speichert Präferenzen, Geräte-Tokens, Status jeder Nachricht und die In-App-Inbox.
  4. Queue pro Kanal: Ein langsamer SMS-Provider bremst so keine Push-Nachrichten. Jeder Kanal skaliert eigene Worker.
  5. Kanal-Worker: rufen den Provider, werten die Antwort aus und planen Retries. Beispiel: FCM meldet „Token ungültig“ → Token löschen.
  6. Externe Provider: APNs und FCM für Push, ein E-Mail-Dienst, ein SMS-Gateway. Sie haben eigene Limits und Ausfälle.

2. Die Reise einer Benachrichtigung (die Geschichte zum Merken)

  1. Ereignis: Der Versand-Service meldet „Bestellung 981 von Nutzer 42 ist unterwegs“. Er schickt den Schlüssel order-981:shipped mit.
  2. Fan-out: Die API liest die Präferenzen von Nutzer 42: Push, E-Mail und In-App sind an, SMS ist aus.
  3. Speichern: Pro Kanal entsteht eine Zeile mit status = 'queued'. Kommt das Ereignis doppelt, blockt der Unique-Key.
  4. Claim: Ein Push-Worker holt bis zu 100 fällige Nachrichten. SKIP LOCKED verhindert, dass zwei Worker dieselbe nehmen.
  5. Provider: Der Worker ruft FCM oder APNs mit dem Geräte-Token.
  6. Erfolg: Status sent, Metrik hoch. „Gesendet“ heisst nicht „gelesen“: Der Provider stellt selbst zu.
  7. Fehler: Bei Timeout oder 5xx plant der Worker einen neuen Versuch mit exponentiellem Backoff. Nach 5 Versuchen ist die Nachricht dead und landet in der DLQ.
  8. In-App: Die Inbox-Zeile ist sofort sichtbar. Ist die App offen, kommt sie über WebSocket; sonst beim nächsten Öffnen mit Badge-Zähler.

3. Beispiel: API, Datenmodell und die Queries laut gesagt

API:

POST /v1/notifications                (intern, von Services)
     {idempotencyKey, userId, template, data, priority: "transactional"|"marketing"}
     → 202 Accepted {notificationIds[]}
GET  /v1/users/{id}/inbox?cursor=…    → {items[], unread}
POST /v1/users/{id}/inbox/{nid}:read  → 204
PUT  /v1/users/{id}/preferences       {push: true, email: true, sms: false, quietHours}
POST /v1/devices                      {platform, token}   (Token-Registrierung)

Datenmodell:

CREATE TABLE user_prefs (
  user_id bigint NOT NULL,
  channel text   NOT NULL CHECK (channel IN ('push','email','sms','inapp')),
  enabled boolean NOT NULL DEFAULT true,
  PRIMARY KEY (user_id, channel)
);
CREATE TABLE notifications (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  idempotency_key text   NOT NULL,
  user_id         bigint NOT NULL,
  channel         text   NOT NULL,
  template        text   NOT NULL,
  payload         jsonb  NOT NULL,
  status          text   NOT NULL DEFAULT 'queued'
                  CHECK (status IN ('queued','sending','sent','failed','dead')),
  attempts        int    NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  read_at         timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (idempotency_key, channel)
);
CREATE INDEX notif_due_idx   ON notifications (next_attempt_at) WHERE status = 'queued';
CREATE INDEX notif_inbox_idx ON notifications (user_id, created_at DESC) WHERE channel = 'inapp';

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_notifications, danach gelöscht).

  1. SMS fehlt: Die Präferenz ist aus, also entsteht keine Zeile. Präferenzen wirken beim Fan-out, nicht erst im Worker.
  2. Idempotenz: Der Producer darf blind wiederholen. Der zweite Aufruf erzeugt 0 Zeilen.
  3. Backoff: Die Wartezeit wächst exponentiell und ist gedeckelt. In echt kommt Jitter (Zufall) dazu, sonst wiederholen alle gleichzeitig.
  4. Inbox: Der Badge-Zähler ist ein Count über einen Partial Index. Bei vielen Nutzern speichert man ihn als Zähler pro Nutzer.

4. Details, die Interviewer fragen

  1. Anforderungen: Kanäle (Push, E-Mail, SMS, In-App), Typen (transaktional vs Marketing), Präferenzen und Opt-out, Sprachen, Zustell-Latenz (Sekunden für Sicherheitscodes, Minuten für Newsletter).
  2. Schätzung: 10 Mio. Nutzer, 5 Nachrichten pro Tag = 50 Mio. pro Tag ≈ 580/s. Ein Broadcast an alle in 10 Minuten sind ca. 17 000/s. Die Spitze bestimmt das Design.
  3. Priorität: Eigene Queues für transaktional (Login-Code, Zahlung) und Marketing. Ein grosser Newsletter darf einen Login-Code nie verzögern.
  4. Zustellgarantie: At-least-once zwischen unseren Komponenten. Exactly-once bis zum Gerät gibt es nicht. Wir dedupen bei uns; APNs und FCM können über Collapse-IDs gleiche Nachrichten auf dem Gerät zusammenfassen.
  5. Retry: Nur bei vorübergehenden Fehlern (Timeout, 429, 5xx). Bei dauerhaften (ungültiges Token, ungültige Adresse) sofort aufhören und Daten bereinigen.
  6. Geräte-Tokens: Ein Nutzer hat mehrere Geräte. FCM Multicast nimmt bis zu 500 Tokens pro Aufruf. Meldet der Provider ein Token als nicht registriert, wird es gelöscht.
  7. Rate Limits: Pro Nutzer (z. B. max. 3 Marketing-Nachrichten pro Tag) gegen Spam-Gefühl. Pro Provider gegen Drosselung. Token Bucket pro Kanal.
  8. Quiet Hours: Marketing nachts nicht senden: next_attempt_at auf 08:00 Uhr in der Zeitzone des Nutzers setzen. Sicherheitsnachrichten ignorieren das.
  9. Templates und Sprache: Templates versioniert, Sprache aus dem Profil. In der Schweiz mindestens de, fr, it. Rendern vor dem Einreihen, damit Retries denselben Text senden.
  10. Broadcast: Nicht 10 Mio. Zeilen in einer Transaktion. Ein Job teilt die Nutzer in Blöcke (z. B. 10 000) und reiht Blöcke ein. Bei Push alternativ FCM-Topics.
  11. Outbox beim Producer: Der Bestell-Service schreibt das Ereignis in seiner eigenen Transaktion in eine Outbox. So geht kein Ereignis verloren, wenn er nach dem Commit abstürzt.
  12. Fallback-Kanal: Push nicht zugestellt nach X Minuten → E-Mail. Das braucht einen Zeitplan pro Nachricht und eine Lese-Rückmeldung.
  13. Tracking: Zustell- und Öffnungsraten über Provider-Callbacks und Tracking-Links. Achtung: Datenschutz und Einwilligung für Marketing-Tracking.
  14. Sicherheit: Keine sensiblen Daten in Push-Texten (Sperrbildschirm). Bei Gesundheits- oder Behördendaten nur „Sie haben eine neue Nachricht“ und Inhalt nach Login.

5. Vergleich: drei Design-Varianten

  • A. Jeder Service sendet selbst: schnell gebaut. Aber: Präferenzen, Limits und Provider-Logik sind x-fach dupliziert, keine Gesamtsicht.
  • B. Zentraler Service mit DB-Queue (wie oben): einfach, transaktional, gut beobachtbar. Grenze: einige tausend Nachrichten pro Sekunde, dann wird die Tabelle heiss.
  • C. Zentraler Service mit Broker (Kafka, Service Bus, SQS): hoher Durchsatz, Partitionierung, Replay. Mehr Betrieb; Status und Idempotenz trotzdem in einer DB.

6. In der Produktion

  1. Doppelte Nachrichten: Producer-Retry ohne Schlüssel oder Worker-Absturz nach dem Provider-Call. Fix: Idempotenz-Schlüssel, Status vor und nach dem Call, Collapse-ID beim Provider.
  2. Login-Codes kommen zu spät: Ein Newsletter verstopft die Queue. Fix: Prioritäts-Queues, getrennte Worker-Pools.
  3. SMS-Kosten explodieren: Retry-Schleife oder Bot-Registrierungen. Fix: Limit pro Nummer, Captcha, Budget-Alarm.
  4. Provider-Ausfall: FCM antwortet mit 5xx. Fix: Circuit Breaker, Backoff mit Jitter, Nachrichten bleiben in der Queue.
  5. Retry-Sturm: Nach dem Ausfall wiederholen alle gleichzeitig. Fix: Jitter und begrenzte Parallelität pro Provider.
  6. Tote Tokens: Viele Fehler „nicht registriert“. Fix: Token sofort löschen, Token beim App-Start neu registrieren.

7. Diagnose: Werkzeuge und Queries

  • SELECT channel, status, count(*) FROM notifications WHERE created_at > now() - interval '1 hour' GROUP BY 1, 2;
  • Alter der ältesten fälligen Nachricht pro Kanal und Priorität: now() - min(next_attempt_at) WHERE status = 'queued'.
  • Provider-Fehler nach Code: 429, 5xx, ungültiges Token. Ein Sprung bei 429 heisst: zu schnell senden.
  • DLQ-Grösse und Gründe. Eine wachsende DLQ ist ein Alarm, kein Archiv.
  • End-to-end-Latenz: Ereignis bis sent, als Histogramm pro Priorität.

8. Senior-Punkte

  1. Transaktional und Marketing nie in derselben Queue. Prioritäten sind Architektur, kein Feld.
  2. At-least-once plus Idempotenz ist die ehrliche Garantie. Exactly-once bis zum Handy verspreche ich nicht.
  3. Nur vorübergehende Fehler wiederholen. Dauerhafte Fehler bereinigen Daten (Token, Adresse).
  4. Präferenzen und Opt-out sind Recht, nicht nur Komfort. Marketing ohne Einwilligung ist ein rechtliches Risiko.
  5. Keine sensiblen Inhalte im Push. Der Sperrbildschirm ist öffentlich.
  6. Erst DB-Queue, dann Broker. Ich wechsle, wenn Durchsatz oder Replay es verlangen.

„Ein Benachrichtigungs-System habe ich nicht gebaut. Am nächsten liegen bei DAZiT Kafka-Events zwischen Microservices und bei DigiSanté der Sedex-Messaging-Client als Sidecar für den Nachrichtenaustausch.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Wir garantieren exactly-once.“ → Falsch. Netz und Provider erlauben nur at-least-once. Duplikate verhindert man mit Schlüsseln.
  • „Jeder Fehler wird wiederholt.“ → Falsch. Ungültige Tokens oder Adressen nie wiederholen.
  • „Eine Queue für alles reicht.“ → Ein Newsletter blockiert dann Login-Codes.
  • „Retry sofort und fest alle 5 Sekunden.“ → Retry-Sturm. Exponentiell, gedeckelt, mit Jitter.
  • „Gesendet heisst zugestellt.“ → Nein. Der Provider stellt asynchron zu; das Gerät kann offline sein.

11. Selbsttest

Warum?

Welche Fragen stellen Sie zuerst?

Welche Kanäle, wie viele Nutzer und Nachrichten, wie schnell (Login-Code vs Newsletter), Präferenzen und Opt-out, Sprachen, Broadcasts.

Warum eine Queue pro Kanal?

Kanäle haben andere Latenz, Limits und Ausfälle. Ein langsamer SMS-Provider darf Push nicht bremsen.

Welche Zustellgarantie geben Sie?

At-least-once intern. Exactly-once bis zum Gerät ist nicht möglich.

Wie innen?

Skizzieren Sie das System in einer Minute.

Services senden Ereignisse an eine zentrale API. Sie prüft Idempotenz, Präferenzen und Limits und reiht pro Kanal ein. Kanal-Worker rufen Provider, wiederholen mit Backoff und schieben Tote in eine DLQ.

Wie verhindern Sie Duplikate?

Idempotenz-Schlüssel vom Producer, Unique-Key auf Schlüssel und Kanal. Beim Provider Collapse-IDs.

Wie bauen Sie Retries?

Nur bei vorübergehenden Fehlern. Exponentieller Backoff mit Deckel und Jitter, max. N Versuche, dann DLQ.

Was ist eine DLQ?

Eine Dead Letter Queue für Nachrichten, die nach allen Versuchen scheitern. Man beobachtet sie, analysiert Gründe und spielt nach dem Fix neu ein.

Wie geht kein Ereignis beim Producer verloren?

Transactional Outbox: Ereignis in derselben Transaktion wie die Fachdaten schreiben, ein Relay sendet es danach.

Was geht kaputt, wenn der Worker nach dem Provider-Call und vor dem Status-Update abstürzt?

Die Nachricht bleibt queued und wird erneut gesendet: ein Duplikat beim Nutzer. Abhilfe: Status sending vor dem Call, Collapse-ID beim Provider.

Zahlen

Wie gross ist die Last?

50 Mio. Nachrichten pro Tag sind ca. 580/s. Ein Broadcast an 10 Mio. in 10 Minuten braucht ca. 17 000/s.

Wie senden Sie an 10 Mio. Nutzer?

Ein Job teilt die Nutzer in Blöcke und reiht sie ein. Bei Push Multicast oder Topics. Rate Limits pro Provider beachten.

Was geht kaputt, wenn ein Broadcast an 10 Mio. Nutzer in einer Transaktion eingereiht wird?

Eine riesige Transaktion sperrt die Tabelle und frisst Speicher. Darum Blöcke von z. B. 10 000 Nutzern, bei Push alternativ FCM-Topics.

Vergleich

DB-Queue oder Kafka?

DB-Queue ist einfach und transaktional bis einige tausend pro Sekunde. Kafka für hohen Durchsatz, Partitionierung und Replay.

Warum zuerst eine DB-Queue und erst später ein Broker?

Die DB-Queue ist transaktional, einfach und gut beobachtbar. Erst bei einigen tausend Nachrichten pro Sekunde oder Replay-Bedarf lohnt ein Broker.

Produktion

Wie gehen Sie mit ungültigen Geräte-Tokens um?

Meldet der Provider das Token als nicht registriert, löschen. Die App registriert beim Start neu.

Szenario: Nutzer bekommen jede Nachricht doppelt. Wo suchen Sie?

Producer-Retries ohne Schlüssel oder Worker, die nach dem Provider-Call abstürzen und neu senden. Fix: Idempotenz-Schlüssel, Status-Übergänge prüfen, Collapse-ID.

Szenario: FCM ist 20 Minuten gestört. Was passiert in Ihrem System?

Circuit Breaker öffnet, Nachrichten bleiben queued, Backoff mit Jitter. Danach langsam hochfahren, damit kein Retry-Sturm entsteht. Optional Fallback auf E-Mail für kritische Nachrichten.

Szenario: Die SMS-Rechnung ist zehnmal höher als sonst. Was prüfen Sie?

Retry-Schleifen, Bot-Registrierungen mit SMS-Verifikation, fehlende Limits pro Nummer. Fix: Limits, Captcha, Budget-Alarm.

Was geht kaputt, wenn auch dauerhafte Fehler wiederholt werden?

Ungültige Tokens und Adressen scheitern bei jedem Versuch. Retries verbrennen Kontingent und Geld (SMS). Dauerhafte Fehler: sofort stoppen und Daten bereinigen.

Design

Wie verhindern Sie, dass ein Newsletter Login-Codes verzögert?

Getrennte Queues und Worker-Pools pro Priorität.

Wie setzen Sie Quiet Hours um?

next_attempt_at in die nächste erlaubte Zeit in der Zeitzone des Nutzers schieben. Sicherheitsnachrichten sind ausgenommen.

Wie machen Sie die In-App-Inbox?

Eine Tabelle pro Nutzer mit Index auf Nutzer und Zeit, Ungelesen-Zähler, Live-Updates per WebSocket oder SSE.

Was gehört nicht in eine Push-Nachricht?

Sensible Inhalte wie Gesundheits- oder Finanzdaten. Der Text ist auf dem Sperrbildschirm sichtbar.

Warum rendern Sie das Template vor dem Einreihen?

Retries senden dann exakt denselben Text. Sprache und Template-Version sind beim Fan-out fixiert.
