Fall: Bild-Upload mit Erkennung und Suche

System-Design-Fall · Tier 1 · Quellen: Microsoft Learn (Defender for Storage: Malware Scanning, Limits und Ergebnis-Kanäle), AWS S3 User Guide (Presigned URLs, Ablaufzeit), PostgreSQL 17 Docs (INSERT … ON CONFLICT, SELECT … FOR UPDATE SKIP LOCKED, Indexes, EXPLAIN), Apache Tika Docs (MIME-Erkennung), Kleppmann DDIA Kap. 3 und 11, Alex Xu „System Design Interview“ Vol. 1, Elastic Docs (Similarity/BM25, Language Analyzers, Decompounder, kNN Search und Query, kNN Retriever, Reciprocal Rank Fusion)

Kern (die 1-Minuten-Antwort): Der Client holt sich eine Upload-Intent und lädt das Bild direkt in einen Quarantäne-Bucket. Ein Event startet den Malware-Scan; erst ein sauberes Bild geht über eine Queue an Worker für Thumbnails und Erkennung (Labels, Embeddings). Metadaten liegen in PostgreSQL als Wahrheit, gesucht wird in einem Suchindex, ausgeliefert über ein CDN. Alles ist asynchron, idempotent und hat einen klaren Status pro Bild.

1. Wo sitzt was? (Architektur)

  1. Upload-API: prüft das Token, legt die Bild-Zeile an und gibt eine kurzlebige Upload-URL zurück. Beispiel: POST /v1/images:upload-intent.
  2. Object Storage: speichert die Bytes. Zwei Bereiche: quarantine/ für Ungeprüftes, clean/ für Freigegebenes.
  3. Malware-Scan: scannt jedes neue Objekt und meldet das Ergebnis als Event. Beispiel: Defender for Storage mit On-upload-Scanning.
  4. Queue + Worker: verarbeiten saubere Bilder asynchron: Format prüfen, EXIF entfernen, Thumbnails, Erkennung. Beispiel: 3 Labels und ein Embedding pro Bild.
  5. PostgreSQL: ist die Source of Truth für Besitzer, Status, Labels und Rechte. Beispiel: Tabelle images mit status.
  6. Suchindex: eine Projektion, also eine abgeleitete, schnell lesbare Kopie. Er wird über eine Outbox befüllt und ist jederzeit aus der DB neu baubar.
  7. CDN: liefert Thumbnails und Bilder mit signierten URLs aus. Die API liefert nie Bytes selbst.

2. Die Reise eines Bildes (die Geschichte zum Merken)

  1. Intent: Anna wählt ferien.jpg (2,4 MB). Die App sendet Grösse, Typ und SHA-256. Die API prüft Token und Quota, legt die Zeile mit status = 'pending' an und gibt eine Upload-URL für 15 Minuten zurück.
  2. Bytes hochladen: Die App lädt direkt in quarantine/42/7f3a. Die API sieht die Bytes nie. So skaliert der Upload mit dem Storage, nicht mit den API-Pods.
  3. Scan: Das Storage meldet „neues Objekt“. Der Scanner prüft es und schickt das Ergebnis als Event.
  4. Freigabe: Ein kleiner Consumer liest das Ergebnis. „Sauber“: Objekt nach clean/ kopieren, Status uploaded. „Malicious“: löschen, Status rejected.
  5. Worker: Ein Worker claimt das Bild atomar. Er prüft die Magic Bytes (echter Dateityp), entfernt EXIF mit GPS, rechnet Thumbnails und ruft das Erkennungsmodell auf.
  6. Commit: Labels, Status ready und ein Outbox-Eintrag gehen in einer Transaktion in die DB. Stürzt der Worker vorher ab, bleibt nichts halb.
  7. Index und Push: Ein Relay liest die Outbox und schreibt in den Suchindex. Die App erfährt per Push oder Polling auf GET /v1/images/{id}, dass das Bild fertig ist.
  8. Suche: Anna sucht „berg“. Der Index liefert IDs, die API filtert nach Rechten und gibt signierte CDN-URLs zurück.

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_image_upload, 200 000 Bilder, 540 000 Labels, danach gelöscht). Plan-Zeilen leicht gekürzt (Worker-Zeilen, Hash Cond).

  1. Idempotenz über Daten: Der Unique-Key (owner_id, sha256) macht den zweiten Upload zu „0 rows“. Die API liefert dann die bestehende ID zurück.
  2. Work-Queue in der DB: SKIP LOCKED plus Partial Index auf status = 'uploaded' gibt eine einfache, sichere Queue. Bei sehr hoher Last nimmt man eine echte Queue.
  3. Join ist teuer: Der Label-Index greift, aber die Sortierung nach created_at zwingt einen Seq Scan über alle Bilder: 46 ms.
  4. Projektion für die Suche: Eine denormalisierte Tabelle mit Index (label, created_at DESC) liest nur 118 Zeilen: 0,17 ms. Das ist genau die Idee hinter einem separaten Suchindex.

4. So funktioniert die Suche

Ein Suchindex ist eine Datenstruktur, die Treffer findet, ohne alle Dokumente zu lesen. Hier: Labels und Titel als Text, dazu ein Embedding pro Bild. Beispiele beziehen sich auf Elasticsearch und OpenSearch.

  1. Invertierter Index: eine Tabelle Term → Posting List, also die Liste der Dokument-IDs mit diesem Term. Beispiel: berg → [7, 42, 99]. Eine Suche liest nur die Listen der Suchwörter und schneidet sie.
  2. Analyzer: macht aus Text Terme, beim Indexieren und beim Suchen gleich. Schritte: Tokenizer (Text in Wörter teilen), Lowercase, Stemming (Wortstamm, „Berge“ → „berg“). Der eingebaute german-Analyzer macht genau das, plus Stoppwörter.
  3. Deutsche Komposita: „Bergsee“ ist ein Wort. Der german-Analyzer zerlegt es nicht, „see“ findet es also nicht. Ein Decompounder-Filter fügt Teilwörter wie „berg“ und „see“ hinzu. Elastic empfiehlt hyphenation_decompounder statt des langsameren dictionary_decompounder.
  4. BM25: die Standard-Bewertung in Elasticsearch und OpenSearch. Sie hat drei Teile:
    • TF (Term Frequency) mit Sättigung: Das zehnte „berg“ im Text zählt kaum mehr als das dritte. Parameter k1, Standard 1.2.
    • Längen-Normalisierung: Ein Treffer in einem kurzen Feld zählt mehr als in einem langen. Parameter b, Standard 0.75.
    • IDF (Inverse Document Frequency): Seltene Terme zählen mehr. „matterhorn“ wiegt mehr als „foto“.
  5. Vektorsuche: Ein Modell macht aus Bild oder Text ein Embedding, also einen Vektor aus Zahlen. Ähnliche Inhalte liegen nah beieinander. Gemessen wird oft mit Cosine Similarity, dem Winkel zwischen zwei Vektoren. In Elasticsearch ist cosine der Standard für dense_vector.
  6. Exakt vs. approximativ (kNN): Exakte Suche vergleicht mit jedem Vektor. Sie ist genau, aber langsam bei Millionen Bildern. Approximative Suche nutzt einen HNSW-Graphen (Hierarchical Navigable Small World). Sie ist schnell, findet aber nicht immer die echten Top-k. Den Anteil echter Treffer nennt man Recall.
  7. k und num_candidates: k ist die Zahl der nächsten Nachbarn, die zurückkommen. num_candidates ist die Zahl der geprüften Kandidaten pro Shard, höchstens 10 000. Mehr Kandidaten verbessern meist den Recall, kosten aber mehr Vergleiche.
  8. Filter in der Vektorsuche: Ein Filter wie owner_id wirkt während der approximativen kNN-Suche. So kommen trotzdem k passende Treffer zurück.
  9. Hybride Suche: BM25 findet exakte Wörter, Vektoren finden Bedeutung. Reciprocal Rank Fusion (RRF) mischt beide Ranglisten. Jedes Dokument bekommt pro Liste 1 / (k + Rang), Standard k = 60. RRF braucht keine vergleichbaren Scores, nur Ränge.

Die Query, laut gesagt: „Anna sucht ‚Sonnenuntergang am Bergsee‘. Ich schicke zwei Suchen: BM25 über Titel und Labels, und kNN mit dem Text-Embedding. Beide filtern im Index auf Annas owner_id. RRF mischt die zwei Ranglisten zu 20 Treffern.“

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): 20 Treffer, nur Bilder von owner_id 42. Der Vektor ist gekürzt; echt hat er dims Zahlen. Ein Bild auf Rang 1 in beiden Listen bekommt 1/61 + 1/61 ≈ 0,033. Ein Bild auf Rang 1 nur in einer Liste bekommt 1/61 ≈ 0,016.

  1. Mapping: Der german-Analyzer stemmt Titel und Labels. Für „Bergsee“ → „see“ braucht es zusätzlich einen Decompounder.
  2. BM25-Teil: multi_match sucht in zwei Feldern. Der Filter ändert den Score nicht, er schränkt nur ein.
  3. kNN-Teil: HNSW findet die 20 nächsten Vektoren aus 100 Kandidaten pro Shard. Der Filter gilt schon während der Suche.
  4. RRF: Ein Bild, das in beiden Listen weit oben steht, gewinnt. So ergänzen sich Wort-Treffer und Bedeutungs-Treffer.

5. Details, die Interviewer fragen

  1. Anforderungen zuerst: Funktional: hochladen, Status sehen, nach Labels und Text suchen, löschen. Nicht-funktional: Upload-Antwort unter 1 s, „suchbar“ nach Sekunden bis Minuten, keine Malware ausliefern, Bilder nur für Berechtigte.
  2. Schätzung (Annahmen): 1 Mio. Uploads pro Tag, 3 MB im Schnitt. Das sind ca. 12 Uploads/s, Spitze ×5 ca. 60/s. Eingehend ca. 3 TB pro Tag, ca. 35 MB/s im Schnitt, Spitze ca. 1,4 Gbit/s.
  3. Speicher: 3 TB pro Tag sind ca. 1,1 PB pro Jahr Originale. Thumbnails kosten ca. 10 % dazu. Darum Lifecycle-Regeln: alte Originale in einen kalten Tier.
  4. Metadaten: 1 Mio. Zeilen pro Tag zu ca. 1 KB sind ca. 365 GB pro Jahr. 10 Labels pro Bild sind 3,65 Mrd. Label-Zeilen pro Jahr. Das passt nicht mehr bequem in eine Tabelle: Partitionierung oder Suchindex.
  5. Erkennung: Angenommen 200 ms GPU-Zeit pro Bild. Spitze 60 Bilder/s braucht ca. 12 parallele Inferenzen. Mit Batching weniger GPUs. Die Queue puffert Spitzen, GPUs skalieren nach Queue-Länge.
  6. Suche: 5 Mio. Suchen pro Tag sind ca. 60 QPS, Spitze ca. 300 QPS. Das schafft ein kleiner Suchcluster leicht. Der Engpass ist eher die Rechte-Filterung.
  7. Direkt-Upload: Eine Presigned URL (S3) oder SAS (Azure) erlaubt einen PUT ohne Zugangsdaten. Bei S3 mit SigV4 maximal 7 Tage gültig; für Uploads nimmt man Minuten.
  8. Grosse Dateien: Über einige hundert MB nutzt man Multipart (S3) oder Block-Upload (Azure). Teile laufen parallel und sind einzeln wiederholbar. Achtung: Ein Scan von Teilstücken ist wertlos; gescannt wird das fertige Objekt.
  9. Malware-Scan: Defender for Storage scannt beim Upload Blobs bis 50 GB. Ergebnisse kommen als Blob Index Tags, Alerts, Event Grid oder Log Analytics. Index Tags sind nicht manipulationssicher; für Sicherheit Events nutzen.
  10. Dateityp-Spoofing: Die Endung und der Content-Type lügen oft. Der Worker prüft die Magic Bytes, z. B. mit Apache Tika, und re-encodet das Bild. Ein neu kodiertes JPEG enthält keinen versteckten Payload mehr.
  11. Decompression Bomb: Ein 50-KB-PNG kann 50 000 × 50 000 Pixel haben. Darum vor dem Dekodieren Pixel-Limit prüfen und Worker mit Speicherlimit laufen lassen.
  12. Datenschutz: EXIF enthält oft GPS-Koordinaten. Der Worker entfernt sie vor der Auslieferung. Gesichtserkennung ist rechtlich heikel und braucht eine eigene Grundlage.
  13. Erkennung: Labels vs Embeddings: Labels sind Wörter mit Konfidenz („berg 0,97“). Embeddings sind Vektoren; ähnliche Bilder liegen nah beieinander. Damit geht „finde ähnliche Bilder“ und Freitext-Suche.
  14. Modell-Version: Labels speichern mit model_version. Ein neues Modell bedeutet Re-Processing über die Queue, mit eigener niedriger Priorität.
  15. Suchindex-Konsistenz: Der Index ist eventual consistent. Die Outbox garantiert, dass jede Änderung ankommt. Ein Reindex-Job baut den Index aus der DB neu.
  16. Rechte in der Suche: Jeder Index-Eintrag trägt owner_id oder ACL-Gruppen. Die Suche filtert im Index, nicht erst danach. Sonst stimmen Seiten und Trefferzahlen nicht.
  17. Löschen: Löschen heisst: DB-Zeile, Original, Thumbnails, Index-Eintrag, CDN-Cache. Ein Lösch-Job mit Status ist sicherer als ein einzelner Call.
  18. Fehler im Ablauf: Worker-Absturz → Lease läuft ab, Bild geht zurück in die Queue. Modell-Timeout → Retry mit Backoff, nach N Versuchen DLQ. Scan-Timeout → Status scan_timeout, manuell prüfen, nie automatisch freigeben.

6. Vergleich: drei Design-Varianten

  • A. Direkt-Upload mit Presigned URL: API bleibt klein, Storage trägt die Last, Client kann fortsetzen. Aber: Bytes kommen ungeprüft an. Darum Quarantäne und Scan zwingend.
  • B. Upload über einen Service: Der Service prüft JWT, Grösse und Typ vor dem ersten gespeicherten Byte. Gut bei Storage nur mit Private Endpoints. Aber: Der Service trägt die ganze Bandbreite und muss mitskalieren.
  • C. Synchrone Erkennung im Upload-Request: Einfach, Ergebnis sofort. Aber: Upload-Latenz hängt am Modell, GPU-Spitzen schlagen auf den Nutzer durch, Retries doppeln Arbeit. Nur für kleine Last oder Prototypen.

7. In der Produktion

  1. Bilder hängen in pending: Der Client hat nie hochgeladen oder das Event ging verloren. Fix: Aufräum-Job löscht Intents nach 24 h; ein Reconciler vergleicht Storage und DB.
  2. Scan-Ergebnisse kommen nicht an: Bei Defender wird die Event-Grid-Zustellung an Topics ohne Public Network Access nicht unterstützt. Fix: Netzwerk-Design früh mit der Doku abgleichen, damit die Scan-Ergebnisse zugestellt werden.
  3. GPU-Kosten explodieren: Ein Re-Processing aller Bilder läuft mit voller Priorität. Fix: eigene Queue mit niedriger Priorität und Rate Limit.
  4. Suchtreffer zeigen gelöschte Bilder: Index-Update fehlgeschlagen. Fix: Outbox mit Retry, API prüft Status in der DB vor der Auslieferung.
  5. Worker OOM-killed: Riesige oder bösartige Bilder. Fix: Pixel-Limit vor dem Dekodieren, Memory-Limit, Bild nach 3 Fehlern in die DLQ.
  6. CDN liefert altes Bild nach Löschung: Fix: versionierte URLs plus Purge beim Löschen, kurze Gültigkeit der signierten URLs.

8. Diagnose: Werkzeuge und Queries

  • Status-Verteilung: SELECT status, count(*) FROM images GROUP BY 1; Wächst uploaded, fehlen Worker.
  • Alter des ältesten Jobs: SELECT now() - min(created_at) FROM images WHERE status = 'uploaded'; Das ist die wichtigste Alarm-Metrik.
  • Queue-Metriken: Länge, Alter der ältesten Nachricht, DLQ-Grösse, Verarbeitungszeit pro Stufe (Scan, Thumbs, Erkennung).
  • Defender: Tabelle StorageMalwareScanningResults in Log Analytics für Scan-Historie und Audit.
  • EXPLAIN (ANALYZE, BUFFERS): für Such- und Claim-Queries. Ziel: Index Scan, wenige gelesene Zeilen.
  • Tracing: eine Trace-ID vom Intent bis zum Index-Update, z. B. mit OpenTelemetry. So sieht man, wo ein Bild hängt.

9. Senior-Punkte

  1. Upload-Pfad und Verarbeitungs-Pfad trennen. Der Nutzer wartet nur auf den Upload, nie auf Scan oder Modell.
  2. Nie ungeprüfte Bytes ausliefern. Quarantäne, Scan, Typ-Prüfung und Re-Encoding sind Pflicht bei fremden Dateien.
  3. Ein Status-Automat pro Bild macht Fehler sichtbar und Retries sicher: pending → uploaded → processing → ready oder rejected.
  4. DB ist die Wahrheit, der Index eine Projektion. Ich kann den Index jederzeit wegwerfen und neu bauen.
  5. Rechte im Index filtern, nicht nach der Suche. Sonst stimmen Paging und Trefferzahl nicht, und Daten können leaken.
  6. Erst einfach: PostgreSQL mit Labels und SKIP-LOCKED-Queue reicht für Millionen Bilder. Einen Suchcluster und eine echte Queue füge ich ein, wenn Zahlen es verlangen.

„Bei DigiSanté habe ich eine ereignisgesteuerte Upload-Pipeline mit Malware-Scan und Quarantäne in Azure gebaut. Der Upload antwortet direkt nach dem Speichern. Erst nach dem Scan wird die Datei freigegeben oder gelöscht. Erkennung und Suche habe ich dort nicht gebaut.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

11. Fallen

  • „Die API nimmt die Datei an und ruft das Modell auf.“ → Falsch bei Last. Upload und Verarbeitung entkoppeln, sonst bestimmt die GPU die Upload-Latenz.
  • „Content-Type image/jpeg reicht als Prüfung.“ → Falsch. Der Header kommt vom Client. Magic Bytes prüfen und re-encoden.
  • „Wir speichern Bilder in der Datenbank.“ → Nur Metadaten. Bytes gehören ins Object Storage, die DB hält den Schlüssel.
  • „Der Suchindex ist die Datenbank.“ → Falsch. Er ist async und kann Lücken haben. Wahrheit ist die DB.
  • „Blob Index Tags vom Scanner sind sicher genug für die Freigabe.“ → Laut Microsoft nicht manipulationssicher. Für die Freigabe Events oder Alerts nutzen.
  • „Rechte prüfe ich nach der Suche.“ → Falsch. Trefferzahl und Paging stimmen nicht, und Metadaten können leaken.

12. Fragen

Skizzieren Sie das System in einer Minute.

Upload-Intent, direkter Upload in Quarantäne, Malware-Scan per Event, Queue mit Workern für Thumbnails und Erkennung, PostgreSQL als Wahrheit, Suchindex über Outbox, Auslieferung über CDN.

Welche Fragen stellen Sie zuerst?

Wie viele Uploads pro Tag, welche Grösse, wie schnell muss ein Bild suchbar sein, wer darf was sehen, welche Erkennung (Labels, Text, ähnliche Bilder), wie lange aufbewahren.

Rechnen Sie Speicher und Durchsatz grob.

1 Mio. Uploads à 3 MB sind 3 TB pro Tag, ca. 1,1 PB pro Jahr. Im Schnitt 12 Uploads/s, Spitze ca. 60/s.

Warum lädt der Client direkt ins Storage?

Die API muss keine Bytes tragen und bleibt klein. Das Storage skaliert die Bandbreite. Die API vergibt nur kurzlebige, auf ein Objekt beschränkte Rechte.

Wann laden Sie trotzdem über einen Service hoch?

Wenn das Storage nur privat erreichbar ist oder man vor dem ersten Byte prüfen muss, z. B. JWT und Dateityp. Preis: Der Service trägt die Bandbreite.

Wie verhindern Sie Malware im System?

Quarantäne-Bereich, Scan jedes Objekts, Freigabe nur per Scan-Event, Magic-Bytes-Prüfung, Re-Encoding. Ungeprüftes wird nie ausgeliefert.

Warum asynchrone Erkennung?

Das Modell ist langsam und teuer. Die Queue puffert Spitzen, Worker skalieren nach Queue-Länge, und Fehler werden einzeln wiederholt.

Wie verhindern Sie, dass zwei Worker dasselbe Bild verarbeiten?

Atomarer Claim mit FOR UPDATE SKIP LOCKED oder die Lease einer Queue. Dazu idempotente Verarbeitung: Labels ersetzen, nicht anhängen.

Was passiert, wenn ein Worker mitten in der Arbeit abstürzt?

Die Lease oder der Status läuft ab, ein anderer Worker übernimmt. Weil das Ergebnis in einer Transaktion geschrieben wird, gibt es keinen halben Zustand.

Wie machen Sie den Upload idempotent?

Idempotency-Key am Intent und ein Unique-Key auf Besitzer und SHA-256. Ein Retry liefert dieselbe Bild-ID.

Wie bauen Sie die Suche?

Labels und Text in einen Suchindex mit Besitzer- oder ACL-Feld. Für „ähnliche Bilder“ Embeddings in einem Vektorindex. Gefüllt über Outbox aus der DB.

Labels oder Embeddings?

Labels sind einfach, erklärbar und filterbar. Embeddings finden ähnliche Bilder und Freitext. Oft beides: Labels für Filter, Vektoren für Ranking.

Wie bleibt der Suchindex konsistent?

Gar nicht sofort. Die Outbox garantiert, dass jede Änderung ankommt. Ein Reindex-Job baut ihn aus der DB neu. Die API prüft den Status vor der Auslieferung.

Wie setzen Sie Rechte in der Suche um?

Jeder Index-Eintrag trägt Besitzer oder ACL-Gruppen. Die Suche filtert im Index. So stimmen Trefferzahl und Paging.

Warum ist Ihre erste Such-Query langsam?

Filter auf Labels, Sortierung nach Datum aus einer anderen Tabelle. Die DB muss alle Bilder lesen. Eine Projektion mit Index (label, created_at) macht daraus einen Index Scan.

Wie gehen Sie mit grossen Dateien um?

Multipart- oder Block-Upload, Teile parallel und einzeln wiederholbar. Gescannt wird das fertige Objekt, nicht die Teile.

Was ist eine Decompression Bomb?

Eine kleine Datei, die beim Dekodieren riesig wird. Schutz: Pixel-Limit vor dem Dekodieren, Speicherlimit im Worker.

Welche Datenschutz-Punkte nennen Sie?

EXIF mit GPS entfernen, Rechte pro Bild, Löschung überall inklusive Index und CDN, Gesichtserkennung nur mit Rechtsgrundlage.

Wie löschen Sie ein Bild vollständig?

Ein Lösch-Job mit Status: DB-Zeile, Original, Thumbnails, Index-Eintrag, CDN-Purge. Jeder Schritt idempotent und wiederholbar.

Was passiert bei einem neuen Erkennungsmodell?

Labels tragen die Modell-Version. Ein Re-Processing läuft über eine eigene Queue mit niedriger Priorität und Rate Limit.

Welche Metriken alarmieren Sie?

Alter des ältesten Jobs pro Stufe, DLQ-Grösse, Fehlerrate von Scan und Modell, Zeit vom Upload bis ready.

Wie skaliert die Datenbank?

Metadaten sind klein. Label-Zeilen wachsen schnell: Partitionierung nach Zeit oder Auslagerung der Suche in einen Index. Lese-Replikate für Statusabfragen.

Was ist ein invertierter Index, und was macht BM25 damit?

Eine Tabelle Term → Liste der Dokument-IDs. BM25 bewertet die Treffer: Termhäufigkeit mit Sättigung (k1 = 1.2), Längen-Normalisierung (b = 0.75) und seltene Terme zählen mehr (IDF).

Was geht kaputt, wenn Nutzer „see“ suchen, aber nur „Bergsee“ im Index steht?

Ohne Zerlegung gibt es keinen Treffer, denn „bergsee“ ist ein einziger Term. Lösung: ein Decompounder-Filter im Analyzer, z. B. hyphenation_decompounder.

Warum kombinieren Sie BM25 und Vektorsuche?

BM25 findet exakte Wörter und Namen, Vektoren finden Bedeutung und ähnliche Bilder. RRF mischt beide Ranglisten nach Rang, mit 1 / (60 + Rang) pro Liste. Approximatives kNN (HNSW) ist schnell, aber der Recall ist nicht 100 %.

Szenario: Nach einem Marketing-Event kommen 10× mehr Uploads. Was passiert?

Upload und Storage halten, weil sie direkt laufen. Die Queue wächst, Bilder sind später suchbar. Worker und GPUs skalieren nach Queue-Länge; die Nutzer sehen „in Bearbeitung“.

Szenario: Ein Nutzer findet ein Bild eines anderen Nutzers in seiner Suche. Was ist passiert?

Wahrscheinlich fehlt der Rechte-Filter im Index oder ein Eintrag hat falsche ACL-Felder. Sofort: Rechte-Prüfung in der API vor der Auslieferung. Dann Index-Mapping korrigieren und neu indexieren.

Szenario: Viele Bilder bleiben im Status uploaded hängen. Wie gehen Sie vor?

Alter des ältesten Jobs prüfen, Worker-Logs, DLQ. Typisch: Modell-Timeouts oder OOM. Fix: Retry mit Backoff, Pixel-Limit, mehr Worker; hängende Claims per Timeout zurücksetzen.
