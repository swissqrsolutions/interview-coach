Fall: Verteilter Cache

Kern (die 1-Minuten-Antwort): Ein verteilter Cache ist ein In-Memory-Key-Value-Speicher über viele Knoten, der eine langsame Datenbank entlastet. Schlüssel werden über Partitionierung (Consistent Hashing oder feste Hash Slots) verteilt, jede Partition hat Replikate für Ausfälle. Volle Knoten evicten mit LRU oder LFU. Die DB bleibt die Wahrheit; Änderungen invalidieren den Cache über eine Outbox mit Versionsnummer, und eine TTL begrenzt jede Veraltung.

Gerüst

Warum?
500 000 Reads/s schafft die DB nicht: RAM über viele Knoten entlastet sie. Datenverlust ist erlaubt, es ist ein Cache.
Wie innen?
16 384 Hash Slots (CRC16), Smart Client routet direkt; MOVED/ASK bei Umzug. Replikat je Shard asynchron in anderer Zone.
Zahlen
2 TB Arbeitsmenge / 50 GB pro Knoten ≈ 40 Primär-Shards, mit Replikaten 80. mod N verschiebt beim Skalieren 75 % der Keys.
Vergleich
In-Process (schnell, pro Instanz) vs verteilt (geteilt, Netz-Hop) vs zwei Stufen L1 + L2. Smart Client vs Proxy.
Produktion
Hot Key macht einen Shard heiss. Kalter Start trifft die DB. Invalidierung über Outbox mit Version, DEL ist idempotent.
Design
DB bleibt die Wahrheit, TTL als Netz. Kein Cache für Werte, die nie veralten dürfen. Managed Service vor Eigenbau.

Antwort-Muster

Frage: Entwerfen Sie einen verteilten Cache.

  1. Mechanismus: Keys liegen über Hash Slots auf Shards im RAM, jeder Shard hat ein Replikat in einer anderen Zone.
  2. Zahl: 2 TB bei 50 GB pro Knoten sind rund 40 Primär-Shards; mod N würde beim Skalieren 75 Prozent der Keys verschieben.
  3. Trade-off: Die Replikation ist asynchron, ein Failover kann letzte Writes verlieren; für einen Cache ist das ok.
  4. Produktion: Invalidiert wird über eine Outbox mit Version, die TTL ist das Sicherheitsnetz.

1. Wo sitzt was? (Architektur)

  1. Client-Bibliothek: berechnet den Shard für einen Key, hält einen kleinen L1-Cache im Prozess und setzt harte Timeouts. Beispiel: GET product:4711 geht direkt an Shard 2.
  2. Shards: jeder hält einen Teil der Keys im RAM. In Redis Cluster sind das Bereiche der 16 384 Hash Slots.
  3. Replikate: kopieren asynchron vom Primär-Shard, in einer anderen Zone. Bei Ausfall wird ein Replikat befördert.
  4. PostgreSQL: die Wahrheit. Bei Miss liest die App hier und füllt den Cache (Cache-Aside).
  5. Invalidator: liest Änderungen aus der Outbox und löscht die betroffenen Keys.
  6. Failure Detection: erkennt tote Knoten per Gossip (Redis Cluster) oder Sentinel und startet den Failover.

2. Die Reise eines Reads und einer Änderung (die Geschichte zum Merken)

  1. Slot berechnen: Die Client-Lib rechnet den Slot von product:4711 und kennt die Slot-Karte. Sie fragt direkt den richtigen Shard.
  2. GET: Hit in ca. 1 ms. Bei falscher Karte antwortet der Knoten mit MOVED, die Lib aktualisiert ihre Karte.
  3. Miss: Die App liest aus der DB. Kommen 1000 Requests gleichzeitig, lädt nur einer (Single Flight oder Lock mit SET NX).
  4. Füllen: SET product:4711 {…, version: 1} EX 3600. Die TTL hat etwas Zufall (Jitter).
  5. Änderung: Ein Preis ändert sich. UPDATE und Outbox-Eintrag gehen in eine Transaktion. Die Version steigt auf 2.
  6. Invalidator: liest die Outbox und löscht den Key. Fällt er kurz aus, holt er nach; nichts geht verloren.
  7. Nächster Read: Miss, lädt Version 2. Die Veraltung dauerte nur Millisekunden bis Sekunden.
  8. Ausfall: Shard 2 stirbt. Ein Replikat wird Primär. Fehlende letzte Writes sind kein Drama: Der nächste Miss lädt aus der DB.

3. Beispiel: API, Datenmodell und die Queries laut gesagt

Cache-API (Client-Bibliothek, angelehnt an Redis):

get(key)                         → value | null
set(key, value, ttl)             → ok
delete(key)                      → ok
getOrLoad(key, loader, ttl)      → value     (Single Flight bei Miss)
mget(keys[])                     → values[]  (pro Shard gebündelt)

Datenmodell der DB-Seite:

CREATE TABLE products (
  id      bigint PRIMARY KEY,
  name    text NOT NULL,
  price   numeric(10,2) NOT NULL,
  version bigint NOT NULL DEFAULT 1
);
CREATE TABLE cache_outbox (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  cache_key  text NOT NULL,
  version    bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  sent_at    timestamptz
);

Query 1, laut gesagt: „Ich ändere den Preis, erhöhe die Version und schreibe in derselben Transaktion einen Outbox-Eintrag. Entweder beides oder nichts.“

BEGIN;
WITH u AS (
  UPDATE products SET price = 19.90, version = version + 1
  WHERE id = 4711
  RETURNING id, version)
INSERT INTO cache_outbox (cache_key, version)
SELECT 'product:' || id, version FROM u
RETURNING cache_key, version;
  cache_key   | version
--------------+---------
 product:4711 |       2
COMMIT;

Query 2, laut gesagt: „Der Invalidator holt bis zu 500 offene Einträge. Mehrere Invalidatoren stören sich dank SKIP LOCKED nicht.“

UPDATE cache_outbox SET sent_at = now()
WHERE id IN (SELECT id FROM cache_outbox
             WHERE sent_at IS NULL
             ORDER BY id LIMIT 500
             FOR UPDATE SKIP LOCKED)
RETURNING cache_key, version;
  cache_key   | version
--------------+---------
 product:4711 |       2

Query 3, laut gesagt: „Warum nicht einfach hash mod N für die Shards? Ich rechne aus, wie viele Keys beim Schritt von 3 auf 4 Knoten den Knoten wechseln.“

SELECT count(*) FILTER (WHERE abs(hashtext('product:' || g)) % 3
                           <> abs(hashtext('product:' || g)) % 4) * 100.0 / count(*)
       AS prozent_verschoben_mod3_zu_mod4
FROM generate_series(1, 100000) g;
 prozent_verschoben_mod3_zu_mod4
---------------------------------
             74.9010000000000000

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_distributed_cache, 100 000 Produkte, danach gelöscht).

  1. Atomar: Preis und Invalidierungs-Auftrag sind in einer Transaktion. Ein Absturz zwischen DB-Write und Cache-DEL kann so keinen alten Wert hinterlassen.
  2. Version: Der Cache-Wert trägt die Version. Ein Leser, der einen alten Wert zurückschreiben will, kann vorher vergleichen. Das schliesst das klassische Race.
  3. At-least-once: Der Invalidator kann einen Key doppelt löschen. Das ist harmlos: DEL ist idempotent.
  4. mod N: 75 % der Keys wechseln beim Skalieren den Knoten. Das sind 75 % Misses auf einen Schlag. Darum Hash Slots oder Consistent Hashing (ca. 1/N bewegt sich).

4. Details, die Interviewer fragen

  1. Anforderungen: get, set, delete mit TTL; p99 unter 5 ms; sehr hoher Durchsatz; Datenverlust erlaubt (es ist ein Cache); horizontal skalierbar; überlebt Knotenausfall.
  2. Schätzung: 500 000 Reads/s, 50 000 Writes/s, Werte ca. 1 KB. Das sind ca. 550 MB/s Netz. Arbeitsmenge 2 TB.
  3. Kapazität: Bei ca. 50 GB nutzbarem RAM pro Knoten sind 2 TB ca. 40 Primär-Shards, mit je einem Replikat 80 Knoten. Pro Shard ca. 14 000 Ops/s; der Engpass ist hier RAM, nicht CPU.
  4. Partitionierung: Redis Cluster nutzt 16 384 Hash Slots (CRC16). Slots ziehen als Ganzes um. Memcached-Clients nutzen meist einen Consistent-Hash-Ring.
  5. Routing: Smart Client (kennt die Karte, ein Hop) oder Proxy (Client simpel, ein Hop mehr). Redis Cluster antwortet bei falscher Karte mit MOVED oder während eines Umzugs mit ASK.
  6. Replikation: Asynchron. Failover kann die letzten Writes verlieren. Für einen Cache meist akzeptabel, für Sessions oder Locks nicht.
  7. Eviction: LRU oder LFU, approximiert über Stichproben. Für reine Caches allkeys-lru oder allkeys-lfu. Standard in Open-Source-Redis ist noeviction.
  8. Invalidierung: Löschen nach DB-Commit, über Outbox oder CDC. TTL als Sicherheitsnetz. Versionen im Wert gegen Races.
  9. Stampede: Viele gleichzeitige Misses auf einen Key. Schutz: Single Flight, Lock pro Key, stale-while-revalidate, TTL-Jitter. Facebook nutzt dafür Leases: Nur der Inhaber der Lease darf füllen.
  10. Hot Keys: Ein Key trifft immer einen Shard. Schutz: L1-Cache im Prozess, Key-Kopien mit Suffix auf mehrere Shards, Read-Replikate.
  11. Grosse Werte: Redis führt Befehle single-threaded aus. Ein 10-MB-Wert blockiert andere. Werte klein halten, gross ins Object Storage.
  12. Multi-Key-Operationen: Funktionieren nur im selben Slot. Hash Tags wie {user:42}:cart erzwingen das.
  13. Kalter Start: Nach Neustart ist ein Shard leer, die DB bekommt die volle Last. Schutz: Replikat befördern statt leer starten, Warm-up, Rate Limit auf DB-Loads. Facebook nutzt einen kleinen Gutter-Pool als Ersatz für ausgefallene Knoten.
  14. Sicherheit: Cache nicht ins Internet, TLS, ACLs pro Service, keine sensiblen Daten ohne Bedarf; ein Cache-Dump ist ein Datenleck.

5. Vergleich: drei Design-Varianten

  • A. Nur In-Process-Cache pro Instanz: Nanosekunden, kein Netz. Aber: jede Instanz hat eine eigene Kopie, Invalidierung über alle Instanzen ist schwer, Grösse begrenzt.
  • B. Zentraler verteilter Cache (Redis Cluster, Memcached): eine Kopie, ein DEL invalidiert für alle, skaliert mit Knoten. Preis: Netz-Hop, eigener Betrieb.
  • C. Zwei Stufen (L1 im Prozess + L2 verteilt): schnellste Reads und Schutz vor Hot Keys. Preis: zwei Invalidierungen, L1 mit kurzer TTL oder Pub/Sub-Invalidierung.

6. In der Produktion

  1. DB bricht nach Cache-Failover ein: Kalter Shard, alle Reads gehen an die DB. Fix: Replikate in anderer Zone, Rate Limit auf DB-Loads, Stampede-Schutz.
  2. Alte Preise im Shop: DEL vergessen oder Race. Fix: Outbox-Invalidierung, Versionen, kurze TTL.
  3. Latenz-Spitzen: Grosse Keys oder KEYS *. Fix: Werte klein halten, SCAN, Slowlog überwachen.
  4. Ein Shard bei 100 % CPU: Hot Key. Fix: L1-Cache, Key-Splitting.
  5. OOM-Fehler bei Writes: noeviction aktiv. Fix: Eviction-Policy für reine Caches setzen, maxmemory prüfen.
  6. Scale-out macht alles langsam: Slot-Umzug kostet Netz. Fix: einen Knoten nach dem anderen, ausserhalb der Spitze.

7. Diagnose: Werkzeuge und Befehle

  • INFO stats: keyspace_hits, keyspace_misses, evicted_keys. INFO memory: Speicher und Policy.
  • CLUSTER SHARDS oder CLUSTER SLOTS: Slot-Verteilung. redis-cli --cluster check: Gesundheit.
  • redis-cli --bigkeys, --hotkeys (nur mit LFU-Policy), MEMORY USAGE key.
  • SLOWLOG GET 10, LATENCY DOCTOR: langsame Befehle.
  • Outbox-Lag: SELECT now() - min(created_at) FROM cache_outbox WHERE sent_at IS NULL;
  • App-Metriken: Hit Ratio pro Key-Präfix, Loader-Aufrufe pro Sekunde, Timeouts zum Cache.

8. Senior-Punkte

  1. Ein Cache darf jederzeit leer sein. Die DB muss einen kalten Cache gedrosselt überleben.
  2. Invalidierung ist das eigentliche Problem. Ich löse sie mit Outbox oder CDC, Versionen und TTL als Netz.
  3. Feste Slots statt mod N. Umzüge sind dann explizit und betreffen nur einen Teil.
  4. Hot Keys und Stampedes plane ich vorab, nicht nach dem ersten Ausfall.
  5. Kein Cache für Daten, die nicht veralten dürfen, z. B. Kontostand beim Bezahlen. Dort lese ich aus der DB.
  6. Managed Service vor Eigenbau. Einen eigenen verteilten Cache zu bauen lohnt fast nie; das Design muss ich trotzdem verstehen.

9. Dein Beispiel

10. Fallen

  • „Redis-Replikation verliert keine Daten.“ → Falsch. Sie ist asynchron; bei Failover fehlen die letzten Writes.
  • „hash mod N reicht für die Verteilung.“ → Beim Skalieren wechseln 75 % der Keys, siehe Messung.
  • „Bei einer Änderung schreibe ich den neuen Wert in den Cache.“ → Race bei parallelen Writes. Löschen plus Version ist sicherer.
  • „Erst Cache löschen, dann DB ändern.“ → Ein Leser lädt dazwischen den alten Wert wieder hinein.
  • „Mehr Knoten lösen Hot Keys.“ → Nein. Ein Key liegt immer auf einem Shard.

11. Selbsttest

Warum?

Warum eine Outbox für die Invalidierung?

DB-Änderung und Invalidierungs-Auftrag sind in einer Transaktion. Ein Absturz dazwischen lässt keinen alten Wert zurück.

Warum darf ein verteilter Cache Daten verlieren?

Er ist eine Kopie: Die DB bleibt die Wahrheit, ein Miss lädt den Wert neu. Darum reicht asynchrone Replikation.

Wie innen?

Wie verteilen Sie die Keys?

Feste Hash Slots wie Redis Cluster oder Consistent Hashing. Beides bewegt beim Skalieren nur einen Teil der Keys.

Was passiert bei einem Knotenausfall?

Ein Replikat wird Primär. Die letzten async Writes können fehlen. Der Cache lädt fehlende Werte bei Miss aus der DB.

Was sind MOVED und ASK?

Redirects von Redis Cluster. MOVED: Slot liegt dauerhaft woanders, Karte aktualisieren. ASK: Slot zieht gerade um, nur diese Anfrage woanders stellen.

Wie machen Sie Multi-Key-Operationen im Cluster?

Alle Keys müssen im selben Slot liegen. Hash Tags in geschweiften Klammern erzwingen das.

Was geht kaputt, wenn Sie Keys mit hash mod N verteilen?

Beim Schritt von 3 auf 4 Knoten wechseln rund 75 % der Keys den Knoten: eine Miss-Welle auf die DB. Hash Slots oder Consistent Hashing bewegen nur einen Teil.

Zahlen

Wie viele Knoten brauchen Sie?

2 TB Arbeitsmenge bei ca. 50 GB pro Knoten sind ca. 40 Primär-Shards, mit Replikaten 80. Der Engpass ist RAM.

Wie viele Hash Slots hat Redis Cluster, und wie wird der Slot berechnet?

16 384 Slots; der Slot ist CRC16 des Keys modulo 16 384. Slots ziehen beim Skalieren als Ganzes um.

Was geht kaputt, wenn ein einzelner Wert 10 MB gross ist?

Redis arbeitet single-threaded: Der grosse Wert blockiert alle anderen Befehle auf dem Shard. Werte klein halten, Grosses ins Object Storage.

Vergleich

Smart Client oder Proxy?

Smart Client spart einen Hop, braucht aber Logik in jeder Sprache. Proxy hält Clients simpel und kostet Latenz.

In-Process, verteilt oder beides?

Oft beides: L1 im Prozess mit kurzer TTL gegen Hot Keys, L2 verteilt als gemeinsame Kopie.

Wann cachen Sie nicht?

Wenn Werte nie veralten dürfen, z. B. Kontostand beim Bezahlen, oder wenn die Hit Ratio zu klein ist.

Was geht kaputt, wenn der L1-Cache im Prozess keine kurze TTL hat?

Jede Instanz behält alte Werte, obwohl L2 längst invalidiert wurde. Kurze L1-TTL oder Pub/Sub-Invalidierung begrenzen das.

Produktion

Was ist eine Cache Stampede und wie verhindern Sie sie?

Viele gleichzeitige Misses auf einen Key überlasten die DB. Schutz: Single Flight, Lock oder Lease pro Key, stale-while-revalidate, TTL-Jitter.

Was tun Sie gegen Hot Keys?

L1-Cache im Prozess, Key-Kopien auf mehreren Shards, Lesen von Replikaten.

Was ist ein kalter Start und wie schützen Sie die DB?

Ein leerer Cache nach Neustart schickt alle Reads an die DB. Schutz: Replikat befördern, Warm-up, Rate Limit auf Loads.

Szenario: Nach einem Deployment sehen Kunden alte Preise. Wo suchen Sie?

Fehlt die Invalidierung im neuen Code-Pfad? Outbox-Lag prüfen, Race zwischen Read und Write, L1-Caches in den Instanzen. Fix: Outbox, Versionen, kurze TTL.

Szenario: Ein Cache-Knoten ist bei 100 % CPU, die anderen bei 20 %. Was tun Sie?

Hot Key oder schlechte Slot-Verteilung. Mit --hotkeys und Metriken pro Key prüfen. Fix: L1-Cache, Key-Splitting oder Slots umverteilen.

Szenario: Nach dem Hinzufügen von Knoten bricht die DB ein. Warum?

Viele Keys haben den Knoten gewechselt und sind Misses, typisch bei mod N. Fix: Slots oder Consistent Hashing, schrittweise skalieren, Stampede-Schutz.

Was geht kaputt, wenn alle Replikate in derselben Zone wie ihr Primär laufen?

Ein Zonenausfall nimmt Primär und Replikat zugleich mit: kalter Shard, Miss-Welle auf die DB. Replikate gehören in eine andere Zone.

Design

Skizzieren Sie den verteilten Cache in einer Minute.

Shards im RAM über Hash Slots verteilt, je mit Replikat. Smart Client routet direkt. Cache-Aside mit TTL, Invalidierung über Outbox, Eviction mit LRU oder LFU, Failover per Gossip oder Sentinel.

Wie bleibt der Cache konsistent mit der DB?

Gar nicht perfekt. Delete nach Commit über Outbox oder CDC, Versionen gegen Races, TTL als Sicherheitsnetz.

Welche Eviction-Policy wählen Sie?

Für reine Caches allkeys-lru oder allkeys-lfu. LFU übersteht Scans besser. noeviction nur, wenn der Speicher kein Cache ist.

Warum gehört der Kontostand beim Bezahlen nicht in den Cache?

Er darf nie veralten, ein Cache liefert aber per Definition manchmal alte Werte. Solche Reads gehen direkt an die DB.
