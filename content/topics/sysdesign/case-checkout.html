Fall: E-Commerce-Checkout

System-Design-Fall · Tier 2 · Quellen: Stripe API Reference (Idempotent Requests: Schlüssel bis 255 Zeichen, frühestens nach 24 h entfernt, Parameter-Vergleich), PostgreSQL 17 Docs (Transaktionen, CHECK Constraints, INSERT … ON CONFLICT, UPDATE … RETURNING), microservices.io (Saga, Transactional Outbox), Kleppmann DDIA Kap. 7 und 9

Kern (die 1-Minuten-Antwort): Der Checkout macht aus einem Warenkorb eine bezahlte Bestellung, ohne doppelte Belastung und ohne Überverkauf. Die Bestellung entsteht mit einem Idempotenz-Schlüssel; der Bestand wird mit einem bedingten UPDATE reserviert; Bestellung, Reservierung und ein Outbox-Event gehen in eine Transaktion. Die Zahlung läuft beim Payment-Provider mit eigenem Idempotenz-Schlüssel und wird per Webhook bestätigt. Fehler kompensiert eine Saga: Reservierung freigeben oder erstatten.

1. Wo sitzt was? (Architektur)

  1. Warenkorb und Preise: liefern einen Snapshot: Artikel, Preis, Rabatt, MWST zum Zeitpunkt des Checkouts. Spätere Preisänderungen ändern die Bestellung nicht.
  2. Checkout-Service: erzeugt die Bestellung, reserviert Bestand und steuert die Schritte der Saga.
  3. PostgreSQL: Bestellung, Positionen, Bestand und Outbox in einer DB. So geht der kritische Teil in eine Transaktion.
  4. Payment-Provider: belastet die Karte oder TWINT. Er ist extern und kann langsam sein oder doppelt antworten.
  5. Webhook-Endpoint: empfängt „Zahlung erfolgreich“ oder „fehlgeschlagen“. Er prüft die Signatur und ist idempotent.
  6. Broker und Folge-Services: Versand, Bestätigungs-Mail und Buchhaltung reagieren auf order.paid aus der Outbox.

2. Die Reise einer Bestellung (die Geschichte zum Merken)

  1. Kaufen: Kundin 42 klickt „Kaufen“ für 2 × Parfum à 89.90 CHF. Die App sendet den Schlüssel c42-cart-8f1e mit. Ein Doppelklick schickt denselben Schlüssel.
  2. Eine Transaktion: Bestellung anlegen, Bestand bedingt reservieren, Position und Outbox-Event schreiben. Alles oder nichts.
  3. Zahlung: Der Service erzeugt beim Provider eine Zahlung mit eigenem Idempotenz-Schlüssel (z. B. order-1). Ein Retry belastet nicht doppelt.
  4. Webhook: Der Provider meldet „succeeded“, oft Sekunden später und manchmal mehrfach.
  5. Bezahlt: Ein bedingtes UPDATE setzt paid nur aus pending_payment. Der zweite Webhook ändert nichts.
  6. Folgen: Das Event order.paid geht über die Outbox an Versand, Mail und Buchhaltung.
  7. Kompensation: Scheitert die Zahlung oder kommt nach 15 Minuten nichts, storniert die Saga: Reservierung zurück, Bestellung cancelled. War schon Geld da, folgt eine Erstattung.

3. Beispiel: API, Datenmodell und die Queries laut gesagt

API:

POST /v1/checkout            {cartId, shippingAddressId, paymentMethod}
     Idempotency-Key: c42-cart-8f1e
     → 201 {orderId, status: "pending_payment", paymentRedirectUrl}
GET  /v1/orders/{id}         → {status, items[], totalChf}
POST /v1/webhooks/payments   (vom Provider, signiert) → 200
POST /v1/orders/{id}:cancel  → 202

Datenmodell:

CREATE TABLE inventory (
  sku       text PRIMARY KEY,
  available int NOT NULL CHECK (available >= 0),
  reserved  int NOT NULL DEFAULT 0 CHECK (reserved >= 0)
);
CREATE TABLE orders (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id     bigint NOT NULL,
  idempotency_key text   NOT NULL UNIQUE,
  status          text   NOT NULL DEFAULT 'pending_payment'
                  CHECK (status IN ('pending_payment','paid','cancelled','shipped')),
  total_chf       numeric(12,2) NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE order_items (
  order_id  bigint NOT NULL REFERENCES orders(id),
  sku       text   NOT NULL REFERENCES inventory(sku),
  qty       int    NOT NULL CHECK (qty > 0),
  price_chf numeric(10,2) NOT NULL,          -- Preis-Snapshot
  PRIMARY KEY (order_id, sku)
);
CREATE TABLE outbox (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  topic text NOT NULL, payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(), sent_at timestamptz
);

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_checkout, danach gelöscht). Kommandozeilen wie INSERT 0 1 weggelassen.

  1. Idempotenz: Der Unique-Key auf idempotency_key macht Doppelklicks und Client-Retries harmlos.
  2. Kein Überverkauf: Das bedingte UPDATE prüft und ändert in einem Schritt. Kein „erst SELECT, dann UPDATE“ mit Lücke dazwischen.
  3. Letzte Verteidigung: Der CHECK-Constraint lässt keinen negativen Bestand zu, auch nicht bei einem Bug.
  4. Zustandsautomat: Übergänge nur mit Bedingung auf den alten Status. So werden doppelte Webhooks zu „0 Zeilen“.

4. Details, die Interviewer fragen

  1. Anforderungen: Bestellung aus Warenkorb, Zahlung (Karte, TWINT, Rechnung), Bestandsreservierung, Bestätigung, Storno. Nicht-funktional: nie doppelt belasten, nie überverkaufen, auch bei Retries und Ausfällen.
  2. Schätzung: 1 Mio. Bestellungen pro Tag sind ca. 12/s. Ein Flash Sale kann 1000 Bestellungen/s auf einen Artikel bringen. Das Problem ist die heisse Zeile, nicht der Durchschnitt.
  3. Idempotenz beim Provider: Stripe speichert Status und Body der ersten Anfrage pro Schlüssel und liefert bei Retries dieselbe Antwort, auch einen 500er. Schlüssel sind bis 255 Zeichen lang und werden frühestens nach 24 h entfernt.
  4. Warum keine verteilte Transaktion: Der Provider nimmt an keinem 2PC teil. Darum Saga: lokale Transaktionen plus Kompensation.
  5. Orchestrierung vs Choreografie: Orchestrierte Saga: ein Koordinator ruft die Schritte. Choreografie: Services reagieren auf Events. Für Checkout ist Orchestrierung meist übersichtlicher.
  6. Transactional Outbox: Event und Fachdaten in einer DB-Transaktion. Ein Relay sendet später. So gibt es kein „bezahlt, aber Versand weiss nichts“.
  7. Reservierung mit Ablauf: Reservierter Bestand verfällt nach z. B. 15 Minuten ohne Zahlung. Ein Job gibt ihn frei. Sonst blockieren abgebrochene Checkouts den Bestand.
  8. Heisse Zeile beim Flash Sale: 1000 UPDATEs/s auf dieselbe Zeile warten aufeinander. Lösungen: Bestand in Buckets aufteilen (10 Zeilen à 100), Reservierungen über eine Queue serialisieren, oder Token vorab in Redis verteilen und danach in der DB bestätigen.
  9. Webhook-Sicherheit: Signatur prüfen, Zeitstempel prüfen, idempotent verarbeiten, schnell 200 antworten und schwere Arbeit asynchron.
  10. Unklarer Zahlungsstatus: Timeout beim Provider heisst nicht „gescheitert“. Status beim Provider nachfragen (Reconciliation), nie blind neu belasten.
  11. Geldbeträge: numeric oder ganzzahlige Rappen, nie Float. Preis, Rabatt und MWST als Snapshot in der Bestellung speichern.
  12. Sicherheit: Kartendaten nie selbst speichern: Hosted Fields oder Redirect des Providers, damit der PCI-DSS-Umfang klein bleibt.
  13. Lesen vs Schreiben: Produktseiten und Warenkorb kommen aus Cache. Der Checkout liest den Bestand aus der DB, nicht aus dem Cache.

5. Vergleich: drei Design-Varianten

  • A. Alles synchron in einem Request: Bestellung, Zahlung und Bestand in einem Aufruf. Einfach, aber ein langsamer Provider blockiert, und Fehler mitten drin hinterlassen halbe Zustände.
  • B. Saga mit Outbox (wie oben): lokale Transaktion, Zahlung asynchron, Kompensation bei Fehlern. Robust und nachvollziehbar; mehr Zustände und Jobs.
  • C. Reservierung vor dem Checkout (Ticketing-Stil): Bestand wird schon beim „In den Warenkorb“ für Minuten reserviert. Fair bei Knappheit; aber viel blockierter Bestand und mehr Freigabe-Logik.

6. In der Produktion

  1. Doppelte Belastung: Client-Retry nach Timeout ohne Schlüssel. Fix: Idempotency-Key am Checkout und beim Provider.
  2. Überverkauf: „SELECT available, dann UPDATE“ in zwei Schritten. Fix: bedingtes UPDATE und CHECK-Constraint.
  3. Bezahlt, aber keine Versandmeldung: Event nach dem Commit gesendet, Service stürzte dazwischen ab. Fix: Outbox.
  4. Bestand blockiert: Abgebrochene Checkouts halten Reservierungen. Fix: Ablaufzeit und Freigabe-Job.
  5. Flash Sale legt die DB lahm: Lock-Warteschlange auf einer Zeile. Fix: Bucket-Bestand, Queue, Rate Limit vor dem Checkout.
  6. Webhook kommt vor der Bestellung an: Reihenfolge nicht garantiert. Fix: Webhook speichern und später verarbeiten, Status beim Provider nachfragen.

7. Diagnose: Werkzeuge und Queries

  • Hängende Bestellungen: SELECT count(*) FROM orders WHERE status = 'pending_payment' AND created_at < now() - interval '15 minutes';
  • Reconciliation: täglicher Abgleich unserer Bestellungen mit den Zahlungen des Providers. Jede Differenz ist ein Ticket.
  • Lock-Wartezeiten: pg_stat_activity mit wait_event_type = 'Lock', pg_locks.
  • Outbox-Lag: Alter des ältesten nicht gesendeten Events.
  • Business-Metriken: Checkout-Abbruchrate, Zahlungsfehler nach Grund, Bestellungen pro Minute. Ein plötzlicher Einbruch ist oft ein technischer Fehler.

8. Senior-Punkte

  1. Geld und Bestand sind die zwei Invarianten. Ich schütze sie in der DB (Unique, bedingtes UPDATE, CHECK), nicht nur im Code.
  2. Idempotenz auf jeder Grenze: Client → Checkout, Checkout → Provider, Provider → Webhook.
  3. Saga statt 2PC, weil externe Provider nicht mitmachen. Jeder Schritt hat eine Kompensation.
  4. Timeout heisst „unbekannt“, nicht „gescheitert“. Ich frage den Status nach, statt neu zu belasten.
  5. Reconciliation ist Pflicht. Kein verteiltes System ist ohne täglichen Abgleich wirklich konsistent.
  6. Kartendaten bleiben beim Provider. Das spart PCI-Aufwand und Risiko.

„Bei Flaconi, einem grossen Online-Shop für Beauty-Produkte, habe ich am Spring-Boot-Backend und an SOAP-Anbindungen an Legacy-Systeme gearbeitet, nicht am Checkout selbst. Das Muster ‚Ergebnis idempotent schreiben‘ habe ich bei MATCH umgesetzt.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Erst Bestand lesen, dann abziehen.“ → Race. Zwei Käufer lesen beide „1 da“. Bedingtes UPDATE nutzen.
  • „Bei Timeout zahle ich einfach nochmals.“ → Doppelte Belastung. Erst Status nachfragen, mit gleichem Schlüssel wiederholen.
  • „Wir nutzen eine verteilte Transaktion über Shop und Provider.“ → Der Provider macht kein 2PC. Saga mit Kompensation.
  • „Event nach dem Commit senden reicht.“ → Absturz dazwischen verliert das Event. Outbox.
  • „Preise als double.“ → Rundungsfehler. numeric oder Rappen als Ganzzahl.
  • „Bestand kommt aus dem Cache.“ → Für die Anzeige ja, für die Reservierung nie.

11. Fragen

Skizzieren Sie den Checkout in einer Minute.

Bestellung mit Idempotenz-Schlüssel, bedingte Reservierung, Outbox in einer Transaktion. Zahlung beim Provider mit eigenem Schlüssel, Bestätigung per Webhook, bedingter Statuswechsel. Fehler kompensiert eine Saga.

Wie verhindern Sie doppelte Belastung?

Idempotency-Key vom Client bis zum Provider. Der Provider liefert bei Retries dieselbe Antwort. Webhooks setzen den Status nur aus dem erwarteten Vorzustand.

Wie verhindern Sie Überverkauf?

UPDATE mit Bedingung available ≥ Menge, in einem Schritt. Dazu ein CHECK-Constraint gegen negativen Bestand.

Was ist eine Saga?

Eine Folge lokaler Transaktionen mit je einer Kompensation. Scheitert ein Schritt, werden die vorherigen rückgängig gemacht, z. B. Reservierung freigeben oder erstatten.

Orchestrierung oder Choreografie?

Orchestrierung hat einen Koordinator und ist übersichtlich. Choreografie koppelt lose über Events, ist aber schwerer zu verfolgen. Für Checkout meist Orchestrierung.

Warum eine Outbox?

Fachdaten und Event gehen in einer Transaktion. So geht kein Event verloren, wenn der Service nach dem Commit abstürzt.

Was tun Sie bei einem Timeout beim Provider?

Status beim Provider abfragen. Nur mit demselben Idempotenz-Schlüssel wiederholen. Nie neu belasten ohne Klarheit.

Wie sichern Sie Webhooks ab?

Signatur und Zeitstempel prüfen, idempotent verarbeiten, schnell antworten und asynchron weiterarbeiten.

Wie lange bleibt Bestand reserviert?

Eine fachlich gewählte Zeit, z. B. 15 Minuten. Ein Job gibt abgelaufene Reservierungen frei und storniert die Bestellung.

Wie überstehen Sie einen Flash Sale?

Bestand in Buckets, Reservierungen über eine Queue, Rate Limit und Warteraum vor dem Checkout. Produktseiten aus dem Cache.

Wie speichern Sie Geldbeträge?

Als numeric oder ganzzahlige Rappen. Preis, Rabatt und MWST als Snapshot in der Bestellung.

Was ist Reconciliation?

Ein regelmässiger Abgleich unserer Bestellungen mit den Daten des Providers. Er findet Fälle, die Saga und Webhooks verpasst haben.

Speichern Sie Kartendaten?

Nein. Hosted Fields oder Redirect des Providers. So bleibt der PCI-DSS-Umfang klein.

Wie lange hält Stripe Idempotenz-Schlüssel?

Laut Doku können Schlüssel entfernt werden, wenn sie mindestens 24 Stunden alt sind. Danach erzeugt derselbe Schlüssel eine neue Anfrage.

Welche Statusübergänge erlauben Sie?

pending_payment → paid oder cancelled, paid → shipped. Jeder Übergang als UPDATE mit Bedingung auf den alten Status.

Szenario: Eine Kundin wurde doppelt belastet. Wie untersuchen Sie das?

Zahlungen beim Provider zur Bestellung suchen, Idempotenz-Schlüssel vergleichen. Typisch: Retry ohne Schlüssel oder mit neuem Schlüssel. Sofort erstatten, dann Schlüssel-Logik korrigieren.

Szenario: Im Flash Sale meldet die DB viele Lock-Wartezeiten. Was tun Sie?

Die Bestandszeile ist heiss. Kurzfristig Rate Limit und Warteraum. Dann Bestand in Buckets aufteilen oder Reservierungen über eine Queue serialisieren.

Szenario: Bestellungen sind bezahlt, aber der Versand bekommt nichts. Wo suchen Sie?

Outbox-Lag und Relay prüfen, Broker und Consumer-Lag. Falls ohne Outbox gebaut: Event ging zwischen Commit und Send verloren. Fix: Outbox und Nachversand.
