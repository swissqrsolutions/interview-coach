Consistent Hashing

System-Design-Grundlagen · Tier 2 · Quellen: Karger et al. 1997 (Consistent Hashing and Random Trees), DeCandia et al. 2007 (Dynamo, SOSP), Lamping & Veach 2014 (A Fast, Minimal Memory, Consistent Hash Algorithm), Thaler & Ravishankar 1998 (Rendezvous/HRW Hashing), Mirrokni, Thorup, Zadimoghaddam 2018 (Consistent Hashing with Bounded Loads), Apache Cassandra 5.0 Docs (cassandra.yaml: num_tokens), Envoy Docs (Cluster: RingHashLbConfig, MaglevLbConfig), Redis Cluster Specification, Kleppmann DDIA Kap. 6

Kern: Consistent Hashing ist ein Verfahren, das Schlüssel so auf Knoten verteilt, dass bei einem neuen oder fehlenden Knoten nur ca. 1/N der Schlüssel umziehen. Mit hash % N ziehen fast alle um. Darum nutzen verteilte Caches, Datenbanken und Load Balancer mit Affinität Consistent Hashing oder eine Variante davon.

1. Wo sitzt Consistent Hashing?

  1. Client: will einen Schlüssel lesen oder schreiben, z. B. user:42.
  2. Router: berechnet den Hash und wählt den Knoten. Er sitzt in der Client-Bibliothek, in einem Proxy oder in jedem Datenbank-Knoten.
  3. Hash-Ring: Der Wertebereich des Hashes ist ein Kreis. Knoten und Schlüssel liegen beide darauf.
  4. Regel: Ein Schlüssel gehört zum nächsten Knoten im Uhrzeigersinn. user:42 gehört hier zu B.
  5. Virtuelle Knoten: Jeder Server steht mehrfach auf dem Ring. Das glättet die Verteilung.
  6. Typische Orte: Memcached-Clients, Cassandra und Dynamo-artige Datenbanken, Envoy mit RING_HASH oder MAGLEV, CDN-Caches.

2. Die Reise eines Schlüssels (die Geschichte zum Merken)

  1. Hash berechnen: Der Router hasht user:42 auf eine Zahl, z. B. 64 Bit. Das ist die Position auf dem Ring.
  2. Nächstes Token suchen: Die Tokens liegen sortiert in einem Array. Eine Binärsuche findet das erste Token, das grösser oder gleich ist. Kosten: O(log T) bei T Tokens.
  3. Token zum Server: Jedes Token gehört zu einem echten Server. Das Token B'#17 gehört Server B.
  4. Replikate: Bei Replikationsfaktor 3 gehen die Kopien an die nächsten zwei verschiedenen Server im Uhrzeigersinn. Das ist die Preference List aus Dynamo.
  5. Server kommt dazu: Server D setzt seine Tokens auf den Ring. Er übernimmt nur die Schlüssel direkt vor seinen Tokens. Ca. 1/N wandert, alles andere bleibt.
  6. Server fällt aus: Seine Bereiche gehen an die Nachfolger. Mit virtuellen Knoten verteilt sich seine Last auf viele Server, nicht auf einen Nachbarn.

3. Beispiel: sechs Verfahren, ein Knoten mehr

def h(s): return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")
KEYS = [f"user:{i}" for i in range(100_000)]

def modn(nodes):  return {k: nodes[h(k) % len(nodes)] for k in KEYS}

    def __init__(self, nodes, vnodes):

Echte Ausgabe, Python 3.12.10 (Simulation, 100 000 Schlüssel, MD5 als Hash). Die Zahlen zeigen die Mechanik, keine Produktmessung.

  1. hash % N: perfekte Verteilung, aber beim Schritt von 4 auf 5 Knoten ziehen 80 % der Schlüssel um. Für einen Cache heisst das: 80 % Misses auf einen Schlag.
  2. Ring mit 1 Token pro Server: Nur 25 % ziehen um. Aber ein Server trägt 1,66-mal den Durchschnitt. Die Lücken auf dem Ring sind zufällig ungleich.
  3. Virtuelle Knoten: Mit 256 Tokens sinkt die Spitze auf 1,14. Bei 10 Servern fällt sie von 2,26 (1 Token) auf 1,11 (256 Tokens).
  4. Jump Hash und Rendezvous: fast perfekte Verteilung (1,01) und fast genau 20 % Bewegung. Beide brauchen keinen Ring.
  5. Ausfall: Fällt n2 weg, verteilen sich seine Schlüssel auf alle vier anderen Server. Kein anderer Schlüssel bewegt sich (0).

4. Details, die Interviewer fragen

  1. Problem von hash % N: Ändert sich N, ändert sich das Ergebnis für fast jeden Schlüssel. Von N auf N+1 bleiben nur ca. 1/(N+1) am Platz.
  2. Monotonie: Monotonie heisst, ein neuer Knoten nimmt nur Schlüssel auf, er verschiebt keine zwischen alten Knoten. Das ist die Kern-Eigenschaft aus Karger 1997.
  3. Virtuelle Knoten (vnodes, Tokens): Jeder Server erhält viele Positionen auf dem Ring. Ergebnis: gleichmässige Last und Verteilung der Last eines Ausfalls auf viele Server.
  4. Gewichtung: Ein starker Server bekommt mehr Tokens. So trägt er mehr Daten. Cassandra beschreibt genau das für num_tokens.
  5. Cassandra: num_tokens ist in Cassandra 5.0 standardmässig 16. Wenige Tokens mit dem Allocator (allocate_tokens_for_local_replication_factor, Standard 3) geben gute Balance bei weniger Reparatur-Aufwand.
  6. Replikation auf dem Ring: Kopien liegen auf den nächsten RF−1 verschiedenen Servern. Mit vnodes muss man Tokens desselben Servers überspringen. Rack- und Zonen-Bewusstsein kommt dazu.
  7. Jump Consistent Hash: Eine Funktion jump(key, n) liefert direkt einen Bucket 0…n−1. Kein Speicher, perfekte Verteilung. Aber: Buckets nur am Ende hinzufügen oder entfernen. Gut für nummerierte Shards, schlecht für zufällig ausfallende Server.
  8. Rendezvous Hashing (HRW): Für jeden Server einen Score hash(server, key) rechnen, der höchste gewinnt. Kein Ring, beliebige Server entfernbar. Kosten: O(N) pro Lookup.
  9. Maglev Hashing: Google baut daraus eine feste Lookup-Tabelle. Sehr schneller Lookup, sehr gleichmässig, minimal mehr Bewegung als ein Ring. Envoy nutzt standardmässig eine Tabelle mit 65 537 Einträgen.
  10. Envoy Ring Hash: minimum_ring_size ist standardmässig 1024 Einträge, maximal 8M. Mehr Einträge heisst bessere Verteilung, mehr Speicher.
  11. Bounded Loads: Ein Knoten darf höchstens (1+ε) mal den Durchschnitt tragen. Ist er voll, geht der Schlüssel zum nächsten. Gut gegen Hot Spots bei Sticky Routing.
  12. Hot Keys: Consistent Hashing verteilt Schlüssel, nicht Last. Ein einzelner sehr heisser Key landet immer auf einem Server. Lösung: Key-Splitting, lokale Caches, Replikate lesen.
  13. Redis Cluster ist kein Ring: Er nutzt 16 384 feste Hash Slots (CRC16 mod 16384). Slots werden zwischen Knoten verschoben. Das ist das Muster „viele feste Partitionen“.
  14. Feste Partitionen als Alternative: Viel mehr Partitionen als Knoten anlegen, z. B. 1024. Beim Skalieren ziehen ganze Partitionen um. Kafka, Elasticsearch und Redis Cluster arbeiten so.
  15. Hash-Funktion: Sie muss gleichmässig sein, nicht kryptografisch. Typisch: MurmurHash3, xxHash. Wichtig: Alle Clients nutzen exakt dieselbe Funktion.

5. Vergleich

  • hash % N: trivial, gleichmässig. Bei Änderung von N zieht fast alles um. Nur für feste N.
  • Ring mit vnodes: beliebige Knoten hinzufügen und entfernen, Gewichtung möglich. Speicher O(Tokens), Lookup O(log T).
  • Jump Hash: kein Speicher, perfekt gleichmässig. Nur Buckets am Ende ändern, keine Gewichte.
  • Rendezvous (HRW): einfach, gleichmässig, beliebige Knoten entfernbar. Lookup O(N), gut bis einige hundert Knoten.
  • Maglev: Lookup O(1) über Tabelle, sehr gleichmässig. Tabelle neu bauen bei Änderung. Gut für L4-Load-Balancer.
  • Feste Partitionen / Hash Slots: Zuordnung Partition → Knoten liegt in Metadaten. Volle Kontrolle beim Umzug, braucht aber einen Koordinator.

6. In der Produktion

  1. Cache-Sturm nach Scale-out: Ein Memcached-Pool mit % N bekommt einen Knoten mehr. Fast alle Keys sind Misses, die DB bricht ein. Lösung: Consistent Hashing (z. B. Ketama) in allen Clients.
  2. Clients rechnen verschieden: Zwei Services nutzen andere Hash-Funktionen oder andere Server-Reihenfolge. Derselbe Key liegt doppelt, Invalidierung trifft die falsche Kopie. Lösung: eine gemeinsame Bibliothek und Server-Namen statt Indizes.
  3. Ungleiche Last: Zu wenige vnodes geben einen heissen Knoten. Lösung: mehr Tokens oder Token-Allocator, Last pro Knoten messen.
  4. Flapping: Ein Knoten fällt kurz aus und kommt zurück. Jedes Mal wandern Keys hin und her. Lösung: Ausfall erst nach mehreren Health-Check-Fehlern melden, Hysterese.
  5. Hot Key trotz guter Verteilung: Ein einzelnes Produkt im Sale trifft einen Server. Lösung: lokaler Cache, Key mit Suffix auf mehrere Kopien verteilen.
  6. Daten-Umzug kostet: Beim Rebalancing streamen Knoten Daten. Das frisst Netz und I/O. Lösung: Throttling, Knoten einzeln hinzufügen, ausserhalb der Spitzenzeit.

7. Diagnose: Werkzeuge und Befehle

  • nodetool status und nodetool ring (Cassandra): Tokens, Anteil (Owns) und Zustand pro Knoten.
  • CLUSTER SHARDS oder CLUSTER SLOTS (Redis Cluster): welche Slots auf welchem Knoten liegen.
  • redis-cli --cluster check und --cluster rebalance: Slot-Verteilung prüfen und ausgleichen.
  • Metriken pro Knoten: Keys, Bytes, Requests pro Sekunde, Hit Ratio. Ein Ausreisser zeigt schlechte Verteilung oder einen Hot Key.
  • Envoy-Statistiken: Cluster-Statistiken ring_hash_lb.size, min_hashes_per_host, max_hashes_per_host zeigen die Gleichmässigkeit.
  • Offline-Simulation: echte Keys durch die Hash-Funktion schicken wie oben. So sieht man Bewegung und Spitze vor dem Umbau.

8. Senior-Punkte

  1. Consistent Hashing löst das Umzugs-Problem, nicht das Hot-Key-Problem. Für Hot Keys braucht es Caching oder Key-Splitting.
  2. Für Datenbanken wähle ich oft feste Partitionen mit Metadaten. Umzüge sind dann explizit, beobachtbar und drosselbar.
  3. Für Client-seitiges Routing (Cache-Pool) reicht ein Ring mit vnodes oder Rendezvous. Wichtig ist eine gemeinsame Bibliothek.
  4. Jump Hash nur mit nummerierten Shards, die am Ende wachsen. Nie für Server, die zufällig ausfallen.
  5. Bewegung kostet immer etwas: kalte Caches oder Daten-Streaming. Ich plane Scale-out schrittweise und messe die Hit Ratio dabei.
  6. Im Interview: zuerst % N zeigen, dann das Umzugsproblem, dann Ring, dann vnodes. Diese Reihenfolge zeigt Verständnis.

10. Fallen

  • „Mit Consistent Hashing zieht beim Scale-out nichts um.“ → Falsch. Ca. 1/N zieht um. Das ist das Minimum, nicht null.
  • „Consistent Hashing verteilt die Last gleichmässig.“ → Nur die Schlüssel, und nur mit genug vnodes. Hot Keys bleiben heiss.
  • „Redis Cluster nutzt einen Hash-Ring.“ → Falsch. 16 384 feste Hash Slots, die zwischen Knoten verschoben werden.
  • „Mehr vnodes sind immer besser.“ → Nicht ganz. Mehr Speicher, mehr Metadaten, und in Cassandra mehr Reparatur-Aufwand. Darum dort heute 16 statt früher 256.
  • „Jump Hash passt für jeden Cluster.“ → Falsch. Nur Buckets am Ende ändern. Ein ausgefallener Server in der Mitte bricht die Zuordnung.
  • „Die Hash-Funktion muss kryptografisch sein.“ → Nein. Gleichmässig und schnell reicht, z. B. Murmur oder xxHash.

11. Fragen

Was ist Consistent Hashing?

Ein Verfahren, das Schlüssel so auf Knoten verteilt, dass bei Änderung der Knotenzahl nur ca. 1/N der Schlüssel umzieht. Knoten und Schlüssel liegen dafür auf einem Hash-Ring.

Warum nicht einfach hash % N?

Ändert sich N, ändert sich die Zuordnung fast jedes Schlüssels. In der Simulation zogen beim Schritt 4 → 5 rund 80 % um.

Wie findet man den Knoten für einen Schlüssel?

Hash des Schlüssels berechnen, dann per Binärsuche das nächste Token im Uhrzeigersinn finden. Das Token gehört zu einem Server.

Was sind virtuelle Knoten?

Jeder Server steht mehrfach auf dem Ring. Das glättet die Verteilung und verteilt die Last eines Ausfalls auf viele Server.

Wie viele Schlüssel ziehen bei einem neuen Knoten um?

Im Mittel ca. 1/(N+1) aller Schlüssel. Bei 4 → 5 Knoten also ca. 20 %.

Was passiert, wenn ein Knoten ausfällt?

Seine Bereiche gehen an die Nachfolger auf dem Ring. Mit vnodes sind das viele verschiedene Server. Kein anderer Schlüssel bewegt sich.

Wie gewichtet man starke Server?

Sie bekommen mehr Tokens auf dem Ring. So gehört ihnen ein grösserer Anteil.

Wie funktioniert Replikation auf dem Ring?

Die Kopien liegen auf den nächsten RF−1 verschiedenen Servern im Uhrzeigersinn. Tokens desselben Servers werden übersprungen, oft auch dieselbe Zone.

Was ist Jump Consistent Hash?

Eine kurze Funktion, die Schlüssel und Bucket-Anzahl auf einen Bucket abbildet. Kein Speicher, perfekt gleichmässig. Buckets darf man nur am Ende ändern.

Was ist Rendezvous Hashing?

Für jeden Server einen Score aus Server und Schlüssel berechnen, der höchste gewinnt. Kein Ring nötig, Lookup kostet O(N).

Was ist Maglev Hashing?

Ein Verfahren, das eine feste Lookup-Tabelle baut. Lookup O(1), sehr gleichmässig. Envoy nutzt standardmässig 65 537 Einträge.

Nutzt Redis Cluster Consistent Hashing?

Nein. Er nutzt 16 384 feste Hash Slots mit CRC16. Slots werden als Ganzes zwischen Knoten verschoben.

Feste Partitionen oder Ring?

Feste Partitionen geben kontrollierte Umzüge über Metadaten. Ein Ring braucht keinen Koordinator. Datenbanken nutzen oft Partitionen, Client-Caches oft einen Ring.

Löst Consistent Hashing Hot Keys?

Nein. Ein Schlüssel landet immer auf einem Server. Dagegen helfen lokale Caches, Lese-Replikate oder Key-Splitting.

Was ist Consistent Hashing with Bounded Loads?

Jeder Knoten hat eine Obergrenze von (1+ε) mal dem Durchschnitt. Ist er voll, geht der Schlüssel weiter zum nächsten Knoten.

Wie viele Tokens nutzt Cassandra?

In Cassandra 5.0 standardmässig 16 pro Knoten, mit einem Allocator für gute Balance. Früher waren 256 üblich.

Welche Hash-Funktion nehmen Sie?

Eine schnelle, gleichmässige wie MurmurHash3 oder xxHash. Alle Clients müssen exakt dieselbe nutzen.

Wo nutzt ein Load Balancer Consistent Hashing?

Für Affinität: Requests eines Nutzers oder Keys sollen am selben Backend landen, z. B. für lokale Caches. Envoy bietet RING_HASH und MAGLEV.

Szenario: Nach dem Hinzufügen eines Memcached-Knotens bricht die Datenbank ein. Warum?

Die Clients nutzen hash % N. Fast alle Keys landen auf einem anderen Knoten und sind Misses. Lösung: Consistent Hashing in allen Clients, Scale-out ausserhalb der Spitze.

Szenario: Ein Knoten im Cluster hat doppelt so viel Last wie die anderen. Was prüfen Sie?

Zuerst die Verteilung der Keys: zu wenige vnodes oder falsche Gewichte. Dann einen Hot Key mit Requests pro Key. Lösung: mehr Tokens, Rebalancing oder Hot-Key-Caching.

Szenario: Zwei Services lesen denselben Cache, aber Invalidierungen wirken nicht. Woran denken Sie?

Die Services berechnen den Knoten verschieden, z. B. andere Hash-Funktion oder Server-Reihenfolge. Lösung: eine gemeinsame Client-Bibliothek und stabile Server-Namen.
