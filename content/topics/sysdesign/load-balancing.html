Load Balancing

Kern: Ein Load Balancer verteilt eingehende Requests auf mehrere Server (Backends). Er löst zwei Probleme, nämlich Skalierung (mehr Server, mehr Last) und Verfügbarkeit (kranke Server bekommen keinen Traffic). Er arbeitet entweder auf Layer 4 (TCP/UDP) oder auf Layer 7 (HTTP).

Antwort-Muster

Frage: Was ist der Unterschied zwischen L4- und L7-Load-Balancing?

  1. Mechanismus: L4 sieht nur IP und Port und verteilt Verbindungen. L7 versteht HTTP und verteilt einzelne Requests.
  2. Zahl: In der Simulation drückt Least Connections die p99 von 36 Sekunden (Round Robin) auf gut 100 Millisekunden.
  3. Trade-off: L4 ist schneller und protokollneutral. L7 kann Routing, WAF und Retries, kostet aber TLS-Arbeit.
  4. Produktion: Lange gRPC-Verbindungen verteilt nur ein L7-LB. Sonst klebt der Traffic auf einem Pod.

1. Die Reise eines Requests

  1. DNS: Der Browser fragt app.example.ch auf. Front Door antwortet mit einer Anycast-IP. Bei Anycast teilen viele Edge-Standorte eine IP. Das Netz wählt den nächsten.
  2. Edge (L7): Der nächste Edge-Standort beendet TLS. Die WAF (Web Application Firewall) prüft den Request. Eine Route wählt die Origin-Gruppe nach Host und Pfad.
  3. Pool filtern: Der LB kennt nur gesunde Backends. Health Probes fragen jedes Backend regelmässig ab, z. B. GET /healthz.
  4. Algorithmus: Aus den gesunden Backends wählt ein Algorithmus eines. Beispiele sind Round Robin, Least Connections und Hash.
  5. Backend: Das Backend sieht als Absender den LB. Die echte Client-IP steht im Header X-Forwarded-For.
  6. Antwort: Bei L7 geht die Antwort über den LB zurück. Er kann sie komprimieren oder Header ändern.
  7. Fehlerfall: Ein Pod antwortet nicht mehr auf die Probe. Nach einigen Fehlversuchen nimmt der LB ihn aus dem Pool. Laufende Requests dürfen noch fertig werden (Connection Draining).

2. Aufbau

  1. Azure Front Door: globaler L7-Load-Balancer am Microsoft-Edge. Er leitet den Nutzer zur nächsten gesunden Region. Er bietet WAF und Caching.
  2. Application Gateway: regionaler L7-Load-Balancer. Er routet nach Host und Pfad, beendet TLS und bietet WAF.
  3. Azure Load Balancer: regionaler L4-Load-Balancer für TCP und UDP. Ein Kubernetes-Service vom Typ LoadBalancer bekommt auf AKS einen solchen.
  4. Ingress- oder Gateway-Controller: L7-Router im Cluster. Er verteilt nach Host und Pfad auf Services.
  5. Service: eine stabile virtuelle IP. kube-proxy verteilt Verbindungen auf die Pods (L4).
  6. Man kombiniert die Stufen: global → regional → Cluster → Pod. Jede Stufe prüft die Gesundheit der nächsten.

3. Details, die Interviewer fragen

  1. Layer 4: Ein L4-LB sieht nur IP, Port und Protokoll. Er verteilt Verbindungen, nicht Requests. Er ist sehr schnell. Er kann jedes TCP/UDP-Protokoll.
  2. Layer 7: Ein L7-LB versteht HTTP. Er routet nach Host, Pfad, Header oder Cookie. Er beendet TLS. Er kann Retries, Rewrites und WAF.
  3. Round Robin: Die Server kommen der Reihe nach dran. Das ist einfach, aber blind für Last. Weighted Round Robin gibt stärkeren Servern mehr.
  4. Least Connections: Der Server mit den wenigsten offenen Verbindungen gewinnt. Das ist gut bei unterschiedlich langen Requests.
  5. Least Response Time / Latency: Der schnellste Server gewinnt. Front Door wählt so zwischen Regionen.
  6. Power of Two Choices: Man wählt zwei Server zufällig und nimmt den weniger belasteten. Das ist fast so gut wie Least Connections. Es braucht keinen globalen Zustand.
  7. Hash-basiert: Ein Hash über Client-IP, Header oder Schlüssel wählt den Server. Gleicher Schlüssel, gleicher Server. Das braucht man für Caches und Sharding.
  8. Consistent Hashing: Knoten und Schlüssel liegen auf einem Ring. Ein Schlüssel gehört zum nächsten Knoten im Uhrzeigersinn. Ein neuer Knoten übernimmt nur seinen Abschnitt. Virtuelle Knoten glätten die Verteilung.
  9. Aktive Probes: Aktive Probes fragen regelmässig einen Endpunkt ab. Der Endpunkt prüft nur, ob die Instanz Traffic annehmen kann.
  10. Passive Checks: Passive Checks werten echte Fehler aus (Outlier Detection).
  11. Sticky Sessions: Session Affinity schickt einen Client immer zum selben Backend. Application Gateway nutzt dafür ein Cookie. Azure Load Balancer nutzt Client-IP (2-Tupel) oder Client-IP plus Protokoll (3-Tupel).
  12. Azure Load Balancer Standard-Verteilung: Sie ist ein 5-Tupel-Hash (Quell-IP, Quell-Port, Ziel-IP, Ziel-Port, Protokoll). Stickiness gilt nur innerhalb einer Verbindung.
  13. Lange Verbindungen: HTTP/2, gRPC und WebSockets halten eine TCP-Verbindung lange offen. Ein L4-LB verteilt dann nur Verbindungen, nicht Requests. Neue Pods bekommen nichts.
  14. Lösung für lange Verbindungen: Man nimmt einen L7-LB oder ein Service Mesh für gRPC.
  15. TLS-Terminierung: Der LB entschlüsselt, um L7 zu sehen. Danach geht es unverschlüsselt oder neu verschlüsselt (End-to-End TLS) zum Backend.
  16. Kubernetes Service: ClusterIP ist eine virtuelle IP. kube-proxy schreibt Regeln (iptables, IPVS oder nftables). Im iptables-Modus wählt er pro Verbindung zufällig einen Pod.
  17. Readiness Probes: Readiness Probes entscheiden, ob ein Pod im Service ist.
  18. externalTrafficPolicy: Cluster (Standard) kann einen zweiten Hop machen. Es kann die Client-IP durch SNAT verlieren. Local behält die Client-IP. Es verteilt aber nur auf Knoten mit Pods.
  19. Ingress: Ingress beschreibt L7-Regeln (Host, Pfad → Service). Ein Ingress-Controller setzt sie um. Ingress NGINX wurde im März 2026 eingestellt.
  20. Gateway API: Die Gateway API ist der Nachfolger von Ingress. Sie hat Rollen und mehr Protokolle.

4. Fallen

  • „Round Robin verteilt die Last gleichmässig.“ → Falsch. Es verteilt die Anzahl gleich, nicht die Arbeit.
  • „Ein Kubernetes-Service balanciert gRPC-Requests.“ → Falsch. Er balanciert nur Verbindungen (L4).
  • „Front Door und Application Gateway sind dasselbe.“ → Falsch. Front Door ist global am Edge, Application Gateway regional im VNet.
  • „Traffic Manager leitet Traffic weiter.“ → Falsch. Er beantwortet nur DNS. Der Client verbindet sich direkt.
  • „Sticky Sessions sind ein gutes Default.“ → Falsch. Sie machen Last ungleich und verlieren Sessions beim Ausfall.
  • „Health Check soll alle Abhängigkeiten prüfen.“ → Falsch. Dann reisst ein DB-Problem alle Instanzen aus dem Pool.

5. Selbsttest

Warum?

Was ist ein Load Balancer?

Eine Komponente, die Requests auf mehrere Backends verteilt. Sie bringt Skalierung und Verfügbarkeit, weil kranke Backends keinen Traffic mehr bekommen.

Warum nicht einfach hash % N?

Ändert sich N, wandern fast alle Schlüssel. In der Simulation 80 % bei 4 → 5 Knoten. Ein Cache wird dadurch fast leer.

Wie innen?

Welche Algorithmen kennen Sie?

Round Robin, Weighted Round Robin, Least Connections, Least Response Time, Power of Two Choices, IP-Hash und Consistent Hashing.

Was ist Consistent Hashing?

Knoten und Schlüssel liegen auf einem Hash-Ring. Ein Schlüssel gehört zum nächsten Knoten im Uhrzeigersinn. Bei einem neuen Knoten wandern nur ca. 1/N der Schlüssel.

Warum virtuelle Knoten?

Mit einem Punkt pro Knoten sind die Abschnitte ungleich gross. Viele Punkte pro Knoten glätten die Verteilung. Man kann so auch stärkeren Knoten mehr Gewicht geben.

Was ist ein Health Check?

Eine regelmässige Abfrage, ob ein Backend Traffic annehmen kann. Nach mehreren Fehlern nimmt der LB das Backend aus dem Pool.

Wie verteilt Azure Load Balancer standardmässig?

Mit einem 5-Tupel-Hash aus Quell-IP, Quell-Port, Ziel-IP, Ziel-Port und Protokoll. Optional Session Persistence mit 2- oder 3-Tupel.

Wie funktioniert ein Kubernetes-Service?

Er hat eine stabile virtuelle IP. kube-proxy programmiert Regeln, die jede neue Verbindung auf einen bereiten Pod leiten.

Wie sieht das Backend die echte Client-IP?

Bei L7 im Header X-Forwarded-For. Bei L4 bleibt sie oft erhalten, in Kubernetes mit externalTrafficPolicy: Local.

Zahlen

Welche Zahlen zeigen das Problem von Round Robin?

In der Simulation mit einem dreimal langsameren Server: p99 von 36 Sekunden mit Round Robin, 112 Millisekunden mit Least Connections.

Was geht kaputt, wenn der Idle-Timeout des Azure Load Balancers zuschlägt?

Inaktive TCP-Verbindungen werden standardmässig nach 4 Minuten getrennt. Lange stille Verbindungen brechen. Lösung: TCP-Keepalive oder Timeout erhöhen.

Vergleich

Was ist der Unterschied zwischen L4 und L7?

L4 sieht nur IP, Port und Protokoll und verteilt Verbindungen. L7 versteht HTTP, routet nach Pfad, Header oder Cookie und verteilt einzelne Requests.

Wann ist Least Connections besser als Round Robin?

Wenn Requests unterschiedlich lange dauern oder Server unterschiedlich schnell sind. Round Robin überlastet dann den langsamen Server.

Azure Load Balancer vs Application Gateway vs Front Door?

Load Balancer: regional, L4. Application Gateway: regional, L7 mit WAF im VNet. Front Door: global, L7 am Edge mit WAF und Caching.

Was macht Traffic Manager?

Globales Load Balancing über DNS. Er gibt die IP eines gesunden Endpunkts zurück. Der Traffic selbst geht nicht durch ihn.

Was ist der Unterschied zwischen Service und Ingress?

Ein Service balanciert auf L4 zwischen Pods. Ein Ingress beschreibt L7-Regeln nach Host und Pfad zu Services. Er braucht einen Ingress-Controller.

Was ist die Gateway API?

Der Nachfolger von Ingress in Kubernetes. Sie trennt Rollen (Infrastruktur, Cluster, App) und kann mehr Protokolle und Traffic-Splitting.

Warum ersetzt die Gateway API den Ingress?

Sie trennt Rollen, kann mehr Protokolle und Traffic-Splitting. Ingress NGINX wurde im März 2026 eingestellt.

Produktion

Warum balanciert ein Service gRPC schlecht?

gRPC nutzt eine lange HTTP/2-Verbindung. kube-proxy verteilt nur beim Verbindungsaufbau. Alle Requests gehen an denselben Pod.

Was ist Connection Draining?

Ein Backend bekommt keine neuen Verbindungen mehr, laufende dürfen fertig werden. Wichtig bei Deployments und Scale-in.

Szenario: Nach einem Scale-out bekommen die neuen Pods kaum Traffic. Warum?

Wahrscheinlich lange Verbindungen (HTTP/2, gRPC, Keepalive) oder Sticky Sessions. Bestehende Verbindungen bleiben auf alten Pods. Lösung: L7-Balancing, maximale Verbindungsdauer begrenzen, Affinity entfernen.

Szenario: Die Datenbank hat 30 Sekunden Störung, danach ist die ganze App 5 Minuten down. Warum?

Der Health Check prüft die Datenbank. Alle Pods wurden unhealthy und aus dem Pool genommen. Dazu Retry-Sturm beim Wiederanlauf. Lösung: flache Health Checks, Backoff, Circuit Breaker.

Design

Was soll ein Health-Endpunkt prüfen?

Nur die eigene Instanz: Prozess läuft, kann antworten. Nicht die Datenbank. Sonst reisst ein DB-Fehler alle Instanzen gleichzeitig raus.

Was sind Sticky Sessions und wann brauchen Sie sie?

Ein Client geht immer zum selben Backend, per Cookie oder Client-IP. Nur bei Altsystemen mit Session im Speicher. Besser: Session extern speichern.

Wo beenden Sie TLS?

Am L7-LB, damit er Routing und WAF machen kann. Für sensible Daten neu verschlüsseln bis zum Backend (End-to-End TLS).

Wie verhindern Sie, dass der LB ein Single Point of Failure ist?

Cloud-LBs sind intern redundant und zonenredundant. Eigene LBs laufen als Paar mit Failover, z. B. über eine virtuelle IP.

Szenario: Eine App soll in zwei Azure-Regionen laufen, mit Failover. Was bauen Sie?

Front Door global mit Health Probes auf beide Regionen. Pro Region Application Gateway oder AKS-Gateway mit WAF. Daten repliziert. Routing nach Latenz oder Priorität.

Was geht kaputt, wenn Sessions im Pod-Speicher liegen?

Dann braucht es Sticky Sessions: Die Last wird ungleich, und ein Pod-Ausfall verliert die Sessions. Besser: Session in Redis oder im Token.

Mehr

Gerüst

  • Warum? Requests auf mehrere Backends verteilen: Skalierung und Verfügbarkeit. Kranke Backends fliegen per Health Probe aus dem Pool.
  • Wie innen? L4 sieht IP/Port und verteilt Verbindungen, L7 versteht HTTP und verteilt Requests. Algorithmen: Round Robin, Least Connections, Hash/Ring. Client-IP steht in X-Forwarded-For.
  • Zahlen Simulation: langsamer Server mit Round Robin → p99 36 s, mit Least Connections 112 ms. Azure LB: 5-Tupel-Hash, Idle-Timeout 4 min.
  • Vergleich Azure LB (L4, regional) vs App Gateway (L7, regional, WAF) vs Front Door (L7, global, Edge) vs Traffic Manager (nur DNS).
  • Produktion gRPC/HTTP-2 klebt auf einem Pod → L7 oder Client-Balancing. Health Check prüft die DB → Totalausfall. Deployment ohne Draining → Fehler.
  • Design Zustandslose Backends, flache Health Checks, TLS am L7 beenden, der LB selbst redundant.

Beispiel: drei Algorithmen simuliert

# 3 servers, C is 3x slower (noisy neighbour); one request every 4 ms
rr = lambda i, active: SERVERS[i % len(SERVERS)]                  # round robin
lc = lambda i, active: min(SERVERS, key=lambda s: len(active[s])) # least connections
# duration grows with active requests: work * slow * (1 + 0.5 * active)

# consistent hashing ring with virtual nodes
class Ring:
    def __init__(self, nodes, vnodes):
        self.ring = sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vnodes))
        self.points = [p for p, _ in self.ring]
    def get(self, k):
        i = bisect.bisect(self.points, h(k)) % len(self.ring)
        return self.ring[i][1]

Echte Ausgabe, Python 3 (Simulation). Vereinfachtes Modell: Ein Request wird langsamer, je mehr Requests gleichzeitig auf demselben Server laufen.

  1. Round Robin ist blind: Jeder Server bekommt genau ein Drittel. Der langsame Server C schafft das nicht. Seine Warteschlange wächst auf über 1 000 Verbindungen. Die p99 steigt auf 36 Sekunden.
  2. Least Connections passt sich an: C bekommt nur noch 14 %, weil er länger beschäftigt ist. Keine Warteschlange, p99 ca. 112 ms.
  3. Modulo-Hash (hash % N) verteilt gut. Aber bei einem neuen Knoten wandern 80 % der Schlüssel. Für einen Cache heisst das: fast alles ist ein Miss.
  4. Consistent Hashing bewegt nur ca. 1/N der Schlüssel (hier 22 %, ideal 20 %).
  5. Virtuelle Knoten sind nötig: Mit 1 Punkt pro Knoten trägt n4 41 % und n3 nur 9 %. Mit 100 Punkten pro Knoten liegt alles bei 22–27 %.

Vergleich: Azure-Optionen

  • Azure Load Balancer: L4 (TCP/UDP), regional, sehr niedrige Latenz. Für VMs, AKS-Services, Nicht-HTTP-Protokolle.
  • Application Gateway: L7 (HTTP/S), regional. Pfad-Routing, TLS, WAF, Cookie-Affinity. Kann eine private IP im VNet haben.
  • Azure Front Door: L7 (HTTP/S), global am Edge. Multi-Region-Failover, WAF, CDN-Caching. Routing nach Latenz, Priorität oder Gewicht.
  • Traffic Manager: DNS-basiert, global, jedes Protokoll. Er gibt nur eine IP zurück und sieht den Traffic nie. Failover hängt am DNS-TTL.
  • Application Gateway for Containers: L7 für AKS, gesteuert über Gateway API oder Ingress.
  • Faustregel der Azure-Doku: global + HTTP → Front Door; global + Nicht-HTTP → Traffic Manager oder Cross-Region-LB; regional + HTTP → Application Gateway; regional + Nicht-HTTP → Load Balancer.

In der Produktion

  1. Ein Pod bekommt allen gRPC-Traffic: Eine HTTP/2-Verbindung bleibt auf einem Pod. Lösung: L7-Balancing (Gateway, Service Mesh) oder Client-seitiges Balancing.
  2. Health Check zu tief: /healthz prüft die Datenbank. Die DB hängt kurz, alle Pods fliegen raus. Totalausfall. Lösung: Health Check prüft nur die eigene Instanz.
  3. Sticky Sessions machen Last ungleich: Ein grosser Kunde klebt an einem Server. Neue Pods bleiben leer. Lösung: zustandslose Server, Session in Redis oder im Token.
  4. Fehler beim Deployment: Pods werden beendet, während der LB noch Traffic schickt. Lösung: Readiness Probe, preStop-Pause, Connection Draining.
  5. Idle Timeout trennt Verbindungen: Azure Load Balancer trennt inaktive TCP-Flows standardmässig nach 4 Minuten. Lösung: TCP-Keepalive oder Timeout erhöhen.
  6. SNAT-Port-Erschöpfung: Viele ausgehende Verbindungen über einen Load Balancer brauchen alle Ports auf. Lösung: Connection Pooling, NAT Gateway.
  7. Retry-Sturm: Der LB wiederholt fehlgeschlagene Requests. Das verdoppelt die Last auf ein schon krankes System. Lösung: Retries begrenzen, Backoff, Circuit Breaker.

Diagnose: Werkzeuge und Metriken

  • Azure Load Balancer: Metriken Health Probe Status (DipAvailability), Data Path Availability, SNAT Connection Count.
  • Application Gateway: Healthy/Unhealthy Host Count, Backend Response Status, Access Logs mit timeTaken. Befehl: az network application-gateway show-backend-health.
  • Front Door: Origin Health Percentage, Origin Latency, Access Logs pro Request.
  • Kubernetes: kubectl get endpointslices -l kubernetes.io/service-name=<svc> zeigt, welche Pods im Service sind. kubectl describe pod zeigt fehlgeschlagene Readiness Probes.
  • Verteilung prüfen: Requests pro Pod in Prometheus vergleichen. Ein Pod mit viel mehr Last zeigt Sticky Sessions oder lange Verbindungen.
  • curl -v mit Header-Ausgabe: zeigt TLS, Weiterleitungen und Cookie-Affinity.

Senior-Punkte

  1. Zustandslose Backends sind die Voraussetzung. Dann ist jeder Algorithmus gut genug, und Skalieren ist einfach.
  2. Health Checks sind ein Design-Thema. Zu flach: kranke Pods bekommen Traffic. Zu tief: ein Abhängigkeitsfehler wird zum Totalausfall.
  3. L4 oder L7 ist eine Abwägung: L4 ist schneller und protokollneutral. L7 ist klüger, kostet aber TLS-Arbeit und Latenz.
  4. Lange Verbindungen (gRPC, WebSocket) brauchen L7 oder Client-Balancing. Sonst verteilt der LB nur beim Verbindungsaufbau.
  5. Consistent Hashing nutze ich, wenn Daten am Server hängen (Cache, Shards). Für zustandslose Server reicht Least Connections.
  6. Der Load Balancer selbst darf kein Single Point of Failure sein. Cloud-LBs sind redundant. Eigene LBs brauchen ein Paar mit Failover.
