Fall: Dokumentensystem einer Behörde

Kern (die 1-Minuten-Antwort): Ein Dokumentensystem einer Behörde speichert Dokumente in Dossiers mit Versionen, Klassifizierung und Aufbewahrungsfrist. Bytes liegen verschlüsselt im Object Storage, Metadaten, Rechte und Versionen in PostgreSQL, die Volltextsuche filtert immer nach Rechten. Jede Aktion landet in einem append-only Audit-Log. Am Ende der Frist wird ein Dossier dem Archiv angeboten und erst dann vernichtet. Last ist klein; schwer sind Sicherheit, Nachvollziehbarkeit und Langzeit.

Gerüst

Warum?
Die Last ist klein (ca. 2 TB/Jahr, 7 Suchen/s). Schwer sind Sicherheit, lückenloses Audit und Jahrzehnte Aufbewahrung.
Wie innen?
Bytes WORM-verschlüsselt im Object Storage, Metadaten/ACL/Volltext in PostgreSQL. Versionen mit Optimistic Locking; Audit append-only per Trigger.
Zahlen
ISG-Stufen: intern, vertraulich, geheim. 1 Mio. Dokumente/Jahr à 2 MB; Frist z. B. 10 Jahre. Versionskonflikt → HTTP 412.
Vergleich
GEVER-Produkt vs Eigenbau vs Fachanwendung + GEVER. Mandanten: eigene DB/Schema (hart) vs Zeilen-Filter (billig, riskant).
Produktion
Rechte nach der Suche gefiltert = Leak über Titel und Snippets. Vernichtung ohne Legal Hold. Scans ohne OCR sind unauffindbar.
Design
Rechte in jede Query, zentrale Zugriffsschicht. Nie überschreiben, nie still löschen. Fristablauf: erst Archiv-Angebot, dann protokollierte Vernichtung.

Antwort-Muster

Frage: Entwerfen Sie ein Dokumentensystem für eine Behörde.

  1. Mechanismus: Dossiers mit versionierten Dokumenten: Bytes unveränderbar im Object Storage, Metadaten, Rechte und Volltext in PostgreSQL, jede Aktion im append-only Audit.
  2. Zahl: Die Last ist klein, rund 2 TB pro Jahr; das Design treiben Sicherheit und Fristen, nicht der Durchsatz.
  3. Trade-off: Ein GEVER-Standardprodukt bringt Archiv-Wege fertig mit, Eigenbau passt besser zum Fachprozess.
  4. Produktion: Rechte filtere ich in der Such-Query selbst, sonst leaken Titel und Snippets.

1. Wo sitzt was? (Architektur)

  1. IAM: liefert Identität, Rollen und Organisationseinheit per SSO. Beispiel: user:mueller in org:Abteilung B.
  2. Dokument-API: prüft jede Aktion gegen Dossier-Rechte und Klassifizierung und schreibt einen Audit-Eintrag.
  3. PostgreSQL: Dossiers, ACL, Dokumente, Versionen, Volltext-Index und Audit-Log. Die Wahrheit über alles ausser den Bytes.
  4. Object Storage: Neue Dateien landen in Quarantäne. Nach dem Scan liegen sie unveränderbar (WORM, Write Once Read Many) und verschlüsselt.
  5. Verarbeitung: Malware-Scan, Texterkennung (OCR) für Scans, Umwandlung in PDF/A für die Langzeit-Lesbarkeit.
  6. Archiv-Export: Bei Fristablauf wird das Dossier dem Archiv angeboten. Erst nach dessen Entscheid wird vernichtet.

2. Die Reise eines Dokuments (die Geschichte zum Merken)

  1. Hochladen: Frau Müller lädt eine überarbeitete Verfügung in Dossier 7. Die API prüft: Hat sie Schreibrecht auf Dossier 7?
  2. Quarantäne: Die Datei wird gescannt, der echte Typ über Magic Bytes geprüft. Erst danach ist sie nutzbar.
  3. Aufbereiten: OCR liefert Text für die Suche. Eine PDF/A-Kopie sichert die Lesbarkeit in 20 Jahren. Ein SHA-256 belegt die Unverändertheit.
  4. Neue Version: Version 2 entsteht nur, wenn niemand zwischenzeitlich eine Version 2 angelegt hat (Optimistic Locking). Version und Audit-Eintrag gehen in eine Transaktion.
  5. Suche: Ein Kollege sucht „Lärmschutzwände Verfügung“. Er sieht nur Treffer aus Dossiers, auf die er Rechte hat.
  6. Lesen: Er bekommt einen kurzlebigen Download-Link. Auch das Lesen wird protokolliert.
  7. Abschluss: Das Dossier wird geschlossen. Ab jetzt läuft die Aufbewahrungsfrist, z. B. 10 Jahre.
  8. Fristablauf: Ein Job findet fällige Dossiers. Sie werden dem Archiv angeboten. Was nicht archivwürdig ist, wird protokolliert vernichtet. Ein Legal Hold (laufendes Verfahren) stoppt das.

Datenmodell:

CREATE TABLE dossiers (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title           text NOT NULL,
  org_unit        text NOT NULL,
  classification  text NOT NULL DEFAULT 'intern'
                  CHECK (classification IN ('intern','vertraulich','geheim')),
  closed_at       date,
  retention_years int NOT NULL DEFAULT 10
);
CREATE TABLE dossier_acl (
  dossier_id bigint NOT NULL REFERENCES dossiers(id),
  principal  text   NOT NULL,                 -- 'user:…' oder 'org:…'
  PRIMARY KEY (dossier_id, principal)
);
CREATE TABLE documents (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  dossier_id      bigint NOT NULL REFERENCES dossiers(id),
  title           text   NOT NULL,
  body_text       text   NOT NULL,            -- aus OCR / Textextraktion
  current_version int    NOT NULL DEFAULT 1,
  tsv tsvector GENERATED ALWAYS AS
      (to_tsvector('german', title || ' ' || body_text)) STORED
);
CREATE INDEX documents_tsv_idx ON documents USING gin (tsv);
CREATE TABLE document_versions (
  document_id bigint NOT NULL REFERENCES documents(id),
  version     int    NOT NULL,
  blob_key    text   NOT NULL,
  sha256      text   NOT NULL,
  created_by  text   NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (document_id, version)
);
CREATE TABLE audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at timestamptz NOT NULL DEFAULT now(),
  actor text NOT NULL, action text NOT NULL, object_ref text NOT NULL
);
CREATE FUNCTION audit_append_only() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE EXCEPTION 'audit_log ist append-only (% verboten)', TG_OP; END $$;
CREATE TRIGGER audit_no_change BEFORE UPDATE OR DELETE ON audit_log
  FOR EACH ROW EXECUTE FUNCTION audit_append_only();

Echte Ausgabe, PostgreSQL 17.12 (Schema demo_authority_documents, 2000 Dossiers, 100 000 Dokumente aus 5 Textvorlagen, danach gelöscht). Plan gekürzt.

  1. Stemming: „Lärmschutzwände“ wird zu larmschutzwand, „Verfügung“ zu verfug. Der Stemmer entfernt auch Umlaute. Französisch und Italienisch brauchen eigene Konfigurationen.
  2. Rechte in der Query: 20 000 Treffer gesamt, nur 6650 berechtigt. Ein Filter erst nach der Suche würde Seiten und Zahlen verfälschen.
  3. Seq Scan trotz GIN-Index: 20 % aller Dokumente passen. Der Planer liest dann lieber alles. Bei seltenen Wörtern nimmt er den GIN-Index.
  4. Optimistic Locking: Die Bedingung current_version = 1 verhindert, dass ein Bearbeiter die Änderung eines anderen überschreibt.
  5. Append-only: Der Trigger blockt UPDATE und DELETE. Zusätzlich gehört das Log in ein getrenntes System mit eigenen Rechten.

4. Details, die Interviewer fragen

  1. Anforderungen: Dossiers und Dokumente, Versionen, Rechte nach Organisation und Person, Volltextsuche in de/fr/it, Klassifizierung, Aufbewahrung und Archivierung, lückenloses Audit, Betrieb in der Schweiz.
  2. Schätzung: 30 000 Mitarbeitende, 1 Mio. neue Dokumente pro Jahr à 2 MB = 2 TB pro Jahr. Bei 10 Jahren Frist und Versionen ca. 30 TB. Suche: 600 000 pro Tag ≈ 7/s, Spitze ca. 50/s. Last ist klein.
  3. Klassifizierung: Das ISG kennt die Stufen intern, vertraulich und geheim. Höhere Stufen brauchen strengere Kontrollen: engere Rechte, Verschlüsselung, eventuell getrennte Systeme. „Geheim“ gehört meist nicht in ein normales Dokumentensystem.
  4. Rechte-Modell: RBAC (Rollen) für Funktionen, ACL pro Dossier für Inhalte, Need-to-know als Prinzip. Rechte erben vom Dossier auf Dokumente, Ausnahmen explizit.
  5. Audit: Wer hat wann was gelesen, geändert, gelöscht, exportiert. Append-only, in einem getrennten Speicher, mit Zeitstempel und Korrelations-ID. Personendaten im Log selbst schützen (DSG).
  6. Versionierung: Nie überschreiben. Jede Version hat Hash, Autor und Zeit. Optimistic Locking mit If-Match und HTTP 412.
  7. Unveränderbarkeit: WORM-Storage oder Immutability-Policies am Storage verhindern Änderung und Löschen vor Fristende, auch durch Admins.
  8. Langzeit-Format: PDF/A ist ein PDF-Profil für Langzeitarchivierung: Schriften eingebettet, keine externen Abhängigkeiten. Original zusätzlich behalten.
  9. Aufbewahrung und Archiv: Nach Fristablauf werden Unterlagen dem zuständigen Archiv angeboten (im Bund nach Archivierungsgesetz). Vernichten nur, was nicht archivwürdig ist, und mit Protokoll.
  10. Legal Hold: Ein Flag pro Dossier stoppt jede Vernichtung, solange ein Verfahren läuft.
  11. Suche: PostgreSQL-Volltext reicht für Millionen Dokumente. Für Facetten, Tippfehler-Toleranz und sehr grosse Mengen ein Suchcluster, mit Rechte-Feldern im Index.
  12. Datenschutz: Datenminimierung, Löschung nach Frist, Auskunftsrecht. Personendaten in Dokumenten machen auch Suchindex und Backups schützenswert.
  13. Netz und Schlüssel: Private Endpoints, keine öffentlichen Storage-Zugänge, Schlüssel im Key Vault oder HSM, Daten in Schweizer Regionen.
  14. Mandanten: Mehrere Ämter im selben System: getrennte Datenbanken oder Schemas pro Amt geben harte Isolation; Zeilen-Filter sind billiger, aber riskanter.

5. Vergleich: drei Design-Varianten

  • A. Standardprodukt (GEVER-System, DMS): Fachfunktionen, Archiv-Schnittstellen und Zertifizierungen fertig. Aber: Anpassung schwer, Lizenz, Integration in eigene Fachanwendungen aufwendig.
  • B. Eigenbau auf PostgreSQL + Object Storage (wie oben): passt genau zum Fachprozess, offene Technologie. Preis: Audit, Retention, Archiv-Export und Nachweise selbst bauen und betreiben.
  • C. Fachanwendung + angebundenes GEVER: Die Fachanwendung arbeitet schnell, das GEVER-System ist Ablage und Archiv-Weg. Oft der realistische Weg; Preis: Synchronisation und zwei Rechte-Modelle.

6. In der Produktion

  1. Treffer zeigen fremde Titel: Rechte erst nach der Suche gefiltert, oder Snippets aus nicht berechtigten Dokumenten. Fix: Rechte-Filter in der Query, Snippets nur für berechtigte Treffer.
  2. Bearbeitungen gehen verloren: Zwei Personen speichern gleichzeitig. Fix: Optimistic Locking mit 412 und Hinweis im UI.
  3. Audit-Lücken: Lesezugriffe über einen Batch-Export nicht protokolliert. Fix: Audit in der gemeinsamen Zugriffsschicht, nicht in jedem Endpoint.
  4. Vernichtung trotz Verfahren: Kein Legal Hold. Fix: Flag, Vier-Augen-Prinzip für Vernichtungsläufe, Protokoll.
  5. Gescannte PDFs nicht findbar: Kein Text. Fix: OCR in der Verarbeitungs-Pipeline, Qualität stichprobenartig prüfen.
  6. Backup enthält gelöschte Personendaten: Fix: Backup-Fristen dokumentieren, Wiederherstellung mit erneuter Löschung.

7. Diagnose: Werkzeuge und Queries

  • Wer hat Dokument X gelesen? SELECT at, actor, action FROM audit_log WHERE object_ref LIKE 'document:4711%' ORDER BY at;
  • Rechte prüfen: SELECT principal FROM dossier_acl WHERE dossier_id = 7; plus Gruppen aus dem IAM.
  • Fällige Dossiers mit der Retention-Query; Anzahl pro Monat als Kennzahl.
  • Suche: EXPLAIN (ANALYZE, BUFFERS), ts_debug('german', '…') für unerwartete Stämme.
  • Integrität: periodisch SHA-256 der gespeicherten Bytes gegen document_versions.sha256 prüfen.
  • Scan-Ergebnisse: Defender-Protokoll (z. B. Log Analytics) für Uploads.

8. Senior-Punkte

  1. Hier ist nicht die Last das Problem, sondern Sicherheit, Nachvollziehbarkeit und Jahrzehnte Lebensdauer. Das sage ich im Interview früh.
  2. Rechte gehören in jede Query, auch in Suche, Export und Vorschau. Eine zentrale Zugriffsschicht verhindert Lücken.
  3. Nie überschreiben, nie still löschen. Versionen, WORM und protokollierte Vernichtung.
  4. Audit ist ein eigenes System mit eigenen Rechten. Wer Dokumente verwaltet, darf das Log nicht ändern.
  5. Retention ist Fachlogik, nicht ein Storage-Lifecycle allein. Archiv-Angebot und Legal Hold gehören dazu.
  6. Standardprodukt zuerst prüfen. Eigenbau nur, wenn der Fachprozess es wirklich verlangt.

9. Dein Beispiel

10. Fallen

  • „Ich filtere die Rechte nach der Suche.“ → Falsche Trefferzahlen und Leaks über Titel und Snippets. Filter in der Query.
  • „Nach 10 Jahren löscht ein Lifecycle-Job automatisch.“ → Falsch für Behörden. Erst dem Archiv anbieten, Legal Hold beachten, protokollieren.
  • „Das Audit-Log liegt in derselben Tabelle mit denselben Rechten.“ → Admins könnten Spuren löschen. Getrennt und append-only.
  • „PDF reicht für die Langzeit.“ → Nur PDF/A garantiert eingebettete Schriften und keine externen Abhängigkeiten.
  • „Volltext auf Deutsch reicht.“ → In der Schweiz kommen fr und it dazu, mit eigenen Stemmern.
  • „Klassifizierung ist nur ein Label.“ → Sie bestimmt Rechte, Verschlüsselung, Speicherort und Protokollierung.

11. Selbsttest

Warum?

Warum PDF/A?

Es ist für Langzeitarchivierung gemacht: Schriften eingebettet, keine externen Inhalte. Das Original bleibt zusätzlich erhalten.

Warum ist hier nicht die Last das Hauptproblem?

2 TB pro Jahr und rund 7 Suchen pro Sekunde sind klein. Schwer sind Sicherheit, lückenloses Audit und Jahrzehnte Lebensdauer.

Wie innen?

Wie setzen Sie Rechte in der Suche durch?

Der Rechte-Filter ist Teil der Query oder des Index-Filters. Snippets nur für berechtigte Treffer.

Wie versionieren Sie Dokumente?

Jede Änderung ist eine neue Version mit Hash, Autor und Zeit. Optimistic Locking über die Versionsnummer, HTTP 412 bei Konflikt.

Wie machen Sie das Audit-Log manipulationssicher?

Append-only per Trigger oder Rechte, in einem getrennten System mit eigenen Admins. Optional Hash-Kette oder WORM-Speicher.

Wie machen Sie gescannte Dokumente durchsuchbar?

OCR in der Verarbeitungs-Pipeline, Text in die Volltext-Spalte. Qualität stichprobenartig prüfen.

Was geht kaputt, wenn die Rechte erst nach der Suche gefiltert werden?

Trefferzahlen und Seiten stimmen nicht, und Titel und Snippets fremder Dossiers leaken. Der Rechte-Filter gehört in die Query.

Zahlen

Wie gross ist die Last?

Klein: ca. 2 TB pro Jahr und einige Suchen pro Sekunde. Das Design wird von Sicherheit und Langzeit getrieben.

Was geht kaputt, wenn 20 % aller Dokumente auf eine Suche passen?

Der Planer nimmt dann den Seq Scan statt des GIN-Index; bei seltenen Wörtern nutzt er den Index. Beides mit EXPLAIN (ANALYZE) prüfen.

Vergleich

PostgreSQL-Volltext oder Suchcluster?

PostgreSQL reicht für Millionen Dokumente und macht Rechte-Joins leicht. Ein Suchcluster lohnt für Facetten, Tippfehler und sehr grosse Mengen.

Wie isolieren Sie mehrere Ämter?

Hart über eigene Datenbank oder Schema pro Amt, weich über Zeilen-Filter. Bei sensiblen Daten bevorzuge ich harte Isolation.

Standardprodukt oder Eigenbau?

Erst ein GEVER- oder DMS-Produkt prüfen, weil Archiv-Wege und Nachweise fertig sind. Eigenbau nur bei besonderem Fachprozess, oft als Fachanwendung mit GEVER-Anbindung.

Warum harte Isolation pro Amt statt Zeilen-Filter?

Eine eigene DB oder ein eigenes Schema isoliert auch bei Bugs und vereinfacht Nachweise. Zeilen-Filter sind billiger, aber ein vergessener Filter leakt sofort.

Produktion

Szenario: Ein Mitarbeiter sieht in der Trefferliste Titel aus einem vertraulichen Dossier. Was tun Sie?

Sofort Snippets und Titel für nicht berechtigte Treffer abschalten. Ursache finden: Filter nach der Suche oder falsche ACL im Index. Im Audit prüfen, wer was gesehen hat, und den Vorfall melden.

Szenario: Zwei Sachbearbeiter überschreiben gegenseitig ihre Änderungen. Was ändern Sie?

Optimistic Locking mit Versionsnummer und If-Match. Der zweite bekommt 412 und sieht die neue Version zum Zusammenführen.

Szenario: Die Revision fragt, wer ein Dokument vor drei Jahren gelesen hat. Können Sie das beantworten?

Nur wenn Lesezugriffe zentral und append-only protokolliert sind und die Audit-Frist lang genug ist. Darum Audit in der Zugriffsschicht und eine definierte Aufbewahrung für das Log.

Was geht kaputt, wenn ein Batch-Export am Audit vorbeiliest?

Lesezugriffe fehlen im Log, und die Revision kann Fragen nicht beantworten. Audit gehört in die gemeinsame Zugriffsschicht, nicht in jeden Endpoint.

Design

Skizzieren Sie das System in einer Minute.

Dossiers mit versionierten Dokumenten, Bytes verschlüsselt und unveränderbar im Object Storage, Metadaten, Rechte und Volltext in PostgreSQL, append-only Audit. Upload über Quarantäne und Scan. Am Fristende Archiv-Angebot, dann protokollierte Vernichtung.

Welche Fragen stellen Sie zuerst?

Klassifizierungsstufen, Rechte-Modell, Sprachen, Fristen und Archiv-Weg, Mengen, Integration mit bestehendem GEVER, Betrieb in der Schweiz.

Wie bauen Sie das Rechte-Modell?

Rollen für Funktionen, ACL pro Dossier mit Personen und Organisationseinheiten, Need-to-know. Dokumente erben vom Dossier.

Welche Klassifizierungsstufen kennt der Bund?

Das ISG kennt intern, vertraulich und geheim. Die Stufe bestimmt Schutzmassnahmen und Speicherort.

Was passiert am Ende der Aufbewahrungsfrist?

Das Dossier wird dem Archiv angeboten. Archivwürdiges geht dorthin, der Rest wird protokolliert vernichtet. Legal Hold stoppt das.

Wie gehen Sie mit drei Landessprachen um?

Sprache pro Dokument erkennen oder erfassen und die passende Textsuche-Konfiguration nutzen: german, french, italian.

Wie schützen Sie die Dateien?

Quarantäne und Malware-Scan, Verschlüsselung mit Schlüsseln im Key Vault, Private Endpoints, kurzlebige Download-Links, WORM bis Fristende.

Was geht kaputt, wenn ein Lifecycle-Job nach 10 Jahren automatisch löscht?

Behörden müssen Unterlagen zuerst dem Archiv anbieten, und ein Legal Hold stoppt jede Vernichtung. Ein automatischer Lösch-Job verletzt beides.
