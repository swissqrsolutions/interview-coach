Caching: Strategien, Redis, Invalidierung

Kern: Ein Cache ist ein schneller Zwischenspeicher für Daten, die teuer zu holen oder zu berechnen sind. Er senkt Latenz und entlastet die Datenbank. Der Preis ist Veraltung: Der Cache kann einen alten Wert liefern.

Antwort-Muster

Frage: Wie bauen Sie einen Cache vor die Datenbank?

  1. Mechanismus: Cache-Aside: Die App liest zuerst Redis, bei Miss die DB, und füllt den Cache mit TTL.
  2. Zahl: Ein Hit kostet rund 1 ms; schon 10 Prozent Cache-Grösse bringen etwa zwei Drittel Hits.
  3. Trade-off: Beim Write lösche ich den Key statt ihn zu überschreiben; die TTL ist das Sicherheitsnetz gegen Veraltung.
  4. Produktion: Gegen Stampedes nutze ich TTL-Jitter und einen Lock pro Key.

1. Die Reise eines Reads und eines Writes (Cache-Aside)

  1. App fragt zuerst den Cache: GET user:42. Bei Cache-Aside steuert die App alles selbst.
  2. Cache-Hit: Redis liefert den Wert in ca. 1 ms. Die Datenbank bleibt unberührt.
  3. Cache-Miss: Die App liest aus der Datenbank. Das kostet viel mehr Zeit.
  4. Befüllen: Die App schreibt den Wert mit Ablaufzeit: SET user:42 … EX 300. Die TTL (Time to Live) begrenzt, wie alt ein Wert werden kann.
  5. Write: Ein Nutzer ändert sein Profil.
  6. Datenbank zuerst: Die App schreibt in die Datenbank. Die DB bleibt die Source of Truth.
  7. Key löschen: Danach löscht die App den Cache-Eintrag. Der nächste Read lädt frisch. Löschen ist sicherer als Überschreiben, weil zwei parallele Writes sonst in falscher Reihenfolge landen können.
  8. Stampede: Läuft die TTL eines sehr beliebten Keys ab, fragen alle gleichzeitig die DB. Das heisst Cache Stampede (auch Thundering Herd, Dogpile).

2. Aufbau

  1. Browser-Cache: speichert HTTP-Antworten nach Cache-Control. Kein Netz nötig.
  2. CDN: speichert statische und öffentliche Antworten an Edge-Standorten nahe beim Nutzer.
  3. In-Process-Cache: eine Map im Speicher der App, z. B. Caffeine. Am schnellsten, aber jede Instanz hat ihre eigene Kopie.
  4. Verteilter Cache (Redis): ein gemeinsamer Cache für alle Instanzen. Ein Netz-Hop, ca. 1 ms.
  5. Datenbank: hat einen eigenen Buffer Pool für Seiten im RAM. Den steuert man kaum direkt.

3. Details, die Interviewer fragen

  1. Cache-Aside (Lazy Loading): Die App liest aus dem Cache, lädt bei Miss aus der DB und füllt den Cache. Nur gelesene Daten landen im Cache. Häufigstes Muster.
  2. Read-Through: Die App fragt nur den Cache. Der Cache lädt bei Miss selbst aus der DB. Die Ladelogik sitzt in der Cache-Bibliothek.
  3. Write-Through: Jeder Write geht synchron in Cache und DB. Der Cache ist immer aktuell, Writes werden langsamer.
  4. Write-Back (Write-Behind): Der Write geht nur in den Cache. Der Cache schreibt später gebündelt in die DB. Sehr schnell, aber Datenverlust bei Ausfall möglich.
  5. Write-Around: Writes gehen nur in die DB. Der Cache füllt sich erst beim Lesen. Gut für Daten, die selten gelesen werden.
  6. Refresh-Ahead: Der Cache lädt beliebte Keys neu, bevor die TTL abläuft. Weniger Misses, aber Arbeit für Keys, die keiner mehr braucht.
  7. TTL: Die TTL ist die maximale Lebensdauer eines Eintrags. Sie ist die einfachste Invalidierung und ein Sicherheitsnetz für vergessene Deletes.
  8. Eviction: Eviction entfernt Einträge, wenn der Speicher voll ist. Redis prüft dafür maxmemory und maxmemory-policy.
  9. Redis-Policies: noeviction (Writes schlagen fehl, Standard in Open-Source-Redis), allkeys-lru, allkeys-lfu, allkeys-random, volatile-lru, volatile-lfu, volatile-random, volatile-ttl. Seit Redis 8.6 auch allkeys-lrm und volatile-lrm (least recently modified). volatile-* betrifft nur Keys mit TTL.
  10. LRU vs LFU: LRU (Least Recently Used) wirft den am längsten nicht genutzten Key raus. LFU (Least Frequently Used) wirft den selten genutzten raus. LFU übersteht Scans besser. Redis rechnet beides approximiert über Stichproben (maxmemory-samples).
  11. Stampede-Schutz: Lock pro Key (SET lock:key 1 NX EX 10), Request-Bündelung in der App (Single Flight), alten Wert liefern und im Hintergrund neu laden (stale-while-revalidate), probabilistisch früh neu laden, TTL-Jitter.
  12. Cache Penetration: Requests für Keys, die es nicht gibt, gehen immer an die DB. Lösung: auch „nicht gefunden“ kurz cachen (Negative Caching) oder ein Bloom-Filter.
  13. Hot Key: Ein einzelner Key bekommt so viel Last, dass ein Redis-Knoten heiss läuft. Lösung: zusätzlicher In-Process-Cache, Key auf mehrere Kopien verteilen.
  14. Konsistenz-Race: Leser A liest alten Wert aus der DB. Schreiber B ändert DB und löscht den Key. A schreibt danach seinen alten Wert in den Cache. Lösung: kurze TTL, verzögertes zweites Löschen, Versionsnummer im Wert oder Invalidierung über CDC (Change Data Capture).
  15. Redis Cluster: Redis Cluster verteilt Keys auf 16 384 Hash Slots. Mehr-Key-Befehle brauchen Keys im gleichen Slot. Das erzwingt man mit Hash Tags wie {user:42}:profile.
  16. Replikation: Redis repliziert asynchron. Bei Failover können die letzten Writes verloren gehen. Für einen Cache ist das meist ok, für einen Session-Store vielleicht nicht.
  17. Azure: Azure Cache for Redis wird abgelöst. Basic, Standard und Premium enden am 30.09.2028, Enterprise am 31.03.2027. Nachfolger ist Azure Managed Redis.

4. Fallen

  • „Beim Update schreibe ich den neuen Wert in den Cache.“ → Riskant. Parallele Writes können in falscher Reihenfolge landen. Löschen ist sicherer.
  • „Erst Cache löschen, dann DB schreiben.“ → Falsch. Ein Leser lädt dazwischen den alten Wert neu in den Cache.
  • „Redis wirft automatisch alte Keys raus.“ → Nicht standardmässig. Open-Source-Redis nutzt noeviction.
  • „Mehr Cache bringt immer mehr.“ → Falsch. Der Ertrag nimmt stark ab, siehe Simulation.
  • „Ein Cache macht Writes schneller.“ → Meist nicht. Nur Write-Back tut das, mit Risiko.
  • „volatile-lru schützt mich vor OOM.“ → Nur, wenn genug Keys eine TTL haben.

5. Selbsttest

Warum?

Was ist ein Cache und welches Problem löst er?

Ein schneller Zwischenspeicher für teure Daten. Er senkt Latenz und entlastet die Datenbank. Preis: Werte können veraltet sein.

Warum den Key löschen statt aktualisieren?

Zwei parallele Writes können den Cache in falscher Reihenfolge überschreiben. Nach dem Löschen lädt der nächste Read den aktuellen Wert.

Wie innen?

Was ist Cache-Aside?

Die App liest zuerst den Cache. Bei Miss liest sie die DB und schreibt den Wert mit TTL in den Cache. Beim Write ändert sie die DB und löscht den Key.

Warum zuerst DB, dann Cache löschen?

Löscht man zuerst, kann ein Leser in der Lücke den alten DB-Wert neu cachen. Er bleibt dann bis zur TTL falsch.

Ist Redis-LRU exakt?

Nein. Redis nimmt Stichproben von Keys und wirft den ältesten davon raus. Die Grösse steuert maxmemory-samples.

Wie verteilt Redis Cluster die Keys?

Über 16 384 Hash Slots, berechnet mit CRC16 des Keys. Hash Tags in geschweiften Klammern legen zusammengehörige Keys in denselben Slot.

Zahlen

Was ist eine TTL und wie wählen Sie sie?

Die maximale Lebensdauer eines Eintrags. Sie richtet sich danach, wie alt ein Wert sein darf. Dazu etwas Zufall gegen gleichzeitiges Ablaufen.

Was bringt ein Cache von 10 % der Key-Menge?

Bei schiefer Verteilung rund zwei Drittel Hits (Simulation: 67 %). Danach nimmt der Ertrag stark ab: 50 % Grösse bringen nur noch 89 %.

Was geht kaputt, wenn 10 000 Keys dieselbe TTL bekommen?

Alle laufen in derselben Sekunde ab, und die DB bekommt eine Miss-Welle. TTL-Jitter von ±10 % verteilt die Spitze auf rund 200 pro Sekunde.

Vergleich

Wo kann man cachen?

Browser, CDN, Reverse Proxy, In-Process in der App, verteilt in Redis und im Buffer Pool der Datenbank.

Read-Through vs Cache-Aside?

Bei Read-Through lädt der Cache selbst aus der DB. Bei Cache-Aside macht das die App. Das Verhalten ist ähnlich, der Code sitzt anders.

Write-Through vs Write-Back?

Write-Through schreibt synchron in Cache und DB: konsistent, aber langsamer. Write-Back schreibt erst in den Cache und später gebündelt in die DB: schnell, aber Datenverlust möglich.

Was ist Write-Around?

Writes gehen nur in die DB, nicht in den Cache. Gut für Daten, die nach dem Schreiben selten gelesen werden.

LRU vs LFU?

LRU wirft den am längsten nicht genutzten Key raus. LFU wirft den selten genutzten raus. LFU ist robuster gegen Scans, LRU reagiert schneller auf neue Trends.

In-Process-Cache oder Redis?

In-Process ist schneller, aber pro Instanz und schwer zu invalidieren. Redis ist geteilt und einfach zu löschen, kostet aber einen Netz-Hop. Oft beides: zwei Stufen.

Welches Azure-Produkt nutzen Sie heute für Redis?

Azure Managed Redis. Azure Cache for Redis wird abgelöst: Basic, Standard, Premium bis 30.09.2028, Enterprise bis 31.03.2027.

Warum übersteht LFU einen Scan besser als LRU?

Ein Scan fasst jeden Key genau einmal an. Bei LRU verdrängt das die heissen Keys; LFU zählt die Häufigkeit und behält sie.

Produktion

Was ist eine Cache Stampede?

Ein beliebter Key läuft ab, und viele Requests laden ihn gleichzeitig aus der DB. Die DB wird überlastet.

Wie verhindern Sie eine Stampede?

Lock pro Key mit SET NX, Single Flight in der App, alten Wert liefern und im Hintergrund neu laden, früh probabilistisch neu laden, TTL-Jitter.

Was ist Cache Penetration?

Requests für nicht existierende Keys gehen immer an die DB. Lösung: Negative Caching mit kurzer TTL oder Bloom-Filter.

Was ist ein Hot Key und was tun Sie?

Ein Key mit so viel Last, dass ein Redis-Knoten überlastet ist. Lösung: lokaler In-Process-Cache davor oder den Key auf mehrere Kopien verteilen.

Kann Redis Daten verlieren?

Ja. Replikation ist asynchron, bei Failover fehlen die letzten Writes. Persistenz mit RDB oder AOF hilft, macht Redis aber nicht zur Datenbank.

Szenario: Nach einem Redis-Failover ist die Datenbank 10 Minuten überlastet. Was tun Sie?

Cold Start: Der Cache ist leer. Kurzfristig DB-Last drosseln. Langfristig: Replica mit Daten statt leerer Neustart, Cache vorwärmen, Stampede-Schutz, DB-Kapazität für Cache-Ausfall planen.

Szenario: Nutzer sehen nach einer Profiländerung minutenlang alte Daten. Warum?

Der Key wird nicht gelöscht, oder ein Race schreibt den alten Wert zurück. Prüfen: Delete nach Commit, alle Instanzen und Stufen (auch In-Process und CDN) invalidieren, kürzere TTL.

Szenario: Redis meldet OOM, obwohl Eviction eingeschaltet ist. Warum?

Wahrscheinlich volatile-lru ohne genug Keys mit TTL, oder noeviction. Lösung: allkeys-lru oder allkeys-lfu für reine Caches, TTL auf alle Keys, maxmemory prüfen.

Was geht kaputt, wenn die App ohne Cache nicht mehr funktioniert?

Der Cache ist dann ein Single Point of Failure: Fällt er aus, kippt die DB. DB-Kapazität für den Cache-Ausfall planen und Lasten drosseln.

Design

Welche Eviction Policies hat Redis?

noeviction, allkeys- und volatile-Varianten von lru, lfu und random, dazu volatile-ttl. Seit Redis 8.6 auch allkeys-lrm und volatile-lrm. Standard in Open-Source-Redis: noeviction.

Wie bleibt der Cache konsistent mit der DB?

Gar nicht perfekt. Man begrenzt die Veraltung: Delete nach Commit, TTL als Netz, Invalidierung über Events oder CDC, Versionen im Wert.

Welche Metriken beobachten Sie?

Hit Ratio, Evicted Keys, Speicher, Latenz, Server Load und langsame Befehle. Die Hit Ratio pro Key-Bereich, nicht nur gesamt.

Warum lautet die erste Design-Frage: Wie alt darf der Wert sein?

Die Antwort bestimmt TTL und Invalidierung. Ein Kontostand verträgt keine Veraltung, Referenzdaten vertragen Minuten.

Mehr

Gerüst

  • Warum? Teure Reads aus dem RAM statt aus der DB: weniger Latenz, weniger Last. Preis: Der Cache kann alte Werte liefern.
  • Wie innen? Cache-Aside: GET, bei Miss DB lesen und SET mit TTL. Beim Write: DB ändern, dann Key löschen, nicht überschreiben.
  • Zahlen Redis-Hit ca. 1 ms. 10 % Cache-Grösse ≈ 67 % Hits bei Zipf-Last. Redis Cluster: 16 384 Hash Slots. TTL immer mit Jitter.
  • Vergleich In-Process (Nanosekunden, pro Instanz) vs Redis (geteilt, ein Netz-Hop). LRU reagiert schnell, LFU übersteht Scans.
  • Produktion Stampede, wenn ein Hot Key abläuft. Cold Start nach Failover trifft die DB. OOM bei noeviction (Standard).
  • Design Zuerst fragen: Wie alt darf der Wert sein? DB bleibt die Wahrheit und muss den Cache-Ausfall gedrosselt überleben.

class LRU:                                  # OrderedDict = LRU in a few lines
    def get(self, k, load):
        if k in self.d:
            self.d.move_to_end(k); self.hits += 1; return self.d[k]
        self.miss += 1; v = load(k); self.d[k] = v
        if len(self.d) > self.cap:
            self.d.popitem(last=False)     # evict least recently used
        return v

weights = [1 / (i + 1) for i in range(10_000)]          # Zipf-like popularity

Echte Ausgabe, Python 3 (Simulation). Kein echtes Redis; die Zahlen zeigen nur die Mechanik.

  1. Kleiner Cache, grosse Wirkung: Bei schiefer Verteilung (wenige Keys sehr beliebt) bringen 10 % der Keys schon 67 % Hits.
  2. Abnehmender Ertrag: Von 20 % auf 50 % Grösse steigt die Hit Ratio nur noch um 12 Punkte.
  3. Scan verdrängt heisse Keys: Ein Batch-Job liest jeden Key einmal. Danach fällt die Hit Ratio von 68 % auf 51 %. Das heisst Cache Pollution. LFU ist dagegen robuster.
  4. Stampede: Ohne Schutz gehen 400 Requests gleichzeitig an die DB. Mit Lock nur einer, aber 399 warten. Mit „alten Wert liefern, einer lädt neu“ wartet niemand.
  5. TTL-Jitter: Gleiche TTL lässt alle 10 000 Keys in derselben Sekunde ablaufen. ±10 % Zufall senkt die Spitze auf ca. 200 pro Sekunde.

Vergleich: Schreib-Strategien

  • Cache-Aside: einfach, robust bei Cache-Ausfall. Erster Read ist langsam, Race möglich.
  • Read-Through: wie Cache-Aside, aber Logik in der Bibliothek. Sauberer Code.
  • Write-Through: Cache immer frisch. Writes langsamer, Cache voll mit nie gelesenen Daten.
  • Write-Back: schnellste Writes, bündelt Last. Risiko: Datenverlust, komplexe Fehlerfälle.
  • Write-Around: schützt den Cache vor Einmal-Writes. Erster Read nach Write ist ein Miss.

In der Produktion

  1. DB bricht nach Redis-Neustart ein: Der Cache ist leer (Cold Start). Alle Reads gehen an die DB. Lösung: Cache vorwärmen, Rate Limit auf DB-Lasten, Replica statt Neustart.
  2. Stampede um Mitternacht: Ein Batch setzt alle Keys mit gleicher TTL. Lösung: TTL-Jitter, Lock pro Key, stale-while-revalidate.
  3. OOM-Fehler bei Writes: Redis meldet OOM command not allowed. Ursache: noeviction oder volatile-* ohne Keys mit TTL. Lösung: allkeys-lru oder allkeys-lfu für reine Caches.
  4. Alte Daten nach Update: Delete vergessen oder Race. Lösung: Löschen nach Commit, kurze TTL als Netz, Events für Invalidierung.
  5. Latenz-Spitzen: Grosse Keys (MB-Werte) oder KEYS * blockieren den Single-Thread-Ablauf von Redis. Lösung: Werte klein halten, SCAN statt KEYS.
  6. Cache verdeckt Fehler: Die App ist ohne Cache zu langsam, um zu funktionieren. Lösung: DB-Kapazität für den Cache-Ausfall planen, Circuit Breaker.

Diagnose: Werkzeuge und Befehle

  • INFO stats: keyspace_hits, keyspace_misses (Hit Ratio), evicted_keys, expired_keys.
  • INFO memory: used_memory, maxmemory, maxmemory_policy, Fragmentierung.
  • SLOWLOG GET 10: langsame Befehle. LATENCY DOCTOR: Ursachen für Latenz.
  • redis-cli --bigkeys und --hotkeys (nur mit LFU-Policy): grosse und heisse Keys finden.
  • MEMORY USAGE <key> und TTL <key>: Grösse und Restlaufzeit eines Keys.
  • Azure Monitor für Azure Redis: Cache Hits, Cache Misses, Server Load, Used Memory, Evicted Keys.
  • Anwendungsmetrik: Hit Ratio pro Key-Präfix. Eine Gesamt-Hit-Ratio versteckt schlechte Bereiche.

Senior-Punkte

  1. Zuerst fragen: Wie alt darf der Wert sein? Diese Antwort bestimmt TTL und Invalidierung, nicht die Technik.
  2. Die Datenbank bleibt die Wahrheit. Der Cache ist ein Optimierungs-Layer und darf jederzeit leer sein.
  3. Löschen statt Überschreiben beim Write. Dazu eine TTL als Sicherheitsnetz.
  4. Stampede und Cold Start plane ich ein, bevor sie passieren: Jitter, Lock, stale-while-revalidate.
  5. Die DB muss einen Cache-Ausfall überleben, zumindest gedrosselt. Sonst ist der Cache ein Single Point of Failure.
  6. Hit Ratio messen, pro Bereich. Ein Cache mit 20 % Hits kostet oft mehr, als er spart.
