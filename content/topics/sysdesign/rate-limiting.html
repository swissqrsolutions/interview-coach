Rate Limiting: Algorithmen

Kern: Rate Limiting ist eine Grenze, wie viele Requests ein Client pro Zeitfenster schicken darf. Es schützt das Backend vor Überlast, Missbrauch und einem lauten Mandanten (Noisy Neighbor). Wer die Grenze überschreitet, bekommt 429 Too Many Requests mit Retry-After. Der Algorithmus bestimmt, wie viele Bursts (kurze Spitzen) durchkommen.

Antwort-Muster

Frage: Wie funktioniert ein Token Bucket?

  1. Mechanismus: Ein Eimer hält höchstens b Tokens und füllt sich mit r pro Sekunde, jeder Request kostet eines.
  2. Zahl: Bei Kapazität 5 und 0,5 Token/s kommen Bursts bis 5 sofort durch, der Durchschnitt bleibt 0,5/s.
  3. Trade-off: Kurzfristig kommt mehr als Rate mal Fenster durch, das ist gewollt.
  4. Produktion: Der Zähler liegt atomar in Redis (Lua-Skript), sonst zählt jede Instanz für sich.

1. Die Reise eines Requests durch den Rate Limiter

  1. Request kommt an. Ein Partner schickt POST /orders an das Gateway.
  2. Key bestimmen. Der Counter Key sagt, wer gezählt wird. Typisch: Subscription-Key, User-ID aus dem JWT oder IP. Der Key entscheidet über Fairness.
  3. Zähler prüfen. Der Limiter liest und erhöht den Zähler in einem atomaren Schritt. In Redis: INCR oder ein Lua-Skript.
  4. Entscheiden. Der Algorithmus vergleicht mit dem Limit. Er entscheidet auch, wie viel Burst erlaubt ist.
  5. Erlaubt: Der Request geht ans Backend. Die Antwort kann Header mit dem Restkontingent tragen. Abgelehnt: Das Gateway antwortet sofort mit 429 und Retry-After.
  6. Client wartet. Ein guter Client liest Retry-After. Ohne Header nutzt er exponentielles Backoff mit Jitter, also wachsende, zufällig gestreute Wartezeiten.
  7. Neuer Versuch. Jetzt ist wieder Kontingent frei. Ohne Warten würde der Client das Problem verschärfen (Retry Storm).

2. Aufbau

  1. Edge: Die Web Application Firewall (WAF) von Azure Front Door blockt grobe Flut pro IP. Sie kennt keine Benutzer.
  2. API Gateway: Azure API Management (APIM) begrenzt pro Subscription-Key, Benutzer oder IP. Das ist der Standardort für API-Limits.
  3. Service: Der Service selbst kennt Geschäftsregeln. Beispiel: max. 3 Passwort-Resets pro Stunde und Konto.
  4. Redis: Mehrere Instanzen teilen ihre Zähler in einem zentralen Speicher. Sonst zählt jede Instanz für sich.
  5. Ablehnung: Jede Schicht antwortet mit 429 und Retry-After. Das Backend sieht die Anfrage dann nie.

3. Details, die Interviewer fragen

  1. Token Bucket: Ein Eimer hält max. b Tokens (Burst-Grösse). Er füllt sich mit r Tokens pro Sekunde. Jeder Request kostet ein Token. Zwei Parameter: Rate und Burst. Speicher: zwei Zahlen pro Key (Tokens, letzter Zeitpunkt).
  2. Leaky Bucket: Requests fliessen in einen Eimer mit fester Abflussrate. Als Queue glättet er den Ausgang. Als Meter ist er gleich wie der Token Bucket. NGINX limit_req nutzt diese Methode.
  3. Fixed Window Counter: Ein Zähler pro Key und Fenster, z. B. user:42:202611241310. Sehr billig: INCR und EXPIRE. Schwäche: bis zum doppelten Limit an der Fenstergrenze.
  4. Sliding Window Log: Jeder Zeitstempel kommt in eine sortierte Liste. Alte Einträge fallen raus. Exakt, aber Speicher wächst mit dem Limit. In Redis: Sorted Set mit ZADD, ZREMRANGEBYSCORE, ZCARD.
  5. Sliding Window Counter: Formel: prev × Überlappung + curr. Bei 30 % im neuen Fenster zählt das alte zu 70 %. Billig wie Fixed Window, fast so genau wie der Log.
  6. Atomarität: Lesen, Prüfen und Schreiben müssen ein Schritt sein. In Redis: INCR (atomar), MULTI/EXEC oder ein Lua-Skript. Ein Token Bucket braucht fast immer ein Lua-Skript.
  7. 429 Too Many Requests: RFC 6585 definiert den Statuscode. Die Antwort darf Retry-After enthalten. Caches dürfen 429 nicht speichern.
  8. Retry-After: RFC 9110 erlaubt zwei Formen: Sekunden (Retry-After: 4) oder ein HTTP-Datum. Er kommt auch mit 503 vor.
  9. RateLimit-Header: Üblich sind X-RateLimit-Limit, -Remaining, -Reset (nicht standardisiert). Die IETF arbeitet an RateLimit-Policy und RateLimit. Das ist noch ein Entwurf (draft-12, November 2026). Beispiel: RateLimit-Policy: "default";q=100;w=60 und RateLimit: "default";a=99;w=50.
  10. Rate Limit vs Quota: Ein Rate Limit schützt vor Spitzen (pro Sekunde, Minute). Eine Quota begrenzt das Volumen über lange Zeit (pro Monat), oft fürs Geschäftsmodell.
  11. APIM-Policies: rate-limit zählt pro Subscription. rate-limit-by-key zählt pro frei wählbarem Key, z. B. IP oder JWT-Claim. Beide antworten mit 429. quota und quota-by-key antworten mit 403 Forbidden und Retry-After.
  12. APIM-Algorithmus: Die klassischen Tiers nutzen ein Sliding Window, die v2-Tiers einen Token Bucket. renewal-period ist bei rate-limit-by-key max. 300 s.
  13. APIM-Genauigkeit: Microsoft sagt: Rate Limiting ist wegen der verteilten Architektur nie ganz genau. Jedes regionale Gateway zählt für sich. Ein Multi-Region-APIM aggregiert die Zähler nicht.
  14. Throttling vs Rate Limiting Pattern: Das Throttling Pattern (Azure Architecture Center) schützt den eigenen Service. Das Rate Limiting Pattern drosselt die eigenen Aufrufe an einen fremden Dienst, z. B. mit einer Queue.
  15. Fail-open vs fail-closed: Fällt Redis aus, muss der Limiter entscheiden. Fail-open lässt alles durch und schützt die Verfügbarkeit. Fail-closed blockt alles und schützt das Backend.

4. Fallen

  • „Rate Limiting in jedem Pod reicht.“ → Falsch. Jede Instanz zählt für sich. Das echte Limit wächst mit der Pod-Anzahl.
  • „Fixed Window hält das Limit exakt.“ → Falsch. An der Fenstergrenze kommt bis zum Doppelten durch.
  • „Token Bucket und Leaky Bucket sind verschieden streng.“ → Falsch als Meter. Sie sind gleich. Nur der Leaky Bucket als Queue glättet.
  • „Bei Überlast antwortet man mit 503.“ → Für einen Client über seinem Limit ist 429 richtig. 503 heisst: Der Server selbst kann nicht.
  • „Die RateLimit-Header sind Standard.“ → Falsch. Sie sind ein IETF-Entwurf. Viele APIs nutzen X-RateLimit-*.
  • „APIM-Quota liefert auch 429.“ → Falsch. quota und quota-by-key liefern 403.

5. Selbsttest

Warum?

Was ist Rate Limiting und welches Problem löst es?

Eine Grenze für Requests pro Zeitfenster und Client. Es schützt das Backend vor Überlast, Missbrauch und lauten Mandanten.

Warum bekommt ein Client über dem Limit 429 und nicht 503?

429 heisst: Der Client schickt zu viel. 503 heisst: Der Server selbst kann nicht. Caches dürfen 429 nicht speichern.

Wie innen?

Wie funktioniert ein Token Bucket?

Ein Eimer hält max. b Tokens und füllt sich mit r pro Sekunde. Jeder Request nimmt ein Token. Kein Token: 429.

Wie funktioniert ein Leaky Bucket?

Requests fliessen in einen Eimer mit fester Abflussrate. Ist er voll, wird abgelehnt. Als Queue glättet er den Ausgang.

Wie bauen Sie einen verteilten Rate Limiter mit Redis?

Zähler pro Key in Redis. Fixed Window: INCR plus EXPIRE. Sliding Log: Sorted Set. Token Bucket: Lua-Skript, damit alles atomar ist.

Warum muss die Prüfung atomar sein?

Sonst lesen zwei Instanzen denselben Stand und lassen beide durch. Das Limit wird überschritten.

Zahlen

Welche zwei Parameter hat ein Token Bucket?

Die Rate (Tokens pro Sekunde) und die Kapazität (maximaler Burst).

Was ist das Problem beim Fixed Window?

An der Fenstergrenze passen zwei volle Fenster direkt hintereinander. So kommt bis zum doppelten Limit in einem Fensterzeitraum durch.

Wie rechnet der Sliding Window Counter?

Vorheriges Fenster × Überlappung + aktuelles Fenster. Bei 30 % im neuen Fenster zählt das alte zu 70 %.

Welche Formen hat Retry-After?

Sekunden, z. B. Retry-After: 4, oder ein HTTP-Datum.

Was geht kaputt, wenn zwei Instanzen mit GET und SET zählen?

Beide lesen denselben Stand und lassen beide durch: In der Simulation 6 statt 5 Requests. Atomares INCR oder ein Lua-Skript verhindert das.

Vergleich

Token Bucket vs Leaky Bucket?

Als Meter entscheiden beide gleich. Der Leaky Bucket als Queue puffert und gibt gleichmässig weiter. Der Token Bucket lässt Bursts sofort durch.

Sliding Log vs Sliding Counter?

Der Log speichert jeden Zeitstempel und ist exakt. Der Counter nutzt zwei Zähler mit Gewichtung und ist eine billige Näherung.

Gateway oder Service?

Gateway für einheitliche Limits ohne Code. Service, wenn die Regel Geschäftswissen braucht, z. B. pro Konto und Aktion.

Welche Rate-Limit-Policies hat Azure API Management?

rate-limit (pro Subscription), rate-limit-by-key (pro beliebigem Key), quota und quota-by-key (Volumen über lange Zeit). Dazu Token-Limits für LLM-APIs.

Welchen Status liefert eine APIM-Quota?

403 Forbidden mit Retry-After. Das Rate Limit liefert 429.

Rate Limit vs Quota?

Rate Limit schützt vor Spitzen in kurzen Fenstern. Quota begrenzt das Gesamtvolumen, z. B. pro Monat.

Warum erlaubt ein Token Bucket mehr als Rate × Fenster?

Er begrenzt den Durchschnitt, nicht jedes Fenster. Bursts bis zur Kapazität sind gewollt, z. B. für Partner-APIs.

Produktion

Ist das APIM-Rate-Limit exakt?

Nein. Microsoft sagt, es ist wegen der verteilten Architektur nie ganz genau. Jede Region zählt für sich.

Was soll ein Client bei 429 tun?

Retry-After beachten. Ohne Header: exponentielles Backoff mit Jitter und eine Obergrenze an Versuchen.

Wie testen Sie einen Rate Limiter?

Unit-Tests mit simulierter Uhr. Lasttest mit k6 oder Azure Load Testing. Prüfen: 429-Anteil, Retry-After, Verhalten an der Fenstergrenze.

Szenario: Nach dem Hochskalieren von 2 auf 10 Pods kommt viel mehr Last zur Datenbank. Warum?

Das Limit ist pro Pod im Speicher. Mit 10 Pods ist das echte Limit fünfmal höher. Lösung: zentraler Zähler in Redis oder Limit im Gateway.

Szenario: Ein grosser Kunde meldet ständig 429, obwohl seine Benutzer wenig tun. Woran denken Sie?

Das Limit läuft pro IP, und alle Benutzer sitzen hinter einem Firmen-NAT. Lösung: pro Subscription-Key oder User-ID limitieren.

Szenario: Nach einem kurzen Ausfall kommt eine Lastwelle, und das System fällt erneut. Was tun Sie?

Ein Retry Storm. Lösung: Retry-After senden, Clients mit Backoff und Jitter, Limit am Gateway, eventuell Load Shedding. Mit 429-Metriken prüfen.

Was geht kaputt, wenn 429 ohne Retry-After gesendet wird?

Clients wiederholen sofort: ein Retry Storm, der die Last erhöht. Retry-After plus Backoff mit Jitter im Client verhindern das.

Design

Was passiert, wenn Redis ausfällt?

Der Limiter muss fail-open oder fail-closed sein. Fail-open schützt die Verfügbarkeit, fail-closed das Backend. Oft: fail-open mit lokalem Notfall-Limit.

Welchen Statuscode und welche Header schicken Sie?

429 Too Many Requests (RFC 6585) mit Retry-After (RFC 9110). Optional Restkontingent in X-RateLimit-* oder den RateLimit-Headern des IETF-Entwurfs.

Sind die RateLimit-Header ein Standard?

Nein. Sie sind ein IETF-Entwurf (draft-ietf-httpapi-ratelimit-headers). Er definiert RateLimit-Policy und RateLimit.

Wo setzen Sie Rate Limiting durch?

Edge (WAF) gegen Flut pro IP, Gateway (APIM) für API-Verträge pro Key, Service für Geschäftsregeln. Je früher, desto billiger.

Welchen Key wählen Sie?

Am besten eine stabile Identität: Subscription-Key, Client-ID oder User-ID. IP nur für anonyme Endpunkte, wegen NAT.

Was ist das Rate Limiting Pattern im Azure Architecture Center?

Die eigenen Aufrufe an einen gedrosselten Dienst steuern, z. B. per Queue und fester Verarbeitungsrate. So vermeidet man 429 vom Dienst.

Warum ist der Key wichtiger als der Algorithmus?

Der Key entscheidet über Fairness. Ein Limit pro IP trifft alle Benutzer hinter einem Firmen-NAT gemeinsam. Besser Subscription-Key oder User-ID.

Gerüst

  • Warum? Schützt das Backend vor Überlast, Missbrauch und Noisy Neighbors. Über dem Limit: 429 Too Many Requests mit Retry-After.
  • Wie innen? Key bestimmen (Subscription, User, IP) → Zähler atomar prüfen (Redis INCR oder Lua) → Entscheid. Token Bucket: Rate r, Burst b, zwei Zahlen pro Key.
  • Zahlen Fixed Window: bis 2× Limit an der Fenstergrenze (Simulation: 9 statt 5 in 10 s). Race ohne INCR: 6 statt 5. APIM rate-limit-by-key: renewal-period max. 300 s.
  • Vergleich Token Bucket = Leaky Meter (Bursts ok) vs Leaky Queue (glättet) vs Fixed Window (billig) vs Sliding Log (exakt) vs Sliding Counter (Näherung).
  • Produktion Limit pro Pod wächst mit den Replicas. Firmen-NAT: ein Kunde blockiert alle. 429 ohne Retry-After → Retry-Sturm.
  • Design Der Key ist wichtiger als der Algorithmus. Fail-open oder fail-closed bewusst wählen. Limits in Schichten: Edge, Gateway, Service.

Echte Ausgabe, Python 3 (Simulation). Keine echte Infrastruktur; Zeiten sind simulierte Sekunden.

  1. Fixed Window lässt bei 10.1–10.5 fünf Requests durch, direkt nach dem Fenster davor. So kommen 9 Requests in 10 Sekunden durch, fast das Doppelte. Das ist das Grenzproblem (Boundary Burst).
  2. Sliding Log hält das Limit exakt: nie mehr als 5 in irgendwelchen 10 Sekunden. Es speichert aber jeden Zeitstempel.
  3. Sliding Window Counter trifft hier dasselbe Ergebnis mit nur zwei Zählern. Er ist eine Näherung, nimmt also gleichmässige Verteilung im alten Fenster an.
  4. Token Bucket erlaubt bei 9.0–9.9 weitere Requests, weil Tokens nachgefüllt wurden. Er erlaubt Bursts bis zur Kapazität. Das ist gewollt: Der Durchschnitt ist begrenzt, nicht jedes Fenster.
  5. Leaky Bucket als Meter entscheidet genau wie der Token Bucket. Beide sind mathematisch gleich, nur gespiegelt.
  6. Leaky Bucket als Queue lehnt nicht sofort ab. Er puffert und gibt gleichmässig alle 2 s einen Request weiter. Preis: Wartezeit bis 8.7 s.
  7. Race: Mit GET und SET lesen zwei Instanzen beide 4. Beide lassen durch: 6 statt 5. Mit atomarem INCR stimmt das Limit.

  • Öffentliche API mit Partnern: Token Bucket oder Sliding Counter. Bursts sind normal, der Durchschnitt zählt.
  • Schwaches Legacy-Backend: Leaky Bucket als Queue. Das Backend sieht eine konstante Rate.
  • Login, Passwort-Reset: Sliding Log oder Fixed Window pro Konto. Wenige Requests, Genauigkeit zählt.

In der Produktion

  1. Jede Instanz zählt für sich: 3 Pods mit In-Memory-Limit 100/min lassen 300/min durch. Beim Skalieren wächst das Limit mit. Lösung: zentraler Zähler in Redis oder Limit am Gateway.
  2. Race Conditions: GET und SET getrennt lassen zu viel durch (siehe Beispiel). Lösung: INCR oder Lua-Skript.
  3. Redis wird zum Engpass: Jeder Request kostet einen Redis-Roundtrip. Lösung: lokale Vorab-Zähler, die in Batches synchronisieren. Preis: etwas Ungenauigkeit.
  4. Retry Storm: Alle Clients bekommen 429 und versuchen es sofort wieder. Die Last steigt. Lösung: Retry-After setzen, Clients mit Backoff und Jitter.
  5. Falscher Key: Limit pro IP trifft alle Benutzer hinter einem Firmen-NAT gemeinsam. Lösung: pro Subscription-Key oder User-ID zählen.
  6. Health Checks und interne Aufrufe: Sie verbrauchen Kontingent. Lösung: eigene Keys oder increment-condition in APIM.
  7. Multi-Region: Zwei APIM-Regionen mit je 100/min lassen zusammen 200/min durch. Lösung: Limit pro Region teilen oder bewusst akzeptieren.

Diagnose: Werkzeuge und Metriken

  • Metrik: Anteil der 429-Antworten pro Key und API. Ein Anstieg zeigt Missbrauch oder ein zu tiefes Limit.
  • APIM: Azure Monitor Requests nach GatewayResponseCode filtern. In ApiManagementGatewayLogs (Log Analytics) nach ResponseCode == 429 suchen.
  • Front Door WAF: Logs mit Aktion Block und Regel-Typ RateLimitRule.
  • Redis: redis-cli --latency, INFO stats (instantaneous_ops_per_sec), SLOWLOG GET für langsame Lua-Skripte.
  • Test: curl -i zeigt Status und Retry-After. Lasttests mit k6 oder Azure Load Testing prüfen, ob das Limit greift.
  • Application Insights: Abhängigkeiten mit 429 zeigen, dass wir von einem fremden Dienst gedrosselt werden.

Senior-Punkte

  1. Das Limit gehört so früh wie möglich. Edge für Flut, Gateway für API-Verträge, Service für Geschäftsregeln. Mehrere Schichten ergänzen sich.
  2. Der Key ist wichtiger als der Algorithmus. Falscher Key heisst unfair: Ein NAT oder ein Mandant blockiert alle.
  3. Exaktheit kostet. Ein leicht ungenaues Limit ist meist ok. APIM sagt selbst, dass es nie ganz genau ist.
  4. Fail-open oder fail-closed ist eine bewusste Entscheidung. Sie gehört ins Design-Dokument.
  5. Rate Limiting ersetzt keine Kapazitätsplanung. Es schützt nur vor Spitzen. Dazu kommen Autoscaling, Load Shedding und Circuit Breaker.
  6. Clients sind Teil des Systems. Ein SDK mit Retry-After, Backoff und Jitter verhindert Retry Storms.
