Drill 3: Terminbuchung (Locking, Reminder-Queue)

1. Die Aufgabe

So stellt sie der Interviewer: „Entwerfen Sie eine Terminbuchungs-Plattform für Arztpraxen. 2'000 Praxen, zusammen etwa 500'000 Termine pro Monat. Patienten sehen freie Slots und buchen online. 24 h vorher geht eine Erinnerung per E-Mail oder SMS raus. Ein Slot darf nie doppelt gebucht werden — auch nicht, wenn zwei Patienten in derselben Millisekunde klicken. Storno muss möglich sein."

20 Minuten: Stell die Uhr. Löse die Aufgabe laut an einem leeren Blatt — Rückfragen, Zahlen, Tabellen, der Buchungs-Fluss, ein Diagramm. Dann erst weiterlesen und vergleichen.

2. Schritt 1: Verstehen

Die Rückfragen, die du stellst — mit plausiblen Antworten:

  1. „Woher kommen die Slots — definiert die Praxis sie vorab?" → „Ja, jede Praxis legt ihren Kalender als feste Slots an, z. B. alle 15 min." Gut: dann existiert jeder Slot als Zeile, bevor jemand bucht.
  2. „Wie lange darf ein Slot ‚reserviert' sein, bevor die Buchung bestätigt ist?" → „Buchung ist ein Klick, keine Bezahlung — sofort verbindlich." Das spart einen Reservierungs-Zustand mit Timeout.
  3. „Erinnerung: reicht ‚mindestens einmal', oder ist doppelt schlimm?" → „Doppelt ist unschön, fehlend ist schlimm." Also at-least-once + Dedup.
  4. „Storno bis wann? Was passiert mit der Erinnerung?" → „Storno bis 2 h vorher; danach keine Erinnerung mehr senden."
  5. „Gibt es einen Ansturm-Moment?" → „Montag 7:00, wenn Praxen die neue Woche freischalten." Dann plane ich für die Spitze, nicht den Schnitt.
  6. „PII: welche Patientendaten speichern wir?" → „Name, Telefon, E-Mail, Grund des Besuchs." Gesundheitsdaten ⇒ Verschlüsselung + Zugriffskontrolle sind Muss.

Zahlenschätzung (laut rechnen): 500'000 Buchungen/Monat ≈ 20'000/Arbeitstag ≈ 0,7 Buchungen/s im Schnitt. Spitze Montag 7:00: Faktor 50–100 ⇒ ~50 Buchungen/s, dazu ~10× mehr Lese-Zugriffe auf die Slot-Suche ⇒ ~500 Reads/s. Speicher: Termin-Zeile ~300 Bytes ⇒ 6 Mio Termine/Jahr ≈ 2 GB/Jahr. Fazit laut sagen: „Das ist eine kleine Datenmenge — die Schwierigkeit ist Korrektheit unter Nebenläufigkeit, nicht Skalierung."

3. Anforderungen

Muss:

  • Kein Doppelverkauf eines Slots — unter beliebiger Nebenläufigkeit.
  • Slot-Suche pro Praxis und Tag unter 200 ms.
  • Erinnerung 24 h vorher, mindestens einmal; nach Storno keine Erinnerung.
  • Storno bis 2 h vor Termin; Slot wird wieder frei.
  • PII geschützt: TLS, Verschlüsselung at rest, Zugriff nur eigene Praxis.

Kann:

  • Warteliste, wenn ein Slot frei wird.
  • SMS-Antwort „ABSAGEN" als Storno-Kanal.
  • No-Show-Statistik pro Praxis.
  • Kalender-Export (iCal) für Patienten.

4. DB-Design

CREATE TABLE praxis (
  praxis_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text NOT NULL
);

CREATE TABLE slot (
  slot_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  praxis_id   bigint NOT NULL REFERENCES praxis,
  beginn      timestamptz NOT NULL,
  status      text NOT NULL DEFAULT 'frei'
              CHECK (status IN ('frei','gebucht','gesperrt')),
  version     int NOT NULL DEFAULT 0,
  UNIQUE (praxis_id, beginn)          -- kein doppelter Slot im Kalender
);
-- DER Index der Aufgabe: Slot-Suche "freie Slots dieser Praxis ab heute"
CREATE INDEX idx_slot_suche ON slot (praxis_id, beginn) WHERE status = 'frei';

CREATE TABLE buchung (
  buchung_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id       bigint NOT NULL REFERENCES slot,
  patient_id    bigint NOT NULL,
  idempotenz_key uuid NOT NULL,
  status        text NOT NULL DEFAULT 'aktiv'
                CHECK (status IN ('aktiv','storniert')),
  erstellt_am   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (idempotenz_key)             -- Doppelklick/Retry = gleiche Buchung
);
-- Sicherheitsnetz Nr. 2 gegen Doppelbuchung: hoechstens EINE aktive
-- Buchung pro Slot, als partieller Unique-Index
CREATE UNIQUE INDEX uq_buchung_slot_aktiv
  ON buchung (slot_id) WHERE status = 'aktiv';
  • slot: ein Datensatz pro buchbarem Zeitfenster; der Zustand lebt in status, und das atomare UPDATE darauf ist die erste Verteidigungslinie.
  • buchung: wer hat wann gebucht; der partielle Unique-Index uq_buchung_slot_aktiv ist die zweite Verteidigungslinie — selbst ein Code-Fehler kann keine zwei aktiven Buchungen auf einen Slot schreiben.
  • praxis: Mandant; jede Query filtert auf praxis_id (Mehrmandanten-Trennung).

5. API

  • GET /praxen/{id}/slots?von=2026-12-01&bis=2026-12-07 — freie Slots, nutzt idx_slot_suche.
  • POST /buchungen — Body: slot_id, Patientendaten, Header Idempotency-Key; Antwort 201 oder 409 „Slot schon vergeben".
  • DELETE /buchungen/{id} — Storno; 409, wenn weniger als 2 h bis Termin.
  • GET /patienten/{id}/buchungen — meine Termine.
  • POST /praxen/{id}/slots:generieren — Praxis erzeugt Wochenraster (z. B. Mo–Fr, 8–17 Uhr, 15 min).
  • Intern: Queue-Nachricht ErinnerungFaellig {buchung_id}, geplante Zustellung = Terminbeginn − 24 h.

6. Pseudo-Code an der Tafel

// POST /buchungen  — der kritische Fluss
funktion buche(slotId, patient, idemKey):
  // 0) Retry/Doppelklick? Gleiche Antwort zurueckgeben, nichts neu buchen.
  alt = SELECT * FROM buchung WHERE idempotenz_key = idemKey
  wenn alt existiert: return 201 mit alt

  BEGIN TRANSACTION
    // 1) DER atomare Schritt: pruefen + schreiben in EINEM Statement.
    //    Die DB serialisiert konkurrierende UPDATEs auf dieselbe Zeile.
    n = UPDATE slot SET status = 'gebucht', version = version + 1
        WHERE slot_id = slotId AND status = 'frei'
    wenn n == 0:                     // Fehlerpfad: jemand war schneller
      ROLLBACK
      return 409 "Slot ist bereits vergeben"

    // 2) Buchung schreiben — Unique-Indexe sind das Sicherheitsnetz
    buchung = INSERT INTO buchung (slot_id, patient_id, idempotenz_key)
              VALUES (slotId, patient.id, idemKey)
  COMMIT                             // erst jetzt ist der Slot weg

  // 3) NACH dem Commit: Erinnerung planen (Queue, Zustellzeit = beginn-24h).
  //    Schlaegt das fehl: Buchung bleibt gueltig, Nachholer-Job sendet spaeter.
  queue.sende("ErinnerungFaellig", {buchungId: buchung.id},
              zustellenUm = slot.beginn - 24h)
  return 201

// Reminder-Worker, wenn die Nachricht faellig wird:
funktion sendeErinnerung(buchungId):
  b = SELECT * FROM buchung JOIN slot USING (slot_id) WHERE buchung_id = buchungId
  wenn b.status != 'aktiv': return   // storniert ⇒ still verwerfen
  wenn b.erinnerung_gesendet: return // Dedup: at-least-once abfangen
  sendeMailOderSms(b)
  UPDATE buchung SET erinnerung_gesendet = true WHERE buchung_id = buchungId

7. Architektur

Sprich das Bild so: „FE redet nur mit der API. Die API macht die Buchung in einer Transaktion in PostgreSQL. Erst nach dem Commit plane ich die Erinnerung als Queue-Nachricht mit Zustellzeit Termin minus 24 h. Der Worker prüft beim Senden nochmal den Status in der DB — so erledigt sich Storno von selbst."

8. Der schwierige Teil als Bild

Der Mechanismus in einem Satz: Beide UPDATEs zielen auf dieselbe Zeile; PostgreSQL lässt nur einen Schreiber gleichzeitig an die Zeile. Ben wartet, bis Annas Transaktion committet, prüft dann die WHERE-Bedingung neu — status='frei' stimmt nicht mehr, also 0 Zeilen betroffen, also 409. Kein expliziter Lock-Code nötig.

9. Frontend kurz

  • Komponenten: SlotKalenderComponent (Woche, freie Slots), BuchungDialogComponent, MeineTermineComponent.
  • State: ein BuchungService mit Signals; Slots werden nach jeder Buchung neu geladen — nie clientseitig „frei" raten.
  • Auf 409: Meldung „Slot wurde soeben vergeben" + Kalender sofort aktualisieren.
  • Idempotency-Key: UUID beim Öffnen des Dialogs erzeugen, bei Retry denselben mitsenden.

10. Cloud (Azure)

  • App Service für API + FE: wenige Pods reichen bei 50 req/s Spitze — AKS wäre Overhead ohne Nutzen.
  • Azure Service Bus (nicht Event Hubs): wir brauchen geplante Zustellung pro Nachricht, Dead-Letter-Queue und Einzel-Nachricht-Semantik — das ist Queue-Arbeit, kein Event-Stream.
  • Azure Database for PostgreSQL (Flexible Server, zonenredundant): verwaltete Backups + PITR; Gesundheitsdaten ⇒ Region Schweiz wählen.
  • Azure Functions mit Service-Bus-Trigger als Reminder-Worker: skaliert mit der Queue, kostet bei Leerlauf fast nichts.
  • Blob Storage: hier kaum nötig (keine Dokumente) — laut sagen, dass man es bewusst weglässt.
  • Key Vault für DB- und Provider-Secrets; Monitor/App Insights mit Alarm auf 409-Rate und Queue-Alter.

11. Trade-offs

  • Atomares UPDATE vs pessimistisch (SELECT … FOR UPDATE) vs optimistisch (version-Spalte): gewählt atomares UPDATE, weil Prüfung + Schreiben in einem Statement liegen und die Sperre nur Mikrosekunden hält. Preis: die Logik muss in ein Statement passen; mehrschrittige Abläufe bräuchten doch FOR UPDATE.
  • Unique-Constraint als Netz vs „UPDATE reicht doch": gewählt beides (Defense in depth), weil ein späterer Code-Pfad (Import, Admin-Tool) das UPDATE umgehen könnte. Preis: ein Index mehr, der bei jedem INSERT geprüft wird.
  • Reminder: Cron-Scan vs geplante Queue-Nachricht: gewählt geplante Nachricht, weil kein minütlicher Full-Scan über alle Buchungen läuft und Zustellung + Retry + DLQ die Queue erledigt. Preis: Storno muss beim Senden geprüft werden (Nachricht lässt sich nicht verlässlich zurückziehen) — darum der Status-Check im Worker. Ein täglicher Mini-Cron als Nachholer für verlorene Nachrichten bleibt sinnvoll.
  • Buchung sofort verbindlich vs Reservierung mit Timeout: gewählt sofort, weil keine Bezahlung im Spiel ist. Preis: bei späterem Payment-Feature muss ein Zustand reserviert + Ablauf-Job nachgerüstet werden.
  • Eine DB für alle Praxen vs DB pro Praxis: gewählt eine DB mit praxis_id-Filter, weil 2 GB/Jahr trivial sind und Betrieb × 2'000 unbezahlbar wäre. Preis: ein vergessener Mandanten-Filter ist ein Datenschutz-Vorfall ⇒ Row-Level Security als Netz erwähnen.

12. Selbsttest

Typische Fehler genau bei dieser Aufgabe:

  • Lesen-prüfen-schreiben in zwei Statements („erst SELECT status, dann UPDATE") — genau das ist die Race Condition, die der Interviewer sehen will.
  • Lock im Application-Server (synchronized, Mutex): wirkt nur in einem Pod; ab zwei Pods doppelt gebucht.
  • Erinnerung in der Buchungs-Transaktion senden: Mail-Provider langsam ⇒ Transaktion hält Locks sekundenlang; Provider down ⇒ Buchung schlägt fehl, obwohl nur die Mail klemmt.
  • Mit Kafka/Sharding anfangen: bei 50 req/s wirkt das auswendig gelernt — erst die Zahl nennen, dann klein bauen.
Warum verhindert UPDATE … WHERE status='frei' die Doppelbuchung — Mechanismus, nicht Behauptung?

Ein UPDATE sperrt die Zielzeile bis zum Commit. Der zweite UPDATE wartet auf diese Sperre und wertet danach die WHERE-Bedingung auf dem neuen Zeilenstand aus. status ist jetzt gebucht, also betrifft er 0 Zeilen — der Code sieht n=0 und antwortet 409.

Was geht kaputt, wenn der Server zwischen COMMIT und dem Queue-Send abstürzt?

Buchung existiert, Erinnerungs-Nachricht fehlt — genau der „fehlend ist schlimm"-Fall. Darum läuft ein Nachholer-Job (z. B. stündlich): „Buchungen in 23–25 h ohne geplante Erinnerung" nachplanen. Die saubere Senior-Antwort heisst Outbox-Pattern: Event in derselben Transaktion in eine Outbox-Tabelle schreiben, ein Relay publiziert es.

Warum nicht das Outbox-Pattern von Anfang an?

Es kostet Tabelle, Relay-Prozess und Monitoring. Bei genau einem nachgelagerten Effekt (Erinnerung) deckt der Nachholer-Job das Risiko billiger ab. Ab mehreren Konsumenten (Statistik, Warteliste, Abrechnung) kippt die Rechnung zur Outbox.

Zwei identische Requests mit demselben Idempotency-Key treffen gleichzeitig ein. Was passiert?

Beide finden keinen Alt-Eintrag, beide buchen los. Einer gewinnt das Slot-UPDATE; der zweite scheitert am UPDATE (409) oder — falls er denselben Slot gar nicht mehr erreicht — am UNIQUE (idempotenz_key) beim INSERT. Den Unique-Fehler fängt der Code und liefert die bestehende Buchung als 201 zurück: gleiche Antwort für gleichen Key.

Wie funktioniert Storno, ohne dass die Erinnerung trotzdem rausgeht?

Storno setzt buchung.status='storniert' und slot.status='frei' in einer Transaktion. Die geplante Queue-Nachricht bleibt liegen — aber der Worker prüft beim Fälligwerden den Status in der DB und verwirft still. Die DB ist die Wahrheit, die Nachricht nur ein Wecker.

Der Mail-Provider ist 2 h down. Was passiert mit den Erinnerungen?

Der Worker wirft einen Fehler, die Queue stellt die Nachricht mit Backoff erneut zu (at-least-once). Nach n Fehlversuchen landet sie in der Dead-Letter-Queue mit Alarm. Verspätete Erinnerung ist okay — das sage ich dem Interviewer explizit als bewusste Entscheidung.

Warum 409 und nicht 200 mit Fehlertext im Body?

409 Conflict ist maschinenlesbar: das FE kann gezielt „Slot vergeben" behandeln und den Kalender neu laden, Monitoring kann die 409-Rate als Metrik führen (hohe Rate = Ansturm oder UI zeigt veraltete Slots zu lange).

Zahlen: Montag 7:00 schalten 2'000 Praxen die Woche frei. Hält die DB das aus?

50 Buchungen/s sind ~50 kleine Transaktionen/s — eine einzelne PostgreSQL-Instanz schafft tausende. Die 500 Reads/s auf die Slot-Suche trägt der partielle Index; notfalls eine Read-Replica. Der Engpass wäre eher der Connection-Pool: begrenzen (z. B. 20–50) und Requests kurz halten.

Skalierung ×10: 20'000 Praxen, 5 Mio Termine/Monat. Was änderst du?

Fast nichts am Kern: 500 Buchungen/s Spitze bleiben DB-tauglich, 20 GB/Jahr bleiben klein. Konkret: mehr API-Pods, Read-Replica für die Suche, Partitionierung von slot/buchung nach Monat für Archivierung. Kein Sharding — das sage ich mit der Zahl als Begründung.

Was geht kaputt, wenn zwei Worker dieselbe Erinnerungs-Nachricht doppelt bekommen?

Ohne Schutz: doppelte SMS. Darum das Flag erinnerung_gesendet; streng gemacht per atomarem UPDATE … SET erinnerung_gesendet=true WHERE … AND erinnerung_gesendet=false — nur wer 1 Zeile trifft, darf senden. Rest-Risiko (Crash zwischen Senden und Flag) bleibt at-least-once: akzeptiert, laut Anforderung.

Warum liegt die Doppelbuchungs-Logik in der DB und nicht in Redis (z. B. SETNX)?

Die DB hält ohnehin die Wahrheit über den Slot; ein zweites System für dieselbe Invariante schafft zwei Wahrheiten, die auseinanderlaufen können (Redis sagt belegt, DB-Transaktion rollte zurück). Redis lohnt erst, wenn die DB die Schreiblast nicht mehr trägt — hier ist sie Faktor 100 davon entfernt.

Interviewer: „Die Praxis will einen Slot sperren (Urlaub). Kollidiert das mit Buchungen?

Gleicher Mechanismus: UPDATE slot SET status='gesperrt' WHERE slot_id=? AND status='frei' — 0 Zeilen heisst „schon gebucht", dann muss die Praxis den Termin aktiv absagen (eigener Prozess mit Patienten-Benachrichtigung). Keine Sonderlogik, derselbe atomare Pfad.

Sicherheits-/PII-Punkt: Was ist hier besonders heikel?

Besuchsgrund ist ein Gesundheitsdatum (besondere Kategorie nach DSGVO/DSG). Konkret: TLS, Verschlüsselung at rest, Zugriff pro Praxis (Row-Level Security oder Mandanten-Filter in jeder Query), Besuchsgrund nie in die SMS/Mail schreiben — nur „Sie haben morgen 10:15 einen Termin", Löschkonzept nach Aufbewahrungsfrist.

Wie testest du die Race Condition, bevor der Interviewer fragt?

Integrationstest: 100 parallele Threads buchen denselben Slot gegen eine echte PostgreSQL (Testcontainer). Assertion: genau 1× 201, 99× 409, und SELECT count(*) FROM buchung WHERE slot_id=? AND status='aktiv' ergibt 1. Ein Unit-Test mit gemocktem Repository kann diese Klasse Fehler prinzipiell nicht finden.

Was geht kaputt, wenn die Queue komplett ausfällt?

Buchen funktioniert weiter (Queue-Send ist nach dem Commit und darf fehlschlagen) — nur Erinnerungen verspäten sich. Der Nachholer-Job plant sie nach, sobald die Queue zurück ist. Das ist der Grund, die Queue nicht in den kritischen Pfad zu nehmen: Buchung verkauft, Erinnerung ist Komfort.

Szenario: Support meldet „Patient sagt, er hat gebucht, aber der Slot gehört jemand anderem." Diagnose?

Erst Daten statt Meinung: SELECT * FROM buchung WHERE slot_id=? — gibt es zwei aktive Zeilen (dann wäre der Unique-Index verletzt ⇒ praktisch unmöglich) oder bekam der Patient ein 409 und hat die Fehlermeldung übersehen? Danach Logs zum Idempotency-Key des Patienten. Meist: UI zeigte einen veralteten „frei"-Stand und der 409-Hinweis war zu leise.

Übe den Drill, bis du Abschnitt 2–8 in 20 Minuten frei an der Tafel erzählst — mit dem atomaren UPDATE als Kernsatz.
