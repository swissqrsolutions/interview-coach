Kotlin-Grundlagen und Null Safety

Kern: Kotlin ist eine statisch typisierte Sprache für die JVM. Das Typsystem trennt nullable (String?) und non-null (String) Typen. Der Compiler verlangt vor jedem Zugriff auf einen nullable Wert eine Prüfung.

Antwort-Muster

Frage: Was ist an Kotlin anders als an Java, vor allem bei null?

  1. Mechanismus: String darf nie null sein, String? schon. Der Compiler erzwingt ?., ?: oder eine Prüfung.
  2. Zahl: Klassen und Methoden sind in Kotlin standardmässig final. Java-Typen ohne Annotation sind Platform Types (String!).
  3. Trade-off: Die Null-Sicherheit endet an der Java-Grenze. Und !! wirft bei null eine Exception.
  4. Produktion: Ich annotiere Java-Code mit @Nullable oder nutze JSpecify. Für Spring brauche ich das kotlin-spring-Plugin.

1. Ein nullable Zugriff in 6 Schritten

  1. Typ prüfen: Jeder Typ ist entweder non-null (String) oder nullable (String?). Ein null für String geht nicht durch den Compiler.
  2. Zugriff: x.length mit x: String? ist ein Compiler-Fehler. Der Compiler verlangt Behandlung.
  3. Wahl: Du nutzt x?.length (Safe Call), x ?: 0 (Elvis), x!! (Assertion, wirft bei null) oder eine if-Prüfung.
  4. Smart Cast: Nach if (x != null) behandelt der Compiler x im Block als String. Das geht, wenn er sicher ist, dass sich der Wert nicht ändert.
  5. Bytecode: Der Compiler macht daraus normale Prüfungen auf null. Es gibt keine Wrapper wie Optional.
  6. Java-Grenze: Typen aus Java ohne Annotation sind Platform Types (String!). Der Compiler warnt dort nicht. Ein null kann zur Laufzeit einen NPE auslösen.

Der Operator !! und Platform Types sind die zwei Wege, auf denen ein NullPointerException in Kotlin noch entsteht.

2. Aufbau

  1. val ist eine Variable, die man nur einmal setzt. var ist veränderbar. Man nutzt standardmässig val.
  2. Typinferenz: Der Compiler leitet Typen oft ab. Bei öffentlichen APIs schreibt man sie trotzdem.
  3. Klassen und Methoden sind standardmässig final. Mit open erlaubt man Vererbung.
  4. Properties ersetzen Getter und Setter. Der Compiler erzeugt sie.
  5. when ist ein Ausdruck wie switch, aber mächtiger. Mit sealed Klassen prüft er Vollständigkeit.
  6. Default- und benannte Argumente ersetzen viele Überladungen.

3. Details

  1. Nullable Typen: String? kann null sein, String nie. Das steht im Typ. Der Compiler prüft es überall.
  2. Safe Call ?.: x?.length liefert null, wenn x null ist. Es wirft keinen NPE. Man kann Aufrufe verketten.
  3. Elvis ?:: x ?: default liefert x, wenn es nicht null ist, sonst den Wert rechts. Rechts kann auch return oder throw stehen.
  4. Not-null Assertion !!: Sie wirft einen NPE, wenn der Wert null ist. Sie schaltet die Sicherheit ab. Im Review ist sie ein Warnzeichen.
  5. Safe Cast as?: Ein Cast, der bei falschem Typ null liefert statt ClassCastException zu werfen.
  6. Platform Types: Java-Typen ohne Annotation sehen aus wie String!. Kotlin erlaubt beides, nullable und non-null. Beim Zuweisen an einen non-null Typ kann zur Laufzeit ein NPE kommen.
  7. Nullability-Annotationen: Mit @Nullable und @NotNull (JetBrains), JSpecify oder JSR-305 sieht Kotlin echte Typen statt Platform Types. JSpecify ist die einzige Variante, die standardmässig strikt meldet.
  8. final als Standard: Klassen und Methoden sind final. Frameworks wie Spring brauchen oft offene Klassen für Proxys. Das kotlin-spring-Plugin macht Klassen mit Spring-Annotationen open.
  9. Keine Checked Exceptions: Kotlin hat sie nicht. Der Compiler zwingt nicht zum Fangen.
  10. Properties und Konstruktoren: class User(val name: String) deklariert Feld, Getter und Konstruktor in einer Zeile.
  11. when und sealed: when ist ein Ausdruck. Bei einer sealed Klasse prüft der Compiler, dass alle Fälle da sind.
  12. Scope-Funktionen: let, apply, also, run und with führen Code im Kontext eines Objekts aus. x?.let { ... } läuft nur bei nicht null.

4. Fallen

  • „In Kotlin gibt es keine NullPointerException.“ → Falsch. Es gibt sie noch. Sie kommt von !!, von Platform Types und von falsch initialisierten Properties.
  • „Ein Java-Typ ist in Kotlin automatisch nullable.“ → Falsch. Ohne Annotation ist er ein Platform Type. Kotlin prüft nichts. Mit Annotationen sieht Kotlin den echten Typ.
  • „val heisst, das Objekt ist unveränderlich.“ → Falsch. val heisst nur, die Referenz ändert sich nicht. Ein val list = mutableListOf() kann sich ändern.
  • „Kotlin-Klassen kann man wie Java-Klassen vererben.“ → Falsch. Sie sind final. Man braucht open. Das ist bei Spring-Proxys ein Thema.
  • „x!! ist wie ein Cast und darum sicher.“ → Falsch. Es wirft eine Exception bei null. Es ist eine Behauptung ohne Prüfung.
  • „?: gibt es nur für Standardwerte.“ → Falsch. Rechts darf auch return oder throw stehen. So bricht man früh ab.

5. Selbsttest

Warum?

Warum trennt Kotlin nullable und non-null Typen?

Null-Fehler sind häufig. Das Typsystem erzwingt die Prüfung schon beim Kompilieren. Der Fehler fällt nicht erst zur Laufzeit auf.

Warum sind Kotlin-Klassen final?

Vererbung soll eine bewusste Entscheidung sein. Das passt zum Prinzip, für Vererbung zu planen oder sie zu verbieten.

Warum braucht Spring mit Kotlin ein Plugin?

Spring erzeugt Proxys und braucht dafür offene Klassen. Das kotlin-spring-Plugin macht Klassen mit Spring-Annotationen open.

Wie innen?

Wie wird x?.length kompiliert?

Zu einer Prüfung auf null. Ist x null, ist das Ergebnis null, sonst wird length gelesen. Es gibt kein Optional-Objekt.

Was ist ein Smart Cast?

Nach einer Prüfung wie x != null behandelt der Compiler x als non-null. Das gilt, wenn er sicher ist, dass sich der Wert nicht ändert.

Was ist ein Platform Type?

Ein Java-Typ ohne Null-Annotation. Kotlin kennt seine Nullability nicht und prüft sie nicht. Man schreibt ihn als String!.

Wie funktioniert as??

Es versucht einen Cast. Passt der Typ nicht, liefert es null statt einer Exception.

Zahlen

Welche Kotlin-Version ist aktuell?

Kotlin 2.4.21 vom 8. Oktober 2026 (laut GitHub Release).

Wie viele Wege gibt es, einen nullable Wert zu behandeln?

Vier übliche: Safe Call, Elvis, Assertion !! und eine if-Prüfung mit Smart Cast.

Welche Standardsichtbarkeit hat eine Kotlin-Klasse?

Sie ist öffentlich und final.

Vergleich

Kotlin null safety vs Java Optional?

Optional ist ein Wrapper zur Laufzeit. Kotlin prüft im Typsystem beim Kompilieren, ohne Wrapper.

Kotlin val vs Java final?

Beide verbieten die Neuzuweisung der Variable. Bei Properties erzeugt val nur einen Getter.

Kotlin vs Java bei Checked Exceptions?

Kotlin hat keine. Java zwingt zum Fangen oder Deklarieren.

Kotlin when vs Java switch?

when ist ein Ausdruck und prüft beliebige Bedingungen. Mit sealed Klassen prüft er Vollständigkeit.

Produktion

Wo entsteht noch ein NPE in Kotlin?

Bei !!, bei Platform Types aus Java und bei Properties mit lateinit, die vor dem Setzen gelesen werden.

Wie macht man Java-Code für Kotlin sicherer?

Mit Annotationen @Nullable und @NotNull oder JSpecify. Dann sieht Kotlin echte Typen und meldet Fehler beim Kompilieren.

Szenario: Ein Kotlin-Service wirft NPE aus einer Java-Bibliothek. Was tun Sie?

Ich vermute einen Platform Type. Ich gebe dem Wert den nullable Typ und behandle null. Ich prüfe, ob die Bibliothek Annotationen hat.

Szenario: Spring-Bean in Kotlin lässt sich nicht proxen, ein Fehler zu final. Was tun Sie?

Ich aktiviere das kotlin-spring-Plugin. Es macht Klassen mit Spring-Annotationen open. Alternativ markiere ich die Klasse mit open.

Design

Wie modelliere ich ein optionales Feld?

Als nullable Typ, zum Beispiel val email: String?. Wer es liest, muss null behandeln.

Wann nehme ich val, wann var?

Standard ist val. var nur, wenn der Wert sich wirklich ändert. Das macht Code leichter verständlich.

Wann ist !! erlaubt?

Fast nie. Eine Ausnahme sind Tests oder Stellen, an denen ein Fehler sofort sichtbar sein soll. Sonst nehme ich ?: mit throw und einer klaren Meldung.

Gerüst

  • Warum? Null-Fehler schon beim Kompilieren finden, weniger Boilerplate als Java.
  • Wie innen? T gegen T? im Typsystem. Compiler erzwingt ?. ?: oder Prüfung. Smart Cast.
  • Zahlen Kotlin 2.4.21 (Oktober 2026). Klassen sind final. Vier Wege für null.

Beispiel: Null Safety und final

fun length(s: String?): Int = s?.length ?: 0           // Safe Call + Elvis

fun firstUpper(names: List<String>?): String {
    val first = names?.firstOrNull() ?: throw IllegalArgumentException("keine Namen")
    return first.uppercase()                            // first ist hier non-null
}

val fromJava = javaService.findName()   // Platform Type String!
val safe: String? = javaService.findName()              // bewusst nullable
val risky: String = javaService.findName()              // NPE zur Laufzeit, wenn null

open class Base { open fun hello() = "base" }           // ohne open: Vererbung verboten

Nicht ausgeführt.

  1. s?.length ?: 0 liefert 0, wenn s null ist. Es gibt keinen NPE.
  2. Beim Elvis-Operator steht rechts throw. So endet die Funktion mit einer klaren Meldung, und danach ist first sicher non-null.
  3. fromJava hat einen Platform Type. Der Compiler warnt nicht.
  4. risky: String ist die Falle. Die Prüfung kommt erst zur Laufzeit bei der Zuweisung.
  5. Ohne open ist Base final. Das ist der Standard in Kotlin.

Vergleich

  • Kotlin: T und T?, Smart Cast, final als Standard, keine Checked Exceptions.
  • Java: Alles kann null sein. Optional als Rückgabe. Checked Exceptions.
  • C#: Nullable Reference Types, ähnliche Idee, aber nur als Compiler-Warnungen.
  • TypeScript: strictNullChecks mit T | null. Ähnliche Idee im Typsystem.
  • Java mit Annotationen: @Nullable und JSpecify geben Kotlin echte Typen.

Produktion

  1. NPE aus Java: Platform Types sind unsicher. Lösung: Java-Code annotieren oder Werte als nullable behandeln.
  2. !! im Code: Jedes !! ist eine mögliche Exception. Lösung: ?: mit throw und Meldung, oder Code umbauen.
  3. lateinit nicht gesetzt: Zugriff vor der Initialisierung wirft eine Exception. Lösung: Konstruktor-Injection statt lateinit.
  4. Spring-Proxys: final Klassen lassen sich nicht proxen. Lösung: kotlin-spring Plugin.
  5. JPA-Entities: JPA braucht oft einen leeren Konstruktor und offene Klassen. Lösung: kotlin-jpa Plugin (basiert auf no-arg und all-open).
  6. Daten von aussen: JSON oder Datenbank können null liefern, auch wenn der Typ non-null ist. Lösung: Eingaben an der Grenze validieren.

Diagnose: Werkzeuge und Befehle

  • Compiler-Warnungen zu Platform Types und !! ernst nehmen. Eine Warnung als Fehler im Build ist möglich.
  • detekt und ktlint (Linter): finden !! und andere Muster.
  • IntelliJ Show Kotlin Bytecode und Decompile: zeigen, was der Compiler daraus macht.
  • javap -c auf der .class-Datei: zeigt den Bytecode.
  • Stacktrace des NPE lesen: zeigt die Zeile mit !! oder die Java-Quelle.
  • Unit-Tests mit null-Werten aus Java-Schnittstellen.

Senior-Punkte

  1. Die Null-Sicherheit endet an der Java-Grenze. Dort muss man annotieren oder defensiv sein.
  2. !! ist ein Warnzeichen im Review. Besser ist ?: mit throw und klarer Meldung.
  3. final ist eine Designhilfe, keine Schikane. Für Frameworks gibt es Plugins.
  4. val als Standard macht Code einfacher zu lesen und sicherer bei Threads.
  5. Kotlin ändert die Sprache, nicht die JVM. Laufzeitverhalten und Tools bleiben gleich.
  6. Migration schrittweise: Neue Dateien in Kotlin, alte in Java. Beide laufen im selben Modul.
