Data Classes und Extension Functions

Kern: Eine Data Class erzeugt aus dem primären Konstruktor equals, hashCode, toString, componentN und copy. Eine Extension Function fügt einem Typ von aussen eine Funktion hinzu, ohne ihn zu ändern. Der Compiler macht daraus eine statische Methode.

Antwort-Muster

Frage: Was bringt eine Data Class, und wie funktionieren Extension Functions?

  1. Mechanismus: data class erzeugt Methoden aus den Properties des primären Konstruktors. Eine Extension wird zu einer statischen Methode mit dem Receiver als erstem Parameter.
  2. Zahl: Der primäre Konstruktor braucht mindestens einen Parameter. Alle sind val oder var.
  3. Trade-off: Extensions werden statisch aufgelöst und sind nicht polymorph. Eine Member-Funktion gewinnt immer gegen eine gleiche Extension.
  4. Produktion: Ich nutze val in Data Classes und copy für Änderungen. Bei JPA beachte ich final und leere Konstruktoren.

1. Von data class bis copy in 6 Schritten

  1. Deklaration: data class User(val name: String, val age: Int). Der primäre Konstruktor braucht mindestens einen Parameter, und jeder ist val oder var.
  2. Compiler: Er nutzt nur die Properties im primären Konstruktor. Properties im Klassenkörper bleiben ausserhalb.
  3. Erzeugte Methoden: equals() und hashCode(), toString(), componentN() und copy().
  4. copy: u.copy(age = 31) erzeugt ein neues Objekt. Alle anderen Felder bleiben gleich. Die Kopie ist flach (shallow).
  5. Destructuring: val (name, age) = u ruft component1() und component2() auf.
  6. Bytecode: Das Ergebnis ist eine normale Klasse. Java sieht Getter (und Setter bei var) und kann alles nutzen.

Ein record in Java ist ähnlich. Eine Kotlin Data Class darf aber auch var haben und hat copy und componentN.

2. Aufbau

  1. Eine Extension Function hat einen Receiver-Typ vor dem Funktionsnamen. Im Körper heisst das Objekt this.
  2. Der Compiler erzeugt eine statische Methode. Funktionen in app.kt landen in der Java-Klasse AppKt.
  3. Der Aufruf "ab".twice() wird zu einem statischen Aufruf. Es gibt keine virtuelle Methode.
  4. Eine Extension Property ist möglich. Sie darf aber kein Backing Field haben.
  5. Ein nullable Receiver ist möglich: fun String?.orEmpty2(). Dann darf man auf null aufrufen.
  6. Extensions findet man über Imports und das Package. Sie sind nur sichtbar, wenn importiert.

3. Details

  1. Erzeugte Methoden: Nur Properties aus dem primären Konstruktor zählen für equals, hashCode, toString, componentN und copy. Properties im Körper werden ignoriert.
  2. Regeln: Der primäre Konstruktor braucht mindestens einen Parameter. Alle Parameter sind val oder var. Data Classes können nicht abstract, open, sealed oder inner sein.
  3. Eigene Implementierung: Steht equals, hashCode oder toString selbst im Körper, erzeugt der Compiler sie nicht. componentN und copy darf man nicht selbst schreiben.
  4. copy: Mit benannten Argumenten ändert man einzelne Felder. Die Kopie ist flach. Ein veränderbares Objekt darin wird geteilt.
  5. val oder var: Mit val ist die Data Class unveränderlich. Das ist die Empfehlung. Mit var kann ein Objekt in einer HashMap seinen Hash ändern.
  6. Statische Auflösung: Eine Extension wird nach dem deklarierten Typ gewählt, nicht nach dem Laufzeittyp. Sie überschreibt nichts. Darum ist sie nicht polymorph.
  7. Member gewinnt: Hat die Klasse eine Member-Funktion mit gleichem Namen und gleicher Signatur, wird immer diese aufgerufen. Eine Extension mit anderer Signatur kann überladen.
  8. Keine Änderung der Klasse: Eine Extension fügt dem Typ kein Member hinzu. Sie sieht nur öffentliche Teile. Private Felder sind tabu.
  9. Extension Properties: Sie haben keinen Speicher (kein Backing Field). Initialisierer sind verboten. Nur ein Getter oder Setter ist möglich.
  10. Aus Java: Eine Extension ist eine statische Methode. Java ruft sie als AppKt.twice(s) auf. @file:JvmName ändert den Klassennamen.
  11. Typische Nutzung: Hilfsfunktionen für Konvertierung und DSLs. Die Standardbibliothek besteht stark aus Extensions, zum Beispiel für Collections.
  12. Vergleich mit Lombok: Lombok erzeugt Code per Annotation für @Data. Kotlin macht es im Compiler als Spracheigenschaft. Es braucht kein Plugin und keine Annotation.

4. Fallen

  • „Eine Extension kann eine Methode der Klasse überschreiben.“ → Falsch. Sie kann es nicht. Bei gleicher Signatur gewinnt immer die Member-Funktion.
  • „Extensions sind polymorph wie normale Methoden.“ → Falsch. Sie werden statisch nach dem deklarierten Typ gewählt. Ein Subtyp-Objekt in einer Variable vom Basistyp nutzt die Extension des Basistyps.
  • „equals einer Data Class vergleicht alle Properties der Klasse.“ → Falsch. Nur die im primären Konstruktor. Properties im Körper bleiben aussen vor.
  • „copy() kopiert tief.“ → Falsch. Die Kopie ist flach. Verschachtelte veränderbare Objekte sind danach geteilt.
  • „Eine Data Class kann open sein.“ → Falsch. Sie kann nicht abstract, open, sealed oder inner sein.
  • „Eine Extension kann private Felder der Klasse lesen.“ → Falsch. Sie sieht nur die öffentliche Schnittstelle.

5. Selbsttest

Warum?

Warum gibt es Data Classes?

Datenklassen brauchen immer equals, hashCode, toString und Kopie. Der Compiler erzeugt sie. Das spart Boilerplate und vermeidet Fehler.

Warum gibt es Extension Functions?

Man kann Typen erweitern, die man nicht ändern kann, zum Beispiel String oder Java-Klassen. Der Aufruf liest sich wie eine Methode.

Warum sollen Data Classes val nutzen?

Unveränderliche Objekte sind sicher als Map-Schlüssel und über Threads. Änderungen macht man mit copy.

Wie innen?

Was erzeugt der Compiler für eine Data Class?

equals, hashCode, toString, componentN und copy. Alles nur aus den Properties des primären Konstruktors.

Wie wird eine Extension Function kompiliert?

Zu einer statischen Methode. Der Receiver ist der erste Parameter. Sie liegt in der Klasse der Datei, zum Beispiel AppKt.

Wie löst Kotlin Extension und Member auf?

Bei gleicher Signatur gewinnt die Member-Funktion. Bei Extensions entscheidet der deklarierte Typ zur Compile-Zeit.

Was macht Destructuring?

val (a, b) = obj ruft component1() und component2() auf. Data Classes erzeugen sie.

Zahlen

Wie viele Parameter braucht der primäre Konstruktor einer Data Class?

Mindestens einen.

Wie viele Methoden erzeugt eine Data Class?

Fünf Gruppen: equals, hashCode, toString, componentN und copy.

Welche Modifier sind bei Data Classes verboten?

abstract, open, sealed und inner.

Vergleich

Data Class vs Java Record?

Beide erzeugen Gleichheit und toString. Java Records sind immer unveränderlich. Kotlin hat zusätzlich copy und componentN, und erlaubt var.

Data Class vs Lombok @Data?

Lombok nutzt einen Annotation Processor. Kotlin macht es im Compiler. Lombok @Data erzeugt auch Setter.

Extension Function vs Util-Klasse in Java?

Beide sind statisch. Die Extension liest sich beim Aufruf wie eine Methode. Sie ist auch im Code sichtbar und findbar mit IDE.

Extension vs Vererbung?

Extension ändert keine Klasse und ist nicht polymorph. Vererbung braucht den Zugriff auf die Klasse und ist polymorph.

Produktion

Was geht bei Data Classes als JPA-Entity schief?

Entities brauchen oft einen leeren Konstruktor und offene Klassen. equals über alle Felder passt nicht zu Entity-Identität. Besser eine normale Klasse mit kotlin-jpa Plugin.

Was geht mit var in Data Classes als Map-Schlüssel schief?

Ändert sich ein Feld, ändert sich der Hash. Die Map findet den Eintrag nicht mehr.

Szenario: Eine Extension verhält sich nach einem Update der Bibliothek anders. Warum?

Die Bibliothek hat eine Member-Funktion mit gleicher Signatur bekommen. Member gewinnt gegen die Extension. Ich benenne die Extension um oder nutze die neue Member-Funktion.

Szenario: Ein Objekt in einer Data Class ändert sich nach copy auch im Original. Warum?

Die Kopie ist flach. Das innere Objekt ist geteilt. Ich nehme unveränderliche innere Typen oder kopiere sie mit.

Design

Wann nutze ich eine Data Class?

Für Daten ohne viel Verhalten: DTOs, Nachrichten, Werte-Objekte. Für Objekte mit Identität und Lebenszyklus nehme ich eine normale Klasse.

Wann nutze ich eine Extension?

Für Hilfsfunktionen, die zu einem Typ passen, aber nicht in ihn gehören. Zum Beispiel Konvertierungen. Sie bleiben klein und im Package nahe am Gebrauch.

Wie nutze ich Extensions in einem grossen Projekt?

Mit klarer Benennung, in eigenen Dateien und nur importiert, wo nötig. Zu viele globale Extensions machen Code schwer lesbar.

Mehr

Gerüst

  • Warum? Weniger Boilerplate für Datenobjekte. Erweitern von Typen, die man nicht besitzt.
  • Wie innen? Compiler erzeugt Methoden aus dem primären Konstruktor. Extension ist eine statische Methode.
  • Zahlen Mindestens ein Parameter. Fünf Gruppen erzeugter Methoden. Kein abstract, open, sealed, inner.
  • Vergleich Record, Lombok, Util-Klasse, Vererbung.
  • Produktion JPA-Entities, var als Map-Schlüssel, flache Kopie, Member gewinnt.
  • Design val, copy, kleine Extensions in eigenen Dateien.

Beispiel: Data Class und Extension

data class User(val name: String, val age: Int) {
    var note: String = ""          // im Körper: zählt nicht für equals/copy
}

fun String.twice(): String = this + this          // Extension Function
val String.lastChar: Char get() = this[length - 1] // Extension Property

fun main() {
    val a = User("Ana", 30)
    val b = User("Ana", 30).also { it.note = "x" }
    println(a == b)                    // true: note zählt nicht
    println(a.copy(age = 31))          // User(name=Ana, age=31)
    val (n, ag) = a                    // component1(), component2()
    println("ab".twice())              // abab
}

Nicht ausgeführt.

  1. note steht im Körper. Darum ist a == b wahr, obwohl note verschieden ist.
  2. copy(age = 31) erzeugt ein neues User. toString zeigt nur die Properties des primären Konstruktors.
  3. val (n, ag) = a ruft component1() und component2() auf.
  4. "ab".twice() wird zu einem statischen Aufruf in der Datei-Klasse.

Vergleich

  • Data Class (Kotlin): Wertobjekt mit copy, componentN, auch mit var.
  • Record (Java): Wertobjekt, immer unveränderlich, keine copy-Methode.
  • Lombok @Data: Code per Annotation, auch Setter. Ein Plugin ist nötig.
  • Extension Function: Statische Methode mit Receiver. Nicht polymorph.
  • Util-Klasse (Java): Auch statisch, aber Aufruf als Util.twice(s).
  • Default-Methoden (Java): Erweitern eigene Interfaces. Fremde Typen kann man damit nicht erweitern.

Produktion

  1. Data Class als Entity: JPA verlangt Proxys und leere Konstruktoren. Lösung: normale Klasse mit kotlin-jpa und eigener Gleichheit.
  2. Veränderbare Keys: var in Data Classes als Map-Schlüssel verliert Einträge. Lösung: val.
  3. Flache Kopie: copy teilt innere Objekte. Lösung: unveränderliche innere Typen.
  4. Extension verdeckt: Eine neue Member-Funktion der Bibliothek überstimmt die Extension still. Lösung: Tests und Umbenennen.
  5. Zu viele Extensions: Globale Extensions auf String und Any machen Code unklar. Lösung: sparsam und lokal.
  6. Personenbezogene Daten im toString: Die erzeugte toString zeigt alle Felder und landet im Log. Lösung: Feld nicht in den Konstruktor nehmen oder toString selbst schreiben.

Diagnose: Werkzeuge und Befehle

  • IntelliJ Show Kotlin Bytecode und Decompile: zeigen die erzeugten Methoden.
  • javap -p -c User.class: listet equals, hashCode, copy und component1.
  • Debugger: zeigt toString der Data Class mit allen Feldern.
  • Unit-Test für Gleichheit und Hash bei Schlüsseln.
  • Im Log nach unerwarteten Daten in toString-Ausgaben suchen.
  • IDE-Hinweis bei überschatteten Extensions (Warnung "Extension is shadowed by a member").

Senior-Punkte

  1. Data Classes sind für Daten, nicht für Verhalten und Identität. Entities sind ein Sonderfall.
  2. val und copy als Standard. Das macht Code sicherer bei Threads und in Maps.
  3. toString und Logs: Sensible Felder gehören nicht in generierte toString-Methoden.
  4. Extensions sind statisch. Sie ersetzen weder Polymorphie noch Vererbung.
  5. Member gewinnt. Ein Bibliotheks-Update kann Extensions verdecken. Das gehört in die Tests.
  6. Sparsam erweitern. Zu viele Extensions auf Standardtypen sind schwer auffindbar.
