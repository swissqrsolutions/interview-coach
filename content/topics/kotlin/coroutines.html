Coroutines

Kern: Eine Coroutine ist ein leichter, unterbrechbarer Ablauf. Eine suspend-Funktion gibt den Thread frei, statt ihn zu blockieren. Structured Concurrency bindet jede Coroutine an einen Scope, damit Abbruch und Fehler sauber weitergegeben werden.

Antwort-Muster

Frage: Wie funktionieren Kotlin Coroutines, und wie unterscheiden sie sich von Threads?

  1. Mechanismus: Der Compiler macht aus suspend-Funktionen eine State Machine mit Continuation. Ein Dispatcher setzt sie auf Threads fort.
  2. Zahl: Dispatchers.Default nutzt so viele Threads wie CPU-Kerne, mindestens zwei. Dispatchers.IO nutzt bis 64 Threads oder die Zahl der Kerne, je nachdem, was grösser ist.
  3. Trade-off: Coroutines sind billig, aber Abbruch ist nur kooperativ. Blockierender Code in Default hält Threads fest.
  4. Produktion: Ich nutze Scopes mit Lebenszyklus, withContext(Dispatchers.IO) für blockierende Aufrufe und fange CancellationException nie still ab.

1. Ein launch in 6 Schritten

  1. Scope: Jede Coroutine läuft in einem CoroutineScope. Er enthält einen Job und einen Kontext mit Dispatcher.
  2. launch: scope.launch { ... } erzeugt einen Kind-Job und gibt die Coroutine dem Dispatcher.
  3. Dispatcher: Er wählt einen Thread aus seinem Pool und startet die Coroutine dort.
  4. suspend: Bei einem Aufruf wie delay(100) speichert der Compiler-Code den Zustand in einer Continuation. Die Funktion kehrt zurück. Der Thread ist frei.
  5. resume: Ist die Zeit um oder das I/O fertig, ruft die Continuation resume auf. Der Dispatcher macht an der Stelle weiter.
  6. Ende: Ist der Code fertig, ist das Kind fertig. Der Eltern-Job wartet auf alle Kinder. Ein Fehler eines Kindes bricht Eltern und Geschwister ab.

Das Prinzip heisst Structured Concurrency. Eine neue Coroutine startet nur in einem Scope, der ihre Lebensdauer begrenzt.

2. Aufbau

  1. Der CoroutineScope hält den Kontext und begrenzt die Lebensdauer. coroutineScope {} und withContext {} erzeugen Scopes.
  2. Der Job ist der Griff auf eine Coroutine. Man kann ihn abbrechen oder auf ihn warten.
  3. Der Dispatcher bestimmt den Thread. Default ist für CPU, IO für blockierende Aufrufe, Main für UI.
  4. Die Continuation ist der gespeicherte Rest einer suspend-Funktion.
  5. Die Builder sind launch (liefert Job), async (liefert Deferred) und runBlocking.
  6. Flow ist ein kalter Strom von Werten. Er läuft erst beim Einsammeln.

3. Details

  1. suspend-Funktion: Der Compiler fügt einen Continuation-Parameter hinzu und baut eine State Machine (Continuation Passing Style). Jeder Suspension Point ist ein Zustand. Es braucht keinen eigenen Thread.
  2. Structured Concurrency: Neue Coroutines starten nur in einem CoroutineScope. Der Scope ist erst fertig, wenn alle Kinder fertig sind. So gehen keine Coroutines verloren.
  3. launch und async: launch meldet Fehler als unbehandelte Ausnahme. async gibt ein Deferred zurück. Der Fehler kommt erst bei await. Bei einem Kind-Job geht der Fehler an den Eltern-Job.
  4. Dispatchers.Default: Er nutzt einen gemeinsamen Pool. Die Zahl der Threads ist die Zahl der CPU-Kerne, mindestens zwei. Er ist für CPU-Arbeit.
  5. Dispatchers.IO: Er ist für blockierende Aufrufe. Er nutzt bis zu 64 Threads oder die Zahl der Kerne, was grösser ist.
  6. Unconfined: Die Coroutine startet im aufrufenden Thread, bis zum ersten Suspension Point. Danach läuft sie dort weiter, wo die Funktion sie fortsetzt. Nur für Sonderfälle.
  7. Abbruch ist kooperativ: Ein Abbruch wirft CancellationException an der nächsten Suspension. Reiner CPU-Code muss isActive, ensureActive() oder yield() prüfen.
  8. CancellationException: Sie darf man nicht still schlucken. Ein catch (e: Exception) fängt sie auch und bricht die Weitergabe des Abbruchs. Man wirft sie erneut.
  9. Fehler und Geschwister: Fällt ein Kind aus, bricht es den Eltern-Job und die Geschwister ab. Mit supervisorScope oder SupervisorJob geben Kinder Fehler nicht an den Eltern weiter.
  10. CoroutineExceptionHandler: Er fängt nur unbehandelte Fehler einer Wurzel-Coroutine. Man kann damit nichts mehr retten. Bei Kindern hat er keine Wirkung.
  11. Flow: Ein kalter Flow läuft nicht, bevor jemand ihn einsammelt. Jeder Sammler startet ihn neu. Werte kommen nacheinander.
  12. runBlocking und GlobalScope: runBlocking blockiert den Thread, bis alles fertig ist, und gehört in main und Tests. GlobalScope ist eine heikle API, weil nichts die Lebensdauer begrenzt.

4. Fallen

  • „Eine Coroutine ist ein Thread.“ → Falsch. Sie ist ein unterbrechbarer Ablauf. Viele Coroutines teilen wenige Threads. Bei suspend gibt sie den Thread frei.
  • „Abbruch beendet jede Coroutine sofort.“ → Falsch. Abbruch ist kooperativ. Reine Rechenschleifen ohne Prüfung laufen weiter.
  • „catch (e: Exception) ist harmlos in Coroutines.“ → Falsch. Es fängt CancellationException. Der Abbruch geht verloren und die Coroutine läuft weiter. Man wirft sie erneut.
  • „async meldet Fehler sofort.“ → Falsch. Der Fehler wartet im Deferred bis await. Bei einem Kind-Job bricht er aber auch den Eltern-Job ab.
  • „Blockierende Aufrufe in Dispatchers.Default sind harmlos.“ → Falsch. Sie halten Threads des kleinen Pools fest. Blockierendes gehört in withContext(Dispatchers.IO).
  • „CoroutineExceptionHandler fängt alle Fehler.“ → Falsch. Nur unbehandelte Fehler von Wurzel-Coroutines. Bei Kindern und bei async wirkt er nicht.

5. Selbsttest

Warum?

Warum nutzt man Coroutines statt Threads?

Sie sind leicht. Man kann sehr viele starten. Beim Warten gibt eine Coroutine den Thread frei. Der Code liest sich wie sequentieller Code.

Warum gibt es Structured Concurrency?

Jede Coroutine hat einen Eltern-Scope. So wartet der Scope auf alle Kinder, Fehler gehen nach oben und Abbruch geht nach unten. Nichts läuft unbeachtet weiter.

Warum gibt es mehrere Dispatchers?

CPU-Arbeit und blockierende I/O brauchen verschiedene Pools. Sonst verstopft blockierender Code die Rechen-Threads.

Wie innen?

Was macht der Compiler aus einer suspend-Funktion?

Er fügt einen Continuation-Parameter hinzu und baut eine State Machine. Jeder Suspension Point ist ein Zustand, der Rest der Funktion liegt in der Continuation.

Was passiert bei delay()?

Die Coroutine speichert ihren Zustand und gibt den Thread frei. Nach der Zeit setzt der Dispatcher sie fort.

Wie funktioniert Abbruch?

Der Job wird auf abgebrochen gesetzt. An der nächsten Suspension wirft die Coroutine CancellationException. Der Code muss kooperieren.

Wie breitet sich ein Fehler aus?

Ein Kind meldet ihn dem Eltern-Job. Der bricht die anderen Kinder ab und meldet nach oben. In einem Supervisor-Scope bricht nur das betroffene Kind ab.

Zahlen

Wie viele Threads hat Dispatchers.Default?

So viele wie CPU-Kerne, mindestens zwei.

Wie viele Threads hat Dispatchers.IO?

Bis zu 64 oder die Zahl der Kerne, was grösser ist.

Welche Version von kotlinx.coroutines ist aktuell?

1.11.0 vom 8. Mai 2026 (laut GitHub Release).

Vergleich

Coroutines vs Java Threads?

Ein Thread ist ein Betriebssystem-Objekt mit eigenem Stack. Coroutines sind Objekte und teilen sich wenige Threads. Sie sind billiger zu erzeugen.

Coroutines vs Java Virtual Threads?

Beide machen Nebenläufigkeit billig. Virtual Threads blockieren billig und brauchen keine neue Syntax. Coroutines haben suspend, Scopes und Flow.

Coroutines vs CompletableFuture?

CompletableFuture braucht Ketten. Coroutines schreibt man sequentiell. Coroutines haben dazu Scopes mit Abbruch.

Flow vs Reactor Flux?

Beide sind Ströme von Werten. Flow ist kalt und baut auf suspend auf. Reactor hat viele Operatoren und Gegendruck als Teil des Protokolls.

Produktion

Was ist die häufigste Falle mit Coroutines?

Blockierende Aufrufe auf Default, verschluckte CancellationException und Coroutines ohne Scope mit GlobalScope.

Wie testet man Coroutines?

Mit einer Test-Bibliothek wie runTest aus kotlinx-coroutines-test. Sie steuert die Zeit virtuell.

Szenario: Ein Service reagiert nach Last kaum noch, die CPU ist niedrig. Was prüfen Sie?

Ich suche blockierende Aufrufe auf Dispatchers.Default. Der Pool hat nur so viele Threads wie Kerne. Ich lege sie in withContext(Dispatchers.IO) oder nutze eine nicht blockierende API.

Szenario: Beim Abbruch eines Requests laufen Datenbankabfragen weiter. Warum?

Der Code prüft den Abbruch nicht oder blockiert in einer API ohne Abbruch-Support. Ich nutze suspend-fähige Clients und prüfe ensureActive() in langen Schleifen.

Design

Wie führe ich zwei Aufrufe parallel aus?

In coroutineScope { } zwei async starten und beide mit await einsammeln. Fällt einer aus, bricht der andere ab.

Wann nehme ich supervisorScope?

Wenn Kinder unabhängig sein sollen. Ein Fehler eines Kindes soll die anderen nicht abbrechen.

Wie begrenze ich die Zahl paralleler Aufrufe?

Mit einem Semaphore oder limitedParallelism am Dispatcher. Ohne Grenze überlastet man den Nachbardienst.

Mehr

Gerüst

  • Warum? Billige Nebenläufigkeit mit sequentiellem Code. Scopes verhindern Verluste.
  • Wie innen? State Machine mit Continuation. Dispatcher setzt fort. Abbruch kooperativ.
  • Zahlen Default: Kerne, mindestens zwei. IO: 64 oder Kerne. kotlinx.coroutines 1.11.0.
  • Vergleich Gegen Threads, Virtual Threads, CompletableFuture, Flux.
  • Produktion Blockieren auf Default, CancellationException schlucken, GlobalScope.
  • Design coroutineScope und async für Parallelität, supervisorScope für unabhängige Kinder.

Beispiel: Parallel mit Scope und Abbruch

suspend fun loadUser(id: Int): User = withContext(Dispatchers.IO) { db.find(id) }   // blockierend

suspend fun profile(id: Int): Profile = coroutineScope {
    val user  = async { loadUser(id) }
    val posts = async { api.posts(id) }            // suspend-fähiger Client
    Profile(user.await(), posts.await())           // Fehler in einem bricht den anderen ab
}

suspend fun worker() {
    try {
        while (true) { work(); delay(1_000) }       // delay prüft den Abbruch
    } catch (e: CancellationException) {
        cleanup(); throw e                          // erneut werfen
    }
}

val result = withTimeoutOrNull(500) { profile(1) } // null nach 500 ms

Nicht ausgeführt.

  1. withContext(Dispatchers.IO) legt den blockierenden Datenbank-Aufruf auf den IO-Pool.
  2. coroutineScope startet zwei async. Beide laufen parallel. Fällt einer aus, bricht der andere ab.
  3. delay ist ein Suspension Point. Dort prüft die Coroutine den Abbruch.
  4. throw e gibt CancellationException weiter. Sonst läuft die Coroutine nach dem Abbruch weiter.
  5. withTimeoutOrNull(500) liefert null, wenn der Block länger als 500 ms braucht.

Vergleich

  • Coroutines: leicht, suspend, Scopes, kooperativer Abbruch, Flow.
  • Java Threads: schwer, blockierend, kein eingebauter Scope.
  • Java Virtual Threads: billig, blockierende Syntax, kein Scope-Modell in der Sprache.
  • CompletableFuture: Ketten, kein Strukturmodell, Abbruch schwach.
  • Reactor und RxJava: Ströme mit vielen Operatoren und Gegendruck.
  • Kotlin und Spring: Spring unterstützt suspend-Controller und Flow direkt.

Produktion

  1. Blockieren auf Default: Wenige Threads sind blockiert und alles stockt. Lösung: withContext(Dispatchers.IO) oder suspend-fähige APIs.
  2. Verschluckter Abbruch: catch (e: Exception) fängt CancellationException. Lösung: erneut werfen oder gezielt fangen.
  3. Coroutine-Leck: GlobalScope oder ein Scope ohne Ende. Lösung: Scope an den Lebenszyklus binden und abbrechen.
  4. Fehler wird still: launch in einem Scope ohne Handler. Lösung: Fehler im Code fangen und loggen, Supervisor bewusst wählen.
  5. Zu viele parallele Aufrufe: Tausende async gleichzeitig überlasten ein Backend. Lösung: Semaphore oder limitedParallelism.
  6. Gemeinsamer Zustand: Mehrere Coroutines ändern eine Variable. Lösung: Mutex, Atomics oder Zustand in einer Coroutine halten.

Diagnose: Werkzeuge und Befehle

  • kotlinx-coroutines-debug und der Coroutine Dump der IDE (IntelliJ): zeigen laufende und wartende Coroutines.
  • JVM-Thread-Dump (jcmd <pid> Thread.print): zeigt Threads von DefaultDispatcher-worker.
  • Die Option -Dkotlinx.coroutines.debug: macht Coroutine-Namen im Thread-Namen sichtbar.
  • Profiler (async-profiler, JFR): zeigt, ob Threads blockiert sind.
  • runTest mit virtueller Zeit: testet Zeitverhalten schnell.
  • Logging mit Coroutine-Name im Kontext: hilft beim Verfolgen von Abläufen.

Senior-Punkte

  1. Scope-Lebensdauer ist das Kernthema. Wer startet, wer bricht ab, wer wartet.
  2. Abbruch muss unterstützt werden. Blockierende Bibliotheken ohne Abbruch brechen das Modell.
  3. Dispatcher bewusst wählen. Default für Rechnen, IO für Blockierendes, Main für UI.
  4. Fehler-Strategie festlegen. Strikt (ein Fehler bricht alle) oder Supervisor (unabhängig).
  5. Parallelität begrenzen. Coroutines sind billig, die Backends nicht.
  6. Gegenüber Java 21: Virtual Threads lösen viele Fälle mit normalem Code. Coroutines bleiben stark bei Scopes, Flow und Multiplattform.
