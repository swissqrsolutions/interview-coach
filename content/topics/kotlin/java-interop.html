Interop mit Java

Kern: Kotlin und Java laufen im selben Modul und rufen sich gegenseitig auf, weil beide zu JVM-Bytecode kompilieren. Aus Kotlin sieht Java-Code wie Kotlin aus, aber ohne Null-Information (Platform Types). Aus Java sieht Kotlin-Code wie Java aus, mit Annotationen wie @JvmStatic zur Feinsteuerung.

Antwort-Muster

Frage: Wie arbeiten Kotlin und Java in einem Projekt zusammen, und wo sind die Stolpersteine?

  1. Mechanismus: Beide werden zu .class-Dateien. Kotlin-Properties werden zu Gettern, Top-Level-Funktionen zu statischen Methoden in DateinameKt.
  2. Zahl: Ohne Annotation sind Java-Typen Platform Types (String!). Klassen sind in Kotlin final.
  3. Trade-off: Die Annotationen @JvmStatic, @JvmField, @JvmOverloads machen die Java-Sicht schöner, aber auch mehr Code.
  4. Produktion: Ich annotiere Java mit Nullability, nutze kotlin-spring und kotlin-jpa und prüfe die Java-Sicht der API.

1. Aufruf über die Grenze in 6 Schritten

  1. Kotlin-Code: Du schreibst app.kt im Package org.example.
  2. Compiler: Er erzeugt .class-Dateien. Die JVM kennt keinen Unterschied zu Java.
  3. Namen: Funktionen und Properties einer Datei, auch Extensions, werden zu statischen Methoden der Klasse org.example.AppKt. @JvmName ändert den Namen.
  4. Java ruft: AppKt.getTime() ist ein normaler statischer Aufruf. Properties erscheinen als Getter und Setter.
  5. Typen: Kotlin List wird auf java.util.List abgebildet. Eine Java-Methode mit void hat in Kotlin den Rückgabetyp Unit.
  6. Aus Kotlin: Ein Java-Typ ohne Annotation wird zum Platform Type. Kotlin prüft Null dort nicht.

Der Weg Kotlin nach Java und Java nach Kotlin ist ein Aufruf auf Bytecode-Ebene. Es gibt keine Brücke und keinen Laufzeit-Overhead.

2. Aufbau

  1. Platform Types entstehen für Java-Typen ohne Null-Annotation. Sie werden String! geschrieben.
  2. Nullability-Annotationen wie @Nullable (JetBrains), JSpecify und JSR-305 machen daraus echte Typen.
  3. Datei-Klassen: Top-Level-Code einer Datei liegt in der Klasse DateinameKt.
  4. Annotationen für Java-Sicht: @JvmStatic, @JvmField, @JvmOverloads, @JvmName, @Throws.
  5. Mapped Types: Kotlin-Typen wie List sind auf Java-Typen abgebildet.
  6. Compiler-Plugins: kotlin-spring (open) und kotlin-jpa (no-arg) helfen Frameworks.

3. Details

  1. Platform Types: Ein Java-Typ ohne Annotation kann null sein oder nicht. Kotlin lässt beides zu. Bei Zuweisung an einen non-null Typ kann zur Laufzeit ein NPE auftreten.
  2. Annotationen für Null: Kotlin liest @Nullable und @NotNull von JetBrains, JSpecify und JSR-305. JSpecify ist die einzige Variante, die standardmässig strikt meldet.
  3. Getter und Setter: Java-Getter und Setter erscheinen in Kotlin als Properties. Ein Kotlin-Property erscheint in Java als Getter und Setter.
  4. Top-Level-Funktionen: Sie werden zu statischen Methoden in DateinameKt. Mit @file:JvmName("Utils") ändert man den Klassennamen.
  5. Companion Object: Seine Funktionen sind aus Java nur über Klasse.Companion.foo() erreichbar. @JvmStatic erzeugt zusätzlich eine echte statische Methode.
  6. @JvmField: Das Property wird in Java ein öffentliches Feld statt Getter und Setter. In einem Companion wird es ein statisches Feld.
  7. @JvmOverloads: Kotlin hat Default-Argumente. Java kennt sie nicht. Die Annotation erzeugt Überladungen für Java.
  8. Checked Exceptions: Kotlin hat keine. Wirft eine Kotlin-Funktion eine IOException, kann Java sie nicht fangen. Die Java-Seite meldet einen Fehler. @Throws schreibt die Exception in die Signatur.
  9. Mapped Types und Collections: Kotlin hat List (nur lesen) und MutableList. Java sieht beide als java.util.List. Java-Collections erscheinen als (Mutable)List!.
  10. final als Standard: Kotlin-Klassen sind final. Spring-Proxys brauchen offene Klassen. Das kotlin-spring-Plugin öffnet Klassen mit Spring-Annotationen.
  11. JPA: JPA braucht einen leeren Konstruktor. Das no-arg-Plugin erzeugt ihn. kotlin-jpa stellt no-arg und all-open für JPA-Annotationen ein.
  12. Records und Coroutines: @JvmRecord erzeugt eine Java-Record-Klasse. Eine suspend-Funktion bekommt aus Java-Sicht einen zusätzlichen Continuation-Parameter und ist dort schwer zu nutzen.

4. Fallen

  • „Java-Typen sind in Kotlin automatisch nullable.“ → Falsch. Ohne Annotation sind sie Platform Types. Kotlin prüft nichts.
  • „Ein Kotlin-Property ist ein Feld.“ → Falsch. Es erscheint in Java als Getter und Setter. Ein öffentliches Feld gibt es nur mit @JvmField.
  • „Kotlin-Default-Argumente funktionieren in Java.“ → Falsch. Java sieht nur die volle Signatur. Man braucht @JvmOverloads.
  • „Java kann Checked Exceptions aus Kotlin immer fangen.“ → Falsch. Ohne @Throws steht die Exception nicht in der Signatur. Der Java-Compiler lehnt ein catch ab.
  • „Spring-Beans in Kotlin brauchen keine Anpassung.“ → Falsch. Kotlin-Klassen sind final. Ohne das kotlin-spring-Plugin schlagen Proxys fehl.
  • „Eine Kotlin-suspend-Funktion ist aus Java normal aufrufbar.“ → Falsch. Sie hat einen versteckten Continuation-Parameter. Für Java bietet man eine Hülle, zum Beispiel mit CompletableFuture.

5. Selbsttest

Warum?

Warum kann man Kotlin schrittweise einführen?

Beide kompilieren zu Bytecode und rufen sich direkt auf. Neue Dateien in Kotlin, alte in Java, im selben Modul.

Warum gibt es Platform Types?

Java-Code sagt nichts über Null. Kotlin will Java-Bibliotheken trotzdem bequem nutzen. Es gibt darum eine Zwischenstufe ohne Prüfung.

Warum braucht man @JvmStatic?

Companion-Funktionen sind aus Java sonst nur über Companion erreichbar. Die Annotation erzeugt eine statische Methode.

Wie innen?

Wo landen Top-Level-Funktionen?

Als statische Methoden in der Klasse DateinameKt, zum Beispiel org.example.AppKt.

Wie sieht Java ein Kotlin-Property?

Als Getter, bei var auch als Setter. Das Feld ist privat. Mit @JvmField ist es öffentlich.

Was macht @JvmOverloads?

Es erzeugt für Funktionen mit Default-Argumenten Überladungen. Java kann sie dann mit weniger Parametern aufrufen.

Wie sieht Kotlin eine Java-Methode mit void?

Als Funktion mit Rückgabetyp Unit.

Zahlen

Wie viele Wege gibt es, Java-Null-Information zu geben?

Drei Annotationsfamilien: JetBrains, JSpecify und JSR-305. Es gibt noch weitere, die Doku listet sie.

Wie heisst die Datei-Klasse für app.kt?

AppKt.

Welche Standardsichtbarkeit und Vererbung hat eine Kotlin-Klasse?

Öffentlich und final.

Vergleich

Kotlin-Property vs Java-Getter?

In Kotlin ist es ein Property mit Syntax wie ein Feld. In Java ist es ein Getter-Aufruf. Beides ist dasselbe im Bytecode.

Kotlin-Data-Class vs Java-Record aus Java-Sicht?

Eine Data Class ist eine normale Klasse mit Gettern. Mit @JvmRecord wird sie ein echter Java-Record.

Kotlin-Extension vs Java-Util-Methode?

Aus Java ist eine Extension eine statische Methode mit dem Receiver als erstem Parameter.

Annotationen vs Plugins?

Annotationen wie @JvmStatic wirken auf einzelne Stellen. Plugins wie kotlin-spring ändern Klassen im Compiler nach Regeln.

Produktion

Wie macht man eine Java-API für Kotlin sicher?

Null-Annotationen setzen (@Nullable, JSpecify). Dann sieht Kotlin echte Typen und meldet Fehler beim Kompilieren.

Wie macht man eine Kotlin-API für Java angenehm?

Mit @JvmStatic, @JvmOverloads, @JvmField und @Throws. Die Java-Sicht der API prüft man mit einem kleinen Java-Test.

Szenario: Eine Spring-Bean in Kotlin wirft beim Start einen Fehler wegen einer finalen Klasse. Was tun Sie?

Ich aktiviere das kotlin-spring-Plugin. Es macht Klassen mit Spring-Annotationen open. Neue Projekte von start.spring.io haben es schon an.

Szenario: Hibernate meldet, dass eine Kotlin-Entity keinen Standardkonstruktor hat. Was tun Sie?

Ich nutze das kotlin-jpa-Plugin. Es erzeugt einen leeren Konstruktor und öffnet die Entities.

Design

Wie führe ich Kotlin in ein Java-Projekt ein?

Zuerst Tests oder neue Module in Kotlin. Build mit Gradle oder Maven für beide Sprachen. Dann schrittweise Dateien umstellen.

Wie gestalte ich eine Bibliothek für beide Sprachen?

Kotlin-API mit Java-Annotationen. Keine suspend-Funktionen in der öffentlichen API ohne Java-Hülle. Nullability sauber setzen.

Wann nehme ich @JvmField?

Für Konstanten und für Felder, die Java direkt lesen soll, zum Beispiel für Frameworks, die Felder nutzen. Sonst bleiben Getter besser.

Mehr

Gerüst

  • Warum? Gleicher Bytecode, schrittweise Migration ohne Brücke.
  • Wie innen? Datei-Klassen AppKt, Getter und Setter, Platform Types.
  • Zahlen Drei Annotationsfamilien für Null. Klassen sind final. AppKt als Dateiname.
  • Vergleich Property gegen Getter, Data Class gegen Record, Extension gegen Util.
  • Produktion Platform-Type-NPE, final bei Spring, kein leerer Konstruktor bei JPA.
  • Design Null-Annotationen, @Jvm..., Plugins, Java-Sicht testen.

Beispiel: Dieselbe API aus Kotlin und aus Java

// Kotlin: Util.kt im Package org.example
@file:JvmName("Utils")
package org.example

class Config {
    companion object {
        @JvmStatic fun load(path: String = "app.conf", strict: Boolean = false): Config = Config()
        @JvmField val VERSION = 1
    }
}

@JvmOverloads fun connect(host: String, port: Int = 8080, tls: Boolean = false) { /* ... */ }

@Throws(java.io.IOException::class)
fun readAll(path: String): String = TODO()

// Java
Utils.connect("db");                      // dank @JvmOverloads
Utils.connect("db", 5432);
Config c = Config.load("x.conf", true);   // dank @JvmStatic
int v = Config.VERSION;                   // dank @JvmField

Nicht ausgeführt.

  1. @file:JvmName("Utils") ändert den Namen der Datei-Klasse von UtilKt auf Utils.
  2. @JvmOverloads erzeugt connect(host), connect(host, port) und die volle Variante.
  3. @JvmStatic macht Config.load zu einer echten statischen Methode.
  4. @JvmField macht VERSION zu einem öffentlichen statischen Feld.
  5. @Throws schreibt IOException in die Signatur. So kann Java sie fangen.

Vergleich

  • Kotlin aus Java: Getter, statische Methoden in DateinameKt, Annotationen für Feinheiten.
  • Java aus Kotlin: Platform Types, Getter als Properties, SAM-Umwandlung für Lambdas.
  • Spring: Läuft mit Kotlin. Es braucht kotlin-spring.

Produktion

  1. NPE durch Platform Types: Java liefert null, Kotlin nimmt non-null an. Lösung: Annotationen oder nullable Typ.
  2. Final-Klassen bei Spring: Proxys scheitern. Lösung: kotlin-spring.
  3. JPA ohne Standardkonstruktor: Hibernate kann nicht instanziieren. Lösung: kotlin-jpa.
  4. Checked Exceptions: Java-Code fängt eine Exception nicht, die Kotlin wirft. Lösung: @Throws.
  5. Unschöne Java-API: Companion und Default-Argumente sind aus Java umständlich. Lösung: @JvmStatic und @JvmOverloads.
  6. Build-Reihenfolge: Gemischte Module brauchen die Kotlin-Plugin-Einstellungen. Lösung: Gradle oder Maven nach Kotlin-Doku konfigurieren.

Diagnose: Werkzeuge und Befehle

  • javap -p -c Datei.class: zeigt, wie Java die Kotlin-Klasse sieht.
  • IntelliJ Show Kotlin Bytecode und Decompile to Java: zeigen die Java-Sicht.
  • Compiler-Warnungen zu Platform Types und Annotationen ernst nehmen.
  • Ein kleiner Java-Test gegen die Kotlin-API: findet unschöne Signaturen.
  • Stacktrace eines NPE: zeigt, ob die Quelle ein Java-Aufruf war.
  • Spring-Startfehler lesen: "final" oder "no default constructor" zeigen fehlende Plugins.

Senior-Punkte

  1. Die Grenze ist der Ort der Fehler. Null und Exceptions gehen dort verloren.
  2. Annotieren lohnt sich. Eine Annotation im Java-Code spart viele NPEs im Kotlin-Code.
  3. Öffentliche API für beide Sprachen testen. Ein Java-Test findet unschöne Signaturen früh.
  4. Plugins sind Teil des Frameworks-Setups. kotlin-spring und kotlin-jpa gehören in jedes Projekt.
  5. Schrittweise migrieren. Kein Big Bang. Zuerst Tests und neue Module.
  6. suspend ist keine Java-freundliche API. Dafür eine Hülle anbieten.
