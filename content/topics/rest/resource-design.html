Ressourcen-Design, URLs, Richardson Maturity Model

Kern: Ressourcen-Design ist die Entscheidung, welche fachlichen Dinge eine API als adressierbare Ressourcen zeigt und unter welchen URIs. Die URI nennt das Ding (Nomen), die HTTP-Methode nennt die Aktion. Gutes Design macht eine API vorhersagbar, cachebar und leicht weiterzuentwickeln.

Antwort-Muster

Frage: Wie entwirft man gute REST-URIs?

  1. Mechanismus: Die URI nennt das Ding als Nomen im Plural, die HTTP-Methode die Aktion. Beispiel ist POST /orders.
  2. Zahl: Ich nutze höchstens zwei Ebenen, z. B. /orders/42/items. Die meisten APIs sind auf Richardson-Level 2.
  3. Trade-off: Tiefe Pfade zeigen Besitz, sind aber starr. Flache URIs mit Filtern sind flexibler.
  4. Produktion: Für Aktionen mit eigenen Daten nehme ich eine Ressource wie POST /orders/42/cancellation. Jede ID braucht eine Objekt-Prüfung.

1. Die Reise eines Clients durch die API

  1. Level 0 (Swamp of POX): Ein Endpoint, alles per POST. Die Aktion steht im Body: {"action":"cancelOrder"}. Fehler kommen als 200 mit "ok": false.
  2. Level 1, Ressourcen: Jede Bestellung hat eine eigene URI. Die Methode ist aber noch egal, oft nur POST.
  3. Level 2, HTTP-Verben: GET liest, POST legt an, DELETE löscht. Fehler sind echte Statuscodes. Die meisten „REST“-APIs sind hier.
  4. Level 3, Hypermedia Controls: Die Antwort enthält Links für die nächsten Schritte. Das heisst HATEOAS (Hypermedia as the Engine of Application State).
  5. Im Beispiel: Bestellung 42 ist NEW und hat einen Link cancel. Nach der Stornierung fehlt der Link. Die Regel „wann darf man stornieren“ bleibt im Server.

2. Aufbau

  1. Fachmodell: die Dinge der Domäne. Beispiel: Kunde, Bestellung, Position.
  2. Ressource: alles, was eine eigene URI verdient. Eine Ressource ist nicht gleich eine DB-Tabelle.
  3. Collection: eine Liste gleicher Ressourcen, z. B. /orders. POST legt dort an.
  4. Element: ein Eintrag der Collection, z. B. /orders/42. GET, PUT, PATCH, DELETE wirken hier.
  5. Sub-Ressource: gehört fachlich zu einem Eltern-Element, z. B. /orders/42/items.
  6. Repräsentation: was über die Leitung geht, meist JSON. Eine Ressource kann mehrere haben (JSON, CSV, PDF).

3. Details, die Interviewer fragen

  1. Nomen statt Verben: Man schreibt /orders, nicht /getOrders. Das Verb ist die HTTP-Methode.
  2. Plural für Collections: Man schreibt /orders und /orders/42. So bleibt das Muster gleich.
  3. Schreibweise: Man schreibt klein und trennt Wörter mit Bindestrich (kebab-case), z. B. /shipping-addresses. Es gibt keine Dateiendungen wie .json. Das Format kommt über Accept.
  4. Hierarchie: Sie ist nur für echte Besitz-Beziehungen. /orders/42/items ist gut, denn Positionen existieren nicht ohne Bestellung. Faustregel: höchstens zwei Ebenen tief.
  5. Sub-Ressource oder Filter? /customers/7/orders und /orders?customerId=7 sind beide gültig. Die erste zeigt Besitz. Die zweite ist flexibler, weil man Filter kombinieren kann.
  6. Singleton-Ressource: Das ist genau ein Ding ohne ID, z. B. /orders/42/shipping-address oder /me.
  7. Aktionen: Es gibt drei Muster. Erstens ein Zustandsfeld per PATCH, z. B. {"status":"CANCELLED"}. Zweitens eine Aktion als Ressource, z. B. POST /orders/42/cancellation. Drittens eine Custom Method im Google-Stil, z. B. POST /orders/42:cancel (AIP-136).
  8. Wann Aktion als Ressource? Das lohnt sich, wenn die Aktion eigene Daten (Grund, Zeit, Nutzer) oder eigene Regeln hat. Dann ist sie auch abfragbar und auditierbar.
  9. IDs: Sie sind stabil und opak, also ohne Bedeutung für den Client. Fortlaufende Zahlen sind leicht zu raten. Darum prüft man die Autorisierung pro Objekt, oder nutzt UUIDs.
  10. Statelessness: Jeder Request trägt alles, was der Server braucht (z. B. Token). Es gibt keine Server-Session. Das ist eine REST-Bedingung nach Fielding. Es erlaubt horizontales Skalieren.
  11. Uniform Interface: Alle Ressourcen nutzen gleiche Methoden und Statuscodes. Darum funktionieren generische Caches und Clients.
  12. Vier Interface-Constraints: Fielding nennt vier. Es sind Identifikation von Ressourcen, Änderung über Repräsentationen, selbstbeschreibende Nachrichten und Hypermedia (HATEOAS).
  13. Cache-Constraint: Antworten müssen als cachebar oder nicht cachebar gekennzeichnet sein. Ein Cache darf sie dann für gleiche spätere Requests wiederverwenden.
  14. HATEOAS: Links in der Antwort sagen dem Client, was er als Nächstes tun kann. Formate sind HAL (_links, ein Internet-Draft), JSON:API und Siren. In Spring gibt es Spring HATEOAS.
  15. Link-Header (RFC 8288): Links gehen auch in den Header, z. B. Link: </orders?page=3>; rel="next". Das nutzt z. B. Pagination.
  16. Richardson Maturity Model: Level 0 ist POX, 1 Ressourcen, 2 Verben und Statuscodes, 3 Hypermedia. Laut Fielding ist erst Level 3 wirklich REST.
  17. Bulk-Operationen: Viele Elemente legt man auf einmal an mit POST /orders/batch oder mit einem Job-Muster und 202. Teilerfolge meldet man klar.
  18. Lange Aktionen: POST /reports gibt 202 mit Location: /reports/7. Die Report-Ressource hat einen Status. Wenn sie fertig ist, zeigt ein Link auf das Ergebnis.

4. Fallen

  • „REST heisst JSON über HTTP.“ → Falsch. REST ist ein Architekturstil mit Bedingungen: Ressourcen, Uniform Interface, Stateless, Cache, Hypermedia.
  • „Eine Ressource ist eine Tabelle.“ → Falsch. Eine Ressource ist ein fachliches Konzept. Sie kann aus vielen Tabellen kommen.
  • „Verben in URIs sind immer falsch.“ → Zu streng. Für echte Aktionen sind Aktions-Ressourcen oder Custom Methods (:cancel) akzeptiert.
  • „Unsere API ist RESTful, weil sie GET und POST nutzt.“ → Das ist höchstens Level 2. Fielding nennt erst Hypermedia echtes REST.
  • „HATEOAS heisst, man braucht keine Doku.“ → Falsch. Der Client muss die Link-Relationen und Datenformate trotzdem kennen.
  • „UUIDs machen Autorisierung überflüssig.“ → Falsch. IDs leaken über Logs und Links. Die Prüfung pro Objekt bleibt Pflicht.

5. Selbsttest

Warum?

Warum Nomen statt Verben in URIs?

Die URI nennt das Ding, die HTTP-Methode die Aktion. So bleibt die API einheitlich und Caches und Gateways verstehen sie.

Wann lohnt sich eine Aktions-Ressource?

Wenn die Aktion eigene Daten oder Regeln hat, z. B. Grund und Zeitpunkt. Dann ist sie auch abfragbar und auditierbar.

Welchen Nutzen hat HATEOAS konkret?

Der Server steuert erlaubte Aktionen über Links und kann URIs ändern. Der Client braucht weniger Geschäftsregeln.

Warum keine Dateiendungen wie .json in URIs?

Das Format wählt der Client über den Accept-Header. Die URI nennt nur die Ressource.

Fortlaufende IDs oder UUIDs?

Fortlaufende IDs sind lesbar, aber leicht zu raten und verraten Mengen. UUIDs verbergen das. Autorisierung pro Objekt braucht man in beiden Fällen.

Wie innen?

Was ist eine Ressource in REST?

Ein fachliches Ding mit eigener URI, z. B. eine Bestellung. Der Client sieht Repräsentationen davon, meist JSON.

Wann eine Sub-Ressource?

Wenn das Kind ohne Eltern nicht existiert, z. B. /orders/42/items. Sonst lieber Top-Level mit Filter.

Was bedeutet stateless in REST?

Jeder Request enthält alle nötigen Informationen. Der Server hält keine Session pro Client. Das erleichtert Skalierung.

Was ist das Uniform Interface?

Alle Ressourcen nutzen dieselben Methoden, Statuscodes und Medientypen. Darum funktionieren generische Clients, Caches und Gateways.

Was ist HAL?

Ein JSON-Format für Links mit _links und _embedded. Es ist ein Internet-Draft und wird z. B. von Spring HATEOAS unterstützt.

Zahlen

Was ist das Richardson Maturity Model?

Vier Stufen: 0 ein Endpoint (POX), 1 Ressourcen, 2 HTTP-Verben und Statuscodes, 3 Hypermedia Controls.

Wie tief sollen URIs verschachtelt sein?

Faustregel höchstens zwei Ebenen. Tiefer wird starr und jede Ebene braucht eine Prüfung.

Auf welchem Level sind die meisten APIs?

Level 2. Hypermedia nutzen nur wenige konsequent.

Wie viele Interface-Constraints hat REST?

Vier: Identifikation von Ressourcen, Änderung über Repräsentationen, selbstbeschreibende Nachrichten und Hypermedia (HATEOAS). So definiert es Fielding.

Vergleich

/customers/7/orders oder /orders?customerId=7?

Beides geht. Die Sub-Collection zeigt Besitz. Der Filter ist flexibler und kombinierbar. Viele APIs bieten den Filter als Standard.

Wie modelliert man eine Aktion wie „stornieren“?

Als Zustand per PATCH, als Aktions-Ressource POST /orders/42/cancellation, oder als Custom Method POST /orders/42:cancel.

Was ist HATEOAS?

Hypermedia as the Engine of Application State: Die Antwort enthält Links zu möglichen nächsten Schritten. Der Client folgt Links statt URIs selbst zu bauen.

REST, gRPC oder GraphQL?

REST ist cachebar und mit curl einfach. gRPC ist schnell und typisiert, gut zwischen Services. GraphQL lässt den Client Felder wählen, Caching und Rate Limiting sind aber schwieriger.

Produktion

Was ist eine chatty API und was hilft?

Ein Bildschirm braucht viele Requests. Hilfe: zusammengesetzte Ressourcen, expand-Parameter oder ein Backend for Frontend.

Szenario: Ein neues Team will jede DB-Tabelle als Endpoint freigeben. Was sagen Sie?

Das koppelt Clients an das Schema. Besser Ressourcen nach Anwendungsfällen, DTOs und ein Review der URIs vor der Freigabe.

Szenario: Das Frontend braucht für eine Detailseite 25 Requests. Was tun Sie?

Messen, welche Daten zusammengehören. Dann eine zusammengesetzte Ressource oder expand anbieten, oder ein BFF für diesen Client.

Szenario: Ein Pentest findet, dass /orders/{id} fremde Bestellungen zeigt. Was ändern Sie?

Autorisierung pro Objekt im Service: Gehört die Bestellung dem Nutzer? Sonst 404. Zentral umsetzen, z. B. in der Repository-Abfrage, und mit Tests absichern.

Design

Plural oder Singular?

Plural für Collections: /orders und /orders/42. Singular nur für Singletons wie /me.

Wie gibt man Links ohne Body?

Mit dem Link-Header aus RFC 8288, z. B. rel="next" für die nächste Seite.

Wie modelliert man eine lange Verarbeitung?

POST legt einen Job an, Antwort 202 mit Location. Der Client fragt den Job-Status ab und folgt am Ende einem Link zum Ergebnis.

Mehr

Gerüst

  • Warum? Die API wird vorhersagbar, cachebar und leicht weiterzuentwickeln. Die URI nennt das Ding, die Methode die Aktion.
  • Wie innen? Collection /orders, Element /orders/42, Sub-Ressource /orders/42/items. Repräsentation meist JSON. Stateless: jeder Request trägt alles.
  • Zahlen Richardson: 4 Stufen (0 bis 3), die meisten APIs sind auf Level 2. Höchstens 2 Ebenen tief. REST hat 4 Interface-Constraints.
  • Vergleich Sub-Collection zeigt Besitz, Filter ist flexibler. REST: cachebar. gRPC: schnell und typisiert. GraphQL: Client wählt die Felder.
  • Produktion DB-Tabellen 1:1 als API. Chatty API mit 30 Requests. Erratbare IDs ohne Objekt-Prüfung (OWASP API1).
  • Design Ressourcen aus Anwendungsfällen, nicht aus Tabellen. Aktion mit eigenen Daten wird eine Ressource. Lange Arbeit: 202 + Status-Ressource.

Beispiel: Level 0 gegen Level 3

# resource_demo.py (gekürzt): http.server + urllib
def links(o):                              # Links hängen vom Zustand ab
    l = {"self": {"href": f"/orders/{o['id']}"},
         "customer": {"href": f"/customers/{o['customerId']}"},
         "items": {"href": f"/orders/{o['id']}/items"}}
    if o["status"] == "NEW":
        l["cancel"] = {"href": f"/orders/{o['id']}/cancellation", "method": "POST"}
    return l
# POST /orders/{id}/cancellation  -> 201, oder 409 wenn nicht NEW
# POST /api {"action": "cancelOrder"} -> immer 200, Fehler im Body
Level 3: Bestellung lesen, Links folgen
GET /orders/42 -> 200
  {"id": 42, "customerId": 7, "status": "NEW", "items": [{"sku": "B-1", "qty": 2}], "_links": {"self": {"href": "/orders/42"}, "customer": {"href": "/customers/7"}, "items": {"href": "/orders/42/items"}, "cancel": {"href": "/orders/42/cancellation", "method": "POST"}}}
GET /customers/7/orders -> 200
  [42]
POST /orders/42/cancellation -> 201
  {"orderId": 42, "reason": "doppelt bestellt"}
GET /orders/42 -> 200
  {"id": 42, "customerId": 7, "status": "CANCELLED", "items": [{"sku": "B-1", "qty": 2}], "_links": {"self": {"href": "/orders/42"}, "customer": {"href": "/customers/7"}, "items": {"href": "/orders/42/items"}}}
POST /orders/42/cancellation -> 409
  {"title": "Order not cancellable"}
Level 0: alles über POST /api
POST /api -> 200
  {"ok": false, "error": "not cancellable"}

Echte Ausgabe, Python 3.12 (http.server + urllib). Das _links-Format ist an HAL angelehnt.

  1. Die Bestellung zeigt per Link auf Kunde, Positionen und die erlaubte Aktion cancel.
  2. /customers/7/orders ist eine Sub-Collection: die Bestellungen eines Kunden.
  3. Stornieren ist eine eigene Ressource. POST legt eine cancellation an: 201, mit Grund.
  4. Danach fehlt der Link cancel. Ein zweiter Versuch ergibt 409 Conflict.
  5. Level 0 meldet denselben Fehler als 200. Gateways, Monitoring und Retries sehen nur „Erfolg“.

Vergleich

  • REST (Level 2): Ressourcen, Verben, Statuscodes. Gut cachebar, einfach mit curl. Standard für öffentliche APIs.
  • REST mit HATEOAS (Level 3): Client folgt Links statt URIs zu bauen. Server kann URIs ändern. Mehr Aufwand, wenige Clients nutzen es wirklich.
  • RPC über HTTP (Level 0): eine URI, Aktion im Body. Einfach, aber kein Caching, keine Semantik für Gateways.
  • gRPC: RPC mit Protobuf und HTTP/2. Schnell und typisiert, gut zwischen Services. Nicht direkt im Browser.
  • GraphQL: ein Endpoint, der Client wählt die Felder. Gut gegen Over-Fetching bei vielen Frontends. Caching und Rate Limiting sind schwieriger.
  • Tiefe Hierarchie vs flache URIs: Tief zeigt Besitz, aber URIs werden lang und starr. Flach mit Filtern ist flexibler.

In der Produktion

  1. DB-Tabellen als API: Die API zeigt jede Tabelle 1:1. Jede DB-Änderung bricht Clients. Lösung: Ressourcen nach Anwendungsfällen schneiden, DTOs statt Entities.
  2. Chatty API: Eine Seite braucht 30 Requests. Lösung: zusammengesetzte Ressourcen, ?expand=items, oder ein BFF (Backend for Frontend).
  3. Verben in URIs wuchern: /updateOrderStatus, /setOrderPaid. Lösung: Zustand per PATCH oder Aktionen als Ressourcen mit klaren Regeln.
  4. Zu tiefe Pfade: /customers/7/orders/42/items/3/notes. Jede Ebene braucht eine Prüfung, ob die Eltern zusammenpassen. Lösung: ab der zweiten Ebene eigene Top-Level-Ressource.
  5. Erratbare IDs ohne Prüfung: /orders/43 zeigt fremde Daten. Lösung: Autorisierung pro Objekt (OWASP API1).
  6. Uneinheitliche Namen: customerId, customer_id, custId in einer API. Lösung: API-Guidelines und Linter (z. B. Spectral) in der CI.

Diagnose: Werkzeuge und Befehle

  • OpenAPI-Dokument lesen: alle Pfade auf einen Blick. Verben in Pfaden und tiefe Hierarchien fallen sofort auf.
  • Spectral (API-Linter) mit eigenem Regelsatz: prüft Namen, Plural, kebab-case in der CI.
  • Gateway-Logs: Anzahl Requests pro Seitenaufruf zeigt eine chatty API.
  • Tracing (OpenTelemetry): zeigt N+1-Aufrufe zwischen Frontend und API.
  • curl -i URL: zeigt Link-Header und Location nach POST.

Senior-Punkte

  1. Ressourcen kommen aus Anwendungsfällen, nicht aus Tabellen. Die API ist ein Produkt mit eigenem Lebenszyklus.
  2. Level 2 reicht meist. Level 3 lohnt sich bei Workflows mit Zuständen, wo der Server erlaubte Aktionen steuern soll. Sonst ist der Aufwand grösser als der Nutzen.
  3. Pragmatismus vor Reinheit: Eine Aktion als POST …/cancellation ist sauberer als ein PATCH, das versteckt Geschäftslogik auslöst.
  4. Konsistenz schlägt Eleganz. Eine einheitliche Guideline über alle Teams ist wichtiger als die perfekte einzelne URI.
  5. URIs sind ein Vertrag. Einmal veröffentlicht, bleiben sie. Darum vorher gut überlegen und reviewen.
  6. Sicherheit gehört zum Design: Jede URI mit ID braucht eine Objekt-Prüfung. Das ist die häufigste API-Lücke.
