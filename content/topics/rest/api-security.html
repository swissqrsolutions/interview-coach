API-Sicherheit: Auth, CORS, CSRF, Rate Limiting

Kern: API-Sicherheit ist der Schutz einer API vor unbefugtem Zugriff, Datenabfluss und Missbrauch. Sie hat Schichten: TLS (Transport), Authentifizierung (wer?), Autorisierung pro Objekt und Funktion (darf er?), Eingabeprüfung und Ressourcen-Grenzen. Die häufigste Lücke ist laut OWASP nicht das Login, sondern die fehlende Prüfung, wem ein Objekt gehört.

1. Wo sitzt die Sicherheit?

  1. TLS: verschlüsselt den Transport. Ohne TLS kann jeder im Netz Tokens mitlesen.
  2. Gateway oder WAF: setzt grobe Grenzen: Rate Limit, maximale Body-Grösse, Timeouts, CORS, oft auch das TLS-Ende.
  3. Identity Provider: z. B. Keycloak. Der Client holt dort per OAuth2 (Authorization Code mit PKCE) ein Access Token.
  4. Security-Filter: prüft das Token: Signatur über die Public Keys (JWKS), Ablauf exp, Empfänger aud, Aussteller iss. Fehler: 401.
  5. Service: prüft Rolle (Funktion), Objekt (gehört es dem Nutzer?) und Felder (welche darf er lesen und schreiben?). Fehler: 403 oder 404.
  6. Datenbank: Die Objekt-Prüfung steckt am besten direkt in der Abfrage, z. B. WHERE owner_id = :sub.

2. Die Reise eines Angreifers (die Geschichte zum Merken)

  1. Token fälschen: Der Angreifer setzt im JWT-Header alg: none und gibt sich die Rolle admin. Der Server akzeptiert nur seinen festen Algorithmus. Antwort: 401.
  2. ID raten: Anna ist echt angemeldet und ändert /orders/1 zu /orders/2. Ohne Objekt-Prüfung sieht sie Bens Bestellung. Das ist BOLA, Platz 1 bei OWASP.
  3. Feld einschmuggeln: Anna schickt {"status":"CANCELLED","price":"0.00"}. Bindet der Server alles blind an die Entity, ändert sie den Preis. Das ist Mass Assignment, Teil von BOPLA.
  4. Admin-Endpoint: Anna ruft DELETE /admin/users/2. Ohne Rollen-Prüfung pro Funktion geht das durch. Das ist BFLA.
  5. Fremde Webseite: evil.example ruft die API aus dem Browser. Der Preflight bekommt keinen Access-Control-Allow-Origin. Der Browser gibt die Antwort nicht frei.
  6. Massen-Abfragen: Ein Skript fragt tausende Bestellungen ab. Das Rate Limit antwortet mit 429 und Retry-After.

3. Beispiel: sechs Angriffe gegen einen kleinen Service

# security_demo.py (gekürzt): http.server + urllib, JWT HS256 mit hmac (echt: RS256 + JWKS)
def verify(token):
    h, p, s = token.split(".")
    if json.loads(unb64(h)).get("alg") != "HS256": return None, "alg not allowed"   # nie "none"
    if not hmac.compare_digest(s, sign(h, p)):     return None, "bad signature"
    c = json.loads(unb64(p))
    if c.get("aud") != "order-api":                return None, "wrong audience"
    if c["exp"] < time.time():                     return None, "token expired"
    return c, None
# BOLA:  if o["owner"] != claims["sub"]: return 404
# BOPLA: nur WRITABLE = {"status"} annehmen, nur PUBLIC = ("id","status","price") ausgeben
# BFLA:  if "admin" not in claims["roles"]: return 403
# CORS:  Access-Control-Allow-Origin nur für https://app.example.ch
ohne Token                   GET     /orders/1        -> 401  WWW-Authenticate: Bearer realm="order-api"
Anna, eigene Bestellung      GET     /orders/1        -> 200 {"id": 1, "status": "NEW", "price": "49.90"}
Anna, Bens Bestellung (BOLA) GET     /orders/2        -> 404 {"title": "Not Found"}
alg=none, admin gefälscht    DELETE  /admin/users/2   -> 401  WWW-Authenticate: Bearer error="invalid_token", error_description="alg not allowed"
Token abgelaufen             GET     /orders/1        -> 401  WWW-Authenticate: Bearer error="invalid_token", error_description="token expired"
Token für andere API         GET     /orders/1        -> 401  WWW-Authenticate: Bearer error="invalid_token", error_description="wrong audience"
Mass Assignment (BOPLA)      PATCH   /orders/1        -> 400 {"title": "Unknown or read-only fields", "fields": ["price"]}
erlaubtes Feld               PATCH   /orders/1        -> 200 {"id": 1, "status": "CANCELLED", "price": "49.90"}
Anna als Admin (BFLA)        DELETE  /admin/users/2   -> 403 {"title": "Forbidden"}
Preflight erlaubter Origin   OPTIONS /orders/1        -> 204  Access-Control-Allow-Origin: https://app.example.ch
Preflight fremder Origin     OPTIONS /orders/1        -> 204
10. Request (Rate Limit)     GET     /orders/1        -> 429 {"title": "Too Many Requests"} Retry-After: 30

Echte Ausgabe, Python 3.12 (http.server + urllib, JWT mit hmac/hashlib). Das Rate Limit ist zum Zeigen auf 9 Requests gesetzt.

  1. Ohne Token: 401 mit WWW-Authenticate: Bearer, wie RFC 6750 es beschreibt.
  2. BOLA: Anna bekommt für Bens Bestellung 404, nicht 403. So verrät die API nicht, dass Bestellung 2 existiert.
  3. Gefälschtes Token: alg=none hat keine Signatur. Der Server prüft den Algorithmus gegen eine feste Liste (RFC 8725). Abgelehnt.
  4. Abgelaufen und falsche aud: beide 401 mit error="invalid_token". Ein Token für die Billing-API gilt nicht für die Order-API.
  5. BOPLA: price ist nicht schreibbar. Der Server lehnt ab, statt still zu ignorieren. internalCost steht im Datensatz, kommt aber nie in der Antwort vor.
  6. BFLA: Anna ist angemeldet, aber nicht Admin: 403.
  7. CORS: Beide Preflights bekommen 204. Nur der erlaubte Origin bekommt den Header. Ohne Header blockiert der Browser.
  8. Rate Limit: Der 10. Request bekommt 429 mit Retry-After.

4. Details, die Interviewer fragen

  1. TLS: nur HTTPS, TLS 1.2 oder 1.3, alte Versionen aus. HSTS (Header Strict-Transport-Security) zwingt Browser zu HTTPS. Zwischen Services: mTLS (beide Seiten mit Zertifikat), z. B. über ein Service Mesh.
  2. Authentifizierung vs Autorisierung: AuthN beantwortet „wer bist du?“ (401). AuthZ beantwortet „darfst du das?“ (403).
  3. OAuth 2.0: ein Framework für delegierten Zugriff. Rollen: Resource Owner, Client, Authorization Server, Resource Server (die API). OpenID Connect setzt Login und ID Token darauf.
  4. Grants nach RFC 9700: Authorization Code mit PKCE für Browser und Apps. Client Credentials für Service-zu-Service. Der Password Grant darf nicht verwendet werden. Der Implicit Grant gilt als unsicher. OAuth 2.1 (noch ein Draft) fasst das zusammen.
  5. PKCE (RFC 7636): Der Client schickt einen Hash eines Geheimnisses mit und beweist es beim Token-Tausch. Schützt gegen gestohlene Authorization Codes. RFC 9700 verlangt es für Public Clients.
  6. JWT (RFC 7519): Header, Payload (Claims), Signatur, Base64URL-kodiert. Signiert, aber nicht verschlüsselt. Jeder kann den Inhalt lesen.
  7. JWT prüfen: Signatur mit Key aus JWKS, Algorithmus aus fester Liste (nie none), exp, nbf, iss, aud. RFC 8725 beschreibt die Angriffe, z. B. Algorithmus-Wechsel.
  8. RS256 vs HS256: RS256 ist asymmetrisch: Der IdP signiert privat, APIs prüfen mit dem Public Key. HS256 nutzt ein geteiltes Geheimnis, das jede prüfende API kennen müsste.
  9. Token-Lebensdauer: Access Tokens kurz (Minuten), Refresh Tokens länger und rotierend. JWTs kann man nicht einfach widerrufen. Kurze Laufzeit ist der Ausgleich.
  10. Autorisierung pro Objekt (API1 BOLA): Jeder Zugriff per ID prüft den Besitz. Am sichersten in der Abfrage: findByIdAndOwnerId(id, sub). In Spring auch mit @PreAuthorize oder @PostAuthorize.
  11. Autorisierung pro Feld (API3 BOPLA): eigene Request- und Response-DTOs statt Entities. So kann niemand price oder role setzen und nichts Internes leakt.
  12. Autorisierung pro Funktion (API5 BFLA): Admin-Funktionen mit Rollen oder Scopes absichern. „Versteckte“ URIs sind kein Schutz.
  13. Input Validation: Typ, Länge, Format, Bereich mit Bean Validation (@Valid, @Size, @Pattern). Allowlist statt Blocklist. SQL nur mit Parametern. Bei Uploads den echten Dateityp prüfen, nicht die Endung.
  14. Rate Limiting (API4): pro Client, Nutzer oder IP, meist im Gateway. Algorithmen: Token Bucket, Sliding Window. Antwort 429 mit Retry-After. Die Header RateLimit und RateLimit-Policy sind noch ein IETF-Draft.
  15. CORS: eine Browser-Regel. Der Server erlaubt fremden Origins per Header, Antworten zu lesen. Nicht-einfache Requests (z. B. mit Authorization oder PATCH) lösen einen Preflight (OPTIONS) aus. Mit Credentials ist Access-Control-Allow-Origin: * verboten. Access-Control-Max-Age cacht den Preflight (Standard 5 Sekunden).
  16. CSRF: Ein Angriff, bei dem eine fremde Seite den Browser mit Cookies des Nutzers Requests senden lässt. Betrifft APIs mit Cookie-Session. Bei Bearer-Token im Header (nicht automatisch gesendet) ist CSRF kein Thema. Schutz: CSRF-Token, SameSite-Cookies.
  17. Secrets: nie im Code oder Repo, sondern in Vault oder Key Vault. Tokens und Passwörter nie loggen.

5. Vergleich

  • OWASP API Top 10 2023: API1 Broken Object Level Authorization · API2 Broken Authentication · API3 Broken Object Property Level Authorization · API4 Unrestricted Resource Consumption · API5 Broken Function Level Authorization · API6 Unrestricted Access to Sensitive Business Flows · API7 Server Side Request Forgery · API8 Security Misconfiguration · API9 Improper Inventory Management · API10 Unsafe Consumption of APIs.
  • JWT (self-contained) vs opakes Token: JWT prüft die API lokal, schnell, aber schwer zu widerrufen. Opakes Token braucht Introspection beim IdP (RFC 7662), dafür sofort widerrufbar.
  • API-Key vs OAuth2: API-Key identifiziert eine Anwendung, ist langlebig und ohne Nutzerbezug. OAuth2 gibt kurzlebige Tokens mit Scopes und Nutzer.
  • Session-Cookie vs Bearer Token: Cookie: Browser sendet automatisch, braucht CSRF-Schutz. Bearer: Client setzt es selbst, kein CSRF, aber Token darf nicht in falsche Hände (XSS).
  • 403 vs 404 bei fremden Objekten: 404 verrät nichts über Existenz, 403 ist ehrlicher für Debugging. Für externe APIs meist 404.
  • Gateway vs Service: Gateway für grobe, gleiche Regeln (TLS, Rate Limit, Token-Prüfung). Service für fachliche Regeln (Objekt, Feld, Geschäftsfluss).

6. In der Produktion

  1. Datenleck durch ID-Raten (BOLA): fortlaufende IDs, keine Besitz-Prüfung. Lösung: Prüfung in jedem Zugriff, zentral im Repository, Tests mit zwei Nutzern.
  2. Entity direkt als Request-Body: Ein Client setzt isAdmin=true. Lösung: eigene Request-DTOs, nur erlaubte Felder.
  3. Access-Control-Allow-Origin spiegelt jeden Origin: mit Credentials kann jede Seite Daten lesen. Lösung: feste Allowlist, kein Reflektieren.
  4. Token im Log oder in der URL: ?access_token=… landet in Proxy-Logs und Browser-History. Lösung: nur im Authorization-Header, Logs maskieren.
  5. Keine Grenzen: riesige Uploads, ?size=1000000, teure Suchen ohne Limit. Lösung: Body-Limit, Max-Page-Size, Timeouts, Rate Limit, Kosten-Limits für Drittanbieter (API4).
  6. Alte API-Version ungepatcht online (API9): /v1 ohne neue Prüfungen. Lösung: Inventar aller Endpunkte und Versionen, alte abschalten.
  7. SSRF (API7): Ein Endpoint lädt eine vom Nutzer gegebene URL, z. B. für Webhooks. Ein Angreifer ruft interne Adressen oder Cloud-Metadaten auf. Lösung: Allowlist für Ziele, interne Netze sperren.

7. Diagnose: Werkzeuge und Befehle

  • jwt.io oder echo $TOKEN | cut -d. -f2 | base64 -d: Claims eines Tokens lesen (nie produktive Tokens in fremde Webseiten kopieren).
  • curl -i -X OPTIONS -H 'Origin: https://evil.example' -H 'Access-Control-Request-Method: PATCH' URL: CORS-Konfiguration testen.
  • openssl s_client -connect host:443 -tls1_1: prüft, ob alte TLS-Versionen noch gehen.
  • OWASP ZAP oder Burp Suite: Scans und manuelle Tests, z. B. ID-Wechsel für BOLA.
  • Spring Security Debug: logging.level.org.springframework.security=DEBUG zeigt, welcher Filter ablehnt.
  • Gateway-Metriken: Anteil 401/403/429 pro Client. Ein plötzlicher Anstieg von 404 bei einem Nutzer deutet auf ID-Raten.
  • Integrationstests mit zwei Nutzern: Nutzer A legt an, Nutzer B versucht zu lesen. Erwartung: 404.

8. Senior-Punkte

  1. Authentifizierung ist gelöst, Autorisierung nicht. Login kauft man ein (IdP). Objekt- und Feld-Rechte muss jedes Team selbst bauen und testen.
  2. Defense in Depth: Gateway, Filter und Service prüfen je ihren Teil. Keine Schicht vertraut blind der vorigen, auch nicht intern (Zero Trust).
  3. Standards statt Eigenbau: OAuth2/OIDC mit Keycloak oder Entra ID, Spring Security Resource Server. Eigene Krypto oder Token-Formate sind ein Risiko.
  4. DTOs sind ein Sicherheits-Werkzeug. Sie verhindern Mass Assignment und Datenlecks gleichzeitig.
  5. Grenzen sind Teil des Vertrags: Rate Limits, Max-Grössen und Timeouts gehören in Doku und OpenAPI.
  6. Sicherheit testen wie Funktion: negative Tests (fremder Nutzer, falsche Rolle, abgelaufenes Token) in der CI, nicht nur im jährlichen Pentest.

10. Fallen

  • „Mit gültigem Token ist der Zugriff erlaubt.“ → Falsch. Das Token sagt nur, wer es ist. Ob das Objekt ihm gehört, prüft der Service (BOLA).
  • „JWT ist verschlüsselt.“ → Falsch. Es ist nur signiert. Jeder kann die Claims lesen. Keine Geheimnisse hinein.
  • „CORS schützt meine API vor Angriffen.“ → Falsch. CORS ist eine Browser-Regel. curl und Skripte ignorieren sie.
  • „REST-APIs brauchen nie CSRF-Schutz.“ → Falsch. Mit Cookie-Session schon. Nur bei Bearer-Token im Header entfällt CSRF.
  • „UUIDs verhindern BOLA.“ → Falsch. Sie erschweren Raten, aber IDs leaken. Die Besitz-Prüfung bleibt Pflicht.
  • „Der Password Grant ist für eigene Apps okay.“ → Falsch. RFC 9700: Er darf nicht verwendet werden.

11. Fragen

Was ist der Unterschied zwischen Authentifizierung und Autorisierung?

Authentifizierung klärt, wer jemand ist (Fehler 401). Autorisierung klärt, was er darf (Fehler 403).

Was ist BOLA?

Broken Object Level Authorization, OWASP API1: Ein Nutzer greift über eine fremde ID auf fremde Objekte zu, weil der Besitz nicht geprüft wird.

Wie verhindert man BOLA?

Bei jedem Zugriff per ID den Besitz prüfen, am besten in der Abfrage. Dazu Tests mit zwei Nutzern.

Was ist BOPLA?

Broken Object Property Level Authorization, API3: Nutzer lesen oder schreiben Felder, die sie nicht dürfen. Es vereint Excessive Data Exposure und Mass Assignment.

Was ist Mass Assignment?

Der Server bindet alle Request-Felder an das Objekt, auch geschützte wie role oder price. Lösung: eigene Request-DTOs.

Was ist BFLA?

Broken Function Level Authorization, API5: Ein normaler Nutzer ruft Admin-Funktionen auf, weil Rollen pro Endpoint fehlen.

Nennen Sie die OWASP API Top 10 2023.

BOLA, Broken Authentication, BOPLA, Unrestricted Resource Consumption, BFLA, Unrestricted Access to Sensitive Business Flows, SSRF, Security Misconfiguration, Improper Inventory Management, Unsafe Consumption of APIs.

Welcher OAuth2-Flow für eine Angular-SPA?

Authorization Code mit PKCE. Implicit und Password Grant nicht mehr nutzen.

Welcher Flow für Service-zu-Service?

Client Credentials, ohne Nutzer. Optional mit mTLS oder private_key_jwt statt Client Secret.

Was ist PKCE?

Proof Key for Code Exchange: Der Client sendet den Hash eines Geheimnisses und beweist es beim Token-Tausch. So nützt ein gestohlener Code nichts.

Was prüft eine API an einem JWT?

Signatur mit Key aus JWKS, erlaubten Algorithmus, exp, nbf, iss und aud. Danach Rollen oder Scopes.

Warum ist alg=none gefährlich?

Ein Token ohne Signatur kann jeder bauen. Die API muss den Algorithmus fest vorgeben und none ablehnen.

Warum den aud-Claim prüfen?

Sonst gilt ein Token für Dienst A auch bei Dienst B. Ein kompromittierter Dienst könnte Tokens weiterverwenden.

RS256 oder HS256?

RS256: Nur der IdP hat den Private Key, APIs prüfen mit dem Public Key. HS256 braucht ein geteiltes Geheimnis in jeder API.

Wie widerruft man ein JWT?

Direkt kaum. Darum kurze Laufzeit, Refresh Tokens widerrufen, oder opake Tokens mit Introspection.

Was ist CORS?

Eine Browser-Regel: Der Server erlaubt per Header, dass Seiten von fremden Origins seine Antworten lesen. Ohne Erlaubnis blockt der Browser.

Wann sendet der Browser einen Preflight?

Bei nicht-einfachen Requests, z. B. Methoden ausser GET/HEAD/POST oder Headern wie Authorization oder Content-Type: application/json.

Darf man Access-Control-Allow-Origin: * mit Credentials nutzen?

Nein. Mit Credentials muss der Server den konkreten Origin nennen, sonst gibt der Browser die Antwort nicht frei.

Braucht eine REST-API CSRF-Schutz?

Wenn sie Cookies zur Anmeldung nutzt, ja. Mit Bearer-Token im Authorization-Header nicht, weil der Browser es nicht automatisch sendet.

Wie setzt man Rate Limiting um?

Im Gateway pro Client oder Nutzer mit Token Bucket oder Sliding Window. Antwort 429 mit Retry-After.

Was gehört zur Input Validation?

Typ, Länge, Format und Bereich prüfen, Allowlists, parametrisierte SQL-Abfragen, Uploads nach echtem Dateityp und Grösse prüfen.

Was ist SSRF bei APIs?

Die API lädt eine vom Nutzer gegebene URL und erreicht so interne Systeme. Schutz: Ziel-Allowlist und interne Netze sperren.

Was bedeutet Unsafe Consumption of APIs?

Daten von Drittanbieter-APIs werden ungeprüft vertraut. Sie brauchen dieselbe Validierung wie Nutzereingaben, plus TLS und Timeouts.

Szenario: Ein Kunde sieht nach Änderung der URL die Rechnung eines anderen. Was tun Sie sofort und langfristig?

Sofort: Besitz-Prüfung im Endpoint, Logs auf weitere Zugriffe prüfen, Vorfall melden. Langfristig: Prüfung zentral im Datenzugriff, Tests mit zwei Nutzern für jeden ID-Endpoint, Review-Checkliste.

Szenario: Das Frontend meldet „CORS error“ nach dem Umzug auf eine neue Domain. Was prüfen Sie?

Ob der neue Origin in der Allowlist steht, ob der Preflight OPTIONS durch Gateway und Security-Filter kommt und ob Allow-Headers Authorization enthält. Nicht mit * lösen, wenn Credentials im Spiel sind.

Szenario: Ein Partner-Skript legt die API mit tausenden Requests pro Minute lahm. Was ändern Sie?

Rate Limit pro Client-ID im Gateway mit 429 und Retry-After, Limits im Vertrag festhalten, Partner zu Backoff und Bulk-Endpoints bewegen. Teure Endpoints zusätzlich begrenzen.
