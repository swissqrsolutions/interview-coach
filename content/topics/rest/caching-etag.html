HTTP-Caching: Cache-Control und ETag

Kern: HTTP-Caching speichert Antworten, damit sie nicht jedes Mal neu berechnet werden. Cache-Control sagt, wie lange eine Antwort frisch ist. Ein ETag erlaubt danach eine bedingte Anfrage, die mit 304 Not Modified ohne Body antwortet.

Antwort-Muster

Frage: Wie funktioniert HTTP-Caching mit Cache-Control und ETag?

  1. Mechanismus: Der Server sendet Cache-Control und ETag. Ein Cache nutzt die Antwort, solange sie frisch ist, danach fragt er mit If-None-Match nach.
  2. Zahl: Frische kommt aus s-maxage, max-age oder Expires. Ohne alle drei darf ein Cache sie schätzen, typisch mit 10 % der Zeit seit Last-Modified.
  3. Trade-off: Langes max-age spart Requests, aber man kann die Antwort nicht zurückrufen. Ein ETag spart nur den Body, nicht die Anfrage.
  4. Produktion: Statische Dateien mit Hash im Namen bekommen langes max-age mit immutable. API-Daten bekommen ETag oder no-cache.

1. Eine Anfrage durch den Cache, in 8 Schritten

  1. Request: Der Client sendet GET /item. Zuerst schaut er in seinen Cache.
  2. Treffer suchen: Der Cache sucht eine gespeicherte Antwort zur gleichen URL. Bei Vary müssen auch die genannten Request-Header passen.
  3. Frisch prüfen: Alter der Antwort gegen Lebensdauer. Die Lebensdauer kommt aus s-maxage (nur Shared Cache), sonst max-age, sonst Expires minus Date.
  4. Frisch heisst nutzen: Der Cache liefert die gespeicherte Antwort. Der Server sieht nichts davon.
  5. Stale heisst nachfragen: Der Cache sendet den Request mit If-None-Match: "v1". Das ist die bedingte Anfrage.
  6. Server vergleicht: Der Server prüft das ETag der aktuellen Version. Bei If-None-Match gilt der schwache Vergleich.
  7. 304 oder 200: Gleich heisst 304 ohne Body. Anders heisst 200 mit neuem Body und neuem ETag.
  8. Cache aktualisieren: Bei 304 erneuert der Cache die Header der gespeicherten Antwort und nutzt den alten Body weiter. Bei 200 ersetzt er die Antwort.

Ein normaler GET auf eine 200-Antwort ist der häufigste Fall für Caches. Viele Caches speichern nur GET.

2. Aufbau

  1. Cache-Control hat Direktiven für Frische (max-age) und Regeln (no-store, private).
  2. ETag ist ein Validator, also eine Kennung der Version. Er steht in Anführungszeichen. Ein W/ davor macht ihn schwach.
  3. Last-Modified ist ein Datum als Validator. Der Client sendet es als If-Modified-Since zurück.
  4. Vary nennt Request-Header, die den Inhalt ändern, zum Beispiel Accept-Encoding. Der Cache speichert pro Wert eine Variante.
  5. Private Cache gehört einem Nutzer (Browser). Shared Cache bedient viele (CDN, Proxy).
  6. Age ist die vom Cache geschätzte Zeit seit der letzten Prüfung durch den Origin.

3. Details

  1. Frische: Eine Antwort ist frisch, solange ihr Alter kleiner ist als die Lebensdauer. Danach ist sie stale. Stale heisst nicht gelöscht, sondern nur prüfpflichtig.
  2. Reihenfolge der Lebensdauer: s-maxage (nur Shared Cache), dann max-age, dann Expires minus Date. Gibt es nichts davon, darf der Cache heuristisch schätzen.
  3. Heuristische Frische: Hat die Antwort Last-Modified, ist ein Anteil der Zeit seit diesem Datum üblich. Die Spezifikation nennt typisch 10 %. Wer das nicht will, setzt Cache-Control selbst.
  4. no-cache: Der Cache darf die Antwort speichern, aber nur nach Validierung beim Server wiederverwenden. Der Name ist irreführend.
  5. no-store: Der Cache darf keinen Teil von Request oder Antwort speichern. Das ist die Regel für sensible Daten.
  6. private und public: private erlaubt nur einem privaten Cache zu speichern. public markiert die Antwort ausdrücklich als cachebar.
  7. must-revalidate: Ist die Antwort stale, darf der Cache sie nur nach erfolgreicher Prüfung nutzen. Ist der Server nicht erreichbar, kommt ein Fehler, zum Beispiel 504.
  8. Starker und schwacher ETag: Ein starker ETag ändert sich bei jeder Änderung der Daten. Ein schwacher (W/"1") darf gleich bleiben, wenn der Inhalt gleichwertig ist.
  9. If-None-Match: Der Server nutzt den schwachen Vergleich. Bei GET und HEAD antwortet er mit 304, bei anderen Methoden mit 412.
  10. If-Match: Der Server nutzt den starken Vergleich. Passt der ETag nicht, antwortet er mit 412 Precondition Failed. So verhindert man verlorene Updates (Optimistic Locking).
  11. If-Modified-Since: Der Server ignoriert ihn, wenn If-None-Match im Request steht. ETag hat Vorrang vor dem Datum.
  12. Erweiterungen: stale-while-revalidate und stale-if-error stehen in RFC 5861, nicht in RFC 9111. immutable steht in RFC 8246 und verhindert Nachfragen beim Reload.

4. Fallen

  • „no-cache heisst, die Antwort wird nicht gespeichert.“ → Falsch. Sie wird gespeichert, aber vor jeder Wiederverwendung beim Server geprüft. Nicht speichern heisst no-store.
  • „Ein ETag spart die Anfrage zum Server.“ → Falsch. Der Client fragt weiterhin nach. Gespart wird nur der Body bei 304.
  • „Ein 304 hat einen Body.“ → Falsch. Ein 304 hat keinen Body. Der Cache nutzt den gespeicherten Body und erneuert die Header.
  • „Ein CDN darf Authorization-Antworten einfach cachen.“ → Falsch. Personenbezogene Antworten brauchen private oder no-store. Sonst sieht ein Nutzer die Daten eines anderen.
  • „Mit max-age=31536000 kann ich die Datei später ändern.“ → Falsch. Der Cache ruft sie ein Jahr lang nicht ab. Darum langes max-age nur mit Hash oder Version im Dateinamen.
  • „If-Match und If-None-Match sind das Gleiche.“ → Falsch. If-None-Match prüft für Caching (304). If-Match schützt Updates (412).

5. Selbsttest

Warum?

Warum cachen wir HTTP-Antworten?

Weniger Latenz, weniger Last auf dem Server und weniger Datenverkehr. Frische Antworten kommen ohne Serverkontakt.

Warum braucht man ein ETag, wenn es max-age gibt?

max-age sagt nur, wie lange nicht gefragt werden muss. Danach spart das ETag per 304 den Body.

Warum gibt es If-Match?

Es schützt Updates. Hat jemand die Ressource inzwischen geändert, antwortet der Server mit 412.

Wie innen?

Wie prüft ein Cache, ob eine Antwort frisch ist?

Alter gegen Lebensdauer. Die Lebensdauer kommt aus s-maxage (Shared), max-age, Expires minus Date, sonst aus einer Schätzung.

Wie läuft eine bedingte Anfrage ab?

Der Cache sendet If-None-Match mit dem gespeicherten ETag. Passt er, antwortet der Server 304 ohne Body. Sonst 200 mit neuem Body.

Was macht der Cache bei einem 304?

Er erneuert die Header der gespeicherten Antwort und nutzt den alten Body weiter.

Was bewirkt Vary?

Der Cache speichert Varianten pro Wert der genannten Request-Header. Ein Vary: * passt nie.

Was ist der Unterschied zwischen starkem und schwachem ETag?

Stark heisst Byte-genau gleich. Schwach (W/-Präfix) heisst gleichwertig. If-Match braucht stark, If-None-Match vergleicht schwach.

Zahlen

Welchen Status liefert eine unveränderte Ressource bei If-None-Match?

304 Not Modified, ohne Body.

Welchen Status liefert If-Match bei falschem ETag?

412 Precondition Failed.

Wie viel Frische schätzt ein Cache ohne Angaben?

Die Spezifikation nennt typisch 10 % der Zeit seit Last-Modified. Eine feste Zahl schreibt sie nicht vor.

Wie lange ist max-age=31536000?

Ein Jahr in Sekunden. Das ist der übliche Wert für Dateien mit Hash im Namen, zusammen mit immutable.

Vergleich

no-cache vs no-store?

no-cache speichert und prüft vor jeder Nutzung. no-store speichert gar nichts.

ETag vs Last-Modified?

ETag ist eine beliebige Kennung und genauer. Last-Modified ist ein Datum mit Sekundengenauigkeit. Der ETag hat Vorrang.

private vs public?

private nur im Browser-Cache, public auch in CDN und Proxy. Fehlt beides, gelten die Standardregeln der Antwort.

max-age vs s-maxage?

max-age gilt für alle Caches. s-maxage gilt nur für Shared Caches wie ein CDN und hat dort Vorrang.

Produktion

Warum sehen Nutzer nach einem Deployment noch das alte JavaScript?

Die Datei hat langes max-age unter gleichem Namen. Lösung: Hash im Dateinamen, dann ändert sich die URL.

Warum bekommt ein Nutzer die Daten eines anderen?

Eine personalisierte Antwort wurde im CDN gecacht. Lösung: private oder no-store, und Vary für Header, die den Inhalt ändern.

Szenario: Eine Preis-API ist langsam. Die Preise ändern sich alle paar Minuten. Was tun Sie?

Ein ETag und Cache-Control mit kurzem max-age. Clients fragen mit If-None-Match nach und bekommen oft 304. Mit stale-while-revalidate wartet niemand auf die Prüfung.

Szenario: Zwei Nutzer ändern denselben Datensatz und einer überschreibt die Änderung des anderen. Wie verhindern Sie das?

GET liefert ein ETag. PUT sendet If-Match mit diesem ETag. Hat sich der Datensatz geändert, antwortet der Server mit 412 und der Client lädt neu.

Design

Wie cachen Sie statische Dateien richtig?

Hash im Dateinamen und Cache-Control: max-age=31536000, immutable. Die HTML-Seite selbst bekommt kurz oder no-cache.

Wie berechnet man ein ETag?

Aus dem Inhalt (Hash) oder einer Versionsnummer. Es muss sich bei jeder Änderung ändern.

Wann nimmt man no-store?

Bei sensiblen Daten wie Kontoständen. Der Cache darf nichts speichern.

Was macht stale-while-revalidate?

Der Cache liefert die stale Antwort sofort und prüft im Hintergrund nach. Die Direktive steht in RFC 5861.

Mehr

Gerüst

  • Warum? Weniger Latenz und Last. Frische Antworten kommen ohne Server.
  • Wie innen? Alter gegen Lebensdauer. Stale: bedingte Anfrage mit If-None-Match, Antwort 304 ohne Body.
  • Zahlen 304 Not Modified, 412 Precondition Failed, Heuristik typisch 10 %, ein Jahr = 31536000 Sekunden.
  • Vergleich no-cache prüft, no-store speichert nichts. ETag ist genauer als Last-Modified.
  • Produktion Altes JavaScript nach Deploy, fremde Daten im CDN, verlorene Updates ohne If-Match.
  • Design Hash im Dateinamen mit immutable, ETag für APIs, If-Match für Updates, private bei Nutzerdaten.

Beispiel: ETag und If-Match im Test

GET /item                         -> 200, ETag "v1", Cache-Control max-age=60
GET /item  If-None-Match: "v1"    -> 304 (kein Body)
PUT /item  If-Match: "v1"         -> 204, neuer ETag "v2"
GET /item  If-None-Match: "v1"    -> 200 (ETag ist jetzt "v2")
PUT /item  If-Match: "v1"         -> 412
1) GET ohne Header
  status=200 etag="v1" cache-control=max-age=60 body={"id":1,"price":10}
2) GET mit If-None-Match: "v1"
  status=304 etag="v1" cache-control=max-age=60 body=(leer)
3) PUT mit If-Match: "v1"
  status=204 etag="v2" cache-control=- body=(leer)
4) GET mit altem If-None-Match: "v1"
  status=200 etag="v2" cache-control=max-age=60 body={"id":1,"price":12}
5) PUT mit veraltetem If-Match: "v1"
  status=412 etag=- cache-control=- body=(leer)
Bodies gesendet: 2 von 3 GET-Anfragen

Echte Ausgabe, Java 17.0.3 (com.sun.net.httpserver und java.net.http). Die Demo ist ein kleiner Eigenbau-Server, kein Spring.

  1. Bei Schritt 2 passt der ETag. Der Server sendet 304 und keinen Body.
  2. Bei Schritt 3 passt If-Match. Das Update gelingt und der ETag wird "v2".
  3. Bei Schritt 4 passt der alte ETag nicht mehr. Der Server sendet 200 mit dem neuen Body.
  4. Bei Schritt 5 bekommt ein zweiter Schreiber mit altem ETag 412. Sein Update geht nicht durch.
  5. Von 3 GET-Anfragen trugen nur 2 einen Body. Eine war ein 304.

Vergleich

  • Browser-Cache: private, pro Nutzer. Respektiert Cache-Control.
  • CDN oder Reverse Proxy: Shared Cache für viele Nutzer. Nutzt s-maxage. Gefährlich bei personalisierten Antworten.
  • Application Cache (Redis, Caffeine): im Server, kein HTTP. Spart Datenbank-Zugriffe, nicht Netz.
  • ETag: beliebige Kennung, genau. Last-Modified: Datum, sekundengenau.
  • max-age: relative Sekunden. Expires: absolutes Datum und hängt an Uhren.
  • no-cache, no-store, must-revalidate: drei verschiedene Regeln. Oft werden sie verwechselt.

Produktion

  1. Altes JavaScript oder CSS nach Deployment: Langes max-age unter gleichem Namen. Lösung: Hash im Dateinamen.
  2. Fremde Daten im CDN: Eine personalisierte Antwort wurde geteilt. Lösung: private oder no-store, Vary richtig setzen.
  3. Verlorene Updates: Zwei Clients schreiben ohne Prüfung. Lösung: ETag mit If-Match und 412.
  4. Cache wird nie getroffen: Das ETag ändert sich bei jeder Antwort, zum Beispiel wegen eines Zeitstempels im Body. Lösung: ETag aus dem stabilen Inhalt berechnen.
  5. Falsche Varianten: Antwort ändert sich je nach Header, aber Vary fehlt. Lösung: Vary setzen, zum Beispiel Accept-Encoding.
  6. API nach Änderung noch alt: Ein Gateway cached ohne Absprache. Lösung: Cache-Control explizit senden.

Diagnose: Werkzeuge und Befehle

  • Browser DevTools, Tab Network: zeigt 'from disk cache', 304 und die Header.
  • curl -i: zeigt Antwort-Header. curl -i -H 'If-None-Match: "v1"' URL testet die bedingte Anfrage.
  • Header Age: zeigt, ob ein Shared Cache die Antwort ausgeliefert hat.
  • CDN-Logs: Hit- und Miss-Rate pro Pfad.
  • Integrationstest: Zweimal anfragen und den Status prüfen (200, dann 304).

Senior-Punkte

  1. Caching ist ein Vertrag mit allen Caches auf dem Weg. Man kann eine gecachte Antwort nicht zurückrufen.
  2. Unveränderliche URLs sind der sicherste Weg. Hash im Namen, langes max-age, immutable.
  3. ETag sorgt für Konsistenz, nicht für Tempo. Es spart Bytes, die Anfrage bleibt. Mit If-Match schützt es zusätzlich vor verlorenen Updates.
  4. Personalisierte Antworten sind die Hauptgefahr. Im Zweifel private oder no-store.
  5. Cache-Control immer ausdrücklich setzen. Sonst entscheidet die Heuristik des Caches.
  6. Kurzes max-age plus stale-while-revalidate ist oft der gute Kompromiss für APIs.
