OpenAPI, Contract-First, Code-Generierung

Kern: OpenAPI ist eine Spezifikation, mit der man eine HTTP-API maschinenlesbar in YAML oder JSON beschreibt, also Pfade, Parameter, Schemas, Fehler und Security. Das Dokument ist der Vertrag zwischen Anbieter und Clients. Aus ihm entstehen Doku, Client- und Server-Code, Mocks und Tests.

Antwort-Muster

Frage: Was ist OpenAPI, und wie setzt man es ein?

  1. Mechanismus: Ein YAML- oder JSON-Dokument beschreibt Pfade, Schemas, Fehler und Security. Daraus entstehen Doku, Code, Mocks und Tests.
  2. Zahl: OpenAPI 3.1 nutzt JSON Schema 2020-12. Dort ersetzt type: [string, 'null'] das alte nullable.
  3. Trade-off: Contract-First gibt Review vor dem Bau, kostet aber Anfangsaufwand. Code-First ist schnell, der Vertrag ändert sich aber still.
  4. Produktion: Ich prüfe den Vertrag mit Contract-Tests und einem Diff in der CI.

1. Die Reise eines Vertrags

  1. Entwurf: Das Team schreibt den Endpoint zuerst in openapi.yaml, mit Beispielen und Fehlern (Problem Details).
  2. Review: Frontend und Partner-Teams lesen den PR. Spectral prüft Namen, Fehlerformat und Security-Angaben.
  3. Generieren: Der Build erzeugt ein Spring-Interface OrdersApi und DTOs. Das Frontend erzeugt einen TypeScript-Client.
  4. Parallel bauen: Backend implementiert das Interface. Frontend arbeitet gegen einen Mock aus dem Vertrag.
  5. Prüfen: Ein Contract-Test ruft den echten Service und vergleicht die Antwort mit dem Schema. Abweichung: Build rot.
  6. Nächste Änderung: Ein Diff gegen den Stand auf main erkennt Breaking Changes vor dem Merge.

2. Aufbau

  1. Vertrag (openapi.yaml): beschreibt die API vollständig. Bei Contract-First liegt er im Git und wird reviewt wie Code.
  2. Server-Stubs: Ein Generator erzeugt Interfaces und DTOs. Der Entwickler implementiert nur die Logik.
  3. Client-SDKs: Frontend und andere Teams generieren typisierte Clients, z. B. TypeScript für Angular.
  4. Doku: Swagger UI oder Redoc rendern den Vertrag als Webseite mit „Try it out“.
  5. Tests und Lint: Contract-Tests prüfen echte Antworten. Linter (Spectral) prüfen Guidelines. Diff-Tools finden Breaking Changes.
  6. springdoc (gestrichelt): der umgekehrte Weg, Code-First. Es erzeugt den Vertrag zur Laufzeit aus dem Spring-Code.

3. Details, die Interviewer fragen

  1. Aufbau: Ein Dokument hat openapi (Version), info, servers, paths und components (schemas, parameters, responses, securitySchemes). Dazu kommen security und tags. In 3.1 ist zusätzlich webhooks erlaubt.
  2. Swagger vs OpenAPI: OpenAPI ist die Spezifikation. Swagger ist der alte Name (bis 2.0). Heute ist es eine Tool-Familie (Swagger UI, Swagger Editor).
  3. OpenAPI 3.1 vs 3.0: 3.1 ist voll kompatibel mit JSON Schema 2020-12. nullable: true wird zu type: [string, 'null']. exclusiveMinimum ist eine Zahl statt Boolean. examples ist ein Array. Neu sind webhooks, und paths ist optional.
  4. Mindestinhalt 3.1: Ein Dokument braucht mindestens eines von paths, components oder webhooks. So kann eine Datei nur Schemas teilen.
  5. OpenAPI 3.2: 3.2.0 ist seit September 2025 veröffentlicht, die neueste Patch-Version ist 3.2.1. Es hat keine Breaking Changes gegenüber 3.1. Neu ist u. a. die Methode QUERY. Neu sind auch additionalOperations für eigene Methoden, itemSchema für Streaming (z. B. Server-Sent Events) und hierarchische Tags. Tools ziehen erst nach.
  6. $ref: Er verweist auf wiederverwendbare Teile, auch in anderen Dateien. So bleibt ein grosser Vertrag wartbar.
  7. operationId: Sie muss unter allen Operationen eindeutig sein. Tools dürfen sie nutzen, um eine Operation zu erkennen. Generatoren machen daraus oft den Methodennamen.
  8. Polymorphie: Man nutzt oneOf, anyOf und allOf mit discriminator. Generatoren unterstützen das unterschiedlich gut. Es ist ein häufiger Grund für hässlichen generierten Code.
  9. Contract-First (API-First): Zuerst kommt der Vertrag, dann der Code. Die Vorteile sind Review vor dem Bau, paralleles Arbeiten und stabile Clients. Die Nachteile sind Generator-Einschränkungen und YAML-Pflege.
  10. Code-First: Zuerst kommt der Code, der Vertrag entsteht daraus, z. B. mit springdoc. Das ist schnell für einzelne Teams. Das Risiko ist, dass jede Code-Änderung den Vertrag unbemerkt ändert.
  11. springdoc-openapi: Es scannt Spring-Controller. Es liefert /v3/api-docs (JSON, auch .yaml) und /swagger-ui.html. Der Starter ist springdoc-openapi-starter-webmvc-ui. Linie 2.x gilt für Spring Boot 3, Linie 3.x für Spring Boot 4. Die Standard-Ausgabe ist OpenAPI 3.1.
  12. springdoc in Produktion: springdoc.api-docs.enabled=false und springdoc.swagger-ui.enabled=false schalten die Endpunkte ab. Oder man gibt sie nur intern frei.
  13. OpenAPI Generator (spring): interfaceOnly=true erzeugt nur Interfaces und DTOs. delegatePattern=true trennt Controller und Logik. useSpringBoot3 ist Standard, useSpringBoot4 gibt es auch. useBeanValidation erzeugt @NotNull, @Pattern usw.
  14. Client-Generierung: Für Angular nimmt man z. B. typescript-angular. Für Java nimmt man java mit RestClient oder WebClient. Generierte Clients ändert man nicht von Hand.
  15. Contract-Tests: Es gibt drei Arten. Ein Provider-Test prüft gegen das Schema, z. B. mit Schemathesis (Property-Based, erzeugt viele Requests aus dem Vertrag). Consumer-Driven Contracts nutzen Pact oder Spring Cloud Contract. Ein Diff zwischen zwei Vertragsversionen nutzt oasdiff.
  16. Linting: Spectral prüft Regeln wie „jede Operation hat operationId“, „Fehler sind problem+json“ und „Pfade in kebab-case“.
  17. Security im Vertrag: securitySchemes beschreibt z. B. OAuth2 oder Bearer JWT. security pro Operation zeigt, welche Scopes nötig sind.

4. Fallen

  • „Swagger und OpenAPI sind dasselbe.“ → Ungenau. OpenAPI ist die Spezifikation, Swagger sind Tools (und der alte Name bis 2.0).
  • „In 3.1 schreibt man nullable: true.“ → Falsch. Das ist 3.0. In 3.1: type: [string, 'null'].
  • „springdoc erzeugt den Vertrag, also ist er immer korrekt.“ → Nur formal. Er beschreibt, was der Code tut, nicht was vereinbart war. Breaking Changes rutschen durch.
  • „Generierten Code kann man anpassen.“ → Falsch. Der nächste Build überschreibt ihn. Anpassen über Templates oder Konfiguration.
  • „OpenAPI 3.1 ist die neueste Version.“ → Veraltet. 3.2.0 ist seit September 2025 veröffentlicht, die neueste Patch-Version ist 3.2.1. Viele Tools nutzen aber noch 3.0 oder 3.1.
  • „Ein valider Vertrag heisst, die API ist gut.“ → Falsch. Validität prüft nur Syntax. Design prüft man mit Guidelines und Review.

5. Selbsttest

Warum?

Welche Vorteile hat Contract-First?

Review vor dem Bau, paralleles Arbeiten mit Mocks, stabile generierte Clients und ein klarer Vertrag.

Welche Nachteile hat Contract-First?

Mehr Anfangsaufwand, YAML-Pflege und Grenzen der Generatoren, z. B. bei Polymorphie.

Soll Swagger UI in Produktion laufen?

Meist nicht öffentlich. Abschalten mit springdoc.swagger-ui.enabled=false oder hinter Authentifizierung legen.

Wofür ist ein discriminator?

Er sagt bei oneOf oder anyOf, welches Feld den konkreten Typ bestimmt. Generatoren brauchen ihn für saubere Klassen.

Wie innen?

Was ist OpenAPI?

Eine Spezifikation, um HTTP-APIs maschinenlesbar in YAML oder JSON zu beschreiben. Aus dem Dokument entstehen Doku, Code, Mocks und Tests.

Was sind die Hauptteile eines OpenAPI-Dokuments?

openapi, info, servers, paths, components, security, tags, in 3.1 auch webhooks.

Was macht springdoc-openapi?

Es scannt Spring-Controller und liefert den Vertrag unter /v3/api-docs und die Swagger UI unter /swagger-ui.html.

Was macht interfaceOnly im Spring-Generator?

Es erzeugt nur API-Interfaces und Modelle, keine Controller. Der eigene Controller implementiert das Interface.

Wie beschreibt man null in OpenAPI 3.1?

Mit einem type-Array wie type: [string, 'null'].

Wie beschreibt man Security in OpenAPI?

Unter components.securitySchemes, z. B. oauth2 oder http bearer. Mit security pro Operation die nötigen Scopes.

Zahlen

Was ändert sich von 3.0 zu 3.1?

Volle JSON-Schema-2020-12-Kompatibilität: type-Arrays statt nullable, numerisches exclusiveMinimum, examples als Array. Dazu webhooks, und paths ist optional.

Was bringt OpenAPI 3.2?

Kompatibel zu 3.1. Neu u. a. QUERY-Methode, additionalOperations, itemSchema für Streaming und hierarchische Tags.

Welche springdoc-Version für welches Spring Boot?

springdoc 2.x für Spring Boot 3, springdoc 3.x für Spring Boot 4.

Wie viele Brüche hatte Build 43 im Beispiel?

Drei: ID als String, neuer Enum-Wert SHIPPED und Betrag als Float. Jeder davon bricht generierte Clients.

Vergleich

Was ist der Unterschied zwischen Swagger und OpenAPI?

OpenAPI ist die Spezifikation. Swagger war der Name bis Version 2.0 und ist heute eine Tool-Familie wie Swagger UI.

Contract-First oder Code-First?

Contract-First bei mehreren Consumern oder externen Partnern. Code-First für schnelle interne Services, dann aber mit Vertrags-Diff in der CI.

Was ist Consumer-Driven Contract Testing?

Consumer beschreiben, was sie vom Provider brauchen. Der Provider prüft in seiner CI, dass er diese Erwartungen erfüllt. Werkzeuge: Pact, Spring Cloud Contract.

Was ist AsyncAPI?

Das Gegenstück zu OpenAPI für Event-getriebene APIs, z. B. Kafka-Topics und Nachrichten-Schemas.

Produktion

Wie bindet man den Generator in den Build ein?

Mit dem openapi-generator Maven- oder Gradle-Plugin. Der Code entsteht bei jedem Build neu und wird nicht eingecheckt.

Was ist ein Contract-Test?

Ein Test, der prüft, ob echte Requests und Antworten zum Vertrag passen. Zum Beispiel Schema-Validierung oder Pact.

Wie erkennt man Breaking Changes im Vertrag?

Mit einem Diff-Tool wie oasdiff gegen den Stand auf main, als Pflicht-Check im PR.

Szenario: Das Frontend-Team beschwert sich, dass sich Felder ständig ändern. Was führen Sie ein?

Vertrag im Git, Diff gegen main in der CI, generierter TypeScript-Client und Contract-Tests. Breaking Changes nur mit Ankündigung oder neuer Version.

Szenario: Der generierte Java-Code ist für oneOf unbrauchbar. Was tun Sie?

Discriminator ergänzen, Modell vereinfachen oder für diesen Teil eigene Klassen schreiben. Den Generator nicht von Hand patchen.

Szenario: Ein Partner meldet, die Doku stimmt nicht mit der API überein. Wie verhindern Sie das künftig?

Eine Quelle der Wahrheit festlegen und automatisch prüfen: Contract-Test oder Schemathesis gegen den laufenden Service in der CI, Build rot bei Abweichung.

Design

Wie teilen Sie eine riesige OpenAPI-Datei auf?

Mit $ref in Dateien pro Ressource und einem Bündeln im Build. So gibt es weniger Merge-Konflikte.

Wann wählen Sie eine Mischform aus Code-First und Contract?

Bei bestehenden Services. Der erzeugte Vertrag wird ins Git exportiert und in der CI gegen main gedifft.

Warum den Betrag als String mit pattern beschreiben?

So verhindert man Rundungsfehler von Floats. Das ist eine bewusste Vertragsentscheidung.

Mehr

Gerüst

  • Warum? Ein maschinenlesbarer Vertrag zwischen Anbieter und Clients. Aus ihm entstehen Doku, Code, Mocks und Tests.
  • Wie innen? paths, components, $ref, securitySchemes. 3.1 nutzt JSON Schema 2020-12 (type: [string, 'null']). springdoc liest den Vertrag aus dem Code.
  • Zahlen 3.1: nullable weg, exclusiveMinimum als Zahl. 3.2 (September 2025) bricht nichts. springdoc 2.x für Spring Boot 3, 3.x für Spring Boot 4.
  • Vergleich Contract-First: Review vor dem Bau, mehr Aufwand. Code-First: schnell, Vertrag ändert sich still. Provider-Test vs Consumer-Driven (Pact).
  • Produktion Doku und Realität laufen auseinander. Swagger UI offen im Internet. Generierter Code von Hand geändert. Polymorphie ohne Discriminator.
  • Design Vertrag im Git, Spectral und oasdiff in der CI. Contract-Test macht ihn verbindlich. Betrag als String mit pattern.

Beispiel: ein Contract-Test fängt Breaking Changes

# Vertrag (Ausschnitt), OpenAPI 3.1
openapi: 3.1.1
info: { title: Order API, version: 1.4.0 }
paths:
  /orders/{id}:
    get:
      operationId: getOrder
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
components:
  schemas:
    Order:
      type: object
      required: [id, status, total]
      properties:
        id:     { type: integer }
        status: { type: string, enum: [NEW, PAID, CANCELLED] }
        total:  { type: string, pattern: '^[0-9]+\.[0-9]{2}$' }
        note:   { type: [string, 'null'] }     # 3.1: statt nullable: true
# contract_demo.py: Server pro "Build" starten, GET /orders/42, Antwort gegen Schema prüfen
contract_test("Build 41 (korrekt)       ", {"id": 42, "status": "NEW", "total": "49.90", "note": None})
contract_test("Build 42 (Feld umbenannt)", {"id": 42, "state": "NEW", "total": "49.90"})
contract_test("Build 43 (Typ geaendert) ", {"id": "42", "status": "SHIPPED", "total": 49.9})
Build 41 (korrekt)       : PASS  {"id": 42, "status": "NEW", "total": "49.90", "note": null}
Build 42 (Feld umbenannt): FAIL  {"id": 42, "state": "NEW", "total": "49.90"}
   - $.status: Pflichtfeld fehlt
Build 43 (Typ geaendert) : FAIL  {"id": "42", "status": "SHIPPED", "total": 49.9}
   - $.id: erwartet ['integer'], bekommen str
   - $.status: 'SHIPPED' nicht in ['NEW', 'PAID', 'CANCELLED']
   - $.total: erwartet ['string'], bekommen float

Echte Ausgabe, Python 3.12 (http.server + urllib, Vertrag als JSON im Skript, kleiner eigener Validator für type, required, enum, pattern). In echten Projekten macht das eine Bibliothek, z. B. ein JSON-Schema-Validator oder Schemathesis.

  1. Build 41 erfüllt den Vertrag. note: null ist erlaubt, weil der Typ [string, 'null'] ist.
  2. Build 42 hat status in state umbenannt. Für den Server ist das „nur ein Refactoring“. Der Test findet das fehlende Pflichtfeld.
  3. Build 43 hat drei Brüche: ID als String, neuer Enum-Wert SHIPPED, Betrag als Float. Jeder davon bricht generierte Clients.
  4. Betrag als String mit pattern verhindert Rundungsfehler von Floats. Das ist eine bewusste Vertragsentscheidung.

Vergleich

  • Contract-First: Vertrag zuerst, Review vor dem Bau, mehrere Teams parallel. Mehr Anfangsaufwand, Generator-Grenzen.
  • Code-First (springdoc): schnell, immer passend zum Code. Vertrag ändert sich still, Review erst nach dem Bau.
  • Mischform: Code-First, aber der erzeugte Vertrag wird ins Git exportiert und in der CI gegen main gedifft. Guter Kompromiss für bestehende Services.
  • OpenAPI vs AsyncAPI: OpenAPI für Request/Response über HTTP. AsyncAPI für Events, z. B. Kafka-Topics.
  • OpenAPI vs Protobuf/gRPC: Protobuf ist Vertrag und Serialisierung in einem, stark typisiert, binär. OpenAPI beschreibt JSON-APIs, die lesbar und browserfreundlich sind.
  • Provider-Contract vs Consumer-Driven: Provider prüft gegen sein Schema. Consumer-Driven prüft, was echte Clients wirklich nutzen. Das findet auch „erlaubte, aber schädliche“ Änderungen.

In der Produktion

  1. Doku und Realität laufen auseinander: Der Vertrag sagt integer, der Service liefert String. Lösung: Contract-Test in der CI, Vertrag als einzige Quelle.
  2. Generierter Code wird von Hand geändert: Beim nächsten Build ist alles weg. Lösung: Code in target/ generieren, nie einchecken, Anpassung über Templates oder Konfiguration.
  3. Swagger UI offen im Internet: verrät alle Endpunkte, auch interne. Lösung: in Produktion abschalten oder hinter Authentifizierung.
  4. Riesige YAML-Datei: Merge-Konflikte bei jedem PR. Lösung: mit $ref in Dateien pro Ressource aufteilen, im Build bündeln.
  5. Polymorphie bricht den Generator: oneOf ohne Discriminator erzeugt unbrauchbare Klassen. Lösung: Discriminator setzen oder Modell vereinfachen.
  6. Tools können 3.1 noch nicht ganz: Ein Gateway-Import oder Generator versteht type: [string, 'null'] nicht. Lösung: Tool-Support vorher prüfen, notfalls 3.0 ausgeben.

Diagnose: Werkzeuge und Befehle

  • curl -s localhost:8080/v3/api-docs | jq '.paths | keys': welche Pfade springdoc wirklich sieht.
  • Spectral (spectral lint openapi.yaml): Guideline-Verstösse in der CI.
  • oasdiff (oasdiff breaking main.yaml pr.yaml): Breaking Changes vor dem Merge.
  • Schemathesis: erzeugt Tests aus dem Vertrag und findet 500er und Schema-Abweichungen.
  • Prism (Stoplight): Mock-Server aus dem Vertrag, oder Proxy, der echte Antworten gegen den Vertrag prüft.
  • Swagger Editor: Syntax- und Strukturfehler direkt beim Schreiben.

Senior-Punkte

  1. Der Vertrag ist ein Produkt-Artefakt, nicht ein Nebenprodukt. Er wird versioniert, reviewt und getestet wie Code.
  2. Contract-First lohnt sich bei mehreren Consumern oder anderen Teams. Bei einem internen Service mit einem Client reicht oft Code-First mit Diff in der CI.
  3. Ein Vertrag ohne Test ist eine Behauptung. Erst Contract-Tests machen ihn verbindlich.
  4. Generatoren sind Werkzeuge, kein Architektur-Entscheid. Wenn der generierte Code das Design verbiegt, lieber nur DTOs generieren oder das Modell vereinfachen.
  5. Guidelines automatisieren: Spectral-Regeln statt Wiki-Seite. So bleiben viele Teams konsistent.
  6. Version bewusst wählen: 3.1 bringt echtes JSON Schema. 3.2 ist kompatibel, aber Tool-Support ist entscheidend. Vor dem Umstieg Generator, Gateway und Doku-Tool prüfen.
