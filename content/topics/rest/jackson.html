JSON mit Jackson

Kern: Jackson wandelt Java-Objekte in JSON um und zurück. Der ObjectMapper baut dafür pro Klasse einen Serializer und Deserializer aus Getter, Feldern und Annotations. In Jackson 2 ist FAIL_ON_UNKNOWN_PROPERTIES standardmässig an, in Jackson 3 aus.

Antwort-Muster

Frage: Wie wandelt Jackson ein Java-Objekt in JSON um und zurück?

  1. Mechanismus: Der ObjectMapper sucht Getter und Felder per Reflection und baut daraus einen Serializer, den er cached.
  2. Zahl: Jackson 2 bricht bei unbekannten JSON-Feldern ab. Jackson 3 ignoriert sie standardmässig.
  3. Trade-off: Strikt lesen findet Tippfehler früh. Tolerant lesen überlebt neue Felder des Servers.
  4. Produktion: Ich nutze einen geteilten ObjectMapper und prüfe Datumsformat und unbekannte Felder bewusst.

1. writeValueAsString() in 6 Schritten

  1. Aufruf: mapper.writeValueAsString(order) bekommt das Objekt. Der Mapper prüft zuerst seine Konfiguration (Features).
  2. Serializer suchen: Der Mapper schaut in einen Cache nach einem Serializer für die Klasse. Beim ersten Mal ist dort nichts.
  3. Eigenschaften finden: Beim ersten Mal untersucht Jackson die Klasse per Reflection. Es sammelt Getter, Felder und Annotations zu logischen Eigenschaften.
  4. Serializer bauen und cachen: Aus den Eigenschaften entsteht ein Bean-Serializer. Er wird im Cache abgelegt. Der nächste Aufruf überspringt Schritt 3.
  5. Tokens schreiben: Der Serializer schreibt über einen JsonGenerator der Reihe nach Objekt-Start, Feldname, Wert und Objekt-Ende.
  6. Werte wandeln: Zahlen, Strings und Booleans gehen direkt. Datum, Enum oder eigene Typen gehen über spezielle Serializer.

readValue() läuft gegenläufig. Ein JsonParser liest Tokens. Ein Deserializer ruft Konstruktor oder Setter und füllt die Felder. Unbekannte Felder lösen je nach Feature einen Fehler aus.

2. Aufbau

  1. jackson-core ist die Streaming-Ebene. JsonParser liest, JsonGenerator schreibt. Sie kennt keine Java-Klassen.
  2. jackson-annotations enthält nur die Annotations wie @JsonProperty. Sie ist ein eigenes Jar.
  3. jackson-databind enthält den ObjectMapper und bindet JSON an Java-Klassen.
  4. Module erweitern den Mapper um Typen. Beispiele sind Datums-Typen oder Kotlin-Klassen. Man registriert sie am Mapper.
  5. Tree Model: JsonNode hält JSON als Baum, ohne eigene Klasse. Gut für unbekannte Strukturen.
  6. Jackson 3: Neue Packages tools.jackson. Nur jackson-annotations behält com.fasterxml.jackson.annotation.

3. Details

  1. ObjectMapper wiederverwenden: Die Doku rät, einen Mapper zu erzeugen und für alle Aufrufe zu nutzen. Er cached Serializer und Deserializer. Ein neuer Mapper pro Request wirft diesen Cache weg.
  2. Jackson 2 und 3: Jackson 3 braucht Java 17. Group-ID und Packages heissen tools.jackson. jackson-annotations bleibt bei com.fasterxml.jackson.annotation. Spring Boot 4 nutzt Jackson 3 als Standard.
  3. Mapper in Jackson 3: ObjectMapper ist unveränderlich und entsteht über einen Builder. Es gibt JsonMapper. Exceptions sind unchecked (JacksonException).
  4. Unbekannte Felder: FAIL_ON_UNKNOWN_PROPERTIES ist in Jackson 2 standardmässig true. In Jackson 3 ist er false. Pro Klasse hilft @JsonIgnoreProperties(ignoreUnknown = true).
  5. Datum und Zeit: In Jackson 2 ist WRITE_DATES_AS_TIMESTAMPS standardmässig true. Für java.time braucht man dort das Modul jackson-datatype-jsr310. In Jackson 3 ist es in databind eingebaut und die Timestamps sind aus.
  6. Namen: @JsonProperty("first_name") setzt den JSON-Namen. @JsonAlias erlaubt beim Lesen weitere Namen. Eine globale Strategie wie Snake Case setzt man am Mapper.
  7. Ausblenden: @JsonIgnore blendet eine Eigenschaft beim Lesen und Schreiben aus. Für ein Passwort, das nur gelesen wird, nimmt man @JsonProperty(access = WRITE_ONLY).
  8. Null und Leeres: @JsonInclude(NON_NULL) lässt null-Felder weg. Es gibt auch NON_EMPTY. Für API-Verträge ist ein fehlendes Feld etwas anderes als ein Feld mit null.
  9. Konstruktor statt Setter: @JsonCreator wählt Konstruktor oder Factory zum Lesen. Records und unveränderliche Klassen brauchen das. Moderne Versionen erkennen Records von selbst.
  10. Polymorphie: @JsonTypeInfo schreibt einen Typ-Hinweis ins JSON. @JsonSubTypes listet die erlaubten Untertypen. Offene Typ-Angaben aus fremdem JSON sind ein Sicherheitsrisiko.
  11. Views: @JsonView wählt pro Anwendungsfall andere Felder. Zum Beispiel öffentlich und intern. Ein DTO pro Fall ist oft klarer.
  12. Primitive und null: FAIL_ON_NULL_FOR_PRIMITIVES ist in Jackson 2 false. Ein null im JSON wird dann zu 0. In Jackson 3 ist es true.

4. Fallen

  • „Jackson ignoriert unbekannte JSON-Felder immer.“ → Falsch. In Jackson 2 wirft es eine Exception. Erst Jackson 3 ignoriert sie standardmässig.
  • „Datumsfelder werden automatisch als ISO-Text geschrieben.“ → Falsch. Jackson 2 schreibt Timestamps und braucht das jsr310-Modul. Jackson 3 hat Timestamps aus.
  • „Jackson 3 ist nur ein Versions-Update.“ → Falsch. Group-ID und Packages ändern sich auf tools.jackson. Nur die Annotations behalten ihr Package.
  • „new ObjectMapper() pro Request ist harmlos.“ → Falsch. Der Mapper cached Serializer. Ein neuer pro Request verschenkt das. Einen teilen.
  • „@JsonIgnore versteckt ein Feld nur beim Schreiben.“ → Falsch. Es gilt für Lesen und Schreiben. Für nur-lesen nutzt man access = WRITE_ONLY.
  • „Ein fehlendes Zahlenfeld gibt in Jackson immer einen Fehler.“ → Falsch. Bei int setzt Jackson 2 still 0. Erst Jackson 3 meldet null für Primitive als Fehler.

5. Selbsttest

Warum?

Warum nutzt man Jackson statt JSON von Hand zu bauen?

Jackson bindet JSON automatisch an Java-Klassen. Das spart Code und Fehler bei Namen, Typen und Escaping.

Warum soll man den ObjectMapper wiederverwenden?

Er cached Serializer und Deserializer pro Klasse. Ein neuer Mapper muss alles neu aufbauen.

Warum liest man manchmal tolerant, manchmal strikt?

Tolerant überlebt neue Felder eines Servers. Strikt findet Tippfehler und falsche Verträge früh.

Wie innen?

Wie serialisiert Jackson ein Objekt?

Der Mapper holt einen Serializer aus dem Cache. Fehlt er, untersucht Jackson die Klasse per Reflection und baut ihn. Dann schreibt er Tokens über den JsonGenerator.

Wie liest Jackson JSON in ein Objekt?

Ein JsonParser liefert Tokens. Der Deserializer erzeugt das Objekt per Konstruktor oder Setter und füllt die Felder.

Was sind die Teile von Jackson?

jackson-core für Streaming, jackson-annotations für Annotations und jackson-databind für den ObjectMapper. Dazu kommen Module.

Was ist ein Modul?

Eine Erweiterung, die am Mapper registriert wird. Sie bringt zusätzliche Serializer, zum Beispiel für Datums-Typen.

Was ist das Tree Model?

JsonNode hält JSON als Baum. Man liest Felder ohne eigene Klasse. Das passt für wechselnde oder unbekannte Strukturen.

Zahlen

Was ist der Standard für unbekannte Felder?

Jackson 2 wirft eine Exception (FAIL_ON_UNKNOWN_PROPERTIES true). Jackson 3 ignoriert sie (false).

Wie schreibt Jackson 2 ein Datum standardmässig?

Als Zahl (Timestamp), weil WRITE_DATES_AS_TIMESTAMPS true ist. In Jackson 3 ist es false.

Welche Java-Version braucht Jackson 3?

Java 17. Spring Boot 4 nutzt Jackson 3 als Standard.

Was passiert mit null bei einem int-Feld?

Jackson 2 setzt 0, weil FAIL_ON_NULL_FOR_PRIMITIVES false ist. Jackson 3 meldet einen Fehler.

Vergleich

Jackson 2 vs Jackson 3?

Jackson 3 hat neue Packages (tools.jackson), unveränderliche Mapper, unchecked Exceptions und strengere Defaults. Annotations bleiben im alten Package.

Jackson vs Gson?

Beide binden JSON an Java. Jackson hat mehr Funktionen: Module, Streaming, Views, Polymorphie. Es ist der Standard in Spring.

Tree Model vs Data Binding?

Data Binding gibt typsichere Klassen. Das Tree Model ist flexibel, aber ohne Typen. Für feste Verträge nimmt man Klassen.

@JsonView vs eigene DTOs?

Views blenden Felder einer Klasse aus. DTOs sind getrennte Klassen. DTOs sind meist klarer und besser testbar.

Produktion

Was tun, wenn ein neues Feld vom Server den Client bricht?

Der Client liest in Jackson 2 strikt. Lösung: ignoreUnknown oder das Feature am Mapper ausschalten. So überlebt der Client neue Felder.

Warum sieht ein Datum plötzlich wie 1700000000000 aus?

Jackson 2 schreibt ohne Konfiguration Timestamps. Lösung: WRITE_DATES_AS_TIMESTAMPS ausschalten und das jsr310-Modul registrieren.

Warum verlieren JavaScript-Clients bei langen IDs Ziffern?

JavaScript speichert Zahlen als double. Sehr grosse Long-Werte verlieren Genauigkeit. Lösung: IDs als String senden.

Szenario: Nach einem Upgrade auf Spring Boot 4 gehen JSON-Antworten anders aus. Was prüfen Sie?

Boot 4 nutzt Jackson 3 mit anderen Defaults. Ich vergleiche Datumsformat, Null-Handling und Feldreihenfolge. Zum Übergang gibt es spring.jackson.use-jackson2-defaults.

Szenario: Ein Endpunkt nimmt JSON mit @JsonTypeInfo von aussen an. Was ist das Risiko?

Ein Angreifer wählt den Typ und kann gefährliche Klassen laden. Lösung: nur eine feste Liste erlaubter Untertypen zulassen.

Design

Szenario: Ihre API soll neue Felder später erlauben, ohne Clients zu brechen. Wie bauen Sie das?

Der Server darf Felder nur hinzufügen. Clients lesen tolerant und ignorieren Unbekanntes. Entfernen oder Umbenennen braucht eine neue Version.

Wie baut man ein unveränderliches DTO?

Ein Java-Record oder eine Klasse mit @JsonCreator. Dann gibt es keine Setter und das Objekt ist nach dem Lesen fertig.

Wie verbirgt man ein Passwort in der Antwort?

@JsonProperty(access = WRITE_ONLY) oder besser ein eigenes Antwort-DTO ohne das Feld.

Wie ändert man den Namensstil für die ganze API?

Am Mapper per Property-Naming-Strategie, zum Beispiel Snake Case. Einzelne Ausnahmen setzt man mit @JsonProperty.

Mehr

Gerüst

  • Warum? JSON an Java-Klassen binden, ohne von Hand zu parsen.
  • Wie innen? ObjectMapper baut pro Klasse Serializer aus Getter, Feldern, Annotations und cached sie. Core streamt, databind bindet.
  • Zahlen Jackson 2: Unbekannte Felder Fehler, Datum als Timestamp. Jackson 3: beides aus, Java 17, Package tools.jackson.
  • Vergleich Gson ist kleiner. Jackson hat Module, Views, Polymorphie und ist Spring-Standard.
  • Produktion Neues Feld bricht Client, Datum als Zahl, @JsonTypeInfo von aussen ist ein Risiko.
  • Design Ein geteilter Mapper, DTOs als Records, tolerant lesen, ISO-Datum, Version nur additiv ändern.

Beispiel: Ein Record mit Annotations

public record OrderDto(
    @JsonProperty("order_id") long id,
    String status,
    @JsonInclude(JsonInclude.Include.NON_NULL) String note,
    @JsonIgnore String internalCode) {}

// Jackson 2: new ObjectMapper().registerModule(new JavaTimeModule())
String json = mapper.writeValueAsString(new OrderDto(7, "PAID", null, "x"));
OrderDto back = mapper.readValue("{\"order_id\":7,\"status\":\"PAID\",\"extra\":1}", OrderDto.class);

Erwartetes Ergebnis laut Doku: json ist {"order_id":7,"status":"PAID"}. Das Feld note fehlt wegen NON_NULL. internalCode fehlt wegen @JsonIgnore. Beim Lesen wirft Jackson 2 wegen extra eine Exception, Jackson 3 ignoriert das Feld.

Nicht ausgeführt.

  1. order_id ist der JSON-Name, id der Java-Name.
  2. Null-Felder und ignorierte Felder erscheinen nicht im JSON.
  3. Das unbekannte Feld extra zeigt den Unterschied zwischen Jackson 2 und 3.

Vergleich

  • Jackson 2: Packages com.fasterxml.jackson, Java 8 reicht ab Version 2.13, veränderlicher Mapper, checked Exceptions.
  • Jackson 3: Packages tools.jackson, Java 17, unveränderlicher Mapper über Builder, unchecked Exceptions, java.time eingebaut.
  • Gson: kleine Bibliothek von Google. Weniger Funktionen, keine Module wie bei Jackson.
  • JSON-B (Jakarta): ein Standard für JSON-Binding. Jackson ist in der Praxis weiter verbreitet.
  • Streaming API: sehr schnell und sparsam im Speicher. Man verarbeitet Token für Token von Hand.
  • Tree Model: JsonNode für wechselnde Strukturen. Data Binding für feste Verträge.

Produktion

  1. Neues Feld bricht den Client: Jackson 2 wirft bei unbekannten Feldern. Lösung: tolerant lesen mit ignoreUnknown oder Feature aus.
  2. Datum als Zahl: Timestamps sind der Standard in Jackson 2. Lösung: Timestamps aus, jsr310-Modul registrieren, ISO-8601 nutzen.
  3. Stille Nullen: Ein fehlendes int-Feld wird 0. Lösung: FAIL_ON_NULL_FOR_PRIMITIVES einschalten oder Wrapper-Typen nutzen.
  4. Langsame Starts oder viel GC: Ein neuer Mapper pro Aufruf. Lösung: einen geteilten Mapper als Bean.
  5. Daten-Leck: Eine Entity geht direkt ins JSON und zeigt interne Felder. Lösung: eigene Antwort-DTOs.
  6. Unsichere Polymorphie: Typ-Angaben aus fremdem JSON. Lösung: feste Liste erlaubter Untertypen.

Diagnose: Werkzeuge und Befehle

  • Logs mit der Exception: Die Meldung nennt Feld und Pfad, zum Beispiel UnrecognizedPropertyException mit dem Namen des Felds.
  • Mapper ausgeben: Im Debugger die aktiven Features prüfen. Spring Boot setzt sie über spring.jackson.*.
  • Contract-Test mit echtem JSON: Beispieldateien einlesen und wieder schreiben. Das findet Name- und Datumsfehler.
  • Profiler oder Heap Dump: Viele ObjectMapper-Instanzen zeigen den Fehler 'Mapper pro Request'.
  • curl oder HTTP-Client: Die rohe Antwort ansehen. So sieht man, was wirklich über die Leitung geht.

Senior-Punkte

  1. Das Datenformat ist ein Vertrag. Namen, Datum und Null-Handling sind Teil der API. Ein Mapper-Update kann ihn ändern.
  2. Jackson 3 ist ein Migrationsprojekt. Neue Packages, neue Defaults, unchecked Exceptions. Man plant es, man tauscht es nicht nebenbei.
  3. Tolerant lesen, vorsichtig schreiben. Das erlaubt unabhängige Releases von Client und Server.
  4. Eigene DTOs statt Entities. So bleibt das JSON stabil, auch wenn die Datenbank sich ändert.
  5. Typ-Hinweise sind eine Sicherheitsgrenze. Offene Polymorphie aus fremdem JSON vermeiden.
  6. Ein Mapper, zentral konfiguriert. Dann verhalten sich alle Endpunkte gleich.
