Pagination, Filter, Sortierung

Kern: Pagination ist das Aufteilen einer grossen Liste in kleine Seiten, damit weder Server noch Client alles auf einmal laden. Es gibt zwei Hauptarten, nämlich Offset („überspringe 1000, nimm 20“) und Cursor/Keyset („nimm 20 nach diesem Schlüssel“). Filter und Sortierung gehören dazu, denn jede Seite braucht eine stabile, eindeutige Reihenfolge.

Antwort-Muster

Frage: Offset oder Cursor-Pagination?

  1. Mechanismus: Offset überspringt Zeilen, die DB liest sie aber trotzdem. Keyset filtert auf die Sortierwerte der letzten Zeile und springt im Index.
  2. Zahl: Bei 1 Mio. Zeilen braucht OFFSET 999980 etwa 10,84 ms. Keyset braucht 0,02 ms.
  3. Trade-off: Keyset ist schnell und stabil, kann aber nicht zu Seite N springen. Es braucht eine eindeutige Sortierung.
  4. Produktion: Ich nehme Keyset mit id als Tie-Breaker und setze ein Maximum für limit.

1. Die Reise durch eine lange Liste

  1. Seite 1: Der Client ruft GET /orders?limit=20. Beide Arten liefern die 20 neuesten Bestellungen.
  2. Offset, tiefe Seite: ?page=25000 wird zu OFFSET 500000. Die DB muss 500 000 Zeilen lesen und wegwerfen. Je tiefer, desto langsamer.
  3. Keyset, tiefe Seite: Der Cursor enthält die letzte Zeile der Vorseite, z. B. created_at und id. Die DB springt im Index direkt dorthin. Jede Seite ist gleich schnell.
  4. Neue Daten: Zwischen Seite 1 und 2 kommt eine neue Bestellung. Bei Offset rutscht alles um eins. Die letzte Zeile von Seite 1 erscheint auf Seite 2 nochmals.
  5. Keyset bleibt stabil: Seite 2 beginnt strikt nach dem Cursor. Keine Duplikate, keine Lücken.
  6. Preis: Keyset kann nicht zu „Seite 37“ springen. Für Infinite Scroll, Feeds und Exporte ist das egal.

2. Aufbau

  1. Client: schickt Filter, Sortierung und Seitengrösse als Query-Parameter. Beispiel: GET /orders?status=NEW&sort=-createdAt&limit=20.
  2. Controller: prüft alles. limit bekommt ein Maximum. Nur erlaubte Felder dürfen in Filter und Sortierung.
  3. Repository: baut SQL mit WHERE, ORDER BY und LIMIT.
  4. Datenbank: braucht einen Index, der zu Filter und Sortierung passt. Sonst sortiert sie alle Zeilen.
  5. Antwort: die Seite plus ein Verweis auf die nächste Seite, im Body oder im Link-Header (RFC 8288).

3. Details, die Interviewer fragen

  1. Offset-Pagination: Man schreibt ?page=3&size=20 oder ?offset=40&limit=20. Sie ist einfach und erlaubt Sprünge. Tiefe Seiten sind aber langsam. Bei Änderungen rutschen die Daten.
  2. Keyset-Pagination (Seek-Methode): Man filtert auf die Sortier-Spalten der letzten Zeile. In PostgreSQL nutzt man dafür einen Row-Value-Vergleich: WHERE (created_at, id) < ($1, $2). Der Index muss (created_at, id) sein.
  3. Row-Value-Vergleich: PostgreSQL vergleicht die Elemente von links nach rechts. Es stoppt beim ersten ungleichen oder NULL-Paar. Ist dieses Paar NULL, ist das Ergebnis unbekannt.
  4. Cursor-Pagination: Das ist die API-Sicht auf Keyset. Der Server packt die Schlüssel in einen opaken Cursor, z. B. Base64-JSON. Der Client gibt ihn nur zurück.
  5. Tie-Breaker: Die Sortierung muss eindeutig sein. ORDER BY created_at allein reicht nicht, wenn zwei Zeilen dieselbe Zeit haben. Darum hängt man immer id an.
  6. Cursor-Inhalt: Er enthält Sortierwerte, Richtung und oft die Filter. Ändert der Client die Filter, ist der alte Cursor ungültig (400). Ein signierter Cursor verhindert Manipulation.
  7. Zurückblättern: Man dreht die Sortierung um und nimmt > statt <. Dann dreht man das Ergebnis wieder um. Viele APIs bieten nur „vorwärts“.
  8. NULL in Sortierspalten: Sie stören Keyset, weil Vergleiche mit NULL nicht wahr sind. Spring Data warnt davor. Die Lösung ist NOT NULL oder COALESCE.
  9. Total Count: COUNT(*) braucht eine zweite Abfrage über alle Treffer. In PostgreSQL ist sie wegen MVCC (jede Transaktion sieht ihre eigene Version) nicht gratis. Alternativen sind hasMore, eine geschätzte Zahl (pg_class.reltuples oder EXPLAIN) oder Count nur auf Wunsch (?includeTotal=true).
  10. reltuples: Das ist eine Schätzung des Planers für die Zeilenzahl. VACUUM, ANALYZE und manche DDL-Befehle aktualisieren sie. Wurde die Tabelle nie analysiert, steht dort -1.
  11. hasMore billig: Man holt LIMIT 21 und zeigt 20. Gibt es die 21. Zeile, gibt es eine nächste Seite. Spring Data macht das für Slice und Window so (limit + 1).
  12. Spring Data: Page<T> löst eine zusätzliche Count-Query aus. Slice<T> tut das nicht. Window<T> mit ScrollPosition unterstützt Offset und Keyset.
  13. Limits: Man setzt immer ein Maximum für limit. Sonst holt ein Client mit ?size=1000000 die ganze Tabelle (OWASP API4).
  14. Sortierung: Üblich ist ?sort=-createdAt,id (Minus = absteigend). Spring nutzt ?sort=createdAt,desc. Erlaubt sind nur Felder aus einer Allowlist, die einen Index haben.
  15. Filter einfach: Man schreibt ?status=NEW&customerId=7. Mehrere Werte gehen mit ?status=NEW,PAID. Bereiche gehen mit ?createdAfter=2026-01-01.
  16. Filter mit Operatoren: Es gibt LHS-Klammern ?price[gte]=10, RSQL/FIQL ?filter=status==NEW;price=gt=10 und OData $filter. Das ist mächtig. Jeder freie Filter braucht aber Index-Planung.
  17. Suche mit vielen Kriterien: Bei zu langen URLs nimmt man POST /orders/search mit Body. Sauberer ist die neue Methode QUERY (RFC 10008).
  18. Konsistenz: Keine Pagination ist ein Snapshot. Für exakte Exporte nimmt man eine Snapshot-Tabelle oder einen Export-Job. Oder man nutzt Keyset über unveränderliche Daten.

4. Fallen

  • „Mit Index ist OFFSET schnell.“ → Falsch. Der Index hilft beim Sortieren, aber die DB muss die übersprungenen Zeilen trotzdem durchlaufen.
  • „ORDER BY created_at reicht für Keyset.“ → Falsch. Ohne eindeutigen Tie-Breaker wie id gehen Zeilen verloren oder kommen doppelt.
  • „COUNT(*) ist in PostgreSQL billig.“ → Falsch. Wegen MVCC muss es sichtbare Zeilen prüfen. Bei grossen Tabellen kostet es spürbar.
  • „Cursor-Pagination liefert einen Snapshot.“ → Falsch. Sie ist stabil gegen Verschiebung, zeigt aber neue Zeilen, die nach dem Cursor liegen.
  • „Der Client kann den Cursor selbst bauen.“ → Schlecht. Der Cursor ist ein internes Format. Clients dürfen ihn nur zurückgeben.
  • „Spring Page ist kostenlos.“ → Falsch. Page löst eine zweite Count-Query aus. Slice nicht.

5. Selbsttest

Warum?

Warum wird OFFSET bei tiefen Seiten langsam?

Die DB muss alle übersprungenen Zeilen lesen und verwerfen. Die Kosten wachsen linear mit dem Offset.

Warum braucht Keyset einen Tie-Breaker?

Ohne eindeutige Sortierung sind Zeilen mit gleichem Wert nicht klar geordnet. Dann gehen Zeilen verloren oder kommen doppelt.

Warum soll der Cursor opak sein?

Der Server kann das Format ändern, ohne Clients zu brechen. Und Clients können keine ungültigen Positionen bauen.

Warum ist der Total Count teuer?

Er braucht eine zweite Abfrage über alle Treffer. In PostgreSQL ist COUNT(*) wegen MVCC nicht aus Metadaten lesbar.

Wie innen?

Wie funktioniert Keyset-Pagination?

Die nächste Seite filtert auf die Sortierwerte der letzten Zeile: WHERE (created_at, id) < (letzter Wert). Ein passender Index macht das zu einem direkten Sprung.

Was steht in einem Cursor?

Die Sortierwerte der letzten Zeile, oft auch Richtung und Filter. Kodiert, zum Beispiel Base64, und für den Client opak.

Wie macht man Zurückblättern mit Keyset?

Sortierung und Vergleich umdrehen, LIMIT anwenden, Ergebnis wieder umdrehen.

Was passiert mit NULL-Werten bei Keyset?

Vergleiche mit NULL sind nie wahr, Zeilen fallen heraus. Darum Sortierspalten NOT NULL oder mit COALESCE.

Was ist Window in Spring Data?

Ein Ergebnis für Scrolling mit ScrollPosition, offset- oder keyset-basiert. Es weiss, ob es mehr Daten gibt.

Zahlen

Warum braucht limit ein Maximum?

Ohne Grenze kann ein Client riesige Antworten anfordern. Das kostet Speicher und DB-Zeit und ist ein DoS-Risiko.

Wie viel langsamer wird OFFSET im Beispiel mit 1 Mio. Zeilen?

Von 0,01 ms auf 10,84 ms bei OFFSET 999980, also etwa 1000-mal. Keyset bleibt bei 0,02 ms.

Wie viele Zeilen holt man für hasMore?

Eine mehr als die Seitengrösse, also LIMIT 21 bei Seitengrösse 20. Gibt es die 21. Zeile, gibt es eine nächste Seite.

Vergleich

Offset- oder Cursor-Pagination?

Offset für kleine Daten und Sprünge zu Seite N. Cursor/Keyset für grosse oder sich ändernde Daten, Feeds und Exporte.

Welche Probleme hat Offset bei Änderungen?

Neue oder gelöschte Zeilen verschieben alles. Einträge erscheinen doppelt oder werden übersprungen.

Was ist der Nachteil von Keyset?

Kein Sprung zu Seite N, keine Seitenzahl. Die Sortierung muss eindeutig sein und einen passenden Index haben.

Page oder Slice in Spring Data?

Page enthält Total und Seitenzahl, kostet eine Count-Query. Slice weiss nur, ob es weitergeht, und spart die Count-Query.

Wo gibt man den Link zur nächsten Seite zurück?

Im Body als next oder im Link-Header mit rel="next" nach RFC 8288.

Produktion

Szenario: Die Listen-API wird mit der Zeit langsamer, besonders hinten. Was prüfen Sie?

EXPLAIN der Offset-Query und den Count. Lösung: Keyset mit passendem Index, Slice statt Page, Maximum für page.

Szenario: Ein Partner meldet Duplikate und fehlende Einträge beim nächtlichen Abgleich. Warum?

Offset-Paging während paralleler Inserts. Lösung: Keyset auf einem unveränderlichen, eindeutigen Schlüssel, oder ein Export-Job mit Snapshot.

Szenario: Das Produkt will „Treffer: 1 234 567“ auf jeder Seite. Was antworten Sie?

Ein exakter Count kostet bei jeder Seite eine volle Abfrage. Vorschlag: Schätzung oder „mehr als 10 000“, exakte Zahl nur auf Klick oder gecacht.

Design

Was sind Alternativen zum Total Count?

hasMore über LIMIT n+1, eine Schätzung, Count nur auf Wunsch oder ein gecachter Wert.

Wie gestaltet man Sortier-Parameter?

Zum Beispiel ?sort=-createdAt,id. Nur Felder aus einer Allowlist, die einen Index haben.

Welche Filter-Syntax würden Sie wählen?

Einfache Felder als Query-Parameter für die häufigen Fälle. Operatoren wie price[gte] oder RSQL nur, wenn nötig, und dann mit Allowlist.

Was tun bei sehr komplexen Suchen?

POST auf eine Such-Ressource mit Body, oder die neue QUERY-Methode. Oder eine Suchmaschine für Volltext.

Mehr

Gerüst

  • Warum? Grosse Listen in kleinen Seiten liefern. Stabile Seiten brauchen eine eindeutige Sortierung.
  • Wie innen? Keyset: WHERE (created_at, id) < (?, ?) + Index, ein direkter Sprung. Offset: die DB liest alle übersprungenen Zeilen. Der Cursor ist opak.
  • Zahlen 1 Mio. Zeilen: OFFSET 0,01 ms → 10,84 ms, Keyset 0,02 ms. LIMIT 21 für hasMore. Maximum für limit.
  • Vergleich Offset: Sprung zu Seite N, Duplikate bei Änderungen. Keyset: konstant schnell, kein Sprung. Page: 2 Queries, Slice: 1 Query.
  • Produktion Crawler auf Seite 50 000. Count teurer als die Seite. Duplikate in Exporten bei parallelen Inserts.
  • Design Default Keyset mit Tie-Breaker id. Total Count nur auf Wunsch. Sortierfelder per Allowlist mit Index.

Beispiel: Offset gegen Keyset mit 1 Mio. Zeilen

# paging_demo.py (gekürzt): sqlite3, Tabelle orders mit 1 000 000 Zeilen
CREATE INDEX ix_created ON orders(created_at, id)

OFFSET = "SELECT id, created_at FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET ?"
KEYSET = ("SELECT id, created_at FROM orders WHERE (created_at, id) < (?, ?) "
          "ORDER BY created_at DESC, id DESC LIMIT 20")
# Cursor = (created_at, id) der letzten Zeile der Vorseite
1) Zeit pro Seite (Mittel aus 20 Läufen)
   OFFSET       0:    0.01 ms
   OFFSET   10000:    0.12 ms
   OFFSET  500000:    5.33 ms
   OFFSET  999980:   10.84 ms
   KEYSET tief  :    0.02 ms  (gleiche Zeilen wie OFFSET 999980: True)
2) Query-Plan
   OFFSET: SCAN orders USING COVERING INDEX ix_created
   KEYSET: SEARCH orders USING COVERING INDEX ix_created (created_at<?)
3) COUNT(*) kostet
   COUNT(*) WHERE status='NEW': 66.61 ms
4) Neue Zeile zwischen Seite 1 und 2
   Seite 1 letzte id: 999981
   OFFSET Seite 2 erste id: 999981  -> doppelt: True
   KEYSET Seite 2 erste id: 999980  -> doppelt: False

Echte Ausgabe, Python 3.12 mit sqlite3 (SQLite 3.49, In-Memory). Absolute Zeiten sind klein, weil alles im RAM liegt. Wichtig ist das Wachstum.

  1. Offset wird linear langsamer: von 0,01 ms auf ca. 11 ms, rund 1000-mal. Keyset bleibt bei 0,02 ms, auch ganz hinten.
  2. Beide liefern auf der letzten Seite die gleichen Zeilen. Keyset ist also korrekt.
  3. Der Plan zeigt den Unterschied: Offset macht SCAN (Index von vorne durchlaufen). Keyset macht SEARCH (direkt springen).
  4. Ein COUNT(*) mit Filter ohne passenden Index kostet mehr als 3000 Keyset-Seiten.
  5. Nach einem Insert zeigt Offset die id 999981 doppelt. Keyset nicht.

Vergleich

  • Offset/Page: Sprung zu jeder Seite, „Seite 3 von 50“. Langsam bei tiefen Seiten, Duplikate und Lücken bei Änderungen. Gut für Admin-Tabellen mit wenig Daten.
  • Keyset/Cursor: konstant schnell, stabil bei Änderungen. Kein Sprung zu Seite N, eindeutige Sortierung und passender Index nötig. Gut für Feeds, Infinite Scroll, Sync und Exporte.
  • Page (Spring): Inhalt + Total. Zwei Queries.
  • Slice (Spring): Inhalt + „gibt es mehr?“. Eine Query.
  • Link-Header vs Body-Felder: Header hält den Body sauber und ist ein Standard (RFC 8288). Body-Felder sind für Frontends leichter zu lesen.
  • Exakter Count vs Schätzung: Exakt kostet eine volle Abfrage. Schätzung ist schnell, aber ungenau. „Mehr als 10 000“ reicht oft.

In der Produktion

  1. Crawler blättert bis Seite 50 000: DB-CPU steigt, alle Requests werden langsam. Lösung: Keyset oder ein Maximum für page.
  2. Count-Query teurer als die Seite: Jede Listenansicht zählt Millionen Zeilen. Lösung: Slice statt Page, Count nur auf Wunsch, Schätzung oder gecachter Wert.
  3. Duplikate und fehlende Einträge in Exporten: Offset plus parallele Inserts. Lösung: Keyset mit eindeutigem Schlüssel.
  4. Sortierung ohne Index: ?sort=lastName zwingt die DB, alles zu sortieren. Lösung: Allowlist für Sortierfelder, je ein passender Index.
  5. Unbegrenztes limit: Ein Client holt 1 Mio. Zeilen in einer Antwort, der Pod läuft aus dem Speicher (OOM). Lösung: Maximum serverseitig erzwingen.
  6. Instabile Sortierung: Ohne Tie-Breaker liefert die DB gleiche Werte in zufälliger Reihenfolge. Einträge springen zwischen Seiten. Lösung: id als letztes Sortierfeld.

Diagnose: Werkzeuge und Befehle

  • EXPLAIN (ANALYZE, BUFFERS) SELECT … OFFSET 500000 LIMIT 20 (PostgreSQL): zeigt, wie viele Zeilen gelesen und verworfen werden.
  • pg_stat_statements: findet die teuersten Queries. Count- und Offset-Queries stehen oft oben.
  • Gateway-Logs: Verteilung von page- und size-Werten. Sehr hohe Werte deuten auf Crawler oder Exporte.
  • Hibernate SQL-Log (spring.jpa.show-sql oder Logger org.hibernate.SQL): zeigt die zusätzliche Count-Query eines Page.
  • APM/Tracing: Latenz pro Endpoint nach Seitentiefe aufschlüsseln.

Senior-Punkte

  1. Default Keyset, Offset nur bei Bedarf. Wenn Nutzer wirklich zu „Seite 7“ springen müssen und die Daten klein sind, ist Offset okay.
  2. Der Cursor ist opak. So kann der Server später das Verfahren ändern, ohne Clients zu brechen.
  3. Total Count ist ein Produkt-Entscheid. Fragen: Braucht der Nutzer die exakte Zahl? Oft reicht „mehr als 1000“ oder „es gibt weitere“.
  4. Filter und Sortierung sind Index-Design. Jede erlaubte Kombination braucht einen Plan. Freie Filter ohne Index sind ein DoS-Risiko.
  5. Grenzen sind Sicherheit: maximales limit, maximale Filterzahl, Timeouts. Das gehört in den API-Vertrag.
  6. Grosse Exporte sind kein Paging-Problem. Dafür gibt es asynchrone Export-Jobs mit 202 und Download-Link.
