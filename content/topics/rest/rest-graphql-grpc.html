REST vs GraphQL vs gRPC

Kern: REST modelliert Ressourcen mit URLs und HTTP-Methoden. GraphQL hat einen Endpunkt, und der Client wählt die Felder der Antwort. gRPC ruft typisierte Methoden über HTTP/2 mit Protocol Buffers auf.

Antwort-Muster

Frage: Wann nehmen Sie REST, GraphQL oder gRPC?

  1. Mechanismus: REST ist ressourcenorientiert über HTTP. GraphQL lässt den Client Felder wählen. gRPC ruft generierte Methoden binär über HTTP/2 auf.
  2. Zahl: gRPC sendet jede Nachricht mit 5 Byte Präfix und braucht HTTP/2. GraphQL kennt drei Operationen: query, mutation, subscription.
  3. Trade-off: REST nutzt HTTP-Caching, ist aber oft over- oder underfetching. GraphQL spart Requests, macht Caching und Limits schwerer. gRPC ist schnell, aber im Browser nicht direkt nutzbar.
  4. Produktion: Für eine öffentliche API nehme ich REST. Für mobile Clients mit vielen Sichten nehme ich GraphQL. Für interne Calls mit Streaming nehme ich gRPC.

1. Ein Aufruf bei jedem Stil, in 6 Schritten

  1. Client: Er braucht die Daten einer Bestellung und wählt je nach API einen der drei Wege.
  2. REST: GET /orders/7. Die URL nennt die Ressource, die Methode die Aktion. Der Server wählt den Umfang der Antwort.
  3. GraphQL: Meist ein POST an einen einzigen Endpunkt mit einer Query. Der Client nennt die gewünschten Felder.
  4. gRPC: Ein POST auf den Pfad /Service/Methode über HTTP/2. Der Body ist eine Protobuf-Nachricht mit Längen-Präfix.
  5. Server: REST ruft einen Controller. GraphQL ruft Resolver pro Feld. gRPC ruft die generierte Service-Methode.
  6. Antwort: REST und GraphQL senden meist JSON. gRPC sendet Protobuf und beendet den Aufruf mit einem Status in den Trailern.

Die Wahl betrifft den Vertrag zwischen Teams. Sie ist kein reines Technik-Thema.

2. Aufbau

  1. REST beschreibt man oft mit OpenAPI. Clients nutzen Statuscodes, Header und Caching von HTTP.
  2. GraphQL hat ein typisiertes Schema. Es erlaubt Introspection, also Fragen an das Schema selbst.
  3. gRPC definiert Services und Messages in einer .proto-Datei. Daraus entstehen Client- und Server-Code.
  4. Transport: Die GraphQL-Spezifikation legt keinen Transport fest. In der Praxis ist es HTTP. gRPC braucht HTTP/2.
  5. Streaming: gRPC hat vier Methodenarten. GraphQL hat Subscriptions. REST nutzt dafür etwas wie SSE oder WebSockets.
  6. Fehler: REST nutzt Statuscodes. GraphQL liefert errors neben data. gRPC liefert Status in den Trailern.

3. Details

  1. REST und HTTP-Semantik: Methoden wie GET, PUT und DELETE haben definierte Bedeutung. Caches, Proxys und Gateways verstehen sie. Das ist der Hauptvorteil.
  2. Overfetching und Underfetching: Eine feste REST-Antwort liefert zu viel oder zu wenig. Dann braucht der Client mehrere Aufrufe. GraphQL löst das über die Feldauswahl.
  3. GraphQL-Operationen: query liest, mutation schreibt, subscription liefert Daten bei Ereignissen. Das sind die drei Typen der Spezifikation.
  4. GraphQL-Ausführung: Mutations im obersten Level laufen in Reihenfolge. Felder einer Query dürfen parallel laufen.
  5. GraphQL-Fehler: Ein Fehler in einem Feld wird wie null behandelt. Ein Non-Null-Feld reicht den Fehler an das Elternfeld weiter. Die Antwort kann so Teildaten und Fehler enthalten.
  6. GraphQL-Schema: Felder sind standardmässig nullable. Mit ! sind sie non-null. Das Schema entwickelt man weiter, ohne Versionen, und markiert Altes als deprecated.
  7. N+1-Problem: Ein Resolver pro Listeneintrag löst pro Eintrag eine Datenbankabfrage aus. DataLoader bündelt solche Abfragen. Ohne das ist GraphQL langsam.
  8. gRPC-Aufbau: HTTP/2, POST, Pfad /Service/Methode, Content-Type application/grpc. Jede Nachricht hat ein Byte für Kompression und 4 Byte Länge.
  9. gRPC-Status: Der Status kommt immer in den Trailern, auch bei Erfolg. Der HTTP-Status ist bei gRPC-Antworten 200.
  10. gRPC-Methoden: Unary, Server Streaming, Client Streaming und Bidirectional Streaming. Die Reihenfolge der Nachrichten in einem Aufruf ist garantiert.
  11. Deadlines: Ein gRPC-Client kann ein Zeitlimit setzen. Läuft es ab, endet der Aufruf mit DEADLINE_EXCEEDED. Eine Abbruch-Meldung macht bisherige Änderungen nicht rückgängig.
  12. Protobuf-Felder: Jedes Feld hat eine Nummer. Nummern werden nie wiederverwendet. Gelöschte Nummern setzt man auf reserved. Fehlende Felder haben den Standardwert, bei Zahlen 0.
  13. gRPC im Browser: Browser nutzen gRPC-Web über einen Proxy wie Envoy.

4. Fallen

  • „GraphQL ist schneller als REST.“ → Falsch. Es spart Requests, aber jeder Resolver kann langsam sein. Ohne DataLoader droht das N+1-Problem.
  • „GraphQL braucht keine Versionen und keine Limits.“ → Falsch. Man entwickelt das Schema additiv. Clients können aber teure Queries bauen. Tiefe und Kosten braucht Limits.
  • „gRPC läuft direkt im Browser.“ → Falsch. Browser brauchen gRPC-Web und einen Proxy wie Envoy.
  • „gRPC-Fehler stehen im HTTP-Status.“ → Falsch. Der HTTP-Status ist 200. Der gRPC-Status steht in den Trailern.
  • „Ein GraphQL-Fehler heisst immer, dass die ganze Antwort leer ist.“ → Falsch. Fehler können Teildaten liefern. Nur wenn alles bis zur Wurzel non-null ist, ist data null.
  • „Man kann Protobuf-Nummern nach dem Löschen frei wiederverwenden.“ → Falsch. Nie. Das führt zu falsch gelesenen Daten. Gelöschte Nummern gehen auf reserved.

5. Selbsttest

Warum?

Warum hat sich GraphQL entwickelt?

Clients wollten genau die Felder bekommen, die sie brauchen, in einem Aufruf. REST-Endpunkte lieferten oft zu viel oder zu wenig.

Warum nutzt man gRPC zwischen Services?

Binäre Nachrichten, generierte Clients, Streaming und Deadlines. Das passt für interne Aufrufe mit vielen Requests.

Warum bleibt REST so verbreitet?

Es nutzt HTTP direkt. Caching, Proxys, Gateways, Tools und Clients sind überall vorhanden.

Wie innen?

Wie sieht ein gRPC-Aufruf auf der Leitung aus?

Ein HTTP/2-POST auf /Service/Methode mit Content-Type application/grpc. Jede Nachricht hat 1 Byte Kompressions-Flag und 4 Byte Länge. Am Ende kommt der Status in den Trailern.

Wie läuft eine GraphQL-Query intern?

Der Server prüft die Query gegen das Schema. Dann ruft er Resolver pro Feld auf und baut das Ergebnis im Format der Query.

Wie behandelt GraphQL Fehler in Feldern?

Der Fehler wird wie null behandelt. Bei Non-Null-Feldern geht er zum Elternfeld. Die Antwort kann Teildaten und ein errors-Array haben.

Was ist ein Resolver?

Eine Funktion, die den Wert eines Felds liefert. Sie kann aus einer Datenbank oder einem anderen Service lesen.

Was ist ein Protobuf-Schema?

Eine .proto-Datei mit Messages und Services. Aus ihr werden Klassen und Stubs für viele Sprachen erzeugt.

Zahlen

Welche drei Operationstypen kennt GraphQL?

query, mutation und subscription.

Wie viele Methodenarten hat gRPC?

Vier: unary, server streaming, client streaming und bidirectional streaming.

Wie gross ist der Präfix einer gRPC-Nachricht?

5 Byte. Ein Byte für das Kompressions-Flag und vier Byte für die Länge.

Welche Protobuf-Feldnummern brauchen nur ein Byte?

Die Nummern 1 bis 15. Häufige Felder bekommen darum diese Nummern.

Vergleich

REST vs GraphQL beim Caching?

REST nutzt URL und HTTP-Caching direkt. GraphQL hat meist einen Endpunkt und POST, daher braucht es eigenes Caching, zum Beispiel über Objekt-IDs.

REST vs gRPC bei Performance?

gRPC ist binär und nutzt HTTP/2, meist kompakter und schneller. REST ist lesbarer und leichter zu debuggen.

Versionierung bei REST und GraphQL?

REST nutzt oft Versionen in URL oder Header. GraphQL entwickelt das Schema ohne Versionen und markiert Altes als deprecated.

GraphQL vs gRPC bei Streaming?

GraphQL hat Subscriptions für Ereignisse. gRPC hat vier Methodenarten mit echtem Streaming in beide Richtungen.

Produktion

Warum ist GraphQL bei Listen plötzlich langsam?

Wahrscheinlich das N+1-Problem. Pro Eintrag läuft eine Abfrage. Lösung: DataLoader oder Joins im Resolver bündeln.

Warum bricht ein gRPC-Aufruf im Browser?

Browser sprechen kein gRPC direkt. Man braucht gRPC-Web und einen Proxy wie Envoy.

Szenario: Ein Client schickt eine sehr tiefe GraphQL-Query und der Server hängt. Was tun Sie?

Limits für Tiefe und Kosten, Timeouts und erlaubte Queries. Ausserdem DataLoader gegen N+1. Lange Queries sind ein Missbrauchsrisiko.

Szenario: gRPC-Calls hängen, wenn ein Backend langsam ist. Wie sichern Sie das ab?

Immer Deadlines setzen und weitergeben. Dann endet der Aufruf mit DEADLINE_EXCEEDED statt endlos zu warten. Dazu Retries nur bei idempotenten Aufrufen.

Design

Szenario: Eine öffentliche API für Partner. Was wählen Sie?

REST mit OpenAPI. Partner kennen es, HTTP-Caching und Gateways funktionieren, und es braucht keine Spezialwerkzeuge.

Szenario: Eine Mobile App braucht je Bildschirm andere Felder aus vielen Services. Was wählen Sie?

GraphQL als Schicht vor den Services. Die App holt pro Bildschirm genau die Felder. Mit DataLoader und Limits gegen Missbrauch.

Szenario: Zwei interne Services tauschen viele kleine Nachrichten mit Streaming. Was wählen Sie?

gRPC. Binär, schnell, mit Streaming und Deadlines. Der .proto-Vertrag gibt beiden Seiten generierten Code.

Kann man die Stile mischen?

Ja. Oft nutzt man gRPC intern, GraphQL oder REST an der Aussengrenze. Ein Gateway übersetzt dazwischen.

Mehr

Gerüst

  • Warum? Passenden Vertrag zwischen Client und Server wählen.
  • Wie innen? REST: Ressourcen über HTTP. GraphQL: ein Endpunkt, Feldauswahl. gRPC: HTTP/2, Protobuf, 5-Byte-Frames.
  • Zahlen 3 GraphQL-Operationen, 4 gRPC-Methodenarten, 5 Byte Frame-Präfix, Protobuf-Nummern 1 bis 15 sparen ein Byte.
  • Vergleich REST cachet über HTTP. GraphQL spart Requests. gRPC ist schnell, im Browser braucht es gRPC-Web.
  • Produktion N+1 bei GraphQL, teure Queries ohne Limits, gRPC ohne Deadline, kein Browser-Support.
  • Design Öffentlich REST, mobile Sichten GraphQL, intern gRPC. Ein Gateway verbindet die Welten.

Beispiel: Dieselbe Anfrage in drei Stilen

# REST
GET /orders/7
-> 200 {"id":7,"status":"PAID","items":[...],"customer":{...}}   (alles, was der Server wählt)

# GraphQL (ein Endpunkt, der Client wählt Felder)
POST /graphql
{ "query": "query { order(id: 7) { status customer { name } } }" }
-> 200 {"data":{"order":{"status":"PAID","customer":{"name":"Muster AG"}}}}

# gRPC (.proto)
service Orders { rpc Get(GetOrderRequest) returns (Order); }
message GetOrderRequest { int64 id = 1; }
message Order { int64 id = 1; string status = 2; }

Nicht ausgeführt. Die Antworten zeigen nur die Form.

  1. REST liefert die Ressource, wie der Server sie definiert.
  2. GraphQL liefert genau status und customer.name.
  3. gRPC nutzt Feldnummern (= 1, = 2). Sie stehen im binären Format.

Vergleich

  • REST: Ressourcen, HTTP-Methoden, HTTP-Caching, OpenAPI. Gut für öffentliche und einfache APIs.
  • GraphQL: ein Endpunkt, Feldauswahl, typisiertes Schema, Introspection. Gut für Clients mit wechselnden Sichten.
  • gRPC: HTTP/2, Protobuf, Codegenerierung, Streaming, Deadlines. Gut für interne Service-Aufrufe.
  • Lesbarkeit: REST und GraphQL sind JSON und leicht zu prüfen. gRPC ist binär und braucht Werkzeuge.
  • Browser: REST und GraphQL direkt. gRPC nur über gRPC-Web mit Proxy.
  • Fehlermodell: HTTP-Status bei REST. errors-Array bei GraphQL. Status in Trailern bei gRPC.

Produktion

  1. N+1 in GraphQL: Ein Resolver pro Eintrag. Lösung: DataLoader und Batching.
  2. Teure Queries: Ein Client baut tief verschachtelte Abfragen. Lösung: Limits für Tiefe und Kosten, Timeouts.
  3. Kein Caching bei GraphQL: Alles geht an einen POST-Endpunkt. Lösung: eigenes Caching mit Objekt-IDs oder persistierte Queries.
  4. gRPC ohne Deadline: Aufrufe hängen, wenn ein Backend langsam ist. Lösung: Deadline überall setzen und weitergeben.
  5. Proxy versteht gRPC nicht: Ein alter Load Balancer kennt kein HTTP/2 mit Trailern. Lösung: einen passenden Proxy wählen.
  6. Protobuf-Nummer wiederverwendet: Alte Clients lesen Daten falsch. Lösung: reserved nutzen.

Diagnose: Werkzeuge und Befehle

  • curl: für REST und GraphQL. curl -X POST -d '{"query":"..."}' URL.
  • GraphQL-Introspection und Playground: zeigt das Schema und testet Queries.
  • grpcurl: ruft gRPC-Methoden auf der Kommandozeile auf, wenn der Server Reflection anbietet.
  • Tracing pro Resolver: zeigt, welches Feld langsam ist.
  • Proxy- und Server-Logs: zeigen HTTP/2-Fehler und Statuscodes.

Senior-Punkte

  1. Die Wahl ist eine Teamfrage. Wer konsumiert die API, und wer kann sie betreiben?
  2. REST ist der sichere Standard, wenn es keinen klaren Grund für etwas anderes gibt.
  3. GraphQL verschiebt Komplexität zum Server. Limits, DataLoader und Caching gehören dazu.
  4. gRPC lohnt sich intern, mit klarem Vertrag und Deadlines. Nach aussen ist es unbequem.
  5. Gateways verbinden die Stile. Aussen REST oder GraphQL, innen gRPC.
  6. Verträge entwickelt man additiv. In allen drei Stilen darf man Felder hinzufügen. Entfernen oder Umnummerieren bricht Clients.
