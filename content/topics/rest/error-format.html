Fehlerformat: Problem Details (RFC 9457)

Kern: Problem Details ist ein einheitliches JSON-Format für Fehler einer HTTP-API. Es hat die Felder type, title, status, detail und instance und den Media Type application/problem+json. Clients erkennen den Fehler am type, nicht am Text.

Antwort-Muster

Frage: Wie gibt eine REST-API Fehler zurück?

  1. Mechanismus: Der Server sendet den richtigen HTTP-Status und einen Body im Format Problem Details mit type, title, status, detail und instance.
  2. Zahl: Das Format steht in RFC 9457. Ohne type gilt about:blank, dann ist der title der Standardtext des Statuscodes.
  3. Trade-off: Ein eigenes Format ist schneller gebaut. Der Standard spart Clients den Aufwand, jede API neu zu verstehen.
  4. Produktion: Ich gebe nie Stack Traces aus. Ich logge die Fehler-ID und gebe sie in instance oder einem Extension-Feld mit.

1. Ein Fehler vom Server zum Client, in 6 Schritten

  1. Fehler: Im Code wird eine Exception geworfen, zum Beispiel OrderNotFoundException.
  2. Zentral fangen: Ein zentraler Handler fängt sie ab. In Spring ist das ein @ControllerAdvice, oft auf Basis von ResponseEntityExceptionHandler.
  3. Problem bauen: Der Handler füllt type, title, status und detail. In Spring dient dafür die Klasse ProblemDetail.
  4. Extensions ergänzen: Eigene Felder wie errors oder traceId kommen dazu. Clients müssen unbekannte Extensions ignorieren.
  5. Senden: Der HTTP-Status der Antwort ist derselbe wie im Feld status. Der Content-Type ist application/problem+json.
  6. Client liest: Er schaut zuerst auf den HTTP-Status. Dann nutzt er type als Kennung des Problems. Er parst detail nicht.

Das Feld status im Body ist nur ein Hinweis. Massgebend ist immer der HTTP-Status der Antwort.

2. Aufbau

  1. type ist eine URI-Referenz und die Hauptkennung des Problem-Typs. Fehlt sie, gilt about:blank.
  2. title ist ein kurzer Text. Er soll sich von Fall zu Fall nicht ändern, ausser durch Übersetzung.
  3. status ist der HTTP-Code. Der Hinweis im Body ändert den echten Status nicht.
  4. detail erklärt diesen einen Fall für Menschen. Clients sollen ihn nicht parsen.
  5. instance ist eine URI-Referenz für genau dieses Auftreten. Sie ist oft eine Fehler-ID.
  6. Extensions sind eigene Mitglieder. Beispiele sind errors mit Feldfehlern oder traceId.

3. Details

  1. Media Types: application/problem+json für JSON und application/problem+xml für XML. Der Client kann den Typ über Content Negotiation anfordern.
  2. type als Hauptkennung: Clients müssen die type-URI als primäre Kennung nutzen. Maschinen entscheiden anhand von type, nicht anhand von title oder detail.
  3. Default about:blank: Fehlt type, heisst das nichts über den Statuscode hinaus. Dann soll der title der übliche Text des Codes sein.
  4. Dereferenzieren: Eine type-URI kann auf eine Doku-Seite zeigen. Clients sollen sie aber nicht automatisch aufrufen.
  5. status ist nur ein Hinweis: Der Server muss denselben Code im HTTP-Status senden. Zwischenschichten können den Status ändern.
  6. Extension-Regel: Eigene Felder sind erlaubt. Clients müssen unbekannte Extensions ignorieren. So kann man Felder später ergänzen.
  7. Validierungsfehler: Das Beispiel der RFC nutzt eine Extension errors mit detail und einem JSON Pointer pro Fehler. Der Pointer zeigt auf das fehlerhafte Feld.
  8. Generische Fehler: Die RFC sagt, allgemeine Bedingungen drückt man oft besser nur mit einem Statuscode aus. Ein eigener type lohnt sich für fachliche Fehler.
  9. Sicherheit: Keine Implementierungsdetails wie Stack Dumps in die Antwort. Das hilft Angreifern. Details gehören ins Log.
  10. RFC 7807 und 9457: RFC 9457 ersetzt RFC 7807. Das Format bleibt gleich. Die Neufassung ergänzt unter anderem ein Register für gängige Problem-Typen.
  11. Spring: ProblemDetail bildet das Format ab. ErrorResponse ist der Vertrag für Exceptions. Alle Spring-MVC-Exceptions implementieren ihn. Mit spring.mvc.problemdetails.enabled behandelt Boot die eingebauten Exceptions als Problem Details.
  12. Extensions in Spring: Mit setProperty füllt man die Map properties. Spring Framework schreibt sie als Felder auf oberster Ebene ins JSON.

4. Fallen

  • „Das Feld status im Body ersetzt den HTTP-Status.“ → Falsch. Es ist nur ein Hinweis. Der HTTP-Status der Antwort zählt.
  • „Clients sollen detail parsen, um den Fehler zu erkennen.“ → Falsch. Sie sollen type nutzen. Daten für Maschinen gehören in Extensions.
  • „Jede API braucht ihr eigenes Fehlerformat.“ → Falsch. Es gibt einen Standard (RFC 9457). Ein eigenes Format zwingt jeden Client zu Sonderlogik.
  • „Ein Stack Trace im detail hilft dem Entwickler.“ → Falsch. Er verrät Interna. Gib eine Fehler-ID zurück und logge den Trace.
  • „Immer HTTP 200 mit Fehler im Body ist einfacher.“ → Falsch. Dann sehen Caches, Monitoring und Clients keinen Fehler. Der Statuscode muss stimmen.
  • „RFC 9457 ist ein ganz neues Format gegenüber RFC 7807.“ → Falsch. 9457 ersetzt 7807 und bleibt kompatibel. Die Felder sind gleich.

5. Selbsttest

Warum?

Warum ein Standardformat für Fehler?

Clients können Fehler aller APIs gleich lesen. Bibliotheken und Gateways verstehen das Format.

Warum nicht nur den HTTP-Status senden?

Der Status sagt nur die Klasse des Fehlers. Der Body erklärt den genauen Grund und liefert Details wie Feldfehler.

Warum gehört der Fehler in einen eigenen Media Type?

Der Client erkennt am Content-Type application/problem+json sofort, dass es ein Fehlerobjekt ist.

Wie innen?

Welche Felder hat Problem Details?

type, title, status, detail und instance. Alle sind optional. Dazu kommen beliebige Extensions.

Was bedeutet about:blank?

Das ist der Standardwert von type. Er bedeutet keine zusätzliche Semantik über den Statuscode hinaus.

Wofür ist instance?

Es identifiziert genau dieses Auftreten des Problems, zum Beispiel mit einer Fehler-ID.

Wie erweitert man das Format?

Mit eigenen Mitgliedern, zum Beispiel errors. Clients müssen unbekannte Extensions ignorieren.

Wie arbeitet das in Spring?

ProblemDetail ist die Klasse. Ein @ControllerAdvice mit ResponseEntityExceptionHandler fängt Exceptions und rendert sie als application/problem+json.

Zahlen

Welchen Statuscode nimmt man bei Validierungsfehlern?

Üblich sind 400 oder 422. Wichtig ist, dass die API es einheitlich macht und im Body die Felder nennt.

Wie heisst der Media Type?

application/problem+json. Für XML application/problem+xml.

Welche RFC-Nummer gilt heute?

RFC 9457. Sie ersetzt RFC 7807.

Wie viele Felder sind Pflicht?

Keines. Alle fünf Standardfelder sind optional.

Vergleich

Problem Details vs eigenes Fehlerformat?

Der Standard ist wiederverwendbar und bekannt. Ein eigenes Format ist frei, aber jeder Client muss es lernen.

Problem Details vs GraphQL-Fehler?

GraphQL liefert Fehler in einem errors-Array neben data, oft mit HTTP 200. Problem Details nutzt den HTTP-Status.

Problem Details vs gRPC-Status?

gRPC hat eigene Status-Codes in den Trailern. Problem Details gilt für HTTP-APIs.

Fehlercode im title vs type?

Der type ist die stabile Kennung für Maschinen. Der title ist Text für Menschen und kann übersetzt werden.

Produktion

Warum zeigt die API einem Angreifer interne Pfade?

Ein Stack Trace oder Exception-Text steht im detail. Lösung: nur Fehler-ID in die Antwort, Trace ins Log.

Warum zeigt der Client 'Unbekannter Fehler'?

Der Server sendet ein anderes Format als erwartet, etwa HTML von einem Proxy. Lösung: Content-Type prüfen und Fallback auf den Status.

Szenario: Support fragt nach einem Kundenfehler von gestern. Was bauen Sie ein?

Eine Fehler-ID oder trace-ID in instance oder einer Extension. Sie steht auch im Log. So findet der Support die Zeile in Sekunden.

Szenario: Mobile Apps zeigen Fehlertexte, die Sie ändern wollen. Was tun Sie?

Die App entscheidet über type und zeigt ihren eigenen Text. So kann der Server title und detail ändern, ohne die App zu brechen.

Design

Szenario: Ihre API hat 30 fachliche Fehlerarten. Wie benennen Sie die types?

Eine stabile URI pro Fehlerart, zum Beispiel unter der eigenen Domain. Ein kurzer Doku-Text steht dort. Der type ändert sich nie.

Wie meldet man mehrere Feldfehler gleichzeitig?

Eine Extension errors mit einem Eintrag pro Feld. Jeder Eintrag hat pointer und detail, wie im RFC-Beispiel.

Wo setzt man die Fehlerbehandlung in Spring?

Zentral in einem @ControllerAdvice. Eigene Handler müssen vor dem Handler von Boot kommen, dessen Order 0 ist.

Soll man title übersetzen?

Ja, das ist erlaubt. Der title soll sonst gleich bleiben. Maschinen nutzen type, nicht title.

Mehr

Gerüst

  • Warum? Ein einheitliches Fehlerformat, das jeder Client lesen kann.
  • Wie innen? Fünf optionale Felder plus Extensions. Der type ist die Kennung. Status im Body ist nur ein Hinweis.
  • Zahlen RFC 9457 ersetzt RFC 7807. Media Type application/problem+json. Default about:blank.
  • Vergleich Eigenes Format ist frei. GraphQL liefert Fehler in errors. gRPC hat eigene Status-Codes.
  • Produktion Stack Trace in der Antwort, anderes Format von Proxys, Support ohne Fehler-ID.
  • Design Zentraler Handler, stabile type-URIs, Fehler-ID in instance, Details nur ins Log.

Beispiel: Eine 422-Antwort mit Feldfehlern

HTTP/1.1 422
Content-Type: application/problem+json

{ "type": "https://example.test/problems/validation-error",
  "title": "Your request is not valid.",
  "status": 422,
  "detail": "2 fields are invalid.",
  "instance": "/orders",
  "errors": [ { "pointer": "#/quantity", "detail": "must be greater than 0" },
              { "pointer": "#/email",    "detail": "must be a valid address" } ] }
HTTP status      : 422
Content-Type     : application/problem+json
status im Body   : true
Body             : {"type":"https://example.test/problems/validation-error","title":"Your request is not valid.","status":422,"detail":"2 fields are invalid.","instance":"/orders","errors":[{"pointer":"#/quantity","detail":"must be greater than 0"},{"pointer":"#/email","detail":"must be a valid address"}]}
Client erkennt Problem Details: true

Echte Ausgabe, Java 17.0.3 (kleiner Eigenbau-Server mit com.sun.net.httpserver). Das Format ist von Hand geschrieben, nicht von Spring erzeugt.

  1. Der HTTP-Status ist 422. Das Feld status im Body zeigt dieselbe Zahl.
  2. Der Content-Type ist application/problem+json. Daran erkennt der Client das Format.
  3. type ist die Kennung für Maschinen. Hier eine Beispiel-URI.
  4. errors ist eine Extension mit je einem Pointer und einem Text pro Feld.
@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handle(OrderNotFoundException ex) {
  ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
  pd.setProperty("orderId", ex.getOrderId());   // erscheint als Feld auf oberster Ebene
  return pd;
}

Nicht ausgeführt (Spring-Variante).

Vergleich

  • Problem Details: Standard für HTTP-APIs. Status plus strukturierter Body.
  • Eigenes JSON: freie Felder wie code und message. Schnell, aber nicht wiederverwendbar.
  • GraphQL-Fehler: Array errors neben data. Teilerfolge sind möglich.
  • gRPC: Status-Code und Meldung in den Trailern, nicht im Body.
  • HTML-Fehlerseite: für Menschen im Browser. Für APIs ungeeignet.
  • Nur Statuscode: reicht bei allgemeinen Fehlern wie 404 oder 401.

Produktion

  1. Interna in der Antwort: Stack Trace oder SQL-Text im detail. Lösung: generischer Text, Fehler-ID, Trace nur im Log.
  2. Inkonsistente Fehler: Jeder Controller baut sein eigenes JSON. Lösung: ein zentraler Handler.
  3. Clients parsen Text: Sie suchen Wörter im detail. Lösung: stabile type-URIs und Extensions für Maschinendaten.
  4. Falscher Statuscode: 200 bei Fehler oder 500 bei Validierung. Lösung: den passenden 4xx-Code wählen.
  5. Proxy sendet HTML: Der Client erwartet JSON und stürzt ab. Lösung: Content-Type prüfen, Fallback auf den Status.
  6. Fehlerflut im Log: Jeder 404 loggt einen Trace. Lösung: Client-Fehler ohne Trace loggen.

Diagnose: Werkzeuge und Befehle

  • curl -i: zeigt Status, Content-Type und Body der Fehlerantwort.
  • Log-Suche nach der Fehler-ID: findet die Server-Zeile zu einer Kundenmeldung.
  • Distributed Tracing: die trace-ID als Extension mitgeben und im Tracing-Tool nachschlagen.
  • Contract-Test: prüft, dass jede Fehlerantwort den richtigen Content-Type und die Pflichtfelder hat.
  • OpenAPI-Beschreibung: die Fehlerantworten mit Schema dokumentieren, damit Clients es kennen.

Senior-Punkte

  1. Fehler sind Teil der API. Sie brauchen denselben Vertrag und dieselbe Versionierung wie Erfolgsantworten.
  2. type ist die stabile Kennung. Man ändert sie nie. title und detail darf man umformulieren.
  3. Nichts Internes nach aussen. Details gehören ins Log. Die Antwort trägt nur eine ID.
  4. Ein Handler für alles. So sieht jeder Fehler gleich aus, auch aus Frameworks und Filtern.
  5. Generische Fehler brauchen keinen eigenen type. Eigene types nur für fachliche Fehler, auf die ein Client reagiert.
  6. Das Format macht den Fehler maschinenlesbar, aber den Entscheid, was der Nutzer sieht, trifft der Client.
