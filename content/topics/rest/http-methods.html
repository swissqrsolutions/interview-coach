HTTP-Methoden: sicher und idempotent

Kern: Eine HTTP-Methode ist das Verb eines Requests, also was der Client mit der Ressource will. RFC 9110 gibt jeder Methode zwei Eigenschaften, nämlich sicher (nur lesen) und idempotent (Wiederholen ändert nichts mehr). Davon hängen Caches, automatische Retries und das API-Design ab.

Antwort-Muster

Frage: Was ist der Unterschied zwischen sicher und idempotent?

  1. Mechanismus: Sicher heisst, der Client verlangt keine Änderung. Idempotent heisst, mehrere gleiche Requests haben denselben beabsichtigten Effekt wie einer.
  2. Zahl: GET, HEAD, OPTIONS und TRACE sind sicher. PUT und DELETE sind idempotent, POST und PATCH nicht.
  3. Trade-off: Idempotente Requests darf ein Client nach einem Timeout automatisch wiederholen. POST braucht dafür einen Idempotency-Key.
  4. Produktion: Ich schalte Retries im Gateway nur für idempotente Methoden ein.

1. Die Reise einer Bestellung

  1. POST anlegen: Der Client schickt POST /orders. Der Server vergibt die ID. Er antwortet mit 201 Created und dem Header Location: /orders/1.
  2. Timeout: Die Antwort geht verloren. Der Client weiss nicht, ob die Bestellung existiert. Ein blindes Retry erzeugt eine zweite Bestellung. Lösung: ein Idempotency-Key-Header, den der Server speichert.
  3. GET lesen: GET /orders/1 liefert 200 und ein ETag, also eine Versionskennung der Ressource.
  4. PATCH ändern: Der Client schickt nur die geänderten Felder. Mit If-Match: "etag" verhindert er, dass er fremde Änderungen überschreibt.
  5. PUT ersetzen: Der Client schickt die ganze Ressource. Zweimal senden ergibt denselben Zustand.
  6. DELETE löschen: Der erste Aufruf liefert 204. Der zweite liefert 404. Der Zustand ist gleich: Die Bestellung ist weg. Das ist idempotent.

2. Aufbau

  1. Client: wählt die Methode. Beispiel: GET /orders/42 liest eine Bestellung.
  2. Proxy oder Cache: speichert Antworten nur für sichere Methoden, praktisch GET und HEAD.
  3. API Gateway oder HTTP-Client: wiederholt nach einem Timeout nur idempotente Requests automatisch.
  4. Service: muss die versprochene Semantik einhalten. Ein GET, das Daten ändert, bricht alle Schichten davor.
  5. Datenbank: setzt die Idempotenz um, z. B. mit Upsert oder eindeutigem Schlüssel.

3. Details, die Interviewer fragen

  1. Sicher (safe): Eine Methode ist sicher, wenn der Client keine Zustandsänderung verlangt. RFC 9110 nennt GET, HEAD, OPTIONS und TRACE. Logging oder Zähler auf dem Server sind trotzdem erlaubt. Der Client ist dafür nicht verantwortlich.
  2. Idempotent: Mehrere gleiche Requests haben denselben beabsichtigten Effekt wie einer. Das gilt für PUT, DELETE und alle sicheren Methoden. Die Antwort darf sich unterscheiden.
  3. Warum Idempotenz zählt: RFC 9110 erlaubt, idempotente Requests nach einem Verbindungsfehler automatisch zu wiederholen. Nicht-idempotente wie POST soll ein Client nicht automatisch wiederholen. Eine Ausnahme ist, wenn er weiss, dass es sicher ist (z. B. mit Idempotency-Key).
  4. GET: Es liest eine Repräsentation. Ein Body im GET hat keine definierte Semantik. Manche Server lehnen ihn ab. Komplexe Suchen gehen per POST oder neu per QUERY.
  5. HEAD: Es ist wie GET, aber ohne Body. Es eignet sich, um Grösse oder ETag zu prüfen.
  6. POST: Es ist der Allzweck. Man legt damit eine Ressource ohne bekannte ID an. Man gibt damit auch Daten an einen Prozess. Oder man löst eine Aktion aus. Bei einer Anlage kommt 201 mit Location.
  7. PUT: Es ersetzt die ganze Ressource an einer bekannten URI. Neu angelegt gibt es 201. Geändert gibt es 200 oder 204. Fehlende Felder bedeuten „leer“, nicht „unverändert“.
  8. PATCH (RFC 5789): Es ändert nur Teile. PATCH ist weder sicher noch idempotent. Der Server muss alle Änderungen atomar anwenden. Bei Konflikt-Gefahr soll der Client If-Match mit ETag senden.
  9. JSON Merge Patch (RFC 7396): Der Media Type ist application/merge-patch+json. Das Patch-Dokument sieht aus wie die Ressource. null löscht ein Feld. Arrays werden immer ganz ersetzt. Man kann keinen Wert auf null setzen.
  10. JSON Patch (RFC 6902): Der Media Type ist application/json-patch+json. Es ist ein Array von Operationen: add, remove, replace, move, copy, test. Pfade sind JSON Pointer wie /items/0/qty. Scheitert eine Operation, scheitert das ganze Dokument.
  11. test-Operation: Sie prüft einen Wert vor der Änderung, z. B. {"op":"test","path":"/status","value":"NEW"}. Das ist optimistisches Locking im Patch selbst.
  12. DELETE: Es entfernt die Zuordnung der URI. Die Antwort ist 204 (fertig, kein Body), 200 (mit Statusbeschreibung) oder 202 (noch nicht ausgeführt).
  13. OPTIONS: Es fragt die Fähigkeiten einer Ressource ab. Browser nutzen es für den CORS-Preflight.
  14. QUERY (RFC 10008, Juni 2026): Das ist eine neue Methode mit Body. Sie ist sicher und idempotent. Sie löst „GET mit Body“ sauber. Die Unterstützung in Frameworks und Proxys ist noch jung.
  15. QUERY und Cache: Die Antwort auf QUERY ist cachebar. Der Cache-Key enthält den Body des Requests. Der Header Accept-Query nennt die erlaubten Body-Formate.
  16. Idempotency-Key: Das ist ein Header für POST und PATCH. Er ist noch ein IETF-Draft. Der Server speichert Key und Antwort. Gleicher Key mit anderem Body gibt 422. Läuft das Original noch, gibt es 409. Ein fehlender Key gibt 400.
  17. Cachebar: GET- und HEAD-Antworten sind cachebar. POST-Antworten sind es nur mit expliziter Frische und passendem Content-Location. In der Praxis cacht niemand POST.

4. Fallen

  • „Idempotent heisst, die Antwort ist immer gleich.“ → Falsch. Der beabsichtigte Zustand ist gleich. DELETE liefert erst 204, dann 404.
  • „PATCH ist idempotent.“ → Falsch. RFC 5789: weder sicher noch idempotent. Ein Patch wie „füge Element an“ ändert bei jedem Aufruf.
  • „PUT ist zum Ändern, POST zum Anlegen.“ → Zu einfach. PUT kann anlegen (201), wenn der Client die URI kennt. POST kann auch Aktionen auslösen.
  • „Sicher heisst, der Server darf nichts schreiben.“ → Falsch. Logs und Statistiken sind erlaubt. Der Client verlangt nur keine Änderung.
  • „In Merge Patch setzt null ein Feld auf null.“ → Falsch. null löscht das Feld.
  • „GET mit Body ist verboten.“ → Ungenau. Der Body hat keine definierte Semantik. Clients sollen ihn nicht senden, Server können ihn ablehnen.

5. Selbsttest

Warum?

Warum ist POST nicht idempotent?

Jeder POST kann eine neue Ressource oder Aktion erzeugen. Zwei gleiche POST können zwei Bestellungen anlegen.

Warum ist DELETE idempotent, obwohl der zweite Aufruf 404 liefert?

Idempotenz betrifft den Zustand, nicht die Antwort. Nach beiden Aufrufen ist die Ressource weg.

Darf ein Gateway einen fehlgeschlagenen POST wiederholen?

Nicht automatisch. RFC 9110: Nicht-idempotente Requests soll man nur wiederholen, wenn man weiss, dass es sicher ist, z. B. dank Idempotency-Key.

Ist ein PUT, der einen Zähler erhöht, idempotent?

Nein. Die Methode verspricht Idempotenz, der Code bricht sie. Solche Aktionen gehören in POST.

Wie innen?

Was bedeutet „sichere Methode“?

Der Client verlangt keine Zustandsänderung, die Methode ist im Kern nur lesend. Laut RFC 9110: GET, HEAD, OPTIONS, TRACE.

Was bedeutet „idempotent“?

Mehrere gleiche Requests haben denselben beabsichtigten Effekt wie einer. Idempotent sind PUT, DELETE und alle sicheren Methoden.

Ist jede sichere Methode idempotent?

Ja. Wer nichts ändert, ändert auch beim zehnten Mal nichts. Umgekehrt gilt es nicht: PUT ist idempotent, aber nicht sicher.

Was ist JSON Merge Patch?

RFC 7396, Media Type application/merge-patch+json. Das Patch sieht aus wie die Ressource, null löscht ein Feld, Arrays werden ganz ersetzt.

Was ist JSON Patch?

RFC 6902, application/json-patch+json. Eine Liste von Operationen (add, remove, replace, move, copy, test) mit JSON-Pointer-Pfaden. Scheitert eine, scheitert alles.

Was macht die test-Operation?

Sie prüft einen Wert vor den Änderungen. Stimmt er nicht, wird das ganze Patch nicht angewendet.

Wofür ist HEAD gut?

Metadaten ohne Body holen, z. B. Content-Length oder ETag prüfen.

Zahlen

Welche Statuscodes liefert PUT?

201 beim Anlegen. 200 oder 204 beim Ersetzen. Das verlangt RFC 9110.

Welche Statuscodes liefert DELETE?

204 ohne Body, 200 mit Statusbeschreibung oder 202, wenn das Löschen noch nicht ausgeführt ist.

Was antwortet der Server bei unbekanntem Patch-Format?

415 Unsupported Media Type, am besten mit Accept-Patch, das die erlaubten Formate nennt.

Was passiert bei gleichem Idempotency-Key mit anderem Body?

Der Draft empfiehlt 422. Läuft der Original-Request noch, empfiehlt er 409.

Vergleich

PUT oder PATCH?

PUT ersetzt die ganze Ressource und ist idempotent. PATCH ändert nur Teile und ist nicht garantiert idempotent.

PUT oder POST zum Anlegen?

PUT, wenn der Client die URI bestimmt. POST, wenn der Server die ID vergibt. Antwort jeweils 201.

Wann JSON Patch statt Merge Patch?

Wenn man einzelne Array-Elemente ändern, ein Feld explizit auf null setzen oder vorher mit test prüfen will.

Was ist die QUERY-Methode?

RFC 10008: eine sichere und idempotente Methode mit Body. Sie ersetzt das Muster „POST für Suchen“.

Sind POST-Antworten cachebar?

Nur mit expliziter Frische und Content-Location gleich der Ziel-URI. In der Praxis werden sie nicht gecacht.

Produktion

Wie macht man POST idempotent?

Mit einem Idempotency-Key-Header. Der Server speichert Key und Antwort und liefert bei Wiederholung dieselbe Antwort.

Wie verhindert man Lost Updates bei PUT oder PATCH?

Mit ETag und If-Match. Hat sich die Ressource geändert, antwortet der Server 412 Precondition Failed.

Szenario: Kunden zahlen manchmal doppelt. Woran denken Sie?

An Retries bei POST nach Timeout, im Client oder Gateway. Lösung: Idempotency-Key, Unique Constraint auf die Zahlungs-ID, Retries im Gateway nur für idempotente Methoden.

Szenario: Nach einem PUT eines Mobile-Clients fehlen Felder. Warum?

Der Client schickt nur geänderte Felder per PUT. PUT ersetzt alles, fehlende Felder werden leer. Lösung: PATCH mit Merge Patch oder volle Repräsentation senden.

Szenario: Zwei Sachbearbeiter ändern dieselbe Akte, eine Änderung verschwindet. Was tun Sie?

Lost Update. ETag bei GET liefern, If-Match bei PUT/PATCH verlangen, bei Abweichung 412. Optional 428 Precondition Required, wenn If-Match fehlt.

Design

Darf ein GET einen Body haben?

Ein Body hat keine definierte Semantik. Clients sollen ihn nicht senden, Server und Proxys können ihn ablehnen.

Wofür ist OPTIONS gut?

Fähigkeiten einer Ressource abfragen. Browser senden es als CORS-Preflight vor nicht-einfachen Requests.

Wie legen Sie das PATCH-Format in Ihrer API fest?

Merge Patch für einfache Objekte, JSON Patch für Listen und präzise Operationen. Das Format gehört in den Vertrag (OpenAPI), sonst rät der Server die Semantik von null.

Mehr

Gerüst

  • Warum? Caches, Retries und API-Design hängen an der Semantik. Sicher = nur lesen. Idempotent = Wiederholen ändert nichts mehr.
  • Wie innen? GET, HEAD, OPTIONS, TRACE sind sicher. PUT, DELETE und alle sicheren Methoden sind idempotent. POST und PATCH sind es nicht.
  • Zahlen POST anlegen: 201 + Location. PUT: 201 neu, 200 oder 204 ersetzt. DELETE: 204, dann 404. Falsches Patch-Format: 415.
  • Vergleich PUT ersetzt alles, PATCH ändert Teile. Merge Patch: einfach, null löscht. JSON Patch: Operationen, kann alles.
  • Produktion Retry bei POST → Doppelbuchung. Lost Update → ETag + If-Match, 412. GET mit Seiteneffekt trifft einen Crawler.
  • Design Idempotency-Key für POST. Patch-Format in den OpenAPI-Vertrag. Komplexe Suchen: POST oder QUERY.

Beispiel: Methoden-Semantik live

# methods_demo.py (gekürzt): http.server + urllib, ohne Bibliotheken
def do_POST(self):                 # neue ID pro Aufruf
    i = str(next(ids)); orders[i] = self.body()
    self.send(201, orders[i], Location=f"/orders/{i}")
def do_PUT(self):                  # ersetzt komplett
    i = self.oid(); existed = i in orders
    orders[i] = self.body()
    self.send(200 if existed else 201, orders[i])
def do_PATCH(self):                # nur application/merge-patch+json
    if self.headers["Content-Type"] != "application/merge-patch+json":
        return self.send(415, Accept_Patch="application/merge-patch+json")
    orders[i] = merge_patch(orders[i], self.body())   # null = Feld löschen
def do_DELETE(self):
    self.send(204) if orders.pop(self.oid(), None) is not None else self.send(404)

Echte Ausgabe, Python 3.12 (http.server + urllib).

  1. Zwei gleiche POST erzeugen zwei Bestellungen (1 und 2). POST ist nicht idempotent.
  2. Zwei gleiche PUT ergeben einen Zustand. Erst 201 (neu angelegt), dann 200 (ersetzt). RFC 9110 verlangt genau das.
  3. Der erste Merge Patch ändert qty und fügt note hinzu. Der zweite löscht note mit null.
  4. Ein falscher Content-Type ergibt 415 mit Accept-Patch. So empfiehlt es RFC 5789.
  5. DELETE: 204, dann 404. Der Statuscode ändert sich, der Zustand nicht. Das bleibt idempotent.

Vergleich

  • GET: sicher, idempotent, cachebar, kein Body.
  • POST: nicht sicher, nicht idempotent. Server vergibt die ID.
  • PUT: nicht sicher, idempotent. Client kennt die URI und schickt alles.
  • PATCH: nicht sicher, nicht idempotent (kann idempotent gebaut werden). Nur Änderungen.
  • DELETE: nicht sicher, idempotent.
  • QUERY: sicher, idempotent, mit Body.
  • Merge Patch vs JSON Patch: Merge Patch ist einfach und lesbar, kann aber keine Array-Elemente und kein explizites null. JSON Patch kann alles, ist aber schwerer zu lesen und zu validieren.
  • PUT vs POST zum Anlegen: PUT, wenn der Client die ID bestimmt (z. B. natürlicher Schlüssel). POST, wenn der Server sie vergibt.

In der Produktion

  1. Doppelte Zahlungen oder Bestellungen: Client oder Gateway wiederholen ein POST nach Timeout. Lösung: Idempotency-Key, eindeutiger fachlicher Schlüssel in der DB, oder PUT mit Client-ID.
  2. GET mit Seiteneffekt: Ein Link GET /orders/1/delete wird von einem Crawler oder Prefetch aufgerufen. Daten sind weg. Lösung: Ändern nur mit unsicheren Methoden.
  3. Lost Update: Zwei Clients machen PUT auf dieselbe Ressource. Der zweite überschreibt den ersten. Lösung: ETag mit If-Match, Antwort 412 bei Konflikt.
  4. PUT löscht Felder: Ein Client schickt nur zwei Felder per PUT. Der Rest wird leer. Lösung: PATCH für Teiländerungen, PUT nur mit voller Repräsentation.
  5. PATCH ohne Format: Der Server nimmt application/json und rät die Semantik. null bedeutet mal „löschen“, mal „ignorieren“. Lösung: Merge Patch oder JSON Patch explizit festlegen.
  6. Proxy blockiert Methoden: Alte Firewalls lassen nur GET und POST durch. Notlösung: X-HTTP-Method-Override. Besser: Infrastruktur korrigieren.

Diagnose: Werkzeuge und Befehle

  • curl -i -X PATCH -H 'Content-Type: application/merge-patch+json' -d '{"qty":5}' URL: Methode, Header und Status direkt sehen.
  • curl -i -X OPTIONS URL: zeigt Allow und Accept-Patch, falls der Server sie setzt.
  • Access-Logs am Gateway: doppelte POST mit gleichem Body in kurzer Zeit zeigen Retry-Probleme.
  • Retry-Konfiguration prüfen: Spring Retry, Resilience4j, Service Mesh. Retries nur für idempotente Methoden einschalten.
  • Distributed Tracing (OpenTelemetry): zeigt, ob ein Request zweimal beim Service ankam.
  • Datenbank: Unique Constraint auf den fachlichen Schlüssel zeigt Duplikate als Fehler statt stiller Daten.

Senior-Punkte

  1. Idempotenz ist eine Server-Eigenschaft, keine Eigenschaft des Verbs. PUT ist nur idempotent, wenn der Code es auch ist. Ein PUT, das einen Zähler erhöht, bricht den Vertrag.
  2. Jeder Retry braucht Idempotenz. In verteilten Systemen gibt es kein „genau einmal“ über das Netz. Es gibt nur „mindestens einmal“ plus idempotente Verarbeitung.
  3. PATCH-Format ist eine API-Entscheidung. Merge Patch für einfache Objekte. JSON Patch für Listen und präzise Operationen. Das Format gehört in den Vertrag (OpenAPI).
  4. Optimistic Locking über HTTP mit ETag und If-Match ist günstiger als Locks in der DB über mehrere Requests.
  5. Komplexe Suchen: GET mit Query-Parametern bleibt Standard. Zu lange URLs → POST auf eine Such-Ressource. QUERY ist die saubere Zukunft, aber Werkzeuge müssen nachziehen.
  6. Nicht alles muss CRUD sein. Eine Aktion wie „stornieren“ kann ein POST auf eine Unterressource sein. Wichtig ist die richtige Semantik, nicht die Reinheit.
