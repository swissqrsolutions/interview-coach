API-Versionierung

Kern: API-Versionierung ist der Weg, eine API zu ändern, ohne bestehende Clients zu brechen. Die wichtigste Regel ist, dass abwärtskompatible Änderungen keine neue Version brauchen. Nur ein Breaking Change braucht eine neue Major-Version, mit Parallelbetrieb, Deprecation-Header und Abschaltdatum.

Antwort-Muster

Frage: Wie versioniert man eine API?

  1. Mechanismus: Nur Breaking Changes brauchen eine neue Major-Version. Die Version steht in URI, Header, Query oder Media Type.
  2. Zahl: Ich betreibe höchstens zwei Major-Versionen parallel. v1 bekommt Deprecation und Sunset.
  3. Trade-off: URI-Versionierung ist sichtbar und einfach, aber starr. Header sind sauberer, brauchen aber Vary.
  4. Produktion: Ich messe Requests pro Version und Client und prüfe Breaking Changes per OpenAPI-Diff in der CI.

1. Die Reise einer Version

  1. v1 ist live. Bestellungen haben ein Feld name und amount als Zahl.
  2. v1.1, additive Änderung: Das Feld currency kommt dazu. Alte Clients ignorieren es. Keine neue Major-Version nötig.
  3. v2, Breaking Change: name wird in firstName und lastName geteilt, amount wird ein Objekt. v2 läuft parallel zu v1.
  4. v1 wird deprecated: Jede v1-Antwort trägt Deprecation (RFC 9745), Sunset (RFC 8594) und einen Link zur Migrationsanleitung.
  5. Monitoring: Das Team misst, welche Clients noch v1 aufrufen, und spricht sie direkt an.
  6. v1 wird abgeschaltet: Nach dem Sunset-Datum liefert v1 z. B. 410 Gone.

2. Aufbau

  1. URI-Version: Die Version steht im Pfad, z. B. /v2/orders. Sichtbar, einfach zu routen und zu cachen.
  2. Header- oder Query-Version: eigener Header wie API-Version: 2 oder Parameter wie ?api-version=2. Die URI bleibt stabil.
  3. Media-Type-Version: über Content Negotiation, z. B. Accept: application/vnd.shop.order.v2+json. Version pro Repräsentation.
  4. Gateway oder Framework: liest die Version und wählt den Handler. Spring Framework 7 kann das selbst.
  5. Handler: Alte und neue Version teilen meist das gleiche Domänenmodell. Nur die Abbildung nach aussen unterscheidet sich.

3. Details, die Interviewer fragen

  1. Abwärtskompatibel (non-breaking): Dazu zählen ein neues optionales Feld in der Antwort und ein neuer Endpoint. Auch ein neuer optionaler Parameter oder Header ist kompatibel. Das gilt ebenso für eine gelockerte Validierung.
  2. Breaking: Dazu zählen Feld entfernen oder umbenennen. Auch Typ oder Format ändern bricht Clients. Ein optionales Feld zur Pflicht zu machen bricht sie ebenfalls. Auch ein neues Pflichtfeld im Request und strengere Validierung brechen Clients. Das gilt ebenso für geänderte Statuscodes, Fehlerformate und URIs. Auch eine neue Semantik eines Feldes bricht Clients.
  3. Graubereich Enum: Ein neuer Enum-Wert in der Antwort bricht Clients mit switch ohne Default. Er bricht auch Clients mit strikter Deserialisierung. Darum sagt man im Vertrag, dass unbekannte Werte möglich sind.
  4. Tolerant Reader: Clients ignorieren unbekannte Felder und lesen nur, was sie brauchen. In Jackson schaltet man FAIL_ON_UNKNOWN_PROPERTIES aus. Springs Jackson2ObjectMapperBuilder macht das schon. Bei einem eigenen Mapper oder Jackson 3 prüft man es selbst.
  5. Semantic Versioning: Das Schema ist MAJOR.MINOR.PATCH. Für APIs zählt nach aussen meist nur MAJOR. MINOR und PATCH sind kompatibel und brauchen keine neue URI.
  6. URI-Versionierung: Sie sieht so aus: /v1/…. Sie ist sichtbar und einfach im Browser, im Gateway und in Logs. Die URI soll laut REST aber die Ressource nennen, nicht ihre Version. Clients müssen alle URIs umschreiben.
  7. Header-Versionierung: Die URIs bleiben stabil. Der Nachteil ist, dass sie im Browser unsichtbar ist. Sie braucht Vary für Caches.
  8. Media-Type-Versionierung: Das ist die sauberste REST-Lösung, mit Version pro Repräsentation. Der Nachteil ist, dass sie für Clients und Werkzeuge komplex ist.
  9. Query-Parameter: Man schreibt ?api-version=2024-10-01, z. B. bei Azure-APIs. Oft steht ein Datum statt einer Zahl. Das ist einfach, aber leicht vergessen.
  10. Default-Version: Fehlt die Version, ist „neueste“ gefährlich. Ein Release bricht dann alte Clients. Besser ist, die Version zu verlangen oder eine feste Version zu setzen.
  11. Deprecation-Header (RFC 9745): Er sieht so aus: Deprecation: @<Unix-Sekunden>. Das Datum kann in der Zukunft oder Vergangenheit liegen. Dazu kommt Link: <…>; rel="deprecation" zur Doku.
  12. Format des Deprecation-Headers: Er ist ein Structured Field vom Typ Item. Der Wert muss ein Datum sein. Darum steht ein @ vor den Unix-Sekunden.
  13. Sunset-Header (RFC 8594): Er nennt das Datum, ab dem die Ressource wahrscheinlich nicht mehr antwortet. Laut RFC 9745 darf Sunset nicht früher als Deprecation sein.
  14. Spring Framework 7: Es hat eingebaute API-Versionierung. Es gibt Resolver für Header, Query, Pfad oder Media-Type-Parameter. Das Mapping geht mit @GetMapping(version = "1.2+"). Das + heisst „diese und höhere“. Eine unbekannte Version ergibt 400. StandardApiVersionDeprecationHandler setzt Deprecation- und Sunset-Header.
  15. Spring-Mapping mit mehreren Versionen: Passen mehrere Methoden, gewinnt die höchste Version bis zur Request-Version. Eine Methode ohne Version passt auf jede Version. Eine genauere Version hat Vorrang.
  16. Expand and Contract: Zuerst liefert man das neue Feld zusätzlich (expand). Clients migrieren. Dann entfernt man das alte (contract). So vermeidet man oft eine neue Major-Version.
  17. Vertragstests: Ein OpenAPI-Diff in der CI (z. B. oasdiff) erkennt Breaking Changes. Consumer-Driven Contracts (Pact, Spring Cloud Contract) prüfen, was echte Clients brauchen.

4. Fallen

  • „Jede Änderung braucht eine neue Version.“ → Falsch. Additive Änderungen sind kompatibel. Nur Breaking Changes brauchen eine neue Major-Version.
  • „Ein neues Feld in der Antwort ist immer sicher.“ → Nur mit Tolerant Reader. Strikte Clients mit FAIL_ON_UNKNOWN_PROPERTIES brechen.
  • „Ein neuer Enum-Wert ist additiv, also harmlos.“ → Falsch. Für Clients ohne Default-Zweig ist er breaking.
  • „Ohne Version liefern wir einfach die neueste.“ → Gefährlich. Jedes Release kann dann alte Clients brechen.
  • „Der Deprecation-Header schaltet die API ab.“ → Falsch. Er informiert nur. Das Abschaltdatum steht im Sunset-Header, abschalten muss man selbst.
  • „Deprecation ist noch ein Draft.“ → Veraltet. Seit März 2025 ist es RFC 9745.

5. Selbsttest

Warum?

Ist ein neuer Enum-Wert breaking?

Für strikte Clients ja. Darum im Vertrag festhalten, dass unbekannte Werte kommen können, und Clients mit Default-Zweig bauen.

Warum braucht Header-Versionierung Vary?

Sonst speichert ein Cache eine Antwort pro URI und liefert einem v1-Client eine v2-Antwort.

Was passiert, wenn der Client keine Version sendet?

Entweder Fehler 400 oder eine feste Default-Version. „Immer die neueste“ bricht Clients bei jedem Release.

Warum ist eine vergessene alte Version ein Sicherheitsrisiko?

Sie bekommt oft keine Patches und hat alte Schwächen. OWASP nennt das API9: Improper Inventory Management.

Wie innen?

Welche Arten der Versionierung gibt es?

URI (/v2/), eigener Header (API-Version), Query-Parameter (?api-version=) und Media Type (Accept: application/vnd.x.v2+json).

Was ist ein Tolerant Reader?

Ein Client, der unbekannte Felder ignoriert und nur liest, was er braucht. So überlebt er additive Änderungen.

Was macht der Deprecation-Header?

RFC 9745: Er sagt, dass die Ressource deprecated ist oder ab einem Datum wird. Format @ plus Unix-Sekunden, oft mit Link rel="deprecation".

Was macht der Sunset-Header?

RFC 8594: Er nennt das Datum, ab dem die Ressource wahrscheinlich nicht mehr antwortet. Es darf nicht vor dem Deprecation-Datum liegen.

Wie unterstützt Spring Versionierung?

Seit Spring Framework 7 eingebaut: Resolver für Header, Query, Pfad oder Media Type, und @GetMapping(version = "1.2+"). Unbekannte Version ergibt 400.

Zahlen

Wie lange betreibt man alte Versionen?

So kurz wie möglich, so lang wie nötig. Intern Wochen bis Monate, öffentlich und bei Mobile-Apps oft deutlich länger. Datum früh kommunizieren.

Was bedeutet Deprecation: @1782864000?

Das Datum steht in Unix-Sekunden, mit @ davor. Der Wert ist 2026-07-01 00:00 UTC. Es ist ein Structured-Field-Datum nach RFC 9745.

Wie viele Major-Versionen betreibt man parallel?

Meist höchstens zwei. Jede Version kostet Betrieb: Tests, Sicherheits-Patches und Doku.

Vergleich

Welche Strategie empfehlen Sie?

Pragmatisch meist URI-Versionierung nur für Major-Versionen, weil sie sichtbar und einfach ist. Wichtiger ist, Breaking Changes zu vermeiden und automatisch zu prüfen.

Was ist ein Breaking Change?

Eine Änderung, die bestehende Clients bricht: Feld entfernen oder umbenennen, Typ ändern, neues Pflichtfeld, strengere Validierung, anderer Statuscode.

Was ist kompatibel?

Neue optionale Felder, neue Endpoints, neue optionale Parameter und gelockerte Validierung.

Deprecation oder Sunset?

Deprecation sagt, dass die Ressource veraltet ist oder wird. Sunset nennt das Abschaltdatum, und es darf nicht früher liegen als Deprecation.

Produktion

Wie erkennt man Breaking Changes automatisch?

OpenAPI-Diff in der CI, z. B. oasdiff, und Consumer-Driven Contract Tests wie Pact.

Wie vermeidet man Code-Duplikation bei zwei Versionen?

Ein Domänenmodell und eine Service-Schicht. Versionen unterscheiden sich nur in DTOs und Mappern.

Szenario: Ein Partner meldet nach Ihrem Release Abstürze, obwohl Sie „nur ein Feld ergänzt“ haben. Was ist passiert?

Der Partner deserialisiert strikt und scheitert an unbekannten Feldern, oder es war ein neuer Enum-Wert. Kurzfristig zurückrollen oder Feld abschaltbar machen, dann Tolerant Reader verlangen und im Vertrag festhalten.

Szenario: Sie müssen ein Pflichtfeld im Request ergänzen. Wie gehen Sie vor?

Erst optional mit sinnvollem Default einführen, Clients informieren und messen. Erst wenn alle es senden, Pflicht machen, oder dafür eine neue Major-Version.

Szenario: v1 soll in drei Monaten weg, aber Sie wissen nicht, wer sie nutzt. Was tun Sie?

Metriken pro Client-ID am Gateway auswerten, Deprecation- und Sunset-Header setzen, Teams direkt kontaktieren. Vor dem Abschalten kurze geplante Ausfälle (Brownouts) testen.

Design

Was ist Expand and Contract?

Erst das Neue zusätzlich anbieten, dann Clients migrieren, dann das Alte entfernen. So vermeidet man oft eine neue Major-Version.

Was antwortet eine abgeschaltete Version?

Zum Beispiel 410 Gone mit einem Hinweis auf die neue Version. 404 geht auch, ist aber weniger klar.

Wann brauchen Sie überhaupt eine neue Major-Version?

Nur bei einem Breaking Change. Dann läuft die neue Version parallel, die alte bekommt Deprecation, Sunset und einen Link zur Migrationsanleitung.

Mehr

Gerüst

  • Warum? Eine API ändern, ohne bestehende Clients zu brechen. Additive Änderungen brauchen keine neue Version.
  • Wie innen? Version in URI (/v2/), Header, Query oder Media Type. Header-Versionen brauchen Vary. Spring 7 wählt den Handler per version.
  • Zahlen Meist höchstens 2 Major-Versionen parallel. Deprecation: @1782864000 = Unix-Sekunden. Unbekannte Version: 400. Abgeschaltet: 410.
  • Vergleich URI: sichtbar, einfach. Header: stabile URIs, Vary nötig. Media Type: REST-konform, komplex. Keine Version: nur kompatible Änderungen.
  • Produktion Feld von Zahl zu String bricht Mobile Apps. Neuer Enum-Wert. v1 läuft ewig, niemand kennt die Clients. Cache ohne Vary.
  • Design Zuerst Expand/Contract und Tolerant Reader. OpenAPI-Diff in der CI. Deprecation, Sunset und Link zusammen setzen.

Beispiel: drei Strategien und Deprecation-Header

# version_demo.py (gekürzt): http.server + urllib
def v1_1(o): return {**v1(o), "currency": "CHF"}      # additiv
def v2(o):   return {"id": o["id"], "firstName": ..., "lastName": ...,
                     "amount": {"value": "49.90", "currency": "CHF"}}   # Breaking
V1_HEADERS = {"Deprecation": "@1782864000",           # 2026-07-01 00:00 UTC
              "Sunset": "Thu, 31 Dec 2026 23:59:59 GMT",
              "Link": '<https://api.example.ch/docs/migrate-v2>; rel="deprecation"; type="text/html"'}
# Version aus: Pfad /vN/… | Header API-Version | Accept: application/vnd.shop.order.vN+json
1) URI-Versionierung
GET /v1/orders/42
  -> 200 application/json
     Deprecation: @1782864000
     Sunset: Thu, 31 Dec 2026 23:59:59 GMT
     Link: <https://api.example.ch/docs/migrate-v2>; rel="deprecation"; type="text/html"
     {"id": 42, "name": "Anna Meier", "amount": 49.9, "currency": "CHF"}
GET /v2/orders/42
  -> 200 application/json
     {"id": 42, "firstName": "Anna", "lastName": "Meier", "amount": {"value": "49.90", "currency": "CHF"}}
2) Header-Versionierung
GET /orders/42 API-Version: 1
  -> 200 application/json
     Deprecation: @1782864000
     [Sunset, Link und Body wie oben]
GET /orders/42 API-Version: 3
  -> 400 application/problem+json
     {"title": "Unsupported API version", "supported": ["1", "2"]}
3) Media-Type-Versionierung
GET /orders/42 Accept: application/vnd.shop.order.v2+json
  -> 200 application/vnd.shop.order.v2+json
     {"id": 42, "firstName": "Anna", "lastName": "Meier", "amount": {"value": "49.90", "currency": "CHF"}}
4) Tolerant Reader: alter v1-Client liest v1.1 (neues Feld currency)
GET /v1/orders/42
  -> 200 application/json
     [Header und Body wie oben]
     Client nutzt nur: {'id': 42, 'name': 'Anna Meier', 'amount': 49.9}

Echte Ausgabe, Python 3.12 (http.server + urllib). In eckigen Klammern gekürzt, weil identisch mit dem ersten Block.

  1. Alle drei Strategien liefern dieselben Daten. Nur der Ort der Version unterscheidet sich.
  2. Deprecation ist ein Structured-Field-Datum: @ plus Unix-Sekunden. Sunset nutzt das klassische HTTP-Datum. RFC 9745 nennt den Unterschied „historisch“.
  3. Eine unbekannte Version ergibt 400 mit der Liste der erlaubten Versionen. Spring 7 antwortet hier ebenfalls mit 400.
  4. Bei der Media-Type-Variante kommt der Versions-Typ auch im Content-Type zurück.
  5. Der alte Client nutzt nur seine drei Felder. Das neue Feld currency stört ihn nicht. Das ist der Tolerant Reader.
  6. Bei Header- oder Media-Type-Versionierung muss der Server Vary: API-Version, Accept setzen. Sonst liefert ein Cache die falsche Version.

Vergleich

  • URI (/v2/): sehr sichtbar, einfach zu routen und zu cachen. Unschön aus REST-Sicht, grober Wechsel für Clients.
  • Eigener Header: stabile URIs, feinere Steuerung. Unsichtbar, Vary nötig, im Browser schwer zu testen.
  • Media Type: REST-konform, Version pro Ressource. Am komplexesten für Clients und Tools.
  • Query-Parameter: einfach, oft mit Datum. Mischt Version und Filter.
  • Gar keine Version (Evolution): nur kompatible Änderungen, Breaking Changes vermeiden. Funktioniert gut bei internen APIs mit wenigen Clients und Vertragstests.

In der Produktion

  1. „Kleine“ Änderung bricht Clients: Ein Feld wird von Zahl zu String. Mobile Apps stürzen ab. Lösung: OpenAPI-Diff in der CI, Breaking-Change-Regeln im Review.
  2. Neuer Enum-Wert: Ein Partner wirft bei unbekanntem Status eine Exception. Lösung: im Vertrag erlauben, Clients mit Default-Zweig, vorher ankündigen.
  3. v1 läuft ewig: Niemand weiss, wer v1 noch nutzt. Lösung: Metriken pro Version und Client-ID, Deprecation-Header, aktive Kommunikation, festes Sunset-Datum.
  4. Cache liefert falsche Version: Header-Versionierung ohne Vary. Lösung: Vary: API-Version setzen oder URI-Versionierung.
  5. Code-Kopie pro Version: v1 und v2 sind zwei kopierte Controller-Bäume. Bugs werden nur in einem gefixt. Lösung: ein Domänenmodell, Versionen nur im Mapping (DTOs, Adapter).
  6. Mobile Apps lassen sich nicht erzwingen: Alte App-Versionen bleiben jahrelang installiert. Lösung: längere Sunset-Fristen, Mindestversion in der App prüfen.

Diagnose: Werkzeuge und Befehle

  • curl -i -H 'API-Version: 1' URL: prüft, ob Deprecation, Sunset und Vary kommen.
  • oasdiff (z. B. oasdiff breaking old.yaml new.yaml): listet Breaking Changes zwischen zwei OpenAPI-Dateien.
  • Gateway-Metriken: Requests pro Version und pro Client (API-Key, OAuth client_id). Zeigt, wer migrieren muss.
  • Pact Broker oder Spring Cloud Contract: zeigt, welche Consumer welche Felder nutzen.
  • Logs nach Deserialisierungsfehlern auf Client-Seite durchsuchen, z. B. UnrecognizedPropertyException.

Senior-Punkte

  1. Die beste Version ist keine neue Version. Erst Evolution versuchen: additiv, Expand and Contract, Tolerant Reader.
  2. Die Strategie ist weniger wichtig als die Disziplin. URI-Versionierung ist pragmatisch und weit verbreitet. Wichtig sind klare Regeln, was „breaking“ heisst, und automatische Prüfung.
  3. Jede Version kostet Betrieb: Tests, Sicherheits-Patches, Doku. Darum wenige Major-Versionen gleichzeitig, meist höchstens zwei.
  4. Deprecation ist Kommunikation, nicht nur ein Header. Changelog, Migrationsanleitung, Datum, Kontakt mit den Teams.
  5. Interne vs öffentliche APIs: Intern mit wenigen Consumern und Vertragstests geht schnelle Evolution. Öffentlich braucht es lange Fristen.
  6. Versionierung gehört ins Inventar. Vergessene alte Versionen sind ein Sicherheitsrisiko (OWASP API9: Improper Inventory Management).
