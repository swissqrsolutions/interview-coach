HTTP-Statuscodes richtig wählen

Kern: Ein Statuscode ist die dreistellige Zahl, mit der der Server das Ergebnis eines Requests meldet. Die erste Ziffer ist die Klasse: 2xx Erfolg, 3xx Umleitung, 4xx Fehler des Clients, 5xx Fehler des Servers. Der Code steuert Clients, Caches, Retries und Monitoring. Den Fehler-Body beschreibt RFC 9457 Problem Details.

1. Wo sitzen die Statuscodes?

  1. Gateway oder Proxy: erzeugt eigene Codes. 429 beim Rate Limit, 502/504 bei Problemen mit dem Service dahinter, 503 bei Überlast.
  2. Security-Filter: prüft vor dem Controller. Kein gültiges Token: 401. Token gültig, aber keine Rechte: 403.
  3. Controller: prüft Syntax und Validierung. Kaputtes JSON: 400. Fachlich ungültig: 422 (oder 400, je nach Konvention).
  4. Domäne und DB: melden Konflikte. Duplikat oder falscher Zustand: 409. ETag passt nicht: 412.
  5. Jede Schicht liefert ihren Fehler am besten im gleichen Format: application/problem+json.

2. Die Reise eines Requests durch die Codes (die Geschichte zum Merken)

  1. Rate Limit: Das Gateway zählt Requests. Zu viele: 429 mit Retry-After. Der Service sieht den Request nie.
  2. Authentifizierung: Fehlt das Token oder ist es abgelaufen, kommt 401 mit WWW-Authenticate.
  3. Autorisierung: Anna ist angemeldet, will aber Bestellung 2 von Ben. Antwort: 403, oder 404, um die Existenz zu verbergen.
  4. Syntax: Der Body ist kein gültiges JSON. Antwort: 400.
  5. Validierung: JSON ist gültig, aber qty = 0. Antwort: 422 mit Feldfehlern.
  6. Zustand: Bestellnummer existiert schon: 409. Client hat eine alte Version (ETag): 412.
  7. Erfolg: neu angelegt: 201 + Location. Asynchron angenommen: 202. Fertig ohne Body: 204. Sonst 200.
  8. Unerwarteter Fehler: 500 ohne Interna. Der Body enthält nur eine Referenz für die Logs.

Echte Ausgabe, Python 3.12 (http.server + urllib). 502, 503 und 504 entstehen am Gateway und fehlen darum hier.

  1. 201 und 202 tragen beide Location. Bei 201 zeigt sie auf die neue Ressource, bei 202 auf einen Status-Monitor.
  2. 301: urllib folgt der Umleitung selbst. Der Client sieht nur das 200 der neuen URI.
  3. 304: Der Client hat If-None-Match: "v3" gesendet. Der Server spart den Body.
  4. 412 vs 204: Mit altem ETag "v2" scheitert das PUT. Mit aktuellem ETag gelingt es, und ein neues ETag kommt zurück.
  5. 401 trägt WWW-Authenticate. RFC 9110 verlangt diesen Header.
  6. 422 nutzt einen eigenen type und die Erweiterung errors mit JSON Pointer. Das Muster stammt aus RFC 9457.
  7. 429: Retry-After ist ein Header, kein Body-Feld. Erst die dritte Anfrage scheitert.
  8. 500: Die Exception enthielt eine interne DB-URL. Der Body zeigt sie nicht, nur eine Referenz.

4. Details, die Interviewer fragen

  1. 200 OK: Erfolg mit Body. Standard für GET und für PUT/PATCH, wenn der neue Zustand zurückkommt.
  2. 201 Created: Eine neue Ressource existiert. Bei POST soll Location auf sie zeigen. Fehlt Location, ist die Ziel-URI gemeint.
  3. 202 Accepted: angenommen, aber nicht fertig. Die Antwort ist „bewusst unverbindlich“. Sie soll auf einen Status-Monitor zeigen, z. B. /reports/7.
  4. 204 No Content: Erfolg ohne Body. Typisch für DELETE und PUT. Header wie ETag gelten trotzdem.
  5. 301 Moved Permanently: neue feste URI in Location. Clients dürfen aus historischen Gründen POST zu GET machen. Soll die Methode bleiben: 308. Temporär: 307.
  6. 304 Not Modified: Antwort auf ein bedingtes GET oder HEAD (If-None-Match, If-Modified-Since). Kein Body. Der Client nutzt seine Kopie.
  7. 400 Bad Request: Der Client hat etwas falsch gemacht, z. B. kaputte Syntax. Er soll den Request nicht unverändert wiederholen.
  8. 401 Unauthorized: Gültige Authentifizierung fehlt. Der Name ist irreführend. Der Server muss WWW-Authenticate senden.
  9. 403 Forbidden: Der Server versteht den Request, verweigert ihn aber. Neue Credentials helfen meist nicht. Um Existenz zu verbergen, darf der Server 404 senden.
  10. 404 Not Found: keine aktuelle Repräsentation, oder der Server will die Existenz nicht verraten. Ob es dauerhaft ist, sagt 404 nicht. Dauerhaft weg: 410 Gone.
  11. 409 Conflict: Konflikt mit dem aktuellen Zustand, den der Client lösen kann. Beispiele: Duplikat, falscher Statusübergang. Der Body soll den Konflikt erklären.
  12. 412 Precondition Failed: Eine Bedingung im Header (If-Match, If-Unmodified-Since) ist falsch. Das ist optimistisches Locking über HTTP. 428 (RFC 6585) verlangt, dass der Client überhaupt eine Bedingung sendet.
  13. 422 Unprocessable Content: Seit RFC 9110 Teil des Kerns (früher WebDAV). Content-Type und Syntax stimmen, aber der Inhalt ist fachlich ungültig.
  14. 429 Too Many Requests (RFC 6585): Rate Limit überschritten. Retry-After ist erlaubt, als Sekunden (120) oder als Datum.
  15. 500 Internal Server Error: unerwarteter Fehler im Server. Immer ein Bug oder ein nicht behandelter Fall.
  16. 502 Bad Gateway: Ein Gateway oder Proxy bekam eine ungültige Antwort vom Service dahinter, z. B. Verbindungsabbruch.
  17. 503 Service Unavailable: vorübergehend überlastet oder in Wartung. Retry-After ist möglich.
  18. 504 Gateway Timeout: Das Gateway bekam keine rechtzeitige Antwort vom Service dahinter.
  19. 415 und 406: 415, wenn der Server das Format des Request-Bodys nicht kann. 406, wenn er kein Format aus Accept liefern kann.
  20. Problem Details (RFC 9457): Media Type application/problem+json. Felder: type (URI, Standard about:blank), title, status, detail, instance. Eigene Felder sind Extensions. RFC 9457 ersetzt RFC 7807.
  21. Regeln in RFC 9457: type ist der Schlüssel für Clients, nicht title. status im Body ist nur ein Hinweis und muss dem echten Code gleichen. detail hilft dem Client, ist aber kein Debug-Output. RFC 9457 führt eine IANA-Registry für Problem Types ein.
  22. Spring: ProblemDetail ist die Klasse für RFC 9457. Alle Spring-MVC-Exceptions implementieren ErrorResponse. Eine @ControllerAdvice, die ResponseEntityExceptionHandler erweitert, rendert sie. In Spring Boot schaltet spring.mvc.problemdetails.enabled=true das ein.

5. Vergleich

  • 401 vs 403: 401 = „Wer bist du?“, Authentifizierung fehlt oder ist ungültig. 403 = „Ich weiss, wer du bist, aber nein.“
  • 403 vs 404: 404 verbirgt, dass eine fremde Ressource existiert. Gut gegen ID-Raten.
  • 400 vs 422: 400 für kaputte Syntax oder falsche Parameter. 422 für syntaktisch gültige, aber fachlich falsche Daten. Viele APIs nutzen nur 400. Wichtig ist eine feste Konvention.
  • 409 vs 412: 409 = Konflikt mit dem Zustand, im Body erklärt. 412 = eine Header-Bedingung ist falsch.
  • 200 vs 204: 200 mit Body, 204 ohne.
  • 201 vs 202: 201 = fertig angelegt. 202 = angenommen, Ergebnis kommt später.
  • 301 vs 308 vs 307: 301 permanent, POST darf zu GET werden. 308 permanent, Methode bleibt. 307 temporär, Methode bleibt.
  • 502 vs 503 vs 504: 502 kaputte Upstream-Antwort. 503 Service sagt selbst „gerade nicht“. 504 Upstream antwortet nicht rechtzeitig.

6. In der Produktion

  1. „200 mit Fehler im Body“: Monitoring zählt keine Fehler, Clients und Caches glauben an Erfolg. Lösung: echte 4xx/5xx-Codes.
  2. Stacktraces im Body: 500-Antworten zeigen Klassen, SQL und interne Hosts. Lösung: globaler Exception-Handler, Problem Details mit Referenz-ID, Details nur ins Log.
  3. Retry-Sturm: Clients wiederholen 4xx-Fehler oder 503 sofort und ohne Pause. Lösung: nur 429/503/502/504 wiederholen, mit Exponential Backoff, Jitter und Retry-After.
  4. 502/504 am Ingress: Der Service ist zu langsam oder startet neu. Ursachen: Timeout des Gateways kürzer als die Verarbeitung, Pods nicht bereit. Lösung: Timeouts abstimmen, Readiness Probes, lange Arbeit asynchron mit 202.
  5. 401 statt 403 (oder umgekehrt): Der Frontend-Client leitet bei 403 zum Login um, obwohl das nicht hilft. Lösung: 401 nur bei fehlender oder ungültiger Anmeldung.
  6. Uneinheitliche Fehlerformate: Jeder Service hat sein eigenes JSON. Lösung: Problem Details als Standard, gemeinsame Bibliothek, im OpenAPI-Vertrag beschrieben.

7. Diagnose: Werkzeuge und Befehle

  • curl -i URL: Statuszeile und Header sehen. curl -v zeigt auch die Request-Header.
  • curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' URL: nur Code und Dauer, gut für Skripte.
  • Ingress- und Gateway-Logs (NGINX, Envoy, Azure Application Gateway): zeigen, ob 502/504 vom Gateway oder vom Service kommt.
  • Prometheus/Grafana: Rate von 5xx pro Endpoint, z. B. Micrometer-Metrik http_server_requests_seconds_count{status=~"5.."}.
  • Tracing (OpenTelemetry): Die Referenz-ID im Problem-Detail führt zum Trace und zum Log.
  • Browser DevTools, Tab Network: zeigt CORS-Fehler, die wie „kein Status“ aussehen.

8. Senior-Punkte

  1. Codes sind ein Vertrag mit Maschinen. Clients, Caches, Gateways und Alarme reagieren darauf. Der Body ist für Menschen und für Details.
  2. Wenige Codes, fest definiert. Ein Team-Katalog mit ca. 15 Codes ist besser als jeder Code im RFC. Wichtig ist Konsistenz über alle Services.
  3. 4xx vs 5xx entscheidet über Retries und Alarme. Validierungsfehler als 500 wecken nachts den Bereitschaftsdienst. Bugs als 400 bleiben unsichtbar.
  4. Problem Details mit eigenem type geben Clients einen stabilen Schlüssel. Texte dürfen sich ändern, der type nicht.
  5. 404 statt 403 ist eine Sicherheitsentscheidung. Es verrät nicht, welche IDs existieren.
  6. Lange Arbeit asynchron: 202 plus Status-Ressource statt eines Requests, der in den 504 läuft.

10. Fallen

  • „401 heisst: keine Berechtigung.“ → Falsch. 401 heisst: Authentifizierung fehlt oder ist ungültig. Keine Berechtigung ist 403.
  • „422 ist nur WebDAV.“ → Veraltet. Seit RFC 9110 ist 422 „Unprocessable Content“ ein allgemeiner Code.
  • „Problem Details ist RFC 7807.“ → Veraltet. RFC 9457 ersetzt RFC 7807.
  • „502 und 504 sind dasselbe.“ → Falsch. 502 = ungültige Antwort von oben. 504 = keine Antwort in der Zeit.
  • „DELETE auf eine gelöschte Ressource muss 204 liefern, sonst ist es nicht idempotent.“ → Falsch. 404 ist korrekt. Idempotenz betrifft den Zustand.
  • „status im Problem-Body darf vom HTTP-Code abweichen.“ → Falsch. Er muss gleich sein. Er ist nur ein Hinweis.

11. Fragen

Was bedeuten die fünf Klassen von Statuscodes?

1xx Information, 2xx Erfolg, 3xx Umleitung, 4xx Fehler des Clients, 5xx Fehler des Servers.

401 oder 403?

401: Authentifizierung fehlt oder ist ungültig, mit WWW-Authenticate-Header. 403: Der Nutzer ist bekannt, hat aber keine Rechte.

Wann 404 statt 403?

Wenn der Server nicht verraten will, dass die Ressource existiert. RFC 9110 erlaubt das ausdrücklich.

Was gehört in eine 201-Antwort?

Ein Location-Header mit der URI der neuen Ressource, oft auch ihre Repräsentation im Body.

Wann 202?

Wenn die Verarbeitung asynchron ist. Die Antwort zeigt auf eine Status-Ressource, die der Client abfragen kann.

Wann 204?

Erfolg ohne Body, typisch nach DELETE oder PUT.

Was ist 304?

Antwort auf ein bedingtes GET: Die Kopie des Clients ist noch aktuell, darum kein Body.

301 oder 308?

Beide permanent. Bei 301 dürfen Clients POST zu GET ändern, bei 308 bleibt die Methode gleich.

400 oder 422?

400 für kaputte Syntax oder ungültige Parameter. 422, wenn die Syntax stimmt, der Inhalt aber fachlich falsch ist.

Wann 409?

Bei einem Konflikt mit dem aktuellen Zustand, den der Client lösen kann, z. B. Duplikat oder ungültiger Statusübergang.

Wann 412?

Wenn eine Header-Bedingung wie If-Match falsch ist, z. B. bei veraltetem ETag.

Was ist 428?

Precondition Required (RFC 6585): Der Server verlangt einen bedingten Request, z. B. mit If-Match, gegen Lost Updates.

Was gehört zu einer 429-Antwort?

Eine Erklärung und optional Retry-After mit Sekunden oder Datum.

502, 503 oder 504?

502: ungültige Antwort vom Upstream. 503: vorübergehend überlastet oder Wartung. 504: Upstream antwortet nicht rechtzeitig.

Welche Fehler darf ein Client automatisch wiederholen?

Vor allem 429, 503, 502, 504 und Netzwerkfehler, mit Backoff, und nur bei idempotenten Requests. 4xx wie 400 oder 422 nicht.

Was ist RFC 9457?

Problem Details for HTTP APIs: ein Standardformat für Fehler-Bodies als application/problem+json. Es ersetzt RFC 7807.

Welche Felder hat ein Problem-Detail?

type, title, status, detail, instance. Dazu beliebige Extensions wie errors.

Was bedeutet type: about:blank?

Es ist der Standard, wenn kein eigener Typ gesetzt ist. Das Problem hat dann keine Semantik über den Statuscode hinaus.

Worauf soll ein Client reagieren: type oder title?

Auf type. title ist nur ein lesbarer Hinweis und darf sich, z. B. durch Übersetzung, ändern.

Wie meldet man mehrere Validierungsfehler?

Mit einer Extension wie errors, eine Liste mit pointer und detail pro Feld. So zeigt es RFC 9457.

Wie nutzt man Problem Details in Spring?

ProblemDetail aus einem @ExceptionHandler zurückgeben. Für Spring-MVC-Exceptions eine @ControllerAdvice, die ResponseEntityExceptionHandler erweitert, oder in Boot spring.mvc.problemdetails.enabled.

Warum keine Stacktraces in Fehlerantworten?

Sie verraten Interna wie Klassen, SQL und Hosts. Das hilft Angreifern. Details gehören ins Log, der Client bekommt eine Referenz.

Warum nicht immer 200 mit success:false?

Caches, Gateways, Retries und Monitoring verstehen nur den Statuscode. Fehler wären unsichtbar.

Szenario: Nach einem Deployment melden Nutzer sporadisch 502. Wo suchen Sie?

Am Ingress oder Gateway: Pods wurden beendet, bevor Verbindungen leer waren, oder neue Pods waren nicht bereit. Lösung: Readiness Probe, Graceful Shutdown, preStop-Pause, passende Timeouts.

Szenario: Ein Report-Endpoint liefert ab und zu 504. Was tun Sie?

Die Verarbeitung dauert länger als das Gateway-Timeout. Kurzfristig Query optimieren oder Timeout prüfen. Besser: asynchron mit 202, Status-Ressource und Abruf des Ergebnisses.

Szenario: Ein Partner wiederholt jeden Fehler sofort, das System kippt. Was ändern Sie?

Fehler sauber trennen: 4xx nicht wiederholen. Rate Limit mit 429 und Retry-After, 503 bei Überlast. Vom Partner Exponential Backoff mit Jitter verlangen und im Vertrag festhalten.
