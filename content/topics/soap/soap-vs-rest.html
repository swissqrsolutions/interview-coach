SOAP vs REST

Kern: SOAP ist ein XML-Nachrichtenprotokoll mit festem Envelope, einem formalen Vertrag (WSDL + XSD) und Standards für Sicherheit und Zuverlässigkeit (WS-*). REST ist ein Architekturstil über HTTP mit Ressourcen, Verben und meist JSON. SOAP lebt heute vor allem dort, wo strenge Verträge, Signaturen und lange Lebensdauer zählen, z. B. in Behörden und Banken.

1. Wo sitzt SOAP im Stack?

  1. XSD (XML Schema): beschreibt die Datentypen. Beispiel: Person mit vn und geburtsdatum.
  2. WSDL (Web Services Description Language): beschreibt Operationen, Nachrichten, Binding und Endpoint-URL. Beispiel: Operation getPerson.
  3. Envelope: das Wurzelelement jeder SOAP-Nachricht. Es enthält Header und Body.
  4. Header: optional, für Querschnittsthemen wie Sicherheit (wsse:Security) oder Routing.
  5. Body: die eigentliche Nachricht oder ein Fault (Fehler).
  6. Client und Server: Code wird meist aus der WSDL generiert. Beispiel: wsimport oder Apache CXF erzeugen Java-Klassen.

2. Die Reise eines SOAP-Aufrufs

  1. Java-Aufruf: Der Client ruft eine generierte Methode auf, z. B. port.getPerson(vn). Er sieht kein XML.
  2. Marshalling: JAXB (Jakarta XML Binding) macht aus dem Java-Objekt XML nach der XSD.
  3. Security: Ein Handler fügt den wsse:Security-Header hinzu. Er signiert den Body und setzt einen Timestamp.
  4. HTTP: Die Nachricht geht als HTTP POST über TLS. SOAP 1.2 nutzt den Media Type application/soap+xml.
  5. Server: Er prüft Signatur, Schema und Header mit mustUnderstand. Dann führt er die Operation aus.
  6. Antwort: Ein Body mit Daten wird wieder ein Java-Objekt. Ein Fault wird im Client eine Exception, z. B. SOAPFaultException.

3. Beispiel: SOAP-1.2-Request, Fault und JAX-WS-Client

POST /personService HTTP/1.1
Content-Type: application/soap+xml; charset=utf-8

<env:Envelope xmlns:env="http://www.w3.org/2003/05/soap-envelope"
              xmlns:p="urn:example:person:1">
  <env:Header>
    <wsse:Security env:mustUnderstand="true"
      xmlns:wsse="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-secext-1.0.xsd">
      <!-- BinarySecurityToken (X.509), ds:Signature über den Body, Timestamp -->
    </wsse:Security>
  </env:Header>
  <env:Body>
    <p:getPerson><p:vn>756.1234.5678.97</p:vn></p:getPerson>
  </env:Body>
</env:Envelope>
<env:Envelope xmlns:env="http://www.w3.org/2003/05/soap-envelope">
  <env:Body>
    <env:Fault>
      <env:Code><env:Value>env:Sender</env:Value></env:Code>
      <env:Reason><env:Text xml:lang="de">Ungültige Versichertennummer</env:Text></env:Reason>
      <env:Detail><p:fehlerCode xmlns:p="urn:example:person:1">VN_CHECKSUM</p:fehlerCode></env:Detail>
    </env:Fault>
  </env:Body>
</env:Envelope>
// Contract-first: Klassen aus der WSDL generieren (jaxws-tools / CXF wsdl2java)
PersonService service = new PersonService(new URL("https://host/personService?wsdl"));
PersonPort port = service.getPersonPort();
((BindingProvider) port).getRequestContext()
    .put(BindingProvider.ENDPOINT_ADDRESS_PROPERTY, "https://host/personService");
try {
  Person p = port.getPerson("756.1234.5678.97");
} catch (SOAPFaultException e) {
  log.warn("Fault {}: {}", e.getFault().getFaultCodeAsQName(), e.getFault().getFaultString());
}

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): JAX-WS ist seit Java 11 nicht mehr im JDK (JEP 320); hier ist keine JAX-WS-Bibliothek installiert. Namespaces und Fault-Struktur nach W3C SOAP 1.2 Part 1 und OASIS WSS 1.1.1. Service und Daten sind fiktiv.

  1. Der Namespace http://www.w3.org/2003/05/soap-envelope zeigt SOAP 1.2. SOAP 1.1 nutzt http://schemas.xmlsoap.org/soap/envelope/.
  2. mustUnderstand="true" zwingt den Server, den Security-Header zu verarbeiten. Kann er das nicht, muss er einen MustUnderstand-Fault senden.
  3. Der Fault hat Pflichtelemente Code und Reason. Detail ist optional und trägt fachliche Fehlerdaten.
  4. env:Sender heisst: Die Anfrage ist falsch, nicht unverändert wiederholen. env:Receiver heisst: Problem beim Server, später erneut versuchen.
  5. Im Client wird der Fault eine SOAPFaultException. Die fachliche Antwort ist ein normales Java-Objekt.

4. Details, die Interviewer fragen

  1. SOAP 1.1 vs 1.2:
    • 1.1 (W3C Note 2000): Media Type text/xml, HTTP-Header SOAPAction Pflicht, Faults Client/Server.
    • 1.2 (W3C Recommendation, 2. Ausgabe 2007): application/soap+xml, Action als Parameter im Content-Type, Faults Sender/Receiver.
  2. Fault Codes SOAP 1.2: VersionMismatch, MustUnderstand, DataEncodingUnknown, Sender, Receiver.
  3. Rollen: Ein Header-Block kann an einen Zwischenknoten gehen. Vordefiniert: next, ultimateReceiver, none.
  4. WSDL-Teile: types (XSD), message, portType (in WSDL 2.0: interface), binding (SOAP über HTTP), service mit Endpoint.
  5. Document/literal wrapped: der übliche Stil. Der Body enthält ein Element nach XSD, das wie die Operation heisst. RPC/encoded ist veraltet und nicht WS-I-konform.
  6. WS-Security (OASIS WSS): Sicherheit auf Nachrichtenebene. Elemente: wsse:Security, UsernameToken, BinarySecurityToken (z. B. X.509), ds:Signature (XML Signature), xenc:EncryptedData (XML Encryption), wsu:Timestamp.
  7. Nachrichten- vs Transportsicherheit: TLS schützt nur von Punkt zu Punkt. Eine Signatur in der Nachricht bleibt über Zwischenstationen und im Archiv prüfbar. Das ist Non-Repudiation (Nichtabstreitbarkeit).
  8. JAX-WS: heute Jakarta XML Web Services. Seit Java 11 nicht mehr im JDK (JEP 320 entfernte java.xml.ws, java.xml.bind und Tools wie wsimport). Heute als Bibliothek: z. B. Eclipse Metro (Referenzimplementierung) oder Apache CXF. Version 4.0 gehört zu Jakarta EE 10.
  9. Contract-first vs Code-first: Contract-first schreibt zuerst WSDL/XSD und generiert Code (wsimport, CXF wsdl2java). Code-first erzeugt die WSDL aus Java-Annotationen (@WebService). Spring Web Services unterstützt nur Contract-first.
  10. MTOM: überträgt Binärdaten (z. B. PDF) effizient als Anhang statt als Base64 im XML.
  11. Weitere WS-* Standards: WS-Addressing (Routing-Infos im Header), WS-ReliableMessaging (Zustellgarantie), WS-Policy (Anforderungen beschreiben).

5. Vergleich

  • Vertrag: SOAP hat WSDL/XSD verpflichtend und streng. REST hat optional OpenAPI.
  • Format: SOAP nur XML. REST meist JSON, aber jedes Format möglich.
  • HTTP-Nutzung: SOAP nutzt HTTP als Transport, meist nur POST auf eine URL. REST nutzt Verben, URLs, Status-Codes und Caching.
  • Fehler: SOAP gibt einen Fault im Body. REST nutzt Status-Codes, oft mit Problem Details (RFC 9457).
  • Sicherheit: SOAP hat WS-Security auf Nachrichtenebene. REST nutzt meist TLS plus OAuth2/JWT; Signaturen nur mit Zusatz wie JWS.
  • Leistung: SOAP-XML ist grösser und langsamer zu parsen. REST/JSON ist leichter.
  • Tooling: SOAP generiert typisierte Clients sehr zuverlässig. REST braucht dafür OpenAPI-Generatoren.
  • gRPC: binär mit Protobuf, starker Vertrag wie SOAP, aber schnell. Gut zwischen eigenen Services.

6. In der Produktion

  1. Java-Upgrade bricht SOAP-Clients: Ab Java 11 fehlen JAX-WS und JAXB. Fehler: ClassNotFoundException: javax.xml.ws.... Lösung: Bibliotheken als Dependency, bei Jakarta EE 9+ Namespace jakarta.* statt javax.*.
  2. WSDL-Änderung beim Partner: Ein neues Pflichtfeld bricht alle Clients. Lösung: Versionierung im Namespace, nur optionale Felder ergänzen, Contract-Tests.
  3. Zertifikat läuft ab: Signatur oder mTLS schlägt fehl, alle Aufrufe scheitern. Lösung: Ablauf überwachen, Rotation automatisieren.
  4. Clock Skew: Der wsu:Timestamp ist „in der Zukunft“, der Server lehnt ab. Lösung: NTP auf allen Servern, Toleranz konfigurieren.
  5. Grosse Nachrichten: DOM-Parsing frisst Speicher. Lösung: MTOM für Binärdaten, Streaming, Grössenlimits.
  6. XML-Angriffe: XXE (externe Entities) oder „Billion Laughs“. Lösung: sichere Parser-Konfiguration, DTDs deaktivieren.
  7. Unklare Fehler: Nur „Internal Error“ im Fault. Lösung: fachliche Codes im Detail, Korrelations-ID im Header loggen.

7. Diagnose

  • SoapUI / ReadyAPI: WSDL importieren, Requests bauen, Mock-Services und Tests.
  • Message Logging: CXF LoggingFeature oder Metro-System-Property com.sun.xml.ws.transport.http.client.HttpTransportPipe.dump=true. Achtung: Personendaten im Log.
  • Schema-Validierung: Nachricht gegen die XSD prüfen, z. B. mit xmllint --schema.
  • ?wsdl an die Endpoint-URL hängen: Ist der Vertrag erreichbar und aktuell?
  • TLS-Probleme: openssl s_client -connect host:443 und Java -Djavax.net.debug=ssl:handshake.
  • Wireshark oder Proxy (z. B. mitmproxy) in Testumgebungen.

8. Senior-Punkte

  1. Wann SOAP: fester, langlebiger Vertrag zwischen Organisationen, Signaturen auf Nachrichtenebene, bestehende Behörden- oder Bankenstandards. Wann REST: neue APIs, Web und Mobile, einfache Integration, Caching.
  2. Schweizer Behörden: Viele Austausche laufen über XML mit eCH-Standards (XSDs für Personen, Meldungen usw.). sedex ist die Plattform des BFS für sicheren, asynchronen Datenaustausch; das BIT betreibt sie.
  3. sedex im Detail: Ein Java-sedex-Client tauscht Dateien über Ordner (Inbox, Outbox, Receipts) oder eine REST-API. Jede Nachricht hat einen XML-Umschlag nach eCH-0090. Der sedex Web Service Proxy gibt Fachanwendungen Zugriff auf Web Services, z. B. UPI-Abfragen nach eCH-0214. Der Teilnehmer wird über sein sedex-Zertifikat im TLS-Handshake erkannt.
  4. Contract-first ist der bessere Default zwischen Organisationen. Der Vertrag ist das Produkt, nicht ein Nebenprodukt des Codes.
  5. Eine Fassade bauen: Intern REST oder Events, nach aussen SOAP über einen Adapter. So bleibt die Kernlogik frei vom alten Protokoll.
  6. Nicht ohne Grund migrieren. Ein funktionierender SOAP-Partner mit Standardvertrag wird nicht durch REST ersetzt, nur weil REST moderner ist.

10. Fallen

  • „SOAP ist an HTTP gebunden.“ → Falsch. SOAP ist transportunabhängig. HTTP ist nur das häufigste Binding.
  • „SOAP ist tot.“ → Falsch. In Behörden, Banken und Versicherungen läuft viel produktiv, oft mit Standardverträgen.
  • „JAX-WS ist im JDK.“ → Nur bis Java 10. Seit Java 11 (JEP 320) als externe Bibliothek.
  • „TLS reicht immer, WS-Security ist überflüssig.“ → Nicht immer. TLS endet am nächsten Knoten. Nachrichtensignaturen bleiben prüfbar.
  • „sedex ist ein SOAP-Protokoll.“ → Falsch. sedex tauscht Nachrichten mit eCH-0090-Umschlag; Web Services laufen zusätzlich über den Web Service Proxy.
  • „SOAP 1.2 nutzt text/xml.“ → Falsch. Das ist SOAP 1.1. SOAP 1.2 nutzt application/soap+xml.

11. Fragen

Was ist SOAP?

Ein XML-Nachrichtenprotokoll mit Envelope, Header und Body. Der Vertrag steht in WSDL und XSD.

Was ist der grösste Unterschied zwischen SOAP und REST?

SOAP ist ein Protokoll mit strengem Vertrag und WS-Standards. REST ist ein Architekturstil, der HTTP mit Ressourcen, Verben und Status-Codes voll nutzt.

Was steht in einer WSDL?

Datentypen (XSD), Nachrichten, Operationen, Binding (z. B. SOAP über HTTP) und die Endpoint-Adresse.

Welche Teile hat eine SOAP-Nachricht?

Envelope als Wurzel, optionaler Header für Querschnittsthemen und Body mit Daten oder Fault.

Was ist ein SOAP Fault?

Die Fehlerantwort im Body. Pflicht sind Code und Reason, optional Node, Role und Detail.

Welche Fault Codes kennt SOAP 1.2?

VersionMismatch, MustUnderstand, DataEncodingUnknown, Sender und Receiver.

Was macht mustUnderstand?

Ist es true, muss der Empfänger den Header-Block verarbeiten. Sonst sendet er einen MustUnderstand-Fault.

Unterschiede SOAP 1.1 und 1.2?

1.1: text/xml, SOAPAction-Header, Faults Client/Server. 1.2: application/soap+xml, Sender/Receiver, W3C Recommendation.

Was ist WS-Security?

Ein OASIS-Standard für Sicherheit in der Nachricht: Tokens, XML-Signatur, XML-Verschlüsselung und Timestamp im Security-Header.

Warum Nachrichtensicherheit statt nur TLS?

TLS schützt nur bis zum nächsten Knoten. Eine Signatur bleibt über Zwischenstationen und im Archiv prüfbar.

Was ist Contract-first?

Zuerst WSDL und XSD schreiben, dann Code generieren. Der Vertrag bleibt stabil, egal wie sich der Code ändert.

Was ist JAX-WS heute?

Jakarta XML Web Services. Seit Java 11 nicht mehr im JDK; man nutzt z. B. Metro oder Apache CXF.

Was macht JAXB?

Es bildet XML auf Java-Objekte ab und zurück, nach einer XSD.

Was ist document/literal wrapped?

Der übliche WSDL-Stil. Der Body hat ein Element nach XSD, benannt wie die Operation. WS-I-konform.

Was ist MTOM?

Ein Verfahren, Binärdaten als Anhang statt Base64 im XML zu senden. Spart Grösse und Speicher.

Wann wählen Sie SOAP, wann REST?

SOAP für strenge, langlebige Verträge zwischen Organisationen und Nachrichtensignaturen. REST für neue, offene oder Web-APIs.

Was ist sedex?

Die Plattform des BFS für sicheren, asynchronen Datenaustausch zwischen Behörden, betrieben vom BIT. Nachrichten haben einen XML-Umschlag nach eCH-0090.

Was ist der sedex Web Service Proxy?

Eine Komponente des sedex-Clients. Fachanwendungen rufen darüber berechtigte Web Services auf, z. B. UPI-Abfragen.

Was sind eCH-Standards?

Schweizer E-Government-Standards. Sie definieren u. a. XML-Schemas für Datenaustausch, z. B. eCH-0090 für den sedex-Umschlag und eCH-0214 für UPI-Abfragen.

Welche XML-Sicherheitsrisiken kennen Sie?

XXE und Entity-Expansion wie Billion Laughs. Schutz: DTDs und externe Entities im Parser deaktivieren.

Szenario: Nach dem Upgrade auf Java 21 startet der SOAP-Client nicht mehr. Was tun Sie?

JAX-WS und JAXB sind seit Java 11 nicht mehr im JDK. Ich füge die Jakarta-Bibliotheken hinzu, generiere die Stubs neu und prüfe javax- vs jakarta-Namespaces.

Szenario: Ein Partner meldet „Signature verification failed“ seit heute Morgen. Wie gehen Sie vor?

Ich prüfe Zertifikatsablauf, Zeitabweichung beim Timestamp und Änderungen am Body nach dem Signieren. Dazu Nachrichten-Log mit Korrelations-ID vergleichen.

Szenario: Ihr Team will einen stabilen SOAP-Partnerservice durch REST ersetzen. Wie entscheiden Sie?

Ich frage nach dem Nutzen: Gibt es ein echtes Problem? Oft ist eine REST-Fassade intern und SOAP nach aussen besser. Standardverträge mit Behörden ändert man nicht einseitig.
