JAX-WS und Spring-WS

Kern: JAX-WS (heute Jakarta XML Web Services) ist die Java-API für SOAP-Services. Eine annotierte Klasse wird zum Endpoint, und die Laufzeit macht Marshalling und Fehler. Spring-WS ist ein Spring-Framework für Contract-first und routet Nachrichten nach dem Wurzelelement des Payloads.

Antwort-Muster

Frage: Was ist der Unterschied zwischen JAX-WS und Spring-WS?

  1. Mechanismus: JAX-WS macht aus einer annotierten Klasse einen Service samt WSDL. Spring-WS startet bei XSD und WSDL und wählt den Endpoint nach dem Payload-Element.
  2. Zahl: Jakarta XML Web Services 4.0 gehört zu Jakarta EE 10. JAX-WS ist seit Java 11 nicht mehr im JDK.
  3. Trade-off: JAX-WS ist schnell geschrieben, aber der Code bestimmt den Vertrag. Spring-WS verlangt zuerst den Vertrag, dafür bleibt er stabil.
  4. Produktion: Bei Partnerverträgen nehme ich Contract-first. Ich schütze Faults vor internen Texten.

1. Ein Aufruf in 6 Schritten

  1. HTTP POST: Ein Servlet nimmt die Nachricht an. Bei Spring-WS ist es der MessageDispatcherServlet. Er erweitert den DispatcherServlet von Spring.
  2. Dispatcher: Die Laufzeit liest die SOAP-Nachricht. Spring-WS hält sie je nach Message Factory im Speicher (SAAJ ist DOM-basiert) oder als Strom (Axiom).
  3. Vorverarbeitung: Bei JAX-WS laufen Handler, bei Spring-WS laufen Interceptors. Hier liegen Validierung, Logging und WS-Security.
  4. Endpoint wählen: JAX-WS ruft die Methode des @WebService-Endpoints auf. Spring-WS wählt mit @PayloadRoot nach Namespace und Wurzelname des Payloads, oder mit @SoapAction nach dem Header.
  5. JAXB und Aufruf: Das XML wird ein Objekt. Spring-WS braucht dafür einen konfigurierten Marshaller, zum Beispiel Jaxb2Marshaller mit Context-Pfad. Dann läuft die Methode.
  6. Antwort oder Fault: Der Rückgabewert wird XML. Bei Spring-WS braucht die Methode dafür @ResponsePayload. Eine Exception wird zu einem SOAP Fault.

2. Aufbau

  1. Endpoint: Bei JAX-WS ist es eine annotierte Klasse. Bei Spring-WS ist es eine Klasse mit @Endpoint und Methoden mit @PayloadRoot.
  2. Laufzeit: JAX-WS ist nur die API. Die Laufzeit kommt von einer Bibliothek wie Eclipse Metro oder Apache CXF. Spring-WS bringt seine eigene Laufzeit mit.
  3. Routing: JAX-WS bildet Operationen auf Methoden ab. Spring-WS routet nach Payload oder SOAPAction.
  4. Erweiterungen: JAX-WS nutzt Handler. Spring-WS nutzt Interceptors und Exception Resolver.
  5. Client: JAX-WS nutzt generierte Stubs oder die Dispatch-API. Spring-WS nutzt das WebServiceTemplate mit Marshaller.
  6. Vertrag: JAX-WS geht in beide Richtungen. Spring-WS unterstützt nur Contract-first.

3. Details

  1. Namen und Versionen: Jakarta XML Web Services 4.0 gehört zu Jakarta EE 10. Version 3.0 gehört zu Jakarta EE 9. Version 2.3 ist das erste Release unter Jakarta. Die Annotationen wie @WebService liegen im Paket jakarta.jws der Spezifikation Web Services Metadata.
  2. Nicht mehr im JDK: JEP 320 hat java.xml.ws mit Werkzeugen wie wsimport und wsgen in Java 11 entfernt. Die Referenzimplementierung ist als Maven-Artefakt erhältlich.
  3. @WebService-Namen: name wird der portType. serviceName ist standardmässig der Klassenname plus Service. portName ist standardmässig name plus Port. endpointInterface verweist auf ein Interface mit dem Vertrag.
  4. @SOAPBinding-Standard: Ohne Annotation gilt style DOCUMENT, use LITERAL und parameterStyle WRAPPED. Das ist document/literal wrapped.
  5. Wrapper Style: Er gilt nur, wenn Input und Output je einen Part haben. Das Input-Element heisst wie die Operation. Der Typ ist eine xsd:sequence ohne Attribute und Wildcards.
  6. Endpoint.publish: Endpoint.publish(adresse, objekt) startet einen Server für Tests. Eine http:-Adresse ergibt das SOAP-1.1/HTTP-Binding. Ein gestoppter Endpoint lässt sich nicht erneut publizieren.
  7. Client-APIs: Service ist die Client-Sicht. Dispatch sendet XML dynamisch. Provider ist die dynamische Server-Alternative. Holder trägt Ausgabeparameter. AsyncHandler meldet asynchrone Antworten.
  8. Fehler in JAX-WS: WebServiceException ist die Basis aller Laufzeitfehler. Mit @WebFault wird eine Exception ein Fault im Vertrag.
  9. Spring-WS Contract-first: Die Dokumentation sagt, es unterstütze nur Contract-first. Das vermeidet Object/XML-Impedance-Mismatch und Versionsprobleme.
  10. WSDL aus XSD: DefaultWsdl11Definition macht für jedes globale Element eine Message. Elemente mit Suffix Request und Response ergeben eine Operation. Aus GetOrdersRequest und GetOrdersResponse wird GetOrders. Für Produktion empfiehlt die Doku, die generierte WSDL zu speichern und statisch auszuliefern.
  11. Faults in Spring-WS: SoapFaultMappingExceptionResolver mappt Exception-Klassen auf Faults. @SoapFault an einer Exception legt den Fault fest. Ein defaultFault mit eigenem Text verhindert, dass unerwartete Exception-Texte nach aussen gehen.
  12. Validierung: PayloadValidatingInterceptor prüft gegen XSD. Die Doku rät, die Antwort zu validieren, weil der Endpoint sein Schema einhalten soll. Im Beispiel der Doku bleibt die Request-Validierung aus.
  13. Message Factory: SAAJ ist DOM-basiert, die ganze Nachricht liegt im Speicher. Axiom kann streamen. Beide haben laut Doku eine Standardgrenze von 10 MB. Die SOAP-Version ist standardmässig 1.1, mit soapVersion wählt man 1.2.

4. Fallen

  • „JAX-WS ist Teil des JDK.“ → Falsch. Es wurde in Java 11 entfernt (JEP 320).
  • „Spring-WS erzeugt die WSDL aus Java-Klassen.“ → Falsch. Es unterstützt nur Contract-first. Die WSDL entsteht aus der XSD.
  • „Spring-WS routet nach der URL wie Spring MVC.“ → Falsch. Es routet standardmässig nach dem Wurzelelement des Payloads oder nach der SOAPAction.
  • „JAX-WS ist eine Implementierung.“ → Falsch. Es ist eine API. Die Laufzeit kommt von Metro, CXF oder ähnlichen.
  • „Ein Endpoint-Methodenname bestimmt den Vertrag.“ → Nur bei Code-first. Bei Contract-first bestimmt die WSDL den Namen.
  • „Spring-WS Standard ist SOAP 1.2.“ → Falsch. Der Standard ist 1.1.

5. Selbsttest

Warum?

Warum bevorzugt Spring-WS Contract-first?

Der Vertrag soll stabil bleiben und nicht aus Code entstehen. Das vermeidet Impedance-Mismatch zwischen Objekten und XML und Versionsprobleme.

Warum routet Spring-WS nach dem Payload-Element?

Bei document/literal wrapped heisst das Wurzelelement im Body wie die Operation. SOAP hat sonst nur eine URL und optional eine SOAPAction.

Warum setzt man bei Spring-WS einen defaultFault?

Damit unerwartete Exceptions einen festen Text bekommen. So gehen keine internen Meldungen an den Aufrufer.

Wie innen?

Wie wird eine Klasse zu einem JAX-WS-Endpoint?

Mit @WebService. Die Laufzeit erzeugt daraus Binding und WSDL, oder man gibt mit wsdlLocation eine vorhandene WSDL an.

Welche Standardwerte hat @SOAPBinding?

Style DOCUMENT, use LITERAL, parameterStyle WRAPPED.

Wie funktioniert @PayloadRoot?

Die Annotation an einer Endpoint-Methode nennt Namespace und localPart. Eine Nachricht mit diesem Wurzelelement im Payload geht an diese Methode.

Was macht @ResponsePayload?

Sie markiert den Rückgabewert als Antwort-Payload. Ohne sie gibt es keine Antwort aus dem Rückgabewert.

Wie erzeugt Spring-WS eine WSDL?

DefaultWsdl11Definition baut sie aus der XSD. Elemente mit Request und Response ergeben Operationen. Dazu kommen portType, binding und service.

Wie wird eine Exception ein SOAP Fault?

Bei JAX-WS wird eine Exception mit @WebFault ein Fault im Vertrag. Spring-WS nutzt ExceptionResolver wie SoapFaultMappingExceptionResolver.

Wie ruft ein Spring-Client einen Service auf?

Mit WebServiceTemplate.marshalSendAndReceive. Ein Marshaller macht aus dem Objekt XML und ein Unmarshaller aus der Antwort ein Objekt.

Zahlen

Welche Version gehört zu Jakarta EE 10?

Jakarta XML Web Services 4.0. Version 3.0 gehört zu Jakarta EE 9.

Seit wann ist JAX-WS nicht mehr im JDK?

Seit Java 11. JEP 320 hat java.xml.ws sowie wsimport und wsgen entfernt.

Welche SOAP-Version nutzt Spring-WS standardmässig?

SOAP 1.1. Die Doku sagt, derzeit sei 1.1 die beste Wahl. Mit soapVersion wählt man 1.2.

Welche Grenze hat die Nachrichtengrösse in Spring-WS?

Laut Doku 10 MB als Standard, einstellbar mit maxMessageSize. Der Wert -1 hebt die Grenze auf.

Vergleich

JAX-WS gegen Spring-WS?

JAX-WS ist eine API mit Code-first und Contract-first, Spring-WS ist Contract-first mit Payload-Routing und Spring-Integration. JAX-WS braucht eine Laufzeit wie Metro oder CXF.

SAAJ gegen Axiom?

SAAJ ist DOM-basiert und hält alles im Speicher. Axiom kann streamen und eignet sich für grosse Nachrichten.

Code-first gegen Contract-first bei JAX-WS?

Code-first startet bei der annotierten Klasse und erzeugt die WSDL. Contract-first startet bei der WSDL und erzeugt Klassen mit wsimport.

Handler gegen Interceptor?

Beides sind Hooks vor und nach dem Endpoint. Handler gehören zu JAX-WS, Interceptors zu Spring-WS.

Produktion

Szenario: Der Service wirft bei Fehlern interne SQL-Texte im Fault. Was tun Sie?

Ich setze einen SoapFaultMappingExceptionResolver mit defaultFault und eigenem Text. Fachfehler bekommen eigene Faults. Details gehören ins Log.

Szenario: Spring-WS lehnt grosse Anhänge mit einem Fehler ab. Was prüfen Sie?

Die Grenze maxMessageSize der Message Factory. Für grosse Daten nehme ich MTOM und Streaming statt eine höhere Grenze.

Szenario: Ein Aufruf findet keinen Endpoint. Wie gehen Sie vor?

Ich prüfe Namespace und Wurzelname gegen @PayloadRoot. Ein falscher Namespace ist die häufigste Ursache. Ein defaultEndpoint kann Nachrichten abfangen.

Szenario: Nach dem Java-Upgrade fehlt die JAX-WS-Klasse. Was tun Sie?

JAX-WS ist seit Java 11 nicht im JDK. Ich füge Metro oder CXF als Dependency hinzu und passe bei Jakarta EE 9 oder neuer die Imports auf jakarta an.

Design

Wann nehmen Sie JAX-WS, wann Spring-WS?

Spring-WS, wenn die Anwendung ohnehin Spring nutzt und der Vertrag zuerst kommt. JAX-WS, wenn ein Application Server es bereitstellt oder ein generierter Client genügt.

Wie schützen Sie einen Service vor ungültigen Nachrichten?

Mit einem PayloadValidatingInterceptor gegen die XSD. Die Antwort validiere ich immer, die Anfrage nur bei Bedarf.

Wie versioniert man Spring-WS-Endpoints?

Mit einem Namespace pro Hauptversion in der XSD. @PayloadRoot trennt dann die Versionen nach Namespace.

Warum die generierte WSDL statisch ausliefern?

Eine zur Laufzeit erzeugte WSDL kann sich still ändern. Die Doku empfiehlt, sie nach der Entwicklung zu speichern.

Mehr

Gerüst

  • Warum? Eine Java-Schicht für SOAP, die Marshalling, Routing und Fehler übernimmt.
  • Wie innen? Servlet, Dispatcher, Handler oder Interceptors, Endpoint wählen, JAXB, Antwort oder Fault.
  • Zahlen Jakarta XML Web Services 4.0 in EE 10. Nicht im JDK seit Java 11. Spring-WS Standard SOAP 1.1.
  • Vergleich JAX-WS gegen Spring-WS. SAAJ gegen Axiom. Code-first gegen Contract-first.
  • Produktion Interne Texte im Fault. Grössengrenze. Falscher Namespace im Payload-Routing.
  • Design Contract-first, WSDL statisch, Antwort validieren, Namespace pro Version.

Beispiel: derselbe Service in beiden Welten

// JAX-WS, Code-first
@WebService(serviceName = "PersonService", targetNamespace = "urn:example:person:1")
public class PersonEndpoint {
  @WebMethod public Person getPerson(@WebParam(name = "vn") String vn) { ... }
}
// Test-Server: Endpoint.publish("http://localhost:8080/personService", new PersonEndpoint());

// Spring-WS, Contract-first (XSD mit GetPersonRequest und GetPersonResponse)
@Endpoint
public class PersonEndpoint {
  private static final String NS = "urn:example:person:1";

  @PayloadRoot(namespace = NS, localPart = "GetPersonRequest")
  @ResponsePayload
  public GetPersonResponse getPerson(@RequestPayload GetPersonRequest request) { ... }
}

@Bean(name = "person")
public DefaultWsdl11Definition wsdl(XsdSchema personSchema) {
  DefaultWsdl11Definition d = new DefaultWsdl11Definition();
  d.setPortTypeName("PersonPort");
  d.setLocationUri("/ws");
  d.setSchema(personSchema);
  return d;
}

Nicht ausgeführt. JAX-WS ist seit Java 11 nicht im JDK, und weder Metro noch Spring-WS sind auf dieser Maschine installiert.

  1. Bei JAX-WS bestimmt die Klasse den Vertrag. Namen kommen aus serviceName, name und den Parametern.
  2. Bei Spring-WS kommt der Vertrag aus der XSD. Die Elemente GetPersonRequest und GetPersonResponse ergeben die Operation GetPerson.
  3. @PayloadRoot verbindet Namespace und Wurzelname mit der Methode.
  4. @RequestPayload und @ResponsePayload lassen das Framework marshallen. Es braucht dafür einen konfigurierten Marshaller.
  5. DefaultWsdl11Definition erzeugt die WSDL aus der XSD. Für Produktion speichert man das Ergebnis.

Vergleich

  • JAX-WS: API und Annotationen, beide Richtungen, Handler, Client-Stubs, Laufzeit von Metro oder CXF.
  • Spring-WS: Nur Contract-first, Payload-Routing, Interceptors, WebServiceTemplate, WSDL aus XSD.
  • Apache CXF: Eine Laufzeit für JAX-WS.
  • Eclipse Metro: Die Referenzimplementierung von JAX-WS und JAXB.
  • REST-Controller: Routen nach URL und HTTP-Verb. SOAP-Endpoints routen nach Payload oder Operation.

Produktion

  1. Interne Texte im Fault: Exception-Meldungen erreichen den Partner. Lösung: defaultFault mit eigenem Text und eigene Faults für Fachfehler.
  2. Grosse Nachrichten: Die Grenze von 10 MB greift, oder der Speicher wächst. Lösung: MTOM, Streaming mit Axiom, begrenzte Eingaben.
  3. Kein Endpoint gefunden: Namespace oder Wurzelname im Payload weichen ab. Lösung: @PayloadRoot und XSD abgleichen.
  4. WSDL ändert sich still: Die WSDL entsteht bei jedem Start neu. Lösung: statische WSDL ausliefern.
  5. Java-Upgrade: Ab Java 11 fehlt JAX-WS im JDK. Lösung: Laufzeit als Dependency.
  6. javax gegen jakarta: Eine Bibliothek erwartet den anderen Namespace. Lösung: Versionen von Server, Framework und Bibliothek abstimmen.

Diagnose: Werkzeuge und Befehle

  • Message-Logging: Request und Response mit Korrelations-ID loggen. Achtung: Personendaten.
  • WSDL ansehen: Die Adresse mit ?wsdl (bei vielen Frameworks) oder die Datei aus der Versionskontrolle.
  • SoapUI: Gegen Test und Produktion dieselbe Nachricht senden.
  • Breakpoint im Mapping: Welcher Endpoint wird gewählt, welcher Resolver greift?
  • Interceptor-Reihenfolge prüfen: Security-Interceptors laufen vor dem Addressing-Interceptor.
  • Dependency-Baum: Gibt es zwei Laufzeiten oder gemischte javax- und jakarta-Klassen?

Senior-Punkte

  1. Contract-first ist der Standard bei Partnerverträgen. Spring-WS erzwingt es. Bei JAX-WS muss man es selbst wählen.
  2. Routing nach Payload ist eine Designfrage. Die Wurzelelemente müssen eindeutig sein, und der Namespace trägt die Version.
  3. Faults sind Schnittstelle und Schutz. Fachfehler mit Code, alles andere mit einem festen Text.
  4. Antwort validieren. Der Service soll sein eigenes Schema einhalten. Die Anfrage prüft man am Rand.
  5. Speicherverhalten kennen. SAAJ hält alles im Speicher. Für grosse Nachrichten braucht es Streaming und Grenzen.
  6. Laufzeit wählen und festhalten. API ist nicht Implementierung. Der Server oder die Anwendung bringt Metro oder CXF mit.
