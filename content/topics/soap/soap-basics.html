SOAP: Envelope, Header, Body, Fault

Kern: Eine SOAP-Nachricht ist ein XML-Dokument mit einem Envelope als Wurzel. Darin liegen ein optionaler Header für Zusatzinfos und ein Pflicht-Body mit den Nutzdaten oder einem Fault. Die Regeln für mustUnderstand, role und die Fault Codes machen aus XML ein Protokoll.

Antwort-Muster

Frage: Wie ist eine SOAP-Nachricht aufgebaut?

  1. Mechanismus: Ein Envelope enthält einen optionalen Header mit Blöcken und einen Body mit genau einem Nutzdaten-Element oder einem Fault.
  2. Zahl: SOAP 1.2 kennt fünf Fault Codes. Ein Fault braucht mindestens Code und Reason.
  3. Trade-off: Header-Blöcke mit mustUnderstand geben strenge Regeln. Dafür ist jede Nachricht gross und der Parser muss alles lesen.
  4. Produktion: Bei einem Fault lese ich zuerst Code und Subcode, dann Detail. Sender heisst, ich sende nicht unverändert nochmals.

1. Eine Nachricht in 6 Schritten

  1. Envelope bauen: Der Sender erzeugt das Wurzelelement Envelope. Er legt optionale Header-Blöcke und ein Body-Kind hinein.
  2. Transport: Meist geht die Nachricht als HTTP POST. SOAP 1.1 nutzt text/xml und den Header SOAPAction. SOAP 1.2 nutzt application/soap+xml mit dem Parameter action.
  3. Namespace prüfen: Der Empfänger liest den Namespace des Envelope. Kennt er ihn nicht, sendet er einen VersionMismatch-Fault.
  4. Header verarbeiten: Jeder Knoten prüft die Blöcke für seine Rolle. Ein Block mit mustUnderstand true, den er nicht versteht, ergibt einen MustUnderstand-Fault. Danach läuft keine weitere Verarbeitung.
  5. Body verarbeiten: Der letzte Empfänger (Ultimate Receiver) muss die direkten Kinder des Body korrekt verarbeiten. Dann führt er die Operation aus.
  6. Antwort: Der Body der Antwort enthält die Nutzdaten. Bei einem Fehler enthält er einen Fault als einziges Kind.

Ein Zwischenknoten (Intermediary) verarbeitet nur Header-Blöcke und leitet die Nachricht weiter. Er muss alle verarbeiteten Blöcke entfernen.

2. Aufbau

  1. Envelope: Das Wurzelelement. Es hat einen optionalen Header und einen Pflicht-Body, in dieser Reihenfolge.
  2. Header-Block: Ein Kind des Header. Es muss einen Namespace haben. So wissen Knoten, wer den Block versteht.
  3. Body: Er enthält die Nutzdaten. Im Stil document/literal hat er genau ein Kind nach XSD.
  4. Fault: Er ersetzt die Nutzdaten bei einem Fehler. Er ist nur gültig als einziges Kind des Body.
  5. Code und Reason: Code ist ein maschinenlesbarer Wert. Reason ist der Text für Menschen, mit xml:lang.
  6. Detail: Hier stehen fachliche Fehlerdaten, zum Beispiel ein eigener Fehlercode.

3. Details

  1. Envelope-Namespace: SOAP 1.1 nutzt http://schemas.xmlsoap.org/soap/envelope/. SOAP 1.2 nutzt http://www.w3.org/2003/05/soap-envelope. Daran erkennt der Empfänger die Version.
  2. VersionMismatch: Ein unbekannter Envelope-Namespace ergibt diesen Fault. Der Knoten sollte einen Upgrade-Header-Block mit SupportedEnvelope mitschicken. Er listet die bekannten Versionen.
  3. mustUnderstand: Der Wert ist in SOAP 1.2 ein xs:boolean. Fehlt das Attribut, gilt false. In SOAP 1.1 sind nur 1 und 0 gültig. Bei true muss der Knoten den Block verarbeiten, sonst gibt es einen Fault.
  4. role (SOAP 1.1: actor): Es sagt, welcher Knoten den Block verarbeitet. Fehlt es, gilt ultimateReceiver. SOAP 1.2 definiert next, none und ultimateReceiver.
  5. relay: Dieses Attribut gibt es nur in SOAP 1.2. Mit true leitet ein Zwischenknoten einen Block weiter, den er nicht verarbeitet hat. Bei mustUnderstand true hat es keine Wirkung.
  6. Fault in SOAP 1.2: Ein Fault hat Code und Reason als Pflicht. Optional sind Node, Role und Detail. Node muss ein Zwischenknoten setzen, wenn er den Fault erzeugt.
  7. Fault Codes 1.2: Es gibt VersionMismatch, MustUnderstand, DataEncodingUnknown, Sender und Receiver. Ein Subcode verfeinert den Code. Er ist ein QName und kann geschachtelt sein.
  8. Fault in SOAP 1.1: Die Kinder heissen faultcode, faultstring, faultactor und detail. Die Codes sind VersionMismatch, MustUnderstand, Client und Server. Client entspricht Sender, Server entspricht Receiver.
  9. Sender oder Receiver: Sender heisst, die Nachricht ist fehlerhaft. Ein unveränderter Versuch lohnt nicht. Receiver heisst, der Fehler liegt beim Server. Ein späterer Versuch kann klappen.
  10. detail in SOAP 1.1: Das Element ist Pflicht, wenn der Body nicht verarbeitet werden konnte. Es darf keine Fehler über Header-Einträge enthalten. Fehlt es, hat der Fehler mit dem Body nichts zu tun.
  11. HTTP-Status bei Faults: In SOAP 1.1 und im WS-I Basic Profile ist es immer 500. SOAP 1.2 nennt in einer Tabelle 400 für Sender und 500 für Receiver, MustUnderstand und VersionMismatch.
  12. Body bei document/literal: Das WS-I Basic Profile erlaubt null oder ein Kind im Body (R9981). Ein Fault ist eines davon. Die Kinder sollen einen Namespace haben.
  13. Transport: SOAP ist nicht an HTTP gebunden. Beim HTTP-Binding von SOAP 1.2 entspricht POST dem Request-Response-Muster. GET entspricht dem Response-Muster ohne Request-Envelope.

4. Fallen

  • „Ein Fault braucht immer HTTP 500.“ → Falsch. SOAP 1.2 nennt für Sender 400. Nur SOAP 1.1 und das WS-I Basic Profile verlangen 500.
  • „Der Header ist Pflicht.“ → Falsch. Er ist optional. Der Body ist Pflicht.
  • „Fault Codes heissen immer Client und Server.“ → Falsch. Das ist SOAP 1.1. SOAP 1.2 nutzt Sender und Receiver.
  • „mustUnderstand heisst, der Server muss den Header validieren.“ → Falsch. Er muss den Block verstehen und verarbeiten. Sonst gibt es einen Fault.
  • „Ein Fault darf neben anderen Elementen im Body stehen.“ → Falsch. Er zählt nur, wenn er das einzige Kind des Body ist.
  • „Der Header ist nur für Sicherheit da.“ → Falsch. Er trägt jede Zusatzinfo mit eigenem Namespace, etwa Routing, Korrelation oder Addressing.

5. Selbsttest

Warum?

Warum gibt es den Header neben dem Body?

Der Header trägt Zusatzinfos wie Sicherheit oder Routing. Die Nutzdaten im Body bleiben davon unberührt. Zwischenknoten können Blöcke verarbeiten, ohne den Body zu kennen.

Warum gibt es mustUnderstand?

Ein Sender kann damit erzwingen, dass ein Block verarbeitet wird. Versteht der Empfänger ihn nicht, gibt es einen Fault. So wird eine Signatur nie still ignoriert.

Warum heisst es Sender und Receiver statt Client und Server?

SOAP 1.2 beschreibt Knoten in einer Kette, nicht nur Client und Server. Es sagt, wer die Ursache des Fehlers ist.

Wie innen?

Welche Teile hat eine SOAP-Nachricht?

Envelope als Wurzel, ein optionaler Header mit Blöcken und ein Pflicht-Body mit Nutzdaten oder einem Fault.

Was passiert, wenn ein Header-Block mit mustUnderstand true nicht verstanden wird?

Der Knoten erzeugt einen Fault mit Code MustUnderstand und verarbeitet nichts weiter. Er sollte NotUnderstood-Blöcke mitschicken.

Welche Rolle hat ein Zwischenknoten?

Er verarbeitet Header-Blöcke für die Rolle next oder seine eigene Rolle. Er entfernt verarbeitete Blöcke und leitet die Nachricht weiter.

Wie ist ein Fault in SOAP 1.2 aufgebaut?

Code mit Value und optionalem Subcode, Reason mit Text und xml:lang, dazu optional Node, Role und Detail. Der Fault ist das einzige Kind des Body.

Wie erkennt ein Empfänger die SOAP-Version?

Am Namespace des Envelope. Ein unbekannter Namespace ergibt einen VersionMismatch-Fault.

Was ist der Unterschied zwischen Code und Subcode?

Code ist einer der fünf festen Werte. Subcode ist ein anwendungsdefinierter QName, der den Code verfeinert, zum Beispiel eine Fachfehler-Klasse.

Wie werden Faults im Java-Client sichtbar?

Ein SOAP Fault wird eine Exception. Mit JAX-WS ist es eine SOAPFaultException. Ein im WSDL deklarierter Fault wird eine eigene Exception mit der Annotation WebFault.

Zahlen

Wie viele Fault Codes hat SOAP 1.2?

Fünf. VersionMismatch, MustUnderstand, DataEncodingUnknown, Sender und Receiver.

Welche Fault Codes hat SOAP 1.1?

Vier. VersionMismatch, MustUnderstand, Client und Server.

Welchen HTTP-Status hat ein Fault?

SOAP 1.1 und das WS-I Basic Profile verlangen 500. SOAP 1.2 nennt 400 für Sender und 500 für die anderen Codes.

Welche Werte hat mustUnderstand?

SOAP 1.1 kennt 1 und 0. SOAP 1.2 kennt einen Boolean. Senden soll man true, empfangen muss man jede gültige Form.

Vergleich

SOAP 1.1 gegen SOAP 1.2?

1.1 nutzt text/xml, SOAPAction und Client/Server. 1.2 nutzt application/soap+xml, den Parameter action und Sender/Receiver. 1.2 hat auch relay und Subcode.

Fault gegen HTTP-Fehlercode in REST?

Ein SOAP Fault ist ein XML-Body mit Code und Detail. REST trägt den Fehler im HTTP-Status und oft in einem Problem-Body.

role next gegen ultimateReceiver?

Next trifft jeden Knoten, auch Zwischenknoten. UltimateReceiver trifft nur den letzten Empfänger. Fehlt role, gilt ultimateReceiver.

Header-Block gegen Body-Kind?

Header-Blöcke sind Zusatzinfos mit Rollen und mustUnderstand. Das Body-Kind sind die Nutzdaten für den letzten Empfänger.

Produktion

Szenario: Ein Partner meldet MustUnderstand-Faults seit gestern. Was prüfen Sie?

Ich lese den Fault und die NotUnderstood-Blöcke. Wahrscheinlich sendet der Partner einen neuen Header-Block, den unser Knoten nicht kennt. Ich prüfe, ob eine Handler-Konfiguration oder ein Update fehlt.

Szenario: Der Client wiederholt bei jedem Fault die Anfrage endlos. Was ändern Sie?

Ich unterscheide Sender und Receiver. Bei Sender gibt es kein Retry. Bei Receiver gibt es begrenzte Retries mit Wartezeit.

Szenario: Ein Fault zeigt nur „Internal Error“. Wie verbessern Sie das?

Ich setze einen fachlichen Code im Detail und einen Subcode. Dazu gebe ich eine Korrelations-ID im Header zurück. Interne Stacktraces gehören nicht in den Fault.

Warum leckt ein Fault manchmal interne Daten?

Manche Frameworks schreiben die Exception-Meldung in den Reason. Darin können Pfade oder SQL stehen. Man mappt Exceptions auf eigene Faults ohne Interna.

Design

Wann nutzt man einen Header-Block statt eines Feldes im Body?

Wenn die Info quer zur Operation gilt, etwa Sicherheit, Korrelation oder Routing. Fachdaten gehören in den Body.

Wie modelliert man Fachfehler?

Als Fault mit Detail-Element nach XSD. Im WSDL deklariert man es mit wsdl:fault. So kennt der Client die Fehlertypen im Voraus.

Darf man mustUnderstand für eigene Header setzen?

Ja, wenn der Block zwingend verarbeitet werden muss, zum Beispiel eine Signatur. Für optionale Infos wie Tracing lässt man es weg.

Warum ist eine Korrelations-ID im Header sinnvoll?

Sie ist Zusatzinfo und gehört nicht zu den Fachdaten. Alle Knoten können sie loggen. So findet man eine Anfrage über Systeme hinweg.

Mehr

Gerüst

  • Warum? Eine einheitliche Hülle trennt Nutzdaten von Zusatzinfos. Header-Regeln und Faults sind standardisiert.
  • Wie innen? Envelope-Namespace prüfen, Header-Blöcke je Rolle, mustUnderstand erzwingen, Body verarbeiten, Antwort oder Fault.
  • Zahlen 5 Fault Codes in 1.2 (4 in 1.1). Code und Reason sind Pflicht. 1.2 nennt HTTP 400 für Sender.
  • Vergleich 1.1 gegen 1.2: text/xml und SOAPAction gegen application/soap+xml und action. Client/Server gegen Sender/Receiver.
  • Produktion MustUnderstand durch neue Header. Retry-Schleifen bei Sender-Fehlern. Fault mit internen Daten.
  • Design Querschnitt im Header, Fachdaten im Body. Fachfehler im Detail mit Subcode.

Beispiel: Nachrichten mit DOM prüfen

f.setNamespaceAware(true);
f.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
Element env = f.newDocumentBuilder().parse(in).getDocumentElement();
String ns = env.getNamespaceURI();            // Version aus dem Envelope-Namespace
// pro Header-Block: mustUnderstand, role/actor lesen
String mu = b.getAttributeNS(ns, "mustUnderstand");
boolean must = mu.equals("1") || (v12 && mu.equals("true"));
// Body: ein einziges Kind namens Fault? Dann Code/Reason/Detail ausgeben

Vier Testnachrichten: ein 1.1-Fault, ein 1.2-Fault mit Subcode, eine Nachricht mit drei Header-Blöcken (der Knoten versteht nur urn:example:trace:1) und ein Envelope mit fremdem Namespace.

== 1.1 Fault
  Version: SOAP 1.1
  Fault.faultcode = e:Client
  Fault.faultstring = Ungueltige Nummer
  Fault.detail = VN
== 1.2 Fault mit Subcode
  Version: SOAP 1.2
  Fault.Code.Value = e:Sender  Subcode = x:VnChecksum
  Fault.Reason = Ungueltige Nummer
== 1.2 Header mustUnderstand
  Version: SOAP 1.2
  Header trace mustUnderstand=true role=(fehlt) verstanden=true
  Header sig mustUnderstand=true role=http://www.w3.org/2003/05/soap-envelope/role/next verstanden=false  -> MustUnderstand-Fault
  Header opt mustUnderstand=(fehlt) role=(fehlt) verstanden=false
  Body: 1 Kind, getPerson
== falscher Namespace
  Envelope-Namespace http://example.org/soap/9 -> VersionMismatch

Echte Ausgabe, OpenJDK 17.0.3 (nur javax.xml.parsers, keine SOAP-Bibliothek).

  1. Der Namespace des Envelope entscheidet über die Version. Der Fault Code heisst in 1.1 Client und in 1.2 Sender mit Subcode.
  2. Der Block sig hat mustUnderstand true und wird nicht verstanden. Der Knoten müsste jetzt einen MustUnderstand-Fault senden.
  3. Der Block opt hat kein mustUnderstand. Der Knoten darf ihn ignorieren.
  4. Der Body hat genau ein Kind. Bei einem Fault wäre dieses Kind der Fault.

Vergleich

  • SOAP 1.1: W3C Note von 2000, text/xml, SOAPAction Pflicht, Attribut actor, Faults Client und Server.
  • SOAP 1.2: W3C Recommendation, application/soap+xml, Parameter action, Attribut role, relay, Subcode.
  • WS-I Basic Profile 1.1: baut auf SOAP 1.1 auf. Es verlangt HTTP POST, literal use und HTTP 500 für Faults.
  • REST-Fehler: HTTP-Status und Body (zum Beispiel Problem Details). Kein Fault-Standard im Body.

Produktion

  1. MustUnderstand-Fault nach einem Partner-Update: Ein neuer Header-Block ist beim Empfänger unbekannt. Lösung: Block mit dem Partner abstimmen und Handler ergänzen.
  2. Endlose Retries: Der Client wiederholt auch Sender-Faults. Lösung: Retry nur bei Receiver, mit Backoff und Obergrenze.
  3. Fault verrät Interna: Der Reason enthält Stacktrace oder SQL. Lösung: Exceptions auf eigene Faults mit festem Code mappen.
  4. Falsche HTTP-Behandlung: Ein Proxy oder Client wirft bei 500 die Antwort weg. Lösung: Body auch bei 500 lesen. Der Fault steckt dort.
  5. VersionMismatch: Ein Client sendet SOAP 1.2 an einen 1.1-Endpoint. Lösung: Binding in der WSDL prüfen und richtige Version nutzen.
  6. Fachfehler ohne Struktur: Nur Freitext im Reason. Lösung: Detail-Element nach XSD und Subcode.

Diagnose: Werkzeuge und Befehle

  • SoapUI oder ein HTTP-Proxy: Request und Response roh ansehen, inklusive Fault.
  • curl -v -H "Content-Type: text/xml" -H "SOAPAction: """ --data @req.xml URL: SOAP 1.1 von Hand senden.
  • Envelope-Namespace prüfen: Passt er zur Version des Endpoints?
  • HTTP-Status und Content-Type der Antwort lesen: text/xml oder application/soap+xml.
  • xmllint oder ein Parser: Ist die Antwort wohlgeformt? Bei malformed ist oft ein Proxy mit HTML-Fehlerseite schuld.
  • Message-Logging im Framework mit Korrelations-ID. Achtung: Personendaten im Log.

Senior-Punkte

  1. Fault ist ein Vertragsteil. Man deklariert Fachfehler im WSDL. Dann sind sie Teil der Schnittstelle und testbar.
  2. Sender und Receiver steuern Retries. Das ist die wichtigste praktische Folge der Fault Codes.
  3. Header-Blöcke sind Erweiterungspunkte. Neue Querschnittsfunktionen kommen in den Header. Der Body-Vertrag bleibt stabil.
  4. mustUnderstand sparsam setzen. Es macht Nachrichten strikt, aber ein unbekannter Block bricht den ganzen Aufruf.
  5. Faults nie mit Interna füllen. Details für Menschen gehören ins Log, nicht in die Antwort.
  6. Version bewusst wählen. Viele Partner und das WS-I Basic Profile bleiben bei SOAP 1.1. Man folgt dem Partnervertrag.
