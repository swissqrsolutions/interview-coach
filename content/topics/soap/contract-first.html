Contract-First vs Code-First

Kern: Bei Contract-first schreibt man zuerst den Vertrag (XSD und WSDL) und erzeugt daraus den Code. Bei Code-first schreibt man zuerst Java-Klassen und leitet den Vertrag daraus ab. Zwischen Organisationen ist der Vertrag das Produkt, darum ist Contract-first der übliche Weg.

Antwort-Muster

Frage: Contract-first oder Code-first, was wählen Sie?

  1. Mechanismus: Contract-first startet bei XSD und WSDL und generiert Klassen mit xjc und wsimport. Code-first startet bei annotierten Klassen und erzeugt die WSDL.
  2. Zahl: Ein neues Pflichtelement bricht alte Sender. Ein neues optionales Element bricht nur strenge, alte Empfänger.
  3. Trade-off: Code-first ist schneller am Anfang. Contract-first hält den Vertrag stabil, auch wenn der Code sich ändert.
  4. Produktion: Bei Partnern wähle ich Contract-first, validiere alte Nachrichten gegen jedes neue Schema und liefere eine statische WSDL.

1. Contract-first in 6 Schritten

  1. XSD schreiben: Man legt Elemente, Typen und Einschränkungen fest. Hier entscheidet man über Namespaces, Pflichtfelder und Erweiterungspunkte.
  2. WSDL schreiben oder erzeugen: Man definiert Operationen, Binding und Adresse. Spring-WS erzeugt sie mit DefaultWsdl11Definition aus der XSD.
  3. Beispielnachrichten: Man schreibt gültige und ungültige Beispiele und prüft sie gegen die XSD.
  4. Code generieren: xjc erzeugt die Datenklassen. wsimport erzeugt Service-Interface und Client-Stubs.
  5. Endpoint implementieren: Man schreibt nur die Fachlogik. Das generierte Interface gibt die Signatur vor.
  6. Vertrag testen: Alte Nachrichten laufen gegen das neue Schema. So findet man Brüche vor dem Release.

2. Aufbau

  1. Contract-first: XSD und WSDL sind die Quelle. Generatoren erzeugen Klassen und Stubs.
  2. Code-first: Annotierte Klassen sind die Quelle. Die Laufzeit erzeugt WSDL und XSD.
  3. Versionierung: Ein Namespace pro Hauptversion. Kompatible Änderungen bleiben im selben Namespace.
  4. Vertragstests: Beispielnachrichten gegen die XSD. Alte Nachrichten gegen das neue Schema.
  5. Statische WSDL: Die Datei liegt in der Versionskontrolle. Sie ändert sich nur bewusst.
  6. Generierter Code: Er entsteht im Build und wird nicht eingecheckt oder editiert.

3. Details

  1. Spring-WS Begründung: Die Dokumentation sagt, Spring-WS unterstütze nur Contract-first. Sie nennt als Probleme von Contract-last den Object/XML-Impedance-Mismatch, Fragilität und Versionsprobleme. Beispiele sind XSD-Erweiterungen, nicht portable Typen und zyklische Graphen.
  2. Der Code bestimmt die Namen: Bei Code-first kommen Namen aus dem Code. serviceName ist standardmässig Klassenname plus Service, portName ist name plus Port. Der Standard für targetNamespace ist von der Implementierung abhängig. Ein Refactoring kann den Vertrag ändern.
  3. Code-first mit Vertrag festnageln: Mit wsdlLocation nennt man eine vorhandene WSDL. Mit endpointInterface legt man den Vertrag in ein Interface. So wird Code-first stabiler.
  4. Wrapper Style als Regel: Ein Generator erzeugt normale Methodenparameter nur unter Bedingungen. Input und Output haben je einen Part. Das Input-Element heisst wie die Operation. Die XSD folgt also einer Konvention.
  5. Basic Profile: Das WS-I Basic Profile verlangt literal use und verbietet encoded. Ein Binding ist entweder rpc-literal oder document-literal. Ein Contract-first-Vertrag hält das von Anfang an ein.
  6. Kompatibilität: Der Test zeigt vier Fälle. Ein optionales Element bricht alte Nachrichten nicht, aber ein altes Schema lehnt Nachrichten mit dem neuen Element ab. Ein Pflichtelement bricht alte Nachrichten. Ein neuer Enum-Wert bricht alte Schemas. Ein entfernter Enum-Wert bricht alte Nachrichten.
  7. Tolerant empfangen: Ein Empfänger, der unbekannte Elemente zulässt, übersteht optionale Ergänzungen. Mit xs:any und namespace="##other" lässt ein Schema fremde Elemente zu.
  8. Namespace als Version: Bei einem echten Bruch führt man einen neuen Namespace ein. Die Elementnamen ändern sich dann, und beide Versionen laufen parallel.
  9. WSDL statisch ausliefern: Spring-WS kann die WSDL zur Laufzeit erzeugen. Die Doku empfiehlt, sie für den Betrieb zu speichern, damit sie sich nicht ändert.
  10. Generierung im Build: xjc und wsimport sind seit Java 11 nicht mehr im JDK (JEP 320). Man nutzt die Referenzimplementierungen als Build-Plugin.
  11. Wann Code-first passt: Für interne Services, die nur ein Team nutzt, und für schnelle Prototypen. Der Vertrag darf sich dort ändern, weil alle Beteiligten mitziehen.
  12. Ein Vertrag von aussen: Gibt ein Partner oder ein Standard die XSD vor, ist die Frage entschieden. Man generiert aus der gegebenen XSD.

4. Fallen

  • „Ein optionales Element ist immer abwärtskompatibel.“ → Nur teilweise. Alte Nachrichten bleiben gültig. Ein altes, striktes Schema lehnt neue Nachrichten ab.
  • „Code-first und Contract-first geben dieselbe WSDL.“ → Falsch. Bei Code-first bestimmt der Code Namen und Namespace. Sie ändern sich mit dem Code.
  • „Die WSDL darf zur Laufzeit generiert werden.“ → Riskant. Sie kann sich still ändern. Besser ist eine statische Datei.
  • „Einen neuen Enum-Wert kann man jederzeit ergänzen.“ → Falsch. Alte Schemas lehnen ihn ab.
  • „Generierte Klassen darf man anpassen.“ → Falsch. Die nächste Generierung überschreibt sie. Man passt die XSD oder die Binding-Datei an.
  • „Spring-WS kann Code-first.“ → Falsch. Es unterstützt nur Contract-first.

5. Selbsttest

Warum?

Warum ist Contract-first bei Partnern der bessere Weg?

Der Vertrag ist das Produkt und bleibt stabil. Code kann sich ändern, ohne dass Partner brechen. Beide Seiten generieren aus derselben XSD.

Warum nennt Spring-WS Code-first fragil?

Weil Typen im Code nicht portabel auf XSD abbildbar sind. Zyklische Graphen und XSD-Erweiterungen gehen verloren. Kleine Code-Änderungen ändern den Vertrag.

Warum eine statische WSDL?

Eine zur Laufzeit erzeugte WSDL kann sich bei Code-Änderungen still ändern. Eine Datei in der Versionskontrolle zeigt jede Änderung.

Wie innen?

Wie läuft Contract-first ab?

XSD und WSDL schreiben, Beispiele prüfen, mit xjc und wsimport generieren, Endpoint implementieren, Vertrag testen.

Wie läuft Code-first ab?

Klasse mit @WebService annotieren. Die Laufzeit erzeugt WSDL und XSD. Mit wsgen kann man sie vorab erzeugen.

Wie legt man bei Code-first den Vertrag fest?

Mit endpointInterface für ein Vertrags-Interface und mit explizitem targetNamespace und Namen. Mit wsdlLocation nennt man eine vorhandene WSDL.

Wie erzeugt Spring-WS die WSDL?

DefaultWsdl11Definition liest die XSD. Elemente mit Request und Response ergeben Operationen.

Was ist ein Vertragstest?

Ein Test, der Beispielnachrichten gegen die XSD prüft. Alte Nachrichten gegen das neue Schema zeigen Brüche.

Was passiert mit generiertem Code im Repository?

Er sollte im Build entstehen und nicht eingecheckt werden. Die XSD ist die Quelle.

Zahlen

Welche Änderung bricht alte Sender?

Ein neues Pflichtelement und ein entfernter Enum-Wert. Alte Nachrichten sind danach gegen das neue Schema ungültig.

Welche Änderung bricht alte Empfänger?

Ein neues Element und ein neuer Enum-Wert. Das alte, strikte Schema lehnt neue Nachrichten ab.

Seit wann gibt es wsimport und xjc nicht mehr im JDK?

Seit Java 11. JEP 320 hat sie entfernt.

Welche Standardnamen gelten bei @WebService?

serviceName ist Klassenname plus Service. portName ist name plus Port. name ist der einfache Klassenname.

Vergleich

Contract-first gegen Code-first?

Contract-first: Vertrag zuerst, stabil, mehr Aufwand am Anfang. Code-first: schnell, aber der Code bestimmt den Vertrag.

XSD ändern gegen Namespace erneuern?

Kompatible Änderungen bleiben im Namespace. Bei einem Bruch führt man einen neuen Namespace ein und betreibt beide Versionen parallel.

Streng gegen tolerant empfangen?

Streng findet Fehler früh, bricht aber bei Ergänzungen. Tolerant, zum Beispiel mit xs:any, übersteht optionale Ergänzungen.

wsimport gegen wsgen?

wsimport erzeugt Java aus der WSDL. wsgen erzeugt WSDL aus Java-Klassen.

Produktion

Szenario: Ein Partner meldet nach Ihrem Release „ungültige Nachricht“. Was prüfen Sie?

Ich vergleiche die alte und die neue XSD. Wahrscheinlich ist ein Pflichtelement oder ein Typ neu. Ich stelle Kompatibilität wieder her oder biete einen neuen Namespace an.

Szenario: Ein Refactoring ändert den Namen einer Operation in der WSDL. Wie verhindern Sie das künftig?

Mit Contract-first oder einem Vertrags-Interface und einer statischen WSDL. Ein Test vergleicht die generierte mit der gespeicherten WSDL.

Szenario: Zwei Partner verlangen verschiedene Versionen desselben Vertrags. Was tun Sie?

Ich betreibe beide Versionen mit eigenen Namespaces. Die Fachlogik liegt gemeinsam, nur die Adapter unterscheiden sich.

Szenario: Der Build erzeugt andere Klassen als gestern. Warum?

Die XSD oder die Generator-Version hat sich geändert. Ich fixiere Version und Binding-Datei und prüfe den Diff der XSD.

Design

Wie planen Sie Erweiterbarkeit in der XSD?

Mit optionalen Elementen und einem xs:any-Erweiterungspunkt. Ein Enum nur dann, wenn die Werte fix sind, sonst ein String mit Codeliste.

Wie testen Sie Kompatibilität automatisch?

In der CI laufen gespeicherte Nachrichten früherer Versionen gegen die neue XSD. Schlägt eine fehl, ist es ein Bruch.

Wann ist Code-first vertretbar?

Bei internen Services mit einem Team und bei Prototypen. Sobald ein externer Partner dazukommt, wechselt man zu Contract-first.

Wie gehen Sie mit einem vorgegebenen Standard-Schema um?

Ich generiere die Klassen aus dem Standard und ändere nichts daran. Eigene Felder kommen in eigene Erweiterungspunkte oder eigene Klassen.

Mehr

Gerüst

  • Warum? Ein stabiler, prüfbarer Vertrag unabhängig vom Code.
  • Wie innen? XSD, WSDL, Beispiele, Generator, Endpoint, Vertragstests.
  • Zahlen Pflichtelement bricht Sender. Neues Element bricht strenge Empfänger. wsimport und xjc seit Java 11 nicht im JDK.
  • Vergleich Contract-first gegen Code-first. Streng gegen tolerant. Neuer Namespace gegen kompatible Änderung.
  • Produktion Vertragsbruch durch Release. Refactoring ändert die WSDL. Zwei Versionen parallel.
  • Design xs:any als Erweiterungspunkt, Vertragstests in der CI, statische WSDL.

Beispiel: Kompatibilität mit dem Validator prüfen

// Schema v1: order mit id (int) und status (Enum A, B)
// Vier Änderungen, je zwei Richtungen:
//   alte Nachricht gegen neues Schema   (sind alte Sender noch gültig?)
//   neue Nachricht gegen altes Schema   (nehmen alte Empfänger neue Daten an?)
valid(schema("A,B", optionalNote), msg("A", ""));
valid(schema("A,B"),               msg("A", "<o:note>x</o:note>"));
Aenderung                   | alte Nachricht, neues Schema | neue Nachricht, altes Schema
optionales Element dazu     | gueltig                      | UNGUELTIG
Pflichtelement dazu         | UNGUELTIG                    | UNGUELTIG
Enum-Wert C dazu            | gueltig                      | UNGUELTIG
Enum-Wert B entfernt        | UNGUELTIG                    | gueltig

Echte Ausgabe, OpenJDK 17.0.3 (javax.xml.validation, XSD 1.0). Die Schemas sind selbst geschrieben und fiktiv.

  1. Ein optionales Element bricht keine alten Nachrichten. Ein striktes altes Schema lehnt neue Nachrichten mit dem Element aber ab.
  2. Ein Pflichtelement macht alle alten Nachrichten ungültig. In der zweiten Spalte steht UNGUELTIG, weil das alte Schema das neue Element nicht kennt.
  3. Ein neuer Enum-Wert ist für alte Sender harmlos, aber alte Empfänger lehnen ihn ab.
  4. Ein entfernter Enum-Wert bricht alte Sender. Neue Nachrichten mit einem gültigen Wert bleiben für das alte Schema gültig.
  5. Dieser Test gehört als Vertragstest in die CI, mit gespeicherten echten Nachrichten statt der Beispiele.

Vergleich

  • Contract-first: Vertrag ist die Quelle. Stabil, gut für Partner. Mehr Aufwand am Anfang.
  • Code-first: Klasse ist die Quelle. Schnell, gut intern. Vertrag kann sich mit dem Code ändern.
  • Code-first mit Interface und wsdlLocation: Ein Mittelweg. Das Interface oder die Datei fixiert den Vertrag.
  • OpenAPI Contract-first: Dasselbe Prinzip bei REST. Man schreibt die Beschreibung zuerst und generiert daraus.
  • Consumer-driven Contracts: Konsumenten legen fest, was sie brauchen. Ein Test prüft, ob der Anbieter es liefert.

Produktion

  1. Vertragsbruch durch ein Release: Ein neues Pflichtfeld oder ein neuer Typ bricht Partner. Lösung: Vertragstests mit alten Nachrichten in der CI.
  2. Refactoring ändert die WSDL: Eine Klasse wird umbenannt, der Service-Name ändert sich. Lösung: explizite Namen, Interface oder Contract-first.
  3. WSDL ändert sich zwischen Umgebungen: Sie wird bei jedem Start erzeugt. Lösung: statische WSDL aus der Versionskontrolle.
  4. Unterschiedliche Generator-Version: Lokal und in der CI entstehen andere Klassen. Lösung: Version fixieren, Generierung im Build.
  5. Enum erweitert: Alte Empfänger lehnen neue Werte ab. Lösung: Erweiterbarkeit früh planen, zum Beispiel String mit Codeliste.
  6. Zwei Versionen parallel: Doppelte Logik. Lösung: gemeinsame Fachlogik, getrennte Adapter je Namespace.

Diagnose: Werkzeuge und Befehle

  • Diff der XSD und WSDL zwischen zwei Versionen: Pflichtfelder, Typen und Enum-Werte suchen.
  • xmllint --noout --schema neu.xsd alt.xml: Alte Nachricht gegen das neue Schema prüfen.
  • SoapUI: WSDL importieren, Requests erzeugen, Mock-Service gegen den Vertrag bauen.
  • Generierte Klassen vergleichen: Ein Diff zwischen zwei Generierungen zeigt Vertragsänderungen als Codeänderung.
  • WSDL aus dem laufenden Service holen und mit der gespeicherten vergleichen. Ein Unterschied ist ein Fehler.
  • Build-Log des Generators: Warnungen zu Namenskonflikten oder nicht abbildbaren Typen lesen.

Senior-Punkte

  1. Der Vertrag ist das Produkt. Bei Partnern pflegt man XSD und WSDL wie Quellcode, mit Review und Versionen.
  2. Kompatibilität ist eine Richtung. Man fragt immer zuerst, wer alt und wer neu ist. Sender und Empfänger brechen aus verschiedenen Gründen.
  3. Erweiterungspunkte früh einbauen. Ein xs:any mit fremdem Namespace erlaubt Ergänzungen ohne neue Version.
  4. Vertragstests in die CI. Gespeicherte Nachrichten früherer Versionen sind das billigste Sicherheitsnetz.
  5. Code-first nur mit Absicht. Für interne Dienste ist es in Ordnung. Sobald ein Partner den Vertrag nutzt, wird er festgeschrieben.
  6. Generierter Code ist Wegwerf-Code. Man ändert die Quelle und generiert neu.
