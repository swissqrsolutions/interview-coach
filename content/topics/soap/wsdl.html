WSDL

Kern: Eine WSDL beschreibt einen Web Service als XML-Vertrag. Der abstrakte Teil (types, message, portType) sagt, welche Operationen und Daten es gibt. Der konkrete Teil (binding, service) sagt, wie und wo man sie aufruft.

Antwort-Muster

Frage: Was steht in einer WSDL-Datei?

  1. Mechanismus: Types (XSD), Messages und ein PortType beschreiben die Operationen. Ein Binding legt SOAP über HTTP fest und ein Service nennt die Adresse.
  2. Zahl: WSDL 1.1 hat fünf Hauptelemente und vier Operationsarten. WSDL 1.1 ist ein W3C Note, WSDL 2.0 eine Recommendation.
  3. Trade-off: Die Trennung erlaubt mehrere Bindings für einen PortType. Dafür ist die Datei lang und stark verschachtelt.
  4. Produktion: Ich prüfe zuerst, ob die WSDL erreichbar ist und die richtige Endpoint-Adresse enthält.

1. Eine WSDL lesen in 6 Schritten

  1. service: Der Einstieg. Er enthält einen oder mehrere port-Einträge.
  2. port: Er verbindet ein binding mit einer Adresse. Bei SOAP steht sie in soap:address als location.
  3. binding: Es legt Protokoll und Stil fest. Es hat soap:binding mit style und transport, je Operation soap:operation mit soapAction und je Nachricht soap:body mit use.
  4. portType: Es verweist über type vom Binding aus. Es listet die Operationen mit input, output und fault.
  5. message: Jede Nachricht hat part-Elemente. Ein Part zeigt auf ein Element oder einen Typ.
  6. types: Hier steht die XSD. Das Part-Element zeigt auf ein globales Element, zum Beispiel getPerson.

2. Aufbau

  1. definitions: Das Wurzelelement mit targetNamespace und den Namespace-Präfixen.
  2. types: Die Datentypen als XSD, meist inline oder per xs:import.
  3. message und part: Die abstrakten Nachrichten. Ein part zeigt auf element oder type.
  4. portType: Die Operationen als abstrakte Schnittstelle. Es ist das Gegenstück zu einem Java-Interface.
  5. binding: Es macht den portType konkret. Es kann mehrere Bindings für einen portType geben, zum Beispiel SOAP 1.1 und 1.2.
  6. service und port: Die Adresse, unter der ein Binding erreichbar ist.

3. Details

  1. WSDL 1.1: Es ist ein W3C Note vom 15. März 2001. Es ist keine W3C-Recommendation. Das WS-I Basic Profile baut trotzdem darauf auf und verlangt WSDL 1.1.
  2. WSDL 2.0: Es ist seit dem 26. Juni 2007 eine W3C Recommendation. Statt message und portType gibt es interface. Statt port gibt es endpoint.
  3. Vier Operationsarten: One-way hat nur input. Request-response hat input, dann output. Solicit-response hat output, dann input. Notification hat nur output. Die Reihenfolge der Elemente legt die Art fest.
  4. Nur zwei Arten mit Binding: Die Spezifikation definiert SOAP-Bindings nur für One-way und Request-response.
  5. Style: soap:binding style ist document oder rpc. Fehlt das Attribut, gilt document. Bei rpc steht ein Wrapper-Element mit dem Operationsnamen im Body. Bei document stehen die Parts direkt unter dem Body.
  6. use: Der Wert ist literal oder encoded. Literal heisst, die XSD gilt direkt. Das WS-I Basic Profile verbietet encoded (R2706).
  7. part: element oder type: Bei document/literal zeigt ein Part auf ein element (R2204). Bei rpc/literal zeigt er auf einen type (R2203). Ein Binding ist entweder rpc-literal oder document-literal (R2705).
  8. Wrapper Style: Das ist keine WSDL-Syntax, sondern eine Regel der JAX-WS-Spezifikation. Input und Output haben je einen Part. Das Input-Element heisst wie die Operation. Der Typ ist eine xsd:sequence aus Kindern ohne Attribute und Wildcards. Dann erzeugt der Generator normale Methodenparameter.
  9. soapAction: Es gibt keinen Standardwert für HTTP. Das Attribut muss also dort stehen. Es kann ein leerer String sein. SOAP 1.2 trägt die Action stattdessen im Content-Type.
  10. Faults: Ein wsdl:fault im portType zeigt auf eine Message mit genau einem Part. Im Binding gibt es dazu soap:fault. Der Generator macht daraus eine Exception.
  11. Header: Mit soap:header beschreibt man einen Header-Block aus einer Message. Diese Message muss nicht die des Body sein.
  12. Operationsnamen: In WSDL 1.1 müssen sie nicht eindeutig sein. Das Binding unterscheidet dann nach dem name von input und output. In WSDL 2.0 müssen sie in einem interface eindeutig sein.
  13. Werkzeuge: Clients und Server-Stubs werden aus der WSDL generiert. wsimport und xjc sind seit Java 11 nicht mehr im JDK (JEP 320). Man nimmt die Referenzimplementierungen oder Apache CXF.

4. Fallen

  • „WSDL 1.1 ist ein W3C-Standard.“ → Falsch. Es ist ein W3C Note. WSDL 2.0 ist die Recommendation.
  • „Die WSDL enthält nur die Operationen.“ → Falsch. Sie enthält auch Datentypen, Protokoll-Bindung und Adresse.
  • „document/literal wrapped ist ein WSDL-Stil.“ → Falsch. Der Stil heisst document. Wrapped ist eine Konvention aus JAX-WS.
  • „Ohne style-Attribut gilt rpc.“ → Falsch. Der Standard ist document.
  • „soapAction ist bei HTTP optional.“ → Falsch. Es hat keinen Standardwert und muss angegeben werden. Es darf leer sein.
  • „Ein portType hat eine Adresse.“ → Falsch. Die Adresse steht im port des service. Der portType ist abstrakt.

5. Selbsttest

Warum?

Warum trennt WSDL abstrakt und konkret?

Die Schnittstelle (portType) bleibt gleich, auch wenn Protokoll oder Adresse wechseln. Ein portType kann mehrere Bindings haben.

Warum zeigt ein Part bei document/literal auf ein element?

Dann ist der Body-Inhalt direkt durch die XSD bestimmt. Die Nachricht ist mit der XSD validierbar (R2204 im Basic Profile).

Warum verbietet das Basic Profile use encoded?

Encoded folgt SOAP-Kodierungsregeln und ist schwer interoperabel. Literal hält sich an die XSD (R2706).

Wie innen?

Welche Hauptelemente hat WSDL 1.1?

types, message, portType, binding und service. Dazu kommen import und das Wurzelelement definitions.

Wie hängen die Elemente zusammen?

Service enthält Ports. Ein Port zeigt auf ein Binding. Das Binding zeigt auf einen portType. Operationen nutzen Messages, deren Parts auf die XSD zeigen.

Was ist der Unterschied zwischen document und rpc?

Bei rpc steht ein Wrapper mit dem Operationsnamen im Body, und die Parts sind Parameter darin. Bei document stehen die Parts direkt unter dem Body.

Was ist Wrapper Style?

Eine Konvention aus JAX-WS. Das Body-Element heisst wie die Operation und enthält die Parameter als Kinder. So entstehen normale Methodenparameter.

Wie wird ein Fault beschrieben?

Im portType mit wsdl:fault auf eine Message mit einem Part. Im Binding mit soap:fault. Daraus wird eine Exception.

Wie lädt ein Client die WSDL?

Ein Generator liest sie von URL oder Datei und erzeugt Klassen. Die Adresse im port ist die Standard-Adresse, die man bei Bedarf überschreibt.

Wozu dient soap:header?

Es beschreibt einen Header-Block aus einer Message, zum Beispiel ein Token. Die Message kann eine andere sein als die des Body.

Zahlen

Welche Operationsarten kennt WSDL 1.1?

Vier. One-way, request-response, solicit-response und notification.

Wann ist WSDL 2.0 erschienen und welchen Status hat es?

Am 26. Juni 2007 als W3C Recommendation. WSDL 1.1 ist ein Note von 2001.

Welches transport-URI nutzt SOAP über HTTP?

http://schemas.xmlsoap.org/soap/http. Das Basic Profile verlangt diesen Wert (R2702).

Seit wann sind wsimport und xjc nicht mehr im JDK?

Seit Java 11. JEP 320 hat die Module java.xml.ws und java.xml.bind samt Werkzeugen entfernt.

Vergleich

WSDL 1.1 gegen WSDL 2.0?

2.0 hat interface statt message und portType, endpoint statt port und eindeutige Operationsnamen. 2.0 ist Recommendation, 1.1 nur Note.

WSDL gegen OpenAPI?

Beide beschreiben eine Schnittstelle maschinenlesbar. WSDL deckt SOAP mit XSD ab, OpenAPI deckt HTTP-APIs mit JSON Schema ab. WSDL beschreibt auch Binding und Fault-Typen.

rpc/literal gegen document/literal?

Rpc/literal hat den Operationsnamen im Body und Parts mit type. Document/literal hat ein Element nach XSD und ist mit XSD validierbar. Document/literal wrapped ist der übliche Standard.

Inline-Schema gegen xs:import?

Inline ist ein einziges File, aber das Schema ist nicht wiederverwendbar. Mit xs:import teilt man Schemas, aber der Client muss alle Dateien laden können.

Produktion

Szenario: Der Client ruft die Test-Adresse statt der Produktion. Warum?

Die WSDL enthält im port eine feste soap:address. Der Client nutzt sie als Standard. Ich überschreibe den Endpoint in der Konfiguration oder liefere die richtige Adresse in der WSDL.

Szenario: Nach einer WSDL-Änderung des Partners schlagen alle Aufrufe fehl. Wie gehen Sie vor?

Ich vergleiche alte und neue WSDL und XSD. Ein neues Pflichtfeld oder ein neuer Namespace bricht Clients. Ich generiere die Klassen neu und teste gegen die neue XSD.

Szenario: Der Generator meldet, ein Schema sei nicht auffindbar. Was tun Sie?

Die WSDL hat ein xs:import mit einer Adresse, die vom Build aus nicht erreichbar ist. Ich lade WSDL und XSDs lokal herunter und generiere aus lokalen Dateien.

Szenario: Ein Aufruf liefert „Unexpected element“ im Body. Warum?

Der Namespace oder Elementname stimmt nicht mit der WSDL überein. Ich prüfe targetNamespace, elementFormDefault und die Part-Elemente.

Design

Soll man die WSDL von Hand schreiben oder generieren?

Bei Verträgen zwischen Organisationen schreibt man XSD und WSDL zuerst und generiert Code daraus. Das ist Contract-first. Die WSDL ist dann das Produkt, nicht ein Nebenprodukt.

Wie versioniert man eine WSDL?

Mit einem Namespace pro Hauptversion. Kompatible Änderungen wie optionale Felder bleiben im selben Namespace. Alte Clients müssen weiter laufen.

Warum sollte die WSDL statisch sein?

Eine zur Laufzeit generierte WSDL kann sich bei einer Code-Änderung still ändern. Eine statische Datei in der Versionskontrolle macht jede Änderung sichtbar.

Wie testet man einen Vertrag?

Mit Beispielnachrichten, die gegen die XSD validiert werden. Dazu Tests mit alten Nachrichten gegen das neue Schema. So findet man Brüche vor dem Release.

Mehr

Gerüst

  • Warum? Ein maschinenlesbarer Vertrag, aus dem Clients und Server generiert werden.
  • Wie innen? service → port → binding → portType → operation → message → part → XSD-Element.
  • Zahlen 5 Hauptelemente, 4 Operationsarten. WSDL 1.1 Note 2001, WSDL 2.0 Recommendation 2007.
  • Vergleich WSDL 1.1 gegen 2.0. rpc gegen document. WSDL gegen OpenAPI.
  • Produktion Falsche Adresse im port. Vertragsbruch durch Änderung. Schema nicht auffindbar.
  • Design Contract-first, statische WSDL, Namespace-Versionierung.

Beispiel: eine WSDL mit XPath lesen

<!-- person.wsdl (Auszug), document/literal, SOAP 1.1 -->
<wsdl:message name="getPersonRequest">
  <wsdl:part name="parameters" element="tns:getPerson"/>
</wsdl:message>
<wsdl:portType name="PersonPort">
  <wsdl:operation name="getPerson">
    <wsdl:input message="tns:getPersonRequest"/>
    <wsdl:output message="tns:getPersonResponse"/>
    <wsdl:fault name="PersonFault" message="tns:PersonFault"/>
  </wsdl:operation>
</wsdl:portType>
<wsdl:binding name="PersonBinding" type="tns:PersonPort">
  <soap:binding style="document" transport="http://schemas.xmlsoap.org/soap/http"/>
  <wsdl:operation name="getPerson">
    <soap:operation soapAction="urn:example:person:1:getPerson"/>
    ...
// Java: XPath-Ausdruecke auf dem DOM (namespace-bewusst), danach das
// eingebettete Schema mit SchemaFactory kompilieren und eine Nutzlast pruefen
/w:definitions/w:portType/w:operation/@name           = getPerson
/w:definitions/w:portType/w:operation/w:input/@message = tns:getPersonRequest
/w:definitions/w:message[@name='getPersonRequest']/w:part/@element = tns:getPerson
/w:definitions/w:binding/s:binding/@style             = document
/w:definitions/w:binding/s:binding/@transport         = http://schemas.xmlsoap.org/soap/http
/w:definitions/w:binding/w:operation/s:operation/@soapAction = urn:example:person:1:getPerson
/w:definitions/w:binding/w:operation/w:input/s:body/@use = literal
/w:definitions/w:service/w:port/s:address/@location   = https://host.example/personService
name(/w:definitions/w:portType/w:operation/*[1])      = wsdl:input
name(/w:definitions/w:portType/w:operation/*[2])      = wsdl:output
Body gueltig
Body ungueltig: cvc-complex-type.2.4.a: Invalid content was found starting with element '{"urn:example:person:1":ahv}'. One of '{"urn:example:person:1":vn}' is expected.

Echte Ausgabe, OpenJDK 17.0.3. Die Ausgabe ist gekürzt und neu ausgerichtet. Die WSDL ist selbst geschrieben und fiktiv.

  1. Der Part zeigt auf das Element getPerson. Das ist document/literal.
  2. Das erste Kind der Operation ist input, das zweite output. Diese Reihenfolge macht sie zu request-response.
  3. style="document" und use="literal" sind genau das Muster, das das Basic Profile verlangt.
  4. Die soapAction kommt aus dem Binding, die Adresse aus dem Port.
  5. Das eingebettete Schema lässt sich kompilieren. Eine Nutzlast mit falschem Element wird abgelehnt.

Vergleich

  • WSDL 1.1: message, portType, port. W3C Note. Grundlage des Basic Profile.
  • WSDL 2.0: interface, endpoint. W3C Recommendation. Eindeutige Operationsnamen.
  • rpc/literal: Wrapper mit Operationsname, Parts mit type. Erlaubt im Basic Profile.
  • document/literal wrapped: Ein Element nach XSD. Üblicher Standard bei JAX-WS.
  • OpenAPI: Beschreibung für HTTP-APIs, meist mit JSON. Kein Binding-Konzept wie in WSDL.
  • XSD allein: Beschreibt Daten, aber keine Operationen und keine Adresse.

Produktion

  1. Falsche Endpoint-Adresse: Die WSDL nennt einen internen Host. Lösung: Endpoint im Client überschreiben oder die WSDL pro Umgebung ausliefern.
  2. Vertragsbruch durch Änderung: Ein neues Pflichtelement bricht alte Clients. Lösung: nur optionale Elemente ergänzen, sonst neuer Namespace.
  3. Generator findet Schema nicht: Ein xs:import zeigt auf eine unerreichbare URL. Lösung: Dateien lokal ablegen und Pfade anpassen.
  4. Alte Stubs nach WSDL-Update: Der Code wurde nicht neu generiert. Lösung: Generierung im Build und generierte Klassen nicht einchecken.
  5. Namespace-Fehler: elementFormDefault fehlt, Kinder liegen im falschen Namespace. Lösung: XSD korrigieren und gegen Beispielnachrichten testen.
  6. Java-Upgrade: Ab Java 11 fehlen wsimport und xjc. Lösung: Maven- oder Gradle-Plugin mit der Referenzimplementierung.

Diagnose: Werkzeuge und Befehle

  • WSDL abrufen: Viele Frameworks liefern sie unter der Endpoint-URL mit ?wsdl. Ist sie erreichbar und aktuell?
  • SoapUI: WSDL importieren, Requests erzeugen, Antworten prüfen.
  • xmllint --schema: Nachricht oder Schema-Datei prüfen.
  • Diff: Alte und neue WSDL und XSD vergleichen, um Brüche zu finden.
  • Generierte Klassen lesen: Stimmen Methodennamen und Typen mit dem Vertrag überein?
  • Proxy-Mitschnitt: Passen Namespace und SOAPAction der echten Nachricht zur WSDL?

Senior-Punkte

  1. Die WSDL ist das Produkt. Man pflegt XSD und WSDL als Quelle. Der Code ist abgeleitet.
  2. Abstrakt und konkret trennen. Eine Schnittstelle kann mehrere Bindings und Adressen haben. Das hilft bei Umgebungen und Versionen.
  3. Basic Profile als Leitplanke. Document/literal, kein encoded, ein Part pro Nachricht. So klappt Interoperabilität.
  4. Kompatibilität bewusst planen. Optionale Elemente sind sicher. Pflichtelemente und Umbenennungen brechen Clients.
  5. Statische WSDL ausliefern. Dann ist jede Änderung ein bewusster Commit.
  6. WSDL 2.0 nur bei Bedarf. Das Basic Profile und der Partnervertrag bestimmen die Version. Man prüft vorher, ob Werkzeuge 2.0 unterstützen.
