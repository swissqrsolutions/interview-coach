Merge-Konflikte lösen

Kern: Ein Merge-Konflikt entsteht, wenn beide Seiten dieselbe Stelle seit der Merge-Base unterschiedlich geändert haben. Git kann dann nicht automatisch entscheiden und hält an. Der Mensch löst den Konflikt, markiert ihn mit git add und schliesst den Merge, Rebase oder Cherry-Pick ab.

Antwort-Muster

Frage: Wie löst du einen Merge-Konflikt?

  1. Mechanismus: Git hält an und legt Base, ours und theirs in den Index. Im Working Tree stehen Konflikt-Marker. Ich entscheide fachlich, lösche die Marker und baue und teste.
  2. Zahl: Der Index hält 3 Stages pro Datei. Nach git add bleibt nur Stage 0.
  3. Trade-off: --theirs für eine ganze Datei ist schnell, verliert aber Änderungen. Mit zdiff3 sehe ich die Base und entscheide besser.
  4. Produktion: Vor dem Commit prüfe ich mit git diff --check auf Marker. CI baut das Merge-Ergebnis, damit semantische Konflikte auffallen.

1. Die Reise eines Konflikts

  1. Merge startet: main hat replicas: 3, feature hat replicas: 4. Die Base hatte replicas: 2.
  2. Konflikt: Beide Seiten haben dieselbe Zeile geändert. Git meldet CONFLICT (content) und endet mit Exit-Code 1.
  3. Verstehen: git status zeigt both modified. Mit Base-Anzeige (zdiff3) sieht man: beide wollten mehr Replicas.
  4. Lösen: Man entscheidet fachlich, z. B. 4. Man löscht alle Marker. Dann baut und testet man.
  5. Abschliessen: git add values.yaml markiert die Lösung. git commit erzeugt den Merge-Commit.
  6. Notausgang: Jederzeit stellt --abort den Stand vor dem Merge wieder her.

2. Aufbau

  1. Bei einem Konflikt legt Git drei Versionen der Datei in den Index: Stage 1 (Base), Stage 2 (ours), Stage 3 (theirs).
  2. Eine Datei mit diesen Stages heisst unmerged path. Commit ist dann blockiert.
  3. Im Working Tree schreibt Git eine Datei mit Konflikt-Markern.
  4. git add ersetzt die drei Stages durch eine Version: Stage 0. Damit gilt die Datei als gelöst.

3. Details, die Interviewer fragen

  1. Konflikt-Arten: content betrifft gleiche Zeilen. modify/delete heisst, eine Seite ändert und die andere löscht. rename/rename betrifft zwei Umbenennungen. add/add heisst, beide legen die gleiche Datei an. Bei binary sind keine Marker möglich.
  2. Konflikt-Stile: merge.conflictStyle steuert die Marker. merge ist der Standard. diff3 zeigt zusätzlich die Base. zdiff3 ist wie diff3, aber gemeinsame Zeilen stehen ausserhalb der Marker.
  3. ours und theirs: Beim Merge ist ours der aktuelle Branch (HEAD). Beim Rebase ist ours die neue Basis. Dort ist theirs der eigene Commit.
  4. Ganze Datei wählen: git checkout --ours datei oder --theirs holt Stage 2 oder 3. Danach folgt git add.
  5. -X ours / -X theirs: Diese Optionen lösen nur Konflikt-Hunks automatisch zugunsten einer Seite. Nicht konfliktierende Änderungen der anderen Seite kommen trotzdem.
  6. Strategie -s ours: Sie ignoriert die andere Seite ganz. Das Ergebnis ist der eigene Baum. Sie ist selten sinnvoll, z. B. um einen alten Branch als „gemergt“ zu markieren.
  7. rerere („reuse recorded resolution“): Git merkt sich gelöste Konflikte. Kommt derselbe Konflikt wieder, löst Git ihn automatisch. Man aktiviert es mit rerere.enabled=true.
  8. mergetool: git mergetool öffnet ein grafisches Werkzeug, z. B. VS Code oder Meld. Die Konfiguration läuft über merge.tool.
  9. Semantische Konflikte: Git meldet nur textuelle Konflikte. Zwei saubere Änderungen können zusammen den Build brechen. Nur Build und Tests finden das.
  10. Lock-Dateien: Mische bei package-lock.json nie Marker von Hand. Nimm eine Seite und erzeuge die Datei neu (npm install).

4. Fallen

  • „ours ist immer mein Branch.“ → Falsch. Beim Rebase ist ours die neue Basis, theirs der eigene Commit.
  • „-X ours und -s ours sind gleich.“ → Falsch. -X ours entscheidet nur Konflikt-Hunks. -s ours verwirft die ganze andere Seite.
  • „Kein Konflikt heisst, der Merge ist korrekt.“ → Falsch. Semantische Konflikte findet nur der Build.
  • „Git merkt, wenn noch Marker in der Datei sind.“ → Falsch. git add akzeptiert die Datei. Erst git diff --check warnt.
  • „Bei einem Konflikt ist der Merge kaputt.“ → Falsch. --abort stellt den alten Stand wieder her.

5. Selbsttest

Warum?

Wann entsteht ein Merge-Konflikt?

Wenn beide Seiten dieselbe Stelle seit der Merge-Base unterschiedlich geändert haben. Oder wenn eine Seite ändert und die andere löscht.

Was ist ours und theirs beim Rebase?

ours ist die neue Basis, auf die rebased wird. theirs ist der eigene Commit, der gerade angewendet wird.

Was ist ein semantischer Konflikt?

Beide Änderungen mergen sauber, aber zusammen ist der Code falsch. Git sieht ihn nicht, nur Build und Tests.

Warum kann ein Rebase mehrfach stoppen?

Rebase wendet jeden Commit einzeln an. Jeder Commit kann einen eigenen Konflikt haben.

Wie innen?

Was bedeuten die Konflikt-Marker?

Zwischen <<<<<<< und ======= steht ours. Zwischen ======= und >>>>>>> steht theirs. Mit diff3 oder zdiff3 zeigt ein Block nach ||||||| die Base.

Was ist zdiff3?

Ein Konflikt-Stil, der zusätzlich die Base zeigt. Gemeinsame Zeilen am Rand werden aus dem Konflikt-Block herausgenommen.

Wie nehmen Sie bei einer Datei komplett eine Seite?

git checkout --ours datei oder --theirs datei. Danach git add datei.

Was ist rerere?

Reuse recorded resolution. Git speichert gelöste Konflikte und wendet die Lösung beim gleichen Konflikt wieder an.

Was ist ein modify/delete-Konflikt?

Eine Seite ändert eine Datei, die andere löscht sie. Man entscheidet mit git add (behalten) oder git rm (löschen).

Welche Befehle helfen, den Konflikt zu verstehen?

git status, git diff (combined diff), git log --merge -p datei, git show :1:datei für die Base.

Zahlen

Was sind die Stages im Index?

Stage 1 ist die Base, Stage 2 ours, Stage 3 theirs. Nach git add bleibt nur Stage 0.

Mit welchem Exit-Code endet ein Merge mit Konflikt?

Git meldet CONFLICT (content) und endet mit Exit-Code 1.

Vergleich

Was ist der Unterschied zwischen -X theirs und git checkout --theirs?

-X theirs gilt für den ganzen Merge und nur für Konflikt-Hunks. checkout --theirs nimmt für eine Datei die ganze Version der anderen Seite.

Was ist anders bei Konflikten in Merge, Rebase und Cherry-Pick?

Beim Merge gibt es einen Konflikt-Moment und ours ist der aktuelle Branch. Beim Rebase kann jeder Commit stoppen und ours ist die neue Basis. Beim Cherry-Pick geht es um einen Commit, Ende mit --continue oder --abort.

Produktion

Wie gehen Sie mit Konflikten in package-lock.json um?

Eine Seite nehmen und die Datei mit dem Paketmanager neu erzeugen. Nie die Marker von Hand mischen.

Wie finden Sie vergessene Marker?

git diff --check vor dem Commit. Zusätzlich ein CI-Schritt, der nach Markern sucht.

Szenario: Der PR in Azure DevOps zeigt „Konflikte“. Was tun Sie?

Lokal den Ziel-Branch holen, mergen oder rebasen, Konflikte lösen, bauen, testen und pushen. Der PR wird dann wieder mergebar.

Szenario: Nach dem Merge ist im Produktions-YAML ein <<<<<<<. Was tun Sie?

Sofort fixen oder den Merge reverten. Danach eine Sperre einbauen: git diff --check in einem Hook oder im CI, und Pflicht-Review.

Szenario: Beim Rebase von 20 Commits lösen Sie immer wieder denselben Konflikt. Was tun Sie?

Abbrechen und rerere aktivieren, oder zuerst interaktiv squashen. Alternativ einmal mergen statt rebasen.

Design

Wie lösen Sie einen Konflikt Schritt für Schritt?

git status lesen, Datei öffnen, fachlich entscheiden, Marker löschen, bauen und testen. Dann git add und git commit oder --continue.

Wie brechen Sie einen Merge ab?

git merge --abort. Beim Rebase git rebase --abort, beim Cherry-Pick git cherry-pick --abort.

Wie vermeiden Sie Konflikte im Team?

Kleine PRs, kurze Branches, täglich integrieren, gemeinsamer Formatter, getrennte Dateien pro Umgebung.

Mehr

Gerüst

  • Warum? Git kennt nur Text, nicht Absicht. Bei gleicher Stelle muss ein Mensch fachlich entscheiden.
  • Wie innen? Der Index hält 3 Stages: Base, ours, theirs. Im Working Tree stehen Marker. git add macht Stage 0.
  • Zahlen Exit-Code 1 beim Merge mit Konflikt. git ls-files -u zeigt Stage 1, 2, 3.
  • Vergleich Merge hat einen Konflikt-Moment, Rebase einen pro Commit. -X ours gegen -s ours. Beim Rebase ist ours die neue Basis.
  • Produktion Marker im Commit brechen das Deployment. Blindes --theirs verliert Änderungen. Ein sauberer Merge kann den Build brechen.
  • Design Base mit zdiff3 zeigen. Kurze Branches und kleine Pull Requests. CI auf dem Merge-Ergebnis.

Rebase-Variante (gleiches Repo):

git switch feature
git rebase main          # Konflikt
git checkout --ours values.yaml;   head -1 values.yaml
git checkout --theirs values.yaml; head -1 values.yaml
git rebase --abort
CONFLICT (content): Merge conflict in values.yaml
error: could not apply d441976... feature: 4 replicas
replicas: 3
replicas: 4

Echte Ausgabe, git 2.56.0.windows.3 (gekürzt um die Hinweis-Zeilen).

  1. Beim Rebase ist ours die Basis main (3). theirs ist der eigene Commit, der gerade angewendet wird (4).
  2. Das ist genau umgekehrt zum Gefühl. Die Git-Doku warnt ausdrücklich davor.

Vergleich

  • Konflikt beim Merge: ein Moment, ein Merge-Commit. ours = aktueller Branch.
  • Konflikt beim Rebase: pro Commit möglich. ours = neue Basis. Ende mit git rebase --continue.
  • Konflikt beim Cherry-Pick oder Revert: ein Commit. Ende mit --continue, Abbruch mit --abort.
  • Konflikt bei git stash pop: Der Stash bleibt erhalten. Nach dem Lösen git stash drop.
  • Konflikt im Pull Request (Azure DevOps, GitHub): Der Server kann nicht mergen. Lösung lokal: Ziel-Branch hereinholen, lösen, pushen.

In der Produktion

  1. Marker landen im Commit: <<<<<<< steht in einer YAML-Datei, das Deployment bricht. Lösung: git diff --check vor dem Commit, CI bricht bei Markern ab.
  2. „Gelöst“ durch blindes --theirs: Fremde Änderungen gehen still verloren. Lösung: Base anschauen (zdiff3), Review des Merge-Commits.
  3. Build bricht nach sauberem Merge: Semantischer Konflikt, z. B. eine Methode umbenannt und ein neuer Aufruf auf der anderen Seite. Lösung: CI auf dem Merge-Ergebnis, nicht nur auf dem Branch.
  4. Immer gleiche Konflikte bei langen Branches: Bei jedem Rebase dieselbe Arbeit. Lösung: rerere und kürzere Branches.
  5. Generierte Dateien im Repo: Lock-Dateien und Helm-Abhängigkeiten konfliktieren oft. Lösung: neu erzeugen statt mischen.

Diagnose: Werkzeuge und Befehle

  • git status: zeigt unmerged paths und den laufenden Vorgang.
  • git diff: im Konflikt ein Combined Diff (diff --cc) gegen beide Seiten.
  • git ls-files -u: zeigt die Stages 1–3.
  • git show :1:datei, :2:datei, :3:datei: zeigt Base, ours, theirs.
  • git log --merge -p datei: zeigt die Commits beider Seiten, die die Datei berühren.
  • git diff --check: findet übrig gebliebene Marker und Whitespace-Fehler.
  • git checkout -m datei: stellt die Konflikt-Datei wieder her, wenn man sich verrannt hat.

Senior-Punkte

  1. Ein Konflikt ist eine fachliche Entscheidung. Bei Unklarheit den Autor der anderen Seite fragen.
  2. Base anzeigen mit zdiff3. Erst die Base zeigt, was jede Seite wollte.
  3. Vorbeugen ist billiger: kleine Pull Requests, kurze Branches, oft integrieren, Formatter für alle.
  4. CI auf dem Merge-Ergebnis fängt semantische Konflikte. Azure DevOps baut PRs auf dem Merge-Commit (refs/pull/…/merge).
  5. Nie Konflikte blind mit -X theirs in automatisierten Skripten lösen, ausser bei klar generierten Dateien.
  6. Konfig-Dateien pro Umgebung trennen (z. B. values.prod.yaml), dann konfliktieren Teams seltener.
