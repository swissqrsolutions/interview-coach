Merge vs Rebase

Git · Tier 1 · Quellen: git-scm.com (Pro Git Kap. 3.2 „Basic Branching and Merging“, Kap. 3.6 „Rebasing“, Kap. 7.6 „Rewriting History“; Referenz git-merge, git-rebase, git-config, git-push), Git 2.56

Kern: Merge und Rebase bringen die Arbeit von zwei Branches zusammen. Merge erhält die Geschichte und erzeugt einen Merge-Commit mit zwei Eltern. Rebase spielt die eigenen Commits neu auf eine andere Basis und schreibt dabei die Geschichte neu (neue Commit-IDs).

1. Wo sitzen Merge und Rebase?

  1. Commit-Graph: Git speichert Commits als DAG (gerichteter Graph ohne Zyklen). Jeder Commit zeigt auf seine Eltern.
  2. Refs: Ein Branch ist nur ein Zeiger auf einen Commit. HEAD zeigt auf den aktuellen Branch.
  3. merge fügt einen neuen Commit hinzu. Alte Commits bleiben unverändert.
  4. rebase erzeugt Kopien der Commits auf einer neuen Basis. Dann setzt es den Branch-Zeiger auf die Kopien.
  5. Der Remote teilt die Geschichte mit dem Team. Darum ist Rebase von bereits gepushten Commits heikel.

2. Die Reise eines Feature-Branches (die Geschichte zum Merken)

  1. Start: feature zweigt bei Commit A ab. Danach kommt Commit B auf main. Die Branches sind divergiert.
  2. Weg 1, Merge: git merge feature sucht die Merge-Base A. Git macht einen Three-Way-Merge aus A, B und F2. Das Ergebnis ist Commit M mit zwei Eltern.
  3. Weg 2, Rebase: git rebase main auf feature nimmt F1 und F2 als Patches. Git spielt sie nacheinander auf B ab. Es entstehen F1' und F2' mit neuen IDs.
  4. Fast-Forward: Jetzt liegt main direkt vor feature. git merge --ff-only feature schiebt nur den Zeiger nach vorn.
  5. Die alten Commits: F1 und F2 sind nicht gelöscht. Sie sind unerreichbar und bleiben im Reflog, bis git gc sie entfernt.
  6. Konflikte: Merge hat höchstens einen Konflikt-Moment. Rebase kann bei jedem kopierten Commit stoppen.

4. Details, die Interviewer fragen

  1. Merge-Base: Die Merge-Base ist der beste gemeinsame Vorfahr. git merge-base main feature zeigt sie. Der Three-Way-Merge vergleicht beide Seiten gegen diese Basis.
  2. Fast-Forward vs --no-ff: Ist der Ziel-Branch ein Vorfahr, schiebt Git nur den Zeiger. --no-ff erzwingt trotzdem einen Merge-Commit. So bleibt sichtbar, welche Commits zu einem Feature gehörten.
  3. Strategie ort: ort ist die Standard-Strategie für zwei Branches. Sie ersetzt recursive. Optionen wie -X ours lösen nur Konflikt-Hunks zugunsten einer Seite.
  4. Squash Merge: git merge --squash packt alle Änderungen in einen einzigen neuen Commit. Der Commit hat nur einen Eltern-Commit. Git sieht den Feature-Branch danach nicht als gemergt.
  5. Interaktives Rebase: git rebase -i HEAD~5 öffnet eine Todo-Liste. Befehle: pick, reword, edit, squash, fixup, drop. So räumt man Commits vor dem Pull Request auf.
  6. Autosquash: git commit --fixup=<sha> erzeugt einen fixup!-Commit. git rebase -i --autosquash sortiert ihn automatisch an die richtige Stelle.
  7. --onto: git rebase --onto main base feature verpflanzt nur die Commits nach base. Typisch für Branches, die auf einem anderen Feature-Branch aufbauen.
  8. --update-refs: Bei gestapelten Branches setzt Rebase alle Zwischen-Branches mit um. Konfiguration: rebase.updateRefs.
  9. pull = fetch + merge oder rebase: git pull --rebase spielt lokale Commits auf den neuen Remote-Stand. Konfiguration: pull.rebase.
  10. Force Push nach Rebase: Neue IDs heissen: der Remote lehnt einen normalen Push ab. git push --force-with-lease überschreibt nur, wenn der Remote noch dem bekannten Stand entspricht.
  11. Goldene Regel: Pro Git sagt: keine Commits rebasen, die ausserhalb des eigenen Repos existieren und auf denen andere aufbauen.

5. Vergleich

  • Merge: erhält die echte Geschichte, nicht destruktiv, ein Konflikt-Moment. Nachteil: viele Merge-Commits, Graph wird unübersichtlich.
  • Rebase: lineare, lesbare Geschichte, git bisect einfacher. Nachteil: neue IDs, Force Push nötig, Konflikte pro Commit.
  • Squash Merge: ein Commit pro Pull Request auf main. Nachteil: Detail-Commits gehen auf main verloren, Branch gilt nicht als gemergt.
  • Fast-Forward only: erzwingt lineare Geschichte ohne Merge-Commit. Klappt nur, wenn vorher rebased wurde.
  • Rebase + --no-ff Merge (semi-linear): lineare Commits, aber ein Merge-Commit markiert jedes Feature. Azure DevOps und GitLab bieten das als Merge-Option an.

6. In der Produktion

  1. Kollege hat auf einem rebasten Branch gearbeitet: Seine Commits basieren auf alten IDs. Ein Merge dupliziert dann Commits. Lösung: git pull --rebase oder git rebase --onto; besser: geteilte Branches nicht rebasen.
  2. git push --force löscht fremde Commits: Ein anderer hat inzwischen gepusht. Lösung: --force-with-lease, und Branch Protection auf main verbietet Force Push.
  3. Langer Feature-Branch, riesiger Merge-Konflikt: Wochen ohne Integration. Lösung: täglich main hereinholen (Merge oder Rebase), kleinere Pull Requests.
  4. Revert eines Merge-Commits: git revert -m 1 <merge> macht den Inhalt rückgängig. Ein späterer erneuter Merge bringt die alten Commits nicht zurück. Lösung: zuerst den Revert reverten.
  5. Rebase mitten im Konflikt abgebrochen: Repo steht in „rebase in progress“. Lösung: git status lesen, dann --continue, --skip oder --abort.

7. Diagnose: Werkzeuge und Befehle

  • git log --oneline --graph --all: zeigt Rauten (Merges) und divergierte Branches.
  • git merge-base A B: zeigt den gemeinsamen Vorfahr.
  • git log main..feature: Commits, die nur in feature sind.
  • git range-diff: vergleicht zwei Versionen einer Commit-Serie, z. B. vor und nach dem Rebase.
  • git reflog: findet den Stand vor einem misslungenen Rebase. Dann git reset --hard HEAD@{n} oder ORIG_HEAD.
  • git status: zeigt, ob ein Merge oder Rebase noch läuft.

8. Senior-Punkte

  1. Die Team-Regel zählt mehr als die Technik. Eine dokumentierte Merge-Strategie pro Repo verhindert Streit und kaputte Geschichte.
  2. Lokal rebasen, öffentlich mergen. Eigene, ungeteilte Commits aufräumen ist gut. Geteilte Geschichte umschreiben ist teuer.
  3. Lineare Geschichte hilft beim Debuggen. git bisect und git blame sind einfacher ohne viele Merge-Commits.
  4. Squash Merge verliert Information. Für grosse Pull Requests mit sinnvollen Einzel-Commits ist Rebase + Merge besser.
  5. Kurze Branches lösen das eigentliche Problem. Konflikte wachsen mit der Lebensdauer eines Branches, nicht mit der Merge-Technik.
  6. Branch Protection im Server (Azure DevOps, GitHub) setzt die Regel durch: erlaubte Merge-Typen, kein Force Push, Pull Request Pflicht.

10. Fallen

  • „Rebase verändert die Commits nicht.“ → Falsch. Rebase erzeugt neue Commits mit neuen IDs. Die alten bleiben nur im Reflog.
  • „Rebase ist immer besser, weil die Geschichte sauber ist.“ → Falsch. Auf geteilten Branches zerstört Rebase die Arbeit anderer.
  • „Merge erzeugt immer einen Merge-Commit.“ → Falsch. Bei Fast-Forward nur mit --no-ff.
  • „--force und --force-with-lease sind gleich.“ → Falsch. Lease prüft zuerst, ob der Remote noch dem bekannten Stand entspricht.
  • „Nach einem Squash Merge kann ich den Branch mit git branch -d löschen.“ → Nicht ohne Weiteres. Git sieht ihn nicht als gemergt; -d verweigert, -D nötig.

11. Fragen

Was ist der Unterschied zwischen Merge und Rebase?

Merge verbindet zwei Branches mit einem neuen Merge-Commit und erhält die Geschichte. Rebase kopiert die eigenen Commits auf eine neue Basis und erzeugt eine lineare Geschichte mit neuen IDs.

Was ist ein Fast-Forward Merge?

Der Ziel-Branch ist ein Vorfahr des anderen Branches. Git schiebt nur den Zeiger nach vorn. Es entsteht kein Merge-Commit.

Wann nutzen Sie --no-ff?

Wenn sichtbar bleiben soll, dass Commits zu einem Feature gehörten. Der Merge-Commit lässt sich später als Einheit reverten.

Was ist die Merge-Base?

Der beste gemeinsame Vorfahr zweier Branches. Git nutzt sie für den Three-Way-Merge.

Was ist ein Three-Way-Merge?

Git vergleicht beide Branch-Spitzen mit der Merge-Base. Was nur eine Seite geändert hat, wird übernommen. Was beide Seiten an der gleichen Stelle geändert haben, wird ein Konflikt.

Warum ändern sich beim Rebase die Commit-IDs?

Die ID ist ein Hash über Inhalt, Metadaten und Eltern. Rebase ändert die Eltern, darum entsteht ein neuer Hash.

Was ist die goldene Regel des Rebasing?

Keine Commits rebasen, die schon geteilt sind und auf denen andere aufbauen. Sonst entstehen doppelte Commits und Chaos.

Was macht git rebase -i?

Es öffnet eine Liste der Commits. Man kann sie umsortieren, zusammenfassen (squash, fixup), umbenennen (reword), bearbeiten (edit) oder löschen (drop).

Was ist der Unterschied zwischen squash und fixup?

Beide verschmelzen einen Commit mit dem vorherigen. squash fragt nach einer neuen Nachricht. fixup verwirft die Nachricht des verschmolzenen Commits.

Was ist ein Squash Merge?

Alle Änderungen eines Branches werden ein einziger Commit auf dem Ziel-Branch. Er hat nur einen Eltern-Commit, die Einzel-Commits fehlen auf main.

Was macht git rebase --onto?

Es verpflanzt einen Bereich von Commits auf eine beliebige neue Basis. Beispiel: einen Branch von einem anderen Feature-Branch lösen und auf main setzen.

Was ist git pull --rebase?

fetch und dann rebase statt merge. Lokale, noch nicht gepushte Commits kommen auf den neuen Remote-Stand. So entstehen keine unnötigen Merge-Commits.

Warum --force-with-lease statt --force?

Lease überschreibt nur, wenn der Remote-Branch noch dem bekannten Stand entspricht. So löscht man nicht versehentlich fremde Commits.

Welche Merge-Strategie nutzt Git standardmässig?

ort für zwei Branches. Sie hat recursive als Standard ersetzt.

Was bedeutet -X ours beim Merge?

Bei Konflikt-Hunks gewinnt die eigene Seite. Nicht-konfliktierende Änderungen der anderen Seite kommen trotzdem herein. Das ist nicht die Strategie -s ours, die die andere Seite ganz ignoriert.

Wie machen Sie einen Rebase rückgängig?

git reflog zeigt den Stand vor dem Rebase. Dann git reset --hard HEAD@{n} oder direkt ORIG_HEAD.

Merge oder Rebase für einen Pull Request?

Lokal vor dem PR rebasen und aufräumen. Beim Abschluss nach Team-Regel mergen, oft Squash oder Rebase + Merge-Commit.

Welche Vorteile hat eine lineare Geschichte?

Sie ist leichter zu lesen. git bisect und git blame funktionieren einfacher.

Szenario: Ein Kollege hat feature rebased und force-gepusht. Ihr lokaler Branch hat noch die alten Commits. Was tun Sie?

Nicht mergen, sonst kommen doppelte Commits. Eigene neue Commits mit git pull --rebase oder git rebase --onto origin/feature <alter-stand> auf den neuen Stand setzen.

Szenario: Nach einem Rebase fehlen plötzlich Änderungen. Wie retten Sie sie?

Mit git reflog den Commit vor dem Rebase finden. Dann zurücksetzen oder die fehlenden Commits per cherry-pick holen.

Szenario: Das Team streitet über Merge vs Rebase. Was schlagen Sie vor?

Eine klare Regel pro Repo: lokal rebasen, PR mit Squash oder Rebase + Merge-Commit abschliessen. Branch Protection erzwingt die Merge-Typen und verbietet Force Push auf main.
