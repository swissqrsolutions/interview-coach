Cherry-Pick und Revert

Kern: Cherry-Pick kopiert die Änderung eines einzelnen Commits als neuen Commit auf den aktuellen Branch. Revert erzeugt einen neuen Commit, der die Änderung eines alten Commits umkehrt. Beide schreiben keine Geschichte um und sind darum sicher auf geteilten Branches.

Antwort-Muster

Frage: Wie bringst du einen Hotfix auf einen Release-Branch?

  1. Mechanismus: Ich fixe zuerst auf main mit Test und CI. Dann kopiert git cherry-pick -x den Fix als neuen Commit auf den Release-Branch.
  2. Zahl: Der neue Commit hat eine neue ID. -x hängt die Herkunft in die Nachricht.
  3. Trade-off: Cherry-Pick holt nur den einen Commit, aber keine Abhängigkeiten. Viele Picks erzeugen doppelte Commits.
  4. Produktion: Fixe ich nur auf dem Release-Branch, kommt der Bug als Regression zurück. Darum fixe ich zuerst auf main.

1. Die Reise eines Hotfixes

  1. Bug in Produktion: Release 1.0 hat einen Null-Pointer im Parser. main ist schon weiter, mit neuen Features.
  2. Fix auf main: Der Fix entsteht auf main, mit Test, Pull Request und CI.
  3. Cherry-Pick: git cherry-pick -x <sha> auf release/1.0 kopiert nur den Fix. Die Features bleiben draussen.
  4. Release: Die Pipeline des Release-Branches baut, testet und taggt 1.0.1.
  5. Prüfen: git cherry zeigt, welche Commits schon auf beiden Seiten sind.
  6. Fehlschlag: Ist der Fix falsch, kehrt git revert ihn um. Die Geschichte bleibt ehrlich.

2. Aufbau

  1. main: Hier entsteht der Fix zuerst. So verlangt es Trunk-Based Development: zuerst auf dem Trunk fixen und testen.
  2. release/1.0: Ein Release-Branch bekommt den Fix per Cherry-Pick. Der neue Commit fix' hat eine eigene ID.
  3. Revert: Ist ein Commit fehlerhaft, kehrt git revert ihn mit einem neuen Commit um.
  4. Kein Befehl löscht oder ändert alte Commits. Darum braucht keiner einen Force Push.

3. Details, die Interviewer fragen

  1. Was Cherry-Pick wirklich tut: Es berechnet den Diff des Commits zu seinem Eltern-Commit. Diesen Diff wendet es per Merge-Logik an. Es entsteht ein neuer Commit mit neuer ID.
  2. -x: Es fügt (cherry picked from commit …) an. Laut Doku ist das zwischen öffentlichen Branches nützlich, z. B. beim Backport. Bei privaten Branches ist es unnötig.
  3. Bereich: git cherry-pick A..B nimmt alle Commits nach A bis B. A^..B nimmt A mit.
  4. -n (--no-commit): Die Änderungen landen nur im Index. So kann man mehrere Commits zu einem zusammenfassen.
  5. Merge-Commit picken oder reverten: Ein Merge hat zwei Eltern. -m 1 sagt, dass Eltern 1 die Hauptlinie ist. Ohne -m bricht Git ab.
  6. Leere Commits: --empty=drop|keep|stop steuert, was mit Commits passiert, die schon vorhanden sind. Der Standard ist stop.
  7. Revert eines Merge-Commits: git revert -m 1 <merge> entfernt den Inhalt. Git denkt aber weiter, die Commits seien gemergt. Ein neuer Merge bringt sie nicht zurück. Revertiere dann zuerst den Revert.
  8. Revert mehrerer Commits: Nutze git revert --no-commit A..B und dann einen Commit. Revert geht von neu nach alt.
  9. Konflikte: Beide Befehle können Konflikte haben. Der Ablauf ist lösen, git add, --continue. Alternativ gibt es --skip und --abort.
  10. Reset als Gegenstück: git reset verschiebt den Branch-Zeiger zurück. Das schreibt Geschichte um. Details stehen auf der Seite „Fehler rückgängig machen“.

4. Fallen

  • „Cherry-Pick verschiebt den Commit.“ → Falsch. Er kopiert die Änderung. Das Original bleibt, die Kopie hat eine neue ID.
  • „Revert löscht den Commit.“ → Falsch. Revert fügt einen Gegen-Commit hinzu. Der alte Commit bleibt.
  • „Nach Revert eines Merges kann ich den Branch einfach neu mergen.“ → Falsch. Git sieht die Commits als gemergt. Zuerst den Revert reverten.
  • „git branch --contains findet auch gepickte Commits.“ → Falsch. Nur gleiche IDs. Für gleiche Patches: git cherry.
  • „Fix auf dem Release-Branch, später zurück nach main picken.“ → Schlecht. Das wird vergessen. Besser: main zuerst.

5. Selbsttest

Warum?

Was passiert, wenn man einen revertierten Merge erneut mergen will?

Git bringt die alten Commits nicht zurück, weil sie schon gemergt sind. Man muss zuerst den Revert-Commit reverten.

Warum ist ein leerer Cherry-Pick möglich?

Die Änderung ist schon im Ziel-Branch. Git stoppt standardmässig; mit --empty=drop wird er übersprungen.

Warum zuerst auf main fixen?

Sonst fehlt der Fix im nächsten Release und der Bug kommt zurück. Trunk-Based Development empfiehlt: auf dem Trunk fixen, dann auf den Release-Branch picken.

Was ist der Nachteil vieler Cherry-Picks?

Doppelte Commits, vergessene Backports und Abhängigkeiten, die fehlen. Es zeigt meist zu lange Release-Branches.

Wie innen?

Was macht git cherry-pick?

Es nimmt die Änderung eines Commits und wendet sie als neuen Commit auf den aktuellen Branch an. Der neue Commit hat eine neue ID.

Was macht -x?

Es hängt „(cherry picked from commit …)“ an die Nachricht. So sieht man die Herkunft des Backports.

Wie picken Sie mehrere Commits?

Mit einer Liste oder einem Bereich: git cherry-pick A..B. A^..B nimmt A mit.

Was zeigt git cherry?

Welche Commits schon als gleichwertiger Patch im Upstream sind (-) und welche fehlen (+). Es vergleicht Patch-Inhalt, nicht IDs.

Was passiert bei einem Konflikt im Cherry-Pick?

Git stoppt. Man löst, git add, dann git cherry-pick --continue. Oder --skip oder --abort.

Was macht git cherry-pick -n?

Es wendet die Änderung an, aber committet nicht. So kann man mehrere Picks zu einem Commit bündeln.

Wie hängen Rebase und Cherry-Pick zusammen?

Rebase ist im Kern eine Serie von Cherry-Picks auf eine neue Basis, danach wird der Branch-Zeiger umgesetzt.

Zahlen

Wie reverten Sie einen Merge-Commit?

git revert -m 1 <merge>. Die 1 sagt, welcher Eltern-Commit die Hauptlinie ist.

Wie reverten Sie drei Commits in einem Commit?

git revert --no-commit für die drei Commits, dann ein git commit.

Vergleich

Was macht git revert?

Es erzeugt einen neuen Commit mit der umgekehrten Änderung. Die Geschichte wird nicht umgeschrieben.

Revert oder Reset?

Revert auf geteilten Branches, weil nichts umgeschrieben wird. Reset nur für lokale Commits, die noch niemand hat.

Produktion

Wie macht man Rollback in GitOps?

Den schlechten Commit im Konfig-Repo mit git revert umkehren und pushen. Der GitOps-Agent synchronisiert den alten Stand.

Szenario: Ein gemergtes Feature bricht Produktion. Es ist Freitagabend. Was tun Sie?

Den Merge-Commit mit git revert -m 1 rückgängig machen, pushen, deployen. Montag Ursache suchen. Beim Neu-Merge zuerst den Revert reverten.

Szenario: Nach einem Cherry-Pick bricht der Build auf dem Release-Branch. Warum?

Der Fix hängt von einem Commit ab, der dort fehlt. Lösung: den abhängigen Commit mitnehmen oder den Fix für den alten Code anpassen.

Design

Wann nutzen Sie Cherry-Pick?

Für Backports: ein Fix von main auf einen Release-Branch. Oder um einen einzelnen Commit aus einem verworfenen Branch zu retten.

Szenario: Ein Hotfix muss in Release 2.3 und 2.4. Wie gehen Sie vor?

Fix auf main mit Test und PR. Dann git cherry-pick -x auf beide Release-Branches, je eigene CI und Tag. Mit git cherry prüfen, dass er überall ist.

Mehr

Gerüst

  • Warum? Ein Fix muss auf einen Release-Branch, aber die neuen Features nicht. Revert macht Fehler rückgängig, ohne Geschichte umzuschreiben.
  • Wie innen? Cherry-Pick berechnet den Diff zum Eltern-Commit und wendet ihn per Merge-Logik an. Neuer Commit, neue ID.
  • Zahlen revert -m 1 bei Merge-Commits, denn ein Merge hat 2 Eltern. A..B nimmt A nicht mit, A^..B schon.
  • Vergleich Cherry-Pick kopiert einzelne Commits. Merge übernimmt die ganze Geschichte. Revert ist sicher auf geteilten Branches, Reset nur lokal.
  • Produktion Fix nur auf dem Release-Branch kommt als Regression zurück. Nach einem Merge-Revert bringt ein neuer Merge nichts.
  • Design Zuerst auf main fixen, dann picken. Viele Cherry-Picks zeigen zu lange Release-Branches. Kleine Commits.

Beispiel: Backport und Revert

git switch release/1.0
git cherry-pick -x ff93706
git log -1 --format='%h %s%n%n%b'
git log --oneline --all --graph
git cherry -v main release/1.0
git cherry-pick ff93706          # noch einmal
git switch main
git revert --no-edit HEAD
[release/1.0 7b54dd4] fix: null check in parser
 1 file changed, 1 insertion(+)
7b54dd4 fix: null check in parser

(cherry picked from commit ff93706265caf536d4eebace67fa4e3bfbeed6c0)

* ff93706 fix: null check in parser
* a9e619a new feature
| * 7b54dd4 fix: null check in parser
|/
* 42bf143 release 1.0

- 7b54dd4b57977aefc250eb35767a1c2d9500e74a fix: null check in parser

The previous cherry-pick is now empty, possibly due to conflict resolution.

[main a91d8f8] Revert "fix: null check in parser"
 1 file changed, 1 deletion(-)
 delete mode 100644 fix.txt

Echte Ausgabe, git 2.56.0.windows.3 (Scratch-Repo, gekürzt).

  1. Der kopierte Commit hat die neue ID 7b54dd4. Die Zeile (cherry picked from commit …) kommt von -x.
  2. Der Graph zeigt den Fix zweimal: einmal auf main, einmal auf release/1.0.
  3. git cherry zeigt -: Eine gleichwertige Änderung ist schon in main. Git vergleicht dafür den Patch-Inhalt, nicht die ID.
  4. Der zweite Cherry-Pick ist leer. Git stoppt und fragt (--empty=stop ist Standard).
  5. git revert erzeugt einen neuen Commit Revert "…". Der alte Fix bleibt in der Geschichte.

Vergleich

  • cherry-pick: einzelne Commits kopieren, neue IDs. Gut für Backports und Hotfixes.
  • merge: ganze Geschichte eines Branches übernehmen. Git merkt sich, was gemergt ist.
  • rebase: eigene Commits auf neue Basis kopieren. Ist intern eine Serie von Cherry-Picks.
  • revert: neuer Commit, der umkehrt. Sicher auf geteilten Branches.
  • reset: Branch-Zeiger zurücksetzen. Nur für lokale, ungeteilte Commits.

In der Produktion

  1. Fix nur auf dem Release-Branch: Der Bug kommt mit dem nächsten Release zurück (Regression). Lösung: zuerst auf main fixen, dann picken.
  2. Cherry-Pick zieht Abhängigkeiten nicht mit: Der Fix nutzt eine Methode, die es auf dem Release-Branch nicht gibt. Build bricht. Lösung: abhängige Commits mitnehmen oder Fix anpassen; CI auf dem Release-Branch.
  3. Doppelte Commits beim späteren Merge: Gepickte Commits erscheinen zweimal im Log. Meist harmlos, aber verwirrend. Lösung: -x und git cherry zur Kontrolle.
  4. Feature nach Merge-Revert fehlt: Nach git revert -m 1 bringt ein neuer Merge nichts. Lösung: zuerst den Revert-Commit reverten.
  5. Schlechtes Deployment in GitOps: Rollback = git revert des Commits im Konfig-Repo. ArgoCD synchronisiert den alten Stand.

Diagnose: Werkzeuge und Befehle

  • git cherry -v upstream head: + = fehlt noch, - = gleichwertiger Patch schon da.
  • git log --cherry-pick --left-right A...B: blendet gleichwertige Commits beider Seiten aus.
  • git log --grep="cherry picked from": findet Backports mit -x.
  • git branch --contains <sha>: zeigt, welche Branches genau diesen Commit haben (nur gleiche ID).
  • git show <sha>: zeigt den Diff, der gepickt oder reverted wird.

Senior-Punkte

  1. Fix zuerst auf main. Release-Branches bekommen Fixes nur per Cherry-Pick. Das verhindert Regressionen.
  2. Viele Cherry-Picks sind ein Warnsignal. Sie zeigen zu viele oder zu lange Release-Branches.
  3. Revert ist der Standard für geteilte Branches. Reset nur lokal.
  4. Revert eines Merges ist eine Entscheidung mit Folgen. Das Team muss wissen, dass ein erneuter Merge den Revert zuerst reverten muss.
  5. Kleine, atomare Commits machen Cherry-Pick und Revert einfach. Ein Commit mit Fix und Refactoring lässt sich schlecht picken.
  6. Roll forward oder Roll back: Ein Revert ist schnell. Ein Fix-Forward ist oft sauberer, wenn er klein und getestet ist.
