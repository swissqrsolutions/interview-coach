Fehler rückgängig machen: reset, revert, restore, reflog

Kern: Git hat für jede der drei Ebenen (Commit-Geschichte, Index, Working Tree) eigene Werkzeuge zum Rückgängigmachen. reset verschiebt den Branch-Zeiger, restore setzt Dateien zurück, revert kehrt einen Commit mit einem neuen Commit um. Das Reflog merkt sich jede Bewegung von HEAD und rettet fast jeden Fehler.

Antwort-Muster

Frage: Wie machst du einen falschen Commit rückgängig?

  1. Mechanismus: Ich frage zuerst, ob der Commit schon gepusht ist. Lokal nutze ich reset oder --amend, geteilt nutze ich git revert.
  2. Zahl: Das Reflog hält Einträge 90 Tage und unerreichbare Einträge 30 Tage. Damit hole ich einen Stand mit reset --hard HEAD@{n} zurück.
  3. Trade-off: Reset schreibt Geschichte um und ist nur lokal sicher. Revert fügt einen Gegen-Commit hinzu und ist auf geteilten Branches sicher.
  4. Produktion: Bei einem gepushten Secret hilft kein Revert. Ich rotiere es zuerst und bereinige dann die Geschichte.

1. Die Reise eines falschen Commits

  1. Der Fehler: Ein Commit hat eine falsche Nachricht, eine vergessene Datei oder falschen Code.
  2. Erste Frage: Ist der Commit schon gepusht und haben andere ihn?
  3. Nein, nur lokal: Geschichte umschreiben ist erlaubt. git commit --amend für den letzten Commit. git reset für mehrere.
  4. Ja, geteilt: Nichts umschreiben. git revert erzeugt einen Gegen-Commit, der normal gepusht wird.
  5. Zu viel weg: Das Reflog zeigt jeden alten Stand von HEAD. git reset --hard HEAD@{1} holt ihn zurück.
  6. Grenze: Was nie committet oder gestaged war, kennt Git nicht. Nach reset --hard ist es weg.

2. Aufbau

  1. HEAD / Branch: zeigt auf den letzten Commit. reset verschiebt diesen Zeiger.
  2. Index (Staging Area): enthält den Stand für den nächsten Commit. Beispiel: nach git add.
  3. Working Tree: die Dateien, die man editiert.
  4. Die Balken zeigen, welche Ebenen ein Befehl ändert. --soft nur HEAD, --mixed HEAD und Index, --hard alle drei.
  5. restore --staged ändert nur den Index. restore ohne Option ändert nur den Working Tree.

3. Details, die Interviewer fragen

  1. reset --soft: Es verschiebt nur den Branch. Index und Dateien bleiben. Typisch ist das Zusammenfassen mehrerer Commits zu einem.
  2. reset --mixed (Standard): Es verschiebt den Branch und setzt den Index zurück. Die Dateien bleiben. Typisch ist das neue Aufteilen eines Commits.
  3. reset --hard: Es setzt alle drei Ebenen zurück. Ungesicherte Änderungen im Working Tree sind verloren.
  4. reset --keep: Es ist wie --hard. Es bricht aber ab, wenn lokale Änderungen überschrieben würden.
  5. git restore: Es setzt Dateien zurück, ohne den Branch zu bewegen. --staged nimmt Dateien aus dem Index. --source=<commit> holt eine alte Version.
  6. switch und restore: Sie teilen die Aufgaben des alten git checkout. switch wechselt Branches. restore setzt Dateien zurück.
  7. git commit --amend: Es ersetzt den letzten Commit durch einen neuen. Das ist eine neue ID, also umgeschriebene Geschichte. Nach einem Push braucht man einen Force Push.
  8. Reflog: Das Reflog ist ein lokales Protokoll jeder Bewegung von HEAD und jedes Branches. Es wird nicht gepusht. Standardmässig laufen Einträge nach 90 Tagen ab, unerreichbare Einträge nach 30 Tagen (gc.reflogExpire, gc.reflogExpireUnreachable).
  9. ORIG_HEAD: Gefährliche Befehle wie reset, merge und rebase speichern den alten Stand in ORIG_HEAD. git reset --hard ORIG_HEAD geht einen Schritt zurück.
  10. Garbage Collection: git gc löscht unerreichbare lose Objekte, die älter als 2 Wochen sind (gc.pruneExpire). Darum ist ein „gelöschter“ Commit meist noch rettbar.
  11. Gelöschter Branch: Das Reflog von HEAD enthält den letzten Commit des Branches. git branch name <sha> stellt ihn wieder her.
  12. Gepushtes Secret: Revert hilft nicht, denn das Secret bleibt in der Geschichte. Rotiere zuerst das Secret. Bereinige dann die Geschichte, z. B. mit git filter-repo, und ziehe alle Klone neu.

4. Fallen

  • „reset --hard löscht Commits sofort.“ → Falsch. Die Commits bleiben im Reflog und sind meist wochenlang rettbar. Verloren sind nur nicht committete Änderungen.
  • „Revert macht den Commit unsichtbar.“ → Falsch. Der Commit bleibt in der Geschichte, dazu kommt ein Gegen-Commit.
  • „--amend ändert den Commit.“ → Falsch. Es entsteht ein neuer Commit mit neuer ID.
  • „Das Reflog ist auf dem Server.“ → Falsch. Es ist lokal pro Klon und wird nicht gepusht.
  • „Ein gepushtes Secret entferne ich mit revert.“ → Falsch. Es bleibt in der Geschichte. Rotieren und Geschichte bereinigen.
  • „git reset datei verwirft meine Änderungen.“ → Falsch. Es nimmt die Datei nur aus dem Index. Die Änderung auf der Disk bleibt.

5. Selbsttest

Warum?

Was macht git commit --amend?

Es ersetzt den letzten Commit durch einen neuen, mit neuer Nachricht oder neuen Dateien. Neue ID, darum nur vor dem Push.

Warum gibt es git switch und git restore?

git checkout machte zu viel: Branches wechseln und Dateien zurücksetzen. switch und restore trennen diese Aufgaben und sind sicherer.

Was ist verloren nach reset --hard?

Nicht committete Änderungen im Working Tree. Commits nicht, die sind im Reflog. Gestagte Inhalte findet fsck als Blobs.

Wie innen?

Was ist der Unterschied zwischen reset --soft, --mixed und --hard?

soft verschiebt nur den Branch. mixed setzt zusätzlich den Index zurück. hard setzt auch den Working Tree zurück und verwirft Änderungen.

Welcher Reset-Modus ist Standard?

--mixed. Der Branch und der Index gehen zurück, die Dateien bleiben.

Was macht git restore?

Es setzt Dateien zurück, ohne den Branch zu bewegen. --staged nimmt Dateien aus dem Index, ohne Option werden Änderungen auf der Disk verworfen.

Was ist das Reflog?

Ein lokales Protokoll jeder Bewegung von HEAD und den Branches. Damit findet man alte Stände nach reset, rebase oder amend.

Was ist ORIG_HEAD?

Der Stand vor dem letzten gefährlichen Befehl wie reset, merge oder rebase. git reset --hard ORIG_HEAD macht ihn rückgängig.

Was ist ein dangling Commit?

Ein Commit, den kein Branch und kein Tag erreicht. git fsck --lost-found findet ihn, gc löscht ihn nach Ablauf der Frist.

Zahlen

Wie lange bleiben Reflog-Einträge?

Standard: 90 Tage, unerreichbare Einträge 30 Tage. Einstellbar mit gc.reflogExpire und gc.reflogExpireUnreachable.

Nach wie vielen Tagen löscht git gc unerreichbare lose Objekte?

Nach 2 Wochen (gc.pruneExpire). Darum ist ein „gelöschter“ Commit meist noch rettbar.

Vergleich

Reset oder Revert?

Reset für lokale, ungeteilte Commits. Revert für gepushte Commits, weil die Geschichte erhalten bleibt.

Was ist der Unterschied zwischen reset --hard und reset --keep?

--keep bricht ab, wenn lokale Änderungen überschrieben würden. --hard überschreibt ohne Rückfrage.

Produktion

Szenario: Sie haben ein Passwort in ein öffentliches Repo gepusht. Was tun Sie?

Zuerst das Passwort rotieren. Dann die Geschichte mit git filter-repo bereinigen, force-pushen und das Team neu klonen lassen. Danach einen Secret-Scan in die Pipeline einbauen.

Szenario: Nach git reset --hard HEAD~3 merken Sie, dass ein Commit wichtig war. Was tun Sie?

git reflog öffnen, den Stand vor dem Reset finden (HEAD@{1}). Dann git reset --hard HEAD@{1} oder den einen Commit per cherry-pick holen.

Szenario: Ein Kollege hat auf main einen Reset und Force Push gemacht. Commits fehlen. Wie retten Sie?

Ein Klon, der die alten Commits hat, findet sie im Reflog oder in origin/main@{1}. Von dort wieder pushen. Danach Force Push auf main mit Branch Protection verbieten.

Design

Wie fassen Sie die letzten drei Commits zu einem zusammen?

git reset --soft HEAD~3, dann git commit. Alternativ interaktives Rebase mit squash.

Wie nehmen Sie eine Datei aus dem Staging?

git restore --staged datei. Früher git reset HEAD datei.

Wie holen Sie eine Datei aus einem alten Commit?

git restore --source=<commit> datei.

Wie stellen Sie einen gelöschten Branch wieder her?

Mit git reflog den letzten Commit des Branches finden. Dann git branch name <sha>.

Wie machen Sie einen Merge rückgängig, der schon gepusht ist?

git revert -m 1 <merge-commit>. Kein Reset, weil andere die Commits schon haben.

Mehr

Gerüst

  • Warum? Es gibt drei Ebenen mit je eigenem Werkzeug. Revert schreibt nichts um, reset schon. Das Reflog rettet fast alles.
  • Wie innen? --soft bewegt nur HEAD, --mixed HEAD und Index, --hard alle drei. restore ändert Index oder Working Tree.
  • Zahlen Reflog: 90 Tage, unerreichbare Einträge 30 Tage. git gc löscht lose Objekte nach 2 Wochen.
  • Vergleich Reset nur lokal, Revert auf geteilten Branches. --hard gegen --keep. Das Reflog ist kein Undo-Befehl, sondern eine Landkarte.
  • Produktion reset --hard mit ungesicherter Arbeit verliert sie. Force Push nach Reset bringt alte Commits zurück. Ein Secret zuerst rotieren.
  • Design Die Grenze ist der Push. Vor gefährlichen Befehlen ein Backup-Branch. Branch Protection gegen Force Push.

Echte Ausgabe, git 2.56.0.windows.3 (Scratch-Repo). Autor- und Commit-Datum waren fest gesetzt; darum hat C3 jedes Mal dieselbe ID a934333.

  1. reset --soft: C3 ist weg aus dem Log. Die Änderung ist gestaged (M in Spalte 1).
  2. reset (mixed): Die Änderung ist nicht gestaged (M in Spalte 2).
  3. reset --hard: Die Datei hat nur noch Zeilen 1 und 2. Die Änderung ist aus dem Working Tree weg.
  4. git reflog zeigt C3 als HEAD@{1}. reset --hard HEAD@{1} holt ihn zurück.
  5. restore --staged nimmt die Datei aus dem Index. restore verwirft die Änderung auf der Disk.
  6. --amend erzeugt einen neuen Commit d6faf55. Der alte a934333 steht noch im Reflog.

Vergleich

  • reset: verschiebt den Branch, schreibt Geschichte um. Nur lokal.
  • revert: neuer Gegen-Commit, Geschichte bleibt. Für geteilte Branches.
  • restore: nur Dateien (Index oder Working Tree), kein Branch bewegt.
  • commit --amend: letzten Commit ersetzen. Nur vor dem Push sicher.
  • stash: lokale Änderungen kurz wegpacken, nichts geht verloren.
  • reflog: kein Undo-Befehl, sondern die Landkarte, um den alten Stand zu finden.

In der Produktion

  1. reset --hard mit ungesicherter Arbeit: Nicht gestagte Änderungen sind weg. Lösung: vorher git stash; gestagte Dateien findet git fsck --lost-found als lose Blobs.
  2. Reset auf einem gepushten Branch und Force Push: Kollegen haben die alten Commits und mergen sie wieder herein. Lösung: auf geteilten Branches nur revert; Branch Protection verbietet Force Push.
  3. Falscher Merge auf main: git revert -m 1 <merge>. Beim späteren erneuten Merge zuerst den Revert reverten.
  4. Secret committet: Secret sofort rotieren. Geschichte umschreiben reicht nicht, Klone und Forks haben es schon.
  5. Fehlerhaftes Deployment in GitOps: Revert im Konfig-Repo, nicht kubectl edit. Sonst überschreibt der Agent die Änderung wieder.

Diagnose: Werkzeuge und Befehle

  • git reflog bzw. git reflog show main: alle alten Stände von HEAD oder einem Branch.
  • git log -g: Reflog im Log-Format, mit Datum.
  • git fsck --lost-found: findet dangling Commits und Blobs ohne Reflog-Eintrag.
  • git show HEAD@{2} oder main@{yesterday}: einen alten Stand anschauen, bevor man zurücksetzt.
  • git status: zeigt laufende Vorgänge und schlägt den passenden Undo-Befehl vor.
  • git diff ORIG_HEAD HEAD: was der letzte Merge oder Rebase geändert hat.

Senior-Punkte

  1. Die Grenze ist der Push. Vorher darf man umschreiben, danach nur noch hinzufügen (revert).
  2. Fast nichts ist verloren, was einmal committet war. Reflog und ORIG_HEAD retten es. Verloren ist, was nie committet oder gestaged war.
  3. Vor gefährlichen Befehlen einen Backup-Branch anlegen: git branch backup. Kostet nichts.
  4. Revert ist auch Rollback-Strategie. In GitOps ist git revert der Standard-Weg zurück, mit Audit-Spur.
  5. Secrets in Git sind ein Sicherheitsvorfall, kein Git-Problem. Rotation zuerst, Aufräumen danach.
  6. Server-Schutz: Branch Protection gegen Force Push und Löschen auf main und Release-Branches.
