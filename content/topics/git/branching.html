Branching-Modelle in Git

Kern: Ein Branch in Git ist ein beweglicher Zeiger auf einen Commit. Ein Branching-Modell legt fest, wie ein Team Branches nutzt und wie oft es sie zusammenführt. Die wichtigsten Modelle sind Trunk-Based Development, GitHub Flow und Git Flow.

Antwort-Muster

Frage: Welches Branching-Modell nutzen Sie und warum?

  1. Mechanismus: Ein Branch ist nur ein Zeiger auf einen Commit. Das Modell regelt, wie lange Branches leben und wann sie in den Hauptzweig gehen.
  2. Zahl: Je häufiger man integriert, desto kleiner sind die Merges. Trunk-Based integriert innerhalb eines Tages, Feature-Branches erst beim Fertigstellen.
  3. Trade-off: Git Flow gibt Struktur für versionierte Software mit mehreren Releases. Für Continuous Delivery ist es laut seinem Autor zu schwer.
  4. Produktion: Ich nehme kurze Branches mit Pull Request, Feature Flags für Unfertiges und Release-Branches nur, wenn mehrere Versionen leben müssen.

1. Ein Feature von Branch bis Release, in 6 Schritten

  1. Branch anlegen: git switch -c feature/x schreibt eine kleine Datei mit der Commit-ID. Es kopiert keine Dateien. Der Branch ist sofort da.
  2. Committen: Bei jedem Commit auf dem Branch rückt der Zeiger des Branches vor. HEAD zeigt auf den aktuellen Branch.
  3. Pull Request: Das Team prüft die Änderung. Automatische Checks laufen auf dem Branch (Healthy Branch).
  4. Merge: Der Branch geht in den Hauptzweig. Ist der Hauptzweig nicht weiter, ist es ein Fast-Forward. Sonst entsteht ein Merge-Commit.
  5. Tag setzen: Für ein Release setzt man einen Tag auf den Commit. Annotierte Tags sind für Releases gedacht.
  6. Branch löschen: Nach dem Merge löscht man den Branch. Der Verlauf und der Pull Request bleiben.

Das beschreibt GitHub Flow. In Trunk-Based Development ist der Branch nur ein paar Stunden alt oder man committet direkt auf den Trunk.

2. Aufbau

  1. Commit: ein Schnappschuss mit Verweis auf den Vorgänger. Er ändert sich nie.
  2. Branch: ein beweglicher Zeiger auf einen Commit. Bei jedem Commit auf dem Branch rückt er vor.
  3. HEAD: ein besonderer Zeiger auf den aktuellen Branch. Wechselt man den Branch, wandert HEAD.
  4. Tag: ein Name für einen Commit. Er wandert nicht mit. Lightweight ist nur ein Name, annotiert ist ein eigenes Objekt mit Autor, Datum und Nachricht.
  5. Hauptzweig: meist main. Er ist ein ganz normaler Branch ohne Sonderrechte in Git.
  6. Remote: ein anderes Repository wie origin. Branches und Tags werden dorthin gepusht.

3. Details

  1. Branch ist billig: Git schreibt beim Anlegen nur 41 Bytes, nämlich 40 Zeichen Commit-ID und einen Zeilenumbruch. Nichts wird kopiert. Darum sind viele kurze Branches ok.
  2. Wechsel: git switch bewegt HEAD und schreibt das Arbeitsverzeichnis auf den Stand des Branches. Geht das nicht sauber, wechselt Git gar nicht.
  3. Detached HEAD: git switch --detach wechselt zu einem Commit ohne Branch. Das ist für Ansehen und wegwerfbare Versuche gedacht.
  4. Fast-Forward und --no-ff: Ein Fast-Forward schiebt nur den Zeiger vor. --no-ff erzeugt immer einen Merge-Commit und hält fest, dass es einen Branch gab.
  5. Integrationsfrequenz: Nach Fowler führt häufiges Integrieren zu kleineren, weniger riskanten Merges. Seine Faustregel heisst: Wenn es weh tut, tue es öfter.
  6. Feature-Branching: Alle Arbeit eines Features liegt auf einem eigenen Branch und geht erst bei Fertigstellung in den Hauptzweig. Der Nachteil sind grosse Merges. Es hemmt auch Refactoring.
  7. Trunk-Based Development: Entwickler arbeiten auf einem gemeinsamen Hauptzweig. Feature-Branches sind kurz und stammen von einem einzelnen Entwickler. Release-Branches sind optional.
  8. Feature Flags: Sie verstecken unfertige Arbeit im Hauptzweig. Man kann ein Feature auch schrittweise für einen Teil der Nutzer freischalten.
  9. Branch by Abstraction: Für grosse Änderungen baut man eine Abstraktionsschicht ein und ändert schrittweise im Trunk, ohne langlebigen Branch.
  10. Git Flow: Hauptzweige master und develop, dazu Feature-, Release- und Hotfix-Branches. Release- und Hotfix-Branches gehen in beide Hauptzweige. Der Autor rät in einem Rückblick bei Continuous Delivery zu einem einfacheren Ablauf.
  11. GitHub Flow: Branch vom Standardzweig, Commits, Pull Request, Review, Merge, Branch löschen. Es ist ein leichter, branch-basierter Ablauf.
  12. Release-, Hotfix-, Environment-Branch: Ein Release-Branch stabilisiert eine Version. Ein Hotfix-Branch behebt einen dringenden Fehler in Produktion. Ein Environment-Branch (Branch pro Umgebung) gilt bei Fowler als klassisches Anti-Pattern.

4. Fallen

  • „Ein Branch kopiert die Dateien.“ → Falsch. Ein Branch ist eine Datei mit einer Commit-ID. Er kopiert nichts und ist sofort da.
  • „Git Flow ist der Standard für jedes Team.“ → Falsch. Der Autor rät bei Continuous Delivery zu einem einfacheren Ablauf. Git Flow passt zu versionierter Software.
  • „Trunk-Based heisst, man darf keine Branches nutzen.“ → Falsch. Kurze Branches sind erlaubt. Sie leben nur kurz und stammen von einem Entwickler.
  • „Ein Branch pro Umgebung (dev, test, prod) ist ein gutes Modell.“ → Falsch. Fowler nennt es ein klassisches Anti-Pattern. Konfiguration gehört in Dateien oder Variablen ausserhalb des Codes.
  • „git push sendet auch alle Tags.“ → Falsch. Tags gehen nicht von selbst mit. Man pusht sie ausdrücklich, zum Beispiel git push origin v1.0.
  • „Ein Fast-Forward-Merge erzeugt einen Merge-Commit.“ → Falsch. Er schiebt nur den Zeiger vor. Einen Merge-Commit erzwingt man mit --no-ff.

5. Selbsttest

Warum?

Warum integriert man oft in den Hauptzweig?

Kleine Merges sind weniger riskant, und Konflikte zeigen sich früh. Lange Branches sammeln Schmerz an.

Warum nutzt man Feature Flags?

Sie verstecken unfertige Arbeit im Hauptzweig. So muss man keinen langen Branch halten.

Warum wird Git Flow heute oft kritisiert?

Es ist schwer für Continuous Delivery. Sein Autor rät dort selbst zu einem einfacheren Ablauf.

Wie innen?

Was ist ein Branch in Git?

Ein beweglicher Zeiger auf einen Commit, gespeichert als kleine Datei mit der Commit-ID.

Was macht HEAD?

Er zeigt auf den aktuellen Branch. Beim Wechsel zeigt er auf den neuen Branch.

Was passiert bei git switch?

Git bewegt HEAD und schreibt das Arbeitsverzeichnis auf den Stand des Branches. Wenn das nicht sauber geht, wechselt es nicht.

Was ist der Unterschied zwischen Lightweight- und annotiertem Tag?

Lightweight ist nur ein Name für ein Objekt. Annotiert ist ein eigenes Objekt mit Datum, Autor und Nachricht. Annotierte sind für Releases gedacht.

Wann ist ein Merge ein Fast-Forward?

Wenn der Zielzweig seit dem Abzweigen nicht weitergewandert ist. Git schiebt dann nur den Zeiger vor.

Zahlen

Wie gross ist eine Branch-Datei?

41 Bytes bei SHA-1: 40 Zeichen Commit-ID und ein Zeilenumbruch.

Wie viele Hauptzweige hat Git Flow?

Zwei: master (später oft main) und develop.

Wie lange soll ein Feature-Branch im Trunk-Based leben?

Kurz. Eine feste Zahl gibt es nicht. Fowler spricht von Integration innerhalb eines Arbeitstags.

Wie viele Schritte hat GitHub Flow?

Sechs: Branch, Commits, Pull Request, Review, Merge, Branch löschen.

Vergleich

Trunk-Based vs Feature-Branching?

Trunk-Based integriert sehr oft in einen Hauptzweig. Feature-Branching sammelt Arbeit auf einem Branch bis zur Fertigstellung.

GitHub Flow vs Git Flow?

GitHub Flow hat nur Standardzweig und kurze Branches mit Pull Request. Git Flow hat develop, Release- und Hotfix-Branches.

Merge-Commit vs Fast-Forward?

Ein Merge-Commit hält die Branch-Geschichte fest. Ein Fast-Forward gibt eine gerade Linie.

Release-Branch vs Release direkt vom Trunk?

Ein Release-Branch stabilisiert eine Version, während der Trunk weiterläuft. Bei Release vom Trunk korrigiert man nach vorn (fix forward).

Produktion

Warum gibt es bei jedem Merge Konflikte?

Die Branches leben zu lange. Lösung: kleiner schneiden, öfter integrieren und den Hauptzweig regelmässig einholen.

Warum fehlt ein Tag im Remote?

Tags werden nicht automatisch gepusht. Lösung: git push origin v1.0 oder alle Tags pushen.

Szenario: Ein dringender Fehler in Produktion, der Hauptzweig hat schon neue Features. Was tun Sie?

Einen Hotfix-Branch von der ausgelieferten Version abzweigen, den Fehler beheben und die Korrektur auch in den Hauptzweig und offene Release-Branches bringen.

Szenario: Ein Feature ist erst in drei Wochen fertig, soll aber nicht in einem langen Branch hängen. Was tun Sie?

In kleinen Schritten in den Hauptzweig integrieren und das Feature hinter einem Feature Flag verstecken. Bei grossen Umbauten Branch by Abstraction.

Design

Szenario: Ein Team liefert eine Web-App mehrmals täglich aus. Welches Modell wählen Sie?

Trunk-Based oder GitHub Flow mit kurzen Branches, CI auf jedem Commit und Feature Flags. Kein develop-Branch.

Szenario: Eine Bibliothek unterstützt mehrere Hauptversionen gleichzeitig. Welches Modell wählen Sie?

Release-Branches pro unterstützter Version, Fixes zuerst im Hauptzweig und per Cherry-Pick in die Release-Branches. Das ähnelt Git Flow.

Wie schützen Sie den Hauptzweig?

Mit Branch-Schutz: Pull Request, Review und grüne CI vor dem Merge. Der Hauptzweig bleibt gesund.

Wie benennt man Tags für Releases?

Mit einer festen Form wie v1.0 und als annotierter Tag mit Nachricht. Die Namensregel legt das Team fest.

Mehr

Gerüst

  • Warum? Zusammenarbeit regeln und Merges klein und sicher halten.
  • Wie innen? Branch = Zeiger auf Commit, HEAD zeigt auf den Branch, Tag benennt einen Commit fest.
  • Zahlen 41 Bytes pro Branch, 2 Hauptzweige bei Git Flow, 6 Schritte bei GitHub Flow.
  • Vergleich Trunk-Based oft integrieren. GitHub Flow leicht. Git Flow für versionierte Software.
  • Produktion Konflikte bei langen Branches, Tag nicht gepusht, Hotfix neben neuen Features.
  • Design Kurze Branches, Feature Flags, geschützter Hauptzweig, Release-Branches nur bei Bedarf.

  1. Die Branch-Datei hat 41 Bytes. main und feature/x zeigen zuerst auf denselben Commit.
  2. Nach einem Commit auf feature/x rückt nur dieser Zeiger vor.
  3. Der Merge von feature/x war ein Fast-Forward. Die Historie bleibt eine gerade Linie.
  4. Mit --no-ff entsteht ein Merge-Commit. Der Graph zeigt den Branch.
  5. v1.0 ist ein tag-Objekt, build-42 nur ein commit. git describe ignoriert Lightweight Tags ohne --tags.
  6. Nach git push origin main hat das Remote 0 Tags. Erst git push origin v1.0 bringt ihn hin.

Vergleich

  • Trunk-Based: ein Hauptzweig, sehr oft integrieren, Feature Flags. Für Continuous Delivery.
  • GitHub Flow: Standardzweig plus kurze Branches mit Pull Request. Leicht.
  • Git Flow: master, develop, Feature-, Release-, Hotfix-Branches. Für explizit versionierte Software.
  • Feature-Branching: ein Branch pro Feature bis zur Fertigstellung. Grosse Merges möglich.
  • Release-Train: feste Release-Termine. Fertige Features warten auf den nächsten Zug.
  • Environment-Branches: ein Branch pro Umgebung. Gilt als Anti-Pattern.

Produktion

  1. Dauernde Merge-Konflikte: Branches leben zu lange. Lösung: kleiner schneiden, öfter integrieren.
  2. Unfertiges Feature blockiert den Release: Alles hängt am selben Branch. Lösung: Feature Flags.
  3. Hotfix fehlt im Hauptzweig: Korrektur nur im Release-Branch. Lösung: immer auch in den Hauptzweig und offene Release-Branches bringen.
  4. Tag fehlt im Remote: Tags nicht gepusht. Lösung: Tag ausdrücklich pushen, in der Pipeline automatisieren.
  5. Hauptzweig kaputt: Ungeprüfte Merges. Lösung: Branch-Schutz mit Review und CI.
  6. Verhalten je Umgebung verschieden: Environment-Branches. Lösung: gleiche Artefakte, Konfiguration ausserhalb des Codes.

Diagnose: Werkzeuge und Befehle

  • git log --oneline --graph --all: zeigt Branches und Merges als Graph.
  • git branch -vv: zeigt Branches mit Remote-Bezug.
  • git describe --tags: zeigt, wie weit ein Commit vom letzten Tag entfernt ist.
  • git merge-base A B: zeigt den gemeinsamen Vorfahren zweier Branches.
  • git cat-file -t NAME: zeigt, ob ein Tag annotiert (tag) oder leicht (commit) ist.

Senior-Punkte

  1. Das Modell folgt dem Release-Rhythmus. Mehrmals täglich heisst Trunk-Based. Mehrere Versionen heisst Release-Branches.
  2. Die Integrationsfrequenz zählt mehr als der Name des Modells. Kurze Branches schlagen jedes Schema.
  3. Feature Flags tauschen Branch-Komplexität gegen Code-Komplexität. Man muss sie später wieder entfernen.
  4. Ein gesunder Hauptzweig ist ein Vertrag. CI auf jedem Commit, und ein roter Build hat Vorrang.
  5. Kein Branch pro Umgebung. Ein Artefakt wandert durch die Umgebungen.
  6. Panazeen gibt es nicht. Man wählt das einfachste Modell, das zur Lieferweise passt.
