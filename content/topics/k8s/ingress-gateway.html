Ingress und Gateway API

Kern: Ingress und die Gateway API sind Kubernetes-APIs für den L7-Eingang mit Routing nach Host und Pfad und TLS für viele Services. Die API beschreibt nur Regeln, und ein Controller setzt sie um. Ingress ist eingefroren, die Gateway API ist der empfohlene Nachfolger.

Antwort-Muster

Frage: Was ist der Unterschied zwischen Ingress und Gateway API?

  1. Mechanismus: Beide routen HTTP nach Host und Pfad. Ingress hat ein Objekt, die Gateway API trennt GatewayClass, Gateway und HTTPRoute nach Rollen.
  2. Zahl: Ein Canary mit 90/10 ist in der Gateway API ein Standardfeld. Im Ingress braucht man Annotations, die je Controller anders heissen.
  3. Trade-off: Ingress ist eingefroren, aber nicht entfernt. Neue Funktionen kommen nur in die Gateway API.
  4. Produktion: Bestand auf ingress-nginx ist ein Risiko, es gibt seit März 2026 keine Security-Fixes. Ich plane die Migration mit Inventar der Annotations.

1. Die Reise eines HTTPS-Requests

  1. Browser. Er löst shop.example.ch auf. Der DNS-Eintrag zeigt auf die öffentliche IP des Load Balancers. Oft setzt external-dns ihn automatisch.
  2. Load Balancer. Der Cloud-LB arbeitet auf L4. Er reicht die TCP-Verbindung an die Proxy-Pods weiter.
  3. Listener und TLS. Der Proxy liest den Hostnamen aus dem TLS-Handshake (SNI). Er wählt den passenden Listener und das Zertifikat aus einem Kubernetes-Secret (certificateRefs). Er terminiert TLS: ab hier ist der Request entschlüsselt.
  4. Route-Match. Der Proxy sucht die passende HTTPRoute. Er prüft Host, Pfad (PathPrefix, Exact, RegularExpression), Header, Query und Methode. Die spezifischste Regel gewinnt.
  5. Filter. Die Route kann den Request ändern: Header setzen, Pfad umschreiben (URLRewrite), umleiten (RequestRedirect), spiegeln (RequestMirror).
  6. Backend. Der Proxy wählt ein Backend nach Gewicht, z. B. 90/10 für einen Canary. Er schickt den Request meist direkt an Pod-IPs aus den EndpointSlices, an kube-proxy vorbei. Optional wieder mit TLS (BackendTLSPolicy).

2. Aufbau

  1. GatewayClass: cluster-weites Objekt. Es sagt, welcher Controller zuständig ist (controllerName). Rolle: Infrastruktur-Anbieter. Beispiel: envoy-gateway.
  2. Gateway: ein konkreter Eingang mit Listeners (Port, Protokoll, Hostname, TLS-Zertifikat). Rolle: Cluster-Operator. Beispiel: HTTPS auf 443 für *.example.ch.
  3. HTTPRoute: Routing-Regeln einer App. Sie hängt sich per parentRefs an ein Gateway. Rolle: App-Entwickler. Beispiel: /api → Service api.
  4. Controller: beobachtet die Objekte und konfiguriert den Proxy. Ohne Controller passiert nichts.
  5. Proxy-Pods und Load Balancer: der echte Datenpfad. Meist ein Service type: LoadBalancer vor Envoy-, Traefik- oder NGINX-Pods.
  6. Ingress (alt): ein Objekt mit Host, Pfad, TLS und Backend. IngressClass wählt den Controller. Alles andere läuft über controller-spezifische Annotations.

3. Details, die Interviewer fragen

  1. Ingress-Status: Die Ingress-API ist GA und wird nicht entfernt. Sie ist aber eingefroren. Es gibt keine neuen Funktionen. Kubernetes empfiehlt die Gateway API.
  2. ingress-nginx ist retired: Das Projekt kubernetes/ingress-nginx bekam seit März 2026 keine Releases und keine Security-Fixes mehr. Bestehende Installationen laufen weiter, aber ungepatcht. Gründe waren zu wenige Maintainer und riskante Funktionen. Ein Beispiel sind Snippet-Annotations mit beliebiger NGINX-Konfiguration. Dazu kam CVE-2025-1974 „IngressNightmare“ mit CVSS 9.8. Über den Validating Admission Controller konnte alles im Pod-Netz Konfiguration einschleusen, ohne Rechte. Der Fix kam in v1.12.1 und v1.11.5.
  3. Nicht verwechseln: ingress-nginx ist das Community-Projekt und retired. Es ist nicht der NGINX Ingress Controller von F5/NGINX. Die Ingress-API ist auch nicht der Controller.
  4. pathType: Exact passt genau. Prefix vergleicht nach Pfad-Segmenten. So passt /api auf /api/x, aber nicht auf /apix. Bei ImplementationSpecific entscheidet der Controller.
  5. IngressClass: Sie wählt den Controller über spec.ingressClassName. Die Annotation ingressclass.kubernetes.io/is-default-class: "true" macht eine Klasse zum Standard.
  6. Gateway-API-Ressourcen: GatewayClass, Gateway, HTTPRoute, GRPCRoute und ReferenceGrant sind im Standard Channel. BackendTLSPolicy kam mit v1.4 dazu. TLSRoute (TLS-Passthrough nach SNI) und ListenerSet sind seit v1.5 im Standard Channel (v1). TCPRoute und UDPRoute sind seit v1.6 GA.
  7. Channels: Die Gateway API sind CRDs, die man selbst installiert. Der Standard Channel ist stabil. Der Experimental Channel hat neue Felder und Ressourcen. Sie können sich ändern.
  8. ReferenceGrant: Eine Route darf auf einen Service in einem anderen Namespace zeigen. Das geht nur, wenn dort ein ReferenceGrant es erlaubt. Ingress kann das gar nicht.
  9. TLS-Modi: Terminate ist der Standard. Das Gateway entschlüsselt. Bei Passthrough leitet das Gateway verschlüsselt nach SNI weiter, mit TLSRoute. Re-Encryption zum Backend läuft über BackendTLSPolicy.
  10. Zertifikate: Sie liegen als Secret vom Typ kubernetes.io/tls. cert-manager stellt sie aus und erneuert sie, z. B. mit Let's Encrypt. Das geht für Ingress und Gateway.
  11. Status-Conditions: Ein Gateway hat Accepted und Programmed. Eine Route hat Accepted und ResolvedRefs. Ingress hat fast keinen Status, nur die LB-Adresse.
  12. Portabilität: Funktionen wie Rewrite, Timeouts und Canary stecken im Ingress in Annotations. Sie sind nicht portabel. Die Gateway API hat sie als typisierte Felder mit Conformance-Tests.
  13. GAMMA: Die Gateway API beschreibt auch Service-Mesh-Routing (Ost-West). Eine HTTPRoute hängt sich dann an einen Service statt an ein Gateway.

4. Fallen

  • „Ingress ist deprecated und wird entfernt.“ → Falsch. Die API ist GA und eingefroren. Retired ist der Controller ingress-nginx.
  • „Ein Ingress-Objekt allein macht schon Routing.“ → Falsch. Ohne Controller passiert nichts.
  • „Gateway API ist nur ein neues Ingress.“ → Zu kurz. Rollenmodell, L4-Routes, Gewichte, Cross-Namespace-Regeln, Mesh-Support.
  • „Gateway API ist in Kubernetes eingebaut.“ → Falsch. Es sind CRDs, die man selbst installiert und versioniert.
  • „ingress-nginx und NGINX Ingress Controller sind dasselbe.“ → Falsch. Zwei verschiedene Projekte.
  • „Prefix: /api passt auf /apix.“ → Falsch. Prefix vergleicht ganze Pfad-Segmente.

5. Selbsttest

Warum?

Warum sind Ingress-Annotations ein Problem?

Sie sind controller-spezifisch, ungetypt und nicht portabel. Snippet-Annotations waren zudem ein Sicherheitsrisiko.

Warum trennt die Gateway API Rollen?

Das Plattform-Team besitzt Gateway und Zertifikate. App-Teams besitzen ihre Routes. Das Gateway begrenzt über allowedRoutes, wer anhängen darf.

Warum ist ingress-nginx ein Risiko?

Es gibt seit März 2026 keine Releases und keine Security-Fixes mehr. Neue Lücken bleiben offen.

Ist die Ingress-API deprecated?

Nein. Sie ist GA und bleibt, ist aber eingefroren. Neue Funktionen kommen nur in die Gateway API.

Wie innen?

Was ist ein Ingress?

Eine Kubernetes-API für HTTP-Routing von aussen nach Host und Pfad, mit TLS-Terminierung. Ein Ingress-Controller setzt sie um.

Was ist ein Ingress-Controller?

Ein Proxy mit Controller, der Ingress-Objekte beobachtet und sich selbst konfiguriert, z. B. Traefik oder Envoy-basierte Controller.

Was ist eine GatewayClass?

Ein cluster-weites Objekt, das den zuständigen Controller nennt. Ähnlich wie StorageClass oder IngressClass.

Was ist ein Listener?

Ein Eintrag im Gateway mit Port, Protokoll, optionalem Hostname, TLS-Einstellungen und erlaubten Routes.

Wie funktioniert TLS-Terminierung?

Der Proxy wählt per SNI das Zertifikat aus einem TLS-Secret, entschlüsselt und leitet HTTP weiter. Mit BackendTLSPolicy wieder verschlüsselt zum Backend.

Was ist TLS-Passthrough?

Der Proxy entschlüsselt nicht und leitet nach SNI weiter. Das Backend terminiert TLS. In Gateway API mit TLSRoute.

Wie kommen Zertifikate in den Cluster?

Als Secret vom Typ kubernetes.io/tls. Meist stellt cert-manager sie automatisch aus und erneuert sie.

Was bedeuten Accepted und Programmed?

Accepted: Controller hat das Objekt angenommen. Programmed: Konfiguration ist im Proxy aktiv, Adresse vergeben.

Was ist GAMMA?

Die Gateway-API-Initiative für Service Mesh. Routes hängen sich an Services und steuern Ost-West-Traffic.

Zahlen

Seit welchen Gateway-API-Versionen sind BackendTLSPolicy, TLSRoute, ListenerSet und TCPRoute stabil?

BackendTLSPolicy im Standard Channel seit v1.4. TLSRoute und ListenerSet seit v1.5. TCPRoute und UDPRoute sind seit v1.6 GA.

Wie läuft ein Canary 90/10 ab?

Zwei backendRefs in einer HTTPRoute mit weight 90 und 10. Das Gewicht erhöht man schrittweise.

Wie schwer war IngressNightmare?

CVE-2025-1974 hat CVSS 9.8. Der Fix kam in v1.12.1 und v1.11.5.

Vergleich

Welche pathTypes gibt es im Ingress?

Exact, Prefix (segmentweise) und ImplementationSpecific (Controller entscheidet).

Welche Ressourcen hat die Gateway API?

GatewayClass, Gateway, HTTPRoute, GRPCRoute, ReferenceGrant, BackendTLSPolicy, dazu TCPRoute/UDPRoute und TLSRoute.

Wie machen Sie einen Canary mit Gateway API?

Zwei backendRefs in einer HTTPRoute mit weight, z. B. 90 und 10. Gewicht schrittweise erhöhen.

Was ist mit ingress-nginx passiert?

Das Community-Projekt ist retired. Seit März 2026 gibt es keine Releases und Security-Fixes mehr. Empfohlen: Migration auf Gateway API oder einen anderen Controller.

Produktion

Szenario: Ein Audit findet ingress-nginx im Cluster. Was empfehlen Sie?

Risiko benennen: keine Security-Fixes seit März 2026. Annotations inventarisieren, Ziel-Controller mit Gateway API wählen, parallel aufbauen, per DNS umschalten.

Szenario: Die HTTPRoute ist angelegt, aber der Traffic kommt nie an. Wie gehen Sie vor?

Route-Status prüfen: Accepted false heisst Listener oder allowedRoutes passen nicht. ResolvedRefs false heisst Service fehlt oder ReferenceGrant fehlt. Dann Controller-Logs.

Szenario: Kunden melden ein abgelaufenes Zertifikat. Was tun Sie?

openssl s_client zeigt das ausgelieferte Zertifikat. cert-manager Certificate und Challenge prüfen, Ursache beheben, Erneuerung anstossen. Danach Alarm auf Ablaufdatum.

Wie migrieren Sie von Ingress zur Gateway API?

Annotations inventarisieren, ingress2gateway für Entwürfe nutzen, Gateway parallel aufbauen, Routes testen, DNS schrittweise umstellen.

Design

Was ist ein ReferenceGrant?

Eine Erlaubnis im Ziel-Namespace, dass Objekte aus einem anderen Namespace darauf verweisen dürfen. Schützt vor fremden Zugriffen auf Services oder Secrets.

Welches Rollenmodell hat die Gateway API?

Infrastruktur-Anbieter (GatewayClass), Cluster-Operator (Gateway), App-Entwickler (Routes). Jede Rolle hat eigene Objekte und RBAC.

Wo terminieren Sie TLS?

Am Gateway ist es einfach. Regulierte Umgebungen verlangen oft Re-Encryption oder mTLS bis zum Pod.

Szenario: Mehrere Teams brauchen einen Eingang. Wie bauen Sie ihn?

Wenige Gateways teilen, das spart LBs und IPs. HA, Limits und Monitoring einplanen, weil ein gemeinsamer Eingang ein gemeinsamer Ausfallpunkt ist.

Mehr

Gerüst

  • Warum? Ein Eingang für viele Services mit Host- und Pfad-Routing und TLS. Ein LoadBalancer pro Service kostet jeweils eine IP.
  • Wie innen? GatewayClass wählt den Controller, Gateway hat Listeners, HTTPRoute hängt per parentRefs daran. Der Proxy liest den Host per SNI.
  • Zahlen Gewichte wie 90/10 für Canary sind Teil des Standards. ingress-nginx: keine Releases mehr seit März 2026. CVE-2025-1974 hat CVSS 9.8.
  • Vergleich Ingress: nur Host und Pfad, Rest per Annotations. Gateway API: Rollen, Gewichte, Filter, Cross-Namespace mit ReferenceGrant, gRPC/TCP/UDP.
  • Produktion 404 durch falsche Klasse oder Route nicht Accepted, 502 ohne Endpunkte, Zertifikat abgelaufen, Client-IP fehlt.
  • Design Neue Plattformen auf Gateway API. Rollentrennung zwischen Plattform- und App-Team. Annotations sind Lock-in.

Beispiel: Gateway, HTTPRoute mit Canary, und dasselbe als Ingress

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: web, namespace: infra }
spec:
  gatewayClassName: envoy-gateway
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: "*.example.ch"
    tls:
      mode: Terminate
      certificateRefs: [{ name: wildcard-example-ch }]   # Secret, z. B. von cert-manager
    allowedRoutes:
      namespaces: { from: Selector, selector: { matchLabels: { gateway-access: "true" } } }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop, namespace: shop }
spec:
  parentRefs: [{ name: web, namespace: infra, sectionName: https }]
  hostnames: ["shop.example.ch"]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }
    - { name: api-v2, port: 80, weight: 10 }

# Dasselbe als Ingress: keine Gewichte im Standard, Canary nur über Controller-Annotations
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop, namespace: shop }
spec:
  ingressClassName: traefik
  tls: [{ hosts: ["shop.example.ch"], secretName: shop-tls }]
  rules:
  - host: shop.example.ch
    http:
      paths:
      - { path: /api, pathType: Prefix, backend: { service: { name: api-v1, port: { number: 80 } } } }
  1. Das Gateway liegt im Namespace infra. Nur Namespaces mit dem Label gateway-access=true dürfen Routes anhängen. Das ist die Rollentrennung.
  2. PROGRAMMED True heisst: Der Controller hat den Proxy konfiguriert und eine Adresse vergeben.
  3. Die HTTPRoute meldet Accepted (Gateway nimmt sie an) und ResolvedRefs (alle Backends gefunden). Fehlt eine, steht der Grund in status.
  4. Die Gewichte 90/10 sind Teil des Standards. Im Ingress braucht derselbe Canary Annotations, die je Controller anders heissen.

Vergleich

  • Service LoadBalancer: L4, eine IP pro Service, kein Host-Routing, TLS nur in der App.
  • Ingress: L7, ein Objekt, nur HTTP/HTTPS, Host und Pfad. Alles Weitere per Annotations. Eingefroren.
  • Gateway API: L7 und L4, Rollen getrennt, Header-Matching, Gewichte, Filter, Cross-Namespace mit ReferenceGrant, gRPC/TCP/UDP. Empfohlener Standard.
  • Controller-Auswahl: Envoy Gateway, Cilium, Istio, Traefik, NGINX Gateway Fabric, Contour, Kong. In Azure: Application Gateway for Containers. In k3s ist Traefik als Ingress-Controller vorinstalliert.
  • Service Mesh: regelt Traffic zwischen Services (mTLS, Retries). Gateway regelt den Eingang. Die Gateway API deckt mit GAMMA beides ab.

In der Produktion

  1. Noch auf ingress-nginx: keine Security-Patches mehr. Lösung: Migration planen, z. B. mit dem Tool ingress2gateway. Vorher Annotations und Sonderverhalten (Regex, Rewrite, Snippets) inventarisieren.
  2. 404 vom Controller: Host oder Pfad passen nicht, falsche ingressClassName, oder Route nicht Accepted. Lösung: Status und Controller-Logs prüfen.
  3. 502/503: Backend-Service hat keine Ready-Endpunkte, falscher Port, oder Network Policy blockt den Controller.
  4. Zertifikat abgelaufen: cert-manager konnte nicht erneuern (DNS- oder HTTP-Challenge scheitert). Lösung: kubectl describe certificate, Alarm auf Ablaufdatum.
  5. Route hängt nicht am Gateway: allowedRoutes erlaubt den Namespace nicht, oder ReferenceGrant fehlt. Status zeigt NotAllowedByListeners oder RefNotPermitted.
  6. Client-IP fehlt: LB macht SNAT. Lösung: externalTrafficPolicy: Local am Proxy-Service oder Proxy-Protocol, dann X-Forwarded-For.
  7. Grosse Uploads brechen ab: Body-Size- oder Timeout-Limits im Proxy. Bei Ingress per Annotation, bei Gateway per Feld oder Policy des Controllers.

Diagnose: Werkzeuge und Befehle

  • kubectl get gatewayclass,gateway,httproute -A: Übersicht inkl. PROGRAMMED.
  • kubectl describe httproute <r>: Conditions mit Grund, z. B. BackendNotFound.
  • kubectl get ingress -A und kubectl describe ingress: Adresse, Regeln, Events.
  • kubectl get ingressclass: welche Klasse Standard ist.
  • kubectl logs -n <controller-ns> deploy/<controller>: Konfig-Fehler und Access-Logs.
  • curl -v --resolve shop.example.ch:443:<LB-IP> https://shop.example.ch/api: Test mit richtigem SNI ohne DNS.
  • openssl s_client -connect <LB-IP>:443 -servername shop.example.ch: welches Zertifikat ausgeliefert wird.
  • kubectl get certificate,certificaterequest -A: Status von cert-manager.

Senior-Punkte

  1. Neue Plattformen auf Gateway API. Ingress nur noch für Bestand. Die Wahl des Controllers ist wichtiger als die API.
  2. Rollentrennung ist der eigentliche Gewinn: Plattform-Team besitzt Gateway und Zertifikate, App-Teams besitzen ihre Routes.
  3. Annotations sind Lock-in. Jede Ingress-Annotation ist eine Migrationsaufgabe. Standardfelder sind portabel.
  4. Wenige Gateways teilen spart LBs und IPs. Aber ein gemeinsamer Eingang ist ein gemeinsamer Ausfallpunkt: HA, Limits und Monitoring einplanen.
  5. TLS bis wohin? Terminierung am Gateway ist einfach. Regulierte Umgebungen verlangen oft Re-Encryption oder mTLS bis zum Pod.
  6. Retired Software ist ein Risiko-Thema, kein reines Technik-Thema. Migration mit Inventar, Tests pro Route und schrittweiser Umstellung per DNS.
