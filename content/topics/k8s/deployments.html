Deployments, ReplicaSets, Rollouts, Rollback

Kern: Ein Deployment ist ein Controller für zustandslose Anwendungen. Er verwaltet ReplicaSets, und jedes ReplicaSet hält eine feste Zahl gleicher Pods. Bei einer Änderung am Pod-Template rollt das Deployment schrittweise auf ein neues ReplicaSet um und kann auf ein altes zurückrollen.

1. Wo sitzt das Deployment?

  1. Deployment: beschreibt den Soll-Zustand: Image, Replicas, Strategie. Beispiel: api mit 3 Replicas.
  2. ReplicaSet: hält genau replicas Pods am Leben. Jede Template-Version hat ein eigenes ReplicaSet. Beispiel: Pod stirbt → ReplicaSet erzeugt einen neuen.
  3. Revision: Jedes ReplicaSet ist eine Revision. Alte ReplicaSets bleiben mit 0 Replicas stehen. Sie sind die Grundlage für den Rollback.
  4. pod-template-hash: ein Label, das der Controller aus dem Template berechnet. So überschneiden sich die Selektoren der ReplicaSets nicht.
  5. Selector: spec.selector wählt die Pods. Er ist nach dem Erstellen unveränderlich.

2. Die Reise eines Rolling Updates (die Geschichte zum Merken)

  1. Auslöser. Jemand ändert das Pod-Template, z. B. das Image von v1 auf v2. Nur Template-Änderungen starten einen Rollout. Ein Scale auf 5 Replicas nicht.
  2. Neues ReplicaSet. Der Deployment-Controller berechnet den neuen Hash. Er erzeugt ein neues ReplicaSet mit 0 Replicas. Revision steigt auf 2.
  3. Hochskalieren. maxSurge erlaubt Pods über der Soll-Zahl. Mit Surge 1 startet ein neuer Pod: 4 Pods total.
  4. Warten auf Readiness. Der Controller zählt den neuen Pod erst als verfügbar, wenn seine Readiness Probe grün ist und minReadySeconds vorbei sind. Das ist das Readiness Gating.
  5. Herunterskalieren. maxUnavailable bestimmt, wie viele Pods unter der Soll-Zahl liegen dürfen. Bei 0 wird ein alter Pod erst nach einem neuen Ready-Pod beendet.
  6. Wiederholen. Schritt für Schritt, bis das neue ReplicaSet 3 Pods hat und das alte 0.
  7. Hängen bleiben. Wird ein neuer Pod nie Ready, stoppt der Rollout. Die alten Pods laufen weiter. Nach progressDeadlineSeconds (Standard 600 s) meldet das Deployment ProgressDeadlineExceeded. Ein automatischer Rollback passiert nicht.

3. Beispiel: Rollout, kaputtes Image, Rollback

$ kubectl create deployment api --image=nginx:1.26 --replicas=3 -n demo-deployments

4. Details, die Interviewer fragen

  1. Standardwerte: Strategie RollingUpdate, maxSurge: 25% (aufgerundet), maxUnavailable: 25% (abgerundet), revisionHistoryLimit: 10, progressDeadlineSeconds: 600, minReadySeconds: 0.
  2. maxSurge und maxUnavailable: Beide sind Zahlen oder Prozent. Beide dürfen nicht gleichzeitig 0 sein. maxSurge: 0, maxUnavailable: 1 spart Ressourcen, senkt aber die Kapazität.
  3. Recreate: Alle alten Pods werden beendet, dann starten die neuen. Es gibt eine Ausfallzeit. Nötig, wenn zwei Versionen nicht gleichzeitig laufen dürfen, z. B. ein ReadWriteOnce-Volume oder inkompatibles DB-Schema.
  4. Readiness Gating: Ohne Readiness Probe gilt ein Pod sofort nach dem Start als Ready. Der Rollout läuft dann blind durch, auch wenn die App noch bootet. Pod Readiness Gates erlauben zusätzliche Bedingungen, z. B. vom Cloud Load Balancer.
  5. minReadySeconds: Ein Pod muss so lange Ready bleiben, bevor er als available zählt. Schützt vor Pods, die kurz nach dem Start abstürzen.
  6. Rollback: kubectl rollout undo geht eine Revision zurück. --to-revision=N geht zu einer bestimmten. Rollback ist nur möglich, solange das alte ReplicaSet existiert (revisionHistoryLimit).
  7. Was ein Rollback nicht zurücksetzt: ConfigMaps, Secrets, Replica-Zahl, Datenbank-Schema. Nur das Pod-Template.
  8. Pause und Resume: kubectl rollout pause sammelt mehrere Änderungen. resume startet einen einzigen Rollout.
  9. Restart: kubectl rollout restart setzt die Annotation kubectl.kubernetes.io/restartedAt im Template. Das ist eine Template-Änderung, also ein normaler Rolling Update.
  10. Deployment-Conditions: Available (genug Pods verfügbar), Progressing (Rollout läuft oder fertig), ReplicaFailure (Pods können nicht erzeugt werden, z. B. Quota).
  11. Proportional Scaling: Wird während eines Rollouts skaliert, verteilt der Controller die neuen Replicas anteilig auf altes und neues ReplicaSet.
  12. ConfigMap-Änderungen starten keinen Rollout. Lösung: Hash der Config als Annotation im Template (Helm-Muster checksum/config) oder Name mit Hash.

5. Vergleich

  • RollingUpdate: kein Ausfall, zwei Versionen laufen kurz parallel. Standard.
  • Recreate: kurzer Ausfall, nie zwei Versionen gleichzeitig.
  • Blue/Green: zwei komplette Umgebungen, Umschalten am Service oder Router. Schneller Rollback, doppelte Ressourcen. Nicht eingebaut, z. B. mit Argo Rollouts.
  • Canary: wenige Prozent Traffic auf die neue Version, mit Metriken prüfen. Mit Argo Rollouts, Flagger oder Gateway-API-Gewichten.
  • Deployment vs ReplicaSet: ReplicaSet hält nur die Zahl. Deployment bringt Rollout und Rollback. ReplicaSets nie direkt anlegen.
  • Deployment vs StatefulSet: StatefulSet für feste Identität, stabile Namen und eigenes Volume pro Pod, z. B. Datenbanken.
  • kubectl rollout undo vs git revert: undo ändert nur den Cluster. Mit GitOps ist git revert der richtige Weg, sonst stellt Argo CD den Git-Stand wieder her.

6. In der Produktion

  1. Rollout hängt: neuer Pod in ImagePullBackOff oder CrashLoopBackOff. Lösung: rollout status mit Timeout in der Pipeline, dann undo oder Fix.
  2. Fehler trotz grünem Rollout: keine Readiness Probe, Traffic geht an bootende Pods. Lösung: echte Readiness Probe, minReadySeconds.
  3. Kapazität bricht ein: Standard maxUnavailable: 25% bei knapper Kapazität. Lösung: maxUnavailable: 0, dazu PodDisruptionBudget für Node-Wartung.
  4. Pods Pending beim Rollout: Surge-Pods passen nicht auf die Nodes oder in die ResourceQuota. Lösung: Surge senken, Cluster-Autoscaler oder Karpenter.
  5. Rollback geht nicht: alte ReplicaSets durch zu kleines revisionHistoryLimit gelöscht. Oder GitOps setzt den Rollback sofort zurück.
  6. Inkompatible Versionen parallel: v1 und v2 schreiben verschiedene DB-Schemas. Lösung: rückwärtskompatible Migration (expand, migrate, contract) oder Recreate.
  7. Selector-Änderung scheitert: spec.selector ist unveränderlich. Lösung: neues Deployment.

7. Diagnose: Werkzeuge und Befehle

  • kubectl rollout status deploy/<d> --timeout=5m: wartet und liefert Exit-Code ≠ 0 bei Fehler. Gut für CI/CD.
  • kubectl rollout history deploy/<d> --revision=3: Template einer Revision.
  • kubectl get rs -l app=<a>: welche Revision wie viele Pods hat.
  • kubectl describe deploy <d>: Conditions, Strategie, Events wie ScalingReplicaSet.
  • kubectl get deploy <d> -o jsonpath='{.status.conditions}': ProgressDeadlineExceeded erkennen.
  • kubectl diff -f deploy.yaml: was sich vor dem Apply ändert.
  • Argo CD UI/CLI (argocd app history): Sync-Historie und Git-Revision pro Deployment.

8. Senior-Punkte

  1. Readiness Probe ist die halbe Rollout-Strategie. Ohne sie ist RollingUpdate nur ein langsames Recreate ohne Schutz.
  2. maxSurge/maxUnavailable ist eine Kosten-Entscheidung: Surge kostet Ressourcen, Unavailable kostet Kapazität.
  3. Rollback ist nur Code-Rollback. Schema, Config und Daten brauchen eigene Rückwärtskompatibilität.
  4. Kubernetes macht kein Auto-Rollback. Die Pipeline oder ein Tool (Argo Rollouts, Flagger) muss entscheiden.
  5. In GitOps ist Git die Wahrheit. Rollback per git revert, sonst überschreibt Self-Heal die manuelle Änderung.
  6. Progressive Delivery (Canary mit Metriken) lohnt sich bei viel Traffic. Bei wenig Traffic sind die Metriken zu dünn.

10. Fallen

  • „Ein fehlgeschlagener Rollout rollt automatisch zurück.“ → Falsch. Er bleibt stehen und meldet ProgressDeadlineExceeded.
  • „Scaling erzeugt eine neue Revision.“ → Falsch. Nur Änderungen am Pod-Template.
  • „Rollback setzt auch ConfigMaps zurück.“ → Falsch. Nur das Pod-Template.
  • „Eine ConfigMap-Änderung startet die Pods neu.“ → Falsch. Nur mit Template-Änderung, z. B. Checksum-Annotation.
  • „rollout undo stellt die alte Revisionsnummer wieder her.“ → Falsch. Es entsteht eine neue Revision mit altem Template.
  • „maxSurge und maxUnavailable können beide 0 sein.“ → Falsch. Dann käme der Rollout nie voran. Die API lehnt das ab.

11. Fragen

Was ist ein Deployment?

Ein Controller für zustandslose Apps. Er verwaltet ReplicaSets und macht Rolling Updates und Rollbacks.

Wie hängen Deployment, ReplicaSet und Pod zusammen?

Das Deployment erzeugt pro Template-Version ein ReplicaSet. Das ReplicaSet hält die Anzahl Pods. Die Pods tragen das Label pod-template-hash.

Was löst einen Rollout aus?

Jede Änderung an spec.template, z. B. Image, Env oder Annotation. Scaling löst keinen aus.

Was bedeuten maxSurge und maxUnavailable?

maxSurge: wie viele Pods über der Soll-Zahl liegen dürfen. maxUnavailable: wie viele darunter. Standard je 25 %.

Wann nutzen Sie Recreate?

Wenn zwei Versionen nie gleichzeitig laufen dürfen, z. B. RWO-Volume oder inkompatibles Schema. Preis: kurze Ausfallzeit.

Welche Rolle spielt die Readiness Probe beim Rollout?

Der Controller wartet, bis neue Pods Ready sind, bevor er alte beendet. Ohne Probe läuft der Rollout blind durch.

Was ist minReadySeconds?

Wie lange ein Pod Ready sein muss, bevor er als verfügbar zählt. Schützt vor Pods, die kurz nach dem Start abstürzen.

Was ist progressDeadlineSeconds?

Zeit ohne Fortschritt, bis das Deployment ProgressDeadlineExceeded meldet. Standard 600 s. Kein automatischer Rollback.

Wie machen Sie einen Rollback?

kubectl rollout undo, optional --to-revision. Mit GitOps per git revert.

Was ist revisionHistoryLimit?

Wie viele alte ReplicaSets bleiben. Standard 10. Ohne altes ReplicaSet kein Rollback dorthin.

Was macht kubectl rollout restart?

Es setzt eine Zeitstempel-Annotation im Template. Das startet einen normalen Rolling Update mit neuen Pods.

Wozu rollout pause?

Mehrere Änderungen sammeln und mit resume als einen Rollout ausführen.

Wie sorgen Sie dafür, dass eine neue ConfigMap neue Pods startet?

Hash der Config als Annotation im Template, z. B. Helm checksum/config, oder ConfigMap-Name mit Hash.

Wie machen Sie Canary oder Blue/Green?

Nicht eingebaut. Mit Argo Rollouts oder Flagger, oder mit zwei Deployments und Gewichten im Gateway API HTTPRoute.

Warum keine ReplicaSets direkt anlegen?

Ein ReplicaSet kann kein Rolling Update. Ein Image-Wechsel ändert laufende Pods nicht.

Kann man den Selector eines Deployments ändern?

Nein, spec.selector ist in apps/v1 unveränderlich. Man braucht ein neues Deployment.

Was setzt ein Rollback nicht zurück?

ConfigMaps, Secrets, Replica-Zahl, Daten und DB-Schema. Nur das Pod-Template.

Wie schützt ein PodDisruptionBudget beim Rollout?

Gar nicht direkt. Ein PDB begrenzt freiwillige Störungen wie Node-Drain. Den Rollout steuern maxSurge und maxUnavailable.

Szenario: Der Rollout hängt seit 10 Minuten bei 1 von 3. Was tun Sie?

rollout status und describe: neuer Pod in ImagePullBackOff oder CrashLoopBackOff? Logs prüfen. Dann rollout undo oder Fix, bei GitOps per git revert.

Szenario: Nach jedem Deploy gibt es eine Minute lang Fehler, obwohl der Rollout grün ist. Warum?

Wahrscheinlich keine oder eine zu schwache Readiness Probe. Pods bekommen Traffic, bevor die App bereit ist. Lösung: echte Probe, minReadySeconds, Graceful Shutdown.

Szenario: Sie machen kubectl rollout undo, aber nach einer Minute läuft wieder die kaputte Version. Warum?

Argo CD mit Self-Heal setzt den Cluster auf den Git-Stand zurück. Lösung: Rollback per git revert.
