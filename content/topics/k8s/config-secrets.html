ConfigMaps und Secrets

Kern: Eine ConfigMap ist ein API-Objekt für nicht geheime Konfiguration als Schlüssel-Wert-Paare. Ein Secret ist das gleiche für sensible Daten wie Passwörter und Tokens. Beide trennen Konfiguration vom Image, damit ein Image in jeder Umgebung läuft. Ein Secret ist nur base64-kodiert, nicht verschlüsselt: Schutz kommt von RBAC, Encryption at Rest und externen Secret Stores.

1. Wo sitzen ConfigMaps und Secrets?

  1. kube-apiserver: nimmt ConfigMap und Secret an, prüft RBAC (wer darf lesen) und verschlüsselt Secrets, wenn konfiguriert.
  2. etcd: speichert beide Objekte. Ohne Encryption at Rest liegt ein Secret dort lesbar.
  3. kubelet: holt nur die Secrets der Pods auf seinem Node. Secret-Volumes liegen im RAM (tmpfs), nicht auf der Disk.
  4. Pod: bekommt die Werte als Env-Variable oder als Datei in einem Volume. Beispiel: DB_URL als Env, application.yaml als Datei.
  5. Externe Quelle: Vault oder Azure Key Vault halten das echte Geheimnis. Der External Secrets Operator (ESO) oder der Secrets Store CSI Driver bringt es in den Cluster.

2. Die Reise eines Secrets (von Key Vault bis in den Container)

  1. Das Geheimnis entsteht in Key Vault. Das Security-Team setzt db-password in Azure Key Vault. Niemand legt es ins Git-Repo.
  2. Git enthält nur den Auftrag. Im Repo liegt ein ExternalSecret: „Hol db-password aus dem Store azure-kv und erzeuge Secret db.“ Das ist kein Geheimnis, also darf ArgoCD es synchronisieren.
  3. ESO meldet sich an. Der ESO-Controller nutzt Workload Identity: Sein ServiceAccount bekommt ein Kubernetes-Token. Entra ID tauscht es über eine Federated Credential gegen ein Azure-Token. Kein Client-Secret nötig.
  4. ESO schreibt ein normales Secret. Der API-Server verschlüsselt es beim Speichern in etcd (bei AKS optional mit KMS und einem Schlüssel aus Key Vault).
  5. Der Pod liest es. Als Env-Variable bleibt der alte Wert bis zum Neustart. Als Volume aktualisiert der kubelet die Datei nach einiger Zeit.
  6. Rotation. Nach refreshInterval holt ESO die neue Version und aktualisiert das Secret. Ein Tool wie Reloader oder ein Hash-Annotation-Trick startet die Pods neu, falls die App nur beim Start liest.

3. Beispiel: ConfigMap als Env und als Volume

kubectl create namespace demo-config
kubectl -n demo-config create configmap app-cfg --from-literal=LOG_LEVEL=info
kubectl -n demo-config create secret generic db --from-literal=password='S3cret!'

# Pod: LOG_LEVEL als Env, dieselbe ConfigMap zusätzlich als Volume
apiVersion: v1
kind: Pod
metadata: { name: cfg-demo, namespace: demo-config }
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo env=$LOG_LEVEL file=$(cat /cfg/LOG_LEVEL); sleep 10; done"]
    env:
    - name: LOG_LEVEL
      valueFrom: { configMapKeyRef: { name: app-cfg, key: LOG_LEVEL } }
    volumeMounts: [{ name: cfg, mountPath: /cfg }]
  volumes:
  - name: cfg
    configMap: { name: app-cfg }

kubectl -n demo-config get secret db -o jsonpath='{.data.password}'
kubectl -n demo-config get secret db -o jsonpath='{.data.password}' | base64 -d
kubectl -n demo-config patch configmap app-cfg -p '{"data":{"LOG_LEVEL":"debug"}}'
kubectl -n demo-config logs cfg-demo --tail=1     # sofort
kubectl -n demo-config logs cfg-demo --tail=1     # nach ca. 1-2 Minuten
UzNjcmV0IQ==
S3cret!
env=info file=info
env=info file=debug

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Der lokale k3s-Cluster war nicht erreichbar.

  1. UzNjcmV0IQ== ist nur base64. Jeder mit get secret-Recht liest das Passwort mit einem Befehl.
  2. Nach dem Patch zeigt die Env-Variable weiter info. Env wird nur beim Container-Start gesetzt.
  3. Die Volume-Datei zeigt nach dem kubelet-Sync debug. Die Verzögerung ist Sync-Periode plus Cache-TTL, laut Doku bis etwa eine Minute plus.
  4. Aufräumen: kubectl delete namespace demo-config.

4. Details, die Interviewer fragen

  1. Vier Wege in den Pod: env.valueFrom (ein Schlüssel), envFrom (alle Schlüssel), Volume (jeder Schlüssel eine Datei), oder die App liest direkt über die API.
  2. Updates: Volume-Dateien werden aktualisiert, über einen atomaren Symlink-Tausch (..data). Env-Variablen nie. Ein subPath-Mount bekommt keine Updates.
  3. Grösse: Eine ConfigMap und ein Secret dürfen maximal 1 MiB gross sein. Grosse Dateien gehören in ein Volume oder Object Storage.
  4. immutable: true: Ein unveränderliches ConfigMap oder Secret kann nicht mehr geändert werden. Der kubelet muss es nicht beobachten, das entlastet den API-Server. Änderung heisst: neuer Name, neues Rollout.
  5. Secret-Typen: Opaque (Standard), kubernetes.io/tls, kubernetes.io/dockerconfigjson (Image Pull), kubernetes.io/service-account-token (alt, heute kurzlebige Tokens über die TokenRequest API).
  6. data vs stringData: data erwartet base64. stringData nimmt Klartext und der API-Server kodiert ihn. Beim Lesen sieht man immer data.
  7. Encryption at Rest: Eine EncryptionConfiguration auf dem API-Server verschlüsselt Secrets in etcd. Provider: aescbc, aesgcm, secretbox oder KMS v2 (Schlüssel in externem KMS, Envelope Encryption). Der erste Provider in der Liste schreibt.
  8. Envelope Encryption: Jedes Objekt bekommt einen Daten-Schlüssel (DEK). Der DEK wird mit dem Schlüssel im KMS (KEK) verschlüsselt. Der KEK verlässt das KMS nie.
  9. Bestehende Secrets: Nach dem Einschalten der Verschlüsselung bleiben alte Secrets unverschlüsselt. Man muss sie neu schreiben: kubectl get secrets -A -o json | kubectl replace -f -.
  10. RBAC-Falle: Wer Pods in einem Namespace erstellen darf, kann jedes Secret dieses Namespaces mounten und lesen. list und watch auf Secrets geben ebenfalls alle Werte heraus.
  11. External Secrets Operator: Ein Controller mit CRDs. SecretStore / ClusterSecretStore: wie man sich am Backend anmeldet. ExternalSecret: welcher Schlüssel in welches K8s-Secret kommt, plus refreshInterval.
  12. Secrets Store CSI Driver: Ein CSI-Volume, das Geheimnisse beim Pod-Start direkt als Dateien aus Key Vault oder Vault mountet. Konfiguration über eine SecretProviderClass. Ein K8s-Secret entsteht nur optional (secretObjects).
  13. AKS Workload Identity: ServiceAccount mit Annotation azure.workload.identity/client-id, Pod mit Label azure.workload.identity/use: "true", dazu eine Federated Identity Credential auf der Managed Identity. Der Pod bekommt ein projiziertes Token und tauscht es gegen ein Entra-ID-Token.
  14. Vault Kubernetes Auth: Der Client schickt sein ServiceAccount-Token an Vault. Vault prüft es per TokenReview beim API-Server und gibt ein Vault-Token mit einer Policy zurück.

5. Vergleich

  • ConfigMap: nicht geheim, Klartext, max. 1 MiB. Für Feature-Flags, URLs, Log-Level.
  • Secret (nativ): base64, tmpfs auf dem Node, eigene RBAC-Regeln. Ohne Encryption at Rest kaum sicherer als eine ConfigMap.
  • Sealed Secrets: Das Secret wird mit einem Cluster-Schlüssel verschlüsselt und darf ins Git. Einfach, aber der Schlüssel hängt am Cluster und Rotation ist Handarbeit.
  • SOPS: verschlüsselt Werte in YAML-Dateien im Repo (z. B. mit Azure Key Vault oder age). Gut mit Flux oder Helm-Plugins.
  • External Secrets Operator: Wahrheit bleibt im externen Store, ESO synchronisiert in K8s-Secrets. Viele Backends, automatische Rotation, GitOps-tauglich.
  • Secrets Store CSI Driver: mountet direkt als Datei, ohne K8s-Secret. Nachteil: Pod startet nicht, wenn der Store nicht erreichbar ist; Env-Variablen nur über den Sync-Umweg.
  • Vault Agent Injector: Sidecar schreibt Geheimnisse in ein gemeinsames Volume. Kann dynamische Secrets (z. B. kurzlebige DB-Passwörter) erneuern. Dafür ein Sidecar pro Pod.

6. In der Produktion

  1. Konfig geändert, nichts passiert: Die App liest Env-Variablen oder liest die Datei nur beim Start. Lösung: Checksum-Annotation im Pod-Template (Helm: sha256sum der ConfigMap) oder Reloader. Dann rollt ein normales Rollout.
  2. subPath-Mount ohne Updates: Eine einzelne Datei per subPath bekommt keine Änderungen. Lösung: ganzes Verzeichnis mounten.
  3. Secret im Git: Jemand committet ein base64-Secret und hält es für verschlüsselt. Lösung: ESO oder Sealed Secrets, Secret Scanning in der CI, Geheimnis sofort rotieren.
  4. Rotation bricht die App: Das alte Passwort ist weg, bevor alle Pods das neue haben. Lösung: zwei gültige Versionen überlappen lassen, erst dann die alte löschen.
  5. ESO kann nicht lesen: Status SecretSyncedError. Ursachen: falsche Federated Credential (Subject muss system:serviceaccount:<ns>:<sa> sein), fehlende Key-Vault-Rolle, Netzwerk-Policy blockiert. Das alte Secret bleibt bestehen, der Pod läuft weiter.
  6. Secret im Log: Die App loggt ihre Env-Variablen beim Start. Lösung: Werte maskieren, Secrets lieber als Datei mounten.
  7. Zu breite RBAC: Ein Monitoring-Tool hat list secrets clusterweit. Lösung: Rechte auf Namespaces und Namen beschränken, regelmässig prüfen.

7. Diagnose: Werkzeuge und Befehle

  • kubectl get cm,secret -n <ns> und kubectl describe secret <name>: zeigt Schlüssel und Grössen, nicht die Werte.
  • kubectl exec <pod> -- env und -- ls -la /cfg: was der Container wirklich sieht (Achtung: Ausgabe enthält Geheimnisse).
  • kubectl get externalsecret -A: Spalte STATUS (SecretSynced) und READY. kubectl describe externalsecret zeigt Fehler.
  • kubectl get secretstore,clustersecretstore -A: ob der Store Valid ist.
  • kubectl auth can-i get secrets -n <ns> --as system:serviceaccount:<ns>:<sa>: RBAC prüfen.
  • Encryption prüfen (Self-Managed): etcdctl get /registry/secrets/<ns>/<name> muss mit k8s:enc: beginnen, nicht mit Klartext.
  • AKS: az aks show --query securityProfile.azureKeyVaultKms zeigt, ob KMS aktiv ist.

8. Senior-Punkte

  1. Die Quelle der Wahrheit liegt ausserhalb des Clusters. Vault oder Key Vault halten Geheimnisse, Git hält nur Verweise. So bleibt GitOps sauber.
  2. Env oder Datei ist eine Entscheidung: Env ist einfach, aber statisch und landet leicht in Logs und Crash-Dumps. Dateien unterstützen Rotation ohne Neustart, wenn die App neu liest.
  3. Kein Client-Secret für den Secret-Zugriff. Workload Identity löst das Henne-Ei-Problem: Der Pod beweist seine Identität mit einem kurzlebigen Token.
  4. Encryption at Rest ist Pflicht, aber sie schützt nur etcd-Backups und Disks. Gegen einen Angreifer mit API-Rechten hilft nur enge RBAC.
  5. Rotation muss geübt werden. Ein Secret, das nie rotiert wurde, wird bei der ersten Rotation einen Ausfall auslösen.
  6. Immutable ConfigMaps mit Hash im Namen machen Rollouts reproduzierbar und Rollbacks trivial. Kustomize configMapGenerator macht das automatisch.

10. Fallen

  • „Secrets sind verschlüsselt.“ → Falsch. Sie sind nur base64-kodiert. Verschlüsselt sind sie erst mit Encryption at Rest, und auch dann nur in etcd.
  • „Eine geänderte ConfigMap kommt sofort in den Pod.“ → Falsch. Env nie, Volumes nach Verzögerung, subPath nie.
  • „Ohne get secret-Recht kommt man nicht an Secrets.“ → Falsch. Wer Pods erstellen darf, mountet das Secret einfach.
  • „Encryption at Rest verschlüsselt auch alte Secrets.“ → Falsch. Erst beim nächsten Schreiben. Man muss sie neu schreiben.
  • „ESO-Secrets sind sicherer als normale Secrets.“ → Nur teilweise. Am Ende entsteht ein normales K8s-Secret. Der Gewinn ist Herkunft, Rotation und kein Geheimnis im Git.

11. Fragen

Was ist eine ConfigMap?

Ein API-Objekt für nicht geheime Konfiguration als Schlüssel-Wert-Paare. Sie trennt Konfiguration vom Image.

Was ist der Unterschied zwischen ConfigMap und Secret?

Ein Secret ist für sensible Daten: base64-kodiert, eigene RBAC, tmpfs auf dem Node und optional verschlüsselt in etcd. Technisch sind beide sehr ähnlich.

Ist ein Secret verschlüsselt?

Nein, nur base64-kodiert. Verschlüsselung in etcd braucht eine EncryptionConfiguration oder bei AKS die KMS-Option.

Wie kommt eine ConfigMap in einen Pod?

Als Env-Variable mit valueFrom oder envFrom, als Volume mit einer Datei pro Schlüssel, oder die App liest sie über die API.

Was passiert, wenn ich eine ConfigMap ändere?

Volumes werden nach kubelet-Sync aktualisiert. Env-Variablen und subPath-Mounts bleiben alt. Für Env braucht es einen Neustart.

Wie erzwinge ich ein Rollout nach einer Konfig-Änderung?

Eine Checksum-Annotation der ConfigMap ins Pod-Template schreiben, oder Reloader nutzen, oder kubectl rollout restart.

Warum bekommt ein subPath-Mount keine Updates?

Der kubelet aktualisiert das Verzeichnis per Symlink-Tausch. Ein subPath bindet die Datei direkt, ohne den Symlink zu folgen.

Was bringt immutable: true?

Schutz vor versehentlichen Änderungen und weniger Last, weil der kubelet nicht beobachten muss. Änderungen gehen nur über ein neues Objekt.

Wie gross darf ein Secret sein?

Maximal 1 MiB. Das gilt auch für ConfigMaps.

Was ist Encryption at Rest in Kubernetes?

Der API-Server verschlüsselt Secrets, bevor er sie in etcd schreibt. Konfiguriert über EncryptionConfiguration mit Providern wie aescbc oder KMS v2.

Was ist Envelope Encryption mit KMS?

Jedes Objekt bekommt einen Daten-Schlüssel. Dieser wird mit einem Schlüssel im externen KMS verschlüsselt, der das KMS nie verlässt.

Wer kann ein Secret lesen?

Wer get, list oder watch auf Secrets hat, und jeder, der Pods im Namespace erstellen darf. Ausserdem Admins mit etcd-Zugriff.

Was macht der External Secrets Operator?

Er liest Geheimnisse aus Vault, Key Vault und anderen Stores und schreibt sie als K8s-Secrets. Konfiguration über SecretStore und ExternalSecret, Refresh über refreshInterval.

SecretStore vs ClusterSecretStore?

SecretStore gilt für einen Namespace. ClusterSecretStore kann von ExternalSecrets aus allen Namespaces genutzt werden.

ESO oder Secrets Store CSI Driver?

ESO erzeugt K8s-Secrets und passt gut zu Env-Variablen und GitOps. CSI mountet direkt als Datei ohne K8s-Secret, aber der Pod-Start hängt am Store.

Wie funktioniert AKS Workload Identity?

Der Pod bekommt ein projiziertes ServiceAccount-Token. Entra ID tauscht es über eine Federated Identity Credential gegen ein Azure-Token. Kein Passwort im Cluster.

Wie meldet sich ein Pod bei Vault an?

Mit der Kubernetes Auth Method: Er schickt sein ServiceAccount-Token. Vault prüft es per TokenReview und gibt ein Token mit Policy zurück.

Sealed Secrets vs ESO?

Sealed Secrets verschlüsselt das Secret fürs Git. ESO lässt das Geheimnis im externen Store. ESO ist besser für zentrale Verwaltung und Rotation.

Env-Variable oder Datei für Secrets?

Datei, wenn möglich: Rotation ohne Neustart und weniger Risiko, dass Werte in Logs landen. Env ist einfacher für Apps, die nur Env kennen.

Was ist stringData?

Ein Feld für Klartext beim Schreiben. Der API-Server kodiert es base64 nach data. Beim Lesen erscheint nur data.

Wie rotiert man ein DB-Passwort ohne Ausfall?

Neues Passwort zusätzlich aktivieren, Secret aktualisieren, Pods neu laden, dann das alte Passwort entfernen. Zwei Versionen überlappen.

Szenario: Ein Kollege hat ein Secret-YAML ins Git gepusht. Was tun Sie?

Das Geheimnis sofort rotieren, denn die Git-Historie ist kompromittiert. Danach auf ESO oder Sealed Secrets umstellen und Secret Scanning in der CI einführen.

Szenario: Das Passwort in Key Vault wurde geändert, die App nutzt aber noch das alte. Warum?

ESO hat noch nicht synchronisiert (refreshInterval), oder die App liest es als Env-Variable. Prüfen mit describe externalsecret, dann Rollout auslösen oder Reloader einsetzen.

Szenario: Neue Pods starten nicht, Events zeigen „secret not found“. Was prüfen Sie?

Ob das ExternalSecret synchronisiert ist und der SecretStore gültig ist: Federated Credential, Key-Vault-Rolle, Netzwerk. Bis dahin hilft ein vorhandenes Secret oder optional: true nur bei unkritischen Werten.
