Docker: Image, Layer, Multi-Stage, Container vs VM

Kern: Ein Image ist ein unveränderlicher Stapel von Dateisystem-Layern plus Konfiguration. Ein Container ist ein normaler Linux-Prozess, den Namespaces isolieren und cgroups begrenzen. Er teilt den Kernel mit dem Host. Darum startet er in Millisekunden, isoliert aber schwächer als eine VM.

1. Wo sitzt Docker?

  1. docker CLI: ein Client. Er spricht per REST-API mit dem Daemon.
  2. dockerd: der Docker-Daemon. Er baut Images mit BuildKit (Standard seit Engine 23.0) und verwaltet Netz und Volumes.
  3. containerd: verwaltet Images und Container-Lebenszyklus. Kubernetes spricht über CRI direkt mit containerd, ohne dockerd.
  4. runc: die OCI Runtime. Sie legt Namespaces und cgroups an und startet den Prozess.
  5. Kernel: ein einziger für alle Container. Die Isolation kommt komplett aus Kernel-Funktionen.
  6. Registry: speichert Images im OCI-Format. Docker-gebaute Images laufen darum auch unter containerd und CRI-O.

2. Die Reise eines Images: vom Dockerfile zum Prozess

  1. Build-Kontext. docker build . schickt den Ordner an BuildKit. Die .dockerignore hält target/, .git und Secrets draussen.
  2. Build-Stage. Ein Image mit JDK und Maven baut das JAR. Zuerst nur pom.xml kopieren und Abhängigkeiten laden. Dieser Layer bleibt im Cache, solange sich pom.xml nicht ändert.
  3. Runtime-Stage. Ein zweites FROM mit nur einer JRE. COPY --from=build holt nur das JAR. JDK, Maven und Quellcode bleiben im Build-Stage zurück.
  4. Scan und Push. Ein Scanner (z. B. Trivy) prüft Pakete auf CVEs. Dann geht das Image in die Registry. Jeder Layer hat einen Digest (SHA-256).
  5. Pull. Der Node lädt nur Layer, die er noch nicht hat. Ein gemeinsames Basis-Image spart darum Zeit und Platz.
  6. OverlayFS. Die Layer werden read-only übereinander gelegt (lowerdir). Oben liegt ein leerer Writable Layer (upperdir). Ändert der Container eine Datei, kopiert OverlayFS sie zuerst nach oben (Copy-on-Write).
  7. Start. runc legt Namespaces und cgroups an und startet den Prozess als PID 1 im Container, als nicht-root User.

3. Beispiel: Multi-Stage-Dockerfile für Spring Boot

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline   # Cache-Layer
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q package -DskipTests

FROM eclipse-temurin:21-jre AS runtime
RUN useradd --uid 10001 --no-create-home app
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
USER 10001
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]   # exec form: java ist PID 1
$ docker build -t api:1.0 .            # zweiter Build, nur src/ geändert
 => CACHED [build 3/6] COPY pom.xml .
 => CACHED [build 4/6] RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline
 => [build 5/6] COPY src ./src
 => [build 6/6] RUN --mount=type=cache,target=/root/.m2 mvn -q package -DskipTests
 => CACHED [runtime 2/4] RUN useradd --uid 10001 --no-create-home app
 => [runtime 4/4] COPY --from=build /src/target/app.jar app.jar

$ docker images
REPOSITORY   TAG    SIZE
api          1.0    ~ 300 MB     (JRE-Basis + JAR)
# Der Build-Stage (JDK + Maven, viel grösser) wird nicht getaggt und nicht ausgeliefert.

$ docker history api:1.0       # zeigt jeden Layer mit Grösse und Befehl

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Docker war hier nicht verfügbar. Grössen sind Richtwerte und hängen vom Basis-Image ab.

  1. COPY pom.xml und dependency:go-offline sind CACHED. Nur der Code hat sich geändert.
  2. Ab dem ersten geänderten Schritt baut Docker alle folgenden Schritte neu. Darum kommt Selten-Geändertes nach oben.
  3. --mount=type=cache hält das Maven-Repository zwischen Builds, ohne es ins Image zu legen.
  4. Das ausgelieferte Image enthält nur JRE und JAR. Weniger Pakete heisst weniger CVEs und schnellere Pulls.
  5. USER 10001 und exec-Form-ENTRYPOINT: kein root, und java bekommt SIGTERM direkt.

4. Details, die Interviewer fragen

  1. Image-Aufbau (OCI): Manifest (Liste der Layer-Digests), Config (Env, Entrypoint, User), Layer (tar-Archive mit Änderungen). Ein Image Index bündelt Varianten für mehrere Architekturen (amd64, arm64).
  2. Welche Befehle erzeugen Layer: RUN, COPY, ADD ändern das Dateisystem. ENV, CMD, LABEL ändern nur die Config.
  3. Löschen schrumpft nicht: Eine Datei in Layer 2 löschen erzeugt in Layer 3 nur eine Whiteout-Markierung. Die Bytes bleiben im Image. Darum Download und Aufräumen im selben RUN.
  4. Cache-Regeln: RUN wird nach dem Befehlstext gecacht, COPY/ADD nach Prüfsumme der Dateien. Ein Treffer-Fehler invalidiert alle folgenden Schritte.
  5. Multi-Stage: Mehrere FROM in einem Dockerfile. Nur der letzte Stage (oder --target) wird zum Image. BuildKit baut nicht gebrauchte Stages gar nicht und baut unabhängige parallel.
  6. Build-Secrets: RUN --mount=type=secret,id=npmrc stellt ein Secret nur für diesen Schritt bereit. ARG oder ENV für Secrets landen in der Image-History.
  7. Basis-Image wählen: distroless (nur Runtime, keine Shell, kein Paketmanager), slim/alpine (klein, Alpine nutzt musl statt glibc), oder ein volles OS-Image für Debugging.
  8. Non-root: USER mit numerischer UID. In Kubernetes passt das zu runAsNonRoot: true, das eine numerische UID prüfen kann.
  9. PID 1 und Signale: Shell-Form (CMD java -jar) startet /bin/sh -c. Die Shell gibt SIGTERM oft nicht weiter. Nach der Grace Period kommt SIGKILL. Darum exec-Form oder ein Init wie tini (docker run --init).
  10. ENTRYPOINT vs CMD: ENTRYPOINT ist das Programm, CMD die Standard-Argumente. In Kubernetes überschreibt command ENTRYPOINT und args CMD.
  11. Tags vs Digest: Ein Tag ist ein verschiebbarer Name. Ein Digest (@sha256:...) ist unveränderlich. Für reproduzierbare Deployments Digest oder unveränderliche Tags.
  12. Namespaces: pid (eigene Prozess-IDs), net (eigenes Netz), mnt (eigenes Dateisystem), uts (Hostname), ipc, user (UID-Mapping), cgroup, time.
  13. cgroups v2: begrenzen CPU, Memory, PIDs und I/O. Überschreitet ein Prozess memory.max, tötet ihn der OOM-Killer. Kubernetes-Limits werden genau zu diesen Werten.
  14. Weitere Härtung: Capabilities (root-Rechte in Teilen, z. B. alle droppen), seccomp (erlaubte Syscalls), AppArmor/SELinux, read-only Root-Dateisystem.
  15. Container vs VM: Container teilen den Host-Kernel. Eine VM hat einen eigenen Kernel über einem Hypervisor. Ein Kernel-Exploit kann aus einem Container ausbrechen, aus einer VM viel schwerer.
  16. Dazwischen: gVisor (Kernel im User-Space) und Kata Containers (leichte VM pro Pod). In Kubernetes per RuntimeClass.
  17. Docker und Kubernetes: Kubernetes hat in 1.24 dockershim entfernt. Nodes nutzen containerd oder CRI-O. Images aus docker build laufen trotzdem, weil sie OCI-Images sind.
  18. Image Scanning: Scanner (Trivy, Grype, Docker Scout, Microsoft Defender für ACR) vergleichen Pakete mit CVE-Datenbanken. Dazu SBOM (Paketliste) und Signatur (cosign) für die Lieferkette.

5. Vergleich

  • Container vs VM: Container: geteilter Kernel, Start in Millisekunden, MB gross, schwächere Isolation. VM: eigener Kernel, Start in Sekunden bis Minuten, GB gross, starke Isolation.
  • Single-Stage vs Multi-Stage: Single-Stage liefert Compiler und Quellcode mit aus. Multi-Stage liefert nur das Ergebnis.
  • distroless vs alpine vs slim: distroless am kleinsten in der Angriffsfläche, aber ohne Shell. alpine sehr klein, aber musl kann Probleme machen. slim ist Debian/Ubuntu ohne Extras.
  • COPY vs ADD: COPY kopiert nur. ADD entpackt auch tar und lädt URLs. Standard: COPY.
  • Docker vs containerd vs CRI-O: Docker ist eine Entwickler-Plattform mit Build. containerd und CRI-O sind schlanke Runtimes für Kubernetes.
  • Docker vs Podman: Podman hat keinen Daemon und läuft gut rootless. Die CLI ist weitgehend kompatibel.
  • Volume vs Bind Mount vs Writable Layer: Writable Layer verschwindet mit dem Container. Volumes verwaltet Docker. Bind Mounts zeigen auf einen Host-Pfad.

6. In der Produktion

  1. Riesige Images, langsame Deployments: JDK, Build-Tools und Cache im finalen Image. Lösung: Multi-Stage, kleines Runtime-Basis-Image, .dockerignore.
  2. Jeder Build lädt alle Abhängigkeiten: COPY . . steht vor dem Dependency-Download. Lösung: Abhängigkeits-Dateien zuerst kopieren, Cache-Mounts nutzen.
  3. Secret im Image: Passwort per ARG oder in einem gelöschten Layer. Es bleibt in docker history und im Layer. Lösung: BuildKit-Secret-Mount, Secrets erst zur Laufzeit.
  4. Langsames Herunterfahren: Shell-Form-CMD, die App bekommt kein SIGTERM. Nach 30 s killt Kubernetes hart, Requests gehen verloren. Lösung: exec-Form oder Init-Prozess.
  5. Corporate Proxy: Ein Proxy signiert TLS neu, Builds und Downloads scheitern. Lösung: die Firmen-CA ins Image einbauen.
  6. CVEs im Basis-Image: Das Image ist alt, obwohl der Code sich nicht änderte. Lösung: regelmässig neu bauen, Scanner in der Pipeline mit Schwelle (z. B. keine kritischen CVEs).
  7. Unerwartete Architektur: Auf einem ARM-Laptop gebautes Image läuft nicht auf amd64-Nodes (exec format error). Lösung: docker buildx build --platform linux/amd64,linux/arm64.

7. Diagnose: Werkzeuge und Befehle

  • docker history <image>: Layer mit Grösse und Befehl.
  • docker image inspect <image>: Config, User, Entrypoint, Layer-Digests.
  • dive: Inhalt jedes Layers ansehen, verschwendeten Platz finden.
  • docker build --progress=plain --no-cache: jeden Schritt sehen, Cache-Probleme finden.
  • docker buildx imagetools inspect <image>: Plattformen und Digests im Image Index.
  • trivy image <image>, docker scout cves <image>, grype: CVEs finden.
  • docker stats, docker inspect --format '{{.State.OOMKilled}}': Verbrauch und OOM.
  • docker system df, docker system prune: Speicherplatz von Images, Cache und Volumes.
  • Im Container: cat /proc/1/status, cat /sys/fs/cgroup/memory.max, ls -l /proc/self/ns.

8. Senior-Punkte

  1. Das Image ist das Release-Artefakt. Einmal bauen, per Digest durch alle Umgebungen schieben. Konfiguration kommt zur Laufzeit.
  2. Kleine Angriffsfläche schlägt Patchen. Was nicht im Image ist, hat keine CVE. Distroless oder minimales JRE, non-root, read-only Root-FS.
  3. Debuggen ohne Shell planen: distroless braucht kubectl debug mit Ephemeral Container. Das Team muss das kennen.
  4. Container sind keine Sicherheitsgrenze wie VMs. Für fremden Code: gVisor, Kata oder getrennte Nodes.
  5. Lieferkette absichern: nur eigene Registry zulassen (z. B. per Kyverno), scannen, SBOM erzeugen, signieren.
  6. Docker-Versionen in CI kontrollieren. Neue Engine-Versionen können Tools wie Testcontainers brechen.

10. Fallen

  • „Ein Container ist eine leichte VM.“ → Falsch. Er ist ein isolierter Prozess auf dem Host-Kernel. Kein eigener Kernel.
  • „RUN rm macht das Image kleiner.“ → Falsch. Die Datei bleibt im früheren Layer. Nur im selben RUN aufräumen.
  • „Kubernetes kann seit 1.24 keine Docker-Images mehr.“ → Falsch. Nur dockershim fiel weg. Docker-Images sind OCI-Images und laufen weiter.
  • „Secrets per ARG sind sicher, weil sie nicht im Image landen.“ → Falsch. Sie stehen in der Image-History. Secret-Mounts nutzen.
  • „latest ist die neueste Version.“ → Falsch. Es ist nur ein Tag-Name ohne Garantie. Feste Tags oder Digests nutzen.
  • „Im Container ist root harmlos.“ → Falsch. Ohne User Namespace ist es dieselbe UID 0 wie auf dem Host. Ein Ausbruch hat dann root-Rechte.

11. Fragen

Was ist ein Docker-Image?

Ein unveränderlicher Stapel von Dateisystem-Layern plus Config (Entrypoint, Env, User). Beschrieben durch ein Manifest im OCI-Format.

Was ist ein Container?

Ein Linux-Prozess, isoliert durch Namespaces und begrenzt durch cgroups. Er nutzt die Image-Layer plus einen eigenen Writable Layer.

Was ist ein Layer?

Ein tar-Archiv mit den Dateisystem-Änderungen eines Schritts. Layer sind read-only, per Digest adressiert und werden zwischen Images geteilt.

Welche Dockerfile-Befehle erzeugen Layer?

RUN, COPY und ADD. Befehle wie ENV, CMD oder LABEL ändern nur die Image-Config.

Wie funktioniert der Build-Cache?

Jeder Schritt wird wiederverwendet, wenn Befehl und Eingaben gleich sind. COPY prüft die Datei-Prüfsummen. Nach dem ersten Cache-Fehler wird alles danach neu gebaut.

Wie ordnen Sie ein Dockerfile für guten Cache?

Selten Geändertes nach oben: Basis, Systempakete, Abhängigkeits-Dateien, Abhängigkeiten laden. Der Quellcode kommt zuletzt.

Was ist ein Multi-Stage-Build?

Mehrere FROM in einem Dockerfile. Man baut in einem grossen Stage und kopiert nur das Ergebnis mit COPY --from in ein kleines Runtime-Image.

Warum schrumpft ein Image nicht, wenn man Dateien löscht?

Die Datei steckt im früheren Layer. Der neue Layer enthält nur eine Whiteout-Markierung.

Was ist Copy-on-Write in OverlayFS?

Die Image-Layer sind read-only. Ändert der Container eine Datei, kopiert OverlayFS sie zuerst in den Writable Layer.

Was ist distroless?

Ein Basis-Image nur mit der Runtime und ihren Bibliotheken, ohne Shell und Paketmanager. Kleine Angriffsfläche, aber Debugging nur über Ephemeral Container.

Warum non-root?

Ohne User Namespace ist root im Container root auf dem Host. Ein Ausbruch hätte volle Rechte. Darum USER mit numerischer UID und runAsNonRoot.

Shell-Form vs exec-Form?

Shell-Form startet /bin/sh -c, die Shell gibt SIGTERM oft nicht weiter. Exec-Form startet das Programm direkt als PID 1.

ENTRYPOINT vs CMD?

ENTRYPOINT ist das Programm, CMD die Standard-Argumente. In Kubernetes überschreibt command ENTRYPOINT und args CMD.

Wie geben Sie beim Build ein Secret mit?

Mit RUN --mount=type=secret. Es existiert nur während dieses Schritts. ARG und ENV landen in der History.

Tag vs Digest?

Ein Tag ist ein verschiebbarer Name. Ein Digest ist der SHA-256 des Manifests und damit unveränderlich.

Was sind Namespaces?

Kernel-Funktionen, die die Sicht eines Prozesses begrenzen: eigene PIDs, Netz, Mounts, Hostname, IPC, Users.

Was sind cgroups?

Kernel-Funktionen, die Ressourcen begrenzen und messen: CPU, Memory, PIDs, I/O. Kubernetes-Limits werden zu cgroup-Werten.

Container vs VM?

Container teilen den Host-Kernel, starten in Millisekunden und sind klein. VMs haben einen eigenen Kernel und isolieren stärker, sind aber schwerer.

Wann nehmen Sie eine VM statt Container?

Bei nicht vertrauenswürdigem Code, anderem Kernel oder anderem Betriebssystem. Mittelweg: gVisor oder Kata Containers.

Was hat Kubernetes 1.24 mit Docker geändert?

dockershim wurde entfernt. Nodes nutzen containerd oder CRI-O direkt. Docker-gebaute Images laufen weiter, weil sie OCI-Images sind.

Wie läuft ein Container von docker run bis zum Prozess?

CLI → dockerd → containerd → shim → runc. runc legt Namespaces und cgroups an und startet den Prozess.

Wie scannen Sie Images?

Mit Trivy, Grype oder Docker Scout in der Pipeline, mit Schwelle für kritische CVEs. Dazu regelmässiger Scan in der Registry, weil neue CVEs dazukommen.

Was ist eine SBOM?

Eine Software Bill of Materials: die Liste aller Pakete und Versionen im Image. Damit findet man betroffene Images bei einer neuen CVE schnell.

Wie bauen Sie für mehrere Architekturen?

docker buildx build --platform linux/amd64,linux/arm64. Das Ergebnis ist ein Image Index mit einem Manifest pro Plattform.

COPY vs ADD?

COPY kopiert nur lokale Dateien. ADD entpackt auch tar-Archive und lädt URLs. Standard ist COPY, weil es vorhersehbar ist.

Szenario: Das Image ist 1,2 GB und Deployments dauern Minuten. Was tun Sie?

Mit docker history oder dive die grossen Layer finden. Dann Multi-Stage mit kleinem Runtime-Image, .dockerignore und Aufräumen im selben RUN.

Szenario: Der Pod braucht beim Stoppen immer genau 30 Sekunden. Warum?

Die App bekommt SIGTERM nicht, wahrscheinlich Shell-Form-CMD. Nach der Grace Period kommt SIGKILL. Lösung: exec-Form oder tini.

Szenario: Builds hinter dem Firmen-Proxy scheitern mit TLS-Fehlern. Was tun Sie?

Der Proxy signiert TLS mit einer Firmen-CA neu. Ich baue das CA-Bundle ins Image ein und setze es für Java, Python und pip. TLS-Prüfung abschalten ist keine Lösung.
