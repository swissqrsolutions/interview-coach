Troubleshooting: CrashLoopBackOff, Pending, ImagePullBackOff

Kern: Kubernetes-Troubleshooting folgt einem festen Pfad aus get, describe, logs --previous und events. Der Status zeigt, wo der Pod hängt. Pending heisst Scheduler oder Volume, ImagePullBackOff heisst Registry und CrashLoopBackOff heisst, die App selbst stirbt.

Antwort-Muster

Frage: Ein Pod steckt in CrashLoopBackOff. Wie gehen Sie vor?

  1. Mechanismus: Ich gehe get, describe, logs --previous, events. Last State und Exit-Code zeigen den echten Fehler, CrashLoopBackOff ist nur die Wartezeit.
  2. Zahl: Exit 137 ist 128 + 9, also SIGKILL, meist OOMKilled. Der Backoff wächst von 10 s bis 5 Minuten und wird nach 10 Minuten stabilem Lauf zurückgesetzt.
  3. Trade-off: Eine Änderung nach der anderen testen, z. B. das Memory-Limit hoch. Sonst weiss man nicht, was gewirkt hat.
  4. Produktion: Erst stabilisieren, z. B. Rollback per git revert. Dann den Fix in Git und einen Alarm auf Restarts setzen.

1. Die Reise einer Fehlersuche

  1. get pods. kubectl get pods -n match -o wide zeigt: CrashLoopBackOff, 7 Restarts, Node aks-spark-01. Die Restart-Zahl beweist: Der Container startete schon.
  2. describe. kubectl describe pod zeigt Last State: Terminated, Reason: OOMKilled, Exit Code: 137. Das ist die wichtigste Zeile.
  3. Events. Unten in describe oder kubectl get events --sort-by=.lastTimestamp. Sie zeigen Scheduler-, Pull- und Probe-Meldungen. Events leben standardmässig nur ca. eine Stunde.
  4. logs --previous. Die Logs des gestorbenen Containers. Ohne --previous sieht man den neuen, oft leeren Container.
  5. kubectl debug. Hat das Image keine Shell (distroless), hängt man einen Ephemeral Container an. Oder man kopiert den Pod mit anderem Command.
  6. Hypothese testen. Eine Änderung zur Zeit, z. B. Memory-Limit hoch. Dann beobachten.
  7. Fix dauerhaft machen. Die Änderung kommt in Git (Helm values). Dazu ein Alarm auf Restarts, damit es nächstes Mal früher auffällt.

2. Aufbau

  1. Scheduler: findet einen passenden Node. Findet er keinen, bleibt der Pod Pending ohne Node.
  2. Kubelet: bindet Volumes, holt Secrets und ConfigMaps, ruft das CNI. Hängt das, zeigt der Pod ContainerCreating oder CreateContainerConfigError.
  3. Registry: Der Kubelet zieht das Image über containerd. Scheitert das: ErrImagePull, dann ImagePullBackOff.
  4. Container: läuft. Stirbt er wiederholt, wartet der Kubelet immer länger: CrashLoopBackOff.
  5. Probes: Readiness steuert den Traffic, Liveness den Neustart. Ein Pod kann Running sein und trotzdem keinen Traffic bekommen.

3. Details, die Interviewer fragen

  1. Pod-Phasen: Pending, Running, Succeeded, Failed und Unknown. CrashLoopBackOff ist keine Phase. Es ist der Wartegrund eines Containers.
  2. Container-States: Waiting hat einen Reason. Running läuft. Terminated hat Reason und Exit Code.
  3. CrashLoopBackOff: Der Container endet immer wieder, und restartPolicy verlangt Neustart. Der Backoff startet bei 10 s und verdoppelt sich. Der Deckel ist 5 Minuten. Ab 1.35 kann man den Deckel pro Node in der Kubelet-Config senken. Das Feld heisst maxContainerRestartPeriod.
  4. Häufige Crash-Ursachen: Typisch sind eine App-Exception beim Start und eine fehlende Env-Variable. Auch ein falscher Command und eine nicht erreichbare Datenbank kommen vor. Dazu kommen OOMKilled und eine zu strenge Liveness Probe.
  5. Exit Codes: 0 heisst fertig. Ein Deployment startet trotzdem neu. 1 ist ein App-Fehler. 137 ist SIGKILL, also OOM oder Kill nach der Grace Period. 143 ist SIGTERM. 126 und 127 heissen, der Command ist nicht ausführbar oder nicht gefunden.
  6. OOMKilled und Evicted: Bei OOMKilled ist der Container über seinem Limit, und der Kernel tötet ihn. Bei Evicted hat der Node zu wenig Speicher. Der Kubelet wirft Pods nach QoS-Klasse raus.
  7. Pending-Ursachen: Häufig sind es zu wenig CPU oder Memory für die Requests. Auch Taints ohne Toleration oder nodeSelector und Affinity sind möglich. Auch ein PVC, das nicht gebunden ist, und eine ResourceQuota sind möglich. Manchmal gibt es keine Nodes, weil der Autoscaler noch skaliert.
  8. Requests zählen, nicht Verbrauch: Der Scheduler plant nach Requests. Ein fast leerer Node kann „voll“ sein.
  9. ImagePullBackOff-Ursachen: Möglich sind ein Tippfehler in Name oder Tag und ein gelöschter Tag. Auch eine private Registry ohne imagePullSecrets und AKS ohne ACR-Berechtigung (AcrPull) kommen vor. Dazu kommen Rate Limit bei Docker Hub, Proxy oder TLS und eine falsche Architektur.
  10. CreateContainerConfigError: Ein referenziertes Secret oder eine ConfigMap fehlt. Oder ein Key darin fehlt.
  11. Probes: Wenn Liveness scheitert, gibt es einen Neustart. Das sieht aus wie ein CrashLoop. Wenn Readiness scheitert, gibt es keinen Traffic und keinen Neustart. Startup schützt langsame Starts. Bis sie gelingt, laufen die anderen Probes nicht.
  12. DNS-Probleme: Die /etc/resolv.conf des Pods zeigt auf CoreDNS mit ndots:5. Externe Namen erzeugen dadurch mehrere Suchanfragen. Ursachen sind CoreDNS down, eine NetworkPolicy auf Port 53 oder ein falscher Service-Name oder Namespace.
  13. kubectl debug (Ephemeral Container): Der Befehl ist kubectl debug -it <pod> --image=busybox:1.36 --target=<container>. Er teilt den Prozess-Namespace des Ziel-Containers. Er ist ideal für distroless.
  14. kubectl debug --copy-to: Der Befehl legt eine Kopie des Pods an, z. B. mit --container=app -- sh oder anderem Image. Der Original-Pod bleibt unberührt.
  15. kubectl debug node/<name>: Er startet einen Pod im Host-Namespace. Das Node-Dateisystem liegt unter /host. Das hilft für Kubelet-Logs und crictl.
  16. Terminating hängt: Meist ist ein Finalizer schuld oder ein Node, der nicht erreichbar ist. Man klärt erst die Ursache. Notfalls nutzt man --force --grace-period=0.

4. Fallen

  • „CrashLoopBackOff ist der Fehler.“ → Falsch. Es ist nur die Wartezeit. Der Fehler steht im Last State und in logs --previous.
  • „kubectl logs zeigt den Absturz.“ → Oft nicht. Es zeigt den neuen Container. Den alten zeigt --previous.
  • „Exit 137 heisst immer OOM.“ → Falsch. 137 ist SIGKILL. Auch ein Kill nach der Grace Period gibt 137. Reason OOMKilled prüfen.
  • „Pending heisst, der Cluster ist voll.“ → Nicht immer. Auch Taints, Affinity, PVC oder Quota.
  • „Der Scheduler schaut auf den echten Verbrauch.“ → Falsch. Er plant nach Requests.
  • „Readiness-Fehler starten den Pod neu.“ → Falsch. Nur Liveness startet neu. Readiness nimmt nur den Traffic weg.

5. Selbsttest

Warum?

Warum logs --previous?

Ohne den Schalter zeigt kubectl den aktuellen, frisch gestarteten Container. Die Absturzmeldung steht im vorherigen.

Ist CrashLoopBackOff eine Pod-Phase?

Nein. Es ist der Waiting-Reason eines Containers. Die Phase ist meist Running.

Ein Node hat 10 % Last, trotzdem Insufficient cpu. Warum?

Der Scheduler zählt Requests, nicht Verbrauch. Die Requests der Pods füllen den Node schon.

Warum sieht man alte Events nicht mehr?

Events sind kurzlebig, standardmässig ca. eine Stunde. Für später braucht es einen Event-Exporter oder Logging.

Warum zeigt kubectl logs den Absturz oft nicht?

Ohne --previous sieht man den neuen, oft leeren Container.

Wie innen?

Wie gehen Sie bei einem kaputten Pod vor?

kubectl get pods, dann describe für Last State und Events, dann logs --previous. Bei Bedarf kubectl debug.

Was bedeutet CrashLoopBackOff?

Der Container startet und endet immer wieder. Der Kubelet wartet zwischen Neustarts immer länger, bis maximal 5 Minuten.

Warum ist ein Pod Pending?

Kein Node passt: zu wenig CPU/Memory für die Requests, Taints, Affinity, ungebundenes PVC oder Quota. Die FailedScheduling-Events nennen den Grund pro Node.

Was ist CreateContainerConfigError?

Ein referenziertes Secret, eine ConfigMap oder ein Key darin fehlt. Die Events nennen den Namen.

Liveness vs Readiness vs Startup Probe?

Liveness startet neu, Readiness steuert Traffic, Startup schützt langsame Starts und blockiert die anderen Probes, bis sie gelingt.

Wie verursacht eine Probe CrashLoopBackOff?

Eine zu strenge Liveness Probe tötet den Container immer wieder. Events zeigen „failed liveness probe, will be restarted“.

Wie debuggen Sie ein distroless Image ohne Shell?

kubectl debug mit Ephemeral Container und --target. Er teilt den Prozess-Namespace und bringt eigene Tools mit.

Was macht kubectl debug --copy-to?

Es legt eine Kopie des Pods an, z. B. mit anderem Command oder Image. So debuggt man, ohne den Original-Pod zu ändern.

Wie debuggen Sie einen Node?

kubectl debug node/<name> startet einen Pod im Host-Namespace mit Node-Dateisystem unter /host. Dort crictl und Kubelet-Logs.

Wie prüfen Sie DNS im Pod?

nslookup kubernetes.default und den Service-Namen, /etc/resolv.conf lesen, CoreDNS-Pods und Logs prüfen, NetworkPolicy für Port 53 prüfen.

Was bedeutet ndots:5?

Namen mit weniger als 5 Punkten probiert der Resolver zuerst mit allen Suchdomains. Externe Namen erzeugen so mehrere unnötige Anfragen.

Zahlen

Wie lange ist der Backoff?

10 s, dann verdoppelt, Deckel 300 s. Nach 10 Minuten stabilem Lauf beginnt er wieder bei 10 s.

Was bedeutet Exit Code 137?

128 + 9, also SIGKILL. Meist OOMKilled, aber auch ein Kill nach abgelaufener Grace Period.

Was bedeutet Exit Code 143?

128 + 15, also SIGTERM. Der Container wurde regulär gestoppt und hat sich beendet.

Wie lange leben Events?

Standardmässig etwa eine Stunde.

Welche Exit Codes sollte man kennen?

0 fertig, 1 App-Fehler, 137 SIGKILL, 143 SIGTERM, 126 und 127 Command nicht ausführbar oder nicht gefunden.

Vergleich

OOMKilled vs Evicted?

OOMKilled: Container über seinem Memory-Limit, der Kernel tötet ihn. Evicted: Node hat zu wenig Ressourcen, der Kubelet entfernt Pods nach QoS.

ErrImagePull vs ImagePullBackOff?

ErrImagePull ist der erste Fehlschlag. ImagePullBackOff heisst, der Kubelet wartet vor dem nächsten Versuch.

Typische Ursachen für ImagePullBackOff?

Falscher Name oder Tag, fehlende Pull-Berechtigung, Rate Limit, Proxy oder TLS, falsche CPU-Architektur.

Wie zieht AKS Images aus ACR ohne Secret?

Die Kubelet-Identität des Clusters bekommt die Rolle AcrPull auf der Registry. Prüfen mit az aks check-acr.

Pending, ContainerCreating oder ImagePullBackOff?

Pending heisst kein Node gewählt. ContainerCreating heisst Node gewählt, aber Volume, CNI oder Secret hängt. ImagePullBackOff heisst Registry, Tag oder Auth.

Liveness oder Readiness bei einem Fehler?

Liveness startet neu, Readiness nimmt nur den Traffic weg.

Produktion

Ein Pod hängt in Terminating. Was tun?

Finalizer und Node-Zustand prüfen. Erst die Ursache lösen, nur notfalls --force --grace-period=0.

Welche Alarme setzen Sie für Pods?

Restarts über Zeit, letzter Abbruchgrund OOMKilled, Pods lange Pending, Deployments mit fehlenden Replicas.

Szenario: Ein Java-Service geht nach jedem Lasttest in CrashLoopBackOff mit Exit 137. Wie gehen Sie vor?

describe zeigt OOMKilled. Ich vergleiche Speicher-Metriken mit dem Limit, setze MaxRAMPercentage und ein gemessenes Limit. Dann Lasttest wiederholen.

Szenario: Nach einem Release bleiben alle neuen Pods in ImagePullBackOff. Was prüfen Sie?

Events lesen: not found oder unauthorized. Tag in der Registry prüfen, Pipeline-Reihenfolge, AcrPull-Rolle mit az aks check-acr. Sofort-Massnahme: Rollback per Git.

Szenario: Spark-Pods bleiben bei Lastspitzen Pending. Was ist Ihre Analyse?

FailedScheduling-Events zeigen Insufficient cpu/memory. Ich prüfe, ob der Node-Autoscaler neue Nodes startet, ob Requests realistisch sind und ob Taints oder Affinity passen.

Design

Wie gehen Sie unter Druck bei einem Ausfall vor?

Ein fester Pfad schlägt Raten. Erst stabilisieren, dann analysieren. Der Fix gehört in Git.

Wie setzen Sie Limits richtig?

Nach Messung und nicht nach Gefühl. Memory-Limit gleich Request ist meist richtig. CPU-Limits verursachen Throttling.

Szenario: Liveness tötet unter Last gesunde Pods. Wie bauen Sie die Probes um?

Liveness nur für „hängt fest“, grosszügige Timeouts und eine Startup Probe. Keine Abhängigkeiten in Liveness.

Wie bauen Sie Alarme für Pods?

Alarme auf Symptome wie Restarts, Pending-Dauer und OOMKilled-Grund.

Gerüst

  • Warum? Ohne festen Pfad rät man unter Druck. Der Status zeigt die Stelle im Lebenslauf des Pods.
  • Wie innen? Scheduler, kubelet (Volume, Secret, CNI), Registry, Container, Probes. Last State und Exit-Code zeigen den echten Fehler.
  • Zahlen Backoff 10 s, 20 s, 40 s bis 5 Minuten, Reset nach 10 Minuten. Exit 137 = 128 + 9, 143 = SIGTERM. Events leben ca. 1 Stunde.
  • Vergleich Pending: Scheduler. ContainerCreating: Volume, CNI, Secret. ImagePullBackOff: Registry. CrashLoopBackOff: App. OOMKilled: eigenes Limit. Evicted: Node.
  • Produktion Liveness zu streng, JVM OOMKilled, Pending bei Lastspitzen, ImagePullBackOff nach Release, Exit 0 in CrashLoop.
  • Design Erst stabilisieren, dann analysieren. Fix in Git. Alarme auf Symptome wie Restarts und OOMKilled.

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Der lokale k3s-Cluster war nicht erreichbar. Testpod: stress --vm 1 --vm-bytes 150M mit Limit 64Mi.

  1. STATUS ist der aktuelle Wartegrund. Der echte Fehler steht im Last State.
  2. Exit Code 137 = 128 + 9 (SIGKILL). Der Kernel hat den Prozess wegen des Memory-Limits der cgroup getötet.
  3. Die Wartezeit wächst: 10 s, 20 s, 40 s … bis maximal 5 Minuten. Nach 10 Minuten stabilem Lauf setzt der Kubelet den Zähler zurück.
  4. Logs sind bei OOMKilled oft leer. Die App bekommt kein Signal, das sie loggen könnte.
  5. Fix: Limit passend zum echten Verbrauch setzen, oder den Speicherbedarf der App senken (z. B. JVM -XX:MaxRAMPercentage).

Vergleich

  • Pending: kein Node gewählt oder Volume fehlt. Suchen in Scheduler-Events.
  • ContainerCreating: Node gewählt, aber Volume, CNI oder Secret hängt. Suchen in Kubelet-Events.
  • ErrImagePull / ImagePullBackOff: erster Fehlschlag / wiederholter Fehlschlag mit Wartezeit. Suchen in Registry, Tag, Auth.
  • CrashLoopBackOff: Container startet und stirbt. Suchen in Last State, Exit Code, logs --previous.
  • Running, aber 0/1 READY: Readiness Probe scheitert. Suchen in Probe-Events und App-Health-Endpoint.
  • Evicted: Node unter Druck (Memory, Disk). Suchen in Node-Conditions und QoS.
  • OOMKilled: eigenes Limit überschritten. Suchen in Metriken zum Speicherverbrauch.

In der Produktion

  1. Liveness zu streng: Unter Last antwortet /health langsam, Liveness tötet gesunde Pods. Ergebnis: Kaskade von Neustarts. Lösung: Liveness nur für „hängt fest“, grosszügige Timeouts, Startup Probe für langsamen Start, keine Abhängigkeiten in Liveness.
  2. JVM OOMKilled: Heap plus Metaspace plus Threads plus Direct Memory über dem Limit. Lösung: -XX:MaxRAMPercentage (z. B. 75), Limit an echte Messung anpassen.
  3. Pending bei Lastspitzen: Requests zu hoch oder Autoscaler zu langsam. Lösung: Requests messen und anpassen, Node-Autoscaling (z. B. Karpenter), Prioritäten.
  4. ImagePullBackOff nach Release: Tag nicht gepusht oder Pipeline-Reihenfolge falsch. Lösung: Deploy erst nach erfolgreichem Push, Images per Digest oder unveränderlichem Tag.
  5. Docker-Hub-Rate-Limit: Viele Nodes ziehen gleichzeitig. Lösung: eigene Registry (ACR) als Quelle oder Cache.
  6. DNS-Timeouts sporadisch: UDP-Conntrack-Rennen oder überlastetes CoreDNS. Lösung: CoreDNS skalieren, NodeLocal DNSCache, FQDN mit Punkt am Ende für externe Namen.
  7. Exit 0 in CrashLoop: Der Prozess endet normal, z. B. Hintergrundprozess ohne Vordergrund. Ein Deployment startet ihn trotzdem neu. Lösung: Prozess im Vordergrund oder Job statt Deployment.

Diagnose: Werkzeuge und Befehle

  • kubectl get pods -o wide, -w zum Beobachten.
  • kubectl describe pod <pod>: State, Last State, Exit Code, Events.
  • kubectl logs <pod> -c <container> --previous: Logs des letzten gestorbenen Containers. --all-containers für Init- und Sidecar-Container.
  • kubectl get events -n <ns> --sort-by=.lastTimestamp oder kubectl events --for pod/<pod>.
  • kubectl top pod / kubectl top node: aktueller Verbrauch (braucht metrics-server).
  • kubectl describe node <node>: Allocatable, Allocated resources, Taints, Conditions (MemoryPressure, DiskPressure).
  • kubectl debug -it <pod> --image=busybox:1.36 --target=<container>: Shell neben distroless-Container.
  • kubectl debug node/<node> -it --image=ubuntu, dann chroot /host, crictl ps, journalctl -u kubelet.
  • DNS: kubectl exec -it <pod> -- nslookup kubernetes.default, cat /etc/resolv.conf, CoreDNS-Logs.
  • AKS: az aks check-acr --name <cluster> -g <rg> --acr <acr>.azurecr.io prüft den Pull aus ACR.
  • Prometheus: kube_pod_container_status_restarts_total, kube_pod_container_status_last_terminated_reason für Alarme.

Senior-Punkte

  1. Ein fester Pfad schlägt Raten. Status → Last State → Events → Logs. Unter Druck spart das die meiste Zeit.
  2. Erst stabilisieren, dann analysieren. Rollback per Git (z. B. git revert mit ArgoCD), dann in Ruhe die Ursache suchen.
  3. Kein Patchen im Cluster. Mit GitOps überschreibt Self-Heal manuelle Änderungen ohnehin. Der Fix gehört in Git.
  4. Probes sind Betriebsdesign. Falsche Liveness-Probes verursachen mehr Ausfälle, als sie verhindern.
  5. Limits nach Messung, nicht nach Gefühl. Memory-Limit = Request ist für Speicher meist richtig; CPU-Limits verursachen Throttling.
  6. Alarme auf Symptome: Restarts, Pending-Dauer, OOMKilled-Grund. Nicht erst warten, bis Nutzer melden.
