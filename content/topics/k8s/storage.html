PV, PVC, StorageClass, StatefulSet

Kern: Ein PersistentVolume (PV) ist Speicher im Cluster, der länger lebt als ein Pod. Ein PersistentVolumeClaim (PVC) bestellt ihn, und eine StorageClass legt fest, wie ein PV automatisch entsteht. Ein StatefulSet gibt jedem Pod einen festen Namen und ein eigenes Volume für zustandsbehaftete Software wie Datenbanken.

Antwort-Muster

Frage: Wie bekommt ein Pod dauerhaften Speicher in Kubernetes?

  1. Mechanismus: Der Pod nennt im Volume nur den Namen eines PVC. Die StorageClass lässt den CSI-Treiber die Disk anlegen, und das PV wird an den PVC gebunden.
  2. Zahl: RWO erlaubt einen Node, RWOP genau einen Pod. Ein StatefulSet legt pro Pod ein eigenes PVC an, z. B. data-pg-0.
  3. Trade-off: Zonale Disks binden den Pod an eine Zone. Darum WaitForFirstConsumer, sonst entsteht die Disk in der falschen Zone.
  4. Produktion: Beim Löschen eines StatefulSets bleiben die PVCs, das schützt Daten, kostet aber Speicher. Ein Snapshot ist kein Backup.

1. Die Reise eines Volumes (dynamisches Provisioning im StatefulSet)

  1. Das StatefulSet startet. pg hat replicas: 2 und ein volumeClaimTemplate namens data. Der Controller erzeugt zuerst nur Pod pg-0.
  2. Ein PVC entsteht. Aus der Vorlage wird PVC data-pg-0. Sein Name ist <template>-<statefulset>-<ordinal>. Es bleibt Pending.
  3. Der Scheduler entscheidet zuerst. Die StorageClass hat volumeBindingMode: WaitForFirstConsumer. Darum wählt der Scheduler erst einen Node, zum Beispiel in Zone 1.
  4. Der Provisioner erzeugt die Disk. Der CSI-Treiber legt die Azure Disk in Zone 1 an. So passen Disk und Node zusammen.
  5. PV und PVC werden gebunden. Das PV ist Bound. Der kubelet hängt die Disk an den Node und mountet sie in den Pod.
  6. Ordnung: Erst wenn pg-0 Running und Ready ist, startet pg-1 mit eigenem PVC data-pg-1.
  7. Der Pod stirbt. Der neue Pod heisst wieder pg-0 und bekommt wieder data-pg-0. Die Daten bleiben. Aber: Er muss in Zone 1 laufen, denn die Disk ist zonal.

2. Aufbau

  1. Pod: verweist im Volume nur auf den Namen des PVC. Er kennt keine Disk.
  2. PVC: die Bestellung im Namespace. Beispiel: „10 GiB, ReadWriteOnce, Klasse managed-csi“.
  3. StorageClass: die Vorlage der Plattform. Sie nennt den Provisioner (CSI-Treiber), Parameter wie SKU, die Reclaim Policy und den Binding Mode.
  4. PV: das Cluster-Objekt für ein echtes Volume. Es ist nicht an einen Namespace gebunden. Ein PV gehört zu genau einem PVC.
  5. CSI-Treiber: das Container Storage Interface-Plugin. Es erzeugt, hängt an (attach) und mountet die echte Disk. Beispiel: disk.csi.azure.com auf AKS, rancher.io/local-path auf k3s.

3. Details, die Interviewer fragen

  1. Statisch und dynamisch: Beim statischen Provisioning legt ein Admin PVs vorher an. Beim dynamischen Provisioning erzeugt die StorageClass das PV, sobald ein PVC kommt. Heute ist dynamisch der Normalfall.
  2. Access Modes: ReadWriteOnce (RWO) erlaubt einem Node das Schreiben. ReadOnlyMany (ROX) erlaubt vielen das Lesen. ReadWriteMany (RWX) erlaubt vielen Nodes das Schreiben. ReadWriteOncePod (RWOP) erlaubt genau einem Pod den Zugriff. RWO erlaubt mehrere Pods auf demselben Node.
  3. Wer kann was: Azure Disk ist normalerweise RWO oder RWOP. Mit Shared Disk (maxShares ab 2) und volumeMode: Block geht auch RWX, die App koordiniert dann die Schreibzugriffe selbst. Azure Files und NFS können RWX. Blockspeicher ist schnell. Dateispeicher ist teilbar.
  4. Reclaim Policy: Delete löscht die Disk mit dem PVC. Retain behält PV und Disk. Das PV wird dann Released und muss von Hand bereinigt werden. Dynamische PVs erben die Policy der StorageClass. Der Standard ist Delete.
  5. Binding Mode: Immediate erzeugt die Disk sofort, vielleicht in der falschen Zone. WaitForFirstConsumer wartet auf den Scheduler. Für zonale Disks nimmt man immer WaitForFirstConsumer.
  6. Volume Expansion: Mit allowVolumeExpansion: true vergrössert man ein PVC. Dazu ändert man spec.resources.requests.storage. Verkleinern geht nicht.
  7. Default StorageClass: Die Annotation storageclass.kubernetes.io/is-default-class: "true" macht eine Klasse zum Standard. PVCs ohne storageClassName nutzen sie. Auf AKS ist das managed-csi.
  8. Schutz: Ein PVC in Benutzung hat den Finalizer kubernetes.io/pvc-protection. Das Löschen wartet, bis kein Pod es mehr nutzt.
  9. StatefulSet-Identität: Der Name hat eine Ordinalzahl, z. B. pg-0. Die DNS ist fest über einen Headless Service mit clusterIP: None. Das Volume ist fest pro Ordinal.
  10. Reihenfolge: OrderedReady startet 0, 1, 2 nacheinander und stoppt rückwärts. Parallel startet alle gleichzeitig. Rolling Updates gehen immer von der höchsten Ordinalzahl rückwärts. Mit partition macht man einen Canary.
  11. maxUnavailable beim Rolling Update: Das Feld begrenzt, wie viele Pods gleichzeitig fehlen dürfen. Der Standard ist 1. Das Feature ist beta seit 1.37 und standardmässig an.
  12. PVC-Retention: persistentVolumeClaimRetentionPolicy hat whenDeleted und whenScaled. Die Werte sind Retain oder Delete. Der Standard ist zweimal Retain. Das Feature ist stabil seit Kubernetes 1.32.
  13. volumeClaimTemplates sind unveränderlich: Man kann die Grösse im Template nicht einfach ändern. Man vergrössert jedes PVC einzeln. Dann löscht man das StatefulSet mit --cascade=orphan und legt es mit neuem Template neu an.
  14. Snapshots: VolumeSnapshot und VolumeSnapshotClass erzeugen CSI-Snapshots. Ein neues PVC kann aus einem Snapshot starten (dataSource). Ein Snapshot ist nicht automatisch ein konsistentes DB-Backup.
  15. Ephemeral Storage: emptyDir lebt so lange wie der Pod. Generic Ephemeral Volumes erzeugen ein PVC pro Pod. Es wird mit dem Pod gelöscht.

4. Fallen

  • „ReadWriteOnce heisst: nur ein Pod.“ → Falsch. Ein Node. Für genau einen Pod gibt es ReadWriteOncePod.
  • „Ein StatefulSet repliziert meine Datenbank.“ → Falsch. Es gibt nur feste Identität und Volumes. Replikation macht die DB oder ein Operator.
  • „Beim Löschen eines StatefulSets sind die Daten weg.“ → Standardmässig falsch. PVCs bleiben, ausser die Retention Policy sagt Delete.
  • „Ein PVC kann man verkleinern.“ → Falsch. Nur vergrössern, und nur mit allowVolumeExpansion.
  • „Retain schützt vor Datenverlust.“ → Nur teilweise. Es schützt vor versehentlichem Löschen, nicht vor Korruption oder Zonen-Ausfall. Backups bleiben Pflicht.

5. Selbsttest

Warum?

Warum WaitForFirstConsumer?

Die Disk entsteht erst, wenn der Scheduler einen Node gewählt hat. So liegen Disk und Pod in derselben Zone.

Warum nicht ein Deployment für eine Datenbank?

Alle Replikas würden ein PVC teilen und haben zufällige Namen. Rolling Updates mit RWO-Disk führen zu Multi-Attach-Fehlern.

Warum bleibt ein PVC beim Herunterskalieren bestehen?

Das schützt Daten. Ein späteres Hochskalieren findet das Volume wieder. Es kostet aber Speicher.

Warum hat das StatefulSet einen Headless Service?

Er gibt jedem Pod einen festen DNS-Namen wie pg-0.pg.ns.svc.cluster.local.

Wie innen?

Was ist ein PersistentVolume?

Ein Cluster-Objekt für echten Speicher, der länger lebt als ein Pod. Es ist nicht an einen Namespace gebunden.

Was ist ein PersistentVolumeClaim?

Die Bestellung von Speicher im Namespace: Grösse, Access Mode, StorageClass. Kubernetes bindet sie an genau ein passendes PV.

Was macht eine StorageClass?

Sie beschreibt, wie PVs dynamisch erzeugt werden: Provisioner, Parameter, Reclaim Policy, Binding Mode, Expansion.

Was ist dynamisches Provisioning?

Ein PVC mit StorageClass löst automatisch das Anlegen einer Disk und eines PV aus. Kein Admin muss PVs vorher erzeugen.

Was garantiert ein StatefulSet?

Feste Pod-Namen mit Ordinalzahl, feste DNS-Namen über einen Headless Service, ein eigenes PVC pro Pod und geordnete Starts und Updates.

Was ist ein Headless Service?

Ein Service mit clusterIP: None. DNS liefert die Pod-IPs direkt und für StatefulSets einen Namen pro Pod.

Was sind volumeClaimTemplates?

Vorlagen im StatefulSet, aus denen pro Pod ein PVC entsteht, z. B. data-pg-0. Das PVC bleibt beim Neustart des Pods dasselbe.

Wie macht man ein Canary-Update bei einem StatefulSet?

Mit rollingUpdate.partition. Nur Pods mit Ordinalzahl ab der Partition bekommen die neue Version.

OrderedReady vs Parallel?

OrderedReady startet Pods nacheinander und wartet auf Ready. Parallel startet alle gleichzeitig, z. B. für Systeme, die keine Reihenfolge brauchen.

Zahlen

Welche Access Modes gibt es?

RWO (ein Node), ROX (viele lesen), RWX (viele Nodes schreiben), RWOP (genau ein Pod).

Was ist der Unterschied zwischen RWO und RWOP?

RWO erlaubt mehrere Pods auf demselben Node. RWOP erlaubt clusterweit nur einen Pod.

Was passiert mit den PVCs beim Herunterskalieren?

Standardmässig bleiben sie. Mit persistentVolumeClaimRetentionPolicy whenScaled: Delete werden sie gelöscht.

Seit wann ist die PVC-Retention stabil und welche Standardwerte gelten?

Stabil seit Kubernetes 1.32. whenDeleted und whenScaled sind beide Retain.

Welchen Standard hat maxUnavailable beim StatefulSet?

1. Das Feature ist beta seit 1.37.

Vergleich

Was bedeutet Reclaim Policy Delete vs Retain?

Delete löscht die Disk, wenn das PVC gelöscht wird. Retain behält sie; das PV wird Released und muss von Hand bereinigt werden.

Azure Disk oder Azure Files?

Disk für Datenbanken: Block, schnell, RWO, zonal. Files für geteilte Dateien: RWX, aber höhere Latenz.

Sind Volume Snapshots ein Backup?

Nicht allein. Sie sind nicht immer app-konsistent und liegen oft im gleichen Konto. Ein Backup braucht Konsistenz, Kopie ausserhalb und getesteten Restore.

Datenbank auf Kubernetes oder managed?

Managed, wenn kein Team für DB-Betrieb da ist. Auf Kubernetes mit Operator, wenn Portabilität, Kosten oder Datenhoheit wichtiger sind und Backups geübt werden.

Deployment + PVC oder StatefulSet?

Beim Deployment teilen alle Replikas ein PVC. Mit RWO geht nur 1 Replika sinnvoll. Ein StatefulSet gibt jedem Pod ein eigenes Volume.

Operator oder nacktes StatefulSet?

Ein Operator wie CloudNativePG kennt Failover, Backup und Upgrades. Für Datenbanken ist er fast immer besser.

Produktion

Szenario: Ein StatefulSet-Pod bleibt nach einem Node-Ausfall Pending mit „volume node affinity conflict“. Was tun Sie?

Die Disk ist zonal und in ihrer Zone ist kein Node frei. Kapazität in dieser Zone schaffen (Autoscaler, Node-Pool pro Zone) oder auf zonenredundanten Speicher umstellen.

Szenario: Nach einem Deployment hängt der neue Pod mit „Multi-Attach error“. Warum?

Ein Deployment mit RWO-Disk startet den neuen Pod, während der alte die Disk noch hält. Lösung: strategy Recreate oder ein StatefulSet.

Szenario: Nach helm uninstall sind die Daten einer Testumgebung weg, aber das Team wollte sie behalten. Was ändern Sie?

Helm hat die PVCs aus dem Chart gelöscht, und Reclaim Policy Delete hat die Disks mitgelöscht. Für wichtige Daten eine StorageClass mit Retain, PVCs mit helm.sh/resource-policy: keep schützen und echte Backups einführen.

Kann man ein PVC vergrössern?

Ja, wenn die StorageClass allowVolumeExpansion hat: requests.storage erhöhen. Verkleinern geht nicht.

Design

Wie ändert man die Grösse in volumeClaimTemplates?

Das Feld ist unveränderlich. PVCs einzeln vergrössern, StatefulSet mit --cascade=orphan löschen und mit neuem Template anlegen.

Wie verteilen Sie ein StatefulSet auf Zonen?

Replikas über Zonen verteilen und auf App-Ebene replizieren. Zonale Disks binden den Pod an eine Zone.

Szenario: Welche Reclaim Policy wählen Sie für Produktion?

Retain für Produktionsdaten, Delete für Wegwerf-Umgebungen. Dazu echte Backups.

Szenario: Die Disk einer Datenbank läuft voll. Was tun Sie?

Volume Expansion nutzen, falls erlaubt. Dazu Monitoring auf kubelet_volume_stats_available_bytes und einen Alarm bei 80 %.

Mehr

Gerüst

  • Warum? Daten müssen einen Pod überleben. Der Pod kennt nur den PVC-Namen, nicht die Disk.
  • Wie innen? PVC, StorageClass, CSI-Treiber, PV. Mit WaitForFirstConsumer wählt zuerst der Scheduler den Node, dann entsteht die Disk in dessen Zone.
  • Zahlen RWO = ein Node, RWOP = ein Pod. PVC data-pg-0 pro Ordinal. PVC-Retention seit 1.32 stable, Standard zweimal Retain.
  • Vergleich Deployment + PVC teilt ein Volume. StatefulSet gibt eigene Volumes. Operator oder Managed DB für Datenbanken. Azure Disk ist Block, Files ist RWX.
  • Produktion volume node affinity conflict, Multi-Attach beim Rollout, Daten weg nach helm uninstall, Disk voll.
  • Design Ein StatefulSet repliziert nicht. Zonen bestimmen das Design. Snapshots sind keine Backups.

Beispiel: StatefulSet mit volumeClaimTemplates

apiVersion: v1
kind: Service
metadata: { name: pg, namespace: demo-storage }
spec: { clusterIP: None, selector: { app: pg }, ports: [{ port: 5432 }] }   # headless
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: pg, namespace: demo-storage }
spec:
  serviceName: pg
  replicas: 2
  selector: { matchLabels: { app: pg } }
  template:
    metadata: { labels: { app: pg } }
    spec:
      containers:
      - name: pg
        image: postgres:17
        env: [{ name: POSTGRES_PASSWORD, value: demo }, { name: PGDATA, value: /data/pgdata }]
        volumeMounts: [{ name: data, mountPath: /data }]
  volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: local-path
      resources: { requests: { storage: 1Gi } }

$ kubectl -n demo-storage get pods,pvc
$ kubectl -n demo-storage delete pod pg-0 && kubectl -n demo-storage get pvc
$ kubectl -n demo-storage scale sts pg --replicas=1 && kubectl -n demo-storage get pvc

# nach delete pod pg-0: neuer pg-0, gleiches PVC data-pg-0

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Der lokale k3s-Cluster war nicht erreichbar. local-path ist die Standard-StorageClass von k3s.

  1. pg-1 startet 15 Sekunden nach pg-0: Standard ist podManagementPolicy: OrderedReady.
  2. Jeder Pod hat sein eigenes PVC. Das ist der Unterschied zu einem Deployment, wo alle Pods dasselbe PVC teilen würden.
  3. Nach dem Löschen von pg-0 kommt ein Pod mit gleichem Namen und gleichem Volume.
  4. Beim Herunterskalieren bleibt data-pg-1 standardmässig bestehen. Das schützt Daten, kostet aber Speicher.
  5. DNS: pg-0.pg.demo-storage.svc.cluster.local zeigt immer auf pg-0. Aufräumen: kubectl delete namespace demo-storage (PVCs gehen mit, PVs mit Reclaim Policy Delete ebenso).

Vergleich

  • Deployment + PVC: alle Replikas teilen ein PVC. Mit RWO geht nur 1 Replika sinnvoll. Gut für einen einzelnen Service mit Datei-Cache.
  • StatefulSet: feste Namen, feste DNS, eigenes Volume pro Pod, geordnete Starts. Für Datenbanken, Kafka, ZooKeeper, MinIO verteilt.
  • Operator (z. B. CloudNativePG, Strimzi): nutzt intern StatefulSets oder eigene Pods. Er kennt die Software: Failover, Backup, Upgrades. Für Datenbanken auf K8s fast immer besser als ein nacktes StatefulSet.
  • Managed DB (Azure Database for PostgreSQL): kein Betrieb im Cluster, Backups und HA vom Provider. Teurer pro Leistung, weniger Kontrolle.
  • Azure Disk vs Azure Files: Disk ist Block, RWO, zonal, niedrige Latenz. Files ist SMB/NFS, RWX, langsamer, gut für geteilte Dateien.
  • Local PV / local-path: sehr schnell, aber an einen Node gebunden. Stirbt der Node, sind die Daten weg, ausser die App repliziert selbst.

In der Produktion

  1. Pod hängt in Pending mit „volume node affinity conflict“: Die Disk liegt in Zone 1, in Zone 1 ist kein Node frei. Lösung: WaitForFirstConsumer, Nodes in jeder Zone, oder ZRS-Disks (zonenredundant), wo unterstützt.
  2. Multi-Attach-Fehler beim Rollout: Ein Deployment mit RWO-Disk und RollingUpdate will den neuen Pod auf einem anderen Node starten. Die Disk hängt noch am alten. Lösung: strategy: Recreate oder StatefulSet.
  3. Daten weg nach helm uninstall: Helm löscht ein PVC aus seinem Chart, und Reclaim Policy Delete löscht die Disk mit. (PVCs aus volumeClaimTemplates löscht Helm nicht.) Lösung: für wichtige Daten eine StorageClass mit Retain, plus echte Backups.
  4. Disk voll: Die DB stoppt. Lösung: Monitoring auf kubelet_volume_stats_available_bytes, Volume Expansion erlauben, Alarm bei 80 %.
  5. Zustand im falschen Ort: Eine Komponente speichert in einer eingebetteten DB auf einem Volume ohne Backup. Ein Reschedule oder ein neues Volume löscht den Zustand. Lösung: Zustand in eine echte, gesicherte Datenbank auslagern.
  6. Langsame Pod-Starts: Attach und Detach von Cloud-Disks dauern Sekunden bis Minuten, besonders nach einem Node-Ausfall. Das verlängert Failover.

Diagnose: Werkzeuge und Befehle

  • kubectl get pvc -A und kubectl get pv: Status Pending, Bound, Released, Failed.
  • kubectl describe pvc <name>: Events wie waiting for first consumer oder Provisioning-Fehler.
  • kubectl describe pod <name>: FailedAttachVolume, Multi-Attach error, FailedMount.
  • kubectl get volumeattachment: welche Disk an welchem Node hängt.
  • kubectl get storageclass: Default-Klasse, Provisioner, Reclaim Policy, Binding Mode.
  • kubectl get pv <name> -o jsonpath='{.spec.nodeAffinity}': in welcher Zone das Volume liegt.
  • Prometheus: kubelet_volume_stats_used_bytes / capacity_bytes für Füllstand.

Senior-Punkte

  1. Datenbanken auf Kubernetes sind möglich, aber kein Selbstläufer. Man braucht einen Operator, getestete Backups, Monitoring und Leute mit DB-Wissen. Ohne das ist eine Managed DB billiger.
  2. Ein StatefulSet macht keine Replikation. Es gibt nur Identität und Volumes. Replikation, Failover und Quorum muss die Software selbst oder ein Operator liefern.
  3. Zonen bestimmen das Design. Zonale Disks binden Pods an eine Zone. HA heisst: Replikas über Zonen verteilen und auf App-Ebene replizieren.
  4. Reclaim Policy ist eine Geschäftsentscheidung. Retain für Produktionsdaten, Delete für Wegwerf-Umgebungen.
  5. Snapshots sind keine Backups. Ein Backup muss konsistent, ausserhalb des Clusters und mit Restore getestet sein.
  6. Der kostbarste Zustand zuerst. Kataloge, Metadaten und Konfiguration gehören in gesicherte Datenbanken, nicht in eingebettete Stores auf einem einzelnen Volume.
