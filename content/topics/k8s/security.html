Pod Security und Admission Controller (Kyverno)

Kubernetes · Tier 2 · Quellen: kubernetes.io Docs „Pod Security Standards“, „Pod Security Admission“, „Admission Control in Kubernetes“, „Dynamic Admission Control“, „Validating Admission Policy“, „Mutating Admission Policy“, Feature-Gate-Referenz (Stand Kubernetes 1.37); kyverno.io Docs (Policy Types, Migrating to CEL Policies), Kyverno Release v1.20.0

Kern: Ein Admission Controller ist ein Prüfschritt im API-Server, der eine Anfrage nach der Anmeldung und RBAC ändern (mutating) oder ablehnen (validating) kann, bevor sie in etcd landet. Pod Security Admission ist der eingebaute Controller, der Pods gegen drei Stufen prüft: privileged, baseline, restricted. Kyverno ist eine Policy-Engine für eigene Regeln, z. B. „nur Images aus unserer Registry“.

1. Wo sitzt Admission?

  1. Authentifizierung: Wer schickt die Anfrage? Beispiel: der ServiceAccount von Argo CD.
  2. Autorisierung (RBAC): Darf er Pods in diesem Namespace anlegen? RBAC prüft nur Verben und Ressourcen, nicht den Inhalt.
  3. Mutating Admission: ändert das Objekt, z. B. Default-Labels oder Sidecar einfügen. Läuft immer zuerst.
  4. Schema-Prüfung: Ist das Objekt nach dem Ändern noch gültig?
  5. Validating Admission: prüft den Inhalt und lehnt ab. Hier sitzen Pod Security Admission, ValidatingAdmissionPolicy und Webhooks wie Kyverno.
  6. Kyverno: läuft als Pods im Cluster. Der API-Server ruft es per Webhook auf, für mutating und validating.

2. Die Reise eines unsicheren Pods (die Geschichte zum Merken)

  1. Deployment: Ein Team deployt web ohne securityContext in einen Namespace mit enforce=restricted.
  2. Warnung: PSA prüft das Pod-Template im Deployment nur mit warn und audit. kubectl zeigt eine Warnung, das Deployment wird trotzdem angelegt.
  3. ReplicaSet: Der Controller will den Pod anlegen. Jetzt prüft PSA den echten Pod mit enforce.
  4. Abgelehnt: Der Pod verletzt restricted. Der API-Server lehnt ihn ab.
  5. Stille Störung: Der Fehler steht nur als Event FailedCreate am ReplicaSet. Das Deployment zeigt 0/1.
  6. Lösung: Das Team setzt runAsNonRoot, allowPrivilegeEscalation: false, capabilities.drop: [ALL] und seccompProfile: RuntimeDefault.

3. Beispiel: Pod Security und eine CEL-Policy im echten Cluster

$ kubectl create ns demo-security
$ kubectl label ns demo-security pod-security.kubernetes.io/enforce=restricted pod-security.kubernetes.io/warn=restricted

--- 1) privilegierter Pod
$ kubectl -n demo-security run priv --image=busybox:1.36 --privileged -- sleep 3600
Error from server (Forbidden): pods "priv" is forbidden: violates PodSecurity "restricted:latest":
  privileged (container "priv" must not set securityContext.privileged=true),
  allowPrivilegeEscalation != false (container "priv" must set securityContext.allowPrivilegeEscalation=false),
  unrestricted capabilities (container "priv" must set securityContext.capabilities.drop=["ALL"]),
  runAsNonRoot != true (pod or container "priv" must set securityContext.runAsNonRoot=true),
  seccompProfile (pod or container "priv" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")

--- 3) gehärteter Pod (runAsNonRoot, runAsUser 1000, seccomp RuntimeDefault, drop ALL, no escalation)
$ kubectl -n demo-security apply -f ok.yaml
pod/hardened created

--- 4) Deployment ohne securityContext
$ kubectl -n demo-security create deployment web --image=busybox:1.36 -- sleep 3600
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (...), ...
deployment.apps/web created
$ kubectl -n demo-security get deploy web
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    0/1     0            0           7s
$ kubectl -n demo-security events --types=Warning
Warning   FailedCreate   ReplicaSet/web-5d84849455   Error creating: pods "web-5d84849455-gh59x" is forbidden: violates PodSecurity "restricted:latest": ...

--- 5) ValidatingAdmissionPolicy (CEL): Label team ist Pflicht
validations:
- expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
  message: "Jedes Deployment braucht das Label team."
$ kubectl -n demo-security create deployment api --image=busybox:1.36 -- sleep 3600
Warning: would violate PodSecurity "restricted:latest": ...
error: failed to create deployment: deployments.apps "api" is forbidden: ValidatingAdmissionPolicy
  'demo-security-require-team' with binding 'demo-security-require-team' denied request: Jedes Deployment braucht das Label team.

Echte Ausgabe, k3s v1.36 (v1.36.4+k3s1). Lange Zeilen umbrochen und gekürzt. Namespace, Policy und Binding wurden danach gelöscht. Kyverno ist in diesem Cluster nicht installiert.

  1. PSA nennt jede verletzte Regel mit dem Feld, das fehlt. Das ist die Checkliste für restricted.
  2. restricted:latest heisst: Stufe restricted in der Version des Clusters. Mit enforce-version kann man eine Version festnageln.
  3. Der gehärtete Pod kommt durch. Vier Felder genügen für ein normales Image.
  4. Das Deployment wird nur gewarnt, die Pods werden abgelehnt. Der Fehler steht als Event am ReplicaSet.
  5. Die ValidatingAdmissionPolicy läuft im API-Server, ohne Webhook-Pod. Die Bindung begrenzt sie hier per namespaceSelector auf einen Namespace.

4. Details, die Interviewer fragen

  1. Pod Security Standards: privileged (keine Grenzen), baseline (verhindert bekannte Ausbrüche: kein privileged, keine Host-Namespaces, kein hostPath, keine gefährlichen Capabilities), restricted (Härtung: nonRoot, drop ALL, seccomp, keine Privilege Escalation, nur bestimmte Volume-Typen).
  2. PSA-Modi: enforce (ablehnen), audit (Eintrag im Audit-Log), warn (Warnung an den Client). Pro Namespace kombinierbar, z. B. enforce baseline und warn restricted.
  3. Labels: pod-security.kubernetes.io/<MODE>: <LEVEL> und optional <MODE>-version. Stabil seit 1.25, Nachfolger der entfernten PodSecurityPolicy.
  4. Exemptions: Ausnahmen nach Benutzer, RuntimeClass oder Namespace, nur in der Admission-Konfiguration. Controller-ServiceAccounts nicht ausnehmen, sonst ist jeder Deployment-Ersteller ausgenommen.
  5. Reihenfolge: Erst alle mutating, dann alle validating. Ein Webhook darf nach einer Mutation erneut laufen (reinvocationPolicy: IfNeeded, Standard Never).
  6. Webhook-Einstellungen: failurePolicy Standard Fail (fail-closed). timeoutSeconds Standard 10, erlaubt 1–30. sideEffects für Dry-Run. Bis zu 64 matchConditions in CEL, um Aufrufe zu sparen.
  7. ValidatingAdmissionPolicy (stabil seit 1.30): Regeln in CEL direkt im API-Server. validationActions: Deny, Warn, Audit. Parameter über paramKind. Kein Webhook, also keine Latenz und kein Ausfallrisiko.
  8. MutatingAdmissionPolicy (stabil seit 1.36): Mutation in CEL, als ApplyConfiguration oder JSONPatch. Ersetzt einfache Mutating Webhooks.
  9. Kyverno: Policy-Engine als Webhook. Kann validieren, mutieren, Ressourcen erzeugen, löschen und Image-Signaturen prüfen. Ergebnisse auch als PolicyReports für bestehende Ressourcen.
  10. Kyverno im Umbruch: Neue CEL-basierte Typen in policies.kyverno.io/v1: ValidatingPolicy, MutatingPolicy, GeneratingPolicy, DeletingPolicy, ImageValidatingPolicy. Laut Migrationsleitfaden ist ClusterPolicy seit v1.19 deprecated und soll in v1.20 entfernt werden. v1.20.0 ist seit 12.11.2026 aktuell.
  11. Pod-Controller-Regeln: Kyverno erzeugt aus einer Pod-Regel automatisch Regeln für Deployments, Jobs usw. So kommt der Fehler schon beim Deployment, nicht erst beim Pod.
  12. securityContext-Basis: runAsNonRoot, runAsUser, allowPrivilegeEscalation: false, capabilities.drop: [ALL], readOnlyRootFilesystem, seccompProfile: RuntimeDefault.

5. Vergleich

  • Pod Security Admission: eingebaut, drei feste Stufen, nur Pods, keine eigenen Regeln. Gute Basis für jeden Namespace.
  • ValidatingAdmissionPolicy (CEL): eingebaut, eigene Regeln, schnell, kein Webhook. Keine externen Daten, kein Image-Verify.
  • Kyverno: YAML/CEL-Policies, Mutation, Generierung, Image-Signaturen, Reports. Läuft als Webhook, also Betrieb und Ausfallrisiko.
  • OPA Gatekeeper: Policies in Rego. Mächtig, aber eigene Sprache.
  • RBAC: wer darf welche Aktion. Admission: was darf im Objekt stehen.
  • NetworkPolicy: wer darf mit wem reden. Pod Security: was darf der Container auf dem Node.

6. In der Produktion

  1. Cluster blockiert: niemand kann Pods anlegen: Ein Webhook mit failurePolicy: Fail ist down, z. B. Kyverno-Pods. Lösung: Kyverno hochverfügbar, kube-system und Kyverno selbst aus den Webhook-Regeln ausnehmen, Notfall-Runbook.
  2. Deployment grün, aber 0 Pods: Pods werden von PSA oder einer Policy abgelehnt. Lösung: Events am ReplicaSet lesen, Policies schon für Pod-Controller prüfen.
  3. Einführung bricht alte Workloads: Direkt enforce=restricted. Lösung: erst warn und audit, PolicyReports auswerten, dann Namespace für Namespace auf enforce.
  4. Langsame Deployments: Viele Webhooks mit hohem Timeout. Lösung: matchConditions, CEL-Policies im API-Server, Timeouts kurz.
  5. Kyverno-Upgrade auf 1.20: Alte ClusterPolicy-Objekte verlieren ihre Wirkung. Lösung: vorher auf die CEL-Typen migrieren und in Staging testen.
  6. Images aus fremden Registries: Ohne Regel kann jeder Docker-Hub-Images starten. Lösung: Policy „nur unsere Registry“, besser zusätzlich Signaturprüfung.

7. Diagnose: Werkzeuge und Befehle

  • kubectl label --dry-run=server --overwrite ns X pod-security.kubernetes.io/enforce=restricted: zeigt, welche laufenden Pods die Stufe verletzen würden.
  • kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations: welche Webhooks im Spiel sind.
  • kubectl get validatingadmissionpolicies,validatingadmissionpolicybindings.
  • kubectl events --types=Warning: FailedCreate mit dem Ablehnungsgrund.
  • kubectl get policyreports -A: Kyverno-Ergebnisse für bestehende Ressourcen.
  • kyverno apply und kyverno test (CLI): Policies in der CI gegen Manifeste testen.
  • API-Server-Metriken: pod_security_evaluations_total, Webhook-Latenz (apiserver_admission_webhook_admission_duration_seconds).

8. Senior-Punkte

  1. Schichten statt einem Werkzeug: PSA als Basis, CEL-Policies für einfache Regeln, Kyverno für Mutation, Generierung und Images.
  2. Einführen in Stufen: audit → warn → enforce. Mit Reports messen, wie viele Workloads betroffen sind.
  3. Webhooks sind Teil der Control Plane. Fallen sie aus, steht der Cluster. Hochverfügbarkeit, Ausnahmen und Monitoring sind Pflicht.
  4. Policies gehören ins Git und durch die CI, wie Code. Bei GitOps greifen sie, sobald Argo CD synchronisiert; ein abgelehnter Sync zeigt den Policy-Grund.
  5. Fehler früh zeigen: Regeln auf Deployment-Ebene, nicht nur auf Pods. Sonst sieht das Team nur „0/1“.
  6. Kyverno-Migration jetzt planen: Die neuen CEL-Typen sind die Zukunft. Alte ClusterPolicies sind technische Schuld.

10. Fallen

  • „RBAC verhindert privilegierte Pods.“ → Falsch. RBAC prüft nur, ob man Pods anlegen darf, nicht deren Inhalt.
  • „PSA lehnt ein falsches Deployment ab.“ → Falsch. Nur Warnung. Abgelehnt werden die Pods.
  • „PodSecurityPolicy ist der Standard.“ → Falsch. PSP ist entfernt. Nachfolger ist Pod Security Admission.
  • „Validating Webhooks laufen vor Mutating.“ → Falsch. Erst mutating, dann validating.
  • „failurePolicy Ignore ist sicherer.“ → Falsch. Dann wird bei Ausfall alles durchgelassen. Sicher ist Fail, aber mit Hochverfügbarkeit.
  • „Für jede Regel braucht man Kyverno.“ → Falsch. Einfache Regeln gehen mit ValidatingAdmissionPolicy im API-Server.

11. Fragen

Was ist ein Admission Controller?

Ein Schritt im API-Server nach AuthN und AuthZ. Er kann Objekte ändern (mutating) oder ablehnen (validating), bevor sie gespeichert werden.

In welcher Reihenfolge laufen Admission-Schritte?

Mutating, dann Schema-Prüfung, dann Validating. Erst danach schreibt der API-Server nach etcd.

Was sind die Pod Security Standards?

Drei Stufen: privileged (offen), baseline (gegen bekannte Ausbrüche), restricted (gehärtet nach Best Practices).

Wie aktiviert man Pod Security Admission?

Mit Namespace-Labels pod-security.kubernetes.io/<mode>: <level>. Modi: enforce, audit, warn.

Was verlangt restricted mindestens?

runAsNonRoot, allowPrivilegeEscalation false, capabilities drop ALL, seccompProfile RuntimeDefault oder Localhost, plus alles aus baseline.

Gilt enforce auch für Deployments?

Nein. enforce gilt für Pods. audit und warn prüfen auch Pod-Templates in Workloads.

Was ersetzt PodSecurityPolicy?

Pod Security Admission, stabil seit 1.25. Für eigene Regeln zusätzlich CEL-Policies oder Kyverno.

Was ist ein Admission Webhook?

Ein externer HTTPS-Dienst, den der API-Server bei passenden Anfragen aufruft. Mutating oder validating.

Was bedeutet failurePolicy?

Was passiert, wenn der Webhook nicht antwortet. Fail (Standard) lehnt ab, Ignore lässt durch.

Welches Timeout haben Webhooks?

Standard 10 Sekunden, erlaubt 1 bis 30.

Was ist eine ValidatingAdmissionPolicy?

Eine Regel in CEL, die der API-Server selbst prüft, ohne Webhook. Stabil seit 1.30, mit Binding und Aktionen Deny, Warn, Audit.

Was ist eine MutatingAdmissionPolicy?

Mutation in CEL im API-Server, als ApplyConfiguration oder JSONPatch. Stabil seit 1.36.

Was kann Kyverno, was VAP nicht kann?

Ressourcen erzeugen und löschen, Image-Signaturen prüfen, Reports über bestehende Ressourcen, externe Daten einbeziehen.

Was ändert sich bei Kyverno gerade?

Neue CEL-basierte Policy-Typen wie ValidatingPolicy und ImageValidatingPolicy. ClusterPolicy ist laut Migrationsleitfaden seit 1.19 deprecated und soll in 1.20 entfernt werden.

Was sind PolicyReports?

Ressourcen, in denen Kyverno Ergebnisse für bestehende Objekte festhält. Gut für die audit-Phase.

Kyverno oder OPA Gatekeeper?

Kyverno: Policies in YAML und CEL, nah an Kubernetes. Gatekeeper: Rego, mächtig, eigene Sprache.

Wie führen Sie restricted ohne Ausfall ein?

Erst warn und audit, Dry-Run mit kubectl label --dry-run=server, Workloads anpassen, dann enforce pro Namespace.

RBAC vs Admission?

RBAC: darf ich Pods anlegen? Admission: darf dieser Pod so aussehen?

Was ist readOnlyRootFilesystem?

Das Root-Dateisystem des Containers ist schreibgeschützt. Ein Angreifer kann keine Werkzeuge ablegen. Schreibbare Pfade kommen als emptyDir.

Warum sollten Webhooks kube-system ausnehmen?

Sonst kann ein kaputter Webhook verhindern, dass Systemkomponenten oder er selbst wieder starten.

Szenario: Nach einem Kyverno-Ausfall kann niemand mehr deployen. Was tun Sie?

Kurzfristig: Kyverno-Pods reparieren oder den Webhook gezielt entschärfen. Langfristig: Replikas über Nodes, PDB, Ausnahmen für kube-system, Alarm auf Webhook-Fehler.

Szenario: Ein Deployment zeigt seit einer Stunde 0/3, kubectl apply war erfolgreich. Was prüfen Sie?

Events am ReplicaSet: FailedCreate mit Grund von PSA oder einer Policy. Dann securityContext oder Labels ergänzen.

Szenario: Ein Audit verlangt, dass nur signierte Images aus der eigenen Registry laufen. Wie setzen Sie das um?

Policy auf erlaubte Registry plus Signaturprüfung, z. B. Kyverno ImageValidatingPolicy mit Cosign. Zuerst im Audit-Modus, dann erzwingen.
