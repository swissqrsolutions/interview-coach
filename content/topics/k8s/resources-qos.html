Requests, Limits, QoS-Klassen, OOMKilled

Kubernetes · Tier 1 · Quellen: kubernetes.io (Resource Management for Pods and Containers, Pod Quality of Service Classes, Node-pressure Eviction, Reserve Compute Resources, Resize CPU and Memory Resources assigned to Containers — stabil seit 1.35, LimitRange, ResourceQuota), Linux-Kernel-Doku cgroup v2 (cpu.max, memory.max), OpenJDK (UseContainerSupport, MaxRAMPercentage, JDK-8281181)

Kern: Ein Request ist die Menge CPU und Speicher, die Kubernetes einem Container beim Planen fest reserviert. Ein Limit ist die Obergrenze, die der Linux-Kernel zur Laufzeit durchsetzt. Über CPU-Limit wird ein Container gedrosselt (Throttling), über Memory-Limit wird er getötet (OOMKilled). Aus Requests und Limits folgt die QoS-Klasse, die bestimmt, wer bei Speichermangel zuerst gehen muss.

1. Wo wirken Requests und Limits?

  1. Pod-Spec: Jeder Container nennt resources.requests und resources.limits, z. B. cpu: 500m (eine halbe CPU) und memory: 1Gi.
  2. Scheduler: summiert die Requests aller Pods auf einem Node. Passt der neue Request nicht mehr in Allocatable, kommt der Pod nicht dorthin. Die echte Auslastung zählt nicht.
  3. Allocatable: Node-Kapazität minus kube-reserved, system-reserved und Eviction-Schwelle.
  4. kubelet und Runtime: übersetzen die Werte in cgroups. Der CPU-Request wird ein Gewicht (cpu.weight), das CPU-Limit eine Quote (cpu.max), das Memory-Limit eine harte Grenze (memory.max).
  5. QoS-Klasse: wird aus Requests und Limits berechnet und in status.qosClass gespeichert.

2. Die Reise eines Containers durch Engpässe

  1. Geplant. Ein Spring-Boot-Pod hat requests: cpu 500m, memory 1Gi und limits: cpu 1, memory 1Gi. Der Scheduler findet einen Node mit genug freien Requests.
  2. CPU-Spitze. Ein Request startet 8 parallele Threads. Das CPU-Limit 1 heisst: 100 ms CPU-Zeit pro 100-ms-Periode (CFS-Quota). 8 Threads verbrauchen das in 12,5 ms.
  3. Throttling. Für die restlichen 87,5 ms der Periode darf der Container nicht rechnen. Die Antwortzeit steigt stark, obwohl die durchschnittliche CPU-Last nur 30 % zeigt.
  4. Speicher wächst. Der Heap ist auf 75 % des Limits gesetzt. Dazu kommen Metaspace, Thread-Stacks, Code Cache und Direct Buffers.
  5. Limit erreicht. Der Kernel kann keinen Speicher mehr geben. Der OOM Killer tötet den Prozess mit SIGKILL. Exit-Code 137 = 128 + 9.
  6. Neustart. Der kubelet meldet Last State: Terminated, Reason: OOMKilled und startet den Container neu. Kein Java-Stacktrace, kein OutOfMemoryError im Log.
  7. Node-Druck. Wird der ganze Node knapp, räumt der kubelet Pods (Node-pressure Eviction). Zuerst gehen Pods, die mehr als ihren Request nutzen. Guaranteed-Pods kommen zuletzt dran.

3. Beispiel: OOMKilled und die JVM-Heap-Grösse

apiVersion: v1
kind: Pod
metadata: { name: memory-demo, namespace: demo-resources }
spec:
  containers:
  - name: stress
    image: polinux/stress
    command: ["stress"]
    args: ["--vm", "1", "--vm-bytes", "250M", "--vm-hang", "1"]
    resources:
      requests: { memory: "50Mi" }
      limits:   { memory: "100Mi" }

$ kubectl -n demo-resources get pod memory-demo -o jsonpath='{.status.qosClass}'
$ kubectl -n demo-resources describe pod memory-demo | grep -A4 "Last State"
Burstable
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      ...
      Finished:     ...

   double MaxRAMPercentage     = 75.000000      {product} {command line}

Echte Ausgabe, Oracle JDK 17.0.3 auf einem Windows-Host mit ca. 16 GB RAM (nicht im Container). Spalten gekürzt.

  1. Der Container will 250 MB, das Limit ist 100 Mi. Der Kernel tötet ihn: OOMKilled, Exit-Code 137.
  2. Request (50Mi) ist kleiner als Limit (100Mi): QoS-Klasse Burstable.
  3. Die JVM nimmt standardmässig nur 25 % des Speichers als Heap: hier 3,8 GiB von 16 GB. In einem Container mit 1 GiB Limit wären es nur 256 MiB.
  4. Mit -XX:MaxRAMPercentage=75 steigt der Heap auf 75 %. Im Container zählt das Memory-Limit als „RAM“, weil UseContainerSupport (Linux) standardmässig an ist.
  5. Aufräumen: kubectl delete namespace demo-resources.

4. Details, die Interviewer fragen

  1. Einheiten: CPU in Cores oder Millicores (250m = 0,25 Core). Memory in Bytes mit Suffix: Mi/Gi sind Zweierpotenzen, M/G Zehnerpotenzen. 100m Memory heisst 0,1 Byte, ein häufiger Tippfehler.
  2. Fehlender Request: Ist nur ein Limit gesetzt, setzt Kubernetes den Request gleich dem Limit. Ohne beides gilt der Container als BestEffort, ausser eine LimitRange setzt Standardwerte.
  3. CFS-Quota: Das CPU-Limit wird pro Periode von 100 ms durchgesetzt. Limit 500m heisst 50 ms Rechenzeit pro 100 ms, über alle Threads zusammen. In cgroup v2: cpu.max = 50000 100000.
  4. CPU-Request im Betrieb: Er wirkt als relatives Gewicht bei Konkurrenz. Ist der Node nicht voll, darf ein Pod ohne Limit mehr CPU nutzen als sein Request.
  5. Memory ist nicht komprimierbar. Speicher kann man nicht drosseln, nur wegnehmen. Darum führt Überschreiten zum Kill, nicht zum Warten.
  6. QoS Guaranteed: Jeder Container hat CPU- und Memory-Request gleich Limit. Höchster Schutz bei Eviction, oom_score_adj = -997. Nötig für exklusive CPUs mit dem CPU Manager (Policy static, ganzzahlige CPU).
  7. QoS Burstable: Mindestens ein Container hat einen Request oder ein Limit, aber nicht alles ist gleich. Der OOM-Score hängt vom Memory-Request im Verhältnis zur Node-Grösse ab.
  8. QoS BestEffort: Kein Container hat Requests oder Limits. Wird bei Speicherdruck zuerst geräumt, oom_score_adj = 1000.
  9. OOMKilled vs Eviction: OOMKilled kommt vom Kernel, wenn ein Container sein eigenes Limit sprengt; der Container startet neu. Eviction kommt vom kubelet, wenn der Node knapp wird; der Pod wird beendet und neu geplant (Status Evicted).
  10. JVM im Container: UseContainerSupport liest Limits aus den cgroups. MaxRAMPercentage (Standard 25) bestimmt den Heap. Üblich sind 60–75 %, weil Non-Heap (Metaspace, Threads, Code Cache, Direct Memory) Platz braucht.
  11. CPU-Anzahl der JVM: Aktuelle JDKs leiten availableProcessors() nur aus dem CPU-Limit ab, nicht aus dem Request (JDK-8281181). Ohne Limit sieht die JVM alle Cores des Nodes und baut zu grosse Thread-Pools. Lösung: -XX:ActiveProcessorCount.
  12. In-place Resize: Seit Kubernetes 1.35 stabil. CPU und Memory ändert man über die resize-Subresource ohne neuen Pod. resizePolicy pro Ressource: NotRequired (ohne Neustart) oder RestartContainer. Die QoS-Klasse darf sich dabei nicht ändern.
  13. Resize-Status: Pod-Conditions PodResizePending (Grund Infeasible oder Deferred) und PodResizeInProgress. Memory verkleinern ist „best effort“: Liegt die Nutzung über dem neuen Limit, wartet der Resize.
  14. LimitRange und ResourceQuota: LimitRange setzt Standard- und Maximalwerte pro Container im Namespace. ResourceQuota begrenzt die Summe aller Requests und Limits im Namespace.

5. Vergleich

  • Guaranteed: Request = Limit für CPU und Memory. Vorhersehbar, am besten geschützt, aber keine Bursts. Für Datenbanken und latenzkritische Dienste.
  • Burstable: Request < Limit oder nur teilweise gesetzt. Gute Auslastung, Bursts möglich, mittlerer Schutz. Der Normalfall für Services.
  • BestEffort: nichts gesetzt. Nutzt freie Reste, wird zuerst geopfert. Nur für unwichtige Batch-Arbeit.
  • CPU-Limit vs kein CPU-Limit: Mit Limit: Schutz vor lauten Nachbarn, aber Throttling. Ohne Limit: keine Drosselung, Request garantiert den fairen Anteil.
  • Memory-Limit = Request vs Limit > Request: Gleich ist sicher bei Eviction. Höher erlaubt Überbuchung, riskiert aber Eviction bei vollem Node.

6. In der Produktion

  1. Hohe Latenz bei niedriger CPU-Auslastung: CPU-Throttling durch ein kleines Limit und viele Threads. Lösung: Limit erhöhen oder entfernen, Request realistisch setzen, Thread-Pools passend zur CPU.
  2. OOMKilled ohne Java-Fehler: Heap plus Non-Heap übersteigt das Limit. Lösung: MaxRAMPercentage auf 70–75 % senken oder Limit erhöhen, Native Memory Tracking prüfen.
  3. JVM nutzt nur einen Viertel des Speichers: Standard 25 %, darum häufige GCs trotz grossem Limit. Lösung: MaxRAMPercentage setzen.
  4. Pods Pending mit „Insufficient cpu“, obwohl die Nodes kaum ausgelastet sind. Die Requests sind zu hoch. Lösung: Requests anhand echter Nutzung senken (VPA-Empfehlung), Nodes ergänzen.
  5. Evictions bei Lastspitzen: Viele Burstable-Pods mit kleinem Memory-Request auf einem Node. Lösung: Memory-Request nahe am echten Bedarf, Memory-Limit gleich Request für wichtige Pods.
  6. Test-Container in der CI OOM-killed: parallele Tests und ein speicherhungriger DB-Container. Lösung: harte Speichergrenze für den Container, Tests serialisieren, schnell scheitern beim Start.

7. Diagnose: Werkzeuge und Befehle

  • kubectl describe pod: Last State: Terminated, Reason: OOMKilled, Exit Code: 137, und QoS-Klasse.
  • kubectl describe node <node>: Abschnitt Allocated resources zeigt Summe der Requests und Limits.
  • kubectl top pod --containers und kubectl top node: echte Nutzung über Metrics Server.
  • kubectl get events -A --field-selector reason=Evicted und reason=OOMKilling (Node-Event).
  • Prometheus: container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total für Throttling-Anteil; container_memory_working_set_bytes gegen das Limit.
  • Im Container: cat /sys/fs/cgroup/cpu.max, cat /sys/fs/cgroup/memory.max, cat /sys/fs/cgroup/cpu.stat (nr_throttled).
  • JVM: java -XshowSettings:system -version (erkannte Container-Grenzen), -XX:NativeMemoryTracking=summary mit jcmd <pid> VM.native_memory.

8. Senior-Punkte

  1. Requests sind die wichtigste Zahl. Sie steuern Scheduling, Kosten, Autoscaling und Eviction-Reihenfolge. Falsche Requests machen alles andere falsch.
  2. Memory: Limit setzen, meist gleich Request. Speicher kann man nicht drosseln. Gleiche Werte machen das Verhalten vorhersehbar.
  3. CPU-Limits sind eine echte Abwägung. Sie schützen vor Nachbarn, kosten aber Latenz durch Throttling. Viele Teams setzen nur CPU-Requests, ausser in Multi-Tenant-Clustern.
  4. Die JVM muss die Grenzen kennen. Heap-Prozent, CPU-Anzahl und Thread-Pools gehören zur Ressourcen-Planung, nicht nur zum Java-Code.
  5. Policy statt Disziplin. LimitRange, ResourceQuota oder Admission-Regeln (z. B. Kyverno) erzwingen Requests und Limits für jeden Pod.
  6. Messen, dann setzen. VPA im Empfehlungsmodus oder Prometheus-Daten liefern echte Werte. Raten führt zu Verschwendung oder Ausfällen.

10. Fallen

  • „Der Scheduler plant nach echter Auslastung.“ → Falsch. Nur nach Requests.
  • „Über dem CPU-Limit wird der Container getötet.“ → Falsch. Er wird gedrosselt. Getötet wird er nur über dem Memory-Limit.
  • „Niedrige durchschnittliche CPU heisst kein Throttling.“ → Falsch. Throttling passiert in 100-ms-Perioden. Kurze Spitzen mit vielen Threads reichen.
  • „Xmx gleich Memory-Limit ist richtig.“ → Falsch. Die JVM braucht Non-Heap-Speicher. Dann kommt OOMKilled.
  • „OOMKilled und Evicted sind dasselbe.“ → Falsch. OOMKilled: Kernel, eigenes Limit, Container-Neustart. Evicted: kubelet, Node-Druck, Pod wird neu geplant.
  • „Mit In-place Resize kann ich einen Pod von Burstable auf Guaranteed ändern.“ → Falsch. Die QoS-Klasse bleibt fest.

11. Fragen

Was ist der Unterschied zwischen Request und Limit?

Der Request ist die reservierte Menge fürs Scheduling. Das Limit ist die harte Obergrenze zur Laufzeit.

Wonach plant der Scheduler?

Nach der Summe der Requests im Vergleich zu Allocatable des Nodes. Echte Auslastung zählt nicht.

Was passiert über dem CPU-Limit?

Der Container wird gedrosselt. Er muss bis zur nächsten 100-ms-Periode warten.

Was passiert über dem Memory-Limit?

Der Kernel tötet den Prozess mit SIGKILL. Status OOMKilled, Exit-Code 137, danach Neustart.

Was ist CFS-Throttling?

Der Completely Fair Scheduler gibt pro 100 ms nur die Quote des Limits. Ist sie verbraucht, steht der Container bis zur nächsten Periode.

Warum hat ein Service mit 30 % CPU trotzdem Throttling?

Der Durchschnitt versteckt Spitzen. Viele Threads verbrauchen die Quote früh in der Periode und warten dann.

Welche QoS-Klassen gibt es?

Guaranteed (Request = Limit für CPU und Memory in jedem Container), Burstable (teilweise gesetzt), BestEffort (nichts gesetzt).

Wer wird bei Speichermangel zuerst geräumt?

Pods, deren Nutzung über dem Request liegt, zuerst BestEffort, dann Burstable. Guaranteed zuletzt. Priority spielt auch mit.

Was ist der Unterschied zwischen OOMKilled und Evicted?

OOMKilled: Kernel, Container über eigenem Limit, Neustart im gleichen Pod. Evicted: kubelet bei Node-Druck, Pod wird beendet und neu erzeugt.

Was bedeutet Exit-Code 137?

128 + 9, also SIGKILL. Meist OOMKilled, manchmal ein harter Kill nach der Grace Period.

Was passiert, wenn ich nur ein Limit setze?

Kubernetes setzt den Request gleich dem Limit.

Sollte man CPU-Limits setzen?

Es kommt darauf an. Ohne Limit kein Throttling, der Request garantiert den fairen Anteil. Mit Limit Schutz vor Nachbarn, aber Latenzrisiko.

Wie viel Heap bekommt die JVM im Container standardmässig?

25 % des Memory-Limits (MaxRAMPercentage = 25). Üblich ist, ihn auf 60–75 % zu setzen.

Warum nicht MaxRAMPercentage=100?

Die JVM braucht Speicher ausserhalb des Heaps: Metaspace, Thread-Stacks, Code Cache, Direct Buffers, GC-Strukturen. Sonst OOMKilled.

Wie viele CPUs sieht die JVM im Container?

Aktuelle JDKs leiten sie aus dem CPU-Limit ab. Ohne Limit sieht sie alle Cores des Nodes. Mit ActiveProcessorCount setzt man sie fest.

Was ist In-place Pod Resize?

CPU und Memory eines laufenden Pods ändern, ohne ihn neu zu erzeugen. Stabil seit Kubernetes 1.35, über die resize-Subresource.

Was ist resizePolicy?

Pro Ressource: NotRequired (Änderung ohne Neustart) oder RestartContainer. Für Memory bei Apps wie der JVM oft RestartContainer, weil der Heap beim Start fest ist.

Was machen LimitRange und ResourceQuota?

LimitRange setzt Standard- und Maximalwerte pro Container. ResourceQuota begrenzt die Summe im Namespace.

Was ist Allocatable?

Die Node-Kapazität minus Reserve für System, kubelet und Eviction-Schwelle. Nur das steht Pods zur Verfügung.

Wie misst man Throttling?

container_cpu_cfs_throttled_periods_total geteilt durch container_cpu_cfs_periods_total. Oder nr_throttled in cpu.stat der cgroup.

Szenario: Ein Java-Service wird alle paar Stunden OOMKilled, aber es gibt nie einen OutOfMemoryError. Was tun Sie?

Der Prozess sprengt das Container-Limit, nicht den Heap. Heap-Prozent senken oder Limit erhöhen, mit Native Memory Tracking Non-Heap messen (Threads, Direct Buffers, Metaspace).

Szenario: Die P99-Latenz ist hoch, die CPU-Auslastung im Dashboard niedrig. Woran denken Sie?

An CPU-Throttling durch ein knappes Limit. Throttling-Metrik prüfen, dann Limit erhöhen oder entfernen und Thread-Pools an die CPU anpassen.

Szenario: Neue Pods bleiben Pending mit „Insufficient memory“, aber kubectl top zeigt viel freien Speicher. Warum?

Der Scheduler zählt Requests, nicht Nutzung. Die Requests sind zu hoch angesetzt. Requests nach echten Werten (VPA-Empfehlung) senken oder mehr Nodes bereitstellen.
