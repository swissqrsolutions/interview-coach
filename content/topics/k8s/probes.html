Liveness, Readiness, Startup Probes

Kubernetes · Tier 1 · Quellen: kubernetes.io (Liveness, Readiness and Startup Probes; Configure Liveness, Readiness and Startup Probes; Pod Lifecycle; Container Lifecycle Hooks), Spring Boot 3.x Referenz (Actuator Endpoints, Kubernetes Probes, Application Availability, Health Groups, Graceful Shutdown)

Kern: Eine Probe ist ein Test, den der kubelet regelmässig gegen einen Container ausführt. Die Liveness Probe entscheidet über einen Neustart, die Readiness Probe über Traffic, die Startup Probe schützt langsame Starts. Eine falsche Liveness Probe ist gefährlicher als keine: Sie startet gesunde Pods unter Last neu.

1. Wo sitzen die Probes?

  1. kubelet: führt alle Probes lokal auf dem Node aus. Der API-Server prüft nichts selbst.
  2. Container: beantwortet die Probe, z. B. GET /actuator/health/liveness auf Port 8080.
  3. Liveness rot: Der kubelet tötet den Container und startet ihn nach restartPolicy neu. Der Pod bleibt derselbe.
  4. Readiness rot: Der kubelet setzt die Pod-Condition Ready=false. Der Endpoint-Controller markiert die IP in der EndpointSlice als nicht bereit.
  5. Service: kube-proxy oder Cilium schicken dann keinen neuen Traffic mehr an diesen Pod. Der Container läuft weiter.

2. Die Reise eines Pods (vom Start bis zum Shutdown)

  1. Start. Ein Spring-Boot-Service mit Hibernate braucht 90 Sekunden. Nur die Startup Probe läuft: failureThreshold: 30 × periodSeconds: 10 = bis 300 Sekunden Zeit. Liveness und Readiness sind solange aus.
  2. Gestartet. Die Startup Probe ist einmal grün. Ab jetzt laufen Liveness und Readiness. Die Startup Probe läuft nie wieder.
  3. Ready. Die Readiness Probe ist grün. Der Pod kommt in die EndpointSlice und bekommt Traffic. Erst jetzt ersetzt das Deployment den nächsten alten Pod.
  4. Abhängigkeit langsam. Die Datenbank antwortet zäh. Die Readiness Probe (mit DB-Check) wird rot. Der Pod bekommt keinen neuen Traffic, wird aber nicht neu gestartet.
  5. Echter Hänger. Ein Deadlock blockiert alle Worker-Threads. Die Liveness Probe scheitert 3-mal hintereinander. Der kubelet startet den Container neu. Genau dafür ist Liveness da.
  6. Shutdown. Bei einem Rollout bekommt der Container SIGTERM. Spring Boot setzt Readiness auf REFUSING_TRAFFIC und beendet laufende Requests (Graceful Shutdown). Nach terminationGracePeriodSeconds (Standard 30 s) kommt SIGKILL.

3. Beispiel: eine Liveness Probe schlägt fehl

apiVersion: v1
kind: Pod
metadata: { name: liveness-exec, namespace: demo-probes }
spec:
  containers:
  - name: liveness
    image: busybox:1.36
    args: ["/bin/sh", "-c", "touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600"]
    livenessProbe:
      exec: { command: ["cat", "/tmp/healthy"] }
      initialDelaySeconds: 5
      periodSeconds: 5

$ kubectl -n demo-probes describe pod liveness-exec   # nach ca. 45 s
$ kubectl -n demo-probes get pod liveness-exec
Events:
  Type     Reason     Age   From     Message
  Normal   Started    45s   kubelet  Started container liveness
  Warning  Unhealthy  10s (x3 over 20s)  kubelet  Liveness probe failed: cat: can't open '/tmp/healthy': No such file or directory
  Normal   Killing    10s   kubelet  Container liveness failed liveness probe, will be restarted

NAME            READY   STATUS    RESTARTS      AGE
liveness-exec   1/1     Running   1 (5s ago)    50s

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Das Beispiel stammt aus der kubernetes.io-Aufgabe „Configure Liveness, Readiness and Startup Probes“; der lokale k3s-Cluster war nicht erreichbar.

  1. Die ersten 30 Sekunden existiert /tmp/healthy. Die Probe ist grün.
  2. Danach scheitert cat mit Exit-Code ungleich 0. Nach failureThreshold = 3 Fehlern (Standard) tötet der kubelet den Container.
  3. RESTARTS steigt auf 1. Der Pod und seine IP bleiben gleich, nur der Container ist neu.
  4. Wiederholt sich das, wartet der kubelet immer länger (CrashLoopBackOff, bis 5 Minuten). Aufräumen: kubectl delete namespace demo-probes.

4. Details, die Interviewer fragen

  1. Vier Mechanismen: httpGet (Status 200–399 ist Erfolg), tcpSocket (Port offen), exec (Exit-Code 0), grpc (gRPC Health Checking Protocol).
  2. Standardwerte: initialDelaySeconds: 0, periodSeconds: 10, timeoutSeconds: 1, successThreshold: 1, failureThreshold: 3. Liveness und Startup verlangen successThreshold: 1.
  3. Zeit bis zur Reaktion: ungefähr periodSeconds × failureThreshold. Mit Standardwerten: etwa 30 Sekunden bis zum Neustart.
  4. Timeout zählt als Fehler. timeoutSeconds: 1 ist knapp. Ein GC-Stopp oder voller Thread-Pool lässt die Probe scheitern.
  5. Startup Probe: Solange sie nicht grün ist, laufen keine anderen Probes. Ist sie failureThreshold-mal rot, wird der Container neu gestartet. Sie ersetzt ein grosses initialDelaySeconds.
  6. Readiness läuft immer weiter, das ganze Leben des Pods lang. Ein Pod kann also wieder aus dem Load Balancing fallen.
  7. Readiness und Rollouts: Ein Deployment zählt nur Ready-Pods als verfügbar. minReadySeconds verlangt, dass ein Pod eine Weile ready bleibt. Ohne Readiness Probe gilt der Pod sofort als ready.
  8. Probe-Level terminationGracePeriodSeconds: Eine Liveness- oder Startup-Probe kann eine eigene, kürzere Gnadenfrist haben. So wartet ein hängender Container nicht die lange Pod-Frist ab.
  9. Spring Boot Probes: Läuft die App auf Kubernetes, aktiviert Spring Boot automatisch /actuator/health/liveness und /actuator/health/readiness. Sonst: management.endpoint.health.probes.enabled=true.
  10. Availability States: LivenessState (CORRECT, BROKEN) und ReadinessState (ACCEPTING_TRAFFIC, REFUSING_TRAFFIC). Die App kann sie über AvailabilityChangeEvent selbst ändern.
  11. Health Groups: management.endpoint.health.group.readiness.include=readinessState,db nimmt die DB nur in Readiness auf. Liveness bleibt bei livenessState.
  12. Probes auf dem Hauptport: management.endpoint.health.probes.add-additional-paths=true liefert /livez und /readyz auf dem App-Port. So prüft die Probe, ob der echte Web-Server antwortet, auch wenn Actuator einen eigenen Port hat.
  13. Shutdown-Rennen: Nach SIGTERM braucht das Entfernen aus den Endpoints einen Moment. Ein preStop-Hook mit kurzem sleep (z. B. 5–10 s) verhindert Fehler bei Requests, die noch ankommen.

5. Vergleich

  • Liveness: Frage „Ist der Prozess kaputt und nur durch Neustart heilbar?“ Aktion: Container neu starten. Nur interne Zustände prüfen.
  • Readiness: Frage „Kann der Pod jetzt Requests bedienen?“ Aktion: aus dem Service nehmen. Darf wichtige Abhängigkeiten prüfen.
  • Startup: Frage „Ist der Start fertig?“ Aktion: bis dahin die anderen Probes aussetzen, bei Zeitüberschreitung neu starten.
  • Docker HEALTHCHECK: wird von Kubernetes ignoriert. Nur die Probes im Pod-Spec zählen.
  • Load-Balancer-Health-Check (Azure LB, Ingress): prüft von aussen den Node oder Service. Ergänzt Probes, ersetzt sie nicht.

6. In der Produktion

  1. Kaskade durch Liveness mit DB-Check: Die DB ist 1 Minute langsam. Alle Pods fallen in Liveness durch und starten gleichzeitig neu. Der Kaltstart belastet die DB noch mehr. Lösung: Abhängigkeiten nie in Liveness, nur in Readiness.
  2. Neustarts unter Last: Bei hoher Last ist der Thread-Pool voll. Die Liveness-Anfrage wartet länger als 1 Sekunde und scheitert. Der Neustart nimmt Kapazität weg und verschlimmert die Last. Lösung: grösseres timeoutSeconds, höherer failureThreshold, Probe auf einem eigenen Management-Port.
  3. Endlose Neustarts beim Start: Eine JVM braucht 120 Sekunden, die Liveness Probe greift nach 30. Der Pod kommt nie hoch (CrashLoopBackOff). Lösung: Startup Probe mit genug Zeit.
  4. Alle Pods gleichzeitig nicht ready: Readiness prüft eine gemeinsame Abhängigkeit. Fällt sie aus, hat der Service null Endpoints und liefert 503. Das kann richtig sein, aber man muss es bewusst entscheiden.
  5. Fehler beim Rollout: Ohne Readiness Probe bekommt ein Pod Traffic, bevor Spring Boot fertig ist. Ergebnis: 502 und 503 bei jedem Deployment.
  6. Fehler beim Shutdown: Der Pod beendet sich, bevor Ingress und kube-proxy ihn entfernt haben. Lösung: preStop-Sleep und Graceful Shutdown (server.shutdown=graceful, in Spring Boot 3.4+ Standard).

7. Diagnose: Werkzeuge und Befehle

  • kubectl describe pod <pod>: Events Unhealthy mit Grund (Liveness/Readiness/Startup probe failed) und Killing.
  • kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState}': Exit-Code und Grund des letzten Neustarts.
  • kubectl logs <pod> --previous: Log des abgestürzten Containers.
  • kubectl get endpointslices -l kubernetes.io/service-name=<svc> -o yaml: welche Pods ready: false sind.
  • kubectl exec <pod> -- wget -qO- localhost:8080/actuator/health/readiness: Antwort selbst prüfen.
  • kubectl get events --field-selector reason=Unhealthy -A: alle Probe-Fehler im Cluster.
  • Prometheus: kube_pod_container_status_restarts_total und prober_probe_total{result="failed"} (kubelet-Metrik).

8. Senior-Punkte

  1. Liveness so dumm wie möglich. Sie prüft nur, ob der Prozess selbst lebt. Jede externe Abhängigkeit darin ist ein Risiko für Kaskaden.
  2. Keine Liveness ist oft besser als eine schlechte. Stürzt der Prozess ab, startet Kubernetes ihn sowieso neu. Liveness braucht man nur für Hänger.
  3. Readiness ist ein Lastschutz. Sie darf Abhängigkeiten prüfen, aber man muss entscheiden, ob „alle Pods nicht ready“ das gewünschte Verhalten ist.
  4. Startup statt initialDelaySeconds. Die Startup Probe gibt langsamen JVMs Zeit und erkennt Hänger danach trotzdem schnell.
  5. Probes sind Teil des Rollout-Designs. Readiness, minReadySeconds, maxUnavailable und Graceful Shutdown zusammen entscheiden über Zero-Downtime.
  6. Probe-Neustarts überwachen. Ein Alarm auf steigende Restarts zeigt falsche Probes früh, bevor sie eine Störung auslösen.

10. Fallen

  • „Liveness soll prüfen, ob die Datenbank erreichbar ist.“ → Falsch. Dann starten alle Pods bei einem DB-Problem neu. DB-Checks gehören in Readiness.
  • „Readiness rot startet den Pod neu.“ → Falsch. Readiness nimmt den Pod nur aus dem Service.
  • „Die Startup Probe läuft periodisch weiter.“ → Falsch. Nach dem ersten Erfolg nie wieder.
  • „Ein grosses initialDelaySeconds reicht für langsame Starts.“ → Schlecht. Es verzögert auch die Erkennung von Hängern und passt nie für jeden Start. Besser: Startup Probe.
  • „Docker HEALTHCHECK wird von Kubernetes genutzt.“ → Falsch. Kubernetes ignoriert ihn.

11. Fragen

Was ist eine Liveness Probe?

Ein Test, ob der Container noch lebt. Scheitert er failureThreshold-mal, startet der kubelet den Container neu.

Was ist eine Readiness Probe?

Ein Test, ob der Pod Traffic bedienen kann. Scheitert er, nimmt Kubernetes den Pod aus den Service-Endpoints, ohne Neustart.

Was ist eine Startup Probe?

Ein Test nur für den Start. Bis sie grün ist, laufen Liveness und Readiness nicht. Danach läuft sie nie wieder.

Wer führt Probes aus?

Der kubelet auf dem Node des Pods. Der API-Server bekommt nur das Ergebnis.

Welche Probe-Arten gibt es?

httpGet, tcpSocket, exec und grpc.

Was sind die Standardwerte einer Probe?

initialDelaySeconds 0, periodSeconds 10, timeoutSeconds 1, successThreshold 1, failureThreshold 3.

Wie lange dauert es bis zum Neustart nach einem Hänger?

Etwa periodSeconds × failureThreshold, mit Standardwerten rund 30 Sekunden, plus Timeout.

Warum sollte Liveness keine Datenbank prüfen?

Ein DB-Problem würde alle Pods gleichzeitig neu starten. Ein Neustart heilt die DB nicht und erzeugt zusätzliche Last.

Wie lösen Sie einen langsamen JVM-Start?

Mit einer Startup Probe, z. B. failureThreshold 30 × periodSeconds 10 = 5 Minuten. Dazu ausreichend CPU beim Start.

Warum ist initialDelaySeconds schlechter als eine Startup Probe?

Er ist fest. Zu kurz führt zu Neustarts, zu lang verzögert die Erkennung. Die Startup Probe endet, sobald der Start fertig ist.

Was passiert ohne Readiness Probe?

Der Pod gilt sofort als ready, sobald der Container läuft. Er bekommt Traffic, bevor die App bereit ist.

Wie hängen Readiness und Rolling Updates zusammen?

Das Deployment ersetzt den nächsten alten Pod erst, wenn der neue ready ist. Eine schlechte Readiness Probe stoppt oder beschleunigt das Rollout falsch.

Wie macht Spring Boot Probes?

Actuator liefert /actuator/health/liveness und /readiness, auf Kubernetes automatisch aktiv. Grundlage sind LivenessState und ReadinessState.

Was sind Health Groups in Spring Boot?

Benannte Gruppen von Health Indicators. Man kann z. B. die DB nur in die readiness-Gruppe aufnehmen.

Was macht Spring Boot beim Shutdown mit Readiness?

Es setzt ReadinessState auf REFUSING_TRAFFIC und beendet laufende Requests beim Graceful Shutdown.

Wozu ein preStop-Sleep?

Das Entfernen aus Endpoints und Load Balancern braucht Zeit. Der Sleep hält den Pod kurz am Leben, damit späte Requests noch beantwortet werden.

Was ist CrashLoopBackOff?

Der Container startet immer wieder neu. Der kubelet wartet zwischen den Versuchen immer länger, bis 5 Minuten.

Warum Probes auf einem eigenen Management-Port?

Sie sind von App-Traffic und Security-Filtern getrennt. Aber man prüft dann nicht den echten Web-Server; additional-paths auf dem Hauptport löst das.

Kann eine Probe eine eigene Gnadenfrist haben?

Ja, Liveness und Startup Probes haben terminationGracePeriodSeconds. So wird ein hängender Container schneller beendet als bei einem normalen Shutdown.

Szenario: Unter Last starten Pods immer wieder neu, obwohl die App funktioniert. Was prüfen Sie?

Ob die Liveness Probe wegen Timeout scheitert, z. B. voller Thread-Pool oder GC-Pause. Lösung: grösserer timeoutSeconds und failureThreshold, Probe ohne Abhängigkeiten, eventuell auf eigenem Port.

Szenario: Ein neuer Service bleibt in CrashLoopBackOff, Logs zeigen einen normalen Start. Warum?

Die Liveness Probe tötet ihn, bevor der Start fertig ist. Events zeigen „Liveness probe failed“. Lösung: Startup Probe mit ausreichend Zeit.

Szenario: Bei jedem Deployment gibt es einige 502-Fehler. Was tun Sie?

Readiness Probe prüfen, damit neue Pods erst nach dem Start Traffic bekommen. Beim Shutdown Graceful Shutdown und preStop-Sleep einbauen, damit alte Pods nicht zu früh verschwinden.
