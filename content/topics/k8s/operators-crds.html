Operators und CRDs

Kubernetes · Tier 2 · Quellen: kubernetes.io Docs „Custom Resources“, „Extend the Kubernetes API with CustomResourceDefinitions“, „Operator pattern“, „Finalizers“, „Controllers“, Feature-Gate-Referenz (CRDValidationRatcheting, CustomResourceFieldSelectors) (Stand Kubernetes 1.37); Operator SDK Docs (Operator Capabilities)

Kern: Eine CustomResourceDefinition (CRD) erweitert die Kubernetes-API um einen eigenen Objekttyp, z. B. ReportJob. Ein Operator ist ein Controller, der solche Objekte beobachtet und den echten Zustand ständig an den gewünschten anpasst. Zusammen verpacken sie Betriebswissen (installieren, upgraden, sichern) als Code.

1. Wo sitzen CRD und Operator?

  1. CRD: registriert einen neuen Typ beim API-Server: Gruppe, Namen, Scope, Versionen und ein OpenAPI-Schema. Beispiel: reportjobs.demo.example.com.
  2. Custom Resource (CR): ein Objekt dieses Typs. Es liegt wie jedes Objekt in etcd und hat spec (Wunsch) und status (Ist).
  3. Operator: ein normaler Pod, meist ein Deployment mit Leader Election. Ohne ihn ist eine CR nur gespeicherte Daten.
  4. Informer: beobachtet die API per watch und hält einen lokalen Cache. Änderungen landen als Schlüssel namespace/name in einer Workqueue.
  5. Reconcile: liest den Wunsch, vergleicht mit dem Ist und erzeugt oder ändert Pods, Jobs, Secrets oder externe Ressourcen.
  6. RBAC: Der Operator braucht Rechte auf seine CRs und auf alles, was er erzeugt.

2. Die Reise einer Custom Resource (die Geschichte zum Merken)

  1. apply: Argo CD legt die CR stats-2026-11-23 an: „Statistik für den 23.11. berechnen“.
  2. Validierung: Der API-Server prüft das OpenAPI-Schema und die CEL-Regeln der CRD. Er setzt Defaults, z. B. maxRetries: 3. Unbekannte Felder schneidet er ab (Pruning).
  3. Speichern: Die CR liegt in etcd. metadata.generation ist 1. Der Operator bekommt ein Watch-Event.
  4. Reconcile: Der Operator sieht: Es gibt noch keinen Job für diesen Tag. Er erzeugt einen Job mit einer ownerReference auf die CR.
  5. Status: Er schreibt über die /status-Subresource phase: Completed und observedGeneration: 1. Ändert jemand die spec, steigt generation. So sieht man, ob der Operator die neue Version schon verarbeitet hat.
  6. Löschen: Die CR hat einen Finalizer. Kubernetes setzt nur deletionTimestamp. Der Operator räumt extern auf (z. B. Daten im Lakehouse) und entfernt dann den Finalizer. Erst jetzt ist die CR weg. Der Job geht per Garbage Collection mit.

3. Beispiel: eine CRD im echten Cluster

# Auszug crd.yaml: Gruppe demo.example.com, Kind ReportJob, Kurzname rj
versions:
- name: v1
  served: true
  storage: true
  subresources: {status: {}}
  additionalPrinterColumns: [Day .spec.day, Retries .spec.maxRetries, Phase .status.phase]
  schema.openAPIV3Schema.properties.spec:
    required: [day]
    day:        {type: string, format: date}
    maxRetries: {type: integer, minimum: 0, maximum: 5, default: 3}
    mode:       {type: string, enum: [replace, append]}
    x-kubernetes-validations:
    - rule: "!has(self.mode) || self.mode == 'replace' || self.maxRetries == 0"
      message: "mode=append ist nur ohne Retries erlaubt (sonst Doppelzählung)."
$ kubectl apply -f crd.yaml && kubectl wait --for condition=established crd/reportjobs.demo.example.com
customresourcedefinition.apiextensions.k8s.io/reportjobs.demo.example.com created
customresourcedefinition.apiextensions.k8s.io/reportjobs.demo.example.com condition met

$ kubectl -n demo-operators-crds apply -f cr.yaml          # nur spec.day gesetzt
reportjob.demo.example.com/stats-2026-11-23 created
$ kubectl -n demo-operators-crds apply -f bad.yaml         # maxRetries: 9, mode: append
The ReportJob "bad" is invalid:
* spec.maxRetries: Invalid value: 9: spec.maxRetries in body should be less than or equal to 5
* spec: Invalid value: mode=append ist nur ohne Retries erlaubt (sonst Doppelzählung).

$ kubectl -n demo-operators-crds get rj stats-2026-11-23 -o jsonpath='{.spec}{" generation="}{.metadata.generation}'
{"day":"2026-11-23","maxRetries":3} generation=1

# so schreibt ein Operator den Status:
$ kubectl -n demo-operators-crds patch rj/stats-2026-11-23 --subresource=status --type=merge \
    -p '{"status":{"phase":"Completed","observedGeneration":1}}'
generation=1                                   # Status ändert generation nicht
$ kubectl -n demo-operators-crds patch rj/stats-2026-11-23 --type=merge -p '{"spec":{"maxRetries":1}}'
generation=2 observedGeneration=1              # Spec geändert, Operator noch nicht nachgezogen
$ kubectl -n demo-operators-crds get rj
NAME               DAY          RETRIES   PHASE
stats-2026-11-23   2026-11-23   1         Completed

# Finalizer
$ kubectl -n demo-operators-crds patch rj/stats-2026-11-23 --type=merge -p '{"metadata":{"finalizers":["demo.example.com/cleanup-iceberg"]}}'
$ kubectl -n demo-operators-crds delete rj/stats-2026-11-23 --wait=false
reportjob.demo.example.com "stats-2026-11-23" deleted from demo-operators-crds namespace
$ kubectl ... get rj/stats-2026-11-23 -o jsonpath='...'
deletionTimestamp=2026-11-24T15:28:47Z finalizers=["demo.example.com/cleanup-iceberg"]
$ kubectl ... patch rj/stats-2026-11-23 --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
$ kubectl -n demo-operators-crds get rj
No resources found in demo-operators-crds namespace.

Echte Ausgabe, k3s v1.36 (v1.36.4+k3s1). Es lief kein Operator; Status und Finalizer wurden von Hand gesetzt, wie es ein Operator tun würde. Einige Befehle gekürzt. CRD und Namespace wurden danach gelöscht.

  1. Der API-Server prüft das Schema und die CEL-Regel. Beide Fehler kommen in einer Antwort. Ohne Operator ist die Regel schon wirksam.
  2. maxRetries: 3 stand nicht im YAML. Der API-Server hat den Default aus dem Schema gesetzt.
  3. Ein Patch auf /status ändert generation nicht. Ein Patch auf spec erhöht sie auf 2.
  4. generation=2 und observedGeneration=1 heisst: Der Operator hat die neue Spec noch nicht verarbeitet. Das ist das Standard-Signal für „im Gange“.
  5. Mit Finalizer bleibt das Objekt nach delete stehen, nur mit deletionTimestamp. Erst nach Entfernen des Finalizers ist es weg.
  6. additionalPrinterColumns machen kubectl get rj lesbar.

4. Details, die Interviewer fragen

  1. Strukturelles Schema: In apiextensions.k8s.io/v1 Pflicht. Jedes Feld hat einen Typ. Unbekannte Felder werden beim Speichern entfernt (Pruning), ausser mit x-kubernetes-preserve-unknown-fields.
  2. CEL-Validierung (stabil seit 1.29): x-kubernetes-validations mit rule, message oder messageExpression, reason, fieldPath. Transition Rules nutzen oldSelf, z. B. „Feld darf nicht mehr geändert werden“.
  3. Validation Ratcheting (stabil seit 1.33): Alte ungültige Werte dürfen bleiben, solange man sie nicht ändert. Wichtig beim Verschärfen eines Schemas.
  4. Defaulting: über default im Schema. Gilt beim Schreiben und beim Lesen aus etcd.
  5. Status-Subresource: trennt spec und status. Nutzer ändern spec, der Operator ändert status. generation steigt nur bei spec-Änderungen.
  6. Scale-Subresource: macht kubectl scale und den HPA für die CR nutzbar.
  7. Versionen: mehrere Versionen served, aber genau eine storage: true. Zwischen Versionen konvertiert der API-Server: Strategie None (nur apiVersion ändern) oder Webhook.
  8. Field Selectors für CRs (stabil seit 1.32): mit selectableFields kann man nach Feldern filtern, z. B. --field-selector spec.day=2026-11-23.
  9. Controller-Pattern: level-triggered: Reconcile schaut auf den ganzen Zustand, nicht auf ein einzelnes Event. Darum muss es idempotent sein und darf beliebig oft laufen.
  10. ownerReferences: Erzeugte Objekte zeigen auf die CR. Wird die CR gelöscht, räumt die Garbage Collection sie auf. Owner und Kind müssen im selben Namespace sein (oder Owner cluster-weit).
  11. Finalizer: Liste von Schlüsseln in metadata.finalizers. Solange einer drin ist, wird das Objekt nicht gelöscht. Neue Finalizer kann man nach dem Löschbefehl nicht mehr hinzufügen.
  12. Conditions: Standardform für Status, z. B. Ready=True mit reason und message. Werkzeuge wie kubectl wait --for=condition=Ready verstehen sie.
  13. Operator Capability Levels (Operator SDK): 1 Basic Install, 2 Seamless Upgrades, 3 Full Lifecycle, 4 Deep Insights, 5 Auto Pilot.
  14. Werkzeuge: controller-runtime (Go-Bibliothek), kubebuilder und Operator SDK (Gerüst, Codegenerierung). Java: Java Operator SDK.

5. Vergleich

  • CRD: eigener Typ ohne eigenen Server. Speicherung, RBAC, Watch und kubectl gibt es gratis.
  • Aggregated API Server: eigener API-Server hinter dem Haupt-API-Server. Volle Kontrolle, z. B. eigene Speicherung. Viel mehr Aufwand. Beispiel: metrics-server.
  • Operator: CRD plus Controller mit Betriebswissen. Für zustandsbehaftete Systeme (Datenbanken, Kafka mit Strimzi, PostgreSQL mit CloudNativePG).
  • Helm-Chart: installiert einmal und upgradet auf Befehl. Reagiert nicht auf Zustandsänderungen im Betrieb.
  • ConfigMap plus Skript: einfache Konfiguration ohne Schema und ohne Validierung.
  • Admission Policy: prüft Objekte beim Schreiben. Ein Operator handelt danach.

6. In der Produktion

  1. CRD gelöscht, alle Daten weg: Beim Löschen einer CRD löscht Kubernetes alle CRs dieses Typs. Bei Argo CD-Applications oder Datenbank-Operatoren ein Desaster. Lösung: CRDs mit Schutz (z. B. Prune deaktiviert, eigenes Repo), Backups mit Velero.
  2. Namespace hängt in Terminating: Eine CR hat einen Finalizer, aber der Operator läuft nicht mehr. Lösung: Operator wieder starten. Finalizer nur von Hand entfernen, wenn man weiss, was dann extern übrig bleibt.
  3. Helm aktualisiert CRDs nicht: CRDs im crds/-Ordner werden nur beim Install angelegt, nicht beim Upgrade. Lösung: CRDs separat versionieren und anwenden, oder Chart mit CRD-Templates.
  4. Grosse CRDs scheitern beim Apply: Die Annotation für Client-Side-Apply wird zu gross. Lösung: Server-Side Apply (in Argo CD ServerSideApply=true).
  5. Operator-Upgrade bricht alte CRs: Neue Pflichtfelder oder geänderte Versionen. Lösung: Defaults, Ratcheting, Conversion, Storage-Version-Migration testen.
  6. API-Server wird langsam: Ein Operator macht List-Aufrufe statt Watch und Cache, oder es gibt hunderttausende CRs. Lösung: Informer nutzen, alte CRs aufräumen.
  7. Operator mit zu viel RBAC: Viele Charts geben cluster-weite Rechte. Lösung: Rechte prüfen, auf Namespaces begrenzen, wo es geht.

7. Diagnose: Werkzeuge und Befehle

  • kubectl get crds und kubectl explain reportjob.spec --recursive: Schema einer CRD.
  • kubectl api-resources --api-group=demo.example.com: welche Typen eine Gruppe hat.
  • kubectl get rj X -o yaml: generation, status.observedGeneration, conditions, finalizers.
  • kubectl get crd X -o jsonpath='{.status.storedVersions}': welche Versionen in etcd liegen.
  • kubectl logs deploy/<operator> und Leader-Lease: kubectl get lease -n <ns>.
  • kubectl auth can-i --as=system:serviceaccount:ns:sa list reportjobs: RBAC des Operators.
  • kubectl get ns X -o yaml: bei Terminating zeigen die Conditions, welche Ressourcen und Finalizer blockieren.

8. Senior-Punkte

  1. Erst fragen: braucht es einen Operator? Ein Helm-Chart oder ein CronJob reicht oft. Ein Operator ist ein eigenes Produkt mit Wartung.
  2. Fertige Operatoren für schwere Systeme: Datenbanken, Kafka, Zertifikate, Secrets. Eigener Code nur für echte Fachlogik.
  3. Die CRD ist eine öffentliche API. Versionieren, Defaults setzen, Validierung in CEL, nie Felder umdeuten.
  4. Reconcile idempotent bauen. Beliebig oft, in beliebiger Reihenfolge, nach Neustart. Status ehrlich mit observedGeneration und Conditions.
  5. Finalizer sparsam: nur für echte externe Aufräumarbeit. Jeder Finalizer kann Löschungen blockieren.
  6. Operatoren gehören zum Plattform-Betrieb: Upgrades, RBAC-Review, Monitoring, Backup der CRs.

10. Fallen

  • „Eine CRD macht schon etwas.“ → Falsch. Sie speichert nur Daten. Handeln tut der Controller.
  • „Ein Operator reagiert auf Events, also muss jedes Event ankommen.“ → Falsch. Er ist level-triggered und gleicht den ganzen Zustand ab.
  • „Eine CRD löschen ist harmlos.“ → Falsch. Alle CRs dieses Typs werden mitgelöscht.
  • „Ein hängendes Objekt löse ich immer, indem ich den Finalizer entferne.“ → Falsch. Dann bleibt externer Müll zurück. Erst den Operator reparieren.
  • „Mehrere Versionen heisst mehrere Kopien in etcd.“ → Falsch. Genau eine Storage-Version. Der Rest wird konvertiert.
  • „Status ändern erhöht generation.“ → Falsch. Nur spec-Änderungen erhöhen sie.

11. Fragen

Was ist eine CRD?

Eine Definition, die einen neuen Objekttyp in der Kubernetes-API registriert, mit Schema, Versionen und Scope.

Was ist ein Operator?

Ein Controller, der Custom Resources beobachtet und Betriebswissen ausführt: installieren, upgraden, heilen, sichern.

Was ist ein Reconcile Loop?

Eine Funktion, die den gewünschten Zustand aus der CR mit dem echten vergleicht und Unterschiede behebt. Sie läuft bei jeder Änderung und periodisch.

Was heisst level-triggered?

Der Controller schaut auf den aktuellen Gesamtzustand, nicht auf einzelne Events. Verpasste Events sind kein Problem.

Was ist ein strukturelles Schema?

Ein OpenAPI-Schema, in dem jedes Feld einen Typ hat. Pflicht in v1. Es erlaubt Pruning, Defaults und Validierung.

Wie validiert man komplexe Regeln in einer CRD?

Mit CEL in x-kubernetes-validations. Stabil seit 1.29, ohne Webhook.

Was sind Transition Rules?

CEL-Regeln mit oldSelf, die den alten mit dem neuen Wert vergleichen, z. B. „unveränderlich“.

Was macht die Status-Subresource?

Eigener Endpunkt /status. Spec und Status werden getrennt geschrieben, und generation steigt nur bei spec-Änderungen.

Was ist observedGeneration?

Die generation, die der Operator zuletzt verarbeitet hat. Ist sie kleiner als generation, ist er noch nicht fertig.

Was ist ein Finalizer?

Ein Schlüssel in metadata.finalizers, der das Löschen blockiert, bis ein Controller aufgeräumt und ihn entfernt hat.

Was sind ownerReferences?

Verweise von erzeugten Objekten auf ihren Besitzer. Wird der Besitzer gelöscht, räumt die Garbage Collection sie auf.

Wie versioniert man eine CRD?

Mehrere Versionen served, genau eine storage. Konvertierung None oder per Webhook, danach gespeicherte Objekte migrieren.

Was ist Validation Ratcheting?

Verschärfte Regeln gelten nur für geänderte Felder. Alte, nun ungültige Werte dürfen bleiben. Stabil seit 1.33.

CRD oder Aggregated API Server?

CRD fast immer: einfach, alles inklusive. Aggregated API nur für eigene Speicherung oder spezielle Semantik.

Welche Capability Levels gibt es?

Basic Install, Seamless Upgrades, Full Lifecycle, Deep Insights, Auto Pilot.

Womit baut man Operatoren?

controller-runtime mit kubebuilder oder Operator SDK in Go, Java Operator SDK in Java.

Welche Operatoren kennen Sie aus der Praxis?

Argo CD, External Secrets Operator, Karpenter, Kyverno. Bekannte weitere: Strimzi für Kafka, CloudNativePG für PostgreSQL, cert-manager.

Warum braucht ein Operator Leader Election?

Bei mehreren Replikas darf nur eine reconcilen, sonst kämpfen sie gegeneinander. Die Wahl läuft über ein Lease-Objekt.

Warum aktualisiert Helm CRDs nicht?

CRDs im crds/-Ordner installiert Helm nur einmal. Upgrades und Löschen macht es bewusst nicht, um Datenverlust zu vermeiden.

Szenario: Ein Namespace hängt seit Stunden in Terminating. Was tun Sie?

Conditions des Namespace lesen. Meist hat eine CR einen Finalizer, und ihr Operator läuft nicht. Operator reparieren, erst im Notfall den Finalizer bewusst entfernen.

Szenario: Nach einem Operator-Upgrade werden bestehende CRs abgelehnt. Warum?

Das neue Schema hat Pflichtfelder oder strengere Regeln. Lösung: Defaults setzen, Ratcheting nutzen, Konvertierung prüfen, Upgrade vorher in Staging testen.

Szenario: Das Team will einen eigenen Operator für einen nächtlichen Report. Was sagen Sie?

Wahrscheinlich zu viel. Ein CronJob mit idempotentem Job reicht. Ein Operator lohnt sich erst bei echtem Lebenszyklus mit Zustand und Heilung.
