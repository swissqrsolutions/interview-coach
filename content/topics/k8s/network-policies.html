Network Policies und CNI (Cilium)

Kubernetes · Tier 1 · Quellen: kubernetes.io (Network Policies, Cluster Networking, Network Plugins, Declare Network Policy), CNI Specification (containernetworking/cni), Cilium Docs (Network Policy, Layer 7 Policy, DNS-based Policy, Hubble), Microsoft Learn (Azure CNI Powered by Cilium)

Kern: Eine NetworkPolicy ist eine Firewall-Regel für Pods auf L3/L4. Sie wählt Pods per Label und erlaubt nur bestimmten Verkehr. Ohne Policy darf jeder Pod mit jedem Pod reden (default allow). Durchsetzen muss sie das CNI-Plugin, z. B. Cilium mit eBPF.

1. Wo sitzen Network Policy und CNI?

  1. API-Server: speichert NetworkPolicy-Objekte. Er setzt selbst nichts durch.
  2. Kubelet und Runtime: rufen beim Start eines Pods das CNI-Plugin mit ADD auf. Das Plugin gibt dem Pod eine IP und verbindet ihn mit dem Netz.
  3. Cilium Agent: läuft als DaemonSet auf jedem Node. Er beobachtet Pods und Policies und lädt eBPF-Programme in den Kernel.
  4. eBPF: prüft jedes Paket direkt im Kernel. Erlaubt oder verwirft es nach Policy.
  5. Hubble: liest dieselben eBPF-Daten und zeigt jeden Flow mit Verdict, z. B. FORWARDED oder DROPPED.

2. Die Reise eines Pakets durch die Policy

  1. DNS zuerst. Der api-Pod fragt CoreDNS nach mssql.match.svc. Hat der Pod eine Egress-Policy ohne DNS-Regel, endet die Reise hier: Timeout.
  2. Egress-Check auf der Quelle. Ist der api-Pod von einer Egress-Policy ausgewählt? Dann muss eine Regel Ziel und Port 1433 erlauben.
  3. Transport. Cilium kennt für jeden Pod eine Security Identity, eine Zahl aus seinen Labels. Die Identity reist mit dem Paket, z. B. im VXLAN-Header.
  4. Ingress-Check auf dem Ziel. Ist der mssql-Pod ausgewählt, muss eine Ingress-Regel die Identity von api erlauben.
  5. L7-Check (nur Cilium). Hat die Regel HTTP-Regeln, leitet eBPF den Verkehr durch einen Envoy-Proxy. Er prüft Methode und Pfad.
  6. Verdict. Erlaubt: Paket kommt an. Sonst wird es still verworfen. Die Antwort auf eine erlaubte Verbindung ist automatisch erlaubt (stateful).

3. Beispiel: deny-all, DNS, gezielt erlauben

# 1) Default deny für alles im Namespace (Ingress und Egress)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-all, namespace: demo-netpol }
spec:
  podSelector: {}                 # leer = alle Pods im Namespace
  policyTypes: [Ingress, Egress]  # keine Regeln = nichts erlaubt
---
# 2) DNS erlauben, sonst geht keine Namensauflösung
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: demo-netpol }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector:       { matchLabels: { k8s-app: kube-dns } }   # gleiches Element = UND
    ports: [ { protocol: UDP, port: 53 }, { protocol: TCP, port: 53 } ]
---
# 3) Nur api darf auf db:5432
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-from-api, namespace: demo-netpol }
spec:
  podSelector: { matchLabels: { app: db } }
  policyTypes: [Ingress]
  ingress:
  - from: [ { podSelector: { matchLabels: { app: api } } } ]
    ports: [ { protocol: TCP, port: 5432 } ]
---
# 4) api darf zu db (Egress-Seite)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-to-db, namespace: demo-netpol }
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Egress]
  egress:
  - to: [ { podSelector: { matchLabels: { app: db } } } ]
    ports: [ { protocol: TCP, port: 5432 } ]
$ kubectl -n demo-netpol exec deploy/api -- nc -zv -w 3 db 5432
db (10.43.12.7:5432) open
$ kubectl -n demo-netpol exec deploy/other -- nc -zv -w 3 db 5432
nc: db (10.43.12.7:5432): Operation timed out
$ hubble observe -n demo-netpol --verdict DROPPED
demo-netpol/other-7c9f… -> demo-netpol/db-5d8b…:5432 policy-verdict:none INGRESS DENIED (TCP Flags: SYN)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Der lokale k3s-Cluster war nicht erreichbar; Hubble braucht Cilium.

  1. default-deny-all wählt alle Pods für beide Richtungen. Ohne Regeln ist dann nichts erlaubt.
  2. allow-dns öffnet Port 53 UDP und TCP zu CoreDNS. Grosse Antworten nutzen TCP.
  3. Für eine Verbindung braucht es zwei Erlaubnisse: Egress beim Sender und Ingress beim Empfänger.
  4. other bekommt einen Timeout, kein „connection refused“. Das Paket wird still verworfen.
  5. Hubble zeigt den Drop mit Richtung und Grund. Das ist der schnellste Beweis für ein Policy-Problem.

Cilium L7 und FQDN:

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: { name: api-l7, namespace: demo-netpol }
spec:
  endpointSelector: { matchLabels: { app: api } }
  ingress:
  - fromEndpoints: [ { matchLabels: { app: webui } } ]
    toPorts:
    - ports: [ { port: "8080", protocol: TCP } ]
      rules:
        http: [ { method: "GET", path: "/api/.*" } ]   # Regex auf den Pfad
  egress:
  - toEndpoints: [ { matchLabels: { "k8s:io.kubernetes.pod.namespace": kube-system, k8s-app: kube-dns } } ]
    toPorts:
    - ports: [ { port: "53", protocol: ANY } ]
      rules: { dns: [ { matchPattern: "*" } ] }        # DNS-Proxy lernt Namen → IPs
  - toFQDNs: [ { matchName: "login.microsoftonline.com" } ]
    toPorts: [ { ports: [ { port: "443", protocol: TCP } ] } ]
  1. webui darf nur GET /api/.... Ein DELETE bekommt HTTP 403 vom Envoy-Proxy, keinen Timeout.
  2. toFQDNs erlaubt einen Hostnamen statt IPs. Das klappt nur mit der dns-Regel: Ciliums DNS-Proxy merkt sich die aufgelösten IPs.

4. Details, die Interviewer fragen

  1. Default allow: Ein Pod ist nicht isoliert, bis eine Policy ihn auswählt. Isolation gilt pro Richtung: Ingress und Egress getrennt.
  2. Additiv: Mehrere Policies auf einem Pod ergeben die Vereinigung ihrer Regeln. Die Reihenfolge ist egal. Die Standard-API kennt keine Deny-Regel.
  3. podSelector: wählt die Ziel-Pods der Policy im eigenen Namespace. {} heisst: alle Pods.
  4. from/to-Peers: podSelector (gleicher Namespace), namespaceSelector (andere Namespaces), ipBlock (CIDR mit except, für Ziele ausserhalb).
  5. UND vs ODER: namespaceSelector und podSelector im selben Listenelement: UND. In zwei Elementen (zwei Bindestriche): ODER. Ein häufiger Fehler.
  6. Namespace-Label: Jeder Namespace hat automatisch kubernetes.io/metadata.name: <name>. Damit wählt man Namespaces stabil.
  7. Ports: port und protocol (TCP, UDP, SCTP). Mit endPort ein Portbereich. Benannte Ports sind erlaubt.
  8. Stateful: Antwortpakete einer erlaubten Verbindung brauchen keine eigene Regel.
  9. DNS-Egress: Wer Egress sperrt, muss Port 53 UDP und TCP zu CoreDNS öffnen. Sonst sieht es aus wie ein Netzwerkausfall.
  10. Services: Policies sehen Pod-IPs nach der Service-Übersetzung. Man erlaubt also Pods, nicht Service-Namen.
  11. Grenzen der Standard-API: kein L7, keine FQDN-Regeln, kein Logging, keine expliziten Denies, keine cluster-weiten Policies. Dafür gibt es CNI-eigene CRDs oder die AdminNetworkPolicy-API der SIG Network (noch nicht Teil des Kerns).
  12. CNI: Eine Spezifikation für Netzwerk-Plugins. Die Runtime ruft das Plugin-Binary mit ADD, DEL, CHECK auf. Das Plugin richtet Interface, IP (IPAM) und Routen ein.
  13. Kubernetes-Netzmodell: Jeder Pod hat eine eigene IP. Pods erreichen sich ohne NAT, auch über Nodes hinweg.
  14. Nicht jedes CNI setzt Policies durch: Flannel allein ignoriert sie. Calico, Cilium und Antrea setzen sie durch. k3s bringt einen eigenen Policy-Controller mit.
  15. Cilium Identity: Cilium filtert nach Label-Identities, nicht nach IPs. Pods mit gleichen relevanten Labels teilen eine Identity. Das skaliert besser bei vielen Pod-Neustarts.
  16. CiliumNetworkPolicy: namespaced CRD mit L7 (HTTP, Kafka, DNS), toFQDNs, toEntities (world, cluster, kube-apiserver) und ingressDeny/egressDeny. CiliumClusterwideNetworkPolicy gilt cluster-weit.
  17. kube-proxy-Ersatz: Cilium kann Services selbst per eBPF balancieren. Dann braucht der Cluster keine iptables-Regeln von kube-proxy.
  18. Hubble: Observability von Cilium. Hubble Relay sammelt Flows aller Nodes, Hubble UI zeigt eine Service-Map. Metriken gehen nach Prometheus.
  19. AKS: Azure CNI Powered by Cilium nutzt Cilium als Datenpfad und für Policies. Erweiterte Funktionen wie FQDN- und L7-Policies brauchen dort Advanced Container Networking Services (ACNS, kostenpflichtig, Kubernetes ≥ 1.29). Ohne ACNS-Security sind FQDN- und L7-Policies blockiert.

5. Vergleich

  • NetworkPolicy vs CiliumNetworkPolicy: NetworkPolicy ist portabel und nur L3/L4. CiliumNetworkPolicy kann L7, FQDN und Deny, bindet aber an Cilium.
  • iptables-CNI (Calico klassisch, kube-proxy) vs eBPF (Cilium): iptables-Regeln wachsen linear mit Services und Policies. eBPF nutzt Hash-Maps und bleibt schnell. Dafür braucht eBPF einen neuen Kernel.
  • Calico vs Cilium: Beide setzen Policies durch und haben eigene CRDs. Calico ist stark bei BGP-Routing. Cilium ist stark bei L7 und Observability (Hubble). Calico hat auch einen eBPF-Modus.
  • Flannel: einfaches Overlay ohne Policy-Durchsetzung.
  • NetworkPolicy vs Service Mesh (Istio, Linkerd): Policy filtert Pakete. Ein Mesh bringt mTLS, Identität per Zertifikat und Retries, aber mit mehr Betriebslast.
  • NetworkPolicy vs Azure NSG: NSG filtert auf Subnetz- und VM-Ebene. NetworkPolicy filtert zwischen Pods im Cluster.

6. In der Produktion

  1. Alles hängt nach deny-all: DNS vergessen. Symptom: Name-Lookup-Timeouts überall. Lösung: allow-dns-Policy zuerst ausrollen.
  2. Nur eine Seite erlaubt: Egress beim Sender erlaubt, Ingress beim Empfänger nicht. Lösung: beide Policies, mit Hubble den Drop finden.
  3. UND/ODER verwechselt: Ein zusätzlicher Bindestrich öffnet einen ganzen Namespace. Lösung: Policies im Review mit einem Visualizer oder Tests prüfen.
  4. Policy greift nicht: Das CNI setzt keine Policies durch, oder die Labels passen nicht. Lösung: CNI prüfen, kubectl get pods --show-labels.
  5. Kein Zugriff auf API-Server oder Webhooks: Operatoren und Admission-Webhooks brauchen Egress zum API-Server. Mit Cilium: toEntities: [kube-apiserver].
  6. Externe Ziele mit wechselnden IPs: ipBlock für Cloud-Dienste veraltet schnell. Lösung: Cilium toFQDNs oder Private Endpoints mit fester IP.
  7. Monitoring bricht: Prometheus darf die Pods nicht mehr scrapen. Lösung: Ingress vom Monitoring-Namespace auf den Metrics-Port erlauben.

7. Diagnose: Werkzeuge und Befehle

  • kubectl get networkpolicy -A und kubectl describe networkpolicy <name>: welche Policies wählen welche Pods.
  • kubectl get pods --show-labels: passen die Labels zum Selector?
  • kubectl exec ... -- nc -zv -w 3 <host> <port> oder curl -m 3: Verbindung testen. Timeout deutet auf Drop.
  • hubble observe --verdict DROPPED -n <ns>: alle verworfenen Flows mit Grund. --pod, --port, --protocol dns filtern.
  • cilium status, cilium connectivity test (Cilium CLI): Gesundheit und End-to-End-Tests.
  • Im Agent-Pod: cilium-dbg endpoint list (Policy-Status pro Endpoint), cilium-dbg policy get.
  • kubectl debug mit nicolaka/netshoot: DNS und Verbindungen aus Sicht des Pods prüfen.

8. Senior-Punkte

  1. Default deny pro Namespace, dann gezielt erlauben. DNS und Monitoring sind Teil der Grundlage.
  2. Labels sind die Sicherheitsgrenze. Wer Labels setzen darf, kann Policies umgehen. Darum Labels per Admission (Kyverno) vorschreiben.
  3. Portabel vs mächtig: Standard-NetworkPolicy wo möglich. Cilium-CRDs nur für L7, FQDN oder cluster-weite Regeln, bewusst als Bindung an Cilium.
  4. Ohne Observability keine Policies. Hubble macht Drops sichtbar. Sonst sucht man Stunden nach „Netzwerkproblemen“.
  5. Policies sind keine Verschlüsselung. Für mTLS braucht es ein Mesh oder Cilium-Encryption (WireGuard/IPsec).
  6. Policies gehören ins Helm-Chart, neben den Workload. So wandern sie mit GitOps durch alle Umgebungen.

„Bei MATCH auf AKS nutzen wir Cilium als CNI mit Network Policies: Sie legen fest, welche Pods mit MSSQL, MinIO und Vault reden dürfen, und mit Hubble sehen wir verworfene Flows.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Kubernetes blockt Verkehr zwischen Namespaces standardmässig.“ → Falsch. Ohne Policy ist alles erlaubt.
  • „Eine NetworkPolicy wirkt immer.“ → Falsch. Nur wenn das CNI sie durchsetzt.
  • „Die spezifischste Policy gewinnt.“ → Falsch. Policies sind additiv; es zählt die Vereinigung.
  • „Mit NetworkPolicy kann ich einzelne IPs verbieten.“ → Nur indirekt über ipBlock.except. Echte Deny-Regeln gibt es nur in CNI-CRDs.
  • „Nach deny-all reicht es, die App-Ports zu öffnen.“ → Falsch. DNS auf Port 53 UDP und TCP fehlt dann.
  • „Ingress erlauben reicht.“ → Falsch, wenn der Sender Egress-isoliert ist. Beide Seiten müssen erlauben.

11. Fragen

Was ist eine NetworkPolicy?

Ein Kubernetes-Objekt, das erlaubten Pod-Verkehr auf L3/L4 beschreibt. Es wählt Pods per Label und erlaubt Ingress und Egress gezielt.

Was gilt ohne NetworkPolicy?

Default allow: Jeder Pod erreicht jeden Pod in allen Namespaces.

Wann ist ein Pod isoliert?

Sobald eine Policy ihn für eine Richtung auswählt. Dann ist in dieser Richtung nur noch erlaubter Verkehr möglich.

Wie schreibt man deny-all?

podSelector: {} und policyTypes Ingress und Egress, ohne Regeln. Das isoliert alle Pods im Namespace.

Wie kombinieren sich mehrere Policies?

Additiv. Erlaubt ist, was irgendeine Policy erlaubt. Es gibt keine Reihenfolge und keine Deny-Regel.

Was ist der Unterschied zwischen einem und zwei Listenelementen in from?

namespaceSelector und podSelector in einem Element sind UND. In zwei Elementen sind sie ODER und öffnen viel mehr.

Warum muss man DNS-Egress erlauben?

Mit Egress-Isolation ist auch Port 53 zu CoreDNS gesperrt. Dann scheitert jede Namensauflösung. UDP und TCP öffnen.

Muss man Antwortverkehr erlauben?

Nein. Policies sind stateful. Antworten auf erlaubte Verbindungen sind automatisch erlaubt.

Wer setzt NetworkPolicies durch?

Das CNI-Plugin, z. B. Cilium, Calico oder Antrea. Der API-Server speichert sie nur. Flannel allein ignoriert sie.

Was ist CNI?

Eine Spezifikation für Netzwerk-Plugins. Die Runtime ruft das Plugin mit ADD und DEL auf, das Plugin richtet Interface, IP und Routen für den Pod ein.

Was ist das Kubernetes-Netzmodell?

Jeder Pod hat eine eigene IP. Pods erreichen sich ohne NAT, auch über Nodes hinweg.

Was ist eBPF und warum nutzt Cilium es?

eBPF sind kleine, geprüfte Programme im Linux-Kernel. Cilium filtert und routet damit direkt im Kernel, mit Hash-Maps statt langer iptables-Ketten.

Was ist eine Cilium Security Identity?

Eine Zahl, die aus den Labels eines Pods entsteht. Policies prüfen Identities statt IPs, das bleibt stabil bei Pod-Neustarts.

Was kann CiliumNetworkPolicy zusätzlich?

L7-Regeln für HTTP, Kafka und DNS, FQDN-Ziele, Entities wie world oder kube-apiserver und explizite Deny-Regeln.

Wie funktioniert eine L7-Policy in Cilium?

eBPF leitet den Port an einen Envoy-Proxy auf dem Node. Envoy prüft Methode und Pfad und antwortet bei Verstoss mit 403.

Wie funktioniert toFQDNs?

Ciliums DNS-Proxy beobachtet DNS-Antworten und lernt Name-zu-IP. Dafür braucht die Policy eine dns-Regel auf Port 53.

Was ist Hubble?

Die Observability-Schicht von Cilium. Sie zeigt jeden Flow mit Quelle, Ziel und Verdict, dazu eine Service-Map und Prometheus-Metriken.

Kann Cilium kube-proxy ersetzen?

Ja. Cilium balanciert Services per eBPF. Dann gibt es keine iptables-Regeln von kube-proxy mehr.

NetworkPolicy vs Service Mesh?

Policy filtert Verbindungen. Ein Mesh bringt zusätzlich mTLS, Identität per Zertifikat und Traffic-Steuerung, aber mehr Betriebslast.

Wie erlaubt man Verkehr aus einem anderen Namespace?

Mit namespaceSelector auf kubernetes.io/metadata.name, optional im selben Element mit podSelector für bestimmte Pods.

Wie testen Sie eine Policy?

Mit nc oder curl aus einem erlaubten und einem nicht erlaubten Pod. Dazu hubble observe --verdict DROPPED als Beweis.

Warum sind Labels sicherheitsrelevant?

Policies wählen per Label. Wer Labels frei setzt, kann sich Zugang verschaffen. Darum Labels per Admission kontrollieren.

Szenario: Nach dem Ausrollen von deny-all laufen alle Pods in Timeouts. Was ist los?

Fast sicher fehlt DNS-Egress zu CoreDNS. Ich rolle allow-dns aus und prüfe mit hubble observe --protocol dns.

Szenario: Der api-Pod erreicht die Datenbank nicht, obwohl eine Ingress-Policy existiert. Wie suchen Sie?

Labels mit --show-labels prüfen, dann ob api Egress-isoliert ist. hubble observe zeigt, ob der Drop bei EGRESS oder INGRESS passiert.

Szenario: Ein Pod darf nur einen externen Azure-Dienst erreichen, dessen IPs wechseln. Wie lösen Sie das?

Mit Cilium toFQDNs und einer dns-Regel, oder mit einem Private Endpoint mit fester IP und ipBlock. ipBlock auf öffentliche Cloud-IPs veraltet schnell.
