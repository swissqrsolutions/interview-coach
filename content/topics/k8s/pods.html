Pods: Container, Sidecar, Init Container

Kubernetes · Tier 1 · Quellen: kubernetes.io Docs „Pods“, „Pod Lifecycle“, „Init Containers“, „Sidecar Containers“ (stable seit 1.33), „Ephemeral Containers“, „Debug Running Pods“, „Resize CPU and Memory Resources assigned to Containers“ (Stand Kubernetes 1.37)

Kern: Ein Pod ist die kleinste Einheit, die Kubernetes plant und startet. Er ist eine Gruppe von Containern mit gemeinsamer IP, gemeinsamen Volumes und gleichem Node. Init Container laufen vorher einmal, Sidecars laufen neben der App, Ephemeral Container kommen nur zum Debuggen dazu.

1. Wo sitzt ein Pod?

  1. Pod Sandbox: die Hülle des Pods. Die Runtime legt sie zuerst an, oft mit einem kleinen pause-Container. Sie hält den Netzwerk-Namespace.
  2. App-Container (spec.containers): die eigentliche Anwendung. Beispiel: Spring-Boot-Service auf Port 8080.
  3. Init Container (spec.initContainers): laufen nacheinander bis zum Ende, bevor die App startet. Beispiel: auf die Datenbank warten, Schema migrieren.
  4. Sidecar: ein Init Container mit restartPolicy: Always. Er startet vor der App und läuft die ganze Zeit mit. Beispiel: Log-Shipper, Proxy.
  5. Ephemeral Container (spec.ephemeralContainers): wird zur Laufzeit zum Debuggen hinzugefügt. Beispiel: Shell mit curl in einem distroless-Pod.
  6. Gemeinsam: eine IP, ein Port-Raum, localhost zwischen Containern, Volumes. Nicht gemeinsam: Dateisystem des Images, Prozess-Namespace (ausser mit shareProcessNamespace: true).

2. Die Reise eines Pods (die Geschichte zum Merken)

  1. Pending. Der Pod existiert im API-Server. Er wartet auf einen Node oder auf das Image-Pull. Bleibt er hier hängen: zu wenig Ressourcen, Taints, fehlendes PVC.
  2. Init Container laufen. Der kubelet startet sie einzeln und nacheinander. Jeder muss mit Exit-Code 0 enden. Scheitert einer, startet der kubelet ihn neu (ausser bei restartPolicy: Never, dann ist der Pod Failed). Status: Init:0/2.
  3. Sidecars starten. Sie stehen auch in initContainers, an ihrer Position. Der kubelet wartet, bis ihr startupProbe erfolgreich ist oder der Prozess läuft. Dann geht es weiter.
  4. Running. Die App-Container starten parallel. Liveness, Readiness und Startup Probes laufen. Erst wenn alle Readiness Probes grün sind, ist der Pod Ready und bekommt Service-Traffic.
  5. Absturz. Ein Container endet. Der kubelet startet ihn nach der restartPolicy neu, mit wachsender Wartezeit. Das ist CrashLoopBackOff. Der Pod bleibt auf demselben Node, die IP bleibt.
  6. Ende. Beim Löschen läuft der preStop-Hook, dann kommt SIGTERM. Nach terminationGracePeriodSeconds (Standard 30 s) folgt SIGKILL. Sidecars stoppen erst nach der App.

3. Beispiel: Init Container, Sidecar und Debug

apiVersion: v1
kind: Pod
metadata: { name: web, namespace: demo-pods }
spec:
  restartPolicy: Always
  initContainers:
  - name: wait-db                      # klassischer Init Container
    image: busybox:1.36
    command: ['sh','-c','until nslookup db; do sleep 2; done']
  - name: log-shipper                  # native Sidecar
    image: busybox:1.36
    restartPolicy: Always
    command: ['sh','-c','tail -F /logs/app.log']
    volumeMounts: [{ name: logs, mountPath: /logs }]
  containers:
  - name: app
    image: busybox:1.36
    command: ['sh','-c','while true; do date >> /logs/app.log; sleep 5; done']
    volumeMounts: [{ name: logs, mountPath: /logs }]
  volumes:
  - name: logs
    emptyDir: {}
$ kubectl get pod web -n demo-pods -w
NAME   READY   STATUS     RESTARTS   AGE
web    0/2     Init:0/2   0          2s
web    0/2     Init:1/2   0          9s       # nach: kubectl create svc clusterip db --tcp=5432
web    1/2     PodInitializing  0     10s
web    2/2     Running    0          12s

$ kubectl logs web -c log-shipper -n demo-pods
Mon Nov 24 10:15:02 UTC 2026

$ kubectl debug -it web -n demo-pods --image=busybox:1.36 --target=app
/ # ps
PID   USER     COMMAND
    1 root     sh -c while true; do date >> /logs/app.log; sleep 5; done

  1. Init:0/2: Der Pod hängt im ersten Init Container, bis der Service db per DNS auflösbar ist.
  2. READY 2/2: Der Sidecar zählt als Container im READY-Wert, obwohl er in initContainers steht.
  3. App und Sidecar teilen das Volume logs. Der Sidecar sieht die Datei der App.
  4. kubectl debug --target=app fügt einen Ephemeral Container hinzu. Mit --target sieht er die Prozesse des App-Containers.

4. Details, die Interviewer fragen

  1. Pod-Phasen: Pending, Running, Succeeded, Failed, Unknown (Node nicht erreichbar). CrashLoopBackOff und Terminating sind keine Phasen, sondern Anzeigen von kubectl.
  2. Container-Zustände: Waiting (mit Grund, z. B. ImagePullBackOff), Running, Terminated (mit Exit-Code und Grund, z. B. OOMKilled).
  3. Pod Conditions: PodScheduled, PodReadyToStartContainers, Initialized, ContainersReady, Ready. Services nutzen nur Ready.
  4. restartPolicy (Pod-Ebene): Always (Standard, für Deployments), OnFailure (nur bei Exit-Code ≠ 0, für Jobs), Never. Sie gilt für App-Container und Init Container.
  5. Restart-Backoff: 10 s, 20 s, 40 s … bis max. 5 Minuten. Nach 10 Minuten stabilem Lauf setzt der kubelet den Backoff zurück.
  6. Native Sidecar: ein Init Container mit restartPolicy: Always. Stable seit 1.33. Er startet vor der App, darf Probes haben, stoppt nach der App und blockiert das Ende eines Jobs nicht.
  7. Alter Sidecar-Stil: ein zweiter normaler Container. Problem: keine Startreihenfolge, und in einem Job endet der Pod nie, weil der Sidecar weiterläuft.
  8. Init Container: keine Readiness/Liveness Probes, laufen nacheinander, müssen erfolgreich enden. Sie sollen idempotent sein, weil sie bei einem Pod-Neustart erneut laufen.
  9. Ressourcen mit Init Containern: Der effektive Request ist das Maximum aus dem grössten Init Container und der Summe aller App-Container plus Sidecars.
  10. Ephemeral Container: stable seit 1.25. Keine Ports, keine Probes, keine Ressourcen-Garantie. Man kann sie nicht entfernen oder neu starten. Ideal für distroless-Images ohne Shell.
  11. Graceful Shutdown: Beim Löschen entfernt der EndpointSlice-Controller den Pod aus dem Service. Gleichzeitig kommt SIGTERM. Darum braucht die App einen kurzen preStop-Sleep oder muss Requests noch kurz annehmen.
  12. Pod ist kurzlebig: Ein gelöschter Pod kommt nie zurück. Ein Controller erzeugt einen neuen Pod mit neuem Namen und neuer IP.
  13. In-Place Resize: CPU und Memory eines laufenden Pods ändern, ohne Neustart (kubectl patch --subresource resize). GA seit 1.35.

5. Vergleich

  • Init Container: läuft vorher, einmal, muss enden. Für Vorbereitung.
  • Native Sidecar: läuft vorher an und dann die ganze Zeit. Für Hilfsdienste mit sauberer Start- und Stopp-Reihenfolge.
  • Zweiter App-Container: startet parallel, keine Reihenfolge. Nur noch für echte gleichwertige Prozesse.
  • Ephemeral Container: nur zum Debuggen, nachträglich, ohne Garantien.
  • Pod vs Container: Ein Container ist ein Prozess mit Image. Ein Pod ist die geplante Einheit mit Netzwerk und Volumes.
  • Pod vs Deployment: Ein nackter Pod wird nach einem Node-Ausfall nicht ersetzt. Ein Deployment ersetzt ihn.
  • Sidecar vs DaemonSet: Ein Sidecar läuft pro Pod. Ein DaemonSet läuft einmal pro Node, z. B. für Log-Sammlung aller Pods.

6. In der Produktion

  1. CrashLoopBackOff: App stürzt beim Start ab, z. B. fehlende Config oder Secret. Lösung: kubectl logs --previous, Exit-Code prüfen.
  2. OOMKilled (Exit-Code 137): Container überschreitet sein Memory-Limit. Lösung: Limit an echte Nutzung anpassen, bei Java Heap über MaxRAMPercentage steuern.
  3. Pod hängt in Init:0/1: Init Container wartet auf einen Dienst, der nie kommt. Lösung: Logs des Init Containers, Timeout einbauen.
  4. 502 beim Rolling Update: Pod bekommt SIGTERM, bevor alle Load Balancer ihn entfernt haben. Lösung: preStop mit kurzem Sleep, Graceful Shutdown in der App.
  5. Job endet nie: Ein klassischer Sidecar (z. B. Proxy) läuft weiter. Lösung: native Sidecar mit restartPolicy: Always in initContainers.
  6. Kein Debuggen möglich: distroless-Image ohne Shell. Lösung: kubectl debug mit Ephemeral Container oder Kopie des Pods (--copy-to).
  7. Pod hängt in Terminating: Finalizer oder Node nicht erreichbar. Lösung: Finalizer prüfen. --force --grace-period=0 nur, wenn sicher ist, dass der Prozess wirklich weg ist.

7. Diagnose: Werkzeuge und Befehle

  • kubectl get pod -o wide: Status, Restarts, Node, IP.
  • kubectl describe pod <p>: Events, Conditions, Last State mit Exit-Code und Grund.
  • kubectl logs <p> -c <container> --previous: Log des abgestürzten Containers.
  • kubectl get pod <p> -o jsonpath='{.status.containerStatuses[*].lastState}': Grund des letzten Endes.
  • kubectl debug -it <p> --image=busybox --target=<c>: Ephemeral Container.
  • kubectl debug node/<n> -it --image=busybox: Debug-Pod direkt auf dem Node.
  • kubectl exec -it <p> -c <c> -- sh: in einen laufenden Container.
  • kubectl events --for pod/<p>: nur die Events dieses Pods.

8. Senior-Punkte

  1. Ein Pod, ein Hauptprozess. Mehrere Container nur, wenn sie eng gekoppelt sind und gemeinsam skalieren.
  2. Native Sidecars lösen echte alte Probleme: Startreihenfolge, Shutdown-Reihenfolge, Jobs mit Proxy. Neue Sidecars sollten so gebaut werden.
  3. Init Container vs Job: Eine DB-Migration im Init Container läuft bei jedem Pod und jeder Replica. Ein separater Job (z. B. Helm-Hook oder Argo-CD-Hook) läuft einmal pro Release.
  4. Pods sind Vieh, keine Haustiere. Keine Daten im Container-Dateisystem. Zustand in Volumes oder externe Dienste.
  5. Graceful Shutdown ist Pflicht. SIGTERM behandeln, preStop setzen, Grace Period passend zur längsten Anfrage.
  6. Distroless + Ephemeral Container ist ein gutes Paar: kleine Angriffsfläche im Betrieb, trotzdem debuggbar.

10. Fallen

  • „CrashLoopBackOff ist eine Pod-Phase.“ → Falsch. Die Phase ist meist Running. CrashLoopBackOff ist der Waiting-Grund eines Containers.
  • „Container in einem Pod teilen das Dateisystem.“ → Falsch. Nur gemountete Volumes sind gemeinsam.
  • „Ein neu gestarteter Container bekommt eine neue IP.“ → Falsch. Die IP gehört dem Pod. Nur ein neuer Pod bekommt eine neue IP.
  • „Init Container laufen parallel.“ → Falsch. Sie laufen nacheinander. Erst danach starten die App-Container parallel.
  • „Sidecar ist einfach ein zweiter Container.“ → Veraltet. Seit 1.33 stable: Init Container mit restartPolicy: Always.
  • „Mit kubectl exec kann man jeden Pod debuggen.“ → Falsch. Ohne Shell im Image geht es nicht. Dafür gibt es Ephemeral Container.

11. Fragen

Was ist ein Pod?

Die kleinste planbare Einheit. Ein oder mehrere Container mit gemeinsamer IP, gemeinsamen Volumes und gleichem Node.

Warum plant Kubernetes Pods und nicht Container?

Eng gekoppelte Container brauchen denselben Node, dasselbe Netzwerk und gemeinsame Dateien. Der Pod garantiert das.

Was teilen Container in einem Pod?

Netzwerk-Namespace (IP, Ports, localhost), Volumes und optional den Prozess-Namespace. Nicht das Image-Dateisystem.

Welche Pod-Phasen gibt es?

Pending, Running, Succeeded, Failed, Unknown.

Welche Container-Zustände gibt es?

Waiting, Running, Terminated. Waiting und Terminated haben einen Grund, z. B. ImagePullBackOff oder OOMKilled.

Was ist ein Init Container?

Ein Container, der vor der App einmal bis zum Ende läuft. Mehrere laufen nacheinander. Beispiel: auf eine Abhängigkeit warten oder Dateien vorbereiten.

Was ist ein nativer Sidecar?

Ein Init Container mit restartPolicy: Always. Er startet vor der App, läuft weiter und stoppt nach ihr. Stable seit 1.33.

Welche Probleme lösen native Sidecars?

Startreihenfolge (Proxy vor der App), Stopp-Reihenfolge (Logs bis zum Ende) und Jobs, die wegen eines Sidecars nie fertig wurden.

Welche restartPolicy-Werte gibt es?

Always, OnFailure, Never. Deployments brauchen Always, Jobs nutzen OnFailure oder Never.

Was ist CrashLoopBackOff?

Ein Container stürzt immer wieder ab. Der kubelet wartet zwischen den Neustarts immer länger, bis max. 5 Minuten.

Was ist ein Ephemeral Container?

Ein Container, der zur Laufzeit zum Debuggen in einen Pod kommt. Keine Ports, keine Probes, nicht entfernbar. Start mit kubectl debug.

Was passiert beim Löschen eines Pods?

Pod wird Terminating und aus den EndpointSlices entfernt. preStop läuft, dann SIGTERM. Nach der Grace Period (Standard 30 s) kommt SIGKILL.

Was bedeutet Exit-Code 137?

128 + 9, also SIGKILL. Meist OOMKilled durch das Memory-Limit, oder Abbruch nach der Grace Period.

Wann ist ein Pod Ready?

Wenn alle Container (inkl. Sidecars mit Readiness Probe) ready sind und alle Readiness Gates erfüllt sind. Erst dann bekommt er Service-Traffic.

Wie berechnet sich der Ressourcenbedarf mit Init Containern?

Das Maximum aus dem grössten Init-Container-Request und der Summe von App-Containern plus Sidecars.

Warum sollen Init Container idempotent sein?

Sie laufen bei jedem Pod-Neustart erneut. Ein zweiter Lauf darf nichts kaputt machen.

Wie debuggen Sie einen Pod ohne Shell?

kubectl debug mit Ephemeral Container und --target, oder eine Kopie des Pods mit --copy-to und anderem Image.

Kann man CPU und Memory eines laufenden Pods ändern?

Ja, mit In-Place Resize über die resize-Subresource, GA seit 1.35. Vorher nur mit neuem Pod.

Was ist der pause-Container?

Ein winziger Container, der den Netzwerk-Namespace der Pod Sandbox hält. Die anderen Container treten diesem Namespace bei.

Szenario: Ein Job wird nie Completed, obwohl die Arbeit fertig ist. Warum?

Wahrscheinlich läuft ein klassischer Sidecar (z. B. Proxy) als normaler Container weiter. Lösung: ihn als nativen Sidecar in initContainers mit restartPolicy: Always definieren.

Szenario: Bei jedem Deployment gibt es ein paar 502-Fehler. Was prüfen Sie?

Den Shutdown: SIGTERM kommt, bevor der Load Balancer den Pod entfernt hat. Lösung: preStop mit kurzem Sleep, Graceful Shutdown in der App, Readiness Probe korrekt.

Szenario: Ein Pod hat 40 Restarts und Exit-Code 137. Was tun Sie?

describe zeigt OOMKilled. Memory-Nutzung in Prometheus/Grafana prüfen, Limit anpassen oder Speicher in der App senken (z. B. Java-Heap-Einstellung).
