Reihenfolge und Keys

Kern: Kafka garantiert Reihenfolge nur innerhalb einer Partition, nicht über das ganze Topic. Der Key einer Nachricht bestimmt die Partition. Darum ist die Wahl des Keys die eigentliche Entscheidung über Reihenfolge, Lastverteilung und Skalierung.

1. Wo sitzt die Reihenfolge?

  1. Producer: Er schickt eine Nachricht mit Key, z. B. die ID einer Steuererklärung.
  2. Partitioner: Er rechnet den Hash des Keys. Standard ist murmur2, eine schnelle Hash-Funktion. Partition = Hash modulo Anzahl Partitionen.
  3. Partition: Sie ist ein Append-only Log, also ein Log, an das nur angehängt wird. Jede Nachricht bekommt einen Offset, eine fortlaufende Nummer.
  4. Consumer: In einer Consumer Group liest genau ein Consumer eine Partition. Er liest in Offset-Reihenfolge.
  5. Folge: Alle Events eines Keys sind geordnet. Events verschiedener Keys haben keine feste Reihenfolge zueinander.

2. Die Reise einer Nachricht durch den idempotenten Producer

  1. send(): Die Anwendung ruft send(record) auf. Der Partitioner wählt die Partition aus dem Key.
  2. Batch: Der Producer sammelt Nachrichten pro Partition in einem Batch. Er wartet dafür bis linger.ms (Standard seit Kafka 4.0: 5 ms). Jeder Batch trägt Producer-ID (PID), Epoch und eine Sequence Number pro Partition.
  3. In-Flight: Der Producer schickt bis zu max.in.flight.requests.per.connection Requests ohne Antwort ab. Standard: 5. Das erhöht den Durchsatz.
  4. Leader prüft: Der Partition-Leader merkt sich die letzten Sequenzen pro Producer. Er erwartet immer die nächste Nummer.
  5. Fall a: Die Nummer passt, also hängt er an. Kommt ein Batch doppelt (Retry nach verlorenem Ack), erkennt er die Nummer und schreibt nichts zweimal.
  6. Fall b: Batch 1 ist gescheitert, Batch 2 kommt zuerst an. Der Leader sieht eine Lücke und lehnt Batch 2 ab. Der Producer schickt beide in richtiger Reihenfolge neu.
  7. Ergebnis: Mit Idempotenz bleibt die Reihenfolge auch bei 5 Requests in-flight und Retries. Ohne Idempotenz kann Batch 2 vor Batch 1 landen.

3. Beispiel: den Partitioner nachrechnen

# partitioner.py – Nachbau von Kafka Utils.murmur2 (Seed 0x9747b28c)
def partition(key: str, n: int) -> int:
    return (murmur2(key.encode()) & 0x7fffffff) % n

            for i in range(10000))

  1. Der Producer rechnet murmur2(keyBytes), macht das Ergebnis positiv (& 0x7fffffff) und nimmt Modulo Anzahl Partitionen.
  2. Die Rechnung ist deterministisch: Gleicher Key und gleiche Partitionszahl ergeben immer die gleiche Partition.
  3. Von 6 auf 8 Partitionen wechseln ca. 75 % aller Keys die Partition. Alte Events eines Keys liegen dann in P5, neue in P3.
  4. Ein Consumer kann so ein neues Event vor einem alten Event desselben Keys verarbeiten. Die Reihenfolge pro Key ist für die Übergangszeit gebrochen.

4. Details, die Interviewer fragen

  1. Garantie pro Partition: Nachrichten eines Producers an eine Partition stehen in Sende-Reihenfolge im Log. Ein Consumer sieht sie in Offset-Reihenfolge.
  2. Kein globales Ordering: Über Partitionen und Topics gibt es keine Reihenfolge. Globale Reihenfolge heisst: genau eine Partition. Dann skaliert nur ein Consumer.
  3. Default-Partitioner mit Key: murmur2(key) % numPartitions. Der Key wird vorher serialisiert. Andere Serializer ergeben also andere Partitionen.
  4. Default-Partitioner ohne Key: Der Sticky Partitioner füllt einen Batch für eine Partition und wechselt dann. Seit KIP-794 (Kafka 3.3) wechselt er nach batch.size Bytes und bevorzugt schnelle Broker. Ohne Key gibt es keine Reihenfolge zwischen Events.
  5. partitioner.ignore.keys=true: Der Producer ignoriert den Key bei der Partitionswahl. Der Key bleibt in der Nachricht, z. B. für Compaction.
  6. Eigener Partitioner: partitioner.class setzt eine eigene Klasse. Typisch: VIP-Kunden auf eigene Partitionen. Risiko: Alle Producer müssen dieselbe Logik nutzen.
  7. Explizite Partition: new ProducerRecord(topic, partition, key, value) umgeht den Partitioner ganz.
  8. Retries und Umordnung: Ohne Idempotenz, mit retries > 0 und max.in.flight > 1 kann ein Retry Batch 1 hinter Batch 2 schieben. Früher half nur max.in.flight=1, auf Kosten des Durchsatzes.
  9. Idempotenter Producer: Er ist seit Kafka 3.0 Standard (enable.idempotence=true). Er braucht acks=all, retries > 0 und max.in.flight ≤ 5. Dann bleibt die Reihenfolge erhalten und Duplikate durch Retries verschwinden.
  10. Warum maximal 5: Der Broker speichert pro Producer und Partition den Zustand der letzten 5 Batches. Mehr in-flight kann er nicht prüfen.
  11. Sequence Number: Die Sequence Number ist ein Zähler pro Producer-ID und Partition. Lücke → OutOfOrderSequenceException, Wiederholung → Duplikat wird verworfen.
  12. Grenze der Idempotenz: Sie gilt nur pro Producer-Session. Startet der Producer neu, bekommt er eine neue PID. Über Neustarts schützt erst ein transactional.id.
  13. Partitionen erweitern: --alter --partitions ändert n im Modulo. Viele Keys landen auf einer neuen Partition. Verkleinern geht gar nicht.
  14. Hot Key: Ein Hot Key ist ein Key mit sehr viel Traffic. Seine Partition ist überlastet, ihr Consumer hat Lag, die anderen sind leer. Mehr Partitionen helfen nicht, denn ein Key bleibt auf einer Partition.
  15. Consumer-Seite: Ein Consumer verarbeitet eine Partition sequenziell. Verarbeitet er Records parallel in einem Thread-Pool, ist die Reihenfolge weg. Lösung: Parallelität pro Key, nicht pro Record.
  16. Rebalancing: Bei einem Rebalance wechselt eine Partition den Consumer. Der neue liest ab dem letzten Commit. Es gibt Duplikate, aber die Reihenfolge pro Partition bleibt.
  17. Retry-Topics brechen Reihenfolge: Ein fehlerhaftes Event geht in ein Retry-Topic. Spätere Events desselben Keys laufen vorbei. Die Spring-Kafka-Doku sagt das ausdrücklich.
  18. Versionsnummer im Event: Eine fachliche Version pro Entity (z. B. version=7) lässt den Consumer veraltete Events erkennen. Das schützt auch über Partitionen und Neustarts hinweg.

5. Vergleich

  • Key = Entity-ID (z. B. Erklärungs-ID): Reihenfolge pro Entity, gute Verteilung bei vielen Entities. Der Normalfall.
  • Key = Mandant oder Kanton: Reihenfolge pro Mandant, aber grosse Mandanten werden Hot Keys.
  • Kein Key: beste Verteilung, keine Reihenfolge. Gut für Logs und Metriken.
  • Zusammengesetzter Key (z. B. kunde:auftrag): feinere Verteilung, Reihenfolge nur pro Kombination.
  • Salting (Key + Zufallszahl 0–9): verteilt einen Hot Key auf 10 Partitionen. Preis: Reihenfolge des ursprünglichen Keys ist weg.
  • Eine Partition: globale Reihenfolge, aber nur ein aktiver Consumer und ein Leader-Broker als Engpass.
  • RabbitMQ / Service Bus: Reihenfolge pro Queue bei einem Consumer. Service Bus Sessions geben Reihenfolge pro Session-ID, ähnlich wie ein Key.
  • Event Hubs: Partition Key wie in Kafka. Reihenfolge nur pro Partition.

6. In der Produktion

  1. „Status DONE kam vor CREATED“: Die Events hatten verschiedene Keys oder keinen Key. Lösung: Entity-ID als Key, und alle Producer dieses Topics nutzen denselben Key.
  2. Partitionen erweitert, danach falsche Zustände: Alte und neue Events eines Keys lagen in verschiedenen Partitionen. Lösung: Partitionszahl am Anfang grosszügig wählen. Sonst neues Topic anlegen, Producer umstellen, altes Topic leer laufen lassen.
  3. Eine Partition mit riesigem Lag: Ein Hot Key. Lösung: feineren Key wählen oder die Last fachlich aufteilen. Nur salzen, wenn Reihenfolge dort egal ist.
  4. Umordnung nach Retries: Jemand hat enable.idempotence=false gesetzt, aber max.in.flight=5 gelassen. Lösung: Idempotenz an lassen. Achtung: Widersprüchliche Configs schalten sie ohne Fehler aus, wenn sie nicht explizit aktiviert ist.
  5. Thread-Pool im Listener: Ein Team verarbeitet Records parallel für mehr Speed. Lösung: mehr Partitionen und Consumer oder Parallelität pro Key.
  6. Retry-Topic überholt: Event 1 ist im Retry-Topic, Event 2 desselben Keys ist schon verarbeitet. Lösung: Blocking Retry für ordnungskritische Topics oder Versionsprüfung im Consumer.
  7. Verschiedene Producer-Sprachen: Ein Nicht-Java-Client nutzt einen anderen Hash. Beispiel: librdkafka-Standard ist consistent_random (CRC32). Gleicher Key, andere Partition. Lösung: dort partitioner=murmur2_random setzen, das entspricht dem Java-Default.

7. Diagnose: Werkzeuge und Befehle

  • kafka-topics.sh --describe --topic X: Anzahl Partitionen, Leader, Replikate.
  • kafka-consumer-groups.sh --describe --group G: Lag pro Partition. Eine Partition mit viel Lag deutet auf einen Hot Key.
  • kafka-console-consumer.sh --property print.key=true --property print.partition=true --property print.offset=true: welcher Key in welcher Partition liegt.
  • kafka-get-offsets.sh --topic X: End-Offsets pro Partition. Grosse Unterschiede zeigen eine schiefe Verteilung.
  • Producer-Metriken: record-retry-rate, record-error-rate. Retries sind der Ort, wo Umordnung entsteht.
  • Producer-Log beim Start: Die Zeile mit enable.idempotence zeigt die echten Werte. So sieht man stille Abschaltung.
  • Consumer-Log: Key, Partition, Offset und fachliche Version loggen. Dann sieht man Umordnung direkt.

8. Senior-Punkte

  1. Reihenfolge ist eine fachliche Frage. Erst klären, wofür sie gilt: pro Erklärung, pro Kunde, oder gar nicht. Dann den Key daraus ableiten.
  2. Partitionszahl früh und grosszügig planen. Erweitern bricht die Key-Zuordnung, verkleinern geht nicht. Ziel-Durchsatz geteilt durch Durchsatz pro Consumer, plus Reserve.
  3. Nicht blind auf Reihenfolge vertrauen. Ein Consumer mit Versionsprüfung oder Zustandsautomat ist robust gegen Duplikate, Retries und Umordnung.
  4. Idempotenz ist Standard und soll es bleiben. Sie kostet fast nichts und schützt Reihenfolge und Duplikate bei Retries.
  5. Reihenfolge und Parallelität sind ein Tausch. Mehr Reihenfolge heisst weniger Parallelität. Die Grenze ist die Partition.
  6. Fehlerbehandlung entscheidet mit. Non-blocking Retries und DLT geben Durchsatz, aber nehmen Reihenfolge. Für ordnungskritische Flüsse bewusst blockieren.

10. Fallen

  • „Kafka garantiert die Reihenfolge im Topic.“ → Falsch. Nur pro Partition.
  • „Mehr Partitionen lösen einen Hot Key.“ → Falsch. Ein Key landet immer auf genau einer Partition.
  • „Partitionen kann man später gefahrlos erhöhen.“ → Falsch bei Topics mit Keys. Die Key→Partition-Zuordnung ändert sich.
  • „Für Reihenfolge braucht man max.in.flight=1.“ → Veraltet. Mit Idempotenz reichen bis zu 5.
  • „Idempotenz verhindert alle Duplikate.“ → Falsch. Nur Retries innerhalb einer Producer-Session. Consumer-Duplikate bleiben.
  • „Ohne Key gibt es Round Robin pro Nachricht.“ → Falsch. Der Sticky Partitioner füllt Batches pro Partition.

11. Fragen

Welche Reihenfolge garantiert Kafka?

Nur innerhalb einer Partition. Dort sind Nachrichten in Schreib-Reihenfolge, und Consumer lesen in Offset-Reihenfolge.

Wie bestimmt der Key die Partition?

Der Default-Partitioner rechnet murmur2 über die serialisierten Key-Bytes, macht das Ergebnis positiv und nimmt Modulo Anzahl Partitionen.

Was passiert mit Nachrichten ohne Key?

Der Sticky Partitioner füllt einen Batch für eine Partition und wechselt dann. Es gibt keine Reihenfolge zwischen diesen Nachrichten.

Wie bekomme ich globale Reihenfolge?

Nur mit einer Partition. Dann arbeitet nur ein Consumer pro Gruppe, und ein Broker trägt die ganze Last.

Wie wählen Sie einen Key?

Nach der fachlichen Einheit, die geordnet sein muss, meist die Entity-ID. Dazu prüfen: genug verschiedene Werte, kein Key mit extrem viel Traffic.

Was ist ein Hot Key?

Ein Key mit sehr viel Traffic. Seine Partition und ihr Consumer sind überlastet, während andere wenig zu tun haben.

Wie lösen Sie einen Hot Key?

Feineren Key wählen oder den Fluss fachlich teilen. Salting verteilt die Last, opfert aber die Reihenfolge dieses Keys.

Warum kann ein Retry die Reihenfolge ändern?

Mit mehreren Requests in-flight kann Batch 1 scheitern und Batch 2 gelingen. Der Retry von Batch 1 landet dann hinter Batch 2.

Wie verhindert der idempotente Producer Umordnung?

Jeder Batch hat PID und Sequence Number pro Partition. Der Leader nimmt nur die erwartete nächste Nummer an und lehnt Batches nach einer Lücke ab.

Warum darf max.in.flight mit Idempotenz höchstens 5 sein?

Der Broker speichert pro Producer und Partition nur die letzten 5 Batches. Mehr kann er nicht auf Duplikate und Lücken prüfen.

Welche Voraussetzungen hat die Idempotenz?

acks=all, retries > 0, max.in.flight ≤ 5. Seit Kafka 3.0 sind das die Standardwerte.

Was passiert bei widersprüchlicher Config?

Ist Idempotenz explizit an, gibt es eine ConfigException. Ist sie nur Standard, schaltet Kafka sie still ab.

Was ist eine Sequence Number im Producer?

Ein Zähler pro Producer-ID und Partition. Der Broker erkennt damit Duplikate und Lücken.

Schützt die Idempotenz über einen Producer-Neustart?

Nein. Ein Neustart bringt eine neue PID. Dafür braucht es eine transactional.id.

Was passiert, wenn ich Partitionen hinzufüge?

Das Modulo ändert sich, viele Keys wechseln die Partition. Alte und neue Events eines Keys liegen getrennt, die Reihenfolge bricht.

Kann ich Partitionen reduzieren?

Nein. Nur über ein neues Topic und Migration.

Wie verliert ein Consumer die Reihenfolge?

Durch parallele Verarbeitung von Records einer Partition, z. B. in einem Thread-Pool. Oder durch Retry-Topics, an denen spätere Events vorbeilaufen.

Bricht ein Rebalance die Reihenfolge?

Nein, pro Partition nicht. Der neue Consumer liest ab dem letzten Commit. Es können aber Duplikate entstehen.

Brechen non-blocking Retries die Reihenfolge?

Ja. Das fehlerhafte Event wartet im Retry-Topic, spätere Events desselben Keys laufen vorbei.

Was bringt eine Versionsnummer im Event?

Der Consumer erkennt veraltete oder doppelte Events und ignoriert sie. Das hilft auch über Partitionen und Neustarts hinweg.

Was macht partitioner.ignore.keys?

Der Producer wählt die Partition ohne Key, also sticky. Der Key bleibt in der Nachricht.

Wie skaliert man trotz Reihenfolge?

Viele Keys und genug Partitionen. Reihenfolge gilt pro Key, Parallelität entsteht über Partitionen.

Gibt es Reihenfolge über zwei Topics?

Nein. Braucht man sie, gehören die Events in ein Topic mit gleichem Key.

Szenario: Ein Consumer sieht „Erklärung eingereicht“ vor „Erklärung erstellt“. Was prüfen Sie?

Ob beide Events denselben Key haben und alle Producer ihn gleich setzen. Dann Partitionserweiterung, Retry-Topics und parallele Verarbeitung im Consumer prüfen.

Szenario: Das Team will das Topic von 6 auf 12 Partitionen erweitern. Was sagen Sie?

Bei Keys wechselt ein Grossteil der Keys die Partition, die Reihenfolge bricht kurz. Entweder Producer stoppen, Consumer leer laufen lassen, dann erweitern. Oder ein neues Topic anlegen und umstellen.

Szenario: Eine Partition hat 2 Mio. Lag, die anderen null. Was tun Sie?

Mit dem Console Consumer die Keys ansehen, wahrscheinlich ein Hot Key. Dann Key verfeinern oder fachlich aufteilen. Mehr Partitionen oder Consumer helfen nicht.
