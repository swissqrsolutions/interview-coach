Kafka vs RabbitMQ vs Event Hub vs Solace

Kern: Kafka und Event Hubs sind ein Log: Nachrichten bleiben nach dem Lesen liegen und lassen sich erneut lesen. RabbitMQ und Service Bus sind Queues: Eine Nachricht verschwindet nach dem Ack, dafür gibt es Routing, Ack pro Nachricht und DLQ. Solace ist ein Event Broker mit feinem Topic-Routing über viele Standorte. Die Wahl hängt am Muster: Event-Stream mit Replay oder Arbeitsauftrag mit Zustellung.

1. Wo sitzen die vier Systeme?

  1. Kafka: Ein verteiltes, partitioniertes Commit Log. Consumer ziehen Daten (Pull) und merken sich ihren Offset. Jede Consumer Group liest unabhängig.
  2. Azure Event Hubs: Ein verwaltetes Log in Azure. Gleiches Modell wie Kafka (Namespace = Cluster, Event Hub = Topic). Es spricht AMQP und, ab Standard-Tier, das Kafka-Protokoll.
  3. RabbitMQ: Ein Broker mit Exchanges (Verteiler nach Regeln) und Queues. Er schiebt Nachrichten zum Consumer (Push mit Prefetch). Nach dem Ack ist die Nachricht weg.
  4. Azure Service Bus: Verwaltete Enterprise-Queues und Topics mit Subscriptions und Filtern. Dazu Sessions, DLQ, geplante Nachrichten, Duplikaterkennung.
  5. Solace PubSub+: Ein Event Broker mit hierarchischen Topics pro Nachricht. Mehrere Broker bilden ein Event Mesh über Standorte und Clouds.

2. Die Reise einer Entscheidung

  1. Fakt oder Auftrag? Ein Event beschreibt, was passiert ist („Erklärung eingereicht“). Viele Systeme lesen es, auch später. Ein Command ist ein Auftrag („PDF erzeugen“). Genau ein Worker soll ihn erledigen.
  2. Fakt → Log: Replay, mehrere unabhängige Leser, hoher Durchsatz, Reihenfolge pro Key. Das ist Kafka oder Event Hubs.
  3. Log selbst betreiben? Kafka gibt alle Features: Transaktionen, Compaction, Kafka Streams, Connect, lange Retention. Event Hubs nimmt den Betrieb ab, hat aber Quotas und Lücken.
  4. Auftrag → Queue: Ack pro Nachricht, Wettbewerb mehrerer Worker, Routing, Verzögerung, DLQ. Das ist RabbitMQ oder Service Bus.
  5. Azure oder portabel? Service Bus ist voll verwaltet und mit Entra ID und Private Endpoints integriert. RabbitMQ läuft überall, braucht aber Betrieb.
  6. Sonderfall Solace: Hybride Landschaften mit vielen Standorten, MQTT-Geräten oder JMS-Altsystemen. Dort zählt das Event Mesh.

3. Beispiel: Kafka-Client auf Event Hubs umstellen

# Vorher: eigener Kafka-Cluster
bootstrap.servers=kafka-1:9092,kafka-2:9092,kafka-3:9092

# Nachher: Event Hubs Kafka-Endpoint (Standard, Premium oder Dedicated)
bootstrap.servers=NAMESPACENAME.servicebus.windows.net:9093
security.protocol=SASL_SSL
sasl.mechanism=OAUTHBEARER
sasl.jaas.config=org.apache.kafka.common.security.oauthbearer.OAuthBearerLoginModule required;
sasl.login.callback.handler.class=CustomAuthenticateCallbackHandler

# Alternative mit SAS (Connection String), weniger sicher:
# sasl.mechanism=PLAIN
# sasl.jaas.config=...PlainLoginModule required username="$ConnectionString" password="Endpoint=sb://...";

Erwartetes Ergebnis (laut Microsoft Learn, nicht ausgeführt): Der unveränderte Kafka-Producer schreibt in den Event Hub mit dem Namen des Topics. Ein AMQP-Consumer (z. B. eine Azure Function) kann dieselben Events lesen.

  1. Nur die Konfiguration ändert sich, der Code bleibt. Der Event Hub heisst wie das Kafka-Topic.
  2. Port 9093 und SASL_SSL sind Pflicht. TLS ist immer an.
  3. OAUTHBEARER mit Entra ID ist besser als der Connection String: RBAC statt geteiltem Schlüssel, keine Secrets im Repo.
  4. Prüfen vor der Migration: Event-Grösse (1 MB Standard), Retention (7 Tage Standard, 90 Premium), Partitionen (32 Standard), Consumer Groups (20 Standard), Compression (nur Premium/Dedicated), Transaktionen (Preview, nur Premium/Dedicated).

4. Details, die Interviewer fragen

  1. Log vs Queue: Im Log bleibt die Nachricht, jeder Leser hat seinen Offset. In der Queue wird sie nach dem Ack gelöscht, der Broker verwaltet den Zustand pro Nachricht.
  2. Retention und Replay: Kafka hält Daten nach Zeit oder Grösse, unabhängig vom Lesen. Replay = Offset zurücksetzen. Event Hubs: maximal 1 Tag (Basic), 7 Tage (Standard), 90 Tage (Premium/Dedicated). Queues haben kein Replay nach dem Ack.
  3. Routing: Kafka routet nur über Topic und Key. RabbitMQ hat direct, topic (mit * und #), fanout, headers. Service Bus hat SQL-Filter auf Subscriptions. Solace hat Topics pro Nachricht mit Wildcards * und >.
  4. Durchsatz: Kafka ist für sehr hohen Durchsatz gebaut: sequentielles Schreiben, Batches, Zero-Copy, Partitionen. Queues sind langsamer pro Knoten, weil sie Zustand pro Nachricht halten.
  5. Reihenfolge: Kafka und Event Hubs: pro Partition. RabbitMQ: pro Queue, aber nur mit einem Consumer (sonst Single Active Consumer). Service Bus: FIFO pro Session.
  6. Competing Consumers: In Kafka begrenzt die Partitionszahl die Parallelität. In Queues teilen sich beliebig viele Worker eine Queue. Kafka 4.2 bringt Share Groups (Queues for Kafka) produktionsreif: mehr Consumer als Partitionen, Ack pro Record.
  7. DLQ: RabbitMQ: Dead Letter Exchange, Quorum Queues mit delivery-limit 20 seit 4.0. Service Bus: eingebaute DLQ nach MaxDeliveryCount (Standard 10). Kafka und Event Hubs: keine, der Client baut sie.
  8. Verfügbarkeit: Kafka: ISR-Replikation, KRaft für Metadaten. RabbitMQ 4: Quorum Queues mit Raft, Classic Mirrored Queues sind entfernt. Event Hubs und Service Bus: von Microsoft betrieben, mit Zonen.
  9. RabbitMQ Streams: RabbitMQ hat seit 3.9 auch ein Log (Streams) mit Replay. Für grosse Event-Streams bleibt Kafka das Standardwerkzeug.
  10. Event Hubs Checkpoints: Mit dem Kafka-Endpoint speichert Event Hubs Offsets wie Kafka. Mit dem AMQP-SDK speichert der Event Processor die Checkpoints in Blob Storage.
  11. Event Hubs Capture: schreibt Events automatisch als Avro oder Parquet nach Blob oder ADLS. Gut für Archiv und Analyse.
  12. Event Hubs Skalierung: Standard: Throughput Units, je 1 MB/s rein und 2 MB/s raus. Premium: Processing Units. Partitionen lassen sich in Standard nicht nachträglich erhöhen.
  13. Service Bus Features: Peek-Lock (erst sperren, dann bestätigen), Sessions, geplante Nachrichten, Deferral, Duplikaterkennung, Transaktionen. Nachricht bis 256 KB (Standard). Premium: Standard 1 MB pro Entity, per AMQP bis 100 MB einstellbar.
  14. Solace Features: Direct Messaging (schnell, ohne Persistenz), Guaranteed Messaging (persistente Queues mit Topic-Abos), Replay Log, Dead Message Queue, Protokolle SMF, AMQP, MQTT, JMS, REST.
  15. Betrieb: Kafka selbst: Broker, KRaft-Controller, Partitionen, Rebalancing, Upgrades, Monitoring. Managed (Event Hubs, Confluent Cloud, MSK) nimmt das ab, kostet aber Flexibilität.
  16. Event Grid: ein weiterer Azure-Dienst. Er verteilt reaktive Events (z. B. „Blob erstellt“, Defender-Ergebnis) per Push an Handler. Kein Stream, keine Retention für Replay.

5. Vergleich

  • Modell: Kafka, Event Hubs = Log mit Pull. RabbitMQ, Service Bus = Queue mit Push oder Lock. Solace = Broker mit Topic-Routing und Queues.
  • Replay: Kafka (beliebig lange Retention, auch Compaction), Event Hubs (bis 90 Tage), RabbitMQ nur mit Streams, Service Bus nein, Solace mit Replay Log.
  • Routing: Kafka einfach (Topic, Key). RabbitMQ und Service Bus reich (Exchanges, Filter). Solace am feinsten (Topic-Hierarchie pro Nachricht, über Standorte).
  • Durchsatz: Kafka sehr hoch und linear über Partitionen. Event Hubs hoch, aber an TUs/PUs gebunden. Queues mittel.
  • Reihenfolge: Kafka/Event Hubs pro Partition, Service Bus pro Session, RabbitMQ pro Queue mit einem Consumer.
  • Fehlerbehandlung: Queues haben Retry-Zähler und DLQ eingebaut. Logs nicht.
  • Ökosystem: Kafka Connect, Kafka Streams, Schema Registry. Event Hubs: Capture, Stream Analytics, Functions. Service Bus: Functions, Logic Apps.
  • Betrieb: Kafka und RabbitMQ selbst betreiben oder managed kaufen. Event Hubs und Service Bus nur Azure. Solace als Software, Appliance oder Cloud.

6. In der Produktion

  1. Kafka als Job-Queue missbraucht: Langsame Jobs blockieren eine Partition, und mehr Worker als Partitionen bleiben leer. Lösung: Queue (Service Bus, RabbitMQ) oder Share Groups ab Kafka 4.2.
  2. RabbitMQ als Event-Store missbraucht: Ein neuer Consumer braucht alte Events, aber sie sind gelöscht. Lösung: Log mit Retention (Kafka, Event Hubs oder RabbitMQ Streams).
  3. Event Hubs Throttling: Fehler ServerBusy oder Kafka-Throttling, weil die TUs erschöpft sind. Lösung: Auto-Inflate oder mehr TUs, Premium mit PUs.
  4. Kafka-Feature fehlt auf Event Hubs: z. B. Compression in Standard, Transaktionen nur Preview. Lösung: vor der Migration die Feature-Liste prüfen, sonst Premium oder echtes Kafka.
  5. Zu wenige Partitionen in Event Hubs Standard: Später nicht erhöhbar. Lösung: am Anfang genug wählen, oder Premium/Dedicated mit dynamischer Erweiterung.
  6. Service Bus DLQ läuft voll: Niemand liest sie, die Nachrichten zählen gegen die Quota. Lösung: Alarm auf DeadletteredMessages, Runbook.
  7. RabbitMQ Speicher-Alarm: Consumer zu langsam, Queues wachsen, der Broker blockiert Publisher. Lösung: Quorum Queues mit Längenlimit, mehr Consumer, Backpressure.
  8. Netzwerk in Azure: Event Hubs und Service Bus brauchen Private Endpoints für Private Networks. Event Hubs Basic hat keinen Private Link.

7. Diagnose: Werkzeuge und Metriken

  • Kafka: kafka-consumer-groups.sh --describe (Lag), JMX UnderReplicatedPartitions, BytesInPerSec.
  • Event Hubs (Azure Monitor): IncomingMessages, OutgoingMessages, ThrottledRequests, ServerErrors, UserErrors, Kafka-Consumer-Lag über die Kafka-CLI.
  • Service Bus (Azure Monitor): ActiveMessages, DeadletteredMessages, ScheduledMessages, ThrottledRequests. Service Bus Explorer im Portal zum Lesen der DLQ.
  • RabbitMQ: rabbitmq-diagnostics status, rabbitmqctl list_queues name messages consumers, Management UI, Prometheus-Plugin.
  • Solace: PubSub+ Broker Manager, SEMP-API für Queues, Spool-Nutzung und Verbindungen.
  • Alle: OpenTelemetry-Tracing über Producer und Consumer, damit man einen Event-Fluss durch mehrere Systeme sieht.

8. Senior-Punkte

  1. Erst das Muster, dann das Produkt. Event-Stream, Work Queue, Pub/Sub mit Filtern oder Request/Reply. Jedes Muster hat ein natürliches Werkzeug.
  2. Oft ist die Antwort „beides“. Kafka für Fachereignisse zwischen Domänen, Service Bus oder RabbitMQ für Aufträge innerhalb eines Teams.
  3. Managed zuerst prüfen. In Azure sind Event Hubs und Service Bus wenig Betrieb. Eigenes Kafka lohnt sich bei Features oder Durchsatz, die Event Hubs nicht bietet.
  4. Kafka-Protokoll ist kein Kafka-Cluster. Event Hubs spricht Kafka, aber Quotas, Retention und Features unterscheiden sich. Vor der Migration Feature für Feature prüfen.
  5. Betriebskosten zählen. Ein Team ohne Kafka-Erfahrung zahlt viel für Upgrades, Rebalancing und Monitoring. Das gehört in die Entscheidung.
  6. Lock-in bewusst wählen. Kafka-Protokoll und AMQP sind offen. Service Bus und Solace-SMF binden stärker an den Anbieter.

10. Fallen

  • „Kafka ist einfach eine schnellere Queue.“ → Falsch. Kafka ist ein Log. Kein Ack pro Nachricht, kein Routing, kein DLQ im Broker.
  • „Event Hubs ist gehostetes Kafka.“ → Falsch. Es spricht das Kafka-Protokoll, ist aber ein eigener Dienst mit eigenen Quotas und Feature-Lücken.
  • „RabbitMQ kann kein Replay.“ → Veraltet. RabbitMQ Streams können es. Klassische Queues nicht.
  • „Mehr Consumer machen Kafka immer schneller.“ → Falsch. Mehr Consumer als Partitionen bleiben in einer Consumer Group leer. Ausnahme: Share Groups.
  • „Service Bus und Event Hubs sind austauschbar.“ → Falsch. Service Bus ist eine Queue für Aufträge, Event Hubs ein Log für Streams.
  • „Solace ist nur ein weiterer JMS-Broker.“ → Falsch. Der Kern ist Topic-Routing pro Nachricht und ein Event Mesh über Standorte.

11. Fragen

Was ist der Kernunterschied zwischen Log und Queue?

Im Log bleiben Nachrichten nach dem Lesen, jeder Consumer hat einen Offset. In der Queue wird eine Nachricht nach dem Ack gelöscht.

Wann wählen Sie Kafka?

Für Event-Streams mit hohem Durchsatz, mehreren unabhängigen Lesern, Replay und Reihenfolge pro Key. Auch für Event Sourcing, CDC und Stream Processing.

Wann wählen Sie RabbitMQ?

Für Aufträge an Worker mit flexiblem Routing, Ack pro Nachricht, Prioritäten und DLX. Und wenn das System portabel bleiben soll.

Wann wählen Sie Service Bus?

Für Enterprise-Messaging in Azure: Aufträge, Sessions mit FIFO, DLQ, geplante Nachrichten, Duplikaterkennung, Transaktionen. Ohne eigenen Betrieb.

Wann wählen Sie Event Hubs?

Für Event-Streams und Telemetrie in Azure, wenn man kein Kafka betreiben will und Quotas und Features passen.

Wann wählen Sie Solace?

Bei hybriden Landschaften mit vielen Standorten, feinem Topic-Routing pro Nachricht und vielen Protokollen wie MQTT und JMS.

Wie funktioniert der Kafka-Endpoint von Event Hubs?

Der Kafka-Client verbindet sich mit NAMESPACE.servicebus.windows.net:9093 über SASL_SSL. Namespace entspricht Cluster, Event Hub entspricht Topic. Ab Standard-Tier.

Welche Kafka-Features fehlen oder sind eingeschränkt auf Event Hubs?

Compression nur Premium/Dedicated, Transaktionen und Kafka Streams nur als Preview in Premium/Dedicated. Dazu Quotas für Retention, Event-Grösse und Partitionen.

Wie lange hält Event Hubs Daten?

Basic 1 Tag, Standard 7 Tage, Premium und Dedicated 90 Tage. Länger nur mit Capture nach Blob oder ADLS.

Wie skaliert Event Hubs?

Standard mit Throughput Units (1 MB/s rein, 2 MB/s raus pro TU), Premium mit Processing Units, Dedicated mit Capacity Units. Dazu die Partitionen.

Wie routet RabbitMQ?

Über Exchanges: direct (genauer Key), topic (Muster mit * und #), fanout (an alle), headers (nach Headern). Bindings verbinden Exchange und Queue.

Wie routet Solace?

Jede Nachricht hat ein hierarchisches Topic wie a/b/c. Abos nutzen Wildcards * und >. Das Event Mesh leitet Abos über Broker weiter.

Wie garantieren die Systeme Reihenfolge?

Kafka und Event Hubs pro Partition. Service Bus pro Session. RabbitMQ pro Queue mit einem aktiven Consumer.

Was sind Share Groups in Kafka?

Queues for Kafka, seit 4.2 produktionsreif. Mehrere Consumer teilen sich eine Partition, jeder Record wird einzeln bestätigt, nach 5 Versuchen archiviert.

Was sind Quorum Queues?

Replizierte RabbitMQ-Queues mit Raft. Seit RabbitMQ 4.0 Standard für Hochverfügbarkeit, Classic Mirrored Queues sind entfernt.

Was ist der Unterschied zwischen Event Hubs und Event Grid?

Event Hubs ist ein Log für grosse Streams mit Pull und Retention. Event Grid verteilt einzelne reaktive Events per Push, ohne Replay.

Push oder Pull: wer macht was?

Kafka und Event Hubs: Pull, der Consumer bestimmt das Tempo. RabbitMQ: Push mit Prefetch-Grenze. Service Bus: Receive mit Peek-Lock.

Warum ist Kafka so schnell?

Sequentielles Schreiben, Batches, Page Cache, Zero-Copy beim Senden und Parallelität über Partitionen. Kein Zustand pro Nachricht im Broker.

Was kostet eigenes Kafka im Betrieb?

Broker und KRaft-Controller, Upgrades, Partitionsplanung, Rebalancing, Monitoring, Sicherheit. Dafür volle Features und keine Cloud-Quotas.

Szenario: Ein Team will Kafka für PDF-Aufträge mit 30 s Laufzeit. Was raten Sie?

Eher eine Queue wie Service Bus oder RabbitMQ: Ack pro Auftrag, beliebig viele Worker, DLQ eingebaut. Mit Kafka nur über Share Groups (ab 4.2) oder viele Partitionen.

Szenario: Eine Azure-Plattform braucht Events für fünf Teams, Replay von 14 Tagen und 50 MB/s. Was wählen Sie?

Event Hubs Premium (90 Tage Retention, PUs) oder eigenes Kafka. Standard reicht nicht wegen 7 Tagen Retention. Die Entscheidung hängt an Betriebskapazität und benötigten Kafka-Features.

Szenario: Sie migrieren einen Kafka-Producer auf Event Hubs, danach kommen Fehler. Was prüfen Sie?

Tier (nicht Basic), Port 9093 und SASL_SSL, Event-Grösse über 1 MB, Compression in Standard, Transaktionen, Throttling wegen zu wenigen TUs.
