Fehler, Retries, Dead Letter Topic

Kafka · Tier 1 · Quellen: Spring for Apache Kafka Reference 4.x (Handling Exceptions: DefaultErrorHandler, DeadLetterPublishingRecoverer, ErrorHandlingDeserializer; Non-Blocking Retries: How the Pattern Works, Topic Naming, DLT Strategies, Configuration), Apache Kafka 4.x Documentation (Consumer Configs max.poll.interval.ms; Kafka Connect error reporting; Share Groups), KIP-932

Kern: Ein Dead Letter Topic (DLT) ist ein eigenes Topic für Nachrichten, die ein Consumer nicht verarbeiten kann. Es löst das Problem der Poison Message: Eine fehlerhafte Nachricht blockiert sonst die ganze Partition oder geht still verloren. Davor stehen Retries, entweder blocking im Consumer oder non-blocking über Retry-Topics.

1. Wo sitzt die Fehlerbehandlung?

  1. ErrorHandlingDeserializer: Er umhüllt den echten Deserializer. Ein kaputtes Byte-Format wird so ein Fehler pro Record, statt poll() zu blockieren.
  2. Listener: Die Fachlogik wirft eine Exception, z. B. Validierung fehlgeschlagen oder DB nicht erreichbar.
  3. DefaultErrorHandler: Er entscheidet: noch einmal versuchen (mit BackOff, also Wartezeit) oder aufgeben. Manche Exceptions gelten als nicht retryable.
  4. Recoverer: Nach dem letzten Versuch ruft der Handler den Recoverer auf. Der DeadLetterPublishingRecoverer schreibt den Record ins DLT.
  5. DLT: Standardname in Spring Kafka 4.x: <topic>-dlt, gleiche Partition. Header enthalten Original-Topic, Partition, Offset und Exception.
  6. Danach: Der Offset wird committet, die Partition läuft weiter. Ein Alarm meldet das DLT. Nach dem Fix spielt man die Nachricht zurück (Replay).

2. Die Reise einer Poison Message

  1. Versuch 1: Der Listener bekommt Offset 42 und wirft eine Exception.
  2. Seek und BackOff: Der DefaultErrorHandler setzt die Position per Seek auf 42 zurück. Der Thread wartet die BackOff-Zeit ab. Die ganze Partition steht so lange still.
  3. Weitere Versuche: Der Consumer holt Offset 42 erneut. Ohne eigene Config sind es 10 Versuche ohne Pause (FixedBackOff(0, 9)).
  4. Recoverer: Sind die Versuche aufgebraucht, schreibt der DeadLetterPublishingRecoverer den Record ins DLT. Gelingt das nicht, wirft er, und der Record wird erneut versucht.
  5. Commit: Danach gilt der Record als behandelt (ackAfterHandle=true). Der Offset 43 wird gelesen.
  6. Alarm: Ein Monitoring sieht neue Nachrichten im DLT und meldet sich beim Team.
  7. Fix und Replay: Das Team behebt den Fehler und schickt die Nachricht zurück ins Haupt-Topic. Der Consumer muss idempotent sein, denn sie kann schon teilweise gewirkt haben.

3. Beispiel: Spring Kafka mit Blocking Retry und DLT

// application.yml (Auszug)
spring.kafka.consumer:
  key-deserializer:   org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
  value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
  properties:
    spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer

// Konfiguration: 3 Versuche (1 + 2 Retries), 1 s Pause, dann DLT
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
  var recoverer = new DeadLetterPublishingRecoverer(template);   // → orders-dlt, gleiche Partition
  var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L));
  handler.addNotRetryableExceptions(ValidationException.class);   // sofort ins DLT
  return handler;   // Spring Boot hängt ihn an die Container Factory
}

@KafkaListener(topics = "orders", groupId = "billing")
void on(Order order) { billing.process(order); }

  Commit orders-0@43, Verarbeitung läuft weiter

Erwartete Header im DLT-Record:
  kafka_dlt-original-topic=orders  kafka_dlt-original-partition=0
  kafka_dlt-original-offset=42     kafka_dlt-exception-fqcn=...TimeoutException
  kafka_dlt-exception-message=...  kafka_dlt-exception-stacktrace=...

Erwartetes Ergebnis (laut Spring-Kafka-Doku, nicht ausgeführt). Ältere Spring-Kafka-Versionen nutzten den Suffix .DLT statt -dlt.

  1. ErrorHandlingDeserializer fängt Deserialisierungsfehler. Sie gelten als nicht retryable und gehen direkt ins DLT, mit den Original-Bytes.
  2. FixedBackOff(1000, 2) heisst: 2 Retries im Abstand von 1 s, also 3 Versuche total.
  3. ValidationException ist ein permanenter Fehler: Wiederholen hilft nie. Darum sofort ins DLT.
  4. Das DLT muss mindestens so viele Partitionen haben wie orders, sonst scheitert der Recoverer.
// Variante non-blocking: Retry-Topics statt Warten im Consumer
@RetryableTopic(attempts = "4", backOff = @BackOff(delay = 1000, multiplier = 2.0),
                exclude = ValidationException.class)
@KafkaListener(topics = "orders", groupId = "billing")
void on(Order order) { billing.process(order); }

@DltHandler
void dlt(Order order, @Header(KafkaHeaders.RECEIVED_TOPIC) String topic) { alerting.store(order, topic); }

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): Spring legt orders-retry-1000, orders-retry-2000, orders-retry-4000 und orders-dlt an. Das Haupt-Topic läuft sofort weiter. Die Doku warnt: Die Reihenfolge des Topics geht dabei verloren.

4. Details, die Interviewer fragen

  1. Poison Message: Eine Poison Message ist eine Nachricht, die bei jedem Versuch scheitert. Ohne Grenze blockiert sie die Partition für immer.
  2. Transient vs permanent: Ein transienter Fehler verschwindet von selbst (Timeout, DB kurz weg). Retry hilft. Ein permanenter Fehler bleibt (falsches Format, Validierung). Retry verschwendet nur Zeit.
  3. Kafka hat kein eingebautes DLQ: Der Broker kennt keine Fehler. Ein DLT ist ein normales Topic, das die Client-Bibliothek befüllt.
  4. DefaultErrorHandler-Standard: FixedBackOff(0, 9), also 10 Versuche ohne Pause. Danach loggt der Standard-Recoverer den Record auf ERROR und überspringt ihn. Ohne DLT ist die Nachricht dann weg.
  5. Nicht retryable per Standard: DeserializationException, MessageConversionException, ConversionException, MethodArgumentResolutionException, NoSuchMethodException, ClassCastException. Eigene kommen mit addNotRetryableExceptions dazu.
  6. Blocking Retry: Der Thread schläft während des BackOffs, die Partition steht. Vorteil: Reihenfolge bleibt. Nachteil: Ein Fehler stoppt den ganzen Fluss dieser Partition.
  7. BackOff und max.poll.interval.ms: Der Consumer muss innerhalb von max.poll.interval.ms (Standard 5 min) wieder poll() aufrufen. Sonst verlässt er die Gruppe und es gibt einen Rebalance. Lange Pausen darum nur pro Versuch kurz halten oder ContainerPausingBackOffHandler nutzen.
  8. Non-blocking Retry (@RetryableTopic): Der Record geht in ein Retry-Topic mit Fälligkeits-Zeitstempel. Der Retry-Consumer pausiert die Partition, bis er fällig ist. Das Haupt-Topic läuft sofort weiter.
  9. Preis von non-blocking: Die Reihenfolge ist weg. Dazu kommen mehr Topics, mehr Consumer und mehr Betrieb.
  10. Topic-Namen: Suffixe -retry und -dlt. Standard ist der Delay im Namen (-retry-1000). Seit Spring Kafka 4.1 nutzt eine feste Pause standardmässig ein einziges Retry-Topic.
  11. DLT-Strategien: ALWAYS_RETRY_ON_ERROR (Standard: scheitert der DLT-Handler, geht der Record zurück ins DLT), FAIL_ON_ERROR, NO_DLT.
  12. Deserialisierungsfehler: Ohne ErrorHandlingDeserializer scheitert schon poll(). Der Listener sieht den Record nie. Mit ihm landet der Fehler im Header, und der Record geht mit den Original-Bytes ins DLT.
  13. DLT-Header: kafka_dlt-original-topic, -original-partition, -original-offset, -exception-fqcn, -exception-message, -exception-stacktrace. Damit findet man Ursache und Herkunft.
  14. Batch-Listener: Der Listener wirft BatchListenerFailedException mit dem Index. Dann committet der Handler die Records davor und behandelt nur den fehlerhaften.
  15. Error vs RuntimeException: Der DefaultErrorHandler behandelt nur Exceptions. Ein Error (z. B. OutOfMemoryError) beendet den Consumer.
  16. Kafka Connect: errors.tolerance=all und errors.deadletterqueue.topic.name schreiben fehlerhafte Records eines Sink-Connectors in ein DLQ-Topic.
  17. Share Groups (Kafka 4.2 produktionsreif): Records werden einzeln bestätigt. Nach group.share.delivery.attempt.limit Versuchen (Standard 5) archiviert Kafka sie. Ein DLT gibt es dort nicht automatisch.

5. Vergleich

  • Blocking Retry (DefaultErrorHandler): einfach, Reihenfolge bleibt, aber die Partition steht. Gut für kurze transiente Fehler.
  • Non-blocking Retry (@RetryableTopic): Haupt-Topic läuft weiter, lange Pausen möglich. Aber keine Reihenfolge, mehr Topics.
  • Nur DLT, keine Retries: für permanente Fehler wie Validierung und Deserialisierung.
  • Log and skip (Standard ohne Recoverer): Durchsatz bleibt, aber die Nachricht ist verloren. Nur für unwichtige Daten.
  • Pause der ganzen Verarbeitung: Container stoppen, bis ein abhängiges System zurück ist. Gut, wenn alle Nachrichten den gleichen Fehler hätten.
  • RabbitMQ: Dead Letter Exchange eingebaut. Quorum Queues haben seit 4.0 ein delivery-limit von 20.
  • Azure Service Bus: DLQ als Sub-Queue eingebaut. Nach MaxDeliveryCount (Standard 10) wandert die Nachricht dorthin.
  • Event Hubs: kein DLQ, wie Kafka. Der Consumer muss Fehler selbst in ein Topic oder einen Speicher schreiben.

6. In der Produktion

  1. Consumer hängt seit Stunden auf einem Offset: Poison Message mit endlosen Retries. Lösung: Retry-Grenze und DLT. Permanente Fehler als nicht retryable markieren.
  2. Nachrichten verschwinden still: Der Standard loggt nach 10 Versuchen und springt weiter. Lösung: DeadLetterPublishingRecoverer immer konfigurieren.
  3. Endlose Rebalances: Die BackOff-Summe überschreitet max.poll.interval.ms. Lösung: kürzere Pausen, weniger Versuche, oder non-blocking Retry.
  4. Recoverer scheitert: Das DLT fehlt oder hat weniger Partitionen. Lösung: DLT mit gleicher Partitionszahl anlegen, nicht auf Auto-Create verlassen.
  5. DLT voll, niemand schaut: Das DLT ist ein Datenfriedhof. Lösung: Alarm bei jedem neuen Eintrag, ein Owner, ein Runbook für Analyse und Replay.
  6. Replay erzeugt Doppel-Buchungen: Die Nachricht hatte schon teilweise gewirkt. Lösung: idempotenter Consumer (Dedup-Tabelle oder fachlicher Schlüssel).
  7. Replay überschreibt neuere Daten: Das alte Event kommt nach neueren Events desselben Keys. Lösung: Versionsprüfung im Consumer, Replay mit Original-Key.
  8. Retention läuft ab: Das DLT hat die gleiche kurze Retention wie das Haupt-Topic. Lösung: längere Retention für DLTs, z. B. 14–30 Tage.
  9. Personendaten im DLT: Payload und Stacktrace enthalten sensible Daten. Lösung: gleiche ACLs und Verschlüsselung wie das Haupt-Topic, Exception-Message nicht mit Payload füllen.

7. Diagnose: Werkzeuge und Befehle

  • kafka-consumer-groups.sh --describe --group billing: steht CURRENT-OFFSET fest und LAG wächst auf einer Partition, hängt eine Poison Message.
  • kafka-get-offsets.sh --topic orders-dlt: End-Offsets des DLT. Steigen sie, gibt es neue Fehler.
  • kafka-console-consumer.sh --topic orders-dlt --from-beginning --property print.headers=true: Fehler-Header lesen.
  • Micrometer/Prometheus: Spring-Kafka-Listener-Metriken (spring.kafka.listener mit result=failure), Consumer-Lag pro Partition, Rate ins DLT.
  • Alarm: DLT-End-Offset steigt → Ticket. Lag einer Partition wächst, Offset steht → Poison Message.
  • Logs: Original-Topic, Partition, Offset und Key in jede Fehlermeldung. Dazu Trace-ID per OpenTelemetry.
  • Replay-Werkzeug: Ein kleiner Service oder Admin-Endpoint liest aus dem DLT und schreibt mit Original-Key zurück. Notfall: Console Consumer mit --max-messages plus Console Producer.

8. Senior-Punkte

  1. Fehler klassifizieren, bevor man konfiguriert. Transient → Retry mit BackOff. Permanent → sofort DLT. Infrastruktur ganz weg → Container pausieren.
  2. Blocking vs non-blocking ist ein Tausch zwischen Reihenfolge und Durchsatz. Für Zustandsänderungen einer Entity meist blocking.
  3. Ein DLT ohne Prozess ist nutzlos. Es braucht Owner, Alarm, Runbook und ein Replay-Werkzeug.
  4. Replay setzt Idempotenz voraus. Jeder Consumer muss eine Nachricht zweimal vertragen.
  5. Retries nach unten abstimmen: Die Summe aller Retries darf nicht länger dauern, als das Geschäft warten kann. Und nicht länger als max.poll.interval.ms pro Pause.
  6. Retry-Stürme vermeiden: Ist ein Downstream-System weg, scheitert jede Nachricht. Dann lieber pausieren oder einen Circuit Breaker nutzen, statt alles ins DLT zu schieben.

10. Fallen

  • „Kafka hat eine Dead Letter Queue.“ → Falsch. Der Broker hat keine. Spring Kafka oder Kafka Connect schreiben ein normales Topic.
  • „Spring Kafka wiederholt standardmässig endlos.“ → Falsch. 10 Versuche, dann loggen und überspringen.
  • „Mehr Retries machen das System robuster.“ → Falsch bei permanenten Fehlern. Sie blockieren nur länger.
  • „@RetryableTopic behält die Reihenfolge.“ → Falsch. Spätere Nachrichten laufen am Retry vorbei.
  • „Deserialisierungsfehler landen im Listener.“ → Falsch. Ohne ErrorHandlingDeserializer scheitert schon poll().
  • „Replay ist einfach Copy-Paste ins Haupt-Topic.“ → Falsch. Ohne Idempotenz und Versionsprüfung entstehen Duplikate und veraltete Zustände.

11. Fragen

Was ist eine Poison Message?

Eine Nachricht, die bei jedem Versuch scheitert. Ohne Grenze blockiert sie die Partition für immer.

Was ist ein Dead Letter Topic?

Ein normales Topic für Nachrichten, die nicht verarbeitet werden konnten. Es enthält den Original-Record plus Fehler-Header.

Hat der Kafka-Broker eine DLQ?

Nein. Die Client-Bibliothek, z. B. Spring Kafka oder Kafka Connect, schreibt das DLT.

Was macht der DefaultErrorHandler ohne Konfiguration?

10 Versuche ohne Pause, dann loggt er den Record auf ERROR und überspringt ihn. Die Nachricht ist dann verloren.

Wie hängen Sie ein DLT an?

Mit einem DeadLetterPublishingRecoverer im DefaultErrorHandler. Standardziel: <topic>-dlt, gleiche Partition.

Warum braucht das DLT gleich viele Partitionen?

Der Recoverer schreibt standardmässig in dieselbe Partitionsnummer. Fehlt sie, scheitert das Publizieren.

Was ist der Unterschied zwischen transientem und permanentem Fehler?

Transient verschwindet von selbst, Retry hilft. Permanent bleibt, Retry ist sinnlos. Darum permanente Fehler sofort ins DLT.

Welche Exceptions sind standardmässig nicht retryable?

Unter anderem DeserializationException, MessageConversionException, ConversionException und ClassCastException. Eigene ergänzt man mit addNotRetryableExceptions.

Was ist Blocking Retry?

Der Consumer versucht denselben Record nach einer Pause erneut. Die Partition steht so lange, die Reihenfolge bleibt.

Was ist Non-blocking Retry?

Der Record geht in ein Retry-Topic und wird später erneut verarbeitet. Das Haupt-Topic läuft weiter, aber die Reihenfolge ist weg.

Wie funktioniert die Verzögerung bei @RetryableTopic?

Der Record trägt einen Fälligkeits-Zeitstempel. Der Retry-Consumer pausiert die Partition, bis er fällig ist.

Welche Topics legt @RetryableTopic an?

Retry-Topics mit Suffix -retry (meist mit Delay im Namen) und ein -dlt. Bei fester Pause seit 4.1 nur ein Retry-Topic.

Was passiert bei einem Deserialisierungsfehler?

Ohne ErrorHandlingDeserializer scheitert poll() und der Consumer kommt nicht weiter. Mit ihm geht der Record mit den Original-Bytes direkt ins DLT.

Warum ist max.poll.interval.ms bei Retries wichtig?

Wartet der Consumer zu lange ohne poll(), gilt er als tot. Es gibt einen Rebalance, und der Record kommt woanders wieder.

Welche Header schreibt Spring ins DLT?

Original-Topic, Partition, Offset, Zeitstempel, Exception-Klasse, Message und Stacktrace.

Was passiert, wenn der DLT-Handler selbst scheitert?

Standard ALWAYS_RETRY_ON_ERROR: Der Record geht zurück ins DLT. Ausnahme: fatale Exceptions wie Deserialisierungsfehler.

Wie überwachen Sie ein DLT?

Alarm, sobald der End-Offset steigt. Dazu Dashboard mit Rate ins DLT, Owner und Runbook.

Wie spielen Sie Nachrichten aus dem DLT zurück?

Nach dem Fix liest ein Replay-Werkzeug das DLT und schreibt mit Original-Key ins Haupt-Topic. Voraussetzung: idempotenter Consumer.

Was ist das Risiko beim Replay?

Duplikate, wenn die Nachricht schon teilweise gewirkt hat. Und veraltete Zustände, wenn neuere Events desselben Keys schon verarbeitet sind.

Wie behandeln Sie Fehler in einem Batch-Listener?

Mit BatchListenerFailedException und dem Index. Dann werden die Records davor committet und nur der fehlerhafte behandelt.

Wie macht Kafka Connect Fehlerbehandlung?

Mit errors.tolerance=all und errors.deadletterqueue.topic.name schreibt ein Sink-Connector fehlerhafte Records in ein DLQ-Topic.

Wie unterscheidet sich Service Bus?

Service Bus hat eine eingebaute Dead-Letter-Sub-Queue. Nach MaxDeliveryCount (Standard 10) wandert die Nachricht automatisch dorthin.

Was tun, wenn ein Downstream-System komplett ausfällt?

Nicht alles ins DLT schieben. Container pausieren oder Circuit Breaker nutzen und nach Rückkehr weitermachen.

Szenario: Der Consumer-Lag einer Partition wächst seit einer Stunde, der Offset steht fest. Was tun Sie?

Wahrscheinlich eine Poison Message mit endlosen Retries. Den Record per Offset ansehen, Retry-Grenze und DLT konfigurieren, den Fehlertyp als nicht retryable markieren.

Szenario: Fachbereich meldet fehlende Bestellungen, im Log stehen nur ERROR-Zeilen. Was ist passiert?

Der Standard-Recoverer hat nach 10 Versuchen geloggt und übersprungen. Lösung: DLT einrichten, Offsets aus dem Log nehmen und die Records gezielt neu lesen.

Szenario: Nach einem Bugfix liegen 5000 Nachrichten im DLT. Wie gehen Sie vor?

Erst Ursache und Idempotenz prüfen. Dann klein starten: wenige Records zurückspielen, Ergebnis prüfen, dann den Rest mit begrenzter Rate. Neuere Zustände per Version schützen.
