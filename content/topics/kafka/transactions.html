Kafka-Transaktionen

Kafka · Tier 2 · Quellen: Apache Kafka 4.4 Documentation (Design: Using Transactions, Operations: Transaction Protocol, Producer/Consumer/Broker Configs), KafkaProducer Javadoc, KIP-98, KIP-447, KIP-664, KIP-890, KIP-939, Spring for Apache Kafka Reference (Transactions). Grundlagen zu Exactly-once: Seite „Delivery Semantics“.

Kern: Eine Kafka-Transaktion schreibt mehrere Nachrichten in mehrere Partitionen atomar: alle sichtbar oder keine. Sie kann auch die Consumer-Offsets im selben Schritt committen. So entsteht Read-Process-Write ohne Duplikate, aber nur innerhalb von Kafka.

1. Wo sitzt die Transaktion?

  1. Der transaktionale Producer hat eine feste transactional.id. Sie überlebt Neustarts.
  2. Der Transaction Coordinator ist ein Broker. Er ist Leader der Partition von __transaction_state, die zum Hash der transactional.id passt.
  3. __transaction_state speichert den Zustand jeder Transaktion. Standard: 50 Partitionen, RF 3, min ISR 2.
  4. Die Daten landen sofort in den Ziel-Partitionen. Sie sind nur noch nicht sichtbar für read_committed-Consumer.
  5. Am Ende schreibt der Coordinator Transaktions-Marker (Commit oder Abort) in jede beteiligte Partition.

2. Die Reise einer Transaktion (die Geschichte zum Merken)

  1. initTransactions(): Der Producer meldet seine transactional.id beim Coordinator an. Er bekommt eine Producer-ID und eine höhere Epoch. Offene alte Transaktionen dieser ID werden beendet. Ein alter „Zombie“ mit kleinerer Epoch ist ab jetzt ausgesperrt.
  2. beginTransaction(): Passiert nur im Client. Noch kein Netzwerk.
  3. send(): Beim ersten Schreiben in eine Partition meldet der Producer sie beim Coordinator an (AddPartitionsToTxn). Dann schreibt er die Daten normal. Der Zustand ist jetzt Ongoing.
  4. sendOffsetsToTransaction(offsets, groupMetadata): Die Offsets der gelesenen Nachrichten gehören jetzt zur Transaktion. Sie landen in __consumer_offsets, aber noch unsichtbar.
  5. commitTransaction(): Der Producer leert seinen Puffer. Der Coordinator schreibt PrepareCommit in __transaction_state. Ab hier ist der Commit sicher, auch bei einem Crash.
  6. Marker: Der Coordinator schreibt Commit-Marker in jede beteiligte Partition. Dann CompleteCommit. Der Last Stable Offset rückt vor, Consumer sehen die Daten.
  7. Abort: Bei einem Fehler ruft die App abortTransaction(). Läuft transaction.timeout.ms (Standard 60 s) ab, bricht der Coordinator selbst ab. Die Daten bleiben im Log, werden aber übersprungen.

3. Beispiel: Read-Process-Write mit Transaktion

props.put("transactional.id", "vsp-enricher-" + instanceId);   // stabil pro Instanz
props.put("transaction.timeout.ms", "60000");
consumerProps.put("isolation.level", "read_committed");
consumerProps.put("enable.auto.commit", "false");

producer.initTransactions();
while (running) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
  if (records.isEmpty()) continue;
  producer.beginTransaction();
  try {
    for (var r : records) producer.send(new ProducerRecord<>("steuer-angereichert", r.key(), enrich(r.value())));
    producer.sendOffsetsToTransaction(nextOffsets(records), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException e) {
    producer.close();               // fatal: nicht reparierbar
    throw e;
  } catch (KafkaException e) {
    producer.abortTransaction();    // abbrechen, Position zurücksetzen, neu versuchen
    rewindToCommitted(consumer);
  }
}

4. Details, die Interviewer fragen

  1. Zustände im Coordinator: Empty, Ongoing, PrepareCommit, PrepareAbort, CompleteCommit, CompleteAbort, Dead, PrepareEpochFence.
  2. Kontroll-Records: Ein Transaktions-Marker ist ein eigener Record im Log. Er belegt einen Offset. Darum hat ein transaktionales Topic Offset-Lücken für den Consumer.
  3. Last Stable Offset (LSO): der erste Offset einer noch offenen Transaktion. read_committed-Consumer lesen nur bis dorthin. Eine lange offene Transaktion blockiert also alle Leser dieser Partition.
  4. Aborted Transaction Index: Jedes Segment hat eine .txnindex-Datei. Der Broker liefert damit die Liste abgebrochener Transaktionen mit. Der Consumer filtert sie selbst heraus.
  5. Timeouts: transaction.timeout.ms im Producer (Standard 60 000). Der Broker erlaubt höchstens transaction.max.timeout.ms (Standard 15 Minuten). Der Coordinator prüft alle 10 s auf abgelaufene Transaktionen.
  6. Ablauf der ID: Eine unbenutzte transactional.id verfällt nach transactional.id.expiration.ms (Standard 7 Tage).
  7. KIP-890 (Server-Side Defense): Seit Kafka 4.0 ist das neue Protokoll auf dem Server Standard (transaction.version=2). Clients ab 4.0 erhöhen die Epoch bei jeder Transaktion. Das verhindert, dass ein verspäteter Retry in die nächste Transaktion rutscht.
  8. Hängende Transaktion: Eine Transaktion, die der Coordinator vergessen hat, die Partition aber noch offen sieht. Der LSO bleibt stehen. KIP-890 soll das verhindern; KIP-664 gibt das Werkzeug kafka-transactions.sh find-hanging und abort.
  9. Kosten: Pro Transaktion kommen Anmelde-Requests und Marker in jede Partition dazu. Darum lieber viele Nachrichten pro Transaktion als eine.
  10. Spring Kafka: spring.kafka.producer.transaction-id-prefix aktiviert Transaktionen. Der KafkaTransactionManager verbindet sie mit @Transactional. Ein Listener-Container startet die Transaktion selbst und schickt die Offsets mit.
  11. Zwei-Phasen-Commit (KIP-939): Kafka kann Teilnehmer an einem externen 2PC werden: prepareTransaction() und completeTransaction(...). Dafür braucht es den Broker-Schalter transaction.two.phase.commit.enable (Standard false) und ein eigenes ACL-Recht.

5. Vergleich

  • Idempotenter Producer: keine Duplikate pro Partition und Session. Keine Atomarität über Partitionen. Standard seit Kafka 3.0.
  • Kafka-Transaktion: atomar über mehrere Partitionen und Offsets. Nur innerhalb eines Kafka-Clusters.
  • Kafka Streams exactly_once_v2: nutzt dieselben Transaktionen, aber automatisch. Kein eigener Code für begin und commit.
  • Outbox-Pattern: DB-Änderung und Event in einer DB-Transaktion. Ein Relay schreibt später nach Kafka. Atomar zwischen DB und Kafka, ohne 2PC.
  • Idempotenter Consumer: Duplikate erkennen statt verhindern, z. B. mit einer Tabelle verarbeiteter IDs. Einfach und robust für externe Systeme.
  • XA / 2PC über DB und Kafka: mit KIP-939 möglich, aber komplex. Selten die erste Wahl.

6. In der Produktion

  1. Consumer bleiben stehen, Lag wächst, aber keine Fehler: Eine offene oder hängende Transaktion hält den LSO fest. Lösung: kafka-transactions.sh list und find-hanging, notfalls abort. Timeouts der Producer prüfen.
  2. ProducerFencedException nach Rolling Update: Zwei Pods nutzen dieselbe transactional.id. Lösung: ID pro Instanz eindeutig, z. B. aus dem StatefulSet-Namen oder einem Präfix plus Pod-Index.
  3. Durchsatz bricht ein: Eine Transaktion pro Nachricht. Lösung: pro poll() eine Transaktion, also ganze Batches.
  4. „Exactly-once“, aber Duplikate in der DB: Der Service schreibt zusätzlich in eine Datenbank. Kafka-Transaktionen decken die DB nicht ab. Lösung: Upsert, idempotenter Consumer oder Outbox.
  5. Consumer sieht abgebrochene Daten: isolation.level ist noch read_uncommitted (Standard). Lösung: read_committed in allen nachgelagerten Consumern.
  6. Lange Verarbeitung pro Batch: Die Transaktion läuft in den Timeout und wird abgebrochen. Lösung: kleinere Batches (max.poll.records) oder Timeout passend erhöhen.

7. Diagnose: Werkzeuge und Befehle

  • kafka-transactions.sh list: alle bekannten Transaktionen mit Zustand.
  • kafka-transactions.sh describe --transactional-id X: Zustand, Dauer, Partitionen.
  • kafka-transactions.sh describe-producers --topic T --partition P: aktive Producer und offene Transaktionen einer Partition.
  • kafka-transactions.sh find-hanging --broker-id N und abort --topic T --partition P --start-offset O.
  • kafka-dump-log.sh --files ... --print-data-log: zeigt isTransactional und Kontroll-Records (COMMIT/ABORT).
  • Consumer-Metrik records-lag-max: Bei read_committed wird Lag bis zum LSO gemessen. Wächst er ohne Last, an hängende Transaktionen denken.
  • Producer-Logs mit transactional.id: Meldungen zu Epoch und Fencing.

8. Senior-Punkte

  1. Transaktionen lösen nur Kafka → Kafka. Sobald eine DB, eine REST-API oder ein Mailversand dazukommt, braucht es Idempotenz im Ziel.
  2. Erst fragen: reicht at-least-once plus Idempotenz? Oft ja. Das ist einfacher zu betreiben und zu debuggen.
  3. Die transactional.id ist ein Design-Thema. Stabil pro Instanz, eindeutig, nachvollziehbar. Doppelte IDs fencen sich gegenseitig.
  4. Alle Leser müssen mitspielen. Ein einziger Consumer mit read_uncommitted sieht abgebrochene Daten.
  5. Transaktionsgrösse ist ein Kompromiss: grosse Transaktionen für Durchsatz, kleine für Latenz. Lange Transaktionen bremsen alle read_committed-Leser.
  6. Upgrade-Plan: Mit Kafka 4.x und KIP-890 auf aktuelle Clients gehen. Erst dann wirkt der volle Schutz.

10. Fallen

  • „Mit Transaktionen ist das Schreiben in meine DB exactly-once.“ → Falsch. Nur Kafka-Partitionen und Offsets sind in der Transaktion.
  • „Abgebrochene Nachrichten werden gelöscht.“ → Falsch. Sie bleiben im Log. read_committed-Consumer überspringen sie.
  • „Transaktionen sind Standard.“ → Falsch. Nur Idempotenz ist Standard. Transaktionen brauchen transactional.id, und Consumer stehen auf read_uncommitted.
  • „Nach abortTransaction() geht es automatisch weiter.“ → Falsch. Die App muss die Consumer-Position selbst zurücksetzen.
  • „Eine zufällige transactional.id pro Start ist gut.“ → Falsch. Dann fenct niemand den alten Zombie. Die ID muss stabil sein.
  • „Offsets committe ich nach der Transaktion mit commitSync.“ → Falsch. Sie gehören mit sendOffsetsToTransaction in die Transaktion.

11. Fragen

Was ist eine Kafka-Transaktion?

Atomares Schreiben in mehrere Partitionen plus Offsets. Alles wird sichtbar oder nichts. Gedacht für Read-Process-Write innerhalb von Kafka.

Welche API-Aufrufe gehören dazu?

initTransactions, beginTransaction, send, sendOffsetsToTransaction, dann commitTransaction oder abortTransaction.

Was macht initTransactions()?

Meldet die transactional.id an, holt Producer-ID und höhere Epoch und beendet offene Transaktionen dieser ID. Alte Instanzen sind danach gefenct.

Wo speichert Kafka den Transaktionszustand?

Im internen Topic __transaction_state. Standard: 50 Partitionen, RF 3, min ISR 2.

Welche Zustände hat eine Transaktion im Coordinator?

Empty, Ongoing, PrepareCommit oder PrepareAbort, dann CompleteCommit oder CompleteAbort. Dazu Dead und PrepareEpochFence.

Ab wann ist ein Commit sicher?

Sobald PrepareCommit in __transaction_state steht. Danach schreibt der Coordinator die Marker auch nach einem Crash fertig.

Was ist ein Transaktions-Marker?

Ein Kontroll-Record (COMMIT oder ABORT) in jeder beteiligten Partition. Er belegt einen Offset.

Was bedeutet read_committed genau?

Der Consumer liest nur bis zum Last Stable Offset und überspringt abgebrochene Transaktionen. Standard ist read_uncommitted.

Warum kann eine offene Transaktion andere Consumer bremsen?

Der LSO bleibt am Anfang der offenen Transaktion stehen. Auch fertige Nachrichten dahinter sind für read_committed nicht sichtbar.

Was passiert bei transaction.timeout.ms?

Der Coordinator bricht die Transaktion ab und erhöht die Epoch. Der Producer bekommt beim nächsten Schritt einen Fehler. Standard 60 s, Broker-Maximum 15 min.

Welche Fehler sind fatal?

Laut Javadoc u. a. ProducerFencedException, OutOfOrderSequenceException, AuthorizationException. Dann Producer schliessen. Andere KafkaException: abort und neu versuchen.

Warum consumer.groupMetadata() in sendOffsetsToTransaction?

Seit KIP-447 fenct der Broker damit Zombies nach einem Rebalance über die Gruppen-Generation. So braucht man nicht mehr einen Producer pro Partition.

Wie wählen Sie die transactional.id?

Stabil und eindeutig pro Instanz, z. B. Präfix plus StatefulSet-Index. Nie zufällig pro Start.

Was hat KIP-890 geändert?

Server-seitiger Schutz seit Kafka 4.0: Epoch-Erhöhung pro Transaktion und Prüfung beim Anmelden der Partition. Verhindert hängende Transaktionen und verspätete Duplikate.

Was ist eine hängende Transaktion?

Eine Partition sieht eine offene Transaktion, die nie endet. Der LSO steht still. Finden mit kafka-transactions.sh find-hanging, beenden mit abort.

Was kosten Transaktionen?

Zusätzliche Requests und Marker pro Partition und Transaktion, plus Wartezeit für Leser. Mit grossen Batches pro Transaktion ist der Aufwand klein.

Wie macht Spring Kafka Transaktionen?

Mit transaction-id-prefix und KafkaTransactionManager. Der Listener-Container startet die Transaktion und sendet die Offsets mit.

Was ist KIP-939?

Kafka als Teilnehmer an einem externen Zwei-Phasen-Commit: prepareTransaction und completeTransaction. Braucht transaction.two.phase.commit.enable=true auf dem Broker.

Transaktion oder Outbox?

Kafka zu Kafka: Transaktion. DB-Änderung plus Event: Outbox, weil die DB-Transaktion beides atomar macht.

Warum sieht ein transaktionales Topic Offset-Lücken?

Marker belegen Offsets, und abgebrochene Records werden übersprungen. Code darf nie mit „Offset + 1“ rechnen.

Szenario: Alle Consumer eines Topics stehen still, der Producer läuft. Was prüfen Sie?

Eine offene oder hängende Transaktion hält den LSO. kafka-transactions.sh list, describe-producers und find-hanging nutzen, dann gezielt abbrechen.

Szenario: Nach dem Skalieren auf 3 Pods gibt es ständig ProducerFencedException. Warum?

Die Pods teilen sich eine transactional.id und fencen sich gegenseitig. Lösung: ID pro Pod eindeutig machen.

Szenario: Das Team will Transaktionen, damit Kafka und PostgreSQL immer zusammenpassen. Was sagen Sie?

Kafka-Transaktionen decken PostgreSQL nicht ab. Besser Outbox-Pattern oder idempotentes Upsert im Consumer. 2PC mit KIP-939 nur, wenn es wirklich nötig ist.
