Schema Registry, Avro, Kompatibilität

Kafka · Tier 2 · Quellen: Confluent Platform Docs (Schema Evolution and Compatibility, Formats/Serializers/Deserializers mit Wire Format, Schema Registry Configuration Reference), Apache Avro Specification (Schema Resolution)

Kern: Eine Schema Registry ist ein eigener Dienst, der Schemas für Kafka-Nachrichten speichert und jedem Schema eine ID gibt. Der Producer schickt nur diese ID plus kompakte Binärdaten. Die Registry prüft jede neue Version auf Kompatibilität, damit kein Producer die Consumer bricht.

1. Wo sitzt die Schema Registry?

  1. Die Schema Registry ist ein eigener Dienst neben Kafka, kein Teil des Brokers. Der Broker kennt keine Schemas.
  2. Sie speichert alles im Topic _schemas. Es hat eine Partition und muss kompaktiert sein. Standard-RF: 3.
  3. Ein Subject ist der Name, unter dem die Versionen eines Schemas liegen. Standard: <topic>-value und <topic>-key.
  4. Der Serializer im Producer registriert oder sucht das Schema und schreibt die ID vor die Daten.
  5. Der Deserializer im Consumer liest die ID, holt das Schema einmal und cached es.
  6. Bei mehreren Instanzen gibt es einen Primary. Andere Instanzen leiten Schreibzugriffe an ihn weiter.

2. Die Reise eines Schemas (die Geschichte zum Merken)

  1. Neue Version: Das Team fügt im Event SteuerfallEingereicht das Feld kanton mit Default null hinzu.
  2. Prüfung: Der Serializer oder die CI schickt das Schema an die Registry. Sie prüft es gegen die letzte Version im Subject. Standard ist BACKWARD.
  3. Registrieren: Das Schema ist kompatibel. Die Registry speichert es in _schemas und gibt eine global eindeutige ID zurück, hier 42.
  4. Senden: Der Producer schreibt Byte 0 (Magic Byte), dann 4 Bytes ID (Big Endian), dann die Avro-Binärdaten. Feldnamen stehen nicht in der Nachricht.
  5. Lesen: Der Consumer liest die ID und holt das Writer-Schema einmal aus der Registry.
  6. Schema Resolution: Avro übersetzt vom Writer-Schema ins Reader-Schema der App. Fehlt ein Feld, nimmt Avro den Default. Unbekannte Felder ignoriert es.
  7. Inkompatibel: Die Registry lehnt das Schema mit HTTP 409 ab. Der Producer kann dann nicht senden. Der Fehler kommt früh, nicht beim Consumer.

3. Beispiel: Kompatibilität prüfen und das Wire Format sehen

# v2: neues optionales Feld mit Default
$ curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"schema": "{\"type\":\"record\",\"name\":\"SteuerfallEingereicht\",\"fields\":[{\"name\":\"fallId\",\"type\":\"string\"},{\"name\":\"kanton\",\"type\":[\"null\",\"string\"],\"default\":null}]}"}' \
  http://schema-registry:8081/compatibility/subjects/steuer-events-value/versions/latest
{"is_compatible":true}

# v3: Pflichtfeld ohne Default
$ curl ... --data '{"schema": "... {\"name\":\"betrag\",\"type\":\"long\"} ..."}' \
  ".../compatibility/subjects/steuer-events-value/versions/latest?verbose=true"
{"is_compatible":false,"messages":["... READER_FIELD_MISSING_DEFAULT_VALUE ... betrag ..."]}

Erwartetes Ergebnis (laut Confluent-Doku, nicht ausgeführt). Keine Registry hier. Meldungstext gekürzt.

Bytes   : 00 00 00 00 2a 0c 66 61 6c 6c 2d 37 02
Magic   : 0
SchemaID: 42
Payload : b'\x0cfall-7\x02'
JSON statt Avro -> erstes Byte: 123 (nicht 0 -> 'Unknown magic byte!')

Echte Ausgabe, Python 3.12.10. Nachbau des dokumentierten Wire Formats mit struct.pack(">I", 42), keine Registry.

  1. v2 ist BACKWARD-kompatibel: Ein Consumer mit v2 kann alte v1-Daten lesen. Für kanton nimmt er den Default null.
  2. v3 ist nicht kompatibel: Ein Reader mit v3 braucht betrag, alte Daten haben es nicht, und es gibt keinen Default.
  3. Byte 0 ist das Magic Byte 0. Bytes 1–4 sind die ID 42 als 00 00 00 2a.
  4. Danach folgen nur Werte: Länge 6 (als ZigZag 0c), Text, eine Zahl. Keine Feldnamen. Darum braucht der Leser das Schema.
  5. Schickt jemand JSON ins Topic, ist das erste Byte { = 123. Der Avro-Deserializer meldet „Unknown magic byte!“.

4. Details, die Interviewer fragen

  1. Kompatibilitätsstufen:
    • BACKWARD (Standard): neues Schema liest alte Daten. Erlaubt: Felder löschen, optionale Felder hinzufügen. Consumer zuerst upgraden.
    • FORWARD: altes Schema liest neue Daten. Erlaubt: Felder hinzufügen, optionale Felder löschen. Producer zuerst.
    • FULL: beides. Nur optionale Felder hinzufügen oder löschen. Reihenfolge egal.
    • NONE: keine Prüfung.
  2. Transitive Varianten: BACKWARD prüft nur gegen die letzte Version. BACKWARD_TRANSITIVE prüft gegen alle. Wichtig, wenn Consumer von ganz vorne lesen.
  3. Optional heisst in Avro: ein Feld mit default, meist als Union ["null", "string"] mit "default": null. null muss dann zuerst in der Union stehen.
  4. Umbenennen: Für Avro ein Löschen plus Hinzufügen. Mit Aliases im Reader-Schema geht es kompatibel.
  5. Typänderung: Avro erlaubt einige Promotions, z. B. int → long. string → int ist nicht kompatibel.
  6. Subject Name Strategy: TopicNameStrategy (Standard, ein Schema pro Topic), RecordNameStrategy (pro Record-Typ, Topic-übergreifend), TopicRecordNameStrategy (Topic plus Record). Mehrere Event-Typen in einem Topic brauchen eine der letzten zwei.
  7. Auto-Registrierung: Serializer registrieren Schemas standardmässig selbst (auto.register.schemas). In Produktion oft aus: Schemas kommen aus der CI. Dann use.latest.version=true.
  8. Normalisierung: normalize.schemas=true behandelt gleichwertige Schemas (andere Reihenfolge, Namen) als gleich. Standard aus.
  9. Protobuf: Felder haben Nummern. Eine Nummer nie wiederverwenden, gelöschte mit reserved sperren. Confluent empfiehlt BACKWARD_TRANSITIVE.
  10. JSON Schema: Regeln hängen vom Content Model ab: offen (additionalProperties erlaubt) oder geschlossen.
  11. Header-Format: Neuere Confluent-Serializer können die Schema-ID als 16-Byte-GUID im Header __value_schema_id schicken. Deserializer prüfen zuerst den Header, dann das Präfix.
  12. Kafka Streams: Confluent unterstützt dort nur BACKWARD- und FULL-Varianten. Streams-Apps zuerst upgraden.

5. Vergleich

  • Avro: kompakt, Schema nötig zum Lesen, sehr klare Evolutionsregeln. Standard im Kafka-Umfeld.
  • Protobuf: kompakt, Feldnummern statt Namen, gut mit gRPC. Code-Generierung in vielen Sprachen.
  • JSON Schema: lesbar, gross, langsamer. Evolution weniger klar.
  • JSON ohne Registry: einfach, aber kein Vertrag. Brüche fallen erst beim Consumer auf.
  • Confluent Schema Registry: Referenz, Confluent Community License. Apicurio Registry: Open Source, Confluent-kompatible API. Azure Schema Registry (in Event Hubs) und AWS Glue Schema Registry: Cloud-Varianten mit eigenen Serializern.

6. In der Produktion

  1. Producer kann nicht senden: HTTP 409: Ein Entwickler hat ein Pflichtfeld ohne Default hinzugefügt. Lösung: Default setzen oder neues Topic. Kompatibilität schon in der CI prüfen (Maven-Plugin oder REST-Aufruf).
  2. „Unknown magic byte!“ im Consumer: Jemand schreibt JSON oder Text ins Avro-Topic, oft ein Test-Tool. Lösung: ErrorHandlingDeserializer plus DLT, Schreibrechte per ACL begrenzen.
  3. Registry nicht erreichbar: Neue Producer und Consumer starten nicht, weil sie Schemas nicht holen können. Laufende Clients arbeiten mit dem Cache weiter. Lösung: mehrere Instanzen, Monitoring.
  4. Wildwuchs an Versionen: Auto-Registrierung in jeder Umgebung. Lösung: auto.register.schemas=false, Schemas im Git, Registrierung nur aus der Pipeline.
  5. Replay bricht: Mit BACKWARD (nicht transitiv) ist v3 nur zu v2 kompatibel, nicht zu v1. Ein Replay von ganz vorne scheitert. Lösung: BACKWARD_TRANSITIVE für Topics mit langer Retention.
  6. _schemas verloren: Ohne Compaction oder mit Retention gelöscht. Dann kennt niemand mehr die IDs. Lösung: Topic kompaktiert, RF 3, Backup.

7. Diagnose: Werkzeuge und Befehle

  • GET /subjects und GET /subjects/X-value/versions: welche Subjects und Versionen es gibt.
  • GET /schemas/ids/42: Schema zu einer ID aus einer kaputten Nachricht.
  • GET /config und GET /config/X-value: globale und Subject-Kompatibilität.
  • POST /compatibility/subjects/X-value/versions/latest?verbose=true: Grund der Inkompatibilität.
  • kafka-avro-console-consumer (Confluent): Avro-Nachrichten lesbar ausgeben.
  • Erste 5 Bytes einer Nachricht ansehen (z. B. mit kcat oder kafka-console-consumer und Hex): Magic Byte und ID.

8. Senior-Punkte

  1. Das Schema ist ein Vertrag zwischen Teams. Es gehört ins Git, mit Review und CI-Prüfung, nicht in den Producer-Code allein.
  2. Kompatibilität nach Retention wählen. Lange Retention oder Replay → transitiv. Kurzlebige Events → BACKWARD reicht.
  3. Upgrade-Reihenfolge ist Teil des Releases. BACKWARD heisst: Consumer zuerst. Das muss jeder im Team wissen.
  4. Breaking Change = neues Topic (z. B. steuer-events.v2) mit Übergangszeit, nicht NONE setzen.
  5. Keine Logik in Defaults verstecken. Ein Default ist ein fachlicher Wert. null ist oft ehrlicher als ein erfundener Wert.
  6. Die Registry ist kritische Infrastruktur. Hochverfügbar betreiben, _schemas sichern, Zugriff absichern.

10. Fallen

  • „Der Kafka-Broker prüft die Schemas.“ → Falsch. Der Broker sieht nur Bytes. Prüfen tun Registry und Serializer.
  • „BACKWARD heisst: alte Consumer lesen neue Daten.“ → Falsch. Das ist FORWARD. BACKWARD heisst: neue Consumer lesen alte Daten.
  • „BACKWARD schützt vor allen alten Versionen.“ → Falsch. Nur gegen die letzte. Für alle: BACKWARD_TRANSITIVE.
  • „Ein neues Feld ist immer kompatibel.“ → Falsch. Ohne Default ist es für BACKWARD ein Bruch.
  • „Die Nachricht enthält das Schema.“ → Falsch. Nur 5 Bytes Präfix mit der ID.
  • „Feld umbenennen ist harmlos.“ → Falsch. Für Avro ist es Löschen plus Hinzufügen, ausser mit Alias.

11. Fragen

Was ist eine Schema Registry?

Ein eigener Dienst, der Schemas versioniert, IDs vergibt und neue Versionen auf Kompatibilität prüft. Producer und Consumer holen Schemas per REST.

Warum braucht Kafka eine Schema Registry?

Kafka speichert nur Bytes. Ohne Vertrag bricht ein Producer leicht alle Consumer. Die Registry fängt das vor dem Senden ab und spart Platz.

Wie sieht das Wire Format aus?

Byte 0 = Magic Byte 0, Bytes 1–4 = Schema-ID Big Endian, dann die Daten. Bei Protobuf kommen noch Message-Indizes davor.

Was ist ein Subject?

Der Name, unter dem Schema-Versionen liegen. Standard: <topic>-value und <topic>-key.

Welche Subject Name Strategies gibt es?

TopicNameStrategy (Standard), RecordNameStrategy, TopicRecordNameStrategy. Mehrere Event-Typen pro Topic brauchen eine Record-basierte Strategie.

Was ist der Standard-Kompatibilitätsmodus?

BACKWARD, nicht transitiv. Neue Schemas müssen alte Daten der letzten Version lesen können.

Erklären Sie BACKWARD, FORWARD und FULL.

BACKWARD: neuer Reader, alte Daten. FORWARD: alter Reader, neue Daten. FULL: beides.

Wer wird bei BACKWARD zuerst upgegradet?

Die Consumer. Sie können dann alte und neue Daten lesen. Danach die Producer.

Was bedeutet TRANSITIVE?

Prüfung gegen alle früheren Versionen statt nur gegen die letzte. Wichtig bei langer Retention und Replay.

Wie fügt man in Avro ein Feld kompatibel hinzu?

Mit Default, meist ["null","string"] und "default": null.

Wie benennt man ein Avro-Feld um?

Mit einem Alias im Reader-Schema. Ohne Alias ist es Löschen plus Hinzufügen.

Was ist Writer- und Reader-Schema?

Writer = Schema beim Schreiben, steht über die ID in der Nachricht. Reader = Schema der lesenden App. Avro übersetzt zwischen beiden.

Wo speichert die Registry ihre Daten?

Im Kafka-Topic _schemas: eine Partition, kompaktiert, Standard-RF 3.

Was passiert, wenn die Registry ausfällt?

Laufende Clients nutzen ihren Cache weiter. Neue Clients und neue Schemas scheitern.

Sollte auto.register.schemas in Produktion an sein?

Meist nein. Schemas kommen geprüft aus der CI. Clients nutzen use.latest.version.

Was ist bei Protobuf zu beachten?

Feldnummern nie wiederverwenden, gelöschte mit reserved sperren. Empfohlen: BACKWARD_TRANSITIVE.

Avro, Protobuf oder JSON Schema?

Avro für Kafka-Standard und klare Evolution. Protobuf, wenn gRPC und viele Sprachen. JSON Schema, wenn Lesbarkeit wichtiger ist als Grösse.

Was bedeutet „Unknown magic byte!“?

Die Nachricht beginnt nicht mit Byte 0. Sie wurde nicht mit dem Registry-Serializer geschrieben, z. B. reines JSON.

Wie behandeln Sie einen Breaking Change?

Neues Topic oder neues Subject, beide Versionen eine Zeit parallel, Consumer migrieren, altes Topic auslaufen lassen.

Welche Alternativen zur Confluent Registry gibt es?

Apicurio Registry, Azure Schema Registry in Event Hubs, AWS Glue Schema Registry.

Szenario: Nach einem Deploy schlagen alle Producer mit HTTP 409 fehl. Was tun Sie?

Das neue Schema ist inkompatibel. Mit ?verbose=true den Grund holen, z. B. Pflichtfeld ohne Default. Schema korrigieren und die Prüfung in die CI ziehen.

Szenario: Ein Consumer liest von Anfang an und scheitert bei alten Nachrichten. Warum?

Wahrscheinlich nur BACKWARD, nicht transitiv. Die neue Version passt zur letzten, aber nicht zur ersten. Lösung: BACKWARD_TRANSITIVE und Schema korrigieren.

Szenario: Ein Team will Events als freies JSON ohne Registry. Was sagen Sie?

Geht für ein Team, wird aber riskant bei vielen Consumern. Mindestens JSON Schema mit Registry und CI-Prüfung, sonst brechen Änderungen erst in Produktion.
