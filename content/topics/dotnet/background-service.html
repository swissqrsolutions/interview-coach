BackgroundService und Worker

Kern: Ein BackgroundService ist eine Basisklasse für Code, der dauernd im Hintergrund läuft. Der Generic Host startet ihn mit der App und stoppt ihn mit einem CancellationToken. Ein Worker Service ist eine App, die nur aus solchen Diensten besteht.

Antwort-Muster

Frage: Wie baue ich einen Hintergrunddienst in .NET und wie stoppt er sauber?

  1. Mechanismus: Ich erbe von BackgroundService und schreibe ExecuteAsync. Der Host ruft StartAsync auf und gibt beim Stop den Token frei.
  2. Zahl: Der Host wartet beim Stoppen standardmässig 30 Sekunden (ShutdownTimeout). In .NET 6 waren es 5 Sekunden.
  3. Trade-off: Ein Fehler in ExecuteAsync stoppt standardmässig den ganzen Host. Das ist sicher, aber hart.
  4. Produktion: Ich fange Fehler pro Durchlauf, nutze IServiceScopeFactory für Scoped-Dienste und prüfe den Token in jeder Schleife.

1. Start und Stop in 6 Schritten

  1. Host bauen: AddHostedService<Worker>() meldet den Dienst als Singleton an. Der Host baut den DI-Container.
  2. StartAsync: Der Host ruft StartAsync jedes Dienstes auf, einen nach dem anderen. Das ist der Standard (ServicesStartConcurrently ist false).
  3. ExecuteAsync: BackgroundService.StartAsync ruft ExecuteAsync(stoppingToken) auf. Die Methode gibt einen Task zurück, der die ganze Lebenszeit darstellt.
  4. Stop-Signal: Ctrl+C oder SIGTERM (zum Beispiel docker stop) löst ApplicationStopping aus. Der Host beginnt das Herunterfahren.
  5. StopAsync: Der Host ruft StopAsync in umgekehrter Reihenfolge auf. BackgroundService bricht den stoppingToken ab und wartet auf das Ende von ExecuteAsync.
  6. Warten: Der Host wartet höchstens ShutdownTimeout. Danach läuft der Prozess weiter zum Ende, auch wenn der Dienst noch arbeitet.

Ab .NET 10 startet BackgroundService.StartAsync den Code mit Task.Run. In .NET 6 bis 9 lief ExecuteAsync bis zum ersten await im Aufrufer-Thread, wie das Demo unten zeigt.

2. Aufbau

  1. IHostedService hat zwei Methoden: StartAsync und StopAsync.
  2. BackgroundService ist eine abstrakte Klasse darüber. Du schreibst nur ExecuteAsync.
  3. IHostedLifecycleService ergänzt StartingAsync, StartedAsync, StoppingAsync und StoppedAsync.
  4. HostOptions hält ShutdownTimeout, StartupTimeout und BackgroundServiceExceptionBehavior.
  5. IHostApplicationLifetime bietet die Events und StopApplication().
  6. Die Worker-Vorlage (dotnet new worker) erzeugt Program und Worker. Sie nutzt Microsoft.NET.Sdk.Worker.

3. Details

  1. ExecuteAsync: Die Methode muss einen Task liefern, der die Arbeit darstellt. Sie läuft meist in einer Schleife mit while (!stoppingToken.IsCancellationRequested). Das Ende des Tasks beendet nur den Dienst, nicht den Host.
  2. StartAsync darf nicht blockieren: Der Host startet die Dienste der Reihe nach. Ein Dienst, der in ExecuteAsync vor dem ersten await lange synchron rechnet, hält in .NET 6 bis 9 den Start auf. Ab .NET 10 startet Task.Run den Code.
  3. ShutdownTimeout: Standard sind 30 Sekunden. In .NET 6 waren es 5 Sekunden. Der Timeout gilt für alle Dienste zusammen. Man kann ihn in HostOptions oder mit shutdownTimeoutSeconds setzen.
  4. StopAsync in BackgroundService: Es bricht den stoppingToken ab. Dann wartet es auf den Task von ExecuteAsync oder auf den eigenen Token von StopAsync. Der erste Fall, der eintritt, zählt.
  5. Reihenfolge: Beim Start laufen die Dienste in der Reihenfolge der Anmeldung. Beim Stop laufen sie umgekehrt. So stoppt ein abhängiger Dienst zuerst.
  6. Fehler in ExecuteAsync: Standard ist BackgroundServiceExceptionBehavior.StopHost. Der Host loggt den Fehler und ruft StopApplication() auf. Mit Ignore läuft der Host weiter, aber ohne diesen Dienst.
  7. Scoped-Dienste: Gehostete Dienste sind Singletons. Ein DbContext ist scoped und darf nicht per Konstruktor kommen. Man injiziert IServiceScopeFactory und erzeugt pro Durchlauf einen Scope.
  8. Laufender Takt: Task.Delay in einer Schleife driftet. PeriodicTimer (seit .NET 6) gibt einen festen Takt. Er wartet mit WaitForNextTickAsync(token).
  9. Einmaliger Lauf: Ein Dienst, der fertig ist, muss StopApplication() rufen, wenn der Host enden soll. Sonst läuft der Host weiter.
  10. Hosting-Arten: Als Windows Service nutzt man AddWindowsService. Unter Linux läuft der Worker als systemd-Dienst oder im Container. Der Host reagiert auf SIGTERM.
  11. Warteschlange: Für Arbeit von aussen nimmt man oft einen Channel<T> oder eine Queue. Der Dienst liest daraus. Die API schreibt hinein. So blockiert die API nicht.
  12. Cooperative Stop: Der Dienst muss den Token prüfen und an Task.Delay und I/O weitergeben. Sonst läuft er in den Timeout.

4. Fallen

  • „Ein Fehler in ExecuteAsync beendet nur diesen Dienst.“ → Falsch. Standard ist StopHost. Der ganze Host stoppt. Man muss Fehler in der Schleife selbst fangen, wenn der Dienst weiterlaufen soll.
  • „Ein BackgroundService darf einen DbContext im Konstruktor nehmen.“ → Falsch. Der Dienst ist ein Singleton und der DbContext scoped. Nimm IServiceScopeFactory und erzeuge pro Durchlauf einen Scope.
  • „Der Host wartet beim Stoppen beliebig lang.“ → Falsch. Er wartet höchstens ShutdownTimeout. Danach endet der Prozess, auch wenn Arbeit läuft.
  • „Task.Delay in einer Schleife läuft exakt jede Sekunde.“ → Falsch. Die Zeit der Arbeit kommt dazu. Der Takt driftet. PeriodicTimer hält den Takt.
  • „Ohne Prüfung des Tokens stoppt der Dienst von selbst.“ → Falsch. Abbruch ist kooperativ. Ohne Token-Prüfung läuft der Dienst bis zum ShutdownTimeout.
  • „ExecuteAsync läuft immer auf einem eigenen Thread.“ → Falsch. In .NET 6 bis 9 läuft der Anfang im Aufrufer-Thread. Erst ab .NET 10 nutzt StartAsync dafür Task.Run.

5. Selbsttest

Warum?

Warum nimmt man BackgroundService statt eines eigenen Threads?

Der Host verwaltet Start, Stop, DI, Logging und Konfiguration. Er gibt den Stop-Token weiter und wartet beim Herunterfahren.

Warum braucht ExecuteAsync einen CancellationToken?

So kann der Host beim Stop dem Dienst Bescheid sagen. Der Dienst beendet seine Arbeit sauber.

Warum stoppt der Host die Dienste in umgekehrter Reihenfolge?

Dienste, die von anderen abhängen, wurden später gestartet. Sie stoppen zuerst, bevor ihre Abhängigkeiten verschwinden.

Wie innen?

Was macht BackgroundService.StartAsync?

Es erzeugt einen verlinkten Token. Es ruft ExecuteAsync auf und merkt sich den Task. Es gibt sofort einen fertigen Task zurück.

Was macht BackgroundService.StopAsync?

Es bricht den Token ab. Dann wartet es auf den ExecuteAsync-Task oder auf den eigenen Token von StopAsync.

Wie merkt der Host einen Fehler in ExecuteAsync?

Er wartet im Hintergrund auf den Task. Bei einer Exception loggt er sie und handelt nach BackgroundServiceExceptionBehavior.

Was passiert bei SIGTERM?

Die ConsoleLifetime fängt das Signal. Sie löst ApplicationStopping aus. Der Host ruft StopAsync der Dienste auf.

Zahlen

Wie lang ist der Standard-ShutdownTimeout?

30 Sekunden. In .NET 6 waren es 5 Sekunden.

Was ist der Standard bei einem Fehler in ExecuteAsync?

StopHost. Der Host stoppt.

Wie lang ist der Standard-StartupTimeout?

Unendlich (Timeout.InfiniteTimeSpan).

Vergleich

IHostedService vs BackgroundService?

IHostedService hat Start und Stop. BackgroundService ist eine Basisklasse, die daraus einen langlaufenden Task macht.

BackgroundService vs Spring @Scheduled?

BackgroundService ist ein eigener Lebenszyklus mit Token. @Scheduled ruft Methoden im Takt auf. In .NET nutzt man PeriodicTimer oder eine Bibliothek wie Quartz.NET.

Worker Service vs Web-API mit Hosted Service?

Der Worker hat keinen HTTP-Server. Eine Web-App kann beides. Der Hosted Service läuft dann neben den Requests.

PeriodicTimer vs Task.Delay in einer Schleife?

PeriodicTimer hält einen festen Takt. Task.Delay addiert die Arbeitszeit zum Warten.

Produktion

Wie vermeidet man, dass ein Fehler den Host stoppt?

Fehler pro Durchlauf mit try/catch fangen und loggen. Nur OperationCanceledException beim Stop durchlassen.

Was tun, wenn der Dienst beim Stoppen in den Timeout läuft?

Prüfen, ob der Token überall durchgereicht wird. Lange Arbeit in kleine Teile zerlegen. Notfalls ShutdownTimeout erhöhen und Kubernetes-Grace-Period anpassen.

Szenario: Der Worker stürzt nachts ab und der Pod startet neu. Was prüfen Sie?

Ich lese das Log nach der Zeile, dass der BackgroundService fehlgeschlagen ist. Ein unbehandelter Fehler in ExecuteAsync stoppt den Host. Ich fange Fehler pro Durchlauf und logge sie.

Szenario: Beim Deployment gehen Nachrichten verloren, weil der Worker hart beendet wird. Was tun Sie?

Ich prüfe, ob der Token beachtet wird und die laufende Nachricht fertig wird. Ich setze ShutdownTimeout und die Grace-Period im Orchestrator passend. Ich bestätige Nachrichten erst nach Erfolg.

Design

Wie nutze ich einen DbContext im Worker?

Ich injiziere IServiceScopeFactory. Pro Durchlauf erzeuge ich einen Scope und hole den DbContext daraus. Am Ende wird der Scope entsorgt.

Wie gebe ich dem Worker Arbeit von einer API?

Mit einem Channel<T> oder einer Queue. Die API schreibt, der Worker liest. Eine Grenze für die Grösse schützt den Speicher.

Wann ist ein Worker die falsche Lösung?

Bei Aufgaben, die genau einmal im Cluster laufen sollen, oder die lange und genau geplant sind. Dann nehme ich einen Job-Scheduler oder einen CronJob.

Mehr

Gerüst

  • Warum? Der Host verwaltet Start, Stop, DI und Token. Du schreibst nur ExecuteAsync.
  • Wie innen? StartAsync ruft ExecuteAsync auf. StopAsync bricht den Token ab und wartet. Stop in umgekehrter Reihenfolge.
  • Zahlen ShutdownTimeout 30 s (in .NET 6: 5 s). Standard bei Fehlern: StopHost.
  • Vergleich IHostedService gegen BackgroundService. PeriodicTimer gegen Task.Delay.
  • Produktion Fehler stoppen den Host. Scoped-Dienste im Singleton. Timeout beim Stoppen.
  • Design IServiceScopeFactory, Channel für Arbeit, Token überall durchreichen.

Beispiel: Host, Worker und Stop live

class Worker : BackgroundService {
  protected override async Task ExecuteAsync(CancellationToken ct) {
    Console.WriteLine($"Worker.ExecuteAsync start, thread {Environment.CurrentManagedThreadId}");
    try { while (!ct.IsCancellationRequested) { Console.WriteLine("tick"); await Task.Delay(500, ct); } }
    catch (OperationCanceledException) { Console.WriteLine("Worker: cancellation seen"); }
    await Task.Delay(100);
    Console.WriteLine("Worker: cleanup done");
  }
}

  2. Worker.ExecuteAsync start erscheint vor Quick.StartAsync. In .NET 6 lief der Anfang von ExecuteAsync direkt im Aufruf von StartAsync, auf Thread 1.
  3. Der Worker tickt alle 500 ms. Nach calling StopAsync bricht der Host den Token ab.
  4. Worker: cancellation seen und cleanup done zeigen den sauberen Stop. Der Host wartet auf das Ende des Tasks.
  5. Quick.StopAsync steht zweimal. Mein Demo ruft StopAsync selbst auf und RunAsync stoppt den Host danach noch einmal.

Vergleich

  • BackgroundService: Hintergrund-Task mit Token im Host. Standard für Worker.
  • IHostedService: Nur Start und Stop. Für Dienste ohne Dauerschleife.
  • IHostedLifecycleService: Zusätzliche Hooks vor und nach Start und Stop.
  • Spring @Scheduled: Methodenaufruf im Takt. In .NET dafür PeriodicTimer oder Quartz.NET.
  • Kubernetes CronJob: Ein eigener Prozess pro Lauf. Gut für seltene Aufgaben.
  • Hangfire oder Quartz.NET: Bibliotheken mit Speicher, Wiederholung und Plan.
  • Windows Service: Der Host kann als Dienst laufen. Dafür nutzt man AddWindowsService.

Produktion

  1. Fehler stoppt den Host: Eine unbehandelte Exception in ExecuteAsync beendet die App. Lösung: Fehler pro Durchlauf fangen und loggen.
  2. Scoped in Singleton: DbContext im Konstruktor erzeugt Fehler oder Daten-Lecks. Lösung: IServiceScopeFactory.
  3. Hartes Beenden: Der Dienst prüft den Token nicht und läuft in den Timeout. Lösung: Token überall durchreichen.
  4. Blockierender Start: Lange synchrone Arbeit vor dem ersten await hält den Host-Start auf (bis .NET 9). Lösung: früh ein await oder Task.Yield().
  5. Unbegrenzte Queue: Die API schreibt schneller als der Worker liest. Lösung: begrenzter Channel mit Gegendruck.
  6. Doppelte Arbeit bei mehreren Pods: Jeder Pod startet den Worker. Lösung: Sperre, Leader Election oder ein CronJob.

Diagnose: Werkzeuge und Befehle

  • Log nach BackgroundService failed und Application is shutting down durchsuchen.
  • dotnet-counters: zeigt Thread-Pool und GC bei einem laufenden Worker.
  • dotnet-dump: zeigt, wo ExecuteAsync hängt.
  • kubectl logs und kubectl describe pod: zeigen Restart-Gründe und Exit-Codes.
  • kubectl get pod -o yaml: prüft terminationGracePeriodSeconds gegen den ShutdownTimeout.
  • Health Checks und Log-Metriken pro Durchlauf: zeigen, ob der Worker noch lebt.

Senior-Punkte

  1. Stoppen ist Teil des Designs. Token, Timeout und Grace-Period des Orchestrators müssen zusammenpassen.
  2. Fehler-Strategie bewusst wählen. StopHost ist sicher, wenn der Orchestrator neu startet. Bei Teilausfall fängt man pro Durchlauf.
  3. At-least-once denken. Nach einem Absturz läuft Arbeit erneut. Verarbeitung muss idempotent sein.
  4. Scoped-Dienste per Scope. Sonst entstehen lang lebende DbContext und Speicherprobleme.
  5. Version beachten. ShutdownTimeout und Startverhalten haben sich zwischen .NET 6 und 10 geändert.
  6. Skalierung klären. Mehrere Instanzen führen den Worker mehrfach aus.
