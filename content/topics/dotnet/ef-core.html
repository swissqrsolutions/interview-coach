Entity Framework Core

Kern: Entity Framework Core (EF Core) ist ein ORM für .NET. Es übersetzt LINQ in SQL und merkt Änderungen an geladenen Objekten im Change Tracker. SaveChanges schreibt alle Änderungen in einer Transaktion.

Antwort-Muster

Frage: Wie funktioniert EF Core, und was ist der Unterschied zu JPA?

  1. Mechanismus: Ein DbContext übersetzt LINQ in SQL. Der Change Tracker merkt Änderungen, SaveChanges schreibt sie.
  2. Zahl: Der Context-Pool hält standardmässig bis zu 1024 Instanzen. Ein DbContext ist nicht thread-sicher.
  3. Trade-off: Tracking ist bequem, kostet aber Speicher und Zeit. Lesende Abfragen laufen mit AsNoTracking schneller.
  4. Produktion: Ich achte auf N+1, Cartesian Explosion und Concurrency Tokens. Migrations rolle ich als Bundle aus.

1. Abfrage und Speichern in 6 Schritten

  1. LINQ-Abfrage: db.Orders.Where(o => o.Total > 100) baut einen Ausdrucksbaum. Es läuft noch nichts. Der Typ ist IQueryable.
  2. Übersetzung: Beim Auslesen (ToListAsync(), foreach) übersetzt der Datenbank-Provider den Baum in SQL.
  3. Datenbank: Die Datenbank führt das SQL aus. Sie liefert Zeilen.
  4. Materialisieren: EF macht aus den Zeilen Objekte. Bei einer Tracking-Abfrage registriert der Change Tracker jedes Objekt mit seinem Original-Zustand.
  5. Änderung: Du änderst Properties der Objekte. Die Datenbank weiss davon noch nichts.
  6. SaveChanges: EF vergleicht Objekte mit dem Original-Zustand und erzeugt INSERT, UPDATE und DELETE. Standardmässig läuft alles in einer Transaktion.

Bei AsNoTracking() entfällt Schritt 4 für das Tracking. Dann findet SaveChanges keine Änderungen.

2. Aufbau

  1. Der DbContext ist die Sitzung zur Datenbank. Er ist Unit of Work und Query-Einstieg.
  2. Ein DbSet<T> steht für eine Tabelle oder Sicht. Man fragt es mit LINQ ab.
  3. Der Change Tracker hält jedes geladene Objekt mit Zustand: Added, Modified, Deleted, Unchanged oder Detached.
  4. Der Provider (zum Beispiel für SQL Server oder PostgreSQL) übersetzt LINQ in das SQL der Datenbank.
  5. Die Konfiguration liegt in OnModelCreating, Attributen und Konventionen. Sie legt Schlüssel, Beziehungen und Spalten fest.
  6. Migrations sind C#-Dateien für Schema-Änderungen. Man erzeugt sie mit dotnet ef migrations add.

3. Details

  1. DbContext-Lebensdauer: Ein Context ist für eine einzelne Arbeitseinheit gedacht. In einer Web-App ist das ein Request. AddDbContext meldet ihn als scoped an. Er ist nicht thread-sicher.
  2. Tracking: Abfragen, die Entitäten liefern, tracken standardmässig. SaveChanges schreibt Änderungen daran. Mit AsNoTracking() entfällt das Tracking. Das spart Speicher und Zeit bei reinem Lesen.
  3. Identity Resolution: Bei Tracking gibt EF für dieselbe Zeile immer dieselbe Instanz zurück. Das ist ähnlich wie der Persistence Context in JPA.
  4. Laden verwandter Daten: Include lädt sofort (eager). Lazy Loading braucht Proxies und virtual Navigationen und ist nicht Standard. Beim Laden in einer Schleife entsteht das N+1-Problem.
  5. Cartesian Explosion: Zwei Collection-Includes auf gleicher Ebene bilden ein Kreuzprodukt. Die Datenmenge wächst stark. AsSplitQuery() teilt das in mehrere Abfragen. Der Standard ist eine einzelne Abfrage.
  6. Projektion: Mit Select holt man nur die nötigen Spalten. Das ist oft schneller als ganze Entitäten zu laden. Eine Projektion ohne Entitäten wird nicht getrackt.
  7. SaveChanges: Alle Änderungen eines Aufrufs laufen standardmässig in einer Transaktion. Schlägt eine fehl, wird alles zurückgerollt. Für mehrere Aufrufe nutzt man Database.BeginTransaction.
  8. Optimistic Concurrency: Ein Concurrency Token (zum Beispiel [Timestamp]) kommt in die WHERE-Klausel von UPDATE. Ändert eine andere Sitzung die Zeile, wirft EF DbUpdateConcurrencyException.
  9. ExecuteUpdate und ExecuteDelete: EF Core 7 hat sie eingeführt. Sie führen eine Massenänderung als ein SQL aus. Sie umgehen den Change Tracker.
  10. Context Pooling: AddDbContextPool hält Instanzen zur Wiederverwendung. Der Standard für die Poolgrösse ist 1024. Es ist unabhängig vom Connection Pool der Datenbank.
  11. Compiled Queries: EF.CompileAsyncQuery kompiliert eine LINQ-Abfrage einmal zu einem Delegate. Das spart die Übersetzung bei heissen Abfragen.
  12. Migrations: Für die Produktion nutzt man ein Migration Bundle aus der CI. Lokal reicht dotnet ef database update. Man prüft jede erzeugte Migration. Sie kann zum Beispiel eine Spalte löschen statt umzubenennen.

4. Fallen

  • „Ein DbContext darf man als Singleton teilen.“ → Falsch. Er ist nicht thread-sicher und für eine kurze Arbeitseinheit gedacht. Man nimmt scoped, oder erzeugt Contexts per Factory.
  • „Lazy Loading ist in EF Core eingeschaltet wie in JPA.“ → Falsch. Es ist aus. Man braucht Proxies und virtual Navigationen. Standard ist explizites Laden mit Include.
  • „Ein Include ist immer besser als mehrere Abfragen.“ → Falsch. Mehrere Collection-Includes erzeugen ein Kreuzprodukt. AsSplitQuery() kann schneller sein.
  • „SaveChanges findet Änderungen an jedem Objekt.“ → Falsch. Nur an getrackten Objekten. Nach AsNoTracking() oder ExecuteUpdate weiss der Tracker nichts.
  • „ExecuteUpdate ruft die Setter der Entitäten auf.“ → Falsch. Es führt ein SQL direkt aus. Es umgeht den Change Tracker, Setter und Entitäten im Speicher.
  • „Die Migration beim App-Start auszuführen ist immer sicher.“ → Falsch. Bei mehreren Instanzen laufen Migrationen parallel. Für die Produktion nimmt man ein Bundle als eigenen Schritt.

5. Selbsttest

Warum?

Warum gibt es einen Change Tracker?

EF muss wissen, was sich geändert hat. Er merkt den Original-Zustand jedes Objekts. Beim SaveChanges entstehen daraus gezielte INSERT, UPDATE und DELETE.

Warum ist ein DbContext kurzlebig?

Er hält getrackte Objekte im Speicher. Ein langer Context wächst und hält veraltete Daten. Eine Arbeitseinheit pro Request ist üblich.

Warum nutzt man AsNoTracking?

Beim reinen Lesen braucht man keinen Zustand. Ohne Tracking spart EF Speicher und Zeit.

Wie innen?

Wie wird LINQ zu SQL?

LINQ baut einen Ausdrucksbaum. Beim Ausführen übersetzt der Provider ihn in SQL. Erst dann geht die Abfrage zur Datenbank.

Was macht SaveChanges?

Es erkennt Änderungen im Tracker. Es erzeugt die SQL-Befehle und führt sie in einer Transaktion aus. Danach setzt es alle Zustände auf Unchanged.

Wie funktioniert Optimistic Concurrency?

Ein Concurrency Token steht in der WHERE-Klausel des UPDATE. Betrifft das UPDATE 0 Zeilen, wirft EF DbUpdateConcurrencyException.

Was ist Identity Resolution?

Bei Tracking liefert EF für dieselbe Zeile dieselbe Objekt-Instanz. Zwei Abfragen geben so keine zwei Kopien.

Zahlen

Wie gross ist der Standard-Pool bei AddDbContextPool?

1024 Instanzen. Darüber werden neue Instanzen nicht mehr zwischengespeichert.

Seit welcher EF-Core-Version gibt es ExecuteUpdate?

Seit EF Core 7.

Wie viele Entity-Zustände gibt es?

Fünf: Detached, Unchanged, Deleted, Modified und Added.

Vergleich

EF Core vs JPA mit Hibernate?

Beide haben Unit of Work, Tracking und Lazy Loading. In EF Core ist Lazy Loading aus. Die Abfragesprache ist LINQ statt JPQL. SaveChanges ist der explizite Flush.

Single Query vs Split Query?

Single Query holt alles mit JOINs. Bei mehreren Collections droht ein Kreuzprodukt. Split Query macht mehrere SQL-Abfragen, dafür weniger Daten.

EF Core vs Dapper?

EF Core ist ein ORM mit Tracking und Migrations. Dapper ist ein schlanker Mapper für eigenes SQL. Dapper ist bei reinen Lesezugriffen oft schneller.

Lazy vs eager vs explicit Loading?

Eager lädt mit Include sofort. Lazy lädt beim Zugriff. Explicit lädt mit Entry(x).Collection(...).Load() auf Anforderung.

Produktion

Woran erkennt man das N+1-Problem?

Viele kleine gleiche SELECT im Log, einer pro Element. Ein SQL-Profiler oder EF-Logging zeigt es. Lösung: Include, Projektion oder Split Query.

Was tun bei DbUpdateConcurrencyException?

Die Daten neu laden und mit der Änderung vergleichen. Dann neu versuchen, mergen oder dem Benutzer den Konflikt zeigen.

Szenario: Eine Listenseite wird mit mehr Daten sehr langsam. Wie gehen Sie vor?

Ich logge das SQL und zähle die Abfragen. Ich suche N+1 und Kreuzprodukte. Ich nehme Select, AsNoTracking, Paging und prüfe Indizes.

Szenario: Zwei Nutzer ändern dieselbe Bestellung, die letzte Änderung überschreibt die erste. Was tun Sie?

Ich führe ein Concurrency Token ein, zum Beispiel rowversion. EF wirft dann DbUpdateConcurrencyException. Ich zeige den Konflikt oder mache einen Merge.

Design

Wie lade ich nur nötige Daten?

Mit Select auf ein DTO. Nur diese Spalten kommen aus der Datenbank. Das ist meist ohne Tracking.

Wie ändere ich viele Zeilen effizient?

Mit ExecuteUpdate oder ExecuteDelete als ein SQL. Ohne Laden der Objekte.

Wann nutze ich Compiled Queries oder Pooling?

Nur für heisse Pfade und nach einer Messung. Beide sparen Zeit pro Aufruf, machen den Code aber komplexer.

Mehr

Gerüst

  • Warum? Unit of Work mit Tracking, LINQ statt SQL im Code, Migrations für das Schema.
  • Wie innen? LINQ wird zum Ausdrucksbaum, der Provider macht SQL. Der Tracker findet Änderungen. SaveChanges in einer Transaktion.
  • Zahlen Pool-Standard 1024. ExecuteUpdate seit EF Core 7. Fünf Entity-Zustände.
  • Vergleich Lazy Loading ist aus (anders als bei JPA). LINQ statt JPQL. Gegen Dapper.
  • Produktion N+1, Cartesian Explosion, Concurrency-Konflikte, Migrationen beim Start.
  • Design Projektion mit Select, AsNoTracking beim Lesen, Concurrency Token, Bundle für Migrations.

Beispiel: Abfrage, Änderung und Concurrency Token

public class Order {
    public int Id { get; set; }
    public decimal Total { get; set; }
    public List<Line> Lines { get; set; } = new();
    [Timestamp] public byte[] RowVersion { get; set; } = default!;   // Concurrency Token
}

// Lesen ohne Tracking, nur nötige Spalten
var list = await db.Orders.AsNoTracking()
    .Where(o => o.Total > 100)
    .Select(o => new { o.Id, o.Total })
    .ToListAsync(ct);

// Ändern mit Tracking
var order = await db.Orders.Include(o => o.Lines).SingleAsync(o => o.Id == id, ct);
order.Total += 10;
await db.SaveChangesAsync(ct);           // UPDATE ... WHERE Id = @id AND RowVersion = @old

// Massenänderung ohne Tracker (EF Core 7+)
await db.Orders.Where(o => o.Total == 0).ExecuteDeleteAsync(ct);

Nicht ausgeführt.

  1. Die erste Abfrage nutzt AsNoTracking und Select. Sie lädt nur Id und Total und trackt nichts.
  2. Die zweite Abfrage trackt. SaveChangesAsync erkennt die Änderung an Total.
  3. Das [Timestamp]-Feld steht im WHERE des UPDATE. Ändert jemand anderes die Zeile, wirft EF DbUpdateConcurrencyException.
  4. ExecuteDeleteAsync läuft als ein SQL, ohne Objekte zu laden.

Vergleich

  • EF Core: LINQ, Change Tracker, SaveChanges, Migrations. Lazy Loading ist aus.
  • JPA mit Hibernate: JPQL, Persistence Context, Flush. Lazy Loading ist bei Collections üblich.
  • Dapper: Eigenes SQL und schnelles Mapping. Kein Tracking, keine Migrations.
  • Raw SQL in EF: FromSql und ExecuteSql für Fälle, die LINQ nicht gut abbildet.
  • Spring Data: Repositories über JPA. In EF Core ist DbSet das Repository.
  • Unit of Work: In EF Core ist der DbContext selbst die Unit of Work.

Produktion

  1. N+1: Eine Abfrage pro Element in einer Schleife. Lösung: Include, Projektion oder Split Query.
  2. Cartesian Explosion: Mehrere Collection-Includes erzeugen riesige Ergebnisse. Lösung: AsSplitQuery() oder getrennte Abfragen.
  3. Zu viel Tracking: Grosse Leselisten mit Tracking brauchen viel Speicher. Lösung: AsNoTracking().
  4. Singleton-Context: Ein geteilter DbContext erzeugt Fehler wie "A second operation started on this context". Lösung: scoped oder Factory.
  5. Lost Update: Die letzte Änderung überschreibt still. Lösung: Concurrency Token.
  6. Migration beim Start: Mehrere Instanzen migrieren gleichzeitig. Lösung: Migration Bundle als eigener Deploy-Schritt.

Diagnose: Werkzeuge und Befehle

  • optionsBuilder.LogTo(Console.WriteLine) oder Logging der Kategorie Microsoft.EntityFrameworkCore.Database.Command: zeigt das SQL.
  • query.ToQueryString(): zeigt das SQL einer Abfrage ohne Ausführung.
  • Der Query-Plan der Datenbank (EXPLAIN): zeigt fehlende Indizes.
  • dotnet ef migrations script: zeigt das SQL einer Migration vor dem Rollout.
  • dotnet-counters: zeigt GC und Allokationen bei zu viel Tracking.
  • Ein Test mit einer echten Datenbank (zum Beispiel im Container): findet Übersetzungsfehler, die In-Memory-Provider verdecken.

Senior-Punkte

  1. Abfragen sind Code mit Kosten. Immer das erzeugte SQL und die Zahl der Abfragen ansehen.
  2. Lesen und Schreiben trennen. Lesen mit Projektion ohne Tracking. Schreiben mit Tracking oder ExecuteUpdate.
  3. Concurrency ist ein Design-Thema. Ein Token gehört in jede Entität, die mehrere Nutzer ändern.
  4. Der DbContext ist keine Cache-Schicht. Er ist kurzlebig und nicht thread-sicher.
  5. Migrationen sind Deployments. Prüfen, versionieren, als Bundle ausführen und Rollback planen.
  6. Wo EF nicht passt, nimmt man SQL. Raw SQL oder Dapper für Berichte und Massenoperationen.
