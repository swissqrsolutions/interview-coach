Blazor

Kern: Blazor ist ein Web-UI-Framework, das Razor-Komponenten in C# statt in JavaScript schreibt. Jede Komponente hat einen Render Mode. Er legt fest, ob sie auf dem Server oder im Browser läuft und ob sie interaktiv ist.

Antwort-Muster

Frage: Wie funktioniert Blazor, und welche Render Modes gibt es?

  1. Mechanismus: Eine Komponente baut einen Render-Baum. Bei Änderungen entsteht ein Diff, der das DOM aktualisiert.
  2. Zahl: Es gibt vier Render Modes: Static Server, Interactive Server, Interactive WebAssembly und Interactive Auto. Der Standard ist Static.
  3. Trade-off: Interactive Server startet schnell, braucht aber eine dauernde Verbindung und hat Latenz. WebAssembly lädt die Runtime, läuft dann im Browser.
  4. Produktion: Ich wähle den Mode pro Seite, achte auf Zustand bei Verbindungsabbruch und gebe Ressourcen in Dispose frei.

1. Ein Klick bei Interactive Server in 6 Schritten

  1. Erste Seite: Der Server rendert die Seite zu HTML. Interaktive Komponenten werden standardmässig zuerst vorgerendert (Prerendering).
  2. Circuit: Der Browser baut eine Verbindung zum Server auf. Sie heisst Circuit und nutzt SignalR. Erst jetzt ist die Komponente interaktiv.
  3. Klick: Der Nutzer klickt eine Schaltfläche. Das Event geht über die Verbindung zum Server.
  4. Handler: Die Methode in der Komponente läuft auf dem Server. Sie ändert den Zustand.
  5. Render-Diff: Nach dem Handler rendert die Komponente neu. Blazor vergleicht den neuen Render-Baum mit dem alten und bildet einen Diff.
  6. Browser: Nur der Diff geht zum Browser. Dort wird das DOM angepasst.

Bei Interactive WebAssembly läuft derselbe Code im Browser. Dann entfallen die Schritte 2 und 3 über das Netz. Dafür lädt der Browser die .NET-Runtime.

2. Aufbau

  1. Eine Razor-Komponente ist eine .razor-Datei. Sie mischt HTML und C#.
  2. Der Render Mode wird mit @rendermode an der Komponente gesetzt.
  3. Der Render-Baum beschreibt die Ausgabe. Beim Update wird nur der Diff angewendet.
  4. Der Lifecycle hat feste Methoden. SetParametersAsync, OnInitialized, OnParametersSet und OnAfterRender.
  5. Der Zustand liegt in Feldern, Parametern und DI-Diensten.
  6. Ab .NET 8 nutzt die Blazor Web App die Render Modes.

3. Details

  1. Static Server: Die Komponente rendert auf dem Server zu HTML und ist nicht interaktiv. Das ist der Standard-Render-Mode. Formulare und Links laufen über normale Requests.
  2. Interactive Server: Die Komponente läuft auf dem Server. Der Browser spricht über eine Echtzeit-Verbindung (Circuit). Jede Aktion braucht einen Netzwerk-Weg.
  3. Interactive WebAssembly: Die Komponente läuft im Browser auf einer WebAssembly-.NET-Runtime. Komponenten, Abhängigkeiten und Runtime werden zum Browser geladen. Der Browser speichert sie im Cache.
  4. Interactive Auto: Die Komponente startet mit Interactive Server. Beim nächsten Besuch läuft sie im Browser, wenn das Bundle geladen ist.
  5. Prerendering: Interaktive Modes rendern standardmässig zuerst statisch auf dem Server. Das zeigt schnell Inhalt. Danach wird die Komponente interaktiv und läuft ihren Lifecycle erneut.
  6. Lifecycle-Reihenfolge: Beim ersten Rendern kommen SetParametersAsync, OnInitialized{Async} und OnParametersSet{Async}. Dann rendert die Komponente und OnAfterRender{Async} läuft.
  7. StateHasChanged: Er stellt ein neues Rendern in die Warteschlange. Nach einem Event-Handler passiert das automatisch. Bei Änderungen von aussen, etwa einem Timer, ruft man ihn selbst auf.
  8. Rendering steuern: ShouldRender kann ein Neu-Rendern unterdrücken. Das spart Arbeit bei teuren Komponenten.
  9. Interactive Server Nachteile: Latenz bei jeder Interaktion. Kein Offline. Der Server hält Zustand für jede Verbindung. Skalierung braucht Serverressourcen.
  10. WebAssembly Nachteile: Der erste Start lädt die Runtime. Die Grösse der App ist wichtig. Der Code ist im Browser sichtbar und muss API-Aufrufe absichern.
  11. Zustand bei Abbruch: Bricht die Verbindung ab, ist der Zustand im Server-Speicher in Gefahr. Wichtiges gehört in eine Datenbank oder in den Browser-Speicher.
  12. Dispose: Komponenten implementieren IDisposable oder IAsyncDisposable, um Events und Timer zu lösen. Sonst bleiben Ressourcen hängen.

4. Fallen

  • „Blazor heisst, der Code läuft immer im Browser.“ → Falsch. Nur bei WebAssembly. Bei Interactive Server läuft er auf dem Server, bei Static Server nur beim Rendern.
  • „Die Standard-Komponente in einer Blazor Web App ist interaktiv.“ → Falsch. Der Standard ist Static Server. Interaktivität braucht einen Render Mode wie @rendermode InteractiveServer.
  • „Interactive Server braucht keine dauernde Verbindung.“ → Falsch. Er braucht eine offene Verbindung (Circuit). Bricht sie ab, ist die Seite nicht mehr interaktiv.
  • „Code in WebAssembly ist vor dem Nutzer geschützt.“ → Falsch. Der Code und die Daten laufen beim Nutzer. Geheimnisse gehören auf den Server hinter eine API.
  • „Beim Prerendering läuft der Lifecycle nur einmal.“ → Falsch. Er läuft zuerst beim statischen Rendern und danach erneut, wenn die Komponente interaktiv wird.
  • „StateHasChanged muss man nach jedem Handler rufen.“ → Falsch. Nach einem Event-Handler rendert Blazor automatisch neu. Nur bei Änderungen von aussen ist er nötig.

5. Selbsttest

Warum?

Warum nutzt man Blazor?

Man schreibt UI und Logik in C# und teilt Code mit dem Backend. Man braucht dafür kein eigenes JavaScript-Framework.

Warum gibt es mehrere Render Modes?

Server und Browser haben verschiedene Vor- und Nachteile. Man wählt je Seite oder Komponente den Mode, der passt.

Warum gibt es Prerendering?

Der Nutzer sieht schnell Inhalt, bevor die Verbindung oder die Runtime bereit ist.

Wie innen?

Wie aktualisiert Blazor das DOM?

Die Komponente baut einen Render-Baum. Blazor vergleicht ihn mit dem alten Baum und wendet nur den Diff auf das DOM an.

Was ist ein Circuit?

Die Verbindung zwischen Browser und Server bei Interactive Server. Auf dem Server hängt der Zustand der Komponenten daran.

Was ist die Reihenfolge im Lifecycle?

SetParametersAsync, OnInitialized, OnParametersSet, Rendern, OnAfterRender.

Was macht Interactive Auto?

Erst läuft die Komponente per Server. Wenn das Bundle im Browser liegt, läuft sie danach im Browser.

Zahlen

Wie viele Render Modes gibt es?

Vier: Static Server, Interactive Server, Interactive WebAssembly und Interactive Auto.

Welcher Render Mode ist Standard?

Static Server. Die Komponente ist dann nicht interaktiv.

Welche Lifecycle-Methoden gibt es synchron und async?

OnInitialized, OnParametersSet und OnAfterRender haben je eine sync und eine Async-Variante.

Vergleich

Interactive Server vs WebAssembly?

Server startet schnell, hat aber Latenz je Aktion und braucht eine Verbindung. WebAssembly lädt die Runtime und läuft dann lokal, auch ohne Server-Verbindung.

Blazor vs Angular oder React?

Blazor nutzt C# und .NET. Angular und React nutzen TypeScript oder JavaScript. Blazor hat ein kleineres Ökosystem für UI-Bibliotheken.

Blazor Server vs Vaadin?

Beide halten die UI-Logik auf dem Server. Die Idee ist ähnlich, Vaadin nutzt Java und Blazor C#.

Static SSR vs Interactive?

Static SSR liefert HTML ohne Interaktivität. Interactive hält eine Komponente lebendig, mit Zustand und Events.

Produktion

Was passiert, wenn die Verbindung bei Interactive Server abbricht?

Die Seite ist nicht mehr interaktiv. Der Zustand im Circuit kann verloren gehen. Man speichert Wichtiges ausserhalb.

Wie skaliert man Interactive Server?

Jede Verbindung braucht Serverressourcen. Man plant Speicher pro Nutzer ein. Die Doku empfiehlt den Azure SignalR Service für viele Verbindungen.

Szenario: Die Startseite der WebAssembly-App lädt zu langsam. Was tun Sie?

Ich prüfe die Grösse des Downloads. Ich nutze Prerendering, Trimming, Lazy Loading von Assemblies und Caching. Ich prüfe, ob Interactive Auto oder Static SSR reicht.

Szenario: Auf einer Admin-Seite verschwinden Eingaben nach kurzer Netzstörung. Was tun Sie?

Das ist ein Circuit-Abbruch bei Interactive Server. Ich speichere Entwürfe im Browser oder in der Datenbank. Ich zeige eine Meldung beim Wiederverbinden.

Design

Wie wähle ich den Render Mode?

Für Inhalte ohne Interaktion reicht Static Server. Für interne Tools passt Interactive Server. Für Offline oder viel lokale Arbeit nehme ich WebAssembly.

Wie greife ich in WebAssembly auf Daten zu?

Über eine API mit Authentifizierung, wie bei einer Single-Page-App. Der Browser ist nicht vertrauenswürdig.

Wie vermeide ich Speicherlecks?

Events abmelden und Timer stoppen in Dispose. Beim Interactive Server auch Zustand pro Circuit klein halten.

Mehr

Gerüst

  • Warum? UI in C# mit Komponenten, geteilter Code, kein eigenes JavaScript-Framework.
  • Wie innen? Render-Baum und Diff. Circuit bei Interactive Server. Lifecycle mit festen Methoden.
  • Zahlen Vier Render Modes. Standard ist Static Server.
  • Vergleich Server gegen WebAssembly. Gegen Angular oder React. Gegen Vaadin.
  • Produktion Verbindungsabbruch, Ladegrösse, Speicher je Circuit, Lecks ohne Dispose.
  • Design Mode pro Seite wählen, API für Daten, Zustand ausserhalb des Circuits sichern.

Beispiel: Komponente mit Render Mode

@page "/counter"
@rendermode InteractiveServer
@implements IDisposable

<h1>Zähler</h1>
<p>Stand: @count</p>
<button @onclick="Inc">Plus</button>

@code {
    private int count;
    private Timer? timer;

    protected override void OnInitialized()
    {
        timer = new Timer(_ => InvokeAsync(() => { count++; StateHasChanged(); }), null, 1000, 1000);
    }

    private void Inc() => count++;   // nach einem Event-Handler rendert Blazor automatisch

    public void Dispose() => timer?.Dispose();
}

Nicht ausgeführt.

  1. @rendermode InteractiveServer macht die Komponente interaktiv. Sie läuft auf dem Server.
  2. Inc ändert nur das Feld. Nach dem Handler rendert Blazor automatisch neu.
  3. Der Timer ändert count ausserhalb eines Handlers. Darum ruft der Code StateHasChanged über InvokeAsync auf.
  4. Dispose stoppt den Timer. Ohne das läuft er weiter, nachdem die Komponente weg ist.

Vergleich

  • Blazor Server (Interactive Server): UI-Logik auf dem Server, Verbindung nötig, kleiner Download.
  • Blazor WebAssembly: Logik im Browser, grosser Erst-Download, danach lokal.
  • Static SSR: HTML vom Server, wenig Overhead, keine Interaktion.
  • Angular, React: TypeScript oder JavaScript im Browser, grosses Ökosystem.
  • Vaadin, JSF: Server-seitige UI in Java. Blazor Server hat eine ähnliche Idee.
  • Thymeleaf und Razor Pages: Server rendert HTML pro Request, ohne Komponentenmodell im Browser.

Produktion

  1. Verbindungsabbruch: Interactive Server verliert Interaktivität und Zustand. Lösung: Wichtiges in der Datenbank sichern und Wiederverbinden anzeigen.
  2. Speicher pro Nutzer: Jeder Circuit hält Zustand auf dem Server. Lösung: Zustand klein halten, Kapazität planen, SignalR Service nutzen.
  3. Langer Erststart bei WebAssembly: Runtime und Assemblies müssen laden. Lösung: Prerendering, Trimming, Lazy Loading, Cache.
  4. Fehlende Dispose: Timer und Event-Handler halten Komponenten am Leben. Lösung: IDisposable und abmelden.
  5. Doppelte Initialisierung: Prerendering führt den Lifecycle zweimal aus. Lösung: Zustand beim Wechsel zum interaktiven Modus beachten.
  6. Geheimnisse im Browser: WebAssembly-Code ist beim Nutzer. Lösung: Schlüssel und Logik hinter eine abgesicherte API.

Diagnose: Werkzeuge und Befehle

  • Browser DevTools, Tab Network: zeigt Download-Grösse und die WebSocket-Verbindung.
  • Browser Konsole: zeigt Circuit-Fehler und Verbindungsabbrüche.
  • dotnet-counters: zeigt Speicher und GC auf dem Server bei vielen Circuits.
  • Server-Logs der Kategorie SignalR und Blazor: zeigen Verbindungsabbrüche.
  • dotnet publish mit Trimming: zeigt die Grösse der WebAssembly-App.
  • Unit-Tests für Komponenten, zum Beispiel mit bUnit: prüfen Rendering und Events ohne Browser.

Senior-Punkte

  1. Der Render Mode ist eine Architektur-Entscheidung. Er bestimmt Latenz, Skalierung, Offline und Sicherheit.
  2. Interactive Server verschiebt Last auf den Server. Kapazität und Verbindungsabbrüche gehören in die Planung.
  3. WebAssembly heisst: Browser ist nicht vertrauenswürdig. Auth und Regeln liegen in der API.
  4. Static SSR ist oft genug. Nicht jede Seite braucht Interaktivität.
  5. Lifecycle und Dispose verstehen. Prerendering und Wiederverbinden führen Code mehrfach aus.
  6. Teamfrage: Blazor lohnt sich, wenn das Team C# stark nutzt und weniger JavaScript pflegen will.
