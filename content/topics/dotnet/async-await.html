async/await in .NET

Kern: async/await lässt Code auf I/O warten, ohne einen Thread zu blockieren. Der Compiler baut aus der Methode eine State Machine. Ein Task ist das Objekt, das Status, Ergebnis oder Exception hält.

Antwort-Muster

Frage: Wie funktioniert async/await in .NET?

  1. Mechanismus: Der Compiler baut eine State Machine. Bei await gibt die Methode den Thread frei und läuft später weiter.
  2. Zahl: Code vor dem ersten await läuft synchron auf dem Aufrufer-Thread. Danach läuft er meist auf einem Pool-Thread.
  3. Trade-off: Async spart Threads bei I/O. Bei CPU-Arbeit hilft es nicht. Jede async-Methode kostet etwas Speicher.
  4. Produktion: Ich blockiere nie mit .Result oder .Wait(). Ich gebe den CancellationToken weiter und nutze WhenAll für parallele Aufrufe.

1. Ein await in 6 Schritten

  1. Aufruf: Die async-Methode startet wie jede andere. Der Code bis zum ersten await läuft auf dem Thread des Aufrufers.
  2. await: Der Compiler fragt den Awaiter des Tasks, ob er fertig ist. Ist er fertig, läuft der Code ohne Pause weiter.
  3. Rückgabe: Ist der Task nicht fertig, merkt die State Machine den Zustand. Die Methode gibt ihren eigenen Task zurück. Der Thread ist frei.
  4. I/O läuft: Das Betriebssystem arbeitet an der Anfrage. Es braucht dafür keinen Thread, der wartet.
  5. Fortsetzung: Ist der Task fertig, ruft der Awaiter die Continuation auf. Sie ruft MoveNext() der State Machine auf.
  6. Task fertig: Am Ende setzt die Methode das Ergebnis im Task. Bei einem Fehler speichert sie die Exception im Task.

Im Demo unten läuft Work start auf Thread 1. Nach dem await läuft der Rest auf Thread 5.

2. Aufbau

  1. Ein Task (oder Task<T>) hält den Status, das Ergebnis oder die Exception.
  2. Die State Machine ist vom Compiler erzeugt. Lokale Variablen werden zu Feldern.
  3. Der Awaiter hat IsCompleted und OnCompleted. await ruft sie auf.
  4. Der TaskScheduler und der SynchronizationContext bestimmen, wo die Fortsetzung läuft.
  5. Das Thread-Pool führt Fortsetzungen aus, wenn kein Kontext vorhanden ist.
  6. Der CancellationToken meldet Abbruch. Er wird als Parameter durchgereicht.

3. Details

  1. Task ist kein Thread: Ein Task ist ein Objekt für ein späteres Ergebnis. Bei I/O läuft dafür gar kein Thread. Nur bei Task.Run läuft Code auf einem Pool-Thread.
  2. State Machine: Der Compiler macht aus der Methode eine Klasse oder einen struct mit MoveNext(). Ein Feld merkt die Position. Lokale Variablen werden zu Feldern. Jedes await ist ein möglicher Sprung zurück.
  3. Synchroner Anfang: Eine async-Methode läuft synchron bis zum ersten await, der nicht fertig ist. Auch ein Fehler vor dem ersten await landet erst im Task. Argumentprüfungen macht man oft in einer nicht-async Hülle.
  4. SynchronizationContext: Er legt fest, wo die Fortsetzung läuft. Eine UI-App kehrt zum UI-Thread zurück. Eine Konsolen-App hat keinen Kontext, dort läuft sie im Thread-Pool.
  5. ConfigureAwait(false): Es sagt, dass die Fortsetzung nicht zum alten Kontext zurück muss. Bibliotheken nutzen es oft. In ASP.NET Core läuft App-Code ohnehin auf normalen Pool-Threads.
  6. Exceptions: Eine Exception in einer async-Methode wird im Task gespeichert. Erst await wirft sie wieder. Bei Task.WhenAll wirft await nur die erste. Alle stehen in task.Exception.
  7. async void: Nur für Event-Handler nutzen. Der Aufrufer bekommt keinen Task und kann nicht warten. Eine Exception kann er nicht fangen.
  8. Cancellation: Abbruch ist kooperativ. Der Code prüft den Token oder gibt ihn an Task.Delay und HttpClient weiter. Ein Abbruch wirft OperationCanceledException.
  9. WhenAll und WhenAny: WhenAll wartet auf alle Tasks. WhenAny wartet auf den ersten und liefert diesen Task. Danach muss man den fertigen Task selbst awaiten, sonst geht ein Fehler verloren.
  10. Task.Run: Nur für CPU-intensive Arbeit, die man vom aktuellen Thread weg will. In ASP.NET Core soll man Task.Run nicht für eine sync API als Async-Hülle nutzen. Es kostet nur einen zweiten Thread.
  11. ValueTask: Er spart eine Allokation, wenn das Ergebnis oft schon fertig ist. Die Doku sagt, man nutzt ihn nur nach einer Messung. Man darf ihn nur einmal auswerten.
  12. Blockieren: .Result und .Wait() blockieren einen Thread. Viele davon führen zu Thread Pool Starvation. In einer UI-App oder mit einem Kontext kann es einen Deadlock geben.

4. Fallen

  • „async macht den Code automatisch parallel.“ → Falsch. Es macht ihn nicht parallel. await startet nichts Neues. Parallel wird es erst mit mehreren gestarteten Tasks und WhenAll.
  • „Ein Task läuft immer auf einem eigenen Thread.“ → Falsch. Bei I/O läuft gar kein Thread. Nur Task.Run nutzt einen Pool-Thread.
  • „.Result ist harmlos, wenn der Task schnell ist.“ → Falsch. Es blockiert einen Thread. Unter Last führt das zu Thread Pool Starvation. Mit Kontext droht ein Deadlock.
  • „await Task.WhenAll(...) zeigt alle Fehler.“ → Falsch. Es wirft nur die erste Exception. Alle stehen in task.Exception.InnerExceptions.
  • „async void ist wie async Task.“ → Falsch. Der Aufrufer kann nicht warten und keine Exception fangen. Nur für Event-Handler.
  • „In einer async-Methode wirft ein Fehler sofort beim Aufruf.“ → Falsch. Die Exception steckt im Task. Sie wird erst bei await geworfen.

5. Selbsttest

Warum?

Warum nutzt man async/await bei I/O?

Ein Thread muss nicht auf die Antwort warten. Er kann andere Anfragen bearbeiten. So bedient ein Server mit wenig Threads viele Anfragen.

Warum ist .Result gefährlich?

Es blockiert einen Thread, bis der Task fertig ist. Unter Last gehen die Pool-Threads aus. Mit einem Kontext kann es einen Deadlock geben.

Warum gibt es ConfigureAwait(false)?

Es verhindert den Rückweg in den alten Kontext. Das vermeidet Deadlocks und spart Aufwand in Bibliotheken.

Wie innen?

Was baut der Compiler aus einer async-Methode?

Eine State Machine mit der Methode MoveNext(). Sie hat ein Zustandsfeld und Felder für die lokalen Variablen.

Was macht await genau?

Es holt den Awaiter. Ist IsCompleted wahr, läuft der Code weiter. Sonst meldet es die Fortsetzung mit OnCompleted an und gibt die Methode zurück.

Wo läuft die Fortsetzung nach await?

Mit SynchronizationContext dort, zum Beispiel auf dem UI-Thread. Ohne Kontext auf einem Thread-Pool-Thread.

Wo landet eine Exception in einer async-Methode?

Im zurückgegebenen Task. Erst await oder .Result wirft sie wieder.

Zahlen

Wie lange dauern drei Delays von 200 ms nacheinander?

Etwa 600 ms. Mit Task.WhenAll laufen sie zusammen und brauchen etwa 200 ms. Das zeigt das Demo.

Wie viele Exceptions kann ein Task halten?

Beliebig viele in Task.Exception.InnerExceptions. Bei zwei fehlgeschlagenen Tasks in WhenAll sind es 2.

Welches Suffix hat eine async-Methode?

Async, zum Beispiel GetUserAsync. Das ist die Konvention des Task-based Asynchronous Pattern.

Vergleich

Task vs Java CompletableFuture?

Beide stehen für ein späteres Ergebnis. await macht den Code lesbar wie sequentiell. CompletableFuture braucht Ketten mit thenApply.

async/await vs Java Virtual Threads?

Virtual Threads blockieren billig, der Code bleibt normal. In C# markiert async die Methode und der Compiler baut eine State Machine.

Task vs ValueTask?

ValueTask spart eine Allokation bei oft sofortigem Ergebnis. Er hat Regeln für die Nutzung. Standard ist Task.

WhenAll vs sequentielles await?

WhenAll startet alles zuerst und wartet dann. Sequentiell wartet jedes Mal, die Zeiten addieren sich.

Produktion

Wie erkennt man Thread Pool Starvation?

Anfragen werden langsam, obwohl die CPU wenig arbeitet. dotnet-counters zeigt eine wachsende Thread-Pool-Queue und wenige freie Threads.

Was tun gegen blockierende Aufrufe in einer API?

Blockierende Stellen suchen und durch async API ersetzen. Kein .Result und kein .Wait(). Kein Task.Run als Alibi.

Szenario: Ein ASP.NET-Core-Dienst wird unter Last langsam, die CPU ist niedrig. Was tun Sie?

Ich vermute Thread Pool Starvation. Mit dotnet-counters sehe ich die Queue. Ich suche .Result, .Wait() und sync I/O und stelle sie auf async um.

Szenario: Eine Fehlermeldung aus einem Hintergrund-Task fehlt im Log. Warum?

Der Task wurde nicht awaited, die Exception blieb im Task. Oder es war async void. Ich awaite den Task oder fange die Exception und logge sie.

Design

Wie reiche ich den Abbruch weiter?

Jede async-Methode bekommt einen CancellationToken als letzten Parameter. Sie gibt ihn an alle Aufrufe weiter, die ihn annehmen.

Wie rufe ich 10 Dienste parallel auf?

Alle Tasks zuerst starten und in einer Liste sammeln. Dann await Task.WhenAll(tasks). Bei Grenzen helfen SemaphoreSlim oder Parallel.ForEachAsync.

Wann nehme ich Task.Run?

Für CPU-Arbeit in einer UI-App, damit der UI-Thread frei bleibt. Nicht, um eine sync I/O-Methode async zu tarnen.

  • Wie innen? State Machine mit MoveNext(). await fragt den Awaiter und gibt die Methode frei.

Beispiel: async/await live

async Task Work() { T("Work start"); await Task.Delay(50); T("Work after await"); }
var t = Work(); T("Caller continues, task done: " + t.IsCompleted);
await t;

for (int i = 0; i < 3; i++) await Task.Delay(200);                 // nacheinander
await Task.WhenAll(Task.Delay(200), Task.Delay(200), Task.Delay(200));

async Task Boom() { await Task.Yield(); throw new InvalidOperationException("boom"); }
var bt = Boom();
try { await bt; } catch (Exception e) { Console.WriteLine("caught at await: " + e.Message); }

var w = Task.WhenAll(Fail("a"), Fail("b"));
try { await w; } catch (Exception e) { /* e.Message = "a", w.Exception hat 2 */ }

try { await Task.Delay(5000, cts.Token); } catch (OperationCanceledException) { }

  1. SynchronizationContext.Current ist null. Eine Konsolen-App hat keinen Kontext.
  2. Work start und Caller continues laufen beide auf Thread 1. Der Rest nach await läuft auf Thread 5.
  3. Drei Delays nacheinander dauern etwa 600 ms. Mit WhenAll sind es etwa 200 ms.
  4. Der Task bt existiert schon, aber der Fehler kommt erst beim await.

Vergleich

  • Task: Status, Ergebnis oder Exception. Entspricht ungefähr CompletableFuture.
  • Virtual Threads (Java): Blockieren kostet fast nichts. Kein async-Schlüsselwort nötig.
  • async/await (C#): Der Compiler baut die State Machine. Der Code bleibt lesbar.
  • ValueTask: Struct, spart eine Allokation. Nur einmal nutzen.
  • Parallel.ForEachAsync: Parallele Schleife mit Begrenzung.
  • Thread: Eigene Threads nur für lange Spezialarbeit. Sonst Task und Pool.
  • Task.Run: Schiebt CPU-Arbeit auf einen Pool-Thread.

Produktion

  1. Thread Pool Starvation: Viele blockierende .Result-Aufrufe halten die Pool-Threads. Anfragen warten. Lösung: überall async nutzen. Blockierende Stellen finden.
  2. Deadlock mit Kontext: .Result wartet, die Fortsetzung will in denselben Kontext. Lösung: nicht blockieren, sonst ConfigureAwait(false) in Bibliotheken.
  3. Verlorene Exceptions: Ein Task wird gestartet, aber nie awaited. Lösung: immer await oder bewusst behandeln.
  4. Kein Timeout: Ein Aufruf hängt ewig. Lösung: CancellationToken mit Timeout.
  5. Zu viele parallele Aufrufe: WhenAll auf 10 000 Tasks überlastet den Dienst. Lösung: begrenzen mit SemaphoreSlim oder Parallel.ForEachAsync.
  6. Zu viel async in heissen Pfaden: Jede Methode kostet eine State Machine. Lösung: ValueTask nur nach Messung.

Diagnose: Werkzeuge und Befehle

  • dotnet-counters monitor: zeigt Thread-Pool-Länge der Queue und Thread-Anzahl.
  • dotnet-stack report und dotnet-dump: zeigen, wo Threads blockiert sind.
  • dotnet-trace: sammelt Traces und zeigt Task-Ereignisse.
  • Roslyn Analyzer: warnen bei async void und bei nicht awaited Tasks.
  • Im Debugger das Fenster Tasks (Visual Studio) zeigt wartende Tasks.
  • Suche im Code nach .Result, .Wait() und GetAwaiter().GetResult().

Senior-Punkte

  1. Async ist ein Vertrag von oben bis unten. Eine blockierende Stelle in der Mitte macht den Gewinn kaputt.
  2. Async hilft bei I/O, nicht bei CPU. Für CPU-Arbeit braucht man Parallelität und mehr Kerne.
  3. Jeder Aufruf nach aussen braucht Timeout und Abbruch. Ohne sie hängt ein langsamer Dienst den ganzen Pool.
  4. Parallelität begrenzen. WhenAll ohne Grenze ist ein Selbst-Angriff auf den Nachbardienst.
  5. Fehler sind Daten im Task. Wer nicht awaited, verliert sie.
  6. Gegenüber Java: Virtual Threads lösen dasselbe Problem anders. In .NET ist der Preis die Einfärbung der Methoden.
