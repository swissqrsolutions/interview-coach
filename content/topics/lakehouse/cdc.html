Change Data Capture

Kern: Change Data Capture (CDC) ist das Erfassen jeder Änderung (Insert, Update, Delete) einer Datenbank als Strom von Events. Es löst das Problem, Zieltabellen aktuell zu halten, ohne immer ganze Tabellen zu kopieren. Gutes CDC liest das Transaktions-Log der Datenbank und sieht so auch Deletes und Zwischenstände.

1. Wo sitzt CDC?

  1. WAL (Write-Ahead Log): Jede Änderung steht zuerst im Log der Datenbank. In SQL Server heisst es Transaction Log, in MySQL Binlog.
  2. Replication Slot: ein Lesezeiger im WAL. PostgreSQL löscht kein WAL, das der Slot noch braucht.
  3. Debezium: ein Open-Source-CDC-Tool als Kafka-Connect-Connector. Es liest das Log und macht daraus Events.
  4. Kafka: ein Topic pro Tabelle, Key = Primärschlüssel. So bleibt die Reihenfolge pro Zeile erhalten.
  5. Spark oder Flink: Sie lesen die Events, deduplizieren pro Schlüssel und wenden sie per MERGE an.
  6. Bronze und Silver: Bronze hält alle Events (Historie). Silver ist der aktuelle Spiegel der Quelltabelle.

2. Die Reise einer Änderung

  1. UPDATE: Eine App ändert die Stadt von Kunde 1 auf „Thun“ und macht COMMIT.
  2. WAL-Eintrag: Die Änderung steht im WAL mit einer LSN (Log Sequence Number). Sie ist eine wachsende Position im Log.
  3. Logical Decoding: Das Plugin pgoutput wandelt WAL-Bytes in logische Zeilen-Änderungen. Debezium liest sie über den Slot. Nur committete Transaktionen kommen an.
  4. Event: Debezium baut ein Event mit op (c create, u update, d delete, r Snapshot-Read, t truncate), before, after und source (LSN, Transaktions-ID).
  5. Kafka: Key ist der Primärschlüssel. Alle Events von Kunde 1 landen in derselben Partition, in Reihenfolge.
  6. Micro-Batch: Spark sammelt Events. Pro Schlüssel bleibt nur das letzte Event nach LSN.
  7. MERGE: Spark wendet es auf Silver an: Update, Insert oder Delete. Mit dem Commit merkt sich Spark den Kafka-Offset im Checkpoint.

3. Beispiel: Query-basiert gegen Log-basiert

-- Kunde 1: Bern → Thun → Zürich, Kunde 2 gelöscht, Kunde 3 neu.
-- Log per Trigger als Stand-in für das WAL (wal_level ist hier nicht 'logical').
\echo '--- Query-basiert: WHERE updated_at > High-Water Mark'
SELECT id, city FROM customer WHERE updated_at > (SELECT ts FROM hwm) ORDER BY id;
\echo '--- Log-basiert: alle Änderungen in Reihenfolge'
SELECT lsn, op, id, after->>'city' AS city FROM change_log ORDER BY lsn;
-- Anwenden: pro id nur die letzte Änderung, dann MERGE
MERGE INTO silver_customer t
USING (SELECT DISTINCT ON (id) id, op, after->>'city' AS city
       FROM change_log WHERE lsn > 2 ORDER BY id, lsn DESC) s
ON t.id = s.id
WHEN MATCHED AND s.op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET city = s.city
WHEN NOT MATCHED AND s.op <> 'd' THEN INSERT VALUES (s.id, s.city)
RETURNING merge_action(), t.*;
--- Query-basiert: WHERE updated_at > High-Water Mark
 id |  city
----+--------
  1 | Zürich
  3 | Genf
(2 rows)

--- Log-basiert: alle Änderungen in Reihenfolge
 lsn | op | id |  city
-----+----+----+--------
   1 | i  |  1 | Bern
   2 | i  |  2 | Basel
   3 | u  |  1 | Thun
   4 | u  |  1 | Zürich
   5 | d  |  2 |
   6 | i  |  3 | Genf
(6 rows)

 merge_action | id |  city
--------------+----+--------
 UPDATE       |  1 | Zürich
 DELETE       |  2 | Basel
 INSERT       |  3 | Genf
(3 rows)

Echte Ausgabe, PostgreSQL 17.12 (Docker), Schema demo_cdc, danach gelöscht. Das Log entsteht hier per Trigger, weil wal_level = replica ist; Debezium würde es aus dem WAL lesen. Debezium schreibt c statt i.

  1. Query-basiert sieht nicht, dass Kunde 2 gelöscht wurde. Er sieht auch „Thun“ nicht. Das Ziel behält Kunde 2 für immer.
  2. Log-basiert sieht alle 6 Änderungen in Reihenfolge, auch das Delete.
  3. Für den aktuellen Stand zählt pro id nur das letzte Event. DISTINCT ON … ORDER BY lsn DESC wählt es.
  4. merge_action() (neu in PostgreSQL 17) zeigt: 1 Update, 1 Delete, 1 Insert.

Dasselbe in Spark auf Iceberg:

latest = (cdc_df  # aus Kafka, Debezium-JSON entpackt
  .withColumn("rn", F.row_number().over(
      Window.partitionBy("id").orderBy(F.col("source.lsn").desc())))
  .filter("rn = 1"))
latest.createOrReplaceTempView("changes")
spark.sql("""
  MERGE INTO lake.silver.customer t USING changes s ON t.id = s.id
  WHEN MATCHED AND s.op = 'd' THEN DELETE
  WHEN MATCHED THEN UPDATE SET t.city = s.after.city
  WHEN NOT MATCHED AND s.op != 'd' THEN INSERT (id, city) VALUES (s.id, s.after.city)""")

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): ein Iceberg-Snapshot pro Batch. Ohne Dedup bricht MERGE ab, weil Iceberg pro Zielzeile nur eine passende Quellzeile erlaubt.

4. Details, die Interviewer fragen

  1. Initialer Snapshot: Der Slot sieht nur Änderungen ab seiner Erstellung. Darum liest Debezium zuerst alle Zeilen (op = r). Standard ist snapshot.mode = initial. Andere Modi: no_data, when_needed, always.
  2. Inkrementeller Snapshot: Debezium kann grosse Tabellen in Stücken nachladen, während das Streaming weiterläuft. Ausgelöst über ein Signal, z. B. eine Signal-Tabelle.
  3. REPLICA IDENTITY: Standard schreibt bei Update und Delete nur den Primärschlüssel ins WAL. Mit REPLICA IDENTITY FULL enthält before alle alten Spalten. Kosten: mehr WAL.
  4. Tombstone: Nach einem Delete schickt Debezium ein Event mit gleichem Key und Wert null. Kafka Log Compaction löscht dann alle älteren Events zu diesem Key.
  5. WAL-Wachstum: Ein Slot hält WAL, bis Debezium bestätigt. Steht Debezium still, läuft die Platte voll. Schutz: max_slot_wal_keep_size und Monitoring von pg_replication_slots.
  6. Heartbeats: Ändern sich nur andere Tabellen, bestätigt Debezium keine neue LSN. heartbeat.interval.ms schickt regelmässig Events, damit der Slot weiterrückt.
  7. Reihenfolge: nur pro Kafka-Partition garantiert. Darum Key = Primärschlüssel und im Ziel nach LSN ordnen, nicht nach Ankunft.
  8. Duplikate: Nach einem Neustart kann Debezium Events erneut senden (at-least-once). Darum MERGE nach Schlüssel und LSN, nie blind INSERT.
  9. Schema-Änderungen: Ein ALTER TABLE ändert die Events. Mit einer Schema Registry (Avro) und Iceberg Schema Evolution kommen neue Spalten sauber an.
  10. Outbox Pattern: Der Service schreibt ein Event in eine Outbox-Tabelle, in derselben Transaktion wie die Daten. CDC liest die Outbox. So gibt es kein „DB geschrieben, Kafka nicht“.
  11. SQL Server: Dort liest ein SQL Agent Job das Log in Change-Tabellen (cdc.<schema>_<table>_CT). Debezium liest diese Change-Tabellen.
  12. Iceberg-Ziel: Viele kleine MERGEs erzeugen Delete Files. Merge-on-Read plus regelmässige Compaction.

5. Vergleich

  • Log-basiertes CDC (Debezium): sieht alles inkl. Deletes, wenig Last auf der Quelle, Reihenfolge exakt. Preis: Slots, Kafka Connect, Betrieb.
  • Query-basiertes CDC (updated_at > High-Water Mark): einfach, nur SQL. Aber keine Deletes, keine Zwischenstände, braucht eine verlässliche Spalte und einen Index.
  • Trigger-basiertes CDC: sieht alles, aber jede Schreib-Transaktion wird langsamer. Heute selten.
  • Voller Abzug (Full Load): ganze Tabelle kopieren und vergleichen. Robust für kleine Tabellen, teuer für grosse.
  • Outbox statt Tabellen-CDC: fachliche Events statt Zeilen-Änderungen. Gut zwischen Microservices.

6. In der Produktion

  1. Platte der Quell-DB voll: Debezium stand still, der Slot hielt WAL. Lösung: Slot-Lag alarmieren, max_slot_wal_keep_size setzen, toten Slot löschen und neu snapshotten.
  2. Failover der DB, Slot weg: Vor PostgreSQL 17 gingen logische Slots beim Failover verloren. PostgreSQL 17 kann sie auf den Standby synchronisieren (failover-Option). Sonst: neuer Snapshot.
  3. Gelöschte Zeilen bleiben im Ziel: Query-basiertes CDC oder Deletes im MERGE vergessen. Lösung: Log-basiert, op = 'd' behandeln.
  4. MERGE bricht ab: zwei Events für dieselbe Zeile im Batch. Lösung: vorher pro Schlüssel das letzte nach LSN nehmen.
  5. Alte Werte überschreiben neue: Events nach Ankunft statt nach LSN sortiert. Lösung: LSN in Silver speichern, nur neuere anwenden.
  6. Snapshot einer Riesentabelle dauert Tage: Lösung: inkrementeller Snapshot in Stücken.

7. Diagnose

  • SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) FROM pg_replication_slots; zeigt, wie viel WAL ein Slot zurückhält.
  • Kafka Connect REST: GET /connectors/<name>/status zeigt, ob Connector und Tasks laufen.
  • Debezium-Metriken (JMX): MilliSecondsBehindSource, Snapshot-Fortschritt.
  • Abgleich: Zeilenzahl und Prüfsumme pro Tabelle Quelle gegen Silver, z. B. täglich.
  • SQL Server: sys.dm_cdc_log_scan_sessions und sys.dm_cdc_errors.

8. Senior-Punkte

  1. CDC verlagert Komplexität, es entfernt sie nicht. Slots, Snapshots, Reihenfolge und Deletes sind die eigentliche Arbeit.
  2. Ein Slot ist ein Risiko für die Quelle. Ohne Monitoring kann CDC die produktive DB stoppen.
  3. Immer nach LSN, nie nach Ankunft. Nur die Position im Log ist eine verlässliche Reihenfolge.
  4. Bronze hält alle Events. Damit kann man Silver jederzeit neu bauen und Historie (SCD2) ableiten.
  5. Outbox für Fach-Events, Tabellen-CDC für Replikation. Interne Tabellen sind kein öffentlicher Vertrag.
  6. Nicht jede Quelle braucht CDC. Dateien mit Fristen oder kleine Tabellen sind mit Batch einfacher.

„CDC habe ich nicht produktiv eingesetzt; bei ElCom MATCH kommen die Daten als Dateien, darum habe ich eine Batch-Ingestion mit atomarem Claim gebaut, statt Änderungen aus SQL Server zu streamen.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „WHERE updated_at > letzter Lauf ist CDC.“ → Nur halb. Es verpasst Deletes und Zwischenstände.
  • „Debezium liefert exactly-once.“ → Falsch im Normalfall. Nach Neustarts kommen Duplikate. Das Ziel muss idempotent sein.
  • „Der Slot ist harmlos.“ → Falsch. Ein inaktiver Slot hält WAL, bis die Platte voll ist.
  • „Reihenfolge ist in Kafka garantiert.“ → Nur pro Partition. Key = Primärschlüssel nötig.
  • „Bei Delete reicht der Key im Event.“ → Für MERGE ja. Für Historie oder Audit braucht man before, also REPLICA IDENTITY FULL.

11. Fragen

Was ist CDC?

Das Erfassen jeder Änderung einer Datenbank als Event-Strom. Ziele bleiben aktuell, ohne ganze Tabellen zu kopieren.

Wie funktioniert log-basiertes CDC in PostgreSQL?

Logical Decoding liest das WAL über einen Replication Slot. Das Plugin pgoutput liefert Zeilen-Änderungen, Debezium macht daraus Events.

Was ist ein Replication Slot?

Ein Lesezeiger im WAL. PostgreSQL behält alles WAL, das der Slot noch nicht bestätigt hat.

Was steht in einem Debezium-Event?

op (c, u, d, r, t), before, after und source mit LSN, Transaktions-ID und Zeitstempel.

Warum braucht Debezium einen initialen Snapshot?

Der Slot kennt nur Änderungen ab seiner Erstellung. Der Snapshot liefert den Bestand als op = r.

Was ist ein inkrementeller Snapshot?

Debezium lädt eine Tabelle in Stücken nach, während das Streaming läuft. Ausgelöst per Signal.

Was bewirkt REPLICA IDENTITY FULL?

Update- und Delete-Events enthalten alle alten Spaltenwerte im before-Feld. Kostet mehr WAL.

Was ist ein Tombstone?

Ein Event mit gleichem Key und Wert null nach einem Delete. Kafka Log Compaction entfernt damit ältere Events zu diesem Key.

Warum kann CDC die Quell-DB gefährden?

Ein stehender Slot hält WAL zurück, die Platte läuft voll. Schutz: max_slot_wal_keep_size und Monitoring.

Wofür sind Heartbeats?

Ändern sich nur nicht erfasste Tabellen, rückt der Slot sonst nicht vor. Heartbeats lassen Debezium regelmässig eine LSN bestätigen.

Wie wenden Sie CDC-Events auf Iceberg an?

Pro Schlüssel das letzte Event nach LSN wählen, dann MERGE mit Delete, Update und Insert. Merge-on-Read plus Compaction.

Warum nach LSN sortieren und nicht nach Ankunft?

Ankunft kann sich nach Retries oder über Partitionen verschieben. Die LSN ist die echte Reihenfolge der Commits.

Was ist das Outbox Pattern?

Daten und Event werden in derselben Transaktion geschrieben, das Event in eine Outbox-Tabelle. CDC liest die Outbox und publiziert. Kein Dual-Write-Problem.

Was passiert bei einem DB-Failover?

Vor PostgreSQL 17 war der logische Slot weg, man brauchte einen neuen Snapshot. PostgreSQL 17 kann Failover-Slots auf den Standby synchronisieren.

Wie funktioniert CDC in SQL Server?

Ein Agent-Job liest das Transaktions-Log in Change-Tabellen mit __$operation und __$start_lsn. Debezium oder eigene Jobs lesen diese Tabellen.

Wie gehen Sie mit Schema-Änderungen um?

Schema Registry mit Kompatibilitätsregeln, Iceberg Schema Evolution für neue Spalten. Breaking Changes vorher mit dem Quell-Team abstimmen.

Wann wählen Sie kein CDC?

Wenn die Daten als Dateien kommen, Tabellen klein sind oder Stunden Latenz reichen. Dann ist Batch einfacher.

Wie bauen Sie aus CDC eine SCD2-Historie?

Jedes Update-Event schliesst die alte Version (valid_to) und öffnet eine neue. Die Event-Zeit oder LSN bestimmt die Reihenfolge.

Szenario: Die Platte der produktiven PostgreSQL läuft voll, pg_wal ist riesig. Was prüfen Sie?

pg_replication_slots auf inaktive Slots mit grossem Lag. Connector wieder starten oder den Slot löschen und neu snapshotten. Danach max_slot_wal_keep_size und Alarm setzen.

Szenario: Im Silver stehen manchmal alte Werte, obwohl die Quelle neuer ist. Warum?

Events wurden nach Ankunft statt nach LSN angewendet, oder ein Duplikat kam später. Die LSN in Silver speichern und nur neuere Events anwenden.

Szenario: Der Connector war drei Tage aus, der Slot wurde gelöscht. Wie holen Sie auf?

Neuer Slot und neuer Snapshot, am besten inkrementell. Silver per MERGE abgleichen, gelöschte Zeilen über Vergleich der Schlüssel finden.
