ETL vs ELT

Kern: ETL (Extract, Transform, Load) transformiert Daten vor dem Laden in einer eigenen Engine. ELT (Extract, Load, Transform) lädt zuerst roh und transformiert im Ziel, meist mit SQL. Die Frage ist also: Wo läuft die Transformation, und bleiben die Rohdaten erhalten?

1. Wo sitzt die Transformation?

  1. Extract: Daten aus der Quelle holen. Beispiel: Tabelle, API, Datei, CDC-Stream.
  2. Transform bei ETL: läuft in einer eigenen Engine zwischen Quelle und Ziel. Das Ziel sieht nur das fertige Ergebnis.
  3. Load bei ELT: Rohdaten kommen zuerst ins Ziel, fast unverändert.
  4. Transform bei ELT: läuft im Ziel mit dessen Rechenleistung, meist als SQL. Beispiel: dbt-Modelle auf Rohtabellen.
  5. Im Lakehouse verschwimmt die Grenze: Spark ist Transform-Engine, und Ziel ist eine Iceberg-Tabelle. Das Laden nach Bronze ist ELT-artig, Silver und Gold sind Transformationen im Ziel.

2. Die Reise einer Lieferung (die Geschichte zum Merken)

  1. Quelle: Ein operatives System, z. B. SQL Server, oder eine Dateilieferung.
  2. Extract: drei Arten. Voll: alles jedes Mal. Inkrementell: nur Zeilen mit neuem Zeitstempel oder höherer ID (High-Water Mark). CDC: jede Änderung aus dem Transaktionslog.
  3. Load roh: Die Daten landen fast unverändert im Ziel. Das ist schnell und verliert nichts.
  4. Transform im Ziel: SQL oder Spark baut daraus saubere Tabellen. Die Rechenleistung des Ziels skaliert.
  5. Modelle: Die Transformationen liegen als Code im Git, mit Tests und Review.
  6. Logik ändert sich: Man transformiert die Rohdaten neu. Die Quelle wird nicht erneut belastet. Bei ETL wäre der Rohzustand oft weg.

3. Beispiel: ETL, ELT und CDC als Quelle

# Python 3 + sqlite3, gleiche 3 JSON-Records (einer mit Preis "x")
# ETL: in Python transformieren, nur Gültiges laden
for s in src:
    d = json.loads(s)
    try: etl.execute("insert into trades values (?,?,?)",
                     (d["id"], float(d["price"]), d["ccy"].upper()))
    except ValueError: pass

# ELT: roh laden, Transformation als SQL-View im Ziel
elt.executemany("insert into raw_trades values (?)", [(s,) for s in src])
elt.execute("""create view trades as select json_extract(payload,'$.id') as id,
  cast(json_extract(payload,'$.price') as real) as price,
  upper(json_extract(payload,'$.ccy')) as ccy from raw_trades
  where json_extract(payload,'$.price') glob '[0-9]*.[0-9]*'""")

# CDC: (LSN, __$operation, id, city); 1=delete 2=insert 4=update after
changes = [(10,2,7,"Bern"), (11,4,7,"Basel"), (12,2,8,"Thun"), (13,1,8,None)]
apply(changes); apply(changes)   # zweites Mal = Replay
ETL  target: [(1, 51.2, 'EUR'), (2, 49.8, 'EUR')]
ELT  raw   : 3 Zeilen
ELT  model : [(1, 51.2, 'EUR'), (2, 49.8, 'EUR')]
CDC  Lauf 1: [(7, 'Basel')]
CDC  Lauf 2 (Replay): [(7, 'Basel')]

Echte Ausgabe, Python 3.12.10 mit sqlite3 3.49.1 (Simulation). apply macht pro Änderung in LSN-Reihenfolge ein Upsert über den Schlüssel oder ein Delete.

  1. Gleiches Ergebnis, anderer Ort: ETL und ELT liefern dieselben zwei Zeilen.
  2. ETL verliert den Rohzustand: Der kaputte Record ist weg. Niemand sieht ihn später.
  3. ELT behält ihn: raw_trades hat alle 3 Zeilen. Ändert sich die Regel, ändert man nur die View.
  4. CDC: Insert, Update und Delete werden der Reihe nach angewendet. Kunde 8 ist am Ende gelöscht, Kunde 7 wohnt in Basel.
  5. Replay ist harmlos: Upsert über den Schlüssel und Delete sind idempotent, solange der ganze Bereich in LSN-Reihenfolge kommt.

4. Details, die Interviewer fragen

  1. Warum ELT populär wurde: Cloud-Warehouses und Lakehouses trennen Compute und Storage. Rechenleistung im Ziel ist elastisch. Speicher für Rohdaten ist billig.
  2. Wann ETL besser ist: Sensible Daten müssen vor dem Ziel maskiert werden. Das Ziel kann die Transformation nicht (z. B. Entschlüsseln, XML-Parsen). Oder das Ziel ist teuer pro Rechenzeit.
  3. Schema-on-Write vs Schema-on-Read: ETL setzt das Schema vor dem Laden durch. ELT lädt erst und legt das Schema beim Transformieren fest.
  4. dbt: ein Werkzeug für das T in ELT. Modelle sind SELECT-Statements in Dateien. dbt baut daraus Tabellen oder Views, in der richtigen Reihenfolge, mit Tests und Doku.
  5. dbt-Inkrementell: Strategien append, merge, delete+insert, insert_overwrite, microbatch. merge braucht einen unique_key, sonst verhält es sich wie append. Der Spark-Adapter kennt delete+insert nicht.
  6. CDC (Change Data Capture): liest Änderungen aus dem Transaktionslog der Datenbank. Es liefert Inserts, Updates und auch Deletes, ohne Polling-Last.
  7. Log-basiert vs Query-basiert: Query-basiert fragt WHERE updated_at > :last. Es sieht keine Deletes und braucht eine Zeitstempel-Spalte. Log-basiert (Debezium, SQL Server CDC) sieht alles und braucht keine Schema-Änderung.
  8. SQL Server CDC: Ein SQL-Server-Agent-Job liest das Log und schreibt in Change Tables (cdc.<instance>_CT). Die Spalte __$operation sagt: 1 = Delete, 2 = Insert, 3 = Update vorher, 4 = Update nachher. Ordnung über __$start_lsn.
  9. CDC-Aufbewahrung: Der Cleanup-Job behält standardmässig 3 Tage (4320 Minuten). Ein Consumer, der länger steht, verliert Änderungen und braucht einen neuen Voll-Snapshot.
  10. CDC anwenden im Lakehouse: mit MERGE INTO auf den Schlüssel. In Iceberg darf jede Zielzeile nur von einer Quellzeile getroffen werden. Darum vorher pro Schlüssel nur die letzte Änderung behalten.
  11. Wo die Logik lebt: In ELT liegt Geschäftslogik als SQL im Ziel. Sie braucht dieselbe Disziplin wie Anwendungscode: Git, Review, Tests, CI.

5. Vergleich

  • ETL: Transformation vor dem Ziel. Weniger Daten im Ziel, Maskierung früh. Rohzustand oft weg, neue Logik heisst neu extrahieren.
  • ELT: Transformation im Ziel. Rohdaten bleiben, Logik als SQL, elastische Rechenleistung. Mehr Speicher, sensible Rohdaten liegen im Ziel.
  • EtLT: leichte Transformation vor dem Laden (entschlüsseln, parsen, maskieren), schwere danach. In der Praxis sehr häufig.
  • Voll-Extract: einfach, aber teuer bei grossen Tabellen.
  • Inkrementell per Zeitstempel: billig, aber keine Deletes und Probleme mit Uhren und Transaktionen, die spät committen.
  • CDC: vollständig mit Deletes, geringe Verzögerung. Mehr Betrieb: Log-Aufbewahrung, Schema-Änderungen, Reihenfolge.

6. In der Produktion

  1. Verlorene Updates bei Zeitstempel-Extract: Eine Transaktion committet nach dem Lauf, hat aber einen älteren Zeitstempel. Lösung: Überlappungsfenster plus idempotentes Merge, oder CDC.
  2. Deletes fehlen im Ziel: Query-basiertes Extract sieht sie nicht. Lösung: CDC oder Soft Deletes in der Quelle.
  3. CDC-Lücke: Der Consumer stand länger als die Log-Aufbewahrung. Lösung: Monitoring der Verzögerung, dann neuer Snapshot.
  4. MERGE scheitert: Mehrere Änderungen zum gleichen Schlüssel im Batch. Lösung: vor dem Merge pro Schlüssel die letzte Änderung nach LSN wählen.
  5. Zu teures ELT: Jeder Lauf transformiert alles neu. Lösung: inkrementelle Modelle (z. B. dbt merge oder insert_overwrite pro Partition).
  6. Last auf der Quelle: Grosse Extract-Abfragen bremsen das operative System. Lösung: Replika lesen, CDC, Off-Peak-Fenster.

7. Diagnose: Werkzeuge und Abfragen

  • Zeilen abgleichen: count(*) und Summen pro Tag in Quelle, Rohtabelle und Modell.
  • SQL Server CDC: sys.sp_cdc_help_change_data_capture, sys.fn_cdc_get_min_lsn / sys.fn_cdc_get_max_lsn, sys.sp_cdc_help_jobs.
  • Iceberg: t.snapshots zeigt jeden Load als Snapshot mit Operation und Zeilen-Summary.
  • dbt: dbt build führt Modelle und Tests aus, dbt test prüft z. B. unique und not_null.
  • Spark UI: zeigt, welche Stage der Transformation teuer ist (Shuffle, Skew).

8. Senior-Punkte

  1. Die Frage ist nicht ETL oder ELT, sondern: Wo läuft welche Transformation, und wo bleibt der Rohzustand?
  2. Rohdaten behalten ist meist die beste Entscheidung. Es macht Logik-Änderungen und Bug-Fixes billig.
  3. Was das Ziel nicht kann, kommt vorher: entschlüsseln, Binärformate parsen, PII maskieren. Der Rest im Ziel.
  4. CDC ist kein Gratis-Stream. Log-Aufbewahrung, Schema-Änderungen, Reihenfolge und Replays müssen geplant sein.
  5. SQL ist Code. Transformationen gehören ins Git, mit Tests und CI, egal ob dbt oder Spark SQL.
  6. Lade-Schritte idempotent machen: Jeder Extract kann zweimal kommen. Merge über Schlüssel statt blindes Append.

10. Fallen

  • „ELT heisst: keine Transformation.“ → Falsch. Es transformiert genauso, nur später und im Ziel.
  • „ETL ist veraltet.“ → Falsch. Maskierung, Entschlüsselung und Parsing laufen weiter vor dem Ziel.
  • „Ein updated_at-Filter findet alle Änderungen.“ → Falsch. Er sieht keine Deletes und verpasst spät committete Transaktionen.
  • „CDC liefert jede Änderung für immer.“ → Falsch. SQL Server CDC behält standardmässig 3 Tage.
  • „dbt ist eine Engine.“ → Falsch. dbt erzeugt SQL. Rechnen tut das Warehouse oder Spark.

11. Fragen

Was ist der Unterschied zwischen ETL und ELT?

ETL transformiert vor dem Laden in einer eigenen Engine. ELT lädt roh und transformiert im Ziel, meist mit SQL.

Warum ist ELT heute so verbreitet?

Cloud-Warehouses und Lakehouses haben elastische Rechenleistung und billigen Speicher. Rohdaten im Ziel machen spätere Logik-Änderungen einfach.

Wann wählen Sie ETL?

Wenn Daten vor dem Ziel maskiert werden müssen, das Ziel die Transformation nicht kann oder Rechenzeit im Ziel teuer ist.

Was ist EtLT?

Leichte Transformation vor dem Laden, z. B. parsen und maskieren, und die schwere Geschäftslogik danach im Ziel.

Was ist dbt?

Ein Werkzeug für Transformationen im Ziel. Modelle sind SELECT-Statements; dbt baut sie in der richtigen Reihenfolge und testet sie.

Welche Inkrementell-Strategien kennt dbt?

append, merge, delete+insert, insert_overwrite und microbatch. Welche geht, hängt vom Adapter ab.

Was passiert bei dbt merge ohne unique_key?

Es verhält sich wie append. Re-Runs erzeugen dann Duplikate.

Was ist Change Data Capture?

Änderungen werden aus dem Transaktionslog der Quelle gelesen. Man bekommt Inserts, Updates und Deletes in Commit-Reihenfolge.

Log-basiertes vs Query-basiertes CDC?

Query-basiert fragt per Zeitstempel ab, sieht keine Deletes und belastet die Quelle. Log-basiert sieht alles mit geringer Verzögerung und braucht keine Schemaänderung.

Was bedeutet __$operation in SQL Server CDC?

1 = Delete, 2 = Insert, 3 = Update vorher, 4 = Update nachher.

Wie wenden Sie CDC-Änderungen auf eine Iceberg-Tabelle an?

Pro Schlüssel die letzte Änderung nach LSN wählen, dann MERGE INTO: Delete bei Operation 1, sonst Update oder Insert.

Warum muss man vor MERGE deduplizieren?

Iceberg wirft einen Fehler, wenn mehrere Quellzeilen dieselbe Zielzeile treffen.

Was ist eine High-Water Mark?

Der höchste schon verarbeitete Wert, z. B. Zeitstempel, ID oder LSN. Der nächste Lauf liest ab dort.

Wo laufen Transformationen im Lakehouse?

In einer Engine wie Spark, die auf Tabellen im Object Storage arbeitet. Laden nach Bronze ist ELT-artig, Silver und Gold sind Transformationen im Ziel.

Was ist das Risiko von ELT für den Datenschutz?

Sensible Rohdaten liegen im Ziel. Darum früh maskieren oder Bronze streng berechtigen.

Wie testen Sie SQL-Transformationen?

Mit Schema- und Datentests (unique, not_null, Beziehungen), Abgleich gegen Referenzwerte und CI vor jedem Merge.

Szenario: Im Ziel fehlen gelöschte Kunden nicht, sie sind noch da. Warum?

Das Extract arbeitet per Zeitstempel und sieht keine Deletes. Lösung: CDC oder Soft Deletes in der Quelle.

Szenario: Der CDC-Consumer war eine Woche down. Was tun Sie?

Prüfen, ob die minimale LSN noch vor dem letzten verarbeiteten Stand liegt. Bei 3 Tagen Aufbewahrung ist sie es nicht: neuer Voll-Snapshot, dann CDC ab dem Snapshot-Punkt.

Szenario: Die Fachlogik für eine Kennzahl ändert sich rückwirkend. Was ist bei ETL und was bei ELT nötig?

Bei ELT nur das Modell ändern und aus den Rohtabellen neu rechnen. Bei ETL fehlt der Rohzustand oft, dann muss man neu extrahieren.
