Datenqualität und Data Contracts

Kern: Datenqualität ist die Prüfung, ob Daten die erwarteten Regeln erfüllen, zum Beispiel für Schema, Pflichtfelder, Wertebereiche, Eindeutigkeit und Aktualität. Sie verhindert, dass falsche Daten still in Reports landen. Gute Pipelines prüfen an jeder Schichtgrenze, trennen schlechte Zeilen in eine Quarantäne und machen Ergebnisse erst nach bestandener Prüfung sichtbar.

Antwort-Muster

Frage: Wie prüfen Sie Datenqualität in einer Pipeline?

  1. Mechanismus: Jede Zeile wird gegen benannte Regeln geprüft. Gute Zeilen gehen nach Silver, schlechte mit Regelname in die Quarantäne.
  2. Zahl: Im Beispiel hat Bronze 6 Zeilen, nach dem Dedup bleiben 5. Davon gehen 2 nach Silver und 3 in die Quarantäne.
  3. Trade-off: Viele Checks kosten Rechenzeit. Einzelne Fehler sperren nur Zeilen, systemische Fehler stoppen den Lauf.
  4. Produktion: Ich prüfe vor dem Publizieren, überwache Frische und Menge als Metrik und gebe der Quarantäne einen Besitzer.

1. Die Reise eines Datensatzes durch die Prüfung

  1. Bronze: Ein Trade kommt roh an, alle Felder als Text. Bronze speichert ihn unverändert.
  2. Dedup: Exakte Duplikate fallen weg, z. B. dieselbe Datei zweimal geliefert. Das ist keine Fehlerzeile, sondern ein normaler Fall.
  3. Regeln: Jede Zeile wird gegen Regeln geprüft. Jede Regel hat einen Namen, damit der Grund später sichtbar ist.
  4. Silver oder Quarantäne: Besteht die Zeile, geht sie typisiert nach Silver. Sonst geht sie mit Regelname und Lauf-ID in die Quarantäne.
  5. Tabellen-Checks: Danach prüft der Job die ganze Tabelle: Ist der neueste Tag da? Ist die Menge plausibel? Erst dann wird das Ergebnis sichtbar.
  6. Korrigieren: Jemand fixt die Ursache, meist an der Quelle. Die Zeilen werden neu geladen, nicht von Hand in Silver geschrieben.

2. Aufbau

  1. Eingang (①): Datei vollständig, lesbar, erwartetes Format. Beispiel: ZIP entschlüsselbar, XML parsebar.
  2. Bronze → Silver (②): Schema und Typen prüfen, Pflichtfelder auf NULL prüfen. Hier werden Strings zu Zahlen und Datumswerten.
  3. Silver (③): Fachregeln prüfen: Wertebereiche, erlaubte Werte, Eindeutigkeit, Beziehungen zwischen Tabellen.
  4. Gold (④): Ergebnisse abgleichen: Summen gegen Quelle, Zeilenzahlen gegen Vortag, Parität gegen ein Altsystem.
  5. Quarantäne: Schlechte Zeilen landen mit Grund in einer eigenen Tabelle. Gute Zeilen fliessen weiter.
  6. Monitoring: Frische und Mengen laufen als Metriken mit Alarm, nicht nur als Test im Job.

3. Details

  1. Check-Arten (Inhalt): Schema prüft Spalten, Typen und Format, zum Beispiel ob price eine Zahl ist. Completeness prüft Pflichtfelder, zum Beispiel trade_id IS NOT NULL. Validity prüft Bereiche oder Listen, zum Beispiel Preis ≥ 0 oder Markt in (CH, DE, FR, IT). Uniqueness prüft, dass ein Schlüssel nur einmal vorkommt.
  2. Check-Arten (Lauf und Beziehung): Freshness prüft, dass die neuesten Daten nicht zu alt sind, zum Beispiel max(trade_date) ist gestern. Volume prüft, dass die Zeilenzahl zu früheren Läufen passt. Referential Integrity prüft, dass Fremdschlüssel auf existierende Zeilen zeigen. Consistency prüft, dass Summen zwischen Schichten oder zum Altsystem passen.
  3. Zeilen-Checks vs Tabellen-Checks: Ein Zeilen-Check bewertet jede Zeile einzeln und kann sie in die Quarantäne schicken. Ein Tabellen-Check bewertet den ganzen Lauf, zum Beispiel Frische oder Menge. Er kann nur den Lauf stoppen.
  4. Hart vs weich: Eine harte Regel stoppt den Lauf oder sperrt die Zeile. Eine weiche Regel erzeugt nur eine Warnung. Deequ nennt das CheckLevel.Error und CheckLevel.Warning.
  5. Quarantäne: Eine Quarantäne-Tabelle hält schlechte Zeilen mit Grund, Lauf-ID und Zeitstempel. Der Vorteil ist, dass der Rest der Daten weiterfliesst. Das Risiko ist, dass niemand hineinschaut.
  6. Write-Audit-Publish (WAP): Iceberg kann in einen eigenen Audit-Branch schreiben. Man setzt write.wap.enabled=true und spark.wap.branch. Nach der Prüfung bewegt fast_forward den Branch main auf den geprüften Stand. Leser sehen nie ungeprüfte Daten.
  7. Data Contract: Ein Data Contract ist eine schriftliche Vereinbarung zwischen Produzent und Konsument. Er regelt Schema, Bedeutung, Regeln, Frische und Verantwortliche. Die Checks sind die ausführbare Form des Vertrags.
  8. Great Expectations (GX): GX ist eine Python-Bibliothek für Datentests. Eine Expectation ist eine prüfbare Aussage, zum Beispiel ExpectColumnValuesToNotBeNull. Eine Expectation Suite bündelt sie. Ein Checkpoint führt die Prüfung in Produktion aus und löst Actions aus, zum Beispiel Alarme. Data Docs zeigen die Ergebnisse als Webseite.
  9. Deequ: Deequ ist eine Scala-Bibliothek von AWS auf Apache Spark für „Unit Tests für Daten“. Man baut einen Check mit isComplete, isUnique, isNonNegative und isContainedIn. Man führt ihn mit VerificationSuite aus. Dazu gibt es Constraint Suggestion, Metrics Repository und Anomaly Detection. PyDeequ ist die Python-Schnittstelle.
  10. Schema im Tabellenformat: Iceberg erzwingt Spaltentypen und Pflichtfelder (required). Fachregeln wie „Preis ≥ 0“ prüft Iceberg nicht. Dafür braucht es eigene Checks.
  11. Parität bei Migrationen: Ein Paritäts-Check vergleicht neue Ergebnisse Tabelle für Tabelle mit dem Altsystem. Er ist der härteste Qualitätsbeweis bei einer Ablösung.
  12. Kosten: Jeder Check ist ein Scan oder eine Aggregation. Viele Checks auf grossen Tabellen kosten Rechenzeit. Deequ rechnet darum Metriken gebündelt und kann inkrementell rechnen.

4. Fallen

  • „Iceberg prüft die Datenqualität.“ → Falsch. Iceberg erzwingt Typen und Pflichtfelder, keine Fachregeln.
  • „Unique-Fehler heisst immer schlechte Daten.“ → Falsch. Oft ist es ein doppelter Import. Erst exakte Duplikate entfernen, dann Unique prüfen.
  • „Alle Checks pro Zeile reichen.“ → Falsch. Fehlende Daten sieht nur ein Tabellen-Check (Frische, Menge).
  • „Bei einem Fehler stoppt man immer den ganzen Lauf.“ → Nicht immer. Einzelne schlechte Zeilen gehören in die Quarantäne. Abbruch nur bei systemischen Fehlern.
  • „Great Expectations läuft auf Spark wie Deequ.“ → Ungenau. GX ist Python und hat mehrere Backends, darunter Spark. Deequ ist für Spark gebaut.

5. Selbsttest

Warum?

Warum braucht man Volume-Checks?

Fehlt eine Lieferung, gibt es keine Zeilen und damit keinen Zeilenfehler. Nur die Menge zeigt die Lücke.

Was ist der gefährlichste Qualitätsfehler?

Ein plausibler falscher Wert. Er besteht alle Range-Checks und fällt nur beim Abgleich mit einer anderen Quelle auf.

Wie erkennen Sie Schema-Drift?

Null-Rate pro Spalte über die Zeit beobachten. Ein Sprung auf 100 % heisst oft: Feld umbenannt.

Wie innen?

Was ist Datenqualität in einer Pipeline?

Die Prüfung, ob Daten die erwarteten Regeln erfüllen: Schema, Pflichtfelder, Wertebereiche, Eindeutigkeit, Frische. Ziel: Keine falschen Daten erreichen still den Report.

Welche Arten von Checks kennen Sie?

Schema, Completeness (Nulls), Validity (Ranges, erlaubte Werte), Uniqueness, Freshness, Volume, Referential Integrity, Consistency.

Wo prüfen Sie in einer Medallion-Architektur?

Beim Eingang Format und Lesbarkeit. Zwischen Bronze und Silver Schema und Nulls. In Silver Fachregeln und Unique. In Gold Abgleiche.

Was ist eine Quarantäne-Tabelle?

Eine Tabelle für schlechte Zeilen mit Grund, Lauf-ID und Zeit. Die guten Zeilen fliessen weiter.

Zeilen-Check vs Tabellen-Check?

Ein Zeilen-Check bewertet jede Zeile und kann sie sperren. Ein Tabellen-Check bewertet den ganzen Lauf, z. B. Frische oder Menge.

Wie prüfen Sie Freshness?

Ich vergleiche das neueste Event-Datum mit der erwarteten Zeit. Das läuft als Metrik mit Alarm, nicht nur im Job.

Was ist Write-Audit-Publish?

Daten in einen Audit-Branch schreiben, dort prüfen, dann publizieren. In Iceberg mit write.wap.enabled, spark.wap.branch und fast_forward auf main.

Was ist ein Data Contract?

Eine Vereinbarung zwischen Produzent und Konsument über Schema, Bedeutung, Regeln, Frische und Verantwortliche. Checks setzen ihn um.

Was ist Great Expectations?

Eine Python-Bibliothek für Datentests. Expectations bilden Suites, Checkpoints führen sie aus und lösen Actions aus, Data Docs zeigen die Ergebnisse.

Was ist Deequ?

Eine Bibliothek von AWS auf Spark für „Unit Tests für Daten“. Checks wie isComplete und isUnique laufen über eine VerificationSuite. Dazu Constraint Suggestion und Anomaly Detection.

Zahlen

Wie viele Zeilen bleiben im Beispiel nach dem Dedup und wie viele landen in Silver?

Bronze hat 6 Zeilen, nach dem Dedup bleiben 5. Davon gehen 2 nach Silver und 3 in die Quarantäne.

Wie viele Check-Arten gibt es?

Acht: Schema, Completeness, Validity, Uniqueness, Freshness, Volume, Referential Integrity und Consistency.

Vergleich

Wann stoppen Sie den Lauf statt Zeilen zu sperren?

Bei systemischen Fehlern: falsches Format, Schema geändert, sehr viele Fehler auf einmal. Einzelne Fehler gehen in die Quarantäne.

GX oder Deequ?

Deequ für sehr grosse Spark-Tabellen und Metriken über Zeit. GX für Python-Teams mit vielen Quellen und guten Berichten.

Prüft Iceberg die Datenqualität?

Nur Typen und Pflichtfelder über das Schema. Fachregeln braucht es selbst.

Produktion

Szenario: Der Report zeigt heute 40 % weniger Umsatz. Was tun Sie?

Zuerst Frische und Menge pro Quelle prüfen, dann die Quarantäne. Oft fehlt eine Lieferung oder eine Regel sperrt zu viel. Danach fixen und den Tag neu rechnen.

Szenario: Eine Spalte ist seit gestern überall NULL. Ursache?

Wahrscheinlich Schema-Drift: Die Quelle hat das Feld umbenannt oder das Format geändert. Ich prüfe die Rohdaten in Bronze und spreche mit dem Produzenten.

Szenario: Die Quarantäne hat 50 000 Zeilen, niemand kümmert sich. Was ändern Sie?

Einen Besitzer festlegen, Alarm auf die Menge, Auswertung nach Grund. Dazu ein klarer Weg, korrigierte Zeilen neu zu laden.

Design

Wie finden Sie Duplikate?

GROUP BY Schlüssel HAVING COUNT(*) > 1. Vorher exakte Duplikate entfernen, sonst meldet man doppelte Importe als Fehler.

Wie verhindern Sie, dass Leser ungeprüfte Daten sehen?

Prüfen vor dem Publizieren: WAP mit Branch, Staging-Tabelle, oder Schreiben und Prüfen in einer Transaktion.

Was kostet Datenqualität?

Rechenzeit für Scans und Aggregationen. Darum Checks bündeln, inkrementell rechnen und nicht jede Regel auf jeder Schicht wiederholen.

Wie beweisen Sie Korrektheit bei einer Migration?

Mit einem automatischen Paritäts-Check gegen das Altsystem, Tabelle für Tabelle. Go-live erst bei voller Übereinstimmung.

Mehr

Gerüst

  • Warum? Falsche Daten landen sonst still im Report. Zeilen-Checks sehen eine fehlende Lieferung nicht, darum braucht es Tabellen-Checks.
  • Wie innen? Schema und Nulls vor Silver, Fachregeln in Silver, Abgleich in Gold. Schlechte Zeilen gehen mit Regelname in die Quarantäne.
  • Zahlen Beispiel: 6 Zeilen in Bronze, 5 nach Dedup, 2 in Silver, 3 in der Quarantäne. Acht Check-Arten.
  • Vergleich Eigene SQL-Checks, Great Expectations, Deequ, dbt Tests. Quarantäne gegen Abbruch. WAP-Branch gegen Staging-Tabelle.
  • Produktion Quarantäne ohne Besitzer läuft voll. Schema-Drift zeigt sich als NULL-Spalte. Alarm-Müdigkeit bei zu vielen Warnungen.
  • Design Prüfen vor dem Publizieren. Erst Dedup, dann Unique. Parität gegen das Altsystem als Qualitätsbeweis.

Beispiel: Checks und Quarantäne mit SQL

CREATE TABLE staged AS SELECT DISTINCT * FROM bronze;     -- exakte Duplikate raus
rules = {
  "schema: price numeric": "price GLOB '*[^0-9.-]*'",
  "null: volume_mwh":      "volume_mwh IS NULL",
  "range: price >= 0":     "CAST(price AS REAL) < 0",
  "unique: trade_id":      "trade_id IN (SELECT trade_id FROM staged GROUP BY 1 HAVING COUNT(*) > 1)",
}
reason = "CASE WHEN <regel1> THEN 'name1' WHEN ... END"
CREATE TABLE quarantine AS SELECT *, {reason} AS reason FROM staged WHERE {reason} IS NOT NULL
CREATE TABLE silver AS SELECT trade_id, CAST(price AS REAL) ... FROM staged WHERE {reason} IS NULL
bronze 6 rows, after exact dedup 5
schema: price numeric  bad = 1
null: volume_mwh       bad = 1
range: price >= 0      bad = 1
unique: trade_id       bad = 0
freshness: max date    = 2026-11-21
silver     [('T1', 45.1), ('T5', 51.2)]
quarantine [('T2', 'schema: price numeric'), ('T3', 'null: volume_mwh'), ('T4', 'range: price >= 0')]

Echte Ausgabe, Python 3.12 mit sqlite3 (gekürztes Skript). In Spark wäre es dieselbe Logik mit DataFrames und Iceberg-Tabellen.

  1. Bronze hat 6 Zeilen. T1 kam zweimal identisch. Nach dem Dedup bleiben 5.
  2. Darum meldet unique: trade_id 0 Fehler. Prüft man Unique vor dem Dedup, landet ein normaler Doppel-Import fälschlich in der Quarantäne.
  3. T2 hat den Preis abc: Schemafehler. T3 hat kein Volumen: Null-Fehler. T4 hat einen negativen Preis: Range-Fehler.
  4. Jede Quarantäne-Zeile trägt ihren Grund. So kann der Fachbereich sie ohne Entwickler verstehen.
  5. Silver enthält nur geprüfte, typisierte Zeilen. Der Frische-Check zeigt den neuesten Tag: 2026-11-21.

Vergleich

  • Eigene SQL- oder PySpark-Checks: keine neue Abhängigkeit, volle Kontrolle. Aber Berichte und Historie muss man selbst bauen.
  • Great Expectations: Python, viele fertige Expectations, Data Docs als Bericht. Eher schwergewichtig in der Einrichtung.
  • Deequ / PyDeequ: direkt auf Spark, gut für grosse Tabellen, Metriken über Zeit, Anomalie-Erkennung. Kern ist Scala.
  • dbt Tests: Tests in SQL neben dem Modell (not_null, unique). Passt, wenn die Transformationen in dbt laufen.
  • Quarantäne vs Abbruch: Quarantäne lässt gute Daten fliessen. Abbruch schützt bei systemischen Fehlern, z. B. falsches Dateiformat.
  • WAP mit Branch vs Staging-Tabelle: Branch ist atomar und ohne Kopie. Staging-Tabelle ist einfacher zu verstehen, braucht aber einen Kopierschritt.

In der Produktion

  1. Falsche Zahlen ohne Fehler: Ein Parser liest 1,5 als 15, weil die Kultur falsch ist. Kein Check schlägt an. Lösung: Range-Checks und Abgleich gegen eine unabhängige Quelle.
  2. Quarantäne läuft voll: Niemand schaut hinein, die Daten fehlen im Report. Lösung: Alarm auf Quarantäne-Menge, klarer Besitzer, Reprocessing-Weg.
  3. Alarm-Müdigkeit: Zu viele weiche Warnungen, niemand liest sie. Lösung: wenige harte Regeln, Warnungen mit Schwellenwert.
  4. Stille Lücke: Eine Quelle liefert gar nicht. Zeilen-Checks sehen nichts, weil keine Zeilen da sind. Lösung: Frische- und Mengen-Checks.
  5. Schema-Drift: Die Quelle benennt ein Feld um. Die Spalte ist plötzlich überall NULL. Lösung: Null-Rate pro Spalte überwachen, Schema-Vertrag mit der Quelle.
  6. Halbe Ergebnisse sichtbar: Leser sehen Daten vor dem Check. Lösung: Prüfen vor dem Publizieren, z. B. WAP oder eine Transaktion pro Lauf.

Diagnose: Werkzeuge und Abfragen

  • Null-Rate pro Spalte: SELECT AVG(CASE WHEN col IS NULL THEN 1.0 ELSE 0 END) FROM t, pro Tag als Zeitreihe.
  • Duplikate finden: SELECT key, COUNT(*) FROM t GROUP BY key HAVING COUNT(*) > 1.
  • Frische: SELECT MAX(event_date) FROM t als Prometheus-Metrik mit Alarm.
  • Quarantäne-Auswertung: SELECT reason, COUNT(*) FROM quarantine GROUP BY reason pro Lauf.
  • Iceberg Metadaten: db.t.snapshots zeigt die Summary pro Commit, z. B. added-records. Ein Sprung fällt so schnell auf.
  • Deequ Data Profiling und Constraint Suggestion: ein erstes Profil einer unbekannten Tabelle und Vorschläge für Regeln.

Senior-Punkte

  1. Früh prüfen, aber nicht alles überall. Schema und Nulls an der Grenze zu Silver. Fachregeln in Silver. Abgleich in Gold.
  2. Die gefährlichsten Fehler sind plausibel. Ein falscher Preis, der im Bereich liegt, fällt nur beim Abgleich mit einer zweiten Quelle auf.
  3. Quarantäne braucht einen Besitzer und einen Weg zurück. Sonst ist sie ein Papierkorb.
  4. Prüfen vor Publizieren. Leser dürfen nie ungeprüfte Daten sehen. WAP oder eine Transaktion pro Lauf lösen das.
  5. Kein Tool ersetzt Regeln vom Fachbereich. Das Tool ist zweitrangig. Wichtig ist, welche Regeln gelten und wer sie besitzt.
  6. Bei Migrationen ist Parität der Qualitätsbeweis. Erst bei 100 % Übereinstimmung geht das neue System live.
