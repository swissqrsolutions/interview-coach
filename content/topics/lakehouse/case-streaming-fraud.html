Fall: Streaming-Betrugserkennung für Zahlungen

Lakehouse · Design-Fall · Tier 2 · Quellen: Apache Kafka 4.4 Docs (Producer Configs, Transactions), Apache Flink 2.3 Docs (Checkpointing, State, Kafka Connector), Apache Spark 4.3 Docs (Structured Streaming, Real-time Mode), Apache Iceberg 1.12 Docs (Spark Structured Streaming, Maintenance)

Kern (die 1-Minuten-Antwort): Streaming-Betrugserkennung bewertet jede Zahlung in Millisekunden, bevor sie freigegeben wird. Ich trenne zwei Wege: einen synchronen Hot Path (Scoring-Service liest vorberechnete Features aus einem Online-Store) und einen Streaming-Pfad (Kafka → Flink oder Spark), der Features pro Karte laufend aktualisiert. Alle Events landen zusätzlich in Iceberg (Bronze/Silver/Gold) für Analyse, Audit und Modell-Training.

1. Wo sitzt was? (Architektur)

  1. Payment API: Sie bekommt die Autorisierung. Sie fragt synchron den Scoring-Service und schreibt das Event nach Kafka.
  2. Scoring-Service: Er wendet Regeln (z. B. „mehr als 4 Zahlungen in 10 Minuten“) und ein ML-Modell an. Antwort: freigeben, ablehnen oder prüfen.
  3. Online-Store: ein Key-Value-Speicher mit kleiner Latenz, z. B. Redis. Er hält Features pro Karte, z. B. Anzahl und Summe der letzten 10 Minuten.
  4. Kafka: das Event-Log. Der Key ist das Karten-Token. So landen alle Zahlungen einer Karte in derselben Partition, in Reihenfolge.
  5. Stream-Prozessor: Flink oder Spark Structured Streaming. Er hält State pro Karte, aktualisiert Features und erkennt Muster über mehrere Events.
  6. Alerts: Verdachtsfälle gehen an die Fall-Bearbeitung.
  7. Iceberg Bronze/Silver/Gold: Rohevents, bereinigte Events mit späteren Labels (Chargeback = echter Betrug), daraus KPIs und Trainingsdaten.

2. Die Reise einer Zahlung

  1. Zahlung: Karte A zahlt 950 CHF in Brasilien. Vorher kamen zwei kleine Zahlungen in der Schweiz.
  2. Score: Der Scoring-Service liest die Features von Karte A aus dem Online-Store. Das dauert wenige Millisekunden.
  3. Entscheidung: Regeln und Modell geben z. B. OK. Das Budget für alles liegt meist unter 100 ms.
  4. Kafka: Die API schreibt das Event mit der Entscheidung nach Kafka. Key ist das Karten-Token.
  5. Stream-Prozessor: Er zählt die Zahlung in den State von Karte A. Jetzt sind es 3 Zahlungen und 1031,50 CHF in 10 Minuten.
  6. Online-Store: Der Prozessor schreibt die neuen Features. Das ist asynchron, ein paar hundert Millisekunden später.
  7. Nächste Zahlung: Die 4. Zahlung von Karte A sieht die neuen Features und geht auf REVIEW.
  8. Iceberg: Das Event landet in Bronze. Silver dedupliziert. Wochen später kommt ein Chargeback, also eine Rückbuchung. Sie wird zum Label für das Modell-Training.

3. Beispiel: Schemas, Kern-Transformation, Qualitäts-Checks

Event-Schema (Avro in einer Schema Registry):

{ "type": "record", "name": "Payment", "fields": [
  {"name": "event_id",    "type": "string"},           // eindeutig, für Dedup
  {"name": "card_token",  "type": "string"},           // nie die echte Kartennummer
  {"name": "event_time",  "type": {"type":"long","logicalType":"timestamp-millis"}},
  {"name": "amount_minor","type": "long"},              // Rappen, keine float
  {"name": "currency",    "type": "string"},
  {"name": "merchant_id", "type": "string"},
  {"name": "country",     "type": "string"} ]}

Kern-Transformation: Dedup und Velocity-Features (echt ausgeführt, SQL wie im Streaming-Job):

WITH dedup AS (                       -- 1) Duplikate weg (event_id)
  SELECT * FROM (SELECT *, row_number() OVER (PARTITION BY event_id ORDER BY ts) rn
                 FROM payment) WHERE rn = 1),
feat AS (                             -- 2) Features pro Karte, letzte 10 Minuten
  SELECT *,
    count(*)        OVER w AS tx_10min,
    sum(amount_chf) OVER w AS sum_10min
  FROM dedup
  WINDOW w AS (PARTITION BY card_token ORDER BY ts RANGE BETWEEN 600 PRECEDING AND CURRENT ROW))
SELECT event_id, card_token, ts, amount_chf, country, tx_10min, round(sum_10min,1) sum_10min,
  CASE WHEN tx_10min >= 4 OR sum_10min > 2000 THEN 'REVIEW' ELSE 'OK' END AS decision
FROM feat ORDER BY ts, event_id
event_id | card_token | ts | amount_chf | country | tx_10min | sum_10min | decision
e1 | card_A | 0 | 42.0 | CH | 1 | 42.0 | OK
e2 | card_A | 120 | 39.5 | CH | 2 | 81.5 | OK
e3 | card_B | 200 | 18.0 | CH | 1 | 18.0 | OK
e4 | card_A | 300 | 950.0 | BR | 3 | 1031.5 | OK
e5 | card_A | 330 | 980.0 | BR | 4 | 2011.5 | REVIEW
e6 | card_A | 360 | 990.0 | BR | 5 | 3001.5 | REVIEW
e7 | card_B | 900 | 22.0 | CH | 1 | 22.0 | OK

Echte Ausgabe, Python 3.12 + sqlite3 3.49.1. Input: 8 Zeilen, e2 doppelt (Producer-Retry). ts in Sekunden.

  1. Das doppelte e2 erscheint nur einmal. Ohne Dedup wäre tx_10min ab e2 um 1 zu hoch.
  2. Das Fenster ist ein Sliding Window pro Karte: immer die letzten 600 Sekunden vor dem Event.
  3. Bei e5 greift die Regel: 4 Zahlungen und über 2000 CHF in 10 Minuten.
  4. Karte B bleibt unauffällig, weil der State pro Karte getrennt ist.

Derselbe Job im Streaming (PySpark, Ausschnitt):

events = (spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "kafka:9092")
  .option("subscribe", "payments").load()
  .select(from_avro("value", schema).alias("p")).select("p.*")
  .withWatermark("event_time", "10 minutes")
  .dropDuplicatesWithinWatermark(["event_id"]))

features = (events
  .groupBy("card_token", F.window("event_time", "10 minutes", "1 minute"))
  .agg(F.count("*").alias("tx_10min"), F.sum("amount_minor").alias("sum_10min")))

(events.writeStream.format("iceberg").outputMode("append")
  .trigger(processingTime="1 minute")
  .option("checkpointLocation", "s3a://chk/payments_bronze")
  .toTable("lake.bronze.payments"))

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): ein Iceberg-Commit pro Micro-Batch (jede Minute); Duplikate mit gleicher event_id innerhalb der Watermark fallen weg. Kafka und Spark laufen hier nicht.

Qualitäts-Checks:

  1. Schema: Die Schema Registry lehnt inkompatible Producer ab.
  2. Pflichtfelder und Bereich: amount_minor > 0, Währung in einer Liste, event_time nicht weit in der Zukunft. Fehler → Dead Letter Topic.
  3. Duplikat-Rate: Anteil verworfener Duplikate pro Minute. Ein Sprung zeigt Producer-Probleme.
  4. Freshness: Abstand zwischen event_time und jetzt im Online-Store. Zu alt → Scoring nutzt veraltete Features.
  5. Abgleich: Anzahl Events in Bronze pro Stunde = Anzahl Autorisierungen im Zahlungssystem.

4. Details, die Interviewer fragen

  1. Volumen (Beispielrechnung): 2000 Zahlungen pro Sekunde im Mittel, 10 000 in der Spitze. Bei 1 KB pro Event sind das 10 MB/s Spitze. Pro Tag ca. 173 Mio. Events, ca. 170 GB roh. Als Parquet deutlich weniger.
  2. Kafka-Partitionen: Key = Karten-Token. Die Zahl der Partitionen begrenzt die Parallelität der Consumer. Für 10 000 Events/s reichen z. B. 24–48 Partitionen. Die Zahl später zu ändern verschiebt Keys, also früh grosszügig planen.
  3. Latenz-Budget: Der synchrone Weg (API → Scoring → Online-Store) muss in wenigen zehn Millisekunden fertig sein. Der Streaming-Weg darf Sekunden brauchen. Darum ist Scoring kein Teil des Stream-Jobs.
  4. Idempotenz: Der Kafka-Producer ist standardmässig idempotent (enable.idempotence=true, acks=all). Das verhindert Duplikate durch Producer-Retries innerhalb einer Session. Gegen App-Retries hilft nur Dedup über event_id.
  5. Exactly-Once: Flink und Spark machen den State per Checkpoint exactly-once. Ins Iceberg-Ziel kommt jede Micro-Batch genau einmal, weil Spark die Batch-ID mit dem Commit verknüpft. Externe Sinks wie Redis sind at-least-once, also Writes idempotent machen (SET statt INCR).
  6. Late Data: Events können verspätet kommen, z. B. nach einem Netzwerkproblem. Eine Watermark sagt, wie lange man wartet. Für Scoring zählt aber der Moment der Zahlung, nicht das perfekte Fenster.
  7. State-Grösse: Pro Karte wenige Zahlen. Bei 10 Mio. aktiven Karten sind das einige GB. Flink nutzt dafür RocksDB als State Backend und State TTL, damit inaktive Karten verschwinden.
  8. Iceberg im Streaming: Jede Micro-Batch ist ein Commit und erzeugt Dateien. Trigger von 1–5 Minuten statt Sekunden, plus Compaction und expire_snapshots.
  9. Partitionierung Iceberg: days(event_time) für Bronze und Silver. Nicht nach Karte, das gibt Millionen Partitionen.
  10. Datenschutz: Nie die Kartennummer speichern, nur ein Token. PCI DSS verlangt Schutz der Kartendaten. Zugriff auf Silver mit Personenbezug einschränken.
  11. Kosten: Ein Streaming-Job läuft 24/7, also zahlt man immer. Darum nur die Teile streamen, die Sekunden brauchen. Reports und Training laufen als Batch auf Gold.

5. Vergleich: Alternativen

  • Apache Flink: echtes Event-für-Event-Processing, sehr kleiner Latenz, reicher State (Timer, CEP für Muster). Stark für komplexe Muster über viele Events. Preis: eigener Cluster und eigenes Know-how.
  • Spark Structured Streaming: Micro-Batches, gleiche API wie Batch, ideal, wenn das Team schon Spark nutzt. Seit Spark 4.1 gibt es den Real-time Mode für Millisekunden-Latenz, aber nur mit Kafka als Quelle und Einschränkungen bei Sinks.
  • Nur Regeln im Scoring-Service + Batch-Features: Features einmal pro Stunde aus dem Lakehouse rechnen. Viel einfacher, aber blind für schnelle Angriffe in Minuten.

6. In der Produktion

  1. Consumer Lag wächst: Der Job ist zu langsam oder eine Partition ist heiss (Skew durch einen Händler). Lösung: mehr Parallelität, Key prüfen, heisse Keys getrennt behandeln.
  2. Doppelte Alerts nach Neustart: Der Sink ist at-least-once. Lösung: Alerts mit event_id als Schlüssel idempotent schreiben.
  3. State wächst ohne Ende: keine Watermark oder kein State TTL. Lösung: Watermark und TTL setzen.
  4. Scoring wird langsam, Zahlungen hängen: Online-Store überlastet. Lösung: Timeout mit Fallback (nur Regeln), nie den Bezahlvorgang blockieren.
  5. Viele kleine Iceberg-Dateien: Trigger zu kurz. Lösung: längerer Trigger, Compaction alle paar Stunden.
  6. Modell wird schlechter: Betrüger ändern ihr Verhalten (Concept Drift). Lösung: Quote von REVIEW und Chargebacks überwachen, regelmässig neu trainieren.

7. Diagnose

  • Consumer Lag: kafka-consumer-groups.sh --describe --group fraud zeigt Lag pro Partition.
  • Spark: query.lastProgress zeigt inputRowsPerSecond, processedRowsPerSecond, Batch-Dauer und State-Grösse.
  • Flink: Web UI mit Backpressure, Checkpoint-Dauer und State-Grösse pro Operator.
  • Iceberg: SELECT count(*) FROM lake.bronze.payments.files und Dateigrössen, .snapshots für Commits pro Stunde.
  • Fachlich: Anteil REVIEW pro Stunde, Latenz p99 des Scoring-Services, Chargeback-Quote.

8. Senior-Punkte

  1. Die Entscheidung bleibt synchron, die Features werden gestreamt. So hängt die Zahlung nie an einem Stream-Job.
  2. Exactly-Once ist ein Ende-zu-Ende-Thema. Engine-Garantien enden am Sink. Idempotente Writes mit event_id sind der eigentliche Schutz.
  3. Fallback statt Ausfall: Ist das Scoring zu langsam, entscheiden einfache Regeln. Der Fachbereich legt fest, ob man im Zweifel freigibt oder ablehnt.
  4. Gleiche Feature-Logik online und offline. Sonst lernt das Modell andere Werte, als es live sieht (Training-Serving Skew).
  5. Streaming kostet 24/7. Nur streamen, was Sekunden braucht.
  6. Das Lakehouse ist das Gedächtnis: Audit, Nachrechnen, Training. Der Stream ist nur der schnelle Weg.

9. Aus dem Projekt

„Streaming-Betrugserkennung habe ich nicht produktiv gebaut; am nächsten dran sind die Kafka-Microservices bei BIT DAZiT und die idempotente, crash-sichere Batch-Pipeline bei ElCom MATCH, wo ich bewusst Batch statt Streaming gewählt habe, weil Minuten Latenz reichten.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Der Stream-Job entscheidet über die Zahlung.“ → Riskant. Die Entscheidung gehört in einen synchronen Service mit Timeout und Fallback.
  • „Kafka ist exactly-once, also gibt es keine Duplikate.“ → Falsch. Der idempotente Producer schützt nur vor eigenen Retries. App-Retries und Sinks brauchen Dedup.
  • „Je kürzer der Trigger, desto besser.“ → Falsch. Kurze Trigger erzeugen viele kleine Dateien und Commits.
  • „Wir speichern die Kartennummer für das Training.“ → Falsch. Nur Tokens. Kartendaten fallen unter PCI DSS.
  • „Processing Time reicht für Fenster.“ → Falsch. Verspätete Events landen dann im falschen Fenster. Event Time plus Watermark nutzen.

11. Fragen (Interviewer-Nachfragen)

Wie bekommen Sie die Entscheidung unter 100 ms?

Scoring läuft synchron in einem eigenen Service. Er liest nur vorberechnete Features aus einem Online-Store. Schwere Berechnungen macht der Stream-Job vorher.

Warum ist der Kafka-Key das Karten-Token?

Alle Events einer Karte landen in derselben Partition und bleiben in Reihenfolge. So kann der State pro Karte lokal bleiben.

Flink oder Spark?

Flink für sehr kleine Latenz und komplexe Muster mit Timern. Spark, wenn das Team Spark schon nutzt und Sekunden reichen; der Real-time Mode senkt die Latenz, hat aber Einschränkungen.

Wie verhindern Sie doppelte Events?

Idempotenter Producer gegen eigene Retries. Dazu Dedup über event_id im Stream, z. B. dropDuplicatesWithinWatermark, und idempotente Sinks.

Was passiert bei einem Absturz des Stream-Jobs?

Er startet vom letzten Checkpoint mit Offsets und State. Events seit dem Checkpoint werden erneut verarbeitet. Darum müssen Sinks idempotent sein.

Wie gehen Sie mit verspäteten Events um?

Mit Event Time und einer Watermark. Zu späte Events gehen nicht ins Fenster, landen aber in Bronze und in der Batch-Analyse.

Wie gross wird der State?

Wenige Werte pro Karte, also bei Millionen Karten einige GB. RocksDB als State Backend und State TTL für inaktive Karten.

Warum schreiben Sie auch nach Iceberg?

Für Audit, Nachrechnen, BI und Modell-Training. Kafka hält Daten nur begrenzt; Iceberg ist das langfristige Gedächtnis.

Wie partitionieren Sie die Iceberg-Tabellen?

Nach Tag der Event Time. Nicht nach Karte, das ergibt Millionen winziger Partitionen.

Wie verhindern Sie kleine Dateien?

Trigger von einer bis fünf Minuten, Compaction mit rewrite_data_files und regelmässig expire_snapshots.

Woher kommen die Labels für das Training?

Aus Chargebacks und Fall-Entscheidungen, oft Wochen später. Silver verbindet sie über die Zahlungs-ID mit dem ursprünglichen Event.

Was ist Training-Serving Skew?

Das Modell sieht live andere Feature-Werte als im Training. Lösung: dieselbe Feature-Definition online und offline, z. B. über einen Feature Store.

Was tun Sie, wenn der Online-Store ausfällt?

Timeout und Fallback auf einfache Regeln. Die Zahlung darf nicht hängen bleiben. Der Ausfall wird alarmiert.

Wie schützen Sie Kartendaten?

Nur Tokens im ganzen System, Verschlüsselung, enge Zugriffsrechte auf Silver. Kartendaten fallen unter PCI DSS.

Was ist Concept Drift?

Betrüger ändern ihr Verhalten, das Modell wird schlechter. Man überwacht Trefferquoten und trainiert regelmässig neu.

Wie testen Sie neue Regeln ohne Risiko?

Im Shadow Mode: Die Regel rechnet mit, entscheidet aber nicht. Ergebnisse vergleicht man in Gold mit den echten Fällen.

Was kostet diese Lösung am meisten?

Der 24/7-Betrieb von Stream-Jobs und Online-Store. Darum nur zeitkritische Teile streamen und den Rest als Batch rechnen.

Szenario: Der Consumer Lag steigt jeden Abend um 20 Uhr. Was prüfen Sie?

Lastspitze oder heisse Partition. Lag pro Partition ansehen, Batch-Dauer und Backpressure prüfen. Dann skalieren oder heisse Keys verteilen.

Szenario: Nach einem Deployment des Stream-Jobs gibt es doppelte Alerts. Warum?

Der Job hat ab dem letzten Checkpoint neu verarbeitet, und der Alert-Sink ist nicht idempotent. Alerts mit event_id als Schlüssel schreiben.

Szenario: Die Fachseite will alle Features auch für Zahlungen von vor zwei Jahren. Wie liefern Sie das?

Als Batch-Backfill auf Silver in Iceberg mit derselben Feature-Logik wie im Stream. Ergebnis in eine Gold-Tabelle, partitioniert nach Tag.
