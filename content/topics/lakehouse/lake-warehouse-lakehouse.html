Data Lake vs Warehouse vs Lakehouse

Kern: Ein Lakehouse ist ein Data Lake mit einer Tabellen-Schicht darüber. Die Daten liegen als offene Dateien (meist Parquet) im billigen Object Storage. Ein Open Table Format wie Iceberg macht daraus Tabellen mit ACID, Schema und Snapshots, die viele Engines lesen und schreiben.

Antwort-Muster

Frage: Was ist ein Data Lakehouse?

  1. Mechanismus: Parquet-Dateien liegen im Object Storage, ein Table Format wie Iceberg beschreibt per Metadaten, welche Dateien die Tabelle sind.
  2. Zahl: Iceberg zielt auf 512 MB pro Datei. Bei einem Commit-Konflikt gibt es standardmässig 4 Retries.
  3. Trade-off: Man bekommt offene Formate und mehrere Engines, muss aber Compaction, Snapshot-Pflege und Catalog selbst betreiben.
  4. Produktion: Ich sichere den Catalog wie eine Datenbank und plane Compaction und expire_snapshots ein.

1. Die Reise eines Commits

  1. Datendateien schreiben: Spark schreibt neue Parquet-Dateien in MinIO. Noch sieht niemand sie. Ein Absturz hier hinterlässt nur verwaiste Dateien (orphan files).
  2. Manifest schreiben: Ein Manifest ist eine Liste von Datendateien. Es speichert pro Datei Partitionswerte und Spalten-Statistiken (min, max, null count).
  3. Manifest List schreiben: Die Manifest List zählt alle Manifeste eines Snapshots auf. Ein Snapshot ist der vollständige Zustand der Tabelle zu einem Zeitpunkt.
  4. Neue Metadaten-Datei: Eine neue metadata.json enthält Schema, Partition Spec, Properties und die Liste der Snapshots.
  5. Commit im Catalog: Der Catalog tauscht den Zeiger von alter auf neue Metadaten-Datei. Der Tausch ist atomar. Er gelingt nur, wenn der Zeiger noch auf die Basis-Version zeigt.
  6. Leser: Ein Leser holt den Zeiger einmal und liest einen festen Snapshot. Er sieht nie einen halben Commit. Leser brauchen keine Locks.
  7. Konflikt: Hat ein anderer Writer zuerst committet, scheitert der Swap. Das ist Optimistic Concurrency. Der Writer prüft seine Annahmen und baut die Metadaten auf dem neuen Stand neu. Iceberg wiederholt den Commit standardmässig bis zu 4-mal (commit.retry.num-retries).

2. Aufbau

  1. Object Storage: Speicher für Dateien über eine HTTP-API (S3-kompatibel). Er ist billig und fast unbegrenzt. Beispiel: MinIO im Kubernetes-Cluster.
  2. Datendateien: Spaltenformat Parquet (oder ORC, Avro). Die Dateien sind unveränderlich. Ein Update schreibt neue Dateien.
  3. Table Format: Metadaten-Dateien, die sagen, welche Dateien zur Tabelle gehören. Beispiel: Apache Iceberg.
  4. Catalog: Er kennt pro Tabelle den Pfad der aktuellen Metadaten-Datei. Er macht den Commit atomar. Beispiel: Nessie, Iceberg REST Catalog, Hive Metastore.
  5. Compute: Engines lesen und schreiben dieselben Tabellen. Spark schreibt, Dremio liest. Compute läuft nur bei Bedarf und skaliert unabhängig vom Speicher.

3. Details

  1. Data Warehouse: Es ist eine Datenbank für Analysen mit festem Schema (Schema-on-Write). Daten werden vor dem Laden bereinigt. Es ist stark für BI und SQL. Viele Warehouses speichern in einem proprietären Format. Das erschwert ML und andere Engines.
  2. Data Lake: Er ist ein billiger Dateispeicher für Daten jeder Art. Das Schema entsteht erst beim Lesen (Schema-on-Read). Ohne Tabellen-Schicht fehlen ACID, Updates und verlässliche Schemas. Das Ergebnis ist oft ein Data Swamp. Es gibt viele Dateien, und niemand weiss, was gilt.
  3. Lakehouse: Es ist Lake-Speicher plus Metadaten-Schicht. Laut Databricks-Doku bietet es offene Formate, direkten Zugriff und geringe Latenz für BI. Ein System dient BI, Data Engineering und ML.
  4. Open Table Format: Es ist eine offene Spezifikation, wie Metadaten über Datendateien eine Tabelle bilden. Die drei bekannten sind Apache Iceberg, Delta Lake und Apache Hudi.
  5. Trennung von Compute und Storage: Speicher und Rechenleistung skalieren getrennt. Man zahlt Speicher dauerhaft und Compute nur beim Rechnen. Mehrere Engines teilen eine Kopie der Daten.
  6. ACID im Object Storage: Object Storage kann kein atomares Umbenennen von Verzeichnissen. Iceberg braucht das nicht. Es listet keine Verzeichnisse und benennt nichts um. Der einzige atomare Schritt ist der Zeiger-Tausch im Catalog.
  7. Snapshot Isolation: Jeder Leser liest einen festen Snapshot. Gleichzeitige Writes stören ihn nicht. Die Iceberg-Spezifikation zielt auf serialisierbare Isolation für Commits.
  8. Hidden Partitioning: Die Partition entsteht durch eine Transform (years, months, days, hours, bucket, truncate). Nutzer filtern auf die echte Spalte. Die Partitionierung kann sich später ändern (Partition Evolution), und alte Dateien bleiben gültig.
  9. Schema Evolution: Iceberg verfolgt Spalten über IDs, nicht über Namen. Umbenennen, Hinzufügen und Löschen ist sicher. Es schreibt keine Daten neu.
  10. Copy-on-Write vs Merge-on-Read: Copy-on-Write schreibt betroffene Dateien bei Update oder Delete neu. Der Write ist teuer und der Read schnell. Merge-on-Read schreibt Delete Files, und der Leser verrechnet sie. Der Write ist billig und der Read teurer. Der Iceberg-Standard für write.delete.mode, write.update.mode und write.merge.mode ist copy-on-write.
  11. Format-Versionen: v1 kennt analytische Tabellen. v2 bringt Row-Level Deletes (Position und Equality Delete Files). v3 bringt Deletion Vectors, Row Lineage, Default-Werte und neue Typen wie variant. Seit Iceberg 1.4.0 ist v2 der Standard.
  12. Catalog: Ohne Catalog gibt es keinen atomaren Commit. Nessie ist ein Catalog mit Git-artigen Branches und Commits über mehrere Tabellen.

4. Fallen

  • „Ein Lakehouse ist ein Data Lake mit Parquet.“ → Falsch. Parquet allein hat kein ACID und keine Snapshots. Erst Table Format und Catalog machen Tabellen daraus.
  • „Iceberg ist eine Query Engine.“ → Falsch. Iceberg ist ein Tabellenformat und eine Bibliothek. Rechnen tun Spark, Dremio, Trino, Flink.
  • „Time Travel ist unbegrenzt.“ → Falsch. Nach expire_snapshots sind alte Snapshots weg.
  • „Object Storage ist transaktional, darum ist der Lake sicher.“ → Falsch. Einzelne Objekte sind atomar, mehrere Dateien nicht. Den Commit über viele Dateien macht das Table Format.
  • „Ein Update ändert die Parquet-Datei.“ → Falsch. Dateien sind unveränderlich. Es entstehen neue Dateien oder Delete Files.

5. Selbsttest

Warum?

Was ist ein Data Swamp?

Ein Lake ohne Struktur, Schema und Ownership. Niemand weiss, welche Dateien gelten. Table Formats und Catalogs verhindern das.

Warum trennt man Compute und Storage?

Beide skalieren unabhängig. Speicher ist billig und dauerhaft, Compute läuft nur bei Bedarf. Mehrere Engines teilen eine Datenkopie.

Warum ist das Small-Files-Problem im Lakehouse so wichtig?

Jede Datei kostet Metadaten, Öffnen und Netzwerk-Requests. Viele kleine Dateien machen Planung und Scan langsam. Lösung: Compaction.

Wie innen?

Was ist ein Data Lakehouse?

Ein Data Lake im Object Storage mit einem Open Table Format darüber. Er bringt ACID, Schema und Snapshots auf offene Dateien. BI, ETL und ML arbeiten auf einer Kopie.

Was ist ein Open Table Format?

Eine offene Spezifikation für Metadaten, die Dateien zu einer Tabelle machen. Beispiele: Iceberg, Delta Lake, Hudi.

Wie ist eine Iceberg-Tabelle aufgebaut?

Catalog-Zeiger → metadata.json → Manifest List (ein Snapshot) → Manifeste → Datendateien. Manifeste speichern Partitionswerte und Spalten-Statistiken.

Wie macht Iceberg einen Commit atomar?

Alle neuen Dateien werden zuerst geschrieben. Dann tauscht der Catalog atomar den Zeiger auf die neue metadata.json. Scheitert der Tausch, wird auf neuem Stand wiederholt.

Was ist Optimistic Concurrency in Iceberg?

Writer arbeiten ohne Lock und prüfen erst beim Commit, ob die Basis noch aktuell ist. Bei Konflikt prüfen sie ihre Annahmen und versuchen es erneut.

Was ist Hidden Partitioning?

Die Partition wird per Transform aus einer Spalte abgeleitet, z. B. days(ts). Nutzer filtern auf ts und bekommen trotzdem Pruning. Keine extra Partitionsspalte.

Was ist Partition Evolution?

Die Partitionierung kann sich ändern, ohne alte Daten neu zu schreiben. Alte Dateien behalten ihre alte Spec, Abfragen planen über beide.

Wie funktioniert Schema Evolution in Iceberg?

Spalten haben IDs. Umbenennen, Hinzufügen, Löschen ändert nur Metadaten. Es gibt keine Verwechslung, wenn ein Name wiederverwendet wird.

Was ist Time Travel?

Abfrage auf einen alten Snapshot mit VERSION AS OF oder TIMESTAMP AS OF. Nur möglich, solange der Snapshot nicht abgelaufen ist.

Welche Rolle spielt der Catalog?

Er bildet Tabellennamen auf die aktuelle Metadaten-Datei ab und macht den Commit atomar. Ohne ihn gibt es keine Transaktionen.

Was ist Nessie?

Ein transaktionaler Catalog mit Git-artiger Versionierung. Er kann Commits über mehrere Tabellen und Branches für Daten.

Zahlen

Was bringt Format-Version 3?

Deletion Vectors, Row Lineage, neue Typen wie variant und Geo-Typen, Default-Werte für Spalten.

Was macht expire_snapshots?

Es entfernt alte Snapshots und die nur von ihnen genutzten Dateien. Der Iceberg-Standard für das Maximalalter ist 5 Tage. Danach ist Time Travel dorthin nicht mehr möglich.

Vergleich

Was ist der Unterschied zwischen Data Lake und Data Warehouse?

Das Warehouse hat Schema-on-Write und saubere, strukturierte Daten für BI. Der Lake speichert alles billig mit Schema-on-Read, aber ohne Transaktionen.

Copy-on-Write oder Merge-on-Read?

Copy-on-Write schreibt betroffene Dateien neu: langsamer Write, schneller Read. Merge-on-Read schreibt Delete Files: schneller Write, Read muss verrechnen. Standard in Iceberg ist Copy-on-Write.

Iceberg oder Delta Lake?

Beide bringen ACID auf Parquet. Iceberg ist breiter Engine-neutral und hat Hidden Partitioning. Delta ist im Databricks- und Fabric-Ökosystem Standard.

Produktion

Szenario: Abfragen auf eine Iceberg-Tabelle werden Woche für Woche langsamer. Was prüfen Sie?

In t.files die Anzahl und Grösse der Dateien, in t.delete_files die Delete Files, in t.snapshots die Anzahl Snapshots. Dann Compaction und expire_snapshots einplanen.

Szenario: Nach einem Pod-Neustart des Catalogs sind alle Tabellen „leer“. Was ist passiert?

Der Catalog hat seinen Zustand verloren, z. B. weil er in einem flüchtigen Speicher lag. Die Dateien liegen noch in MinIO. Lösung: persistentes Backend wie PostgreSQL und Backup.

Szenario: Zwei Spark-Jobs schreiben gleichzeitig in dieselbe Tabelle, einer scheitert mit einer Commit-Exception. Was tun Sie?

Das ist ein Konflikt der Optimistic Concurrency nach allen Retries. Writes nach Partition trennen oder bündeln, einen atomaren Claim gegen überlappende Läufe nutzen, Retries erhöhen.

Design

Ist ein Warehouse heute noch sinnvoll?

Ja, für überschaubare relationale BI-Lasten. Ein Lakehouse lohnt bei grossen Datenmengen, Rohdaten-Historie und mehreren Engines.

Wie wählst du Copy-on-Write oder Merge-on-Read?

Nach dem Verhältnis von Schreiben und Lesen. Viele kleine Updates passen zu Merge-on-Read plus Compaction. Seltene Updates und viele Reads passen zu Copy-on-Write.

Mehr

Gerüst

  • Warum? Ein Warehouse ist teuer und eng. Ein Lake hat kein ACID. Das Lakehouse gibt offenen Dateien Tabellen-Eigenschaften.
  • Wie innen? Object Storage + Parquet + Table Format + Catalog. Der Commit ist ein atomarer Zeiger-Tausch im Catalog.
  • Zahlen Ziel 512 MB pro Datei. Standard-Format ist v2 seit Iceberg 1.4.0. 4 Retries bei Commit-Konflikt.
  • Vergleich Warehouse: Schema-on-Write. Lake: Schema-on-Read. Lakehouse: offene Dateien mit Metadaten. Iceberg, Delta und Hudi.
  • Produktion Small Files, wachsender Speicher, verlorener Catalog. Merge-on-Read braucht Compaction.
  • Design Der Catalog ist der Single Point of Truth. Ein Lakehouse lohnt bei grossen Daten, mehreren Engines und Rohdaten-Historie.

Beispiel: eine Iceberg-Tabelle anlegen, schreiben, in die Vergangenheit schauen

-- Spark SQL mit Iceberg-Catalog "nessie"
CREATE TABLE nessie.match.trades (
  message_id     STRING,
  schema_type    STRING,
  received_date  TIMESTAMP,
  volume         DECIMAL(18,3))
USING iceberg
PARTITIONED BY (days(received_date), schema_type);

INSERT INTO nessie.match.trades VALUES
  ('m1', 'TRADE', TIMESTAMP '2026-11-23 09:00:00', 10.000);
INSERT INTO nessie.match.trades VALUES
  ('m2', 'TRADE', TIMESTAMP '2026-11-24 09:00:00', 5.000);

SELECT snapshot_id, parent_id, operation FROM nessie.match.trades.snapshots;
SELECT count(*) FROM nessie.match.trades VERSION AS OF <erste snapshot_id>;
SELECT * FROM nessie.match.trades WHERE received_date >= '2026-11-24';
snapshot_id   parent_id     operation
<S1>          NULL          append
<S2>          <S1>          append

count(*)
1

message_id  schema_type  received_date        volume
m2          TRADE        2026-11-24 09:00:00  5.000

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Die Snapshot-IDs sind lange Zufallszahlen und hier durch <S1>, <S2> ersetzt.

  1. days(received_date) ist Hidden Partitioning: Iceberg leitet den Partitionswert aus der Spalte ab. Es gibt keine extra Spalte received_day.
  2. Jedes INSERT erzeugt einen neuen Snapshot mit operation = append. Der zweite zeigt über parent_id auf den ersten.
  3. VERSION AS OF ist Time Travel: Die Abfrage liest den alten Snapshot. Darin gibt es nur eine Zeile.
  4. Der Filter auf received_date genügt für Partition Pruning. Iceberg überspringt die Partition vom 23.11. ohne sie zu öffnen.

Vergleich

  • Data Warehouse: Schema-on-Write, saubere Daten, schnelles SQL. Meist proprietärer Speicher. Teuer bei grossen Rohdaten, schwach für ML.
  • Data Lake: billig, jedes Format, Schema-on-Read. Kein ACID, keine Updates, Gefahr Data Swamp.
  • Lakehouse: offene Dateien plus Table Format. ACID, Schema Evolution, Time Travel. Mehr Betrieb: Compaction, Snapshot-Pflege, Catalog.
  • Iceberg: Engine-neutral, Hidden Partitioning, Partition Evolution, viele Catalogs (REST, Nessie, Glue, Hive).
  • Delta Lake: Transaction Log (_delta_log) neben den Parquet-Dateien. Standard in Databricks und Microsoft Fabric.
  • Hudi: auf Upserts und inkrementelles Lesen ausgelegt.
  • Cloud-Warehouse (z. B. Snowflake, BigQuery): trennt Compute und Storage auch. Der Speicher gehört aber dem Anbieter.

In der Produktion

  1. Viele kleine Dateien: Häufige kleine Writes erzeugen viele kleine Parquet-Dateien und Manifeste. Abfragen werden langsam. Lösung: grössere Batches, Compaction mit rewrite_data_files. Iceberg zielt auf 512 MB pro Datei (write.target-file-size-bytes).
  2. Speicher wächst ohne Ende: Alte Snapshots halten alte Dateien fest. Lösung: expire_snapshots regelmässig. Danach ist Time Travel auf diese Snapshots weg.
  3. Verwaiste Dateien: Abgebrochene Writes lassen Dateien ohne Snapshot zurück. Lösung: remove_orphan_files mit genügend Abstand zu laufenden Jobs.
  4. Catalog verloren: Der Catalog ist der wertvollste Teil. Liegt sein Zustand in einem flüchtigen Speicher, sind alle Tabellen-Zeiger weg. Lösung: Catalog mit echter Datenbank (z. B. Nessie auf PostgreSQL) und Backup.
  5. Commit-Konflikte: Viele parallele Writer auf dieselbe Tabelle scheitern nach den Retries. Lösung: Writer pro Partition trennen, Writes bündeln, Retries erhöhen.
  6. Merge-on-Read ohne Pflege: Delete Files sammeln sich an. Lesen wird langsamer. Lösung: Compaction, die Deletes einarbeitet (rewrite_position_delete_files, rewrite_data_files).

Diagnose: Werkzeuge und Abfragen

  • Metadaten-Tabellen: SELECT * FROM t.snapshots, t.history, t.files, t.manifests, t.partitions, t.refs.
  • Kleine Dateien finden: SELECT count(*), avg(file_size_in_bytes) FROM t.files.
  • Delete Files zählen: SELECT count(*) FROM t.delete_files.
  • Pflege: CALL cat.system.rewrite_data_files('db.t'), expire_snapshots, remove_orphan_files, rollback_to_snapshot.
  • Spark UI: Anzahl gelesener Dateien und Partitionen pro Scan zeigt, ob Pruning wirkt.
  • Nessie: Commit-Log pro Branch zeigt, wer wann welche Tabelle geändert hat.

Senior-Punkte

  1. Lakehouse ist kein Produkt, sondern ein Muster: Object Storage + Table Format + Catalog + Engines. Man kann es aus Open-Source-Teilen bauen.
  2. Der Catalog ist der Single Point of Truth. Dateien ohne Catalog-Zeiger sind nur Dateien. Ihn sichern wie eine Produktionsdatenbank.
  3. Offene Formate kaufen Freiheit, kosten aber Betrieb: Compaction, Snapshot-Ablauf, Upgrades von Spark, Iceberg und Catalog im Gleichschritt.
  4. Warehouse ist nicht tot. Für kleine, rein relationale BI-Lasten ist eine Datenbank einfacher. Ein Lakehouse lohnt bei grossen Datenmengen, mehreren Engines oder Rohdaten-Historie.
  5. Copy-on-Write oder Merge-on-Read nach Lese/Schreib-Verhältnis wählen. Viele kleine Updates → Merge-on-Read plus Compaction. Seltene Updates, viele Reads → Copy-on-Write.
  6. Trennung von Compute und Storage heisst auch: Netzwerk wird zum Engpass. Partition Pruning und Spalten-Statistiken sind darum Pflicht.
