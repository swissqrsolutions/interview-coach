Fall: IoT-Datenaufnahme

Lakehouse · Design-Fall · Tier 2 · Quellen: OASIS MQTT 5.0 Spezifikation (QoS, Retained, Session), Apache Kafka 4.4 Docs, Apache Spark 4.3 Docs (Structured Streaming, Watermarks), Apache Iceberg 1.12 Docs (Partitioning, Spark Writes, Maintenance), PostgreSQL 17 Docs (INSERT … ON CONFLICT, date_bin)

Kern (die 1-Minuten-Antwort): IoT-Datenaufnahme sammelt Messwerte von tausenden Geräten zuverlässig in einem Lakehouse. Geräte senden per MQTT, ein Broker leitet nach Kafka, ein Stream-Job schreibt alle paar Minuten nach Iceberg Bronze. Silver typisiert, vereinheitlicht Einheiten und dedupliziert über (device_id, seq); Gold rechnet betroffene Stunden bei Late Data komplett neu.

1. Wo sitzt was? (Architektur)

  1. Geräte: Sensoren messen z. B. Temperatur und Druck. Sie puffern lokal, wenn das Netz weg ist.
  2. MQTT-Broker: MQTT ist ein leichtes Publish/Subscribe-Protokoll für schwache Geräte. Jedes Gerät hat ein eigenes Zertifikat und eigene Topics, z. B. plant1/pump-7/telemetry.
  3. Kafka: Ein Connector oder eine Bridge schreibt alle Nachrichten nach Kafka. Kafka puffert Tage und entkoppelt Broker und Lakehouse.
  4. Ingest-Job: Spark liest Kafka und schreibt alle 5 Minuten nach Bronze. Kurze Trigger würden zu viele kleine Dateien erzeugen.
  5. Bronze: der Payload als String plus Kafka-Offset und Ankunftszeit. Nichts wird verworfen.
  6. Silver: getypte Messwerte, eine Einheit, dedupliziert, sortiert nach Gerät und Zeit.
  7. Gold: Aggregate pro Gerät und Stunde (Anzahl, Mittel, Maximum). Dashboards lesen nur Gold.
  8. Quarantäne: nicht lesbare Payloads mit Grund. So geht nichts still verloren.

2. Die Reise eines Messwerts

  1. Messung: pump-7 misst um 10:50 UTC 55 °C. Das Gerät gibt jeder Messung eine laufende Nummer seq.
  2. Offline: Das Gerät hat kein Netz. Es puffert die Messung zwei Tage lang.
  3. MQTT QoS 1: Danach sendet es mit QoS 1 (at least once). Fehlt die Bestätigung, sendet es noch einmal. Duplikate sind also normal.
  4. Kafka → Bronze: Der Ingest-Job schreibt den Rohwert in Bronze, partitioniert nach Ankunftstag (22.11.).
  5. Silver: Der Silver-Job typisiert und macht ein MERGE auf (device_id, seq). Ein Duplikat ändert nichts.
  6. Betroffene Stunde: Der Job merkt sich alle (Gerät, Stunde), die neue Zeilen bekamen. Hier: 20.11. 10:00.
  7. Gold: Der Gold-Job rechnet genau diese Stunde komplett neu und ersetzt sie. Ein zweiter Lauf ergibt dasselbe.

3. Beispiel: Schemas, Kern-Transformation, Qualitäts-Checks

Schemas (Spark SQL mit Iceberg):

CREATE TABLE lake.bronze.telemetry_raw (
  kafka_partition INT, kafka_offset BIGINT, ingest_time TIMESTAMP, payload STRING
) USING iceberg PARTITIONED BY (days(ingest_time));

CREATE TABLE lake.silver.reading (
  device_id STRING, seq BIGINT, event_time TIMESTAMP, temp_c DECIMAL(5,2),
  pressure_bar DECIMAL(6,3), firmware INT
) USING iceberg
PARTITIONED BY (days(event_time), bucket(16, device_id))
TBLPROPERTIES ('write.distribution-mode'='hash');
ALTER TABLE lake.silver.reading WRITE ORDERED BY device_id, event_time;

CREATE TABLE lake.gold.reading_hourly (
  device_id STRING, hour TIMESTAMP, n BIGINT, avg_temp DECIMAL(5,2), max_temp DECIMAL(5,2)
) USING iceberg PARTITIONED BY (days(hour));

Kern-Transformation, echt ausgeführt (PostgreSQL als Stand-in):

-- Bronze -> Silver: typisieren, Einheit vereinheitlichen, ungültige filtern, Duplikate ignorieren
INSERT INTO silver_reading
SELECT payload->>'d', (payload->>'seq')::bigint, (payload->>'ts')::timestamptz,
       CASE WHEN payload ? 'temp_f' THEN round(((payload->>'temp_f')::numeric - 32) * 5 / 9, 2)
            ELSE (payload->>'temp_c')::numeric END
FROM bronze_raw
WHERE coalesce(payload->>'temp_c', payload->>'temp_f') ~ '^-?[0-9]+(\.[0-9]+)?$'
ON CONFLICT (device_id, seq) DO NOTHING;
SELECT (SELECT count(*) FROM bronze_raw) bronze, (SELECT count(*) FROM silver_reading) silver;

Echte Ausgabe, PostgreSQL 17.12 (Docker), Schema demo_iot_ingestion, danach gelöscht. Bronze hatte 5 Payloads: 1 Duplikat, 1 Wert "ERR", 1 Gerät mit Fahrenheit (Firmware 2). Die Demo-Prozedur rechnet alle Stunden neu; im echten Job nur die betroffenen.

  1. Aus 5 Rohzeilen werden 3 Silver-Zeilen: Das Duplikat fällt per ON CONFLICT weg, "ERR" per Regex.
  2. pump-9 sendet 104 °F. Silver speichert 40,00 °C. Eine Einheit pro Spalte.
  3. date_bin('1 hour', …) legt jede Messung in ihre Stunde nach Event Time.
  4. Nach der späten Messung steigt n von 2 auf 3. Zwei Läufe ergeben dasselbe: idempotent.

Derselbe Silver-Schritt in Spark/Iceberg:

MERGE INTO lake.silver.reading t
USING (SELECT device_id, seq, event_time, temp_c, pressure_bar, firmware
       FROM (SELECT *, row_number() OVER (PARTITION BY device_id, seq
                                          ORDER BY ingest_time) AS rn
             FROM parsed_batch) WHERE rn = 1) s
ON t.device_id = s.device_id AND t.seq = s.seq
   AND t.event_time >= TIMESTAMP '2026-11-18 00:00:00'  -- Pruning: nur Tage ab dem ältesten Event im Batch
WHEN NOT MATCHED THEN INSERT *

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): Iceberg erlaubt pro Zielzeile nur eine passende Quellzeile, sonst bricht MERGE ab. Darum vorher im Batch deduplizieren. Die Datumsgrenze setzt der Job aus dem ältesten event_time im Batch. Spark läuft hier nicht.

Qualitäts-Checks:

  1. Parsebar: Anteil Quarantäne pro Firmware-Version. Steigt er, hat ein Update das Format geändert.
  2. Physikalischer Bereich: z. B. −40 bis 150 °C. Ausserhalb → Flag, nicht löschen.
  3. Lücken: fehlende seq-Nummern pro Gerät zeigen verlorene Nachrichten.
  4. Uhr: event_time mehr als 5 Minuten in der Zukunft → Uhr des Geräts falsch.
  5. Stille Geräte: Gerät ohne Messung seit 1 Stunde → Alarm an den Betrieb.

4. Details, die Interviewer fragen

  1. Volumen (Beispielrechnung): 50 000 Geräte, 1 Messung alle 10 Sekunden, ca. 200 Bytes. Das sind 5000 Messungen/s und ca. 1 MB/s. Pro Tag 432 Mio. Zeilen, ca. 86 GB JSON. In Parquet mit Sortierung nach Gerät und Zeit oft nur ein Bruchteil davon.
  2. MQTT QoS: QoS 0 höchstens einmal (kann verloren gehen), QoS 1 mindestens einmal (Duplikate), QoS 2 genau einmal zwischen zwei Partnern (teurer Handshake). Meist QoS 1 plus Dedup im Lakehouse.
  3. Dedup-Schlüssel: (device_id, seq) ist besser als (device_id, event_time). Zwei Messungen können dieselbe Sekunde haben.
  4. Partitionierung: Bronze nach Ankunftstag, damit Ingest nur anhängt. Silver nach days(event_time) plus bucket(16, device_id). Nie identity(device_id): 50 000 Partitionen pro Tag.
  5. Sortierung: In Silver nach device_id, event_time sortieren. Dann überspringt die Engine über Min/Max-Statistiken die meisten Dateien bei „ein Gerät, eine Woche“.
  6. Late Data: Geräte puffern Stunden oder Tage. Eine feste Watermark würde diese Daten verwerfen. Darum Gold nicht im Stream, sondern pro betroffener Stunde im Batch neu rechnen.
  7. Idempotenz: Bronze ist append-only mit Kafka-Offset. Silver nutzt MERGE auf den Schlüssel. Gold ersetzt Stunden. Jeder Schritt darf wiederholt werden.
  8. Schema-Versionen: Firmware-Updates ändern Felder. Bronze speichert den String, Silver kennt jede Version. Neue Felder per Iceberg Schema Evolution als Spalte hinzufügen.
  9. Small Files: Trigger 5 Minuten, write.distribution-mode=hash, tägliche Compaction mit Sortierung.
  10. Retention und Kosten: Rohdaten 90 Tage in Bronze, Silver 2 Jahre, Gold für immer. Ältere Snapshots mit expire_snapshots löschen. Object Storage kostet pro GB wenig, Abfragen ohne Pruning kosten viel Rechenzeit.

5. Vergleich: Alternativen

  • Zeitreihen-Datenbank (z. B. TimescaleDB, InfluxDB): sehr schnelle Abfragen auf neue Daten, eingebautes Downsampling. Aber teurer bei Jahren Historie, und Data Science braucht oft offene Dateien.
  • Cloud-IoT-Dienst (z. B. Azure IoT Hub, AWS IoT Core) statt eigenem Broker: Geräte-Identität und Skalierung inklusive. Preis: Kosten pro Nachricht und Bindung an den Anbieter.
  • Lakehouse mit Iceberg (diese Lösung): günstig für Jahre Historie, offen für Spark, SQL-Engines und Python. Schwäche: Sekunden-Dashboards. Oft kombiniert: heisse 7 Tage in einer Zeitreihen-DB, alles in Iceberg.

6. In der Produktion

  1. Ein Firmware-Update ändert das Format: Die Quarantäne läuft voll. Lösung: Parser pro Version, Alarm auf Quarantäne-Quote, Bronze neu verarbeiten.
  2. Gold-Werte ändern sich Tage später: Das ist Late Data und korrekt. Lösung: der Fachseite erklären, Gold-Stunden mit „zuletzt neu berechnet“ markieren.
  3. Geräte mit falscher Uhr: Messungen im Jahr 1970 oder in der Zukunft. Lösung: Ankunftszeit als Ersatz und Flag setzen.
  4. Tausende kleine Dateien: zu kurzer Trigger oder Partition nach Gerät. Lösung: Trigger länger, Bucketing, Compaction.
  5. Kafka-Retention zu kurz: Der Ingest war 3 Tage aus, Daten sind weg. Lösung: Retention länger als die längste erwartete Störung, Lag alarmieren.
  6. Ein Gerät flutet: Defekt sendet tausend Nachrichten pro Sekunde. Lösung: Rate-Limit am Broker, Skew im Spark-Job beachten.

7. Diagnose

  • Kafka-Lag: kafka-consumer-groups.sh --describe oder Lag-Metriken in Grafana.
  • Spark Streaming: query.lastProgress zeigt Zeilen pro Sekunde, Batch-Dauer und Watermark.
  • Iceberg: SELECT partition, file_count, record_count FROM lake.silver.reading.partitions für Dateien pro Partition.
  • Lücken: seq - lag(seq) OVER (PARTITION BY device_id ORDER BY seq) > 1 findet verlorene Messungen.
  • Late-Data-Anteil: Differenz ingest_time - event_time als Histogramm.

8. Senior-Punkte

  1. Kafka zwischen Broker und Lakehouse entkoppelt. Fällt das Lakehouse aus, verliert man nichts.
  2. At-least-once plus Dedup ist robuster und billiger als Exactly-Once über alle Hops.
  3. Bronze nach Ankunft, Silver nach Event Time. So bleibt Ingest einfach, und Abfragen sind fachlich richtig.
  4. Gold wird neu berechnet, nicht fortgeschrieben. Late Data von Tagen ist bei IoT normal.
  5. Alarme gehören nicht ins Lakehouse. Sekunden-Alarme laufen direkt auf Kafka; das Lakehouse ist für Analyse.
  6. Partition nach Zeit, Clustering nach Gerät. Hohe Kardinalität nie als Partition.

10. Fallen

  • „Wir partitionieren nach device_id, dann sind Abfragen pro Gerät schnell.“ → Falsch. Zehntausende Partitionen und winzige Dateien. Bucket oder Sortierung nutzen.
  • „QoS 2 löst alle Duplikate.“ → Falsch. QoS 2 gilt nur zwischen zwei MQTT-Partnern, nicht bis ins Lakehouse.
  • „Die Watermark verwirft alte Daten, das ist ok.“ → Falsch. Bei IoT sind Tage Verspätung normal. Gold im Batch neu rechnen.
  • „event_time ist ein guter Dedup-Schlüssel.“ → Falsch. Zwei Messungen können dieselbe Zeit haben. Eine Sequenznummer nutzen.
  • „Bronze können wir sparen.“ → Falsch. Ohne Rohdaten kann man nach einem Parser-Bug nicht neu verarbeiten.

11. Fragen (Interviewer-Nachfragen)

Warum MQTT und nicht direkt Kafka auf den Geräten?

MQTT ist leicht, braucht wenig Strom und Bandbreite und kommt mit instabilen Netzen klar. Kafka-Clients sind für Server gedacht.

Warum noch Kafka hinter dem Broker?

Kafka puffert Tage und erlaubt mehrere Consumer, z. B. Alarme und Lakehouse. Der Broker ist kein Langzeitspeicher.

Welche QoS wählen Sie?

QoS 1 als Standard: kein Verlust, Duplikate werden im Lakehouse entfernt. QoS 0 nur für unwichtige, häufige Werte.

Wie deduplizieren Sie?

Über (device_id, seq). In Silver per MERGE, vorher im Batch selbst mit row_number().

Wie partitionieren Sie Silver?

Nach Tag der Event Time plus bucket(16, device_id), sortiert nach Gerät und Zeit. Nie identity auf device_id.

Wie gehen Sie mit Geräten um, die Tage offline waren?

Sie senden gepufferte Daten später. Silver nimmt sie per MERGE an. Gold rechnet die betroffenen Stunden neu.

Warum Gold nicht direkt im Stream rechnen?

Eine Watermark müsste Tage lang warten oder würde Daten verwerfen. Batch-Neuberechnung der betroffenen Stunden ist einfacher und korrekt.

Wie gehen Sie mit Firmware-Versionen um?

Bronze speichert den Rohstring. Silver hat einen Parser pro Version und schreibt eine einheitliche Einheit. Neue Felder kommen per Schema Evolution dazu.

Welcher Trigger für den Ingest?

Einige Minuten. Kürzer erzeugt viele kleine Dateien und Commits; das Lakehouse braucht keine Sekunden.

Wie finden Sie verlorene Messungen?

Über Lücken in der Sequenznummer pro Gerät, mit lag() in einer Fensterfunktion.

Was tun Sie mit falschen Zeitstempeln?

Plausibilität prüfen. Ist die Zeit unmöglich, Ankunftszeit nutzen und ein Flag setzen. Nie still verwerfen.

Wie lange behalten Sie welche Schicht?

Bronze z. B. 90 Tage, Silver Jahre, Gold dauerhaft. Snapshots regelmässig mit expire_snapshots löschen.

Zeitreihen-DB oder Lakehouse?

Zeitreihen-DB für schnelle Dashboards auf neue Daten. Lakehouse für lange Historie und Data Science. Oft beides.

Wie sichern Sie die Geräte ab?

TLS mit einem Zertifikat pro Gerät und Topic-Rechte pro Gerät. Ein Gerät darf nur in sein eigenes Topic schreiben.

Was kostet am meisten?

Rechenzeit für Abfragen ohne Pruning und Dauerbetrieb von Broker und Kafka. Speicher in Object Storage ist günstig.

Wie testen Sie die Pipeline?

Mit aufgezeichneten Payloads aller Firmware-Versionen, mit Duplikaten und späten Daten. Prüfen: zweimal laufen ergibt dasselbe Gold.

Szenario: Seit gestern landen 30 % der Nachrichten in der Quarantäne. Was tun Sie?

Quarantäne nach Firmware-Version gruppieren. Wahrscheinlich ein Update mit neuem Format. Parser erweitern und die Bronze-Daten neu verarbeiten.

Szenario: Das Dashboard für gestern zeigt heute andere Werte als heute Morgen. Fehler?

Meist nicht: Geräte haben gepufferte Daten nachgeliefert, Gold wurde neu berechnet. Prüfen mit ingest_time minus event_time.

Szenario: Abfragen für ein Gerät über einen Monat dauern Minuten. Was prüfen Sie?

Ob nach Gerät sortiert und gebuckettet ist und ob Compaction läuft. Im Plan prüfen, wie viele Dateien gelesen werden.
