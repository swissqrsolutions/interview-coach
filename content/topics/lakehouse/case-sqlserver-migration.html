Fall: SQL Server → Lakehouse-Migration

Kern (die 1-Minuten-Antwort): Eine SQL-Server-→-Lakehouse-Migration verschiebt Analyse und Statistik aus der operativen Datenbank in offene Tabellen (Iceberg auf Object Storage). Ich baue Bronze/Silver/Gold mit Spark, schreibe idempotent (Delete + Append pro Nachricht in einem Commit) und rechne Statistiken pro Tag komplett neu. Ich gehe parallel live hinter einem Feature Switch und schalte erst um, wenn ein automatischer Paritäts-Check 100 % Gleichheit mit dem Altsystem zeigt.

1. Wo sitzt was? (Architektur)

  1. Quellen: Dateien kommen wie bisher an. Der SQL Server bleibt die Steuerung: Er hält pro Nachricht einen Status, z. B. Pending.
  2. Ingest (Spark): Ein Spark-Job holt offene Nachrichten, lädt die Datei und parst sie. Für die Historie liest er Altdaten einmalig per JDBC.
  3. Bronze: roh geparste Records, kaum verändert. Damit kann man später neu rechnen.
  4. Silver: getypte, geprüfte, deduplizierte Fachtabellen, partitioniert nach Datum.
  5. Gold: fertige Statistiken pro Tag, z. B. Anzahl und Volumen.
  6. Katalog: Er zeigt auf die aktuelle Metadaten-Datei jeder Tabelle. Ohne ihn gibt es keine Tabellen.
  7. Serving: Eine Query Engine liest Iceberg und liefert an die neue UI. Die alte UI bleibt auf SQL Server.
  8. Paritäts-Job: Er vergleicht Altsystem und Gold Tabelle für Tabelle. Er ist das Abnahmekriterium.

2. Die Reise eines Records (von der Datei bis zum Chart)

  1. Pending: Eine neue Datei ist da. In SQL Server steht eine Zeile mit status = 'Pending'.
  2. Atomarer Claim: Der Job setzt in einer Anweisung Pending → Processing und bekommt die Zeilen zurück. In SQL Server mit UPDATE … OUTPUT INSERTED.*. Zwei Jobs können dieselbe Nachricht nicht beide holen.
  3. Parse und Prüfen: Spark lädt die Datei, parst sie und prüft Typen, Pflichtfelder und Schlüssel. Ungültige Zeilen gehen in eine Quarantäne-Tabelle.
  4. Ein Commit: Spark löscht alle Zeilen dieser message_id und hängt die neuen an. Beides liegt in einem Iceberg-Commit. Leser sehen alt oder neu, nie halb.
  5. Completed: Erst nach dem Commit setzt der Job den Status. Stirbt er davor, ist die Nachricht noch Processing.
  6. Gold-Job: Er rechnet jeden betroffenen Tag komplett neu und ersetzt ihn. Er startet erst, wenn der Ingest Completed ist.
  7. Chart: Die neue UI liest Gold über die Query Engine.
  8. Absturz: Eine Stale-Job-Recovery setzt Nachrichten, die zu lange in Processing hängen, auf Pending zurück. Der Neulauf ersetzt statt zu addieren. Das Ergebnis ist gleich.

3. Beispiel: Schemas, Kern-Transformation, Qualitäts-Checks

Schemas (Spark SQL mit Iceberg):

CREATE TABLE lake.silver.trade (
  message_id     BIGINT    NOT NULL,
  trade_id       STRING    NOT NULL,
  schema_type    STRING    NOT NULL,
  received_date  TIMESTAMP NOT NULL,   -- immer UTC
  trade_date     DATE,
  volume_mwh     DECIMAL(18,3),
  price_eur      DECIMAL(18,2)
) USING iceberg
PARTITIONED BY (days(received_date), schema_type)
TBLPROPERTIES ('format-version'='2',
               'write.delete.mode'='merge-on-read',
               'write.update.mode'='merge-on-read',
               'write.merge.mode'='merge-on-read');

CREATE TABLE lake.gold.daily_stats (
  stat_date DATE, trades BIGINT, volume_mwh DECIMAL(18,3)
) USING iceberg PARTITIONED BY (months(stat_date));

Kern-Transformation (PySpark, Ausschnitt):

# Delete + Append für die geclaimten Nachrichten in EINEM Commit.
# parsed_df enthält alle neuen Zeilen der geclaimten message_ids.
parsed_df.createOrReplaceTempView("incoming")
ids = ",".join(str(r.message_id) for r in claimed)
spark.sql(f"""
  MERGE INTO lake.silver.trade t
  USING incoming s
  ON t.message_id = s.message_id AND t.trade_id = s.trade_id
  WHEN MATCHED THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *
  WHEN NOT MATCHED BY SOURCE AND t.message_id IN ({ids}) THEN DELETE""")

# Gold: betroffene Tage komplett neu rechnen (replace, nicht add)
spark.sql("""
  MERGE INTO lake.gold.daily_stats t
  USING (SELECT trade_date AS stat_date, count(*) AS trades, sum(volume_mwh) AS volume_mwh
         FROM lake.silver.trade WHERE trade_date IN (SELECT d FROM affected_days)
         GROUP BY trade_date) s
  ON t.stat_date = s.stat_date
  WHEN MATCHED THEN UPDATE SET *
  WHEN NOT MATCHED THEN INSERT *""")

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): jedes MERGE erzeugt genau einen neuen Snapshot; mit Merge-on-Read schreibt es Delete Files plus neue Datendateien. Alte Zeilen der Nachricht, die nicht mehr im Input sind, löscht WHEN NOT MATCHED BY SOURCE (Spark 3.5+). Spark und Iceberg laufen hier nicht.

Dasselbe Muster echt ausgeführt (PostgreSQL als Stand-in):

-- Claim (SQL Server: UPDATE ... OUTPUT INSERTED.*)
UPDATE message SET status='Processing', claimed_at=now()
WHERE message_id IN (SELECT message_id FROM message WHERE status='Pending'

RETURNING message_id, status;

Echte Ausgabe, PostgreSQL 17.12 (Docker), Schema demo_sqlserver_migration, danach gelöscht. Gekürzt auf die wichtigen Zeilen.

  1. Der Claim gibt genau die geholten Zeilen zurück. SKIP LOCKED lässt einen zweiten Job andere Zeilen nehmen.
  2. Der erste Lauf löscht 0 Zeilen, der Retry löscht 3 und schreibt 3. Danach sind es 3 Zeilen, nicht 6. Das ist Idempotenz.
  3. Die Recovery setzt Nachricht 3 zurück auf Pending, weil sie zu lange in Processing hing.
  4. Der Paritäts-Check findet 0 abweichende Zeilen, und 2 von 2 Tagen sind gleich.

Qualitäts-Checks (pro Lauf):

  1. Schlüssel: trade_id ist pro message_id eindeutig. Duplikate → Lauf stoppen.
  2. Pflichtfelder: received_date, trade_id nicht NULL. Sonst Zeile in die Quarantäne.
  3. Zeilenzahl: Anzahl geparster Records = Anzahl Records im XML. Abweichung → Failed.
  4. Wertebereich: Volumen ≥ 0, Datum nicht in der Zukunft.
  5. Parität: Gold gegen Altsystem pro Tabelle mit EXCEPT in beide Richtungen.

4. Details, die Interviewer fragen

  1. Volumen (Rechnung): 250 Mio. Zeilen × ca. 200 Bytes sind ca. 50 GB im Zeilenformat. Als Parquet mit Kompression sind es oft nur einige GB. Das ist eine Schätzung, kein Messwert. Für Spark ist das eine kleine bis mittlere Datenmenge.
  2. Historien-Backfill: Spark liest Altdaten per JDBC parallel. Die Optionen partitionColumn, lowerBound, upperBound und numPartitions teilen den Read in Bereiche. Ohne sie liest ein einziger Task alles. Der Backfill läuft nachts, damit die OLTP-Last klein bleibt.
  3. Partitionierung: days(received_date) plus ein Typ-Feld. Das passt zu den Abfragen „pro Tag“ und erlaubt Partition Pruning. Keine Partition nach hoher Kardinalität wie trade_id.
  4. Idempotenz: Der Schlüssel ist die message_id. Ein Neulauf ersetzt genau ihre Zeilen. Gold ersetzt ganze Tage. Nichts wird addiert.
  5. Gleichzeitigkeit: Der atomare Claim verhindert, dass zwei Läufe dieselbe Nachricht holen. Iceberg selbst nutzt optimistische Commits: Bei einem Konflikt scheitert ein Commit und wird wiederholt.
  6. Late Data: Eine Korrektur für einen alten Tag ist einfach eine neue Nachricht. Der Gold-Job rechnet alle betroffenen Tage neu.
  7. Zwei Status pro Nachricht: einer für Ingest, einer für Statistik. Statistik startet nur nach Completed im Ingest. So rechnet Gold nie auf halben Daten.
  8. Kosten: Object Storage ist billig. Teuer sind Rechenzeit und Betrieb. Spark läuft nur bei Bedarf (demand-driven), Nodes skalieren danach wieder herunter.
  9. Typen-Fallen: DATETIME ohne Zeitzone, money, Kultur-abhängige Zahlen- und Datumsformate, NULL gegen leeren String. Jede davon kann die Parität brechen.
  10. Wartung: Merge-on-Read erzeugt Delete Files und kleine Dateien. Darum regelmässig rewrite_data_files und expire_snapshots.

5. Vergleich: Alternativen

  • Im SQL Server bleiben und tunen (Columnstore-Index, Read Replica, Reporting-DB): wenig Umbau. Aber Analyse und OLTP teilen sich weiter Lizenz und Ressourcen, und Neu-Rechnen der Historie bleibt teuer.
  • Cloud-Warehouse (z. B. Synapse, Snowflake): gut für SQL-Analysen, wenig Betrieb. Aber proprietäres Format, Kosten pro Abfrage, und eine Behörde will oft keinen Vendor Lock-in.
  • Lakehouse mit Iceberg (diese Lösung): offenes Format, mehrere Engines, günstiger Speicher, Time Travel. Preis: mehr Komponenten im Betrieb (Katalog, Storage, Spark, Engine).
  • Big Bang statt Parallelbetrieb: schneller fertig, aber kein Beweis der Korrektheit und kein schneller Rückweg. Für ein reguliertes System zu riskant.

6. In der Produktion

  1. Zahlen stimmen nicht mit dem Altsystem überein: Ursachen sind oft Parsing-Unterschiede (Kultur, Zeitzone, NULL gegen leer). Lösung: automatischer Paritäts-Job pro Tabelle, Fehler einzeln fixen.
  2. Doppelte Summen nach Retry: Ein Job addiert statt zu ersetzen. Lösung: ganze Tage neu rechnen und überschreiben.
  3. Nachrichten hängen in Processing: Ein Pod ist gestorben. Lösung: Stale-Job-Recovery mit Timeout.
  4. Katalog weg, Tabellen „leer“: Der Katalog lief ohne persistenten Speicher. Lösung: Katalog auf eine echte Datenbank, z. B. PostgreSQL, mit Backup.
  5. Abfragen werden langsam: kleine Dateien und viele Delete Files. Lösung: Compaction und Snapshot-Expiry planen.
  6. JDBC-Backfill legt die OLTP-DB lahm: zu viele parallele Verbindungen. Lösung: numPartitions begrenzen, nachts laufen, gegen eine Replica lesen.

7. Diagnose

  • Backlog: SELECT status, count(*) FROM message GROUP BY status. Wachsendes Pending heisst: Ingest zu langsam oder blockiert.
  • Iceberg-Metadaten: SELECT * FROM lake.silver.trade.snapshots (wer schrieb wann was), .files (Dateigrössen), .partitions.
  • Parität: EXCEPT in beide Richtungen pro Tabelle, dazu Zeilenzahl und Summen pro Tag.
  • Spark UI: Stage-Dauer, Spill, Skew beim Parse- und Gold-Job.
  • Monitoring: Job-Dauer, Anzahl Failed, Pod-Restarts als Metriken mit Alarm.
  • Time Travel: VERSION AS OF <snapshot_id> zeigt, wie Gold vor einem Lauf aussah.

8. Senior-Punkte

  1. Parität ist das Abnahmekriterium, nicht „sieht gut aus“. Ohne maschinellen Vergleich portiert man keine Fachlogik.
  2. Erst Verhalten migrieren, dann Semantik korrigieren. Ein Fehler im Altsystem wird zuerst nachgebaut. Die Korrektur ist eine eigene, sichtbare Entscheidung.
  3. Ersetzen statt addieren macht Retries sicher. Das ist wichtiger als jede Exactly-Once-Garantie.
  4. Batch statt Streaming, wenn Daten als Dateien mit Fristen kommen. Minuten Latenz reichen, und Batch ist leichter crash-sicher.
  5. Der Katalog ist das wertvollste Teil. Er braucht Backup und eine echte Datenbank.
  6. Parallelbetrieb mit Feature Switch gibt einen Rückweg ohne Deployment.
  7. SQL Server bleibt die Steuerung. Man muss nicht alles auf einmal migrieren.

9. Dein Beispiel

10. Fallen

  • „Wir kopieren die Tabellen 1:1 und sind fertig.“ → Falsch. Die Fachlogik (Statistik) muss mit bewiesener Parität mitkommen.
  • „Spark schreibt exactly-once, also gibt es keine Duplikate.“ → Falsch. Ein Retry nach Absturz schreibt neu. Nur Ersetzen pro Schlüssel schützt.
  • „Status zuerst auf Completed, dann schreiben.“ → Falsch. Erst committen, dann Status setzen.
  • „Iceberg-Tabellen liegen in MinIO, also ist ein Bucket-Backup genug.“ → Falsch. Ohne Katalog findet niemand die aktuelle Version.
  • „Streaming ist moderner, also nehmen wir Streaming.“ → Falsch. Die Latenz-Anforderung entscheidet.

11. Fragen (Interviewer-Nachfragen)

Warum überhaupt weg vom SQL Server?

Statistik Zeile für Zeile skaliert bei hunderten Millionen Zeilen nicht. Analysen belasten die operative DB. Und Neu-Rechnen der Historie ist dort teuer.

Warum Iceberg und nicht Delta Lake?

Iceberg ist herstellerneutral und wird von vielen Engines gelesen, z. B. Spark und Dremio. Dazu Hidden Partitioning, Schema Evolution und freie Wahl des Katalogs. Delta ist stärker an Spark und Databricks gebunden.

Wie verhindern Sie, dass zwei Jobs dieselbe Nachricht verarbeiten?

Mit einem atomaren Claim: ein UPDATE von Pending auf Processing, das die Zeilen zurückgibt. In SQL Server mit OUTPUT INSERTED.*, in PostgreSQL mit RETURNING und SKIP LOCKED.

Was passiert, wenn der Job mitten im Schreiben stirbt?

Der Iceberg-Commit ist atomar, also ist nichts halb sichtbar. Die Nachricht bleibt in Processing. Die Stale-Job-Recovery setzt sie zurück, und der Neulauf ersetzt die Zeilen.

Wie schreiben Sie idempotent in Iceberg?

Delete aller Zeilen einer message_id und Append der neuen in einem Commit, z. B. mit einem MERGE mit WHEN NOT MATCHED BY SOURCE … DELETE. Ein Retry ergibt dasselbe Ergebnis.

Warum rechnen Sie Gold pro Tag neu statt inkrementell?

Weil Ersetzen bei Retries immer richtig ist. Montag hat 10, es kommen 3 dazu: Neu-Rechnen gibt immer 13, doppeltes Addieren gibt 16.

Wie migrieren Sie die Historie?

Einmaliger Backfill per Spark JDBC mit partitionColumn und numPartitions, nachts oder gegen eine Replica. Danach laufen neue Daten über den normalen Ingest.

Wie beweisen Sie, dass die neuen Zahlen stimmen?

Mit einem Paritäts-Job: Ergebnis Altsystem und Gold pro Tabelle mit EXCEPT in beide Richtungen. Go-live erst bei 100 %.

Welche Unterschiede brechen die Parität am häufigsten?

Kultur-abhängiges Parsen von Zahlen und Datum, Zeitzonen, NULL gegen leeren String, Rundung bei Dezimalzahlen.

Das Altsystem rechnet eine Kennzahl falsch. Bauen Sie den Fehler nach?

Ja, zuerst. Sonst ist die Parität nicht prüfbar. Die Korrektur kommt danach als eigene, sichtbare Entscheidung mit der Fachseite.

Wie partitionieren Sie die Silver-Tabelle?

Nach Tag des Empfangs und nach Nachrichtentyp, mit Iceberg Hidden Partitioning. Das passt zu den Abfragen und erlaubt Pruning.

Copy-on-Write oder Merge-on-Read?

Merge-on-Read für häufige kleine Deletes pro Nachricht, weil Schreiben dann billig ist. Dafür braucht es regelmässige Compaction für schnelles Lesen.

Warum Batch und nicht CDC-Streaming?

Die Daten kommen als Dateien mit Fristen, Minuten Latenz reichen. Batch ist viel einfacher idempotent und crash-sicher zu machen.

Wann würden Sie CDC nutzen?

Wenn die Quelle laufend Zeilen ändert und das Lakehouse aktuell bleiben muss. Dann liest man das Transaktions-Log, z. B. SQL Server CDC, statt ganze Tabellen zu kopieren.

Wie schalten Sie um, ohne Risiko?

Parallelbetrieb: Altsystem läuft weiter, die neue UI ist hinter einem Feature Switch. Umschalten und Zurückschalten ist eine Konfiguration, kein Deployment.

Wer liest die Daten, und wie?

Eine Query Engine wie Dremio liest Iceberg über den Katalog. Die UI holt Daten per Arrow Flight SQL, das spaltenweise und schnell überträgt.

Was passiert mit kleinen Dateien?

Viele kleine Batches erzeugen viele kleine Dateien und Delete Files. Lösung: Nachrichten bündeln, rewrite_data_files und expire_snapshots regelmässig.

Was kostet diese Architektur?

Speicher ist billig. Kosten entstehen durch Rechenzeit und Betrieb mehrerer Komponenten. Spark nur bei Bedarf starten und Nodes automatisch herunterskalieren.

Wie testen Sie die Pipeline?

Unit-Tests für Parser und Rechner, Integrationstests mit echten Containern, Idempotenz-Test (zweimal laufen, gleiches Ergebnis) und der Paritäts-Job.

Was ist das grösste Risiko der Migration?

Stille Abweichungen in Zahlen. Darum ist der automatische Paritäts-Check wichtiger als Geschwindigkeit.

Szenario: Nach dem Go-live meldet die Fachseite, die Summe für einen Tag ist zu hoch. Was tun Sie?

Prüfen, ob ein Retry addiert statt ersetzt hat. Snapshots der Gold-Tabelle ansehen und mit Time Travel vergleichen. Den Tag neu rechnen und die Ursache im Job fixen.

Szenario: Die Pending-Warteschlange wächst seit Stunden. Wie gehen Sie vor?

Prüfen, ob Spark-Jobs starten (Pods Pending, Ressourcen), ob Nachrichten in Processing hängen und ob die Recovery läuft. Dann Logs des letzten Laufs und Spark UI.

Szenario: Der Paritäts-Check zeigt 0,1 % Abweichung, alle an einem Tag um Mitternacht. Woran denken Sie?

An Zeitzonen: Das Altsystem rechnet in Lokalzeit, Spark in UTC. Datum vor dem Gruppieren in derselben Zeitzone bestimmen und erneut vergleichen.
