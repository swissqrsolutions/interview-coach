Dateiformate: Parquet, Avro, ORC, CSV

Lakehouse · Tier 1 · Quellen: Apache Parquet Docs (File Format, Compression), Apache Avro 1.12 Specification (Object Container Files, Schema Resolution), Apache ORC Docs, Spark SQL Data Sources (Parquet), Apache Iceberg Docs (Configuration)

Kern: Ein Dateiformat legt fest, wie Zeilen und Spalten als Bytes auf der Platte liegen. Zeilenformate (CSV, JSON, Avro) sind gut zum Schreiben und Austauschen ganzer Datensätze. Spaltenformate (Parquet, ORC) sind gut für Analysen, weil sie nur die nötigen Spalten lesen und stark komprimieren.

1. Wo sitzt das Dateiformat?

  1. Engine: Spark schreibt, Dremio liest. Beide sprechen dieselben Formate.
  2. Tabellenformat: Iceberg verwaltet, welche Dateien zu einer Tabelle gehören. Es ist kein Dateiformat. Datendateien können Parquet, Avro oder ORC sein.
  3. Dateiformat: Es legt die Bytes in der Datei fest. In Iceberg ist Parquet der Standard (write.format.default=parquet).
  4. Zeilenformat: Alle Felder eines Datensatzes liegen nebeneinander. Gut zum Anhängen und zum Lesen ganzer Datensätze.
  5. Spaltenformat: Alle Werte einer Spalte liegen nebeneinander. Gut für SUM(price) über Millionen Zeilen.

2. Die Reise einer Abfrage durch zwei Formate

  1. Die Abfrage: Ein Analyst fragt den Durchschnittspreis für den Markt CH. Er braucht 2 von 5 Spalten.
  2. CSV: Die Engine liest jedes Byte. Sie parst jede Zeile, wandelt Text in Zahlen und filtert erst danach. Kein Schema, keine Statistik.
  3. Parquet, Schritt 1: Die Engine liest zuerst den Footer am Ende der Datei. Dort stehen Schema, Positionen und Min/Max-Werte.
  4. Parquet, Schritt 2: Blöcke, deren Statistik „CH“ ausschliesst, liest sie nicht. Das heisst Predicate Pushdown.
  5. Parquet, Schritt 3: Sie liest nur die Spalten market und price. Das heisst Column Pruning (Projection Pushdown).
  6. Ergebnis: Weniger I/O, keine Text-Umwandlung, bessere Kompression. Bei breiten Tabellen ist das oft ein Faktor 10 oder mehr.

3. Beispiel: Grösse und Kompression messen

100 000 Trades (ID, Markt, Preis, Volumen, Datum). Gleiche Werte, verschiedene Formate, gzip Stufe 6. Parquet und Avro sind hier nicht installiert. Darum vergleicht die Messung auch dieselben Bytes einmal zeilenweise und einmal spaltenweise.

rows = [{"trade_id": f"T{i:07d}", "market": random.choice(["CH","DE","FR","IT"]),
         "price": round(random.uniform(40, 60), 2), "volume_mwh": random.randint(1, 50),
         "trade_date": f"2026-11-{random.randint(1, 30):02d}"} for i in range(100_000)]
csv_b  = ...                                   # csv.DictWriter
json_b = "\n".join(json.dumps(r) for r in rows)  # JSON Lines
row_b  = "\n".join("|".join(values of one row))        # zeilenweise
col_b  = "".join("\n".join(values of one column))      # spaltenweise
gzip.compress(x, 6)
CSV               3.27 MB  gzip   0.78 MB
JSON Lines       10.27 MB  gzip   1.02 MB
rows  (|-sep)     3.17 MB  gzip   0.78 MB
columns (same)    3.17 MB  gzip   0.66 MB
read only 'price': row layout scans   3.17 MB | column layout scans   0.59 MB

Echte Ausgabe, Python 3.12 (eigene Messung, kein echtes Parquet). Ein echtes Parquet wäre durch Dictionary-Encoding und Binärtypen noch kleiner. Erwartung laut Doku, nicht gemessen.

  1. JSON ist 3× grösser als CSV, weil jeder Datensatz die Feldnamen wiederholt. Nach gzip schrumpft der Unterschied stark.
  2. Dieselben Bytes spaltenweise komprimieren besser (0.66 statt 0.78 MB). Gleichartige Werte stehen nebeneinander, der Kompressor findet mehr Muster.
  3. Nur eine Spalte lesen: Spaltenweise liest man 0.59 MB statt 3.17 MB. Das ist der Hauptvorteil von Parquet und ORC.
  4. gzip auf CSV hilft beim Speichern, aber nicht beim Lesen: Eine gzip-Datei ist nicht teilbar. Ein Spark-Task muss sie ganz lesen.

4. Details, die Interviewer fragen

  1. CSV: Text, eine Zeile pro Datensatz. Kein Schema, keine Typen, keine Nulls (nur leere Felder). Probleme: Trennzeichen im Text, Zeilenumbrüche in Feldern, Kodierung, Dezimalkomma.
  2. JSON: Text, selbstbeschreibend, verschachtelt. Spark liest standardmässig JSON Lines: ein Objekt pro Zeile. Kein festes Schema, Typen nur grob (Zahl, String, Bool).
  3. Avro: binäres Zeilenformat. Die Datei (Object Container File) beginnt mit Obj und Byte 1. Im Header steht das Schema als JSON (avro.schema) und ein 16-Byte Sync Marker. Danach folgen Blöcke, jeder mit dem Sync Marker am Ende. So ist die Datei teilbar.
  4. Avro Schema Evolution: Beim Lesen gibt es ein Writer-Schema und ein Reader-Schema. Felder werden per Name zugeordnet. Ein neues Feld im Reader braucht einen Default. Ein Feld nur im Writer wird ignoriert. Typen dürfen erweitert werden, z. B. int → long.
  5. Parquet: binäres Spaltenformat. Aufbau: Magic PAR1, Row Groups mit je einem Column Chunk pro Spalte, darin Pages, am Ende der Footer mit Schema und Statistiken. Der Footer steht am Ende, damit man in einem Durchgang schreiben kann.
  6. ORC: binäres Spaltenformat aus der Hive-Welt. Die Datei ist in Stripes geteilt, standardmässig etwa 64 MB. Eingebaute Row-Indizes grenzen eine Suche auf Gruppen von 10 000 Zeilen ein. Unterstützt alle Hive-Typen, auch Structs, Lists, Maps und Unions.
  7. Kompression: Parquet erlaubt u. a. SNAPPY, GZIP, ZSTD, LZ4_RAW, BROTLI. Spark schreibt Parquet standardmässig mit snappy. Iceberg schreibt Parquet standardmässig mit zstd. Snappy ist schnell, zstd kleiner bei ähnlicher Geschwindigkeit, gzip klein aber langsam.
  8. Kompression pro Block: Parquet und Avro komprimieren pro Page bzw. Block. Darum bleiben sie teilbar (splittable). Eine .csv.gz-Datei ist nicht teilbar.
  9. Schema im Format: Avro, Parquet und ORC speichern das Schema in der Datei. CSV und JSON nicht. Darum braucht Spark bei CSV inferSchema oder ein festes Schema.
  10. Schema-Merge in Spark: spark.sql.parquet.mergeSchema ist standardmässig false. Spark nimmt dann das Schema einer Datei. Iceberg löst das sauberer: Das Schema steht in den Tabellen-Metadaten.
  11. Iceberg und Formate: Iceberg-Datendateien sind Parquet, Avro oder ORC. Die Manifest-Dateien von Iceberg selbst sind Avro.
  12. Arrow: Apache Arrow ist ein spaltenweises In-Memory-Format, kein Speicherformat. Parquet liegt auf der Platte, Arrow im Speicher. Dremio liest Parquet und arbeitet intern mit Arrow.

5. Vergleich

  • CSV: Zeile, Text, kein Schema. Gut für Austausch mit Menschen und Excel. Schlecht für Analysen.
  • JSON: Zeile, Text, verschachtelt, kein festes Schema. Gut für APIs und Logs. Gross und langsam zu parsen.
  • Avro: Zeile, binär, Schema im Header, gute Schema Evolution. Gut für Kafka-Nachrichten, Ingestion, Schreiben Datensatz für Datensatz.
  • Parquet: Spalte, binär, Schema und Statistiken im Footer. Standard für Lakehouse-Analysen, breit unterstützt (Spark, Dremio, Trino, DuckDB, pandas).
  • ORC: Spalte, binär, Stripes mit Indizes. Stark im Hive-Umfeld. Ausserhalb davon weniger verbreitet als Parquet.
  • Zeile vs Spalte: Zeile für „schreibe oder lies ganze Datensätze“. Spalte für „lies wenige Spalten aus vielen Zeilen“.

6. In der Produktion

  1. CSV mit Dezimalkomma oder falscher Kodierung: Zahlen werden zu Text oder NULL. Lösung: festes Schema, Optionen wie encoding setzen, Range-Checks.
  2. Grosse .csv.gz-Dateien: Ein Task liest die ganze Datei allein. Lösung: früh in Parquet umwandeln (Bronze → Silver).
  3. Schema-Konflikte in Parquet-Ordnern: Alte und neue Dateien haben verschiedene Spalten. Ohne Tabellenformat liest Spark nur ein Schema. Lösung: Iceberg mit Schema Evolution.
  4. Zeitstempel falsch: Spark schreibt Parquet-Zeitstempel standardmässig als INT96. Andere Engines lesen sie anders oder mit falscher Zeitzone. Lösung: spark.sql.parquet.outputTimestampType bewusst setzen, Zeitzone testen.
  5. Viele kleine Parquet-Dateien: Jede Datei hat einen eigenen Footer. Das Spaltenformat lohnt sich dann kaum. Lösung: Compaction.
  6. JSON in Bronze ohne Schema: Spark leitet das Schema bei jedem Lesen neu ab, das ist langsam und instabil. Lösung: Schema fest vorgeben.

7. Diagnose: Werkzeuge und Befehle

  • Spark-Plan: df.explain() zeigt bei Parquet PushedFilters und ReadSchema. So sieht man Pushdown und Column Pruning.
  • Spark UI: „Input Size“ und „Number of files read“ pro Stage zeigen, wie viel wirklich gelesen wurde.
  • Parquet-Metadaten: parquet-cli meta datei.parquet (parquet-java) zeigt Row Groups, Codec, Encodings, Statistiken.
  • Iceberg: SELECT file_format, record_count, file_size_in_bytes FROM db.t.files zeigt Format und Grösse jeder Datei.
  • Erste Bytes prüfen: PAR1 am Anfang und Ende heisst Parquet. Obj plus Byte 1 heisst Avro. ORC am Anfang heisst ORC.

8. Senior-Punkte

  1. Rohformat und Analyseformat trennen. Rohe Dateien (XML, CSV, JSON) bleiben in Bronze. Ab Silver ist alles Parquet in einem Tabellenformat.
  2. Das Format allein reicht nicht. Erst Tabellenformat plus Parquet gibt Schema Evolution, Transaktionen und Partition Pruning.
  3. Avro für Nachrichten, Parquet für Tabellen. Avro passt zu einzelnen Datensätzen im Fluss. Parquet passt zu grossen Scans.
  4. Kompression ist eine Abwägung zwischen CPU und I/O. zstd ist heute oft der beste Kompromiss.
  5. Interoperabilität entscheidet. Parquet liest fast jede Engine. Darum ist es der sichere Standard für mehrere Engines.

10. Fallen

  • „Iceberg ist ein Dateiformat wie Parquet.“ → Falsch. Iceberg ist ein Tabellenformat. Es verwaltet Parquet-, Avro- oder ORC-Dateien.
  • „Arrow und Parquet sind dasselbe.“ → Falsch. Arrow ist im Speicher, Parquet auf der Platte.
  • „gzip macht CSV gut für Spark.“ → Falsch. Eine .gz-Datei ist nicht teilbar. Ein Task liest sie allein.
  • „Parquet ist immer besser.“ → Falsch. Für einzelne Datensätze im Stream oder für ganze-Zeile-Zugriffe ist Avro besser.
  • „Spaltenformate kann man nicht anhängen.“ → Ungenau. Eine Parquet-Datei ändert man nicht. Man schreibt neue Dateien, das Tabellenformat hängt sie an.

11. Fragen

Was ist der Unterschied zwischen Zeilen- und Spaltenformat?

Zeilenformat: Felder eines Datensatzes liegen nebeneinander. Spaltenformat: Werte einer Spalte liegen nebeneinander. Spalten sind besser für Analysen, Zeilen für ganze Datensätze.

Warum ist ein Spaltenformat schneller für Analysen?

Es liest nur die nötigen Spalten, überspringt Blöcke per Statistik und komprimiert besser, weil gleichartige Werte nebeneinander liegen.

Was sind die Schwächen von CSV?

Kein Schema, keine Typen, keine echten Nulls. Probleme mit Trennzeichen, Kodierung und Dezimalkomma. Jede Abfrage liest alles.

Was ist JSON Lines?

Ein JSON-Objekt pro Zeile. Spark liest das standardmässig. Für ein grosses JSON-Dokument braucht es die Option multiLine.

Wie ist eine Avro-Datei aufgebaut?

Header mit Magic, Schema als JSON und 16-Byte Sync Marker. Dann Datenblöcke mit Anzahl, Grösse, Daten und Sync Marker.

Wie funktioniert Schema Evolution in Avro?

Writer- und Reader-Schema werden per Feldname abgeglichen. Neue Felder im Reader brauchen einen Default. Felder nur im Writer werden ignoriert.

Wo wird Avro typisch genutzt?

Für Nachrichten in Kafka und für Ingestion, also Datensatz für Datensatz. Iceberg nutzt Avro auch für seine Manifest-Dateien.

Wie ist eine Parquet-Datei grob aufgebaut?

PAR1, dann Row Groups mit Column Chunks und Pages, dann der Footer mit Schema und Statistiken, seine Länge und wieder PAR1.

Warum steht der Parquet-Footer am Ende?

Damit der Writer in einem Durchgang schreiben kann. Die Positionen der Blöcke sind erst am Ende bekannt.

Parquet vs ORC?

Beide sind Spaltenformate mit Statistiken. ORC kommt aus Hive und hat Stripes mit Indizes. Parquet ist ausserhalb von Hive weiter verbreitet.

Was ist Predicate Pushdown?

Der Filter geht bis in den Reader. Blöcke, deren Min/Max den Filter ausschliessen, werden nicht gelesen.

Was ist Column Pruning?

Die Engine liest nur die Spalten, die die Abfrage braucht. Das geht nur in Spaltenformaten effizient.

Welche Kompression nutzt Spark und Iceberg standardmässig für Parquet?

Spark: snappy. Iceberg: zstd.

Snappy, gzip oder zstd?

Snappy ist schnell mit mittlerer Kompression. Gzip ist klein, aber langsam. Zstd ist klein und schnell, oft der beste Kompromiss.

Warum ist .csv.gz schlecht für Spark?

Gzip ist als ganze Datei nicht teilbar. Ein einziger Task muss die Datei lesen, das bremst die Parallelität.

Ist Iceberg ein Dateiformat?

Nein, ein Tabellenformat. Es verwaltet Metadaten, Snapshots und Dateilisten. Die Daten liegen in Parquet, Avro oder ORC.

Arrow vs Parquet?

Arrow ist ein spaltenweises Format im Speicher für schnelle Verarbeitung und Übertragung. Parquet ist ein spaltenweises Format auf der Platte.

Was macht spark.sql.parquet.mergeSchema?

Bei true vereint Spark die Schemas aller Dateien. Standard ist false, weil das Lesen aller Footer teuer ist.

Wie sehen Sie, ob Pushdown greift?

Mit explain(): PushedFilters und ReadSchema im Scan. Dazu Input Size in der Spark UI.

Szenario: Eine Abfrage auf einer breiten CSV-Tabelle dauert Minuten. Was tun Sie?

Die Daten einmal in Parquet in einer Iceberg-Tabelle speichern. Dann liest die Abfrage nur die nötigen Spalten und überspringt Blöcke.

Szenario: Nach dem Export aus Spark zeigt ein anderes Tool falsche Zeitstempel. Ursache?

Wahrscheinlich INT96 oder Zeitzonen. Ich setze outputTimestampType bewusst und teste die Zeitzone in beiden Engines.

Szenario: Ein Partner will Daten per Kafka liefern. Welches Format schlagen Sie vor?

Avro mit Schema und klaren Regeln für Schema Evolution. Im Lakehouse wandle ich es dann in Parquet-Tabellen um.
