Tests, Sources, Lineage

Kern: Ein dbt-Test ist eine SQL-Abfrage, die fehlerhafte Zeilen liefert, und er besteht bei null Zeilen. Sources beschreiben die Rohtabellen und prüfen ihre Freshness. Über ref() und source() kennt dbt die Lineage, also wer von wem abhängt.

Antwort-Muster

Frage: Wie testet man Daten in dbt, und wozu dienen Sources?

  1. Mechanismus: Ein Test ist eine Abfrage auf fehlerhafte Zeilen. Null Zeilen heisst bestanden. Generic Tests stehen in YAML, Singular Tests als SQL-Datei.
  2. Zahl: dbt liefert vier Generic Tests mit: unique, not_null, accepted_values und relationships. Die Standard-Severity ist error, die Schwellen error_if und warn_if sind !=0.
  3. Trade-off: Strenge Tests schützen Downstream-Models, blockieren sie aber bei Fehlern. Mit warn oder Schwellen steuert man das.
  4. Produktion: Ich teste Sources und Keys früh und prüfe die Freshness. In CI nutze ich dbt build, damit Fehler Nachfolger stoppen.

1. Ein Testlauf mit dbt build in 8 Schritten

  1. Source prüfen: Man prüft die Freshness der Rohdaten und startet Tests auf Sources, zum Beispiel mit dbt test --select "source:*".
  2. Model bauen: dbt build arbeitet in DAG-Reihenfolge. Es baut Models, führt Tests aus, macht Snapshots und lädt Seeds.
  3. Unit Test: Er läuft auf dem Model mit festen Eingaben, bevor das Model materialisiert wird. Man nutzt sie in Entwicklung und CI.
  4. Data Test: Nach dem Bauen läuft die Abfrage auf den echten Daten. Sie liefert die fehlerhaften Zeilen.
  5. Zeilen zählen: dbt zählt die Fehlerzeilen. Bei null besteht der Test. Mit --store-failures speichert dbt sie in eine Tabelle.
  6. Severity: Bei severity: error prüft dbt zuerst error_if, dann warn_if. Beide stehen standardmässig auf !=0.
  7. Nachfolger: Ein fehlgeschlagener Test auf einem Vorgänger blockiert die Nachfolger. Sie werden SKIP.
  8. Ergebnis: dbt zeigt pass, warn oder error. Die Resultate liegen im target-Ordner.

dbt test führt nur Tests aus. dbt build kombiniert Bauen und Testen in DAG-Reihenfolge.

2. Aufbau

  1. Eine Source ist die Beschreibung einer Rohtabelle in YAML. Sie hat Datenbank, Schema und Tabellen.
  2. source() und ref() erzeugen Abhängigkeiten. Aus ihnen entsteht der DAG, also die Lineage.
  3. Ein Generic Test steht in YAML bei einer Spalte. Er ist wiederverwendbar.
  4. Ein Singular Test ist eine SQL-Datei in tests/, die fehlerhafte Zeilen liefert.
  5. Ein Unit Test steht in YAML im Ordner models/ und nutzt given und expect.
  6. Freshness prüft, wie alt die neueste Zeile einer Source ist. Dafür gibt es loaded_at_field.

3. Details

  1. Wie ein Test funktioniert: Ein Data Test liefert eine Menge fehlerhafter Zeilen. Bei null Zeilen besteht er. Man kann mit dbt test alle ausführen.
  2. Vier Generic Tests: unique, not_null, accepted_values und relationships. Mehr gibt es in Paketen oder man schreibt eigene.
  3. Singular Test: Eine einzelne SQL-Datei, die genau die fehlerhaften Zeilen zurückgibt. Sie gilt für einen einzigen Zweck.
  4. Schlüsselwort data_tests: Früher hiess es tests. Seit es Unit Tests gibt, heisst der Key data_tests. tests: geht als Alias weiter. Beides am selben Objekt geht nicht.
  5. Severity: severity ist error oder warn, Standard error. Bei error prüft dbt zuerst error_if, dann warn_if. Bei warn prüft es nur warn_if.
  6. Schwellen: error_if und warn_if sind Ausdrücke wie > 5 oder between 5 and 10. Standard ist !=0. So darf ein Test mit wenigen Fehlern nur warnen.
  7. store_failures: Mit --store-failures speichert dbt die Fehlerzeilen in eine Tabelle, standardmässig im Schema mit dbt_test__audit. Ein neuer Lauf ersetzt die alten Fehler des Tests.
  8. Test-Fehler blockieren: Bei dbt build blockiert ein fehlgeschlagener Test die Nachfolger. Sie werden übersprungen. Mit warn oder höherer Schwelle verhindert man das.
  9. Unit Tests: Sie gibt es seit dbt 1.8. Sie prüfen SQL-Logik mit festen Eingaben (given) und erwarteter Ausgabe (expect). Sie laufen vor dem Materialisieren und nur für SQL-Models im aktuellen Projekt.
  10. Wann Unit Test, wann Data Test: Data Tests prüfen die echten Daten nach dem Bauen. Unit Tests prüfen die Logik. Man nutzt Unit Tests für komplexe Logik und Randfälle und führt sie in Entwicklung und CI aus.
  11. Sources: Man deklariert sie in YAML unter sources:. schema ist standardmässig gleich dem name. Mit {{ source('shop', 'orders') }} liest ein Model daraus.
  12. Source-Tests und Selektion: Man kann auf Sources Tests und Beschreibungen setzen. Mit dbt test --select source:shop testet man eine Source, mit dbt run --select source:shop+ baut man alle Nachfolger.
  13. Freshness: warn_after und error_after mit Anzahl und Periode. Ohne beide rechnet dbt keine Freshness. loaded_at_field ist nötig, ausser dbt nutzt Warehouse-Metadaten. Die Werte gelten hierarchisch von Source zu Tabelle.
  14. Freshness-Befehl: In dbt 1.x heisst der Befehl dbt source freshness. In dbt v2 ist es dbt freshness. Die Ergebnisse stehen in target/freshness.json. Ein filter begrenzt den Scan bei teuren Tabellen.
  15. Lineage: ref() und source() sagen dbt, wovon ein Model abhängt. Daraus entsteht der DAG. Mit + in --select nimmt man Vorgänger oder Nachfolger dazu.

4. Fallen

  • „Ein Test besteht, wenn er Zeilen liefert.“ → Falsch. Er besteht bei null Zeilen. Zeilen sind die Fehler.
  • „dbt run führt auch die Tests aus.“ → Falsch. Nein. dbt run baut nur. dbt test testet, dbt build macht beides.
  • „Ein Unit Test prüft die echten Produktionsdaten.“ → Falsch. Er prüft die Logik mit festen Eingaben, vor dem Materialisieren.
  • „Freshness läuft automatisch bei jedem dbt run.“ → Falsch. Man startet sie mit eigenem Befehl und braucht warn_after oder error_after.
  • „Ein fehlgeschlagener Test hat keine Folgen für andere Models.“ → Falsch. Bei dbt build werden Nachfolger übersprungen, ausser die Severity ist warn.
  • „unique prüft auch Zeilen mit NULL.“ → Falsch. unique prüft Duplikate. NULL prüft man mit not_null.

5. Selbsttest

Warum?

Warum liefern dbt-Tests Fehlerzeilen statt eines Ja oder Nein?

So sieht man die Fehler selbst. Man kann sie speichern und analysieren. Null Zeilen heisst bestanden.

Warum prüft man Sources?

Fehler in Rohdaten gehen sonst durch alle Models. Je früher man sie findet, desto billiger ist die Korrektur.

Warum Freshness?

Ein Job kann leise stehen bleiben. Freshness zeigt, dass die neueste Zeile zu alt ist.

Wie innen?

Wie führt dbt einen unique-Test aus?

Es kompiliert eine Abfrage, die Duplikate liefert. Gibt sie Zeilen zurück, schlägt der Test fehl.

Wie wertet dbt error_if und warn_if aus?

Bei severity: error zuerst error_if. Trifft sie nicht zu, prüft dbt warn_if. Bei warn nur warn_if.

Wie rechnet dbt die Freshness?

Mit einer Abfrage auf max(loaded_at_field) und der aktuellen Zeit. Das Alter wird mit warn_after und error_after verglichen.

Was macht --store-failures?

dbt speichert die Fehlerzeilen in eine Tabelle und rechnet die Fehlerzahl daraus. Ein neuer Lauf ersetzt die alten Zeilen.

Wie entsteht die Lineage?

Aus ref() und source() in den Models. Sie machen die Abhängigkeiten sichtbar und bestimmen die Reihenfolge.

Was läuft bei dbt build in welcher Reihenfolge?

In DAG-Reihenfolge: Models, Tests, Snapshots, Seeds. Unit Tests laufen vor dem Materialisieren, Data Tests danach.

Zahlen

Wie viele Generic Tests bringt dbt mit?

Vier.

Welche Standard-Severity gilt?

error. error_if und warn_if sind standardmässig !=0.

Ab welcher Version gibt es Unit Tests?

Ab dbt 1.8.

Vergleich

Generic vs Singular Test?

Generic ist wiederverwendbar und steht in YAML. Singular ist eine einmalige SQL-Datei.

Data Test vs Unit Test?

Data Test prüft echte Daten nach dem Bauen. Unit Test prüft Logik mit festen Eingaben vor dem Materialisieren.

dbt test vs dbt build?

test führt nur Tests aus. build baut und testet in DAG-Reihenfolge und blockiert Nachfolger bei Fehlern.

Produktion

Ein unique-Test schlägt in Produktion fehl. Was tun Sie?

Mit --store-failures die Duplikate speichern, Ursache in Quelle oder Join suchen und beheben. Nachfolger bleiben bis dahin blockiert.

Ein Test ist oft rot wegen weniger Ausreisser. Was tun Sie?

warn_if und error_if mit Schwelle setzen. So warnt er bei wenigen Fehlern und blockiert nur bei vielen.

Die Freshness meldet stale, aber der Job lief. Was prüfen Sie?

loaded_at_field und Zeitzone. Vielleicht zeigt die Spalte nicht den Ladezeitpunkt.

Szenario: Eine Source liefert seit gestern keine neuen Zeilen. Wie merken Sie das?

Mit warn_after und error_after und dem Freshness-Befehl im Scheduler. Der Alarm kommt, bevor Dashboards leer sind.

Szenario: Ein Test auf einer Zwischenstufe blockiert 20 Nachfolger. Was tun Sie?

Ich prüfe, ob der Test kritisch ist. Wenn nicht, stelle ich ihn auf warn oder eine Schwelle. Wenn ja, ist das Blockieren das gewollte Verhalten.

Design

Welche Tests setzt man auf jedes Model?

unique und not_null auf den Schlüssel, relationships auf Fremdschlüssel, accepted_values bei festen Listen.

Wann schreibt man einen Unit Test?

Bei komplexer Logik, bekannten Bugs und Randfällen. Nicht für einfache Funktionen, die das Warehouse schon testet.

Wo laufen Unit Tests?

In Entwicklung und CI. Die Eingaben sind fest, darum braucht man sie in Produktion nicht.

Szenario: Ein neues Team hat keine Tests. Wo fangen Sie an?

Bei den Sources und den Schlüsseln der Marts. Dann Freshness für die wichtigsten Sources und Unit Tests für die komplexeste Logik.

Mehr

Gerüst

  • Warum? Datenfehler früh und automatisch finden und Nachfolger davor schützen.
  • Wie innen? Test = Abfrage auf Fehlerzeilen. Source + ref() ergeben die Lineage. Freshness aus max(loaded_at_field).
  • Zahlen 4 Generic Tests, Standard-Severity error, Schwellen !=0, Unit Tests ab 1.8.
  • Vergleich Generic vs Singular, Data vs Unit, test vs build.
  • Produktion Test blockiert Nachfolger, Source bleibt stehen, Duplikate analysieren.
  • Design Tests auf Keys und Sources zuerst, Unit Tests für Logik, Schwellen mit Verstand.

Beispiel: Tests und Source mit Freshness

# models/schema.yml  (dbt)
sources:
  - name: shop
    config:
      loaded_at_field: _etl_loaded_at
      freshness:
        warn_after: {count: 12, period: hour}
        error_after: {count: 24, period: hour}
    tables:
      - name: orders

models:
  - name: orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: customer_id
        data_tests:
          - relationships: {to: ref('customers'), field: customer_id}
      - name: status
        data_tests:
          - accepted_values: {values: [paid, shipped, refunded]}

-- tests/assert_amount_not_negative.sql  (singular)
select order_id, amount from {{ ref('orders') }} where amount < 0

-- Die SQL-Logik dieser Tests, vereinfacht, auf Testdaten in sqlite:
--   unique:          select order_id, count(*) from orders group by 1 having count(*) > 1
--   not_null:        select * from orders where customer_id is null
--   accepted_values: select status from orders where status not in ('paid','shipped','refunded')
--   relationships:   select customer_id from orders where customer_id not in (select customer_id from customers)
FAIL unique(order_id): 1 Zeile(n) [(2, 2)]
FAIL not_null(customer_id): 1 Zeile(n) [(3, None, 'shipped', 5.0)]
FAIL accepted_values(status): 1 Zeile(n) [('lost',)]
FAIL relationships(customer_id): 1 Zeile(n) [(9,)]
FAIL singular: amount < 0: 1 Zeile(n) [(4, -3.0)]

Echte Ausgabe, Python 3.12.10 mit sqlite3. Nur die SQL-Logik der Tests auf Testdaten, kein dbt. Das YAML oben ist nicht ausgeführt.

  1. Die Source shop.orders hat Freshness: Warnung nach 12 Stunden, Fehler nach 24 Stunden.
  2. unique und not_null stehen bei order_id. relationships prüft den Fremdschlüssel.
  3. accepted_values prüft die Liste der Status. Der Wert lost ist nicht erlaubt.
  4. Der Singular Test liefert alle Bestellungen mit negativem Betrag.
  5. Die Ausgabe zeigt: Jeder Test liefert genau eine Fehlerzeile. Darum ist jeder rot.
  6. In dbt würde dbt build die Nachfolger dieser Models überspringen.

Vergleich

  • Generic Test: wiederverwendbar, YAML, vier eingebaut.
  • Singular Test: SQL-Datei in tests/, für einen Zweck.
  • Unit Test: feste Eingaben, vor dem Materialisieren, nur SQL-Models.
  • Source-Test: gleiche Tests, aber auf Rohdaten.
  • dbt test: nur Tests. dbt build: Bauen und Testen in DAG-Reihenfolge.
  • warn vs error: warn zeigt nur an, error blockiert Nachfolger.

Produktion

  1. Test rot, Nachfolger übersprungen: Lösung: Ursache beheben oder Severity bewusst auf warn setzen.
  2. Rauschen durch Ausreisser: Lösung: Schwellen mit error_if und warn_if.
  3. Freshness fehlt: Kein loaded_at_field oder keine Schwellen. Lösung: konfigurieren, sonst rechnet dbt nichts.
  4. Teure Freshness-Abfrage: Lösung: filter setzen.
  5. Tests dauern lange: viele Tests auf grossen Tabellen. Lösung: where oder Stichprobe, wichtigste Tests zuerst.
  6. Fehler nicht analysierbar: Lösung: --store-failures nutzen.

Diagnose: Werkzeuge und Befehle

  • dbt test --select model und dbt build --select model+: gezielt testen.
  • dbt test --select "source:*": alle Source-Tests.
  • dbt source freshness (dbt 1.x) oder dbt freshness (v2): Freshness prüfen.
  • --store-failures: Fehlerzeilen in einer Tabelle ansehen.
  • target/freshness.json und die Test-Ausgabe: Alter und Fehlerzahl.

Senior-Punkte

  1. Tests sind ein Vertrag mit den Nutzern. Schlüssel und Sources zuerst.
  2. Blockieren ist eine Entscheidung. error stoppt Nachfolger, warn nicht.
  3. Freshness findet stille Fehler. Sie ist oft wichtiger als ein weiterer Test.
  4. Unit Tests sichern Logik, Data Tests sichern Daten. Beides hat seinen Platz.
  5. Zu viele Tests erzeugen Lärm. Ich teste, was Entscheidungen beeinflusst.
  6. Lineage hilft beim Auswirkungs-Check. Vor einer Änderung sehe ich alle Nachfolger.
