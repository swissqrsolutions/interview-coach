Enterprise Integration Patterns und Camel Routes

Kern: Apache Camel ist ein Integrations-Framework, das die Enterprise Integration Patterns (EIP) als Bausteine in Java, XML oder YAML anbietet. Eine Route verbindet einen Consumer (from) über Schritte mit einem Producer (to). Jede Nachricht reist als Exchange durch diese Schritte.

Antwort-Muster

Frage: Was ist eine Camel Route und wie läuft eine Nachricht durch?

  1. Mechanismus: Ein Consumer in from() erzeugt pro Nachricht einen Exchange. Dieser läuft durch die Schritte und endet in einem Producer.
  2. Zahl: Ein Splitter läuft standardmässig seriell, ein Aggregator hält Daten standardmässig im Speicher. Camel 4 braucht mindestens Java 17.
  3. Trade-off: Fertige Patterns sparen Code. Dafür sind Fehlerbehandlung und Zustand (Aggregator) das eigentliche Risiko.
  4. Produktion: Ich setze Dead Letter Channel, Idempotent Consumer und einen persistenten Aggregator ein.

1. Eine Nachricht in 7 Schritten

  1. from(): Der Consumer liest eine Quelle, zum Beispiel eine Datei oder eine Queue. Pro Nachricht entsteht ein Exchange.
  2. Pipeline: Die Schritte der Route laufen nacheinander. Jeder Schritt arbeitet auf dem Exchange des Vorgängers.
  3. Router und Filter: Ein choice() wählt einen Zweig. Das erste when, das passt, entscheidet. Ohne Treffer läuft otherwise, falls vorhanden.
  4. Split und Aggregate: Ein Splitter teilt eine Nachricht in Teile. Ein Aggregator führt Teile mit gleichem Schlüssel zusammen.
  5. to(): Der Producer sendet die Nachricht an das Ziel. Das kann eine Queue, ein HTTP-Dienst oder eine Datei sein.
  6. Fehler: Wirft ein Schritt eine Exception, übernimmt der Error Handler. Er kann es erneut versuchen oder an einen Dead Letter Endpoint senden.
  7. Fertig: Ist der Exchange fertig, bestätigt der Consumer die Quelle. Bei Dateien wird sie verschoben, bei Queues quittiert.

2. Aufbau

  1. Der CamelContext ist die Laufzeit. Er hält Routen, Komponenten und Konverter.
  2. Eine Route ist eine Kette von Schritten. Sie beginnt mit genau einem from.
  3. Eine Component ist ein Anschluss wie kafka, file oder jms. Sie erzeugt Endpoints.
  4. Ein Endpoint wird durch eine URI beschrieben, etwa file:in?noop=true. Er erzeugt Consumer und Producer.
  5. Ein Exchange ist eine Anfrage mit Antwort oder Fehler. Bei einem Event gibt es nur die eingehende Nachricht.
  6. Die Message trägt Body und Headers. Variablen gibt es seit Camel 4.4.

3. Details

  1. EIP als Bausteine: Camel bietet die Patterns aus dem Katalog von Hohpe und Woolf als DSL-Schritte. Die Doku gruppiert sie in Messaging Systems, Channels, Construction, Routing, Transformation, Endpoints und weitere. Man baut Integration aus bekannten Namen.
  2. Content-Based Router: choice().when(...).otherwise() entscheidet nach dem Inhalt. Das erste passende when gewinnt. Bei Splitter oder Load Balancer im Zweig braucht man endChoice(), nicht end().
  3. Headers, Properties, Variablen: Headers reisen mit der Nachricht. Properties gehören zum Exchange und Camel nutzt sie auch intern. Variablen gibt es seit 4.4 nur für Anwender, mit Scope Exchange, Route, Group oder Global.
  4. Splitter: Er läuft standardmässig seriell und ohne Streaming. Alle Teile entstehen vor der Verarbeitung. Für grosse Dateien nimmt man streaming() und tokenize.
  5. Splitter und Fehler: Ein fehlerhaftes Teil stoppt die anderen standardmässig nicht. stopOnException bricht ab. CamelSplitIndex ist der nullbasierte Zähler. Ohne AggregationStrategy bleibt die Original-Nachricht das Ergebnis.
  6. Aggregator: Er braucht eine Correlation Expression und eine AggregationStrategy. Dazu kommt eine Completion-Bedingung, etwa completionSize oder completionTimeout. Die erste Bedingung, die zutrifft, schliesst die Gruppe.
  7. Aggregator-Zustand: Das Repository ist standardmässig im Speicher (MemoryAggregationRepository). Persistent geht es zum Beispiel mit SQL, Redis oder Infinispan. forceCompletionOnStop ist standardmässig aus.
  8. Error Handler: Der Standard ist DefaultErrorHandler. Er hat keine Dead Letter Queue. Ist er erschöpft, geht die Exception zurück an den Aufrufer.
  9. Dead Letter Channel: Er versucht es erneut und sendet danach an einen Dead Letter Endpoint. Laut Doku sind es bis zu 6 Redeliveries mit 1 Sekunde Pause. maximumRedeliveries(-1) wiederholt endlos.
  10. onException: Es wählt nach Exception-Typ den nächsten passenden Treffer. handled(true) markiert den Fehler als behandelt. Eine aufgerufene Route nutzt ihren eigenen Error Handler.
  11. Idempotent Consumer: Er überspringt Duplikate anhand eines Schlüssels. eager ist standardmässig an, removeOnFailure auch. Das Memory-Repository im Beispiel vergisst alles beim Neustart.
  12. Wire Tap: Er sendet eine Kopie des Exchange fire-and-forget in einem eigenen Thread. Die Kopie ist flach, Objekte werden geteilt. Ist der Pool voll, läuft der Tap synchron.
  13. Camel 4: Es braucht mindestens Java 17. Der Weg von Camel 3 führt über 3.20. Einige Komponenten wie camel-rabbitmq und camel-vm wurden entfernt.

4. Fallen

  • „Ein Aggregator ist sicher, er speichert doch alles.“ → Falsch. Das Repository ist standardmässig im Speicher. Beim Neustart gehen offene Gruppen verloren.
  • „Der Splitter stoppt bei einem Fehler.“ → Falsch. Standardmässig laufen die anderen Teile weiter. Man braucht stopOnException.
  • „Der Splitter läuft parallel.“ → Falsch. parallelProcessing ist standardmässig aus.
  • „Der Default Error Handler schickt in eine Dead Letter Queue.“ → Falsch. Das kann nur der Dead Letter Channel.
  • „Idempotent Consumer überlebt jeden Neustart.“ → Falsch. Das Memory-Repository hält nur die letzten IDs im Speicher. Für Neustarts braucht man ein persistentes Repository.
  • „Wire Tap blockiert die Route.“ → Falsch. Er läuft in einem eigenen Thread. Nur bei vollem Pool läuft er synchron.

5. Selbsttest

Warum?

Warum Camel und nicht eigener Code?

Camel liefert fertige Patterns und viele Komponenten. Man schreibt weniger Klebecode für Protokolle, Retries und Routing. Dafür lernt man die Camel-Begriffe.

Warum nutzt man Enterprise Integration Patterns?

Sie geben bekannten Problemen feste Namen und Lösungen. Teams reden dieselbe Sprache. Camel bildet sie direkt als DSL ab.

Warum braucht ein Aggregator eine Completion-Bedingung?

Er weiss sonst nicht, wann eine Gruppe fertig ist. Ohne Bedingung bliebe sie ewig im Repository.

Wie innen?

Was ist ein Exchange?

Er ist der Container einer Nachricht in der Route. Er enthält die Message, Properties und eine mögliche Exception. Bei Request-Reply gibt es auch eine Antwort.

Was ist der Unterschied zwischen Endpoint und Component?

Die Component ist der Anschluss, zum Beispiel kafka. Der Endpoint ist eine konkrete Konfiguration aus einer URI. Er erzeugt Consumer und Producer.

Wie arbeitet choice()?

Es prüft die when-Bedingungen der Reihe nach. Das erste Treffer-when bestimmt den Zweig. Ohne Treffer läuft otherwise, sonst kein Zweig.

Wie funktioniert der Splitter?

Ein Ausdruck teilt die Nachricht in Teile. Jedes Teil läuft als eigener Exchange durch den Unterzweig. Eine AggregationStrategy fügt die Ergebnisse optional zusammen.

Wie funktioniert der Aggregator?

Eine Correlation Expression berechnet den Schlüssel. Die AggregationStrategy fügt jede neue Nachricht in den Aggregat-Exchange ein. Trifft eine Completion-Bedingung zu, geht der Aggregat weiter.

Wie arbeitet der Idempotent Consumer?

Ein Ausdruck liefert den Schlüssel. Ist er im Repository, wird die Nachricht übersprungen. Sonst wird der Schlüssel eingetragen und die Nachricht läuft weiter.

Was macht ein Wire Tap?

Er kopiert den Exchange und sendet die Kopie fire-and-forget in einem eigenen Thread. Gut für Audit-Logs, ohne die Route zu bremsen.

Was sind Variablen in Camel?

Schlüssel-Wert-Paare seit Camel 4.4 mit Scope Exchange, Route, Group oder Global. Sie sind für Anwender gedacht, damit sie nicht mit internen Properties kollidieren.

Zahlen

Welche Java-Version braucht Camel 4?

Mindestens Java 17. Java 11 fällt weg.

Welche Standardwerte hat der Splitter?

parallelProcessing, stopOnException, streaming und shareUnitOfWork sind aus. Das Timeout ist 0. Das Trennzeichen ist das Komma.

Welche Standardwerte hat der Aggregator?

forceCompletionOnStop und completeAllOnStop sind aus. discardOnCompletionTimeout ist aus. Der Timeout-Checker läuft alle 1000 ms. Bei parallelProcessing hat der Pool 10 Threads.

Wie oft versucht der Dead Letter Channel es erneut?

Laut Doku bis zu 6 Mal mit 1 Sekunde Pause. Mit maximumRedeliveries -1 endlos.

Was sind die Standardwerte beim Idempotent Consumer?

eager, skipDuplicate und removeOnFailure sind alle an. completionEager ist aus.

Vergleich

Camel gegen Spring Integration?

Beide setzen EIP um. Camel hat sehr viele Komponenten und eine eigene DSL mit URIs. Spring Integration ist enger an Spring und nutzt Kanäle und Adapter.

Camel gegen einen ESB?

Camel ist eine Bibliothek in der eigenen Anwendung. Ein ESB ist ein eigener zentraler Server. Camel läuft in Spring Boot, Quarkus oder Karaf.

Splitter gegen Multicast?

Der Splitter teilt eine Nachricht in Teile. Multicast sendet die gleiche Nachricht an mehrere Ziele.

Dead Letter Channel gegen onException?

Der Dead Letter Channel ist ein Error Handler mit Ziel nach den Retries. onException regelt pro Exception-Typ, ob Retry, handled oder weiter.

enrich gegen pollEnrich?

Beide holen Zusatzdaten für eine Nachricht. Enrich nutzt einen Producer, pollEnrich einen Polling Consumer. Beide sind in der EIP-Liste von Camel aufgeführt.

Produktion

Was passiert mit Aggregaten beim Neustart?

Mit dem Standard-Repository im Speicher gehen sie verloren. Ein persistentes Repository und forceCompletionOnStop helfen.

Wie vermeidet man Doppelverarbeitung bei Retries?

Mit einem Idempotent Consumer und einem persistenten Repository. Der Schlüssel kommt aus einer Fach-ID.

Szenario: Eine 2-GB-Datei lässt die Anwendung mit OutOfMemory abstürzen. Warum?

Der Splitter ohne streaming erzeugt alle Teile vor der Verarbeitung. Lösung: streaming() mit tokenize und group.

Szenario: Nach einem Fehler kommt dieselbe Nachricht zehnmal im Zielsystem an. Was prüfen Sie?

Die Redelivery-Einstellungen und ob der Fehler nach dem Senden auftritt. Ich setze einen Idempotent Consumer im Ziel und begrenze die Wiederholungen.

Szenario: Der Aggregator schliesst nie und der Speicher wächst. Was tun Sie?

Ich prüfe die Completion-Bedingungen. Oft fehlt completionTimeout oder der Schlüssel ist nie gleich. Dann setze ich ein Timeout und logge Schlüssel.

Design

Wie entwerfen Sie eine robuste Route?

Idempotenter Consumer am Eingang, Error Handler mit Dead Letter Channel, klare Timeouts und ein Wire Tap für Audit. Zustand wie Aggregate kommt in ein persistentes Repository.

Szenario: Aufträge kommen aus Kafka, jeder besteht aus 3 Teilnachrichten, die zusammen weiterlaufen sollen. Wie bauen Sie das?

Aggregator mit der Auftrags-ID als Correlation Expression und completionSize 3. Dazu completionTimeout für fehlende Teile und ein persistentes Repository.

Wann nutzt man Variablen statt Headers?

Wenn die Daten nur intern in der Route gebraucht werden. Headers reisen mit zum Ziel, Variablen nicht.

Wann wählen Sie Camel nicht?

Bei einer einzigen simplen Schnittstelle genügt ein Client. Bei sehr hohem Durchsatz mit Zustand nehme ich eher Kafka Streams oder Flink.

Mehr

Gerüst

  • Warum? Fertige Integrations-Patterns und viele Komponenten statt Klebecode.
  • Wie innen? Route = from, Schritte, to. Ein Exchange mit Message wandert durch die Pipeline.
  • Zahlen Camel 4 braucht Java 17. Variablen seit 4.4. DLC: laut Doku bis 6 Redeliveries, 1 s Pause.
  • Vergleich Spring Integration: Kanäle. ESB: zentraler Server. Camel: Bibliothek.
  • Produktion Aggregate im Speicher gehen verloren, Retries erzeugen Duplikate, OOM ohne streaming.
  • Design Idempotent Consumer, Dead Letter Channel, persistenter Aggregator, Mock-Tests.

Beispiel: Route mit Router, Splitter und Fehlerbehandlung

public class OrderRoutes extends RouteBuilder {
  @Override public void configure() {
    errorHandler(deadLetterChannel("jms:queue:dead")
        .maximumRedeliveries(3).redeliveryDelay(1000));

    from("file:in?noop=true")
      .idempotentConsumer(header("CamelFileName"),
          new MemoryIdempotentRepository())
      .split(body().tokenize("\n")).streaming()
        .choice()
          .when(simple("${body} contains 'EXPRESS'"))
            .to("jms:queue:express")
          .otherwise()
            .to("jms:queue:normal")
        .end()
      .end()
      .wireTap("direct:audit");
  }
}

Nicht ausgeführt.

  1. Der Dead Letter Channel versucht es dreimal mit 1 Sekunde Pause. Dann geht der Exchange nach jms:queue:dead.
  2. Der Idempotent Consumer überspringt Dateien mit gleichem Namen. Das Memory-Repository vergisst beim Neustart.
  3. streaming() erzeugt die Zeilen nach Bedarf. So bleibt der Speicher klein.
  4. choice() schickt jede Zeile in genau eine Queue.
  5. Das erste end() schliesst den Choice, das zweite den Splitter.
  6. Der Wire Tap sendet eine Kopie an direct:audit, ohne zu warten.

Vergleich

  • Camel: Bibliothek mit EIP-DSL und vielen Komponenten. Läuft in Spring Boot, Quarkus oder Karaf.
  • Spring Integration: EIP mit Kanälen und Adaptern, eng an Spring.
  • ESB: zentraler Server mit eigenem Betrieb. Camel lässt sich in einen ESB einbauen.
  • Kafka Streams: Stream-Verarbeitung mit Zustand. Kein EIP-Katalog für beliebige Protokolle.
  • Direkter Client: einfach für eine einzige Schnittstelle. Keine Patterns, kein Retry.
  • Kamelets und Camel K: wiederverwendbare Route-Bausteine für Kubernetes-Umgebungen.

Produktion

  1. Verlorene Aggregate: Memory-Repository und Neustart. Lösung: persistentes Repository, forceCompletionOnStop.
  2. Duplikate nach Retry: Der Fehler kommt nach dem Senden. Lösung: Idempotenz im Ziel und im Consumer.
  3. OutOfMemory beim Splitten: Alle Teile entstehen vorab. Lösung: streaming() und group.
  4. Endlos-Retry: maximumRedeliveries(-1) blockiert den Consumer. Lösung: Obergrenze und Dead Letter Channel.
  5. Wire Tap bremst: Der Pool ist voll und der Tap läuft synchron. Lösung: eigener executorService.
  6. Alte Camel-Version: Komponenten sind entfernt oder ohne Support. Lösung: auf eine aktuelle LTS-Version von Camel 4 migrieren.

Diagnose: Werkzeuge und Befehle

  • Route-Logging: .log("${body}") und der Message History EIP zeigen den Weg.
  • Camel JMX oder Actuator-Endpunkte: zeigen Zähler pro Route.
  • Mock-Endpoints in Tests: prüfen Anzahl und Inhalt der Nachrichten.
  • Dead Letter Queue: Inhalt ansehen, der Exchange trägt die Fehlerinfo.

Senior-Punkte

  1. Fehlerbehandlung ist der Kern. Der Happy Path ist drei Zeilen, der Rest ist Retry, Dead Letter und Idempotenz.
  2. Zustand ist teuer. Aggregator und Idempotent Repository brauchen einen persistenten Speicher.
  3. At-least-once gilt fast immer. Darum müssen Ziele Duplikate vertragen.
  4. Patterns nicht stapeln. Eine Route mit zehn verschachtelten EIP ist schwer zu testen. Lieber mehrere Routen mit direct:.
  5. Camel ist Kleber, keine Geschäftslogik. Die Fachlogik gehört in Beans.
  6. Version bewusst wählen. Camel 4 LTS wählen, nicht Camel 3.
