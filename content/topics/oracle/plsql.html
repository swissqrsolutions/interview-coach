PL/SQL: Prozeduren, Packages, Cursors

Kern: PL/SQL ist die prozedurale Sprache in der Oracle-Datenbank. Code liegt als Procedures, Functions und Packages kompiliert in der Datenbank, und Cursors holen Zeilen aus SQL ins PL/SQL. Schnell ist es nur, wenn man Mengen statt einzelner Zeilen bearbeitet.

Antwort-Muster

Frage: Was ist ein Package, und warum nutzt man es?

  1. Mechanismus: Ein Package ist ein Schema-Objekt aus Spec (öffentlich) und Body (Implementierung) und kann Zustand pro Session halten.
  2. Zahl: Mit BULK COLLECT ... LIMIT 500 und FORALL sinkt die Zahl der Wechsel zwischen PL/SQL und SQL stark.
  3. Trade-off: Packages bringen Kapselung und Wiederverwendung, aber Zustand pro Session und Abhängigkeiten machen Änderungen heikel.
  4. Produktion: Ich fange Exceptions gezielt, verschlucke keine mit WHEN OTHERS und lasse den Aufrufer committen.

1. Ein Package-Aufruf in 7 Schritten

  1. Aufruf: Ein Client oder anderer Code ruft emp_pkg.raise_salary(50, 5) auf.
  2. Package laden: Beim ersten Zugriff in der Session läuft der Init-Block am Ende des Body. Er setzt den Zustand, hier g_calls.
  3. Parameter binden: IN ist lesend und der Standard. OUT gibt einen Wert zurück. IN OUT macht beides.
  4. PL/SQL-Engine: Sie führt Schleifen, Bedingungen und Zuweisungen aus. SQL-Anweisungen gibt sie weiter.
  5. SQL-Anweisung: Jede SQL-Anweisung ist ein Wechsel zwischen den beiden Engines (Context Switch). Bulk SQL spart diese Wechsel.
  6. Exception: Tritt ein Fehler auf, sucht PL/SQL im Block den passenden Handler. Sonst geht der Fehler an den äusseren Block und zuletzt an den Aufrufer.
  7. Rückgabe: Die Prozedur gibt die Kontrolle zurück. Der Aufrufer entscheidet über COMMIT oder ROLLBACK.

2. Aufbau

  1. Ein Block hat die Teile DECLARE, BEGIN, EXCEPTION und END. Nur BEGIN und END sind Pflicht.
  2. Eine Procedure führt eine Aktion aus. Eine Function berechnet einen Wert.
  3. Ein Package bündelt Typen, Variablen, Konstanten, Subprogramme, Cursors und Exceptions.
  4. Die Spec ist die öffentliche Schnittstelle. Der Body enthält den Code und private Teile.
  5. Ein Cursor zeigt auf einen privaten SQL-Bereich mit dem Ergebnis einer Abfrage.
  6. Bulk SQL holt oder schreibt viele Zeilen in einem Schritt.

3. Details

  1. Block: DECLARE und EXCEPTION sind optional. Variablen können ihren Typ mit %TYPE von einer Spalte übernehmen. Das hält den Code stabil bei Schemaänderungen.
  2. Procedure und Function: Man nutzt eine Procedure für eine Aktion und eine Function für einen Wert. Eine Function hat RETURN und lässt sich in SQL nutzen.
  3. Parameter-Modi: IN ist der Standard. NOCOPY ist nur ein Hinweis, dass Oracle per Referenz übergeben soll. Bei einem Fehler können dann halbe Änderungen sichtbar bleiben.
  4. Package: Es ist ein Schema-Objekt. Es wird kompiliert und in der Datenbank gespeichert, und viele Anwendungen teilen es. Nur die Spec ist von aussen sichtbar. Private Teile im Body sind versteckt.
  5. Package-Zustand: Variablen, Konstanten und Cursors des Package bilden den Zustand. Er gilt pro Session und bleibt über Transaktionen erhalten. Ein Init-Block am Ende des Body läuft einmal pro Session. Bei SERIALLY_REUSABLE gilt der Zustand nur für einen Server Call.
  6. Abhängigkeiten: Ändert man nur den Body, bleiben abhängige Objekte meist gültig. Ändert man die Spec, werden sie ungültig und müssen neu kompiliert werden. Darum hält man Specs klein und stabil.
  7. AUTHID: Mit DEFINER (Standard) läuft Code mit den Rechten des Besitzers. Mit CURRENT_USER läuft er mit den Rechten des Aufrufers.
  8. Implizite Cursors: Oracle legt für jedes DML und jedes SELECT INTO einen impliziten Cursor an. SQL%FOUND und SQL%ROWCOUNT beschreiben die letzte Anweisung. SELECT INTO wirft NO_DATA_FOUND bei null Zeilen und TOO_MANY_ROWS bei mehreren.
  9. Explizite Cursors: Man macht OPEN, FETCH in einer Schleife mit EXIT WHEN c%NOTFOUND und dann CLOSE. Die Cursor-FOR-Schleife macht das alles selbst. Sie ist die einfachste Form.
  10. REF CURSOR: Eine Cursor-Variable kann zur Laufzeit auf verschiedene Abfragen zeigen. Man kann sie an Subprogramme und Clients übergeben. SYS_REFCURSOR ist der vordefinierte, schwach typisierte Typ.
  11. Context Switch und Bulk SQL: PL/SQL und SQL sind getrennte Engines. Zeile für Zeile bedeutet viele Wechsel. BULK COLLECT holt viele Zeilen in eine Collection. LIMIT begrenzt die Zeilen pro Aufruf und damit den PGA-Speicher.
  12. FORALL und Fehler: FORALL schickt ein DML für alle Elemente einer Collection. Ohne SAVE EXCEPTIONS stoppt es beim ersten Fehler und macht die Änderungen dieser Anweisung rückgängig. Mit SAVE EXCEPTIONS läuft es weiter. Danach kommt ORA-24381, und SQL%BULK_EXCEPTIONS listet die Fehler.
  13. Exceptions: Vordefinierte Fehler sind zum Beispiel TOO_MANY_ROWS, DUP_VAL_ON_INDEX, ZERO_DIVIDE und VALUE_ERROR. RAISE_APPLICATION_ERROR nimmt Codes von -20000 bis -20999. Ein unbehandelter Fehler in einer gespeicherten Prozedur rollt ihre Änderungen nicht zurück. Das entscheidet der Aufrufer.

4. Fallen

  • „WHEN OTHERS THEN NULL ist ein sicherer Schutz.“ → Falsch. Es versteckt jeden Fehler. Besser loggen und mit RAISE weitergeben.
  • „Ein Fehler in einer Prozedur rollt automatisch die ganze Transaktion zurück.“ → Falsch. PL/SQL rollt die Änderungen der Prozedur nicht zurück. Der Aufrufer entscheidet. Nur die fehlerhafte SQL-Anweisung ist atomar.
  • „Eine Cursor-Schleife mit INSERT pro Zeile ist schnell genug.“ → Falsch. Jede Zeile ist ein Context Switch. FORALL oder ein einzelnes SQL ist viel schneller.
  • „Package-Variablen sind für alle Sessions gleich.“ → Falsch. Der Zustand gilt pro Session. Jede Session hat ihre eigene Kopie.
  • „Eine Änderung am Body invalidiert immer alle Aufrufer.“ → Falsch. Meist nur bei einer Änderung der Spec.
  • „FORALL macht bei einem Fehler einfach weiter.“ → Falsch. Nur mit SAVE EXCEPTIONS. Sonst stoppt es und macht die Änderungen dieser Anweisung rückgängig.

5. Selbsttest

Warum?

Warum Logik in die Datenbank legen?

Daten und Logik sind nah beieinander. Das spart Netzwerk-Roundtrips. Der Code ist einmal kompiliert und für viele Anwendungen nutzbar.

Warum Packages statt einzelner Prozeduren?

Packages bündeln und verstecken. Nur die Spec ist öffentlich, und sie hält Zustand pro Session.

Warum BULK COLLECT mit LIMIT?

Ohne LIMIT landen alle Zeilen im PGA-Speicher. LIMIT holt die Zeilen in Paketen.

Wie innen?

Was ist ein Context Switch?

Der Wechsel zwischen PL/SQL-Engine und SQL-Engine. Er kostet bei jeder SQL-Anweisung etwas.

Wie arbeitet ein expliziter Cursor?

OPEN startet die Abfrage, FETCH holt Zeilen, %NOTFOUND zeigt das Ende, CLOSE gibt ihn frei.

Was macht die Cursor-FOR-Schleife?

Sie öffnet, holt und schliesst den Cursor selbst. Man schreibt weniger Code und vergisst kein CLOSE.

Wann läuft der Init-Block eines Package?

Einmal pro Session, beim ersten Zugriff auf das Package.

Was passiert bei einer Exception ohne Handler?

Sie geht an den äusseren Block, zuletzt an den Aufrufer. Eine gespeicherte Prozedur rollt ihre Änderungen nicht selbst zurück.

Wie meldet FORALL Fehler?

Mit SAVE EXCEPTIONS läuft es weiter und wirft am Ende ORA-24381. SQL%BULK_EXCEPTIONS hat Index und Code jedes Fehlers.

Zahlen

Welchen Bereich haben Codes bei RAISE_APPLICATION_ERROR?

-20000 bis -20999. Die Meldung hat höchstens 2048 Bytes.

Welchen Code hat TOO_MANY_ROWS?

-1422, also ORA-01422.

Welche Teile eines PL/SQL-Blocks sind Pflicht?

Nur BEGIN und END.

Vergleich

Procedure vs Function?

Eine Procedure führt eine Aktion aus. Eine Function berechnet einen Wert mit RETURN.

Spec vs Body?

Die Spec ist die öffentliche Schnittstelle. Der Body enthält den Code und private Teile.

Cursor-FOR-Schleife vs BULK COLLECT?

Die Schleife ist einfach, holt aber Zeile für Zeile. BULK COLLECT holt viele Zeilen in einem Schritt.

Definer's Rights vs Invoker's Rights?

AUTHID DEFINER nutzt die Rechte des Besitzers. AUTHID CURRENT_USER nutzt die Rechte des Aufrufers.

Produktion

Was tun bei einer langsamen Zeile-für-Zeile-Schleife?

Als einzelnes SQL schreiben, oder BULK COLLECT und FORALL nutzen. Das reduziert die Context Switches.

Was tun, wenn ein Package nach einer Änderung ungültig ist?

Neu kompilieren und Abhängigkeiten prüfen. Bei einer Spec-Änderung sind auch Aufrufer betroffen.

Szenario: Ein Job lädt 5 Millionen Zeilen in PL/SQL und bricht mit Speicherfehler ab. Was tun Sie?

Ich nutze BULK COLLECT mit LIMIT und verarbeite in Paketen. Oder ich schreibe es als ein SQL mit INSERT ... SELECT.

Szenario: Ein Fehler wird nie gemeldet, aber Daten fehlen. Woran denken Sie?

An ein WHEN OTHERS THEN NULL. Ich ersetze es durch gezielte Handler, Logging und RAISE.

Szenario: Eine Prozedur schlägt in der Mitte fehl, und halbe Änderungen bleiben. Was tun Sie?

PL/SQL rollt nicht selbst zurück. Der Aufrufer macht ROLLBACK, oder ich setze einen Savepoint und gehe bei Fehler dahin zurück.

Design

Wie gestaltet man eine gute Package-Spec?

Klein und stabil, nur das Nötige öffentlich. Details bleiben im Body, damit sich Aufrufer nicht neu kompilieren müssen.

Wann nimmt man einen REF CURSOR?

Wenn ein Client eine Ergebnismenge bekommen soll, die die Prozedur erst zur Laufzeit festlegt.

Wer soll COMMIT machen?

Meist der Aufrufer, also die Anwendung. Dann bleibt die Geschäftstransaktion unter Kontrolle.

Wann braucht man eine autonome Transaktion?

Für Logging, das auch bei Rollback bleiben muss. Sie ist eine unabhängige Transaktion mit eigenem COMMIT.

Wie behandelt man SELECT INTO sicher?

Mit Handlern für NO_DATA_FOUND und TOO_MANY_ROWS, oder mit einer Cursor-Schleife, wenn mehrere Zeilen möglich sind.

Mehr

Gerüst

  • Warum? Logik nah an den Daten, einmal kompiliert, für viele Anwendungen nutzbar.
  • Wie innen? Block aus DECLARE, BEGIN, EXCEPTION, END. Package aus Spec und Body mit Zustand pro Session.
  • Zahlen Pflicht: BEGIN und END. Fehlercodes -20000 bis -20999. Meldung höchstens 2048 Bytes.
  • Vergleich Procedure gegen Function. Spec gegen Body. DEFINER gegen CURRENT_USER.
  • Produktion Zeile-für-Zeile-Schleifen, WHEN OTHERS ohne RAISE, ungültige Packages nach Spec-Änderung.
  • Design Kleine Spec, Bulk SQL, gezielte Handler, Commit beim Aufrufer.

Beispiel: Package mit Bulk SQL und Fehlerbehandlung

CREATE OR REPLACE PACKAGE emp_pkg AS
  PROCEDURE raise_salary(p_dept IN NUMBER, p_pct IN NUMBER);
END emp_pkg;
/
CREATE OR REPLACE PACKAGE BODY emp_pkg AS
  g_calls PLS_INTEGER := 0;                -- Zustand pro Session
  TYPE t_ids IS TABLE OF employees.employee_id%TYPE;

  PROCEDURE raise_salary(p_dept IN NUMBER, p_pct IN NUMBER) IS
    CURSOR c IS SELECT employee_id FROM employees WHERE department_id = p_dept;
    l_ids t_ids;
    dml_errors EXCEPTION;
    PRAGMA EXCEPTION_INIT(dml_errors, -24381);
  BEGIN
    g_calls := g_calls + 1;
    OPEN c;
    LOOP
      FETCH c BULK COLLECT INTO l_ids LIMIT 500;   -- Pakete zu 500 Zeilen
      EXIT WHEN l_ids.COUNT = 0;
      BEGIN
        FORALL i IN 1 .. l_ids.COUNT SAVE EXCEPTIONS
          UPDATE employees SET salary = salary * (1 + p_pct / 100)
           WHERE employee_id = l_ids(i);
      EXCEPTION
        WHEN dml_errors THEN
          FOR j IN 1 .. SQL%BULK_EXCEPTIONS.COUNT LOOP
            DBMS_OUTPUT.PUT_LINE('Element ' || SQL%BULK_EXCEPTIONS(j).ERROR_INDEX
              || ' Fehler ' || SQL%BULK_EXCEPTIONS(j).ERROR_CODE);
          END LOOP;
      END;
    END LOOP;
    CLOSE c;
  EXCEPTION
    WHEN OTHERS THEN
      IF c%ISOPEN THEN CLOSE c; END IF;
      RAISE;                               -- Fehler nicht verschlucken
  END raise_salary;
BEGIN
  g_calls := 0;                            -- Init-Block, einmal pro Session
END emp_pkg;
/
-- Aufruf: BEGIN emp_pkg.raise_salary(50, 5); COMMIT; END;

Nicht ausgeführt.

  1. Die Spec zeigt nur raise_salary. g_calls und der Typ t_ids sind privat im Body.
  2. g_calls ist Zustand pro Session. Der Init-Block am Ende setzt ihn einmal pro Session auf 0.
  3. FETCH ... BULK COLLECT ... LIMIT 500 holt höchstens 500 Zeilen pro Schritt.
  4. FORALL ... SAVE EXCEPTIONS macht ein Update pro Element ohne Context Switch. Fehler landen in SQL%BULK_EXCEPTIONS.
  5. PRAGMA EXCEPTION_INIT gibt dem Fehler -24381 einen Namen, damit man ihn fangen kann.
  6. WHEN OTHERS schliesst den Cursor und macht RAISE. Der Aufrufer sieht den Fehler und entscheidet über COMMIT oder ROLLBACK.

Vergleich

  • Anonymer Block: nicht gespeichert, gut für Skripte und Tests.
  • Procedure: gespeichert, führt eine Aktion aus.
  • Function: gespeichert, gibt einen Wert zurück.
  • Package: bündelt mehrere Einheiten, hat Zustand pro Session.
  • Implizite Cursors: Oracle verwaltet sie bei DML und SELECT INTO.
  • Explizite Cursors: volle Kontrolle mit OPEN, FETCH, CLOSE.
  • Cursor-FOR-Schleife: kurz und sicher für Zeile-für-Zeile.
  • PostgreSQL PL/pgSQL: hat keine Packages. Man nutzt Schemas.

Produktion

  1. Langsame Jobs: Zeile für Zeile mit vielen Context Switches. Lösung: Bulk SQL oder ein einzelnes SQL.
  2. Speicherfehler: BULK COLLECT ohne LIMIT. Lösung: LIMIT setzen.
  3. Verschluckte Fehler: WHEN OTHERS THEN NULL. Lösung: loggen und RAISE.
  4. Halbe Änderungen: Eine Prozedur bricht ab, und niemand macht Rollback. Lösung: Aufrufer verwaltet die Transaktion, oder Savepoint.
  5. Ungültige Objekte: Eine Spec-Änderung invalidiert Aufrufer. Lösung: Specs stabil halten und Deployment mit Neukompilierung planen.
  6. Alter Zustand: Ein Package hält Werte in der Session. Lösung: Zustand bewusst initialisieren oder vermeiden.

Diagnose: Werkzeuge und Befehle

  • USER_ERRORS oder SHOW ERRORS: zeigt Kompilierfehler.
  • USER_OBJECTS mit STATUS: zeigt ungültige Objekte.
  • USER_DEPENDENCIES: zeigt, wer von einem Package abhängt.
  • DBMS_OUTPUT.PUT_LINE: einfache Ausgabe zum Testen.
  • SQLCODE und SQLERRM im Handler: Code und Text des Fehlers.
  • DBMS_PROFILER oder DBMS_HPROF: zeigt, wo PL/SQL Zeit braucht.

Senior-Punkte

  1. Mengen statt Zeilen. Ein SQL schlägt jede Schleife. Danach kommt Bulk SQL.
  2. Packages sind Verträge. Eine kleine, stabile Spec hält Aufrufer gültig.
  3. Fehler sind Daten. Loggen, weitergeben, nie verschlucken.
  4. Der Aufrufer besitzt die Transaktion. Procedures committen meist nicht.
  5. Zustand pro Session ist versteckter Zustand. Er macht Tests und Verbindungspools schwieriger.
  6. Portierung nach PostgreSQL kostet. Packages, Package-Variablen und autonome Transaktionen haben dort keine Entsprechung.
