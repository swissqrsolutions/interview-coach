Oracle vs PostgreSQL

Kern: Oracle und PostgreSQL sind beide relationale Datenbanken mit MVCC und ACID. Sie unterscheiden sich in der Mechanik, besonders bei alten Zeilenversionen (Undo gegen Heap), bei Sperren, bei NULL und Typen und bei PL/SQL gegen PL/pgSQL. Wer die Unterschiede kennt, portiert Code sicher und findet Produktionsfehler schneller.

Antwort-Muster

Frage: Wie unterscheiden sich Oracle und PostgreSQL bei der Nebenläufigkeit?

  1. Mechanismus: Oracle schreibt in den Block und legt den alten Stand im Undo ab. PostgreSQL legt eine neue Row Version im Heap an.
  2. Zahl: Beide laufen standardmässig mit READ COMMITTED. Oracle kennt zusätzlich READ ONLY, PostgreSQL behandelt READ UNCOMMITTED wie READ COMMITTED.
  3. Trade-off: Oracle kann bei langen Abfragen ORA-01555 werfen, PostgreSQL braucht VACUUM gegen Bloat.
  4. Produktion: Ich prüfe in Produktion Undo-Retention und Long Transactions in Oracle, und Autovacuum und alte Snapshots in PostgreSQL.

1. Ein UPDATE und ein Leser in 7 Schritten

  1. Leser startet: Die Abfrage bekommt einen festen Zeitpunkt. Bei Oracle ist das eine SCN. Bei PostgreSQL ist es ein Snapshot.
  2. Schreiber ändert: Eine zweite Session macht ein UPDATE auf dieselbe Zeile. Sie sperrt nur diese Zeile.
  3. Oracle: Der neue Wert kommt in den Datenblock. Der alte Stand geht ins Undo.
  4. PostgreSQL: Es entsteht eine neue Row Version. Die alte Version bleibt im selben Heap stehen.
  5. Leser liest: Oracle baut den alten Blockstand aus dem Undo nach. PostgreSQL prüft per Snapshot, welche Version sichtbar ist. Der Leser wartet nicht.
  6. Aufräumen: In Oracle wird Undo mit der Zeit überschrieben. In PostgreSQL entfernt VACUUM alte Versionen, die kein Snapshot mehr braucht.
  7. Fehlerbild: Fehlt das Undo, wirft Oracle ORA-01555 (snapshot too old). Läuft VACUUM nicht, wächst in PostgreSQL die Tabelle (Bloat).

2. Aufbau

  1. Oracle nutzt Undo-Daten, um ältere Blockstände zu bauen. Jede Abfrage sieht einen festen Zeitpunkt.
  2. PostgreSQL hält alte Versionen als Zeilen im Heap und räumt sie mit VACUUM auf.
  3. Oracle speichert Sperren im Header des Datenblocks. Es gibt keinen zentralen Lock-Manager für Zeilen.
  4. Oracle ordnet Speicher in Datenblock, Extent, Segment und Tablespace.
  5. Oracle-Code liegt oft in Packages. PostgreSQL hat keine Packages und nutzt Schemas.
  6. Typen heissen anders. Oracle VARCHAR2 wird zu varchar oder text, NUMBER zu numeric.

3. Details

  1. Read Consistency: Jede Oracle-Abfrage liefert Daten von einem einzigen Zeitpunkt (SCN). Bei READ COMMITTED ist das der Start der Anweisung. Bei SERIALIZABLE oder READ ONLY ist es der Start der Transaktion. Leser blockieren Schreiber nicht, und umgekehrt.
  2. Isolation in Oracle: Es gibt READ COMMITTED (Standard), SERIALIZABLE und READ ONLY. Dirty Reads gibt es nie. Bei SERIALIZABLE kann ORA-08177 kommen. Dann wiederholt die Anwendung die Transaktion.
  3. Isolation in PostgreSQL: Standard ist READ COMMITTED. READ UNCOMMITTED verhält sich wie READ COMMITTED. REPEATABLE READ ist Snapshot Isolation und lässt keine Phantome zu. SERIALIZABLE nutzt SSI und meldet Konflikte mit SQLSTATE 40001.
  4. ORA-01555: Eine lange Abfrage braucht Undo, das schon überschrieben ist. Eine längere Undo-Retention senkt das Risiko. PostgreSQL hat dieses Problem nicht, dafür Bloat.
  5. Zeilen-Locks: Oracle sperrt nur geänderte Zeilen. Ein zweiter Schreiber auf dieselbe Zeile wartet bis COMMIT oder ROLLBACK. Oracle eskaliert Zeilenlocks nie zu Tabellenlocks.
  6. Deadlock: Oracle erkennt ihn selbst und rollt eine Anweisung zurück, mit ORA-00060. Ohne Index auf der Fremdschlüssel-Spalte kann das Ändern eines Parent-Schlüssels die ganze Kindtabelle sperren.
  7. Leerer String: Oracle behandelt einen String der Länge null als NULL. Die Doku warnt, dass sich das ändern könnte. In PostgreSQL ist ein leerer String ein normaler Wert. Das ändert WHERE, || und Constraints beim Portieren.
  8. Typen: NUMBER hat 1 bis 38 Stellen Genauigkeit. DATE enthält in Oracle auch die Uhrzeit, ohne Zeitzone. VARCHAR2 hat standardmässig höchstens 4000 Bytes. Mit MAX_STRING_SIZE = EXTENDED sind es 32767. PostgreSQL text und varchar sind gleich schnell.
  9. PL/SQL und Packages: Ein Package hat Spec und Body. Es hält Zustand pro Session. PostgreSQL hat keine Packages und deshalb auch keine Package-Variablen. Man gruppiert Funktionen in Schemas.
  10. Autonome Transaktion: Oracle kennt PRAGMA AUTONOMOUS_TRANSACTION. Das ist eine unabhängige Transaktion, zum Beispiel für ein Fehlerlog. In PostgreSQL braucht man dafür einen anderen Weg, zum Beispiel eine zweite Verbindung.
  11. DDL und Transaktionen: Oracle committet vor und nach jedem DDL-Befehl implizit. In PostgreSQL ist TRUNCATE transaktionssicher und lässt sich zurückrollen.
  12. Sequenzen: In PostgreSQL macht nextval nie ein Rollback. Es gibt Lücken. Wer lückenlose Nummern braucht, nutzt eine Tabelle mit Sperre. Das ist viel teurer.

4. Fallen

  • „In Oracle und PostgreSQL ist ein leerer String dasselbe.“ → Falsch. In Oracle ist er NULL. In PostgreSQL ist er ein normaler Wert.
  • „Oracle hat kein Bloat-Problem, also keine MVCC-Probleme.“ → Falsch. Es hat ein eigenes: ORA-01555, wenn das Undo für eine lange Abfrage fehlt.
  • „Ein DDL-Befehl lässt sich in Oracle zurückrollen.“ → Falsch. Oracle committet vor und nach jedem DDL-Befehl. Es gibt nichts zum Zurückrollen.
  • „PostgreSQL READ UNCOMMITTED liest ungeschriebene Daten.“ → Falsch. Es verhält sich wie READ COMMITTED. Dirty Reads gibt es nicht.
  • „PL/SQL-Packages laufen unverändert in PL/pgSQL.“ → Falsch. PostgreSQL hat keine Packages. Man nutzt Schemas, und Package-Variablen gibt es nicht.
  • „Eine Sequenz ist lückenlos.“ → Falsch. Ein Rollback gibt Nummern nicht zurück. In PostgreSQL ist nextval nie rückgängig.

5. Selbsttest

Warum?

Warum blockieren Leser in Oracle keine Schreiber?

Leser nutzen Undo-Daten für einen alten Stand. Sie brauchen keine Sperre auf die Zeile.

Warum gibt es in Oracle ORA-01555?

Ein langer Leser braucht Undo, das schon überschrieben ist. Der alte Stand lässt sich nicht mehr bauen.

Warum ist der leere String beim Portieren ein Risiko?

Oracle-Code verlässt sich darauf, dass '' NULL ist. In PostgreSQL gilt das nicht, also ändern sich Vergleiche und Constraints.

Wie innen?

Wie macht Oracle Read Consistency?

Es nutzt Undo-Daten und baut ältere Datenblöcke nach. Jede Abfrage sieht Daten zu einer SCN.

Wie macht PostgreSQL das?

Es legt neue Row Versions im Heap an. Ein Snapshot entscheidet, welche Version sichtbar ist. VACUUM räumt auf.

Wo liegen Zeilen-Locks in Oracle?

Im Header des Datenblocks. Es gibt keinen Lock-Manager für Zeilen.

Was heisst Oracle eskaliert nie Locks?

Viele Zeilenlocks werden nie zu einem Tabellenlock. Das vermeidet eine häufige Deadlock-Quelle.

Wie ordnet Oracle den Speicher?

Datenblock, Extent, Segment, Tablespace. Der Datenblock ist die kleinste Einheit.

Was ist Row Migration in Oracle?

Wächst eine Zeile über den Block hinaus, zieht sie in einen neuen Block um. Die Rowid bleibt gleich, im alten Block bleibt ein Verweis.

Zahlen

Welche Standard-Isolation haben beide?

READ COMMITTED.

Wie viel kann ein Oracle-VARCHAR2 fassen?

Standardmässig 4000 Bytes. Mit MAX_STRING_SIZE = EXTENDED bis 32767.

Welche Länge hat PostgreSQL varchar(n) höchstens?

n darf höchstens 10485760 sein. Ein Wert ist höchstens etwa 1 GB gross.

Vergleich

Oracle Undo vs PostgreSQL VACUUM?

Oracle hält alte Stände im Undo, das überschrieben wird. PostgreSQL hält sie im Heap, bis VACUUM sie entfernt.

PL/SQL-Package vs PostgreSQL-Schema?

Ein Package hat Spec, Body und Session-Zustand. Ein Schema gruppiert nur Objekte.

Oracle SERIALIZABLE vs PostgreSQL SERIALIZABLE?

Beide verlangen Retry bei Konflikt. Oracle meldet ORA-08177. PostgreSQL meldet SQLSTATE 40001 und nutzt SSI.

VARCHAR2 vs text?

VARCHAR2 ist Oracle-spezifisch. In PostgreSQL nimmt man text oder varchar, ohne Geschwindigkeitsunterschied.

Produktion

Was tut man gegen ORA-01555?

Undo-Retention erhöhen, lange Abfragen kürzen oder in kleinere Teile splitten und lange Transaktionen vermeiden.

Was wächst bei PostgreSQL ohne VACUUM?

Tote Row Versions belegen Platz. Tabellen und Indexe blähen sich auf.

Szenario: Ein Bericht in Oracle bricht nachts mit ORA-01555 ab. Was tun Sie?

Ich prüfe Undo-Grösse und Retention und die Laufzeit des Berichts. Dann erhöhe ich die Retention oder splitte den Bericht.

Szenario: Nach dem Portieren findet ein Filter WHERE feld IS NULL keine Zeilen mehr. Warum?

Oracle hat leere Strings als NULL gespeichert. In PostgreSQL sind es leere Strings. Ich prüfe, wie die Daten gefüllt werden, und passe den Filter an.

Szenario: Eine PostgreSQL-Tabelle wird gross, obwohl wenige Zeilen aktiv sind. Warum?

Alte Row Versions werden nicht entfernt. Oft hält ein alter Snapshot oder eine lange Transaktion VACUUM auf.

Design

Wie portiert man ein Package nach PostgreSQL?

Ich lege ein Schema an und schreibe Funktionen und Prozeduren dort hinein. Zustand lege ich in eine Tabelle, eine temporäre Tabelle oder in Parameter.

Wie geht man mit Oracle-VARCHAR2 und NUMBER um?

Ich nehme text oder varchar und numeric. Ich prüfe vorher die Länge und Genauigkeit.

Wann nimmt man SERIALIZABLE?

Wenn Anomalien teuer sind. Die Anwendung muss die Transaktion bei ORA-08177 oder 40001 wiederholen.

Wie schützt man sich vor Lost Updates in READ COMMITTED?

Man nimmt die alten Werte in die WHERE-Bedingung auf. Betrifft das Update 0 Zeilen, hat jemand die Zeile geändert.

Wann braucht man Autonomous Transactions?

Für Logging, das auch bei Rollback bleiben muss. In PostgreSQL braucht man dafür einen anderen Weg, zum Beispiel eine zweite Verbindung.

Mehr

Gerüst

  • Warum? Beide sind ACID mit MVCC. Die Mechanik ist verschieden, darum auch die Fehlerbilder.
  • Wie innen? Oracle: Undo und SCN. PostgreSQL: Row Versions im Heap, Snapshot und VACUUM.
  • Zahlen READ COMMITTED ist Standard. VARCHAR2 bis 4000 Bytes. 40001 gegen ORA-08177.
  • Vergleich Undo gegen VACUUM. Package gegen Schema. VARCHAR2 gegen text.
  • Produktion ORA-01555 und Undo-Retention in Oracle. Bloat und alte Snapshots in PostgreSQL.
  • Design Leerer String, Packages, DDL und Sequenzen beim Portieren prüfen.

Beispiel: Drei Unterschiede in SQL

-- 1) Leerer String (Oracle)
SELECT CASE WHEN '' IS NULL THEN 'leer ist NULL' ELSE 'leer ist nicht NULL' END FROM dual;
-- 1) Leerer String (PostgreSQL, kein FROM nötig)
SELECT CASE WHEN '' IS NULL THEN 'leer ist NULL' ELSE 'leer ist nicht NULL' END;

-- 2) Leser und Schreiber (beide Datenbanken, READ COMMITTED)
-- Session A
UPDATE konto SET saldo = saldo - 100 WHERE id = 1;   -- noch kein COMMIT
-- Session B
SELECT saldo FROM konto WHERE id = 1;                -- wartet nicht, alter Wert
-- Session A
COMMIT;
-- Session B, neue Anweisung
SELECT saldo FROM konto WHERE id = 1;                -- neuer Wert

-- 3) Serializable: bei Konflikt Fehler und Retry
-- PostgreSQL: SQLSTATE 40001      Oracle: ORA-08177

Nicht ausgeführt.

  1. Block 1: Laut Oracle-Doku wird ein String der Länge null wie NULL behandelt. Der erste Befehl müsste also "leer ist NULL" liefern. In PostgreSQL ist '' ein normaler Wert. Beim Portieren braucht es eine Prüfung.
  2. Block 2: Session B wartet nicht auf Session A. Sie sieht den alten Wert, bis A committet. Das gilt in beiden Datenbanken, weil Leser alte Versionen lesen.
  3. Block 2: Die zweite Abfrage von B ist eine neue Anweisung. Bei READ COMMITTED sieht sie den neuen Wert.
  4. Block 3: Bei SERIALIZABLE kann ein Konflikt entstehen. Die Anwendung muss die ganze Transaktion wiederholen.
  5. Die Ausgabe dieser Befehle habe ich nicht gemessen. Es lief keine Datenbank.

Vergleich

  • Alte Versionen: Oracle Undo, PostgreSQL Heap mit VACUUM.
  • Isolation: Oracle READ COMMITTED, SERIALIZABLE, READ ONLY. PostgreSQL vier Namen, drei echte Verhalten.
  • Locks: Oracle Lock im Blockheader, nie Eskalation.
  • Fehler bei langen Lesern: Oracle ORA-01555, PostgreSQL Bloat und Verzögerung von VACUUM.
  • Strings: Oracle '' ist NULL, PostgreSQL nicht.
  • Code in der DB: PL/SQL mit Packages, PL/pgSQL mit Schemas.
  • Autonome Transaktion: in Oracle mit Pragma, in PostgreSQL nicht in der Doku.
  • DDL: Oracle committet implizit, PostgreSQL TRUNCATE ist rollbar.

Produktion

  1. ORA-01555: Undo zu klein oder Abfrage zu lang. Lösung: Retention erhöhen, Abfrage kürzen.
  2. Bloat in PostgreSQL: VACUUM kommt nicht nach oder ein alter Snapshot blockiert es. Lösung: Autovacuum prüfen, lange Transaktionen beenden.
  3. Falsche Ergebnisse nach Migration: Leere Strings sind nicht mehr NULL. Lösung: Daten und Filter prüfen.
  4. Deadlocks wegen Fremdschlüssel: Ein Index auf der Kindspalte fehlt. Lösung: Index anlegen.
  5. Lücken in Nummern: Eine Sequenz ist nicht lückenlos. Lösung: Lücken akzeptieren oder eine Zählertabelle mit Sperre nutzen.
  6. Package-Zustand fehlt: PostgreSQL hat keine Package-Variablen. Lösung: temporäre Tabellen oder Parameter.

Diagnose: Werkzeuge und Befehle

  • Oracle: V$UNDOSTAT und die Undo-Retention prüfen.
  • Oracle: V$SESSION und V$LOCK für wartende Sessions.
  • Oracle: AWR- oder Statspack-Bericht für Last und Wartezeiten.
  • PostgreSQL: pg_stat_activity für lange Transaktionen und alte Snapshots.
  • PostgreSQL: pg_stat_user_tables für n_dead_tup und das Datum von Autovacuum.
  • PostgreSQL: EXPLAIN (ANALYZE, BUFFERS) für den Plan.

Senior-Punkte

  1. Die Mechanik erklärt die Fehlerbilder. Undo gibt ORA-01555, der Heap gibt Bloat.
  2. Portieren heisst Verhalten prüfen, nicht nur Syntax tauschen. Leerer String, Sequenzen und DDL sind Beispiele.
  3. Packages sind ein Designmittel. In PostgreSQL ersetzt man sie mit Schemas und trägt den Zustand explizit.
  4. Isolation ist ein Vertrag mit Retry. SERIALIZABLE braucht in beiden Systemen eine Wiederholung.
  5. Die Tests müssen Daten enthalten, die in Oracle NULL waren, sonst fällt der Unterschied nicht auf.
  6. Keine Meinung, sondern Messung. Vor dem Wechsel Last und Pläne in beiden Systemen messen.
