Subject, BehaviorSubject, ReplaySubject

Angular · Tier 1 · Quellen: rxjs.dev (RxJS 7.8) Guide „Subject“, API Subject, BehaviorSubject, ReplaySubject, AsyncSubject, share, shareReplay; angular.dev (v22) „Signals“, „RxJS interop“

Kern: Ein Subject ist gleichzeitig Observable und Observer: Man kann next() aufrufen, und viele Subscriber bekommen denselben Wert. Es ist immer hot. BehaviorSubject merkt sich den aktuellen Wert, ReplaySubject die letzten n Werte; das macht sie zur klassischen Basis für State in Angular-Services.

1. Wo sitzt ein Subject?

  1. Schreiber: Komponenten oder HTTP-Antworten rufen Methoden des Services auf, z. B. setFilter().
  2. Service: hält ein privates BehaviorSubject. Nur der Service ruft next() auf.
  3. Öffentlich: state$ = subject.asObservable(). Leser können nicht schreiben.
  4. Leser: Viele Komponenten abonnieren. Alle bekommen denselben Wert, neue sofort den aktuellen.

2. Die Reise eines next() (die Geschichte zum Merken)

  1. Werte 1, 2, 3: Der Service ruft dreimal next() auf. Alle bestehenden Subscriber bekommen sie sofort, synchron.
  2. Später Subscriber: Eine neue Komponente abonniert nach Wert 3.
  3. Subject: Sie bekommt nichts Altes. Erst Wert 4.
  4. BehaviorSubject: Sie bekommt sofort den aktuellen Wert 3, dann 4.
  5. ReplaySubject(2): Sie bekommt die letzten zwei Werte 2 und 3, dann 4.
  6. AsyncSubject: Alle bekommen nur den letzten Wert, und zwar erst bei complete().

3. Beispiel: State-Service wie in einem Dashboard (Angular-14-Stil und Angular-22-Stil)

// Angular-14-Stil: RxJS-Service-State
@Injectable({ providedIn: 'root' })
export class FilterStore {
  private readonly state = new BehaviorSubject<Filter>({ region: 'all', days: 7 });
  readonly filter$ = this.state.asObservable();
  readonly days$   = this.filter$.pipe(map(f => f.days), distinctUntilChanged());

  setDays(days: number) {
    this.state.next({ ...this.state.value, days });   // neue Referenz, keine Mutation
  }
}

// Test der Reihenfolge
const s  = new Subject<number>();
const b  = new BehaviorSubject<number>(0);
const r  = new ReplaySubject<number>(2);
[1, 2, 3].forEach(v => { s.next(v); b.next(v); r.next(v); });
s.subscribe(v => console.log('Subject', v));
b.subscribe(v => console.log('Behavior', v));
r.subscribe(v => console.log('Replay', v));
console.log('value', b.value);

// Angular-22-Stil: dasselbe mit Signals
@Injectable({ providedIn: 'root' })
export class FilterState {
  private readonly _filter = signal<Filter>({ region: 'all', days: 7 });
  readonly filter = this._filter.asReadonly();
  readonly days   = computed(() => this._filter().days);
  setDays(days: number) { this._filter.update(f => ({ ...f, days })); }
}

Replay 2
Replay 3
value 3
(Subject gibt nichts aus: Die Werte kamen vor dem subscribe.)
  1. Das Subject hat keinen Speicher. Wer zu spät kommt, verpasst alles.
  2. BehaviorSubject liefert beim Abonnieren sofort den aktuellen Wert. .value liest ihn synchron.
  3. ReplaySubject(2) liefert die letzten zwei Werte.
  4. Die Signal-Version macht dasselbe ohne Subscription. computed ersetzt map + distinctUntilChanged.

4. Details, die Interviewer fragen

  1. Subject ist Multicast: Eine Ausführung, viele Subscriber. Ein normales Observable ist Unicast, jeder Subscriber hat eine eigene.
  2. BehaviorSubject braucht einen Startwert. Es hat immer einen aktuellen Wert. Darum passt es zu State.
  3. getValue()/.value: liest synchron. Praktisch, aber verführt zu imperativem Code.
  4. ReplaySubject(bufferSize, windowTime): speichert n Werte, optional nur für eine Zeitspanne. Ohne Grenze wächst der Puffer endlos.
  5. AsyncSubject: liefert nur den letzten Wert bei complete. Ähnlich wie ein Promise.
  6. Nach complete: next() hat keine Wirkung mehr. Neue Subscriber bekommen nur complete. Bei BehaviorSubject auch keinen Wert.
  7. Nach error: Neue Subscriber bekommen sofort den Fehler. Das Subject ist tot.
  8. asObservable(): versteckt next() nach aussen. Nur der Besitzer schreibt.
  9. share() und shareReplay() nutzen intern ein Subject bzw. ReplaySubject. Oft besser als ein eigenes Subject.
  10. Subject als Event-Bus: möglich, aber schwer nachzuvollziehen. Besser klare Services pro Thema.
  11. destroy$-Muster (Angular 14): destroy$ = new Subject<void>(), takeUntil(this.destroy$), in ngOnDestroy next() und complete(). Heute: takeUntilDestroyed.
  12. Signals vs BehaviorSubject: Beide halten einen aktuellen Wert. Signals brauchen kein Unsubscribe und sind mit der Change Detection verbunden. RxJS bleibt für Zeit und Events.
  13. NgRx: eine Bibliothek für globalen State mit Actions, Reducern und Effects. Intern auch auf RxJS gebaut. Nicht in Produktion genutzt (nur gelernt).

5. Vergleich

  • Subject: kein Startwert, kein Speicher. Für Events: Klick, „Neu laden“, destroy$.
  • BehaviorSubject: Startwert, aktueller Wert. Für State: Filter, eingeloggter Nutzer.
  • ReplaySubject: letzte n Werte. Für Verlauf oder Daten, die später Hinzukommende brauchen.
  • AsyncSubject: nur letzter Wert bei complete. Selten.
  • Signal: aktueller Wert, synchron, kein Unsubscribe. In Angular 22 die erste Wahl für UI-State.

6. In der Produktion

  1. Jeder schreibt überall: Subject ist public, Komponenten rufen next(). Fehler sind kaum nachvollziehbar. Lösung: privates Subject, asObservable(), klare Methoden.
  2. Mutierter State: state.value.items.push(x) ohne next(). OnPush sieht nichts. Lösung: neues Objekt und next().
  3. Memory Leak durch ReplaySubject: ohne Puffergrenze. Lösung: bufferSize setzen.
  4. Komponente zeigt alten Nutzer nach Logout: BehaviorSubject im Root-Service wird nicht zurückgesetzt. Lösung: beim Logout Startwert setzen.
  5. Race beim Start: Subject statt BehaviorSubject, die Komponente abonniert nach dem ersten Wert. Lösung: BehaviorSubject oder ReplaySubject(1).

7. Diagnose: Werkzeuge und Befehle

  • tap(v => console.log('[FilterStore]', v)) direkt am Subject-Ausgang.
  • Angular DevTools: Signals und Komponenten-State ansehen. Für RxJS: eigene Debug-Operatoren.
  • Heap Snapshot: grosse ReplaySubject-Puffer finden.
  • Marble-Tests für Services: Reihenfolge von next und Subscribern prüfen.
  • Redux DevTools nur mit NgRx oder ähnlichen Stores.

8. Senior-Punkte

  1. Service mit BehaviorSubject ist ein leichter Store. Er reicht für die meisten Apps, bevor man NgRx einführt.
  2. Ein Schreibweg: privates Subject, öffentliche Methoden, öffentliches Observable. Das ist die wichtigste Regel.
  3. Unveränderliche Updates immer mit neuer Referenz. Das macht OnPush und Debugging einfach.
  4. Migration zu Signals schrittweise: toSignal(state$) in Komponenten, später den Store auf signal() umstellen.
  5. Kein globaler Event-Bus. Er versteckt Abhängigkeiten und macht Fehler schwer findbar.

9. Aus dem Projekt

„In den CARIAD-Dashboards (Angular 14) lag der State in RxJS-Services; Komponenten haben nur Observables gelesen, Änderungen liefen über Service-Methoden.“ (Prüfen und durch dein echtes Beispiel ersetzen: BehaviorSubject oder ReplaySubject?)

10. Fallen

  • „Ein Subject liefert späten Subscribern den letzten Wert.“ → Falsch. Das macht BehaviorSubject oder ReplaySubject.
  • „BehaviorSubject und ReplaySubject(1) sind gleich.“ → Fast. BehaviorSubject braucht einen Startwert und hat .value. ReplaySubject(1) liefert ohne Wert nichts.
  • „Subjects sind cold.“ → Falsch. Sie sind immer hot.
  • „Nach complete kann man weiter next() rufen.“ → Wirkungslos. Das Subject ist beendet.
  • „Signals ersetzen RxJS ganz.“ → Falsch. Für Zeit, Events und Abbruch bleibt RxJS.

11. Fragen

Was ist ein Subject?

Ein Observable und Observer zugleich. next() verteilt einen Wert an alle Subscriber.

Unicast vs Multicast?

Unicast: jeder Subscriber hat eine eigene Ausführung. Multicast: alle teilen eine, wie beim Subject.

Was ist ein BehaviorSubject?

Ein Subject mit Startwert und aktuellem Wert. Neue Subscriber bekommen ihn sofort.

Was ist ein ReplaySubject?

Ein Subject, das die letzten n Werte speichert und neuen Subscribern liefert.

Was ist ein AsyncSubject?

Es liefert nur den letzten Wert, und zwar erst bei complete.

BehaviorSubject vs ReplaySubject(1)?

BehaviorSubject braucht einen Startwert und hat .value. ReplaySubject(1) liefert nichts, bis der erste Wert kommt.

Warum asObservable()?

Leser sollen nicht next() rufen können. Nur der Service schreibt.

Wann nutzen Sie ein normales Subject?

Für Events ohne Zustand: Klicks, Reload-Trigger, das alte destroy$-Muster.

Was passiert nach complete?

next() wirkt nicht mehr. Neue Subscriber bekommen nur complete.

Was passiert nach error?

Das Subject ist beendet. Neue Subscriber bekommen sofort den Fehler.

Wie baue ich einen einfachen Store?

Ein Service mit privatem BehaviorSubject, öffentlichem Observable und Methoden für Updates. Updates immer mit neuer Referenz.

Warum ist .value gefährlich?

Es lädt zu imperativem Code ein. Abgeleitete Werte besser deklarativ mit map oder computed.

Wie hängen share/shareReplay mit Subjects zusammen?

Sie nutzen intern ein Subject bzw. ReplaySubject. So wird eine cold Quelle hot.

BehaviorSubject oder Signal in Angular 22?

Für UI-State ein Signal: kein Unsubscribe, direkt an der Change Detection. Für Event-Ströme mit Zeitlogik RxJS.

Wie ersetzt man das destroy$-Muster?

Mit takeUntilDestroyed() seit v16. Es nutzt DestroyRef.

Wann NgRx statt Service-Store?

Bei grossem, geteiltem State, vielen Teams und dem Bedarf an Nachvollziehbarkeit. Sonst reicht ein Service.

Szenario: Eine neue Komponente zeigt keinen Filter, obwohl er gesetzt ist. Warum?

Der Service nutzt ein Subject. Der Wert kam vor dem Subscribe. Lösung: BehaviorSubject.

Szenario: Nach Logout und Login als anderer Nutzer sieht man alte Daten. Warum?

Root-Services halten den alten State im BehaviorSubject. Lösung: beim Logout alle Stores zurücksetzen.

Szenario: Ein Kollege mutiert state.value direkt. Was sagen Sie im Review?

OnPush und Subscriber merken nichts, Fehler werden unsichtbar. Immer neues Objekt bauen und über eine Service-Methode next() rufen.
