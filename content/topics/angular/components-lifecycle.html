Komponenten und Lifecycle Hooks

Angular · Tier 1 · Quellen: angular.dev (v20) Guides „Component Lifecycle“, „Inputs“, „Outputs“, „Queries“, „Content projection“; API afterNextRender, afterEveryRender, DestroyRef, takeUntilDestroyed

Kern: Eine Komponente ist eine Klasse mit Template, Styles und Selektor. Angular ruft während ihres Lebens Lifecycle Hooks auf: beim Erstellen, bei jeder Change Detection, nach dem Rendern und beim Zerstören. Wer die Reihenfolge kennt, weiss, wo Inputs, Queries und DOM bereit sind.

1. Wo sitzt eine Komponente?

  1. Host-Element: das DOM-Element zum Selektor, z. B. <app-chart>.
  2. Input: Daten vom Parent in die Komponente. In v20: data = input.required<Point[]>().
  3. Output: Events an den Parent. In v20: select = output<Point>().
  4. View Children: Elemente im eigenen Template. Abfrage mit viewChild().
  5. Content Children: Elemente, die der Parent per <ng-content> hineingibt. Abfrage mit contentChild().
  6. Element-Injector: Jede Komponente kann eigene providers haben. Sie gelten für sie und ihre Kinder.

2. Die Reise einer Komponente (die Geschichte zum Merken)

  1. constructor: Angular erstellt die Klasse. Hier läuft inject(). Inputs sind noch nicht gesetzt.
  2. ngOnChanges: läuft, wenn sich ein Input ändert. Der erste Aufruf kommt vor ngOnInit. Er bekommt ein SimpleChanges-Objekt.
  3. ngOnInit: läuft einmal, nachdem die Inputs ihre ersten Werte haben. Hier startet man das Laden von Daten.
  4. ngDoCheck: läuft bei jeder Prüfung der Komponente. Teuer, nur für eigene Änderungserkennung.
  5. ngAfterContentInit/Checked: Der projizierte Inhalt ist geprüft. contentChild() ist jetzt gesetzt.
  6. ngAfterViewInit/Checked: Die eigene View und alle Kinder sind geprüft. viewChild() ist jetzt gesetzt.
  7. afterNextRender / afterEveryRender: Angular hat das DOM aller Komponenten geschrieben. Hier misst man Grössen oder startet eine Chart-Bibliothek. Sie laufen nicht bei SSR.
  8. ngOnDestroy / DestroyRef: Die Komponente wird entfernt. Hier räumt man Subscriptions, Timer und Listener auf.

3. Beispiel: Chart-Komponente mit Signal-Inputs und Render-Hooks

@Component({
  selector: 'app-chart',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<canvas #canvas></canvas>`,
})
export class Chart implements OnInit, OnDestroy {
  data   = input.required<number[]>();
  select = output<number>();
  canvas = viewChild.required<ElementRef<HTMLCanvasElement>>('canvas');
  private chart?: ChartLib;

  constructor() {
    console.log('constructor');               // Inputs noch nicht da
    afterNextRender({                         // einmal, nur im Browser
      write: () => { this.chart = new ChartLib(this.canvas().nativeElement); },
    });
    inject(DestroyRef).onDestroy(() => this.chart?.destroy());
    interval(5000).pipe(takeUntilDestroyed())  // ohne Argument: im Konstruktor erlaubt
      .subscribe(() => console.log('tick'));
    effect(() => this.chart?.update(this.data())); // reagiert auf Input-Signal
  }
  ngOnInit()    { console.log('ngOnInit', this.data().length); }
  ngOnDestroy() { console.log('ngOnDestroy'); }
}
Erwartetes Ergebnis (laut Doku, nicht ausgeführt), Parent mit data=[1,2,3], später entfernt:
constructor
ngOnInit 3
(afterNextRender: Chart wird gezeichnet)
tick            (alle 5 s)
ngOnDestroy
(DestroyRef-Callback: chart.destroy(); interval wird beendet)
  1. Im Konstruktor ist this.data() noch nicht lesbar. Bei input.required würde das sogar einen Fehler werfen (NG0950).
  2. afterNextRender braucht einen Injection Context, darum im Konstruktor. Die Phase write sagt: Hier wird das DOM geschrieben.
  3. takeUntilDestroyed() ohne Argument nutzt die aktuelle DestroyRef. Ausserhalb des Konstruktors muss man sie übergeben.
  4. effect läuft erneut, wenn sich data ändert. Er ersetzt hier ngOnChanges.

4. Details, die Interviewer fragen

  1. constructor vs ngOnInit: Der Konstruktor ist für DI und Felder. ngOnInit ist für Logik, die Inputs braucht.
  2. ngOnChanges: läuft nur bei neuen Referenzen von Template-Inputs. Ein mutiertes Array löst ihn nicht aus. Setzt Code den Input direkt, läuft er auch nicht.
  3. Signal-Inputs (input(), stabil seit v19): Der Input ist ein Signal. Abgeleitete Werte baut man mit computed(), nicht mit ngOnChanges.
  4. model(): ein schreibbarer Input für Two-Way-Binding [(value)]. Er ersetzt das Paar @Input value + @Output valueChange.
  5. output(): der neue Weg für Events. outputFromObservable() macht aus einem Observable einen Output.
  6. Signal Queries: viewChild(), viewChildren(), contentChild() liefern Signals. Kein {static: true} mehr nötig.
  7. afterNextRender: läuft einmal nach dem nächsten Rendern aller Komponenten. Gut für einmalige DOM-Initialisierung, z. B. eine Chart-Bibliothek.
  8. afterEveryRender: läuft nach jedem Rendern. In v20 umbenannt, in v17–v19 hiess es afterRender.
  9. Phasen: earlyRead, write, mixedReadWrite (Standard), read. Angular sortiert so alle Lese- und Schreibzugriffe und vermeidet Layout Thrashing, also erzwungenes Neuberechnen des Layouts.
  10. Kein SSR: Render-Callbacks laufen nicht auf dem Server und nicht beim Prerendering. Darum sind sie der sichere Ort für window und DOM-APIs.
  11. DestroyRef (seit v16): ein injizierbares Objekt mit onDestroy(callback). Es funktioniert auch in Services, Direktiven und Funktionen.
  12. takeUntilDestroyed (seit v16): RxJS-Operator, der beim Zerstören beendet. Er ersetzt das alte Muster mit destroy$ = new Subject().
  13. Angular 14: Dort gab es nur die Klassen-Hooks und @Input/@Output. Kein DestroyRef, kein afterNextRender, keine Signals.
  14. View Encapsulation: Standard ist Emulated. Angular fügt Attribute hinzu, damit Styles nur in der Komponente gelten. ShadowDom und None sind Alternativen.
  15. Content Projection: <ng-content select="header"> verteilt Inhalt in Slots. Projizierter Inhalt gehört zum Parent, nicht zur Komponente.

5. Vergleich

  • constructor: DI, Signals anlegen, Render-Hooks registrieren. Keine Inputs.
  • ngOnInit: einmal, Inputs bereit. Daten laden.
  • ngAfterViewInit: Queries bereit, DOM existiert. Aber State hier ändern gibt ExpressionChangedAfterItHasBeenCheckedError.
  • afterNextRender: DOM ist im Browser geschrieben. Sicher für DOM-Bibliotheken, läuft nie auf dem Server.
  • ngOnDestroy vs DestroyRef: gleiche Wirkung. DestroyRef ist auch ausserhalb von Klassen-Hooks nutzbar.
  • @Input vs input(): Dekorator-Feld vs Signal. Signal ist reaktiv, typisiert und passt zu computed.

6. In der Produktion

  1. Memory Leak: Subscriptions in Komponenten werden nie beendet. Speicher wächst bei jeder Navigation. Lösung: takeUntilDestroyed oder async-Pipe.
  2. ExpressionChangedAfterItHasBeenCheckedError: State wird in ngAfterViewInit geändert. Nur im Dev-Modus sichtbar. Lösung: Wert früher berechnen oder Signal nutzen.
  3. SSR-Absturz: window is not defined in ngOnInit. Lösung: DOM-Code in afterNextRender.
  4. Langsame Seiten durch ngDoCheck: Teure Logik läuft bei jedem Event. Lösung: computed oder OnPush.
  5. Input mutiert: Ein Array wird per push geändert. OnPush und ngOnChanges sehen nichts. Lösung: neue Referenz erzeugen.

7. Diagnose: Werkzeuge und Befehle

  • Angular DevTools: Komponentenbaum, Inputs, Outputs und Signals live ansehen. Der Profiler zeigt Zeit pro Hook.
  • Chrome DevTools Memory: Heap Snapshot vor und nach Navigation vergleichen. Detached DOM Nodes zeigen Leaks.
  • Dev-Modus: Die doppelte Prüfung findet ExpressionChanged…-Fehler.
  • ESLint (@angular-eslint): Regeln wie no-lifecycle-call und use-lifecycle-interface.
  • Migrationen: ng generate @angular/core:signal-input-migration, …:output-migration, …:signal-queries-migration.

8. Senior-Punkte

  1. Weniger Hooks, mehr Signals: computed statt ngOnChanges, Signal Queries statt ngAfterViewInit.
  2. DOM nur in Render-Hooks. Das macht Komponenten SSR-sicher und vermeidet Layout Thrashing.
  3. Aufräumen ist Pflicht: jede manuelle Subscription bekommt takeUntilDestroyed. Code-Review-Regel.
  4. Presentational Components ohne Hooks sind am einfachsten: nur Inputs, Outputs, computed.
  5. effect sparsam: nur für Seiteneffekte nach aussen (DOM-Bibliothek, Logging). State daraus ableiten ist ein Anti-Pattern.

9. Aus dem Projekt

„In den Angular-14-Dashboards bei CARIAD hatten Presentational Components nur Inputs und Outputs; Subscriptions mussten wir damals noch selbst beenden, weil es DestroyRef erst ab v16 gibt.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Inputs sind im Konstruktor verfügbar.“ → Falsch. Erst ab ngOnChanges/ngOnInit.
  • „ngOnChanges erkennt jede Änderung.“ → Falsch. Nur neue Referenzen über das Template.
  • „afterNextRender läuft nach dem Rendern dieser Komponente.“ → Falsch. Es läuft, wenn alle Komponenten gerendert sind.
  • „afterRender gibt es in v20.“ → Falsch. Es heisst dort afterEveryRender.
  • „ngAfterViewInit ist der richtige Ort für DOM-Bibliotheken.“ → Mit SSR nicht. afterNextRender ist sicherer.
  • „Die async-Pipe braucht manuelles Unsubscribe.“ → Falsch. Sie beendet selbst.

11. Fragen

Nennen Sie die Lifecycle Hooks in Reihenfolge.

constructor, ngOnChanges, ngOnInit, ngDoCheck, ngAfterContentInit, ngAfterContentChecked, ngAfterViewInit, ngAfterViewChecked, Render-Callbacks, ngOnDestroy.

Was gehört in den Konstruktor, was in ngOnInit?

Konstruktor: DI und Registrierung von Hooks. ngOnInit: Logik mit Inputs, z. B. Daten laden.

Wann läuft ngOnChanges?

Wenn sich ein Template-Input auf eine neue Referenz ändert. Der erste Aufruf kommt vor ngOnInit.

Was ist der Unterschied zwischen ngAfterContentInit und ngAfterViewInit?

Content ist projizierter Inhalt vom Parent. View ist das eigene Template. Content wird zuerst geprüft.

Was macht afterNextRender?

Es führt einen Callback einmal aus, nachdem alle Komponenten ins DOM gerendert haben. Nur im Browser.

Was ist afterEveryRender?

Wie afterNextRender, aber nach jedem Rendern. In v17–v19 hiess es afterRender.

Wozu dienen die Phasen earlyRead, write, mixedReadWrite, read?

Angular bündelt Lese- und Schreibzugriffe aufs DOM. So gibt es kein Layout Thrashing.

Warum laufen Render-Callbacks nicht auf dem Server?

Auf dem Server gibt es kein echtes DOM und kein Layout. Darum sind sie der Ort für Browser-Code.

Was ist DestroyRef?

Ein injizierbares Objekt mit onDestroy(callback). Es meldet das Ende eines Injector-Kontexts, auch in Services.

Wie beenden Sie Subscriptions in Angular 20?

Mit takeUntilDestroyed(), der async-Pipe oder toSignal(). In Angular 14 mit einem destroy$-Subject und takeUntil.

Warum braucht takeUntilDestroyed ausserhalb des Konstruktors ein Argument?

Ohne Argument ruft es inject(DestroyRef) auf. Das geht nur im Injection Context.

Was sind Signal-Inputs?

input() und input.required() liefern Inputs als Signals. Stabil seit v19, nutzbar mit computed und effect.

Was macht model()?

Ein schreibbarer Signal-Input für Two-Way-Binding mit [(x)]. Angular erzeugt das xChange-Event automatisch.

Was ist Content Projection?

Der Parent gibt Markup in die Komponente. ng-content mit select verteilt es auf Slots.

Was ist View Encapsulation?

Styles gelten nur in der Komponente. Emulated ist Standard, ShadowDom nutzt das echte Shadow DOM.

Was ist ExpressionChangedAfterItHasBeenCheckedError?

Ein Binding-Wert ändert sich nach der Prüfung. Angular erkennt das im Dev-Modus mit einem zweiten Durchlauf.

Warum ist ngDoCheck gefährlich?

Es läuft bei jeder Change Detection. Teure Logik dort bremst die ganze App.

Szenario: Der Speicher wächst bei jedem Wechsel zwischen zwei Seiten. Was prüfen Sie?

Offene Subscriptions, Intervals und Event-Listener. Heap Snapshots vergleichen. Lösung: takeUntilDestroyed, async-Pipe, DestroyRef.

Szenario: Mit SSR stürzt der Server mit „window is not defined“ ab. Lösung?

Browser-Code aus ngOnInit in afterNextRender verschieben. Oder Plattform mit isPlatformBrowser prüfen.

Szenario: Eine OnPush-Tabelle zeigt neue Zeilen nicht an. Warum?

Das Array wurde mutiert, die Referenz blieb gleich. Lösung: neues Array erzeugen oder ein Signal setzen.
