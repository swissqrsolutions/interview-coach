Routing, Guards, Resolver, Lazy Loading

Kern: Der Router bildet eine URL auf eine Komponente ab, ohne die Seite neu zu laden. Guards entscheiden, ob eine Navigation erlaubt ist, und Resolver laden Daten vorher. Lazy Loading lädt den Code einer Route erst, wenn sie gebraucht wird, und die Grundlagen sind seit Angular 14 gleich, während Angular 22 einige Defaults ändert.

Antwort-Muster

Frage: Wie funktioniert der Router und wie schützt man eine Route?

  1. Mechanismus: Der Router vergleicht die URL mit dem Routes-Array. Dann lädt er lazy Code, prüft Guards, führt Resolver aus und aktiviert die Komponente im router-outlet.
  2. Zahl: canMatch ersetzt das deprecated canLoad seit v15.1. Seit v22 erben Kind-Routen Parameter mit 'always'.
  3. Trade-off: Guards sind nur UX, denn Code im Browser ist umgehbar. Resolver warten auf Daten, aber die UI wirkt dann eingefroren.
  4. Produktion: Autorisierung gehört ins Backend, der Guard leitet nur um. Alle Features lade ich lazy, damit der Initial-Chunk klein bleibt.

1. Die Reise einer Navigation

  1. Start: Der Nutzer klickt auf „Report 42“. Der Router feuert NavigationStart.
  2. Matching: Der Router sucht die erste passende Route. redirectTo und canMatch wirken hier. canMatch false heisst: nächste Route probieren.
  3. Lazy laden: Hat die Route loadChildren oder loadComponent, lädt der Browser jetzt den Chunk.
  4. Guards: Zuerst canDeactivate der alten Route, dann canActivateChild und canActivate. Jeder gibt true, false, einen UrlTree oder RedirectCommand zurück.
  5. Resolver: laden Daten. Der Router wartet, bis alle fertig sind.
  6. Aktivieren: Die Komponente entsteht im router-outlet. Parameter und Resolver-Daten kommen als Inputs.
  7. Ende: NavigationEnd. Die URL in der Adresszeile ist aktualisiert.

2. Aufbau

  1. URL: Der Nutzer öffnet /reports/42 oder klickt einen routerLink.
  2. Router: wird mit provideRouter(routes) registriert. Er vergleicht die URL mit dem Routes-Array.
  3. Routes: Jede Route hat path, Ziel (component, loadComponent, loadChildren) und optional Guards und Resolver.
  4. router-outlet: der Platz im Template, an dem die Ziel-Komponente erscheint.
  5. Daten in die Komponente: klassisch über ActivatedRoute. Mit withComponentInputBinding() direkt als Inputs.

3. Details, die Interviewer fragen

  1. Guard-Typen: canActivate fragt, ob man rein darf. canActivateChild gilt für Kinder. canDeactivate fragt, ob man raus darf. canMatch fragt, ob diese Route überhaupt passen darf.
  2. canMatch vs canActivate: Bei canMatch false probiert der Router die nächste Route. Er lädt den lazy Code nicht. Das passt für Rollen-Varianten derselben URL. Es ersetzt das deprecated canLoad.
  3. Funktionale Guards: Sie sind seit v14.2 möglich und seit v15.2 empfohlen. Klassen- und InjectionToken-Guards sind seitdem deprecated. In Angular 14 waren Klassen mit CanActivate-Interface üblich. Alte Klassen-Guards bindet man mit mapToCanActivate ein.
  4. RedirectCommand (seit v18): Guards und Resolver geben es für Redirects mit Navigationsoptionen zurück, z. B. skipLocationChange.
  5. Resolver: Die Navigation wartet auf die Daten. Der Vorteil ist, dass keine halbe Seite erscheint. Der Nachteil ist, dass die UI eingefroren wirkt. Eine Alternative ist das Laden in der Komponente mit Skeleton.
  6. Resolver-Fehler: Ein Fehler bricht die Navigation ab (NavigationError). Darum nutzt man im Resolver catchError mit Redirect oder Ersatzwert.
  7. loadChildren vs loadComponent: loadChildren lädt ein Routes-Array, also ein Feature. loadComponent lädt eine einzelne Komponente.
  8. Preloading: withPreloading(PreloadAllModules) lädt lazy Chunks im Hintergrund nach dem Start. Eigene Strategien sind möglich, z. B. nur markierte Routen.
  9. withComponentInputBinding (seit v16): Es gibt Route-Daten als Inputs. Das ist weniger Code als ActivatedRoute und einfacher zu testen. Seit v22 hat es Optionen, z. B. queryParams (Standard true) und unmatchedInputBehavior.
  10. paramMap als Observable: Navigiert man von /reports/1 zu /reports/2, wird die Komponente wiederverwendet. Ein einmaliger snapshot-Wert ist dann veraltet.
  11. title: Routen können einen Seitentitel setzen. Eigene Logik schreibt man mit einer TitleStrategy.
  12. Weitere Features: Es gibt withViewTransitions(), withHashLocation() und withRouterConfig({...}).
  13. paramsInheritanceStrategy: Seit v22 ist der Standard 'always'. Kind-Routen erben dann Parameter aller Eltern. Bis v21 war es 'emptyOnly'. Wer das alte Verhalten will, setzt es in withRouterConfig. Es gibt keine automatische Migration.
  14. v22-Änderungen: CanMatchFn bekommt als dritten Parameter den currentSnapshot. Bei Klassen ist er jetzt Pflicht. provideRoutes() wurde entfernt. routerLink hat ein neues Input browserUrl.
  15. Route-Providers: providers an einer Route erzeugen einen Environment-Injector für das Feature.

4. Fallen

  • „Guards schützen meine Daten.“ → Falsch. Code im Browser ist umgehbar. Das Backend schützt.
  • „canActivate verhindert das Laden des lazy Codes.“ → Falsch. Das macht canMatch.
  • „Im Guard router.navigate() aufrufen und false zurückgeben.“ → Schlecht. Einen UrlTree oder RedirectCommand zurückgeben.
  • „Die Komponente wird bei jedem Parameterwechsel neu erstellt.“ → Falsch. Gleiche Route, gleiche Instanz.
  • „canLoad ist der Standard.“ → Veraltet seit v15.1. canMatch nutzen.
  • „Kind-Routen sehen nur ihre eigenen Parameter.“ → Seit v22 falsch. Der Standard ist paramsInheritanceStrategy: 'always'.

5. Selbsttest

Warum?

Warum snapshot nicht immer reicht?

Bei Parameterwechsel auf derselben Route bleibt die Komponente. Der Snapshot ist dann veraltet.

Was passiert, wenn ein Resolver fehlschlägt?

Die Navigation bricht mit NavigationError ab. Darum Fehler im Resolver abfangen.

Warum schützen Guards keine Daten?

Der Code läuft im Browser und ist umgehbar. Ein Guard ist nur UX. Das Backend muss jede Anfrage prüfen.

Wie innen?

Wie registriert man den Router in Angular 22?

Mit provideRouter(routes, ...features) in der appConfig. Früher RouterModule.forRoot.

Was ist ein Guard?

Eine Funktion, die entscheidet, ob eine Navigation erlaubt ist. Rückgabe: boolean, UrlTree oder RedirectCommand, auch als Observable oder Promise.

Welche Guard-Typen gibt es?

canActivate, canActivateChild, canDeactivate, canMatch. Dazu resolve für Daten.

Was ist ein funktionaler Guard?

Eine Funktion vom Typ CanActivateFn. Abhängigkeiten holt sie mit inject().

Wie lädt man eine Route lazy?

loadComponent für eine Komponente, loadChildren für ein Routes-Array. Beide mit dynamischem import().

Was macht withComponentInputBinding?

Es bindet Pfad- und Query-Parameter, data und Resolver-Ergebnisse an gleichnamige Inputs.

Was ist ein UrlTree?

Eine geparste URL. Gibt ein Guard ihn zurück, leitet der Router dorthin um.

Wozu pathMatch: 'full'?

Die ganze URL muss passen. Bei leerem Pfad mit redirectTo ist es Pflicht.

Welche Router-Events kennen Sie?

NavigationStart, RoutesRecognized, GuardsCheckEnd, ResolveEnd, NavigationEnd, NavigationCancel, NavigationError.

Zahlen

Was ändert Angular 22 am Router?

paramsInheritanceStrategy ist jetzt 'always', CanMatchFn hat einen dritten Parameter currentSnapshot, provideRoutes() ist entfernt, withComponentInputBinding hat Optionen.

Seit wann gibt es funktionale Guards, canMatch und RedirectCommand?

Funktionale Guards sind seit v14.2 möglich und seit v15.2 empfohlen. canMatch ersetzt canLoad seit v15.1. RedirectCommand gibt es seit v18.

Vergleich

canMatch vs canActivate?

canMatch wirkt beim Matching. Bei false probiert der Router die nächste Route und lädt den Code nicht.

Wie bindet man alte Klassen-Guards ein?

Mit mapToCanActivate([AuthGuard]) oder einer Funktion, die inject(AuthGuard).canActivate() aufruft.

Was ist ein Resolver?

Eine Funktion, die Daten vor der Aktivierung lädt. Die Navigation wartet darauf.

Produktion

Szenario: Nach einem Deployment melden Nutzer „Loading chunk failed“. Was tun Sie?

Alte Chunks einige Zeit weiter ausliefern. Den Fehler global abfangen und die Seite neu laden.

Szenario: Admins und Nutzer sollen unter /dashboard verschiedene Seiten sehen. Wie?

Zwei Routen mit gleichem Pfad und canMatch nach Rolle. Nur der passende Code wird geladen.

Szenario: Beim Wechsel von Report 1 zu Report 2 bleibt der alte Inhalt. Warum?

Die Komponente liest den Snapshot einmal. Lösung: Input-Binding mit Signal-Input oder paramMap abonnieren.

Design

Was ist Preloading?

Lazy Chunks werden nach dem Start im Hintergrund geladen. withPreloading(PreloadAllModules) oder eine eigene Strategie.

Wie setzt man den Seitentitel pro Route?

Mit der title-Eigenschaft der Route oder einer eigenen TitleStrategy.

Mehr

Gerüst

  • Warum? Der Router macht aus einer URL eine Seite ohne Reload. Lazy Routes halten den Initial-Chunk klein.
  • Wie innen? Matching, Lazy-Chunk laden, Guards, Resolver, Aktivieren. Ein UrlTree als Rückgabe ist ein sauberer Redirect.
  • Zahlen canLoad ist seit v15.1 deprecated, canMatch ersetzt es. Funktionale Guards seit v14.2. Seit v22 ist paramsInheritanceStrategy: 'always'.
  • Vergleich canMatch wirkt beim Matching und lädt Code nicht. canActivate kommt danach. Resolver warten, Laden in der Komponente nicht.
  • Produktion Endlos-Redirect, wenn die Login-Route selbst einen Guard hat. Ein Snapshot ist bei Parameterwechsel veraltet. „Loading chunk failed“ nach Deployment.
  • Design Jedes Feature lazy. Guards sind UX, Security gehört ins Backend. Input-Binding statt ActivatedRoute.

Beispiel: Routen mit funktionalen Guards, Resolver und Input-Binding

// app.config.ts
provideRouter(routes, withComponentInputBinding(), withPreloading(PreloadAllModules))

// auth.guard.ts
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  return auth.isLoggedIn()
    ? true
    : inject(Router).createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

export const unsavedGuard: CanDeactivateFn<ReportEdit> = c =>
  c.dirty() ? confirm('Änderungen verwerfen?') : true;

export const reportResolver: ResolveFn<Report> = route =>
  inject(ReportApi).get(route.paramMap.get('id')!);

// app.routes.ts
export const routes: Routes = [
  { path: 'login', loadComponent: () => import('./login/login') },  // default export
  { path: 'reports', canActivate: [authGuard],
    loadChildren: () => import('./reports/reports.routes').then(m => m.REPORT_ROUTES) },
  { path: '', redirectTo: 'reports', pathMatch: 'full' },
  { path: '**', loadComponent: () => import('./not-found') },
];

// reports/reports.routes.ts
export const REPORT_ROUTES: Routes = [
  { path: ':id', component: ReportDetail, resolve: { report: reportResolver },
    title: 'Report' },
  { path: ':id/edit', component: ReportEdit, canDeactivate: [unsavedGuard] },
];

// report-detail.ts
export class ReportDetail {
  id     = input.required<string>();   // aus :id
  report = input.required<Report>();   // aus resolve.report
}
Erwartetes Ergebnis (laut Doku, nicht ausgeführt):
- Nicht eingeloggt, /reports/42 → Redirect auf /login?returnUrl=%2Freports%2F42
- Eingeloggt, /reports/42 → Chunk "reports.routes" wird geladen,
  GET /api/reports/42, danach erscheint ReportDetail mit id="42" und report gesetzt.
- /reports/42/edit verlassen mit dirty=true → confirm-Dialog; "Abbrechen" → NavigationCancel.
- /gibtsnicht → NotFound-Komponente.
- ng build listet reports.routes, login und not-found als "Lazy chunk files".
  1. Funktionale Guards sind normale Funktionen. inject() geht darin, weil der Router sie im Injection Context ausführt.
  2. Ein UrlTree als Rückgabe ist besser als router.navigate() im Guard. Der Router behandelt es als sauberen Redirect.
  3. withComponentInputBinding() bindet Pfad-Parameter, Query-Parameter, data und Resolver-Ergebnisse an gleichnamige Inputs.
  4. loadComponent mit Default-Export braucht kein .then().
  5. pathMatch: 'full' ist bei leerem Pfad Pflicht, sonst passt der Redirect auf alles.

Vergleich

  • canActivate vs canMatch: nach dem Matching prüfen vs schon beim Matching; canMatch verhindert auch das Laden des Codes.
  • Resolver vs Laden in der Komponente: fertige Daten beim Anzeigen vs schnelle Navigation mit Ladezustand.
  • loadChildren vs loadComponent: Feature mit vielen Routen vs eine einzelne Seite.
  • ActivatedRoute vs Input-Binding: Observable und Snapshot vs Signal-Inputs ohne Router-Abhängigkeit.
  • Funktionaler Guard vs Klassen-Guard: weniger Code und inject() vs Klasse mit Interface (v14-Stil).

In der Produktion

  1. Endlos-Redirect: Guard leitet auf /login, das selbst den Guard hat. Lösung: Login-Route ohne Guard.
  2. Daten wechseln nicht: Komponente liest snapshot.paramMap, Router verwendet sie wieder. Lösung: Input-Binding oder paramMap-Observable.
  3. „Loading chunk failed“ nach Deployment: Alte Seite fordert alten Chunk an, der nicht mehr existiert. Lösung: alte Chunks eine Zeit behalten, Fehler abfangen und neu laden.
  4. Weisse Seite bei langsamer API: Resolver wartet. Lösung: Ladeanzeige über Router-Events oder Laden in der Komponente.
  5. Sicherheit nur im Frontend: Guards sind UX, kein Schutz. Lösung: Backend prüft jede Anfrage.
  6. Riesiger Initial-Chunk: Features eager importiert. Lösung: alle Features lazy.

Diagnose: Werkzeuge und Befehle

  • withDebugTracing(): loggt alle Router-Events in die Konsole.
  • inject(Router).events.pipe(filter(e => e instanceof NavigationError)): Fehler zentral loggen.
  • Angular DevTools, Router Tree: zeigt die aktive Routen-Struktur.
  • ng build: Liste der Lazy Chunks und ihre Grösse.
  • Network-Tab: prüfen, wann ein Chunk geladen wird.

Senior-Punkte

  1. Jedes Feature lazy, mit eigenem Routes-Array. Das ist die wichtigste Bundle-Massnahme.
  2. Guards sind UX, nicht Security. Autorisierung gehört ins Backend.
  3. Resolver bewusst einsetzen: für kleine, kritische Daten. Grosse Listen besser in der Komponente laden.
  4. Input-Binding macht Komponenten unabhängig vom Router und leicht testbar.
  5. Deployment-Strategie für Chunks: alte Dateien behalten oder Service Worker, sonst brechen offene Tabs.
