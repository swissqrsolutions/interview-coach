Reactive, Template und Signal Forms

Angular · Tier 1 · Quellen: angular.dev (v22) Guides „Forms overview“, „Reactive forms“, „Typed forms“, „Template-driven forms“, „Validating form input“; API FormControl, FormGroup, FormRecord, NonNullableFormBuilder, AsyncValidatorFn; angular.dev „Signal Forms“ (Overview, Models, Validation), API form, FormField (stabil seit v22); Angular-CHANGELOG

Kern: Angular hat zwei klassische Formular-Ansätze. Reactive Forms bauen das Formular-Modell im TypeScript-Code und binden es ans Template; Template-driven Forms erzeugen das Modell aus Direktiven wie ngModel im Template. Seit v14 sind Reactive Forms typisiert. Der dritte Ansatz, Signal Forms, kam in v21 experimentell und ist seit Angular 22 stabil.

1. Wo sitzt das Formular-Modell?

  1. Reactive: Das Modell (FormGroup, FormControl) steht im Code. Das Template verbindet sich mit [formGroup] und formControlName.
  2. Template-driven: Direktiven im Template (ngModel, required) erzeugen das Modell. Es entsteht asynchron nach dem ersten Rendern.
  3. ControlValueAccessor (CVA): die Brücke zwischen Control und DOM-Element. Beide Ansätze nutzen sie. Eigene Inputs implementieren das Interface.
  4. Daten: Reactive arbeitet unveränderlich mit value. Template-driven schreibt per Two-Way-Binding direkt ins Datenobjekt.
  5. Signal Forms (v22): Das Modell ist ein signal(). form(model, schema) baut daraus einen Feldbaum; das Template bindet Felder mit [formField].

2. Die Reise einer Eingabe (die Geschichte zum Merken)

  1. Tippen: Der Nutzer tippt eine E-Mail. Das DOM feuert input. Mit updateOn: 'blur' erst beim Verlassen.
  2. CVA: Der DefaultValueAccessor ruft onChange. Das Control bekommt den neuen Wert.
  3. Sync-Validatoren: required, email und eigene laufen sofort. Ergebnis: null oder ein Fehlerobjekt.
  4. Async-Validatoren: laufen nur, wenn alle sync-Validatoren bestanden sind. Während sie laufen, ist der Status PENDING.
  5. Status: Das Control ist VALID, INVALID, PENDING oder DISABLED. Dazu dirty/pristine und touched/untouched.
  6. Nach oben: Die Parent-FormGroup berechnet Wert und Status neu. Gruppen-Validatoren laufen jetzt.
  7. Events: valueChanges, statusChanges und seit v18 events melden die Änderung.

3. Beispiel: typisiertes Formular mit Sync-, Gruppen- und Async-Validator

const samePassword: ValidatorFn = g =>
  g.get('pw')?.value === g.get('pw2')?.value ? null : { mismatch: true };

@Component({
  selector: 'app-register',
  imports: [ReactiveFormsModule],
  template: `
  <form [formGroup]="form" (ngSubmit)="save()">
    <input formControlName="email">
    @if (form.controls.email.hasError('emailTaken')) { <p>E-Mail vergeben</p> }
    <input type="password" formControlName="pw">
    <input type="password" formControlName="pw2">
    <button [disabled]="form.invalid || form.pending">Speichern</button>
  </form>`,
})
export class Register {
  private fb = inject(NonNullableFormBuilder);
  private api = inject(UserApi);
  form = this.fb.group({
    email: this.fb.control('', {
      validators: [Validators.required, Validators.email],
      asyncValidators: [c => this.api.exists(c.value).pipe(map(e => e ? { emailTaken: true } : null))],
      updateOn: 'blur' }),
    pw:  ['', [Validators.required, Validators.minLength(12)]],
    pw2: [''],
  }, { validators: samePassword });

  save() {
    const v = this.form.getRawValue();   // Typ: { email: string; pw: string; pw2: string }
    console.log(v, this.form.status);
  }
}

// Dasselbe Feld als Signal Form (Angular 22, stabil; in v21 experimentell)
import { form, FormField, required, email, minLength, validateHttp } from '@angular/forms/signals';

model = signal({ email: '', pw: '' });
reg = form(this.model, p => {
  required(p.email); email(p.email);
  required(p.pw); minLength(p.pw, 12);
  validateHttp(p.email, {
    request: ({ value }) => `/api/users/exists?email=${value()}`,
    onSuccess: (taken: boolean) => taken ? { kind: 'emailTaken' } : null,
    onError: () => ({ kind: 'networkError' }),
  });
});
// Template: <input [formField]="reg.email">  ·  reg.email().errors()  ·  reg().invalid()
  1. Der NonNullableFormBuilder macht alle Controls non-nullable. reset() setzt auf den Startwert zurück, nicht auf null.
  2. Ein Async-Validator läuft nur, wenn die sync-Validatoren bestehen. Das spart Requests.
  3. updateOn: 'blur' verhindert einen Request pro Tastendruck.
  4. Gruppen-Validatoren setzen Fehler an der Gruppe. Das Template muss form.errors prüfen.
  5. Der Async-Validator nutzt this.api aus einem Feld. Ein inject() direkt im Validator würde zur Laufzeit NG0203 werfen.
  6. Signal Forms: Fehler sind Objekte mit kind und optional message. validateHttp läuft erst, wenn die sync-Regeln bestehen; dazwischen ist pending() true.

4. Details, die Interviewer fragen

  1. Typed Forms (seit v14): FormControl<string | null> ist der Standard-Typ. null kommt dazu, weil reset() auf null setzt.
  2. nonNullable: new FormControl('', { nonNullable: true }) oder fb.nonNullable. Dann ist der Typ nur string.
  3. UntypedFormGroup: Die Migration nach v14 hat alte Formulare auf UntypedFormGroup umgestellt. Neue Formulare sollten typisiert sein.
  4. FormRecord: eine Gruppe mit dynamischen Schlüsseln gleichen Typs. FormArray für Listen.
  5. value vs getRawValue(): value lässt disabled Controls weg. getRawValue() enthält alle.
  6. Eigener Validator: eine Funktion (control) => ValidationErrors | null. Wiederverwendbar und einfach testbar.
  7. Async-Validator: liefert ein Observable oder Promise. Das Observable muss enden. Bei neuer Eingabe beendet Angular die alte Prüfung.
  8. updateOn: 'change' (Standard), 'blur', 'submit'. Steuert, wann Wert und Validierung aktualisiert werden.
  9. Control-Events (seit v18): control.events liefert ValueChangeEvent, StatusChangeEvent, TouchedChangeEvent, PristineChangeEvent, FormSubmittedEvent, FormResetEvent.
  10. setValue vs patchValue: setValue braucht alle Felder, patchValue nur einen Teil. emitEvent: false unterdrückt valueChanges.
  11. ControlValueAccessor: vier Methoden: writeValue, registerOnChange, registerOnTouched, setDisabledState. Registriert mit NG_VALUE_ACCESSOR.
  12. Template-driven: FormsModule, [(ngModel)], #f="ngForm". Gut für kleine Formulare. Schwer testbar ohne DOM.
  13. Signal Forms: In Angular 20 gibt es sie nicht. In v21 experimentell, seit v22 stabil. Paket @angular/forms/signals, Funktion form(model, schema) auf einem signal(), Direktive FormField mit [formField], Regeln wie required, email, validateHttp. Feldzustand als Signals: value(), errors(), touched(), pending().
  14. Absenden bei Signal Forms: submit(form, { action }) führt die Aktion aus; Server-Fehler kommen als ValidationError zurück ans Feld. Parallele Submits sind verboten.
  15. v22-Breaking-Change: Die Validatoren min/max akzeptieren keine Strings mehr, nur Zahlen oder null.

5. Vergleich

  • Reactive: Modell im Code, synchron verfügbar, unveränderlich, typisiert, gut testbar. Für komplexe und dynamische Formulare.
  • Template-driven: Modell aus dem Template, asynchron, mutiert Daten. Wenig Code für einfache Formulare.
  • Signal Forms (stabil seit v22): Modell ist ein Signal, Zustand als Signals, Validierung als Schema. Kein valueChanges, kein Subscribe. Für Angular 20 nicht verfügbar.
  • Sync- vs Async-Validator: sofort vs nach Server-Antwort, Status PENDING dazwischen.
  • Control- vs Gruppen-Validator: ein Feld vs Regeln über mehrere Felder.

6. In der Produktion

  1. Server-Last durch Async-Validator: Request pro Tastendruck. Lösung: updateOn: 'blur' oder Debounce im Validator.
  2. Formular bleibt PENDING: Async-Validator-Observable endet nie. Lösung: take(1) oder first().
  3. Fehlende Felder beim Speichern: disabled Controls fehlen in value. Lösung: getRawValue().
  4. Endlosschleife: valueChanges ruft setValue auf demselben Control. Lösung: emitEvent: false.
  5. Typfehler nach v14-Upgrade: viele UntypedFormGroup. Lösung: Formular für Formular typisieren.
  6. Doppelte Submits: Button nicht gesperrt. Lösung: form.pending prüfen und exhaustMap.

7. Diagnose: Werkzeuge und Befehle

  • <pre>{{ form.getRawValue() | json }} {{ form.status }}</pre>: Zustand im Dev-Modus anzeigen.
  • form.events.subscribe(console.log): alle Änderungen eines Formulars sehen (v18+).
  • Angular DevTools: Komponenten-State und Formular-Objekte ansehen.
  • Unit-Tests für Validatoren ohne TestBed: expect(samePassword(group)).toEqual({ mismatch: true }).
  • Network-Tab: Anzahl der Requests eines Async-Validators prüfen.

8. Senior-Punkte

  1. Reactive Forms als Standard für Business-Apps. Template-driven nur für sehr einfache Formulare.
  2. Immer typisiert und nonNullable. Das findet Fehler beim Build statt in Produktion.
  3. Validierung doppelt: Frontend für UX, Backend für Wahrheit und Sicherheit.
  4. Eigene Inputs per ControlValueAccessor statt Hacks mit @Output. Dann funktionieren Validatoren und Status.
  5. Signal Forms für neue Formulare ab v22 (stabil). Bestehende Reactive Forms nicht umschreiben, solange sie funktionieren; Reactive Forms bleiben unterstützt.

10. Fallen

  • „Ein Async-Validator läuft immer.“ → Falsch. Nur wenn alle sync-Validatoren bestehen.
  • „form.value enthält alle Felder.“ → Falsch. Disabled Controls fehlen. getRawValue() nutzen.
  • „FormControl<string> ist der Standard-Typ.“ → Falsch. string | null, ausser mit nonNullable.
  • „Signal Forms gibt es in Angular 20.“ → Falsch. Erst ab v21 (experimentell), stabil seit v22.
  • „Signal Forms sind noch experimentell.“ → Seit v22 falsch. form() und FormField sind stabil.
  • „Template-driven Forms sind synchron.“ → Falsch. Die Controls entstehen nach dem Rendern.
  • „Frontend-Validierung reicht.“ → Falsch. Das Backend muss immer prüfen.

11. Fragen

Was ist der Unterschied zwischen Reactive und Template-driven Forms?

Reactive: Modell im Code, synchron, unveränderlich. Template-driven: Modell aus Direktiven, asynchron, mutiert Daten.

Wann nehmen Sie welche?

Reactive für komplexe, dynamische, getestete Formulare. Template-driven für kleine, einfache Formulare.

Was sind Typed Forms?

Seit v14 haben Controls einen Werttyp. Fehler wie falsche Feldnamen findet der Compiler.

Warum ist der Typ string | null?

reset() setzt ein Control standardmässig auf null. Mit nonNullable setzt es auf den Startwert.

Was ist der NonNullableFormBuilder?

Ein FormBuilder, der alle Controls non-nullable erzeugt. Zugriff auch über fb.nonNullable.

Was ist ein FormRecord?

Eine FormGroup mit dynamischen Schlüsseln gleichen Typs.

Wie schreibt man einen eigenen Validator?

Eine Funktion, die ein Control nimmt und null oder ein Fehlerobjekt liefert.

Wie validiert man zwei Felder zusammen?

Mit einem Validator auf der FormGroup. Der Fehler steht dann an der Gruppe.

Wie funktioniert ein Async-Validator?

Er liefert Observable oder Promise mit null oder Fehlern. Er läuft nach den sync-Validatoren, dazwischen ist der Status PENDING.

Wie verhindert man zu viele Requests eines Async-Validators?

updateOn: 'blur' oder Debounce. Das Observable muss enden.

value vs getRawValue?

value ohne disabled Controls, getRawValue mit allen.

setValue vs patchValue?

setValue braucht die komplette Struktur. patchValue setzt nur angegebene Felder.

Was ist ein ControlValueAccessor?

Die Brücke zwischen Control und UI-Element. Eigene Inputs implementieren writeValue, registerOnChange, registerOnTouched, setDisabledState.

Welche Status hat ein Control?

VALID, INVALID, PENDING, DISABLED. Dazu dirty/pristine und touched/untouched.

Was bringt control.events?

Seit v18 ein Strom aller Änderungen: Wert, Status, touched, pristine, submit, reset.

Was sind Signal Forms?

Ein Formular-API auf Basis von Signals im Paket @angular/forms/signals. Experimentell in v21, stabil seit v22, nicht in Angular 20.

Wie bindet man ein Signal-Forms-Feld ans Template?

Mit der Direktive FormField: <input [formField]="loginForm.email">. Den Wert liest man mit loginForm.email().value().

Szenario: Beim Speichern fehlt das Feld „Kundennummer“. Warum?

Das Control ist disabled und fehlt in value. Lösung: getRawValue().

Szenario: Der Speichern-Button bleibt grau, obwohl alles gültig aussieht. Warum?

Ein Async-Validator endet nicht, der Status bleibt PENDING. Lösung: Observable mit take(1) beenden.

Szenario: Sie migrieren 50 Formulare von Angular 14 nach 22. Wie?

Zuerst UntypedFormGroup schrittweise typisieren und nonNullable nutzen. Neue Formulare in Signal Forms (stabil seit v22), alte nur bei Bedarf umstellen.
