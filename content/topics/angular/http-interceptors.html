HttpClient und Interceptors

Kern: HttpClient ist Angulars Dienst für HTTP-Requests; er liefert typisierte, cold Observables. Ein Interceptor ist eine Funktion in der Kette zwischen HttpClient und Netzwerk, die jeden Request und jede Antwort sehen und ändern kann. Typische Aufgaben: Auth-Token anhängen, Fehler zentral behandeln, Retry, Logging, Ladeanzeige. In Angular 22 sendet HttpClient standardmässig über fetch.

1. Wo sitzen die Interceptors?

  1. Service: ruft http.get<T>(url) auf. Das ergibt ein cold Observable.
  2. HttpClient: baut beim Subscribe ein unveränderliches HttpRequest-Objekt.
  3. Interceptors: laufen in der Reihenfolge aus withInterceptors([...]). Jeder ruft next(req) für den nächsten.
  4. Backend-Handler: sendet seit v22 über fetch (Standard). XHR gibt es mit withXhr(). Bis v21 war XHR Standard und fetch kam mit withFetch().
  5. Antwort: läuft in umgekehrter Reihenfolge zurück, weil jeder Interceptor das Observable von next umhüllt.

2. Die Reise eines Requests mit abgelaufenem Token (die Geschichte zum Merken)

  1. Subscribe: Der Report-Service abonniert GET /api/reports. Erst jetzt startet die Kette.
  2. Auth-Interceptor: HttpRequest ist unveränderlich. Darum req.clone({ setHeaders: { Authorization: 'Bearer …' } }).
  3. Server: antwortet mit 401, das Token ist abgelaufen.
  4. catchError: Der Interceptor sieht den HttpErrorResponse mit status === 401.
  5. Refresh: Er holt ein neues Token. Laufen mehrere Requests gleichzeitig, teilen sie sich einen Refresh (geteiltes Observable).
  6. Wiederholen: Mit switchMap sendet er den Request mit neuem Token erneut über next().
  7. Erfolg: Der Service merkt nichts vom Umweg. Scheitert der Refresh: Logout und Fehler weiterwerfen.

3. Beispiel: Auth-, Fehler- und Retry-Interceptor

// app.config.ts (Angular 22: fetch ist Standard, withFetch() ist deprecated)
provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]))

export const SKIP_AUTH = new HttpContextToken<boolean>(() => false);

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.context.get(SKIP_AUTH)) return next(req);
  const token = inject(AuthService).token();
  const authReq = token ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : req;
  return next(authReq);
};

export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);
  const notify = inject(Notifier);
  return next(req).pipe(
    retry({
      count: req.method === 'GET' ? 2 : 0,            // nur idempotente Requests
      delay: (err, n) => err.status >= 500 || err.status === 0
        ? timer(300 * 2 ** n)                          // Backoff: 600, 1200 ms
        : throwError(() => err),                       // 4xx: nicht wiederholen
    }),
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) router.navigate(['/login']);
      else if (err.status === 0) notify.error('Keine Verbindung');
      else if (err.status >= 500) notify.error('Serverfehler, bitte später erneut');
      return throwError(() => err);                   // Aufrufer entscheidet weiter
    }),
  );
};

// Aufruf ohne Token
http.get('/public/info', { context: new HttpContext().set(SKIP_AUTH, true) });

  1. Funktionale Interceptors laufen im Injection Context. inject() ist darin erlaubt.
  2. HttpContextToken trägt Metadaten pro Request, z. B. „kein Token“. Besser als URL-Listen im Interceptor.
  3. retry abonniert next(req) neu, also läuft der Request wirklich erneut. Nur GET, weil POST nicht idempotent ist.
  4. status === 0 heisst: keine Antwort vom Server, z. B. Netzwerk weg oder CORS.
  5. Der Fehler wird weitergeworfen. Ein Interceptor soll Fehler nicht stillschweigend schlucken.

4. Details, die Interviewer fragen

  1. provideHttpClient (seit v15): ersetzt HttpClientModule, das seit v18 deprecated ist. Seit v21 ist HttpClient auch ohne provideHttpClient() injizierbar; man braucht es nur für Features wie Interceptors.
  2. Funktionale Interceptors (seit v15): HttpInterceptorFn = (req, next) => Observable<HttpEvent>. Angular empfiehlt sie, weil die Reihenfolge klarer ist.
  3. Klassen-Interceptors (Angular-14-Stil): implements HttpInterceptor, registriert mit HTTP_INTERCEPTORS und multi: true. Mit Standalone braucht man withInterceptorsFromDi().
  4. Reihenfolge: Request in Listen-Reihenfolge, Antwort umgekehrt. Auth vor Logging, Fehlerbehandlung möglichst aussen.
  5. Unveränderlich: HttpRequest und HttpHeaders sind immutable. Ändern nur mit clone().
  6. Cold: Kein Subscribe, kein Request. Zwei Subscribes, zwei Requests.
  7. Abbruch: Unsubscribe bricht den laufenden Request ab. Das nutzt switchMap.
  8. observe und Fortschritt: observe: 'response' liefert Header und Status. observe: 'events' liefert Fortschritts-Events. Seit v22 ist reportProgress deprecated; neu sind reportUploadProgress und reportDownloadProgress.
  9. fetch vs XHR: Seit v22 ist FetchBackend der Standard, withFetch() ist deprecated. withXhr() schaltet auf XHR zurück, z. B. für Upload-Fortschritt, den fetch nicht kann. Die ng update-Migration ergänzt withXhr(), wo vorher kein withFetch() stand.
  10. Transfer Cache bei SSR: GET-Antworten vom Server werden ins HTML gelegt. Der Browser fragt nicht doppelt. Konfigurierbar mit withHttpTransferCacheOptions.
  11. XSRF: HttpClient liest das Cookie XSRF-TOKEN und sendet den Header X-XSRF-TOKEN. Konfiguration mit withXsrfConfiguration.
  12. Tests: provideHttpClientTesting() und HttpTestingController: expectOne(url).flush(data), am Ende verify().
  13. httpResource: ein signalbasiertes API zum Laden von Daten. Experimentell seit 19.2, stabil seit v22. Es läuft auch durch die Interceptors.

5. Vergleich

  • Funktional vs Klasse: withInterceptors([fn]) mit klarer Reihenfolge vs HTTP_INTERCEPTORS mit DI-Reihenfolge.
  • Interceptor vs Service-Wrapper: Interceptor gilt für alle Requests. Ein Wrapper nur für die, die ihn nutzen.
  • retry vs Retry im Backend-Client: Frontend-Retry nur für idempotente Lesezugriffe und kurze Störungen.
  • XHR vs fetch: XHR kann Upload-Fortschritt. fetch ist seit v22 Standard und passt besser zu SSR.
  • HttpClient vs httpResource: Observable für alles vs Signal-API für Lesen (stabil seit v22).

6. In der Produktion

  1. Token geht an fremde Domains: Interceptor hängt den Header an jeden Request. Lösung: nur für die eigene API-URL.
  2. Refresh-Sturm: 10 Requests bekommen 401, es gibt 10 Refreshes. Lösung: ein geteiltes Refresh-Observable (shareReplay) und Warten.
  3. Endlosschleife: Der Refresh-Request selbst läuft durch den Auth-Interceptor und bekommt 401. Lösung: HttpContextToken zum Überspringen.
  4. Doppelte Bestellungen: Retry auf POST. Lösung: nur GET wiederholen oder Idempotency-Key im Backend.
  5. Fehler verschwinden: Interceptor gibt bei Fehler EMPTY zurück. Komponenten warten ewig. Lösung: Fehler weiterwerfen.
  6. Upload-Fortschritt fehlt nach Update auf v22: HttpClient nutzt jetzt fetch. Lösung: provideHttpClient(withXhr()).
  7. Interceptor wirkt nicht: Klassen-Interceptor in Standalone-App ohne withInterceptorsFromDi(). Oder ein Feature hat einen eigenen provideHttpClient().

7. Diagnose: Werkzeuge und Befehle

  • Network-Tab: Header, Status, Wiederholungen, „(canceled)“.
  • Logging-Interceptor mit tap und finalize: Methode, URL, Status, Dauer.
  • HttpTestingController: prüft in Tests Header, Retry-Anzahl und Fehlerpfade.
  • OpenTelemetry Web oder ein Header wie traceparent per Interceptor: Frontend-Requests im Backend-Trace sehen.
  • Angular DevTools Injector Tree: prüfen, ob ein Feature einen eigenen HttpClient bekommt.

8. Senior-Punkte

  1. Querschnitt in Interceptors: Auth, Fehler, Tracing, Ladeanzeige. Business-Logik nicht.
  2. Retry nur idempotent, mit Backoff und Grenze. Sonst verstärkt das Frontend einen Ausfall.
  3. Fehler zentral anzeigen, lokal entscheiden: Interceptor meldet, Komponente reagiert fachlich.
  4. Token-Handling sicher: Header nur für eigene Domain. Am besten übernimmt eine Bibliothek für OIDC/Keycloak den Refresh.
  5. Reihenfolge dokumentieren. Sie ist Teil der Architektur.

10. Fallen

  • „Ich ändere req.headers direkt.“ → Geht nicht. Requests sind unveränderlich, clone() nutzen.
  • „Interceptors laufen auch für die Antwort in derselben Reihenfolge.“ → Falsch. Die Antwort läuft umgekehrt.
  • „Klassen-Interceptors funktionieren mit provideHttpClient() automatisch.“ → Falsch. withInterceptorsFromDi() nötig.
  • „Retry ist immer gut.“ → Falsch. Nicht für POST und nicht für 4xx.
  • „status 0 ist ein Serverfehler.“ → Falsch. Keine Antwort: Netzwerk, CORS oder Abbruch.

11. Fragen

Wie richtet man HttpClient in Angular 22 ein?

Ohne Setup ist HttpClient injizierbar (seit v21). Für Interceptors oder XHR: provideHttpClient(withInterceptors([...]), withXhr()) in der appConfig.

Was ist ein Interceptor?

Eine Funktion zwischen HttpClient und Netzwerk. Sie sieht und ändert Requests und Antworten.

Wie sieht ein funktionaler Interceptor aus?

(req, next) => next(req), optional mit pipe() auf der Antwort. inject() ist darin erlaubt.

Wie hängt man ein Auth-Token an?

req.clone({ setHeaders: { Authorization: 'Bearer …' } }) und next(clone). Nur für die eigene API.

In welcher Reihenfolge laufen Interceptors?

Requests in Listen-Reihenfolge, Antworten in umgekehrter Reihenfolge.

Warum clone()?

HttpRequest ist unveränderlich. So kann ein Retry den Original-Request sicher neu senden.

Wie behandelt man Fehler zentral?

catchError im Interceptor: nach Status reagieren, Meldung zeigen, Fehler weiterwerfen.

Wie macht man Retry richtig?

retry({ count, delay }) nur für GET, nur bei 5xx oder status 0, mit Backoff.

Wie verhindert man mehrere Token-Refreshes gleichzeitig?

Ein geteiltes Refresh-Observable. Alle 401-Requests warten darauf und wiederholen dann.

Was ist ein HttpContextToken?

Metadaten pro Request für Interceptors, z. B. „Auth überspringen“ oder „kein Spinner“.

Wie nutzt man alte Klassen-Interceptors in einer Standalone-App?

provideHttpClient(withInterceptorsFromDi()) und weiter HTTP_INTERCEPTORS mit multi: true.

Was bedeutet status 0?

Keine HTTP-Antwort: Netzwerkfehler, CORS-Blockade oder Abbruch.

Was macht withFetch?

Bis v21 schaltete es HttpClient von XHR auf fetch. Seit v22 ist fetch Standard und withFetch deprecated; withXhr() holt XHR zurück.

Wie testet man HTTP-Code?

provideHttpClientTesting und HttpTestingController: expectOne, flush, verify.

Was ist der HTTP Transfer Cache?

Bei SSR werden GET-Antworten ins HTML gelegt. Der Browser nutzt sie und fragt nicht doppelt.

Wie zeigt man Upload-Fortschritt?

observe: 'events' und reportUploadProgress: true (bis v21 reportProgress). Dann kommen HttpEventType.UploadProgress-Events, nur mit XHR, also ab v22 mit withXhr().

Szenario: Nach Token-Ablauf feuert die App 20 Refresh-Requests. Lösung?

Refresh als geteiltes Observable mit shareReplay. Alle wartenden Requests nutzen dasselbe Ergebnis.

Szenario: Kunden haben doppelte Einträge nach Netzwerk-Wacklern. Warum?

Retry auf POST. Lösung: nur GET wiederholen, im Backend Idempotency-Key.

Szenario: Ein lazy Feature sendet Requests ohne Token. Warum?

Das Feature hat ein eigenes provideHttpClient() ohne Interceptors. Lösung: nur einmal in der appConfig registrieren.
