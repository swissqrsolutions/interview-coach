RxJS-Operatoren: switchMap, mergeMap, concatMap, exhaustMap

Angular · Tier 1 · Quellen: rxjs.dev (RxJS 7.8) API switchMap, mergeMap, concatMap, exhaustMap, debounceTime, distinctUntilChanged, shareReplay, catchError, retry, combineLatest, forkJoin; Guide „Operators“

Kern: Ein Operator ist eine Funktion, die ein Observable nimmt und ein neues zurückgibt. Die vier Higher-Order-Mapping-Operatoren machen aus jedem Wert ein inneres Observable, z. B. einen HTTP-Request. Sie unterscheiden sich nur darin, was mit einem laufenden inneren Observable passiert, wenn ein neuer Wert kommt.

1. Wo sitzen Operatoren?

  1. pipe(): verbindet Operatoren in Reihenfolge. Jeder Operator abonniert den vorherigen.
  2. Filter-Operatoren wie debounceTime und distinctUntilChanged reduzieren die Werte.
  3. Mapping-Operator wie switchMap startet für jeden Wert ein inneres Observable.
  4. Fehlerbehandlung mit catchError gehört in das innere Observable.
  5. Multicasting mit shareReplay am Ende teilt das Ergebnis mit mehreren Subscribern.

2. Die Reise einer Suche (die Geschichte zum Merken)

  1. A kommt: Der Nutzer tippt „A“. Alle vier Operatoren starten einen Request für A. Er dauert 200 ms.
  2. B kommt nach 140 ms: Der Request für A läuft noch. Jetzt unterscheiden sie sich.
  3. switchMap: bricht A ab (unsubscribe, HTTP wird abgebrochen) und startet B. Nur b kommt an. Richtig für Suche.
  4. mergeMap: lässt A laufen und startet B parallel. a und b kommen, Reihenfolge nach Antwortzeit.
  5. concatMap: stellt B in eine Warteschlange. B startet erst, wenn A fertig ist. Reihenfolge garantiert.
  6. exhaustMap: ignoriert B, solange A läuft. Richtig für einen Login-Button, der doppelt geklickt wird.

3. Beispiel: Suche mit allen wichtigen Operatoren

@Injectable({ providedIn: 'root' })
export class ReportSearch {
  private http = inject(HttpClient);

  search(term$: Observable<string>): Observable<Report[]> {
    return term$.pipe(
      map(t => t.trim()),
      debounceTime(300),                 // warten, bis 300 ms Ruhe ist
      distinctUntilChanged(),            // gleiche Eingabe nicht neu suchen
      filter(t => t.length >= 2),
      switchMap(t =>
        this.http.get<Report[]>('/api/reports', { params: { q: t } }).pipe(
          retry({ count: 2, delay: 500 }),
          catchError(() => of([] as Report[])),   // innen: äusserer Strom lebt weiter
        )),
      shareReplay({ bufferSize: 1, refCount: true }),
    );
  }
}

// Kombinieren
const view$  = combineLatest([filters$, page$]);          // bei jeder Änderung
const init$  = forkJoin({ user: getUser(), cfg: getCfg() }); // einmal, wenn alle fertig
Erwartetes Ergebnis (laut RxJS-Doku, nicht ausgeführt), Eingabe: "r", "re", "rep" schnell, Pause, "rep ":
- "r" und "re" werden durch debounceTime verworfen.
- Ein Request: GET /api/reports?q=rep
- "rep " wird durch trim zu "rep" → distinctUntilChanged verwirft es, kein Request.
- Server-Fehler: 2 Wiederholungen mit 500 ms Abstand, dann [] und die Suche bleibt aktiv.
- combineLatest liefert erst, wenn filters$ und page$ je einmal geliefert haben.
- forkJoin liefert genau einmal {user, cfg}, wenn beide complete sind.
  1. debounceTime spart Requests beim Tippen. distinctUntilChanged vergleicht mit ===, darum zuerst trim.
  2. switchMap bricht veraltete Requests ab. So zeigt die UI nie ein altes Ergebnis nach einem neuen (Race Condition).
  3. catchError im inneren Observable: Nur dieser Request scheitert. Stünde es aussen, würde die ganze Suche enden.
  4. shareReplay mit refCount: true teilt das Ergebnis und stoppt, wenn niemand mehr zuhört.

4. Details, die Interviewer fragen

  1. switchMap: abbrechen und wechseln. Für Lesen: Suche, Route-Parameter, Filter. Nicht für Schreiben, sonst gehen Saves verloren.
  2. mergeMap: alles parallel. Für unabhängige Aufgaben. Mit concurrent-Parameter begrenzbar, z. B. mergeMap(f, 4).
  3. concatMap: eins nach dem anderen. Für Schreiben, wenn die Reihenfolge zählt, z. B. Autosave.
  4. exhaustMap: neue Werte ignorieren, solange einer läuft. Für Login, Submit, Refresh-Button.
  5. debounceTime: liefert den letzten Wert erst nach einer Ruhezeit. throttleTime liefert dagegen den ersten und sperrt dann.
  6. distinctUntilChanged: unterdrückt gleiche Werte direkt hintereinander. Für Objekte braucht es einen Vergleicher oder distinctUntilKeyChanged.
  7. shareReplay: teilt die Quelle und speichert die letzten n Werte für späte Subscriber. Ohne refCount: true bleibt die Quelle für immer abonniert.
  8. catchError: fängt einen Fehler und gibt ein Ersatz-Observable zurück. Der ursprüngliche Strom ist danach trotzdem beendet.
  9. retry: abonniert die Quelle neu. In RxJS 7: retry({count, delay}). retryWhen ist deprecated.
  10. combineLatest: liefert, sobald jede Quelle einmal geliefert hat, dann bei jeder Änderung. Gut für Filter-Kombinationen.
  11. forkJoin: liefert einmal die letzten Werte, wenn alle Quellen complete sind. Endet eine Quelle ohne Wert, liefert es nichts. Wie Promise.all.
  12. withLatestFrom: nimmt den letzten Wert einer zweiten Quelle, löst aber nur bei der ersten aus.
  13. zip: paart Werte nach Position. Selten nötig.
  14. tap: Seiteneffekt ohne Änderung, z. B. Logging oder Loading-Flag.
  15. finalize: läuft bei complete, error und unsubscribe. Gut zum Zurücksetzen eines Spinners.

5. Vergleich

  • switchMap: nur der neueste zählt. Suche, Navigation.
  • mergeMap: alle parallel, Reihenfolge nach Antwort. Unabhängige Uploads.
  • concatMap: alle nacheinander, Reihenfolge garantiert. Speichern in Reihenfolge.
  • exhaustMap: der erste gewinnt, Rest ignoriert. Submit, Login.
  • combineLatest vs forkJoin: laufend bei jeder Änderung vs einmal am Ende aller Quellen.
  • debounceTime vs throttleTime: letzter Wert nach Ruhe vs erster Wert, dann Sperre.
  • share vs shareReplay: ohne Speicher vs mit Puffer für späte Subscriber.

6. In der Produktion

  1. Alte Suchergebnisse überschreiben neue: mergeMap statt switchMap. Langsame alte Antwort kommt zuletzt.
  2. Gespeicherte Daten fehlen: switchMap beim Speichern bricht frühere Saves ab. Lösung: concatMap.
  3. Doppelte Bestellungen: Doppelklick auf Submit mit mergeMap. Lösung: exhaustMap und Button sperren.
  4. Suche geht nach einem Fehler nie wieder: catchError aussen. Lösung: innen.
  5. Veraltete Daten für immer: shareReplay(1) ohne Ablauf als Cache. Lösung: Neuladen per Trigger oder Zeitlimit.
  6. forkJoin liefert nie: Eine Quelle endet nicht, z. B. ein Subject. Lösung: take(1) oder combineLatest.
  7. Server-Überlast durch retry: sofortige Wiederholungen bei 500. Lösung: delay mit Backoff, nur idempotente Requests wiederholen.

7. Diagnose: Werkzeuge und Befehle

  • Network-Tab: „(canceled)“ zeigt switchMap-Abbrüche. Viele parallele Requests zeigen mergeMap.
  • tap({ next, error, complete, subscribe, unsubscribe, finalize }): Lebenszyklus eines Stroms loggen (RxJS 7.3+).
  • Marble-Tests mit TestScheduler: Verhalten der Mapping-Operatoren exakt prüfen.
  • rxmarbles.com und die Entscheidungshilfe „Operator Decision Tree“ auf rxjs.dev.

8. Senior-Punkte

  1. Lesen → switchMap, Schreiben → concatMap oder exhaustMap. Diese Regel verhindert die meisten Bugs.
  2. Fehler innen behandeln, damit lang lebende Ströme überleben.
  3. shareReplay immer mit refCount bedenken. Sonst Leaks und veraltete Daten.
  4. Retry nur für idempotente Requests und mit Backoff. Ein POST darf nicht doppelt laufen.
  5. Wenige, gut benannte Ströme statt langer Ketten. Lange Pipes in Funktionen auslagern.
  6. Mit Signals kombinieren: RxJS für Zeit und Events, am Ende toSignal für das Template.

10. Fallen

  • „switchMap ist immer richtig.“ → Falsch. Beim Schreiben bricht es Saves ab.
  • „catchError lässt den Strom weiterlaufen.“ → Falsch. Der Strom endet; nur das Ersatz-Observable läuft.
  • „forkJoin ist wie combineLatest.“ → Falsch. forkJoin wartet auf complete aller Quellen und liefert einmal.
  • „debounceTime und throttleTime sind gleich.“ → Falsch. Letzter Wert nach Ruhe vs erster Wert mit Sperre.
  • „shareReplay(1) räumt selbst auf.“ → Nicht ohne refCount: true.
  • „mergeMap hält die Reihenfolge.“ → Falsch. Nur concatMap.

11. Fragen

Was ist ein Operator?

Eine Funktion, die ein Observable nimmt und ein neues liefert. Man verbindet sie mit pipe().

Was ist ein Higher-Order-Mapping-Operator?

Er macht aus jedem Wert ein inneres Observable und liefert dessen Werte nach aussen.

Was macht switchMap?

Es beendet das laufende innere Observable und startet das neue. Nur der neueste Wert zählt.

Was macht mergeMap?

Es startet alle inneren Observables parallel. Ergebnisse kommen in Antwortreihenfolge.

Was macht concatMap?

Es wartet, bis das innere Observable fertig ist, und startet dann das nächste. Reihenfolge garantiert.

Was macht exhaustMap?

Es ignoriert neue Werte, solange ein inneres Observable läuft.

Welchen Operator für eine Typeahead-Suche?

debounceTime, distinctUntilChanged, dann switchMap mit catchError im Inneren.

Welchen Operator für einen Submit-Button?

exhaustMap. Doppelklicks erzeugen keinen zweiten Request.

Welchen Operator für Autosave?

concatMap, damit Saves in Reihenfolge ankommen und keiner verloren geht.

debounceTime vs throttleTime?

debounceTime liefert den letzten Wert nach einer Ruhezeit. throttleTime liefert den ersten und sperrt dann.

Was macht distinctUntilChanged?

Es unterdrückt Werte, die gleich dem vorherigen sind. Vergleich mit === oder eigener Funktion.

Was macht shareReplay?

Es teilt eine Quelle und gibt späten Subscribern die letzten n Werte. refCount: true stoppt die Quelle ohne Subscriber.

Wo gehört catchError hin?

In das innere Observable. Sonst endet der äussere Strom beim ersten Fehler.

Wie wiederholen Sie einen Request mit Pause?

retry({ count: 3, delay: 1000 }). delay kann auch eine Funktion für Backoff sein.

combineLatest vs forkJoin?

combineLatest liefert laufend nach dem ersten Wert jeder Quelle. forkJoin liefert einmal, wenn alle complete sind.

Wann liefert forkJoin nie?

Wenn eine Quelle nie endet oder ohne Wert endet.

Was ist withLatestFrom?

Es löst nur bei der Hauptquelle aus und hängt den letzten Wert einer zweiten an.

Was macht finalize?

Es läuft bei complete, error und unsubscribe. Gut, um Loading-Flags zurückzusetzen.

Szenario: Die Suche zeigt manchmal Ergebnisse für einen alten Begriff. Warum?

mergeMap lässt alte Requests laufen, eine langsame Antwort kommt zuletzt. Lösung: switchMap.

Szenario: Kunden melden doppelte Bestellungen. Was ändern Sie im Frontend?

exhaustMap für den Submit, Button während des Requests sperren. Im Backend zusätzlich Idempotency-Key.

Szenario: Nach einem 500-Fehler reagiert die Suche nicht mehr. Warum?

catchError steht ausserhalb von switchMap, der Strom ist beendet. Lösung: catchError ins innere Observable.
