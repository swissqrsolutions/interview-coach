MVCC: wie PostgreSQL Versionen speichert

PostgreSQL · Tier 1 · Quellen: PostgreSQL 17 Doku: „Concurrency Control“ (Introduction, Transaction Isolation), „Database Page Layout“, „Heap-Only Tuples (HOT)“, „Visibility Map“, „Routine Vacuuming“ (Preventing Transaction ID Wraparound Failures), „System Columns“, „System Information Functions“ (pg_current_snapshot, pg_current_xact_id), Modul pageinspect

Kern: MVCC (Multi-Version Concurrency Control) heisst: Jede Änderung erzeugt eine neue Zeilenversion, die alte bleibt stehen. Jede Transaktion liest mit einem Snapshot und sieht genau die Versionen, die zu ihm passen. So blockieren Leser keine Schreiber und Schreiber keine Leser.

1. Wo sitzen die Versionen?

  1. Heap: Die Tabelle selbst, aufgeteilt in Seiten zu 8 kB. Alte und neue Versionen liegen beide im Heap. Es gibt kein separates Undo-Log.
  2. Tuple: Eine physische Zeilenversion. Sie trägt im Header xmin, xmax und t_ctid.
  3. xmin: die xid der Transaktion, die die Version erzeugt hat. xmax: die xid, die sie gelöscht, ersetzt oder gesperrt hat. 0 heisst: noch nicht gelöscht.
  4. ctid: die physische Adresse (Seite, Line Pointer), z. B. (0,2). Die alte Version zeigt mit t_ctid auf ihre Nachfolgerin.
  5. Snapshot: eine Momentaufnahme: Welche Transaktionen sind fertig, welche laufen noch?
  6. pg_xact: der Commit-Status jeder xid. Der Snapshot plus pg_xact entscheiden über Sichtbarkeit.
  7. Visibility Map: zwei Bits pro Seite: all-visible und all-frozen. Nutzt VACUUM und Index-Only Scans.
  8. Index: zeigt auf ein Tuple, hat aber keine Sichtbarkeitsinfo. Jeder Treffer muss im Heap oder in der Visibility Map geprüft werden.

2. Die Reise eines UPDATE (die Geschichte zum Merken)

  1. Zeile finden: UPDATE t SET v = 'b' WHERE id = 1 sucht die Version, die für den eigenen Snapshot sichtbar ist.
  2. Row Lock: Transaktion 751 schreibt ihre xid in xmax der alten Version. Das ist zugleich Löschmarke und Row Lock. Eine andere Transaktion, die die Zeile ändern will, wartet jetzt.
  3. Neue Version: 751 schreibt (1, 'b') mit xmin = 751 als neues Tuple. Die alte Version bekommt t_ctid auf die neue. UPDATE = DELETE + INSERT.
  4. HOT prüfen: Hat sich keine indizierte Spalte geändert und hat die Seite Platz? Dann ist es ein HOT Update (Heap-Only Tuple). Die Indexe bekommen keinen neuen Eintrag. Sonst bekommt jeder Index einen neuen Eintrag.
  5. COMMIT: pg_xact markiert 751 als committed. Eine Transaktion, die vorher ihren Snapshot nahm, sieht weiter 'a'. Neue Snapshots sehen 'b'.
  6. Aufräumen: Sobald kein Snapshot 'a' mehr braucht, ist die alte Version ein dead tuple. VACUUM gibt ihren Platz frei. Bei HOT kann das schon ein normaler Zugriff tun (Page Pruning).

3. Beispiel: Versionen sichtbar machen

CREATE TABLE t (id int PRIMARY KEY, v text);
INSERT INTO t VALUES (1, 'a');
SELECT ctid, xmin, xmax, * FROM t;

UPDATE t SET v = 'b' WHERE id = 1;          -- v ist nicht indiziert
SELECT ctid, xmin, xmax, * FROM t;

CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid,
       (t_infomask2 & 16384) > 0 AS hot_updated,   -- HEAP_HOT_UPDATED
       (t_infomask2 & 32768) > 0 AS heap_only      -- HEAP_ONLY_TUPLE
FROM heap_page_items(get_raw_page('t', 0));

SELECT pg_current_snapshot();

  1. Nach dem INSERT liegt die Zeile an (0,1). xmin = 750, xmax = 0: lebt.
  2. Nach dem UPDATE zeigt SELECT nur die neue Version an (0,2). Die ctid hat sich geändert: Es ist physisch eine neue Zeile.
  3. pageinspect zeigt beide Versionen. Die alte hat xmax = 751 und zeigt auf (0,2).
  4. hot_updated und heap_only zeigen ein HOT Update. Der Primary-Key-Index zeigt weiter auf (0,1) und folgt der Kette.
  5. 752:752: ist xmin:xmax:xip_list des Snapshots. Keine andere Transaktion läuft, die Liste ist leer.

4. Details, die Interviewer fragen

  1. Sichtbarkeitsregel (vereinfacht): Eine Version ist sichtbar, wenn xmin committed und für den Snapshot „vorher“ ist. Und wenn xmax leer, abgebrochen oder für den Snapshot „nachher“ ist.
  2. Snapshot-Inhalt: xmin = älteste noch laufende xid. xmax = erste noch nicht vergebene xid. xip_list = laufende xids dazwischen. Alles ab xmax oder in der Liste ist unsichtbar.
  3. Wann der Snapshot entsteht: In Read Committed bei jedem Befehl neu. In Repeatable Read und Serializable einmal beim ersten Befehl der Transaktion, nicht bei BEGIN.
  4. Eigene Änderungen: Die Transaktion sieht ihre eigenen Änderungen. Innerhalb der Transaktion unterscheidet cmin/cmax (Command ID) die Befehle.
  5. Hint Bits: Der erste Leser schlägt den Status in pg_xact nach. Danach setzt er Bits im Tuple-Header, z. B. „xmin committed“. Darum kann ein SELECT Seiten schmutzig machen und WAL erzeugen (bei Checksums).
  6. DELETE: setzt nur xmax. Die Zeile bleibt physisch liegen, bis VACUUM sie entfernt.
  7. xmax als Lock: SELECT … FOR UPDATE schreibt auch xmax, aber mit einem Lock-Flag. Teilen sich mehrere Transaktionen einen Lock, steht in xmax eine MultiXact-ID.
  8. HOT-Bedingungen: Keine Spalte eines Index ändert sich. Und die neue Version passt auf dieselbe Seite. Ein tieferer fillfactor (z. B. 90) lässt dafür Platz.
  9. Write Amplification: Ohne HOT erzeugt ein UPDATE einen Eintrag in jedem Index, auch bei nicht geänderten Spalten. Viele Indexe machen Updates teuer.
  10. Visibility Map und Index-Only Scan: Ist eine Seite all-visible, braucht ein Index-Only Scan den Heap nicht. Sonst muss er doch in den Heap (Heap Fetches in EXPLAIN).
  11. 32-Bit-xid: Eine xid hat 32 Bit, also ca. 4 Mrd. Werte. Verglichen wird im Kreis: ca. 2 Mrd. gelten als Vergangenheit, 2 Mrd. als Zukunft.
  12. Wraparound: Ist eine Zeile über 2 Mrd. Transaktionen alt, würde sie plötzlich „in der Zukunft“ liegen und verschwinden. Das verhindert Freezing: VACUUM markiert alte Versionen als „für alle sichtbar“.
  13. Schutz vor Wraparound: Ab autovacuum_freeze_max_age (200 Mio.) startet ein Pflicht-Autovacuum, auch bei autovacuum = off. Bleiben weniger als 40 Mio. xids, warnt PostgreSQL. Bei 3 Mio. vergibt es keine neuen xids mehr.
  14. xid8: pg_current_xact_id() liefert eine 64-Bit-xid mit Epoche. Auf der Disk speichert PostgreSQL aber weiter 32 Bit.

5. Vergleich

  • PostgreSQL: alte Versionen im Heap. Rollback billig. Preis: Bloat und VACUUM.
  • Oracle und MySQL InnoDB: ändern an Ort und Stelle, alte Version im Undo-Log. Wenig Bloat. Lange Leser können „snapshot too old“ bekommen (Oracle).
  • SQL Server: Standard ohne MVCC (Lock-basiert). Mit READ_COMMITTED_SNAPSHOT oder SNAPSHOT landen alte Versionen im tempdb Version Store.
  • HOT Update vs normales Update: HOT: kein Index-Eintrag, Aufräumen per Pruning. Normal: Eintrag in jedem Index, Aufräumen nur per VACUUM.
  • MVCC vs Locking (2PL): MVCC: Leser warten nie auf Schreiber. 2PL: Leser nehmen Shared Locks und warten. Schreiber gegen Schreiber warten in beiden.
  • Iceberg Snapshots: Auch Versionen, aber auf Tabellenebene mit Dateien. Alte Snapshots entfernt expire_snapshots, ähnlich wie VACUUM.

6. In der Produktion

  1. Bloat: Häufige Updates erzeugen viele tote Versionen. Tabelle und Indexe wachsen. Lösung: Autovacuum pro Tabelle schärfer stellen, lange Transaktionen verhindern.
  2. Hot Row: Ein Zähler wird tausendmal pro Sekunde aktualisiert. Jede Änderung ist eine neue Version, alle warten auf denselben Row Lock. Lösung: Zähler aufteilen oder Events sammeln und periodisch summieren.
  3. Kaum HOT Updates: Eine oft geänderte Spalte wie updated_at ist indiziert. Jedes Update schreibt alle Indexe. Lösung: Index prüfen, fillfactor senken.
  4. Index-Only Scan langsam: Viele Heap Fetches, weil die Visibility Map veraltet ist. Lösung: VACUUM öfter laufen lassen.
  5. Wraparound-Gefahr: Log-Warnung „must be vacuumed within … transactions“. Ursache meist: blockiertes VACUUM durch alte Transaktion, Replication Slot oder prepared Transaction. Lösung: Blocker entfernen, dann VACUUM (ohne FULL).
  6. Lange Abfragen auf Replicas: Der Primary räumt Versionen weg, die eine Abfrage auf der Replica noch braucht. Folge: Query wird abgebrochen. Lösung: hot_standby_feedback = on (kostet Bloat am Primary) oder max_standby_streaming_delay.

7. Diagnose: Werkzeuge und Abfragen

-- HOT-Quote pro Tabelle
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables ORDER BY n_tup_upd DESC LIMIT 10;

-- Alter der ältesten xid pro Datenbank (Wraparound)
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- Wer hält den ältesten Snapshot?
SELECT pid, backend_xmin, state, now() - xact_start AS dauer
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;
  • Systemspalten ctid, xmin, xmax: direkt in jedem SELECT abfragbar.
  • pageinspect: heap_page_items zeigt auch tote Versionen.
  • pg_visibility: zeigt die Visibility Map pro Seite.
  • pg_current_snapshot(), pg_current_xact_id(), pg_xact_status(xid8).
  • EXPLAIN (ANALYZE, BUFFERS): Heap Fetches bei Index-Only Scans.
  • pg_replication_slots (xmin, catalog_xmin) und pg_prepared_xacts: weitere Halter alter Snapshots.

8. Senior-Punkte

  1. MVCC tauscht Sperren gegen Speicher. Leser warten nicht, dafür entstehen tote Versionen. VACUUM ist der Preis.
  2. Update-lastige Tabellen anders designen. Wenige Indexe, fillfactor unter 100, keine indizierten Spalten, die sich ständig ändern.
  3. Append-only ist MVCC-freundlich. Events anhängen statt Zeilen ständig ändern erzeugt keine toten Versionen.
  4. Die älteste Transaktion bestimmt das Aufräumen. Ein einziger vergessener Snapshot bremst die ganze Datenbank, auch über Replicas.
  5. Wraparound ist ein Betriebsthema. age(datfrozenxid) gehört ins Monitoring mit Alarm, z. B. ab 500 Mio.
  6. Undo-Log oder Heap-Versionen ist ein Design-Tausch. PostgreSQL: billiger Rollback, aber Bloat. Undo: kompakter, aber teurer Rollback und lange Leser.

10. Fallen

  • „UPDATE ändert die Zeile an Ort und Stelle.“ → Falsch. Es schreibt eine neue Version. Die alte bleibt, bis VACUUM sie entfernt.
  • „DELETE gibt sofort Platz frei.“ → Falsch. Es setzt nur xmax. Den Platz gibt erst VACUUM frei, und meist nicht an das Betriebssystem.
  • „Bei MVCC gibt es keine Locks.“ → Falsch. Schreiber auf dieselbe Zeile warten aufeinander. Nur Leser und Schreiber blockieren sich nicht.
  • „Der Snapshot entsteht bei BEGIN.“ → Falsch. Er entsteht beim ersten Befehl der Transaktion.
  • „Ein Index weiss, ob eine Zeile sichtbar ist.“ → Falsch. Indexe haben keine Sichtbarkeitsinfo. Darum Heap-Zugriff oder Visibility Map.
  • „Wraparound passiert nach 4 Mrd. Transaktionen.“ → Ungenau. Die Grenze ist ca. 2 Mrd. Abstand zur ältesten ungefrorenen xid.
  • „Ein SELECT schreibt nie.“ → Falsch. Er kann Hint Bits setzen und HOT-Ketten prunen.

11. Fragen

Was ist MVCC?

Jede Änderung erzeugt eine neue Zeilenversion. Jede Transaktion sieht über ihren Snapshot die passende Version. Leser und Schreiber blockieren sich nicht.

Was sind xmin und xmax?

xmin ist die xid, die die Version erzeugt hat. xmax ist die xid, die sie gelöscht, ersetzt oder gesperrt hat. 0 in xmax heisst: lebt.

Was ist die ctid?

Die physische Adresse einer Version: Seite und Line Pointer. Sie ändert sich bei jedem UPDATE. Nie als stabile ID nutzen.

Warum ist UPDATE in PostgreSQL ein DELETE plus INSERT?

Die alte Version bekommt xmax, eine neue Version wird geschrieben. So können ältere Snapshots weiter die alte Version lesen.

Was steht in einem Snapshot?

xmin (älteste laufende xid), xmax (erste noch nicht vergebene xid) und die Liste der laufenden xids dazwischen.

Wann ist eine Version sichtbar?

Wenn xmin committed und vor dem Snapshot ist. Und wenn xmax leer, abgebrochen oder für den Snapshot noch nicht committed ist.

Wann wird der Snapshot genommen?

Read Committed: bei jedem Befehl. Repeatable Read und Serializable: beim ersten Befehl der Transaktion.

Was ist ein HOT Update?

Ein Update ohne Änderung an indizierten Spalten, mit Platz auf derselben Seite. Die Indexe bekommen keinen neuen Eintrag. Tote Versionen räumt Pruning ohne VACUUM.

Wie fördert man HOT Updates?

Keine oft geänderten Spalten indizieren. fillfactor unter 100 setzen, damit Platz auf der Seite bleibt. Die Quote in n_tup_hot_upd prüfen.

Was sind Hint Bits?

Bits im Tuple-Header, die den Commit-Status von xmin und xmax zwischenspeichern. Spätere Leser müssen pg_xact nicht mehr fragen.

Was ist ein dead tuple?

Eine Version, die kein Snapshot mehr sehen kann. Sie belegt Platz, bis VACUUM oder Pruning sie freigibt.

Was ist die Visibility Map?

Zwei Bits pro Seite: all-visible und all-frozen. VACUUM überspringt solche Seiten, und Index-Only Scans brauchen den Heap nicht.

Was ist Transaction ID Wraparound?

xids haben 32 Bit und werden im Kreis verglichen. Ohne Freezing würde eine über 2 Mrd. Transaktionen alte Zeile plötzlich als Zukunft gelten und verschwinden.

Was ist Freezing?

VACUUM markiert alte Versionen als für alle sichtbar. Ihr xmin zählt dann nicht mehr im Vergleich. So ist Wraparound harmlos.

Was passiert kurz vor Wraparound?

Ab 40 Mio. verbleibenden xids kommen Warnungen. Bei 3 Mio. vergibt PostgreSQL keine neuen xids mehr. Schreibende Befehle scheitern, bis VACUUM gelaufen ist.

Was ist eine MultiXact?

Eine ID für eine Gruppe von Transaktionen, die gemeinsam einen Row Lock halten, z. B. mehrere FOR SHARE. Sie steht in xmax und muss auch gefroren werden.

Wie unterscheidet sich MVCC in PostgreSQL von Oracle?

PostgreSQL hält alte Versionen im Heap und braucht VACUUM. Oracle ändert an Ort und Stelle und rekonstruiert alte Versionen aus dem Undo.

Warum braucht ein Index-Only Scan manchmal den Heap?

Der Index kennt die Sichtbarkeit nicht. Ist die Seite nicht all-visible, muss der Scan den Heap prüfen. Das zeigt Heap Fetches.

Kann ein SELECT WAL erzeugen?

Ja. Er kann Hint Bits setzen und HOT-Ketten prunen. Mit Data Checksums erzeugt das WAL-Records.

Was ist hot_standby_feedback?

Die Replica meldet dem Primary ihren ältesten Snapshot. Der Primary räumt diese Versionen nicht weg. Weniger abgebrochene Queries, aber mehr Bloat am Primary.

Szenario: Eine Tabelle mit 1 Mio. Zeilen ist 10 GB gross. Was prüfen Sie?

n_dead_tup und HOT-Quote in pg_stat_user_tables, älteste Snapshots in pg_stat_activity, Replication Slots. Dann Blocker entfernen und Autovacuum anpassen. Platz zurück nur mit Rewrite, z. B. pg_repack.

Szenario: Das Log warnt „database must be vacuumed within 30000000 transactions“. Was tun Sie?

Sofort Blocker suchen: alte Transaktionen, verwaiste Replication Slots, prepared Transactions. Sie beenden. Dann VACUUM auf die ältesten Tabellen, nicht VACUUM FULL.

Szenario: Updates auf eine Tabelle sind langsam und erzeugen viel WAL. Warum?

Wahrscheinlich keine HOT Updates: Jede Änderung schreibt in alle Indexe. Indexe auf oft geänderten Spalten prüfen und fillfactor senken.
