Index-Typen: B-Tree, Hash, GIN, GiST, BRIN, partial, covering

PostgreSQL · Tier 1 · Quellen: PostgreSQL 17 Doku, Kapitel 11 „Indexes“ (11.1–11.11), Kapitel 64 „Built-in Index Access Methods“ (B-Tree, GiST, SP-GiST, GIN, BRIN, Hash), CREATE INDEX, Kapitel 27.2 „Cumulative Statistics“ (pg_stat_user_indexes), Kapitel 73.4 „Visibility Map“; Markus Winand, „Use The Index, Luke“ (Anatomy, WHERE clause, Partial Results)

Kern: Ein Index ist eine eigene Datenstruktur neben der Tabelle, die Zeilen über einen Schlüssel schnell findet. Er macht Lesen schnell, aber jedes INSERT/UPDATE langsamer. Der Standard ist B-Tree. Für JSONB, Arrays und Volltext nimmt man GIN, für Geo und Bereiche GiST, für riesige Log-Tabellen BRIN.

1. Wo sitzt der Index?

  1. Heap: Die Tabelle selbst. Zeilen liegen ungeordnet in 8-kB-Pages. Jede Zeile hat eine TID (Tuple ID, sichtbar als ctid), z. B. (4711,3) = Page 4711, Slot 3.
  2. Index: Eine eigene Datei. Ein B-Tree speichert Schlüssel sortiert, jeweils mit der TID der Zeile.
  3. Root und Inner Pages: Sie leiten die Suche nach unten. Der Baum ist flach: meist 3–4 Ebenen, auch bei Millionen Zeilen.
  4. Leaf Pages: Sie sind in beide Richtungen verkettet. So läuft ein Bereich (BETWEEN) ohne neuen Abstieg durch.
  5. Visibility Map: Sie merkt sich pro Heap-Page, ob alle Zeilen für alle sichtbar sind. Sie macht Index-Only Scans möglich.
  6. Der Index enthält keine Sichtbarkeitsinfo (MVCC). Darum muss PostgreSQL meist trotzdem in den Heap.

2. Die Reise einer Abfrage durch den Index (die Geschichte zum Merken)

  1. Planner entscheidet. Die Abfrage WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10 kommt an. Der Planner sieht den Index (customer_id, created_at). Er schätzt: wenige Treffer, also Index billiger als Seq Scan.
  2. Abstieg im Baum. PostgreSQL liest die Root Page, dann eine Inner Page, dann die erste passende Leaf Page. Das sind 3–4 Page-Zugriffe, meist aus dem Cache (shared_buffers).
  3. Leaf-Kette folgen. Alle Einträge mit customer_id = 42 liegen nebeneinander, schon nach created_at sortiert. Der Scan läuft rückwärts (Index Scan Backward) und stoppt nach 10 Treffern.
  4. Visibility Map fragen. Für jede TID prüft PostgreSQL: Ist die Heap-Page „all-visible“?
  5. Heap oder nicht. Nein: Er liest die Zeile im Heap und prüft MVCC (Heap Fetch, teurer Zufallszugriff). Ja, und alle Spalten stehen im Index: kein Heap-Zugriff, das ist ein Index-Only Scan.
  6. Ergebnis. Die Zeilen kommen schon sortiert heraus. Ein eigener Sort-Schritt fällt weg.
  7. Viele Treffer? Dann wäre jeder Heap Fetch ein Zufallszugriff. Der Planner wählt einen Bitmap Index Scan: TIDs sammeln, nach Page sortieren, Heap einmal in Reihenfolge lesen.

3. Beispiel: Composite, Partial und Covering Index im Plan

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id int         NOT NULL,
  status      text        NOT NULL,          -- ca. 2 % 'open'
  created_at  timestamptz NOT NULL,
  amount      numeric(12,2) NOT NULL
);
-- 5 Mio. Zeilen per generate_series laden, dann:
CREATE INDEX orders_cust_created ON orders (customer_id, created_at) INCLUDE (amount);
CREATE INDEX orders_open         ON orders (created_at) WHERE status = 'open';
VACUUM ANALYZE orders;

-- A) passt zum Index: Gleichheit vorne, Sortierung hinten, alle Spalten im Index
EXPLAIN (ANALYZE, BUFFERS)
SELECT created_at, amount FROM orders
WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10;

-- B) nur die zweite Spalte: kein Leftmost Prefix
EXPLAIN SELECT count(*) FROM orders WHERE created_at > now() - interval '1 hour';

-- C) Partial Index: WHERE der Abfrage enthält die Bedingung des Index
EXPLAIN SELECT id FROM orders
WHERE status = 'open' AND created_at > now() - interval '1 day';
A)
Limit  (cost=0.43..9.71 rows=10 width=14) (actual time=0.031..0.040 rows=10 loops=1)
  Buffers: shared hit=4
  ->  Index Only Scan Backward using orders_cust_created on orders
        (cost=0.43..46.81 rows=50 width=14) (actual time=0.030..0.037 rows=10 loops=1)
        Index Cond: (customer_id = 42)
        Heap Fetches: 0
        Buffers: shared hit=4
B)
Finalize Aggregate
  ->  Gather  (Workers Planned: 2)
        ->  Partial Aggregate
              ->  Parallel Seq Scan on orders
                    Filter: (created_at > (now() - '01:00:00'::interval))
C)
Index Scan using orders_open on orders  (cost=0.29..1690.12 rows=1720 width=8)
  Index Cond: (created_at > (now() - '1 day'::interval))

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Kosten und Zeiten sind Beispielwerte; die Plan-Form ist das, was zählt.

  1. A: customer_id ist Gleichheit und steht vorne. created_at liefert die Sortierung, rückwärts gelesen. amount liegt per INCLUDE im Index. Darum Index Only Scan mit Heap Fetches: 0 und nur 4 Pages.
  2. B: created_at ist die zweite Spalte. Ohne customer_id im WHERE fehlt der Leftmost Prefix. PostgreSQL 17 nimmt einen Seq Scan (Skip Scan gibt es erst ab Version 18).
  3. C: Der Partial Index enthält nur die ca. 2 % offenen Bestellungen. Er ist klein und passt, weil die Abfrage status = 'open' wörtlich enthält.
  4. Heap Fetches steigt, wenn VACUUM die Visibility Map nicht aktuell hält. Dann ist der Index-Only Scan kaum schneller als ein normaler.

4. Details, die Interviewer fragen

  1. B-Tree: Ein balancierter Baum (Lehman-Yao-Variante) für Gleichheit und Bereiche. Operatoren: < <= = >= >, BETWEEN, IN, IS NULL, LIKE 'abc%'. Er liefert Zeilen sortiert, also hilft er auch bei ORDER BY und MIN/MAX. Beispiel: jeder PRIMARY KEY und UNIQUE nutzt einen B-Tree.
  2. Deduplication (seit PostgreSQL 13): Gleiche Schlüssel speichert der B-Tree einmal mit einer Liste von TIDs. Indizes auf Spalten mit vielen Duplikaten werden dadurch deutlich kleiner.
  3. Composite Index (mehrspaltig): Die Reihenfolge der Spalten zählt. Er ist sortiert nach Spalte 1, dann Spalte 2. Regel aus „Use The Index, Luke“: Gleichheit zuerst, Bereich zuletzt. Beispiel: (tenant_id, created_at) für WHERE tenant_id = ? AND created_at > ?.
  4. Leftmost Prefix: Ein Index (a, b, c) hilft effizient bei a, a,b und a,b,c. Bei nur b muss PostgreSQL 17 den ganzen Index lesen, was selten lohnt. Ab Version 18 gibt es Skip Scan für wenige verschiedene Werte in a.
  5. ASC/DESC und NULLS FIRST/LAST: Ein B-Tree kann vorwärts und rückwärts gelesen werden. Gemischte Richtung wie ORDER BY a ASC, b DESC braucht einen Index (a ASC, b DESC).
  6. Partial Index: Ein Index mit WHERE-Bedingung. Er indiziert nur einen Teil der Zeilen. Beispiel: WHERE status = 'open' oder WHERE deleted_at IS NULL. Klein, billig zu pflegen. Der Planner nutzt ihn nur, wenn das WHERE der Abfrage die Bedingung beweisbar enthält. Mit Prepared Statements und Parameter $1 klappt das oft nicht.
  7. Partial Unique Index: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL erzwingt Eindeutigkeit nur für aktive Zeilen. Typisch bei Soft Delete.
  8. Expression Index: Ein Index auf einem Ausdruck statt einer Spalte. Beispiel: CREATE INDEX ON users (lower(email)) für WHERE lower(email) = ?. Der Ausdruck in der Abfrage muss exakt gleich sein. Funktionen müssen IMMUTABLE sein. ANALYZE sammelt eigene Statistiken für den Ausdruck.
  9. Covering Index mit INCLUDE (seit PostgreSQL 11): Zusatzspalten liegen nur in den Leaf Pages. Sie sind nicht Teil des Suchschlüssels und nicht der Eindeutigkeit. Beispiel: UNIQUE (id) INCLUDE (name). Zweck: Index-Only Scans. Unterstützt von B-Tree, GiST und SP-GiST.
  10. Index-Only Scan: Alle benötigten Spalten stehen im Index, und die Heap-Page ist laut Visibility Map all-visible. Dann liest PostgreSQL den Heap nicht. Die Visibility Map setzt nur VACUUM. Jede Änderung auf der Page löscht das Bit wieder.
  11. Bitmap Scan: Er sammelt TIDs aus einem oder mehreren Indizes in einer Bitmap. Er kann Indizes mit AND/OR kombinieren. Dann liest er den Heap in Page-Reihenfolge. Gut für mittlere Treffermengen.
  12. Hash Index: Speichert nur einen 32-Bit-Hash. Er kann nur =. Kein UNIQUE, keine mehrspaltigen Indizes, kein Sortieren. Seit Version 10 WAL-geloggt und crash-sicher. Vorteil nur bei sehr langen Schlüsseln (kleiner Index). Meist ist B-Tree die bessere Wahl.
  13. GIN (Generalized Inverted Index): Ein invertierter Index. Er speichert jeden Teilwert (Array-Element, JSON-Key, Wort) mit einer Liste der Zeilen. Für jsonb @>, ?, Arrays @> &&, Volltext tsvector @@, Trigramme (pg_trgm) für LIKE '%abc%'.
  14. GIN für JSONB: Die Standard-Opclass jsonb_ops kann @>, ?, ?|, ?&, @?, @@. jsonb_path_ops kann nur @>, @?, @@, ist aber kleiner und schneller. Für einen einzelnen Key reicht oft ein B-Tree auf (data->>'status').
  15. GIN Write-Kosten: Eine neue Zeile erzeugt viele Index-Einträge. Darum puffert GIN sie in einer Pending List (fastupdate, Grösse gin_pending_list_limit, Standard 4 MB). VACUUM oder eine volle Liste schreibt sie in den Baum. Lesen muss die Liste immer mit durchsuchen.
  16. GiST (Generalized Search Tree): Ein balancierter Baum über „überlappt/enthält“-Beziehungen, z. B. Bounding Boxes. Für PostGIS-Geometrien, Range-Typen (tstzrange &&), Volltext, Nächste-Nachbarn-Suche mit ORDER BY geom <-> point. Grundlage für Exclusion Constraints wie „keine überlappenden Buchungen“.
  17. SP-GiST (space-partitioned GiST): Teilt den Raum in nicht überlappende Teile: Quadtree, k-d-Tree, Radix Tree. Gut für Punkte, IP-Adressen (inet), Präfix-Suche auf Text. Bei ungleich verteilten Daten oft schneller als GiST.
  18. BRIN (Block Range Index): Speichert pro Block Range (Standard 128 Pages, pages_per_range) nur Minimum und Maximum. Winzig: Kilobytes statt Gigabytes. Funktioniert nur, wenn der Wert mit der physischen Reihenfolge korreliert. Typisch: created_at in einer Append-only-Log-Tabelle. Das Ergebnis ist immer ein Bitmap Scan mit Recheck.
  19. BRIN-Varianten: Seit Version 14 gibt es minmax_multi (mehrere Intervalle, robuster bei Ausreissern) und bloom (für Gleichheit). Neue Ranges fasst erst VACUUM oder autosummarize = on zusammen.
  20. Write-Kosten: Jeder Index muss bei INSERT und DELETE (später via VACUUM) gepflegt werden. Er kostet WAL, Speicher und Cache. Ändert ein UPDATE eine indizierte Spalte, ist kein HOT-Update (Heap-Only Tuple) möglich. Dann bekommen alle Indizes einen neuen Eintrag.
  21. CREATE INDEX CONCURRENTLY: Normales CREATE INDEX nimmt einen SHARE-Lock und blockiert Schreiben. CONCURRENTLY blockiert Schreiben nicht. Preis: zwei Tabellen-Scans, Warten auf alte Transaktionen, nicht in einem Transaktionsblock. Bei Fehler bleibt ein INVALID Index zurück.
  22. REINDEX CONCURRENTLY (seit Version 12): Baut einen aufgeblähten Index ohne Schreibsperre neu.
  23. Unique und NULL: NULL gilt standardmässig als verschieden. Ein UNIQUE-Index erlaubt also viele NULL. Seit Version 15 ändert NULLS NOT DISTINCT das.
  24. Warum ein Index nicht genutzt wird: Funktion oder Cast auf der Spalte (WHERE date(created_at) = ...), falscher Typ, LIKE '%abc', zu viele Treffer, veraltete Statistiken. Bei nicht-C-Collation braucht LIKE 'abc%' die Opclass text_pattern_ops.
  25. Foreign Keys: PostgreSQL legt für die referenzierende Spalte keinen Index automatisch an. Ohne Index wird DELETE auf der Eltern-Tabelle langsam, weil jede Prüfung die Kind-Tabelle scannt.

5. Vergleich

  • B-Tree: =, Bereiche, Sortierung, Unique. Standard für fast alles.
  • Hash: nur =, kein Unique, kein Sortieren. Selten nötig.
  • GIN: „enthält“-Abfragen auf zusammengesetzten Werten: JSONB, Arrays, Volltext, Trigramme. Schnelles Lesen, teures Schreiben, gross.
  • GiST: Geometrie, Ranges, Nächste Nachbarn, Exclusion Constraints. Verlustbehaftet, also mit Recheck.
  • SP-GiST: nicht überlappende Partitionierung: Punkte, IPs, Präfixe.
  • BRIN: riesige, physisch sortierte Tabellen. Winzig, aber grob. Nutzlos ohne Korrelation.
  • Partial: nur ein Teil der Zeilen. Klein, gezielt, Bedingung muss in der Abfrage stehen.
  • Expression: Index auf lower(email) oder (data->>'key'). Ausdruck muss exakt passen.
  • Covering (INCLUDE): Zusatzspalten für Index-Only Scans. Macht den Index grösser.
  • PostgreSQL vs SQL Server/MySQL InnoDB: PostgreSQL hat keinen Clustered Index. Die Tabelle ist ein Heap. CLUSTER sortiert einmalig, die Ordnung zerfällt danach wieder.

6. In der Produktion

  1. CREATE INDEX blockiert Schreiben: Auf einer grossen Tabelle stehen alle Writes minutenlang. Lösung: immer CREATE INDEX CONCURRENTLY in Migrationen. In Flyway/Liquibase die Migration ausserhalb einer Transaktion laufen lassen.
  2. INVALID Index nach abgebrochenem CONCURRENTLY: Er kostet Schreibarbeit, hilft aber nicht beim Lesen. Lösung: mit pg_index.indisvalid = false finden, DROP INDEX CONCURRENTLY, neu anlegen.
  3. Zu viele Indizes: Inserts werden langsam, WAL und Replikations-Lag wachsen, HOT-Updates fallen weg. Lösung: ungenutzte und doppelte Indizes entfernen.
  4. Index wird nicht genutzt: Typisch WHERE lower(email) = ? ohne Expression Index, oder bigint-Spalte mit numeric-Parameter aus dem ORM. Lösung: Abfrage oder Index anpassen, mit EXPLAIN prüfen.
  5. Index-Only Scan langsam, viele Heap Fetches: Autovacuum kommt nicht nach, die Visibility Map ist veraltet. Lösung: Autovacuum für die Tabelle aggressiver einstellen.
  6. Index Bloat: Viele Updates und Deletes lassen Indizes wachsen. Lösung: REINDEX CONCURRENTLY, Ursache (lange Transaktionen, Autovacuum) beheben.
  7. Langsames DELETE auf Eltern-Tabelle: Foreign-Key-Spalte ohne Index. Lösung: Index auf die FK-Spalte.
  8. GIN-Lesen schwankt: Die Pending List ist gross. Lösung: gin_pending_list_limit anpassen, VACUUM öfter, oder fastupdate = off bei leseintensiven Tabellen.

7. Diagnose: Werkzeuge und Abfragen

-- ungenutzte Indizes (ohne Unique/PK), grösste zuerst
SELECT s.relname, s.indexrelname, s.idx_scan, s.last_idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC;

-- ungültige Indizes (abgebrochenes CONCURRENTLY)
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
  • EXPLAIN (ANALYZE, BUFFERS): welcher Index, Index Cond vs Filter, Heap Fetches, gelesene Pages.
  • pg_stat_user_indexes: idx_scan (Nutzung), last_idx_scan (seit Version 16). Achtung: Zähler gelten pro Server. Replicas separat prüfen. Statistik-Reset beachten.
  • pg_stat_user_tables: seq_scan vs idx_scan, n_tup_hot_upd (Anteil HOT-Updates).
  • pg_relation_size, pg_indexes_size: Grösse der Indizes.
  • pg_stat_progress_create_index: Fortschritt von CREATE INDEX.
  • pgstattuple-Extension, Funktion pgstatindex(): Füllgrad und Bloat eines B-Trees.
  • amcheck-Extension: prüft B-Tree-Indizes auf Korruption.

8. Senior-Punkte

  1. Indizes folgen den Abfragen, nicht dem Schema. Ich schaue zuerst in pg_stat_statements, dann entwerfe ich Indizes für die teuersten Muster.
  2. Ein Composite Index ersetzt oft mehrere einzelne. Gleichheit vorne, Bereich hinten, Sortierung am Ende. Ein Index (a, b) macht einen Index (a) meist überflüssig.
  3. Jeder Index ist eine Steuer auf Writes. Bei schreiblastigen Tabellen ist weniger mehr. HOT-Updates bleiben nur, wenn häufig geänderte Spalten nicht indiziert sind.
  4. Partial Indizes sind unterschätzt. Für Queues, offene Aufträge, Soft Delete sind sie klein und schnell.
  5. BRIN statt B-Tree bei Zeitreihen mit Milliarden Zeilen spart Gigabytes. Partitionierung nach Zeit ist oft die bessere Lösung, und beides geht zusammen.
  6. Migrationen immer CONCURRENTLY, mit Lock-Timeout und Monitoring. Ein Index-Build ist eine Betriebsaktion, keine Entwickler-Kleinigkeit.
  7. Indizes regelmässig aufräumen: ungenutzt, doppelt, ungültig, aufgebläht. Vor dem Löschen Replicas und Monatsjobs prüfen.

10. Fallen

  • „Mehr Indizes machen die Datenbank schneller.“ → Falsch. Nur das Lesen. Jeder Index verlangsamt Writes, kostet WAL und verhindert HOT-Updates.
  • „Ein Index (a, b) hilft auch bei WHERE b = ?.“ → Falsch in PostgreSQL 17. Ohne a fehlt der Leftmost Prefix. Skip Scan gibt es erst ab 18.
  • „Ein Index-Only Scan liest nie den Heap.“ → Falsch. Nur für Pages, die in der Visibility Map all-visible sind. Siehe Heap Fetches.
  • „PostgreSQL legt Indizes für Foreign Keys automatisch an.“ → Falsch. Nur für PRIMARY KEY und UNIQUE.
  • „Hash Index ist für Gleichheit immer besser.“ → Falsch. Kein Unique, kein Sortieren, kaum schneller. B-Tree ist meist richtig.
  • „BRIN funktioniert auf jeder Spalte.“ → Falsch. Nur bei Korrelation mit der physischen Reihenfolge, z. B. Einfügezeit.
  • „Ein Seq Scan ist immer schlecht.“ → Falsch. Bei vielen Treffern oder kleinen Tabellen ist er der schnellste Weg.
  • „CREATE INDEX CONCURRENTLY sperrt gar nichts.“ → Falsch. Er nimmt einen schwächeren Lock, wartet auf alte Transaktionen und blockiert anderes DDL.

11. Fragen

Was ist ein Index in PostgreSQL?

Eine eigene Datenstruktur neben der Tabelle. Sie bildet Schlüssel auf TIDs (Zeilen-Adressen im Heap) ab. Sie beschleunigt Lesen und verlangsamt Schreiben.

Wie ist ein B-Tree aufgebaut?

Root, Inner und Leaf Pages zu je 8 kB. Die Leaf Pages enthalten sortierte Schlüssel mit TIDs und sind doppelt verkettet. Der Baum ist balanciert und meist nur 3–4 Ebenen tief.

Welche Operatoren kann ein B-Tree?

Gleichheit, Bereiche, IN, IS NULL und LIKE mit festem Präfix. Er liefert auch sortierte Ergebnisse für ORDER BY.

Warum zählt die Reihenfolge in einem Composite Index?

Der Index ist nach Spalte 1, dann Spalte 2 sortiert. Nur ein Präfix von links ist effizient nutzbar. Gleichheitsspalten gehören nach vorne, Bereichsspalten nach hinten.

Was ist der Leftmost Prefix?

Ein Index (a, b, c) hilft bei Bedingungen auf a, a+b und a+b+c. Ohne a muss der ganze Index gelesen werden. Ab PostgreSQL 18 hilft Skip Scan teilweise.

Was ist ein Partial Index und wann nutzt man ihn?

Ein Index mit WHERE-Bedingung, der nur einen Teil der Zeilen enthält. Gut für offene Aufträge, Queues oder Soft Delete. Die Abfrage muss die Bedingung enthalten.

Was ist ein Expression Index?

Ein Index auf einem Ausdruck wie lower(email). Die Abfrage muss genau denselben Ausdruck nutzen. Die Funktion muss IMMUTABLE sein.

Was macht INCLUDE?

Es legt Zusatzspalten nur in die Leaf Pages. Sie zählen nicht zum Suchschlüssel und nicht zur Eindeutigkeit. Ziel ist ein Index-Only Scan.

Wann ist ein Index-Only Scan möglich?

Wenn alle benötigten Spalten im Index stehen und die Heap-Pages in der Visibility Map all-visible sind. Sonst gibt es Heap Fetches.

Was ist die Visibility Map?

Zwei Bits pro Heap-Page: all-visible und all-frozen. VACUUM setzt sie, jede Änderung löscht sie. Sie ermöglicht Index-Only Scans und schnelleres VACUUM.

Warum enthält ein PostgreSQL-Index keine Sichtbarkeitsinfo?

MVCC-Infos (xmin, xmax) stehen nur im Heap-Tupel. Sonst müsste jedes Update alle Indizes ändern. Darum braucht es den Heap oder die Visibility Map.

Index Scan vs Bitmap Scan?

Ein Index Scan holt jede Zeile sofort, gut bei wenigen Treffern und für Sortierung. Ein Bitmap Scan sammelt erst alle TIDs und liest den Heap in Page-Reihenfolge, gut bei mittleren Mengen und für AND/OR mehrerer Indizes.

Wann nimmt man GIN?

Für Werte mit vielen Teilen: JSONB, Arrays, Volltext, Trigramme. GIN speichert jeden Teilwert mit einer Liste der Zeilen.

jsonb_ops vs jsonb_path_ops?

jsonb_ops ist Standard und kann auch Key-Existenz (?, ?|, ?&). jsonb_path_ops kann nur @>, @? und @@, ist aber kleiner und schneller.

Warum ist GIN beim Schreiben teuer, und was hilft?

Eine Zeile erzeugt viele Einträge. Die Pending List (fastupdate) puffert sie. Dafür muss jedes Lesen die Liste mit durchsuchen.

Wofür ist GiST gut?

Für Geometrie (PostGIS), Ranges, Nächste-Nachbarn-Suche mit <-> und Exclusion Constraints. GiST arbeitet mit überlappenden Bounding Boxes und braucht einen Recheck.

GiST vs SP-GiST?

GiST erlaubt überlappende Bereiche, SP-GiST teilt den Raum ohne Überlappung (Quadtree, Radix Tree). SP-GiST passt gut zu Punkten, IPs und Präfixen.

Was ist BRIN und wann lohnt er sich?

Er speichert nur min/max pro Block Range (Standard 128 Pages). Er lohnt sich bei riesigen Tabellen, deren Werte mit der physischen Reihenfolge korrelieren, z. B. Einfügezeit.

Wann ist ein Hash Index sinnvoll?

Fast nie. Nur bei sehr langen Werten und reiner Gleichheit. Er kann kein Unique, kein Sortieren und keine mehreren Spalten.

Was kostet ein Index beim Schreiben?

Zusätzliche Page-Writes, WAL, Speicher und Cache. Bei Updates auf indizierten Spalten fällt HOT weg, dann bekommen alle Indizes neue Einträge.

Was ist ein HOT-Update?

Heap-Only Tuple: Die neue Zeilenversion liegt auf derselben Page, und keine indizierte Spalte ändert sich. Dann braucht kein Index einen neuen Eintrag.

Was macht CREATE INDEX CONCURRENTLY anders?

Es blockiert keine Writes. Dafür scannt es die Tabelle zweimal, wartet auf alte Transaktionen und läuft nicht in einer Transaktion. Bei Fehler bleibt ein INVALID Index.

Wie finden Sie ungenutzte Indizes?

pg_stat_user_indexes mit idx_scan = 0, ohne Unique-Indizes. Auf allen Replicas prüfen und den Zeitraum seit dem Statistik-Reset beachten.

Warum wird mein Index nicht genutzt?

Funktion oder Cast auf der Spalte, falscher Datentyp, LIKE mit führendem %, zu viele Treffer oder veraltete Statistiken. EXPLAIN zeigt es.

Braucht eine Foreign-Key-Spalte einen Index?

Meist ja. PostgreSQL legt ihn nicht automatisch an. Ohne Index scannt jedes DELETE oder UPDATE auf der Eltern-Tabelle die Kind-Tabelle.

Hat PostgreSQL einen Clustered Index?

Nein. Die Tabelle ist ein Heap. CLUSTER sortiert einmalig nach einem Index, die Ordnung geht bei neuen Writes wieder verloren.

Wie viele NULL erlaubt ein Unique Index?

Standardmässig beliebig viele, weil NULL als verschieden gilt. Mit NULLS NOT DISTINCT (seit Version 15) nur eines.

Szenario: Eine Migration mit CREATE INDEX legt die Produktion lahm. Was ist passiert, was tun Sie?

Normales CREATE INDEX blockiert alle Writes bis zum Ende. Abbrechen, mit CREATE INDEX CONCURRENTLY und lock_timeout neu ausrollen. Danach indisvalid prüfen.

Szenario: Inserts auf einer Event-Tabelle werden immer langsamer. Woran denken Sie?

An zu viele Indizes, besonders GIN, oder an Bloat. pg_stat_user_indexes und Grössen prüfen, ungenutzte Indizes löschen. Für created_at eventuell BRIN statt B-Tree.

Szenario: Eine Abfrage zeigt Index Only Scan, ist aber langsam. Warum?

Wahrscheinlich viele Heap Fetches, weil die Visibility Map veraltet ist. EXPLAIN (ANALYZE, BUFFERS) prüfen. Lösung: VACUUM, Autovacuum für die Tabelle aggressiver einstellen, lange Transaktionen beenden.
