Join-Algorithmen: Nested Loop, Hash Join, Merge Join

PostgreSQL · Tier 1 · Quellen: PostgreSQL 17 Doku (aktuell ist PostgreSQL 19; wichtige Unterschiede in 18/19 laut Release Notes stehen im Text), Kapitel 51.5 „Planner/Optimizer“ (Join-Strategien), Kapitel 14.1 „Using EXPLAIN“, Kapitel 19.4 „Resource Consumption“ (work_mem, hash_mem_multiplier), Kapitel 19.7 „Query Planning“ (enable_*, join_collapse_limit), Kapitel 15 „Parallel Query“; Markus Winand, „Use The Index, Luke“, Kapitel „The Join Operation“

Kern: Ein Join-Algorithmus ist die Methode, mit der PostgreSQL zwei Zeilenmengen zu passenden Paaren verbindet. Es gibt drei: Nested Loop (für wenige Zeilen mit Index), Hash Join (für grosse, unsortierte Mengen mit =) und Merge Join (für grosse, schon sortierte Mengen). Der Planner wählt nach geschätzten Zeilen. Eine falsche Schätzung führt zum falschen Algorithmus.

1. Wo sitzt der Join?

  1. Join-Knoten: Ein Knoten im Plan-Baum. Er hat immer genau zwei Kinder. Ein Join über 4 Tabellen sind also 3 Join-Knoten.
  2. Outer: das erste (obere) Kind in EXPLAIN. Es liefert die Zeilen, die den Join treiben.
  3. Inner: das zweite Kind. Beim Nested Loop wird es pro Outer-Zeile durchsucht, beim Hash Join wird es in eine Hash-Tabelle geladen.
  4. Scans: Seq Scan, Index Scan oder Bitmap Scan liefern die Zeilen an den Join.
  5. work_mem: Speichergrenze pro Hash-Tabelle und pro Sort. Passt es nicht, schreibt PostgreSQL temporäre Dateien.
  6. Planner: wählt Reihenfolge und Algorithmus nach den geschätzten Zeilen jeder Seite.

2. Die Reise eines Joins: drei Wege (die Geschichte zum Merken)

  1. Nested Loop. Die Abfrage will alle Bestellungen der 200 Kunden aus Bern. PostgreSQL liest die 200 Kunden (Outer). Für jeden Kunden sucht er im Index orders(customer_id) die Bestellungen (Inner). Der Inner-Knoten läuft also 200 Mal: loops=200. Ohne Index wäre jeder Durchlauf ein Seq Scan über 5 Mio. Zeilen.
  2. Hash Join, Build. Jetzt will der Report alle 5 Mio. Bestellungen mit Kundendaten. PostgreSQL liest die kleinere Seite (100 000 Kunden) einmal. Er baut daraus im RAM eine Hash-Tabelle über id.
  3. Hash Join, Probe. Dann liest er die 5 Mio. Bestellungen einmal. Für jede berechnet er den Hash von customer_id und schaut im passenden Bucket nach. Jede Tabelle wird nur einmal gelesen.
  4. Hash Join, Spill. Passt die Hash-Tabelle nicht in work_mem × hash_mem_multiplier, teilt PostgreSQL beide Seiten in Batches. Er schreibt die übrigen Batches in temporäre Dateien und arbeitet sie nacheinander ab. Das Ergebnis bleibt richtig, wird aber langsamer.
  5. Merge Join. Beide Seiten kommen sortiert nach dem Join-Schlüssel, z. B. aus zwei Indizes auf id. Zwei Zeiger laufen gleichzeitig. Sind die Werte gleich: Treffer. Sonst rückt der kleinere vor. Jede Seite wird einmal gelesen, und das Ergebnis ist schon sortiert.

3. Beispiel: drei Abfragen, drei Algorithmen

-- customers: 100 000 Zeilen, Index auf id (PK) und city
-- orders:    5 Mio. Zeilen, Index auf customer_id
SET max_parallel_workers_per_gather = 0;   -- Pläne einfacher lesbar

-- A) wenige Outer-Zeilen + Index auf Inner
EXPLAIN ANALYZE
SELECT c.name, o.amount FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE c.city = 'Bern';

-- B) alles mit allem, Aggregat
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.city, sum(o.amount) FROM orders o JOIN customers c ON c.id = o.customer_id
GROUP BY c.city;

-- C) dasselbe B mit kleinem work_mem
SET work_mem = '1MB';
EXPLAIN (ANALYZE, BUFFERS) ... wie B ...

        Index Cond: (customer_id = c.id)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Zeiten und Kosten sind Beispielwerte, gekürzt mit „...“. Die Form der Pläne ist das, was zählt.

  1. A: Nur ca. 200 Kunden in Bern. Der Planner nimmt Nested Loop. Der Inner-Knoten zeigt loops=197: 197 Index-Lookups mit je ca. 50 Zeilen. Index Cond: (customer_id = c.id) heisst: der Wert kommt aus der Outer-Zeile (parametrisierter Index Scan).
  2. B: Alle Zeilen beider Tabellen. Der Planner nimmt Hash Join. Unter Hash steht die kleinere Tabelle (customers). Batches: 1 heisst: Die Hash-Tabelle (ca. 6 MB) passte in den Hash-Speicher. Standard ist work_mem 4 MB × hash_mem_multiplier 2.0 = 8 MB.
  3. C: Mit 1 MB work_mem passt die Hash-Tabelle nicht. Batches: 4 und temp written zeigen den Spill auf Platte. Beide Seiten werden in temporäre Dateien partitioniert.
  4. Merge Join sieht man typisch bei ... JOIN ... ORDER BY c.id, wenn beide Seiten einen Index auf dem Schlüssel haben. Im Plan: Merge Join, Merge Cond, zwei Index Scans darunter, kein Sort.

4. Details, die Interviewer fragen

  1. Nested Loop: Für jede Outer-Zeile wird die Inner-Seite durchsucht. Kosten ohne Index: Outer × Inner, also O(N·M). Mit Index auf der Inner-Seite: Outer × log(Inner). Er kann jede Join-Bedingung: =, <, BETWEEN, LIKE, Geo-Funktionen.
  2. Nested Loop Startkosten: sehr klein. Die erste Ergebniszeile kommt sofort. Darum gewinnt er oft bei LIMIT und bei EXISTS.
  3. Materialize: Hat die Inner-Seite keinen Index, kann PostgreSQL sie einmal in den Speicher legen (Materialize-Knoten). Dann liest er sie nicht jedes Mal neu von der Tabelle.
  4. Memoize (seit PostgreSQL 14): Ein Cache zwischen Nested Loop und Inner-Seite. Wiederholt sich der Outer-Schlüssel, kommt das Ergebnis aus dem Cache. Im Plan: Memoize mit Hits und Misses.
  5. Hash Join: Build-Phase über die Inner-Seite (die kleinere), Probe-Phase über die Outer-Seite. Kosten ca. O(N + M). Nur für Gleichheit (=). Hohe Startkosten, weil die Hash-Tabelle erst fertig sein muss. Ergebnis ist unsortiert.
  6. Hash-Speicher: Grenze ist work_mem × hash_mem_multiplier. Standard 4 MB × 2.0 = 8 MB (Multiplikator 2.0 seit Version 15). Im Plan: Buckets, Batches, Memory Usage.
  7. Batches: Batches: 1 = alles im RAM. Mehr Batches = Spill in temporäre Dateien. Batches: 8 (originally 1) heisst: Die Schätzung war zu klein, PostgreSQL musste während der Ausführung nachteilen.
  8. Skew: Sehr häufige Werte auf der Outer-Seite behandelt der Hash Join gesondert (Skew-Optimierung über die MCV-Statistik). Trotzdem können Batches mit einem Riesenwert ungleich gross werden.
  9. Parallel Hash Join (seit Version 11): Mehrere Worker bauen gemeinsam eine geteilte Hash-Tabelle. Im Plan: Parallel Hash Join und Parallel Hash.
  10. Merge Join: Beide Seiten müssen nach dem Join-Schlüssel sortiert sein. Entweder durch einen Index oder durch einen Sort-Knoten. Kosten O(N + M) plus Sortieren. Nur für Gleichheit (mergejoinable Operatoren).
  11. Merge Join mit Duplikaten: Gibt es auf beiden Seiten gleiche Schlüssel, muss die Inner-Seite zurückspulen (mark/restore). Darum steht manchmal ein Materialize unter dem Merge Join.
  12. Wann der Planner was wählt: Kleine Outer-Seite und Index innen → Nested Loop. Grosse Mengen ohne Ordnung → Hash Join. Beide schon sortiert oder sortiertes Ergebnis nötig → Merge Join. Nicht-Gleichheit → nur Nested Loop.
  13. FULL OUTER JOIN: Geht nur mit Hash Join oder Merge Join, also nur mit einer Gleichheitsbedingung. Sonst Fehler: „FULL JOIN is only supported with merge-joinable or hash-joinable join conditions“.
  14. Semi Join und Anti Join: EXISTS wird zu einem Semi Join (stoppt beim ersten Treffer). NOT EXISTS wird zu einem Anti Join. Alle drei Algorithmen gibt es in diesen Varianten.
  15. NOT IN: Kann kein Anti Join werden, weil NULL die Logik ändert. Ein einziges NULL in der Unterabfrage macht das Ergebnis leer. Darum NOT EXISTS nutzen.
  16. Join-Reihenfolge: Der Planner tauscht Tabellen frei, bis join_collapse_limit (8). Darüber behält er die geschriebene Reihenfolge. Ab geqo_threshold (12) nutzt er GEQO.
  17. work_mem ist pro Knoten: Ein Plan mit 3 Hash Joins und 2 Sorts darf 5 × work_mem (Hash × 2) nutzen. Dazu pro paralleler Worker. Darum ist ein globales work_mem = 1GB bei vielen Verbindungen gefährlich.
  18. Indizes für Joins: Ein Nested Loop braucht einen Index auf der Join-Spalte der Inner-Seite, typisch die Foreign-Key-Spalte. Hash Join braucht keinen Index. Merge Join profitiert von Indizes, weil der Sort wegfällt.

5. Vergleich

AlgorithmusGut, wenn …Schwäche
Nested Loopwenige Outer-Zeilen, Index innen, LIMIT, jede Bedingungexplodiert bei vielen Outer-Zeilen
Hash Joingrosse, unsortierte Mengen, nur =Speicher, Spill, hohe Startkosten
Merge Joinbeide Seiten sortiert, sortiertes Ergebnis nötigSortieren kostet, nur =
  • PostgreSQL vs Spark: Spark hat Broadcast Hash Join (kleine Seite an alle Executors) und Sort-Merge Join (Standard für grosse Seiten). Die Ideen sind dieselben, verteilt über Knoten.
  • PostgreSQL vs MySQL: MySQL hatte lange nur Nested Loop. Hash Join kam erst mit 8.0.18.

6. In der Produktion

  1. Nested Loop mit Millionen loops: Die Outer-Seite wurde auf 1 Zeile geschätzt, es sind 500 000. Die Abfrage läuft Minuten statt Sekunden. Lösung: Schätzung reparieren (ANALYZE, CREATE STATISTICS), Abfrage umschreiben. Zum Testen SET enable_nestloop = off in der Session.
  2. Hash Join spillt: Batches > 1 und viele temp-Buffers. Lösung: SET work_mem für diese Abfrage oder Rolle erhöhen. Oder die Build-Seite kleiner machen (weniger Spalten, früher filtern).
  3. Out of Memory bei vielen Verbindungen: work_mem global hoch gesetzt, viele parallele Hash Joins. Lösung: global moderat lassen, gezielt pro Session erhöhen. Verbindungen mit einem Pool begrenzen.
  4. Temp-Dateien füllen die Platte: Riesige Spills. Lösung: temp_file_limit setzen, log_temp_files aktivieren, Abfrage reparieren.
  5. Fehlender Index auf Foreign Key: Nested Loop macht pro Zeile einen Seq Scan. Lösung: Index auf die FK-Spalte.
  6. ORM erzeugt 12+ Joins: Planner nutzt GEQO, Pläne schwanken. Lösung: weniger Joins pro Abfrage, eventuell join_collapse_limit anpassen.

7. Diagnose: Werkzeuge und Abfragen

  • EXPLAIN (ANALYZE, BUFFERS): Join-Typ, Hash Cond/Merge Cond/Join Filter, loops, Batches, temp read/written.
  • SET enable_nestloop / enable_hashjoin / enable_mergejoin = off: nur in einer Test-Session, um Alternativen zu vergleichen.
  • log_temp_files = 0: loggt jede temporäre Datei mit Grösse.
  • pg_stat_statements.temp_blks_written: welche Abfragen auf Platte spillen.
  • pg_stat_database.temp_files und temp_bytes: Spills für die ganze Datenbank.
  • SHOW work_mem; SHOW hash_mem_multiplier;: aktuelle Grenzen der Session.

8. Senior-Punkte

  1. Kein Algorithmus ist „schlecht“. Der falsche Algorithmus kommt fast immer von einer falschen Zeilenschätzung. Ich repariere die Schätzung, nicht den Join.
  2. Nested Loop ist der Risiko-Join. Er ist der beste bei kleinen Mengen und der schlimmste bei grossen. Eine Unterschätzung um Faktor 1000 trifft ihn am härtesten.
  3. work_mem ist ein Budget, keine Einstellung pro Abfrage. Rechnung: Verbindungen × Knoten × work_mem × Multiplikator. Gezielt pro Rolle oder Session erhöhen, z. B. für Reporting.
  4. OLTP und Reporting trennen. OLTP will Nested Loops mit Index. Reporting will Hash Joins mit viel Speicher. Eine Read Replica oder eigene Rolle mit eigenem work_mem hilft.
  5. Indizes auf FK-Spalten sind die Grundlage für schnelle Nested Loops und für schnelle Deletes.
  6. EXISTS statt NOT IN und statt DISTINCT über Joins: Semi und Anti Joins sind sicherer und oft schneller.

9. Aus dem Projekt

„Join-Tuning in PostgreSQL ist in meinem Profil nicht belegt. Am nächsten dran ist MATCH: Dort laufen PySpark-Jobs, und Spark nutzt dieselben Ideen, Broadcast Hash Join und Sort-Merge Join.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Hash Join ist immer am schnellsten.“ → Falsch. Bei wenigen Zeilen mit Index ist Nested Loop schneller, und Hash Join hat hohe Startkosten.
  • „Nested Loop heisst, es fehlt ein Index.“ → Falsch. Mit Index innen und kleiner Outer-Seite ist er optimal.
  • „Hash Join geht auch für < und BETWEEN.“ → Falsch. Nur für Gleichheit. Merge Join auch nur für Gleichheit.
  • „work_mem ist der Speicher pro Abfrage.“ → Falsch. Pro Sort- oder Hash-Knoten, pro Worker. Eine Abfrage kann ein Vielfaches nutzen.
  • „Wenn die Hash-Tabelle nicht passt, bricht die Abfrage ab.“ → Falsch. Sie spillt in Batches auf Platte und wird langsamer.
  • „NOT IN und NOT EXISTS sind gleich.“ → Falsch. Ein NULL in der Unterabfrage macht NOT IN leer, und es wird kein Anti Join.
  • „Die Reihenfolge im SQL bestimmt die Join-Reihenfolge.“ → Falsch bis join_collapse_limit. Der Planner ordnet selbst.

11. Fragen

Welche Join-Algorithmen hat PostgreSQL?

Nested Loop, Hash Join und Merge Join. Dazu Varianten für Semi, Anti und Outer Joins sowie parallele Versionen.

Wie funktioniert ein Nested Loop?

Für jede Zeile der Outer-Seite wird die Inner-Seite durchsucht, am besten über einen Index. Kosten: Outer-Zeilen × Kosten eines Lookups.

Wann wählt der Planner Nested Loop?

Bei wenigen Outer-Zeilen und einem Index auf der Inner-Seite, bei LIMIT und bei Nicht-Gleichheits-Bedingungen. Für Nicht-Gleichheit ist er die einzige Option.

Wie funktioniert ein Hash Join?

Build: die kleinere Seite wird in eine Hash-Tabelle geladen. Probe: die grössere Seite wird gelesen, jede Zeile wird im passenden Bucket gesucht.

Wann wählt der Planner Hash Join?

Bei grossen, unsortierten Mengen mit Gleichheitsbedingung, wenn die kleinere Seite in den Hash-Speicher passt.

Welche Seite wird beim Hash Join gehasht?

Die Inner-Seite, im Plan unter dem Knoten „Hash“. Der Planner legt dorthin meist die kleinere Menge.

Was passiert, wenn die Hash-Tabelle nicht in den Speicher passt?

PostgreSQL teilt beide Seiten in Batches und schreibt sie in temporäre Dateien. Im Plan steht Batches grösser als 1 und temp read/written.

Was ist hash_mem_multiplier?

Ein Faktor auf work_mem nur für Hash-Operationen. Standard 2.0 seit PostgreSQL 15. Hash-Tabellen dürfen also doppelt so viel nutzen wie Sorts.

Wie funktioniert ein Merge Join?

Beide Seiten sind nach dem Schlüssel sortiert. Zwei Zeiger laufen gleichzeitig, der kleinere rückt vor, gleiche Werte sind Treffer.

Wann wählt der Planner Merge Join?

Wenn beide Seiten schon sortiert sind, z. B. durch Indizes, oder wenn das Ergebnis sortiert gebraucht wird. Auch bei sehr grossen Mengen, die nicht in den Hash-Speicher passen.

Welche Algorithmen können FULL OUTER JOIN?

Nur Hash Join und Merge Join, also nur mit Gleichheitsbedingung.

Was ist Memoize?

Ein Cache seit PostgreSQL 14 zwischen Nested Loop und Inner-Seite. Bei wiederholten Schlüsseln kommt das Ergebnis aus dem Cache statt aus einem neuen Lookup.

Was ist ein Semi Join?

Ein Join, der pro Outer-Zeile nur prüft, ob es mindestens einen Treffer gibt. Typisch aus EXISTS oder IN.

Warum ist NOT EXISTS besser als NOT IN?

NOT IN liefert bei einem NULL in der Unterabfrage keine Zeilen. Darum kann es kein Anti Join werden. NOT EXISTS ist korrekt und wird ein Anti Join.

Was bedeutet loops beim Inner-Knoten eines Nested Loop?

Wie oft die Inner-Seite durchsucht wurde, also meist die Zahl der Outer-Zeilen. Zeit und Zeilen sind pro Durchlauf.

Welche Indizes helfen Joins?

Ein Index auf der Join-Spalte der Inner-Seite für Nested Loops, typisch die FK-Spalte. Für Merge Join Indizes auf beiden Schlüsseln, damit der Sort wegfällt.

Warum ist work_mem gefährlich hoch?

Es gilt pro Sort- und Hash-Knoten und pro Worker. Viele Verbindungen mit mehreren Knoten können den Server in Out of Memory treiben.

Bestimmt die Reihenfolge im SQL die Join-Reihenfolge?

Nein, bis join_collapse_limit (8) ordnet der Planner frei. Darüber hält er sich an die geschriebene Reihenfolge.

Was ist ein Parallel Hash Join?

Mehrere Worker bauen gemeinsam eine geteilte Hash-Tabelle und proben parallel. Seit PostgreSQL 11.

Wie testen Sie, ob ein anderer Join-Algorithmus besser wäre?

In einer Test-Session z. B. SET enable_nestloop = off und EXPLAIN ANALYZE vergleichen. Danach die eigentliche Ursache beheben, nicht den Schalter in die Produktion bringen.

Szenario: Eine Abfrage läuft 20 Minuten, der Plan zeigt Nested Loop mit loops=800000. Was tun Sie?

Die Outer-Seite wurde unterschätzt. Schätzung vs actual rows prüfen, ANALYZE oder CREATE STATISTICS, eventuell Abfrage umschreiben. Mit enable_nestloop = off testen, ob Hash Join schneller wäre.

Szenario: Ein Report schreibt Gigabytes an temporären Dateien. Was tun Sie?

EXPLAIN (ANALYZE, BUFFERS) auf Batches und Sort Method prüfen. work_mem nur für die Reporting-Rolle erhöhen, Spalten und Zeilen früher reduzieren, temp_file_limit setzen.

Szenario: Nach dem Erhöhen von work_mem auf 512 MB stürzt die Datenbank unter Last ab. Warum?

work_mem gilt pro Knoten, pro Worker und pro Verbindung. Hunderte Verbindungen mit Hash Joins brauchen dann viel mehr RAM als vorhanden. Global zurücksetzen und gezielt pro Rolle erhöhen.
