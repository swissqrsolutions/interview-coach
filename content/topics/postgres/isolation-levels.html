Isolation Levels und Anomalien

PostgreSQL · Tier 1 · Quellen: PostgreSQL 17 Doku (aktuell ist PostgreSQL 19; wichtige Unterschiede in 18/19 laut Release Notes stehen im Text): „Concurrency Control“ – „Transaction Isolation“ (Read Committed, Repeatable Read, Serializable), „Serialization Failure Handling“, „Data Consistency Checks at the Application Level“, SQL-Befehl SET TRANSACTION, Anhang „PostgreSQL Error Codes“ (40001, 40P01), PostgreSQL Wiki „SSI“, PostgreSQL 19 Doku „Lock Management“ (max_pred_locks_*)

Gerüst

Warum?
Parallele Transaktionen erzeugen Anomalien: Lost Update, Write Skew. Das Level tauscht Anomalien gegen Abbrüche.
Wie innen?
MVCC-Snapshot: Read Committed pro Befehl, Repeatable Read pro Transaktion. Serializable = Snapshot + SSI, SIRead Locks blockieren nie.
Zahlen
SQLSTATE 40001 = Serialization Failure, 40P01 = Deadlock. 64 Predicate Locks pro Transaktion, über 32 pro Tabelle → Tabellen-Lock.
Vergleich
PG Repeatable Read verhindert Phantoms, der Standard nicht. Oracle „Serializable“ ist Snapshot Isolation mit Write Skew.
Produktion
Serializable ohne Retry → Fehler 500. Seq Scan → Lock auf ganze Tabelle → mehr False Positives.
Design
Standard Read Committed + atomares UPDATE. Serializable nur für Mehrzeilen-Regeln, mit zentralem Retry. Constraint schlägt Isolation.

Antwort-Muster

Frage: Welche Isolation Levels gibt es, und welches nehmen Sie?

  1. Mechanismus: Read Committed, Repeatable Read und Serializable, alle auf MVCC-Snapshots.
  2. Zahl: Ab Repeatable Read kann eine Transaktion mit SQLSTATE 40001 abbrechen.
  3. Trade-off: Ein höheres Level verhindert mehr Anomalien, braucht aber Retries.
  4. Produktion: Ich lasse Read Committed, schreibe Updates atomar und nutze Serializable nur mit zentralem Retry.
Kern: Ein Isolation Level legt fest, wie viel eine Transaktion von parallelen Transaktionen sieht. PostgreSQL hat drei echte Stufen: Read Committed (Standard, Snapshot pro Befehl), Repeatable Read (ein Snapshot pro Transaktion) und Serializable (Snapshot plus SSI, das gefährliche Muster erkennt). Je höher die Stufe, desto weniger Anomalien, aber desto mehr Serialization Failures, die die Anwendung wiederholen muss.

1. Wo sitzt die Isolation?

  1. Transaktion: hat ein Level, gesetzt mit BEGIN ISOLATION LEVEL … oder default_transaction_isolation.
  2. Snapshot: bestimmt, welche Versionen die Transaktion sieht. Read Committed nimmt pro Befehl einen neuen.
  3. Heap: hält alle Versionen. Leser lesen ohne Sperre.
  4. Row Locks: Zwei Schreiber auf dieselbe Zeile warten aufeinander, in jedem Level.
  5. SSI: Serializable Snapshot Isolation. Nur bei Serializable merkt sich PostgreSQL, was gelesen wurde (SIRead Locks). Diese Locks blockieren nie.
  6. Fehler 40001: serialization_failure. Die Transaktion wird abgebrochen. Die Anwendung muss sie komplett wiederholen.

2. Die Reise einer Write-Skew-Anomalie (die Geschichte zum Merken)

  1. Alice prüft: Regel: Mindestens ein Arzt muss im Dienst sein. Alice startet eine Transaktion und zählt: 2 im Dienst. Sie darf gehen.
  2. Bob prüft gleichzeitig: Sein Snapshot sieht auch 2. Er darf auch gehen.
  3. Alice schreibt: UPDATE doctors SET on_call = false WHERE name = 'Alice'.
  4. Bob schreibt: Er ändert eine andere Zeile (Bob). Darum gibt es keinen Row-Lock-Konflikt.
  5. Alice committet. Alles gut aus ihrer Sicht.
  6. Bob committet: In Repeatable Read klappt es. Jetzt ist niemand im Dienst. Das ist Write Skew: Jeder hat korrekt gelesen, aber zusammen brechen sie die Regel.
  7. Serializable erkennt es: SSI sieht zwei rw-Abhängigkeiten (A las, was B schrieb, und umgekehrt). Einer muss abbrechen: Fehler 40001. Bob wiederholt, sieht nun 1 Arzt und darf nicht gehen.

3. Beispiel: Lost Update und Write Skew

CREATE TABLE konto   (id int PRIMARY KEY, saldo int);
CREATE TABLE doctors (name text PRIMARY KEY, on_call bool);
INSERT INTO konto VALUES (1, 100);
INSERT INTO doctors VALUES ('Alice', true), ('Bob', true);

-- A) Lost Update unter REPEATABLE READ
A: BEGIN ISOLATION LEVEL REPEATABLE READ;  SELECT saldo FROM konto WHERE id = 1;  -- 100
B: BEGIN ISOLATION LEVEL REPEATABLE READ;  SELECT saldo FROM konto WHERE id = 1;  -- 100
A: UPDATE konto SET saldo = 100 + 10 WHERE id = 1;  COMMIT;
B: UPDATE konto SET saldo = 100 + 20 WHERE id = 1;

-- B) Write Skew unter SERIALIZABLE
A: BEGIN ISOLATION LEVEL SERIALIZABLE;  SELECT count(*) FROM doctors WHERE on_call;  -- 2
B: BEGIN ISOLATION LEVEL SERIALIZABLE;  SELECT count(*) FROM doctors WHERE on_call;  -- 2
A: UPDATE doctors SET on_call = false WHERE name = 'Alice';
B: UPDATE doctors SET on_call = false WHERE name = 'Bob';
A: COMMIT;
B: COMMIT;
-- A) Session B beim UPDATE:
ERROR:  could not serialize access due to concurrent update

-- B) Session B beim COMMIT:
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.

Erwartetes Ergebnis (laut Doku, nicht ausgeführt), zwei psql-Sessions mit PostgreSQL 17. Der „Reason code“ kann je nach Ablauf anders lauten.

  1. In A rechnet die Anwendung den neuen Wert selbst (read-modify-write). Unter Read Committed würde B einfach 120 schreiben. Die +10 von A wären verloren: Lost Update.
  2. Unter Repeatable Read merkt B: Die Zeile wurde nach meinem Snapshot geändert. B bekommt 40001 statt den Wert zu überschreiben.
  3. In B ändern A und B verschiedene Zeilen. Es gibt keinen Lock-Konflikt. Unter Repeatable Read kämen beide durch.
  4. Unter Serializable erkennt SSI den Zyklus und bricht B ab. Der HINT sagt es klar: wiederholen.
  5. Beide Fehler haben SQLSTATE 40001. Der Retry-Code muss genau darauf reagieren.

4. Details, die Interviewer fragen

  1. Dirty Read: Lesen von nicht committeten Daten. In PostgreSQL nie möglich. READ UNCOMMITTED verhält sich wie Read Committed.
  2. Non-repeatable Read: Dieselbe Zeile zweimal gelesen, anderer Wert, weil jemand dazwischen committet hat. Möglich in Read Committed.
  3. Phantom Read: Dieselbe Abfrage mit WHERE liefert beim zweiten Mal neue Zeilen. Möglich in Read Committed. In PostgreSQL-Repeatable-Read nicht möglich, strenger als der SQL-Standard.
  4. Lost Update: Zwei Transaktionen lesen, rechnen und schreiben. Eine überschreibt die andere. Möglich in Read Committed bei read-modify-write in der App.
  5. Write Skew: Zwei Transaktionen lesen überlappende Daten und schreiben verschiedene Zeilen. Eine Regel über mehrere Zeilen bricht. Möglich bis Repeatable Read.
  6. Read Committed im Detail: Jeder Befehl hat einen neuen Snapshot. Trifft ein UPDATE auf eine gerade gesperrte Zeile, wartet es. Nach dem COMMIT des anderen prüft es die neueste Version erneut gegen das WHERE.
  7. Repeatable Read im Detail: Ein Snapshot für die ganze Transaktion, genommen beim ersten Befehl. Das ist Snapshot Isolation. Will sie eine Zeile ändern, die seit dem Snapshot geändert wurde, kommt 40001.
  8. Serializable (SSI): Wie Repeatable Read plus Überwachung. PostgreSQL merkt sich Lesezugriffe als SIRead Locks (Predicate Locks). Findet es zwei aufeinanderfolgende rw-Abhängigkeiten mit einem „Pivot“, bricht es eine Transaktion ab.
  9. False Positives: SSI bricht manchmal ab, obwohl kein echter Fehler entstanden wäre. Grund: grobe Locks, z. B. auf Seite oder Tabelle statt Zeile. Sequential Scans sperren die ganze Tabelle als Prädikat.
  10. Retry-Regel: Bei 40001 (und 40P01 Deadlock) die ganze Transaktion wiederholen, inklusive aller Lesezugriffe. Nicht nur den letzten Befehl. Mit Obergrenze und kurzem Backoff.
  11. READ ONLY DEFERRABLE: BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE wartet auf einen sicheren Snapshot. Danach kann sie nie mit 40001 scheitern. Gut für lange Reports.
  12. Mischen von Levels: SSI schützt nur Transaktionen, die selbst Serializable laufen. Eine Read-Committed-Transaktion daneben kann trotzdem Anomalien erzeugen.
  13. Replicas: Auf einem Hot Standby gibt es kein Serializable. Dort geht höchstens Repeatable Read.
  14. Lost Update ohne höheres Level verhindern: atomares UPDATE … SET saldo = saldo + 10, SELECT … FOR UPDATE, oder optimistisch mit Versionsspalte (WHERE version = 7, JPA @Version).
  15. Write Skew ohne Serializable verhindern: Die gelesenen Zeilen mit FOR UPDATE sperren. Oder den Konflikt „materialisieren“: eine Zeile, die beide ändern müssen. Oder ein Constraint.

5. Vergleich

  • Read Committed: kein Dirty Read. Non-repeatable Read, Phantom, Lost Update und Write Skew möglich. Fast nie 40001.
  • Repeatable Read: kein Dirty, Non-repeatable oder Phantom Read. Lost Update wird zu Fehler 40001. Write Skew möglich.
  • Serializable: keine Anomalie. Ergebnis wie bei einer seriellen Reihenfolge. Mehr 40001, etwas Overhead für Predicate Locks.
  • SQL-Standard vs PostgreSQL: Der Standard erlaubt Phantoms in Repeatable Read. PostgreSQL verhindert sie. Read Uncommitted gibt es nur dem Namen nach.
  • SQL Server: Standard Read Committed mit Locks: Leser warten auf Schreiber. SNAPSHOT entspricht etwa PostgreSQL Repeatable Read. Serializable dort mit Range Locks, also blockierend.
  • Oracle: Standard Read Committed. Sein „Serializable“ ist Snapshot Isolation, erlaubt also Write Skew.
  • MySQL InnoDB: Standard Repeatable Read mit Gap Locks gegen Phantoms bei sperrenden Reads.
  • Pessimistisch vs optimistisch: FOR UPDATE wartet vorher. Repeatable Read, Serializable und @Version scheitern nachher und brauchen Retry.

6. In der Produktion

  1. Lost Update in Read Committed: Lagerbestand per SELECT lesen, in Java rechnen, zurückschreiben. Unter Last stimmt der Bestand nicht. Lösung: SET bestand = bestand - 1 mit WHERE bestand > 0, oder FOR UPDATE.
  2. Serializable ohne Retry: Das Team schaltet Serializable ein. Unter Last sehen Nutzer Fehler 500. Lösung: generischer Retry für 40001 um die ganze Transaktion.
  3. Retry wiederholt Seiteneffekte: Die Transaktion schickt vor dem COMMIT eine E-Mail. Bei Retry kommt sie doppelt. Lösung: Seiteneffekte erst nach COMMIT, z. B. per Outbox.
  4. Viele False Positives: Serializable mit vielen Sequential Scans sperrt ganze Tabellen als Prädikat. Lösung: passende Indexe, kurze Transaktionen, max_pred_locks_per_transaction erhöhen.
  5. Report ist inkonsistent: Ein Report liest mehrere Tabellen in Read Committed. Zwischen den Abfragen ändern sich Daten. Lösung: Repeatable Read oder Serializable Read Only Deferrable für den Report.
  6. Lange Repeatable-Read-Transaktion: Sie hält einen alten Snapshot. VACUUM kann nicht aufräumen. Lösung: Reports kurz halten oder auf eine Replica legen.

7. Diagnose: Werkzeuge und Abfragen

SHOW default_transaction_isolation;          -- read committed
SHOW transaction_isolation;                  -- aktuelle Transaktion

-- Predicate Locks von SSI sehen
SELECT pid, locktype, relation::regclass, page, tuple
FROM pg_locks WHERE mode = 'SIReadLock';

-- Abbrüche zählen (PostgreSQL 17)
SELECT datname, xact_rollback, conflicts, deadlocks FROM pg_stat_database;
  • Logs: Fehler mit SQLSTATE 40001 zählen. log_line_prefix mit %e zeigt den SQLSTATE.
  • pg_locks mit mode = 'SIReadLock': wie grob SSI sperrt (Tupel, Seite, Relation).
  • pg_stat_database: xact_rollback und deadlocks steigen bei vielen Konflikten.
  • Anwendungs-Metrik: Anzahl Retries pro Endpoint. Sie zeigt Hotspots.
  • max_pred_locks_per_transaction (64), max_pred_locks_per_relation, max_pred_locks_per_page: steuern, wann SSI auf gröbere Locks wechselt.
  • Die Standardwerte genau: max_pred_locks_per_page = 2. Ab mehr als 2 gesperrten Tupeln einer Seite gilt der Lock für die ganze Seite. max_pred_locks_per_relation = -2 heisst: 64 / 2 = 32 Seiten- oder Tupel-Locks pro Tabelle, dann ein Lock auf die ganze Tabelle.
  • Warum das zählt: Jede Vergröberung meldet mehr scheinbare Konflikte. Die Doku nennt das als Grund für steigende 40001-Raten. Gegenmittel: die drei Werte erhöhen oder Index Scans statt Seq Scans.

8. Senior-Punkte

  1. Read Committed ist oft genug, wenn Updates atomar formuliert sind. Die meisten Bugs kommen von read-modify-write im Code.
  2. Serializable ist die einfachste korrekte Lösung für komplexe Regeln über mehrere Zeilen. Der Preis: Retry-Logik und etwas Durchsatz.
  3. Retry ist Pflicht ab Repeatable Read. Er gehört an eine zentrale Stelle, nicht in jede Methode. Seiteneffekte erst nach dem COMMIT.
  4. Pessimistisch bei hohem Konflikt, optimistisch bei seltenem Konflikt. Viele Retries kosten mehr als kurzes Warten.
  5. Isolation Level ist pro Transaktion wählbar. Standard lassen und nur kritische Pfade höher stellen.
  6. Constraints schlagen Isolation. Ein UNIQUE- oder EXCLUDE-Constraint schützt eine Regel in jedem Level.

9. Aus dem Projekt

„Bei MATCH darf eine Nachricht nicht doppelt verarbeitet werden. Darum holt ein Job sie mit einem einzigen atomaren UPDATE (Pending → Processing), nicht mit SELECT und danach UPDATE. In PostgreSQL wäre das UPDATE … RETURNING. Dafür reicht Read Committed.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „PostgreSQL erlaubt Dirty Reads mit READ UNCOMMITTED.“ → Falsch. READ UNCOMMITTED ist dort Read Committed.
  • „Repeatable Read erlaubt Phantoms.“ → Falsch für PostgreSQL. Nur der SQL-Standard erlaubt sie.
  • „Repeatable Read ist schon serialisierbar.“ → Falsch. Write Skew ist möglich.
  • „Serializable sperrt alles und ist darum langsam.“ → Falsch für PostgreSQL. SIRead Locks blockieren nie. Es bricht stattdessen ab.
  • „Bei 40001 wiederhole ich den letzten Befehl.“ → Falsch. Die ganze Transaktion muss neu laufen, mit neuem Snapshot.
  • „Der Snapshot gilt ab BEGIN.“ → Falsch. Ab dem ersten Befehl.
  • „Ein höheres Level verhindert Deadlocks.“ → Falsch. Deadlocks kommen von Row Locks und gibt es in jedem Level.

11. Selbsttest

Warum?

Warum gibt es überhaupt verschiedene Isolation Levels?

Mehr Isolation verhindert mehr Anomalien, führt aber zu mehr Abbrüchen und Retries. Jede Transaktion wählt ihren Kompromiss selbst.

Was ist ein Dirty Read?

Lesen von Daten, die noch nicht committed sind. In PostgreSQL in keinem Level möglich.

Was ist ein Non-repeatable Read?

Dieselbe Zeile liefert beim zweiten Lesen einen anderen Wert, weil jemand dazwischen committet hat. Möglich in Read Committed.

Was ist ein Phantom Read?

Dieselbe Abfrage liefert beim zweiten Mal neue Zeilen. In PostgreSQL nur in Read Committed möglich.

Was ist ein Lost Update?

Zwei Transaktionen lesen denselben Wert, rechnen und schreiben. Die zweite überschreibt die erste. Typisch bei read-modify-write in der App.

Was ist Write Skew?

Zwei Transaktionen lesen dieselben Daten und schreiben verschiedene Zeilen. Jede für sich ist korrekt, zusammen brechen sie eine Regel.

Wie innen?

Welche Isolation Levels hat PostgreSQL?

Read Committed (Standard), Repeatable Read und Serializable. Read Uncommitted wird als Read Committed behandelt.

Wie funktioniert Read Committed?

Jeder Befehl sieht einen neuen Snapshot. Bei gesperrten Zeilen wartet ein UPDATE und prüft danach die neueste Version gegen das WHERE.

Wie funktioniert Repeatable Read in PostgreSQL?

Ein Snapshot für die ganze Transaktion, ab dem ersten Befehl. Ändert sie eine Zeile, die seit dem Snapshot geändert wurde, kommt Fehler 40001.

Was ist Snapshot Isolation?

Jede Transaktion liest aus einem festen Snapshot. Konkurrierende Schreibzugriffe auf dieselbe Zeile scheitern. In PostgreSQL ist das Repeatable Read.

Wie funktioniert Serializable in PostgreSQL?

Mit SSI: Snapshot Isolation plus Überwachung der Lese- und Schreib-Abhängigkeiten. Bei einem gefährlichen Muster bricht eine Transaktion mit 40001 ab.

Was sind SIRead Locks?

Predicate Locks von SSI. Sie merken sich, was gelesen wurde. Sie blockieren nie, sie dienen nur der Konflikterkennung.

Wann wird der Snapshot in Repeatable Read genommen?

Beim ersten Befehl nach BEGIN, nicht bei BEGIN selbst.

Was ist READ ONLY DEFERRABLE?

Eine Serializable-Lesetransaktion, die auf einen sicheren Snapshot wartet. Danach scheitert sie nie mit 40001. Gut für lange Reports.

Warum gibt es bei Serializable False Positives?

SSI sperrt grob, z. B. eine ganze Seite oder Tabelle bei Sequential Scans. Dann sieht es Konflikte, die es in Wirklichkeit nicht gab.

Zahlen

Was bedeutet SQLSTATE 40001?

serialization_failure. Die Transaktion konnte nicht serialisiert werden. Die Anwendung soll sie komplett wiederholen.

Welches Level ist Standard, und wie ändern Sie es?

Read Committed. Pro Transaktion mit BEGIN ISOLATION LEVEL …, global mit default_transaction_isolation.

Warum steigen die 40001-Fehler, wenn der Speicher für Predicate Locks knapp wird?

PostgreSQL fasst dann Locks zusammen: über 2 Tupel → ganze Seite, über 32 Locks → ganze Tabelle (Standard 64 pro Transaktion). Gröbere Locks melden mehr scheinbare Konflikte.

Vergleich

Wie unterscheidet sich SQL Server?

SQL Server nutzt standardmässig Locks: Leser warten auf Schreiber. Mit READ_COMMITTED_SNAPSHOT und SNAPSHOT nutzt es Versionen im tempdb.

Warum ist Oracle Serializable nicht echt serialisierbar?

Nein. Es ist Snapshot Isolation und erlaubt Write Skew. PostgreSQL Serializable ist echt serialisierbar.

Worin ist PostgreSQL Repeatable Read strenger als der SQL-Standard?

Der Standard erlaubt dort Phantom Reads. PostgreSQL verhindert sie, weil der Snapshot für die ganze Transaktion gilt. Write Skew bleibt trotzdem möglich.

Produktion

Wie bauen Sie einen Retry richtig?

Um die ganze Transaktion, nur bei 40001 und 40P01, mit Obergrenze und Backoff. Seiteneffekte erst nach dem COMMIT.

Kann ich auf einer Replica Serializable nutzen?

Nein. Auf Hot Standby geht maximal Repeatable Read.

Was geht kaputt, wenn eine Transaktion vor dem COMMIT eine E-Mail schickt?

Bei einem Retry nach 40001 läuft alles nochmal, die E-Mail kommt doppelt. Lösung: Seiteneffekte erst nach dem COMMIT, z. B. per Outbox.

Szenario: Ein Lagerbestand wird unter Last negativ. Was tun Sie?

Wahrscheinlich read-modify-write in Read Committed. Lösung: UPDATE mit SET bestand = bestand - 1 WHERE bestand > 0 und Rückgabe prüfen. Zusätzlich CHECK (bestand >= 0).

Szenario: Nach dem Wechsel auf Serializable häufen sich Fehler 500. Was ist los?

Serialization Failures (40001) ohne Retry. Lösung: zentraler Retry um die Transaktion. Danach Hotspots über Indexe und kürzere Transaktionen entschärfen.

Design

Wie verhindern Sie einen Lost Update in Read Committed?

Atomares UPDATE mit Rechnung in SQL, SELECT FOR UPDATE, oder optimistisch mit Versionsspalte.

Wie verhindern Sie Write Skew ohne Serializable?

Gelesene Zeilen mit FOR UPDATE sperren, den Konflikt in einer gemeinsamen Zeile materialisieren, oder ein Constraint nutzen.

Warum schlägt ein Constraint die Isolation?

Ein UNIQUE- oder EXCLUDE-Constraint gilt in jedem Level und für jeden Client. Die Regel hängt dann nicht am richtigen Level im Code.

Szenario: Zwei Buchungen für denselben Raum und Zeitraum kommen gleichzeitig durch. Wie verhindern Sie das?

Am besten mit einem EXCLUDE-Constraint auf Raum und Zeitbereich. Alternativ Serializable mit Retry oder FOR UPDATE auf eine Raum-Zeile.
