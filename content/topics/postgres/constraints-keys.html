Constraints, Keys, Sequences vs UUID

Kern: Ein Constraint ist eine Regel, die PostgreSQL bei jedem Schreiben prüft und so die Daten korrekt hält, egal welche Anwendung schreibt. Der Primärschlüssel ist der wichtigste Constraint. Seine Werte kommen aus einer Sequence (bigint) oder sind eine UUID, seit PostgreSQL 18 auch zeitlich sortierbar mit uuidv7() (Release Notes 18, Functions).

Antwort-Muster

Frage: bigint-Sequence oder UUID als Primärschlüssel?

  1. Mechanismus: Beide füllen einen Unique B-Tree-Index. Zufällige UUIDs landen überall im Baum, Sequences rechts.
  2. Zahl: bigint braucht 8 Byte, uuid 16 Byte. Bei 500 000 Zeilen war der Index 11 MB gegen 19 MB.
  3. Trade-off: UUIDs sind überall erzeugbar und nicht erratbar. Sie kosten aber Platz und Seitensplits.
  4. Produktion: Ich nehme bigint intern. UUIDv7 nehme ich, wenn IDs verteilt oder öffentlich sind.

1. Die Reise eines INSERT durch die Constraints

  1. Default: INSERT INTO kunde (email) VALUES ('c@x.ch') hat keine ID. Die Identity-Spalte ruft nextval() und bekommt 3.
  2. NOT NULL und CHECK: PostgreSQL prüft die Zeile allein. Ein CHECK sieht nur diese Zeile, nie andere Zeilen.
  3. Heap: Die Zeile wird in die Tabelle geschrieben, noch unsichtbar für andere (Seite MVCC).
  4. Indizes: Jeder Index bekommt einen Eintrag. Der Unique-Index meldet sofort ein Duplikat. Läuft gerade eine andere Transaktion mit demselben Wert, wartet der Insert auf deren Ende.
  5. FK-Trigger: Für bestellung.kunde_id sucht der Trigger den Kunden. Er sperrt ihn mit FOR KEY SHARE, damit niemand ihn gleichzeitig löscht (Seite Locking).
  6. Deferred: Ist der Constraint DEFERRABLE INITIALLY DEFERRED, wartet die Prüfung bis zum COMMIT (Seite ACID und Transaktionen).
  7. Fehler: Ein Verstoss rollt die Anweisung zurück. Die Sequence-Nummer ist trotzdem weg. Darum hat eine Identity-Spalte Lücken.

2. Aufbau

  1. pg_constraint: Der Katalog speichert jeden Constraint mit Name und Typ (p, u, f, c, x). Seit 18 stehen auch NOT-NULL-Constraints dort, mit eigenem Namen (Release Notes 18, Constraints).
  2. NOT NULL und CHECK: PostgreSQL prüft sie direkt an der neuen Zeile. Kein Index nötig. Beispiel: CHECK (preis > 0).
  3. PRIMARY KEY und UNIQUE: Beide erzeugen automatisch einen Unique B-Tree-Index. Der Index prüft die Eindeutigkeit. Ein PK setzt zusätzlich NOT NULL.
  4. EXCLUDE: Ein Exclusion Constraint verbietet zwei Zeilen, für die alle Operatoren true liefern. Er erzeugt einen Index, meist GiST. Beispiel: keine überlappenden Buchungen pro Raum.
  5. FOREIGN KEY: Er läuft über interne RI-Trigger (Referential Integrity). Beim Schreiben im Kind sucht PostgreSQL die Eltern-Zeile über deren PK.
  6. Sequence: Eine Sequence ist ein eigenes Objekt, das Zahlen ausgibt. Eine Identity-Spalte holt ihren Default per nextval() daraus.

3. Details, die Interviewer fragen

  1. Primärschlüssel: Er ist UNIQUE plus NOT NULL. Er erzeugt einen Unique B-Tree-Index. Pro Tabelle gibt es höchstens einen.
  2. Natürlicher vs Surrogat-Schlüssel: Ein natürlicher Schlüssel kommt aus der Fachlichkeit, z. B. AHV-Nummer. Ein Surrogat-Schlüssel ist eine technische ID. Üblich ist Surrogat als PK plus UNIQUE auf den natürlichen Schlüssel.
  3. FK braucht Index im Kind: PostgreSQL legt keinen Index auf die referenzierende Spalte an. Ohne Index liest jedes DELETE im Eltern-Teil die ganze Kind-Tabelle.
  4. ON DELETE: Es gibt NO ACTION (Standard), RESTRICT, CASCADE, SET NULL und SET DEFAULT. NO ACTION lässt sich aufschieben, RESTRICT nicht. Seit 18 meldet RESTRICT SQLSTATE 23001 statt 23503 (Release Notes 18, Migration).
  5. NOT VALID und VALIDATE: ADD CONSTRAINT … NOT VALID prüft nur neue Zeilen und ist schnell. VALIDATE CONSTRAINT prüft später die Altdaten mit einem schwächeren Lock. Das gilt für CHECK und FK. Seit 18 gilt es auch für NOT NULL (Release Notes 18, Constraints).
  6. NOT ENFORCED (seit 18): Ein CHECK oder FK wird nur dokumentiert, nicht geprüft (Release Notes 18, Constraints). Seit 19 lässt sich das auch bei CHECK per ALTER CONSTRAINT … [NOT] ENFORCED umschalten. Vorher ging das nur beim FK (Release Notes 19, Constraints).
  7. CHECK-Grenzen: Ein CHECK sieht nur die eigene Zeile. Er muss immutable sein. Das heisst: Für dieselbe Zeile antwortet er immer gleich. Für Regeln über mehrere Zeilen nimmt man UNIQUE, EXCLUDE, FK oder Trigger.
  8. Temporale Schlüssel (seit 18): PRIMARY KEY (raum, zeit WITHOUT OVERLAPS) verbietet überlappende Zeiträume pro Schlüssel. Der FK dazu nutzt PERIOD (Release Notes 18, Constraints).
  9. Identity vs serial: serial ist eine Abkürzung für Sequence plus Default. Es ist nicht SQL-Standard. GENERATED … AS IDENTITY ist Standard und an die Spalte gebunden. ALWAYS blockt eigene Werte, BY DEFAULT nicht.
  10. Sequence-Lücken: nextval() wird nie zurückgerollt. Für lückenlose Nummern (z. B. Rechnungen) braucht es eine Zähler-Tabelle mit Lock. Das ist viel langsamer.
  11. Sequence-CACHE: Der Standard ist 1. Mit grösserem Cache reserviert jede Session einen Block. Werte sind dann eindeutig. Sie sind aber nicht mehr global in Reihenfolge.
  12. JPA/Hibernate: Der JPA-Standard allocationSize ist 50. Die Sequence braucht dann INCREMENT BY 50. Sonst passen IDs nicht zusammen.
  13. UUID-Typ: uuid speichert 16 Byte binär, nicht 36 Zeichen Text. Als text gespeichert kostet eine UUID mehr als doppelt so viel.
  14. UUIDv4 vs UUIDv7: gen_random_uuid() bzw. uuidv4() ist rein zufällig. uuidv7() gibt es seit 18 (Release Notes 18, Functions). Dort kam auch der Alias uuidv4() dazu. Es beginnt mit einem Zeitstempel in Millisekunden. Darum ist es ungefähr sortiert. Neue Werte landen rechts im B-Tree.
  15. Zeit aus der UUID: uuid_extract_timestamp() liest den Zeitstempel einer v7-UUID. Das verrät die Erstellzeit. Bei öffentlichen IDs bedenken.

4. Fallen

  • „Ein Foreign Key legt automatisch einen Index an.“ → Falsch. Nur PK und UNIQUE auf der Eltern-Seite haben einen Index. Das Kind braucht einen eigenen.
  • „Eine Sequence ist lückenlos.“ → Falsch. Rollbacks, Fehler, Cache und Crashs erzeugen Lücken.
  • „UNIQUE verbietet doppelte NULL.“ → Falsch. Nur mit NULLS NOT DISTINCT.
  • „UUIDs sind immer schlecht als Primärschlüssel.“ → Falsch. Zufällige v4 sind teuer im Index. v7 verhält sich fast wie eine Sequence.
  • „RESTRICT und NO ACTION sind gleich.“ → Fast. NO ACTION lässt sich bis zum COMMIT aufschieben, RESTRICT nicht.
  • „Ein CHECK kann andere Zeilen prüfen.“ → Falsch. Er sieht nur die eigene Zeile.
  • „serial und Identity sind verschiedene Techniken.“ → Falsch. Beide nutzen eine Sequence. Identity ist nur die Standard-Syntax mit mehr Schutz.

5. Selbsttest

Warum?

Was ist ein Constraint?

Eine Regel, die PostgreSQL bei jedem Schreiben prüft. Verstösse brechen die Anweisung ab.

Warum reicht eine Prüfung in der Anwendung nicht?

Zwei parallele Requests prüfen gleichzeitig und sehen beide keinen Konflikt. Ausserdem schreiben Skripte und Batch-Jobs an der App vorbei. Nur der Constraint in der DB gilt für alle.

Wie verhindere ich doppelte Einträge bei parallelen Requests?

Mit einem UNIQUE Constraint und INSERT … ON CONFLICT. Ein Check in der App vorher reicht nicht.

Wie innen?

Welche Constraint-Arten gibt es?

NOT NULL, CHECK, UNIQUE, PRIMARY KEY, FOREIGN KEY und EXCLUDE.

Was ist der Unterschied zwischen PRIMARY KEY und UNIQUE?

Der PK ist zusätzlich NOT NULL und es gibt nur einen pro Tabelle. Beide erzeugen einen Unique B-Tree-Index.

Was ist ein Deferrable Constraint?

Ein Constraint, dessen Prüfung bis zum COMMIT warten kann. Nützlich bei zyklischen FKs oder beim Tauschen eindeutiger Werte.

Was macht NOT VALID?

Der Constraint gilt sofort für neue Zeilen, prüft aber die Altdaten nicht. VALIDATE CONSTRAINT holt das später nach.

Was kann ein CHECK nicht?

Andere Zeilen oder Tabellen prüfen. Er muss immutable sein und sieht nur die neue Zeile.

Was ist ein Exclusion Constraint?

Er verbietet zwei Zeilen, für die alle angegebenen Operatoren true liefern. Beispiel: gleicher Raum und überlappende Zeit.

Was ist der Unterschied zwischen GENERATED ALWAYS und BY DEFAULT?

ALWAYS lehnt eigene Werte ab, ausser mit OVERRIDING SYSTEM VALUE. BY DEFAULT nimmt eigene Werte an.

Warum hat meine ID-Spalte Lücken?

nextval() wird nie zurückgerollt. Rollbacks, Fehler, Sequence-Cache und Crashs verbrauchen Nummern.

Was macht der Sequence-CACHE?

Jede Session reserviert einen Block von Werten. Das spart Zugriffe, aber Werte sind nicht mehr global in Reihenfolge und Lücken werden grösser.

Zahlen

Wie gross ist eine UUID?

16 Byte im Typ uuid, doppelt so viel wie bigint. Als text gespeichert etwa 37 Byte.

Warum allocationSize 50 bei Hibernate?

Hibernate holt einen Wert und vergibt 50 IDs im Speicher. Die Sequence muss dazu mit INCREMENT BY 50 laufen.

Was geht kaputt, wenn eine ID-Spalte vom Typ integer ist?

Bei 2 147 483 647 ist Schluss, jeder weitere Insert scheitert. Umstellen auf bigint heisst die Tabelle umschreiben. Darum von Anfang an bigint.

Vergleich

Darf eine UNIQUE-Spalte mehrere NULL haben?

Ja, standardmässig. Mit NULLS NOT DISTINCT seit Version 15 nicht.

NO ACTION vs RESTRICT?

Beide verhindern das Löschen. NO ACTION kann aufgeschoben werden, RESTRICT prüft sofort.

serial oder Identity?

Identity. Es ist SQL-Standard, an die Spalte gebunden, und mit ALWAYS sind manuelle Werte gesperrt.

Natürlicher oder Surrogat-Schlüssel?

Meist Surrogat als PK, weil natürliche Werte sich ändern. Der natürliche Schlüssel bekommt zusätzlich einen UNIQUE Constraint.

Was ist UUIDv7?

Eine UUID, die mit einem Millisekunden-Zeitstempel beginnt. Sie ist ungefähr sortiert und verhält sich im Index fast wie eine Sequence. In PostgreSQL seit 18 per uuidv7() (Release Notes 18).

Warum sind zufällige UUIDs als PK teuer?

Jeder Insert landet an zufälliger Stelle im B-Tree. Das spaltet Seiten, braucht mehr Cache und erzeugt mehr WAL.

Hat UUIDv7 einen Nachteil?

Ja. Die Erstellzeit ist ablesbar, z. B. mit uuid_extract_timestamp(). Für öffentliche IDs kann das ein Datenschutzthema sein.

Produktion

Braucht ein Foreign Key einen Index?

Auf der Eltern-Seite ist er durch PK oder UNIQUE da. Auf der Kind-Seite muss man ihn selbst anlegen, sonst sind DELETE und UPDATE auf den Eltern langsam.

Wie finde ich Foreign Keys ohne Index?

pg_constraint mit contype 'f' gegen pg_index abgleichen: Gibt es einen Index, der mit den FK-Spalten beginnt?

Was geht kaputt, wenn ON DELETE CASCADE über mehrere Tabellen geht?

Ein einziges DELETE löscht ganze Bäume von Daten, oft mehr als gewollt. CASCADE nur für echte Teile eines Ganzen, sonst RESTRICT und bewusstes Löschen.

Szenario: Ein DELETE auf der Kunden-Tabelle dauert pro Zeile Sekunden. Was prüfen Sie?

Ob alle FKs, die auf Kunden zeigen, einen Index im Kind haben. EXPLAIN ANALYZE zeigt die Zeit in den RI-Triggern. Lösung: fehlende Indizes CONCURRENTLY anlegen.

Szenario: Nach einem Datenimport scheitern alle Inserts mit „duplicate key“. Warum?

Der Import hat eigene IDs geschrieben, die Sequence steht noch tief. Lösung: Sequence auf max(id) setzen, z. B. mit setval oder ALTER COLUMN … RESTART.

Design

Welche ON-DELETE-Aktionen gibt es?

NO ACTION, RESTRICT, CASCADE, SET NULL und SET DEFAULT. Standard ist NO ACTION.

Was ist NOT ENFORCED?

Seit 18 (Release Notes 18): Ein CHECK oder FK wird deklariert, aber nicht geprüft. Er dokumentiert eine Beziehung, schützt aber nicht.

Was bringt WITHOUT OVERLAPS?

Seit 18 (Release Notes 18) ein temporaler PK oder UNIQUE: pro Schlüssel keine überlappenden Zeiträume. Der passende FK nutzt PERIOD.

Wie baue ich lückenlose Rechnungsnummern?

Mit einer Zähler-Tabelle, die in derselben Transaktion gesperrt und erhöht wird. Das serialisiert alle Schreiber.

Warum ist ein EXCLUDE-Constraint für Raumbuchungen besser als eine Prüfung im Code?

Im Code sehen zwei parallele Buchungen beide keinen Konflikt. Der Exclusion Constraint prüft im Index: Die zweite Buchung wartet auf die erste und scheitert dann mit 23P01.

Szenario: Sie müssen einen FK auf eine Tabelle mit 500 Millionen Zeilen hinzufügen, ohne Downtime. Wie?

Erst Index auf die FK-Spalte CONCURRENTLY, dann ADD CONSTRAINT … NOT VALID, dann VALIDATE CONSTRAINT. Vorher Altdaten bereinigen.

Mehr

Gerüst

  • Warum? Regel in der DB gilt für jeden Schreiber und gegen Race Conditions. App-Check allein reicht nicht.
  • Wie innen? PK/UNIQUE = Unique B-Tree-Index, EXCLUDE = GiST-Index, FK = interne RI-Trigger mit FOR KEY SHARE. CHECK sieht nur die eigene Zeile.
  • Zahlen bigint 8 Byte, uuid 16 Byte. integer endet bei 2 147 483 647. Sequence-CACHE 1, Hibernate allocationSize 50.
  • Vergleich bigint: kompakt, zentral. UUIDv4: zufällig, Seitensplits. UUIDv7: zeitlich sortiert, verrät Erstellzeit.
  • Produktion FK ohne Index im Kind → DELETE mit Seq Scan pro Zeile. ADD FK auf Riesentabelle → NOT VALID + VALIDATE.
  • Design bigint intern, UUIDv7 bei verteilten oder öffentlichen IDs. Lückenlos ist Fachlogik: Zähler-Tabelle mit Lock.

Echte Ausgabe, PostgreSQL 17.12. Gekürzt: CREATE/SET/INSERT-Meldungen ohne Aussage; Fehlerzeilen (stderr) an ihre Anweisung gesetzt; eine lange DETAIL-Zeile umbrochen. Server-Zeitzone UTC, darum 08:00 statt 09:00+01. uuidv7() gibt es erst ab 18 (Release Notes 18), darum simuliert Teil 6 sie mit sortierten UUIDs.

  1. GENERATED ALWAYS: Eine eigene ID wird abgelehnt. Nur OVERRIDING SYSTEM VALUE erlaubt sie, z. B. bei einer Migration.
  2. Lücke: Die ID 2 ging an die zurückgerollte Transaktion. Der nächste Kunde bekommt 3. nextval() wird nie zurückgerollt.
  3. NULL in UNIQUE: Standardmässig sind zwei NULL „verschieden“, also erlaubt. NULLS NOT DISTINCT (seit 15) behandelt sie als gleich.
  4. NOT VALID: Der FK entsteht ohne Prüfung der Altdaten. Neue Zeilen werden sofort geprüft (888 abgelehnt). VALIDATE findet die alte 777. Nach der Bereinigung ist convalidated = t.
  5. EXCLUDE: Raum 1 von 09:30 bis 11:00 überlappt mit 09:00 bis 10:00 und wird abgelehnt. Raum 2 zur gleichen Zeit ist erlaubt. btree_gist liefert den =-Operator für GiST.
  6. Indexgrösse: UUID braucht 16 Byte, bigint 8 Byte. Zufällige UUIDs landen überall im Baum und spalten Seiten, darum 19 MB statt 15 MB bei gleichen Werten in wachsender Reihenfolge.

Vergleich

  • bigint Identity: 8 Byte, kompakter Index, schnelle Inserts rechts im Baum. Nachteil: zentral vergeben, erratbar, Konflikte beim Zusammenführen von Datenbanken.
  • UUIDv4: 16 Byte, überall erzeugbar, nicht erratbar. Nachteil: zufällige Index-Position, mehr Seitensplits, mehr WAL, schlechterer Cache.
  • UUIDv7: 16 Byte, überall erzeugbar, ungefähr zeitlich sortiert. Index-Verhalten fast wie bei bigint. Nachteil: verrät die Erstellzeit.
  • serial vs Identity: Gleiche Technik. Identity ist Standard-SQL und schützt mit ALWAYS vor manuellen Werten.
  • UNIQUE Constraint vs Unique Index: Gleiche Prüfung, beide können Ziel eines FK sein. Ein partieller Unique Index (WHERE deleted_at IS NULL) geht nur als Index.
  • CHECK vs Trigger: CHECK ist deklarativ und schnell, sieht aber nur eine Zeile. Ein Trigger kann alles, ist aber versteckte Logik.
  • Constraint in DB vs Validierung in der App: Die App liefert gute Fehlermeldungen. Nur die DB schützt gegen Race Conditions und andere Schreiber. Beides zusammen ist richtig.

In der Produktion

  1. DELETE auf Eltern-Tabelle dauert Minuten: Der FK hat keinen Index im Kind. Jede gelöschte Zeile löst einen Seq Scan aus. Lösung: Index auf die FK-Spalte, z. B. CREATE INDEX CONCURRENTLY.
  2. ALTER TABLE ADD FOREIGN KEY blockiert: Die Prüfung aller Altdaten dauert lange. Lösung: NOT VALID anlegen, dann separat VALIDATE CONSTRAINT laufen lassen.
  3. integer-ID läuft über: Bei 2 147 483 647 ist Schluss, Inserts scheitern. Lösung: von Anfang an bigint. Umstellen später heisst Tabelle umschreiben.
  4. Doppelte Schlüssel nach Datenimport: Zeilen wurden mit eigenen IDs importiert, die Sequence steht noch tief. Lösung: setval() auf max(id) setzen, bei Identity ALTER TABLE … ALTER COLUMN id RESTART WITH ….
  5. Schreiblast und WAL hoch mit UUIDv4-PK: Zufällige Inserts treffen viele Seiten, Checkpoints schreiben mehr Full Page Images. Lösung: uuidv7() oder bigint intern und UUID nur als öffentliche ID.
  6. CASCADE löscht zu viel: Eine Kette von ON DELETE CASCADE löscht ganze Bäume. Lösung: CASCADE nur für echte Teile eines Ganzen, sonst RESTRICT und bewusstes Löschen.
  7. Unique-Verstoss unter Last: „Prüfen, dann einfügen“ in der App ist eine Race Condition. Lösung: UNIQUE in der DB und INSERT … ON CONFLICT.

Diagnose: Werkzeuge und Abfragen

  • Alle Constraints einer Tabelle: SELECT conname, contype, convalidated, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 't'::regclass;
  • Nicht validierte Constraints: WHERE NOT convalidated auf pg_constraint. Seit 18 zeigt conenforced auch nicht erzwungene (Release Notes 18, Constraints).
  • FK ohne Index finden: pg_constraint mit contype = 'f' gegen pg_index prüfen: Beginnt ein Index mit conkey?
  • Sequence-Stand: SELECT * FROM pg_sequences; zeigt last_value, max_value, increment_by, cache_size.
  • Überlauf früh erkennen: last_value / max_value aus pg_sequences überwachen.
  • Identity-Sequence finden: SELECT pg_get_serial_sequence('kunde', 'id');
  • Indexgrösse und Bloat: pg_relation_size('…_pkey'), genauer mit pgstattuple bzw. pgstatindex (Seite VACUUM).
  • Fehlercodes: 23505 unique, 23503 FK, 23001 restrict (seit 18, Release Notes 18), 23514 check, 23502 not null, 23P01 exclusion.

Senior-Punkte

  1. Integrität gehört in die Datenbank. Anwendungen ändern sich, Batch-Jobs und Skripte schreiben auch. Die Regel in der DB gilt für alle.
  2. Jeder FK bekommt einen Index, ausser die Eltern-Seite wird nie gelöscht oder geändert. Das prüfe ich im Review.
  3. Schlüssel-Strategie: bigint Identity für interne Tabellen. UUIDv7, wenn IDs verteilt erzeugt werden oder öffentlich sind. UUIDv4 nur, wenn die Erstellzeit geheim bleiben muss.
  4. Constraints auf grossen Tabellen in zwei Schritten: NOT VALID, dann VALIDATE. Das hält Migrationen ohne Downtime.
  5. Lückenlos ist eine Fachanforderung, keine Sequence-Eigenschaft. Dafür baue ich eine eigene Nummernvergabe und akzeptiere den Lock.
  6. EXCLUDE und WITHOUT OVERLAPS lösen Buchungs- und Gültigkeitsprobleme in der DB. Ohne sie gibt es Race Conditions.
  7. Namen für Constraints vergeben. Dann sind Fehlermeldungen und Migrationen lesbar.
