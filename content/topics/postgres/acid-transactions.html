ACID und Transaktionen

Kern: Eine Transaktion ist eine Gruppe von Befehlen, die ganz oder gar nicht wirkt. ACID heisst Atomicity, Consistency, Isolation, Durability. PostgreSQL erreicht Atomicity und Durability mit dem WAL, Isolation mit MVCC und Consistency mit Constraints.

Antwort-Muster

Frage: Was bedeutet ACID, und wie setzt PostgreSQL es um?

  1. Mechanismus: Atomicity und Durability kommen vom WAL, Isolation von MVCC, Consistency von Constraints.
  2. Zahl: Beim COMMIT wird nur das WAL per fsync geschrieben, die Datenseiten kommen später mit dem Checkpoint.
  3. Trade-off: Mit synchronous_commit = off ist der COMMIT schneller, aber Commits aus ca. 600 ms können bei einem Crash fehlen.
  4. Produktion: Ich halte Transaktionen kurz und setze idle_in_transaction_session_timeout gegen vergessene Transaktionen.

1. Die Reise eines COMMIT

  1. BEGIN: Die Transaktion startet. Sie hat nur eine virtuelle xid, also eine billige lokale ID. Reine Lese-Transaktionen bleiben so.
  2. Erstes UPDATE: Jetzt bekommt die Transaktion eine echte xid, z. B. 801. Sie zählt gegen den 32-Bit-Zähler.
  3. Seite ändern: PostgreSQL schreibt eine neue Zeilenversion mit xmin = 801 in die Seite. Die alte bekommt xmax = 801. Zuerst kommt ein WAL-Record, dann die Seite. Daher „Write-Ahead“.
  4. COMMIT: Ein Commit-Record kommt ins WAL.
  5. WAL flush: Das WAL wird bis zur LSN (Log Sequence Number, Position im WAL) des Commit-Records auf Disk gezwungen. Ab hier ist die Transaktion durable.
  6. pg_xact: Der Status von 801 wird „committed“. Ab jetzt sehen neue Snapshots die Zeile.
  7. Locks frei: Row Locks und Table Locks werden erst jetzt freigegeben. Der Client bekommt „COMMIT“.
  8. Checkpoint: Die Datenseiten schreibt der Checkpointer irgendwann später. Bei einem Crash spielt PostgreSQL das WAL ab dem letzten Checkpoint neu ab (Redo).

ROLLBACK ist billig: PostgreSQL markiert die xid als „aborted“. Die neuen Versionen bleiben als tote Zeilen liegen. VACUUM räumt sie später weg.

2. Aufbau

  1. Client: schickt BEGIN, Befehle und COMMIT. Beispiel: JDBC mit setAutoCommit(false).
  2. Backend-Prozess: ein Betriebssystem-Prozess pro Verbindung. Er hält die xid (Transaction ID), den Snapshot und die Locks.
  3. Shared Buffers: der Seiten-Cache. Änderungen landen zuerst hier als dirty pages, also geänderte, noch nicht geschriebene Seiten.
  4. WAL Buffers: Puffer für das WAL (Write-Ahead Log), das Protokoll aller Änderungen.
  5. WAL-Dateien: liegen in pg_wal/. Beim COMMIT wird das WAL bis zum Commit-Eintrag auf Disk geschrieben (fsync).
  6. Datendateien: Die Tabellen selbst. Der Checkpointer schreibt dirty pages erst später.
  7. pg_xact: speichert für jede xid zwei Bits: in progress, committed, aborted oder sub-committed.

3. Details, die Interviewer fragen

  1. Atomicity: Alle Änderungen gelten oder keine. PostgreSQL braucht dafür kein Undo-Log. Ein Abort setzt nur den Status in pg_xact auf „aborted“. Die Zeilen werden dadurch unsichtbar.
  2. Consistency: Die Datenbank geht von einem gültigen Zustand in den nächsten. Sie prüft Constraints: PRIMARY KEY, UNIQUE, FOREIGN KEY, CHECK, NOT NULL, EXCLUDE. Geschäftsregeln ohne Constraint muss die Anwendung sichern.
  3. Deferred Constraints: Ein Constraint mit DEFERRABLE INITIALLY DEFERRED wird erst beim COMMIT geprüft. Beispiel: zwei Zeilen, die gegenseitig per Foreign Key aufeinander zeigen. CHECK und NOT NULL sind nie deferrable.
  4. Isolation: Parallele Transaktionen stören sich nicht, je nach Isolation Level. Standard ist Read Committed. PostgreSQL nutzt dafür MVCC: Leser blockieren keine Schreiber.
  5. Durability: Nach „COMMIT“ überlebt die Änderung einen Crash. Grund: Der Commit-Record steht per fsync im WAL. Bei Neustart spielt Crash Recovery das WAL ab.
  6. WAL-Regel: Eine Datenseite darf erst auf Disk, wenn ihr WAL-Record schon auf Disk ist. So kann Recovery jede Änderung wiederholen.
  7. full_page_writes: Nach jedem Checkpoint schreibt PostgreSQL bei der ersten Änderung die ganze Seite ins WAL. Das schützt vor torn pages, also halb geschriebenen Seiten. Standard: on.
  8. synchronous_commit: Mit off wartet der COMMIT nicht auf den fsync. Bei einem Crash fehlen höchstens die Commits der letzten 3 × wal_writer_delay (Standard 200 ms), also ca. 600 ms. Die Datenbank bleibt aber konsistent. Pro Transaktion setzbar.
  9. fsync = off: Das ist etwas ganz anderes. Ein Crash kann die Datenbank korrupt machen. Nie in Produktion.
  10. Autocommit: Ohne BEGIN ist jeder Befehl eine eigene Transaktion. psql, JDBC und die meisten Treiber starten im Autocommit-Modus. Spring @Transactional schaltet ihn pro Methode aus.
  11. Savepoint: Ein Savepoint ist ein Zwischenstand in einer Transaktion. ROLLBACK TO SAVEPOINT verwirft nur die Arbeit danach. Intern ist das eine Subtransaktion mit eigener Sub-xid.
  12. Versteckte Subtransaktionen: Ein EXCEPTION-Block in PL/pgSQL startet einen Savepoint. Der JDBC-Treiber mit autosave=always setzt vor jedem Befehl einen. psql mit ON_ERROR_ROLLBACK auch.
  13. Subtransaktions-Overflow: Pro Backend merkt sich PostgreSQL bis zu 64 Sub-xids im Shared Memory. Darüber muss jeder Snapshot in pg_subtrans nachschlagen. Das bremst stark, vor allem auf Replicas.
  14. Transaktionale DDL: CREATE TABLE, ALTER TABLE, DROP lassen sich zurückrollen. Ausnahmen: CREATE INDEX CONCURRENTLY, CREATE DATABASE, VACUUM. Sie laufen nicht in einem Transaktionsblock.
  15. Lange Transaktionen: Eine offene Transaktion hält ihren Snapshot. VACUUM darf dann keine Zeilen entfernen, die sie noch sehen könnte. Folge: Bloat. Dazu hält sie alle Locks bis zum Ende.
  16. idle in transaction: Eine Session mit offenem BEGIN, die nichts tut. Gegenmittel: idle_in_transaction_session_timeout. Neu in PostgreSQL 17: transaction_timeout begrenzt die ganze Transaktion.
  17. Two-Phase Commit: PREPARE TRANSACTION speichert eine Transaktion für einen späteren COMMIT PREPARED. Das braucht ein externer Transaktionsmanager (XA). Standard: max_prepared_transactions = 0, also aus.

4. Fallen

  • „COMMIT schreibt die Tabellen auf Disk.“ → Falsch. COMMIT schreibt nur das WAL. Die Seiten kommen später mit dem Checkpoint.
  • „Ein Rollback kostet so viel wie die Transaktion.“ → Falsch in PostgreSQL. Er setzt nur den Status. Die toten Zeilen räumt VACUUM weg.
  • „Ohne BEGIN gibt es keine Transaktion.“ → Falsch. Im Autocommit ist jeder Befehl eine eigene Transaktion.
  • „Nach einem Fehler kann ich in der Transaktion weitermachen.“ → Falsch. Sie ist aborted. Nur ROLLBACK oder ROLLBACK TO SAVEPOINT helfen.
  • „synchronous_commit = off kann die Datenbank korrupt machen.“ → Falsch. Nur die letzten Commits können fehlen. Korrupt macht fsync = off.
  • „Consistency in ACID ist dasselbe wie im CAP-Theorem.“ → Falsch. ACID: Regeln und Constraints gelten. CAP: alle Knoten sehen denselben Wert.
  • „DDL ist nie transaktional.“ → Falsch für PostgreSQL. Fast jede DDL kann man zurückrollen.

5. Selbsttest

Warum?

Was bedeutet ACID?

Atomicity: ganz oder gar nicht. Consistency: nur gültige Zustände. Isolation: parallele Transaktionen stören sich nicht. Durability: nach COMMIT crash-sicher.

Was macht Consistency konkret?

Die Datenbank prüft Constraints wie PRIMARY KEY, FOREIGN KEY und CHECK. Eine Verletzung bricht den Befehl ab.

Warum sind lange Transaktionen schlecht?

Sie halten ihren Snapshot, darum kann VACUUM tote Zeilen nicht entfernen. Sie halten Locks und blockieren andere. Und Replicas können Konflikte bekommen.

Wie innen?

Wie setzt PostgreSQL Atomicity um?

Jede Zeilenversion trägt die xid. Bei Abort wird die xid in pg_xact als aborted markiert. Damit sind alle ihre Versionen auf einen Schlag unsichtbar.

Wie setzt PostgreSQL Durability um?

Mit dem WAL. Beim COMMIT wird das WAL bis zum Commit-Record per fsync geschrieben. Nach einem Crash spielt Recovery das WAL ab.

Was ist das WAL?

Das Write-Ahead Log protokolliert jede Änderung, bevor die Datenseite geschrieben wird. Es dient für Crash Recovery, Replikation und Point-in-Time Recovery.

Warum schreibt COMMIT nicht die Datenseiten?

Das WAL wird sequenziell geschrieben, Seiten liegen verstreut. Ein sequenzieller fsync ist viel schneller. Die Seiten schreibt der Checkpointer gebündelt.

Was ist ein Checkpoint?

Ein Punkt, an dem alle dirty pages auf Disk sind. Recovery muss nur ab dem letzten Checkpoint abspielen. Gesteuert von checkpoint_timeout und max_wal_size.

Was ist Autocommit?

Jeder Befehl ohne BEGIN ist eine eigene Transaktion und wird sofort committed. Treiber wie JDBC starten so.

Was ist ein Savepoint?

Ein Zwischenstand in einer Transaktion. ROLLBACK TO SAVEPOINT verwirft nur die Arbeit danach. Intern eine Subtransaktion.

Was passiert nach einem Fehler in einer Transaktion?

Sie ist aborted. Jeder weitere Befehl gibt einen Fehler (25P02). COMMIT wird zu ROLLBACK.

Wann bekommt eine Transaktion eine xid?

Erst bei der ersten Schreiboperation. Reine Leser haben nur eine virtuelle xid. Das spart xids und verlangsamt den Wraparound.

Zahlen

Wie viele Commits kann synchronous_commit = off höchstens verlieren?

Die Commits aus maximal 3 × wal_writer_delay. Mit dem Standard 200 ms sind das ca. 600 ms. Die Datenbank bleibt trotzdem konsistent.

Was geht kaputt, wenn eine Transaktion sehr viele Savepoints offen hat?

Jeder Savepoint mit Schreibzugriff bekommt eine Sub-xid. Nur 64 offene Sub-xids pro Backend passen in den Shared-Memory-Cache. Darüber müssen Snapshots in pg_subtrans nachschlagen, das bremst stark, besonders auf Replicas.

Welchen Standard hat max_prepared_transactions, und was heisst das?

0. Two-Phase Commit ist also aus. Man schaltet es nur ein, wenn ein externer Transaktionsmanager es braucht.

Vergleich

Was ist der Unterschied zwischen synchronous_commit = off und fsync = off?

synchronous_commit = off verliert höchstens die letzten Commits, bleibt aber konsistent. fsync = off kann die ganze Datenbank korrupt machen.

Warum ist ein Rollback in PostgreSQL billiger als in Oracle?

PostgreSQL setzt nur den Status der xid auf aborted, die neuen Versionen werden unsichtbar. Oracle und InnoDB müssen die alten Werte aus dem Undo-Log zurückschreiben.

Ist DDL in PostgreSQL transaktional?

Ja, meistens. CREATE TABLE und ALTER TABLE kann man zurückrollen. Ausnahmen sind z. B. CREATE INDEX CONCURRENTLY und CREATE DATABASE.

Was ist Two-Phase Commit in PostgreSQL?

PREPARE TRANSACTION speichert eine fertige Transaktion. Später entscheidet COMMIT PREPARED oder ROLLBACK PREPARED. Vergessene prepared Transactions blockieren VACUUM.

Produktion

Was ist „idle in transaction“?

Eine Session mit offener Transaktion, die nichts tut. Oft ein Bug im Code oder Pool. Gegenmittel: idle_in_transaction_session_timeout.

Was ist neu in PostgreSQL 17 für Transaktionen?

Der Parameter transaction_timeout. Er bricht eine Transaktion ab, die insgesamt länger als erlaubt läuft.

Was geht kaputt, wenn die Verbindung beim COMMIT abreisst?

Der Client weiss nicht, ob der COMMIT durch ist. Die Operation muss idempotent sein oder man prüft den Zustand vor einem Retry.

Szenario: Eine Tabelle wächst stark, obwohl die Zeilenzahl gleich bleibt. Woran denken Sie?

An eine lange oder vergessene Transaktion, die VACUUM blockiert. Prüfen mit pg_stat_activity (xact_start, backend_xmin). Session beenden und Timeouts setzen.

Szenario: Im Log steht tausendfach „current transaction is aborted“. Was ist los?

Die Anwendung fängt einen SQL-Fehler und nutzt dieselbe Transaktion weiter. Den ersten Fehler im Log suchen. Danach rollback machen oder einen Savepoint nutzen.

Design

Warum gehört die Transaktionsgrenze in die Service-Schicht?

Ein Anwendungsfall soll ganz oder gar nicht wirken, auch über mehrere Repositories. Dort sieht man auch, dass kein HTTP-Aufruf in der Transaktion steckt.

Was ist ein Deferred Constraint?

Ein Constraint, der erst beim COMMIT geprüft wird. Man deklariert ihn als DEFERRABLE. Typisch für zyklische Foreign Keys oder das Tauschen eindeutiger Werte.

Wie hängen Spring @Transactional und PostgreSQL zusammen?

Spring schaltet Autocommit auf der Verbindung aus und ruft am Methodenende commit oder rollback. Standard-Rollback nur bei RuntimeException.

Kann man über zwei Microservices eine ACID-Transaktion haben?

Praktisch nein. 2PC ist möglich, aber blockierend und selten. Üblich sind Outbox, Saga und idempotente Consumer.

Szenario: Ein Import mit 10 Mio. Zeilen in einer Transaktion blockiert alles. Was tun Sie?

In Batches committen, z. B. je 10 000 Zeilen, mit Wiederaufsetzpunkt. Für reinen Import COPY nutzen. Das Ganze idempotent machen, damit ein Neustart sicher ist.

Mehr

Gerüst

  • Warum? Ohne Transaktion bleibt eine halbe Überweisung stehen. ACID heisst: ganz oder gar nicht, nur gültige Zustände, auch nach einem Crash.
  • Wie innen? A + D: WAL, fsync beim COMMIT. I: MVCC-Snapshots. C: Constraints. Abort = Status „aborted“ in pg_xact, kein Undo-Log.
  • Zahlen synchronous_commit = off verliert max. 3 × wal_writer_delay (200 ms). 64 Sub-xids pro Backend im Cache. SQLSTATE 25P02 = Transaktion aborted.
  • Vergleich PostgreSQL: alte Versionen im Heap, Rollback billig, dafür VACUUM. Oracle/InnoDB: Undo-Log, grosser Rollback teuer.
  • Produktion „idle in transaction“ → Bloat und Lock-Stau. Gegenmittel: idle_in_transaction_session_timeout, seit 17 transaction_timeout.
  • Design Transaktionen kurz, Grenze in der Service-Schicht. Constraints in die DB. Über Services: Outbox und Saga statt 2PC.

Beispiel: Atomarität und Savepoints

CREATE TABLE konto (id int PRIMARY KEY, saldo numeric CHECK (saldo >= 0));
INSERT INTO konto VALUES (1, 100), (2, 0);

-- A) Überweisung 150 von 1 nach 2: der zweite Schritt scheitert
BEGIN;
UPDATE konto SET saldo = saldo + 150 WHERE id = 2;
UPDATE konto SET saldo = saldo - 150 WHERE id = 1;   -- verletzt CHECK
SELECT * FROM konto;
COMMIT;
SELECT * FROM konto ORDER BY id;

-- B) Savepoint: nur einen Teil zurückrollen
BEGIN;
INSERT INTO konto VALUES (3, 10);
SAVEPOINT s1;
INSERT INTO konto VALUES (3, 20);                    -- doppelter Key
ROLLBACK TO SAVEPOINT s1;
INSERT INTO konto VALUES (4, 20);
COMMIT;
SELECT * FROM konto ORDER BY id;
BEGIN
UPDATE 1
ERROR:  new row for relation "konto" violates check constraint "konto_saldo_check"
DETAIL:  Failing row contains (1, -50).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
 id | saldo
----+-------
  1 |   100
  2 |     0
(2 rows)

BEGIN
INSERT 0 1
SAVEPOINT
ERROR:  duplicate key value violates unique constraint "konto_pkey"
DETAIL:  Key (id)=(3) already exists.
ROLLBACK
INSERT 0 1
COMMIT
 id | saldo
----+-------
  1 |   100
  2 |     0
  3 |    10
  4 |    20
(4 rows)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt), psql mit PostgreSQL 17.

  1. Der erste UPDATE klappt. Der zweite verletzt den CHECK-Constraint. Das ist Consistency: Die Datenbank lehnt den ungültigen Zustand ab.
  2. Nach dem Fehler ist die Transaktion im Zustand aborted. Jeder weitere Befehl liefert SQLSTATE 25P02.
  3. COMMIT auf eine abgebrochene Transaktion macht ein ROLLBACK. psql zeigt darum „ROLLBACK“. Das ist Atomicity: Konto 2 hat wieder 0.
  4. In B fängt ROLLBACK TO SAVEPOINT s1 den Fehler auf. Zeile 3 aus der Zeit vor dem Savepoint bleibt erhalten.
  5. ROLLBACK TO SAVEPOINT zeigt in psql auch „ROLLBACK“, rollt aber nur bis s1 zurück.

Vergleich

  • PostgreSQL: MVCC mit alten Versionen in der Tabelle. Kein Undo-Log. Rollback ist billig, VACUUM räumt auf.
  • Oracle, MySQL InnoDB: Ändern die Zeile an Ort und Stelle. Die alte Version kommt ins Undo-Log. Ein grosser Rollback ist dort teuer.
  • SQL Server: Standard Read Committed mit Locks. Leser warten auf Schreiber. Erst mit READ_COMMITTED_SNAPSHOT gibt es Versionen im tempdb.
  • synchronous_commit = on vs off: on = keine verlorenen Commits. off = schneller, aber kleines Verlustfenster. Beide sind konsistent.
  • Savepoint vs neue Transaktion: Ein Savepoint teilt Snapshot und Locks mit der Haupttransaktion. Eine neue Transaktion (z. B. REQUIRES_NEW in Spring) braucht eine zweite Verbindung.
  • ACID vs BASE: BASE (Basically Available, Soft state, Eventually consistent) beschreibt viele verteilte NoSQL-Systeme. Sie tauschen Isolation gegen Verfügbarkeit.
  • Lokale Transaktion vs Saga: Über Service-Grenzen gibt es keine ACID-Transaktion. Dort helfen Outbox und Saga mit Kompensation.

In der Produktion

  1. Bloat durch vergessene Transaktion: Ein Tool lässt BEGIN offen. Tabellen wachsen, Abfragen werden langsam. Lösung: idle_in_transaction_session_timeout setzen, z. B. 5 min. Ursache im Code beheben.
  2. Lock-Stau durch lange Transaktion: Ein Batch hält Row Locks über Minuten. Andere Requests warten. Lösung: in kleinen Häppchen committen, z. B. 1000 Zeilen pro Transaktion.
  3. „current transaction is aborted“ im Log: Die Anwendung fängt einen SQL-Fehler und macht weiter. Jeder Folgebefehl scheitert. Lösung: Rollback machen oder gezielt Savepoints nutzen.
  4. Langsam auf Replicas durch Subtransaktionen: Viele Savepoints pro Transaktion (z. B. autosave=always, Schleifen mit EXCEPTION). Wait Event SubtransSLRU. Lösung: Savepoints vermeiden, Fehler vorher prüfen.
  5. Hohe Commit-Latenz: Viele kleine Transaktionen warten je auf einen fsync. Lösung: Arbeit bündeln, schnellere Disks, oder synchronous_commit = off für unkritische Daten wie Logs.
  6. Verwaiste prepared Transactions: Sie halten Locks und blockieren VACUUM, auch nach Neustart. Lösung: pg_prepared_xacts prüfen, mit ROLLBACK PREPARED aufräumen.

Diagnose: Werkzeuge und Abfragen

-- Älteste offene Transaktionen
SELECT pid, usename, state, now() - xact_start AS dauer, left(query, 60)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

-- Sessions, die "idle in transaction" sind
SELECT pid, now() - state_change AS idle_seit FROM pg_stat_activity
WHERE state = 'idle in transaction';
  • pg_stat_activity: Spalten xact_start, state, backend_xid, backend_xmin.
  • pg_stat_database: xact_commit, xact_rollback. Viele Rollbacks zeigen Fehler in der Anwendung.
  • pg_prepared_xacts: offene Two-Phase-Transaktionen.
  • pg_current_xact_id() und pg_current_snapshot(): eigene xid und eigener Snapshot.
  • pg_stat_wal: WAL-Menge, Anzahl Syncs, Sync-Zeit.
  • pg_terminate_backend(pid): beendet eine hängende Session. Ihre Transaktion wird zurückgerollt.
  • log_min_duration_statement und log_lock_waits = on: lange Befehle und Lock-Wartezeiten ins Log. Seit PostgreSQL 19 ist log_lock_waits standardmässig an (PG 19 Release Notes).

Senior-Punkte

  1. Transaktionen kurz halten. Kein HTTP-Aufruf, keine Benutzereingabe, kein Datei-Upload innerhalb einer Transaktion.
  2. Die Transaktionsgrenze ist eine Design-Entscheidung. Sie gehört in die Service-Schicht, nicht in jedes Repository.
  3. Durability ist einstellbar. synchronous_commit = off pro Transaktion ist ein bewusster Tausch: Durchsatz gegen ein kleines Verlustfenster.
  4. Constraints in die Datenbank. Nur sie sind bei parallelen Requests sicher. Ein Check im Code allein hat eine Race Condition.
  5. Retries brauchen Idempotenz. Ist das COMMIT-Ergebnis unklar (Verbindung weg), weiss der Client nicht, ob es geklappt hat. Nur idempotente Operationen darf man blind wiederholen.
  6. ACID endet an der Datenbank. Über Services hinweg: Outbox, Saga, idempotente Consumer.
