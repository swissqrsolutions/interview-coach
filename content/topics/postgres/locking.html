Locks, Row Locks, Deadlocks, SELECT FOR UPDATE, SKIP LOCKED

Kern: Ein Lock ist eine Sperre, die gleichzeitige Zugriffe auf dasselbe Objekt ordnet. PostgreSQL hat Table Locks in 8 Stufen, Row Locks in 4 Stufen und frei nutzbare Advisory Locks. Mit SELECT … FOR UPDATE SKIP LOCKED baut man eine sichere Job-Queue, in der mehrere Worker nie denselben Job bekommen.

Antwort-Muster

Frage: Welche Locks kennt PostgreSQL, und wie nutzen Sie sie?

  1. Mechanismus: Jeder Befehl nimmt automatisch einen Table Lock, und geänderte Zeilen bekommen einen Row Lock im Tuple-Header.
  2. Zahl: Es gibt 8 Table-Lock-Stufen und 4 Row-Lock-Stufen, und ein Deadlock wird nach 1 s gesucht und endet mit 40P01.
  3. Trade-off: Warten ist korrekt, aber blockiert; NOWAIT und SKIP LOCKED blockieren nicht, liefern aber einen Fehler oder andere Zeilen.
  4. Produktion: Für Queues nutze ich FOR UPDATE SKIP LOCKED, und jede Migration bekommt ein lock_timeout.

1. Die Reise eines Job-Claims mit SKIP LOCKED

  1. Worker 1 sucht Arbeit: Er liest die ältesten Zeilen mit status = 'pending', LIMIT 3, FOR UPDATE SKIP LOCKED.
  2. Row Locks: PostgreSQL sperrt die Zeilen 1, 2, 3 für Worker 1. Es schreibt dazu seine xid in xmax.
  3. Worker 2 kommt gleichzeitig: Ohne SKIP LOCKED würde er auf Zeile 1 warten. Mit SKIP LOCKED überspringt er gesperrte Zeilen und nimmt 4, 5, 6.
  4. Status setzen: Im selben Befehl setzt UPDATE … RETURNING den Status auf processing und gibt die IDs zurück.
  5. COMMIT: Die Row Locks sind frei. Ab jetzt schützt der Status: Kein anderer Worker sieht diese Zeilen mehr als pending.
  6. Arbeit ausserhalb der Transaktion: Der Worker verarbeitet die Jobs und setzt danach completed oder failed. Stirbt er, setzt ein Stale-Job-Recovery alte processing-Zeilen nach einem Timeout zurück.

2. Aufbau

  1. Lock Table: ein Bereich im Shared Memory. Hier stehen Table Locks, Advisory Locks und Locks auf Transaktions-IDs. Grösse: max_locks_per_transaction (64, seit PostgreSQL 19: 128; PG 19 Release Notes) × (Verbindungen + prepared Transactions). Gezählt werden Objekte wie Tabellen, nicht Zeilen. Die Zahl ist ein Durchschnitt: Eine Transaktion darf mehr sperren, solange die Tabelle insgesamt reicht.
  2. Table Lock: Jeder Befehl nimmt automatisch einen. SELECT nimmt den schwächsten, DROP TABLE den stärksten.
  3. Row Lock: steht nicht im Speicher, sondern im Tuple selbst: xmax plus Lock-Bits. Darum kann man Millionen Zeilen sperren, ohne Speicher zu füllen.
  4. Warten auf eine Zeile: B sieht xmax = 801 und wartet auf den transactionid-Lock von 801. Er ist frei, sobald 801 endet.
  5. Deadlock Detector: Wartet ein Backend länger als deadlock_timeout (1 s), sucht er einen Zyklus. Findet er einen, bricht er eine Transaktion ab.
  6. pg_locks: die View auf die Lock Table. Row Locks sieht man dort nur indirekt.

3. Details, die Interviewer fragen

  1. Die 8 Table Lock Modes (schwach → stark):
    • ACCESS SHARE: SELECT. Konflikt nur mit ACCESS EXCLUSIVE.
    • ROW SHARE: SELECT … FOR UPDATE/SHARE.
    • ROW EXCLUSIVE: INSERT, UPDATE, DELETE, MERGE.
    • SHARE UPDATE EXCLUSIVE: VACUUM, ANALYZE, CREATE INDEX CONCURRENTLY, manche ALTER TABLE.
    • SHARE: CREATE INDEX (ohne CONCURRENTLY). Blockiert Schreiben.
    • SHARE ROW EXCLUSIVE: CREATE TRIGGER, manche ALTER TABLE.
    • EXCLUSIVE: REFRESH MATERIALIZED VIEW CONCURRENTLY. Nur Lesen erlaubt.
    • ACCESS EXCLUSIVE: DROP, TRUNCATE, die meisten ALTER TABLE, VACUUM FULL, CLUSTER. Blockiert sogar SELECT.
  2. Die 4 Row Lock Modes (stark → schwach):
    • FOR UPDATE: volle Sperre. Nehmen auch DELETE und ein UPDATE auf Key-Spalten.
    • FOR NO KEY UPDATE: schwächer. Nimmt ein normales UPDATE, das keine Key-Spalte ändert. Erlaubt FOR KEY SHARE.
    • FOR SHARE: mehrere Leser dürfen sperren. Blockiert jedes Ändern.
    • FOR KEY SHARE: nimmt ein Foreign-Key-Check auf die Elternzeile. Blockiert nur Löschen und Key-Änderung.
  3. Warum NO KEY UPDATE und KEY SHARE? Ein Insert in eine Kindtabelle sperrt die Elternzeile mit FOR KEY SHARE. Ein normales Update der Elternzeile nimmt nur NO KEY UPDATE. Beide passen zusammen, es gibt kein Warten.
  4. Locks halten bis Transaktionsende. Es gibt kein vorzeitiges Freigeben von Row Locks oder Table Locks. Ausnahme: Advisory Locks auf Session-Ebene.
  5. Lock Queue: Wartende Locks stellen sich in eine Schlange. Ein wartendes ALTER TABLE (ACCESS EXCLUSIVE) blockiert alle späteren SELECTs, auch wenn sie mit den aktuellen Lock-Haltern kompatibel wären.
  6. lock_timeout: bricht ab, wenn ein Lock länger als die Zeit wartet. Standard 0 = unendlich. Für Migrationen: SET lock_timeout = '3s' und bei Fehler wiederholen.
  7. statement_timeout: begrenzt die ganze Laufzeit eines Befehls, inklusive Warten.
  8. NOWAIT: wirft sofort einen Fehler, wenn die Zeile gesperrt ist. Gut, wenn der Nutzer sofort eine Meldung bekommen soll.
  9. SKIP LOCKED: überspringt gesperrte Zeilen still. Das Ergebnis ist bewusst inkonsistent. Nur für Queues geeignet, nicht für Reports.
  10. Deadlock: Zwei Transaktionen warten im Kreis aufeinander. PostgreSQL prüft nach deadlock_timeout (1 s), bricht eine ab (40P01) und loggt beide Queries.
  11. Deadlock vermeiden: immer gleiche Sperr-Reihenfolge, kurze Transaktionen, Batch-Updates sortiert nach Key. Fremdschlüssel und Trigger können versteckte Reihenfolgen erzeugen.
  12. Advisory Locks: Locks auf eine frei gewählte Zahl. pg_advisory_lock(42) (Session), pg_advisory_xact_lock(42) (bis Transaktionsende), pg_try_advisory_lock(42) (ohne Warten). Für „nur ein Cron-Job läuft“ oder Migrationen. Flyway nutzt sie auf PostgreSQL, standardmässig transaktional (flyway.postgresql.transactional.lock = true).
  13. Advisory Locks und PgBouncer: Im Transaction Pooling wechselt die Verbindung pro Transaktion. Session-Advisory-Locks landen dann auf der falschen Verbindung. Dort nur pg_advisory_xact_lock nutzen.
  14. UPDATE … RETURNING: gibt die geänderten Zeilen zurück. Das ist das PostgreSQL-Gegenstück zu SQL Server UPDATE … OUTPUT INSERTED.*. Dort entspricht WITH (UPDLOCK, READPAST) etwa SKIP LOCKED.
  15. Lock Escalation: PostgreSQL eskaliert Row Locks nie zu Table Locks. Row Locks liegen auf der Disk. SQL Server eskaliert ab ca. 5000 Locks.
  16. Warum Locks trotz MVCC? MVCC trennt nur Leser von Schreibern. Zwei Schreiber auf dieselbe Zeile brauchen eine Reihenfolge, sonst überschreibt einer den anderen (Lost Update). Und DDL darf eine Tabelle nicht ändern, während eine Query sie liest. Darum nimmt jeder Befehl mindestens ACCESS SHARE.

4. Fallen

  • „SELECT nimmt keinen Lock.“ → Falsch. Er nimmt ACCESS SHARE. Darum blockiert ein wartendes ALTER TABLE und blockiert den SELECT.
  • „ADD COLUMN ist harmlos, es dauert nur Millisekunden.“ → Falsch. Es braucht ACCESS EXCLUSIVE und kann ewig in der Queue warten.
  • „Row Locks stehen in pg_locks.“ → Meist falsch. Sie stehen im Tuple. In pg_locks sieht man nur das Warten auf die xid.
  • „PostgreSQL eskaliert viele Row Locks zu einem Table Lock.“ → Falsch. Es gibt keine Lock Escalation.
  • „SKIP LOCKED ist gut für konsistente Reports.“ → Falsch. Es lässt Zeilen still weg.
  • „PostgreSQL löst Deadlocks, ich muss nichts tun.“ → Falsch. Eine Transaktion scheitert mit 40P01. Die App braucht Retry.
  • „FOR UPDATE ist die einzige Row-Lock-Stufe.“ → Falsch. Es gibt vier: UPDATE, NO KEY UPDATE, SHARE, KEY SHARE.

5. Selbsttest

Warum?

Welche Arten von Locks hat PostgreSQL?

Table Locks (8 Stufen), Row Locks (4 Stufen), Page Locks intern und Advisory Locks für die Anwendung.

Warum braucht PostgreSQL Row Locks, obwohl es MVCC hat?

MVCC trennt nur Leser und Schreiber. Zwei Schreiber auf dieselbe Zeile brauchen eine Reihenfolge, sonst geht ein Update verloren.

Was ist ein Deadlock?

Zwei oder mehr Transaktionen warten im Kreis aufeinander. Keine kann weiter.

Wie innen?

Welchen Lock nimmt ein SELECT?

ACCESS SHARE auf die Tabelle. Er kollidiert nur mit ACCESS EXCLUSIVE, z. B. DROP oder die meisten ALTER TABLE.

Welchen Lock nehmen INSERT, UPDATE und DELETE?

ROW EXCLUSIVE auf die Tabelle und Row Locks auf die geänderten Zeilen.

Warum blockiert CREATE INDEX das Schreiben?

Es nimmt SHARE, das mit ROW EXCLUSIVE kollidiert. CREATE INDEX CONCURRENTLY nimmt nur SHARE UPDATE EXCLUSIVE.

Wo speichert PostgreSQL Row Locks?

Im Tuple-Header: xmax plus Lock-Bits. Bei mehreren Haltern eine MultiXact-ID. Darum braucht es keinen Speicher pro Zeile.

Wie erkennt PostgreSQL Deadlocks?

Wartet ein Backend länger als deadlock_timeout (1 s), sucht es einen Zyklus im Warte-Graphen. Eine Transaktion wird mit 40P01 abgebrochen.

Was ist die Lock Queue?

Wartende Lock-Anfragen stehen in einer Reihe. Spätere Anfragen warten hinter einer starken wartenden Anfrage, auch wenn sie kompatibel wären.

Gibt es Lock Escalation in PostgreSQL?

Nein. Row Locks liegen auf der Disk und werden nie zu Table Locks.

Zahlen

Was macht NOWAIT?

Ist die Zeile gesperrt, kommt sofort der Fehler 55P03 statt Warten. Seit 18 loggt log_lock_failures solche Fehler im Detail (PG 18 Release Notes).

Wie gross ist die Lock Table?

max_locks_per_transaction × (Verbindungen + prepared Transactions). Der Standard ist seit PostgreSQL 19 128, vorher 64 (PG 19 Release Notes). Gezählt werden Objekte wie Tabellen, nicht Zeilen.

Was geht kaputt, wenn eine Transaktion tausende Partitionen anfasst?

Die Lock Table läuft voll: „out of shared memory“ mit HINT auf max_locks_per_transaction. Lösung: Parameter erhöhen (Neustart) oder weniger Partitionen pro Abfrage.

Vergleich

Was ist der Unterschied zwischen FOR UPDATE und FOR NO KEY UPDATE?

FOR UPDATE blockiert auch Foreign-Key-Checks. FOR NO KEY UPDATE nicht. Ein normales UPDATE ohne Key-Änderung nimmt NO KEY UPDATE.

Warum gibt es FOR KEY SHARE?

Für Foreign-Key-Checks auf die Elternzeile. Er verhindert nur, dass sie gelöscht wird oder ihr Key sich ändert. So blockiert ein Insert in die Kindtabelle kein normales Update der Elternzeile.

Was ist das PostgreSQL-Gegenstück zu SQL Server UPDATE … OUTPUT?

UPDATE … RETURNING. Das Gegenstück zu READPAST ist SKIP LOCKED.

Warten, NOWAIT oder SKIP LOCKED: wann was?

Warten, wenn das Ergebnis vollständig sein muss. NOWAIT, wenn der Nutzer sofort eine Meldung bekommen soll. SKIP LOCKED für Queues, wo jede freie Zeile passt.

Produktion

Was ist lock_timeout und warum ist es wichtig?

Es bricht ab, wenn ein Lock zu lange wartet. In Migrationen verhindert es, dass ein wartendes ALTER TABLE die ganze App blockiert.

Was geht kaputt, wenn Session-Advisory-Locks über PgBouncer laufen?

Im Transaction Pooling gehört die Verbindung nach der Transaktion jemand anderem. Session-Locks hängen dann falsch. Lösung: pg_advisory_xact_lock.

Wie finden Sie, wer wen blockiert?

pg_stat_activity mit pg_blocking_pids(pid), dazu pg_locks mit granted = false. log_lock_waits für die Historie, seit 19 standardmässig an (PG 19 Release Notes).

Szenario: Nach einem Deployment mit Migration hängt die ganze Anwendung. Was ist passiert?

Wahrscheinlich wartet ein ALTER TABLE auf ACCESS EXCLUSIVE hinter einer langen Transaktion. Alle Queries stauen sich dahinter. Sofort: Migration abbrechen. Künftig: lock_timeout und Retry.

Szenario: Im Log stehen jede Nacht Deadlocks aus einem Batch-Job. Was tun Sie?

Die beiden Queries im Server-Log ansehen. Meist sperren zwei Pfade Zeilen in anderer Reihenfolge. Lösung: sortiert sperren, Batches kleiner, Retry für 40P01.

Design

Was macht SKIP LOCKED?

Gesperrte Zeilen werden übersprungen. Jeder Worker bekommt freie Zeilen. Ideal für Job-Queues.

Wie bauen Sie eine Job-Queue in PostgreSQL?

Ein UPDATE, das per Subquery mit FOR UPDATE SKIP LOCKED und LIMIT auswählt, Status auf processing setzt und RETURNING nutzt. Dazu ein Partial Index auf pending und Stale-Job-Recovery.

Wie vermeiden Sie Deadlocks?

Zeilen immer in gleicher Reihenfolge sperren, kurze Transaktionen, Batches nach Key sortieren. Retry für 40P01 bleibt trotzdem nötig.

Was sind Advisory Locks?

Locks auf eine frei gewählte Zahl, ohne Bezug zu Daten. Für „nur einer darf das tun“, z. B. Cron-Jobs oder Migrationen.

Warum eine Status-Spalte statt eines Locks über den ganzen Job?

So bleiben Transaktionen kurz und halten keine Locks über Minuten. Der Preis ist Stale-Job-Recovery und idempotente Verarbeitung.

Szenario: Zwei Worker verarbeiten gelegentlich dieselbe Nachricht. Wie beheben Sie das?

Claim atomar machen: ein UPDATE mit FOR UPDATE SKIP LOCKED in der Subquery und RETURNING. Zusätzlich die Verarbeitung idempotent machen, z. B. erst löschen, dann schreiben.

Mehr

Gerüst

  • Warum? MVCC trennt Leser und Schreiber, nicht Schreiber und Schreiber. Ohne Locks: Lost Updates, doppelte Jobs, DDL mitten in einer Query.
  • Wie innen? Table Locks in der Lock Table im Shared Memory. Row Locks im Tuple (xmax + Bits); Wartende warten auf die xid. Keine Lock Escalation.
  • Zahlen 8 Table-, 4 Row-Lock-Stufen. deadlock_timeout 1 s. max_locks_per_transaction 128 (vor 19: 64; PG 19 Release Notes). 40P01 = Deadlock, 55P03 = NOWAIT.
  • Vergleich Warten vs NOWAIT (Fehler) vs SKIP LOCKED (andere Zeile). FOR NO KEY UPDATE blockiert FK-Checks nicht. SQL Server: READPAST, Escalation.
  • Produktion Wartendes ALTER TABLE in der Lock Queue staut alle SELECTs. Unsortierte Batch-Updates → Deadlocks.
  • Design Claim mit FOR UPDATE SKIP LOCKED + RETURNING, dann committen und arbeiten. Migration mit lock_timeout. Nach Key sortiert sperren.

Beispiel: Queue-Claim, NOWAIT und Deadlock

CREATE TABLE message (id bigint PRIMARY KEY, status text NOT NULL, claimed_at timestamptz);
CREATE INDEX message_pending ON message (id) WHERE status = 'pending';
INSERT INTO message SELECT g, 'pending' FROM generate_series(1, 6) g;

-- A) Zwei Worker gleichzeitig (je in eigener Session, Transaktion noch offen)
BEGIN;
WITH next AS MATERIALIZED (
  SELECT id FROM message
  WHERE status = 'pending'
  ORDER BY id LIMIT 3
  FOR UPDATE SKIP LOCKED)
UPDATE message m SET status = 'processing', claimed_at = now()
FROM next WHERE m.id = next.id
RETURNING m.id;

-- B) Worker 3 will Zeile 1 sofort oder gar nicht
SELECT * FROM message WHERE id = 1 FOR UPDATE NOWAIT;

-- C) Deadlock: A sperrt 1 dann 2, B sperrt 2 dann 1
A: BEGIN; UPDATE message SET claimed_at = now() WHERE id = 1;
B: BEGIN; UPDATE message SET claimed_at = now() WHERE id = 2;
A: UPDATE message SET claimed_at = now() WHERE id = 2;   -- wartet
B: UPDATE message SET claimed_at = now() WHERE id = 1;   -- Zyklus
-- A) Worker 1        -- A) Worker 2
 id                    id
----                  ----
  1                     4
  2                     5
  3                     6
(3 rows)              (3 rows)

-- B)
ERROR:  could not obtain lock on row in relation "message"

-- C) nach ca. 1 s in einer der Sessions:
ERROR:  deadlock detected
DETAIL:  Process 4711 waits for ShareLock on transaction 802; blocked by process 4712.
Process 4712 waits for ShareLock on transaction 801; blocked by process 4711.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "message"

Erwartetes Ergebnis (laut Doku, nicht ausgeführt), PostgreSQL 17. PIDs, xids und Tuple-Adressen sind Beispiele.

  1. Worker 1 bekommt 1–3, Worker 2 bekommt 4–6. Kein Job doppelt, kein Warten.
  2. AS MATERIALIZED zwingt PostgreSQL, die Auswahl genau einmal auszuführen. Der Partial Index auf pending hält die Suche schnell.
  3. NOWAIT wartet nicht, sondern wirft sofort SQLSTATE 55P03 (lock_not_available).
  4. Beim Deadlock wartet jeder auf die xid des anderen („ShareLock on transaction“). Nach deadlock_timeout bricht PostgreSQL eine Seite ab: SQLSTATE 40P01. Die andere läuft weiter.
  5. Die Lösung für C: Zeilen immer in gleicher Reihenfolge sperren, z. B. ORDER BY id … FOR UPDATE.

Vergleich

  • Warten (Standard) vs NOWAIT vs SKIP LOCKED: Warten = korrekt, aber blockierend. NOWAIT = sofort Fehler. SKIP LOCKED = andere Zeile nehmen.
  • FOR UPDATE vs FOR NO KEY UPDATE: Wer die Zeile nur ändern will, ohne Key, nimmt NO KEY UPDATE. Das blockiert Foreign-Key-Checks nicht.
  • Pessimistisch (FOR UPDATE) vs optimistisch (Versionsspalte): Pessimistisch bei häufigem Konflikt. Optimistisch bei seltenem Konflikt und langen Nutzer-Interaktionen.
  • Row Lock vs Advisory Lock: Row Lock schützt Daten. Advisory Lock schützt eine Idee, z. B. „Import für Kunde 42“, ohne Zeile.
  • PostgreSQL-Queue vs Message Broker: Queue in der DB: transaktional mit den Daten, einfach. Kafka oder RabbitMQ: mehr Durchsatz, Fan-out, Replay. Bei moderatem Volumen reicht die Tabelle.
  • Lock halten vs Status-Spalte: Lock über die ganze Verarbeitung: Absturz gibt ihn automatisch frei, aber lange Transaktion. Status-Spalte: kurze Transaktionen, braucht Stale-Job-Recovery.

In der Produktion

  1. Migration legt die App lahm: ALTER TABLE ADD COLUMN wartet hinter einem langen Report. Alle neuen Queries stauen sich dahinter. Lösung: SET lock_timeout = '3s' in jeder Migration, mit Retry.
  2. CREATE INDEX blockiert Schreiben: Er nimmt SHARE. Inserts warten minutenlang. Lösung: CREATE INDEX CONCURRENTLY (nicht in einer Transaktion, kann mit INVALID-Index enden).
  3. Deadlocks bei Batch-Updates: Zwei Jobs ändern dieselben Zeilen in anderer Reihenfolge. Lösung: Zeilen sortiert sperren (ORDER BY id FOR UPDATE), Retry bei 40P01.
  4. Worker verarbeiten denselben Job doppelt: SELECT und danach UPDATE in zwei Schritten ohne Lock. Lösung: ein atomarer Claim mit FOR UPDATE SKIP LOCKED und RETURNING.
  5. Jobs hängen in „processing“: Ein Worker ist abgestürzt. Lösung: Stale-Job-Recovery: UPDATE … SET status = 'pending' WHERE status = 'processing' AND claimed_at < now() - interval '30 minutes'. Die Verarbeitung muss idempotent sein.
  6. Hot Row: Alle Requests ändern dieselbe Zeile, z. B. einen globalen Zähler. Alle warten seriell. Lösung: Zähler aufteilen oder Änderungen sammeln.
  7. „out of shared memory“, HINT max_locks_per_transaction: Eine Transaktion berührt tausende Partitionen oder Tabellen. Lösung: Parameter erhöhen (Neustart nötig) oder Abfrage einschränken.

Diagnose: Werkzeuge und Abfragen

-- Wer blockiert wen?
SELECT pid, pg_blocking_pids(pid) AS blockiert_von,
       wait_event_type, wait_event, state,
       now() - xact_start AS tx_dauer, left(query, 60) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Locks auf einer Tabelle
SELECT l.pid, l.mode, l.granted, a.state, left(a.query, 60)
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'message'::regclass;

-- Notfall
SELECT pg_cancel_backend(4711);      -- Query abbrechen
SELECT pg_terminate_backend(4711);   -- Verbindung beenden
  • pg_stat_activity: wait_event_type = 'Lock' mit wait_event relation, transactionid, tuple oder advisory.
  • pg_blocking_pids(pid): die direkten Blocker. Der Anfang der Kette ist oft „idle in transaction“.
  • pg_locks: granted = false zeigt wartende Locks.
  • log_lock_waits = on: loggt jedes Warten länger als deadlock_timeout. Sehr nützlich. Seit PostgreSQL 19 ist es standardmässig an (PG 19 Release Notes).
  • log_lock_failures (seit 18, Standard aus; PG 18 Release Notes): loggt Details, wenn ein NOWAIT keinen Lock bekommt.
  • pg_stat_lock (seit 19; PG 19 Release Notes): Statistik pro Lock-Typ.
  • pg_stat_database.deadlocks: Zähler für Deadlocks. Details im Server-Log.
  • pgrowlocks (Extension): zeigt Row Locks einer Tabelle.

Senior-Punkte

  1. Jede Migration mit lock_timeout. Der gefährlichste Lock ist der, der wartet, nicht der, der hält.
  2. Sperr-Reihenfolge ist Architektur. Wer Zeilen immer nach Key sortiert sperrt, hat kaum Deadlocks. Deadlocks brauchen trotzdem Retry.
  3. Atomarer Claim statt Lesen-dann-Schreiben. Ein Befehl mit FOR UPDATE SKIP LOCKED und RETURNING ist die Standard-Queue in PostgreSQL.
  4. Kurze Transaktionen, Status statt Lock. Den Job nicht in der Transaktion verarbeiten. Claim committen, dann arbeiten, dann Status setzen.
  5. At-least-once ist die Realität. Stale-Job-Recovery kann einen Job zweimal starten. Die Verarbeitung muss idempotent sein.
  6. Die Datenbank als Queue hat Grenzen. Bis einige tausend Jobs pro Sekunde gut. Darüber Bloat und Lock-Druck, dann ein Broker.
