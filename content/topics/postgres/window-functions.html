Window Functions

PostgreSQL · Tier 1 · Quellen: PostgreSQL 17 Doku (aktuell ist PostgreSQL 19; wichtige Unterschiede in 18/19 laut Release Notes stehen im Text), Kapitel 3.5 „Window Functions“ (Tutorial), Kapitel 4.2.8 „Window Function Calls“ (Frame-Syntax), Kapitel 9.22 „Window Functions“ (Funktionsliste), Kapitel 7.2.5 „Window Function Processing“, SELECT (WINDOW-Klausel), Release Notes 15 (Run Condition)

Kern: Eine Window Function ist eine Funktion, die für jede Zeile über eine Gruppe verwandter Zeilen rechnet, das Fenster. Anders als GROUP BY bleiben dabei alle Zeilen erhalten. Sie löst Ranglisten, laufende Summen, Vergleiche mit der Vorzeile und Top-N pro Gruppe in einer Abfrage, ohne Self-Join.

1. Wo sitzen Window Functions?

  1. FROM / JOIN: baut die Ausgangszeilen.
  2. WHERE: filtert Zeilen. Window Functions sind hier noch nicht berechnet.
  3. GROUP BY / HAVING: fasst Zeilen zusammen. Danach arbeitet das Fenster auf den Gruppen-Zeilen.
  4. WINDOW: Der Executor-Knoten WindowAgg rechnet alle Window Functions. Er braucht die Zeilen sortiert nach PARTITION BY und ORDER BY.
  5. SELECT, DISTINCT, ORDER BY, LIMIT: kommen danach. Darum darf ORDER BY der Abfrage nach einem Window-Wert sortieren.

2. Die Reise einer Zeile durch das Fenster (die Geschichte zum Merken)

  1. Zeilen kommen an. Die Abfrage will pro Händler eine laufende Summe: sum(volume) OVER (PARTITION BY trader ORDER BY day). Die Zeilen kommen aus WHERE in beliebiger Reihenfolge.
  2. Sortieren und teilen. WindowAgg braucht die Zeilen nach trader, day sortiert. Ein Sort-Knoten macht das, oder ein passender Index. Jeder Händler ist jetzt eine Partition.
  3. Frame bestimmen. Für die Zeile „Alpine, 03-03“ ist der Frame der Ausschnitt der Partition, über den gerechnet wird. Standard mit ORDER BY: vom Anfang bis zur aktuellen Zeile (inklusive gleicher Werte). Also 03-02 und 03-03.
  4. Rechnen und anhängen. Die Summe ist 40 + 90 = 130. Die Zeile bleibt erhalten und bekommt eine neue Spalte.
  5. Weiter. Die nächste Zeile (03-05) erweitert den Frame: 150. Bei „Bern“ beginnt eine neue Partition, die Summe startet wieder bei 0.

3. Beispiel: Ranking, laufende Summe, LAG, ROWS vs RANGE, Gaps and Islands

CREATE TABLE trades(day date, trader text, volume int);
INSERT INTO trades VALUES
 ('2026-03-02','Alpine',40),('2026-03-02','Bern',70),('2026-03-02','Ceres',70),
 ('2026-03-03','Alpine',90),('2026-03-03','Bern',30),
 ('2026-03-05','Alpine',20),('2026-03-06','Alpine',50);

-- 1) Ranking pro Tag, laufende Summe und Vorwert pro Händler
SELECT day, trader, volume,
  row_number() OVER w AS rn,
  rank()       OVER w AS rnk,
  dense_rank() OVER w AS drnk,
  sum(volume)  OVER (PARTITION BY trader ORDER BY day) AS running,
  lag(volume)  OVER (PARTITION BY trader ORDER BY day) AS prev
FROM trades
WINDOW w AS (PARTITION BY day ORDER BY volume DESC)
ORDER BY day, volume DESC, trader;

-- 2) RANGE (Standard) vs ROWS bei gleichen Werten
SELECT trader, volume,
  sum(volume) OVER (ORDER BY volume) AS range_default,
  sum(volume) OVER (ORDER BY volume ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_frame
FROM trades WHERE day = '2026-03-02' ORDER BY volume, trader;

-- 3) Gaps and Islands: zusammenhängende Handelstage pro Händler
SELECT trader, min(day) AS von, max(day) AS bis, count(*) AS tage
FROM (SELECT trader, day,
             julianday(day) - row_number() OVER (PARTITION BY trader ORDER BY day) AS grp
      FROM trades) t
GROUP BY trader, grp ORDER BY trader, von;
-- in PostgreSQL: day - (row_number() OVER (...))::int AS grp   (date minus integer = date)

Echte Ausgabe, SQLite 3.49.1 (über Python 3.12), weil PostgreSQL hier nicht lief. Die Window-Syntax und -Semantik sind SQL-Standard und in PostgreSQL 17 gleich. Einziger Unterschied: julianday(day) ist SQLite; in PostgreSQL rechnet man direkt day - (row_number() OVER (...))::int. Die Tabelle legte das Skript als day text an.

  1. row_number vs rank vs dense_rank: Bern und Ceres haben am 03-02 beide 70. row_number vergibt trotzdem 1 und 2. Welcher die 1 bekommt, ist nicht garantiert. rank gibt beiden 1 und springt dann auf 3. dense_rank gibt beiden 1 und macht mit 2 weiter.
  2. running: Alpine: 40 → 130 → 150 → 200. Die Partition ist pro Händler, sortiert nach Tag.
  3. prev (LAG): Der Wert der Vorzeile in derselben Partition. Die erste Zeile jeder Partition hat NULL.
  4. RANGE vs ROWS: Mit dem Standard-Frame RANGE zählen Peers (Zeilen mit gleichem ORDER BY-Wert) zusammen. Bern und Ceres bekommen beide 180. Mit ROWS zählt die physische Zeile: 110, dann 180.
  5. Gaps and Islands: In einer Folge ohne Lücke steigen Datum und row_number gleich schnell. Ihre Differenz ist konstant. Eine Lücke (03-04 fehlt) ändert die Differenz. So entstehen zwei „Inseln“ für Alpine.

4. Details, die Interviewer fragen

  1. OVER: macht aus einer Funktion eine Window Function. OVER () leer heisst: das Fenster ist die ganze Ergebnismenge. Beispiel: volume * 100.0 / sum(volume) OVER () = Anteil am Total.
  2. PARTITION BY: teilt die Zeilen in unabhängige Gruppen. Die Funktion startet pro Partition neu. Ohne PARTITION BY ist alles eine Partition.
  3. ORDER BY im Fenster: bestimmt die Reihenfolge in der Partition. Sie ist unabhängig vom ORDER BY der Abfrage. Für row_number, lag und laufende Summen ist sie Pflicht.
  4. Frame: der Ausschnitt der Partition für Aggregat-Funktionen und first_value/last_value/nth_value. Ranking-Funktionen und lag/lead ignorieren den Frame.
  5. Standard-Frame: Mit ORDER BY: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, inklusive Peers. Ohne ORDER BY: die ganze Partition.
  6. ROWS: zählt physische Zeilen. Beispiel gleitender Durchschnitt über 7 Zeilen: avg(x) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW).
  7. RANGE: arbeitet mit Werten. Seit PostgreSQL 11 auch mit Abstand: RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW. Das ist korrekt auch bei fehlenden Tagen. ROWS wäre dann falsch.
  8. GROUPS (seit Version 11): zählt Gruppen von Peers. GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW = aktuelle und vorige Wertegruppe.
  9. EXCLUDE (seit Version 11): EXCLUDE CURRENT ROW, GROUP, TIES, NO OTHERS. Beispiel: Durchschnitt der Nachbarn ohne die eigene Zeile.
  10. Ranking-Funktionen: row_number() (fortlaufend, eindeutig), rank() (gleiche Werte gleicher Rang, dann Lücke), dense_rank() (ohne Lücke), percent_rank(), cume_dist(), ntile(n) (in n etwa gleich grosse Gruppen teilen, z. B. Quartile).
  11. LAG / LEAD: lag(x, n, default) holt den Wert n Zeilen davor, lead danach. Typisch: Differenz zum Vortag x - lag(x) OVER (ORDER BY day). IGNORE NULLS gibt es erst seit PostgreSQL 19 (für lead, lag, first_value, last_value, nth_value). PostgreSQL 17 und 18 kennen es nicht.
  12. first_value / last_value / nth_value: Wert aus dem Frame. Falle: last_value mit Standard-Frame liefert die aktuelle Zeile (bzw. ihren letzten Peer). Lösung: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.
  13. Laufende Summe: sum(x) OVER (PARTITION BY k ORDER BY t). Bei doppelten t lieber ROWS oder einen eindeutigen Tie-Breaker, sonst springen Peers gemeinsam.
  14. Top-N pro Gruppe: row_number() in einer Subquery oder CTE, aussen WHERE rn <= 3. Für Top-1: PostgreSQL-eigenes DISTINCT ON (k) ... ORDER BY k, x DESC. Bei wenigen Gruppen und Index: LATERAL (... ORDER BY x DESC LIMIT 3) pro Gruppe.
  15. Run Condition (seit Version 15): Bei WHERE rn <= 3 aussen hört WindowAgg pro Partition früh auf. Im Plan: Run Condition: (row_number() OVER (?) <= 3). Gilt für row_number, rank, dense_rank, count.
  16. Kein Filter auf Window-Werte im WHERE: WHERE row_number() OVER ... = 1 ist ein Fehler. PostgreSQL 17 hat kein QUALIFY. Lösung: Subquery oder CTE.
  17. WINDOW-Klausel: benannte Fenster, z. B. WINDOW w AS (PARTITION BY day ORDER BY volume DESC). Weniger Wiederholung, und gleiche Fenster teilen sich einen Sort.
  18. Aggregat + Window kombiniert: sum(sum(volume)) OVER (ORDER BY day) = laufende Summe der Tagessummen. Das innere sum ist das GROUP BY-Aggregat, das äussere das Fenster.
  19. FILTER: Aggregate im Fenster können filtern: count(*) FILTER (WHERE status = 'open') OVER (PARTITION BY k).
  20. Kosten: Jedes andere PARTITION BY/ORDER BY kann einen eigenen Sort brauchen. Ein Index auf (partition_key, order_key) kann den Sort sparen. Grosse Partitionen nutzen einen Tuplestore, der über work_mem auf Platte geht.

5. Vergleich

  • Window Function vs GROUP BY: GROUP BY macht aus vielen Zeilen eine. Window Functions behalten jede Zeile und hängen den Gruppenwert an.
  • row_number: 1, 2, 3, 4 – immer eindeutig, bei Gleichstand zufällig.
  • rank: 1, 1, 3, 4 – Gleichstand gleich, dann Lücke („Olympia-Ranking“).
  • dense_rank: 1, 1, 2, 3 – Gleichstand gleich, keine Lücke.
  • ROWS: physische Zeilen. Vorhersagbar, schnell.
  • RANGE: Werte, Peers zählen zusammen. Mit Offset für Zeitfenster.
  • GROUPS: Gruppen von Peers.
  • Window Function vs korrelierte Subquery / Self-Join: Für Vorwert oder laufende Summe brauchte man früher einen Self-Join, oft O(n²). Das Fenster braucht einen Sort und einen Durchlauf.
  • DISTINCT ON vs row_number: DISTINCT ON ist kürzer für Top-1, aber nur PostgreSQL. row_number ist Standard und kann Top-N.

6. In der Produktion

  1. Nicht-deterministische Ergebnisse: row_number() OVER (ORDER BY created_at) mit gleichen Zeitstempeln liefert bei jedem Lauf andere Nummern. Pagination oder Deduplizierung wird instabil. Lösung: eindeutigen Tie-Breaker ergänzen, z. B. ORDER BY created_at, id.
  2. Falsche laufende Summe bei Duplikaten: Der Standard-Frame RANGE fasst Peers zusammen. Lösung: ROWS oder Tie-Breaker.
  3. last_value liefert die aktuelle Zeile: Standard-Frame endet bei der aktuellen Zeile. Lösung: Frame bis UNBOUNDED FOLLOWING oder first_value mit umgekehrter Sortierung.
  4. Gleitender 7-Tage-Schnitt falsch: ROWS 6 PRECEDING bei fehlenden Tagen nimmt mehr als 7 Tage. Lösung: RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW.
  5. Langsamer Report mit vielen Fenstern: Jedes Fenster sortiert neu, Sorts spillen auf Platte. Lösung: gleiche Fenster per WINDOW-Klausel teilen, früher filtern, Index auf Partition und Ordnung, work_mem für die Session.
  6. Deduplizierung: Doppelte Zeilen löschen: row_number() OVER (PARTITION BY business_key ORDER BY updated_at DESC), alles mit rn > 1 löschen. Vorher in einer Transaktion prüfen.

7. Diagnose: Werkzeuge und Abfragen

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM (
  SELECT t.*, row_number() OVER (PARTITION BY trader ORDER BY volume DESC) AS rn
  FROM trades t) s
WHERE rn <= 3;

-- typische Plan-Form (PostgreSQL 15+)
Subquery Scan on s
  Filter: (s.rn <= 3)
  ->  WindowAgg
        Run Condition: (row_number() OVER (?) <= 3)
        ->  Sort
              Sort Key: t.trader, t.volume DESC
              Sort Method: quicksort  Memory: 25kB
              ->  Seq Scan on trades t

Plan-Form: Erwartetes Ergebnis (laut Doku, nicht ausgeführt).

  • EXPLAIN: Anzahl WindowAgg- und Sort-Knoten. Jedes neue Fenster kann einen Sort kosten.
  • Sort Method: external merge Disk: work_mem zu klein.
  • Run Condition: zeigt, dass PostgreSQL früh abbricht. Fehlt sie, ist der Filter nicht direkt auf der Window-Spalte.
  • Testdaten mit Gleichstand anlegen: prüft, ob row_number, rank und Frames das Richtige tun.

8. Senior-Punkte

  1. Immer einen eindeutigen Tie-Breaker im Fenster-ORDER BY, wenn das Ergebnis stabil sein muss. Sonst sind Tests grün und Produktion flackert.
  2. Frame bewusst setzen. Der Standard RANGE ... CURRENT ROW ist selten das, was man meint, wenn es Duplikate gibt. Ich schreibe den Frame explizit.
  3. Zeitfenster mit RANGE und Intervall, nicht mit ROWS. Daten haben Lücken.
  4. Top-N pro Gruppe hat drei Lösungen: row_number (Standard, liest alles), DISTINCT ON (Top-1, kurz), LATERAL ... LIMIT mit Index (wenige Gruppen, sehr viele Zeilen). Ich wähle nach Datenform.
  5. Semantik vor Performance: Laufende Summe, Tagessumme und Anteil am Total sehen ähnlich aus, sind aber verschiedene Fragen. Vor dem Schreiben klären, was gemeint ist.
  6. Window Functions ersetzen viel Anwendungscode. Ranking und Differenzen in der Datenbank sind meist schneller und einfacher als Schleifen in Java.

10. Fallen

  • „Window Functions fassen Zeilen zusammen wie GROUP BY.“ → Falsch. Jede Zeile bleibt erhalten.
  • „WHERE row_number() OVER (...) = 1 geht.“ → Falsch. Window Functions laufen nach WHERE. Subquery oder CTE nutzen.
  • „sum() OVER (ORDER BY x) summiert Zeile für Zeile.“ → Nicht immer. Der Standard-Frame ist RANGE. Gleiche x-Werte bekommen dieselbe Summe.
  • „last_value gibt den letzten Wert der Partition.“ → Falsch mit Standard-Frame. Er gibt den letzten Wert bis zur aktuellen Zeile.
  • „row_number ist bei Gleichstand stabil.“ → Falsch. Ohne Tie-Breaker ist die Reihenfolge zufällig.
  • „rank und dense_rank sind gleich.“ → Falsch. rank lässt nach Gleichstand Lücken, dense_rank nicht.
  • „ROWS 6 PRECEDING ist ein 7-Tage-Fenster.“ → Falsch bei Lücken. Es sind 7 Zeilen, nicht 7 Tage.

11. Fragen

Was ist eine Window Function?

Eine Funktion, die für jede Zeile über ein Fenster verwandter Zeilen rechnet. Die Zeilen bleiben erhalten, anders als bei GROUP BY.

Was ist der Unterschied zu GROUP BY?

GROUP BY macht aus einer Gruppe eine Zeile. Eine Window Function hängt den Gruppenwert an jede einzelne Zeile.

Was macht PARTITION BY?

Es teilt die Zeilen in unabhängige Gruppen. Die Funktion startet in jeder Partition neu.

Was macht ORDER BY in OVER?

Es legt die Reihenfolge innerhalb der Partition fest. Ranking, LAG/LEAD und laufende Summen hängen davon ab.

Was ist ein Frame?

Der Ausschnitt der Partition, über den Aggregate und first/last/nth_value rechnen. Er wandert mit der aktuellen Zeile.

Was ist der Standard-Frame?

Mit ORDER BY: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, inklusive Peers. Ohne ORDER BY: die ganze Partition.

ROWS vs RANGE?

ROWS zählt physische Zeilen. RANGE arbeitet mit Werten: Zeilen mit gleichem Wert zählen zusammen, und mit Offset kann man Zeitfenster bilden.

Was ist GROUPS?

Ein Frame-Modus seit PostgreSQL 11, der Gruppen von Peers zählt statt Zeilen oder Werte.

ROW_NUMBER vs RANK vs DENSE_RANK?

row_number: immer eindeutig. rank: Gleichstand gleicher Rang, dann Lücke (1,1,3). dense_rank: Gleichstand gleicher Rang, ohne Lücke (1,1,2).

Was machen LAG und LEAD?

Sie holen einen Wert aus einer früheren oder späteren Zeile der Partition. Mit Offset und Default-Wert, z. B. lag(x, 1, 0).

Wie berechnen Sie eine laufende Summe?

sum(x) OVER (PARTITION BY k ORDER BY t). Bei doppelten t mit ROWS oder einem Tie-Breaker, sonst springen Peers gemeinsam.

Wie berechnen Sie den Anteil am Total?

x * 100.0 / sum(x) OVER () für das Gesamttotal, oder OVER (PARTITION BY k) für den Anteil pro Gruppe.

Wie lösen Sie Top-N pro Gruppe?

row_number() OVER (PARTITION BY gruppe ORDER BY wert DESC) in einer Subquery, aussen WHERE rn <= N. Für Top-1 auch DISTINCT ON, bei Index und wenigen Gruppen LATERAL mit LIMIT.

Warum kann ich nicht im WHERE auf row_number filtern?

Window Functions werden nach WHERE, GROUP BY und HAVING berechnet. Darum braucht es eine äussere Abfrage.

Was ist Gaps and Islands?

Zusammenhängende Folgen finden, z. B. aufeinanderfolgende Tage. Trick: Wert minus row_number ist in einer lückenlosen Folge konstant und dient als Gruppen-Schlüssel.

Warum liefert last_value oft die aktuelle Zeile?

Der Standard-Frame endet bei der aktuellen Zeile. Für den echten letzten Wert den Frame bis UNBOUNDED FOLLOWING erweitern.

Wie macht man einen gleitenden 7-Tage-Durchschnitt?

avg(x) OVER (ORDER BY day RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW). ROWS wäre bei fehlenden Tagen falsch.

Was ist die WINDOW-Klausel?

Sie benennt ein Fenster einmal, z. B. WINDOW w AS (...). Mehrere Funktionen nutzen es mit OVER w, und PostgreSQL sortiert nur einmal.

Was kostet eine Window Function?

Meist einen Sort nach Partition und Ordnung, dann einen Durchlauf. Verschiedene Fenster können mehrere Sorts brauchen. Ein passender Index kann den Sort sparen.

Was ist die Run Condition?

Seit PostgreSQL 15 hört WindowAgg früh auf, wenn aussen z. B. rn <= 3 filtert. Im Plan steht „Run Condition“.

Was bedeutet sum(sum(x)) OVER (ORDER BY day)?

Das innere sum ist das GROUP-BY-Aggregat pro Tag. Das äussere ist die laufende Summe über die Tagessummen.

Was macht ntile(4)?

Es teilt die Partition in 4 möglichst gleich grosse Gruppen und gibt die Gruppennummer zurück, z. B. für Quartile.

Unterstützt PostgreSQL IGNORE NULLS bei LAG?

Erst seit PostgreSQL 19, für lead, lag, first_value, last_value und nth_value. In 17 und 18 gilt immer RESPECT NULLS. Umweg dort: Gruppen über count(x) OVER (...) bilden und first_value pro Gruppe nehmen.

Wie löschen Sie Duplikate mit Window Functions?

row_number() OVER (PARTITION BY business_key ORDER BY updated_at DESC, id DESC) berechnen und alle Zeilen mit rn > 1 löschen.

Szenario: Ein Paging-Endpoint mit row_number zeigt manchmal Datensätze doppelt oder gar nicht. Warum?

Das ORDER BY im Fenster ist nicht eindeutig, z. B. gleiche Zeitstempel. Jeder Lauf nummeriert anders. Lösung: eindeutigen Tie-Breaker wie id ergänzen, besser Keyset-Pagination.

Szenario: Die „kumulierte Summe“ im Dashboard springt bei manchen Tagen doppelt. Woran liegt es?

Wahrscheinlich mehrere Zeilen pro Tag und der Standard-Frame RANGE. Peers bekommen dieselbe Summe. Lösung: erst pro Tag gruppieren, dann sum(sum(x)) OVER (ORDER BY day), oder ROWS mit Tie-Breaker.

Szenario: Ein Report mit fünf verschiedenen Fenstern ist langsam. Was tun Sie?

EXPLAIN prüfen: Jedes Fenster sortiert neu, vielleicht auf Platte. Fenster mit gleicher Partition und Ordnung zusammenlegen, früher filtern, Index auf (partition, order) und work_mem für die Session erhöhen.
