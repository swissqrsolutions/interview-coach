JSONB und Indizes darauf

Kern: JSONB ist der binäre JSON-Typ von PostgreSQL: Das Dokument wird beim Schreiben einmal geparst und zerlegt gespeichert. Dadurch sind Zugriffe auf Felder schnell, und ein GIN-Index findet Dokumente nach Inhalt. Der Preis: keine Statistiken über innere Felder und jedes Update schreibt das ganze Dokument neu.

Antwort-Muster

Frage: Wie indizieren Sie eine JSONB-Spalte?

  1. Mechanismus: Ein GIN-Index speichert Keys und Werte invertiert und beantwortet @>. Für ein einzelnes Feld nehme ich einen B-Tree auf den Ausdruck.
  2. Zahl: Bei 200 000 Zeilen war jsonb_path_ops 25 % kleiner als jsonb_ops.
  3. Trade-off: jsonb_path_ops ist kleiner, kann aber kein ?. Jeder GIN macht Inserts teurer.
  4. Produktion: Ich prüfe mit EXPLAIN, ob der Operator der Abfrage zur Opclass passt.

1. Die Reise einer JSONB-Abfrage

  1. Abfrage: WHERE doc @> '{"firma":"F42"}' fragt: Enthält das Dokument dieses Teil-Dokument?
  2. Operator prüfen: Der Planner nutzt einen Index nur, wenn dessen Operator Class den Operator kennt. jsonb_path_ops kennt @>, @?, @@.
  3. Query zerlegen: GIN zerlegt die Suche in Schlüssel. Bei jsonb_path_ops ist das ein Hash aus Pfad und Wert, hier firma → F42.
  4. GIN-Lookup: Zu jedem Schlüssel gibt es eine Posting List, eine Liste von Zeilenadressen (TIDs).
  5. Bitmap: Die TIDs kommen in eine Bitmap. PostgreSQL liest die Heap-Seiten in Reihenfolge.
  6. Recheck: Hashes können kollidieren. Darum prüft PostgreSQL @> auf jedem gefundenen Dokument noch einmal.
  7. Ergebnis: 100 Zeilen. Dieselbe Frage als doc->>'firma' = 'F42' ist ein anderer Operator. Der GIN hilft dort nicht.

2. Aufbau

  1. Parsen beim Schreiben: PostgreSQL prüft das JSON und baut den binären Wert. Leerzeichen fallen weg, Keys werden sortiert, bei doppelten Keys gewinnt der letzte.
  2. jsonb-Wert: Ein Header mit Längen und Offsets erlaubt, einen Key ohne Parsen zu finden. Zahlen werden als numeric gespeichert.
  3. Heap-Zeile: Kleine Dokumente liegen direkt in der Zeile. Beispiel: das Event im Beispiel unten hat 93 Byte.
  4. TOAST: Ist die Zeile breiter als etwa 2 kB, komprimiert TOAST (The Oversized-Attribute Storage Technique) den Wert und lagert ihn in eine eigene Tabelle aus. Maximal 1 GB pro Wert.
  5. GIN-Index: Ein invertierter Index über Keys und Werte des ganzen Dokuments. Er beantwortet „enthält“-Fragen wie @>. Interna und Pending List: Seite Index-Typen.
  6. B-Tree auf Ausdruck: Ein normaler Index auf ein einzelnes Feld, z. B. (doc->>'firma'). Er beantwortet =, < und Sortierung.
  7. Planner: ANALYZE sammelt Statistiken für die ganze Spalte, nicht für innere Felder. Ohne Hilfe rät der Planner bei Filtern auf Feldern.

3. Details, die Interviewer fragen

  1. Operatoren: -> liefert jsonb, ->> liefert text. #> und #>> gehen über einen Pfad, z. B. doc #>> '{kopf,art}'.
  2. Containment-Regeln: Array-Reihenfolge zählt nicht, Duplikate auch nicht. '[1,2,3]' @> '[3,1]' ist true. Ein Array enthält auch einen einzelnen Wert: '["a","b"]' @> '"b"' ist true.
  3. jsonb_ops: Die Standard-Opclass legt je einen Eintrag pro Key und pro Wert an. Sie kann @>, ?, ?|, ?&, @?, @@.
  4. jsonb_path_ops: Ein Eintrag ist ein Hash aus Pfad und Wert. Kleiner und genauer, aber kein ?. Leere Strukturen wie {"a": {}} erzeugen keinen Eintrag; eine Suche danach liest den ganzen Index.
  5. Teil-Index auf ein Unterobjekt: USING gin ((doc->'tags')) indiziert nur die Tags. Kleiner, aber die Abfrage muss genau diesen Ausdruck nutzen.
  6. B-Tree auf jsonb: Ein B-Tree auf die ganze Spalte hilft nur bei Gleichheit kompletter Dokumente. Für Felder: Ausdrucksindex.
  7. SQL/JSON Path: jsonpath ist eine eigene Pfadsprache. @? fragt „liefert der Pfad etwas?“, @@ wertet ein Prädikat aus. Beispiel: doc @? '$.tags[*] ? (@ == "storno")'.
  8. lax vs strict: Im Standardmodus lax passt sich der Pfad an die Daten an, Strukturfehler ergeben „kein Treffer“. strict wirft einen Fehler.
  9. SQL/JSON-Funktionen (seit 17): JSON_VALUE liefert einen Skalar, JSON_QUERY ein JSON-Stück, JSON_EXISTS ein boolean, JSON_TABLE Zeilen. Ohne ON ERROR gibt es NULL bzw. false.
  10. Ändern: jsonb_set(doc, '{pfad}', wert), || zum Zusammenführen (flach), - löscht einen Key, #- löscht über einen Pfad. Subscripting (seit 14) schreibt doc['key'] = ….
  11. Jedes Update schreibt alles neu: MVCC erzeugt eine neue Zeilenversion mit dem ganzen Dokument. Ist es getoastet, wird der TOAST-Wert neu geschrieben. Ein unverändertes TOAST-Feld kostet beim Update nichts.
  12. TOAST: Ab etwa 2 kB Zeilenbreite wird komprimiert (pglz Standard oder lz4) und ausgelagert. Jeder Feldzugriff muss den Wert dann ganz holen und entpacken.
  13. Statistiken: Für innere Felder gibt es keine. Lösung: Ausdrucksindex (bekommt eigene Statistik) oder CREATE STATISTICS auf den Ausdruck (seit 14).
  14. Generated Column: Ein Feld als Spalte herausziehen: firma text GENERATED ALWAYS AS (doc->>'firma') STORED. Seit 18 ist VIRTUAL der Standard (Release Notes 18, Utility Commands); für Index und Speicherung schreibe ich STORED explizit.
  15. Zahlen: jsonb speichert Zahlen als numeric. 1.230e-5 wird zu 0.00001230, Nullen am Ende bleiben, NaN ist verboten.
  16. Neu in 19: jsonpath bekommt String-Methoden wie lower(), upper(), replace() (Release Notes 19, Data Types). COPY TO kann JSON ausgeben (Release Notes 19, COPY). Ein json_array() über eine Abfrage ohne Zeilen liefert jetzt [] statt NULL (Release Notes 19, Migration).
  17. Neu in 18: Ein jsonb-null lässt sich in einen Skalar-Typ casten und ergibt SQL-NULL; vorher gab das einen Fehler (Release Notes 18, Data Types). Beispiel: ('{"menge": null}'::jsonb->'menge')::int.

4. Fallen

  • „Ein GIN auf doc beschleunigt jede JSONB-Abfrage.“ → Falsch. Nur Operatoren der Opclass, z. B. @>. doc->>'x' = 'y' braucht einen Ausdrucksindex.
  • „? findet Keys überall im Dokument.“ → Falsch. Nur auf der obersten Ebene.
  • „|| führt verschachtelte Objekte zusammen.“ → Falsch. Es ist flach und ersetzt den ganzen Wert eines Keys.
  • „Ein Update auf ein Feld ändert nur dieses Feld auf der Platte.“ → Falsch. Es entsteht eine neue Zeilenversion mit dem ganzen Dokument.
  • „jsonb behält die Reihenfolge der Keys.“ → Falsch. Keys werden sortiert gespeichert. Nur json behält sie.
  • „jsonb_path_ops ist immer besser.“ → Falsch. Es kann kein ? und findet leere Strukturen nur per Full-Index-Scan.
  • „Der Planner kennt die Werte in meinem JSON.“ → Falsch. Ohne Ausdrucksindex oder CREATE STATISTICS rät er.

5. Selbsttest

Warum?

Was ist der Unterschied zwischen json und jsonb?

json speichert den Text unverändert. jsonb speichert binär, mit sortierten Keys, ohne Duplikate, und ist indizierbar.

Warum speichert man JSON überhaupt in einer relationalen Datenbank?

Für variable Attribute und externe Payloads, die nicht für jedes Feld eine Migration wert sind. Man behält dabei Transaktionen, Joins und Backups an einem Ort.

Warum ist jsonb beim Lesen schneller als json?

jsonb wird einmal beim Schreiben geparst. Ein Header mit Offsets findet einen Key ohne neues Parsen. json muss bei jedem Zugriff den Text neu parsen.

Wie innen?

Was passiert mit doppelten Keys in jsonb?

Nur der letzte Wert bleibt.

Was ist der Unterschied zwischen -> und ->>?

-> liefert jsonb, ->> liefert text. Für Vergleiche mit Strings und für Casts nimmt man ->>.

Was macht @>?

Containment: Enthält das linke Dokument das rechte als Teilstruktur, ab der Wurzel? Array-Reihenfolge spielt keine Rolle.

Findet ? einen verschachtelten Key?

Nein. ? prüft nur Keys oder String-Elemente auf der obersten Ebene.

Wie baut jsonb_path_ops seine Index-Einträge?

Ein Eintrag pro Wert, als Hash aus dem Wert und allen Keys auf dem Weg dorthin.

Warum braucht ein GIN-Scan einen Recheck?

Die Index-Einträge sind Hashes und können kollidieren. Darum wird jedes gefundene Dokument noch einmal geprüft.

Was ist TOAST?

Die Technik für grosse Werte: Ab etwa 2 kB Zeilenbreite wird komprimiert und in eine eigene Tabelle ausgelagert. Maximal 1 GB pro Wert.

Was ist SQL/JSON Path?

Eine Pfadsprache für JSON, z. B. '$.tags[*] ? (@ == "storno")'. Nutzbar mit @?, @@ und den jsonb_path_*-Funktionen.

Was macht JSON_TABLE?

Seit 17: Es macht aus JSON Zeilen und Spalten, mit NESTED PATH auch aus verschachtelten Arrays. Es steht im FROM-Teil.

Wie ändere ich einen Wert in einem Dokument?

Mit jsonb_set, mit Subscripting doc['key'] = '…' seit 14, oder mit || für flaches Zusammenführen.

Zahlen

Hat der Planner Statistiken für JSON-Felder?

Nein. Er rät mit festen Anteilen. Ein Ausdrucksindex oder CREATE STATISTICS auf den Ausdruck liefert echte Statistiken.

Warum schätzt der Planner bei (doc->>'menge')::int < 10 genau 66 667 von 200 000 Zeilen?

Ohne Statistik nimmt er für einen Bereichsfilter fest ein Drittel an. Wahr waren 4 000. Mit CREATE STATISTICS auf den Ausdruck schätzte er 4 050.

Was kostet ein Update auf ein Feld?

Eine neue Zeilenversion mit dem ganzen Dokument, plus WAL und eventuell neuer TOAST-Wert.

Wie gross sind meine Dokumente?

pg_column_size(doc) zeigt die gespeicherte Grösse nach Kompression. Der Durchschnitt über eine Stichprobe reicht meist.

Vergleich

Welche Indizes gibt es für JSONB?

GIN mit jsonb_ops oder jsonb_path_ops, GIN auf ein Unterobjekt, B-Tree auf einen Ausdruck wie doc->>'firma', und B-Tree/Hash für ganze Dokumente.

jsonb_ops oder jsonb_path_ops?

jsonb_ops, wenn Key-Existenz mit ? gebraucht wird. Sonst jsonb_path_ops: kleiner, genauer, für @>, @? und @@.

Was ist der Unterschied zwischen lax und strict?

lax ist Standard und ignoriert Strukturfehler. strict wirft bei fehlenden Keys oder falschen Typen einen Fehler.

JSON_VALUE vs JSON_QUERY?

JSON_VALUE liefert einen Skalar als SQL-Wert. JSON_QUERY liefert ein JSON-Stück, z. B. ein Objekt oder Array.

Warum reicht JSONB oft statt MongoDB?

JSONB gibt Dokumente mit Transaktionen, Joins und Constraints in derselben Datenbank. MongoDB lohnt sich eher bei nativem Sharding und sehr grossen, oft teilweise geänderten Dokumenten.

Produktion

Warum nutzt WHERE doc->>'firma' = 'F42' meinen GIN nicht?

Weil der Operator = auf text nicht zur GIN-Opclass gehört. Lösung: doc @> '{"firma":"F42"}' oder ein Ausdrucksindex.

Szenario: Eine Suche über JSONB ist trotz GIN langsam. Was prüfen Sie?

Den Operator in der Abfrage: Passt er zur Opclass? Dann EXPLAIN ANALYZE: Index genutzt, Schätzung richtig, Recheck teuer? Lösung: Abfrage als @> umschreiben oder Ausdrucksindex.

Szenario: Ein Join mit JSONB-Filter wählt einen Nested Loop und braucht Minuten. Warum?

Der Planner schätzt den Filter falsch, weil er keine Statistik für das Feld hat. Lösung: CREATE STATISTICS auf den Ausdruck oder Generated Column, dann ANALYZE.

Szenario: Die WAL-Menge explodiert, seit ein Status-Feld im JSON-Dokument oft aktualisiert wird. Was tun Sie?

Das Status-Feld als eigene Spalte herausziehen. Dann bleibt ein grosses, ausgelagertes Dokument beim Update unverändert im TOAST und wird nicht neu geschrieben.

Design

Wann ziehe ich ein Feld in eine Spalte heraus?

Wenn es oft gefiltert, gejoint, sortiert, referenziert oder oft geändert wird.

Kann ich ein JSON-Feld als Generated Column abbilden?

Ja: GENERATED ALWAYS AS (doc->>'firma') STORED. Seit 18 ist VIRTUAL der Standard (Release Notes 18), darum STORED ausdrücklich angeben, wenn der Wert gespeichert werden soll.

Wie validiere ich JSONB-Inhalte in der DB?

Mit CHECK-Constraints wie doc ? 'firma' oder jsonb_typeof(doc->'menge') = 'number'. Komplexe Schemata prüft meist die App.

Was geht kaputt, wenn alle Daten in einer JSONB-Spalte liegen?

Keine FKs, keine Typen, keine Planner-Statistik pro Feld. Jede App schreibt ein eigenes Format. Besser: Kern-Felder als Spalten, nur variable Attribute als JSONB.

Mehr

Gerüst

  • Warum? Einmal parsen beim Schreiben → schneller Feldzugriff und GIN-Suche nach Inhalt. json parst bei jedem Zugriff neu.
  • Wie innen? Binär mit Offsets, Keys sortiert, letzter doppelter Key gewinnt. GIN: Posting List pro Key/Wert oder Hash(Pfad, Wert), danach Recheck.
  • Zahlen TOAST ab ca. 2 kB Zeile, max. 1 GB. Planner rät 0,5 % bei =, ein Drittel bei <. jsonb_path_ops hier 25 % kleiner.
  • Vergleich jsonb_ops: auch ?, ?|, ?&. jsonb_path_ops: nur @>, @?, @@. GIN für „enthält“, Ausdrucks-B-Tree für = und Sortierung.
  • Produktion doc->>'x' = 'y' ignoriert GIN → Seq Scan. Zähler im 50-kB-Dokument → jedes Update schreibt 50 kB neu.
  • Design Hybrid: Kern-Felder als Spalten, Rest JSONB. Statistik per CREATE STATISTICS, Format per CHECK.

-- 1) json vs jsonb

-- 2) Containment und Existenz
SELECT '{"art":"trade","tags":["eu","strom"]}'::jsonb @> '{"tags":["strom"]}' AS enthaelt,

       '{"kopf":{"art":"trade"}}'::jsonb ? 'art'                     AS existenz_oben;
-- 3) || ist flach
SELECT '{"kopf":{"x":1}}'::jsonb || '{"kopf":{"y":2}}' AS flach;
-- 4) 200 000 Events, zwei GIN-Varianten
CREATE TABLE event (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, doc jsonb NOT NULL);
INSERT INTO event (doc) SELECT jsonb_build_object(
  'art', (ARRAY['order','trade','info'])[1 + g % 3], 'firma', 'F' || (g % 2000),
  'menge', g % 500, 'tags', jsonb_build_array('eu', CASE WHEN g % 100 = 0 THEN 'storno' ELSE 'ok' END))
FROM generate_series(1, 200000) g;
CREATE INDEX event_gin      ON event USING gin (doc);
CREATE INDEX event_gin_path ON event USING gin (doc jsonb_path_ops);
-- 5) Pläne
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
  SELECT count(*) FROM event WHERE doc @> '{"firma":"F42"}';
EXPLAIN (...) SELECT count(*) FROM event WHERE doc->>'firma' = 'F42';
CREATE INDEX event_firma ON event ((doc->>'firma')); ANALYZE event;
EXPLAIN (...) SELECT count(*) FROM event WHERE doc->>'firma' = 'F42';
-- 6) Schätzung ohne und mit Statistik (Index event_firma vorher gelöscht)
EXPLAIN SELECT * FROM event WHERE (doc->>'menge')::int < 10;
SELECT count(*) FROM event WHERE (doc->>'menge')::int < 10;
CREATE STATISTICS event_menge ON ((doc->>'menge')::int) FROM event; ANALYZE event;
EXPLAIN SELECT * FROM event WHERE (doc->>'menge')::int < 10;
-- 7) JSON_TABLE (seit 17)
SELECT jt.* FROM event, JSON_TABLE(doc, '$' COLUMNS (
    art text PATH '$.art', menge int PATH '$.menge',
    NESTED PATH '$.tags[*]' COLUMNS (tag text PATH '$'))) AS jt
WHERE event.id = 300;
-- 8) Subscripting-Update (seit 14)
UPDATE event SET doc['status'] = '"geprueft"' WHERE id = 300 RETURNING doc;

Echte Ausgabe, PostgreSQL 17.12. Gekürzt: Kopfzeilen „QUERY PLAN“, „(n rows)“ und CREATE-Meldungen. Teil 6b lief in einem zweiten Durchlauf mit denselben Daten.

  1. json vs jsonb: json speichert den Text exakt, mit doppeltem Key. jsonb sortiert die Keys und behält nur den letzten Wert "a": 3.
  2. Containment: @> prüft die Struktur von der Wurzel aus. {"art":"trade"} steckt nur verschachtelt drin, darum f. Auch ? prüft nur die oberste Ebene.
  3. || ist flach: Der ganze Wert von kopf wird ersetzt, nicht zusammengeführt. x ist weg.
  4. Indexgrössen: jsonb_path_ops ist hier 25 % kleiner, weil es nur einen Hash pro Pfad und Wert speichert, keine einzelnen Keys.
  5. GIN genutzt: Der Planner wählt den kleineren event_gin_path. 100 Treffer, 100 Heap-Seiten.
  6. GIN nicht genutzt: ->> … = ist kein GIN-Operator. Ergebnis: Parallel Seq Scan über 200 000 Zeilen.
  7. Ausdrucksindex: Ein B-Tree auf (doc->>'firma') passt genau zu diesem Ausdruck. Wieder 100 Treffer per Index.
  8. Schätzung: Ohne Statistik rät der Planner bei < ein Drittel: 66 667 Zeilen. Wahr sind 4 000. Mit CREATE STATISTICS auf dem Ausdruck schätzt er 4 050.
  9. JSON_TABLE: Es macht aus einem Dokument Zeilen. NESTED PATH erzeugt eine Zeile pro Tag.
  10. Subscripting: doc['status'] = '"geprueft"' setzt einen Key. Der Wert muss selbst jsonb sein, darum die inneren Anführungszeichen.

Vergleich

  • jsonb vs json: json behält Text, Reihenfolge und doppelte Keys, ist aber bei jedem Zugriff neu zu parsen und nicht per GIN indizierbar. Fast immer jsonb.
  • jsonb vs Spalten: Spalten haben Typen, Constraints, FKs und Statistiken. JSONB passt für variable Attribute. Entscheidung: Seite Normalisierung.
  • jsonb_ops vs jsonb_path_ops: jsonb_ops für Key-Existenz und gemischte Abfragen. jsonb_path_ops für reine @>-Suchen, kleiner und schneller.
  • GIN vs Ausdrucks-B-Tree: GIN für viele verschiedene Felder in „enthält“-Form. B-Tree für ein festes Feld mit =, Bereich und Sortierung.
  • JSONB vs hstore: hstore ist flach, nur Text-Werte. JSONB ist verschachtelt mit Typen.
  • PostgreSQL JSONB vs MongoDB: JSONB gibt Dokumente mit Transaktionen und Joins. MongoDB bietet natives Sharding und Dokument-Updates an Ort. Für ein Team mit PostgreSQL reicht JSONB meist.

In der Produktion

  1. Abfrage ignoriert den GIN: Sie nutzt ->> = statt @>. Lösung: Abfrage als Containment schreiben oder einen Ausdrucksindex für dieses Feld anlegen.
  2. Schlechter Plan durch falsche Schätzung: Der Planner rät bei Feldern 0,5 % für Gleichheit oder ein Drittel für Bereiche. Joins und Nested Loops kippen. Lösung: CREATE STATISTICS auf den Ausdruck oder eine Generated Column.
  3. WAL und Bloat durch kleine Updates: Ein Zähler in einem 50-kB-Dokument wird oft erhöht. Jede Änderung schreibt 50 kB neu. Lösung: veränderliche Felder als eigene Spalte.
  4. Langsame Lesezugriffe auf grosse Dokumente: Jeder ->>-Zugriff entpackt den ganzen TOAST-Wert. Lösung: oft gelesene Felder herausziehen, Dokumente klein halten, lz4 prüfen.
  5. Inserts langsam nach GIN-Index: Ein Dokument erzeugt viele Index-Einträge. Lösung: jsonb_path_ops oder GIN nur auf ein Unterobjekt. Pending-List-Tuning: Seite Index-Typen.
  6. Ungültige Daten: Jede App schreibt ein anderes Format. Lösung: CHECK (doc ? 'firma'), CHECK (jsonb_typeof(doc->'menge') = 'number') oder Validierung per JSON Schema in der App.
  7. Lock-Konflikte: Zwei Requests ändern verschiedene Felder desselben Dokuments. Beide sperren die ganze Zeile. Lösung: Dokument teilen oder Updates bündeln.

Diagnose: Werkzeuge und Abfragen

  • EXPLAIN (ANALYZE, BUFFERS): Wird der GIN genutzt? Stimmt rows geschätzt vs tatsächlich? (Seite Planner und EXPLAIN)
  • pg_column_size(doc): Grösse eines Werts nach Kompression. avg(pg_column_size(doc)) über eine Stichprobe zeigt die Dokumentgrösse.
  • pg_relation_size('event') gegen pg_total_relation_size('event'): Der Unterschied ist TOAST plus Indizes.
  • pg_stat_user_indexes.idx_scan: Wird der GIN überhaupt genutzt? Ungenutzte GIN-Indizes kosten nur Schreibzeit.
  • pg_stats_ext_exprs: zeigt die Statistiken aus CREATE STATISTICS auf Ausdrücken.
  • jsonb_typeof(), jsonb_object_keys(), jsonb_each(): finden, welche Keys und Typen wirklich in den Daten stehen.
  • jsonb_pretty(doc): macht ein Dokument in psql lesbar.

Senior-Punkte

  1. Hybrid-Modell: Kern-Felder als Spalten mit Constraints, variable Rest-Attribute als JSONB. Das gibt Flexibilität ohne Planner-Blindflug.
  2. Index nach Abfrage, nicht nach Spalte. Erst die echten Filter sammeln, dann GIN, Ausdrucksindex oder Generated Column wählen.
  3. Dokumente klein halten. Unter 2 kB bleibt alles inline, und Updates bleiben billig.
  4. Schema gehört trotzdem irgendwohin. Ohne CHECK oder App-Validierung entstehen viele Formate in einer Spalte.
  5. Statistiken nachrüsten: Bei JSONB-Filtern in Joins ist CREATE STATISTICS oft die billigste Plan-Reparatur.
  6. JSONB ist kein Dokumentenstore-Ersatz für sehr grosse, oft partiell geänderte Dokumente. Dort zahlt MVCC jede Änderung voll.
