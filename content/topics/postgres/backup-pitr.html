Backup und Point-in-Time Recovery

PostgreSQL 19 (aktuell seit 19.11.2026; Beispiele auf 17.12 ausgeführt) · Quellen: PostgreSQL 19 Doku, Kapitel 25 „Backup and Restore“ (SQL Dump, File System Level Backup, Continuous Archiving and PITR inkl. Incremental Backup, Timelines, Caveats), Kapitel 19.5 „Write Ahead Log“ (Archiving, Recovery Target, summarize_wal), Programme pg_dump, pg_dumpall, pg_restore, pg_basebackup, pg_combinebackup, pg_verifybackup; Release Notes 17 (inkrementelle Backups), 18 (pg_dump --statistics/--no-data, Checksums standardmässig an, pg_verifybackup für tar), 19 (standard_conforming_strings immer an, pg_dump mit erweiterten Statistiken)

Kern: Ein Backup ist eine Kopie der Datenbank, aus der man nach Fehlern, Löschungen oder Ausfällen wiederherstellen kann. Point-in-Time Recovery (PITR) kombiniert ein physisches Basis-Backup mit dem archivierten WAL. So lässt sich die Datenbank auf jeden Zeitpunkt zurücksetzen, z. B. eine Sekunde vor einem falschen DELETE.

1. Wo sitzt das Backup?

  1. Logisches Backup: pg_dump schreibt den Inhalt einer Datenbank als SQL oder Archiv-Datei. Es liest unter einem Snapshot, ist also konsistent, ohne Schreiber zu blockieren.
  2. pg_dumpall: Es sichert alle Datenbanken plus globale Objekte: Rollen und Tablespaces. pg_dump allein sichert keine Rollen.
  3. Physisches Basis-Backup: pg_basebackup kopiert die Datendateien des ganzen Clusters über das Replikationsprotokoll, im laufenden Betrieb.
  4. WAL-Archiv: archive_command oder archive_library kopiert jedes fertige WAL-Segment weg. Die Kette darf keine Lücke haben.
  5. Konfiguration: postgresql.conf, pg_hba.conf und pg_ident.conf stehen nicht im WAL. Sie brauchen eine eigene Sicherung.
  6. Speicherort: Backups gehören auf ein anderes System, ideal unveränderbar. Ein Backup auf derselben Platte ist keins.

2. Die Reise einer Wiederherstellung auf 14:31:59 (die Geschichte zum Merken)

  1. Unfall: Um 14:32 löscht ein Skript alle Konten. Die Replikas haben den Fehler sofort übernommen (Seite Replikation).
  2. Basis-Backup: Das letzte Basis-Backup von 02:00 wird in ein leeres Datenverzeichnis auf einem anderen Server kopiert. Das alte bleibt als Beweis und Rückfall.
  3. Konfigurieren: restore_command = 'cp /archiv/%f %p' holt WAL aus dem Archiv. recovery_target_time = '2026-11-24 14:31:59+01' setzt den Stopp.
  4. Starten: Eine leere Datei recovery.signal im Datenverzeichnis sagt: Archiv-Recovery. Dann startet der Server.
  5. WAL einspielen: PostgreSQL spielt jedes Segment von 02:00 an ein. Beim ersten Commit nach 14:31:59 hält es an.
  6. Prüfen und öffnen: Standard ist recovery_target_action = pause. Man prüft die Daten lesend. pg_wal_replay_resume() beendet die Recovery; es entsteht Timeline 2. Dann Daten zurückkopieren oder auf diesen Server umschalten.

3. Beispiel: pg_dump/pg_restore, Basis-Backup, Verify, Inkrementell, Restore Point

# im Container pg17, als Benutzer postgres
psql -c "CREATE SCHEMA demo_backup_pitr;
         CREATE TABLE demo_backup_pitr.konto (id int PRIMARY KEY, saldo numeric NOT NULL);
         INSERT INTO demo_backup_pitr.konto SELECT g, 100 FROM generate_series(1, 10000) g;"
# 1) Logisches Backup im custom format, Inhalt auflisten
pg_dump -Fc -n demo_backup_pitr -f /tmp/demo_backup_pitr.dump postgres
pg_restore -l /tmp/demo_backup_pitr.dump | grep -v '^;'
# 2) Unfall, dann Restore in eine NEUE Datenbank (2 parallele Jobs)
psql -c "DELETE FROM demo_backup_pitr.konto WHERE id > 10"
createdb demo_backup_pitr_restore
pg_restore -d demo_backup_pitr_restore -j 2 /tmp/demo_backup_pitr.dump
psql -d demo_backup_pitr_restore -c "SELECT count(*) AS zeilen_im_restore FROM demo_backup_pitr.konto"
# 3) Physisches Basis-Backup mit WAL-Stream, dann prüfen
pg_basebackup -D /tmp/demo_base -Fp -Xs -c fast
du -sh /tmp/demo_base; ls /tmp/demo_base
pg_verifybackup /tmp/demo_base
# 4) Inkrementelles Backup (summarize_wal = off)

Echte Ausgabe, PostgreSQL 17.12 (Programme im Container pg17). Lange Zeilen umbrochen. Eine echte PITR braucht archive_mode = on und einen Neustart; das lief hier nicht.

  1. Custom Format: -Fc erzeugt ein komprimiertes Archiv. pg_restore -l zeigt das Inhaltsverzeichnis: Schema, Tabelle, Daten, Constraint. Man kann einzelne Einträge auswählen.
  2. Restore in neue DB: Die Produktion bleibt unberührt. Alle 10 000 Zeilen sind im Restore. Von dort kopiert man gezielt zurück.
  3. Basis-Backup: 49 MB für den ganzen Cluster, mit allen Datenbanken. -Xs streamt das WAL während des Backups mit, darum ist es allein startfähig.
  4. Manifest und Verify: backup_manifest listet jede Datei mit Prüfsumme. pg_verifybackup prüft sie und das nötige WAL.
  5. Inkrementell: Es scheitert, weil summarize_wal aus ist. Mit summarize_wal = on kopiert --incremental nur geänderte Blöcke seit dem Manifest.
  6. Restore Point: pg_create_restore_point('vor_migration') setzt eine Marke im WAL. Später reicht recovery_target_name = 'vor_migration'. Der WAL-Dateiname enthält die Timeline (00000001).

4. Details, die Interviewer fragen

  1. pg_dump-Formate: -Fp Klartext-SQL für psql. -Fc custom, komprimiert, selektiver Restore. -Fd directory, eine Datei pro Tabelle, einziges Format für paralleles pg_dump -j. -Ft tar.
  2. Konsistenz: pg_dump nutzt eine Transaktion mit einem Snapshot. Er blockiert Schreiber nicht, hält aber lange einen Snapshot und blockiert so VACUUM-Aufräumen (Seite VACUUM).
  3. Locks von pg_dump: Er nimmt ACCESS SHARE auf jede Tabelle. Ein ALTER TABLE wartet dann, und hinter ihm stauen sich alle anderen (Seite Locking).
  4. Dump zwischen Versionen: Man nutzt das pg_dump der neuen Version. Seit 19 ist standard_conforming_strings immer an; alte Dumps mit off laden nicht mehr.
  5. Statistiken im Dump: Seit 18 kann pg_dump --statistics Planner-Statistiken mitnehmen; seit 19 auch erweiterte Statistiken. Sonst nach dem Restore immer ANALYZE.
  6. Basis-Backup: pg_basebackup nutzt eine Replikationsverbindung. -Xs streamt WAL parallel, -Ft -z schreibt komprimiertes tar. Manuell geht es mit pg_backup_start() und pg_backup_stop().
  7. archive_command-Regeln: Exit-Code 0 nur bei echtem Erfolg. Bestehende Dateien nicht überschreiben. Bei Fehlern versucht PostgreSQL es erneut, und pg_wal wächst bis zur vollen Platte.
  8. Recovery-Ziele: recovery_target_time, recovery_target_name, recovery_target_lsn, recovery_target_xid oder recovery_target = 'immediate' (nur bis konsistent). Das Ziel muss nach dem Ende des Basis-Backups liegen.
  9. recovery_target_inclusive: Standard true: Die Ziel-Transaktion ist noch dabei. false hält direkt davor an.
  10. Timeline: Nach jeder PITR beginnt eine neue Timeline mit einer History-Datei im Archiv. So kann man mehrmals zu verschiedenen Zeitpunkten zurück, ohne alte WAL-Dateien zu überschreiben.
  11. Inkrementelle Backups (seit 17): summarize_wal = on schreibt WAL-Zusammenfassungen. pg_basebackup --incremental=<manifest> kopiert nur geänderte Blöcke. pg_combinebackup baut daraus ein volles Backup für den Restore.
  12. Kette verwalten: PostgreSQL merkt sich nicht, welche Backups ein inkrementelles braucht. Das muss das Backup-Werkzeug oder der Betrieb tun.
  13. Data Checksums: Seit 18 schaltet initdb sie standardmässig ein. Sie erkennen kaputte Seiten beim Lesen, und Werkzeuge prüfen sie beim Backup.
  14. Snapshot des Dateisystems: Ein konsistenter Snapshot (z. B. Cloud-Disk-Snapshot) aller Volumes gleichzeitig ist auch ein gültiges Backup. Er ist dann wie ein Crash-Zustand und braucht beim Start WAL-Recovery.

5. Vergleich

  • Logisch (pg_dump): Eine Datenbank oder Tabelle, versionsübergreifend, lesbar. Kein PITR, Restore bei grossen Daten langsam, weil Indizes neu gebaut werden.
  • Physisch (pg_basebackup + WAL): Ganzer Cluster, gleiche Hauptversion, schneller Restore, PITR möglich. Keine einzelnen Tabellen zurückholen.
  • pgBackRest: Voll, differentiell, inkrementell, parallel, Verschlüsselung, S3/Azure Blob, Prüfung und Retention. Für Produktion meist die erste Wahl.
  • Barman: Zentraler Backup-Server für viele PostgreSQL-Instanzen, mit WAL-Streaming.
  • WAL-G: Schlank, auf Object Storage ausgelegt, beliebt in Kubernetes.
  • Managed Service: Azure Database for PostgreSQL oder AWS RDS machen Basis-Backups und WAL-Archiv automatisch, PITR per Klick innerhalb der Aufbewahrungszeit. Restore erzeugt einen neuen Server.
  • Backup vs Replikation: Replikation schützt vor Hardware-Ausfall. Nur Backups schützen vor Fehlern, Löschungen und Ransomware.

6. In der Produktion

  1. Backup da, Restore scheitert: Nie getestet, WAL-Lücke oder falsches Passwort zum Schlüssel. Lösung: automatischer Restore-Test, z. B. wöchentlich, mit Zeitmessung.
  2. pg_wal läuft voll: archive_command scheitert, z. B. Storage-Credentials abgelaufen. Lösung: pg_stat_archiver.failed_count und last_failed_time alarmieren.
  3. pg_dump dauert Stunden und erzeugt Bloat: Der lange Snapshot hält VACUUM auf. Lösung: physisches Backup oder Dump vom Standby.
  4. Restore eines Dumps braucht einen Tag: Indizes und Constraints werden neu gebaut. Lösung: -Fd und pg_restore -j, oder für grosse Datenbanken physische Backups.
  5. Rollen fehlen nach Restore: Nur pg_dump wurde gesichert. Lösung: pg_dumpall --globals-only zusätzlich.
  6. Ransomware löscht auch die Backups: Backups waren vom selben Account schreibbar. Lösung: unveränderbarer Storage, eigener Account, Kopie in anderer Region.
  7. RTO verfehlt: Das letzte Voll-Backup ist eine Woche alt, das Einspielen von WAL dauert Stunden. Lösung: häufigere Basis-Backups oder inkrementelle Backups.

7. Diagnose: Werkzeuge und Abfragen

  • Archivierung: SELECT archived_count, last_archived_wal, failed_count, last_failed_wal, last_failed_time FROM pg_stat_archiver;
  • Backup-Fortschritt: pg_stat_progress_basebackup; seit 19 mit Spalte backup_type (full oder incremental).
  • Backup prüfen: pg_verifybackup <dir> prüft Manifest, Prüfsummen und WAL. Seit 18 auch für tar-Backups.
  • WAL-Summaries: pg_available_wal_summaries(), pg_get_wal_summarizer_state().
  • Recovery beobachten: pg_is_in_recovery(), pg_last_wal_replay_lsn(), pg_is_wal_replay_paused(), Server-Log mit „recovery stopping before …“.
  • WAL-Datei zur LSN: pg_walfile_name(lsn); Inhalt mit pg_waldump, z. B. um den Zeitpunkt eines falschen DELETE zu finden.
  • pgBackRest: pgbackrest info zeigt Backups, WAL-Bereich und Grösse; pgbackrest check testet die Archivierung.

8. Senior-Punkte

  1. Ein Backup existiert erst, wenn der Restore getestet ist. Ich automatisiere den Test und messe die Dauer gegen das RTO.
  2. RPO bestimmt die Methode: Täglicher Dump heisst bis zu 24 Stunden Verlust. PITR mit WAL-Archiv heisst Sekunden bis Minuten.
  3. 3-2-1-Regel: drei Kopien, zwei Medien, eine ausser Haus. Dazu unveränderbar gegen Ransomware.
  4. Physisch für Katastrophen, logisch für Einzelfälle. Ein Dump hilft, eine einzelne Tabelle zurückzuholen oder Daten zu migrieren.
  5. Fertige Werkzeuge statt eigener Skripte. pgBackRest oder der Managed Service lösen Retention, Verschlüsselung und Prüfung.
  6. PITR auf einen Neben-Server, nicht auf die Produktion. Dann Daten gezielt zurückkopieren und den Rest des Tages behalten.
  7. Restore Points vor riskanten Änderungen setzen, z. B. vor Migrationen. Das macht das Recovery-Ziel eindeutig.

10. Fallen

  • „pg_dump sichert alles.“ → Falsch. Keine Rollen und Tablespaces. Dafür pg_dumpall --globals-only.
  • „Mit pg_dump kann ich auf 14:31 zurück.“ → Falsch. Nur auf den Zeitpunkt des Dumps. PITR braucht Basis-Backup plus WAL-Archiv.
  • „Ein Basis-Backup reicht für PITR.“ → Falsch. Es braucht das lückenlose WAL ab dem Backup bis zum Ziel.
  • „Kopieren des Datenverzeichnisses im Betrieb ist ein Backup.“ → Falsch. Nur mit pg_backup_start/stop, pg_basebackup oder einem atomaren Snapshot aller Volumes.
  • „Inkrementelle Backups gehen einfach so.“ → Falsch. Erst ab 17 und nur mit summarize_wal = on, plus pg_combinebackup beim Restore.
  • „Ein physisches Backup kann ich in eine neuere Hauptversion einspielen.“ → Falsch. Nur gleiche Hauptversion. Für Upgrades: pg_upgrade, Dump oder logische Replikation.
  • „archive_command darf Fehler ignorieren.“ → Falsch. Exit 0 heisst für PostgreSQL „gesichert“, und es löscht die Datei.

11. Fragen

Welche Backup-Arten gibt es in PostgreSQL?

Logisch mit pg_dump/pg_dumpall, physisch mit pg_basebackup oder Dateisystem-Snapshot, und kontinuierliche WAL-Archivierung für PITR.

Was ist PITR?

Wiederherstellung auf einen beliebigen Zeitpunkt: Basis-Backup einspielen, dann archiviertes WAL bis zum Ziel abspielen.

Was braucht man für PITR?

wal_level replica oder höher, archive_mode on, eine funktionierende Archivierung, ein Basis-Backup und das lückenlose WAL danach.

Wie startet man eine PITR?

Basis-Backup in leeres PGDATA, restore_command und Recovery-Ziel setzen, recovery.signal anlegen, Server starten.

Welche Recovery-Ziele gibt es?

Zeit, Name eines Restore Points, LSN, Transaktions-ID oder immediate.

Was passiert am Recovery-Ziel?

Standardmässig pausiert der Server. Man prüft und beendet mit pg_wal_replay_resume(). Dann entsteht eine neue Timeline.

Was ist eine Timeline?

Ein Zweig der WAL-Geschichte. Jede beendete Archiv-Recovery startet eine neue, mit History-Datei im Archiv.

Was muss ein archive_command erfüllen?

Exit 0 nur bei echtem Erfolg, nie bestehende Dateien überschreiben, und die Datei dauerhaft speichern.

Was passiert, wenn die Archivierung scheitert?

PostgreSQL versucht es weiter, pg_wal wächst. Ist die Platte voll, stoppt der Server mit PANIC.

Welche pg_dump-Formate gibt es?

plain, custom, directory und tar. Custom und directory erlauben selektiven und parallelen Restore.

Wie mache ich pg_dump parallel?

Mit -Fd und -j n. Der Restore mit pg_restore -j geht für custom und directory.

Blockiert pg_dump die Datenbank?

Nicht für normale Lese- und Schreibzugriffe. Er hält aber ACCESS SHARE auf allen Tabellen und einen langen Snapshot.

Was sichert pg_dumpall zusätzlich?

Globale Objekte wie Rollen und Tablespaces, und alle Datenbanken.

Was macht pg_basebackup -Xs?

Es streamt das WAL während des Backups mit. Das Backup ist damit allein startfähig.

Was ist das backup_manifest?

Eine Liste aller Dateien mit Prüfsummen. pg_verifybackup prüft das Backup dagegen, und inkrementelle Backups bauen darauf auf.

Wie funktionieren inkrementelle Backups?

Seit 17: summarize_wal erfasst geänderte Blöcke. pg_basebackup --incremental kopiert nur diese, pg_combinebackup baut ein volles Backup daraus.

Was ist ein Restore Point?

Eine benannte Marke im WAL, gesetzt mit pg_create_restore_point(). Ziel für recovery_target_name.

Logisches oder physisches Backup?

Physisch für den ganzen Cluster, schnellen Restore und PITR. Logisch für einzelne Tabellen, Migrationen und Versionswechsel.

Was sind RPO und RTO beim Backup?

RPO: wie viel Datenverlust erlaubt ist, bestimmt durch Archiv-Frequenz. RTO: wie lange der Restore dauern darf, bestimmt durch Backup-Grösse und WAL-Menge.

Welche Werkzeuge nutzt man in Produktion?

pgBackRest, Barman oder WAL-G, oder die Backups des Managed Service.

Wie prüfe ich, ob die Archivierung läuft?

pg_stat_archiver: last_archived_wal, failed_count und last_failed_time.

Warum nach einem Restore ANALYZE?

Ein Dump enthält standardmässig keine Planner-Statistiken. Ohne ANALYZE plant der Planner blind. Seit 18 kann pg_dump Statistiken mitnehmen.

Szenario: Jemand hat um 14:32 eine Tabelle gelöscht. Wie holen Sie sie zurück?

PITR auf einen Neben-Server bis 14:31:59 oder bis vor die Transaktion, dort prüfen, dann die Tabelle mit pg_dump/pg_restore in die Produktion kopieren.

Szenario: pg_wal wächst und die Platte ist zu 90 % voll. Was prüfen Sie zuerst?

pg_stat_archiver auf Fehler, dann pg_replication_slots auf alte Slots. Ursache beheben, nie WAL-Dateien von Hand löschen.

Szenario: Die Datenbank hat 3 TB, der nächtliche pg_dump passt nicht mehr ins Zeitfenster. Was schlagen Sie vor?

Physische Backups mit pgBackRest: wöchentlich voll, täglich inkrementell oder differentiell, dazu WAL-Archiv für PITR. pg_dump nur noch für einzelne Schemas.
