Performance-Tuning: Konfiguration und Abfragen

PostgreSQL · Quellen: PostgreSQL 17 Doku (19.4 Resource Consumption, 19.5 WAL/Checkpoints, 19.7 Query Planning, 19.8 Logging, 28.5 WAL Configuration, F.32 pg_stat_statements, F.4 auto_explain, 11.8 Partial Indexes, 14.4 Populating a Database, 27.2 pg_stat_checkpointer), pgJDBC Doku (reWriteBatchedInserts), Hibernate ORM 6 User Guide (Fetching, Batching)

Kern: Performance-Tuning in PostgreSQL ist ein Kreislauf: messen, die teuerste Abfrage finden, gezielt verbessern, wieder messen. Die meisten Gewinne kommen aus Abfragen und Indizes, nicht aus Konfiguration. Die Konfiguration setzt nur den Rahmen: Speicher (shared_buffers, work_mem) und Schreiblast (Checkpoints).

1. Wo sitzen die Stellschrauben?

  1. App / ORM: bestimmt, wie viele Abfragen kommen. N+1 und fehlendes Batching kosten hier am meisten.
  2. Planner: wählt den Ausführungsplan. Beispiel: effective_cache_size sagt ihm, wie viel Cache es insgesamt gibt.
  3. Backend: ein Prozess pro Verbindung. work_mem gilt pro Sortier- oder Hash-Operation darin.
  4. shared_buffers: der eigene Cache von PostgreSQL für Tabellen- und Indexseiten. Alle Backends teilen ihn.
  5. WAL und Checkpointer: Jede Änderung geht zuerst ins WAL (Write-Ahead Log). Der Checkpointer schreibt geänderte Seiten periodisch auf Disk.
  6. Wartung: VACUUM, CREATE INDEX und FK-Prüfungen nutzen maintenance_work_mem.
  7. OS-Page-Cache: PostgreSQL liest über den Cache des Betriebssystems. Daten liegen oft doppelt: in shared_buffers und im OS-Cache.

2. Die Reise einer Tuning-Runde

  1. Symptom: Das Monitoring zeigt steigende Latenz oder hohe DB-CPU. Noch keine Vermutung, nur Fakten.
  2. Top-Abfragen finden: pg_stat_statements sortiert nach total_exec_time. Die Abfrage mit der grössten Gesamtzeit zählt, nicht die langsamste Einzelabfrage.
  3. Plan lesen: EXPLAIN (ANALYZE, BUFFERS) mit echten Parametern. Man sucht Seq Scans auf grossen Tabellen, falsche Zeilenschätzungen und Sorts auf Disk.
  4. Ursache benennen: fehlender Index, N+1 aus dem ORM, zu kleiner work_mem, alte Statistiken.
  5. Eine Änderung: genau eine. Sonst weiss man nicht, was geholfen hat.
  6. Neu messen: pg_stat_statements_reset(), Last abwarten, Werte vergleichen. Dann die nächste Abfrage.

3. Beispiel: von pg_stat_statements zum Partial Index

-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'  (Neustart)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT left(query, 60) AS query, calls,
       round(total_exec_time) AS total_ms,
       round(mean_exec_time, 2) AS mean_ms,
       shared_blks_read
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 3;
                            query                             |  calls  | total_ms | mean_ms | shared_blks_read
--------------------------------------------------------------+---------+----------+---------+------------------
 SELECT * FROM orders WHERE status = $1 ORDER BY created_at L |   48210 |   612400 |   12.70 |          9120334
 SELECT * FROM order_item WHERE order_id = $1                 | 2410500 |   180770 |    0.07 |            21004
 UPDATE orders SET status = $1 WHERE id = $2                  |   51022 |    20410 |    0.40 |             3310
-- nur 0,5 % der Bestellungen sind 'OPEN', aber genau diese werden ständig gesucht
CREATE INDEX CONCURRENTLY orders_open_created_idx
  ON orders (created_at) WHERE status = 'OPEN';
ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'OPEN' ORDER BY created_at LIMIT 50;
 Limit  (actual time=0.031..0.145 rows=50 loops=1)
   Buffers: shared hit=53
   ->  Index Scan using orders_open_created_idx on orders  (actual rows=50 loops=1)
 Planning Time: 0.210 ms
 Execution Time: 0.170 ms

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Zahlen sind ein typisches Beispiel, Plan gekürzt.

  1. Zeile 1 kostet die meiste Gesamtzeit. Hohe shared_blks_read heisst: Sie liest viele Seiten von Disk oder OS-Cache. Das deutet auf einen Seq Scan.
  2. Zeile 2 ist einzeln schnell (0,07 ms), läuft aber 2,4 Mio. Mal. Das ist das Muster von N+1: eine Abfrage pro Bestellung.
  3. Der Partial Index enthält nur Zeilen mit status = 'OPEN'. Er ist winzig und liefert die Zeilen schon sortiert.
  4. Der Planer nutzt ihn nur, wenn die Abfrage die Bedingung beweisbar enthält. Mit Parameter status = $1 beim Generic Plan klappt das nicht.
  5. CONCURRENTLY baut den Index ohne Schreibsperre. Er dauert länger und läuft nicht in einer Transaktion.

4. Details, die Interviewer fragen

  1. shared_buffers (Standard 128 MB): der Cache von PostgreSQL. Die Doku nennt für einen dedizierten Server mit ≥ 1 GB RAM 25 % als Startwert. Mehr als 40 % hilft selten, weil der OS-Cache auch arbeitet. Änderung braucht einen Neustart.
  2. effective_cache_size (Standard 4 GB): reserviert keinen Speicher. Es sagt dem Planer, wie viel Cache (shared_buffers plus OS) etwa verfügbar ist. Hoch heisst: Index Scans werden attraktiver. Üblich: 50–75 % des RAM.
  3. work_mem (Standard 4 MB): Speicher pro Sortier- oder Hash-Operation, bevor auf Disk ausgelagert wird. Eine Abfrage kann mehrere solche Knoten haben, plus parallele Worker. Hash-Operationen dürfen work_mem × hash_mem_multiplier (Standard 2.0) nutzen.
  4. work_mem gezielt: lieber pro Session oder Rolle erhöhen: SET work_mem = '256MB' für einen Report, oder ALTER ROLE reporting SET work_mem = .... Global hoch ist bei vielen Verbindungen gefährlich.
  5. maintenance_work_mem (Standard 64 MB): Speicher für VACUUM, CREATE INDEX und ALTER TABLE ADD FOREIGN KEY. Höher macht Index-Builds schneller. Autovacuum nutzt autovacuum_work_mem pro Worker, sonst diesen Wert.
  6. PostgreSQL 17 und VACUUM: Seit 17 speichert VACUUM tote Tupel in einer neuen, kompakten Struktur. Das alte Limit von 1 GB Speicher dafür fällt weg. Grosse Tabellen brauchen weniger Index-Durchläufe.
  7. Checkpoint: Ein Checkpoint schreibt alle geänderten Seiten (dirty pages) auf Disk. Danach kann altes WAL weg. Ausgelöst durch checkpoint_timeout (Standard 5 min) oder durch WAL-Menge über max_wal_size (Standard 1 GB).
  8. Checkpoint-Spitzen: Zu häufige Checkpoints erzeugen I/O-Spitzen und viele Full Page Writes (die erste Änderung einer Seite nach einem Checkpoint schreibt die ganze Seite ins WAL). checkpoint_completion_target = 0.9 verteilt das Schreiben über 90 % des Intervalls.
  9. Checkpoint-Warnung: Das Log meldet checkpoints are occurring too frequently. Lösung: max_wal_size erhöhen. In PostgreSQL 17 zeigt pg_stat_checkpointer (num_timed vs. num_requested) das an. Früher stand es in pg_stat_bgwriter.
  10. random_page_cost (Standard 4.0): Kosten eines zufälligen Seitenzugriffs relativ zu sequenziell (1.0). Auf SSD oft 1.1. Sonst unterschätzt der Planer Index Scans.
  11. pg_stat_statements: Eine Extension, die normalisierte Abfragen mit Aufrufen, Zeiten, Zeilen und Block-I/O sammelt. Braucht shared_preload_libraries. Mit track_io_timing = on sieht man auch I/O-Zeit.
  12. Slow Query Log: log_min_duration_statement = '500ms' loggt jede Abfrage ab 500 ms mit Dauer. auto_explain loggt zusätzlich den Plan (auto_explain.log_min_duration). log_analyze dort kostet Overhead auf jeder Abfrage.
  13. N+1: Das ORM lädt eine Liste (1 Abfrage) und dann pro Element eine Beziehung (N Abfragen). Ursache: Lazy Loading in einer Schleife. Lösungen: JOIN FETCH, @EntityGraph, oder hibernate.default_batch_fetch_size (lädt per IN (...)).
  14. Batching beim Schreiben: hibernate.jdbc.batch_size = 50 plus order_inserts = true. Mit GenerationType.IDENTITY schaltet Hibernate Insert-Batching ab. Lösung: SEQUENCE mit allocationSize.
  15. reWriteBatchedInserts=true: pgJDBC schreibt einen Batch aus Einzel-Inserts in mehrzeilige INSERT ... VALUES (...), (...) um. Weniger Roundtrips.
  16. COPY: der schnellste Weg für Massenimport. Dazu Indizes und FKs vorher entfernen und danach anlegen, laut Doku „Populating a Database“.
  17. Partial Index: Ein Index nur über Zeilen, die eine WHERE-Bedingung erfüllen. Gut für seltene, oft gesuchte Werte wie status = 'OPEN' oder deleted_at IS NULL. Auch für partial unique: eindeutig nur unter aktiven Zeilen.

5. Vergleich

  • shared_buffers vs. effective_cache_size: das eine reserviert Speicher, das andere ist nur ein Hinweis an den Planer.
  • work_mem vs. maintenance_work_mem: pro Abfrage-Operation vs. pro Wartungsoperation. Der zweite darf viel grösser sein, weil es wenige gleichzeitig gibt.
  • pg_stat_statements vs. Slow Query Log: Summen über alle Aufrufe vs. einzelne langsame Ausführungen. N+1 sieht man nur im ersten.
  • EXPLAIN vs. EXPLAIN ANALYZE: geschätzter Plan vs. wirklich ausgeführt mit echten Zeiten. ANALYZE führt auch UPDATE/DELETE aus, also in eine Transaktion mit ROLLBACK packen.
  • Partial Index vs. voller Index: kleiner, schneller zu pflegen, aber nur für passende Abfragen nutzbar.
  • JOIN FETCH vs. Batch Fetch: eine Abfrage mit Join (Gefahr: kartesisches Produkt bei mehreren Collections) vs. wenige IN-Abfragen.

6. In der Produktion

  1. Out of Memory durch work_mem: Jemand setzt global work_mem = 1GB. 200 Verbindungen mit je mehreren Hash Joins sprengen den RAM. Der OOM-Killer beendet ein Backend, PostgreSQL startet alle Prozesse neu. Lösung: global klein, pro Rolle oder Session gross.
  2. Sort auf Disk: Im Plan steht Sort Method: external merge Disk: 120MB. Lösung: work_mem für diese Abfrage erhöhen oder einen Index, der die Sortierung liefert.
  3. I/O-Spitzen alle paar Minuten: Checkpoints wegen zu kleinem max_wal_size bei hoher Schreiblast. Lösung: max_wal_size erhöhen (z. B. 4–16 GB), Log und pg_stat_checkpointer prüfen.
  4. N+1 nach Release: Eine neue Ansicht greift auf eine Lazy-Collection zu. Abfragen pro Request springen von 3 auf 300. Lösung: Fetch-Plan korrigieren, und in Tests die Anzahl Statements prüfen (z. B. Hibernate Statistics).
  5. Falscher Plan nach Datenwachstum: Statistiken sind alt, der Planer schätzt 10 Zeilen statt 1 Mio. Lösung: ANALYZE, Autovacuum-Analyse-Schwellen pro Tabelle anpassen, bei korrelierten Spalten CREATE STATISTICS.
  6. Langsamer Bulk-Import: Einzel-Inserts mit Autocommit. Lösung: Batching, eine Transaktion pro Batch, oder COPY.
  7. Cloud-Managed: In Azure Flexible Server setzt man Parameter über Server-Parameter, nicht über die Datei. Manche (z. B. shared_buffers) brauchen einen Neustart.

7. Diagnose: Werkzeuge und Abfragen

  • SELECT query, calls, total_exec_time, mean_exec_time, rows, shared_blks_hit, shared_blks_read FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
  • Cache-Hit-Ratio: SELECT sum(blks_hit) * 100.0 / sum(blks_hit + blks_read) FROM pg_stat_database;. Bei OLTP meist über 99 %.
  • EXPLAIN (ANALYZE, BUFFERS, SETTINGS): echter Plan, Seitenzugriffe und geänderte Einstellungen.
  • pg_stat_user_tables: seq_scan vs. idx_scan, n_dead_tup, last_autoanalyze.
  • pg_stat_user_indexes mit idx_scan = 0: ungenutzte Indizes, die nur Writes kosten.
  • SELECT * FROM pg_stat_checkpointer; (PostgreSQL 17): geplante vs. erzwungene Checkpoints.
  • log_checkpoints = on (Standard seit 15), log_temp_files = 0 (loggt jede Temp-Datei, also Sorts auf Disk), log_min_duration_statement, auto_explain.
  • SHOW work_mem;, SELECT name, setting, source FROM pg_settings WHERE source <> 'default';: was wirklich gesetzt ist.
  • Azure: Query Store und Intelligent Performance (Index-Empfehlungen) in Flexible Server.

8. Senior-Punkte

  1. Abfragen vor Konfiguration. Ein Index oder ein behobenes N+1 bringt oft Faktor 100. Ein Parameter selten mehr als Faktor 2.
  2. Gesamtzeit zählt. Eine 0,1-ms-Abfrage, die 10 Mio. Mal läuft, kostet mehr als ein 10-s-Report.
  3. work_mem ist ein Multiplikator: Verbindungen × Operationen × Worker. Darum global konservativ, gezielt grosszügig.
  4. Eine Änderung pro Runde, mit Vorher-Nachher-Zahlen. Sonst wird Tuning Aberglaube.
  5. Jeder Index kostet Writes, WAL und VACUUM-Zeit. Partial Indexes sind oft der beste Kompromiss.
  6. Statement-Anzahl in Tests prüfen. N+1 ist ein Regressionsthema und gehört in die CI, nicht nur ins Monitoring.

9. Aus dem Projekt

„Bei NABODAT habe ich mit Hibernate auf PostgreSQL/PostGIS gearbeitet und Datentabellen auf Lazy Loading umgestellt, damit nur die sichtbare Seite geladen wird.“ (Prüfen und durch dein echtes Beispiel ersetzen. Konkrete Tuning-Zahlen oder pg_stat_statements-Einsatz stehen nicht im Profil.)

10. Fallen

  • „effective_cache_size reserviert Speicher.“ → Falsch. Es ist nur eine Schätzung für den Planer.
  • „work_mem ist der Speicher pro Verbindung.“ → Falsch. Pro Sort- oder Hash-Operation, also oft mehrfach pro Abfrage.
  • „shared_buffers so gross wie möglich.“ → Falsch. PostgreSQL nutzt auch den OS-Cache. Über 40 % des RAM hilft selten.
  • „Die langsamste Abfrage zuerst optimieren.“ → Meist falsch. Die mit der grössten Gesamtzeit zuerst.
  • „Ein Partial Index wird immer genutzt.“ → Falsch. Nur wenn der Planer beweisen kann, dass die Abfrage-Bedingung den Index-Prädikat impliziert.
  • „Hibernate batcht Inserts automatisch.“ → Falsch. Nur mit jdbc.batch_size, und nicht mit IDENTITY-IDs.

11. Fragen

Wie gehen Sie bei einer langsamen PostgreSQL-Datenbank vor?

pg_stat_statements nach Gesamtzeit sortieren, Top-Abfrage mit EXPLAIN (ANALYZE, BUFFERS) prüfen, eine gezielte Änderung, neu messen.

Was ist shared_buffers und wie setzen Sie es?

Der eigene Seiten-Cache von PostgreSQL, Standard 128 MB. Startwert etwa 25 % des RAM auf einem dedizierten Server, Neustart nötig.

Was macht effective_cache_size?

Es sagt dem Planer, wie viel Cache insgesamt verfügbar ist. Es reserviert nichts und beeinflusst, ob Index Scans günstig wirken.

Was ist work_mem und warum ist es gefährlich?

Speicher pro Sort- oder Hash-Operation. Er kann pro Abfrage mehrfach und pro Verbindung anfallen. Global hoch führt zu OOM.

Wie erkennen Sie, dass work_mem zu klein ist?

EXPLAIN ANALYZE zeigt „external merge Disk“ oder Hash Batches > 1. log_temp_files loggt Temp-Dateien.

Wofür ist maintenance_work_mem?

Für VACUUM, CREATE INDEX und ADD FOREIGN KEY. Höher macht diese Operationen schneller, Standard 64 MB.

Was ist ein Checkpoint?

Alle geänderten Seiten werden auf Disk geschrieben, danach kann altes WAL entfernt werden. Ausgelöst durch Zeit oder WAL-Menge.

Was tun bei „checkpoints are occurring too frequently“?

max_wal_size erhöhen, damit Checkpoints zeitgesteuert statt mengengesteuert kommen. checkpoint_completion_target bei 0.9 lassen.

Was ist checkpoint_completion_target?

Der Anteil des Intervalls, über den der Checkpoint seine Writes verteilt. Standard 0.9, das glättet I/O.

Wie richten Sie pg_stat_statements ein?

shared_preload_libraries = 'pg_stat_statements', Neustart, CREATE EXTENSION. Optional track_io_timing = on.

Welche Spalten von pg_stat_statements schauen Sie an?

calls, total_exec_time, mean_exec_time, rows, shared_blks_hit und shared_blks_read. Viele calls mit kleiner mean deuten auf N+1.

Wie richten Sie ein Slow Query Log ein?

log_min_duration_statement auf z. B. 500 ms. Mit auto_explain zusätzlich den Plan langsamer Abfragen loggen.

Was ist das N+1-Problem?

Eine Abfrage lädt N Elemente, dann folgt pro Element eine weitere Abfrage. Ursache meist Lazy Loading in einer Schleife.

Wie lösen Sie N+1 in Hibernate?

JOIN FETCH oder @EntityGraph für den Use Case, oder default_batch_fetch_size für IN-Abfragen. Danach Statement-Anzahl im Test prüfen.

Wie machen Sie Inserts mit Hibernate schnell?

jdbc.batch_size und order_inserts setzen, SEQUENCE statt IDENTITY, pgJDBC reWriteBatchedInserts=true. Für Massenimport COPY.

Warum verhindert IDENTITY das Insert-Batching?

Hibernate braucht die ID sofort nach jedem Insert. Bei IDENTITY liefert erst die DB sie, also muss jeder Insert einzeln laufen.

Was ist ein Partial Index?

Ein Index nur über Zeilen mit einer WHERE-Bedingung. Klein und schnell für seltene, oft gesuchte Werte.

Wann nutzt der Planer einen Partial Index nicht?

Wenn die Abfrage-Bedingung das Index-Prädikat nicht beweisbar impliziert, z. B. bei einem Parameter im Generic Plan.

Warum random_page_cost auf SSD senken?

Zufälliger Zugriff ist auf SSD fast so billig wie sequenzieller. Mit 4.0 unterschätzt der Planer Index Scans.

Was ist bei EXPLAIN ANALYZE auf einem UPDATE zu beachten?

Es führt das UPDATE wirklich aus. Darum in BEGIN … ROLLBACK packen.

Was hat sich in PostgreSQL 17 für VACUUM geändert?

Eine neue Speicherstruktur für tote Tupel braucht viel weniger Speicher. Das 1-GB-Limit fällt weg.

Wo sehen Sie Checkpoint-Statistiken in PostgreSQL 17?

In pg_stat_checkpointer mit num_timed und num_requested. Vorher in pg_stat_bgwriter.

Szenario: Die DB-CPU ist bei 90 %, aber keine Abfrage ist langsamer als 50 ms. Was tun Sie?

pg_stat_statements nach total_exec_time und calls. Wahrscheinlich eine sehr häufige kleine Abfrage, z. B. N+1. Lösung im ORM oder mit Caching.

Szenario: Alle 5 Minuten gibt es Latenzspitzen bei hoher Schreiblast. Woran denken Sie?

An Checkpoints und Full Page Writes. Log und pg_stat_checkpointer prüfen, max_wal_size erhöhen, completion_target 0.9.

Szenario: Nach dem Erhöhen von work_mem stürzt die DB nachts ab. Warum?

Viele parallele Batch-Abfragen mit mehreren Hash-Knoten haben den RAM überschritten, der OOM-Killer griff. work_mem global senken und nur pro Rolle oder Session erhöhen.
