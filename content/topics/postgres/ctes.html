CTEs und rekursive Abfragen

Gerüst

Warum?
Lange SQL in benannte Schritte teilen. WITH RECURSIVE für Bäume und Graphen. DML im WITH: mehrere Änderungen atomar in einer Anweisung.
Wie innen?
Seit 12: einmal genutzt, reines SELECT, nicht volatil, nicht rekursiv → gefaltet. Sonst CTE Scan. Rekursion = Schleife über eine Working Table.
Zahlen
Inlining seit 12, SEARCH/CYCLE seit 14, CTE-Statistiken seit 17, Speicher im EXPLAIN seit 18 (PG 18 Release Notes). Puffer über work_mem (4 MB) → Platte.
Vergleich
CTE = eine Anweisung. Temp-Tabelle = Session, mit Index und Statistik. View = gespeichert für alle. Oracle hat zusätzlich CONNECT BY.
Produktion
Zyklus in den Daten → Endlosschleife, UNION ALL hilft nicht. MATERIALIZED oder Mehrfachnutzung → Filter wandert nicht hinein → Seq Scan.
Design
MATERIALIZED nur nach Plan-Vergleich. Jede Rekursion: CYCLE + Tiefengrenze + Timeout. Grosse Bäume: ltree oder Closure Table.

Antwort-Muster

Frage: Ist eine CTE in PostgreSQL ein Optimierungszaun?

  1. Mechanismus: Seit Version 12 faltet der Planner eine einfache CTE in die Hauptabfrage, dann wandern äussere Filter hinein.
  2. Zahl: Im Test mit 100 000 Zeilen nutzte die gefaltete CTE den Index, mit MATERIALIZED las sie alle Zeilen per Seq Scan.
  3. Trade-off: MATERIALIZED rechnet die CTE nur einmal, verhindert aber, dass äussere Filter einen Index nutzen.
  4. Produktion: Ich lasse den Standard und setze MATERIALIZED nur nach einem Plan-Vergleich, mit Kommentar.
Kern: Eine CTE (Common Table Expression) ist eine benannte Hilfsabfrage im WITH-Teil einer Anweisung. Sie macht lange SQL-Abfragen lesbar und erlaubt mit WITH RECURSIVE Abfragen über Bäume und Graphen. Seit PostgreSQL 12 ist eine einfache CTE kein Optimierungszaun mehr: Der Planner faltet sie in die Hauptabfrage.

1. Wo sitzt die CTE?

  1. WITH-Klausel: Sie steht vor der Hauptabfrage und definiert eine oder mehrere benannte Hilfsabfragen. Beispiel: WITH aktive AS (SELECT …) SELECT … FROM aktive.
  2. Parser: Er macht aus jeder CTE eine Unterabfrage mit Namen. Andere CTEs im selben WITH dürfen sie benutzen.
  3. Planner: Er entscheidet, ob er die CTE inline faltet, also wie eine Unterabfrage behandelt. Bedingungen: nicht rekursiv, ein reines SELECT ohne volatile Funktionen, genau einmal referenziert.
  4. CTE Scan: Sonst rechnet PostgreSQL die CTE einmal aus und puffert das Ergebnis. Die Hauptabfrage liest dann diesen Puffer.
  5. Rekursive CTE: Sie wird im Plan zu Recursive Union mit einem WorkTable Scan, also einer Schleife über eine Arbeitstabelle.
  6. Datenändernde CTE: INSERT, UPDATE, DELETE oder MERGE im WITH. Nur ihr RETURNING ist für den Rest der Abfrage sichtbar.

2. Die Reise einer rekursiven Abfrage (die Geschichte zum Merken)

  1. Anker-Teil: Der nicht-rekursive Teil läuft genau einmal. Er findet die Wurzel, hier Anna ohne Chef.
  2. Working Table: Annas Zeile kommt ins Ergebnis und in die Working Table, die Zeilen der letzten Runde.
  3. Rekursiver Teil: Er joint mitarbeiter mit der Working Table. Er sieht nur die Zeilen der letzten Runde, nicht alle bisherigen.
  4. Intermediate Table: Beat und Carla landen in der Intermediate Table. Mit UNION fallen Duplikate und schon gesehene Zeilen weg, mit UNION ALL nicht.
  5. Tausch: Die neuen Zeilen kommen ins Ergebnis. Dann ersetzen sie die Working Table. Die nächste Runde findet Dario.
  6. Ende: Liefert eine Runde keine Zeile mehr, endet die Schleife. „Rekursiv“ heisst intern also iterativ, Runde für Runde.

3. Beispiel: Hierarchie, Zyklus, Inline vs Materialized, Daten verschieben

CREATE SCHEMA demo_ctes; SET search_path = demo_ctes;
CREATE TABLE mitarbeiter (id int PRIMARY KEY, name text,
                          chef_id int REFERENCES mitarbeiter(id));
INSERT INTO mitarbeiter VALUES (1,'Anna',NULL),(2,'Beat',1),(3,'Carla',1),
                               (4,'Dario',2),(5,'Eva',4);
-- 1) Hierarchie von oben nach unten
WITH RECURSIVE kette AS (
  SELECT id, name, 1 AS ebene, name AS pfad FROM mitarbeiter WHERE chef_id IS NULL
  UNION ALL
  SELECT m.id, m.name, k.ebene + 1, k.pfad || ' > ' || m.name
  FROM mitarbeiter m JOIN kette k ON m.chef_id = k.id
)
SELECT * FROM kette ORDER BY pfad;

-- 2) Zyklus einbauen: Anna bekommt Eva als Chefin
UPDATE mitarbeiter SET chef_id = 5 WHERE id = 1;
SET statement_timeout = '2s';
WITH RECURSIVE kette AS (
  SELECT id, chef_id FROM mitarbeiter WHERE id = 5
  UNION ALL
  SELECT m.id, m.chef_id FROM mitarbeiter m JOIN kette k ON m.id = k.chef_id
) SELECT count(*) FROM kette;                       -- ohne Schutz
RESET statement_timeout;
WITH RECURSIVE kette AS ( ...gleich... )
  CYCLE id SET ist_zyklus USING pfad                -- mit Schutz
SELECT * FROM kette;

-- 3) Inline vs MATERIALIZED (100 000 Zeilen, Index auf kunde_id)
EXPLAIN (COSTS OFF) WITH a AS (SELECT * FROM auftrag)
  SELECT * FROM a WHERE kunde_id = 7;
EXPLAIN (COSTS OFF) WITH a AS MATERIALIZED (SELECT * FROM auftrag)
  SELECT * FROM a WHERE kunde_id = 7;

-- 4) Zeilen in einer Anweisung ins Archiv verschieben
WITH weg AS (DELETE FROM auftrag WHERE kunde_id = 7 RETURNING *)
INSERT INTO archiv SELECT * FROM weg;

-- 5) Gleicher Snapshot für alle Teile
WITH u AS (UPDATE mitarbeiter SET name = upper(name) WHERE id = 2 RETURNING name)
SELECT (SELECT name FROM mitarbeiter WHERE id = 2) AS tabelle,
       (SELECT name FROM u) AS returning;

-- 6) Aggregat im rekursiven Teil
WITH RECURSIVE t AS (SELECT 1 AS n UNION ALL SELECT count(*) FROM t) SELECT * FROM t;
DROP SCHEMA demo_ctes CASCADE;

Echte Ausgabe, PostgreSQL 17.12. Gekürzt: Ausgaben von CREATE, SET, ANALYZE und DROP.

  1. Hierarchie: Der Pfad wächst pro Runde. ORDER BY pfad ergibt eine Tiefensuche-Reihenfolge, Carla steht nach Beats ganzem Ast.
  2. Zyklus ohne Schutz: Die Kette 5 → 4 → 2 → 1 → 5 endet nie. Erst der statement_timeout bricht ab. UNION ALL hilft hier nicht.
  3. Zyklus mit CYCLE: CYCLE id SET ist_zyklus USING pfad merkt sich den Pfad. Die Zeile, die eine ID zum zweiten Mal sieht, bekommt ist_zyklus = t und wird nicht weiter verfolgt.
  4. Inline: Ohne Schlüsselwort faltet der Planner die CTE. Das WHERE kunde_id = 7 wandert hinein, der Index wird genutzt.
  5. MATERIALIZED: Die CTE wird ganz gelesen (Seq Scan, 100 000 Zeilen). Der Filter läuft erst danach auf dem CTE Scan.
  6. Verschieben: DELETE … RETURNING und INSERT laufen in einer Anweisung, also atomar. 100 Zeilen sind im Archiv, keine bleibt zurück.
  7. Snapshot: Die Hauptabfrage liest die Tabelle mit dem alten Snapshot und sieht noch „Beat“. Nur RETURNING zeigt den neuen Wert „BEAT“.
  8. Einschränkung: Aggregate sind im rekursiven Teil verboten. Zählen geht erst in der Hauptabfrage.

4. Details, die Interviewer fragen

  1. Inlining-Regel: Seit PostgreSQL 12 faltet der Planner eine CTE, wenn sie nicht rekursiv, frei von Seiteneffekten und genau einmal referenziert ist. Vorher wurde jede CTE immer zuerst ausgerechnet.
  2. MATERIALIZED: Es erzwingt das separate Ausrechnen. Nutzen: eine teure Funktion soll nur einmal laufen, oder man will dem Planner bewusst eine Grenze setzen.
  3. NOT MATERIALIZED: Es erzwingt das Falten, auch bei mehrfacher Nutzung. Risiko: doppelte Berechnung. Gewinn: Jede Nutzung liest nur ihren kleinen Teil per Index.
  4. Mehrfach referenzierte CTE: Sie läuft einmal pro Ausführung der Hauptabfrage. Der Planner schiebt keine Filter der Hauptabfrage hinein.
  5. Volatile Funktionen: Enthält die CTE random() oder nextval(), wird sie nicht gefaltet. So läuft die Funktion nur einmal pro Zeile.
  6. Aufbau einer rekursiven CTE: Immer Anker-Teil, dann UNION oder UNION ALL, dann rekursiver Teil. Nur der rekursive Teil darf die CTE selbst referenzieren.
  7. UNION vs UNION ALL: UNION verwirft Zeilen, die schon im Ergebnis sind. Das stoppt Zyklen nur, wenn die ganze Zeile gleich ist. Eine wachsende Spalte wie ebene macht jede Zeile neu.
  8. Einschränkungen im rekursiven Teil: Keine Aggregate (siehe Beispiel). Die CTE darf dort nur einmal vorkommen. Lösung: Zählen und Gruppieren in der Hauptabfrage.
  9. SEARCH (seit 14): SEARCH DEPTH FIRST BY id SET ord oder BREADTH FIRST erzeugt eine Sortierspalte. Sie steuert nicht die Auswertung, nur das spätere ORDER BY.
  10. CYCLE (seit 14): CYCLE id SET ist_zyklus USING pfad erkennt Zyklen. Vorher schrieb man das von Hand mit einem Array-Pfad und id = ANY(pfad).
  11. Datenändernde CTE: Sie läuft genau einmal und immer vollständig. Das gilt auch, wenn die Hauptabfrage ihr RETURNING nie liest.
  12. Ein Snapshot: Alle Teile einer Anweisung sehen denselben Snapshot. Sie sehen gegenseitig ihre Änderungen nicht. Der einzige Kanal ist RETURNING. Details zum Snapshot: Seite MVCC.
  13. Gleiche Zeile zweimal ändern: Das ist in einer Anweisung nicht unterstützt. Nur eine Änderung wirkt, welche, ist nicht sicher vorhersagbar.
  14. Nur auf oberster Ebene: Datenändernde CTEs sind nur im WITH der obersten Anweisung erlaubt. Bei INSERT … SELECT gehört das WITH vor das INSERT.
  15. Statistiken (seit 17): Der Planner nutzt bei einer CTE die Statistiken und die Sortierung ihrer Spalten. Schätzungen über einen CTE Scan sind damit besser als früher.

5. Vergleich

  • CTE vs Unterabfrage: Gefaltet sind beide gleich schnell. Die CTE ist lesbarer und kann mehrfach genutzt werden.
  • CTE vs temporäre Tabelle: Eine temporäre Tabelle lebt für die Session, bekommt Indizes und mit ANALYZE echte Statistiken. Gut für grosse Zwischenergebnisse, die mehrere Abfragen brauchen.
  • CTE vs View: Eine View ist eine gespeicherte Abfrage für alle Sessions. Eine CTE gilt nur für eine Anweisung.
  • CTE vs Materialized View: Eine Materialized View speichert das Ergebnis auf Platte und wird per REFRESH neu gebaut. Siehe Seite Normalisierung.
  • Rekursive CTE vs LATERAL: LATERAL darf auf die Zeile links davon zugreifen, ist aber nicht rekursiv. Gut für „Top N pro Gruppe“.
  • Rekursive CTE vs Graph-Datenbank: Für Bäume und kleine Graphen reicht die CTE. Für tiefe Traversierung über Millionen Kanten ist eine Graph-Engine meist schneller.
  • PostgreSQL vs Oracle: Oracle kennt zusätzlich CONNECT BY. PostgreSQL nutzt nur den SQL-Standard WITH RECURSIVE.

6. In der Produktion

  1. Abfrage langsam nach Upgrade von 11 oder älter: Vorher war jede CTE ein Zaun, danach wird gefaltet. Meist schneller, manchmal plant der Planner schlechter. Lösung: Plan vergleichen, gezielt MATERIALIZED setzen.
  2. Riesiger CTE Scan: Eine mehrfach genutzte CTE liest die ganze Tabelle, obwohl jede Nutzung nur wenige Zeilen braucht. Lösung: NOT MATERIALIZED oder den Filter in die CTE schreiben.
  3. Endlose Rekursion: Schlechte Daten mit einem Zyklus lassen die Abfrage laufen, bis Speicher oder Platte voll ist. Lösung: CYCLE-Klausel, eine Tiefengrenze (WHERE ebene < 50) und ein statement_timeout.
  4. Temp-Dateien bei grossen CTEs: Ein materialisiertes Ergebnis über work_mem (Standard 4 MB) geht auf Platte. Lösung: Ergebnis klein halten, sonst work_mem pro Session erhöhen (Seite Performance-Tuning).
  5. Unerwartetes Ergebnis bei DML in CTE: Die Hauptabfrage liest die Tabelle und sieht die Änderung nicht. Lösung: immer über RETURNING lesen.
  6. Lange Transaktion durch Batch-Verschiebung: DELETE … RETURNING über Millionen Zeilen hält Locks lange und erzeugt viel WAL. Lösung: in Paketen mit LIMIT in einer Unterabfrage verschieben.

7. Diagnose: Werkzeuge und Abfragen

  • EXPLAIN (ANALYZE, BUFFERS): Ein Knoten CTE Scan zeigt Materialisierung. Fehlt er, wurde gefaltet. Seit 18 zeigt EXPLAIN dort auch Speicher und Plattenverbrauch (PG 18 Release Notes).
  • Recursive Union / WorkTable Scan im Plan: loops beim WorkTable Scan zeigt die Zahl der Runden.
  • log_temp_files = 0: protokolliert jede temporäre Datei, auch von grossen CTEs.
  • pg_stat_statements: findet die teuersten Abfragen; dann den Plan mit EXPLAIN prüfen (Seite Planner und EXPLAIN).
  • SET statement_timeout beim Testen einer neuen Rekursion: schützt vor Endlosschleifen.
  • Zyklen in den Daten finden: dieselbe Abfrage mit CYCLE … SET ist_zyklus laufen lassen und WHERE ist_zyklus filtern.

8. Senior-Punkte

  1. Lesbarkeit kostet seit 12 nichts mehr. Lange Abfragen in benannte CTEs zerlegen ist der Normalfall.
  2. MATERIALIZED ist ein Werkzeug, kein Standard. Ich setze es nur mit Plan-Vergleich, und ich kommentiere warum.
  3. Jede Rekursion braucht eine Grenze: CYCLE, eine maximale Tiefe und ein Timeout. Daten mit Zyklen kommen in der Praxis vor.
  4. Datenändernde CTEs ersetzen Rundreisen. Verschieben, Claim und Log in einer Anweisung sind atomar und sparen Netzwerk.
  5. Grosse Hierarchien anders speichern, wenn sie oft gelesen werden: ltree-Pfade oder eine Closure Table. Die CTE bleibt für seltene oder kleine Abfragen.
  6. ORMs erzeugen selten CTEs. Für Baum-Abfragen schreibe ich natives SQL und teste es mit echten Datenmengen.

9. Aus dem Projekt

Das Muster der datenändernden CTE kenne ich aus MATCH: Der Claim ist ein atomares UPDATE … OUTPUT INSERTED.* auf SQL Server; in PostgreSQL wäre das UPDATE … RETURNING, auch innerhalb eines WITH.“ (Prüfen und durch dein echtes Beispiel ersetzen. 10. Fallen

  • „Eine CTE ist immer ein Optimierungszaun.“ → Falsch. Das galt bis Version 11. Seit 12 wird eine einfache CTE gefaltet.
  • „Eine CTE wird immer nur einmal ausgerechnet.“ → Falsch. Gefaltet läuft sie als Teil der Hauptabfrage, mit NOT MATERIALIZED sogar pro Nutzung.
  • „UNION ALL verhindert Endlosschleifen.“ → Falsch. UNION ALL behält alles. Erst CYCLE oder ein Pfad-Check stoppt Zyklen.
  • „Rekursiv heisst, PostgreSQL ruft sich selbst auf.“ → Falsch. Die Auswertung ist eine Schleife über eine Working Table.
  • „Die Hauptabfrage sieht die Änderungen aus dem WITH.“ → Falsch. Alle Teile nutzen denselben Snapshot. Nur RETURNING transportiert Änderungen.
  • „Eine DML-CTE ohne Verwendung läuft nicht.“ → Falsch. Sie läuft immer genau einmal und vollständig.
  • „SEARCH DEPTH FIRST ändert die Auswertung.“ → Falsch. Es erzeugt nur eine Sortierspalte.

11. Selbsttest

Warum?

Was ist eine CTE?

Eine benannte Hilfsabfrage im WITH-Teil einer Anweisung. Sie gilt nur für diese eine Anweisung.

Wozu nutzt man CTEs?

Für Lesbarkeit, für Rekursion über Bäume und Graphen und für mehrere Änderungen in einer atomaren Anweisung.

Warum war eine CTE bis Version 11 ein Optimierungszaun?

Bis 11 rechnete PostgreSQL jede CTE zuerst ganz aus. Filter der Hauptabfrage wanderten nicht hinein, Indizes blieben ungenutzt. Seit 12 wird eine einfache CTE gefaltet.

Wie innen?

Ist eine CTE in PostgreSQL ein Optimierungszaun?

Seit Version 12 nicht mehr, wenn sie nicht rekursiv, ohne Seiteneffekte und einmal referenziert ist. Dann wird sie gefaltet.

Was macht MATERIALIZED?

Es erzwingt, dass die CTE separat ausgerechnet und gepuffert wird. Filter der Hauptabfrage wandern dann nicht hinein.

Was macht NOT MATERIALIZED?

Es erzwingt das Falten, auch bei mehrfacher Nutzung. Das kann doppelte Arbeit bedeuten, spart aber, wenn jede Nutzung nur wenig braucht.

Woran sehe ich im Plan, ob eine CTE materialisiert wurde?

An einem Knoten „CTE Scan“ mit einem Unterplan „CTE name“. Fehlt er, wurde gefaltet.

Wie ist eine rekursive CTE aufgebaut?

Anker-Teil, dann UNION oder UNION ALL, dann der rekursive Teil, der die CTE selbst referenziert.

Wie wertet PostgreSQL eine rekursive CTE aus?

Iterativ: Der Anker füllt die Working Table. Jede Runde joint nur die Zeilen der letzten Runde. Ist eine Runde leer, ist Schluss.

Was macht die SEARCH-Klausel?

Sie erzeugt eine Sortierspalte für Tiefen- oder Breitensuche. Sortiert wird erst mit ORDER BY auf diese Spalte.

Warum sieht die Hauptabfrage die Änderung einer CTE nicht?

Alle Teile einer Anweisung laufen mit demselben Snapshot. Die Änderung ist darin noch nicht sichtbar. Nur über RETURNING kommen die neuen Werte an.

Zahlen

Seit wann gibt es SEARCH und CYCLE?

Seit PostgreSQL 14. Vorher schrieb man Pfad-Array und Zyklus-Check von Hand.

Wann faltet PostgreSQL eine CTE nicht?

Wenn sie rekursiv ist, Daten ändert, volatile Funktionen enthält, mehrfach genutzt wird oder MATERIALIZED trägt.

Was zeigt EXPLAIN seit PostgreSQL 18 bei einem CTE-Knoten?

Speicher- und Plattenverbrauch des CTE-Puffers, wie bei Material- und WindowAgg-Knoten (PG 18 Release Notes). So sieht man, ob die CTE auf Platte ging.

Was geht kaputt, wenn ein materialisiertes CTE-Ergebnis grösser als work_mem ist?

Nichts bricht ab, aber der Puffer geht in temporäre Dateien. Standard ist work_mem 4 MB. Die Abfrage wird langsamer, log_temp_files zeigt es.

Vergleich

Warum stoppt UNION einen Zyklus oft nicht?

UNION entfernt nur Zeilen, die ganz gleich sind. Eine wachsende Spalte wie ebene oder pfad macht jede Zeile neu. UNION ALL ist schneller, stoppt aber gar nichts.

CTE oder temporäre Tabelle?

CTE für eine Anweisung. Temporäre Tabelle, wenn mehrere Abfragen das Zwischenergebnis brauchen oder es Indizes und Statistiken braucht.

Produktion

Wie verhindere ich eine Endlosschleife?

Mit der CYCLE-Klausel, einer Tiefengrenze im rekursiven Teil und einem statement_timeout.

Was macht die CYCLE-Klausel?

Sie merkt sich den Pfad der Schlüsselspalten. Sieht sie einen Wert erneut, setzt sie die Markierungsspalte auf true und verfolgt die Zeile nicht weiter.

Darf ich im rekursiven Teil count(*) nutzen?

Nein. Aggregate sind dort verboten. Gezählt wird in der Hauptabfrage.

Was geht kaputt, wenn zwei Teile einer Anweisung dieselbe Zeile ändern?

Nur eine Änderung wirkt, und welche, ist nicht sicher vorhersagbar. Das muss man vermeiden.

Szenario: Nach dem Upgrade von PostgreSQL 11 ist ein Report langsamer. Was prüfen Sie?

Ob eine CTE jetzt gefaltet wird und der Plan schlechter ist. Plan vor und nach vergleichen, bei Bedarf MATERIALIZED setzen und Statistiken prüfen.

Szenario: Eine Organigramm-Abfrage läuft plötzlich endlos. Was ist los?

Vermutlich ein Zyklus in den Daten. Mit CYCLE den Zyklus finden, Daten korrigieren, und künftig CYCLE plus Tiefengrenze und Timeout einbauen.

Szenario: Eine CTE wird dreimal genutzt und liest jedes Mal die ganze Tabelle. Was tun Sie?

Den Filter in die CTE ziehen oder NOT MATERIALIZED setzen, damit jede Nutzung per Index nur ihre Zeilen liest. Danach mit EXPLAIN ANALYZE prüfen.

Design

Was ist eine datenändernde CTE?

Ein INSERT, UPDATE, DELETE oder MERGE im WITH. Mit RETURNING liefert es Zeilen an die Hauptabfrage.

Läuft eine DML-CTE, wenn niemand ihr Ergebnis liest?

Ja. Sie läuft genau einmal und vollständig.

Wie verschiebe ich Zeilen atomar in ein Archiv?

WITH weg AS (DELETE … RETURNING *) INSERT INTO archiv SELECT * FROM weg. Beides ist eine Anweisung und damit eine Transaktion.

Wie bekomme ich alle Vorgesetzten eines Mitarbeiters?

Rekursive CTE von unten nach oben: Anker ist der Mitarbeiter, der rekursive Teil joint auf m.id = k.chef_id.

Warum speichert man grosse, oft gelesene Bäume nicht nur mit chef_id?

Jede Teilbaum-Abfrage braucht dann eine Rekursion mit vielen Runden. Mit Materialized Path (ltree) oder einer Closure Table ist sie ein einfacher Index-Zugriff. Preis: Schreiben und Verschieben werden aufwendiger.
