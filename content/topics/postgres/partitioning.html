Tabellen-Partitionierung

Gerüst

Warum?
Retention per DETACH + DROP statt DELETE: kein Bloat, kein VACUUM. Kleinere Indizes, VACUUM pro Partition.
Wie innen?
Parent ohne Daten (relkind p), Tuple Routing beim INSERT. Pruning beim Planen (Konstante) oder beim Start ($1).
Zahlen
Doku: einige tausend Partitionen gehen, wenn fast alle geprunt werden. Pruning standardmässig an, partitionwise Join/Aggregate aus.
Vergleich
RANGE für Zeit, LIST für Mandant, HASH für Verteilung. Ersetzt keinen Index, ist kein Sharding (ein Server).
Produktion
Monats-Partition fehlt → alle Inserts scheitern. Funktion auf dem Key → kein Pruning. Parent ohne ANALYZE → schlechte Pläne.
Design
Key = Spalte in fast jedem WHERE und in der Retention. PK muss den Key enthalten: kein globaler Unique-Index.

Antwort-Muster

Frage: Wann und wie partitionieren Sie eine Tabelle?

  1. Mechanismus: Ich teile sie mit PARTITION BY RANGE nach Datum. Der Planner liest dank Pruning nur passende Partitionen.
  2. Zahl: Die Doku nennt einige tausend Partitionen als machbar, wenn Abfragen fast alle wegprunen.
  3. Trade-off: Ich gewinne schnelles Löschen per DROP, verliere aber globale Unique-Indizes und zahle Planungszeit.
  4. Produktion: Ich lege Partitionen per Job vorab an und alarmiere, wenn der nächste Monat fehlt.
Kern: Partitionierung teilt eine grosse logische Tabelle in kleinere physische Tabellen, die Partitionen, nach einem Partition Key wie dem Datum. Abfragen lesen dank Partition Pruning nur die passenden Partitionen. Alte Daten löscht man mit DETACH und DROP in Millisekunden statt mit einem riesigen DELETE.

1. Wo sitzt die Partitionierung?

  1. Partitionierte Tabelle: meldung ist eine virtuelle Tabelle ohne eigenen Speicher (relkind = 'p'). Sie definiert Spalten, Key und Methode.
  2. Partitionen: Jede Partition ist eine normale Tabelle mit eigenem Heap, eigenem VACUUM und eigenen Statistiken. Beispiel: meldung_2026_11 für November.
  3. Methoden: RANGE (untere Grenze inklusiv, obere exklusiv), LIST (feste Werte, z. B. Mandant oder Land) und HASH (Modulus und Rest, gleichmässige Verteilung).
  4. Tuple Routing: Ein INSERT auf meldung landet automatisch in der richtigen Partition. Passt keine, gibt es einen Fehler, ausser es existiert eine DEFAULT-Partition.
  5. Partitionierter Index: Ein Index auf dem Parent erzeugt einen Index pro Partition, auch für spätere Partitionen. Einen globalen Index über alle Partitionen gibt es nicht.
  6. Planner: Er entfernt Partitionen, die laut WHERE nicht passen können. Das ist Partition Pruning.

2. Die Reise einer Abfrage und eines Monatswechsels (die Geschichte zum Merken)

  1. Abfrage: Ein Report fragt nach Meldungen vom 10. November. Der Filter steht auf dem Partition Key eingang.
  2. Plan-Pruning: Ist der Wert eine Konstante, entfernt der Planner September und Oktober schon beim Planen. Sie erscheinen nicht im Plan.
  3. Laufzeit-Pruning: Ist der Wert ein Parameter ($1, Prepared Statement), entscheidet der Executor beim Start. EXPLAIN zeigt dann Subplans Removed. Auch Werte aus Joins und Unterabfragen können zur Laufzeit prunen.
  4. Scan: Nur meldung_2026_11 wird gelesen. Ihr Index ist klein und liegt eher im Cache.
  5. ATTACH: Vor dem Monatswechsel bekommt die neue Tabelle einen CHECK mit genau den Grenzen. Dann prüft ATTACH PARTITION die Daten nicht noch einmal.
  6. Retention: Der älteste Monat wird mit DETACH PARTITION … CONCURRENTLY gelöst und gelöscht. Das ist eine Datei-Operation, kein zeilenweises DELETE.

3. Beispiel: PK-Regel, Routing, Pruning, Attach/Detach, Row Movement

CREATE SCHEMA demo_partitioning; SET search_path = demo_partitioning;
-- 1) PK ohne Partition Key
CREATE TABLE meldung_x (id bigint PRIMARY KEY, eingang date NOT NULL)
  PARTITION BY RANGE (eingang);
-- 2) Drei Monate, 300 000 Zeilen
CREATE TABLE meldung (id bigint GENERATED ALWAYS AS IDENTITY, eingang date NOT NULL,
                      art text NOT NULL, PRIMARY KEY (id, eingang))
  PARTITION BY RANGE (eingang);
CREATE TABLE meldung_2026_09 PARTITION OF meldung FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
CREATE TABLE meldung_2026_10 PARTITION OF meldung FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE meldung_2026_11 PARTITION OF meldung FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE INDEX ON meldung (art);
INSERT INTO meldung (eingang, art) SELECT DATE '2026-09-01' + (g % 91),
  (ARRAY['order','trade'])[1 + g % 2] FROM generate_series(1, 300000) g;
SELECT tableoid::regclass AS partition, count(*) FROM meldung GROUP BY 1 ORDER BY 1;
-- 3) Zeile ausserhalb aller Partitionen
INSERT INTO meldung (eingang, art) VALUES ('2026-12-05', 'order');
-- 4) Pruning beim Planen
EXPLAIN (COSTS OFF) SELECT count(*) FROM meldung
 WHERE eingang >= '2026-11-10' AND eingang < '2026-11-11';
-- 5) Kein Pruning: Ausdruck auf dem Key
EXPLAIN (COSTS OFF) SELECT count(*) FROM meldung
 WHERE art = 'order' AND eingang + 1 = '2026-11-11';
-- 6) Pruning zur Laufzeit (generischer Plan mit $1)
PREPARE q(date) AS SELECT count(*) FROM meldung WHERE eingang = $1;
SET plan_cache_mode = force_generic_plan;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF) EXECUTE q('2026-10-15');
-- 7) Dezember ohne Scan anhängen, September abhängen
CREATE TABLE meldung_2026_12 (LIKE meldung INCLUDING DEFAULTS);
ALTER TABLE meldung_2026_12 ADD CONSTRAINT c
  CHECK (eingang >= '2026-12-01' AND eingang < '2027-01-01');
ALTER TABLE meldung ATTACH PARTITION meldung_2026_12
  FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');
ALTER TABLE meldung_2026_12 DROP CONSTRAINT c;
ALTER TABLE meldung DETACH PARTITION meldung_2026_09 CONCURRENTLY;
DROP TABLE meldung_2026_09;
SELECT relname, relkind FROM pg_class
 WHERE relname LIKE 'meldung%' AND relkind IN ('p','r') ORDER BY 1;
-- 8) Zeile wandert bei UPDATE des Keys
UPDATE meldung SET eingang = '2026-12-24'
 WHERE id = (SELECT min(id) FROM meldung_2026_10) RETURNING tableoid::regclass, id, eingang;
DROP SCHEMA demo_partitioning CASCADE;

Echte Ausgabe, PostgreSQL 17.12. Gekürzt: CREATE/ALTER-Meldungen, „(n rows)“, zwei gleiche Filter-Zeilen als (...); Fehlerzeilen (stderr) an ihre Anweisung gesetzt; eine DETAIL-Zeile umbrochen. Teil 8 stammt aus einem zweiten Lauf desselben Skripts.

  1. PK-Regel: Ein PK oder UNIQUE auf einer partitionierten Tabelle muss alle Key-Spalten enthalten. Jede Partition prüft nur ihre eigenen Zeilen, ein globaler Index fehlt.
  2. Routing: 300 000 Inserts auf meldung verteilen sich selbst auf drei Monate.
  3. Ausserhalb: Für den 5. Dezember gibt es keine Partition und keine DEFAULT-Partition. Der Insert scheitert. Darum Partitionen immer vorab anlegen.
  4. Plan-Pruning: Der Plan enthält nur November. Die anderen Monate tauchen gar nicht auf.
  5. Kein Pruning: eingang + 1 = … ist ein Ausdruck auf dem Key. Der Planner kann ihn nicht gegen die Grenzen prüfen und liest alle drei Partitionen.
  6. Laufzeit-Pruning: Im generischen Plan ist $1 beim Planen unbekannt. Der Executor entfernt beim Start zwei Partitionen: Subplans Removed: 2.
  7. Attach/Detach: Dezember ist dabei, September ist weg. Der CHECK vorab hat den Prüf-Scan beim Attach gespart.
  8. Row Movement: Ein UPDATE des Keys verschiebt die Zeile. Intern ist das ein DELETE in Oktober und ein INSERT in Dezember.

4. Details, die Interviewer fragen

  1. Deklarativ vs Vererbung: Heute nutzt man deklarative Partitionierung mit PARTITION BY. Die alte Variante über Tabellen-Vererbung und Trigger braucht man nicht mehr.
  2. DEFAULT-Partition: Sie nimmt alle Zeilen ohne passende Partition. Nachteil: Ein späteres ATTACH muss sie scannen, mit ACCESS EXCLUSIVE auf ihr. Und DETACH CONCURRENTLY geht nicht, solange eine DEFAULT-Partition existiert.
  3. Sub-Partitionierung: Eine Partition kann selbst partitioniert sein, z. B. RANGE nach Monat, dann LIST nach Art. Mehr Ebenen heissen mehr Planungsaufwand.
  4. Lock-Stufen: ATTACH PARTITION nimmt SHARE UPDATE EXCLUSIVE auf dem Parent, Lesen und Schreiben laufen weiter. DETACH ohne CONCURRENTLY und DROP einer Partition brauchen ACCESS EXCLUSIVE auf dem Parent (Seite Locking).
  5. DETACH CONCURRENTLY: Es läuft in zwei Transaktionen und wartet auf alle laufenden Abfragen. Es geht nicht in einem Transaktionsblock. Ein Abbruch wird mit DETACH … FINALIZE beendet.
  6. Index ohne lange Sperre: CREATE INDEX auf dem Parent kann nicht CONCURRENTLY. Weg: CREATE INDEX … ON ONLY meldung, dann pro Partition CONCURRENTLY und ALTER INDEX … ATTACH PARTITION.
  7. Pruning-Voraussetzung: Der Filter muss direkt auf den Key-Spalten stehen. Funktionen oder Rechnungen auf dem Key verhindern Pruning. enable_partition_pruning ist standardmässig an.
  8. Partitionwise Join und Aggregate: enable_partitionwise_join und enable_partitionwise_aggregate lassen gleich partitionierte Tabellen Partition für Partition joinen. Beide sind standardmässig aus, weil sie Planungszeit und Speicher kosten.
  9. Statistiken: Autovacuum bearbeitet nur die Partitionen, nicht den Parent. Der Parent braucht ein manuelles ANALYZE für Abfragen über alle Partitionen. Seit 18 gibt es ANALYZE ONLY meldung nur für den Parent (Release Notes 18, Utility Commands). Seit 19 analysiert vacuumdb --analyze-only ohne Ziel auch partitionierte Tabellen; vorher übersprang es sie (Release Notes 19, Server Applications).
  10. Foreign Keys: Eine partitionierte Tabelle kann einen FK haben und Ziel eines FK sein. Seit 18 auch als NOT VALID (Release Notes 18, Constraints).
  11. Neu in 17: Identity-Spalten und Exclusion Constraints auf partitionierten Tabellen. Der Exclusion Constraint muss die Key-Spalten mit = vergleichen.
  12. Neu in 18 und 19: 18 verbietet UNLOGGED partitionierte Tabellen; vorher wirkte UNLOGGED dort gar nicht auf die Partitionen (Release Notes 18, Migration). 18 plant Abfragen über viele Partitionen effizienter (Release Notes 18, Optimizer). 19 erlaubt COPY meldung TO … direkt, vorher brauchte man COPY (SELECT …) (Release Notes 19, COPY).
  13. Kein SPLIT/MERGE: Auch PostgreSQL 19 hat kein SPLIT PARTITION oder MERGE PARTITIONS (nicht in der ALTER-TABLE-Doku 19). Umbauen heisst: neue Partition anlegen, Daten kopieren, alte abhängen.
  14. Anzahl Partitionen: Die Doku nennt einige tausend Partitionen als gut machbar, wenn Abfragen fast alle wegprunen. Jede berührte Partition kostet Planungszeit und Speicher pro Session.
  15. Einschränkungen: Partitionen haben keine eigenen Zusatzspalten. Ein BEFORE ROW-Trigger kann das Ziel nicht ändern. Generated Columns dürfen nicht im Partition Key sein.

5. Vergleich

  • RANGE: Für Zeitreihen und Retention nach Datum. Der häufigste Fall.
  • LIST: Für wenige bekannte Werte, z. B. Mandant, Land oder Status. Gut, wenn man ganze Gruppen abhängen will.
  • HASH: Für gleichmässige Verteilung ohne natürliche Grenze. Pruning nur bei Gleichheit, keine Retention per Partition.
  • Partitionierung vs Index: Ein Index findet Zeilen schnell. Partitionierung hilft beim Löschen, Archivieren, VACUUM und bei Abfragen über grosse Zeiträume. Sie ersetzt keinen Index.
  • Partitionierung vs Sharding: Partitionen liegen auf einem Server. Sharding verteilt Daten auf mehrere Server, z. B. mit Citus. Partitionierung skaliert also nicht über einen Server hinaus.
  • PostgreSQL vs Iceberg: Iceberg hat Hidden Partitioning: Die Partition entsteht aus einer Transformation wie days(ts), und Abfragen müssen den Key nicht kennen. PostgreSQL braucht den Filter direkt auf der Key-Spalte.
  • PostgreSQL vs Oracle: Oracle hat globale Indizes und Interval-Partitionierung mit automatischem Anlegen. PostgreSQL hat beides nicht; Partitionen legt man selbst an oder mit pg_partman.

6. In der Produktion

  1. Inserts scheitern am Monatsersten: Die neue Partition fehlt. Lösung: Partitionen Wochen im Voraus anlegen, per Job oder pg_partman, und überwachen.
  2. Abfragen lesen alle Partitionen: Der Filter nutzt eine Funktion wie date_trunc auf dem Key oder fehlt ganz. Lösung: Filter als Bereich direkt auf der Spalte schreiben.
  3. Planung langsamer als Ausführung: Tausende Partitionen ohne Pruning. Lösung: weniger, grössere Partitionen oder Filter, die prunen.
  4. DELETE alter Daten erzeugt Bloat: Retention per DELETE statt per DROP. Lösung: Partitionsgrenzen an die Retention anpassen, dann DETACH und DROP.
  5. Doppelte IDs trotz PK: Der PK ist (id, eingang). Dieselbe id mit anderem Datum ist erlaubt. Lösung: IDs aus einer Sequence oder UUIDv7, Eindeutigkeit der ID nicht vom PK erwarten.
  6. Schlechte Pläne über alle Partitionen: Der Parent hat keine Statistiken, weil Autovacuum ihn nicht analysiert. Lösung: regelmässiges ANALYZE meldung.
  7. DEFAULT-Partition wird riesig: Fehlende Partitionen fallen still in DEFAULT. Ein späteres Attach scannt sie und sperrt. Lösung: DEFAULT überwachen oder ganz weglassen.

7. Diagnose: Werkzeuge und Abfragen

  • Partitionsbaum: SELECT * FROM pg_partition_tree('meldung'); zeigt alle Ebenen. \d+ meldung in psql zeigt Grenzen.
  • Grenzen lesen: SELECT relname, pg_get_expr(relpartbound, oid) FROM pg_class WHERE relispartition;
  • Grösse pro Partition: pg_total_relation_size() über pg_partition_tree.
  • Pruning prüfen: EXPLAIN: Welche Partitionen stehen im Plan? EXPLAIN ANALYZE: „Subplans Removed“ und (never executed).
  • Zeilen pro Partition: SELECT tableoid::regclass, count(*) … GROUP BY 1.
  • Hängendes Detach: pg_inherits.inhdetachpending zeigt eine halb abgehängte Partition; dann DETACH … FINALIZE.
  • Statistiken des Parents: pg_stat_user_tables.last_analyze für die partitionierte Tabelle.

8. Senior-Punkte

  1. Partitionieren erst ab echter Grösse. Meist ab vielen GB oder wenn Retention per DELETE weh tut. Für kleine Tabellen ist es nur Komplexität.
  2. Key nach Abfragen und Retention wählen. Die Spalte, die in fast jedem WHERE steht und nach der gelöscht wird.
  3. Kein globaler Unique-Index ist eine echte Grenze. Eindeutigkeit über alle Partitionen sichere ich über die ID-Erzeugung.
  4. Partitionen automatisch anlegen und das Fehlen alarmieren. Ein vergessener Monat ist ein Produktionsausfall.
  5. Wenige hundert Partitionen sind für OLTP ein guter Rahmen. Data-Warehouse-Last verträgt mehr.
  6. Partitionierung ist kein Sharding. Wenn ein Server nicht reicht, braucht es Read Replicas, Citus oder eine andere Architektur.

10. Fallen

  • „Partitionierung macht jede Abfrage schneller.“ → Falsch. Ohne Filter auf dem Key liest sie alle Partitionen, plus Planungsaufwand.
  • „Ich kann einen PK nur auf id setzen.“ → Falsch. UNIQUE und PK müssen alle Key-Spalten enthalten.
  • „Mehr Partitionen sind immer besser.“ → Falsch. Planungszeit und Speicher wachsen mit der Zahl der nicht geprunten Partitionen.
  • „Autovacuum hält die Statistiken des Parents aktuell.“ → Falsch. Nur die der Partitionen. Der Parent braucht manuelles ANALYZE.
  • „DETACH ist immer ohne Sperre.“ → Falsch. Nur mit CONCURRENTLY, und das geht nicht mit DEFAULT-Partition.
  • „WHERE date_trunc('day', eingang) = … prunt.“ → Falsch. Ein Ausdruck auf dem Key verhindert Pruning. Ein Bereich auf der Spalte prunt.
  • „PostgreSQL kann Partitionen splitten.“ → Falsch. Auch in 19 gibt es kein SPLIT oder MERGE PARTITION (ALTER-TABLE-Doku 19).

11. Selbsttest

Warum?

Was ist Tabellen-Partitionierung?

Eine logische Tabelle wird nach einem Key in mehrere physische Tabellen geteilt. Abfragen und Wartung arbeiten auf kleineren Teilen.

Welche Probleme löst sie?

Schnelles Löschen alter Daten, kleinere Indizes, schnellere Abfragen auf Teilbereiche und VACUUM pro Partition.

Warum ist DROP einer Partition so viel billiger als ein DELETE?

DROP entfernt die Dateien der Partition auf einmal. DELETE markiert jede Zeile einzeln, schreibt WAL pro Zeile und hinterlässt tote Tupel für VACUUM.

Wie lösche ich alte Daten effizient?

Die Partition abhängen und droppen. Kein DELETE, kein Bloat, kein VACUUM.

Wie innen?

Welche Methoden gibt es?

RANGE, LIST und HASH. Kombinationen über Sub-Partitionierung.

Hat die partitionierte Tabelle eigene Daten?

Nein. Sie ist virtuell, alle Zeilen liegen in den Partitionen.

Was passiert mit einer Zeile ohne passende Partition?

Der Insert scheitert, ausser es gibt eine DEFAULT-Partition.

Was ist Partition Pruning?

Der Planner oder Executor lässt Partitionen weg, die laut Filter keine Treffer haben können.

Wann passiert Pruning zur Laufzeit?

Wenn der Wert beim Planen unbekannt ist, z. B. ein Parameter im generischen Plan oder ein Wert aus einem Join. EXPLAIN zeigt dann Subplans Removed.

Warum prunt WHERE eingang + 1 = … nicht?

Der Filter ist ein Ausdruck auf dem Key. Der Planner kann ihn nicht mit den Grenzen vergleichen.

Was passiert bei UPDATE des Partition Keys?

Die Zeile wandert in die passende Partition. Intern ist das DELETE plus INSERT.

Zahlen

Wie viele Partitionen sind sinnvoll?

Die Doku nennt einige tausend als machbar bei gutem Pruning. Für OLTP plane ich eher Dutzende bis wenige hundert.

Was ist Partitionwise Join?

Zwei gleich partitionierte Tabellen werden Partition für Partition gejoint. Standardmässig aus.

Warum zeigt EXPLAIN ANALYZE „Subplans Removed: 2“?

Der Wert war beim Planen unbekannt, z. B. $1 im generischen Plan. Der Executor hat beim Start 2 von 3 Partitionen entfernt. Nur eine wurde gelesen.

Vergleich

Gibt es globale Indizes?

Nein. Ein Index auf dem Parent besteht aus einem Index pro Partition.

Partitionierung oder Sharding?

Partitionierung bleibt auf einem Server. Sharding verteilt auf mehrere Server und braucht z. B. Citus.

Kann PostgreSQL Partitionen splitten oder zusammenlegen?

Nein, auch 19 nicht (ALTER-TABLE-Doku 19). Man legt neue Partitionen an, kopiert und hängt alte ab.

Warum eignet sich HASH-Partitionierung nicht für Retention?

Jede HASH-Partition enthält Zeilen aus allen Zeiträumen. Man kann also keinen alten Monat abhängen. Pruning geht ausserdem nur bei Gleichheit.

Produktion

Welche Sperre braucht ATTACH PARTITION?

SHARE UPDATE EXCLUSIVE auf dem Parent und ACCESS EXCLUSIVE auf der neuen Tabelle und einer DEFAULT-Partition.

Was macht DETACH PARTITION CONCURRENTLY?

Es löst eine Partition mit schwacher Sperre in zwei Transaktionen. Nicht im Transaktionsblock, nicht mit DEFAULT-Partition.

Analysiert Autovacuum die partitionierte Tabelle?

Nein, nur die Partitionen. Für den Parent braucht es manuelles ANALYZE.

Was geht kaputt, wenn die DEFAULT-Partition gross wird?

Jedes spätere ATTACH muss sie scannen und sperrt sie dabei mit ACCESS EXCLUSIVE. DETACH CONCURRENTLY geht mit DEFAULT-Partition gar nicht. Lösung: DEFAULT überwachen oder weglassen.

Szenario: Am 1. des Monats schlagen alle Inserts fehl. Was ist los?

Die Partition für den neuen Monat fehlt. Sofort anlegen, dann Vorab-Anlage automatisieren und überwachen.

Szenario: Ein Report über einen Tag liest trotz Partitionierung alle Partitionen. Was prüfen Sie?

Den Filter: Steht er direkt als Bereich auf der Key-Spalte, ohne Funktion? EXPLAIN zeigt, welche Partitionen gelesen werden.

Design

Warum muss der PK den Partition Key enthalten?

Es gibt keinen globalen Index. Jede Partition prüft Eindeutigkeit nur lokal; mit dem Key im PK reicht das.

Wie lege ich einen Index ohne lange Sperre an?

CREATE INDEX ON ONLY auf dem Parent, dann pro Partition CONCURRENTLY, dann ALTER INDEX … ATTACH PARTITION.

Wie hänge ich eine Partition ohne Daten-Scan an?

Vorher einen CHECK mit genau den Grenzen anlegen. ATTACH nutzt ihn und prüft nicht erneut. Danach den CHECK löschen.

Wie legt man Partitionen automatisch an?

Mit einem geplanten Job oder der Erweiterung pg_partman, die Partitionen vorab anlegt und alte entfernt.

Szenario: Eine Log-Tabelle mit 2 TB wächst, das nächtliche DELETE älterer Daten dauert Stunden. Was schlagen Sie vor?

RANGE-Partitionierung nach Datum mit der Retention als Grenze. Dann löscht DETACH und DROP einen Monat in Sekunden. Migration: neue partitionierte Tabelle, alte Daten schrittweise umziehen.
