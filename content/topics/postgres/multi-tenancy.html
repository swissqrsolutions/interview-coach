Mandantenfähigkeit: DB, Schema oder Zeile

Kern: Mandantenfähigkeit (Multi-Tenancy) heisst: Eine Anwendung bedient mehrere Kunden (Mandanten), deren Daten getrennt bleiben. In PostgreSQL gibt es drei Modelle: Datenbank pro Mandant, Schema pro Mandant oder geteilte Tabellen mit tenant_id. Die Wahl ist ein Trade-off zwischen Isolation und Betriebskosten.

Antwort-Muster

Frage: Wie trennen Sie Mandanten in PostgreSQL?

  1. Mechanismus: Es gibt drei Modelle: Datenbank pro Mandant, Schema pro Mandant oder geteilte Tabellen mit tenant_id und Row-Level Security.
  2. Zahl: DB pro Mandant heisst Pool pro Mandant. 200 Mandanten × 5 Verbindungen × 3 Pods sind 3000 Verbindungen.
  3. Trade-off: Mehr Isolation kostet mehr Pools und Migrationen. Geteilte Tabellen sind billig, aber ein Bug kann fremde Daten zeigen.
  4. Produktion: Für sensible Daten nehme ich eine DB pro Mandant mit Registry. Für viele kleine Kunden nehme ich geteilte Tabellen mit RLS und FORCE.

1. Die Reise eines Requests im Modell „DB pro Mandant“

  1. Request kommt. Ein Filter validiert das JWT und liest den Mandanten b.
  2. TenantContext setzen. Der Mandant kommt in einen ThreadLocal. Alle Schichten darunter lesen ihn dort.
  3. Routing. Ein AbstractRoutingDataSource (Spring) oder ein MultiTenantConnectionProvider (Hibernate) wählt die DataSource für b.
  4. SQL läuft. Die Abfrage landet in der Datenbank von b. Ein Zugriff auf Daten von a ist technisch unmöglich.
  5. Neuer Mandant. Beim Onboarding legt die App CREATE DATABASE tenant_b an, führt Flyway darauf aus und registriert erst danach einen Pool.
  6. Registry. Eine zentrale Tabelle kennt alle Mandanten mit Datenbank, Schema-Version und Status (z. B. PROVISIONING, ACTIVE).
  7. Aufräumen. Nach dem Request wird der Kontext gelöscht. Bei Thread-Pools ist das Pflicht.

2. Aufbau

  1. Tenant-Resolver: bestimmt den Mandanten pro Request. Beispiel: ein Claim tenant im validierten JWT.
  2. A: Datenbank pro Mandant: Jeder Mandant hat eine eigene Datenbank im Cluster oder auf einem eigenen Server. Die App wählt die richtige Verbindung.
  3. B: Schema pro Mandant: Eine Datenbank, ein Schema (Namensraum für Tabellen) pro Mandant. Die App setzt search_path.
  4. C: Geteilte Tabellen: Alle Mandanten in denselben Tabellen. Jede Zeile hat tenant_id. Row-Level Security filtert in der Datenbank.

3. Details, die Interviewer fragen

  1. Datenbank pro Mandant: Das ist die beste Isolation innerhalb von PostgreSQL. Kein SQL kann Datenbanken übergreifend lesen. Jeder Mandant hat ein eigenes Backup und eigenes Löschen (DROP DATABASE). Er hat auch eigene Extensions und Einstellungen.
  2. CREATE DATABASE zur Laufzeit: Es geht nicht in einem Transaktionsblock. Die App-Rolle braucht CREATEDB. Mit TEMPLATE kopiert man eine vorbereitete Datenbank. Der Name kann kein Bind-Parameter sein. Darum validiert man ihn streng und baut ihn mit quote_ident oder einer Whitelist. Namen sind höchstens 63 Byte lang. Längere kürzt PostgreSQL still. Seit 19 sind Zeilenumbrüche (CR, LF) in Datenbank- und Rollennamen verboten (Release Notes 19).
  3. Flyway pro Mandant: 
    Flyway.configure()
      .dataSource(tenantUrl, user, password)   // oder .schemas("tenant_b")
      .locations("classpath:db/migration/tenant")
      .load()
      .migrate();
    Jede Datenbank (oder jedes Schema) hat eine eigene flyway_schema_history. Spring Boot migriert automatisch nur die primäre DataSource. Für Mandanten ruft man Flyway selbst auf. Das geschieht beim Start für alle und beim Onboarding für den neuen.
  4. Migrationen bei vielen Mandanten: Sie laufen nacheinander oder begrenzt parallel. Ein Mandant kann scheitern, während andere schon neu sind. Darum macht man Migrationen rückwärtskompatibel (expand/contract). Man führt den Status pro Mandant in der Registry. Und man wiederholt bei Fehlern.
  5. Schema pro Mandant: Die Isolation läuft per search_path und Rechte pro Schema. Ein Fehler im search_path zeigt Daten des falschen Mandanten. Tausende Schemas machen den Systemkatalog gross. pg_dump und Migrationen werden langsam.
  6. search_path hinter PgBouncer: Im Transaction Mode blieb ein SET search_path früher auf dem Backend. Er galt dann für den nächsten Client. Seit PostgreSQL 18 meldet der Server search_path-Änderungen an den Client (Release Notes 18). PgBouncer verfolgt den Wert seit 1.26 standardmässig. Er stellt ihn pro Client wieder her (Changelog 1.26). Mit älteren Versionen nutzt man nur SET LOCAL search_path in der Transaktion.
  7. Geteilte Tabellen: Sie sind billig und einfach zu migrieren (eine Migration für alle). Das Risiko ist ein vergessenes WHERE tenant_id. Es zeigt fremde Daten. RLS ist das Sicherheitsnetz in der DB.
  8. Wer RLS umgeht: Das tun Superuser, Rollen mit BYPASSRLS und der Tabellen-Owner (ohne FORCE). Ohne Policy gilt default deny. Unique- und FK-Prüfungen ignorieren RLS. Das kann Informationen verraten („Schlüssel existiert schon“).
  9. RLS und Performance: Die Policy ist ein zusätzliches Prädikat. Ohne Index mit tenant_id vorne gibt es Seq Scans. Funktionen in Policies sollten STABLE sein. Sie sollten keine Unterabfragen pro Zeile auslösen.
  10. Hibernate 6: @TenantId auf einem Feld filtert und befüllt automatisch (geteilte Tabelle). Für DB oder Schema pro Mandant nimmt man MultiTenantConnectionProvider plus CurrentTenantIdentifierResolver.
  11. Connection Routing und Pools: DB pro Mandant heisst Pool pro Mandant. 200 Mandanten × Pool 5 × 3 Pods = 3000 Verbindungen. Die Lösung sind kleine Pools. Man legt Pools lazy an, schliesst idle Pools und setzt PgBouncer davor. Achtung: PgBouncer poolt pro User/Datenbank-Paar. In Azure ist pgbouncer.default_pool_size 50. Bei 200 Mandanten-DBs sind das bis zu 10 000 Server-Verbindungen. Den Wert setzt man darum klein.
  12. Noisy Neighbour: Ein Mandant verbraucht CPU, I/O oder Verbindungen. Er bremst alle anderen. Im selben Cluster gibt es keine echte CPU- oder I/O-Isolation. Grenzen setzt man mit ALTER DATABASE tenant_b CONNECTION LIMIT 20, ALTER ROLE ... SET statement_timeout und Rate Limits in der App.
  13. Backup und Restore pro Mandant: Bei DB pro Mandant nutzt man pg_dump -Fc -d tenant_b und pg_restore einzeln. Bei Schema nutzt man pg_dump -n tenant_b. Bei geteilten Tabellen geht es nur per Export mit WHERE tenant_id. Azure Point-in-Time-Restore stellt immer den ganzen Server als neuen Server her. Einen Mandanten holt man dann per Dump daraus.
  14. Löschen eines Mandanten (DSG/DSGVO): Bei DB pro Mandant nutzt man DROP DATABASE. Bei geteilten Tabellen nutzt man DELETE über viele Tabellen. Das gibt Bloat. Die Daten bleiben in alten Backups bis zum Ablauf der Aufbewahrung.

4. Fallen

  • „RLS schützt auch vor dem Admin.“ → Falsch. Superuser und BYPASSRLS-Rollen umgehen RLS immer, Owner ohne FORCE auch.
  • „Schema pro Mandant ist so sicher wie DB pro Mandant.“ → Falsch. Ein falscher search_path oder ein voll qualifizierter Name greift auf fremde Schemas zu.
  • „Mit SET app.tenant_id bin ich sicher.“ → Falsch hinter einem Pool. Nur SET LOCAL bzw. set_config(..., true) endet mit der Transaktion.
  • „Azure PITR stellt einen Mandanten wieder her.“ → Falsch. Es stellt den ganzen Server als neuen Server her.
  • „DB pro Mandant löst Noisy Neighbours.“ → Falsch. Im gleichen Cluster teilen sich alle CPU, I/O, WAL und max_connections.
  • „Ohne Policy sieht man mit RLS alles.“ → Falsch. Ohne Policy gilt default deny.

5. Selbsttest

Warum?

Welche drei Modelle für Mandantenfähigkeit gibt es in PostgreSQL?

Datenbank pro Mandant, Schema pro Mandant und geteilte Tabellen mit tenant_id. Dazu Server pro Mandant als teuerste Variante.

Warum soll ein fehlender Mandant nichts zeigen statt alles?

Fail closed: Ein Bug im Tenant-Resolver darf kein Datenleck sein. Leere Ergebnisse fallen im Test auf, fremde Daten oft nicht.

Was ist ein Noisy Neighbour?

Ein Mandant verbraucht so viele Ressourcen, dass andere leiden. Im gleichen Cluster gibt es keine echte CPU- oder I/O-Isolation.

Wie innen?

Was ist Row-Level Security?

Policies, die PostgreSQL als Filter an jede Abfrage auf einer Tabelle anhängt. USING filtert lesbare Zeilen, WITH CHECK prüft geschriebene.

Wer umgeht RLS?

Superuser, Rollen mit BYPASSRLS und der Tabellen-Owner, ausser mit FORCE ROW LEVEL SECURITY.

Was passiert mit RLS ohne Policy?

Default deny: Keine Zeilen sind sichtbar oder änderbar.

Wie übergeben Sie den Mandanten an RLS?

Mit set_config('app.tenant_id', x, true) am Anfang jeder Transaktion. Die Policy liest current_setting('app.tenant_id', true).

Warum set_config mit true?

Der Wert gilt nur bis zum Transaktionsende. So bleibt er nicht auf einer gepoolten Verbindung für den nächsten Nutzer.

Kann RLS Informationen verraten?

Ja. Unique- und FK-Prüfungen ignorieren RLS. Ein Fehler „Schlüssel existiert“ verrät fremde Daten.

Wie routen Sie Verbindungen bei DB pro Mandant?

Tenant aus JWT in einen Kontext, dann AbstractRoutingDataSource oder Hibernate MultiTenantConnectionProvider. Ein Pool pro Mandant.

Was macht Hibernate @TenantId?

Es befüllt und filtert eine Mandanten-Spalte automatisch für geteilte Tabellen. Der Wert kommt vom CurrentTenantIdentifierResolver.

Zahlen

Wie viele Verbindungen erzeugen 200 Mandanten-DBs mit Pool 5 und 3 Pods?

200 × 5 × 3 = 3000. Standard max_connections ist 100. Darum kleine, lazy Pools und PgBouncer.

Warum ist pgbouncer.default_pool_size = 50 bei vielen Mandanten-DBs gefährlich?

PgBouncer poolt pro User/Datenbank-Paar. 200 Mandanten-DBs × 50 erlauben bis zu 10 000 Server-Verbindungen. Den Wert also klein setzen.

Wie lang darf der Name einer Mandanten-DB sein?

Höchstens 63 Byte, längere Namen kürzt PostgreSQL still. Seit 19 sind CR und LF im Namen verboten (Release Notes 19).

Vergleich

Warum ist Schema pro Mandant schwächer isoliert als DB pro Mandant?

Alle Schemas liegen in einer Datenbank. Ein falscher search_path oder ein voll qualifizierter Name liest fremde Daten, und Ressourcen sind geteilt.

Was sind Nachteile von Schema pro Mandant?

Grosser Systemkatalog ab tausenden Schemas, langsame Dumps und Migrationen. Isolation hängt am korrekten search_path.

Was ist ein Hybrid-Modell?

Kleine Mandanten in geteilten Tabellen, grosse oder sensible mit eigener DB. Eine Registry steuert das Routing.

Produktion

Welches Problem bringt ein Pool pro Mandant?

Die Verbindungen wachsen mit Mandanten × Pods × Poolgrösse. Lösung: kleine, lazy Pools und PgBouncer.

Was geht kaputt, wenn die App SET app.tenant_id statt set_config(..., true) nutzt?

Der Wert bleibt auf der gepoolten Verbindung. Der nächste Request auf dieser Verbindung sieht die Daten des alten Mandanten. PgBouncer setzt eigene Werte nicht zurück.

Was tun, wenn die Migration bei einem Mandanten scheitert?

Mandant markieren und sperren, die anderen laufen weiter. Migrationen rückwärtskompatibel halten, Fehler beheben, Retry.

Wie begrenzen Sie einen Noisy Neighbour?

CONNECTION LIMIT pro DB oder Rolle, statement_timeout pro Rolle, Rate Limits in der App. Grosse Mandanten auf eigenen Server.

Wie stellen Sie einen einzelnen Mandanten wieder her?

Bei DB pro Mandant mit pg_dump/pg_restore. In Azure: PITR auf einen neuen Server, dann den Mandanten per Dump zurückholen.

Szenario: Ein Kunde sieht kurz Daten eines anderen Kunden. Wo suchen Sie?

ThreadLocal nicht geleert, Async-Thread ohne Kontext, oder Session-SET auf gepoolter Verbindung. Als Netz RLS mit FORCE und App-Rolle ohne BYPASSRLS.

Szenario: Mit dem 150. Mandanten kommt „too many clients already“. Was tun Sie?

Verbindungsbudget rechnen. Pools pro Mandant verkleinern und idle schliessen, PgBouncer davor, oder Mandanten auf mehrere Server verteilen.

Design

Wann wählen Sie Datenbank pro Mandant?

Bei hohen Isolations- und Compliance-Anforderungen, wenigen bis mittleren Mandantenzahlen und Bedarf an Backup oder Löschen pro Mandant.

Wann wählen Sie geteilte Tabellen?

Bei sehr vielen kleinen Mandanten, gleichem Schema für alle und Kostendruck. Mit RLS als Sicherheitsnetz.

Wie legen Sie eine Mandanten-DB zur Laufzeit an?

CREATE DATABASE ausserhalb einer Transaktion mit CREATEDB-Recht, Name streng validiert. Dann Flyway migrate, dann Status ACTIVE.

Wie migrieren Sie mit Flyway pro Mandant?

Flyway per API für jede Mandanten-DataSource oder jedes Schema aufrufen. Jede hat ihre eigene flyway_schema_history.

Warum gehört tenant_id an die erste Stelle des Primärschlüssels?

Jede Abfrage filtert über RLS nach tenant_id. Steht die Spalte vorne, nutzt der Index genau den Bereich eines Mandanten statt zu scannen.

Wie löschen Sie einen Mandanten vollständig?

DB pro Mandant: DROP DATABASE. Geteilte Tabellen: DELETE über alle Tabellen. Backups enthalten die Daten bis zum Ende der Aufbewahrung.

Szenario: Ein Mandant hat versehentlich Daten gelöscht und will den Stand von gestern. Wie gehen Sie vor?

Bei DB pro Mandant: PITR auf einen neuen Server, pg_dump dieser Mandanten-DB, in eine neue DB restoren, prüfen, dann umschalten. Die anderen Mandanten bleiben unberührt.

Mehr

Gerüst

  • Warum? Eine App, viele Kunden: Daten müssen getrennt bleiben, der Betrieb bezahlbar. Jedes Modell tauscht Isolation gegen Kosten.
  • Wie innen? DB: Routing-DataSource pro Mandant. Schema: search_path. Zeile: tenant_id + RLS-Policy mit current_setting('app.tenant_id', true).
  • Zahlen 200 Mandanten × Pool 5 × 3 Pods = 3000 Verbindungen, Standard max_connections ist 100. DB-Name max. 63 Byte.
  • Vergleich DB: stärkste Isolation, teuer. Schema: Mittelweg, Katalog wächst. Geteilt + RLS: billig, schwächste Isolation. Server: auch CPU/I/O getrennt.
  • Produktion ThreadLocal nicht geleert oder SET statt SET LOCAL → fremde Daten. Flyway scheitert bei Mandant 37 von 120 → gemischte Versionen.
  • Design Risiko wählt das Modell. Registry (Ort, Version, Status), fail closed, RLS plus App-Filter, Migrationen expand/contract.

Beispiel: geteilte Tabelle mit Row-Level Security

CREATE TABLE orders (
  tenant_id uuid   NOT NULL,
  id        bigint GENERATED ALWAYS AS IDENTITY,
  amount    numeric(10,2) NOT NULL,
  PRIMARY KEY (tenant_id, id)             -- tenant_id vorne: Index pro Mandant
);
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE  ROW LEVEL SECURITY;   -- gilt auch für den Owner

CREATE POLICY tenant_isolation ON orders
  USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);

-- App-Rolle: kein Superuser, kein BYPASSRLS
CREATE ROLE app_user LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_user;

-- pro Transaktion (funktioniert auch hinter PgBouncer im Transaction Mode)
BEGIN;
SELECT set_config('app.tenant_id', '11111111-1111-1111-1111-111111111111', true);
SELECT count(*) FROM orders;
INSERT INTO orders (tenant_id, amount)
  VALUES ('22222222-2222-2222-2222-222222222222', 10);
ROLLBACK;

BEGIN;   -- ohne Mandant
SELECT count(*) FROM orders;
COMMIT;
 count
-------
     3
(1 row)

ERROR:  new row violates row-level security policy for table "orders"

 count
-------
     0
(1 row)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Annahme: Mandant 1111… hat 3 Bestellungen in der Tabelle.

  1. Die Policy hängt tenant_id = ... an jede Abfrage an. Die App sieht nur 3 eigene Zeilen, ohne WHERE im Code.
  2. WITH CHECK verhindert, dass ein Mandant Zeilen für einen anderen schreibt. Das Insert scheitert.
  3. Ohne gesetzten Mandanten liefert current_setting(..., true) NULL oder, nach einem früheren SET LOCAL in der Session, einen Leerstring. nullif(..., '') macht beides zu NULL. Der Vergleich ist nie wahr. Man sieht nichts statt alles: fail closed.
  4. set_config(..., true) wirkt wie SET LOCAL: nur bis Transaktionsende. Darum bleibt kein Wert auf einer gepoolten Verbindung hängen.
  5. FORCE ROW LEVEL SECURITY ist nötig, wenn die App als Tabellen-Owner verbindet. Owner umgehen RLS sonst.

Vergleich

  • DB pro Mandant: stärkste Isolation, einfaches Backup und Löschen pro Mandant, Mandanten-spezifische Anpassungen möglich. Teuer: viele Pools, viele Migrationen, Cross-Tenant-Reports schwer.
  • Schema pro Mandant: Mittelweg. Eine DB, getrennte Namensräume. Geteilte Ressourcen, Katalog-Probleme ab tausenden Schemas.
  • Geteilte Tabellen + RLS: billigster Betrieb, skaliert auf sehr viele kleine Mandanten, eine Migration. Schwächste Isolation, Noisy Neighbour, Restore pro Mandant schwer.
  • Server pro Mandant: volle Ressourcen-Isolation (CPU, I/O, Wartungsfenster). Am teuersten. Für grosse oder regulierte Mandanten.
  • Hybrid: kleine Mandanten geteilt, grosse oder sensible Mandanten mit eigener DB. Die Registry entscheidet das Routing.
  • Sharding nach tenant_id (z. B. Citus, Azure elastic clusters): geteilte Tabellen, aber verteilt über Knoten. Für sehr grosse Mandantenzahlen.

In der Produktion

  1. Daten des falschen Mandanten: Ein ThreadLocal wird nicht geleert. Ein Async-Thread oder der nächste Request erbt den Mandanten. Lösung: finally { clear(); }, Kontext explizit an Async-Tasks übergeben, Tests mit zwei Mandanten.
  2. Session-Wert klebt auf der Verbindung: SET app.tenant_id statt SET LOCAL. Hinter einem Pool sieht der nächste Nutzer fremde Daten. PgBouncer hilft hier nicht: Eigene Werte meldet PostgreSQL nicht an den Client. Lösung: set_config(..., true) in jeder Transaktion.
  3. Verbindungen erschöpft: Jeder neue Mandant bringt einen Pool. Irgendwann kommt too many clients already. Lösung: Verbindungsbudget, kleine und lazy Pools, PgBouncer.
  4. Halb migrierte Mandanten: Flyway scheitert bei Mandant 37 von 120. Die App läuft mit gemischten Schema-Versionen. Lösung: rückwärtskompatible Migrationen, Status pro Mandant, Mandant bis zum Erfolg sperren.
  5. Onboarding halb fertig: CREATE DATABASE klappt, Flyway nicht. Lösung: idempotentes Provisioning mit Status-Maschine und Retry. Beim nächsten Versuch existiert die DB schon.
  6. Noisy Neighbour: Ein grosser Import eines Mandanten macht alle langsam. Lösung: Limits pro Datenbank oder Rolle, eigener Batch-Pool, grosse Mandanten auf eigenen Server.
  7. RLS umgangen: Die App verbindet als Owner oder Superuser. Die Policy greift nie. Lösung: eigene App-Rolle ohne BYPASSRLS, plus FORCE ROW LEVEL SECURITY.

Diagnose: Werkzeuge und Abfragen

  • SELECT datname, numbackends, xact_commit, blks_read FROM pg_stat_database;: Last pro Mandanten-DB.
  • SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname;: Verbindungen pro Mandant.
  • pg_stat_statements mit Spalte dbid: teure Abfragen pro Mandanten-DB.
  • SELECT pg_size_pretty(pg_database_size('tenant_b'));: Grösse pro Mandant.
  • SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class WHERE relname = 'orders'; und SELECT * FROM pg_policies;: RLS aktiv und welche Policies.
  • SELECT rolname, rolsuper, rolbypassrls FROM pg_roles;: wer RLS umgeht.
  • SELECT version, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 1;: Schema-Version pro Mandant.
  • SET row_security = off; bei Backups: Abfrage scheitert mit Fehler, statt still Zeilen zu filtern.

Senior-Punkte

  1. Isolation folgt dem Risiko. Gesundheits- oder Personendaten mit strengen Vorgaben sprechen für DB pro Mandant. Viele kleine SaaS-Kunden sprechen für geteilte Tabellen.
  2. Die Registry ist das Herz. Sie kennt Mandant, Ort, Schema-Version und Status. Ohne sie gibt es kein sicheres Routing und keine Migration im grossen Stil.
  3. Fail closed. Fehlt der Mandant, sieht man nichts. Nie einen Default-Mandanten oder „alle“.
  4. Defense in Depth: Filter in der App plus RLS in der DB. Ein Bug in einer Schicht reicht dann nicht für ein Datenleck.
  5. Migrationen sind das grösste Betriebsrisiko bei DB und Schema pro Mandant. Expand/contract und Status pro Mandant sind Pflicht.
  6. Verbindungen skalieren mit Mandanten. Das muss man vor dem 100. Mandanten planen, nicht danach.
  7. Restore pro Mandant vorher üben. PITR in Azure stellt den ganzen Server her. Den Weg zum einzelnen Mandanten muss man kennen.
