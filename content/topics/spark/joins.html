Joins: Broadcast, Sort-Merge, Shuffle Hash

Kern: Eine Join-Strategie ist der physische Weg, auf dem Spark zwei Tabellen verbindet. Spark wählt sie nach Grösse, Join-Typ und Hints. Die richtige Strategie entscheidet, ob ein Join Sekunden oder Stunden dauert, weil sie den Shuffle bestimmt.

1. Wo sitzt die Join-Strategie?

  1. Der Code ruft df.join(other, "message_id") auf. Das ist nur ein logischer Join.
  2. Catalyst, der Optimizer, schiebt Filter vor den Join (Predicate Pushdown) und schätzt Grössen.
  3. JoinSelection, eine Planer-Regel, wählt die physische Strategie. Reihenfolge: zuerst Hints, dann Grösse, dann Join-Typ.
  4. Vier Strategien sind möglich: Broadcast Hash Join, Sort-Merge Join, Shuffle Hash Join, Nested Loop Join (Broadcast oder Cartesian).
  5. AQE (Adaptive Query Execution) prüft nach jedem Shuffle echte Grössen und kann die Strategie wechseln.

2. Die Reise eines Joins (die Geschichte zum Merken)

  1. Start: Ein Job verbindet 500 Mio. Trades mit einer Tabelle von 40 schema_type-Werten. Spark schätzt die kleine Seite auf 2 MB.
  2. Broadcast-Weg: 2 MB liegt unter autoBroadcastJoinThreshold (10 MB). Der Driver sammelt die kleine Tabelle und baut eine Hash-Tabelle. Jeder Executor bekommt eine Kopie.
  3. Probe: Jeder Task liest seine Trades-Partition und sucht jeden Schlüssel in der Hash-Tabelle. Die grosse Tabelle bewegt sich nicht.
  4. Anderer Fall, zwei grosse Tabellen: Trades mit 500 Mio. Orders. Kein Broadcast möglich. Beide Seiten werden nach message_id gehasht und geshuffelt. Gleiche Schlüssel landen in der gleichen Partition.
  5. Sort und Merge: Jede Partition wird auf beiden Seiten sortiert. Dann laufen zwei Zeiger parallel durch die Listen. Das ist der Sort-Merge Join. Er kann auf Disk spillen und ist darum robust.
  6. Shuffle Hash Join: Gleicher Shuffle, aber ohne Sort. Pro Partition baut Spark eine Hash-Tabelle aus der kleineren Seite. Schneller, aber die Tabelle muss in den Speicher passen.

3. Beispiel: Strategien im Plan erkennen

from pyspark.sql import functions as F

trades = spark.table("lake.silver.trades")           # gross
types  = spark.table("lake.silver.schema_types")     # klein, ca. 40 Zeilen
orders = spark.table("lake.silver.orders")           # gross

trades.join(types, "schema_type").explain()                       # 1) automatisch
trades.join(orders, "message_id").explain()                       # 2) zwei grosse
trades.join(F.broadcast(types), "schema_type").explain()          # 3) Hint im Code
trades.join(orders.hint("shuffle_hash"), "message_id").explain()  # 4) Shuffle Hash

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)        # 5) Broadcast aus
trades.join(types, "schema_type").explain()

   :- Filter isnotnull(schema_type#12)
   +- BroadcastExchange HashedRelationBroadcastMode(...), [plan_id=31]

2) SortMergeJoin [message_id#3L], [message_id#77L], Inner
   :- Sort [message_id#3L ASC NULLS FIRST], false, 0
   :  +- Exchange hashpartitioning(message_id#3L, 200), ENSURE_REQUIREMENTS
   +- Sort [message_id#77L ASC NULLS FIRST], false, 0
      +- Exchange hashpartitioning(message_id#77L, 200), ENSURE_REQUIREMENTS

3) BroadcastHashJoin ... BuildRight ...          (wie 1)

4) ShuffledHashJoin [message_id#3L], [message_id#77L], Inner, BuildRight
   :- Exchange hashpartitioning(message_id#3L, 200)
   +- Exchange hashpartitioning(message_id#77L, 200)

5) SortMergeJoin [schema_type#12], [schema_type#40], Inner

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spark 3.5/4.x, Ausschnitte unter AdaptiveSparkPlan isFinalPlan=false.

  1. BuildRight heisst: Die rechte Seite (types) wird zur Hash-Tabelle. Es gibt einen BroadcastExchange, aber keinen Shuffle für trades.
  2. Zwei grosse Seiten: zwei Exchange-Knoten (Shuffle) und zwei Sort-Knoten. Das ist der teure Standardfall.
  3. F.broadcast() erzwingt den Broadcast auch über 10 MB. Gefährlich, wenn die Tabelle wächst.
  4. ShuffledHashJoin: Shuffle bleibt, Sort fällt weg.
  5. Mit Schwelle -1 plant Spark keinen automatischen Broadcast mehr. Es fällt auf Sort-Merge zurück.

4. Details, die Interviewer fragen

  1. autoBroadcastJoinThreshold (10 MB): maximale geschätzte Grösse für automatischen Broadcast. -1 schaltet ihn ab.
  2. Geschätzte Grösse: Spark nutzt Statistiken aus Datei-Metadaten oder ANALYZE TABLE. Nach Filtern und Projektionen ist die Schätzung oft falsch. Komprimiertes Parquet ist im Speicher viel grösser.
  3. spark.sql.broadcastTimeout (300 s): Zeitlimit, um die Broadcast-Tabelle zu bauen.
  4. Broadcast-Grenze: Die Broadcast-Tabelle muss in Driver und jeden Executor passen. Spark hat eine harte Obergrenze von 8 GB.
  5. Build Side: Die Seite, aus der die Hash-Tabelle entsteht. Bei LEFT OUTER kann nur die rechte Seite gebroadcastet werden, bei RIGHT OUTER nur die linke. FULL OUTER unterstützt keinen Broadcast Hash Join.
  6. preferSortMergeJoin (true): Spark bevorzugt Sort-Merge vor Shuffle Hash. Grund: Sort-Merge kann spillen.
  7. Join Hints: BROADCAST (auch BROADCASTJOIN, MAPJOIN), MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL. Priorität in genau dieser Reihenfolge.
  8. Hint ist keine Garantie: Unterstützt eine Strategie den Join-Typ nicht, ignoriert Spark den Hint.
  9. Nicht-Equi-Join: Ohne = im ON (z. B. a.ts BETWEEN b.start AND b.end) bleibt nur Nested Loop. Ist eine Seite klein: BroadcastNestedLoopJoin, sonst CartesianProduct.
  10. Bucketing: bucketBy(64, "message_id") schreibt die Tabelle in 64 Hash-Buckets. Joinen zwei Tabellen mit gleichen Buckets, entfällt der Shuffle. Gilt für Spark-Tabellen im Metastore; Iceberg hat eigene bucket(N, col)-Partitionen.
  11. AQE-Umstellung: Ist eine Seite nach dem Shuffle klein, stellt AQE Sort-Merge auf Broadcast um. Der Shuffle ist dann schon passiert, aber Sort und Netzwerk-Lesen fallen weg.
  12. Null-Schlüssel: null = null ist nicht wahr. Null-Schlüssel finden nie einen Partner. Für Null-Gleichheit gibt es <=> (eqNullSafe).

5. Vergleich

  • Broadcast Hash Join: eine Seite klein, kein Shuffle der grossen Seite, am schnellsten. Risiko: Driver- und Executor-OOM.
  • Sort-Merge Join: zwei grosse Seiten, Shuffle und Sort, spillt auf Disk. Standard und robust.
  • Shuffle Hash Join: Shuffle ohne Sort. Schneller, wenn eine Seite pro Partition in den Speicher passt.
  • Broadcast Nested Loop Join: Nicht-Equi-Join mit kleiner Seite. O(n × m), aber ohne Shuffle.
  • Cartesian Product: Nicht-Equi-Join mit zwei grossen Seiten. Fast immer ein Fehler.
  • Bucketed Sort-Merge Join: Sort-Merge ohne Shuffle, weil beide Tabellen gleich gebucketet sind.

6. In der Produktion

  1. Broadcast zu gross: Ein Hint oder hoher Threshold broadcastet eine gewachsene Tabelle. Folge: Driver-OOM oder broadcastTimeout. Lösung: Hint entfernen, Threshold realistisch, AQE entscheiden lassen.
  2. Kein Broadcast trotz kleiner Tabelle: Spark kennt die Grösse nicht, z. B. nach einer UDF oder einem komplexen Filter. Lösung: F.broadcast() bewusst setzen oder Statistiken sammeln.
  3. Explodierender Join: Duplikate im Schlüssel vervielfachen Zeilen. 1000 × 1000 Zeilen pro Schlüssel = 1 Mio. Lösung: Schlüssel vorher prüfen und deduplizieren.
  4. Skew: Ein Schlüssel hat 80 % der Zeilen. Ein Task läuft Stunden. Lösung: AQE Skew Join oder Salting (siehe Seite Data Skew).
  5. Versteckter Cartesian Product: Fehlende Join-Bedingung oder ein OR in ON. Lösung: Plan lesen, Bedingung korrigieren.
  6. Shuffle Hash Join mit OOM: Eine Build-Partition passt nicht in den Speicher. Lösung: Sort-Merge erzwingen (MERGE-Hint) oder mehr Partitionen.

7. Diagnose: Werkzeuge und Befehle

  • df.explain("formatted") oder SQL EXPLAIN FORMATTED: zeigt die gewählte Strategie und die Build Side.
  • df.explain("cost"): zeigt geschätzte Grössen (Statistics(sizeInBytes=...)). Damit sieht man, warum kein Broadcast kam.
  • Spark UI, SQL-Tab: der finale Plan nach AQE (isFinalPlan=true), Zeilen pro Knoten, Grösse des Broadcasts (data size).
  • Spark UI, Stages-Tab: Shuffle Read/Write pro Join-Stage. Max vs Median zeigt Skew.
  • ANALYZE TABLE t COMPUTE STATISTICS: Statistiken für Spark-Katalog-Tabellen sammeln.
  • df.groupBy("key").count().orderBy(F.desc("count")).show(10): häufigste Schlüssel vor dem Join prüfen.

8. Senior-Punkte

  1. Der beste Join ist der ohne Shuffle. Vorher filtern, nur nötige Spalten lesen, kleine Seiten broadcasten.
  2. Hints sind Wetten auf die Zukunft. Ein Broadcast-Hint auf eine wachsende Tabelle wird später zum OOM. Lieber Threshold und AQE nutzen.
  3. Sort-Merge ist der sichere Standard. Er ist langsamer, aber er spillt statt abzustürzen.
  4. Plan lesen gehört zum Code-Review bei teuren Jobs. Ein unerwarteter CartesianProduct oder ein doppelter Exchange fällt sofort auf.
  5. Datenqualität vor Tuning: Doppelte oder Null-Schlüssel ändern Ergebnis und Laufzeit. Eindeutigkeit prüfen, bevor man joint.
  6. Bucketing nur bei wiederholten Joins auf demselben Schlüssel. Es fixiert das Layout und braucht Pflege.

10. Fallen

  • „Ein Hint erzwingt immer die Strategie.“ → Falsch. Unterstützt sie den Join-Typ nicht, ignoriert Spark den Hint.
  • „10 MB Threshold heisst 10 MB auf Disk.“ → Falsch. Es ist eine Schätzung. Im Speicher ist die Tabelle oft viel grösser als komprimiertes Parquet.
  • „Broadcast ist immer am schnellsten.“ → Falsch. Bei grossen Tabellen kostet das Sammeln auf dem Driver mehr als ein Shuffle und riskiert OOM.
  • „Bei LEFT JOIN kann Spark jede Seite broadcasten.“ → Falsch. Nur die rechte Seite.
  • „Shuffle Hash Join ist veraltet.“ → Falsch. Er ist schneller ohne Sort, braucht aber genug Speicher pro Partition.
  • „null-Schlüssel joinen miteinander.“ → Falsch. Nur mit <=> / eqNullSafe.

11. Fragen

Welche Join-Strategien kennt Spark?

Broadcast Hash Join, Sort-Merge Join, Shuffle Hash Join, Broadcast Nested Loop Join und Cartesian Product.

Wie funktioniert ein Broadcast Hash Join?

Der Driver sammelt die kleine Seite, baut eine Hash-Tabelle und schickt sie an alle Executors. Die grosse Seite wird ohne Shuffle dagegen geprüft.

Wie funktioniert ein Sort-Merge Join?

Beide Seiten werden nach dem Schlüssel geshuffelt und je Partition sortiert. Dann werden zwei sortierte Listen gemischt.

Wie funktioniert ein Shuffle Hash Join?

Beide Seiten werden geshuffelt. Pro Partition baut Spark eine Hash-Tabelle aus der kleineren Seite. Es gibt keinen Sort.

Warum ist Sort-Merge der Standard?

Er funktioniert für alle Grössen und kann auf Disk spillen. Shuffle Hash braucht die Hash-Tabelle im Speicher.

Was ist autoBroadcastJoinThreshold?

Die maximale geschätzte Grösse für automatischen Broadcast, Standard 10 MB. Mit -1 ist Auto-Broadcast aus.

Warum broadcastet Spark eine kleine Tabelle nicht?

Spark kennt die Grösse nicht oder schätzt sie zu hoch, z. B. nach UDFs. Oder der Join-Typ erlaubt diese Build Side nicht.

Welche Join Hints gibt es?

BROADCAST, MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL. Bei Konflikt gilt diese Reihenfolge als Priorität.

Wie setzen Sie einen Broadcast in PySpark?

df.join(F.broadcast(small), "key") oder small.hint("broadcast").

Was ist die Build Side?

Die Seite, aus der die Hash-Tabelle gebaut wird. Im Plan steht BuildLeft oder BuildRight.

Welche Seite kann bei LEFT OUTER JOIN gebroadcastet werden?

Nur die rechte. Bei FULL OUTER geht kein Broadcast Hash Join.

Was passiert bei einem Join ohne Gleichheitsbedingung?

Spark nutzt Nested Loop: Broadcast Nested Loop bei kleiner Seite, sonst Cartesian Product. Beides ist teuer.

Was ist Bucketing?

Die Tabelle wird in eine feste Anzahl Hash-Buckets nach dem Join-Schlüssel geschrieben. Gleich gebucketete Tabellen joinen ohne Shuffle.

Was macht AQE bei Joins?

Es misst nach dem Shuffle echte Grössen. Ist eine Seite klein, stellt es auf Broadcast um. Bei Skew teilt es grosse Partitionen.

Woran erkennen Sie im Plan einen Shuffle?

Am Knoten Exchange hashpartitioning(...). Ein Broadcast zeigt BroadcastExchange.

Warum kann ein Broadcast zum Driver-OOM führen?

Der Driver sammelt die ganze Broadcast-Seite und baut die Hash-Tabelle. Ist sie zu gross, reicht sein Heap nicht.

Warum explodiert manchmal die Zeilenzahl nach einem Join?

Doppelte Schlüssel auf beiden Seiten multiplizieren sich. Schlüssel vorher auf Eindeutigkeit prüfen.

Was passiert mit null-Schlüsseln?

Sie finden keinen Partner, weil null = null nicht wahr ist. Mit eqNullSafe (<=>) werden sie gleich behandelt.

Was zeigt explain("cost")?

Die geschätzten Grössen und Zeilenzahlen. Damit sieht man, warum Spark eine Strategie gewählt hat.

Szenario: Ein Join-Job stürzt seit einer Woche mit Driver-OOM ab, ohne Code-Änderung. Woran denken Sie?

Eine gebroadcastete Tabelle ist gewachsen, oft wegen eines festen Hints. Plan prüfen, Hint entfernen oder Threshold senken, Sort-Merge zulassen.

Szenario: Ein Join mit einer Mapping-Tabelle von 40 Zeilen macht einen Shuffle über 500 GB. Was tun Sie?

Im Plan prüfen, warum kein Broadcast kam. Dann F.broadcast() setzen. Die grosse Seite muss dann nicht geshuffelt werden.

Szenario: Ein Join läuft Stunden, im Plan steht CartesianProduct. Was ist passiert?

Die Join-Bedingung fehlt oder ist kein Gleichheitsvergleich, z. B. ein OR. Bedingung korrigieren oder einen Equi-Schlüssel ergänzen.
