Spark-Architektur: Driver, Executor, Cluster Manager

Kern: Spark ist eine verteilte Engine, die Daten parallel auf vielen Rechnern verarbeitet. Ein Driver plant die Arbeit, viele Executors rechnen sie in Tasks. Ein Cluster Manager (z. B. Kubernetes) gibt ihnen CPU und Speicher.

1. Wo sitzen Driver, Executor und Cluster Manager?

  1. Driver: plant und steuert. Er führt dein main() aus und hält die SparkSession, also den Einstiegspunkt. Beispiel: spark.read.parquet(...) läuft im Driver.
  2. Cluster Manager: verteilt Ressourcen. Er startet Prozesse mit CPU und Speicher. Beispiel: Auf Kubernetes erzeugt der Driver über die API Executor-Pods.
  3. Executor: rechnet. Ein Executor ist ein JVM-Prozess auf einem Worker. Er führt Tasks aus, hält Cache und schreibt Shuffle-Dateien.
  4. Core: Task-Slot. Jeder Core führt gleichzeitig einen Task aus, also die Arbeit für eine Partition. Beispiel: 10 Executors × 4 Cores = 40 Tasks parallel.
  5. Speicher: hält die Daten. Spark selbst speichert nichts dauerhaft. Die Executors lesen und schreiben direkt im Object Store, nicht über den Driver.

2. Die Reise einer Anwendung (die Geschichte zum Merken)

  1. Submit. Ein Client ruft spark-submit --master k8s://https://<api>:443 --deploy-mode cluster auf. Bei MATCH schickt ein .NET-Worker den Job per REST.
  2. Driver startet. Im Cluster Mode läuft der Driver als eigener Pod im Cluster. Er erstellt die SparkSession.
  3. Executors kommen. Der Driver bittet die Kubernetes-API um Executor-Pods. Diese starten, verbinden sich mit dem Driver und melden ihre Cores.
  4. Eine Action startet Arbeit. Transformationen bauen nur einen Plan. Erst eine Action (z. B. write, count) startet einen Job.
  5. Planen. Catalyst optimiert den Plan. Der DAGScheduler teilt den Job an Shuffle-Grenzen in Stages.
  6. Verteilen. Der TaskScheduler schickt pro Partition einen Task an einen freien Core. Er bevorzugt Executors, die die Daten schon haben (Data Locality). Scheitert ein Task, startet er ihn neu (Standard: 4 Versuche).
  7. Ende. Nach spark.stop() löscht Spark die Executor-Pods. Der Driver-Pod bleibt im Status Completed und behält die Logs.

3. Beispiel: Job auf Kubernetes starten und Parallelität ablesen

$ spark-submit \
  --master k8s://https://aks-api.example:443 \
  --deploy-mode cluster \
  --name ingest-orders \
  --conf spark.kubernetes.container.image=myacr.azurecr.io/spark-etl:1.4 \
  --conf spark.kubernetes.namespace=spark-jobs \
  --conf spark.executor.instances=3 \
  --conf spark.executor.cores=4 \
  --conf spark.executor.memory=8g \
  local:///opt/app/ingest.py
# ingest.py
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("ingest-orders").getOrCreate()
sc = spark.sparkContext
print("master:", sc.master)
print("deployMode:", sc.getConf().get("spark.submit.deployMode"))
print("defaultParallelism:", sc.defaultParallelism)
spark.stop()

4. Details, die Interviewer fragen

  1. Driver-Aufgaben: Code ausführen, Plan bauen, Stages und Tasks planen, Executors überwachen, Ergebnisse von collect() annehmen. Stirbt der Driver, stirbt die ganze Anwendung.
  2. Executor-Aufgaben: Tasks in Threads ausführen, Daten cachen (BlockManager), Shuffle-Dateien schreiben und anderen Executors liefern. Stirbt ein Executor, rechnet Spark seine Tasks woanders neu.
  3. Cores und Tasks: spark.executor.cores legt die Task-Slots pro Executor fest. spark.task.cpus (Standard 1) legt fest, wie viele Cores ein Task braucht. Parallelität = Executors × Cores / task.cpus.
  4. Executor-Grösse: Viele kleine Executors (1 Core) teilen keinen Cache und keine Broadcasts. Wenige riesige Executors haben lange GC-Pausen. Üblich sind 4–5 Cores pro Executor.
  5. Speicher pro Executor: spark.executor.memory ist der JVM-Heap. Dazu kommt memoryOverhead, also Speicher ausserhalb des Heaps. Standard 10 %, mindestens 384 MB; auf Kubernetes für Nicht-JVM-Jobs wie PySpark 40 %.
  6. Pod-Limit auf Kubernetes: Der Pod bekommt Heap + Overhead (+ spark.executor.pyspark.memory). Überschreitet der Prozess das, tötet Kubernetes ihn: OOMKilled, Exit-Code 137.
  7. PySpark-Aufbau: Dein Python-Code läuft im Driver als Python-Prozess. Er steuert die Driver-JVM über Py4J. DataFrame-Operationen laufen danach ganz in den Executor-JVMs.
  8. Python Worker: Nur Python-UDFs und RDD-Lambdas brauchen auf den Executors Python-Worker-Prozesse. Die Daten werden dafür zwischen JVM und Python kopiert (Pickle oder Arrow).
  9. Client vs Cluster Mode: Im Client Mode läuft der Driver dort, wo du startest (Notebook, Laptop, Pod). Im Cluster Mode läuft er im Cluster. Für Produktion: Cluster Mode.
  10. Client Mode auf Kubernetes: Die Executors müssen den Driver erreichen. Läuft der Driver in einem Pod, braucht er einen Headless Service und spark.driver.host.
  11. Cluster Manager: Standalone (eingebaut), YARN (Hadoop), Kubernetes (seit 2.3, GA seit 3.1). Mesos ist seit 3.2 veraltet und in 4.0 entfernt. local[*] ist kein Cluster, sondern Tests auf einem Rechner.
  12. Dynamic Allocation: Spark fordert Executors nach Bedarf an und gibt freie wieder ab. Auf Kubernetes gibt es keinen External Shuffle Service. Darum braucht man spark.dynamicAllocation.shuffleTracking.enabled=true.
  13. Spark Connect (seit 3.4): Ein dünner Client schickt den ungelösten logischen Plan per gRPC an einen Spark-Server (Port 15002). Der Client braucht keine JVM. Ab 4.0 gibt es dafür das schlanke Paket pyspark-client.
  14. Spark Connect Grenzen: Kein direkter Zugriff auf SparkContext und RDDs. DataFrame-API und SQL funktionieren. Ein Absturz des Clients reisst den Server nicht mit.

5. Vergleich

  • Kubernetes: Pods pro Anwendung, Container-Images, Isolation per Namespace. Kein External Shuffle Service. Passt, wenn die Plattform schon Kubernetes ist.
  • YARN: klassisch mit Hadoop/HDFS. Data Locality mit HDFS, External Shuffle Service im NodeManager. Weniger üblich in Cloud-Plattformen.
  • Standalone: eigener Master und Worker von Spark. Einfach, aber Spark-only. Hat einen REST-Submission-Endpunkt (wenn aktiviert).
  • Managed (Databricks, Synapse, EMR, Dataproc): Cluster-Betrieb fällt weg. Dafür Kosten pro Nutzung und Bindung an einen Anbieter.
  • Spark Operator (Kubeflow): beschreibt eine Anwendung als SparkApplication-CRD in YAML. Gut für GitOps, statt spark-submit per Skript.
  • Client Mode vs Cluster Mode: Client: interaktiv, Logs lokal, Driver stirbt mit dem Client. Cluster: robust, Driver im Cluster, gut für geplante Jobs.
  • Klassisch vs Spark Connect: Klassisch: Client = Driver, volle API. Connect: Client getrennt vom Driver, nur DataFrame/SQL, leichter und stabiler für Notebooks und Apps.

6. In der Produktion

  1. Driver OOM durch collect(): Alle Daten fliessen in den Driver. Lösung: Ergebnis schreiben statt sammeln, take(n), oder spark.driver.maxResultSize als Schutz.
  2. Executor-Pod OOMKilled (137): Nicht der Heap, sondern der Pod ist voll. Ursache oft Python-Worker oder Off-Heap-Speicher. Lösung: spark.executor.memoryOverhead erhöhen.
  3. Executors bleiben in Pending: Kein Node hat genug CPU oder RAM. Lösung: Requests passend setzen, Node-Autoscaler (z. B. Karpenter), Quota im Namespace prüfen.
  4. Executors verlieren Shuffle-Daten: Ein Node wird entfernt (Spot, Autoscaler), die Shuffle-Dateien sind weg. Spark rechnet die vorige Stage neu. Lösung: Decommissioning mit Shuffle-Migration oder PVC-basierte Shuffle-Speicher.
  5. Executors finden den Driver nicht: Im Client Mode fehlt der Headless Service oder eine NetworkPolicy blockiert die Ports. Lösung: Service anlegen, Driver-Ports freigeben.
  6. Kleiner Job, grosser Overhead: Pod-Start und JVM-Start kosten Sekunden bis Minuten. Lösung: Arbeit bündeln statt viele Mini-Jobs zu starten.

7. Diagnose: Werkzeuge und Befehle

  • Spark UI (Port 4040 am Driver): Tab Executors zeigt Cores, Speicher, GC-Zeit, fehlgeschlagene Tasks. Auf Kubernetes: kubectl port-forward <driver-pod> 4040:4040.
  • Spark History Server: UI nach Job-Ende. Braucht spark.eventLog.enabled=true und ein gemeinsames Log-Verzeichnis.
  • kubectl get pods -l spark-role=executor, kubectl describe pod: Status, Events, OOMKilled, FailedScheduling.
  • kubectl logs <driver-pod>: Driver-Log mit Stacktraces und Task-Fehlern.
  • spark.sparkContext.getConf().getAll(): alle wirksamen Einstellungen. In der UI: Tab Environment.
  • Prometheus: spark.ui.prometheus.enabled=true liefert Executor-Metriken für Grafana.

8. Senior-Punkte

  1. Der Driver ist ein Single Point of Failure. Darum: keine grossen Daten im Driver, Jobs idempotent bauen, damit ein Neustart sicher ist.
  2. Executor-Grösse ist eine Abwägung: mehr Cores pro Executor = mehr Sharing, aber mehr GC und grössere Ausfälle. 4–5 Cores sind ein guter Start, dann messen.
  3. Kubernetes oder Managed Spark ist eine Plattform-Entscheidung. Kubernetes passt, wenn der Rest schon dort läuft und das Team es betreibt. Sonst ist Managed oft günstiger im Betrieb.
  4. PySpark ist schnell, solange Python nur steuert. Teuer wird es erst mit Python-UDFs, weil dann Daten zwischen JVM und Python wandern.
  5. Overhead-Speicher einplanen. Auf Kubernetes zählt der ganze Pod, nicht nur der Heap.
  6. Spark Connect lohnt sich für viele Clients (Notebooks, Apps) gegen einen langlebigen Server. Für Batch-Jobs im Cluster Mode bringt es wenig.

10. Fallen

  • „Die Daten fliessen durch den Driver.“ → Falsch. Executors lesen und schreiben direkt. Nur collect(), toPandas() und Broadcasts belasten den Driver.
  • „Ein Executor ist ein Node.“ → Falsch. Ein Executor ist ein Prozess. Ein Node kann mehrere Executors haben.
  • „Ein Executor führt einen Task aus.“ → Falsch. Er führt so viele Tasks gleichzeitig aus, wie er Cores hat.
  • „spark.executor.memory=8g heisst Pod mit 8 GB.“ → Falsch. Dazu kommt Overhead. Der Pod ist grösser.
  • „PySpark-Code läuft komplett in Python.“ → Falsch. DataFrame-Operationen laufen in der JVM. Python steuert nur, ausser bei UDFs.
  • „Dynamic Allocation geht auf Kubernetes nicht.“ → Falsch. Sie geht mit Shuffle Tracking statt External Shuffle Service.

11. Fragen

Welche Hauptteile hat eine Spark-Anwendung?

Einen Driver, der plant und steuert, und viele Executors, die Tasks ausführen. Ein Cluster Manager stellt die Ressourcen bereit.

Was macht der Driver genau?

Er führt main() aus, baut und optimiert den Plan, teilt Jobs in Stages und Tasks und verteilt diese. Er überwacht Executors und sammelt Ergebnisse.

Was macht ein Executor?

Er führt Tasks in Threads aus, einen pro Core. Er cached Daten und schreibt und liefert Shuffle-Dateien.

Was ist ein Task?

Die kleinste Arbeitseinheit: eine Stage auf einer Partition. Ein Task läuft auf einem Core.

Wie viele Tasks laufen gleichzeitig?

Executors × Cores pro Executor / spark.task.cpus. Beispiel: 10 × 4 / 1 = 40.

Welche Cluster Manager gibt es?

Standalone, YARN und Kubernetes. Mesos ist in Spark 4.0 entfernt. local[*] dient für Tests.

Client Mode vs Cluster Mode?

Client: Driver läuft beim Aufrufer, gut für Notebooks. Cluster: Driver läuft im Cluster, gut für Produktion, weil er nicht vom Client-Rechner abhängt.

Was passiert, wenn der Driver stirbt?

Die ganze Anwendung bricht ab. Die Executors werden beendet. Darum müssen Jobs neu startbar und idempotent sein.

Was passiert, wenn ein Executor stirbt?

Spark plant seine Tasks auf anderen Executors neu. Fehlen Shuffle-Dateien, rechnet Spark die nötige vorige Stage neu.

Wie läuft Spark auf Kubernetes?

spark-submit spricht mit der Kubernetes-API. Es entsteht ein Driver-Pod, der selbst Executor-Pods anlegt. Nach dem Ende werden die Executor-Pods gelöscht.

Was ist memoryOverhead?

Speicher ausserhalb des JVM-Heaps, z. B. für Python-Worker, Netty und native Puffer. Auf Kubernetes zählt er zum Pod-Limit.

Wie arbeitet PySpark mit der JVM zusammen?

Im Driver steuert Python die JVM über Py4J. DataFrame-Code läuft in der JVM. Nur UDFs und RDD-Lambdas starten Python-Worker auf den Executors.

Was ist Spark Connect?

Eine Client-Server-Architektur seit 3.4. Der Client schickt ungelöste logische Pläne per gRPC an den Server. Er braucht keine JVM und stört den Server bei einem Absturz nicht.

Was ist Dynamic Allocation?

Spark passt die Zahl der Executors an die Last an. Auf Kubernetes braucht es Shuffle Tracking, weil es keinen External Shuffle Service gibt.

Wie viele Cores pro Executor sind sinnvoll?

Meist 4–5. Weniger verhindert Sharing von Cache und Broadcasts. Mehr führt zu langen GC-Pausen und I/O-Engpässen.

Was ist Data Locality?

Der Scheduler schickt einen Task bevorzugt dorthin, wo seine Daten schon liegen. Bei Object Stores wie S3 oder ADLS spielt das kaum eine Rolle.

Warum ist collect() gefährlich?

Alle Zeilen gehen in den Driver-Speicher. Bei grossen Daten gibt es einen Driver-OOM. Besser schreiben oder take(n).

Was ist die SparkSession?

Der Einstiegspunkt für DataFrames und SQL seit Spark 2.0. Sie enthält den SparkContext und die Konfiguration.

Szenario: Executor-Pods enden mit Exit-Code 137, die Spark UI zeigt aber wenig Heap-Nutzung. Was ist los?

Kubernetes hat den Pod wegen des Pod-Limits getötet (OOMKilled). Der Speicher ausserhalb des Heaps war zu gross, oft Python-Worker. Lösung: memoryOverhead erhöhen oder Python-UDFs reduzieren.

Szenario: Der Job startet, aber Executor-Pods bleiben auf Pending. Was prüfen Sie?

kubectl describe pod: oft FailedScheduling wegen zu wenig CPU/RAM oder Namespace-Quota. Lösung: Requests anpassen, Autoscaler prüfen, Quota erhöhen.

Szenario: Ein Team will Notebooks direkt gegen den Produktions-Cluster laufen lassen. Was raten Sie?

Spark Connect gegen einen eigenen Server statt Client Mode pro Notebook. Der Client braucht keine JVM, und ein Absturz trifft den Server nicht. Dazu Ressourcen-Quotas und eigene Namespaces.
