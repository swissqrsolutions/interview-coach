Spark-Speicher und OutOfMemory

Kern: Spark teilt den Speicher eines Executors in Heap (JVM) und Overhead (alles ausserhalb des Heaps). Im Heap teilen sich Execution (Shuffle, Join, Sort) und Storage (Cache) einen gemeinsamen Bereich, das Unified Memory. OOM heisst entweder Heap voll (Java-Fehler) oder Container-Limit überschritten (Kubernetes tötet den Pod).

Antwort-Muster

Frage: Warum bekommt ein Spark-Job einen OutOfMemory, und wie unterscheiden Sie die Fälle?

  1. Mechanismus: Der Executor-Heap teilt sich in Execution und Storage. Dazu kommt Overhead ausserhalb des Heaps. OOM ist entweder Heap voll oder Pod über dem Limit.
  2. Zahl: memory.fraction ist 0.6 von (Heap − 300 MB). Der Overhead ist standardmässig 10 %, mindestens 384 MiB.
  3. Trade-off: Mehr Speicher kostet auf jedem Knoten Geld und verschiebt das Problem. Spill ist langsam, verhindert aber OOM.
  4. Produktion: Ich kläre zuerst, ob es Driver, Heap oder Container ist. Bei PySpark erhöhe ich den Overhead und prüfe Skew und collect() im Code.

1. Die Reise eines Tasks bis zum OOM

  1. Task startet: Ein Join-Task braucht Platz für seine Hash-Tabelle. Er fordert Execution Memory an. Jeder Task bekommt zwischen 1/(2N) und 1/N des Execution-Bereichs, N = laufende Tasks.
  2. Leihen: Ist Execution voll, leiht es sich Platz von Storage. Gecachte Blöcke werden verdrängt, aber nur bis zur geschützten Grenze (storageFraction).
  3. Spill: Reicht es immer noch nicht, schreibt der Sort- oder Aggregations-Operator Teile auf die lokale Disk. Der Task wird langsamer, stürzt aber nicht ab.
  4. Heap-OOM: Manche Daten kann Spark nicht spillen. Beispiel: eine einzelne riesige Zeile, ein collect_list über Millionen Werte, eigene Objekte im User Memory. Dann kommt java.lang.OutOfMemoryError: Java heap space.
  5. Container-OOM: Der Python-Worker eines Pandas UDF lädt einen grossen Batch. Er lebt im Overhead, nicht im Heap. Überschreitet der Pod sein Limit, tötet der Linux-Kernel ihn. Kubernetes zeigt OOMKilled, Exit Code 137.
  6. Folge: Der Driver verliert den Executor und plant die Tasks neu. Nach 4 Fehlversuchen (spark.task.maxFailures) bricht der Job ab.

2. Aufbau

  1. JVM Heap (spark.executor.memory): Speicher der Java-Objekte. Beispiel: 8 GB.
  2. Reserved Memory: 300 MB fest für Spark-Interna.
  3. Unified Memory (spark.memory.fraction = 0.6): gemeinsamer Bereich für Execution und Storage. Bei 8 GB sind das ca. 4,6 GB.
  4. Execution: Puffer für Shuffle, Join, Sort und Aggregation. Beispiel: die Hash-Tabelle eines Joins.
  5. Storage: gecachte DataFrames und Broadcast-Variablen. spark.memory.storageFraction = 0.5 davon ist vor Verdrängung geschützt.
  6. User Memory: die übrigen 40 %. Hier liegen eigene Datenstrukturen und Spark-Metadaten.
  7. memoryOverhead: alles ausserhalb des Heaps. Dazu gehören die Python-Worker von PySpark, wenn spark.executor.pyspark.memory nicht gesetzt ist.
  8. Pod-Limit: Kubernetes setzt das Limit auf die Summe. Wer darüber geht, wird vom Kernel getötet.

3. Details, die Interviewer fragen

  1. Unified Memory Model (seit Spark 1.6): Execution und Storage teilen sich einen Bereich. Vorher waren beide fest getrennt.
  2. Wer verdrängt wen: Execution kann Storage verdrängen, bis Storage auf storageFraction schrumpft. Storage kann Execution nie verdrängen. Der Tuning Guide nennt als Grund nur Komplexität in der Implementierung.
  3. spark.memory.fraction (0.6): Das ist der Anteil von (Heap − 300 MB) für Unified Memory. Niedriger heisst mehr Spill und mehr User Memory.
  4. Spill: Sort, Hash-Aggregation und Sort-Merge Join schreiben Daten auf lokale Disk, wenn Execution voll ist. In der UI sieht man Spill (Memory) und Spill (Disk).
  5. Off-Heap (spark.memory.offHeap.enabled, false): Tungsten legt Execution- und Storage-Daten ausserhalb des Heaps ab. Das gibt weniger GC. Aber offHeap.size muss ins Pod-Limit passen.
  6. memoryOverhead: Der Standard ist executorMemory × 0.10, mindestens 384 MiB. Für Kubernetes non-JVM-Jobs (PySpark) ist der Faktor 0.40.
  7. spark.executor.pyspark.memory: Es begrenzt den Python-Speicher pro Executor. Es wird zum Pod-Request addiert. Ohne Wert teilt sich Python den Overhead.
  8. Driver-OOM: Ursachen sind collect(), toPandas() und das Bauen von Broadcast-Tabellen. Auch sehr viele Partitionen oder Dateien (Metadaten) und sehr grosse Pläne gehören dazu.
  9. Executor-OOM: Ursachen sind eine skewed Partition, zu grosse Partitionen, collect_list und riesige Zeilen. Auch ein Broadcast, der für jeden Executor zu gross ist, und zu viele Cores pro Executor gehören dazu.
  10. Cores pro Executor: Mehr Cores heisst mehr parallele Tasks, also weniger Speicher pro Task. 4–5 Cores pro Executor ist ein häufiger Kompromiss.
  11. GC overhead limit exceeded: Die JVM verbringt fast nur noch Zeit mit Garbage Collection. Das ist ein Heap-Problem wie OOM.
  12. Cache und Speicher: cache() auf DataFrames nutzt standardmässig Speicher und Disk (MEMORY_AND_DISK-Familie). Gecachte Blöcke werden bei Druck verdrängt. Es gibt kein OOM.

4. Fallen

  • „spark.executor.memory=8g heisst, der Pod braucht 8 GB.“ → Falsch. Dazu kommen Overhead, eventuell Off-Heap und pyspark.memory.
  • „OOMKilled ist ein Java-Heap-Problem.“ → Falsch. Der Kernel tötet den Container wegen des Limits. Ursache ist meist Speicher ausserhalb des Heaps.
  • „Storage kann Execution verdrängen.“ → Falsch. Nur umgekehrt.
  • „Spill ist ein Fehler.“ → Falsch. Spill verhindert OOM. Er macht den Job nur langsamer.
  • „maxResultSize=0 löst das Problem.“ → Falsch. Dann stirbt der Driver-Heap statt eines sauberen Abbruchs.
  • „Python-UDFs nutzen den Executor-Heap.“ → Falsch. Python-Worker sind eigene Prozesse im Overhead.

5. Selbsttest

Warum?

Wer darf wen verdrängen?

Execution darf Storage bis zur Grenze storageFraction verdrängen. Storage darf Execution nie verdrängen.

Was heisst OOMKilled mit Exit Code 137?

Der Linux-Kernel hat den Container getötet, weil er sein Memory Limit überschritten hat. Es gibt dann keinen Java-Fehler im Log.

Warum brauchen PySpark-Jobs mehr Overhead?

Python-Worker sind eigene Prozesse ausserhalb des JVM-Heaps. Pandas UDFs und Arrow-Batches brauchen dort Speicher.

Wie innen?

Wie ist der Executor-Speicher aufgeteilt?

Heap: 300 MB reserviert, 60 % des Rests Unified Memory (Execution und Storage), 40 % User Memory. Dazu kommt Overhead ausserhalb des Heaps.

Was ist das Unified Memory Model?

Execution und Storage teilen sich einen Bereich und leihen sich gegenseitig Platz. Seit Spark 1.6.

Was ist Execution Memory?

Speicher für Shuffle, Join, Sort und Aggregation während eines Tasks.

Was ist Storage Memory?

Speicher für gecachte Daten und Broadcast-Variablen.

Was ist Spill?

Ist Execution Memory voll, schreiben Sort und Aggregation Teile auf lokale Disk. Langsam, aber kein Absturz.

Was macht spark.driver.maxResultSize?

Es begrenzt die Grösse aller Ergebnisse einer Aktion beim Driver, Standard 1 GB. Darüber bricht der Job sauber ab.

Was macht spark.executor.pyspark.memory?

Es begrenzt den Python-Speicher pro Executor und wird zum Pod-Request addiert. Ohne Wert teilt sich Python den Overhead.

Was ist Off-Heap Memory in Spark?

Tungsten-Speicher ausserhalb des Heaps, wenn offHeap.enabled an ist. Weniger GC, muss aber ins Container-Limit passen.

Zahlen

Was macht spark.memory.fraction?

Es legt den Anteil von (Heap − 300 MB) für Unified Memory fest, Standard 0,6.

Was ist memoryOverhead?

Speicher ausserhalb des Heaps: JVM-Interna, Netty, Python-Worker, native Puffer. Standard 10 %, mindestens 384 MiB; PySpark auf Kubernetes 40 %.

Wie gross wird ein Executor-Pod?

executor.memory + memoryOverhead + offHeap.size + pyspark.memory. Spark setzt Request und Limit gleich.

Vergleich

Wie unterscheiden Sie Heap-OOM und Container-OOM?

Heap-OOM: OutOfMemoryError im Executor-Log. Container-OOM: OOMKilled und Exit 137 in kubectl describe pod.

Driver-OOM vs Executor-OOM?

Driver-OOM: Heap des Drivers voll, meist Code wie collect, toPandas oder Broadcast, der ganze Job stirbt. Executor-OOM: meist Skew oder grosse Partitionen, Spark wiederholt den Task.

On-Heap vs Off-Heap?

On-Heap ist einfach und Standard. Off-Heap spart GC, muss aber selbst im Container-Limit eingeplant werden.

Spill vs OOM?

Spill ist kein Fehler, nur langsam. Er zeigt zu grosse Partitionen oder zu wenig Execution Memory. OOM bricht den Task ab.

Produktion

Was verursacht Driver-OOM?

collect(), toPandas(), grosse Broadcasts, sehr viele Partitionen oder Dateien und grosse Pläne.

Was verursacht Executor-OOM?

Skew, zu grosse Partitionen, collect_list, riesige Zeilen, zu grosse Broadcasts oder zu viele Tasks pro Executor.

Was zeigt GC Time in der Spark UI?

Wie viel Task-Zeit in Garbage Collection geht. Über ca. 10 % deutet auf Speicherdruck hin.

Szenario: Ein PySpark-Job auf AKS verliert immer wieder Executors, im Log steht kein OutOfMemoryError. Was prüfen Sie?

kubectl describe pod auf OOMKilled/137. Dann Python-Speicher: UDFs, Arrow-Batch-Grösse. Lösung: memoryOverhead oder pyspark.memory erhöhen, UDFs durch eingebaute Funktionen ersetzen.

Szenario: Nur ein Executor stirbt mit OOM, immer in derselben Stage. Was vermuten Sie?

Skew: eine Partition ist viel grösser. Stage-Metriken prüfen (Max vs Median Shuffle Read), dann Skew beheben statt Speicher erhöhen.

Design

Wie viele Cores pro Executor?

Oft 4–5. Mehr Cores heissen weniger Execution Memory pro Task und mehr GC-Druck.

Wie holen Sie grosse Ergebnisse sicher aus Spark?

In Dateien oder eine Tabelle schreiben. Für kleine Teile limit() oder toLocalIterator().

Szenario: Der Job bricht mit "bigger than spark.driver.maxResultSize" ab. Ein Kollege will das Limit auf 0 setzen. Was sagen Sie?

Dann stirbt der Driver-Heap später. Besser: kein collect() auf grosse Daten, sondern schreiben oder vorher aggregieren.

Mehr

Gerüst

  • Warum? Es gibt drei OOM-Arten mit drei Lösungen: Driver, Executor-Heap, Container. Mehr Speicher ist die letzte Lösung.
  • Wie innen? Execution und Storage teilen sich das Unified Memory. Execution darf Storage verdrängen, Storage nie Execution. Reicht der Speicher nicht, gibt es Spill statt OOM.
  • Zahlen memory.fraction 0.6 von (Heap − 300 MB). storageFraction 0.5. Overhead 10 %, mindestens 384 MiB, bei PySpark auf Kubernetes 40 %.
  • Vergleich Driver-OOM = Code (collect). Heap-OOM = Skew oder grosse Partitionen. OOMKilled (137) = Pod über Limit. Spill = nur langsam.
  • Produktion Driver-OOM durch collect(), PySpark-Pod OOMKilled, Skew-Task, Broadcast zu gross, lokale Disk voll.
  • Design Erst die Art klären. 4–5 Cores pro Executor. Defaults für memory.fraction belassen. Request = Limit.

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Spark 3.5/4.x; Zahlen nach den dokumentierten Standardwerten berechnet. Namespace, Pod- und Dateinamen sind Beispiele.

  1. Unified Memory = (8192 − 300) × 0,6 = 4735 MiB. Nur hier spillen Shuffle und Sort.
  2. Overhead: Für PySpark auf Kubernetes ist der Faktor 0,4. Für JVM-Jobs 0,1, mindestens 384 MiB.
  3. Pod-Limit: Spark setzt Request und Limit für Speicher gleich. Darum gibt es kein Überbuchen.
  4. maxResultSize: collect() und toPandas() holen alles zum Driver. Die 1-GB-Grenze bricht den Job sauber ab, bevor der Driver-Heap platzt.
  5. OOMKilled / 137: Der Kernel hat den Container getötet. Im Spark-Log steht dann kein OutOfMemoryError, nur ein verlorener Executor.

Vergleich

  • Driver-OOM: Heap des Drivers voll. Ursache meist Code (collect, toPandas, Broadcast). Der ganze Job stirbt.
  • Executor Heap-OOM: OutOfMemoryError im Executor-Log. Ursache meist Skew oder grosse Partitionen. Spark wiederholt den Task.
  • Container-OOM (OOMKilled): Pod über Limit, Exit 137, kein Java-Fehler. Ursache meist Python, Arrow, native Puffer. Lösung: Overhead oder pyspark.memory.
  • Spill: kein Fehler, nur langsam. Zeichen für zu grosse Partitionen oder zu wenig Execution Memory.
  • On-Heap vs Off-Heap: On-Heap ist einfach und Standard. Off-Heap spart GC, muss aber selbst im Container-Limit eingeplant werden.

In der Produktion

  1. collect() auf grosse Daten: Driver-OOM oder maxResultSize-Fehler. Lösung: write statt collect, limit, oder toLocalIterator().
  2. maxResultSize hochsetzen: Der Fehler verschwindet, dann stirbt der Driver-Heap. Lösung: Ursache im Code beheben, nicht nur das Limit.
  3. PySpark-Executor OOMKilled: Pandas UDFs oder Python-Objekte sprengen den Overhead. Lösung: memoryOverhead erhöhen, spark.executor.pyspark.memory setzen, kleinere Arrow-Batches (spark.sql.execution.arrow.maxRecordsPerBatch), eingebaute Funktionen statt UDFs.
  4. Executor-OOM durch Skew: ein Task mit 30 GB Shuffle Read. Lösung: Skew beheben, mehr Partitionen. Mehr Speicher verschiebt nur das Problem.
  5. Broadcast zu gross: Driver baut die Tabelle, jeder Executor hält eine Kopie. Lösung: Threshold senken, Hint entfernen.
  6. Pod passt auf keinen Knoten: Ein Executor mit 64 GB Request findet keinen Knoten und bleibt Pending. Lösung: kleinere Executors oder einen Knotenpool, der passt; ein Autoscaler wie Karpenter wählt Knoten nach den Pod-Requests.
  7. Lokale Disk voll durch Spill: Spill und Shuffle-Dateien liegen im Pod (emptyDir). Lösung: genug ephemeral Storage oder ein Volume für spark.local.dir.

Diagnose: Werkzeuge und Befehle

  • Spark UI, Stages-Tab: Spill (Memory/Disk), GC Time, Shuffle Read pro Task. Max vs Median zeigt Skew.
  • Spark UI, Executors-Tab: Storage Memory, GC Time, Failed Tasks, Gründe für verlorene Executors.
  • Spark UI, Storage-Tab: welche DataFrames gecacht sind und wie viel davon auf Disk liegt.
  • kubectl describe pod <executor>: Reason: OOMKilled, Exit Code: 137.
  • kubectl get pod <executor> -o jsonpath='{.spec.containers[0].resources}': Request und Limit prüfen.
  • kubectl logs <executor> --previous: Log des gestorbenen Containers, z. B. OutOfMemoryError.
  • Prometheus/Grafana: container_memory_working_set_bytes gegen das Limit, Pod-Restarts.
  • spark.executor.extraJavaOptions=-XX:+HeapDumpOnOutOfMemoryError: Heap Dump bei JVM-OOM.

Senior-Punkte

  1. Zuerst die Art des OOM klären: Driver, Executor-Heap oder Container. Jede hat eine andere Lösung.
  2. Speicher erhöhen ist die letzte Lösung. Erst Partitionen, Skew und collect prüfen. Mehr Speicher kostet auf jedem Knoten Geld.
  3. PySpark braucht Overhead. Python lebt ausserhalb des Heaps. Darum ist der Standard-Faktor auf Kubernetes 0,4.
  4. Kleine bis mittlere Executors (4–5 Cores, 8–16 GB) sind meist robuster als riesige. Sie passen auf mehr Knoten und haben weniger GC-Pausen.
  5. Request = Limit: Spark-Pods überbuchen keinen Speicher. Das macht OOMKilled vorhersagbar, aber die Rechnung muss stimmen.
  6. Defaults für memory.fraction belassen. Die Doku empfiehlt es. Lieber Datenlayout und Partitionen ändern.
