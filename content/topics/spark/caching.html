cache und persist

Kern: cache() und persist() sagen Spark, das Ergebnis eines DataFrames nach der ersten Berechnung auf den Executors zu behalten. Das löst das Problem, dass Spark wegen Lazy Evaluation bei jeder Action den ganzen Plan ab der Quelle neu rechnet. Caching lohnt sich nur, wenn ein teures Zwischenergebnis mehrfach genutzt wird.

1. Wo sitzt der Cache?

  1. CacheManager (im Driver): Er merkt sich, welche logischen Pläne gecacht sind. Neue Abfragen mit gleichem Teilplan nutzen den Cache automatisch.
  2. Unified Memory: Execution (Shuffle, Joins, Sort) und Storage (Cache) teilen sich einen Bereich. Execution darf Cache-Blöcke verdrängen.
  3. BlockManager: Er speichert pro Partition einen Block auf dem Executor. Fehlt Platz, fliegen alte Blöcke per LRU (least recently used) raus.
  4. Lokale Disk: Bei MEMORY_AND_DISK kommen nicht passende Partitionen auf die Disk statt neu gerechnet zu werden.
  5. Off-Heap: mit OFF_HEAP ausserhalb des JVM-Heaps; braucht aktivierten Off-Heap-Speicher.
  6. Storage-Tab: Die Spark UI zeigt jeden Cache mit Grösse im Speicher und auf Disk.

2. Die Reise eines gecachten DataFrames

  1. cache(): markiert den Plan. Es passiert noch nichts. cache() ist lazy.
  2. Erste Action: Spark rechnet den Plan. Jede Partition wird beim Rechnen als Block gespeichert.
  3. Zweite Action: Der Plan enthält jetzt InMemoryTableScan. Spark liest aus dem Cache statt aus der Quelle.
  4. Verdrängt oder verloren: Fehlt ein Block (LRU, Executor tot), rechnet Spark nur diese Partition über die Lineage neu.
  5. unpersist(): gibt den Speicher frei. Ohne das bleibt der Cache, bis LRU ihn verdrängt oder die App endet.

3. Beispiel: wie oft wird die Quelle gelesen?

# Modell der Lineage: ein "DataFrame" ist ein Rezept; jede Action rechnet es neu
reads = 0
def source():
    global reads; reads += 1                 # zählt, wie oft die Quelle gelesen wird
    return [(d, v) for d in range(1, 31) for v in range(1000)]

class DF:
    def __init__(self, fn): self.fn, self.cached = fn, None
    def filter(self, p): return DF(lambda: [r for r in self.collect() if p(r)])
    def cache(self): self.keep = True; return self      # lazy: noch nichts passiert
    def collect(self):
        if self.cached is not None: return self.cached
        rows = self.fn()
        if getattr(self, "keep", False): self.cached = rows
        return rows

for use_cache in (False, True):
    reads = 0
    silver = DF(source).filter(lambda r: r[1] % 7 == 0)
    if use_cache: silver.cache()
    print(f"cache={use_cache}: nach cache() gelesen={reads}", end="  ")
    n1 = len(silver.filter(lambda r: r[0] <= 15).collect())   # Action 1
    n2 = len(silver.filter(lambda r: r[0] > 15).collect())    # Action 2
    n3 = len(silver.collect())                                 # Action 3
    print(f"Actions: {n1}, {n2}, {n3} | Quelle gelesen: {reads}x")

cache=True: nach cache() gelesen=0  Actions: 2145, 2145, 4290 | Quelle gelesen: 1x

4. Details, die Interviewer fragen

  1. cache vs persist: cache() ist persist() mit Standard-Level. persist(level) wählt das Level selbst.
  2. Standard-Level: DataFrame/Dataset: MEMORY_AND_DISK in Scala, in PySpark MEMORY_AND_DISK_DESER (seit 3.0 an Scala angeglichen). RDD: MEMORY_ONLY.
  3. Levels: MEMORY_ONLY, MEMORY_AND_DISK, MEMORY_ONLY_SER, MEMORY_AND_DISK_SER, DISK_ONLY, OFF_HEAP, dazu _2 (zwei Kopien auf zwei Knoten).
  4. Spalten-Cache: DataFrames werden im Cache spaltenweise und komprimiert gespeichert (spark.sql.inMemoryColumnarStorage.compressed = true, Batches von 10 000 Zeilen). Abfragen lesen nur nötige Spalten.
  5. Lazy vs eager: df.cache() ist lazy. SQL CACHE TABLE t ist eager; CACHE LAZY TABLE t ist lazy.
  6. Plan-Gleichheit: Der Cache greift, wenn ein späterer Plan den gecachten Teilplan enthält. Ein leicht anderer Plan (anderer Filter vor dem Cache) trifft ihn nicht.
  7. Veraltete Daten: Ein Cache ist ein Schnappschuss. Ändert sich die Iceberg-Tabelle, sieht der Cache das nicht. REFRESH TABLE oder unpersist().
  8. cache vs checkpoint: checkpoint() schreibt in zuverlässigen Speicher und schneidet die Lineage ab. localCheckpoint() schreibt lokal, schneller, aber nicht ausfallsicher.
  9. Speicher-Konkurrenz: Cache nutzt Storage Memory. Execution kann Cache verdrängen, aber nur bis zu spark.memory.storageFraction (Standard 0.5) geschützt.
  10. Kosten: Ein Cache-Lauf ist teurer als ein normaler Lauf, weil Spark zusätzlich speichert. Er lohnt sich erst ab der zweiten Nutzung.

5. Vergleich

  • cache/persist: schnell, im Cluster, Lineage bleibt. Weg, wenn die App endet.
  • checkpoint: zuverlässig, Lineage abgeschnitten, langsamer. Gut für sehr lange Pläne, z. B. Schleifen.
  • Zwischentabelle schreiben (z. B. Iceberg tmp): überlebt die App, für andere Jobs nutzbar, sauber debuggbar. Kostet Schreibzeit und Speicher.
  • Broadcast: kein Cache, sondern eine kleine Tabelle an alle Executors für Joins.

6. In der Produktion

  1. Job wird mit cache() langsamer: Der DataFrame wird nur einmal genutzt. Lösung: Cache entfernen.
  2. Executor OOM oder viel Spill: Grosser Cache nimmt Execution den Speicher. Lösung: MEMORY_AND_DISK, kleiner cachen (nur nötige Spalten, nach Filter), unpersist().
  3. Alte Zahlen im Report: In einer langlebigen Session (Notebook, Thrift Server) liegt ein alter Cache. Lösung: REFRESH TABLE, spark.catalog.clearCache().
  4. Cache greift nicht: Plan unterscheidet sich, oder cache() wurde auf einem anderen DataFrame-Objekt aufgerufen. Lösung: explain() auf InMemoryTableScan prüfen.
  5. Executor-Verlust auf Kubernetes: Gecachte Blöcke sind weg, die Neuberechnung dauert. Lösung: wichtige Zwischenstände als Tabelle schreiben.

7. Diagnose

  • Storage-Tab der Spark UI: Name, Level, Anteil gecacht, Grösse im Speicher und auf Disk.
  • df.explain(): InMemoryRelation und InMemoryTableScan zeigen den Cache im Plan.
  • df.storageLevel und spark.catalog.isCached("t").
  • Executors-Tab: „Storage Memory“ pro Executor.
  • Stages-Tab: „skipped“ Stages oder kürzere Stages nach dem ersten Lauf zeigen Wiederverwendung.

8. Senior-Punkte

  1. Erst messen, dann cachen. Caching ist kein Standard-Schritt.
  2. Cachen, was teuer und mehrfach genutzt ist: nach Joins und Filtern, vor Verzweigungen.
  3. Immer unpersist, wenn der Teil fertig ist. Speicher ist für Shuffles wichtiger.
  4. Für Batch-Pipelines lieber Zwischentabellen als grosse Caches: wiederholbar, debuggbar, idempotent.
  5. Caches in langen Sessions sind ein Konsistenz-Risiko. Ergebnisse können still veralten.

10. Fallen

  • „cache() rechnet sofort.“ → Falsch. Erst die nächste Action füllt den Cache.
  • „Cache macht jeden Job schneller.“ → Falsch. Bei einmaliger Nutzung kostet er nur.
  • „Gecachte Daten sind sicher gespeichert.“ → Falsch. Sie können verdrängt werden oder mit dem Executor verschwinden.
  • „Der Cache sieht neue Daten in der Tabelle.“ → Falsch. Er ist ein Schnappschuss.
  • „checkpoint und cache sind gleich.“ → Falsch. checkpoint schneidet die Lineage ab und schreibt zuverlässig.

11. Fragen

Was machen cache() und persist()?

Sie markieren einen DataFrame, damit Spark das Ergebnis nach der ersten Berechnung auf den Executors behält.

Was ist der Unterschied zwischen cache und persist?

cache nutzt das Standard-Level. persist erlaubt ein eigenes Level, z. B. DISK_ONLY.

Welches Standard-Level hat df.cache()?

MEMORY_AND_DISK für DataFrames (PySpark: MEMORY_AND_DISK_DESER). RDD.cache nutzt MEMORY_ONLY.

Ist cache() eine Action?

Nein, es ist lazy. Erst die nächste Action füllt den Cache.

Wann lohnt sich Caching?

Wenn ein teures Zwischenergebnis mehrfach genutzt wird, z. B. für mehrere Aggregationen oder iterative Algorithmen.

Wann schadet Caching?

Bei einmaliger Nutzung oder wenn der Cache Execution-Speicher wegnimmt und Spill oder OOM erzeugt.

Was passiert, wenn ein gecachter Block verloren geht?

Spark rechnet nur die betroffene Partition über die Lineage neu. Das Ergebnis bleibt korrekt.

Wie speichert Spark einen DataFrame-Cache?

Spaltenweise und komprimiert in Batches. Abfragen lesen nur die nötigen Spalten.

MEMORY_ONLY oder MEMORY_AND_DISK?

MEMORY_ONLY rechnet fehlende Partitionen neu. MEMORY_AND_DISK legt sie auf Disk; besser, wenn Neuberechnung teuer ist.

Was bedeutet _2 bei einem Storage Level?

Jede Partition liegt auf zwei Knoten. Schneller nach Ausfall, aber doppelter Speicher.

cache oder checkpoint?

cache behält die Lineage und ist schnell. checkpoint schreibt zuverlässig und schneidet die Lineage ab, gut bei sehr langen Plänen.

Ist CACHE TABLE lazy?

Nein, CACHE TABLE ist eager. CACHE LAZY TABLE ist lazy.

Wie sehen Sie, ob der Cache genutzt wird?

Im Plan steht InMemoryTableScan. Die Spark UI zeigt den Cache im Storage-Tab.

Wie geben Sie den Cache frei?

Mit df.unpersist(), spark.catalog.uncacheTable oder clearCache für alles.

Warum sieht ein Cache neue Daten nicht?

Er speichert das Ergebnis zum Zeitpunkt der Berechnung. Neue Daten braucht REFRESH TABLE oder einen neuen Cache.

Szenario: Ein Job wird nach Einbau von cache() langsamer. Warum?

Der DataFrame wird nur einmal genutzt, und das Speichern kostet zusätzlich. Oder der Cache nimmt Shuffles den Speicher. Cache entfernen und messen.

Szenario: Im Notebook zeigt ein Report gestrige Zahlen, obwohl die Tabelle neu ist. Ursache?

Ein alter Cache in der langlebigen Session. REFRESH TABLE oder clearCache und neu rechnen.

Szenario: Ein iterativer Job wird mit jeder Runde langsamer, der Plan wird riesig. Was tun Sie?

Die Lineage wächst. Alle paar Runden checkpoint() oder eine Zwischentabelle schreiben, um den Plan abzuschneiden.
