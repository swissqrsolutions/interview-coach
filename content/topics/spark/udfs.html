UDFs vs eingebaute Funktionen, Pandas UDFs

Spark · Tier 2 · Quellen: Apache Spark 4.3 Docs (PySpark: Python UDFs, Arrow in PySpark, Pandas UDFs, Python UDTFs), Spark 4.2.0 Release Notes (Arrow-optimierte Python UDFs standardmässig an), Spark-Quellcode SQLConf (v4.3.0)

Kern: Eine UDF (User-Defined Function) ist eigener Code, den Spark pro Zeile oder pro Batch aufruft. Sie löst Logik, die eingebaute Funktionen nicht können. Der Preis: Für den Optimizer ist sie eine Black Box, und Python-UDFs laufen in einem eigenen Python-Prozess, sodass jede Zeile zwischen JVM und Python übertragen wird; Pandas UDFs machen das per Arrow batchweise und viel billiger.

1. Wo läuft eine Python-UDF?

  1. Driver: Er serialisiert deine Python-Funktion (Pickle) und schickt sie mit dem Plan an die Executors.
  2. JVM-Teil: Scan, Filter und eingebaute Funktionen laufen in der JVM mit Whole-Stage Codegen.
  3. Python-Knoten im Plan: BatchEvalPython (klassisch, Pickle) oder ArrowEvalPython (Arrow-Batches).
  4. Python Worker: ein eigener Prozess pro Task-Slot. Er bekommt Daten, ruft deine Funktion und schickt Ergebnisse zurück.
  5. Speicher: Der Python-Prozess liegt ausserhalb des JVM-Heaps. Auf Kubernetes zählt er zum memoryOverhead des Pods.

2. Die Reise einer Zeile durch eine UDF

  1. UnsafeRow: Die Zeile liegt binär in der JVM, im Tungsten-Format.
  2. Serialisieren: Klassisch per Pickle pro Zeile. Mit Arrow als spaltenweiser Batch (Standard 10 000 Zeilen pro Batch).
  3. Socket: Die Daten gehen über einen lokalen Socket an den Python-Worker.
  4. Funktion: Python ruft deine Funktion. Bei Pandas UDFs einmal pro Batch mit einer pandas.Series.
  5. Zurück: Das Ergebnis geht denselben Weg zurück.
  6. Deserialisieren: Die JVM baut wieder Zeilen daraus.
  7. Weiter: Der Rest des Plans läuft in der JVM. Der Optimizer konnte nicht in die UDF hineinsehen.

3. Beispiel: eingebaut gegen UDF

import sqlite3, time
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE trade(id INTEGER PRIMARY KEY, price REAL, qty REAL)")
db.executemany("INSERT INTO trade(price, qty) VALUES (?, ?)",
               [(50 + i % 100, 1 + i % 7) for i in range(1_000_000)])
db.create_function("py_amount", 2, lambda p, q: p * q, deterministic=True)   # "UDF"

def run(sql):
    t = time.perf_counter(); r = db.execute(sql).fetchone()[0]
    return r, round((time.perf_counter() - t) * 1000)

print("eingebaut :", run("SELECT sum(price * qty) FROM trade"))
print("Python-UDF:", run("SELECT sum(py_amount(price, qty)) FROM trade"))
# Optimizer: Filter auf Schlüssel nutzt den Index, durch eine UDF nicht
db.create_function("py_id", 1, lambda x: x, deterministic=True)
for sql in ("SELECT price FROM trade WHERE id = 42",
            "SELECT price FROM trade WHERE py_id(id) = 42"):
    plan = db.execute("EXPLAIN QUERY PLAN " + sql).fetchall()[0][3]
    print(f"{plan:<45} {run(sql)[1]} ms")
eingebaut : (397999749.0, 80)
Python-UDF: (397999749.0, 294)
SEARCH trade USING INTEGER PRIMARY KEY (rowid=?) 0 ms
SCAN trade                                    206 ms

Echte Ausgabe, Python 3.12 + sqlite3 3.49.1, 1 Mio. Zeilen. sqlite steht hier für Spark: Das Prinzip (Sprachgrenze pro Zeile, Black Box für den Optimizer) ist dasselbe. Zeiten schwanken je nach Rechner.

  1. Gleiches Ergebnis, aber die UDF ist ca. 3,7× langsamer. Der Aufruf pro Zeile über die Sprachgrenze kostet.
  2. Mit id = 42 nutzt der Optimizer den Primärschlüssel: SEARCH, 0 ms.
  3. Mit py_id(id) = 42 weiss er nicht, was die Funktion tut: SCAN über 1 Mio. Zeilen, 206 ms.
  4. In Spark ist es genauso: Ein Filter über eine UDF wird nicht an Parquet oder Iceberg gepusht. Partition Pruning und Min/Max-Statistiken fallen weg.

Dieselbe Logik in PySpark, drei Varianten:

from pyspark.sql import functions as F
import pandas as pd

# 1) eingebaut: Catalyst + Codegen, kein Python
df1 = df.withColumn("amount", F.col("price") * F.col("qty"))

# 2) Python UDF (seit Spark 4.2 standardmässig Arrow-optimiert)
@F.udf("double")
def amount_udf(p, q): return p * q
df2 = df.withColumn("amount", amount_udf("price", "qty"))

# 3) Pandas UDF: eine Series pro Batch
@F.pandas_udf("double")
def amount_pd(p: pd.Series, q: pd.Series) -> pd.Series: return p * q
df3 = df.withColumn("amount", amount_pd("price", "qty"))

df2.explain()

4. Details, die Interviewer fragen

  1. Arten von UDFs: Python UDF (@udf), Pandas UDF (@pandas_udf), Python UDTF (@udtf, gibt Tabellen zurück, seit 3.5), Scala/Java UDF in der JVM.
  2. Arrow-optimierte Python UDFs: seit 3.5 per useArrow=True. Seit Spark 4.2 ist spark.sql.execution.pythonUDF.arrow.enabled standardmässig true. Die Funktion bleibt zeilenweise, aber der Transport ist batchweise.
  3. Pandas UDF-Typen (über Type Hints): Series → Series (skalar), Iterator[Series] → Iterator[Series] (teure Initialisierung einmal pro Partition), Series → Skalar (Aggregation).
  4. Pandas Function APIs: mapInPandas, groupBy().applyInPandas (ganze Gruppe als DataFrame), mapInArrow.
  5. applyInPandas-Falle: Jede Gruppe muss komplett in den Speicher eines Workers passen. Eine riesige Gruppe gibt OOM.
  6. Scala-UDF: kein Prozesswechsel, aber trotzdem Black Box: keine Pushdown-Optimierung, und Konvertierung in externe Typen kostet.
  7. Determinismus: Spark nimmt an, dass UDFs deterministisch sind, und darf sie mehrfach oder umsortiert aufrufen. Zufall oder Zeit → .asNondeterministic().
  8. Null-Handling: Die UDF bekommt None. Ohne Prüfung gibt es Fehler oder falsche Werte. Eingebaute Funktionen behandeln null definiert.
  9. Rückgabetyp: Passt der deklarierte Typ nicht, liefert eine klassische Python-UDF oft still null.
  10. Speicher: Python-Worker leben ausserhalb des Heaps. spark.executor.pyspark.memory begrenzt sie; auf Kubernetes muss der Overhead reichen.

5. Vergleich

  • Eingebaute Funktionen (pyspark.sql.functions, SQL): schnellste Wahl, voll optimiert, Pushdown möglich. Immer zuerst prüfen, auch expr(), transform, aggregate für Arrays.
  • Pandas UDF: vektorisiert, gut für numerische Logik und Python-Bibliotheken. Overhead pro Batch statt pro Zeile.
  • Python UDF: einfach zu schreiben. Mit Arrow erträglich, ohne Arrow am langsamsten.
  • Scala UDF: schneller als Python, aber eigene Build-Kette; Black Box für den Optimizer bleibt.

6. In der Produktion

  1. Job 10× langsamer als erwartet: Plan zeigt BatchEvalPython. Lösung: durch eingebaute Funktionen ersetzen, sonst Pandas UDF.
  2. Executor-Pods OOMKilled ohne Java-OOM: Python-Worker brauchen Speicher ausserhalb des Heaps. Lösung: Overhead erhöhen, Batch kleiner (spark.sql.execution.arrow.maxRecordsPerBatch).
  3. Partition Pruning greift nicht: Filter über eine UDF. Lösung: Filter auf Rohspalten vor der UDF.
  4. Plötzlich nulls im Ergebnis: Rückgabetyp passt nicht oder Exception bei None. Lösung: Typen prüfen, None behandeln, Tests.
  5. Andere Ergebnisse nach Upgrade: Arrow-Optimierung ändert Typ-Umwandlungen in Randfällen. Lösung: Paritäts-Tests, notfalls Konfiguration explizit setzen.
  6. applyInPandas OOM bei einer Gruppe: Skew. Lösung: Gruppe aufteilen oder Logik als Aggregation.

7. Diagnose

  • df.explain(): BatchEvalPython, ArrowEvalPython, FlatMapGroupsInPandas zeigen Python im Plan.
  • Spark UI, SQL-Tab: Zeit und Zeilen pro Python-Knoten.
  • spark.python.profile=true und spark.sparkContext.show_profiles() bzw. seit Spark 4.0 spark.sql.pyspark.udf.profiler=perf oder memory für Profile in der UDF.
  • Pod-Metriken: Speicher des ganzen Containers gegen JVM-Heap vergleichen.

8. Senior-Punkte

  1. Erst eingebaut, dann Pandas UDF, zuletzt Python UDF. Diese Reihenfolge spart oft Faktor 10.
  2. UDFs sind Black Boxes. Filter und Joins vorher auf Rohspalten machen, damit Pushdown greift.
  3. Fachlogik in UDFs braucht Tests wie jede Bibliothek: nulls, Grenzen, Typen.
  4. Beim Portieren von .NET- oder Java-Logik: zuerst in Spark-Ausdrücke übersetzen, UDFs nur für den Rest.
  5. Speicherplanung für PySpark heisst: JVM-Heap und Python-Prozesse zusammen rechnen.

10. Fallen

  • „Eine UDF ist so schnell wie eine eingebaute Funktion.“ → Falsch. Black Box, kein Codegen, bei Python zusätzlich Prozesswechsel.
  • „Pandas UDFs laufen in der JVM.“ → Falsch. Sie laufen in Python, aber batchweise über Arrow.
  • „Spark ruft meine UDF genau einmal pro Zeile auf.“ → Falsch. Bei deterministischen UDFs darf Spark mehrfach aufrufen.
  • „Python-UDFs nutzen kein Arrow.“ → Veraltet. Seit Spark 4.2 standardmässig Arrow-optimiert.
  • „Ein Filter nach der UDF wird gepusht.“ → Falsch. Ein Filter über die UDF kommt nicht an die Quelle.

11. Fragen

Was ist eine UDF in Spark?

Eigener Code, den Spark pro Zeile oder Batch aufruft, wenn eingebaute Funktionen nicht reichen.

Warum sind Python-UDFs langsam?

Daten gehen zwischen JVM und Python-Prozess hin und her und werden serialisiert. Und der Optimizer kann nicht hineinsehen.

Was bedeutet Black Box für den Optimizer?

Catalyst kennt die Logik nicht. Kein Pushdown, keine Constant Folding, kein Codegen über die UDF hinweg.

Was ist eine Pandas UDF?

Eine vektorisierte UDF: Sie bekommt pandas-Series pro Batch über Arrow statt einzelne Zeilen per Pickle.

Was ist eine Arrow-optimierte Python UDF?

Eine normale Python UDF, deren Daten per Arrow statt Pickle übertragen werden. Seit Spark 4.2 Standard.

Woran erkennen Sie eine UDF im Plan?

An BatchEvalPython oder ArrowEvalPython, bei Gruppen an FlatMapGroupsInPandas.

Welche Pandas-UDF-Typen gibt es?

Series zu Series, Iterator zu Iterator und Series zu Skalar für Aggregationen. Der Typ kommt aus den Type Hints.

Wofür ist der Iterator-Typ gut?

Teure Initialisierung, z. B. ein Modell laden, passiert einmal pro Partition statt pro Batch.

Was macht applyInPandas?

Es gibt jede Gruppe als pandas-DataFrame an eine Funktion. Jede Gruppe muss in den Speicher passen.

Was ist eine Python UDTF?

Eine Funktion, die pro Eingabe mehrere Zeilen zurückgibt, also eine Tabelle. Seit Spark 3.5.

Sind Scala-UDFs besser?

Schneller als Python, weil kein Prozesswechsel. Aber weiterhin Black Box für den Optimizer.

Warum asNondeterministic()?

Spark nimmt Determinismus an und darf die UDF mehrfach aufrufen oder verschieben. Bei Zufall oder Zeit muss man das abschalten.

Wie gehen UDFs mit null um?

Sie bekommen None. Ohne Prüfung gibt es Fehler. Eingebaute Funktionen haben definierte null-Semantik.

Wo liegt der Speicher der Python-Worker?

Ausserhalb des JVM-Heaps, im Overhead des Containers. spark.executor.pyspark.memory kann ihn begrenzen.

Wie ersetzen Sie eine UDF durch eingebaute Funktionen?

Mit when/otherwise, regexp_extract, to_date, transform für Arrays oder expr() mit SQL. Fast jede Zeilenlogik geht so.

Szenario: Ein PySpark-Job ist zehnmal langsamer als die SQL-Version. Was prüfen Sie?

Den Plan auf BatchEvalPython. Die UDF durch eingebaute Funktionen ersetzen oder als Pandas UDF schreiben, dann messen.

Szenario: Executor-Pods sterben mit Exit 137, der Heap ist halb leer. Woran denken Sie?

An Python-Worker ausserhalb des Heaps. Overhead erhöhen oder Arrow-Batches verkleinern.

Szenario: Nach Einbau einer UDF liest der Job alle Partitionen statt einer. Warum?

Der Filter läuft über die UDF und wird nicht gepusht. Den Filter auf die Rohspalte vor die UDF legen.
