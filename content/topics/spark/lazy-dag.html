Lazy Evaluation, DAG, Jobs, Stages, Tasks

Spark · Tier 1 · Quellen: Apache Spark Docs 3.5/4.x – RDD Programming Guide (Transformations, Actions), Cluster Mode Overview (Glossary), Web UI Guide, SQL Performance Tuning (AQE), Monitoring and Instrumentation

Kern: Lazy Evaluation heisst: Spark führt Transformationen nicht sofort aus, sondern sammelt sie als Plan. Erst eine Action startet einen Job. Der Job wird an Shuffle-Grenzen in Stages geteilt, jede Stage in einen Task pro Partition.

1. Wo sitzen Job, Stage und Task?

  1. Application: ein Driver mit seinen Executors. Beispiel: ein spark-submit-Lauf.
  2. Job: die Arbeit für eine Action. Beispiel: df.count() oder df.write....
  3. Stage: ein Abschnitt des Jobs ohne Shuffle. Alle Schritte darin laufen hintereinander auf derselben Partition.
  4. Task: eine Stage auf einer Partition. Er läuft auf einem Core eines Executors.
  5. DAG (Directed Acyclic Graph): der Graph aller Schritte ohne Zyklen. Der DAGScheduler schneidet ihn an Shuffles in Stages.

2. Die Reise von Code zu Tasks (die Geschichte zum Merken)

  1. Transformationen sammeln. filter, select, groupBy, join geben sofort einen neuen DataFrame zurück. Es läuft kein Job.
  2. Eine Action kommt. write braucht ein echtes Ergebnis. Spark startet jetzt einen Job.
  3. Catalyst plant. Er optimiert die ganze Kette auf einmal. Das geht nur, weil Spark wartet: Er sieht Filter und Spaltenauswahl, bevor er liest.
  4. DAGScheduler schneidet. Er geht vom Ende rückwärts. Bei jeder Shuffle-Abhängigkeit beginnt eine neue Stage. Stages ohne gegenseitige Abhängigkeit können parallel laufen.
  5. TaskScheduler verteilt. Jede Stage wird ein TaskSet, ein Task pro Partition. Freie Cores bekommen Tasks.
  6. Tasks laufen. Ein Task liest seine Partition, rechnet alle Schritte der Stage am Stück und schreibt Shuffle-Dateien oder das Ergebnis. Scheitert er, versucht Spark es neu (spark.task.maxFailures, Standard 4).
  7. Nächste Stage. Eine Stage nach einem Shuffle startet erst, wenn die Stage davor ganz fertig ist. Ein langsamer Task hält also alle auf.

3. Beispiel: wann Jobs entstehen und wie viele Stages

from pyspark.sql import functions as F

trades = spark.read.parquet("/data/trades")              # (a)
big    = trades.filter(F.col("price") > 100)              # (b) kein Job
daily  = (big.groupBy("market", F.to_date("ts").alias("day"))
             .agg(F.sum("volume").alias("volume")))       # (c) kein Job
daily.explain()                                          # (d) kein Job
daily.write.mode("overwrite").parquet("/out/daily")       # (e) Action
print(big.count())                                       # (f) Action

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Annahme: 8 Input-Partitionen, AQE an (Standard seit 3.2). Die genaue Jobzahl hängt von Version und Dateizahl ab.

  1. (b), (c), (d) starten keinen Job. explain() zeigt nur den Plan.
  2. (a) kann einen kleinen Job starten, um das Parquet-Schema oder die Dateiliste zu lesen. Nicht jedes read ist also ganz lazy.
  3. Exchange im Plan = Shuffle = Stage-Grenze. Die Schreibabfrage hat darum 2 Stages: 8 Map-Tasks, dann die Reduce-Tasks.
  4. Mit AQE wird jede Shuffle-Stage als eigener Job ausgeführt. Danach plant Spark den Rest mit echten Statistiken. Darum zeigt die UI pro Action oft mehrere Jobs.
  5. Die Reduce-Seite hat nur 3 statt 200 Tasks: AQE hat kleine Shuffle-Partitionen zusammengelegt (Coalesce).
  6. skipped heisst: Diese Stage war schon fertig, ihre Shuffle-Dateien werden wiederverwendet.
  7. (f) liest die Daten noch einmal, weil big nicht gecacht ist. Auch count() hat einen Shuffle (Teilsummen, dann eine Endsumme).

4. Details, die Interviewer fragen

  1. Transformation: erzeugt aus einem DataFrame einen neuen, ohne zu rechnen. Beispiele: select, filter, withColumn, join, groupBy().agg(), repartition.
  2. Action: liefert ein Ergebnis an den Driver oder schreibt nach aussen. Beispiele: count, collect, show, take, first, write, foreach, toPandas.
  3. Warum lazy: Spark sieht die ganze Kette und optimiert sie als Ganzes. Beispiel: Ein Filter am Ende wird zur Quelle geschoben. Ausserdem fasst Spark Schritte in einer Stage zusammen.
  4. Folge von lazy: Fehler in Daten (z. B. ein Cast) zeigen sich erst bei der Action. Der Stacktrace zeigt dann die Action, nicht die schuldige Zeile.
  5. Mehrfache Berechnung: Ohne cache() rechnet jede Action die ganze Lineage neu. Zwei Actions auf denselben DataFrame lesen die Quelle zweimal.
  6. Stage-Typen: Eine ShuffleMapStage schreibt Shuffle-Dateien für die nächste Stage. Eine ResultStage liefert das Ergebnis der Action.
  7. Anzahl Tasks in der ersten Stage: Sie folgt den Input-Partitionen. Bei Dateien steuert spark.sql.files.maxPartitionBytes (Standard 128 MB) die Grösse.
  8. Anzahl Tasks nach einem Shuffle: spark.sql.shuffle.partitions (Standard 200). AQE kann diese Zahl zur Laufzeit verkleinern.
  9. Pipelining: Innerhalb einer Stage läuft jede Zeile durch alle Schritte am Stück. Es gibt keine Zwischenergebnisse auf Disk.
  10. Fehlerbehandlung: Ein fehlgeschlagener Task wird neu gestartet. Fehlen Shuffle-Dateien (FetchFailedException), rechnet Spark die vorige Stage neu. Nach zu vielen Fehlern bricht der Job ab.
  11. Speculation: Mit spark.speculation=true startet Spark langsame Tasks parallel ein zweites Mal. Der schnellere gewinnt. Vorsicht bei Schreibvorgängen ohne sicheren Commit.
  12. Checkpoint: df.checkpoint() schreibt die Daten auf zuverlässigen Speicher und schneidet die Lineage ab. Gut bei sehr langen Plänen.
  13. cache ist auch lazy: df.cache() markiert nur. Die Daten landen erst bei der nächsten Action im Speicher.

5. Vergleich

  • Job vs Stage vs Task: Job = eine Action. Stage = Abschnitt ohne Shuffle. Task = Stage × eine Partition.
  • Transformation vs Action: Transformation gibt einen DataFrame zurück und rechnet nicht. Action gibt einen Wert zurück oder schreibt, und rechnet.
  • Lazy (Spark) vs eager (pandas): pandas rechnet jede Zeile Code sofort. Spark wartet und optimiert den ganzen Plan.
  • cache vs checkpoint: cache behält die Lineage und kann verloren gehen. checkpoint schreibt dauerhaft und schneidet die Lineage ab.
  • Spark-DAG vs MapReduce: MapReduce schreibt nach jedem Schritt auf HDFS. Spark verbindet viele Schritte in einer Stage im Speicher.

6. In der Produktion

  1. Quelle wird mehrfach gelesen: Mehrere Actions auf derselben Kette (z. B. count() zum Loggen, dann write). Lösung: count() weglassen, Metriken aus dem Write nehmen, oder bewusst cachen.
  2. Ein Task hält die Stage auf: Eine Partition ist viel grösser (Skew). Alle warten auf den letzten Task. Lösung: AQE Skew Join, Salting, Schlüssel prüfen.
  3. 200 winzige Tasks: Kleine Daten, aber shuffle.partitions=200. Viel Overhead und viele kleine Dateien. Lösung: AQE Coalesce, Zahl anpassen.
  4. Riesiger Plan, langsame Planung: Schleifen mit withColumn in hunderten Schritten. Lösung: select mit vielen Spalten auf einmal, checkpoint().
  5. Fehler zeigt auf falsche Stelle: Ein Cast-Fehler erscheint bei write. Lösung: in der UI die fehlgeschlagene Stage und ihren Plan ansehen, Teilschritte isoliert testen.
  6. Stage-Retries durch verlorene Executors: Ein Node verschwindet, Shuffle-Dateien fehlen. Spark rechnet die Map-Stage neu. Lösung: stabile Nodes für Spark, Decommissioning nutzen.

7. Diagnose: Werkzeuge und Befehle

  • Spark UI, Tab Jobs: alle Jobs mit Dauer, Stages und Tasks. Ein Klick zeigt die DAG Visualization.
  • Tab Stages: pro Stage Tasks, Input, Shuffle Read/Write, Spill. Summary Metrics (Min, Median, Max) zeigen Skew.
  • Tab SQL / DataFrame: Plan als Grafik mit Zeilen pro Operator, verknüpft mit den Job-IDs.
  • df.explain("formatted"): Exchange zählen = Zahl der Shuffles. AdaptiveSparkPlan isFinalPlan=true zeigt nach der Ausführung den finalen Plan.
  • spark.sparkContext.setJobDescription("ingest day 2026-11-24"): eigene Beschreibung in der UI. Hilft bei vielen Jobs.
  • History Server: dieselbe UI nach Job-Ende (Event Log nötig).

8. Senior-Punkte

  1. Lazy ist ein Vorteil und eine Falle. Optimierung über die ganze Kette, aber versteckte Mehrfachberechnung bei mehreren Actions.
  2. Zähle Shuffles, nicht Codezeilen. Die Laufzeit hängt an Stages und Datenbewegung. explain() gehört in jedes Code-Review.
  3. Eine Stage ist so schnell wie ihr langsamster Task. Gleichmässige Partitionen sind wichtiger als mehr Executors.
  4. Actions für Logging kosten Geld. Ein count() nur fürs Log kann die Laufzeit verdoppeln.
  5. Retries brauchen idempotente Writes. Tasks und Stages laufen mehrfach. Der Output muss trotzdem genau einmal korrekt sein, z. B. durch atomare Commits wie bei Iceberg.
  6. AQE ändert die Sicht in der UI. Mehr Jobs pro Action und weniger Tasks als erwartet sind normal, kein Fehler.

10. Fallen

  • „Ein Job ist ein spark-submit.“ → Falsch. Ein spark-submit ist eine Application. Jede Action darin startet mindestens einen Job.
  • „Jede Transformation ist eine Stage.“ → Falsch. Viele Transformationen laufen in einer Stage. Nur Shuffles trennen Stages.
  • „cache() speichert sofort.“ → Falsch. Es ist lazy. Erst die nächste Action füllt den Cache.
  • „spark.read startet nie einen Job.“ → Falsch. Schema-Inferenz oder Dateilisten können kleine Jobs starten.
  • „Eine Action = genau ein Job.“ → Falsch. Mit AQE, orderBy (Sampling) oder Broadcasts entstehen oft mehrere Jobs.
  • „Mehr Executors machen jede Stage schneller.“ → Falsch. Gibt es nur 10 Partitionen, laufen nur 10 Tasks.

11. Fragen

Was ist Lazy Evaluation?

Spark führt Transformationen nicht sofort aus. Es baut einen Plan und rechnet erst, wenn eine Action ein Ergebnis braucht.

Warum ist Spark lazy?

So sieht der Optimizer die ganze Kette. Er kann Filter verschieben, Spalten weglassen und Schritte in Stages zusammenfassen.

Transformation vs Action?

Eine Transformation gibt einen neuen DataFrame zurück und rechnet nicht. Eine Action liefert ein Ergebnis oder schreibt und startet einen Job.

Nennen Sie fünf Actions.

count, collect, show, take, write. Dazu first, foreach und toPandas.

Was ist der DAG?

Ein gerichteter Graph ohne Zyklen aus allen Schritten bis zum Ergebnis. Der DAGScheduler teilt ihn in Stages.

Was ist ein Job?

Die Arbeit für eine Action. Er besteht aus einer oder mehreren Stages.

Was ist eine Stage?

Ein Abschnitt eines Jobs ohne Shuffle. Alle Schritte darin laufen pro Partition am Stück.

Wo beginnt eine neue Stage?

An jeder Shuffle-Abhängigkeit, also bei Wide Transformations wie groupBy, join oder repartition. Im Plan steht dort Exchange.

Was ist ein Task?

Eine Stage auf einer Partition. Er läuft auf einem Core eines Executors.

Wie viele Tasks hat eine Stage?

So viele wie Partitionen. Die erste Stage folgt den Input-Dateien, eine Stage nach einem Shuffle folgt spark.sql.shuffle.partitions oder AQE.

ShuffleMapStage vs ResultStage?

Die ShuffleMapStage schreibt Shuffle-Dateien für die nächste Stage. Die ResultStage berechnet das Ergebnis der Action.

Was heisst „skipped“ bei einer Stage?

Die Stage war schon berechnet und ihre Shuffle-Dateien existieren noch. Spark nutzt sie wieder und rechnet sie nicht neu.

Was passiert, wenn ein Task scheitert?

Spark startet ihn neu, standardmässig bis zu 4 Versuche. Fehlen Shuffle-Daten, wird die vorige Stage neu berechnet.

Warum zeigt die UI mehrere Jobs für ein write?

AQE führt Shuffle-Stages als eigene Jobs aus und plant danach neu. Auch Schema-Lesen, Sampling für orderBy oder Broadcasts erzeugen Jobs.

Ist cache() eine Action?

Nein. cache() markiert den DataFrame nur. Die nächste Action füllt den Cache.

Was ist Speculative Execution?

Spark startet langsame Tasks ein zweites Mal auf anderen Executors. Das schnellere Ergebnis zählt. Es hilft bei langsamen Nodes, nicht bei Skew.

Was ist ein Checkpoint?

Spark schreibt den DataFrame auf zuverlässigen Speicher und schneidet die Lineage ab. Das hilft bei sehr langen Plänen und iterativen Algorithmen.

Wie finde ich in der Spark UI die teuerste Stage?

Im Tab Stages nach Dauer sortieren. Dann Shuffle Read/Write, Spill und die Summary Metrics der Tasks prüfen.

Szenario: Ein Job liest die Quelle doppelt, obwohl der Code nur einmal read aufruft. Warum?

Es gibt zwei Actions auf derselben Kette, z. B. count() und write. Jede rechnet die Lineage neu. Lösung: eine Action weglassen oder bewusst cachen.

Szenario: Eine Stage hat 199 Tasks in Sekunden fertig, einer läuft 40 Minuten. Was ist los?

Data Skew: eine Partition hat viel mehr Daten. Summary Metrics zeigen Max weit über dem Median. Lösung: AQE Skew Join, Salting oder Schlüssel prüfen.

Szenario: Ein Fehler „cannot cast“ erscheint bei write, aber der Cast steht weit oben im Code. Wie finden Sie ihn?

Wegen Lazy Evaluation zeigt der Fehler die Action. Ich sehe in der UI die fehlgeschlagene Stage und ihren Plan an. Dann teste ich die Teilschritte einzeln mit kleinen Daten.
