Einen Server debuggen

Linux · Tier 1 · Quellen: man7.org free(1), vmstat(8), iostat(1), df(1), du(1), top(1), proc(5), journalctl(1), dmesg(1); Kernel-Doku cgroup v2 (memory.events); Brendan Gregg „USE Method“; Kubernetes Docs „Node-pressure Eviction“ (oom_score_adj); Docker Docs (docker inspect)

Kern: Einen Server debuggen ist ein systematisches Vorgehen: zuerst den Überblick, dann jede Ressource prüfen: CPU, Speicher, Disk, Netzwerk. Für jede Ressource fragt man nach Auslastung, Sättigung und Fehlern (USE-Methode). So findet man den Engpass, statt zu raten.

1. Wo schaut man hin?

  1. Überblick: uptime (Load), dmesg/journalctl (Kernel- und Systemfehler), top (wer frisst was).
  2. CPU: Ist sie voll (Auslastung)? Warten Prozesse (Sättigung: Load über Anzahl CPUs, Spalte r in vmstat)? Wird gedrosselt (cgroup)?
  3. Speicher: Wie viel ist available? Wird geswappt (si/so)? Gab es OOM-Kills?
  4. Disk: Ist sie voll (Platz und Inodes)? Ist sie langsam (await, %util, wa)?
  5. Netzwerk: Fehler und Drops am Interface, Socket-Zustände, Latenz zu Abhängigkeiten.
  6. Danach den verantwortlichen Prozess finden und in die App schauen (Logs, Thread Dump, Profiler).

2. Die Reise einer Störung: „Der Server ist langsam“

  1. Alarm: Die p99-Latenz einer API steigt. Benutzer melden „langsam“.
  2. uptime: Load 12 auf 4 CPUs. Das heisst nicht automatisch CPU-Problem: Load zählt auch Prozesse im Zustand D (Warten auf I/O).
  3. vmstat 1: us (User-CPU) ist tief, wa (I/O-Wait) ist 60 %, b (blockierte Prozesse) ist hoch. Die CPU wartet auf die Disk.
  4. iostat -x 1: Ein Gerät hat %util nahe 100 und await 250 ms. Die Disk ist gesättigt.
  5. Wer schreibt? iotop oder pidstat -d zeigt einen Backup-Job.
  6. Fix: Job drosseln (ionice), in die Nacht verschieben oder auf andere Disk legen.
  7. Prüfen: Latenz wieder normal. Dann ein Alarm auf Disk-Sättigung, damit es nächstes Mal früher auffällt.

4. Details, die Interviewer fragen

  1. USE-Methode (Brendan Gregg): Für jede Ressource drei Fragen. Utilization: Wie beschäftigt? Saturation: Wie viel Arbeit wartet? Errors: Gibt es Fehler? Beispiel Disk: %util, aqu-sz, I/O-Fehler in dmesg.
  2. Load Average: Durchschnitt der Tasks in R und D über 1, 5, 15 Minuten. Vergleichen mit nproc. Steigt 1 über 15: Problem wird schlimmer.
  3. CPU-Spalten: us User-Code, sy Kernel, wa Warten auf I/O, st Steal (die VM bekommt keine CPU vom Hypervisor), si Software-Interrupts (oft Netzwerk).
  4. free: used, free, buff/cache und available. „Linux frisst meinen RAM“ ist meist Page Cache. available schätzt, was Programme noch bekommen können.
  5. vmstat: r laufbereit (CPU-Sättigung), b blockiert (I/O), si/so Swap rein/raus (Speicherdruck), cs Kontextwechsel.
  6. iostat -x: r_await/w_await = mittlere Zeit pro I/O in ms, aqu-sz = Warteschlange, %util = wie oft das Gerät beschäftigt war. Bei SSD und NVMe ist %util nahe 100 kein sicherer Beweis für Sättigung, weil sie parallel arbeiten.
  7. df vs du: df fragt das Dateisystem, du summiert Dateien. Unterschied: gelöschte, aber noch offene Dateien. Ein Prozess hält eine gelöschte Logdatei offen. Finden mit lsof +L1. Lösung: Prozess neu starten oder Datei leeren statt löschen.
  8. OOM-Killer: Hat der Kernel (oder eine cgroup) keinen Speicher mehr, wählt er einen Prozess nach oom_score und beendet ihn mit SIGKILL. oom_score_adj (-1000 bis 1000) verschiebt die Wahl.
  9. OOM in Kubernetes: Container über limits.memory → cgroup-OOM, Grund OOMKilled, Exit 137. Node ohne Speicher → Kubelet evicted Pods. Die QoS-Klasse setzt oom_score_adj: Guaranteed -997, BestEffort 1000, Burstable dazwischen.
  10. JVM im Container: Heap ist nicht alles. Metaspace, Thread-Stacks, Direct Buffers und Code Cache kommen dazu. Darum Heap über -XX:MaxRAMPercentage setzen und Platz lassen. Ein Java-OutOfMemoryError ist etwas anderes als ein OOM-Kill.
  11. journalctl: -u dienst nach Unit, -f folgen, --since "1 hour ago", -p err nur Fehler, -k nur Kernel, -b -1 letzter Boot.
  12. dmesg: Kernel-Ringpuffer: OOM-Kills, Disk-Fehler, Netzwerk-Fehler, Segfaults. dmesg -T zeigt lesbare Zeiten.
  13. CPU-Throttling: Ein Container mit CPU-Limit wird pro Periode gebremst. cpu.stat zeigt nr_throttled und throttled_usec. Symptom: hohe Latenz bei niedriger Durchschnitts-CPU.

5. Vergleich

  • top vs htop vs ps: Live, Standard überall vs Live, bedienbarer vs Momentaufnahme für Skripte.
  • vmstat vs iostat: Gesamtbild (CPU, Speicher, Swap, I/O) vs Detail pro Disk.
  • free vs /proc/meminfo: Zusammenfassung vs alle Details (z. B. Dirty, Slab).
  • df vs du: Sicht des Dateisystems vs Summe der sichtbaren Dateien.
  • dmesg vs journalctl: nur Kernel-Puffer vs alle Logs von systemd inklusive Kernel (-k).
  • OOM-Kill vs Java OutOfMemoryError: Kernel beendet den Prozess (137) vs die JVM wirft eine Exception, der Prozess lebt evtl. weiter.
  • Eviction vs OOM-Kill: Kubelet beendet Pods geplant bei Node-Druck vs Kernel beendet einen Prozess sofort.

6. In der Produktion

  1. Disk voll: Logs ohne Rotation, Docker-Images, WAL. df -h, dann du -xh / --max-depth=1 | sort -h. Lösung: logrotate, Aufräumen, Alarm ab 80 %.
  2. df sagt voll, du findet nichts: Gelöschte offene Datei. lsof +L1. Lösung: Prozess neu starten.
  3. „No space left on device“ bei freiem Platz: Inodes voll, z. B. Millionen kleiner Dateien in einem Cache-Ordner. df -i.
  4. Pod startet immer neu, Exit 137: kubectl describe pod zeigt OOMKilled. Lösung: echten Speicherbedarf messen, Limit erhöhen oder Leck beheben, JVM-Heap anpassen.
  5. Hohe Latenz, CPU nur 30 %: CPU-Throttling durch kleines Limit, oder I/O-Wait. cpu.stat und vmstat prüfen.
  6. Server swappt: si/so dauerhaft > 0. Alles wird langsam. Lösung: Speicherverbrauch senken oder mehr RAM.
  7. Lokale VM-Disk voll: Bei Docker Desktop oder Rancher Desktop wächst das VM-Image. Dienste wie MinIO lehnen Schreibzugriffe ab. Die Kette lautet: App-Fehler → Disk → VM-Image.

7. Diagnose: die ersten 60 Sekunden

  • uptime: Load und Trend.
  • dmesg -T | tail bzw. journalctl -k -n 50: OOM, Disk- und Netzwerkfehler.
  • vmstat 1 5: r, b, si/so, us/sy/wa/st.
  • mpstat -P ALL 1: eine CPU voll, andere leer? (ein Thread am Limit)
  • pidstat 1: CPU pro Prozess über Zeit.
  • iostat -xz 1: Latenz und Auslastung pro Disk.
  • free -m: available und Swap.
  • sar -n DEV 1, ip -s link: Netzwerkdurchsatz, Fehler, Drops.
  • ss -s, ss -tan state close-wait: Socket-Zustände.
  • top / top -H -p PID: der Täter und seine Threads.
  • Container: cat /sys/fs/cgroup/memory.events, cpu.stat, kubectl top pod, kubectl describe pod, kubectl get events --sort-by=.lastTimestamp.
  • JVM: jcmd PID GC.heap_info, jcmd PID Thread.print, jcmd PID VM.native_memory summary (mit NMT).

8. Senior-Punkte

  1. Methode vor Werkzeug. Ich gehe CPU, Speicher, Disk, Netzwerk systematisch durch. Das verhindert, dass ich beim ersten Verdacht hängen bleibe.
  2. Erst stabilisieren, dann analysieren. Daten sichern (Thread Dump, Heap Dump, Logs), dann neu starten oder skalieren.
  3. Sättigung ist wichtiger als Auslastung. 100 % CPU ohne Warteschlange ist okay. 60 % mit Throttling ist ein Problem.
  4. Container ändern die Sicht. free und top zeigen oft den Host. Die Wahrheit steht in der cgroup.
  5. Jeder Vorfall endet mit einem Alarm oder Fix, der ihn nächstes Mal früher zeigt: Disk 80 %, OOM-Kills, Throttling.
  6. Memory-Limits bewusst setzen: Request = Limit für Speicher macht OOM-Verhalten vorhersagbar.

10. Fallen

  • „free zeigt 166 MB frei, der Server hat zu wenig RAM.“ → Falsch. Entscheidend ist available. Page Cache wird freigegeben.
  • „Hohe Load heisst CPU voll.“ → Falsch. Load zählt auch Prozesse, die auf I/O warten (D).
  • „Die erste Zeile von vmstat ist der aktuelle Zustand.“ → Falsch. Sie ist der Durchschnitt seit dem Boot.
  • „Disk hat Platz, also kann man schreiben.“ → Nicht, wenn die Inodes voll sind.
  • „Exit 137 ist ein Java-OutOfMemoryError.“ → Falsch. 137 ist SIGKILL vom Kernel. Ein OutOfMemoryError ist eine Exception in der JVM.
  • „Datei gelöscht, Platz ist frei.“ → Nicht, solange ein Prozess sie offen hält.

11. Fragen

Wie gehen Sie vor, wenn ein Server langsam ist?

Überblick mit uptime, dmesg und top. Dann systematisch CPU, Speicher, Disk und Netzwerk auf Auslastung, Sättigung und Fehler prüfen.

Was ist die USE-Methode?

Für jede Ressource Utilization, Saturation und Errors prüfen. Von Brendan Gregg.

Was bedeutet der Load Average?

Durchschnitt der Tasks, die laufen wollen oder auf I/O warten, über 1, 5 und 15 Minuten. Vergleich mit der CPU-Zahl.

Was ist der Unterschied zwischen free und available?

free ist ungenutzter RAM. available schätzt, was Programme bekommen können, inklusive freigebbarem Cache.

Was zeigen si und so in vmstat?

Swap-In und Swap-Out pro Sekunde. Dauerhaft über 0 heisst Speicherdruck.

Was bedeutet hoher wa-Wert?

Die CPU wartet auf I/O. Meist ist eine Disk oder ein Netzwerk-Speicher langsam oder gesättigt.

Was bedeutet st (steal)?

Die VM wollte CPU, bekam sie aber nicht vom Hypervisor. Ein Zeichen für überbuchte Hosts.

Welche iostat-Werte schauen Sie an?

r_await und w_await (Latenz), aqu-sz (Warteschlange) und %util (Beschäftigung).

Warum zeigen df und du verschiedene Werte?

Gelöschte, aber noch offene Dateien belegen Platz. lsof +L1 findet sie.

Was tun bei „No space left on device“ mit freiem Platz?

df -i prüfen. Wahrscheinlich sind die Inodes voll, z. B. durch viele kleine Dateien.

Was ist der OOM-Killer?

Der Kernel beendet bei Speichermangel einen Prozess mit SIGKILL. Er wählt nach oom_score, verschiebbar mit oom_score_adj.

Wie erkennen Sie einen OOM-Kill?

Exit 137, OOMKilled in docker inspect oder kubectl describe, memory.events in der cgroup, Meldung in dmesg.

Welcher Pod wird bei Speichermangel zuerst beendet?

BestEffort zuerst (oom_score_adj 1000), dann Burstable, Guaranteed zuletzt (-997).

Warum stirbt eine JVM im Container mit 137, obwohl der Heap kleiner als das Limit ist?

Die JVM braucht mehr als Heap: Metaspace, Stacks, Direct Buffers, Code Cache. Zusammen überschreiten sie das Limit.

Wie lesen Sie Logs eines systemd-Dienstes?

journalctl -u dienst --since "10 min ago" -p err, mit -f zum Folgen.

Was zeigt dmesg?

Kernel-Meldungen: OOM-Kills, Disk-Fehler, Segfaults, Netzwerk-Fehler.

Was ist CPU-Throttling?

Ein Container mit CPU-Limit wird pro Periode gebremst. Sichtbar in cpu.stat (nr_throttled). Folge: hohe Latenz trotz niedriger Durchschnitts-CPU.

Warum sind free und top im Container irreführend?

Sie zeigen oft die Werte des Hosts. Das echte Limit steht in der cgroup, z. B. memory.max.

Was sichern Sie vor einem Neustart?

Thread Dump, Heap Dump wenn möglich, Logs und Metriken des Zeitraums. Sonst ist die Ursache weg.

Szenario: Ein Pod startet alle paar Stunden neu, Exit Code 137. Was tun Sie?

kubectl describe pod prüfen: OOMKilled? Speicherverlauf in Grafana ansehen. Leck suchen oder Limit und JVM-Heap richtig setzen.

Szenario: df zeigt 100 %, aber du findet nur 40 % belegt. Was ist los?

Gelöschte Dateien sind noch offen, oft eine rotierte Logdatei. lsof +L1 findet den Prozess, ein Neustart gibt den Platz frei.

Szenario: Die API ist langsam, CPU-Auslastung ist nur 30 %. Wo suchen Sie?

Bei I/O-Wait mit vmstat und iostat, bei CPU-Throttling in cpu.stat, und bei langsamen Abhängigkeiten wie DB oder Netzwerk.
