Dateien und Rechte

Kern: Jede Datei in Linux hat einen Besitzer (User), eine Gruppe und Rechte für drei Klassen, nämlich Besitzer, Gruppe und alle anderen. Jede Klasse hat r (lesen), w (schreiben) und x (ausführen). Der Kernel prüft bei jedem Zugriff die numerische UID/GID des Prozesses gegen diese Angaben.

Antwort-Muster

Frage: Wie funktionieren Dateirechte in Linux?

  1. Mechanismus: Die Inode speichert Besitzer, Gruppe und Modus. Der Kernel wählt genau eine Klasse, nämlich Besitzer, sonst Gruppe, sonst Other, und prüft dort r, w oder x.
  2. Zahl: Oktal ist r = 4, w = 2, x = 1. Mit umask 022 werden Dateien 644 und Verzeichnisse 755.
  3. Trade-off: Gruppen und ACLs geben mehr Freiheit, aber chmod 777 öffnet alles für alle. Rechte sollen so klein wie möglich sein.
  4. Produktion: Ein Container-Prozess mit UID 1000 kann nicht in ein Verzeichnis schreiben, das root gehört. Ich korrigiere den Besitzer mit COPY --chown.

1. Die Reise eines Dateizugriffs

  1. Start: Ein Prozess mit UID 1000 will /data/a/x lesen.
  2. Pfad durchlaufen: Für jedes Verzeichnis auf dem Weg braucht er x (betreten). Fehlt x auf /data, endet die Reise hier.
  3. Klasse wählen: UID gleich Besitzer → Besitzer-Bits. Sonst eine seiner Gruppen gleich GID → Gruppen-Bits. Sonst Other-Bits.
  4. Bit prüfen: Zum Lesen braucht es r, zum Schreiben w, zum Ausführen x.
  5. Ergebnis: Datei offen, oder Fehler EACCES („Permission denied“).
  6. Wichtig: Löschen und Umbenennen prüfen die Rechte des Verzeichnisses (w + x), nicht der Datei.

2. Aufbau

  1. Verzeichnis-Eintrag: verbindet einen Namen mit einer Inode-Nummer. Ein Verzeichnis ist eine Liste solcher Einträge.
  2. Inode: speichert Typ, Rechte (Modus), UID, GID, Grösse, Zeiten und Zeiger auf die Daten. Den Namen speichert er nicht.
  3. Prozess: hat eine effektive UID, eine GID und Zusatzgruppen. Beispiel: Ein Container-Prozess mit UID 1000.
  4. Prüfung: Der Kernel nimmt genau eine Klasse: Besitzer, sonst Gruppe, sonst Other. Er kombiniert sie nicht.
  5. root (UID 0) umgeht die meisten Prüfungen. Genauer: Er hat Capabilities wie CAP_DAC_OVERRIDE.

3. Details, die Interviewer fragen

  1. rwx bei Verzeichnissen: r listet Namen auf. w legt Einträge an, löscht oder benennt um und braucht auch x. x betritt das Verzeichnis und spricht Dateien darin an. Mit nur x ohne r kann man eine bekannte Datei öffnen, aber nicht auflisten.
  2. Oktal: r ist 4, w ist 2 und x ist 1. 755 heisst rwxr-xr-x. 644 heisst rw-r--r--. 600 heisst rw-------. Eine vierte Ziffer davor setzt Spezial-Bits. 4 ist setuid, 2 ist setgid und 1 ist sticky. Ein Beispiel ist chmod 1777 /tmp.
  3. umask: Sie ist eine Maske, die Bits beim Anlegen wegnimmt. Sie ist kein Recht, das hinzugefügt wird. Sie gilt pro Prozess und wird vererbt.
  4. chown: Den Besitzer ändern darf nur root (bzw. CAP_CHOWN). Der Aufruf ist chown user:gruppe datei, rekursiv mit -R. Die Gruppe allein ändert chgrp.
  5. setuid / setgid: Eine Programmdatei mit setuid läuft mit der UID des Besitzers. setgid auf einem Verzeichnis lässt neue Dateien die Gruppe des Verzeichnisses erben. Linux ignoriert setuid auf Shell-Skripten.
  6. Sticky Bit: Auf einem Verzeichnis dürfen nur der Besitzer der Datei, der Besitzer des Verzeichnisses oder root löschen. Typisch ist /tmp.
  7. Capabilities: Sie zerlegen root-Rechte in Teile, z. B. CAP_NET_BIND_SERVICE für Ports unter 1024 und CAP_CHOWN. Container sollten alle unnötigen entfernen (drop: ["ALL"]).
  8. ACLs: Access Control Lists geben einzelnen Usern oder Gruppen Rechte zusätzlich zu den drei Klassen. Die Befehle sind getfacl und setfacl. Ein + in ls -l zeigt eine ACL.
  9. Hard Link vs Symlink: Ein Hard Link ist ein zweiter Name für dieselbe Inode. Ein Symlink ist eine eigene Datei mit einem Pfad. Die Rechte eines Symlinks sind egal. Es zählen die des Ziels.
  10. Container als Non-Root: Der Prozess läuft mit einer UID ungleich 0. Man setzt sie über USER 1000 im Dockerfile oder runAsUser in Kubernetes. Dateien im Image gehören oft root. Nutze darum COPY --chown=1000:1000 oder lege Schreibpfade auf Volumes.
  11. fsGroup in Kubernetes: securityContext.fsGroup: 2000 setzt die Gruppe von Volume-Dateien auf 2000. Es gibt dem Prozess diese Zusatzgruppe. So kann ein Non-Root-Prozess auf ein Volume schreiben.
  12. Zufällige UIDs: Manche Plattformen (z. B. OpenShift) starten Container mit einer zufälligen UID in Gruppe 0. Mache darum Schreibpfade für Gruppe 0 schreibbar (chgrp 0, chmod g=u).
  13. readOnlyRootFilesystem: Das Container-Dateisystem ist nur lesbar. Temporäre Daten gehen in ein emptyDir-Volume, z. B. für /tmp.

4. Fallen

  • „Zum Löschen einer Datei braucht man w auf der Datei.“ → Falsch. Man braucht w und x auf dem Verzeichnis.
  • „umask 022 gibt Dateien 755.“ → Falsch. Dateien starten bei 666, also 644. Nur Verzeichnisse bekommen 755.
  • „Wer in der Gruppe ist, bekommt Gruppe + Other.“ → Falsch. Der Kernel nimmt genau eine Klasse.
  • „Root im Container ist harmlos.“ → Falsch. Ohne User Namespaces ist es dieselbe UID 0 wie auf dem Host.
  • „chmod 777 löst das Problem.“ → Es öffnet die Datei für alle. Richtig: Besitzer oder Gruppe korrigieren.
  • „Der Benutzername im Container zählt.“ → Falsch. Der Kernel prüft nur die UID-Zahl.

5. Selbsttest

Warum?

Wie prüft der Kernel die Rechte?

Er wählt genau eine Klasse: Besitzer, sonst Gruppe, sonst Other. Dann prüft er das passende Bit.

Wer darf chown ausführen?

Nur root bzw. ein Prozess mit CAP_CHOWN. Normale Benutzer können Dateien nicht verschenken.

Warum Container als Non-Root?

Ohne User Namespaces ist root im Container root auf dem Host. Bei einem Ausbruch begrenzt Non-Root den Schaden.

Warum zeigt ls -l im Container eine Zahl statt eines Namens?

Die UID existiert nicht in /etc/passwd des Containers. Der Kernel speichert nur Zahlen.

Wie innen?

Was bedeuten r, w, x bei einer Datei?

Lesen, schreiben und ausführen.

Was bedeuten r, w, x bei einem Verzeichnis?

r: Namen auflisten. w: Einträge anlegen und löschen (mit x). x: betreten und Dateien darin ansprechen.

Was ist die umask?

Eine Maske, die beim Anlegen Rechte wegnimmt. Mit 022 werden Dateien 644 und Verzeichnisse 755.

Was ist setuid?

Ein Programm läuft mit der UID des Dateibesitzers. Beispiel: passwd läuft als root.

Was macht setgid auf einem Verzeichnis?

Neue Dateien erben die Gruppe des Verzeichnisses. Gut für Team-Verzeichnisse.

Was ist das Sticky Bit?

Auf einem Verzeichnis darf jeder nur eigene Dateien löschen. Typisch für /tmp (1777).

Was ist eine Inode?

Die Struktur mit Metadaten einer Datei: Typ, Rechte, UID, GID, Grösse, Zeiten und Datenblöcke. Ohne Namen.

Zahlen

Was heisst chmod 750?

Besitzer rwx, Gruppe r-x, alle anderen nichts.

Welche Rechte bekommen neue Dateien und Verzeichnisse mit umask 022?

Dateien starten bei 666 und werden 644. Verzeichnisse starten bei 777 und werden 755.

Wie rechnet man chmod 750?

r ist 4, w ist 2, x ist 1. Besitzer 7 = rwx, Gruppe 5 = r-x, Other 0 = nichts.

Vergleich

Hard Link vs Symlink?

Hard Link: zweiter Name für dieselbe Inode. Symlink: eigene Datei, die auf einen Pfad zeigt.

Was sind Linux Capabilities?

Teile der root-Rechte, einzeln vergebbar. Beispiel: CAP_NET_BIND_SERVICE für Ports unter 1024.

Produktion

Was macht fsGroup?

Kubernetes setzt die Gruppe der Volume-Dateien und gibt dem Prozess diese Zusatzgruppe. So kann er schreiben.

Was zeigt namei -l?

Die Rechte jedes Verzeichnisses entlang eines Pfads. Damit findet man das fehlende x-Bit.

Szenario: Ihre Spring-Boot-App im Container meldet „Permission denied“ beim Schreiben nach /app/tmp. Was tun Sie?

id und ls -ln prüfen. Meist gehört das Verzeichnis root, der Prozess läuft als 1000. Lösung: COPY --chown oder ein emptyDir-Volume für tmp.

Szenario: Nach dem Mount eines Host-Verzeichnisses kann der Container-Prozess nichts lesen. Warum?

Die numerischen UIDs passen nicht. Namen sind egal. Lösung: UID abstimmen oder fsGroup und Gruppenrechte nutzen.

Szenario: Ein Kollege will das Problem mit chmod -R 777 lösen. Was sagen Sie?

Das öffnet alles für alle und ist ein Sicherheitsrisiko. Ich korrigiere Besitzer oder Gruppe und gebe nur die nötigen Rechte.

Design

Wie lassen Sie einen Container als Non-Root laufen?

USER 1000 im Dockerfile oder runAsUser und runAsNonRoot im securityContext. Dazu Dateien mit COPY --chown übergeben.

Wie finden Sie alle setuid-Dateien?

find / -perm -4000 -type f.

Was ist readOnlyRootFilesystem?

Das Root-Dateisystem des Containers ist nur lesbar. Schreibpfade kommen über Volumes wie emptyDir.

Mehr

Gerüst

  • Warum? Mehrere Nutzer und Prozesse teilen sich ein System. Rechte begrenzen, wer lesen, schreiben und ausführen darf.
  • Wie innen? Der Name steht im Verzeichnis, Rechte, UID und GID stehen in der Inode. Der Kernel wählt genau eine Klasse.
  • Zahlen Oktal: r = 4, w = 2, x = 1. umask 022 gibt Dateien 644 und Verzeichnisse 755. chmod 1777 für /tmp.
  • Vergleich Hard Link gegen Symlink. setuid gegen sudo. root im Container ist dieselbe UID 0 wie auf dem Host.
  • Produktion App im Container kann nicht schreiben, weil UID 1000 nicht zum Besitzer passt. Secret-Dateien brauchen 600 oder 400.
  • Design Non-Root ist Standard, Rechte im Image setzen, Capabilities auf drop: ["ALL"].

Beispiel: umask, chmod, chown und Container-Benutzer

$ umask 022; umask
0022
$ echo hallo > a.txt; mkdir dir; ls -ld a.txt dir
-rw-r--r-- 1 root root    6 Nov 24 15:30 a.txt
drwxr-xr-x 2 root root 4096 Nov 24 15:30 dir
$ umask 077; echo geheim > b.txt; ls -l b.txt; umask 022
-rw------- 1 root root 7 Nov 24 15:30 b.txt
$ chmod 750 dir; chmod u+x,g-r a.txt; stat -c "%A %a %U:%G %n" a.txt dir
-rwx---r-- 704 root:root a.txt
drwxr-x--- 750 root:root dir
$ su postgres -c "cat /tmp/demo/b.txt"
cat: /tmp/demo/b.txt: Permission denied
$ su postgres -c "touch /tmp/demo/dir/x"
touch: cannot touch '/tmp/demo/dir/x': Permission denied
$ chown postgres:postgres a.txt; ls -l a.txt; ls -ln a.txt
-rwx---r-- 1 postgres postgres 6 Nov 24 15:30 a.txt
-rwx---r-- 1 999 999 6 Nov 24 15:30 a.txt

$ ls -l /usr/bin/passwd /usr/bin/su; ls -ld /tmp
-rwsr-xr-x 1 root root 118168 Apr 19  2025 /usr/bin/passwd
-rwsr-xr-x 1 root root  84360 Jul 31 15:34 /usr/bin/su
drwxrwxrwt 1 root root 4096 Nov 24 15:16 /tmp
$ id postgres
uid=999(postgres) gid=999(postgres) groups=999(postgres),101(ssl-cert)
$ ls -ld /var/lib/postgresql/data
drwx------ 19 postgres postgres 4096 Nov 24 14:57 /var/lib/postgresql/data

# umask in einer docker-exec-Shell dieses Containers
$ docker exec pg17 sh -c umask
0000
$ docker exec -u postgres pg17 sh -c 'touch /tmp/x1; ls -l /tmp/x1'
-rw-rw-rw- 1 postgres postgres 0 Nov 24 15:16 /tmp/x1

Echte Ausgabe, Debian in Container pg17 (Debian GNU/Linux 13, coreutils). Drei Aufrufe nacheinander, im Verzeichnis /tmp/demo.

  1. umask 022 nimmt Schreibrecht für Gruppe und Other weg. Dateien starten bei 666 → 644. Verzeichnisse starten bei 777 → 755.
  2. umask 077 gibt private Dateien: 600. Gut für Schlüssel und Secrets.
  3. chmod 750 (oktal): Besitzer rwx (7), Gruppe r-x (5), Other nichts (0). Symbolisch: u+x,g-r ändert einzelne Bits.
  4. s statt x beim Besitzer heisst setuid: passwd läuft als root, egal wer es startet. t bei /tmp ist das Sticky Bit: Jeder darf anlegen, aber nur eigene Dateien löschen.
  5. Warum „Permission denied“? postgres ist nicht Besitzer und nicht in Gruppe root. Darum gelten die Other-Bits: bei b.txt (600) keine, bei dir (750) keine.
  6. ls -ln zeigt die Wahrheit: Der Kernel speichert nur Zahlen (999), keine Namen. Namen kommen aus /etc/passwd des jeweiligen Systems.
  7. Das Postgres-Datenverzeichnis ist 700 und gehört UID 999. PostgreSQL verweigert den Start bei zu offenen Rechten.
  8. In diesem Container hatte eine docker exec-Shell umask 0000. Neue Dateien waren für alle schreibbar (666). Man darf sich auf eine umask nie verlassen.

Vergleich

  • chmod oktal vs symbolisch: setzt alle Bits auf einmal vs ändert einzelne Bits.
  • umask vs chmod: Standard für neue Dateien vs Änderung bestehender Dateien.
  • setuid vs sudo: fest in einer Datei, für alle Aufrufer vs Regel pro Benutzer und Befehl, mit Log.
  • root im Container vs root auf dem Host: Ohne User Namespaces ist es dieselbe UID 0. Ein Ausbruch hat dann Host-root-Rechte.
  • runAsNonRoot vs runAsUser: prüft nur, dass die UID nicht 0 ist vs setzt eine konkrete UID.
  • Hard Link vs Symlink: gleiche Inode, nur gleiches Dateisystem vs eigener Pfadverweis, auch über Dateisysteme.

In der Produktion

  1. App im Container kann nicht schreiben: „Permission denied“ auf /app/logs. Das Verzeichnis gehört root, der Prozess läuft als 1000. Lösung: COPY --chown, Verzeichnis im Dockerfile anlegen und übergeben, oder Volume mit fsGroup.
  2. Volume vom Host mit falscher UID: Ein Bind Mount hat UID 1001, der Container läuft als 999. Namen sind egal, nur die Zahlen zählen. Lösung: UIDs abstimmen oder fsGroup.
  3. Policy blockiert Pod: Eine Policy (z. B. Kyverno oder Pod Security Standards „restricted“) verbietet root und privilegierte Pods. Lösung: Image auf Non-Root umbauen, nicht die Policy aufweichen.
  4. Secret-Datei zu offen: SSH oder PostgreSQL verweigern den Start bei zu offenen Rechten. Lösung: chmod 600 bzw. defaultMode: 0400 für Secret-Volumes.
  5. Skript startet nicht: „Permission denied“ beim Aufruf. Das x-Bit fehlt, oft nach Git unter Windows. Lösung: chmod +x und git update-index --chmod=+x.
  6. chown -R beim Start dauert Minuten: Viele Dateien auf einem grossen Volume. Lösung: fsGroupChangePolicy: OnRootMismatch in Kubernetes.

Diagnose: Werkzeuge und Befehle

  • ls -l, ls -ln (Zahlen statt Namen), ls -ld dir (das Verzeichnis selbst).
  • stat -c "%A %a %U:%G %n" datei: Rechte symbolisch und oktal.
  • id, id -u, whoami: wer bin ich im Container?
  • namei -l /pfad/zur/datei: Rechte jedes Verzeichnisses entlang des Pfads.
  • find / -perm -4000 -type f 2>/dev/null: alle setuid-Dateien finden.
  • find /app -not -user 1000: Dateien mit falschem Besitzer.
  • getfacl datei: ACLs anzeigen. getcap datei: Datei-Capabilities.
  • grep Cap /proc/self/status: Capabilities des Prozesses.
  • kubectl exec pod -- id und kubectl get pod -o jsonpath='{.spec.securityContext}'.

Senior-Punkte

  1. Non-Root ist Standard, nicht Option. Dazu allowPrivilegeEscalation: false, capabilities.drop: ["ALL"], nur lesbares Root-Dateisystem.
  2. UIDs sind Zahlen. Über Systemgrenzen (Host, Container, NFS) stimme ich Zahlen ab, nicht Namen.
  3. Least Privilege auch bei Dateien: Secrets 400 oder 600, Konfiguration nur lesbar, Schreiben nur in klar definierte Pfade.
  4. setuid-Dateien im Image minimieren. Sie sind ein Weg zur Rechteausweitung.
  5. Rechte im Image festlegen, nicht beim Start mit chown -R reparieren. Das ist schneller und reproduzierbar.
