Netzwerk-Befehle

Kern: Netzwerk-Befehle sind Werkzeuge, die bei einem Verbindungsfehler die Ursache eingrenzen. Sie beantworten eine Frage nach der anderen: Löst der Name auf? (dig) Gibt es eine Route? (ip route, traceroute) Ist der Port offen? (nc, ss) Klappt TLS und HTTP? (curl -v) Was geht wirklich über die Leitung? (tcpdump). Man geht die Schichten von unten nach oben durch.

1. Wo sitzt welcher Befehl?

  1. DNS: dig fragt einen DNS-Server direkt. getent hosts löst auf wie die Anwendung, inklusive /etc/hosts.
  2. Interface: ip addr zeigt IP-Adressen, ip link den Zustand der Schnittstellen. tcpdump zeichnet Pakete auf.
  3. Routing: ip route zeigt, wohin Pakete gehen. traceroute zeigt jeden Hop bis zum Ziel.
  4. Ports: ss zeigt eigene Sockets (wer lauscht, wer verbunden ist). nc -vz prüft, ob ein entfernter Port erreichbar ist.
  5. Anwendung: curl -v zeigt DNS, Verbindung, TLS-Handshake, Request- und Response-Header.

2. Die Reise eines Requests (und wo er scheitert)

  1. DNS: Der Client fragt den Resolver aus /etc/resolv.conf. Kein Ergebnis: „Could not resolve host“. Prüfen mit dig.
  2. Route: Der Kernel wählt nach ip route ein Interface und ein Gateway. Fehlt die Route oder verwirft eine Firewall still: Timeout.
  3. TCP-Handshake: SYN → SYN-ACK → ACK. Lauscht niemand auf dem Port, antwortet der Host mit RST: Connection refused. Das ist schnell und eindeutig.
  4. TLS: Der Server zeigt sein Zertifikat. Fehlt die ausstellende CA im Truststore: certificate problem. Typisch hinter einem Firmen-Proxy, der TLS neu signiert.
  5. HTTP: Request-Header, Status, Body. Ein 500 ist für curl Erfolg (Exit 0). Nur --fail macht daraus einen Fehler.

4. Details, die Interviewer fragen

  1. ss: zeigt Sockets. Wichtige Flags: -t TCP, -u UDP, -l nur lauschende, -n Zahlen statt Namen, -p Prozess, -a alle. Klassiker: ss -tlnp. Filter: ss -tn state established '( dport = :5432 )'.
  2. ss vs netstat: netstat (net-tools) ist veraltet. ss (iproute2) ist schneller und zeigt mehr Details, z. B. TCP-Infos mit -i.
  3. Recv-Q / Send-Q: Bei LISTEN-Sockets ist Recv-Q die aktuelle und Send-Q die maximale Accept-Queue. Bei Verbindungen sind es Bytes, die noch nicht gelesen bzw. noch nicht bestätigt sind. Volles Send-Q heisst: Gegenseite liest nicht schnell genug.
  4. TCP-Zustände: LISTEN (wartet), ESTABLISHED (verbunden), TIME_WAIT (aktiv geschlossen, wartet auf späte Pakete), CLOSE_WAIT (Gegenseite hat geschlossen, die eigene App noch nicht). Viele CLOSE_WAIT heissen fast immer: Die eigene App schliesst ihre Verbindungen nicht.
  5. curl: -v Details, -I nur Header (HEAD), -L Redirects folgen, -k Zertifikat nicht prüfen (nur zum Testen), --resolve host:443:IP DNS umgehen, -H Header setzen, --fail bei 4xx/5xx Exit ≠ 0, --cacert eigene CA, -x Proxy.
  6. dig: dig +short name, dig name A/AAAA/CNAME/MX/SRV, dig @8.8.8.8 name (bestimmten Server fragen), dig +trace name (von der Root an). Die Spalte TTL zeigt, wie lange gecacht wird.
  7. DNS in Kubernetes: resolv.conf im Pod hat search-Domains und meist ndots:5. Ein Name mit weniger als 5 Punkten wird zuerst mit allen Search-Domains probiert. Das erzeugt viele DNS-Abfragen. Ein vollständiger Name mit Punkt am Ende (api.example.com.) vermeidet das.
  8. nc (netcat): nc -vz host port testet eine TCP-Verbindung. nc -l 8080 lauscht für Tests. Varianten (OpenBSD, ncat, BusyBox) haben leicht andere Flags.
  9. ip: ip addr (Adressen), ip link (Interfaces), ip route (Routing-Tabelle), ip route get IP (welcher Weg für dieses Ziel), ip neigh (ARP-Tabelle). Ersetzt ifconfig und route.
  10. traceroute: schickt Pakete mit steigender TTL. Jeder Router meldet „TTL exceeded“ und verrät sich so. * * * heisst nur: Dieser Hop antwortet nicht, nicht zwingend ein Fehler. mtr kombiniert traceroute und ping fortlaufend.
  11. tcpdump: zeichnet Pakete auf. -i any alle Interfaces, -nn keine Namensauflösung, -w file.pcap in Datei für Wireshark. Filter: host 10.0.0.5, port 443, tcp[tcpflags] & tcp-syn != 0. Braucht root oder CAP_NET_RAW.
  12. Refused vs Timeout: Refused = Host erreichbar, aber niemand lauscht (RST). Timeout = keine Antwort: Firewall verwirft, falsche Route, Host aus. Das grenzt das Problem sofort ein.

5. Vergleich

  • dig vs getent hosts: nur DNS, mit Details vs Auflösung wie die App (inkl. /etc/hosts).
  • ss vs nc: eigene lokale Sockets ansehen vs entfernten Port aktiv testen.
  • curl vs wget: Diagnose von HTTP mit vielen Optionen vs vor allem Herunterladen.
  • ping vs traceroute: erreichbar und Latenz vs Weg Hop für Hop. ICMP ist oft blockiert, also ist kein Ping kein Beweis.
  • tcpdump vs Wireshark: Aufzeichnen auf dem Server vs grafisch analysieren auf dem Laptop.
  • ip vs ifconfig/route/netstat: modern (iproute2) vs veraltet (net-tools).

6. In der Produktion

  1. „SSL certificate problem: unable to get local issuer certificate“: Ein Firmen-Proxy signiert TLS neu. curl -v zeigt den Aussteller des Zertifikats. Lösung: Firmen-CA in den Truststore des Images (OS-Bundle und Java-Truststore), nicht -k.
  2. App findet die DB nicht, curl auf dem Laptop schon: Anderer DNS im Pod. kubectl exec + getent hosts im Pod prüfen, nicht auf dem Laptop.
  3. Timeout zwischen zwei Pods: Eine NetworkPolicy verwirft Pakete still. Refused wäre ein offener Weg ohne Dienst. Lösung: Policy prüfen, z. B. mit Hubble bei Cilium.
  4. Tausende CLOSE_WAIT: Die App schliesst HTTP- oder DB-Verbindungen nicht. Folge: Dateideskriptoren laufen voll. Lösung: Ressourcen schliessen (try-with-resources), Pool-Konfiguration prüfen.
  5. Viele TIME_WAIT und „Cannot assign requested address“: Für jeden Request eine neue Verbindung, die Ephemeral Ports gehen aus. Lösung: Connection Pooling und Keep-Alive.
  6. Langsame erste Requests: curl -w zeigt grosse DNS-Zeit. Ursache oft ndots und Search-Domains. Lösung: FQDN mit Punkt oder dnsConfig anpassen.

7. Diagnose: Werkzeuge und Befehle

  • getent hosts NAME, dig +short NAME, dig @SERVER NAME, cat /etc/resolv.conf.
  • ip -br addr, ip route, ip route get ZIEL-IP.
  • nc -vz HOST PORT oder timeout 2 bash -c '</dev/tcp/HOST/PORT'.
  • ss -tlnp (wer lauscht), ss -tan state close-wait, ss -s (Zusammenfassung).
  • curl -v, curl -w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer}'.
  • openssl s_client -connect HOST:443 -servername HOST -showcerts: komplette Zertifikatskette.
  • traceroute -n HOST, mtr -rw HOST.
  • tcpdump -i any -nn -w /tmp/cap.pcap port 5432, dann in Wireshark öffnen.
  • Kubernetes: kubectl debug -it pod --image=nicolaka/netshoot bringt alle Werkzeuge in einen Pod ohne Tools.

8. Senior-Punkte

  1. Schicht für Schicht, von unten nach oben. DNS → Route → Port → TLS → HTTP. So finde ich den Fehler in Minuten statt Stunden.
  2. Vom richtigen Ort testen. Aus dem Pod, nicht vom Laptop. Netzwerk-Sicht ist ortsabhängig.
  3. Refused und Timeout lesen. Refused: Dienst fehlt. Timeout: Firewall, Policy oder Route.
  4. Minimale Images haben keine Tools. Ich nutze Ephemeral Debug Container statt Tools ins Produktions-Image zu packen.
  5. Nie -k als Lösung. TLS-Probleme löse ich mit dem richtigen Truststore.
  6. Socket-Zustände sind App-Signale: CLOSE_WAIT = Bug in der App, TIME_WAIT-Flut = fehlendes Pooling.

„Bei MATCH hat ein Firmen-Proxy TLS neu signiert. Spark-Jobs und pip schlugen fehl. Die Lösung war, das Firmen-CA-Bundle ins Spark-Image einzubauen.“ (Prüfen und durch dein echtes Beispiel ersetzen, z. B. welche Befehle du zur Diagnose genutzt hast.)

10. Fallen

  • „Ping geht nicht, also ist der Host down.“ → Falsch. ICMP ist oft blockiert. Den echten Port testen.
  • „curl hat Exit 0, also lief alles gut.“ → Falsch. Ein HTTP 500 gibt Exit 0. --fail nutzen.
  • „dig zeigt die IP, also findet die App den Namen.“ → Nicht sicher. dig ignoriert /etc/hosts und nsswitch. getent zeigt die App-Sicht.
  • „Viele TIME_WAIT sind ein Fehler.“ → Normal bei vielen kurzen Verbindungen. Problematisch erst, wenn Ports ausgehen.
  • „* * * in traceroute heisst, dort ist es kaputt.“ → Nur dieser Router antwortet nicht. Kommt das Ziel an, ist alles gut.
  • „-k behebt das Zertifikatsproblem.“ → Es schaltet nur die Prüfung ab. Die CA gehört in den Truststore.

11. Fragen

Wie gehen Sie bei „Service nicht erreichbar“ vor?

Schicht für Schicht: DNS mit dig/getent, Route mit ip route, Port mit nc oder /dev/tcp, TLS und HTTP mit curl -v.

Was zeigt ss -tlnp?

Alle lauschenden TCP-Sockets mit Port als Zahl und dem Prozess dahinter.

Warum ss statt netstat?

netstat ist veraltet (net-tools). ss ist schneller, liest direkt aus dem Kernel und zeigt mehr Details.

Was bedeutet CLOSE_WAIT?

Die Gegenseite hat die Verbindung geschlossen, die eigene App noch nicht. Viele davon sind ein Bug in der App.

Was bedeutet TIME_WAIT?

Die eigene Seite hat aktiv geschlossen und wartet auf späte Pakete. Normal, problematisch erst bei Port-Mangel.

Was ist der Unterschied zwischen Connection refused und Timeout?

Refused: Host antwortet mit RST, niemand lauscht. Timeout: keine Antwort, meist Firewall, Policy oder falsche Route.

Was zeigt curl -v?

DNS-Ergebnis, Verbindungsaufbau, TLS-Handshake, gesendete Header (>) und empfangene Header (<).

Wie messen Sie, wo ein Request Zeit verliert?

curl -w mit time_namelookup, time_connect, time_appconnect und time_starttransfer.

Wie umgehen Sie DNS mit curl?

Mit --resolve host:port:IP. Der Host-Header und SNI bleiben richtig.

Was ist der Unterschied zwischen dig und getent hosts?

dig fragt nur DNS. getent löst wie die Anwendung auf, inklusive /etc/hosts.

Was macht ndots:5 in Kubernetes?

Namen mit weniger als 5 Punkten werden zuerst mit allen Search-Domains probiert. Das erzeugt viele DNS-Abfragen.

Wie testen Sie einen Port ohne nc?

In Bash mit timeout 2 bash -c '</dev/tcp/host/port'. Exit 0 heisst offen.

Was zeigt ip route get?

Welches Interface, welches Gateway und welche Quell-IP der Kernel für ein bestimmtes Ziel nutzt.

Wie funktioniert traceroute?

Es sendet Pakete mit steigender TTL. Jeder Router meldet „TTL exceeded“ und zeigt sich so.

Wann nutzen Sie tcpdump?

Wenn Logs nicht reichen: Kommen Pakete an, gibt es SYN ohne Antwort, oder RST? Aufzeichnen mit -w und in Wireshark ansehen.

Wie prüfen Sie eine Zertifikatskette?

openssl s_client -connect host:443 -servername host -showcerts, oder curl -v.

Was bedeuten die Spalten Recv-Q und Send-Q?

Bei LISTEN: aktuelle und maximale Accept-Queue. Bei Verbindungen: ungelesene bzw. unbestätigte Bytes.

Wie debuggen Sie das Netzwerk in einem Pod ohne Tools?

kubectl debug mit einem Image wie netshoot als Ephemeral Container, oder Bash-Mittel wie /dev/tcp und /proc/net/tcp.

Szenario: curl meldet „unable to get local issuer certificate“ nur im Firmennetz. Was ist los?

Ein Proxy signiert TLS mit einer Firmen-CA neu. Ich prüfe den Aussteller mit curl -v und füge die CA in den Truststore des Images ein.

Szenario: Pod A erreicht Pod B nicht, curl läuft in einen Timeout. Was prüfen Sie?

Timeout statt Refused deutet auf Policy oder Firewall. Ich prüfe NetworkPolicies, Service-Endpoints und Ports, z. B. mit Hubble.

Szenario: Ein Server hat Tausende CLOSE_WAIT-Verbindungen und „Too many open files“. Ursache?

Die eigene App schliesst Verbindungen nicht. Ich suche das Leck im Code (fehlendes close) und prüfe die Pool-Konfiguration.
