Generics

Java · Tier 1 · Quellen: JLS SE 25 §4.5.1 (Type Arguments, Wildcards), §4.6 (Type Erasure), §4.7 (Reifiable Types), §4.12.2 (Heap Pollution), §8.4.8 (Bridge-Kontext); Java SE 25 API (Collections, SafeVarargs, java.lang.reflect.ParameterizedType)

Kern: Generics sind Typ-Parameter wie List<String>. Sie lösen das Problem, dass der Compiler Typfehler früh findet, statt dass zur Laufzeit eine ClassCastException kommt. Java prüft Generics nur beim Kompilieren und löscht sie danach: Type Erasure. Zur Laufzeit ist List<String> nur noch List.

1. Wo sitzen Generics?

  1. Quellcode: Typ-Parameter (T) und Typ-Argumente (String) stehen im Code.
  2. javac: prüft alle Zuweisungen. Danach ersetzt er T durch seine Schranke (Bound) oder Object.
  3. Bytecode: Wo ein konkreter Typ gebraucht wird, steht ein checkcast. Beispiel: (String) s.get(0).
  4. Signature-Attribut: Generische Deklarationen von Feldern, Methoden und Oberklassen bleiben in der Class-Datei. Reflection kann sie lesen.
  5. Objekte: Ein ArrayList-Objekt weiss nicht, ob es <String> oder <Integer> ist.

2. Die Reise eines generischen Aufrufs (die Geschichte zum Merken)

  1. Inferenz: Der Diamond-Operator <> (Java 7) lässt javac das Typ-Argument aus dem Ziel ableiten.
  2. Prüfung: s.add(42) auf List<String> ist ein Compile-Fehler. Das ist der ganze Nutzen.
  3. Erasure: javac löscht die Typ-Argumente. T extends Comparable<T> wird zu Comparable, ein freies T zu Object.
  4. checkcast: Beim Lesen fügt javac einen Cast ein. Wenn alles typsicher war, kann er nie scheitern.
  5. Umgehung: Über einen Raw Type (List ohne Argument) kann man falsche Objekte einfügen. Der Compiler warnt nur.
  6. Heap Pollution: Eine List<String> enthält jetzt ein Integer. Die ClassCastException kommt erst beim Lesen, weit weg von der Ursache.

Echte Ausgabe, Oracle JDK 17.0.3 (javac, java, javap). In Java 21 und 25 gleich.

  1. List<String> und List<Integer> sind zur Laufzeit dieselbe Klasse.
  2. Das Feld T wert hat nach Erasure den Typ der Schranke Comparable. Die Deklaration T bleibt im Signature-Attribut.
  3. javac erzeugt eine Bridge-Methode compareTo(Object). Sie castet und ruft compareTo(Name). So funktioniert Overriding trotz Erasure.
  4. ? extends Number liest beliebige Zahlen. ? super Integer nimmt eine List<Number> zum Schreiben.
  5. Der Raw Type schmuggelt ein Integer hinein. Der Fehler kommt erst beim checkcast nach get.
  6. Super Type Token: Eine Unterklasse hält das volle Typ-Argument in ihrer Oberklassen-Signatur. So arbeiten Jackson TypeReference und Spring ParameterizedTypeReference.
  7. Die Compile-Fehler zeigen die Grenzen: keine generischen Arrays, keine Primitive, kein instanceof mit Typ-Argument, kein T im static-Kontext, kein Schreiben in ? extends.

4. Details, die Interviewer fragen

  1. Type Erasure (JLS §4.6): Typ-Argumente werden entfernt. Typ-Variablen werden durch ihre erste Schranke ersetzt. Grund: Kompatibilität mit Code und Class-Dateien vor Java 5.
  2. Reifiable Types (JLS §4.7): Typen, die zur Laufzeit vollständig bekannt sind: Primitive, normale Klassen, Raw Types, List<?>. List<String> ist nicht reifiable.
  3. Bounded Types: <T extends Number> erlaubt nur Untertypen von Number und gibt Zugriff auf deren Methoden. Mehrere Schranken: <T extends Number & Comparable<T>>, die Klasse zuerst.
  4. Wildcards: ? steht für einen unbekannten Typ. ? extends T ist eine Obergrenze, ? super T eine Untergrenze. Wildcards gibt es nur bei der Verwendung, nicht bei der Deklaration einer Klasse.
  5. PECS („Producer Extends, Consumer Super"): Liefert eine Collection Werte, nimm extends. Nimmt sie Werte auf, nimm super. Beispiel aus der API: Collections.copy(List<? super T> dest, List<? extends T> src).
  6. Invarianz: List<Integer> ist kein Untertyp von List<Number>. Sonst könnte man ein Double in eine Integer-Liste schreiben. Arrays sind dagegen kovariant und prüfen zur Laufzeit (ArrayStoreException).
  7. Raw Types: generischer Typ ohne Argument, nur für Altcode. Jede Prüfung wird abgeschaltet. List<?> ist die sichere Alternative für „irgendeine Liste".
  8. Heap Pollution (JLS §4.12.2): eine Variable eines parametrisierten Typs zeigt auf ein Objekt eines anderen Typs. Ursachen: Raw Types, unchecked Casts, generische Varargs.
  9. Generische Varargs: T... erzeugt ein Object[]. Das kann Heap Pollution verursachen. @SafeVarargs sagt dem Compiler, dass die Methode das Array nicht missbraucht. Erlaubt nur auf Methoden, die man nicht überschreiben kann (static, final, private, Konstruktoren).
  10. Warum kein List<int>: Nach Erasure wird T zu Object. Ein int ist kein Objekt. Man nutzt Integer mit Autoboxing, das Speicher und Zeit kostet. Abhilfe: IntStream, int[] oder Bibliotheken mit primitiven Collections. Project Valhalla arbeitet daran; in Java 25 gibt es das nicht.
  11. Warum kein new T() oder new T[]: Zur Laufzeit ist T unbekannt. Lösung: Supplier<T> oder Class<T> übergeben, oder IntFunction<T[]> wie in toArray(String[]::new).
  12. Bridge-Methoden: Synthetische Methoden, die javac nach Erasure einfügt, damit Overriding mit generischen Parametern funktioniert. Sichtbar mit javap -p oder Method.isBridge().
  13. Generische Methoden: static <T> T first(List<T> l). Der Typ-Parameter steht vor dem Rückgabetyp. Explizit: Util.<String>first(l).
  14. Overloading nach Erasure: m(List<String>) und m(List<Integer>) haben dieselbe Erasure. Das ist ein Compile-Fehler (name clash).
  15. Rekursive Schranke: <T extends Comparable<? super T>> wie in Collections.sort. Das ? super T erlaubt Klassen, die Comparable über eine Oberklasse erben.

5. Vergleich

  • List<Object>: nimmt alles auf, aber eine List<String> passt nicht hinein (Invarianz).
  • List<?>: irgendeine Liste, lesen als Object, schreiben nur null. Typsicher.
  • List (raw): alles erlaubt, keine Prüfung. Nur Altcode.
  • ? extends T: lesen als T, nicht schreiben (Producer).
  • ? super T: T schreiben, lesen nur als Object (Consumer).
  • Java-Generics (Erasure): eine Klasse für alle Typ-Argumente, keine Laufzeit-Infos, keine Primitive.
  • C#-Generics (reified) und C++-Templates (Kopie pro Typ): Typ zur Laufzeit bekannt bzw. eigener Code pro Typ. Java wählte Erasure für Rückwärtskompatibilität.

6. In der Produktion

  1. ClassCastException weit weg von der Ursache: Heap Pollution über Raw Types oder unchecked Casts, oft an Grenzen zu Altcode oder Reflection. Lösung: -Xlint:unchecked als Fehler behandeln, Casts kapseln.
  2. JSON wird zu LinkedHashMap statt DTO: mapper.readValue(json, List.class) kennt das Element nicht. Lösung: TypeReference<List<Dto>> (Jackson) oder ParameterizedTypeReference (Spring RestClient/WebClient).
  3. Hoher Speicher durch Boxing: List<Integer> mit Millionen Werten braucht pro Wert ein Objekt. Lösung: int[], IntStream oder primitive Collections.
  4. Schwer lesbare APIs: Map<String, List<Map<Long, Set<?>>>>. Lösung: eigene Records oder Klassen mit Namen.
  5. Unterdrückte Warnungen: @SuppressWarnings("unchecked") auf ganzer Klasse versteckt echte Fehler. Lösung: so eng wie möglich, mit Kommentar warum sicher.

7. Diagnose: Werkzeuge und Befehle

  • javac -Xlint:unchecked,rawtypes: zeigt unchecked-Aufrufe und Raw Types. Mit -Werror werden sie zu Fehlern.
  • javap -c: zeigt checkcast nach Erasure. javap -p zeigt Bridge-Methoden.
  • javap -v: zeigt das Signature-Attribut mit den generischen Deklarationen.
  • Reflection: getGenericType(), getGenericSuperclass(), ParameterizedType.
  • SonarQube / Error Prone: melden Raw Types und unsichere Casts.

8. Senior-Punkte

  1. Wildcards in Parametern, nicht in Rückgaben. PECS macht APIs flexibel für Aufrufer. Wildcard-Rückgaben zwingen Aufrufer zu Casts.
  2. Erasure ist ein bewusster Kompromiss: volle Rückwärtskompatibilität, dafür keine Laufzeit-Typen und keine Primitive.
  3. Typ-Informationen gezielt mitgeben (Class<T>, Type Tokens), wenn Frameworks sie zur Laufzeit brauchen.
  4. Unchecked-Warnungen sind Fehler, bis bewiesen ist, dass der Cast sicher ist. Eine unterdrückte Warnung braucht eine Begründung.
  5. Generics nicht übertreiben. Mehr als zwei Typ-Parameter oder verschachtelte Wildcards sind meist ein Zeichen für ein fehlendes Domänenobjekt.

10. Fallen

  • „List<Integer> ist ein List<Number>.“ → Falsch. Generics sind invariant. Nutze List<? extends Number>.
  • „Zur Laufzeit kennt die Liste ihren Elementtyp.“ → Falsch. Erasure. Nur Deklarationen sind per Reflection lesbar.
  • „In eine List<? extends Number> kann ich ein Integer schreiben.“ → Falsch. Nur null. Der echte Typ könnte List<Double> sein.
  • „Raw Types und List<?> sind dasselbe.“ → Falsch. List<?> ist typsicher, Raw Types schalten die Prüfung ab.
  • „Generics machen Code langsamer.“ → Falsch. Nach Erasure ist es derselbe Bytecode plus Casts. Langsam macht nur Boxing.
  • „@SafeVarargs macht Varargs sicher.“ → Falsch. Es ist ein Versprechen des Autors und unterdrückt nur die Warnung.

11. Fragen

Was ist Type Erasure?

javac prüft Generics und entfernt danach die Typ-Argumente. Typ-Variablen werden zu ihrer Schranke oder Object, dazu kommen Casts.

Warum hat Java Erasure gewählt?

Für Rückwärtskompatibilität mit Code und Bibliotheken vor Java 5. Alte und neue Class-Dateien arbeiten zusammen.

Ist List<String>.class gleich List<Integer>.class?

Es gibt nur List.class. Beide Objekte haben zur Laufzeit dieselbe Klasse, z. B. ArrayList.

Warum gibt es kein List<int>?

Nach Erasure wird T zu Object, und int ist kein Objekt. Man nutzt Integer mit Autoboxing oder primitive Spezialisierungen wie IntStream.

Was ist ein Bounded Type?

Ein Typ-Parameter mit Schranke, z. B. T extends Number. Er erlaubt nur passende Typen und gibt Zugriff auf deren Methoden.

Was bedeutet PECS?

Producer Extends, Consumer Super. Liest man aus einer Collection, nimmt man ? extends T; schreibt man hinein, ? super T.

Warum kann ich nicht in List<? extends Number> schreiben?

Der echte Typ ist unbekannt, vielleicht List<Double>. Ein Integer würde sie verschmutzen. Nur null ist erlaubt.

Was kann ich aus List<? super Integer> lesen?

Nur Object. Der echte Elementtyp kann Integer, Number oder Object sein.

Warum ist List<Integer> kein Untertyp von List<Number>?

Sonst könnte man über die Number-Referenz ein Double in die Integer-Liste schreiben. Generics sind darum invariant.

Warum sind Arrays kovariant, Generics aber nicht?

Arrays kennen ihren Elementtyp zur Laufzeit und werfen ArrayStoreException. Generics haben nach Erasure keine Laufzeitprüfung, darum verbietet der Compiler es.

Was ist ein Raw Type?

Ein generischer Typ ohne Typ-Argument, z. B. List. Er existiert für Altcode und schaltet die Typprüfung ab.

Was ist Heap Pollution?

Eine Variable vom Typ List<String> zeigt auf eine Liste mit fremden Objekten. Die ClassCastException kommt später beim Lesen.

Wofür ist @SafeVarargs?

Es unterdrückt die Warnung bei generischen Varargs. Der Autor verspricht, das Array nicht unsicher zu nutzen. Nur bei nicht überschreibbaren Methoden erlaubt.

Warum kann man kein new T[] erzeugen?

Zur Laufzeit ist T unbekannt, das Array bräuchte aber seinen echten Elementtyp. Lösung: IntFunction<T[]> oder Class<T> übergeben.

Warum geht instanceof List<String> nicht?

Das Typ-Argument ist zur Laufzeit nicht da. Erlaubt ist instanceof List<?>.

Was ist eine Bridge-Methode?

Eine synthetische Methode, die javac nach Erasure erzeugt. Sie castet und delegiert, damit Overriding mit generischen Parametern funktioniert.

Kann man m(List<String>) und m(List<Integer>) überladen?

Nein. Beide haben dieselbe Erasure m(List). Das ist ein name clash.

Wie kommt Jackson an den Elementtyp einer Liste?

Über ein Type Token: eine anonyme Unterklasse von TypeReference<List<Dto>>. Ihre Oberklassen-Signatur ist per Reflection lesbar.

Was bedeutet <T extends Comparable<? super T>>?

T muss mit sich selbst vergleichbar sein, auch wenn Comparable von einer Oberklasse kommt.

Was ist der Diamond-Operator?

<> bei new, seit Java 7. javac leitet das Typ-Argument aus dem Zieltyp ab.

Kann eine static-Methode den Typ-Parameter der Klasse nutzen?

Nein. T gehört zu einer Instanz. Eine static-Methode braucht einen eigenen Typ-Parameter.

Szenario: Eine ClassCastException kommt in einem Report-Modul, aber der Fehler ist ganz woanders. Wie finden Sie ihn?

Wahrscheinlich Heap Pollution. Mit -Xlint:unchecked Raw Types und unchecked Casts suchen, besonders an Grenzen zu Altcode oder Reflection.

Szenario: Ein REST-Client liefert List<Dto>, aber die Elemente sind LinkedHashMap. Warum?

Der Client hat wegen Erasure nur List.class bekommen. Lösung: ParameterizedTypeReference oder TypeReference mit dem vollen Typ.

Szenario: Eine Berechnung über 50 Millionen Werte braucht zu viel Heap. Die Daten liegen in List<Long>. Was tun?

Boxing vermeiden: long[] oder LongStream nutzen. Jeder Long ist ein eigenes Objekt mit Header.
