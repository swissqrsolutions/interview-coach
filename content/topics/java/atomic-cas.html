Atomic-Klassen und Compare-and-Swap (CAS)

Kern: Atomic-Klassen sind Variablen, die man ohne Lock atomar ändern kann. Sie lösen das Problem, dass count++ bei mehreren Threads Updates verliert. Innen nutzen sie CAS (Compare-and-Swap): „Setze den neuen Wert nur, wenn noch der alte Wert drin steht.“

1. Wo sitzen Atomic-Klassen?

  1. Dein Code ruft z. B. incrementAndGet() auf. Kein synchronized nötig.
  2. JDK-Bausteine wie ConcurrentHashMap und AQS (die Basis von ReentrantLock) nutzen dieselbe CAS-Technik.
  3. Atomic-Klassen und VarHandle: Sie liefern atomare Lese-Ändere-Schreibe-Operationen mit volatile-Semantik.
  4. JIT-Intrinsic: Der JIT ersetzt den Aufruf durch fertigen CPU-Code.
  5. CPU: Ein einziger atomarer Befehl vergleicht und schreibt. Kein Betriebssystem, kein Parken von Threads.

2. Die Reise eines incrementAndGet() (die Geschichte zum Merken)

  1. Lesen: Thread A liest den aktuellen Wert 41. Der Read ist volatile, also aktuell.
  2. Rechnen: Thread A berechnet lokal 42. Noch ist nichts geschrieben.
  3. CAS: Thread A sagt der CPU: „Schreibe 42, aber nur wenn noch 41 drin steht.“ Die CPU macht Vergleich und Schreiben in einem unteilbaren Schritt.
  4. Erfolg: Steht noch 41 drin, gewinnt Thread A. Der Wert ist 42.
  5. Misserfolg: Thread B hat inzwischen 42 geschrieben. Der CAS von A schlägt fehl und schreibt nichts. A liest neu (42), rechnet 43 und versucht es nochmals. Diese Schleife heisst CAS-Loop oder Spin.
  6. Kein Thread blockiert: Mindestens ein Thread kommt immer weiter. Das heisst lock-free.

3. Beispiel: Lost Updates, CAS-Fehlversuche, LongAdder, ABA

static int plain = 0;
AtomicInteger ai = new AtomicInteger();
run(8 Threads, je 1_000_000×: plain++; ai.incrementAndGet());          // 1)

do { old = v.get(); } while (!v.compareAndSet(old, old + 1));          // 2) Fehlversuche zählen

8 Threads × 5_000_000: AtomicLong.incrementAndGet() vs LongAdder.increment()  // 3)

ref.set("B"); ref.set("A"); ref.compareAndSet(seen, "C");              // 4) ABA
stamped.compareAndSet("A", "C", alterStamp, alterStamp + 1);

max.accumulateAndGet(x, Math::max); max.updateAndGet(x -> x * 2);      // 5)

2) value=8000000 failedCAS=5460310
3) run 1: AtomicLong 557 ms (40000000), LongAdder 60 ms (40000000)
3) run 2: AtomicLong 535 ms (40000000), LongAdder 73 ms (40000000)
3) run 3: AtomicLong 506 ms (40000000), LongAdder 31 ms (40000000)

Echte Ausgabe, Oracle JDK 17.0.3 (16 Kerne, Windows). Die Zahlen bei 1) bis 3) ändern sich bei jedem Lauf. Java 21 und 25 verhalten sich gleich.

  1. plain++ verliert fast 43 % der Updates. AtomicInteger verliert keinen.
  2. Für 8 Mio. erfolgreiche CAS gab es 5,4 Mio. Fehlversuche. Jeder Fehlversuch ist verlorene CPU-Zeit. Das ist der Preis von CAS bei hoher Konkurrenz.
  3. LongAdder ist hier 7- bis 16-mal schneller als AtomicLong. Er verteilt die Threads auf mehrere Zellen.
  4. ABA: Der Wert ging A → B → A. Der normale CAS merkt das nicht und gelingt. Mit AtomicStampedReference zählt ein Stamp (Versionsnummer) mit. Der alte Stamp passt nicht mehr, der CAS schlägt fehl.
  5. accumulateAndGet und updateAndGet verstecken die CAS-Schleife. Die Funktion muss ohne Seiteneffekte sein, weil sie mehrmals laufen kann.

4. Details, die Interviewer fragen

  1. Was CAS garantiert: Vergleich und Schreiben sind ein unteilbarer Schritt. compareAndSet hat die Memory-Wirkung von VarHandle.compareAndSet, also volatile Read und Write.
  2. Sichtbarkeit: get() wirkt wie ein volatile Read, set() wie ein volatile Write. Darum gilt happens-before zwischen den Threads.
  3. Die Familie:
    • AtomicBoolean, AtomicInteger, AtomicLong, AtomicReference: eine Variable.
    • AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray: atomare Array-Elemente mit volatile-Semantik.
    • AtomicIntegerFieldUpdater usw.: CAS auf ein volatile-Feld einer fremden Klasse, per Reflection. Spart ein Objekt pro Instanz.
    • AtomicStampedReference (Referenz + int-Stamp) und AtomicMarkableReference (Referenz + boolean-Markierung): gegen ABA.
    • LongAdder, DoubleAdder, LongAccumulator, DoubleAccumulator: verteilte Zähler.
  4. ABA-Problem: Ein Wert wechselt von A nach B und zurück nach A. CAS vergleicht nur den Wert und merkt die Änderung nicht. Bei Zahlen ist das meist egal. Bei lock-freien Datenstrukturen mit wiederverwendeten Knoten ist es gefährlich.
  5. LongAdder innen: Er hat eine Basis-Variable und bei Konkurrenz ein Array von Zellen. Jeder Thread zählt in „seiner“ Zelle. sum() addiert alle Zellen. Das ist kein atomarer Schnappschuss, wenn gleichzeitig geschrieben wird.
  6. LongAccumulator: wie LongAdder, aber mit eigener Funktion, z. B. Long::max. Die Funktion muss assoziativ und ohne Seiteneffekte sein.
  7. Kein equals/hashCode: Atomic-Klassen überschreiben equals und hashCode nicht. Sie sind darum schlechte Map-Schlüssel. Sie sind kein Ersatz für Integer.
  8. Schwächere Varianten (Java 9): weakCompareAndSetPlain und weakCompareAndSetVolatile dürfen grundlos fehlschlagen (spurious failure). Sie gehören in eine Schleife. Das alte weakCompareAndSet ist seit Java 9 deprecated.
  9. compareAndExchange (Java 9): Liefert den tatsächlichen Wert (witness value) statt nur true/false. Das spart einen zusätzlichen Read.
  10. lazySet / setRelease: schreibt mit Release-Semantik, also ohne volle volatile-Barriere. Etwas billiger, wenn nur Reihenfolge zählt.
  11. VarHandle (Java 9, JEP 193): Ein VarHandle gibt CAS direkt auf ein normales Feld, ohne Atomic-Objekt. Das JDK selbst nutzt es intern. Für Anwendungs-Code reichen Atomic-Klassen.
  12. Mehrere Variablen: CAS schützt genau eine Variable. Zwei Felder zusammen brauchen einen Lock oder ein unveränderliches Objekt in einer AtomicReference.

5. Vergleich

  • volatile: nur Sichtbarkeit. Kein atomares ++. Gut für ein Flag.
  • AtomicInteger / AtomicLong: Sichtbarkeit plus atomare Updates einer Variable. Exakter Wert jederzeit lesbar.
  • LongAdder: sehr schnell bei vielen schreibenden Threads. Mehr Speicher. sum() ist nicht exakt während Writes. Kein CAS von aussen.
  • synchronized / ReentrantLock: schützt mehrere Variablen und längere Abläufe. Threads blockieren, dafür kein Spin.
  • AtomicReference mit unveränderlichem Objekt: mehrere Felder als ein Objekt atomar austauschen (Copy-on-Write).
  • ConcurrentHashMap.merge / compute: atomare Updates pro Schlüssel, z. B. Zähler pro Kategorie.

6. In der Produktion

  1. Hohe CPU durch Spin: Viele Threads machen CAS auf dieselbe Variable. Die meisten Versuche scheitern. Lösung: LongAdder, Arbeit pro Thread sammeln, seltener zentral schreiben.
  2. Check-then-act mit zwei Aufrufen: if (a.get() < max) a.incrementAndGet(); ist nicht atomar. Zwei Threads gehen beide durch. Lösung: eine CAS-Schleife oder updateAndGet.
  3. Seiteneffekte in updateAndGet: Ein Log oder ein Remote-Call in der Funktion läuft bei Konkurrenz mehrfach. Lösung: reine Funktion, Seiteneffekt danach.
  4. Zwei Atomics, die zusammengehören: min und max als zwei AtomicLong sind zusammen nicht konsistent. Lösung: ein Record in einer AtomicReference oder ein Lock.
  5. False Sharing: Zwei heisse Atomics liegen in derselben Cache Line (meist 64 Bytes). Jeder Write macht die Cache Line der anderen Kerne ungültig. LongAdder polstert seine Zellen deshalb intern auf (@Contended).
  6. Metriken: Eigene Zähler sind selten nötig. Micrometer nutzt intern bereits passende Zähler.

7. Diagnose: Werkzeuge und Befehle

  • async-profiler oder JFR (Methoden-Profil): viel CPU-Zeit in getAndAddInt, compareAndSet oder einer eigenen CAS-Schleife zeigt Konkurrenz.
  • Thread Dump (jcmd <pid> Thread.print): Spinnende Threads stehen auf RUNNABLE, nicht auf BLOCKED. Bei Locks wäre es umgekehrt.
  • jcstress (OpenJDK): testet Nebenläufigkeit systematisch, z. B. ob ein Ablauf Updates verliert.
  • JMH: misst AtomicLong gegen LongAdder mit @Threads korrekt, mit Warm-up.
  • Lasttest mit Zählervergleich: Zähler gegen eine zweite Quelle prüfen, z. B. Access-Log.

8. Senior-Punkte

  1. Lock-free heisst nicht kostenlos. Bei hoher Konkurrenz verbrennt CAS CPU im Spin. Ein Lock parkt Threads und kann dann sogar besser sein.
  2. Für Zähler LongAdder, für Zustand AtomicLong. Braucht man den exakten Wert oder CAS, nimmt man AtomicLong.
  3. Eine Variable, ein CAS. Sobald zwei Werte zusammenpassen müssen, braucht es ein unveränderliches Objekt in einer AtomicReference oder einen Lock.
  4. Eigene lock-freie Strukturen sind fast nie nötig. Das JDK hat getestete: ConcurrentHashMap, ConcurrentLinkedQueue, LongAdder.
  5. Atomics lösen nur Atomarität im Speicher. Über mehrere Pods hinweg hilft nur die Datenbank, z. B. ein atomarer SQL-Update.
  6. Erst messen. Bei wenig Konkurrenz ist AtomicLong schnell genug und einfacher zu verstehen.

10. Fallen

  • „volatile int reicht für einen Zähler.“ → Falsch. ++ sind drei Schritte. Es braucht AtomicInteger, LongAdder oder einen Lock.
  • „Lock-free heisst wait-free.“ → Falsch. Lock-free garantiert nur, dass ein Thread weiterkommt. Ein einzelner Thread kann lange spinnen.
  • „CAS ist immer schneller als ein Lock.“ → Falsch. Bei starker Konkurrenz kosten die Fehlversuche viel CPU.
  • „LongAdder.sum() liefert einen exakten Stand.“ → Falsch. Während paralleler Writes ist es kein atomarer Schnappschuss.
  • „Zwei AtomicLong sind zusammen thread-sicher.“ → Falsch. Jede einzeln ja, zusammen nicht konsistent.
  • „AtomicInteger kann als Map-Schlüssel dienen.“ → Falsch. Kein eigenes equals/hashCode, und der Wert ändert sich.

11. Fragen

Was ist CAS?

Compare-and-Swap: Schreibe den neuen Wert nur, wenn noch der erwartete alte Wert drin steht. Vergleich und Schreiben sind ein atomarer CPU-Befehl.

Was liefert compareAndSet zurück?

true, wenn der Wert ersetzt wurde. false, wenn ein anderer Wert drin stand. Dann wurde nichts geschrieben.

Warum ist count++ nicht thread-sicher?

Es sind drei Schritte: lesen, plus 1, schreiben. Zwei Threads können denselben alten Wert lesen. Ein Update geht verloren.

Wie funktioniert incrementAndGet intern?

Lesen, neuen Wert berechnen, CAS. Schlägt der CAS fehl, nochmals. Auf x86 ersetzt der JIT das durch einen atomaren LOCK-Befehl.

Was ist der Unterschied zwischen volatile und AtomicInteger?

volatile gibt nur Sichtbarkeit. AtomicInteger gibt Sichtbarkeit plus atomare Lese-Ändere-Schreibe-Operationen.

Was heisst lock-free?

Kein Thread hält einen Lock. Mindestens ein Thread kommt immer weiter. Ein einzelner Thread kann aber mehrmals scheitern.

Was ist das ABA-Problem?

Der Wert geht A → B → A. CAS sieht wieder A und gelingt, obwohl sich etwas geändert hat. Lösung: AtomicStampedReference mit Versionsnummer.

Wann ist ABA wirklich gefährlich?

Bei lock-freien Datenstrukturen mit Zeigern, z. B. ein Stack, dessen Knoten wiederverwendet werden. Bei einem einfachen Zähler meist nicht.

Was ist LongAdder und wie funktioniert er?

Ein Zähler mit Basis-Variable und Zellen. Bei Konkurrenz schreibt jeder Thread in eine eigene Zelle. sum() addiert alles.

AtomicLong oder LongAdder?

LongAdder für Zähler mit vielen Schreibern. AtomicLong, wenn man den exakten Wert, CAS oder getAndIncrement für IDs braucht.

Kann man mit LongAdder eine eindeutige Sequenz-ID erzeugen?

Nein. LongAdder hat kein getAndIncrement mit eindeutigem Ergebnis. Dafür AtomicLong.getAndIncrement.

Was machen updateAndGet und accumulateAndGet?

Sie verstecken die CAS-Schleife und wenden eine Funktion an. Die Funktion muss seiteneffektfrei sein, weil sie mehrmals laufen kann.

Was ist weakCompareAndSet?

Ein CAS, der grundlos fehlschlagen darf (spurious failure). Er ist nur in einer Schleife sinnvoll. Heute heissen die Varianten weakCompareAndSetPlain und weakCompareAndSetVolatile.

Was ist compareAndExchange?

Ein CAS, der den tatsächlichen Wert zurückgibt statt nur true/false. Seit Java 9.

Was ist ein AtomicIntegerFieldUpdater?

Er macht CAS auf ein volatile-int-Feld einer anderen Klasse. Er spart pro Instanz ein Atomic-Objekt. Heute ersetzt VarHandle ihn meist.

Was ist ein VarHandle?

Ein typisierter Zugriff auf ein Feld oder Array-Element mit wählbaren Zugriffsarten und CAS. Seit Java 9, vor allem für Bibliotheks-Code.

Wie ändern Sie zwei Werte atomar ohne Lock?

Beide in ein unveränderliches Objekt packen, z. B. einen Record. Dann in einer AtomicReference per CAS das ganze Objekt tauschen.

Warum sind Atomic-Klassen schlechte Map-Schlüssel?

Sie überschreiben equals und hashCode nicht. Und ihr Wert soll sich ändern.

Was ist False Sharing?

Zwei unabhängige heisse Variablen liegen in derselben Cache Line. Writes eines Kerns machen den Cache der anderen ungültig. LongAdder polstert seine Zellen dagegen.

Wann ist ein Lock besser als CAS?

Bei sehr hoher Konkurrenz auf eine Variable, bei mehreren Variablen oder bei längeren Abläufen. Ein Lock parkt Threads statt CPU zu verbrennen.

Wie sieht spinnende Konkurrenz im Thread Dump aus?

Viele Threads stehen RUNNABLE in derselben CAS-Methode. Bei einem Lock stünden sie BLOCKED oder WAITING.

Hilft AtomicLong bei mehreren Pods?

Nein. Atomics wirken nur in einer JVM. Über Pods hinweg braucht es die Datenbank, z. B. einen atomaren UPDATE oder eine Sequenz.

Szenario: Ein Service mit einem globalen AtomicLong-Zähler hat unter Last hohe CPU. Was tun Sie?

Profiler prüfen: viel Zeit im CAS heisst Konkurrenz. Zähler auf LongAdder umstellen. Wenn ein exakter Wert nötig ist: lokal sammeln und seltener zentral addieren.

Szenario: Ein Limit „max. 10 gleichzeitige Jobs“ mit get() und incrementAndGet() lässt manchmal 11 durch. Warum?

Check-then-act mit zwei Aufrufen ist nicht atomar. Lösung: CAS-Schleife, die nur bei Wert unter 10 erhöht, oder ein Semaphore.

Szenario: In updateAndGet steht ein Log-Aufruf, und das Log zeigt Einträge doppelt. Warum?

Bei Konkurrenz scheitert der CAS, und die Funktion läuft nochmals. Lösung: Funktion ohne Seiteneffekte, Log nach dem Update mit dem Ergebnis.
