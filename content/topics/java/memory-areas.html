Speicherbereiche der JVM: Heap, Stack, Metaspace, Code Cache, Direct Memory

Kern: Die JVM teilt ihren Speicher in getrennte Bereiche mit eigenen Grenzen. Der Heap hält Objekte und der Stack hält Methodenaufrufe pro Thread. Metaspace, Code Cache und Direct Memory liegen ausserhalb des Heaps, darum ist der ganze Prozess immer grösser als -Xmx.

Antwort-Muster

Frage: Welche Speicherbereiche hat die JVM?

  1. Mechanismus: Der Heap hält Objekte, jeder Thread hat einen Stack. Metaspace, Code Cache und Direct Memory liegen im nativen Speicher.
  2. Zahl: Ohne -Xmx nimmt die JVM 25 % des RAM als Heap. Der Code Cache hat 240 MB.
  3. Trade-off: Off-Heap spart Kopien und GC-Arbeit, aber Leaks sind schwerer zu finden.
  4. Produktion: Im Container plane ich den ganzen Prozess und setze MaxRAMPercentage auf etwa 70–75.

1. Die Reise eines Objekts

  1. Klasse laden: new Order() braucht zuerst die Klasse. Der Class Loader (lädt .class-Dateien) legt ihre Metadaten in den Metaspace. Das passiert nur einmal pro Class Loader.
  2. Referenz auf dem Stack: Die Variable o liegt im Frame von main(). Sie ist nur ein Zeiger, nicht das Objekt.
  3. Objekt im Eden: Das Objekt entsteht im Eden (Teil der Young Generation). Jeder Thread hat dort einen eigenen TLAB (Thread-Local Allocation Buffer). Darum ist new sehr schnell und braucht kein Lock.
  4. Young GC: Der Young GC räumt den Eden. Lebt das Objekt noch, wird es in einen Survivor-Bereich kopiert. Sein Alter steigt um 1.
  5. Old Gen: Nach mehreren Young GCs kommt das Objekt in die Old Generation. Grenze: MaxTenuringThreshold, Standard 15. Sehr grosse Objekte (Humongous Objects in G1, ab halber Regionsgrösse) kommen direkt dorthin.
  6. Unerreichbar: Endet main(), verschwindet der Frame und damit die Referenz. Das Objekt ist dann von keiner GC Root (Startpunkt wie Stack-Variable oder statisches Feld) mehr erreichbar.
  7. Freigabe: Der nächste passende GC gibt den Speicher frei. Die meisten Objekte sterben schon im Eden. Das ist die Generational Hypothesis.

Die Klasse Order bleibt im Metaspace, bis ihr Class Loader selbst unerreichbar ist. Das ist bei normalen Anwendungsklassen nie der Fall.

2. Aufbau

  1. Heap: Der Heap ist der Bereich für alle Objekte und Arrays. Alle Threads teilen ihn. Der Garbage Collector (GC, räumt unerreichbare Objekte weg) arbeitet nur hier. Beispiel: new Order() liegt im Heap.
  2. Thread Stacks: Jeder Thread hat einen eigenen Stack mit einem Frame (Speicher für einen Methodenaufruf) pro Aufruf. Ein Frame hält lokale Variablen und Referenzen auf Heap-Objekte. Beispiel: Order o ist eine Referenz im Frame.
  3. Metaspace: Der Metaspace hält die Metadaten geladener Klassen im nativen Speicher. Dazu gehören Methoden, Bytecode und der Runtime Constant Pool (Konstanten und Symbol-Referenzen einer Klasse). Beispiel: die Beschreibung der Klasse Order.
  4. Code Cache: Der Code Cache hält den Maschinencode, den der JIT (Just-in-Time-Compiler) erzeugt. Beispiel: die kompilierte Methode Order.total().
  5. Direct Memory: Direct Memory ist nativer Speicher für Direct ByteBuffers (Puffer ausserhalb des Heaps). Netty und NIO nutzen ihn für schnelles I/O. Beispiel: ByteBuffer.allocateDirect(8_000_000).
  6. Sonstiges nativ: Der GC braucht eigene Datenstrukturen, z. B. Remembered Sets (Listen von Verweisen zwischen Regionen). Dazu kommen Symbole, Thread-Strukturen und native Bibliotheken.
  7. Container-Limit: Die Summe aller Bereiche muss unter dem Limit bleiben. Sonst beendet der Kernel den Prozess, ohne Java-Fehlermeldung.

3. Details, die Interviewer fragen

  1. Heap-Grösse: -Xms ist die Startgrösse und -Xmx die Obergrenze. Ohne Flags nimmt die JVM 25 % des RAM als Maximum (MaxRAMPercentage=25). Die Startgrösse ist 1/64 des RAM (InitialRAMPercentage=1.5625). Das gilt gleich in Java 21 und 25.
  2. Container Awareness: Auf Linux liest die JVM die cgroup-Limits (v1 und v2) statt des Host-RAMs. Das steuert -XX:+UseContainerSupport, standardmässig an. Die 25 % beziehen sich dann auf das Pod-Limit. Mit -XX:MaxRAMPercentage=75 setzt man den Anteil selbst.
  3. Generationen in G1: G1 ist seit Java 9 der Standard-GC. Er teilt den Heap in gleich grosse Regionen (1–32 MB). Jede Region ist Eden, Survivor, Old oder Humongous.
  4. ZGC: ZGC ist seit Java 21 optional generational (JEP 439). Ab Java 23 ist es standardmässig generational.
  5. Stack-Inhalt: Ein Frame hält lokale Variablen. Er hält auch den Operand Stack (Zwischenwerte für Bytecode). Dazu kommt ein Verweis auf den Constant Pool. Primitive lokale Variablen liegen direkt im Frame. Objekte liegen nie im Frame, nur ihre Referenzen.
  6. Stack-Grösse: -Xss setzt die Grösse pro Thread. Auf Linux x64 und Windows x64 ist sie meist 1 MB. Zu tiefe Rekursion wirft StackOverflowError. Zu viele Threads werfen OutOfMemoryError: unable to create native thread.
  7. Virtual Threads: Sie gibt es seit Java 21 (JEP 444). Sie haben keinen festen OS-Stack. Ihre Frames liegen als Stack Chunks im Heap, solange sie blockiert sind. Darum sind Millionen Virtual Threads möglich.
  8. PC Register und Native Method Stack: Die JVM-Spezifikation nennt auch das PC Register. Es hält die aktuelle Bytecode-Adresse pro Thread. Dazu kommt der Native Method Stack für JNI-Code. HotSpot nutzt für Java- und native Frames denselben Thread-Stack.
  9. Metaspace: Er ersetzt seit Java 8 die PermGen (JEP 122). Er liegt im nativen Speicher und hat standardmässig keine Grenze. -XX:MetaspaceSize ist keine Startgrösse. Es ist die Schwelle für den ersten GC wegen Metadaten.
  10. Compressed Class Space: Sie ist ein Teil des Metaspace für Klassenstrukturen. Objekt-Header zeigen mit 32-Bit-Zeigern dorthin. Standard sind 1 GB reserviert (CompressedClassSpaceSize).
  11. Metaspace freigeben: Metadaten werden nur frei, wenn der ganze Class Loader unerreichbar ist. Seit Java 16 gibt Elastic Metaspace (JEP 387) freien Speicher schneller ans OS zurück.
  12. Strings und statische Felder: Der String Pool liegt im Heap. Statische Felder liegen ebenfalls im Heap. Sie hängen am java.lang.Class-Objekt. Nur die Klassenbeschreibung liegt im Metaspace.
  13. Code Cache: Er ist seit Java 9 in drei Segmente geteilt (JEP 197). Der Standard sind 240 MB (ReservedCodeCacheSize) mit Tiered Compilation. Ist er voll, stoppt der JIT. Dann wird die Anwendung langsam.
  14. Direct Memory: Die Grenze ist -XX:MaxDirectMemorySize. Ohne das Flag gilt Runtime.maxMemory(), also etwa -Xmx. Der Speicher wird frei, wenn der GC das kleine ByteBuffer-Objekt im Heap einsammelt. Das geht über einen Cleaner.
  15. System.gc() bei Direct Memory: Reicht das Limit nicht, ruft java.nio.Bits selbst System.gc() auf. Dann wartet es. Erst danach kommt OutOfMemoryError. Mit -XX:+DisableExplicitGC fällt diese Rettung weg.
  16. Memory-mapped Files: FileChannel.map erzeugt einen MappedByteBuffer. Er zählt nicht zu MaxDirectMemorySize. Er belegt Seiten des Betriebssystems.
  17. Compact Object Headers: Seit Java 25 gibt es -XX:+UseCompactObjectHeaders (JEP 519). Der Objekt-Header schrumpft von 12 auf 8 Bytes. Das spart Heap bei vielen kleinen Objekten. Es ist nicht standardmässig an.

4. Fallen

  • „Klassen-Metadaten liegen in der PermGen.“ → Falsch. Die PermGen gibt es seit Java 8 nicht mehr. Metadaten liegen im Metaspace im nativen Speicher.
  • „-Xmx2g heisst, der Prozess braucht 2 GB.“ → Falsch. Dazu kommen Metaspace, Stacks, Code Cache, Direct Memory und GC-Strukturen.
  • „Primitive liegen immer auf dem Stack.“ → Falsch. Nur lokale Variablen. Ein int-Feld eines Objekts liegt im Heap.
  • „Objekte liegen manchmal auf dem Stack.“ → Nicht ganz. HotSpot macht keine echte Stack-Allokation. Escape Analysis zerlegt ein Objekt höchstens in Variablen (Scalar Replacement).
  • „Der Metaspace ist begrenzt wie der Heap.“ → Falsch. Ohne MaxMetaspaceSize wächst er, bis das System oder der Container keinen Speicher mehr hat.
  • „Statische Variablen liegen im Metaspace.“ → Falsch. Sie liegen seit Java 8 im Heap, im Class-Objekt.
  • „MetaspaceSize ist die Maximalgrösse.“ → Falsch. Es ist die Schwelle für den ersten Metadaten-GC. Das Maximum ist MaxMetaspaceSize.

5. Selbsttest

Warum?

Warum ist new so schnell?

Jeder Thread hat einen TLAB im Eden. Ein neues Objekt verschiebt dort nur einen Zeiger, ohne Lock.

Warum wurde die PermGen durch den Metaspace ersetzt?

Die PermGen hatte eine feste Grösse und führte oft zu „OutOfMemoryError: PermGen space“. Der Metaspace wächst nach Bedarf im nativen Speicher.

Was sind Young und Old Generation?

Neue Objekte entstehen im Young-Bereich (Eden, Survivor). Objekte, die mehrere GCs überleben, kommen in die Old Generation. Grund: Die meisten Objekte sterben jung.

Warum ist der Prozess immer grösser als -Xmx?

Metaspace, Code Cache, Direct Memory, Thread-Stacks und GC-Strukturen liegen ausserhalb des Heaps. -Xmx begrenzt nur den Heap.

Wie innen?

Welche Speicherbereiche hat die JVM?

Heap für Objekte, ein Stack pro Thread, Metaspace für Klassen-Metadaten, Code Cache für JIT-Code und Direct Memory für NIO-Puffer. Dazu kommt nativer Speicher für GC und JVM-Interna.

Ist der Heap thread-sicher? Ist der Stack geteilt?

Der Heap ist von allen Threads geteilt, darum braucht geteilter Zustand Synchronisation. Der Stack gehört genau einem Thread und ist nie geteilt.

Was ist ein Humongous Object?

Ein Objekt in G1, das mindestens eine halbe Region gross ist. Es kommt direkt in eigene Regionen der Old Generation.

Wo liegen die Stacks von Virtual Threads?

Ihre Frames liegen als Stack Chunks im Heap, solange sie nicht laufen. Beim Laufen werden sie auf den Stack des Carrier-Threads kopiert.

Was ist der Metaspace?

Nativer Speicher für Klassen-Metadaten: Methoden, Bytecode, Constant Pool. Er ersetzt seit Java 8 die PermGen und hat standardmässig keine Grenze.

Was ist die Compressed Class Space?

Ein Teil des Metaspace für Klassenstrukturen, auf die Objekt-Header mit 32-Bit-Zeigern zeigen. Standard: 1 GB reserviert.

Wann wird Metaspace frei?

Wenn der Class Loader einer Klasse unerreichbar ist und der GC ihn einsammelt. Einzelne Klassen werden nicht entladen.

Wo liegen statische Felder und der String Pool?

Beide liegen im Heap. Statische Felder hängen am java.lang.Class-Objekt.

Was ist der Code Cache?

Nativer Speicher für Maschinencode vom JIT. Er ist in drei Segmente geteilt und hat standardmässig 240 MB.

Was ist Direct Memory und wer nutzt ihn?

Nativer Speicher für Direct ByteBuffers. NIO, Netty und Datenbanktreiber nutzen ihn, um Kopien zwischen Heap und Betriebssystem zu sparen.

Wie wird Direct Memory freigegeben?

Wenn der GC das ByteBuffer-Objekt im Heap einsammelt, gibt ein Cleaner den nativen Speicher frei. Ist das Limit erreicht, ruft die JDK selbst System.gc() auf.

Was ist Native Memory Tracking?

Eine JVM-Funktion, die den nativen Speicher nach Bereichen zählt. Einschalten mit -XX:NativeMemoryTracking=summary, lesen mit jcmd VM.native_memory.

Was ist der Unterschied zwischen reserved und committed?

Reserved ist reservierter Adressraum ohne echten Speicher. Committed ist wirklich belegter Speicher und zählt für RSS und Container-Limit.

Liegen Objekte bei HotSpot je auf dem Stack?

Nein. Escape Analysis kann ein Objekt aber in Einzelwerte zerlegen (Scalar Replacement). Dann gibt es gar kein Objekt mehr.

Zahlen

Wie gross ist der Heap ohne -Xmx?

25 % des verfügbaren RAM (MaxRAMPercentage=25). Im Container auf Linux sind es 25 % des cgroup-Limits.

Was macht -XX:MaxRAMPercentage?

Es setzt den maximalen Heap als Anteil am RAM oder Container-Limit. Gut für Container, weil der Heap mit dem Pod-Limit mitwächst.

Was macht -Xss?

Es setzt die Stack-Grösse pro Plattform-Thread, meist 1 MB. Kleiner erlaubt mehr Threads, aber weniger Rekursionstiefe.

Wie gross darf Direct Memory werden?

So gross wie MaxDirectMemorySize. Ohne das Flag gilt Runtime.maxMemory(), also etwa -Xmx.

Was bringen Compact Object Headers?

Seit Java 25 (JEP 519) schrumpft der Objekt-Header mit -XX:+UseCompactObjectHeaders auf 8 Bytes. Das spart Heap bei vielen kleinen Objekten.

Vergleich

Was liegt im Heap, was auf dem Stack?

Im Heap liegen alle Objekte und Arrays. Auf dem Stack liegen Frames mit lokalen Variablen, primitiven Werten und Referenzen auf Heap-Objekte.

Was ist der Unterschied zwischen StackOverflowError und OutOfMemoryError?

StackOverflowError: Der Stack eines Threads ist voll, meist durch zu tiefe Rekursion. OutOfMemoryError: Ein Speicherbereich wie Heap oder Metaspace hat keinen Platz mehr.

Was ist der Unterschied zwischen MetaspaceSize und MaxMetaspaceSize?

MetaspaceSize ist die Schwelle für den ersten GC wegen Metadaten. MaxMetaspaceSize ist die harte Obergrenze.

Metaspace vs. PermGen?

Die PermGen hatte eine feste Grösse. Der Metaspace liegt im nativen Speicher, hat standardmässig keine Grenze und existiert seit Java 8.

Heap vs. Direct Memory?

Der Heap wird vom GC verwaltet und mit -Xmx begrenzt. Direct Memory ist nativer Speicher für NIO-Puffer und wird mit MaxDirectMemorySize begrenzt.

Produktion

Was ist Container Awareness?

Die JVM liest auf Linux die cgroup-Limits für CPU und Speicher. Heap-Grösse und Thread-Zahlen richten sich dann nach dem Container, nicht nach dem Host.

Szenario: Der Pod hat 2 GiB, -Xmx ist 2g, und Kubernetes beendet ihn mit Exit-Code 137. Warum?

Der Prozess braucht mehr als den Heap: Metaspace, Stacks, Code Cache, Direct Memory, GC. Er sprengt das Limit, und der Kernel beendet ihn. Lösung: MaxRAMPercentage um 70–75 und NMT prüfen.

Szenario: RSS steigt, aber der Heap ist stabil. Wie gehen Sie vor?

NMT einschalten, baseline setzen und später summary.diff vergleichen. Wächst Other, Thread oder Metaspace, ist es Direct Memory, Threads oder Class Loader. Wächst nichts in NMT, liegt es in nativen Bibliotheken.

Szenario: Eine Rekursion über einen tiefen Baum wirft StackOverflowError. Was tun Sie?

Zuerst die Rekursion in eine Schleife mit eigenem Stack (Deque) umbauen. Nur als Notlösung -Xss erhöhen oder die Arbeit in einem Thread mit grossem Stack starten.

Szenario: Die Anwendung wird langsam, im Log steht „CodeCache is full. Compiler has been disabled.“ Was tun Sie?

Der Code Cache ist voll, darum stoppt der JIT. Mit jcmd Compiler.codecache den Füllstand prüfen und -XX:ReservedCodeCacheSize erhöhen.

Design

Wie legen Sie -Xmx im Container fest?

Mit MaxRAMPercentage auf etwa 70–75 % des Limits statt festem -Xmx. Der Rest bleibt für nativen Speicher.

Wann setzen Sie -Xms gleich -Xmx?

In Containern spart das Resize-Arbeit und zeigt Fehler sofort. Der Preis ist, dass der Speicher immer belegt ist.

Warum setzen Sie MaxMetaspaceSize und MaxDirectMemorySize?

Sie machen aus einem Container-Kill einen klaren Java-Fehler mit Stacktrace.

Wann lohnt sich Off-Heap?

Direct Memory spart Kopien beim I/O und GC-Arbeit. Dafür sind Leaks schwerer zu finden, und Heap Dumps zeigen den Inhalt nicht.

Mehr

Gerüst

  • Warum? Getrennte Bereiche mit eigenen Grenzen. Jeder Fehler zeigt auf einen Bereich (Java heap space, Metaspace, StackOverflowError).
  • Wie innen? Heap (Eden, Survivor, Old) für Objekte, ein Stack mit Frames pro Thread. Metaspace, Code Cache und Direct Memory sind nativ.
  • Zahlen Ohne -Xmx 25 % des RAM als Heap. Stack meist 1 MB. Code Cache 240 MB. Compressed Class Space 1 GB reserviert.
  • Vergleich Heap, Stack, Metaspace, Code Cache, Direct Memory. Metaspace statt PermGen seit Java 8.
  • Produktion Pod mit Exit-Code 137 ohne Java-Fehler: Der Prozess ist grösser als das Limit.
  • Design Heap 50–75 % des Limits. MaxMetaspaceSize und MaxDirectMemorySize setzen. Off-Heap ist ein Trade-off.

Echte Ausgabe, OpenJDK 17.0.3 (Windows x64, G1). Der Java-Code ist gekürzt. Die NMT-Ausgabe ist gekürzt: Unterzeilen und kleine Kategorien (Symbol, Arena Chunk) fehlen. Java 21 und 25 zeigen die gleichen Pools und NMT-Kategorien; die Zahlen und Details weichen leicht ab. Die Stack-Tiefe schwankt von Lauf zu Lauf, weil der JIT die Frame-Grösse ändert.

  1. Heap-Pools: G1 zeigt drei Pools: Eden, Survivor, Old Gen. Nur Old Gen hat ein festes max (64 MB = -Xmx). Eden und Survivor haben keine feste Grenze, weil G1 ihre Grösse laufend anpasst.
  2. Metaspace: max=-1 heisst: keine Grenze, solange -XX:MaxMetaspaceSize fehlt. Die Compressed Class Space hat dagegen 1024 MB Grenze.
  3. Code Cache: Er besteht aus drei CodeHeaps: non-nmethods (JVM-interner Code), profiled (C1) und non-profiled (C2). 7 + 116 + 116 MB ≈ 240 MB.
  4. Stack: Mit Standard-Stack (1 MB) gehen ca. 22 000 Aufrufe. Mit -Xss256k nur ca. 3 000. Der Stack ist also klein und fest pro Thread.
  5. Direct Memory: Der 8-MB-Puffer erscheint im BufferPoolMXBean und in NMT unter Other, nicht im Heap.
  6. Prozess vs Heap: NMT zeigt 160 MB committed bei nur 64 MB Heap. Allein der GC braucht hier 61 MB für seine Strukturen. Reserved heisst Adressraum reserviert, committed heisst echter Speicher belegt.

Vergleich

  • Heap: Objekte und Arrays · geteilt · -Xmx · GC räumt · Fehler: Java heap space.
  • Stack: Frames pro Thread · privat · -Xss · frei beim Methodenende · Fehler: StackOverflowError.
  • Metaspace: Klassen-Metadaten · nativ · -XX:MaxMetaspaceSize · frei mit dem Class Loader · Fehler: Metaspace oder Compressed class space.
  • Code Cache: JIT-Maschinencode · nativ · -XX:ReservedCodeCacheSize · Fehler: kein OOM, sondern Warnung CodeCache is full. Compiler has been disabled.
  • Direct Memory: NIO-Puffer · nativ · -XX:MaxDirectMemorySize · frei, wenn der GC den Buffer einsammelt · Fehler: Cannot reserve … bytes of direct buffer memory.
  • PermGen (bis Java 7): Klassen-Metadaten im Heap-nahen festen Bereich. Gibt es seit Java 8 nicht mehr. Mit -XX:MaxPermSize startet Java 17 gar nicht: Unrecognized VM option.

In der Produktion

  1. Pod wird OOMKilled, ohne Java-Fehler: -Xmx ist zu nah am Container-Limit. Heap, Metaspace, Stacks, Direct Memory und GC zusammen sprengen das Limit. Der Kernel beendet den Prozess (Exit-Code 137). Lösung: -XX:MaxRAMPercentage=70 bis 75 statt festem -Xmx, Rest für nativen Speicher lassen.
  2. Alte JVM im Container sieht den ganzen Host: Ohne Container-Support (Java 8 vor 8u191) nimmt die JVM 25 % vom Host-RAM. Lösung: aktuelles JDK, Limit im Pod setzen.
  3. Viele Threads fressen Speicher: 2 000 Plattform-Threads reservieren bis zu 2 GB Stack. Lösung: Thread-Pools begrenzen oder Virtual Threads nutzen (Java 21+).
  4. Metaspace wächst nach Redeploys: Ein Application Server lädt die App neu, aber der alte Class Loader bleibt erreichbar. Lösung: Leak finden (siehe Memory Leaks), -XX:MaxMetaspaceSize als Schutz setzen.
  5. Direct Memory voll bei Netty: Netty-Puffer werden nicht freigegeben (release() fehlt). Lösung: Netty Leak Detector, -XX:MaxDirectMemorySize bewusst setzen.
  6. Code Cache voll: Viele generierte Klassen oder lange Laufzeit füllen den Code Cache. Der JIT stoppt. Lösung: -XX:ReservedCodeCacheSize erhöhen.

Diagnose: Werkzeuge und Flags

  • -XX:NativeMemoryTracking=summary (oder detail): schaltet NMT ein (Native Memory Tracking, zählt den nativen Speicher der JVM). Kostet etwa 5–10 % Leistung.
  • jcmd <pid> VM.native_memory summary scale=MB: zeigt alle Bereiche. baseline und später summary.diff zeigen, was wächst.
  • jcmd <pid> GC.heap_info: Heap- und Metaspace-Belegung auf einen Blick.
  • jcmd <pid> VM.metaspace und VM.classloader_stats: Metaspace pro Class Loader.
  • jcmd <pid> Compiler.codecache: Füllstand des Code Cache.
  • java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|MaxRAMPercentage": zeigt die echten Werte im Container.
  • -Xlog:gc* und -Xlog:gc+heap=debug: GC-Log mit Heap-Grössen. -Xlog:os+container=debug: zeigt erkannte Container-Limits.
  • JMX: MemoryPoolMXBean und BufferPoolMXBean für Monitoring, z. B. über Micrometer und Prometheus (jvm_memory_used_bytes).
  • Betriebssystem: RSS des Prozesses (ps, top, kubectl top pod) mit NMT vergleichen. Der Rest ist Speicher ausserhalb der JVM, z. B. von JNI oder malloc.

Senior-Punkte

  1. Heap ist nicht gleich Prozess. Plane den Pod als Heap + Metaspace + Threads × Stack + Direct Memory + Code Cache + GC. Faustregel: Heap 50–75 % des Limits, je nach Off-Heap-Bedarf.
  2. -Xms gleich -Xmx in Containern spart Resize-Arbeit und zeigt Fehler sofort. Der Preis: Der Speicher ist immer belegt.
  3. Grenzen für native Bereiche setzen: MaxMetaspaceSize und MaxDirectMemorySize machen aus einem Container-Kill einen klaren Java-Fehler mit Stacktrace.
  4. Off-Heap ist ein Trade-off: Direct Memory spart Kopien beim I/O und GC-Arbeit. Dafür sind Leaks schwerer zu finden, und Heap Dumps zeigen den Inhalt nicht.
  5. Virtual Threads verschieben Stack-Speicher in den Heap. Viele blockierte Virtual Threads erhöhen also den Heap-Bedarf, nicht die Thread-Stacks.
  6. Messen mit NMT, nicht raten. Ein Vergleich RSS vs NMT zeigt, ob das Problem in der JVM oder in nativen Bibliotheken liegt.
