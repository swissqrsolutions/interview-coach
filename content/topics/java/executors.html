ExecutorService und Thread Pools

Kern: Ein ExecutorService nimmt Aufgaben an und führt sie auf wiederverwendeten Threads aus. Er trennt „was tun" (Task) von „wer tut es" (Thread). Ein ThreadPoolExecutor steuert das mit vier Stellschrauben: Core-Grösse, Max-Grösse, Queue und Rejection Policy.

Antwort-Muster

Frage: Wie funktioniert ein ThreadPoolExecutor?

  1. Mechanismus: Ein neuer Task bekommt zuerst einen Core-Thread. Sind alle belegt, kommt er in die Queue. Erst wenn die Queue voll ist, startet ein Thread bis max.
  2. Zahl: Ein Pool hat sieben Parameter. Bei newFixedThreadPool ist die Queue unbegrenzt, darum wird max nie erreicht.
  3. Trade-off: Eine begrenzte Queue schützt den Heap. Dafür muss ich auf „voll" reagieren, zum Beispiel mit CallerRunsPolicy.
  4. Produktion: Ich gebe jedem langsamen Downstream einen eigenen Pool. Dann blockiert er nicht die ganze App.

1. Die Reise eines Tasks durch execute()

  1. Unter Core: Es laufen weniger als corePoolSize Threads. Der Pool startet einen neuen Thread, auch wenn andere frei sind.
  2. Queue zuerst: Sind alle Core-Threads da, kommt der Task in die Queue. Der Pool wächst noch nicht.
  3. Queue voll: Erst jetzt startet der Pool Threads bis maximumPoolSize. Diese Reihenfolge überrascht viele.
  4. Alles voll: Kein Platz in Queue und Pool. Der Rejection Handler entscheidet. Standard: AbortPolicy wirft RejectedExecutionException.
  5. Worker-Schleife: Ein Worker führt seinen ersten Task aus. Danach holt er den nächsten aus der Queue.
  6. Leerlauf: Threads über der Core-Grösse sterben nach keepAliveTime ohne Arbeit. Mit allowCoreThreadTimeOut(true) gilt das auch für Core-Threads.

Core-Threads entstehen standardmässig erst beim ersten Task (lazy). prestartAllCoreThreads() startet sie sofort.

2. Aufbau

  1. Aufrufer: übergibt einen Runnable oder Callable. Beispiel: ein Controller schickt einen Report-Job.
  2. Work Queue: eine BlockingQueue, also eine thread-sichere Warteschlange. Sie hält Tasks, bis ein Worker frei ist.
  3. Worker-Threads: wiederverwendete Platform Threads. Eine ThreadFactory erzeugt sie, z. B. mit sprechendem Namen.
  4. Rejection Handler: entscheidet, was bei Überlast passiert. Beispiel: Exception werfen oder den Aufrufer selbst rechnen lassen.
  5. Future: ein Platzhalter für das spätere Ergebnis. get() wartet darauf und liefert auch die Exception.

Was ein Thread selbst ist (Zustände, Interrupt), steht auf der Seite Threads. Diese Seite behandelt nur Pools.

3. Details, die Interviewer fragen

  1. Die sieben Parameter: corePoolSize, maximumPoolSize, keepAliveTime + TimeUnit, workQueue, threadFactory und handler. Bei fixer Grösse ist core gleich max.
  2. execute() in drei Schritten: Sind weniger als core Threads da, startet der Pool einen neuen. Sonst versucht er, den Task in die Queue zu legen. Klappt das nicht, startet er einen Thread bis max. Scheitert auch das, lehnt er den Task ab.
  3. Doppelte Prüfung: Nach dem Einreihen prüft der Pool noch einmal. Er schaut, ob er inzwischen herunterfährt oder ob kein Worker mehr lebt. So geht kein Task verloren.
  4. Worker-Schleife: Jeder Worker holt in einer Schleife den nächsten Task aus der Queue. Das ist die Wiederverwendung des Threads. Ein Thread über core wartet nur bis zur keepAliveTime, dann endet er. Ein Core-Thread wartet ohne Limit auf den nächsten Task.
  5. Queue-Wahl:
    • SynchronousQueue: Sie speichert nichts. Sie gibt den Task direkt an einen Thread (direct handoff). Sie braucht ein grosses max, sonst gibt es Rejection.
    • LinkedBlockingQueue ohne Grenze: max ist wirkungslos. Die Queue kann ohne Ende wachsen.
    • ArrayBlockingQueue (begrenzt): Sie schützt vor Ressourcen-Erschöpfung. Sie ist schwerer zu tunen. Für Produktion ist sie die richtige Wahl.
    • PriorityBlockingQueue: Tasks laufen nach Priorität. Sie ist unbegrenzt. Darum gilt die gleiche Gefahr wie bei LinkedBlockingQueue.
  6. Rejection Policies:
    • AbortPolicy (Standard): Sie wirft RejectedExecutionException.
    • CallerRunsPolicy: Der Aufrufer-Thread führt den Task selbst aus. Das ist einfache Backpressure.
    • DiscardPolicy: Sie verwirft den Task still. Nur nutzen, wenn das Ergebnis egal ist.
    • DiscardOldestPolicy: Sie wirft den ältesten wartenden Task weg und versucht es erneut. Laut Doku ist das „selten akzeptabel".
  7. Executors-Fabriken:
    • newFixedThreadPool(n): n Threads und eine unbegrenzte Queue.
    • newCachedThreadPool(): SynchronousQueue und Threads ohne Grenze. Leerlauf-Threads sterben nach 60 Sekunden.
    • newSingleThreadExecutor(): ein Thread und eine unbegrenzte Queue. Die Reihenfolge ist garantiert.
    • newScheduledThreadPool(n): für verzögerte und periodische Tasks.
    • newWorkStealingPool(): ein ForkJoinPool.
    • newVirtualThreadPerTaskExecutor() (Java 21): ein neuer Virtual Thread pro Task. Es ist kein Pool.
  8. execute vs submit: execute lässt eine Exception zum UncaughtExceptionHandler durch. submit speichert sie im Future. Wer get() nie aufruft, verliert sie.
  9. invokeAll / invokeAny: invokeAll wartet auf alle Tasks. invokeAny liefert das erste erfolgreiche Ergebnis. Den Rest bricht es ab.
  10. Shutdown-Muster: Erst shutdown(), dann awaitTermination(timeout), dann bei Bedarf shutdownNow(). Tasks müssen auf Interrupt reagieren. Sonst hilft shutdownNow() nicht.
  11. close() (Java 19): ExecutorService ist AutoCloseable. close() ruft shutdown() und wartet auf das Ende aller Tasks. Damit geht try-with-resources.
  12. Hooks: beforeExecute und afterExecute eignen sich für Metriken, MDC-Kontext und ThreadLocal-Aufräumen. terminated() läuft am Ende.
  13. ForkJoinPool: Jeder Worker hat eine eigene Deque (Warteschlange mit zwei Enden). Freie Worker stehlen Tasks aus fremden Deques. Das heisst Work Stealing. Es passt für rekursiv geteilte Arbeit (RecursiveTask).
  14. Common Pool: Das ist ein JVM-weiter ForkJoinPool. Parallel Streams und CompletableFuture-Async-Methoden ohne Executor nutzen ihn. Die Grösse steuert die Property java.util.concurrent.ForkJoinPool.common.parallelism. Laut Java-25-Doku ist setParallelism besser.
  15. ManagedBlocker: Blockiert ein ForkJoin-Task auf I/O, kann der Pool mit ForkJoinPool.managedBlock Ersatz-Threads starten. Ohne das garantiert er nichts.
  16. CompletableFuture und Pools: thenApply (ohne Async) läuft im Thread, der die Stufe abschliesst. Ist die Stufe schon fertig, läuft es im Aufrufer. thenApplyAsync ohne Executor springt in den Common Pool. Details zur Komposition stehen auf der Seite CompletableFuture.
  17. Timeouts: orTimeout und completeOnTimeout gibt es seit Java 9. future.get(timeout) bricht den Task nicht ab. Es wartet nur nicht länger.
  18. ForkJoinPool als Scheduler (Java 25): ForkJoinPool implementiert jetzt auch ScheduledExecutorService. Es gibt schedule und scheduleAtFixedRate.

4. Fallen

  • „Der Pool wächst bis max, bevor er Tasks in die Queue stellt." → Falsch. Erst Queue, dann max. Mit unbegrenzter Queue wird max nie erreicht.
  • „newFixedThreadPool ist sicher, weil er begrenzt ist." → Nur die Threads. Die Queue ist unbegrenzt.
  • „shutdown() bricht laufende Tasks ab." → Falsch. Das macht shutdownNow(), und auch nur per Interrupt.
  • „Exceptions in submit-Tasks erscheinen im Log." → Falsch. Sie stecken im Future, bis jemand get() aufruft.
  • „future.get(5, SECONDS) stoppt den Task nach 5 Sekunden." → Falsch. Nur das Warten endet. Abbrechen mit cancel(true).
  • „Virtual Threads sollte man in einen Pool stecken." → Falsch. Laut JEP 444 nie poolen. Begrenzen mit Semaphore.
  • „thenApplyAsync läuft im selben Pool wie die vorige Stufe." → Falsch. Ohne Executor-Argument immer im Common Pool.

5. Selbsttest

Warum?

Was ist ein ExecutorService?

Ein Dienst, der Tasks annimmt und auf wiederverwendeten Threads ausführt. Er liefert Futures und hat einen Lifecycle mit shutdown.

Warum Thread Pools statt new Thread()?

Threads sind teuer zu erzeugen. Ein Pool verwendet sie wieder und begrenzt ihre Zahl. So schützt er Speicher und CPU.

Warum erreicht ein Pool mit LinkedBlockingQueue nie maximumPoolSize?

Die unbegrenzte Queue ist nie voll. Neue Threads über core entstehen aber nur bei voller Queue.

Warum ist CallerRunsPolicy eine Form von Backpressure?

Der Aufrufer muss den Task selbst ausführen. In dieser Zeit schickt er keine neuen Tasks. So bremst er sich selbst.

Wie innen?

In welcher Reihenfolge wächst ein ThreadPoolExecutor?

Erst Threads bis core, dann die Queue füllen, dann Threads bis max. Danach Rejection.

Welche Parameter hat ThreadPoolExecutor?

corePoolSize, maximumPoolSize, keepAliveTime mit TimeUnit, workQueue, threadFactory und RejectedExecutionHandler.

Was ist eine SynchronousQueue?

Eine Queue ohne Kapazität. Sie übergibt den Task direkt an einen freien Thread. newCachedThreadPool nutzt sie.

Was macht keepAliveTime?

Threads über der Core-Grösse sterben nach dieser Leerlaufzeit. Mit allowCoreThreadTimeOut(true) auch Core-Threads.

Was ist Work Stealing?

Jeder ForkJoin-Worker hat eine eigene Deque. Ein freier Worker holt Tasks aus der Deque eines anderen. So bleiben alle Kerne beschäftigt.

Was ist der Common Pool?

Ein JVM-weiter ForkJoinPool. Ihn nutzen Parallel Streams und CompletableFuture-Async-Methoden ohne Executor. Im Beispiel oben hatte er CPUs − 1 = 15 Threads.

Wo läuft thenApply und wo thenApplyAsync?

thenApply läuft im Thread, der die vorige Stufe abschliesst, oder im Aufrufer. thenApplyAsync ohne Executor läuft im Common Pool.

Wofür sind beforeExecute und afterExecute?

Hooks um jeden Task: Metriken, Logging-Kontext setzen, ThreadLocals aufräumen, Exceptions loggen.

Zahlen

Wie gross machen Sie einen Pool?

CPU-Arbeit: etwa Anzahl Kerne. I/O: mehr, grob Kerne × (1 + Wartezeit / Rechenzeit). Dann unter Last messen.

Wie viele Parameter hat ThreadPoolExecutor und was ist bei fixer Grösse anders?

Es sind sieben Parameter. Bei fixer Grösse ist core gleich max.

Vergleich

execute() oder submit()?

execute gibt nichts zurück, Exceptions gehen zum UncaughtExceptionHandler. submit liefert ein Future, die Exception steckt darin.

Wann ForkJoinPool statt ThreadPoolExecutor?

Für rekursiv teilbare CPU-Arbeit mit fork und join. Für blockierende I/O ist er ungeeignet.

Soll man Virtual Threads poolen?

Nein. Sie sind billig, pro Task ein neuer. Zum Begrenzen eines knappen Downstreams eine Semaphore nutzen.

Was hat sich in Java 19 und 25 am ExecutorService geändert?

Java 19: ExecutorService ist AutoCloseable mit close(). Java 25: ForkJoinPool implementiert auch ScheduledExecutorService.

Was ist der Unterschied zwischen shutdown() und shutdownNow()?

shutdown nimmt nichts Neues an und lässt alles fertig laufen. shutdownNow unterbricht laufende Tasks und gibt die wartenden zurück.

Welche Rejection Policies gibt es?

AbortPolicy (Exception, Standard), CallerRunsPolicy (Aufrufer rechnet selbst), DiscardPolicy (still verwerfen), DiscardOldestPolicy (ältesten wegwerfen, neu versuchen).

Produktion

Was ist an Executors.newFixedThreadPool riskant?

Die Queue ist unbegrenzt. Unter Dauerlast wächst sie, bis Latenz und Heap explodieren.

Was ist an newCachedThreadPool riskant?

Die Thread-Zahl hat keine Grenze. Bei langsamen Downstreams entstehen Tausende Threads.

Was ist ein Pool-Deadlock?

Tasks warten mit get() auf Unter-Tasks im selben vollen Pool. Die Unter-Tasks finden keinen Thread. Alles steht.

Bricht future.get(timeout) den Task ab?

Nein. Es wirft TimeoutException und wartet nicht weiter. Abbrechen geht mit cancel(true), das den Thread unterbricht.

Warum sollte man supplyAsync einen Executor geben?

Ohne Executor läuft blockierende Arbeit im Common Pool. Das bremst Parallel Streams und andere Async-Aufrufe der ganzen JVM.

Szenario: Unter Last steigt die Latenz minutenlang, dann kommt OutOfMemoryError. Der Pool ist newFixedThreadPool(20). Was ist los?

Die unbegrenzte Queue wächst, weil Tasks schneller kommen, als 20 Threads sie abarbeiten. Lösung: begrenzte Queue, Rejection mit Fehler oder Backpressure, Queue-Länge als Metrik.

Szenario: Alle Worker eines Pools stehen im Thread Dump in Future.get(). Was vermuten Sie?

Einen Pool-Deadlock: Tasks warten auf Unter-Tasks im selben Pool. Lösung: eigener Pool für Unter-Tasks oder nicht blockierend mit thenCompose komponieren.

Szenario: Parallel Streams werden langsam, seit ein Kollege CompletableFuture für HTTP-Aufrufe nutzt. Warum?

Die HTTP-Aufrufe blockieren im Common Pool, ohne eigenen Executor. Parallel Streams teilen diesen Pool. Lösung: eigenen I/O-Executor an supplyAsync übergeben oder Virtual Threads nutzen.

Design

Welche Queue wählen Sie für Produktion?

Eine begrenzte, z. B. ArrayBlockingQueue. Dazu eine bewusste Rejection Policy und Metriken für die Queue-Länge.

Wie fahren Sie einen Pool sauber herunter?

shutdown, dann awaitTermination mit Timeout, dann shutdownNow. Seit Java 19 auch close() mit try-with-resources.

Wofür braucht man eine eigene ThreadFactory?

Für sprechende Namen, Daemon-Status und einen UncaughtExceptionHandler. Namen machen Thread Dumps lesbar.

Szenario: Ein Service ruft zwei Downstreams auf, einer wird langsam. Wie schützen Sie den anderen?

Pro Downstream ein eigener Pool (Bulkhead) mit begrenzter Queue. Der langsame Dienst füllt dann nur seinen Pool, der andere läuft weiter.

Mehr

Gerüst

  • Warum? Threads sind teuer. Ein Pool nutzt sie wieder und begrenzt ihre Zahl.
  • Wie innen? Erst Threads bis core, dann Queue füllen, dann Threads bis max, dann Rejection.
  • Zahlen Sieben Parameter. CPU-Arbeit: etwa Anzahl Kerne. I/O: Kerne × (1 + Wartezeit / Rechenzeit).
  • Vergleich ForkJoinPool: eigene Deque pro Worker, Work Stealing. Virtual Threads: ein Thread pro Task, kein Pool.
  • Produktion Unbegrenzte Queue frisst den Heap. Blockierender Code im Common Pool bremst die ganze JVM.
  • Design Jede Queue hat eine Grenze und eine Antwort auf „voll". Pro Downstream ein eigener Pool (Bulkhead).

  2. Task 7 findet keinen Platz: AbortPolicy wirft die Exception. Die anderen 6 Tasks laufen fertig.

Vergleich

  • new Thread() pro Task: keine Grenze, teuer, kein Rückgabewert. Nur für einzelne, lange Hintergrund-Threads.
  • ThreadPoolExecutor: volle Kontrolle über Grössen, Queue und Rejection. Standard für Platform Threads.
  • Executors.newFixedThreadPool: bequem, aber unbegrenzte Queue. In Produktion lieber selbst bauen.
  • ScheduledThreadPoolExecutor: für Timer und periodische Jobs. Ersetzt java.util.Timer, der bei einer Exception ganz stirbt.
  • ForkJoinPool: Work Stealing für teilbare CPU-Arbeit. Schlecht für blockierende I/O.
  • Virtual-Thread-Executor (Java 21): ein Thread pro Task, praktisch ohne Grenze. Für viele blockierende I/O-Tasks. Begrenzung über Semaphore. Siehe Seite Virtual Threads.
  • Spring ThreadPoolTaskExecutor: eine Hülle um ThreadPoolExecutor mit Lifecycle im Spring-Kontext.

In der Produktion

  1. Unbegrenzte Queue frisst den Heap: newFixedThreadPool nimmt unter Last immer weiter an. Die Latenz steigt, am Ende kommt OutOfMemoryError. Lösung: begrenzte Queue plus bewusste Rejection Policy.
  2. Thread-Explosion: newCachedThreadPool startet bei langsamen Downstreams Tausende Threads. Ergebnis: unable to create native thread. Lösung: Grenze setzen.
  3. Common Pool blockiert: Blockierende I/O in supplyAsync ohne Executor oder in Parallel Streams belegt den Common Pool. Andere Teile der App stehen dann. Lösung: eigener Executor für I/O.
  4. Pool-Deadlock (Starvation): Ein Task wartet mit get() auf einen Unter-Task im selben vollen Pool. Alle Threads warten, niemand arbeitet. Lösung: getrennte Pools oder nicht blockierend komponieren.
  5. Verschluckte Exceptions: Ein submit-Task scheitert, niemand ruft get(). Lösung: Exception im Task loggen oder afterExecute nutzen.
  6. Hänger beim Herunterfahren: Nicht-Daemon-Threads eines nie geschlossenen Pools halten die JVM am Leben. Lösung: Pool im Lifecycle schliessen (z. B. @PreDestroy, try-with-resources).
  7. ThreadLocal-Leck: Pool-Threads leben lange. Ein vergessenes ThreadLocal.remove() trägt Daten in den nächsten Task. Lösung: im finally oder in afterExecute aufräumen.
  8. Falsche Grösse im Container: Die JVM sieht das CPU-Limit des Containers. Ein Pool mit fixer Grösse 200 auf 1 CPU erzeugt viel Kontextwechsel. Lösung: Grösse aus Messung und availableProcessors() ableiten.

Diagnose: Werkzeuge und Befehle

  • Pool-Metriken: getPoolSize(), getActiveCount(), getQueue().size(), getCompletedTaskCount(). Als Gauge exportieren (z. B. Micrometer ExecutorServiceMetrics).
  • Thread Dump (jcmd <pid> Thread.print): alle Worker in WAITING bei LinkedBlockingQueue.take = Pool leer. Alle in Future.get = möglicher Pool-Deadlock. Siehe Seite Thread Dumps.
  • Sprechende Thread-Namen über eine eigene ThreadFactory, z. B. report-worker-3. Sonst steht im Dump nur pool-7-thread-3.
  • JFR: Events jdk.ThreadPark (warten in der Queue), jdk.JavaMonitorEnter, jdk.ThreadStart. Siehe Seite Profiling.
  • Rejection zählen: eigener Handler, der loggt und eine Metrik erhöht, dann die Standard-Policy aufruft.
  • ForkJoinPool: getStealCount(), getQueuedTaskCount(), toString() zeigt Zustand und Zähler.

Senior-Punkte

  1. Jede Queue braucht eine Grenze, und jede Grenze braucht eine Antwort auf „voll". Rejection ist Teil des API-Vertrags, kein Bug.
  2. Pool-Grösse ist Messung, nicht Formel. Startpunkt CPU-Arbeit: etwa Anzahl Kerne. Startpunkt I/O: Kerne × (1 + Wartezeit / Rechenzeit). Danach unter Last messen.
  3. Bulkhead: getrennte Pools pro Downstream. Ein langsamer Dienst blockiert dann nur seinen Pool, nicht die ganze App.
  4. CallerRunsPolicy ist einfache Backpressure. Aber sie blockiert den Aufrufer. Im Event-Loop- oder Kafka-Consumer-Thread kann das schaden.
  5. Kein blockierender Code im Common Pool. Für I/O immer einen eigenen Executor an *Async-Methoden übergeben.
  6. Ab Java 21 ändert sich die Frage: Für viele blockierende I/O-Tasks sind Virtual Threads oft einfacher als ein fein getunter Pool. Pools bleiben für CPU-Arbeit und als Grenze für knappe Ressourcen.
  7. Shutdown ist Pflicht: geordnet mit Timeout, Tasks müssen Interrupts beachten. Sonst hängen Deployments.
