Exceptions

Kern: Eine Exception ist ein Objekt, das einen Fehler meldet und den normalen Ablauf abbricht. Sie wandert den Call Stack hoch, bis ein passender catch sie fängt. Checked Exceptions muss man fangen oder deklarieren, unchecked nicht, und try-with-resources schliesst Ressourcen auch im Fehlerfall sicher.

Antwort-Muster

Frage: Was ist der Unterschied zwischen checked und unchecked Exceptions?

  1. Mechanismus: Checked Exceptions prüft der Compiler, man muss sie fangen oder mit throws deklarieren. Unchecked sind RuntimeException, Error und ihre Unterklassen (JLS §11.1.1).
  2. Zahl: Multi-Catch gibt es seit Java 7. try-with-resources kann seit Java 9 eine effektiv finale Variable nutzen.
  3. Trade-off: Checked passt zu erwartbaren Fehlern von aussen, passt aber schlecht zu Lambdas. Unchecked ist frei, braucht aber gute Doku.
  4. Produktion: Im Anwendungscode nehme ich meist unchecked und einen zentralen Handler, der einmal mit Stack Trace loggt.

1. Die Reise einer Exception

  1. throw: parse() wirft. Beim Erzeugen füllt der Konstruktor von Throwable den Stack Trace (fillInStackTrace). Das ist der teure Teil.
  2. Stack Unwinding: Hat die Methode keinen passenden catch, läuft ihr finally. Dann verlässt die Exception den Frame und geht zum Aufrufer.
  3. Wrap: importiere() fängt die technische Exception und wirft eine fachliche: new ImportFehler("…", e). Die alte ist die cause.
  4. try-with-resources: Beim Verlassen schliesst Java alle Ressourcen, in umgekehrter Reihenfolge.
  5. Suppressed: Wirft auch close(), geht diese Exception nicht verloren. Sie hängt als suppressed an der ersten.
  6. Handler oben: Ein zentraler Handler (z. B. @ControllerAdvice) loggt einmal mit Stack Trace und baut die Antwort.
  7. Kein Handler: Der Thread endet. Der UncaughtExceptionHandler gibt den Stack Trace aus. In einem Thread-Pool kann der Fehler sonst still verschwinden.

2. Aufbau

  1. Throwable: die Wurzel. Nur Throwables kann man werfen und fangen. Sie tragen Nachricht, Ursache (cause), Stack Trace und unterdrückte Exceptions.
  2. Error: schwere Probleme der JVM, z. B. OutOfMemoryError. Normaler Code fängt sie nicht.
  3. Exception: Fehler, mit denen ein Programm rechnen kann. Direkte Unterklassen sind checked, z. B. IOException.
  4. RuntimeException: unchecked. Meist Programmierfehler, z. B. NullPointerException, IllegalArgumentException.
  5. Regel (JLS §11.1.1): Unchecked sind RuntimeException, Error und ihre Unterklassen. Alles andere ist checked.

3. Details, die Interviewer fragen

  1. Checked vs unchecked: Checked prüft der Compiler (JLS §11.2). Man fängt sie oder deklariert sie mit throws. Unchecked prüft er nicht. Checked passt zu erwartbaren, behebbaren Fehlern von aussen, etwa einer fehlenden Datei. Unchecked passt zu Programmierfehlern und zu Fällen, die der Aufrufer nicht sinnvoll behandeln kann.
  2. Kritik an checked Exceptions: Sie lecken durch Schichten. Sie passen nicht zu Lambdas. Sie führen zu leeren catch-Blöcken. Spring übersetzt darum SQLException in die unchecked DataAccessException.
  3. try-with-resources (JLS §14.20.3): Es gilt für alles, was AutoCloseable implementiert. Es schliesst rückwärts. Seit Java 9 geht auch eine effektiv finale Variable, also try (r) { … }.
  4. Suppressed Exceptions: Dafür gibt es Throwable.addSuppressed und getSuppressed(). Mit klassischem finally überschreibt ein close-Fehler die eigentliche Exception. try-with-resources verhindert das.
  5. finally: Es läuft fast immer, auch bei return und Exception. Es läuft nicht bei System.exit, bei einem JVM-Absturz oder wenn der Prozess getötet wird. Man nutzt kein return und kein throw in finally.
  6. Multi-Catch (Java 7): catch (IOException | SQLException e) fängt mehrere Typen. Die Typen dürfen nicht verwandt sein. Die Variable e ist implizit final.
  7. Reihenfolge der catch-Blöcke: Spezifische Typen stehen vor allgemeinen. Ein unerreichbarer catch ist ein Compile-Fehler.
  8. Exception Chaining: Man gibt die Ursache immer weiter, also new XException(msg, e). Sonst geht der ursprüngliche Stack Trace verloren.
  9. Eigene Exceptions: Sie haben einen fachlichen Namen, etwa KundeNichtGefundenException. Sie haben Konstruktoren mit message und cause. Wichtige Felder wie kundenId gehören dazu. Meist leitet man von RuntimeException ab.
  10. Exceptions in Lambdas und Streams: Die Standard-Functional-Interfaces deklarieren keine checked Exceptions. Man kann im Lambda fangen und in UncheckedIOException wickeln. Man kann eine Schleife statt Stream nutzen. Man kann Fehler als Ergebnis-Objekt sammeln.
  11. Kosten: Teuer ist das Erfassen des Stack Traces, nicht try selbst. Für Kontrollfluss nutzt man nie Exceptions. Der Konstruktor Throwable(msg, cause, enableSuppression, writableStackTrace) kann den Stack Trace abschalten.
  12. Overriding und throws: Eine überschreibende Methode darf keine neuen oder breiteren checked Exceptions deklarieren. Weniger oder engere sind erlaubt.
  13. Exceptions in Threads: Bei ExecutorService.submit landet die Exception im Future. Wer get() nie aufruft, sieht sie nie. CompletableFuture braucht exceptionally oder handle.
  14. InterruptedException: Man verschluckt sie nicht. Man wirft sie weiter oder setzt Thread.currentThread().interrupt().
  15. Precise Rethrow (Java 7): catch (Exception e) { throw e; } wirft nur die checked Typen, die der try-Block wirklich werfen kann. Das gilt, wenn e nicht neu zugewiesen wird.

4. Fallen

  • „catch (Exception e) fängt alles.“ → Falsch. Errors wie OutOfMemoryError sind keine Exceptions.
  • „finally läuft immer.“ → Fast. Nicht bei System.exit, JVM-Absturz oder Kill.
  • „Ein Fehler in close() überschreibt die eigentliche Exception.“ → Nur bei try-finally. Bei try-with-resources wird er suppressed.
  • „try-Blöcke sind teuer.“ → Falsch. Teuer ist das Erfassen des Stack Traces beim Werfen.
  • „Checked Exceptions gehen in Lambdas.“ → Nicht mit Standard-Interfaces. Function deklariert kein throws.
  • „RuntimeException ist checked, weil sie von Exception erbt.“ → Falsch. RuntimeException und Unterklassen sind unchecked.
  • „return in finally ist harmlos.“ → Falsch. Es verschluckt jede Exception.

5. Selbsttest

Warum?

Warum muss catch spezifisch vor allgemein stehen?

Sonst wäre der spezifische Block unerreichbar. Der Compiler meldet das als Fehler.

Sind Exceptions teuer?

Das Erfassen des Stack Traces kostet. Für normalen Kontrollfluss darum keine Exceptions nutzen.

Warum verschwinden Exceptions in einem ExecutorService?

Bei submit() landet die Exception im Future. Ohne get() sieht sie niemand.

Warum fehlen manchmal Stack Traces bei NPE im Log?

Der JIT ersetzt sehr häufige eingebaute Exceptions durch vorgefertigte ohne Stack Trace. -XX:-OmitStackTraceInFastThrow schaltet das ab.

Warum übersetzt Spring SQLException in DataAccessException?

SQLException ist checked und herstellerspezifisch. Die unchecked DataAccessException-Hierarchie ist einheitlich und zwingt keine Schicht zu throws.

Wie innen?

Wie funktioniert try-with-resources?

Ressourcen, die AutoCloseable sind, werden am Ende automatisch geschlossen, auch bei Exception. Die Reihenfolge ist umgekehrt zur Öffnung.

Was sind suppressed Exceptions?

Exceptions aus close(), die während einer anderen Exception auftreten. Sie hängen an der ersten und sind über getSuppressed() lesbar.

Was passiert bei try-finally, wenn close() im finally wirft?

Die close-Exception ersetzt die ursprüngliche. Diese geht verloren. try-with-resources löst genau das.

Läuft finally immer?

Fast immer, auch bei return. Nicht bei System.exit, Absturz der JVM oder wenn der Prozess getötet wird.

Was passiert bei return im finally?

Es überschreibt den Rückgabewert und verschluckt jede Exception aus try oder catch.

Was ist Exception Chaining?

Eine neue Exception trägt die alte als cause. So bleiben fachlicher Kontext und technischer Stack Trace erhalten.

Was passiert, wenn in einem Stream eine Exception fliegt?

Die ganze Pipeline bricht ab. Restliche Elemente werden nicht verarbeitet, Teilergebnisse gehen verloren.

Zahlen

Was ist Multi-Catch?

Ein catch für mehrere unverwandte Typen mit |, seit Java 7. Die Variable ist implizit final.

Was sind Helpful NullPointerExceptions?

NPE-Meldungen, die den genauen null-Ausdruck nennen, z. B. den Rückgabewert von adresse(). Eingeführt mit JEP 358, in JDK 17 standardmässig an.

Seit welcher Java-Version kann try-with-resources eine vorhandene Variable nutzen?

Seit Java 9. Die Variable muss effektiv final sein, also try (r) { … }.

Vergleich

Was ist der Unterschied zwischen checked und unchecked Exceptions?

Checked muss man fangen oder deklarieren, der Compiler prüft das. Unchecked sind RuntimeException, Error und Unterklassen, ohne Pflicht.

Was ist der Unterschied zwischen Error und Exception?

Error sind schwere JVM-Probleme wie OutOfMemoryError, die man normal nicht behandelt. Exceptions sind Fehler, mit denen ein Programm rechnen kann.

Welche Regeln gelten für throws beim Overriding?

Die überschreibende Methode darf keine neuen oder breiteren checked Exceptions deklarieren. Unchecked sind frei.

Exception oder Optional / Ergebnis-Typ?

Exception für Ausnahmefälle. Optional oder ein Ergebnis-Typ für erwartbares „nicht gefunden“ oder Validierungsfehler, ohne Kosten für Stack Traces.

try-finally oder try-with-resources?

try-finally kann die echte Exception überschreiben. try-with-resources schliesst sicher, rückwärts, mit suppressed.

Produktion

Was tun mit InterruptedException?

Weiterwerfen oder das Interrupt-Flag wieder setzen. Nie still verschlucken, sonst hört der Thread nicht auf Abbruch.

Sollte man Exceptions loggen und dann weiterwerfen?

Nein. Das loggt denselben Fehler mehrfach. Entweder behandeln und loggen, oder wrappen und weiterwerfen.

Szenario: Ein Import von 1 Million Zeilen bricht bei einer kaputten Zeile komplett ab. Wie bauen Sie es um?

Jede Zeile einzeln validieren, Fehler mit Zeilennummer sammeln und gültige Zeilen verarbeiten. Am Ende Fehlerbericht. Der Import ist so idempotent wiederholbar.

Szenario: Nach einigen Stunden meldet der Service „Too many open files". Ursache?

Ein Ressourcen-Leck: Streams oder Connections werden im Fehlerfall nicht geschlossen. Lösung: try-with-resources und offene Handles mit lsof prüfen.

Szenario: Im Log steht nur „java.lang.NullPointerException" ohne Stack Trace. Was tun Sie?

Ältere Einträge suchen, wo der volle Trace noch geloggt wurde. Für die Analyse -XX:-OmitStackTraceInFastThrow setzen und den null-Ausdruck aus der Helpful-NPE-Meldung lesen.

Design

Wann nutzen Sie checked, wann unchecked?

Checked, wenn der direkte Aufrufer sinnvoll reagieren kann, z. B. Datei fehlt. Sonst unchecked, besonders für Programmierfehler.

Wie schreibt man eine gute eigene Exception?

Fachlicher Name, Konstruktoren mit message und cause, relevante Felder als Kontext. Meist unchecked.

Wie gehen Sie mit checked Exceptions in Lambdas um?

Im Lambda fangen und in eine unchecked wie UncheckedIOException wickeln, eine Schleife nutzen, oder Fehler als Ergebnis-Objekte sammeln.

Welche Fehlerstrategie wählen Sie für ein System?

Fachliche Exceptions, ein zentraler Handler und eine klare Zuordnung zu HTTP-Status oder Retry. Loggen nur dort, wo der Fehler endet.

Wann ist ein Retry sinnvoll?

Nur bei vorübergehenden Fehlern wie Timeout oder 503. Nie bei fachlichen Fehlern wie Validierung. Die Exception-Klasse sollte das unterscheiden.

Mehr

Gerüst

  • Warum? Fehler wandern den Call Stack hoch, bis jemand sie behandelt. Der Compiler zwingt bei checked Exceptions zur Entscheidung.
  • Wie innen? Der Konstruktor von Throwable füllt den Stack Trace. try-with-resources schliesst rückwärts und hängt close-Fehler als suppressed an.
  • Zahlen Multi-Catch seit Java 7, effektiv finale Variable in try seit Java 9. Helpful NPE per JEP 358 (Java 14).
  • Vergleich Checked: Compiler erzwingt. Unchecked: frei. try-finally kann die echte Exception überschreiben, try-with-resources nicht.
  • Produktion Verschluckte Exceptions, doppeltes Loggen, Ressourcen-Lecks, stille Fehler in Thread-Pools. Teuer ist der Stack Trace.
  • Design Eine Fehlerstrategie pro System, cause immer mitgeben. Bei Massenverarbeitung Fehler als Daten sammeln.

Echte Ausgabe, Oracle JDK 17.0.3 (java und javac). In Java 21 und 25 gleich.

  1. Ressourcen öffnen in Reihenfolge A, B und schliessen rückwärts B, A. Die Body-Exception gewinnt. Beide close-Fehler hängen als suppressed daran.
  2. return in finally verschluckt die Exception komplett. javac warnt (-Xlint:finally).
  3. Der Rückgabewert wird vor finally gemerkt. x = 99 ändert ihn nicht.
  4. Die fachliche Exception trägt die technische als cause. Im Stack Trace erscheint „Caused by:".
  5. Helpful NullPointerExceptions (JEP 358) nennen den genauen null-Ausdruck. In JDK 17 sind sie standardmässig an, wie die Ausgabe zeigt.
  6. Eine Exception im Stream bricht die ganze Pipeline ab. Die Elemente danach werden nicht verarbeitet.
  7. Alternative: Fehler als Daten behandeln. Gültige und ungültige Zeilen trennen statt abbrechen.
  8. Error ist keine Exception. catch (Exception e) fängt keine Errors.
  9. Auch Errors kann man fangen. Nach einem StackOverflowError ist der Stack wieder frei; nach OOM ist der Zustand oft unklar.

Vergleich

  • Checked: Compiler erzwingt Behandlung, gut für erwartbare externe Fehler, schlecht für Lambdas.
  • Unchecked: frei, gut für Programmierfehler und Framework-Code, Doku wichtig.
  • Error: nicht behandeln, ausser loggen und kontrolliert beenden.
  • try-finally: close-Fehler kann die echte Exception überschreiben.
  • try-with-resources: schliesst sicher, rückwärts, mit suppressed.
  • Exception werfen: für Ausnahmefälle.
  • Optional / Ergebnis-Typ: für erwartbares „nicht gefunden" oder Validierungsergebnisse, ohne Kosten für Stack Traces.

In der Produktion

  1. Verschluckte Exceptions: catch (Exception e) {} oder nur e.getMessage() loggen. Fehler sind unsichtbar. Lösung: mit Stack Trace loggen oder weiterwerfen.
  2. Doppeltes Loggen: Jede Schicht loggt und wirft weiter. Ein Fehler erscheint fünfmal im Log. Lösung: entweder behandeln und loggen, oder wrappen und werfen, nicht beides.
  3. Verlorene Ursache: throw new XException(e.getMessage()) ohne cause. Der echte Stack Trace fehlt. Lösung: cause immer mitgeben.
  4. Ressourcen-Leck: Streams, Connections oder Files ohne close. Folge: „Too many open files" oder leerer Connection-Pool. Lösung: try-with-resources.
  5. Stille Fehler in Thread-Pools: submit() ohne get(). Lösung: Future auswerten, execute() mit UncaughtExceptionHandler oder Logging im Task.
  6. Exceptions als Kontrollfluss: z. B. NumberFormatException für Validierung pro Zeile in einem grossen Import. Hohe CPU-Last durch Stack Traces. Lösung: vorher prüfen.
  7. Stack Traces fehlen im Log: Der JIT kann bei sehr häufigen eingebauten Exceptions vorgefertigte Instanzen ohne Stack Trace werfen (OmitStackTraceInFastThrow). Lösung: frühere Log-Einträge suchen oder das Flag beim Debuggen abschalten.

Diagnose: Werkzeuge und Befehle

  • Stack Trace lesen: oberste Zeile = wo geworfen, „Caused by:" ganz unten = eigentliche Ursache.
  • -XX:-OmitStackTraceInFastThrow: erzwingt volle Stack Traces für häufige NPE und Co.
  • JFR: Event jdk.JavaErrorThrow standardmässig; jdk.JavaExceptionThrow kann man aktivieren, um alle geworfenen Exceptions zu zählen.
  • jcmd <pid> Thread.print: zeigt hängende Threads, z. B. nach verschluckter InterruptedException.
  • javac -Xlint:finally,try: warnt vor return in finally und Problemen mit try-with-resources.
  • Monitoring (z. B. Grafana mit Log-Metriken): Rate der Exceptions pro Typ als Alarm.

Senior-Punkte

  1. Eine Fehlerstrategie pro System: fachliche Exceptions, ein zentraler Handler, klare Zuordnung zu HTTP-Status oder Retry.
  2. Behandeln oder weiterwerfen, nicht beides. Loggen nur dort, wo der Fehler endet.
  3. Unchecked als Standard in Anwendungscode, checked nur, wenn der direkte Aufrufer wirklich reagieren kann.
  4. Retry nur für vorübergehende Fehler (Timeout, 503), nie für fachliche (Validierung). Die Exception-Klasse sollte das unterscheiden.
  5. Exceptions tragen Kontext: IDs und Werte in die Nachricht, aber keine Passwörter oder Personendaten.
  6. Fehler als Daten bei Massenverarbeitung: eine kaputte Zeile darf nicht den ganzen Import stoppen. Fehlerliste sammeln und melden.
