Comparable vs Comparator

Kern: Comparable ist ein Interface, mit dem eine Klasse ihre eigene natürliche Ordnung festlegt (compareTo). Comparator ist ein separates Objekt, das eine zusätzliche Ordnung von aussen festlegt (compare). Beide lösen das Problem „Wie sortiere ich Objekte?“; Sortierung, TreeMap, TreeSet und PriorityQueue nutzen sie.

1. Wo sitzen Comparable und Comparator?

  1. Comparable (java.lang): Die Klasse implementiert compareTo(T other). Beispiel: String, Integer, LocalDate.
  2. Comparator (java.util): ein eigenes Objekt mit compare(T a, T b). Beispiel: Comparator.comparing(Person::city).
  3. Ergebnis: negativ heisst „a vor b“, 0 heisst „gleich“, positiv heisst „a nach b“. Nur das Vorzeichen zählt.
  4. Nutzer: Sortieren, sortierte Collections und Heaps fragen beide Interfaces. Ohne Comparator nutzen sie Comparable.

2. Die Reise eines Sortier-Aufrufs (die Geschichte zum Merken)

  1. Aufruf: list.sort(c) bekommt einen Comparator. Ist er null, nutzt Java die natürliche Ordnung (Comparable).
  2. Kopie: List.sort kopiert die Elemente in ein Array. ArrayList sortiert ihr internes Array direkt.
  3. TimSort: Für Objekte nutzt Java TimSort, eine Mischung aus Merge Sort und Insertion Sort. Er findet bereits sortierte Teilstücke (Runs) und fügt sie zusammen. Er ist stabil: Gleiche Elemente behalten ihre Reihenfolge.
  4. Jeder Vergleich: TimSort ruft O(n log n)-mal compare auf. Bricht der Comparator den Vertrag, kann TimSort das merken und wirft IllegalArgumentException: Comparison method violates its general contract!.
  5. Zurück: Das sortierte Array wird in die Liste geschrieben.

3. Beispiel: Ketten, null, Overflow, BigDecimal, Stabilität, Vertragsbruch

record Person(String name, String city, int age) implements Comparable<Person> {
  public int compareTo(Person o) { return Integer.compare(age, o.age); }
}
// Mia/Bern/31, Luca/Basel/25, Anna/Bern/25, Noah/null/40
Collections.sort(ps);                                                          // 1)
ps.sort(comparing(Person::city, nullsLast(naturalOrder())).thenComparing(Person::name)); // 2)
ps.sort(comparingInt(Person::age).reversed().thenComparing(Person::name));     // 3)
ps.sort(comparing(Person::city));                                              // 4)
Comparator<Integer> minus = (x, y) -> x - y; minus.compare(MIN_VALUE, 1);     // 5)
new BigDecimal("1.0") vs "1.00": equals, compareTo, HashSet, TreeSet           // 6)
A/30, B/20, C/30, D/20 nach Alter sortieren                                    // 7)
10 000 Zahlen mit Comparator (x, y) -> random(-1, 0, 1)                         // 8)
Arrays.sort({"b","A","a","B"}); dann mit CASE_INSENSITIVE_ORDER                 // 9)

2) city nullsLast, then name: [Luca, Anna, Mia, Noah]
3) age desc, then name: [Noah, Mia, Anna, Luca]
4) comparing(city) with null city: NullPointerException
5) (x - y): compare(MIN_VALUE, 1) = 2147483647 -> MIN_VALUE seems GREATER; Integer.compare = -1
6) equals=false compareTo=0 HashSet size=2 TreeSet size=1

Echte Ausgabe, Oracle JDK 17.0.3. Java 21 und 25 verhalten sich gleich. Ob TimSort einen Vertragsbruch erkennt, hängt von den Daten ab; bei anderen Daten sortiert er still falsch.

  1. Die natürliche Ordnung (Alter) gilt ohne Comparator. Luca und Anna sind gleich alt und bleiben in Eingabe-Reihenfolge.
  2. nullsLast stellt Noah ohne Stadt ans Ende. thenComparing entscheidet bei gleicher Stadt nach Name.
  3. reversed() dreht nur den Teil davor um. Danach kommt der Name aufsteigend.
  4. Ohne nullsLast wirft comparing bei null eine NullPointerException.
  5. x - y läuft über: MIN_VALUE - 1 ergibt MAX_VALUE. Das Vorzeichen stimmt nicht mehr. Integer.compare ist korrekt.
  6. BigDecimal ist nicht konsistent mit equals: 1.0 und 1.00 sind für compareTo gleich, für equals nicht. HashSet behält beide, TreeSet nur einen.
  7. Die Sortierung ist stabil: B vor D und A vor C bleiben erhalten.
  8. Ein zufälliger Comparator bricht die Transitivität. TimSort erkennt es hier und wirft.
  9. Die natürliche String-Ordnung vergleicht UTF-16-Codes: Grossbuchstaben kommen vor Kleinbuchstaben.

4. Details, die Interviewer fragen

  1. Der Vertrag:
    • Antisymmetrie: sgn(compare(a,b)) == -sgn(compare(b,a)).
    • Transitivität: a > b und b > c heisst a > c.
    • Gleichheit konsistent: compare(a,b) == 0 heisst, a und b vergleichen sich mit jedem c gleich.
  2. Konsistent mit equals: Empfohlen, aber nicht Pflicht. Ohne Konsistenz verhalten sich TreeSet und TreeMap anders als HashSet und HashMap. Die Klasse sollte das dokumentieren, wie BigDecimal.
  3. Fabrik-Methoden (Java 8): comparing, comparingInt/Long/Double, thenComparing, reversed, naturalOrder, reverseOrder, nullsFirst, nullsLast.
  4. comparingInt statt comparing: comparingInt vermeidet Autoboxing bei jedem Vergleich. Bei grossen Listen spart das Zeit und Garbage.
  5. Nie subtrahieren: a - b läuft bei grossen Werten über. Immer Integer.compare, Long.compare, Double.compare.
  6. Double: Double.compare behandelt NaN und -0.0 sauber. Mit < und > ist NaN mit nichts vergleichbar.
  7. Stabil oder nicht: List.sort, Collections.sort und Arrays.sort für Objekte sind stabil (TimSort). Arrays.sort für primitive Arrays nutzt Dual-Pivot Quicksort; Stabilität spielt dort keine Rolle.
  8. Lambda-Typ-Inferenz: comparing(p -> p.name()).reversed() kompiliert oft nicht, weil der Typ von p verloren geht. Lösung: Methoden-Referenz Person::name oder Typ angeben.
  9. Comparable bei Records und Enums: Enums sind Comparable nach ordinal(). Records sind es nicht automatisch.
  10. Comparator und Serialisierung: Eine serialisierbare TreeMap braucht einen serialisierbaren Comparator. Lambdas sind es nur mit Cast auf Comparator & Serializable.
  11. Sprache und Umlaute: Die natürliche String-Ordnung kennt keine Sprache. Für deutsche Sortierung: java.text.Collator.getInstance(Locale.GERMAN).

5. Vergleich

  • Comparable: in der Klasse, genau eine Ordnung, Methode compareTo(T), Paket java.lang. Nur möglich, wenn man die Klasse ändern kann.
  • Comparator: ausserhalb, beliebig viele Ordnungen, Methode compare(T, T), Paket java.util. Funktioniert auch für fremde Klassen.
  • equals: beantwortet nur „gleich oder nicht“. Keine Ordnung.
  • Collator: ein Comparator für Strings nach Sprachregeln (Umlaute, Gross/Klein).
  • Sortieren in der DB: ORDER BY nutzt die Collation der Datenbank. Sie kann von Java abweichen.

6. In der Produktion

  1. Subtraktions-Comparator: Sortierung bei grossen IDs oder Zeitstempeln falsch. Kein Fehler, nur falsche Reihenfolge. Lösung: Long.compare oder comparingLong.
  2. „Comparison method violates its general contract!“: Der Comparator ist nicht transitiv, z. B. durch Zufall, veränderliche Felder während der Sortierung oder falsche null-Behandlung. Lösung: Comparator aus comparing-Ketten bauen.
  3. NullPointerException beim Sortieren: Ein Feld ist manchmal null. Lösung: nullsFirst/nullsLast.
  4. Verlorene Einträge in TreeSet/TreeMap: Der Comparator liefert 0 für verschiedene Objekte. Lösung: mit einem eindeutigen Feld abschliessen, z. B. .thenComparing(Person::id).
  5. Paging mit instabiler Sortierung: Sortiert man nur nach Datum, wechseln gleiche Datums-Einträge zwischen Seiten. Lösung: immer einen eindeutigen Tiebreaker, in Java und in SQL.
  6. Java- und DB-Sortierung weichen ab: Umlaute oder Gross/Klein ergeben eine andere Reihenfolge. Lösung: an einer Stelle sortieren oder gleiche Regeln (Collator, Collation).

7. Diagnose: Werkzeuge und Befehle

  • Stack Trace mit java.util.TimSort.mergeHi oder mergeLo und „general contract“: Der Comparator ist kaputt.
  • Unit-Test für den Vertrag: für Testdaten prüfen, ob compare(a,b) und compare(b,a) entgegengesetzt sind und ob Transitivität gilt.
  • Property-based Tests (z. B. jqwik): viele zufällige Eingaben gegen den Vertrag.
  • Profiler: viel Zeit in compare und Integer.valueOf zeigt Boxing; comparingInt hilft.
  • Statische Analyse: SonarQube und SpotBugs melden Subtraktions-Comparatoren und compareTo ohne passendes equals.

8. Senior-Punkte

  1. Comparable nur für eine wirklich natürliche Ordnung. Geld nach Betrag, Datum nach Zeit. Alles andere als Comparator.
  2. Comparatoren deklarativ bauen. comparing().thenComparing() ist lesbar und hält den Vertrag. Eigene if-Ketten sind fehleranfällig.
  3. Immer einen eindeutigen Tiebreaker. Das macht Sortierung deterministisch, Paging stabil und TreeSet verlustfrei.
  4. compareTo konsistent mit equals halten, oder die Abweichung dokumentieren.
  5. Wo sortieren? Grosse Daten sortiert die Datenbank mit Index. Java sortiert, was schon im Speicher ist.

9. Aus dem Projekt

10. Fallen

  • „return a - b; ist ein guter Comparator.“ → Falsch. Overflow bei grossen Werten. Integer.compare(a, b).
  • „compareTo muss -1, 0 oder 1 liefern.“ → Falsch. Nur das Vorzeichen zählt. Darum nie auf == -1 prüfen.
  • „reversed() dreht die ganze Kette um.“ → Falsch. Es dreht nur den Comparator, auf dem es aufgerufen wird.
  • „compareTo 0 heisst equals true.“ → Nicht immer. BigDecimal 1.0 und 1.00.
  • „Collections.sort ist Quicksort.“ → Falsch. Für Objekte ist es TimSort, stabil. Quicksort nur für primitive Arrays.
  • „String-Sortierung ist alphabetisch.“ → Falsch. Sie ist nach UTF-16-Code: „B“ vor „a“, Umlaute am Ende.

11. Fragen

Was ist der Unterschied zwischen Comparable und Comparator?

Comparable definiert die natürliche Ordnung in der Klasse selbst. Comparator definiert weitere Ordnungen ausserhalb, auch für fremde Klassen.

Welche Methoden haben die Interfaces?

Comparable: compareTo(T other). Comparator: compare(T a, T b), plus viele default- und static-Methoden.

Was bedeutet der Rückgabewert?

Negativ: a kommt vor b. 0: gleich. Positiv: a kommt nach b. Nur das Vorzeichen zählt.

Welche Regeln muss ein Comparator erfüllen?

Antisymmetrie, Transitivität und konsistente Gleichheit. Sonst sortieren Algorithmen falsch oder werfen eine Exception.

Was heisst „consistent with equals“?

compare liefert genau dann 0, wenn equals true ist. Empfohlen, aber nicht Pflicht.

Nennen Sie eine JDK-Klasse, die nicht konsistent mit equals ist.

BigDecimal. 1.0 und 1.00 sind per compareTo gleich, per equals verschieden.

Warum ist a - b als Vergleich gefährlich?

Bei grossen Werten gibt es Integer-Overflow, und das Vorzeichen kippt. Integer.compare nutzen.

Wie sortieren Sie nach Stadt, dann nach Name?

Comparator.comparing(Person::city).thenComparing(Person::name).

Wie behandeln Sie null-Werte beim Sortieren?

Mit Comparator.nullsFirst oder nullsLast um den Schlüssel-Comparator, z. B. comparing(Person::city, nullsLast(naturalOrder())).

Warum comparingInt statt comparing?

comparingInt arbeitet mit int und vermeidet Autoboxing bei jedem Vergleich.

Welchen Algorithmus nutzt Collections.sort?

TimSort, eine Mischung aus Merge Sort und Insertion Sort. Er ist stabil und O(n log n).

Was heisst stabil?

Gleiche Elemente behalten ihre ursprüngliche Reihenfolge. Wichtig, wenn man nach mehreren Kriterien nacheinander sortiert.

Was bedeutet „Comparison method violates its general contract“?

TimSort hat erkannt, dass der Comparator nicht transitiv oder nicht symmetrisch ist. Der Comparator muss korrigiert werden.

Wie nutzt TreeMap den Comparator?

Für die Position im Baum und für Gleichheit. Liefert er 0, gilt der Schlüssel als gleich.

Wie sortieren Sie deutsche Wörter mit Umlauten richtig?

Mit java.text.Collator.getInstance(Locale.GERMAN) als Comparator.

Sind Enums Comparable?

Ja, nach der Reihenfolge der Deklaration (ordinal). Man kann compareTo bei Enums nicht überschreiben.

Warum kompiliert comparing(p -> p.name()).reversed() manchmal nicht?

Durch die Verkettung kann Java den Typ von p nicht ableiten. Lösung: Person::name oder den Typ explizit angeben.

Wie vergleichen Sie double-Werte?

Mit Double.compare. Es behandelt NaN und -0.0 korrekt.

Wann implementieren Sie Comparable?

Wenn die Klasse eine einzige, offensichtliche Ordnung hat, z. B. Geldbetrag oder Version. Sonst Comparator.

Szenario: Eine Liste nach Zeitstempel (long) ist manchmal falsch sortiert. Was prüfen Sie?

Ob der Comparator subtrahiert und auf int castet. Das läuft über. Lösung: Long.compare oder comparingLong.

Szenario: Eine paginierte API liefert ein Element doppelt und eines gar nicht. Woran liegt es?

Die Sortierung hat keinen eindeutigen Tiebreaker. Gleiche Werte wechseln zwischen Seiten. Lösung: zusätzlich nach ID sortieren, in SQL und Java.

Szenario: Nach einem Deployment wirft ein Sortier-Aufruf sporadisch IllegalArgumentException. Was tun Sie?

Stack Trace zeigt TimSort und den Vertrag. Den Comparator auf Transitivität prüfen, z. B. veränderliche Felder oder Sonderfälle. Mit comparing-Ketten neu bauen und einen Vertrags-Test schreiben.
