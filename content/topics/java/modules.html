Java-Module (JPMS)

Kern: Das Java Platform Module System (JPMS, seit Java 9) ist ein Modul-System, bei dem ein Modul in module-info.java erklärt, was es braucht (requires) und was es anbietet (exports). Es löst zwei Probleme des Classpath, denn alles public war für alle sichtbar und fehlende Abhängigkeiten fielen erst zur Laufzeit auf. Das JDK selbst ist seit Java 9 in Module zerlegt, die meisten Anwendungen laufen aber weiter auf dem Classpath.

Antwort-Muster

Frage: Was ist JPMS, und was bringt es?

  1. Mechanismus: Ein Modul erklärt in module-info.java mit requires und exports, was es braucht und anbietet. Beim Start löst die JVM alle requires auf.
  2. Zahl: Es gibt JPMS seit Java 9. In der Demo war ein jlink-Image 35 MB gross, das ganze JDK 290 MB.
  3. Trade-off: Man bekommt starke Kapselung und frühe Fehler. Dafür gibt es keine Versionen, und alte Bibliotheken brauchen --add-opens.
  4. Produktion: Bei Spring-Boot-Services bleibe ich meist auf dem Class Path. Ich prüfe mit jdeps auf JDK-Interna.

1. Die Reise beim Start einer modularen Anwendung

  1. Start: java -p out -m com.bank.app/com.bank.app.Main nennt das Root-Modul.
  2. Resolution: Die JVM folgt allen requires rekursiv. Dazu bindet sie Service-Provider (uses/provides).
  3. Prüfen: Fehlt ein Modul, gibt es einen Zyklus oder zwei Module mit demselben Paket (Split Package), startet die JVM gar nicht. Der Fehler kommt sofort, nicht Stunden später.
  4. Boot Layer: Der fertige Modul-Graph steht fest. Module, die niemand braucht, sind nicht geladen.
  5. Zugriff: Bei jedem Zugriff prüft die JVM: Liest A das Modul B? Exportiert B das Paket? Für tiefe Reflection: Öffnet B das Paket (opens)?

2. Aufbau

  1. Modul: eine Gruppe von Paketen mit Namen und module-info.class. Beispiel: com.bank.core.
  2. requires: Das Modul liest ein anderes Modul. Beispiel: com.bank.app requires com.bank.core.
  3. exports: Nur exportierte Pakete sind für andere sichtbar. public allein reicht nicht mehr. Beispiel: api ja, internal nein.
  4. JDK-Module: Das JDK besteht aus Modulen. java.base ist immer dabei.
  5. Module Path vs Class Path: Auf dem Module Path gelten die Regeln streng. Auf dem Class Path landet alles im Unnamed Module, das alle Module liest.

3. Details, die Interviewer fragen

  1. Direktiven in module-info: Es gibt sechs wichtige Direktiven.
    • requires X: liest Modul X.
    • requires transitive X: Wer mich liest, liest auch X. Man nutzt es für Typen von X in meiner API.
    • requires static X: nur zur Compile-Zeit nötig, zur Laufzeit optional. Beispiel: Annotationen.
    • exports P und exports P to M: Paket P ist für alle oder nur für Modul M sichtbar (qualified export).
    • opens P: Das Paket ist zur Laufzeit für tiefe Reflection offen, z. B. für Hibernate oder Jackson. open module öffnet alle Pakete.
    • uses S und provides S with Impl: Verbraucher und Anbieter von Services für ServiceLoader.
  2. Resolution: Schritt 1 zählt ab den Root-Modulen alle requires rekursiv auf. Schritt 2 baut daraus den Readability-Graph. Die Kanten sagen, welches Modul welches liest. Fehlt ein Modul oder gibt es einen Zyklus, scheitert die Resolution. Dann startet die JVM nicht.
  3. Readability-Fehler: Die Resolution scheitert auch, wenn ein Modul zwei Module mit gleichem Namen liest. Sie scheitert, wenn zwei Module dasselbe Paket an ein Modul exportieren. Das ist der Grund für das Verbot von Split Packages.
  4. exports und opens: exports gibt Compile- und Laufzeit-Zugriff auf public-Mitglieder. opens gibt nur zur Laufzeit Reflection-Zugriff auf alles, auch auf private.
  5. Drei Arten von Modulen: Benannte Module haben eine module-info. Automatische Module sind normale JARs auf dem Module Path. Ihr Name kommt aus Automatic-Module-Name im Manifest oder aus dem Dateinamen. Sie exportieren und öffnen alles. Das Unnamed Module enthält alles auf dem Class Path.
  6. Regeln: Es gibt keine Zyklen zwischen Modulen. Es gibt kein Split Package, also kein Paket in zwei Modulen. Jedes Modul liest java.base.
  7. Starke Kapselung des JDK: Seit Java 16 sind JDK-Interna standardmässig gesperrt. Seit Java 17 gibt es den Schalter --illegal-access nicht mehr. Zugriff geht nur mit --add-opens oder --add-exports. sun.misc.Unsafe liegt im Modul jdk.unsupported und war lange erreichbar.
  8. Kommandozeile: Die wichtigen Schalter sind -p (--module-path), -m (--module), --add-modules, --add-opens und --add-exports. Dazu kommen --add-reads, --list-modules, --describe-module und --show-module-resolution.
  9. ServiceLoader: Das Modul-System macht Plugins sauber. Der Verbraucher kennt nur das Interface. Anbieter registrieren sich mit provides.
  10. Module Import (Java 25, JEP 511): import module java.base; importiert alle exportierten Pakete eines Moduls auf einmal. Das ist erwartetes Verhalten laut Doku und nicht ausgeführt. Auf JDK 17 gibt es das nicht.
  11. Tests: Unit-Tests im selben Paket brauchen Zugriff auf interne Klassen. Maven Surefire und Gradle patchen dafür das Modul mit --patch-module. Oder sie laufen auf dem Class Path.

4. Fallen

  • „public heisst für alle sichtbar.“ → Nicht mehr in Modulen. Nur, wenn das Paket exportiert ist.
  • „exports erlaubt Reflection auf private Felder.“ → Falsch. Dafür braucht es opens.
  • „Seit Java 9 muss jede App ein Modul sein.“ → Falsch. Der Class Path funktioniert weiter. Das Unnamed Module liest alles.
  • „JPMS löst Versionskonflikte.“ → Falsch. Es kennt keine Versionen und erlaubt kein Modul zweimal.
  • „Maven-Module und JPMS-Module sind dasselbe.“ → Falsch. Maven strukturiert den Build, JPMS prüft zur Compile- und Laufzeit.
  • „--add-opens ist eine dauerhafte Lösung.“ → Falsch. Es ist ein Übergang, bis die Bibliothek korrigiert ist.

5. Selbsttest

Warum?

Welche Probleme löst es?

Fehlende starke Kapselung (public war für alle sichtbar) und unzuverlässige Abhängigkeiten auf dem Class Path, die erst zur Laufzeit auffallen.

Was ist ein Split Package?

Dasselbe Paket in zwei Modulen. JPMS verbietet das; die App startet nicht.

Muss eine Spring-Boot-App modular sein?

Nein. Sie läuft normal auf dem Class Path. Volle Modularisierung ist selten und bringt wenig.

Warum scheitert die Resolution?

Ein Modul fehlt, es gibt einen Zyklus in den requires, ein Modul liest zwei Module mit gleichem Namen, oder zwei Module exportieren dasselbe Paket an ein Modul. Die JVM startet dann gar nicht.

Wie innen?

Was ist JPMS?

Das Java Platform Module System seit Java 9. Module erklären in module-info.java, was sie brauchen und was sie anbieten.

Was steht in module-info.java?

Der Modulname und Direktiven: requires, exports, opens, uses, provides.

Was ist das Unnamed Module?

Alles auf dem Class Path. Es liest alle Module und sieht deren exportierte Pakete. Benannte Module können es nicht lesen.

Was ist ein Automatic Module?

Ein normales JAR auf dem Module Path. Es bekommt einen Namen, exportiert und öffnet alles und liest alle Module.

Wie funktionieren Services im Modul-System?

Der Verbraucher erklärt uses S, der Anbieter provides S with Impl. ServiceLoader findet die Anbieter.

Sind Zyklen zwischen Modulen erlaubt?

Nein, nicht zur Compile-Zeit. Der Modul-Graph muss zyklenfrei sein.

Wie läuft die Resolution ab?

Schritt 1: Ab den Root-Modulen werden alle requires rekursiv aufgezählt. Schritt 2: Daraus entsteht der Readability-Graph. Seine Kanten sagen, welches Modul welches liest.

Zahlen

Was bedeutet starke Kapselung des JDK?

Interne JDK-Pakete sind seit Java 16 standardmässig gesperrt, seit Java 17 ohne Ausweg ausser --add-opens oder --add-exports.

Was ist ein Module Import in Java 25?

import module M; importiert alle exportierten Pakete eines Moduls auf einmal (JEP 511).

Wie viele Module hat das JDK?

In der Demo (JDK 17.0.3): 71. Im Boot Layer sind nur 40 geladen, mit --add-modules java.sql sind es 42.

Wie viel spart jlink?

In der Demo 35 MB statt 290 MB für das ganze JDK. Die Werte hängen von Plattform und Version ab.

Vergleich

requires vs requires transitive?

requires: nur ich lese das Modul. transitive: auch jeder, der mich liest. Nötig, wenn Typen des Moduls in meiner API vorkommen.

exports vs opens?

exports gibt Zugriff auf public-Typen zur Compile- und Laufzeit. opens gibt Reflection-Zugriff zur Laufzeit, auch auf private Mitglieder.

JPMS vs OSGi?

JPMS ist statisch, ohne Versionen, in der Plattform eingebaut. OSGi lädt dynamisch und erlaubt mehrere Versionen, ist aber viel komplexer.

Produktion

Wofür ist --add-opens?

Es öffnet ein Paket eines Moduls zur Laufzeit für Reflection, z. B. für alte Bibliotheken.

Szenario: Nach dem Upgrade von Java 11 auf 17 startet ein Service mit InaccessibleObjectException. Was tun Sie?

Im Stack Trace die Bibliothek finden, jdeps --jdk-internals laufen lassen, Bibliothek aktualisieren. Als Übergang gezielt --add-opens für genau dieses Paket setzen.

Szenario: Ein jlink-Image startet, aber TLS-Verbindungen schlagen fehl. Woran liegt es?

Benötigte Krypto-Module fehlen (bis Java 21 z. B. jdk.crypto.ec). Lösung: Modul-Liste mit jdeps --print-module-deps ermitteln, fehlende Module ergänzen, Image testen.

Was ist jdeps?

Ein Werkzeug, das Abhängigkeiten von Klassen und JARs analysiert und Nutzung von JDK-Interna findet.

Design

Was ist requires static?

Eine Abhängigkeit nur zur Compile-Zeit, zur Laufzeit optional. Zum Beispiel für Annotationen.

Was ist ein qualified export?

exports P to M: Das Paket ist nur für bestimmte Module sichtbar.

Woher kommt der Name eines Automatic Module?

Aus Automatic-Module-Name im Manifest, sonst aus dem Dateinamen des JARs.

Was ist jlink?

Ein Werkzeug, das eine eigene Java-Laufzeit nur mit den benötigten Modulen baut. Kleinere Images, weniger Angriffsfläche.

Szenario: Ein Team will interne Klassen einer Shared Library vor anderen Teams verstecken. Welche Optionen gibt es?

Mit JPMS nur das API-Paket exportieren. Leichter: Paketstruktur plus ArchUnit-Regeln im Build der Nutzer. Dazu Automatic-Module-Name als stabiler Name.

Wann setzen Sie Automatic-Module-Name?

Bei jeder Bibliothek, die noch nicht voll modularisiert ist. Das gibt einen stabilen Namen, ohne module-info.

Mehr

Gerüst

  • Warum? Der Class Path macht alles public sichtbar und meldet fehlende JARs erst zur Laufzeit. JPMS prüft beim Start und kapselt Pakete.
  • Wie innen? requires, exports, opens in module-info. Die Resolution baut beim Start den Readability-Graph. Danach prüft die JVM jeden Zugriff.
  • Zahlen Seit Java 9. Starke Kapselung: Java 16 Standard, Java 17 ohne Ausweg. Demo: jlink-Image 35 MB statt 290 MB.
  • Vergleich Class Path: einfach, alles sichtbar. JPMS: streng, keine Versionen. OSGi: dynamisch, mehrere Versionen.
  • Produktion InaccessibleObjectException nach dem Upgrade auf Java 17. Split Packages stoppen den Start. Ein jlink-Image braucht alle Module.
  • Design JPMS lohnt sich für Bibliotheken, selten für Spring-Boot-Services. Automatic-Module-Name setzen. --add-opens nur als Übergang.

Beispiel: zwei Module, Kapselung, Reflection, jdeps, jlink

module com.bank.core { exports com.bank.core.api; }      // internal wird NICHT exportiert
// src/com.bank.app/module-info.java
module com.bank.app { requires com.bank.core; }

javac -d out --module-source-path src $(find src -name "*.java")          // 1)
java -p out -m com.bank.app/com.bank.app.Main                             // 2)–5)

  Rates.class.getDeclaredField("hidden").setAccessible(true);
  ModuleLayer.boot().findModule("java.sql").isPresent();
javac … (App nutzt com.bank.core.internal direkt)                          // 6)
jdeps -s --module-path out -m com.bank.app                                // 7)

Echte Ausgabe, Oracle JDK 17.0.3 auf Windows (Pfade mit \). Mehrere Läufe zusammengefasst; „add-modules“ und „add-opens“ sind zusätzliche Läufe mit --add-modules java.sql bzw. --add-opens com.bank.core/com.bank.core.api=com.bank.app. Die Grössen hängen von Plattform und Version ab.

  1. javac kompiliert beide Module in einem Schritt.
  2. Der Aufruf über die exportierte API funktioniert. Jede Klasse kennt ihr Modul.
  3. Auch per Reflection ist ein nicht exportiertes Paket nicht erreichbar, obwohl Klasse und Methode public sind.
  4. Ein exportiertes Paket erlaubt nur Zugriff auf public. Für setAccessible auf private Felder muss das Paket geöffnet sein (opens). Mit --add-opens klappt es.
  5. Nur benötigte Module sind geladen. java.sql fehlt, bis man es mit requires oder --add-modules hinzufügt. Die 40 Module im Boot Layer kommen von java.base plus Service-Bindung.
  6. Schon der Compiler verweigert den Zugriff auf internal.
  7. jdeps zeigt die Modul-Abhängigkeiten. Für Classpath-JARs schlägt es eine module-info vor.
  8. requires transitive: Wer java.sql liest, liest automatisch auch java.xml. java.base ist immer dabei (mandated).
  9. jlink baut eine eigene Laufzeit nur mit den nötigen Modulen: 35 MB statt 290 MB für das ganze JDK.

Vergleich

  • Class Path: einfach, alles sieht alles. Fehlende JARs zeigen sich erst als ClassNotFoundException oder NoClassDefFoundError. Doppelte Klassen: die erste gewinnt („JAR Hell“).
  • JPMS: Abhängigkeiten und API explizit, Prüfung beim Start, starke Kapselung, jlink. Kein Versions-Management, keine zwei Versionen eines Moduls nebeneinander.
  • OSGi: dynamisches Laden und Entladen, mehrere Versionen nebeneinander. Viel komplexer; z. B. in Eclipse.
  • Maven/Gradle-Module: Build-Struktur, keine Laufzeit-Kapselung. Ergänzen JPMS, ersetzen es nicht.
  • ArchUnit: prüft Architektur-Regeln (wer darf wen nutzen) als Test, ohne JPMS. In der Praxis oft der leichtere Weg.

In der Produktion

  1. Upgrade auf Java 17 bricht: InaccessibleObjectException, weil eine Bibliothek JDK-Interna per Reflection nutzt. Lösung: Bibliothek aktualisieren; als Übergang gezielt --add-opens.
  2. Hibernate oder Jackson in modularer App: Sie brauchen Reflection auf Entities und DTOs. Lösung: opens com.x.entity to org.hibernate.orm.core bzw. an Jackson.
  3. Split Packages: Zwei JARs enthalten dasselbe Paket (z. B. alte javax-Bibliotheken). Auf dem Module Path startet die App nicht. Lösung: JARs zusammenführen, ersetzen oder auf dem Class Path bleiben.
  4. Automatic-Module-Namen ändern sich: Ohne Automatic-Module-Name leitet Java den Namen vom Dateinamen ab. Ein Umbenennen bricht requires.
  5. Kleine Container-Images: jlink baut eine schlanke Laufzeit. Wichtig: auch Module für Logging (java.logging), Locale-Daten (jdk.localedata) oder TLS-Kryptografie mitnehmen (welche, hängt von der Java-Version ab), sonst Fehler erst im Betrieb.
  6. Spring Boot: Fat JARs laufen auf dem Class Path. Volle Modularisierung einer Spring-Boot-App ist selten und bringt wenig.

Diagnose: Werkzeuge und Befehle

  • jdeps -s app.jar / jdeps --jdk-internals app.jar: Abhängigkeiten und Nutzung von JDK-Interna finden.
  • jdeps --print-module-deps: liefert die Modul-Liste direkt für jlink --add-modules.
  • java --list-modules, java --describe-module java.sql: Module und ihre Direktiven.
  • java --show-module-resolution …: zeigt, welches Modul warum geladen wird.
  • jar --describe-module --file x.jar: Ist das JAR ein Modul, und wie heisst es?
  • Exception-Text lesen: „module X does not export P to module Y“ oder „does not open P“ sagt genau, welche Direktive oder welcher Schalter fehlt.

Senior-Punkte

  1. JPMS ist für Bibliotheken und Plattformen wertvoll, für typische Spring-Boot-Services selten. Die meisten Apps profitieren indirekt: über das modulare JDK und jlink.
  2. Kapselung ist der Hauptnutzen. Eine Bibliothek kann endlich interne Pakete verstecken, obwohl Klassen darin public sind.
  3. Upgrade-Fähigkeit: Abhängigkeiten von JDK-Interna sind technische Schulden. jdeps im Build findet sie früh.
  4. Bibliotheken sollten mindestens Automatic-Module-Name setzen. Das gibt einen stabilen Namen ohne volle Modularisierung.
  5. Architektur-Regeln brauchen nicht immer JPMS. ArchUnit oder Build-Module sind oft billiger.
  6. jlink spart Image-Grösse und Angriffsfläche, braucht aber eine vollständige Modul-Liste und Tests.
