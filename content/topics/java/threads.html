Threads

Kern: Ein Thread ist ein eigener Ausführungsstrang mit eigenem Stack in einem JVM-Prozess. Er löst das Problem, mehrere Aufgaben gleichzeitig oder parallel zu erledigen. Alle Threads teilen sich den Heap, darum brauchen geteilte Daten Synchronisation.

1. Wo sitzt ein Thread?

  1. JVM-Prozess: Er enthält alle Threads der Anwendung. Beispiel: main, GC-Threads, JIT-Compiler-Threads.
  2. Heap: Alle Threads teilen ihn. Ein Objekt, das zwei Threads sehen, braucht Synchronisation.
  3. Platform Thread: Ein Platform Thread ist eine dünne Hülle um einen OS-Thread (1:1). Er hat einen eigenen Stack (Grösse über -Xss), einen Namen, eine Priorität und ein Interrupt-Flag.
  4. Virtual Thread (Java 21, JEP 444): Ein Virtual Thread ist ein leichter Thread der JVM. Er läuft abwechselnd auf wenigen Carrier Threads. Details auf der eigenen Seite.
  5. OS-Scheduler: Er entscheidet, welcher OS-Thread wann auf welchem CPU-Kern läuft. Java hat darauf kaum Einfluss.

2. Die Reise eines Threads durch seine Zustände (die Geschichte zum Merken)

  1. NEW: new Thread(task) erzeugt nur ein Java-Objekt. Es gibt noch keinen OS-Thread.
  2. RUNNABLE: start() erzeugt den OS-Thread und ruft run() darin auf. RUNNABLE heisst: läuft oder könnte laufen. Auch ein Thread, der im OS auf Netzwerk-I/O wartet, steht oft auf RUNNABLE.
  3. BLOCKED: Der Thread will in einen synchronized-Block. Ein anderer Thread hält den Monitor, also den Lock des Objekts. Der Thread wartet, bis der Lock frei ist.
  4. WAITING: Der Thread wartet ohne Zeitlimit auf einen anderen Thread. Auslöser: Object.wait(), join(), LockSupport.park(). Auch Warten auf einen ReentrantLock ist WAITING, nicht BLOCKED.
  5. TIMED_WAITING: Wie WAITING, aber mit Zeitlimit. Auslöser: Thread.sleep(ms), wait(ms), join(ms), parkNanos.
  6. Zurück zu RUNNABLE: Der Lock wird frei, ein notify kommt, das Zeitlimit endet oder ein Interrupt weckt den Thread.
  7. TERMINATED: run() ist fertig, normal oder mit einer Exception. Ein zweites start() wirft IllegalThreadStateException.

3. Beispiel: Zustände, Interrupt, Callable, Daemon

  2. Hält main den Lock, steht der Worker auf BLOCKED. In lock.wait() steht er auf WAITING. wait() gibt den Lock dabei frei.
  3. Nach join() ist er TERMINATED. join wartet, bis run() fertig ist.
  4. Der Interrupt weckt sleep mit InterruptedException. Das Flag ist danach gelöscht (false). Darum setzt der Handler es neu.
  5. Ein Callable liefert 42 über das Future. Seine Exception kommt erst bei get(), verpackt in ExecutionException.
  6. Der Daemon-Thread hält die JVM nicht am Leben. main endet, die JVM beendet sich.
  7. Im Dump zeigt - locked <0x…3308> den Besitzer, waiting to lock <0x…3308> den Wartenden. Gleiche Adresse heisst gleicher Lock.

4. Details, die Interviewer fragen

  1. Thread erzeugen: Drei Wege.
    • Runnable übergeben: new Thread(runnable, "name").start(). Bevorzugt: Aufgabe und Thread sind getrennt.
    • Thread erweitern: run() überschreiben. Selten sinnvoll, die Klasse ist dann an Thread gebunden.
    • Thread.Builder (Java 21): Thread.ofPlatform().name("worker-", 0).start(r) oder Thread.ofVirtual().start(r).
  2. start() vs run(): start() erzeugt einen neuen Thread. run() direkt aufgerufen läuft im aktuellen Thread, ganz normal wie eine Methode.
  3. Runnable vs Callable: Runnable hat void run() ohne Rückgabe und ohne checked Exception. Callable<V> hat V call() throws Exception. Callable läuft über einen ExecutorService und liefert ein Future.
  4. Interrupt: Ein Interrupt ist eine höfliche Bitte zum Aufhören. t.interrupt() setzt ein Flag. Blockierende Methoden wie sleep, wait, join werfen dann InterruptedException und löschen das Flag.
  5. isInterrupted() vs interrupted(): t.isInterrupted() liest das Flag. Das statische Thread.interrupted() liest und löscht es.
  6. InterruptedException richtig behandeln: Weiterwerfen oder Thread.currentThread().interrupt() aufrufen. Nie leer fangen, sonst geht das Stopp-Signal verloren.
  7. Nicht unterbrechbar: Warten auf synchronized (BLOCKED) und klassische Socket-I/O von Platform Threads reagieren nicht auf Interrupt. InterruptibleChannel wird bei Interrupt geschlossen (ClosedByInterruptException).
  8. Daemon: Ein Daemon-Thread ist ein Hintergrund-Thread. Die JVM beendet sich, wenn nur noch Daemon-Threads laufen. Deren finally-Blöcke laufen dann nicht. setDaemon geht nur vor start(), sonst IllegalThreadStateException. Ein neuer Thread erbt den Status seines Erzeugers.
  9. join: t.join() wartet, bis t endet. Es gibt eine happens-before-Garantie: Alle Writes von t sind danach sichtbar.
  10. sleep vs wait: sleep behält alle Locks. wait braucht den Monitor, gibt ihn frei und holt ihn nach dem Aufwachen zurück. wait gehört in eine while-Schleife, wegen Spurious Wakeups (Aufwachen ohne notify).
  11. Uncaught Exceptions: Eine Exception in run() beendet nur diesen Thread. Der UncaughtExceptionHandler druckt sie standardmässig auf System.err. Bei submit landet sie im Future und erscheint nirgends, bis jemand get() ruft.
  12. Priorität: setPriority (1–10) ist nur ein Hinweis an das OS. Bei Virtual Threads wird sie ignoriert (immer NORM_PRIORITY).
  13. Thread-ID: threadId() seit Java 19. getId() ist seit Java 19 deprecated.
  14. Thread.stop: Seit Java 1.2 deprecated, seit Java 20 wirft es immer UnsupportedOperationException. Es ist zum Entfernen markiert. suspend/resume gibt es in Java 25 nicht mehr.
  15. Platform vs Virtual (kurz): Ein Platform Thread kostet einen OS-Thread mit ca. 1 MB reserviertem Stack. Ein Virtual Thread kostet wenige KB im Heap. Virtual Threads sind immer Daemon und lohnen sich für viele blockierende I/O-Aufgaben, nicht für CPU-Arbeit.

5. Vergleich

  • Thread: ein einzelner Ausführungsstrang. Direkt nutzen nur für einfache, lang laufende Hintergrund-Aufgaben.
  • Runnable: eine Aufgabe ohne Ergebnis. Läuft in einem Thread oder Executor.
  • Callable: eine Aufgabe mit Ergebnis und checked Exception. Läuft im Executor, Ergebnis über Future.
  • ExecutorService: ein Thread-Pool. Er verwaltet Threads, Warteschlange und Shutdown. Standard für Anwendungen.
  • CompletableFuture: verkettet asynchrone Schritte ohne blockierendes get().
  • Platform Thread: 1:1 auf einen OS-Thread. Gut für CPU-Arbeit. Teuer in grosser Zahl.
  • Virtual Thread (Java 21): von der JVM geplant, billig. Gut für viele gleichzeitige I/O-Requests. Nie poolen.

6. In der Produktion

  1. Zu viele Threads: Ein neuer Platform Thread pro Request endet in OutOfMemoryError: unable to create native thread. Lösung: begrenzter Thread-Pool oder Virtual Threads für I/O.
  2. Shutdown hängt: Ein Task fängt InterruptedException und macht weiter. shutdownNow() wirkt dann nicht. Lösung: Interrupt-Flag wiederherstellen und die Schleife beenden.
  3. JVM beendet sich nicht: Ein vergessener Nicht-Daemon-Thread läuft noch, z. B. ein eigener Pool ohne shutdown(). Lösung: Pools sauber schliessen oder Daemon-Threads über eine ThreadFactory.
  4. Fehler verschwinden: Eine Exception in einem mit submit gestarteten Task erscheint nirgends. Lösung: Future.get() prüfen, oder Fehler im Task selbst loggen.
  5. Deadlock: Zwei Threads halten je einen Lock und warten auf den anderen. Beide stehen für immer auf BLOCKED. Lösung: Locks immer in derselben Reihenfolge nehmen, oder tryLock mit Timeout.
  6. ThreadLocal-Leak im Pool: Pool-Threads leben lange. Ein nicht gelöschter ThreadLocal hält Daten oder gibt sie an den nächsten Request weiter. Lösung: remove() im finally.
  7. Namenlose Threads: Im Dump steht nur Thread-17. Lösung: sprechende Namen über ThreadFactory oder Thread.Builder.

7. Diagnose: Werkzeuge und Befehle

  • jcmd <pid> Thread.print oder jstack <pid>: Thread Dump mit Zuständen und Locks. jstack meldet Deadlocks am Ende als Found one Java-level deadlock.
  • jcmd <pid> Thread.dump_to_file -format=json datei.json (Java 21): Dump inklusive Virtual Threads.
  • kill -3 <pid> (Linux): Thread Dump auf stdout der JVM.
  • Mehrere Dumps im Abstand von 5–10 Sekunden: Ein Thread, der immer an derselben Stelle steht, hängt dort.
  • JFR (Java Flight Recorder): Events jdk.ThreadStart, jdk.JavaMonitorEnter (Lock-Wartezeit), jdk.ThreadPark, jdk.VirtualThreadPinned.
  • ThreadMXBean: getThreadCount(), findDeadlockedThreads(). Auch sichtbar in JConsole und VisualVM.
  • top -H -p <pid> (Linux): CPU pro OS-Thread. Die nid im Dump ist dieselbe ID in Hex.
  • -Xss: Stack-Grösse pro Platform Thread. StackOverflowError heisst meist Rekursion, nicht zu kleiner Stack.

8. Senior-Punkte

  1. Kein new Thread() in Anwendungs-Code. Executor oder Framework nutzen. Sie geben Grenzen, Namen, Fehlerbehandlung und Shutdown.
  2. Interrupt ist ein Vertrag. Jeder lang laufende Task muss ihn prüfen und respektieren. Sonst funktioniert kein sauberer Shutdown und kein Timeout.
  3. Pool-Grösse ist eine Entscheidung: CPU-Arbeit → etwa Anzahl Kerne. Blockierende I/O → mehr Threads oder Virtual Threads. Immer eine begrenzte Queue.
  4. Virtual Threads ersetzen Pools für I/O, nicht für CPU-Arbeit. Begrenzung erfolgt dann über eine Semaphore, nicht über die Pool-Grösse. Seit Java 24 (JEP 491) pinnt synchronized den Carrier nicht mehr.
  5. Geteilter Zustand ist das eigentliche Problem. Weniger teilen, unveränderliche Daten, Übergabe über Queues.
  6. Thread Dumps lesen können ist eine Kernfähigkeit. Die meisten Hänger und Deadlocks findet man dort in Minuten.

9. Aus dem Projekt

„Ein Hintergrund-Job lief in einem benannten Executor und prüfte das Interrupt-Flag, damit das Deployment ohne Hänger herunterfährt.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „run() startet einen Thread.“ → Falsch. Nur start() startet einen neuen Thread. run() läuft im aktuellen Thread.
  • „interrupt() stoppt einen Thread.“ → Falsch. Es setzt nur ein Flag. Der Thread muss selbst reagieren.
  • „Mit Thread.stop() beendet man einen Thread hart.“ → Falsch. Seit Java 20 wirft es immer UnsupportedOperationException. Richtig: Interrupt oder ein volatile Flag.
  • „sleep gibt den Lock frei.“ → Falsch. Nur wait gibt den Monitor frei.
  • „Ein Thread im Socket-Read ist BLOCKED.“ → Falsch. Er ist meist RUNNABLE. BLOCKED heisst nur: wartet auf einen synchronized-Monitor.
  • „Ein Thread kann zweimal gestartet werden.“ → Falsch. Das zweite start() wirft IllegalThreadStateException.
  • „Daemon-Threads räumen beim Ende auf.“ → Falsch. Die JVM bricht sie ab. finally-Blöcke laufen nicht.
  • „Eine höhere Priorität garantiert mehr CPU.“ → Falsch. Sie ist nur ein Hinweis an das OS.

11. Fragen

Was ist ein Thread?

Ein eigener Ausführungsstrang mit eigenem Stack und Programmzähler. Alle Threads eines Prozesses teilen den Heap.

Welche Zustände hat ein Java-Thread?

NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. Das ist das Enum Thread.State.

Was ist der Unterschied zwischen BLOCKED und WAITING?

BLOCKED wartet auf einen synchronized-Monitor. WAITING wartet ohne Zeitlimit auf eine Aktion eines anderen Threads, z. B. notify, join-Ende oder unpark.

Welchen Zustand hat ein Thread, der auf einen ReentrantLock wartet?

WAITING oder TIMED_WAITING. ReentrantLock nutzt LockSupport.park, nicht den Monitor.

Welchen Zustand hat ein Thread in einem blockierenden Socket-Read?

Meist RUNNABLE. Die JVM sieht, dass er in nativem Code läuft. Das Warten passiert im Betriebssystem.

Was ist der Unterschied zwischen start() und run()?

start() erzeugt einen neuen Thread, der run() aufruft. run() direkt aufgerufen läuft im aktuellen Thread.

Was passiert bei einem zweiten start()?

IllegalThreadStateException. Ein Thread-Objekt lässt sich nur einmal starten.

Runnable oder Callable?

Runnable hat keine Rückgabe und keine checked Exception. Callable gibt einen Wert zurück und darf Exception werfen. Callable läuft über einen ExecutorService mit Future.

Wie kommt eine Exception aus einem Callable zum Aufrufer?

Sie liegt im Future. Future.get() wirft sie als ExecutionException mit der Original-Exception als cause.

Thread erweitern oder Runnable implementieren?

Runnable. Aufgabe und Ausführung sind getrennt, die Klasse kann erben, und die Aufgabe läuft auch in einem Executor.

Wie funktioniert interrupt()?

Es setzt das Interrupt-Flag. Blockierende Methoden wie sleep, wait und join werfen dann InterruptedException und löschen das Flag. Sonst muss der Thread das Flag selbst prüfen.

Was ist der Unterschied zwischen isInterrupted() und Thread.interrupted()?

isInterrupted() liest das Flag eines Threads. Das statische Thread.interrupted() liest das Flag des aktuellen Threads und löscht es.

Wie behandelt man InterruptedException richtig?

Weiterwerfen, oder Thread.currentThread().interrupt() aufrufen und die Arbeit beenden. Nie leer fangen.

Wie stoppt man einen Thread sauber?

Mit interrupt() oder einem volatile Flag. Der Thread prüft es und beendet run() selbst. Bei Executors: shutdown(), dann shutdownNow() und awaitTermination().

Warum gibt es Thread.stop() nicht mehr?

Es brach den Thread an beliebiger Stelle ab und hinterliess Objekte in kaputtem Zustand. Seit Java 20 wirft es immer UnsupportedOperationException.

Was ist ein Daemon-Thread?

Ein Hintergrund-Thread, der die JVM nicht am Leben hält. Laufen nur noch Daemons, beendet sich die JVM ohne deren finally-Blöcke.

Wann muss setDaemon() aufgerufen werden?

Vor start(). Danach wirft es IllegalThreadStateException. Ohne Aufruf erbt der Thread den Status seines Erzeugers.

Was macht join()?

Der aufrufende Thread wartet, bis der andere Thread endet. Danach sind alle seine Writes sichtbar (happens-before).

Was ist der Unterschied zwischen sleep() und wait()?

sleep behält alle Locks und braucht keinen. wait braucht den Monitor, gibt ihn frei und wartet auf notify oder Timeout.

Warum steht wait() in einer while-Schleife?

Wegen Spurious Wakeups und weil ein anderer Thread die Bedingung schon wieder ändern kann. Nach dem Aufwachen muss man die Bedingung neu prüfen.

Was passiert mit einer Exception, die run() nicht fängt?

Nur dieser Thread endet. Der UncaughtExceptionHandler bekommt sie, standardmässig Ausgabe auf System.err. Andere Threads laufen weiter.

Was bringt Thread-Priorität?

Wenig. Sie ist nur ein Hinweis an das OS. Bei Virtual Threads wird sie ignoriert.

Platform Thread oder Virtual Thread?

Platform Threads für CPU-Arbeit und wenige lange Aufgaben. Virtual Threads (Java 21) für sehr viele gleichzeitige, blockierende I/O-Aufgaben.

Warum nicht einfach 10'000 Platform Threads starten?

Jeder braucht einen OS-Thread und reservierten Stack. Das kostet Speicher und Kontextwechsel. Oft endet es in „unable to create native thread“.

Wie liest man einen Thread Dump?

Pro Thread: Name, Zustand, Stack. „- locked <adr>“ zeigt den Lock-Besitzer, „waiting to lock <adr>“ den Wartenden. Mehrere Dumps vergleichen.

Was ist ein ThreadLocal und was ist sein Risiko?

Eine Variable mit eigenem Wert pro Thread. In Pools leben Threads lange, darum kann ein vergessener Wert lecken oder zum nächsten Request wandern. Immer remove() im finally.

Szenario: Der Service hängt, alle Requests laufen in den Timeout. Was tun Sie zuerst?

Mehrere Thread Dumps mit jcmd Thread.print ziehen. Nach BLOCKED-Threads, Deadlock-Meldungen und Threads suchen, die immer an derselben Stelle stehen, z. B. bei einem leeren Connection-Pool.

Szenario: Nach dem Deployment-Stop beendet sich der Pod erst nach dem Kill-Timeout. Warum?

Ein Nicht-Daemon-Thread läuft weiter, oder ein Task ignoriert den Interrupt. Lösung: Executor im Shutdown-Hook schliessen, InterruptedException korrekt behandeln.

Szenario: Unter Last kommt „OutOfMemoryError: unable to create native thread“, der Heap ist aber frei. Woran liegt es?

Zu viele Platform Threads, oft ein Thread pro Request oder ein unbegrenzter Pool. Das Limit liegt im OS oder Container, nicht im Heap. Lösung: begrenzter Pool oder Virtual Threads.
