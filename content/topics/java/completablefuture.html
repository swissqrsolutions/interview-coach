CompletableFuture und asynchrone Programmierung

Java · Tier 2 · Quellen: Java SE 25 API-Doku (CompletableFuture, CompletionStage, ForkJoinPool), JEP 266 (More Concurrency Updates, Java 9), JEP 444 (Virtual Threads), JEP 505 (Structured Concurrency, Preview)

Kern: Eine CompletableFuture ist ein Platzhalter für ein Ergebnis, das später kommt. Sie löst das Problem, dass Future.get() blockiert und sich nicht verketten lässt. Man hängt Schritte an (thenApply, thenCompose, thenCombine), und diese laufen, sobald das Ergebnis da ist.

1. Wo sitzt die CompletableFuture?

  1. Aufrufer-Thread: Er startet die Arbeit mit supplyAsync und bekommt sofort eine CompletableFuture zurück.
  2. CompletableFuture: Sie hält das Ergebnis (oder die Exception) und einen Stack der angehängten Folge-Schritte.
  3. Executor: Ohne Angabe läuft die Arbeit im commonPool. Mit Angabe im eigenen Pool, z. B. für I/O.
  4. Arbeit: Ein Worker-Thread erledigt sie und ruft intern complete(result) auf.
  5. Folge-Schritte: Danach laufen alle angehängten Schritte.

2. Die Reise eines Requests mit zwei parallelen Calls (die Geschichte zum Merken)

  1. Start: Der Request-Thread startet zwei Calls mit supplyAsync(…, ioPool). Er wartet nicht.
  2. Parallel arbeiten: Zwei Threads aus dem I/O-Pool laden User und Bestellungen gleichzeitig.
  3. Zusammenführen: thenCombine registriert eine Funktion. Sie läuft erst, wenn beide fertig sind.
  4. Fehler: Wirft ein Call eine Exception, ist auch das kombinierte Ergebnis fehlerhaft. handle oder exceptionally liefern einen Fallback. orTimeout begrenzt die Wartezeit.
  5. Antwort: Die Gesamtzeit ist die des langsamsten Calls, nicht die Summe.

3. Beispiel: Kombinieren, Threads, Fehler, Timeout, allOf, cancel

ExecutorService io = Executors.newFixedThreadPool(4, …);              // Threads "io-NN"
user.thenCombine(orders, (u, o) -> u + " hat " + o + " Bestellungen").join(); // 2) je 300 ms
CompletableFuture.supplyAsync(() -> t()).join();                     // 3) ohne Executor
supplyAsync(() -> 21, io).thenApply(x -> x * 2)
    .thenCompose(x -> supplyAsync(() -> "id=" + x, io));              // 4)
fail.join(); fail.get();                                              // 5) wirft "DB down"
fail.exceptionally(ex -> -1); fail.handle((v, ex) -> …);              // 6)
slow.orTimeout(200, MILLISECONDS); slow2.completeOnTimeout("cached", 200, MILLISECONDS); // 7)
CompletableFuture.allOf(5 Tasks à 100 ms).join();                     // 8)
completedFuture("x").thenApply(s -> t());                             // 9)
cancelMe.cancel(true);   // Task läuft schon 100 ms                    // 10)

Echte Ausgabe, Oracle JDK 17.0.3 (16 Kerne). Zeiten und Thread-Namen ändern sich pro Lauf. Java 21 und 25 verhalten sich gleich.

  1. Der commonPool hat hier 15 Threads, also Kerne minus 1. Er ist für CPU-Arbeit gedacht.
  2. Zwei Calls à 300 ms brauchen zusammen nur 314 ms. Sie laufen parallel.
  3. Ohne Executor läuft supplyAsync im commonPool.
  4. thenApply ändert den Wert. thenCompose hängt eine weitere asynchrone Aufgabe an und „glättet“ das Ergebnis: CompletableFuture<String>, nicht CompletableFuture<CompletableFuture<String>>.
  5. join() wirft eine unchecked CompletionException. get() wirft eine checked ExecutionException. Die echte Ursache steckt in getCause().
  6. In einem abhängigen Schritt kommt die Exception eingepackt als CompletionException an. Man muss getCause() prüfen.
  7. orTimeout beendet mit TimeoutException. completeOnTimeout liefert einen Ersatzwert.
  8. allOf wartet auf alle. 5 Tasks à 100 ms auf 4 Threads brauchen zwei Runden, also ca. 300 ms. allOf selbst liefert kein Ergebnis; man liest danach jede Future.
  9. Ist die Future schon fertig, läuft thenApply sofort im aufrufenden Thread, hier main.
  10. cancel(true) markiert die Future als abgebrochen. Der laufende Task wird aber nicht unterbrochen und läuft zu Ende.

4. Details, die Interviewer fragen

  1. Future vs CompletableFuture: Ein Future hat nur get(), das blockiert. Eine CompletableFuture kann man verketten, kombinieren, von aussen abschliessen (complete) und Fehler behandeln.
  2. CompletionStage: Das Interface mit allen Verkettungs-Methoden. CompletableFuture implementiert es und Future.
  3. Die wichtigsten Methoden:
    • thenApply(fn): Wert umwandeln, wie map.
    • thenAccept(consumer) / thenRun(runnable): Ergebnis nutzen, nichts zurückgeben.
    • thenCompose(fn): nächste asynchrone Aufgabe, wie flatMap.
    • thenCombine(other, fn): zwei unabhängige Ergebnisse zusammenführen.
    • allOf / anyOf: auf alle oder auf die erste warten.
    • exceptionally(fn): nur im Fehlerfall, liefert Ersatzwert.
    • handle(bifn): immer, bekommt Wert oder Exception, liefert neuen Wert.
    • whenComplete(biconsumer): immer, ändert das Ergebnis nicht. Gut für Logs und Metriken.
  4. Async-Varianten: thenApplyAsync usw. laufen im Executor (Standard: commonPool). Ohne Async läuft der Schritt im Thread, der die Future abschliesst, oder im Aufrufer, wenn sie schon fertig ist.
  5. Welcher Thread? Das ist bei Nicht-Async-Methoden nicht festgelegt. Darum gehört blockierender Code nie in einen Nicht-Async-Schritt.
  6. commonPool: Er ist JVM-weit geteilt, auch mit parallelen Streams. Blockierende I/O dort hungert alle anderen aus. Für I/O immer einen eigenen Executor mitgeben.
  7. Fehler-Weitergabe: Schlägt eine Stufe fehl, werden alle Folge-Stufen übersprungen. Erst exceptionally, handle oder whenComplete sehen den Fehler.
  8. cancel: cancel wirkt wie completeExceptionally(new CancellationException()). Der Parameter mayInterruptIfRunning hat keine Wirkung. Die laufende Arbeit muss man selbst stoppen.
  9. Timeouts (Java 9): orTimeout und completeOnTimeout. Dazu delayedExecutor für verzögerte Ausführung.
  10. Neuere Methoden: exceptionallyCompose und exceptionallyAsync (Java 12). resultNow(), exceptionNow() und state() (Java 19).
  11. Manuell abschliessen: new CompletableFuture<>() plus complete(v) oder completeExceptionally(ex). So verbindet man Callback-APIs mit Futures.
  12. ThreadLocal und MDC: Ein anderer Thread sieht keine ThreadLocal-Werte des Aufrufers. Log-Kontext (MDC), Security-Context und Transaktionen gehen verloren. Man muss sie selbst übergeben.

5. Vergleich

  • Future + ExecutorService: einfach, aber get() blockiert. Kein Verketten.
  • CompletableFuture: verkettet, kombiniert, Fehlerbehandlung. Code wird bei vielen Stufen schwer lesbar.
  • Virtual Threads (Java 21): einfacher blockierender Code, der trotzdem skaliert. Für viele I/O-Fälle heute die einfachere Wahl.
  • Structured Concurrency (StructuredTaskScope): mehrere Teilaufgaben als eine Einheit mit gemeinsamem Abbruch. In Java 25 noch Preview.
  • Reactive (Project Reactor, WebFlux): Streams mit Backpressure. Mächtig, aber steile Lernkurve und schwer zu debuggen.
  • Spring @Async: gibt eine CompletableFuture zurück. Läuft im konfigurierten Spring-Executor.

6. In der Produktion

  1. commonPool blockiert: REST- oder DB-Calls im commonPool belegen alle Threads. Parallele Streams und andere Futures warten. Lösung: eigener, begrenzter I/O-Executor.
  2. Verschluckte Exceptions: Niemand ruft join() auf und niemand hängt exceptionally an. Der Fehler verschwindet ohne Log. Lösung: am Ende immer whenComplete oder exceptionally mit Log.
  3. Hängende Requests: Ein Downstream-Service antwortet nie. join() wartet ewig. Lösung: orTimeout plus Timeout im HTTP-Client.
  4. Unbegrenzte Queue: Executors.newFixedThreadPool hat eine unbegrenzte Queue. Bei Last wächst sie bis zum OOM. Lösung: ThreadPoolExecutor mit begrenzter Queue und Rejection Policy.
  5. Verlorener Kontext: Logs ohne Trace-ID, Security-Context fehlt. Lösung: Context weitergeben, z. B. mit Micrometer Context Propagation oder einem dekorierten Executor.
  6. cancel stoppt nichts: Nach einem Timeout läuft der teure Call weiter und belastet den Downstream. Lösung: Timeout direkt im Client setzen.
  7. Deadlock im Pool: Ein Task im Pool wartet mit join() auf einen anderen Task im selben, vollen Pool. Lösung: nicht blockierend verketten (thenCompose) oder getrennte Pools.

7. Diagnose: Werkzeuge und Befehle

  • Thread Dump (jcmd <pid> Thread.print): alle ForkJoinPool.commonPool-worker in socketRead oder WAITING zeigt blockierende I/O im commonPool.
  • Thread-Namen: Eigene Executors mit einer ThreadFactory benennen (io-, report-). Dann sieht man im Dump sofort, wer hängt.
  • Pool-Metriken: Micrometer ExecutorServiceMetrics zeigt aktive Threads, Queue-Länge, abgelehnte Tasks.
  • JFR: Events jdk.ThreadPark und jdk.JavaMonitorWait zeigen, wo Threads warten.
  • Distributed Tracing (OpenTelemetry): zeigt, ob Calls wirklich parallel laufen und welcher Call langsam ist.
  • Logs mit Ursache: Immer ex.getCause() loggen, nicht nur die CompletionException.

8. Senior-Punkte

  1. Executor immer bewusst wählen. commonPool nur für kurze CPU-Arbeit. I/O bekommt einen eigenen, begrenzten Pool.
  2. Jede Kette braucht ein Ende mit Fehlerbehandlung und Timeout. Sonst verschwinden Fehler oder Requests hängen.
  3. Parallelität ist kein Selbstzweck. Zwei Calls parallel sparen Zeit, aber verdoppeln die Last auf Downstream-Systeme.
  4. Mit Java 21 neu abwägen. Virtual Threads mit einfachem, blockierendem Code sind oft lesbarer als lange Future-Ketten.
  5. Kontext ist Teil des Designs. Trace-ID, Security und Transaktion wandern nicht automatisch mit.
  6. cancel ist nur ein Signal an die Future. Echtes Abbrechen braucht Timeouts im Client oder eigene Abbruch-Flags.

10. Fallen

  • „cancel(true) unterbricht den laufenden Task.“ → Falsch. Der Parameter hat keine Wirkung. Der Task läuft weiter.
  • „supplyAsync ohne Executor ist für REST-Calls okay.“ → Falsch. Es blockiert den geteilten commonPool.
  • „thenApply läuft immer in einem anderen Thread.“ → Falsch. Ist die Future fertig, läuft es im Aufrufer.
  • „exceptionally bekommt die Original-Exception.“ → Nicht immer. In Folge-Stufen kommt sie als CompletionException. getCause() prüfen.
  • „allOf liefert die Liste der Ergebnisse.“ → Falsch. Es liefert CompletableFuture<Void>. Die Ergebnisse liest man danach.
  • „thenApply mit einer Funktion, die eine Future zurückgibt, ist okay.“ → Falsch. Das ergibt eine verschachtelte Future. Dafür thenCompose.

11. Fragen

Was ist eine CompletableFuture?

Ein Platzhalter für ein späteres Ergebnis. Man kann Schritte anhängen, Ergebnisse kombinieren und Fehler behandeln, ohne zu blockieren.

Was ist der Unterschied zu Future?

Future hat nur ein blockierendes get(). CompletableFuture kann man verketten, kombinieren und von aussen abschliessen.

thenApply vs thenCompose?

thenApply wandelt den Wert um, wie map. thenCompose hängt eine weitere asynchrone Aufgabe an und vermeidet eine verschachtelte Future, wie flatMap.

thenCombine vs thenCompose?

thenCombine führt zwei unabhängige, parallele Ergebnisse zusammen. thenCompose ist sequentiell: der zweite Schritt braucht das erste Ergebnis.

Welcher Executor wird ohne Angabe genutzt?

ForkJoinPool.commonPool(). Er ist JVM-weit geteilt und hat standardmässig Kerne minus 1 Threads.

Warum gehört I/O nicht in den commonPool?

Blockierende Calls belegen die wenigen Threads. Andere Futures und parallele Streams warten dann.

thenApply vs thenApplyAsync?

thenApplyAsync läuft immer im Executor. thenApply läuft im Thread, der die Future abschliesst, oder im Aufrufer, wenn sie schon fertig ist.

join vs get?

join wirft eine unchecked CompletionException. get wirft checked ExecutionException und InterruptedException. Beide blockieren.

exceptionally vs handle vs whenComplete?

exceptionally nur bei Fehler, liefert Ersatzwert. handle immer, liefert neuen Wert. whenComplete immer, ändert das Ergebnis nicht.

Wie geben Sie einem Call ein Timeout?

orTimeout wirft TimeoutException, completeOnTimeout liefert einen Ersatzwert. Seit Java 9. Dazu ein Timeout im HTTP-Client.

Was macht cancel(true)?

Es schliesst die Future mit CancellationException ab. Der laufende Task wird nicht unterbrochen.

allOf vs anyOf?

allOf ist fertig, wenn alle fertig sind, und liefert Void. anyOf ist fertig mit dem ersten Ergebnis.

Wie sammeln Sie die Ergebnisse nach allOf?

Nach allOf(...).join() jede Future mit join() lesen, z. B. per Stream. Sie blockieren dann nicht mehr.

Was passiert mit einer Exception in der Mitte der Kette?

Die folgenden thenApply-Schritte werden übersprungen. Erst exceptionally, handle oder whenComplete sehen den Fehler.

Wie verbinden Sie eine Callback-API mit CompletableFuture?

new CompletableFuture() erzeugen, im Callback complete(v) oder completeExceptionally(ex) aufrufen, die Future zurückgeben.

Warum fehlt im async Code die Trace-ID im Log?

MDC und ThreadLocal hängen am Thread. Der Worker-Thread kennt sie nicht. Lösung: Kontext weitergeben, z. B. mit einem dekorierten Executor.

Kann ein Thread Pool mit CompletableFuture deadlocken?

Ja. Wartet ein Task mit join() auf einen Task im selben vollen Pool, wartet er ewig. Lösung: nicht blockierend verketten.

CompletableFuture oder Virtual Threads?

Für viele I/O-Calls sind Virtual Threads mit einfachem Code oft lesbarer. CompletableFuture bleibt gut für Kombinieren, Fallbacks und bestehende asynchrone APIs.

Was ist Structured Concurrency?

Teilaufgaben eines Requests werden als eine Einheit gestartet, gewartet und gemeinsam abgebrochen. StructuredTaskScope ist in Java 25 noch Preview.

Was liefert Spring @Async zurück?

Eine CompletableFuture oder void. Die Methode läuft im konfigurierten Spring-Executor, nur bei Aufruf über den Proxy.

Was sind resultNow und state?

Seit Java 19. resultNow liefert das Ergebnis einer fertigen Future ohne Wartezeit. state zeigt RUNNING, SUCCESS, FAILED oder CANCELLED.

Szenario: Unter Last werden alle Endpoints langsam, auch die ohne DB. Der Thread Dump zeigt alle commonPool-Worker in socketRead. Was ist los?

Blockierende I/O läuft im geteilten commonPool. Alle anderen Futures und parallelen Streams warten. Lösung: eigener begrenzter I/O-Executor und Timeouts.

Szenario: Ein Fehler im async Teil erscheint nie im Log. Warum?

Niemand ruft join auf und keine Stufe behandelt den Fehler. Die Exception bleibt in der Future. Lösung: am Ende whenComplete oder exceptionally mit Log.

Szenario: Ein Endpoint ruft drei Services nacheinander auf und braucht 900 ms. Wie verbessern Sie das?

Unabhängige Calls parallel mit supplyAsync im I/O-Pool starten und mit thenCombine oder allOf zusammenführen. Dazu orTimeout und Fallback mit handle. Die Last auf die Downstreams beachten.
