Reflection und Annotations: Funktion, Kosten, Nutzung in Frameworks

Kern: Reflection ist eine API, mit der ein Programm zur Laufzeit Klassen, Felder, Methoden und Konstruktoren untersucht und aufruft. Annotations sind Metadaten im Code (@Entity, @Transactional), die Compiler, Werkzeuge oder Frameworks lesen. Zusammen lösen sie das Problem, dass Frameworks wie Spring, Hibernate und Jackson mit Klassen arbeiten müssen, die sie beim Kompilieren nicht kennen.

1. Wo sitzen Reflection und Annotations?

  1. Quellcode: Der Entwickler setzt Annotations, z. B. @NotBlank auf ein Feld.
  2. javac: Der Compiler speichert die Annotation in der .class-Datei, je nach Retention.
  3. Annotation Processor: Ein Plugin für javac liest Annotations beim Kompilieren und erzeugt Code. Beispiel: MapStruct.
  4. Class-Objekt: Die JVM hält für jede Klasse ein Class-Objekt. Daraus liefert Reflection Field, Method, Constructor und Runtime-Annotations.
  5. Frameworks: Sie scannen Klassen, lesen Annotations und rufen Methoden per Reflection auf. Beispiel: Spring findet @Service, baut die Bean und setzt @Autowired-Felder.

2. Die Reise einer @Transactional-Methode durch Spring (die Geschichte zum Merken)

  1. Scan: Spring durchsucht Pakete nach Klassen mit @Component, @Service usw.
  2. Instanz: Spring ruft den Konstruktor per Reflection auf und übergibt die Abhängigkeiten.
  3. Annotation lesen: Spring prüft per Reflection, ob Methoden @Transactional tragen. Die Annotation braucht dafür @Retention(RUNTIME).
  4. Proxy bauen: Spring legt einen Proxy um die Bean. Ein Proxy ist ein Stellvertreter-Objekt, das jeden Aufruf abfängt. Mit Interface: JDK Dynamic Proxy. Ohne: eine generierte Unterklasse (CGLIB).
  5. Aufruf: Andere Beans bekommen den Proxy. Er startet die Transaktion, ruft die echte Methode und macht Commit oder Rollback.
  6. Self-Invocation: Ruft die Bean intern this.save() auf, geht der Aufruf am Proxy vorbei. Die Annotation wirkt dann nicht.

Echte Ausgabe, Oracle JDK 17.0.3. Zeiten ändern sich pro Lauf; für echte Messungen JMH nutzen. Ab Java 18 nutzt Method.invoke intern Method Handles (JEP 416); die Zahlen können dort anders aussehen.

  1. Reflection liefert alle Felder samt Modifiern, auch private.
  2. Ein Mini-Validator: Er liest @NotBlank und prüft den Wert. So arbeitet im Prinzip Bean Validation (Hibernate Validator).
  3. @ClassOnly hat Retention CLASS. Sie steht in der .class-Datei, ist zur Laufzeit aber unsichtbar.
  4. setAccessible(true) umgeht private im eigenen Code. Kapselung ist also keine Sicherheitsgrenze gegen Reflection.
  5. Seit Java 17 sind JDK-Interna stark gekapselt (JEP 403). setAccessible auf String.value wirft InaccessibleObjectException. Nur mit --add-opens geht es.
  6. Ein JDK Dynamic Proxy erzeugt zur Laufzeit eine Klasse ($Proxy2), die ein Interface implementiert. Jeder Aufruf geht an den Handler. So funktionieren Spring AOP mit Interfaces und Spring-Data-Repositories.
  7. Records liefern ihre Komponenten per Reflection. Jackson nutzt das für Records.
  8. Method.invoke ist hier 2- bis 7-mal langsamer als ein direkter Aufruf: Boxing, Zugriffsprüfung, Array für Argumente. Ein Method Handle in einer nicht-finalen Variable inlinet der JIT schlecht. In einem static final-Feld wird es fast so schnell wie direkt.

4. Details, die Interviewer fragen

  1. Einstieg in Reflection: obj.getClass(), Customer.class oder Class.forName("…"). Dann getDeclaredFields() (alle eigenen, auch private) oder getFields() (nur public, auch geerbte).
  2. Retention:
    • SOURCE: nur im Quellcode, z. B. @Override, @SuppressWarnings.
    • CLASS: in der .class-Datei, zur Laufzeit unsichtbar. Das ist der Standard ohne Angabe.
    • RUNTIME: per Reflection lesbar, z. B. @Transactional, @Entity.
  3. Weitere Meta-Annotations: @Target (wo erlaubt: Feld, Methode, Typ …), @Inherited (Klassen-Annotation wird an Unterklassen vererbt), @Repeatable (mehrfach erlaubt), @Documented.
  4. Annotation-Elemente: nur Primitive, String, Class, Enums, Annotations und Arrays davon. Werte müssen Konstanten sein.
  5. Meta-Annotations in Spring: @RestController trägt selbst @Controller und @ResponseBody. Spring liest Annotations über mehrere Ebenen (AnnotationUtils/MergedAnnotations).
  6. Kosten: Lookup (getMethod) ist teuer, Ergebnisse cachen. invoke hat Overhead durch Prüfungen, Boxing und Argument-Arrays. Der JIT kann reflektive Aufrufe schlechter inlinen.
  7. Method Handles (java.lang.invoke): typisierte, direkt ausführbare Zeiger auf Methoden. In static final-Feldern behandelt der JIT sie wie Konstanten und inlinet sie.
  8. Starke Kapselung: Seit Java 16 standardmässig, seit Java 17 ohne Ausweg per --illegal-access (JEP 403). Zugriff auf JDK-Interna nur mit --add-opens modul/paket=ALL-UNNAMED.
  9. Proxies: JDK Dynamic Proxy nur für Interfaces. Für Klassen erzeugen Bibliotheken eine Unterklasse (CGLIB in Spring, ByteBuddy in Hibernate und Mockito). final-Klassen und -Methoden lassen sich so nicht abfangen.
  10. Type Erasure und Reflection: List<String> ist zur Laufzeit nur List. Generische Typen in Feld- und Methoden-Signaturen sind aber über getGenericType() lesbar. Jackson nutzt dafür TypeReference.
  11. GraalVM Native Image: Reflection braucht dort eine Konfiguration, weil alles vorher analysiert wird. Spring Boot erzeugt diese Hinweise bei seinem AOT-Build.

5. Vergleich

  • Direkter Aufruf: schnell, vom Compiler geprüft. Geht nur, wenn man den Typ kennt.
  • Reflection: flexibel, für unbekannte Typen. Langsamer, Fehler erst zur Laufzeit, umgeht Kapselung.
  • Method Handles: schneller als Reflection, wenn konstant. Komplexere API.
  • Annotation Processing (Compile-Zeit): erzeugt Code vor dem Start. Kein Laufzeit-Overhead, Fehler beim Build. Beispiele: MapStruct, Lombok, Micronaut, Dagger.
  • Bytecode-Generierung zur Laufzeit (ByteBuddy, CGLIB): erzeugt neue Klassen, z. B. Proxies und Mocks.
  • Spring AOT: verlagert Teile der Reflection-Arbeit in den Build. Schnellerer Start, Basis für Native Images.

6. In der Produktion

  1. @Transactional wirkt nicht: Self-Invocation, private-Methode oder Bean nicht von Spring erzeugt. Lösung: Methode in eine andere Bean, public machen, Aufruf über den Proxy.
  2. Langsamer Start: Classpath-Scanning und Reflection über tausende Klassen. Lösung: Scan-Pakete eingrenzen, Lazy Init prüfen, Spring AOT oder CDS.
  3. InaccessibleObjectException nach Java-Upgrade: Alte Bibliotheken greifen auf JDK-Interna zu. Lösung: Bibliothek aktualisieren; als Übergang --add-opens gezielt setzen.
  4. Reflection in heissem Pfad: getMethod pro Request. Lösung: Lookups einmal cachen, oder Method Handles.
  5. Metaspace wächst: Proxies und generierte Klassen in Massen, z. B. pro Request neu erzeugt. Lösung: Proxy-Klassen wiederverwenden; Metaspace beobachten.
  6. Native Image findet Klasse nicht: Reflection ohne Konfiguration. Lösung: Reflection-Hints (Spring RuntimeHints) oder Tracing-Agent.

7. Diagnose: Werkzeuge und Befehle

  • javap -v Customer.class: zeigt RuntimeVisibleAnnotations und RuntimeInvisibleAnnotations (Retention CLASS).
  • Spring Debug-Log (logging.level.org.springframework.transaction=DEBUG): zeigt, ob eine Transaktion wirklich startet.
  • Stack Trace: Frames wie $Proxy, CglibAopProxy oder $$SpringCGLIB$$ zeigen, dass ein Proxy dazwischen ist. Fehlen sie, wirkt die Annotation nicht.
  • -Xlog:class+load: zeigt generierte Proxy-Klassen beim Laden.
  • jcmd <pid> VM.metaspace: Metaspace-Verbrauch bei vielen generierten Klassen.
  • Profiler / JFR: viel Zeit in Method.invoke oder Class.getMethod zeigt ungecachte Reflection.
  • Spring Boot Startup-Analyse: ApplicationStartup mit BufferingApplicationStartup und Actuator /startup.

8. Senior-Punkte

  1. Reflection gehört in Frameworks, nicht in Fachcode. Im eigenen Code verliert man Typ-Sicherheit und Refactoring-Hilfe.
  2. Annotations sind Konfiguration. Zu viele machen das Verhalten unsichtbar. Man muss wissen, wer sie liest und wann.
  3. Proxies erklären viele „Spring-Rätsel“. Self-Invocation, private Methoden, final Klassen: Alles fällt am Proxy vorbei.
  4. Trend zur Compile-Zeit. Annotation Processing, Spring AOT und Native Image verschieben Reflection in den Build: schnellerer Start, Fehler früher.
  5. Starke Kapselung ernst nehmen. --add-opens ist ein Übergang, kein Dauerzustand. Bei Upgrades Bibliotheken zuerst prüfen.
  6. Lookups cachen. Reflection ist beim Suchen teuer, nicht nur beim Aufruf.

10. Fallen

  • „Jede Annotation ist zur Laufzeit lesbar.“ → Falsch. Nur mit @Retention(RUNTIME). Standard ist CLASS.
  • „private schützt vor Reflection.“ → Falsch. Im eigenen Code hebt setAccessible(true) es auf. Nur Modulgrenzen schützen.
  • „@Transactional auf einer privaten Methode wirkt.“ → Falsch. Der Proxy fängt nur Aufrufe von aussen auf überschreibbare Methoden ab.
  • „Annotations tun selbst etwas.“ → Falsch. Sie sind nur Daten. Ein Prozessor, Framework oder Werkzeug muss sie lesen.
  • „Reflection ist immer extrem langsam.“ → Übertrieben. Der Aufruf kostet etwas, der Lookup viel. Gecacht und selten ist es harmlos.
  • „JDK-Proxies funktionieren für jede Klasse.“ → Falsch. Nur für Interfaces. Für Klassen braucht es Unterklassen-Generierung.

11. Fragen

Was ist Reflection?

Eine API, um zur Laufzeit Klassen, Felder, Methoden und Konstruktoren zu untersuchen und aufzurufen, auch wenn man sie beim Kompilieren nicht kennt.

Wofür nutzen Frameworks Reflection?

Spring baut Beans und injiziert Abhängigkeiten, Hibernate mappt Entities, Jackson liest und schreibt Felder, JUnit findet Testmethoden.

Wie bekommen Sie ein Class-Objekt?

Mit obj.getClass(), Typ.class oder Class.forName("voller.Name").

getFields vs getDeclaredFields?

getFields: nur public, auch geerbte. getDeclaredFields: alle der Klasse selbst, auch private, aber keine geerbten.

Was ist eine Annotation?

Metadaten im Code. Sie tun selbst nichts. Compiler, Annotation Processor oder Frameworks lesen und interpretieren sie.

Welche Retention-Arten gibt es?

SOURCE (nur Quellcode), CLASS (in der .class-Datei, Standard), RUNTIME (per Reflection lesbar).

Wozu dient @Target?

Es legt fest, wo eine Annotation stehen darf, z. B. nur an Feldern oder Methoden.

Was ist @Inherited?

Eine Klassen-Annotation wird an Unterklassen vererbt. Es gilt nur für Klassen, nicht für Methoden oder Interfaces.

Wie schreiben Sie eine eigene Annotation?

Mit @interface, dazu @Retention und @Target. Elemente sind Methoden ohne Parameter, optional mit default.

Was ist ein Annotation Processor?

Ein javac-Plugin, das Annotations beim Kompilieren liest und Code oder Fehler erzeugt. Beispiele: MapStruct, Lombok.

Was kostet Reflection?

Lookups sind teuer, Aufrufe haben Overhead durch Prüfungen, Boxing und Argument-Arrays, und der JIT inlinet schlechter.

Was sind Method Handles?

Typisierte, direkt ausführbare Referenzen auf Methoden oder Felder aus java.lang.invoke. In static final Feldern kann der JIT sie inlinen.

Kann Reflection private Felder lesen?

Ja, mit setAccessible(true) im eigenen Code. Über Modulgrenzen nur, wenn das Paket geöffnet ist.

Was änderte Java 17 für Reflection?

JDK-Interna sind stark gekapselt (JEP 403). setAccessible darauf wirft InaccessibleObjectException, ausser mit --add-opens.

Was ist ein Dynamic Proxy?

Eine zur Laufzeit erzeugte Klasse, die Interfaces implementiert und jeden Aufruf an einen InvocationHandler gibt.

JDK-Proxy vs CGLIB in Spring?

JDK-Proxy implementiert Interfaces. CGLIB erzeugt eine Unterklasse und funktioniert auch ohne Interface, aber nicht für final Klassen oder Methoden. Spring Boot nutzt standardmässig Klassen-Proxies.

Warum wirkt @Transactional bei Self-Invocation nicht?

this.methode() ruft das echte Objekt direkt, nicht den Proxy. Der Proxy startet also keine Transaktion.

Wie liest Jackson generische Typen trotz Type Erasure?

Generische Typen in Signaturen bleiben als Metadaten erhalten. TypeReference fängt den Typ über eine anonyme Unterklasse ein.

Warum braucht GraalVM Native Image Reflection-Konfiguration?

Native Image analysiert vorab, welche Klassen erreichbar sind. Reflektive Zugriffe sieht es nicht und muss sie aus Hints kennen.

Was sind Meta-Annotations in Spring?

Annotations auf Annotations. @RestController trägt @Controller und @ResponseBody. Spring wertet diese Ebenen aus.

Szenario: Ein @Transactional-Service schreibt bei einer Exception halbe Daten. Was prüfen Sie?

Ob der Aufruf über den Proxy kommt (kein Self-Invocation), ob die Methode public ist und ob die Exception unchecked ist; checked Exceptions lösen standardmässig keinen Rollback aus. Mit DEBUG-Log der Transaktion prüfen.

Szenario: Nach dem Upgrade auf Java 17 startet ein Service nicht: InaccessibleObjectException. Was tun Sie?

Die Bibliothek im Stack Trace finden und aktualisieren. Als Übergang gezielt --add-opens für genau dieses Paket setzen und ein Ticket für die Entfernung anlegen.

Szenario: Ein Mapping-Code ruft pro Request getDeclaredFields und setAccessible auf und ist langsam. Wie verbessern Sie ihn?

Lookups einmal pro Klasse cachen. Besser: Mapping zur Compile-Zeit erzeugen, z. B. MapStruct, oder Method Handles.
