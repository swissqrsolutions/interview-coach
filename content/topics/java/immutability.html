Unveränderliche Objekte: Regeln, Vorteile, defensive Kopien

Java · Tier 2 · Quellen: JLS 21 §17.5 (final Field Semantics), Java SE 25 API-Doku (List „Unmodifiable Lists“, List.copyOf, Collections.unmodifiableList, java.time Package, Record), JEP 395 (Records)

Kern: Ein unveränderliches Objekt (immutable) ist ein Objekt, dessen Zustand sich nach dem Konstruktor nie mehr ändert. Es löst Probleme mit geteiltem Zustand: Es ist ohne Lock thread-sicher, ein sicherer Map-Schlüssel und leicht zu verstehen. Der Preis: Jede Änderung erzeugt ein neues Objekt.

1. Wo sitzt Unveränderlichkeit?

  1. Aufrufer: Er übergibt Daten, z. B. eine ArrayList. Er kann diese Liste später noch ändern.
  2. Konstruktor: Er prüft die Werte und kopiert veränderliche Eingaben. Das heisst defensive Kopie (eine eigene Kopie, die niemand sonst kennt).
  3. private final Felder: Sie werden genau einmal gesetzt. Sie enthalten nur unveränderliche Werte oder Kopien.
  4. Getter und withX(): Sie geben nichts Veränderliches heraus. Eine „Änderung“ liefert ein neues Objekt.
  5. Nutzer: Viele Threads lesen ohne Lock. Maps nutzen das Objekt als stabilen Schlüssel.

2. Die Reise eines unveränderlichen Objekts (die Geschichte zum Merken)

  1. Eingabe: Ein Aufrufer baut eine ArrayList mit „Milch“ und übergibt sie.
  2. Kopie rein: Der Konstruktor ruft List.copyOf(items) auf. Jetzt hat das Objekt eine eigene, unveränderliche Liste.
  3. final Freeze: Am Ende des Konstruktors „friert“ die JVM die final-Felder ein. Jeder Thread, der das Objekt danach sieht, sieht die richtigen Werte (JLS §17.5).
  4. Teilen: Das Objekt geht an viele Threads oder in eine Map. Niemand braucht einen Lock.
  5. „Ändern“: withItem("Brot") baut ein neues Objekt mit neuer Liste. Das alte bleibt unverändert. Wer es noch hält, sieht weiter den alten Stand.

3. Beispiel: final reicht nicht, Kopie vs View, Records, java.time

final class BadOrder  { private final List<String> items; BadOrder(List<String> i) { items = i; } … }
final class GoodOrder { private final List<String> items; GoodOrder(List<String> i) { items = List.copyOf(i); } … }
record RecOrder(List<String> items) {}
record SafeRec(List<String> items) { SafeRec { items = List.copyOf(items); } }
final class Period { Period(Date s) { start = new Date(s.getTime()); } Date start() { return new Date(start.getTime()); } }

src.add("Brot"); bad.items().add("Hack");                       // 1)
src.add("Brot"); good.items().add("Hack");                      // 2)
base.add("y") nach unmodifiableList(base) und List.copyOf(base) // 3)
List.of("a", null); List.copyOf(copy) == copy                   // 4)
src.add("Brot") nach new RecOrder(src)                          // 5)
d.setTime(…); p.start().setTime(1);                             // 6)
day.plusDays(1); s.toUpperCase();                               // 7) 8)
1) BadOrder (final field, no copy): [Milch, Brot, Hack]
2) GoodOrder after caller change: [Milch] | add -> UnsupportedOperationException
3) unmodifiableList view=[x, y] List.copyOf=[x]
4) List.of with null: NullPointerException
4) List.copyOf(immutable) same instance: true
5) record without copy: [Milch, Brot] | record with compact-ctor copy: List12
6) Period start still epoch: true
7) LocalDate.plusDays returns new object: day=2026-11-24 next=2026-11-25
8) String after toUpperCase() without assignment: bern

Echte Ausgabe, Oracle JDK 17.0.3. List12 ist eine interne JDK-Klasse für unveränderliche Listen mit 1–2 Elementen; der Name kann sich ändern. Java 21 und 25 verhalten sich gleich.

  1. final schützt nur die Referenz, nicht die Liste. Aufrufer und Getter-Nutzer ändern das Objekt von aussen.
  2. Mit List.copyOf im Konstruktor ist die Änderung des Aufrufers egal. Der Getter liefert eine unveränderliche Liste.
  3. Collections.unmodifiableList ist nur ein View (eine Sicht ohne Schreibrecht). Ändert jemand die Original-Liste, sieht man das. List.copyOf ist eine echte Kopie.
  4. List.of und List.copyOf verbieten null. copyOf einer schon unveränderlichen Liste kopiert nicht nochmals.
  5. Ein Record ist nur flach unveränderlich. Eine veränderliche Liste darin bleibt veränderlich. Lösung: Kopie im kompakten Konstruktor.
  6. Date ist veränderlich. Darum Kopie rein und Kopie raus. Besser: Instant oder LocalDate.
  7. java.time-Typen sind unveränderlich. plusDays liefert ein neues Objekt.
  8. String ist unveränderlich. Ohne Zuweisung geht das Ergebnis verloren.

4. Details, die Interviewer fragen

  1. Die Regeln:
    • Keine Setter: keine Methode ändert den Zustand.
    • Klasse final: Unterklassen können sonst veränderliches Verhalten hinzufügen. Alternativ: privater Konstruktor mit Fabrik-Methode.
    • Felder private final: genau eine Zuweisung im Konstruktor.
    • Defensive Kopie rein: veränderliche Parameter kopieren, bevor man sie prüft.
    • Nichts Veränderliches raus: Getter liefern Kopien oder unveränderliche Sichten.
    • this nicht entkommen lassen: im Konstruktor this nicht an andere Threads oder Listener geben.
  2. Erst kopieren, dann prüfen: Prüft man zuerst, kann ein anderer Thread den Parameter zwischen Prüfung und Kopie ändern. Das ist eine TOCTOU-Lücke (Time of Check to Time of Use).
  3. final und das JMM: Ist der Konstruktor fertig und ist this nicht entkommen, sieht jeder Thread die final-Felder korrekt. Auch ohne volatile oder Lock.
  4. Flach vs tief: Flach unveränderlich heisst, die Referenzen ändern sich nicht. Tief unveränderlich heisst, auch die referenzierten Objekte ändern sich nicht. Nur tief ist wirklich sicher.
  5. Unveränderliche Collections: List.of, Set.of, Map.of, List.copyOf, Stream.toList() (Java 16). Sie verbieten null und werfen bei Änderung UnsupportedOperationException.
  6. Unmodifiable vs immutable: Collections.unmodifiableList verhindert nur Änderungen über diese Referenz. Das Original kann sich weiter ändern.
  7. Records: Felder sind private final, die Klasse ist final, keine Setter. Aber Komponenten mit veränderlichen Typen brauchen eine Kopie im kompakten Konstruktor.
  8. „Änderung“ per with-Methode: withStatus(DONE) liefert ein neues Objekt. Das ist auch das Muster in java.time und String.
  9. Lazy gecachte Werte: Ein Objekt darf intern etwas cachen und trotzdem unveränderlich wirken. Beispiel: String speichert seinen hashCode erst beim ersten Aufruf.
  10. Unveränderliche JDK-Klassen: String, Wrapper wie Integer, BigDecimal, BigInteger, java.time-Typen, UUID, Optional.

5. Vergleich

  • Unveränderliches Objekt: thread-sicher, guter Map-Schlüssel, einfach. Kosten: neue Objekte bei jeder Änderung.
  • Veränderliches Objekt mit Lock: spart Objekte, aber jeder Zugriff braucht Synchronisation.
  • Builder: veränderlich während des Aufbaus, dann build() zu einem unveränderlichen Objekt. Gut für viele Felder.
  • Record: kurzer Weg zu einem flach unveränderlichen Datenträger.
  • Lombok @Value: erzeugt eine ähnliche Klasse per Annotation-Processing. Seit Records oft unnötig.
  • Persistente Collections (Bibliotheken wie Vavr): unveränderlich mit geteilter Struktur, billige „Änderungen“.

6. In der Produktion

  1. Geteilte Konfiguration ändert sich unter der Hand: Ein Service gibt seine interne Map heraus, ein Aufrufer ändert sie. Lösung: Map.copyOf im Getter oder beim Aufbau.
  2. Hibernate-Entities: JPA braucht einen leeren Konstruktor und veränderliche Felder. Entities sind darum selten unveränderlich. Lösung: unveränderliche DTOs und Value Objects (Records) an den Grenzen.
  3. Viel Garbage in heissen Schleifen: Tausende BigDecimal.add oder String-Verkettungen erzeugen viele Objekte. Lösung: messen; meist ist der GC schnell genug, sonst StringBuilder oder primitive Typen.
  4. Jackson und Records: Jackson (ab 2.12) deserialisiert Records über den kanonischen Konstruktor. Ältere Versionen brauchen @JsonCreator.
  5. Konfiguration neu laden: Ein neues unveränderliches Objekt bauen und die Referenz atomar tauschen (volatile oder AtomicReference). Leser sehen immer einen konsistenten Stand.

7. Diagnose: Werkzeuge und Befehle

  • Stack Trace mit UnsupportedOperationException aus ImmutableCollections: jemand will eine unveränderliche Liste ändern. Meist ein Design-Fehler beim Aufrufer.
  • SpotBugs: Regeln EI_EXPOSE_REP und EI_EXPOSE_REP2 melden herausgegebene oder gespeicherte veränderliche Referenzen.
  • SonarQube: meldet public static Arrays und veränderliche Collections in Konstanten.
  • ArchUnit: Test, dass alle Klassen in ..domain.value.. final sind und nur final Felder haben.
  • JFR Allocation-Profil: zeigt, ob unveränderliche Objekte wirklich zu viel Garbage erzeugen.

8. Senior-Punkte

  1. Standard ist unveränderlich. Veränderlich nur dort, wo es einen Grund gibt, z. B. JPA-Entities oder Builder.
  2. Unveränderlichkeit ersetzt Locks. Geteilter Zustand ohne Änderungen braucht keine Synchronisation. Das ist die billigste Thread-Sicherheit.
  3. Kopien an den Grenzen. Wo Daten in ein Objekt hinein- oder herausgehen, wird kopiert. Innen nicht.
  4. Records sind flach. Wer Listen in Records hat, braucht einen kompakten Konstruktor mit List.copyOf.
  5. Kosten messen, nicht raten. Kurzlebige Objekte sind für moderne GCs billig. Escape Analysis entfernt manche ganz.
  6. Gleiche Idee in Daten-Systemen: Append-only-Logs und Snapshots sind auch unveränderlich und darum leicht zu wiederholen.

10. Fallen

  • „Ein final-Feld macht das Objekt unveränderlich.“ → Falsch. Es fixiert nur die Referenz. Eine Liste darin bleibt veränderlich.
  • „Collections.unmodifiableList ist unveränderlich.“ → Falsch. Es ist ein View. Das Original kann sich ändern.
  • „Records sind tief unveränderlich.“ → Falsch. Nur flach. Veränderliche Komponenten brauchen eine Kopie.
  • „Unveränderliche Objekte sind immer langsam.“ → Falsch. Kurzlebige Objekte sind billig, und man spart Locks und Kopien beim Lesen.
  • „Erst prüfen, dann kopieren.“ → Falsch. Erst kopieren, dann die Kopie prüfen. Sonst TOCTOU.
  • „s.toUpperCase() ändert s.“ → Falsch. Es liefert einen neuen String.

11. Fragen

Was ist ein unveränderliches Objekt?

Ein Objekt, dessen Zustand sich nach dem Konstruktor nie ändert. Änderungen erzeugen ein neues Objekt.

Welche Regeln gelten für eine unveränderliche Klasse?

Keine Setter, Klasse final, Felder private final, defensive Kopien rein und raus, this nicht im Konstruktor entkommen lassen.

Warum soll die Klasse final sein?

Eine Unterklasse könnte veränderliche Felder oder Methoden hinzufügen und sich als die Basisklasse ausgeben.

Was ist eine defensive Kopie?

Eine eigene Kopie eines veränderlichen Parameters oder Feldes. So kann niemand von aussen den Zustand ändern.

Warum zuerst kopieren und dann prüfen?

Sonst kann ein anderer Thread den Parameter nach der Prüfung ändern. Die Prüfung gilt dann nicht mehr.

Warum sind unveränderliche Objekte thread-sicher?

Es gibt nichts zu ändern, also keine Race Conditions. Final-Felder sind nach dem Konstruktor für alle Threads sichtbar.

Welche Rolle spielt final im Java Memory Model?

Final-Felder sind nach Ende des Konstruktors für alle Threads korrekt sichtbar, wenn this nicht entkommen ist. Ohne volatile oder Lock.

Warum sind unveränderliche Objekte gute Map-Schlüssel?

Ihr hashCode ändert sich nie. Die Map findet den Eintrag immer wieder.

Unmodifiable vs immutable?

Unmodifiable heisst: über diese Referenz nicht änderbar. Immutable heisst: überhaupt nie änderbar.

List.copyOf vs Collections.unmodifiableList?

List.copyOf macht eine echte unveränderliche Kopie. unmodifiableList ist ein View, der Änderungen am Original zeigt.

Sind Records unveränderlich?

Flach ja: final Felder, keine Setter, final Klasse. Veränderliche Komponenten wie Listen muss man im kompakten Konstruktor kopieren.

Was ist der Unterschied zwischen flach und tief unveränderlich?

Flach: Referenzen ändern sich nicht. Tief: auch die referenzierten Objekte ändern sich nicht.

Wie „ändert“ man ein unveränderliches Objekt?

Mit einer with-Methode, die ein neues Objekt mit dem geänderten Wert liefert, z. B. LocalDate.plusDays.

Nennen Sie unveränderliche JDK-Klassen.

String, Integer und andere Wrapper, BigDecimal, LocalDate und andere java.time-Typen, UUID, Optional.

Warum ist String unveränderlich?

Für String Pool, Sicherheit (z. B. Klassennamen, Pfade), gecachten hashCode und Thread-Sicherheit.

Was ist das Problem mit java.util.Date?

Date ist veränderlich. Wer ein Date-Feld hat, braucht Kopien rein und raus. Besser Instant oder LocalDate.

Kann ein unveränderliches Objekt intern etwas cachen?

Ja, wenn es von aussen nicht sichtbar ist. String cacht seinen hashCode beim ersten Aufruf.

Wann ist ein Builder sinnvoll?

Bei vielen, teils optionalen Feldern. Der Builder ist veränderlich, build() liefert das unveränderliche Objekt.

Warum sind JPA-Entities selten unveränderlich?

JPA braucht einen leeren Konstruktor und setzt Felder per Reflection. Dirty Checking erwartet Änderungen.

Was kostet Unveränderlichkeit?

Neue Objekte bei jeder Änderung. Meist billig für den GC, in sehr heissen Schleifen messbar.

Szenario: Eine Konfigurations-Map ändert sich zur Laufzeit, obwohl niemand sie neu lädt. Was prüfen Sie?

Ob ein Getter die interne Map herausgibt und ein Aufrufer sie ändert. Lösung: Map.copyOf beim Aufbau, unveränderliche Map herausgeben.

Szenario: Ein Record mit einer Liste wird als Map-Schlüssel genutzt, und Einträge sind plötzlich unauffindbar. Warum?

Die Liste wurde nach dem put geändert. Der hashCode des Records ändert sich mit. Lösung: List.copyOf im kompakten Konstruktor.

Szenario: Eine Konfiguration soll im Betrieb neu geladen werden, ohne Leser zu stören. Wie bauen Sie das?

Ein neues unveränderliches Konfig-Objekt bauen und die Referenz atomar tauschen, z. B. per volatile oder AtomicReference. Leser sehen immer alten oder neuen Stand, nie einen halben.
