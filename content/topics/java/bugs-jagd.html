Drill: Bugs finden und fixen

Vorgehen pro Snippet — immer dieselben 3 Schritte, dann erst die Lösung öffnen:

  1. Laut lesen: Zeile für Zeile sagen, was der Code wirklich tut — nicht, was er tun soll.
  2. Checkliste abklopfen: Null? Gleichheit (== / equals / hashCode)? Threads und geteilter Zustand? Ressourcen geschlossen? Transaktion/Atomarität?
  3. Fix nennen + warum: erst die Laufzeit-Folge (Exception, falscher Wert, Leak), dann die Fix-Zeile, dann der Mechanismus in einem Satz.

2. Übung 1

@Service
public class GutscheinService {
    private final GutscheinRepository repo;

    public GutscheinService(GutscheinRepository repo) { this.repo = repo; }

    public BigDecimal rabatt(String eingabe) {
        Gutschein g = repo.findeCode(eingabe.trim().toUpperCase());
        if (g.status() == "AKTIV") {          // status() liefert String
            return g.rabattProzent();
        }
        return BigDecimal.ZERO;
    }
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: String-Vergleich mit ==.

Zur Laufzeit: keine Exception, sondern ein falscher Wert — der Status aus der Datenbank ist ein anderes String-Objekt als das Literal "AKTIV", der Vergleich ist fast immer false, jeder gültige Gutschein liefert 0 %.

Fix: if ("AKTIV".equals(g.status())) — oder besser ein Enum für den Status.

Mechanismus: == vergleicht bei Objekten Referenzen, nie Inhalt; nur equals vergleicht Zeichen.

Warum war der Unit-Test trotzdem grün?

Im Test stand vermutlich new Gutschein(..., "AKTIV") mit einem Literal — Literale landen im String-Pool, beide Referenzen zeigen auf dasselbe Objekt, == ist zufällig true. Strings aus DB, Netzwerk oder toUpperCase() sind frische Objekte. Genau deshalb ist „funktioniert im Test" hier kein Beweis.

3. Übung 2

public class ArtikelNummer {
    private final String wert;

    public ArtikelNummer(String wert) { this.wert = wert; }

    @Override
    public boolean equals(Object o) {
        return o instanceof ArtikelNummer a && wert.equals(a.wert);
    }
}

Map<ArtikelNummer, Integer> bestand = new HashMap<>();
bestand.put(new ArtikelNummer("A-100"), 25);
int stueck = bestand.get(new ArtikelNummer("A-100"));
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: equals überschrieben, hashCode nicht.

Zur Laufzeit: get liefert null (die zwei Objekte haben verschiedene Identitäts-Hashes und landen in verschiedenen Buckets) — und beim Unboxing in int stueck knallt eine NullPointerException.

Fix: @Override public int hashCode() { return wert.hashCode(); } — oder die Klasse als record ArtikelNummer(String wert) deklarieren, dann kommen beide Methoden konsistent geschenkt.

Mechanismus: HashMap sucht erst den Bucket per hashCode, erst darin vergleicht sie mit equals — ohne gleichen Hash wird equals nie gefragt.

4. Übung 3

public void bereinige(List<Buchung> buchungen) {
    for (Buchung b : buchungen) {
        if (b.istStorniert()) {
            buchungen.remove(b);
        }
    }
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: Entfernen aus der Liste mitten im for-each über dieselbe Liste.

Zur Laufzeit: ConcurrentModificationException beim nächsten Iterationsschritt — single-threaded, ganz ohne Nebenläufigkeit: der Iterator prüft bei jedem next() seinen Änderungszähler (modCount) gegen die Liste.

Fix: buchungen.removeIf(Buchung::istStorniert); — oder explizit über Iterator laufen und it.remove() benutzen.

Mechanismus: for-each benutzt verdeckt einen Iterator; nur der Iterator selbst darf während des Laufs strukturell ändern.

5. Übung 4

@Service
public class RechnungsExport {
    private static final SimpleDateFormat FORMAT =
            new SimpleDateFormat("yyyy-MM-dd");

    // wird von vielen HTTP-Requests parallel aufgerufen
    public String kopfzeile(Rechnung r) {
        return r.nummer() + ";" + FORMAT.format(r.datum());
    }
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: SimpleDateFormat als geteiltes static-Feld — die Klasse ist nicht threadsafe (sie hat ein internes, veränderliches Calendar-Objekt).

Zur Laufzeit: unter Last sporadisch vertauschte/korrupte Datumswerte oder NumberFormatException — zwei Threads schreiben gleichzeitig in denselben internen Zustand. Der schlimmste Bug-Typ: im Test nie, in Produktion freitags.

Fix: private static final DateTimeFormatter FORMAT = DateTimeFormatter.ofPattern("yyyy-MM-dd"); und LocalDate statt Date — DateTimeFormatter ist immutable und laut Doku threadsafe.

Mechanismus: unveränderliche Objekte können gefahrlos geteilt werden; veränderliche geteilte Zustände brauchen Synchronisation — oder man schafft sie ab.

6. Übung 5

public List<String> leseZeilen(Path datei) throws IOException {
    BufferedReader reader = Files.newBufferedReader(datei);
    List<String> zeilen = new ArrayList<>();
    String zeile;
    while ((zeile = reader.readLine()) != null) {
        zeilen.add(zeile);
    }
    reader.close();
    return zeilen;
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: Ressourcen-Leak — close() wird bei einer Exception in readLine() nie erreicht.

Zur Laufzeit: jedes fehlerhafte Einlesen lässt ein offenes Datei-Handle zurück; unter Last endet das im Betriebssystem-Fehler „too many open files" — der ganze Prozess kann keine Dateien und Sockets mehr öffnen.

Fix: try (BufferedReader reader = Files.newBufferedReader(datei)) { ... } — oder hier gleich Files.readAllLines(datei).

Mechanismus: try-with-resources ruft close() garantiert auf, auch im Fehlerfall, und hängt Folgefehler als suppressed Exceptions an.

7. Übung 6

public List<Bestellung> eigeneBestellungen(Integer kundeId,
                                           List<Bestellung> alle) {
    return alle.stream()
            .filter(b -> b.kundeId() == kundeId)   // beide Integer
            .toList();
}

// Test:   kundeId = 42     → findet alles, gruen
// Prod:   kundeId = 48213  → findet nichts
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: == auf zwei Integer-Objekten.

Zur Laufzeit: falscher Wert statt Exception — Integer.valueOf cached die Werte −128 bis 127; kleine Test-Ids zeigen auf dasselbe gecachte Objekt (== true), echte Ids ab 128 sind frische Objekte (== false). Der Kunde sieht eine leere Bestellliste.

Fix: b.kundeId().equals(kundeId) — oder null-sicher Objects.equals(b.kundeId(), kundeId); langfristig long/Long konsequent als Primitiv vergleichen.

Mechanismus: == vergleicht bei Wrapper-Objekten Referenzen; der kleine Cache macht den Fehler heimtückisch, weil er „bis 127 funktioniert".

Warum gibt es diesen Cache überhaupt?

Autoboxing (Integer x = 5;) läuft über Integer.valueOf, und häufige kleine Werte zu teilen spart Objekte. Der Cache ist Pflicht für −128..127, kann aber per JVM-Option größer sein — noch ein Grund, warum sich == auf Wrappern nie lohnt: das Verhalten hängt an der Laufzeit-Konfiguration.

8. Übung 7

public class WarenkorbRechner {
    // Preise liegen als double vor, z. B. 0.10 und 0.20
    public double brutto(List<Position> positionen) {
        double summe = 0.0;
        for (Position p : positionen) {
            summe += p.preis() * p.menge();
        }
        return summe * 1.19;
    }
}

// brutto([0.10, 0.20]) erwartet: 0.357 — tatsaechlich?
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: double für Geldbeträge.

Zur Laufzeit: schleichend falsche Werte: schon 0.1 + 0.2 ergibt 0.30000000000000004, denn 0.1 ist binär nicht exakt darstellbar; über viele Positionen und die Steuer-Multiplikation wachsen Rundungsfehler bis zum sichtbaren Cent-Unterschied auf der Rechnung.

Fix: BigDecimal, erzeugt aus String: new BigDecimal("0.10"), summieren mit add, am Ende setScale(2, RoundingMode.HALF_UP).

Mechanismus: Binär-Gleitkomma kann Zehntel nicht exakt speichern; BigDecimal(String) speichert dezimal exakt — der double-Konstruktor new BigDecimal(0.1) würde den Fehler dagegen mit übernehmen.

9. Übung 8

Stream<Bestellung> offene = bestellungen.stream()
        .filter(b -> b.status() == Status.OFFEN);

long anzahl = offene.count();

BigDecimal summe = offene
        .map(Bestellung::betrag)
        .reduce(BigDecimal.ZERO, BigDecimal::add);
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: derselbe Stream wird zweimal benutzt.

Zur Laufzeit: IllegalStateException: „stream has already been operated upon or closed" — beim zweiten Zugriff, denn count() ist eine Terminal-Operation und verbraucht die Pipeline.

Fix: erst materialisieren: List<Bestellung> offene = ...filter(...).toList(); und dann offene.size() und die Summe aus der Liste — oder zweimal frisch bestellungen.stream() aufsetzen.

Mechanismus: ein Stream ist eine Einweg-Pipeline über der Quelle, keine Datenstruktur — genau eine Terminal-Operation, danach ist er zu.

10. Übung 9

// equals/hashCode von Sitzplatz gehen ueber (reihe, nummer)
Set<Sitzplatz> reserviert = new HashSet<>();

Sitzplatz s = new Sitzplatz("A", 12);
reserviert.add(s);

s.setReihe("B");                        // Umbuchung

reserviert.contains(s);                 // ?
reserviert.remove(s);                   // ?
System.out.println(reserviert.size());  // ?
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: veränderlicher Schlüssel — das Objekt wird nach dem Einfügen ins HashSet mutiert.

Zur Laufzeit: contains ist false und remove wirkungslos (beide suchen im Bucket des neuen Hashes, das Objekt liegt aber im alten), size() bleibt 1 — der Platz ist unauffindbar, aber belegt: ein logisches Leck, das ewig „reserviert" bleibt.

Fix: Schlüsselklassen unveränderlich machen (record Sitzplatz(String reihe, int nummer)); eine Umbuchung ist dann remove(alt) + add(neu).

Mechanismus: HashSet merkt sich den Bucket vom Einfüge-Zeitpunkt; ändert sich der Hash danach, zeigt die Suche auf den falschen Bucket.

11. Übung 10

@Service
public class KontoService {
    private final KontoRepository repo;

    public KontoService(KontoRepository repo) { this.repo = repo; }

    public void monatsabschluss(List<Long> kontoIds) {
        for (Long id : kontoIds) {
            verbuche(id);                    // interner Aufruf
        }
    }

    @Transactional
    private void verbuche(Long id) {
        Konto k = repo.findById(id).orElseThrow();
        k.zinsenGutschreiben();
        repo.save(k);
    }
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: @Transactional ist hier wirkungslos — doppelt: die Methode ist private, und sie wird per Selbstaufruf (this.verbuche(id)) gerufen.

Zur Laufzeit: keine Exception, es läuft einfach ohne die erwartete Transaktion — jede DB-Operation committet für sich; fliegt mitten im Abschluss ein Fehler, gibt es keinen Rollback, die Konten sind halb verbucht.

Fix: Methode public machen und den Aufruf durch den Proxy führen: die transaktionale Logik in eine zweite @Service-Bean auslagern und diese injizieren.

Mechanismus: Spring legt die Transaktion in einen Proxy um die Bean; nur Aufrufe von außen laufen durch ihn. this.methode() umgeht den Proxy, und private Methoden kann der Proxy gar nicht abfangen.

Woran erkennst du diese Bug-Klasse in 5 Sekunden?

Suchmuster: eine annotierte Methode (@Transactional, @Cacheable, @Async), die aus derselben Klasse heraus aufgerufen wird. Sobald du „this." vor einem annotierten Aufruf siehst oder die Annotation auf etwas Nicht-Öffentlichem steht: Proxy-Mechanismus erklären — das ist eine klassische Senior-Erkennungsfrage.

12. Übung 11

public Kunde findePerEmail(String email) throws SQLException {
    String sql = "SELECT id, name, email FROM kunde WHERE email = '"
            + email + "'";
    try (Statement st = verbindung.createStatement();
         ResultSet rs = st.executeQuery(sql)) {
        if (rs.next()) {
            return new Kunde(rs.getLong(1), rs.getString(2), rs.getString(3));
        }
        return null;
    }
}
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: SQL-Injection — Nutzereingabe wird in den SQL-Text konkateniert.

Zur Laufzeit: die Eingabe ' OR '1'='1 macht die WHERE-Bedingung immer wahr und liefert fremde Kundendaten; mit '; DROP TABLE kunde;-- wird aus einer Suche ein Schema-Angriff. Kein Absturz — ein Datenleck.

Fix: PreparedStatement ps = verbindung.prepareStatement("SELECT id, name, email FROM kunde WHERE email = ?"); ps.setString(1, email);

Mechanismus: beim PreparedStatement gehen SQL-Text und Parameter getrennt an die Datenbank — der Parameter wird nie als SQL geparst, egal was drinsteht.

13. Übung 12

@Transactional
public void reserviere(long artikelId, int menge) {
    Artikel a = repo.findById(artikelId).orElseThrow();

    if (a.bestand() >= menge) {              // 1. lesen + pruefen
        a.setBestand(a.bestand() - menge);   // 2. schreiben
        repo.save(a);
    } else {
        throw new AusverkauftException();
    }
}
// Black-Friday: 2 Requests gleichzeitig, bestand = 1, menge = 1
Finde den Bug. Was passiert zur Laufzeit? Dein Fix?
Lösung

Bug: read-then-write ohne Atomarität — die Prüfung und das Schreiben sind zwei getrennte Schritte über Transaktionsgrenzen hinweg nicht geschützt.

Zur Laufzeit: Doppelbuchung: beide Transaktionen lesen bestand = 1 (Read Committed sperrt Lesen nicht), beide bestehen die Prüfung, beide schreiben — Bestand −1, zwei Kunden haben denselben letzten Artikel gekauft.

Fix: die Datenbank atomar prüfen und schreiben lassen: UPDATE artikel SET bestand = bestand - :menge WHERE id = :id AND bestand >= :menge — und die Anzahl betroffener Zeilen prüfen: 0 Zeilen = ausverkauft. Alternativen: @Version (Optimistic Locking) oder SELECT ... FOR UPDATE.

Mechanismus: ein einzelnes UPDATE sperrt die Zeile während der Ausführung — Bedingung und Schreiben passieren unteilbar in der DB statt in zwei Java-Schritten.

Aber da steht doch @Transactional — warum rettet das nichts?

Eine Transaktion garantiert Atomarität der eigenen Schritte (alles oder nichts bei Commit/Rollback), aber mit Standard-Isolation Read Committed verhindert sie nicht, dass zwei parallele Transaktionen denselben alten Wert lesen (Lost Update). Isolation gegen parallele Leser-Schreiber kostet extra: atomares UPDATE, Locks oder eine Versionsspalte. Diesen Unterschied zu kennen trennt im Interview Mid von Senior.

15. So formulierst du den Fix im Interview

Vier Sätze, feste Reihenfolge — damit klingst du nach Produktion, nicht nach Quiz:

  1. Bug: „Hier wird der Status mit == verglichen — das prüft die Referenz, nicht den Inhalt."
  2. Laufzeit-Folge: „Zur Laufzeit ist das fast immer false — gültige Gutscheine liefern 0 %, ohne jede Exception."
  3. Fix: „Ich ersetze es durch "AKTIV".equals(status) — Literal zuerst, dann ist es auch nullsicher."
  4. Test: „Und ich schreibe einen Test, der den Status als neues String-Objekt baut, damit die Regression nie zurückkommt."

16. Drei Fallen beim Bug-Nennen

  • Nur das Symptom nennen: „Da kommt eine Exception" ist die halbe Antwort — ohne den Mechanismus (warum der Iterator wirft, warum der Bucket nicht mehr passt) klingt es geraten.
  • Fix ohne Begründung: „Ich nehme BigDecimal" überzeugt erst mit dem Warum — „weil 0.1 binär nicht exakt darstellbar ist und der String-Konstruktor dezimal exakt speichert".
  • Den zweiten versteckten Bug raten: nenne zuerst sicher den Haupt-Bug mit Mechanismus und Fix; danach darfst du sagen „zusätzlich würde ich X prüfen" — aber wackle nie die sichere Antwort durch Spekulation an.

Übe jedes Snippet, bis Bug, Laufzeit-Folge, Fix und Mechanismus in 45 Sekunden frei kommen — genau in dieser Reihenfolge.
