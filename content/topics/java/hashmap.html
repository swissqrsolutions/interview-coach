HashMap

Java · Tier 1 · Quellen: OpenJDK java.util.HashMap (Quellcode JDK 17/21), Java SE 21 API-Doku (HashMap, Object.hashCode), JEP 180, JDK-8186958 (newHashMap, Java 19)

Kern: Eine HashMap ist eine Map, die Schlüssel-Wert-Paare in einem Array von Buckets speichert. Sie findet einen Eintrag über den Hash des Schlüssels, im Durchschnitt in O(1). Sie ist nicht thread-sicher und hat keine feste Reihenfolge.

1. Wo sitzt die HashMap?

  1. Das HashMap-Objekt hält ein Array table und Zähler wie size und threshold.
  2. Jedes Feld im Array ist ein Bucket, also ein Fach für Einträge.
  3. Ein Eintrag ist ein Node mit vier Feldern: hash, key, value, next.
  4. Landen zwei Schlüssel im gleichen Bucket, hängt der zweite über next am ersten. Das ist eine Kollision.
  5. Hat ein Bucket sehr viele Einträge, wird die Liste ein TreeNode-Baum, also ein Rot-Schwarz-Baum.
  6. Das Array entsteht erst beim ersten put (lazy). Standardgrösse: 16.

2. Die Reise eines put() (die Geschichte zum Merken)

  1. hashCode(): put("Bern", 1) ruft zuerst "Bern".hashCode() auf. Ergebnis: 2066911.
  2. Bits mischen (Hash Spreading): HashMap rechnet h ^ (h >>> 16). So zählen die oberen Bits auch für den Index.
  3. Index berechnen: Der Index ist (n − 1) & hash, also nur die unteren Bits. Bei n = 16 sind es die unteren 4 Bits.
  4. Bucket prüfen: Ist der Bucket leer, kommt ein neuer Node hinein. Fertig.
  5. Kette durchsuchen: Ist der Bucket voll, vergleicht HashMap jeden Node. Gleicher hash und equals() true: Der alte Wert wird ersetzt. Sonst kommt der neue Node ans Ende.
  6. Treeify prüfen: Wird die Kette zu lang, entsteht ein Baum. Aber nur, wenn das Array schon 64 Buckets hat. Sonst vergrössert HashMap zuerst das Array.
  7. Resize prüfen: Ist size grösser als threshold, verdoppelt HashMap das Array und verteilt alle Einträge neu.

get() geht denselben Weg bis Schritt 5. Es ersetzt nichts, sondern gibt den Wert zurück oder null.

Echte Ausgabe, OpenJDK 17.0.3 (HashMap ist in 21 gleich). Bei 4) sind die Zeilen 1–7 gekürzt; sie zeigen alle capacity=16 bucket=Node.

  1. "Aa" und "BB" haben den gleichen hashCode 2112. Sie landen im gleichen Bucket: eine echte Kollision.
  2. Resize passiert genau beim 13., 25., 49. und 97. Eintrag. Die Grenze ist immer Kapazität × 0.75.
  3. new HashMap<>(1000) rundet auf 1024 auf. Die Grenze ist 768. Ab dem 769. Eintrag kommt ein Resize.
  4. Beim 9. und 10. Eintrag im gleichen Bucket gibt es kein Treeify, sondern ein Resize (16 → 32 → 64). Erst bei Kapazität 64 wird der Bucket ein TreeNode.
  5. Nach key.add("b") ändert sich der Hash der Liste. get findet den Eintrag nicht mehr, aber size ist noch 1.

4. Details, die Interviewer fragen

  1. Hash Spreading: h ^ (h >>> 16) mischt die oberen 16 Bits in die unteren. Der Index nutzt nur die unteren Bits. Ohne Mischen kollidieren Schlüssel, die sich nur oben unterscheiden.
  2. Kapazität als Zweierpotenz: Die Grösse ist immer 16, 32, 64 … So ist (n − 1) & hash gleich wie Modulo, aber schneller. Eine Kapazität wie 1000 wird auf 1024 aufgerundet.
  3. Kollision und Separate Chaining: Eine Kollision heisst, zwei Schlüssel landen im gleichen Bucket. HashMap löst sie mit einer verketteten Liste (Separate Chaining). Neue Nodes kommen seit Java 8 ans Ende.
  4. Treeify: Wächst eine Kette über 8 Nodes (TREEIFY_THRESHOLD = 8), ruft HashMap treeifyBin auf. Ist das Array kleiner als 64 (MIN_TREEIFY_CAPACITY), macht es stattdessen ein Resize. Sonst wird die Kette ein Rot-Schwarz-Baum. Suche dort: O(log n).
  5. Untreeify: Hat ein Baum nach einem Resize 6 oder weniger Nodes (UNTREEIFY_THRESHOLD = 6), wird er wieder eine Liste. Der Abstand 8 zu 6 verhindert ständiges Hin und Her.
  6. Load Factor: Der Load Factor (Standard 0.75) bestimmt, wie voll die Map werden darf. Threshold = Kapazität × Load Factor. 0.75 ist ein Kompromiss aus Speicher und Kollisionen.
  7. Resize: Ein Resize verdoppelt das Array und verteilt alle Einträge neu. Ein Eintrag bleibt am Index oder geht auf Index + alte Grösse. Ein einziges Bit entscheidet. Kosten: O(n), aber selten.
  8. equals/hashCode-Vertrag: Gleiche Objekte (equals true) müssen den gleichen hashCode haben. Gleicher hashCode heisst aber nicht gleiche Objekte. Nur equals überschreiben bricht die Map: Gleiche Schlüssel landen in verschiedenen Buckets.
  9. Veränderbare Schlüssel: Ändert sich ein Schlüssel nach put, ändert sich sein Hash. Der Eintrag ist dann unerreichbar, belegt aber Speicher. Darum unveränderliche Schlüssel nutzen: String, Integer, Records.
  10. null: Ein null-Schlüssel ist erlaubt und liegt immer in Bucket 0. get liefert null bei fehlendem Schlüssel und bei Wert null. Darum containsKey.
  11. Iteration: Die Reihenfolge ist nicht garantiert und kann sich nach einem Resize ändern. Ändert man die Map beim Iterieren, kommt eine ConcurrentModificationException. Sie ist fail-fast, aber nur „best effort“.
  12. Komplexität: get, put, remove: im Durchschnitt O(1). Schlimmster Fall: O(log n) mit Baum, vor Java 8 O(n). containsValue: immer O(n).

5. Vergleich

  • HashMap: keine Reihenfolge, ein null-Schlüssel, nicht thread-sicher, O(1).
  • LinkedHashMap: merkt sich Einfüge- oder Zugriffsreihenfolge mit einer doppelt verketteten Liste. Mit accessOrder = true und removeEldestEntry baut man einen LRU-Cache.
  • TreeMap: sortiert nach Schlüssel (Rot-Schwarz-Baum), O(log n), kein null-Schlüssel mit natürlicher Ordnung.
  • ConcurrentHashMap: thread-sicher mit feinen Sperren (CAS und Lock pro Bucket). Kein null. Iteratoren sind weakly consistent statt fail-fast.
  • Hashtable: alt (Java 1.0), jede Methode synchronized, kein null. Heute nicht mehr nutzen.
  • Collections.synchronizedMap: ein Lock für alles. Beim Iterieren muss man selbst synchronisieren.
  • EnumMap: für Enum-Schlüssel, intern ein Array, sehr schnell.
  • HashSet: ist intern eine HashMap. Das Element ist der Schlüssel, der Wert ein Dummy-Objekt.
  • Map.of(): unveränderlich, kein null, zufällige Reihenfolge.

6. In der Produktion

  1. Daten weg oder falsch bei mehreren Threads: HashMap ist nicht thread-sicher. Gleichzeitige put verlieren Einträge. Vor Java 8 konnte ein Resize sogar eine Endlosschleife bauen. Lösung: ConcurrentHashMap.
  2. Memory Leak durch Cache: Eine statische HashMap als Cache wächst ohne Grenze. Lösung: begrenzter Cache (LRU mit LinkedHashMap oder eine Bibliothek wie Caffeine) mit Grösse und Ablaufzeit.
  3. Memory Leak durch veränderte Schlüssel: Einträge werden unerreichbar, bleiben aber im Speicher. Lösung: unveränderliche Schlüssel.
  4. Langsam durch schlechten hashCode: Ein hashCode, der oft gleich ist, erzeugt lange Ketten. Lösung: Objects.hash(...) oder ein Record.
  5. Kurze Spitzen durch Resize: Ein Resize bei Millionen Einträgen kostet Zeit. Lösung: Grösse vorher setzen mit HashMap.newHashMap(n) (Java 19+).
  6. Viel Speicher: Jeder Eintrag ist ein eigenes Objekt (Node, etwa 32 Bytes plus Schlüssel und Wert). Bei Millionen Einträgen zählt das. HashMap<Integer,Integer> erzeugt zusätzlich viele Wrapper-Objekte.

7. Diagnose: Werkzeuge und Befehle

  • jcmd <pid> GC.class_histogram: zeigt viele java.util.HashMap$Node-Objekte bei einem Leak.
  • Heap Dump (jcmd <pid> GC.heap_dump file.hprof) mit Eclipse MAT: findet die grösste HashMap und wer sie hält.
  • JFR (Java Flight Recorder): zeigt Allokationen und heisse Methoden wie HashMap.resize.
  • Profiler (async-profiler, IntelliJ): zeigt Zeit in HashMap.getNode bei langen Ketten.
  • Unit-Test für equals/hashCode: z. B. mit EqualsVerifier.

8. Senior-Punkte

  1. O(1) ist ein Durchschnitt, keine Garantie. Er hängt vom hashCode ab. Treeify begrenzt den schlimmsten Fall auf O(log n).
  2. Die richtige Map ist eine Entscheidung: Threads → ConcurrentHashMap. Reihenfolge → LinkedHashMap. Sortierung → TreeMap. Enum → EnumMap.
  3. Schlüssel immer unveränderlich. Records sind dafür ideal: equals und hashCode kommen automatisch.
  4. Grösse vorher setzen, wenn sie bekannt ist. Aber nur in heissen Pfaden, sonst lohnt es nicht.
  5. Ein Cache ist nie eine nackte HashMap. Er braucht eine Grenze und eine Ablaufzeit.
  6. Treeify ist ein Schutz gegen Hash-Flooding, also Angriffe mit vielen gleichen Hashes. Es ist kein normaler Betriebszustand.

9. Aus dem Projekt

„Für Lookups über eine ID nutze ich eine HashMap, bei mehreren Threads eine ConcurrentHashMap.“ (Prüfen und durch dein echtes Beispiel ersetzen, z. B. aus DAZiT oder CARIAD.)

10. Fallen

  • „HashMap hat immer O(1).“ → Falsch. Nur im Durchschnitt. Schlimmster Fall O(log n), ein Resize kostet O(n).
  • „Ab 8 Einträgen in einem Bucket gibt es einen Baum.“ → Falsch. Erst über 8 und nur ab 64 Buckets. Sonst kommt zuerst ein Resize.
  • „Gleicher hashCode heisst gleiche Objekte.“ → Falsch. Nur umgekehrt: Gleiche Objekte brauchen den gleichen hashCode.
  • „new HashMap<>(1000) hält 1000 Einträge ohne Resize.“ → Falsch. Kapazität 1024, Grenze 768.
  • „synchronizedMap ist so gut wie ConcurrentHashMap.“ → Falsch. Ein Lock für alles, und Iteration braucht eigene Synchronisation.
  • „get() == null heisst, der Schlüssel fehlt.“ → Falsch. Der Wert kann null sein. Prüfen mit containsKey.

11. Fragen

Wie funktioniert eine HashMap intern?

Ein Array von Buckets. Der Index kommt aus dem Hash des Schlüssels. Kollisionen kommen in eine Liste, bei vielen in einen Baum. Ab 75 % Füllung verdoppelt sich das Array.

Was passiert bei put()?

hashCode, Bits mischen, Index berechnen, Bucket prüfen, mit equals vergleichen. Dann ersetzen oder anhängen. Danach eventuell Treeify oder Resize.

Was passiert bei get()?

Hash und Index berechnen, dann die Kette oder den Baum mit hash und equals durchsuchen. Nichts gefunden: null.

Was ist eine Kollision und wie wird sie gelöst?

Zwei Schlüssel im gleichen Bucket. HashMap löst sie mit einer verketteten Liste (Separate Chaining), bei vielen Einträgen mit einem Rot-Schwarz-Baum.

Warum h ^ (h >>> 16)?

Der Index nutzt nur die unteren Bits. Das Mischen bringt die oberen Bits dazu. So gibt es weniger Kollisionen.

Warum ist die Kapazität immer eine Zweierpotenz?

Dann ist (n − 1) & hash gleich wie Modulo, aber schneller. Und beim Resize entscheidet ein Bit über den neuen Index.

Was ist der Load Factor und warum 0.75?

Der Füllgrad, ab dem die Map wächst. 0.75 ist ein Kompromiss: wenig Kollisionen, nicht zu viel leerer Speicher.

Was ist der Threshold?

Kapazität × Load Factor. Ist size grösser, kommt ein Resize. Bei 16 Buckets: 12.

Was passiert beim Resize?

Das Array wird doppelt so gross. Jeder Eintrag bleibt am Index oder geht auf Index + alte Grösse. Kosten O(n).

Wann wird ein Bucket zum Baum?

Wenn die Kette über 8 Nodes wächst und das Array mindestens 64 Buckets hat. Sonst gibt es zuerst ein Resize.

Warum nicht sofort ein Baum?

Ein TreeNode braucht etwa doppelt so viel Speicher. Bei gutem hashCode sind Ketten sehr kurz.

Wann wird ein Baum wieder eine Liste?

Bei 6 oder weniger Nodes nach einem Resize. Der Abstand zu 8 verhindert ständiges Wechseln.

Welche Komplexität haben get und put?

Im Durchschnitt O(1). Schlimmster Fall O(log n) seit Java 8, vorher O(n).

Darf ein Schlüssel null sein?

Ja, einer. Er liegt in Bucket 0. Werte dürfen beliebig oft null sein. ConcurrentHashMap erlaubt kein null.

Was ist der equals/hashCode-Vertrag?

Gleiche Objekte müssen den gleichen hashCode haben. Gleicher hashCode heisst nicht gleiche Objekte.

Was passiert, wenn ich nur equals überschreibe?

Gleiche Objekte haben verschiedene Hashes und landen in verschiedenen Buckets. Die Map findet sie nicht und speichert Duplikate.

Was passiert mit einem veränderbaren Schlüssel?

Ändert sich sein Hash, sucht die Map im falschen Bucket. Der Eintrag ist unerreichbar und bleibt im Speicher.

Warum ist String ein guter Schlüssel?

String ist unveränderlich, equals ist korrekt, und der Hash wird nach dem ersten Aufruf gespeichert.

Ist HashMap thread-sicher?

Nein. Gleichzeitige Writes verlieren Daten. Für Threads: ConcurrentHashMap.

HashMap vs Hashtable?

Hashtable ist alt, ganz synchronized und ohne null. HashMap ist schneller, aber nicht thread-sicher. Heute statt Hashtable: ConcurrentHashMap.

HashMap vs ConcurrentHashMap?

ConcurrentHashMap ist thread-sicher mit feinen Sperren und CAS. Kein null. Iteratoren werfen keine ConcurrentModificationException.

HashMap vs TreeMap?

TreeMap ist sortiert, O(log n). HashMap ist ungeordnet, O(1).

HashMap vs LinkedHashMap?

LinkedHashMap merkt sich die Reihenfolge. Mit Zugriffsreihenfolge baut man einen LRU-Cache.

Wie ist HashSet aufgebaut?

Intern eine HashMap. Das Element ist der Schlüssel, der Wert ein festes Dummy-Objekt.

Was ist eine ConcurrentModificationException?

Die Map wurde beim Iterieren verändert. Lösung: iterator.remove() oder removeIf().

Was ist schneller: keySet() mit get() oder entrySet()?

entrySet(). Es braucht keine zweite Suche.

Wie gross wird new HashMap<>(100)?

Kapazität 128, Grenze 96.

Wie reserviere ich Platz für 1000 Einträge?

HashMap.newHashMap(1000) seit Java 19. Vorher Kapazität 1000 / 0.75 + 1.

Was machen computeIfAbsent und merge?

computeIfAbsent erzeugt einen fehlenden Wert, gut zum Gruppieren. merge kombiniert alten und neuen Wert, gut zum Zählen.

Was ist Hash-Flooding?

Ein Angreifer schickt viele Schlüssel mit gleichem Hash. Die Map wird langsam. Treeify begrenzt das auf O(log n).

Welche Reihenfolge hat die Iteration?

Keine garantierte. Sie kann sich nach einem Resize ändern.

Szenario: Ein Report zeigt nach Last manchmal weniger Einträge als erwartet. Warum?

Wahrscheinlich teilen sich mehrere Threads eine HashMap. Gleichzeitige put verlieren Einträge. Lösung: ConcurrentHashMap oder die Map nicht teilen.

Szenario: Der Heap wächst Tag für Tag, im Heap Dump sind Millionen HashMap$Node. Was tun Sie?

Im Heap Dump mit MAT den Besitzer finden, oft ein statischer Cache. Lösung: begrenzter Cache mit Grösse und Ablaufzeit. Prüfen, ob Schlüssel verändert werden.

Szenario: Lookups sind plötzlich langsam, obwohl die Map klein ist. Woran denken Sie?

An einen schlechten hashCode mit vielen Kollisionen. Im Profiler sieht man viel Zeit in getNode. Lösung: hashCode korrigieren, z. B. mit Objects.hash oder einem Record.
