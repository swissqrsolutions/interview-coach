ConcurrentHashMap

Kern: Eine ConcurrentHashMap ist eine thread-sichere Hash-Map für viele Threads gleichzeitig. Sie löst das Problem, dass eine HashMap bei parallelen Schreibzugriffen Daten verliert. Lesen braucht keinen Lock, Schreiben nutzt CAS oder einen Lock pro Bucket. Sie erlaubt kein null.

1. Wo sitzt die ConcurrentHashMap?

  1. table: ein volatile Array von Buckets, wie bei der HashMap. Es entsteht erst beim ersten put (lazy). Standardgrösse: 16.
  2. Leerer Bucket: Ein neuer Eintrag kommt per CAS hinein (Compare-and-Swap, atomarer CPU-Befehl). Kein Lock.
  3. Node-Liste: Ist der Bucket voll, sperrt ein Schreiber den ersten Node mit synchronized. Nur dieser eine Bucket ist gesperrt.
  4. TreeBin: Ein Bucket mit vielen Kollisionen wird ein Rot-Schwarz-Baum. Sein Kopf hat den Hash −2 (TREEBIN).
  5. ForwardingNode: eine Markierung während des Resize. Hash −1 (MOVED). Sie sagt: „Dieser Bucket ist schon in nextTable.“
  6. sizeCtl: ein Steuerfeld. Positiv heisst: nächste Resize-Grenze. Negativ heisst: Initialisierung oder Resize läuft gerade.
  7. baseCount und CounterCells: der Zähler für size(). Er funktioniert wie ein LongAdder: Bei Konkurrenz zählt jeder Thread in einer eigenen Zelle.

Hashing, Buckets, Treeify und Resize kennst du von der HashMap. Hier geht es nur darum, was ConcurrentHashMap für Threads anders macht.

2. Die Reise eines put() in ConcurrentHashMap (die Geschichte zum Merken)

  1. Hash berechnen: put("Bern", 1) ruft "Bern".hashCode() auf. spread mischt die Bits wie die HashMap und macht das Ergebnis positiv. Negative Hashes sind für Spezial-Nodes reserviert.
  2. Leerer Bucket: Thread T1 findet Bucket 0 leer. Er setzt den neuen Node per CAS. Schreibt T2 gleichzeitig dorthin, verliert einer den CAS und versucht es neu. Kein Lock nötig.
  3. Resize läuft: Steht dort eine ForwardingNode (Hash −1), läuft gerade ein Resize. T1 wartet nicht, sondern hilft beim Umkopieren (helpTransfer). Danach versucht er es in der neuen Tabelle.
  4. Bucket sperren: Ist der Bucket voll, sperrt T1 nur den ersten Node dieses Buckets mit synchronized. Alle anderen Buckets bleiben frei.
  5. Nachprüfen: Mit dem Lock prüft T1, ob der Kopf noch derselbe ist. Ein anderer Thread könnte ihn inzwischen geändert haben. Dann sucht T1 mit hash und equals: gefunden heisst ersetzen, sonst anhängen.
  6. Treeify prüfen: Wächst die Kette über 8 Nodes, wird sie ein Baum. Ist das Array kleiner als 64, gibt es stattdessen ein Resize.
  7. Zählen und Resize: addCount erhöht den Zähler per CAS. Bei Konkurrenz nutzt T1 eine eigene CounterCell. Erreicht die Grösse sizeCtl, startet ein Resize. Mehrere Threads teilen sich die Arbeit in Blöcken von mindestens 16 Buckets.

get() nimmt nie einen Lock. Es liest das Array und die Nodes über volatile-Zugriffe. Darum sieht es immer einen fertig geschriebenen Eintrag. Läuft ein Resize, folgt get der ForwardingNode in die neue Tabelle.

3. Beispiel: HashMap vs ConcurrentHashMap unter Last

// 1) 4 Threads, je 25_000 verschiedene Schlüssel
run(4, () -> { for (...) { int k = next.getAndIncrement(); m.put(k, k); } });

// 2) ein Wort 100_000 Mal zählen: get+put vs merge
run(4, () -> { for (...) c1.put("java", c1.get("java") + 1); });
run(4, () -> { for (...) c2.merge("java", 1, Integer::sum); });

// 3) null
chm.put(1, null);  chm.get(null);

// 4) beim Iterieren neue Schlüssel einfügen
for (String k : h.keySet()) h.put(k + "x", 0);   // HashMap a,b,c
for (String k : w.keySet()) w.put(k + "x", 0);   // CHM a,b,c

// 5) size und mappingCount bei 1000 Einträgen
// 6) 8 Threads x 1000 Mal computeIfAbsent("user-42", ...)

Echte Ausgabe, OpenJDK 17.0.3. Die Werte bei 1) HashMap und 2) get+put ändern sich bei jedem Lauf (zweiter Lauf: HashMap size=77026). Die Zeile „after put 13“ ist gekürzt, sie ist gleich wie „after put 12“. Die letzte Zeile ruft computeIfAbsent(100, …) und darin computeIfAbsent(132, …) auf; beide Schlüssel liegen in Bucket 4. Der ConcurrentHashMap-Code ist in Java 21 und 25 in diesen Punkten gleich.

  1. Die HashMap verliert rund 22 % der Einträge, ohne Fehlermeldung. Die ConcurrentHashMap hat alle 100 000.
  2. get und dann put ist check-then-act: zwei einzelne atomare Aufrufe, aber nicht zusammen atomar. 60 % der Zählungen fehlen. merge macht Lesen und Schreiben in einem Schritt unter dem Bucket-Lock.
  3. null als Wert oder Schlüssel wirft sofort NullPointerException.
  4. Die HashMap wirft ConcurrentModificationException. Der CHM-Iterator ist weakly consistent: kein Fehler. Er hat 5 von 8 Schlüsseln gesehen, also einige neue, aber nicht alle.
  5. Ohne Konkurrenz sind size() und mappingCount() gleich und genau.
  6. 8 Threads rufen 8000 Mal computeIfAbsent auf. Die Funktion läuft trotzdem nur einmal. Gut für einen Cache, der teure Werte nur einmal lädt.
  7. Reflection: Das Resize kommt schon beim 12. Eintrag (Grösse ≥ sizeCtl), bei der HashMap erst beim 13. new ConcurrentHashMap<>(16) ergibt eine Tabelle mit 32 Buckets, weil der Konstruktor 16 / 0.75 + 1 rechnet und aufrundet.
  8. Ein computeIfAbsent in einem anderen auf denselben Bucket wirft IllegalStateException: Recursive update.

4. Details, die Interviewer fragen

  1. Keine Segments mehr: Bis Java 7 bestand CHM aus 16 Segments, also 16 kleinen Hash-Tabellen mit je einem ReentrantLock. Seit Java 8 gibt es nur noch ein Array mit CAS und einem Lock pro Bucket. Die Klasse Segment existiert nur noch für die Serialisierung.
  2. concurrencyLevel: Der dritte Konstruktor-Parameter ist seit Java 8 nur noch ein Grössenhinweis. Er legt keine Lock-Anzahl mehr fest.
  3. CAS: Compare-and-Swap setzt einen Wert nur, wenn der alte Wert noch stimmt. CHM nutzt CAS für leere Buckets, für sizeCtl und für den Zähler.
  4. Bucket-Lock: Der Lock ist ein synchronized auf dem ersten Node des Buckets. Es gibt kein eigenes Lock-Objekt. Bei guter Hash-Verteilung kollidieren zwei Schreiber fast nie.
  5. Lock-freies Lesen: get, containsKey und Iteratoren sperren nie. val und next im Node sind volatile. Ein Lesen kann also parallel zu einem Schreiben laufen und sieht den alten oder den neuen Wert.
  6. Happens-before: Laut API-Doku happens-before ein put jedem get, das diesen Wert liest. Was ein Thread vor dem put geschrieben hat, sieht der Leser also auch.
  7. Paralleles Resize: Ein Resize verdoppelt das Array. Jeder schreibende Thread kann helfen. Er nimmt sich einen Block von Buckets (mindestens 16), kopiert sie und setzt dort ForwardingNodes.
  8. size() und CounterCells: Der Zähler ist wie ein LongAdder aufgebaut: baseCount plus ein Array von CounterCells. size() summiert alles ohne Lock. Bei laufenden Updates ist das Ergebnis nur ein Schätzwert.
  9. mappingCount(): gibt die Grösse als long zurück. Die API-Doku empfiehlt es statt size(), weil eine CHM mehr als Integer.MAX_VALUE Einträge haben kann.
  10. compute-Methoden: compute, computeIfAbsent, computeIfPresent und merge sind pro Schlüssel atomar. Die Funktion läuft, während der Bucket gesperrt ist. Andere Schreiber auf denselben Bucket warten so lange.
  11. Regeln für die Funktion: Laut API-Doku soll sie kurz und einfach sein. Sie darf die Map nicht ändern. Seit Java 9 erkennt CHM rekursive Updates oft und wirft IllegalStateException. In Java 8 konnte das in einer Endlosschleife enden (JDK-8062841).
  12. Atomare Einzelmethoden: putIfAbsent, remove(key, value) und replace(key, old, new) kommen aus ConcurrentMap. Sie ersetzen check-then-act-Code wie if (!containsKey) put.
  13. Weakly consistent Iteratoren: Sie werfen nie ConcurrentModificationException. Sie zeigen den Stand zu einem Zeitpunkt bei oder nach ihrer Erstellung. Änderungen danach sieht man vielleicht, vielleicht nicht.
  14. null-Regeln: Weder Schlüssel noch Wert darf null sein. So ist get() == null eindeutig: Der Schlüssel fehlt. In einer geteilten Map könnte man das sonst nicht atomar von „Wert ist null“ unterscheiden.
  15. Bulk-Operationen: forEach, search und reduce mit einem parallelismThreshold laufen parallel im ForkJoinPool.commonPool(). Sie sehen ebenfalls nur einen weakly consistent Stand.
  16. Set-Variante: ConcurrentHashMap.newKeySet() gibt ein thread-sicheres Set. Es gibt keine eigene Klasse ConcurrentHashSet.

5. Vergleich

  • ConcurrentHashMap: CAS und ein Lock pro Bucket, Lesen ohne Lock. Kein null. Iteratoren weakly consistent. Erste Wahl für geteilte Maps.
  • Hashtable: alt (Java 1.0). Jede Methode ist synchronized auf dem ganzen Objekt. Auch Lesen sperrt. Kein null. Iteratoren fail-fast. Heute nicht mehr nutzen.
  • Collections.synchronizedMap(map): ein Wrapper mit einem Lock für alle Methoden. null geht, wenn die innere Map es erlaubt. Beim Iterieren muss man selbst synchronized (map) schreiben, sonst droht ConcurrentModificationException.
  • HashMap: nicht thread-sicher, schnellste Wahl für einen Thread. Details auf der Seite HashMap.
  • ConcurrentSkipListMap: thread-sicher und sortiert, lock-frei, O(log n). Die sortierte Alternative, wie TreeMap für Threads.
  • Map.copyOf / unveränderliche Map: ohne Lock thread-sicher, wenn sich die Daten nie ändern. Für Konfiguration oft die beste Wahl.

6. In der Produktion

  1. Falsche Zähler trotz CHM: map.put(k, map.get(k) + 1) verliert Updates (im Beispiel 60 %). Lösung: merge(k, 1, Integer::sum) oder computeIfAbsent(k, x -> new LongAdder()).increment().
  2. Langsame oder blockierte Threads durch teure compute-Funktion: Ein Remote-Call in computeIfAbsent hält den Bucket-Lock. Andere Schreiber auf diesen Bucket warten. Lösung: Funktion kurz halten oder einen Cache wie Caffeine nutzen, der Laden ausserhalb sperrt.
  3. IllegalStateException: Recursive update: Eine compute-Funktion ändert dieselbe Map, z. B. rekursives Memoisieren. Lösung: Wert ausserhalb berechnen, dann putIfAbsent.
  4. NullPointerException nach Wechsel von HashMap: Bestehender Code speichert null-Werte. Lösung: Optional oder ein eigenes Platzhalter-Objekt, oder den Eintrag weglassen.
  5. Memory Leak durch unbegrenzten Cache: Eine statische CHM als Cache wächst ohne Grenze. Lösung: Caffeine mit Grösse und Ablaufzeit.
  6. Geschäftslogik über zwei Einträge: CHM ist nur pro Schlüssel atomar. Eine Überweisung von Konto A nach B braucht einen eigenen Lock oder eine Transaktion.

7. Diagnose: Werkzeuge und Befehle

  • jcmd <pid> Thread.print: Viele Threads BLOCKED in ConcurrentHashMap.computeIfAbsent oder putVal zeigen eine langsame compute-Funktion oder einen heissen Schlüssel.
  • JFR: Event jdk.JavaMonitorEnter zeigt Wartezeit auf Bucket-Locks, denn sie sind synchronized.
  • jcmd <pid> GC.class_histogram: viele ConcurrentHashMap$Node-Objekte deuten auf einen wachsenden Cache.
  • Heap Dump mit Eclipse MAT: findet die grösste CHM und wer sie hält.
  • async-profiler (-e lock oder CPU): zeigt Contention und heisse Methoden wie transfer beim Resize.
  • jcstress: ein OpenJDK-Werkzeug, das eigenen nebenläufigen Code auf Races testet.

8. Senior-Punkte

  1. Thread-sichere Map heisst nicht thread-sicherer Code. Jede einzelne Methode ist atomar, eine Folge von Aufrufen nicht. Darum merge, compute und putIfAbsent statt check-then-act.
  2. compute-Funktionen sind kritische Abschnitte. Sie halten einen Lock. Darum kein I/O, keine Remote-Calls, keine Änderung derselben Map.
  3. size() ist ein Schätzwert unter Last. Keine Logik wie „wenn size < 100, dann put“ darauf bauen. Dafür braucht es eine eigene atomare Grenze.
  4. Ein Cache ist mehr als eine CHM. Er braucht Grösse, Ablaufzeit und Schutz gegen gleichzeitiges Laden. Caffeine baut intern auf CHM auf und liefert das.
  5. Heisse Schlüssel skalieren nicht. Schreiben viele Threads auf denselben Schlüssel, warten sie am selben Bucket. Lösung: LongAdder als Wert oder Last aufteilen.
  6. Grösse vorher setzen spart Resizes bei bekanntem Volumen. Achtung: new ConcurrentHashMap<>(n) rechnet anders als new HashMap<>(n) und reserviert mehr.

9. Aus dem Projekt

„Für einen Lookup-Cache, den viele Request-Threads teilen, nutze ich ConcurrentHashMap.computeIfAbsent mit kurzer Ladefunktion, für Zähler merge oder LongAdder.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „ConcurrentHashMap hat 16 Segments mit je einem Lock.“ → Veraltet. Das war bis Java 7. Seit Java 8: CAS plus ein Lock pro Bucket.
  • „Mit ConcurrentHashMap ist mein Code automatisch thread-sicher.“ → Falsch. Nur einzelne Methoden sind atomar. get plus put verliert Updates.
  • „get() sperrt die Map kurz.“ → Falsch. Lesen nimmt nie einen Lock. Es nutzt volatile-Zugriffe.
  • „size() ist immer genau.“ → Falsch. Bei laufenden Updates ist es ein Schätzwert.
  • „Der Iterator wirft eine ConcurrentModificationException.“ → Falsch. Er ist weakly consistent und wirft nie CME.
  • „Ein null-Wert ist erlaubt wie bei HashMap.“ → Falsch. Schlüssel und Werte dürfen nie null sein. Es kommt eine NullPointerException.
  • „Hashtable und synchronizedMap sind gleich gut.“ → Falsch. Beide haben einen Lock für alles, auch beim Lesen. CHM skaliert mit vielen Threads viel besser.
  • „In computeIfAbsent darf ich die Map weiter befüllen.“ → Falsch. Die Funktion darf die Map nicht ändern. Sonst IllegalStateException: Recursive update oder falsche Daten.

11. Fragen

Wie funktioniert ConcurrentHashMap intern?

Ein Array von Buckets wie bei der HashMap. Leere Buckets füllt sie per CAS, volle sperrt sie mit synchronized auf dem ersten Node. Lesen braucht keinen Lock.

Was passiert bei put()?

Hash berechnen, Bucket finden. Leer: CAS. ForwardingNode: beim Resize helfen. Sonst Kopf-Node sperren, nachprüfen, ersetzen oder anhängen. Danach Zähler erhöhen und eventuell Resize.

Warum braucht get() keinen Lock?

Die Tabelle und die Felder val und next sind volatile. Ein Leser sieht immer einen fertig geschriebenen Node, den alten oder den neuen Wert.

Was sind Segments, und gibt es sie noch?

Bis Java 7 war CHM in 16 Segments mit je einem Lock geteilt. Seit Java 8 gibt es sie nicht mehr. Die Klasse Segment ist nur noch für die Serialisierung da.

Was ist CAS, und wo nutzt CHM es?

Compare-and-Swap setzt einen Wert nur, wenn der alte Wert noch stimmt, atomar in der CPU. CHM nutzt es für leere Buckets, sizeCtl und den Zähler.

Was wird beim Schreiben genau gesperrt?

Nur der erste Node des betroffenen Buckets, mit synchronized. Alle anderen Buckets bleiben frei.

Wie läuft ein Resize ab?

Eine doppelt so grosse nextTable entsteht. Threads kopieren Blöcke von Buckets und setzen ForwardingNodes. Andere Schreiber helfen mit, Leser folgen der ForwardingNode.

Wann macht CHM ein Resize?

Wenn die Grösse sizeCtl erreicht, normal 0.75 × Kapazität. Bei 16 Buckets schon beim 12. Eintrag.

Wie zählt CHM seine Grösse?

Mit baseCount und einem Array von CounterCells, wie LongAdder. Bei Konkurrenz zählt jeder Thread in einer eigenen Zelle. size() summiert alles.

Ist size() genau?

Nur ohne gleichzeitige Updates. Unter Last ist es ein Schätzwert.

size() oder mappingCount()?

mappingCount(). Es gibt einen long zurück, weil eine CHM mehr als Integer.MAX_VALUE Einträge haben kann.

Warum erlaubt CHM kein null?

Damit get() == null eindeutig „Schlüssel fehlt“ heisst. In einer geteilten Map kann man sonst nicht atomar zwischen fehlend und null unterscheiden.

Was heisst weakly consistent?

Der Iterator wirft nie ConcurrentModificationException. Er zeigt den Stand bei oder nach seiner Erstellung und sieht spätere Änderungen vielleicht.

Ist map.put(k, map.get(k) + 1) auf einer CHM sicher?

Nein. Das ist check-then-act aus zwei Aufrufen, Updates gehen verloren. Richtig: merge(k, 1, Integer::sum).

Was garantieren compute und merge?

Sie sind pro Schlüssel atomar. Die Funktion läuft unter dem Bucket-Lock Bei computeIfAbsent läuft sie nur, wenn der Schlüssel fehlt, und nur in einem Thread.

Welche Regeln gelten für die Funktion in computeIfAbsent?

Kurz und einfach, kein I/O, und sie darf die Map nicht ändern. Sonst blockiert sie andere Schreiber oder wirft IllegalStateException: Recursive update.

Was machen putIfAbsent, replace und remove(key, value)?

Atomare Bedingungs-Operationen aus ConcurrentMap. Sie ersetzen check-then-act-Code wie if (!containsKey) put.

CHM vs Hashtable?

Hashtable sperrt das ganze Objekt bei jeder Methode, auch beim Lesen. CHM sperrt nur einen Bucket und liest ohne Lock. Beide verbieten null.

CHM vs Collections.synchronizedMap?

synchronizedMap hat einen Lock für alles und erlaubt null, wenn die innere Map es tut. Beim Iterieren muss man selbst synchronisieren.

Wird ein Bucket in CHM auch zum Baum?

Ja, wenn die Kette über 8 Nodes wächst und die Tabelle mindestens 64 Buckets hat, wie in der HashMap. Der Kopf ist dann ein TreeBin mit Hash −2.

Was macht der Parameter concurrencyLevel heute?

Nur noch ein Grössenhinweis für die Anfangskapazität. Er legt keine Anzahl Locks mehr fest.

Wie bekomme ich ein thread-sicheres Set auf CHM-Basis?

Mit ConcurrentHashMap.newKeySet(). Eine Klasse ConcurrentHashSet gibt es nicht.

Was ist eine sortierte Alternative für mehrere Threads?

ConcurrentSkipListMap. Thread-sicher, sortiert, O(log n).

Wann reicht CHM nicht?

Wenn eine Operation mehrere Schlüssel atomar ändern muss. Oder wenn ein Cache Grenze und Ablaufzeit braucht, dann Caffeine.

Szenario: Ein Zähler pro Kunde in einer ConcurrentHashMap zeigt unter Last zu kleine Werte. Warum?

Der Code macht vermutlich get und dann put, das ist nicht atomar. Lösung: merge(k, 1, Long::sum) oder ein LongAdder pro Schlüssel über computeIfAbsent.

Szenario: Viele Request-Threads hängen BLOCKED in ConcurrentHashMap.computeIfAbsent. Was ist los?

Die Ladefunktion ist langsam, z. B. ein Datenbank- oder HTTP-Call, und hält den Bucket-Lock. Lösung: Laden ausserhalb oder einen Cache wie Caffeine mit asynchronem Laden.

Szenario: Nach dem Wechsel von HashMap auf ConcurrentHashMap gibt es NullPointerExceptions. Warum?

Der Code speichert null-Werte oder fragt mit null-Schlüsseln. CHM verbietet beides. Lösung: Eintrag weglassen, Optional oder ein Platzhalter-Objekt.
