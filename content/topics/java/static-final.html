static, final, finally, finalize

Java · Tier 2 · Quellen: JLS 21 (§8.3.1.1 static Fields, §8.3.1.2 final Fields, §4.12.4 final Variables, §13.1 und §13.4.9 Binary Compatibility, §14.20.2 try-finally, §12.4 Initialization), Java SE 25 API-Doku (Object.finalize, java.lang.ref.Cleaner), JEP 421 (Deprecate Finalization for Removal, Java 18)

Kern: Die vier Wörter klingen ähnlich, haben aber nichts miteinander zu tun. static heisst „gehört zur Klasse, nicht zum Objekt“. final heisst „nur einmal zuweisbar / nicht überschreibbar / nicht erweiterbar“. finally ist ein Block, der nach try fast immer läuft. finalize() ist eine alte Aufräum-Methode für den GC, seit Java 9 deprecated und seit Java 18 zur Entfernung markiert.

1. Wo sitzen die vier Begriffe?

  1. static sitzt an der Klasse. Es gibt das Feld genau einmal pro geladener Klasse. Beispiel: ein Zähler für alle Objekte.
  2. final sitzt an Feldern, Variablen, Methoden und Klassen. Beispiel: final class String, private final int id.
  3. finally sitzt in einer Methode nach try. Beispiel: einen Lock freigeben.
  4. finalize() gehört zum GC. Ein eigener Thread ruft sie irgendwann vor dem Löschen eines Objekts auf. Heute nicht mehr nutzen.

2. Die Reise einer Klasse vom Laden bis zum Aufräumen (die Geschichte zum Merken)

  1. Klasse laden und initialisieren: Beim ersten aktiven Zugriff führt die JVM alle static-Feld-Initialisierer und static-Blöcke aus. In Quelltext-Reihenfolge, genau einmal.
  2. Objekt bauen: Bei jedem new laufen Instanz-Initialisierer, dann der Konstruktor. final-Felder müssen am Ende des Konstruktors gesetzt sein.
  3. Arbeiten und aufräumen: Eine Methode nutzt try. Der finally-Block läuft danach: bei normalem Ende, bei return und bei Exception.
  4. Aufräumen durch den GC: Ist das Objekt unerreichbar, kann der GC es löschen. Hat es finalize(), kommt es zuerst in eine Warteschlange. Ein eigener Finalizer-Thread ruft die Methode irgendwann auf. Das Objekt lebt dadurch mindestens einen GC-Zyklus länger.

Echte Ausgabe, Oracle JDK 17.0.3. javac warnt bei finalize („deprecated“) und bei p.who() („static method should be qualified by type name“). Ob und wann finalize läuft, ist nicht garantiert. Ab Java 18 ist finalize „for removal“ markiert; mit --finalization=disabled läuft es gar nicht (Erwartetes Ergebnis laut JEP 421, nicht ausgeführt).

  1. Static-Initialisierung läuft einmal, vor main. Instanz-Initialisierung läuft bei jedem new, vor dem Konstruktor-Rumpf.
  2. Statische Methoden werden nicht überschrieben, sondern verdeckt (hiding). Der Compiler wählt nach dem deklarierten Typ Parent.
  3. final fixiert nur die Referenz. Der Inhalt der Liste bleibt änderbar.
  4. Der Rückgabewert wird vor dem finally gemerkt. Das Ändern von x im finally ändert das Ergebnis nicht.
  5. Ein return im finally verschluckt die Exception. Sie verschwindet ohne Spur.
  6. finalize() läuft in einem eigenen Thread namens Finalizer, nicht im Aufrufer.
  7. VERSION ist eine Compile-Time-Konstante. javac kopiert "v1" direkt in SfDemo.class. Nach Änderung nur von Const sieht SfDemo weiter „v1“. START ist keine Konstante und wird zur Laufzeit gelesen.
  8. System.exit beendet die JVM sofort. Shutdown-Hooks laufen, finally nicht.

4. Details, die Interviewer fragen

  1. static Feld: eine Kopie pro Klasse und ClassLoader. Alle Objekte teilen sie. Lebt so lange wie die Klasse.
  2. static Methode: braucht kein Objekt, hat kein this. Kann nur über ein Objekt auf Instanz-Felder zugreifen. Wird nicht überschrieben, nur verdeckt.
  3. static-Block: Code zur Klassen-Initialisierung. Wirft er eine Exception, ist die Klasse kaputt: erst ExceptionInInitializerError, danach NoClassDefFoundError bei jedem Zugriff.
  4. static nested class: Eine statische innere Klasse hat keinen Verweis auf das äussere Objekt. Eine nicht-statische innere Klasse hat einen versteckten Verweis und kann ein Memory Leak verursachen.
  5. static import: import static java.lang.Math.max; erlaubt max(a, b) ohne Klassennamen.
  6. final Variable: nur einmal zuweisbar. Effectively final (Java 8) heisst: nie neu zugewiesen, auch ohne final. Lambdas und anonyme Klassen dürfen nur solche lokalen Variablen nutzen.
  7. final Feld: muss bis zum Ende des Konstruktors gesetzt sein (blank final ist erlaubt). Das JMM garantiert danach Sichtbarkeit für alle Threads.
  8. final Methode: kann nicht überschrieben werden. Schützt Verhalten, z. B. in Template-Methoden.
  9. final Klasse: kann nicht erweitert werden. Beispiele: String, Integer, Records. sealed (Java 17) ist der Mittelweg: nur erlaubte Unterklassen.
  10. Compile-Time-Konstante: static final mit primitivem Typ oder String und konstantem Ausdruck. javac kopiert den Wert in jede nutzende Klasse. Eine Änderung braucht Neukompilierung aller Nutzer.
  11. finally läuft nicht: bei System.exit, bei Runtime.halt, bei Absturz der JVM, bei Kill des Prozesses, oder wenn der Thread ewig im try hängt.
  12. try-with-resources: schliesst Ressourcen automatisch. Exceptions aus close() werden als suppressed an die Haupt-Exception gehängt, nicht verschluckt.
  13. finalize-Probleme: unbestimmter Zeitpunkt, vielleicht nie, verlängert die Lebenszeit von Objekten, kann Objekte „wiederbeleben“, Exceptions darin werden ignoriert, Sicherheitsrisiko (Finalizer-Angriff). Ersatz: AutoCloseable + try-with-resources, als Sicherheitsnetz Cleaner.

5. Vergleich

  • static: Zugehörigkeit zur Klasse. Gegenteil: Instanz-Mitglied.
  • final: Unveränderbarkeit der Zuweisung, Schutz vor Überschreiben und Erben.
  • finally: garantiertes Aufräumen im normalen Ablauf. Moderner: try-with-resources.
  • finalize: unzuverlässiges Aufräumen durch den GC. Deprecated for removal.
  • Cleaner (Java 9): registriert eine Aufräum-Aktion für ein Objekt, ohne dessen Lebenszeit zu verlängern. Nur als Sicherheitsnetz.
  • volatile vs final: volatile für Felder, die sich ändern und sichtbar sein müssen. final für Felder, die sich nie ändern.

6. In der Produktion

  1. Statischer Zustand als globaler Cache: Eine static Map wächst ohne Grenze. Memory Leak. Bei Redeploys in App-Servern hält sie sogar den alten ClassLoader fest. Lösung: Cache-Bean mit Grösse und TTL.
  2. Statischer veränderlicher Zustand und Threads: static SimpleDateFormat ist nicht thread-sicher und liefert falsche Daten. Lösung: DateTimeFormatter (unveränderlich).
  3. Konstante geändert, Nutzer nicht neu gebaut: Ein Modul liest weiter den alten Wert. Lösung: alle abhängigen Module neu bauen, oder den Wert nicht als Compile-Time-Konstante deklarieren.
  4. Exception im static-Block: Beim Start fehlt eine Konfiguration. Danach überall NoClassDefFoundError, die echte Ursache steht nur im ersten Fehler. Lösung: im Log nach dem ersten ExceptionInInitializerError suchen; keine riskante Logik in static-Blöcke.
  5. Ressourcen-Leak mit finalize: Datei-Handles werden erst bei einem späten GC geschlossen. „Too many open files“. Lösung: try-with-resources.
  6. return in finally: Fehler verschwinden ohne Log. Lösung: kein return und kein throw im finally; javac-Warnung -Xlint:finally beachten.
  7. static und Spring: Spring injiziert nicht in static-Felder. Lösung: Instanz-Felder in einer Bean, Konstruktor-Injektion.

7. Diagnose: Werkzeuge und Befehle

  • javac -Xlint:all: Warnungen zu finally, static-Zugriff über Objekte und deprecated finalize.
  • javap -c: zeigt, ob eine Konstante eingebettet (ldc "v1") oder gelesen (getstatic) wird.
  • jdeprscan: findet Nutzung von deprecated APIs wie finalize in JARs.
  • JFR: Event jdk.FinalizerStatistics (seit Java 18) zeigt Klassen mit Finalizern.
  • jcmd <pid> GC.finalizer_info: zeigt wartende Objekte in der Finalizer-Queue.
  • java --finalization=disabled (ab Java 18): testet, ob die Anwendung ohne Finalizer funktioniert.
  • Heap Dump mit MAT: grosse static-Collections als GC Roots finden.

8. Senior-Punkte

  1. Statischer veränderlicher Zustand ist globaler Zustand. Er erschwert Tests, Threads und Redeploys. Nur für Konstanten und reine Hilfsfunktionen.
  2. final als Standard für Felder. Das dokumentiert Absicht, hilft dem JMM und verhindert Fehler.
  3. Vererbung bewusst erlauben. Klassen ohne geplante Erweiterung final machen oder sealed nutzen.
  4. Aufräumen ist deterministisch, nicht GC-abhängig: try-with-resources. Cleaner nur als Netz.
  5. Öffentliche Konstanten sind API. Ihre Änderung kann Binärkompatibilität brechen. Für Werte, die sich ändern können, eine Methode oder Konfiguration.
  6. Finalization verschwindet. Bei Upgrades mit --finalization=disabled testen und Bibliotheken prüfen.

10. Fallen

  • „Statische Methoden kann man überschreiben.“ → Falsch. Man kann sie nur verdecken. Der Compiler wählt nach dem deklarierten Typ.
  • „final List ist unveränderlich.“ → Falsch. Nur die Referenz ist fest. Der Inhalt bleibt änderbar.
  • „finally läuft immer.“ → Fast. Nicht bei System.exit, JVM-Absturz, Kill oder Endlosschleife im try.
  • „finalize ist wie ein Destruktor in C++.“ → Falsch. Zeitpunkt unbestimmt, vielleicht nie. Deprecated for removal.
  • „Eine geänderte static final String-Konstante wirkt sofort überall.“ → Falsch. Sie ist in Nutzer-Klassen eingebettet. Neukompilieren nötig.
  • „Ein return im finally ist harmlos.“ → Falsch. Es verschluckt Exceptions und überschreibt Rückgabewerte.

11. Fragen

Was ist der Unterschied zwischen final, finally und finalize?

final: nicht änderbar, überschreibbar oder erweiterbar. finally: Block nach try, der fast immer läuft. finalize: alte GC-Aufräum-Methode, deprecated.

Was bedeutet static?

Das Mitglied gehört zur Klasse, nicht zum Objekt. Es existiert einmal pro Klasse und ClassLoader.

Kann eine statische Methode auf Instanz-Felder zugreifen?

Nicht direkt, sie hat kein this. Nur über eine Objekt-Referenz.

Kann man statische Methoden überschreiben?

Nein. Eine gleichnamige statische Methode in der Unterklasse verdeckt sie (hiding). Der deklarierte Typ entscheidet.

Wann läuft ein static-Block?

Einmal bei der Initialisierung der Klasse, beim ersten aktiven Zugriff. In Quelltext-Reihenfolge mit den static-Feldern.

Was passiert bei einer Exception im static-Block?

Erst ExceptionInInitializerError, danach bei jedem Zugriff NoClassDefFoundError. Die Klasse bleibt unbenutzbar.

Statische vs nicht-statische innere Klasse?

Die nicht-statische hält einen Verweis auf das äussere Objekt. Die statische nicht. Statisch ist der Standard, ausser man braucht das äussere Objekt.

Was bedeutet final bei Variable, Methode, Klasse?

Variable: einmal zuweisbar. Methode: nicht überschreibbar. Klasse: nicht erweiterbar.

Was ist effectively final?

Eine lokale Variable, die nie neu zugewiesen wird, auch ohne final. Lambdas dürfen nur solche Variablen nutzen.

Warum dürfen Lambdas nur effectively final Variablen nutzen?

Lambdas kopieren den Wert. Wäre die Variable änderbar, wären Kopie und Original inkonsistent, besonders über Threads.

Was ist ein blank final?

Ein final Feld ohne Initialisierer. Jeder Konstruktor muss es genau einmal setzen.

Was garantiert final für Threads?

Nach Ende des Konstruktors sehen alle Threads die final-Felder korrekt, wenn this nicht entkommen ist.

Was ist eine Compile-Time-Konstante?

Ein static final Feld mit primitivem Typ oder String und konstantem Ausdruck. javac kopiert den Wert in jede nutzende Klasse.

Wann läuft finally nicht?

Bei System.exit, Runtime.halt, JVM-Absturz, Kill des Prozesses oder wenn der try-Block nie endet.

Was passiert bei return im try und Änderung im finally?

Der Rückgabewert wird vor finally gemerkt. Eine Änderung der Variable ändert ihn nicht. Ein return im finally würde ihn ersetzen.

Warum ist return im finally schlecht?

Es überschreibt den Rückgabewert und verschluckt jede Exception aus try oder catch.

finally oder try-with-resources?

try-with-resources für alles mit AutoCloseable. Kürzer, und Exceptions aus close werden als suppressed angehängt.

Warum ist finalize deprecated?

Unbestimmter Zeitpunkt, vielleicht nie, verlängert Objekt-Lebenszeit, kostet GC-Leistung, Sicherheitsrisiken. Seit Java 9 deprecated, seit Java 18 for removal.

Was ersetzt finalize?

AutoCloseable mit try-with-resources. Als Sicherheitsnetz java.lang.ref.Cleaner.

Welcher Thread ruft finalize auf?

Ein eigener JVM-Thread namens Finalizer. Ist er langsam, staut sich die Queue und der Speicher wächst.

Ist SimpleDateFormat als static Feld sicher?

Nein, es ist nicht thread-sicher. Besser DateTimeFormatter, der unveränderlich ist.

Szenario: Nach einem Deployment zeigt ein Service die alte Versionsnummer, obwohl die Konstante geändert wurde. Warum?

Die Konstante ist eine Compile-Time-Konstante und in den Nutzer-Klassen eingebettet. Nur die Library wurde neu gebaut. Lösung: alle Nutzer neu bauen oder Wert zur Laufzeit lesen.

Szenario: Im Log steht überall NoClassDefFoundError für eine Klasse, die im JAR ist. Was prüfen Sie?

Den ersten Fehler: ExceptionInInitializerError aus einem static-Block, z. B. fehlende Konfiguration. Ursache beheben, keine riskante Logik in static-Blöcken.

Szenario: Ein Service bekommt „Too many open files“, obwohl Klassen finalize() zum Schliessen haben. Was ist los?

finalize läuft spät oder nie. Die Handles bleiben offen. Lösung: AutoCloseable und try-with-resources, offene Handles mit lsof prüfen.
