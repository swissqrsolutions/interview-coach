IO vs NIO: Streams, Buffers, Channels, Files API

Java · Tier 3 · Quellen: Java SE 25 API-Doku (java.io, java.nio ByteBuffer, java.nio.channels FileChannel/Selector, java.nio.file.Files/Path), JEP 400 (UTF-8 by Default, Java 18), JEP 444 (Virtual Threads)

Kern: java.io ist die klassische, stream-orientierte und blockierende Ein-/Ausgabe: Man liest Byte für Byte oder Zeichen für Zeichen aus einem InputStream. java.nio ist buffer-orientiert: Daten gehen über Channels in Buffers, und Netzwerk-Channels können nicht-blockierend mit einem Selector arbeiten. NIO.2 (java.nio.file) ist die moderne API für Dateien: Path und Files.

1. Wo sitzen IO und NIO?

  1. java.io: Streams für Bytes (InputStream/OutputStream) und Reader/Writer für Zeichen. Man stapelt sie als Decorator, z. B. new BufferedReader(new InputStreamReader(in, UTF_8)).
  2. java.nio: Ein Channel ist eine Verbindung zu Datei oder Socket. Ein ByteBuffer ist ein Speicherblock mit Positionszeigern. Ein Selector überwacht viele Channels mit einem Thread.
  3. NIO.2: Path ersetzt File. Files bietet fertige Methoden: lesen, schreiben, kopieren, durchsuchen.
  4. Native Ebene: Am Ende werden alle zu System Calls. NIO nutzt dabei zusätzlich Mechanismen wie epoll (Linux) oder Zero-Copy.

2. Die Reise einer Netzwerk-Anfrage durch einen Selector (die Geschichte zum Merken)

  1. Registrieren: Der Server setzt jeden SocketChannel auf configureBlocking(false) und registriert ihn am Selector, z. B. für OP_READ.
  2. Warten: Ein Thread ruft selector.select(). Das Betriebssystem meldet, welche Verbindungen Daten haben. Auf Linux nutzt die JVM dafür epoll.
  3. Verarbeiten: Der Thread liest nur aus bereiten Channels in einen ByteBuffer. Er blockiert nie auf einer langsamen Verbindung.
  4. Antworten: Er schreibt die Antwort aus einem Buffer zurück. Ist der Socket voll, registriert er OP_WRITE und macht später weiter.
  5. Ergebnis: Wenige Threads bedienen tausende Verbindungen. Das ist die Basis von Netty, und damit von Spring WebFlux, gRPC-Java und Kafka-Clients.

4. Details, die Interviewer fragen

  1. Byte- vs Zeichen-Streams: InputStream/OutputStream für Bytes. Reader/Writer für Text; sie brauchen einen Charset. InputStreamReader ist die Brücke.
  2. Decorator-Muster: BufferedInputStream, DataInputStream, GZIPInputStream umhüllen einen anderen Stream und fügen Funktion hinzu. Schliessen des äusseren schliesst den inneren.
  3. Blockierend: read() wartet, bis Daten da sind. Klassisch heisst das: ein Thread pro Verbindung.
  4. ByteBuffer: allocate (im Heap) oder allocateDirect (ausserhalb des Heaps). Direct Buffers spart das Kopieren bei I/O, sind aber teurer anzulegen. Grenze: -XX:MaxDirectMemorySize.
  5. Channels: FileChannel (Dateien, transferTo, map für Memory-Mapped Files, lock), SocketChannel, ServerSocketChannel, DatagramChannel. Channels sind bidirektional möglich, Streams nur eine Richtung.
  6. Selector: nur für Netzwerk-Channels. FileChannel ist nicht selektierbar.
  7. Memory-Mapped Files: FileChannel.map blendet eine Datei in den Speicher ein. Sehr schnell für grosse Dateien. Der Speicher wird erst freigegeben, wenn der GC den Buffer einsammelt.
  8. NIO.2-Highlights: Files.readString/writeString (Java 11), Files.lines, Files.walk, Files.copy/move mit Optionen wie ATOMIC_MOVE, Files.mismatch (Java 12), WatchService für Änderungen, Datei-Attribute und Rechte.
  9. Standard-Zeichensatz: Files-Methoden nutzen ohne Angabe immer UTF-8. Ältere APIs wie FileReader und new String(bytes) nutzten vor Java 18 den Plattform-Zeichensatz. Seit Java 18 ist der Standard überall UTF-8 (JEP 400).
  10. Atomares Schreiben: In eine temporäre Datei schreiben, dann Files.move(tmp, ziel, ATOMIC_MOVE). Leser sehen nie eine halbe Datei.
  11. Virtual Threads (Java 21): Blockierendes java.io mit Virtual Threads skaliert ähnlich wie NIO, mit einfachem Code. Die JVM parkt den Virtual Thread statt den OS-Thread zu blockieren.

5. Vergleich

  • java.io: einfach, blockierend, stream-orientiert. Gut für Dateien und wenige Verbindungen.
  • java.nio (Channels, Buffers, Selector): buffer-orientiert, nicht-blockierend im Netzwerk. Komplex; meist nutzt man es über Netty.
  • NIO.2 (Path, Files): der heutige Standard für Dateien. Klare Exceptions, Streams, Attribute.
  • AsynchronousFileChannel / AsynchronousSocketChannel: Callback- oder Future-basiert. Selten direkt genutzt.
  • Virtual Threads + java.io: einfacher blockierender Code mit hoher Parallelität. Oft die einfachste Wahl ab Java 21.
  • File vs Path: File ist alt, mit schwachen Fehlern. Path ist modern. Umwandeln mit file.toPath().

6. In der Produktion

  1. Too many open files: Streams, Files.lines oder Files.walk ohne try-with-resources. Lösung: immer try-with-resources; ulimit -n und offene Handles prüfen.
  2. Kaputte Umlaute: Text ohne Zeichensatz gelesen, auf dem Server ist der Standard ein anderer als lokal. Lösung: Charset immer explizit, ab Java 18 ist UTF-8 Standard.
  3. Langsamer Import: Ungepuffertes Lesen oder Schreiben. Lösung: Buffered-Klassen oder Files.newBufferedReader.
  4. OutOfMemoryError beim Einlesen: Files.readAllBytes auf einer GB-Datei. Lösung: streamen (Files.lines, InputStream in Blöcken).
  5. OOM: Direct buffer memory: Netty oder eigene Direct Buffers über dem Limit. Lösung: MaxDirectMemorySize passend setzen, Leaks suchen, Container-Limit inklusive Off-Heap planen.
  6. Halbe Dateien beim Konsumenten: Ein anderer Prozess liest, während man schreibt. Lösung: temporäre Datei plus atomares Move.
  7. Event-Loop blockiert: In Netty oder WebFlux läuft ein blockierender Aufruf (JDBC, Datei) im Event-Loop-Thread. Alle Verbindungen stehen. Lösung: blockierende Arbeit auf einen eigenen Pool.

7. Diagnose: Werkzeuge und Befehle

  • lsof -p <pid> oder ls /proc/<pid>/fd | wc -l: Anzahl offener Dateien und Sockets.
  • JFR-Events jdk.FileRead, jdk.FileWrite, jdk.SocketRead, jdk.SocketWrite: langsame I/O mit Stack Trace.
  • jcmd <pid> VM.native_memory summary (mit -XX:NativeMemoryTracking=summary): Direct-Buffer-Verbrauch.
  • JMX/Micrometer: BufferPoolMXBean zeigt direct- und mapped-Pools.
  • Thread Dump: viele Threads in socketRead0 zeigen blockierende Netzwerk-I/O ohne Timeout.
  • java -XshowSettings:properties -version: zeigt file.encoding und andere Standard-Einstellungen.

8. Senior-Punkte

  1. Für Dateien NIO.2, für Netzwerk ein Framework (Netty, HTTP-Client). Selbst geschriebene Selector-Loops lohnen sich selten.
  2. Charset immer explizit. Das spart die häufigsten Fehler beim Wechsel zwischen Windows, Linux und Container.
  3. Streamen statt laden. Grosse Dateien nie ganz in den Speicher.
  4. Jede Ressource hat einen Besitzer, der sie schliesst: try-with-resources.
  5. Virtual Threads ändern die Abwägung. Blockierender Code skaliert wieder; nicht-blockierend lohnt sich vor allem bei Streaming und Backpressure.
  6. Off-Heap-Speicher planen. Direct Buffers und Mapped Files zählen zum Container-Limit, nicht zum Heap.

10. Fallen

  • „NIO ist immer schneller als IO.“ → Falsch. Für einfaches Datei-Lesen sind gepuffertes IO und NIO ähnlich. Der Vorteil liegt bei vielen Verbindungen und Zero-Copy.
  • „FileChannel ist nicht-blockierend.“ → Falsch. Nur Netzwerk-Channels sind selektierbar.
  • „Nach put() kann ich sofort aus dem Buffer lesen.“ → Falsch. Erst flip().
  • „Files.lines muss man nicht schliessen.“ → Falsch. Der Stream hält die Datei offen.
  • „Ohne Charset-Angabe ist es immer UTF-8.“ → Erst seit Java 18 für alle APIs. Vorher galt bei FileReader und Co. der Plattform-Standard.
  • „Direct Buffers zählen zum Heap.“ → Falsch. Sie liegen ausserhalb, mit eigenem Limit.

11. Fragen

Was ist der Hauptunterschied zwischen IO und NIO?

IO ist stream-orientiert und blockierend. NIO ist buffer-orientiert, nutzt Channels und kann im Netzwerk mit einem Selector nicht-blockierend arbeiten.

Byte-Stream vs Character-Stream?

InputStream/OutputStream für Bytes. Reader/Writer für Text mit Zeichensatz. InputStreamReader verbindet beide.

Warum BufferedInputStream?

Ohne Puffer macht jedes read() einen System Call. Der Puffer liest grosse Blöcke und spart so viel Zeit.

Was ist ein Channel?

Eine Verbindung zu einer Datei oder einem Socket, über die man Buffers liest und schreibt.

Was sind position, limit und capacity?

position: nächste Stelle. limit: Ende der gültigen Daten. capacity: Grösse des Buffers.

Was macht flip()?

Es setzt limit auf die aktuelle position und position auf 0. So wechselt man vom Schreiben zum Lesen.

Heap Buffer vs Direct Buffer?

Heap Buffer liegt im Java-Heap. Direct Buffer liegt ausserhalb und spart Kopien bei I/O, ist aber teurer anzulegen und hat ein eigenes Limit.

Was ist ein Selector?

Ein Objekt, das viele nicht-blockierende Netzwerk-Channels überwacht. Ein Thread bedient so viele Verbindungen.

Kann man FileChannel mit einem Selector nutzen?

Nein. FileChannel ist nicht selektierbar und immer blockierend.

Was ist Zero-Copy?

Daten gehen im Kernel direkt von Datei zu Socket oder Datei, ohne in den Java-Heap kopiert zu werden. In Java: FileChannel.transferTo.

Was ist ein Memory-Mapped File?

Eine Datei, die per FileChannel.map in den Speicher eingeblendet ist. Sehr schneller Zugriff, Freigabe erst durch den GC.

Warum Path statt File?

Path und Files geben klare Exceptions, unterstützen Symlinks, Attribute und Streams. File liefert oft nur false ohne Grund.

Wie lesen Sie eine grosse Textdatei speicherschonend?

Mit Files.lines oder Files.newBufferedReader im try-with-resources, Zeile für Zeile.

Warum muss Files.lines geschlossen werden?

Der Stream hält einen offenen Datei-Handle. Ohne Schliessen gibt es ein Leak bis „Too many open files“.

Welcher Zeichensatz gilt ohne Angabe?

Files-Methoden: immer UTF-8. Andere APIs: vor Java 18 der Plattform-Standard, seit Java 18 UTF-8 (JEP 400).

Wie schreiben Sie eine Datei atomar?

In eine temporäre Datei im gleichen Verzeichnis schreiben, dann Files.move mit ATOMIC_MOVE.

Welche Frameworks nutzen NIO?

Netty, und damit Spring WebFlux, gRPC-Java, viele HTTP-Clients. Auch Tomcat nutzt NIO-Connectoren.

Brauche ich mit Virtual Threads noch NIO?

Für viele Fälle nicht direkt. Blockierender Code skaliert mit Virtual Threads. NIO bleibt die Basis darunter und für Streaming mit Backpressure.

Was beobachtet ein WatchService?

Änderungen in einem Verzeichnis: Erstellen, Ändern, Löschen von Dateien.

Szenario: Ein Service stirbt nach Tagen mit „Too many open files“. Wie gehen Sie vor?

Mit lsof die offenen Handles zählen und nach Typ ordnen. Code nach Streams, Files.lines, Files.walk ohne try-with-resources durchsuchen und schliessen.

Szenario: Lokal sind Umlaute korrekt, im Container kaputt. Was ist los?

Text wird ohne Charset gelesen oder geschrieben, und der Container hat einen anderen Standard. Lösung: Charset explizit, ab Java 18 ist UTF-8 Standard.

Szenario: Ein Pod wird OOM-gekillt, obwohl der Heap nur halb voll ist. Woran denken Sie?

An Off-Heap-Speicher: Direct Buffers (Netty), Mapped Files, Metaspace, Thread-Stacks. Mit Native Memory Tracking und BufferPoolMXBean prüfen, MaxDirectMemorySize und Container-Limit anpassen.
