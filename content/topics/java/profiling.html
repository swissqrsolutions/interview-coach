Profiling mit JFR und async-profiler

Kern: Profiling ist das Messen, welcher Code wie viel einer Ressource verbraucht: CPU, Wartezeit, Speicher oder Locks. Es verhindert, dass man den falschen Code optimiert. In Java sind die Standard-Werkzeuge JFR (in die JVM eingebaut, produktionstauglich) und async-profiler (externer Sampling-Profiler mit Flame Graphs).

Antwort-Muster

Frage: Wie finden Sie heraus, warum ein Java-Service langsam ist?

  1. Mechanismus: Ich nehme eine JFR-Aufnahme. Ein Sampling-Profiler liest in festen Abständen die Stacks, und gleiche Stacks ergeben die Hot Spots.
  2. Zahl: JFR hat laut JEP 328 höchstens 1 % Overhead mit Standard-Settings. Darum läuft es in Produktion.
  3. Trade-off: Ein CPU-Profil zeigt keine Wartezeit. Bei hoher Latenz brauche ich Lock-Events oder ein Wall-Clock-Profil.
  4. Produktion: Ich starte die Aufnahme mit jcmd JFR.start ohne Neustart. Nach dem Fix messe ich erneut.

1. Die Reise eines CPU-Samples

  1. Timer: Ein Sampling-Profiler misst nicht jede Methode. Er schaut in festen Abständen nach. JEP 518 nennt als Beispiel 20 ms.
  2. Anhalten: Der Sampler hält einen laufenden Thread kurz an, genau an der aktuellen Stelle.
  3. Stack lesen: Er liest den Aufruf-Stack, z. B. main → parsePrices → Long.parseLong.
  4. Event: Der Stack wird ein Event, bei JFR jdk.ExecutionSample. Es landet in einem Puffer.
  5. Zählen: Nach Tausenden Samples zählt das Tool gleiche Stacks. Häufige Stacks = viel CPU-Zeit.
  6. Flame Graph: Jeder Kasten ist eine Methode. Seine Breite ist der Anteil der Samples. Unten liegt main, oben die Methode, die gerade rechnet.
  7. Safepoint Bias: Liest ein Profiler Stacks nur an Safepoints (Stellen, an denen die JVM Threads sicher anhalten kann), sieht er nur diese Stellen. Heisse Schleifen dazwischen verschwinden. JFR und async-profiler vermeiden das.

2. Aufbau

  1. JFR (JDK Flight Recorder): ein Ereignis-Rekorder in der JVM. Er schreibt Events wie CPU-Samples, GC-Pausen und Lock-Wartezeiten in eine .jfr-Datei. Beispiel: -XX:StartFlightRecording.
  2. JMC (JDK Mission Control): die grafische Auswertung für .jfr-Dateien. Aktuell Version 9.1.2.
  3. jfr-Tool: die Kommandozeile im JDK: jfr summary, jfr print, ab Java 21 jfr view.
  4. async-profiler: ein Open-Source-Profiler, der als Agent in die JVM geladen wird. Er kombiniert Kernel-Stacks aus perf_events mit Java-Stacks aus AsyncGetCallTrace. Ausgabe: interaktiver Flame Graph.

3. Details, die Interviewer fragen

  1. JFR-Herkunft: JFR war früher ein kommerzielles Feature des Oracle JDK. Seit Java 11 ist es Open Source in OpenJDK (JEP 328). Das Ziel ist höchstens 1 % Overhead mit der Standard-Konfiguration.
  2. Zwei Konfigurationen: default.jfc ist für den Dauerbetrieb. profile.jfc hat mehr Details und etwas mehr Overhead. Man wählt mit settings=profile.
  3. Starten: Man startet beim Programmstart mit -XX:StartFlightRecording=.... Im laufenden Prozess nutzt man jcmd <pid> JFR.start, JFR.dump und JFR.stop.
  4. Dauer-Aufnahme: Eine Aufnahme mit maxage oder maxsize läuft als Ringpuffer. Bei einem Incident holt man mit JFR.dump die letzten Minuten.
  5. Wichtige Events: jdk.ExecutionSample steht für CPU. jdk.ObjectAllocationSample steht für Allokation. jdk.JavaMonitorEnter und jdk.ThreadPark stehen für Locks. Dazu kommen jdk.GarbageCollection, jdk.SocketRead und jdk.VirtualThreadPinned.
  6. Event Streaming (Java 14, JEP 349): Ein Programm kann JFR-Events live lesen, z. B. für Metriken. Man muss keine Datei auswerten.
  7. Flame Graph lesen: Die x-Achse ist keine Zeit. Sie zeigt den Anteil der Samples, alphabetisch sortiert. Die y-Achse ist die Stack-Tiefe. Gesucht sind breite Kästen ganz oben, die Plateaus.
  8. Safepoint Bias: Alte Profiler fragen Stacks über JVMTI nur an Safepoints ab. Sie zeigen dann Schleifenenden statt der echten heissen Zeile. async-profiler wirbt damit, dieses Problem nicht zu haben.
  9. Java 25, JEP 518 (Cooperative Sampling): JFR merkt sich beim Anhalten nur Programmzähler und Stack-Pointer. Den Stack liest es am nächsten Safepoint. Dabei rechnet es den Bias heraus. Das Ziel ist ein stabileres Verfahren ohne riskante Heuristiken.
  10. Java 25, JEP 509 (experimentell, nur Linux): Es gibt echtes CPU-Zeit-Profiling mit dem Kernel-CPU-Timer. Das neue Event heisst jdk.CPUTimeSample. Es ist standardmässig aus.
  11. Java 25, JEP 520: jdk.MethodTiming und jdk.MethodTrace zählen und messen ausgewählte Methoden. Man wählt sie per Filter, z. B. java.util.HashMap::resize.
  12. CPU und Wall Clock: Ein CPU-Profil zeigt nur rechnende Threads. Ein Wall-Clock-Profil (async-profiler -e wall) samplet alle Threads, auch schlafende und blockierte. Für Latenz-Fragen braucht man Wall Clock oder Lock-Events.
  13. Allokations-Profiling: async-profiler -e alloc samplet bei neuen TLABs und bei Allokationen ausserhalb. Es zählt nur echte Heap-Allokationen. Von Escape Analysis entfernte zählt es nicht.
  14. async-profiler-Modi: Es gibt cpu, alloc, lock, wall und nativemem für native Lecks. Dazu kommen Hardware-Zähler wie Cache Misses. Er zeigt auch native und Kernel-Frames sowie GC- und JIT-Threads.

4. Fallen

  • „Die x-Achse im Flame Graph ist die Zeit." → Falsch. Sie ist der Anteil der Samples, nicht die zeitliche Reihenfolge.
  • „Ein Thread ohne CPU-Samples ist kein Problem." → Falsch. Er kann blockiert sein. Im Beispiel wartete main 8.6 s auf einen Lock.
  • „JFR kostet in Produktion zu viel." → Falsch. Das Ziel von JEP 328 ist höchstens 1 % mit Standard-Settings.
  • „JFR ist kostenpflichtig." → Veraltet. Seit Java 11 Open Source in OpenJDK.
  • „Ein Profiler zeigt genau, wo die Zeit ist." → Nur ungefähr. Sampling ist Statistik, und Safepoint Bias kann Ergebnisse verschieben.
  • „Viele Allokationen sieht man im CPU-Profil." → Kaum. Man sieht GC-Arbeit. Die Quelle zeigt erst das Allokationsprofil.

5. Selbsttest

Warum?

Was ist Profiling?

Messen, welcher Code wie viel CPU, Wartezeit, Speicher oder Locks verbraucht. Damit optimiert man die richtige Stelle.

Warum zeigt ein CPU-Profil oft GC-Threads?

Weil die App viel allokiert und der GC viel arbeitet. Die Ursache findet das Allokationsprofil.

Warum lokal profilen nicht reicht?

Lokal fehlen echte Last, Daten und Nebenläufigkeit. Hot Spots in Produktion sind oft andere.

Was ist Safepoint Bias?

Ein Profiler, der Stacks nur an Safepoints liest, sieht nur diese Stellen. Heisse Code-Abschnitte dazwischen erscheinen falsch oder gar nicht.

Warum reicht ein CPU-Profil bei hoher Latenz nicht?

Es zeigt nur rechnende Threads. Wartende Threads haben keine CPU-Samples. Im Beispiel hatte main nur 3 Samples, wartete aber 8.6 s auf einen Lock.

Wie innen?

Was ist JFR?

Der JDK Flight Recorder: ein in die JVM eingebauter Ereignis-Rekorder mit sehr wenig Overhead. Er schreibt Events in eine .jfr-Datei.

Was ist ein Sampling-Profiler?

Er schaut in festen Abständen, wo jeder Thread gerade steht. Aus vielen Samples ergibt sich, wo die Zeit hingeht.

Wie vermeiden JFR und async-profiler Safepoint Bias?

Sie halten Threads an beliebiger Stelle an. async-profiler nutzt AsyncGetCallTrace und perf_events. JFR in Java 25 merkt sich die genaue Position und liest den Stack am nächsten Safepoint (JEP 518).

Wie lesen Sie einen Flame Graph?

Unten die Einstiegsmethode, oben die rechnende Methode. Die Breite ist der Anteil der Samples. Breite Kästen ganz oben sind die Hot Spots.

Was ist JFR Event Streaming?

Seit Java 14 kann ein Programm JFR-Events live konsumieren, z. B. für Monitoring. Keine Datei nötig.

Wie entsteht ein Flame Graph?

Der Sampler liest viele Stacks, und gleiche Stacks werden gezählt. Jeder Kasten ist eine Methode, seine Breite ist der Anteil der Samples.

Zahlen

Seit wann ist JFR frei verfügbar?

Seit Java 11 in OpenJDK (JEP 328). Vorher war es ein kommerzielles Feature des Oracle JDK.

Was ist der Unterschied zwischen default und profile?

default ist für Dauerbetrieb mit sehr wenig Overhead. profile sammelt mehr Details, z. B. mehr Allokations- und Lock-Daten, und kostet etwas mehr.

Was ist neu bei JFR in Java 25?

Cooperative Sampling (JEP 518), experimentelles CPU-Zeit-Profiling auf Linux (JEP 509) und Method Timing und Tracing (JEP 520).

Was ist JMC?

JDK Mission Control, die grafische Auswertung für JFR-Dateien. Aktuell Version 9.1.2.

Wie viel Overhead darf JFR haben?

Das Ziel von JEP 328 ist höchstens 1 % mit der Standard-Konfiguration.

Vergleich

Was ist der Unterschied zwischen CPU- und Wall-Clock-Profiling?

CPU-Profiling zeigt nur rechnende Threads. Wall Clock samplet alle Threads, auch wartende, und erklärt damit Latenz.

Was kann async-profiler, was JFR schlecht kann?

Native und Kernel-Frames, GC- und JIT-Threads im Profil, Hardware-Zähler und native Speicherlecks.

Wie werten Sie eine JFR-Datei ohne GUI aus?

jfr summary für die Übersicht, jfr print für Events, ab Java 21 jfr view mit fertigen Views wie hot-methods.

JFR oder async-profiler in Produktion?

Zuerst JFR, weil es eingebaut ist. async-profiler für tiefe CPU- und native Analysen, wo es erlaubt ist. Er braucht perf_events.

Produktion

Wie starten Sie JFR in einer laufenden Produktion?

jcmd <pid> JFR.start, später JFR.dump für die Datei und JFR.stop. Kein Neustart nötig.

Ist eine JFR-Datei sicher zum Teilen?

Nicht ohne Prüfung. Sie kann Umgebungsvariablen und System Properties enthalten. jfr scrub (ab JDK 21) entfernt solche Daten.

Szenario: Die p99-Latenz ist hoch, aber die CPU nur bei 20 %. Wo suchen Sie?

Nicht im CPU-Profil. Lock-Events, jdk.ThreadPark, Socket-Reads und ein Wall-Clock-Profil zeigen, worauf die Threads warten.

Szenario: Nach einem Release steigt die CPU um 30 %, ohne mehr Last. Wie gehen Sie vor?

JFR-Aufnahmen vor und nach dem Release vergleichen: hot-methods, Allokationsrate, GC-Pausen. Die neue breite Methode oder die gestiegene Allokation zeigt die Änderung.

Szenario: Der GC läuft ständig, das CPU-Profil zeigt vor allem GC-Threads. Was tun Sie?

Allokationsprofil mit allocation-by-class oder async-profiler -e alloc. Die heisse Allokationsstelle finden und Objekte dort vermeiden oder wiederverwenden.

Design

Was schauen Sie zuerst an?

Das Symptom: CPU, Latenz oder Speicher. Dann GC und Allokationsrate, dann Hot Methods oder Lock- und I/O-Events.

Wie finden Sie heraus, wer viel Speicher allokiert?

JFR jdk.ObjectAllocationSample oder jfr view allocation-by-class. Oder async-profiler -e alloc als Flame Graph.

Wie finden Sie Lock-Contention?

JFR jdk.JavaMonitorEnter für synchronized und jdk.ThreadPark für j.u.c.-Locks. Ab Java 21 jfr view contention-by-site. Oder async-profiler -e lock.

Wie setzen Sie JFR dauerhaft auf?

Mit default-Settings und maxage oder maxsize als Ringpuffer. Bei einem Incident holt JFR.dump die letzten Minuten.

Mehr

Gerüst

  • Warum? Man misst, bevor man optimiert, sonst optimiert man den falschen Code. Ein CPU-Profil zeigt keine Wartezeit.
  • Wie innen? Ein Sampling-Profiler hält Threads in festen Abständen an und liest den Stack. Gleiche Stacks werden gezählt und als Flame Graph gezeigt.
  • Zahlen JFR: Ziel höchstens 1 % Overhead (JEP 328). Open Source seit Java 11. jfr view ab Java 21.
  • Vergleich JFR: eingebaut, viele Event-Arten. async-profiler: native Frames, Flame Graphs. APM: welcher Request. Profiler: welche Methode.
  • Produktion Hohe Latenz bei wenig CPU: Lock- und Wall-Clock-Profil. Hohe Allokation: GC-Threads im Profil. JFR als Ringpuffer dauerhaft an.
  • Design JFR immer an mit default-Settings. Erst Symptom, dann GC, dann Hot Methods oder Locks. Nach dem Fix erneut messen.

Vergleich

  • JFR: im JDK eingebaut, sehr wenig Overhead, viele Event-Arten (GC, Locks, I/O). Gut für Dauerbetrieb in Produktion. Native Frames sieht es kaum.
  • async-profiler: sehr genaue CPU-, Lock- und Allokationsprofile mit nativen und Kernel-Frames. Flame Graphs direkt. Braucht einen Agent, Fokus Linux und macOS.
  • JMC: Oberfläche für JFR-Dateien mit automatischen Hinweisen. Kein eigener Profiler.
  • VisualVM, IDE-Profiler: bequem lokal. Teilweise Instrumentierung mit hohem Overhead, nicht für Produktion.
  • APM-Agenten (z. B. OpenTelemetry, Datadog): zeigen, welcher Request langsam ist. Profiler zeigen, welche Methode darin langsam ist.
  • JMH: Microbenchmarks für eine einzelne Methode. Kein Profiler, aber Pflicht für saubere Vorher-Nachher-Messungen.

In der Produktion

  1. Optimiert am falschen Ort: Das Team baut einen Cache, aber die Zeit geht in Lock-Wartezeit. Lösung: erst Wall-Clock- oder Lock-Profil, dann handeln.
  2. Profil nur lokal: Lokal ist der Hot Spot anders als unter echter Last und Daten. Lösung: JFR-Dauer-Aufnahme in Produktion, Dump bei Bedarf.
  3. Hohe Allokationsrate: Der GC läuft ständig, die CPU ist hoch. Das CPU-Profil zeigt GC-Threads. Lösung: Allokationsprofil, dann Objekte in der heissen Schleife vermeiden.
  4. Container ohne Rechte: async-profiler braucht perf_events. In Containern ist das oft gesperrt. Lösung: JFR nutzen oder die Rechte für perf_events bewusst freigeben.
  5. Riesige JFR-Dateien: profile-Settings über Tage ohne maxage. Lösung: Grenzen setzen, im Normalbetrieb default.
  6. Sensible Daten in der Aufnahme: JFR enthält z. B. Umgebungsvariablen und System Properties. Lösung: Dateien vor der Weitergabe mit jfr scrub (ab JDK 21) bereinigen.

Diagnose: Werkzeuge und Befehle

  • java -XX:StartFlightRecording=duration=60s,filename=rec.jfr,settings=profile -jar app.jar
  • jcmd <pid> JFR.start name=x maxage=30m · JFR.dump name=x filename=rec.jfr · JFR.check · JFR.stop
  • jfr summary rec.jfr: welche Events wie oft.
  • jfr print --events jdk.ExecutionSample --stack-depth 10 rec.jfr, auch --json.
  • jfr view hot-methods | allocation-by-class | contention-by-site | gc-pauses | pinned-threads rec.jfr (Java 21+). Im laufenden Prozess: jcmd <pid> JFR.view.
  • asprof -e cpu|alloc|lock|wall -d 30 -f out.html <pid>: Flame Graph. -t trennt nach Thread.
  • JMC 9: Datei öffnen, Seiten für Methoden-Profil, Speicher und Locks, dazu eine automatische Analyse mit Hinweisen.

Was zuerst ansehen?

  1. Symptom klären: CPU hoch? Oder Latenz hoch bei wenig CPU? Oder Speicher?
  2. GC prüfen: gc-pauses und Allokationsrate. Viel GC verfälscht jedes CPU-Bild. Siehe Seite GC-Collectors.
  3. CPU hoch: hot-methods oder CPU-Flame-Graph. Breite Plateaus oben suchen.
  4. Latenz hoch, CPU niedrig: Lock-Events, jdk.ThreadPark, Socket-Reads, Wall-Clock-Profil.
  5. Danach messen: gleiche Aufnahme nach dem Fix wiederholen und vergleichen.

Senior-Punkte

  1. Erst messen, dann optimieren. Eine Methode mit 0,1 % Anteil zehnmal schneller zu machen, spart 0,09 %. Das Beispiel steht so in JEP 518.
  2. JFR immer an mit default-Settings und Ringpuffer. Der Overhead ist klein, und beim nächsten Incident liegen Daten bereit.
  3. CPU-Profil ≠ Latenz-Profil. Für Antwortzeiten braucht man Wall Clock, Lock- und I/O-Events.
  4. Sampling hat Grenzen: sehr kurze, seltene Ereignisse fehlen. Dafür gezielte Events (z. B. jdk.MethodTrace in Java 25) oder Tracing.
  5. Profiling braucht Hypothesen. Das Profil zeigt das „Wo". Das „Warum" kommt aus Code, Daten und Architektur.
  6. Werkzeugwahl: In Produktion zuerst JFR, weil es eingebaut und abgesichert ist. async-profiler für tiefe CPU- und native Analysen, wo es erlaubt ist.
