Serialisierung: Serializable, Risiken, Alternativen (JSON)

Kern: Java-Serialisierung ist der eingebaute Mechanismus, der ein Objekt samt allen erreichbaren Objekten in einen Byte-Strom schreibt und daraus wieder baut. Er löst das Problem „Objekt speichern oder über das Netz schicken“ ohne eigenen Code. Heute gilt er als Sicherheitsrisiko und als schlechtes Austauschformat, darum nimmt man für neue Systeme JSON, Protobuf oder Avro.

Antwort-Muster

Frage: Warum ist Java-Serialisierung gefährlich?

  1. Mechanismus: ObjectInputStream baut Klassen, die der Strom auswählt, ohne deren Konstruktor. Deren readObject-Code läuft mit Daten des Angreifers.
  2. Zahl: Der Strom beginnt mit AC ED 00 05, in Base64 mit rO0. Daran erkennt man ihn in Logs und Requests.
  3. Trade-off: Der Mechanismus ist ohne eigenen Code bequem. Dafür bindet er das Format an Klassen und öffnet Gadget Chains.
  4. Produktion: Ich nehme JSON oder Protobuf mit Schema. Muss es Java sein, setze ich eine Allow-List per jdk.serialFilter.

1. Die Reise eines Objekts durch writeObject und readObject

  1. Prüfen: writeObject(account) prüft, ob die Klasse Serializable ist. Sonst kommt NotSerializableException, auch für ein einzelnes Feld tief im Graph.
  2. Schreiben: Felder mit transient (nicht speichern) und static werden übersprungen. Jedes Objekt wird nur einmal geschrieben; Wiederholungen werden Rückverweise.
  3. Unterwegs: Die Bytes sind nicht signiert. Jeder, der sie ändern kann, ändert die Feldwerte.
  4. Lesen: readObject() vergleicht die serialVersionUID. Ein Filter kann Klassen ablehnen.
  5. Bauen: Die JVM erzeugt das Objekt ohne den Konstruktor der Klasse. Sie ruft nur den No-Arg-Konstruktor der ersten nicht-serialisierbaren Oberklasse (oft Object). transient-Felder bekommen null, 0 oder false.
  6. Gefahr: Klassen auf dem Classpath können eigene readObject-Methoden haben. Ein Angreifer kombiniert sie zu einer Gadget Chain, einer Kette harmloser Methoden, die am Ende Code ausführt.

2. Aufbau

  1. Objekt-Graph: Die Klasse implementiert Serializable, ein Marker-Interface ohne Methoden. Alle erreichbaren Objekte werden mitgeschrieben.
  2. ObjectOutputStream: Er schreibt eine Klassen-Beschreibung (Name, serialVersionUID, Felder) und die Feldwerte. Er liest die Felder per Reflection.
  3. Bytes: Der Strom beginnt mit AC ED 00 05. Er landet in Dateien, HTTP-Sessions, Caches oder bei RMI und JMS.
  4. ObjectInputFilter: ein Filter, der vor dem Bauen prüft, welche Klassen und Grössen erlaubt sind.
  5. ObjectInputStream: Er lädt die Klasse und setzt die Felder direkt. Der Konstruktor der Klasse läuft nicht.

3. Details, die Interviewer fragen

  1. serialVersionUID: Sie ist eine Versionsnummer der Klasse. Fehlt sie, berechnet Java sie aus der Klassenstruktur. Dann bricht schon ein neues Feld oder eine neue Methode das Lesen alter Daten. Es kommt eine InvalidClassException. Darum setzt man sie explizit.
  2. Stream-Aufbau: Der Strom beginnt mit der Magic Number AC ED und der Version 5. Dann folgt je Objekt ein Typ-Byte. Danach kommen die Klassen-Beschreibung und die Feldwerte. Ein wiederholtes Objekt wird nur als Rückverweis geschrieben.
  3. Konstruktor-Bypass: Die JVM erzeugt das Objekt über den Konstruktor der ersten nicht-serialisierbaren Oberklasse. Der Konstruktor der eigenen Klasse läuft nicht. Die Felder setzt sie danach direkt aus dem Strom.
  4. Kompatible Änderungen: Ein neues Feld ist kompatibel. Alte Daten bekommen den Standardwert. Ein entferntes Feld wird ignoriert. Inkompatibel sind ein geänderter Feldtyp und eine verschobene Klasse in der Hierarchie.
  5. transient: Das Feld wird nicht geschrieben. Man nutzt es für Passwörter, Caches, Verbindungen und Logger.
  6. Eigene Logik: Dafür gibt es die privaten Methoden writeObject(ObjectOutputStream) und readObject(ObjectInputStream). In readObject muss man selbst validieren. Man muss auch defensiv kopieren.
  7. readResolve und writeReplace: readResolve ersetzt das gelesene Objekt, z. B. um ein Singleton zu erhalten. writeReplace schreibt ein Ersatz-Objekt. Das ist das Serialization-Proxy-Muster.
  8. Externalizable: Die Klasse schreibt und liest alles selbst. Sie braucht einen public No-Arg-Konstruktor.
  9. Oberklassen: Ist die Oberklasse nicht serialisierbar, werden ihre Felder nicht gespeichert. Sie braucht einen erreichbaren No-Arg-Konstruktor. Dieser läuft beim Lesen.
  10. Records: Sie werden über ihre Komponenten geschrieben. Sie werden über den kanonischen Konstruktor gelesen. Eigene readObject-Methoden werden ignoriert.
  11. Enums: Es wird nur der Name geschrieben. Beim Lesen kommt dieselbe Konstante zurück. Darum ist ein Enum das sicherste Singleton.
  12. Lambdas: Sie sind nur mit einem Cast auf ein serialisierbares Interface serialisierbar. Das ist sehr fragil. Sie sind an die Compiler-Ausgabe gebunden.
  13. Filter: ObjectInputFilter gibt es seit Java 9 (JEP 290). Man setzt ihn per Stream oder JVM-weit über -Djdk.serialFilter=…. Seit Java 17 gibt es eine Filter-Factory (jdk.serialFilterFactory) für kontext-spezifische Filter (JEP 415). Liefert ein Filter UNDECIDED, lässt er die Klasse durch.
  14. Warum unsicher? Beim Lesen läuft Code von Klassen, die der Angreifer im Strom auswählt. Bekannte Fälle nutzten Gadgets aus Apache Commons Collections. Die Oracle Secure Coding Guidelines sagen, Deserialisierung nicht vertrauenswürdiger Daten sei grundsätzlich gefährlich.

4. Fallen

  • „Beim Deserialisieren läuft der Konstruktor.“ → Falsch. Felder werden direkt gesetzt. Nur Records nutzen den kanonischen Konstruktor.
  • „serialVersionUID ist optional und egal.“ → Falsch. Ohne sie bricht fast jede Klassenänderung alte Daten.
  • „transient-Felder behalten ihren Initialwert.“ → Falsch. Sie bekommen null, 0 oder false.
  • „Unsere Klassen sind harmlos, also ist Deserialisierung sicher.“ → Falsch. Gadgets kommen aus Bibliotheken auf dem Classpath.
  • „Ein Filter, der nur Schlechtes ablehnt, reicht.“ → Falsch. Block-Listen sind immer unvollständig. Allow-List mit !*.
  • „JSON ist automatisch sicher.“ → Falsch. Polymorphic Typing mit Klassennamen im JSON öffnet ähnliche Lücken.

5. Selbsttest

Warum?

Warum ist Deserialisierung gefährlich?

Der Strom bestimmt, welche Klassen gebaut werden. Deren readObject-Code läuft mit Angreifer-Daten. Gadget Chains führen bis zur Code-Ausführung.

Wozu dient serialVersionUID?

Sie ist die Versionsnummer der Klasse. Passt sie beim Lesen nicht, kommt InvalidClassException. Ohne explizite UID berechnet Java sie aus der Struktur.

Allow-List oder Block-List?

Allow-List. Nur bekannte Klassen erlauben, alles andere mit !* ablehnen. Block-Listen sind nie vollständig.

Warum läuft der Konstruktor beim Lesen nicht?

Die JVM baut das Objekt über den Konstruktor der ersten nicht-serialisierbaren Oberklasse. Die Felder setzt sie danach direkt aus dem Strom.

Wie innen?

Was ist Java-Serialisierung?

Ein eingebauter Mechanismus, der einen Objekt-Graphen in Bytes schreibt und daraus wieder baut, mit ObjectOutputStream und ObjectInputStream.

Was ist Serializable?

Ein Marker-Interface ohne Methoden. Es erlaubt der JVM, Objekte dieser Klasse zu serialisieren.

Läuft beim Deserialisieren der Konstruktor?

Nein. Nur der No-Arg-Konstruktor der ersten nicht-serialisierbaren Oberklasse läuft. Records sind die Ausnahme: Sie nutzen den kanonischen Konstruktor.

Was ist eine Gadget Chain?

Eine Kette von Methoden aus Bibliotheken auf dem Classpath, die beim Deserialisieren nacheinander laufen und am Ende z. B. einen Befehl ausführen.

Was bewirkt transient?

Das Feld wird nicht geschrieben. Beim Lesen hat es den Standardwert null, 0 oder false.

Werden static-Felder serialisiert?

Nein. Sie gehören zur Klasse, nicht zum Objekt.

Wie ist der Serialisierungsstrom aufgebaut?

Erst der Header AC ED und Version 5. Dann je Objekt ein Typ-Byte, die Klassen-Beschreibung und die Feldwerte. Ein wiederholtes Objekt wird nur als Rückverweis geschrieben.

Zahlen

Woran erkennt man Java-Serialisierung im Traffic?

Am Anfang AC ED 00 05, in Base64 rO0AB.

Was brachte Java 17 für Serialisierung?

Eine Filter-Factory für kontext-spezifische Filter (JEP 415) und das JFR-Event jdk.Deserialization.

Mit welchen Bytes beginnt der Strom?

Mit AC ED 00 05. Das ist die Magic Number AC ED und die Version 5. In Base64 sieht man rO0AB.

Seit wann gibt es ObjectInputFilter?

Seit Java 9 (JEP 290). Die Filter-Factory kam mit Java 17 (JEP 415).

Vergleich

Serializable vs Externalizable?

Serializable schreibt automatisch per Reflection. Externalizable schreibt alles selbst und braucht einen public No-Arg-Konstruktor.

Ist Jackson immer sicher?

Nicht mit Polymorphic Default Typing, das Klassennamen aus dem JSON nutzt. Das war Ursache vieler CVEs.

Welche Alternativen gibt es?

JSON mit Jackson, Protobuf, Avro, XML mit Schema. Sie beschreiben nur Daten und sind sprachneutral.

Java-Serialisierung oder Protobuf?

Java-Serialisierung braucht null Aufwand, ist aber nur Java und an die Klasse gebunden. Protobuf hat ein Schema, ist kompakt und versioniert über Feldnummern.

Produktion

Szenario: Nach einem Deployment werfen Logins InvalidClassException. Was ist los?

Sessions der alten Version sind Java-serialisiert, die Klasse hat sich geändert und keine feste serialVersionUID. Lösung: UID festlegen, Sessions bei Release verwerfen, besser JSON im Session-Store.

Szenario: Ein Pentest findet einen Endpoint, der Base64 mit rO0AB annimmt. Was tun Sie?

Sofort: strikte Allow-List per jdk.serialFilter und Gadget-Bibliotheken aktualisieren. Dauerhaft: auf JSON oder Protobuf mit Schema umstellen.

Szenario: Ein verteilter Cache liefert nach Rolling Update Fehler beim Lesen. Wie lösen Sie es dauerhaft?

Alte und neue Pods teilen Einträge mit verschiedenen Klassen-Versionen. Lösung: schema-basiertes Format wie JSON oder Protobuf, Versions-Präfix im Cache-Schlüssel.

Was passiert mit einem nicht-serialisierbaren Feld?

writeObject wirft NotSerializableException. Lösung: Feld transient machen oder serialisierbar.

Design

Was sind writeObject und readObject?

Private Methoden in der Klasse für eigene Logik. In readObject muss man selbst validieren und defensiv kopieren.

Was macht readResolve?

Es ersetzt das gelesene Objekt durch ein anderes, z. B. die einzige Singleton-Instanz.

Was ist ein ObjectInputFilter?

Ein Filter, der beim Lesen Klassen, Tiefe, Referenzen und Grösse prüft. Seit Java 9, JVM-weit über jdk.serialFilter.

Wie werden Records serialisiert?

Über ihre Komponenten. Beim Lesen läuft der kanonische Konstruktor mit Validierung.

Wie werden Enums serialisiert?

Nur der Name. Beim Lesen kommt dieselbe Konstante zurück. Darum sind Enum-Singletons serialisierungssicher.

Was ist das Serialization-Proxy-Muster?

writeReplace schreibt ein einfaches Proxy-Objekt, dessen readResolve das echte Objekt über den Konstruktor baut. So läuft die Validierung immer.

Szenario: Sie erweitern ein Serializable-Objekt um ein Feld. Was beachten Sie?

Die serialVersionUID bleibt fest. Ein neues Feld ist kompatibel, alte Daten bekommen den Standardwert. Ein geänderter Feldtyp bricht das Lesen.

Mehr

Gerüst

  • Warum? Ein Objekt ohne eigenen Code speichern oder senden. Heute gilt das als unsicher und als schlechtes Austauschformat.
  • Wie innen? ObjectOutputStream liest die Felder per Reflection. ObjectInputStream baut das Objekt ohne dessen Konstruktor.
  • Zahlen Der Strom beginnt mit AC ED 00 05, in Base64 mit rO0. Filter seit Java 9, Filter-Factory seit Java 17.
  • Vergleich JSON: lesbar, nur Daten. Protobuf: Schema, kompakt. Avro: Schema-Evolution. Java-Serialisierung: nur Java.
  • Produktion Gadget Chains führen zu Remote Code Execution. Eine neue Klassenversion gibt InvalidClassException. Schutz: Allow-List per jdk.serialFilter.
  • Design Keine Java-Serialisierung über Vertrauensgrenzen. Das Format ist ein Vertrag mit Schema. Records validieren im Konstruktor.

Beispiel: transient, Konstruktor-Bypass, Records, Filter

class Account implements Serializable { serialVersionUID = 1L; String owner; int balance;
  transient String password; transient int cacheHits = 5;
  Account(…) { if (b < 0) throw …; println("Account constructor ran"); } }
record Money(String currency, long cents) implements Serializable { Money { if (cents < 0) throw …; } }
class Holder implements Serializable { Plain p = new Plain(); }   // Plain ist nicht Serializable

ser(new Account("Anna", 100, "geheim")); de(bytes);                   // 1) 2)
Bytes ändern: int 100 → -1000, dann de(evil)                          // 3)
Bytes ändern: long 500 → -1 im Record, dann de(…)                     // 4)
ser(new Holder());                                                    // 5)
createFilter("SerDemo$Money;java.lang.*;!*")                          // 6)
50 verschachtelte Listen mit createFilter("maxdepth=10")              // 7)
1) serialize:
   Account constructor ran
1) deserialize:
1) owner=Anna balance=100 password=null cacheHits=0 bytes=86
2) stream magic: ACED version 0005
3) tampered bytes -> balance=-1000 (constructor check bypassed)
4) record tampered -> InvalidObjectException: record ctor: negative cents
5) NotSerializableException: SerDemo$Plain
6) filter allows Money: Money[currency=CHF, cents=500]
6) filter rejects Account: filter status: REJECTED
7) maxdepth=10: filter status: REJECTED

Echte Ausgabe, Oracle JDK 17.0.3. Java 21 und 25 verhalten sich gleich.

  1. Beim Lesen läuft der Konstruktor nicht. password ist null, und cacheHits ist 0 statt 5: Feld-Initialisierer laufen auch nicht.
  2. Jeder Java-Serialisierungs-Strom beginnt mit AC ED 00 05. In Base64 beginnt er mit rO0. Daran erkennt man ihn in Logs, Cookies und Requests.
  3. Vier geänderte Bytes ergeben einen negativen Kontostand. Die Prüfung im Konstruktor wird umgangen.
  4. Records werden anders gelesen: über den kanonischen Konstruktor. Die Validierung läuft, die Manipulation fällt auf.
  5. Ein nicht-serialisierbares Feld bricht das Schreiben des ganzen Graphen.
  6. Ein Allow-List-Filter lässt nur bekannte Klassen durch. !* lehnt alles andere ab.
  7. Grenzen wie maxdepth schützen vor tief verschachtelten Daten, die Stack oder Speicher sprengen.

Vergleich

  • Java-Serialisierung: null Aufwand, aber nur Java, an Klassenstruktur gebunden, unsicher bei fremden Daten.
  • JSON (Jackson): lesbar, sprachneutral, nur Daten ohne Code. Nutzt Konstruktoren oder Setter, Validierung möglich. Achtung: Polymorphic Typing mit Klassennamen im JSON ist ähnlich gefährlich.
  • Protobuf / gRPC: kompaktes Binärformat mit Schema. Schnell, gute Versionierung über Feldnummern.
  • Avro: Schema mit Evolution, typisch mit Kafka und Schema Registry.
  • XML (JAXB): mit XSD-Schema validierbar, ausführlich. Bei Behörden-Schnittstellen verbreitet.
  • Kryo / FST: schnelle Binär-Serialisierer für Java. Gleiche Grundprobleme bei fremden Daten, Klassen registrieren.

In der Produktion

  1. Remote Code Execution: Ein Endpoint oder ein Cookie nimmt Java-serialisierte Daten an. Ein Angreifer schickt eine Gadget Chain. Lösung: keine Java-Deserialisierung fremder Daten; sonst strikte Allow-List per jdk.serialFilter.
  2. InvalidClassException nach Deployment: Sessions oder Cache-Einträge aus der alten Version passen nicht mehr. Lösung: serialVersionUID fest, oder Cache leeren und Sessions verwerfen.
  3. NotSerializableException in der Session: Ein Feld (z. B. ein Service oder Logger) ist nicht serialisierbar. Lösung: transient oder nicht in die Session legen.
  4. Riesige Payloads: Ein Objekt zieht seinen ganzen Graphen mit, z. B. einen Hibernate-Proxy samt Session. Lösung: DTOs für den Transport.
  5. Verteilter Cache mit Java-Serialisierung: Bei Rolling Updates lesen alte und neue Pods dieselben Einträge. Lösung: JSON oder Protobuf im Cache, versionierte Schlüssel.
  6. JSON mit Default Typing: Jackson mit aktiviertem Polymorphic Typing und Klassennamen im JSON war Ursache vieler CVEs. Lösung: kein Default Typing, nur bekannte Subtypen.

Diagnose: Werkzeuge und Befehle

  • Muster in Traffic und Logs: AC ED 00 05 (binär) oder rO0AB (Base64) zeigen Java-Serialisierung.
  • -Djdk.serialFilter="com.example.*;java.base/*;!*": JVM-weite Allow-List.
  • Logger java.io.serialization (System.Logger) auf DEBUG oder TRACE: protokolliert Filter-Entscheidungen.
  • JFR-Event jdk.Deserialization (seit Java 17): zeigt jede deserialisierte Klasse und das Filter-Ergebnis.
  • serialver Klasse: zeigt die berechnete serialVersionUID.
  • OWASP Dependency-Check / Snyk: finden bekannte Gadget-Bibliotheken mit CVEs.
  • SonarQube: Regeln zu serialVersionUID, nicht-serialisierbaren Feldern und unsicherer Deserialisierung.

Senior-Punkte

  1. Keine Java-Serialisierung über Vertrauensgrenzen. Alles, was von aussen kommt, wird JSON, Protobuf oder XML mit Schema.
  2. Formate sind Verträge. Ein explizites Schema (OpenAPI, Protobuf, Avro, XSD) überlebt Refactorings. Java-Serialisierung bindet das Format an interne Klassen.
  3. Wenn unvermeidbar: Allow-List-Filter, Grenzen für Tiefe und Grösse, Gadget-Bibliotheken aktuell halten.
  4. Records sind die sichere Form, weil der Konstruktor validiert.
  5. Daten ohne Code. Ein gutes Austauschformat beschreibt nur Daten. Es darf nie bestimmen, welche Klasse instanziert wird.
