OOP-Grundlagen

Kern: OOP (objektorientierte Programmierung) ist ein Stil, in dem Objekte Daten und Verhalten bündeln, um grosse Systeme in kleine, austauschbare Teile zu zerlegen. In Java tragen vier Säulen, nämlich Kapselung, Vererbung, Polymorphismus und Abstraktion. Die wichtigste Interviewfrage ist dieser Unterschied, denn Overloading wählt der Compiler und Overriding die JVM zur Laufzeit.

Antwort-Muster

Frage: Was ist der Unterschied zwischen Overloading und Overriding?

  1. Mechanismus: Overloading wählt der Compiler nach dem statischen Typ der Argumente. Overriding wählt die JVM zur Laufzeit über die vtable nach der echten Klasse des Empfängers.
  2. Zahl: Beim Overloading prüft javac in drei Phasen. Im Bytecode gibt es fünf Invoke-Befehle, zum Beispiel invokevirtual und invokestatic.
  3. Trade-off: Overloading kostet nichts zur Laufzeit. Overriding ist dank JIT-Inlining fast gratis. Die Gefahr ist eine falsche Überladung, etwa list.remove(1) mit Index statt Wert.
  4. Produktion: Darum schreibe ich immer @Override. Sonst wird aus equals(Person p) still eine Überladung.

1. Die Reise eines Methodenaufrufs

  1. Statischer Typ: Der Code sagt Tier t = new Hund(). javac kennt nur Tier. Er sucht die Methode in Tier.
  2. Overload wählen: Es gibt fuetter(Object) und fuetter(String). Das Argument hat den statischen Typ Object. javac wählt fuetter(Object). Das ist statische Bindung (static dispatch).
  3. Bytecode: javac schreibt invokevirtual Tier.fuetter(Object) in die Class-Datei. Die Signatur ist jetzt fest.
  4. Echte Klasse: Zur Laufzeit schaut die JVM auf das echte Objekt. Es ist ein Hund.
  5. vtable: Die vtable ist eine Tabelle der überschreibbaren Methoden pro Klasse. Hat Hund genau diese Signatur überschrieben, läuft Hund.fuetter(Object). Das ist dynamische Bindung (dynamic dispatch).
  6. JIT: Sieht der JIT an der Stelle immer nur eine Klasse, ruft er die Methode direkt auf oder inlined sie. Darum kostet Polymorphismus in heissem Code fast nichts.

Merksatz: Overloading = Compiler + statischer Typ der Argumente. Overriding = JVM + echte Klasse des Empfängers.

2. Aufbau

  1. Abstraktion: zeigt nur, was ein Objekt kann, nicht wie. Beispiel: interface Zahlung { void bezahle(long rappen); }.
  2. Vererbung: eine Klasse übernimmt Felder und Methoden einer Oberklasse mit extends. Beispiel: KartenZahlung extends BasisZahlung.
  3. Kapselung: der Zustand ist private und nur über Methoden erreichbar. Beispiel: kartenNr hat keinen Setter.
  4. Polymorphismus: derselbe Aufruf z.bezahle(100) führt je nach Objekt anderen Code aus. Beispiel: Karte oder Twint.
  5. Der Aufrufer kennt nur das Interface. Neue Zahlungsarten brauchen keine Änderung beim Aufrufer.

3. Details, die Interviewer fragen

  1. Kapselung: Felder sind private. Der Zugriff geht nur über Methoden, die Regeln prüfen. Getter und Setter für jedes Feld sind keine echte Kapselung. Gute Kapselung zeigt Verhalten, zum Beispiel konto.abheben(betrag) statt setSaldo().
  2. Zugriffsmodifier: private gilt nur in der Klasse. Package-private (kein Modifier) gilt im Paket. protected gilt im Paket und in Unterklassen. public gilt für alle. Seit Java 9 begrenzen Module zusätzlich, welche Pakete exportiert werden.
  3. Vererbung: Java erlaubt nur eine Oberklasse (extends), aber viele Interfaces (implements). Jede Klasse erbt am Ende von Object. Konstruktoren werden nicht vererbt.
  4. Overriding-Regeln (JLS §8.4.8.3): Die Signatur ist gleich. Der Rückgabetyp ist gleich oder ein Untertyp (kovarianter Rückgabetyp). Die Sichtbarkeit ist gleich oder weiter. Es kommen keine neuen oder breiteren checked Exceptions dazu. final-, static- und private-Methoden kann man nicht überschreiben.
  5. @Override: Der Compiler prüft diese Annotation. Ein Tippfehler wie equals(Person p) statt equals(Object o) wird so zum Fehler. Ohne sie wäre es eine stille Überladung.
  6. Overloading (JLS §8.4.9): Der Name ist gleich, die Parameterliste anders. Der Rückgabetyp allein reicht nicht. javac wählt in drei Phasen (JLS §15.12.2). Zuerst gilt es ohne Boxing und Varargs, dann mit Boxing, zuletzt mit Varargs.
  7. Static vs dynamic dispatch: invokestatic und invokespecial sind fest gebunden. invokespecial gilt für Konstruktoren, private und super.m(). invokevirtual und invokeinterface suchen zur Laufzeit die Methode der echten Klasse.
  8. Single Dispatch: Java entscheidet zur Laufzeit nur nach dem Empfänger, nicht nach den Argumenten. Für Dispatch nach Argumenttyp braucht man das Visitor-Pattern. Heute geht auch switch mit Patterns.
  9. super: super.m() ruft die Version der Oberklasse auf und ist fest gebunden. super(...) im Konstruktor ruft den Konstruktor der Oberklasse. Seit Java 25 (JEP 513) dürfen davor Anweisungen stehen. Sie dürfen das Objekt nicht lesen, aber eigene Felder initialisieren.
  10. Überschreibbare Methode im Konstruktor: Der Konstruktor der Oberklasse läuft zuerst. Ruft er eine überschriebene Methode auf, sieht diese noch nicht initialisierte Felder der Unterklasse. Sie sind null oder 0.
  11. Abstraktion: Man nutzt abstract class oder interface. Abstrakte Klassen können Zustand und Konstruktoren haben. Interfaces beschreiben eine Fähigkeit. Details stehen auf der Seite „Interface vs abstrakte Klasse".
  12. Komposition statt Vererbung: Ein Objekt hält ein anderes als Feld und delegiert (has-a). Vererbung (is-a) koppelt fest an die Interna der Oberklasse. Vererbung passt, wenn die Oberklasse dafür gebaut und dokumentiert ist.
  13. Liskov Substitution Principle (LSP): Eine Unterklasse muss überall funktionieren, wo die Oberklasse erwartet wird. Klassisch verletzt ist Quadrat extends Rechteck, wenn setBreite die Höhe mitändert.
  14. final und sealed: final class verbietet Unterklassen. sealed (final seit Java 17, JEP 409) erlaubt nur die Klassen in permits. So steuert man Vererbung bewusst.

4. Fallen

  • „Overloading ist Laufzeit-Polymorphismus.“ → Falsch. Overloading entscheidet der Compiler. Nur Overriding ist Laufzeit-Polymorphismus.
  • „Static-Methoden kann man überschreiben.“ → Falsch. Sie werden versteckt (Hiding). Der statische Typ entscheidet.
  • „Felder sind polymorph.“ → Falsch. Felder werden versteckt. t.name liest das Feld des statischen Typs.
  • „Ein anderer Rückgabetyp reicht zum Überladen.“ → Falsch. Die Parameterliste muss sich unterscheiden.
  • „Getter und Setter sind Kapselung.“ → Nur halb. Ein Setter für jedes Feld legt den Zustand offen. Kapselung schützt Regeln.
  • „Private Methoden kann man in der Unterklasse überschreiben.“ → Falsch. Eine gleichnamige Methode ist eine neue, unabhängige Methode.
  • „Java hat keine Mehrfachvererbung.“ → Halb richtig. Keine Mehrfachvererbung von Zustand. Verhalten über mehrere Interfaces mit default-Methoden geht.

5. Selbsttest

Warum?

Warum @Override verwenden?

Der Compiler prüft, dass wirklich etwas überschrieben wird. Tippfehler oder falsche Parametertypen fallen sofort auf.

Warum keine Mehrfachvererbung von Klassen?

Um Konflikte bei Zustand und Konstruktoren zu vermeiden (Diamond-Problem). Mehrere Interfaces sind erlaubt, Konflikte bei default-Methoden muss man selbst auflösen.

Was heisst „Komposition statt Vererbung"?

Ein Objekt hält ein anderes als Feld und delegiert. Das entkoppelt von Interna der Oberklasse und erlaubt Austausch zur Laufzeit.

Was ist das Fragile Base Class Problem?

Eine Änderung in der Oberklasse bricht Unterklassen, weil diese auf interne Selbstaufrufe bauen. Beispiel: addAll ruft add und die Unterklasse zählt doppelt.

Was ist das Liskov Substitution Principle?

Eine Unterklasse muss überall statt der Oberklasse funktionieren, ohne Überraschungen. Quadrat extends Rechteck verletzt es oft.

Warum keine überschreibbaren Methoden im Konstruktor aufrufen?

Der Konstruktor der Oberklasse läuft vor der Initialisierung der Unterklasse. Die überschriebene Methode sieht null oder 0 in deren Feldern.

Warum stört final bei Spring?

Spring erzeugt für AOP oft Unterklassen-Proxies mit CGLIB. Finale Klassen oder Methoden kann der Proxy nicht überschreiben, z. B. greift @Transactional dann nicht.

Wie innen?

Was ist Polymorphismus?

Ein Aufruf über einen gemeinsamen Typ führt je nach echtem Objekt anderen Code aus. In Java über Overriding und dynamische Bindung.

Was ist statische und was dynamische Bindung?

Statisch: Ziel steht beim Kompilieren fest (static, private, Konstruktoren, Overload-Auswahl). Dynamisch: die JVM wählt zur Laufzeit die Methode der echten Klasse (invokevirtual, invokeinterface).

Welche Methode läuft bei Tier t = new Hund(); t.fuetter(o) mit Object o = "x"?

Der Compiler wählt fuetter(Object) nach dem statischen Typ von o. Zur Laufzeit läuft Hunds Override dieser Signatur.

Kann man static-Methoden überschreiben?

Nein. Sie werden versteckt. Der Aufruf hängt vom statischen Typ ab, javac erzeugt invokestatic.

Sind Felder polymorph?

Nein. Ein gleichnamiges Feld in der Unterklasse versteckt das alte. Der Zugriff richtet sich nach dem statischen Typ.

Was macht list.remove(1) bei List<Integer>?

Es löscht das Element an Index 1. Die Überladung remove(int) passt ohne Boxing und gewinnt. Für den Wert: remove(Integer.valueOf(1)).

Was ist eine vtable?

Eine Tabelle pro Klasse mit Zeigern auf ihre überschreibbaren Methoden. Die JVM findet darüber schnell die Methode der echten Klasse.

Was ist Single Dispatch?

Java wählt zur Laufzeit nur nach dem Empfänger-Objekt. Die Argumenttypen zählen nur beim Kompilieren. Double Dispatch braucht ein Visitor-Pattern.

Zahlen

Wie wählt javac zwischen Überladungen?

In drei Phasen: zuerst ohne Boxing und Varargs, dann mit Boxing, dann mit Varargs. In der Phase gewinnt die spezifischste Methode, sonst gibt es einen Mehrdeutigkeitsfehler.

Welche Bytecode-Befehle gibt es für Methodenaufrufe?

invokestatic, invokespecial, invokevirtual, invokeinterface, invokedynamic. Die ersten zwei binden fest, die mittleren zwei dynamisch, invokedynamic bindet über eine Bootstrap-Methode.

Was ist eine sealed-Klasse?

Eine Klasse, die nur die in permits genannten Unterklassen erlaubt. Final seit Java 17. Der Compiler kann damit Vollständigkeit im switch prüfen.

Seit welcher Java-Version dürfen Anweisungen vor super(...) stehen?

Seit Java 25 (JEP 513). Sie dürfen das Objekt nicht lesen, aber eigene Felder initialisieren.

Seit welcher Java-Version gibt es Module?

Seit Java 9. Sie begrenzen zusätzlich, welche Pakete exportiert werden.

Vergleich

Was ist der Unterschied zwischen Abstraktion und Kapselung?

Abstraktion zeigt nur das Was (Interface). Kapselung versteckt das Wie und schützt den Zustand (private Felder).

Overloading vs Overriding?

Overloading: gleicher Name, andere Parameter, entschieden vom Compiler. Overriding: gleiche Signatur in der Unterklasse, entschieden zur Laufzeit nach der echten Klasse.

Was ist der Unterschied zwischen protected und package-private?

Package-private ist nur im Paket sichtbar. protected ist zusätzlich in Unterklassen in anderen Paketen sichtbar.

Polymorphismus oder switch?

Viele Typen und wenige Operationen sprechen für Polymorphismus. Wenige feste Typen und viele Operationen sprechen für sealed und switch mit Patterns.

Produktion

Kostet dynamic dispatch Performance?

Kaum. Der JIT inlined Aufrufe, an denen er nur eine oder zwei Klassen sieht. Teuer werden nur megamorphe Stellen in heissem Code.

Szenario: Ein Kollege hat equals(Kunde k) geschrieben, aber das HashSet enthält Duplikate. Warum?

equals(Kunde) ist eine Überladung, kein Override. HashSet ruft equals(Object) und nutzt Object.equals. Lösung: equals(Object) mit @Override und passend hashCode.

Szenario: Nach einem Bibliotheks-Update zählt Ihre Unterklasse von HashSet falsch. Was ist passiert?

Die Oberklasse hat ihre interne Selbstnutzung geändert, z. B. ob addAll add aufruft. Das ist Fragile Base Class. Lösung: Komposition mit Delegation statt Vererbung.

Szenario: Eine Methode mit @Transactional rollt im Fehlerfall nicht zurück. Was prüfen Sie zuerst?

Ob die Methode final oder private ist oder intern über this aufgerufen wird. Dann greift der Proxy nicht. Lösung: Methode public und nicht final, Aufruf über die Bean.

Design

Was sind die vier Säulen der OOP?

Kapselung, Vererbung, Polymorphismus, Abstraktion. Zusammen erlauben sie austauschbare Teile mit klaren Verträgen.

Was ist Kapselung?

Zustand ist privat und nur über Methoden mit Regeln erreichbar. So kann kein Aufrufer ein Objekt in einen ungültigen Zustand bringen.

Welche Regeln gelten beim Overriding?

Gleiche Signatur, gleicher oder kovarianter Rückgabetyp, gleiche oder weitere Sichtbarkeit, keine breiteren checked Exceptions. final, static und private geht nicht.

Was ist ein kovarianter Rückgabetyp?

Die überschreibende Methode darf einen Untertyp zurückgeben. Beispiel: clone() in einer Klasse gibt die Klasse selbst statt Object zurück.

Was bewirkt final an Klasse, Methode und Variable?

Klasse: keine Unterklassen. Methode: kein Overriding. Variable: nur einmal zuweisbar, das Objekt selbst bleibt veränderbar.

Was ist ein anämisches Domänenmodell?

Klassen nur mit Daten und Getter/Setter, die Logik liegt in Services. Das verletzt Kapselung und verteilt Regeln.

Mehr

Gerüst

  • Warum? Grosse Systeme in kleine, austauschbare Teile zerlegen. Der Aufrufer kennt nur das Interface.
  • Wie innen? javac wählt die Überladung nach dem statischen Typ und schreibt invokevirtual. Die JVM sucht über die vtable die Methode der echten Klasse.
  • Zahlen Drei Phasen bei der Überladung, fünf Invoke-Befehle im Bytecode. Sealed final seit Java 17, Statements vor super(...) seit Java 25.
  • Vergleich Overloading: Compiler, statischer Typ. Overriding: JVM, echte Klasse. Vererbung ist is-a, Komposition ist has-a.
  • Produktion Fragile Base Class zählt doppelt (adds=6 statt 3). list.remove(1) löscht nach Index. final bricht Spring-Proxies.
  • Design Komposition als Standard, Interfaces an den Grenzen. Verhalten in die Klasse mit den Daten. Overloading sparsam.

Beispiel: statische und dynamische Bindung sehen

static class Tier {
  String name = "Tier";
  static String art() { return "Tier.art"; }
  String laut() { return "..."; }
  void fuetter(Object o) { println("Tier.fuetter(Object)"); }

}
static class Hund extends Tier {
  String name = "Hund";                          // versteckt das Feld
  static String art() { return "Hund.art"; }     // versteckt die static-Methode
  @Override String laut() { return "Wuff"; }
  @Override void fuetter(Object o) { println("Hund.fuetter(Object)"); }
}
static void zeige(Tier t) { println("zeige(Tier)"); }

Echte Ausgabe, Oracle JDK 17.0.3. Das Verhalten ist durch die JLS festgelegt und in Java 21 und 25 gleich.

  1. laut() ist überschrieben. Die JVM nimmt die echte Klasse: Wuff.
  2. Felder sind nie polymorph. t.name liest das Feld von Tier (getfield Tier.name). Das heisst Field Hiding.
  3. static-Methoden werden nicht überschrieben, sondern versteckt (Method Hiding). invokestatic Tier.art ist fest.
  4. zeige(t) nimmt die Überladung für Tier. Der Compiler kennt nur den statischen Typ.
  5. t.fuetter(o): Overload (Object) wählt javac, dann Override in Hund wählt die JVM. Beide Regeln wirken nacheinander.
  6. t.fuetter("x"): javac wählt (String). Hund überschreibt diese Signatur nicht. Also läuft Tier.fuetter(String).
  7. remove(1) ist remove(int index), nicht remove(Object). Ohne Boxing gewinnt die exakte Überladung.

Komposition statt Vererbung, auch real gemessen:

class ZaehlHashSet<E> extends HashSet<E> {          // Vererbung
  int adds = 0;
  public boolean add(E e) { adds++; return super.add(e); }
  public boolean addAll(Collection<? extends E> c) { adds += c.size(); return super.addAll(c); }
}
class ZaehlSetKomp<E> {                               // Komposition
  private final Set<E> inner = new HashSet<>();
  int adds = 0;
  boolean add(E e) { adds++; return inner.add(e); }
  boolean addAll(Collection<? extends E> c) { adds += c.size(); return inner.addAll(c); }
}
// beide: addAll(List.of("a", "b", "c"))
Vererbung:  adds=6
Komposition: adds=3

Echte Ausgabe, Oracle JDK 17.0.3.

  1. HashSet.addAll ruft intern add für jedes Element auf (geerbt von AbstractCollection). Die Unterklasse zählt doppelt.
  2. Das ist das Fragile Base Class Problem: die Unterklasse hängt von Interna der Oberklasse ab.
  3. Die Komposition hält das Set nur als Feld. Interna der Oberklasse spielen keine Rolle.

Vergleich

  • Overloading: gleicher Name, andere Parameter, in derselben Klasse oder geerbt. Entscheidung beim Kompilieren nach statischen Typen. Rückgabetyp frei.
  • Overriding: gleiche Signatur in der Unterklasse. Entscheidung zur Laufzeit nach der echten Klasse. Rückgabetyp gleich oder kovariant.
  • Hiding: gleiche static-Methode oder gleiches Feld in der Unterklasse. Entscheidung beim Kompilieren nach statischem Typ.
  • Vererbung (is-a): wenig Code, aber feste Kopplung und Fragile-Base-Class-Risiko.
  • Komposition (has-a): etwas mehr Code (Delegation), dafür austauschbar und testbar.
  • Interface: Vertrag ohne Instanz-Zustand, mehrfach implementierbar.
  • Abstrakte Klasse: Teil-Implementierung mit Zustand, nur eine Oberklasse.

In der Produktion

  1. Tiefe Vererbungsbäume: BaseService → AbstractCrudService → … über fünf Ebenen. Eine Änderung oben bricht Klassen unten. Lösung: flache Hierarchie, gemeinsames Verhalten als Komponente injizieren.
  2. Doppelte Zählung oder Logik durch überschriebene Methoden, die die Oberklasse intern ruft (siehe ZaehlHashSet). Lösung: Komposition oder nur dokumentierte Hooks überschreiben.
  3. Falsche Überladung: list.remove(i) mit int i löscht nach Index statt nach Wert. Lösung: remove(Integer.valueOf(i)) und Tests.
  4. Stilles Overloading statt Overriding: equals(Person p) überschreibt nichts. HashSet ruft equals(Object) und findet keine Duplikate. Lösung: immer @Override.
  5. NullPointerException im Konstruktor: Oberklasse ruft im Konstruktor eine überschriebene Methode. Felder der Unterklasse sind noch null. Lösung: keine überschreibbaren Methoden im Konstruktor; final oder private.
  6. Anämisches Domänenmodell: Objekte haben nur Getter/Setter, Logik liegt in Services. Regeln werden an vielen Stellen dupliziert. Lösung: Verhalten in die Klasse mit den Daten.
  7. Proxy-Probleme mit final: Frameworks wie Spring (CGLIB) erzeugen Unterklassen. final-Klassen oder -Methoden können sie nicht abfangen. Ein @Transactional auf einer final-Methode wirkt dann still nicht.

Diagnose: Werkzeuge und Befehle

  • javap -c Klasse: zeigt invokevirtual, invokestatic, invokeinterface. So sieht man, welche Überladung javac gewählt hat.
  • javac -Xlint:all: warnt z. B. bei Raw Types, unsicheren Varargs und fehlendem serialVersionUID.
  • IDE-Typhierarchie (IntelliJ: Ctrl+H) und „Find Usages": zeigt, wer eine Methode überschreibt.
  • ArchUnit: Test-Bibliothek, prüft Architekturregeln, z. B. „Services erben nicht von X".
  • SonarQube: meldet tiefe Vererbung (Depth of Inheritance) und überschreibbare Aufrufe im Konstruktor.
  • -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining: zeigt, ob der JIT einen virtuellen Aufruf inlined.

Senior-Punkte

  1. Vererbung ist ein öffentliches Versprechen. Wer eine Klasse zum Erben freigibt, muss die Selbstaufrufe dokumentieren. Sonst final oder sealed.
  2. Komposition ist der Standard, Vererbung die Ausnahme. Sie passt für echte is-a-Beziehungen innerhalb eines Moduls.
  3. Interfaces an den Grenzen. Services hängen von Interfaces ab, nicht von Klassen. Das macht Tests mit Fakes einfach.
  4. Polymorphismus oder switch? Viele Typen, wenige Operationen: Polymorphismus. Wenige feste Typen, viele Operationen: sealed + switch mit Patterns.
  5. Overloading sparsam. Überladungen mit gleicher Parameterzahl und verwandten Typen verwirren Leser und Boxing-Regeln. Lieber unterschiedliche Namen.
  6. Virtuelle Aufrufe sind billig. Der JIT inlined monomorphe und bimorphe Aufrufe. Design nie wegen eingebildeter Dispatch-Kosten verbiegen.
