Thread Dumps lesen

Kern: Ein Thread Dump ist eine Momentaufnahme aller Threads einer JVM: Name, Zustand, Stack Trace und Locks. Er beantwortet die Frage „Was macht die Anwendung gerade?“. Er ist das erste Werkzeug bei Hängern, Deadlocks und hoher CPU.

Antwort-Muster

Frage: Wie analysieren Sie einen hängenden Java-Service mit Thread Dumps?

  1. Mechanismus: Ich ziehe mit jcmd <pid> Thread.print -l mehrere Dumps. Zuerst lese ich das Ende nach Found one Java-level deadlock. Dann folge ich den Lock-Adressen.
  2. Zahl: Ich ziehe drei Dumps im Abstand von 5–10 Sekunden. Nur so sehe ich, was wirklich feststeckt.
  3. Trade-off: Ein Dump ist billig, aber nur ein Foto. Für seltene Wartezeiten ist JFR besser.
  4. Produktion: Ich ziehe die Dumps vor dem Neustart. Sonst ist die Ursache weg.

1. Die Reise durch einen Dump

  1. Drei Dumps ziehen: Ein einzelner Dump ist ein Foto. Erst drei Dumps im Abstand von 5–10 Sekunden zeigen, ob ein Thread feststeckt oder nur gerade vorbeikommt.
  2. Zuerst ans Ende: Die JVM erkennt Lock-Zyklen selbst. Sie schreibt am Ende Found one Java-level deadlock.
  3. Filtern: JVM-Threads (GC, Compiler, Reference Handler) ignorieren. Gute Thread-Namen sparen hier viel Zeit.
  4. Nach Zustand zählen: 180 von 200 Request-Threads in BLOCKED an derselben Zeile? Das ist die Spur.
  5. Lock-Adresse folgen: Ein Thread zeigt waiting to lock <0x…a70>. Gesucht ist der Thread mit - locked <0x…a70>. Was macht der gerade?
  6. Dumps vergleichen: Steht der Halter in allen Dumps an derselben Stelle, hängt er wirklich. Zum Beispiel an einem Remote-Call ohne Timeout.
  7. Eigenen Code finden: Den obersten Frame aus dem eigenen Package suchen. Darüber liegt nur Framework- oder JDK-Code.

2. Aufbau

  1. jcmd / jstack: ein eigener Prozess. Er verbindet sich über den Attach-Mechanismus mit der Ziel-JVM. Beispiel: jcmd 4711 Thread.print.
  2. Attach Listener: ein Thread in der Ziel-JVM. Er nimmt den Befehl an.
  3. VM Thread: führt den Dump als VM-Operation aus. Die klassische Variante braucht einen kurzen Safepoint, also eine Pause aller Java-Threads.
  4. Platform Threads: erscheinen alle, auch JVM-interne wie C2 CompilerThread0 oder G1 Conc#0.
  5. Virtual Threads: erscheinen im klassischen Dump nicht. Dafür gibt es Thread.dump_to_file. Laut JEP 444 pausiert dieser die Anwendung nicht.

3. Details, die Interviewer fragen

  1. Die sechs Zustände (Thread.State):
    • NEW: erzeugt, noch nicht gestartet. Erscheint nicht im Dump.
    • RUNNABLE: läuft oder ist lauffähig. Auch ein Thread in blockierender Socket-I/O ist RUNNABLE.
    • BLOCKED: wartet auf den Monitor eines synchronized. Der Text ist waiting for monitor entry.
    • WAITING: wartet ohne Zeitlimit, z. B. in Object.wait(), join() oder LockSupport.park(). Das gilt auch für ReentrantLock, Queues und Latches.
    • TIMED_WAITING: wartet mit Zeitlimit, z. B. in sleep, wait(ms), parkNanos oder poll(timeout).
    • TERMINATED: fertig. Erscheint nicht im Dump.
  2. Die Lock-Zeilen: - locked heisst, der Thread hält den Monitor. - waiting to lock heisst, er will ihn (BLOCKED). - waiting on heisst, er hat ihn in wait() abgegeben. - parking to wait for heisst, er wartet auf einen java.util.concurrent-Synchronizer.
  3. Attach-Mechanismus auf Linux: Das Tool legt die Datei .attach_pid<pid> an. Dann sendet es SIGQUIT an die JVM. Der Signal-Handler startet den Attach Listener. Dieser öffnet einen Socket .java_pid<pid> im Temp-Verzeichnis. Über ihn läuft der Befehl.
  4. jstack und jcmd: Beide liefern denselben Dump. Das Java-25-Manual nennt jstack „experimental and unsupported“. Empfohlen ist jcmd <pid> Thread.print. Mit -l kommen j.u.c.-Locks dazu, mit -e erweiterte Infos.
  5. Andere Wege: kill -3 <pid> (SIGQUIT) schreibt den Dump auf die Standardausgabe der JVM. Das ist im Container das Log. Über JMX geht ThreadMXBean.dumpAllThreads. Dazu kommen IDEs, VisualVM und JMC.
  6. Deadlock-Erkennung: Die JVM findet Zyklen über Monitore und ownable synchronizers, z. B. ReentrantLock. Ein Pool, der auf sich selbst wartet, ist kein Lock-Zyklus. Den meldet sie nicht.
  7. Hohe CPU finden: Unter Linux zeigt top -H -p <pid> die CPU pro OS-Thread. Man rechnet die Thread-ID in Hex um. Dann sucht man im Dump nach nid=0x…. Alternativ vergleicht man das Feld cpu= in zwei Dumps.
  8. RUNNABLE heisst nicht „rechnet“: SocketInputStream.read oder EPoll.wait stehen auf RUNNABLE. Sie warten aber auf das Netz. CPU sieht man nur über cpu= oder top -H.
  9. Safepoint-Kosten: Der klassische Dump hält alle Threads kurz an. Bei Tausenden Threads kann das spürbar sein. Ein paar Dumps sind in Produktion aber unkritisch.
  10. Virtual Threads: Im klassischen Dump erscheinen nur Carrier-Threads wie ForkJoinPool-1-worker-1. Den Virtual Thread selbst zeigt nur Thread.dump_to_file. Bei -Djdk.trackAllThreads=false fehlen dort manche direkt erzeugte Virtual Threads.
  11. Thread-Container: Das neue Format gruppiert Threads nach Containern. Das sind Executor, StructuredTaskScope und Root. So sieht man Eltern-Kind-Beziehungen.

4. Fallen

  • „RUNNABLE heisst, der Thread verbraucht CPU." → Falsch. Auch blockierende Socket-Reads stehen auf RUNNABLE.
  • „Ein Thread, der auf einen ReentrantLock wartet, ist BLOCKED." → Falsch. Er ist WAITING (parking). BLOCKED gibt es nur bei synchronized.
  • „Ein Thread in wait() hält den Monitor." → Falsch. wait() gibt ihn frei. Der Dump zeigt waiting on.
  • „Ein Dump reicht." → Falsch. Erst mehrere Dumps zeigen, was feststeckt.
  • „jstack zeigt alle Threads." → Nicht seit Java 21. Virtual Threads fehlen. Dafür Thread.dump_to_file.
  • „Die JVM findet jeden Deadlock." → Falsch. Nur Zyklen über Monitore und ownable synchronizers. Pool-Starvation erkennt sie nicht.

5. Selbsttest

Warum?

Warum mehrere Dumps statt einem?

Ein Dump ist ein Zufallsmoment. Erst der Vergleich zeigt, welche Threads wirklich an derselben Stelle feststecken.

Warum sind Thread-Namen wichtig?

pool-7-thread-3 sagt nichts. Ein Name wie orders-consumer-3 zeigt sofort, welcher Teil der App betroffen ist.

Steht ein Thread in Socket-Read auf WAITING?

Nein, auf RUNNABLE. Die JVM sieht nativen I/O als laufend an.

Warum meldet die JVM einen Pool, der auf sich selbst wartet, nicht als Deadlock?

Sie sucht nur Zyklen über Monitore und ownable synchronizers. Ein Pool ohne freie Threads ist kein Lock-Zyklus.

Wie innen?

Was ist ein Thread Dump?

Eine Momentaufnahme aller Threads der JVM mit Name, Zustand, Stack Trace und Locks.

Welche Thread-Zustände gibt es?

NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.

Welchen Zustand hat ein Thread in Thread.sleep?

TIMED_WAITING (sleeping).

Welchen Zustand hat ein Thread, der auf ReentrantLock.lock() wartet?

WAITING (parking). Im Dump steht „parking to wait for" mit dem Sync-Objekt des Locks.

Was bedeuten „locked", „waiting to lock" und „waiting on"?

locked: hält den Monitor. waiting to lock: will ihn haben. waiting on: hat ihn in wait() abgegeben und wartet auf notify.

Was sind „Locked ownable synchronizers"?

Gehaltene java.util.concurrent-Locks wie ReentrantLock. Sie erscheinen nur mit jstack -l oder jcmd Thread.print -l.

Wie erkennen Sie einen Deadlock im Dump?

Am Ende steht „Found one Java-level deadlock". Darunter: welcher Thread welchen Lock hält und welchen er will.

Findet die JVM auch Deadlocks mit ReentrantLock?

Ja, über ownable synchronizers. Nicht aber Warte-Zyklen über Pools, Semaphoren oder externe Ressourcen.

Wie verbindet sich jcmd unter Linux mit der JVM?

Es legt die Datei .attach_pid<pid> an und sendet SIGQUIT. Der Signal-Handler startet den Attach Listener. Dieser öffnet den Socket .java_pid<pid> im Temp-Verzeichnis, über den der Befehl läuft.

Zahlen

Was ist nid im Dump?

Die ID des OS-Threads in Hex. Mit ihr verbinden Sie top -H mit dem Java-Thread.

Wie finden Sie den Thread, der 100 % CPU verbraucht?

top -H -p <pid>, Thread-ID in Hex umrechnen, im Dump nid=0x… suchen. Dessen Stack über mehrere Dumps ansehen.

Pausiert ein Thread Dump die Anwendung?

Der klassische Dump braucht einen kurzen Safepoint. Bei sehr vielen Threads ist das spürbar. Der neue Dump mit dump_to_file pausiert laut JEP 444 nicht.

Wie viele Dumps ziehen Sie, und in welchem Abstand?

Drei Dumps im Abstand von 5–10 Sekunden. Nur der Vergleich zeigt, was feststeckt.

Vergleich

Was ist der Unterschied zwischen BLOCKED und WAITING?

BLOCKED wartet auf den Eintritt in einen synchronized-Monitor. WAITING wartet auf ein Signal, z. B. wait(), join() oder park().

jstack oder jcmd?

jcmd. Das Java-25-Manual nennt jstack experimentell und nicht unterstützt. jcmd kann zusätzlich JFR, Heap Dumps und mehr.

Was ist der Unterschied zwischen Thread Dump und Heap Dump?

Thread Dump: was die Threads gerade tun. Heap Dump: welche Objekte im Speicher liegen und wer sie hält.

Wann JFR statt Thread Dumps?

Bei seltenen oder kurzen Wartezeiten. JFR misst Lock-Wartezeiten über Zeit, ein Dump zeigt nur einen Moment.

Produktion

Wie ziehen Sie einen Thread Dump?

jcmd <pid> Thread.print -l. Alternativ jstack -l <pid> oder kill -3 <pid>, dann steht er im Log der JVM.

Wie bekommen Sie einen Dump aus einem Container ohne JDK?

kill -3 auf den Java-Prozess, dann steht der Dump im Container-Log. Oder ein Debug-Container mit JDK.

Szenario: Der Service antwortet nicht mehr, CPU ist bei 2 %. Was tun Sie?

Vor dem Neustart drei Dumps mit jcmd Thread.print -l ziehen. Ans Ende schauen (Deadlock?), dann BLOCKED-Threads und ihre Lock-Halter verfolgen. Typisch: Deadlock, leerer Connection Pool oder Call ohne Timeout.

Szenario: Der Pod hat dauerhaft 100 % CPU, die Latenz ist hoch. Wie gehen Sie vor?

top -H zeigt die heissen OS-Threads, nid im Dump zeigt den Java-Stack. Bleibt es eine App-Schleife, Code fixen. Sind es GC-Threads, GC-Log und Heap prüfen.

Szenario: Die Thread-Zahl steigt über Tage von 200 auf 8000. Was suchen Sie im Dump?

Die Namensmuster der neuen Threads, z. B. pool-N-thread-1 mit steigendem N. Das deutet auf pro Aufruf erzeugte, nie geschlossene Executors.

Design

Wie sehen Sie Virtual Threads?

Mit jcmd <pid> Thread.dump_to_file, als Text oder JSON. Der klassische Dump zeigt nur Carrier-Threads.

Was zeigt das JSON-Format zusätzlich?

Thread-Container wie Executors und StructuredTaskScopes mit Eltern-Beziehung. Ab Java 25 auch Zustand, Locks und Carrier.

Szenario: Wie bereiten Sie eine App auf einfache Diagnose vor?

Eigene ThreadFactory mit sprechenden Namen, Timeouts bei jedem Netzwerk-Aufruf und ein Runbook, das bei Alarm drei Dumps zieht und sichert.

Szenario: Ihre App nutzt Virtual Threads und hängt. Wie diagnostizieren Sie das?

Mit jcmd Thread.dump_to_file, denn der klassische Dump zeigt nur Carrier-Threads. Ab Java 25 enthält die Datei auch Zustand und Locks.

Mehr

Gerüst

  • Warum? Bei Hänger, Deadlock oder hoher CPU zeigt er, was jeder Thread gerade tut.
  • Wie innen? jcmd verbindet sich per Attach-Mechanismus. Der VM Thread schreibt den Dump in einem kurzen Safepoint. Die JVM erkennt Lock-Zyklen selbst.
  • Zahlen Drei Dumps im Abstand von 5–10 Sekunden. 6 Thread-Zustände. nid ist die OS-Thread-ID in Hex.
  • Vergleich Thread Dump: Wo hängt es jetzt? Heap Dump: Wer hält den Speicher? JFR: Wo geht die Zeit hin?
  • Produktion Hänger bei CPU fast 0 %: Deadlock, leerer Pool oder Call ohne Timeout. CPU 100 %: gleicher Stack in mehreren Dumps. Erst Dump, dann Neustart.
  • Design Sprechende Thread-Namen, Timeouts überall, Dumps im Runbook automatisieren. Bei Virtual Threads: dump_to_file.

Vergleich

  • Thread Dump: Momentaufnahme der Threads. Frage: „Wo hängt es jetzt?" Billig, wenige KB bis MB.
  • Heap Dump: alle Objekte im Heap. Frage: „Wer hält den Speicher?" Gross und pausiert lange. Seite Memory Leaks und OutOfMemoryError.
  • JFR-Aufnahme: Ereignisse über Zeit, z. B. Lock-Wartezeiten und CPU-Samples. Frage: „Wo geht die Zeit hin?" Seite Profiling.
  • Klassischer Dump vs Thread.dump_to_file: klassisch mit Locks, Adressen und JVM-Threads, aber ohne Virtual Threads. Neu mit Virtual Threads und JSON, ohne Safepoint-Pause.
  • Core Dump: Abbild des ganzen Prozesses für JVM-Abstürze. Auswertung mit jhsdb.

In der Produktion

  1. Service hängt, CPU fast 0 %: Typisch Deadlock, leerer Connection Pool oder Remote-Call ohne Timeout. Im Dump: viele Threads BLOCKED oder in getConnection. Lösung: Timeouts, feste Lock-Reihenfolge, Pool-Grösse prüfen.
  2. CPU 100 %: Dieselben Threads sind in mehreren Dumps RUNNABLE in derselben Schleife. Typisch: Endlosschleife, Regex-Backtracking, zu viel GC. Mit top -H und nid verbinden.
  3. Thread-Zahl wächst ständig: Dumps zeigen Hunderte pool-N-thread-M mit steigendem N. Ursache: pro Request ein neuer Executor, nie geschlossen. Lösung: einen Pool teilen und schliessen.
  4. Kein jcmd im Container: Das Image hat nur eine JRE. Lösung: kill -3 1 und das Pod-Log lesen. Oder ein Debug-Container mit JDK im selben Prozess-Namensraum.
  5. Attach scheitert: jcmd muss als gleicher Benutzer laufen und das gleiche Temp-Verzeichnis sehen. In Containern scheitert das oft. Dann hilft kill -3.
  6. Nur ein Dump gezogen: Ein einzelner Dump zeigt Zufall. Immer mehrere Dumps vergleichen, bevor man Schlüsse zieht.

Diagnose: Werkzeuge und Befehle

  • jps -l oder jcmd ohne Argument: Java-Prozesse und PIDs auflisten.
  • jcmd <pid> Thread.print -l: klassischer Dump mit j.u.c.-Locks.
  • jcmd <pid> Thread.dump_to_file -format=json datei.json: neuer Dump mit Virtual Threads (Java 21+). -overwrite erlaubt Überschreiben.
  • Drei Dumps im Abstand von 5 Sekunden per Schleife ziehen und als dump1.txt bis dump3.txt speichern.
  • kill -3 <pid>: Dump in die Standardausgabe der JVM.
  • top -H -p <pid> plus Umrechnung der Thread-ID in Hex: heissen Thread finden.
  • Analyse-Tools: fastThread, IBM TMDA, IntelliJ „Analyze Stack Trace". Sie gruppieren Threads mit gleichem Stack.
  • JFR: jdk.JavaMonitorEnter und jdk.ThreadPark zeigen Wartezeiten über Zeit, nicht nur einen Moment.

Senior-Punkte

  1. Thread-Namen sind Diagnose-Design. Eigene ThreadFactory mit Namen wie kafka-consumer-orders-1. Das spart im Incident Minuten.
  2. Dumps automatisieren: Ein Runbook oder Skript zieht bei Alarm drei Dumps und sichert sie. Der Neustart löscht sonst die Beweise.
  3. Erst Dump, dann Neustart. Ein Neustart behebt das Symptom. Ohne Dump bleibt die Ursache unbekannt.
  4. Dump ist ein Foto, JFR ein Film. Für seltene Lock-Wartezeiten ist eine JFR-Aufnahme oft besser als viele Dumps.
  5. Virtual Threads ändern das Werkzeug. Ab Java 21 braucht man Thread.dump_to_file. Ab Java 25 enthält es auch Zustand und Locks.
  6. Timeouts überall: Die meisten „Hänger" im Dump sind Netzwerk-Aufrufe ohne Timeout. Das ist eine Design-Regel, kein Tuning.
