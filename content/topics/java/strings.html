String

Kern: String ist eine unveränderliche (immutable) Zeichenfolge, und jede „Änderung" erzeugt ein neues Objekt. Gleiche Literale teilen sich ein Objekt im String Pool. Inhalt vergleicht man darum mit equals und nie mit ==.

Antwort-Muster

Frage: Warum ist String unveränderlich, und was ist der String Pool?

  1. Mechanismus: Ein String ist final, und sein Inhalt kann sich nie ändern. Gleiche Literale zeigen auf dieselbe Instanz im String Pool.
  2. Zahl: Der Hash wird einmal berechnet und im Objekt gespeichert. Latin-1-Text braucht 1 Byte pro Zeichen.
  3. Trade-off: Dafür erzeugt jede Änderung ein neues Objekt. In Schleifen wird += darum O(n²).
  4. Produktion: In der Produktion nutze ich equals für Inhalt und StringBuilder in Schleifen. Passwörter halte ich in char[].

1. Die Reise eines Strings

  1. javac: Jedes Literal kommt in den Constant Pool der Class-Datei. Konstante Ausdrücke wie "Be" + "rn" faltet javac schon hier zu "Bern".
  2. ldc: Beim ersten Ausführen des Befehls ldc legt die JVM den String in die StringTable. Spätere Aufrufe bekommen dieselbe Referenz.
  3. coder: Beim Erzeugen prüft String die Zeichen. Alle in Latin-1: 1 Byte pro Zeichen. Sonst UTF-16.
  4. hashCode: Der erste Aufruf rechnet s[0]*31^(n-1) + … + s[n-1] und speichert das Ergebnis im Feld hash.
  5. Verketten zur Laufzeit: teil + "rn" wird seit Java 9 zu invokedynamic makeConcatWithConstants (JEP 280). Das Ergebnis ist ein neues Objekt, nicht im Pool.
  6. intern(): sucht den Inhalt im Pool. Gefunden: Pool-Instanz zurück. Sonst wird dieser String eingetragen.
  7. GC: Auch Pool-Einträge werden abgeräumt, wenn niemand sie mehr referenziert.

2. Aufbau

  1. String-Objekt: hält ein byte[] value, ein Feld coder (LATIN1 oder UTF16) und den gecachten hash.
  2. String Pool: eine interne Hash-Tabelle (StringTable) im Heap. Sie hält eine Instanz pro Literal-Inhalt. Seit Java 7 liegt sie im Heap, nicht mehr in PermGen.
  3. Literale wie "Bern" zeigen auf den Pool. a und b sind dasselbe Objekt.
  4. new String("Bern") erzeugt ein eigenes Objekt ausserhalb des Pools. Es darf das byte[] mit dem Original teilen.
  5. Compact Strings (Java 9, JEP 254): Passt jedes Zeichen in Latin-1, braucht es 1 Byte. Sonst UTF-16 mit 2 Bytes.

3. Details, die Interviewer fragen

  1. Warum unveränderlich: Es gibt vier Gründe. Ein String ist ein sicherer HashMap-Schlüssel, weil der Hash gleich bleibt. Der Pool kann Instanzen teilen. Er ist thread-sicher ohne Lock. Ein geprüfter Pfad oder Klassenname kann sich danach nicht ändern.
  2. Wie unveränderlich: Die Klasse ist final. Das Feld value ist private final. Keine Methode ändert es. Reflection könnte es brechen. Das Modulsystem sperrt das standardmässig.
  3. String Pool / StringTable: Das ist eine native Hash-Tabelle mit Referenzen auf String-Objekte im Heap. Die Grösse steuert -XX:StringTableSize. In JDK 17 sind es 65536 Buckets, siehe oben.
  4. Literale auflösen: Löst die JVM ein Literal zum ersten Mal auf, prüft sie den Pool. Gibt es dort schon einen String mit gleichem Inhalt, nimmt sie diesen. Sonst legt sie ein neues Objekt an und trägt es in den Pool ein. Darum teilen sich gleiche Literale ein Objekt.
  5. intern(): Es gibt die kanonische Pool-Instanz zurück. Es ist nützlich bei sehr vielen Duplikaten aus Parsing. Es kostet eine Suche in der Tabelle. Pool-Einträge leben so lange, wie sie referenziert werden.
  6. Wie viele Objekte erzeugt new String("a")? Es sind bis zu zwei. Das Literal liegt im Pool, falls es noch nicht da ist. Dazu kommt das neue Objekt.
  7. Compile-Time-Konstanten (JLS §15.29): javac faltet Ausdrücke aus Literalen und final-Variablen mit Konstanten-Initialisierung. Sie landen im Pool.
  8. Verkettung: Seit Java 9 (JEP 280) wird a + b zu invokedynamic mit StringConcatFactory. Vorher erzeugte javac StringBuilder-Code. In Schleifen bleibt StringBuilder trotzdem nötig.
  9. StringBuilder vs StringBuffer: StringBuffer ist synchronized (Java 1.0). StringBuilder (Java 5) ist nicht synchronisiert und schneller. Lokale Puffer sind nie geteilt, also nimmt man StringBuilder.
  10. StringBuilder-Kapazität: Der Standard ist 16 Zeichen. Bei Bedarf wächst der Puffer auf etwa das Doppelte. Ist die Grösse bekannt, nutzt man new StringBuilder(n).
  11. hashCode-Formel: Der Hash ist s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1] in int-Arithmetik. Der leere String hat den Hash null. Der Wert wird beim ersten Aufruf berechnet und gespeichert.
  12. Compact Strings (JEP 254): Das Feld coder ist 0 (LATIN1) oder 1 (UTF16). Bei westlichem Text spart das etwa die Hälfte des Zeichenspeichers. Man kann es mit -XX:-CompactStrings abschalten. Das ist kaum sinnvoll.
  13. length() zählt UTF-16-Code-Units, keine Zeichen. Ein Emoji ausserhalb der BMP zählt 2. Echte Zeichen zählen codePointCount und codePoints().
  14. Text Blocks (Java 15, JEP 378): Das sind mehrzeilige Literale mit """. Die gemeinsame Einrückung wird entfernt. \ am Zeilenende unterdrückt den Umbruch. \s erhält ein Leerzeichen. Das Ergebnis ist ein normaler String.
  15. Passwörter in char[]: Ein Array kann man nach Gebrauch mit Nullen überschreiben. Ein String bleibt bis zum GC im Heap. In Heap Dumps ist er lesbar.
  16. String Deduplication: -XX:+UseStringDeduplication lässt den GC gleiche byte[] verschiedener Strings zusammenlegen. Die String-Objekte bleiben getrennt. == ändert sich nicht.
  17. switch auf String (Java 7): Er nutzt hashCode und dann equals. Ein null als Selektor wirft ohne case null eine NullPointerException.

4. Fallen

  • „s1 == s2 vergleicht den Inhalt.“ → Falsch. Es vergleicht Referenzen. Inhalt: equals.
  • „s.toUpperCase() ändert s.“ → Falsch. Es gibt einen neuen String zurück.
  • „javac macht aus + immer einen StringBuilder.“ → Veraltet. Seit Java 9 invokedynamic. Konstanten faltet javac direkt.
  • „Der String Pool liegt in PermGen.“ → Veraltet. Seit Java 7 im Heap; PermGen gibt es seit Java 8 nicht mehr.
  • „Pool-Strings werden nie aufgeräumt.“ → Falsch. Unreferenzierte Einträge räumt der GC ab.
  • „length() zählt Zeichen.“ → Ungenau. Es zählt UTF-16-Code-Units. Emojis zählen 2.
  • „Ein String braucht 2 Bytes pro Zeichen.“ → Veraltet. Seit Java 9 meist 1 Byte (Compact Strings).

5. Selbsttest

Warum?

Warum ist String unveränderlich?

Sicherer Map-Schlüssel mit stabilem Hash, Teilen im Pool, Thread-Sicherheit ohne Locks, und Sicherheit bei geprüften Werten wie Pfaden.

Warum StringBuilder in Schleifen?

+= erzeugt in jeder Runde einen neuen String und kopiert alles: O(n²). StringBuilder hängt in einen wachsenden Puffer an.

Warum Passwörter als char[] statt String?

Ein Array kann man nach Gebrauch löschen. Ein String bleibt bis zum GC im Heap und erscheint in Heap Dumps.

Warum ist String als HashMap-Schlüssel ideal?

Unveränderlich, korrektes equals, und der Hash wird gecacht.

Wie innen?

Was ist der String Pool?

Eine JVM-interne Tabelle mit einer Instanz pro Literal-Inhalt. Gleiche Literale zeigen auf dasselbe Objekt.

Wo liegt der String Pool?

Im Heap, seit Java 7. Die StringTable selbst ist eine native Hash-Tabelle mit Referenzen.

Was macht intern()?

Liefert die Pool-Instanz mit gleichem Inhalt. Gibt es keine, wird der String eingetragen.

Wie funktioniert String-Verkettung seit Java 9?

javac erzeugt invokedynamic mit StringConcatFactory.makeConcatWithConstants. Die JVM wählt zur Laufzeit eine optimierte Strategie.

Was sind Compact Strings?

Seit Java 9 speichert String Latin-1-Text mit 1 Byte pro Zeichen, sonst UTF-16. Das Feld coder merkt sich die Kodierung.

Was passiert, wenn ein langer Latin-1-String ein Emoji enthält?

Der ganze String wird UTF-16 und braucht doppelt so viel Speicher.

Was zählt length()?

UTF-16-Code-Units. Zeichen ausserhalb der BMP wie viele Emojis zählen 2. Für echte Zeichen codePointCount.

Was ist String Deduplication?

Eine GC-Option, die gleiche byte[] verschiedener Strings zusammenlegt. Die Objekte bleiben verschieden, nur der Inhalt wird geteilt.

Was macht die JVM, wenn sie ein Literal zum ersten Mal auflöst?

Sie sucht im Pool einen String mit gleichem Inhalt. Findet sie keinen, legt sie ein neues Objekt an und trägt es ein.

Zahlen

Wie viele Objekte erzeugt new String("abc")?

Eins oder zwei. Das Literal im Pool, falls noch nicht vorhanden, plus das neue Objekt.

Ist der hashCode eines Strings teuer?

Nur beim ersten Aufruf. Danach ist er im Objekt gespeichert.

Wie wird der hashCode eines Strings berechnet?

Mit der Formel s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1] in int-Arithmetik. Der leere String hat den Hash null.

Vergleich

Was ist der Unterschied zwischen == und equals bei Strings?

== vergleicht Referenzen, equals den Inhalt. Für Inhalt immer equals.

Ist "Be" + "rn" == "Bern"?

Ja. Das ist ein konstanter Ausdruck, javac faltet ihn zu einem Literal.

Und wenn "Be" in einer nicht-finalen Variable steht?

Dann ist es false. Die Verkettung passiert zur Laufzeit und erzeugt ein neues Objekt ausserhalb des Pools.

StringBuilder vs StringBuffer?

StringBuffer ist synchronisiert und langsamer. StringBuilder ist nicht synchronisiert und der Standard.

strip() vs trim()?

trim entfernt Zeichen bis U+0020. strip (Java 11) entfernt alle Unicode-Leerzeichen.

Produktion

Szenario: Ein Login-Vergleich funktioniert lokal, aber nicht mit Daten aus der DB. Warum?

Wahrscheinlich == statt equals. Lokal waren es Literale aus dem Pool, aus der DB neue Objekte.

Szenario: Ein Heap Dump zeigt 40 % Strings, viele mit gleichem Inhalt. Was tun?

In MAT „Duplicate Strings" prüfen und die Quelle finden, oft ein Parser. Dort deduplizieren oder G1 String Deduplication aktivieren.

Szenario: Ein Batch-Job baut eine CSV mit += und wird mit der Datenmenge quadratisch langsamer. Lösung?

StringBuilder mit geschätzter Kapazität oder direkt in einen Writer streamen. Dann ist der Aufwand linear.

Design

Was sind Text Blocks?

Mehrzeilige String-Literale mit """ seit Java 15. Gemeinsame Einrückung wird entfernt, das Ergebnis ist ein normaler String.

Was passiert bei new String(bytes) ohne Zeichensatz?

Der Standard-Zeichensatz wird genutzt, seit Java 18 UTF-8. Davor hing er vom Betriebssystem ab. Darum immer explizit angeben.

Ist switch auf String null-sicher?

Nein. Ein null-Selektor wirft eine NullPointerException, ausser es gibt case null (Pattern-switch, Java 21).

Mehr

Gerüst

  • Warum? Unveränderlich heisst sicherer Map-Schlüssel, teilbar im Pool und thread-sicher ohne Lock.
  • Wie innen? Ein byte[] plus coder (Compact Strings). Der Pool ist eine native Hash-Tabelle mit Referenzen auf Heap-Objekte.
  • Zahlen Latin-1 braucht 1 Byte pro Zeichen, UTF-16 braucht 2. StringBuilder startet mit 16 Zeichen. Der Hash wird einmal berechnet und gespeichert.
  • Vergleich StringBuilder: schnell, nicht synchronisiert. StringBuffer: synchronisiert. char[] für Passwörter, weil man es überschreiben kann.
  • Produktion == statt equals klappt nur bei Pool-Literalen. += in einer Schleife ist O(n²). Viele doppelte Strings füllen den Heap.
  • Design equals für Inhalt, StringBuilder in Schleifen. Zeichensatz immer explizit angeben.

  2. d entsteht zur Laufzeit und ist nicht im Pool. e ist eine Compile-Time-Konstante, weil fteil final ist. javac schreibt direkt ldc "Bern". d.intern() liefert die Pool-Instanz.

  6. += in einer Schleife kopiert jedes Mal den ganzen bisherigen Text: O(n²). StringBuilder hängt an einen wachsenden Puffer an: O(n).

Vergleich

  • ==: gleiche Referenz. Nur bei Pool-Strings zufällig richtig. Nie für Inhalt.
  • equals: gleicher Inhalt. "x".equals(s) ist null-sicher.
  • equalsIgnoreCase / compareTo: ohne Gross/Klein oder lexikografisch nach UTF-16-Werten. Für Sprachen: Collator.
  • String: unveränderlich, thread-sicher, poolbar.
  • StringBuilder: veränderbar, nicht thread-sicher, für Aufbau in Schleifen.
  • StringBuffer: veränderbar, synchronisiert, Altlast.
  • String.join / Collectors.joining / StringJoiner: Listen mit Trennzeichen verbinden.
  • String.format / formatted(): lesbar, aber deutlich langsamer als Verkettung. Nicht in heissen Pfaden.

In der Produktion

  1. Vergleich mit ==: Funktioniert im Test mit Literalen, scheitert mit Daten aus DB, JSON oder HTTP. Lösung: equals, und SonarQube-Regel aktivieren.
  2. Hohe Allokationsrate durch Verkettung in Schleifen oder Logs: log.debug("x=" + obj) baut den String auch bei abgeschaltetem Debug. Lösung: Platzhalter log.debug("x={}", obj).
  3. Viele doppelte Strings im Heap: z. B. Ländercodes aus Millionen geparster Zeilen. Lösung: Deduplizieren beim Parsen (eigene Map oder intern), oder UseStringDeduplication mit G1.
  4. Passwörter und Tokens in Heap Dumps: Strings bleiben lesbar. Lösung: char[] wo möglich, Heap Dumps wie Geheimnisse behandeln.
  5. Kaputte Umlaute: new String(bytes) ohne Zeichensatz nutzt den Standard der Plattform. Seit Java 18 (JEP 400) ist der Standard UTF-8; davor oft Windows-1252. Lösung: immer StandardCharsets.UTF_8 angeben.
  6. Doppelter Speicher bei einem einzelnen Sonderzeichen: Ein Emoji macht einen langen String zu UTF-16. Meist egal, bei riesigen Texten messbar.

Diagnose: Werkzeuge und Befehle

  • jcmd <pid> VM.stringtable: Statistik der StringTable (Einträge, Buckets).
  • jcmd <pid> GC.class_histogram: Anteil von java.lang.String und [B (byte[]) am Heap.
  • Eclipse MAT: Abfrage „Duplicate Strings" zeigt doppelte Inhalte im Heap Dump.
  • JFR mit Allocation-Profiling: findet Stellen mit vielen String- und StringBuilder-Allokationen.
  • javap -c: zeigt ldc (Konstante) und makeConcatWithConstants (Laufzeit-Verkettung).
  • -Xlog:stringdedup*=debug: zeigt, was String Deduplication spart.

Senior-Punkte

  1. Unveränderlichkeit ist ein Design-Vorbild. Dieselben Gründe (Thread-Sicherheit, sichere Schlüssel) gelten für eigene Wertobjekte und Records.
  2. intern() ist kein Standardwerkzeug. Nur nach Messung bei echten Duplikat-Problemen. Oft ist eine eigene Dedupe-Map oder Deduplication im GC besser.
  3. Verkettung ist heute schnell, ausser in Schleifen. Lesbarkeit zuerst, StringBuilder nur bei Wiederholung.
  4. Zeichensatz immer explizit. Das macht Verhalten unabhängig von Plattform und JDK-Version.
  5. Strings sind oft der grösste Heap-Anteil. Bei Speicherproblemen zuerst Histogramm und Duplikate anschauen.
