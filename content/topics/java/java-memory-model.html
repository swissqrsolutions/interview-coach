Java Memory Model

Kern: Das Java Memory Model (JMM) ist die Regel, welchen Wert ein Read in einem Thread sehen darf. Es löst das Problem, dass Compiler, JIT und CPU Code umordnen und Werte zwischenspeichern. Nur eine happens-before-Beziehung garantiert, dass ein Thread den Write eines anderen Threads sieht.

Antwort-Muster

Frage: Was garantiert das Java Memory Model?

  1. Mechanismus: Nur eine happens-before-Beziehung garantiert, dass ein Thread den Write eines anderen sieht, z. B. volatile Write vor volatile Read.
  2. Zahl: count++ sind drei Schritte. Im Beispiel gingen bis zu 35 % der Updates verloren.
  3. Trade-off: volatile gibt Sichtbarkeit ohne Lock, aber keine Atomarität. synchronized gibt beides, kostet aber gegenseitigen Ausschluss.
  4. Produktion: Ein Stop-Flag ist volatile, Zähler sind AtomicLong oder LongAdder.

1. Die Reise eines Writes zum anderen Thread

  1. Thread A schreibt data = 42. Das ist ein normaler Write. Er liegt vielleicht nur im Store Buffer. Thread B sieht ihn noch nicht.
  2. Thread A schreibt ready = true. Das Feld ist volatile. Ein volatile Write wirkt als Release: Alle Writes davor werden vorher sichtbar. Der JIT darf data = 42 nicht hinter diesen Write schieben.
  3. Thread B liest ready und sieht true. Ein volatile Read wirkt als Acquire: Spätere Reads dürfen nicht davor rutschen. Der Write in 2 synchronizes-with diesem Read.
  4. Thread B liest data. Die Kette 1 → 2 → 3 → 4 ist transitiv. Darum gilt: Write 1 happens-before Read 4. Thread B sieht garantiert 42.
  5. Ohne volatile auf ready gibt es keine Kette. Thread B darf dann ready nie sehen, oder ready = true sehen und trotzdem data = 0.

2. Aufbau

  1. Java-Code: Der Programmierer schreibt Reads und Writes auf Felder. Beispiel: x = 1; ready = true;.
  2. javac und JIT: Sie dürfen Befehle umordnen und einen Wert im Register halten. Das ist erlaubt, solange der eigene Thread keinen Unterschied merkt (as-if-serial).
  3. CPU: Sie schreibt erst in einen Store Buffer, also eine Warteschlange vor dem Cache. Sie führt Befehle auch Out-of-Order aus, also nicht in Code-Reihenfolge.
  4. Heap: Nur geteilte Variablen sind betroffen: Instanzfelder, static-Felder, Array-Elemente. Lokale Variablen gehören einem Thread allein.
  5. JMM: Es ist der Vertrag über allen Schichten. Es sagt nicht, wie die Hardware arbeitet. Es sagt, welche Ergebnisse ein Programm haben darf.

3. Details, die Interviewer fragen

  1. happens-before (hb): Wenn Aktion A happens-before B, dann sieht B alle Effekte von A. Das ist eine Garantie über Sichtbarkeit und Reihenfolge. Es geht nicht um Uhrzeit.
  2. Program Order und Transitivität: Das sind hb-Regeln aus JLS 17.4.5. Jede Aktion in einem Thread hb jede spätere im selben Thread. Wenn A hb B und B hb C gilt, dann gilt A hb C.
  3. Monitor und volatile: Das Verlassen von synchronized (unlock) hb jedes spätere Betreten mit demselben Lock. Ein Write auf ein volatile Feld hb jeden späteren Read desselben Felds.
  4. Thread-Regeln: t.start() hb jede Aktion im gestarteten Thread. Jede Aktion im Thread hb die Rückkehr von t.join() oder ein t.isAlive() == false. t.interrupt() hb den Moment, in dem t den Interrupt bemerkt. Das Setzen auf 0/null hb die erste Aktion jedes Threads.
  5. j.u.c.-Garantien: Die API-Doku von java.util.concurrent ergänzt Regeln. Ein put in eine ConcurrentHashMap oder BlockingQueue hb das get/take dieses Elements. submit an einen Executor hb den Start der Task. Das Ende der Task hb Future.get().
  6. Data Race: Ein Data Race sind zwei Zugriffe auf dieselbe Variable aus zwei Threads. Mindestens einer schreibt, und kein hb ordnet sie. Ein Programm ohne Data Races heisst korrekt synchronisiert.
  7. DRF-SC-Garantie: Ein korrekt synchronisiertes Programm verhält sich sequenziell konsistent. Das heisst, alle Aktionen laufen scheinbar in einer Reihenfolge. Diese passt zur Code-Reihenfolge jedes Threads.
  8. volatile: Es garantiert Sichtbarkeit und Ordnung (Release/Acquire). Es garantiert keine Atomarität für zusammengesetzte Operationen. Beispiele sind x++ oder „prüfen, dann setzen“.
  9. Reordering: Compiler, JIT und CPU dürfen unabhängige Befehle tauschen. Ein Thread merkt das bei sich selbst nie. Ein anderer Thread sieht ohne hb die Writes in beliebiger Reihenfolge.
  10. Atomarität von Reads und Writes: Reads und Writes von Referenzen, int, boolean usw. sind atomar. Bei nicht-volatile long und double darf die JVM in zwei 32-Bit-Hälften schreiben (Word Tearing, JLS 17.7). Mit volatile sind sie atomar.
  11. final-Felder (JLS 17.5): Nach Ende des Konstruktors sieht jeder Thread die final-Felder korrekt. Das gilt auch ohne Lock. Es gilt auch für Objekte, die über das final-Feld erreichbar sind. Bedingung ist, dass this nicht während des Konstruktors entkommt.
  12. synchronized: Es gibt gegenseitigen Ausschluss und Sichtbarkeit. Beim Unlock werden alle Writes sichtbar. Sie sind sichtbar für den nächsten, der denselben Lock nimmt.
  13. Safe Publication: Ein Objekt ist sicher veröffentlicht, wenn ein anderer Thread es nur über eine hb-Kante bekommt. Wege sind static-Initialisierer, volatile Feld oder AtomicReference, final Feld, Lock und Concurrent Collection.
  14. Double-Checked Locking: Das Singleton-Feld muss volatile sein. Sonst kann ein Thread die Referenz sehen, bevor der Konstruktor fertig ist. Einfacher ist das Holder-Idiom. Dabei wird die Klasse erst bei Bedarf initialisiert, und die JVM synchronisiert das.
  15. VarHandle (Java 9, JEP 193): Ein VarHandle gibt feine Zugriffsarten. Sie heissen plain, opaque, release/acquire und volatile. Dazu kommen CAS-Operationen. Das ist für Bibliotheks-Code und selten für Anwendungen.
  16. Thread.sleep und Thread.yield: Sie haben laut JLS 17.3 keine Synchronisations-Semantik. Der Compiler darf Felder trotz sleep im Register halten.

4. Fallen

  • „volatile macht count++ thread-sicher.“ → Falsch. Es macht nur jeden Read und Write sichtbar. Für ++ braucht es AtomicInteger oder einen Lock.
  • „happens-before heisst: passiert zeitlich vorher.“ → Falsch. Es ist eine Sichtbarkeitsgarantie. Zeitlich frühere Writes ohne hb dürfen unsichtbar bleiben.
  • „synchronized dient nur dem gegenseitigen Ausschluss.“ → Falsch. Es sorgt auch für Sichtbarkeit. Auch Reads brauchen denselben Lock.
  • „Auf x86 braucht man kein volatile.“ → Falsch. Der JIT ordnet unabhängig von der CPU um. Das Demo oben hing auf x86.
  • „final macht ein Objekt unveränderlich.“ → Falsch. Nur die Referenz ist fest. Eine final List bleibt veränderbar.
  • „long lesen und schreiben ist immer atomar.“ → Falsch. Nur mit volatile garantiert (JLS 17.7). 64-Bit-HotSpot macht es in der Praxis atomar.
  • „Thread.sleep() in der Schleife lässt das Flag erscheinen.“ → Falsch. sleep hat keine Synchronisations-Semantik (JLS 17.3).
  • „Double-Checked Locking ohne volatile ist ok.“ → Falsch. Ein Thread kann ein halb gebautes Objekt sehen.

5. Selbsttest

Warum?

Welches Problem löst das JMM?

Compiler, JIT und CPU ordnen um und speichern Werte zwischen. Ohne Regeln wäre nebenläufiger Code nicht portabel. Das JMM sagt, wann ein Write für einen anderen Thread sichtbar ist.

Warum hängt eine Schleife mit nicht-volatile Flag?

C2 liest das Flag nur einmal vor der Schleife (Hoisting). Das ist erlaubt, weil der Thread keine happens-before-Kante zum Writer hat.

Warum braucht Double-Checked Locking volatile?

Ohne volatile darf die Referenz sichtbar werden, bevor der Konstruktor fertig ist. Ein Thread sieht dann ein halb gebautes Objekt.

Warum zeigen sich Memory-Model-Bugs auf ARM öfter?

ARM hat ein schwächeres Hardware-Speichermodell als x86. Die CPU ordnet mehr um. Fehlende happens-before-Kanten fallen dort eher auf.

Wie innen?

Was ist das Java Memory Model?

Die Regel aus JLS Kapitel 17, welchen Wert ein Read sehen darf. Es erlaubt Optimierungen durch Umordnen und gibt mit happens-before klare Garantien.

Was bedeutet happens-before?

Wenn A happens-before B, sieht B alle Effekte von A. Es ist eine Garantie über Sichtbarkeit und Ordnung, nicht über Zeit.

Nennen Sie die wichtigsten happens-before-Regeln.

Program Order, Unlock vor späterem Lock desselben Monitors, volatile Write vor späterem Read, Thread.start vor dem Thread, Thread-Ende vor join, dazu Transitivität.

Was ist ein Data Race?

Zwei Threads greifen auf dieselbe Variable zu, mindestens einer schreibt, und kein happens-before ordnet die Zugriffe. Dann sind auch „unmögliche“ Werte erlaubt.

Was garantiert ein korrekt synchronisiertes Programm?

Sequenzielle Konsistenz (DRF-SC). Es verhält sich, als ob alle Aktionen in einer Reihenfolge laufen, die zur Code-Reihenfolge jedes Threads passt.

Was macht volatile genau?

Jeder Read sieht den letzten Write. Ein volatile Write ist ein Release, ein volatile Read ein Acquire. Writes davor werden mit sichtbar.

Was ist Reordering?

Compiler, JIT oder CPU tauschen die Reihenfolge unabhängiger Befehle. Der eigene Thread merkt nichts (as-if-serial). Andere Threads sehen ohne happens-before eine andere Reihenfolge.

Was garantiert final im JMM?

Nach dem Konstruktor sieht jeder Thread die final-Felder korrekt, auch ohne Lock. Bedingung: this entkommt nicht während des Konstruktors.

Was heisst „this entkommt im Konstruktor“?

Der Konstruktor gibt this weiter, z. B. an einen Listener oder Thread. Ein anderer Thread kann das Objekt dann vor Ende des Konstruktors sehen, auch mit Default-Werten in final-Feldern.

Sind long und double atomar?

Nicht garantiert ohne volatile. Die JLS (17.7) erlaubt zwei 32-Bit-Writes. Mit volatile sind sie atomar.

Was gibt synchronized ausser gegenseitigem Ausschluss?

Sichtbarkeit. Alles vor dem Unlock ist sichtbar für den Thread, der denselben Lock als Nächstes nimmt.

Was ist Safe Publication?

Ein anderer Thread bekommt das Objekt nur über eine happens-before-Kante. Wege: static-Initialisierer, volatile oder AtomicReference, final Feld, Lock, Concurrent Collection.

Was ist das Holder-Idiom?

Eine statische innere Klasse hält das Singleton. Die JVM initialisiert sie beim ersten Zugriff thread-sicher. Kein volatile und kein Lock nötig.

Welche happens-before-Garantien gibt java.util.concurrent?

Ein put in eine Concurrent Collection hb das spätere get. submit hb den Start der Task. Das Ende der Task hb Future.get().

Hat Thread.sleep Synchronisations-Semantik?

Nein. JLS 17.3 sagt das ausdrücklich. Der Compiler darf ein Feld trotz sleep im Register halten.

Was ist ein VarHandle?

Ein typisierter Zeiger auf ein Feld oder Array-Element (Java 9). Er bietet Zugriffsarten wie plain, opaque, acquire/release, volatile und CAS.

Ist eine unveränderliche Klasse automatisch thread-sicher?

Ja, wenn alle Felder final sind und this im Konstruktor nicht entkommt. Dann ist sie sogar über einen Data Race sicher lesbar.

Zahlen

Wie viele Updates verliert count++ im Beispiel?

Bis zu 35 %. Ein Lauf ergab 3218797 statt 4000000. AtomicInteger verlor nichts.

Wie viele Schritte hat count++?

Drei: lesen, plus 1, schreiben. Zwei Threads können denselben Wert lesen.

Was ist Word Tearing?

Bei nicht-volatile long und double darf die JVM in zwei 32-Bit-Hälften schreiben (JLS 17.7). Mit volatile sind sie atomar.

Seit wann gibt es VarHandle?

Seit Java 9 (JEP 193). Es bietet plain, opaque, release/acquire und volatile.

Vergleich

Ist volatile genug für einen Zähler?

Nein. count++ ist lesen, rechnen, schreiben. Zwei Threads können denselben Wert lesen. Lösung: AtomicInteger, LongAdder oder Lock.

volatile oder AtomicInteger?

volatile für ein Flag oder eine Referenz, die nur gesetzt wird. AtomicInteger, wenn der neue Wert vom alten abhängt, z. B. Zähler oder CAS.

AtomicLong oder LongAdder?

LongAdder ist bei vielen schreibenden Threads schneller, weil er auf Zellen verteilt. AtomicLong, wenn man einen exakten Wert oder CAS braucht.

volatile, synchronized oder ReentrantLock?

volatile gibt Sichtbarkeit und Ordnung für ein Feld. synchronized gibt zusätzlich gegenseitigen Ausschluss. ReentrantLock hat dieselben JMM-Garantien, dazu tryLock, Timeout, Fairness und mehrere Conditions.

Produktion

Szenario: Ein Worker-Thread reagiert nicht auf running = false. Was prüfen Sie?

Ob running volatile ist. Im Thread Dump steht der Thread RUNNABLE in der Schleife. Lösung: volatile, AtomicBoolean oder Interrupt nutzen.

Szenario: Ein Request-Zähler zeigt unter Last weniger Requests als das Load-Balancer-Log. Warum?

Mehrere Threads machen count++ ohne Synchronisation und verlieren Updates. Lösung: LongAdder oder AtomicLong, oder eine Metrik-Bibliothek wie Micrometer.

Szenario: Selten gibt ein Singleton eine NullPointerException aus einem Feld, das im Konstruktor gesetzt wird. Woran denken Sie?

An Double-Checked Locking ohne volatile oder an this, das im Konstruktor entkommt. Lösung: volatile, Holder-Idiom oder enum-Singleton. Mit jcstress nachweisen.

Wie finden Sie ein Flag, das nie ankommt?

Im Thread Dump steht der Thread immer RUNNABLE in derselben Schleife. Mit -Xint prüfen, ob der Bug verschwindet. Dann ist ein JIT-Hoisting wahrscheinlich.

Wie testen Sie nebenläufigen Code auf Memory-Model-Bugs?

Mit jcstress, das Code millionenfach laufen lässt. Tests auf einer ARM-Maschine finden Reordering-Bugs eher.

Design

Wie vermeiden Sie JMM-Probleme im Design?

Unveränderlichkeit zuerst. final-Felder und Records brauchen keine Synchronisation. Geteilter veränderbarer Zustand ist die Fehlerquelle.

Welche Werkzeuge bevorzugen Sie?

Executor, ConcurrentHashMap, BlockingQueue und CompletableFuture. Sie bringen die hb-Kanten schon mit.

Wie veröffentlichen Sie eine neu geladene Konfiguration?

Über eine volatile Referenz auf eine unveränderliche Map, z. B. mit Map.copyOf.

Wann schreiben Sie lock-freien Code?

Fast nur in Bibliotheken. Er braucht jcstress-Tests und Reviews.

Mehr

Gerüst

  • Warum? Compiler, JIT und CPU ordnen um und speichern Werte zwischen. Ohne Regeln wäre nebenläufiger Code nicht portabel.
  • Wie innen? happens-before-Kanten durch volatile, synchronized, Thread.start/join und final. Volatile Write ist Release, volatile Read ist Acquire. Data Race heisst kein hb.
  • Zahlen count++ verlor im Beispiel bis zu 35 % der Updates. Word Tearing bei long/double in zwei 32-Bit-Hälften. VarHandle seit Java 9.
  • Vergleich volatile, synchronized, ReentrantLock, Atomic, LongAdder, final.
  • Produktion Stop-Flag ohne volatile: Der Worker stoppt nie. Double-Checked Locking ohne volatile. Bug nur auf ARM.
  • Design Unveränderlichkeit zuerst. High-Level-Werkzeuge nutzen. Lock-freier Code ist Experten-Code.

Beispiel: ein Flag, das nie ankommt

public class JmmDemo {
  static boolean stop;              // nicht volatile
  static volatile boolean vstop;    // volatile
  static int count;                 // count++ ohne Lock
  static AtomicInteger atomic = new AtomicInteger();

  public static void main(String[] args) throws Exception {
    Thread t1 = new Thread(() -> { long n = 0; while (!stop) n++; });
    t1.start(); Thread.sleep(1000);
    stop = true;  t1.join(3000);                       // höchstens 3 s warten
    System.out.println("1) plain flag:    alive after 3 s = " + t1.isAlive());

    Thread t2 = new Thread(() -> { long n = 0; while (!vstop) n++; });
    t2.start(); Thread.sleep(1000);
    vstop = true; t2.join(3000);
    System.out.println("2) volatile flag: alive after 3 s = " + t2.isAlive());

    // 4 Threads, je 1_000_000 Mal: count++ und atomic.incrementAndGet()
    ...
    System.exit(0);                                    // t1 läuft sonst endlos
  }
}
$ java JmmDemo
1) plain flag:    alive after 3 s = true
2) volatile flag: alive after 3 s = false
3) count++ = 3218797, AtomicInteger = 4000000 (expected 4000000)

$ java -Xint JmmDemo
1) plain flag:    alive after 3 s = false
2) volatile flag: alive after 3 s = false
3) count++ = 3979650, AtomicInteger = 4000000 (expected 4000000)

Echte Ausgabe, OpenJDK 17.0.3 (HotSpot, x86-64, Windows). Teil 3) ist im Code gekürzt. Drei Läufe mit JIT: Thread 1 hing jedes Mal; count++ ergab 3218797, 3223622 und 2590697. Java 21 und 25 verhalten sich gleich, weil das JMM gleich ist. Das Hängen ist aber nur erlaubt, nicht garantiert.

  1. Plain Flag: Thread 1 läuft auch nach 3 Sekunden weiter. Der C2-Compiler sieht keinen Write auf stop in der Schleife. Er liest stop darum nur einmal vor der Schleife (Hoisting). Das ist erlaubt, weil kein happens-before existiert.
  2. Volatile Flag: Thread 2 endet sofort. Ein volatile Read muss jedes Mal den aktuellen Wert holen.
  3. Mit -Xint (nur Interpreter) endet sogar Thread 1. Der Interpreter liest das Feld jedes Mal. Das beweist: Der Bug entsteht durch den JIT, nicht durch den Cache. Korrekt ist der Code trotzdem nicht.
  4. Atomarität: count++ verliert bis zu 35 % der Updates. count++ sind drei Schritte: lesen, plus 1, schreiben. AtomicInteger nutzt CAS (Compare-and-Swap) und verliert nichts.

Vergleich

  • volatile: Sichtbarkeit und Ordnung für ein Feld. Kein Lock, keine Atomarität für x++. Gut für Flags und für eine Referenz auf ein unveränderliches Objekt.
  • synchronized: Sichtbarkeit, Ordnung und gegenseitiger Ausschluss. Gut für mehrere Felder, die zusammen stimmen müssen.
  • ReentrantLock: gleiche JMM-Garantien wie synchronized. Dazu tryLock, Timeout, Fairness, mehrere Conditions.
  • AtomicInteger / AtomicReference: volatile-Semantik plus atomare CAS-Operationen. Gut für Zähler und lock-freie Updates einer Variable.
  • LongAdder: Zähler mit mehreren Zellen. Schneller als AtomicLong bei vielen schreibenden Threads. sum() ist kein exakter Schnappschuss.
  • final: sichere Veröffentlichung nach dem Konstruktor. Keine spätere Änderung möglich. Basis für unveränderliche Objekte und Records.
  • Concurrent Collections: ConcurrentHashMap, BlockingQueue: Übergabe zwischen Threads mit eingebautem hb.

In der Produktion

  1. Worker stoppt nie beim Shutdown: Ein running-Flag ist nicht volatile. Der JIT hat den Read aus der Schleife gezogen. Lösung: volatile, AtomicBoolean oder Interrupt.
  2. Zähler oder Metriken sind zu klein: count++ auf einem geteilten Feld verliert Updates. Lösung: AtomicLong, LongAdder oder ein Lock.
  3. Halb initialisiertes Objekt: Double-Checked Locking ohne volatile liefert ein Objekt mit null-Feldern. Lösung: volatile, Holder-Idiom oder ein enum-Singleton.
  4. Konfiguration wird neu geladen, aber nicht gesehen: Ein Thread ersetzt eine Map in einem normalen Feld. Lösung: volatile-Referenz auf eine unveränderliche Map (Map.copyOf).
  5. Läuft auf x86, bricht auf ARM: ARM-CPUs (z. B. AWS Graviton, Apple Silicon) ordnen stärker um als x86. Fehlende Synchronisation zeigt sich dort öfter. Lösung: Code gegen das JMM schreiben, nicht gegen die Hardware.
  6. Bug verschwindet im Debugger: Ein Breakpoint oder ein println ändert das Timing und das JIT-Verhalten. Lösung: Ursache im Code suchen, nicht im Laufzeitverhalten.

Diagnose: Werkzeuge und Flags

  • jcstress (OpenJDK Code Tools): testet nebenläufigen Code millionenfach und zählt erlaubte und verbotene Ergebnisse.
  • -Xint: nur Interpreter. Verschwindet der Bug, ist eine JIT-Optimierung wie Hoisting wahrscheinlich. Nur zum Prüfen einer Hypothese.
  • Thread Dump (jcmd <pid> Thread.print): Ein Thread steht immer RUNNABLE in derselben Schleife. Das deutet auf ein nie gesehenes Flag hin.
  • -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly (braucht hsdis): zeigt den Maschinencode, z. B. ob ein Read in der Schleife fehlt.
  • Statische Analyse: SpotBugs (z. B. inkonsistente Synchronisation), Error Prone mit @GuardedBy.
  • Stresstests auf ARM: Tests auf einer ARM-Maschine finden Reordering-Bugs eher.

Senior-Punkte

  1. Gegen das JMM programmieren, nicht gegen die CPU. „Auf x86 geht es“ ist kein Beweis. Unser Demo hing auf x86 wegen des JIT.
  2. Unveränderlichkeit zuerst. final-Felder und Records brauchen keine Synchronisation. Geteilter veränderbarer Zustand ist die eigentliche Fehlerquelle.
  3. High-Level-Werkzeuge bevorzugen: Executor, ConcurrentHashMap, BlockingQueue, CompletableFuture. Sie bringen die hb-Kanten schon mit.
  4. volatile hat Kosten. Ein volatile Write braucht auf x86 eine Store-Load-Barriere. Ein volatile Read verhindert Hoisting. In heissen Schleifen zählt das.
  5. Lock-freier Code ist Experten-Code. Ihn schreiben fast nur Bibliotheken. Er braucht jcstress-Tests und Reviews.
  6. „Benign Data Races“ (z. B. der Hash-Cache in String) sind Sonderfälle im JDK. In Anwendungscode sind sie ein Risiko ohne Nutzen.
