Class Loading

Java · Tier 2 · Quellen: Java SE 25 API (java.lang.ClassLoader, Class.forName, ServiceLoader), JVM Specification SE 21/25 Kap. 5 (Loading, Linking, Initializing), JLS 21 §12.4 und §12.7, JEP 261 (Module System), JEP 220 (Modular Run-Time Images), JEP 371 (Hidden Classes), JEP 483 (AOT Class Loading & Linking)

Kern: Class Loading ist der Weg, auf dem die JVM eine Klasse zur Laufzeit findet, prüft und vorbereitet. Es löst das Problem, dass Klassen erst bei Bedarf und aus verschiedenen Quellen kommen: JDK, Classpath, Plugins. Eine Klasse ist in der JVM eindeutig durch Name plus ClassLoader.

1. Wo sitzen die ClassLoader?

  1. Bootstrap ClassLoader: ist in die JVM eingebaut und hat keinen Parent. Er lädt die Kernmodule wie java.base. In Java ist er null. Beispiel: String.class.getClassLoader() gibt null.
  2. Platform ClassLoader: lädt weitere Java-SE- und JDK-Module. Er ersetzt seit Java 9 den alten Extension ClassLoader. Beispiel: java.sql.Connection.
  3. App ClassLoader (auch System ClassLoader): lädt Klassen vom Classpath und Module Path. Beispiel: deine Klasse Main.
  4. Eigene ClassLoader: laden Klassen aus anderen Quellen, z. B. pro Webapp in Tomcat. Ihr Standard-Parent ist der App ClassLoader.
  5. Parent Delegation: Ein Loader fragt zuerst seinen Parent. Nur wenn der nichts findet, sucht er selbst. So kann niemand java.lang.String ersetzen.
  6. Module seit Java 9: Platform und App Loader kennen die Zuordnung Paket → Modul. Liegt das Paket in einem benannten Modul, geht die Anfrage direkt an dessen Loader (JEP 261).

2. Die Reise einer Klasse (die Geschichte zum Merken)

  1. Auslöser: Der Code nutzt Lazy zum ersten Mal. Die JVM fragt den Loader der aufrufenden Klasse: „Lade Lazy.“
  2. Loading: Der Loader prüft findLoadedClass, also ob er die Klasse schon hat. Dann fragt er seinen Parent. Findet keiner sie, liest er die Bytes selbst und ruft defineClass. Die JVM baut die Metadaten im Metaspace und ein Class-Objekt im Heap.
  3. Verify: Der Verifier prüft den Bytecode: korrekte Typen, kein Stack-Überlauf, keine falschen Sprünge. Fehler: VerifyError.
  4. Prepare: Die JVM legt die static-Felder an und setzt sie auf Standardwerte (0, null, false). Es läuft noch kein Java-Code.
  5. Resolve: Symbolische Referenzen im Constant Pool werden zu echten Referenzen. HotSpot macht das lazy, also erst beim ersten Ausführen der Stelle.
  6. Initialization: Die JVM führt <clinit> aus: alle static-Zuweisungen und static-Blöcke in Textreihenfolge. Zuerst wird die Oberklasse initialisiert. Das passiert genau einmal, thread-sicher unter einem Lock.
  7. Benutzen: Ab jetzt sind new, statische Aufrufe und Felder frei. Die Klasse bleibt geladen.
  8. Unloading: Eine Klasse verschwindet nur, wenn ihr ClassLoader nicht mehr erreichbar ist. Dann räumt der GC alle seine Klassen ab. Klassen der drei eingebauten Loader werden nie entladen.

Auslöser für Initialization (JLS §12.4.1): new, Aufruf einer static-Methode, Zugriff auf ein static-Feld (keine Konstante), Class.forName(name), Initialisierung einer Unterklasse, die Startklasse mit main.

3. Beispiel: Loader, Delegation und Initialisierung sehen

public class LoaderDemo {
  public static class Lazy {
    public Lazy() {}
    static final int CONST = 42;          // Compile-Zeit-Konstante
    static int counter = 7;
    static { System.out.println("  >> Lazy wird initialisiert"); }
  }

  public static void main(String[] args) throws Exception {
    System.out.println("1) Wer laedt welche Klasse?");
    for (Class<?> c : new Class<?>[]{String.class, java.sql.Connection.class, LoaderDemo.class})
      System.out.printf("  %-20s -> %s%n", c.getSimpleName(), c.getClassLoader());

    System.out.println("2) Kette der Eltern");
    for (ClassLoader l = LoaderDemo.class.getClassLoader(); l != null; l = l.getParent())
      System.out.println("  " + l.getName() + "  (" + l.getClass().getName() + ")");
    System.out.println("  null = Bootstrap ClassLoader");

    System.out.println("3) Laden ist nicht Initialisieren");
    System.out.println("  CONST = " + Lazy.CONST);
    ClassLoader app = LoaderDemo.class.getClassLoader();
    Class<?> c = Class.forName("LoaderDemo$Lazy", false, app);
    System.out.println("  geladen: " + c.getName() + ", noch kein static-Block");
    System.out.println("  counter = " + Lazy.counter);

    System.out.println("4) Gleicher Name, anderer Loader");
    var url = LoaderDemo.class.getProtectionDomain().getCodeSource().getLocation();
    try (var isolated = new java.net.URLClassLoader(new java.net.URL[]{url}, null)) {
      Class<?> other = isolated.loadClass("LoaderDemo$Lazy");
      System.out.println("  gleicher Name: " + other.getName().equals(Lazy.class.getName()));
      System.out.println("  gleiche Klasse: " + (other == Lazy.class));
      try { Object o = other.getDeclaredConstructor().newInstance(); Lazy l = (Lazy) o; }
      catch (ClassCastException e) { System.out.println("  " + e.getMessage()); }
    }
  }
}

4. Details, die Interviewer fragen

  1. loadClass-Algorithmus: (1) findLoadedClass, (2) parent.loadClass oder Bootstrap bei Parent null, (3) findClass. Eigene Loader überschreiben meist nur findClass.
  2. Defining vs. Initiating Loader: Der Defining Loader ruft defineClass auf und besitzt die Klasse. Ein Initiating Loader hat nur delegiert. getClassLoader() gibt den Defining Loader.
  3. Identität einer Klasse: Laufzeit-Typ = binärer Name + Defining Loader. Darum gibt es ClassCastException: X cannot be cast to X und LinkageError: loader constraint violation.
  4. Class.forName vs. loadClass: Class.forName(name) nutzt den Loader des Aufrufers und initialisiert. ClassLoader.loadClass(name) lädt nur. Class.forName(name, false, loader) lädt ohne Initialisieren.
  5. Thread Context ClassLoader (TCCL): ein Loader, der an jedem Thread hängt (Thread.getContextClassLoader()). Er löst das Problem, dass Code im JDK keine App-Klassen sieht. ServiceLoader.load(Class) nutzt ihn, ebenso viele Frameworks.
  6. ServiceLoader: findet Implementierungen über META-INF/services/ oder provides in module-info.java. Beispiel: JDBC-Treiber, SLF4J-Bindings.
  7. Child-first: Manche Loader suchen zuerst selbst, dann beim Parent. Beispiele: Tomcat-Webapp-Loader (ausser java.*), Flink (classloader.resolve-order: child-first), Spark mit spark.driver.userClassPathFirst. Ziel: eigene Bibliotheksversion statt der des Containers.
  8. Parallel Capable: Ein Loader, der registerAsParallelCapable() aufruft, sperrt pro Klassenname statt den ganzen Loader. Die eingebauten Loader sind parallel capable. Ohne das drohen Deadlocks bei nicht-hierarchischer Delegation.
  9. Initialisierungs-Reihenfolge: Oberklasse vor Unterklasse. Innerhalb der Klasse: static-Felder und -Blöcke in Textreihenfolge. Interfaces werden nicht mit initialisiert, ausser sie haben default-Methoden und werden gebraucht.
  10. Lazy Holder Idiom: Ein Singleton in einer inneren static-Klasse wird erst beim ersten Zugriff gebaut. Die JVM garantiert Thread-Sicherheit über das Init-Lock, ohne synchronized.
  11. Fehler beim Laden:
    • ClassNotFoundException (checked): Suche per Name schlägt fehl, z. B. Class.forName("x.Y").
    • NoClassDefFoundError: Klasse war beim Kompilieren da, fehlt aber zur Laufzeit. Oder ihre Initialisierung ist schon einmal gescheitert: „Could not initialize class X“.
    • ExceptionInInitializerError: Exception im static-Block, beim ersten Versuch.
    • UnsupportedClassVersionError: Class-Datei zu neu. Version 61 = Java 17, 65 = Java 21, 69 = Java 25.
  12. Hidden Classes (Java 15, JEP 371): Klassen ohne findbaren Namen, erzeugt mit Lookup.defineHiddenClass. Lambdas und Frameworks nutzen sie. Sie können einzeln entladen werden.
  13. AOT Cache (Java 24, JEP 483): speichert Klassen schon geladen und gelinkt aus einem Trainingslauf. Java 25 vereinfacht das mit -XX:AOTCacheOutput (JEP 514). Ergebnis: schnellerer Start.

5. Vergleich

  • Bootstrap: in der JVM, null in Java, lädt java.base und weitere Kernmodule. Keine Parent.
  • Platform: Name "platform", lädt z. B. java.sql. Parent: Bootstrap. Seit Java 9.
  • App/System: Name "app", lädt Classpath und Module Path. Parent: Platform. Startet meist die Anwendung.
  • Extension ClassLoader (bis Java 8): lud jre/lib/ext. Mit Java 9 entfernt, die Rolle übernimmt der Platform Loader.
  • Classpath vs. Module Path: Classpath: alles in einem unnamed module, keine Kapselung, Duplikate möglich. Module Path: benannte Module, klare Abhängigkeiten, ein Paket gehört nur zu einem Modul.
  • Parent-first vs. Child-first: Parent-first schützt die Kernklassen. Child-first erlaubt eigene Versionen, birgt aber Konflikte mit geteilten Typen.
  • Class.forName vs. loadClass: initialisiert vs. lädt nur.

6. In der Produktion

  1. JAR Hell: Zwei Versionen derselben Bibliothek im Classpath. Die erste gewinnt, Methoden fehlen: NoSuchMethodError. Lösung: mvn dependency:tree, Versionen fixieren, Duplikate ausschliessen.
  2. NoClassDefFoundError: Could not initialize class X: Der static-Block ist früher gescheitert. Die Ursache steht nur beim ersten Fehler: ExceptionInInitializerError. Lösung: im Log nach dem ersten Fehler suchen.
  3. Metaspace-Leak nach Redeploy: Ein Thread, ThreadLocal oder JDBC-Treiber hält den alten Webapp-Loader. Seine Klassen bleiben. Lösung: Ressourcen beim Undeploy freigeben, Treiber deregistrieren, Heap Dump prüfen.
  4. X cannot be cast to X: Dieselbe Klasse wurde von zwei Loadern geladen. Häufig bei Plugins, Hot Reload (Spring DevTools) oder Spark/Flink mit Child-first. Lösung: geteilte Typen nur im Parent-Loader halten.
  5. ServiceLoader findet nichts: Falscher TCCL in einem Thread-Pool oder fehlende META-INF/services-Datei nach Shade/Fat-JAR. Lösung: Service-Dateien beim Shade mergen, TCCL bewusst setzen.
  6. UnsupportedClassVersionError: Mit Java 21 gebaut, auf Java 17 gestartet. Lösung: --release beim Kompilieren setzen oder die Runtime anheben.
  7. Langsamer Start mit vielen Klassen: Spring-Apps laden oft über 10 000 Klassen. Lösung: AppCDS (-XX:ArchiveClassesAtExit) oder AOT Cache ab Java 24.

7. Diagnose: Werkzeuge, Flags, Befehle

  • -verbose:class oder -Xlog:class+load: jede geladene Klasse mit Quelle. -Xlog:class+unload: entladene Klassen.
  • jcmd <pid> VM.classloaders: Baum der Loader. Echte Ausgabe (JDK 17): 
    +-- <bootstrap>
      +-- "platform", jdk.internal.loader.ClassLoaders$PlatformClassLoader
            +-- "app", jdk.internal.loader.ClassLoaders$AppClassLoader
  • jcmd <pid> VM.classloader_stats: Klassen und Metaspace pro Loader. Gut für Leaks.
  • jcmd <pid> VM.metaspace: Metaspace-Verbrauch im Detail.
  • jcmd <pid> GC.class_histogram: Anzahl Objekte pro Klasse.
  • java --show-module-resolution: welche Module aufgelöst werden.
  • javap -v X.class | grep major: Class-Datei-Version.
  • jdeps: Abhängigkeiten und Nutzung interner JDK-APIs.
  • Im Code: X.class.getClassLoader(), getParent(), X.class.getProtectionDomain().getCodeSource() (aus welchem JAR?).
  • Heap Dump mit Eclipse MAT: „Path to GC Roots“ vom alten ClassLoader zeigt, wer ihn festhält.

8. Senior-Punkte

  1. Parent Delegation ist ein Sicherheits- und Konsistenz-Mechanismus. Kernklassen gibt es nur einmal. Child-first bricht das bewusst für Isolation.
  2. Isolation kostet: Jeder eigene Loader lädt Klassen neu, braucht Metaspace und kann lecken. Nur einsetzen, wo Plugins oder Mandanten getrennt sein müssen.
  3. Geteilte Typen gehören in den Parent. Schnittstellen zwischen Host und Plugin müssen vom gleichen Loader kommen. Sonst gibt es ClassCastException.
  4. Static-Initialisierung ist riskant: Netzwerk, Dateien oder Konfiguration im static-Block machen die Klasse dauerhaft unbrauchbar, wenn sie einmal scheitert.
  5. Module Path statt Classpath lohnt sich für Bibliotheken und grosse Systeme: Duplikate und Split Packages fallen beim Start auf, nicht zur Laufzeit.
  6. Startzeit ist Class-Loading-Zeit. Weniger Abhängigkeiten, AppCDS oder AOT Cache bringen oft mehr als JVM-Flags.

10. Fallen

  • „Es gibt Bootstrap, Extension und Application ClassLoader.“ → Veraltet. Seit Java 9 heisst der mittlere Platform ClassLoader. Der Extension-Mechanismus ist entfernt.
  • „Der Bootstrap Loader lädt rt.jar.“ → Veraltet. Seit Java 9 gibt es kein rt.jar. Die Klassen kommen aus Modulen im JDK-Image (jrt:/) oder aus dem CDS-Archiv.
  • „Laden und Initialisieren sind dasselbe.“ → Falsch. loadClass lädt nur. Der static-Block läuft erst beim ersten aktiven Zugriff.
  • „Zugriff auf eine static final-Konstante initialisiert die Klasse.“ → Falsch. Compile-Zeit-Konstanten setzt javac direkt ein. Die Klasse wird nicht einmal geladen.
  • „Gleicher voll qualifizierter Name heisst gleiche Klasse.“ → Falsch. Name plus Defining Loader bestimmt die Klasse.
  • „Klassen werden nie entladen.“ → Falsch. Sie werden entladen, wenn ihr Loader unerreichbar ist. Nur Klassen der eingebauten Loader bleiben immer.
  • „ClassNotFoundException und NoClassDefFoundError sind gleich.“ → Falsch. Die erste ist eine checked Exception bei Suche per Name. Der zweite ist ein Error: Die Klasse war beim Kompilieren da und fehlt jetzt, oder ihre Initialisierung scheiterte.
  • „Klassen liegen in der PermGen.“ → Veraltet. Seit Java 8 im Metaspace.

11. Fragen

Was ist ein ClassLoader?

Ein Objekt, das die Bytes einer Klasse findet und daraus mit defineClass eine Klasse in der JVM macht. Jede Klasse kennt ihren Loader.

Welche eingebauten ClassLoader gibt es seit Java 9?

Bootstrap (in der JVM, null in Java), Platform ("platform") und App/System ("app"). Der Extension Loader existiert nicht mehr.

Was ist Parent Delegation?

Ein Loader fragt zuerst seinen Parent und sucht erst selbst, wenn der nichts findet. So kommen Kernklassen immer vom Bootstrap Loader.

Warum gibt es Parent Delegation?

Sicherheit und Konsistenz. Niemand kann java.lang.String ersetzen, und jede Kernklasse existiert nur einmal.

Was hat sich mit dem Modulsystem geändert?

Platform und App Loader schauen zuerst, zu welchem Modul ein Paket gehört, und delegieren direkt an dessen Loader. rt.jar und der Extension-Mechanismus sind weg.

Welche drei Phasen hat Class Loading?

Loading, Linking (Verify, Prepare, Resolve) und Initialization. Danach kann die Klasse benutzt und später entladen werden.

Was passiert in der Prepare-Phase?

Static-Felder werden angelegt und auf 0, null oder false gesetzt. Java-Code läuft dabei noch nicht.

Wann wird eine Klasse initialisiert?

Beim ersten aktiven Zugriff: new, static-Methode, static-Feld (keine Konstante), Class.forName oder Initialisierung einer Unterklasse.

Was ist der Unterschied zwischen Class.forName und loadClass?

Class.forName(name) initialisiert die Klasse. loadClass lädt sie nur. Class.forName(name, false, loader) lädt ohne Initialisieren.

Wann ist eine Klasse in der JVM gleich einer anderen?

Wenn Name und Defining Loader gleich sind. Gleicher Name in zwei Loadern ergibt zwei verschiedene Klassen.

Wie bekomme ich ClassCastException: X cannot be cast to X?

Wenn dieselbe Klasse von zwei verschiedenen Loadern geladen wurde. Typisch bei Plugins, Hot Reload und Child-first-Loadern.

ClassNotFoundException vs. NoClassDefFoundError?

ClassNotFoundException: Suche per Name schlägt fehl, checked. NoClassDefFoundError: Die Klasse war beim Kompilieren da, fehlt aber zur Laufzeit oder ihre Initialisierung scheiterte.

Was bedeutet "Could not initialize class X"?

Der static-Block von X ist früher schon gescheitert. Die echte Ursache steht beim ersten Fehler als ExceptionInInitializerError.

Was ist der Thread Context ClassLoader?

Ein Loader pro Thread, den Bibliotheken nutzen, um App-Klassen zu finden. ServiceLoader.load und JDBC nutzen ihn.

Wie schreibe ich einen eigenen ClassLoader?

Von ClassLoader erben und findClass überschreiben: Bytes lesen, defineClass aufrufen. loadClass nur überschreiben, wenn man Child-first will.

Was ist ein Child-first ClassLoader und wo gibt es ihn?

Er sucht zuerst selbst, dann beim Parent. Tomcat-Webapps, Flink und Spark mit userClassPathFirst nutzen das, damit eigene Bibliotheksversionen gewinnen.

Wann wird eine Klasse entladen?

Wenn ihr ClassLoader nicht mehr erreichbar ist und der GC läuft. Klassen der eingebauten Loader werden nie entladen.

Wo liegen die Daten einer geladenen Klasse?

Metadaten und Bytecode im Metaspace. Das Class-Objekt und die static-Werte im Heap.

Ist die Initialisierung einer Klasse thread-sicher?

Ja. Die JVM hält ein Init-Lock, <clinit> läuft genau einmal. Darauf baut das Lazy Holder Idiom für Singletons.

Warum lädt der Zugriff auf eine static final int-Konstante die Klasse nicht?

Javac setzt Compile-Zeit-Konstanten direkt in den Aufrufer ein. Darum muss man Aufrufer neu kompilieren, wenn sich die Konstante ändert.

Was ist ein parallel capable ClassLoader?

Er sperrt pro Klassenname statt den ganzen Loader. Das erlaubt paralleles Laden und vermeidet Deadlocks.

Was sind Hidden Classes?

Klassen ohne findbaren Namen seit Java 15, erzeugt mit Lookup.defineHiddenClass. Lambdas und Frameworks nutzen sie, sie können einzeln entladen werden.

Was sind CDS und der AOT Cache?

CDS speichert geparste Klassen in einem Archiv für schnelleren Start. Der AOT Cache (Java 24+) speichert sie zusätzlich geladen und gelinkt.

Wie sehe ich, welche Klasse woher geladen wird?

Mit -verbose:class oder -Xlog:class+load. Die Quelle zeigt shared objects file, jrt:/ oder den JAR-Pfad.

Szenario: Nach jedem Redeploy wächst der Metaspace, bis OutOfMemoryError: Metaspace kommt. Was tun Sie?

Ein ClassLoader-Leak. Mit jcmd VM.classloader_stats viele alte Loader finden, im Heap Dump den Pfad zu den GC Roots prüfen. Typische Halter sind Threads, ThreadLocals und registrierte JDBC-Treiber.

Szenario: In Produktion kommt NoSuchMethodError, lokal läuft alles. Woran denken Sie?

An zwei Versionen derselben Bibliothek im Classpath. Mit -verbose:class oder getCodeSource das geladene JAR finden, mit dependency:tree den Konflikt lösen.

Szenario: Ein Plugin-System wirft "Plugin cannot be cast to Plugin". Was ist falsch?

Das Interface wurde vom Plugin-Loader selbst geladen, nicht vom Parent. Das Interface gehört nur in den Host-Loader, das Plugin-JAR darf es nicht enthalten oder muss parent-first laden.
