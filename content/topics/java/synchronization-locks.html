Synchronisation und Locks

Java · Tier 1 · Quellen: JLS 17 Kapitel 17 (Threads and Locks, 17.1 und 17.4.5), Java SE 21 API-Doku java.util.concurrent.locks (Lock, ReentrantLock, ReentrantReadWriteLock, StampedLock, Condition, AbstractQueuedSynchronizer), OpenJDK-Quellcode java.util.concurrent.locks (JDK 21), JEP 374 (Biased Locking), JEP 444 (Virtual Threads), JEP 491 (Synchronize Virtual Threads without Pinning)

Kern: Ein Lock ist eine Sperre, die nur ein Thread zur selben Zeit hält. Er löst zwei Probleme: Atomarität (kein Thread sieht halbfertige Änderungen) und Sichtbarkeit (Änderungen vor dem unlock sieht der nächste Thread nach dem lock). Java hat zwei Familien: synchronized in der JVM und die Klassen aus java.util.concurrent.locks.

1. Wo sitzen Locks in der JVM?

  1. synchronized: ein Schlüsselwort. Der Compiler erzeugt monitorenter und monitorexit. Beispiel: synchronized (konto) { saldo -= 100; }.
  2. Intrinsic Lock (auch Monitor): der eingebaute Lock, den jedes Java-Objekt hat. Eine synchronized-Instanzmethode sperrt this, eine statische Methode das Class-Objekt.
  3. Object Header (Mark Word): die ersten Bytes jedes Objekts. Ohne Konkurrenz merkt sich die JVM den Lock dort, sehr billig.
  4. ObjectMonitor: eine native Struktur für den Fall mit Konkurrenz. Sie hat einen Owner, ein Entry Set (Threads, die auf den Lock warten) und ein Wait Set (Threads in wait()).
  5. java.util.concurrent.locks: Locks als normale Java-Klassen. Sie bieten mehr: tryLock, Timeout, Unterbrechung, Fairness, mehrere Conditions.
  6. AQS (AbstractQueuedSynchronizer): die Basis von ReentrantLock und ReentrantReadWriteLock. Er hält ein int state, ändert es per CAS (Compare-and-Swap, atomarer CPU-Befehl) und parkt wartende Threads in einer Warteschlange. StampedLock nutzt eine eigene, ähnliche Warteschlange.

2. Die Reise eines Threads zum Lock (die Geschichte zum Merken)

  1. Start: lock(). Thread T2 will Geld von Konto A abbuchen. Er ruft lock.lock() auf.
  2. Schneller Weg: CAS. Ist der Lock frei (state = 0), setzt T2 ihn per CAS auf 1. Kein Betriebssystem, nur ein CPU-Befehl. Hält T2 den Lock schon, zählt er nur hoch: Der Lock ist reentrant (wiederbetretbar).
  3. Owner. T2 ist jetzt Owner, also Besitzer. Er führt den kritischen Abschnitt aus, den Code, den nur ein Thread zur selben Zeit ausführen darf.
  4. Freigeben in finally. T2 ruft unlock() auf. Der Zähler geht auf 0. Der erste Thread in der Warteschlange wird geweckt.
  5. Lock belegt: warten. Hält T1 den Lock, kommt T2 in die Warteschlange und wird geparkt. Bei synchronized steht er als BLOCKED im Thread Dump, bei ReentrantLock als WAITING (parking). Geweckt versucht er es neu.
  6. Auf eine Bedingung warten. Ist das Konto leer, ruft T2 condition.await() auf. Er gibt den Lock frei und schläft. Ein anderer Thread zahlt ein und ruft signal(). T2 holt den Lock wieder und prüft die Bedingung neu.

Bei synchronized ist es dieselbe Geschichte, nur in der JVM: wait() und notify() statt await() und signal(). Und es gibt nur ein Wait Set pro Objekt.

3. Beispiel: Race, tryLock und ein echter Deadlock

static int plain = 0, synced = 0;
static final Object LOCK = new Object();

Runnable r = () -> {                       // 2 Threads, je 1 Mio. Mal
  for (int i = 0; i < 1_000_000; i++) {
    plain++;                                 // ohne Lock
    synchronized (LOCK) { synced++; }        // mit Lock
  }
};
// ... start, join, Ausgabe 1)

ReentrantLock lock = new ReentrantLock();
lock.lock(); lock.lock();                    // 2) zweimal derselbe Thread
// ... getHoldCount(), unlock() zweimal

// 3) ein anderer Thread hält den Lock 2 s, wir warten max. 500 ms
boolean got = lock.tryLock(500, TimeUnit.MILLISECONDS);

  1. plain++ ist drei Schritte: lesen, plus 1, schreiben. Zwei Threads überschreiben sich gegenseitig. Das ist ein Lost Update, hier 2863 verlorene Zählungen. Mit synchronized stimmt das Ergebnis genau.
  2. Derselbe Thread nimmt den ReentrantLock zweimal. holdCount=2 zeigt: Er muss auch zweimal unlock() aufrufen.
  3. tryLock(500 ms) gibt nach 500 ms false zurück statt ewig zu warten. Der Thread kann dann einen Fehler melden oder es später versuchen.
  4. Im Deadlock hält t1 Konto A und will B. t2 hält B und will A. Beide stehen auf BLOCKED. Die JVM erkennt den Zyklus: Found one Java-level deadlock.

4. Details, die Interviewer fragen

  1. Happens-before: Laut JLS 17.4.5 gilt: Ein unlock auf einem Monitor happens-before jedem späteren lock auf demselben Monitor. Darum sieht der nächste Thread alle Schreibzugriffe. Die Lock-Klassen geben dieselbe Garantie.
  2. Gleiches Objekt nötig: Zwei Threads schützen sich nur gegenseitig, wenn sie dasselbe Objekt sperren. synchronized auf this und auf Foo.class sind zwei verschiedene Locks.
  3. Reentrancy: Beide Lock-Arten sind reentrant. Ein Thread, der den Lock hält, kann ihn erneut nehmen. So kann eine synchronized-Methode eine andere aufrufen.
  4. wait/notify: wait() gibt den Monitor frei und schläft. Man muss den Monitor halten, sonst kommt IllegalMonitorStateException. notify() weckt einen Thread, notifyAll() alle.
  5. Spurious Wakeup: Ein Thread kann ohne notify aufwachen. Darum steht wait() und await() immer in einer while-Schleife, nie in einem if.
  6. ReentrantLock: ein expliziter, reentranter Lock auf AQS-Basis. Extras: tryLock(), tryLock(timeout), lockInterruptibly(), Fairness, mehrere Conditions. Pflicht: unlock() im finally.
  7. Fairness: new ReentrantLock(true) gibt den Lock an den Thread, der am längsten wartet. Das verhindert Starvation (ein Thread kommt nie dran). Kostet aber deutlich Durchsatz. Standard ist unfair.
  8. Condition: eine Warteschlange für eine Bedingung, z. B. notEmpty und notFull in einem Puffer. Erzeugt mit lock.newCondition(). Methoden: await(), signal(), signalAll(). ArrayBlockingQueue nutzt genau das.
  9. ReadWriteLock (ReentrantReadWriteLock): viele Leser oder ein Schreiber. Gut bei viel Lesen und wenig Schreiben. Downgrade (Write → Read) ist erlaubt. Upgrade (Read → Write) ist nicht möglich und blockiert für immer.
  10. StampedLock: ein Lock mit drei Modi: write, read und optimistic read. tryOptimisticRead() gibt einen Stempel (long) ohne zu sperren. Nach dem Lesen prüft validate(stamp), ob inzwischen jemand geschrieben hat. Wenn ja: noch einmal mit echtem Read-Lock lesen.
  11. StampedLock-Grenzen: Er ist nicht reentrant und hat keine Condition. Nimmt ein Thread ihn zweimal, blockiert er sich selbst.
  12. Deadlock: Zwei oder mehr Threads warten im Kreis aufeinander. Vier Bedingungen müssen gleichzeitig gelten: gegenseitiger Ausschluss, Halten und Warten, kein Entzug, zyklisches Warten. Bricht man eine, gibt es keinen Deadlock.
  13. Lock Ordering: die Standard-Lösung. Alle Threads nehmen Locks in derselben festen Reihenfolge, z. B. nach Konto-ID. Damit ist zyklisches Warten unmöglich.
  14. Livelock: Threads blockieren nicht, weichen sich aber ständig aus und kommen nicht weiter. Typisch bei tryLock-Schleifen ohne zufällige Pause.
  15. Biased Locking: eine alte Optimierung für Locks ohne Konkurrenz. Ab Java 15 standardmässig aus, in Java 18 entfernt (JEP 374). In Java 21 und 25 gibt es sie nicht mehr.
  16. JIT und Locks: Der JIT entfernt Locks auf Objekten, die nur ein Thread sieht (Lock Elision). Er fasst viele kleine Locks zu einem zusammen (Lock Coarsening). Mehr dazu auf der Seite JIT-Compiler.
  17. Virtual Threads: In Java 21 bis 23 pinnt synchronized einen Virtual Thread. Pinning heisst: Er blockiert dabei seinen Carrier-Thread (den echten OS-Thread). Seit Java 24 ist das behoben (JEP 491). In Java 25 ist synchronized mit Virtual Threads also wieder unproblematisch.

5. Vergleich

  • synchronized: einfach, Freigabe automatisch, auch bei Exception. Kein Timeout, keine Unterbrechung, nur ein Wait Set. Erste Wahl für einfache Fälle.
  • ReentrantLock: gleiche Semantik plus tryLock, Timeout, lockInterruptibly, Fairness, mehrere Conditions. Preis: unlock im finally selbst schreiben.
  • ReentrantReadWriteLock: viele Leser parallel, ein Schreiber exklusiv. Lohnt sich nur bei langen Lesezugriffen und wenig Schreiben. Kein Upgrade von Read zu Write.
  • StampedLock: optimistisches Lesen ohne Sperre, sehr schnell bei fast nur Lesen. Nicht reentrant, keine Condition, Code schwerer korrekt zu schreiben.
  • volatile: nur Sichtbarkeit, keine Atomarität. count++ auf einem volatile-Feld ist trotzdem ein Race.
  • Atomic-Klassen (AtomicInteger, LongAdder): lock-frei per CAS für einzelne Variablen. Schneller als ein Lock für einen Zähler.
  • Concurrent Collections (ConcurrentHashMap, BlockingQueue): Die Synchronisation steckt schon drin. Siehe die Seite ConcurrentHashMap.

6. In der Produktion

  1. Deadlock: Requests hängen, CPU ist niedrig, Thread-Pool läuft voll. Ursache: Locks in verschiedener Reihenfolge. Lösung: feste Lock-Reihenfolge, tryLock mit Timeout, oder nur einen Lock nehmen.
  2. Lock Contention: Viele Threads warten auf einen Lock, der Durchsatz bricht ein. Ursache oft: I/O oder Remote-Call im synchronized-Block. Lösung: Block kürzer machen, I/O ausserhalb, feinere Locks oder Concurrent Collections.
  3. Vergessenes unlock(): Eine Exception überspringt unlock. Der Lock bleibt für immer belegt. Lösung: immer lock(); try { … } finally { unlock(); }.
  4. Lock auf falschem Objekt: synchronized auf einem String-Literal, einem Integer oder einem Feld, das neu zugewiesen wird. Fremder Code teilt sich den Lock oder jeder Thread hat einen anderen. Lösung: private final Object lock = new Object();.
  5. Virtual Threads auf Java 21: synchronized um blockierende I/O pinnt Carrier-Threads. Bei wenigen Carriern steht die ganze Anwendung. Lösung: auf Java 24+ wechseln oder dort ReentrantLock nutzen.
  6. Lost Updates ohne Fehlermeldung: Zähler und Summen stimmen unter Last nicht. Kein Log zeigt es. Lösung: AtomicLong, LongAdder oder ein Lock um die ganze Lese-Ändere-Schreibe-Folge.

7. Diagnose: Werkzeuge und Befehle

  • jcmd <pid> Thread.print (oder jstack <pid>): Thread Dump. Zeigt BLOCKED, WAITING (parking), wer welchen Lock hält, und meldet Deadlocks. Mit -l auch gehaltene ReentrantLocks (ownable synchronizers).
  • Mehrere Thread Dumps im Abstand von ein paar Sekunden: Steht derselbe Thread immer am selben Lock, ist das ein Hänger, kein Zufall.
  • ThreadMXBean.findDeadlockedThreads(): findet Deadlocks im Programm selbst, z. B. für einen Health-Check.
  • JFR (Java Flight Recorder): Event jdk.JavaMonitorEnter zeigt lange Wartezeiten auf synchronized. jdk.ThreadPark zeigt Wartezeiten bei ReentrantLock. jdk.VirtualThreadPinned zeigt Pinning.
  • async-profiler im Lock-Modus (-e lock): zeigt, welche Locks am meisten Wartezeit kosten.
  • jcmd <pid> Thread.dump_to_file -format=json file.json: Thread Dump inklusive Virtual Threads (seit Java 21).

8. Senior-Punkte

  1. Erst ohne Lock denken. Unveränderliche Objekte, Thread-Confinement, Concurrent Collections und Atomics brauchen keinen eigenen Lock. Jeder eigene Lock ist eine Fehlerquelle.
  2. synchronized zuerst, ReentrantLock nur bei echtem Bedarf: Timeout, Unterbrechung, Fairness, mehrere Conditions. Seit Java 24 fällt auch das Virtual-Thread-Argument weg.
  3. Kritische Abschnitte klein halten. Nie I/O, Remote-Calls oder fremden Code (Callbacks) unter einem Lock. Fremder Code kann andere Locks nehmen und Deadlocks bauen.
  4. ReadWriteLock ist kein Gratis-Gewinn. Er hat mehr Overhead als ein einfacher Lock. Er lohnt sich nur bei vielen Lesern und langen Lesezugriffen. Messen.
  5. StampedLock nur in heissem, gut gekapseltem Code. Optimistisches Lesen ist schnell, aber schwer korrekt. Gelesene Werte sind vor validate möglicherweise inkonsistent.
  6. Locks schützen nur innerhalb einer JVM. Mehrere Pods brauchen einen verteilten Ansatz: Datenbank-Lock, optimistisches Locking mit Versionsspalte oder ein Lock-Dienst.
  7. Fairness kostet Durchsatz. Unfair ist Standard, weil ein gerade laufender Thread den Lock oft sofort nehmen kann. Fair nur, wenn Starvation real gemessen wurde.

10. Fallen

  • „volatile macht count++ thread-sicher.“ → Falsch. volatile gibt nur Sichtbarkeit. count++ bleibt drei Schritte. Lösung: AtomicInteger oder Lock.
  • „Eine synchronized-Methode sperrt die Methode.“ → Falsch. Sie sperrt das Objekt (this) bzw. das Class-Objekt. Alle synchronized-Methoden desselben Objekts teilen den Lock.
  • „Read-Lock halten und dann Write-Lock nehmen geht.“ → Falsch. Upgrade blockiert bei ReentrantReadWriteLock für immer. Nur Downgrade geht.
  • „StampedLock ist ein schnellerer ReentrantReadWriteLock.“ → Falsch. Er ist nicht reentrant und hat keine Condition. Zweimal nehmen blockiert den Thread selbst.
  • „wait() in einem if reicht.“ → Falsch. Spurious Wakeups und andere Threads ändern die Bedingung. Immer while.
  • „Biased Locking macht ungeteilte Locks billig.“ → Veraltet. In Java 18 entfernt (JEP 374). Heute helfen leichte Locks im Header und Lock Elision des JIT.
  • „Virtual Threads und synchronized vertragen sich nicht.“ → Veraltet. Gilt für Java 21 bis 23. Seit Java 24 (JEP 491) gibt ein blockierter Virtual Thread seinen Carrier frei.
  • „ReentrantLock ist immer schneller als synchronized.“ → Falsch. Heute sind beide ähnlich schnell. Wähle nach Funktionen, nicht nach Tempo.

11. Fragen

Was macht synchronized genau?

Es nimmt den Monitor eines Objekts, führt den Block aus und gibt ihn wieder frei, auch bei Exception. So ist der Block atomar und alle Änderungen sind für den nächsten Thread sichtbar.

Was ist ein Intrinsic Lock oder Monitor?

Der eingebaute Lock, den jedes Java-Objekt hat. synchronized und wait/notify nutzen ihn.

Welchen Lock nimmt eine synchronized static-Methode?

Den Monitor des Class-Objekts, z. B. Konto.class. Das ist ein anderer Lock als der von this.

Was garantiert ein Lock für die Sichtbarkeit?

Ein unlock happens-before jedem späteren lock auf demselben Lock (JLS 17.4.5). Der nächste Thread sieht also alle Schreibzugriffe davor.

Was heisst reentrant?

Ein Thread, der den Lock hält, kann ihn noch einmal nehmen. Ein Zähler merkt sich, wie oft. Er muss genauso oft freigeben.

Wann ReentrantLock statt synchronized?

Wenn man tryLock, ein Timeout, lockInterruptibly, Fairness oder mehrere Conditions braucht. Sonst synchronized, weil es einfacher ist und sich selbst freigibt.

Warum unlock() im finally?

Sonst bleibt der Lock nach einer Exception für immer belegt. Alle anderen Threads warten dann ewig.

Was ist der Unterschied zwischen lock() und lockInterruptibly()?

lock() wartet auch bei interrupt() weiter. lockInterruptibly() bricht dann mit InterruptedException ab. Gut für abbrechbare Aufgaben.

Was ist ein fairer Lock?

Er gibt den Lock an den Thread, der am längsten wartet. Er verhindert Starvation, kostet aber viel Durchsatz.

Was ist AQS?

AbstractQueuedSynchronizer, die Basis von ReentrantLock, Semaphore und CountDownLatch. Er hält ein int state, ändert es per CAS und parkt wartende Threads in einer Warteschlange.

Was ist eine Condition?

Eine Warteschlange für eine Bedingung an einem Lock. await() gibt den Lock frei und wartet, signal() weckt einen Wartenden. Ein Lock kann mehrere Conditions haben.

Warum wait() und await() immer in einer while-Schleife?

Wegen Spurious Wakeups und weil ein anderer Thread die Bedingung schon wieder geändert haben kann. Nach dem Aufwachen muss man neu prüfen.

Was passiert, wenn man wait() ohne den Monitor aufruft?

Es kommt eine IllegalMonitorStateException. Man muss in einem synchronized-Block auf demselben Objekt sein.

notify() oder notifyAll()?

notifyAll() ist sicherer, wenn Threads auf verschiedene Bedingungen warten. notify() weckt nur einen, vielleicht den falschen.

Wie funktioniert ein ReadWriteLock?

Viele Threads dürfen gleichzeitig lesen. Ein Schreiber braucht den Lock exklusiv. Gut bei viel Lesen und wenig Schreiben.

Kann man bei ReentrantReadWriteLock vom Read- zum Write-Lock wechseln?

Nein, ein Upgrade blockiert für immer. Ein Downgrade geht: Write-Lock halten, Read-Lock nehmen, Write-Lock freigeben.

Was ist ein optimistic read bei StampedLock?

tryOptimisticRead() gibt einen Stempel ohne zu sperren. Nach dem Lesen prüft validate(stamp), ob jemand geschrieben hat. Wenn ja, liest man mit echtem Read-Lock neu.

Was sind die Grenzen von StampedLock?

Nicht reentrant und keine Condition. Code ist schwerer korrekt zu schreiben.

Was ist ein Deadlock?

Threads warten im Kreis aufeinander, jeder hält einen Lock, den ein anderer braucht. Keiner kommt je weiter.

Welche vier Bedingungen braucht ein Deadlock?

Gegenseitiger Ausschluss, Halten und Warten, kein Entzug, zyklisches Warten. Bricht man eine, ist kein Deadlock möglich.

Wie verhindern Sie Deadlocks?

Feste Lock-Reihenfolge, z. B. nach ID. Oder tryLock mit Timeout. Oder weniger Locks und keine fremden Aufrufe unter einem Lock.

Wie finden Sie einen Deadlock?

Mit jcmd <pid> Thread.print oder jstack. Die JVM schreibt „Found one Java-level deadlock“ und zeigt, wer welchen Lock hält.

Was ist der Unterschied zwischen Deadlock, Livelock und Starvation?

Deadlock: alle blockiert. Livelock: alle aktiv, aber ohne Fortschritt. Starvation: ein Thread kommt nie an die Reihe.

Reicht volatile statt synchronized?

Nur für ein einzelnes Flag, das ein Thread schreibt. volatile gibt Sichtbarkeit, aber keine Atomarität für Lesen-Ändern-Schreiben.

Was ist Biased Locking, und gibt es das noch?

Eine alte Optimierung für Locks ohne Konkurrenz. Seit Java 15 aus, in Java 18 entfernt (JEP 374). In Java 21 und 25 gibt es sie nicht.

Was ist Pinning bei Virtual Threads?

Ein Virtual Thread kann beim Blockieren seinen Carrier-Thread nicht freigeben. In Java 21 bis 23 passiert das in synchronized. Seit Java 24 (JEP 491) nicht mehr, nur noch z. B. in nativem Code und Klassen-Initialisierern.

Warum nicht synchronized auf einem String oder Integer?

Literale und kleine Integer werden geteilt. Fremder Code kann denselben Lock nehmen. Besser ein private final Object als Lock.

Was machen Lock Elision und Lock Coarsening?

Der JIT entfernt Locks auf Objekten, die nur ein Thread sieht. Er fasst aufeinanderfolgende Locks auf dasselbe Objekt zu einem zusammen.

Szenario: Der Service hängt, CPU ist fast 0 %, keine Fehler im Log. Was tun Sie?

Zwei bis drei Thread Dumps mit jcmd Thread.print ziehen. Nach „Found one Java-level deadlock“ und BLOCKED-Threads am selben Lock suchen. Lösung: feste Lock-Reihenfolge oder tryLock mit Timeout.

Szenario: Unter Last steigt die Latenz stark, der Thread Dump zeigt viele BLOCKED-Threads an einer Stelle. Was tun Sie?

Das ist Lock Contention. Prüfen, was im synchronized-Block passiert, oft I/O oder ein Remote-Call. Lösung: Block verkleinern, I/O hinaus, oder eine Concurrent Collection statt eigenem Lock.

Szenario: Eine Java-21-Anwendung mit Virtual Threads friert unter Last ein. Woran denken Sie?

An Pinning: synchronized um blockierende I/O belegt alle Carrier-Threads. Prüfen mit JFR jdk.VirtualThreadPinned. Lösung: auf Java 24+ aktualisieren oder ReentrantLock nutzen.
