Garbage Collection: Grundlagen

Kern: Die Garbage Collection (GC) gibt Heap-Speicher von Objekten frei, die das Programm nicht mehr erreicht, damit man Speicher nicht von Hand freigeben muss. Erreichbar ist, was von einer GC Root aus über Referenzen erreichbar ist. Der Heap ist in Generationen geteilt, weil die meisten Objekte jung sterben.

Antwort-Muster

Frage: Wie arbeitet die Garbage Collection?

  1. Mechanismus: Die GC markiert ab den GC Roots alle erreichbaren Objekte und gibt den Rest frei. Young wird oft und billig geräumt.
  2. Zahl: Das Alter eines Objekts hat 4 Bits, darum ist die Tenuring Threshold höchstens 15.
  3. Trade-off: Kurze Pausen kosten CPU und Heap-Reserve. Man bekommt nur zwei von drei aus Latenz, Durchsatz und Speicher.
  4. Produktion: Bei langen Pausen lese ich zuerst das GC-Log mit -Xlog:gc.

1. Die Reise eines Objekts durch die Generationen

  1. Geburt im Eden. new Order() legt das Objekt im Eden an. Jeder Thread hat dort einen eigenen Block, den TLAB (Thread-Local Allocation Buffer). Darum ist new sehr schnell: nur ein Zeiger wird verschoben.
  2. Eden ist voll: Minor GC. Die JVM stoppt alle Threads. Die GC markiert ab den GC Roots alle erreichbaren Objekte. Sie liest nur die Young Generation, nicht die ganze Old Generation.
  3. Überleben: Kopie in den Survivor. Lebende Objekte werden in den leeren Survivor kopiert. Ihr Alter steigt um 1. Eden und der alte Survivor sind danach komplett leer. Tote Objekte kosten nichts, sie werden nie angefasst.
  4. Alt genug: Promotion. Erreicht das Alter die Tenuring Threshold (höchstens 15), wird das Objekt in die Old Generation kopiert. Ist der Survivor zu klein, kommt es früher dorthin: Premature Promotion.
  5. Old ist voll: Major oder Full GC. Jetzt arbeitet die GC auf der Old Generation mit Mark-Sweep-Compact. Bei Serial und Parallel ist das eine lange Pause über den ganzen Heap.
  6. Tod. Zeigt keine Referenzkette von einer Root mehr auf das Objekt, ist es unerreichbar. Bei der nächsten passenden GC wird sein Speicher frei. Es gibt keinen festen Zeitpunkt dafür.

Warum das funktioniert: die Weak Generational Hypothesis. Sie sagt: Die meisten Objekte sterben jung. Darum ist eine Minor GC billig, sie kopiert nur die wenigen Überlebenden.

2. Aufbau

  1. GC Roots: Startpunkte, die sicher lebendig sind. Beispiel: eine lokale Variable in main.
  2. Young Generation: Bereich für neue Objekte. Sie besteht aus Eden und zwei Survivor Spaces (S0, S1).
  3. Eden: Hier entsteht fast jedes neue Objekt. Beispiel: new byte[10_000] in einer Schleife.
  4. Survivor Spaces: Hier liegen Objekte, die schon eine GC überlebt haben. Immer ist einer der beiden leer.
  5. Old Generation (auch Tenured): Bereich für langlebige Objekte. Beispiel: ein Cache, der Stunden lebt.
  6. Metaspace: Speicher für Klassen-Metadaten ausserhalb des Heaps. Er wird nur beim Entladen von Klassen frei.
  7. GC-Threads: Sie finden lebendige Objekte und geben den Rest frei.

Dieses Bild gilt für Serial und Parallel. G1 teilt den Heap in gleich grosse Regionen, jede Region spielt Eden, Survivor oder Old. ZGC ist seit Java 21 generational, seit Java 23 standardmässig.

3. Details, die Interviewer fragen

  1. Reachability: Ein Objekt ist erreichbar, wenn von einer GC Root eine Referenzkette zu ihm führt. Nur das zählt. Zyklen ohne Root werden gesammelt.
  2. GC Roots: Sie sind die Startpunkte der Markierung. Lokale Variablen und Parameter auf den Thread-Stacks sind Roots, z. B. order in einer laufenden Methode. Auch static-Felder geladener Klassen sind Roots, z. B. static Map cache.
  3. Weitere GC Roots: Aktive Threads sind Roots, z. B. ein laufender Worker-Thread. JNI-Referenzen aus nativem Code sind Roots. Objekte mit gehaltenem synchronized-Monitor sind es auch. Dazu kommen Klassen des System-Classloaders und JVM-interne Objekte.
  4. Mark: Das ist die erste Phase von Mark-Sweep-Compact. Die GC markiert ab den Roots alle erreichbaren Objekte. Alle anderen Objekte bleiben unmarkiert.
  5. Sweep: Das ist die zweite Phase. Die GC trägt nicht markierte Objekte als frei ein. Danach ist der Heap löchrig. Das heisst Fragmentierung.
  6. Compact: Das ist die dritte Phase. Die GC schiebt lebende Objekte zusammen und passt Referenzen an. Danach ist der freie Platz ein Block.
  7. Copying Collector: Die Young Generation nutzt Kopieren statt Sweep. Lebende Objekte wandern in einen leeren Bereich. Die Kosten hängen nur von den lebenden Objekten ab. Tote Objekte kosten nichts.
  8. Stop-the-World (STW): Eine STW-Pause hält alle Java-Threads an. Die Threads stoppen an einem Safepoint. Das ist eine Stelle mit bekanntem Zustand. Jeder Collector in HotSpot hat STW-Pausen, auch ZGC (unter 1 ms).
  9. Parallel vs. Concurrent: Parallel heisst, mehrere GC-Threads arbeiten während einer Pause. Concurrent heisst, GC-Threads arbeiten, während die Anwendung weiterläuft.
  10. Minor, Major, Full GC: Minor GC räumt nur Young. Major GC räumt Old. Full GC räumt den ganzen Heap, meist mit Compaction. Die Begriffe sind nicht streng definiert, darum zählt der Log-Text.
  11. Card Table und Remembered Set: Ein Old-Objekt kann auf ein Young-Objekt zeigen. Darum merkt sich die JVM solche Stellen. Serial und Parallel nutzen die Card Table. G1 nutzt das Remembered Set. So muss eine Minor GC nicht die ganze Old Generation lesen.
  12. Write Barrier: Sie ist ein kleiner Code bei jedem Feld-Schreiben. Sie pflegt die Card Table oder das Remembered Set. Darum weiss die GC, welche Old-Stellen auf Young zeigen.
  13. Tenuring Threshold: Das Alter eines Objekts steht im Objekt-Header in 4 Bits. Darum ist MaxTenuringThreshold höchstens 15. Die JVM senkt die Schwelle selbst, wenn die Survivor voll werden.
  14. Referenzarten (java.lang.ref): Eine Strong-Referenz hält das Objekt am Leben. Eine SoftReference wird erst bei Speicherdruck geräumt, z. B. für einfache Caches. Eine WeakReference wird bei der nächsten GC geräumt, z. B. bei WeakHashMap-Schlüsseln. Eine PhantomReference meldet den Tod über eine Queue, z. B. für den Cleaner.
  15. finalize(): Es ist seit Java 9 deprecated. Seit Java 18 ist es „for removal“ (JEP 421). Es verzögert die Freigabe um mindestens eine GC. Ersatz sind try-with-resources oder java.lang.ref.Cleaner.
  16. System.gc(): Es ist nur eine Bitte an die JVM. Bei Serial und Parallel löst es meist eine Full GC aus. -XX:+DisableExplicitGC schaltet es ab.
  17. Heap-Grösse ohne Flags: Die Startgrösse ist 1/64 des physischen Speichers. Das Maximum ist 1/4. Im Container gilt das Container-Limit. -XX:MaxRAMPercentage (Standard 25) ändert den Anteil.
  18. Standard-Collector: In Java 21 und 25 ist es G1 auf einer „server-class machine“. Das heisst mindestens 2 CPUs und 1792 MB. Sonst ist es Serial. Ab Java 27 ist G1 überall Standard (JEP 523).

4. Fallen

  • „Java zählt Referenzen, Zyklen sind ein Leak.“ → Falsch. Die JVM prüft Erreichbarkeit ab GC Roots. Zyklen ohne Root werden gesammelt.
  • „System.gc() erzwingt eine GC.“ → Falsch. Es ist nur eine Bitte. Sie kann ignoriert oder abgeschaltet werden.
  • „Variablen auf null setzen hilft dem GC.“ → Meist falsch. Lokale Variablen sterben mit der Methode. Nur bei langlebigen Feldern oder Collections hilft es.
  • „Mit GC gibt es keine Memory Leaks.“ → Falsch. Erreichbare, aber unnötige Objekte bleiben, z. B. in einer statischen Map.
  • „ZGC hat kein Stop-the-World.“ → Falsch. Es hat sehr kurze Pausen (unter 1 ms), aber es hat sie.
  • „finalize() ist ein Destruktor.“ → Falsch. Kein fester Zeitpunkt, vielleicht nie. Deprecated for removal seit Java 18.
  • „Der Standard ist immer G1.“ → Falsch für Java 21 und 25. Bei 1 CPU oder unter 1792 MB nimmt die JVM Serial. Erst ab Java 27 immer G1.
  • „CMS ist der Collector für kurze Pausen.“ → Veraltet. CMS ist seit Java 14 entfernt (JEP 363). Heute: G1, ZGC oder Shenandoah.

5. Selbsttest

Warum?

Warum teilt die JVM den Heap in Generationen?

Wegen der Weak Generational Hypothesis: Die meisten Objekte sterben jung. Darum räumt man Young oft und billig, Old selten.

Warum kopiert die Young Generation statt zu sweepen?

Kopieren kostet nur pro lebendem Objekt. In Young überleben sehr wenige. Danach ist der Bereich ohne Löcher.

Warum nicht finalize() benutzen?

Kein fester Zeitpunkt, verzögerte Freigabe, Risiko für Leaks. Seit Java 18 deprecated for removal. Ersatz: try-with-resources oder Cleaner.

Warum ist eine Minor GC billig?

Sie liest nur die Young Generation. Sie kopiert nur die wenigen Überlebenden. Tote Objekte werden nie angefasst.

Wie innen?

Was ist Garbage Collection?

Die JVM gibt automatisch Speicher von Objekten frei, die nicht mehr erreichbar sind. So muss man Speicher nicht von Hand freigeben.

Wann ist ein Objekt Müll?

Wenn keine Referenzkette von einer GC Root zu ihm führt. Ob noch Referenzen auf das Objekt zeigen, ist egal.

Was sind GC Roots?

Startpunkte der Markierung: lokale Variablen auf Thread-Stacks, static-Felder, aktive Threads, JNI-Referenzen und gehaltene Monitore.

Werden zyklische Referenzen gesammelt?

Ja. Die JVM nutzt Erreichbarkeit, kein Reference Counting. Ein Zyklus ohne Root ist unerreichbar und wird gesammelt.

Wie ist die Young Generation aufgebaut?

Eden für neue Objekte und zwei Survivor Spaces. Einer der Survivor ist immer leer und dient als Ziel der nächsten Kopie.

Was passiert bei einer Minor GC?

Alle Threads stoppen. Lebende Objekte aus Eden und Survivor werden in den leeren Survivor oder nach Old kopiert. Danach ist Eden leer.

Wann kommt ein Objekt in die Old Generation?

Wenn sein Alter die Tenuring Threshold erreicht (höchstens 15). Oder früher, wenn der Survivor zu klein ist: Premature Promotion.

Was ist Mark-Sweep-Compact?

Mark: lebende Objekte ab den Roots markieren. Sweep: den Rest freigeben. Compact: lebende Objekte zusammenschieben gegen Fragmentierung.

Was ist Stop-the-World?

Alle Java-Threads stehen an einem Safepoint still, während die GC arbeitet. Jeder HotSpot-Collector hat solche Pausen, nur verschieden lang.

Was ist ein Safepoint?

Eine Stelle im Code, an der der Zustand des Threads bekannt ist. Dort können Threads für eine GC anhalten.

Wie findet eine Minor GC Referenzen von Old nach Young?

Über die Card Table oder das Remembered Set. Eine Write Barrier markiert jedes Feld-Schreiben in Old. So muss die GC nicht ganz Old lesen.

Was ist ein TLAB?

Thread-Local Allocation Buffer: ein eigener Block im Eden pro Thread. new verschiebt nur einen Zeiger, ohne Lock.

Zahlen

Wie gross ist der Heap ohne -Xmx?

Maximal 1/4 des physischen Speichers oder des Container-Limits. MaxRAMPercentage ändert den Anteil.

Welcher Collector ist Standard?

In Java 21 und 25: G1 bei mindestens 2 CPUs und 1792 MB, sonst Serial. Ab Java 27 immer G1.

Wie viele Bits hat das Alter und was folgt daraus?

Das Alter steht in 4 Bits im Objekt-Header. Darum ist MaxTenuringThreshold höchstens 15.

Wie gross sind Eden und Survivor im Beispiel-Log?

Mit -Xmn16m ist Eden 13184K und jeder Survivor 1600K (Verhältnis 8:1:1).

Vergleich

Minor, Major, Full GC: was ist der Unterschied?

Minor räumt Young, Major räumt Old, Full räumt den ganzen Heap. Full GC ist am teuersten.

Parallel vs Concurrent bei der GC?

Parallel: mehrere GC-Threads in einer Pause. Concurrent: die GC arbeitet, während die Anwendung läuft.

Soft, Weak, Phantom Reference: was ist der Unterschied?

Soft wird erst bei Speicherdruck geräumt. Weak bei der nächsten GC. Phantom meldet nach dem Tod über eine Queue, z. B. für Cleaner.

Mark-Sweep, Mark-Compact und Copying: was ist der Unterschied?

Mark-Sweep ist schnell, hinterlässt aber Löcher. Mark-Compact schiebt Objekte zusammen und ist teurer. Copying ist sehr schnell bei wenigen Überlebenden, braucht aber einen leeren Zielbereich.

Produktion

Was macht System.gc()?

Es bittet um eine GC, meist eine Full GC. Die JVM darf es ignorieren. Mit -XX:+DisableExplicitGC ist es abgeschaltet.

Kann Java Memory Leaks haben?

Ja. Objekte, die erreichbar bleiben, aber nicht mehr gebraucht werden. Typisch: statische Collections, Listener, ThreadLocals.

Wie sehen Sie, was die GC macht?

Mit -Xlog:gc*, jstat -gcutil, jcmd GC.heap_info und JFR in JDK Mission Control.

Szenario: Die Anwendung hängt alle paar Minuten für 3 Sekunden. Wie gehen Sie vor?

GC-Log prüfen: Gibt es Pause Full zur gleichen Zeit? Wenn ja, Ursache suchen: Leak, zu kleiner Heap, Premature Promotion oder System.gc(). Dann Code oder Heap anpassen, eventuell G1 oder ZGC.

Szenario: Der Pod wird OOMKilled, aber es gibt keinen OutOfMemoryError. Warum?

Das Container-Limit wurde vom ganzen Prozess überschritten, nicht vom Heap. Metaspace, Stacks und Direct Memory zählen mit. Lösung: MaxRAMPercentage senken und Off-Heap messen.

Szenario: Der Old-Bereich wächst nach jeder Full GC weiter. Was heisst das?

Der Live-Set wächst, also wahrscheinlich ein Leak. Heap Dump mit jcmd GC.heap_dump ziehen und in Eclipse MAT den Besitzer der grössten Objekte suchen.

Design

Wie legen Sie die Heap-Grösse fest?

Als Betriebsentscheidung mit Container-Limit, MaxRAMPercentage und Platz für Off-Heap. Immer explizit setzen.

Wie gehen Sie mit GC-Problemen um?

Erst das GC-Log lesen, dann Flags ändern. Die meisten GC-Probleme sind Allokations- oder Leak-Probleme im Code.

Latenz, Durchsatz oder Speicher?

Man bekommt zwei von drei. Kurze Pausen kosten CPU und Heap-Reserve.

Wie räumen Sie Ressourcen auf?

Mit try-with-resources. Code baut man nie auf GC-Zeitpunkte, auch nicht mit finalize.

Mehr

Gerüst

  • Warum? Kein manuelles Freigeben von Speicher. Die meisten Objekte sterben jung, darum gibt es Generationen.
  • Wie innen? Mark ab den GC Roots. Young: Eden und zwei Survivor, Kopieren. Old: Mark-Sweep-Compact. Card Table und Write Barrier für Referenzen von Old nach Young.
  • Zahlen Tenuring Threshold höchstens 15 (4 Bits). Heap-Maximum 1/4 des RAM. G1 ab 2 CPUs und 1792 MB, sonst Serial.
  • Vergleich Mark-Sweep, Mark-Compact, Copying. Minor gegen Full GC. Strong, Soft, Weak, Phantom.
  • Produktion Lange Pausen durch Full GC. Pod wird OOMKilled. System.gc() im Log.
  • Design Heap mit MaxRAMPercentage bewusst setzen. Latenz, Durchsatz, Speicher abwägen. try-with-resources statt finalize.

Beispiel: Generationen und Reachability im Log sehen

import java.lang.ref.WeakReference;
import java.util.ArrayList;
import java.util.List;

public class GcDemo {
  static List<byte[]> keep = new ArrayList<>();   // GC Root: static field

  static class Node { Node other; }

  public static void main(String[] args) {
    // 1) a cycle with no root: unreachable, collected despite the references
    Node a = new Node(), b = new Node();
    a.other = b; b.other = a;
    WeakReference<Node> cycle = new WeakReference<>(a);
    a = null; b = null;

    // 2) much short-lived garbage, a few long-lived objects
    for (int i = 0; i < 6_000; i++) {
      byte[] tmp = new byte[10_000];              // dies at once
      if (i % 100 == 0) keep.add(new byte[100_000]); // survives
    }
    System.out.println("kept: " + keep.size() + " x 100 KB");
    System.out.println("cycle collected: " + (cycle.get() == null));

    // 3) drop the root, then ask for a full GC
    keep = null;
    System.gc();
    System.out.println("done");
  }
}

Echte Ausgabe, OpenJDK 17.0.3 (Oracle-Build 17.0.3.1), ungekürzt. Zeiten schwanken von Lauf zu Lauf. In Java 21 und 25 ist die Ausgabe von Serial sehr ähnlich. Ohne -XX:+UseSerialGC nutzt Java 17, 21 und 25 auf grossen Maschinen G1, dann heisst die Zeile Pause Young (Normal) (G1 Evacuation Pause).

  1. DefNew ist die Young Generation von Serial. -Xmn16m ergibt Eden 13184K und zwei Survivor mit je 1600K (Verhältnis 8:1:1).
  2. Pause Young (Allocation Failure): Eden ist voll, ein new findet keinen Platz. Die Minor GC leert Eden komplett: Eden: 13091K->0K.
  3. Die Pause ist kurz: meist unter 1,3 ms für 13 MB Eden. Nur die wenigen Überlebenden werden kopiert. Der Ausreisser 26 ms in GC(2) ist Rauschen beim Start (Messung nicht wiederholbar).
  4. Premature Promotion: Ab GC(1) wächst Tenured um ca. 1,2 MB pro GC. Der Survivor (1600K) ist zu klein für die 100-KB-Arrays. Sie gehen direkt in die Old Generation, lange vor Alter 15.
  5. Zyklus gesammelt: cycle collected: true. a und b zeigen aufeinander, aber keine Root zeigt auf sie. Die JVM zählt keine Referenzen, sie prüft Erreichbarkeit.
  6. Root entfernt: Nach keep = null sind die 60 Arrays unerreichbar. Die Full GC räumt Young und Old: Tenured: 5190K->616K. Der Rest (616K) sind JDK-interne Objekte.
  7. Pause Full (System.gc()) ist ein Stop-the-World über den ganzen Heap. Hier kurz, weil der Heap fast leer ist. Bei mehreren GB dauert es Sekunden.

Vergleich

  • Mark-Sweep: schnell, verschiebt nichts, hinterlässt aber Löcher (Fragmentierung).
  • Mark-Compact: kein Loch mehr, aber teurer: Objekte verschieben und alle Referenzen anpassen.
  • Copying: sehr schnell bei wenigen Überlebenden, braucht aber einen leeren Zielbereich.
  • Reference Counting (nicht in der JVM): zählt Referenzen pro Objekt, findet aber keine Zyklen.
  • Minor GC: nur Young, häufig, kurz.
  • Full GC: ganzer Heap, selten, lang. Ein häufiger Full GC ist ein Warnsignal.
  • STW-Phase vs Concurrent-Phase: STW ist einfach und schnell pro Byte, Concurrent kostet CPU und Barriers, hält aber die Pausen klein.

In der Produktion

  1. OutOfMemoryError: Java heap space: Die lebenden Objekte passen nicht in den Heap. Ursache ist oft ein Leak, z. B. ein Cache ohne Grenze. Lösung: Heap Dump analysieren, Cache begrenzen. Erst danach den Heap vergrössern.
  2. Lange Pausen durch Full GC: Requests hängen für Sekunden. Ursache: Old Generation voll, oft durch Premature Promotion. Lösung: Young Generation oder Heap grösser, Allokationen senken, Collector mit kurzen Pausen (G1, ZGC).
  3. Container wird gekillt (OOMKilled): Der Prozess braucht mehr als das Pod-Limit. Heap ist nur ein Teil: dazu kommen Metaspace, Thread-Stacks, Code Cache und Direct Memory. Lösung: -XX:MaxRAMPercentage auf ca. 50–75 setzen, nicht 100.
  4. Kleiner Container nutzt Serial: Ein Pod mit 1 CPU oder weniger als 1792 MB bekommt in Java 21 und 25 ohne Flag Serial. Lösung: Collector explizit setzen, z. B. -XX:+UseG1GC.
  5. System.gc() in Bibliotheken: erzeugt unerwartete Full GCs. Lösung: im Log nach (System.gc()) suchen, Aufrufer finden, oder -XX:+DisableExplicitGC.
  6. Hohe Allokationsrate: viele Minor GCs, viel CPU für GC. Lösung: Profiler auf Allokationen, z. B. weniger temporäre Objekte in heissen Schleifen.

Diagnose: Werkzeuge und Flags

  • -Xlog:gc: eine Zeile pro GC mit Art, Grund, Heap vorher/nachher und Pause.
  • -Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=20m: ausführliches Log mit Rotation für die Produktion.
  • -Xlog:gc+heap: Grössen von Eden, Survivor und Old pro GC (wie im Beispiel). -Xlog:gc+age=trace: Alter der Objekte im Survivor.
  • jstat -gcutil <pid> 1000: Füllgrad der Generationen und GC-Zeiten jede Sekunde.
  • jcmd <pid> GC.heap_info: aktueller Aufbau des Heaps. jcmd <pid> GC.class_histogram: Objekte pro Klasse.
  • jcmd <pid> GC.heap_dump /tmp/heap.hprof und -XX:+HeapDumpOnOutOfMemoryError: Heap Dump für Eclipse MAT.
  • JFR (Java Flight Recorder) mit JDK Mission Control: Events jdk.GarbageCollection, jdk.GCPhasePause, jdk.ObjectAllocationSample.
  • java -XX:+PrintFlagsFinal -version | grep -E "Use.*GC|MaxHeapSize": welcher Collector und welche Heap-Grösse wirklich gelten.

Senior-Punkte

  1. GC-Kosten hängen von lebenden Objekten ab, nicht von Müll. Viel kurzlebiger Müll ist billig. Viele langlebige Objekte sind teuer.
  2. Kein Speicherleck heisst nicht kein Problem. Ein grosser Live-Set (z. B. riesiger Cache) macht jede Old-GC teurer.
  3. Die Abwägung heisst Latenz, Durchsatz, Speicher. Man bekommt zwei von drei. Kurze Pausen kosten CPU und Heap-Reserve.
  4. Heap-Grösse ist eine Betriebsentscheidung: Container-Limit, MaxRAMPercentage, Platz für Off-Heap. Immer explizit setzen.
  5. Erst das GC-Log lesen, dann Flags ändern. Die meisten GC-Probleme sind Allokations- oder Leak-Probleme im Code.
  6. Code nie auf GC-Zeitpunkte bauen. Ressourcen schliesst man mit try-with-resources, nicht mit finalize.
