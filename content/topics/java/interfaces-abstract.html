Interface vs abstrakte Klasse

Kern: Ein Interface ist ein Vertrag: es sagt, was ein Typ kann, ohne eigenen Instanz-Zustand. Eine abstrakte Klasse ist eine halbfertige Klasse mit Zustand, Konstruktor und gemeinsamem Code. Eine Klasse kann viele Interfaces implementieren, aber nur eine Klasse erweitern.

1. Wo sitzen Interface und abstrakte Klasse?

  1. Interface: definiert Fähigkeiten. Beispiel: Exporter mit export(Report).
  2. Abstrakte Methode: nur Signatur, die Klasse muss sie implementieren. Beispiel: export.
  3. default-Methode (seit Java 8): Methode mit Rumpf im Interface, die Klassen erben. Beispiel: exportAll ruft export in einer Schleife.
  4. static-Methode (seit Java 8): gehört zum Interface, wird nicht vererbt. Beispiel: Exporter.of("csv").
  5. private-Methode (seit Java 9): Hilfscode für default-Methoden, von aussen unsichtbar.
  6. Abstrakte Klasse: hält Zustand (Path ziel) und einen Konstruktor. Unterklassen erben beides.

2. Die Reise einer default-Methode (die Geschichte zum Merken)

  1. Aufruf: h.foto() auf einem Handy. Die JVM sucht die passende Methode.
  2. Regel 1, Klasse gewinnt: Hat die Klasse oder eine Oberklasse foto(), gewinnt diese. Eine default-Methode kann eine Klassenmethode nie verdrängen.
  3. Regel 2, spezifischstes Interface gewinnt: Erbt Gross von Kamera und überschreibt foto(), gewinnt Gross.
  4. Genau ein Kandidat: Dann läuft diese default-Methode.
  5. Regel 3, Diamond: Zwei unabhängige Interfaces liefern dieselbe default-Methode. javac meldet einen Fehler. Die Klasse muss foto() überschreiben und kann mit Kamera.super.foto() eine Version wählen.

Echte Ausgabe, Oracle JDK 17.0.3 (javac und java). Die Regeln sind in Java 21 und 25 gleich.

  1. Zwei unabhängige default-Methoden mit gleicher Signatur: javac bricht ab. Java löst das Diamond-Problem beim Kompilieren, nicht zur Laufzeit.
  2. Kamera.super.foto() ruft gezielt die Version eines Interfaces. Das geht nur für direkte Ober-Interfaces.
  3. Handy2: die Methode aus der Klasse Basis gewinnt ohne Fehler.
  4. Handy3: Gross ist spezifischer als Kamera, also kein Konflikt.
  5. Waehrung hat genau eine abstrakte Methode. Darum kann chf() ein Lambda zurückgeben. Die private Methode teile teilt Code zwischen default-Methoden.
  6. Felder in Interfaces sind immer public static final, also Konstanten. Instanz-Zustand gibt es nicht.
  7. @FunctionalInterface prüft: genau eine abstrakte Methode. Zwei abstrakte Methoden sind ein Compile-Fehler.

4. Details, die Interviewer fragen

  1. Was ein Interface enthalten darf: abstrakte Methoden, default-, static- und private-Methoden, Konstanten, verschachtelte Typen. Keine Instanzfelder, keinen Konstruktor.
  2. Modifier im Interface: Methoden ohne Rumpf sind implizit public abstract. Felder sind implizit public static final. protected gibt es nicht.
  3. Was eine abstrakte Klasse enthalten darf: alles, was eine Klasse hat: Felder, Konstruktoren, protected-Methoden, final-Methoden. Man kann sie nur nicht direkt instanziieren.
  4. Konstruktor der abstrakten Klasse: existiert und läuft über super(...) der Unterklasse. Er initialisiert gemeinsamen Zustand.
  5. default-Methoden, warum: Sie wurden in Java 8 eingeführt, um Interfaces wie Collection zu erweitern (stream(), forEach), ohne alle Implementierungen zu brechen. Das heisst Interface Evolution.
  6. default-Methoden, Grenzen: Sie können equals, hashCode und toString von Object nicht als default liefern. Das ist ein Compile-Fehler, weil die Klasse immer gewinnt.
  7. static-Methoden im Interface: werden nicht vererbt. Aufruf nur über den Interface-Namen: List.of(), Comparator.comparing().
  8. private-Methoden (Java 9, JEP 213): Hilfscode für default- und static-Methoden. Sie sind nicht Teil der API.
  9. Diamond-Problem: Bei Klassen verhindert Java es durch Einfachvererbung. Bei default-Methoden gelten drei Regeln: Klasse gewinnt, spezifischeres Interface gewinnt, sonst muss man überschreiben.
  10. Functional Interface (JLS §9.8): ein Interface mit genau einer abstrakten Methode (SAM, Single Abstract Method). default-, static- und Object-Methoden zählen nicht. Comparator deklariert equals und ist trotzdem funktional.
  11. @FunctionalInterface: ist optional. Es lässt den Compiler die SAM-Regel prüfen und dokumentiert die Absicht.
  12. Standard-Interfaces in java.util.function: Function<T,R>, Supplier<T>, Consumer<T>, Predicate<T>, BiFunction, UnaryOperator, plus Varianten für Primitive wie IntPredicate. Details: Seite „Lambdas".
  13. Marker-Interface: ein Interface ohne Methoden, z. B. Serializable oder RandomAccess. Heute meist durch Annotationen ersetzt, aber als Typ prüfbar.
  14. sealed Interfaces: seit Java 17 mit permits. So kennt der Compiler alle Implementierungen. Details: Seite „Records und Sealed".
  15. Template Method Pattern: die abstrakte Klasse definiert den Ablauf in einer final-Methode und lässt Schritte abstrakt. Typisch für abstrakte Klassen.

5. Vergleich

  • Anzahl: Interface: beliebig viele pro Klasse. Abstrakte Klasse: genau eine.
  • Zustand: Interface: nur Konstanten. Abstrakte Klasse: beliebige Felder.
  • Konstruktor: Interface: keiner. Abstrakte Klasse: ja.
  • Sichtbarkeit: Interface: Methoden public oder private. Abstrakte Klasse: alle vier Stufen.
  • Methoden mit Code: Interface: default, static, private. Abstrakte Klasse: normale Methoden, auch final.
  • Lambda-fähig: Interface mit genau einer abstrakten Methode: ja. Abstrakte Klasse: nie.
  • Wann: Interface für Fähigkeiten und Verträge an Grenzen. Abstrakte Klasse für gemeinsamen Zustand und Ablauf in einer engen Familie.

6. In der Produktion

  1. Neue abstrakte Methode bricht alle Implementierungen: Ein geteiltes Interface bekommt eine Methode. Alle Teams müssen nachziehen. Lösung: neue Methode als default mit sinnvollem Verhalten.
  2. default-Methode mit Seiteneffekt: Eine default-Methode nutzt Annahmen, die nicht jede Implementierung erfüllt. Beispiel: Thread-Sicherheit. Lösung: default nur für Hilfslogik, sonst abstrakt lassen.
  3. Plötzlicher Diamond nach Update: Eine Bibliothek fügt eine default-Methode hinzu, die eine andere schon hat. Der Build bricht. Lösung: in der Klasse überschreiben und mit X.super.m() wählen.
  4. Konstanten-Interface: Klassen implementieren ein Interface nur für Konstanten. Die Konstanten werden Teil ihrer API. Lösung: final class mit privatem Konstruktor oder ein enum.
  5. Abstrakte Basisklasse wird zum Mülleimer: Jede Gemeinsamkeit landet in AbstractBaseService. Lösung: kleine Interfaces und Komposition.
  6. Interface für jede Klasse: FooService + FooServiceImpl ohne zweite Implementierung. Das ist Rauschen. Lösung: Interface nur an echten Grenzen oder für mehrere Implementierungen.

7. Diagnose: Werkzeuge und Befehle

  • javac-Fehler „inherits unrelated defaults": Diamond. Lösung im Code, nicht in der Konfiguration.
  • javap -p Interface.class: zeigt default-, static- und private-Methoden.
  • IDE „Implementations" (IntelliJ: Ctrl+Alt+B): wer implementiert ein Interface.
  • japicmp oder Revapi: prüfen binäre Kompatibilität zwischen Versionen einer Bibliothek.
  • ArchUnit: Regel wie „Klassen in ..api.. sind Interfaces".

8. Senior-Punkte

  1. Interface zuerst an Modul- und Teamgrenzen. Es ist flexibler und erlaubt Mocks und Fakes.
  2. Abstrakte Klasse, wenn es echten gemeinsamen Zustand oder einen festen Ablauf gibt. Oft ist sie eine Implementierungshilfe hinter einem Interface (AbstractList hinter List).
  3. default-Methoden sind für Evolution, nicht für Mehrfachvererbung von Logik. Zu viel Logik in defaults macht Interfaces schwer verständlich.
  4. Kleine Interfaces (Interface Segregation Principle). Ein Client hängt nur von dem ab, was er nutzt.
  5. Öffentliche Interfaces sind teuer zu ändern. Jede neue abstrakte Methode bricht Kunden. Plane Erweiterungen mit default oder neuen Interfaces.
  6. sealed Interface + Records ersetzen heute oft abstrakte Klassenhierarchien für Datenvarianten.

10. Fallen

  • „Interfaces können keinen Code enthalten.“ → Falsch seit Java 8: default und static; seit Java 9 auch private.
  • „Abstrakte Klassen haben keinen Konstruktor.“ → Falsch. Sie haben einen. Er läuft über super() der Unterklasse.
  • „Mit default-Methoden hat Java Mehrfachvererbung wie C++.“ → Falsch. Nur Verhalten, kein Instanz-Zustand. Konflikte löst der Compiler.
  • „Eine default-Methode kann toString() liefern.“ → Falsch. Methoden von Object als default sind ein Compile-Fehler.
  • „Static-Methoden eines Interfaces erbt die Klasse.“ → Falsch. Aufruf nur über den Interface-Namen.
  • „Ein Functional Interface darf nur eine Methode haben.“ → Falsch. Nur eine abstrakte. default- und static-Methoden sind erlaubt.
  • „Ohne @FunctionalInterface geht kein Lambda.“ → Falsch. Die Annotation ist optional; sie prüft nur.

11. Fragen

Was ist der Unterschied zwischen Interface und abstrakter Klasse?

Interface: Vertrag ohne Instanz-Zustand, viele pro Klasse. Abstrakte Klasse: Teil-Implementierung mit Feldern und Konstruktor, nur eine pro Klasse.

Wann wählen Sie ein Interface, wann eine abstrakte Klasse?

Interface für Fähigkeiten und API-Grenzen. Abstrakte Klasse für gemeinsamen Zustand oder einen festen Ablauf in einer engen Klassenfamilie.

Was ist eine default-Methode?

Eine Interface-Methode mit Rumpf, seit Java 8. Implementierende Klassen erben sie und können sie überschreiben.

Warum wurden default-Methoden eingeführt?

Um bestehende Interfaces wie Collection um stream() oder forEach zu erweitern, ohne alle Implementierungen zu brechen.

Was ist das Diamond-Problem bei default-Methoden?

Zwei Interfaces liefern dieselbe default-Methode. javac meldet einen Fehler, die Klasse muss überschreiben.

Wie löst man den Konflikt?

Die Methode in der Klasse überschreiben und mit Kamera.super.foto() eine Version gezielt aufrufen oder kombinieren.

Welche Regeln gelten, wenn mehrere Versionen einer Methode erreichbar sind?

Erstens gewinnt die Klasse. Zweitens gewinnt das spezifischste Interface. Sonst muss die Klasse selbst überschreiben.

Kann eine default-Methode equals oder toString überschreiben?

Nein. Das ist ein Compile-Fehler. Die Version aus der Klasse (mindestens Object) würde ohnehin immer gewinnen.

Was sind static-Methoden in Interfaces?

Hilfs- oder Fabrikmethoden, die zum Interface gehören, z. B. List.of. Sie werden nicht vererbt.

Wozu private-Methoden in Interfaces?

Um Code zwischen default- oder static-Methoden zu teilen, ohne ihn öffentlich zu machen. Seit Java 9.

Kann ein Interface Felder haben?

Nur Konstanten. Jedes Feld ist implizit public static final.

Hat eine abstrakte Klasse einen Konstruktor?

Ja. Er initialisiert gemeinsamen Zustand und läuft beim Erzeugen jeder Unterklasse.

Kann eine abstrakte Klasse ohne abstrakte Methoden existieren?

Ja. Dann verhindert abstract nur das direkte Instanziieren.

Kann ein Interface ein anderes erweitern?

Ja, mit extends, sogar mehrere. Eine Klasse implementiert dann alle geerbten abstrakten Methoden.

Was ist ein Functional Interface?

Ein Interface mit genau einer abstrakten Methode. Seine Instanzen kann man mit Lambdas oder Method References erzeugen.

Warum ist Comparator funktional, obwohl es equals deklariert?

Methoden, die Object-Methoden entsprechen, zählen nicht zur SAM-Regel. Es bleibt nur compare als abstrakte Methode.

Was macht @FunctionalInterface?

Der Compiler prüft, dass genau eine abstrakte Methode existiert. Ohne die Annotation funktionieren Lambdas trotzdem.

Nennen Sie wichtige Functional Interfaces.

Function, Supplier, Consumer, Predicate, BiFunction, UnaryOperator, BinaryOperator, Runnable, Callable, Comparator.

Was ist ein Marker-Interface?

Ein Interface ohne Methoden, das einen Typ markiert, z. B. Serializable oder RandomAccess. Man kann es mit instanceof prüfen.

Was ist das Template Method Pattern?

Eine abstrakte Klasse legt den Ablauf in einer finalen Methode fest. Unterklassen füllen einzelne abstrakte Schritte.

Kann ein Interface final sein?

Nein. Man kann es aber sealed machen und die Implementierungen mit permits begrenzen.

Kann man eine Interface-Methode protected machen?

Nein. Interface-Methoden sind public oder private.

Ist FooService + FooServiceImpl immer nötig?

Nein. Ein Interface lohnt sich bei mehreren Implementierungen oder an Modulgrenzen. Spring und Mockito brauchen es nicht zwingend.

Was passiert mit binärer Kompatibilität, wenn ich eine default-Methode hinzufüge?

Alte Klassen laufen weiter und erben die default-Methode. Nur wenn sie mit einer anderen default kollidiert, bricht das Neu-Kompilieren.

Szenario: Sie müssen einem Interface, das 20 Teams implementieren, eine Methode hinzufügen. Wie?

Als default-Methode mit sicherem Verhalten, dokumentiert und versioniert. Später eventuell abstrakt machen, mit Vorlauf und Changelog.

Szenario: Nach einem Library-Upgrade bricht der Build mit „inherits unrelated defaults". Was tun?

Zwei Interfaces haben jetzt dieselbe default-Methode. In der Klasse überschreiben und bewusst mit X.super.m() die richtige Version wählen.

Szenario: Eine abstrakte Basisklasse hat 40 Methoden und 15 Unterklassen. Wie gehen Sie vor?

Verhalten in kleine Interfaces und Komponenten aufteilen. Unterklassen schrittweise auf Komposition umstellen, mit Tests als Sicherheitsnetz.
