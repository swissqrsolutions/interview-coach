JIT-Compiler

Java · Tier 1 · Quellen: OpenJDK HotSpot, JEP 197, JEP 483, JEP 515, -XX:+PrintFlagsFinal auf OpenJDK 17.0.3, HotSpot-Quellcode compiler_globals.hpp

Gerüst

Warum?
Interpreter ist langsam: 3700 ms gegen 120 ms mit JIT. Kompiliert wird nur heisser Code, mit echtem Profil.
Wie innen?
Stufe 0 Interpreter → 3 C1 mit Profil → 4 C2. Falsche Annahme → Deoptimierung; lange Schleife → OSR.
Zahlen
C1 ab ca. 200, C2 ab ca. 5000 Aufrufen. Inlining bis 35 Bytes, heiss bis 325. Code Cache 240 MB.
Vergleich
JIT: Warm-up, dann Spitzenleistung. Native Image: Start in ms, kein Laufzeit-Profil. AOT Cache: JIT mit warmem Start.
Produktion
Erste Requests nach Deploy langsam; 0,5 CPU verlängert Warm-up. Code Cache voll → Compiler aus.
Design
Kleine Methoden, wenige Klassen pro heisser Aufrufstelle → Inlining. Lang laufend → JIT, kurz lebend → Native Image.

Antwort-Muster

Frage: Was macht der JIT-Compiler?

  1. Mechanismus: Er übersetzt heissen Bytecode zur Laufzeit in Maschinencode und nutzt dabei das Profil.
  2. Zahl: C1 kompiliert nach ca. 200 Aufrufen, C2 nach ca. 5000.
  3. Trade-off: Der Preis ist Warm-up, die ersten Requests laufen noch im Interpreter oder C1.
  4. Produktion: Darum melde ich einen Pod erst nach Warm-up-Requests als bereit.
Kern: Der JIT-Compiler (Just-in-Time) übersetzt heissen Bytecode zur Laufzeit in optimierten Maschinencode. Er optimiert mit echten Messdaten aus dem laufenden Programm. Er macht die Ausführung schnell, nicht die Kompilierung.

1. Wo sitzt der JIT in der JVM?

  1. javac übersetzt Java in Bytecode. Bytecode ist für keine echte CPU.
  2. Der Class Loader lädt die Klasse und prüft den Bytecode.
  3. Die Execution Engine führt ihn aus: zuerst der Interpreter, später der JIT.
  4. Der JIT legt den fertigen Maschinencode in den Code Cache.

2. Die Reise einer Methode (die Geschichte zum Merken)

  1. Start: Interpreter (Stufe 0). Die JVM führt Bytecode Befehl für Befehl aus. Das ist langsam, aber sofort bereit. Sie zählt Aufrufe und Schleifen-Durchläufe jeder Methode.
  2. Die Methode wird heiss: C1 (Stufe 3). Nach ca. 200 Aufrufen kompiliert C1 sie schnell zu Maschinencode. Dieser Code sammelt ein Profil: welche Klassen kommen vor, welche if-Zweige laufen.
  3. Die Methode ist sehr heiss: C2 (Stufe 4). Nach ca. 5000 Aufrufen kompiliert C2 sie neu. C2 nutzt das Profil und wettet: „Hier kommt immer nur ArrayList.“ Damit optimiert er stark.
  4. Code Cache. Der Maschinencode liegt im Code Cache. Ab jetzt springt die JVM direkt dorthin.
  5. Die Wette ist falsch: Deoptimierung. Kommt plötzlich eine LinkedList, trifft der Code eine uncommon trap. Die JVM wirft den C2-Code weg (made not entrant), geht zurück in den Interpreter und misst neu.
  6. Lange Schleife in main? Die Methode wird nur einmal aufgerufen. Darum ersetzt die JVM den Code mitten in der Schleife: On-Stack Replacement (OSR).

Diese 5 Stufen (0–4) heissen Tiered Compilation. Sie ist seit Java 8 Standard. Stufe 1 und 2 nutzt C1 nur in Sonderfällen (z. B. wenn C2 überlastet ist).

3. Beispiel: den JIT bei der Arbeit sehen

public class Demo {
  static int square(int x) { return x * x; }
  public static void main(String[] args) {
    long sum = 0;
    for (int i = 0; i < 1_000_000; i++) sum += square(i);
    System.out.println(sum);
  }
}
$ java -XX:+PrintCompilation Demo
15    6       3   Demo::square (4 bytes)
16    7       4   Demo::square (4 bytes)
16    6       3   Demo::square (4 bytes)   made not entrant
16    8 %     3   Demo::main @ 4 (32 bytes)
16   10 %     4   Demo::main @ 4 (32 bytes)

Echte Ausgabe, OpenJDK 21. Spalten: Zeit in ms · Compile-ID · % = OSR · Stufe · Methode.

  1. square wird zuerst von C1 (Stufe 3), dann von C2 (Stufe 4) kompiliert.
  2. Danach wird die C1-Version weggeworfen: made not entrant. Die C2-Version ersetzt sie.
  3. main läuft nur einmal, aber die Schleife ist heiss. Darum OSR (%) mitten in der Schleife.

Gemessen (300 Mio. Durchläufe, gleicher Code):

  • -Xint (nur Interpreter): 3700 ms
  • -XX:TieredStopAtLevel=1 (nur C1): 133 ms
  • Standard (C1 + C2): 120 ms

Der JIT macht diesen Code also ca. 30× schneller.

4. Die wichtigsten Optimierungen von C2

  1. Inlining (die wichtigste): Der Code einer kleinen Methode wird direkt an der Aufrufstelle eingesetzt. Kein Aufruf mehr, und alle anderen Optimierungen sehen mehr Code. Grenzen: heisse Methoden bis 325 Bytes Bytecode, andere bis 35 Bytes.
  2. Devirtualisierung: Ein Interface-Aufruf hat oft nur eine echte Klasse. Der JIT ruft sie direkt auf und kann sie inlinen.
    • monomorph (1 Klasse) und bimorph (2 Klassen): schnell.
    • megamorph (3+ Klassen): langsamer Aufruf über die Methodentabelle, kein Inlining.
  3. Escape Analysis: Verlässt ein Objekt die Methode nicht, muss es nicht auf den Heap. C2 zerlegt es in einzelne Variablen (Scalar Replacement). Weniger Arbeit für den GC.
  4. Lock Elision und Lock Coarsening: Ein Lock auf einem Objekt, das nur ein Thread sieht, fällt weg. Viele kleine Locks nacheinander werden zu einem.
  5. Schleifen: Loop Unrolling, Range-Check-Elimination (Array-Grenzen nur einmal prüfen), Vektorisierung (SIMD).
  6. Dead Code Elimination und Constant Folding: Unnötiger Code fällt weg, feste Werte werden vorher berechnet.
  7. Intrinsics: Für bekannte Methoden (z. B. System.arraycopy, Math, String) hat der JIT fertigen CPU-Code.

5. JIT vs AOT vs Interpreter

  • Interpreter: startet sofort, läuft langsam, kein Kompilieren.
  • JIT (HotSpot): Warm-up nötig, dann höchste Leistung. Passt sich zur Laufzeit an. Braucht CPU und Speicher für Compiler und Code Cache.
  • AOT – GraalVM Native Image: alles vorher kompiliert. Start in Millisekunden, wenig Speicher. Aber: lange Build-Zeit, Reflection braucht Konfiguration, keine Laufzeit-Optimierung, Spitzenleistung oft etwas tiefer. Spring Boot 3 unterstützt es.
  • Mittelweg – AOT Cache (Projekt Leyden): Java 24 speichert geladene Klassen vorab (JEP 483). Java 25 speichert auch Profile (JEP 515). Der JIT startet so schneller warm, bleibt aber ein JIT.
  • CDS (Class Data Sharing): geladene Klassen als Datei teilen. Schnellerer Start, älter und einfacher als Leyden.

6. In der Produktion

  1. Warm-up nach jedem Deployment: Die ersten Requests sind langsam (Interpreter und C1). Lösung: Readiness Probe erst nach Warm-up-Requests auf „bereit“ setzen, AOT Cache oder CDS nutzen.
  2. Kleine CPU-Limits in Kubernetes: Die Compiler-Threads brauchen CPU. Bei 0,5 CPU dauert der Warm-up lange, und es gibt CPU-Throttling. Darum beim Start mehr CPU erlauben (Requests/Limits passend setzen).
  3. Code Cache voll: Meldung CodeCache is full. Compiler has been disabled. Danach wird neuer Code nur noch interpretiert, die Anwendung wird langsam. Lösung: -XX:ReservedCodeCacheSize erhöhen (Standard 240 MB).
  4. Serverless (z. B. Azure Functions): Kalte Starts mit JIT sind teuer. Native Image oder AOT Cache helfen.
  5. Benchmarks: Ohne Warm-up misst man den Interpreter. Und der JIT löscht Code, dessen Ergebnis niemand nutzt. Darum JMH.
  6. Riesige Methoden: Über 8000 Bytes Bytecode kompiliert HotSpot nicht (z. B. generierter Code). Lösung: Methode aufteilen.

7. Diagnose: Werkzeuge und Flags

  • -XX:+PrintCompilation: welche Methode wann auf welcher Stufe kompiliert wird.
  • -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining: was inlined wird und warum nicht.
  • JFR (Java Flight Recorder): Events jdk.Compilation, jdk.Deoptimization, jdk.CodeCacheFull. Geeignet für die Produktion.
  • jcmd <pid> Compiler.codecache: wie voll der Code Cache ist.
  • -Xint (nur Interpreter), -XX:TieredStopAtLevel=1 (nur C1, schneller Start, z. B. lokal in der Entwicklung).
  • JITWatch: JIT-Logs grafisch lesen.
  • java -XX:+PrintFlagsFinal -version: zeigt die echten Schwellwerte. Auf OpenJDK 17.0.3: Tier3InvocationThreshold = 200, Tier4InvocationThreshold = 5000, Tier3BackEdgeThreshold = 60000, Tier4BackEdgeThreshold = 40000 (Schleifen-Zähler für OSR).
  • Gleiche Ausgabe, Inlining und Code Cache: MaxInlineSize = 35, FreqInlineSize = 325, ReservedCodeCacheSize = 251658240 (240 MB), DontCompileHugeMethods = true. Die Grenze 8000 Bytes (HugeMethodLimit) ist ein develop-Flag und steht nur im Quellcode.
  • Schwellen sind nicht fix: Ist die C1-Queue voll (Tier3LoadFeedback = 5 Einträge pro Compiler-Thread), verdoppeln sich die Stufe-3-Schwellen. So schützt sich die JVM vor Überlast.

8. Senior-Punkte

  1. Der JIT wettet. Er optimiert mit Annahmen aus dem Profil. Ist eine Annahme falsch, deoptimiert er. Darum kann Leistung kurz einbrechen, z. B. wenn neuer Code oder eine neue Klasse geladen wird.
  2. Warm-up ist ein Betriebsthema, nicht nur ein Java-Thema: Readiness Probe, CPU-Limits, Rolling Update langsam genug.
  3. Lesbarer Code ist meist schneller Code. Kleine Methoden werden inlined. Mikro-Optimierungen von Hand helfen selten.
  4. Megamorphe Aufrufe (viele Klassen hinter einem Interface an einer heissen Stelle) verhindern Inlining. Das sieht man im Profiler, nicht im Code-Review.
  5. JIT oder Native Image ist eine Abwägung: lange laufender Service mit viel Last → JIT. Kurz lebende Funktion, wenig Speicher → Native Image oder AOT Cache.
  6. Erst messen, dann Flags ändern. Standard-Einstellungen sind fast immer richtig.

10. Fallen

  • „Der JIT macht das Kompilieren schneller.“ → Falsch. Er macht die Ausführung schneller. Kompilieren kostet sogar Zeit.
  • „Java ist interpretiert, darum langsam.“ → Nur am Anfang. Heisser Code läuft als optimierter Maschinencode.
  • „AOT ist immer schneller.“ → Nur beim Start. Bei langer Laufzeit ist der JIT oft schneller.
  • „javac optimiert den Code.“ → Kaum. Die echte Optimierung macht der JIT.

11. Selbsttest

Warum?

Was ist der JIT-Compiler?

Er übersetzt heissen Bytecode zur Laufzeit in optimierten Maschinencode. Er nutzt dafür Messdaten aus dem laufenden Programm.

Warum interpretiert die JVM zuerst?

Schneller Start. Und sie sammelt Profildaten, damit der JIT später besser optimiert.

Warum kompiliert die JVM nicht alles sofort mit C2?

C2 kompiliert langsam und braucht ein Profil für gute Annahmen. Kalter Code würde nur CPU und Code Cache verbrauchen.

Wie innen?

Wie kommt Java-Code bis zur CPU?

javac → Bytecode → Class Loader → Interpreter → heisse Methoden kompiliert der JIT (C1, dann C2) → Code Cache → CPU.

Was ist Tiered Compilation?

Die 5 Stufen 0–4: Interpreter, dann C1, dann C2. Seit Java 8 Standard. Verbindet schnellen Start mit hoher Spitzenleistung.

Warum ist Inlining die wichtigste Optimierung?

Der Code der aufgerufenen Methode wird direkt eingesetzt. Das spart den Aufruf und öffnet die Tür für alle anderen Optimierungen.

Was ist Deoptimierung?

Eine Annahme von C2 stimmt nicht mehr, z. B. eine neue Klasse. Die JVM wirft den Code weg und geht zurück in den Interpreter. Später kompiliert sie neu.

Was ist OSR?

On-Stack Replacement. Die JVM wechselt mitten in einer laufenden Schleife zum kompilierten Code. Wichtig für lange Schleifen in Methoden, die nur einmal laufen.

Was ist Escape Analysis?

C2 prüft, ob ein Objekt die Methode verlässt. Wenn nicht, legt er es nicht auf den Heap, sondern zerlegt es in Variablen. Weniger GC-Arbeit, und Locks darauf fallen weg.

Zahlen

Wann wird eine Methode kompiliert?

Wenn ihre Zähler (Aufrufe und Schleifen-Durchläufe) eine Schwelle überschreiten. Grob: C1 nach ca. 200, C2 nach ca. 5000 Aufrufen.

Bis zu welcher Grösse inlinet C2 eine Methode?

Normale Methoden bis 35 Bytes Bytecode (MaxInlineSize). Heisse Methoden bis 325 Bytes (FreqInlineSize).

Was geht kaputt, wenn eine Methode mehr als 8000 Bytes Bytecode hat?

HotSpot kompiliert sie nicht (DontCompileHugeMethods). Sie bleibt im Interpreter und ist langsam. Lösung: Methode aufteilen, oft bei generiertem Code.

Vergleich

Was ist der Unterschied zwischen C1 und C2?

C1 kompiliert schnell und optimiert wenig. C2 kompiliert langsamer, optimiert stark und nutzt das Profil von C1.

Warum ist AOT nicht immer schneller als der JIT?

AOT kennt kein Laufzeit-Profil. Der JIT optimiert mit echten Typen und Zweigen. Darum ist er bei langer Laufzeit oft schneller.

Was ist der Unterschied zwischen AOT Cache und Native Image?

Der AOT Cache speichert geladene Klassen (JEP 483, Java 24) und Profile (JEP 515, Java 25). Der JIT bleibt aktiv. Native Image kompiliert alles vorab und hat keinen JIT.

Produktion

Was geht kaputt, wenn der Code Cache voll ist?

Speicher für den kompilierten Maschinencode. Ist er voll, stoppt der JIT. Neuer Code läuft nur noch im Interpreter. Lösung: ReservedCodeCacheSize erhöhen.

Warum braucht ein Benchmark Warm-up?

Sonst misst man den Interpreter. Und der JIT entfernt Code, dessen Ergebnis niemand nutzt. Darum JMH.

Wie sehen Sie, was der JIT macht?

-XX:+PrintCompilation, PrintInlining, JFR-Events (jdk.Compilation, jdk.Deoptimization), jcmd Compiler.codecache, JITWatch.

Szenario: Nach jedem Deployment sind die ersten Requests langsam. Warum, und was tun Sie?

JIT-Warm-up: Der Code läuft noch im Interpreter oder in C1. Lösung: Warm-up-Requests, Readiness Probe erst danach, genug CPU beim Start, AOT Cache oder CDS. Prüfen mit JFR.

Szenario: Der Service ist nach Tagen plötzlich langsam, ohne mehr Last. Woran denken Sie?

Unter anderem: Code Cache voll (Meldung im Log, jcmd Compiler.codecache). Dazu GC-Probleme und Memory Leaks prüfen.

Szenario: Der Pod hat nur 0,5 CPU und braucht Minuten zum Warmlaufen. Warum?

Die Compiler-Threads bekommen zu wenig CPU, und es gibt Throttling. Lösung: CPU-Limit erhöhen oder beim Start mehr erlauben, oder AOT Cache.

Design

Wann wählen Sie JIT, wann GraalVM Native Image?

JIT für lange laufende Services mit hoher Last. Native Image für schnellen Start und wenig Speicher, z. B. Serverless. Preis: Build-Zeit, Reflection-Konfiguration, keine Laufzeit-Optimierung.

Warum können megamorphe Aufrufe langsam sein?

An der Aufrufstelle kommen 3 oder mehr Klassen vor. Der JIT ruft dann über die Methodentabelle auf und kann nicht inlinen.

Warum lohnt sich Mikro-Optimierung von Hand selten?

Der JIT inlinet kleine Methoden und entfernt Objekte per Escape Analysis selbst. Lesbarer Code mit kleinen Methoden ist meist schon schnell. Erst messen, dann ändern.
