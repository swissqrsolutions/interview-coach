Memory Leaks und OutOfMemoryError

Java · Tier 1 · Quellen: Java SE 25 Troubleshooting Guide („Troubleshoot Memory Leaks“, „Understand the OutOfMemoryError Exception“), Java SE 21 Troubleshooting Guide, OpenJDK-Quellcode JDK 21/25 (runtime/os.hpp, prims/jvm.cpp, java.nio.Bits, gc_globals.hpp, globals.hpp, g1CollectedHeap.cpp), JEP 387 (Elastic Metaspace)

Kern: Ein Memory Leak in Java ist ein Objekt, das das Programm nicht mehr braucht, aber noch erreichbar ist. Der GC darf es darum nicht löschen. Ein OutOfMemoryError (OOM) kommt, wenn ein Speicherbereich voll ist und der GC keinen Platz mehr schafft. Die Meldung zeigt, welcher Bereich voll ist.

1. Wo sitzt ein Memory Leak?

  1. GC Roots: Eine GC Root ist ein Startpunkt, den der GC immer als lebendig ansieht. Beispiele: statische Felder, lokale Variablen auf Thread-Stacks, aktive Threads, JNI-Referenzen.
  2. Erreichbarkeit: Der GC folgt allen Referenzen ab den Roots. Alles, was er erreicht, bleibt. Alles andere ist Müll und wird frei.
  3. Leak: Ein statischer CACHE hält Sessions, die niemand mehr braucht. Sie sind erreichbar, also kein Müll. Der GC kann nichts tun.
  4. Folge: Die Objekte wandern in die Old Generation und füllen sie Stück für Stück. Am Ende kommt ein OutOfMemoryError.
  5. Heap Dump: Ein Heap Dump ist eine Datei mit allen Objekten im Heap und ihren Referenzen. Er zeigt, wer den Speicher hält.

2. Die Reise zum OutOfMemoryError (die Geschichte zum Merken)

  1. Der Leak beginnt: Jeder Request legt eine Session in eine statische Map. Niemand entfernt sie. Pro Request bleiben 10 KB übrig.
  2. Die Old Gen füllt sich: Die Sessions überleben jeden Young GC und landen in der Old Gen. Nach jedem GC ist der Heap etwas voller. Im GC-Log steigt die Zahl nach dem Pfeil.
  3. Der GC gerät in Stress: Der GC läuft immer öfter. Dann kommen Full GCs (Stop-the-World über den ganzen Heap). Die Latenz steigt, der Durchsatz fällt.
  4. Full GC ohne Erfolg: Der Full GC findet nichts mehr zum Freigeben. Das Log zeigt 15M->15M(16M).
  5. OutOfMemoryError: Die nächste Allokation scheitert. Der Thread, der gerade new ruft, bekommt den Fehler. Das ist oft nicht der Thread mit dem Leak.
  6. Heap Dump: Mit -XX:+HeapDumpOnOutOfMemoryError schreibt die JVM vorher eine .hprof-Datei. Sie ist so gross wie der belegte Heap.
  7. Analyse: In Eclipse MAT zeigt der Dominator Tree das Objekt, das den meisten Speicher hält. Path to GC Roots zeigt, warum es lebt.

3. Beispiel: einen Leak bis zum OOM treiben

public class Leak {
  record Session(String id, byte[] data) {}
  static final Map<String, Session> CACHE = new HashMap<>();   // wächst ohne Grenze

  public static void main(String[] args) throws Exception {
    switch (args[0]) {
      case "heap" -> { for (int i = 0; ; i++) CACHE.put("s" + i, new Session("s" + i, new byte[10_000])); }
      case "slow" -> { /* 1000 Sessions, dann 60 s schlafen für jcmd */ }
      case "meta" -> { /* je Iteration neuer URLClassLoader + Proxy-Klasse, alles behalten */ }
      case "direct" -> { /* ByteBuffer.allocateDirect(1 MB) in einer Schleife, alles behalten */ }
      case "gc" -> { Map<Integer, String> m = new HashMap<>(); for (int i = 0; ; i++) m.put(i, "v" + i); }
    }
  }
}

Echte Ausgabe, OpenJDK 17.0.3 (Windows x64). Gekürzt: GC-Log-Zeilen, Stacktraces und Histogramm-Zeilen (markiert mit ...). Der Java-Code ist gekürzt. Java 21 und 25 geben die gleichen Meldungen aus; der Text für Direct Memory ist im Quellcode von 21 und 25 gleich. Den Fehler unable to create native thread haben wir nicht provoziert, weil er das ganze System belastet.

  1. GC-Log: Der Heap ist nach jedem GC voller: 5M, 6M, dann 15M. Am Ende räumen Full GCs nichts mehr frei (15M->15M). Das ist das typische Muster eines Leaks.
  2. Heap Dump: Die Datei ist 18 MB gross, also etwas mehr als der 16-MB-Heap. Ein Dump von einem 8-GB-Heap ist entsprechend etwa 8 GB gross.
  3. Fehler im Fehler: Auch das Ausgeben des Stacktraces braucht Speicher. Darum kommt die Meldung thrown from the UncaughtExceptionHandler. Ein Programm nach einem OOM ist nicht mehr verlässlich.
  4. Histogramm: [B (byte-Arrays) belegen 10 MB. Genau 1000 Leak$Session zeigen den Verursacher. Das Histogramm zeigt nur flache Grössen; wer die Arrays hält, zeigt erst der Heap Dump.
  5. Metaspace: Jeder neue Class Loader mit eigener Proxy-Klasse belegt Metaspace. Nach ca. 2 000 Klassen sind 16 MB voll.
  6. Direct Memory: Die Meldung nennt Grösse, Belegung und Limit. Trotz HeapDumpOnOutOfMemoryError entsteht kein Heap Dump. Diesen Fehler wirft Java-Code (java.nio.Bits), nicht die JVM.
  7. GC overhead: Mit dem Parallel GC erkennt die JVM, dass sie fast nur noch GC macht. Sie bricht früher ab, statt endlos zu kriechen.
  8. Array zu gross: Ein Array über dem VM-Limit scheitert sofort, egal wie gross der Heap ist.
  9. ExitOnOutOfMemoryError: Die JVM beendet sich beim ersten OOM mit Exit-Code 3. So startet Kubernetes den Pod sauber neu.

4. Details, die Interviewer fragen

  1. Java heap space: Ein Objekt passt nicht in den Heap. Ursache: Leak oder zu kleiner Heap. Unterscheiden: Wächst der Heap nach Full GCs stetig, ist es ein Leak.
  2. GC overhead limit exceeded: Der GC braucht über 98 % der Zeit (GCTimeLimit) und gewinnt unter 2 % Heap zurück (GCHeapFreeLimit). Das gilt in Java 21 und 25 nur für den Parallel GC. G1 (Standard) wirft stattdessen Java heap space. Abschalten mit -XX:-UseGCOverheadLimit.
  3. Metaspace: Klassen-Metadaten erreichen MaxMetaspaceSize. Ursache: Class-Loader-Leak oder viele generierte Klassen (Proxies, Lambdas, Groovy, Bytecode-Bibliotheken).
  4. Compressed class space: Die Klassenstrukturen erreichen CompressedClassSpaceSize (Standard 1 GB). Gleiche Ursachen wie bei Metaspace.
  5. Cannot reserve … bytes of direct buffer memory: Direct ByteBuffers erreichen MaxDirectMemorySize. Bis Java 12 hiess die Meldung kurz Direct buffer memory. Ursache: Netty-Buffer ohne release() oder zu wenig GC, der die Buffer-Objekte einsammelt.
  6. unable to create native thread: possibly out of memory or process/resource limits reached: Das Betriebssystem erlaubt keinen weiteren Thread. Ursache: Thread-Leak, ulimit -u, pids.max im Container oder kein Speicher für den Stack.
  7. Requested array size exceeds VM limit: Ein Array ist grösser als die JVM erlaubt (knapp unter Integer.MAX_VALUE Elemente). Ursache: meist ein Rechenfehler bei der Grösse.
  8. request … bytes for … Out of swap space?: Eine native Allokation der JVM scheitert. Die JVM stürzt ab und schreibt ein Fatal Error Log (hs_err_pid<pid>.log).
  9. Typische Leak-Ursachen:
    • Statische Collections: Caches ohne Grenze und Ablaufzeit.
    • Listener und Callbacks: registriert, aber nie abgemeldet.
    • ThreadLocal in Thread-Pools: Der Thread lebt ewig, also auch der Wert. Lösung: remove() im finally.
    • Veränderte HashMap-Schlüssel: Der Eintrag ist unerreichbar, belegt aber Speicher.
    • Nicht geschlossene Ressourcen: Streams, Connections, Statements. Lösung: try-with-resources.
    • Class-Loader-Leak: Ein Objekt der alten App-Version bleibt erreichbar, z. B. über einen JDBC-Treiber oder ThreadLocal. Dann bleibt der ganze Class Loader mit allen Klassen im Metaspace.
    • Innere Klassen: Eine nicht-statische innere Klasse hält eine versteckte Referenz auf das äussere Objekt.
  10. Shallow vs Retained Size: Shallow Size ist die Grösse des Objekts selbst. Retained Size ist alles, was mit ihm frei würde. Ein Leak zeigt sich in der Retained Size.
  11. Dominator: Ein Objekt A dominiert B, wenn jeder Weg von den Roots zu B über A geht. Der Dominator Tree in MAT zeigt so die echten Besitzer des Speichers.
  12. Referenztypen: WeakReference hält ein Objekt nicht am Leben (z. B. WeakHashMap-Schlüssel). SoftReference wird erst bei Speichermangel geleert. Beide sind kein Ersatz für einen begrenzten Cache.
  13. OOM fangen: OutOfMemoryError ist ein Error, keine Exception. Man sollte ihn nicht fangen und weiterlaufen. Der Zustand der Anwendung ist danach unklar.

5. Vergleich

  • Memory Leak: Speicher steigt stetig, auch nach Full GCs. Mehr Heap verschiebt nur den Zeitpunkt des OOM.
  • Zu kleiner Heap: Speicher ist stabil, aber zu nah am Limit. Eine Lastspitze reicht für ein OOM. Mehr Heap löst es.
  • Allokations-Spitze: Ein Request lädt z. B. 2 GB in eine Liste. Kein Leak, sondern ein Designfehler. Lösung: Streaming, Paging.
  • Java-OOM: Die JVM wirft OutOfMemoryError mit Meldung, Heap Dump möglich.
  • Container OOMKilled: Der Kernel beendet den Prozess (Exit 137). Keine Java-Meldung, kein Heap Dump. Ursache: Summe aller Bereiche über dem Pod-Limit.
  • Nativer Leak: RSS wächst, Heap und NMT bleiben stabil. Ursache: JNI-Bibliothek oder malloc-Fragmentierung ausserhalb der JVM.

6. In der Produktion

  1. Kein Heap Dump nach OOM: Das Flag fehlt, oder der Pfad liegt im flüchtigen Container-Dateisystem. Lösung: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps auf ein Volume mit genug Platz.
  2. App lebt halb tot weiter: Ein Thread stirbt am OOM, die anderen laufen fehlerhaft weiter. Lösung: -XX:+ExitOnOutOfMemoryError. Kubernetes startet den Pod neu.
  3. Unbegrenzter Cache: Eine statische Map wächst mit jedem Kunden. Lösung: Caffeine mit maximumSize und expireAfterWrite.
  4. ThreadLocal-Leak im Webserver: Tomcat-Threads leben ewig, ThreadLocal-Werte auch. Lösung: ThreadLocal.remove() im finally oder im Filter.
  5. Metaspace-Leak nach Redeploy: Jeder Redeploy lädt alle Klassen neu, der alte Class Loader bleibt. Lösung: Leak in MAT über ClassLoader-Pfade finden. Besser: ein Deployment pro Container, Neustart statt Redeploy.
  6. Heap Dump enthält Geheimnisse: Ein Dump hat Passwörter, Tokens und Kundendaten im Klartext. Lösung: wie Produktionsdaten behandeln, verschlüsselt speichern, schnell löschen.
  7. Dump stoppt die App: Ein Heap Dump ist eine lange Pause. Bei 30 GB Heap dauert er Minuten. Lösung: Pod vorher aus dem Load Balancer nehmen, -gz nutzen oder mit JFR beginnen.

7. Diagnose: Werkzeuge, Flags und Befehle

  • -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps: Dump beim ersten OOM aus der JVM. -XX:HeapDumpGzipLevel=1 komprimiert ihn (seit Java 17).
  • -XX:+ExitOnOutOfMemoryError: beenden beim ersten OOM. -XX:+CrashOnOutOfMemoryError: Absturz mit hs_err-Log und Core Dump.
  • jcmd <pid> GC.heap_dump -gz=1 /dumps/app.hprof: Dump einer laufenden JVM. Standard: nur lebende Objekte (vorher Full GC).
  • jcmd <pid> GC.class_histogram: Objekte pro Klasse. Mehrmals im Abstand von Minuten ausführen und vergleichen.
  • jcmd <pid> GC.heap_info: aktuelle Belegung von Heap und Metaspace.
  • -Xlog:gc*:file=gc.log: GC-Log. Wichtig ist die Heap-Grösse nach dem GC über die Zeit.
  • JFR (Java Flight Recorder): Das Event jdk.OldObjectSample zeigt alte, lebende Objekte mit Allokations-Stack. jcmd <pid> JFR.dump filename=rec.jfr path-to-gc-roots=true fügt den Weg zur GC Root hinzu.
  • Eclipse MAT: Leak Suspects Report, Dominator Tree, Path to GC Roots, OQL. Für grosse Dumps braucht MAT selbst viel RAM.
  • NMT: -XX:NativeMemoryTracking=summary, dann jcmd <pid> VM.native_memory baseline und summary.diff für Metaspace, Threads und Direct Memory.
  • jcmd <pid> VM.classloader_stats und VM.metaspace: welcher Class Loader wie viel Metaspace hält.
  • jcmd <pid> Thread.print: Thread-Liste bei unable to create native thread.
  • Monitoring: Micrometer-Metriken wie jvm_memory_used_bytes{area="heap"} nach GC, jvm_buffer_memory_used_bytes, jvm_threads_live_threads, Alarm bei stetigem Anstieg.

8. Senior-Punkte

  1. Erst die Meldung lesen. Sie sagt, welcher Bereich voll ist. Mehr -Xmx hilft bei Metaspace, Direct oder native thread nicht.
  2. Mehr Heap ist keine Lösung für einen Leak. Er verschiebt nur den Absturz und macht Dumps und Full GCs grösser.
  3. Exit statt Weiterlaufen: Nach einem OOM ist der Zustand unklar. ExitOnOutOfMemoryError plus Neustart durch Kubernetes ist meist die sichere Wahl.
  4. Heap Dump oder JFR: Ein Dump ist genau, aber gross, langsam und enthält sensible Daten. JFR mit OldObjectSample ist leicht genug für die Produktion. Erst JFR, dann gezielt ein Dump.
  5. Jeder Cache braucht eine Grenze und eine Ablaufzeit. Das ist eine Architektur-Entscheidung, keine Optimierung.
  6. Grenzen für native Bereiche (MaxMetaspaceSize, MaxDirectMemorySize) machen aus einem stillen Container-Kill einen klaren Java-Fehler mit Stacktrace.

10. Fallen

  • „Java hat einen GC, also gibt es keine Memory Leaks.“ → Falsch. Der GC löscht nur unerreichbare Objekte. Unnötige, aber erreichbare Objekte bleiben.
  • „Bei OOM einfach -Xmx erhöhen.“ → Falsch. Bei einem Leak verschiebt das nur den Absturz. Bei Metaspace- oder Thread-OOM hilft es gar nicht.
  • „OutOfMemoryError: PermGen space heisst MaxPermSize erhöhen.“ → Veraltet. Die PermGen gibt es seit Java 8 nicht mehr. Heute heisst die Meldung Metaspace, und das Flag ist MaxMetaspaceSize.
  • „Der Stacktrace des OOM zeigt den Verursacher.“ → Falsch. Er zeigt nur die letzte Allokation. Den Verursacher zeigt der Heap Dump.
  • „HeapDumpOnOutOfMemoryError schreibt bei jedem OOM einen Dump.“ → Falsch. Nur bei OOMs aus der JVM. Bei Direct Memory (aus java.nio.Bits) gibt es keinen Dump.
  • „GC overhead limit exceeded kommt bei jedem GC.“ → Falsch. In Java 21 und 25 nur beim Parallel GC. G1 meldet Java heap space.
  • „OOMKilled im Pod ist ein Java-OOM.“ → Falsch. Das ist der Linux-Kernel. Java merkt nichts, es gibt keinen Dump.
  • „System.gc() rettet vor einem OOM.“ → Falsch. Die JVM macht vor jedem OOM schon einen Full GC.

11. Fragen

Was ist ein Memory Leak in Java?

Ein Objekt, das nicht mehr gebraucht wird, aber noch von einer GC Root erreichbar ist. Der GC darf es darum nicht löschen.

Wie kann es mit einem GC überhaupt Leaks geben?

Der GC entscheidet nach Erreichbarkeit, nicht nach Nutzen. Eine vergessene Referenz hält das Objekt am Leben.

Was ist eine GC Root?

Ein Startpunkt, den der GC immer als lebendig ansieht. Beispiele: statische Felder, lokale Variablen aktiver Threads, JNI-Referenzen.

Nennen Sie typische Ursachen für Leaks.

Statische Caches ohne Grenze, nicht abgemeldete Listener, ThreadLocal in Thread-Pools, nicht geschlossene Ressourcen, veränderte HashMap-Schlüssel, Class-Loader-Leaks.

Welche OutOfMemoryError-Meldungen kennen Sie?

Java heap space, GC overhead limit exceeded, Metaspace, Compressed class space, Cannot reserve … bytes of direct buffer memory, unable to create native thread, Requested array size exceeds VM limit.

Was bedeutet „Java heap space“?

Ein Objekt passt nicht mehr in den Heap, auch nach einem Full GC. Ursache ist ein Leak oder ein zu kleiner Heap.

Was bedeutet „GC overhead limit exceeded“?

Der GC braucht über 98 % der Zeit und gewinnt unter 2 % zurück. In Java 21 und 25 meldet das nur der Parallel GC.

Was bedeutet „OutOfMemoryError: Metaspace“?

Die Klassen-Metadaten haben MaxMetaspaceSize erreicht. Meist ein Class-Loader-Leak oder sehr viele generierte Klassen.

Was bedeutet „unable to create native thread“?

Das Betriebssystem erlaubt keinen weiteren Thread. Ursachen: Thread-Leak, Prozess- oder Container-Limits, kein Speicher für den Stack.

Was bedeutet der Fehler zu Direct Buffer Memory?

Direct ByteBuffers haben MaxDirectMemorySize erreicht. Typisch bei Netty ohne release() oder zu grossen Puffern.

Was ist ein Heap Dump?

Eine Datei (.hprof) mit allen Objekten im Heap und ihren Referenzen. Man analysiert ihn mit Eclipse MAT.

Wie bekommen Sie einen Heap Dump?

Automatisch mit -XX:+HeapDumpOnOutOfMemoryError oder manuell mit jcmd <pid> GC.heap_dump datei.hprof.

Was ist der Unterschied zwischen Shallow und Retained Size?

Shallow Size ist das Objekt allein. Retained Size ist alles, was frei würde, wenn das Objekt wegfällt.

Was zeigt der Dominator Tree?

Welche Objekte den meisten Speicher exklusiv halten. Ganz oben steht meist der Leak, z. B. eine grosse Map.

Was ist „Path to GC Roots“?

Die Referenzkette von einer GC Root zum Objekt. Sie zeigt, warum das Objekt noch lebt.

Wie erkennen Sie einen Leak im GC-Log?

Die Heap-Grösse nach jedem GC steigt stetig. Am Ende befreien Full GCs fast nichts mehr.

Was ist der Unterschied zwischen Leak und zu kleinem Heap?

Beim Leak steigt der Speicher nach GC immer weiter. Beim zu kleinen Heap ist er stabil, aber zu nah am Limit.

Warum ist ThreadLocal gefährlich in Thread-Pools?

Pool-Threads leben ewig, also auch ihre ThreadLocal-Werte. Ohne remove() bleiben sie und können sogar einen Class Loader festhalten.

Was ist ein Class-Loader-Leak?

Ein Objekt einer alten App-Version bleibt erreichbar. Dann bleiben ihr Class Loader und alle Klassen im Metaspace.

Sollte man OutOfMemoryError fangen?

Nein. Danach ist der Zustand der Anwendung unklar. Besser mit ExitOnOutOfMemoryError beenden und neu starten.

Was machen ExitOnOutOfMemoryError und CrashOnOutOfMemoryError?

Exit beendet die JVM beim ersten OOM. Crash bricht ab und schreibt ein hs_err-Log und einen Core Dump.

Hilft WeakHashMap gegen Leaks?

Nur für Schlüssel ohne andere Referenzen. Hält der Wert den Schlüssel fest, leakt sie trotzdem. Für Caches besser Caffeine mit Grenze.

Wie finden Sie Leaks in der Produktion ohne Heap Dump?

Mit JFR und dem Event jdk.OldObjectSample, mit Klassen-Histogrammen im Abstand und mit Metriken zum Heap nach GC.

Warum ist ein Heap Dump in der Produktion heikel?

Er stoppt die JVM lange, ist so gross wie der Heap und enthält Passwörter und Kundendaten im Klartext.

Was ist der Unterschied zwischen Java-OOM und OOMKilled?

Ein Java-OOM wirft die JVM, mit Meldung und Dump. OOMKilled ist der Linux-Kernel im Container, ohne Meldung und ohne Dump.

Szenario: Der Heap wächst über Tage, dann kommt „Java heap space“. Was tun Sie?

Heap Dump vom OOM in MAT öffnen, Dominator Tree und Path to GC Roots prüfen. Meist ist es ein Cache oder eine statische Collection. Lösung: Grenze und Ablaufzeit, dann im GC-Log prüfen.

Szenario: Nach jedem Redeploy im Application Server steigt der Metaspace, bis „OutOfMemoryError: Metaspace“ kommt. Warum?

Der alte Class Loader bleibt erreichbar, z. B. über ThreadLocal, JDBC-Treiber oder einen Thread. Mit VM.classloader_stats und MAT den Halter finden. Langfristig: Neustart statt Redeploy.

Szenario: Der Pod wird OOMKilled, aber der Heap ist nur halb voll. Wie gehen Sie vor?

NMT einschalten und RSS mit NMT vergleichen. Wachsen Direct Memory, Threads oder Metaspace, Grenzen setzen und den Leak suchen. MaxRAMPercentage senken, damit Platz für nativen Speicher bleibt.
