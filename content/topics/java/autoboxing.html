Primitive vs Wrapper, Autoboxing, Integer-Cache

Java · Tier 2 · Quellen: JLS 21 (§4.2 Primitive Types, §5.1.7 Boxing, §5.1.8 Unboxing, §15.25 Conditional Operator, §15.21 Equality), Java SE 25 API-Doku (Integer.valueOf, Integer Konstruktoren, Value-based Classes), JEP 390 (Warnings for Value-Based Classes, Java 16)

Kern: Java hat 8 primitive Typen (int, long …) und zu jedem eine Wrapper-Klasse (Integer, Long …). Autoboxing ist die automatische Umwandlung primitiv → Wrapper, Unboxing die Rückrichtung. Das löst das Problem, dass Collections und Generics nur Objekte speichern; der Preis sind Objekte auf dem Heap, null-Gefahr und ==-Fallen.

1. Wo sitzen Primitive und Wrapper?

  1. Primitive (boolean, byte, short, char, int, long, float, double): Der Wert selbst steht in der Variable. Kein Objekt, kein null.
  2. Wrapper (Boolean, Byte, Short, Character, Integer, Long, Float, Double): ein unveränderliches Objekt auf dem Heap. Die Variable hält nur eine Referenz.
  3. IntegerCache: Für Werte von -128 bis 127 gibt Integer.valueOf immer dasselbe vorbereitete Objekt zurück.
  4. Andere Werte: Jedes Boxing ausserhalb des Caches erzeugt ein neues Objekt mit Header, ca. 16 Bytes statt 4.

2. Die Reise eines Werts durch Boxing und Unboxing (die Geschichte zum Merken)

  1. Primitiver Wert: Der Code ruft list.add(128) auf. Die Liste erwartet aber ein Integer.
  2. Compiler: javac fügt still Integer.valueOf(128) ein. Das ist Autoboxing. Es passiert beim Kompilieren, nicht zur Laufzeit-Magie.
  3. Cache-Prüfung: valueOf schaut in den IntegerCache. 128 liegt ausserhalb von -128…127. Darum entsteht ein neues Objekt.
  4. In der Liste: Die Liste speichert die Referenz auf das Objekt.
  5. Unboxing: int y = list.get(0) wird zu list.get(0).intValue().
  6. Gefahr: Ist die Referenz null, wirft intValue() eine NullPointerException. In der Zeile steht aber kein sichtbarer Methodenaufruf.

3. Beispiel: Cache, NPE, Ternary, equals, remove, Performance

Integer a1 = 127, b1 = 127, a2 = 128, b2 = 128;  a1 == b1; a2 == b2;  // 1)
int count = map.get("missing");                                     // 2)
Integer r = flag ? 1 : nul;   // nul ist (Integer) null              // 3)
Long l = 1L; Integer i = 1;  l.equals(i); l == 1;                    // 4)
List<Integer> list = [10, 20, 30, 1]; list.remove(1); list.remove(Integer.valueOf(1)); // 5)
Long sumBoxed = 0L; for (k < 50 Mio.) sumBoxed += k;  vs  long sum    // 6)
Integer/Long/Double.valueOf(…) == …                                  // 7)
Integer big1 = 1000, big2 = 1000; big1 == big2;                      // 8)
Object o = 42; 'A' + 1; Integer.MAX_VALUE + 1;                        // 9) 10)
1) 127==127: true, 128==128: false, 128.equals(128): true
2) int count = map.get(missing): NullPointerException
3) flag ? 1 : (Integer) null -> NullPointerException (unboxing in ternary)
4) Long(1).equals(Integer(1)): false, l == 1: true
5) remove(1) removes INDEX 1 -> [10, 30, 1], remove(Integer.valueOf(1)) -> [10, 30]
6) run 1: Long sum 287 ms, long sum 42 ms (equal=true)
6) run 2: Long sum 233 ms, long sum 28 ms (equal=true)
7) Integer.valueOf(127)==Integer.valueOf(127): true, Long.valueOf(127)==Long.valueOf(127): true, Double.valueOf(1.0)==Double.valueOf(1.0): false
8) 1000==1000: false
9) Object o = 42 -> java.lang.Integer
10) 'A' + 1 = 66, (char) = B, Integer.MAX_VALUE + 1 = -2147483648
--- with -XX:AutoBoxCacheMax=1000
1) 127==127: true, 128==128: true, 128.equals(128): true
8) 1000==1000: true

Echte Ausgabe, Oracle JDK 17.0.3. Zeiten bei 6) ändern sich pro Lauf. Der zweite Block ist ein zweiter Lauf mit -XX:AutoBoxCacheMax=1000 (nur die geänderten Zeilen). Java 21 und 25 verhalten sich gleich.

  1. 127 kommt aus dem Cache: gleiches Objekt, == ist true. 128 sind zwei Objekte: == ist false. equals vergleicht den Wert und ist korrekt.
  2. Ein fehlender Map-Eintrag ist null. Das Unboxing in int wirft eine NPE.
  3. Im Ternary ist ein Zweig int. Darum ist der Typ des ganzen Ausdrucks int. Java unboxt den null-Zweig: NPE.
  4. Long.equals(Integer) ist false: verschiedene Klassen. l == 1 unboxt l und vergleicht Zahlen: true.
  5. remove(1) wählt remove(int index), nicht remove(Object). Ohne Boxing gewinnt die primitive Überladung.
  6. Ein Long als Summe erzeugt in jeder Runde ein neues Objekt. 7- bis 8-mal langsamer als long.
  7. Long hat auch einen Cache für -128…127. Double und Float haben keinen.
  8. 1000 liegt ausserhalb des Standard-Caches. Mit -XX:AutoBoxCacheMax=1000 wird er grösser, und == ist true. Das ist kein Grund, == zu nutzen.
  9. Ein int in einer Object-Variable wird ein Integer.
  10. char ist ein Zahlentyp (UTF-16-Code). Primitive Ganzzahlen laufen still über.

4. Details, die Interviewer fragen

  1. Was javac erzeugt: Boxing wird zu Integer.valueOf(x). Unboxing wird zu x.intValue(). Mit javap -c sieht man die Aufrufe.
  2. Cache-Regel (JLS §5.1.7): Für konstante Werte true/false, char bis \u007f und Ganzzahlen von -128 bis 127 liefert Boxing garantiert dasselbe Objekt. Für andere Werte ist die Identität nicht festgelegt.
  3. Welche Wrapper cachen: Integer, Long, Short, Byte für -128…127, Character bis 127, Boolean beide Werte. Float und Double nicht. Nur die Obergrenze von Integer ist per -XX:AutoBoxCacheMax einstellbar.
  4. Wrapper-Konstruktoren: new Integer(5) ist seit Java 9 deprecated und seit Java 16 zur Entfernung markiert (JEP 390). Immer valueOf oder Autoboxing.
  5. Value-based Classes: Wrapper sind value-based: kein ==, kein synchronized darauf. javac warnt seit Java 16 bei synchronized auf einem Wrapper.
  6. == bei gemischten Typen: Ist eine Seite primitiv, wird die andere unboxt und nach Wert verglichen. Sind beide Wrapper, vergleicht == Referenzen.
  7. Überladung: Der Compiler sucht erst ohne Boxing, dann mit Boxing, dann mit Varargs. Darum ruft list.remove(1) die Index-Variante.
  8. Generics: List<int> geht nicht. Typ-Parameter müssen Referenztypen sein. Für primitive Daten: Arrays, IntStream, Bibliotheken wie Eclipse Collections.
  9. Streams: mapToInt, IntStream.sum(), Collectors.summingInt vermeiden Boxing. Stream<Integer>.reduce(0, Integer::sum) boxt bei jedem Schritt.
  10. Speicher: int = 4 Bytes. Integer = Header + 4 Bytes, ca. 16 Bytes, plus 4–8 Bytes Referenz. ArrayList<Integer> mit 1 Mio. Werten braucht mehrfach so viel wie int[].
  11. Default-Werte: Primitive Felder starten mit 0 oder false. Wrapper-Felder starten mit null. In JPA-Entities zeigt Integer „unbekannt“, int kann das nicht.
  12. Escape Analysis: Der JIT entfernt manche kurzlebigen Box-Objekte. Darauf kann man sich aber nicht verlassen.

5. Vergleich

  • int: schnell, 4 Bytes, kein null, Standard 0. Für Rechnen, Zähler, Arrays.
  • Integer: Objekt, kann null sein, nötig für Collections und Generics. Vergleich mit equals.
  • int[] vs List<Integer>: Array ist kompakt und schnell. Liste ist flexibel, aber mit Boxing.
  • IntStream vs Stream<Integer>: IntStream ohne Boxing, mit sum, average, max.
  • OptionalInt vs Optional<Integer>: gleiche Idee ohne Boxing.
  • BigDecimal: kein Wrapper, sondern ein Typ für exakte Dezimalzahlen. Für Geld statt double.

6. In der Produktion

  1. NPE beim Unboxing: Ein JSON-Feld oder eine DB-Spalte ist null, der Code nimmt int. Der Stack Trace zeigt eine Zeile ohne sichtbaren Methodenaufruf. Lösung: Integer mit Prüfung, getOrDefault, Validierung am Eingang.
  2. IDs mit == verglichen: Im Test (kleine IDs) funktioniert es, in der Produktion (IDs über 127) nicht. Lösung: equals oder Objects.equals; SonarQube-Regel aktivieren.
  3. Hohe GC-Last durch Boxing: Map<Long, Long> mit Millionen Einträgen oder Summen in Long. Lösung: primitive Typen, primitive Streams, primitive Collections.
  4. Lock auf Wrapper: synchronized (Integer.valueOf(id)) teilt Locks über den Cache mit fremdem Code. Lösung: eigenes Lock-Objekt.
  5. Ternary-NPE: cond ? 0 : map.get(k) wirft bei fehlendem Schlüssel. Lösung: beide Zweige Integer oder getOrDefault.
  6. Hibernate und primitive Felder: Eine nullable Spalte in ein int-Feld führt zu einer Exception beim Laden. Lösung: Wrapper-Typ für nullable Spalten.

7. Diagnose: Werkzeuge und Befehle

  • javap -c: zeigt versteckte Integer.valueOf- und intValue-Aufrufe.
  • Helpful NullPointerExceptions (JEP 358, seit Java 15 standardmässig aktiv): Die Meldung nennt die Ursache, z. B. „Cannot invoke Integer.intValue() because … is null“.
  • JFR Allocation-Profil oder async-profiler im Modus alloc: viele java.lang.Integer/Long-Objekte zeigen Boxing in heissen Pfaden.
  • jcmd <pid> GC.class_histogram: Millionen java.lang.Long deuten auf Wrapper-Collections.
  • SonarQube / SpotBugs: Regeln gegen == auf Wrappern, Boxing in Schleifen und deprecated Konstruktoren.

8. Senior-Punkte

  1. Primitiv als Standard, Wrapper nur, wenn nötig: Collections, Generics, oder „unbekannt“ als null.
  2. Wrapper immer mit equals vergleichen. Der Cache macht ==-Fehler unsichtbar, bis echte Daten kommen.
  3. null bewusst modellieren. Ein Wrapper-Feld heisst „kann fehlen“. Diese Entscheidung gehört in die API, nicht zufällig in den Code.
  4. Boxing ist in Massen teuer. Bei Millionen Werten: primitive Arrays oder Streams. Erst messen.
  5. Kein Tuning des Caches als Fix. AutoBoxCacheMax versteckt Bugs, statt sie zu lösen.

10. Fallen

  • „Integer a == Integer b vergleicht Werte.“ → Falsch. Es vergleicht Referenzen. Nur im Cache-Bereich zufällig richtig.
  • „int x = map.get(k) ist sicher.“ → Falsch. Bei fehlendem Schlüssel NPE durch Unboxing.
  • „list.remove(1) entfernt die Zahl 1.“ → Falsch. Es entfernt den Index 1.
  • „Long.valueOf(1).equals(1) ist true.“ → Falsch. 1 wird ein Integer, andere Klasse.
  • „Double hat auch einen Cache.“ → Falsch. Nur Ganzzahl-Wrapper, Character und Boolean.
  • „Autoboxing passiert zur Laufzeit durch die JVM.“ → Falsch. javac fügt die Aufrufe beim Kompilieren ein.

11. Fragen

Was ist Autoboxing?

Die automatische Umwandlung eines primitiven Werts in sein Wrapper-Objekt, z. B. int in Integer. javac fügt dafür Integer.valueOf ein.

Was ist Unboxing?

Die Rückrichtung: Wrapper in primitiven Wert, z. B. über intValue(). Bei null kommt eine NullPointerException.

Warum gibt es Wrapper-Klassen?

Collections und Generics speichern nur Objekte. Wrapper können auch null sein und haben Hilfsmethoden wie parseInt.

Was ist der Integer-Cache?

Integer.valueOf liefert für -128 bis 127 immer dasselbe vorbereitete Objekt. Die JLS garantiert diesen Bereich.

Warum ist Integer 127 == 127 true, aber 128 == 128 false?

127 kommt aus dem Cache, beide Referenzen zeigen auf dasselbe Objekt. 128 sind zwei verschiedene Objekte.

Kann man den Cache vergrössern?

Ja, die Obergrenze für Integer mit -XX:AutoBoxCacheMax. Das ist aber kein Fix für ==-Fehler.

Welche Wrapper haben einen Cache?

Integer, Long, Short, Byte (-128 bis 127), Character (bis 127), Boolean. Float und Double nicht.

Warum ist new Integer(5) schlecht?

Es erzeugt immer ein neues Objekt und umgeht den Cache. Seit Java 9 deprecated, seit Java 16 for removal.

Wie vergleichen Sie zwei Integer richtig?

Mit equals oder Objects.equals, falls null möglich ist. Für Sortierung Integer.compare.

Was passiert bei Integer == int?

Der Integer wird unboxt, verglichen werden Werte. Ist der Integer null, kommt eine NPE.

Warum kann ein Ternary eine NPE werfen?

Ist ein Zweig primitiv, ist der ganze Ausdruck primitiv. Der Wrapper-Zweig wird unboxt, auch wenn er null ist.

Was macht list.remove(1) bei List<Integer>?

Es entfernt das Element an Index 1. Für den Wert: remove(Integer.valueOf(1)).

Ist Long.valueOf(1).equals(Integer.valueOf(1)) true?

Nein. equals prüft auch die Klasse. Long und Integer sind verschieden.

Was kostet Boxing?

Ein Objekt pro Wert ausserhalb des Caches, ca. 16 Bytes plus Referenz, und mehr GC-Arbeit. In Schleifen deutlich langsamer.

Wie vermeiden Sie Boxing in Streams?

Mit IntStream, LongStream, mapToInt, sum, summingInt. Nicht reduce auf Stream<Integer>.

Warum geht List<int> nicht?

Typ-Parameter müssen Referenztypen sein. Generics arbeiten mit Type Erasure auf Object.

int oder Integer in einer JPA-Entity?

Integer für nullable Spalten, weil null „unbekannt“ bedeutet. int nur für NOT-NULL-Spalten.

Warum nicht auf einem Integer synchronisieren?

Wrapper sind value-based und gecacht. Fremder Code kann dasselbe Objekt sperren. javac warnt seit Java 16.

Wie sieht man Boxing im Bytecode?

javap -c zeigt Aufrufe von Integer.valueOf und intValue.

Szenario: Ein ID-Vergleich funktioniert im Test, in der Produktion aber nicht. Was prüfen Sie?

Ob Long- oder Integer-IDs mit == verglichen werden. Im Test sind IDs klein und gecacht, in der Produktion grösser. Lösung: equals.

Szenario: Ein Service wirft NPE in einer Zeile wie int total = order.getAmount(); Was ist los?

getAmount liefert einen null-Wrapper, das Unboxing wirft. Die Helpful-NPE-Meldung zeigt es. Lösung: Feld validieren oder bewusst mit null umgehen.

Szenario: Eine Berechnung über 100 Mio. Werte erzeugt hohe GC-Last. Was ändern Sie?

Allocation-Profil prüfen: viele Long/Integer heisst Boxing. Auf long-Variablen, long[] oder LongStream umstellen.
