Records, Sealed Classes, Pattern Matching

Java · Tier 1 · Quellen: JLS SE 25 §8.10 (Record Classes), §8.1.1.2 (sealed), §14.11 (switch), §14.30 (Patterns); Java SE 25 API (Record, Class.isSealed, MatchException); JEP 361 (Switch Expressions, 14), JEP 394 (instanceof-Patterns, 16), JEP 395 (Records, 16), JEP 409 (Sealed, 17), JEP 440 (Record Patterns, 21), JEP 441 (Pattern Matching for switch, 21), JEP 456 (Unnamed Variables, 22), JEP 507 (Primitive Patterns, Preview in 25)

Kern: Ein Record ist eine unveränderliche Datenklasse: der Compiler erzeugt Konstruktor, Accessoren, equals, hashCode und toString. Eine sealed Klasse oder ein sealed Interface legt fest, welche Unterklassen es geben darf. Zusammen mit Pattern Matching für switch (final in Java 21) prüft der Compiler, dass jeder Fall behandelt ist. Das ist Javas Form von algebraischen Datentypen.

1. Wo sitzen Records und sealed Typen?

  1. sealed interface: Nur die Typen in permits dürfen es implementieren. Der Compiler kennt damit alle Fälle.
  2. Record als Unterklasse: Records sind implizit final. Sie erfüllen damit die Regel, dass jede erlaubte Unterklasse final, sealed oder non-sealed sein muss.
  3. Komponenten: Der Record-Header (String nr, long rappen) definiert Felder, Accessoren und den kanonischen Konstruktor.
  4. Verschachtelte Records: Rechnung enthält eine Adresse. Record Patterns können beides in einem Schritt zerlegen.
  5. Fremde Klasse: Dreieck steht nicht in permits und wird vom Compiler abgelehnt.

2. Die Reise einer Zahlung durch switch (die Geschichte zum Merken)

  1. Erzeugen: new Karte("4111", 2000) läuft durch den kompakten Konstruktor. Er prüft Regeln, bevor die Felder gesetzt werden.
  2. switch: Ist der Wert null, springt er zu case null. Ohne diesen Fall kommt eine NullPointerException.
  3. Typ-Test: Die Fälle werden von oben nach unten geprüft. Der erste passende gewinnt.
  4. Zerlegen: Ein Record Pattern Karte(var nr, var r) ruft die Accessoren und bindet die Werte an neue Variablen.
  5. Guard: when r > 100_000 ist eine Zusatzbedingung. Ist sie false, geht es zum nächsten case.
  6. Treffer: case Karte k passt immer für Karten. Der Rumpf liefert das Ergebnis.
  7. Vollständigkeit: Weil Zahlung sealed ist, weiss der Compiler, dass alle Fälle abgedeckt sind. Kommt ein neuer Typ dazu, bricht jeder unvollständige switch beim Kompilieren.

  1. Der kompakte Konstruktor validiert und normalisiert. waehrung = … ändert den Parameter; die Felder werden danach automatisch gesetzt.
  2. Ungültige Werte kommen nie in ein Record-Objekt. Das ist die Stelle für Invarianten.
  3. Ohne List.copyOf würde der Record die fremde, veränderbare Liste teilen. Records sind nur flach unveränderlich.
  4. Ein Record ist final und erbt von java.lang.Record. Reflection kennt seine Komponenten.
  5. isSealed() und getPermittedSubclasses() liefern die erlaubten Typen. Quadrat ist non-sealed und öffnet seinen Zweig wieder für beliebige Unterklassen.
  6. equals, hashCode und toString sind invokedynamic-Aufrufe auf ObjectMethods.bootstrap. Der Code wird zur Laufzeit erzeugt, nicht von javac geschrieben.
  7. Records erlauben keine Instanzfelder ausser den Komponenten und keine Zuweisung an Komponentenfelder.
  8. Im Java-21-Beispiel steht der Fall mit when vor case Karte k. Umgekehrt wäre er „dominated" und ein Compile-Fehler.
  9. _ ignoriert Komponenten, die man nicht braucht (tel, plz).

4. Details, die Interviewer fragen

  1. Was ein Record erzeugt (JLS §8.10): private final-Felder, öffentliche Accessoren mit Komponentennamen (rappen(), nicht getRappen()), kanonischen Konstruktor, equals, hashCode, toString.
  2. Was ein Record nicht kann: keine andere Klasse erweitern (er erbt von Record), keine Instanzfelder zusätzlich, nicht abstrakt, keine Unterklassen. Er darf Interfaces implementieren, static-Felder, Methoden und weitere Konstruktoren haben.
  3. Kanonischer vs kompakter Konstruktor: Der kanonische hat alle Komponenten als Parameter. Der kompakte lässt die Parameterliste weg und setzt die Felder am Ende automatisch. Zusätzliche Konstruktoren müssen mit this(...) an den kanonischen delegieren.
  4. Flache Unveränderlichkeit: Die Felder sind final, aber eine List-Komponente kann sich ändern. Lösung: List.copyOf im kompakten Konstruktor.
  5. equals bei Records: Referenzen über Objects.equals, Primitive über den Wrapper-compare. Arrays vergleichen per Identität. Details: Seite „equals und hashCode".
  6. Records und JPA: Records sind als JPA-Entity ungeeignet: Hibernate braucht einen Konstruktor ohne Argumente und veränderbare, nicht-finale Klassen für Proxies. Gut sind sie als DTOs, Projektionen und, in neueren Hibernate-Versionen, als @Embeddable.
  7. Records und Jackson/Spring: Aktuelle Jackson- und Spring-Boot-Versionen binden Records direkt, z. B. als Request-Body oder @ConfigurationProperties.
  8. sealed (JLS §8.1.1.2): sealed + permits. Jede erlaubte Unterklasse muss final, sealed oder non-sealed sein. Sie muss im selben Modul liegen, oder ohne Modul im selben Paket. Stehen alle in derselben Datei, darf permits fehlen.
  9. non-sealed: öffnet einen Zweig wieder. Ab dort kann jeder erben. Der Compiler kann für diesen Zweig keine Vollständigkeit mehr prüfen.
  10. Pattern Matching für instanceof (Java 16): if (o instanceof Kreis k) prüft und castet in einem Schritt. k ist nur dort sichtbar, wo der Test sicher true war (Flow Scoping).
  11. Switch Expressions (Java 14): switch liefert einen Wert. Pfeil-Syntax ohne Fall-through. yield gibt aus einem Block zurück. Bei Enums ohne default prüft der Compiler die Vollständigkeit.
  12. Pattern-switch (Java 21, JEP 441): case Typ var, Guards mit when, case null. Fälle müssen in Dominanz-Reihenfolge stehen: spezifisch vor allgemein.
  13. Record Patterns (Java 21, JEP 440): case Karte(var nr, var r) zerlegt den Record, auch verschachtelt. Die Variante in for-Schleifen-Köpfen wurde vor Java 21 wieder entfernt.
  14. Exhaustiveness und MatchException: Ein Pattern-switch muss vollständig sein. Wird später eine Unterklasse ohne Neukompilierung hinzugefügt, wirft der alte switch zur Laufzeit MatchException.
  15. null im switch: Ohne case null wirft jeder switch bei null eine NPE, auch der Pattern-switch. default fängt null nicht.
  16. Primitive Patterns: case int i und Patterns für Primitive sind in Java 25 noch Preview (JEP 507), nur mit --enable-preview.

5. Vergleich

  • Record: kein Boilerplate, unveränderlich, Wertgleichheit. Ideal für DTOs, Werte, Events, Schlüssel.
  • Lombok @Value: ähnlich, aber Bibliothek mit Annotation Processing; erlaubt Vererbung von Klassen und Getter-Namen.
  • Normale Klasse: für veränderbaren Zustand, Entities und Klassen mit Identität.
  • enum: feste Menge von Instanzen. sealed: feste Menge von Typen, jeder mit eigenen Daten.
  • sealed + switch: neue Operationen sind leicht, neue Typen brechen alle switches (gewollt).
  • Polymorphismus (abstrakte Methode): neue Typen sind leicht, neue Operationen ändern alle Klassen. Das ist das Expression Problem.
  • Visitor-Pattern: der alte Weg zu Dispatch nach Typ. Pattern-switch über sealed Typen ersetzt ihn meist.

6. In der Produktion

  1. Record mit veränderbarer Liste: Ein Aufrufer ändert die Liste nachträglich. Der „unveränderliche" Record ändert sich mit. Lösung: List.copyOf im kompakten Konstruktor.
  2. Record als JPA-Entity: scheitert beim Start oder bei Lazy Loading. Lösung: Entity als Klasse, Record als DTO oder Projektion.
  3. Sensible Daten im Log: Das generierte toString gibt alle Komponenten aus, auch Passwörter oder AHV-Nummern. Lösung: toString überschreiben oder sensible Werte in eigene Typen packen.
  4. MatchException nach Deployment: Ein Modul mit neuem permits-Typ wird deployt, ein anderes nicht neu kompiliert. Lösung: Module mit sealed Hierarchien gemeinsam bauen und versionieren.
  5. Breaking Change durch neuen Typ: Ein neuer Typ in einer öffentlichen sealed API bricht alle Kunden-switches. Lösung: sealed nur innerhalb eigener Module, oder neue Typen als Major-Version.
  6. NPE im switch: Ein switch über ein Feld aus JSON, das null sein kann. Lösung: case null oder vorher validieren.
  7. Serialisierung: Records serialisieren über den kanonischen Konstruktor. Validierung im kompakten Konstruktor läuft also auch beim Deserialisieren. Das kann alte Daten ablehnen.

7. Diagnose: Werkzeuge und Befehle

  • javap -p Klasse: zeigt Felder, Accessoren und die final-Methoden eines Records.
  • javap -v: zeigt Record- und PermittedSubclasses-Attribute sowie den ObjectMethods-Bootstrap.
  • Reflection: Class.isRecord(), getRecordComponents(), isSealed(), getPermittedSubclasses().
  • javac --release 21: stellt sicher, dass Pattern-switch nicht als Preview kompiliert wird.
  • Stack Trace mit MatchException: Hinweis auf eine Klasse, die nach dem Kompilieren des switch hinzugekommen ist.
  • ArchUnit: prüft z. B. „DTOs sind Records" oder „Entities sind keine Records".

8. Senior-Punkte

  1. Records für Daten, Klassen für Verhalten mit Identität. DTOs, Events, Wertobjekte und Map-Schlüssel sind Records.
  2. Invarianten in den kompakten Konstruktor. Dann gibt es kein ungültiges Objekt im ganzen System.
  3. sealed modelliert Fachlichkeit: „eine Zahlung ist Karte, Twint oder Rechnung". Der Compiler hält diese Liste aktuell.
  4. Kein default im Pattern-switch über sealed Typen. Ein default versteckt neue Fälle; ohne ihn meldet der Compiler sie.
  5. sealed nicht über Teamgrenzen ohne Versionierungsplan. Jeder neue Typ ist ein Breaking Change für Konsumenten.
  6. Version zählt: Pattern-switch und Record Patterns erst ab Java 21 produktiv. Auf Java 17 nur instanceof-Patterns und Switch Expressions.

10. Fallen

  • „Records sind komplett unveränderlich.“ → Falsch. Nur flach. Eine Listen-Komponente kann sich ändern.
  • „Record-Accessoren heissen getX().“ → Falsch. Sie heissen wie die Komponente: x().
  • „Records können von einer Basisklasse erben.“ → Falsch. Sie erben implizit von java.lang.Record. Interfaces gehen.
  • „Im kompakten Konstruktor setzt man this.x = x.“ → Falsch. Das ist ein Fehler; man weist den Parameter zu, die Felder setzt Java danach.
  • „Pattern-switch gibt es seit Java 17.“ → Nur Preview. Final seit Java 21 (JEP 441).
  • „default fängt null.“ → Falsch. Nur case null fängt null; sonst NPE.
  • „sealed ist dasselbe wie final.“ → Falsch. final: keine Unterklassen. sealed: nur die genannten.

11. Fragen

Was ist ein Record?

Eine unveränderliche Datenklasse. Der Compiler erzeugt Felder, Accessoren, kanonischen Konstruktor, equals, hashCode und toString aus dem Header.

Seit wann gibt es Records?

Final seit Java 16 (JEP 395), davor Preview in 14 und 15.

Was ist ein kompakter Konstruktor?

Ein Konstruktor ohne Parameterliste, der vor dem Setzen der Felder läuft. Er validiert und normalisiert die Parameter.

Kann ein Record zusätzliche Felder haben?

Nur static-Felder. Instanzfelder ausser den Komponenten sind verboten.

Kann ein Record von einer Klasse erben?

Nein. Er erbt implizit von java.lang.Record und ist final. Er kann aber Interfaces implementieren.

Sind Records wirklich unveränderlich?

Nur flach. Die Felder sind final, aber referenzierte Objekte wie Listen können sich ändern. Defensive Kopien im kompakten Konstruktor helfen.

Warum sind Records als JPA-Entities ungeeignet?

Hibernate braucht einen No-Arg-Konstruktor, veränderbare Felder und nicht-finale Klassen für Proxies. Records sind final und unveränderlich.

Wie sind equals und hashCode bei Records implementiert?

Über invokedynamic mit ObjectMethods.bootstrap. Gleichheit gilt komponentenweise, der genaue Hash-Algorithmus ist unspezifiziert.

Was ist eine sealed Klasse?

Eine Klasse oder ein Interface, das mit permits genau festlegt, welche Unterklassen erlaubt sind. Final seit Java 17.

Welche Modifier müssen erlaubte Unterklassen haben?

final, sealed oder non-sealed. Records und Enums sind implizit final.

Was bewirkt non-sealed?

Es öffnet einen Zweig wieder für beliebige Unterklassen. Der Rest der Hierarchie bleibt geschlossen.

Wann darf permits fehlen?

Wenn alle Unterklassen in derselben Datei stehen. Der Compiler leitet die Liste dann ab.

Was ist Pattern Matching für instanceof?

Test und Cast in einem: if (o instanceof Kreis k). k ist nur dort sichtbar, wo der Test sicher true war. Final seit Java 16.

Was ist eine Switch Expression?

Ein switch, der einen Wert liefert, mit Pfeil-Syntax ohne Fall-through. yield gibt aus einem Block zurück. Final seit Java 14.

Was bringt Pattern Matching für switch?

case mit Typ-Patterns, Record Patterns, Guards mit when und case null. Final seit Java 21.

Was ist ein Record Pattern?

Ein Pattern, das einen Record zerlegt: case Karte(var nr, var r). Es kann verschachtelt werden. Final seit Java 21.

Warum braucht ein switch über sealed Typen kein default?

Der Compiler kennt alle erlaubten Typen und prüft Vollständigkeit. Ein default würde neue Typen verstecken.

Was ist eine MatchException?

Sie fliegt, wenn ein als vollständig kompilierter Pattern-switch zur Laufzeit einen unbekannten Typ sieht, z. B. nach getrennter Kompilierung.

Was ist Dominanz bei case-Labels?

Ein allgemeiner Fall vor einem spezifischen macht den spezifischen unerreichbar. Der Compiler meldet das als Fehler.

Fängt default im switch null?

Nein. Ohne case null wirft der switch eine NullPointerException.

enum vs sealed?

enum: feste Menge von Instanzen. sealed: feste Menge von Typen, jede mit eigenen Daten und vielen Instanzen.

Was ist das Unnamed Pattern _?

Ein Platzhalter für Komponenten, die man nicht braucht, z. B. case Twint(_, long r). Final seit Java 22.

Was ist neu bei Patterns in Java 25?

Primitive Typen in Patterns, instanceof und switch sind in Java 25 noch Preview (JEP 507). Der Rest ist seit 21 bzw. 22 final.

Szenario: Ein Record-DTO mit einer Liste ändert sich „von selbst". Warum?

Der Record hält dieselbe Liste wie der Aufrufer, der sie später ändert. Lösung: List.copyOf im kompakten Konstruktor.

Szenario: Nach einem Deployment wirft ein Service MatchException. Was ist passiert?

Ein neuer Typ wurde zur sealed Hierarchie hinzugefügt, aber der Service mit dem switch nicht neu kompiliert. Beide Module gemeinsam bauen und deployen.

Szenario: Ihr Team will ein Visitor-Pattern für fünf Nachrichtentypen bauen. Was schlagen Sie vor (Java 21+)?

Ein sealed Interface mit Records und ein Pattern-switch ohne default. Der Compiler prüft Vollständigkeit, der Code ist kürzer als ein Visitor.
