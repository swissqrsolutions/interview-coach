Optional: richtige und falsche Nutzung

Java · Tier 2 · Quellen: Java SE 25 API-Doku (Optional, OptionalInt, Value-based Classes), Spring Data JPA Referenz (Repository-Rückgabetypen)

Kern: Optional ist ein Container, der genau einen Wert oder keinen enthält. Er löst das Problem, dass ein Rückgabewert null still „kein Ergebnis“ bedeutet und später eine NullPointerException auslöst. Laut API-Doku ist Optional vor allem als Rückgabetyp gedacht, nicht für Felder oder Parameter.

1. Wo sitzt Optional?

  1. Quelle: Ein Repository findet einen Datensatz oder nicht. Spring Data liefert dafür z. B. Optional<User> findById(id).
  2. Optional: Er hüllt das Ergebnis ein. Optional[User] heisst „da“, Optional.empty heisst „nicht da“.
  3. Service: Der Typ zwingt den Aufrufer, an den leeren Fall zu denken. Er kann ihn nicht vergessen.
  4. Am Ende: eine klare Entscheidung: Standardwert, Exception oder Aktion.
  5. Nicht hierhin: Felder, Parameter, Collections und Entities. Dort macht Optional den Code schwerer, nicht sicherer.

2. Die Reise einer Abfrage durch eine Optional-Kette (die Geschichte zum Merken)

  1. Suche: find(2) findet Luca und liefert Optional[Luca].
  2. Erster map: map(User::address) liefert Lucas Adresse. Sie ist null. map macht daraus automatisch Optional.empty.
  3. Zweiter map: map(Address::city) sieht ein leeres Optional. Es ruft die Funktion gar nicht auf.
  4. Ende: orElse("unbekannt") liefert den Standardwert. Kein if, keine NullPointerException.
  5. Gleiche Kette für Anna: Alle Schritte haben Werte. Das Ergebnis ist „Bern“.

3. Beispiel: Erzeugen, Ketten, orElse vs orElseGet, Fehlerfälle

Echte Ausgabe, Oracle JDK 17.0.3. Java 21 und 25 verhalten sich gleich.

  1. Optional.of verlangt einen Wert. Für „vielleicht null“ ist ofNullable da.
  2. Eine Kette mit map ersetzt verschachtelte null-Prüfungen. Fehlender User und fehlende Adresse enden gleich.
  3. orElse(expensive()) ruft expensive() immer auf, auch wenn ein Wert da ist. Java wertet Argumente vor dem Aufruf aus. orElseGet ruft den Supplier nur bei leerem Optional.
  4. get() auf leerem Optional wirft NoSuchElementException. Besser: orElseThrow mit eigener, fachlicher Exception.
  5. filter macht ein Optional leer, wenn die Bedingung nicht passt. or (Java 9) liefert ein Ersatz-Optional.
  6. ifPresentOrElse (Java 9) behandelt beide Fälle ohne isPresent()/get().
  7. Optional::stream (Java 9) filtert leere Ergebnisse elegant aus einem Stream.
  8. Liefert die Funktion selbst ein Optional, verschachtelt map. flatMap glättet.
  9. Optional ist nicht Serializable. Darum nicht als Feld in serialisierbaren Klassen.
  10. Für primitive Typen gibt es OptionalInt, OptionalLong, OptionalDouble ohne Boxing.
  11. Eine Methode, die null statt Optional liefert, zerstört den ganzen Sinn.

4. Details, die Interviewer fragen

  1. Erzeugen: Optional.of(v) (v darf nicht null sein), Optional.ofNullable(v), Optional.empty().
  2. Umwandeln: map (Ergebnis null wird leer), flatMap (Funktion liefert Optional), filter.
  3. Auspacken:
    • orElse(v): Standardwert, wird immer ausgewertet.
    • orElseGet(supplier): Standardwert, nur bei Bedarf berechnet.
    • orElseThrow() (Java 10): wie get(), aber mit klarem Namen. Die API-Doku empfiehlt es statt get().
    • orElseThrow(supplier): eigene Exception, z. B. NotFoundException.
  4. Reagieren: ifPresent, ifPresentOrElse (Java 9). Prüfen: isPresent, isEmpty (Java 11).
  5. Value-based Class: Optional ist value-based. Man soll gleiche Instanzen als austauschbar behandeln. Kein ==, kein synchronized darauf. Optional.empty() ist nicht garantiert ein Singleton.
  6. Never null: Eine Variable vom Typ Optional darf laut Doku nie null sein.
  7. Wofür gedacht: Rückgabetyp, wenn „kein Ergebnis“ ein normaler Fall ist. Beispiel: findById, stream.findFirst(), max().
  8. Wofür nicht:
    • Felder: nicht Serializable, extra Objekt, JPA kann es nicht direkt mappen.
    • Parameter: Der Aufrufer muss einpacken. Besser: Überladung oder @Nullable.
    • Collections: Eine leere Liste ist besser als Optional<List>.
    • Getter für Pflichtfelder: Das verschleiert, dass der Wert immer da ist.
  9. Kosten: Jedes Optional ist ein kleines Objekt. In heissen Schleifen kann das messbar sein. Oft entfernt die Escape Analysis des JIT es.
  10. Jackson: Für Optional in DTOs braucht Jackson das Modul jackson-datatype-jdk8. Spring Boot registriert es automatisch.

5. Vergleich

  • null: kein Objekt, keine Warnung im Typ. Vergessene Prüfung führt zu NPE.
  • Optional: „vielleicht leer“ steht im Typ. Der Aufrufer muss entscheiden. Nur für Rückgaben.
  • Leere Collection: für „keine Ergebnisse“ bei Listen. Nie null und nie Optional einer Liste.
  • Exception: wenn das Fehlen ein Fehler ist, nicht ein normaler Fall.
  • Null-Annotationen (@Nullable, JSpecify): für Parameter und Felder. Werkzeuge prüfen sie beim Kompilieren.
  • Kotlin String?: nullable Typen in der Sprache, ohne Wrapper-Objekt.

6. In der Produktion

  1. orElse mit teurem Aufruf: orElse(callRemoteService()) ruft den Service immer auf, auch wenn der Wert da ist. Unnötige Last, eventuell Seiteneffekte. Lösung: orElseGet.
  2. Blindes get(): NoSuchElementException: No value present im Log, ohne Kontext. Lösung: orElseThrow(() -> new NotFoundException("User " + id)), im REST-Layer als 404.
  3. Optional als Feld in einer Entity oder Session: Serialisierung oder JPA-Mapping schlägt fehl. Lösung: normales Feld, Getter liefert Optional.
  4. isPresent() + get(): nur ein umständliches != null. Lösung: map, orElse, ifPresentOrElse.
  5. Methode liefert null statt Optional: NPE genau dort, wo man sich sicher fühlt. Lösung: Code-Review-Regel und statische Analyse.

7. Diagnose: Werkzeuge und Befehle

  • IntelliJ-Inspections: „Optional.get() without isPresent()“, „Optional used as field or parameter type“.
  • SonarQube: Regeln für Optional.get() ohne Prüfung und für Optional als Parameter oder Feld.
  • Stack Trace mit „No value present“: Ein get() oder orElseThrow() ohne fachliche Meldung. Stelle im Trace finden und eigene Exception werfen.
  • JFR Allocation-Profil: zeigt, ob java.util.Optional in heissen Pfaden viel allokiert.
  • NullAway / Error Prone: prüfen @Nullable-Verträge beim Kompilieren, ergänzend zu Optional.

8. Senior-Punkte

  1. Optional ist eine API-Aussage. Es sagt: „Leer ist normal, entscheide selbst.“ Nur dort einsetzen, wo das stimmt.
  2. Rückgabe ja, Feld und Parameter nein. Für Felder und Parameter: Null-Annotationen oder Überladungen.
  3. Leere Collections statt null oder Optional. Das ist einfacher für jeden Aufrufer.
  4. Am Rand entscheiden. Im Controller wird aus „leer“ ein 404, im Service eine fachliche Exception. Nicht Optional durch alle Schichten reichen.
  5. Lesbarkeit vor Ketten. Eine lange Optional-Kette mit Nebenwirkungen ist schlechter als ein klares if.

9. Aus dem Projekt

„In Spring-Boot-Services (z. B. bei DAZiT) liefert ein Repository bei findById ein Optional; im REST-Layer wird daraus mit orElseThrow eine fachliche 404-Antwort.“ (Prüfen und durch dein echtes Beispiel ersetzen. Das Profil belegt Spring Boot bei DAZiT, nicht diesen konkreten Code.)

10. Fallen

  • „orElse und orElseGet sind gleich.“ → Falsch. orElse wertet das Argument immer aus. orElseGet nur bei leerem Optional.
  • „Optional verhindert alle NullPointerExceptions.“ → Falsch. Nur, wenn es nie selbst null ist und man nicht blind get() ruft.
  • „Optional.of(x) ist sicher für jeden Wert.“ → Falsch. Bei null wirft es sofort. ofNullable nutzen.
  • „Optional ist gut für Felder.“ → Falsch. Nicht Serializable, nicht für JPA gedacht. Die API-Doku zielt auf Rückgabetypen.
  • „opt == Optional.empty() prüft auf leer.“ → Falsch. Kein garantiertes Singleton. isEmpty() nutzen.
  • „Optional<List<X>> ist sauber.“ → Falsch. Eine leere Liste sagt dasselbe einfacher.

11. Fragen

Was ist Optional?

Ein Container mit genau einem oder keinem Wert. Er zeigt im Typ, dass ein Ergebnis fehlen kann.

Welches Problem löst Optional?

Ein null-Rückgabewert wird leicht vergessen und führt später zur NPE. Optional zwingt den Aufrufer, den leeren Fall zu behandeln.

Optional.of vs ofNullable?

of wirft bei null eine NPE. ofNullable macht aus null ein leeres Optional.

orElse vs orElseGet?

orElse wertet das Argument immer aus. orElseGet ruft den Supplier nur, wenn das Optional leer ist. Für teure Standardwerte orElseGet.

Warum ist get() problematisch?

Es wirft bei leerem Optional NoSuchElementException ohne Kontext. Die Doku empfiehlt orElseThrow, besser mit eigener Exception.

map vs flatMap bei Optional?

map für Funktionen mit normalem Ergebnis. flatMap für Funktionen, die selbst ein Optional liefern, sonst entsteht Optional<Optional>.

Was passiert, wenn map null zurückgibt?

Das Ergebnis ist ein leeres Optional. Keine Exception.

Wo soll man Optional nutzen?

Als Rückgabetyp, wenn „kein Ergebnis“ ein normaler Fall ist, z. B. findById oder findFirst.

Warum nicht als Feld?

Optional ist nicht Serializable, kostet ein extra Objekt und ist für JPA nicht gedacht. Besser: normales Feld, Getter liefert Optional.

Warum nicht als Parameter?

Der Aufrufer muss einpacken, und der Parameter kann trotzdem null sein. Besser: Überladung oder @Nullable.

Optional oder leere Liste?

Leere Liste. Optional einer Liste hat zwei Arten von „leer“ und macht den Code schwerer.

Was bedeutet value-based bei Optional?

Gleiche Instanzen sind austauschbar. Kein ==, kein synchronized, keine Identität voraussetzen.

Welche Methoden kamen nach Java 8 dazu?

Java 9: or, ifPresentOrElse, stream. Java 10: orElseThrow ohne Argument. Java 11: isEmpty.

Wie entfernen Sie leere Optionals aus einem Stream?

stream.flatMap(Optional::stream). Leere Optionals verschwinden, Werte bleiben.

Was ist OptionalInt?

Eine Optional-Variante für int ohne Boxing. Streams wie IntStream.max() liefern sie.

Ist isPresent() + get() guter Stil?

Nein. Das ist nur ein umständlicher null-Check. Besser map, orElse, orElseThrow oder ifPresentOrElse.

Darf eine Methode mit Rückgabetyp Optional null liefern?

Nein. Die Doku sagt, eine Optional-Variable soll nie null sein. Sonst kommt die NPE an der Stelle, die sicher wirkt.

Was kostet Optional zur Laufzeit?

Ein kleines Objekt pro Aufruf. Meist vernachlässigbar, der JIT kann es oft wegoptimieren. In sehr heissen Pfaden messen.

Wie serialisiert Jackson ein Optional?

Mit dem Modul jackson-datatype-jdk8: leer wird null, sonst der Wert. Spring Boot registriert es automatisch.

Szenario: Ein Endpoint ist langsam, obwohl der Cache fast immer trifft. Im Code steht cache.get(id).orElse(loadFromDb(id)). Was ist los?

orElse wertet loadFromDb immer aus, auch bei Treffer. Jeder Request geht zur DB. Lösung: orElseGet(() -> loadFromDb(id)).

Szenario: Im Log steht NoSuchElementException: No value present, und niemand weiss, welcher Datensatz fehlt. Was ändern Sie?

Das blinde get() durch orElseThrow mit fachlicher Exception und ID ersetzen. Im REST-Layer als 404 abbilden.

Szenario: Ein Kollege will alle Felder einer Entity zu Optional machen, um NPEs zu vermeiden. Was sagen Sie?

Nicht für Felder: nicht Serializable, JPA-Probleme, mehr Objekte. Besser: Pflichtfelder validieren, optionale Felder nullable lassen und Getter Optional liefern lassen, plus Null-Annotationen.
