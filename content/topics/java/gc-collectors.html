GC-Collectors

Kern: Ein Garbage Collector ist die Strategie, mit der die JVM Speicher freigibt. HotSpot hat mehrere, weil es kein Optimum gibt. Jeder Collector wählt zwischen Durchsatz, Latenz (Pausenlänge) und Speicherbedarf. Standard ist G1, für sehr kurze Pausen gibt es ZGC und Shenandoah.

1. Wo sitzen die Collectors? Drei Arten, den Heap zu teilen

  1. Serial: ein GC-Thread, alles in einer Pause. Young wird kopiert, Old mit Mark-Sweep-Compact geräumt. Beispiel: ein Pod mit 1 CPU.
  2. Parallel: gleiche Aufteilung wie Serial, aber viele GC-Threads. Ziel ist Durchsatz, also möglichst wenig GC-Zeit insgesamt. Beispiel: ein Batch-Job über Nacht.
  3. G1 (Garbage First): teilt den Heap in ca. 2048 Regionen (1–32 MB automatisch). Jede Region ist Eden, Survivor, Old oder Humongous. Es räumt zuerst die Regionen mit dem meisten Müll. Ziel: Pausen unter MaxGCPauseMillis (Standard 200 ms).
  4. Humongous-Objekt: ein Objekt ab einer halben Region. Es bekommt eigene, zusammenhängende Regionen. Beispiel: ein byte[4_000_000] bei 4-MB-Regionen.
  5. ZGC: verschiebt Objekte, während die Anwendung läuft. Pausen unter 1 ms, unabhängig von der Heap-Grösse (bis 16 TB). Eine Load Barrier, ein kleiner Code bei jedem Lesen einer Referenz, korrigiert verschobene Zeiger.
  6. Shenandoah: gleiche Idee wie ZGC, andere Technik (Barriers und Forwarding Pointer). Es ist nur in OpenJDK-Builds wie Temurin oder Red Hat enthalten, nicht im Oracle JDK.
  7. Epsilon: gibt nie Speicher frei. Ist der Heap voll, kommt OutOfMemoryError. Beispiel: Performance-Tests ohne GC-Rauschen.

2. Ein G1-Zyklus (die Geschichte zum Merken)

  1. Young-only-Phase. Die Anwendung füllt Eden-Regionen. Sind genug voll, kommt Pause Young (Normal). G1 evakuiert, also kopiert lebende Objekte in Survivor- oder Old-Regionen. Die Grösse von Young passt G1 selbst an, damit die Pause ins Ziel passt.
  2. Old wird voll: Concurrent Start. Erreicht Old die IHOP (Initiating Heap Occupancy Percent, Start 45 %, danach adaptiv), startet G1 einen Markierungszyklus. Er beginnt mit einer normalen Young-Pause: Pause Young (Concurrent Start).
  3. Concurrent Mark. GC-Threads markieren den ganzen Heap. Die Anwendung läuft weiter. Eine Write Barrier (SATB, Snapshot-at-the-Beginning) merkt sich Änderungen in dieser Zeit.
  4. Remark und Cleanup. Zwei kurze Pausen: Pause Remark schliesst die Markierung ab. Pause Cleanup bewertet jede Old-Region nach ihrem Müll-Anteil. Ganz leere Regionen werden sofort frei.
  5. Mixed GCs. Nach Pause Young (Prepare Mixed) folgen Pause Young (Mixed). Jede räumt Young plus einige Old-Regionen mit dem meisten Müll. Daher der Name Garbage First. Dann geht es zurück zu Schritt 1.
  6. Notfall: Full GC. Ist das Marking zu langsam oder kein Platz zum Kopieren frei, macht G1 eine Pause Full. Sie kompaktiert den ganzen Heap. Sie ist seit Java 10 parallel, aber immer noch lang. Im Normalbetrieb sollte es sie nie geben.

3. Beispiel: gleicher Code, vier Collectors

public class Load {
  public static void main(String[] args) {
    byte[][] cache = new byte[100_000][];            // live set: ~100 MB
    long start = System.nanoTime();
    for (int i = 0; i < 30_000_000; i++) {
      byte[] tmp = new byte[1_000];                  // garbage, dies at once
      if (i % 20 == 0) cache[(i / 20) % 100_000] = tmp; // lives longer, replaces an old one
    }
    System.out.println("time: " + (System.nanoTime() - start) / 1_000_000 + " ms");
  }
}

Echte Ausgabe, OpenJDK 17.0.3 (Oracle-Build 17.0.3.1), 16 CPUs, Windows. Gekürzt: ... steht für weggelassene Zeilen. Zeiten schwanken von Lauf zu Lauf. Shenandoah fehlt, weil der Oracle-Build es nicht enthält. Die Zahlen unten sind aus den vollständigen Logs gezählt.

  • Serial: 443 Pausen, davon 16 Full GC. Summe 1569 ms, längste 33,6 ms.
  • Parallel: 410 Pausen, davon 18 Full GC. Summe 1160 ms, längste 21,7 ms.
  • G1: 498 Pausen, 0 Full GC. Summe 1004 ms, längste 6,0 ms.
  • ZGC, 1 GB Heap: 55 Zyklen, 165 Pausen. Summe 2,9 ms, längste 0,040 ms.
  • ZGC, 256 MB Heap: 206 Allocation Stalls, zusammen 4475 ms. Laufzeit 9785 ms statt ca. 5300 ms.
  1. Serial und Parallel brauchen regelmässig eine Full GC: Old ist voll mit toten Cache-Einträgen. Parallel ist schneller, weil 16 Threads helfen. Der Grund (Ergonomics) heisst: Parallel entscheidet selbst, wann Old geräumt wird.
  2. G1 räumt Old ohne Full GC. Man sieht den ganzen Zyklus aus Abschnitt 2: Concurrent Start, Concurrent Mark (9,9 ms, Anwendung läuft), Remark, Cleanup, Prepare Mixed, Mixed. Die längste Pause sinkt von 33,6 ms auf 6,0 ms.
  3. ZGC mit 1 GB hat Pausen von 0,01 bis 0,04 ms. Die echte Arbeit (Mark, Relocate) läuft concurrent. Der Preis: mehr CPU und mehr Heap.
  4. ZGC mit 256 MB zeigt die Grenze: Die Anwendung erzeugt Müll schneller, als ZGC concurrent räumen kann. Dann muss der Thread warten: Allocation Stall. Das ist eine Pause für diesen Thread, nur anders benannt. Lösung: mehr Heap.
  5. Epsilon gibt nichts frei. Nach 0,09 s ist der Heap voll, die JVM endet mit OutOfMemoryError.
  6. Unterschied zu Java 21 und 25: Auf Java 17 ist ZGC nicht generational, es markiert immer den ganzen Heap. In Java 21 braucht man -XX:+UseZGC -XX:+ZGenerational. Ab Java 23 ist das der Standard, ab Java 24 gibt es nur noch generationales ZGC. Es hat Young und Old und hätte hier weniger Stalls. Die Log-Zeilen heissen dort z. B. Major Collection und Minor Collection.

4. Details, die Interviewer fragen

  1. Standard-Wahl (Ergonomics): Java 9 bis 26 wählt G1 auf einer server-class machine: mindestens 2 CPUs und mindestens 1792 MB. Sonst wählt die JVM Serial. Im Container zählen die Container-Limits. Ab Java 27 ist G1 immer Standard (JEP 523).
  2. Serial (-XX:+UseSerialGC): ein Thread, Young per Kopie, Old per Mark-Sweep-Compact. Wenig Overhead, gut für kleine Heaps bis ca. 100 MB und 1 CPU.
  3. Parallel (-XX:+UseParallelGC): wie Serial, aber mit vielen Threads für Young und Old. Höchster Durchsatz, aber lange Full-GC-Pausen. Standard bis Java 8.
  4. G1 (-XX:+UseG1GC): Standard seit Java 9. Regionen, Pausenziel, concurrent Marking, Mixed GCs. Guter Kompromiss für Heaps von ca. 1 bis über 100 GB.
  5. G1-Pausenziel: -XX:MaxGCPauseMillis=200 ist ein Ziel, keine Garantie. G1 erreicht es durch weniger Young-Regionen pro Pause. Ein zu kleines Ziel heisst: mehr Pausen und weniger Durchsatz.
  6. G1 Region Pinning (Java 22, JEP 423): Kritische JNI-Abschnitte blockieren die GC nicht mehr. G1 lässt nur die betroffene Region liegen.
  7. ZGC (-XX:+UseZGC): produktiv seit Java 15. Pausen unter 1 ms, Heap 8 MB bis 16 TB. Generational ab Java 21 (JEP 439), Standardmodus ab 23 (JEP 474), einziger Modus ab 24 (JEP 490).
  8. ZGC-Technik: Colored Pointers speichern GC-Zustand in Bits der Referenz selbst. Die Load Barrier prüft diese Bits beim Lesen und repariert die Referenz, wenn das Objekt verschoben wurde. Darum kann ZGC Objekte verschieben, während die Anwendung läuft.
  9. ZGC tunen: vor allem -Xmx gross genug setzen. -XX:SoftMaxHeapSize ist eine weiche Grenze: ZGC versucht darunter zu bleiben, darf aber bis -Xmx wachsen.
  10. Shenandoah (-XX:+UseShenandoahGC): von Red Hat, produktiv seit Java 15, concurrent Compaction wie ZGC. Generationaler Modus ab Java 25 produktiv (JEP 521), aber nicht Standard: -XX:ShenandoahGCMode=generational. Nicht im Oracle JDK enthalten.
  11. Epsilon (-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC): seit Java 11, experimentell. Gibt keinen Speicher frei. Für Performance-Tests, Speicher-Messungen und sehr kurze Jobs.
  12. CMS (Concurrent Mark Sweep): seit Java 9 deprecated, seit Java 14 entfernt (JEP 363). Auf Java 17 startet die JVM mit -XX:+UseConcMarkSweepGC gar nicht: Unrecognized VM option.
  13. Barriers kosten Durchsatz: Concurrent Collectors brauchen Code bei jedem Lesen oder Schreiben von Referenzen. Das kostet einige Prozent CPU. Darum ist Parallel beim reinen Durchsatz oft vorne.
  14. Tuning-Reihenfolge: 1. richtigen Collector wählen. 2. Heap-Grösse setzen (-Xmx oder -XX:MaxRAMPercentage). 3. Pausenziel setzen. 4. Erst dann Detail-Flags wie G1HeapRegionSize oder ParallelGCThreads.
  15. -Xms gleich -Xmx: verhindert Wachsen und Schrumpfen des Heaps. -XX:+AlwaysPreTouch holt den Speicher schon beim Start. Beides gibt gleichmässigere Latenz, kostet aber Startzeit und RAM.
  16. Compact Object Headers (Java 25, JEP 519, -XX:+UseCompactObjectHeaders): Objekt-Header von 12 auf 8 Bytes. Weniger Heap, weniger GC-Arbeit. Ist nicht standardmässig aktiv.

5. Vergleich

  • Serial: 1 Thread, alles STW, kleinster Overhead. Für 1 CPU, kleine Heaps, Tools.
  • Parallel: viele Threads, alles STW, höchster Durchsatz. Für Batch-Jobs, bei denen Pausen egal sind.
  • G1: Regionen, Mark concurrent, Kopieren STW. Pausen meist 10–200 ms. Für die meisten Services.
  • ZGC (generational): fast alles concurrent, Pausen unter 1 ms. Braucht mehr CPU und Heap-Reserve. Für latenzkritische Services und sehr grosse Heaps.
  • Shenandoah: wie ZGC, Pausen unter 10 ms, auch auf kleineren Heaps gut. Nur in OpenJDK-Builds ausser Oracle.
  • Epsilon: keine GC. Nur für Tests und kurzlebige Jobs.
  • CMS: entfernt seit Java 14. Nur als Falle wichtig.

6. In der Produktion

  1. Unerwartet Serial im Container: Ein Pod mit cpu: 1 oder unter 1792 MB nutzt in Java 21/25 Serial. Dann gibt es lange Pausen auf grösseren Heaps. Lösung: -XX:+UseG1GC explizit setzen und im Log Using ... prüfen.
  2. G1 mit Evacuation Failure oder Full GC: G1 findet keinen Platz zum Kopieren. Im Log steht (Evacuation Failure) hinter der Pause. Ursache: Heap zu voll oder Marking startet zu spät. Lösung: mehr Heap, Allokationen senken, eventuell -XX:G1ReservePercent erhöhen.
  3. Viele Humongous-Allokationen: grosse Arrays (z. B. grosse JSON-Puffer) belegen ganze Regionen und verschwenden Platz. Im Log: (G1 Humongous Allocation). Lösung: Objekte verkleinern oder -XX:G1HeapRegionSize erhöhen.
  4. ZGC Allocation Stalls: Im Log steht Allocation Stall, Latenz-Spitzen trotz ZGC. Ursache: Heap zu klein für die Allokationsrate. Lösung: -Xmx erhöhen, mehr CPU, Allokationen senken. Auf Java 17 zusätzlich: Wechsel auf Java 21+ mit generationalem ZGC.
  5. CPU-Throttling mit concurrent GC: ZGC und Shenandoah brauchen CPU parallel zur Anwendung. Bei engem CPU-Limit in Kubernetes werden sie gebremst. Lösung: CPU-Limit erhöhen oder G1 nutzen.
  6. Upgrade 8 → 17/21: Der Standard wechselt von Parallel zu G1. Durchsatz kann leicht sinken, Pausen werden kürzer. Alte Flags wie -XX:+UseConcMarkSweepGC verhindern den Start. Lösung: Flags aufräumen, GC-Log vor und nach dem Upgrade vergleichen.

7. Diagnose: Werkzeuge und Flags

  • -Xlog:gc: erste Zeile Using G1 zeigt den aktiven Collector. Danach eine Zeile pro GC.
  • -Xlog:gc*,gc+phases=debug:file=gc.log:time,uptime:filecount=5,filesize=20m: Phasen und Details mit Rotation.
  • java -XX:+PrintFlagsFinal -version | grep -E "Use.*GC|MaxGCPauseMillis|G1HeapRegionSize": welche Werte wirklich gelten.
  • jcmd <pid> VM.flags und jcmd <pid> GC.heap_info: Flags und Heap-Aufbau eines laufenden Prozesses.
  • jstat -gcutil <pid> 1000: Füllgrad und GC-Zeiten pro Sekunde.
  • JFR mit JDK Mission Control: Events jdk.GarbageCollection, jdk.GCPhasePause, jdk.G1HeapRegionTypeChange, jdk.ZAllocationStall.
  • -XX:ActiveProcessorCount=1 -Xlog:gc -version: testet, welchen Collector die JVM bei 1 CPU wählt. Auf Java 17 zeigt es Using Serial.

8. Senior-Punkte

  1. Es gibt kein bestes GC. Durchsatz, Latenz und Speicher konkurrieren. Erst das Ziel klären: p99-Latenz oder Jobs pro Stunde?
  2. G1 zuerst. Er ist für die meisten Services richtig. Wechsel nur mit Messung: ZGC bei p99-Problemen durch GC-Pausen, Parallel bei reinen Batch-Jobs.
  3. ZGC braucht Reserve. Er tauscht Pausen gegen CPU und Heap. Mit knappem Heap entstehen Allocation Stalls, die schlimmer sind als G1-Pausen.
  4. Den Collector immer explizit setzen im Container. Die Ergonomics hängen von CPU und RAM ab und ändern sich mit Java-Versionen (Java 27).
  5. Weniger Flags ist mehr. Alte Tuning-Flags aus Java-8-Zeiten passen oft nicht mehr. Wenige Flags: Collector, Heap, Pausenziel.
  6. Der beste GC-Fix ist oft im Code: weniger Allokationen, kleinerer Live-Set, keine riesigen Arrays.

9. Aus dem Projekt

„Für einen latenzkritischen Service haben wir G1 mit ZGC verglichen und die p99-Latenz im GC-Log und in JFR gemessen, bevor wir umgestellt haben.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „CMS ist der Collector für kurze Pausen.“ → Falsch. CMS ist seit Java 14 entfernt. Heute: G1, ZGC oder Shenandoah.
  • „Standard ist immer G1.“ → Falsch für Java 9 bis 26. Bei 1 CPU oder unter 1792 MB wählt die JVM Serial. Erst ab Java 27 immer G1.
  • „ZGC hat keine Pausen.“ → Falsch. Kurze STW-Pausen unter 1 ms, und bei zu kleinem Heap Allocation Stalls.
  • „ZGC ist generational.“ → Hängt von der Version ab. Java 17: nein. Java 21: nur mit -XX:+ZGenerational. Ab Java 23: Standard. Ab Java 24: einziger Modus.
  • „MaxGCPauseMillis garantiert die Pause.“ → Falsch. Es ist ein Ziel. G1 kann es verfehlen.
  • „Parallel GC läuft parallel zur Anwendung.“ → Falsch. Parallel heisst viele GC-Threads, aber die Anwendung steht. Neben der Anwendung heisst concurrent.
  • „Shenandoah gibt es in jedem JDK.“ → Falsch. Das Oracle JDK enthält es nicht. Temurin, Corretto, Red Hat und andere OpenJDK-Builds schon.
  • „Generational Shenandoah ist ab Java 25 Standard.“ → Falsch. Es ist produktiv, aber man muss es mit -XX:ShenandoahGCMode=generational einschalten.

11. Fragen

Welche Garbage Collectors hat HotSpot heute?

Serial, Parallel, G1, ZGC, Shenandoah (nicht im Oracle JDK) und Epsilon. CMS ist seit Java 14 entfernt.

Welcher Collector ist Standard?

G1 seit Java 9, aber nur bei mindestens 2 CPUs und 1792 MB. Sonst Serial. Ab Java 27 immer G1.

Wann nehmen Sie Serial?

Bei 1 CPU und kleinem Heap, z. B. kleine Tools oder Container. Er hat den kleinsten Overhead.

Wann nehmen Sie Parallel?

Bei Batch-Jobs, wo nur der Durchsatz zählt. Er hat die wenigste GC-Zeit insgesamt, aber lange Full-GC-Pausen.

Wie funktioniert G1?

Er teilt den Heap in Regionen. Young-Pausen kopieren lebende Objekte. Ein concurrent Marking findet Müll in Old, danach räumen Mixed GCs die Regionen mit dem meisten Müll.

Was ist eine Region in G1?

Ein gleich grosser Block des Heaps, 1 bis 32 MB automatisch, ca. 2048 Stück. Jede Region hat eine Rolle: Eden, Survivor, Old oder Humongous.

Was ist ein Humongous-Objekt?

Ein Objekt ab einer halben Region. Es bekommt eigene zusammenhängende Regionen. Viele davon verschwenden Platz.

Was ist eine Mixed GC?

Eine G1-Pause, die Young plus einige Old-Regionen räumt. Sie kommt nach einem concurrent Marking.

Was ist die IHOP?

Initiating Heap Occupancy Percent: ab diesem Füllgrad startet G1 das Marking. Start 45 %, danach passt G1 sie adaptiv an.

Was macht MaxGCPauseMillis?

Es setzt das Pausenziel für G1, Standard 200 ms. G1 passt die Grösse von Young an. Es ist ein Ziel, keine Garantie.

Wann macht G1 eine Full GC?

Wenn kein Platz zum Kopieren frei ist oder das Marking zu spät fertig wird. Sie ist seit Java 10 parallel, aber lang.

Wie hält ZGC die Pausen unter 1 ms?

Markieren und Verschieben laufen concurrent. Colored Pointers und eine Load Barrier reparieren Referenzen beim Lesen. In den Pausen bleibt fast nur Root-Arbeit.

Was ist Generational ZGC?

ZGC mit Young und Old. Er räumt junge Objekte öfter und billiger. Java 21 mit -XX:+ZGenerational, ab 23 Standard, ab 24 einziger Modus.

Was ist ein Allocation Stall?

Ein Thread muss bei ZGC warten, weil der Heap voll ist und die GC noch läuft. Lösung: mehr Heap oder weniger Allokationen.

ZGC oder Shenandoah?

Beide haben sehr kurze Pausen. ZGC ist in allen JDKs und skaliert bis 16 TB. Shenandoah fehlt im Oracle JDK und ist seit Java 25 auch generational.

Wofür ist Epsilon?

Für Performance-Tests ohne GC, Speicher-Messungen und sehr kurze Jobs. Er gibt nie frei, bei vollem Heap kommt OutOfMemoryError.

Was ist mit CMS passiert?

Deprecated in Java 9, entfernt in Java 14. Ab dann startet die JVM mit dem Flag nicht mehr. Ersatz: G1 oder ZGC.

Parallel vs Concurrent?

Parallel: mehrere GC-Threads, Anwendung steht. Concurrent: GC läuft gleichzeitig mit der Anwendung.

Warum haben concurrent Collectors weniger Durchsatz?

Sie brauchen Barriers bei jedem Zugriff auf Referenzen und CPU neben der Anwendung. Das kostet einige Prozent.

Welche GC-Flags setzen Sie in einem Container?

Den Collector explizit, z. B. -XX:+UseG1GC. Dazu -XX:MaxRAMPercentage (z. B. 75) oder -Xmx. Mehr nur nach Messung.

Wie gehen Sie beim GC-Tuning vor?

Ziel klären, GC-Log einschalten, messen. Dann Collector, Heap-Grösse, Pausenziel. Detail-Flags zuletzt, eine Änderung nach der anderen.

Warum -Xms gleich -Xmx?

Der Heap muss nicht wachsen oder schrumpfen. Das gibt gleichmässigere Pausen. Der Preis: der Speicher ist von Anfang an belegt.

Wie prüfen Sie, welcher Collector läuft?

Im GC-Log steht Using G1. Oder jcmd <pid> VM.flags bzw. -XX:+PrintFlagsFinal.

Szenario: Ein Service auf Java 21 hat p99-Spitzen von 300 ms, das GC-Log zeigt lange G1-Mixed-Pausen. Was tun Sie?

Erst Allokationen und Live-Set prüfen. Dann MaxGCPauseMillis senken oder mehr Heap geben. Reicht das nicht, ZGC mit -XX:+UseZGC -XX:+ZGenerational und genug Heap testen und p99 vergleichen.

Szenario: Nach dem Wechsel auf ZGC ist die Latenz schlechter, im Log stehen Allocation Stalls. Warum?

Der Heap ist zu klein für die Allokationsrate, oder die GC-Threads bekommen zu wenig CPU. Lösung: -Xmx erhöhen, CPU-Limit prüfen, Allokationen senken.

Szenario: Ein Pod mit 1 CPU und 1 GB hat lange Pausen, obwohl Sie G1 erwartet haben. Woran liegt es?

Die JVM hat Serial gewählt, weil die Maschine nicht server-class ist (unter 2 CPUs oder 1792 MB). Im Log steht Using Serial. Lösung: -XX:+UseG1GC explizit setzen.
