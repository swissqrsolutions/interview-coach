ArrayList, LinkedList, CopyOnWriteArrayList

Java · Tier 1 · Quellen: Java SE 25 API (List, ArrayList, LinkedList, CopyOnWriteArrayList, Collections, SequencedCollection), OpenJDK-Quellcode java.util.ArrayList (JDK 17), JEP 269 (Collection Factory Methods, Java 9), JEP 431 (Sequenced Collections, Java 21)

Kern: Eine List ist eine geordnete Collection mit Index und Duplikaten. ArrayList speichert Elemente in einem wachsenden Array: schneller Zugriff per Index, schnelles Iterieren. LinkedList speichert jedes Element in einem eigenen Node: nur an den Enden schnell. In der Praxis ist ArrayList fast immer die richtige Wahl.

1. Wo sitzen die Elemente?

  1. ArrayList: hält ein Object[] elementData und size. Elemente liegen nebeneinander. Das ist gut für den CPU-Cache.
  2. Kapazität: Das Array ist meist grösser als size. Der Rest ist Reserve für weitere add.
  3. LinkedList: eine doppelt verkettete Liste. Jeder Node hat prev, item, next. Die Liste kennt first und last.
  4. Nodes liegen verstreut im Heap. Jeder Schritt ist ein Zeigersprung und oft ein Cache-Miss.
  5. CopyOnWriteArrayList: hält ein Array in einem volatile-Feld. Schreiben kopiert das Array, Lesen braucht keinen Lock.
  6. modCount: ein Zähler für strukturelle Änderungen. Iteratoren nutzen ihn für fail-fast.

2. Die Reise eines add() in ArrayList (die Geschichte zum Merken)

  1. add(x): erhöht zuerst modCount. Jeder offene Iterator merkt das später.
  2. Platz prüfen: Ist size kleiner als die Array-Länge, ist Platz da.
  3. Eintragen: Das Element kommt an Position size, dann size++. Kosten: O(1).
  4. grow(): Ist das Array voll, rechnet ArrayList eine neue Grösse. Ein leeres new ArrayList<>() bekommt beim ersten add 10 Plätze. Danach wächst es um die Hälfte (oldCapacity >> 1).
  5. Kopieren: Arrays.copyOf legt ein neues Array an und kopiert alles. Das kostet O(n), passiert aber selten. Darum ist add im Mittel O(1) (amortisiert).
  6. Einfügen in der Mitte: add(i, x) und remove(i) verschieben alle Elemente dahinter mit System.arraycopy.

Echte Ausgabe, Oracle JDK 17.0.3, gestartet mit --add-opens java.base/java.util=ALL-UNNAMED. Zeiten aus einem einfachen Lauf ohne JMH; sie schwanken, die Grössenordnung ist der Punkt.

  1. Wachstum 10 → 15 → 22 → 33 → 49: jedes Mal plus die Hälfte. Löschen verkleinert das Array nicht. Erst trimToSize() gibt Speicher frei.
  2. Entfernen in for-each wirft ConcurrentModificationException. „Ben" ist dabei schon gelöscht, deshalb fehlt er auch in der späteren removeIf-Ausgabe.
  3. Sonderfall: Beim vorletzten Element endet die Schleife ohne Fehler, weil hasNext() nur size prüft. Fail-fast ist „best effort", keine Garantie.
  4. List.of ist unveränderlich und verbietet null, sogar bei contains(null). Arrays.asList hat feste Grösse: set geht, add nicht.
  5. unmodifiableList ist nur eine Sicht und zeigt Änderungen der Quelle. List.copyOf ist eine echte Kopie.
  6. CopyOnWriteArrayList: Der Iterator läuft auf dem Snapshot. Kein CME, keine Endlosschleife.
  7. LinkedList.get(i) läuft von einem Ende bis i: über 7000-mal langsamer. Iterieren ist bei beiden O(n), ArrayList trotzdem schneller. Nur vorne einfügen gewinnt LinkedList.

4. Details, die Interviewer fragen

  1. Komplexität ArrayList: get/set O(1); add am Ende amortisiert O(1); add/remove an Index i: O(n − i); contains/indexOf O(n).
  2. Komplexität LinkedList: addFirst/addLast/removeFirst/removeLast O(1); get(i) O(n) (läuft von der näheren Seite); Einfügen mit einem ListIterator an der aktuellen Stelle O(1); contains O(n).
  3. Warum LinkedList in der Praxis verliert: Man muss die Stelle zum Einfügen erst finden: O(n) mit Zeigersprüngen. Dazu kommen ein Objekt pro Element und schlechte Cache-Lokalität. System.arraycopy ist dagegen ein schneller Speicherblock-Kopierbefehl.
  4. Wachstum: Standard-Startkapazität 10, erst beim ersten add angelegt (lazy). Neue Grösse: alt + alt/2. Bei bekannter Grösse new ArrayList<>(n) oder ensureCapacity(n).
  5. RandomAccess: ein Marker-Interface. ArrayList hat es, LinkedList nicht. Algorithmen wie Collections.binarySearch wählen damit Index- oder Iterator-Variante.
  6. Fail-fast Iterator: Der Iterator speichert expectedModCount. Weicht modCount ab, wirft next() eine ConcurrentModificationException. Es geht um Fehlererkennung, nicht um Thread-Sicherheit.
  7. Sicher entfernen: iterator.remove(), removeIf (Java 8) oder eine neue Liste per Stream bauen.
  8. Unveränderliche Listen: List.of (Java 9) und List.copyOf (Java 10): kein add, kein set, kein null. Stream.toList() (Java 16) ist auch unveränderlich, erlaubt aber null.
  9. Unmodifiable vs immutable: Collections.unmodifiableList blockiert nur Schreiben über die Sicht. Die Quelle kann sich ändern. Die Elemente selbst können in beiden Fällen veränderbar sein.
  10. subList: eine Sicht auf die Original-Liste. Ändert man das Original strukturell, wirft die Sicht CME. subList(a, b).clear() löscht einen Bereich effizient.
  11. CopyOnWriteArrayList: thread-sicher ohne Lock beim Lesen. Jedes add kopiert das Array: O(n). Iteratoren sind Snapshots, iterator.remove() wird nicht unterstützt. Ideal für viele Leser, seltene Schreiber, z. B. Listener-Listen.
  12. Collections.synchronizedList: ein Lock pro Methode. Beim Iterieren muss man selbst auf die Liste synchronisieren.
  13. Sequenced Collections (Java 21, JEP 431): List hat jetzt getFirst(), getLast(), addFirst(), removeLast() und reversed(). Vorher: list.get(list.size() - 1).
  14. remove(int) vs remove(Object): Bei List<Integer> ist remove(1) der Index. Siehe Seite „OOP-Grundlagen".
  15. Deque statt LinkedList: Für Stack und Queue ist ArrayDeque schneller als LinkedList. LinkedList erlaubt aber null.

5. Vergleich

  • ArrayList: Standard. Index O(1), Iteration schnell, wenig Speicher pro Element, Einfügen vorne teuer.
  • LinkedList: nur sinnvoll bei vielen Einfügungen über einen bereits positionierten ListIterator. Hoher Speicher, langsamer Index-Zugriff.
  • ArrayDeque: Queue und Stack, O(1) an beiden Enden, kein null, kein Index.
  • CopyOnWriteArrayList: thread-sicher, Lesen ohne Lock, Schreiben O(n). Für seltene Änderungen.
  • Collections.synchronizedList: thread-sicher mit einem Lock, Iteration manuell synchronisieren.
  • List.of / List.copyOf / Stream.toList: unveränderlich; die ersten zwei ohne null.
  • Arrays.asList: feste Grösse, Sicht auf das Array (set schreibt ins Array).

6. In der Produktion

  1. O(n²) durch LinkedList.get(i) in einer Schleife: Eine API liefert List, intern ist es eine LinkedList. Lösung: for-each oder Iterator, oder in ArrayList kopieren.
  2. ConcurrentModificationException: Entfernen in for-each, oder ein zweiter Thread ändert die Liste. Lösung: removeIf, oder bei Threads eine concurrent Collection.
  3. UnsupportedOperationException in Produktion: Eine Methode bekommt List.of oder Arrays.asList und ruft add. Lösung: defensiv kopieren oder klar dokumentieren, dass die Liste unveränderlich ist.
  4. NullPointerException bei contains(null): auf List.of-Listen. Lösung: null vorher prüfen.
  5. Speicher bleibt hoch nach Löschen: eine lange lebende ArrayList hatte kurz Millionen Elemente. Lösung: trimToSize() oder neue Liste.
  6. CopyOnWriteArrayList mit vielen Schreibzugriffen: jedes add kopiert das Array. Hohe CPU und GC-Last. Lösung: ConcurrentLinkedQueue oder Lock mit ArrayList.
  7. Daten verloren bei paralleler Nutzung: parallelStream().forEach(list::add) auf einer ArrayList verliert Elemente oder wirft ArrayIndexOutOfBoundsException. Lösung: collect oder toList().

7. Diagnose: Werkzeuge und Befehle

  • jcmd <pid> GC.class_histogram: viele java.util.LinkedList$Node oder grosse [Ljava.lang.Object; zeigen Listen-Probleme.
  • Eclipse MAT: „Collections → Fill Ratio" zeigt ArrayLists mit viel leerer Kapazität.
  • Profiler (async-profiler, JFR): Zeit in LinkedList.node oder ArrayList.grow.
  • JMH: für echte Mikro-Benchmarks statt einfacher Schleifen wie oben.
  • Stack Trace der CME: zeigt die Zeile mit der Iteration; die Änderung steht im Code davor oder in einem anderen Thread.

8. Senior-Punkte

  1. ArrayList ist der Standard. LinkedList braucht eine gemessene Begründung. Für Queues: ArrayDeque.
  2. Big-O ist nicht alles. Cache-Lokalität und Objekt-Overhead schlagen theoretische O(1)-Einfügungen der LinkedList.
  3. Unveränderliche Listen an API-Grenzen. List.copyOf beim Eingang, List.of oder toList() beim Ausgang. Das verhindert Aliasing-Fehler.
  4. Grösse vorgeben, wenn sie bekannt und gross ist. Sonst bringt es nichts.
  5. Thread-Sicherheit bewusst wählen: Copy-on-Write für Lesen fast ohne Schreiben, sonst Queue-Strukturen oder klare Besitzverhältnisse.

10. Fallen

  • „LinkedList ist schneller beim Einfügen.“ → Nur an den Enden oder mit positioniertem Iterator. Die Stelle zu finden kostet O(n).
  • „ArrayList verdoppelt sich.“ → Falsch. Sie wächst um die Hälfte: 10, 15, 22, 33 …
  • „Remove verkleinert das Array.“ → Falsch. Nur trimToSize().
  • „Fail-fast ist garantiert.“ → Falsch. Best effort. Beim vorletzten Element kommt keine CME.
  • „CME heisst, es gibt mehrere Threads.“ → Falsch. Meist ist es ein einziger Thread, der beim Iterieren ändert.
  • „Collections.unmodifiableList ist unveränderlich.“ → Falsch. Es ist eine Sicht; die Quelle kann sich ändern.
  • „Arrays.asList ist eine normale ArrayList.“ → Falsch. Feste Grösse, Sicht auf das Array.

11. Fragen

ArrayList vs LinkedList: was ist der Unterschied?

ArrayList nutzt ein wachsendes Array: Index O(1), Einfügen in der Mitte O(n). LinkedList nutzt Nodes: Enden O(1), Index O(n), mehr Speicher.

Wann würden Sie LinkedList nutzen?

Fast nie. Höchstens bei vielen Einfügungen über einen positionierten ListIterator. Für Queues ist ArrayDeque besser.

Wie wächst eine ArrayList?

Erste Allokation beim ersten add mit 10 Plätzen. Danach jeweils um die Hälfte: 15, 22, 33. Altes Array wird kopiert.

Warum ist add amortisiert O(1)?

Kopieren passiert nur selten, und jedes Mal wächst das Array um einen festen Faktor. Die Kosten verteilen sich auf viele adds.

Warum ist ArrayList beim Iterieren schneller als LinkedList?

Die Elemente liegen nebeneinander im Speicher und nutzen den CPU-Cache. LinkedList springt zwischen verstreuten Nodes.

Was kostet LinkedList.get(i)?

O(n). Sie läuft vom näheren Ende bis i. In einer Schleife wird das O(n²).

Was ist ein fail-fast Iterator?

Ein Iterator, der bei einer strukturellen Änderung ausserhalb von ihm eine ConcurrentModificationException wirft. Er prüft modCount, nur best effort.

Wie entfernt man sicher Elemente beim Iterieren?

Mit iterator.remove() oder removeIf. Oder eine neue Liste per Stream filtern.

Was ist modCount?

Ein Zähler für strukturelle Änderungen wie add und remove. Iteratoren vergleichen ihn mit ihrem erwarteten Wert.

Was macht List.of?

Erzeugt eine unveränderliche Liste ohne null. add, set und remove werfen UnsupportedOperationException.

List.of vs Collections.unmodifiableList?

List.of ist wirklich unveränderlich. unmodifiableList ist eine Sicht auf eine Liste, die sich weiter ändern kann.

Was ist das Besondere an Arrays.asList?

Feste Grösse und eine Sicht auf das Array. set ändert das Array, add und remove werfen UnsupportedOperationException.

Was ist CopyOnWriteArrayList?

Eine thread-sichere Liste, die bei jedem Schreiben das Array kopiert. Leser brauchen keinen Lock und iterieren über einen Snapshot.

Wann ist CopyOnWriteArrayList passend?

Viele Leser, sehr seltene Schreiber, z. B. Listener- oder Konfigurationslisten. Bei vielen Writes ist sie teuer.

Wirft der Iterator von CopyOnWriteArrayList eine CME?

Nein. Er sieht einen festen Snapshot. Änderungen danach sieht er nicht, und iterator.remove() wird nicht unterstützt.

Ist ArrayList thread-sicher?

Nein. Gleichzeitige adds verlieren Elemente oder werfen Exceptions. Lösung: synchronizedList, CopyOnWriteArrayList oder keine geteilte Liste.

Was ist RandomAccess?

Ein Marker-Interface für schnellen Index-Zugriff. ArrayList hat es, LinkedList nicht. Algorithmen wählen damit ihre Strategie.

Was ist subList?

Eine Sicht auf einen Bereich der Original-Liste. Änderungen wirken auf das Original, strukturelle Änderungen am Original machen die Sicht ungültig.

Gibt ArrayList Speicher frei, wenn man Elemente löscht?

Nein. Das Array bleibt gleich gross. trimToSize() verkleinert es.

Was ist neu bei List in Java 21?

Sequenced Collections: getFirst, getLast, addFirst, addLast, removeFirst, removeLast und reversed.

Stream.toList() vs Collectors.toList()?

Stream.toList (Java 16) liefert eine unveränderliche Liste. Collectors.toList garantiert keine Veränderbarkeit, liefert heute aber eine ArrayList.

Warum ArrayDeque statt LinkedList als Queue?

ArrayDeque nutzt ein Ring-Array: weniger Speicher, besserer Cache, schneller. Nur null ist nicht erlaubt.

Szenario: Ein Export wird mit mehr Daten quadratisch langsamer. Der Code macht for (i…) list.get(i). Ursache?

Die Liste ist eine LinkedList, get(i) ist O(n). Lösung: for-each oder Iterator, oder vorher in eine ArrayList kopieren.

Szenario: Ein Service wirft sporadisch UnsupportedOperationException beim Hinzufügen. Was prüfen Sie?

Woher die Liste kommt. Wahrscheinlich List.of, Stream.toList oder Arrays.asList von einem Aufrufer. Lösung: new ArrayList<>(input) vor Änderungen.

Szenario: Eine Listener-Liste wird von vielen Threads gelesen und selten geändert. Es gibt CME-Fehler. Lösung?

CopyOnWriteArrayList. Lesen braucht keinen Lock, Iteratoren arbeiten auf Snapshots, Änderungen sind selten und damit billig genug.
