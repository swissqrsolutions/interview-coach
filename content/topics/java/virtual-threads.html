Virtual Threads

Kern: Ein Virtual Thread ist ein java.lang.Thread, den die JVM verwaltet, nicht das Betriebssystem. Er belegt einen OS-Thread nur, solange er wirklich rechnet. Beim Blockieren auf I/O gibt er ihn frei. So laufen Millionen blockierende Tasks im einfachen Thread-per-Request-Stil, ohne Thread Pool und ohne reaktiven Code.

1. Wo sitzen Virtual Threads?

  1. Virtual Thread: ein normales Thread-Objekt. Wartet er, liegen seine Stack-Frames im Heap. Beispiel: ein Request, der auf eine DB-Antwort wartet.
  2. Scheduler: ein eigener ForkJoinPool im FIFO-Modus. Er ist getrennt vom Common Pool der Parallel Streams.
  3. Carrier Thread: ein Platform Thread des Schedulers. Er „trägt" gerade einen Virtual Thread. Standard: so viele Carrier wie CPUs.
  4. OS-Thread: Jeder Carrier ist ein echter OS-Thread. Das Verhältnis ist M:N: viele Virtual Threads auf wenigen OS-Threads.

Platform vs Virtual im Überblick steht auf der Seite Threads. Diese Seite geht in die Tiefe.

2. Die Reise eines Virtual Threads (die Geschichte zum Merken)

  1. Start: Thread.ofVirtual().start(task) erzeugt den Thread und reiht ihn beim Scheduler ein. Kosten: ein kleines Heap-Objekt, kein OS-Thread.
  2. Mount: Der Scheduler setzt ihn auf einen freien Carrier. Der Carrier führt jetzt seinen Code aus. Thread.currentThread() liefert trotzdem den Virtual Thread.
  3. Blockieren: Der Code ruft z. B. socket.read() oder queue.take(). Die JDK-Methode merkt: Ich laufe virtuell.
  4. Unmount: Der Virtual Thread kopiert seine Stack-Frames in den Heap und gibt den Carrier frei. Der Carrier holt sofort den nächsten Virtual Thread.
  5. Weiter: Sind die Daten da, reiht ein Poller den Thread wieder beim Scheduler ein.
  6. Mount, eventuell woanders: Er läuft weiter, vielleicht auf einem anderen Carrier. Es gibt keine feste Bindung.
  7. Pinning (rot): Kann er nicht unmounten, blockiert er seinen Carrier mit. In Java 21–23 passiert das in synchronized. Seit Java 24 (JEP 491) nur noch in Sonderfällen.

3. Beispiel: 2000 schlafende Tasks

// Platform Threads: fester Pool mit 200 Threads
ExecutorService ex = Executors.newFixedThreadPool(200);
IntStream.range(0, 2_000).forEach(i -> ex.submit(() -> { Thread.sleep(1000); return i; }));
ex.shutdown(); ex.awaitTermination(1, MINUTES);
2000 Tasks, fixed pool 200: 10172 ms

Echte Ausgabe, Oracle JDK 17.0.3.

// Virtual Threads (Java 21+): ein neuer Virtual Thread pro Task
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  IntStream.range(0, 2_000).forEach(i -> ex.submit(() -> { Thread.sleep(1000); return i; }));
}  // close() wartet auf alle Tasks
2000 Tasks, virtual: etwa 1000 ms (alle schlafen gleichzeitig)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). JEP 444 beschreibt dasselbe Beispiel mit 10 000 Tasks: 200 Platform Threads schaffen 200 Tasks pro Sekunde, Virtual Threads etwa 10 000 pro Sekunde.

  1. Der Pool mit 200 Threads arbeitet in 10 Runden à 1 Sekunde. Das ergibt 10 Sekunden.
  2. Mit Virtual Threads schlafen alle 2000 gleichzeitig. Kein OS-Thread ist dabei blockiert.
  3. Würde jeder Task 1 Sekunde rechnen, hilft das nicht. Mehr Threads als Kerne bringen bei CPU-Arbeit nichts.
// Pinning sichtbar machen (Java 21–23)
synchronized (lock) { Thread.sleep(100); }      // blockiert im Monitor
$ java -XX:StartFlightRecording=filename=pin.jfr App
$ jfr print --events jdk.VirtualThreadPinned pin.jfr

Erwartetes Ergebnis (laut Doku, nicht ausgeführt): Auf Java 21 erscheinen jdk.VirtualThreadPinned-Events mit Stack Trace, Schwelle 20 ms. Auf Java 24 und 25 erscheinen für diesen Code keine Events mehr, weil synchronized nicht mehr pinnt (JEP 491).

4. Details, die Interviewer fragen

  1. Erzeugen: Thread.ofVirtual().name("req-", 0).start(r), Thread.startVirtualThread(r) oder Executors.newVirtualThreadPerTaskExecutor(). Alle seit Java 21.
  2. Scheduler-Grösse: jdk.virtualThreadScheduler.parallelism = Zahl der Carrier, Standard = Anzahl CPUs. jdk.virtualThreadScheduler.maxPoolSize = Obergrenze, Standard 256.
  3. Compensation: Manche Operationen blockieren den OS-Thread trotzdem, z. B. viele Dateisystem-Zugriffe. Dann startet der Scheduler kurz zusätzliche Carrier, bis maxPoolSize.
  4. Pinning in Java 21–23: Ein Virtual Thread pinnt in synchronized und in nativen Methoden oder Foreign Functions. Bei Pinning startet der Scheduler keinen Ersatz-Carrier.
  5. JEP 491 (Java 24): Die JVM verfolgt Monitore jetzt pro Virtual Thread, nicht pro Carrier. Blockieren in synchronized, beim Warten auf den Monitor und in Object.wait() gibt den Carrier frei.
  6. Pinning ab Java 24: Es bleibt bei nativem Code, der zurück in blockierenden Java-Code ruft. Dazu: Blockieren beim Laden einer Klasse, in einem Klassen-Initialisierer (static {}) und beim Warten auf die Initialisierung durch einen anderen Thread.
  7. Diagnose-Property: -Djdk.tracePinnedThreads gab es in Java 21–23. Seit Java 24 ist sie entfernt und wirkungslos. Heute nutzt man das JFR-Event jdk.VirtualThreadPinned.
  8. Kein Time Sharing: Der Scheduler unterbricht einen rechnenden Virtual Thread nicht. Langer CPU-Code belegt seinen Carrier, bis er blockiert oder endet.
  9. Immer Daemon, feste Priorität: setDaemon(false) und setPriority haben keine Wirkung.
  10. ThreadLocal: funktioniert. Aber bei Millionen Threads kostet jede Kopie Speicher. Teure Objekte nie per ThreadLocal „poolen", denn jeder Task hat einen neuen Thread.
  11. Nie poolen: Laut JEP 444 „sollten nie gepoolt werden". Pro Task ein neuer Virtual Thread. Zum Begrenzen eines Downstreams eine Semaphore nutzen.
  12. Scoped Values (final in Java 25, JEP 506): ein ScopedValue teilt unveränderliche Daten mit aufgerufenen Methoden und Kind-Threads. Er gilt nur innerhalb von ScopedValue.where(KEY, v).run(...). Billiger und sicherer als ThreadLocal.
  13. Structured Concurrency (Status November 2026): In Java 21 bis 27 nur Preview, also mit --enable-preview. In Java 25 heisst der Einstieg StructuredTaskScope.open(). JEP 543 will die API in JDK 28 final machen, Status „Integrated".
  14. Thread Dump: Der klassische jstack-Dump ist für Millionen Threads ungeeignet. Neu: jcmd <pid> Thread.dump_to_file -format=json datei.json. Details auf der Seite Thread Dumps.
  15. Spring Boot: spring.threads.virtual.enabled=true schaltet Virtual Threads ein. Die Spring-Doku empfiehlt dafür Java 24 oder neuer. Pool-Properties wirken dann nicht mehr.

5. Vergleich

  • Platform Thread: 1:1 auf einen OS-Thread, teuer, begrenzte Anzahl. Gut für CPU-Arbeit und wenige lange Aufgaben.
  • Virtual Thread: M:N, billig, Millionen möglich. Gut für viele gleichzeitige, blockierende I/O-Aufgaben. Nicht schneller pro Task.
  • Thread Pool (ThreadPoolExecutor): begrenzt und verwendet Platform Threads wieder. Mit Virtual Threads für I/O oft überflüssig. Siehe Seite ExecutorService und Thread Pools.
  • Reaktiv (WebFlux, Reactor): wenige Threads, nicht blockierender Code mit Callbacks. Gleicher Durchsatz möglich, aber schwer zu lesen und zu debuggen. Virtual Threads erreichen viel davon mit normalem, blockierendem Code.
  • CompletableFuture: Komposition asynchroner Schritte. Mit Virtual Threads kann man oft einfach blockierend get() aufrufen.
  • Kotlin Coroutines: ebenfalls leichte Tasks, aber kooperativ mit suspend im Code. Virtual Threads brauchen keine Code-Änderung.

6. In der Produktion

  1. Pinning auf Java 21: synchronized um I/O (z. B. in einem alten JDBC-Treiber) belegt alle Carrier. Die App friert ein, obwohl die CPU leer ist. Lösung: Java 24+ oder ReentrantLock. Seite Synchronisation und Locks.
  2. Downstream überrannt: Ohne Pool gibt es keine natürliche Grenze mehr. 10 000 Virtual Threads öffnen 10 000 DB-Anfragen. Der Connection Pool wird zum Engpass mit Timeouts. Lösung: Semaphore oder eine bewusste Grenze im Connection Pool.
  3. Speicher durch ThreadLocal: Ein Framework legt pro Thread einen grossen Puffer ab. Mit Millionen Threads wächst der Heap stark. Lösung: ThreadLocal-Nutzung prüfen, -Djdk.traceVirtualThreadLocals=true hilft beim Finden.
  4. CPU-lastige Tasks: Lange Berechnungen ohne Blockieren halten Carrier fest. Andere Requests warten. Lösung: CPU-Arbeit in einen begrenzten Platform-Pool auslagern.
  5. Monitoring bricht: Dashboards zählen „aktive Threads im Pool". Mit Virtual Threads gibt es keinen Pool. Lösung: In-Flight-Requests und Semaphore-Wartezeit messen.
  6. Dateisystem-I/O: Viele Dateioperationen blockieren den OS-Thread. Der Scheduler kompensiert nur bis maxPoolSize.

7. Diagnose: Werkzeuge und Befehle

  • JFR-Events: jdk.VirtualThreadPinned (an, Schwelle 20 ms), jdk.VirtualThreadSubmitFailed (an), jdk.VirtualThreadStart und jdk.VirtualThreadEnd (standardmässig aus).
  • jfr view pinned-threads rec.jfr: fertige Auswertung der Pinning-Events (jfr view ab Java 21).
  • jcmd <pid> Thread.dump_to_file -format=json dump.json: Dump mit allen Virtual Threads, gruppiert nach Thread-Containern.
  • jcmd <pid> Thread.vthread_scheduler und Thread.vthread_pollers: Zustand von Scheduler und I/O-Pollern (im Java-25-Manual).
  • -Djdk.virtualThreadScheduler.parallelism=N: Carrier-Zahl zum Testen ändern.
  • -Djdk.tracePinnedThreads=full: nur Java 21–23, druckt Stack Traces bei Pinning.

8. Senior-Punkte

  1. Virtual Threads bringen Durchsatz, nicht Geschwindigkeit. Sie helfen bei vielen gleichzeitigen, wartenden Tasks. Ein einzelner Request wird nicht schneller.
  2. Der Engpass wandert. Ohne Thread-Grenze wird der DB-Connection-Pool oder der Downstream das Limit. Grenzen bewusst setzen, z. B. Semaphore pro Downstream.
  3. Java 25 statt 21 für Virtual Threads. JEP 491 entfernt das grösste Risiko (Pinning in synchronized). Ein LTS-Upgrade ist hier ein echtes Argument.
  4. Migration schrittweise: Erst Lasttest mit JFR (Pinning, Heap, Connection-Wartezeit). Dann einschalten, Feature-Flag behalten.
  5. Kein Ersatz für alles: CPU-Arbeit gehört in einen begrenzten Platform-Pool oder ForkJoinPool. Reaktive Stacks bleiben sinnvoll für Streaming und Backpressure.
  6. Structured Concurrency ist noch Preview (bis Java 27). Für Produktionscode auf Java 25 LTS deshalb mit Vorsicht oder gar nicht.

10. Fallen

  • „Virtual Threads sind schneller." → Falsch. Sie führen Code nicht schneller aus. Sie erlauben mehr gleichzeitige wartende Tasks.
  • „Man sollte Virtual Threads poolen." → Falsch. Pro Task ein neuer. Begrenzen mit Semaphore.
  • „synchronized pinnt immer." → Veraltet. Gilt nur für Java 21–23. Seit Java 24 (JEP 491) nicht mehr.
  • „Ab Java 24 gibt es kein Pinning mehr." → Falsch. Native Frames, Klassen-Laden und Klassen-Initialisierer pinnen weiter.
  • „Virtual Threads laufen im Common Pool." → Falsch. Sie haben einen eigenen ForkJoinPool im FIFO-Modus.
  • „Structured Concurrency ist in Java 21 final." → Falsch. Preview von Java 21 bis 27. Final erst mit JDK 28 geplant (JEP 543).
  • „Scoped Values sind noch Preview." → Veraltet. Final seit Java 25 (JEP 506).

11. Fragen

Was ist ein Virtual Thread?

Ein Thread, den die JVM statt des Betriebssystems verwaltet. Er belegt einen OS-Thread nur, solange er rechnet, und gibt ihn beim Blockieren frei.

Seit wann gibt es Virtual Threads final?

Seit Java 21 (JEP 444). In Java 19 und 20 waren sie Preview.

Welches Problem lösen sie?

Thread-per-Request skaliert mit Platform Threads schlecht, weil OS-Threads teuer sind. Virtual Threads erlauben Millionen wartende Requests mit einfachem, blockierendem Code.

Was ist ein Carrier Thread?

Ein Platform Thread des Virtual-Thread-Schedulers. Er führt gerade einen gemounteten Virtual Thread aus.

Was heisst mount und unmount?

Mount: Der Scheduler setzt einen Virtual Thread auf einen Carrier. Unmount: Beim Blockieren speichert er seine Frames im Heap und gibt den Carrier frei.

Welcher Scheduler steckt dahinter?

Ein eigener ForkJoinPool im FIFO-Modus, getrennt vom Common Pool. Standard: so viele Carrier wie CPUs.

Was ist Pinning?

Der Virtual Thread kann beim Blockieren nicht unmounten. Er blockiert damit auch seinen Carrier und den OS-Thread.

Wann pinnt ein Virtual Thread in Java 21?

In synchronized-Blöcken und -Methoden sowie in nativen Methoden und Foreign Functions.

Was hat JEP 491 geändert?

Seit Java 24 gehören Monitore dem Virtual Thread, nicht dem Carrier. Blockieren in synchronized und in Object.wait() gibt den Carrier frei.

Wo pinnt ein Virtual Thread ab Java 24 noch?

Wenn nativer Code zurück in blockierenden Java-Code ruft, beim Laden einer Klasse, in Klassen-Initialisierern und beim Warten auf deren Initialisierung.

Wie finden Sie Pinning?

Mit dem JFR-Event jdk.VirtualThreadPinned, z. B. mit jfr print oder jfr view pinned-threads. In Java 21–23 zusätzlich -Djdk.tracePinnedThreads.

Kompensiert der Scheduler Pinning?

Nein. Er kompensiert nur bestimmte blockierende JDK-Operationen wie Dateisystem-Zugriffe, bis maxPoolSize (Standard 256).

Sind Virtual Threads für CPU-lastige Arbeit gut?

Nein. Mehr Threads als Kerne bringen bei CPU-Arbeit nichts. Dazu unterbricht der Scheduler rechnende Virtual Threads nicht.

Wann helfen Virtual Threads wirklich?

Bei vielen gleichzeitigen Tasks (Tausende und mehr), die meist warten, z. B. auf HTTP oder DB.

Warum sollte man Virtual Threads nicht poolen?

Sie sind billig. Ein Pool bringt nur Overhead und alte ThreadLocal-Zustände. Für eine Grenze nimmt man eine Semaphore.

Wie begrenzen Sie gleichzeitige Aufrufe an einen Dienst?

Mit einer Semaphore: acquire vor dem Aufruf, release im finally. Die Zahl der Permits ist die Grenze.

Funktionieren ThreadLocals mit Virtual Threads?

Ja, aber jeder der vielen Threads hat eine eigene Kopie. Das kostet Speicher. Für Kontext-Daten besser Scoped Values.

Was ist ein Scoped Value?

Ein unveränderlicher Wert, gebunden für die Dauer eines Aufrufs mit ScopedValue.where(...).run(...). Kind-Threads in Structured Concurrency erben ihn. Final seit Java 25.

Was ist Structured Concurrency, und wie ist der Status?

Eine API, die Unter-Tasks als Einheit mit gemeinsamer Lebensdauer behandelt. Fehler brechen die anderen ab. Preview von Java 21 bis 27, final geplant für JDK 28.

Welche Vorteile hat StructuredTaskScope gegenüber ExecutorService?

Unter-Tasks enden mit dem Scope, es gibt keine Thread-Leaks. Ein Fehler bricht die anderen ab. Thread Dumps zeigen die Eltern-Kind-Beziehung.

Kann man Priorität oder Daemon-Status setzen?

Nein. Virtual Threads sind immer Daemon und haben immer NORM_PRIORITY.

Wie sieht man Virtual Threads im Thread Dump?

Mit jcmd Thread.dump_to_file, auch im JSON-Format. jstack zeigt nur Platform Threads und Carrier.

Wie schalten Sie Virtual Threads in Spring Boot ein?

Mit spring.threads.virtual.enabled=true. Die Spring-Doku empfiehlt Java 24 oder neuer, wegen des Pinnings.

Virtual Threads oder reaktive Programmierung?

Für typische Request-Response-Services mit blockierenden Treibern: Virtual Threads, weil der Code einfach bleibt. Für Streaming mit Backpressure bleibt Reactor sinnvoll.

Szenario: Nach dem Einschalten von Virtual Threads auf Java 21 friert der Service unter Last ein, CPU fast 0 %. Was prüfen Sie?

Pinning: synchronized um I/O belegt alle Carrier. Prüfen mit JFR jdk.VirtualThreadPinned. Lösung: auf Java 25 wechseln oder den Block auf ReentrantLock umstellen.

Szenario: Mit Virtual Threads kommen plötzlich viele Timeouts beim Holen einer DB-Connection. Warum?

Früher begrenzte der Thread Pool die Gleichzeitigkeit. Jetzt warten Tausende Threads auf wenige Connections. Lösung: Semaphore vor der DB oder Grenze bewusst setzen, Pool-Wartezeit messen.

Szenario: Ein Team will einen Bildverarbeitungs-Service auf Virtual Threads umstellen, damit er schneller wird. Ihr Rat?

Das bringt wenig: Bildverarbeitung ist CPU-Arbeit. Virtual Threads helfen nur bei wartenden Tasks. Besser ein Pool mit etwa Kernanzahl Threads und Profiling.
