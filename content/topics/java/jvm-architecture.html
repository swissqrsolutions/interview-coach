JVM-Architektur

Kern: Die JVM (Java Virtual Machine) ist ein Programm, das Bytecode aus .class-Dateien ausführt. Sie löst das Problem, dass jede CPU und jedes Betriebssystem anderen Maschinencode braucht. Sie hat drei Teile: Class Loader Subsystem, Runtime Data Areas (Speicher) und Execution Engine (Interpreter, JIT, GC).

1. Wo sitzt was in der JVM?

  1. Class Loader Subsystem: lädt Klassen bei Bedarf, prüft den Bytecode und initialisiert sie. Beispiel: java.lang.String kommt vom Bootstrap ClassLoader.
  2. Heap: hält alle Objekte und Arrays. Alle Threads teilen ihn. Beispiel: new ArrayList<>() landet hier.
  3. Method Area: hält Klassen-Daten, also Methoden, Bytecode und den Run-Time Constant Pool (Konstanten und symbolische Referenzen pro Klasse). In HotSpot heisst sie Metaspace und liegt im nativen Speicher.
  4. Pro Thread: der PC Register (aktuelle Bytecode-Adresse), der JVM Stack (ein Frame pro Methodenaufruf) und der Native Method Stack (für nativen Code). Beispiel: Eine lokale int-Variable liegt im Frame.
  5. Execution Engine: führt Bytecode aus. Der Interpreter startet sofort. Der JIT kompiliert heisse Methoden in den Code Cache. Der GC räumt den Heap auf.
  6. JNI / FFM: JNI (Java Native Interface) und die FFM API (Foreign Function & Memory, final seit Java 22) rufen C-Code auf. Beispiel: Dateizugriff endet in einer nativen Methode.

2. Die Reise eines Programms (die Geschichte zum Merken)

  1. Start: java Main startet den Launcher. Er liest die Flags und lädt die JVM-Bibliothek (jvm.dll oder libjvm.so). Die JVM reserviert Heap, Metaspace und Code Cache.
  2. Kernklassen laden: Der Bootstrap ClassLoader lädt java.lang.Object, String und weitere aus dem Modul java.base. Die meisten kommen fertig aus dem CDS-Archiv (Class Data Sharing, ein vorbereitetes Abbild geladener Klassen). Das spart Startzeit.
  3. Main laden: Der App ClassLoader findet Main.class im Classpath. Die JVM verifiziert den Bytecode, legt die static-Felder an und führt den static-Block aus.
  4. main() läuft: Der Thread main bekommt einen eigenen JVM Stack. Jeder Aufruf legt einen Frame darauf: lokale Variablen, Operand Stack (Zwischenwerte der Bytecode-Befehle) und eine Referenz auf den Constant Pool.
  5. Objekte entstehen: new legt das Objekt im Heap an. Meist geht das in einen TLAB (Thread-Local Allocation Buffer, ein privates Stück Eden pro Thread). Das ist fast so billig wie ein Pointer-Inkrement. Im Frame liegt nur die Referenz.
  6. Ausführen: Der Interpreter führt den Bytecode aus und zählt Aufrufe. Heisse Methoden kompiliert der JIT in den Code Cache. Neue Klassen werden erst geladen, wenn der Code sie braucht (lazy).
  7. Aufräumen: Ist Eden voll, startet der GC. Er findet erreichbare Objekte ab den GC Roots (Stack-Variablen, statische Felder, JNI-Referenzen). Alle anderen gibt er frei.
  8. Ende: Die JVM endet, wenn der letzte Nicht-Daemon-Thread fertig ist oder System.exit läuft. Vorher laufen die Shutdown Hooks.

3. Beispiel: die Teile der JVM von innen sehen

import java.lang.management.*;

public class JvmTour {
  static int depth = 0;
  static void recurse() { depth++; recurse(); }

  public static void main(String[] args) {
    System.out.println("VM:  " + System.getProperty("java.vm.name") + " " + Runtime.version());
    System.out.println("JIT: " + ManagementFactory.getCompilationMXBean().getName());
    for (GarbageCollectorMXBean gc : ManagementFactory.getGarbageCollectorMXBeans())
      System.out.println("GC:  " + gc.getName());
    System.out.println("Memory Pools:");
    for (MemoryPoolMXBean p : ManagementFactory.getMemoryPoolMXBeans())
      System.out.printf("  %-8s %-31s %,6d KB%n",
          p.getType() == MemoryType.HEAP ? "Heap" : "Non-Heap", p.getName(), p.getUsage().getUsed() / 1024);
    System.out.println("Geladene Klassen: " + ManagementFactory.getClassLoadingMXBean().getLoadedClassCount());
    System.out.println("Java-Threads: " + Thread.getAllStackTraces().keySet().stream().map(Thread::getName).sorted().toList());
    try { recurse(); } catch (StackOverflowError e) {
      System.out.println("StackOverflowError nach " + depth + " Aufrufen");
    }
    try { long[][] keep = new long[1000][]; for (int i = 0; ; i++) keep[i] = new long[1_000_000]; }
    catch (OutOfMemoryError e) { System.out.println("OutOfMemoryError: " + e.getMessage()); }
  }
}

Echte Ausgabe, OpenJDK 17.0.3 (Oracle-HotSpot-Build 17.0.3.1), Windows x64. Java 21 und 25 zeigen dieselben Pool-Namen und dasselbe Verhalten. Die Zahl der Aufrufe bis zum StackOverflowError schwankt von Lauf zu Lauf (ein anderer Lauf: 20540).

  1. Die Execution Engine hat einen JIT („Tiered Compilers“ = C1 + C2) und den G1-GC. G1 ist seit Java 9 der Standard.
  2. Heap besteht bei G1 aus Eden, Survivor und Old Gen. Neue Objekte landen in Eden.
  3. Non-Heap sind Metaspace, Compressed Class Space (Klassen-Metadaten für komprimierte Klassen-Pointer) und drei CodeHeaps (der segmentierte Code Cache).
  4. Ein leeres Programm lädt schon 954 Klassen. Die meisten kommen aus java.base.
  5. Die JVM hat eigene Java-Threads, z. B. Reference Handler und Signal Dispatcher. GC- und JIT-Threads sind native Threads und fehlen in dieser Liste.
  6. Der Stack ist pro Thread begrenzt. -Xss256k macht ihn kleiner, darum kommt der StackOverflowError viel früher.
  7. Der Heap ist durch -Xmx256m begrenzt. Darum kommt OutOfMemoryError: Java heap space.
  8. Mit -Xint gibt es keinen JIT. getCompilationMXBean() liefert dann null.

4. Details, die Interviewer fragen

  1. Spezifikation vs. Implementierung: Die JVM Specification beschreibt nur das Verhalten. HotSpot ist die Implementierung in OpenJDK. Begriffe wie Metaspace, Code Cache oder G1 sind HotSpot, nicht Spec.
  2. Sechs Run-Time Data Areas laut Spec: PC Register, JVM Stack, Native Method Stack (pro Thread). Heap, Method Area, Run-Time Constant Pool (pro JVM).
  3. Stack Frame: Ein Frame hat ein Array für lokale Variablen, einen Operand Stack und eine Referenz auf den Constant Pool der Klasse. Der Frame entsteht beim Aufruf und verschwindet beim Return.
  4. Bytecode ist stack-basiert: a + b wird zu iload_1, iload_2, iadd. Die Werte gehen über den Operand Stack, nicht über Register.
  5. Metaspace: Seit Java 8 ersetzt Metaspace die PermGen (JEP 122). Metaspace liegt im nativen Speicher und ist standardmässig unbegrenzt. -XX:MaxMetaspaceSize setzt eine Grenze.
  6. Wo liegen statische Felder? In HotSpot liegen die Werte von static-Feldern im Heap, im java.lang.Class-Objekt der Klasse. Die Klassen-Metadaten liegen im Metaspace. Auch der String Pool liegt im Heap.
  7. Code Cache: Speicher für JIT-Code, seit Java 9 in drei Segmente geteilt (JEP 197): non-nmethods, profiled, non-profiled. Standardgrösse mit Tiered Compilation: 240 MB.
  8. Object Header: Jedes Objekt hat einen Header mit Mark Word (Hash, Lock-Status, GC-Alter) und Klassen-Pointer. Normal sind das 12 Bytes. Java 25 bietet Compact Object Headers mit 8 Bytes an (JEP 519, Flag -XX:+UseCompactObjectHeaders, nicht Standard).
  9. Virtual Threads (Java 21, JEP 444): Ihr Stack liegt im Heap als Stack-Chunk-Objekte, wenn sie nicht laufen. Darum kosten Millionen Virtual Threads wenig Speicher. Platform Threads haben weiterhin einen festen nativen Stack.
  10. Standard-Heapgrösse: Ohne -Xmx nimmt HotSpot 1/4 des physischen Speichers (MaxRAMPercentage=25). In Containern zählt das Container-Limit (UseContainerSupport, Standard an).
  11. GC-Auswahl: Standard ist G1. Auf sehr kleinen Maschinen (1 CPU oder unter ca. 1792 MB) wählt die JVM Serial GC. ZGC ist seit Java 23 standardmässig generational, ab Java 24 nur noch generational.
  12. Process-Speicher ist mehr als Heap: RSS = Heap + Metaspace + Code Cache + Thread-Stacks + Direct Memory + GC-Strukturen + JVM-intern. Darum braucht ein Container mehr als -Xmx.
  13. Startzeit: CDS ist seit Java 12 standardmässig an. Java 24 bringt den AOT Cache (JEP 483): Klassen geladen und gelinkt aus einem Trainingslauf. Java 25 vereinfacht das mit -XX:AOTCacheOutput (JEP 514) und speichert auch Profile (JEP 515).

5. Vergleich

  • JVM: führt Bytecode aus. Kennt nur .class, nicht die Sprache Java. Auch Kotlin und Scala laufen darauf.
  • JRE: JVM + Standardbibliothek. Seit Java 11 liefert Oracle kein eigenes JRE mehr. Heute baut man mit jlink eine eigene, kleine Runtime.
  • JDK: JRE + Werkzeuge wie javac, jcmd, jlink, jfr.
  • Heap vs. Stack: Heap ist geteilt, hält Objekte und wird vom GC verwaltet. Stack ist pro Thread, hält Frames und wird beim Return frei.
  • Metaspace vs. PermGen: PermGen war fester Teil des Heaps bis Java 7. Metaspace ist nativer Speicher, wächst automatisch und existiert seit Java 8.
  • HotSpot vs. OpenJ9 vs. GraalVM: HotSpot ist die Standard-JVM in OpenJDK. OpenJ9 (Eclipse) braucht oft weniger Speicher. GraalVM hat einen JIT in Java und baut Native Images ohne JVM zur Laufzeit.
  • JVM vs. Native Image: JVM: Warm-up, dann beste Spitzenleistung. Native Image: Start in Millisekunden, aber Reflection braucht Konfiguration.

6. In der Produktion

  1. Container wird OOMKilled, aber kein OutOfMemoryError: Der Prozess braucht mehr als das Container-Limit. Der Heap ist nur ein Teil. Lösung: -XX:MaxRAMPercentage=70–75 statt festem -Xmx nahe am Limit. Native Speicher mit NMT messen.
  2. OutOfMemoryError: Java heap space: Zu viele lebende Objekte, oft ein Leak in einem Cache. Lösung: Heap Dump bei OOM (-XX:+HeapDumpOnOutOfMemoryError) und mit Eclipse MAT den Besitzer finden.
  3. OutOfMemoryError: Metaspace: Zu viele Klassen, oft ein ClassLoader-Leak nach Redeploys oder viele generierte Proxies. Lösung: Leak finden, MaxMetaspaceSize als Schutzgrenze setzen.
  4. StackOverflowError: Endlose oder zu tiefe Rekursion. Lösung: Rekursion in eine Schleife umbauen. -Xss nur erhöhen, wenn die Tiefe wirklich nötig ist.
  5. OutOfMemoryError: unable to create native thread: Zu viele Platform Threads, jeder mit eigenem Stack. Lösung: Thread-Pool begrenzen oder Virtual Threads (Java 21+).
  6. Langsamer Start nach Deployment: Klassen laden und JIT-Warm-up kosten Zeit. Lösung: CDS/AppCDS, AOT Cache (Java 24+), Readiness Probe erst nach Warm-up.

7. Diagnose: Werkzeuge, Flags, Befehle

  • jcmd: listet alle JVMs. jcmd <pid> help zeigt alle Befehle.
  • jcmd <pid> VM.flags oder jinfo -flags <pid>: aktive JVM-Flags.
  • java -XX:+PrintFlagsFinal -version: alle Flags mit Endwerten, z. B. MaxHeapSize, UseG1GC, ReservedCodeCacheSize.
  • jcmd <pid> GC.heap_info: Heap-Regionen und Belegung. jstat -gc <pid> 1000: GC-Statistik jede Sekunde.
  • jcmd <pid> VM.metaspace: Metaspace-Verbrauch pro ClassLoader.
  • -XX:NativeMemoryTracking=summary + jcmd <pid> VM.native_memory summary: nativer Speicher pro Bereich (Heap, Class, Thread, Code, GC).
  • jcmd <pid> Thread.print: Stack aller Threads (Thread Dump).
  • -Xlog:gc*: GC-Log. -Xlog:class+load: geladene Klassen.
  • JFR (Java Flight Recorder): jcmd <pid> JFR.start duration=60s filename=rec.jfr. Geringer Overhead, geeignet für die Produktion. Auswerten mit JDK Mission Control.
  • -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps: Heap Dump automatisch bei OOM.

8. Senior-Punkte

  1. Speicher planen heisst Prozess-Speicher planen, nicht nur Heap. Faustregel im Container: Heap 70–75 % des Limits, der Rest für Metaspace, Stacks, Code Cache und Direct Memory.
  2. Spec und HotSpot trennen. Im Interview zuerst die Spec-Begriffe (Method Area), dann die HotSpot-Umsetzung (Metaspace). Das zeigt Tiefe.
  3. Standardwerte sind meist gut. G1 und Ergonomics passen für die meisten Services. Flags nur nach Messung ändern.
  4. GC-Wahl ist eine Abwägung: G1 für Durchsatz und gute Pausen. ZGC für sehr kurze Pausen bei grossen Heaps, mit etwas mehr CPU und Speicher. Serial für kleine Container mit 1 CPU.
  5. Startzeit vs. Spitzenleistung: Lange laufende Services profitieren vom JIT. Kurze Jobs oder Serverless profitieren von AOT Cache oder Native Image.
  6. Virtual Threads ändern die Rechnung: Viele blockierende Aufgaben brauchen keine grossen Thread-Pools mehr. Aber CPU-lastige Arbeit wird dadurch nicht schneller.

„Ein Service im Kubernetes-Pod wurde OOMKilled, obwohl der Heap nur halb voll war. Mit NMT sahen wir viel Thread- und Metaspace-Speicher und setzten MaxRAMPercentage statt festem -Xmx.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Klassen-Metadaten liegen in der PermGen.“ → Falsch. PermGen gibt es seit Java 8 nicht mehr. Heute: Metaspace im nativen Speicher.
  • „-Xmx ist der Speicher der JVM.“ → Falsch. -Xmx begrenzt nur den Heap. Der Prozess braucht mehr.
  • „Primitive liegen im Stack, Objekte im Heap.“ → Ungenau. Lokale Primitive liegen im Frame. Primitive Felder eines Objekts liegen mit dem Objekt im Heap.
  • „Die JVM ist ein Interpreter.“ → Falsch. Sie hat Interpreter und JIT. Heisser Code läuft als Maschinencode.
  • „Jeder Thread hat seinen eigenen Heap.“ → Falsch. Der Heap ist geteilt. Nur der TLAB ist ein privater Teil von Eden für schnelles Anlegen.
  • „Das JRE ist ein eigenes Download-Paket.“ → Veraltet. Seit Java 11 baut man eine Runtime mit jlink.
  • „Ein StackOverflowError ist ein Heap-Problem.“ → Falsch. Er betrifft den Stack eines Threads. Mehr Heap hilft nicht.

11. Fragen

Was ist die JVM?

Ein Programm, das Bytecode ausführt. Es macht Java plattformunabhängig: gleicher Bytecode, eigene JVM pro Betriebssystem und CPU.

Aus welchen Hauptteilen besteht die JVM?

Class Loader Subsystem, Runtime Data Areas und Execution Engine. Dazu JNI/FFM als Brücke zu nativem Code.

Welche Run-Time Data Areas definiert die Spec?

Pro Thread: PC Register, JVM Stack, Native Method Stack. Pro JVM: Heap, Method Area, Run-Time Constant Pool.

Was ist der Unterschied zwischen Heap und Stack?

Der Heap ist geteilt und hält Objekte, der GC räumt ihn auf. Der Stack gehört einem Thread und hält Frames mit lokalen Variablen.

Was steht in einem Stack Frame?

Lokale Variablen, der Operand Stack und eine Referenz auf den Constant Pool. Er entsteht beim Aufruf und verschwindet beim Return.

Was ist die Method Area und wie heisst sie in HotSpot?

Sie hält Klassen-Metadaten, Bytecode und den Run-Time Constant Pool. In HotSpot ist das der Metaspace im nativen Speicher.

Warum wurde PermGen durch Metaspace ersetzt?

PermGen hatte eine feste Grösse und lief oft voll. Metaspace liegt im nativen Speicher und wächst nach Bedarf. Das kam mit Java 8.

Wo liegen statische Variablen?

In HotSpot im Heap, im Class-Objekt der Klasse. Die Metadaten der Klasse liegen im Metaspace.

Was ist der Run-Time Constant Pool?

Eine Tabelle pro Klasse mit Konstanten und symbolischen Referenzen auf Klassen, Methoden und Felder. Die JVM löst diese Referenzen bei Bedarf auf.

Was macht die Execution Engine?

Sie führt Bytecode aus: zuerst der Interpreter, heisse Methoden der JIT. Der GC gehört auch dazu.

Was ist der Code Cache?

Nativer Speicher für JIT-kompilierten Maschinencode. Seit Java 9 in drei Segmente geteilt. Ist er voll, stoppt der JIT.

Was ist ein TLAB?

Ein privates Stück Eden pro Thread. Objekte werden dort ohne Lock angelegt, nur durch Verschieben eines Pointers.

Was sind GC Roots?

Startpunkte für die Erreichbarkeit: lokale Variablen in Frames, statische Felder, JNI-Referenzen, aktive Threads. Was davon nicht erreichbar ist, kann weg.

Welcher GC ist Standard?

G1, seit Java 9. Auf sehr kleinen Maschinen wählt die JVM Serial GC.

Wie gross ist der Heap ohne -Xmx?

1/4 des physischen Speichers oder des Container-Limits. Steuerbar mit MaxRAMPercentage.

Warum braucht der Java-Prozess mehr Speicher als -Xmx?

Dazu kommen Metaspace, Code Cache, Thread-Stacks, Direct Memory und GC-Strukturen. Messen mit Native Memory Tracking.

Was ist der Unterschied zwischen JVM, JRE und JDK?

JVM führt Bytecode aus. JRE ist JVM plus Bibliothek. JDK ist JRE plus Werkzeuge wie javac.

Was ist JNI und was ist FFM?

JNI ist die alte Schnittstelle zu C-Code. Die FFM API ist der moderne Ersatz, final seit Java 22, ohne C-Glue-Code.

Wo liegt der Stack eines Virtual Threads?

Wenn er nicht läuft, im Heap als Stack-Chunk-Objekte. Darum sind Virtual Threads billig.

Was ist der Object Header?

Mark Word plus Klassen-Pointer, normal 12 Bytes. Java 25 bietet Compact Object Headers mit 8 Bytes als Option.

Wann endet die JVM?

Wenn der letzte Nicht-Daemon-Thread endet oder System.exit läuft. Vorher laufen Shutdown Hooks.

Was ist CDS?

Class Data Sharing: ein Archiv mit vorbereiteten Klassen. Es spart Startzeit und Speicher. Seit Java 12 standardmässig für JDK-Klassen an.

Welche OutOfMemoryError-Arten kennen Sie?

Java heap space, Metaspace, unable to create native thread, Direct buffer memory, GC overhead limit exceeded. Jede zeigt auf einen anderen Speicherbereich.

Wie sehen Sie die Speicherbereiche einer laufenden JVM?

jcmd GC.heap_info, VM.metaspace, VM.native_memory summary (mit NMT), jstat -gc, JFR. Im Code über MemoryPoolMXBean.

Szenario: Der Pod wird OOMKilled, aber es gibt keinen OutOfMemoryError im Log. Was tun Sie?

Der Prozess ist über dem Container-Limit, nicht der Heap. NMT einschalten und Bereiche vergleichen. Heap mit MaxRAMPercentage auf ca. 75 % setzen und Thread-Zahl prüfen.

Szenario: Nach vielen Redeploys im Tomcat kommt OutOfMemoryError: Metaspace. Warum?

Ein ClassLoader-Leak: Etwas hält eine Referenz auf den alten Webapp-ClassLoader. Seine Klassen bleiben im Metaspace. Mit Heap Dump den Pfad zum Loader finden, z. B. ThreadLocal oder JDBC-Treiber.

Szenario: Ein Batch-Job wirft StackOverflowError bei tiefen Bäumen. Was tun Sie?

Die Rekursion ist zu tief für den Thread-Stack. Besser iterativ mit eigenem Deque umbauen. Kurzfristig -Xss erhöhen oder den Job in einem Thread mit grösserem Stack starten.
