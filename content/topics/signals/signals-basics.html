Signals: signal, computed, effect

Kern: Ein Signal ist ein Wrapper um einen Wert, der seine Leser benachrichtigt, wenn der Wert sich ändert. Angular baut daraus einen reaktiven Graphen: signal hält Zustand, computed leitet Werte ab, effect führt Seiteneffekte aus. So weiss Angular genau, welche Stelle neu gerendert werden muss, ohne Zone.js-Raten. In Angular 22 sind signal, computed, effect und linkedSignal stabil; Signals kamen in v16 als Developer Preview.

1. Wo sitzen Signals in Angular?

  1. Producer: ein Knoten, der einen Wert liefert. Beispiel: count = signal(0).
  2. Consumer: ein Knoten, der Signals liest und davon abhängt. Beispiel: ein Template oder ein effect.
  3. computed ist beides: Consumer seiner Quellen, Producer für seine Leser.
  4. Die Kanten entstehen automatisch beim Lesen (dynamic dependency tracking). Es gibt keine Abo-Liste von Hand.
  5. Das Template ist ein Consumer. Ändert sich ein gelesenes Signal, markiert Angular genau diese View zum Neuprüfen.

2. Die Reise einer Änderung (die Geschichte zum Merken)

  1. Schreiben. Code ruft count.set(5). Das Signal vergleicht mit Object.is. Ist der Wert neu, erhöht es seine Version.
  2. Push der Dirtiness. Das Signal ruft keine Funktionen auf. Es markiert nur seine Consumer als „vielleicht veraltet“. Das ist billig und synchron.
  3. Planen. Die Template-View wird zum Neuprüfen markiert. Ein effect wird für später eingeplant, nicht sofort ausgeführt.
  4. Lesen. Später rendert Angular die View oder führt den Effect aus. Der liest double().
  5. Pull. Das computed prüft die Versionen seiner Quellen. Hat sich keine Quelle geändert, liefert es den Cache.
  6. Neu rechnen. Nur wenn nötig, ruft es seine Funktion neu auf. Ist das Ergebnis gleich (laut equal), bleiben die Leser „sauber“.

Dieses Modell heisst push-pull: Dirtiness wird gepusht, Werte werden gepullt. Daraus folgt glitch-free: Kein Consumer sieht je einen halb aktualisierten Zwischenzustand.

3. Beispiel: signal, computed, effect, untracked

import { Component, signal, computed, effect, untracked } from '@angular/core';

@Component({
  selector: 'app-cart',
  template: `
    <p>{{ count() }} × {{ price() }} = {{ total() }}</p>
    <button (click)="add()">+1</button>`,
})
export class CartComponent {
  count = signal(1);
  price = signal(10);
  user  = signal('Ana');
  total = computed(() => {
    console.log('compute total');
    return this.count() * this.price();
  });

  constructor() {
    effect((onCleanup) => {
      const t = this.total();                         // tracked
      const u = untracked(() => this.user());       // NOT tracked
      console.log(`effect: ${u} total=${t}`);
      const id = setTimeout(() => console.log('saved', t), 500);
      onCleanup(() => clearTimeout(id));
    });
  }

  add() {
    this.count.update(c => c + 1);
    this.count.update(c => c + 1);   // two writes, same tick
    this.user.set('Ben');             // untracked: no effect run
  }
}
// Start
compute total
effect: Ana total=10
saved 10                // nach 500 ms
// Klick auf +1
compute total
effect: Ben total=30

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Angular 20 bis 22.

  1. total rechnet nur, wenn jemand es liest. Das Template liest es zuerst, darum „compute total“ einmal.
  2. Der Effect läuft asynchron beim nächsten Durchlauf, nicht im Konstruktor.
  3. Zwei update() im selben Tick: Der Effect läuft trotzdem nur einmal, mit dem Endwert 3 × 10 = 30.
  4. user wird mit untracked gelesen. Allein eine Änderung von user startet den Effect nicht. Er sieht aber den aktuellen Wert „Ben“, weil total ihn auslöst.
  5. Der Klick kommt vor Ablauf der 500 ms? Dann löscht onCleanup den alten Timer vor dem nächsten Lauf. Kein veraltetes „saved“.

4. Details, die Interviewer fragen

  1. WritableSignal API: set(v) ersetzt den Wert. update(fn) rechnet aus dem alten Wert. asReadonly() gibt eine Nur-Lese-Sicht nach aussen. Beispiel: Service hält _items privat und gibt items = _items.asReadonly() heraus.
  2. Equality: Standard ist Object.is. Ein neues Objekt mit gleichem Inhalt gilt als geändert. Eigene Regel: signal(x, { equal: (a, b) => a.id === b.id }).
  3. Immutabilität: items().push(x) ändert das Array, aber nicht die Referenz. Kein Consumer wird benachrichtigt. Richtig: items.update(l => [...l, x]).
  4. Lazy computed: Ein computed rechnet erst beim ersten Lesen. Ohne Leser rechnet es nie. Danach ist es memoized, also gecacht bis eine Quelle sich ändert.
  5. Dynamische Abhängigkeiten: Nur Signals, die im letzten Lauf gelesen wurden, zählen. Beispiel: computed(() => show() ? name() : '') hängt bei show() === false nicht von name ab.
  6. computed ist read-only: Man kann es nicht setzen. Für „abgeleitet, aber überschreibbar“ gibt es linkedSignal (eingeführt in v19, stabil seit v20).
  7. Kein Schreiben in computed: Ein set() in einem computed oder Template wirft NG0600 („Signal write in a disallowed context“). computed muss rein (pure) sein.
  8. effect braucht einen Injection Context: Konstruktor, Feld-Initialisierer oder runInInjectionContext. Sonst effect(fn, { injector }) übergeben.
  9. effect-Lebensdauer: Ein Effect in einer Komponente stirbt mit der Komponente. In einem Root-Service lebt er so lange wie die App. Manuell: const ref = effect(...); ref.destroy().
  10. effect-Timing (seit v19, effect stabil seit v20): Component effects laufen während der Change Detection, vor dem Check ihrer View. Root effects (in Services) laufen vor der Change Detection aller Komponenten. Für DOM-Arbeit nach dem Rendern gibt es afterRenderEffect.
  11. Signal-Writes im effect: Seit v19 erlaubt, das Flag allowSignalWrites hat seitdem keine Wirkung mehr. Trotzdem schlechter Stil: Es erzeugt Kaskaden und mögliche Endlosschleifen.
  12. onCleanup: Läuft vor dem nächsten Lauf und beim Zerstören. Beispiel: Timer, Subscription oder AbortController abbrechen.
  13. untracked(fn): Liest Signals, ohne Abhängigkeit zu erzeugen. Wichtig auch beim Aufruf fremder Funktionen im Effect, die heimlich Signals lesen.
  14. Wann KEIN effect: Um einen Wert aus anderen Signals abzuleiten. Das ist ein computed oder linkedSignal. Effect ist für Sync nach aussen: Logging, localStorage, Canvas, Drittbibliotheken.
  15. Signals und Zoneless: Signals sagen Angular präzise, was sich geändert hat. Damit funktioniert Angular ohne Zone.js: provideZonelessChangeDetection() ist stabil seit v20.2 und seit v21 Default.
  16. Type Guard: isSignal(x) prüft, ob etwas ein Signal ist. Typ Signal<T> ist read-only, WritableSignal<T> schreibbar.

5. Vergleich

  • signal vs BehaviorSubject: Beide halten einen aktuellen Wert. Signal liest synchron mit (), braucht kein Abo und kein Unsubscribe. BehaviorSubject kann Ereignisse über Zeit und Operatoren wie debounceTime.
  • computed vs RxJS combineLatest + map: computed ist glitch-free und lazy. combineLatest feuert bei jeder Quelle einzeln, Zwischenzustände sind sichtbar.
  • computed vs Getter-Methode im Template: Ein Getter rechnet bei jeder Change Detection neu. computed rechnet nur bei geänderten Quellen.
  • effect vs computed: computed liefert einen Wert, ohne Seiteneffekte. effect liefert keinen Wert, nur Seiteneffekte.
  • effect vs afterRenderEffect: effect für Zustand und Aussenwelt. afterRenderEffect für DOM-Messen und -Schreiben nach dem Rendern, mit Phasen earlyRead, write, mixedReadWrite, read.
  • Signals vs Zone.js-Change-Detection: Zone.js meldet „irgendwas ist passiert“, Angular prüft den Baum. Signals melden „genau dieser Wert in genau dieser View“.

6. In der Produktion

  1. Mutation statt neuer Referenz: user().name = 'x' ändert die UI nicht (OnPush). Lösung: immer update mit neuem Objekt.
  2. Endlosschleife im Effect: Ein Effect liest und schreibt dasselbe Signal. Lösung: Ableitung als computed, oder Lesen mit untracked.
  3. Effect als State-Sync-Kette: Effect A setzt B, Effect B setzt C. Schwer zu debuggen, mehrere Render-Durchläufe. Lösung: computed/linkedSignal.
  4. Effect ausserhalb Injection Context: Fehler NG0203 (inject() must be called from an injection context). Lösung: Effect im Konstruktor erstellen oder injector mitgeben.
  5. Memory Leak: Effect in einem Root-Service mit Bezug auf eine Komponente. Lösung: Effect in der Komponente erstellen oder ref.destroy().
  6. Teure computed mit neuem Array: computed(() => list().filter(...)) erzeugt immer ein neues Array. Downstream rechnet jedes Mal neu. Lösung: equal-Funktion oder kleinere Signals.
  7. Race in async Effect: Effect startet fetch, Wert ändert sich, alte Antwort kommt später. Lösung: onCleanup mit AbortController, oder besser resource()/rxResource.

7. Diagnose: Werkzeuge und Befehle

  • Angular DevTools (Browser-Erweiterung): Komponentenbaum, Signal-Werte, Profiler und ein Signal Graph, der Abhängigkeiten zeigt.
  • console.log in computed: zeigt, wie oft es wirklich rechnet. Nur zum Debuggen.
  • ng generate @angular/core:signals: kombinierte Migration (seit v19) für Inputs, Outputs und Queries (siehe Seite signal-inputs).
  • Fehler NG0600: Schreiben in ein Signal an verbotener Stelle, z. B. in einem computed oder Template.
  • Fehler NG0203: effect oder inject ausserhalb eines Injection Context.
  • Chrome Performance-Tab mit Angular-Daten (seit v20): zeigt Change-Detection-Läufe und Effects.

8. Senior-Punkte

  1. Ableiten vor Synchronisieren. Faustregel: 90 % computed, wenige effect. Jeder Effect, der ein Signal setzt, ist ein Code-Smell zur Prüfung.
  2. Signals sind synchroner Zustand. Für Ereignisse über Zeit (Debounce, Abbruch, WebSocket) bleibt RxJS das bessere Werkzeug. Beides wird über Interop verbunden.
  3. Immutabilität ist Pflicht, nicht Stil. Ohne neue Referenzen funktioniert weder Object.is noch OnPush.
  4. Kapselung: Schreibbare Signals privat halten, nach aussen asReadonly() oder computed. Nur der Besitzer ändert Zustand.
  5. Weg zu Zoneless: Signals plus OnPush sind die Voraussetzung. In v22 sind beide Default (Zoneless seit v21, OnPush seit v22). Das senkt Bundle-Grösse und Change-Detection-Kosten.
  6. Migration schrittweise: Neue Komponenten mit Signals, alte RxJS-Services über toSignal anbinden. Kein Big-Bang-Umbau.

10. Fallen

  • „Ein effect läuft sofort und bei jedem set().“ → Falsch. Er läuft asynchron, einmal pro Durchlauf, mit dem Endwert.
  • „computed rechnet bei jeder Change Detection.“ → Nein. Es ist lazy und memoized, es rechnet nur bei geänderten Quellen.
  • „Für abgeleiteten State nehme ich effect + set.“ → Falsch. Das ist computed oder linkedSignal.
  • „items().push(x) aktualisiert die UI.“ → Nein. Gleiche Referenz, keine Benachrichtigung.
  • „Signals ersetzen RxJS komplett.“ → Nein. Signals für Zustand, RxJS für asynchrone Ereignisströme.
  • „untracked heisst, ich sehe einen alten Wert.“ → Nein. Ich sehe den aktuellen Wert, nur ohne Abhängigkeit.

11. Fragen

Was ist ein Signal?

Ein Wrapper um einen Wert, der seine Leser bei Änderungen benachrichtigt. Lesen mit sig(), schreiben mit set oder update.

Welches Problem lösen Signals?

Feingranulare Reaktivität: Angular weiss genau, welche View sich ändert. Das macht Change Detection gezielt und ermöglicht Zoneless.

Was sind Producer und Consumer?

Ein Producer liefert einen Wert (signal, computed). Ein Consumer liest Signals und hängt davon ab (computed, effect, Template). computed ist beides.

Wie entstehen Abhängigkeiten?

Automatisch beim Lesen während eines reaktiven Kontexts. Nur die im letzten Lauf gelesenen Signals zählen.

Was heisst glitch-free?

Kein Consumer sieht einen inkonsistenten Zwischenzustand. Dirtiness wird gepusht, Werte werden erst beim Lesen gepullt und konsistent berechnet.

Was heisst lazy und memoized bei computed?

Lazy: Es rechnet erst beim ersten Lesen. Memoized: Es cached das Ergebnis, bis eine Quelle sich ändert.

Wie vergleicht ein Signal Werte?

Standard mit Object.is. Mit der Option equal kann man eine eigene Vergleichsfunktion setzen.

Warum aktualisiert items().push(x) die UI nicht?

Die Referenz bleibt gleich, Object.is meldet „unverändert“. Richtig ist update(l => [...l, x]).

Wann läuft ein effect?

Mindestens einmal, dann asynchron nach Änderungen. Component effects laufen in der Change Detection vor ihrer View, root effects davor.

Wofür ist onCleanup?

Aufräumen vor dem nächsten Lauf oder beim Zerstören. Beispiel: Timer löschen, Request abbrechen.

Was macht untracked?

Es liest Signals, ohne eine Abhängigkeit zu erzeugen. Der Effect läuft dann nicht neu, wenn sich nur dieses Signal ändert.

Wann sollte man KEIN effect nutzen?

Um State aus State abzuleiten. Dafür gibt es computed und linkedSignal. Effect nur für Sync mit der Aussenwelt.

Darf man in einem effect Signals setzen?

Seit v19 ja, allowSignalWrites ist nicht mehr nötig. Es ist aber riskant: Kaskaden, Endlosschleifen, schwer nachvollziehbar.

Darf man in einem computed Signals setzen?

Nein. Das wirft NG0600. computed muss eine reine Funktion sein.

Warum braucht effect einen Injection Context?

Er holt sich darüber Scheduler und DestroyRef. So wird er mit der Komponente oder dem Service automatisch zerstört.

Was ist asReadonly()?

Eine Nur-Lese-Sicht auf ein WritableSignal. So kann nur der Besitzer, z. B. ein Service, den Zustand ändern.

Was ist afterRenderEffect?

Ein Effect, der nach dem Rendern läuft, in Phasen wie read und write. Für DOM-Messungen und Drittbibliotheken.

Was ist linkedSignal?

Ein schreibbares Signal, das sich bei Änderung einer Quelle zurücksetzt. Beispiel: ausgewählte Option, die auf die erste zurückspringt, wenn die Liste wechselt.

Signal oder BehaviorSubject?

Signal für synchronen Zustand im UI. BehaviorSubject bzw. RxJS, wenn Zeit-Operatoren, Abbruch oder Event-Ströme nötig sind.

Wie hängen Signals und Zoneless zusammen?

Signals melden präzise Änderungen an den Scheduler. Darum braucht Angular Zone.js nicht mehr, um Änderungen zu erraten.

Szenario: Ein Effect setzt ein Signal, das er selbst liest, und die App hängt. Was tun?

Das ist eine Schleife. Den abgeleiteten Wert als computed schreiben, oder das gelesene Signal mit untracked lesen.

Szenario: Ein Kollege ändert ein Feld im Objekt-Signal, die OnPush-Komponente zeigt nichts Neues. Warum?

Mutation behält die Referenz, das Signal meldet keine Änderung. Mit update(u => ({ ...u, name })) ein neues Objekt setzen.

Szenario: Ein Effect lädt Daten bei jeder Filter-Änderung, alte Antworten überschreiben neue. Lösung?

Race Condition. Mit onCleanup und AbortController abbrechen, oder besser resource()/rxResource mit switchMap-Semantik nutzen.
