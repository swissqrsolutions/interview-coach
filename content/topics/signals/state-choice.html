Welches State Management wann?

Angular Signals + NgRx · Tier 1 · Quellen: angular.dev Guides „Signals“, „Sharing data with services / Dependency Injection“, „Async reactivity with resources“, „Signal Forms“ (v22), ngrx.io „@ngrx/store – When should I use NgRx Store?“ (SHARI-Prinzip), ngrx.io „@ngrx/signals – SignalStore“, „Events“ (NgRx 22)

Kern: State Management ist die Entscheidung, wo ein Zustand lebt, wer ihn ändern darf und wie lange er existiert. In Angular 22 (mit NgRx 22) gibt es vier Stufen: Signals in der Komponente, Service mit Signals, NgRx SignalStore, globaler NgRx Store. Die richtige Wahl ist die kleinste Stufe, die die Anforderungen an Teilen, Nachvollziehbarkeit und Teamgrösse erfüllt.

1. Wo sitzt welcher State?

  1. Komponenten-State: lebt und stirbt mit der Komponente. Beispiel: Dropdown offen, aktueller Tab.
  2. Service mit Signals: geteilter Zustand für wenige Komponenten, ohne Bibliothek. Beispiel: CartService mit items-Signal.
  3. SignalStore: strukturierter Feature-State mit Entities, Lade-Status und wiederverwendbaren Features. Beispiel: TodoStore.
  4. Globaler Store: App-weiter Zustand mit Action-Log, Time Travel und strengen Regeln. Beispiel: Auth, Berechtigungen, Mandant.

2. Die Reise einer Entscheidung (die Geschichte zum Merken)

  1. Frage 1: Wer braucht den Zustand? Nur eine Komponente und ihre Kinder? Dann signal in der Komponente, Kinder bekommen ihn per input().
  2. Frage 2: Ist es einfach? Zwei, drei Komponenten teilen einen Wert ohne Laden und Fehlerstatus? Dann ein Service mit privatem signal und asReadonly().
  3. Frage 3: Ist es Feature-Logik? Listen, Laden, Filter, Entities, Lade- und Fehlerstatus? Dann ein SignalStore pro Feature.
  4. Frage 4: Ist es App-weit und kritisch? Viele Teams, viele Features reagieren auf dieselben Ereignisse, Nachvollziehbarkeit ist Pflicht? Dann globaler NgRx Store.
  5. Querschnitt: Ist es Server-State? Daten, die nur angezeigt werden, sind ein Cache. Oft reicht httpResource/rxResource (stabil seit Angular 22) in Komponente oder Store.
  6. Querschnitt: URL-State? Filter und Seite, die man teilen oder bookmarken soll, gehören in die URL (Router-Parameter, mit withComponentInputBinding als input()).

3. Beispiel: derselbe Warenkorb auf drei Stufen

// Stufe 2: Service mit Signals
@Injectable({ providedIn: 'root' })
export class CartService {
  private readonly _items = signal<Item[]>([]);
  readonly items = this._items.asReadonly();
  readonly total = computed(() => this._items().reduce((s, i) => s + i.price, 0));
  add(i: Item) { this._items.update(l => [...l, i]); }
}

// Stufe 3: SignalStore
export const CartStore = signalStore({ providedIn: 'root' },
  withState({ items: [] as Item[] }),
  withComputed(({ items }) => ({ total: computed(() => items().reduce((s, i) => s + i.price, 0)) })),
  withMethods(store => ({ add(i: Item) { patchState(store, s => ({ items: [...s.items, i] })); } })));

// Stufe 4: globaler Store
export const CartActions = createActionGroup({ source: 'Product Page',
  events: { 'Add To Cart Clicked': props<{ item: Item }>() } });
export const cartFeature = createFeature({ name: 'cart',
  reducer: createReducer({ items: [] as Item[] },
    on(CartActions.addToCartClicked, (s, { item }) => ({ items: [...s.items, item] }))),
  extraSelectors: ({ selectItems }) => ({
    selectTotal: createSelector(selectItems, l => l.reduce((s, i) => s + i.price, 0)) }) });

// Nutzung in der Komponente
cart.add(kaffee);                                            // Stufe 2 und 3
store.dispatch(CartActions.addToCartClicked({ item: kaffee })); // Stufe 4
Stufe 2  ~8 Zeilen  · kein Paket      · kein Action-Log
Stufe 3  ~6 Zeilen  · @ngrx/signals   · patchState nur im Store (geschützt)
Stufe 4  ~12 Zeilen · @ngrx/store     · DevTools: "[Product Page] Add To Cart Clicked"
Ergebnis in allen drei: total() bzw. selectTotal = 4.50 nach add(kaffee 4.50)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Angular 22, NgRx 22. Zeilenzahlen grob gezählt aus dem Code oben.

  1. Alle drei liefern dasselbe Ergebnis. Der Unterschied ist Struktur und Nachvollziehbarkeit, nicht die Funktion.
  2. Der Service ist am kürzesten. Aber nichts erzwingt das Muster im Team.
  3. Der SignalStore gibt Struktur und Schutz, bleibt aber direkt (Methode statt Action).
  4. Der globale Store ist indirekt. Dafür kann z. B. ein Analytics-Effect auf addToCartClicked hören, ohne die Komponente zu ändern.

4. Details, die Interviewer fragen

  1. Entscheidungskriterien: Wer teilt den State? Wie lange lebt er? Wie viele Teams? Muss man Änderungen nachvollziehen (Audit, Debug)? Reagieren viele Teile auf dasselbe Ereignis?
  2. SHARI-Prinzip (aus der NgRx-Doku): Store lohnt sich für State, der Shared (geteilt), Hydrated (aus Storage geladen), Available (bei Navigation erhalten), Retrieved (mit Seiteneffekt geholt) oder von Impacted (von anderen Quellen beeinflusst) ist.
  3. Arten von State: UI-State (offen/zu), Formular-State (Reactive Forms), Server-State (Cache von API-Daten), URL-State (Router), App-State (Auth, Settings). Jede Art hat ihren eigenen besten Ort.
  4. Formulare: Formular-State gehört ins Formular-API: Reactive Forms oder Signal Forms (experimentell in Angular 21, stabil seit 22; das Modell ist dort ein signal()). Formular-State nicht in den Store spiegeln.
  5. Zwischenstufe Events im SignalStore: Das Events-Plugin von @ngrx/signals (stabil seit NgRx 21) bringt Ereignisse und Reducer in den SignalStore. Das ist eine Option, wenn ein Feature Entkopplung über Ereignisse braucht, aber kein globaler Store nötig ist.
  6. Service-Muster richtig: privates WritableSignal, öffentlich asReadonly() oder computed, Änderungen nur über Methoden. Sonst ändert jeder den State.
  7. Scope über DI: Service oder SignalStore in providers einer Route oder Komponente gibt Feature-Lebensdauer. providedIn: 'root' gibt App-Lebensdauer.
  8. Mischen ist normal: Globaler Store für Auth und Mandant, SignalStore pro Feature, Signals für UI-Kleinkram. Die Regel muss im Team dokumentiert sein.
  9. Migration von RxJS-Services: Erst BehaviorSubject durch signal ersetzen, Observables nur noch an den Rändern. Bei wachsender Logik in einen SignalStore überführen.
  10. Kosten des globalen Stores: Mehr Dateien, mehr Indirektion, steilere Lernkurve. Nutzen: Konsistenz, DevTools, Entkopplung über Ereignisse.
  11. Kosten eines Services: Wenig Code, aber keine Leitplanken. Bei vielen Entwicklern entstehen verschiedene Muster.

5. Vergleich

  • Komponente: kein Overhead · nicht teilbar ausser über input/output · stirbt mit der Komponente.
  • Service mit Signals: minimal, ohne Bibliothek · keine erzwungene Struktur · kein DevTools-Log.
  • SignalStore: Struktur, Entities, Schutz, Custom Features · wenig Boilerplate · Debugging nur mit Community-Tool.
  • Globaler NgRx Store: Action-Log, Time Travel, Effects, Entkopplung · viel Boilerplate · Indirektion.
  • resource()/httpResource: Server-State mit Lade- und Fehlerstatus · stabil seit Angular 22 · kein Teilen von selbst · für Lesen, nicht für Mutationen.

6. In der Produktion

  1. Alles im globalen Store: Jede Checkbox wird eine Action. Entwickler brauchen 5 Dateien für ein Feature. Lösung: Lokalen UI-State in Komponenten zurückholen.
  2. Services ohne Regeln: Öffentliche WritableSignals, jede Komponente schreibt. Fehler „wer hat das geändert?“ sind nicht auffindbar. Lösung: asReadonly() und Methoden, oder SignalStore mit protectedState.
  3. Doppelter State: Gleiche Daten in Store und Service. Sie laufen auseinander. Lösung: eine Quelle der Wahrheit, der Rest über computed/Selector.
  4. Root-Store für Feature-State: Alter Zustand beim Zurücknavigieren, Speicher wächst. Lösung: Store in die Route- oder Komponenten-Providers.
  5. Server-Cache im Store ohne Invalidierung: Daten veralten. Lösung: bewusstes Neuladen (reload(), Ereignis), oder Server-State nicht global halten.

7. Diagnose: Werkzeuge und Befehle

  • Angular DevTools: Injector-Baum zeigt, wo ein Service oder Store bereitgestellt ist und wie viele Instanzen existieren.
  • Redux DevTools: für den globalen Store, und mit ngrx-toolkit auch für den SignalStore.
  • Suche im Code: grep -r "new BehaviorSubject\|signal(" src/ findet verteilte State-Halter vor einer Migration.
  • ng generate @angular/core:signals: migriert Inputs, Outputs und Queries als ersten Schritt.
  • Architecture Decision Record (ADR): Die Wahl schriftlich festhalten, mit Kriterien. Das ist das Werkzeug gegen Wildwuchs.

8. Senior-Punkte

  1. Kleinste passende Stufe wählen und hochstufen, wenn die Anforderung wächst. Ein Service lässt sich später in einen SignalStore überführen.
  2. Server-State ist kein App-State. Viel „State Management“ ist nur Caching von API-Daten. Das ändert die Werkzeugwahl.
  3. Teamgrösse zählt mehr als App-Grösse. Fünf Teams brauchen Leitplanken, ein Team mit drei Leuten selten.
  4. Ereignisse vs Methoden: Actions entkoppeln (viele Reaktionen auf ein Ereignis). Methoden sind direkt und leichter zu lesen. Die Frage ist: Wie viele Stellen reagieren?
  5. Eine Quelle der Wahrheit pro Datum. Alles andere wird abgeleitet.
  6. Regeln dokumentieren: Eine Seite im Wiki „Welcher State wohin“ spart mehr als jede Bibliothek.

Antwort-Vorlage fürs Interview

„Ich entscheide nach vier Fragen: Wer teilt den Zustand, wie lange lebt er, wie viele Teams arbeiten daran, und muss man Änderungen nachvollziehen?

  1. Lokaler UI-State bleibt als signal in der Komponente.
  2. Einfacher geteilter State kommt in einen Service mit privatem Signal und asReadonly().
  3. Feature-State mit Laden, Listen und Status kommt in einen NgRx SignalStore, meist pro Route bereitgestellt.
  4. App-weiter, kritischer State mit vielen Reaktionen kommt in den globalen NgRx Store, mit Effects und DevTools.

Server-Daten lade ich mit httpResource/rxResource oder im Store mit rxMethod, Formulare bleiben im Formular-API (Reactive Forms oder, ab Angular 22, Signal Forms). Ich starte mit der kleinsten Stufe und stufe hoch, wenn es nötig wird.“

9. Aus dem Projekt

„Produktiv habe ich weder Signals noch NgRx genutzt. Bei CARIAD (Angular 14) lag der Zustand in RxJS-Services pro lazy geladenem Feature-Modul, also Stufe 2 mit Observables. Heute würde ich dort Services mit Signals oder einen SignalStore pro Feature wählen, weil der Zustand nicht über viele Teams geteilt war.“ (Prüfen und durch dein echtes Beispiel ersetzen.)

10. Fallen

  • „Eine grosse App braucht immer NgRx Store.“ → Falsch. Entscheidend sind geteilter State, Teams und Nachvollziehbarkeit, nicht die Grösse.
  • „SignalStore ersetzt den globalen Store komplett.“ → Nein. Für Action-Log und Entkopplung über Ereignisse bleibt der Store stärker.
  • „Ein Service mit öffentlichem WritableSignal ist State Management.“ → Nur halb. Ohne Kapselung ändert jeder den State.
  • „Formular-State gehört in den Store.“ → Meist nicht. Reactive Forms oder Signal Forms verwalten ihn selbst.
  • „Ich muss mich für eine Lösung in der ganzen App entscheiden.“ → Nein. Mischen ist normal, wenn die Regeln klar sind.

11. Fragen

Welche Optionen für State Management gibt es in Angular 22?

Signals in der Komponente, Service mit Signals, NgRx SignalStore, globaler NgRx Store. Dazu resource-APIs für Server-State.

Nach welchen Kriterien entscheiden Sie?

Wer teilt den State, wie lange lebt er, wie viele Teams, ob Änderungen nachvollziehbar sein müssen und wie viele Stellen auf Ereignisse reagieren.

Wann reicht ein Signal in der Komponente?

Wenn nur die Komponente und ihre Kinder den Zustand brauchen, z. B. offen/zu oder ein aktiver Tab.

Wie baut man einen guten Service mit Signals?

Privates WritableSignal, öffentlich asReadonly() und computed, Änderungen nur über Methoden.

Wann SignalStore statt Service?

Wenn Feature-Logik wächst: Listen, Entities, Lade- und Fehlerstatus, wiederverwendbare Bausteine und Schutz vor Schreiben von aussen.

Wann globaler NgRx Store?

Bei App-weitem, kritischem State, vielen Teams und dem Bedarf an Action-Log, Time Travel und Entkopplung über Ereignisse.

Was ist das SHARI-Prinzip?

Store lohnt sich für State, der Shared, Hydrated, Available, Retrieved oder von Impacted (anderen Quellen beeinflusst) ist.

Was ist Server-State und warum ist er besonders?

Ein Cache von API-Daten. Er braucht Laden, Fehler und Invalidierung, nicht unbedingt einen globalen Store. resource-APIs helfen.

Wo gehört Formular-State hin?

In Reactive Forms oder, ab Angular 22 stabil, in Signal Forms. Nur das abgeschickte Ergebnis geht in Store oder Service.

Wo gehören Filter und Seitenzahl hin?

Oft in die URL, damit man sie teilen und bookmarken kann. Mit withComponentInputBinding kommen sie als Inputs.

Wie steuern Sie die Lebensdauer von State?

Über DI: providedIn: 'root' für App-Lebensdauer, Providers einer Route oder Komponente für Feature-Lebensdauer.

Darf man Lösungen mischen?

Ja. Üblich: globaler Store für Auth, SignalStore pro Feature, Signals lokal. Die Regel muss im Team festgehalten sein.

Was kostet der globale Store?

Mehr Dateien, Indirektion, Lernkurve. Er bringt Konsistenz, DevTools und Entkopplung.

Methoden oder Actions?

Methoden sind direkt und lesbar. Actions lohnen sich, wenn viele Stellen auf dasselbe Ereignis reagieren.

Wie migrieren Sie eine Angular-14-App mit RxJS-Services?

Schrittweise: Signal-Migrationen laufen lassen, BehaviorSubject durch Signals ersetzen, in Komponenten toSignal, wachsende Services in SignalStores überführen.

Warum nicht immer die mächtigste Lösung?

Jede Stufe kostet Code und Lernzeit. Die kleinste passende Stufe hält das System einfach, hochstufen geht später.

Wie verhindern Sie Wildwuchs im Team?

Mit einer dokumentierten Regel (ADR), Code-Reviews und gemeinsamen Custom Features oder Vorlagen.

Szenario: Ein Team will für eine kleine Admin-App mit drei Seiten NgRx Store einführen. Was raten Sie?

Erst prüfen, was geteilt wird. Meist reichen Services mit Signals oder ein SignalStore pro Seite. Store erst, wenn Teams, Audit oder viele Reaktionen dazukommen.

Szenario: In einer grossen App weiss niemand, wer den Mandanten-Wechsel auslöst und wer reagiert. Was tun?

Mandant in den globalen Store, Wechsel als Action mit Quelle. Abhängige Features reagieren per Effect oder Selector. DevTools zeigen den Ablauf.

Szenario: Sie sollen im Interview erklären, welche Lösung Sie für ein neues Feature wählen. Wie antworten Sie?

Mit den vier Fragen (wer teilt, wie lange, wie viele Teams, Nachvollziehbarkeit), dann die kleinste passende Stufe nennen und sagen, wann Sie hochstufen würden.
