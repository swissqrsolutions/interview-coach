input(), output(), model(), viewChild()

Angular Signals + NgRx · Tier 1 · Quellen: angular.dev Guides „Inputs“, „Outputs“, „Model inputs“ (Two-way binding), „Queries“ (v20), angular.dev API input, output, model, viewChild, contentChild, outputFromObservable, Migrations-Guides „Signal inputs“, „Outputs“, „Signal queries“

Kern: Signal-basierte Komponenten-APIs ersetzen die Dekoratoren @Input, @Output, @ViewChild und @ContentChild durch Funktionen. input() und die Queries liefern read-only Signals, output() liefert einen Event-Emitter ohne RxJS, model() ein schreibbares Signal für Two-way Binding. Damit sind Inputs direkt in computed nutzbar, und ngOnChanges wird meist überflüssig.

1. Wo sitzen input, output und model?

  1. input(): Der Parent gibt einen Wert nach unten. Das Child bekommt ein InputSignal, das es nur lesen kann. Beispiel: product = input.required<Product>().
  2. output(): Das Child meldet ein Ereignis nach oben. Es ruft emit(). Beispiel: added = output<Product>().
  3. model(): Wert nach unten und Änderung nach oben. Angular erzeugt dafür automatisch das Output qtyChange.
  4. viewChild()/contentChild(): Queries auf Elemente im eigenen Template bzw. im projizierten Inhalt. Ergebnis ist ein Signal.

2. Die Reise eines Input-Werts (die Geschichte zum Merken)

  1. Parent ändert seinen Zustand. Er setzt ein Signal, das im Template an [product] gebunden ist.
  2. Binding. In der Change Detection liest Angular den neuen Wert der Bindung.
  3. transform. Gibt es eine Transform-Funktion, wandelt sie den Rohwert um. Beispiel: "" aus <app-x disabled> wird true.
  4. InputSignal. Angular setzt den Wert intern. Das Child selbst kann kein set() aufrufen.
  5. computed. Alles, was vom Input abhängt, ist jetzt „dirty“ und rechnet beim nächsten Lesen neu. Kein ngOnChanges nötig.
  6. Child-View. Das Template liest die Signals und rendert neu, auch mit OnPush.
  7. Event nach oben. Klickt der Nutzer, ruft das Child added.emit(p). Der Parent-Handler läuft synchron.

3. Beispiel: alle vier APIs in einer Komponente

import { Component, input, output, model, computed, viewChild,
         ElementRef, booleanAttribute, numberAttribute, effect } from '@angular/core';

@Component({
  selector: 'app-product-card',
  template: `
    <h3>{{ product().name }} – {{ priceLabel() }}</h3>
    <input #qtyBox type="number" [value]="qty()" (input)="qty.set(+qtyBox.value)">
    <button [disabled]="disabled()" (click)="added.emit(product())">Add</button>`,
})
export class ProductCard {
  product  = input.required<Product>();
  discount = input(0, { transform: numberAttribute });
  disabled = input(false, { transform: booleanAttribute });
  qty      = model(1);                       // creates output "qtyChange"
  added    = output<Product>();
  qtyBox   = viewChild.required<ElementRef<HTMLInputElement>>('qtyBox');

  priceLabel = computed(() =>
    (this.product().price * (100 - this.discount()) / 100).toFixed(2) + ' CHF');

  constructor() {
    effect(() => console.log('qty is', this.qty()));
  }
}

// Parent template
// <app-product-card [product]="p" discount="10" disabled
//                   [(qty)]="cartQty" (added)="log($event)" />
// Parent: cartQty = signal(2); p = { name: 'Kaffee', price: 20 }
Kaffee – 18.00 CHF          // discount "10" → 10, Button disabled
qty is 2                     // Parent-Wert überschreibt Default 1
// Nutzer tippt 5 ins Feld:
qty is 5                     // und im Parent: cartQty() === 5

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). Angular 20.

  1. discount="10" ist ein statischer String. numberAttribute macht daraus die Zahl 10.
  2. disabled ohne Wert ist "". booleanAttribute macht daraus true.
  3. [(qty)]="cartQty" bindet ein Signal des Parents in beide Richtungen. qty.set(5) im Child aktualisiert cartQty über das Event qtyChange.
  4. product ist required. Fehlt die Bindung, meldet der Compiler einen Fehler zur Build-Zeit.
  5. qtyBox() liefert das Element. Mit .required ist der Typ nie undefined, aber es darf erst nach der View-Erstellung gelesen werden.

4. Details, die Interviewer fragen

  1. input(default): Optionaler Input mit Default. Typ InputSignal<T>. Ohne Default: input<string>() hat Typ string | undefined.
  2. input.required(): Pflicht-Input. Kein Default. Liest man ihn zu früh (z. B. im Konstruktor), wirft Angular NG0950.
  3. transform: Reine Funktion von Rohwert zu Zielwert. Eingebaut: booleanAttribute, numberAttribute. Sie darf keine Seiteneffekte haben.
  4. alias: input(0, { alias: 'max' }) bindet im Template als [max]. Sparsam nutzen, es verwirrt beim Suchen.
  5. Inputs sind read-only: Kein set() im Child. Der Wert gehört dem Parent. Will das Child ihn ändern, ist es ein model() oder ein lokales linkedSignal.
  6. output(): Liefert OutputEmitterRef<T> mit emit(). Kein RxJS, kein EventEmitter. Abo im Code mit ref.subscribe(), das automatisch beim Zerstören endet.
  7. outputFromObservable(obs$): Macht aus einem Observable ein Output. outputToObservable(ref) macht das Gegenteil. Beide aus @angular/core/rxjs-interop.
  8. model(): Schreibbares Signal. Erzeugt Input qty und Output qtyChange. model.required() gibt es auch.
  9. [(x)] mit Signal oder Wert: Der Parent kann ein WritableSignal binden (ohne ()!) oder ein normales Feld.
  10. viewChild(locator): Locator ist ein Template-Ref-Name als String oder ein Typ. read-Option wählt, was geliefert wird, z. B. { read: ElementRef }.
  11. viewChildren / contentChildren: Liefern Signal<readonly T[]>. Kein QueryList und kein changes-Observable mehr nötig.
  12. contentChild: Sucht im projizierten Inhalt (<ng-content>). Option descendants sucht auch tiefer.
  13. Kein static mehr: Signal-Queries haben keine static-Option. Das Signal aktualisiert sich selbst, wenn das Element erscheint (z. B. in @if).
  14. ngOnChanges ersetzen: Ableitungen mit computed, Reaktion nach aussen mit effect. Ein lokal überschreibbarer Wert, der vom Input kommt: linkedSignal(() => this.product().price).
  15. Stabilität: input, output, model und Signal-Queries sind seit Angular 19 stabil.

5. Vergleich

  • @Input() vs input(): Dekorator setzt ein normales Feld, Reaktion nur über ngOnChanges oder Setter. input() ist ein Signal, direkt in computed nutzbar, typensicher mit required.
  • @Output() EventEmitter vs output(): EventEmitter ist ein RxJS-Subject. output() ist leichter, ohne RxJS-Abhängigkeit, Abo endet automatisch.
  • @Input + @Output xChange vs model(): Früher zwei Felder von Hand. model() ist ein Feld, das beides erzeugt.
  • @ViewChild vs viewChild(): Dekorator setzt das Feld erst in ngAfterViewInit. Das Signal ist reaktiv und in computed/effect nutzbar.
  • model() vs linkedSignal vom Input: model meldet Änderungen an den Parent. linkedSignal ändert nur lokal, der Parent erfährt nichts.

6. In der Produktion

  1. NG0950 bei required Input: Ein Feld-Initialisierer oder Konstruktor liest product(). Lösung: in computed, effect oder ab ngOnInit lesen.
  2. Code ruft this.value = x auf einem migrierten Input: Kompiliert nicht mehr. Lösung: model(), wenn der Parent es wissen soll, sonst linkedSignal.
  3. Tests setzen Inputs direkt: component.product = p geht nicht mehr. Lösung: fixture.componentRef.setInput('product', p).
  4. viewChild im Konstruktor gelesen: Element existiert noch nicht. Lösung: afterNextRender, effect oder afterRenderEffect.
  5. [(x)]="sig()" statt [(x)]="sig": Mit Klammern bindet man den Wert, nicht das Signal. Two-way geht verloren oder der Compiler meldet einen Fehler.
  6. Teure transform: Sie läuft bei jeder neuen Bindung. Lösung: billig halten, Logik in computed.

7. Diagnose: Werkzeuge und Befehle

  • ng generate @angular/core:signal-input-migration: migriert @Input zu input(). Felder, die beschrieben werden, lässt es aus und markiert sie.
  • ng generate @angular/core:output-migration: migriert @Output zu output().
  • ng generate @angular/core:signal-queries-migration: migriert @ViewChild, @ContentChild usw.
  • ng generate @angular/core:signals: alle drei Migrationen zusammen. Option --best-effort-mode migriert aggressiver.
  • Angular Language Service in der IDE: zeigt fehlende required Inputs und falsche Typen direkt im Template.
  • Angular DevTools: zeigt Input-Werte und Signal-Zustand je Komponente.

8. Senior-Punkte

  1. Unidirektionaler Fluss bleibt Standard. input + output zuerst. model() nur für echte Formular-artige Controls wie Slider oder Toggle.
  2. required Inputs machen Verträge sichtbar. Fehler kommen zur Build-Zeit statt als undefined zur Laufzeit.
  3. Presentational Components werden einfacher: nur Inputs, computed, Outputs. Kein Lifecycle-Hook, kein Subscribe.
  4. Migration schrittweise mit den Schematics. Erst Leaf-Komponenten, dann Container. Tests auf setInput umstellen.
  5. Queries als Signals beseitigen die ExpressionChangedAfterItHasBeenChecked-Klassiker rund um ngAfterViewInit.

10. Fallen

  • „Ich setze ein input() im Child mit set().“ → Falsch. Inputs sind read-only. Dafür gibt es model() oder linkedSignal.
  • „output() ist ein Observable.“ → Nein. Es ist ein OutputEmitterRef. Für RxJS: outputToObservable.
  • „Ohne ngOnChanges kann ich nicht auf Input-Änderungen reagieren.“ → Doch: mit computed oder effect.
  • „[(qty)]="cartQty()" ist Two-way.“ → Nein. Das Signal selbst ohne () binden.
  • „viewChild hat noch static: true.“ → Nein. Signal-Queries aktualisieren sich selbst.

11. Fragen

Was ist ein Signal-Input?

Ein Input, der mit input() deklariert wird und ein read-only InputSignal liefert. Man liest ihn mit value().

Welche Vorteile hat input() gegenüber @Input?

Reaktiv in computed/effect, kein ngOnChanges, Pflicht-Inputs zur Build-Zeit geprüft, bessere Typen.

Was macht input.required()?

Der Parent muss den Input binden, sonst Compiler-Fehler. Liest man ihn vor dem ersten Setzen, gibt es NG0950.

Was ist eine Input-Transform?

Eine reine Funktion, die den gebundenen Wert umwandelt. Beispiel: booleanAttribute macht aus disabled ohne Wert true.

Kann ein Child einen Input ändern?

Nein. Er gehört dem Parent. Für Rückmeldung model(), für lokale Änderung linkedSignal.

Was liefert output()?

Einen OutputEmitterRef mit emit(). Er braucht kein RxJS und räumt Abos automatisch auf.

Wie verbinde ich output() mit RxJS?

outputFromObservable(obs$) macht aus einem Observable ein Output. outputToObservable(out) macht aus einem Output ein Observable.

Was ist model()?

Ein schreibbares Signal-Input für Two-way Binding. Angular erzeugt dazu das Output <name>Change.

Wie bindet der Parent ein model()?

Mit [(qty)]="cartQty", wobei cartQty ein WritableSignal (ohne Klammern) oder ein normales Feld ist.

Wann model(), wann input + output?

model für Controls, deren Wert der Nutzer direkt ändert, z. B. Slider. Sonst input + output, damit der Datenfluss klar unidirektional bleibt.

Was liefert viewChild()?

Ein Signal auf das gefundene Element, Komponente oder Direktive. viewChild.required entfernt undefined aus dem Typ.

Unterschied viewChild und contentChild?

viewChild sucht im eigenen Template. contentChild sucht im Inhalt, den der Parent per ng-content hineinprojiziert.

Was ersetzt QueryList.changes?

viewChildren() liefert ein Signal mit einem Array. Man reagiert mit computed oder effect.

Wie ersetze ich ngOnChanges?

Ableitungen mit computed, Seiteneffekte mit effect. Für Vergleich mit dem alten Wert: linkedSignal mit previous.

Wie setze ich Inputs im Test?

Mit fixture.componentRef.setInput('name', wert), danach fixture.detectChanges() oder await fixture.whenStable().

Wie migriere ich eine grosse App?

Mit ng generate @angular/core:signals oder den einzelnen Migrationen. Danach Tests und beschriebene Inputs von Hand nacharbeiten.

Seit wann sind diese APIs stabil?

input, output, model und Signal-Queries sind seit Angular 19 stabil.

Szenario: Nach der Migration wirft eine Komponente NG0950. Was ist passiert?

Ein required Input wird zu früh gelesen, z. B. im Konstruktor. Das Lesen in computed, effect oder ngOnInit verschieben.

Szenario: Ein Datepicker soll den Wert ändern und der Parent soll es wissen. Welche API?

model(). Der Parent bindet mit [(date)]="selected". Bei grossen Formularen eher Reactive Forms mit ControlValueAccessor.

Szenario: Eine Liste im Child soll filtern, der Filter startet mit dem Input-Wert, darf aber lokal geändert werden. Lösung?

filter = linkedSignal(() => this.initialFilter()). Lokal schreibbar, setzt sich zurück, wenn der Parent einen neuen Input liefert.
