NgRx SignalStore

Angular Signals + NgRx · Tier 1 · Quellen: ngrx.io Guide „@ngrx/signals“ (SignalStore, SignalState, Lifecycle Hooks, Custom Store Features, Entity Management, RxJS Integration, Testing, Private Store Members, State Tracking), NgRx v20 API

Kern: Der SignalStore aus @ngrx/signals ist ein Store, der Zustand als Signals hält und aus kleinen Features zusammengesetzt wird: withState, withComputed, withMethods, withHooks. Er ändert State direkt über Methoden mit patchState, ohne Actions und Reducer. Er löst das Problem „strukturierter State mit wenig Boilerplate“, lokal pro Komponente oder global.

1. Wo sitzt der SignalStore?

  1. signalStore(): erzeugt eine injizierbare Klasse. Mit { providedIn: 'root' } global, sonst in providers einer Komponente (lokal).
  2. withState: definiert den Zustand. Jedes Feld wird ein Signal. Beispiel: store.filter().
  3. withEntities: fügt normalisierte Collections hinzu. Beispiel: store.entities().
  4. withComputed: abgeleitete Signals. Beispiel: visible = computed(...).
  5. withMethods: die einzige Stelle, die State ändert. Beispiel: setFilter(f) ruft patchState.
  6. withHooks: Code beim Erstellen und Zerstören des Stores. Beispiel: onInit startet das Laden.

Die Reihenfolge zählt: Jedes Feature sieht nur, was davor definiert ist.

2. Die Reise eines Filters (die Geschichte zum Merken)

  1. Eingabe. Die Komponente ruft store.setQuery('ka'). Sie kennt keine Actions.
  2. Methode. Die Methode ruft patchState(store, { query }). Nur Methoden im Store dürfen das (protectedState).
  3. State-Signal. query() hat einen neuen Wert. Andere Felder behalten ihre Referenz.
  4. Reaktion. visible() ist dirty. Und loadByQuery, ein rxMethod, bekam das Signal query beim Start übergeben. Es reagiert mit debounceTime und switchMap.
  5. Ergebnis. Die Antwort landet mit patchState(store, setAllEntities(todos)) im Store.
  6. Anzeige. Das Template liest store.visible(). Signals sorgen für gezieltes Rendern.

3. Beispiel: TodoStore mit Entities, rxMethod und Hooks

import { computed, inject } from '@angular/core';
import { signalStore, withState, withComputed, withMethods, withHooks, patchState } from '@ngrx/signals';
import { withEntities, setAllEntities, updateEntity } from '@ngrx/signals/entities';
import { rxMethod } from '@ngrx/signals/rxjs-interop';
import { tapResponse } from '@ngrx/operators';
import { debounceTime, distinctUntilChanged, pipe, switchMap, tap } from 'rxjs';

type Todo = { id: number; title: string; done: boolean };

export const TodoStore = signalStore(
  { providedIn: 'root' },
  withEntities<Todo>(),
  withState({ query: '', loading: false, error: null as string | null }),
  withComputed(({ entities }) => ({
    openCount: computed(() => entities().filter(t => !t.done).length),
  })),
  withMethods((store, api = inject(TodoApi)) => ({
    setQuery(query: string) { patchState(store, { query }); },
    toggle(id: number) {
      patchState(store, updateEntity({ id, changes: t => ({ done: !t.done }) }));
    },
    loadByQuery: rxMethod<string>(pipe(
      debounceTime(300), distinctUntilChanged(),
      tap(() => patchState(store, { loading: true })),
      switchMap(q => api.search(q).pipe(
        tapResponse({
          next: todos => patchState(store, setAllEntities(todos), { loading: false }),
          error: (e: Error) => patchState(store, { error: e.message, loading: false }),
        }))))),
  })),
  withHooks({
    onInit(store) { store.loadByQuery(store.query); },   // pass the SIGNAL, not a value
    onDestroy() { console.log('store destroyed'); },
  }),
);

// component
store = inject(TodoStore);
// template: {{ store.openCount() }} offen · @for (t of store.entities(); track t.id) …
// API liefert [{id:1,title:'Kaffee',done:false},{id:2,title:'Kakao',done:true}]
store.ids()        → [1, 2]
store.entityMap()  → { 1: {…}, 2: {…} }
store.openCount()  → 1
store.toggle(1);  store.openCount() → 0
store.setQuery('ka')  → nach 300 ms 1 Request: GET /api/todos?q=ka
patchState(store, { query: 'x' })  // ausserhalb des Stores → TypeScript-Fehler

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). NgRx 20, Angular 20.

  1. withEntities fügt ids, entityMap und das abgeleitete entities hinzu.
  2. updateEntity ändert nur ein Entity. Die anderen behalten ihre Referenz.
  3. rxMethod nimmt einen statischen Wert, ein Signal oder ein Observable. Mit einem Signal reagiert es auf jede Änderung.
  4. tapResponse fängt Fehler im inneren Strom. Der rxMethod-Strom lebt weiter.
  5. Seit NgRx 18 ist der State standardmässig geschützt: patchState geht nur im Store. Abschalten mit protectedState: false.

4. Details, die Interviewer fragen

  1. patchState(store, ...updaters): Nimmt Teil-Objekte oder Funktionen s => ({ ... }). Mehrere Updater in einem Aufruf werden zusammen angewendet.
  2. DeepSignal: Ein verschachteltes Objekt im State wird ein Signal mit Unter-Signals. Beispiel: store.user.address.city().
  3. Immutabilität: Wie überall bei Signals: neue Objekte, keine Mutation. Ab NgRx 19 wird State im Dev-Modus eingefroren, Mutation wirft einen Fehler.
  4. Private Members: Namen mit _-Präfix sind ausserhalb des Stores nicht sichtbar. Beispiel: _cache.
  5. withProps (seit NgRx 19): Fügt beliebige Properties hinzu, z. B. injizierte Services oder Observables. Andere Features können sie nutzen.
  6. withLinkedState (NgRx 20): State, der von anderen Signals abgeleitet ist, aber schreibbar bleibt. Wie linkedSignal.
  7. rxMethod: Für RxJS-Logik. Eingabe: Wert, Signal oder Observable. Das Abo endet mit dem Store oder dem Injector des Aufrufers.
  8. signalMethod (seit NgRx 19): Wie rxMethod, aber ohne RxJS, für einfache Seiteneffekte bei Signal-Änderung.
  9. withHooks: onInit läuft im Injection Context beim Erstellen. Dort kann man inject(), effect() oder rxMethod starten. onDestroy beim Zerstören.
  10. Scope: providedIn: 'root' = ein Singleton. Ohne das: in providers: [TodoStore] einer Komponente, dann pro Komponenten-Instanz ein Store, zerstört mit ihr.
  11. Entities-Updater: addEntity, setEntity, setAllEntities, updateEntity, updateAllEntities, removeEntity, upsertEntity (NgRx 20). Eigener ID-Schlüssel mit selectId.
  12. Benannte Collections: withEntities({ entity: type<Todo>(), collection: 'todo' }) gibt todoEntities, todoIds. So hat ein Store mehrere Listen.
  13. Custom Features: signalStoreFeature(withState(...), withMethods(...)) bündelt wiederverwendbare Bausteine, z. B. withRequestStatus().
  14. signalState: Leichte Variante ohne Store-Klasse. Ein Objekt-Signal mit DeepSignals und patchState, z. B. für lokalen Komponenten-State.
  15. Hilfsfunktionen: getState(store) liefert einen Snapshot. watchState(store, fn) reagiert synchron auf jede Änderung, z. B. für Logging.
  16. Events-Plugin (NgRx 20, experimentell): @ngrx/signals/events bringt Event-basierte Architektur mit withReducer und withEffects in den SignalStore.

5. Vergleich

  • SignalStore vs globaler NgRx Store: SignalStore ändert State direkt über Methoden. Store über Actions → Reducer. Store bietet Redux DevTools und Time Travel eingebaut, SignalStore nicht.
  • SignalStore vs Service mit Signals: Service ist freie Form. SignalStore gibt Struktur (State, Computed, Methods, Hooks), Entities, Schutz vor Schreiben von aussen.
  • SignalStore vs ComponentStore: ComponentStore ist Observable-basiert und der ältere lokale Store. SignalStore ist sein Signal-Nachfolger.
  • rxMethod vs Effect: Gleiches RxJS-Muster. rxMethod wird direkt aufgerufen. Ein Effect reagiert indirekt auf Actions.
  • signalState vs signalStore: signalState ist nur State. signalStore ist ein vollständiger injizierbarer Service mit Features.

6. In der Produktion

  1. Globaler Store für lokalen Zustand: providedIn: 'root' für einen Wizard. Alter Zustand bleibt beim nächsten Öffnen. Lösung: Store in den providers der Wizard-Komponente.
  2. rxMethod mit Wert statt Signal: store.loadByQuery(store.query()) lädt nur einmal. Lösung: das Signal selbst übergeben: store.loadByQuery(store.query).
  3. Fehler ohne tapResponse: Ein HTTP-Fehler beendet den rxMethod-Strom. Danach lädt nichts mehr. Lösung: Fehler im inneren Strom mit tapResponse oder catchError.
  4. Kein Debugging-Werkzeug: Keine eingebauten DevTools. Lösung: withDevtools('todos') aus der Community-Bibliothek @angular-architects/ngrx-toolkit, oder watchState fürs Logging.
  5. Riesiger Store: 40 Methoden in einem Store. Lösung: in Custom Features oder mehrere Stores aufteilen.
  6. Store-Abhängigkeiten im Kreis: Store A injiziert B, B injiziert A. Lösung: gemeinsamen State in einen dritten Store, oder Event-basiert entkoppeln.

7. Diagnose: Werkzeuge und Befehle

  • ng add @ngrx/signals@latest: Installation.
  • getState(store) in der Konsole oder im Test: aktueller Snapshot.
  • watchState(store, s => console.log(s)): jede Änderung loggen.
  • Angular DevTools: zeigt Signals des Stores bei der injizierenden Komponente.
  • ngrx-toolkit withDevtools (Community): verbindet den SignalStore mit den Redux DevTools.
  • Tests: Store im TestBed bereitstellen, Methoden aufrufen, Signals prüfen. Für isolierte Tests unprotected(store) aus @ngrx/signals/testing, um State direkt zu setzen.

8. Senior-Punkte

  1. Weniger Zeremonie, weniger Leitplanken. SignalStore ist schneller geschrieben. Dafür fehlt die erzwungene Nachvollziehbarkeit von Actions.
  2. Scope ist die wichtigste Entscheidung: root für geteilten App-Zustand, Komponente für Feature-Zustand mit Lebensdauer.
  3. Custom Features sind der Hebel für Teams: withRequestStatus, withPagination einmal bauen, überall nutzen.
  4. Koexistenz: Globaler Store für Kernzustand (Auth, Settings), SignalStore für Features. Beides passt in eine App.
  5. RxJS nur wo nötig: rxMethod für Debounce/Abbruch, sonst normale Methoden mit async/await oder signalMethod.
  6. Experimentelle Teile (Events-Plugin) bewusst bewerten, bevor ein Team sie flächig einsetzt.

10. Fallen

  • „SignalStore braucht Actions und Reducer.“ → Falsch. State ändert sich direkt über Methoden mit patchState.
  • „Ich kann von der Komponente aus patchState(store, …) aufrufen.“ → Nicht standardmässig. State ist geschützt, nur Store-Methoden dürfen ändern.
  • „SignalStore ist immer global.“ → Nein. Ohne providedIn: 'root' lebt er in den Providers einer Komponente.
  • „rxMethod mit store.query() reagiert auf Änderungen.“ → Nein. Das ist ein einzelner Wert. Das Signal ohne Klammern übergeben.
  • „SignalStore hat Redux DevTools eingebaut.“ → Nein. Dafür braucht es eine Community-Erweiterung.

11. Fragen

Was ist der NgRx SignalStore?

Ein Store aus @ngrx/signals, der Zustand als Signals hält und aus Features wie withState und withMethods gebaut wird.

Was macht withState?

Es definiert den Anfangszustand. Jedes Feld wird als Signal am Store verfügbar, verschachtelte Objekte als DeepSignal.

Was macht withComputed?

Es fügt abgeleitete Signals hinzu, die aus State berechnet werden. Sie sind lazy und memoized wie computed.

Was macht withMethods?

Es fügt Methoden hinzu, die State mit patchState ändern oder Seiteneffekte starten. Hier ist inject() möglich.

Was ist patchState?

Die Funktion, die State ändert. Sie nimmt Teil-Objekte oder Updater-Funktionen und erzeugt neuen, unveränderlichen State.

Was ist protectedState?

Seit NgRx 18 Standard: patchState geht nur innerhalb des Stores. Mit protectedState: false abschaltbar.

Was ist rxMethod?

Eine Methode mit RxJS-Pipeline. Sie nimmt einen Wert, ein Signal oder ein Observable und reagiert auf jede neue Eingabe.

Was macht withHooks?

Es definiert onInit und onDestroy. onInit läuft im Injection Context, z. B. um Laden zu starten.

Was bringt withEntities?

Normalisierte Collections mit ids, entityMap, entities und Updatern wie addEntity und updateEntity.

Wie macht man einen SignalStore lokal?

Ohne providedIn: 'root' und in providers: [Store] der Komponente. Er lebt und stirbt mit ihr.

Was ist ein Custom Store Feature?

Ein wiederverwendbarer Baustein mit signalStoreFeature, z. B. withRequestStatus, der State und Methoden bündelt.

Was ist signalState?

Ein leichtes State-Objekt als Signal mit DeepSignals und patchState, ohne Store-Klasse. Gut für lokalen Komponenten-State.

Was ist ein DeepSignal?

Ein Signal für ein verschachteltes Objekt, das Unter-Signals pro Feld bietet. Beispiel: store.user.name().

Wie verstecke ich interne Members?

Mit _-Präfix im Namen. Diese State-Felder, Computed und Methoden sind ausserhalb nicht sichtbar.

SignalStore oder globaler Store?

SignalStore für Feature- oder lokalen State mit wenig Boilerplate. Globaler Store, wenn Action-Log, Time Travel und strenge Regeln für viele Teams wichtig sind.

Wie testet man einen SignalStore?

Im TestBed bereitstellen, API-Service mocken, Methoden aufrufen, Signals prüfen. Für State-Setup unprotected(store).

Wie debuggt man einen SignalStore?

Mit getState, watchState, Angular DevTools oder withDevtools aus dem Community-ngrx-toolkit.

Szenario: Ein Wizard zeigt beim zweiten Öffnen die alten Eingaben. Warum?

Der Store ist mit providedIn: 'root' ein Singleton. Ihn in die Providers der Wizard-Komponente legen, dann wird er neu erstellt.

Szenario: Eine Suche im SignalStore lädt nur beim Start, danach nie wieder. Was ist falsch?

rxMethod bekam store.query(), also einen Wert. Das Signal store.query übergeben, dann reagiert es auf jede Änderung.

Szenario: Nach einem 500er lädt die Liste im SignalStore nie wieder. Lösung?

Der Fehler hat den rxMethod-Strom beendet. Im inneren switchMap mit tapResponse fangen und error in den State schreiben.
