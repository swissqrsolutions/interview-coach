NgRx Effects

Kern: Ein Effect ist ein Observable-Strom, der auf Actions hört, einen Seiteneffekt ausführt (HTTP, Router, Storage) und meist neue Actions zurückgibt. Effects halten Komponenten und Reducer frei von Seiteneffekten, und die wichtigsten Entscheidungen sind der Flattening-Operator und das Error Handling im inneren Observable. Stand ist NgRx 22 mit Angular 22.

Antwort-Muster

Frage: Was ist ein NgRx Effect und wie behandelt man Fehler richtig?

  1. Mechanismus: Ein Effect hört mit ofType auf Actions, startet mit einem Flattening-Operator einen inneren Strom und gibt eine neue Action zurück.
  2. Zahl: Ein Fehler im äusseren Strom beendet den Effect. NgRx resubscribed zwar bis zu 10 Mal, danach ist der Effect tot.
  3. Trade-off: switchMap bricht ab und passt zum Lesen. concatMap hält die Reihenfolge und passt zum Schreiben. exhaustMap ignoriert neue Auslöser.
  4. Produktion: Darum steht catchError im inneren Strom und liefert eine Failure-Action. Beim Schreiben sichere ich zusätzlich den Server mit einem Idempotenz-Key ab.

1. Die Reise eines Ladevorgangs

  1. Action. Die Seite dispatcht opened. Der Reducer setzt loading: true.
  2. Filter. Der Effect sieht die Action im Actions-Strom. ofType lässt sie durch.
  3. Innerer Strom. switchMap startet den HTTP-Call als inneres Observable. Kommt vorher ein zweites opened, bricht es den ersten Call ab.
  4. Antwort. Der Server antwortet mit Daten oder einem Fehler.
  5. Erfolg oder Fehler. map macht aus Daten loadSuccess. catchError im inneren Strom macht aus dem Fehler loadFailure.
  6. Zurück in den Store. NgRx dispatcht die neue Action. Der Reducer setzt loading: false. Der Effect wartet auf das nächste opened.

2. Aufbau

  1. Actions$: der Strom aller Actions, nachdem die Reducer sie verarbeitet haben. Beispiel: inject(Actions).
  2. ofType: filtert den Strom auf bestimmte Actions. Beispiel: ofType(ProductsPageActions.opened).
  3. Flattening-Operator: startet den inneren Seiteneffekt pro Action. Beispiel: switchMap(() => api.load()).
  4. Ergebnis: eine neue Action, die der Store automatisch dispatcht. Beispiel: loadSuccess({ products }).
  5. EffectsRunner: NgRx abonniert alle registrierten Effects beim Start (provideEffects).

3. Details, die Interviewer fragen

  1. switchMap: Es bricht den vorherigen inneren Strom ab. Es passt zum Lesen und zur Suche, wo nur die neueste Antwort zählt. Man nutzt es nie zum Schreiben, weil ein abgebrochener Request trotzdem am Server ankommen kann.
  2. concatMap: Es wartet, bis der vorherige fertig ist, dann kommt der nächste. Es passt zum Schreiben in Reihenfolge, z. B. Speichern derselben Entität.
  3. mergeMap: Es startet alles parallel. Die Reihenfolge der Antworten ist offen. Es passt zu unabhängigen Schreibvorgängen, z. B. mehrere verschiedene Einträge löschen.
  4. exhaustMap: Es ignoriert neue Actions, solange einer läuft. Es passt zu Login oder zum Doppelklick auf „Bezahlen“.
  5. catchError-Position: Im äusseren Strom beendet ein Fehler den ganzen Effect. Der Standard-Error-Handler von NgRx resubscribed dann zwar bis zu 10 Mal. Man kann das mit useEffectsErrorHandler: false abschalten. Es ist aber ein Notnagel und kein Design.
  6. catchError gibt ein Observable zurück: Man gibt of(failureAction) zurück und nicht die Action direkt.
  7. tapResponse aus @ngrx/operators: Es verbindet tap und catchError sicher. Es ist vor allem in ComponentStore und SignalStore-rxMethod üblich. Seit NgRx 22 gibt es nur noch die Objekt-Form tapResponse({ next, error, finalize }). Die alte Form mit Callbacks hintereinander ist seit NgRx 20 deprecated und jetzt entfernt.
  8. State im Effect lesen: Man nutzt concatLatestFrom(() => store.select(selectQuery)) aus @ngrx/operators. Früher kam es aus @ngrx/effects. Dort ist es seit NgRx 17.2 deprecated und in NgRx 22 nicht mehr exportiert. Es liest den Selector erst, wenn die Action kommt. Das ist lazy, anders als bei withLatestFrom.
  9. dispatch: false: Das ist für Effects ohne Ergebnis-Action, z. B. Navigation, Logging, localStorage und Snackbar.
  10. Klassenbasierte Effects: Man schreibt @Injectable() class ProductsEffects { load$ = createEffect(() => ...) }. Funktionale Effects sind die neuere, kürzere Form. Beides registriert man mit provideEffects.
  11. Lifecycle: ROOT_EFFECTS_INIT wird dispatcht, wenn Root-Effects bereit sind. Effects in einer Lazy Route starten erst beim Laden der Route.
  12. Lifecycle-Hooks: Mit OnInitEffects dispatcht man eine Action beim Start. Mit OnRunEffects lässt man Effects nur in einem Zeitfenster laufen, z. B. nach dem Login.
  13. Nicht-Action-Quellen: Effects können auch auf interval, WebSocket oder Router-Events hören. Sie hören nicht nur auf Actions.
  14. Testing: Man nutzt provideMockActions(() => actions$) mit TestBed. Funktional übergibt man die Parameter direkt. Für Timing nimmt man Marble-Tests mit TestScheduler.
  15. Eine Action rein, eine Action raus: Effects sollen nicht mehrere Actions hintereinander „orchestrieren“. Besser lässt man mehrere Reducer auf eine Erfolgs-Action hören.

4. Fallen

  • „catchError am Ende der Effect-Pipe reicht.“ → Falsch. Dann endet der äussere Strom. catchError gehört in den inneren Strom.
  • „switchMap ist immer richtig.“ → Nein. Für Schreiben kann es Requests abbrechen, die der Server schon verarbeitet.
  • „exhaustMap verhindert doppelte Bestellungen sicher.“ → Nur im Client. Der Server braucht Idempotenz.
  • „Ein Effect ohne Action-Ergebnis geht einfach so.“ → Nur mit dispatch: false. Sonst wird der Wert dispatcht.
  • „Effects laufen vor dem Reducer.“ → Nein. Sie sehen die Action nach dem Reducer.

5. Selbsttest

Warum?

Wo gehört catchError hin?

In den inneren Strom, im Flattening-Operator. Dort beendet ein Fehler nur den einen Request, nicht den Effect.

Was ist dispatch: false?

Eine Option für Effects ohne Ergebnis-Action, z. B. Navigation oder Logging. Sonst würde NgRx das Ergebnis dispatchen.

Darf ein Effect mehrere Actions zurückgeben?

Technisch ja. Besser ist eine Erfolgs-Action, auf die mehrere Reducer hören. Das bleibt nachvollziehbar.

Wie innen?

Was ist ein NgRx Effect?

Ein Observable-Strom, der auf Actions hört, Seiteneffekte ausführt und meist neue Actions zurückgibt. Er hält Reducer und Komponenten rein.

Was macht createEffect?

Es registriert einen Strom als Effect mit Metadaten wie dispatch, functional und useEffectsErrorHandler.

Was ist ein funktionaler Effect?

Ein Effect als Funktion mit { functional: true }. Abhängigkeiten kommen per inject() als Default-Parameter.

Was macht ofType?

Es filtert den Actions-Strom auf einen oder mehrere Action-Typen und typisiert das Ergebnis.

Wie registriert man Effects?

Mit provideEffects(...) in app.config.ts oder in den Providers einer Lazy Route.

Zahlen

Was passiert, wenn der äussere Strom einen Fehler hat?

Der Effect endet. NgRx resubscribed standardmässig bis zu 10 Mal, danach ist er tot.

Was ist tapResponse?

Ein Operator aus @ngrx/operators, der next, error und finalize sicher behandelt, ohne den Strom zu beenden. Seit NgRx 22 nur noch mit Objekt-Argument.

Vergleich

Wann switchMap?

Für Lesen und Suche: Nur das neueste Ergebnis zählt, alte Requests werden abgebrochen.

Wann concatMap?

Für Schreiben, wenn Reihenfolge wichtig ist und nichts verloren gehen darf.

Wann mergeMap?

Für unabhängige, parallele Vorgänge, z. B. mehrere verschiedene Einträge löschen.

Wann exhaustMap?

Wenn neue Auslöser ignoriert werden sollen, solange einer läuft. Beispiel: Login, Bezahlen.

Produktion

Wie testet man einen Effect?

Funktional: Effect-Funktion mit eigenem actions$ und Mock-Service aufrufen. Mit TestBed: provideMockActions. Für Timing Marble-Tests.

Szenario: Nach dem ersten Serverfehler lädt die Seite nie wieder. Ursache?

catchError steht im äusseren Strom, der Effect ist beendet. catchError in den inneren Strom verschieben und eine Failure-Action zurückgeben.

Szenario: Kunden erhalten Bestellungen doppelt. Was prüfen Sie im Effect?

Ob mergeMap genutzt wird. Auf exhaustMap wechseln, Button während des Requests sperren und am Server einen Idempotenz-Key prüfen.

Szenario: Nach dem Speichern friert der Browser ein, DevTools zeigen tausende gleiche Actions. Warum?

Ein Effect gibt die gefilterte Action selbst zurück, oft ein tap ohne dispatch: false. Option setzen oder eine eigene Ergebnis-Action zurückgeben.

Design

Wie liest ein Effect State?

Mit concatLatestFrom(() => store.select(sel)). Es liest lazy beim Eintreffen der Action.

Was sind OnInitEffects und OnRunEffects?

Interfaces für Klassen-Effects. OnInitEffects dispatcht beim Start eine Action. OnRunEffects steuert, wann die Effects laufen.

Mehr

Gerüst

  • Warum? Reducer und Komponenten bleiben rein. HTTP, Router und Storage laufen in Effects, getrennt und testbar.
  • Wie innen? Actions liefert Actions nach dem Reducer. ofType filtert, der Flattening-Operator startet den inneren Strom, das Ergebnis wird dispatcht.
  • Zahlen Der Error Handler resubscribed bis zu 10 Mal. tapResponse hat seit NgRx 22 nur noch die Objekt-Form. withEventHandlers hiess bis NgRx 20 withEffects.
  • Vergleich switchMap: abbrechen. concatMap: nacheinander. mergeMap: parallel. exhaustMap: neue ignorieren. Funktional vs Klasse. Effects vs rxMethod.
  • Produktion catchError aussen beendet den Effect. mergeMap bei Bestellen gibt Doppelte. Fehlendes dispatch: false gibt eine Endlosschleife.
  • Design Operator-Wahl ist Fachentscheidung. Fehler sind Actions. Server braucht Idempotenz. Effects klein halten.

Beispiel: funktionaler Effect mit Fehlerbehandlung und Test

// products.effects.ts
import { inject } from '@angular/core';
import { Actions, createEffect, ofType } from '@ngrx/effects';
import { Router } from '@angular/router';
import { catchError, exhaustMap, map, of, switchMap, tap, concatMap } from 'rxjs';

export const loadProducts = createEffect(
  (actions$ = inject(Actions), api = inject(ProductsApi)) =>
    actions$.pipe(
      ofType(ProductsPageActions.opened, ProductsPageActions.searchChanged),
      switchMap(() => api.load().pipe(                       // cancel stale reads
        map(products => ProductsApiActions.loadSuccess({ products })),
        catchError((e: HttpErrorResponse) =>               // INSIDE the inner pipe
          of(ProductsApiActions.loadFailure({ error: e.message })))))),
  { functional: true });

export const saveProduct = createEffect(
  (actions$ = inject(Actions), api = inject(ProductsApi)) =>
    actions$.pipe(ofType(ProductFormActions.saveClicked),
      concatMap(({ product }) => api.save(product).pipe(     // keep order, no loss
        map(saved => ProductsApiActions.saveSuccess({ product: saved })),
        catchError(e => of(ProductsApiActions.saveFailure({ error: e.message })))))),
  { functional: true });

export const navigateAfterSave = createEffect(
  (actions$ = inject(Actions), router = inject(Router)) =>
    actions$.pipe(ofType(ProductsApiActions.saveSuccess),
      tap(() => router.navigate(['/products']))),
  { functional: true, dispatch: false });

// app.config.ts
import * as productsEffects from './products.effects';
providers: [provideStore(), provideState(productsFeature), provideEffects(productsEffects)]

// products.effects.spec.ts
it('maps API error to loadFailure', () => {
  const api = { load: () => throwError(() => ({ message: 'boom' })) } as any;
  const actions$ = of(ProductsPageActions.opened());
  loadProducts(actions$ as any, api).subscribe(a => console.log(a));
});
{ error: 'boom', type: '[Products API] Load Failure' }

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). NgRx 22, Angular 22.

  1. Funktionale Effects mit { functional: true } sind einfache Funktionen. Abhängigkeiten kommen als Default-Parameter mit inject().
  2. Im Test übergibt man eigene Werte statt inject(). Kein TestBed nötig.
  3. catchError sitzt im switchMap. Der Fehler beendet nur den inneren HTTP-Strom, der Effect lebt weiter.
  4. saveProduct nutzt concatMap: Speichern darf nicht abgebrochen werden und soll in Reihenfolge laufen.
  5. dispatch: false: Der Navigations-Effect gibt keine Action zurück. Ohne diese Option würde NgRx die tap-Ausgabe (die Action selbst) erneut dispatchen, eine Endlosschleife.

Vergleich

  • switchMap vs exhaustMap: switchMap nimmt immer den neuesten Auslöser. exhaustMap behält den ersten und ignoriert neue.
  • concatMap vs mergeMap: concatMap seriell, sichere Reihenfolge. mergeMap parallel, schneller, keine Reihenfolge.
  • Effect vs Service-Aufruf in der Komponente: Effect entkoppelt die Komponente vom HTTP. Die Komponente dispatcht nur ein Ereignis. Preis: mehr Indirektion.
  • Effects vs SignalStore rxMethod: Gleiches RxJS-Muster, aber rxMethod ist eine direkte Methode am Store, ohne Actions.
  • Effects vs SignalStore-Events (withEventHandlers): Das Events-Plugin (stabil seit NgRx 21) bringt das Event-Muster in den SignalStore. withEventHandlers hiess bis NgRx 20 withEffects.
  • Funktional vs klassenbasiert: Funktional ist kürzer und einfacher zu testen. Klassen erlauben Lifecycle-Interfaces wie OnInitEffects.

In der Produktion

  1. Effect stirbt nach erstem Fehler: catchError steht im äusseren Strom. Danach reagiert der Effect nach 10 Fehlern gar nicht mehr. Lösung: catchError in den inneren Strom.
  2. Doppelte Bestellungen: mergeMap bei „Bestellen“, Nutzer klickt zweimal. Lösung: exhaustMap plus Button deaktivieren plus Idempotenz-Key am Server.
  3. Verlorene Speichervorgänge: switchMap beim Speichern, schnelle Folge-Speicherungen brechen ab. Lösung: concatMap.
  4. Endlosschleife: Effect gibt dieselbe Action zurück, die er filtert, oder dispatch: false fehlt bei tap. Browser hängt. Lösung: dispatch: false setzen, Actions sauber trennen.
  5. Veraltete Daten im Effect: withLatestFrom mit einem Selector, der früh abonniert. Lösung: concatLatestFrom.
  6. Effect nicht registriert: Funktion geschrieben, aber nicht in provideEffects. Nichts passiert, kein Fehler. Lösung: Registrierung prüfen, DevTools zeigen fehlende Success-Action.

Diagnose: Werkzeuge und Befehle

  • Redux DevTools: zeigt, ob nach opened ein loadSuccess oder loadFailure folgt, oder gar nichts.
  • Netzwerk-Tab: „canceled“-Requests zeigen switchMap-Abbrüche. Doppelte POSTs zeigen mergeMap.
  • tap({ next: console.log, error: console.error, complete: () => console.log('done') }): Ein „done“ im äusseren Strom heisst, der Effect ist tot.
  • provideMockActions, provideMockStore und Marble-Tests (TestScheduler.run) für Timing-Fehler.
  • @ngrx/eslint-plugin: Regeln avoid-cyclic-effects, no-multiple-actions-in-effects, prefer-concat-latest-from.

Senior-Punkte

  1. Operator-Wahl ist eine Fachentscheidung. „Was soll passieren, wenn der Nutzer zweimal klickt?“ Das beantwortet der Fachbereich, nicht RxJS.
  2. Fehler sind Actions. Jeder Seiteneffekt hat eine Failure-Action. So zeigt die UI Fehler über den Store, und das Log ist vollständig.
  3. Server-seitige Idempotenz ist nötig, auch mit exhaustMap. Client-Abbruch stoppt keinen Request, der schon unterwegs ist.
  4. Effects klein halten: eine Verantwortung pro Effect. Orchestrierung über Ereignisse, nicht über Ketten in einem Effect.
  5. Testbarkeit: Funktionale Effects mit injizierten Parametern testet man ohne TestBed. Das senkt die Hürde für Tests im Team.
