NgRx Entity

Kern: NgRx Entity verwaltet Listen von Objekten mit einer ID in einer normalisierten Form. Der State hat ein Array ids und ein Dictionary entities. Ein Adapter liefert fertige Methoden und Selectors. In SignalStore übernimmt withEntities diese Aufgabe.

Antwort-Muster

Frage: Was macht NgRx Entity, und warum nutzt man es?

  1. Mechanismus: Der State hält ids und entities. Der Adapter bietet Methoden wie addOne, setAll, updateOne und upsertOne für den Reducer.
  2. Zahl: Es gibt vier Selectors: selectIds, selectEntities, selectAll und selectTotal. withEntities liefert drei Signals.
  3. Trade-off: Zugriff per ID ist einfach, und es gibt keine doppelten Kopien. Dafür braucht man Selectors, um wieder Listen und Beziehungen zu bauen.
  4. Produktion: Ich setze sortComparer nur, wenn die Sortierung nötig ist. Ohne ist das Ändern schneller.

1. Von der Action zur Anzeige in 7 Schritten

  1. API-Antwort: Das Backend liefert ein Array von Objekten. Jedes hat eine ID.
  2. Action: Eine Action trägt das Array, zum Beispiel loadSuccess({ users }).
  3. Reducer: Der Reducer ruft eine Adapter-Methode auf. adapter.setAll(users, state) ersetzt die ganze Sammlung.
  4. Adapter: Der Adapter liest die ID mit selectId. Er füllt entities und ids. Mit sortComparer sortiert er ids.
  5. Neuer State: Der Adapter gibt den neuen State zurück, wenn sich etwas geändert hat. Sonst gibt er denselben State zurück.
  6. Selector: selectAll macht aus ids und entities wieder ein Array.
  7. Komponente: Die Komponente liest den Selector. Die Ansicht rendert die Liste.

Für Einzelzugriffe nutzt man selectEntities. Dann liest man entities[id] direkt, ohne die Liste zu durchsuchen.

2. Aufbau

  1. ids: Ein Array aller Primärschlüssel der Sammlung. Es legt die Reihenfolge fest.
  2. entities: Ein Dictionary der Objekte, geordnet nach Primärschlüssel.
  3. createEntityAdapter: Erzeugt den Adapter. Er hat die Optionen selectId und sortComparer.
  4. Adapter-Methoden: Sie ändern die Sammlung im Reducer. Jede gibt den neuen oder denselben State zurück.
  5. getSelectors: Gibt selectIds, selectEntities, selectAll und selectTotal zurück.
  6. withEntities: Die Variante für SignalStore. Sie fügt ids, entityMap und entities hinzu.

3. Details

  1. EntityState: Das Interface hat ids (string[] oder number[]) und entities (Dictionary). Man erweitert es um eigene Felder wie selectedUserId.
  2. Adapter-Optionen: selectId ist optional, wenn der Primärschlüssel id heisst. sortComparer sortiert die Sammlung. Man setzt false für unsortiert. Das ist laut Doku schneller bei CRUD-Operationen.
  3. Normalisieren: Man speichert jedes Objekt einmal im Dictionary. Der Zugriff per ID ist direkt. Andere Teile des States verweisen nur per ID darauf. So gibt es keine veralteten Kopien.
  4. add, set, upsert: addOne fügt hinzu. setOne fügt hinzu oder ersetzt. upsertOne fügt hinzu oder aktualisiert. updateOne aktualisiert teilweise. mapOne aktualisiert mit einer Funktion.
  5. Viele Objekte: Es gibt addMany, setMany, setAll, updateMany, upsertMany, map, removeMany und removeAll. removeMany nimmt IDs oder ein Prädikat.
  6. Gleicher State: Jede Methode gibt bei Änderung den neuen State zurück. Hat sich nichts geändert, gibt sie denselben State zurück. So rechnen Selectors dann nicht neu.
  7. Nur einfache Objekte: Entity fördert Plain Objects. Klasseninstanzen werden zu Plain Objects. So bleibt der State serialisierbar und in den Redux DevTools sichtbar.
  8. getSelectors: Es gibt vier Selectors: selectIds, selectEntities, selectAll und selectTotal. Man kombiniert sie mit einem Feature-Selector.
  9. withEntities: In SignalStore erwartet es eine id vom Typ string oder number. ids und entityMap sind State. entities ist ein Computed Signal.
  10. Updater in SignalStore: addEntity überschreibt vorhandene IDs nicht und wirft keinen Fehler. setEntity fügt hinzu oder ersetzt. upsertEntity führt Eigenschaften zusammen. updateEntity und removeEntity werfen bei unbekannter ID nicht.
  11. Eigene ID: Ohne id-Feld gibt man bei add*, set* und update* als zweites Argument { selectId } mit. remove* findet die ID selbst.
  12. Benannte Sammlungen: withEntities({ entity: type<Todo>(), collection: 'todo' }) benennt die Signals zu todoIds, todoEntityMap und todoEntities. Updater brauchen dann { collection: 'todo' }.

4. Fallen

  • „addEntity ersetzt einen vorhandenen Eintrag.“ → Falsch. Es überschreibt nichts und wirft keinen Fehler. Zum Ersetzen nimmt man setEntity, zum Zusammenführen upsertEntity.
  • „Im State liegt ein Array der Objekte.“ → Falsch. Im State liegen ids und das Dictionary. Das Array baut ein Selector, in SignalStore das Computed Signal entities.
  • „ids ist immer sortiert.“ → Falsch. Nur mit sortComparer. Mit false bleibt die Sammlung unsortiert.
  • „upsertEntity ersetzt das ganze Objekt.“ → Falsch. Es führt nur die gegebenen Eigenschaften mit dem vorhandenen Objekt zusammen.
  • „Entity speichert Klasseninstanzen mit Methoden.“ → Falsch. Entity macht daraus Plain Objects. Logik gehört nicht in den State.
  • „updateEntity wirft bei einer unbekannten ID.“ → Falsch. Es wirft keinen Fehler und tut nichts.

5. Selbsttest

Warum?

Warum normalisiert man Listen?

Jedes Objekt liegt einmal vor. Zugriff per ID ist direkt, und Updates treffen alle Stellen. Es gibt keine veralteten Kopien in verschachtelten Strukturen.

Warum sortComparer: false?

Ohne Sortierung muss der Adapter nach jeder Änderung nicht neu ordnen. Das ist schneller bei CRUD-Operationen.

Warum nur Plain Objects?

Der State bleibt serialisierbar und in den DevTools sichtbar. Klasseninstanzen mit Logik könnten sich selbst verändern.

Wie innen?

Was ist EntityState?

Ein Interface mit ids (Array der Primärschlüssel) und entities (Dictionary nach Primärschlüssel).

Was ist der Unterschied zwischen add, set und upsert?

add fügt hinzu. set fügt hinzu oder ersetzt. upsert fügt hinzu oder aktualisiert. In SignalStore führt upsertEntity Eigenschaften zusammen.

Was macht getSelectors?

Es erzeugt selectIds, selectEntities, selectAll und selectTotal für den Adapter-State.

Wie funktioniert withEntities?

Es fügt dem Store ids, entityMap und das berechnete entities hinzu. Man ändert sie mit Updatern über patchState.

Was passiert bei updateEntity mit unbekannter ID?

Nichts. Es wird kein Fehler geworfen.

Zahlen

Wie viele Selectors liefert getSelectors?

Vier: selectIds, selectEntities, selectAll und selectTotal.

Wie viele Signals fügt withEntities hinzu?

Drei: ids, entityMap und entities.

Welche Typen darf die ID haben?

string oder number.

Vergleich

Classic Adapter oder SignalStore Entities?

Der Adapter arbeitet im Reducer mit Actions. withEntities nutzt Updater mit patchState und Signals. Das Modell aus ids und entities ist gleich.

Array im State oder Entity?

Ein Array ist einfach bei kleinen Listen. Entity lohnt sich bei Zugriff per ID, vielen Updates und Bezügen zwischen Daten.

sortComparer oder Sortierung im Selector?

Der Comparer sortiert im State. Ein Selector sortiert nur für die Anzeige. Mehrere Sortierungen macht man im Selector.

setAll oder upsertMany?

setAll ersetzt die ganze Sammlung. upsertMany behält andere Einträge und ändert nur die genannten.

Produktion

Wie behandeln Sie Updates per WebSocket?

Mit upsertOne oder upsertEntity. Das fügt neue Objekte hinzu und aktualisiert vorhandene.

Szenario: Nach dem Laden sind alte Einträge noch in der Liste. Warum?

Der Code nutzt addMany oder upsertMany statt setAll. Diese behalten alte Einträge. Lösung: setAll beim vollständigen Neuladen.

Szenario: Die Liste hat nach einem Update eine falsche Reihenfolge. Was prüfen Sie?

Ob ein sortComparer gesetzt ist. Ohne ihn bleibt die Reihenfolge von ids wie eingefügt.

Szenario: Ein Update einer Bestellung ändert nichts. Woran denken Sie?

An eine falsche oder fehlende ID. updateEntity wirft bei unbekannter ID keinen Fehler. Der Fehler bleibt unbemerkt.

Design

Wann nutzt man Entity?

Bei Sammlungen von Objekten mit ID. Man liest sie oft und ändert sie einzeln. Sie hängen mit anderen Daten zusammen.

Wie modelliert man Beziehungen?

Ein Objekt speichert nur die ID des anderen. Ein Selector verbindet beide über selectEntities.

Szenario: Ein Optimistic Update soll bei Fehler zurückgehen. Wie bauen Sie das?

Man ändert mit updateOne und merkt sich den alten Wert. Schlägt der Request fehl, setzt man ihn mit setOne zurück.

Wie vergibt man IDs bei neuen Objekten?

Das Backend vergibt sie. Bis dahin nutzt man eine temporäre ID. Nach der Antwort ersetzt man das Objekt per setOne und entfernt die temporäre.

Mehr

Gerüst

  • Warum? Listen mit ID normalisiert speichern, mit fertigen Methoden und Selectors.
  • Wie innen? ids und entities. createEntityAdapter mit selectId und sortComparer.
  • Zahlen Vier Selectors. Drei Signals bei withEntities. ID ist string oder number.
  • Vergleich add, set, upsert, update. Adapter gegen SignalStore. Selector-Sortierung gegen sortComparer.
  • Produktion Alte Einträge bleiben. Falsche Reihenfolge. Update mit falscher ID tut nichts.
  • Design Beziehungen per ID. WebSocket mit upsert. Plain Objects im State.

Beispiel: Adapter im Reducer und withEntities im Store

// klassisch
export const adapter = createEntityAdapter<User>({
  sortComparer: (a, b) => a.name.localeCompare(b.name),
});
export const initialState = adapter.getInitialState({
  selectedUserId: null as string | null,
});
export const userReducer = createReducer(
  initialState,
  on(UserActions.loadSuccess, (s, { users }) => adapter.setAll(users, s)),
  on(UserActions.rename, (s, { id, name }) =>
    adapter.updateOne({ id, changes: { name } }, s)),
);
export const { selectAll, selectEntities } = adapter.getSelectors();

// SignalStore
export const TodosStore = signalStore(
  withEntities<Todo>(),
  withMethods((store) => ({
    add(todo: Todo) { patchState(store, addEntity(todo)); },
    done(id: number) {
      patchState(store, updateEntity({ id, changes: { completed: true } }));
    },
  })),
);

Nicht ausgeführt.

  1. getInitialState: Erzeugt ids und entities und ergänzt das eigene Feld selectedUserId.
  2. setAll: Ersetzt die ganze Sammlung nach dem Laden. Der Comparer sortiert ids nach Name.
  3. updateOne: Ändert nur den Namen. Alle anderen Felder bleiben.
  4. withEntities: Der Store hat ids, entityMap und entities. addEntity und updateEntity ändern sie.

Vergleich

  • Array im State: Einfach, aber Zugriff per ID kostet eine Suche. Updates müssen die Liste neu bauen.
  • EntityState: Dictionary und ID-Liste. Gut bei Zugriff per ID und Teil-Updates.
  • Classic Adapter: Läuft im Reducer mit Actions. Gut für den Global Store.
  • withEntities: Läuft im SignalStore mit Updatern. Gleiche Form, weniger Code.
  • Selectors: Bauen aus ids und entities wieder Listen. Sortierung für die Anzeige gehört oft hierher.
  • NgRx Data: Baut auf Entity auf und liefert Services für Entity-Sammlungen.

Produktion

  1. Alte Einträge bleiben: addMany und upsertMany löschen nichts. Lösung: setAll beim vollständigen Neuladen.
  2. Stille Fehler: updateEntity und removeEntity werfen bei falscher ID nicht. Lösung: Tests und Logging an Grenzen.
  3. Falsche Reihenfolge: Ohne sortComparer bleibt die Einfüge-Reihenfolge. Lösung: Comparer setzen oder im Selector sortieren.
  4. Eigene ID vergessen: Heisst der Schlüssel nicht id, kennt Entity ihn nicht. Lösung: selectId beim Adapter oder in den Updatern mitgeben.
  5. Zu viel im State: Grosse Antworten mit verschachtelten Objekten kopieren Daten. Lösung: normalisieren und Beziehungen per ID.
  6. Klasseninstanzen im State: Methoden gehen verloren. Lösung: Plain Objects speichern, Logik in Funktionen.

Diagnose: Werkzeuge und Befehle

  • Redux DevTools: Zeigen State und Actions. Man sieht ids und entities nach jeder Aktion.
  • Selectors testen: Einen State mit getInitialState bauen und selectAll prüfen.
  • Reducer testen: Eine Action anwenden und prüfen, ob ids und entities stimmen.
  • Gleicher State: Prüfen, ob ein No-op denselben State zurückgibt, mit toBe.
  • Store-Test: Bei SignalStore Methoden aufrufen und store.entities() prüfen.

Senior-Punkte

  1. Normalisieren lohnt sich nicht immer.: Bei kleinen, nur gelesenen Listen reicht ein Array. Entity zahlt sich bei Zugriff per ID und Updates aus.
  2. Die IDs gehören dem Backend.: Eine stabile, eindeutige ID ist die Grundlage von Entity.
  3. Sortierung ist ein Anzeigeproblem.: Meist sortiert ein Selector. Der Comparer im State nur, wenn eine Reihenfolge überall gilt.
  4. Updates sind still.: Fehlende IDs fallen nicht auf. Tests und Prüfungen an der Grenze helfen.
  5. Wähle die Operation bewusst.: add, set und upsert verhalten sich bei vorhandener ID verschieden. Das ist die häufigste Fehlerquelle.
  6. Entity und SignalStore teilen das Modell.: Wer ids und entities versteht, versteht beide Varianten.
