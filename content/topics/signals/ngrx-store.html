NgRx Store: Actions, Reducer, Selectors

Kern: NgRx Store ist ein globaler, Redux-artiger Zustandsspeicher für Angular. Der Zustand ist ein unveränderliches Objekt, das nur Reducer als Antwort auf Actions ändern. Komponenten lesen über memoized Selectors und schicken Actions. Das löst das Problem von verteiltem, schwer nachvollziehbarem Zustand in grossen Apps. Aktuell ist NgRx 22 (August 2026, braucht Angular 22); die NgRx-Major folgt der Angular-Major.

1. Wo sitzt der Store?

  1. Action: ein Objekt, das ein Ereignis beschreibt. Beispiel: { type: '[Product Page] Opened' }.
  2. Reducer: eine reine Funktion (state, action) => newState. Beispiel: setzt loading: true.
  3. Store: hält den einen Zustandsbaum und ist ein Observable davon. Beispiel: { products: { items: [], loading: false } }.
  4. Selector: eine reine, gecachte Lesefunktion auf den Zustand. Beispiel: selectVisibleProducts.
  5. Effects: hören auf Actions und machen Seiteneffekte wie HTTP. Sie schicken neue Actions zurück (eigene Seite).

2. Die Reise einer Action (die Geschichte zum Merken)

  1. Ereignis. Der Nutzer öffnet die Produktseite. Die Komponente ruft store.dispatch(ProductPageActions.opened()).
  2. Dispatcher. Die Action landet im ActionsSubject. Das ist der eine Strom aller Actions.
  3. Reducer. Jeder registrierte Feature-Reducer bekommt die Action. Nur wer ein passendes on(...) hat, ändert etwas. Die anderen geben den alten State unverändert zurück.
  4. Neuer State. Der Reducer liefert ein neues Objekt. Unveränderte Teile behalten ihre Referenz (structural sharing).
  5. Selectors. Jeder Selector vergleicht seine Eingaben mit dem letzten Aufruf. Gleiche Referenzen → gecachtes Ergebnis, keine Neuberechnung.
  6. View. Nur Komponenten, deren Selector ein neues Ergebnis liefert, rendern neu.
  7. Effects. Erst danach sehen Effects die Action. Sie starten z. B. den HTTP-Call und schicken später loadSuccess.

Diese Richtung ist immer gleich: Unidirectional Data Flow. State fliesst nach unten, Actions nach oben.

3. Beispiel: ein Feature mit createActionGroup und createFeature

// products.actions.ts
import { createActionGroup, emptyProps, props } from '@ngrx/store';
export const ProductsPageActions = createActionGroup({
  source: 'Products Page',
  events: {
    'Opened': emptyProps(),
    'Search Changed': props<{ query: string }>(),
  },
});
export const ProductsApiActions = createActionGroup({
  source: 'Products API',
  events: {
    'Load Success': props<{ products: Product[] }>(),
    'Load Failure': props<{ error: string }>(),
  },
});

// products.feature.ts
import { createFeature, createReducer, createSelector, on } from '@ngrx/store';
interface State { items: Product[]; query: string; loading: boolean; error: string | null }
const initialState: State = { items: [], query: '', loading: false, error: null };

export const productsFeature = createFeature({
  name: 'products',
  reducer: createReducer(initialState,
    on(ProductsPageActions.opened, s => ({ ...s, loading: true, error: null })),
    on(ProductsPageActions.searchChanged, (s, { query }) => ({ ...s, query })),
    on(ProductsApiActions.loadSuccess, (s, { products }) => ({ ...s, items: products, loading: false })),
    on(ProductsApiActions.loadFailure, (s, { error }) => ({ ...s, error, loading: false })),
  ),
  extraSelectors: ({ selectItems, selectQuery }) => ({
    selectVisible: createSelector(selectItems, selectQuery,
      (items, q) => { console.log('filter run'); return items.filter(p => p.name.includes(q)); }),
  }),
});

// app.config.ts
providers: [ provideStore(), provideState(productsFeature),
             provideStoreDevtools({ maxAge: 25, logOnly: !isDevMode() }) ]

// component
store = inject(Store);
visible = this.store.selectSignal(productsFeature.selectVisible);
ngOnInit() { this.store.dispatch(ProductsPageActions.opened()); }
ProductsPageActions.opened().type        → "[Products Page] Opened"
ProductsApiActions.loadSuccess.type      → "[Products API] Load Success"
// Store nach opened:            { products: { items: [], query: '', loading: true,  error: null } }
// Store nach loadSuccess(2 P.): { products: { items: [..2..], query: '', loading: false, error: null } }
// Konsole: "filter run" einmal je Änderung von items oder query,
//          nicht bei opened (items und query unverändert)

Erwartetes Ergebnis (laut Doku, nicht ausgeführt). NgRx 22, Angular 22.

  1. createActionGroup baut den Typ aus [source] Event und macht den Namen zu camelCase: „Load Success“ → loadSuccess.
  2. createFeature erzeugt automatisch selectProductsState, selectItems, selectQuery, selectLoading, selectError.
  3. opened ändert nur loading und error. items und query behalten ihre Referenz. Darum rechnet selectVisible nicht neu.
  4. selectSignal liefert ein Angular-Signal. Das Template liest visible() ohne async-Pipe.

4. Details, die Interviewer fragen

  1. Action Hygiene: Actions sind Ereignisse, keine Befehle. Gut: [Products Page] Opened. Schlecht: setLoading. Die Quelle im Namen zeigt im DevTools, wer was ausgelöst hat.
  2. Nicht wiederverwenden: Eine Action pro Ereignis und Quelle. Zwei Seiten, die laden, schicken zwei verschiedene Actions. Mehrere Reducer dürfen auf dieselbe Action hören.
  3. createAction: Einzelne Action: createAction('[Auth] Logout') oder mit props<{...}>(). createActionGroup bündelt mehrere mit derselben Quelle.
  4. Reducer sind rein: Keine HTTP-Calls, kein Date.now(), kein Math.random(). Gleiche Eingabe gibt gleiche Ausgabe. Das macht Time-Travel-Debugging möglich.
  5. Immutabilität: Immer neues Objekt mit Spread. In der Entwicklung prüfen Runtime Checks das: strictStateImmutability und strictActionImmutability sind standardmässig an (eingefrorene Objekte).
  6. Weitere Runtime Checks: strictStateSerializability, strictActionSerializability, strictActionWithinNgZone, strictActionTypeUniqueness sind optional einschaltbar. strictActionWithinNgZone ist in zoneless Apps (Default seit Angular 21) sinnlos.
  7. createSelector: Nimmt bis zu 8 Eingabe-Selectors und eine Projektor-Funktion. Er cached das letzte Ergebnis (Cache-Grösse 1).
  8. Memoization-Regel: Gleiche Eingabe-Referenzen → kein Neurechnen. Darum ist Immutabilität Pflicht: Mutation täuscht den Cache.
  9. Selector mit Parameter: Die alten props-Selectors sind deprecated; laut NgRx-22-Typen werden sie in v23 entfernt. Heute: Factory-Funktion selectById = (id) => createSelector(...), die man pro ID merkt.
  10. selectSignal vs select: store.select(sel) liefert ein Observable. store.selectSignal(sel) (seit NgRx 16) liefert ein Signal. Beide nutzen dieselben Selectors.
  11. createFeature: Fasst Name, Reducer und Selectors zusammen. extraSelectors fügt abgeleitete Selectors hinzu. Registrierung mit provideState(feature).
  12. Lazy Loading: provideState in den providers einer Lazy Route. Der Feature-State erscheint erst beim ersten Besuch.
  13. Meta-Reducer: Wrapper um alle Reducer. Beispiel: Logging, oder State bei Logout zurücksetzen.
  14. dispatch mit Signal: Seit NgRx 19 kann dispatch eine Funktion bekommen, die ein Signal liest. Bei jeder Änderung wird neu dispatcht.
  15. @ngrx/entity: createEntityAdapter normalisiert Listen in ids + entities und liefert CRUD-Helfer und Selectors.

5. Vergleich

  • NgRx Store vs Service mit BehaviorSubject: Store gibt feste Regeln, DevTools, Time Travel, Effects. Service ist weniger Code, aber jeder kann Zustand anders ändern.
  • NgRx Store vs SignalStore: Store ist global, Action-basiert, indirekt. SignalStore ist lokal oder global, methodenbasiert, direkt, mit weniger Boilerplate.
  • Selector vs computed: Beide sind memoized. Selector arbeitet auf dem globalen State und ist in DevTools sichtbar. computed arbeitet auf beliebigen Signals.
  • createAction vs createActionGroup: Gleiches Ergebnis. Group hat weniger Wiederholung und erzwingt eine Quelle.
  • NgRx vs NGXS/Akita: NgRx ist im Angular-Umfeld am weitesten verbreitet und hält mit jeder Angular-Major Schritt. Akita ist nicht mehr aktiv gepflegt.

6. In der Produktion

  1. Mutation im Reducer: state.items.push(p). In Dev wirft der Runtime Check Cannot add property ... object is not extensible. In Prod fehlen die Checks, die UI aktualisiert sich nicht. Lösung: Spread oder Entity-Adapter.
  2. Selector rechnet immer neu: Projektor gibt filter()-Ergebnis zurück, Eingabe-Selector erzeugt jedes Mal ein neues Objekt. Lösung: Eingabe-Selectors nur auf vorhandene State-Teile zeigen lassen.
  3. Alles in den Store: Formular-Eingaben, Dropdown offen/zu, jede Liste. Viel Boilerplate, viele Actions. Lösung: Nur geteilten, langlebigen Zustand global halten.
  4. Generische Actions: [Products] Load von fünf Stellen. Im DevTools ist der Auslöser nicht erkennbar. Lösung: Action pro Quelle.
  5. Nicht serialisierbarer State: Date, Klassen-Instanzen, Funktionen im Store. DevTools und Rehydration brechen. Lösung: nur einfache JSON-Daten, Datum als ISO-String.
  6. DevTools in Prod mit voller Historie: Speicher wächst, sensible Daten sichtbar. Lösung: logOnly: !isDevMode(), maxAge, actionSanitizer/stateSanitizer.

7. Diagnose: Werkzeuge und Befehle

  • Redux DevTools (Browser-Erweiterung) mit provideStoreDevtools(): Action-Log, State-Diff, Time Travel, Export/Import.
  • ng add @ngrx/store@latest und ng add @ngrx/store-devtools@latest: Installation mit Konfiguration.
  • ng generate @ngrx/schematics:feature products: erzeugt Actions, Reducer, Selectors, Effects als Gerüst.
  • provideStore(reducers, { runtimeChecks: { strictStateSerializability: true } }): zusätzliche Prüfungen in Dev.
  • Tests: Reducer als reine Funktion testen: reducer(initialState, action). Selectors mit selector.projector(...) ohne Store testen. provideMockStore und overrideSelector für Komponenten.
  • @ngrx/eslint-plugin: Regeln wie no-reducer-in-key-names, prefer-action-creator, no-store-subscription.

8. Senior-Punkte

  1. Indirektion ist der Preis. Store lohnt sich bei viel geteiltem Zustand, vielen Teams und dem Bedarf an Nachvollziehbarkeit. Für eine CRUD-Maske ist es zu viel.
  2. Actions als Ereignisse machen das System erweiterbar: Ein neues Feature hört auf eine bestehende Action, ohne den Auslöser zu ändern.
  3. Normalisierter State (ids + entities) verhindert Duplikate und widersprüchliche Kopien desselben Objekts.
  4. Server-State vs Client-State: Viel „State“ ist nur ein Cache von Server-Daten. Dafür ist ein globaler Store nicht immer das beste Werkzeug.
  5. Signals-Integration: selectSignal verbindet bestehenden Store mit Signal-Komponenten. Kein Rewrite nötig.
  6. Konventionen festlegen: Ordnerstruktur, Action-Namen, wer was in den Store legt. Ohne Regeln wird ein Store zur globalen Variable mit Extra-Schritten.

10. Fallen

  • „Actions sind Befehle wie setProducts.“ → Falsch. Actions beschreiben Ereignisse mit Quelle: [Products API] Load Success.
  • „Der Reducer lädt die Daten.“ → Nein. Reducer sind rein. HTTP gehört in Effects.
  • „Effects laufen vor dem Reducer.“ → Nein. Erst Reducer, dann Effects.
  • „Selectors rechnen bei jedem State-Wechsel neu.“ → Nein. Nur wenn ihre Eingaben neue Referenzen haben.
  • „Runtime Checks schützen mich in Produktion.“ → Nein. Sie laufen nur im Dev-Modus.
  • „Alles gehört in den Store.“ → Nein. Lokaler UI-Zustand bleibt in der Komponente.

11. Fragen

Was ist NgRx Store?

Ein globaler, Redux-artiger State-Container für Angular. Zustand ist unveränderlich, Reducer ändern ihn als Antwort auf Actions, Selectors lesen ihn.

Was ist Unidirectional Data Flow?

Daten fliessen in eine Richtung: Komponente → Action → Reducer → State → Selector → Komponente. Das macht Änderungen nachvollziehbar.

Was ist eine Action?

Ein Objekt mit type und optionalem Payload. Es beschreibt ein Ereignis mit seiner Quelle.

Was ist gute Action Hygiene?

Ereignisse statt Befehle, Quelle im Typ, keine Wiederverwendung über verschiedene Auslöser hinweg.

Was macht createActionGroup?

Es erzeugt mehrere Action Creators mit gemeinsamer Quelle. Der Typ ist [Source] Event, der Name camelCase.

Was ist ein Reducer?

Eine reine Funktion (state, action) => newState. Mit createReducer und on() pro Action.

Warum müssen Reducer rein sein?

Gleiche Eingabe muss gleichen State geben. Das erlaubt Tests ohne Mocks, Time Travel und verlässliche Memoization.

Was macht createFeature?

Es bündelt Feature-Name, Reducer und automatisch generierte Selectors je State-Feld. extraSelectors ergänzt eigene.

Was ist ein memoized Selector?

Ein Selector, der sein letztes Ergebnis cached. Er rechnet nur neu, wenn die Eingabe-Selectors neue Referenzen liefern.

Wie macht man einen Selector mit Parameter?

Mit einer Factory: selectById = (id) => createSelector(selectEntities, e => e[id]). Die alten props-Selectors sind deprecated und sollen in NgRx 23 wegfallen.

select oder selectSignal?

select liefert ein Observable, selectSignal ein Signal. In neuen Signal-Komponenten selectSignal.

Was sind Runtime Checks?

Prüfungen im Dev-Modus. Standardmässig an: State- und Action-Immutabilität. Optional: Serialisierbarkeit, NgZone, eindeutige Action-Typen.

Was ist ein Meta-Reducer?

Eine Funktion, die alle Reducer umhüllt. Beispiel: Logging oder State beim Logout zurücksetzen.

Wie lädt man Feature-State lazy?

Mit provideState(feature) in den Providers einer Lazy Route.

Was bringen die Redux DevTools?

Action-Log, State-Diffs, Time Travel und Export. In Prod mit logOnly und maxAge begrenzen.

Wie testet man Reducer und Selectors?

Reducer direkt mit State und Action aufrufen. Selectors über projector(). Komponenten mit provideMockStore und overrideSelector.

Was ist @ngrx/entity?

Ein Adapter für normalisierte Listen (ids + entities) mit Methoden wie addOne, upsertMany und fertigen Selectors.

Welche NgRx-Version passt zu Angular 22?

NgRx 22. Die NgRx-Major folgt der Angular-Major; @ngrx/store 22 verlangt @angular/core ^22.

Wann ist NgRx Store zu viel?

Bei wenig geteiltem Zustand, kleinen Teams oder einfachen CRUD-Seiten. Dann reichen Signals im Service oder ein SignalStore.

Szenario: Ein Reducer pusht in ein Array, lokal kommt ein Fehler, in Prod passiert nichts. Was ist los?

Der Runtime Check friert State in Dev ein, darum der Fehler. In Prod fehlt der Check, aber die Referenz bleibt gleich, Selectors melden nichts. Lösung: neues Array mit Spread.

Szenario: Eine Liste rendert bei jeder Action neu, auch bei fremden Features. Warum?

Ein Selector liefert jedes Mal ein neues Objekt, z. B. weil ein Eingabe-Selector map oder Spread macht. Eingabe-Selectors auf echte State-Teile zeigen lassen und Projektoren prüfen.

Szenario: Im DevTools sieht man 50 Mal „[Products] Load“ und weiss nicht, wer es auslöst. Was ändern Sie?

Eigene Actions pro Quelle, z. B. [Products Page] Opened und [Cart Page] Refresh Clicked. Der Effect hört auf beide mit ofType.
